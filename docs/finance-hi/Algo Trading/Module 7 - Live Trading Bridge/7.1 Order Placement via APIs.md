# 7.1 Order Placement via APIs

## Data API ≠ Trading API

Module 3 wali sab APIs READ-ONLY thi — sirf candles padhna.

Trading API ek alag level hai:

| | Data API | Trading API |
|---|---|---|
| Kaam | Candles padhna | Orders BHEJNA |
| Galti pe | Kuch nahi | **Real paisa loss** |
| Setup | Basic keys | IP whitelist + permissions + margins |

Isliye brokers trading-keys ko extra carefully dete hain.

Aur tu bhi extra carefully use karega!

## Pehle Order Anatomy Samjho

Har broker ka order roughly SAME fields maangta hai:

```text
ORDER =
    instrument   → kis stock pe?
    side         → BUY ya SELL?
    order_type   → MARKET / LIMIT / STOPLOSS?
    quantity     → kitne shares?
    product      → INTRADAY ya DELIVERY?
```

Ek-ek karke:

### order_type — Teen Flavours

| Type | Matlab | Analogy |
|---|---|---|
| `MARKET` | ABHI current price pe turant kharido | "Jo bhi mile le lo!" |
| `LIMIT` | "SIRF is price pe ya better" | "₹100 se sasta hi chahiye, warna nahi!" |
| `STOPLOSS` | Trigger cross hote hi activate | "Girne lage toh bachao!" |

```text
MARKET   → execution GUARANTEED, price nahi
LIMIT    → price CONTROLLED, execution guaranteed nahi
```

### quantity — Lot Rules Dhyan Se!

Stocks mein = number of shares (10, 50...)

F&O mein = LOTS! (Reliance futures ka 1 lot = jaise 250 shares)

Galat lot-multiple = order REJECT ho jayega!

### product — Do Types

```text
INTRADAY (MIS)  → shaam ko auto-close (position teri raat ko nahi rehti)
DELIVERY (CNC)  → shares TERE paas rehte hain

Algo traders mostly INTRADAY use karte hain!
```

## Ruk — Abhi Tak Kya Hua?

```text
✅ Order = instrument + side + type + qty + product
✅ MARKET = turant | LIMIT = apni price pe | SL = trigger
✅ F&O mein LOTS count hote hain, shares nahi!
✅ MIS = intraday (auto-close), CNC = delivery
```

## Order Lifecycle — SABSE Important Concept!

Yeh concept jo beginners MISS karte hain:

```text
Tumne order BHEJA          → "placed"     (broker ne mila)
Exchange ne queue kiya     → "open"       (match hone ka wait)
Match ho gaya              → "filled" ✅  (deal done!)
(ya)                       → "rejected" ❌ (na ho paya)
```

**SABSE ZAROORI LINE:**

> **"Order placed successfully" ≠ "position ban gayi!"**

Placement sirf RECEIPT hai!

Limit order poore din OPEN pada reh sakta hai — fill bina.

Isliye serious systems **fill confirmation** check karte hain:

*"order book se poocho — mera order hua ya nahi?"*

### Rejection Ke Common Reasons

```text
❌ Margin kam pada
❌ Galat quantity (lot rules!)
❌ Market band hai
❌ Token/session expire ho gaya
```

## Auth Ke Teen Styles (3.9 Ka Practical!)

Module 3 mein teeno style ke examples dekhe the —

trading pe bhi SAME patterns lagte hain:

### Style 1 — Direct Token (Dhan-style)

Sabse simple: token header mein bhejo:

```python
import requests

headers = {
    "access-token": MY_TOKEN,          # badge dikhaya
    "Content-Type": "application/json"
}

payload = {                             # order ki details
    "securityId": "2885",              # Reliance ka number
    "transactionType": "BUY",
    "orderType": "MARKET",
    "quantity": 10,
    "productType": "INTRADAY"
}

resp = requests.post("https://api.dhan.co/v2/orders",
                     json=payload, headers=headers)
print(resp.json())                      # orderId wapas milti hai!
```

Line-by-line:

```text
headers   → envelope pe likha "yeh authorized hai"
payload   → order ki poori details ek dict mein
requests.post(...) → waiter ko order de diya!
resp.json() → broker ka jawab (orderId + status)
```

### Style 2 — Session Login (Kite/Angel/Groww-style)

Login flow se token generate hota hai (M3 mein kiya),

phir wahi token har trading call ke saath:

```python
# Zerodha example:
kite.place_order(
    tradingsymbol="RELIANCE",
    transaction_type="BUY",
    quantity=10,
    product="MIS",
    order_type="MARKET"
)
```

Pattern: **login.py se session import → orders.py mein functions!**

### Style 3 — HMAC Signature (Delta/crypto-style)

Crypto exchanges ek EXTRA layer maangte hain: **signature**.

Har request ko tere SECRET se sign karna padta hai —

server verify karta hai ki request SACH MEIN tere system se aayi!

```python
import hmac, hashlib

signature = hmac.new(secret.encode(),
                     message.encode(),
                     hashlib.sha256).hexdigest()
```

Concept simple:

```text
Secret network pe KABHI nahi jaata.
Sirf usse banaya hua SIGNATURE jaata hai.
Server same secret se verify kar leta hai.
```

(Practical mein `delta-rest-client` jaisi libraries yeh INTERNALLY karti hain —

par ab tu jaanta hai andar kya ho raha hai! 🔓)

### Style 4 (Bonus) — MT5 Desktop

MetaTrader5 mein orders desktop-terminal ke through jaate hain:

```python
result = mt5.order_send(request_dict)

if result.retcode != mt5.TRADE_RETCODE_DONE:
    print(f"FAILED! retcode = {result.retcode}")   # error code batata hai kyun
```

`retcode` = MT5 version of fill-confirmation.

**"order_send ka retcode check karo"** — yeh rule yaad rakhna!

## 🛡️ Safety Protocol — Pehli Order Se Pehle!

Yeh checklist NON-NEGOTIABLE hai:

```text
1. DEMO ACCOUNT PEHLE!
   Delta demo / MT5 demo / broker paper-trading.
   Real paise pe direct entry = pagalpan.

2. MINIMUM QUANTITY se shuru
   1 share/lot. System proof hone de!

3. IDEMPOTENCY GUARD
   Same signal do baar aaya? DOUBLE order na lage!
   (check: position already open hai?)

4. POSITION STATE TRACK
   System ko pata ho: abhi position open hai ya nahi?
   (4.5 wala flag — ab REAL money pe!)

5. KILL SWITCH ready
   Emergency script jo SAB positions turant close kar de!

6. LOGS HAR JAGAH
   Har order-request + response file mein save.
   Debugging ke liye GOLD.
```

## Nutshell

Trading API = data API + real-money risk + stricter auth. Order anatomy: instrument/side/type(MARKET-LIMIT-SL)/qty(lots!)/product(MIS-CNC). **Lifecycle: placed → open → filled/rejected; PLACEMENT ≠ FILL — confirmation mandatory!** Auth styles: direct-token, session-login, HMAC-signature (+MT5 retcode). Safety: demo-first, min-qty, idempotency, state-tracking, kill-switch, logs. Structure: tokens/login/orders/server split.

## What It Is NOT

- ❌ **"Order placed" ≠ "paisa lag gaya."** Placement sirf RECEIPT hai — LIMIT order din bhar open reh sakta hai, MARKET slippage pe fill hota hai, margin-kam pe REJECT bhi ho sakta hai. Status-check har serious system ka part hai.
- ❌ **MARKET order price guarantee NAHI deta.** Guaranteed EXECUTION deta hai, price nahi! Illiquid moments me slippage badhiya aa sakti hai (2.1 microstructure). Price chahiye toh LIMIT — par phir fill ka risk tumhara.
- ❌ **Signature system = secret safe NAHI hota.** HMAC sirf TRANSIT protection hai (beech me tamper na ho). Secret FILE se leak ho gayi toh sab bekaar — storage discipline (agli file!) utni hi zaroori hai.

**In Your Own Words**

1. Data API vs Trading API ka risk-farq?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Data API read-only hai — galti se max GALAT DATA aata hai, paisa safe. Trading API account MODIFY karti hai — galat side, galat qty, duplicate order = DIRECT monetary loss! Isliye trading APIs pe extra auth layers (IP-whitelist, scopes, signatures) aur testing protocol alag hai: demo-first, min-qty, kill-switch. Risk-asymmetry hi treatment ka difference hai.

</details>

2. MARKET vs LIMIT vs STOPLOSS — kab kaunsa?

<details>
<summary>Sample Jawab</summary>

**Jawab:** MARKET = execution-certainty chahiye, price secondary (SL-exits, urgent square-off). LIMIT = price-control critical, wait kar sakte ho (entries at level, no-slippage). STOPLOSS = trigger-cross pe automatic exit (risk-management). Algo strategies me combo common: LIMIT entries + STOPLOSS exits. Trade-off hamesha: certainty-of-fill vs certainty-of-price.

</details>

3. "Placement ≠ fill" — lifecycle explain karo.

<details>
<summary>Sample Jawab</summary>

**Jawab:** Stages: PLACED (API accepted) → OPEN (exchange queue me, unfilled) → FILLED (matched!) YA REJECTED (margin/qty/rules issue). "Placed ≠ fill" matlab API-success sirf RECEIPT hai — LIMIT order din-bhar open pada reh sakta hai; market-order slippage pe fill hota hai; kuch margin-short hone se reject ho jaate hain. Isliye production systems ORDER-STATUS polling/alerts rakhte hain aur position-state unse update karte hain.

</details>

4. HMAC signature kya solve karta hai, kya NAHI?

<details>
<summary>Sample Jawab</summary>

**Jawab:** SOLVE karta hai: request-authenticity + integrity — server verify kar pata hai ki request tumhare secret-wale system se aayi AUR beech-me modify nahi hui (secret network-pe travel nahi karta, sirf usse banaya hash jaata hai). SOLVE NAHI karta: secret-STORAGE security — agar secret file se leak ho gayi (GitHub push!), koi bhi valid signatures banalega. Transit-crypto ≠ storage-security; isliye .gitignore/env-vars discipline ALAG se chahiye.

</details>

5. Pehli live order se pehle ki 6 safety steps?

<details>
<summary>Sample Jawab</summary>

**Jawab:** (1) DEMO/paper-account pe poora flow test, (2) minimum quantity — 1 lot/share, (3) idempotency-guard — duplicate-signal pe double-order BLOCK, (4) position-state tracking + recovery-plan (server-restart scenario!), (5) kill-switch ready — emergency flatten-script, (6) full logging — har request/response record. In ke bina live jaana = blindfolded driving on highway!

</details>
