# 5.0 Concept — Disconnect/Reconnect Simulation

> **Yaar, ek brutal truth: real feeds pakad mein atak sakti hain. WebSocket drop, network fail, auth timeout — sabse pehle toh app crash nahi chahiye.** 
> Lab mein: pause/resume simulates this.

## The Problem

```typescript
// ❌ Naive approach — feed stops, machines lose everything
feed.stop()  // clearInterval → no more ticks
// Machines think "nothing happened" — but prices kept moving!
// On resume: machine starts at wrong prices
```

## The Solution

State must be **separate** from the feed:

```
Feed (ticks) ←→ Position Machines (state)
  ↓                ↑
Pauses/stops     Remembers state
Resumes          Still watches same symbol
```

**Key insight:** Machines don't die when the feed pauses. They just stop receiving ticks — like a paused WebSocket.

## Real Example — TradeStack streamer.ts

When `streamer.ts` loses WebSocket:
1. **Feed layer stops** — no more ticks coming in
2. **Position machines keep running** — they still track what they last saw
3. **Reconnect logic** — streamer reconnects, resumes subscribing
4. **Catch-up** — backfill recent ticks if buffer was small

Your simulation:
1. **Feed pauses** — `clearInterval` stops the timer
2. **Machines keep state** — `in_position` stays `in_position`
3. **Feed resumes** — `setInterval` restarts, prices continue from last known
4. **No catch-up needed** — you never lost data since it was all in memory

## What It Is NOT

- **NOT production reconnect.** Real code uses exponential backoff, max retry limits, connection health checks
- **NOT data recovery.** Real streamer has a ring buffer for missed ticks. Your simulation has no data loss because there's no network.

## Why This Matters for Interviews

When asked "what happens if WebSocket disconnects?":
1. **Your answer:** "The feed layer (streamer.ts) detects the disconnect and calls reconnect-with-backoff. Meanwhile, position machines keep their state — they don't crash on missing ticks. On reconnect, the streamer resumes subscribing to each symbol's channel."
2. **Why it's convincing:** You built the same pattern — feed stops, machines keep state, feed resumes. You felt the disconnect/resume cycle yourself.

## Dost ka tip

> "Maine pehle socha — disconnect pe machine ka state reset ho jayega toh best hoga. NOPE. Reset = position lost = real money waste. State must persist."

## Bridge

`streamer.ts` method `reconnectWithBackoff()`:
- Clears current WebSocket
- Waits (backoff: 1s → 2s → 4s → cap at 30s)
- Reconnects
- Resubscribes all symbols
- **Machines never stopped running**

Your `feed.resume()` = their `reconnectWithBackoff().then(() => resubscribe())`.
