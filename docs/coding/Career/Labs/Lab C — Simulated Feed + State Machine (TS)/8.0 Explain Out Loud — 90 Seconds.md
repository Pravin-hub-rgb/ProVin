## The Setup

> "So I built a simplified version of TradeStack's live-trading feed. The goal wasn't to recreate WebSocket connections — it was to understand **how event-driven feeds with state machines work** before reading the real code."

## The Two Key Sentences (MEMORIZE THESE)

### Sentence 1 — Concurrency
> **"One process, N subscriptions, callbacks per tick — the event loop is doing the concurrency."**

**Breakdown:**
- **One process:** My simulation runs in a single Node.js process — no threading
- **N subscriptions:** Feed emits for AAPL, MSFT, GOOGL — each has its own PositionMachine listening
- **Callbacks per tick:** Every 500ms, the interval fires one callback that loops through all symbols
- **Event loop is doing the concurrency:** JavaScript's single-threaded event loop handles all of this sequentially — no race conditions, no locks needed

### Sentence 2 — Double Entries Blocked
> **"The state machine guarantees a stock is in exactly one phase, so double entries can't happen."**

**Breakdown:**
- **Exactly one phase:** Each `PositionMachine` has a `status` field that is `idle`, `watching`, `in_position`, or `exited` — never two at once
- **State machine guarantees:** The `ALLOWED_TRANSITIONS` table enforces this — `enter()` from `in_position` is rejected
- **Double entries can't happen:** Even if the feed sends two signals back-to-back, the second `enter` call checks status → it's already `in_position` → rejected

## The Bridge Sentence (Connect to TradeStack)

> "In the real `streamer.ts`, the same pattern applies — `extends EventEmitter`, emits `tick` events, and a `Map<string, SymbolHandler>` routes each tick to the right handler. The differences are: WebSocket instead of `setInterval`, protobuf messages instead of JSON, and `reconnect-with-backoff` for reliability. But the architecture — feed + routing + per-symbol state machines — is identical."

## 90-Second Script (Memorize)

```
"I built a simulated live-trading feed in TypeScript to understand TradeStack's real streamer.ts pattern.

[5s - Concept] The core is an EventEmitter feed — it emits tick events for 3 symbols on a timer. Each symbol has its own state machine that subscribes only to its ticks. This is the publish-subscribe pattern: the feed broadcasts, machines decide what to process.

[25s - Concurrency] One process, N subscriptions, callbacks per tick — the event loop does the concurrency. There's no threading. When the interval fires every 500ms, it loops through all symbols, emits a tick for each. Each PositionMachine's onTick handler runs sequentially in the event loop.

[30s - State Machine] Each PositionMachine has 4 states: idle → watching → in_position → exited. Transitions are validated against a table. The state machine guarantees a stock is in exactly one phase, so double entries can't happen. If a signal arrives while already in_position, the transition is rejected.

[15s - Pause Resume] When the feed pauses (simulating disconnect), machines keep their state. No data loss. When feed resumes, ticks flow again to machines that never reset. This mirrors streamer.ts's reconnect-with-backoff pattern.

[15s - Bridge] The real streamer.ts uses WebSocket + protobuf instead of setInterval + JSON, but the architecture is identical: EventEmitter feed, Map routing, per-symbol state machines."

Total: ~90 seconds
```
