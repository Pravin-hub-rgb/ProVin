# 2.0 Concept — State Machines

> **Think about it: if you never track a trade's state, what happens?** Double entries can occur, or two entries in the same position. Chaos.

## What Is a State Machine (Plain English)

A system where:
1. **An object is in exactly one state** at any time
2. **Transitions** are defined (State A → State B)
3. **Invalid transitions** are rejected (if it's not in the table, don't allow it)

## Real Example — Position States

A stock's position in trading is always in one state:

```
IDLE — not watching this symbol
  ↓ watch
WATCHING — watching for entry signal
  ↓ signal triggers
IN_POSITION — entered the trade
  ↓ exit signal
EXITED — closed the trade
  ↓ reset
IDLE
```

Each state is **exclusive**. You can't be WATCHING AND IN_POSITION at the same time.

## Code Representation

This is the same pattern taught with React's `useReducer`:

```typescript
// React Batch 5.5 concept
type Status = "idle" | "watching" | "in_position" | "exited"
```

## What It Is NOT

- **NOT a database state.** This only tracks in memory — restart = reset
- **NOT a persistence layer.** Nothing is saved — if the process stops, everything starts again from IDLE
- **NOT complex business logic.** This just defines "allowed moves" — whether any transition is legal or not

## Key Rule

> **Every transition table has source + destination.** "watching → in_position" allowed, "idle → exited" not allowed.

## Why This Matters for Interviews

`continuation/state-machine.ts` in TradeStack has **11 states** — same concept, more rows. If you understand the 4-state machine, the 11-state one feels easy.

## A senior dev's tip

> "Build 4 states first, understand them. Then read the real code — when you see 11 states, a table will form in your head."
