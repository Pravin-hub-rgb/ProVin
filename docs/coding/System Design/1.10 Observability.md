## Where We Left Off

1.9 explained how code reaches all those servers. But running correctly *today* says nothing about tomorrow — something will eventually break or slow down. This doc covers the second side-strip from 1.2: **how we watch it**.

## The Problem — "It's Slow" Is Not an Answer

Support says orders take 5 seconds instead of 1. Which box is guilty?

```
browser → DNS? → load balancer? → backend code? → PostgreSQL?
        → Redis? → the queue? → a worker? → the email service?
```

Ten boxes, each running on machines you can't see. SSH-ing into them one by one and staring at terminals doesn't scale — and "nothing looks wrong here" proves nothing. What's needed: the system itself must be able to answer three questions, with data:

1. **Is something wrong?** (a number moved)
2. **What exactly is slow?** (which step in the journey)
3. **What does the system say happened?** (the errors it printed)

## The Three Kinds of Evidence

**Metrics** — numbers over time: requests per second, latency percentiles (p95 — 95% of requests are faster than this), error rate, queue depth (1.8's backlog signal!). The tool: **Prometheus**. It works by **pulling**: on a schedule, it asks every service's `/metrics` endpoint "current numbers?" and stores the answers. If you know polling — `setInterval` fetching a status rather than waiting for an event — you know Prometheus's model.

**Traces** — the journey of *one request* through the boxes, with time spent at each step. The tool: **Jaeger**. Conceptually: `console.time()` around each step of processing — but per request and across services. Every request gets a **trace ID**; each box attaches the same ID to its own data as the request passes through. Then one trace reads like:

```
backend: 40ms
  → PostgreSQL query: 3,200ms   ← THERE. It's the database.
  → queue push: 2ms
```

"It's slow" just became "Postgres queries from the backend are slow" — a place, not a mood.

**Logs** — the text the code prints: error stack traces, warnings, events. For store-sized scale, logs need *search* ("all errors containing timeout, last hour") — and that's a job for a search engine. **OpenSearch — the same tool from 1.6** — indexes logs the way it indexed products. One tool, two jobs, same inverted-index idea.

**Grafana** is the face of it all: dashboards that graph the Prometheus metrics — the screen on the wall during an incident.

## The Wiring — OpenTelemetry

None of this is magic: the app must **emit** the data. Metrics endpoints must exist, trace IDs must be attached, logs must be written. **OpenTelemetry (OTel)** is the standard library for that instrumentation — one integration that produces all three kinds, flowing like this:

```
backends / workers  ──metrics──►  Prometheus ──►  Grafana (dashboards)
                    ──traces───►  Jaeger          (which step is slow)
                    ──logs─────►  OpenSearch      (searchable history)
```

## The Golden Rule, Applied

- **Problem that forced observability in:** at a dozen boxes, "it's slow" has no answer without collected data
- **New problems it brings:**
  - **The app must be instrumented** — OTel wiring is code, in every service; retrofitting is work
  - **Data volume** — metrics and logs for everything, forever, gets expensive; retention and detail levels are real decisions
  - **Alert fatigue** — alert on everything and the team stops reading alerts; choosing *what* matters is a skill of its own

## What It Is NOT

- **Not just logging** — logs tell you what code *said*; metrics say something *moved*; traces show *where* time went. All three, one story
- **Not automatic** — without instrumentation, the system is silent; OTel must be wired in
- **Not a debugging session** — it's permanent infrastructure that answers questions before the pager goes off
- **Not only for incidents** — the same dashboards drive capacity planning ("traffic doubled; queue depth trends say when workers run out")

## Check Yourself

1. The report is "orders are slow." Match each question to its evidence type: Is something wrong? Which step? What did it print?

   <details>
   <summary>Sample Answer</summary>

   "Is something wrong?" → metrics: latency percentiles or error rate moved in Prometheus/Grafana. "Which step?" → traces: one request's trace in Jaeger shows the time per box — e.g. backend 40ms, the Postgres query 3,200ms. "What did it print?" → logs: searchable in OpenSearch for the exact error the code emitted at that moment.
   </details>

2. How does a trace know it's looking at one request across ten different services?

   <details>
   <summary>Sample Answer</summary>

   Every request carries a trace ID; each service that touches the request attaches the same ID to its own trace data. Jaeger assembles all entries with that ID into one timeline. It's console.time per step — but per request and across machines, joined together by the shared ID.
   </details>

3. Prometheus pulls metrics on a schedule. Which JavaScript concept is that model, and what's the opposite model?

   <details>
   <summary>Sample Answer</summary>

   Polling — like setInterval fetching a status endpoint, versus waiting for an event/callback to arrive. Prometheus scrapes each service's /metrics endpoint on a schedule and stores the numbers; the opposite (push/event) model exists too, but pull is Prometheus's way — and it's resilient: a service that's down just misses scrapes, visibly.
   </details>

4. Why did log search not need a new tool in the diagram? Which earlier doc made it free?

   <details>
   <summary>Sample Answer</summary>

   Log search is the same problem as product search — find text fast across millions of entries, ranked and filtered. OpenSearch (1.6) already provides exactly that with its inverted index, so logs flow into the same kind of engine. One tool, two jobs — the search workload, not the product, defines the tool.
   </details>
