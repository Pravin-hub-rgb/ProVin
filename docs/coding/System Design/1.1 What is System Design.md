You've built apps before. A React frontend, maybe a small backend, a database — and it works. You demo it, your friends try it, everything runs fine. Then a question sneaks in: what happens when this stops being 10 users and becomes 10,000? Or 10,00,000? Does the same app just… keep working?

That question is where System Design begins.

## Where We Left Off

The [Course Plan](../00%20Course%20Plan.md) made two promises: every tool in this course arrives because **a problem forced it in**, and every tool **brings a new problem along**. This doc delivers the definition behind those promises — what System Design actually is, and the one mental lens you'll use for the entire course.

## The Problem It Solves

Here's the situation every growing app faces. Two things change as an app gets used for real:

1. **Data grows** — more users means more rows in the database, more files uploaded, more records everywhere. Your app holds more stuff this year than last year.
2. **Traffic grows** — more requests every second. The same "get product page" query that ran 50 times a day now runs 50,000 times a second.

An app that handles both at 10 users can fall apart at 10,000. Not because the code is bad — because the **arrangement** of the pieces can't cope. One server holding everything was fine; now it's the bottleneck.

**System Design is deciding how the pieces — servers, databases, caches, queues — fit together, so the app keeps working as data and traffic grow.**

Read it twice. That's the whole definition. Everything else in this course is detail on top of it.

## You've Already Done a Tiny Version of This

This isn't a new skill — it's one you've already used, in a smaller frame.

When you build a React app and the state grows, you make arrangement decisions: should this state live in this component? Lifted to a parent? Put in context? You move data around so the app stays workable as it grows. You didn't learn a new tool for that — you learned to **arrange** what exists so the growing app still works.

System Design is the same muscle at server scale. Instead of "where should this state live?", the questions become: where should this data live? How many servers should run this? Which work should wait in a queue? Same thinking, bigger pieces.

## What It Is NOT

- **Not memorizing tools.** "Learn Kubernetes, Kafka, Redis" is backwards. You learn the *problems*, and the tools show up as their solutions. A person who memorized 10 tools but can't name the problem each one solves knows nothing usable.
- **Not a language or framework.** Nothing to install in this batch. It's arrangement thinking, not syntax.
- **Not only for giant companies.** The same decisions exist at small scale — "should this run on one server or two?" is already System Design.
- **Not cloud-specific.** AWS, GCP, your own VPS — the concepts are the same; the buttons differ.
- **Not an architect-only job.** Every backend developer makes these decisions eventually. You're just learning them consciously now.

## The Two Forces

Every system design decision traces back to the two forces from earlier:

- **Data growth** — forces decisions about *where data lives* (which storage, how many copies)
- **Traffic growth** — forces decisions about *how requests are handled* (how many servers, who decides)

Keep an eye on these two as the course moves. Every box in the diagrams ahead exists to serve one of them.

## The Golden Rule — The Lens for Everything

Here's the rule this course runs on, the same one from the Course Plan:

> **A problem forces every tool in — and every tool brings a new problem along.**

Concretely, for every tool you meet in this course, you should be able to answer two questions:

1. **What problem forced this tool in?**
2. **What new problem did it bring?**

Example with a tool you know: a caching layer makes reads fast (the problem it solves) but can serve stale data when the underlying data changes (the new problem it brings). This trade-off pattern — solve one thing, inherit another — repeats for every single tool in this course. By the last doc of this batch, it'll be second nature.
