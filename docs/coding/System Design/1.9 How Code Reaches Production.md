## Where We Left Off

## The Problem — Manual Deploys Drift

Picture deploying by hand. Five backends, five releases a day:

```
SSH into server 1 → copy new code → restart
SSH into server 2 → copy new code → restart
... (server 7 gets a different Node version, because it was set up on a different day, by a different person)
```

Two failure modes appear fast:

- **Config drift** — servers that were *supposed* to be identical quietly stop being identical. Different patch levels, different environment variables, different everything. Code that works on server 3 fails on server 7, and nobody knows why
- **Scale** — manual work doesn't compound. The 5th server is tedious; the 50th is impossible

Both problems are the same disease: **the servers' setup exists only in reality — in clicked settings and local history — not anywhere reviewable or repeatable.** The fix comes in two layers: package the app so it runs identically anywhere (Docker), then automate the path from code to running containers (CI/CD), then define the servers themselves as reviewable code (Terraform).

## Docker — One Image, Identical Everywhere

First problem: code that runs on your laptop fails on a server. Different OS, different Node version, a missing environment variable — "works on my machine" is really "works with my machine's exact setup."

**Docker** packages the app with *everything it needs* — runtime, dependencies, system libraries, config — into one **image**. The image runs the same on any machine that runs Docker. No drift, because there's nothing per-machine to drift.

The mental model is one you already own: **a class and its instances.**

```
Docker image  = class     (a blueprint — not running, immutable, one definition)
Container     = instance  (a running copy — many can exist, all from the same blueprint)
```

Backends 1..N in the 1.2 diagram are N containers built from **one image** — the way N instances come from one class. Identical by construction, not by discipline.

Images need a home: a **registry** (ECR, Docker Hub) — effectively GitHub for images. `push` the image once; every server `pull`s the exact same one.

## CI/CD — The Automated Path From Push to Running

With images in place, the deploy becomes a pipeline — a sequence that runs itself on every `git push`:

```
git push
   │
   ▼
CI:  run tests ──fail──► block. Nothing deploys.
   │ pass
   ▼
build Docker image → push to registry
   │
   ▼
CD:  roll the new image out to the servers
```

- **CI (Continuous Integration)** — on every push: run the test suite, build the image, publish it to the registry. An automated quality gate; broken code physically cannot proceed
- **CD (Continuous Deployment)** — the new image gets rolled onto the servers. And here 1.3 pays off: the rollout is **rolling** — a few servers get the new image at a time, the **load balancer health-checks** them, and only when they're healthy do the next ones update. The store never goes down to deploy

So "the same Docker image" from 1.2 is now fully explained: N containers, one image, deployed by a pipeline that rolls them out a few at a time behind the health-checking load balancer.

## Terraform — The Servers Themselves as Code

Docker fixes drift *inside* the servers. But the servers, the network, and the load balancer were all created by hand — clicked into existence in a cloud console. Clicked settings have the same disease as manual deploys: nobody can review them, and they can't be recreated.

**Terraform** writes that infrastructure as code:

```hcl
resource "aws_instance" "backend" {
  count         = 5              # five identical backends
  instance_type = "t3.medium"
}
```

Five lines that say "five backend machines of this size." The whole setup — machines, network, load balancer — lives in files: reviewable in git, versioned, and reproducible from zero. Need an identical setup in a new region? Run the same files. This is **infrastructure as code**.

## ECS / Kubernetes — Who Runs the Containers

One layer below the pipeline sits the system that actually *runs* the containers: **ECS** or **Kubernetes**. It decides which machine runs which container, restarts containers that die (health checks — again — but at the container level), and scales counts up and down. Two conveniences ride on top of it: **Helm** (templates so dozens of services don't hand-write near-identical config) and **ArgoCD** (GitOps — the git repo declares the desired state, and the system continuously makes the cluster match it).

These are Batch 4 territory — for now, know the role: *the container orchestrator*.

## The Golden Rule, Applied

- **Problem that forced this stack in:** manual deploys drift and don't scale; clicked infrastructure can't be reviewed or recreated
- **New problems it brings:**
  - **The pipeline itself is a system** — it can break, and now it's on call too
  - **Bad code can deploy automatically** — tests passing doesn't mean the code is good; automatic deploys make bad releases *faster* too (strategies like canary rollouts — Batch 4)
  - **Complexity moves up a level** — Kubernetes is powerful and famously deep; that's a real cost, and part of why small apps skip it

## What It Is NOT

- **Docker is not a virtual machine** — containers share the host's OS kernel and start in milliseconds; VMs virtualize a whole computer. Lighter, faster, less isolation
- **CI/CD is not one tool** — Jenkins, GitHub Actions, GitLab CI are implementations; the *pipeline* is the idea
- **Kubernetes is not mandatory** — a small app on one server needs none of this; orchestrators arrive when many services and machines force them
- **Terraform is not the only IaC** — CloudFormation, Pulumi; same idea, different dialects
