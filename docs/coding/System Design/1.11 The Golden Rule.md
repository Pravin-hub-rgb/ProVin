## The Ledger — One Table for the Whole Batch

The golden rule said: *a problem forces every tool in — and every tool brings a new problem along.* Filled in from the batch, box by box:

| Box | Problem that forced it in | New problem it brought |
|---|---|---|
| DNS | requests need IPs, browsers hold names | a lookup layer that must stay correct and current (1.3) |
| Load Balancer | one server saturates and dies alone | now the most critical box; pushes state out of servers (1.3) |
| N identical backends | traffic growth, survival | they must be truly identical — solved by Docker (1.9) |
| PostgreSQL | orders must survive and stay correct | repeated identical reads slow it down (1.4) |
| Redis | the DB drowning in repeated reads | stale copies — cache invalidation (1.5) |
| OpenSearch | typo-proof, ranked search at scale | another copy to keep in sync (1.6) |
| S3 | binary files clog the database | URLs become data; lifecycle discipline (1.7) |
| Queue + Workers | customers wait for slow work | at-least-once → idempotency; backlogs (1.8) |
| Docker + CI/CD | manual deploys drift; "works on my machine" | automatic deploys ship bad code fast too (1.9) |
| Terraform | clicked infrastructure can't be reviewed or recreated | infrastructure code is code — it has bugs too (1.9) |
| Observability | "it's slow" needs data to answer | the app must be instrumented; data costs (1.10) |

Read the right column top to bottom — that's the golden rule *in motion*: every solution left a residue, and the residue shaped what came next.

## The Sequence — How a Store Grows Into This Map

The map also reads as a story in order. At 10 users: one server, one PostgreSQL. Then, one pain at a time:

1. **Traffic grows** → load balancer + N identical backends (1.3)
2. **Repeated reads pile up** → Redis cache (1.5)
3. **Search needs typos and ranking** → OpenSearch (1.6)
4. **Images clog the database** → S3 (1.7)
5. **Customers wait for slow work** → queue + workers (1.8)
6. **Deploys drift and break** → Docker, CI/CD, Terraform (1.9)
7. **"It's slow" needs answers** → Prometheus, Jaeger, Grafana, OTel (1.10)

Nobody designs the full-grown map on day one — and nobody should. Each step was *earned* by a pain.

## The Rule Cuts Both Ways

The most practical lesson in this batch is the one 1.6 said out loud: **no problem, no tool.** A store with 500 users needs exactly none of the boxes past DNS, LB, and Postgres — and adding "for the future" infrastructure is how projects drown in complexity they didn't earn. The rule that justifies every tool *limits* every tool: you should be able to name the pain that forced each box in. If you can't, the box is cargo.

## The Batch 1 Contract — Check Yourself Against It

The Course Plan promised: by the end of Batch 1, the diagram reads like a **story, not a map**. That's the self-check — for every box, without notes:

1. What problem forced it in?
2. What new problem did it bring?
3. What breaks if you delete it?

If you can answer all three for every row of the ledger, you have the whole picture — and the deep dives of Batch 2+ will be *adding depth to boxes you already understand*, not meeting strangers.

## What It Is NOT

- **Not the end of the course** — Batch 1 built the premise; Batch 2+ goes deep into each box (scaling, replication, CDNs, sessions, Kafka, Kubernetes)
- **Not a recipe to build all of this** — it's the map of *why*; the *how* of each box is later batches' job
- **Not a fixed architecture** — real systems differ; the *rule* is constant, the boxes vary
- **Not memorization** — the ledger is derivable. Forget a row? Ask "what pain does this box end?" and it comes back

2. Apply the golden rule to a tool this batch never covered: a CDN. What problem would force it in, and what might it bring?

   <details>
   <summary>Sample Answer</summary>

   Forcing problem: product images (1.7) are served from one region — users far away get slow loads, because S3 is regional. A CDN copies files to servers near users, so images load fast everywhere. New problems it brings: another copy of content to keep fresh (the invalidation disease from 1.5, now at global scale), plus a new cost and a new box that can serve stale content. Same rule, brand-new box — that's the test of owning the rule.
   </details>

3. A teammate proposes adding Kafka "because big companies use it." Answer with this batch's rules.

   <details>
   <summary>Sample Answer</summary>

   Two answers. First, no problem, no tool (1.11): "big companies use it" is not a forcing problem — what pain does OUR system have? Second, scope: Kafka is an event-streaming system for many-consumer, high-scale, replayable flows (teased in 1.8) — a real system with real operational cost. If the current queue handles the workload, adding Kafka buys complexity without ending any pain. Revisit when a real forcing problem appears.
   </details>

4. What does it mean for the diagram to read "like a story, not a map"? Which can you do now that you couldn't in 1.2?

   <details>
   <summary>Sample Answer</summary>

   A map says what's *where*; a story says *why* each thing is there and what it cost. In 1.2 you could recite the boxes; now you can retell the growth sequence — traffic forced the LB and N backends, repeated reads forced the cache, typos forced the search engine, and so on — and for each box state its forcing problem, its residue, and what would break without it. Depth comes in later batches; the whole picture came first.
