Last doc ended at a breaking point: 10,000 identical reads per second hitting PostgreSQL, each one a disk read, the whole app slowing down. The reads are identical — same query, same unchanged result. Asking the database again and again is the waste. This doc adds the copy that ends it.

## Where We Left Off

1.4 established PostgreSQL as the **source of truth** — and showed how repeated reads of the same data become the first bottleneck at scale. The fix has a name: a **cache**.

## The Idea — Answer From Memory, Not From Disk

A **cache** is a copy of data kept in **memory (RAM)**, placed in front of the database. The whole trick is one comparison:

```
PostgreSQL: correct, durable … on disk. Built to survive, not to sprint.
Redis:      a copy in RAM. Built to sprint.
```

Memory reads are orders of magnitude faster than disk reads. So if the answer is already sitting in RAM, the database never gets asked.

**Redis** is the tool that holds these copies — a **key-value store** that lives in memory:

```
"product:1001"  →  { name: "iPhone", price: 79999, stock: 42 }
"product:1002"  →  { name: "Headphones", price: 2499, stock: 310 }
```

One key (like `product:1001`), one value, RAM-fast.

## The Read Pattern — How Requests Use It

The backend's read path changes shape. For a product page request:

```
request comes in
   │
   ▼
check Redis for "product:1001"
   │
   ├── found (cache HIT)  → return the copy. Done. Database never touched.
   │
   └── not found (cache MISS)
          │
          ▼
       read from PostgreSQL (the truth)
          │
          ▼
       store a copy in Redis
          │
          ▼
       return the data
```

First request pays the database read. Every repeat after that is served from memory. The 10,000-identical-reads-per-second storm from 1.4 now hits Redis — which exists to sprint — and PostgreSQL only sees the occasional first read.

This pattern — check the copy, fall back to the truth, refill the copy — is the most common caching shape there is. You'll meet it in every system that has a cache.

## The Trap — The Copy Goes Stale

Now the golden rule earns its keep, because this speed comes with a real problem.

The iPhone's price changes in PostgreSQL: ₹79,999 → ₹74,999. The database has the new truth. But Redis still holds the old copy — and the next 10,000 readers get **the old price**.

The copy stopped matching the truth. This is the central disease of caching, and it has a name: **cache invalidation** — deciding when and how to update or remove stale copies.

If you know Git, you know this disease already: a branch that hasn't pulled from main still "works" — it just shows old code, and trusting it causes bugs. A cache without invalidation is exactly that: a stale branch everyone reads.

The two basic moves (deep patterns come in Batch 3):

- **TTL (time-to-live):** every copy carries an expiry — after 60 seconds it's gone, and the next read refills from the truth. Simple; the cost is up-to-a-minute of staleness
- **Invalidate on write:** when the backend updates the price in PostgreSQL, it also deletes/updates the Redis copy. Next read refills fresh. The cache and the write go through the same door

## The Golden Rule, Applied

- **Problem that forced Redis in:** the database drowning in repeated identical reads
- **New problems it brings:**
  - **Stale copies** — invalidation is now a real engineering problem, not an edge case
  - **More than one place holds the data** — the source of truth still rules (1.4), but every copy is another thing to keep consistent
  - **A Redis that dies** — misses refill from the database, so the app survives it (one reason copies must never be treated as the truth)

And notice what Redis is NOT a fix for: the copy still only helps **reads**. A brand-new product, a user-specific page — anything not cached yet — still pays the database read. Caching absorbs repeats; it doesn't erase first reads.

## What It Is NOT

- **Not a replacement for PostgreSQL.** Redis holds copies; Postgres holds the truth. "Redis instead of a database" loses orders
- **Not durable by default.** Memory copies exist to be fast and disposable — eviction and expiry are normal, not failures
- **Not just for product pages.** Sessions, rate counters, hot anything — same pattern. (Redis also gets used for other jobs — Batch 3/4 territory)
- **Not automatically correct.** Every cached read is a bet that the copy is fresh — invalidation strategy is what backs that bet

## Check Yourself

1. Walk the read path for `product:1001` on a cache HIT and on a cache MISS. What does the database see in each case?

   <details>
   <summary>Sample Answer</summary>

   HIT: backend checks Redis, the key exists, the copy is returned — the database sees nothing. MISS: the key isn't in Redis, so the backend reads the truth from PostgreSQL, stores a copy in Redis, then returns. First read pays the database; repeats don't.
   </details>

2. The price changes in PostgreSQL but customers still see the old one. What happened, and what is this called?

   <details>
   <summary>Sample Answer</summary>

   Redis still holds the old copy — the copy stopped matching the source of truth. This is a stale cache, and fixing it is cache invalidation: on write, update or delete the cached copy (or let a TTL expire it), so the next read refills from the truth.
   </details>

3. Redis crashes completely. Does the store go down? What actually happens?

   <details>
   <summary>Sample Answer</summary>

   No — it slows down. Every read becomes a cache MISS, so requests fall through to PostgreSQL. The database sees the full read load again (the 1.4 problem), response times climb, and Redis gets refilled as reads happen. Painful, but not data loss — which is exactly why Redis must hold copies, never the truth.
   </details>

4. Why does caching fix the "10,000 identical reads" problem but not the "100,000 different users' pages" problem?

   <details>
   <summary>Sample Answer</summary>

   A cache absorbs repeats — the same key read many times. 10,000 reads of one product page are one key, so one copy serves all of them. 100,000 user-specific pages are 100,000 different keys, each read a few times — barely any repeats, so each entry would be a cold MISS. Caching rewards popularity and repetition; it does nothing for one-time reads.
   </details>

## What's Next

Caching fixed repeated reads. But the store has a different read problem now: a customer types **"wirless headphone"** — typo and all — and still expects the right products, best match first. PostgreSQL can't serve that well at scale. That's a different job for a different tool: **1.6 — OpenSearch**.
