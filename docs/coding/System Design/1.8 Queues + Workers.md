The order is saved in PostgreSQL — but the job isn't done. A confirmation email must go out, an invoice must be generated, the warehouse must be told, analytics must record the event. And the customer is still staring at a loading spinner. This doc hands off the slow work so the customer doesn't wait for it.

## Where We Left Off

1.7 completed the data layer — truth, cache, search, files. So the backend can now save an order in milliseconds. The question is what happens *around* that save: the order triggers several follow-up jobs, and each one can be slow.

## The Problem — The Customer Waits for Work They Don't Care About

Placing an order triggers:

- a **confirmation email** (an external email service — can take seconds)
- an **invoice PDF** (generation cost)
- a **warehouse notification** (another system, another network call)
- an **analytics event** (another write, another service)

If the backend does all of this inline, inside the request:

```
click → save order (fast) → send email (2s) → build invoice (1s)
      → notify warehouse (1s) → … → THEN respond: 4-5 seconds
```

Worse than slow: if the email service is having a bad day, **every order placement fails or hangs** — checkout, the most critical flow in the store, is now coupled to the least critical one. The customer doesn't care about the email at click time. They care that the order went through.

You already know this move from JavaScript: when a click handler does heavy work synchronously, the UI freezes — so you push the work out (`setTimeout`, an async task) and let it happen after. The backend needs the same escape hatch. That's the queue.

## The Queue — A Waiting Line for Tasks

A **queue** is a service that holds **messages** — small packets of work. The backend's flow changes to:

```
click → save order (fast) → push "send confirmation for order 5001" to the queue
      → respond: "Order placed"          (under 1 second)
```

The slow work didn't disappear — it's now someone else's job to do it later.

## Workers — Who Actually Does the Work

A **worker** is a separate program that sits next to the queue, picks up tasks, and processes them in the background:

```
backend ── "send confirmation, order 5001" ──►  ┌─────────┐
   │                                            │  Queue  │
   ▼                                            └────┬────┘
responds in < 1s                                     │  workers pick up tasks
                                        ┌────────────┼────────────┐
                                        ▼            ▼            ▼
                                   Worker 1      Worker 2      Worker 3
                                   (emails)      (invoices)    (warehouse)
```

Three properties make this shape work:

- **Durability** — the queue *holds* the tasks. If every worker crashes, tasks wait in line; nothing silently vanishes
- **Acknowledgment** — a worker says "done" only *after* finishing a task. If a worker crashes mid-task, the unacknowledged message goes back to the queue and another worker picks it up
- **Independent scaling** — 10× orders on a sale day? Add workers. Backends and workers scale separately, because they're separate programs

## The Trap — The Same Task Can Arrive Twice

Here's where the golden rule bites. Replay the acknowledgment story: a worker sends the email, and *then* crashes — before saying "done". The queue has no way to know the email went out. So it delivers the task again, and the customer gets **two confirmation emails**.

The queue's delivery promise is **at-least-once** — never zero times, but sometimes more than once. So every task must be written to survive running twice. That property is **idempotency**: an operation that produces the same result whether it runs once or ten times.

You've already built this, just in a different layer: the **double-submit guard** in a React form — disable the button after the first click so two clicks don't create two orders. Same disease, server side. The standard fix: each task carries a unique key (`order:5001:confirmation`), and the worker checks "did I already do this key?" before doing the work.

## The Golden Rule, Applied

- **Problem that forced the queue in:** the customer waits for slow work, and checkout gets coupled to flaky services
- **New problems it brings:**
  - **Double delivery** — at-least-once means tasks can rerun; idempotency is now mandatory, not optional
  - **Backlogs** — if workers are slower than tasks arrive, the queue grows and work falls behind; queue depth becomes something to *monitor* (1.10)
  - **No ordering guarantees** — "task 1 before task 2" is not a promise a basic queue makes

One step beyond this doc: when one event needs to reach *many* different consumers with replay and huge scale, a queue stops being enough — that's **Kafka**, an event stream, and it gets its own treatment in Batch 4. For now: queue = a durable task list.

## What It Is NOT

- **Not a cron job** — cron runs "every day at 3am"; a queue runs "there's work right now, process it"
- **Not a data store** — messages are work items, consumed and gone; the order data itself lives in PostgreSQL
- **Not magic parallelism** — workers are separate processes; the concurrency is exactly as many workers as you run
- **Not exactly-once by default** — the at-least-once promise plus idempotent workers *behaves* like exactly-once, and that combination is the real-world standard
