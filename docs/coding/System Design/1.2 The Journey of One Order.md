## The Setup

An online store. A customer browsing on `shop.com`. They find a product, click **Place Order**. From that click to the confirmation email, here's everything that happens — drawn first, explained right after.

## The Request Path

```
                     ┌─────────────────────┐
                     │       Customer      │
                     │  (browser: shop.com)│
                     └──────────┬──────────┘
                                │ clicks "Place Order"
                                ▼
                     ┌─────────────────────┐
                     │         DNS         │   domain → IP address
                     └──────────┬──────────┘
                                ▼
                     ┌─────────────────────┐
                     │    Load Balancer    │   sends traffic to healthy servers only
                     └──────────┬──────────┘
                ┌───────────────┼───────────────┐
                ▼               ▼               ▼
          ┌───────────┐   ┌───────────┐   ┌───────────┐
          │ Backend 1 │   │ Backend 2 │   │ Backend N │  ← all run the SAME Docker image
          └─────┬─────┘   └─────┬─────┘   └─────┬─────┘

  ┌──────────────────────────────────────────────────────────┐
  │                       DATA LAYER                         │
  │                                                          │

  └─────────────────────────────┬────────────────────────────┘

                     │      Queue      │ ─────► │      Workers        │

                     │  waits here)    │        │ warehouse · events │
                     └─────────────────┘        └────────────────────┘
```

## What Each Box Does — One Line Each

Follow the data through the diagram, top to bottom:

- **Customer (browser)** — where the journey starts: a click produces an HTTP request carrying the order data
- **DNS** — the browser only has the domain `shop.com`; the request needs an **IP address**. DNS is the lookup: domain in, IP out. That's its entire job
- **Load Balancer** — the app doesn't run on one server; it runs on N identical ones. The load balancer receives every request and hands it to one healthy backend. Health checks run constantly — a dead server silently stops receiving traffic
- **Backends 1..N** — identical servers, all running the **same Docker image** (the app packaged with everything it needs to run anywhere). One of them processes the order
- **PostgreSQL** — the **source of truth**: the order, the customer, the product — the data that must be correct and must survive. Everything else in the data layer is built around it
- **Redis** — a **cache**: in-memory copies of hot data (like that product page being read 10,000 times a second), so the database doesn't drown in repeated reads
- **OpenSearch** — a **search engine**: it's what lets a typo like "wirless headphone" still return ranked, relevant results — something database search can't do well at scale
- **S3** — **object storage for files**: product images and uploads live here, not in database tables. The DB stores a URL; the browser fetches the file directly from S3
- **Queue + Workers** — placing an order triggers slow work: confirmation email, invoice, warehouse notification. The backend drops tasks into a **queue** and responds to the customer in under a second. **Workers** pick tasks up in the background

## The Two Side-Strips

The order path is the story — but two other things run alongside it:

```
  HOW CODE GETS THERE                       HOW WE WATCH IT
  ───────────────────                       ────────────────
  git push                                  Prometheus   → metrics ("it's slow")
     │                                      Grafana      → the graphs
     ▼                                      OpenTelemetry→ collects the data
  CI: tests → Docker image → Registry       Jaeger       → traces ("THIS step is slow")
     │
     ▼
  ECS / Kubernetes run the new image
  (Terraform built the servers + network underneath)
```

- **How code gets there** — developers push code daily; a **CI/CD pipeline** tests it, builds a new Docker image, and ships it to every server. **Terraform** wrote the servers and network as code so they can be recreated and reviewed; **ECS or Kubernetes** run the containers
- **How we watch it** — one day an order takes 5 seconds instead of 1. **Prometheus** collects metrics that say *something* is slow; **Jaeger traces** follow one request across services and show *which step* ate the time. **Grafana** draws it all as graphs

## The Pattern — Every Box Has a Reason

Here's the table worth remembering. Each box: the problem that forced it in, and the new problem it brought. By the end of this batch you'll be able to fill this table from memory.

| Box | Problem that forced it in | New problem it brings |
|---|---|---|
| DNS | browsers hold domains, requests need IPs | DNS itself must exist and respond fast (covered lightly in 1.3) |
| Load Balancer | one server = one bottleneck and one point of failure | the LB is now critical — if it dies, nothing works (Batch 2) |
| N identical backends | one server can't handle growing traffic | identical deployments everywhere — solved by Docker images (1.9) |
| PostgreSQL | order data must be correct and survive | repeated reads at scale slow it down (1.4) |
| Redis | repeated reads drown the DB | the copy goes stale — cache invalidation (1.5) |
| OpenSearch | DB search can't rank or survive typos | another copy of data to keep in sync (1.6) |
| S3 | binary files bloat the DB | files live outside — URLs must be stored and managed (1.7) |
| Queue + Workers | the customer shouldn't wait for slow work | the same message can arrive twice — idempotency (1.8) |
| CI/CD + Terraform + GitOps | manual deploys drift and break | bad changes can deploy automatically (1.9) |
| Observability | "it's slow" — but WHERE? | the app must be wired to emit the data (1.10) |

## What This Doc Is NOT

This doc is a **map, not the territory**. Each box got one paragraph here — that's deliberately shallow. The rest of Batch 1 walks the boxes in order, one doc each, and later batches deep-dive each one (scaling strategies, replication, Kafka vs queues — all later).

Also: **not every app needs every box.** That's the golden rule from 1.1 — every box in this diagram was added because a problem forced it. An app with 100 users might need exactly none of the data-layer extras. The map shows the full-grown version; your app earns its boxes one problem at a time.

## Check Yourself

1. Without scrolling — list the boxes a request passes through, from the click to the email, in order.

   <details>
   <summary>Sample Answer</summary>

   Browser → DNS (domain → IP) → Load Balancer (pick a healthy backend) → one of N identical backends (process the order) → PostgreSQL (save the order — source of truth) → Queue (drop slow tasks) → Workers (email, invoice, warehouse). Alongside: Redis serves cached reads, OpenSearch handles search, S3 serves the images.
   </details>

2. Why does the diagram show MORE THAN ONE backend server?

   <details>
   <summary>Sample Answer</summary>

   Two reasons: capacity and survival. One server caps the traffic the app can handle (traffic growth) and dies the app dies with it (a single point of failure). N identical servers behind a load balancer share the load and survive one of them going down — the load balancer's health checks stop sending traffic to a dead one.
   </details>

3. A friend asks: "Why is Redis needed if PostgreSQL already stores the data?" Answer using the source-of-truth idea.

   <details>
   <summary>Sample Answer</summary>

   PostgreSQL is the source of truth — the real, correct, permanent data. Redis only holds fast in-memory COPIES of hot data so repeated reads don't hammer the database. Delete Redis and the app still works, just slower; delete Postgres and the orders themselves are gone. The cost of the speed: the copy can go stale — cache invalidation.
   </details>

4. What do the two side-strips (how code gets there / how we watch it) have in common with the request path?

   <details>
   <summary>Sample Answer</summary>

   The same golden rule runs through all three: every box exists because a problem forced it in, and each brings a new problem. Deployment boxes exist because manual deploys drift; observability boxes exist because "it's slow" without a cause is undiagnosable. The pattern — problem in, new problem along — isn't unique to the request path; it's how the whole field works.
   </details>
