The cache absorbed the repeated reads. Now a different kind of read breaks: the customer types **"wirless heaphone"** — typos, wrong spelling — and still expects the right products, best match first. At a million products, that's not a cache problem. It's a search problem.

## Where We Left Off

1.5 added Redis so repeated identical reads stop hammering PostgreSQL. But search traffic isn't identical-repeat traffic — every query is *different* ("wireless headphone", "headphones bluetooth", "head set"), and each one needs **ranking**: best matches first, not just any matches. That's a job PostgreSQL was never built for.

## The Problem — Why PostgreSQL Search Struggles

Postgres can do basic text search — a query like "find products where the name contains 'headphone'" works. But the store's search needs more, and each requirement breaks at scale:

- **Typos** — "wirless" must still match "wireless". Database matching is exact: `LIKE '%wirless%'` simply finds nothing
- **Ranking** — 500 products contain "headphone". Which 10 show first? A database returns rows; ranking them by *relevance* isn't its job
- **Scale** — searching a million products means scanning a million rows per query, thousands of times a second. Even indexed, "match these words across these fields and rank them" is not a database workload

## OpenSearch — A Search Engine, Not a Database

**OpenSearch** is a search engine: a separate system whose entire job is **fast, ranked, typo-tolerant search**. Same drill as Redis — the data gets *copied* out of PostgreSQL into a shape built for one job.

The shape is the interesting part. A database index answers "which row has this ID?" — point lookups. Search needs the reverse: "which products contain this WORD?" So OpenSearch builds an **inverted index** — think of a map in code:

```ts
{
  "wireless":  [product:17, product:402, product:1043],
  "headphone": [product:23, product:402, product:5110],
  "bluetooth": [product:23, product:88,  product:402]
}
```

Word in → matching products out. No scanning a million rows — the words point straight at their products. On top of that index, the engine adds the two things the database couldn't:

- **Fuzzy matching** — "wirless" is one edit away from "wireless", so it matches anyway
- **Relevance scoring** — word frequency, field weight, product popularity → a score per result → best matches first

## Keeping It Honest — Postgres Stays the Truth

Same agreement as 1.4 and 1.5: **PostgreSQL is the source of truth; OpenSearch holds a search copy.** When a product's name or price changes in Postgres, that change flows into the search index — otherwise search starts selling last week's catalog.

Notice the pattern forming across this batch:

```
PostgreSQL (the truth)
   ├── Redis        ← copy for FAST READS      (1.5)
   └── OpenSearch   ← copy for SEARCH           (1.6)
```

Cache and search index are the same move — copy data out of the truth into a shape optimized for one kind of read — with different shapes and different staleness rules. This "copy out for a purpose" pattern is one of the most important in system design. It appears again in every big system you'll ever study.

## The Golden Rule, Applied

- **Problem that forced OpenSearch in:** typo-tolerant, ranked search over a million products — a workload a relational database can't serve
- **New problems it brings:**
  - **Another copy to sync** — product updates must flow into the index or search goes stale (same disease as the cache)
  - **One more running system** — indexing at scale is real resource cost; it's the heaviest box added so far
  - **"Search truth" ambiguity** — if Postgres and the index disagree on a product, users see the index. Sync discipline stops being optional

And the honesty check from 1.1 applies hard here: **an app with 500 products doesn't need OpenSearch.** Postgres full-text search is plenty at small scale. This box arrives when search volume and catalog size force it — not because the roadmap says so.

## What It Is NOT

- **Not a database replacement.** No transactions, no relational integrity — it can't be the source of truth. Orders never live in OpenSearch
- **Not just "faster LIKE queries"** — it's a different data structure (inverted index) for a different workload
- **Not only for products.** Logs, user search, documents — anything text-heavy. (Log search is a real use — it shows up again in 1.10)
- **Not the only search engine.** Elasticsearch is the famous cousin — same concept, different distribution. The idea is the point, not the brand
