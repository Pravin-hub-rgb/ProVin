Reads are fast, search works. One more piece of the product page: the **photo**. An iPhone listing has images; a user has an avatar; customers upload review photos. Where do files live? The answer starts with where they *don't* live — the database.

## Where We Left Off

1.6 finished the "copies of data" family: Redis for fast reads, OpenSearch for search — both copied out of PostgreSQL, the source of truth. This doc completes the data layer with the last kind of data the store handles: **binary files**.

## The Problem — Binary Files Don't Belong in a Database

An image is a binary blob — hundreds of kilobytes to megabytes of bytes with no queryable structure. Tempting shortcut: stuff it into a Postgres column. Here's why that hurts:

- **Bloat** — a table with 10 lakh product images inside it becomes enormous; scans, backups, and replication of that table all crawl
- **Wasted memory** — the database's cache (RAM) fills with image bytes nobody can query, crowding out actual rows
- **Bandwidth through the wrong door** — every image view would pass through the database → backend → browser. The busiest bytes on the site, flowing through the most expensive component (1.4 taught you what heavy traffic through Postgres does)

## S3 — Object Storage

**S3 (Amazon Simple Storage Service)** is **object storage** — storage built for exactly this: files, kept cheap, served directly.

The model is a map:

```
bucket = the container (like a top-level folder)
key    = the file's name inside it  ("products/iphone-15.jpg")
value  = the file's bytes
```

The data flow for the product image:

```
1. seller uploads image
   backend → S3:  PUT products/iphone-15.jpg
   S3 → backend:  "here's the URL"
        https://store-bucket.s3.amazonaws.com/products/iphone-15.jpg

2. backend stores ONLY the URL in PostgreSQL:
   products: { id: 1001, name: "iPhone", image_url: "https://…/iphone-15.jpg" }

3. customer opens the page:
   backend sends the row → browser reads the URL →
   browser fetches the image DIRECTLY from S3
```

Read step 3 again — it's the whole point: **the image bytes never touch your backend or your database.** The DB stores a short URL string; the browser pulls the bytes straight from S3. Postgres holds the data; S3 holds the files.

## Why This Split Works

- **Right tool per data type** — queryable, relational data → Postgres; opaque binary → S3. Each scaled and backed up on its own terms
- **The backend stays light** — image traffic (the heaviest bytes) bypasses it entirely; backends serve requests, not megabytes
- **Cheap at scale** — object storage is dramatically cheaper per gigabyte than database storage. A crore images costs pennies compared to stuffing them into tables

## The Data Layer — Now Complete

Four boxes, four data types, four jobs. The compare table — after each concept is already clear — shows the whole layer at once:

| Box | Holds | Built for | The one job |
|---|---|---|---|
| PostgreSQL | relational rows | durability, correctness, transactions | source of truth |
| Redis | hot-data copies | memory-speed reads | absorb repeated reads |
| OpenSearch | search index | inverted index + fuzzy + ranking | typo-proof ranked search |
| S3 | binary files | cheap storage, direct serving | files without touching the DB |

And one rule running through all four: **Postgres is the truth; everything else is a copy or a complement.** Redis copies rows, OpenSearch copies rows into an index, S3 holds what was never rows at all.

## The Golden Rule, Applied

- **Problem that forced S3 in:** binary files bloat and clog the database — the wrong data in the wrong store
- **New problems it brings:**
  - **URLs become data** — the DB row points at a file that must actually exist; deleted files leave broken URLs, orphaned files waste money
  - **Lifecycle management** — uploads, replacements, deletions need discipline outside the database's transaction guarantees
  - **Speed and access control at scale** — serving images globally fast (CDN — Batch 2) and keeping private files private (signed URLs — Batch 3) are real sub-problems

## What It Is NOT

- **Not a database.** You can't query "all images uploaded by user 42 this week" — S3 answers "give me this key", nothing smarter
- **Not your server's disk.** It's a service behind an API — survives your server dying, which is the point
- **Not automatically fast worldwide.** It's one region by default; global speed needs a CDN layer (Batch 2)
- **Not just for images.** PDFs, backups, video, log archives — any binary that shouldn't live in tables
