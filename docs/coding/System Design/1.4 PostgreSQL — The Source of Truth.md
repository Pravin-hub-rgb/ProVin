The request made it through DNS and the load balancer — it just landed on a healthy backend. Now that backend has an order to process. The first real question of the application layer: **where does the order data go?**

## Where We Left Off

1.3 ended with the request arriving at one of N identical backends. This doc is about what happens next: the backend must **save** the order. Not display it — save it, so it survives, can be found again, and stays correct even when a thousand other requests are racing it.

## The Problem — Data Must Survive and Stay Correct

Two requirements, straight from the business:

1. **Survival** — if the backend crashes 2 seconds after saving an order, that order must still exist. Data can't live in the backend's memory; memory dies with the process.
2. **Correctness under concurrency** — 500 users placing orders at the same moment must produce 500 real orders. No lost orders, no half-written rows, no double charges.

The piece that solves both is a **database** — and for this kind of data, a **relational database**. Our store uses **PostgreSQL**.

## Source of Truth — The Most Important Phrase in This Batch

**Source of truth** = the one place where the data is *real*. Copies may exist elsewhere (they will — 1.5 and 1.6 are coming), but they're all just copies. If any copy disagrees with the source of truth, the copy is wrong. Not the other way around.

```
PostgreSQL  ← THE data. If this says the order exists, the order exists.
   ↑
   copies of it live in Redis / OpenSearch / anywhere else — but they're copies
```

Why this phrase matters: in 1.5 we'll add Redis, and in 1.6 OpenSearch — both hold data too. The only reason that's safe is that **everyone agrees Postgres is the real one**. Every design decision about copies flows from this agreement.

## Why a Relational Database Fits

The store's data is **relational** by nature — the rows reference each other:

```
orders:    id, customer_id → customers, total
customers: id, name, email
products:  id, name, price
order_items: order_id → orders, product_id → products, quantity
```

An order points at the customer who made it and the products in it. A relational database (SQL) stores exactly this: tables with typed columns and references between them. And it gives two guarantees the order flow depends on:

- **Transactions** — a group of writes succeeds fully or not at all. Deduct stock and create the order: both happen, or neither. A crash halfway can't leave a half-order behind.
- **Query power** — "orders from this customer this month" is one declarative query, not application code looping through data.

That's why the store's data — orders, customers, products — lives in **PostgreSQL** and nowhere else. Not in files, not in the backend's memory, not only in a cache.

## The Scale Moment — Where This Breaks

Here's the scene that forces the next tool in. The product page for an iPhone gets huge traffic — say the store grows to **1 lakh (100,000) users**, and that page is opened thousands of times a second.

What happens on every page open?

```
every page open → same query → PostgreSQL reads from disk → returns the same rows
every page open → same query → PostgreSQL reads from disk → returns the same rows
...10,000 times per second
```

The data hasn't changed between reads. The query is identical every time. But a database reads from **disk** — built for durable, correct storage, not for serving the same answer 10,000 times a second. At some request rate, the database saturates: queries queue up, response times climb, and the whole app slows down — because every feature talks to the same database.

Notice what kind of reads these are: **repeated, identical, read-heavy**. The data barely changes, but everyone reads it constantly. That's the profile that breaks a database first.

## The Golden Rule, Applied

- **Problem that forced PostgreSQL in:** order data must survive crashes and stay correct under concurrent writes
- **New problem it brings:** at scale, its careful disk-based correctness makes it slow at *repeated identical reads* — which sets up the next doc

## What It Is NOT

- **Not the only kind of database.** Document stores (MongoDB), key-value stores, graph databases — different data shapes, Batch 3 compares them. For relational order data, SQL is the natural fit
- **Not a cache.** Postgres is built for durability and correctness; caching is a different job — next doc
- **Not where files go.** Product images and uploads are binary blobs, not rows — 1.7's topic
- **Not the thing to reach for when reads get slow.** The first fix for repeated reads isn't a faster database — it's a copy in front of it

3. What is a transaction, and why does the order flow need one?

   <details>
   <summary>Sample Answer</summary>

   A group of writes that succeeds fully or not at all. The order flow needs it because one order touches several writes: create the order row, write its items, deduct stock. A crash between them must not leave a half-order. Transactions make "both or neither" a guarantee, not a hope.
   </details>

   <details>
   <summary>Sample Answer</summary>

The reads are also identical — the same query, the same unchanged result, thousands of times a second. That "repeated identical read" profile is exactly what the next doc's tool — a cache — is built to absorb.
