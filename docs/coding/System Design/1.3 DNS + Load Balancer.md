The last doc drew the whole map — one click passing through DNS, the load balancer, the backends, the data layer, the queue. Now we walk it, one box per doc. First stop: the two boxes the request touches before it even reaches your app.

## Where We Left Off

In 1.2, the journey started with a click on `shop.com`. Two boxes sat between that click and your backend: **DNS** and the **Load Balancer**. This doc explains why both must exist — and the two problems they solve.

## The Problem — How Does the Request Even Find the App?

The customer's browser holds a **domain name** — `shop.com`. But an HTTP request can't be sent to a name. It has to be sent to an **IP address** — a numeric address like `142.250.77.46` that identifies a machine on the internet.

So the very first problem is a conversion problem:

```
the browser has:  "shop.com"     (a name)
the request needs: 142.250.77.46 (an address)
```

## DNS — The Lookup

**DNS (Domain Name System)** is the internet's lookup for exactly this: **domain in, IP out**.

Think of it as a lookup table in code:

```ts
{ "shop.com": "142.250.77.46" }
```

Except this table isn't in your app — it's a distributed system spread across the internet, and the browser asks it automatically before sending the request. From the app's point of view, nothing happens at all: the browser asks DNS, gets the IP, and only then sends the request to that address.

Two things to notice:

- **DNS sends nothing anywhere.** It doesn't touch your request or your order. It just answers one lookup question. The request still travels browser → server directly.
- **DNS answers can change.** If the app moves to new servers, the DNS record updates — and every new request goes to the new address. No app change needed. This little property becomes important in a second.

## The Second Problem — One Server Is Not Enough

Say DNS points at one server running the whole backend. Two forces from 1.1 break this:

1. **Traffic growth** — one machine has one CPU, one amount of RAM, one network pipe. At some request rate, it saturates. Responses slow down, then time out.
2. **Survival** — one server means one **single point of failure**: if that machine crashes, the entire app is offline. Not degraded — gone.

The fix for both is the same: **run the app on several identical servers.** Traffic splits across them; if one dies, the others keep serving.

But this creates a new problem immediately: **who decides which server gets each request?** The browser only knows one address. It can't see the five backends behind it — and it shouldn't; servers going up and down shouldn't change anything the browser does.

## The Load Balancer — The Traffic Distributor

The **load balancer** solves it. It's one stable address that sits in front of all the backends:

```
                        ┌─────────────────────┐
                        │    Load Balancer    │
                        └──────────┬──────────┘
                ┌──────────────────┼──────────────────┐
                ▼                  ▼                  ▼
          ┌───────────┐     ┌───────────┐      ┌───────────┐
          │ Backend 1 │     │ Backend 2 │      │ Backend 3 │
          └───────────┘     └───────────┘      └───────────┘
```

Data-flow view: every request arrives at the load balancer; it forwards the request to one of the healthy backends and passes the response back. The backend machines are invisible from outside — the only public address is the load balancer's.

Its second job matters just as much: **health checks**. The load balancer pings each backend on a schedule (a small "are you alive?" request). A backend that stops responding is marked unhealthy and receives no traffic — automatically. Nobody gets paged to redirect traffic away from a dead server; it just stops receiving requests.

And here's where DNS comes back: **DNS points at the load balancer's IP, not at any backend.** The chain is:

```
browser → DNS lookup → LB's IP → LB picks a healthy backend → request processed
```

So a backend can die, be replaced, or scale up to 50 machines — the browser never knows or cares. The one address stays stable.

## The Golden Rule, Applied

- **Problem that forced DNS in:** requests can't be sent to names — only to IPs
- **New problem DNS brings:** a lookup layer that must respond correctly (and fast), or nothing works — and it must stay updated when servers change
- **Problem that forced the load balancer in:** one server saturates and dies alone
- **New problem the LB brings:** it's now the most critical box in the path — if IT fails, nothing works (real setups run redundant load balancers — Batch 2). Also, once requests land on different servers, any state kept "on the server" becomes a problem — Batch 2 covers that too

## What It Is NOT

- **DNS is not the request path.** It's consulted once per lookup; the order request itself never passes through DNS
- **A load balancer is not a firewall or a proxy for caching** — those are different boxes with different jobs (a CDN can act like a cache — Batch 2)
- **"Load balancing" is not one algorithm.** Round-robin, least-connections, weighted — how the LB picks is a Batch 2 topic. Here, "picks a healthy one" is enough

## Check Yourself

1. Why can't the browser just send the request to `shop.com` directly?

   <details>
   <summary>Sample Answer</summary>

   A request needs an IP address — names mean nothing to network routing. DNS converts `shop.com` into an IP first; only then can the request be sent. Domain in, IP out — that's DNS's entire job.
   </details>

2. The app now runs on 5 identical backends. What breaks if you remove the load balancer and give the browser all 5 IPs?

   <details>
   <summary>Sample Answer</summary>

   The browser would have to pick a server itself — and it has no way to know which are alive or busy. A dead server would keep receiving direct requests that fail. The load balancer centralizes that decision: one stable address, health-checked backends, traffic only to the healthy ones.
   </details>

3. Backend 3 crashes completely. Walk through what happens to traffic — what does the user experience?

   <details>
   <summary>Sample Answer</summary>

   The load balancer's health checks notice Backend 3 stops responding and mark it unhealthy. New requests go only to the healthy backends. Users notice nothing — no errors, no slowdown beyond the remaining servers carrying slightly more load. That's the whole point of health checks: automatic, no human in the loop.
   </details>

4. What new problems did the load balancer bring in? (Golden rule — every tool brings one.)

   <details>
   <summary>Sample Answer</summary>

   First: it's now the most critical box — if the LB dies, no request reaches any backend, so real setups run it redundantly. Second: requests now land on different servers, so anything a backend keeps "locally" (like session state in memory) becomes inconsistent — that pushes state out of the servers, which Batch 2 covers.
   </details>
