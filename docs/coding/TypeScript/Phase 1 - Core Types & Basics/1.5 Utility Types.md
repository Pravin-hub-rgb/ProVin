## Cheat Sheet

```ts
Record<K, V>   // Object: every key is of type K, every value is of type V
Partial<T>     // All properties optional
Required<T>    // All properties required
Readonly<T>    // All properties read-only (cannot modify)
Pick<T, K>     // Choose only a few properties
Omit<T, K>     // Remove a few properties
Exclude<T, U>  // Remove types matching U from union T
Extract<T, U>  // Keep only types matching U from union T
NonNullable<T> // Remove null and undefined
```

## What Has Happened So Far

In the previous topics we learned TypeScript's core types — primitives, objects, arrays, functions, interfaces, union types. Those were tools for building our own types. Now we learn a new thing: **utility types** — TypeScript's built-in generic types that transform existing types.

## Broader Goal

Many times we need a modified version of an existing type — like "make all properties optional" or "remove some properties". Utility types do exactly that. After learning them, you won't need to create new interfaces over and over.

---

## 1.5.1 Record<K, V> — Dynamic Object Type

**THINK:** Sometimes we need an object whose keys we don't know in advance, but whose value structure we do. Like a translation object — keys are language names ("en", "hi"), each value is an object of a specific shape.

**CONCEPT — `Record<K, V>`:** It creates an object type where every key is of type `K` and every value is of type `V`. No property can be missing — if K is a union type, you need an entry for every value in that union.

Simple way to understand: `Record<string, number>` means "an object where every key is a string and every value is a number". It tells TypeScript what the object's shape will be. It exists only at development time — at runtime there's nothing, it's purely for type safety.

```ts
type Language = "en" | "hi";

const texts: Record<Language, string> = {
  en: "Hello",
  hi: "नमस्ते",
};
```

Here `Record<Language, string>` means: "an object whose every key is `en` or `hi`, and whose every value is a string." Providing both keys is mandatory — if you miss even one, TypeScript gives an error.

**Why it's useful:** Whenever keys come from a known set and every value has the same shape, use Record. Like — API responses mapped by ID, translation tables, config objects.

> **What It Is NOT:** Record is not `{}` or `Object`. `{}` allows any key without checking the value type. Record is strict — it enforces both the key type and the value type.

```ts
const bad: Record<string, number> = { a: 1, b: "hello" }; // ❌ "hello" is not a number
```

## 1.5.2 Partial<T> — All Properties Optional

**THINK:** Take a user profile form — the user will only change the name, not the other fields. But you have a full `User` interface where all fields are required. Do you need to create a new `PartialUser` interface? No — `Partial<T>` handles it.

**CONCEPT — `Partial<T>`:** It makes all properties of T optional. A `?` is added in front of every property.

```ts
interface User {
  id: number;
  name: string;
  email: string;
}

// Manual way — you'd need to create a new interface
interface PartialUser {
  id?: number;
  name?: string;
  email?: string;
}

// Partial way — one line
type PartialUser = Partial<User>; // { id?: number; name?: string; email?: string }
```

**Real use case:** Update API calls — you only want to send the fields that changed. Partial gives you the type without creating a new interface.

```ts
function updateUser(id: number, updates: Partial<User>) {
  // Only the fields that were sent will change
}
```

> **What It Is NOT:** Partial makes all properties optional, but it does not give permission to assign `undefined` explicitly. If a property is optional, its value may be missing, but explicitly setting `undefined` is allowed (think about TypeScript strict mode).

---

## 1.5.3 Required<T> — All Properties Mandatory

The opposite of Partial. It makes all optional properties required.

```ts
interface Config {
  url?: string;
  timeout?: number;
  retries?: number;
}

// All properties are now required
type StrictConfig = Required<Config>;
// { url: string; timeout: number; retries: number; }
```

**When to use:** When some internal function actually expects all values, but the public API kept them optional.

---

## 1.5.4 Readonly<T> — Read Only, No Writing

**THINK:** There's a config object — once set, no one should modify it. But TypeScript by default allows `config.url = "new"`. Readonly blocks that.

**CONCEPT:** It makes all properties `readonly`. Any assignment attempt gives a compile-time error.

```ts
interface Theme {
  primary: string;
  secondary: string;
}

const theme: Readonly<Theme> = { primary: "#000", secondary: "#fff" };
theme.primary = "#111"; // ❌ Error: Cannot assign to 'primary' because it is a read-only property
```

**Real use case:** Redux state, global configs, any data that should be immutable.

> **What It Is NOT:** `Readonly<T>` enforces only at the TypeScript level — there's no restriction at runtime. If someone modifies it through JavaScript code, it will happen. This is only development-time safety.

---

## 1.5.5 Pick<T, K> — Pick a Few Properties

**THINK:** There's a `User` interface with 10 properties. A component only needs `name` and `email`. Will you create a new interface? Do it with Pick.

```ts
interface User {
  id: number;
  name: string;
  email: string;
  role: "admin" | "user";
  createdAt: Date;
}

type UserPublic = Pick<User, "name" | "email">;
// { name: string; email: string; }
```

**Line by line:** `Pick<User, "name" | "email">` means — take only the `"name"` and `"email"` properties from the `User` interface, remove the rest.

**Real use case:** You only want to send a few fields in an API response (like a public profile), not internal properties.

---

## 1.5.6 Omit<T, K> — Remove a Few Properties

The opposite of Pick. It removes the specified properties and keeps the rest.

```ts
interface User {
  id: number;
  name: string;
  email: string;
  password: string;
  ssn: string;
}

type UserPublic = Omit<User, "password" | "ssn">;
// { id: number; name: string; email: string; }
```

**Pick vs Omit — When to use which?**
- **Pick** when it's clear what you *want* — pick specific properties
- **Omit** when it's clear what you *don't want* — remove sensitive/private fields

Rule of thumb: Pick for a short list, Omit for a long list.

---

## 1.5.7 Exclude<T, U> — Remove Types from a Union

**THINK:** There's a union type `Status = "loading" | "success" | "error"`. A function accepts only `"success" | "error"`. No need to manually duplicate the type.

```ts
type Status = "loading" | "success" | "error";

type FinishedStatus = Exclude<Status, "loading">;
// "success" | "error"
```

**CONCEPT:** `Exclude<T, U>` removes from union type `T` the types that also exist in `U`. Both `T` and `U` are union types.

```ts
type T = "a" | "b" | "c" | "d";
type U = Exclude<T, "a" | "b">;
// "c" | "d"
```

---

## 1.5.8 Extract<T, U> — Pick Types from a Union

The opposite of Exclude. It keeps only the types that match `U`.

```ts
type T = "a" | "b" | "c" | "d";
type U = Extract<T, "a" | "b">;
// "a" | "b"
```

**Real use case:** When filtering event types — `Extract<EventType, "click" | "submit">` returns only those.

---

## 1.5.9 NonNullable<T> — Remove null/undefined

It removes `null` and `undefined` from a union type.

```ts
type MaybeString = string | null | undefined;
type DefinitelyString = NonNullable<MaybeString>;
// string
```

**Real use case:** API responses come in nullable form — you want a non-nullable version for internal processing.

## When to Use What — Quick Reference

| Problem | Solution |
|---------|----------|
| "Same shape for every value, dynamic or fixed keys" | `Record<K, V>` |
| "Make a few properties optional for a form update" | `Partial<T>` |
| "Need all properties required for internal use" | `Required<T>` |
| "Config/state shouldn't be modifiable by anyone" | `Readonly<T>` |
| "Need only 2-3 properties from an interface" | `Pick<T, K>` |
| "Remove sensitive fields, keep the rest" | `Omit<T, K>` |
| "Remove some values from a union type" | `Exclude<T, U>` |
| "Pick some values from a union type" | `Extract<T, U>` |
| "Remove null/undefined from a nullable type" | `NonNullable<T>` |

---

## Common Mistakes

1. **Forgetting to provide an entry in Record** — If the key is a union type, you need an entry for every value in the union.
2. **Treating Partial as a runtime default** — Partial only makes the type optional. At runtime the value can be undefined — you'll need to handle it.
3. **Writing property names wrong in Pick/Omit** — TypeScript will give an error. Use your IDE's autocomplete.
4. **Applying Exclude/Extract to object types** — These only work with union types (string literals, number literals). For object types use Pick/Omit.

## Summary

| Utility Type | Job |
|---|---|
| `Record<K, V>` | Object type with dynamic/constrained keys |
| `Partial<T>` | All properties optional |
| `Required<T>` | All properties required |
| `Readonly<T>` | All properties read-only |
| `Pick<T, K>` | Pick specific properties |
| `Omit<T, K>` | Omit specific properties |
| `Exclude<T, U>` | Remove types from a union |
| `Extract<T, U>` | Keep only matching union types |
| `NonNullable<T>` | Remove null and undefined |

All utility types exist only at TypeScript time — they have no effect at runtime. They bring speed and safety to writing code.
