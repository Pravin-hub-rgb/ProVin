In 1.3 you built conversations with messages and prompts. When you called `model.invoke()` and printed `response.content`, that reply was **free-form text** — anything could come back. I've hit this problem too: we needed to pull a user's name and age out of the model, and it gave a long paragraph with the name buried inside. I couldn't use that directly in code.

Same issue: a function needs fixed data — not an "essay." That's what this topic does: **structured output**.

# 1.4 Structured Output

**Structured output** means telling the model to give its reply in a **fixed format**, like a shape decided ahead of time. Inside code this is called a **schema** — a template with fixed fields: what the name will be, what type it'll be, what can go in it.

Think of a hotel check-in form. It has a "Name" box, an "Age" box, a "City" box. You don't write a whole paragraph; you fill in the boxes. Structured output does exactly that — give the model a form, it fills the boxes, and code knows which data sits in which field.

## Define the Schema with Pydantic

The simple way in LangChain is to define the form with a `Pydantic` class. Pydantic is a Python library built for validating structured data. Write a class that lists the fields, and the form is ready.

```python
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from pydantic import BaseModel, Field

load_dotenv()

model = init_chat_model("llama-3.3-70b-versatile")

class MovieReview(BaseModel):
    title: str = Field(description="Movie ka naam")
    rating: int = Field(description="5 mein se rating, sirf number")
    favorite_scene: str = Field(description="Ek favorite scene ka description")

structured_model = model.with_structured_output(MovieReview)

review = structured_model.invoke("Tell me about the movie Inception.")
print(review)
print(review.title)
print(review.rating)
```

Line by line:

1. `from pydantic import BaseModel, Field` — brings two things from Pydantic: `BaseModel` (the base for the class) and `Field` (for describing fields).
2. `class MovieReview(BaseModel):` — creates a new Python class whose base is `BaseModel`. This class itself is the template of the form.
3. `title: str = Field(...)` — a field. `title` is the name, `str` is the type (string). `Field(description="...")` — tells the model about this field. That description guides the model on what to write here.
4. `model.with_structured_output(MovieReview)` — tells the model to give its reply in the shape of `MovieReview`. This returns a new `structured_model` object that always returns a `MovieReview` shape.
5. `structured_model.invoke("Tell me about the movie Inception.")` — same invoke, but now the reply is a `MovieReview` object, not just text.
6. `print(review)` — the whole object; `review.title`, `review.rating` — access fields individually. Data can be used.

What's the benefit? In code you work directly — `review.rating` is a real integer, `review.title` is a real string. The model's reply is predictable, so the code is reliable and crash-free. Fixed shape = code knows what it'll get.

## Two More Approaches — TypedDict and dataclass

Besides Pydantic, LangChain gives two more ways. Both are worth learning because real code shows all three.

### Approach 2 — TypedDict

**TypedDict** is a built-in Python thing that describes the shape of a dictionary. Instead of a Pydantic class, you just declare field types — no `Field(description=...)`:

```python
from typing import TypedDict

class MovieReview(TypedDict):
    title: str
    rating: int
    favorite_scene: str

structured_model = model.with_structured_output(MovieReview)

review = structured_model.invoke("Tell me about the movie Interstellar.")
print(review["title"])   # access like a dictionary
print(review["rating"])
```

The difference: `review` is now a **dictionary**, so you access it with `review["title"]`, not `.`. It's lighter — no `Field(description=...)` — but the syntax is simpler and the mental load is less.

### Approach 3 — dataclass

A **dataclass** is Python's built-in way to make simple data classes. Here too you just define fields, and access is through `.`:

```python
from dataclasses import dataclass

@dataclass
class MovieReview:
    title: str
    rating: int
    favorite_scene: str

structured_model = model.with_structured_output(MovieReview)

review = structured_model.invoke("Tell me about the movie Dune.")
print(review.title)
print(review.rating)
```

### Which One When?

| Approach | Access | Field descriptions | Extra features |
|---|---|---|---|
| Pydantic `BaseModel` | `review.title` | ✅ `Field(description=...)` | Validation, defaults, complexity |
| `TypedDict` | `review["title"]` | ❌ | Lighter, it's a dict |
| `dataclass` | `review.title` | ❌ | Simple, built-in |

Rule of thumb: when you need to give the model a lot of context about a field or you want validation, go with **Pydantic**. When you just need a straight shape with nothing extra, `TypedDict`/`dataclass` is enough.

## Why This Matters for Agents

At the core of every agent is a loop: tell the model what to do, get the model's reply, use it directly in code. If the reply is an essay, code has to parse it (TEDIOUS and error-prone). With structured output, the reply is automatically an object like `review.rating` or `plan["tasks"]` — **code knows exactly what the model said.** The same is needed for function calls — a function needs named arguments, not an essay. Next topic we'll see exactly that: tools.

## What It Is NOT

⚠️ **Structured output is NOT just telling the model "send JSON."** Telling it directly sometimes returns a raw JSON string that you then have to parse — easy to get wrong. `with_structured_output` brings the right shape out through the model's own function calling, automatically.

⚠️ **This is NOT just a validation library.** Pydantic's job is validation, but `with_structured_output` goes further — it gets the reply from the model itself in a fixed shape. Pydantic is just a tool; structured output is the resulting skill.
