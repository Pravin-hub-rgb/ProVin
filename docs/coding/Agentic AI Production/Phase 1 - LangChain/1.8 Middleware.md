In 1.7 you gave the model memory. Now think about a real production concern — airport security. They say: everyone passes through, bags get checked, boarding passes verified. A screening happens before every output.

Same with an agent — as long as a model call goes straight through, you have no control around it. Where do you log? What if the API fails? How do you track cost? That's what 1.8 is about — **middleware**.

# 1.8 Middleware

**Middleware** means extra logic that wraps around the model call, before and after. Extra steps before (before) and after (after) the model call. LangChain's own definition: "Middleware provides a way to more tightly control what happens inside the agent."

Think of airport security. The model call = the passenger. Security checks happen before they enter — `before_model` — boarding check at entry; and another check as they exit — `after_model`. These checks are the middleware. You put extra rules on a model call without changing the model's code.

## Built-in (Ready-Made) Middleware

LangChain comes with ready-made middlewares that solve common problems:

| Middleware | What it does |
|---|---|
| **Logging** | Records every call — what was sent, what came back |
| **Retry** | If the API call fails (network problem), tries again on its own |
| **Fallback** | If the primary model is down (broken), tries the backup model |
| **Rate limit** | Controls how many calls are allowed at a time (saves the bill) |
| **Guardrails** | Checks input/output against rules — rejects unsafe stuff |
| **PII detection** | Detects/replaces sensitive info like email, credit card |

The benefit of all of these — they inject into a normal model call without changing the model's logic. Just through a line like `model.with_middlewares([...])`.

## Custom Middleware — Your Own

Besides ready-made ones, you can write your own middleware. Example — a simple middleware that logs every request and response:

```python
from langchain.middleware.base import BaseMiddleware

class LoggingMiddleware(BaseMiddleware):
    async def before_model(self, request):
        print("REQUEST:", request.input)
        return request

    async def after_model(self, response):
        print("RESPONSE:", response.output)
        return response
```

Understand:

- `class LoggingMiddleware(BaseMiddleware)` — a new class that inherits from `BaseMiddleware`. `BaseMiddleware` is the base from which middleware is made.
- `async def before_model(self, request)` — this method runs **before the model**. `async` means this is an async function (Python's pattern for handling concurrency). `request` holds the input that's about to go to the model.
- `print("REQUEST:", request.input)` — print the request, so you can see what's being sent.
- `return request` — send the request forward (return it) — otherwise the pipeline breaks.
- `async def after_model(self, response)` — this runs **after the model**. `response` is the output the model produced.
- `print("RESPONSE:", response.output)` — print the output.
- `return response` — send the response forward.

## Attach the Middleware to the Model

Now connect this logging middleware to the model:

```python
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model

load_dotenv()

model = init_chat_model("llama-3.3-70b-versatile")

wrapped = model.with_middlewares([LoggingMiddleware()])

response = wrapped.invoke("Hello! Kya haal hai?")
print(response.content)
```

- `LoggingMiddleware()` — create an instance (object) of the middleware.
- `model.with_middlewares([...])` — creates a new wrapped copy of the model with that middleware injected. Now whenever `wrapped.invoke()` runs, first `before_model` runs (REQUEST prints), then the model talks, then `after_model` (RESPONSE prints).
- Note — the original `model` stays as it was. Middleware only attaches to the wrapped copy.

Run it — REQUEST and RESPONSE will print on every call, without touching the model's code.

## Where All This Is Useful

With middleware you can make production-ready behaviour around the model — without breaking the model class. Keep the rules separate:

- **Logging** — logs every request, debugging gets easy.
- **Retry** — tries again on its own on a network hiccup.
- **Fallback** — if one model goes down, the other takes over automatically.
- **Guardrails** — catches unsafe inputs/outputs instantly.
- **PII** — detects/replaces sensitive data (email, card).

All of this is "attach to every model call" style. When you have just one model call it feels like extra, but in a real app this is what gives cost control, security, and reliability. We'll go deeper on guardrails in Phase 6.

## What It Is NOT

⚠️ **Middleware does NOT change the model's code.** It stays separate from the model's logic. You add extra logic before/after the model call without modifying the model class.

⚠️ **`before_model`/`after_model` are NOT the same flow everywhere.** These are two separate hooks — before (before) and after (after). Don't mix them up; each has its own job.

⚠️ **Middleware is NOT only a LangChain thing.** It's a general concept — Express/Next.js routers have middleware too, and JavaScript has middleware as well. LangChain applied that same concept to model calls.
