# 2.1 Graphs: State, Nodes, Edges

In Phase 1 you learned LangChain's building blocks — a model call, a tool in it, memory, streaming. All of it was in one line — send to the model, get the reply. But real production agents aren't that simple. In some scenes the agent has to think first, then make a tool call, then think again, then another tool. Sometimes you need to branch ahead based on a question. Controlling all this with a straight line never stays clean.

That's why LangGraph exists — to build agents as a **graph**. Vin learned the multi-agent concept in Introduction course 7.3. Now that same thinking enters the code, through LangGraph.

## What a graph is — understand it from a board game

A graph is a **map that has steps (nodes) and connections between them (edges)**. Think of a board game — the board's squares are nodes, and the arrows between them are edges. Like, you're standing on a square, and the arrow tells you which square you move to next turn.

- **Node** — a step in the graph. Like "read the question," "model thinks," "make the tool call," "write the reply." Every node is a function that takes state and returns it.
- **Edge** — the connection between two nodes. It says "when you're at node X, go to node Y."
- **State** — a shared **bag** that holds all the data. Every node reads it and adds new things. This bag moves forward through the whole graph — like a shared whiteboard in an office where every employee writes their new point.

Once you have such a graph — squares, edges, a shared board — you get flexibility while making decisions. You can branch (if option A then Y, else Z), loop (until the condition is met), or take some steps in parallel. That's a lot of fun compared to a linear loop.

## StateGraph — build the skeleton

In LangGraph you build a graph with the `StateGraph` class. State is defined with a **TypedDict** — a blueprint of a dictionary in Python:

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

# 1. Define state — the blueprint of the shared "bag"
class State(TypedDict):
    messages: list

# 2. A node function — takes state, does work, returns state
def add_hello(state):
    return {"messages": state["messages"] + ["Hello!"]}

# 3. Build the builder
builder = StateGraph(State)

# 4. Register the node
builder.add_node("greet", add_hello)

# 5. Add edges — decide the flow
builder.add_edge(START, "greet")
builder.add_edge("greet", END)

# 6. Compile the graph to make it ready
graph = builder.compile()

# 7. Run
result = graph.invoke({"messages": []})
print(result["messages"])
```

What each line means:

1. `from langgraph.graph import StateGraph, START, END` — LangGraph's core. `StateGraph` is the class that builds a graph, `START` is the entry-point marker, `END` is the exit marker.
2. `class State(TypedDict): messages: list` — Define the state blueprint. This says the shared bag will have a list called `messages`.
3. `def add_hello(state)` — A node function. It gets `state` (the old bag). Its returned dict LangGraph **merges** into the state (new keys/append).
4. `builder = StateGraph(State)` — Build the builder supervisor, which knows the shape of the state.
5. `builder.add_node("greet", add_hello)` — Add a step to the graph: name "greet", function `add_hello`.
6. `add_edge(START, "greet")` then `add_edge("greet", END)` — "START to greet, greet to END."
7. `graph = builder.compile()` — Compute and make the graph ready.
8. `result = graph.invoke({"messages": []})` — Run the whole graph with an empty state. START → greet → END.
9. `print(result["messages"])` — The result is always the final state. This will give `["Hello!"]`.

## Why better than a linear loop

Phase 1's loop was a fixed sequence — step after step, then another, then another. A graph isn't like that. In a graph you can do:
- **Branch** — take a different edge based on a condition.
- **Loop** — run the same node again until a condition is met.
- **Parallel** — run two nodes at the same time.

Real agents need this — thinking, then a tool call, then seeing the result and thinking again. In a linear loop you'd have to wire this loop by hand and it gets messy fast. A graph handles it easily.

## What It Is NOT

⚠️ **This graph is NOT a "machine learning graph."** It's not a chart of data points — it's a **workflow diagram**, the flow of steps, like an architecture flowchart.

⚠️ **State is NOT a permanent file or database.** It's a dictionary that gets passed from node to node. When the graph ends, the state clears.

⚠️ **Node order is NOT necessarily fixed like a list.** You can add nodes in any order — the actual "which node runs when" is decided by the `edges`.

**Answer:** A node is a step/function of the graph. An edge connects one node to another — that's where the flow happens. State is the shared memory/dictionary that every node reads and writes.

<details>
<summary>2. What is the role of `add_node` and `add_edge`?</summary>

**Answer:** `add_node` registers a function in the graph. `add_edge` decides which node runs after which. Nodes are "rooms," edges are "doors."

<summary>3. Why is a graph better than a linear loop for agents?</summary>
