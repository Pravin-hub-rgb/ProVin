# 2.4 Memory & Checkpointers

The agent from 2.3 runs once, gives a reply, and then... forgets everything. For the next `invoke` call, the old conversation is gone. Like you don't remember anything after every conversation. That's why when an agent has a multi-turn conversation, it needs **some record of the state**.

LangGraph gives a concept for this called a **checkpointer** — "the graph's save-game."

## Checkpointer = the graph's "save game"

Like a video game where you save your progress after finishing a level — so you can start from there on the next restart. A checkpointer works exactly the same: it saves the graph's state under a **thread_id**, so the same state is available on the next call.

## MemorySaver — the easiest

`MemorySaver` is LangGraph's in-memory checkpointer — it remembers the state as long as the program keeps running.

```python
from langchain_groq import ChatGroq
from langchain_core.messages import HumanMessage, SystemMessage
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.checkpoint.memory import MemorySaver

llm = ChatGroq(model_name="llama-3.3-70b-versatile")

def chatbot(state: MessagesState):
    messages = [SystemMessage(content="Tum ek helpful dost ho.")] + state["messages"]
    return {"messages": [llm.invoke(messages)]}

# 1. create a checkpointer and attach it to the graph
memory = MemorySaver()

graph = StateGraph(MessagesState)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)
graph = graph.compile(checkpointer=memory)   # <-- attached here

# 2. a thread_id — the chat is saved under this id
config = {"configurable": {"thread_id": "vin-chat-1"}}

# call 1
graph.invoke(
    {"messages": [HumanMessage(content="Main Vin hoon. Tumhe pata hai main kaun hoon?")]},
    config=config,
)

# call 2 — the graph remembers the old chat (because checkpointer = same thread_id)
result = graph.invoke(
    {"messages": [HumanMessage(content="Main kaun tha? Tumhe yaad hai?")]},
    config=config,
)
print(result["messages"][-1].content)
```

Line by line:

1. `MemorySaver()` — an in-memory save-game. Stores state within each run. (In production use `PostgresSaver` / `RedisSaver` — you get persistence.)
2. `graph.compile(checkpointer=memory)` — tells the graph to save state under every `thread_id`. Without this, invoke is stateless.
3. `config = {"configurable": {"thread_id": "..."}}` — says "this all runs under this thread_id."
4. `graph.invoke(..., config=config)` — you must send config with every invoke, so the checkpointer knows which thread's state to retrieve.

If you invoke again with the **same thread_id**, you'll get the old conversation back — like the agent just woke up from sleep.

## How this differs from Phase 1's `InMemoryChatMessageHistory`

In Phase 1, `InMemoryChatMessageHistory` was a **list in RAM** — everything deleted the moment the program restarted. LangGraph's checkpointer stores **structured state under a thread_id** — messages *and other state*. And in production you can easily swap it for a durable store like `PostgresSaver` — without changing code.

## What It Is NOT

⚠️ **A checkpointer is NOT just a chat history object.** It doesn't save only messages — it saves the **entire graph state** (every key you keep in the state).

⚠️ **thread_id is NOT a session.** Different thread_ids inside the same checkpointer = different conversations. Clean isolation by ID.

⚠️ **MemorySaver is NOT permanent storage.** It lives in RAM. Everything resets on restart. For production you need an external saver (Redis/Postgres).

## In Your Own Words

<details>
<summary>1. Why does the graph "forget" without a checkpointer?</summary>

**Answer:** Every `invoke` is a fresh start — the graph doesn't carry state from inside, it behaves like a plain function. If you don't attach a checkpointer, the old conversation doesn't come into the state; every call feels independent.

</details>

<details>
<summary>2. What do thread_id and checkpointer do together?</summary>

**Answer:** `thread_id` is the name/identity of a conversation. The checkpointer stores state under that thread_id. Same ID = same conversation history; different ID = fresh start.

</details>

<details>
<summary>3. Main difference between `InMemoryChatMessageHistory` (Phase 1) and `MemorySaver`?</summary>

**Answer:** History was just a list of messages living in RAM. A checkpointer saves the whole state dict (all keys), structured under a thread_id, and can easily be swapped for a durable store (Postgres/Redis).

</details>
