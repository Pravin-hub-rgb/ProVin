# 2.8 Multi-Agent Systems

So far one agent did one job — it thought, made a tool call, replied. But in the world many tasks need more than one expert. Like writing an article needs a writer, then a reviewer.

In LangGraph you can keep **multiple agents (subgraphs)** inside one graph, working with each other — the writer writes, the reviewer checks, then the writer fixes again. This is a **multi-agent system**.

## Supervisor pattern — one manager, two workers

The most common design: a **supervisor** (manager) node decides who runs next — writer or reviewer or done. Workers do their job, then send the work back to the supervisor.

```python
from typing import Annotated, Literal, TypedDict
from langchain_groq import ChatGroq
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage
from langgraph.graph import StateGraph, START, END, add_messages
from langgraph.types import Command   # for routing

llm = ChatGroq(model_name="llama-3.3-70b-versatile")

# --- shared state: messages + "next" (who runs next) ---
class State(TypedDict):
    messages: Annotated[list, add_messages]   # reducer = merge, not replace
    next: Literal["writer", "reviewer", "FINISH"]

# --- Worker 1: writer (writes a draft) ---
def writer(state: State):
    res = llm.invoke([SystemMessage(content="Tum ek talented copywriter hain. User ke sawal pe ek accha jawaab likho.")] + state["messages"])
    return {"messages": [res], "next": "reviewer"}

# --- Worker 2: reviewer (check + correct) ---
def reviewer(state: State):
    res = llm.invoke([SystemMessage(content="Tum ek senior editor hain. Pichle jawab ko check karo, galati dhundho, behtar banao.")] + state["messages"])
    return {"messages": [res], "next": "FINISH"}

# --- Supervisor (manager decides who runs next) ---
def supervisor(state: State):
    prompt = ("Aap team manager hain. Team mein writer aur reviewer hain. "
              "Agar likha hua jawaab nahi hai to writer ko bulao. "
              "Agar likha hua hai to reviewer ko bulao. "
              "Agar kaam poora ho gaya ho to FINISH likho.")
    res = llm.invoke([SystemMessage(content=prompt)] + state["messages"])
    pick = res.content.strip().lower()
    next_ = "reviewer" if "reviewer" in pick else ("FINISH" if "finish" in pick or "poora" in pick else "writer")
    return {"next": next_}

# --- Build the graph ---
builder = StateGraph(State)
builder.add_node("writer", writer)
builder.add_node("reviewer", reviewer)
builder.add_node("supervisor", supervisor)

def route(state):
    nxt = state.get("next", "FINISH")
    if nxt == "writer":   return "writer"
    if nxt == "reviewer": return "reviewer"
    return END

builder.add_edge(START, "supervisor")
builder.add_edge("writer", "supervisor")
builder.add_edge("reviewer", "supervisor")
builder.add_conditional_edges("supervisor", route)
graph = builder.compile()

# run
result = graph.invoke(
    {"messages": [HumanMessage(content="Electromagnetic field kya hota hai? Thoda lamba batao.")]},
    {"configurable": {"thread_id": "multi-1"}},
)
for m in result["messages"]:
    if isinstance(m, AIMessage):
        print("----"); print(m.content)
```

## How it runs — step by step

1. `Annotated[list, add_messages]` — the `messages` field is tied with a **reducer**. Meaning when a node returns `{"messages": [...]}`, LangGraph **merges** (appends) it to the old messages, not replaces. Without the reducer, the last value would overwrite everything.
2. `next` field — a string that decides "who runs next." The supervisor sets it, the router reads it.
3. `add_conditional_edges("supervisor", route)` — after the supervisor, `route()` runs and returns a node-name or `END`. The graph moves ahead from there — not in a straight line.
4. Flow: START → supervisor (writer) → writer → supervisor (reviewer) → reviewer → supervisor (FINISH) → END. Each worker does its job, then comes back to the manager.

## Where does state go between workers?

Every worker updates its `messages` (which keep joining through the reducer). The reviewer sees all of the writer's messages and adds its review. One `messages` list = one shared board — everyone gets the same place.

## What It Is NOT

⚠️ **Multi-agent is NOT one big thread pool.** Every agent is a separate node/function, inside one graph — with shared state + routing.

⚠️ **The supervisor doesn't have to be model-driven.** Sometimes you can route with plain Python `if/else` (like the `route()` function). Asking the model is flexible, but not required.

⚠️ **Not every worker is a full LLM call.** Sometimes a worker is a tool call or a calculation — an agent is a "role," not a strict template.

## In Your Own Words

<details>
<summary>1. Why is the `add_messages` reducer necessary?</summary>

**Answer:** Without it, when a worker returns its message, the other worker won't have the old message (the state would overwrite). The reducer ensures new messages join the old ones — so a clean conversation keeps building.

</details>

<details>
<summary>2. Supervisor vs Worker — what's the difference?</summary>

**Answer:** The supervisor only decides "who runs next." The worker does the work — thinking, writing, tool calling. If the supervisor does the work itself, the logic gets confused. Keep role-separation.

</details>

<details>
<summary>3. What does `route()` return?</summary>

**Answer:** `route()` returns a node-name ("writer"/"reviewer") or `END`. Conditional edges use it — the graph doesn't move straight, it dynamically decides which node runs next.

</details>
