# 3.7 Agentic RAG

In 3.6 we saw — a `RAG` class that takes a bare query, searches once (k=3), gives the LLM the context, and returns the answer. But in reality an agent isn't satisfied with one search — sometimes it searches again, rewords the query and tries again, sometimes decides it's enough. **Simple RAG = one fixed search. Agentic RAG = the LLM itself decides how many times, what to search, until when.**

## The limit of simple RAG

The simple pipeline (3.5) calls `retriever.get_relevant_documents(q)` only once — then the LLM generates. If the first chunk feels wrong — the LLM chokes on that wrong context. The agent thinks: *"should I search more?"* — then searches again — rewrites the query — searches again — until it finds the right one.

## Agentic RAG = agent loop + retrieval tool

Bridge (Phase 2, 2.3): the ReAct agent — *"think → act → observe → think..."*. Same here — instead of "action," there's not just one retrieval but one or two retrieval tools — the LLM decides which to call, how many times, until when. Structure doc: *"Agentic RAG = the LLM decides how to search (rewrite the query, search multiple times, decide when it has enough)."*

## Code: retrieval as a TOOL → agent

```python
# 3.7_agentic_rag.py — LangChain ReAct agent + retrieval tool
import os
from dotenv import load_dotenv; load_dotenv()
from langchain_community.document_loaders import TextLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_community.vectorstores import FAISS
from langchain_groq import ChatGroq
from langchain_core.tools import tool
from langchain.agents import create_react_agent, AgentExecutor
from langchain_core.prompts import ChatPromptTemplate

# (1) data side — same as 3.5
docs   = TextLoader("rag_example.txt").load()
chunks = RecursiveCharacterTextSplitter(500, 50).split_documents(docs)
emb    = HuggingFaceEmbeddings(model_name="BAAI/bge-small-en-v1.5")
db     = FAISS.from_documents(chunks, emb)

# (2) retrieval as a TOOL — the LLM calls it when it needs to search
@tool
def search(query: str) -> str:
    """Search company documents for discounts/policies."""
    docs = db.as_retriever(search_kwargs={"k": 3}).get_relevant_documents(query)
    return "\n\n".join(d.page_content for d in docs)

# (3) LLM — ChatGroq + llama-3.3-70b-versatile
llm = ChatGroq(model="llama-3.3-70b-versatile", temperature=0.3)

# (4) ReAct prompt — after a tool call the LLM comes back to think
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful RAG agent. Use the search tool only when needed."),
    ("human", "{input}"),
    ("placeholder", "{agent_scratchpad}"),
])

# (5) agent + executor
agent = create_react_agent(llm, tools=[search], prompt=prompt)
ex    = AgentExecutor(agent=agent, tools=[search], verbose=True, max_iterations=3)

# (6) run — the LLM itself decides how many times to search
print(ex.invoke({"input": "College students ke liye discount kya milta?"})["output"])
```

Line by line: (1) data side — the 3.5 version, now `db` ready. (2) `@tool` — turns `search` into a LangChain tool — the docstring tells the LLM when to call it; `get_relevant_documents` — chunks → string. (3) `ChatGroq(..., temperature=0.3)` — generation LLM. (4) ReAct prompt — system role + user input + `agent_scratchpad` placeholder — the agent's thought-trace arrives here. (5) `create_react_agent` — builds the agent; `AgentExecutor` runs it — `verbose=True` shows tool calls — `max_iterations=3` anti-loop. (6) `ex.invoke({"input": q})` — the LLM first thinks — (maybe a tool call) — sees the result — then generates — **this is the agentic behaviour: the LLM itself decided that search was needed.**

## Nutshell

Agentic RAG = agent loop + retrieval tool; the LLM itself decides how many times to search — more flexible + accurate than simple RAG.

## Common Mistakes
- ❌ `max_iterations` too big (10) → agent can get stuck in a loop → fix: keep 2-3
- ❌ k too big in the retrieval tool (10) → context overflow → fix: k=3
- ❌ Sent the agent without a tool → it won't search at all → fix: `tools=[search]` is required

## What It Is NOT
- ⚠️ Not every query needs a search — for simple factual answers the agent can reply directly
- ⚠️ Not safe from infinite loops — `max_iterations` must be set — otherwise the agent keeps circling
- ⚠️ Not smart retrieval — the agent decides *when* to search, but *how* to search is still fixed (top-k) — improves further in 3.6's modular version

## In Your Own Words

<details>
<summary>1. What's the difference between simple RAG and Agentic RAG?</summary>
**Answer:** Simple RAG searches once and hands it to the LLM. In Agentic RAG the LLM itself decides — sometimes once, sometimes again, with a changed query — until the right context is found.
</details>

<details>
<summary>2. What is the `agent_scratchpad` placeholder?</summary>
**Answer:** This is the place where the agent's thinking steps (thoughts, tool calls, results) are stored. The LLM learns what it thought earlier and what result came — so it can take the next step.
</details>

<details>
<summary>3. Why set `max_iterations=3`?</summary>
**Answer:** Anti-loop safety. If the agent can't find the right answer, it would keep searching. Limiting to 3 steps — either the answer is found, or a fallback answer comes.
</details>
