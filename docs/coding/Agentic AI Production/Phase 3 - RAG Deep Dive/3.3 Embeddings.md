# 3.3 Embeddings

In 3.2 chunks were made — now a question arises: **how will FAISS know which chunk is the "student discount" one, when the user asks *"what's the discount policy?"*?** FAISS only compares number-lists (vectors) — not text. So first this text chunk must become a **384-number vector**.

## What an embedding is — the zip-code analogy

Think of each chunk as a city, and the embedding as that city's **zip code** — a 384-number address that tells the *meaning location* of that chunk. The closer two cities are, the closer their meaning:

```
"student discount 50% off"  → [0.21, -0.05, 0.84, ... 0.10]   (384 numbers)
"50% off student discount"  → [0.22, -0.04, 0.85, ... 0.11]   (very close!)
"stock market crash"        → [-0.71, 0.60, 0.12, ... -0.33]  (completely different)
```

The user's question gets an embedding too — FAISS hands back the 3-5 chunks whose zip codes are closest.

## bge-small-en-v1.5 — why this one?

- **Name:** `BAAI/bge-small-en-v1.5` (Beijing Academy of AI)
- **Dimension:** 384 — small, fast, good accuracy-to-size ratio
- **Local + free:** after download, no API/rupees — runs on CPU
- **Retrieval-optimized:** trained for *query vs passage* matching — same-meaning sentences land close

## Cosine similarity — the math of "how close"

We look at the **angle** between vectors — dot product divided by norms. bge's embeddings are **L2-normalized** (magnitude always 1) — so `dot(a,b)` itself becomes the cosine — FAISS doesn't have to normalize separately.

## Code: see text → vector

```python
# 3.3_embeddings.py
from langchain_huggingface import HuggingFaceEmbeddings
import numpy as np

emb = HuggingFaceEmbeddings(model_name="BAAI/bge-small-en-v1.5")

q   = "Student discount kitna hai?"
good = "Student discount 10th standard ko 50% off milta hai."
bad  = "Stock market today crashed by 12%."

vq = emb.embed_query(q)              # (1) query → vector
vg = emb.embed_query(good)          # (2) passage → vector
vb = emb.embed_query(bad)           # (3) unrelated → vector

print("len:", len(vq))                              # should be 384
print("sim(q,good):", round(float(np.dot(vq, vg)), 3))  # ~0.8+
print("sim(q,bad): ", round(float(np.dot(vq, vb)), 3))  # ~0.2
```

Line by line: `embed_query(text)` — one sentence → 384-number vector (for the user query). `embed_documents([list])` — multiple → vectors (when building the index) — you could write 3 queries at once here. `len(vq)` — dimension check — should be 384 — if you get 768, the wrong model is running. `np.dot(vq, vg)` — because of normalization, the dot product = cosine — high value = close.

## Nutshell

Embedding = text → 384-number vector; same-meaning vectors land close; cosine (dot) similarity measures how close they are.

## Common Mistakes
- ❌ One model for the query, another for the index → dim mismatch crash → fix: reuse one `HuggingFaceEmbeddings` object
- ❌ Forgot L2-normalize → cosine comes out wrong → fix: bge normalizes built-in — or manually via `from numpy.linalg import norm`
- ❌ Treated embedding as a perfect synonym detector → nuances get missed → fix: test the RAG pipeline end to end, check chunk quality

## What It Is NOT
- ⚠️ Not perfect semantic understanding — "bank" (river vs finance) can confuse
- ⚠️ Not human-readable numbers — no single number has a meaning; only the vector's *direction* matters
- ⚠️ Not keyword search — "discount" → "bargain" will match, "discount" → "discount" isn't always higher

## In Your Own Words

<details>
<summary>1. Why is the embedding dimension 384?</summary>
**Answer:** Trade-off — more dimensions can give better accuracy but slower + bigger memory. 384 is a small size that's enough for retrieval. The model got this dimension at training time.
</details>

<details>
<summary>2. What's the difference between `embed_query` and `embed_documents`?</summary>
**Answer:** Functionally the same model runs — both turn text → vector. The difference is convention: `embed_query` for one document, `embed_documents` for a list; sometimes query gets different normalization.
</details>

<details>
<summary>3. Cosine similarity vs Euclidean distance — which is better for retrieval?</summary>
**Answer:** Cosine — because it looks at direction, not magnitude. A long document and a short answer — both same topic — cosine brings them close, Euclidean can be biased by length.
</details>
