# 3.2 Chunking Strategies

In 3.1 we saw — you can't put the whole document into FAISS, you have to break it first. A small text file was small, but imagine your company policy is a **200-page PDF**. Put it in one chunk? No — two problems: (1) the context window fills up, (2) retrieval quality drops (the most relevant chunk becomes the whole document, no filtering happened).

## Why break it up — a textbook analogy

When a chapter is big, you split it into sections — each section holds one independent idea. Same for a chunk: one chunk holds one **coherent idea or paragraph**, so that at retrieval time the right piece can be pulled out.

- **chunk_size** — how many characters/words in one chunk (1000 = ~150-250 words).
- **chunk_overlap** — repeat the previous chunk's last `overlap` chars at the start of the next chunk — so a concept broken at the boundary still has its full info in both.

## 3 strategies — which one do you need?

**1. Fixed-size** — breaks at every fixed number of chars. Simple, but can split a word in the middle.

**2. Recursive (recommended)** — `RecursiveCharacterTextSplitter` first tries `\n\n` (paragraph) — if that doesn't work, `\n` (line) — then `" "` (space) — then character. Meaning: break at **logical boundaries** first, only fall to character-level when necessary.

**3. Token-aware** — (detail in 3.6) — break according to the LLM's token limit (one word can sometimes be 3 tokens).

## Code: different chunk_size — what difference does it make?

```python
# chunk_compare.py
from langchain.text_splitter import RecursiveCharacterTextSplitter

doc = "The student discount gives 50% off for grades 6-10. " * 20  # 20x repeat = big text

for size in (200, 500, 1000):
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=size,
        chunk_overlap=0,          # no overlap first — only look at size
        separators=["\n\n", "\n", " ", ""]
    )
    chunks = splitter.split_text(doc)
    print(f"chunk_size={size} -> {len(chunks)} chunks; first len={len(chunks[0])}")
```

Line by line: `"..." * 20` — repeated one idea 20 times — made the document big. `RecursiveCharacterTextSplitter` — separators in priority order — paragraph first, then space, finally char. `split_text(doc)` — text → chunk list. `len(chunks[0])` — length of the first chunk — should be a bit less than size (because it cuts at the paragraph boundary).

## Goldilocks rule — how to pick chunk_size?

- **100-300 chars** — FAQ / short fact — precise retrieval, but boundary cuts happen.
- **500-1000 chars** — paragraphs / snippets — readable + good retrieval — **most common sweet spot**.
- **1500+ chars** — essays — full context, but can fill the prompt, dilution.

**Rule:** chunk_size ≈ your **typically expected answer length**. If the answer is 2-3 paragraphs — 600-800 chars. If it's a 1-line fact — 150-300 chars.

**Troubleshooting:**
- chunks = 1 → the document is too small → do `".... " * 50` or write a bigger file
- different counts → the text must be the same — (no randomness) — check the doc string
- even with overlap=0 it looks fine — but don't forget 10-20% overlap in production

## Nutshell

Chunking = breaking the document into small pieces where each holds one complete idea — size 500-1000 chars, overlap 100-200.

## Common Mistakes
- ❌ `overlap=0` — a concept broken at the boundary comes back half-and-half → fix: always 10-20% overlap (chunk_size/5 or 100-200)
- ❌ `chunk_size` too big (e.g. 8000) — one chunk holds the whole doc → diluted retrieval + context overflow → fix: start at 500-1000
- ❌ Only looked at char count, not tokens → LLM goes out of context → fix: token-aware splitter in 3.6, or rough estimate `chars * 0.25 ≈ tokens`

## What It Is NOT
- ⚠️ Not a simple `text.split(" ")` — that breaks words randomly — a proper splitter breaks at boundaries
- ⚠️ Not always perfect — chunk quality still depends on doc structure — messy PDFs (scanned) need OCR (next phases)
- ⚠️ Not one-size-fits-all — legal docs vs code docs vs FAQs — need different chunk_size

## In Your Own Words

<details>
<summary>1. Why is overlap necessary?</summary>
**Answer:** Because if a concept spans two chunks — half in the first, half in the second — retrieving either one gives a partial result. Overlap repeats so both hold the full info.
</details>

<details>
<summary>2. Where is the "recursion" in RecursiveCharacterTextSplitter?</summary>
**Answer:** Recursion = trying the separator list recursively — first `\n\n`, fail → `\n`, fail → `" "`, fail → char. It keeps dropping to a smaller separator until the chunk reaches the target size.
</details>

<details>
<summary>3. Character split vs token split — which is right?</summary>
**Answer:** Token — because the LLM counts tokens. But token splitting is slow — so we experiment with the char splitter first, then put token-aware in 3.6's modular version.
</details>
