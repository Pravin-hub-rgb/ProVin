# 3.6 Modular RAG for Production

3.5's pipeline was a single file (`3.5_full_rag.py`) — everything at once. But in the capstone (9.x) when 5 documents, 3 query types, and monitoring come in — one file gets very messy. Production code becomes understandable only when every big thing takes **one class / one responsibility**.

## Why production code is modular

Think of a restaurant — can the water-server take orders too? No — one brings water, one takes orders, one cooks. Same in RAG — **EmbeddingManager, TextProcessor, VectorStore, RAG** — each class holds one responsibility. (The transcript showed exactly this architecture.)

## Code: 4 classes + 1 orchestrator

```python
# 3.6_modular_rag.py
import os
from dotenv import load_dotenv; load_dotenv()          # GROQ_API_KEY in env
from langchain_community.document_loaders import DirectoryLoader
from langchain_text_splitter import RecursiveCharacterTextSplitter
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_community.vectorstores import FAISS
from langchain_groq import ChatGroq
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

class EmbeddingManager:                        # (1) only embeddings
    def __init__(self, model="BAAI/bge-small-en-v1.5"):
        self.emb = HuggingFaceEmbeddings(model_name=model)
    def embed_query(self, t): return self.emb.embed_query(t)

class TextProcessor:                           # (2) load + chunk
    def __init__(self, size=500, overlap=50):
        self.sp = RecursiveCharacterTextSplitter(size, overlap)

class VectorStore:                             # (3) embed + store + persist
    def __init__(self, emb_mgr, path="faiss_index"):
        self.emb = emb_mgr.emb; self.path = path
    def build(self, chunks):
        db = FAISS.from_documents(chunks, self.emb); db.save_local(self.path); return db
    def load(self):
        return FAISS.load_local(self.path, self.emb, allow_dangerous_deserialization=True)

class RAG:                                     # (4) retriever + generator
    def __init__(self, vs, k=3):
        self.db = vs.load(); self.k = k
        self.retriever = self.db.as_retriever(search_kwargs={"k": k})
        self.llm = ChatGroq(model="llama-3.3-70b-versatile", temperature=0.3)
        self.prompt = ChatPromptTemplate.from_template("Answer ONLY:\n{ctx}\n\nQ: {q}")
    def _fmt(self, d): return "\n\n".join(x.page_content for x in d)
    def query(self, q):
        chain = {"ctx": self.retriever | self._fmt, "q": RunnablePassthrough()} | self.prompt | self.llm | StrOutputParser()
        return chain.invoke(q)

# === use — the capstone (9.x) will reuse these classes
emb_mgr = EmbeddingManager(); tp = TextProcessor()
db = VectorStore(emb_mgr)                     # build once, then load_local
docs = DirectoryLoader("docs", glob="**/*.txt").load()
print(RAG(db, k=3).query("Student discount kya hai?"))
```

Line by line: `EmbeddingManager` — embedding model in one place; `.emb` reused — dim match on index+query. `TextProcessor` — split config in one place. `VectorStore.build` — embed+index+**save_local**; `.load` — reload from disk (don't rebuild). `RAG` — retriever+LLM+prompt as one unit; `_fmt` — Documents→string. `chain` LCEL — the 3.5 version, but reusable; `RAG(db).query(q)` — one clean call. `DirectoryLoader(glob="**/*.txt")` — loads the whole folder.

## TEST

**Run:** `python 3.6_modular_rag.py` (docs/ folder with 1+ .txt file + GROQ_API_KEY)

**Expected:**
```
Student discount 10th standard ko 50% off milta hai.
```

**Troubleshooting:**
- `DirectoryLoader` → 0 docs → the `docs/` folder is empty or glob wrong → try `**/*.md`
- rebuild vs load error → first run `build` to make `faiss_index/`, then `load` — don't call build twice
- `self` attribute missing → common for Python beginners → double-check constructors
- ChatGroq 401 → `GROQ_API_KEY` not in env → check `.env` or export

## Nutshell

Modular RAG = 4 classes (Embedding / TextProcessor / VectorStore / RAG); each class one responsibility — the capstone will reuse them.

## Common Mistakes
- ❌ Rebuild the index every run → slow + overwrite → fix: build save_local, then load_local
- ❌ Retriever + index on different models → dim mismatch → fix: inject one `EmbeddingManager`
- ❌ `langchain.text_splitter` import → deprecated in langchain>=0.3 → fix: `langchain_text_splitter`

## What It Is NOT
- ⚠️ Not over-engineering — the 3.5 single-file version is fine for a small experiment
- ⚠️ Not framework magic — this is just organizing code — no new pipeline
- ⚠️ Not about class count — SRP (single responsibility) matters, not count

## In Your Own Words

<details>
<summary>1. Single file vs 4 classes — when to switch?</summary>
**Answer:** Prototype → single file (3.5). When 2+ query types / bulk docs / retry needed — make a class. Rule: when you start copy-pasting a second time — make it a class.
</details>

<details>
<summary>2. What does reusing `self.emb` do?</summary>
**Answer:** One embedding object — for both index build and query — so dims stay the same. Using a different model crashes at FAISS load.
</details>

<details>
<summary>3. Why `allow_dangerous_deserialization` on `load_local`?</summary>
**Answer:** FAISS saves a pickle — Python deserializes it — security warning — local trusted file — safe — but the flag must be passed.
</details>
