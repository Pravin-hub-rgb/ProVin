## What This Topic Is Asking (Simple Terms)

A collection of the most common JavaScript mistakes that trip up beginners and even experienced developers. Each one is a real bug pattern with a concrete example and the fix.

---

## 1. Forgetting `new` with Constructor Functions

```js
function Person(name) {
  this.name = name;
}

const p = Person("Vin");  // ❌ forgot `new`
// this = window → window.name = "Vin" (global leak!)
// p = undefined

const p2 = new Person("Vin"); // ✅
// p2 = { name: "Vin" }
```

**Fix:** Always use `new` with constructor functions. Or use classes (which throw if called without `new`).

---

## 2. Not Checking `res.ok` After `fetch`

```js
const res = await fetch("/api/users");
const data = await res.json(); // ❌ if 404, this parses an error page

// ✅ always check
if (!res.ok) throw new Error(`HTTP ${res.status}`);
const data = await res.json();
```

**Why:** `fetch` resolves even on 404/500 — it only rejects on network failure. Without the check, you try to parse an error page as JSON.

## 3. Sequential `await` Where `Promise.all` Fits

```js
// ❌ Slow: 2 seconds (1s + 1s)
const a = await fetchA();
const b = await fetchB();

// ✅ Fast: 1 second (both at once)
const [a, b] = await Promise.all([fetchA(), fetchB()]);
```

**When to use sequential:** only when the second fetch needs data from the first.

## 4. Mutating Prototype Affecting All Instances

```js
function Dog(name) { this.name = name; }

const rex = new Dog("Rex");

// ❌ Adding to prototype affects ALL instances
Dog.prototype.bark = function() { return `${this.name} barks!`; };

// Now even instances created BEFORE this line get bark()
rex.bark(); // "Rex barks!" — surprise!
```

**Fix:** Define all methods on the prototype inside the constructor function, or use classes.

---

## 5. Leaking Closures Holding Large Objects

```js
function createHandler() {
  const hugeData = new Array(1000000).fill("data");

  return function handler() {
    // hugeData is still referenced — never garbage collected
    console.log("handled");
  };
}

const handler = createHandler();
// hugeData stays in memory forever, even though handler doesn't use it
```

**Fix:** Set `hugeData = null` inside the handler after you're done, or restructure to avoid capturing large data.

## 6. `this` Lost in Callbacks

```js
const obj = {
  name: "Vin",
  greet() {
    console.log(this.name);
  },
};

setTimeout(obj.greet, 1000); // ❌ "undefined" — this is window/global

// ✅ Fix 1: arrow function
setTimeout(() => obj.greet(), 1000);

// ✅ Fix 2: bind
setTimeout(obj.greet.bind(obj), 1000);
```

**Why:** `this` is determined by *how* the function is called, not where it's defined. Passing `obj.greet` as a callback calls it as a standalone function, so `this` is `window`.

## 7. Forgetting `break` in `switch`

```js
const day = "Monday";
switch (day) {
  case "Monday":
    console.log("Monday");
    // missing break → falls through!
  case "Tuesday":
    console.log("Tuesday");
    break;
  default:
    console.log("Other");
}
// Prints: "Monday" AND "Tuesday" (fall-through bug)
```

**Fix:** Always add `break` after each case (or `return` if inside a function).

## 8. `sort()` Without Comparator on Numbers

```js
const nums = [10, 2, 1];
nums.sort(); // ❌ [1, 10, 2] — string sort!

nums.sort((a, b) => a - b); // ✅ [1, 2, 10] — numeric sort
```

## 9. Mutating State Directly (React)

```js
// ❌ Mutating state directly — React won't re-render
const [items, setItems] = useState([1, 2, 3]);
items.push(4);
setItems(items); // same reference, React skips re-render

// ✅ Create new array
setItems([...items, 4]);
```

## 10. Not Handling Loading/Error States

```js
// ❌ No loading state — user sees blank screen for 3 seconds
const data = await fetch(url);
render(data);

// ✅ Show loading, then data, then error
setLoading(true);
try {
  const data = await fetch(url);
  setData(data);
} catch (e) {
  setError(e.message);
} finally {
  setLoading(false);
}
```

## 11. Stale Closures in `useEffect`

```js
const [count, setCount] = useState(0);

useEffect(() => {
  const timer = setInterval(() => {
    console.log(count); // ❌ always 0 — stale closure
  }, 1000);
  return () => clearInterval(timer);
}, []); // empty deps → count is frozen at 0

// ✅ Fix: add count to deps, or use functional update
useEffect(() => {
  const timer = setInterval(() => {
    setCount((c) => c + 1); // ✅ uses latest state
  }, 1000);
  return () => clearInterval(timer);
}, []);
```

---

## 12. `for...in` on Arrays

```js
const arr = [10, 20, 30];

// ❌ for...in gives string indices + inherited properties
for (const i in arr) {
  console.log(i, arr[i]); // "0" 10, "1" 20, "2" 30 (strings!)
}

// ✅ Use for...of or forEach
for (const val of arr) console.log(val); // 10, 20, 30
arr.forEach((val, i) => console.log(i, val)); // 0 10, 1 20, 2 30
```

## What This Topic Is NOT

- ❌ Common mistakes are not the same as **syntax errors** — syntax errors are caught by the parser. These are *logic* errors that run fine but produce wrong results.
- ❌ These mistakes are not **edge cases** — they're everyday patterns that trip up beginners and experienced developers alike.

## In Your Own Words

1. Why is forgetting `new` with a constructor function dangerous? What happens to `this`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Without `new`, `this` refers to the global object (`window` in browsers). The constructor's properties get set on `window` (global leak), and the function returns `undefined`. Example: `const p = Person("Vin")` sets `window.name = "Vin"` and `p` is `undefined`. With `new`, `this` is a new empty object, properties are set on it, and it's returned. Classes fix this by throwing an error if called without `new`.

</details>

2. Why does `fetch` need a `res.ok` check? Doesn't it reject on errors?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `fetch` only rejects on network failure (no internet, DNS error, CORS block). It resolves even on HTTP errors (404, 500, 401) — the server responded, just with an error status. `res.ok` is `true` for 2xx responses. Without the check, you'd try to parse an error page as JSON, which might fail or produce garbage data. Always check `res.ok` before parsing.

</details>

3. What's a stale closure, and how do you fix it in `useEffect`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A stale closure happens when a function captures a variable from its outer scope, but that variable has changed since the function was created. In `useEffect` with empty deps `[]`, the effect runs once, and any variable it references is frozen at its initial value. Fix: add the variable to the deps array, or use a functional update (`setCount(c => c + 1)`) which always uses the latest state.

</details>

## Cheat Sheet (Quick Recall)

**Constructor:** Always `new`. Without it, `this` = `window`, properties leak globally.

**fetch:** Check `res.ok` before parsing. `fetch` only rejects on network failure.

**Promise.all:** Use for independent fetches. Sequential `await` is slower.

**Prototype:** Don't mutate after instances exist. Set all methods in constructor or class.

**`this` in callbacks:** Use arrow functions or `.bind()`. Passing a method as callback loses `this`.

**switch:** Always `break`. Without it, cases fall through.

**sort():** Always pass comparator for numbers: `(a, b) => a - b`.

**React state:** Never mutate directly. Create new arrays/objects.

**useEffect:** Add deps for variables you use. Use functional updates to avoid stale closures.

**for...in on arrays:** Don't. Use `for...of` or `forEach`.

**Key rule:** Most bugs come from not understanding *when* code runs (hoisting, closures, async) and *what* `this` is. Master execution context and `this` binding.
