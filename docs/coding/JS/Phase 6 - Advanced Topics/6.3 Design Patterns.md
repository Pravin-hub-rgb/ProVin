## ✅ Module Pattern ⭐

**The problem:** In JavaScript, everything is public by default. Any variable you declare at the top level can be accessed and overwritten by any other script on the page.

```js
let count = 0;  // any other script can do: count = "hacked"
```

In large codebases, this causes bugs where one part of your app accidentally overwrites the data of another part. You need a way to create **private state** — variables that no code outside a specific module can touch.

**The solution:** The Module pattern uses an IIFE (Immediately Invoked Function Expression) combined with closures. Variables inside the IIFE are private — only the functions that are explicitly returned can access them.

```js
const counter = (function() {
  // ✅ This variable is completely private
  // No one can access it from outside
  let count = 0;

  // ✅ Only what we return is public
  return {
    increment: function() {
      count++;
    },
    decrement: function() {
      count--;
    },
    getCount: function() {
      return count;
    }
  };
})();
```

✅ Usage:
```js
counter.increment();
counter.increment();

console.log(counter.getCount()); // 2

console.log(counter.count); // undefined ❌ You cannot access it
```

The `count` variable is completely hidden from the outside world. The only way to interact with it is through the three methods we chose to expose. This is how every JavaScript library is written.

## ✅ Observer Pattern ⭐⭐

**The problem:** What if multiple independent parts of your app need to react to the same event? For example, when a user logs in, you need to:
- Update the navbar to show the user's name
- Redirect to the dashboard
- Send analytics data
- Show a welcome notification

You could hardcode all of this into the login function:

```js
function login(user) {
  // ... login logic ...
  updateNavbar(user.name);
  redirectToDashboard();
  sendAnalytics("login", user.id);
  showWelcomeNotification(user.name);
}
```

But every time you need to add a new action on login, you have to modify the login function. It becomes bloated, tightly coupled, and changes to one action can break the others.

**The solution:** The Observer pattern lets one object broadcast events to many listeners without the broadcaster knowing who is listening. The login function just says "I logged someone in" and any number of listeners can react independently.

```js
events.emit('userLoggedIn', user);
// Who listens? The login function doesn't care. It just broadcasts.
```

✅ This pattern is everywhere — React, Redux, Vue, Angular, Node.js events all use this.

```js
class EventEmitter {
  constructor() {
    this.events = {};
  }

  // Subscribe to an event
  on(eventName, callback) {
    if (!this.events[eventName]) {
      this.events[eventName] = [];
    }
    this.events[eventName].push(callback);
  }

  // Trigger an event
  emit(eventName, data) {
    if (this.events[eventName]) {
      this.events[eventName].forEach(callback => callback(data));
    }
  }

  // Unsubscribe
  off(eventName, callback) {
    if (this.events[eventName]) {
      this.events[eventName] = this.events[eventName].filter(cb => cb !== callback);
    }
  }
}
```

✅ Usage:
```js
const events = new EventEmitter();

events.on('userLoggedIn', (user) => {
  console.log(`Welcome ${user.name}`);
});

events.emit('userLoggedIn', { name: 'John' });
```

## ✅ Singleton Pattern

**The problem:** Some things in your app should only exist once. A database connection — creating a new one every time you need to query wastes resources. A configuration object — storing API keys, URLs, settings — creating multiple copies means they could get out of sync. A logger — multiple loggers writing to the same file would cause chaos.

But if nothing stops you, anyone can call `new AppConfig()` anywhere and create a duplicate:

```js
const config1 = new AppConfig();
const config2 = new AppConfig(); // why is this allowed? there should only be one
```

**The solution:** The Singleton pattern ensures that only one instance of a class ever exists. No matter how many times you call `new`, you always get the exact same object.

```js
class AppConfig {
  constructor() {
    // If instance already exists return it
    if (AppConfig.instance) {
      return AppConfig.instance;
    }

    // Otherwise create it
    this.apiUrl = "https://api.example.com";
    this.debug = true;

    // Save the instance
    AppConfig.instance = this;
  }
}
```

✅ Usage:
```js
const config1 = new AppConfig();
const config2 = new AppConfig();

console.log(config1 === config2); // true
```

✅ No matter how many times you call `new` you always get exactly the same object.

## ✅ When to use each

| Pattern | Use case |
|---------|----------|
| Module | When you need private state |
| Observer | When multiple things need to react to changes |
| Singleton | When you must have only one instance |
