## What This Topic Is Asking (Simple Terms)

Execution context is the "box" JavaScript creates when it runs code. It holds variables, functions, and the `this` value. Understanding it explains *why* closures work, *why* `this` changes, and *why* hoisting happens.

---

## What Is an Execution Context?

Every time JavaScript runs code, it creates an execution context — a container that holds everything needed to run that code:

- **Variable Environment** — all variables and functions declared in this scope
- **Scope Chain** — reference to the outer (parent) context
- **`this` binding** — what `this` refers to in this context

There are two types:

| Type | When created | Count |
|------|-------------|-------|
| **Global Execution Context** | When the script starts | One (always) |
| **Function Execution Context** | When a function is called | One per function call |

---

## The Call Stack

JavaScript uses a **call stack** to manage execution contexts. It's a LIFO (Last In, First Out) structure:

```js
function first() {
  console.log("first");
  second();
  console.log("first again");
}

function second() {
  console.log("second");
  third();
  console.log("second again");
}

function third() {
  console.log("third");
}

first();
```

**Call stack trace:**

```
1. Global context pushed
2. first() called → first() context pushed
   → "first" logged
3. second() called → second() context pushed
   → "second" logged
4. third() called → third() context pushed
   → "third" logged
5. third() returns → third() context popped
   → "second again" logged
6. second() returns → second() context popped
   → "first again" logged
7. first() returns → first() context popped
8. Global context remains
```

**Output:** `"first"`, `"second"`, `"third"`, `"second again"`, `"first again"`

## How Hoisting Works (via Execution Context)

When a function execution context is created, JavaScript does two passes:

**Pass 1 (Creation Phase):** Scan the code for variable and function declarations. Create memory space for them. `var` variables are initialized to `undefined`. Function declarations are fully hoisted (the entire function is available). `let`/`const` are in the "Temporal Dead Zone" (TDZ) — declared but not initialized.

**Pass 2 (Execution Phase):** Run the code line by line, assigning values and executing statements.

```js
console.log(x);  // undefined (var is hoisted, initialized to undefined)
var x = 5;
console.log(x);  // 5

console.log(y);  // ReferenceError (let is in TDZ)
let y = 5;

sayHi();         // "Hi!" (function declaration is fully hoisted)
function sayHi() { console.log("Hi!"); }
```

## Scope Chain

When JavaScript looks up a variable, it checks the current context first. If not found, it walks up the scope chain (parent contexts) until it finds it or reaches the global scope.

```js
const global = "I'm global";

function outer() {
  const outerVar = "I'm outer";

  function inner() {
    const innerVar = "I'm inner";
    console.log(innerVar);   // "I'm inner" (found in current scope)
    console.log(outerVar);   // "I'm outer" (found in parent scope)
    console.log(global);     // "I'm global" (found in global scope)
  }

  inner();
}

outer();
```

**Scope chain lookup:** `inner` → `outer` → `global`. If not found anywhere → `ReferenceError`.

## Closures (Revisited with Execution Context)

A closure happens when a function "remembers" variables from its parent scope even after the parent has finished executing. This works because the function's execution context retains a reference to the parent's variable environment.

```js
function createCounter() {
  let count = 0;  // lives in createCounter's context

  return function increment() {
    count++;       // increment still has access to count
    return count;
  };
}

const counter = createCounter();
// createCounter's context is "done" but count is NOT garbage collected
// because increment still references it

counter(); // 1
counter(); // 2
counter(); // 3
```

**Why it works:** The returned function (`increment`) keeps a reference to `createCounter`'s variable environment. Even though `createCounter` has finished executing, its variables are kept alive by the closure.

## `this` Binding in Execution Context

`this` is determined by *how* a function is called, not where it's defined:

| Call type | `this` value |
|-----------|-------------|
| Global function call | `window` (browser) / `global` (Node) |
| Method call (`obj.method()`) | `obj` |
| Constructor (`new Fn()`) | New instance |
| Arrow function | Lexical `this` (inherited from parent) |
| `call`/`apply`/`bind` | Explicitly set |

```js
const obj = {
  name: "Vin",
  greet() {
    console.log(this.name); // "Vin" — this is obj
  },
  greetArrow: () => {
    console.log(this.name); // undefined — this is global (arrow inherits)
  },
};

obj.greet();        // "Vin"
obj.greetArrow();   // undefined
```

## Common Mistakes

- **Forgetting that `this` changes with call context** — passing a method as a callback loses `this`. Fix: use arrow functions or `.bind()`.
- **Assuming closures copy values** — closures reference variables, not values. If the variable changes, the closure sees the new value.
- **Not understanding hoisting with `let`/`const`** — they're in the TDZ until their declaration line. Accessing them before throws `ReferenceError`.
- **Stack overflow** — infinite recursion fills the call stack. Fix: add a base case.

---

## What This Topic Is NOT

- ❌ Execution context is not the same as **scope** — scope is the *lexical* rules (where variables are accessible). Execution context is the *runtime* container that enforces those rules.
- ❌ Call stack is not the same as **event loop** — call stack is synchronous execution. Event loop handles async callbacks.
- ❌ Closures are not the same as **classes** — closures use function scope, classes use prototype chain. Both can create private state, but differently.

1. What is an execution context, and when is it created?

**Sample Answer:** An execution context is a container that holds everything needed to run a piece of code: variables, functions, scope chain, and `this` binding. The global execution context is created when the script starts (one per script). A function execution context is created every time a function is called. 2. Why does a closure keep a variable alive even after the outer function has finished?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because the inner function still references the outer function's variable environment. JavaScript's garbage collector won't remove variables that are still referenced. The closure "remembers" the scope chain at the time it was created, so the outer variables stay alive as long as the inner function exists.

</details>

3. What's the difference between the creation phase and the execution phase in an execution context?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Creation phase: JavaScript scans for declarations and allocates memory. `var` is initialized to `undefined`, function declarations are fully hoisted, `let`/`const` are in the TDZ (declared but not initialized). Execution phase: code runs line by line, values are assigned, statements are executed. This two-phase process is why hoisting works — declarations are processed before execution.

</details>

## Cheat Sheet (Quick Recall)

**Execution context:** container with variable env, scope chain, `this`. Created per function call.

**Call stack:** LIFO. Function called → pushed. Function returns → popped. Empty stack = done.

**Hoisting:** Creation phase allocates memory. `var` → `undefined`. `let`/`const` → TDZ. Function declarations → fully available.

**Scope chain:** inner → outer → global. Not found → `ReferenceError`.

**Closure:** inner function remembers outer variables. Variables stay alive as long as inner function exists.

**`this`:** determined by call type, not definition. Global → `window`. Method → object. Arrow → lexical. Constructor → instance.

**Key rule:** Understand the creation phase to understand hoisting. Understand the scope chain to understand closures. Understand `this` binding to understand method behavior.
