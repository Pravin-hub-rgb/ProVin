In the last phase, you learned about scope — where variables can be accessed. You know that inner functions can access outer variables, but outer functions can't access inner ones. But what happens when a function finishes running? Are its variables gone forever?

Turns out, not always. And that's where closures come in.

---

## The Bank Vault Analogy

Imagine you walk into a bank. You put ₹10,000 in a safety deposit box. The bank gives you a key. You leave the bank. The bank is still open, still running, but your transaction is done.

You come back the next day with your key. You open the same box, and your ₹10,000 is still there. The bank remembered your money even though you left and came back.

Now imagine you go to a restaurant instead. You order food, eat it, pay, and leave. If you come back the next day and ask for the same food, they'll look at you confused. The restaurant doesn't remember you.

What's the difference? The bank gave you a key (a reference) that lets you access your box later. The restaurant didn't give you anything to hold onto.

A closure is like that bank key. It lets you access variables from an outer function even after that function has finished running.

---

## ✅ What is a closure?

> **A closure is when an inner function retains access to variables from its outer lexical scope, even after the outer function has finished executing.**

Let's unpack that.

**"Inner function retains access"** — you have a function inside another function. The inner function "remembers" the outer function's variables.

**"Lexical scope"** — scope is determined by where the code is written. The inner function was written inside the outer function, so it has access to the outer function's variables.

**"Even after the outer function has finished executing"** — normally, when a function finishes, its local variables are destroyed. With closures, the inner function keeps a reference to those variables, keeping them alive.

---

## ✅ First, the problem closures solve

Imagine you want a counter. Every time you call a function, the number goes up by 1.

You could use a global variable:

```js
let count = 0;

function increment() {
  count++;
  console.log(count);
}

increment(); // 1
increment(); // 2
increment(); // 3
```

It works. But now `count` is public. Anyone can change it from anywhere in the entire codebase:

```js
count = 999999; // works perfectly. No security at all.
```

That's a problem. You want the counter to be private — only the `increment` function should be able to change it.

---

## ✅ The bank analogy again

- `createCounter()` = The bank
- `count` = Your money inside the bank
- `increment` = Your ATM card

You can't go inside the bank and change the number directly. You can only use the ATM card they give you.

That's a closure.

---

## ✅ How closures work

You wrap everything inside an outer function. Then you return only the things you want to give access to.

```js
function createCounter() {
  let count = 0;

  function increment() {
    count++;
    console.log(count);
  }

  return increment;
}
```

What's happening:
- All variables are inside `createCounter()`
- No one can access `count` from outside
- We only return the `increment` function

```js
const myCounter = createCounter();

myCounter(); // 1
myCounter(); // 2
myCounter(); // 3
```

This works perfectly. It remembers. And `count` is 100% private — you cannot access it from outside.

---

## ✅ The part everyone misses

This is the most important question:

> "Why don't we get a new `count = 0` every time I call `myCounter()`?"

Because you are not calling `createCounter()` again. You called `createCounter()` **once**. Only once.

`myCounter()` is calling the inner `increment` function. It is NOT calling `createCounter()` again.

`createCounter()` already ran and finished. But `count` is still alive. It will live as long as `myCounter` exists.

This is the magic. This is what closure actually is.

---

## ✅ Why does this work?

Because of lexical scope. The inner function does not copy the value. It holds a **reference** to the actual variable itself.

And as long as someone holds that reference, the variable will never be garbage collected.

When you call `createCounter()`, it creates a new `count` variable and a new `increment` function. The `increment` function holds a reference to that specific `count`. Even after `createCounter()` finishes, `increment` keeps `count` alive.

If you call `createCounter()` again, you get a completely new counter with a new `count`:

```js
const counter1 = createCounter();
const counter2 = createCounter();

counter1(); // 1
counter1(); // 2
counter2(); // 1 — separate, independent counter
```

Each closure is independent. Each one holds its own private `count`.

## ✅ Real world use cases

1. **Data privacy** — keeping variables hidden from external code
2. **Memoization / Caching** — remembering expensive computations
3. **Event handlers in loops** — each handler gets its own private data
4. **Function factories** — creating customized functions on the fly
5. **Every React hook ever made** — `useState`, `useEffect`, all use closures

Every single React hook works because of closures.

## 🚨 The most famous interview trap

This exact question is asked in literally every junior developer interview:

```js
for (var i = 0; i < 3; i++) {
  setTimeout(function() {
    console.log(i);
  }, 100);
}
```

**This prints: `3, 3, 3`**

Why? Because `var i` is function scoped. There is only one single `i` variable. All three timeouts reference the exact same one. By the time the timeouts run, the loop has finished and `i` is `3`.

### The fix

Change `var` to `let`:

```js
for (let i = 0; i < 3; i++) {
  setTimeout(function() {
    console.log(i);
  }, 100);
}
```

**This prints: `0, 1, 2`**

Because `let` is block scoped. A completely new separate `i` is created for every single loop iteration. Each timeout gets its own private copy — its own closure over that specific `i`.

---

## ✅ What It Is NOT

- **A closure is NOT a copy of the variable.** The inner function holds a reference to the actual variable. If the variable changes later, the closure sees the new value. It's not a snapshot — it's a live connection.

- **A closure is NOT created by returning a function.** The closure happens when the inner function is created, not when it's returned. Even if you never return the inner function, the closure still exists.

- **Closures do NOT cause memory leaks by themselves.** They only cause leaks if you hold references longer than needed. Modern JavaScript engines are smart about cleaning up closures when they're no longer needed.

- **Not every nested function creates a useful closure.** The closure only matters if the inner function outlives the outer function. If the outer function returns immediately and the inner function is never referenced outside, there's no practical closure.

---

## 🧠 Interview Questions

> ❓ What is a closure?
> A closure is when an inner function retains access to variables from its outer lexical scope, even after the outer function has finished executing. The inner function holds a reference to the outer variables, not a copy.

> ❓ Why would you use a closure?
> For data privacy (keeping variables private), memoization/caching, creating function factories, and maintaining state across multiple function calls.

> ❓ What is the difference between a closure and a global variable?
> A closure keeps data private — only the returned functions can access it. A global variable is accessible from anywhere, which can lead to accidental modification and naming conflicts.

> ❓ What does the famous interview question with var in a loop demonstrate?
> It demonstrates that var is function-scoped, so all iterations share the same variable. With let (block-scoped), each iteration creates a new variable, and the closure preserves each one.

> ❓ How does garbage collection interact with closures?
> As long as a reference to the inner function exists, the outer variables are kept alive. When all references to the inner function are gone, the closure and its variables can be garbage collected.
