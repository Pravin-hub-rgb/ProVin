In the last topic, you learned how short-circuit evaluation (`||`, `&&`, `?.`) gives you fine-grained control over when code executes and how to avoid errors. There's another JavaScript feature where "weak" means something specific: WeakMap and WeakSet. These are special collections that hold weak references to their keys, helping you avoid memory leaks in applications that associate data with objects.

---

## The Library Book Tracking Analogy

Imagine a library where every book has a tracking chip. The library keeps a record linking each chip to the book's current borrower. When a book is returned and removed from the library entirely, the tracking record should disappear too — there's no point tracking a book that no longer exists.

A regular `Map` is like a system that holds the book physically by the chip — even if the book is gone, the record stays (memory leak). A `WeakMap` is like a system that says "if the book itself is gone, forget the record automatically." The record is weak — it doesn't keep the book alive. When the book is garbage collected (no more references to it), the record disappears with it.

---

## ✅ What is a WeakMap?

> **A WeakMap is like a Map, but its keys are weakly held. If a key object has no other references, it gets garbage collected — and the entry automatically disappears from the WeakMap.**

The key difference: `Map` holds strong references to both keys and values. `WeakMap` holds weak references only to its keys.

### Creating and using a WeakMap

```js
// Create a WeakMap
const userRoles = new WeakMap();

// Keys must be objects (not primitives like strings or numbers)
const user = { name: "Arjun" };
const admin = { name: "Priya" };

// Set key-value pairs (keys must be objects)
userRoles.set(user, "editor");
userRoles.set(admin, "admin");

// Get values
console.log(userRoles.get(user));   // "editor"
console.log(userRoles.get(admin));  // "admin"

// Check if a key exists
console.log(userRoles.has(user));   // true

// Delete a key
userRoles.delete(user);
console.log(userRoles.get(user));   // undefined
```

### Why keys must be objects

WeakMap keys must be objects because primitives like strings or numbers are compared by value, not by identity. If a primitive key could be garbage collected, another part of your code could accidentally claim the same key:

```js
const wm = new WeakMap();

wm.set("name", "value"); // ❌ TypeError: Invalid value used as weak map key
wm.set(42, "value");      // ❌ TypeError: Invalid value used as weak map key
wm.set(Symbol(), "value"); // ❌ TypeError
wm.set({ id: 1 }, "value"); // ✅ Object keys work
wm.set(function(){}, "value"); // ✅ Functions are objects
wm.set(document.body, "value"); // ✅ DOM elements are objects
```

### The garbage collection in action

```js
const wm = new WeakMap();

function processUser() {
  const user = { name: "Temp User" };
  wm.set(user, { permissions: ["read"] });
  
  // Do some work...
  return "done";
}

processUser();
// After this function returns, `user` has no references.
// The WeakMap entry automatically disappears.
// The permissions object is also garbage collected.
```

Compare this to a regular Map:

```js
const map = new Map();

function processUser() {
  const user = { name: "Temp User" };
  map.set(user, { permissions: ["read"] });
  
  return "done";
}

processUser();
// The Map entry stays forever — even though `user` is unreachable.
// This is a memory leak! The map holds a strong reference to `user`.
```

### Common use case: caching computed values

```js
const cache = new WeakMap();

function expensiveOperation(user) {
  // If we've already computed this user's data, return the cached result
  if (cache.has(user)) {
    console.log("Returning cached result");
    return cache.get(user);
  }

  // Otherwise, compute it (simulating expensive work)
  const result = { id: user.id, processed: Date.now() };
  cache.set(user, result);
  console.log("Computed new result");
  return result;
}

const user = { id: 42, name: "Arjun" };
expensiveOperation(user); // "Computed new result"
expensiveOperation(user); // "Returning cached result"

// When user is no longer referenced anywhere,
// the cache entry disappears automatically — no memory leak.
```

## ✅ What is a WeakSet?

> **A WeakSet is like a Set, but its values are weakly held. Only objects can be added, and if a value object has no other references, it gets garbage collected — and is automatically removed from the WeakSet.**

```js
// Create a WeakSet
const flaggedUsers = new WeakSet();

const user1 = { name: "Arjun" };
const user2 = { name: "Priya" };

// Add objects to the WeakSet
flaggedUsers.add(user1);
flaggedUsers.add(user2);

// Check membership
console.log(flaggedUsers.has(user1)); // true
console.log(flaggedUsers.has(user2)); // true

// Remove an entry
flaggedUsers.delete(user1);
console.log(flaggedUsers.has(user1)); // false
```

### Key differences from Set

| Feature | Set | WeakSet |
|---|---|---|
| Values can be primitives | Yes (strings, numbers, etc.) | No — only objects |
| Can iterate over values | Yes | No — no `.forEach()`, no `for...of` |
| Has `.size` property | Yes | No — size is unknowable |
| Values are garbage collected | No — strong references | Yes — weak references |

### Common use case: tracking "seen" objects

```js
const visitedNodes = new WeakSet();

function traverse(node) {
  // Skip if we've already visited this node (prevents infinite loops on cycles)
  if (visitedNodes.has(node)) {
    return;
  }
  
  visitedNodes.add(node);
  
  // Process the node...
  console.log("Visiting:", node.value);
  
  // Recurse into children
  for (const child of node.children) {
    traverse(child); // Safe — will not revisit visited nodes
  }
}
```

## ✅ WeakMap vs WeakSet vs Map vs Set

| Collection | Key/Value | Primitives? | Iterates? | Garbage Collected? |
|---|---|---|---|---|
| Map | key → value | Yes | Yes | No |
| Set | values only | Yes | Yes | No |
| WeakMap | key → value | No (keys must be objects) | No | Yes (keys are weak) |
| WeakSet | values only | No (must be objects) | No | Yes (values are weak) |

### When to use WeakMap

- Caching data associated with DOM elements (the DOM element gets removed → cache entry disappears)
- Storing private data on objects (the object is deleted → private data disappears)
- Tracking object metadata without causing memory leaks

### When to use WeakSet

- Tracking which objects have been visited (cycle detection in graph traversal)
- Marking objects with a flag (e.g., "this element has been seen")
- Any case where you need a set of objects but want automatic cleanup

---

## ✅ What It Is NOT

- **A WeakMap is NOT a drop-in replacement for Map.** WeakMaps cannot be iterated, don't have `.size`, and only accept object keys. Use a Map if you need primitives, iteration, or size tracking.

- **A WeakSet is NOT about weak references to values.** Both WeakMap and WeakSet hold weak references. The difference is that WeakMap keys are weak (entries are removed when the key is GC'd) while WeakSet entries are removed when the value itself is GC'd.

- **Weak references are NOT about immediate cleanup.** Garbage collection is asynchronous. An entry disappears from a WeakMap/WeakSet only when the garbage collector runs — which you cannot predict.

- **WeakMap/WeakSet are NOT for general-purpose data storage.** Use Map and Set for most cases. Only use WeakMap/WeakSet when you specifically need automatic cleanup of entries tied to object lifetimes.

## 🧠 Interview Questions

> ❓ What is the difference between Map and WeakMap?
> Map holds strong references to both keys and values — entries persist even if the key becomes unreachable, causing potential memory leaks. WeakMap only holds weak references to its keys — when a key object has no other references, it and its entry are automatically garbage collected. Map supports iteration, `.size`, and primitive keys; WeakMap does not.

> ❓ What is the difference between Set and WeakSet?
> Set holds strong references to values and supports iteration, `.size`, and primitive values. WeakSet holds weak references to values (objects only) — entries are garbage collected when the object is no longer referenced anywhere else. WeakSet cannot be iterated and has no `.size`.

> ❓ Why can WeakMap only use objects as keys, not primitives?
> Because primitives are compared by value, not by identity. If `"name"` could be a key, garbage collection of one `"name"` string would affect all entries using that same string value. Objects are compared by reference (identity), so the weak reference can uniquely track that specific object instance.

> ❓ What is a practical use case for WeakMap in the browser?
> A common use: associating data with DOM elements. `const metadata = new WeakMap(); metadata.set(domElement, { clicked: true })`. When the DOM element is removed from the document and no longer referenced, the WeakMap entry is automatically cleaned up — no manual cleanup needed.

> ❓ Can you iterate over a WeakSet? Why or why not?
> No. WeakSet (and WeakMap) are intentionally non-iterable. The number of entries can change at any time (as the garbage collector runs), so providing a stable iteration order or a reliable `.size` would be impossible.

> "WeakMap and WeakSet are collections that hold weak references to their keys/values. Unlike Map and Set (which hold strong references and prevent garbage collection), WeakMap and WeakSet allow their entries to be automatically cleaned up when the referenced object is no longer reachable elsewhere in the program. This makes them ideal for preventing memory leaks when associating data with objects (especially DOM elements). The trade-off is that they only accept object keys/values, are non-iterable, and have no `.size` property."

## In Your Own Words

1. You're building a web app that attaches a click handler to many DOM buttons. You want to track which buttons have been clicked. Why would a WeakSet be a better choice than a regular Set for this use case?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A regular Set holds strong references to the DOM elements. Even if a button is removed from the page, the Set keeps the element alive in memory (memory leak). A WeakSet holds weak references — when a button is removed from the DOM and no other code references it, the WeakSet entry is automatically cleaned up by garbage collection. This prevents memory leaks when UI elements are dynamically added and removed.

</details>

2. What does it mean that a WeakMap key must be an object? Give an example of code that throws an error and explain why.

<details>
<summary>Show Answer</summary>

**Sample Answer:** WeakMap keys must be objects because objects are compared by reference (identity), while primitives are compared by value. If primitives were allowed as keys, two separate `"hello"` strings would be the "same" key, and garbage collection of one wouldn't necessarily remove the other. Here is the error:

```js
const wm = new WeakMap();
wm.set("name", "Arjun"); // TypeError: Invalid value used as weak map key
```

This throws because `"name"` is a primitive string, not an object. You must use an object key: `wm.set(userObject, "Arjun")`.

</details>

3. Can you iterate over a WeakMap with `for...of`? Can you check its `.size` property? Why or why not?

<details>
<summary>Show Answer</summary>

**Sample Answer:** No, you cannot iterate over a WeakMap with `for...of`, and WeakMap has no `.size` property. Both are intentionally omitted because garbage collection is non-deterministic — the entries can change at any time as objects become unreferenced and get cleaned up. Providing a stable iteration order or a reliable count would be impossible. You can only use `.get()`, `.set()`, `.has()`, and `.delete()` on a WeakMap.

</details>
