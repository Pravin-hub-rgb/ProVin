In the last topic, you saw memoization — caching results so you don't recalculate. Now let's look at a different problem: repeating the same input over and over.

---

## ✅ What is Currying?

✅ **The simplest explanation in the world:**

> Currying means feeding a function its inputs one at a time instead of all at once. You give it the first input, it gives you back a new function. You give that function the next input, it gives you another function. This keeps going until all inputs are provided — then it finally runs.

That is all currying is. Nothing more.

✅ This is exactly what happens:
```js
// Normal function — all inputs at once
add(1, 2, 3); // 6

// Curried function — one input at a time
const curriedAdd = curry(add);
curriedAdd(1)(2)(3); // 6
```

---

---

## ✅ Where does the name "Currying" come from?

The name comes from **Haskell Curry**, an American mathematician and logician. He didn't invent the concept — it was actually first described by Moses Schönfinkel in 1924. But Curry's work popularized it, and the technique was named "currying" in his honor.

Haskell Curry also has a programming language named after him: **Haskell**, a purely functional programming language where currying is built in by default. In Haskell, every function is automatically curried — you never have to call a `curry()` function manually. You just write `add 1 2 3` and the language handles the staging behind the scenes.

So when you hear "currying" in an interview, it's named after a person, not a cooking term. (No, it has nothing to do with curry powder.)

---

## ✅ Why do we need it? (The Problem)

Say you have a normal function with two inputs:

```js
function discount(percent, price) {
  return price - price * percent / 100;
}
```

Today's discount is always 10%. But look what you have to do:

```js
discount(10, 200);
discount(10, 50);
discount(10, 80);
discount(10, 999);
```

You type the same `10` every single time. That's the annoying part — the same way recalculating `square(5)` again and again was annoying in memoization.

---

## ✅ The Fix

Give the `10` once, and get back a function that already has the `10` locked in. After that you only give the price:

```js
const tenOff = makeDiscount(10);

tenOff(200); // 180
tenOff(50);  // 45
tenOff(80);  // 72
tenOff(999); // 899.10
```

`tenOff` is just "the discount function with 10 already filled in." That's all it is.

---

## ✅ So why "one input at a time"?

That's only the **how**, not the **why**. To lock in the first input and wait for the rest, you have to give the inputs in stages: first `10`, later the `price`. The staging is the tool. The goal is the thing you already figured out: we know the discount is 10 all day, so don't keep passing it.

It also connects to memoization:

- `memoize(fn)` locks in a function and hands you back a new function.
- `makeDiscount(10)` locks in a number and hands you back a new function.

Same shape, different thing locked in.

---

## ✅ How does `makeDiscount(10)` become a function?

Nothing "becomes" a function. `makeDiscount` just **hands one back**, the same way `createCounter` does:

```js
function createCounter() {
  let count = 0;

  function increment() {
    count++;
    console.log(count);
  }

  return increment;  // <- this is what gets handed back
}

const myCounter = createCounter();
myCounter(); // 1
```

You called `createCounter()` and caught the result in `myCounter`. Then you called `myCounter()` like a function, and it worked. So `myCounter` is a function.

Why? Because of the last line inside `createCounter`: `return increment`. Whatever a function returns is what lands in the variable.

- `createCounter` returns a function → `myCounter` is a function.
- `makeDiscount` returns a function → `tenOff` is a function.

Here it is with the pieces lined up:

```js
function makeDiscount(percent) {
  return function(price) {                 // <- this is what gets handed back
    return price - price * percent / 100;
  };
}

const tenOff = makeDiscount(10);           // tenOff = the handed-back function
```

---

## ✅ Where does the 10 live? (Closure)

The `10` isn't passed again when you call `tenOff(200)`, so something has to be holding it.

You already know a function that held on to a value between calls: `myCounter` held on to `count`. Using that same idea — `tenOff` keeps the `10` inside it, held there by **closure**.

```js
function makeDiscount(percent) {
  return function(price) {
    return price - price * percent / 100;  // percent is still here
  };
}
```

When `makeDiscount(10)` finishes running, the function it handed back (`tenOff`) still uses `percent`. So JavaScript keeps `percent` (the `10`) alive, attached to `tenOff`. It's the same as `count` staying alive for `myCounter`, and `cache` staying alive for `fastSquare`.

So the `10` lives inside `tenOff`, held there by closure.

`curry(fn)` does this same thing, but automatically and for any function. It builds those handed-back functions for you, and each one remembers the inputs given so far.

---

## ✅ The "Rooms" Picture (Scope)

Scopes are like rooms inside rooms:

```js
// GLOBAL ROOM (the big outside)

function makeDiscount(percent) {       // ROOM 1: percent lives here

  return function(price) {             // ROOM 2: price lives here
    return price - price * percent / 100;
  };
}
```

Room 2 (inner function) can look out into Room 1 and see `percent`.
The global room cannot look into Room 1. Global code can't touch `percent`.

So "outer" means Room 1 — the function that contains the inner function. Not global. This is the privacy you already know: `percent` is hidden from everyone, except the inner function that was born inside its room.

## ✅ Currying vs Partial Application

- **Currying** is the technique: feeding a function its inputs one at a time.
- **Partial application** is the act of fixing some arguments now and providing the rest later. Your notes call it "pre-filling some arguments now and providing the rest later." That's what you described when you said we lock in the 10.

`curry(discount)` gives you back a function, you call it with `10`, and that hands back a new function (`tenOff`) that has the `10` inside it.

---

## ✅ Working implementation:

We will build this function step by step.

---

✅ **Step 1:** Create outer curry function. It accepts the original function.

```js
function curry(fn) {

}
```

---

✅ **Step 2:** Return inner function that collects arguments.

```js
function curry(fn) {
  return function curried(...args) {

  };
}
```

---

✅ **Step 3:** Check: do we have all the arguments already?

```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn(...args);
    }
  };
}
```
✅ If YES: just run the original function and return result. We are done.

---

✅ **Step 4:** If NO: return another function that will collect more arguments later.

```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn(...args);
    }

    return function(...moreArgs) {
      return curried(...args, ...moreArgs);
    };
  };
}
```

✅ That is it. Full complete curry function.

## ✅ Usage:

```js
const add = (a, b, c) => a + b + c;
const curriedAdd = curry(add);
```

✅ All of these work:
```js
curriedAdd(1)(2)(3);    // 6
curriedAdd(1, 2)(3);    // 6
curriedAdd(1, 2, 3);    // 6
```

✅ Partial application:
```js
const addFive = curriedAdd(5);
addFive(3)(2); // 10
```

## How to Explain

Currying transforms a function that takes multiple arguments into a sequence of functions each taking one argument. This enables partial application — pre-filling some arguments now and providing the rest later. It's built on higher order functions, closures, and recursion.

**The basic flow:**
```js
function discount(percent, price) {
  return price - price * percent / 100
}
const tenOff = makeDiscount(10)
tenOff(200) // 180
tenOff(50)  // 45
```

You give the first input once, get back a function with that input locked in, then pass the rest one at a time. The locked-in value survives through closure.

**How many can it hold?**

The curried function holds arguments in its closure — same as memoization holds cached results. There's no fixed limit; it holds as many as you pass. Each intermediate function (like `tenOff`) keeps its locked-in arguments alive through closure, just like `count` stayed alive in `createCounter`. The only limit is memory — each locked-in argument takes a small amount of space in RAM.

**The part that trips everyone up:**

`makeDiscount(10)` doesn't "become" a function — it returns a function, the same way `createCounter()` returns a function. Whatever a function returns is what lands in the variable.

Also, currying and partial application are related but not the same. Currying always produces nested one-argument functions. Partial application is the act of fixing some arguments, which can be done with bind or a curried function.

**The mistakes to remember:**
- Confusing currying with partial application — currying is structural, partial application is usage
- Assuming curried functions run immediately — they wait until all arguments arrive
- Using curry on functions with variable arity where fn.length is unreliable
- Forgetting that locked-in arguments live in closure — they don't disappear after the outer function finishes

## 🧠 Interview Questions

> ❓ What is currying?
> Transforming a function that takes multiple arguments into a sequence of functions each taking a single argument.

> ❓ What is the advantage of currying?
> Partial application. You can create reusable specialized functions by pre-filling some arguments.

> ❓ What is the difference between currying and partial application?
> Currying always produces nested functions. Partial application is the act of pre-filling arguments.

> ❓ How does the locked-in value survive after the outer function finishes?
> Closure. The inner function remembers the variable from its outer scope, the same way count stays alive in createCounter.
