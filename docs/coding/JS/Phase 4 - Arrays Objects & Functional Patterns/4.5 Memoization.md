> Memoization = a function that **remembers its past answers**, so it never does the same slow work twice.

---

## 1. The problem (why this exists)

Imagine a slow function. Fetching a greeting takes **2 seconds**:

```js
function getGreeting(name) {
  return new Promise(resolve => {
    setTimeout(() => resolve("hi " + name), 2000);
  });
}
```

A user called "vin" visits **10 times**. Every visit calls `getGreeting("vin")`.

- 10 visits x 2 seconds = **20 seconds** of waiting
- But the answer is **always** `"hi vin"`. We're redoing identical work.

**Goal:** first visit takes 2 seconds, the other 9 take about 0ms.

---

## 2. The idea: keep a notebook

Before doing the slow work, check a notebook:

1. Is this input already in the notebook?
2. **Yes** -> read the answer, done. No slow work.
3. **No** -> do the slow work, **write the answer in the notebook**, return it.

This notebook is called a **cache**.

---

## 3. What is the cache in code?

The notebook has to store **many answers**, each under a label:

| label (input) | answer |
|---|---|
| `"vin"` | `"hi vin"` |
| `"sam"` | `"hi sam"` |

That's exactly what a JavaScript **object** does (labels -> values):

```js
const cache = {};          // empty notebook
cache["vin"] = "hi vin";   // write
cache["vin"];              // read -> "hi vin"
cache["zed"];              // never written -> undefined
```

The label is called a **key**.

A number (like `count` in a counter) isn't enough, because a number can only remember one thing. An object remembers many.

---

## 4. The notebook must survive between calls (closure)

The cache has to stay alive after the function returns. This is the same trick as a counter:

```js
function createCounter() {
  let count = 0;            // remembered variable

  function increment() {
    count++;
    console.log(count);
  }

  return increment;         // hand back the function
}

const myCounter = createCounter();
myCounter(); // 1
myCounter(); // 2
```

Normally `count` would vanish when `createCounter` finishes. But `increment` uses it, so JavaScript keeps it alive for `increment`. This is a **closure**: a function that remembers variables from where it was created.

Same shape for our notebook, just with `cache` instead of `count`:

```js
function createFastGreeter() {
  const cache = {};                          // remembered variable

  async function greet(name) {
    if (name in cache) return cache[name];   // seen it? instant
    const result = await getGreeting(name);  // no? wait 2 seconds
    cache[name] = result;                    // write it down
    return result;
  }

  return greet;                              // hand back the function
}

const myGreet = createFastGreeter();
await myGreet("vin"); // 2 seconds
await myGreet("vin"); // instant
await myGreet("vin"); // instant
```

---

## 5. Why pass a function in? (making it a template)

Now say you also have a slow `getWeather(city)`. It needs the **exact same** three steps (check notebook, do slow work, write it down). Only the slow work is different.

Writing the notebook code again for every slow function is annoying. So we write it **once** and leave a blank for the part that changes.

`n` in `double(n)` is a blank you fill with a **number**.
`fn` in `memoize(fn)` is a blank you fill with a **function**.

```js
const fastGreeting = memoize(getGreeting);
const fastWeather  = memoize(getWeather);
```

Each call returns a **new function with its own separate notebook**. They never mix (same as two separate counters each having their own `count`).

So: **we pass a function in so the notebook logic is written once and works for any slow function.**

The returned function has no name inside `memoize` because the name is chosen by whoever catches it (`fastWeather` above).

---

## 6. First version (one input only)

```js
function memoize(fn) {
  const cache = {};                     // the notebook

  return function(input) {              // the function you'll actually call
    if (input in cache) return cache[input];   // 1. check notebook
    const answer = fn(input);                  // 2. do the slow work
    cache[input] = answer;                     // 3. write it down
    return answer;
  };
}
```

This works, but only for functions with **one** input.

---

## 7. Where it breaks: more than one input

```js
function add(a, b) { return a + b; }
const fastAdd = memoize(add);
fastAdd(2, 3);
```

`function(input)` has room for one thing. The `3` is lost, and `fastAdd(2, 3)` and `fastAdd(2, 9)` would both use the label `2`, so they'd get mixed up.

We need two fixes:

1. **Catch any number of inputs**
2. **Turn all of them into one key**

---

## 8. Fix 1: `...args` collects the inputs into an array

```js
function(...args) { ... }
```

- `fastAdd(2, 3)` -> `args = [2, 3]`
- `fastSquare(5)` -> `args = [5]`
- `fastGreeting("vin")` -> `args = ["vin"]`

One input or ten, they all land in one array. (This `...` is called the **rest operator**.)

## 9. Fix 2: `JSON.stringify` turns the array into a string key

Object keys have to be **strings**, but `args` is an array. So we convert it:

```js
JSON.stringify([5]);     // "[5]"
JSON.stringify([2, 3]);  // "[2,3]"
JSON.stringify([2, 9]);  // "[2,9]"  <- different key, no mixing
```

`"[5]"` isn't magic. It's just "the input 5, written as text so it can be a key."

## 10. Fix 3: `fn(...args)` unpacks the array again

`add` wants separate inputs (`add(2, 3)`), not an array. So when calling the original function, `...` goes the other way:

```js
fn(...args)  // args = [2, 3]  ->  fn(2, 3)
```

So `...` has two mirror-image jobs:

- in the **parameter** (`function(...args)`): **collect** inputs into an array
- in the **call** (`fn(...args)`): **unpack** an array into separate inputs

---

## 11. The full function

```js
function memoize(fn) {
  const cache = {};                          // notebook, kept alive by closure

  return function(...args) {                 // collect inputs into an array
    const key = JSON.stringify(args);        // array -> string key

    if (key in cache) {                      // 1. already in the notebook?
      console.log("Returning from cache");
      return cache[key];
    }

    console.log("Calculating new result");   // 2. no -> do the real work
    const result = fn(...args);              //    (unpack the array)

    cache[key] = result;                     // 3. write it down
    return result;
  };
}
```

In plain words: **take a function in -> make a notebook -> hand back a new function that remembers the notebook. Each call turns the inputs into a key, checks the notebook, and either reads the answer or computes and writes it.**

### Usage

```js
function slowSquare(n) {
  // imagine this takes 5 seconds
  return n * n;
}

const fastSquare = memoize(slowSquare);

fastSquare(5); // Calculating new result -> 25   (cache is now { "[5]": 25 })
fastSquare(5); // Returning from cache   -> 25   (instant)
fastSquare(6); // Calculating new result -> 36   (cache now has two entries)
```

### What it uses

- **Higher order functions** (a function that takes a function in and returns a function)
- **Closures** (the returned function remembers `cache`)
- **Rest operator** (`...args`)

---

## 12. Why `key in cache` and not `if (cache[key])`

`if (cache[key])` checks whether the stored answer is **truthy**. If the real answer is `0`, `""`, or `false`, the check fails and it recalculates every time, so it isn't really cached.

`key in cache` asks "is this label in the notebook?" no matter what the answer is.

---

## 13. How much can the cache hold?

**Searching does NOT get slower as the cache grows.** An object doesn't flip through pages. Think of a coat check: you hand over a ticket and they walk straight to your coat, whether there are 10 coats or 1 million. A lookup takes about the same tiny time at any size, and is still far faster than a 2 second fetch.

**The real limit is memory.** Every entry takes up RAM. A few thousand entries is nothing. But if the function keeps getting new inputs forever, the cache only grows and eventually eats all memory. That's the trade-off: **you trade memory for speed.**

Real code caps the cache (for example, throw away the oldest entries after 1000). That's an advanced topic for later.

## 14. When is memoization NOT worth it?

Only when the slow work is **much slower** than a lookup. For `n * 2`, looking it up costs as much as calculating it, so it's pointless. It's worth it for slow fetches, heavy computation, and recursive algorithms like Fibonacci.

---

## 15. Things that go wrong

- **Unbounded cache** -> memory keeps growing in long-running apps
- **Functions with side effects** -> a cached call skips the side effects entirely
- **Impure functions** (output depends on outside state) -> you'll get stale answers
- **`JSON.stringify` as a key** breaks on objects with different key order, functions, or `undefined`. Two logically equal inputs can produce different keys (cache misses). For complex inputs, use a `Map` with the object reference as key.
- **Trivially fast functions** like `n * 2` -> lookup costs as much as the work

## 16. React connection (for later)

`useMemo` and `useCallback` use the same idea: remember a result and reuse it. React's version is simpler in one way: it only remembers the **last** result and recomputes when its dependency list changes.

## Interview Questions

> **What is memoization?**
> An optimization technique that caches the result of expensive function calls, so later calls with the same arguments return the cached result instead of recomputing.

> **What JavaScript concepts are needed to implement it?**
> Higher order functions, closures, and the rest operator.

> **What is the downside?**
> Extra memory for the cache. You trade memory for speed.

> **Why does the cache survive between calls?**
> Closure. The returned function uses `cache`, so JavaScript keeps it alive for as long as that function exists.

> **Why `JSON.stringify(args)`?**
> Object keys must be strings, and `args` is an array. Stringifying gives the same key for the same inputs.

## Interview Ready Answer

> "Memoization is an optimization pattern that caches function results based on input arguments. If the same inputs are provided again, the cached result is returned immediately instead of recalculating. It is implemented using higher order functions and closures: a wrapper function holds a cache object in its closure, turns the arguments into a key, and either returns the stored result or computes and stores it. It trades memory for speed."
