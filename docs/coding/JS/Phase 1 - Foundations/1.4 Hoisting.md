In the last topic, you learned about scope — where variables can be accessed. But there's another behavior that confuses almost everyone: how can you sometimes use a variable or function before you've declared it in your code?

If you write `console.log(x)` before `let x = 5`, you get an error. But if you write `console.log(x)` before `var x = 5`, you get `undefined` — no error. And if you call a function before declaring it with `function greet() {}`, it works perfectly.

What's going on? It's called hoisting.

---

## The Phone Book Analogy

Imagine you're looking up phone numbers in a phone book. You don't start calling people randomly. First, you flip through the entire book and write down every name and number you might need. Then you start making calls.

JavaScript does the same thing. Before running your code, it does a first pass where it reads every declaration — every `var`, `let`, `const`, and `function` — and registers them in memory. Then it does a second pass where it actually runs the code line by line.

- **Function declarations** → Full contact info (name + number) is in the book from pass one. You can call anytime.
- **`var`** → Name is in the book, but the number just says `undefined`. You can call it, but you'll get `undefined` until pass two assigns the real number.
- **`let` / `const`** → Name is in the book, but there's a note: "Do NOT call before [line X]." If you try, you get a ReferenceError.
- **Function expressions** (`const fn = function() {}`) → Not in the phone book at all. You never saw this person coming.

So "hoisting" isn't lifting — it's just the engine having already read your name in pass one.

---

## ✅ What is hoisting?

> **Hoisting is JavaScript's behavior of moving declarations to the top of their scope before code execution.**

Let's unpack that.

**"Moving declarations to the top"** — during the first pass, JavaScript reads all declarations and effectively acts as if they were written at the top of their scope. The code doesn't physically move, but the effect is the same.

**"Before code execution"** — the first pass happens before any line of code runs. By the time your code starts executing, JavaScript already knows about every variable and function in the current scope.

**"Declarations, not initializations"** — only the declaration part is hoisted. The assignment stays where it is. `var x = 5` is split into two parts: the declaration (`var x`) is hoisted, but the assignment (`= 5`) stays on its original line.

---

## ✅ Different types get hoisted differently

| Type | Behaviour |
|---|---|
| `var` | ✅ Fully hoisted + initialized as `undefined` |
| `let` / `const` | ✅ Hoisted ❌ **NOT initialized** (Temporal Dead Zone) |
| Function Declarations | ✅ Fully hoisted + completely usable |
| Function Expressions | ❌ Not hoisted at all |

---

### 1️⃣ `var` Hoisting

```js
console.log(name); // ✅ undefined. No error.
var name = "Pravin";
```

What actually happens:

1. First pass: JS sees `var name`. It creates the variable at the top of its scope and sets it to `undefined`.
2. Second pass: Runs `console.log(name)` → prints `undefined`
3. Then finally assigns `"Pravin"` to name.

`var` will never give you an error if you access it before declaration. It will just be `undefined`. This is both a feature and a bug — it's convenient but can hide mistakes.

---

### 2️⃣ `let` and `const` Hoisting

This is the lie everyone tells you: "let and const are not hoisted."

**THIS IS 100% WRONG.**

`let` and `const` ARE hoisted. But they are not initialized.

**Declaration** = JavaScript knows this variable exists. It reserved a spot for it in memory.
**Initialization** = JavaScript actually put a value inside that spot.

When JavaScript sees `let` or `const` during first pass:
1. It declares the variable. The spot is reserved.
2. It puts a fence around this variable from the very top of the scope all the way down to the line where it is declared.
3. It says: "No one can touch this until you cross this line."

```js
// 🔴 THIS WHOLE AREA IS INSIDE THE FENCE. YOU CANNOT TOUCH CAR HERE.

console.log(car); // ❌ ReferenceError. Cannot access 'car' before initialization.

// ✅ This is the line where the fence opens.
let car = "Tesla";

// 🟢 Now you can touch it.
console.log(car); // ✅ "Tesla"
```

This fence is called the **Temporal Dead Zone (TDZ)**.

The variable exists. It has been hoisted. But you are not allowed to access it until you reach the line where it is declared.

This is not a bug. This is a safety feature. This is exactly why `let` and `const` were created — to fix the silent `undefined` bugs that `var` caused.

---

### 3️⃣ Function Declarations

Function declarations are **completely and fully hoisted**.

You can call them before they are written in your code.

```js
greet(); // ✅ Works perfectly. "Hello"

function greet() {
  console.log("Hello");
}
```

This works because during first pass, JS finds the entire function and puts it at the top. The whole function body is available immediately.

---

### 4️⃣ Function Expressions

Function expressions are **NOT hoisted**. They behave exactly like normal variables.

```js
sayHi(); // ❌ TypeError: sayHi is not a function
var sayHi = function() {
  console.log("Hi");
};
```

Because `var sayHi` gets hoisted as `undefined`. So you are trying to call `undefined()` which throws a TypeError.

If you use `const` or `let` instead of `var`, you get a ReferenceError instead (because of the Temporal Dead Zone).

---

## ✅ Side by side comparison

| Code | Output | Reason |
|---|---|---|
| `console.log(a); var a = 5;` | `undefined` | var is hoisted as undefined |
| `console.log(b); let b = 5;` | `ReferenceError` | let is hoisted but in TDZ |
| `console.log(c); const c = 5;` | `ReferenceError` | same as let |
| `fn(); function fn() {}` | ✅ Works | function declaration fully hoisted |
| `fn(); var fn = function() {}` | `TypeError` | fn is undefined |

---

## ✅ What It Is NOT

- **Hoisting is NOT physically moving code.** The code stays where you wrote it. JavaScript just reads all declarations first, so it knows about them before execution. The mental model of "moving to the top" is a useful simplification, not what actually happens.

- **Hoisting is NOT the same for all declarations.** `var` gets initialized to `undefined`. `let` and `const` are hoisted but not initialized (Temporal Dead Zone). Function declarations are fully hoisted. Function expressions follow the rules of whatever keyword you used.

- **The Temporal Dead Zone is NOT a bug.** It's a deliberate design choice. `let` and `const` were created to replace `var`, and the TDZ prevents you from accidentally using a variable before it's ready. It's a safety feature.

- **Hoisting does NOT apply to class declarations.** Classes are hoisted but not initialized, similar to `let` and `const`. Accessing a class before its declaration throws a ReferenceError.

## 🧠 Interview Questions

> ❓ What is hoisting?
> Hoisting is JavaScript's behavior of moving declarations to the top of their scope before code execution. During a first pass, JavaScript reads all declarations and registers them in memory before running any code.

> ❓ What is the difference between how var and let/const are hoisted?
> var is hoisted and initialized as undefined. let and const are hoisted but not initialized — they enter the Temporal Dead Zone, which prevents access until the declaration line is reached.

> ❓ Are function declarations hoisted?
> Yes. Function declarations are fully hoisted — both the name and the body. You can call a function declaration before it appears in your code.

> ❓ Are function expressions hoisted?
> No. Function expressions follow the hoisting rules of the keyword used (var, let, or const). They are not treated as function declarations.

> ❓ What is the Temporal Dead Zone?
> The TDZ is the period between entering a scope and reaching the declaration of a let or const variable. Accessing the variable during this period throws a ReferenceError.

But just knowing the name doesn't mean you have the number — `var` gives you `undefined`, `let`/`const` give you a TDZ error, and function declarations give you the full function.

```js
console.log(a);
var a = 10;
console.log(a);
```

<details>
<summary>Show Answer</summary>

**Sample Answer:** It prints `undefined` then `10`. `var a` is hoisted to the top and initialized as `undefined`. So the first `console.log(a)` sees `undefined`. Then the assignment `a = 10` runs, and the second `console.log(a)` sees `10`. No error occurs because `var` always initializes to `undefined`.

</details>

3. What will this code print? Why?

```js
console.log(b);
let b = 20;
```

<details>
<summary>Show Answer</summary>

**Sample Answer:** It throws a ReferenceError: "Cannot access 'b' before initialization." `let b` is hoisted (JavaScript knows about it), but it's in the Temporal Dead Zone from the top of the scope until the `let b = 20` line. Accessing it before that line throws an error. This is different from `var`, which would silently return `undefined`.

</details>

4. Why can you call a function before declaring it with `function greet() {}` but not with `const greet = function() {}`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Function declarations are fully hoisted — both the name and the body are available immediately. So `function greet() {}` can be called anywhere in its scope. Function expressions follow the rules of the keyword used. `const greet = function() {}` is a `const` declaration, so it's hoisted but in the Temporal Dead Zone until the declaration line. You can't call it before that line. If you used `var greet = function() {}`, it would be hoisted as `undefined`, and calling it would throw "greet is not a function."

</details>

5. In your own words, explain the Temporal Dead Zone. Why was it created?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The Temporal Dead Zone (TDZ) is the time between when JavaScript enters a scope and when it reaches the declaration of a `let` or `const` variable. During this time, the variable exists in memory but cannot be accessed. If you try, you get a ReferenceError. The TDZ was created to prevent the silent bugs that `var` caused — with `var`, accessing a variable before its declaration silently returns `undefined`, which can hide logic errors. The TDZ makes these errors visible immediately.

</details>
