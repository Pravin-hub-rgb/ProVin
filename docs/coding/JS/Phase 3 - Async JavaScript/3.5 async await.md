Remember that Promise chain from the last topic? The one that turned callback hell into a flat, readable chain:

```js
getUser(userId)
  .then((user) => getPosts(user.id))
  .then((posts) => getComments(posts[0].id))
  .then((comments) => getLikes(comments[0].id))
  .then((likes) => console.log(likes))
  .catch((err) => console.log("Error:", err));
```

That's already way better than nested callbacks. But wouldn't it be nice if it looked even more like normal synchronous code? Like this:

```js
const user = await getUser(userId);
const posts = await getPosts(user.id);
const comments = await getComments(posts[0].id);
const likes = await getLikes(comments[0].id);
console.log(likes);
```

No `.then()`. No chaining. Just `await` and a variable assignment. That's exactly what async/await gives you.

## ✅ Let's build from 3.4 — the restaurant continued

Remember the restaurant Promise from the last topic? We ordered food, waited 3 seconds, and got our pasta:

```js
const orderFood = new Promise((resolve) => {
  setTimeout(() => resolve("🍝 Pasta Carbonara is ready!"), 3000);
});

orderFood.then((food) => console.log(food));
```

But a real restaurant experience isn't just one step. It's a sequence: you call the waiter, you order food, you eat, you pay the bill. Each step depends on the previous one — you can't eat before the food arrives, and you can't pay before you eat.

Let's write each step as a function that returns a Promise:

```js
function callWaiter() {
  return new Promise((resolve) => {
    setTimeout(() => resolve("👨‍🍳 Waiter is here"), 1000);
  });
}

function orderFood() {
  return new Promise((resolve) => {
    setTimeout(() => resolve("🍝 Pasta Carbonara"), 2000);
  });
}

function eat() {
  return new Promise((resolve) => {
    setTimeout(() => resolve("😋 Finished eating"), 1500);
  });
}

function payBill() {
  return new Promise((resolve) => {
    setTimeout(() => resolve("💳 Bill paid"), 1000);
  });
}
```

Now let's run them in order using a Promise chain (the style you learned in 3.4):

```js
callWaiter()
  .then((msg) => { console.log(msg); return orderFood(); })
  .then((msg) => { console.log(msg); return eat(); })
  .then((msg) => { console.log(msg); return payBill(); })
  .then((msg) => { console.log(msg); })
  .catch((err) => console.log("Error:", err));
```

Output (one line every 1-2 seconds):

```
👨‍🍳 Waiter is here
🍝 Pasta Carbonara
😋 Finished eating
💳 Bill paid
```

Each `.then()` waits for the previous Promise to resolve, logs the message, and returns the next step. The chain reads top-to-bottom, but you still have to manage the `.then()` calls and the `return` statements.

Now here's the same thing with `async/await`:

```js
async function restaurantExperience() {
  try {
    const msg1 = await callWaiter();
    console.log(msg1);
    const msg2 = await orderFood();
    console.log(msg2);
    const msg3 = await eat();
    console.log(msg3);
    const msg4 = await payBill();
    console.log(msg4);
  } catch (err) {
    console.log("Error:", err);
  }
}

restaurantExperience();
```

Same output. Same order. But look at the difference — no `.then()`, no `return` inside callbacks, no chaining. Just `await` and a variable assignment. The code reads exactly like normal synchronous code: "do this, then do that, then do that." Each `await` pauses until the Promise resolves, then stores the value in the variable and moves to the next line.

That is the entire point of async/await. It does not change how JavaScript works. It just makes your async code look like normal code.

But there is something important happening here beyond just cleaner syntax — **order**.

Notice that we cannot order food without calling the waiter first. We cannot eat before the food arrives. We cannot pay before we eat. Each step **depends** on the previous step being complete. The restaurant experience has a strict order, and the code must respect that order.

The same thing happens in real applications all the time:

```js
// ❌ This won't work — posts needs user data, but user hasn't arrived yet
const user = fetchUser(1);
const posts = fetchPosts(user.id); // user.id is undefined at this point
```

```js
// ✅ This works — await forces the order
const user = await fetchUser(1);
const posts = await fetchPosts(user.id); // user is ready, this runs next
```

You cannot fetch a user's posts until you know who the user is. You cannot fetch comments until you know which post. You cannot fetch likes until you know which comment. Each step needs data from the previous step, so each step must **wait** for the previous one to finish.

That is the core problem that async/await solves. It is not just about cleaner syntax. It is about **writing dependent async operations in the correct order** — and having the code read in that same order, top to bottom, left to right.

## ✅ What is async/await?

> **Async/await is syntactic sugar built on top of Promises that allows writing asynchronous code in a synchronous style.**

Let's unpack that.

**"Syntactic sugar"** — it's a sweeter way to write the same thing. It doesn't add new capabilities. It just makes existing capabilities easier to use. Like how a `for...of` loop is syntactic sugar over a regular `for` loop — same result, nicer to write.

**"Built on top of Promises"** — under the hood, async/await still creates Promise objects, still uses `.then()` and `.catch()`, still goes through the event loop's microtask queue. You just don't see any of that. The engine handles it for you.

**"Synchronous style"** — your async code looks like normal synchronous code. No `.then()`, no chaining, just `await` and a variable assignment. It reads top-to-bottom like regular code, even though it's doing async work.

Think of it like this: Promises are the engine. Async/await is the steering wheel. The engine was always there. Async/await just makes it easier to drive.

---

## ✅ How it works

Two simple rules:

1. Add the `async` keyword before a function
2. Use the `await` keyword before any Promise inside that function

```js
async function getUserData(id) {
  try {
    const response = await fetch(`/api/users/${id}`);
    const data = await response.json();
    return data;
  } catch (err) {
    console.error("Error:", err);
  }
}
```

Let's break this down:

1. `async function getUserData(id)` — The `async` keyword tells JavaScript: "This function will contain async code. It should always return a Promise." Even if you return a plain value, JavaScript will wrap it in a resolved Promise automatically.

2. `const response = await fetch(...)` — The `await` keyword pauses the function execution here. It says: "Wait for this Promise to resolve, then store the result in `response`." The function pauses, but nothing else does. The rest of your JavaScript keeps running. Other functions, events, user interactions — all still work normally.

3. `const data = await response.json()` — Same thing again. Wait for `response.json()` to finish (it returns a Promise too), then store the parsed data.

4. `return data` — Since the function is `async`, this return value becomes a resolved Promise. The caller can use `.then()` or `await` to get it.

## ✅ Same code, three styles

Let's see the same operation written three ways to really understand the progression:

**Style 1: Callbacks (old way)**
```js
function getUserData(id) {
  fetch(`/api/users/${id}`, function(response) {
    response.json(function(data) {
      console.log(data);
    });
  });
}
```

**Style 2: Promises (.then)**
```js
function getUserData(id) {
  fetch(`/api/users/${id}`)
    .then((response) => response.json())
    .then((data) => console.log(data))
    .catch((err) => console.error(err));
}
```

**Style 3: Async/await (modern way)**
```js
async function getUserData(id) {
  try {
    const response = await fetch(`/api/users/${id}`);
    const data = await response.json();
    console.log(data);
  } catch (err) {
    console.error(err);
  }
}
```

All three do exactly the same thing. They make a GET request, parse the JSON, log it or log an error. But the async/await version reads like normal synchronous code. No nesting. No chaining. Just a try/catch block like you'd use for any synchronous error handling.

## ✅ The most common mistake: sequential when you should be parallel

This is the #1 mistake everyone makes when learning async/await:

```js
// ❌ WRONG — sequential, slow
const a = await fetch('/api/a');
const b = await fetch('/api/b');
const c = await fetch('/api/c');
```

Each `await` waits for the previous one to finish. If each request takes 1 second, this takes **3 seconds** total. But these requests don't depend on each other. They could all run at the same time.

```js
// ✅ RIGHT — parallel, fast
const [a, b, c] = await Promise.all([
  fetch('/api/a'),
  fetch('/api/b'),
  fetch('/api/c')
]);
```

`Promise.all` starts all three requests immediately, and `await` waits for all of them to finish. If each takes 1 second, this takes only **1 second** total. All three run simultaneously.

Here's when to use which:

| Pattern | When to use |
|---|---|
| `await` one by one | When operations depend on previous results (step 2 needs data from step 1) |
| `Promise.all()` | When operations are independent (no step needs data from another) |

The mistake is easy to make because async/await makes everything look synchronous. You forget that `await` actually pauses your function. You write `await fetch(A)`, then `await fetch(B)` without thinking — and your code runs 3x slower than it should.

---

## ✅ What It Is NOT

- **Async/await is NOT a replacement for Promises.** It's built on top of them. Under the hood, `await` is just `.then()` with different syntax. You can mix `.then()` and `await` in the same code if you need to, though it's usually cleaner to pick one.

- **Async/await does NOT make code synchronous.** The `await` keyword pauses the function, but it doesn't block the main thread. Other code continues running. The event loop still works exactly as described in 3.2. `await` is like a yield — "I'll come back to this when the data is ready."

- **You can NOT use `await` outside an `async` function.** Well, mostly not. Top-level `await` is available in ES Modules (if your project uses `"type": "module"` in package.json or `.mjs` files), but in regular script tags or CommonJS, you'll get a syntax error.

- **Async/await is NOT just for fetch requests.** You can `await` any Promise. Database queries, file reads, timers — anything that returns a Promise can be awaited. `await new Promise(resolve => setTimeout(resolve, 1000))` lets you create delays in your code.

## 🧠 Interview Questions

> ❓ Does async/await replace Promises?
> No. It is syntax sugar. Under the hood it is still Promises. The engine still creates Promise objects, still uses the event loop microtask queue, still works exactly the same way. Only the syntax changed.

> ❓ What happens if you don't use await inside an async function?
> The async function returns a Promise that resolves with whatever the function returns. If you forget `await`, you get a Promise object instead of the actual value. This is a common bug — you log a variable and see `Promise {<pending>}` instead of the data you expected.

> ❓ Can you use await outside an async function?
> In regular scripts, no. In ES Modules (using `<script type="module">` or `"type": "module"` in package.json), yes — top-level await is supported. This is useful for module initialization that needs to fetch data before exporting.

> ❓ What is the advantage of async/await over .then() chains?
> Code reads top-to-bottom like synchronous code. Error handling uses standard try/catch instead of .catch(). Debugging is easier because you can put breakpoints on individual lines. Nested logic is easier to reason about.

> ❓ What happens when you await a non-Promise value?
> JavaScript wraps it in a resolved Promise. `await 5` is equivalent to `await Promise.resolve(5)` — it immediately resolves to 5 without any delay.
