In the last topic, you learned about the event loop — how JavaScript hands off async operations to the browser while continuing to run other code. But there's a missing piece: once the browser finishes an async operation, how does it tell JavaScript to come back and do something with the result?

The answer is callbacks. And before we dive into what they are, you need to understand one concept that makes everything click.

---

## The "Call Me Back" Analogy

Imagine you call a restaurant to order a pizza. You don't want to stay on hold for 20 minutes waiting. So you say: "Can you call me back when the pizza is ready?" The person says "Sure, give me your number." You give them your number. When the pizza is ready, they call you, you pick up, and you go pick up your pizza.

Your phone number is a callback. You gave it to the restaurant (the async operation). You didn't have to wait on hold. You went about your day. When the pizza was ready, they "called you back" using the number you gave them.

In JavaScript, a callback is exactly that: a function (your "phone number") that you hand to an async operation, so it can call you back when it's done.

---

## ✅ First: Higher Order Function

Before you understand callbacks, you need to understand this:

**A Higher Order Function** is any function that accepts another function as an argument. That's it. That's the whole definition.

Examples:
```js
setTimeout(() => {}, 1000);          // accepts a function to run later
[1, 2, 3].map(x => x * 2);           // accepts a function to transform each element
button.addEventListener("click", () => {});  // accepts a function to run on click
```

All of these are higher order functions. And the functions they accept as arguments? Those are callbacks.

---

## ✅ What is a Callback?

> **A callback is a function passed as an argument to another function, to be executed at a later time.**

Let's unpack that.

**"A function passed as an argument"** — you take a function and hand it to another function, just like you'd pass a string or a number. In JavaScript, functions are values. You can pass them around like any other variable.

**"To another function"** — the function that receives the callback is called a higher-order function. `setTimeout`, `fetch`, `addEventListener` — these all accept callbacks.

**"Executed at a later time"** — you don't call the callback yourself. The function you passed it to calls it when it's ready. Maybe immediately (like `array.map`), maybe after 1 second (like `setTimeout`), maybe after a network request finishes (like `fetch`). You wrote the code, but you don't decide when it runs.

```js
function fetchData(callback) {
  setTimeout(() => {
    callback("data received");
  }, 1000);
}

fetchData(function(data) {
  console.log(data);
});
```

That's it. That is the entire idea. Here's what's happening line by line:

1. We call `fetchData` and pass a function as the argument. That function is the callback.

2. Inside `fetchData`, that argument is stored in a parameter called `callback`. The name "callback" is not special — you could call it `cb`, `next`, `done`, or anything. It's just a variable that happens to hold a function.

3. `fetchData` starts a 1-second timer and then finishes immediately. It does not wait.

4. One second later, the timer fires, and `fetchData` runs the function we passed by doing `callback("data received")`.

5. Our function runs and logs the data.

The key insight: **we do not call the callback ourselves.** We hand it to `fetchData`, and `fetchData` calls it for us when the data is ready. We wrote the code, but we didn't decide when it runs — `fetchData` decided that.

Notice how the event loop fits in here: `fetchData` calls `setTimeout`, which hands the timer off to the browser's Web API. The browser starts the 1-second timer. Meanwhile, JavaScript continues running. When the timer finishes, the browser moves the callback to the callback queue. The event loop picks it up when the call stack is empty and runs it.

This is how all async code was written for 20 years.

---

## ✅ The Catch: Error Handling with Callbacks

The problem with callbacks is that they have no standard way to handle errors. Different libraries and APIs did it differently. Some used a pattern where the first argument was always an error:

```js
// The "error-first callback" pattern (Node.js style)
fs.readFile('/file.txt', (err, data) => {
  if (err) {
    console.error("Failed to read:", err);
    return;
  }
  console.log(data);
});
```

Others used two separate callbacks — one for success, one for failure:

```js
// The "two callback" pattern (some browser APIs)
fetchData(
  (data) => console.log(data),   // success callback
  (err) => console.error(err)    // failure callback
);
```

There was no standard. Every library chose its own convention. This made combining multiple async operations a nightmare.

---

## ✅ Callback Hell

This is what actual callback hell looks like in real code:

```js
getUser(userId, function(user) {
  getPosts(user.id, function(posts) {
    getComments(posts[0].id, function(comments) {
      getLikes(comments[0].id, function(likes) {
        // You cannot escape this nesting
      });
    });
  });
});
```

Here's what's happening:

1. First you need a user
2. Then you need their posts (needs user.id from step 1)
3. Then you need comments for that post (needs posts[0].id from step 2)
4. Then you need likes for that comment (needs comments[0].id from step 3)

Every step depends on the previous result. So you have to keep nesting deeper and deeper. Each level gets pushed further to the right. The code forms a pyramid, a triangle, a "Christmas tree" shape.

This is unreadable. Impossible to debug. Impossible to handle errors properly. If any step fails, you need to add error handling inside that specific level — there's no centralized way to catch errors from all steps.

This is the exact problem that Promises (which you'll learn about next) were invented to solve.

---

## ✅ What It Is NOT

- **A callback is NOT the same as a Promise.** A callback is a function you pass to be called later. A Promise is an object that represents a future value. They're different patterns entirely. Callbacks are the old way; Promises are the modern way.

- **A callback is NOT async by default.** Functions like `array.map()` and `array.forEach()` use callbacks, but they run synchronously — the callback is called immediately for each element, not later. Only callbacks passed to things like `setTimeout`, `fetch`, or event listeners are asynchronous.

- **Not every function parameter is a callback.** If a function accepts another function but calls it immediately (not later), that's not a callback in the async sense. It's just a function argument that happens to be a function. The term "callback" specifically implies "call this back later."

---

## 🧠 Interview Questions

> ❓ What is callback hell?
> When you have multiple async operations that depend on each other, resulting in deeply nested callbacks that move rightwards across the screen. They are extremely hard to read, debug, and handle errors. Also called the "pyramid of doom."

> ❓ Why were Promises introduced?
> To solve callback hell. Promises allow you to chain async operations vertically instead of nesting them horizontally, and provide a standardized way to handle errors with `.catch()` instead of error handling at every nesting level.

> ❓ What is a higher order function?
> Any function that accepts another function as an argument, or returns a function as a result. Examples: `setTimeout`, `array.map`, `array.filter`, `addEventListener`.

> ❓ Are all callbacks asynchronous?
> No. A callback is just a function passed to another function. Whether it runs synchronously or asynchronously depends on the function that receives it. `array.map` runs callbacks synchronously (immediately). `setTimeout` runs callbacks asynchronously (later).

> ❓ What are the problems with callbacks besides nesting?
> No standardized error handling (each library chose its own convention), difficult to debug (stack traces get lost across async boundaries), hard to run operations in parallel, and difficult to handle complex flows like "run these three, then do something with all results."

## 🎯 Interview Ready Answer

> "A callback is a function passed as an argument to be executed at a later time. They were the primary method for handling asynchronous operations in JavaScript before Promises were introduced. Deeply nested callbacks create what is known as callback hell — unreadable, triangle-shaped code that is difficult to debug and handle errors in. This led to the adoption of Promises and later async/await."

<details>

**Sample Answer:** It prints "Start", then "End", then "Inside timeout". Even though the timeout is 0 milliseconds, the event loop still processes it asynchronously. The `setTimeout` callback goes to the Web API, then to the callback queue. It only runs after the call stack is empty — and the call stack still has "End" to print. 3. What's the difference between a callback passed to `array.map()` and a callback passed to `setTimeout()`? Both are functions passed to another function. How are they different?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The `array.map()` callback runs synchronously — it's called immediately for every element in the array, right then and there. The `setTimeout` callback runs asynchronously — it's called later, after at least the specified delay. The difference is not in how they're written (both are just functions passed as arguments) but in when they execute. `map()` calls its callback right away. `setTimeout` hands its callback to the browser's Web API and only runs it after the timer fires and the event loop picks it up.

</details>
