In the last topic, you learned that JavaScript can hand off async operations to the browser and continue running other code. But there's a question you might be asking: how does JavaScript know when to come back? How does it decide what to run next? And what happens if multiple async operations finish at the same time?

The answer is the Event Loop. And this is the single most asked interview question in all of JavaScript. 90% of developers don't actually understand it. After this topic, you will.

---

## The Restaurant Kitchen Analogy

Imagine a restaurant kitchen with one chef (JavaScript). The chef can only cook one dish at a time. Orders come in, and the chef cooks them one by one.

But some dishes take a long time — like a roast that needs to be in the oven for an hour. The chef doesn't just stand there staring at the oven. They put the roast in, set a timer, and move on to the next order. When the timer rings, the chef takes the roast out and finishes it.

Now imagine multiple timers going off at the same time. The oven timer rings, the stovetop timer rings, and a waiter comes in with a new order. The chef has to decide: what do I handle first?

That's the event loop. It's the system that decides what the chef works on next.

---

## ✅ Start with the most important fact

**JavaScript is single-threaded.** It can only do one thing at a time. It has only one call stack — one place where code actually runs.

But it can handle thousands of concurrent operations. How? Because of the Event Loop.

The event loop is not part of JavaScript. It's not in the language specification. It's part of the **environment** that runs JavaScript — the browser, or Node.js. JavaScript itself is just a simple single-threaded language. The environment provides the async capabilities.

---

## ✅ The 5 Parts

There are only 5 parts you need to understand. Everything else is details.

| Part | What it does |
|---|---|
| 1. **Call Stack** | Where your code actually runs. One thing at a time. Last In, First Out. |
| 2. **Web APIs** | The browser handles async stuff here. `setTimeout`, `fetch`, click handlers, timers all live here. |
| 3. **Microtask Queue** | Promise callbacks go here. Highest priority. |
| 4. **Callback Queue** (Macrotask Queue) | All other callbacks go here. Lower priority. |
| 5. **Event Loop** | The boss. Decides what runs next. |

---

## ✅ How it all fits together

Let's trace what happens when you run this code:

```js
console.log("1");

setTimeout(() => {
  console.log("2");
}, 1000);

console.log("3");
```

**Step 1:** `console.log("1")` is pushed onto the Call Stack. It runs immediately. It's removed from the stack. Output: `1`

**Step 2:** `setTimeout(...)` is pushed onto the Call Stack. JavaScript sees this is a timer, so it hands it off to the **Web APIs**. The browser starts a 1-second timer. The `setTimeout` call is removed from the Call Stack.

**Step 3:** `console.log("3")` is pushed onto the Call Stack. It runs immediately. Output: `3`

**Step 4:** The Call Stack is now empty. JavaScript has nothing to do.

**Step 5:** 1 second passes. The timer in Web APIs finishes. The browser moves the `setTimeout` callback to the **Callback Queue**.

**Step 6:** The **Event Loop** checks: "Is the Call Stack empty?" Yes. "Is there anything in the Microtask Queue?" No. "Is there anything in the Callback Queue?" Yes — the `setTimeout` callback.

**Step 7:** The Event Loop moves the callback from the Callback Queue to the Call Stack. It runs. Output: `2`

---

## ✅ What does the Event Loop actually do?

> **The Event Loop is a mechanism that continuously checks if the Call Stack is empty and moves callbacks from queues to the stack in a specific priority order.**

Let's unpack that.

**"Continuously checks"** — the Event Loop never sleeps. It's an infinite loop that runs as long as your program is running. It constantly asks: "Is the Call Stack empty yet?"

**"If the Call Stack is empty"** — this is the only condition that matters. If code is still running on the stack, the Event Loop does nothing. It waits. Once the stack is clear, it springs into action.

**"Moves callbacks from queues to the stack"** — the Event Loop takes callbacks waiting in queues and pushes them onto the Call Stack for execution. It's like a bouncer who decides which waiting person gets to enter the club next.

**"Specific priority order"** — not all queues are equal. Promise callbacks (microtasks) get processed before timer callbacks (macrotasks). The order is strict: drain all microtasks first, then process one macrotask, repeat.

Here's the exact rule. Memorize it:

1. Run all synchronous code
2. Run **all** microtasks
3. Run **one** macrotask
4. Repeat

## ✅ The famous interview question

What is the output of this code?

```js
console.log("1");

setTimeout(() => console.log("2"), 0); // macrotask

Promise.resolve().then(() => console.log("3")); // microtask

console.log("4");
```

**Output:**
```
1
4
3
2
```

Let's trace through it step by step:

1. `console.log("1")` — synchronous. Runs immediately. Output: `1`
2. `setTimeout(() => console.log("2"), 0)` — handed to Web APIs. Timer starts with 0ms delay. The callback will go to the **Callback Queue** (macrotask queue).
3. `Promise.resolve().then(() => console.log("3"))` — this creates a resolved Promise and attaches a `.then()` handler. Promise callbacks go to the **Microtask Queue**.
4. `console.log("4")` — synchronous. Runs immediately. Output: `4`
5. Call Stack is empty.
6. Event Loop checks Microtask Queue first. Finds the Promise callback. Runs it. Output: `3`
7. Microtask Queue is empty.
8. Event Loop checks Callback Queue. Finds the `setTimeout` callback. Runs it. Output: `2`

Why does `3` print before `2`? Because Promise callbacks (microtasks) have higher priority than `setTimeout` callbacks (macrotasks). Even though the `setTimeout` has 0ms delay, the Promise callback still runs first.

## ✅ Microtasks vs Macrotasks

This is the key distinction that most interview questions test:

| Type | Examples | Priority |
|---|---|---|
| **Microtasks** | Promise `.then()`, `.catch()`, `.finally()`, `queueMicrotask()`, `MutationObserver` | High — runs before the next macrotask |
| **Macrotasks** (Callback Queue) | `setTimeout`, `setInterval`, `setImmediate`, I/O, UI rendering | Low — one per event loop cycle |

The rule: **the Microtask Queue is drained completely** before the Event Loop picks up even one macrotask. If a microtask adds another microtask, that new microtask runs before any macrotask.

```js
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => {
  console.log("3");
  // This adds another microtask
  Promise.resolve().then(() => console.log("4"));
});

console.log("5");
```

Output:
```
1
5
3
4
2
```

Notice `4` prints before `2`. The first Promise callback (`3`) adds another microtask (`4`). The Event Loop drains the entire Microtask Queue before touching the Callback Queue. So `4` runs before `2`.

## ✅ What It Is NOT

- **The Event Loop is NOT part of JavaScript.** It's provided by the environment (browser or Node.js). JavaScript itself is just a simple single-threaded language with a call stack. The Event Loop is the environment's mechanism for scheduling callbacks.

- **The Event Loop is NOT a queue.** It doesn't store anything. It's a loop that checks if the Call Stack is empty and moves things from queues to the stack. The queues (Microtask Queue and Callback Queue) are separate data structures.

- **The Event Loop does NOT run in parallel with your code.** It only runs when the Call Stack is empty. Your code and the Event Loop never run at the same time. They take turns.

- **setTimeout with 0ms does NOT run immediately.** It runs on the next event loop cycle, after all synchronous code and all microtasks have finished. `setTimeout(fn, 0)` means "run this as soon as possible, but not right now."

## 🧠 Interview Questions

> ❓ What is the Event Loop?
> The Event Loop is a mechanism in the JavaScript runtime that enables asynchronous programming. It continuously checks if the Call Stack is empty. If it is, it processes all microtasks first, then one macrotask, and repeats. This allows JavaScript to be single-threaded while handling async operations.

> ❓ What is the difference between microtasks and macrotasks?
> Microtasks (Promise callbacks, queueMicrotask) have higher priority and are processed before any macrotask. The Microtask Queue is drained completely before the Event Loop picks up a single macrotask (setTimeout, setInterval, I/O). If a microtask adds another microtask, that runs before any macrotask.

> ❓ Why does `Promise.resolve().then(...)` run before `setTimeout(..., 0)`?
> Because Promise callbacks are microtasks and setTimeout callbacks are macrotasks. The Event Loop processes all microtasks before moving to macrotasks. Even with 0ms delay, the setTimeout callback must wait for the Microtask Queue to be empty.

> ❓ Is the Event Loop part of JavaScript?
> No. It's part of the runtime environment (browser or Node.js). The JavaScript engine (V8, SpiderMonkey) only handles the Call Stack. The Event Loop, Web APIs, and callback queues are provided by the environment.

> ❓ What happens if a microtask keeps adding more microtasks?
> The Event Loop will keep processing microtasks indefinitely, never moving to macrotasks. This can starve the Callback Queue and freeze the UI. This is called "microtask starvation" and is a real bug that can make your page unresponsive.

## 🎯 Interview Ready Answer

> "JavaScript is single-threaded with one call stack. The Event Loop enables non-blocking behavior by offloading async operations to the browser's Web APIs. When the Call Stack is empty, the Event Loop first processes all microtasks (Promise callbacks) from the Microtask Queue, then processes a single macrotask (setTimeout, I/O) from the Callback Queue, and repeats. This prioritization ensures Promise callbacks run before timer callbacks."

**In Your Own Words**

1. You're the chef in a restaurant kitchen. You have a roast in the oven (30 minutes), a pasta boiling on the stove (10 minutes), and a new order just came in. You can only do one thing at a time. How do you decide what to work on? How is this like the Event Loop?

<details>
<summary>Show Answer</summary>

**Sample Answer:** You start the roast (hand it off to the oven / Web API), start the pasta (hand it off to the stove / Web API), and then work on the new order (synchronous code). When the pasta timer rings (microtask), you stop what you're doing and handle it immediately because it's almost done and you don't want it to burn. When the roast timer rings (macrotask), you handle it when you have a moment. The oven and stove are like Web APIs — they work in the background. The timers ringing are like callbacks being queued. You (the Event Loop) decide what to handle next based on priority.

</details>

2. What will this code print? Walk through each step.

```js
console.log("A");

setTimeout(() => console.log("B"), 0);

Promise.resolve().then(() => console.log("C"));

console.log("D");
```

<details>
<summary>Show Answer</summary>

**Sample Answer:** Output: A, D, C, B. Step by step: (1) `console.log("A")` runs synchronously. (2) `setTimeout` is handed to Web APIs with 0ms timer — callback goes to Callback Queue. (3) `Promise.resolve().then(...)` — callback goes to Microtask Queue. (4) `console.log("D")` runs synchronously. (5) Call Stack empty. Event Loop checks Microtask Queue first — runs `console.log("C")`. (6) Microtask Queue empty. Event Loop checks Callback Queue — runs `console.log("B")`.

</details>

3. What is "microtask starvation"? How could it happen in real code?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Microtask starvation happens when microtasks keep adding new microtasks, so the Event Loop never gets to process macrotasks. For example, a recursive Promise chain that keeps adding `.then()` callbacks would keep the Microtask Queue non-empty forever. The Callback Queue (and UI rendering) would never get a turn. This can make the page unresponsive because rendering is also a macrotask. In practice, this is rare but can happen with poorly designed recursive Promise logic.

</details>

4. Someone tells you "setTimeout with 0ms delay runs immediately." Are they right? Explain why or why not.

<details>
<summary>Show Answer</summary>

**Sample Answer:** They're wrong. `setTimeout(fn, 0)` does NOT run immediately. It runs on the next event loop cycle, after all synchronous code and all microtasks have finished. The 0ms means "minimum delay of 0ms" — the browser will wait at least 0ms before queuing the callback. But the callback still has to wait in the Callback Queue until the Call Stack is empty and all microtasks are processed. So it runs "as soon as possible, but not right now."

</details>

5. In your own words, explain why understanding the Event Loop matters for writing real applications. Give an example of a bug you could only understand by knowing the Event Loop.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Understanding the Event Loop helps you predict the order your code runs in. A common bug: you have a loading spinner that should show before a long computation, but it never appears. You write:

```js
showSpinner();
longComputation(); // blocks for 2 seconds
hideSpinner();
```

The spinner never shows because `showSpinner()` updates the DOM, but DOM rendering is a macrotask. It gets queued. Then `longComputation()` blocks the Call Stack for 2 seconds. By the time it finishes, the Event Loop processes the rendering macrotask — but then immediately processes `hideSpinner()`. The user never sees the spinner. The fix is to use `setTimeout(() => longComputation(), 0)` or `requestAnimationFrame` to let the rendering happen first. Without understanding the Event Loop, this bug makes no sense.

</details>
