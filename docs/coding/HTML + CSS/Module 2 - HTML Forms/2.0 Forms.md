# Doc 2.0 — Forms

## Where We Are So Far

HTML Basics is complete: structure, elements, attributes, text, links, images, lists, tables, and semantic tags. The page can display content. The next capability is letting the visitor send information back: forms. Connection: static pages are done; now we collect input and ship it to a server.

## Broader Goal

Learn what a form is, how it packages data as name/value pairs, how `action` and `method` decide where and how that data travels, why every field needs a `name`, and how `label` + `id` make a field usable and accessible. This is the foundation the rest of Module 2 builds on.

## Main Content

A form is the part of a web page that lets a visitor type or pick information and send it somewhere, usually to a server. A login box, a search bar, and a signup page are all forms. In HTML you wrap everything in a `<form>` tag; the controls go between the opening and closing tags.

**The smallest possible form:**

```html
<form>
  <input type="text">
  <button>Send</button>
</form>
```

Line by line: `<form>` opens the container; `<input type="text">` is a box where the person types; `<button>` is what they click to send; `</form>` closes the container. Open this in a browser and you see a box and a button, but it does nothing useful yet, because we have not told it where to send the information.

**The `form` tag is just the container** — like the paper a bank form is printed on. The real work is done by the attributes on it and by the controls inside it.

**`action` — where the data goes.** It is a URL, like writing a destination on an envelope. If `action="/search"`, the browser mails the information to that address and the server there deals with it. Leave `action` out and the data is sent back to the same page you are already on.

```html
<form action="/search">
```

**`method` — how the data is sent.** There are two options: `get` and `post`.

- `get`: the data is appended to the end of the URL as query parameters, like `/search?author=Orwell`. You can see it in the address bar, and you can bookmark or share that URL. Use it for searches and for anything that only reads data.
- `post`: the data goes inside the body of the HTTP request, so it does not show up in the URL. Use it for logins, signups, and anything that creates or changes data.

If you do not write a `method`, the default is `get`.

```html
<form action="/search" method="get">
```

The name describes the *goal* of the request, not whether data travels along with it. With a search form you are asking the server to *get* you results for "shoes"; you do send a little data (the search word), but the goal is to receive a page back. `post` is for when you are sending data so the server does something with it, like creating an account.

One caution: `post` is not encrypted by itself. It only keeps data out of the URL. HTTPS is what actually protects the data in transit. So never put a password in a `get` form, and always serve login forms over HTTPS.

**`name` — the label the data travels under.** It goes on each input. When the form is submitted, the browser sends each input's value paired with its name. If you write `<input name="author">` and the user types `Orwell`, the browser sends `author=Orwell`. With `get` that shows up in the URL as `?author=Orwell`.

The critical rule: **if an input has no `name`, its value is not sent at all.** The user can type in it, but the server never receives it. That is why a field with no `name` is silently ignored — the most common beginner bug in forms.

```html
<form action="/search" method="get">
  <input type="text" name="author">
  <button>Search</button>
</form>
```

Walkthrough: type `Orwell` and click Search. The browser navigates to `/search?author=Orwell`. Then change `method="get"` to `method="post"`, reload, and submit again — the data is no longer in the URL.

**`id` vs `name` — two different jobs.** `id` is for linking the label (and for CSS/JS hooks); `name` is what the data travels under. They often hold the same value, but they are not the same thing, and confusing them breaks either the label or the submission.

```html
<input type="text" id="author" name="author">
```

**`label` — the text that tells the user what a field is for.** You write it with a `<label>` tag and connect it to a field using two matching attributes: the input gets an `id`, and the label gets a `for` attribute with the same value.

```html
<label for="author">Author</label>
<input type="text" id="author" name="author">
```

The `id` and the `for` must match exactly. That link does two useful things: clicking the label text puts the cursor in the box, and screen readers announce what the field is for.

You can also wrap the input inside the label, which pairs them without needing `for`/`id`:

```html
<label>
  Author
  <input type="text" name="author">
</label>
```

The explicit `for`/`id` form is preferred because it is more flexible (the label and input can be separated) and is what assistive tech handles most reliably.

**Putting it together:**

```html
<form action="/search" method="get">
  <label for="author">Author</label>
  <input type="text" id="author" name="author">

  <label for="msg">Message</label>
  <textarea id="msg" name="msg" rows="4" cols="30"></textarea>

  <label for="city">City</label>
  <select id="city" name="city" required>
    <option value="">Choose a city</option>
    <option value="lko">Lucknow</option>
    <option value="del">Delhi</option>
  </select>

  <button type="submit">Search</button>
  <button type="reset">Reset</button>
</form>
```

Line by line: the form posts... actually sends with `get` to `/search`; each control has a `name` so its value is submitted; each has an `id` matched by a `label`'s `for`; the select's first option has an empty `value` so `required` can block "nothing chosen"; Reset clears all fields back to their starting values.

**Debugging scenarios:**

- "I typed in the box but the server got nothing" — the input has no `name`. Add `name="..."`.
- "My label click does not focus the input" — the `for` and `id` do not match exactly (case or spelling). Make them identical.
- "The URL shows `?author=` with no value" — the field is named but empty, or the value was a placeholder (placeholder is never sent). Type a real value.
- "Data shows in the URL when it should not" — `method` is `get` (the default) instead of `post`. Set `method="post"`.
- "The form submits to the wrong page" — `action` is missing or wrong. Set it explicitly.
- "My password appears in the address bar" — the form uses `get`. Switch to `post` and serve over HTTPS.

## Common Mistakes

- Forgetting `name` on inputs — the field is silently not submitted.
- Confusing `id` (label linking, CSS, JS) with `name` (submission key).
- Using `get` for sensitive data like passwords.
- Leaving `action` unset and wondering why the page just reloads.
- Treating `placeholder` text as a real default value.
- Forgetting that a `<button>` with no `type` inside a form defaults to `submit`.

## Try It Yourself

1. Build the search form above and submit it with `get`; watch `?author=Orwell` appear in the address bar.
2. Change to `post` and confirm the data leaves the URL.
3. Remove the `name` from one input and confirm it disappears from the submitted data.
4. Add a label, click its text, and watch the cursor jump into the box.
5. Mismatch `for` and `id` on purpose and confirm the click no longer focuses.

## Summary

- `<form>` is the container; controls go inside it.
- `action` sets the destination URL; `method` is `get` (URL) or `post` (body); default is `get`.
- Only controls with a `name` are submitted, as `name=value` pairs.
- `id` links labels and hooks CSS/JS; `name` is the submission key.
- `label` + matching `for`/`id` gives usability and accessibility.
- `post` keeps data out of the URL, but HTTPS is what protects it in transit.

## In Your Own Words

1. What tag creates a form, and what is its job?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The `<form>` tag. It is the container that holds input controls; when submitted, the browser gathers the values of all named controls inside it and sends them to the server as name/value pairs.

</details>

2. What does `action` specify, and what happens if you omit it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `action` specifies the URL that receives the form data. If omitted, the data is submitted to the current page (the page reloads with the data in the URL for `get`).

</details>

3. When should you use `get` vs `post`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Use `get` for reading/searching where the result URL should be bookmarkable (data in URL). Use `post` for creating/changing data or sensitive input like passwords (data in request body). Default is `get`.

</details>

4. Why must an input have a `name` attribute to be submitted?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The browser sends data as `name=value` pairs. Without `name`, the control has no key, so its value is silently dropped and the server never receives it.

</details>

5. What is the difference between `id` and `name` on an input?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `id` uniquely identifies the element on the page and links it to a `<label>` (via `for`) and to CSS/JS. `name` is the key under which the value is submitted to the server. They often match but serve different purposes.

</details>

## Cheat Sheet (Quick Recall)

**Container:** `<form>...</form>`. **Destination:** `action="/path"`. **Method:** `get` (URL) / `post` (body); default `get`.

**Submission rule:** only controls with `name` are sent, as `name=value`.

**Label pairing:** `<label for="x">` + `<input id="x" name="x">`. Clicking the label focuses the input.

**id** = unique hook/label target. **name** = submission key. **HTTPS** protects data in transit; `post` alone does not.
