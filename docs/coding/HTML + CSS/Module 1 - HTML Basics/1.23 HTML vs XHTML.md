## Main Content

HTML and XHTML are two paths. XHTML was a separate, stricter version of HTML that arrived around 2000. It followed XML's rules. HTML5 then took the other path: forgiving and flexible. The problem beginners create: they see `<br />` in old templates and assume it is required in modern HTML, or they expect browsers to reject malformed HTML (they auto-fix). Understanding the split clears up both.

Start from an unclosed `<p>` in your HTML. Guess: the browser refuses to render the page? No — HTML5 auto-fixes it. Guess: the browser renders it fine? Yes. That forgiving behavior is HTML5. XHTML would have refused to render the whole document on a single unclosed tag.

**XHTML rules (strict):**

1. Every tag must be closed (even void elements: `<br />`).
2. Tags in lowercase only.
3. Attribute values always in quotes.
4. Documents must be well-formed XML.

```html
<!-- XHTML style -->
<br />
<img src="photo.jpg" alt="Photo" />
<p>Hello</p>
```

Line by line: void elements carry a trailing slash and space before it. All tags close. Attribute values are quoted.

**HTML5 rules (forgiving):**

1. Void elements need no closing tag or slash: `<br>`, `<img>`.
2. Tags are case-insensitive (but lowercase is convention).
3. Attribute values can be unquoted in simple cases (but quoting is best practice).
4. The browser auto-fixes many mistakes (unclosed tags, missing structure).

```html
<!-- HTML5 style (standard now) -->
<br>
<img src="photo.jpg" alt="Photo">
<p>Hello</p>
```

Line by line: void elements need no slash. Tags are lowercase by convention but not enforced. The browser repairs unclosed tags automatically.

**Why XHTML existed:** XML was popular and strict; applying its rules to HTML promised cleaner, machine-readable documents and better tooling.

**Why HTML5 won:** the web is messy and authored by millions. A forgiving parser that auto-fixes mistakes serves the real web better than a strict one that refuses to render. Developers still write clean code by convention, but the browser does not break on small errors.

**Where you still see XHTML habits:**

- Older codebases and templates with `<br />`.
- React/JSX, which requires self-closing void elements (`<br />`).
- Some validators and XML pipelines.

**Comparison table:**

| Feature | XHTML (strict) | HTML5 (forgiving) |
|---|---|---|
| Void element close | Required: `<br />` | Optional: `<br>` |
| Tag case | Lowercase only | Case-insensitive |
| Attribute quotes | Always required | Optional (but recommended) |
| Error handling | Refuses to render (XML error) | Auto-fixes |
| Status | Legacy | Current standard |

**Debugging scenarios:**

- "My page refuses to render at all" — if served as `application/xhtml+xml`, a single XML error (unclosed tag, unescaped `&`) breaks the whole page. Fix the error or serve as `text/html`.
- "My React component complains about self-closing tags" — JSX requires `<br />`. Add the slash in JSX only.
- "My validator flags `<br>`" — some older validators expect XHTML. Modern HTML5 validators accept `<br>`.
- "My browser auto-closed a tag I left open" — expected in HTML5. Check the Elements tab to see how it was repaired, then fix your source.

## Common Mistakes

- Assuming `<br />` is required in HTML5 (it is optional).
- Thinking XHTML is "better" because it is strict (HTML5 is the standard).
- Mixing XHTML self-closing with HTML5 void tags inconsistently.
- Expecting browsers to reject malformed HTML (they auto-fix).
- Serving HTML as XHTML without ensuring well-formedness.

## Try It Yourself

1. Write `<br>` and `<br />` side by side; confirm identical output.
2. Write an unclosed `<p>` and inspect how the browser auto-closes it.
3. Check an older template for XHTML-style self-closing tags.
4. Note that React/JSX still requires self-closing void elements.

## Summary

- XHTML = strict XML-based HTML (closed tags, lowercase, quoted attrs).
- HTML5 = forgiving (optional slashes, case-insensitive, auto-fix).
- Modern standard is HTML5; XHTML is legacy.
- Trailing slash on void elements is optional in HTML5.
- Clean code by convention, not by parser enforcement.
