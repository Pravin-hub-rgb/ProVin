SOLID — 5 design principles that make **object-oriented code** maintainable, flexible, and scalable. You're already using these in your code — interface separation, private properties, method overriding. SOLID is the collection of these principles.

---

# SOLID Principles

## What is SOLID

**SOLID** = 5 design principles that make **object-oriented code** maintainable, flexible, and scalable. Each has a letter:

| Letter | Principle | One-liner |
|---|---|---|
| **S** | Single Responsibility | A class should have only one job |
| **O** | Open/Closed | Open for extension, closed for modification |
| **L** | Liskov Substitution | Child class can be used in place of parent class |
| **I** | Interface Segregation | Small, specific interfaces are better than one big one |
| **D** | Dependency Inversion | High-level modules should depend on abstractions |

---

## S — Single Responsibility Principle

**A class should have only one job/reason-to-change.**

```typescript
// ❌ BAD — Multiple responsibilities
class Product {
  name: string;
  price: number;

  saveToDatabase(): void {
    // Database logic — not Product's job
  }

  sendEmail(): void {
    // Email logic — also not Product's job
  }

  generateReport(): string {
    // Report logic — also not Product's job
  }
}
```

```typescript
// ✅ GOOD — Single responsibility
class Product {
  constructor(public name: string, public price: number) {}
}

class ProductRepository {
  save(product: Product): void {
    // Database logic — separate class
  }
}

class EmailService {
  sendNotification(product: Product): void {
    // Email logic — separate class
  }
}

class ReportGenerator {
  generate(product: Product): string {
    // Report logic — separate class
  }
}
```

This is like modules — each module has one job. `utils.ts` has utility functions, `api.ts` has API calls. Don't put everything in one file.

## O — Open/Closed Principle

**Open for extension, closed for modification.** Add new features without touching old code.

```typescript
// ❌ BAD — Need to change function for every new discount
function getDiscountedPrice(product: Product, discountType: string): number {
  if (discountType === "percentage") {
    return product.price * 0.9;
  } else if (discountType === "flat") {
    return product.price - 50;
  }
  // Add here for every new discount = modification
}
```

```typescript
// ✅ GOOD — Extension open, modification closed
interface DiscountStrategy {
  apply(price: number): number;
}

class PercentageDiscount implements DiscountStrategy {
  constructor(private percentage: number) {}
  apply(price: number): number {
    return price * (1 - this.percentage / 100);
  }
}

class FlatDiscount implements DiscountStrategy {
  constructor(private amount: number) {}
  apply(price: number): number {
    return price - this.amount;
  }
}

function getDiscountedPrice(product: Product, discount: DiscountStrategy): number {
  return discount.apply(product.price);
}

// Add a new discount — old code doesn't change
class BuyOneGetOne implements DiscountStrategy {
  apply(price: number): number {
    return price; // half price logic
  }
}
```

## L — Liskov Substitution Principle

**Child class can be used in place of parent class without breaking behavior.**

```typescript
// ❌ BAD — Child breaks behavior
class Bird {
  fly(): string {
    return "Flying";
  }
}

class Penguin extends Bird {
  override fly(): string {
    return "Penguins can't fly!"; // ❌ Behavior broken
  }
}

function makeBirdFly(bird: Bird): string {
  return bird.fly(); // wrong for Penguin
}
```

```typescript
// ✅ GOOD — Behavior preserved
interface Flyable {
  fly(): string;
}

interface Swimmable {
  swim(): string;
}

class Sparrow implements Flyable {
  fly(): string { return "Flying"; }
}

class Penguin implements Swimmable {
  swim(): string { return "Swimming"; }
}

// Separate interface for each type — substitution is safe
```

This relates to function parameter types — if a function accepts `Bird`, any `Bird` subclass should work without breaking the function.

## I — Interface Segregation Principle

**Small, specific interfaces are better than one big "everything" interface.**

```typescript
// ❌ BAD — Big interface, forced implementation
interface Worker {
  work(): void;
  eat(): void;
  sleep(): void;
}

// Robot has to implement eat() and sleep() — useless
class Robot implements Worker {
  work() { console.log("Working"); }
  eat() { } // ❌ Robot doesn't eat
  sleep() { } // ❌ Robot doesn't sleep
}
```

```typescript
// ✅ GOOD — Small, specific interfaces
interface Workable {
  work(): void;
}

interface Eatable {
  eat(): void;
}

interface Sleepable {
  sleep(): void;
}

class Robot implements Workable {
  work() { console.log("Working"); }
  // eat() and sleep() not needed
}

class Human implements Workable, Eatable, Sleepable {
  work() { console.log("Working"); }
  eat() { console.log("Eating"); }
  sleep() { console.log("Sleeping"); }
}
```

This is interface separation — `Product` interface separate, `Discountable` interface separate, `Shippable` interface separate. Don't create one big `ProductWithDiscountAndShipping` interface.

## D — Dependency Inversion Principle

**High-level modules shouldn't depend directly on low-level modules; both should depend on abstractions.**

```typescript
// ❌ BAD — High-level directly depends on low-level
class MySQLDatabase {
  query(sql: string) { /* MySQL specific */ }
}

class UserService {
  private db = new MySQLDatabase(); // ❌ Direct dependency

  getUser(id: string) {
    return this.db.query(`SELECT * FROM users WHERE id = ${id}`);
  }
}
```

```typescript
// ✅ GOOD — Both depend on abstraction
interface Database {
  query(sql: string): any;
}

class MySQLDatabase implements Database {
  query(sql: string) { /* MySQL specific */ }
}

class PostgreSQLDatabase implements Database {
  query(sql: string) { /* PostgreSQL specific */ }
}

class UserService {
  constructor(private db: Database) {} // ✅ Depends on abstraction

  getUser(id: string) {
    return this.db.query(`SELECT * FROM users WHERE id = ${id}`);
  }
}

// Easy to switch
const mysqlService = new UserService(new MySQLDatabase());
const pgService = new UserService(new PostgreSQLDatabase());
```

This is constructor injection — accept a `Database` interface, not a concrete class. Makes mocking easy in Jest tests.

## SOLID — Quick Reference

| Principle | Rule | Violation Example | Solution |
|---|---|---|---|
| **S** | One class = one job | Product class does database + email + report | Separate classes: ProductRepository, EmailService, ReportGenerator |
| **O** | Extension open, modification closed | Need to change function for every new discount | Use DiscountStrategy interface |
| **L** | Child can substitute parent | Penguin extends Bird — fly() breaks | Separate via interfaces (Flyable, Swimmable) |
| **I** | Small interfaces better | Worker interface — Robot forced to implement eat/sleep | Separate: Workable, Eatable, Sleepable |
| **D** | Depend on abstractions | UserService directly depends on MySQLDatabase | Inject Database interface |

## Interview Answer

Interviewer asks: "Explain SOLID principles?"

**Answer (short):** "5 design principles — Single Responsibility (one class = one job), Open/Closed (extension open, modification closed), Liskov Substitution (child can substitute parent), Interface Segregation (small interfaces), Dependency Inversion (depend on abstractions). These make code maintainable."

**Practical answer:** "I used these in DukaanOS — Product class only holds data (Single Responsibility). Discount strategies are separate classes (Open/Closed). Payment methods (UPI, Cash) implement one interface (Interface Segregation). Database repository extends an abstract class (Dependency Inversion)."

## What It Is NOT

⚠️ **SOLID ≠ over-engineering.** Not needed for simple apps. When code is complex, team is large, new features keep coming — SOLID helps.

⚠️ **SOLID ≠ rules, they're guidelines.** Not necessary to apply in every situation. Sometimes the simple solution is best.

⚠️ **SOLID ≠ only OOP.** Functional programming has similar principles (pure functions, immutability).

## In Your Own Words

1. What is the Single Responsibility Principle? Give an example.

<details>
<summary>Sample Answer</summary>

**Answer:** A class should have only one job. Example: Product class only holds data (name, price). Database operations go in a separate ProductRepository class. Email goes in a separate EmailService class. If Product class does database + email + report, SRP is violated.

</details>

2. How do you follow the Open/Closed Principle in TypeScript?

<details>
<summary>Sample Answer</summary>

**Answer:** Using interfaces or abstract classes. Create a DiscountStrategy interface — PercentageDiscount, FlatDiscount, BuyOneGetOne implement it. Adding a new discount means just implementing a new class — old code doesn't change. Open for extension, closed for modification.

</details>

3. Why is the Interface Segregation Principle important?

<details>
<summary>Sample Answer</summary>

**Answer:** Big interfaces force small classes to implement unwanted methods. If there's a big Worker interface, Robot has to implement `eat()` and `sleep()`. Small interfaces (Workable, Eatable, Sleepable) let each class implement only what it uses.

</details>

4. Where is the Dependency Inversion Principle used in real projects?

<details>
<summary>Sample Answer</summary>

**Answer:** In the database layer — UserService shouldn't depend directly on MySQLDatabase, it should depend on a Database interface. Easy to mock in tests (replace MySQL with a mock database). In production, switching from MySQL to PostgreSQL means just changing the constructor, not the service class.

</details>
