SOLID — 5 design principles jo **object-oriented code** ko maintainable, flexible, aur scalable banate hain. Ye sab principles tum already use kar rahe ho apne code mein — interface separation, private properties, method overriding. SOLID in principles ka collection hai.

---

# SOLID Principles

## SOLID Kya Hai

**SOLID** = 5 design principles jo **object-oriented code** ko maintainable, flexible, aur scalable banate hain. Har ek ka ek letter hai:

| Letter | Principle | One-liner |
|---|---|---|
| **S** | Single Responsibility | Ek class ka sirf ek kaam hona chahiye |
| **O** | Open/Closed | Extension ke liye open, modification ke liye closed |
| **L** | Liskov Substitution | Child class, parent class ki jagah use ho sakti hai |
| **I** | Interface Segregation | Chhote, specific interfaces behtar hain ek bade se |
| **D** | Dependency Inversion | High-level modules abstraction pe depend karein |

---

## S — Single Responsibility Principle

**Ek class ka sirf ek kaam/reason-to-change hona chahiye.**

```typescript
// ❌ BAD — Multiple responsibilities
class Product {
  name: string;
  price: number;

  saveToDatabase(): void {
    // Database logic — ye Product ka kaam nahi hai
  }

  sendEmail(): void {
    // Email logic — ye bhi Product ka kaam nahi hai
  }

  generateReport(): string {
    // Report logic — ye bhi Product ka kaam nahi hai
  }
}
```

```typescript
// ✅ GOOD — Single responsibility
class Product {
  constructor(public name: string, public price: number) {}
}

class ProductRepository {
  save(product: Product): void {
    // Database logic — alag class
  }
}

class EmailService {
  sendNotification(product: Product): void {
    // Email logic — alag class
  }
}

class ReportGenerator {
  generate(product: Product): string {
    // Report logic — alag class
  }
}
```

Ye modules ki tarah hai — har module ka ek kaam. `utils.ts` mein utility functions, `api.ts` mein API calls. Ek file mein sab mat daalo.

## O — Open/Closed Principle

**Extension ke liye open, modification ke liye closed.** Naya feature add karo bina purana code chhede.

```typescript
// ❌ BAD — Har naye discount ke liye function change karna padega
function getDiscountedPrice(product: Product, discountType: string): number {
  if (discountType === "percentage") {
    return product.price * 0.9;
  } else if (discountType === "flat") {
    return product.price - 50;
  }
  // Har naye discount ke liye yahan add karo = modification
}
```

```typescript
// ✅ GOOD — Extension open, modification closed
interface DiscountStrategy {
  apply(price: number): number;
}

class PercentageDiscount implements DiscountStrategy {
  constructor(private percentage: number) {}
  apply(price: number): number {
    return price * (1 - this.percentage / 100);
  }
}

class FlatDiscount implements DiscountStrategy {
  constructor(private amount: number) {}
  apply(price: number): number {
    return price - this.amount;
  }
}

function getDiscountedPrice(product: Product, discount: DiscountStrategy): number {
  return discount.apply(product.price);
}

// Naya discount add karo — purana code change nahi
class BuyOneGetOne implements DiscountStrategy {
  apply(price: number): number {
    return price; // Half price logic
  }
}
```

## L — Liskov Substitution Principle

**Child class, parent class ki jagah use ho sakti hai bina behavior tode.**

```typescript
// ❌ BAD — Child behavior tode
class Bird {
  fly(): string {
    return "Flying";
  }
}

class Penguin extends Bird {
  override fly(): string {
    return "Penguins can't fly!"; // ❌ Behavior broken
  }
}

function makeBirdFly(bird: Bird): string {
  return bird.fly(); // Penguin ke liye galat
}
```

```typescript
// ✅ GOOD — Behavior preserved
interface Flyable {
  fly(): string;
}

interface Swimmable {
  swim(): string;
}

class Sparrow implements Flyable {
  fly(): string { return "Flying"; }
}

class Penguin implements Swimmable {
  swim(): string { return "Swimming"; }
}

// Har type ke liye alag interface — substitution safe hai
```

Ye function parameters ke types se relate hota hai — agar function `Bird` accept karta hai, toh koi bhi `Bird` ka subclass aana chahiye bina function tode.

## I — Interface Segregation Principle

**Chhote, specific interfaces behtar hain ek bade "sab kuch wale" interface se.**

```typescript
// ❌ BAD — Bada interface, forced implementation
interface Worker {
  work(): void;
  eat(): void;
  sleep(): void;
}

// Robot ko eat() aur sleep() implement karna padega — useless
class Robot implements Worker {
  work() { console.log("Working"); }
  eat() { } // ❌ Robot khana nahi khaata
  sleep() { } // ❌ Robot sota nahi
}
```

```typescript
// ✅ GOOD — Chhote, specific interfaces
interface Workable {
  work(): void;
}

interface Eatable {
  eat(): void;
}

interface Sleepable {
  sleep(): void;
}

class Robot implements Workable {
  work() { console.log("Working"); }
  // eat() aur sleep() implement nahi karna padega
}

class Human implements Workable, Eatable, Sleepable {
  work() { console.log("Working"); }
  eat() { console.log("Eating"); }
  sleep() { console.log("Sleeping"); }
}
```

Ye `interface` separation hai — `Product` interface alag, `Discountable` interface alag, `Shippable` interface alag. Ek bada `ProductWithDiscountAndShipping` interface mat banao.

## D — Dependency Inversion Principle

**High-level modules low-level modules pe directly depend na karein, dono abstraction pe depend karein.**

```typescript
// ❌ BAD — High-level directly depends on low-level
class MySQLDatabase {
  query(sql: string) { /* MySQL specific */ }
}

class UserService {
  private db = new MySQLDatabase(); // ❌ Direct dependency

  getUser(id: string) {
    return this.db.query(`SELECT * FROM users WHERE id = ${id}`);
  }
}
```

```typescript
// ✅ GOOD — Both depend on abstraction
interface Database {
  query(sql: string): any;
}

class MySQLDatabase implements Database {
  query(sql: string) { /* MySQL specific */ }
}

class PostgreSQLDatabase implements Database {
  query(sql: string) { /* PostgreSQL specific */ }
}

class UserService {
  constructor(private db: Database) {} // ✅ Depends on abstraction

  getUser(id: string) {
    return this.db.query(`SELECT * FROM users WHERE id = ${id}`);
  }
}

// Ab easily switch kar sakte ho
const mysqlService = new UserService(new MySQLDatabase());
const pgService = new UserService(new PostgreSQLDatabase());
```

Ye constructor injection hai — `Database` interface accept karo, concrete class nahi. Jest testing mein bhi mock easily kar paoge.

## SOLID — Quick Reference

| Principle | Rule | Violation Example | Solution |
|---|---|---|---|
| **S** | Ek class = ek kaam | Product class database + email + report sab karti hai | Alag classes: ProductRepository, EmailService, ReportGenerator |
| **O** | Extension open, modification closed | Har naye discount ke liye function change karna | DiscountStrategy interface use karo |
| **L** | Child parent ki jagah le sakta hai | Penguin extends Bird — fly() tode | Interface se alag karo (Flyable, Swimmable) |
| **I** | Chhote interfaces behtar | Worker interface — Robot ko eat/sleep implement karna padega | Workable, Eatable, Sleepable alag karo |
| **D** | Abstraction pe depend karo | UserService directly MySQLDatabase depend kare | Database interface inject karo |

## Interview Answer

Interviewer poochhe: "SOLID principles explain karo?"

**Answer (short):** "5 design principles hain — Single Responsibility (ek class = ek kaam), Open/Closed (extension open, modification closed), Liskov Substitution (child parent ki jagah le sake), Interface Segregation (chhote interfaces), Dependency Inversion (abstraction pe depend karo). Ye sab code ko maintainable banate hain."

**Practical answer:** "Maine DukaanOS mein ye use kiya — Product class sirf data rakhti hai (Single Responsibility). Discount strategies alag classes hain (Open/Closed). Payment methods (UPI, Cash) ek interface implement karte hain (Interface Segregation). Database repository abstract class se extend hota hai (Dependency Inversion)."

## What It Is NOT

⚠️ **SOLID = over-engineering nahi.** Simple app ke liye ye sab zaroori nahi. Jab code complex ho, team ho, naye features aate rahein — tab SOLID helpful hai.

⚠️ **SOLID = rules nahi hain guidelines.** Har situation mein apply karna zaroori nahi. Sometimes simple solution best hai.

⚠️ **SOLID = sirf OOP nahi.** Functional programming mein bhi similar principles hain (pure functions, immutability).

## In Your Own Words

1. Single Responsibility Principle kya hai? Ek example do.

<details>
<summary>Sample Jawab</summary>

**Jawab:** Ek class ka sirf ek kaam hona chahiye. Example: Product class sirf data rakhe (name, price). Database operations ke liye ProductRepository alag class ho. Email bhejne ke liye EmailService alag class ho. Agar Product class database + email + report sab karti hai toh SRP violate ho raha hai.

</details>

2. Open/Closed Principle TypeScript mein kaise follow karte ho?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Interface ya abstract class use karke. DiscountStrategy interface banao — PercentageDiscount, FlatDiscount, BuyOneGetOne implement karein. Naya discount add karo toh purana code change nahi karna — sirf naya class implement karo. Open for extension, closed for modification.

</details>

3. Interface Segregation Principle kyun important hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Bade interface se chhote classes ko unwanted methods implement karna padta hai. Robot ko `eat()` aur `sleep()` implement karna padega agar bada Worker interface ho. Chhote interfaces (Workable, Eatable, Sleepable) se har class sirf wahi implement karti hai jo use karti hai.

</details>

4. Dependency Inversion Principle real project mein kahan use hota hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Database layer mein — UserService directly MySQLDatabase pe depend na kare, Database interface pe depend kare. Testing mein easily mock kar paoge (MySQL ke jagah mock database). Production mein MySQL se PostgreSQL switch karna ho toh sirf constructor change karo, service class change nahi.

</details>
