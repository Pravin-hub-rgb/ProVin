# Abstraction

## What is Abstraction

**Abstraction** = hiding complex implementation details, showing only the **necessary/relevant things** to the user.

```typescript
// Interface = Abstraction
interface PaymentProcessor {
  processPayment(amount: number): void;
  refund(amount: number): void;
}

// Caller knows: processPayment() and refund() exist
// Caller doesn't know: is it connecting via Stripe? UPI? Bank transfer?
// Caller doesn't know — that's abstraction
```

**Real-world analogy (code version):**
```typescript
// You use `fetch()` — but what happens inside?
fetch('https://api.example.com');
// You know: request will go, response will come
// You don't know: DNS resolve, TCP connection, SSL handshake...
// That's abstraction — complex details hidden
```

## Abstract Classes

**Abstract class** = incomplete class — some methods are only **declared** (signature exists), **not defined** (no implementation). Must be completed in the child class.

```typescript
abstract class PaymentMethod {
  // Abstract methods — declaration only, no implementation
  abstract processPayment(amount: number): void;
  abstract refund(amount: number): void;

  // Concrete method — has implementation
  logTransaction(amount: number): void {
    console.log(`Transaction of ₹${amount} logged at ${new Date()}`);
  }
}

// ❌ Can't instantiate abstract class directly
// const p = new PaymentMethod(); // Error!

// ✅ Create child class, implement, then instantiate
class UPIPayment extends PaymentMethod {
  processPayment(amount: number): void {
    console.log(`Processing ₹${amount} via UPI`);
    this.logTransaction(amount); // parent's method
  }

  refund(amount: number): void {
    console.log(`Refunding ₹${amount} via UPI`);
  }
}

const upi = new UPIPayment();
upi.processPayment(500); // ✅
```

**Interview question:** "Why can't you instantiate an abstract class?"

**Answer:** "Because it's incomplete — some methods are only declared, not defined. If you instantiate it, incomplete methods could be called — runtime error. So first complete it in a child class, then instantiate the child."

## Interface vs Abstract Class

This is the most common comparison question in interviews.

| | Interface | Abstract Class |
|---|---|---|
| Implementation | Only contract, no implementation | Some methods can be implemented |
| Multiple inheritance | A class can implement multiple interfaces | A class can extend only one abstract class |
| Properties | Only defines type | Properties with values possible |
| Constructor | None | Yes |
| Access modifiers | Only public | Public, private, protected — all |
| When to use | When you only need the contract "these methods must exist" | When common logic should also be shared |

### Interface Example
```typescript
// Interface — only contract
interface Payable {
  pay(amount: number): void;
}

interface Refundable {
  refund(amount: number): void;
}

// Multiple interfaces — allowed
class OnlineOrder implements Payable, Refundable {
  pay(amount: number): void {
    console.log(`Paid ₹${amount}`);
  }
  refund(amount: number): void {
    console.log(`Refunded ₹${amount}`);
  }
}
```

### Abstract Class Example
```typescript
// Abstract class — common logic + contract
abstract class PaymentMethod {
  // Common logic — same for every payment method
  logTransaction(amount: number): void {
    console.log(`₹${amount} transaction logged`);
  }

  // Contract — child implements
  abstract processPayment(amount: number): void;
  abstract refund(amount: number): void;
}

class UPIPayment extends PaymentMethod {
  processPayment(amount: number): void {
    console.log(`UPI: ₹${amount}`);
    this.logTransaction(amount); // reuse common logic
  }
  refund(amount: number): void {
    console.log(`UPI refund: ₹${amount}`);
  }
}

// ❌ Multiple abstract classes — not allowed
// class X extends PaymentMethod, AnotherAbstract { }
```

**Simple rule:** Use an interface when you only need the contract "these methods must exist," leaving implementation freedom to the child. Use an abstract class when you also want to share some common logic among child classes.

## Abstraction — Practical Example

```typescript
// Abstract class — abstraction of database operations
abstract class DatabaseRepository<T> {
  abstract findById(id: string): Promise<T | null>;
  abstract findAll(): Promise<T[]>;
  abstract create(data: T): Promise<T>;
  abstract update(id: string, data: Partial<T>): Promise<T>;
  abstract delete(id: string): Promise<void>;

  // Common logic — validation
  validate(data: any): boolean {
    return data !== null && data !== undefined;
  }
}

// Concrete implementation — Product repository
class ProductRepository extends DatabaseRepository<Product> {
  async findById(id: string): Promise<Product | null> {
    return prisma.product.findUnique({ where: { id } });
  }

  async findAll(): Promise<Product[]> {
    return prisma.product.findMany();
  }

  async create(data: Product): Promise<Product> {
    return prisma.product.create({ data });
  }

  async update(id: string, data: Partial<Product>): Promise<Product> {
    return prisma.product.update({ where: { id }, data });
  }

  async delete(id: string): Promise<void> {
    await prisma.product.delete({ where: { id } });
  }
}

// Caller knows: findById, findAll, create, update, delete exist
// Caller doesn't know: Prisma is used, how queries work
// Abstraction — implementation hidden, interface visible
```

## What It Is NOT

⚠️ **Abstraction ≠ data hiding.** Data hiding = encapsulation (private/protected). Abstraction = hiding complexity — showing only relevant things to the user.

⚠️ **Abstract class ≠ interface.** Abstract class can have common logic, constructor, access modifiers. Interface is only a contract.

⚠️ **Abstraction ≠ unnecessary.** When code is complex and has multiple implementations (UPI, Cash, Card), abstraction keeps it clean.

## In Your Own Words

1. Why can't you instantiate an abstract class?

<details>
<summary>Sample Answer</summary>

**Answer:** An abstract class is incomplete — some methods are only declared, not defined. If you instantiate it, incomplete methods could be called — runtime error. So first complete it in a child class (implement the abstract methods), then instantiate the child class.

</details>

2. Give 3 main differences between Interface and Abstract Class.

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Interface is only a contract; abstract class can also have common logic. (2) Multiple interfaces can be implemented; only one abstract class can be extended. (3) Interface has no constructor; abstract class does. (4) Interface has only public methods; abstract class has public/private/protected all.

</details>

3. Where would abstraction be useful in your DukaanOS?

<details>
<summary>Sample Answer</summary>

**Answer:** Payment methods — UPI, Cash, Card — can all extend the PaymentMethod abstract class. Same `processPayment()` call, different behavior. Discount strategies — PercentageDiscount, FlatDiscount — can all extend DiscountStrategy. Add a new payment method, old code doesn't change.

</details>

4. "Use an interface when implementation freedom should be left to the child" — what does this mean?

<details>
<summary>Sample Answer</summary>

**Answer:** An interface only defines method signatures — `pay(amount: number): void`. Every implementer (UPI, Cash, Card) implements it in its own way. The interface imposes no restriction on "how to do it" — only "what to do." An abstract class has common logic that everyone follows.

</details>
