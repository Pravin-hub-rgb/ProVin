The problem with REST API is — the client has to **send a request every time** to get new data (polling). Like calling `fetch()` every 5 seconds to ask "any new order?" This is inefficient.

**WebSocket** solves this — once the connection is established, the server pushes data itself without the client requesting.

---

# WebSockets — Real-Time Connection

## REST API's Limitation

Imagine your trading bot — stock prices change in real-time. If you use a REST API:

```javascript
// ❌ REST Polling — inefficient
setInterval(async () => {
  const response = await fetch('/api/prices');
  const prices = await response.json();
  updateUI(prices);
}, 1000); // request every second
```

**Problems:**
1. One HTTP request every second — bandwidth waste
2. HTTP headers sent repeatedly — overhead
3. Unnecessary load on the server
4. Latency — by the time request sent and response received, price has changed

## WebSocket — Better Solution

```javascript
// ✅ WebSocket — efficient, real-time
const ws = new WebSocket('wss://api.upstox.com/feed');

ws.onopen = () => {
  console.log('Connected');
  // Subscribe to server
  ws.send(JSON.stringify({ action: 'subscribe', symbol: 'RELIANCE' }));
};

ws.onmessage = (event) => {
  const data = JSON.parse(event.data);
  // Server pushes data itself — no request needed
  updatePrice(data);
};

ws.onclose = () => {
  console.log('Disconnected');
};
```

**Benefits:**
1. **One-time connection** — no repeated requests
2. **Server push** — server sends data itself
3. **Low latency** — real-time updates
4. **Less overhead** — no HTTP headers

## WebSocket vs REST — Comparison

| | REST API | WebSocket |
|---|---|---|
| Connection | New connection per request | One persistent connection |
| Direction | Client → Server (request) | Bidirectional (client + server) |
| Data flow | Client asks | Server pushes |
| Latency | Higher (request-response cycle) | Lower (persistent connection) |
| Use case | CRUD operations | Real-time data, chat, gaming |

---

## WebSocket Connection Lifecycle

```
1. Client: Requests WebSocket connection
2. Server: Accepts connection (upgrade HTTP → WebSocket)
3. Client: Tells server "I need this data" (subscribe)
4. Server: Pushes new data to client as it arrives
5. Connection stays open until client closes it
```

```javascript
// REST = function call each time
const data = await fetch('/api/data'); // one call

// WebSocket = subscribe, data keeps coming
ws.on('price-update', (data) => { // keeps coming continuously });
```

## How WebSocket Works — Under the Hood

1. **HTTP Upgrade:** Client first sends an HTTP request, telling server "I want a WebSocket connection"
2. **Handshake:** Server accepts, connection upgrades HTTP → WebSocket
3. **Persistent Connection:** TCP connection stays open — both sides can send data
4. **Frames:** Data is sent in **frames** (like packets but at application level)

```
Client: HTTP GET /feed (Upgrade: websocket)
Server: HTTP 101 Switching Protocols
Now: TCP connection open, bidirectional data flow
```

---

## What It Is NOT

⚠️ **WebSocket ≠ replacement for REST.** REST is better for CRUD operations. WebSocket is only for real-time, continuous data.

⚠️ **WebSocket ≠ always on.** Connection can drop — server crash, network issue. You have to write reconnection logic.

⚠️ **WebSocket ≠ only for chat.** Trading data, live dashboards, gaming, collaborative editing — many use cases.
