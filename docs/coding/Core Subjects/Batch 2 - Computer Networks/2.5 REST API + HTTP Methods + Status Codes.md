How does data go from frontend to database? Through an **API**. And how do you design an API? By following **REST** principles.

---

# REST API + HTTP Methods + Status Codes

## What is REST

**REST** = Representational State Transfer. An **architecture style** for building APIs. Rules for how an API should be designed:

1. There are **Resources** (data entities) — like Products, Orders, Customers
2. Every resource has a **URL** — `/products`, `/orders`
3. **HTTP methods** define operations — GET, POST, PUT, DELETE

---

## HTTP Methods — CRUD Operations

| Method | Job | SQL Equivalent |
|---|---|---|
| **GET** | Fetch data (read-only) | `SELECT` |
| **POST** | Create new data | `INSERT` |
| **PUT** | Update/replace the whole resource | `UPDATE` (entire row) |
| **PATCH** | Update only a part | `UPDATE` (specific columns) |
| **DELETE** | Delete the resource | `DELETE` |

### GET — Fetching Data

```bash
# all products
curl http://localhost:3000/api/products

# one product
curl http://localhost:3000/api/products/101
```

```javascript
// Client side
const response = await fetch('/api/products');
const products = await response.json();
```

### POST — Creating New Data

```bash
# create a new product
curl -X POST http://localhost:3000/api/products \
  -H "Content-Type: application/json" \
  -d '{"name": "Rice", "price": 120}'
```

```javascript
// Client side
const response = await fetch('/api/products', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Rice', price: 120 })
});
const product = await response.json(); // status: 201 Created
```

### PUT vs PATCH — Update

```bash
# PUT — replace the whole product
curl -X PUT http://localhost:3000/api/products/101 \
  -H "Content-Type: application/json" \
  -d '{"name": "New Rice", "price": 150, "description": "..."}'
# If a field is missing, it becomes null/default

# PATCH — update only a part
curl -X PATCH http://localhost:3000/api/products/101 \
  -H "Content-Type: application/json" \
  -d '{"price": 150}'
# Only price changes, everything else stays the same
```

**Interview question:** "What's the difference between PUT and PATCH?"

**Answer:** "PUT replaces the whole object — if a field is missing, it becomes null. PATCH updates only the fields you send — the rest stay the same. Use PUT when rewriting the whole object, PATCH when updating just a few fields."

### DELETE — Deleting a Resource

```bash
# delete a product
curl -X DELETE http://localhost:3000/api/products/101
```

```javascript
// Client side
await fetch('/api/products/101', { method: 'DELETE' });
```

## REST URL Design — Conventions

```
GET    /products          — all products
GET    /products/:id      — one product
POST   /products          — create a new product
PUT    /products/:id      — replace the whole product
PATCH  /products/:id      — update a few fields
DELETE /products/:id      — delete the product

GET    /products/:id/reviews  — reviews of a product
POST   /products/:id/reviews  — new review on a product
```

**Rules:**
- Use **nouns** (`/products`), not verbs (`/getProducts`)
- Use **plural** (`/products`), not singular (`/product`)
- **Nested** resources for relationships (`/products/:id/reviews`)

## Status Codes — What the Response Means

Every HTTP response has a **status code** — indicating whether the request succeeded.

### 2xx — Success

| Code | Meaning | When |
|---|---|---|
| `200 OK` | Successful request | GET, PUT, PATCH |
| `201 Created` | New resource created | POST |
| `204 No Content` | Successful but no response body | DELETE |

### 3xx — Redirection

| Code | Meaning |
|---|---|
| `301 Moved Permanently` | Resource permanently moved to a new location |
| `304 Not Modified` | Use cache, don't resend |

### 4xx — Client Error (Your Mistake)

| Code | Meaning | When |
|---|---|---|
| `400 Bad Request` | Bad data sent | Invalid JSON, missing fields |
| `401 Unauthorized` | Not authenticated | Not logged in / invalid token |
| `403 Forbidden` | Authenticated but no permission | Non-admin user on admin page |
| `404 Not Found` | Resource not found | Wrong ID, wrong URL |
| `422 Unprocessable Entity` | Data invalid | Validation errors |
| `429 Too Many Requests` | Rate limit hit | Too many requests |

### 5xx — Server Error (Server's Mistake)

| Code | Meaning |
|---|---|
| `500 Internal Server Error` | Server crash / unhandled error |
| `502 Bad Gateway` | No response from upstream server |
| `503 Service Unavailable` | Server down / maintenance |

## 401 vs 403 — Common Confusion

Interview question: "What's the difference between 401 and 403?"

- **401 Unauthorized:** You are **not authenticated** — not logged in, token invalid. "Log in first."
- **403 Forbidden:** You are **authenticated** but don't have **permission** for this resource. "You're logged in but can't access the admin page."

```
401 = "Who are you? Identify yourself first."
403 = "You're identified, but you can't come here."
```

---

## What It Is NOT

⚠️ **REST ≠ only GET/POST.** PUT, PATCH, DELETE are also there. Each HTTP method has its own job.

⚠️ **Status codes ≠ only 200 and 404.** 201 (Created), 401 (Unauthorized), 403 (Forbidden), 500 (Server Error) — all commonly used.

⚠️ **REST ≠ RPC.** REST is resource-based (`/products`), RPC is action-based (`/getProducts`). In REST, verbs are HTTP methods, URLs are nouns.
