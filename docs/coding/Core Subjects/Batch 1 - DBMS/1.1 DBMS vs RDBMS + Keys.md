Data needs a structure to be stored (tables), and the actual data has to be filled into that structure (rows). Defining this structure and managing the data — that's the job of a **DBMS**.

---

# DBMS vs RDBMS + Keys

## What is DBMS

**DBMS** = Database Management System. Any software that stores, retrieves, and manages data.

In simple words — there's data, it needs to be organized, searched, updated. A system does all of this — that's a DBMS.

Real examples: MySQL, PostgreSQL, MongoDB, SQLite, and even Excel is technically a DBMS (structured data store).

## What is RDBMS

**RDBMS** = Relational Database Management System. Stores data in **tables** (rows + columns), and can define **relationships** between tables (via foreign keys).

```sql
-- Products table
CREATE TABLE products (
  product_id SERIAL PRIMARY KEY,
  name VARCHAR(100),
  price DECIMAL(10, 2)
);

-- Orders table — related to products
CREATE TABLE orders (
  order_id SERIAL PRIMARY KEY,
  product_id INTEGER REFERENCES products(product_id),
  quantity INTEGER
);
```

This is the "relationship" — `orders.product_id` actually refers to `products.product_id`. The RDBMS enforces this relationship — you can't insert an invalid `product_id`.

## DBMS vs RDBMS — What's the Difference

| | DBMS | RDBMS |
|---|---|---|
| Data storage | Files, hierarchical, or any format | Tables (rows + columns) |
| Relationships | Must be managed manually | Automatic via foreign keys |
| ACID support | Not required | Yes (consistency guarantee) |
| Data integrity | You ensure it yourself | Database ensures it itself |
| Example | MongoDB, File system | PostgreSQL, MySQL, SQLite |

**Simple:** DBMS = any data management system. RDBMS = a specific type of DBMS where data is in tables and relationships are defined via foreign keys.

In interviews, when asked "difference between DBMS and RDBMS," say directly: "RDBMS is a specific type of DBMS where data is stored in tables and relationships are defined via foreign keys. Plain DBMS doesn't guarantee this."

## Keys — Database Identifiers

Every table needs to uniquely identify its rows. **Keys** are used for this.

### Primary Key

A column in every table that **uniquely identifies each row** — cannot be null, cannot be duplicate.

```sql
CREATE TABLE products (
  product_id SERIAL PRIMARY KEY,  -- this is the Primary Key
  name VARCHAR(100),
  price DECIMAL(10, 2)
);
```

`SERIAL` means the database generates the number itself — 1, 2, 3... Every row gets a unique `product_id`.

### Foreign Key

A column in one table that **references the Primary Key of another table** — creates a relationship.

```sql
CREATE TABLE orders (
  order_id SERIAL PRIMARY KEY,
  product_id INTEGER REFERENCES products(product_id),  -- Foreign Key
  quantity INTEGER
);
```

`REFERENCES products(product_id)` — this line tells the database that the `product_id` column can only contain values that exist in the `products` table. Insert an invalid `product_id` and the database throws an error.

### Composite Key

Sometimes a single column isn't unique — two or more columns together form uniqueness.

```sql
CREATE TABLE order_items (
  order_id INTEGER,
  product_id INTEGER,
  quantity INTEGER,
  PRIMARY KEY (order_id, product_id)  -- Composite Key
);
```

This is useful for junction tables — like "which product is in which order." `order_id` alone isn't unique (one order can have many items), `product_id` alone isn't unique (one product can be in many orders). But together they're unique.

### Candidate Key

Columns that could have been the Primary Key (unique + not null) but weren't. Like `email` could be unique in a `users` table, but you chose `user_id` as the Primary Key.

## DukaanOS Context — Real Schema

Think of your Prisma schema:

```prisma
model Product {
  id        String   @id @default(uuid())
  name      String
  price     Float
  barcode   String   @unique
  orders    OrderItem[]
}

model Order {
  id        String   @id @default(uuid())
  date      DateTime
  items     OrderItem[]
}

model OrderItem {
  id        String   @id @default(uuid())
  orderId   String
  productId String
  quantity  Int
  order     Order    @relation(fields: [orderId], references: [id])
  product   Product  @relation(fields: [productId], references: [id])
}
```

Here:
- `Product.id`, `Order.id`, `OrderItem.id` — these are **Primary Keys**
- `OrderItem.orderId` — **Foreign Key** referencing `Order.id`
- `OrderItem.productId` — **Foreign Key** referencing `Product.id`
- `barcode String @unique` — this is a **Candidate Key** (unique but not the Primary Key)

Prisma understands these relationships automatically — through the `@relation` directive. But in interviews you need to know what's happening underneath.

---

## What It Is NOT

⚠️ **Primary Key ≠ only the `id` column.** Any column that is unique and not null can be a Primary Key. `barcode` could be the Primary Key if you wanted.

⚠️ **Foreign Key can have duplicate values.** Many orders can share the same `product_id`. Only NULL isn't allowed if it's required.

⚠️ **RDBMS ≠ SQL.** RDBMS is a system, SQL is a language. PostgreSQL is an RDBMS, SQL is its language. MongoDB is a DBMS, it doesn't use SQL.

## In Your Own Words

1. What's the difference between DBMS and RDBMS? Why use RDBMS?

<details>
<summary>Sample Answer</summary>

**Answer:** DBMS is any data management system — even a file system. RDBMS is a specific type of DBMS where data is stored in tables and relationships are defined via foreign keys. RDBMS is used because it ensures data integrity — you can't insert invalid data, relationships are maintained automatically, and you get ACID transactions.

</details>

2. If your `orders` table has a `product_id` column that refers to the `product_id` in the `products` table, what is this called and why is it important?

<details>
<summary>Sample Answer</summary>

**Answer:** This is a Foreign Key. It's important because it ensures that `orders` can only contain `product_id` values that exist in the `products` table. If you try to insert an invalid product ID, the database throws an error. This maintains the relationship — data stays consistent.

</details>

3. When should you use a Composite Key? Is it required in every table?

<details>
<summary>Sample Answer</summary>

**Answer:** Use a Composite Key when a single column can't be unique on its own. Like in `order_items` — `order_id` alone isn't unique (one order can have many items), `product_id` alone isn't unique (one product can be in many orders). But together they're unique (a product appears once per order). Not required in every table — as long as a single column is unique, that's enough.

</details>

4. What's the difference between Primary Key and Candidate Key?

<details>
<summary>Sample Answer</summary>

**Answer:** Candidate Keys are columns that are unique and not null — they could have been the Primary Key. Primary Key is the one actually chosen as the unique identifier. Like in a `users` table, both `user_id` and `email` could be unique (candidate keys), but `user_id` was chosen as the Primary Key.

</details>

5. If you add `@unique` on the `barcode` column in the `products` table, what does it do?

<details>
<summary>Sample Answer</summary>

**Answer:** `@unique` ensures no two products can have the same barcode. Inserting a duplicate barcode throws an error. This is a Candidate Key — unique but not the Primary Key (Primary Key is `id`). Practical use: in voice billing, you look up products by barcode, so it must be unique.

</details>
