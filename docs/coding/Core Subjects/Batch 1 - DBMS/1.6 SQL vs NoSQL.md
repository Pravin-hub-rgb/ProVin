Two kinds of databases — **SQL** (PostgreSQL, MySQL) and **NoSQL** (MongoDB, Redis). Each has its place. Structured data → SQL, flexible data → NoSQL.

---

# SQL vs NoSQL

## SQL — Structured, Typed, Rules-Based

**SQL databases** = PostgreSQL, MySQL, SQLite, SQL Server

Data is stored in **tables** — fixed rows and columns. The schema must be defined upfront.

```sql
CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL,  -- fixed type, NOT NULL constraint
  price DECIMAL(10, 2)         -- fixed type
);
-- You can't insert a string where a number is expected
```

**Properties:**
- **Fixed schema** — table structure defined upfront
- **Strong relationships** — tables connected via foreign keys
- **ACID transactions** — consistency guaranteed
- **Complex queries** — JOINs, GROUP BY, subqueries — powerful SQL language
- **Vertical scaling** — more data = more powerful server needed

## NoSQL — Flexible, Schema-less, Scalable

**NoSQL databases** = MongoDB, DynamoDB, Redis, Cassandra

Data is stored in **flexible formats** — documents, key-value pairs, graphs. No schema.

MongoDB document:
```json
{
  "_id": "1",
  "name": "Rice",
  "price": 120,
  "tags": ["organic", "premium"],
  "manufacturer": {
    "name": "ABC Corp",
    "country": "India"
  }
}
```

The next document can have a different structure — no `tags`, no `manufacturer`. Flexible.

**Properties:**
- **Flexible schema** — each document can have a different structure
- **Weak relationships** — no JOINs, embed or reference instead
- **Eventual consistency** — data becomes consistent eventually (not real-time)
- **Simple queries** — no complex JOINs, but fast reads
- **Horizontal scaling** — more data = add more servers (sharding)

---

## Comparison — When Which

| | SQL (PostgreSQL) | NoSQL (MongoDB) |
|---|---|---|
| Structure | Fixed schema (tables, columns) | Flexible schema (documents) |
| Relationships | Strong (JOINs, foreign keys) | Weak (embed or reference) |
| Consistency | ACID — always consistent | Eventual — eventually consistent |
| Query language | SQL — powerful, complex queries | MongoDB query API — simpler |
| Scaling | Vertical (bigger server) | Horizontal (more servers) |
| Best for | Structured data, complex queries | Rapidly changing schema, huge scale |

---

## When to Use SQL

When data is **structured** and relationships are **important**:

- **E-commerce** — clear relationships between products, orders, customers
- **Banking** — transactions, accounts, transfers — ACID required
- **Inventory management** — like DukaanOS — inventory, orders, customers
- **Any CRUD app** — create, read, update, delete with consistency

**Your DukaanOS:** Products, orders, customers — all structured. Relationships exist (order → product, order → customer). So Postgres is the right choice.

## When to Use NoSQL

When data is **flexible** or **schema changes often**:

- **User activity logs** — each event can have a different structure
- **Real-time chat messages** — text, image, video — flexible format
- **Content management** — each article has a different structure (some have video, some have gallery)
- **IoT data** — different types of data from sensors
- **Massive scale** — millions of records, distributed across servers

## JOINs — SQL's Superpower

In SQL you can write complex queries that combine data from multiple tables:

```sql
-- Total order amount per customer
SELECT c.name, SUM(o.amount) as total
FROM customers c
JOIN orders o ON c.id = o.customer_id
GROUP BY c.name
HAVING SUM(o.amount) > 1000;
```

In MongoDB this is hard — you have to do it at the application level:
```javascript
// MongoDB — no JOIN, manually combine
const customers = await db.collection('customers').find().toArray();
const orders = await db.collection('orders').find().toArray();

// Manually match
const result = customers.map(c => ({
  name: c.name,
  total: orders.filter(o => o.customerId === c.id)
    .reduce((sum, o) => sum + o.amount, 0)
}));
```

This is SQL's advantage — complex operations happen at the database level.

---

## Scaling — How It Differs

**SQL (Vertical Scaling):** More data? Upgrade the server — more RAM, more CPU. Single server. Expensive but simple.

**NoSQL (Horizontal Scaling):** More data? Add servers — 10 servers, 100 servers. Split data into pieces (sharding). Cheap but complex.

```
SQL:    [Server 1 — 1TB data]  → upgrade to [Server 1 — 2TB data]

NoSQL:  [Server 1 — 500GB] + [Server 2 — 500GB] + [Server 3 — 500GB]
```

## Interview Answer — Honest Reasoning

Interviewer asks: "Why did you choose Postgres over MongoDB?"

**Honest answer:** "My use case (kirana POS) is structured — clear relationships between inventory, orders, customers. ACID transactions are needed (consistency in sale processing). Complex queries needed (customer-wise totals, product-wise sales). So I chose Postgres."

This shows real reasoning — not a textbook answer. If a startup says "we need real-time chat with millions of users" — MongoDB is right for flexible schema and horizontal scaling.

---

## Hybrid Approach — Use Both

Most applications use both:

- **PostgreSQL** — main business data (users, orders, products)
- **Redis** — caching, session storage, real-time data
- **MongoDB** — logs, analytics, unstructured data

You can do this in DukaanOS too:
```typescript
// PostgreSQL — structured business data
await prisma.product.findMany();

// Redis — caching (fast reads)
const cachedProducts = await redis.get('products');

// Each has its place
```

---

## What It Is NOT

⚠️ **NoSQL ≠ better than SQL.** Each has its place. Structured data with relationships → SQL. Flexible data with scale → NoSQL.

⚠️ **NoSQL ≠ no schema needed.** Schema-less means "schema isn't fixed" — but you still need to validate data at the application level. Don't just insert anything.

⚠️ **SQL ≠ slow.** "SQL is slow, NoSQL is fast" — that's a myth. SQL databases are very fast with proper indexing. The difference is in scaling, not speed.
