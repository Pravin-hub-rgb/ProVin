When two operations happen together — inventory update and sales record creation — both should complete, or neither. Partial execution makes data inconsistent. This is a **Transaction**.

---

# Transactions + ACID

## What is a Transaction

**Transaction** = a group of one or more database operations treated as **one unit**. Either all complete, or none.

Real example — Bank transfer:
```sql
-- Deduct from account A
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
-- Add to account B
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
```

If the first happens (deducted from A) but the second fails (not added to B) — 500 disappears! A transaction prevents this: both steps commit together, or both roll back.

## COMMIT and ROLLBACK

```sql
BEGIN TRANSACTION;  -- start transaction

UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;

-- If both successful:
COMMIT;  -- changes become permanent

-- If an error occurred:
ROLLBACK;  -- all changes undone, as if nothing happened
```

## ACID — 4 Properties

Every transaction follows these 4 properties:

### A — Atomicity

"Either all happen, or none." No partial execution.

```
Transaction: UPDATE inventory + INSERT sales

Case 1: Both successful → COMMIT → data consistent
Case 2: First successful, second fails → ROLLBACK → nothing changed
```

### C — Consistency

Before and after the transaction, the database stays in a **valid state**. Rules/constraints are followed.

```sql
-- Rule: inventory.quantity can never be negative
BEGIN TRANSACTION;
UPDATE inventory SET quantity = quantity - 100 WHERE product_id = 1;
-- If quantity becomes -50 → CONSTRAINT VIOLATION → automatic rollback
COMMIT;
```

The database itself ensures your transaction doesn't corrupt data.

### I — Isolation

Two transactions running **simultaneously** won't **interfere** with each other.

```sql
-- Transaction 1: Reading inventory
BEGIN;
SELECT quantity FROM inventory WHERE product_id = 1;  -- quantity = 10

-- Transaction 2: Updating inventory (in parallel)
BEGIN;
UPDATE inventory SET quantity = 5 WHERE product_id = 1;
-- Not committed yet

-- Transaction 1 reads again
SELECT quantity FROM inventory WHERE product_id = 1;
-- Should it see 10 or 5?
-- Isolation level decides
```

### D — Durability

Once **COMMITTED**, it's **permanent**. Even if the system crashes, data is safe.

```
After COMMIT: data saved to disk
Even if server crashes now: data comes back (via WAL/journaling)
```

---

## Isolation Levels — 4 Types

Interview question: "What are isolation levels?"

### Read Uncommitted

Nothing is prevented — dirty reads possible. Another transaction's **uncommitted data** can be seen.

```
Transaction 1: UPDATE quantity = 5 (not committed yet)
Transaction 2: SELECT quantity → sees 5 (dirty read!)
Transaction 1: ROLLBACK → quantity back to 10
Transaction 2: was working with wrong data
```

### Read Committed

Only **committed data** is visible. Postgres default.

```
Transaction 1: UPDATE quantity = 5 (not committed)
Transaction 2: SELECT quantity → sees 10 (old committed data)
Transaction 1: COMMIT
Transaction 2: SELECT quantity → now sees 5 (new committed data)
```

### Repeatable Read

Within the same transaction, the same query returns the **same result** every time.

```
Transaction 1: SELECT quantity → 10
Transaction 2: UPDATE quantity = 5 + COMMIT
Transaction 1: SELECT quantity → still 10 (repeatable read)
```

### Serializable

Strictest — transactions treated as if running **sequentially**. Slowest but safest.

## Prisma Transactions

```typescript
// Prisma $transaction — atomic operation
await prisma.$transaction([
  prisma.inventory.update({
    where: { productId: "123" },
    data: { quantity: { decrement: 1 } }
  }),
  prisma.sales.create({
    data: { productId: "123", amount: 500 }
  }),
]);
```

Or interactive transaction:
```typescript
await prisma.$transaction(async (tx) => {
  const inventory = await tx.inventory.findUnique({
    where: { productId: "123" }
  });

  if (inventory.quantity < 1) {
    throw new Error("Out of stock");
  }

  await tx.inventory.update({
    where: { productId: "123" },
    data: { quantity: { decrement: 1 } }
  });

  await tx.sales.create({
    data: { productId: "123", amount: 500 }
  });
});
```

In interactive transactions you can write full logic — check, update, create — all in one transaction.

## DukaanOS Context

When a sale happens:
1. Inventory count decreases
2. Sales record created

Both must happen in **one transaction**. If inventory updated but sales record failed — data becomes inconsistent. Inventory shows less but there's no sales record.

```typescript
// DukaanOS sale processing
const processSale = async (productId: string, quantity: number) => {
  await prisma.$transaction(async (tx) => {
    const inventory = await tx.inventory.findUnique({
      where: { productId }
    });

    if (inventory.quantity < quantity) {
      throw new Error("Insufficient stock");
    }

    await tx.inventory.update({
      where: { productId },
      data: { quantity: { decrement: quantity } }
    });

    await tx.sales.create({
      data: { productId, quantity, amount: /* price * quantity */ }
    });
  });
};
```

## What It Is NOT

⚠️ **Transaction ≠ only for bank transfers.** Any data modification where consistency matters should be in a transaction. Inventory update, order processing, user registration — all.

⚠️ **ACID isn't only in SQL databases.** MongoDB also supports ACID transactions (on replica sets). But plain file systems don't have ACID.

⚠️ **Isolation level ≠ always Serializable.** Serializable is safest but slowest. Postgres default is Read Committed — sufficient for most cases.

## In Your Own Words

1. What do `BEGIN`, `COMMIT`, `ROLLBACK` do? Describe a flow.

<details>
<summary>Sample Answer</summary>

**Answer:** `BEGIN` starts the transaction. `COMMIT` makes changes permanent — if everything succeeded. `ROLLBACK` undoes changes — if an error occurred. Flow: BEGIN → operations → (success? COMMIT : ROLLBACK).

</details>

2. What do the 4 letters of ACID stand for? Give a one-liner for each.

<details>
<summary>Sample Answer</summary>

**Answer:** Atomicity — either all or none (no partial execution). Consistency — data stays in valid state after the transaction. Isolation — parallel transactions don't interfere. Durability — once committed, permanent, safe even on crash.

</details>

3. What's the difference between Read Committed and Repeatable Read?

<details>
<summary>Sample Answer</summary>

**Answer:** In Read Committed, only committed data is visible — if another transaction changes and commits, the next read shows new data. In Repeatable Read, the same query in the same transaction returns the same result — even if another transaction changes and commits. Repeatable Read is slower but gives consistent reads.

</details>

4. Write a Prisma `$transaction` example where inventory update and sales record happen together.

<details>
<summary>Sample Answer</summary>

**Answer:**
```typescript
await prisma.$transaction(async (tx) => {
  await tx.inventory.update({
    where: { productId: "123" },
    data: { quantity: { decrement: 1 } }
  });
  await tx.sales.create({
    data: { productId: "123", amount: 500 }
  });
});
```
Both in one transaction — if the inventory update fails, the sales record won't be created either.

</details>

5. What is a dirty read? When does it happen?

<details>
<summary>Sample Answer</summary>

**Answer:** A dirty read happens when one transaction sees another transaction's uncommitted data. Like Transaction 1 sets quantity to 5 but hasn't committed, Transaction 2 reads and sees 5. If Transaction 1 rolls back, quantity returns to 10 — but Transaction 2 already worked with wrong data. This happens at the Read Uncommitted level.

</details>
