React mein `useEffect` cleanup yaad hai? Jab component mount hota hai toh timer start hota hai, aur unmount pe cleanup hota hai. Agar cleanup na ho toh memory leak hoti hai — ya dono ho (start + cleanup), ya koi nahi. Partial state nahi rehni chahiye.

Database mein bhi yahi concept hai — **Transaction**. Jab do operations ek saath hote hain (inventory update + sales record), toh ya dono complete honi chahiye, ya koi nahi. Partial execution data inconsistent kar degi.

# Transactions + ACID

## Transaction Kya Hai

**Transaction** = ek ya zyada database operations ka group jo **ek unit** ke roop mein treat hota hai. Ya toh sab complete honge, ya koi nahi.

```typescript
// TypeScript analogy
async function processSale(orderId: string, productId: string) {
  // Ye dono ek transaction mein hone chahiye
  await prisma.inventory.update({ /* quantity kam karo */ });
  await prisma.sales.create({ /* sales record banao */ });
  // Agar pehla ho gaya but doosra fail ho gaya = DATA INCONSISTENT
}
```

Real example — Bank transfer:
```sql
-- Account A se paisa katna
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
-- Account B mein paisa add karna
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
```

Agar pehla ho gaya (A se kat gaya) but doosra fail ho gaya (B mein add nahi hua) — 500 gayab! Transaction isse rokta hai: dono steps ek saath commit hote hain, ya dono rollback ho jaate hain.

## COMMIT aur ROLLBACK

```sql
BEGIN TRANSACTION;  -- transaction shuru

UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;

-- Agar dono successful:
COMMIT;  -- changes permanent ho jaayenge

-- Agar koi error aaya:
ROLLBACK;  -- sab changes undo ho jaayenge, jaise kuch hua hi nahi
```

TypeScript mein:
```typescript
try {
  await prisma.$transaction([
    prisma.inventory.update({ /* ... */ }),
    prisma.sales.create({ /* ... */ }),
  ]);
  // Dono successful — auto-commit
} catch (error) {
  // Koi error — auto-rollback, kuch change nahi hua
}
```

Prisma `$transaction` automatically ye handle karta hai — try-catch mein success toh commit, error toh rollback.

## ACID — 4 Properties

Har transaction ye 4 properties follow karta hai:

### A — Atomicity

"Ya toh sab ho, ya koi nahi." Partial execution nahi hoga.

```
Transaction: UPDATE inventory + INSERT sales

Case 1: Dono successful → COMMIT → data consistent
Case 2: Pehla successful, doosra fail → ROLLBACK → kuch change nahi
```

TypeScript analogy: `Promise.all()` — ya dono resolve ho, ya reject ho. Partial resolve nahi hota.

### C — Consistency

Transaction ke pehle aur baad database **valid state** mein rahega. Rules/constraints follow honge.

```sql
-- Rule: inventory.quantity kabhi negative nahi ho sakta
BEGIN TRANSACTION;
UPDATE inventory SET quantity = quantity - 100 WHERE product_id = 1;
-- Agar quantity -50 ho raha hai → CONSTRAINT VIOLATION → automatic rollback
COMMIT;
```

Database khud ensure karta hai ki tumhara transaction data ko corrupt nahi kare.

### I — Isolation

Do transactions **simultaneously** chal rahe hon toh ek doosre ko **interfere nahi karenge**.

```sql
-- Transaction 1: Read kar raha hai inventory
BEGIN;
SELECT quantity FROM inventory WHERE product_id = 1;  -- quantity = 10

-- Transaction 2: Update kar raha hai inventory (parallel mein)
BEGIN;
UPDATE inventory SET quantity = 5 WHERE product_id = 1;
-- Abhi commit nahi hua

-- Transaction 1 wapas read karta hai
SELECT quantity FROM inventory WHERE product_id = 1;
-- Quantity kitna dikhna chahiye? 10 ya 5?
-- Isolation level decide karta hai
```

### D — Durability

Ek baar **COMMIT** ho gaya toh **permanent** hai. System crash ho bhi jaaye toh data safe rahega.

```
COMMIT karne ke baad: data disk pe save ho chuka hai
Agar abhi server crash ho jaaye bhi: data wapas aa jayega (WAL/ journaling se)
```

TypeScript analogy: `localStorage.setItem()` — ek baar set ho gaya toh browser band hone ke baad bhi data hai.

---

## Isolation Levels — 4 Types

Interview mein poochte hain: "Isolation levels kya hain?"

### Read Uncommitted

Kuch nahi rokta — dirty reads possible hain. Dusre transaction ka **uncommitted data** bhi dikh sakta hai.

```
Transaction 1: UPDATE quantity = 5 (abhi commit nahi kiya)
Transaction 2: SELECT quantity → 5 dekh raha hai (dirty read!)
Transaction 1: ROLLBACK → quantity wapas 10
Transaction 2: galat data pe kaam kar raha tha
```

### Read Committed

Sirf **committed data** dikhega. Postgres ka default level.

```
Transaction 1: UPDATE quantity = 5 (commit nahi kiya)
Transaction 2: SELECT quantity → 10 dekhega (purana committed data)
Transaction 1: COMMIT
Transaction 2: SELECT quantity → 5 ab dikhega (naya committed data)
```

### Repeatable Read

Same transaction ke andar same query baar-baar chalao toh **same result** milega.

```
Transaction 1: SELECT quantity → 10
Transaction 2: UPDATE quantity = 5 + COMMIT
Transaction 1: SELECT quantity → phir 10 milega (repeatable read)
```

### Serializable

Sabse strict — transactions bilkul **sequentially** chal rahe hain jaise treat hote hain. Slowest but safest.

await prisma.$transaction(async (tx) => {

Interactive transaction mein tum pura logic likh sakte ho — check karo, update karo, create karo — sab ek transaction mein.

## DukaanOS Context

Jab ek sale hoti hai:
1. Inventory count kam hona
2. Sales record create hona

Ye dono **ek transaction** mein hone chahiye. Agar inventory update ho gaya but sales record fail ho gaya — data inconsistent ho jayega. Tumhara inventory kam dikhega but sales record nahi hoga.

```typescript
// DukaanOS sale processing
const processSale = async (productId: string, quantity: number) => {
  await prisma.$transaction(async (tx) => {
    // Step 1: Inventory check + update
    const inventory = await tx.inventory.findUnique({
      where: { productId }
    });

    if (inventory.quantity < quantity) {
      throw new Error("Insufficient stock");
    }

    await tx.inventory.update({
      where: { productId },
      data: { quantity: { decrement: quantity } }
    });

    // Step 2: Sales record
    await tx.sales.create({
      data: { productId, quantity, amount: /* price * quantity */ }
    });
  });
};
```

## What It Is NOT

⚠️ **Transaction = sirf bank transfers ke liye nahi.** Har data modification jisme consistency important hai — wo transaction mein honi chahiye. Inventory update, order processing, user registration — sab.

⚠️ **ACID sirf SQL databases mein nahi.** MongoDB bhi ACID transactions support karta hai (replica sets pe). But plain file system mein ACID nahi hota.

⚠️ **Isolation level = hamesha Serializable nahi.** Serializable sabse safe hai but sabse slow hai. Postgres ka default Read Committed hai — zyada tar cases mein kaafi hai.

## In Your Own Words

1. Transaction `BEGIN`, `COMMIT`, `ROLLBACK` kya karte hain? Ek flow batao.

<details>
<summary>Sample Jawab</summary>

**Jawab:** `BEGIN` transaction shuru karta hai. `COMMIT` changes permanent karta hai — agar sab successful ho. `ROLLBACK` changes undo karta hai — agar koi error aaya. Flow: BEGIN → operations → (success? COMMIT : ROLLBACK). Jaise try-catch: try = BEGIN + operations, success = COMMIT, catch = ROLLBACK.

</details>

2. ACID ke 4 letters kya kehte hain? Har ek ka one-liner do.

<details>
<summary>Sample Jawab</summary>

**Jawab:** Atomicity — ya toh sab ho ya koi nahi (partial execution nahi). Consistency — transaction ke baad data valid state mein rahe. Isolation — parallel transactions interfere nahi karenge. Durability — commit ho gaya toh permanent hai, crash mein bhi safe.

</details>

3. React `useEffect` cleanup aur database transaction mein kya similarity hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Dono "ya toh dono ho ya koi nahi" pattern follow karte hain. `useEffect` mein mount + unmount dono honi chahiye — agar cleanup na ho toh memory leak. Transaction mein inventory update + sales record dono honi chahiye — agar ek ho aur doosra na ho toh data inconsistency.

</details>

5. Read Committed aur Repeatable Read mein kya fark hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Read Committed mein sirf committed data dikhta hai — agar doosra transaction change kare aur commit kare, toh next read mein naya data milega. Repeatable Read mein same transaction ke andar same query baar-baar same result deti hai — chahe doosra transaction change kar de aur commit kar de. Repeatable Read slow hai but consistent read deta hai.

</details>
