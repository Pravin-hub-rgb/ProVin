# Indexing

## The Problem — Full Table Scan

Imagine you have 1,00,000 products and wrote this query:

```sql
SELECT * FROM products WHERE barcode = '8901234567890';
```

Without an index, the database checks every product — "is this the barcode? No. Next." — 1,00,000 times until a match is found.

## The Solution — Index

An index is a data structure (mostly **B-Tree**) that gives fast lookups on specific columns. Like a phone book — names sorted alphabetically, so finding "Sharma" is fast because you jump straight to the S section.

```sql
CREATE INDEX idx_barcode ON products(barcode);
```

Now the database maintains a separate data structure where `barcode` is sorted. When you write `WHERE barcode = '...'`, the database jumps straight into the index — O(log n) or O(1) instead of O(n).

---

## When to Add an Index

Columns that appear **frequently** in queries — in `WHERE`, `JOIN`, or `ORDER BY`:

```sql
-- index these columns
SELECT * FROM products WHERE barcode = '...';      -- WHERE
SELECT * FROM orders WHERE customer_id = 5;         -- WHERE + JOIN
SELECT * FROM products ORDER BY name;               -- ORDER BY
```

**Always index foreign keys:**
```sql
-- customer_id is a foreign key in orders table
CREATE INDEX idx_orders_customer ON orders(customer_id);
```

Because you always run queries like `orders WHERE customer_id = ?` — to find a customer's orders.

## When NOT to Add (asked in interviews, shows understanding)

**1. Small tables (up to 100 rows):**
```sql
-- Index on a 50-row table? No benefit.
-- Database has to update the index on every INSERT/UPDATE
-- Full scan is fast on a small table anyway
```

**2. Frequently updated columns:**
```sql
-- "status" column that changes every minute
-- With index: index rebuilds on every INSERT/UPDATE
-- Write speed becomes slow
```

**3. Low-cardinality columns:**
```sql
-- "gender" column — only 2 values (M/F)
-- Indexing doesn't help — half the table is that value anyway
```

---

## The Trade-Off — Read vs Write

This is the most important concept in indexing:

| | Read (SELECT) | Write (INSERT/UPDATE/DELETE) |
|---|---|---|
| **Without index** | Slow — full scan | Fast — just write data |
| **With index** | Fast — direct jump | Slow — index also needs updating |

**Rule of thumb:** If a table is read-heavy (like products — queried frequently), add an index. If it's write-heavy (like logs — only inserts, rarely queried), keep indexes minimal.

## Index in Prisma

Use the `@index` directive in the Prisma schema:

```prisma
model Product {
  id      String  @id @default(uuid())
  name    String
  barcode String  @unique  // unique = index created automatically
  price   Float

  @@index([name])  // index on name
}
```

`@unique` automatically creates a unique index — that's why lookups on `barcode` are fast.

Using `@@index`:
```prisma
model Order {
  id         String   @id @default(uuid())
  customerId String
  amount     Float
  createdAt  DateTime

  @@index([customerId])  // index on customerId
  @@index([createdAt])   // index on createdAt — for date range queries
}
```

Run the migration: `npx prisma migrate dev` — the index gets created in the database.

## B-Tree — How It Works Inside

Deep interview question: "What is a B-Tree index?"

**Simple answer:** A B-Tree is a sorted data structure. Like a binary tree but each node has multiple children. Data is sorted — so range queries (`WHERE price > 100 AND price < 500`) are also fast.

```
        [50]
       /    \
    [25]    [75]
   /   \   /   \
 [10] [30][60] [90]
```

If you need `WHERE id = 30` — at root 30 < 50, go left. At 25, 30 > 25, go right. Found 30. 3 steps instead of scanning 1,00,000 rows.

---

## Composite Index — Multiple Columns

```sql
CREATE INDEX idx_customer_date ON orders(customer_id, created_at);
```

This index is useful when you query both columns together:
```sql
SELECT * FROM orders WHERE customer_id = 5 AND created_at > '2024-01-01';
```

But if you query only on `created_at` without `customer_id`, this index won't work. **Order matters** — first `customer_id`, then `created_at`.

---

## What It Is NOT

⚠️ **Index ≠ only Primary Key.** Primary Key is automatically indexed, but you can add indexes on extra columns too.

⚠️ **More indexes ≠ always better.** Every index slows down writes. 10 indexes means every INSERT updates 10 indexes.

⚠️ **Index ≠ magic.** If your query is `WHERE name LIKE '%sharma%'` (wildcard at the start), the index won't work. Wildcard at the end (`'sharma%'`) works.

4. What does the Prisma `@@index` directive do?

<details>
<summary>Sample Answer</summary>

**Answer:** `@@index([columnName])` creates an index on that column in the Prisma schema. After running the migration, an actual index is created in the database. `@unique` automatically creates a unique index. This speeds up read queries when you use `WHERE` on that column.

</details>

5. If you create `CREATE INDEX idx ON orders(customer_id, created_at)`, will this index work for `WHERE created_at > '2024-01-01'` without `customer_id`?

<details>
<summary>Sample Answer</summary>

**Answer:** No, it won't work. In a composite index, order matters — first `customer_id`, then `created_at`. If you query only on `created_at` without `customer_id`, the index is ignored. You'd need a separate `@@index([created_at])` if you want to query by date alone.

</details>
