# Indexing

## Problem — Full Table Scan

Socho tumhare paas 1,00,000 products hain aur tumne ye query likha:

```sql
SELECT * FROM products WHERE barcode = '8901234567890';
```

Bina index ke database kya karega? Har ek product check karega — "kya ye barcode hai? Nahi. Agla." 1,00,000 baar check karega jab tak match na mil jaaye.

## Solution — Index

Index ek data structure hai (mostly **B-Tree**) jo specific columns pe fast lookup deta hai. Jaise phone book names alphabetically sorted hai — "Sharma" dhundhna fast hai kyunki S section mein seedha ja sakte ho.

```sql
CREATE INDEX idx_barcode ON products(barcode);
```

Ab database ek alag data structure maintain karta hai jisme `barcode` sorted hai. Jab tum `WHERE barcode = '...'` likhte ho, database seedha index mein jump karta hai — O(log n) ya O(1) instead of O(n).

---

## Kab Lagao Index

Columns jo **baar-baar** query mein aate hain — `WHERE`, `JOIN`, ya `ORDER BY` mein:

```sql
-- ye column pe index lagao
SELECT * FROM products WHERE barcode = '...';      -- WHERE
SELECT * FROM orders WHERE customer_id = 5;         -- WHERE + JOIN
SELECT * FROM products ORDER BY name;               -- ORDER BY
```

**Foreign keys pe hamesha index lagao:**
```sql
-- orders table mein customer_id foreign key hai
CREATE INDEX idx_orders_customer ON orders(customer_id);
```

Kyunki tum hamesha `orders WHERE customer_id = ?` type queries likhte ho — customer ke orders dhundhne ke liye.

## Kab NAHI Lagao

Ye interview mein bhi poochte hain — samajhdaari dikhata hai:

**1. Chhoti tables pe (100 rows tak):**
```sql
-- 50 rows wali table pe index? Fayda nahi.
-- Database ko har INSERT/UPDATE pe index bhi update karna padta hai
-- Chhoti table pe full scan bhi fast hai
```

**2. Baar-baar update hone wale columns:**
```sql
-- "status" column jo har minute change hota hai
-- Index lagao = har INSERT/UPDATE pe index rebuild
-- Write speed slow ho jaayegi
```

**3. Low-cardinality columns:**
```sql
-- "gender" column — sirf 2 values (M/F)
-- Index lagake fayda nahi — half table toh wahi hai
```

---

## Trade-Off — Read vs Write

Ye sabse important concept hai indexing mein:

| | Read (SELECT) | Write (INSERT/UPDATE/DELETE) |
|---|---|---|
| **Bina index** | Slow — full scan | Fast — sirf data write |
| **Index ke saath** | Fast — direct jump | Slow — index bhi update karna padta hai |

**Rule of thumb:** Agar table read-heavy hai (jaise products table — baar-baar query hoti hai), index lagao. Agar write-heavy hai (jaise logs table — sirf insert hota hai, rarely query), toh index kam karo.

## Prisma Mein Index

Prisma schema mein `@index` directive lagao:

```prisma
model Product {
  id      String  @id @default(uuid())
  name    String
  barcode String  @unique  // unique = automatically index ban jaata hai
  price   Float

  @@index([name])  // name pe index
}
```

`@unique` automatically ek unique index banata hai — isliye `barcode` pe lookup fast hai.

Agar tum `@@index` use karte ho:
```prisma
model Order {
  id         String   @id @default(uuid())
  customerId String
  amount     Float
  createdAt  DateTime

  @@index([customerId])  // customerId pe index
  @@index([createdAt])   // createdAt pe index — date range queries ke liye
}
```

Migration run karo: `npx prisma migrate dev` — database mein index ban jaayega.

## B-Tree — Andar Kaise Kaam Karta Hai

Deep interview question: "Index B-Tree kya hai?"

**Simple answer:** B-Tree ek sorted data structure hai. Jaise binary tree hota hai but har node ke multiple children hote hain. Data sorted hota hai — isliye range queries (`WHERE price > 100 AND price < 500`) bhi fast hain.

```
        [50]
       /    \
    [25]    [75]
   /   \   /   \
 [10] [30][60] [90]
```

Agar tumhe `WHERE id = 30` dhundhna hai — root pe 30 < 50, left jao. 25 pe 30 > 25, right jao. 30 mila. 3 steps instead of 1,00,000 rows scan.

---

## Composite Index — Multiple Columns

```sql
CREATE INDEX idx_customer_date ON orders(customer_id, created_at);
```

Ye index tab useful hai jab tum dono columns ko saath mein query karo:
```sql
SELECT * FROM orders WHERE customer_id = 5 AND created_at > '2024-01-01';
```

But agar sirf `created_at` pe query karo bina `customer_id` ke, toh ye index kaam nahi karega. **Order matters** — pehle `customer_id`, phir `created_at`.

---

## What It Is NOT

⚠️ **Index = sirf Primary Key nahi.** Primary Key automatically index hota hai, but tum extra columns pe bhi index laga sakte ho.

⚠️ **Zyada indexes = hamesha better nahi.** Har index write speed slow karta hai. 10 indexes lagao toh har INSERT 10 baar index update karega.

⚠️ **Index = magic nahi hai.** Agar tumhara query `WHERE name LIKE '%sharma%'` hai (wildcard at start), toh index kaam nahi karega. Wildcard at end (`'sharma%'`) chalega.

## In Your Own Words

1. Bina index ke full table scan kya hota hai? Kitna slow ho sakta hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Bina index ke database har row check karta hai jab tak match na mil jaaye — O(n) time. 1 lakh rows hain toh 1 lakh baar check karega. Index ke saath seedha jump hota hai — O(log n) ya O(1). 100x tak fast ho sakta hai.

</details>

2. Agar tumhare `orders` table mein 1,00,000 rows hain aur tum `WHERE customer_id = 5` query daily 100 baar chalate ho — kya karna chahiye?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `customer_id` pe index lagana chahiye. Bina index ke 1,00,000 rows scan hongi har baar. Index ke saath seedha customer ke orders mil jayenge. Write speed thodi slow hogi (kyunki har INSERT pe index update hoga), but read 100x fast ho jaayegi.

</details>

3. Index kab nahi lagana chahiye? Teen situations batao.

<details>
<summary>Sample Jawab</summary>

**Jawab:** (1) Chhoti tables pe (100 rows tak) — full scan bhi fast hai. (2) Baar-baar update hone wale columns pe — har INSERT/UPDATE pe index rebuild hota hai. (3) Low-cardinality columns pe (jaise gender — sirf 2 values) — index lagake fayda nahi.

</details>

4. Prisma `@@index` directive kya karta hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `@@index([columnName])` Prisma schema mein ek index create karta hai us column pe. Migration run karne ke baad database mein actual index ban jaata hai. `@unique` automatically unique index banata hai. Ye read queries ko fast banata hai jab tum us column pe `WHERE` lagate ho.

</details>

5. Agar tum `CREATE INDEX idx ON orders(customer_id, created_at)` lagao, toh ye index `WHERE created_at > '2024-01-01'` query pe kaam karega bina `customer_id` ke?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Nahi, kaam nahi karega. Composite index mein order matters — pehle `customer_id`, phir `created_at`. Agar sirf `created_at` pe query karo bina `customer_id` ke, toh index ignore hoga. Tumhe alag se `@@index([created_at])` lagana padega agar sirf date pe query karni hai.

</details>
