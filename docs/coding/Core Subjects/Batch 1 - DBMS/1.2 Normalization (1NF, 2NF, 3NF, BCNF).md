TypeScript mein tum `interface` define karte ho — `Product { id: string; name: string; price: number }`. Ab socho agar tumne ye kiya:

```typescript
interface OrderItem {
  orderId: string;
  productName: string;    // product ka naam directly order mein
  productPrice: number;   // product ka price directly order mein
  quantity: number;
}
```

Ye galat kyun hai? Kyunki jab product ka price change hoga, tumhe har `OrderItem` mein jaake update karna padega. Agar 1000 orders hain toh 1000 jagah price change karna padega. Ek miss ho gaya — data inconsistent ho gaya.

Isko **data redundancy** kehte hain. Normalization isse rokta hai.

---

# Normalization

## Duplication Kyun Kharab Hai

Socho tumhare `orders` table mein ye data hai:

| orderId | customerName | customerPhone | productName | productPrice |
|---|---|---|---|---|
| 1 | Rahul | 9876543210 | Rice | 120 |
| 2 | Rahul | 9876543210 | Oil | 250 |
| 3 | Priya | 9998887776 | Rice | 120 |

Problem dekho — "Rahul" aur "9876543210" **do baar repeat** ho raha hai. Agar Rahul ka phone number change ho gaya, toh dono jagah update karna padega. Ek miss ho gaya — Rahul ke ek order ka wrong number ho jayega.

TypeScript mein socho — agar tumne ek object ki property 5 jagah copy kar rakhi ho, aur ek jagah change karo baaki mein nahi — inconsistency. Database mein bhi yahi hota hai.

**Normalization** = data duplication khatam karna, aur related data ko alag tables mein rakhna.

---

## 1NF (First Normal Form)

**Rule:** Har column mein **atomic** (single, indivisible) value honi chahiye. Repeating groups nahi hone chahiye.

```typescript
// ❌ BAD — comma-separated values (repeating group)
interface Customer {
  id: string;
  name: string;
  phoneNumbers: string; // "9876543210, 9998887776" — ye atomic nahi hai
}

// ✅ GOOD — alag table banao
interface Customer {
  id: string;
  name: string;
}

interface CustomerPhone {
  customerId: string;
  phone: string; // ek row ek number
}
```

Database mein:
```sql
-- ❌ BAD
CREATE TABLE customers (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100),
  phone_numbers TEXT  -- "9876543210, 9998887776" — comma separated
);

-- ✅ GOOD
CREATE TABLE customers (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100)
);

CREATE TABLE customer_phones (
  customer_id INTEGER REFERENCES customers(id),
  phone VARCHAR(15)  -- ek row ek phone number
);
```

**Real example:** Agar `products` table mein `tags` column hai jisme `"organic, premium, bulk"` comma-separated hai — ye 1NF violate ho raha hai. Fix: alag `product_tags` table banao.

---

## 2NF (Second Normal Form)

**Rule:** Pehle 1NF follow hona chahiye. Phir **partial dependency** nahi honi chahiye — matlab agar composite primary key hai, toh har non-key column **poore** composite key pe depend kare, sirf ek part pe nahi.

TypeScript mein samjho:

```typescript
// ❌ BAD — partial dependency
interface OrderItem {
  orderId: string;      // composite key ka part
  productId: string;    // composite key ka part
  productName: string;  // sirf productId pe depend karta hai, orderId pe nahi
  quantity: number;     // dono pe depend karta hai
}
```

`productName` sirf `productId` se aa raha hai — `orderId` se koi matlab nahi. Ye partial dependency hai.

Fix:
```typescript
// ✅ GOOD — alag tables mein
interface OrderItem {
  orderId: string;    // composite key
  productId: string;  // composite key
  quantity: number;   // dono pe depend karta hai
}

interface Product {
  id: string;         // sirf ye chahiye productName ke liye
  name: string;
}
```

Database mein:
```sql
-- ❌ BAD
CREATE TABLE order_items (
  order_id INTEGER,
  product_id INTEGER,
  product_name VARCHAR(100),  -- sirf product_id pe depend karta hai
  quantity INTEGER,
  PRIMARY KEY (order_id, product_id)
);

-- ✅ GOOD
CREATE TABLE order_items (
  order_id INTEGER,
  product_id INTEGER,
  quantity INTEGER,
  PRIMARY KEY (order_id, product_id)
);

CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100)
);
```

---

## 3NF (Third Normal Form)

**Rule:** Pehle 2NF follow hona chahiye. Phir **transitive dependency** nahi honi chahiye — non-key column, non-key column pe depend nahi karni chahiye.

```typescript
// ❌ BAD — transitive dependency
interface Order {
  id: string;
  customerId: string;
  customerCity: string;    // customerId → customerCity (transitive)
  customerPincode: string; // customerId → customerPincode, aur customerCity ye depend karta hai
}
```

Yahan `customerCity` actually `customerPincode` pe depend karta hai (pincode se city aati hai). Dono `customerId` se indirectly aa rahe hain — ye transitive hai.

Fix:
```typescript
// ✅ GOOD
interface Order {
  id: string;
  customerId: string;
}

interface Customer {
  id: string;
  city: string;
  pincode: string;
}
```

**Simple rule:** Agar tumhe laga ki "ye column toh uss column se aa raha hai, jo ki uss column se aa raha hai" — ye transitive hai. Alag table banao.

---

## BCNF (Boyce-Codd Normal Form)

3NF ka stricter version. Jab table mein **multiple overlapping candidate keys** hon, tab edge cases handle karta hai.

Interview mein sirf itna batao: "BCNF 3NF se strict hai — jab table mein multiple unique key combinations ho, tab BCNF extra constraints enforce karta hai. Real-world applications mein 3NF mostly kaafi hai."

Deep dive zaroori nahi full-stack role ke liye.

---

## Denormalization — Kab Ulta Karo

Normalization data duplication khatam karta hai. But kabhi kabhi **intentionally thoda duplication** rakhte hain — **read performance** ke liye.

```typescript
// Normalized: har baar JOIN karna padega
interface Order {
  id: string;
  customerId: string; // customer ka naam lene ke liye customers table se JOIN
}

// Denormalized: customer naam directly hai (duplication)
interface Order {
  id: string;
  customerId: string;
  customerName: string; // duplication hai, but read fast hai
}
```

**Kab denormalize karo:**
- Analytics dashboards — har baar 5 tables JOIN karna expensive hai
- Read-heavy applications — write thoda slow ho but read fast ho
- Caching layers — data ek jagah pre-computed rakho

**Interview answer:** "Denormalization tab karte hain jab read performance critical ho aur joins bahut expensive ho rahe hon. Trade-off hai: read fast, write/update thoda complex."

---

## Practical Exercise — Apna Schema Check Karo

Apna DukaanOS Prisma schema kholo aur khud se pucho:

1. Kya koi table mein repeated data hai? (Same customer name baar-baar?)
2. Kya koi column dusre column se derive ho raha hai? (Total price = quantity × price?)
3. Kya composite key ke saath koi non-key column sirf ek part pe depend kar raha hai?

Agar kahin bhi "haan" hai — wo normalization violation hai.

---

## What It Is NOT

⚠️ **Normalization = sirf tables ko todna nahi.** Normalization ka matlab hai data consistency maintain karna. Tables todna toh sirf ek step hai.

⚠️ **Zyada normalization = hamesha better nahi.** Har join ek query slow karta hai. Kabhi kabhi denormalization zaroori hai performance ke liye.

⚠️ **1NF, 2NF, 3NF sirf interview ke liye nahi.** Ye concepts real mein use hote hain — jab tum schema design karte ho tab ye sochhte ho ki "kya ye column yahan hona chahiye ya alag table mein?"

## In Your Own Words

1. Agar tumhare `orders` table mein `customer_name` aur `customer_phone` seedha hain (customer table ke bina), toh ye kaunsa normalization violation hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Ye 3NF violation hai — transitive dependency hai. `customer_name` aur `customer_phone` actually `customer_id` pe depend karte hain. Fix: alag `customers` table banao aur `orders` mein sirf `customer_id` foreign key rakho.

</details>

2. 1NF ka simple rule kya hai? Ek example do jo 1NF violate kare.

<details>
<summary>Sample Jawab</summary>

**Jawab:** 1NF ka rule: har column mein atomic value honi chahiye, repeating groups nahi. Example: `tags` column mein `"organic, premium, bulk"` comma-separated hai — ye 1NF violate hai. Fix: alag `product_tags` table banao, har tag ke liye ek row.

</details>

3. Denormalization kab karte hain? Normalization ke baad ulta kyun karte hain?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Denormalization tab karte hain jab read performance critical ho. Agar tumhara dashboard har second 5 tables se data JOIN karke laata hai toh slow hoga. Intentionally thoda duplication rakh ke read fast kar sakte ho. Trade-off: write/update thoda complex ho jaata hai but read fast hota hai.

</details>

4. Agar `order_items` table mein composite key `(order_id, product_id)` hai aur tumne `product_name` column bhi rakha hai — ye kaunsi normalization form violate kar raha hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Ye 2NF violation hai — partial dependency. `product_name` sirf `product_id` pe depend karta hai, `order_id` se koi matlab nahi. Composite key ke sirf ek part pe depend kar raha hai. Fix: `product_name` ko `products` table mein rakho, `order_items` mein sirf `product_id` foreign key rakho.

</details>

5. TypeScript `interface` mein agar tumne ek property ko `any` type di hai — ye normalization se kaise relate hota hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `any` type ka matlab hai koi structure nahi — ye database ke "unstructured data" jaisa hai (NoSQL). Normalized interface (`Product { id: string; name: string }`) structured hai — jaise RDBMS table. `any` use karna flexibility deta hai but type safety chali jaati hai. Database mein bhi: NoSQL flexible hai but consistency guarantees nahi hain, SQL structured hai with consistency.

</details>
