Data duplication is bad. If your `orders` table repeats the customer's name — when Rahul's phone number changes, you have to update it everywhere. Miss one — data becomes inconsistent.

**Normalization** = eliminating data duplication, and keeping related data in separate tables.

---

# Normalization

## Why Duplication is Bad

Imagine your `orders` table has this data:

| orderId | customerName | customerPhone | productName | productPrice |
|---|---|---|---|---|
| 1 | Rahul | 9876543210 | Rice | 120 |
| 2 | Rahul | 9876543210 | Oil | 250 |
| 3 | Priya | 9998887776 | Rice | 120 |

Problem: "Rahul" and "9876543210" are **repeated twice**. If Rahul's phone number changes, both places need updating. Miss one — one of Rahul's orders has the wrong number.

---

## 1NF (First Normal Form)

**Rule:** Every column must hold **atomic** (single, indivisible) values. No repeating groups.

```sql
-- ❌ BAD
CREATE TABLE customers (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100),
  phone_numbers TEXT  -- "9876543210, 9998887776" — comma separated
);

-- ✅ GOOD
CREATE TABLE customers (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100)
);

CREATE TABLE customer_phones (
  customer_id INTEGER REFERENCES customers(id),
  phone VARCHAR(15)  -- one row per number
);
```

**Real example:** If a `products` table has a `tags` column with `"organic, premium, bulk"` comma-separated — that violates 1NF. Fix: create a separate `product_tags` table.

---

## 2NF (Second Normal Form)

**Rule:** First, follow 1NF. Then **no partial dependency** — if there's a composite primary key, every non-key column must depend on the **entire** composite key, not just one part.

```sql
-- ❌ BAD — partial dependency
CREATE TABLE order_items (
  order_id INTEGER,
  product_id INTEGER,
  product_name VARCHAR(100),  -- depends only on product_id
  quantity INTEGER,
  PRIMARY KEY (order_id, product_id)
);
```

`product_name` comes only from `product_id` — `order_id` is irrelevant. That's a partial dependency.

Fix:
```sql
-- ✅ GOOD
CREATE TABLE order_items (
  order_id INTEGER,
  product_id INTEGER,
  quantity INTEGER,   -- depends on both
  PRIMARY KEY (order_id, product_id)
);

CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100)
);
```

---

## 3NF (Third Normal Form)

**Rule:** First, follow 2NF. Then **no transitive dependency** — a non-key column must not depend on another non-key column.

```sql
-- ❌ BAD — transitive dependency
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  customer_id INTEGER,
  customer_city VARCHAR(100),    -- customer_id → customer_city (transitive)
  customer_pincode VARCHAR(10)   -- customer_id → customer_pincode
);
```

Here `customer_city` actually depends on `customer_pincode` (city comes from pincode). Both reach `customer_id` indirectly — that's transitive.

Fix:
```sql
-- ✅ GOOD
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  customer_id INTEGER
);

CREATE TABLE customers (
  id SERIAL PRIMARY KEY,
  city VARCHAR(100),
  pincode VARCHAR(10)
);
```

**Simple rule:** If you feel "this column comes from that column, which comes from that other column" — that's transitive. Create a separate table.

---

## BCNF (Boyce-Codd Normal Form)

Stricter version of 3NF. Handles edge cases when a table has **multiple overlapping candidate keys**.

In interviews, just say: "BCNF is stricter than 3NF — when a table has multiple unique key combinations, BCNF enforces extra constraints. In real-world applications, 3NF is usually enough."

Deep dive isn't needed for full-stack roles.

---

## Denormalization — When to Reverse

Normalization eliminates data duplication. But sometimes you **intentionally keep some duplication** — for **read performance**.

```sql
-- Normalized: JOIN every time
SELECT o.id, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.id;

-- Denormalized: customer name is right there (duplication)
SELECT id, customer_name FROM orders;
```

**When to denormalize:**
- Analytics dashboards — JOINing 5 tables every time is expensive
- Read-heavy applications — writes slightly slower but reads fast
- Caching layers — pre-computed data in one place

**Interview answer:** "Denormalization is done when read performance is critical and joins are getting too expensive. Trade-off: fast reads, slightly complex writes/updates."

## Practical Exercise — Check Your Schema

Open your DukaanOS Prisma schema and ask yourself:

1. Is there any repeated data in any table? (Same customer name over and over?)
2. Is any column derived from another column? (Total price = quantity × price?)
3. With a composite key, is any non-key column depending on only one part?

If "yes" anywhere — that's a normalization violation.

---

## What It Is NOT

⚠️ **Normalization ≠ just splitting tables.** Normalization means maintaining data consistency. Splitting tables is just one step.

⚠️ **More normalization ≠ always better.** Every JOIN slows down a query. Sometimes denormalization is necessary for performance.

⚠️ **1NF, 2NF, 3NF aren't just for interviews.** These concepts are used in real life — when designing a schema, you think "should this column be here or in a separate table?"
