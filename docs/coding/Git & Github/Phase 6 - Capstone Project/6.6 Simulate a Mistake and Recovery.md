Real teams make mistakes. The professional skill isn't avoiding mistakes — it's handling them cleanly when they happen. In this step, you'll deliberately introduce a bug, merge it, then revert it properly.

**Step 1: Introduce a deliberate bug**

On dev-A's machine:

```bash
git switch main
git pull origin main
git switch -c feature/deliberate-bug
```

Make a small, obvious bug. For example, set the wrong background color:

```css
/* in style.css */
body { background: red; }
```

Or make the hero text say something broken:

```html
<h1>UNDER CONSTRUCTION — SITE BROKEN</h1>
```

Something clearly wrong that you'd never actually ship. Commit and push:

```bash
git add index.html
git commit -m "Update hero text (temporary)"
git push -u origin feature/deliberate-bug
```

Open a PR. As dev-B, "miss" the bug during review (or intentionally approve it — yes, this simulates a failed review). Merge.

**Step 2: Realize the mistake**

Now main is broken. The site shows wrong text or a red background. In real life, this is when someone might panic. Instead, you handle it calmly.

**Step 3: Revert the merge**

Go to the merged PR on GitHub. Scroll down. You'll see a "Revert" button. Click it.

GitHub opens a new PR that reverts the changes. The auto-generated description will say something like:

```
Reverts dev-A/bio-link-capstone#6
```

Create the PR. As dev-B, review and approve it (the review step still applies, even for a revert). Merge.

**Step 4: Verify main is fixed**

```bash
git switch main
git pull origin main
```

Check the site. The bug is gone. History shows exactly what happened:

```
$ git tree
* 7d8e9f0 (HEAD -> main) Revert "Update hero text"  ← the fix
* 9a8b7c6 Merge PR #6: Update hero text              ← the mistake
| ...
```

Both events are visible. No one hid anything. The revert is clean.

**Step 5: Delete the revert PR's branch too**

Clean up the revert branch just like any other merged branch. Don't leave stale branches around.

**Why this matters:**

Most developers have never deliberately practiced a revert. When it happens for real, they freeze. You just did it. Next time a bug slips into production, you won't panic — you'll click "Revert" and fix it properly.

**In Your Own Words:**

<details>
<summary>1. Why deliberately introduce a bug instead of learning this during a real incident?</summary>

So you know the revert workflow cold before you actually need it. Panic is replaced by muscle memory.
</details>

<details>
<summary>2. How do you revert a merged PR on GitHub?</summary>

Open the merged PR, scroll to the bottom, click "Revert." GitHub creates a new PR that undoes the changes.
</details>

<details>
<summary>3. Does the revert PR still need to go through review?</summary>

Yes. The same process applies — even reverts should be reviewed before merging.
</details>
