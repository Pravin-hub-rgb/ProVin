Before we go anywhere, let's clear the air on something that trips up almost everyone starting out.

You type `git push` and your code ends up on GitHub. So it's natural to think Git and GitHub are the same thing, or that Git is just the "offline version of GitHub." Neither is true, and understanding the difference is the foundation everything else sits on. If you get this wrong, you'll be confused about PRs, remotes, forks, and basically everything that makes team workflow different from solo coding.

**Git is a program that runs on your computer.** It's a version control system. What does that mean? It tracks changes to your files over time — who changed what, when, and why — and lets you jump back to any point in history. Every time you commit, Git takes a snapshot of your entire project and stores it. You can browse those snapshots, compare them, branch off from them, or revert to them. And here's the crucial part: **Git works completely offline.** Every single Git operation — commit, log, diff, branch, merge — happens on your machine. You could use Git your whole life, build dozens of projects, manage hundreds of branches, and never once connect to the internet. Everything Git does lives inside a hidden folder called `.git` in your project directory. That folder IS your repository. Everything else — your actual source files — are just the "checked out" copy.

**GitHub is a website/service that hosts copies of your Git repositories on their servers.** Its main job is to act as a remote — a central place where you and your teammates can push your work and pull each other's changes. But GitHub isn't just a file host. On top of Git, GitHub adds a whole layer of team collaboration features:

- **Pull Requests** — a structured way to propose changes, discuss them, and merge them after review
- **Issues** — bug tracking and task management tied to your code
- **Code Review** — inline comments on specific lines of code in a PR
- **Actions** — CI/CD pipelines that run tests automatically when you push
- **Projects** — Kanban boards for tracking work
- **Wiki** — documentation
- **Permissions** — who can read, write, or admin the repo

None of these are Git features. Git itself doesn't know what a Pull Request is. If you host your repo on GitLab or Bitbucket, you get similar features but they work differently. The core Git commands (`commit`, `push`, `pull`, `merge`) are identical everywhere. Only the team-layer stuff changes.

Think of it like this: Git is the engine and drivetrain of a car. GitHub is the dealership service center where multiple cars can get serviced together. The engine works the same whether it's in a dealership or not. But the dealership adds services — inspections, scheduling, communication — that the engine can't do on its own.

Here's a gut-check question to test if you understand: if you deleted your GitHub account right now, would your local commits disappear? Answer: no. They're in `.git` on your machine, completely safe. GitHub is just a copy — a remote. If you deleted the repo on GitHub, you'd still have your entire history locally. You could even push it to a different GitHub account or to GitLab and carry on like nothing happened.

A related concept worth understanding: Git is called a **distributed** version control system. That means every local copy is a full, complete repository — not just a snapshot. When you clone a repo from GitHub, you're not downloading just the latest version of the files. You're downloading the entire history, every commit, every branch, ever. Your local copy is a full backup. This is different from older systems like SVN where the server was the single source of truth and your local copy was just a working checkout. In Git, every clone is its own universe.

**Common mistake:** thinking `git push` "saves" your work to GitHub like clicking "Save" in Google Docs. It doesn't. When you push, you're syncing two separate, complete repositories — yours and GitHub's copy. They're peers, not parent and child. Your local repo doesn't need GitHub to exist. GitHub is just the agreed-upon meeting point where everyone syncs.

Another common confusion: "so if I commit locally, that's safe even if I don't push?" Yes. Your commits are written to your local `.git` folder. They're permanent (until deliberately removed). The only thing pushing does is copy those commits to the remote so other people can see them. Your work is never "lost" just because you didn't push. (Unless your hard drive dies. Push is backup too.)

**In Your Own Words:**

<details>
<summary>1. If you lose internet access, can you still use Git? Which operations work?</summary>

Yes. Git is fully offline. Every local operation works — commit, log, diff, branch, merge, stash, reset. Only operations that contact a remote (push, pull, fetch) need internet.
</details>

<details>
<summary>2. What team features does GitHub add that Git itself doesn't have?</summary>

Pull Requests, Issues, code review with inline comments, GitHub Actions (CI/CD), project boards (Kanban), wiki, and granular permissions.
</details>

<details>
<summary>3. Name two alternatives to GitHub that do the same job.</summary>

GitLab and Bitbucket. Both host Git repos and add their own versions of PRs, issues, and CI/CD.
</details>

<details>
<summary>4. If you delete your GitHub repository, what happens to your local commits?</summary>

Nothing. Your local repo is independent. You still have all your history. You can push it to a different remote and carry on.
</details>

<details>
<summary>5. What does it mean that Git is a "distributed" version control system?</summary>

Every local clone is a complete, full repository with entire history — not just a working copy. There's no single "master" copy that holds the truth. Every clone is the truth.
</details>
