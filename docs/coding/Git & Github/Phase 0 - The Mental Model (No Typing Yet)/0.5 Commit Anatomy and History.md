When you run `git log`, you see a list of weird-looking hex strings, author names, dates, and messages. But what's actually inside a commit? How does Git know which commit came before which? And why does understanding this help you work better on a team?

Every commit is a package of data containing exactly these things:

- **A unique hash (SHA-1)** — that 40-character hex string like `a1b2c3d4e5f6...`. This is the commit's ID. It's generated by hashing the commit's contents (plus a timestamp and a reference to the parent), which means it's guaranteed to be unique. No two commits anywhere in the world will ever have the same hash.

- **Author and committer** — name and email. These can be different (the author wrote it, the committer applied it), but in practice they're usually the same person. This is controlled by `git config user.name` and `git config user.email`.

- **Timestamp** — when the commit was created.

- **Commit message** — whatever you wrote after `git commit -m`. This is your chance to explain WHY this change was made. Not what changed (Git can show that with `git diff`), but why.

- **Parent pointer(s)** — the hash(es) of the commit(s) that came before this one. This is the most important part.

That last piece — the parent pointer — is the entire secret to Git's data model. Each commit points to its parent. The parent points to its grandparent, and so on. Together they form a chain, and that chain IS your entire project history. It's literally a singly linked list of snapshots, where each node is a commit.

When you make your very first commit in a repository, it has no parent (it's called a "root commit"). Every commit after that has one parent. A merge commit has two parents (the two branches being merged). This is the only way history gets more than one parent — and that's how Git represents the fact that two lines of development were joined.

Here's what this chain looks like in practice:

```
a1b2c3d (HEAD -> main) Add search functionality
f5e6d7c Fix login validation
8a9b0c1 Add user authentication module
4d3e2f1 Initial commit
```

If you run `git log --oneline`, you see commits in reverse chronological order (newest first). But internally, Git stores them as a linked list going backwards: the newest commit points to the previous one, which points to the one before that, all the way back to the initial commit.

Now, what is a branch in this model? A branch is just a movable pointer that points to a specific commit. When you're on branch `feature/navbar` and you make a new commit, Git:
1. Creates the commit with parent = the current `feature/navbar` commit
2. Moves the `feature/navbar` pointer to the new commit

That's it. The branch name is just a sticky note on a commit. When you `git switch feature/navbar`, Git moves `HEAD` to point to `feature/navbar`. When you commit, the sticky note moves forward.

This is also why creating a branch is instant and costs almost nothing — you're just creating a new file in `.git/refs/heads/` containing a commit hash. No files are copied. No snapshots are duplicated.

Once you truly understand this model, branches, merges, and rebases stop being abstract magic. A merge is just creating a commit with two parents. A rebase is just replaying commits (copying them with new parents) onto a different base. A reset is just moving a branch pointer backwards.

The command that shows you this entire model visually:

```bash
git log --oneline --graph --all --decorate
```

Let's break down the flags:
- `--oneline` — show each commit as a single line (abbreviated hash + message)
- `--graph` — draw ASCII lines connecting commits (shows branches visually)
- `--all` — show ALL branches, not just the current one
- `--decorate` — show branch/tag names next to commits

You'll run this constantly, so set up an alias immediately:

```bash
git config --global alias.tree "log --oneline --graph --all --decorate"
```

Now you can just type `git tree`. You'll use this in every phase of this course.

`git show <commit-hash>` is another useful command — it shows the full diff of what that commit changed, plus metadata. Great for code review or investigating when something broke.

---

**Why this matters for teamwork:**

When someone says "your branch is 3 commits behind main," you now know exactly what that means. There are 3 commits on main's chain that your branch's chain doesn't have. When you merge, Git will create a commit with two parents — joining your chain with main's chain.

Being able to visualize history is a daily survival skill on real projects. You'll look at `git tree` and instantly answer questions like:
- "Has this feature branch been merged yet?" (Check if its commits appear in main's history.)
- "Where did this branch fork off from main?" (Look at the graph — it's right where the lines diverge.)
- "Is this branch up to date with main?" (Check if main's latest commit is an ancestor of your branch.)

**What makes a good commit message:**

This deserves its own section because it matters so much on teams. A good commit message is:

```
Short summary (50 chars or less)

More detailed explanation, if needed. Explain WHY
the change was made, not WHAT was changed. Git
can show what changed. Only you can say why.

- Bullet points for related changes
- Reference issue numbers: Fixes #42
- Mention any breaking changes or migration steps
```

The first line is the subject. Keep it under 50 characters. Capitalize it. Don't end with a period. The subject should complete the sentence "If applied, this commit will ______." (e.g., "Fix null pointer in login handler", "Add user avatar upload endpoint").

The body (separated by a blank line) is optional but valuable for non-trivial changes. Explain the motivation. Why was this approach chosen over alternatives? What tradeoffs were made?

Consistent, descriptive commit messages are what separate professionals from people who write "updated stuff" or "fix" as their entire message. Your future self will thank you when debugging a production issue at 2 AM and reading through commit logs.
