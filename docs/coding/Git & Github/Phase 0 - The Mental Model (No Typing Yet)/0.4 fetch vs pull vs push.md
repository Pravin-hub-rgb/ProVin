There's a good chance you've run `git pull` before and something unexpected happened. Maybe a merge conflict appeared out of nowhere. Maybe your files changed in ways you didn't expect. Maybe you got that scary-looking wall of text with `<<<<<<<` markers and had no idea what to do. That confusion has a name, and it comes from not understanding the difference between `fetch` and `pull`.

Let's break down each operation clearly.

---

**`git fetch`**

This downloads all the latest data from the remote — new commits, new branches, new tags — but it does **NOT** touch your working directory or your current branch. Nothing changes in the files you're editing. Your branch pointers stay exactly where they are.

What does change is your "remote tracking branches." These are special references like `origin/main`, `origin/feature/navbar` that live in your local repo and represent "what the remote looked like the last time I checked." After `git fetch`, `origin/main` gets updated to point to the latest commit on main in the remote repository. Your local `main` branch stays where it was.

Think of fetch like checking your mailbox. You walk to the mailbox, open it, and see what letters arrived. You know what's there. You might flip through the envelopes. But you don't open any of them yet. Your house stays exactly as it was. You just gained information about what's coming.

This is the safe, non-destructive way to see what your team has been up to. You can do it anytime without fear of breaking anything.

```
git fetch origin
git log origin/main --oneline   # inspect what's new on remote main
git diff main..origin/main      # see exactly what changed
```

**`git pull`**

`git pull` is literally `git fetch` followed by `git merge`. It downloads the latest data AND immediately merges the remote changes into your current branch. This is where the surprise factor comes in.

When you run `git pull origin main` while on your `main` branch, Git:
1. Fetches `origin/main`
2. Merges `origin/main` into your current branch (main)

If there are no conflicts, the merge happens silently and your files update. If there ARE conflicts, Git stops mid-pull, puts conflict markers in your files, and asks you to resolve them. This can be jarring if you weren't expecting it — you ran "update my code" and suddenly you're dealing with merge conflicts.

The merge step is important to understand. `git pull` doesn't just "update" your files by overwriting them. It performs a genuine merge. That means it creates a merge commit (if there are diverging changes). Your history gains a new node: "Merge branch 'main' of origin into main."

**`git push`**

The reverse of fetch. You upload your local commits to the remote. Git checks that your local history is a superset of the remote's history — meaning you can't push if someone else has pushed commits you don't have yet. Git enforces this to prevent data loss:

```
! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'origin'
```

When this happens, you need to `git pull` (or `git fetch` + `git merge`) first to incorporate the remote changes, then try pushing again. This is the most common push error beginners face, and it's Git protecting you from accidentally overwriting someone else's work.

The first time you push a new branch, you need the `-u` flag:

```bash
git push -u origin feature/navbar
```

The `-u` sets up "tracking" — it tells Git that your local `feature/navbar` should track `origin/feature/navbar`. After that, you can just run `git push` without arguments and Git knows where to push.

---

**Why this matters for teamwork:**

On professional teams, many developers deliberately avoid blind `git pull`. They do this instead:

```bash
git fetch origin
git log origin/main --oneline   # see what changed
# then decide: merge or rebase?
git merge origin/main           # merge manually when you're ready
```

This gives you control. You see what's coming before it lands in your working directory. If there's a conflict, you're mentally prepared for it — you chose to merge. You're not caught off guard.

Some teams even set up Git to reject `git pull` (via config) to enforce the fetch-first approach. That's how important this distinction is at scale.

Another common pattern is checking what your teammate pushed before merging their changes into your work:

```bash
git fetch origin
git log --oneline origin/feature/login   # see their commits
git diff main..origin/feature/login      # check what they changed
# now decide if you want to merge into your branch
```

---

**Practical exercise with your 2-account setup:**

1. On dev-A: make a small commit and push it to main.
2. On dev-B: run `git fetch`. Don't pull yet.
3. Run `git log origin/main --oneline`. You should see the new commit.
4. Run `git status`. Your local main is still behind. Nothing merged yet.
5. Now run `git pull` and watch it merge in.
6. Notice: fetch let you see the commit. Pull did the merge.

---

**Good practices and common mistakes:**

- **Don't pull into a branch with uncommitted changes.** Git may refuse or create a messy state. Always commit or stash first.

- **Use `git fetch` + `git merge` instead of blind pull** when you want control over when merges happen.

- **Don't use `git pull` with rebase by default** unless you understand rebasing. The default `pull` uses merge, which is safer.

- **If push gets rejected, pull/rebase first, then push again.** Don't force push without understanding the consequences (we'll cover force pushing in Phase 4).
