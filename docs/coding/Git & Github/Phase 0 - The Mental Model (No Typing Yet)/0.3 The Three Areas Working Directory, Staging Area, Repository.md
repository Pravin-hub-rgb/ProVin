You've typed `git add` and `git commit` more times than you can count. They're muscle memory now. But have you ever stopped to ask: why two steps? Why does Git make you `add` before you `commit`? Why can't it just save everything at once?

The answer is Git's three areas. This is the single most important mental model in Git. Most people who only memorize commands never actually understand this, and it shows — they're confused about what `git add .` does, why `git diff` shows nothing, or why a file appears in multiple states. If you understand the three areas, you stop guessing and start knowing.

Here they are:

---

**1. Working Directory**

This is just your files, as they sit on disk. The `index.html` you're editing right now. The `style.css` that's open in VS Code. Every time you save a file, you're changing your working directory. Git sees these changes — run `git status` and it'll show them under "Changes not staged for commit" — but it's not doing anything with them. They're just loose, unsaved changes sitting in your project files.

Git thinks of your working directory as a "checkout" of a specific commit. When you switch branches, Git rewrites your working directory to match the branch you switched to. If you have uncommitted changes when you switch, Git tries to preserve them — but sometimes it can't (if the same file is different on the target branch), and it'll refuse the switch.

**2. Staging Area (the "index")**

This is a holding zone. It lives inside `.git/index` and it's essentially a list of "which changes should go into the next commit." When you run `git add <file>`, Git takes the current version of that file from your working directory and records it in the staging area. Now that version is "staged" — ready to be committed.

Think of it like a prep table in a kitchen. Your counter (working directory) has ingredients spread everywhere. The prep table (staging area) is where you put just the ingredients you're about to cook. Nothing on the prep table is cooked yet. You can add things, remove things, rearrange. Only when you commit do you actually cook the meal.

The staging area exists because you don't always want to commit everything you've changed. Real example: you're working on a new feature and you notice a typo in the documentation. You fix the typo. Now you have two changes in your working directory — the half-finished feature and the documentation fix. If you just `git add . && git commit`, both go into one commit. That's messy. With staging, you can:

```bash
git add docs/readme.md                    # stage just the typo fix
git commit -m "Fix typo in readme"        # commit it cleanly
git add src/feature.js                     # now stage the feature work
git commit -m "Add new feature WIP"       # separate commit
```

Two clean commits instead of one dirty mess. Future-you (and your teammates) can look at `git log` and understand exactly what happened.

`git add -p` is a superpower here. It shows you each chunk of changes (called a "hunk") in each modified file and asks: "do you want to stage this hunk?" You can say `y` (yes), `n` (no), or `s` (split into smaller hunks). This lets you stage parts of a single file separately. If you changed the header on line 5 and the footer on line 100 of the same file, `git add -p` lets you commit the header fix first and the footer later.

**3. Repository (Commit History / The `.git` folder)**

This is the permanent record. When you run `git commit`, Git takes everything in the staging area, packages it into a commit object with a message, author, timestamp, and parent pointer, and writes it into `.git/objects/`. That commit is now part of your project's permanent history.

"Permanent" needs a small qualification — you can rewrite history (amend, rebase, reset), but that's deliberate, advanced work covered in Phase 4. In normal day-to-day Git, once you commit, that commit is there forever.

---

Here's how these three areas interact with the commands you already know:

```bash
git status              # shows: what's in working dir (unstaged), what's in staging (staged), what's untracked
git add <file>          # copies file from working dir to staging area
git add -p              # interactively stage parts of a file
git commit              # takes staging area and locks it into history
git diff                # compares working directory vs staging area
git diff --staged       # compares staging area vs last commit (what will be committed)
git diff HEAD           # compares working directory vs last commit (both staged and unstaged changes)
```

Let me explain those three diff commands more carefully because they're confusing:

- `git diff` — "what have I changed since I last staged?" Shows the difference between your working directory and the staging area. If you just edited a file but haven't `git add`-ed it, `git diff` shows those edits.

- `git diff --staged` — "what's in staging that I'm about to commit?" Shows the difference between the staging area and the last commit. This is your commit preview.

- `git diff HEAD` — "what have I changed overall?" Shows the difference between your working directory AND the last commit, combining both staged and unstaged changes. Useful as a full summary.

---

**Why this matters for teamwork in practice:**

Consider this scenario. You're working on a team project. You've been asked to fix a bug AND refactor a function. You do both in the same file. The bug fix is urgent and needs its own commit with a clear message so the team lead can review it. The refactor is non-urgent. Without staging, you'd have to either make two separate edits in two separate sessions, or commit them together and muddy the history.

With staging: you fix the bug, `git add -p` to stage only the bug fix hunks, commit those with message "Fix null pointer in login handler". Then you do the refactor, stage the remaining hunks, commit with message "Refactor login handler for readability". The team lead sees two clean, focused commits. That's professionalism.

**Common mistake:** always running `git add .` and committing everything blind. This bundles unrelated changes together and makes history useless. Ask yourself: "would I be happy reading this commit message in six months?"

**One commit = one logical change.** Memorize that.
