You've created your feature branch. You're working hard. Life is good. But your teammates are also working — they're merging their own branches into `main` while you code away in happy isolation. Days pass. You finish your feature and try to merge back. Suddenly you're facing 15 merge conflicts. Files you didn't even touch are colliding. Your clean, simple feature is now a nightmare to merge.

This is the "conflict bomb," and it's entirely preventable.

**The problem:**

When you create a branch off main, you get a snapshot of main at that moment. Your branch contains your changes, but it doesn't know about anything that happened on main after you branched. Meanwhile, your teammates are busy — they've merged five PRs, refactored the database layer, updated dependencies, and fixed three bugs. Your branch is now "behind" main by dozens of commits.

The longer your branch lives without syncing, the more it drifts from main. When you finally try to merge, Git has to reconcile two completely different trajectories. If you and your teammates edited the same files (which is common in a real codebase), those become merge conflicts.

The fix is simple: regularly pull the latest main into your branch.

**The command:**

```bash
git switch feature/navbar       # make sure you're on your branch
git fetch origin                 # get the latest from remote
git merge origin/main            # merge main's changes into your branch
```

That's it. Three lines. Do this at least once a day while your branch is alive.

After `git merge origin/main`, your branch now has both your feature work AND all the latest changes from main. Any conflicts that arise are small and manageable because you're only catching up on one day's worth of changes, not two weeks'.

**What actually happens during the merge:**

When you merge `origin/main` into your branch, Git:
1. Identifies the common ancestor commit (where your branch and main last agreed).
2. Applies all commits from main (that your branch doesn't have) on top of your branch.
3. Creates a merge commit that has two parents: your previous branch tip and main's tip.

After the merge, your branch history looks like:

```
*   Merge branch 'main' into feature/navbar
|\
| *  (main) Update footer copyright (teammate's work)
| *  Add database connection pooling (teammate's work)
* |  Add responsive dropdown menu (your work)
* |  Fix z-index on mobile toggle (your work)
|/
*  Initial commit
```

Your feature commit and main's commits are now in the same branch. When you eventually merge your PR into main, there won't be a surprise conflict bomb because you've been resolving conflicts all along.

**Dealing with conflicts during the sync:**

If there's a conflict when you merge main into your branch, don't panic. It just means you and a teammate changed the same lines differently. Resolve it the normal way:

1. Open the conflicted file.
2. Find the conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`).
3. Edit the file to keep the correct version (yours, theirs, or a combination).
4. Remove the conflict markers.
5. Save, `git add <file>`, and `git commit` to complete the merge.

The advantage of doing this during a regular sync instead of at the end: the conflict is smaller and more recent. You remember what you were working on. The context is fresh.

**What about `git rebase`?**

There's an alternative to merging main into your branch: rebasing.

```bash
git switch feature/navbar
git fetch origin
git rebase origin/main
```

Instead of creating a merge commit, rebase rewrites your branch's history so it appears as if you started from the current main. Your commits are replayed on top of main's latest commit, one by one.

The result is a linear history:

```
*  (feature/navbar) Add responsive dropdown menu
*  Fix z-index on mobile toggle
*  (main) Update footer copyright (teammate's work)
*  Add database connection pooling (teammate's work)
*  Initial commit
```

No merge commits. Clean, straight line. Rebasing produces a cleaner history, but it rewrites your branch's commits (they get new hashes). This is fine for local/private branches, but **never rebase a branch that others have pulled from** — you'll rewrite history and cause chaos.

For now, use `git merge origin/main`. It's safer and easier to understand. We'll dive deeper into rebasing in Phase 4.

**Good practices:**

- **Sync daily.** Set a calendar reminder if you need to. "Sync branch with main" is a 30-second operation that saves hours.
- **Sync before requesting a PR review.** Your reviewer should be looking at your code, not wading through conflicts.
- **Sync after a teammate merges something into main.** Especially if you know they were working on related files.
- **Never leave a branch un-synced for more than 2-3 days.** Long-lived branches are a smell.

**Common mistakes:**

- "I'll sync at the end when I'm done." This is exactly what causes conflict bombs. Sync early, sync often.
- "I don't want to bother with conflicts now, I'll deal later." The conflict that takes 5 minutes to resolve today will take an hour to resolve next week, because your branch will have drifted further and the context will be colder.
- Rebasing a shared branch. If anyone else has pulled your branch, don't rebase it. Use merge.

**In Your Own Words:**

<details>
<summary>1. What does it mean for a branch to be "behind" main?</summary>

New commits have been added to main since you branched. Your branch is based on an older version of main and is missing those changes.
</details>

<details>
<summary>2. What two commands do you run to sync main's latest changes into your branch?</summary>

`git fetch origin` (to download remote changes) followed by `git merge origin/main` (to merge them into your current branch).
</details>

<details>
<summary>3. What is a "conflict bomb"?</summary>

A massive pile of merge conflicts that happens when you try to merge a very stale branch that hasn't synced with main in a long time. Regular syncing prevents this.
</details>

<details>
<summary>4. What's the difference between syncing with `git merge` vs `git rebase`?</summary>

Merge creates a merge commit and preserves your branch's history as-is. Rebase rewrites your commits on top of main for a cleaner, linear history but is dangerous for shared branches.
</details>

<details>
<summary>5. How often should you sync your branch with main?</summary>

At least once a day. More often if teammates are actively merging to main.
</details>
