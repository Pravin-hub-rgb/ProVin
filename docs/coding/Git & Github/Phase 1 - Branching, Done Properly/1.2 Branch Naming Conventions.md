You know you need to branch for everything. So the next question is: what do you call it? Naming a branch `my-branch` or `test123` works fine when you're alone. But on a team where 5-10-30 branches might be active at once, bad names make you waste time figuring out what's what. Good names make the repo self-documenting.

**The standard pattern:**

The most widely used convention is `<type>/<short-description>`:

```
feature/user-authentication
fix/login-button-not-clickable
chore/update-dependencies
refactor/api-error-handling
docs/api-documentation
test/integration-setup
```

The type prefix communicates the *intent* of the branch at a glance. Here are the common prefixes:

| Prefix | Purpose | Example |
|--------|---------|---------|
| `feature/` | New functionality | `feature/search-bar` |
| `fix/` | Bug fix | `fix/null-pointer-login` |
| `chore/` | Maintenance (deps, config, build) | `chore/upgrade-nextjs` |
| `refactor/` | Code restructure, no behavior change | `refactor/auth-service` |
| `docs/` | Documentation only | `docs/api-endpoints` |
| `test/` | Adding/fixing tests | `test/user-model` |
| `experiment/` | Trying something, may be discarded | `experiment/new-auth-flow` |

The description after the slash should be short but meaningful. Use hyphens to separate words. No spaces, no CamelCase, no underscores (though underscores work technically, hyphens are the convention).

**Real team examples:**

Good names:
- `feature/payment-webhook-integration`
- `fix/wrong-currency-formatting`
- `chore/remove-dead-code`
- `refactor/database-connection-pool`

Bad names:
- `my-branch` (what does it do?)
- `vin-test-42` (who is vin, and what's test 42?)
- `patch` (patch what?)
- `asdfgh` (meaningless)
- `fix` (fix what? too vague)

**Why this matters:**

When there are 30 open branches and you need to find the one related to the login bug, you can visually scan:
- See `fix/` — likely a bug fix
- See `fix/login-button` — it's about login
- Open it — there's the fix

Without conventions, you'd have to open each branch, read the code, and figure it out. Multiply that by 30 branches and you've wasted half an hour.

It also matters for automation. CI/CD systems often trigger different pipelines based on branch naming. For example, commits to `fix/*` branches might run only unit tests, while commits to `feature/*` branches might run full integration tests too. CI/CD can also auto-deploy branches based on naming — `staging/*` deploys to staging, `release/*` deploys to production.

**A note on issue trackers:**

Many teams include the issue number in the branch name:

```
feature/42-user-authentication
fix/117-login-validation
```

This creates a direct link between the code change and the task tracker. Anyone seeing the branch knows what issue it relates to, and most git hosting platforms (GitHub, GitLab) will link commits on that branch back to the issue automatically.

**Common mistakes:**

- Spaces or special characters: `feature/add new stuff` will cause problems in the terminal (you'd need to quote it). Use hyphens: `feature/add-new-stuff`.
- Being too vague: `fix/update` doesn't help. `fix/update-user-avatar-url` does.
- Mixed conventions within a team: if half the team uses `feature/` and the other half uses `feat/` and `ft/`, the naming loses its value. Agree on prefixes and stick to them.
- Using only issue IDs: `42-fix` — you still have to look up the issue to know what it is. Include both type and description.

<details>
<summary>1. What is the standard branch naming pattern used by most teams?</summary>

`<type>/<short-description>` using hyphens for spaces, e.g. `feature/user-authentication`, `fix/login-button`.
</details>

<details>
<summary>2. Name five type prefixes and describe when to use each.</summary>

`feature/` (new feature), `fix/` (bug fix), `chore/` (maintenance), `refactor/` (restructure), `docs/` (documentation).
</details>

<details>
<summary>3. Why is `my-branch` or `test123` a bad name on a team project?</summary>

They give no information about purpose or scope. Good names let anyone immediately understand what the branch does without reading the code.
</details>

<details>
<summary>4. Why might a team include issue numbers in branch names?</summary>

To create a direct link between the code change and the issue tracker, making it easy to trace why a change was made.
</details>

<details>
<summary>5. What characters should you avoid in branch names?</summary>

Spaces, special characters, and uppercase. Stick to lowercase letters, hyphens, and forward slashes.
</details>
