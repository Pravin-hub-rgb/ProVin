Enough theory. You know why branches exist and how to name them. Now let's run the actual commands. By the end of this section, creating and switching branches will be as natural as breathing.

**The branch toolkit:**

```bash
git branch                      # list local branches (* marks current)
git branch -a                   # list ALL branches (local + remote)
git branch -v                   # list branches with their latest commit
```

The `-a` flag is particularly useful because remote branches don't show up in `git branch` by default. If you've fetched but find yourself unable to see a branch someone else pushed, you probably forgot `-a`.

```bash
git switch <branch-name>        # switch to an existing branch
git switch -c <new-branch>      # create AND switch to a new branch
git checkout <branch-name>      # older way to switch branches
git checkout -b <new-branch>    # older way to create-and-switch
```

If you started with tutorials that taught `git checkout -b`, that's fine — it still works. But `git switch` was introduced in Git 2.23 (released 2019) specifically because `checkout` does too many things. `checkout` can:
- Switch branches (`git checkout main`)
- Create and switch to a branch (`git checkout -b feature/x`)
- Restore a file to a previous version (`git checkout -- file.js`)
- Check out a specific commit (detached HEAD)

That's a confusing mix of operations under one command. `git switch` is dedicated to branch switching. `git restore` handles file restoration. The commands have been split for clarity. Use `git switch` for branches.

**The standard workflow for starting new work:**

```bash
# Step 1: Get the latest main
git switch main
git pull origin main

# Step 2: Create your feature branch
git switch -c feature/navbar

# Step 3: Do work, commit
git add -p
git commit -m "Add responsive navbar"

# Step 4: Push your branch
git push -u origin feature/navbar
```

That `-u` flag (short for `--set-upstream`) is important the first time you push a branch. It tells Git: "my local `feature/navbar` tracks `origin/feature/navbar`." After that, you can just run `git push` without specifying where.

**What happens when you switch branches?**

When you run `git switch feature/login`, Git:
1. Checks if your working directory is clean (no uncommitted changes). If not, it may refuse to switch.
2. Moves `HEAD` to point to `feature/login`.
3. Rewrites your working directory to match the state of `feature/login`'s latest commit.

Step 3 is where people get nervous — Git will literally change your files. If `feature/login` has a different version of `app.js` than what's on your disk, Git overwrites it. But this is fine because:
- Your commits are safe (they're in `.git`)
- Uncommitted changes prevent switching (or are carried along, depending on the situation)

**The dirty working directory problem:**

If you have uncommitted changes and try to switch branches, Git tries to preserve them. It can do this if the files you changed are identical on both branches. But if you changed a file that's different in the target branch, Git will refuse:

```
error: Your local changes to the following files would be overwritten by checkout:
    src/app.js
Please commit your changes or stash them before you switch branches.
```

In this case, you have three options:
1. **Commit** — if your changes are complete, commit them.
2. **Stash** — `git stash` temporarily shelves your changes so you can switch. Come back and `git stash pop` later.
3. **Discard** — `git checkout -- src/app.js` to throw away changes (careful, this is permanent).

Stashing is perfect for the "I forgot I wasn't done yet" scenario:

```bash
git stash push -m "WIP: navbar responsive styles"
git switch main
# do what you need on main
git switch feature/navbar
git stash pop
```

`git stash pop` re-applies the most recent stash and removes it from the stash list. If you want to keep the stash around, use `git stash apply` instead.

**Detached HEAD state:**

One more thing worth knowing: running `git checkout <commit-hash>` puts you in "detached HEAD" state. This means `HEAD` points directly to a commit, not to a branch. You can still make commits, but they won't belong to any branch. If you switch away, those commits are "orphaned" and will eventually be garbage collected (unless you create a branch pointing to them).

If you accidentally end up in detached HEAD and make commits, rescue them by creating a branch:

```bash
git switch -c rescue-branch
```

Now all your detached commits are on `rescue-branch` and safe.

**Critical good practice:**

Always pull the latest `main` BEFORE branching off it. If you branch off a stale `main`, your new branch starts behind. When you eventually merge, you'll have to deal with conflicts that could have been avoided:

```bash
# BAD: branch off potentially stale main
git switch main
git switch -c feature/navbar    # main might be behind!

# GOOD: update main first, then branch
git switch main
git pull origin main            # get the latest
git switch -c feature/navbar    # now you're starting from latest
```

**Another common mistake:**

Accidentally branching off the wrong base. If you're currently on `feature/navbar` and run `git switch -c feature/footer`, the new branch will include all of `feature/navbar`'s commits too. Always verify which branch you're on before creating a new one:

```bash
git branch   # shows your current branch with *
```

**Exercise:**

Run this until it's muscle memory:

```bash
git switch main
git pull origin main
git switch -c exercise-1
# make a small change, commit
git switch main
git switch -c exercise-2
```

Repeat 3-4 times. The point is to make the sequence automatic so you don't have to think about it during actual work.

**In Your Own Words:**

<details>
<summary>1. What's the command to create a new branch and switch to it in one step?</summary>

`git switch -c <new-branch-name>` (or the older `git checkout -b <new-branch-name>`).
</details>

<details>
<summary>2. Why was `git switch` introduced? What problem does it solve over `git checkout`?</summary>

`checkout` was overloaded — it switches branches, restores files, and checks out commits. `switch` is a dedicated, simpler command just for switching branches.
</details>

<details>
<summary>3. What does the `-u` flag do in `git push -u origin feature/navbar`?</summary>

Sets up upstream tracking. It links your local branch to the remote branch so future pushes can use just `git push`.
</details>

<details>
<summary>4. What should you do if Git refuses to switch branches because of uncommitted changes?</summary>

Commit the changes (if complete), `git stash` them (if you want to return later), or discard them with `git checkout -- <file>` (permanent).
</details>

<details>
<summary>5. What is detached HEAD state, and how do you rescue commits made there?</summary>

Detached HEAD means you're on a specific commit, not a branch. Commits made here are orphaned if you leave. Rescue them with `git switch -c new-branch-name`.
</details>
