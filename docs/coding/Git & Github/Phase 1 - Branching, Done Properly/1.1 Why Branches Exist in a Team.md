In the last section, we talked about how commits form a chain — a linked list of snapshots, each pointing to its parent. That's a single line of history. Now imagine five developers all trying to add new links to that same chain at the same time, each with their own half-finished work. It'd be chaos. One person's incomplete feature would mix with another's bug fix. Nothing would be stable. That's exactly why branches exist.

**What a branch actually is:**

A branch is just a movable pointer that points to a specific commit. That's it. It's not a copy of your files. It's not a separate workspace with duplicated data. It's literally a file in `.git/refs/heads/` containing 41 bytes — the hash of a commit plus a newline. When you make a new commit while on a branch, Git:

1. Creates the commit with the parent being the current commit (the one the branch points to).
2. Updates the branch file to contain the new commit's hash.

The branch pointer moves forward. That's the entire mechanism.

Branches are cheap. Creating a branch costs almost nothing — you're just writing a commit hash to a tiny file. This is by design. Git wants you to branch early and branch often. The whole workflow is built around cheap, throwaway branches.

**Then what is `main`?**

`main` (or `master`, depending on when your repo was created) is a branch too. It's not special in Git's architecture. It's special only by convention — teams agree that `main` is the stable, deployable version of the code. Everything else branches off from `main` and eventually merges back into `main`.

If you don't protect it, `main` just becomes another branch where people commit directly. The convention only holds if the team enforces it (via branch protection rules, which we'll cover in Phase 5).

**Why branches matter for teamwork:**

Consider a team of 5 developers working on a web application. Alice is adding a new API endpoint. Bob is fixing a CSS bug. Charlie is refactoring the database layer. Diana is updating documentation. Eric is experimenting with a new build tool.

Without branches, all five of them commit to the same `main`. Alice's half-finished endpoint breaks the build. Bob's CSS fix works but gets lost in the noise of everyone else's changes. Charlie's refactor introduces a bug that affects Diana's docs. Eric's experiment is unfinished and breaks everything. The codebase is permanently broken, and nobody can deploy anything.

With branches, each developer works in isolation:
- `feature/api-endpoint`
- `fix/css-button-alignment`
- `refactor/database-layer`
- `docs/update-readme`
- `experiment/new-build-tool`

Alice can push broken code to her branch — it doesn't affect anyone. Bob works on his fix without being blocked by Alice's unfinished work. They only merge into `main` when their work is complete, tested, and reviewed. `main` stays stable.

**Why this is non-negotiable:**

The rule is simple but absolute: **never commit directly to main on a team project.** Not even a one-line fix. Not even a typo. Every change goes through a branch, a pull request, and a review. If you bypass this, you bypass the entire safety net that makes team collaboration work.

On real teams, even a single-character fix like `fix/typo-readme` gets its own branch. It sounds excessive, but consider: what if that one-character fix introduces a subtle bug? What if it's deployed automatically (via CI/CD) and breaks production? The branch + PR workflow is insurance against exactly these scenarios.

**Common mistakes:**

- "It's just a small fix, I'll commit directly to main." Don't. Small fixes become big problems when they're wrong. The discipline of always branching is what makes `main` reliable.
- "Branches are only for big features." No. Branches are for any change that isn't ready for production, which is every change until it's reviewed.
- "I can just work on main and be careful." You can't be careful enough. The cost of creating a branch is near zero. The cost of a broken main is potentially hours of debugging for the entire team.

**The bigger picture:**

There are different branching strategies teams use — Git Flow, GitHub Flow, Trunk-Based Development — but they all share the same core idea: `main` stays clean, work happens on branches. Which strategy you pick depends on your team size, release cadence, and risk tolerance. We'll touch on these in Phase 6. For now, just internalize the why.
