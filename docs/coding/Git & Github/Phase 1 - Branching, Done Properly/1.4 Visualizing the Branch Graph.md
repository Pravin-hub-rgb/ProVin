Remember the `git tree` shortcut we set up? If you haven't done it yet, now's the time:

```bash
git config --global alias.tree "log --oneline --graph --all --decorate"
```

This command shows your entire project history as a picture. Once you learn to read this picture, you'll never work blindly again.

**What you'll see:**

When you run `git tree` in a repo with multiple branches, you get something like:

![Visual git tree graph showing main branch and a feature branch with commits, plus the --merged and --no-merged commands](/diagrams/gitgithub/branch-graph.svg)

The diagram above shows what `git tree` displays. The blue commits on the left form the `main` branch. The green commits on the right form the `feature/navbar` branch — you can see it split off from `main` and later joined back via a merge. The bottom section shows how to check which branches are safe to delete.

In your terminal, the same information looks like this:

```
*   9a8b7c6 (HEAD -> main) Merge feature/navbar into main
|\
| * 2b3c4d5 (feature/navbar) Add dropdown menu
| * 1a2b3c4 Adjust spacing on mobile
* | f5e6d7c Fix login validation
* | 8a9b0c1 Add password reset
|/
* 4d3e2f1 Initial commit
```

Let's read this bottom to top:

1. We started with "Initial commit"
2. Two people started working in parallel — one on `feature/navbar` (the indented lines with `| *`) and one on `main` (the `* |` lines)
3. `feature/navbar` got two commits (dropdown menu, then spacing fix)
4. `main` got two commits (login fix, then password reset)
5. At the top, the branch was merged back into main (the merge commit with two lines joining)

The symbols are simple:
- `*` — a commit
- `|` — the line continuing
- `\` and `/` — branches splitting apart or joining together
- `(HEAD -> main)` — where you currently are
- `(feature/navbar)` — another branch pointing to a specific commit

**How to read the story:**

Once you can read the graph, you can answer questions instantly:

- **Where did this branch fork off main?** Look where the lines split.
- **Has it been merged already?** Check if the lines rejoined.
- **Is my branch behind?** See if main has commits that your branch doesn't.

**Two more useful commands:**

```bash
git branch --merged main      # show branches that are safe to delete
git branch --no-merged main   # show branches that still need work
```

Before deleting a branch, always check `--merged` to be safe.

When you do delete:
```bash
git branch -d feature/navbar    # safe delete (only works if merged)
git branch -D feature/navbar    # force delete (even if not merged — careful!)
```

Use lowercase `-d` by default. It won't let you delete something that isn't merged. Uppercase `-D` forces it — use only when you're absolutely sure.

**Try this:**

1. Create 2-3 branches off main
2. Make a different commit on each
3. Run `git tree` after each step. Watch the graph grow.
4. Merge one branch into main. Run `git tree` again. See the merge commit with two parents.

Do this a few times. The graph should start making intuitive sense.

**In Your Own Words:**

<details>
<summary>1. What does `git tree` show you?</summary>

A visual graph of all commits and branches in your project, showing how they relate to each other.
</details>

<details>
<summary>2. How can you tell from the graph if a branch has been merged?</summary>

The lines split apart (branching) and rejoin (merging). If your branch's commits appear in main's history, it's merged.
</details>

<details>
<summary>3. What's the difference between `git branch -d` and `git branch -D`?</summary>

`-d` (lowercase) safely refuses if the branch isn't merged. `-D` (uppercase) forces deletion even if not merged.
</details>

<details>
<summary>4. How can you check which branches are safe to delete?</summary>

Run `git branch --merged main` — it lists branches whose work is already in main.
</details>
