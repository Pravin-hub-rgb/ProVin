When you open a PR, you might see green checkmarks, yellow dots spinning, or red X's next to your commits. Those are status checks. They're automated tests or processes that run against your code to make sure it's not broken.

**What are status checks?**

A status check is an automated task that reports pass/fail on a commit or PR. Common examples:
- Tests pass (unit tests, integration tests)
- Linter passes (code style is consistent)
- Build succeeds (the project compiles)
- Security scan passes (no known vulnerabilities)

**What they look like on a PR:**

At the bottom of your PR's Conversation tab, you'll see a section like:

```
All checks have passed
✓ Build (Node.js 18) — success
✓ Lint (ESLint) — success  
✓ Tests (Jest) — success
```

Or, if something failed:

```
Some checks were not successful
✗ Tests (Jest) — 1 failing test
✗ Lint (ESLint) — 2 errors
```

If branch protection is on and requires status checks, a red X blocks the merge button just like a missing review would.

**How do these checks run?**

Usually through GitHub Actions — a CI/CD (Continuous Integration / Continuous Deployment) system built into GitHub. When you push code, GitHub spins up a virtual machine, runs your tests, and reports the result. Setting up GitHub Actions is outside the scope of this course (it's a whole topic on its own), but recognizing status checks is important.

**Why they matter on a team:**

- They catch problems automatically before code reaches main
- They enforce standards (consistent formatting, no lint errors)
- They build trust — a green checkmark means "this PR won't break the build"
- They reduce the reviewer's mental load — the reviewer can focus on logic, not formatting

**For this course:**

You don't need to set up actual CI. Just know what status checks are. If you're curious, you can create a trivial GitHub Action that just echoes "tests passed" on every push — purely to see the green check appear. But it's optional.

**When you join a new team:**

Look at the PR checks. They'll tell you what the team values. If there's a lint check, the team cares about code style. If there's a build check, the team cares about compilation. If there's a test coverage check, tests are important here.
