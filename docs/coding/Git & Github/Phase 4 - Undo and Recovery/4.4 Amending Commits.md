You just made a commit. Then you realize: the message has a typo. Or you forgot to include a file. Or you included a debug log you didn't mean to.

You could make a new commit called "Fix typo in previous commit message." But that clutters history. Instead, use `git commit --amend`.

**What amend does:**

It replaces your most recent commit with a new one. If you only want to change the message:

```bash
git commit --amend -m "Add contact form with validation"
```

This takes everything from the previous commit (same files, same changes) but with a new message.

If you forgot a file:

```bash
git add forgotten-file.js
git commit --amend --no-edit
```

The `--no-edit` flag keeps the existing commit message. The new file is added to the existing commit.

**What amend does NOT do:**

It doesn't "edit" the old commit. It creates a brand new commit with a new hash that replaces the old one. The old commit still exists in reflog for a while, but it's no longer part of your branch history.

This is important because:

```
Before amend:
a1b2c3d (HEAD -> main) Add contact form
4d3e2f1 Initial commit

After amend:
e5f6g7h (HEAD -> main) Add contact form with validation
4d3e2f1 Initial commit
```

Notice: the hash changed from `a1b2c3d` to `e5f6g7h`. A different commit entirely. The old one is orphaned.

**The critical rule (same as reset):**

Only amend commits that haven't been pushed yet. If you've already pushed the commit and someone else has pulled it, amending creates a duplicate and confuses things. The same rule as reset applies: don't rewrite history that others share.

If you need to fix a message on an already-pushed commit, use revert (4.2) or just live with it and move on. Small typos in commit messages are fine.

**When is amend useful?**

- Fixing a typo in the commit message
- Adding a file you forgot to stage
- Removing a file you accidentally included
- Combining the last commit with new minor changes instead of making a separate "oops" commit

**When NOT to use it:**

- If you already pushed the commit (share the mistake, or revert)
- If you're trying to change something more than one commit back (use interactive rebase for that — advanced, not covered here)
- If the commit message is fine but the code is wrong — amend doesn't fix code, it fixes what's IN the commit (and if the code is wrong, make a new commit to fix it)

**In Your Own Words:**

<details>
<summary>1. What does `git commit --amend` do?</summary>

It replaces the most recent commit with a new one, allowing you to change the message or add/remove files.
</details>

<details>
<summary>2. How do you amend without changing the commit message?</summary>

`git commit --amend --no-edit` — it keeps the existing message and just updates the commit content.
</details>

<details>
<summary>3. Why shouldn't you amend a commit that's already been pushed?</summary>

Amending creates a new commit with a new hash, rewriting history. Anyone who already pulled the old commit will have conflicts.
</details>

<details>
<summary>4. Does `git commit --amend` edit the old commit or create a new one?</summary>

It creates a brand new commit with a new hash. The old commit is orphaned (but still in reflog temporarily).
</details>
