You pushed a commit. Maybe it was bad. Maybe it broke something. Maybe your teammate is already looking at it. If you use `git reset` now, you'll rewrite history and confuse everyone who's already pulled your changes.

Enter `git revert`. Instead of erasing the commit from history, it creates a BRAND NEW commit that undoes the changes of the old one. History stays intact. Everyone's repos stay in sync.

**How it works:**

```bash
$ git log --oneline
e5f6g7h (HEAD -> main) Add broken API endpoint
a1b2c3d Fix login validation
4d3e2f1 Initial commit

$ git revert e5f6g7h
```

Git opens your editor with a pre-filled message:

```
Revert "Add broken API endpoint"

This reverts commit e5f6g7h.
```

Save and close. Git creates a new commit:

```
$ git log --oneline
9a8b7c6 (HEAD -> main) Revert "Add broken API endpoint"
e5f6g7h Add broken API endpoint
a1b2c3d Fix login validation
4d3e2f1 Initial commit
```

Notice: the bad commit is still there. Nothing was erased. A new commit simply undid its changes. Anyone who already had `e5f6g7h` can pull and get `9a8b7c6` without any issues.

**Revert vs Reset — the golden rule:**

```
git reset   = for your own unpushed work    (safe, local only)
git revert  = for anything already shared   (safe for teams)
```

Memorize this. It's the single most important rule of undoing in Git.

**Reverting a merge commit:**

This is trickier. If you merged a feature branch and then need to undo that merge, a regular revert isn't enough. You need to tell Git which parent branch to follow:

```bash
git revert -m 1 <merge-commit-hash>
```

The `-m 1` means "follow the first parent" — which is usually main. This reverts all the changes that came in from the merge, as if the merge never happened. We'll cover this more in 4.5.

**Revert on GitHub:**

On a merged PR, GitHub has a "Revert" button in the PR page. Clicking it creates a new PR that reverts the changes. Same concept as the terminal command, just through the UI.

**What people get wrong about revert:**

- Thinking revert "erases" the old commit. It doesn't. It adds a new one. The history is preserved.
- Worrying that history with both "Add X" and "Revert X" looks messy. That's fine. Real projects have real history. It's honest.
- Confusing revert with reset. Remember: reset removes, revert counteracts. Reset rewrites history, revert adds to it.

<summary>1. What does `git revert` do differently from `git reset`?</summary>

Revert creates a NEW commit that undoes the changes of an old commit. Reset moves the branch pointer backward and can delete changes.

<summary>2. Why is revert safe for team use while reset is not?</summary>

Revert doesn't rewrite history — it adds a new commit. Anyone who pulled the old commit can pull the revert without issues.

Reset for your own unpushed work. Revert for anything already shared.
