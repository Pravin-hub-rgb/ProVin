You've seen the green "Merge pull request" button. Click it and the branch merges. But did you notice the little dropdown arrow next to it? Click that. There are three choices. Most people don't know the difference. Let's fix that.

**The three merge strategies on GitHub:**

1. **Create a merge commit** — keeps every commit from your branch, plus adds a merge commit
2. **Squash and merge** — combines ALL your branch's commits into one clean commit
3. **Rebase and merge** — replays your commits one by one onto main, no merge commit

**Strategy 1: Merge commit (the default)**

This preserves everything. Every commit you made on your branch stays in history, exactly as you made them. Plus Git adds one merge commit at the end.

```
$ git tree
*   9a8b7c6 (HEAD -> main) Merge pull request #5 from dev-A/feature/navbar
|\
| * 3c4d5e6 Fix spacing on mobile
| * 2b3c4d5 Add dropdown hover effect
| * 1a2b3c4 Add navbar markup and styles
* | f5e6d7c Fix login validation
|/
* 4d3e2f1 Initial commit
```

Everything is there. The good, the bad, the "oops forgot a semicolon" commits. The merge commit at the top shows "this was a PR from feature/navbar."

**Strategy 2: Squash and merge**

This takes ALL the commits from your branch and smashes them into one commit on main. Your branch had 15 commits with messages like "wip", "fix typo", "actually working now", "damn it still broken"? With squash, that becomes one clean commit.

```
$ git tree
* 8a9b0c1 (HEAD -> main) Add navbar with dropdown and responsive styles (#5)
* f5e6d7c Fix login validation
* 4d3e2f1 Initial commit
```

Clean. Readable. That's why squash is the most popular strategy on teams. Main branch history becomes a list of features, not a diary of every developer's struggles.

**Strategy 3: Rebase and merge**

This rewrites each of your branch's commits on top of main, as if you wrote them starting from main's latest commit. No merge commit at the end. The history is a straight line.

```
$ git tree
* 7d8e9f0 Fix spacing on mobile
* 6a7b8c9 Add dropdown hover effect
* 5a6b7c8 Add navbar markup and styles
* 4d3e2f1 Initial commit
```

Your commits are now at the tip of main, with new hashes (because they were rewritten). No "Merge branch" noise in history.

**Which one should you use?**

It depends on your team. Here's the general advice:

- **Squash and merge** — the most common. Keeps main history clean. One feature = one commit. Easy to read, easy to revert.
- **Merge commit** — use when you want to preserve the full story. If each commit on your branch is meaningful and self-contained, this is fine. Some teams prefer it because they can see exactly what happened during development.
- **Rebase and merge** — use when you want totally linear history. Less common, but some teams swear by it.

The safest question to ask at a new job: "What merge strategy do we use for PRs?" It takes two seconds and shows you know what you're talking about.

**What matters more than the strategy:**

Pick one, agree on it as a team, and be consistent. Nothing is worse than looking at a repo where some commits are squashed, some have merge commits, and some are rebased. It's a mess to read. Consistency > strategy choice.

**Try it yourself:**

Do the same small PR three times on your practice repo. Merge once with each strategy. Then run `git tree` after each one and look at the difference. It'll click immediately when you see it.
