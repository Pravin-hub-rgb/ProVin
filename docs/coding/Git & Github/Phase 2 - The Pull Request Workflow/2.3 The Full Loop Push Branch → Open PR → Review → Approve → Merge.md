> **Prefer practicing in the browser?** Use the **[Git Lab](/lab/gitgithub?scenario=branch-and-pr)** simulator. It gives you a split-screen terminal where **Junior Dev** (purple terminal) creates the feature branch and pushes, while **Senior Dev** (blue terminal) reviews and merges on GitHub.

This is the one. The loop you'll live in on every real software job. If you only learn one thing from this entire course, make it this rhythm.

The loop has 6 steps, and they never change:

1. Branch off latest main
2. Make changes and commit
3. Push your branch to GitHub
4. Open a Pull Request on GitHub.com
5. Someone reviews and approves
6. Merge into main

**Who does what?** The **Junior Dev** (`dev-B`) does steps 1–4 — all the actual coding and PR creation. The **Senior Dev** (`dev-A`) handles steps 5–6 — reviewing and merging. This mirrors a real team: juniors write code, seniors review and merge.

Let's walk through each one.

---

**Step 1: Branch off latest main (Junior Dev)**

Log into your terminal as Junior Dev (`dev-B`). Always start by pulling the latest main before branching off. Never skip this.

```bash
git switch main
git pull origin main
git switch -c feature/add-footer
```

You're now on a new branch called `feature/add-footer`. Everything you do next stays on this branch and won't affect main until you merge.

---

**Step 2: Make changes and commit (Junior Dev)**

Edit your files. Stage. Commit. Keep commits clean.

```bash
# edit index.html
git add index.html
git commit -m "Add footer with social links and copyright"
```

One commit, one focused change. If you have multiple unrelated changes, split them into separate commits.

---

**Step 3: Push your branch to GitHub (Junior Dev)**

The first push to a new branch needs the `-u` flag:

```bash
$ git push -u origin feature/add-footer
Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
Delta compression using up to 8 threads
Compressing objects: 100% (3/3), done.
Writing objects: 100% (3/3), 512 bytes | 512.00 KiB/s, done.
Total 3 (delta 2), reused 0 (delta 0), pack-reused 0
To https://github.com/dev-A/team-practice.git
 * [new branch]      feature/add-footer -> feature/add-footer
Branch 'feature/add-footer' set up to track remote branch 'feature/add-footer' from 'origin'.
```

After this, future pushes are just `git push`. The `-u` sets up tracking so Git knows where to push without you telling it every time.

---

**Step 4: Open a Pull Request on GitHub.com (Junior Dev)**

Still logged in as Junior Dev (`dev-B`), go to the repo on GitHub.com. You'll see a yellow banner at the top that says:

```
feature/add-footer had recent pushes
  Compare & pull request
```

Click it. GitHub opens a PR form with:
- **Base:** main (the branch you're merging INTO)
- **Compare:** feature/add-footer (your branch)
- **Title** — already filled from your commit message, but edit it to be descriptive
- **Description** — write what you did and why

Fill it in:

```
Title: Add footer with social links and copyright

Description:
Adds a site footer with:
- Social media links (Twitter, GitHub, LinkedIn)
- Copyright notice with current year
- Responsive layout (stacks on mobile)
```

Then click "Create pull request."

If you don't see the yellow banner, go to the "Pull requests" tab and click "New pull request." Same thing.

---

**Step 5: Someone reviews and approves (Senior Dev)**

Now switch hats. Log out of GitHub and log back in as **Senior Dev** (`dev-A`). Go to the same repo. Click "Pull requests" — you'll see the open PR that Junior just created.

Click on it. You'll see three tabs:
- **Conversation** — the title, description, and all comments
- **Commits** — every commit in this branch
- **Files changed** — the actual diff, line by line

Click "Files changed." You'll see green lines for additions and red lines for deletions. You can hover over any line and click the blue "+" to leave a comment.

When you're done reviewing, click "Review changes" (top right). Choose one:

- **Comment** — general feedback, doesn't block or approve
- **Approve** — looks good, merge it
- **Request changes** — needs fixes before merge

For practice, start with **Approve**. You can leave a comment like "Looks good!" before clicking.

---

**Step 6: Merge into main (Senior Dev)**

Still logged in as Senior Dev (`dev-A`), the PR now shows a green checkmark and says the branch has no conflicts.

Click "Merge pull request" → "Confirm merge."

```
✅ Pull request successfully merged and closed
```

That's it. The changes are now in main. GitHub even offers to delete the branch for you. Say yes — we'll cover cleanup properly in 2.6.

**What people mess up:**

- Forgetting to pull main before branching off — creates unnecessary conflicts later
- Writing a useless PR description like "fixed stuff" — teammates can't review without context
- Clicking merge without anyone approving — defeats the whole purpose of the PR
- Not switching hats if you have two accounts — reviewing your own PR is pointless practice

**In Your Own Words:**

<details>
<summary>1. What does the `-u` flag do in `git push -u origin feature/navbar`?</summary>

Sets up tracking so future pushes to that branch can be just `git push`.
</details>

<details>
<summary>2. What three tabs do you see when you open a PR on GitHub?</summary>

Conversation (title/comments), Commits (list of commits), Files changed (the diff).
</details>

<details>
<summary>3. What are the three review options and what do they mean?</summary>

Comment (feedback only), Approve (good to merge), Request changes (fix this first).
</details>

<details>
<summary>4. After approval, what button do you click to complete the merge?</summary>

"Merge pull request" → "Confirm merge."
</details>

<details>
<summary>5. What's the first thing you should do before creating a new branch?</summary>

Switch to main and run `git pull origin main` to make sure you're branching off the latest version.
</details>
