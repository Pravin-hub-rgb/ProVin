So you know how to create branches, commit work, and keep your branch in sync with main. But there's a missing piece. How does your code actually get from your branch into main? On a real team, you don't just merge locally and push. There's a gate in between. That gate is called a Pull Request.

**A Pull Request (PR) is a GitHub feature — not a Git feature.**

Let that sink in. Git itself has no concept of a PR. Git only knows branches, commits, and merges. A PR is something GitHub (or GitLab, Bitbucket) adds on top. It's a formal request that says: "Hey, I have a branch with changes. I'd like to merge it into main. Could someone look at it first?"

The name "pull request" comes from the idea that you're asking someone else to pull your changes into theirs. But in practice, what it really means is: "Please review my code before merging."

**Why not just merge locally?**

You could. You could switch to main, run `git merge feature/navbar`, and push. That works technically. But here's what you'd miss:

- **Code review** — nobody looks at your changes before they land in main. What if you made a mistake? What if you accidentally deleted something?
- **Discussion** — there's no place for the team to comment on your changes. No line-level questions. No "hey, I think this could be simpler."
- **CI checks** — automated tests don't run before the merge (if you have them set up). Your broken code goes straight to main.
- **Audit trail** — months later, nobody can look up "why did this change happen?" because there's no PR associated with it.

On real teams, the PR is the unit of work. It's the thing you link to in your task tracker. It's what you mention in standup. It's proof that your change was reviewed and approved before it hit main.

**How a PR works at the GitHub level:**

When you push a branch to GitHub and open a PR, GitHub checks: "can this branch be merged into main without conflicts?" It shows you a green "Able to merge" or a warning about conflicts. Then it waits. Someone reviews your code. They can:

- **Comment** — just feedback, nothing blocks
- **Approve** — "looks good, merge it"
- **Request changes** — "fix this before merging"

Once approved, someone clicks the merge button. Your branch's changes land in main.

**The terminology:**

- **Base branch** — the branch you're merging INTO. Usually `main`.
- **Compare branch** — your feature branch with the changes.
- **PR description** — you write what the change does and why, not just the title.

Here's a typical PR title and description:

```
Title: Add responsive navbar with dropdown support

Description:
Adds a sticky navbar with:
- Logo on the left
- Nav links in the center
- Dropdown menu for "Products" section
- Mobile hamburger menu (collapses on screens < 768px)

Closes #42
```

The `Closes #42` part links to an Issue. When the PR merges, that issue auto-closes. We'll cover that in Phase 5.

**What people get wrong:**

Thinking a PR is a fancy git merge. It's not. It's a collaboration tool built around a merge. The merge is the easy part. The review, discussion, and approval are the point.
