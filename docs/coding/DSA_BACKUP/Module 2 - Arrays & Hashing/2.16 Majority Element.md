**Problem:** Given an array `nums` of size `n`, return the majority element.

The **majority element** is the element that appears more than `n / 2` times. You may assume that the majority element always exists in the array.

**Link:** https://leetcode.com/problems/majority-element/

---

## What This Problem Is Asking (Simple Terms)

You have an array of numbers. You need to find the element that appears **more than half the time** — more than `n/2` occurrences.

For example, if `nums = [2,2,1,1,1,2,2]` (n=7), then `2` appears 4 times, which is more than `7/2 = 3.5`. So `2` is the majority element. (Read it as *n divided by 2*, not *n times 2* — with n=7, "more than 3.5" means at least 4 appearances.)

Two things the statement hands you:

- **Only one element can qualify.** If two numbers both appeared more than half the time, together they'd need more than `n` slots — impossible. So you never have to compare "who has the bigger frequency"; the moment a count crosses the halfway line, that's your answer.
- **A majority is guaranteed to exist.** You never handle a "none found" case (the final `return` in the code is only there to keep the compiler happy).

---

## Example 1

**Input:** `nums = [3,2,3]`

**Output:** `3`

**Explanation:** `3` appears 2 times, which is more than `n/2 = 1.5`.

---

## Example 2

**Input:** `nums = [2,2,1,1,1,2,2]`

**Output:** `2`

**Explanation:** `2` appears 4 times, which is more than `7/2 = 3.5`.

---

## Constraints

- `n == nums.length`
- `1 <= n <= 10^5`
- `-10^9 <= nums[i] <= 10^9`

**Follow-up:** Could you solve the problem in linear time and in O(1) space?

---

## Brute Force Approach (The Simplest Way)

Before optimizing, think like a beginner: how would you solve this by hand? Count how many times each element appears, then check which count exceeds `n/2`.

### Brute Force Pseudocode

```
for each element x in nums:
    count = 0
    for each element y in nums:
        if y == x: count++
    if count > n / 2: return x
return -1
```

### Why Brute Force Is Slow

The outer loop runs `n` times, and the inner loop runs `n` times for each outer iteration. That's O(n²) — too slow for `n = 10^5`.

---

## Which Data Structure, and Why?

Ask the two questions we use for every frequency problem: *how many times does each number appear?* and *based on that, what do I do?*

1. **HashMap** (value → count): count frequencies in one pass, then check which count crosses `n/2`. O(n) time, O(n) space. Simple, general — and the same loop you wrote for Top K Frequent.
2. **Boyer-Moore Voting Algorithm**: O(n) time, **O(1)** space — no map at all, just two variables. It exploits the fact that an element appearing more than half the time can "cancel out" everything else one-for-one.

The map approach answers the problem directly; Boyer-Moore is what the **follow-up** (O(1) space) is fishing for.

**Signal in the problem:** "appears more than n/2 times" / "majority element" → frequency count (HashMap), or Boyer-Moore if O(1) space is required.

## Optimized Approach 1: HashMap (Frequency Count — The One We Built)

**The plan:** walk the array, count every number into a map. Then loop over the map's entries — the moment any count is greater than `n/2`, return that key.

(Earlier brainstorm: you could track the max frequency while counting, then compare. But you answered that worry yourself — at most one number can cross the halfway line, so tracking a maximum is unnecessary. "First count above `n/2`" is the whole check.)

### Java Code

```java
class Solution {
    public int majorityElement(int[] nums) {
        Map<Integer, Integer> freq = new HashMap<>();
        int n = nums.length / 2;

        for (int i = 0; i < nums.length; i++) {
            freq.put(nums[i], freq.getOrDefault(nums[i], 0) + 1);
        }

        for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
            if (e.getValue() > n) return e.getKey();
        }

        return -1; // problem guarantees a majority — compiler needs this line
    }
}
```

### Line-by-line

- `int n = nums.length / 2` — the halfway line you compare each count against. (Division `/` — a common slip is `%`, the remainder operator, see Common Mistakes.)
- `freq.put(nums[i], freq.getOrDefault(nums[i], 0) + 1)` — the standard counting one-liner: `getOrDefault(key, 0)` returns the current count if the key exists, `0` if it's new; add 1; store it back. Same line as Top K Frequent.
- `for (Map.Entry<Integer, Integer> e : freq.entrySet())` — walking the map's entries. The header reads: capital `Map`, dot, `Entry`, then the pair of types `<Integer, Integer>`, then your variable, a colon, and `freq.entrySet()` (the set of entries). Each `e` is one key-value pair.
- `e.getValue() > n` — the count, as a **method call** (brackets required). `>` not `>=`: *more than* half.
- `return e.getKey()` — the **number itself**, not the count, not `n`.
- `return -1;` after the loop — unreachable in practice (a majority is guaranteed), but Java won't compile a method that might finish without returning.

**The trade-off:** O(n) time ✓ — but O(n) **space** for the map. The follow-up wants O(1). That's Approach 2.

## Optimized Approach 2: Boyer-Moore Voting (The Follow-up)

The notes' solution drops the map entirely: two variables, one pass.

### The Two Rules

Keep a `candidate` and a `count`. Walk the array once:

- **Rule 1 (switch rule):** if `count == 0`, the current number becomes the new `candidate`.
- **Rule 2 (tally rule):** then — if the current number equals the candidate, `count++`; if not, `count--`.

That's it. Return `candidate` at the end.

### The Idea: Votes Cancel Out

Think of each element as a vote. Every time a number *doesn't* match the candidate, it cancels one of the candidate's votes (count down). Every time it matches, the lead grows (count up). If the count ever hits zero, the old candidate has been **fully cancelled**, and the next number steps in as the new candidate.

Why does the majority survive? It holds **more than half** of all the votes — the other numbers, all combined, are *fewer* than half. They can't cancel it all the way out. So whatever is left standing at the end must be the majority.

**Memory hook:** *votes cancel out, and the majority can't be cancelled.*

### Traces (One Number at a Time)

**`[2,2,1]`:** first 2 → count 0, so candidate = 2, count → 1. Second 2 → matches, count → 2. Then 1 → doesn't match, count → 1. End: candidate **2**.

**`[1,2,2]`:** 1 becomes candidate (count 1). First 2 mismatches → count → 0. The 1 and the first 2 have **cancelled each other**. Now count is 0, so the third number (the second 2) becomes the new candidate, count → 1. End: candidate **2** — the leftover that survived.

**`[8,8,9,9,9,8,8]`** (same shape as the problem example, different numbers so candidate and count don't blur together):

| Step | x | count==0? | candidate | count | What happened |
|------|---|-----------|-----------|-------|---------------|
| 1 | 8 | yes | **8** | 1 | count was 0 → 8 becomes candidate; it matches itself → +1 |
| 2 | 8 | no | 8 | 2 | match → +1 |
| 3 | 9 | no | 8 | 1 | mismatch → −1. **Candidate does NOT switch** — the count wasn't 0 |
| 4 | 9 | no | 8 | 0 | mismatch → −1. The two 9s have cancelled the 8's two votes |
| 5 | 9 | yes | **9** | 1 | count *is* 0 → 9 becomes candidate; matches itself → +1 |
| 6 | 8 | no | 9 | 0 | mismatch → −1 |
| 7 | 8 | yes | **8** | 1 | count is 0 → 8 becomes candidate; matches → +1 |

End: candidate **8** — the majority. ✅

The key misread to avoid: the candidate does **not** switch at the *first* different number. It only switches when the count is actually zero — the first 9 only dropped the count 2 → 1, candidate stayed 8.

**Your own test — `[9,9,9,9,8,8]`:** count climbs to 4 after the four 9s. First 8 → 3, second 8 → 2. It never reaches zero, so the candidate **stays 9**, and you return 9 — reasoned out without any help.

One wording precision: the count goes *down toward zero*, never into negative numbers — the moment it hits zero, the next number takes over as candidate.

### Java Code (Full If-Else — The Clearer Version)

```java
class Solution {
    public int majorityElement(int[] nums) {
        int count = 0;
        int candidate = 0;

        for (int x : nums) {
            if (count == 0) candidate = x;   // Rule 1: switch when cancelled out
            if (candidate == x) {
                count++;                      // match → one more vote
            } else {
                count--;                      // mismatch → cancel one vote
            }
        }

        return candidate;
    }
}
```

### The Same Thing in One Line (The Notes' Version)

```java
count += (x == candidate) ? 1 : -1;
```

The `(condition) ? a : b` is the **ternary operator** — a tiny if-else: the parentheses hold the condition, the value after `?` is used when it's true, the value after `:` when it's false. So this says *if x equals the candidate add 1, otherwise add −1* — exactly your `count++` / `count--`, squeezed into one statement. The if-else is what you'd explain out loud in an interview; the ternary is the compact form you'll see in notes.

### Honest Expectations

This is a **published research algorithm** (Boyer–Moore), not something anyone invents from scratch in an interview room — struggling with it on first sight is completely normal. In an actual interview, the HashMap answer is a perfectly good response: linear time, correct, what most candidates give. Voting is the *bonus* for the O(1)-space follow-up, and interviewers usually expect to give a hint for it. What people really remember is the pattern ("count things → map") and then rebuild the details by tracing small examples — exactly what you did above.

## Complexity

- **HashMap:** O(n) time (two passes: one count, one map walk), O(n) space.
- **Boyer-Moore:** O(n) time (single pass), O(1) extra space — the follow-up's requirement.

---

## Common Mistakes

- **`%` instead of `/`:** `int n = nums.length % 2` gives the *remainder* (0 or 1), so the first number with a count above 0/1 "wins" — wrong. The halfway line is `nums.length / 2`. Percent and division are one character apart; this is a real bug that ran once.
- **`return -1` at the end of Boyer-Moore:** the answer is the survivor — `return candidate;`. (`-1` is only the HashMap version's compiler-pleaser.)
- **Forgetting the brackets / returning the wrong thing:** `e.getValue()` and `e.getKey()` are method calls; and you return the **key**, not the value and not `n`.
- **Switching the candidate too early:** the candidate changes only when `count == 0`. A different number with a nonzero count just decrements — it does not steal the candidacy.
- **Thinking the count goes negative:** it moves toward zero; at zero, the next number takes over.
- **"More than n/2" is strictly greater** — `> n/2`, not `>= n/2`. For n=4, threshold is >2, so 3+ occurrences.
- **Boyer-Moore without a guaranteed majority:** it finds a *candidate*. If the problem didn't guarantee a majority, you'd need a second pass to verify the count.
- **Assuming the array is sorted** — majority element problems don't guarantee sorted input.

## How to Explain (interview)

**Opening:** Majority Element asks for the value appearing more than n/2 times. The simple approach: count frequencies with a HashMap and return the first entry exceeding n/2 — O(n) time, O(n) space. For the O(1)-space follow-up, Boyer-Moore voting: keep a candidate and a count; count 0 → new candidate; match → +1, mismatch → −1. Votes cancel out, and the majority — holding more than half the votes — can never be fully cancelled, so it survives. O(n) time, O(1) space.

**The basic flow (Boyer-Moore):**
```java
int candidate = 0, count = 0;
for (int x : nums) {
    if (count == 0) candidate = x;
    if (candidate == x) count++; else count--;
}
return candidate;
```

(Compact form: `count += (x == candidate) ? 1 : -1;` — the ternary is just that if-else in one line.)

**The part that trips everyone up:** the candidate switches **only** when the count is zero — not at the first element that differs. And Boyer-Moore only works when a majority (> n/2) is **guaranteed**; otherwise verify with a second pass.

**The mistakes to remember:**
- `%` instead of `/` for the halfway line (HashMap version)
- `return -1` instead of `return candidate` (voting version)
- Switching candidate before the count reaches zero
- "More than n/2" means strictly greater — for n=4, need 3+ occurrences
