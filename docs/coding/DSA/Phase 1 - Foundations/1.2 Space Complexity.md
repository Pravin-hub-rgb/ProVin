In the previous topic we saw how much **time** code takes. But there's another thing that's equally important — **memory**.

Imagine you're building a project and your code loads 10GB of data into the browser. No matter how fast the time is, if memory fills up, it'll crash. Space complexity tells you how much **memory** your code will take.

---

## ✅ What is Space Complexity?

> **Space Complexity tells you how much extra memory your code takes as the size of the input grows.**

The word "extra" is important. Your input (array, string, etc.) always takes memory — that doesn't count. In space complexity we look at the **extra** memory the code creates.

---

## ✅ What takes memory?

### 1. Variables — the most basic

```js
let count = 0;           // 1 unit of space
let name = "Vin";        // 1 unit of space
let total = count + 10;  // 1 unit of space
```

Every variable = one unit of space. Simple.

---

### 2. Arrays / Objects — proportional to size

```js
let arr = [1, 2, 3, 4, 5];  // n units (where n = 5)
let obj = { a: 1, b: 2 };   // k units (where k = number of keys)
```

An array's space = how many elements it has. An object's space = how many key-value pairs it has.

---

### 3. Loops — usually O(1)

```js
function sum(arr) {
  let total = 0;              // 1 unit
  for (let i = 0; i < arr.length; i++) {  // i = 1 unit (reused)
    total += arr[i];          // total already exists
  }
  return total;
}
// Total extra space = O(1) — just the 'total' and 'i' variables
// No new array is created inside the loop
```

**Key insight:** No extra array is created inside the loop, so space is O(1). Space complexity only grows when you create a **new data structure**.

---

### 4. Creating a new array = O(n)

```js
function doubleElements(arr) {
  let doubled = [];                    // new array
  for (let i = 0; i < arr.length; i++) {
    doubled.push(arr[i] * 2);          // store n elements
  }
  return doubled;
}
// Space = O(n) — a new array of size n
```

When you create a new array/object inside a function that's proportional to the input, the space is O(n).

---

## ✅ Auxiliary Space vs Total Space

- **Total Space** = input + all extra combined
- **Auxiliary Space** = only the extra memory (what the code created)

In interviews, mostly **auxiliary space** is asked. Reason: the input always takes space; what matters is what your code adds on top.

**Example:**
```js
function findMax(arr) {    // arr = input, already exists
  let max = arr[0];        // auxiliary: 1 variable = O(1)
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] > max) max = arr[i];
  }
  return max;
}
// Auxiliary Space: O(1)
// Total Space: O(n) — because the input array is also in memory
```

---

## ✅ Recursion = Hidden Space Cost

This is the most important concept in space complexity.

```js
function factorial(n) {
  if (n === 0) return 1;
  return n * factorial(n - 1);
}
```

When you call `factorial(5)`:
- `factorial(5)` is called — pushed onto stack
- `factorial(4)` is called — pushed onto stack
- `factorial(3)` is called — pushed onto stack
- `factorial(2)` is called — pushed onto stack
- `factorial(1)` is called — pushed onto stack

They don't run one after another — they're **all in memory at once** until the base case is hit. That's why recursion's space complexity is O(n).

```
On the stack:
┌─────────────┐
│ factorial(5) │
│ factorial(4) │
│ factorial(3) │
│ factorial(2) │
│ factorial(1) │
└─────────────┘
```

**Every recursive call = one stack frame = one unit of space**

---

## ✅ Space Complexity Patterns

| Pattern | Space | Example |
|---------|-------|---------|
| Only variables | O(1) | `let max = arr[0]` |
| New array/object | O(n) | `let doubled = []` |
| Recursion (depth n) | O(n) | `factorial(n)` |
| Recursion (depth log n) | O(log n) | Recursive Binary Search |
| 2D array / matrix | O(n²) | `let grid = Array(n).fill().map(() => Array(n))` |

---

## ✅ Time vs Space — When to prefer which?

Sometimes you have to **trade off** — save time or save space.

**Space-optimized example:**
```js
// Naive approach — O(n) space
function hasPairWithSum(arr, target) {
  let seen = [];                    // new array
  for (let num of arr) {
    if (seen.includes(target - num)) return true;
    seen.push(num);
  }
  return false;
}

// Optimized — O(1) space (two pointer, assuming sorted array)
function hasPairWithSumSorted(arr, target) {
  let left = 0, right = arr.length - 1;
  while (left < right) {
    let sum = arr[left] + arr[right];
    if (sum === target) return true;
    if (sum < target) left++;
    else right--;
  }
  return false;
}
```

The first approach takes O(n) space (seen array). The second takes O(1) space — just 2 variables. The second is better on space.

**But** — if the array isn't sorted, the second approach won't work. Sometimes you have to spend space.

**Interview rule of thumb:** First optimize time (O(n) to O(log n) or O(1)), then optimize space if the interviewer asks.

## ✅ Common Interview Traps

**Trap 1: String concatenation in a loop**
```js
function buildString(n) {
  let result = "";
  for (let i = 0; i < n; i++) {
    result += "a";  // creates a new string every time
  }
  return result;
}
// Space: technically O(n²) — because every concatenation creates a new string
// But JS engine optimizes it, practically O(n)
```

**Trap 2: Spread operator / slice**
```js
let arr = [1, 2, 3, 4, 5];
let copy = [...arr];    // O(n) space — new array created
let slice = arr.slice(); // O(n) space — same
```

**Trap 3: Objects as function params**
```js
function process(obj) {
  // obj is a reference, not a copy
  // Space = O(1) extra
}

function process(obj) {
  let newObj = { ...obj };  // O(n) — spread creates a copy
  // Space = O(n)
}
```

---

## ✅ What It Is NOT

- **Space complexity isn't only about arrays.** Variables, recursion stack, temporary objects — everything takes memory. Everything created inside the function counts.
- **O(1) space doesn't mean zero memory.** O(1) means constant — no matter how big the input, extra memory stays the same. 1 variable or 10 — O(1) because it doesn't depend on input.
- **Recursion always takes space.** Every recursive call creates a stack frame. If recursion depth is n, space is O(n). That's why sometimes the iterative approach is better on space.
- **Space and Time are separate.** A code can be O(n) time and O(1) space (single loop, no extra array). A code can be O(n) time and O(n) space (loop + new array). Both get analyzed separately.

**In Your Own Words**

1. You write a function that takes an array and returns a new array with every element doubled. What's the space complexity, and why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It's O(n) because you're creating a new array proportional to the input array. The input array's space is the input (not counted), but the new `doubled` array stores n elements — that's your extra space. So auxiliary space is O(n).

</details>

2. Your function makes 100 recursive calls (depth 100). Only one variable is created per call. What's the space complexity?

<details>
<summary>Show Answer</summary>

**Sample Answer:** O(100) = constant — it doesn't depend on input. But if recursion depth is proportional to input (like factorial(n)), then space is O(n). In general, recursion space = recursion depth. Here 100 is fixed, so technically O(1). But usually recursion depth depends on n, so space is O(n).

</details>

3. Two functions: Function A creates a new array the same size as the input. Function B uses only 2 variables. Both have O(n) time complexity. Which is better and why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Function B is better on space. Both have O(n) time (same), but Function A has O(n) space (new array) and Function B has O(1) space (just 2 variables). If the interviewer says "optimize for space," choose Function B. But if Function A's new array is the required result, you have to spend that space.

</details>

4. What's the space complexity of recursive Binary Search? And of iterative?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Recursive Binary Search is O(log n) — because recursion depth is log n (each call eliminates half the data). Iterative Binary Search is O(1) — just `left`, `right`, `mid` variables, no recursion. That's why the iterative approach is better on space.

</details>

5. How do you decide whether to use object spread (`{...obj}`) or not?

<details>
<summary>Show Answer</summary>

**Sample Answer:** If you don't want to modify the original object (immutability needed), use spread — O(n) space but safe. If the original object can be used directly (or you want a reference), don't — O(1) space saved. In React, props aren't mutated, so spread is common. In DSA, you usually want to save space, so avoid it unless necessary.

</details>
