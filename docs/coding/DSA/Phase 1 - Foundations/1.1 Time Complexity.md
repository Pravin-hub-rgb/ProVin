When you order on Zomato, it shows you a "delivery time" — 20 min, 35 min, 1 hour. You don't know the exact number of minutes the food will take, but you get an **estimate** of whether it'll take long or short. Based on that, you decide — "should I order this or not."

In DSA, the same thing happens. You don't know the exact milliseconds the code will take to run. But you need an **estimate** of whether it'll work on 10 elements or on 10 lakh elements. That's Time Complexity — the "delivery time" estimate for your code.

---

## ✅ What is Time Complexity?

> **Time Complexity tells you how many steps your code will take as the size of the input grows.**

Just like Zomato's delivery time depends on the order complexity (just chai = fast, biryani + 5 sides = slow), the time your code takes depends on how big the input is.

**Important:** We don't calculate exact time (in seconds/ms). We say — "if the input becomes 2x, how many times will the steps grow?" That's what Big O tells you.

### Proper Definition

> **Time Complexity of an algorithm is a function, T(n), that measures how the running time grows as the size of the input, n, increases. It's expressed in terms of the number of operations (or steps) the algorithm performs — not in seconds — so it stays meaningful no matter which machine runs it.**

That's the textbook version. Let me unwrap it so it actually lands:

- **"Function T(n)"** is just fancy talk for: *tie the input size `n` to the amount of work done.* How much work, relative to the input — that's all it is.
- **"Number of operations, not seconds"** means we count steps (like each loop iteration), not milliseconds. Why? Because seconds depend on the hardware — a fast laptop runs the same code way faster than a slow phone. But the *count of steps stays the same* on both. So counting steps is the honest measure; counting seconds is noisy.
- **Back to Zomato:** delivery time depends on the *order* (chai fast, 5 sides slow), not on which delivery guy happens to be fastest today. Same idea — time depends on *input size (n)*, not on the machine.

---

## ✅ What is Big O?

Big O notation is an **upper bound** — the worst case for how much time it'll take.

Imagine you need to find a name in a 100-name phone book. If you check **one by one**, that's O(n). If you **open the page directly** where the name is, that's O(1).

Big O tells you how **efficient** an approach is compared to other approaches.

---

## ✅ Common Time Complexities (memorize these)

### O(1) — Constant Time

One task, whether the input is 1 or 1 crore — same time.

```js
function getFirst(arr) {
  return arr[0]; // just fetch the first element
}

// 10 elements or 10 crore — single step
```

**Real life:** You remembering your phone number — one step, always the same time.

---

### O(n) — Linear Time

Bigger input means proportionally more steps. One task per element.

```js
function findMax(arr) {
  let max = arr[0];
  for (let i = 1; i < arr.length; i++) {  // runs n times
    if (arr[i] > max) {
      max = arr[i];
    }
  }
  return max;
}

// 10 elements = 10 steps
// 1000 elements = 1000 steps
```

**Real life:** You scrolling through your old messages — more messages means more time.

---

### O(n²) — Quadratic Time

A loop inside a loop — nested loops. The inner loop runs for every element of the outer loop.

```js
function hasDuplicate(arr) {
  for (let i = 0; i < arr.length; i++) {        // n times
    for (let j = i + 1; j < arr.length; j++) {  // n times for each i
      if (arr[i] === arr[j]) return true;
    }
  }
  return false;
}

// 10 elements = 100 steps (10 x 10)
// 100 elements = 10,000 steps
```

**Real life:** Pairing every student in a class with every other student — n(n-1)/2 pairs. As students grow, pairs grow exponentially.

---

### O(log n) — Logarithmic Time

Half the work is eliminated at every step. The binary search pattern.

```js
function binarySearch(arr, target) {
  let left = 0;
  let right = arr.length - 1;

  while (left <= right) {
    let mid = Math.floor((left + right) / 2);
    if (arr[mid] === target) return mid;
    if (arr[mid] < target) left = mid + 1;
    else right = mid - 1;
  }
  return -1;
}

// 1000 elements = max ~10 steps
// 1,000,000 elements = max ~20 steps
```

**Real life:** Looking up a word in a dictionary — go near "M", then near "Ma", then near "Mar" — half eliminated each time. A 1000-page dictionary in max 10 steps.

---

### O(n log n) — Linearithmic Time

Most efficient sorting algorithms (Merge Sort, Quick Sort average case).

```js
// Merge Sort — n work per level, log n levels
// Total = n x log n

// 10 elements ≈ 33 steps
// 100 elements ≈ 664 steps
// 1000 elements ≈ 9966 steps
```

**Real life:** Splitting 50 students into pairs, then groups of 4, then groups of 8 — at each level you talk to everyone (n), and there are log n levels.

---

## ✅ The Cheat Sheet

| Big O | Name | When it happens | Example |
|-------|------|-----------------|---------|
| O(1) | Constant | Work done in one step | Accessing the first element of an array |
| O(log n) | Logarithmic | Half eliminated per step | Binary Search |
| O(n) | Linear | One loop, work per element | Find max in array |
| O(n log n) | Linearithmic | Sorting efficiently | Merge Sort |
| O(n²) | Quadratic | Nested loops | Compare every pair |
| O(2^n) | Exponential | 2 choices per element | Generating subsets (recursion) |

**Remember:** O(1) > O(log n) > O(n) > O(n log n) > O(n²) — first is best, last is worst.

## ✅ How to Analyze Code?

**Rule 1: Single loop = O(n)**
```js
for (let i = 0; i < n; i++) {
  // O(n)
}
```

**Rule 2: Nested loop = O(n²)**
```js
for (let i = 0; i < n; i++) {
  for (let j = 0; j < n; j++) {
    // O(n²)
  }
}
```

**Rule 3: Loop that halves = O(log n)**
```js
while (left <= right) {
  let mid = Math.floor((left + right) / 2);
  // ...
  left = mid + 1; // or right = mid - 1
  // Half eliminated per step — O(log n)
}
```

**Rule 4: Ignore constants**
```js
// This is also O(n), not O(2n)
for (let i = 0; i < n; i++) {
  console.log(i);
}
for (let j = 0; j < n; j++) {
  console.log(j);
}

// Both are separate O(n), but constants aren't kept in Big O
```

**Rule 5: Different variables = different scales**
```js
// O(n + m) — n and m are different sizes
for (let i = 0; i < n; i++) { }
for (let j = 0; j < m; j++) { }

// O(n × m) — nested, different sizes
for (let i = 0; i < n; i++) {
  for (let j = 0; j < m; j++) { }
}
```

---

## ✅ Worst case vs Best case

A simple example:
```js
function linearSearch(arr, target) {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === target) return i;
  }
  return -1;
}
```

- **Best case:** Target is the first element — O(1)
- **Worst case:** Target is last or not present — O(n)
- **Average case:** Roughly O(n/2), which simplifies to O(n)

In interviews, **worst case** is mostly what's asked. That's the standard.

---

## ✅ What It Is NOT

- **Big O doesn't give exact time.** It tells you the trend — how time grows as input grows. Not 2 seconds or 20 seconds, but "linearly" or "quadratically."
- **O(n²) isn't always bad.** If n is very small (10 or 20 elements), O(n²) is fine too. Big O matters when n is large.
- **Constants don't matter.** O(2n) = O(n), O(100n) = O(n). Reason: when n is 1 crore, the factor of 2 or 100 doesn't matter — both are "linear."
- **Space and Time are separate.** Time complexity tells you how many steps; space complexity tells you how much memory. Both get analyzed separately (we'll cover space next).

**In Your Own Words**

1. You need to find the largest number in an array. You wrote a loop that checks every element. What's the time complexity, and why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It's O(n) because you visit every element of the array once. The larger the input (n), the more steps. There's no shortcut — you have to check everything since any of them could be the largest.

</details>

2. You have two arrays — one of size n and one of size m — and you compare every element of one with every element of the other. What's the time complexity?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It's O(n × m). Because you're using nested loops — the first runs n times, and for each of those the second runs m times. Total steps = n × m. If both arrays are the same size (n = m), you can say O(n²).

</details>

3. Why is Binary Search so much faster than Linear Search?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Binary Search eliminates half the data at every step. Linear Search checks one by one. In 1 million elements, Linear Search takes up to 1 million steps, Binary Search takes ~20 steps. That's an exponential difference — like opening a page directly in a phone book vs reading every page.

</details>

4. If code has 3 separate loops (not nested) all running over n elements, what's the overall time complexity?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It's O(n). Because constants are ignored in Big O. 3 separate loops = O(3n) = O(n). As input grows, each loop grows linearly, and so does the total.

</details>

5. You have a function that first sorts an array (O(n log n)) and then runs a loop over it (O(n)). What's the total time complexity?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It's O(n log n). Because the sort (n log n) dominates the loop (n). In Big O, you keep only the largest term and drop the smaller ones. Same logic: if you had O(n²) + O(n), you'd write O(n²).

</details>
