## Mini Quiz

1. Why does LRU Cache need both a HashMap and a doubly linked list?
2. What are the O(1) operations in LRU Cache, and how is each achieved?
3. What is the LinkedHashMap shortcut for LRU Cache?
4. How do you handle the case where `put` is called with an existing key?
5. What happens when capacity is 0?

<details>
<summary>Show Answer</summary>

**Sample Answers:**
1. HashMap gives O(1) lookup by key. Doubly linked list gives O(1) insert/remove/reorder. HashMap alone: O(1) lookup but O(n) eviction (must scan for LRU). Linked list alone: O(1) reorder but O(n) lookup. Combining both gives O(1) for all operations.
2. get: HashMap lookup (O(1)) + move node to head (O(1) with doubly linked list). put: HashMap lookup (O(1)) + update value + move to head (O(1)) or evict LRU (O(1): remove from tail + remove from map) + add new (O(1)). All O(1).
3. `LinkedHashMap` with `accessOrder = true` automatically moves accessed entries to the end. Override `removeEldestEntry` to evict when size > capacity. This gives LRU in ~5 lines. But interviews expect the manual version.
4. Update the value in the existing node and move it to head (mark as recently used). Do NOT create a new node or evict.
5. With capacity 0, every `put` immediately evicts. The implementation should handle this: if capacity == 0, `put` does nothing (or evicts immediately). Check the problem constraints — usually capacity ≥ 1.

</details>

## One-Page Cheat Sheet

**LRU Cache (manual):**
```java
class LRUCache {
    int capacity;
    Map<Integer, Node> map = new HashMap<>();
    Node head = new Node(0,0), tail = new Node(0,0); // dummies

    // constructor: link head <-> tail
    // get: lookup, moveToHead, return val (or -1)
    // put: if exists, update + moveToHead; else if full, evict LRU (tail.prev), add new at head
    // addToHead, remove, moveToHead: O(1) doubly linked list ops
}
```

**LRU Cache (LinkedHashMap shortcut):**
```java
class LRUCache extends LinkedHashMap<Integer, Integer> {
    private final int capacity;
    public LRUCache(int capacity) {
        super(capacity, 0.75f, true); // accessOrder = true
        this.capacity = capacity;
    }
    protected boolean removeEldestEntry(Map.Entry<Integer, Integer> e) {
        return size() > capacity;
    }
}
```

**Design problem approach:**
1. Identify the operations and their required time complexities.
2. Pick a data structure for each operation (HashMap for O(1) lookup, linked list for O(1) reorder, heap for O(log n) min/max).
3. Combine them so every operation meets its target.
4. Handle edge cases (capacity 0, empty, duplicates).

## In Your Own Words

1. Why does LRU Cache need both a HashMap and a doubly linked list?

<details>
<summary>Show Answer</summary>

**Sample Answer:** HashMap gives O(1) lookup by key. Doubly linked list gives O(1) insert, remove, and reorder (move to head). HashMap alone: O(1) lookup but O(n) eviction (must scan for LRU). Linked list alone: O(1) reorder but O(n) lookup. Combining both: every operation (get, put, evict) is O(1). The HashMap maps key → node; the list maintains recency order.

</details>

2. What is the difference between LRU and LFU cache?

<details>
<summary>Show Answer</summary>

**Sample Answer:** LRU (Least Recently Used) evicts the item that hasn't been accessed for the longest time. LFU (Least Frequently Used) evicts the item with the fewest accesses (ties broken by recency). LRU is simpler (HashMap + doubly linked list). LFU is harder (needs frequency buckets + doubly linked lists per frequency). LRU is more common in interviews.

</details>

3. When would you use LinkedHashMap instead of building from scratch?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In production code, `LinkedHashMap` with `accessOrder = true` gives LRU behavior in a few lines. In interviews, build from scratch to demonstrate understanding of the underlying data structures (HashMap + doubly linked list). Know both: the shortcut for real code, the manual version for interviews.

</details>
