**Problem:** Given an array of integers `nums` and an integer `target`, return indices of the two numbers such that they add up to `target`.

You may assume that each input would have exactly one solution, and you may not use the same element twice.

You can return the answer in any order.

**Link:** https://leetcode.com/problems/two-sum/

---

## What This Problem Is Asking (Simple Terms)

You have an array of integers and a target number. You need to find **two different positions** (indices) in the array where the numbers at those positions add up to the target.

The array is **not sorted**. You cannot use the same element twice (same index). There is exactly one valid answer.

---

## Example 1

**Input:** `nums = [2, 7, 11, 15]`, `target = 9`

**Output:** `[0, 1]`

**Explanation:** `nums[0] + nums[1] = 2 + 7 = 9`, which equals the target. Therefore, indices `[0, 1]` are returned.

---

## Example 2

**Input:** `nums = [3, 2, 4]`, `target = 6`

**Output:** `[1, 2]`

**Explanation:** `nums[1] + nums[2] = 2 + 4 = 6`, which equals the target. Therefore, indices `[1, 2]` are returned.

---

## Example 3

**Input:** `nums = [3, 3]`, `target = 6`

**Output:** `[0, 1]`

**Explanation:** `nums[0] + nums[1] = 3 + 3 = 6`, which equals the target. Therefore, indices `[0, 1]` are returned.

---

## Constraints

- `2 <= nums.length <= 10^4`
- `-10^9 <= nums[i] <= 10^9`
- `-10^9 <= target <= 10^9`
- Only one valid answer exists.

**Follow-up:** Can you come up with an algorithm that is less than O(n²) time complexity?

---

## Brute Force Approach (The Simplest Way)

Before optimizing, let's think like a beginner: how would you solve this by hand?

You stand at index `0` (value `2` in Example 1). You need a partner that adds to `target` (`9`). The partner would be `9 - 2 = 7`. So you scan the rest of the array looking for `7`. You find `7` at index `1`. Done!

If not found at index `0`, you move to index `1` and scan again from index `2`. And so on.

This is a **loop inside a loop**:
- Outer loop: pick each element as the first number
- Inner loop: scan all elements after it looking for the complement

### Brute Force Pseudocode

```
for i from 0 to n-1:
    for j from i+1 to n-1:
        if nums[i] + nums[j] == target:
            return [i, j]
return []
```

### Why Brute Force Is Slow

With `n` elements, the outer loop runs `n` times, and the inner loop runs up to `n` times for each outer iteration. That's about `n × n = n²` operations. For `n = 10^4`, that's `10^8` operations — too slow.

---

## Which Data Structure, and Why?

You learned in 2.8 that a **HashSet** answers: "Have I seen this value before?" → yes/no.

For Two Sum, that's **not enough**. Here's why:

When you're at index `i` with value `nums[i]`, you compute the complement: `target - nums[i]`. You ask: "Have I seen this complement before?"

If you use a **HashSet**, it tells you yes or no. But even if it says "yes," you don't know **where** (which index) the complement appeared. You'd have to scan the array again to find that index — a second traversal, defeating the purpose.

So you need a **HashMap**, which stores `value → index`. When you look up the complement, you get not just "yes" but also the exact index where it appeared.

**HashMap answers:** "Have I seen this key? And if yes, what index was it at?" → yes/no + the index.

**Why `value → index` (not `index → value`)?** Because you look up by **value** and retrieve by **index**. The key in a HashMap is what you search with; the value is what you get back. You search: *"have I seen this complement value before?"* → key = value. You want to know: *"where was it seen?"* → value = index. If you stored `index → value` instead, you'd be looking up by index, which tells you nothing about whether a complement value exists anywhere in the array. So `value → index` is the only mapping that lets you ask both questions in O(1): *"have I seen this value?"* (key lookup) → *"where?"* (value retrieval).

## Building the Logic Step by Step

Let's work through how you actually arrive at the HashMap solution, step by step — just like thinking through it in real time.

### Step 1: The Brute Force (Already Covered)

You start with the obvious approach: for each element, scan the rest of the array looking for its complement (`target - nums[i]`). This gives O(n²) time — too slow for n = 10⁵.

### Step 2: "I Need a Way to Remember What I've Seen"

You're walking through the array one element at a time. At each element `nums[i]`, you need its **complement**: `target - nums[i]`. You ask yourself: *"Have I seen this complement value before?"*

So now you're asking: **"What data structure lets me quickly check if I've seen a value before?"**

### Step 3: First Idea — HashSet

You remember: a HashSet answers "have I seen this value before?" in O(1). So you think: *"Great, I'll put everything in a HashSet!"*

But here's the problem: a HashSet only tells you **yes or no** — *"yes, I've seen 7"* or *"no, I haven't seen 4"*. It doesn't tell you **where** (which index) you saw it.

**So HashSet alone isn't enough.** You need the index of the complement, not just whether it exists.

### Step 4: HashMap — Value → Index

You need to ask: *"Have I seen this complement value before? And if yes, what index was it at?"*

So you use a **HashMap** that stores `value → index`:
- **Key** = the number (what you look up)
- **Value** = its index (what you get back)

Now when you check `containsKey(complement)`, you get **yes/no**. And if yes, you can call `get(complement)` to get back the index where that complement appeared.

### Why `value → index` (not `index → value`)?

Because you look up by **value** and retrieve by **index**. You search: *"have I seen this complement value?"* → key = value. You want to know: *"where was it seen?"* → value = index.

If you stored `index → value` instead, you'd be looking up by index, which tells you nothing about whether a complement value exists anywhere in the array.

**So `value → index` is the only mapping that lets you ask both questions in O(1):**
- "Have I seen this value?" → key lookup
- "Where was it seen?" → value retrieval

### Step 5: The Crucial Insight — Check First, Then Store

Now here's the key insight you discovered:

You process elements one by one from left to right. For each element `nums[i]`:

1. First, calculate `complement = target - nums[i]`
2. Check: have I already seen `complement`? (i.e., is it already in the HashMap?)
3. **If yes** → you found the pair! Return `[seen[complement], i]` — where `seen[complement]` is the earlier index and `i` is your current index.
4. **If no** → store `nums[i] → i` in the HashMap for future lookups

**Why check first, then store?** Because you must not match a number with itself. If you stored `nums[i]` first and then checked, `nums[i] + nums[i] = target` would match itself (same index), which is not allowed.

By checking first, then storing, you guarantee you're always pairing the current element with one you've already seen (a strictly earlier index).

## Optimized Approach (One Pass with HashMap)

Instead of a second traversal, store each value and its index in a HashMap as you go:

1. Start with an empty HashMap
2. For each element at index `i`:
   - Compute `complement = target - nums[i]`
   - Check if `complement` is already in the map
   - If yes: return `[map[complement], i]` — you found the pair
   - If no: store `nums[i] → i` in the map for future lookups
3. Continue until found

### Why This Is O(n)

You traverse the array **once**. Each HashMap operation (`put`, `get`, `containsKey`) is O(1) average. So total time is O(n), space is O(n) for the map.

### Pseudocode

```
seen = empty map (value -> index)   // stores: number -> its index
for i from 0 to n-1:                // i = current index
    complement = target - nums[i]   // the value we need to find
    if seen contains complement:
        return [seen[complement], i]  // seen[complement] = earlier index; i = current index
    seen[nums[i]] = i               // store current value -> current index for future lookups
return []
```

### Java Code

```java
class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>(); // value → index

        for (int i = 0; i < nums.length; i++) {
            int complement = target - nums[i];
            if (seen.containsKey(complement)) {
                return new int[]{seen.get(complement), i};
            }
            seen.put(nums[i], i);
        }
        return new int[]{};
    }
}
```

### Line-by-line

- `seen` maps a value to the index where it appeared.
- For each element, `complement = target - nums[i]` is the value we need.
- `seen.containsKey(complement)` — O(1) check. If true, we found the pair.
- `seen.get(complement)` gives the earlier index; `i` is the current index.
- `seen.put(nums[i], i)` records current value for future complements.
- Return `new int[]{a, b}` — array literal. If no solution (shouldn't happen per problem), return empty.

## Complexity

- Time: O(n) — single pass, O(1) map ops.
- Space: O(n) — map stores up to n entries.

## Common Mistakes

- Returning **values** instead of **indices**.
- Assuming the array is sorted (that's Two Sum II).
- Using `==` for comparison (not relevant here, but habit).
- Forgetting that `get` returns null — use `containsKey` first.
- Storing after checking (always check first, then store, so an element doesn't match itself).

## How to Explain (interview)

**Opening:** Two Sum asks for two indices whose values sum to a target. The brute force checks every pair in O(n²) — a loop inside a loop. The optimized version walks the array once, using a HashMap to remember each value's index. For each element, compute the complement (target minus current value) and check if it's already in the map — if yes, return both indices; if no, record the current value and move on. O(n) time, O(n) space.

**The basic flow:**
```java
Map<Integer, Integer> seen = new HashMap<>();
for (int i = 0; i < nums.length; i++) {
    int complement = target - nums[i];
    if (seen.containsKey(complement)) return new int[]{seen.get(complement), i};
    seen.put(nums[i], i);
}
```

**The part that trips everyone up:** the problem wants **indices**, not the values themselves. Also the input is **not sorted** — don't try binary search. And you must check the map **before** storing, so an element doesn't match itself.

**The mistakes to remember:**
- Returning values instead of indices
- Assuming the array is sorted
- Forgetting the null check on `get` (use `containsKey`)
- Storing before checking (element matches itself)
