**Problem:** Given an integer array `nums`, find the **contiguous subarray** (containing at least one number) which has the largest sum, and return its sum.

A **subarray** is a contiguous part of an array.

**Link:** https://leetcode.com/problems/maximum-subarray/

---

## What This Problem Is Asking (Simple Terms)

You have an array of numbers (some positive, some negative). You need to find a contiguous segment (subarray) whose sum is the largest possible.

For example, if `nums = [-2,1,-3,4,-1,2,1,-5,4]`, the subarray `[4,-1,2,1]` has sum 6, which is the largest.

You are **not** asked to return the subarray itself — just its sum. (First confusion to clear: "do we have to return the subarray also? We just have to return the sum." Yes — you never need to store or rebuild the subarray, only track its sum.)

---

## Example 1

**Input:** `nums = [-2,1,-3,4,-1,2,1,-5,4]`

**Output:** `6`

**Explanation:** `[4,-1,2,1]` has the largest sum = 6.

---

## Example 2

**Input:** `nums = [1]`

**Output:** `1`

**Explanation:** The subarray is `[1]` with sum 1.

---

## Example 3

**Input:** `nums = [5,4,-1,7,8]`

**Output:** `23`

**Explanation:** The whole array `[5,4,-1,7,8]` has sum 23.

## Brute Force Approach (The Simplest Way)

Before optimizing, think like a beginner: how would you solve this by hand? You could check every possible subarray:
- Start at index 0: compute sum of [0], [0,1], [0,1,2], ...
- Start at index 1: compute sum of [1], [1,2], [1,2,3], ...
- And so on...

### Brute Force Pseudocode

```
maxSum = -infinity
for i from 0 to n-1:
    sum = 0
    for j from i to n-1:
        sum = sum + nums[j]
        if sum > maxSum: maxSum = sum
return maxSum
```

### Why Brute Force Is Slow

The outer loop runs `n` times, and the inner loop runs up to `n` times for each outer iteration. That's about `n × n = n²` operations. For `n = 10^5`, that's `10^10` operations — too slow.

---

## Which Data Structure, and Why?

You need the maximum sum of a contiguous subarray. The naive approach checks all subarrays → O(n²). The optimized approach: **Kadane's algorithm** — track a running sum; if it goes negative, it's a burden — drop it and start fresh. No complex data structure — just two variables (`currentSum`, `maxSum`). No map, no set, no rebuilding the subarray.

The insight: a negative running sum can only reduce any future subarray, so discard it and start over.

**Signal in the problem:** "maximum subarray sum" / "contiguous subarray with largest sum" → Kadane's algorithm. If the problem asks for the subarray itself (indices), track start/end too.

---

## The Hand Walk: Drop the Burden

Trace `[-2,1,-3,4,-1,2,1,-5,4]` by hand first. Two variables: `currentSum` (running total of the stretch you're in) and `maxSum` (the best total ever seen). The rule at each step: **add the number; if the running sum has gone negative, it's a burden — drop it to 0 so the next number starts fresh.**

| Step | x | currentSum after add | max check | reset? | currentSum after reset | maxSum |
|------|---|----------------------|-----------|--------|------------------------|--------|
| 1 | -2 | -2 | -2 beats MIN_VALUE → | yes (burden) | 0 | -2 |
| 2 | 1 | 1 | beats -2 → | no | 1 | 1 |
| 3 | -3 | -2 | no | yes (burden) | 0 | 1 |
| 4 | 4 | 4 | beats 1 → | no | 4 | 4 |
| 5 | -1 | 3 | no | no | 3 | 4 |
| 6 | 2 | 5 | beats 4 → | no | 5 | 5 |
| 7 | 1 | 6 | beats 5 → | no | 6 | **6** |
| 8 | -5 | 1 | no | no | 1 | 6 |
| 9 | 4 | 5 | no | no | 5 | 6 |

Two beats from the live trace worth keeping:

- After step 3's `-2`, the sum is a burden, you drop it — and **step 4's `4` starts a fresh running sum of 4.** That's the whole reset idea in one move.
- The running sum peaks at **6** at step 7, then falls to 1, then climbs back to 5 — **it never gets back to 6.** A common slip while tracing by hand is thinking the final `4` returns the sum to 6; check the arithmetic: `1 + 4 = 5`. The *best* stays 6 forever because `maxSum` never goes down.

## Approach 1: The Branching Version (Built Live — 1 ms, Beats 99.98%)

This is the version written and submitted in the session. Three steps per number, in this exact order: **add → max check → reset check.**

### Java Code

```java
class Solution {
    public int maxSubArray(int[] nums) {
        int currentSum = 0;
        int maxSum = Integer.MIN_VALUE;
        for (int i = 0; i < nums.length; i++) {
            currentSum += nums[i];
            if (currentSum > maxSum) {
                maxSum = currentSum;
            }
            if (currentSum < 0) {
                currentSum = 0;
            }
        }
        return maxSum;
    }
}
```

### The Decisions Behind the Declarations

- **`currentSum = 0`** — before touching any number, the running total of "nothing added yet" is zero. With add-first, the first number simply lands on this zero.
- **`maxSum = Integer.MIN_VALUE`** — *not* `0`. You spotted this trap yourself before writing the code: if you start `maxSum` at zero and the array is all negatives, the zero "will be bigger" than any real sum, so you'd return `0` instead of the actual answer. `Integer.MIN_VALUE` (the smallest possible int) means any real sum beats it. Starting at `nums[0]` is the other valid choice.
- **Names after what they hold** — `currentSum` for the running total, `maxSum` for the best seen. (Your submission spelled it `maxsum` — consistent throughout, so it compiled fine; pick one spelling and keep it.)

### Line-by-line

- `currentSum += nums[i];` — first move: add the current number to the running sum (`currentSum = currentSum + nums[i]`, short form).
- `if (currentSum > maxSum) maxSum = currentSum;` — second move: did this step beat the best total ever? Keep the bigger.
- `if (currentSum < 0) currentSum = 0;` — third move: if the running sum has gone negative, **reset only `currentSum`** — drop the burden so the next number starts fresh.
- `return maxSum;` — the winner.

### Why Two Separate `if`s — Not `else if`

The checks are **independent**: one asks whether to update the best, the other whether to reset. An `else if` would skip the second check whenever the first fires — and in the all-negative case the first check *does* fire on a negative sum, so the reset would be skipped and the burden would keep dragging along.

### Why the Order Is add → max → reset

The **max check must come before the reset.** Think `[-3]`: add → `currentSum = -3`. Max check: `-3` beats `Integer.MIN_VALUE` → `maxSum = -3`. *Then* reset: `currentSum = 0`. Return `-3` — correct. If you reset first, the sum becomes `0` before the max check, and you'd return `0` — wrong for an all-negative array.

### Why `maxSum` Is Never Reset

Live mistake, caught in the session: *"in reset we would reset both the max sum also and current sum also."* No — **only `currentSum` gets reset.** `maxSum` is the memory of the best total you've ever seen, and it has to survive after you drop a bad stretch. In the trace, the running sum went to 6 and then dropped — if you reset `maxSum` too, you'd lose that 6.

### Sanity Check: All-Negative

`[-3]`: sum becomes -3, max becomes -3 (it beats MIN_VALUE), then sum resets to 0. Returns **-3** — the right answer for a single negative. This is the case that breaks the `maxSum = 0` initialization.

**Result: submitted — 1 ms, beating 99.98%.**

## Approach 2: The Compact Notes Version (Optional — Same Kadane)

The notes' version compresses add + reset into one line. It's the same algorithm — **both forms are Kadane's algorithm** — written shorter:

### Java Code

```java
class Solution {
    public int maxSubArray(int[] nums) {
        int currentSum = 0;
        int maxSum = Integer.MIN_VALUE;
        for (int x : nums) {
            currentSum = Math.max(x, currentSum + x);
            maxSum = Math.max(maxSum, currentSum);
        }
        return maxSum;
    }
}
```

### How It Links to Your Version

`Math.max(x, currentSum + x)` asks: **is it better to extend the running sum with this number, or start fresh from just this number?** It picks the bigger.

- If `currentSum` is negative, `x` alone wins → that's your reset, done **one step earlier** (decided at the current number instead of after it).
- Your version adds first and resets to zero if negative; theirs decides at each number whether to start fresh — same thing, one step earlier.

`Math.max(maxSum, currentSum)` is just your max check.

### Mini-Trace on [-2, 1, -3, 4] (the two slips to avoid)

| x | Choice A (fresh) | Choice B (extend) | Winner | currentSum | maxSum |
|---|---|---|---|---|---|
| -2 | -2 | 0 + -2 = -2 | tie → -2 | -2 | -2 |
| 1 | **1** | -2 + 1 = -1 | **1** (fresh) | 1 | 1 |
| -3 | -3 | 1 + -3 = **-2** | **-2** (extend) | -2 | 1 |
| 4 | **4** | -2 + 4 = 2 | **4** (fresh — drops the -3 stretch) | 4 | 4 |

Two slips happened while tracing this live, both worth remembering:

1. **At `1`:** choosing -1 over 1 — *"a bigger number means closer to the positive side."* Plain `1` beats `-1`; whenever the running sum is negative, start fresh. That line **is** your reset, one step earlier.
2. **At `-3`:** thinking `currentSum` stays 1 — no: the choices are `-3` alone vs `1 + (-3) = -2`, and `-2` wins. The sum does go negative here; it's dropped at the next step when `4` picks fresh over `2`.

## Common Mistakes

- **Initializing `maxSum = 0`:** on an all-negative array the answer is the largest (least negative) element, not 0 — zero "wins" every comparison and lies. Use `Integer.MIN_VALUE` (or start at `nums[0]`). You predicted this trap before writing the code — keep it.
- **Resetting `maxSum` along with `currentSum`:** only the running sum drops. `maxSum` is the memory of the best total ever — reset it too and you lose the peak (the 6 in the trace would vanish).
- **Using `else if` instead of two `if`s:** the max check and the reset check are independent; `else if` skips one when the other fires (and on negative sums, the max check fires first — the reset gets skipped).
- **Resetting before the max check:** order is add → max → reset. Reset first and an all-negative array returns 0 instead of the real (negative) answer.
- **Expecting to return the subarray:** the problem asks for the **sum** — you never store or rebuild the segment, just `currentSum` and `maxSum`.
- **Forgetting the subarray must be contiguous and non-empty.**
- **Divide and conquer (O(n log n))** exists (the follow-up) — Kadane's O(n) is simpler and faster.

## How to Explain (interview)

**Opening:** Maximum Subarray asks for the largest sum of a contiguous, non-empty subarray. Brute force checks all subarrays — O(n²). Kadane's algorithm does it in O(n): walk the array with a running sum; add each number, record the best sum seen, and if the running sum goes negative, drop it — a negative stretch only drags down whatever comes after. Two variables, one pass, constant space.

**The basic flow (branching version — the one built live):**
```java
int currentSum = 0, maxSum = Integer.MIN_VALUE;
for (int i = 0; i < nums.length; i++) {
    currentSum += nums[i];              // add the number
    if (currentSum > maxSum) {          // did this beat the best ever?
        maxSum = currentSum;
    }
    if (currentSum < 0) {               // burden? drop it — only the running sum
        currentSum = 0;
    }
}
return maxSum;
```

(Compact one-line equivalent: `currentSum = Math.max(x, currentSum + x);` — extend-or-start-fresh, your reset one step earlier.)

**The part that trips everyone up:** the two checks are independent and ordered — max check *before* reset, two `if`s not `else if`, and only `currentSum` ever resets. Plus `maxSum = 0` fails on all-negative input.

**The mistakes to remember:**
- `maxSum = 0` instead of `Integer.MIN_VALUE` (all-negative arrays)
- Resetting `maxSum` too — it must survive the drops
- `else if` instead of two `if`s; reset before max-check
- Expecting to return the subarray — it wants the sum
