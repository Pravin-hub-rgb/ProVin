# Module 0: The Big Picture

Before any detail, here is the full picture. Most tutorials jump straight into arrays and never show you where you're going — that's where the confusion starts. This module exists so you know exactly what DSA is, why interviews test it, how this course is organized, and when you've done enough.

---

## What is DSA, and why do interviews test it?

**DSA** = **D**ata **S**tructures and **A**lgorithms. Two words, one idea: how you store data, and how you work on it.

When a company hires a developer, they can't easily test "will this person write clean code for 6 months." But they *can* test "can this person solve a problem under pressure." DSA problems are a proxy for that — they check whether you can break a problem down, choose the right tool, and reason about efficiency. That's why almost every tech interview has a coding round.

Is it a perfect measure? No. Good projects and communication matter just as much, especially at higher levels. But DSA is the gate you have to pass first, so we treat it seriously — and we don't let it become the only thing you do (see Module 23).

### What the goal is NOT

The goal of DSA is **not** "make it as fast as possible." It is: (1) a correct solution, (2) that fits the problem's constraints, (3) with reasonable time/space trade-offs, (4) that you can explain. A working O(n²) beats a broken O(n); a slightly slower solution you can explain beats a faster one you can't. Big-O tells you whether your approach *scales* — it does not demand the absolute fastest code. Sometimes O(n²) is the right answer because n is small or the O(n) version is too hard to derive under time pressure.

### What DSA is NOT

- It is **not** memorizing 500 solutions. Quality beats quantity — 150 problems you truly understand beats 500 you copied.
- It is **not** the whole interview. Resume, projects, CS fundamentals, and communication decide the rest.
- It is **not** a talent test. It's a skill, and skills are built by practice with a method.

## The Three Layers

Most confusion comes from mixing three different things that all get called "topics." Learn to separate them.

| Layer | What it is | Examples |
|---|---|---|
| **Data structure** | A way to *store* data (a noun) | Array, LinkedList, HashMap, Tree, Heap, Graph, Trie |
| **Algorithm** | A *method* to solve a class of problems (a verb) | Sorting, binary search, BFS, DFS, recursion, backtracking, DP, greedy |
| **Pattern** | A reusable *trick* to recognize and solve a family of problems | Two pointers, sliding window, prefix sum, monotonic stack, binary search on answer, top-K with a heap |

Examples:
- **Array, LinkedList, HashMap, Tree, Heap, Graph, Trie** → data structures (containers).
- **Sorting, binary search, BFS, DFS, recursion, backtracking, DP, greedy** → algorithms (methods).
- **Two pointers, sliding window, prefix sum, monotonic stack, binary search on answer, top-K with a heap** → patterns (techniques).

**Every real problem uses all three.** Take Two Sum: you use an array and a hash map (data structures), a "remember what you've seen" idea (pattern), and a single pass over the input (algorithm). So a problem is never "just an array problem."

## The Full Topic Map

Here is every data structure and algorithm in this course, in one line each, so you can see the whole terrain before walking it.

**Foundations**
- **Big-O notation** — how fast code grows as input grows; the language of efficiency.
- **Java Collections** — ArrayList, HashMap, HashSet, ArrayDeque, PriorityQueue, TreeMap/TreeSet — the ready-made containers you'll use daily.

**Linear structures**
- **Arrays & Strings** — values in a row; the most common starting point.
- **Linked List** — nodes chained by pointers; flexible size, slow access.
- **Stack & Queue & Deque** — last-in-first-out and first-in-first-out containers; the backbone of many algorithms.

**Hash-based**
- **HashMap & HashSet** — instant lookup by key; the single most-used tool in interviews.

**Non-linear**
- **Trees & BST** — hierarchical data; recursion's natural home.
- **Heap / Priority Queue** — always know the biggest (or smallest) element fast.
- **Graphs** — nodes and edges; networks, dependencies, maps.
- **Trie** — prefix tree; fast string search.
- **Union-Find (DSU)** — grouping elements into sets; "are these connected?"

**Algorithms**
- **Sorting** — arranging data; the basis of many other techniques.
- **Binary search** — find in sorted data in log time; also "search on the answer."
- **BFS & DFS** — exploring trees and graphs level by level or depth by depth.
- **Backtracking** — try, fail, undo, retry; subsets, permutations, combinations.
- **Greedy** — take the best local choice and hope it's global.
- **Dynamic Programming** — remember sub-answers to avoid recomputing; the hardest and most rewarding topic.
- **Topological sort** — ordering tasks with dependencies.
- **Shortest path** — Dijkstra, Bellman-Ford; weighted graphs.
- **Bit manipulation** — working at the level of individual bits; fast and clever.

**Patterns (the reusable tricks)**
- Two pointers, sliding window, prefix sum, monotonic stack, intervals, binary search on answer, top-K with a heap.

Don't memorize this list. Come back to it when you feel lost — it's your reference.

## How the Course Is Organized

The course has **24 modules** (Module 0 through Module 23). Modules 2–22 are pattern modules. Each follows the **same template** so you always know where to look:

1. Header (title, goal, tier tags)
2. Prerequisites
3. Data structure primer (only if the module introduces one)
4. The pattern explained + "how to recognize it" checklist
5. Worked example (brute force → optimized, with Java code and complexity)
6. Common mistakes
7. Practice problems (table from the tier files)
8. Revision list (3–5 problems to re-solve after a week)
9. Mini quiz (5 concept/complexity questions)
10. One-page cheat sheet

**Just-in-time teaching:** a module teaches only the data structures it needs, when it needs them. We don't teach "all arrays, then all linked lists" — array problems need hashing and binary search too, so you'd hit things you haven't been taught. And we don't teach "all data structures first" — that's boring and you forget it before using it. Just-in-time avoids both.

**Module 0 (this one)** sets the tone. **Module 1** gets you Java-ready and teaches Big-O. **Modules 2–4** are the pilot — build those fully, get feedback, then continue.

## Choose Your Tier

You don't have to decide your ceiling on day one, but picking a target keeps you from over- or under-studying.

| Tier | Goal | Problems (cumulative) | Typical employers |
|---|---|---|---|
| 1 | Foundation | 83 | Service companies, small startups |
| 2 | Core product | 217 | Mid-level product companies, fintech |
| 3 | Advanced | 300 | Big product companies, big tech |
| 3+ | Deeper big-tech prep | up to 574 | Amazon, Microsoft, Google-style |

**Important:** these ranges come from personal experience in the Indian market, not an official standard. Treat them as rough guides. Company bars vary, and for higher bands communication, projects, and system design matter as much as DSA.

**Which modules each tier needs:**
- **Tier 1:** Modules 0–12 and 14–16, plus the recursion basics part of Module 11. Skip Modules 13, 17, 19, 20 for practice (awareness only — read one paragraph, move on). Treat Modules 18, 21, 22 as light (2–3 problems each).
- **Tier 2:** All modules except Tier 3 problems.
- **Tier 3:** Everything.

**Awareness-only (Tier 1):** Modules 13 (Design), 17 (Trie), 19 (Topological Sort), and 20 (Shortest Path / DSU / MST) have no Tier 1 practice problems. Tier 1 learners read one paragraph on each ("what it is, when it's used") and move on. They'll recognize the names if an interviewer mentions them, without spending days on them.

**Two valid study flows (pick one — content is the same):**
- **Flow A — Module-first (default):** Go module by module. Learn the DS → learn the pattern → worked example → solve all problems for your tier in that module → move on. Depth-first.
- **Flow B — Tier-first (3-pass):** Pass 1: all modules, Tier 1 problems only. Pass 2: all modules, Tier 2 problems (DS known; re-hitting Tier 1 problems = spaced repetition). Pass 3: all modules, Tier 3 problems. Breadth-first.

In both flows, data structures are learned once per module — never repeated.

## How to Practice

These rules live in every module's Module 0 section. Follow them from day one.

1. **Try first.** Spend 20–25 minutes on a problem on your own before reading any solution.
2. **Then learn.** Read the editorial or a solution, understand *why* it works, and write it yourself.
3. **Re-solve next day** from scratch, without looking.
4. **Tick the box only when you can solve it alone**, without hints.
5. **Revisit after one week** the problems that felt hard.
6. **Explain out loud.** For each problem, state the approach, why that data structure, the time and space complexity, and the edge cases. This is what interviews test at higher tiers.
7. **Track progress.** Log solved date, struggled (yes/no), and revisit date.

**Pacing:** the original sheet suggests 2 months at 2 hours/day. That's ambitious for a beginner, especially in DP. **3–4 months at your own pace is perfectly fine.** Order matters more than speed.
