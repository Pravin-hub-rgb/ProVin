## The Core Idea

Binary search finds an element in a **sorted** array by repeatedly halving the search space. Compare the target with the middle element: if equal, found; if target is smaller, search the left half; if larger, search the right half. Each step eliminates half → O(log n).

**The mental model:** you're playing "guess the number" — too high or too low, and you always cut the remaining range in half. The precondition is a **sorted** (or monotonically searchable) space.

**Two variants:**
1. **Standard binary search:** find an element in a sorted array.
2. **Search on answer:** the answer lies in a numeric range [lo, hi], and you can check "is X feasible?" in O(n). Binary search the range. (e.g., Sqrt(x), Koko Eating Bananas, capacity to ship packages.)

## How to Recognize It

Think "Binary Search" when:
- The array is **sorted** and you need to find/search/count.
- The problem asks for the **first/last occurrence** of an element.
- The array is **rotated sorted** — binary search still works with a twist (one half is always sorted).
- The problem asks for **sqrt, cube root, or any root** → search on answer.
- The problem asks "minimum capacity / maximum speed such that feasible" → search on answer (monotonic feasibility).
- Keywords: "sorted array," "find target," "first/last position," "rotated sorted."

**Signal words:** "sorted," "search," "find the index of," "rotated sorted array," "minimum X such that condition holds."

**Binary Search vs Linear Search:** linear search is O(n) and works on unsorted data. Binary search is O(log n) but requires sorted/monotonic data. If the data is sorted, always prefer binary search.

## Worked Example: Search in Rotated Sorted Array

**Problem:** A sorted array was rotated at some pivot. Find the target. O(log n).

### Brute force (O(n))

Linear scan — works but ignores the sorted structure.

### Optimized (O(log n)) — binary search with a twist

```java
class Solution {
    public int search(int[] nums, int target) {
        int left = 0, right = nums.length - 1;

        while (left <= right) {
            int mid = left + (right - left) / 2;
            if (nums[mid] == target) return mid;

            // Determine which half is sorted
            if (nums[left] <= nums[mid]) {       // left half is sorted
                if (nums[left] <= target && target < nums[mid]) {
                    right = mid - 1;               // target in left half
                } else {
                    left = mid + 1;                // target in right half
                }
            } else {                               // right half is sorted
                if (nums[mid] < target && target <= nums[right]) {
                    left = mid + 1;                // target in right half
                } else {
                    right = mid - 1;               // target in left half
                }
            }
        }
        return -1;
    }
}
```

**Line-by-line:**
- `mid = left + (right - left) / 2` — avoids overflow (vs `(left + right) / 2`).
- Check which half is sorted: `nums[left] <= nums[mid]` means left half is sorted.
- If target lies in the sorted half, search there; otherwise search the other half.
- Standard binary search loop: `left <= right`, update `left = mid + 1` or `right = mid - 1`.

**Key insight:** in a rotated sorted array, at least one half is always sorted. Determine which half is sorted, check if the target is in that range, and narrow accordingly.

## Common Mistakes

- **Overflow in mid calculation.** `(left + right) / 2` can overflow for large indices. Use `left + (right - left) / 2`.
- **Wrong loop condition.** Use `left <= right` for "find exact" (inclusive both ends). Use `left < right` for "find boundary" (exclusive right). Mixing them causes infinite loops or missed elements.
- **Off-by-one in updates.** When `nums[mid] != target`, move `left = mid + 1` or `right = mid - 1` (exclude mid). Using `left = mid` or `right = mid` can cause infinite loops.
- **Forgetting the sorted precondition.** Binary search requires sorted/monotonic data. On unsorted data, it gives wrong answers.
- **Search on answer: wrong bounds.** `lo` and `hi` must cover the answer. `lo` = minimum possible answer, `hi` = maximum possible. Check feasibility with a helper function.

## How to Explain (interview)

**Opening:** Binary Search finds an element in a sorted array by repeatedly halving the search space. Compare the target with the middle; if smaller, search left; if larger, search right. O(log n) time, O(1) space. Requires sorted (or monotonic) data. "Search on answer" applies the same idea to a numeric range where you can check feasibility.

**The basic flow:**
```java
int left = 0, right = n - 1;
while (left <= right) {
    int mid = left + (right - left) / 2;
    if (nums[mid] == target) return mid;
    if (nums[mid] < target) left = mid + 1;
    else right = mid - 1;
}
return -1;
```

**The part that trips everyone up:** overflow in `mid = (left + right) / 2` — use `left + (right - left) / 2`. Also, loop condition `left <= right` (inclusive) with `left = mid + 1` / `right = mid - 1` (exclude mid) — mixing these causes infinite loops.

**The mistakes to remember:**
- Overflow in mid calculation
- Wrong loop condition (infinite loop or missed element)
- Using binary search on unsorted data
- Search on answer: wrong lo/hi bounds
