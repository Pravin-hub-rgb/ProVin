You already know what code does. Now learn how to measure **how much time** it takes as input grows — and how to estimate it from the problem's constraints. This is the language every DSA discussion uses.

---

## Why Big-O?

Two solutions can both be "correct" but one takes 1 second and the other 10 hours on the same input. Big-O tells you which scales better, without running it. It's about **growth rate**, not exact seconds.

### What is the goal of optimization?

It is **not** "make it as fast as possible in absolute terms." Big-O is about **scaling**, not raw speed. The real goal, in order:

1. **Correctness first.** A working O(n²) beats a broken O(n). Get a solution that works, then improve.
2. **Fit the constraints.** Read n, pick the target complexity (n ≤ 10⁵ → O(n) or O(n log n)). That is the bar you must clear — not "the fastest possible."
3. **Reasonable trade-offs.** Sometimes O(n) space for O(n) time (a hash map) is worth it; sometimes O(1) space matters more. Depends on the problem and the constraints.
4. **Readable, explainable code.** Interviews grade how you think and communicate, not just the final Big-O. A slightly slower solution you can explain beats a faster one you can't.

So: **correct solution that fits the constraints, then optimize if time permits.** Sometimes the optimal is O(n²) because n is small, or because an O(n) solution is too complex to derive under time pressure. Big-O tells you whether your approach *scales* — it does not demand the absolute fastest code.

### A first taste: Two Sum

Many array problems ask you to find, count, or group elements. A naive approach checks every pair → O(n²). A hash map lets you look up "have I seen X before?" in O(1), turning the problem into a single pass → O(n).

The mental model: as you walk through the array, maintain a "memory" (hash map/set) of what you've seen. For each element, ask: "does my memory already contain what I need?" If yes, you have an answer. If no, record this element and move on.

This is the idea behind the Arrays & Hashing pattern (Module 2) — and it's the same idea behind every optimization you'll do: replace a nested search with a constant-time lookup. The goal isn't "the fastest code"; it's code that *scales* within the constraints, that you can explain.

### What It Is NOT

- Big-O is **not** the actual running time. It ignores constants and lower-order terms. O(2n) and O(n) are both written O(n).
- Big-O is **not** only for "slow" code. Even O(1) code has a constant cost; Big-O just says that cost doesn't grow with n.
- Big-O is **not** about best case. By default it describes **worst case** unless stated otherwise.

## The Common Growth Rates

| Notation | Name | Example | n = 10⁵ ops |
|---|---|---|---|
| O(1) | Constant | array access `arr[i]` | 1 |
| O(log n) | Logarithmic | binary search | ~17 |
| O(n) | Linear | single loop over array | 10⁵ |
| O(n log n) | Linearithmic | merge sort, Arrays.sort | ~1.7 × 10⁶ |
| O(n²) | Quadratic | nested loops | 10¹⁰ (too slow!) |
| O(2ⁿ) | Exponential | subsets/backtracking | astronomically large |
| O(n!) | Factorial | permutations | impossible |

**The rule of thumb for constraints:**
- n ≤ 10 → O(n!) or O(2ⁿ) might be okay (backtracking).
- n ≤ 10³ → O(n²) is okay (10⁶ ops).
- n ≤ 10⁵ → need O(n) or O(n log n) (10⁵–10⁶ ops).
- n ≤ 10⁶ → need O(n) or better.
- n ≤ 10⁹ → need O(log n) or O(1).

This mapping is the single most useful thing in competitive programming. When you read "1 ≤ n ≤ 10⁵", you instantly know: no O(n²).

## How to Analyze a Loop

Count how many times the innermost work runs.

### Single loop → O(n)

```java
for (int i = 0; i < n; i++) {
    System.out.println(i);   // runs n times
}
```

### Nested loops → O(n²)

```java
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        System.out.println(i + j);   // runs n × n = n² times
    }
}
```

### Loop that halves → O(log n)

```java
int i = n;
while (i > 1) {
    System.out.println(i);
    i = i / 2;   // halves each step → log₂(n) steps
}
```

### Two sequential loops → O(n + m) → O(n) if m ≈ n

```java
for (int i = 0; i < n; i++) { ... }   // n
for (int j = 0; j < n; j++) { ... }   // n
// total 2n → O(n)
```

### Loop with a break → still O(n) worst case

```java
for (int i = 0; i < n; i++) {
    if (arr[i] == target) break;   // best case O(1), worst case O(n)
}
```
Big-O describes worst case by default. The break helps average case but not worst.

## How to Analyze a Method

When a method calls another, add (sequential) or multiply (nested).

```java
static void foo(int n) {
    for (int i = 0; i < n; i++) bar(n);   // n calls to bar
}
static void bar(int n) {
    for (int j = 0; j < n; j++) { }       // n work
}
// foo is O(n × n) = O(n²)
```

```java
static void foo(int n) {
    for (int i = 0; i < n; i++) { }   // n
    bar(n);                            // n
}
static void bar(int n) {
    for (int j = 0; j < n; j++) { }   // n
}
// foo is O(n + n) = O(n)
```

## Dropping Constants and Lower Terms

Big-O keeps only the dominant term.

- O(3n² + 5n + 7) → **O(n²)** (n² dominates)
- O(2n) → **O(n)**
- O(n + log n) → **O(n)**
- O(n × m) stays O(n × m) if n and m are independent sizes.

**Why drop constants?** Because Big-O describes *scaling*, not exact speed. O(2n) and O(n) both double when n doubles — same scaling. Constants matter for real performance but not for Big-O class.

## Best, Average, Worst Case

- **Worst case** (default for Big-O): the input that makes the algorithm do the most work.
- **Best case:** the input that makes it do the least (e.g., found target at index 0).
- **Average case:** expected work over random inputs.

Example — linear search:
- Best: O(1) (target at index 0)
- Worst: O(n) (target at end or absent)
- Average: O(n/2) → O(n)

We usually state worst case. When a problem says "O(n) solution expected," it means worst case.

## Estimating from Constraints (the interview skill)

Read the constraint, pick the complexity.

| Constraint on n | Target complexity | Why |
|---|---|---|
| n ≤ 10 | O(n!) / O(2ⁿ) | tiny; backtracking okay |
| n ≤ 10³ | O(n²) | 10⁶ ops, fine |
| n ≤ 10⁴ | O(n²) borderline, prefer O(n log n) | 10⁸ ops, risky |
| n ≤ 10⁵ | O(n) or O(n log n) | 10⁵–10⁶ ops |
| n ≤ 10⁶ | O(n) | 10⁶ ops |
| n ≤ 10⁹ | O(log n) or O(1) | can't even loop |

**Example:** "1 ≤ n ≤ 2 × 10⁵" → your solution must be O(n) or O(n log n). An O(n²) will TLE (time limit exceeded). This single mapping prevents 90% of wrong approaches.

## A Worked Example: Find Max in Array

```java
static int findMax(int[] arr) {
    int max = arr[0];              // O(1)
    for (int i = 1; i < arr.length; i++) {   // n-1 iterations
        if (arr[i] > max) {        // O(1) per iteration
            max = arr[i];
        }
    }
    return max;                    // O(1)
}
```

Total: O(1) + (n-1)×O(1) + O(1) = O(n). Linear scan — one pass, constant work per element.

**Brute force vs optimized:** here the brute force *is* the optimal (you must look at every element to find the max). Not every problem has a faster answer — but many do, and Big-O helps you see when to look for one.

## In Your Own Words

1. What does Big-O measure, and what does it ignore?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Big-O measures the *growth rate* of an algorithm's time (or space) as input size n grows — how it scales, not exact seconds. It ignores constant factors and lower-order terms: O(3n² + 5n) becomes O(n²). It describes worst case by default. It's a classification tool, not a stopwatch.

</details>

2. Given constraint "1 ≤ n ≤ 10⁵", what complexity must your solution be?

<details>
<summary>Show Answer</summary>
**Sample Answer:** O(n) or O(n log n) at most. O(n²) would be ~10¹⁰ operations — too slow, will TLE. O(n) is 10⁵ ops, O(n log n) is ~1.7×10⁶ ops, both fine. This constraint→complexity mapping is the key skill: read n, pick the target complexity, then design the algorithm to fit.

</details>

3. Why is binary search O(log n) and not O(n)?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because each step halves the search space. Start with n elements → n/2 → n/4 → ... → 1. The number of halvings to reach 1 is log₂(n). So even for n = 10⁹, binary search takes ~30 steps. Contrast with linear search, which checks every element → O(n).

</details>

4. If a method calls an O(n) method inside an O(n) loop, what's the total complexity?

<details>
<summary>Show Answer</summary>

**Sample Answer:** O(n²) — the complexities multiply when one is nested inside the other. Sequential calls add: O(n) + O(n) = O(n). Nested calls multiply: O(n) × O(n) = O(n²). This distinction (add vs multiply) is crucial for analyzing multi-step algorithms.

</details>
