# 1.1 Java — What It Is, Why We Use It, and How It Runs

## What Is Java

You want to solve DSA problems — finding duplicates in a list, checking if a string reads the same backward, searching an element in an array. To do that, you need to write instructions that a computer can follow. Those instructions are written in a programming language. Java is one such language.

Java was created in 1995 by James Gosling at Sun Microsystems (now owned by Oracle). The core idea behind Java was that code written once should run anywhere — on Windows, Mac, or Linux — without being rewritten for each operating system.

**Why Java for DSA instead of Python or C++?** Python lets you write very short code but hides how the computer manages memory, which matters when you're learning data structures. C++ gives you full control but requires you to manage memory manually, which can distract you from the actual DSA logic. Java sits in between — it's clear and readable enough that you see what's happening, but it cleans up memory automatically so you don't crash your program while learning. Many companies in India use Java for backend work, so learning Java for DSA also means you're learning a language you may use on the job.

## Java Architecture & How It Runs

Before we write any Java, you need to understand how your Java code actually runs on your computer.

First, a human can only write code in human-readable form — English-like words such as `public class` or `System.out.println`. A machine only understands machine code, which is specific to that machine's processor. Humans can't read machine code, and machines can't read human code directly. Something must convert between the two.

This is true for every programming language. When someone writes HTML, they save it in a `.html` file — that extension categorizes the file, telling the computer "this is HTML code." If they wrote JavaScript or Java inside an `.html` file, it wouldn't run, because it's something else. So for any programming language, you write code in a file with that language's particular extension. For Java, the extension is `.java`.

Suppose you want to write the simplest basic function — a greeting. You pass your name into a function, and it says "hi [name]". Everyone understands this basic idea. For Java, you write that code according to Java's syntax inside a `.java` file.

Now here's where Java works differently from many other languages.

Take C++ as an example. When you compile C++ code, it turns into machine code specific to that machine. If you compile C++ on Windows and send that compiled output to a Mac, it won't run — it's tied to Windows architecture. You'd have to recompile it on Mac.

Java's creators solved this differently. They wanted code that compiles once and runs anywhere — no matter which architecture it runs on.

The code we write in `Hello.java` is called **source code** — it's human-readable, but the machine can't run it directly. When we compile it with `javac`, it turns into **bytecode** stored in `Hello.class`. This bytecode can run on every architecture — Windows, Mac, Linux — because it's the same everywhere.

Then a program on each machine reads that bytecode and translates it into machine instructions for that specific machine.

That program is the **JVM (Java Virtual Machine)** — the engine that reads bytecode and translates it into machine instructions for your operating system (Windows, Mac, Linux). 

But JVM alone isn't enough. Consider your greeting function: it might ask for user input, do some math, and print output. To print to the console, Java needs `System.out`. To read user input, it needs input libraries. These are standard libraries — `String`, `Math`, `System`, and more. The JVM doesn't include them. So you need an environment that bundles the JVM **plus** those standard libraries. That environment is the **JRE (Java Runtime Environment)**:

- **JRE** = JVM + standard libraries. Enough to *run* Java programs, not to write them.

If your program needs `System.out.println()` to print output, or `Math` to do calculations, those come from the JRE's libraries. Without JRE, JVM alone can't provide them — the program would have the bytecode but no way to perform standard operations like printing or reading input.

Now, JRE lets you *run* Java programs. But what if you want to *write* and *compile* your own Java code? You need a compiler — `javac` — that takes your `.java` source code and turns it into `.class` bytecode. The JRE doesn't include `javac`. So you need a development kit that bundles the JRE **plus** the compiler and other developer tools. That kit is the **JDK (Java Development Kit)**:

- **JDK** = JRE + compiler (`javac`) + developer tools. To *write and compile* Java, you need the JDK.

Here's how you unpack it, step by step, from writing code to running it:

**Step 1 — JDK (outer container):** You write source code in `Hello.java` — human-readable code. Then you use `javac`, the compiler that comes with the JDK, to turn it into `Hello.class` — bytecode. This step (source code → bytecode) belongs to the JDK.

**Step 2 — JRE (inside JDK):** Now you have bytecode. To run it, you need standard libraries — `System`, `Math`, input/output libraries. The JRE bundles the JVM with those libraries.

**Step 3 — JVM (inside JRE):** Finally, the JVM reads the `.class` bytecode and translates it into machine instructions for that specific computer's processor.

**Flow from writing code to running it:**

```
Write:   Hello.java   (source code, human-readable)
         │
         │ javac (compiler in JDK)
         ▼
Compile: Hello.class  (bytecode, same on every machine)
         │
         │ JVM (inside JRE, inside JDK)
         ▼
Run:     Machine code  (specific to your OS — Windows, Mac, or Linux)
```

**Nesting order:** JDK contains JRE, JRE contains JVM. As a developer you always install the **JDK**.

Here's the full pipeline: you write source code in `Hello.java` → `javac` (the compiler in the JDK) turns it into `Hello.class` (bytecode) → the JVM reads `Hello.class` and runs it on your operating system. Because bytecode is the same everywhere, the same `.class` file runs on Windows, Mac, and Linux — the JVM on each machine translates it for that machine.

**Common confusion:** JVM is not a compiler — it runs bytecode; `javac` compiles source to bytecode. JRE alone isn't enough to develop — without `javac` (in the JDK) you cannot compile your own code.

## Installing Java on Your Computer

Before you write any code, your computer needs the JDK installed and needs to know where it lives.

Download the JDK from [adoptium.net](https://adoptium.net) (Temurin) or Oracle. Pick the latest LTS version — Java 17 or 21. LTS means long-term support, so it's stable and receives updates for years.

Install it and note the install path, for example `C:\Program Files\Eclipse Adoptium\jdk-21...`.

Set `JAVA_HOME` to that path, and add `%JAVA_HOME%\bin` (Windows) or `$JAVA_HOME/bin` (Mac/Linux) to your `PATH`. This tells your terminal where to find the Java tools.

Open a terminal and verify:

```bash
java -version
javac -version
```

Both should print version numbers. If `javac` says "not recognized", your PATH is wrong — fix that before anything else.

You don't need an IDE to start; a text editor works. But for comfort, use IntelliJ IDEA Community (free, best for Java) or VS Code with the Java extension pack. The IDE handles compile and run with one click and shows errors inline as you type.

## Your First Java Program

Create a file named `Hello.java` — the file name must match the public class name exactly.

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, DSA!");
    }
}
```

Run it from the terminal:

```bash
javac Hello.java
java Hello
```

The first command compiles your source into bytecode (`Hello.class`). The second starts the JVM to run that bytecode. You should see `Hello, DSA!` printed. In an IDE like IntelliJ, just click Run — it does both steps automatically.

Line by line:

- `public class Hello` — declares a class named `Hello`. A class is a blueprint. The file must be named `Hello.java` to match.
- `public static void main(String[] args)` — this is the entry point. Every Java program starts here. The JVM looks for exactly this signature. `public` means the JVM can access it from outside, `static` means it runs without creating an object, `void` means it returns nothing, and `String[] args` holds any command-line arguments you pass.
- `System.out.println("Hello, DSA!");` — prints text to the console followed by a new line. `System` is a built-in class, `out` is the output stream, and `println` prints the message.

Common mistakes:

- **File name mismatch:** class `Hello` must be in `Hello.java`. On case-sensitive systems, `hello.java` is not the same file.
- **Wrong `main` signature:** `public static void main(String args[])` works, but `public void main(...)` or `static void main(...)` won't be found by the JVM.
- **Forgetting the semicolon:** Java requires `;` at the end of every statement.

## How Coding Platforms Expect Your Code

On LeetCode and interview platforms, you don't write `main`. You write a class (usually `Solution`) with a method:

```java
class Solution {
    public int add(int a, int b) {
        return a + b;
    }
}
```

The platform calls your method with test inputs and checks if the output matches. So learn the `class Solution { public ... method(...) }` shape — that's what you'll write most of the time during DSA practice.

---

## Common Mistakes

- **File name mismatch:** class `Hello` must be in `Hello.java`. `hello.java` (lowercase) fails on case-sensitive systems.
- **`main` signature typo:** `public static void main(String args[])` works, but `public void main(...)` or `static void main(...)` won't be found by the JVM.
- **Running `java Hello.java`:** Java 11+ compiles-and-runs in one step, but the classic way is `javac` then `java`. On interview platforms you only write the class.
- **Forgetting the semicolon:** Java requires `;` at the end of every statement.
