## Linear vs Non-Linear — Two Ways to Store Data

Before we dive into any structure, understand the big split:

**Linear structures** store things in a row, one after another:

| Structure | How it looks | How you reach something |
|---|---|---|
| Array | 0, 1, 2, 3... | By index — `arr[5]` jumps straight there |
| ArrayList | Same row, grows automatically | By index |
| String | Row of characters | By index |
| StringBuilder | Row you can edit | By index |
| 2D Array | Rows × columns grid | By row and column |

All of these are **linear**: you start at one end and move step by step. To find something without knowing its index, you scan — O(n). The index is your address; without it, you're walking the whole row.

**Non-linear structures** (HashMap, HashSet) store things by **key**, not by position:

| Structure | How it looks | How you reach something |
|---|---|---|
| HashMap | key → value pairs | By key — `map.get("apple")` |
| HashSet | Just unique keys | By key — `set.contains("apple")` |

You don't count from the start. You say "give me the value for key X" and it jumps straight there. No scanning. That's O(1) average.

Think of an array as a **row of lockers** numbered 0, 1, 2... You need the locker number to open it.

Think of HashMap as a **filing cabinet with labeled drawers**. You read the label and open that drawer directly — no counting.

This module's pattern (traverse, check, store) exists because linear scanning is slow (O(n²) when nested), and non-linear lookup is fast (O(n)). The hash map IS the "memory" that replaces the second loop.

## The problem we're trying to escape

Imagine you're standing at some element in the middle of an array, and you need to find something related to it, like a partner that completes a sum. The obvious move is to go back to the start and scan through everything again, looking for it. Then you move to the next element and do the same thing.

That's a loop inside a loop. With n elements, you might make about n times n checks, so the time complexity is O(n²). It works, but it gets painfully slow as the array grows.

The pattern in this module exists to get rid of that second loop.

## The core idea

The pattern comes down to three words: **traverse, check, store.**

- **Traverse:** walk through the array once, one element at a time.
- **Check:** at each element, ask your memory, "do you already have what I need?"
- **Store:** if not, write the current element into memory and move on.

The order matters. Always check first and store second, otherwise an element can end up matching itself.

Think of a server handling a stream of incoming requests. For each one it needs to know, "have I already seen this user ID?" Rescanning every past request would be slow. Keeping a cache and doing one quick lookup is fast. In this pattern, the **array is the data coming in, and the hash map (or set) is the cache you build as you go.**

The payoff: we turn O(n²) "check every pair" into O(n) "check memory." We spend extra space to save time, and that trade is the heart of the module.

## Worked example: Two Sum

**The problem:** you're given an array of integers and a target number. Find two numbers in the array that add up to the target, and return their **positions** (indices), not the values themselves. Assume exactly one answer exists.

We'll use the array `[2, 7, 11, 15]` with a target of `9`.

### Step 1: Brute force

Stand on one number, then scan the rest of the array looking for its partner. Then move to the next number and repeat.

At index 0 we have 2. We need a partner that makes 9, which is 7. We scan forward and find 7 at index 1. Answer: `[0, 1]`.

```java
class Solution {
    public int[] twoSum(int[] nums, int target) {
        for (int i = 0; i < nums.length; i++) {
            for (int j = i + 1; j < nums.length; j++) {
                if (nums[i] + nums[j] == target) {
                    return new int[]{i, j};
                }
            }
        }
        return new int[]{};
    }
}
```

- **Time:** O(n²), because of the loop inside a loop.
- **Space:** O(1), because we store nothing extra.

### Step 2: Traverse, check, store

The number we're hunting for is called the **complement**: `target - current number`. Instead of scanning for it, we ask the map.

At index 0 we have 2. The complement is 7. The map is empty, so no. We store "2 lives at index 0" and move on.

At index 1 we have 7. The complement is 2. We ask the map, and yes, 2 is there at index 0. Done: `[0, 1]`.

```java
class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>();  // value -> index

        for (int i = 0; i < nums.length; i++) {
            int complement = target - nums[i];
            if (seen.containsKey(complement)) {
                return new int[]{seen.get(complement), i};
            }
            seen.put(nums[i], i);
        }
        return new int[]{};
    }
}
```

- **Time:** O(n), one pass, and each lookup is instant.
- **Space:** O(n), because the map can end up holding every number.

### A longer example

Take `[3, 8, 5, 12, 1]` with a target of `13`.

- At 3 (index 0): the complement is 10. Not in the map. Store 3 at index 0.
- At 8 (index 1): the complement is 5. Not in the map yet. Store 8 at index 1.
- At 5 (index 2): the complement is 8. The map has 8 at index 1. Match! Answer: `[1, 2]`.

The match took longer to appear because the partner had to be sitting in the map before we could find it. That's why we store as we go.

## The memory: hash map vs hash set

The "memory" in this pattern is a hash map or a hash set. Both let you ask "have I seen this before?" and get an instant answer, without scanning through everything you've stored. That instant lookup is what replaces the second loop.

The only real decision is what you need to get back out:

- **Hash map:** use it when you need to attach something to each item, like an index or a count. The item is the key, and the extra information is the value. Two Sum needs the index, so it uses a map (`value -> index`).
- **Hash set:** use it when you only care whether you've seen the item. There are no values, just keys. Contains Duplicate only asks "have I seen this number?", so it uses a set.

A quick rule: if you need to get something back out, use a map. If it's a yes-or-no question, use a set.

The flow is identical either way: traverse, check, store.

## The tools we'll learn next

The pattern needs two kinds of tools: structures that hold the **data we walk through**, and structures that serve as the **memory we check against**. Files 2.2 to 2.8 teach them one by one, and then we come back to Two Sum and put them to work.

| File | Structure | What it is | How it shows up in this pattern |
| --- | --- | --- | --- |
| 2.2 | Array | A fixed-size, ordered block of items, accessed by index | The most common input. We walk it with a loop. |
| 2.3 | ArrayList | A resizable array | Same idea as an array, but it can grow, so it's handy for building results. |
| 2.4 | String | A sequence of characters that can't be changed once created | Many problems walk a string the way they walk an array, character by character. |
| 2.5 | StringBuilder | A changeable version of a string | Use it when you build or edit a string as you go, so you don't create a new one every time. |
| 2.6 | 2D Array | An array of arrays, like a grid or table | Appears when the data has rows and columns, such as a matrix or board. |
| 2.7 | HashMap | Key-value pairs with instant lookup | The memory when you need to get something back, like an index or a count. |
| 2.8 | HashSet | A collection of unique keys with instant lookup | The memory when you only need to know "have I seen this?" |

The first six are mostly about **holding and walking through the data**. The last two are the **cache** that makes the pattern fast. Every problem in this module is some mix of the two groups.

## How to recognize this pattern

Think "traverse, check, store" when the problem asks you to find, count, or group things in an array or string, and a brute-force answer would need a loop inside a loop.

**Problems that use a hash map or set as memory:**

- Do two elements sum to a target? Store seen values and look for the complement. (Two Sum)
- Are all elements distinct? Use a set, and compare its size to the array length. (Contains Duplicate)
- Are two strings anagrams? Compare character frequency maps. (Valid Anagram)
- Group items by a shared property? Map from a key to a list of items. (Group Anagrams)
- Find the k most or least frequent elements? Frequency map plus a heap or bucket sort. (Top K Frequent)
- Find the majority element? Frequency map, or the Boyer-Moore trick. (Majority Element)

**Array-technique problems that live in this module but don't need a map:**

- Product or sum of everything except the current element: prefix and suffix products. (Product Except Self)
- Max profit from one buy and one sell: track the minimum so far. (Best Time to Buy and Sell Stock)
- Maximum subarray sum: Kadane's algorithm, which keeps a running sum and resets when it goes negative. (Maximum Subarray)
- Sort 0s, 1s and 2s in place: counting sort or the Dutch National Flag approach. (Sort Colors)

The second group still follows the spirit of the pattern, a single pass that carries a little memory, but the memory is a variable or two instead of a map.

## Common mistakes

- **Returning values instead of indices.** Two Sum asks for positions. Read the problem statement carefully.
- **Assuming the array is sorted.** Two Sum's array is not sorted. Two Sum II is the sorted variant, and it uses a different technique.
- **Storing before checking.** If you put the current number in the map first, it can match itself. Check, then store.
- **Using `==` to compare Strings** in anagram problems. Use `.equals()`, or compare char arrays.
- **Forgetting that `get` returns null for a missing key.** Calling a number method on that null throws a NullPointerException. Use `containsKey` or `getOrDefault`.
- **Modifying the input when the problem forbids it.** Some problems say not to change the input array, so read the constraints first.
- **Assuming counting sort is always fine.** If the range of values is large, counting needs O(range) space, so check the constraints.

## How to explain it in an interview

**Opening:** "This is a pattern where I walk through the array once and use a hash map or set as memory. At each element I check whether my memory already has what I need. If it does, I'm done. If not, I store the current element and move on. It turns an O(n²) check-every-pair approach into O(n)."

**The flow:** traverse, check, store. For Two Sum, I compute the complement, look it up in the map in constant time, and if it's missing I record the current value and its index.

**The trade-off:** I spend O(n) extra space to save O(n) time per element. Brute force is O(n²) time and O(1) space. The map version is O(n) time and O(n) space.

**Map or set:** if I need to get something back, like an index or a count, I use a map. If I only need to know whether I've seen the item, I use a set.

**Things to watch for:** return indices, not values, don't assume the array is sorted, and check before you store.
