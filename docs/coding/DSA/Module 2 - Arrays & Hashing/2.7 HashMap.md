## What Does "Hash" Mean?

This is where the word **Hash** in HashMap comes from — and it's **not** the same as password hashing.

**Password hashing** (like `bcrypt`) is security: you scramble a password and store the scrambled version. You can't unscramble it. When someone logs in, you scramble their typed password and compare the two scrambled strings. One-way. That's cryptographic hashing.

**Hash table hashing** (what HashMap uses) is completely different. It's an **address calculator**:

1. You have a key: `"apple"`.
2. A **hash function** turns that key into a number: `hashCode("apple")` → say `12345`.
3. That number determines which **bucket** (slot) the value goes into: `bucketIndex = hashCode % numberOfBuckets`.
4. To look up `"apple"`, you hash it again → same bucket → jump straight there → O(1).

So "hash" here just means **"turn a key into a number that tells us where in RAM to store it."** It's an index calculation, not encryption.

**Bucket = RAM slot, not disk.** Your computer's memory (RAM) is one big array of slots. `bucketIndex` is just an index into that array. It's not on disk — it's in memory, right now.

**Why this matters:** In an array, you need the index (0, 1, 2...) to reach an element. In HashMap, you don't need to know the index — you know the key (`"apple"`), and the hash function calculates the index for you automatically.

## What Is a Map

A Map stores data as **key → value pairs**. Given a key, you instantly find its value — without scanning all entries.

Real example from your own data:

- Your `products` table: `product_id` → `Product` object
- Your user system: `email` → `User` profile
- In DSA problems: a character → its frequency count, or an array value → its index position

**Unique keys:** Each key appears once. If you put the same key again, the old value is overwritten. This is what makes Map different from a List (where duplicates are allowed and order matters).

---

## Why String Immutability Matters for Hashing

Remember: String's `hashCode` never changes after creation. If you use a String as a HashMap key:

- Put `"apple"` → hashCode → bucket 5 → stored there
- Get `"apple"` → hashCode → bucket 5 → found instantly

If keys were mutable (e.g., an array you later change), its `hashCode` would change, and the Map would look in the wrong bucket — the entry becomes "lost." That's why String and Integer are safe HashMap keys: their hashCode is stable.

---

## String as Key, Integer as Value — Why This Combination

When you see `Map<String, Integer>`, it means:

- **Key = String** — something unique and immutable that identifies an entry. In frequency counting, each character is a key (`'a'`, `'b'`). In Two Sum, each array value is a key.
- **Value = Integer** — the data attached to that key. In frequency counting, it's the count (how many times `'a'` appeared). In Two Sum, it's the index where that value was seen.

**Why String?** Because `String` is immutable — its `hashCode` never changes, so the Map can always find it.

**Why Integer?** Because the value is whatever you need to store — counts, indices, IDs. Integer is just one example; values can be any type (String, List, custom objects).

---

## Map Interface vs HashMap Implementation

Look at this line:

```java
Map<String, Integer> freq = new HashMap<>();
```

There are two parts:

- **`Map` (left side)** — the **interface**. It defines what operations a Map must support: `put`, `get`, `remove`, `containsKey`, `size`. It's the contract.
- **`HashMap` (right side)** — the **implementation**. It's the actual class that stores data using hash-based buckets for O(1) average operations.

You declare as `Map` (interface) but instantiate as `HashMap` (concrete class). Good practice — if you later need a sorted map, change only the right side to `TreeMap`; the left side (`Map`) stays the same, and all your code using `put`/`get` keeps working.

---

## HashMap and HashSet — Under One Roof

`HashSet` (covered next in 2.8) is **HashMap's sibling** — both use the same hash mechanism underneath:

- **HashMap** stores `key → value` pairs. The key is hashed to find the bucket.
- **HashSet** stores just keys (values are a dummy constant). It uses `HashMap` internally: `key → dummy value`.

Think of them as the same engine with different dashboards:

- HashMap dashboard: "What value is stored at key X?" → `map.get(key)`
- HashSet dashboard: "Has key X been seen?" → `set.contains(x)`

Both give O(1) average operations because both use the same hash function → bucket index → lookup pipeline. When you learn HashMap, you've already learned 90% of how HashSet works.

## Declaration and Creation

```java
import java.util.HashMap;
import java.util.Map;

Map<String, Integer> freq = new HashMap<>();        // empty
Map<String, Integer> copy = new HashMap<>(freq);    // copy of another map
Map<String, Integer> sized = new HashMap<>(100);    // initial capacity 100
```

**Note:** Use the interface type `Map` on the left, `HashMap` on the right. This lets you swap to `TreeMap` (sorted) without changing code.

## Core Operations

```java
Map<String, Integer> map = new HashMap<>();

map.put("apple", 2);                    // insert
map.put("apple", 3);                    // overwrite → apple: 3
System.out.println(map.get("apple"));    // 3
System.out.println(map.get("grape"));    // null (not present)
System.out.println(map.getOrDefault("grape", 0)); // 0 (safe default)

System.out.println(map.containsKey("apple"));  // true
System.out.println(map.containsValue(3));     // true (O(n)!)

map.remove("apple");                    // remove key
System.out.println(map.size());         // 0
map.clear();                            // remove all
```

- `put`, `get`, `containsKey`, `remove`: O(1) average.
- `containsValue`: O(n) — scans all values. Avoid in hot code.
- `getOrDefault(key, default)`: returns the value or default if key absent. Use this to avoid null checks.

## Frequency Counting Pattern

The most common HashMap pattern in DSA.

```java
String s = "aabbc";
Map<Character, Integer> freq = new HashMap<>();
for (char c : s.toCharArray()) {
    freq.put(c, freq.getOrDefault(c, 0) + 1);
}
// freq = {a:2, b:2, c:1}
```

**Shorthand (Java 8+):**
```java
freq.merge(c, 1, Integer::sum);   // same as above, cleaner
```

---

## Grouping Pattern

Map a computed key to a list of items.

```java
String[] words = {"eat", "tea", "tan", "ate", "nat", "bat"};
Map<String, List<String>> groups = new HashMap<>();

for (String w : words) {
    char[] chars = w.toCharArray();
    Arrays.sort(chars);
    String key = new String(chars);   // sorted string as key
    groups.computeIfAbsent(key, k -> new ArrayList<>()).add(w);
}
// groups: {"aet": ["eat","tea","ate"], "ant": ["tan","nat"], "abt": ["bat"]}
```

- `computeIfAbsent(key, k -> new ArrayList<>())` — creates the list if absent, returns it. Cleaner than `if (!map.containsKey(key)) map.put(key, new ArrayList<>())`.

## Iterating

```java
Map<String, Integer> map = new HashMap<>();
map.put("a", 1); map.put("b", 2);

// Iterate over entries (most common)
for (Map.Entry<String, Integer> e : map.entrySet()) {
    System.out.println(e.getKey() + " = " + e.getValue());
}

// Iterate over keys
for (String key : map.keySet()) {
    System.out.println(key + " = " + map.get(key));
}

// Java 8+ forEach
map.forEach((k, v) -> System.out.println(k + " = " + v));
```

**Note:** iteration order is NOT guaranteed (HashMap is unordered). Use `LinkedHashMap` for insertion order, `TreeMap` for sorted order.

## Cost (Big-O)

| Operation | Average | Worst (hash collisions) |
|---|---|---|
| `put`, `get`, `containsKey`, `remove` | O(1) | O(n) |
| `size` | O(1) | O(1) |
| Iteration | O(n) | O(n) |

Worst case O(n) occurs with hash collisions. Java 8+ converts long collision chains to balanced trees (O(log n)) for String/Integer keys, so worst case is rarely hit in practice.

---

## When to Use

- Frequency counting (count occurrences of each element).
- "Have I seen this value?" lookups (Two Sum complement).
- Grouping items by a computed property (anagrams).
- Caching / memoization (store computed results).
- Mapping an entity to its data (id → object).

---

## Common Pitfalls

- **`get` returns null for missing keys.** Calling `.intValue()` on null → NPE. Use `getOrDefault`.
- **Modifying while iterating** → `ConcurrentModificationException`. Use `Iterator.remove()` or collect keys first.
- **Using mutable objects as keys.** If a key's `hashCode` changes after insertion (e.g., a list you modified), the map can't find it. Use immutable keys (String, Integer, or your own with stable hashCode/equals).
- **Forgetting to override `hashCode` and `equals`** in custom key classes. Default `Object.hashCode()` uses memory address — two "equal" objects hash differently and won't match.
- **`containsValue` is O(n).** If you need value lookups, consider a reverse map or a different structure.

## A Small Program: Two Sum with HashMap

```java
import java.util.*;

public class TwoSum {
    static int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>(); // value → index
        for (int i = 0; i < nums.length; i++) {
            int complement = target - nums[i];
            if (seen.containsKey(complement)) {
                return new int[]{seen.get(complement), i};
            }
            seen.put(nums[i], i);
        }
        return new int[]{};
    }

    public static void main(String[] args) {
        int[] nums = {2, 7, 11, 15};
        System.out.println(Arrays.toString(twoSum(nums, 9))); // [0, 1]
    }
}
```

## In Your Own Words

1. What is the average time complexity of HashMap get/put, and what's the worst case?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Average O(1) — hash the key, jump to the bucket. Worst case O(n) if all keys hash to the same bucket (collisions). Java 8+ converts long collision chains to balanced trees (O(log n)) for comparable keys, so worst case is rarely hit in practice. Good hash functions distribute keys evenly.

</details>

2. Why should you use `getOrDefault` instead of `get` when counting frequencies?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `get(key)` returns null for missing keys. Doing `freq.get(c) + 1` on null throws NullPointerException. `getOrDefault(c, 0)` returns 0 for missing keys, so `freq.getOrDefault(c, 0) + 1` works safely without an explicit null check.

</details>

3. What happens if you use a mutable object as a HashMap key and then modify it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The object's hashCode may change after modification, so the map can no longer find it in the original bucket — the entry becomes "lost" (still in the map but unreachable by key). Always use immutable keys (String, Integer, or custom classes with stable hashCode/equals). If you must use a mutable key, don't modify it after insertion.

</details>

4. How is HashMap hashing different from password hashing (like bcrypt)?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Password hashing is one-way security — you scramble a password and can't get the original back. HashMap hashing is an address calculator — you hash a key to find which RAM bucket its value is in, then retrieve the actual value. Different purpose, different mechanism.

</details>
