## Step 1: GitHub OAuth App — External Setup

GitHub ka OAuth system janne ki zaroorat nahi — bas woh form bharo jo GitHub khud deta hai. Steps:

1. **GitHub pe jao** → profile icon (top-right) → **Settings**
2. Sidebar mein sabse neeche → **Developer settings**
3. Left mein **OAuth Apps** → **New OAuth App** button
4. Form mein teen cheezein bharo:

| Field | Value | Kya hai |
|---|---|---|
| Application name | `Member Dashboard (dev)` | Koi bhi naam — user ko approve screen pe dikhta hai |
| Homepage URL | `http://localhost:3000` | Teri app ka address |
| Authorization callback URL | `http://localhost:3000/api/auth/callback/github` | **Sabse important** — GitHub login ke baad user ko wapas bhejega yahan |

Callback URL samjho — OAuth flow mein (4.4 wala diagram yaad hai?) step 4 mein GitHub user ko app pe **wapas bhejta hai** with a code. Woh "wapas bhejne ka pata" yahi callback URL hai. Agar yeh galat ho, toh flow toot jaata hai — GitHub user ko kahin nahi bhej paata.

5. **Register application** karo
6. Ab tumhe do cheezein milengi:
   - **Client ID** — ek public identifier (iski visibility se koi dikkat nahi)
   - **Generate a new client secret** → click karo, **Client Secret** dikhegi — **copy karo turant, kyunki yeh sirf ek baar dikhti hai!** Refresh karo toh gayab.

Client ID + Client Secret = GitHub ka tumhare app pe "bharosa" — inhi se GitHub pehchanta hai ki kaunsi app OAuth maang rahi hai. **Secret ko kabhi bhi kisi ke saath share mat karna, aur code mein hardcode mat karna** — env variable mein jaata hai (agle step).

## Step 2: Environment Variables — `.env.local`

**File:** `.env.local` (project root mein — create-next-app ne shayad already bana rakha hai)

```
AUTH_SECRET=apna-generated-secret-yahan
AUTH_GITHUB_ID=github-pe-mila-client-id
AUTH_GITHUB_SECRET=github-pe-mila-client-secret
```

Teeno ka kaam:

- **`AUTH_SECRET`** — Auth.js ka signing secret. Isse session token sign hota hai (JWT wala signature yaad hai?). **Generate karo, khud mat banao** — Auth.js ka command hai:
  ```bash
  npx auth secret
  ```
  Ye random secret generate karke khud `.env.local` mein daal dega. (Manual way: `openssl rand -base64 32`.)
- **`AUTH_GITHUB_ID`** / **`AUTH_GITHUB_SECRET`** — GitHub pe mile wale values. **Auth.js v5 mein yeh naming convention built-in hai** — `AUTH_GITHUB_` prefix dekhte hi GitHub provider khud inhe padh leta hai, config mein alag se env reading nahi likhni padti.

`.env.local` ko kabhi commit mat karna — create-next-app ki `.gitignore` mein already hai (check kar lena, nahi toh add kar do).

## Step 4: Config File — Root Mein `auth.ts`

**File:** `auth.ts` (project ROOT mein — `app/` ke bahar, `package.json` ke saath)

Is file ko hum **stage-wise** banayenge — pehle minimum config jo login chala de, phir options add karenge. Koi poora config ek saath nahi.

### Stage 1 — Minimum: Sirf Provider

**SOCH:** Auth.js ko sabse pehle yeh batana hai ki login kaise karein. GitHub se login karna hai toh GitHub provider config mein daalo. Bas itna hi minimum hai — baaki options optional hain.

**CONCEPT:** `NextAuth({...})` — config object leta hai. `providers: [GitHub]` — kaunse login methods allowed hain. `GitHub` import `next-auth/providers/github` se — **yeh provider `AUTH_GITHUB_ID` / `AUTH_GITHUB_SECRET` env vars ko khud padh leta hai** (Step 2 wala convention). Google chahiye hota toh `Google` import + `AUTH_GOOGLE_*` env — bas yeh fark hai (4.0 mein bola tha).

**CODE:**

```ts
// auth.ts (project root)
import NextAuth from "next-auth";
import GitHub from "next-auth/providers/github";

export const { handlers, signIn, auth, signOut } = NextAuth({
  providers: [GitHub],
});
```

**TEST:** `npm run dev` — `/api/auth/signin` pe jao. Agar koi error nahi aaya, toh GitHub provider registered hai.

### Stage 2 — Session Strategy: JWT

**SOCH:** Ab Auth.js ko batana hai session kahan rakhe. 4.4 mein JWT wala concept dekha tha — default Auth.js JWT hi use karta hai, par explicitly likhna better hai taaki pata rahe. Plus expiry.

**CONCEPT:** `session.strategy: "jwt"` — Auth.js ko bol rahe hain: session data token mein rakho, server-side store nahi. `maxAge: 30 * 24 * 60 * 60` — session kitne seconds tak valid (30 din).

**CODE** — poora `auth.ts` file state ab aisa hai (naya hissa `// NEW` se mark hai):

```ts
// auth.ts (project root)
import NextAuth from "next-auth";
import GitHub from "next-auth/providers/github";

export const { handlers, signIn, auth, signOut } = NextAuth({
  providers: [GitHub],
  // NEW: session block
  session: {
    strategy: "jwt",
    maxAge: 30 * 24 * 60 * 60,
  },
});
```

**TEST:** Koi change nahi dikhega browser mein — config option hai. Agle step ke saath dekho.

### Stage 3 — Secret + Custom Login Page

**SOCH:** Do cheezein bachi: signing secret (JWT ke signature ka — 4.4 wala point) aur custom login page point karna.

**CONCEPT:** `secret: process.env.AUTH_SECRET` — signing secret `.env.local` se. `pages.signIn: "/login"` — jab bhi Auth.js ko "login karo" bolna ho (unauthorized redirect), toh default Auth.js wali ugly login screen ke bajaye **hamara `/login` page** khulega.

**CODE** — poora `auth.ts` file state ab aisa hai (naya hissa `// NEW` se mark hai):

```ts
// auth.ts (project root) — final
import NextAuth from "next-auth";
import GitHub from "next-auth/providers/github";

export const { handlers, signIn, auth, signOut } = NextAuth({
  providers: [GitHub],
  session: {
    strategy: "jwt",
    maxAge: 30 * 24 * 60 * 60,
  },
  // NEW: secret + pages
  secret: process.env.AUTH_SECRET,
  pages: {
    signIn: "/login",
  },
});
```

**TEST:** `/secret`-type protected cheez pe bina login jaao (agar koi ho) — `/login` pe redirect hota hai na?

**Nutshell:** Root `auth.ts` Auth.js ki config file hai — `providers` (kaunse login), `session` (JWT strategy + expiry), `secret` (signing key), `pages` (custom login URL) — aur isse poore project ke liye `handlers`, `signIn`, `auth`, `signOut` export milte hain.

**`export const { handlers, signIn, auth, signOut }`** — yeh chaar cheezein Auth.js ki taraf se milti hain, aur poore project mein yahin se import hoti hain. Har ek ka kaam:

| Export | Kya hai |
|---|---|
| `handlers` | HTTP handlers (route.ts ke liye — agla step) |
| `signIn` | Login trigger — Server Actions mein `signIn("github")` |
| `signOut` | Logout trigger |
| `auth` | Session reader — Server Components mein `await auth()` |

## Step 5: Route Handler — `app/api/auth/[...nextauth]/route.ts`

**File:** `app/api/auth/[...nextauth]/route.ts` (nayi file)

```ts
// app/api/auth/[...nextauth]/route.ts
import { handlers } from "@/auth";

export const { GET, POST } = handlers;
```

Bas itna hi — do lines. Par iske peeche kaafi kuch hai:

**`[...nextauth]`** — ek catch-all dynamic route (Batch 1 ka concept). `signin`, `callback`, `session`, `providers` — Auth.js ke saare endpoints isi ek route se handle hote hain:

```
/api/auth/signin/github    → GitHub pe redirect (4.4 flow ka step 2)
/api/auth/callback/github  → GitHub ka callback (step 4-6)
/api/auth/session          → session JSON
/api/auth/signout          → logout
```

**Ek maza ki baat:** Batch 3 ke end mein humne `app/api` folder **delete** kiya tha — REST wala kaam khatam ho gaya tha. Ab `app/api` **wapas aa gaya** — par is baar sirf Auth.js ke liye. Route Handlers ka basic concept (3.1) yahan sach mein kaam aa raha hai: yeh bhi ek route handler hi hai, bas `handlers` export ho raha hai.

## Step 6: Login Page — "Sign in with GitHub"

**File:** `app/login/page.tsx` (update karo — 4.2/4.3 wale manual form ki jagah)

Isko bhi stage-wise banate hain — pehle button jo render ho, phir login trigger, phir "already logged in" wala check.

### Stage 1 — Static: Sirf Button

**SOCH:** Login page ka kaam ek hi hai — "Sign in with GitHub" button dikhana. Pehle bas static version jo render ho jaye.

**CODE:**

```tsx
// app/login/page.tsx
export default function LoginPage() {
  return (
    <main>
      <h1>Sign In</h1>
      <form>
        <button type="submit">Sign in with GitHub</button>
      </form>
    </main>
  );
}
```

**TEST:** `/login` pe button dikh raha hai. Abhi button kuch karta nahi — aage action lagega.

### Stage 2 — Action: `signIn("github")`

**SOCH:** Button ko kaam dilana hai — click pe GitHub pe le jaana. 4.2 mein form action se login kiya tha — same pattern, bas action ka kaam alag: server action `signIn("github")` Auth.js ka hai jo user ko GitHub pe redirect kar deta hai.

**CONCEPT:** Inline Server Action — `action={async () => { "use server"; await signIn("github"); }}`. Form submit → `signIn("github")` → Auth.js user ko GitHub pe bhejta hai (4.4 flow ka step 2). **Koi email/password form nahi — ek button hi kaafi hai.** Yahi OAuth ka magic hai.

**CODE:**

```tsx
// app/login/page.tsx
import { signIn } from "@/auth";

export default function LoginPage() {
  return (
    <main>
      <h1>Sign In</h1>
      <form
        action={async () => {
          "use server";
          await signIn("github");
        }}
      >
        <button type="submit">Sign in with GitHub</button>
      </form>
    </main>
  );
}
```

**TEST:** Button click → GitHub authorize page → approve → wapas app pe. Login ho gaya.

### Stage 3 — Already Logged In? Redirect

**SOCH:** Ek edge case bacha: jo already logged in hai uske liye login page dikhana bekaar hai — seedha home pe bhej do. 4.3 ka `getSession()` pattern yaad hai? `auth()` usi ka Auth.js version hai.

**CODE — final** (poora file state, naya hissa `// NEW` se mark hai):

```tsx
// app/login/page.tsx
import { signIn, auth } from "@/auth";              // NEW: auth
import { redirect } from "next/navigation";         // NEW: import

export default async function LoginPage() {
  const session = await auth();                     // NEW
  if (session) {                                    // NEW
    redirect("/");                                  // NEW
  }

  return (
    <main>
      <h1>Sign In</h1>
      <form
        action={async () => {
          "use server";
          await signIn("github");
        }}
      >
        <button type="submit">Sign in with GitHub</button>
      </form>
    </main>
  );
}
```

**TEST:** Login kar ke `/login` pe jao — turant `/` pe redirect. Logout kar ke jaao — button dikhega.

**Nutshell:** Login page 3 stage mein bana — static button → `signIn("github")` action (OAuth trigger) → `auth()` session check (already logged in → redirect). Manual form (4.2 wala) **delete kar do** — ab email/password system hi nahi hai, password ki problem gayab (4.4 wala point).

## What It Is NOT

- **`auth.ts` = session store nahi.** Ye sirf config + exports hai — session ka data JWT token mein hai (cookie mein), koi server-side record nahi.
- **Client ID/Secret = username/password nahi.** Ye app ki pehchaan hain, user ki nahi. Secret leak ho toh koi aur tumhari app ka naam pe OAuth app bana sakta hai.
- **Login hone ka matlab "sab kuch allowed" nahi.** Abhi session hai, par routes protect nahi kiye (4.4.3 mein). Auth.js ne authentication diya — authorization hamari zimmedari.
- **Yeh credentials (email/password) login nahi hai** — humne manual wala system hata diya. GitHub OAuth = password ki zaroorat hi nahi.

## Common Mistakes

- **Callback URL galat** — GitHub settings mein `http://localhost:3000/api/auth/callback/github` exact hona chahiye. Port alag hai (jaise 3001) toh yahan bhi wahi port.
- **Client Secret copy karna bhoolna** — sirf ek baar dikhti hai. Reset karke nayi generate karni padti hai.
- **Env vars ke baad dev server restart nahi karna** — `.env.local` change pe `npm run dev` dobara chalao, warna Auth.js purani config use karega.
- **`auth.ts` galat jagah** — project root mein hona chahiye (`app/` ke andar nahi), kyunki `@/auth` import root ko point karta hai.
- **Secret ko code/hardcode karna ya commit karna** — `.env.local` hi jagah hai, `.gitignore` mein confirm karo.

## Nutshell

Real OAuth setup: GitHub Developer settings mein OAuth App banao (callback `http://localhost:3000/api/auth/callback/github`), Client ID + Secret `.env.local` mein (`AUTH_GITHUB_ID`/`AUTH_GITHUB_SECRET` + `AUTH_SECRET` via `npx auth secret`). `npm i next-auth@beta`. Root `auth.ts` mein config: providers `[GitHub]`, JWT strategy, custom `/login` page. Route handler `app/api/auth/[...nextauth]/route.ts` mein `handlers` export. Login page: `await auth()` (already logged in → redirect) + form action mein `signIn("github")`. Done — `authjs.session-token` cookie set ho gayi, khud httpOnly+secure.

**In Your Own Words**

1. Authorization callback URL kya karta hai — agar galat ho toh OAuth flow kahan toot-ta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** OAuth flow mein GitHub user ko approve ke baad wapas app pe bhejta hai, saath mein ek code de kar. Callback URL wahi "wapas bhejne ka pata" hai — GitHub user ko isi URL pe le jaata hai. Agar galat ho, toh GitHub user ko kahin bhi nahi le ja paata (ya galat jagah le jaata hai) — flow toot jaata hai aur login kabhi complete nahi hota. Isliye yeh URL GitHub settings mein app ke actual callback se exact match hona chahiye.

</details>

2. `AUTH_GITHUB_ID`/`AUTH_GITHUB_SECRET` naam ka convention kyu kaam karta hai — config mein env kyun nahi padhna padta?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Auth.js v5 mein provider-specific env convention built-in hai — `AUTH_GITHUB_` prefix wale vars dekh ke GitHub provider khud unhe config mein use kar leta hai. Isliye config mein sirf `providers: [GitHub]` likhna kaafi hai. Google chahiye hota toh `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` + `Google` import — code change ki zaroorat hi nahi padti, bas env + provider. Provider add karna itna aasaan isi convention ki wajah se hai.

</details>

3. `pages: { signIn: "/login" }` kyun set kiya — bina iske kya hota?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Jab bhi koi unauthored user kisi protected cheez tak pahunchta hai (redirect zaroori ho), Auth.js ko pata hona chahiye ki login kahan le jaana hai. Bina `pages.signIn` ke Auth.js apni default ek built-in login screen dikhata hai jo ugly hai aur hamare design se match nahi karti. Custom login page banaya hai toh usi ko point karna padta hai — warna custom page bekaar hai aur user default screen pe jaata hai.

</details>

4. `[...nextauth]` catch-all route se kaunse endpoints handle hote hain, aur yeh kyun possible hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `[...nextauth]` dynamic catch-all hai — `signin`, `callback`, `session`, `signout` sab `/api/auth/` ke under aate hain aur isi ek route se handle hote hain. Batch 1 ka dynamic route concept yaad karo — `[id]` ek parameter pakadta hai, `[...nextauth]` saare segments pakadta hai. Auth.js ke `handlers` isi ek route pe sab endpoints sunte hain — isliye route file sirf do lines ki hai.

</details>

5. Manual login (4.2) vs yeh Auth.js login — session cookie ke level pe kya fark hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Manual mein humne khud `cookies().set("sessionId", userId, {httpOnly, secure, sameSite})` kiya tha aur cookie mein sirf id thi (record file mein). Auth.js mein cookie `authjs.session-token` khud set hoti hai — isme JWT hai jisme session data signed hai, aur httpOnly/secure attributes bhi khud lagte hain. Dono mein cookie hi hai, par Auth.js ne woh saara boilerplate (attributes, signing, expiry) apne andar kar liya — humne sirf config diya.

</details>
