4.4.2 mein session dikh raha hai — navbar mein naam, dashboard mein email. Par ek badi problem abhi bhi hai: **koi bhi route protect nahi hai.** Bina login ke seedha `/dashboard` kholo toh khul jaayega (email khali dikhega) — koi bhi request bina session ke data access kar sakti hai. Ab woh check add karna hai: bina session aane pe `/login` pe redirect.

Is file mein do cheezein hongi. Pehli — **layout mein `auth()` check** se dashboard ko lock karna (yahi main security hai, 4.3 wala pattern ab Auth.js ke saath). Doosri — **`proxy.ts`** — Next.js 16 ka naya naam jo pehle `middleware.ts` tha — jisse hum routing-level ka kaam karenge (jaise logged-in user `/login` pe jaye toh `/dashboard` bhej do). Aur ek zaroori baat — **auth ko proxy mein kyun nahi rakhna chahiye** (CVE-2025-29927 ke baad Next.js ki official recommendation), jiski wajah se roadmap mein bhi fix hua hai. Chalo.

## Step 1: Layout Protection — Main Security

4.3 mein manual session ke saath layout protection ki thi — `getSession()` + `redirect("/login")`. Ab wahi pattern, bas `auth()` ke saath. `/dashboard` ke andar ek `layout.tsx` banao:

**File:** `app/dashboard/layout.tsx` (nayi file)

```tsx
// app/dashboard/layout.tsx
import { redirect } from "next/navigation";
import { auth } from "@/auth";

export default async function DashboardLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const session = await auth();
  if (!session) {
    redirect("/login");
  }
  return <>{children}</>;
}
```

- **`await auth()`** — session check. `null` = logged out.
- **`if (!session) redirect("/login")`** — 4.3 wala core pattern: **server-side check + redirect.** Dashboard ka data (email etc.) client tak pahunchta hi nahi agar logged out ho — request aate hi `/login` pe.
- **Layout isliye, page nahi** — `/dashboard` ke saare pages (abhi `page.tsx`, kal koi `settings` wagera) ek saath protected. 4.3 wala reason.

**Yahi security ka main point hai — layout check.** Yehi Next.js ka recommended tareeka hai (iski wajah Step 4 mein). Proxy routing woh convenience layer hai jo ab banate hain.

## Step 2: Proxy Routing — Logged-In User Ko Login Pe Mat Phansao

Ab ek nayi problem. Ek user logged in hai (session hai), par woh manually `/login` pe chala jaata hai. 4.4.1 mein login page mein check tha (`if (session) redirect("/")`) — par woh sirf login page ka check hai. **Har request se pehle** ek global layer ho jo aise routing decisions de — wahi **proxy** hai.

### Concept — `proxy.ts` Kya Hai

**`proxy.ts`** Next.js mein ek special file hai jo **har request ke route render hone se PEHLE** chalti hai. Isme tum request ko dekh kar decide kar sakte ho: redirect karo, response return karo, ya request ko aage badhne do.

Version note — **Next.js 16 mein `middleware.ts` ka naam badal kar `proxy.ts` ho gaya hai** (matlab same concept, naya naam; purana naam deprecated). Yehi woh file hai jisse tumne `4_proxy` project mein rate-limiting ki thi — wahi concept, ab auth ke saath.

Flow dekh:

```
Request aayi (/login)
   → proxy.ts chalta hai (render se pehle)
   → "user logged in hai aur /login pe ja raha hai? → /dashboard bhejo"
   → warna request aage badhti hai
   → route render hota hai
```

**File:** `proxy.ts` (project ROOT mein — `auth.ts` ke saath, `app/` ke bahar)

Isse stage-wise banate hain — pehle wrapper ka skeleton, phir routing rule, phir matcher.

### Stage 1 — Wrapper Ka Skeleton

**SOCH:** Proxy ko session ka pata hona chahiye (logged-in hai ya nahi). Cookie khud parse karni padti? Nahi — Auth.js ka wrapper hai.

**CONCEPT:** `export default auth((req) => {...})` — Auth.js ka special wrapper. `auth()` ko proxy function ke roop mein use kar rahe hain — **wrapper proxy ko session deta hai:** `req.auth` mein session aata hai. (Bina wrapper ke proxy cookie khud parse karni padti — wrapper yeh kar deta hai.)

**CODE:**

```ts
// proxy.ts (project root)
import { auth } from "@/auth";

export default auth((req) => {
  // abhi kuch bhi mat karo — request aage badhne do
});
```

**TEST:** App normal chal rahi hai, koi route pehle jaisa khul raha hai — wrapper ne kuch todo. 

### Stage 2 — Routing Rule

**SOCH:** Ab asli kaam: logged-in user `/login` pe jaye toh `/dashboard` bhejo. Do checks chahiye — user logged in hai? Aur login page pe ja raha hai?

**CONCEPT:** `req.nextUrl.pathname.startsWith("/login")` — pathname check (startsWith isliye kyunki `/login` ke under future sub-pages bhi cover ho jaayenge). `NextResponse.redirect(...)` — proxy ka response: request aage nahi badhti, redirect ho jaata hai. **Agar condition false** — kuch return nahi kiya = request aage badhti hai (default behaviour).

**CODE** — poora file state ab aisa hai (naya hissa `// NEW` se mark hai):

```ts
// proxy.ts (project root)
import { auth } from "@/auth";
import { NextResponse } from "next/server";   // NEW: import

export default auth((req) => {
  // NEW: routing rule
  const isLoggedIn = !!req.auth;
  const isLoginPage = req.nextUrl.pathname.startsWith("/login");

  if (isLoggedIn && isLoginPage) {
    return NextResponse.redirect(new URL("/dashboard", req.nextUrl));
  }
});
```

- **`const isLoggedIn = !!req.auth`** — `req.auth` session object hai ya `null`. `!!` se boolean banaya: session hai → `true`.
- **`if (isLoggedIn && isLoginPage)`** — routing rule: **logged-in user login page pe nahi dikhega.**

**TEST:** Login kar ke manually `/login` pe jao → `/dashboard` pe redirect. Logged out ho → `/login` normal khulta hai.

### Stage 3 — Matcher (Proxy Kis URL Pe Chalna Hai)

**SOCH:** Ab ek problem — proxy har request pe chalega, static assets (images, css) pe bhi, jahan session ka matlab nahi. `config.matcher` se batao ki kis URL pe chalna hai.

**CONCEPT:** `matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"]` — "sab kuch, par static assets nahi" — Next.js ki internal files pe proxy nahi chalana.

**CODE — final** (poora file, matcher `// NEW`):

```ts
// proxy.ts (project root) — final
import { auth } from "@/auth";
import { NextResponse } from "next/server";

export default auth((req) => {
  const isLoggedIn = !!req.auth;
  const isLoginPage = req.nextUrl.pathname.startsWith("/login");

  if (isLoggedIn && isLoginPage) {
    return NextResponse.redirect(new URL("/dashboard", req.nextUrl));
  }
});

// NEW: matcher config
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**TEST:** Build output mein `ƒ Proxy (Middleware)` dikhta hai, aur static assets pe proxy kuch karta nahi (performance par asar nahi).

**Notice kiya — proxy mein SECURITY check nahi hai?** `/dashboard` ko bina login wala request proxy mein nahi roka ja raha — woh layout kar raha hai (Step 1). Proxy sirf **routing/UX** ka kaam kar raha hai (login page pe logged-in user ko na dikhana). Yehi intentional split hai — aur ab agla sawaal: kyun?

## Step 3: Auth Proxy Mein Kyun Nahi — CVE-2025-29927

Ab tak tumne YouTube pe (aur shayad apne `3_nextauth_js` project mein bhi) dekha hoga ki log **proxy/middleware se hi routes protect karte hain** — `isProtectedRoute && !isLoggedIn → redirect`. Yeh pattern **chal jaata hai** — tumhare apne project mein chala tha. Par 2025 mein ek critical vulnerability aayi — **CVE-2025-29927** — jisme Next.js ka middleware **bypass kiya ja sakta tha** ek special header bhej kar (`x-middleware-subrequest`). Matlab: hacker bina login ke protected route tak pahunch sakta tha kyunki **middleware hi skip ho jaata tha.**

Iska nateeja — **Next.js team ki official guidance badal gayi:** auth ko middleware/proxy mein mat rakho. **Auth checks layout, Server Components, Route Handlers, ya Server Actions mein honi chahiye** — kyunki yeh app code hai jo bypass nahi ho sakta. Next.js 16 ne middleware ka naam hi `proxy` kar diya aur docs mein clear kar diya: proxy routing/redirects ke liye hai, **auth enforcement ke liye nahi.**

Isliye humara split sahi hai:

| Layer | Kaam | Kyun yahan |
|---|---|---|
| **`layout.tsx` + `auth()`** | Security — bina session redirect | App code, bypass nahi ho sakta |
| **`proxy.ts`** | Routing — logged-in user ko login page se hatana | Convenience, security sirf yahan mat rakho |

**Defense in depth** bhi ho jaata hai — agar proxy kisi wajah se skip ho (ya koi naya exploit aaye), layout check abhi bhi khada hai. Do taale ek darwaze pe — ek toot jaye toh doosra hai.

(Roadmap mein bhi yeh fix ho gaya hai — concept O ab "proxy se auth-check" nahi, balki "layout `auth()` protection + proxy routing" likha hai. 4.4.4 ke baad roadmap wala section update dekhega.)

## Deep Dive — Code Same Hai, Toh Fark Kahan Hai? (Layout vs Proxy)

Ab ek baat jo Step 1 aur Step 2 ka code dekhne waale almost har kisi ko confuse karti hai — shayad tumhe bhi. Dono files mein `auth()` dikhta hai, dono mein check hota hai ki logged-in hai ya nahi, dono mein redirect hota hai. Toh fark kya hai? Code same lagta hai — **fark code ka nahi, layer ka hai.** Aur yahi confusion isliye dangerous hai kyunki isi ki wajah se log aaj bhi security proxy/middleware mein rakh dete hain. Poori baat code se samjho.

**Yeh dekho — CVE se pehle ka pattern, jo tutorials mein (aur shayad tumhare apne project mein bhi) chalta tha:**

```tsx
// OLD: app/dashboard/layout.tsx — khaali! sirf children wrap
export default function DashboardLayout({ children }) {
  return <>{children}</>;
}
```

```ts
// OLD: app/middleware.ts — protection SIRF yahan
export function middleware(request: NextRequest) {
  const isLoggedIn = request.cookies.has("session");
  const isProtected = request.nextUrl.pathname.startsWith("/dashboard");

  if (isProtected && !isLoggedIn) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
}
```

- Layout mein **kuch nahi** — bas children ko wrap karta hai. Koi check nahi, koi session nahi.
- Saara protection middleware mein — `isLoggedIn` (cookie hai?), `isProtected` (dashboard pe ja raha hai?), dono ho toh redirect.

**Attack — CVE-2025-29927, basic level pe:**

```bash
curl -H "x-middleware-subrequest: middleware" http://localhost:3000/dashboard
```

Next.js ke andar "subrequest" ka concept tha — jab app khud andar se request bhejti hai, toh middleware dobara nahi chalna chahiye. Yeh special header us system ko fool kar deta tha: Next ko lagta tha "is request pe middleware already chala hai" → **middleware skip.** Aur layout khaali tha → check bacha hi nahi → page bina login khul gaya. **Protection ek hi jagah thi, wo jagah skip ho gayi, protection khatam.**

**Fix wahi hai jo Step 1 mein kiya — check layout mein:**

```tsx
// NEW: app/dashboard/layout.tsx — check ab YAHAN
export default async function DashboardLayout({ children }) {
  const session = await auth();
  if (!session) {
    redirect("/login");
  }
  return <>{children}</>;
}
```

Same attack ab dobara karo — middleware skip ho jaye, koi fark nahi (security usme hai hi nahi) — layout **ab bhi chalta hai**, kyunki layout page ka hissa hai, saamne ka filter nahi.

**Mental model — filter vs page ka hissa:**

```
/dashboard ki request
   │
   ├─ proxy.ts ──► alag layer, app ke SAAMNE ──► SKIP ho sakti hai (CVE wala case)
   │
   └─ layout.tsx ──► page ka HISSA (render ka wrapper) ──► skip impossible
        │
        └─ page.tsx
```

Proxy ek optional filter hai jo app ke saamne laga hai — CVE ne prove kiya filter hataya ja sakta hai. Layout render ka wrapper hai — `/dashboard` ka data paane ke liye layout se guzre bina koi raasta nahi, kyunki render hi layout ke andar hota hai. `x-middleware-subrequest` header bhejne se layout nahi hat sakta — layout "render hone ka" hissa hai, filter nahi.

**Same code, alag layer — stake table:**

| Check | Layer | Galat ho / skip ho toh kya hota hai |
|---|---|---|
| `req.auth` → routing rule | `proxy.ts` | Sirf UX glitch — logged-in user login page pe dikh jaayega. Data leak nahi |
| `auth()` → redirect | `layout.tsx` | **Data breach** — bina login data mil gaya. Yahi asli security hai |

Isliye ek hi line ka rule yaad rakho — **"Jo page protect karna hai, uska layout check chhod ke kahin aur rakha toh skip ho sakta hai."** Proxy wala auth check ek feature hai (UX routing); layout wala auth check security hai.

## What It Is NOT

- **Proxy ≠ security boundary.** Proxy ko bypass kiya ja sakta hai (CVE wala case) — isliye security layout mein hai. Proxy sirf routing ka shortcut hai.
- **`proxy.ts` = `middleware.ts` ka simple rename nahi** — Next 16 mein yeh Node.js runtime pe chalta hai aur docs isko routing ke liye recommend karte hain. Concept same, role ab clear hai.
- **`auth()` wrapper wala proxy = har request pe full auth nahi** — wrapper session verify karta hai (fast check), par heavy logic proxy mein mat daalo (har request pe chalta hai — isko lightweight rakho).
- **Layout check + proxy redirect = duplicate nahi** — alag-alag kaam: layout security (bypass-proof), proxy UX (logged-in user ko login pe na dikhana).

## Common Mistakes

- **Security sirf proxy mein rakhna (layout khaali chhodna)** — CVE-2025-29927 wala pattern. Proxy skip ho sakta hai — aur layout khaali ho toh bachta kuch nahi, poora data khul jaata hai. Layout check hamesha rakho.
- **`matcher` bhoolna** — bina matcher ke proxy har request pe chalega, static assets bhi — slow app.
- **Login↔Dashboard redirect loop** — agar proxy mein "protected route → /login" aur login page mein "logged in → /dashboard" dono ho, toh koi edge case mein loop ban sakta hai. Isliye proxy ka rule sirf "logged-in + /login → /dashboard" rakha (ek hi direction).
- **Proxy mein heavy kaam** — har request pe chalta hai (images, fonts bhi agar matcher wide ho). Jitna halka, utna behtar. Data fetch/auth logic layout/actions mein.
- **`req.auth` bhoolna aur cookie khud parse karna** — `export default auth(...)` wrapper use karo, woh session de deta hai. Manual cookie parsing proxy mein galat aur risky.

## Nutshell

Protected routes ka recommended pattern: **layout mein `await auth()` + `if (!session) redirect("/login")`** — yeh main security hai (bypass-proof, server-side). **`proxy.ts`** (Next 16 ka middleware) sirf routing ke liye — Auth.js ke `auth()` wrapper se `req.auth` session milta hai, aur logged-in user `/login` pe jaye toh `/dashboard` redirect. Code dono jagah `auth()` se milta hai — fark layer ka: proxy skip ho sakti hai (CVE), layout page ka hissa hai jo skip nahi ho sakta. CVE-2025-29927 ki wajah se auth enforcement proxy mein nahi rakhi jaati — layout/server code mein rakhi jaati hai.
