Soch — jis bhi website pe tu aaj se pehle gaya hoga, wahan ek cheez zaroor thi: **login.** YouTube, GitHub, Instagram, Gmail — sab bolte hain "sign in karo." Aur login karne ke baad site tujhe yaad rakhti hai — "Hello Pravin" dikhaati hai, tera naam, teri profile. Par yeh ek ajeeb cheez hai agar tu sochta hai toh. HTTP protocol toh har request ke saath bhool jaata hai ki tu kaun hai — usko koi memory nahi. Phir site tujhe kaise yaad rakhti hai? Isi sawaal ka jawab Batch 4 ka foundation hai — **cookies aur sessions.**

Batch 3 mein humne data **change** karna seekha — Route Handlers (REST) aur Server Actions dono approaches, Reviews & Ratings App mein practice ki. Ab ek nayi problem aa rahi hai. Reviews tab tak chal jayega jab tak koi bhi review daal sakta hai. Par jab data **user-specific** ho — dashboard, profile, "sirf mera draft" — toh server ko janna padega ki **yeh request kiski aa rahi hai.** Isi ka naam hai **authentication** — aur yeh ab tak ke course ki sabse real-world cheez hai, kyunki har production app mein hoti hai.

## Do Projects — "Manual → Better" Pair

Roadmap ke end mein ek summary table hai — "Manual → Better" pairs. React course jaisa hi pattern: **pehle problem mehsoos karo, phir solution samjho.** Auth iska perfect example hai, kyunki yahan "Manual" mein asli chizein hain jo samajhni zaroori hain:

**Manual (4.2–4.3):** **Login Demo v1** — password hashing (bcryptjs), users store, session cookie khud set/read karna. Ye production ke liye nahi hai — **samajhne ke liye hai.** Isme woh sab kuch hai jo "login" ke andar actually hota hai, jo library chhupa deti hai.

**Better (4.4.x):** **Login Demo v2** — Auth.js (NextAuth) + GitHub OAuth. Yeh wahi hai jo YouTube tutorials mein dikhta hai — real external OAuth setup, "Sign in with GitHub" button, proper session handling. Isme security edge-cases library handle karti hai jo manual mein miss karna bahut aasaan hai.

**Framing yaad rakho (Batch 3 jaisa hi):** Manual galat nahi hai — yeh **foundation** hai. Auth.js isliye "better" hai kyunki production mein login itna critical hai ki khud likhne ki galti bahut mehengi pad sakti hai. Pehle manual se samjho *kya ho raha hai*, phir Auth.js se dekho *library kitna shortcut deti hai.*

## Login Demo v1 — Manual (4.2, 4.3)

Roadmap kehta hai: *"bahut basic, cookie-based session khud set/read karke (sirf samajhne ke liye, production mein use nahi karenge)."*

- **4.2** — Hashing: password kabhi plaintext mein store nahi hota. `bcryptjs` se hash karna (salt kya hai, rainbow-table se bachao kyun), `users.json` file store, **register** Server Action jo naya user `hashPassword()` se banaye (duplicate email check), login Server Action jo `comparePasswords` se verify kare, aur session cookie **set** karna.
- **4.3** — Cookie **read** karke `/secret` route protect karna (layout-level check — "bina login redirect"), logout, aur security warnings (httpOnly, sameSite, secure).

---

## Login Demo v2 — Auth.js + GitHub OAuth (4.4.x)

Roadmap kehta hai: *"same feature, proper auth library se (OAuth provider ya credentials)."* Hum **GitHub OAuth** use karenge:

- **Real external setup** — GitHub pe OAuth app banayenge (Settings → Developer settings), client ID + secret milenge, callback URL configure karenge. Yeh wahi hai jo YouTube wale karte hain.
- **4.4.1** — `next-auth` install, root `auth.ts` config, `[...nextauth]` route handler, custom login page.
- **4.4.2** — Session server mein (`auth()`) aur client mein (`SessionProvider` + `useSession`) — navbar mein "Hello, <naam>" dikhana.
- **4.4.3** — Protected routes ka **recommended** tareeka: main security `layout.tsx` mein `auth()` + `redirect()` se, aur `proxy.ts` sirf routing ke liye. Yahan yeh bhi samjhenge ki **auth proxy mein kyun nahi rakhna chahiye** (CVE-2025-29927 — Next 16 ke baad yeh officially discouraged hai). Roadmap mein bhi yeh fix hoga.
