4.4.1 mein login ho gaya — "Sign in with GitHub" se session cookie set hui (`authjs.session-token`). Par abhi tak humne session ka **use** nahi kiya. Koi page nahi bol raha "Hello, Pravin" — woh feel nahi aayi jo har real app mein aati hai. Soch — Instagram kholte hi top pe tera naam/avatar dikhta hai. Woh naam kahan se aata hai? Session se. Ab hum wohi banayenge: **dashboard page** jisme logged-in user ka email dikhega (server side), aur **navbar** jisme naam + sign out button hoga (client side). 

Is file mein ek important cheez samjhenge — session ko **server components** mein kaise padhte hain aur **client components** mein kaise — kyunki dono ka tareeka alag hai.

## Step 1: Server Components — `auth()`

4.3 mein `getSession()` likha tha — cookie padh ke user file se dhoondhna. Auth.js ka version usi ka `auth()` hai — bas library ka. Aur 4.3 wala rule yahan bhi lagta hai: **session padhna server-side hota hai, `await` karna padta hai.**

**File:** `app/dashboard/page.tsx` (nayi file)

```tsx
import { auth } from "@/auth";

export default async function DashboardPage() {
  const session = await auth();

  return (
    <main>
      <h1>Dashboard</h1>
      <p>Logged in as: {session?.user?.email}</p>
    </main>
  );
}
```

- **`import { auth } from "@/auth"`** — 4.4.1 mein `auth.ts` se jo export mila tha, wahi. `@/auth` root `auth.ts` ko point karta hai.
- **`await auth()`** — session object return karta hai. `session.user` mein GitHub se aaya user data: `name`, `email`, `image` (avatar URL) — yeh wahi profile data hai jo Auth.js ne OAuth callback mein GitHub se fetch kiya tha (4.4 ka flow, step 7).
- **`session?.user?.email`** — `?.` isliye kyunki `auth()` `null` return kar sakta hai (logged out). TypeScript bhi yahi expect karta hai.

**Notice kiya — kitna simple hai?** 4.3 mein `getSession()` ke liye cookie parsing + user lookup + null handling khud likhi thi. Ab `auth()` ek line mein session de deta hai. **Yahi Auth.js ka shortcut hai.**

Abhi `/dashboard` unprotected hai — bina login bhi khulega (sirf `Logged in as: ` khali dikhega). Protection 4.4.3 mein aayegi. Ab pehle client wala hissa.

## Step 2: Client Components — Problem Aur Solution

Ab ek naya problem. Navbar chahiye jisme **client component** ho (kyunki logout button click handler chahiye, dropdown etc.). Par **client component JavaScript browser mein chalta hai — aur woh httpOnly cookie padh nahi sakta.** 4.1 wala rule yaad hai? `httpOnly` cookie JS se chhupi rehti hai — browser ka JS `document.cookie` se bhi nahi dikhta.

Toh client component session kaise jaane? Auth.js ka solution: **session ek endpoint se milta hai** — `/api/auth/session` — jo server-side cookie padh ke session ka JSON return karta hai. Client component usse `fetch` kar sakta hai. Par har component ko khud fetch karna padta? Nahi — isliye **`SessionProvider`** hai:

- `SessionProvider` layout mein pura app wrap karta hai
- Woh session ko ek baar fetch karke **React context** mein rakhta hai (context = app-wide shared data)
- Koi bhi client component `useSession()` se woh data le leta hai — **bina khud fetch kiye**

Soch zomato — har restaurant apna menu alag-alag print karke door pe nahi chipkaata; ek hi jagah (app-level) menu hai, aur har jagah wahi dikhta hai. `SessionProvider` wahi app-level session store hai.

## Step 3: Layout Mein `SessionProvider`

**File:** `app/layout.tsx` (update — `SessionProvider` wrap karo)

```tsx
import type { Metadata } from "next";
import "./globals.css";
import Navbar from "./components/Navbar";
import { SessionProvider } from "next-auth/react";

export const metadata: Metadata = {
  title: "Create Next App",
  description: "Generated by create next app",
};

export default function RootLayout({
  children,
}: Readonly<{
  children: React.ReactNode;
}>) {
  return (
    <html lang="en">
      <body>
        <SessionProvider>
          <Navbar />
          {children}
        </SessionProvider>
      </body>
    </html>
  );
}
```

- **`SessionProvider`** — `next-auth/react` se import (client-side helper). Isse `Navbar` aur saare pages (client wale hisse) `useSession()` use kar sakte hain.
- **`Navbar` layout ke andar** — toh har page pe dikhega. SessionProvider ke andar rakha kyunki Navbar hi client session use karega.
- **`"use client"` nahi lagaya** — layout Server Component rehta hai, sirf `SessionProvider` (jo khud client component hai) use kar raha hai. Client component ko Server Component ke andar use kar sakte ho — bas provider ko props pass mat karo jo functions hain. Isliye `metadata` wala pattern waise hi rehta hai.

## Step 4: Navbar — `useSession` Ke Teeno States

**File:** `app/components/Navbar.tsx` (nayi file)

```tsx
"use client";

import { useSession, signIn, signOut } from "next-auth/react";

export default function Navbar() {
  const { data: session, status } = useSession();

  return (
    <nav style={{ display: "flex", justifyContent: "space-between", padding: 12 }}>
      <span style={{ fontWeight: "bold" }}>MyApp</span>
      <div>
        {status === "loading" && <span>Loading...</span>}
        {status === "unauthenticated" && (
          <button onClick={() => signIn()}>Sign In</button>
        )}
        {status === "authenticated" && (
          <div style={{ display: "flex", gap: 8 }}>
            <span>{session?.user?.name}</span>
            <button onClick={() => signOut()}>Sign Out</button>
          </div>
        )}
      </div>
    </nav>
  );
}
```

**`useSession()` do cheezein deta hai** — `data` (session ya null) aur `status`. Aur `status` ki **teen states** hoti hain — yeh samajhna zaroori hai:

| Status | Matlab | Navbar kya dikhata hai |
|---|---|---|
| `"loading"` | Session abhi fetch ho raha hai (page load pe) | "Loading..." |
| `"unauthenticated"` | Fetch ho gaya, session nahi | "Sign In" button |
| `"authenticated"` | Session mila | Naam + "Sign Out" |

- **`signIn()`** — bina argument ke, `pages.signIn` pe bhejta hai (4.4.1 mein `/login` set kiya tha) — user wahan "Sign in with GitHub" button dekhega.
- **`signOut()`** — session cookie delete + redirect. **Client side se directly call kiya** — `next-auth/react` ka version, Server Action wale `signOut` (auth.ts se) se alag hai.
- **`session?.user?.name`** — GitHub ka display name. `?.` kyunki `data` null ho sakta hai.

**Server vs client — kab kya?** Server component mein `await auth()` (Step 1), client mein `useSession()`. Fark ek table mein:

| | `auth()` (server) | `useSession()` (client) |
|---|---|---|
| **Kahan** | Server Components, Route Handlers, Server Actions | Client Components |
| **Data kaise** | Seedha cookie padhta hai | `SessionProvider` se (fetch `/api/auth/session`) |
| **`await`?** | Haan — async function | Nahi — hook + `status` |
| **Loading state** | Khud manage (async flow) | `status === "loading"` built-in |
| **Kab use** | Protected data, server logic | Interactive UI (navbar, buttons, dropdowns) |

**Rule of thumb:** Jo data server se hi dikhna chahiye (protected page ka content) — `auth()`. Jo UI interactive hai aur har jagah chahiye (navbar) — `useSession()`. Client mein `auth()` use nahi ho sakta (httpOnly cookie), server mein `useSession()` bekaar hai (context client ka concept hai).

## What It Is NOT

- **`useSession()` session "client-side secure" nahi banata** — data display ke liye hai, security ke liye nahi. Client ka data hamesha manipulable hai; asli check server pe hota hai (4.4.3).
- **`SessionProvider` = session storage nahi.** Woh sirf session ko ek baar fetch karke context mein rakhta hai — asli session cookie server-side hai.
- **Client components "logged in" state ke hisaab se UI change kar sakte hain, par protected DATA kabhi client fetch se nahi aana chahiye** — data wala rule 4.3 wala hi hai: server check.
- **`signOut()` client-side wala ≠ server action wala `signOut`** — dono same kaam karte hain (cookie delete), par alag jagah use hote hain: client button mein `next-auth/react` wala, server logic mein `@/auth` wala.

## Common Mistakes

- **`SessionProvider` bhoolna** — bina provider ke `useSession()` error deta hai ("useSession must be wrapped in a SessionProvider").
- **Server component mein `useSession` use karna** — hook hai, `"use client"` chahiye. Server component ke liye `auth()`.
- **`status === "loading"` handle na karna** — pehli render pe session abhi aaya nahi hota; bina loading check ke `session?.user` undefined reh jayega aur UI flicker karegi.
- **Client mein protected data render karna** — navbar naam dikhana theek hai, par sensitive data client fetch se kabhi nahi. Server component + `auth()`.
- **`signOut()` ke baad redirect missing** — `signOut()` option `{ callbackUrl: "/" }` de sakte ho, warna default page pe hi rehta hai.

## Nutshell

Session do jagah use hoti hai: **server** mein `await auth()` (cookie seedha padhta hai — dashboard jaisa protected data) aur **client** mein `useSession()` (SessionProvider context se — navbar jaisa interactive UI). `useSession()` ka `status` teen states deta hai: `loading` / `unauthenticated` / `authenticated`. Navbar: loading → "Loading...", unauthored → Sign In, authenticated → naam + Sign Out.

1. Client component httpOnly cookie kyun nahi padh sakta, aur `SessionProvider` iska kya solution hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `httpOnly` attribute cookie ko JavaScript se chhupa deta hai — browser ka JS `document.cookie` se bhi nahi padh sakta. Client component browser mein chalta hai, toh seedha cookie access nahi kar sakta. Solution: Auth.js ka `/api/auth/session` endpoint hai jo server-side cookie padh ke session ka JSON deta hai. `SessionProvider` ise ek baar fetch karke React context mein rakhta hai — phir har client component `useSession()` se bina khud fetch kiye session le leta hai.

</details>

2. Server component mein `auth()` aur client mein `useSession()` — kaunsi situation mein kaunsa use karna chahiye?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Rule of thumb: protected data server se — `auth()`. Interactive UI har jagah — `useSession()`. Dashboard ka content (email, profile) `auth()` se kyunki woh server-side render hota hai aur cookie padh sakta hai. Navbar ka naam/sign-out `useSession()` se kyunki usme click handlers (interactivity) hain jo client chahiye. `useSession()` sirf display ke liye hai — usse kabhi sensitive/protected logic mat chalao.

</details>

3. `status` ki teen states kya hain aur loading state handle na karne pe kya problem hoti?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `loading` (session abhi fetch ho raha hai), `unauthenticated` (session nahi), `authenticated` (session hai). Pehli render pe session abhi aaya hi nahi hota — agar loading check na ho, toh `status` pehle "unauthenticated" jaisa behave karega (session undefined), UI galat dikhegi aur jab fetch complete hogi toh flash change hoga. Loading state se smooth transition milta hai — "Loading..." dikhao, phir correct state.

</details>

4. `auth()` async hai, `useSession()` nahi — yeh fark kahan se aata hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `auth()` server-side function hai jo seedha cookie padhta hai — async I/O operation hai, isliye `await` karna padta hai. `useSession()` ek React hook hai jo `SessionProvider` ke context se data leta hai (jo pehle se fetch ho chuka hai) — koi blocking operation nahi, isliye sync return hota hai. Fark isliye hai ki ek data "server se abhi le raha hai", doosra "context se already-loaded data le raha hai."

</details>

5. Navbar mein session user ka naam dikhaya — kya isi tarah client mein protected data dikhana theek hai? Kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Nahi — fark hai. Navbar ka naam display-only data hai, jiska leak hone se koi security issue nahi. Protected data (profile details, private content, actions) client fetch se kabhi nahi aana chahiye — kyunki client request ko koi bhi manipulate kar sakta hai, aur asli check server pe hi hota hai. Display ke liye session context theek hai, par "kis cheez tak access hai" ka decision hamesha server component + `auth()` se.

</details>
