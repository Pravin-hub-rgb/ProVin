4.2 mein login banaya — password hash se verify kiya, aur browser ke paas `sessionId` cookie chali gayi. Par cookie ko **use** toh karna hai na? Abhi toh bas set hui hai — koi page nahi bol raha "yeh bandaa logged-in hai." Jaise coat-check mein token lene se kaam nahi hota — coat wapas lene ke liye token dikhana padta hai. Yahi hai 4.3 ka kaam: cookie **read** karna, ek `/secret` route banana jo bina login ke redirect kare, aur **logout** banana. Iske baad Login Demo v1 poora ho jayega.

## Step 1: Session Read Helper — Cookie Se User Tak

### Concept — Session Pattern Ka Aakhri Hissa

4.1 mein session ka poora chakra dekha tha: cookie mein sirf id → server ke paas record → id se user. 4.2 mein humne record **banaya** (cookie mein userId daala). Ab record ko **read** karna hai — cookie se id nikaalo, aur users file se user dhoondo.

Pehle ek chhota upgrade — `lib/users.ts` mein abhi sirf `getUserByEmail` hai (login ke liye), par ab user ko **id** se dhoondhna hai. Ek function aur add karo:

**File:** `app/lib/users.ts` (update — `getUserById` add karo)

```ts
import { readFileSync } from "fs";
import path from "path";

const filePath = path.join(process.cwd(), "app", "lib", "users.json");

export type User = {
  id: number;
  email: string;
  passwordHash: string;
};

export function getAllUsers(): User[] {
  const data = readFileSync(filePath, "utf-8");
  return JSON.parse(data);
}

export function getUserByEmail(email: string): User | null {
  const users = getAllUsers();
  return users.find((u) => u.email === email) ?? null;
}

export function getUserById(id: number): User | null {
  const users = getAllUsers();
  return users.find((u) => u.id === id) ?? null;
}
```

`getUserById` — wahi `find()` wala pattern, bas id se match karta hai.

Ab asli helper — yeh session pattern ka **ek hi jagah** wala function hai. Poore project mein jahan bhi "current user" chahiye, wahi `getSession()` call hoga — alag-alag jagah cookie parsing likhne ki zaroorat nahi (DRY).

**File:** `app/lib/session.ts` (nayi file)

```ts
import { cookies } from "next/headers";
import { getUserById } from "./users";

export async function getSession() {
  const cookieStore = await cookies();
  const sessionId = cookieStore.get("sessionId")?.value;
  if (!sessionId) return null;

  const userId = Number(sessionId);
  const user = getUserById(userId);
  return user;
}
```

Line by line:

- **`cookieStore.get("sessionId")?.value`** — cookie ka value nikaalo. `.get()` cookie nahi mili toh `undefined` deta hai — `?.` se safe access.
- **`if (!sessionId) return null`** — cookie hi nahi toh user bhi nahi. **`null` = "logged out."** Yehi return type hai — caller ko clear signal: user mila ya nahi.
- **`Number(sessionId)`** — cookie ki value string hoti hai (`"1"`), par users file mein id number hai (`1`). Convert karna zaroori hai — warna `find((u) => u.id === "1")` kabhi match nahi karega (string vs number).
- **`getUserById(userId)`** — record lookup. User nahi mila toh `null` return hoga — yeh bhi "logged out" hi hai (jaise purani cookie ho jo kisi deleted user ki hai).

**Notice kiya?** Ye function **async** hai — `cookies()` ko `await` karna padta hai (4.1 wala rule). Toh `getSession()` ko bhi hamesha `await` karo.

## Step 2: Logout Action — Cookie Ko Khatam Karna

Login ka ulta — cookie **delete** karo, aur login page pe bhej do. Wahi Server Action, wahi `cookies()` (delete ki permission bhi sirf Server Actions/Route Handlers ko hai).

**File:** `app/actions.ts` (update — `logoutAction` add karo, aur login ka redirect `/secret` pe karo)

```ts
"use server";

import { cookies } from "next/headers";
import { redirect } from "next/navigation";
import bcrypt from "bcryptjs";
import { getUserByEmail } from "./lib/users";

export type LoginState = {
  error?: string;
};

export async function loginAction(prevState: LoginState, formData: FormData) {
  const email = formData.get("email");
  const password = formData.get("password");

  if (typeof email !== "string" || typeof password !== "string") {
    return { error: "Email aur password dono chahiye" };
  }

  const user = getUserByEmail(email);
  if (!user) {
    return { error: "Email ya password galat hai" };
  }

  const isMatch = await bcrypt.compare(password, user.passwordHash);
  if (!isMatch) {
    return { error: "Email ya password galat hai" };
  }

  const cookieStore = await cookies();
  cookieStore.set("sessionId", String(user.id), {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    maxAge: 60 * 60 * 24 * 7,
  });

  redirect("/secret");
}

export async function logoutAction() {
  const cookieStore = await cookies();
  cookieStore.delete("sessionId");
  redirect("/login");
}
```

Do changes:

- **`loginAction` ka redirect ab `/secret` pe hai** — 4.2 mein `/` pe bhej rahe the, par ab protected route exist karta hai, toh login hone waala seedha wahan.
- **`logoutAction`** — `cookieStore.delete("sessionId")` se cookie khatam, phir `redirect("/login")`. Login hone ke baad `/secret` pe jana tha, logout ke baad wapas login pe. Bina cookie ke `/secret` ab bhi protect hoga (agle step mein).

## Step 3: Protected Layout — `/secret` Ko Lock Karna

Ab ek route banate hain jo **sirf logged-in users** ko dikhe. Ek folder `app/secret/` banao, aur usme ek `layout.tsx` daalo. Kyon layout — page nahi?

**Kyunki layout `secret` ke andar ke saare pages (aur future pages) ko ek saath protect karta hai.** Agar sirf page mein check karte, toh aaj ka `page.tsx` protect hota, par kal koi `secret/settings/page.tsx` bana toh usme bhi check likhna padta. Layout ek baar, sab ke liye.

**File:** `app/secret/layout.tsx` (nayi file)

```tsx
import { redirect } from "next/navigation";
import { getSession } from "../lib/session";

export default async function SecretLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const user = await getSession();
  if (!user) {
    redirect("/login");
  }
  return <div>{children}</div>;
}
```

- **`children: React.ReactNode`** — layout wala standard props pattern (Batch 1 se jaan pehchan).
- **`await getSession()`** — server-side session check.
- **`if (!user) redirect("/login")`** — logged out user ko login page pe bhej do. **Yeh hi protected route ka core pattern hai**: session check karo, nahi hai toh redirect.

**Ek important baat — yeh check deliberately server-side hai.** Client component mein `useEffect` se check karoge toh page pehle render ho jaayega, phir redirect hoga — flash dikhega, aur data bhi client tak pahunch chuka hoga. Server-side check se request aate hi redirect — protected data kabhi client tak jaata hi nahi. **Route protection hamesha server pe karo** — yeh hi Next 16 ka recommended pattern hai (4.4.3 mein iska aur karan milega).

**File:** `app/secret/page.tsx` (nayi file)

```tsx
import { getSession } from "../lib/session";
import { logoutAction } from "../actions";

export default async function SecretPage() {
  const user = await getSession();

  return (
    <main>
      <h1>Secret Page</h1>
      <p>Logged in as: {user?.email}</p>
      <form action={logoutAction}>
        <button type="submit">Logout</button>
      </form>
    </main>
  );
}
```

- **`await getSession()`** — layout ne check kar liya ki user logged-in hai, ab page ko user chahiye display ke liye. (Layout aur page dono alag-alag `getSession()` call kar rahe hain — Next.js isse deduplicate kar deta hai, par concept ke liye: har server component apna data khud le sakta hai.)
- **`user?.email`** — `?.` isliye kyunki `getSession()` ka return type `null` bhi ho sakta hai (TypeScript wala guard). Layout ne redirect toh kiya, par page ko apne type ke hisaab se safe rehna padta hai.
- **`<form action={logoutAction}>`** — Notice kiya? **Koi client component nahi!** Server Actions ko Server Component ke form se bhi bind kar sakte hain — koi `useActionState` nahi chahiye kyunki logout ko pending state ya error display ki zaroorat nahi. Button click → action chala → cookie delete → redirect. Bas.

## What It Is NOT

- **Ye session "real session store" nahi hai.** Isme session id ka record file ke `id` hi hai — koi expiry tracking server pe nahi, koi session table nahi. Agar cookie delete na karo toh 7 din tak valid hai (cookie ki maxAge). Production mein session expiry, revocation, aur store sab properly manage hote hain — Auth.js yeh sab deta hai.
- **Layout check ≠ proxy routing.** Humne check `/secret` ke layout mein kiya. 4.4.3 mein `proxy.ts` dekhenge jo **routing level** pe bhi kaam kar sakta hai (jaise login hua user `/login` pe jaye toh dashboard bhejo) — par security check layout mein hi rehta hai, wahi recommended hai.
- **Ye auth "login hone pe kya hota hai" ka poora manual demo hai** — ab isko production-grade banane ka time aa gaya.

## Common Mistakes

- **Check sirf page mein karna** — kal koi naya page bana toh woh unprotected. Layout mein karo, saare children protect ho jaate hain.
- **`Number(sessionId)` bhoolna** — cookie value string hai, users file ki id number. Bina convert ke match kabhi nahi hoga.
- **Client-side check karna** — `useEffect` mein session check = data pehle client tak pahunchta hai, phir redirect. Server-side check hamesha.
- **`logoutAction` mein cookie delete karna bhoolna** — sirf redirect karo toh cookie wahi rehti hai, wapas `/secret` pe jaoge toh phir logged-in dikhega.
- **Login aur logout ke redirect galat set karna** — login → `/secret`, logout → `/login`. Ulti direction mein user phans jaata hai.

## Nutshell

`getSession()` — cookie se id nikaalo, users file se user dhoondo, nahi toh `null`. Protected route = layout mein `await getSession()` + `if (!user) redirect("/login")` — server-side, ek jagah, saare children ke liye. Logout = Server Action mein `cookieStore.delete("sessionId")` + redirect. Login ka redirect ab `/secret` pe. Login Demo v1 complete — hashing, session set, session read, protection, logout — **sab kuch khud likha.**

**In Your Own Words**

1. `getSession()` kyun `null` return karta hai cookie nahi milne pe — error throw karne ki jagah? Caller isse kaise use karta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `null` ka matlab hai "logged out" — yeh ek normal situation hai, error nahi. Har page/action alag tarike se handle kar sakta hai: layout redirect karega login pe, koi public page "Hello guest" dikhayega, koi action "pehle login karo" error dega. Agar `throw` karte toh har jagah try/catch lagana padta, aur "logged out" ko error maanna galat hai — yeh toh expected state hai. `null` se caller ko decision lene ki freedom milti hai.

</details>

2. `/secret` ki protection layout mein kyun rakhi, page mein nahi — bina layout ke kya problem hoti?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Layout `secret/` folder ke saare pages ko wrap karta hai. Page mein check karo toh sirf wohi ek page protected hai — kal agar `secret/settings` ya `secret/account` banao, toh unmein alag se check likhna padega, aur koi bhool gaya toh woh route khula reh jaayega. Layout mein ek baar check = poora folder locked. Protection "default-on" ho jaati hai — naya page banao, automatically protected.

</details>

3. Session check server-side kyun hona chahiye, client-side `useEffect` mein kyun nahi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Client-side check mein page pehle render ho jaata hai (protected content browser tak pahunch jaata hai), phir useEffect chal ke redirect karta hai — user ko flash dikhta hai aur data expose ho chuka hota hai. Server-side check request aate hi ho jaata hai: session nahi toh redirect, aur protected data server se kabhi jaata hi nahi. Security ke liye data ko client tak pahunchne se pehle hi rokna chahiye — woh sirf server pe possible hai.

</details>

4. `logoutAction` mein kya-kya hota hai, aur agar cookie delete bhool jaayein toh kya hoga?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Logout mein do kaam: cookie delete (browser ke paas session ka proof khatam) aur login page pe redirect. Agar cookie delete bhool jao aur sirf redirect karo, toh cookie browser ke paas wahi rehti hai — user wapas `/secret` pe jaayega toh phir se logged-in dikhega, logout hua hi nahi. Delete hi asli logout hai, redirect sirf UX hai.

</details>

5. `/secret` build mein "ƒ (Dynamic)" kyun dikhta hai — koi aur static route kyun nahi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Kyunki `/secret` (aur uska layout) `cookies()` read karta hai — cookie har request pe alag ho sakti hai, toh page ka content har request pe alag ho sakta hai (kisi ke liye redirect, kisi ke liye content). Isliye Next.js ise static prerender nahi kar sakta — har request pe server par fresh render hota hai (ƒ = dynamic). Static routes wahi rehte hain jinka content request se change nahi hota.

</details>
