## Step 1: Password Hashing — Password Ka Kya Hota Hai

### Concept — Plaintext Kyon Galat Hai

Soch ek app jisme passwords seedhe save hote hain (`password: "super-secret-123"`). Ab wahan **data breach** ho jata hai — hacker ko users ki file mil jaati hai. Uske paas ab **har user ka actual password** hai. Aur dikkat yeh hai ki log ek hi password har jagah use karte hain — toh hacker woh password unke Gmail pe bhi try kar sakta hai. Ek breach, sab jagah talaash.

Solution ka naam hai **hashing.** Hash ek **one-way function** hai — isme password se ek jumble string ban jaati hai, par us jumble se wapas password nahi ban sakta. Jaise mixer mein aata daala toh dough banta hai, par dough se wapas original ingredients alag nahi kar sakte. Toh agar breach ho bhi jaye, hacker ko sirf jumble strings milti hain — **woh useless hain** agar password strong hai.

Ab ek chhota problem — agar do log same password use karein (`"password123"`), toh unke hashes bhi same honge. Hacker yeh pattern dekh ke anjaam laga sakta hai ("yeh dono accounts ka password same hai"). Iske liye **salt** hota hai — har user ke liye ek random string hash se pehle mila di jaati hai. Same password, different salt → different hash. Aur precomputed tables se bachne ke liye bhi (yeh rainbow-table attack hota hai — hacker pehle se popular passwords ke hashes bana ke rakh leta hai aur match karta hai; salt se woh table bekar ho jaati hai).

### Library — `bcryptjs`

Hash banane ke liye **bcryptjs** use karenge — sabse popular password hashing library. `bcryptjs` (pure JavaScript version) isliye chunenge kyunki isme native compilation nahi hoti — kisi bhi system pe turant chal jaati hai. (`bcrypt` naam ki doosri library bhi hai jisme C code compile hota hai — isliye woh kabhi-kabhi setup mein problem deti hai.)

Install karo:

```bash
npm install bcryptjs
```

### Syntax — Do Functions

bcryptjs ka poora kaam do functions mein hai:

```ts
bcrypt.hash(password, saltRounds)      // hash banata hai (async)
bcrypt.compare(password, hash)         // check karta hai: password hash se match karta hai? (async)
```

`saltRounds` ek number hai jo batata hai hash banana **kitna mehenga** hai — 12 ka matlab hash banana intentionally slow hai (lagbhag 250ms). Slow isliye chahiye kyunki agar hacker ko hashes mil bhi jayein, toh brute-force (har password try karna) bhi utna slow hoga. **Kabhi 10 se kam mat rakhna, 12 standard hai.**

### Code — `app/lib/password.ts`

Har project mein ek jagah se hashing handle karna chahiye — do cheezein: hash banana, aur compare karna. Wahi DRY wala 3.4.1 pattern hai.

**File:** `app/lib/password.ts` (nayi file)

```ts
import bcrypt from "bcryptjs";

export async function hashPassword(password: string): Promise<string> {
  const saltRounds = 12;
  const hashedPassword = await bcrypt.hash(password, saltRounds);
  return hashedPassword;
}

export async function comparePasswords(
  password: string,
  hashedPassword: string
): Promise<boolean> {
  const isMatch = await bcrypt.compare(password, hashedPassword);
  return isMatch;
}
```

Notice kiya? Dono functions **async** hain — bcrypt ka hashing intentionally slow hai (saltRounds ki wajah se), toh yeh heavy kaam hai jo async block karta hai. Toh `await` zaroori hai — bina await ke tumhe promise milega, match nahi.

### Test — Apna Pehla Hash

Chal ek baar console mein dekh lete hain hash kaisa dikhta hai. `node` kholo (ya terminal mein `node -e`):

```bash
node -e "const b=require('bcryptjs'); b.hash('super-secret-123', 12).then(h => console.log(h))"
```

Output kuch aisa hoga:

```
$2b$12$he0m9/YAyIfU4Te9XJaDfeCCx4RHmqREcaZDoH2o1MmBwW2CYdaYu
```

Notice karo:
- `$2b$` — bcrypt ka version tag
- `12` — saltRounds (hash kitna mehenga hai)
- Baaki random string — isme salt + hash dono mila hua hai

Aur yeh jo hash hai — isse wapas `super-secret-123` nahi nikal sakta. Ek tarfa hai. **Isi hash ko seed data mein daalenge.**

## Step 2: Users Data Layer — `users.json` + `lib/users.ts`

Batch 3 mein `comments.json` + `lib/comments.ts` ka pattern seekha tha — `fs` se file padhna. Wahi pattern yahan users ke liye. (Production mein DB hota hai — Batch 5 mein Prisma/Supabase aayega. Abhi file kaafi hai.)

**File:** `app/lib/users.json` (nayi file)

```json
[
  {
    "id": 1,
    "email": "pravin@example.com",
    "passwordHash": "$2b$12$he0m9/YAyIfU4Te9XJaDfeCCx4RHmqREcaZDoH2o1MmBwW2CYdaYu"
  }
]
```

**Notice kiya?** File mein **plaintext password nahi hai** — sirf hash hai. Yahan wo password hai jiska hash upar banaya tha (`super-secret-123`). **Apne liye apna password chuno aur apna hash generate karke daalo** — upar wali `node -e` command se. Seed data mein 2-3 users daal sakte ho, bas har ek ka apna hash.

Ab data layer file — padhne ke functions:

**File:** `app/lib/users.ts` (nayi file)

```ts
import { readFileSync } from "fs";
import path from "path";

const filePath = path.join(process.cwd(), "app", "lib", "users.json");

export type User = {
  id: number;
  email: string;
  passwordHash: string;
};

export function getAllUsers(): User[] {
  const data = readFileSync(filePath, "utf-8");
  return JSON.parse(data);
}

export function getUserByEmail(email: string): User | null {
  const users = getAllUsers();
  return users.find((u) => u.email === email) ?? null;
}
```

`User` type mein `passwordHash` field dekhi? Data layer mein user ka model **hash wala** hai — plaintext password wala koi field hi nahi hai. Type level pe hi rule set ho gaya ki password store nahi hota.

`getUserByEmail` — login ke waqt hum email se user dhoondhenge. `find()` pehla match deta hai, warna `undefined` — `?? null` se caller ko clear answer milta hai: user mila ya nahi.

## Step 3: Login Server Action — Email/Password Check + Cookie Set

Ab asli kaam — login ka Server Action. 4.1 mein bola tha: **cookie set karne ki permission sirf Server Actions aur Route Handlers ko hai.** Yahan wahi hota hai.

**File:** `app/actions.ts` (agr file pehle se hai — Batch 3 ke actions — toh **add** karo, warna nayi banao)

```ts
"use server";

import { cookies } from "next/headers";
import { redirect } from "next/navigation";
import bcrypt from "bcryptjs";
import { getUserByEmail } from "./lib/users";

export type LoginState = {
  error?: string;
};

export async function loginAction(prevState: LoginState, formData: FormData) {
  const email = formData.get("email");
  const password = formData.get("password");

  if (typeof email !== "string" || typeof password !== "string") {
    return { error: "Email aur password dono chahiye" };
  }

  const user = getUserByEmail(email);
  if (!user) {
    return { error: "Email ya password galat hai" };
  }

  const isMatch = await bcrypt.compare(password, user.passwordHash);
  if (!isMatch) {
    return { error: "Email ya password galat hai" };
  }

  const cookieStore = await cookies();
  cookieStore.set("sessionId", String(user.id), {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    maxAge: 60 * 60 * 24 * 7,
  });

  redirect("/");
}
```

Line by line:

- **`(prevState: LoginState, formData: FormData)`** — yeh `useActionState` ki signature hai (Batch 3 mein seekhi thi). Form ki state + form data dono milte hain. `LoginState` sirf error rakhne ke liye.
- **`formData.get("email")`** — form ke input ka value. `typeof !== "string"` check isliye kyunki `get()` kabhi `null` bhi de sakta hai — TypeScript ko bhi chahiye ki hum value use karne se pehle confirm karein.
- **`getUserByEmail(email)`** — user file mein dhoondho. **`!user` → wahi error.** Notice kiya? Email galat hone aur password galat hone pe **same error** hai — "Email ya password galat hai." Ye intentional hai — agar alag-alag error do ("email nahi mila"), toh hacker ko pata chal jaayega ki kaunse emails registered hain. Ye account enumeration attack hai, aur isse bachne ka tarika hi same error dena hai.
- **`await bcrypt.compare(password, user.passwordHash)`** — user ka stored hash se compare. `true` = password sahi.
- **`await cookies()`** — 4.1 mein bola tha, Next 15+ mein yeh async hai.
- **`cookieStore.set("sessionId", ...)`** — 4.1 ke teeno safety attributes yahan lag rahe hain: `httpOnly: true` (JS se chura nahi sakta), `secure` (production mein HTTPS pe hi jaayegi), `sameSite: "lax"` (CSRF se bachao). Plus `maxAge: 60*60*24*7` = 7 din.
- **Cookie value sirf `String(user.id)`** — 4.1 wala session pattern yaad hai? Cookie mein user ka data nahi, sirf id. Asli record (`users.json`) server ke paas hai. (Haan, abhi "book" file hi hai — yeh hi session id ka record hai. 4.3 mein isi se user dhoondhenge.)
- **`redirect("/")`** — login success pe home page. (4.3 mein `/secret` route banayenge toh redirect wahan update karenge.)

## Step 4: Login Form + Page — `useActionState` Ke Saath

Batch 3 mein `useActionState` seekha tha — form submit ho raha hai toh `isPending`, aur action ka return value `state` mein. Wahi pattern login ke liye:

**File:** `app/components/LoginForm.tsx` (nayi file)

```tsx
"use client";

import { useActionState } from "react";
import { loginAction, LoginState } from "../actions";

const initialState: LoginState = {};

export default function LoginForm() {
  const [state, formAction, isPending] = useActionState(
    loginAction,
    initialState
  );

  return (
    <form action={formAction}>
      <label>
        Email
        <input type="email" name="email" required />
      </label>
      <label>
        Password
        <input type="password" name="password" required />
      </label>
      <button type="submit" disabled={isPending}>
        {isPending ? "Login ho raha hai..." : "Login"}
      </button>
      {state.error && <p style={{ color: "red" }}>{state.error}</p>}
    </form>
  );
}
```

- **`"use client"`** — kyunki `useActionState` ek React hook hai — hooks sirf Client Components mein.
- **`useActionState(loginAction, initialState)`** — Server Action ko hook se bind kiya. Har submit pe action chalega, return state (error) mila, aur `isPending` submit ke waqt `true`.
- **`input name="email"` / `name="password"`** — inhi names se `formData.get()` ko values milti hain. **Name ka match zaroori hai** — agar input ka `name` change hua aur action ka `get()` wahi, toh data kabhi action tak nahi pahunchega.
- **`type="password"`** — browser dots dikhaata hai, input hide hota hai.
- **Error display** — action se `{ error: "..." }` return hua toh red mein dikhaya. `state.error &&` — error tabhi dikhega jab ho.

**File:** `app/login/page.tsx` (nayi file)

```tsx
import LoginForm from "../components/LoginForm";

export default function LoginPage() {
  return (
    <main>
      <h1>Login</h1>
      <LoginForm />
    </main>
  );
}
```

## What It Is NOT

- **Hashing ≠ encryption.** Encryption reversible hai — encrypted data ko key se wapas original bana sakte ho. Hashing one-way hai — wapas nahi banta. Password ke liye hash hi sahi hai kyunki server ko kabhi bhi original password nahi janna chahiye.
- **Yeh production auth nahi hai.** Isme koi rate limiting nahi (hacker infinite tries kar sakta hai), koi real session store nahi (session id ka record file ke id hi hai), koi lockout nahi. **Isliye roadmap isse "sirf samajhne ke liye" kehta hai** — 4.4 mein Auth.js isko production-grade banayega.
- **`bcryptjs` ≠ `bcrypt`.** Dono almost same API dete hain, par `bcrypt` mein native (C) code compile hota hai. Installation issues se bachne ke liye `bcryptjs` use kar rahe hain.

## Common Mistakes

- **Password plaintext store karna** — sabse badi galti. Data breach = sab passwords leaked. Hash hamesha.
- **`saltRounds` kam rakhna** — 10 se kam ka matlab brute-force aasaan. 12 standard hai.
- **`await` bhoolna** — `bcrypt.compare` async hai. Bina await ke `isMatch` ek promise hai, aur `if (promise)` hamesha truthy — matlab galat password bhi pass ho jaayega!
- **Cookie mein user ka data daalna** — cookie browser ke control mein hai, user khud edit kar sakta hai. Sirf id.
- **`cookies()` bina `await`** — Next 15+ mein async hai, compile error milega.
- **Alag-alag login errors** — "email nahi mila" vs "password galat" do — hacker ke liye email-list discovery ka free ticket.

## Nutshell

Password kabhi plaintext store nahi hota — `bcryptjs` se hash hota hai (one-way, salt ke saath, slow intentionally). Users `users.json` file mein hash ke saath rehte hain. Login Server Action: email se user dhoondo → `bcrypt.compare` se password check karo → `cookies().set("sessionId", userId, {httpOnly, secure, sameSite})` → redirect. Cookie mein sirf user ki id hoti hai — record server ke paas.

1. Password hashing kyun zaroori hai — agar encryption bhi password ko safe rakh sakti hai, toh hash hi kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Hashed password wapas original mein convert nahi ho sakta — encryption hota hai. Yahi iska fayda hai: server ko kabhi original password janna hi nahi chahiye. Agar breach ho jaye, toh hacker ke paas sirf hash honge jo strong password ke liye bekaar hain (aur salt ki wajah se precomputed tables bhi kaam nahi karti). Agar encryption use karte, toh key ke saath hacker saare passwords unlock kar sakta tha — ek breach, sab kuch.

</details>

2. `saltRounds: 12` ka kya matlab hai, aur yeh "slow" wala design intent kyun hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** SaltRounds batata hai hash banana kitna mehenga hai — 12 ka matlab lagbhag 250ms intentional delay. Yeh design by intention hai: legitimate user login pe ek baar 250ms wait karega, koi dikkat nahi. Par hacker ko hash crack karne ke liye har password guess pe 250ms lagenge — ek second mein sirf 4 tries, toh brute-force practically bekaar ho jaata hai. Fast hashing hacker ke kaam ko aasaan banati, isliye bcrypt slow hai.

</details>

3. Login mein email-galat aur password-galat ka error same kyun rakha? (Agar alag hota toh kya galat hota?)

<details>
<summary>Show Answer</summary>

**Sample Answer:** Agar error alag hote — "email nahi mila" vs "password galat" — toh koi bhi try kar sakta tha email list banane ke liye: har email pe login attempt, agar "email nahi mila" aaya toh wo email registered nahi hai, agar "password galat" aaya toh registered hai. Isse attacker ko pata chal jaata ki kaunse emails ka account hai (account enumeration) — phir unhi pe phishing ya brute-force karna. Same error se attacker ko yeh information nahi milti.

</details>

4. Session cookie mein sirf `userId` kyun rakhi — poora user object (naam, email) kyun nahi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Cookie browser ke control mein hai — user DevTools se apni cookie edit kar sakta hai. Agar cookie mein poora user object ho ("email: x, admin: true"), toh user usse badal ke apna fayda kar sakta hai — server ko pata nahi chalega ki cookie fake hai. Sirf id rakho toh user id ko koi bhi badal de, server har request pe file se fresh user record padh ke maan lega ki "yeh id ka user data file se aaya, cookie se nahi."

</details>

5. `useActionState` ka `isPending` login form mein kya kaam karta hai — aur bina iske kya problem hoti?

<details>
