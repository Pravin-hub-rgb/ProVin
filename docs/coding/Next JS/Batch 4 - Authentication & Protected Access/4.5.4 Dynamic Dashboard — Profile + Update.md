## Step 1: Data Layer — `profiles.json` + `profiles.ts`

4.5.1 ke plan ka second data source: bio ka storage. Dashboard/comment demo wala pattern — file-based data layer:

**File:** `app/lib/profiles.json` (nayi file)

```json

```

**File:** `app/lib/profiles.ts` (nayi file)

```ts
import { readFileSync, writeFileSync } from "fs";
import path from "path";

const filePath = path.join(process.cwd(), "app", "lib", "profiles.json");

export type Profile = {
  email: string;
  bio: string;
};

export function getProfileByEmail(email: string): Profile | null {
  const data = readFileSync(filePath, "utf-8");
  const profiles: Profile[] = JSON.parse(data);
  return profiles.find((p) => p.email === email) ?? null;
}

export function saveProfile(email: string, bio: string): Profile {
  const data = readFileSync(filePath, "utf-8");
  const profiles: Profile[] = JSON.parse(data);
  const index = profiles.findIndex((p) => p.email === email);

  const updated: Profile = { email, bio };

  if (index === -1) {
    profiles.push(updated);
  } else {
    profiles[index] = updated;
  }

  writeFileSync(filePath, JSON.stringify(profiles, null, 2));
  return updated;
}
```

**Identity email kyun hai, user id kyun nahi?** GitHub auth ke paas ek id hota hai (`session.user.id` — 4.4.2 mein type extend karke milta). Par email **do sources mein common key hai** — session se bhi milta hai, aur hamari file mein bhi. Id wala version auth config extend karke type-safety laata (4.4.2 ka JWT extend pattern) — email jaldi kaam kar deta hai. Learning project ke liye email sahi hai.

`saveProfile` ka naam "save" hai par kaam **upsert** hai — record nahi hai toh add, hai toh update (findIndex se). Insert + update ek hi function.

## Step 2: Server Action — `updateProfileAction`

**File:** `app/actions.ts` (update — 4.3 ka logoutAction hatao, yeh add karo)

```ts
"use server";

import { redirect } from "next/navigation";
import { revalidatePath } from "next/cache";
import { auth } from "@/auth";
import { saveProfile } from "./lib/profiles";

export type ProfileState = {
  message?: string;
  error?: string;
};

export async function updateProfileAction(
  prevState: ProfileState,
  formData: FormData
): Promise<ProfileState> {
  const session = await auth();
  if (!session?.user?.email) {
    redirect("/login");
  }

  const bio = formData.get("bio");
  if (typeof bio !== "string") {
    return { error: "Bio invalid hai" };
  }
  if (bio.length > 200) {
    return { error: "Bio 200 characters se zyada nahi ho sakta" };
  }

  saveProfile(session.user.email, bio.trim());
  revalidatePath("/profile");

  return { message: "Profile saved!" };
}
```

**Line by line:**

- `const session = await auth();` — Server Action server pe chalta hai, toh `auth()` call kar sakte hain (4.4.2 wala pattern). Session hamein **identity deta hai** — kiski bio save karni hai, user se poochne ki zaroorat nahi.
- `if (!session?.user?.email) redirect("/login");` — action bhi secure: bina session action call nahi hona chahiye. (Form protected page pe hai, par defense-in-depth — koi seedha action URL hit kare toh bhi ruk jaaye.)
- `formData.get("bio")` + type check + length check — Batch 3 wala validation pattern. Max 200 chars — form ke `maxLength` se double layer.
- `saveProfile(session.user.email, bio.trim());` — **email action se nahi, session se** — user form mein email bhej kar kisi aur ki bio nahi badal sakta. Yehi auth ka power.
- `revalidatePath("/profile")` — save ke baad page ka data naya ho (Batch 3).
- Return state — `useActionState` ko message/error dikhane ke liye.


**Kya badla (4.5.2 ke hardcoded se):**

| Hardcoded (4.5.2) | Dynamic (ab) | Source |
|---|---|---|
| `<img src="https://github.com/pravin.png">` | `session.user.image` | GitHub session |
| `Name: Pravin` | `session.user.name` | GitHub session |
| `Email: pravin@example.com` | `session.user.email` | GitHub session |
| `Bio: Next.js seekh raha hoon` | `profile?.bio ?? fallback` | `profiles.json` |

Server component: data nikalta hai (email, bio) aur form ko **initial value** bhejta hai. Form khud client hai (pending/error state dikhane ke liye — Batch 3 ka reason).

**File:** `app/components/ProfileForm.tsx` (nayi file — 4.4.2/4.5.2 LoginForm/4.5.2 form se pattern jodta hai)

```tsx
"use client";

import { useActionState } from "react";
import { updateProfileAction, ProfileState } from "../actions";

const initialState: ProfileState = {};

export default function ProfileForm({ initialBio }: { initialBio: string }) {
  const [state, formAction, isPending] = useActionState(
    updateProfileAction,
    initialState
  );

  return (
    <form action={formAction}>
      <label>
        Bio
        <textarea
          name="bio"
          defaultValue={initialBio}
          rows={4}
          maxLength={200}
        />
      </label>
      <button type="submit" disabled={isPending}>
        {isPending ? "Saving..." : "Save"}
      </button>
      {state.message && <p style={{ color: "green" }}>{state.message}</p>}
      {state.error && <p style={{ color: "red" }}>{state.error}</p>}
    </form>
  );
}
```

- `useActionState` + `isPending` — Batch 3 ka triple-state (pending/error/success) — button "Saving..." + disabled.
- `defaultValue={initialBio}` — pehli baar render pe file se bio form mein (uncontrolled input — controlled `value` use nahi kiya kyunki form reset complicated hota).
- `maxLength={200}` — client-side cap, action mein bhi 200 check — double layer (Batch 3).
- `state.message` green / `state.error` red — success aur error alag dikhte hain.

## Test — Poore Loop Ka

`npm run dev`:

1. **Login** → `/dashboard` pe jao → GitHub ka naam, email, avatar dikhna chahiye + bio fallback ("Koi bio nahi...").
2. `/profile` → bio textarea mein kuch likho → Save.
3. Dashboard pe wapas → **bio ab nayi dikhni chahiye** (revalidate + `getProfileByEmail`).
4. Dobara `/profile` → textarea mein saved bio pre-filled (initial value).
5. Bio empty karke Save → validation/fallback check.
6. Logout → `/dashboard` → `/login` redirect.

**Upsert test** (agla code khud chalao agar data layer check karna ho): pehli baar save → entry add (`profiles.json` mein email + bio), doosri baar save → update, missing email ke liye `getProfileByEmail` → `null`.

## What It Is NOT

- **Bio = identity nahi.** Bio file mein hai, naam/email/avatar session mein — **session ka data file mein save nahi hota** (GitHub ka hamesha fresh). Toh dashboard pe user apna naam change nahi kar sakta — kyunki naam ka source GitHub hai, hamari app nahi. Yehi architecture line hai: auth data vs app data.
- **`saveProfile` "sirf save" nahi** — upsert hai (insert + update). Pehli baar koi save kare toh entry add hoti hai.
- **Form value = server ka data, hamesha nahi.** `defaultValue` sirf initial render pe form bharata hai. Agar do tabs mein same profile khuli ho aur ek mein save karo — doosra tab purana value dikhaata rahega (revalidatePath tab render hi nahi karta jo already browser mein hai).

## Common Mistakes

- **Email form se mat lo** — action mein `formData.get("email")` karna security hole hai (koi bhi kisi aur ki email pass kar de). Email hamesha `auth()` se. Rule: **identity session se, data form se.**
- **`profile?.bio ?? ""` profile page pe** — agr `profile.bio` direct access karo aur entry null ho toh crash. `?.` + `??` dono chain karo.
- **Action mein `auth()` mat bhoolo** — bina check ke action sabko chalta hai (forms spoof kar sakte hain). Server component check ke saath hi action mein bhi.
- **`useActionState` ka return type** — action ka return `Promise<ProfileState>` type se match hona chahiye, warna TS error.

## Nutshell

Dynamic phase: `profiles.json` (empty array start) + `profiles.ts` (`getProfileByEmail` + `saveProfile` upsert) → `actions.ts` mein `updateProfileAction` (session se email, form se bio, validate, save, `revalidatePath`, state return) → dashboard session se naam/email/avatar + file se bio → profile page server data + client `ProfileForm` (`useActionState` triple-state + `defaultValue`) → `/secret` cleanup. Ab har user ka apna dashboard/profile dikhta hai, aur bio update hota hai.

**In Your Own Words**

1. Action mein email form se kyun nahi le rahe — session se lene ka kya fayda?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Form se email lena security hole hai — request ko koibhi tamper kar ke `email: "kisi_aur@mail.com"` bhej sakta hai, toh action uski bio update kar dega. Session se email lete hain toh jo browser authenticated hai usi ka email aata hai — request ka content manne ki zaroorat nahi kyunki identity server pe verified hai. Rule yaad rakho: identity session se, data form se.

</details>

2. `saveProfile` ko "upsert" kyun kehte hain — isme insert aur update kaise alag hota hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Ek function dono kaam karta hai: `findIndex` se file mein email dhundte hain. Index -1 (nahi mila) toh `push` — nayi entry add (insert). Index mila toh `profiles[index] = updated` — purani entry replace (update). Toh pehli baar save pe entry ban jaati hai, aur baad ke saves update karte hain — alag-alag add/update functions ki zaroorat nahi.

</details>

3. Dashboard pe `profile?.bio ?? "Koi bio nahi..."` — `?.` aur `??` alag-alag kya kaam kar rahe hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `profile?.bio` optional chaining hai — agar `profile` khud null ho (file mein entry nahi, user ne kabhi save nahi kiya) toh `.bio` access karte waqt crash ke bajaye `undefined` milta hai. `?? "Koi bio nahi..."` nullish coalescing hai — jo value `null` ya `undefined` ho uski jagah default text dikhaata hai. Dusra operator wahi fallback deta hai, pehla crash bachata hai.

</details>

4. Bio form mein `defaultValue` — controlled `value` se kya farak hai, aur yahan controlled kyun nahi use kiya?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `defaultValue` uncontrolled pattern hai — browser khud input ka state manage karta hai, pehli render pe initial value dikhaata hai. `value` controlled hota hai — React ke state se. Yahan uncontrolled sahi hai kyunki: (a) input ka data har keystroke pe React state mein rakhne ka koi fayda nahi, form submit pe `FormData` se mil hi jaata hai; (b) controlled mein reset/initial sync ki complexity aati hai. `defaultValue` hi "pehle server ka data dikhao, phir user jaisa chahe edit kare" ka simple tarika hai.

</details>

5. `revalidatePath("/profile")` ka kaam kya — save ke baad page khud kaise refresh hota?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Server Action save karke `revalidatePath("/profile")` call karta hai — yeh Next ko bataata hai ki profile route ka cached server component data ab stale hai, dobara render karo. Form submit pe React action complete hone ke baad page ka RSC payload naya aata hai — `getProfileByEmail` dobara file padhega aur nayi bio render hogi. Isi liye dashboard pe wapas jaake bhi bio nayi dikhti hai — same data layer, revalidated.

</details>
