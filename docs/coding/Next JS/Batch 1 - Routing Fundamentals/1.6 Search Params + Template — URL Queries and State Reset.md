# Search Params + Templates — URL Queries and State Reset (1.6)

## Where We Left Off

In 1.5.5 we finished the blog project: dynamic routes with `[slug]`, `getPostBySlug()`, `notFound()` handling, and `loading.tsx`/`error.tsx` states. The blog routes work by **path segments** — `/blog/my-first-post` → `params.slug = "my-first-post"`.

But real-world routing has another dimension: **URL query parameters** (`/blog?tag=react&page=2`) and a need for **state that resets on navigation**. That is what we cover here.

## The Two Dimensions of a URL

Every URL has two parts:

```
/blog/tags/react?sort=new&page=2
  ↑____________↑ ↑__________↑
     path          query (search params)
```

| What | Example | How Next.js gives it to you |
|---|---|---|
| **Path params** | `tags/react` | `params` prop (a folder with `[slug]`) |
| **Query params** | `sort=new&page=2` | `searchParams` prop (a plain object, no folder needed) |

## Search Params — Reading Query Parameters

Query parameters live in the `?` part of the URL. Next.js passes them to your page as a `searchParams` prop — **automatically**, no hooks, no `new URL()` parsing:

```tsx
// app/blog/[...slug]/page.tsx or app/blog/route/page.tsx
interface Props {
  searchParams: Promise<{ tag?: string; sort?: "new" | "old"; page?: string }>;
}

export default async function BlogIndex({ searchParams }: Props) {
  const { tag, sort, page } = await searchParams;  // await it — it's a Promise in Next 16

  // tag might be "react" or undefined (user didn't pass ?tag=...)
  // sort might be "new" or "old" — TypeScript enforces the union
  // page is a string like "2" — convert with Number(page)

  const posts = getPostsByTag(tag); // filter server-side
  const sorted = sort === "old" ? posts.reverse() : posts;
  const currentPage = Number(page) || 1;

  return (
    <div>
      <h1>Blog {tag ? `— tagged "${tag}"` : ""}</h1>
      {sorted.map(post => <BlogCard key={post.id} post={post} />)}
    </div>
  );
}
```

Key points:

1. **`searchParams` is a Promise** in Next 16 — you must `await` it before destructuring.
2. **Values are strings** — `?page=2` gives `"2"`, not `2`. Use `Number()` or `parseInt()`.
3. **Make it optional** — `tag?: string` means the query parameter may not be present. If you type it as required, the page breaks when the user visits without it.
4. **TypeScript validation** — `sort?: "new" | "old"` means only those two values are allowed.

### GET Forms — The Native Way

Want the user to change the URL? Use a **GET form** — the browser builds the query string for you:

```tsx
function BlogFilters() {
  return (
    <form method="get" action="/blog">
      <input name="tag" type="text" placeholder="Filter by tag..." />
      <select name="sort">
        <option value="new">Newest first</option>
        <option value="old">Oldest first</option>
      </select>
      <button type="submit">Filter</button>
    </form>
  );
}
```

When the user submits, the browser navigates to `/blog?tag=react&sort=new` — no JavaScript, no `useSearchParams()` hook. The page re-renders and reads the new `searchParams` prop.

## The Problem Layouts Can't Solve

In 1.2 you learned that `layout.tsx` **persists across navigations** — the header and footer stay in place, which is perfect for shared chrome.

But that creates a problem: **persistent state that should NOT survive navigation.** Consider a form inside a layout:

```tsx
// app/dashboard/layout.tsx
"use client";

import { useState } from "react";

export default function DashboardLayout({ children }) {
  const [search, setSearch] = useState("");  // ← this state PERSISTS across navigation!

  return (
    <div>
      <input value={search} onChange={e => setSearch(e.target.value)} placeholder="Search..." />
      {children}
    </div>
  );
}
```

Navigate from `/dashboard/settings` to `/dashboard/profile` → the search input **still shows what was typed** in settings. That is `layout.tsx` doing its job — but it is the **wrong behavior** for a search box. You want that input to reset.

## `template.tsx` — Remount on Every Navigation

A **`template.tsx`** file works exactly like a `layout.tsx` — it wraps its children — but with one critical difference:

> **A template remounts fresh on every navigation. A layout persists.**

```tsx
// app/dashboard/template.tsx  ← rename from layout.tsx
"use client";

import { useState } from "react";

export default function DashboardTemplate({ children }) {
  const [search, setSearch] = useState("");  // ← reset to "" on every navigation!

  return (
    <div>
      <input value={search} onChange={e => setSearch(e.target.value)} placeholder="Search..." />
      {children}
    </div>
  );
}
```

Now navigating from `/dashboard/settings` → `/dashboard/profile` **clears** the search input. The template component unmounts and remounts — `useState("")` runs again — `search` resets.

### Side-by-Side Comparison

| | `layout.tsx` | `template.tsx` |
|---|---|---|
| Remounts on navigation? | No — the same instance is reused | Yes — fresh component every time |
| State preservation | Persists across navigations | Cleared on every navigation |
| `useEffect` re-runs? | No (component never unmounts) | Yes (remount triggers mount effect) |
| Use when | Shared chrome (header, footer, sidebar) | Forms, modals, or anything that should reset |

### Using `template.tsx` and `layout.tsx` Together

You can use both in the same route:

```
app/dashboard/
├── layout.tsx          ← persists (header, sidebar)
├── template.tsx        ← remounts (search form resets)
├── page.tsx
└── [id]/
    └── page.tsx
```

The rendering order: **layout renders first** (persists), then **template renders inside it** (remounts), then the page. The layout's state survives; the template's state resets.

## Common Mistakes

- ❌ **Forgetting `await` on `searchParams`** — in Next 16 it is a Promise. Destructure first, then it returns `undefined`.
- ❌ **Using `useSearchParams()` (the hook) in a server component** — it only works in client components. The `searchParams` prop is the server-component-friendly way.
- ❌ **Putting `template.tsx` and `layout.tsx` at the same level** — they conflict. Use one or the other per route segment, or nest the template inside the layout.
- ❌ **Making `searchParams` required** — if the user visits the page without that query parameter, the page crashes. Use `tag?: string`.

## What It Is NOT

- **`template.tsx` is not a slower `layout.tsx`.** It is a different tool for a different job — choosing between persistence and reset, not about performance.
- **`searchParams` is not `useSearchParams()`.** The prop is passed automatically to server components (no hooks needed). The hook is for client components that need to read and react to URL changes dynamically.
- **`template.tsx` is not required.** Most routes just need `layout.tsx`. Only use templates when you need the remount behavior.

## In Your Own Words

1. Why does `searchParams` need to be `await`ed in Next.js 16?

<details>
<summary>Sample Answer</summary>

**Answer:** Next.js passes `searchParams` as a **Promise** (alongside `params`). You must `await` it before destructuring to get the actual query values. Without `await`, you get a Promise object, not the `{ tag: "react" }` object.

</details>

2. What is the practical difference between `layout.tsx` and `template.tsx` on navigation?

<details>
<summary>Sample Answer</summary>

**Answer:** `layout.tsx` persists — the same component instance stays mounted, so its state survives navigation. `template.tsx` remounts — the component unmounts and remounts fresh, so all its `useState` resets to initial values.

</details>

3. When would you use a GET form instead of `fetch` + `useSearchParams()`?

<details>
<summary>Sample Answer</summary>

**Answer:** When the query parameters drive server-rendered data (like filtering a list). A GET form submits via browser navigation — the URL updates, the page re-renders server-side, and `searchParams` props arrive with the new values. No JavaScript required, and the URL is shareable/bookmarkable.

</details>

4. Can you use both `layout.tsx` and `template.tsx` in the same folder? How do they nest?

<details>
<summary>Sample Answer</summary>

**Answer:** No — you cannot have both files at the same level (they conflict). But you can nest: a parent folder has `layout.tsx` (persists), and a child folder has `template.tsx` (remounts). The layout renders first and persists; the template renders inside it and remounts on each navigation.

</details>
