1.5.2 mein humne UI dekh liya — hardcoded data se. Blog list page mein posts ka array, single post page mein bhi wahi array. **Ab main tumhe ek problem dikhana chahta hoon jo hardcoded approach mein dikhi.**

Same posts array do jagah hai:
- `app/blog/page.tsx` mein (3 posts)
- `app/blog/[slug]/page.tsx` mein (3 posts, content ke saath)

Ab imagine karo — ek nayi post add karni hai. Do jagah array badalna padega. Agar ek jagah bhool gaye toh list mein post dikhegi, single page pe 404. **Data duplication = bugs ka source.** Isko solve karne ke liye hum data layer banate hain — `lib/posts.ts`.

---

## Ab Data Layer Banate Hain — Kya Kya Hoga Isme

Plan (1.5.1) se yaad karo — `lib/posts.ts` mein 3 cheezein:

1. **`Post` type** — data ka shape (type kyu, abhi samjhenge)
2. **`posts` array** — actual data (ab ek jagah)
3. **`getAllPosts()` + `getPostBySlug()`** — functions (pages inko use karenge)

Chalo ek-ek karke banate hain, aur **har decision ka karan** samajhte hain.

---

## Cheez 1 — `Post` Type: Kyon Chahiye?

`lib/posts.ts` ki pehli cheez — `Post` type:

```ts
// lib/posts.ts
export type Post = {
  slug: string;
  title: string;
  date: string;
  excerpt: string;
  content: string;
};
```

**Type kyun banate hain?** TypeScript ka poora fayda hi yahi hai — **compile time pe error pakdo, runtime pe nahi.** Ab ek example se samjho:

```ts
// Bina type ke — typo chhup jaata hai
const post = {
  slug: "pehla-post",
  title: "Mera Post",
  // content miss ho gaya
};

console.log(post.contnet);  // undefined — pata hi nahi chala, koi error nahi
```

```ts
// Type ke saath — TypeScript turant pakad leta hai
const post: Post = {
  slug: "pehla-post",
  title: "Mera Post",
  date: "7 Aug 2026",
  excerpt: "Test",
  // ❌ content missing — TypeScript compile-time error dega
};
```

**`Post` type ek contract hai** — "jo bhi is type ka ho, usme ye 5 fields zaroor honge." Har jagah jo post use hoti hai, wo is contract ko follow karti hai. Galat field, missing field — sab compile pe pakda jaata hai.

> **Analogy:** Type ek form jaise hai. Form mein kuch fields fixed hain (name, email). Agar koi form bina email ke bharta hai, toh check hota hai — TypeScript wahi check karta hai, par code ke liye.

## Cheez 3 — Functions: Kyon Chahiye, Kya Karte Hain

Ab functions. **Direct `posts` array ko import karke pages mein `posts.find()` kyun nahi karte?** Do reasons:

**Reason 1 — Detail chhupana (Abstraction).** Pages ko nahi pata hona chahiye ki data array hai ya database hai ya API hai. Wo bas "mujhe posts do" bolte hain. Function wahi deta hai. Aage (Batch 2, 2.5) jab data API se aayega, **pages ka code nahi badlega, sirf function ka andar** — yehi abstraction ka fayda hai.

**Reason 2 — Common logic ek jagah.** `posts.find(p => p.slug === slug)` — ye logic har page pe repeat hoti. Function mein rakho, har jagah use karo.

```ts
// lib/posts.ts
export function getAllPosts(): Post[] {
  return posts;
}

export function getPostBySlug(slug: string): Post | undefined {
  return posts.find((post) => post.slug === slug);
}
```

**Notice return types:**
- `getAllPosts(): Post[]` — typed array return
- `getPostBySlug(slug): Post | undefined` — **`| undefined` important hai.** Kya matlab? Agar slug se post nahi mili toh `undefined` return hoga (kyunki `find` undefined deta hai agar match na ho). TypeScript ko ye **declare** karna padta hai — "ye function `Post` bhi de sakta hai aur `undefined` bhi." Isse page pe `if (!post)` check karna compiler enforce karta hai — bhool gaye toh error.

**`export` keyword ka matlab:** is function/type ko dusri files import kar sakti hain. Bina `export` ke file ke andar hi private rehta hai.

## Nutshell

Data layer = type + data + functions. `Post` type ek contract hai (compile-time check). `posts` array ek jagah data (DRY). Functions abstraction dete hain (pages ko data source nahi pata chalta) aur common logic ek jagah. `Post | undefined` return type se compiler `if (!post)` check enforce karta hai.

## What It Is NOT

⚠️ **`lib/posts.ts` = "database" nahi.** Ye abhi ek static array hai. Data source hai, par real DB/API nahi. Iska **pattern** (type + functions) hi aage real data source mein migrate hoga.

⚠️ **Type = "runtime validation" nahi.** `Post` type sirf **compile-time** check karta hai — code likhte waqt. Runtime pe data aata kya hai, wo check nahi karta. (Runtime validation aage security batch mein.)

⚠️ **Data layer = "sirf ek file" nahi.** Ye ek *concept* hai — data + usse access karne ke functions ko alag rakhna. Jitna bada project, utni layers. Yahan chhota sa example hai.
