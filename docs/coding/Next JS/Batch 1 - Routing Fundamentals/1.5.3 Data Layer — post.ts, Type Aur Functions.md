# Data Layer - post.ts, Types & Functions (1.5.3)

In file 1.5.2 we built hardcoded UI for both the blog list (`/blog`) and the individual post (`/blog/:slug`). The structure renders, `<Link>` navigation works, and dynamic routing catches any slug.

## Broader Goal

Right now, the posts data is **duplicated** — hardcoded in both `blog/page.tsx` (for the list) and `blog/[slug]/page.tsx` (for the individual post). If you want to add a new post, you edit two files. If you want to switch from hardcoded data to a real API, you change two files.

The solution: extract the data into a **data layer** — `lib/posts.ts`. This is your single source of truth for posts, with helper functions to read from it.

The React course's "Data Layer" lesson introduced the same idea: a separate file (or service) that owns data logic, imported by component files.

## The Manual Way — Data Mixed Into Components

### React — Data Inside The Component

In React, data logic was often mixed directly into the component:

```tsx
// ❌ Data + UI mixed together
function BlogList() {
  const posts = [
    { title: 'My First Post', ... },
    { title: 'Second Post', ... },
  ];
  // ...render posts
}
```

If another component needs the same posts, it either re-declares the array (duplication) or you lift it to a parent and pass it down (prop drilling). Neither is clean.

## The Next.js Way — Data Layer

### Create `lib/posts.ts`

`lib/` means **library** — it is a convention for non-route utility files. Files in `lib/` are not routes (only files inside `app/` become routes). This is the right place for data logic.

```
app/
├── blog/
│   └── [slug]/
│       └── page.tsx
├── lib/
│   └── posts.ts        ← data layer (NOT a route)
└── page.tsx
```

### The Data Layer File

```ts
// app/lib/posts.ts

export type Post = {
  slug: string;
  title: string;
  content: string;
  excerpt: string;
  date: string;
};

export const posts: Post[] = [
  {
    slug: 'my-first-post',
    title: 'My First Post',
    excerpt: 'This is my first blog post.',
    content: 'This is the full content of my first blog post.',
    date: '2025-01-15',
  },
  {
    slug: 'second-post',
    title: 'Second Post',
    excerpt: 'Here is the second one.',
    content: 'The full content of the second post goes here.',
    date: '2025-02-20',
  },
  {
    slug: 'hello-world',
    title: 'Hello World',
    excerpt: 'Classic first post.',
    content: 'A classic hello world example.',
    date: '2025-03-01',
  },
];
```

### The `Post` Type

```ts
export type Post = {
  slug: string;
  title: string;
  content: string;
  excerpt: string;
  date: string;
};
```

This is a **TypeScript type** — it declares the shape of a post. Every function that works with posts can use `Post` as its parameter or return type. If a post is missing a field, TypeScript flags it at build time — catching bugs before they reach the browser.

> **Why TypeScript types?** In `.ts` files (no `x`), you define types. In `.tsx` files (with `x`), you write components. `posts.ts` is a data file, so `.ts`.

### The `GetPostBySlug` Helper Function

A data layer is not just an array — it provides **functions** to query the data. Instead of every page calling `.find()` itself, the data layer exposes a helper:

```ts
// app/lib/posts.ts (continued)

export function getPostBySlug(slug: string): Post | undefined {
  return posts.find((post) => post.slug === slug);
}

export function getAllPosts(): Post[] {
  return posts;
}
```

- `getPostBySlug(slug)` — returns one post, or `undefined` if not found.
- `getAllPosts()` — returns the full array.

### Why Helper Functions?

1. **Reusability** — both pages import `getPostBySlug` and `getAllPosts` from one place.
2. **Swappability** — when we switch from hardcoded array to real API calls, only `posts.ts` changes. Pages still call `getPostBySlug(slug)` — the interface stays the same.
3. **Type safety** — the `Post` type flows into every consumer. A typo in a field name is caught at compile time.

## Connecting The Data Layer To Pages

### Blog List Page

```tsx
// app/blog/page.tsx
import Link from 'next/link';
import { getAllPosts } from '@/lib/posts';

export default function BlogList() {
  const allPosts = getAllPosts();

  return (
    <main>
      <h1>My Blog</h1>
      <article>
        {allPosts.map((post) => (
          <div key={post.slug}>
            <h2>
              <Link href={`/blog/${post.slug}`}>{post.title}</Link>
            </h2>
            <p>{post.excerpt}</p>
          </div>
        ))}
      </article>
    </main>
  );
}
```

- `import { getAllPosts } from '@/lib/posts'` — named import from the data layer.
- `getAllPosts()` — fetches all posts. Returns `Post[]`.

### Individual Post Page

```tsx
// app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation';
import { getPostBySlug } from '@/lib/posts';

export default async function BlogPost({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = getPostBySlug(slug);

  if (!post) {
    notFound();
  }

  return (
    <article>
      <h1>{post.title}</h1>
      <p><em>Published on {post.date}</em></p>
      <p>{post.content}</p>
    </article>
  );
}
```

- `getPostBySlug(slug)` — looks up the single post for this URL slug.
- `if (!post) notFound()` — if no post matches, trigger a 404.
- `post.title`, `post.content`, `post.date` — TypeScript knows these exist because `post` is typed as `Post`. No runtime surprises.

### The Flow — End To End

1. User visits `/blog` → `blog/page.tsx` → `getAllPosts()` → renders the list.
2. User clicks a post → URL changes to `/blog/my-first-post` → Next.js routes to `[slug]/page.tsx`.
3. `[slug]/page.tsx` → `await params` → `slug = "my-first-post"` → `getPostBySlug("my-first-post")`.
4. If found → render. If not found → `notFound()` → 404 page.

The data layer (`lib/posts.ts`) is the **single source of truth**. Pages only call helper functions — they do not know or care whether the data is hardcoded or comes from an API.

## In Your Own Words

1. Why do we create `lib/posts.ts` separately from the page components? What problem does this solve?

<details>
<summary>Sample Answer</summary>

**Answer:** A page component should focus on rendering UI, not storing data. By extracting posts into `lib/posts.ts`, both pages (the list and the individual post) import from one source of truth — no duplication. If I want to switch from a hardcoded array to a real API later, I only change `lib/posts.ts`'s internal logic; every page keeps calling `getPostBySlug(slug)` and `getAllPosts()` unchanged. It is separation of concerns — data logic in the data layer, presentation logic in the component.

</details>

2. What is the purpose of the `Post` type, and what would happen if we removed it?

<details>
<summary>Sample Answer</summary>

**Answer:** The `Post` type defines the shape of a post (which fields exist and their types). With it, TypeScript checks at compile time that `post.title`, `post.content`, etc. exist and are strings. Without it, those fields are `any` — typos, missing fields, and wrong types would only surface at runtime as crashes, not at build time. The type is a contract that protects every file that imports posts data.

</details>

3. How does `getPostBySlug` returning `Post | undefined` affect the calling page? Why is the `if (!post)` check necessary?

<details>
<summary>Sample Answer</summary>

**Answer:** `Post | undefined` means the function might return a post OR nothing (when the slug does not match). TypeScript forces me to handle both cases. The `if (!post)` check catches the "not found" case and calls `notFound()`. If I skipped this check, TypeScript would complain that `post` might be `undefined` when I access `post.title` — which would crash at runtime. The check makes the "missing post → 404" path explicit and safe.

</details>

3. Why is `lib/posts.ts` named `.ts` and not `.tsx`?

<details>
<summary>Sample Answer</summary>

**Answer:** The `x` in `.tsx` is for files that contain JSX. `lib/posts.ts` has only types and functions — no JSX — so it is `.ts`. Page files use `.tsx` because they return JSX (`return <h1>...</h1>`). If you tried to put JSX in a `.ts` file, TypeScript would error.

</details>
