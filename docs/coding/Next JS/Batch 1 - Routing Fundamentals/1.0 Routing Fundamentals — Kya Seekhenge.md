## A — File-based Routing Basics

### Manual Approach — React Router

In React Router, routing looked like this:

```tsx
// App.tsx — React Router
import { Routes, Route } from 'react-router-dom';
import Home from './pages/Home';
import About from './pages/About';
import Contact from './pages/Contact';

export default function App() {
  return (
    <Routes>
      <Route path="/" element={<Home />} />
      <Route path="/about" element={<About />} />
      <Route path="/contact" element={<Contact />} />
    </Routes>
  );
}
```

Every route needed its own `<Route>` tag — path and element specified. Ten pages meant ten tags. Fifty pages meant fifty tags. A **manual config file**.

### Better Approach — Next.js File-based Routing

In Next.js, you **never write a route config.** The folder name **is** the URL path, and `page.tsx` inside it **is** the content.

```
app/
├── page.tsx          →  /          (home)
├── about/
│   └── page.tsx      →  /about
└── contact/
    └── page.tsx      →  /contact
```

Just create the folders, add `page.tsx` — the routes work automatically. No config, no setup.

### The Rule — Folder + `page.tsx` = Route

1. All route files must live inside the `app/` folder. A file outside `app/` will not become a route.
2. The route file must be named `page.js` / `page.tsx` (`.js` for JavaScript, `.tsx` for TypeScript).
3. The component must be a **default export** — without `export default`, Next.js cannot find the component and the route fails.

Follow these conventions and the file **automatically becomes a route** — nothing else to configure.

```tsx
// app/page.tsx → serves "/"
export default function Home() {
  return <div>Home</div>;
}
```

```tsx
// app/about/page.tsx → serves "/about"
export default function About() {
  return <div>About</div>;
}
```

**Why `export default`?** This is Next.js's contract. When you visit `/about`, Next.js looks inside `app/about/page.tsx`, finds the default export, and renders it. It is like you wrote the import yourself: `import About from './page'` — Next.js does this internally.

### What If the File Name Is Wrong?

Only `page.tsx` works as a route file. `index.tsx`, `Home.tsx`, or any other name will **not** become a route:

```
✅ app/about/page.tsx     →  /about  works
❌ app/about/index.tsx    →  not a route
❌ app/about/Home.tsx     →  not a route
```

### Unknown URLs → Automatic 404

Visit a route you never created (e.g. `/products`) → Next.js automatically shows a 404 page. It can be customized (1.4), but unmatched routes are handled for you out of the box.

### Nested Routes

A nested route = a route inside a route, e.g. `/about/profile`:

```
app/
└── about/
    ├── page.tsx          →  /about
    └── profile/
        └── page.tsx      →  /about/profile
```

Create the `profile` folder **inside** `about` and add its own `page.tsx` (default export) — `/about/profile` now works. Nesting can go as deep as needed:

```
app/
└── about/
    ├── page.tsx              →  /about
    └── profile/
        ├── page.tsx              →  /about/profile
        └── settings/
            └── page.tsx          →  /about/profile/settings
```

**Real-world example:** a blog — `/blog` lists posts; clicking one opens `/blog/first-post`, `/blog/second-post`. Folders nesting gives you that structure for free.

## B — Nested Layouts

### The Problem — Repeated Code

Let us say every page needs a header and footer. Without layouts, you would repeat the same header/footer in every `page.tsx`:

```tsx
// WITHOUT layouts — repeated in every page
export default function About() {
  return (
    <div>
      <nav>My Site</nav>
      <h1>About</h1>
      <footer>© 2026 My Site</footer>
    </div>
  );
}
```

If you have 10 pages, you repeat the header and footer 10 times. That violates the DRY principle.

### Manual Approach — React Router

In React Router, you would create a separate `Layout` component and wrap `<Routes>` in it:

```tsx
// App.tsx — React Router
import { Routes, Route } from 'react-router-dom';
import Layout from './components/Layout';

export default function App() {
  return (
    <Layout>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/about" element={<About />} />
      </Routes>
    </Layout>
  );
}
```

You had to create the Layout component, import it, wrap your routes — manual boilerplate.

### Better Approach — Next.js `layout.tsx`

In Next.js, create `app/layout.tsx`. **Every page in `app/` automatically renders inside this layout.** No wrapping needed — Next.js does it for you.

```
app/
├── layout.tsx        →  shared layout (applies to every page)
├── page.tsx          →  /
├── about/
│   └── page.tsx      →  /about
└── contact/
    └── page.tsx      →  /contact
```

### How `layout.tsx` Works

**The root layout (`app/layout.tsx`) is a special file.** It wraps every page — just like the `<Layout>{children}</Layout>` pattern from React. Whatever you put in the layout, every page renders as its child.

```tsx
// app/layout.tsx — the ROOT layout (only place <html>/<body> live)
import type { ReactNode } from 'react';

export default function RootLayout({ children }: { readonly children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <nav>My Site</nav>
        {children}
        <footer>© 2026 My Site</footer>
      </body>
    </html>
  );
}
```

Now the header and footer appear on **every route** (`/about`, `/contact`, ...) automatically. Anything you want common across the app goes in the root layout.

### Layout Persists Across Navigation

This is the key behavior: when you navigate between pages (say, `/about` → `/contact`), **the layout does not re-mount.** The header, footer, and even scroll position stay. Only `{children}` (the page content) swaps out.

In React Router, if the layout component re-mounted on each route change, the header would re-render too — losing state and scroll position. In Next.js, the layout mounts once and persists.

### Nested Layouts

A layout can also live **inside any route folder**, covering only that section of the tree:

```
app/products/
├── layout.tsx            →  applies to /products, /products/:id, /products/:id/reviews
├── page.tsx              →  /products
└── [id]/
    ├── page.tsx          →  /products/:id
    └── reviews/
        ├── page.tsx      →  /products/:id/reviews
        └── [reviewId]/
            └── page.tsx  →  /products/:id/reviews/:reviewId
```

```tsx
// app/products/layout.tsx — NO <html>/<body> here!
import type { ReactNode } from 'react';

export default function ProductLayout({ children }: { readonly children: ReactNode }) {
  return <div>{children}</div>;
}
```

- Nested layouts render **inside** the parent layout's `children` — the nesting stacks up.
- **Only root layout(s) contain `<html>` and `<body>`** — a nested layout with its own html/body causes an error. Nested layouts are plain wrappers.

## C — Dynamic Routes + Params

### Why Dynamic Routes

Fixed paths (`/about`, `/contact`, `/services`) work for static pages. But what if you have a blog with dozens or hundreds of posts? Creating a separate folder for each post is impossible. **Dynamic routes** solve this: a single page handles URLs based on dynamic data (an ID, a slug).

### `[slug]` — The Dynamic Segment

**Convention:** wrap the folder name in **square brackets**. That folder becomes a dynamic segment:

```
app/
├── blog/
│   ├── page.tsx          →  /blog          (list of posts)
│   └── [slug]/
│       └── page.tsx      →  /blog/:slug    (any slug — ONE page!)
```

```tsx
// app/blog/[slug]/page.tsx — catches ANY slug
export default async function BlogPost({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params; // Next.js 15: params is a Promise, must await
  return <h1>Blog Post: {slug}</h1>;
}
```

**Key points:**

- **The name inside brackets = the key you get in `params`.** Folder `[slug]` → `params.slug`. Use it to fetch the specific post data.
- **`params` is a Promise in Next.js 15+** — you must `await` it. The page becomes `async`.
- **URL `/blog/my-first-post`** → `params.slug = "my-first-post"`.
- **URL `/blog/anything-here`** → same single page catches it.

### The Contract — You Write It, Next.js Calls It

You write the function but **never call it yourself**. When a user visits `/blog/my-first-post`, Next.js does this internally:

```
BlogPost({ params: { slug: "my-first-post" } })
```

Think of it this way: you define the *shape* of what the function needs (`{ params }`), and Next.js fills in the value. It is the same **props pattern** from React — when React renders `<BlogPost params={...}>`, Next.js is the one calling the component.

### `export default` Is Required

In a Server Component, you **can** use `async`/`await` directly — the component waits for the promise to resolve before HTML is generated. If this were a Client Component (`"use client"`), you could not make it `async` (hooks can't be async). Instead, you would use `.then()`:

```tsx
// Client Component version
"useuse client";
export default function BlogPost({ params }) {
  useEffect(() => {
    params.then(({ slug }) => {
      // fetch with slug
    });
  }, []);
  return <div>Loading...</div>;
}
```

But for Server Components, `async` + `await` is the natural, clean pattern.

### Full Example — Blog with Dummy Data

```tsx
// app/blog/[slug]/page.tsx
const posts = [
  { slug: "my-first-post", title: "My First Post", content: "This is my first blog post." },
  { slug: "second-post", title: "Second Post", content: "Here is the second one." },
  { slug: "hello-world", title: "Hello World", content: "Classic first post." },
];

export default async function BlogPost({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const post = posts.find((p) => p.slug === slug);

  if (!post) {
    return <h1>Post not found</h1>;
  }

  return (
    <div>
      <h1>{post.title}</h1>
      <p>{post.content}</p>
    </div>
  );
}
```

## D — Loading, Error, Not-Found States

### Manual Approach — React

In React, handling loading, errors, and not-found was manual:

```tsx
// React — manually wrapping with Suspense
import { Suspense } from 'react';

<Suspense fallback={<div>Loading...</div>}>
  <BlogPost />
</Suspense>
```

```tsx
// React — ErrorBoundary was a class component
class ErrorBoundary extends React.Component {
  constructor(props) { super(props); this.state = { hasError: false }; }
  static getDerivedStateFromError() { return { hasError: true }; }
  render() {
    if (this.state.hasError) return <h1>Something went wrong</h1>;
    return this.props.children;
  }
}
```

```tsx
// React — catch-all route for 404
<Route path="*" element={<NotFound />} />
```

Each required its own setup — a Suspense wrapper, an ErrorBoundary class, a wildcard route. Lots of boilerplate.

### Better Approach — Next.js Special Files

Next.js has **three conventions** — put these files in your route folders, and they work automatically:

| File | When it shows |
|---|---|
| `loading.tsx` | While a page is loading data — shows a loading indicator |
| `error.tsx` | When an error is thrown — shows an error message |
| `not-found.tsx` | When a page is not found — shows a 404 |

```
app/
├── not-found.tsx              →  global 404
├── blog/
│   ├── page.tsx               →  /blog
│   └── [slug]/
│       ├── loading.tsx        →  blog post loading state
│       ├── error.tsx          →  blog post error state
│       └── page.tsx           →  /blog/:slug
```

### The Convention — `export default`

All three files (just like `page.tsx` and `layout.tsx`) require `export default`. Next.js looks for the default export of these files — a named export will not work.

```tsx
// loading.tsx / error.tsx / not-found.tsx — always:
export default function AnyName() {
  return (...);
}
```

The function name can be anything (`Loading`, `ErrorBoundary`, `NotFound`) — only the default export matters. The convention is to name them so the purpose is obvious.

### `loading.tsx` — Loading State

When a page fetches data (async), the user should see something while waiting. Create `loading.tsx`:

```tsx
// app/blog/[slug]/loading.tsx
export default function Loading() {
  return <p>Loading blog post...</p>;
}
```

Next.js **automatically wraps the page in Suspense** with this as the fallback. You do not need to manually `<Suspense>`. When `/blog/my-first-post` is requested, "Loading blog post..." shows first, then the real content appears once data is ready.

### `error.tsx` — Error Handling

When a page throws an error (network failure, API down), `error.tsx` catches it. Before the code, one important concept: **`error` and `reset` are passed in by Next.js** — you do not call the function yourself.

#### How `error` and `reset` Arrive

Just like `params` in 1.1 — **you write the function, Next.js calls it.** When `page.tsx` throws an error (a failed `fetch`, an API down), Next.js's error boundary catches it and calls your `error.tsx` with two arguments:

- `error` — the actual error object. `error.message` tells you what went wrong.
- `reset` — a **function** Next.js gives you. Clicking it asks Next.js to retry rendering the page.

```tsx
// app/blog/[slug]/error.tsx
"useuse client";  // error boundaries must be Client Components

export default function Error({ error, reset }: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>
      <p>{error.message}</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  );
}
```

- `error` is an object — `error.message` shows the readable message of what failed.
- `reset` is a **function** — you call it with `reset()`, not `reset`. It triggers Next.js to re-render the page (loading → fetch → render loop runs again).

**Think of it this way:** `error.tsx` is a special page that Next.js renders when something fails. It hands you two tools: `error` (what broke) and `reset` (try again). You just use them.

### `not-found.tsx` — Custom 404

When a page is not found, `not-found.tsx` renders:

```tsx
// app/not-found.tsx
export default function NotFound() {
  return (
    <div>
      <h2>404 — Page Not Found</h2>
      <p>This page does not exist.</p>
    </div>
  );
}
```

### `next/navigation` — Next.js's Navigation Toolbox

The `notFound()` call comes from `next/navigation`:

```tsx
import { notFound } from 'next/navigation';
```

`next/navigation` is a **module that ships with Next.js** — a toolbox of navigation helpers. Alongside `notFound()`, it also provides `redirect()`, `useRouter()`, `useParams()`, `usePathname()` — things we will use throughout the course. You do not install these separately — **Next.js ships them**, you just import.

This is the same pattern as React Router — you imported `useParams()` and `useNavigate()` from `react-router-dom`. The concept is identical; the package is `next/navigation` instead.

### `notFound()` — Manually Triggering a 404

`notFound()` tells Next.js: *"this page does not exist, show the 404."* Unlike `reset`, you **call it directly** — it does not return. Once you call `notFound()`, Next.js immediately renders the `not-found.tsx` page; any code after that line does not execute.

```tsx
// app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation';
import { getPostBySlug } from '@/lib/posts';

export default async function BlogPost({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = getPostBySlug(slug);

  if (!post) {
    notFound();  // slug not found → renders not-found.tsx
  }

  return <h1>{post.title}</h1>;
}
```

The flow: `getPostBySlug(slug)` returns the post, or `undefined` if the slug does not match. If `undefined`, call `notFound()` → Next.js renders `not-found.tsx`. **The URL was valid (`/blog/xyz`), but the data was not found — so we manually show 404.**

### Cheat Sheet — What Each File Gets

| File | What Next.js does | What the function receives |
|---|---|---|
| `page.tsx` (`BlogPage`) | Matches URL, calls the function | `params` (from dynamic URL segments) |
| `loading.tsx` (`Loading`) | Renders while data is loading | nothing |
| `error.tsx` (`Error`) | Called when something throws | `error` + `reset` |
| `not-found.tsx` (`NotFound`) | Renders when URL is not found | nothing |

The pattern: **you write the function, Next.js calls it.** Each special file gets what it needs from Next.js automatically.

## In Your Own Words

1. How did you set up routing in React Router, and how is Next.js different?

<details>
<summary>Sample Answer</summary>

**Answer:** In React Router, I wrote `<Route path="/about" element={<About />}>` for each route manually — a config file with every path and component. In Next.js, I create a folder `app/about/` and add `page.tsx` inside it — the route is created automatically. No config, no router library. The folder structure is the routing.

</details>

2. Why is `export default` required for `page.tsx`? Can I use a named export instead?

<details>
<summary>Sample Answer</summary>

**Answer:** Next.js looks for the **default export** of `page.tsx` to render. It internally does `import BlogPost from './page'` — only the default export. If you write `export function BlogPost()` (a named export) instead of `export default function BlogPost()`, Next.js gets `undefined` and the build fails. Named exports are for side data (like `revalidate`, `generateMetadata`) — the page component itself must be the default export.

</details>

3. How do you create a dynamic route in Next.js, and how do you get the value from the URL?

<details>
<summary>Sample Answer</summary>

**Answer:** Create a folder with square brackets: `[slug]`. Any URL after the parent route is captured — `/blog/my-first-post` gives `params.slug = "my-first-post"`. Inside `page.tsx`, I `await params` (it is a Promise in Next.js 15+) and destructure `slug`. One page handles any slug value.

</details>

4. When would `loading.tsx` show up, and when would you see it does not?

<details>
<summary>Sample Answer</summary>

**Answer:** `loading.tsx` shows while a Server Component is fetching data — Next.js wraps the page in Suspense automatically, and your loading component appears as the fallback. It does not show for static pages (which have no async data) — only for routes that actually suspend while loading.

</details>
