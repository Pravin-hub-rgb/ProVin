## Where We Left Off

In file 1.5.3 we built the data layer — `lib/posts.ts` with the `Post` type, `getPostBySlug(slug)` for single posts, and `getAllPosts()` for the list. The data is now separate from the pages.

## Broader Goal

This file **wires the dynamic route to the data layer**. The flow becomes complete end to end:

1. User visits `/blog/my-first-post`.
2. The URL slug `"my-first-post"` arrives as `params.slug`.
3. The page calls `getPostBySlug(slug)` to find the matching Post.
4. If found → render the post content.
5. If not found → call `notFound()` → 404 page renders.

The blog list page is also refactored to use `getAllPosts()` instead of its hardcoded array.

## The Wiring — Slug To Data Lookup

### The Dynamic Route Receives `params`

From file 1.3, recall: when a visitor goes to `/blog/my-first-post`, Next.js routes to `[slug]/page.tsx` and calls it with the URL data:

```tsx
// app/blog/[slug]/page.tsx
export default async function BlogPost({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;  // "my-first-post"
  // ...
}
```

The `slug` value comes from the URL — Next.js extracts it based on the folder name `[slug]`.

### Passing `slug` Into the Data Layer

Now that `getPostBySlug` exists in `lib/posts.ts`, the page imports and calls it:

```tsx
// app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation';
import { getPostBySlug } from '@/lib/posts';

export default async function BlogPost({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;

  // Look up the post by its URL slug
  const post = getPostBySlug(slug);

  // No match → trigger 404
  if (!post) {
    notFound();
  }

  return (
    <article>
      <h1>{post.title}</h1>
      <p><em>Published on {post.date}</em></p>
      <p>{post.content}</p>
    </article>
  );
}
```

### Step-by-Step Breakdown

**`const { slug } = await params`** — Next.js passes `params` as a Promise in version 15. The `await` unwraps it so `slug` is the actual string from the URL (e.g. `"my-first-post"`).

**`const post = getPostBySlug(slug)`** — Calls the data layer function. It searches the `posts` array for an entry where `post.slug === slug`. Returns the `Post` object if found, or `undefined` if not.

**`if (!post) { notFound() }`** — `getPostBySlug` returns `undefined` when no post matches. We check this and call `notFound()` — Next.js's function from `next/navigation` that switches the response to the 404 page (`app/not-found.tsx`).

**`{post.title}`**, **`{post.content}`**, **`{post.date}`** — After the `notFound()` check, TypeScript **narrows** `post` from `Post | undefined` to just `Post`. So accessing `.title`, `.content`, `.date` is guaranteed safe — TypeScript knows these exist.

### The Contract Between Page And Data Layer

```
[slug]/page.tsx              lib/posts.ts
-------------                ----------
1. receive params.slug   →   1. exports getPostBySlug(slug: string): Post | undefined
2. call getPostBySlug(slug)  →  2. returns Post or undefined
3. if !post → notFound()  ↩   3. (data layer just returns; page handles 404)
4. render post.title      ↩   4. (data layer owns the data; page owns the UI)
```

The page decides **what to do** when data is missing (404). The data layer decides **how to find** the data. Clean separation.

## Refactoring The Blog List Page

### Before — Hardcoded Array

```tsx
// OLD version — data duplicated in the page
const posts = [...];  // hardcoded array lived here

export default function BlogList() {
  return (
    <main>
      {posts.map((post) => (
        <div key={post.slug}>
          <Link href={`/blog/${post.slug}`}>{post.title}</Link>
        </div>
      ))}
    </main>
  );
}
```

### After — Data Layer Import

```tsx
// app/blog/page.tsx
import Link from 'next/link';
import { getAllPosts } from '@/lib/posts';

export default function BlogList() {
  const allPosts = getAllPosts();

  return (
    <main>
      <h1>My Blog</h1>
      <article>
        {allPosts.map((post) => (
          <div key={post.slug}>
            <h2>
              <Link href={`/blog/${post.slug}`}>{post.title}</Link>
            </h2>
            <p>{post.excerpt}</p>
          </div>
        ))}
      </article>
    </main>
  );
}
```

**Changes from the hardcoded version:**

- `import { getAllPosts } from '@/lib/posts'` — named import from the data layer.
- `getAllPosts()` — instead of referencing a local `posts` array, the page asks the data layer for all posts.
- `post.slug`, `post.title`, `post.excerpt` — all typed as `Post`, so TypeScript guarantees these fields exist.

### Why This Is Better — The Reusability Principle

1. **Single source of truth** — posts data lives only in `lib/posts.ts`. To add a new post, update one file, not two.
2. **The page does not store data** — it only renders what the data layer provides. The page's job is presentation.
3. **Swappable source** — when we later replace the hardcoded array with a real API `fetch`, only `lib/posts.ts` changes. Every page keeps calling `getAllPosts()` and `getPostBySlug()` — the interface stays the same, no page edits needed.

## In Your Own Words

1. After `getPostBySlug` returns `undefined`, how does that lead to a 404 page? Trace each step.

<details>
<summary>Sample Answer</summary>

**Answer:** When I visit `/blog/does-not-exist`, Next.js routes to `[slug]/page.tsx` with `params.slug = "does-not-exist"`. Inside the page, I call `getPostBySlug("does-not-exist")` — it searches the posts array, finds no match, and returns `undefined`. My code checks `if (!post)` — which is true — and calls `notFound()`. `notFound()` is imported from `next/navigation`; it tells Next.js "this page does not exist." Next.js then renders `app/not-found.tsx` as the response.

</details>

2. Why does TypeScript allow accessing `post.title` after the `if (!post) notFound()` check? What is this feature called?

<details>
<summary>Sample Answer</summary>

**Answer:** This is **type narrowing**. `getPostBySlug` returns `Post | undefined`. After `if (!post) { notFound(); }`, TypeScript knows that any code after this block only runs when `post` is **not** undefined — so it narrows `post` from `Post | undefined` to just `Post`. That means `post.title`, `post.content`, `post.date` are all safe to access without null checks. TypeScript uses the control flow analysis to track that `notFound()` (which never returns) eliminates the `undefined` branch.

</details>

3. What would happen if you removed the `if (!post) notFound()` check from the page? Would the app crash?

<details>
<summary>Sample Answer</summary>

**Answer:** Without the check, if `getPostBySlug` returns `undefined`, the page would try to render `post.title` — but `post` is `undefined`, so accessing `.title` throws a `TypeError: Cannot read properties of undefined`. This would trigger the `error.tsx` boundary instead of a clean 404. Even worse, TypeScript would flag this as an error at compile time because `post` is `Post | undefined` and you are accessing a property that only exists on the `Post` branch. The `if (!post) notFound()` guard makes the "post not found → 404" path explicit and prevents both the TypeScript error and the runtime crash.

</details>

4. How does the blog list page (`blog/page.tsx`) use the data layer differently from the individual post page (`[slug]/page.tsx`)?

<details>
<summary>Sample Answer</summary>

**Answer:** The list page calls `getAllPosts()` — fetches the entire array of posts and renders them all (title + excerpt in a list). The individual post page calls `getPostBySlug(slug)` — fetches a single post by its slug (from the URL params) and renders only that one post's full content. Same data layer (`lib/posts.ts`), same `Post` type, but two different query functions for two different needs: "give me all" vs "give me one by identifier."

</details>

The dynamic blog is now fully wired: URL slug → `getPostBySlug` → render or 404, with the list page using `getAllPosts`. The next file (1.5.5) adds **loading and error state files** alongside the blog pages so users get feedback when data operations are slow or fail.
