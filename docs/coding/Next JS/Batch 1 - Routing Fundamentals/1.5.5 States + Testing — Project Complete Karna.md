# States + Testing - Project Complete (1.5.5)

In file 1.5.4 we connected the dynamic route to the data layer: the slug from the URL flows into `getPostBySlug`, the post is found (or not), and `notFound()` handles missing posts. The blog list page now uses `getAllPosts()`.

## Broader Goal

So far the blog pages render **immediately** — the data is in-memory (`lib/posts.ts`), so there is no delay. But in a real app, data comes from an API — and APIs are slow or fail. This file adds **loading and error states** to the blog pages using the special files we learned about in 1.4:

- `loading.tsx` — shows while the page is preparing
- `error.tsx` — shows when something goes wrong

Even though our current data is fast, these files are important scaffolding. When we later swap the hardcoded data for real API calls, the loading/error experience is already handled.

## The Manual Way — States Mixed Into Pages

### React — Inline State Management

In React, you managed loading and error state inside the component:

```tsx
// ❌ React — loading/error mixed into the component
function BlogPost() {
  const [post, setPost] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch(`/api/posts/${slug}`)
      .then((res) => res.json())
      .then((data) => { setPost(data); setLoading(false); })
      .catch((err) => { setError(err); setLoading(false); });
  }, [slug]);

  if (loading) return <div>Loading...</div>;
  if (error) return <div>Error: {error.message}</div>;
  return <div>{post.content}</div>;
}
```

The component had to manage three pieces of state, three conditional renders, and the fetch logic all mixed together. Repetitive across every async page.

## The Next.js Way — Separate Files For Each State

### Split Into Three Files

Instead of one component with internal state, Next.js splits each state into its own file:

```
app/blog/
├── page.tsx          →  the list (main content)
├── loading.tsx       →  loading state
└── error.tsx         →  error state
```

Next.js automatically picks the right file based on the page's state — you never write `if (loading)` in the page.

## A — Loading State (`loading.tsx`)

### The Blog List Loading

When the list page is loading (e.g., fetching posts from an API), show a friendly message:

```tsx
// app/blog/loading.tsx
export default function BlogLoading() {
  return (
    <main>
      <h1>Loading blog posts...</h1>
      <p>Hang tight, we are fetching the latest posts.</p>
    </main>
  );
}
```

### How It Triggers

When `app/blog/page.tsx` becomes slow (in a real app, the `fetch` takes time), Next.js automatically renders `loading.tsx` as a fallback. You do not add `<Suspense>` manually — Next.js sees the file and handles it.

```tsx
// When this takes time:
export default async function BlogList() {
  const allPosts = await getAllPosts();  // ← if this is slow...
  return <main>...</main>;
}

// ...loading.tsx shows automatically
```

### The Individual Post Loading

Also create a loading state for the dynamic route:

```
app/blog/[slug]/
├── loading.tsx   →  loading for individual post
├── error.tsx     →  error for individual post
└── page.tsx      →  /blog/:slug
```

```tsx
// app/blog/[slug]/loading.tsx
export default function PostLoading() {
  return (
```

## B — Error State (`error.tsx`)

### The Blog List Error

When the list page crashes (e.g., the API returns 500), show an error message with a retry button:

```tsx
// app/blog/error.tsx
"use use client";  // error.tsx MUST be a Client Component

export default function BlogError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>
      <p>{error.message || "Could not load blog posts."}</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  );
}
```

### Key Points

- **`"use client"` at the top** — Required. Error boundaries need React hooks (`useTransition`) for the retry mechanism. Without this directive, the build fails.
- **`error.message`** — The error object's message. Shows a readable description of what broke ("Failed to fetch", "Network error", etc.).
- **`error.message || "fallback"`** — Sometimes `error.message` is empty. Use `||` to provide a fallback.
- **`reset`** — A **function** Next.js provides. Calling `reset()` (on button click) asks Next.js to retry rendering the page.

### The Individual Post Error

Create an error state for the dynamic route too:

```tsx
// app/blog/[slug]/error.tsx
"use use client";

export default function PostError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Failed to load post</h2>
      <p>{error.message || "Something went wrong."}</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  );
}
```

### Why Scoping Matters

- `app/blog/error.tsx` — catches errors in `/blog` (the list page).
- `app/blog/[slug]/error.tsx` — catches errors in `/blog/:slug` (individual posts).

If the blog list throws, only `app/blog/error.tsx` catches it. If a post page throws, only `app/blog/[slug]/error.tsx` catches it. **Nested error boundaries are scoped to their subtree.**

If I removed `app/blog/[slug]/error.tsx`, errors in post pages would bubble up to `app/blog/error.tsx`.

## Testing The States

### With Hardcoded Data — States Won't Trigger

Since `lib/posts.ts` is a synchronous array (no `fetch`), the data resolves instantly. The loading and error states will not show. This is expected — these files are **scaffolding for the real API**.

### When The API Comes

When we replace the hardcoded array with a `fetch` call:

```ts
// lib/posts.ts — future version
export async function getAllPosts() {
  return fetch('https://api.example.com/posts').then((res) => res.json());
}
```

Then:
- `loading.tsx` shows while the fetch is in progress.
- If the fetch fails, `error.tsx` shows with `error.message`.
- The `reset` button retries the whole flow.

## Cheat Sheet — State Files Summary

| File | Triggered By | Required Directive | Props |
|---|---|---|---|
| `loading.tsx` | Page is async/slow | None (Server Component) | none |
| `error.tsx` | Page throws/rejects | `"use client"` | `error`, `reset` |
| `not-found.tsx` | URL not found / `notFound()` | None (Server Component) | none |

### The `error` And `reset` Props — Recap

- `error: Error & { digest?: string }` — The thrown error object. `error.message` is the readable text.
- `reset: () => void` — Next.js provides this. Call `reset()` (parentheses — invoke the function) on a button click to retry. Do NOT render `{reset}` — it is a function, not a value.

### Client Component Rule For Error

Only `error.tsx` requires `"use client"`. `loading.tsx` and `not-found.tsx` are Server Components by default — no directive needed. This is because only the error boundary needs hooks for the retry mechanism.

## In Your Own Words

1. Why does `error.tsx` need `"use client"` and a `reset` function, while `loading.tsx` does not?

<details>
<summary>Sample Answer</summary>

**Answer:** `error.tsx` needs `"use client"` because it uses React hooks internally (like `useTransition`) to support the retry mechanism that `reset()` relies on. The `reset` function tells Next.js to re-render the page — hooks are needed to coordinate this across a re-render. `loading.tsx` just shows a static message while data loads — no hooks, no retry, so it stays a plain Server Component with no `"use client"` needed.

</details>

2. Where does `loading.tsx` for the blog list live, and where does the one for individual posts live? Why two different files?

<details>
<summary>Sample Answer</summary>

**Answer:** The blog list loading lives at `app/blog/loading.tsx` — it covers `/blog`. The individual post loading lives at `app/blog/[slug]/loading.tsx` — it covers `/blog/:slug`. Two files because they are in different route scopes — a loading state is scoped to the folder it lives in. Without `[slug]/loading.tsx`, individual posts would fall back to `app/blog/loading.tsx`. By having both, each route shows a context-appropriate message ("Loading posts" vs "Loading post").

</details>

3. What is the difference between `<button onClick={() => reset()}>` and `onClick={reset}`? Which is correct here?

<details>
<summary>Sample Answer</summary>

**Answer:** `onClick={reset}` passes the `reset` function as the event handler — Next.js calls it directly on click, with the click event as the argument. `onClick={() => reset()}` wraps it in an arrow function — I call `reset()` myself, ignoring the click event. Both work for triggering a retry. The wrapper `() => reset()` is safer if I wanted to do extra work (like logging) before resetting, but for a simple retry, `reset` passed directly is cleaner and more idiomatic.

</details>

4. In the current hardcoded setup, why do the loading and error states not trigger? When will they start working?

<details>
<summary>Sample Answer</summary>

**Answer:** The data lives in `lib/posts.ts` as a synchronous in-memory array — `getAllPosts()` returns instantly, no `fetch`, no network. Since nothing suspends or rejects, `loading.tsx` and `error.tsx` never activate. They will start working when we swap the hardcoded array for real API calls (async `fetch`) — the slow fetch triggers loading, and a failed fetch triggers the error boundary. The files are scaffolding: built now so the behavior is ready when the API layer arrives.

</details>
