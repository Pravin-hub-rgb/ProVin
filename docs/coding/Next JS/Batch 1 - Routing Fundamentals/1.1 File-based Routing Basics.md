## A — File-based Routing in Practice

### Setting Up the Project

First, scaffold the project. In React you would set one up with Vite + React Router. In Next.js, the framework **is** the project generator:

```bash
npx create-next-app@latest my-blog
```

- Pick TypeScript when prompted.
- Select the **App Router** (not Pages Router) — the default in modern Next.js.

Or use the shorter form:

```bash
npx create-next-app@latest my-blog --typescript --tailwind --eslint --app
```

### The Project Structure

After creation, `app/` is where routes live. The folder name becomes the URL path — no router config needed:

```
app/
├── layout.tsx     →  root layout (applies to every page)
├── page.tsx       →  /          (Home)
├── about/
│   └── page.tsx   →  /about
├── projects/
│   └── page.tsx   →  /projects
└── contact/
    └── page.tsx   →  /contact
```

Each route is just a folder + `page.tsx`. No `<Routes>`, no `<Route>` tags — the file system **is** the router.

### Writing the Home Page

```tsx
// app/page.tsx — serves "/"
export default function Home() {
  return (
    <main>
      <h1>Home</h1>
      <p>Welcome to the Portfolio / Blog Site</p>
    </main>
  );
}
```

**Convention:** the only requirement is `export default function <Name>()`. The name can be anything (`App`, `HomePage`, `MyProfile`) — Next.js cares only about the default export.

### Writing the About Page

```tsx
// app/about/page.tsx — serves "/about"
export default function About() {
  return (
    <main>
      <h1>About</h1>
      <p>This is my about page.</p>
    </main>
  );
}
```

No import from the home page. No route registration. The file lives in `app/about/` and it is the route `/about`. Done.

### Key Rules (Recap)

1. All route files go inside `app/`.
2. The file must be named `page.tsx` (or `.js`).
3. Must be a **default export** — if `export default` is missing, the route fails.

### The Result

Run `npm run dev` and you visit:

| URL | File |
|---|---|
| `http://localhost:3000/` | `app/page.tsx` |
| `http://localhost:3000/about` | `app/about/page.tsx` |
| `http://localhost:3000/projects` | `app/projects/page.tsx` |
| `http://localhost:3000/contact` | `app/contact/page.tsx` |

If the name is `index.tsx` or `Home.tsx` instead of `page.tsx` — the route does not work. The name **`page.tsx`** is the contract.

## B — The `baseUrl` Shortcut (`@`)

### The Problem — Relative Paths

In React/Vite, importing shared files used relative paths:

```tsx
// React — relative path confusion
import { posts } from '../../lib/posts';
import { getUser } from '../../../utils/user';
import type { Post } from '../../types/post';
```

Move the file one folder deeper → all the `../` break and imports need updating. It works, but it is fragile and unreadable.

### Better — `@/` Absolute Paths

Next.js solves this with `tsconfig.json`:

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["./*"]
    }
  }
}
```

With `"baseUrl": "."` and `"@/*": ["./*"]`, you can import from the **project root** using `@/`:

```tsx
// Next.js — absolute paths
import { posts } from '@/lib/posts';
import { getUser } from '@/utils/user';
import type { Post } from '@/types/post';
```

`@/` always means the project root — move the file anywhere, the imports still work. No more counting `../`.

### `next.config.js` — The Project Configuration

`next.config.js` is Next.js's **project-wide configuration file** — similar to Vite's `vite.config.js` or Webpack's `webpack.config.js`. It sits at the project root and configures how the build works:

```js
// next.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  reactStrictMode: true,
  // Add image domains, redirects, rewrites, etc. here
};
module.exports = nextConfig;
```

Most of the time you leave it alone — it ships with sensible defaults. When you need to configure something project-wide (an external image domain, redirects, environment variables), this is where it goes. We will return to it in later batches.

### `eslint` and `prettier`

`create-next-app` sets up **`eslint`** and **`prettier`** for you. These are code quality tools:

- **ESLint** (`eslint`: *linting*) checks code for errors and style violations — unused variables, missing keys in lists, etc.
- **Prettier** (`prettier`: *formatting*) auto-formats code on save — indentation, quotes, line length.

Run `npm run lint` to check for issues, `npx prettier --write .` to format everything.

## C — `Link` for Client-Side Navigation

### Manual Approach — `<a>` Tags

In React (or plain HTML), you navigated with `<a>` tags:

```tsx
// React — full page reload
<a href="/about">About</a>
```

`<a href="...">` triggers a **full page reload** — the browser downloads HTML, CSS, JS all over again. Slow. Loses in-memory state. Not ideal for SPAs.

### React Router's `<Link>`

React Router introduced `<Link>`:

```tsx
// React Router — client-side navigation
import { Link } from 'react-router-dom';
<Link to="/about">About</Link>
```

`<Link>` intercepts the click, uses the History API to change the URL without reloading, and re-renders the route — instant transition, no full page load. **This is client-side routing.**

### Next.js's `<Link>`

Next.js has its own `<Link>`:

```tsx
// Next.js — client-side navigation
import Link from 'next/link';

export default function Navbar() {
  return (
    <nav>
      <Link href="/">Home</Link>
      <Link href="/about">About</Link>
      <Link href="/projects">Projects</Link>
      <Link href="/contact">Contact</Link>
    </nav>
  );
}
```

Same idea as React Router's `<Link>`. When you click `<Link href="/about">`, Next.js:

1. Intercepts the click (no full page reload).
2. Fetches the target page (`/about`).
3. Renders it instantly — no full page refresh.

**Why `href` instead of `to`?** React Router uses `to="/about"`. Next.js uses `href="/about"`. The prop name differs, but the behavior is identical: both enable client-side transitions.

### Importing `Link` — The Default Import

```tsx
import Link from 'next/link';
```

Note: **no braces**. `Link` is a **default export** from `next/link` — you import it as `Link`, not `{ Link }`. This differs from React Router where `Link` was a named export (`import { Link } from 'react-router-dom'`).

**Rule of thumb:** `next/link`'s `Link` is default. React Router's was named. The import style reflects that.

### `Link` vs `<a>`

`<Link>` is for internal navigation (same Next.js app). `<a>` is still fine for **external links** (different domain):

```tsx
// Internal — use Link
<Link href="/projects">Projects</Link>

// External — use a
<a href="https://github.com/user">GitHub</a>
```

Use `<Link href="...">` for routes in your app. Use `<a href="...">` for links that leave the page entirely.

## In Practice — Scaffolding the Blog Project

### Final Folder Structure

Here is the structure the blog will grow into:

```
app/
├── layout.tsx          →  root layout (shared)
├── page.tsx            →  /  (Home)
├── about/
│   └── page.tsx        →  /about
├── projects/
│   └── page.tsx        →  /projects
├── contact/
│   └── page.tsx        →  /contact
├── blog/
│   ├── page.tsx        →  /blog  (list of posts)
│   └── [slug]/
│       └── page.tsx    →  /blog/:slug  (individual post)
└── lib/
    └── posts.ts        →  dummy data for posts
```

### Shared Data — `lib/posts.ts`

Right now, data is a hardcoded array in `lib/posts.ts`. In the next batch we fetch from a real API. For now, dummy data lets us focus on routing and rendering without a backend:

```tsx
// app/lib/posts.ts
export const posts = [
  { id: 1, slug: 'my-first-post', title: 'My First Post', excerpt: 'This is my first blog post.' },
  { id: 2, slug: 'second-post', title: 'Second Post', excerpt: 'Here is the second one.' },
  { id: 3, slug: 'hello-world', title: 'Hello World', excerpt: 'Classic first post.' },
];
```

We will move this to `lib/posts.ts` (outside `app/`, in the project root) — it is a data file, not a route. Next.js does not turn files outside `app/` into routes.

### Root Layout

```tsx
// app/layout.tsx
import type { ReactNode } from 'react';
import Link from 'next/link';

export default function RootLayout({ children }: { readonly children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <nav>
          <Link href="/">Home</Link>
          <Link href="/about">About</Link>
          <Link href="/projects">Projects</Link>
          <Link href="/contact">Contact</Link>
          <Link href="/blog">Blog</Link>
        </nav>
        {children}
      </body>
    </html>
  );
}
```

The `<nav>` with `<Link>`s is in the **root layout** — it renders on every page. No need to repeat navigation in each page.

### Home Page

```tsx
// app/page.tsx
export default function Home() {
  return (
    <main>
      <h1>Portfolio / Blog</h1>
      <p>Welcome to my site.</p>
    </main>
  );
}
```

### Blog List Page

```tsx
// app/blog/page.tsx
import Link from 'next/link';
import { posts } from '@/lib/posts';

export default function BlogList() {
  return (
    <main>
      <h1>Blog</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.id}>
            <Link href={`/blog/${post.slug}`}>{post.title}</Link>
          </li>
        ))}
      </ul>
    </main>
  );
}
```

- `import { posts }` — named export from our data file.
- `<Link href={`/blog/${post.slug}`}>` — links to the dynamic route `/blog/:slug`.
- `key={post.id}` — required in lists to help React track items.

### Blog Post Page (Dynamic Route)

```tsx
// app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation';
import { posts } from '@/lib/posts';

export default async function BlogPost({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = posts.find((p) => p.slug === slug);

  if (!post) notFound();

  return (
    <main>
      <h1>{post.title}</h1>
      <p>{post.excerpt}</p>
    </main>
  );
}
```

- `[slug]/page.tsx` — one file catches any slug (`/blog/hello-world`, `/blog/my-first-post`).
- `posts.find(...)` — look up the post; if not found, call `notFound()`.

And that is the full site — routed, with a dynamic blog, built entirely through the file system.

## In Your Own Words

1. How does the folder structure map to routes in Next.js? Why is the file named `page.tsx`?

<details>
<summary>Sample Answer</summary>

**Answer:** The folder name inside `app/` is the URL path, and `page.tsx` inside it is the content — `app/about/page.tsx` serves `/about`. The file must be named `page.tsx` because Next.js looks for that exact name by convention to create a route. A file named `index.tsx` or `Home.tsx` would not become a route.

</details>

2. What is `@/` and why is it better than relative imports like `../../lib/posts`?

<details>
<summary>Sample Answer</summary>

**Answer:** `@/` is a shortcut that maps to the project root (configured via `baseUrl` and `paths` in `tsconfig.json`). It is better than `../../lib/posts` because the path never breaks — moving the importing file to a different depth does not require rewriting the `../` chain. `@/lib/posts` always means "project-root/lib/posts" no matter where you are.

</details>

3. When should you use `<Link href="...">` versus a plain `<a href="...">` tag?

<details>
<summary>Sample Answer</summary>

**Answer:** Use `<Link href="...">` for navigation **within your Next.js app** (client-side, instant transitions — no full page reload). Use `<a href="...">` for links that leave the page entirely (external URLs on other domains). `<Link>` intercepts the click and swaps content; `<a>` does a full browser navigation.

</details>

4. Why can the `BlogPost` component use `async` directly, and what happens if you forget `await params`?

<details>
<summary>Sample Answer</summary>

**Answer:** `BlogPost` is a Server Component, so it can use `async` directly — Next.js awaits the server-side rendering before sending HTML. If I forget `await params`, the destructuring `params.slug` fails because `params` is a **Promise object**, not the resolved `{ slug: "value" }` — you would get an error or `undefined`. You must `await params` before destructuring its keys.

</details>
