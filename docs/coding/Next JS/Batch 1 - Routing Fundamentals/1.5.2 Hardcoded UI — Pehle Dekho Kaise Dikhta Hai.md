## Where We Left Off

In file 1.5.1, we planned the blog structure — pages, data shape, the overall flow. Next comes a key strategy: **build the UI with hardcoded data first, before touching the data layer.**

You might wonder: "Why not just create `lib/posts.ts` and go dynamic immediately?" Because of one problem: **if you mix data fetching and UI at the same time, an error is hard to debug.** Was it a UI issue (styling, missing field)? Or a data issue (bad API, wrong shape)? Debugging both simultaneously is painful.

That is why senior developers use the **hardcoded-first approach**: build the UI with fake data so you can see the structure, confirm the data shape, and verify the layout. Then — and only then — replace the hardcoded data with the real data layer.

## Step 1 — Root Layout: `app/layout.tsx`

We learned about layouts in 1.2 — a Navbar + Footer that applies to every page. Let us set up the foundation:

```tsx
// app/layout.tsx — ROOT layout (the one place html/body live)
import type { ReactNode } from 'react';
import Link from 'next/link';

export default function RootLayout({ children }: { readonly children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <nav>
          <Link href="/">Home</Link>
          <Link href="/about">About</Link>
          <Link href="/projects">Projects</Link>
          <Link href="/blog">Blog</Link>
          <Link href="/contact">Contact</Link>
        </nav>
        {children}
        <footer>© 2026 My Portfolio</footer>
      </body>
    </html>
  );
}
```

- **`"use client"` is NOT needed** here — the root layout is a Server Component by default. It does not need interactivity.
- **`<Link>`** instead of `<a>` — client-side navigation, no page reloads (from 1.1).
- **`{children}`** — this is where each page's content renders. The nav and footer persist; only `{children}` swaps per route.

## Step 5 — Blog List: `app/blog/page.tsx`

Now the first **important decision**. In 1.5.1 we planned the data shape — a post has `slug`, `title`, `date`, `excerpt`, `content`. But right now, no data layer exists (`lib/posts.ts` has not been created yet). So what do we do?

**Hardcode a few sample posts** and render the UI to see how it looks — using the exact fields that the final data shape will have:

```tsx
// app/blog/page.tsx — serves "/blog"
import Link from 'next/link';

// ⚠️ TEMPORARY hardcoded data — just to see the UI. Replaced by lib/posts.ts later.
const posts = [
  {
    slug: 'my-first-post',
    title: 'My First Post',
    excerpt: 'Learning Next.js routing for the first day.',
  },
  {
    slug: 'dynamic-routes',
    title: 'Dynamic Routes — The [slug] Folder',
    excerpt: 'One page, many URLs.',
  },
  {
    slug: 'loading-error-404',
    title: 'Loading, Error, and 404 States',
    excerpt: 'Three files that make the UX smooth.',
  },
];

export default function Blog() {
  return (
    <main>
      <h1>Blog</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.slug}>
            <Link href={`/blog/${post.slug}`}>{post.title}</Link>
            <p>{post.excerpt}</p>
          </li>
        ))}
      </ul>
    </main>
  );
}
```

Notice the design decisions (from 1.5.1 planning):
- `title` + `excerpt` are shown in the list — these are the fields needed for a post preview.
- `slug` is used to build the link: `/blog/${post.slug}`.
- `date` and `content` are **not** here — they will appear on the individual post page only, not the list.

## Step 6 — Single Post: `app/blog/[slug]/page.tsx`

Now the dynamic route (recalling 1.3 — folder `[slug]`, params from the URL). Since there is no `getPostBySlug()` function yet (that comes in 1.5.3), we hardcode the posts array here and use `params.slug` to find the match:

```tsx
// app/blog/[slug]/page.tsx — serves "/blog/:slug"
import { notFound } from 'next/navigation';

// ⚠️ TEMPORARY hardcoded data — just to see the UI
const posts = [
  {
    slug: 'my-first-post',
    title: 'My First Post',
    date: 'Aug 7, 2026',
    excerpt: 'Learning Next.js routing for the first day.',
    content: 'This is my first blog post. I built this page using file-based routing.',
  },
  {
    slug: 'dynamic-routes',
    title: 'Dynamic Routes — The [slug] Folder',
    date: 'Aug 8, 2026',
    excerpt: 'One page, many URLs.',
    content: 'This post teaches that a [slug] folder handles multiple URLs with one page.',
  },
  {
    slug: 'loading-error-404',
    title: 'Loading, Error, and 404 States',
    date: 'Aug 9, 2026',
    excerpt: 'Three files that make the UX smooth.',
    content: 'loading.tsx, error.tsx, and not-found.tsx — these files handle every state.',
  },
];

export default async function BlogPost({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;          // Extract slug from URL (from 1.3)
  const post = posts.find((p) => p.slug === slug);

  if (!post) {
    notFound();                             // Slug not found → 404 (from 1.4)
  }

  return (
    <main>
      <h1>{post.title}</h1>
      <p>{post.date}</p>
      <p>{post.content}</p>
    </main>
  );
}
```

Three important points:
1. `params` is a Promise (Next.js 15+), so we `await` it before destructuring `slug`.
2. `posts.find(p => p.slug === slug)` — we search the array by slug. If `undefined` (no match), we call `notFound()`.
3. `date` and `content` are shown **here** on the individual post — not on the list. This follows the plan: list shows `title` + `excerpt`; individual post shows `title` + `date` + `content`.

## Hardcoded First — The Tradeoff We Accept

Open the browser and check: `/blog` shows the list, `/blog/my-first-post` shows the post. **The UI works.**

Here is what we gained and what we lost:

**Gained (the benefits of hardcoded-first):**
1. **UI is confirmed** — we can see the page layout, styling, and structure before the data layer.
2. **Data shape is validated** — `slug`, `title`, `date`, `excerpt`, `content` each appear exactly where the plan said they should.
3. **One problem at a time** — if the next step (data layer) has a bug, we know it is a data issue, not a UI issue.

**The problem we revealed (that the next file fixes):**

Look at the hardcoded posts array — it appears in **two places**: `app/blog/page.tsx` (list) and `app/blog/[slug]/page.tsx` (individual post). **Same data, duplicated.** This is a DRY violation. If you add a new post, you must add it to both files.

This duplication is **intentional** at this stage — it shows us the problem. The next file (1.5.3) solves it: we extract the posts array into `lib/posts.ts` and both pages import from it.

## In Your Own Words

1. Why build the UI with hardcoded data first instead of jumping straight to the data layer?

<details>
<summary>Sample Answer</summary>

**Answer:** Hardcoded-first isolates problems. If I build the UI and data fetching at the same time and something breaks, I cannot tell if it is a UI bug (wrong field displayed, broken styling) or a data bug (API failure, wrong shape). By hardcoding first, the UI gets validated — I confirm the layout, the fields, the links. Then when I add the data layer, any new bug is definitely a data-layer problem, not a UI problem. One issue at a time.

</details>

2. Why does the blog list page show `title` + `excerpt` but the individual post page shows `title` + `date` + `content`?

<details>
<summary>Sample Answer</summary>

**Answer:** The data fields shown depend on the UI role. The list page needs a preview — just enough for the user to scan and choose: title (what) + excerpt (short summary). The individual post page shows the full content: title + date + full body. This matches the plan made in 1.5.1 — `date` and `content` are not needed in a list preview, only in the full post view.

</details>

3. What duplication problem exists in the hardcoded version, and how does the next file solve it?

<details>
<summary>Sample Answer</summary>

**Answer:** The hardcoded `posts` array exists in both `app/blog/page.tsx` and `app/blog/[slug]/page.tsx` — same data, two copies. Adding a post means editing both files. The next file solves this by extracting the array into `lib/posts.ts` — a single source of truth. Both pages then `import` from it: `getAllPosts()` for the list, `getPostBySlug(slug)` for the individual post. One data source, no duplication.

</details>

4. What happens if a visitor goes to `/blog/nonexistent-slug`? How does the `notFound()` call protect the page?

<details>
<summary>Sample Answer</summary>

**Answer:** The URL `/blog/nonexistent-slug` matches the `[slug]` route. `params.slug = "nonexistent-slug"`. We call `posts.find(p => p.slug === slug)` — no post has that slug, so `find` returns `undefined`. The `if (!post)` check catches this and calls `notFound()`, which triggers the 404 page (from `not-found.tsx`). Without this check, `post.title` would crash because `post` is `undefined`, triggering an error boundary instead of a clean 404.

</details>
