## The Manual Way — A Monolithic Page

### React Router — Everything In One File

In React Router, a typical blog post page was a monolith — HTML, styles, data fetching, and error handling all in one component:

```tsx
// App.tsx — React Router (monolithic)
import { useState, useEffect } from 'react';
import { useParams, useNavigate } from 'react-router-dom';

function BlogPost() {
  const { slug } = useParams();
  const navigate = useNavigate();
  const [post, setPost] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch(`/api/posts/${slug}`)
      .then((res) => res.json())
      .then((data) => { setPost(data); setLoading(false); })
      .catch((err) => { setError(err); setLoading(false); });
  }, [slug]);

  if (loading) return <div>Loading...</div>;
  if (error) return <div>Error: {error.message}</div>;
  if (!post) return <div>Post not found</div>;

  return <div>...</div>;
}
```

Everything — fetching, loading, error, rendering — was mixed together in one function. Hard to maintain, hard to test, hard to reuse.

## The Next.js Way — Separation of Concerns

### Split Into Layers

In Next.js, we separate **concerns**:

- **Data layer** — `lib/posts.ts` fetches and returns data
- **Route handler** — `[slug]/page.tsx` calls the data layer, passes data to UI
- **UI layer** — renders the post
- **Error/loading** — special files handle these separately

This is the same principle as the React course's "Separation of Concerns" module: data fetching, state management, and UI each get their own space.

## A — Planning The Code Structure

### The File Layout

For the blog, we need these files:

```
app/
├── blog/
│   ├── page.tsx              →  /blog  (list of posts)
│   ├── loading.tsx           →  loading state for blog routes
│   ├── error.tsx             →  error state for blog routes
│   └── [slug]/
│       ├── loading.tsx       →  loading for individual post
│       ├── error.tsx         →  error for individual post
│       └── page.tsx          →  /blog/:slug  (individual post)
└── lib/
    └── posts.ts              →  data layer (post data + fetching logic)
```

> Note: `lib/` is at the project root (next to `app/`), not inside `app/`. Files in `lib/` are not routes.

### What Each File Does

| File | Responsibility |
|---|---|
| `app/blog/page.tsx` | List all blog posts with `<Link>`s to each |
| `app/blog/[slug]/page.tsx` | Fetch the post for this slug, render it |
| `app/lib/posts.ts` | Array of posts + `getPostBySlug()` helper |
| `app/blog/loading.tsx` | "Loading posts..." |
| `app/blog/error.tsx` | "Something went wrong" + retry button |
| `app/blog/[slug]/error.tsx` | "Post failed to load" + retry |
| `app/not-found.tsx` | Global 404 (created earlier in 1.4) |

### The Data Shape

Posts have these fields:

```ts
type Post = {
  slug: string;      // URL identifier — "my-first-post"
  title: string;     // Display title — "My First Post"
  content: string;   // Full content
  excerpt: string;   // Short preview for the list
  date: string;      // Published date
};
```

- `slug` — used in the URL (`/blog/my-first-post`). Must be URL-safe (lowercase, hyphens).
- `excerpt` — a short preview shown on the blog list page.

### The Flow

1. User visits `/blog` → `app/blog/page.tsx` renders → reads posts from `@/lib/posts` → lists them with `<Link href={`/blog/${post.slug}`}>`.
2. User clicks a post → URL becomes `/blog/my-first-post` → Next.js matches `[slug]/page.tsx` → calls it with `params.slug = "my-first-post"` → page looks up the post → renders content.
3. If slug not found → `notFound()` → 404 page.
4. While data loads or API fails → `loading.tsx` / `error.tsx` show.

### Why `lib/posts.ts` Instead of Hardcoded in the Page?

Putting data in the page file mixes data and UI:

```tsx
// ❌ Bad — data + UI in one file
export default function BlogPost() {
  const posts = [  // ← data definition inside a UI component
    { slug: "my-first-post", ... },
  ];
  // render...
}
```

Instead, keep data separate:

```tsx
// ✅ Good — data in lib/posts.ts, UI in page.tsx
// lib/posts.ts
export const posts = [...];

// page.tsx
import { posts } from '@/lib/posts';
export default function BlogList() {
  return <>{posts.map(post => ...)}</>;
}
```

This way, multiple pages can import the same data, you can swap the data source (API instead of array) without touching the UI, and the code stays organized.

## In Your Own Words

1. Why separate data (`lib/posts.ts`) from the page component (`page.tsx`) instead of putting everything in one file?

<details>
<summary>Sample Answer</summary>

**Answer:** Separation of concerns — data is reusable (multiple pages can import it), testable (test the data layer without rendering UI), and swappable (I can swap the array for a real API call in one place without touching the page). If data lives inside the page component, mixing logic and presentation, it is harder to reuse, harder to test, and harder to change later.

</details>

2. What is the role of `loading.tsx` and `error.tsx` in the blog folder? Do they need to be in the `[slug]` folder too? Why?

<details>
<summary>Sample Answer</summary>

**Answer:** `loading.tsx` and `error.tsx` in `app/blog/` apply to the **blog list page** (`/blog`). I should also create them **inside `app/blog/[slug]/`** — that way each individual post page has its own loading and error states. They are scoped by folder: a `loading.tsx` in `blog/` covers `/blog`; one in `blog/[slug]/` covers `/blog/:slug`. Without them scoped correctly, the global/root loading would show instead of context-specific messages.

</details>
