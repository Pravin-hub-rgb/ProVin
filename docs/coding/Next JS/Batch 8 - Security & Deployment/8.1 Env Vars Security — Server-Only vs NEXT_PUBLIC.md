Think about it — the Photo Gallery is built, Prisma + Neon connected. But a question remains: where is the `DATABASE_URL`? It's in the `.env` file. And where is the `.env` file? In the project root. Now imagine a new developer joins and opens the `.env` file — they'll see `DATABASE_URL="postgresql://user:password@neon.tech/mydb"`. That's fine for now, no problem. But think ahead — when the app deploys, what happens? Does the client browser see the `DATABASE_URL`? If yes, then anyone can see your database — **the password, the data, everything.** That's exactly the problem we'll solve in 8.1.

In this file, we'll understand how to keep **secrets (DATABASE_URL, API keys) safe on the server** — and how they accidentally end up in the client bundle. The manual approach (hardcoded secret) and its problem, then Next.js' better solution (`.env` + server-only vs `NEXT_PUBLIC_`).

---

## Manual Approach — Hardcoded Secret (Problem)

First, let's see what goes wrong when you make mistakes. If you write `DATABASE_URL` directly in code:

**File:** `lib/prisma.ts` — ❌ wrong approach

```ts
import { PrismaClient } from "@prisma/client";

export const prisma = new PrismaClient({
  datasources: {
    db: {
      url: "postgresql://user:password@neon.tech/mydb",  // ❌ hardcoded
    },
  },
});
```

This works fine — the database connects, everything runs. But **there are two problems:**

1. **Secret is visible in code** — if this code gets pushed to GitHub (`.gitignore` missed), everyone will see it. A hacker can directly access your database.

2. **Same value everywhere** — should development and production use the same password? No. Local `localhost:5432` and production `neon.tech` are different databases. With hardcoded values, both must be managed in the same place.

This is the "manual approach" — and it **doesn't work in production.** The solution is environment variables.

---

## CONCEPT — Environment Variables Explained

An environment variable is a **key-value pair** that lives outside your code. You write only the key name in code (`process.env.DATABASE_URL`), and the actual value is set on the deployment platform.

```
DATABASE_URL = "postgresql://user:password@neon.tech/mydb"
AUTH_SECRET = "cX8v7K9mN2pR..."
```

You access it in code only:
```ts
const url = process.env.DATABASE_URL;  // "postgresql://user:password@neon.tech/mydb"
```

**Why is this better?**
- Secret is not in code — it's in the `.env` file
- `.gitignore` lists `.env` — it won't be pushed to GitHub
- Each environment (dev, production) can have different values

But now the question — `.env` file is in `.gitignore`, so **how does it work in local development?** Next.js automatically loads the `.env.local` file when you run `npm run dev`. The values come through `process.env` on the server. In the client bundle? **That's the next section in 8.1.1.**

---

## CODE — Creating `.env` File

Create a `.env.local` file in your project root:

```
# .env.local
DATABASE_URL="postgresql://user:password@neon.tech/mydb"
AUTH_SECRET="cX8v7K9mN2pR4sT6vY1zA3bC5dE7fG9hJ2kL4mN6pQ8rS0tU2vW4xZ6aB8cD0eF2"
```

**Why `.env.local` is different from `.env`?**
- `.env` — general environment file, loaded everywhere (development + production)
- `.env.local` — loaded only on the local machine, not on Vercel/production. **That's why we keep secrets in `.env.local`.**

Now access it in code:

**File:** `lib/prisma.ts` — ✅ correct approach

```ts
import { PrismaClient } from "@prisma/client";

export const prisma = new PrismaClient({
  datasources: {
    db: {
      url: process.env.DATABASE_URL,  // ✅ comes from .env.local
    },
  },
});
```

Confirm in `.gitignore`:

```
# .gitignore
.env
.env.local
.env*.local
```

These lines should be there. If not, add them now. If `.env.local` has already been pushed to GitHub:

```bash
git rm --cached .env.local
git commit -m "remove .env.local from tracking"
git push
```

`git rm --cached` removes the file from git tracking — the file stays on your local machine but git will ignore it.

---

## CONCEPT — Server-Only vs `NEXT_PUBLIC_` (The Two Worlds)

Now comes the most important concept — **the server and client are two different worlds.**

In Next.js, there are two types of components:
- **Server Components** — run only on the server (`page.tsx`, `layout.tsx` by default)
- **Client Components** — also run in the browser (`add 'use client'`)

On every request:
1. **Server** first renders the HTML (Server Components)
2. Then **client** (browser) makes the HTML interactive (Client Components hydrate)

Now think — if `DATABASE_URL` is used in a **Server Component**, it stays only on the server. It never reaches the browser. **Safe.**

But if `DATABASE_URL` is used in a **Client Component** (`'use client'`), Next.js bundles that value **into the browser** — because the client needs it. And in the browser bundle, everything is visible — DevTools → Sources tab → search, and you'll find it. **The secret has leaked.**

This is where the `NEXT_PUBLIC_` prefix comes in.

---

## `NEXT_PUBLIC_` Prefix — Exposed in Client Bundle

Next.js' rule:

| Variable Name | Server (Server Component/Route Handler) | Client (Client Component) |
|---|---|---|
| `DATABASE_URL` | ✅ Available | ❌ undefined |
| `NEXT_PUBLIC_MAPS_KEY` | ✅ Available | ✅ Available (in bundle) |

**Add `NEXT_PUBLIC_` prefix = the value will show up in the browser bundle.** So:

- **`DATABASE_URL`** — don't add `NEXT_PUBLIC_`. It's only needed on the server. If you add it, it shows up in the browser.
- **`NEXT_PUBLIC_MAPS_KEY`** — Google Maps API key needed by the client to render maps. This is **safe** because Maps keys are only for frontend use, not databases.

**Golden Rule:** Anything that is a **secret** (password, API key, database URL, auth secret) — do NOT add `NEXT_PUBLIC_` to it. Only make `NEXT_PUBLIC_` those things that the **client genuinely needs** (public API keys, analytics IDs, public URLs).

---

## TEST — Secrets Should Not Appear in Client Bundle

1. Run `npm run dev`
2. Open `localhost:3000` in the browser
3. DevTools → Sources tab (Chrome) or Debugger tab (Firefox)
4. Search for your `DATABASE_URL` value or `AUTH_SECRET`

**Expected:** You should find nothing. If you do find it — the secret is in the client bundle. Check whether you're using it in a Client Component.

5. Now look at the value with `NEXT_PUBLIC_` prefix (if any):
   - Search for it — it should show up (this is expected)

**Result:** Server-only secrets should not appear in the client. `NEXT_PUBLIC_` ones will show up. That's what security means.

## Compare Table (LAST)

| Thing | Hardcoded (manual) | `.env` + Server-Only | `NEXT_PUBLIC_` |
|---|---|---|---|
| Secret location | In code | `.env.local` (gitignore) | `.env.local` (gitignore) |
| Client bundle | ❌ Visible | ❌ undefined | ✅ Available (public things) |
| Multiple envs | Same value everywhere | Dev/production different | Dev/production different |
| Security | ❌ Leaked | ✅ Safe (server only) | ⚠️ Safe for public things only |

---

## Nutshell

Environment variables live in the `.env` file — outside your code. Next.js automatically loads `.env.local`. **Server-only variables** (without prefix) are only accessible on the server — `process.env.DATABASE_URL` is `undefined` in a Client Component. When you add the **`NEXT_PUBLIC_` prefix**, the value also shows up in the browser bundle — so use it only for public things (analytics, public URLs). Secrets (passwords, API keys, database URLs) should never have `NEXT_PUBLIC_` added.

---

## What It Is NOT

- **`.env.local` = "also loaded in production" is NOT true.** `.env.local` is only loaded locally. In production, `.env.production` or platform env vars (Vercel dashboard) are used.
- **`NEXT_PUBLIC_` = "use for every public thing" is NOT true.** Only use it for things the client genuinely needs (maps key, analytics ID). "Public" doesn't mean "not secret" — but it also doesn't mean "safe for everything."
- **`process.env.X` = "always available" is NOT true.** It's only available when set in `.env` file or platform env vars. Can be `undefined` — handle it optionally in TypeScript.
- **`git rm --cached` = "deletes the file" is NOT true.** It only removes from git tracking — the file stays on your local machine.

1. What happens if you add `NEXT_PUBLIC_` prefix to `DATABASE_URL`?

2. What's the difference between `.env` and `.env.local`? When do you use which?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `.env` is loaded everywhere (development + production). `.env.local` is loaded only on the local machine. **Keep secrets in `.env.local`** — on Vercel/production you set env vars from the platform. In `.env`, keep non-secret defaults (values that are the same on both sides).

</details>

3. If you're using `DATABASE_URL` in a Server Component — will it reach the client?

<details>
<summary>Show Answer</summary>

**Sample Answer:** No. A Server Component renders only on the server — using `process.env.DATABASE_URL` there means it stays accessible only on the server. It never reaches the client (browser). **That's why secrets are safe in Server Components.**

</details>

4. If `.env.local` accidentally gets pushed to GitHub, what should you do?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Use `git rm --cached .env.local` to remove it from tracking (the file stays locally). Then commit + push. And immediately change the password/database URL — because GitHub is public, someone may have already seen it. Add `.env.local` to `.gitignore` so it doesn't happen again.

</details>

5. When is the `NEXT_PUBLIC_` prefix legitimate? Give an example.

<details>
<summary>Show Answer</summary>

**Sample Answer:** When the client genuinely needs some public key/URL — like a Google Maps API key (needed to render maps) or an analytics ID (needed for tracking on the client).
