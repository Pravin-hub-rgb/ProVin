## What Is next-browser?

Vercel built an experimental CLI tool for Next.js 16.2: **`next-browser`**. It lets you look at your running app from your **editor** — all your code shows up right in VS Code, no browser tab needed.

It pairs with **adapters** so your app can run on different hosting environments (AWS Lambda, Vercel, Cloudflare, Netlify).

## Using next-browser

Start it alongside your dev server:

```bash
npm run dev  # terminal 1 — starts the dev server
npx next-browser  # terminal 2 — connects to the running app
```

`next-browser` inspects the running Next.js app and presents it in your editor. You can:

- Navigate routes from VS Code (no browser switch)
- Inspect component trees as they render
- See SSR vs client-rendered segments clearly

> **Note:** `next-browser` is **experimental** — APIs and behavior may change in future Next.js versions.

## Adapters — Run Your App Anywhere

In traditional Next.js, you deploy with `next start`. But what if you want to run on a different platform — AWS Lambda, Cloudflare Workers, or Netlify?

**Adapters** let your app run on these platforms. The adapter file translates Next.js's output into the platform's expected format.

### Types of Adapters

| Adapter | Target Platform |
|---|---|
| `@next/adapter-vercel` | Vercel (default) |
| `@next/adapter-netlify` | Netlify |
| `@next/adapter-cloudflare` | Cloudflare Workers |
| Custom adapter | AWS Lambda, custom infrastructure |

### Setting Up a Custom Adapter

1. Install the adapter package:

```bash
npm install @next/adapter-your-platform
```

2. Create the adapter file:

```js
// adapters/my-adapter.js
module.exports = {
  // Platform-specific configuration
  provider: 'lambda',  // or 'edge', 'cloudflare', etc.
  target: 'my-platform',
};
```

3. Modify `next.config.js`:

```js
// next.config.js
const myAdapter = require('./adapters/my-adapter');

module.exports = {
  // ... your existing config

  // Register the adapter
  adapter: myAdapter,  // Next.js 16+ syntax

  // or with experimental config:
  experimental: {
    adapter: myAdapter,
  },
};
```

4. Deploy:

```bash
npm run build  # builds with the adapter
npm start        # or your platform's deploy command
```

## next-browser + Adapters Workflow

The combination of `next-browser` (inspect) and adapters (deploy) gives you:

1. **Develop** — run `npm run dev`, inspect with `next-browser` from your editor
2. **Test** — verify routing, rendering, and component behavior
3. **Deploy** — swap the adapter to target your platform

## Common Mistakes

- ❌ **Trying next-browser without a dev server** — it inspects the running app, not static files
- ❌ **Expecting production parity** — `next-browser` is experimental; behavior may differ in production
- ❌ **Using a custom adapter without testing** — different platforms have different limitations (edge runtime, cold starts, memory limits)
- ❌ **Committing adapter configs with secrets** — adapter files may reference platform API keys

## What It Is NOT

- **It is not stable.** `next-browser` is experimental — use it for development insight, not production workflows.
- **It is not required.** MCP (`get routes`, etc.) is the primary tool. `next-browser` is a complementary inspector.
- **It is not a deployment target.** Adapters let you target platforms, but you still need an account/deployed infrastructure (AWS, Netlify, Cloudflare).

<details>
<summary>Sample Answer</summary>

3. What is the relationship between `next-browser` and adapters?

<details>
<summary>Sample Answer</summary>

**Answer:** They are complementary tools. `next-browser` is for development-time inspection (see your app in your editor). Adapters are for production deployment (run your app on non-Vercel platforms). Both are experimental and part of Next.js's multi-platform vision.

</details>
