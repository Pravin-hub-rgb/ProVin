## Step 1 — Loading States Trigger With Async Data

### Why Loading Did Not Show Before

In 1.5.5, we created `loading.tsx` files — but they never triggered because the data was synchronous:

```ts
// 1.5 posts.ts — synchronous, instant
function getAllPosts() {
  return posts;  // → no delay, no suspense, loading.tsx never fires
}
```

With synchronous data, there is nothing to wait for. The component resolves immediately. No `loading.tsx`.

### Now — Loading WILL Show

In 2.5.2, `fetchAllPosts()` includes a simulated 500ms delay:

```ts
// 2.5.2 posts-api.ts — async, delayed
export async function fetchAllPosts(): Promise<Post[]> {
  await new Promise((resolve) => setTimeout(resolve, 500));  // 500ms delay
  return posts;
}
```

When the blog list page calls `await fetchAllPosts()`, it **suspends**. Next.js detects this suspense and renders the `loading.tsx` component first:

```tsx
// app/blog/loading.tsx
export default function Loading() {
  return (
    <main>
      <h1>Loading blog posts...</h1>
      <p>Just a moment.</p>
    </main>
  );
}
```

### What The User Sees

```
1. User visits /blog
2. BlogPage() starts — calls await fetchAllPosts()
3. fetch suspends (waiting 500ms)
4. Next.js renders loading.tsx → browser shows "Loading blog posts..."
5. 500ms later, fetch resolves → Next.js renders BlogPage → swaps in the list
6. User sees the blog list
```

The loading state is **automatic** — you do not write any `<Suspense>` or conditional logic. Next.js sees the `loading.tsx` file and wraps the page in Suspense automatically (from 1.4).

### Individual Post Loading

The blog post page has a 300ms delay (`fetchPostBySlug`) and its own loading:

```tsx
// app/blog/[slug]/loading.tsx
export default function Loading() {
  return (
    <main>
      <p>Loading post...</p>
    </main>
  );
}
```

Visit `/blog/my-first-post` — you will briefly see "Loading post..." before the actual post appears.

## Step 2 — Testing Error States

### How to Simulate a Fetch Failure

Since we use `setTimeout` (not a real API that can fail), we simulate errors by throwing in the data function:

```ts
// lib/posts-api.ts — TEMPORARY test only
export async function fetchPostBySlug(slug: string): Promise<Post | undefined> {
  throw new Error('API is down — simulated error');  // test line
  // await new Promise(...);
  // return posts.find(...);
}
```

### What Happens

1. User visits `/blog/my-first-post`.
2. `BlogPost({ params })` runs — calls `await fetchPostBySlug(slug)`.
3. `fetchPostBySlug` throws an error.
4. Error bubbles up → Next.js catches it in the nearest `error.tsx`.
5. Browser shows the error component:

```tsx
// app/blog/[slug]/error.tsx
"use use client";

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>
      <p>{error.message}</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  );
}
```

The user sees "API is down — simulated error" and a "Try again" button.

### The Retry Flow

Clicking "Try again" calls `reset()` — Next.js re-runs the page component from scratch. If the throw is removed, the post loads successfully.

### Important — Remove Test Code After

The `throw new Error(...)` is **only for testing**. Remove it before considering the implementation final. Leaving throw statements in production code would break the app.

## Step 3 — ISR Verification

### How ISR Looks in the Data Source

When the data source uses a real `fetch()`, you add `revalidate` to the fetch options:

```ts
// Real implementation — with ISR
export async function fetchAllPosts(): Promise<Post[]> {
  const res = await fetch('https://api.example.com/posts', {
    next: { revalidate: 300 },  // refresh every 5 minutes
  });
  return (await res.json()).posts;
}
```

### How to Test ISR

ISR requires a **production build** — the dev server does not cache `fetch` the same way:

```bash
npm run build    # production build — this is where caching activates
npm start        # start the production server
```

Then visit `/blog` and observe:

| Action | Expected |
|---|---|
| First visit | Data fetched (slow), HTML cached |
| Refresh immediately | Cached (fast) — same render time |
| Wait 300 seconds | Background revalidate — next request gets fresh data |

### The Render Time Display

To verify caching, add a timestamp to the page:

```tsx
// app/blog/page.tsx
export default async function BlogPage() {
  const posts = await fetchAllPosts();

  return (
    <main>
      <h1>Blog</h1>
      <p>Page rendered at: {new Date().toLocaleTimeString()}</p>
      {/* posts list */}
    </main>
  );
}
```

- **With ISR (or default static):** reload the page multiple times within the revalidate window — the timestamp stays the same. The page was cached.
- **Without caching (`no-store`):** every reload shows a new timestamp. The page is re-fetched.

> **Note:** In `npm run dev`, caching does not work the same way — you will see a new timestamp on every refresh. This is expected. Use `npm run build && npm start` for accurate ISR testing.

## Common Mistakes

- **Forgetting to test in production mode for ISR** — `npm run dev` does not cache `fetch` the same way. Use `npm run build && npm start`.
- **Leaving test `throw` statements** — these break the app in production. Always remove test code.
- **Adding `"use client"` to the entire page** instead of just the button — you lose Server Component benefits (fast load, SEO, server fetch).
- **Not awaiting in `generateMetadata`** — it is `async` and returns a `Promise<Metadata>`. Forgetting `await` when accessing `params` causes `undefined` values.
- **Setting `metadata.title` as a string in root layout when using template** — the `{ default, template }` object form is required for templates to work.

## In Your Own Words

1. Why did `loading.tsx` never show in v1 but shows in v2? What is the technical reason?

<details>
<summary>Sample Answer</summary>

**Answer:** In v1, `getAllPosts()` was synchronous — it returned data instantly, the component never suspended, so Next.js never triggered the Suspense boundary that `loading.tsx` provides as a fallback. In v2, `fetchAllPosts()` is async with a 500ms delay — the component suspends (awaits the Promise), and Next.js shows `loading.tsx` as the Suspense fallback. Loading states require the page to actually suspend — which requires async data.

</details>

2. How do you test the error state without a real failing API?

<details>
<summary>Sample Answer</summary>

**Answer:** Temporarily add `throw new Error('test')` at the start of the data function (like `fetchPostBySlug`). When the page calls it, the error bubbles up to `error.tsx` — the page shows the error message and retry button. After verifying, remove the throw statement. This simulates what happens when a real API is down, without needing to break an actual endpoint.

</details>

3. Why does `generateMetadata` need to be `async` and `await params`?

<details>
<summary>Sample Answer</summary>

**Answer:** `params` is a Promise in Next.js 15 (same as in the page component). I must `await` it to get the actual slug value before I can fetch the post. `generateMetadata` is `async` because it needs to `await` both the params and the data fetch before returning the metadata object. Without `await`, `params` would be a Promise and `params.slug` would be `undefined`.

</details>

4. For ISR testing, why does `npm run dev` behave differently from `npm run build && npm start`?

<details>
<summary>Sample Answer</summary>

**Answer:** The development server (`npm run dev`) does not cache `fetch` responses the same way production does — it re-runs the page on each request for hot reloading. So the timestamp changes on every refresh, making ISR appear broken. The production server (`npm run build && npm start`) caches properly — within the revalidate window, reloads show the same timestamp (cached), proving ISR works. Always test caching and ISR in production mode.

</details>

5. What does the `{error, reset}` destructuring in `error.tsx` mean? Why must you call `reset` (with parentheses) and not render it?

<details>
<summary>Sample Answer</summary>

**Answer:** `error` is the Error object — `error.message` gives the readable message. `reset` is a **function** Next.js provides for retrying. You call it with `reset()` (parentheses invoke the function), typically on a button click — `onClick={() => reset()}`. You do not render `{reset}` — it is a function reference, not displayable content. Calling it tells Next.js to re-render the page from scratch.

</details>
