## Where We Left Off

In 2.5.2, we created `lib/posts-api.ts` — an async data source with `fetchAllPosts()` and `fetchPostBySlug()` that return Promises and simulate network delay. The pages still call the old synchronous functions from `lib/posts.ts`.

## Broader Goal

This file **upgrades the pages** to use the new async data source. Three changes happen:

1. **Blog pages become `async` Server Components** — they `await` the data functions (from 2.1).
2. **A Like button is added** — a Client Component imported into the Server Component page (from 2.2).
3. **Metadata is added** — static on simple pages, `generateMetadata` on blog posts (from 2.4).

We also add the metadata template in the root layout so every page title follows a consistent pattern.

## Step 1 — Root Layout: Add Metadata Template

### The Metadata Template

Adding a template to the root layout ensures every page title is consistent — `"Page Title | My Portfolio"`:

```tsx
// app/layout.tsx
import type { Metadata } from 'next';
import type { ReactNode } from 'react';
import Link from 'next/link';

export const metadata: Metadata = {
  title: {
    default: 'My Portfolio',         // fallback title
    template: '%s | My Portfolio',     // %s = page's own title
  },
  description: 'Pravin — full-stack developer building with Next.js.',
};

export default function RootLayout({ children }: { readonly children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <nav>
          <Link href="/">Home</Link>
          <Link href="/about">About</Link>
          <Link href="/projects">Projects</Link>
          <Link href="/blog">Blog</Link>
          <Link href="/contact">Contact</Link>
        </nav>
        {children}
        <footer>© 2026 My Portfolio</footer>
      </body>
    </html>
  );
}
```

**How the template resolves:**
- About page sets `title: "About"` → final title becomes `"About | My Portfolio"`
- A page with no title set → uses `"My Portfolio"` (from `default`)

From 2.4 — the `%s` is a placeholder replaced with the page's title. Define once in root layout, applied everywhere.

## Step 3 — Like Button: Client Component

### Why a Separate File?

From 2.2: only the interactive part should be a Client Component. The page stays a Server Component (for data fetching and SEO). We extract the button into its own file:

```
components/
└── like-button.tsx    →  Client Component ("use client")
```

### The Component

```tsx
// components/like-button.tsx
"useclient";

import { useState } from 'react';

export default function LikeButton() {
  const [likes, setLikes] = useState(0);

  return (
    <button
      onClick={() => setLikes(likes + 1)}
      style={{ marginTop: '1rem', cursor: 'pointer' }}
    >
      ❤️ {likes} {likes === 1 ? 'Like' : 'Likes'}
    </button>
  );
}
```

**Key points:**
- `"use client"` is the **first line** — marks this as a Client Component.
- `useState(0)` — the like count starts at 0.
- `onClick={() => setLikes(likes + 1)}` — increment on click.
- `{likes === 1 ? 'Like' : 'Likes'}` — proper singular/plural.
- The state is **local to this component** — clicking does not re-render the entire page or refetch post data.

### Server Meets Client

When the Server Component page renders `<LikeButton />`:

1. Server renders a **placeholder** HTML shell: `<button>♡ 0 Like</button>`.
2. Browser receives the HTML — button is visible but not interactive yet.
3. Browser downloads the JavaScript bundle.
4. React **hydrates** the button — wires up `useState` and `onClick`.
5. Now clicking works — the count updates.

From 2.2 — the Server Component produces HTML, the Client Component takes over interactivity on the client.

## Step 4 — Blog List Page: Async Data

### The Updated Page

Now the blog list page uses the async data source:

```tsx
// app/blog/page.tsx
import type { Metadata } from 'next';
import Link from 'next/link';
import { fetchAllPosts } from '@/lib/posts-api';

export const metadata: Metadata = {
  title: 'Blog',
  description: 'Thoughts on Next.js, React, and development.',
};

export default async function BlogPage() {
  const posts = await fetchAllPosts();  // async — was getAllPosts() before

  return (
    <main>
      <h1>Blog</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.slug}>
            <Link href={`/blog/${post.slug}`}>{post.title}</Link>
            <p>{post.excerpt}</p>
          </li>
        ))}
      </ul>
    </main>
  );
}
```

### What Changed (v1 → v2)

1. `import { fetchAllPosts } from '@/lib/posts-api'` — new async source.
2. `async function BlogPage` — the page is now `async` (was sync).
3. `const posts = await fetchAllPosts()` — `await` added (was `getAllPosts()`).
4. `metadata` added — static SEO title/description.
5. **Render logic unchanged** — `posts.map`, keys, links. The UI code did not change — only the data source and async-ness.

From 2.1 — Server Components can `await` directly. The server waits for `fetchAllPosts()` to resolve before generating HTML.

## Step 5 — Single Blog Post: The Full Integration

This is the most complex page — it combines **four** Batch 2 concepts:

1. **`generateMetadata`** (2.4) — dynamic title from post data
2. **`await fetchPostBySlug`** (2.1) — async data fetch in Server Component
3. **`notFound()`** (1.4) — 404 when slug does not match
4. **`<LikeButton />`** (2.2) — Client Component for interactivity

```tsx
// app/blog/[slug]/page.tsx
import type { Metadata } from 'next';
import { notFound } from 'next/navigation';
import { fetchPostBySlug } from '@/lib/posts-api';
import LikeButton from '@/components/like-button';

interface BlogPostProps {
  params: Promise<{ slug: string }>;
}

// Dynamic metadata — runs before page render
export async function generateMetadata({ params }: BlogPostProps): Promise<Metadata> {
  const { slug } = await params;
  const post = await fetchPostBySlug(slug);

  if (!post) {
    return { title: 'Post Not Found' };
  }

  return {
    title: post.title,
    description: post.excerpt,
  };
}

// The page itself
export default async function BlogPost({ params }: BlogPostProps) {
  const { slug } = await params;
  const post = await fetchPostBySlug(slug);

  if (!post) {
    notFound();  // 404 if slug not found
  }

  return (
    <main>
      <h1>{post.title}</h1>
      <p>{post.date}</p>
      <p>{post.content}</p>
      <LikeButton />  {/* Client Component — interactive */}
    </main>
  );
}
```

### Tracing the Flow

```
User visits /blog/my-first-post
  ↓
Next.js calls generateMetadata({ params: { slug: "my-first-post" } })
  ↓
  generateMetadata: await params → await fetchPostBySlug("my-first-post") → post found
  ↓
  Next.js sets <title>My First Post | My Portfolio</title> in HTML head
  ↓
Next.js calls BlogPost({ params: { slug: "my-first-post" } })
  ↓
  BlogPost: await params → await fetchPostBySlug("my-first-post") → post found
  ↓
  Renders: <h1>My First Post</h1>, <p>content</p>, <LikeButton />
  ↓
Browser receives complete HTML with title + content + button shell
  ↓
JavaScript hydrates the LikeButton — now clickable
```

### Why Fetch Twice?

`generateMetadata` and the page component both call `fetchPostBySlug`. At first glance this looks like a waste — and in production it is (we cover `cache()` to fix it later). But for learning:

- `generateMetadata` needs the post **before** the page renders (to set the `<title>` in the `<head>`).
- The page component needs the post **to render the content**.
- Next.js runs `generateMetadata` first, then the page — they happen sequentially, not in parallel.

In a real app, you would use `cache()` so both calls share the same fetch. For now, the duplicate fetch is acceptable — it makes the flow clear.

## In Your Own Words

1. Why does the blog list page stay structurally the same even though it now fetches async data?

<details>
<summary>Sample Answer</summary>

**Answer:** The 1.5.3 abstraction — pages call data functions, data functions return data. When the source went async, the function names changed (`getAllPosts` → `fetchAllPosts`) and pages added `await`, but the render logic (`posts.map`, keys, `<Link>`) is identical. The data layer change was isolated — the UI did not need to change because it was always going to receive a list of posts.

</details>

2. How does `<LikeButton />` (Client Component) work inside a Server Component page?

<details>
<summary>Sample Answer</summary>

**Answer:** The Server Component page renders on the server, fetches data, produces HTML. When it encounters `<LikeButton />`, it renders a placeholder HTML shell (`<button>♡ 0 Likes</button>`) because LikeButton is a Client Component. The browser receives this HTML, then downloads the JS bundle. React hydrates the button — wiring up `useState` and `onClick`. After hydration, the button is interactive. The page stays a Server Component (fast, SEO) while the button gets client-side interactivity.

</details>

3. What is the order of execution: `generateMetadata` vs the page component? Why does this matter?

<details>
<summary>Sample Answer</summary>

**Answer:** `generateMetadata` runs first, then the page component. Next.js needs the metadata (title, description) to inject into the `<head>` of the HTML before sending the page. So it calls `generateMetadata` to get the title, puts it in `<head>`, then renders the page body. This is why `generateMetadata` can `await` params and data — it runs as a separate async step before the page renders.

</details>

4. Why do both `generateMetadata` and `BlogPost` call `fetchPostBySlug`? Isn't that wasteful?

<details>
<summary>Sample Answer</summary>

**Answer:** Yes, it fetches the same post twice — once for metadata (title/description for SEO), once for rendering (content). In production, this is solved with `cache()` so both calls share the same server-side result. For learning, the duplication is acceptable and makes the flow explicit. We will see `cache()` in a later batch to deduplicate.

</details>
