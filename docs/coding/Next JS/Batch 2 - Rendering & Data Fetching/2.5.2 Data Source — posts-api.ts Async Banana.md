## Where We Left Off

In 2.5.1, we planned the v2 upgrades: async data source, Like button (Client Component), SEO metadata, and ISR. Now we begin implementation with the **async data source**.

## Broader Goal

Batch 1's `lib/posts.ts` had **synchronous** functions — `getAllPosts()` returned `Post[]` immediately, `getPostBySlug(slug)` returned `Post | undefined` immediately. No delay, no Promise, no loading states triggered.

In v2, the data source becomes **async** — functions return `Promise<Post[]>` and `Promise<Post | undefined>`, with a simulated network delay. This mirrors real `fetch()` behaviour, which is what triggers loading, error, and ISR states in practice.

This file covers:

**A — The `Post` Type — Same Shape.** We are not changing data structure, just delivery.

**B — Async Functions with Simulated Delay.** Using `setTimeout` to simulate network latency.

**C — Compare: v1 vs v2.** The one-key difference — sync vs async.

**D — What Pages Need to Change.** Every consumer must now `await` the functions.

## Manual Approach — Synchronous Data (v1)

### How v1 Worked

```ts
// lib/posts.ts — v1 (synchronous)
export const posts: Post[] = [...];

export function getAllPosts(): Post[] {
  return posts;                           // instant — no delay
}

export function getPostBySlug(slug: string): Post | undefined {
  return posts.find((p) => p.slug === slug);  // instant — no delay
}
```

- Functions return values directly.
- No `await` needed at call sites.
- No loading states — data is instant.
- No error states possible — no network, no failure.
- No ISR — caching is irrelevant with in-memory data.

This was fine for learning routing and structure (Batch 1), but it does **not** model real-world data fetching.

## Better — Async Data Source (v2)

### A — The `Post` Type (Unchanged)

The data shape stays **exactly the same** — this is intentional. When you know what fields the UI needs (done in 1.5.2), you define the type once. The source of the data (file, API, database) does not change the shape:

```ts
// lib/posts-api.ts
export type Post = {
  slug: string;
  title: string;
  date: string;
  excerpt: string;
  content: string;
};
```

Same fields. Same type. Only the **delivery mechanism** changes — from instant return to Promise-based async.

> **Why keep the type identical?** The Blog's UI (what fields to display) determined the type in 1.5.1. The data source does not change that decision. If the API returns more fields, we still type only what we use (YAGNI from 2.1).

### B — Async Functions With Simulated Delay

The key change: functions become `async`, return `Promise`, and simulate network latency:

```ts
// lib/posts-api.ts

const posts: Post[] = [
  {
    slug: 'my-first-post',
    title: 'My First Post',
    date: 'Aug 7, 2026',
    excerpt: 'Learning Next.js routing on day one.',
    content: 'This is my first blog post, built with file-based routing.',
  },
  {
    slug: 'dynamic-routes',
    title: 'Dynamic Routes — The [slug] Folder',
    date: 'Aug 8, 2026',
    excerpt: 'One page, many URLs.',
    content: 'A [slug] folder lets a single page handle multiple URLs.',
  },
  {
    slug: 'server-fetch',
    title: 'Server Components — Direct Fetch',
    date: 'Aug 9, 2026',
    excerpt: 'Fetching data without useEffect.',
    content: 'Server Components can await fetch() directly — no loading spinner needed.',
  },
];

export async function fetchAllPosts(): Promise<Post[]> {
  // Simulate network delay — in real code, this is: return await fetch(url).then(r => r.json())
  await new Promise((resolve) => setTimeout(resolve, 500));
  return posts;
}

export async function fetchPostBySlug(slug: string): Promise<Post | undefined> {
  await new Promise((resolve) => setTimeout(resolve, 300));
  return posts.find((p) => p.slug === slug);
}
```

### Breaking Down the Pattern

**1. Function names changed:**
```
get*    →  fetch*
getAllPosts()     →  fetchAllPosts()
getPostBySlug()   →  fetchPostBySlug()
```
The `fetch` prefix signals async, network-like behaviour. Naming reflects intent.

**2. `async` keyword:**
```ts
export async function fetchAllPosts()
```
Without `async`, the function returns `Post[]`. With `async`, it returns `Promise<Post[]>`.

**3. `await new Promise(...)`:**
```ts
await new Promise((resolve) => setTimeout(resolve, 500));
```
This simulates network latency. `setTimeout` fires after 500ms, `resolve` is called, `await` completes. In real code, this line is replaced by `await fetch('https://api.example.com/posts')`.

**4. Return type annotation:**
```ts
Promise<Post[]>         // returns all posts, eventually
Promise<Post | undefined>  // returns one post, or undefined if not found
```
The `Post | undefined` is unchanged from v1 — a bad slug still returns `undefined`. The difference is it takes 300ms to get there.

### Real Code vs Simulated

| Aspect | Simulated (this file) | Real API call |
|---|---|---|
| Delay mechanism | `await new Promise(r => setTimeout(r, 500))` | `await fetch('https://...')` |
| Data source | Local `posts` array | External API / database |
| Error possibility | None (array is always there) | Network errors, 500s, timeouts |
| Same return types | ✅ `Promise<Post[]>`, `Promise<Post \| undefined>` |

The **interface is identical** — that is the point. Pages don't know or care if the data is simulated or real.

### When To Add ISR (`revalidate`)

`revalidate` is a `fetch()` option — it goes on the actual `fetch` call, not on a `setTimeout` simulation:

```ts
// Real API call — ISR applied here
export async function fetchAllPosts(): Promise<Post[]> {
  const res = await fetch('https://api.example.com/posts', {
    next: { revalidate: 300 },  // refresh every 5 minutes
  });
  return (await res.json()).posts;
}
```

In the simulated version, there is no real `fetch()` to attach `revalidate` to. But the **pattern is ready** — when we swap in the real API (Batch 5 with a database), we add `next: { revalidate: 300 }` and ISR works automatically.

## C — Compare: v1 vs v2

| Aspect | v1 (`lib/posts.ts`) | v2 (`lib/posts-api.ts`) |
|---|---|---|
| `Post` type | Same 5 fields | Same 5 fields |
| Data content | Same posts | Same posts |
| `getAllPosts` | `get` prefix, sync, `Post[]` | `fetch` prefix, async, `Promise<Post[]>` |
| `getPostBySlug` | `get` prefix, sync, `Post \| undefined` | `fetch` prefix, async, `Promise<Post \| undefined>` |
| Delay | None (instant) | 500ms / 300ms (simulated network) |
| `undefined` case | `.find()` returns undefined | `.find()` returns undefined (same logic) |
| Loading states | Never trigger | Trigger on page (loading.tsx shows) |
| Error possible | No | Yes (simulated by throwing in tests) |

The **one fundamental difference:** synchronous vs asynchronous. And that one difference is what makes loading, error, and ISR states meaningful.

## D — What Pages Need To Change

Every page that calls these functions must update:

```tsx
// Before (v1 — synchronous, no await needed)
const posts = getAllPosts();          // Post[] — instant

// After (v2 — asynchronous, must await)
const posts = await fetchAllPosts();  // Promise<Post[]> — waited on
```

And the page component must become `async`:

```tsx
// Before
export default function BlogPage() {
  const posts = getAllPosts();
  // ...
}

// After
export default async function BlogPage() {
  const posts = await fetchAllPosts();
  // ...
}
```

Why does this work? From 2.1 — Server Components can be `async` and use `await` directly. The server waits for the Promise to resolve before generating HTML. No `useEffect`, no loading state needed at the page level — the page just waits, then renders.

## In Your Own Words

1. Why does the `Post` type stay the same even though the data source changes?

<details>
<summary>Sample Answer</summary>

**Answer:** The type describes **what data the UI needs**, not where it comes from. In 1.5.2, we determined the UI shows `slug`, `title`, `date`, `excerpt`, `content` — that shaped the type. Whether the data comes from a static array or an API, the UI still needs the same fields. The type is a contract between the data and the UI — it does not change when the source changes. This is separation of concerns: the data shape is an UI concern, the delivery is an infrastructure concern.

</details>

2. What is the purpose of `await new Promise((resolve) => setTimeout(resolve, 500))` in the async function?

<details>
<summary>Sample Answer</summary>

**Answer:** It simulates network latency. `setTimeout` waits 500ms before calling `resolve`, and `await` pauses the function until that happens. In a real app, this line would be replaced by `await fetch('https://api...')`. The simulation exists so we can test loading states, error boundaries, and ISR — which all require the data to actually take time. Without it, data is instant and none of those states trigger.

</details>

3. How does changing function names from `get*` to `fetch*` improve the code?

<details>
<summary>Sample Answer</summary>

**Answer:** Naming reflects behaviour. `get*` implied a cheap, synchronous, instant lookup — calling a file or variable. `fetch*` implies async, network-like, potentially slow. Future developers reading `fetchAllPosts()` know it returns a Promise and should be awaited. The name sets the right expectation — this is an async operation, not an instant lookup.

</details>

4. Why return `Promise<Post | undefined>` instead of just `Promise<Post>` from `fetchPostBySlug`?

<details>
<summary>Sample Answer</summary>

**Answer:** Because a slug from the URL might not match any post. `fetchPostBySlug('invalid-slug')` finds no match and returns `undefined`. TypeScript must model this possibility with `Post | undefined` — the caller has to handle both cases. If we returned `Promise<Post>`, the caller would assume a post always exists, but it does not. The `| undefined` is a contract: "call me with any slug, but I might not find anything." The page checks `if (!post)` and calls `notFound()`.

</details>
