Now the data needs to come from somewhere **real** — an API. In the React course, you fetched data with `useEffect` + `fetch()` + loading state + error state — a lot of boilerplate for a single page. Next.js Server Components eliminate all of that with one line: `await fetch()`.

## Manual Approach — React's useEffect Fetch

### The Boilerplate Problem

In React, data fetching always meant this pattern:

```tsx
// React — useEffect + fetch + states
import { useState, useEffect } from 'react';

export default function Products() {
  const [products, setProducts] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch('/api/products')
      .then((res) => res.json())
      .then((data) => {
        setProducts(data);
        setLoading(false);
      })
      .catch((err) => {
        setError(err);
        setLoading(false);
      });
  }, []);

  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error: {error.message}</p>;

  return (
    <ul>
      {products.map((p) => (
        <li key={p.id}>{p.name}</li>
      ))}
    </ul>
  );
}
```

Three state variables (`products`, `loading`, `error`), a `useEffect`, a fetch chain, and three conditional checks. All because **the component renders on the client** — the browser cannot see the data until the fetch resolves, so it needs to handle the "waiting" state.

## Better Approach — Server Component Direct Fetch

### The Key Insight

In Module 0, we learned that **Server Components render on the server**. That changes everything:

> If the component runs on the server, the fetch runs on the server. The data is ready **before** HTML is sent to the browser.

There is no "waiting" moment on the client side — the data is already embedded in the HTML.

### The Code

```tsx
// app/products/page.tsx — a Server Component
interface Product {
  id: number;
  title: string;
  price: number;
}

interface ProductsResponse {
  products: Product[];
}

export default async function ProductsPage() {
  const res = await fetch('https://dummyjson.com/products');
  const data: ProductsResponse = await res.json();

  return (
    <main>
      <h1>Products</h1>
      <ul>
        {data.products.map((product) => (
          <li key={product.id}>
            <h2>{product.title}</h2>
            <p>${product.price}</p>
          </li>
        ))}
      </ul>
    </main>
  );
}
```

**What is gone:**
- No `useState` — no loading state, no error state
- No `useEffect` — no fetch lifecycle
- No `"use client"` — it is a Server Component by default
- No conditional rendering for loading/error

Just `async function` + `await fetch()` + render. The server waits, fetches, renders, and sends **ready HTML** to the browser.

## A — Why Server Components Enable Direct Fetch

### The Rendering Model

```
React (CSR):    Browser renders → needs data → fetch on client → shows loading → data arrives → re-render
Next.js (RSC):  Server renders → fetch on server → data ready → send HTML to browser (no loading)
```

Because the Server Component runs on the server:

1. **Fetch happens server-side** — the browser never sees the fetch call. It runs in the server environment.
2. **Data is resolved before HTML** — by the time Next.js generates the HTML string, all `await` calls have completed.
3. **No client-side waiting** — the browser receives fully-rendered HTML with all data embedded. No loading spinner needed.

### Why `async` Works

A Server Component is just a function. When you mark it `async`, Next.js internally `await`s the returned Promise before generating HTML:

```tsx
// Conceptually — Next.js does this:
const html = await ProductsPage({ params });
// Then html is sent to the browser
```

This is exactly the same **props pattern** from 1.3 — Next.js calls the function, you write the signature. The difference is the function is `async`, so Next.js knows to wait for all resolved promises before producing HTML.

### The DummyJSON API

For these examples, we use [DummyJSON](https://dummyjson.com) — a free fake API that needs no key. It returns product data in this shape:

```json
{
  "products": [
    {
      "id": 1,
      "title": "Essence Mascara Lash Princess",
      "price": 9.99,
      "category": "beauty",
      "description": "The popular mascara...",
      ...
    }
  ],
  "total": 194,
  "limit": 30
}
```

Visit `https://dummyjson.com/products` in your browser to see the full response.

## B — The `async` Page Pattern

### Rule: The Page Must Be `async`

```tsx
// ✅ Correct — async Server Component
export default async function ProductsPage() {
  const res = await fetch('...');
  const data = await res.json();
  return <ul>...</ul>;
}

// ❌ Wrong — cannot await in a non-async function
export default function ProductsPage() {
  const res = await fetch('...');  // SyntaxError!
}
```

The `async` keyword is required — without it, `await` is a syntax error.

### Rule: `export default` Is Still Required

Same as Batch 1 — Next.js needs a default export to render. The function name can be anything (`ProductsPage`, `ProductList`, etc.).

### Rule: No `"use client"` Unless You Need It

This is a Server Component. It fetches data and renders HTML. No `"use client"` directive — that would make it a Client Component, and Client Components **cannot** use `await` (they need `useEffect` instead).

## C — Typing the API Response

### Why Not Just `any`?

A common shortcut is to type the fetched data as `any`:

```tsx
// ❌ Don't do this — loses all type safety
const data: any = await res.json();
data.products.map((p: any) => <li>{p.titel}</li>); // typo: "titel" — no error!
```

With `any`, TypeScript gives you no protection. A typo (`p.titel` instead of `p.title`) runs fine in development but crashes at runtime.

### Type Only What You Use (YAGNI)

The DummyJSON response has 20+ fields per product, but your page only needs `id`, `title`, and `price`. **Type only those:**

```tsx
// ✅ Type only what the UI actually uses
interface Product {
  id: number;
  title: string;
  price: number;
}

interface ProductsResponse {
  products: Product[];
}
```

This follows the **YAGNI principle** ("You Aren't Gonna Need It") from software engineering: don't type fields you are not using. Benefits:

1. **Fewer fields = fewer chances for typos**
2. **API changes are safer** — if the API adds/removes a field you don't type, your code still works
3. **Readability** — another developer sees immediately which fields matter

### How to Know the Response Shape

Before typing, visit the endpoint:

```bash
curl https://dummyjson.com/products
```

Or open it in the browser. Look at the JSON structure, then type only the fields your UI consumes.

## D — Error Handling Without try/catch

### Errors Bubble to `error.tsx`

When `fetch` fails (network error, API down, 500 response), the thrown error bubbles up to the nearest `error.tsx` file — the same one from 1.4:

```tsx
// app/products/error.tsx
"useuse client";

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>
      <p>{error.message}</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  );
}
```

You do **not** need to wrap the fetch in a `try/catch`. If the fetch throws, Next.js catches it and renders the `error.tsx` boundary automatically.

### Why `"use client"` for error.tsx?

From 1.4, remember: `error.tsx` must be a Client Component because the `reset` function requires React hooks for the retry mechanism. The button's `onClick` is a browser event — it can only work if the component is running in the browser.

## Common Mistakes

- **Using `useEffect` in a Server Component** — Server Components do not have a client-side lifecycle. `useEffect` does not run. Use `async`/`await` directly on the server.
- **Adding `"use client"` unnecessarily** — if the component only fetches and renders data, it does not need to be a Client Component. Adding `"use client"` defeats the performance and SEO benefits.
- **Typing the full API response as `any`** — you lose compile-time safety. Type only what you use.
- **Forgetting `export default`** — the page component must be the default export for Next.js to render it.
- **Accessing `res.json()` without checking `res.ok`** — in production, always check the response status before parsing.

## In Your Own Words

1. Why does a Server Component not need `useEffect` or loading states for data fetching?

<details>
<summary>Sample Answer</summary>

**Answer:** Server Components render on the server. When the component function runs, it can `await fetch()` directly — the server waits for the data before generating HTML. By the time the browser receives the page, the data is already embedded. There is no "waiting on the client" moment, so no loading state is needed. React's `useEffect` was needed because the component ran in the browser — it had to request data after the page loaded.

</details>

2. Where does `fetch` actually run in a Server Component? Is it the browser or the server?

<details>
<summary>Sample Answer</summary>

**Answer:** The `fetch` runs on the **server**. Server Components execute in the Node.js server environment. The browser never sees the fetch call — it just receives the rendered HTML with all data already included. This is why there is no loading spinner on the client side.

</details>

Typing only those 3 fields means fewer chances for typos, API changes are safer (extra fields do not break the code), and the interface is more readable — another developer immediately sees which fields matter. YAGNI keeps things minimal and focused.
