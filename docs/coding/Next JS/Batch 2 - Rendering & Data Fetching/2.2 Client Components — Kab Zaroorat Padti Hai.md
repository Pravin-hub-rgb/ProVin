## Where We Left Off

In 2.1, we learned that Server Components fetch data directly with `await fetch()` — no `useEffect`, no loading states, no error handling. Data is ready by the time HTML reaches the browser.

## Broader Goal

Server Components are great for **fetching and rendering data**. But they have a critical limitation: **they cannot handle user interaction.** No `useState`, no `onClick`, no `localStorage`.

If your site needs a button that updates when clicked, a form that captures input, or anything that changes in response to a user action — that needs a **Client Component**. This file covers:

**A — Why Server Components Cannot Be Interactive.** The rendering model that prevents hooks from working.

**B — The `"use client"` Directive.** How to mark a component as client-side.

**C — The Hybrid Model — Server + Client Together.** Importing a Client Component into a Server Component (the recommended pattern).

**D — When to Use Each.** Decision points for choosing Server vs Client.

## Manual Approach — Everything Was Client-Side (React)

### The React Model

In the React course, **every component was a Client Component** by default. `useState`, `useEffect`, `onClick` — all worked everywhere:

```tsx
// React — everything runs in the browser
import { useState } from 'react';

export default function ProductCard() {
  const [favorited, setFavorited] = useState(false);

  return (
    <button onClick={() => setFavorited(!favorited)}>
      {favorited ? "♥ Favorited" : "♡ Add to Favorites"}
    </button>
  );
}
```

No questions asked — every component had access to browser APIs. The downside (from Module 0): the entire app's JavaScript ships to the browser, hurting SEO and performance on first load.

## Better Approach — Server Default, Client Only When Needed

### The Decision Table

Next.js flips the default: **everything is a Server Component unless you explicitly opt in.** Ask yourself:

> Does this component need any of these?

| Need | Means |
|---|---|
| `useState`, `useEffect`, `useReducer` | React state management |
| `onClick`, `onChange`, event handlers | User interaction |
| `localStorage`, `window`, `document` | Browser APIs |
| `usePathname`, `useSearchParams` | Client-side navigation hooks |

If **any** of these apply → **Client Component** (`"use client"`).
If **none** apply → **Server Component** (default, no directive needed).

### The Directive — `"use client"`

To make a component a Client Component, add the directive **as the first line** of the file:

```tsx
// app/components/favorite-button.tsx — a Client Component
"use client";

import { useState } from 'react';

export default function FavoriteButton() {
  const [favorited, setFavorited] = useState(false);

  return (
    <button onClick={() => setFavorited(!favorited)}>
      {favorited ? "♥ Favorited" : "♡ Add to Favorites"}
    </button>
  );
}
```

**Rules:**
- `"use client"` must be the **first line** (before any imports).
- It is file-scoped — the entire file becomes a Client Component.
- It does **not** need to be at the top level of the app router — any `.tsx` file can use it.

## A — Why Server Components Cannot Be Interactive

### The Rendering Model

Server Components run **on the server** during the build step or on each request. They produce HTML, which is sent to the browser. The server has:

- No DOM (`document`, `window` do not exist on the server)
- No persistent state between requests
- No event loop the way a browser does

When React tries to call `useState` on the server, it fails — the hook expects a client-side renderer to manage state across re-renders, but on the server each request is independent.

```tsx
// ❌ This CRASHES — useState on a Server Component
export default function FavoriteButton() {
  const [count, setCount] = useState(0);  // Error: useState is not available on the server
  // ...
}
```

### The Fix

Either:
1. Add `"use client"` to make it a Client Component, or
2. Move the interactive logic to a separate file with `"use client"`.

## B — The Hybrid Model — Server + Client Together

### The Recommended Pattern

You do **not** need to make the whole page a Client Component. Instead, extract the interactive part into its own Client Component and import it into the Server Component page:

```
app/
├── products/
│   ├── favorite-button.tsx    →  Client Component ("use client")
│   └── page.tsx                →  Server Component (fetch + render)
```

```tsx
// app/products/favorite-button.tsx — Client Component
"useuse client";

import { useState } from 'react';

export default function FavoriteButton() {
  const [favorited, setFavorited] = useState(false);

  return (
    <button onClick={() => setFavorited(!favorited)}>
      {favorited ? "♥ Favorited" : "♡ Add to Favorites"}
    </button>
  );
}
```

```tsx
// app/products/page.tsx — Server Component
import FavoriteButton from './favorite-button';

interface Product {
  id: number;
  title: string;
  price: number;
}

interface ProductsResponse {
  products: Product[];
}

export default async function ProductsPage() {
  const res = await fetch('https://dummyjson.com/products');
  const data: ProductsResponse = await res.json();

  return (
    <main>
      <h1>Products</h1>
      <ul>
        {data.products.map((product) => (
          <li key={product.id}>
            <h2>{product.title}</h2>
            <p>${product.price}</p>
            <FavoriteButton />  {/* Client Component, imported */}
          </li>
        ))}
      </ul>
    </main>
  );
}
```

### How This Works — Step by Step

1. On the server, Next.js renders `ProductsPage`. It fetches data with `await fetch()`.
2. The page encounters `<FavoriteButton />` — it is a Client Component.
3. Next.js renders **a placeholder HTML shell** for the button on the server: `<button>♡ Add to Favorites</button>`.
4. The server sends the full HTML (product list + button shell) to the browser.
5. The browser receives HTML, renders it — the button is visible but **not yet interactive**.
6. The browser downloads the JavaScript bundle (which includes the `"use client"` files).
7. React **hydrates** the button — `useState` initializes, `onClick` wires up. Now clicking works.

### The Restaurant Analogy

```
Server Component = Chef in the kitchen
  → Prepares the food (fetches data, renders HTML)
  → Sends it out on a plate (HTML shell to the browser)

Client Component = Waiter at your table
  → Takes your order (clicks, input)
  → Relays back to the kitchen (state changes)

The chef never sits at your table. The waiter never goes into the kitchen.
But they coordinate through a system (React hydration).
```

## C — When to Use Each

### Use Server Components (default) When:

- Rendering data from an API or database
- Displaying static content (blog posts, product info, documentation)
- SEO matters (you want the content in the initial HTML)
- Performance matters (no JavaScript bundle to download)

Server Components are the **default** — if a component only fetches and renders data, leave it as a Server Component.

### Use Client Components (`"use client"`) When:

- You need `useState` (form inputs, counters, toggles)
- You need event handlers (`onClick`, `onChange`, `onSubmit`)
- You need browser APIs (`localStorage`, `window`, `navigator`)
- You need client-side navigation hooks (`useRouter`, `useSearchParams`)

### Extract to a Separate File When:

If only a **small part** of a page needs interactivity, extract just that part:

```tsx
// ✅ Good — page is Server, button is Client
<ProductsPage>              // Server
  <FavoriteButton />        // Client (imported)
</ProductsPage>
```

```tsx
// ❌ Bad — entire page becomes Client (loses Server benefits)
"useuse client";            // whole page is now Client
<ProductsPage>              // loses SSR, SEO, performance
  <FavoriteButton />
</ProductsPage>
```

Making the whole page a Client Component defeats the purpose — you lose server-side rendering, SEO benefits, and fast initial load.

---

## Common Mistakes

- **Placing `"use client"` anywhere except the first line** — it must be the very first thing in the file. Comments or imports before it will cause issues.
- **Making the entire page `"use client"`** when only a small widget needs interactivity — you lose all Server Component benefits.
- **Using `useState` in a Server Component** — it will error. Server Components cannot use React hooks for state.
- **Using `await` in a Client Component** — Client Components cannot be `async`. Use `useEffect` + `fetch` there instead.
- **Importing a Server Component into a Client Component without `"use client"`** — the import direction matters. Client Components importing Server Components can cause issues.

## In Your Own Words

1. What is the difference between a Server Component and a Client Component in terms of where they run and what they can do?

<details>
<summary>Sample Answer</summary>

**Answer:** Server Components run on the server during build or request — they can use `await fetch()` directly, produce HTML, and never ship JavaScript to the browser. They cannot use `useState`, `onClick`, or browser APIs. Client Components run in the browser — they can use hooks, handle events, and access `localStorage`/`window`. They are marked with `"use client"` at the top of the file.

</details>

2. If you need `useState` in a component, must the entire page be a Client Component?

<details>
<summary>Sample Answer</summary>

**Answer:** No. The recommended pattern is to extract the interactive part into its own file with `"use client"`, and import it into the Server Component page. This keeps the page fast (server-rendered, SEO-friendly) while the small interactive widget runs client-side. Making the whole page `"use client"` loses all the Server Component benefits.

</details>

3. When does the Client Component become interactive in the browser? What happens during "hydration"?

<details>
<summary>Sample Answer</summary>

**Answer:** The server sends the HTML shell (including the button's initial markup). The browser renders it immediately — the button is visible but not clickable yet. Then the browser downloads the JavaScript bundle. React then "hydrates" — it attaches event handlers (`onClick`) and initializes state (`useState`). After hydration, the button is interactive. Until hydration completes, clicks do nothing.

</details>
