2.1 mein product listing page banaya — Server Component mein `await fetch()`. Ab ek sawaal — **ye page kitni baar API se fetch karega?**

0.2 mein tumne SSG/SSR ka theory samjha tha, 0.5 mein fetch caching, 0.6 mein ISR. Ab wo sab **practically** try karenge — code likhenge, dekh lenge kaise behave karta hai. Isi liye ye concept hai — theory ko haath mein lena.

## Pehle Samjho — Server Caching Kaise Kaam Karta Hai

Yahan sabse pehle ek basic cheez samjho — **Next.js ka fetch cache BROWSER cache nahi hai, ye SERVER pe hota hai.** Browser cache mein tumhara Chrome/Firefox files store karta hai. Server cache mein **Next.js ka server** response store karta hai.

### Layer System Samjho

Imagine karo tumhara Next.js server ek building hai jisme **do layers** hain:

```
┌─────────────────────────────────────────────────────┐
│                    TUMHARA SERVER                    │
│  ┌─────────────────────────────────────────────┐   │
│  │         LAYER 1: CACHE (Front)              │   │
│  │    (Pehle yahan check hota hai)             │   │
│  │    Agar data yahan hai → seedha de do        │   │
│  │    Agar nahi hai → Layer 2 pe jao            │   │
│  └─────────────────────────────────────────────┘   │
│                       ↓                             │
│  ┌─────────────────────────────────────────────┐   │
│  │         LAYER 2: API CALL (Deep)            │   │
│  │    (Asli API se data fetch hota hai)        │   │
│  │    Response aata hai → Cache mein store karo │   │
│  └─────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
                          ↑
                          │
                    Bahar ki API
              (dummyjson.com/products)
```

### Ab Flow Dekho — 100 Users Ka Case

**Scenario 1: Cache OFF hai (Dynamic — `cache: "no-store"`)**

```
User 1 aaya → Request → Layer 1 (Cache EMPTY) → Layer 2 → API CALL → Response mila → User 1 ko diya
User 2 aaya → Request → Layer 1 (Cache EMPTY) → Layer 2 → API CALL → Response mila → User 2 ko diya
User 3 aaya → Request → Layer 1 (Cache EMPTY) → Layer 2 → API CALL → Response mila → User 3 ko diya
...
User 100 aaya → Request → Layer 1 (Cache EMPTY) → Layer 2 → API CALL → Response mila → User 100 ko diya

Result: 100 API calls! Slow hai, aur API pe load hai.
```

**Scenario 2: Cache ON hai (Static — default behaviour)**

```
User 1 aaya → Request → Layer 1 (Cache EMPTY) → Layer 2 → API CALL → Response mila → 
    → Cache mein STORE kar diya → User 1 ko diya

User 2 aaya → Request → Layer 1 (Cache MEIN DATA HAI!) → Seedha User 2 ko de diya
User 3 aaya → Request → Layer 1 (Cache MEIN DATA HAI!) → Seedha User 3 ko de diya
...
User 100 aaya → Request → Layer 1 (Cache MEIN DATA HAI!) → Seedha User 100 ko de diya

Result: Sirf 1 API call! Baaki 99 users ko cached response mila. Fast hai!
```

### Toh Problem Kya Hai?

Cache bahut achha hai — fast hai. Par ek issue hai: **data stale ho jayega.**

Man lo:
- User 1 aaya → Product ka price ₹500 tha → Cache mein store ho gaya
- Ab API pe price update hua → ₹400 ho gaya
- User 2 aaya → Cache se purana price (₹500) mil gaya — **galat data!**

Ye problem hai — cache bahut purana ho sakta hai. Iska solution hai **revalidate** — cache ko periodically refresh karo.

### Hum Kya Kar Sakte Hain?

Three options hain:

| Option | Kya hota hai | Kab use karein |
|--------|--------------|----------------|
| `cache: "no-store"` | Har request pe API call, koi cache nahi | Jab har baar fresh data chahiye (jaise stock price) |
| Bina option ke (default) | Build time pe ek baar API call, jab tak rebuild na karo wahi data ⚠️ | Sirf static content (About page) — production mein risky |
| `next: { revalidate: 60 }` | Pehle baar API call, phir 60 sec baad refresh | Jab data thoda badalta hai (jaise product listing) |

### Default Kya Hota Hai? (Bina Kisi Option Ke)

Samjho — jab tum `fetch()` likhte ho bina kisi option ke:

```tsx
const res = await fetch("https://dummyjson.com/products");
```

Toh Next.js kya karta hai?

1. **Build time pe** (`next build`) — API se data aata hai, page ban jaata hai
2. **Woh page static HTML mein store ho jaata hai** — CDN pe serve hota hai
3. **Jab tak tum dobara `next build` na maro**, wahi purana page serve hoga

Matlab — agar tumne 1 Jan 2025 ko build kiya aur product ka price ₹500 tha, toh:
- 15 Jan 2025 ko price ₹400 hua → User ko abhi bhi ₹500 dikhega
- 1 Jan 2026 ko user aaya → Abhi bhi ₹500 dikhega (2 saal purana data!)
- Jab tak `next build` na maro, change nahi hoga

**Ye SSG (Static Site Generation) hai** — build time pe ek baar, phir static serve.

**Iska matlab:** Default option sirf tab sahi hai jab data rarely badalta ho — jaise About page, blog posts (jo manually update karte ho). Agar data baar badalta hai (product listing, stock price), toh ya toh `cache: "no-store"` lagao ya `revalidate` use karo.

### Production Reality — Default Option Ka Risk

Ek important baat — default option (bina kisi option ke) sirf tab kaam karta hai jab tum baar baar `next build` maarte ho.

Par **production mein kya hota hai?**
- Tumne ek baar build kiya → Site deploy ho gayi
- Site 10 saal chal rahi hai — tum dobara build nahi kar rahe
- Ab 10 saal purana data serve ho raha hai — **galat hai!**

**Isliye production mein `revalidate` use karo.**

```tsx
// ❌ Default — 10 saal purana data serve hoga
const res = await fetch("https://dummyjson.com/products");

// ✅ Revalidate — har 60 second mein fresh hoga
const res = await fetch("https://dummyjson.com/products", {
  next: { revalidate: 60 },
});
```

**Rule of thumb:** Production app mein **hamesha** `revalidate` lagao (ya `cache: "no-store"`). Default option sirf development ya static content ke liye hai (About page, blog posts jo manually update karte ho).

## Manual Approach — Har Request Pe Fetch (Dynamic)

Upar samjha ki default mein kya hota hai — build time pe ek baar fetch, jab tak rebuild na karo wahi data. Par agar tum **har request pe fresh data** chahte ho (dynamic content), toh `cache: "no-store"` lagao:

```tsx
// app/products/page.tsx
export default async function ProductsPage() {
  const res = await fetch("https://dummyjson.com/products", {
    cache: "no-store",   // koi caching nahi — har request pe fetch
  });
  const data = await res.json();

  return <main>{/* products render */}</main>;
}
```

`cache: "no-store"` ka matlab — **Layer 1 (Cache) skip hota hai.** Har request seedha Layer 2 (API) pe jaata hai. User aaya → API call hua → Fresh data mila. Koi caching nahi.

**Flow ab aisa hai:**
```
User 1 aaya → cache: "no-store" → Layer 1 SKIP → Seedha API CALL → Fresh data
User 2 aaya → cache: "no-store" → Layer 1 SKIP → Seedha API CALL → Fresh data
```

**Ye "Dynamic Rendering" hai** — page har request pe server pe render hota hai. Data kabhi stale nahi, par har baar API hit hoti hai — slow, aur API pe load.

**Kab use karein:** Jab real-time data chahiye — stock prices, live scores, auction bids. Wahan stale data ka koi matlab nahi.

---

## Better Approach — Static (SSG) + Revalidate (ISR)

0.6 mein ISR seekha tha — **page static banao, par periodically refresh karo.** Dono ka best — fast static serve, aur data thoda fresh.

### Step 1 — Pure Static (SSG)

2.1 wala code bina kisi option ke:

```tsx
// app/products/page.tsx
export default async function ProductsPage() {
  const res = await fetch("https://dummyjson.com/products");
  const data = await res.json();

  return <main>{/* products render */}</main>;
}
```

Bina `cache` option ke, `fetch()` **by default cache hota hai** (0.5 wala caching model yaad karo). Matlab — **build time pe ek baar fetch hua, aur har user ko wahi static page.** Fast hai (CDN se serve), par data tab tak stale rahega jab tak rebuild nahi karte.

### Step 2 — ISR: `revalidate` Add Karo

Ab stale hone ki problem fix karte hain — `revalidate` option:

```tsx
// app/products/page.tsx
export default async function ProductsPage() {
  const res = await fetch("https://dummyjson.com/products", {
    next: { revalidate: 60 },   // har 60 second mein refresh
  });
  const data = await res.json();

  return <main>{/* products render */}</main>;
}
```

**`next: { revalidate: 60 }`** ka matlab:
- Page abhi static hai — fast serve hota hai
- Par **60 second ke baad** Next.js page ko background mein dobara render karta hai (fresh fetch)
- User ko kabhi koi slow load nahi dikhta — wo static page dekhta hai, phir Next.js background mein update karta hai
- Data kabhi 60 second se zyada stale nahi rehta

**Yehi ISR hai** (0.6 mein seekha tha). Static ki speed + dynamic ki freshness.

## Minimal Example — Dekho Practically

Ab isko **khud dekh** sakte ho. Product page mein time display add karo taaki pata chale ki page kab render hua:

```tsx
// app/products/page.tsx
interface Product {
  id: number;
  title: string;
  price: number;
}

interface ProductsResponse {
  products: Product[];
}

export default async function ProductsPage() {
  const res = await fetch("https://dummyjson.com/products", {
    next: { revalidate: 30 },
  });
  const data: ProductsResponse = await res.json();

  return (
    <main>
      <h1>Products</h1>
      <p>Page render time: {new Date().toLocaleTimeString()}</p>
      <ul>
        {data.products.map((product) => (
          <li key={product.id}>
            {product.title} — ${product.price}
          </li>
        ))}
      </ul>
    </main>
  );
}
```

**⚠️ Dev vs Production — Fark hai!**

| Mode | Kya hota hai |
|------|--------------|
| `npm run dev` | Caching properly kaam nahi karta — har refresh pe page re-render hota hai. Development ke liye hai, ISR test karne ke liye nahi. |
| `npm run build` + `npm start` | ISR properly kaam karta hai — 30 second cache, phir background refresh. |
| Vercel (production) | Same as production build — ISR properly follow hota hai. |

**ISR kaise test karein?**

```bash
npm run build    # Production build
npm start        # Production server start
```

Ab `/products` kholo:
1. Time note karo (e.g. 10:30:00)
2. Page reload karo (F5) — **time wahi rahega** (10:30:00) kyunki page cache hua hai
3. 30 second baad dobara reload karo — **time badal jayega** (10:30:31) — Next.js ne background mein refresh kiya

Yeh dekha tumne? Static serve + background refresh = ISR.

> **Kyun static + revalidate, dynamic hi kyun nahi?** Product listing mein data kam badalta hai (products roz nahi badalte). Static serve CDN se turant hota hai — user ke liye faster. `revalidate` se thoda thoda fresh rehta hai. Yeh "sweet spot" hai — har cheez dynamic karna overkill hai.

## Dynamic Kaise Banao — Jab Data Har Request Pe Chahiye

Kabhi data har request pe fresh chahiye hota hai — user ka cart, logged-in state, live score. Wahan static mat karo:

```tsx
// Dynamic — har request pe fresh
export default async function CartPage() {
  const res = await fetch("https://api.example.com/cart", {
    cache: "no-store",
  });
  // ...
}
```

Aur kisi ko `cache: "no-store"` har jagah lagane se matlab nahi — **har request pe server hit** = performance ki maut. Socho: ye data kitni baar badalta hai? Bahut → `no-store`. Thoda → `revalidate`. Bilkul nahi → static.

---

## Nutshell

| Rendering | Kya hota hai | Kab use karein |
|---|---|---|
| Static (SSG) | Build time pe ek baar render, CDN se serve | Data kabhi nahi badalta |
| ISR (`revalidate`) | Static + background refresh | Data kabhi-kabhi badalta |
| Dynamic (`no-store`) | Har request pe fresh render | Data har request pe fresh chahiye |

`fetch()` by default static/cache hota hai. `next: { revalidate: 60 }` se ISR banta hai. `cache: "no-store"` se dynamic. **Page ki nature data ki frequency decide karti hai.**

---

## Common Mistakes

- ❌ Har page ko dynamic banana (`no-store` everywhere) — performance kharab. Static/ISR ka fayda chhodo mat.
- ❌ `revalidate` ka matlab "page har 60 sec pe load hoga" samajhna — nahi, page static serve hota hai, **background** mein refresh hota hai. User ko koi slow load nahi dikhta.
- ❌ ISR ko `revalidate: 0` se dynamic banana — ye technical dynamic banata hai par confusing hai. `cache: "no-store"` zyada clear hai.
- ❌ User-specific data (cart, dashboard) ko static banana — security + privacy issue. Har user ka data alag hota hai, static sahi nahi.
- ❌ Data frequency na soch kar default pe rehna — default static hai (0.5 se). Agar data badalta hai aur tumne `revalidate` nahi lagaya, stale data milega.

## What It Is NOT

⚠️ **ISR = "real-time data" nahi.** ISR interval ke baad background mein refresh karta hai — koi exact moment pe update guarantee nahi. Real-time chahiye toh dynamic (ya client-side).

⚠️ **`revalidate` = "har user pe thoda time pe reload" nahi.** Page har user ko static hi milta hai; refresh background mein hota hai, ek baar ka. Concurrency issues Next.js khud handle karta hai.

⚠️ **Static = "sirf data-fetch pages ke liye" nahi.** Koi bhi page jo request-specific nahi (about, contact, documentation) static ho sakta hai — chahiye fetch ho ya na ho.
