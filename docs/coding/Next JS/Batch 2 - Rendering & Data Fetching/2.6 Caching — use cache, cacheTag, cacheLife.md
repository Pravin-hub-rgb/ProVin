# Caching — `use cache`, `cacheTag`, `cacheLife` (2.6)

## Where We Left Off

In 2.5.4 we finished Portfolio/Blog v2 — async Server Component data fetching with `await fetchAllPosts()`, dynamic SEO metadata, ISR via `revalidate`, and verified loading/error states work in production mode.

So far, caching has been at the **route level** — `revalidate` controls how often the entire page regenerates. But what if you want finer control: cache one API call for 5 minutes, another for 1 hour, invalidate a specific cached value when data changes, and share the cache across **all users**? That is the data cache — and it is what we cover next.

## The Three Layers of Caching

```
HTTP Cache (fetch layer) → Data Cache (use cache) → Route Cache (ISR/SSG) → CDN
     ↑                          ↑                       ↑
  cache: "no-store"       'use cache' + cacheTag    revalidate (per route)
```

1. **HTTP cache** — controls whether the `fetch()` response itself is cached (browser/CDN level). `{ cache: "no-store" }` disables it so Next.js controls caching.
2. **Data cache** — Next.js's server-side cache. Remember the *result* of a data fetch function, not just the HTTP response. Multiple users share the same cached result.
3. **Route cache** — `revalidate` / `generateStaticParams` control how long a full page is cached before regeneration.

The data cache (middle layer) is what you will use most. It is faster than hitting the database or API every time, and smarter than route-level caching.

## `'use cache'` — Remember a Data Fetch

The `use cache` directive tells Next.js: **remember the return value of this function.** The first request fetches; every subsequent request serves from cache — no re-fetch, no DB query, no API call.

```ts
// lib/posts.ts — a data-fetching function
import 'server-only';  // never imports run on the client

export async function getAllPosts() {
  const res = await fetch('https://jsonplaceholder.typicode.com/posts', {
    cache: 'no-store',  // let Next.js control caching, not the HTTP layer
  });
  return res.json() as Promise<Post[]>;
}
```

Now, instead of calling `getAllPosts()` directly in a page, we **import it into a cached context**:

```tsx
// app/blog/page.tsx
import { getAllPosts } from '@/lib/posts';
import { cache } from 'react';

// Wrap the fetch function with React's cache — it deduplicates concurrent calls
const getCachedPosts = cache(getAllPosts);

export default async function BlogPage() {
  const posts = await getCachedPosts();  // fetched once, cached forever (or until invalidated)

  return (
    <ul>
      {posts.map(post => <li key={post.id}>{post.title}</li>)}
    </ul>
  );
}
```

Here is what happens:

1. **First visitor** → `getCachedPosts()` runs `getAllPosts()` → fetches from API → caches the result.
2. **Second visitor** (same or different user) → `getCachedPosts()` returns the cached result immediately — no API call.
3. **1,000th visitor** → still serves from cache. The API is hit once per cache lifetime.

> **Remember:** `cache()` is a React primitive (not Next.js-specific). Next.js builds on top of it with `'use cache'` and `cacheTag`/`cacheLife`.

## `cacheTag` + `revalidateTag` — Invalidate by Label

Caching is dangerous if you **never invalidate**. A blog post published at 3 PM shows up at 2 PM forever. That is where **tags** come in — you label cached data and then purge it on command.

```tsx
// app/blog/page.tsx
import { cacheTag } from 'next/cache';
import { getAllPosts } from '@/lib/posts';

const getCachedPosts = cache(async () => {
  'use cache';                          // this function is cacheable
  cacheTag('posts');                    // label this cache entry with "posts"
  return getAllPosts();
});

export default async function BlogPage() {
  const posts = await getCachedPosts();
  return <BlogList posts={posts} />;
}
```

When a post is created (via a Server Action), purge the cache so the next visit sees the new post:

```ts
// app/actions/post.ts
'use server';

import { revalidateTag } from 'next/cache';
import { redirect } from 'next/navigation';

export async function createPostAction(formData: FormData) {
  const title = formData.get('title') as string;
  const body = formData.get('body') as string;

  // ... save to database ...
  await savePostToDB({ title, body });

  revalidateTag('posts');  // ← invalidate ALL cache tagged with "posts"
  redirect('/blog');       // navigate; next visit re-fetches fresh data
}
```

The flow:

1. User submits the create-post form.
2. `createPostAction` saves to the DB.
3. `revalidateTag('posts')` marks the tagged cache as **stale** — the next `getCachedPosts()` call will re-fetch.
4. `redirect('/blog')` navigates to the blog list — which now re-fetches from the DB and shows the new post.

## `cacheLife` — Auto-Expire After Time

Even without explicit invalidation, caches should expire. `cacheLife` sets a TTL (time-to-live):

```tsx
import { cacheLife } from 'next/cache';

const getTrendingPosts = cache(async () => {
  'use cache';
  cacheTag('trending');
  cacheLife({ hours: 1 });  // auto-expire after 1 hour
  return fetchTrendingPosts();
});
```

| Time unit | Example |
|---|---|
| `seconds` | `{ seconds: 30 }` |
| `minutes` | `{ minutes: 5 }` |
| `hours` | `{ hours: 1 }` |
| `days` | `{ days: 7 }` |

If a cache entry is older than its TTL, Next.js re-fetches silently — the stale data serves immediately, the fresh data updates the cache in the background (stale-while-revalidate).

## The Full Admin Flow: Tag → Create → Invalidate → Redirect

Here is the complete real-world pattern:

```tsx
// app/admin/page.tsx — form to create a post
export default async function AdminPage() {
  return (
    <form action={createPostAction}>
      <input name="title" required />
      <textarea name="body" required />
      <button type="submit">Create Post</button>
    </form>
  );
}
```

```ts
// app/actions/post.ts — the server action
'use server';

import { revalidateTag } from 'next/cache';
import { redirect } from 'next/navigation';

export async function createPostAction(prevState, formData: FormData) {
  const title = formData.get('title') as string;
  const body = formData.get('body') as string;

  // 1. Write to database (or API)
  await savePostToDatabase({ title, body });

  // 2. Invalidate the tagged cache — next blog page load re-fetches
  revalidateTag('posts');

  // 3. Redirect — redirect auto-revalidates the target route too
  redirect('/blog');
}
```

```tsx
// app/blog/page.tsx — the consumer
import { cache } from 'react';
import { cacheTag } from 'next/cache';

export const getPosts = cache(async () => {
  'use cache';
  cacheTag('posts');
  return getAllPostsFromDB();  // cached until revalidateTag('posts')
});

export default async function BlogPage() {
  const posts = await getPosts();
  return <BlogList posts={posts} />;
}
```

## Nutshell

| Tool | What it does | When to use |
|---|---|---|
| `'use cache'` | Makes a function cacheable | Expensive data fetches shared across users |
| `cacheTag` + `revalidateTag` | Invalidate specific cache by label | When data changes and you know the tag |
| `cacheLife` | Auto-expire after TTL | When you can't predict when data changes |
| `revalidate` (ISR) | Route-level revalidation | Static pages that update periodically |

## Common Mistakes

- ❌ **Caching user-specific data** — if cache entry A has user 1's data, cache entry B has user 2's data, but they share the same tag, invalidating one invalidates the other's private data. Cache per-user data under unique tags or skip caching.
- ❌ **Forgetting `revalidateTag` after mutations** — cache serves stale data forever. Every `create`/`update`/`delete` must invalidate the relevant tag.
- ❌ **Mixing `cache: "no-store"` and `'use cache'`** — `cache: "no-store"` on `fetch` prevents HTTP-level caching so Next.js's data cache controls the lifecycle. It is the correct combination — don't remove it.
- ❌ **Caching in client components** — `cache()` and `'use cache'` only work in server components. The client never sees the cache — it gets the already-resolved data.

## What It Is NOT

- **`'use cache'` is not browser caching.** It is Next.js's server-side data cache. The browser receives already-resolved data — the cache lives on the server.
- **It is not a substitute for invalidation.** If you cache everything but never invalidate, users see stale data indefinitely. Caching + invalidation is the full story.
- **It is not the same as ISR** (`revalidate` on `generateStaticParams`). ISR caches the **entire rendered page**; `'use cache'` caches the **data result**. They operate at different layers.

## In Your Own Words

1. What is the difference between `cache()` from React and `'use cache'` from Next.js?

<details>
<summary>Sample Answer</summary>

**Answer:** `cache()` (React primitive) deduplicates concurrent calls to the same function within a single render — so if Component A and B both call `getPosts()`, the fetch runs once. `'use cache'` (Next.js directive) persists the result across requests/users on the server — so the second visitor doesn't re-fetch at all.

</details>

2. How does `revalidateTag('posts')` work — is it synchronous?

<details>
<summary>Sample Answer</summary>

**Answer:** It is **not synchronous** — it marks the tagged cache as stale in the background. The current request still completes with whatever data it had. The next request that calls a function tagged with `'posts'` will re-fetch fresh data.

</details>

3. Why pair `cache: 'no-store'` on `fetch` with `'use cache'` on the component?

<details>
<summary>Sample Answer</summary>

**Answer:** `cache: 'no-store'` tells the lower-level HTTP layer NOT to cache the fetch response — so you have full control at the Next.js layer. `'use cache'` then tells Next.js's data cache to remember the *result* of your function. You want Next.js to decide when to re-fetch, not the HTTP cache.

</details>

4. If you cache per-user data, what's the risk with tags?

<details>
<summary>Sample Answer</summary>

**Answer:** If user 1 and user 2's data share the same tag (`'dashboard'`), invalidating the tag for user 1 also invalidates user 2's cache — potentially causing stale data for user 2 until their next fetch. Per-user data needs per-user tags (e.g. `` `dashboard-${userId}` ``) or shouldn't be cached at all.

</details>
