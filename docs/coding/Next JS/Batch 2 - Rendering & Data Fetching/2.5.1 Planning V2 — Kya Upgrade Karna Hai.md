## Planning V2 — What Upgrades?

We re-ask the same four planning questions from 1.5.1, but in the v2 context:

### Question 1 — What Are We Building?

The same Portfolio/Blog Site — upgraded. Same spine (routes, structure, data shape). The capabilities improve: async data, interactivity, SEO, performance.

### Question 2 — Which Pages?

The **same routes** — Home, About, Projects, Contact, Blog list, Blog `[slug]`. No new pages. What is new is a small interactive widget (a Like button on the blog post page) and metadata on every page.

Routes stay identical. The difference is **what happens within each route**, not the routing itself.

### Question 3 — What Is The Data?

The `Post` type stays the same — `slug`, `title`, `date`, `excerpt`, `content`. What changes is the **source**: instead of a synchronous array in `lib/posts.ts`, the data comes from an async function in `lib/posts-api.ts` that returns a `Promise`.

This is the key insight from 1.5.3 — the abstraction pays off. Because pages called `getAllPosts()` / `getPostBySlug(slug)` and did not know the data was from a "file," swapping to an async source changes only the data layer, not the pages' structure.

### Question 4 — What Is The Data Flow?

```
v1 (Batch 1):
  lib/posts.ts (sync array)
      ↓ getAllPosts() / getPostBySlug()
  app/blog/page.tsx, [slug]/page.tsx

v2 (Batch 2):
  lib/posts-api.ts (async, Promise-based)
      ↓ await fetchAllPosts() / await fetchPostBySlug()
  app/blog/page.tsx, [slug]/page.tsx  (now async Server Components)
```

Pages become `async` and use `await` — that is the only page-level change. Data shape, route structure, UI rendering all stay the same.

## The Four Upgrades

### Upgrade 1 — Async Data Source

**Problem:** Right now, `lib/posts.ts` holds a synchronous array — data is instant, no delay. Real apps fetch from an API.

**Solution:** Create `lib/posts-api.ts` with **async** functions:

```ts
// lib/posts-api.ts
export async function fetchAllPosts(): Promise<Post[]> {
  await new Promise((r) => setTimeout(r, 500));  // simulate network delay
  return posts;
}

export async function fetchPostBySlug(slug: string): Promise<Post | undefined> {
  await new Promise((r) => setTimeout(r, 300));
  return posts.find((p) => p.slug === slug);
}
```

- Functions are `async`, return `Promise` — identical behaviour to real `fetch()`.
- `setTimeout` simulates network latency — this is what triggers loading states.
- The `Post` type and data stay the same — only the delivery changes.

Pages now need `await`:

```tsx
// Before (1.5.4 — sync)
const posts = getAllPosts();

// After (v2 — async)
const posts = await fetchAllPosts();
```

And the page must be `async`:

```tsx
export default async function BlogPage() {
  const posts = await fetchAllPosts();
  // ...
}
```

### Upgrade 2 — Interactive Like Button (Client Component)

**Problem:** The site is entirely static — the user can navigate but cannot interact. No buttons that change state.

**Solution:** Add a **Like button** on the blog post page — it uses `useState` and `onClick`, so it must be a Client Component:

```tsx
// components/like-button.tsx
"use client";

import { useState } from 'react';

export default function LikeButton() {
  const [likes, setLikes] = useState(0);

  return (
    <button onClick={() => setLikes(likes + 1)}>
      ❤️ {likes} {likes === 1 ? 'Like' : 'Likes'}
    </button>
  );
}
```

- `"use client"` makes this a Client Component (2.2).
- The Server Component page **imports** this button — hybrid model: server renders the post, client handles the click.

**The rule (from 2.2):** Don't make the whole page a Client Component. Only the button. The page stays a Server Component for data fetching and SEO.

### Upgrade 3 — SEO Metadata

**Problem:** No metadata — browser tab shows a generic title, Google has no description.

**Solution:** Two metadata patterns:

1. **Static metadata** on fixed pages:

```tsx
// app/about/page.tsx
export const metadata = {
  title: 'About',
  description: 'Learn about me.',
};
```

2. **Dynamic metadata** (`generateMetadata`) on blog posts:

```tsx
// app/blog/[slug]/page.tsx
export async function generateMetadata({ params }) {
  const { slug } = await params;
  const post = await fetchPostBySlug(slug);
  if (!post) return { title: 'Post Not Found' };
  return { title: post.title, description: post.excerpt };
}
```

3. **Template** in root layout for consistency:

```tsx
// app/layout.tsx
export const metadata = {
  title: {
    default: 'My Portfolio',
    template: '%s | My Portfolio',
  },
  description: 'Full-stack developer.',
};
```

### Upgrade 4 — ISR Strategy

**Problem:** When does the page re-fetch? With the default, data is frozen at build time.

**Solution:** Add `revalidate` to the fetch (2.3):

```ts
// Real app — on the actual fetch call
export async function fetchAllPosts(): Promise<Post[]> {
  const res = await fetch('https://api.example.com/posts', {
    next: { revalidate: 300 },  // refresh every 5 minutes
  });
  return (await res.json()).posts;
}
```

Since our data layer currently uses `setTimeout` (not real `fetch`), we will demonstrate the concept and add the comment showing where `revalidate` would go in a real implementation. The pattern is ready.

## In Your Own Words

1. Why did we create a NEW file `lib/posts-api.ts` instead of modifying `lib/posts.ts` from Batch 1?

<details>
<summary>Sample Answer</summary>

**Answer:** Two reasons: (1) we want to compare both versions side by side — v1 synchronous and v2 async — to see the difference clearly. (2) It mirrors real-world architecture where data lives in a separate service/API layer. In production, we would share the `Post` type, but for learning, keeping both files makes the transition visible.

</details>

2. Why is the Like button a separate Client Component file instead of adding `"use client"` to the whole blog post page?

<details>
<summary>Sample Answer</summary>

**Answer:** From 2.2 — making the whole page a Client Component loses all Server Component benefits: no server-side data fetching, no SEO, slower initial load. By isolating the button as a small Client Component and importing it into the Server Component page, we keep the page fast and SEO-friendly while the button handles its own interactivity. This is the hybrid model — the recommended pattern.

</details>

3. What is the difference between static `export const metadata` and `generateMetadata`?

<details>
<summary>Sample Answer</summary>

**Answer:** Static `export const metadata` is an object with fixed values — good for pages where the title/description never change (About, Contact). `generateMetadata` is a function that can `await` data and return metadata dynamically — necessary for pages where the title depends on fetched data (e.g., a blog post's title comes from the API). Static is simpler; dynamic is needed when metadata depends on data.

</details>

4. How does the metadata template ensure consistent titles across the site?

<details>
<summary>Sample Answer</summary>

**Answer:** In the root `layout.tsx`, we set `title: { default: "My Portfolio", template: "%s | My Portfolio" }`. The `%s` is a placeholder for the page's own title. When a page sets `title: "About"`, the template resolves to "About | My Portfolio". The `default` is used when a page sets no title. One definition in the root layout ensures every page follows the same pattern — no repetition, no inconsistency.

</details>
