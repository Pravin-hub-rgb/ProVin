## Where We Left Off

In 9.0 we felt the Context re-render problem — 30+ components all re-rendering when one field changes, because Context has no selector. Redux Toolkit's `useSelector` solves this with selective re-renders.

Now, let's **set up Redux Toolkit from scratch**. We will create a store, define a slice, wire up typed hooks, and wrap our app in a provider.

## Broader Goal

- Create a Redux store with `configureStore`
- Define state shape with `createSlice` (auto-generated actions + Immer-powered reducers)
- Create typed hooks (`useAppDispatch`, `useAppSelector`)
- Wrap the app in a `Provider`

## Manual → Better

| Approach | Setup |
|---|---|
| Context API (manual) | `createContext` + `useContext` + manual value objects → no selectors, everyone re-renders |
| Redux Toolkit | `configureStore` + `createSlice` + `useSelector` → selectors pick exact slice, only affected re-render |

## What Is a Store?

Think of a Redux store as a **single JavaScript object** that holds all your app's state:

```ts
// Imagine your entire app's state in one place:
{
  user: { id: 1, name: "Pravin" },
  todos: [{ id: 1, text: "Learn Redux", completed: false }],
  theme: "light",
  cart: [],
}
```

**Three rules (the Redux way):**

1. **Single source of truth** — the store is the one place that holds state.
2. **State is read-only** — you never mutate it directly. You "dispatch an action" (a plain object describing what happened).
3. **Reducers are pure functions** — given the same state and action, they always produce the same new state.

> **Remember:** in plain React, your state is scattered across `useState` calls in each component. Redux centralizes it so any component can grab exactly what it needs — without re-rendering everything else.

## Creating a Slice

A **slice** is a piece of the store (e.g. `todos`). You define it with `createSlice`:

```ts
// store/todosSlice.ts
import { createSlice, type PayloadAction } from '@reduxjs/toolkit';

export interface Todo {
  id: number;
  text: string;
  completed: boolean;
}

const todosSlice = createSlice({
  name: 'todos',           // prefix for auto-generated actions: "todos/addTodo"
  initialState: [] as Todo[],
  reducers: {
    addTodo: (state, action: PayloadAction<Todo>) => {
      state.push(action.payload);  // Immer lets you "mutate" — it handles immutability
    },
    toggleTodo: (state, action: PayloadAction<number>) => {
      const todo = state.find(t => t.id === action.payload);
      if (todo) todo.completed = !todo.completed;
    },
    deleteTodo: (state, action: PayloadAction<number>) => {
      return state.filter(t => t.id !== action.payload);
    },
  },
});

// Auto-generated action creators
export const { addTodo, toggleTodo, deleteTodo } = todosSlice.actions;
// The reducer to install in the store
export default todosSlice.reducer;
```

**Line-by-line:**

- **`name: 'todos'`** — the prefix for action types. `addTodo` becomes `{ type: "todos/addTodo", payload: ... }`.
- **`initialState: [] as Todo[]`** — TypeScript type assertion. The store starts with an empty todos array.
- **`addTodo` reducer** — `PayloadAction<Todo>` types the action payload as `Todo`. `state.push(action.payload)` looks like mutation, but Redux Toolkit uses **Immer** under the hood — your "mutations" become safe immutable updates automatically.
- **`toggleTodo`** — finds the todo by `id`, flips `completed`. Immer tracks the draft mutation.
- **`deleteTodo`** — `return state.filter(...)` — returns a **new array**. No Immer needed here, but it's safe either way.
- **`todosSlice.actions`** — auto-generated. You did not write `ADD_TODO = "todos/addTodo"` or a switch statement.

## Configure the Store

Now wire the slice into a store:

```ts
// store/store.ts
import { configureStore } from '@reduxjs/toolkit';
import todosReducer from './todosSlice';

export const store = configureStore({
  reducer: {
    todos: todosReducer,
  },
});

// TypeScript types — used for typed hooks
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

**`configureStore` does three things auto-matically:**

1. Sets up **Redux DevTools** (inspect state, time-travel debug).
2. Adds **thunk middleware** (for async actions later).
3. Combines reducers (`{ todos: todosReducer }`) into one root reducer.

`RootState` and `AppDispatch` are types derived from the store — they let your hooks know the exact shape of state and which actions you can dispatch.

## Create Typed Hooks

```ts
// store/hooks.ts
import { useDispatch, useSelector, type TypedUseSelectorHook } from 'react-redux';
import type { RootState, AppDispatch } from './store';

export const useAppDispatch = () => useDispatch<AppDispatch>();
export const useAppSelector: TypedUseSelectorHook<RootState> = useSelector;
```

These are just typed wrappers around `useDispatch` and `useSelector` — so TypeScript knows your state shape. Instead of `useDispatch()` returning a generic dispatcher, `useAppDispatch()` knows exactly which actions your app can fire.

## Wire It Into Your App

Redux needs a `<Provider>` wrapper. Since hooks require a client component, the Provider must be a **Client Component** (`'use client'`):

```tsx
// store/store-provider.tsx
'use client';  // React hooks → client component required

import { Provider } from 'react-redux';
import { store } from './store';

export function StoreProvider({ children }: { children: React.ReactNode }) {
  return <Provider store={store}>{children}</Provider>;
}
```

Wrap the entire app in your root layout:

```tsx
// app/layout.tsx
import { StoreProvider } from '@/store/store-provider';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <body>
        <StoreProvider>{children}</StoreProvider>
      </body>
    </html>
  );
}
```

> **Important:** The `<Provider>` lives in `layout.tsx` — it's the highest-level wrapper. Any page or component can now use `useAppSelector` and `useAppDispatch`. The `StoreProvider` is a **Client Component** (`'use client'`) because it uses React hooks — but `layout.tsx` itself can still be a Server Component, with `StoreProvider` as a client child.

## Nutshell

| File | Purpose |
|---|---|
| `todosSlice.ts` | Defines a slice of state + its actions |
| `store.ts` | Combines slices into one store + exports types |
| `hooks.ts` | Typed `useAppDispatch` + `useAppSelector` |
| `store-provider.tsx` | `'use client'` Provider wrapper for the app |

## Common Mistakes

- ❌ **Mutating state directly** in a reducer — use Immer's draft syntax (which `createSlice` enables) or `return` a new state.
- ❌ **Storing non-serializable values** (functions, class instances, Promises) in the store — DevTools and persistence break.
- ❌ **Putting server data in Redux** — if you can re-fetch it from an API, use Server Components + caching instead.
- ❌ **Creating the store inside a component** — the store must be a single instance, created once at module level.

## What It Is NOT

- **It is not a replacement for Context for everything.** A theme toggle across 3 components? Context is fine. A todo list that 20 components read and modify? Redux Toolkit.
- **It is not magic for performance.** It solves selective re-renders, not expensive computation. For render-cost problems, reach for `React.memo`/`useMemo` (0.0.5 Section 15).
- **It does not replace Server Actions** for mutations. Use Server Actions for data that talks to a database — Redux is for **client-side UI state** (selections, filters, drafts, forms).

## In Your Own Words

1. What does `createSlice` auto-generate for you?

<details>
<summary>Sample Answer</summary>

**Answer:** From your `reducers` object, `createSlice` generates: (1) an action creator function for each reducer (e.g. `addTodo`), (2) the reducer function itself with auto-prefixed action types (e.g. `"todos/addTodo"`). You never write the action type strings or switch statements by hand.

</details>

2. Why do we need `RootState` and `AppDispatch` types?

<details>
<summary>Sample Answer</summary>

**Answer:** They let our custom hooks be fully typed. `RootState = ReturnType<typeof store.getState>` gives TypeScript the exact shape of our store state, so `useAppSelector` knows what `state.todos` looks like. `AppDispatch = typeof store.dispatch` lets `useAppDispatch` know which actions can be dispatched.

</details>

3. Why must `StoreProvider` have `'use client'`?

<details>
<summary>Sample Answer</summary>

**Answer:** It uses React hooks (`useState`, `useReducer` internally) from `react-redux`, and hooks can only run in Client Components. Server Components do not execute hooks. The `Provider` wraps the app so every component can access the store — it must be client-side.

</details>

4. Where should the `<Provider>` go — in `page.tsx` or `layout.tsx`?

<details>
<summary>Sample Answer</summary>

**Answer:** In `layout.tsx` — the root layout. This ensures every page in the app has access to the store. If you put it in `page.tsx`, only that page's tree gets Redux; other routes would not.

</details>
