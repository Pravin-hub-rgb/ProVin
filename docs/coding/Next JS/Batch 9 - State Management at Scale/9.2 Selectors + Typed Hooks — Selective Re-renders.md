## Manual → Better

| Approach | Re-renders on `state.user.name` change |
|---|---|
| Context API | ✅ ALL consumers (no selector mechanism) |
| `useSelector(state => state)` | ✅ ALL subscribers (selecting the whole store) |
| `useSelector(state => state.todos)` | ❌ Only components reading `todos` re-render |

## How `useSelector` Works

`useSelector` takes a **selector function** — it calls this function on every store update, gets the result, compares it to the previous result, and decides whether the component re-renders:

```ts
// This selector picks ONLY the todos slice
const todos = useSelector((state) => state.todos);
```

Here is what happens internally:

1. Store updates (e.g. user adds a todo).
2. Redux calls your selector: `selector(state)` → returns `state.todos` (the array).
3. Redux compares: `prevResult !== newResult`?
   - If `state.todos` is the **same reference** (unchanged) → **skip re-render**
   - If `state.todos` is a **new reference** (changed) → **re-render**

This is **shallow comparison** — Redux checks if the return value changed. It does NOT deep-compare the contents. This is fast and reliable because Redux Toolkit's `createSlice` always returns new references when state changes.

## The Mistake That Breaks Selectors

```tsx
// ❌ WRONG — selects the whole store
const everything = useSelector((state) => state);  // every update → re-render

// ❌ WRONG — returns a new object every time
const { todos } = useSelector((state) => ({
  todos: state.todos,
}));  // object is new reference → always re-renders!

// ✅ RIGHT — selects a primitive/slice (stable reference)
const todos = useSelector((state) => state.todos);
```

Picking the whole store (`(state) => state`) means your component re-renders on **every** state change — just like Context! The selector must return the **specific piece** the component needs.

## Precise Selectors — One Component, One Concern

The power of Redux is that different components can read the same store without re-rendering each other:

```tsx
// Component 1 — only cares about the user
function UserProfile() {
  const user = useAppSelector((state) => state.user);
  return <h1>{user.name}</h1>;
}

// Component 2 — only cares about todo count
function TodoCount() {
  const todos = useAppSelector((state) => state.todos);
  return <span>{todos.length} todos</span>;
}

// Component 3 — only cares about theme
function ThemeToggle() {
  const theme = useAppSelector((state) => state.theme);
  return <button className={theme}>Toggle</button>;
}
```

When `user.name` changes:
- `UserProfile` re-renders (it reads `state.user`)
- `TodoCount` does NOT re-render (reads `state.todos` — unchanged)
- `ThemeToggle` does NOT re-render (reads `state.theme` — unchanged)

This is the selective re-render that Context cannot do.

## `createSelector` — Memoized Derived Data

Sometimes you need to **derive** data from state — filter a list, count items, sort. If you do this inside `useSelector`, it runs on every store update:

```tsx
// ❌ Runs the filter on EVERY store update, even if todos didn't change
const completed = useAppSelector((state) =>
  state.todos.filter(t => t.completed)
);
```

`createSelector` from the `reselect` library memoizes the result:

```ts
// ✅ Only recomputes when todos actually change
const selectCompletedTodos = createSelector(
  [(state) => state.todos],
  (todos) => todos.filter(t => t.completed)
);
```

> **Note:** Redux Toolkit re-exports `createSelector` from `@reduxjs/toolkit`, so you don't need a separate `reselect` import. Only use it for expensive derived data — simple property access (`state.todos`) is cheap and has no benefit from `createSelector`.

## Nutshell

| Selector pattern | Re-renders? | When to use |
|---|---|---|
| `useSelector(state => state.todos)` | Only when `todos` changes | Most components — pick a slice |
| `useSelector(state => state)` | On every state change | Never — this defeats the purpose |
| `useSelector(state => ({ todos: state.todos }))` | Always — new object every time | Never — object is new ref each time |
| `createSelector(state => state.todos, ...)` | Only when input slice changes | Expensive derived/computed data |

## Common Mistakes

- ❌ **Selecting the whole store** — `useSelector(state => state)` re-renders on every action
- ❌ **Returning new objects in the selector** — `{ todos: state.todos }` creates a new reference every time
- ❌ **Forgetting that shallow comparison is reference equality** — if your selector returns a primitive (`state.user.name`), it compares values directly. If it returns an object/array, it compares references.
- ❌ **Using `createSelector` for trivial data** — `state.todos.length` doesn't need it; only expensive derived computations do

## What It Is NOT

- **It is not deep comparison.** Redux uses **shallow** comparison — same reference = no re-render. Don't expect nested changes to be detected.
- **It is not a computation optimizer.** `useMemo` is for expensive computations inside a component render. `createSelector` is for expensive computations from store state. Different concerns.
- **It is not optional.** Without precise selectors, Redux is just Context with extra steps — you'll get the exact same re-render cascade.

## In Your Own Words

1. Why does `useSelector((state) => state.todos)` NOT re-render when `state.user` changes?

<details>
<summary>Sample Answer</summary>

**Answer:** Redux calls the selector function, gets `state.todos`, and does a shallow comparison with the previous result. Since `state.user` changed but `state.todos` is the same array reference, the comparison passes as "equal" → no re-render. The component only re-renders when `state.todos` is a new reference.

</details>

2. Why is `useSelector((state) => ({ todos: state.todos }))` a mistake?

<details>
<summary>Sample Answer</summary>

**Answer:** The selector returns a new object `{ todos: state.todos }` every time the store updates. Even though `state.todos` is the same reference, the outer object is new. Shallow comparison sees "new reference" → always re-renders. Use `const todos = useSelector(state => state.todos)` instead — return the slice directly.

</details>

3. When should you use `createSelector`?

<details>
<summary>Sample Answer</summary>

**Answer:** For expensive derived data — like filtering a list, sorting, or computing aggregates — that should NOT recompute unless the input slice changes. For simple property access (`state.todos.length`), it's unnecessary. `createSelector` memoizes the result so the expensive work only runs when the input actually changes.

</details>
