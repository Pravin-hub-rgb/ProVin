## Manual → Better

| Approach | At scale |
|---|---|

## The Problem — Context Re-renders Everyone

You already know Context from the React course. The pattern is simple:

```tsx
// A shared context for a dashboard
const DashboardContext = createContext({
  user: { name: 'Pravin', avatar: '...' },
  theme: 'light',
  todos: [{ id: 1, text: 'Build dashboard', completed: false }],
  notifications: 3,
});

function App() {
  // Everything in one object
  const [dashboard, setDashboard] = useState({
    user: { name: 'Pravin', avatar: '...' },
    theme: 'light',
    todos: [],
    notifications: 3,
  });

  return (
    <DashboardContext.Provider value={dashboard}>
      <Sidebar />      // only reads user
      <TodoList />     // reads todos
      <NotificationBell /> // reads notifications
      <ThemeToggle />  // reads theme
    </DashboardContext.Provider>
  );
}
```

Here is the catch: when `user.name` changes, `dashboard` becomes a **new object** (state is immutable). The provider's `value` prop is now a different reference. React marks the value as "changed" and **re-renders every single consumer** — even `<TodoList>` (which only reads `todos`) and `<ThemeToggle>` (which only reads `theme`).

Why? Because **Context has no selector mechanism.** It hands every consumer the entire context object and says "if the reference changed, everyone re-renders." There is no way to say "I only care about `user.name`."

## Real-World Pain

This is not theoretical. In production Next.js apps:

- 30+ components subscribe to a context holding `{ user, theme, cart, todos, notifications }`.
- A user updates their profile picture → `user` changes → provider value is replaced.
- **All 30 components re-render** — even the ThemeToggle that just needs `theme: 'dark'`.
- You try `useMemo`/`React.memo` patches (0.0.5, Section 15) — but it is whack-a-mole.

## Better Approach — Redux Toolkit

Redux Toolkit gives you three things Context cannot:

1. **A single store** — one object, split into typed slices.
2. **Slices** — `createSlice` auto-generates actions + reducers.
3. **Selectors** — `useSelector(state => state.theme)` picks the exact piece. Only components reading that slice re-render.

Let's see how selectors solve the problem:

```
Without selectors (Context):
dashboard changes → ALL 30 components re-render

With selectors (Redux):
dashboard.user changes → only the 3 components reading state.user re-render
                         (TodoList, ThemeToggle, NotificationBell stay untouched)
```

**React Redux does a shallow comparison** on the selector's return value. If `state.todos` is the same reference as last time, the component does not re-render — period. Context has no equivalent.

## Nutshell

| Context API | Redux Toolkit |
|---|---|
| `value` = whole object → any change re-renders everyone | `useSelector(state => state.X)` → only readers of X re-render |
| No DevTools | Full DevTools + time-travel |
| Fine for < 5 shared consumers | Designed for 10+ shared consumers |

## What It Is NOT

- **It is not always needed.** If only 2 components share state, Context is fine. Add Redux Toolkit only when you feel the re-render pain.
- **It is not magic for performance.** If your components are slow because they do expensive work, `useMemo`/`React.memo` (0.0.5 Section 15) is what you reach for — Redux won't help there.
- **It is not a database.** It is client-side state only — if you can re-fetch it from an API/DB, use Server Components + caching instead.

## In Your Own Words

1. Why do all Context consumers re-render when one field in the context value changes?

<details>
<summary>Sample Answer</summary>

**Answer:** Context has no selector mechanism. When the provider's `value` prop changes (even one field), React sees a new reference and re-renders every consumer. Context can't say "I only care about `theme`." Redux Toolkit's `useSelector(state => state.theme)` does shallow comparison — only theme-reading components re-render.

</details>

2. What does Redux Toolkit's selector do that Context cannot?

<details>
<summary>Sample Answer</summary>

**Answer:** `useSelector((state) => state.todos)` selects only the `todos` slice. React Redux does a shallow comparison on the return value, so the component only re-renders when `state.todos` actually changes — not when `state.user` or `state.theme` changes. Context has no equivalent.

</details>

3. At what point should you consider Redux Toolkit over Context?

<details>
<summary>Sample Answer</summary>

**Answer:** When 10+ components read and write the same shared state, and re-render cascades become a measurable performance problem. Context is fine for small apps (< 5 consumers). Redux Toolkit handles the scaling problem with selectors, DevTools, and structured updates.

</details>
