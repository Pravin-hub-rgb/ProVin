## Broader Goal

- Know the **decision framework** for client-side state management
- Understand the **trade-offs**: bundle size, learning curve, DevTools
- Recognize the **signs** that your app has outgrown Context

## Manual → Better → Production

| Scale | Approach | Example |
|---|---|---|
| 2-3 components | `useState` + props | Toggle in a modal |
| 5-10 components, local | Context API | Theme, locale |
| 10-30 components, shared | Zustand | Shopping cart, form wizard |
| 30+ components, heavy writes | Redux Toolkit | Dashboard with live updates, task management |
| Server data only | Server Actions + caching | API responses, database reads |

## When to Use Redux Toolkit

**Red flags that you've outgrown Context:**

1. **Cascade re-renders are visible** — typing in one field causes unrelated components to jank.
2. **Prop drilling depth > 5** — you are passing callbacks through 5+ component layers.
3. **Debugging is painful** — you don't know which component changed what state, when.
4. **Time-travel would help** — you want to "undo" an action or step back through state changes.

If **two or more** of these apply, Redux Toolkit is worth the setup cost.

## When to Use Context / Zustand Instead

**Stick with Context or Zustand when:**

1. **Fewer than 5 shared consumers** — the re-render cascade is negligible.
2. **State rarely changes** — theme toggle, locale, dark mode.
3. **You need minimal bundle size** — Redux Toolkit adds ~20KB. Context is built-in.
4. **Simple read/write patterns** — no complex derived state or selective updates.

| Tool | Bundle size | Learning curve | DevTools | Selective re-renders |
|---|---|---|---|---|
| Context API | 0 (built-in) | Low | No | No (everyone re-renders) |
| Zustand | ~5KB | Low | Limited | With selectors |
| Redux Toolkit | ~20KB | Medium | Full (time-travel) | Yes (useSelector) |

## When to Skip All of Them

**Don't reach for any of these if:**

- The state can be **fetched from the server** — use Server Actions + `revalidateTag`/`revalidatePath`.
- The state is **purely local** — form input, toggle, expanded/collapsed — use `useState`.
- The state is **derived from props** — compute it directly. No need to store it.

> **Key insight:** Redux is for **shared client-side UI state** that many components read AND write. Server data, local component state, and derived data don't belong in Redux.

## Nutshell

| Use this | For this | When NOT to |
|---|---|---|
| `useState` | Local, component-only state | When siblings or deep children need it |
| Context API | App-wide config (theme, locale) | 10+ consumers with frequent overlapping updates |
| Zustand | Lightweight global store | When you need DevTools, time-travel, or middleware |
| Redux Toolkit | Complex shared state at scale | Small apps, server-only data, local-only state |

## Common Mistakes

- ❌ **Adding Redux to a new project by default** — start with Context + Zustand. Add Redux when you feel the pain.
- ❌ **Putting server data in Redux** — if it can be fetched, use Server Components + caching instead.
- ❌ **Not using selectors** — `useSelector(state => state)` re-renders on every action, just like Context.
- ❌ **Over-memoizing with `createSelector`** — simple `state.todos` access doesn't need it.

## What It Is NOT

- **It is not always needed.** Most Next.js apps work great with Context + Zustand. Add Redux Toolkit only when Context's re-render cascade becomes a measurable problem.
- **It is not a data-fetching replacement.** Redux is for **client state** (UI selections, form drafts, local preferences). Server data (from databases, APIs) should use Server Actions + caching.
- **It is not the only option.** Zustand (with selectors) covers many Redux use cases with 1/4 the bundle size and 1/10th the boilerplate.
