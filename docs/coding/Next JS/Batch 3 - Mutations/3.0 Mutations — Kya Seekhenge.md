## Broader Goal

Think about every app you use daily — Instagram, Gmail, Todoist, or even the comment section on a blog:

- You post a comment (create new data)
- You like a photo (update existing data)
- You delete a message (remove data)
- You edit your profile (update data)

All of these involve **sending data to a server**, not just receiving it.

In technical terms, we're moving beyond `GET` requests (where we just read data) to using other HTTP methods that let us **write, update, and delete** data.

## Two Approaches — Not One

**Don't get confused:** this isn't about "this is right, that is wrong." **Both approaches work in different situations.**

Both approaches move data between the browser and the server — the difference is the path the data takes:

- **Route Handlers** = the browser sends an HTTP request (with method, URL, headers, body) to an API endpoint; the server reads the request, calls the data layer, and sends an HTTP response back
- **Server Actions** = the form submits directly to a server function; the data travels as function arguments (FormData), and the server runs the data layer and returns the result

Both end with the server processing data and updating the store. The question is which connection fits the situation.

---

## Route Handlers (REST API) — The Fundamental Approach

Route Handlers are **fundamental** — every web developer should know this. In React, you used `fetch()` to call APIs — the same pattern. With Route Handlers, you build an API endpoint (`/api/comments`) and call it from the client with `fetch()`.

**Use when:**
- You need to provide an API for third-party apps (mobile app, another website)
- You have complex operations (file upload, payment processing)
- You need to talk to external services
- You're working with microservices architecture

Route Handlers expose an HTTP endpoint, so any client — a browser `fetch()`, a mobile app, or a third-party service — can send data to and receive data from the server. The API layer sits between the caller and the data layer.

---

## Server Actions — The Next.js Shortcut

Server Actions are **Next.js-specific** — they only work in the App Router. Instead of building an API endpoint, the form directly calls a server function. No API endpoint, no `fetch()` — the boilerplate drops significantly.

**Use when:**
- It's a simple form submission (like adding a comment, updating a profile)
- It's only a Next.js app — no external clients
- You want quick CRUD operations
- You don't need a separate API layer

Server Actions skip the HTTP API layer — the form data goes straight to a server function that reads/writes the data store. Less boilerplate, but only works inside a Next.js app.

---

## Comparison

| | Route Handlers (REST) | Server Actions |
|---|---|---|
| **Universal?** | Yes — works everywhere | No — only Next.js |
| **Boilerplate** | More — route file, fetch call, types | Less — write a function, done |
| **External clients** | Supported | Not supported (Next.js app only) |
| **Industry standard** | Yes — REST is universal | No — Next.js specific |
| **Complex operations** | Better control | Limited |

---

## "Manual → Better" Is Not Right — It's "Fundamental → Shortcut"

In the roadmap, Route Handlers were described as "manual" and Server Actions as "better." **That was misleading framing.**

**The right framing:**
- Route Handlers = **Fundamental** — learn this first, it works everywhere
- Server Actions = **Next.js shortcut** — learn this second, it's for forms only

It's like React's `useEffect` (fundamental) versus React Query (shortcut). `useEffect` isn't "worse" than React Query — React Query is just easier for specific use cases.

## In Your Own Words

<details>
<summary>Question 1: What's the difference between reading data and mutating data?</summary>
<p><strong>Answer:</strong> Reading data (GET) means fetching existing data without changing anything — like loading a webpage or viewing a product list. Mutating data means changing the server's data state — creating new records (POST), updating existing ones (PUT), or deleting them (DELETE). Reading is safe and idempotent; mutation permanently changes the data.</p>
</details>

<details>
<summary>Question 2: Why can't we use Server Actions if an external mobile app needs to access our data?</summary>
<p><strong>Answer:</strong> Server Actions are Next.js-specific — they only work within a Next.js app through form submissions. They don't create REST API endpoints that external apps can call. If a mobile app needs to interact with our data, we need Route Handlers to expose a proper API.</p>
</details>

<details>
<summary>Question 3: How do Route Handlers and Server Actions differ in how data travels?</summary>
<p><strong>Answer:</strong> Route Handlers expose an HTTP endpoint: the browser (or any client) sends a request with method/URL/body, the server parses it, calls the data layer, and sends a response back. Server Actions skip that HTTP layer — form data is passed directly as arguments to a server function, which calls the data layer and returns the result. Both end with the server processing and saving data; the difference is whether the data travels over HTTP as a request/response or directly as a function call.</p>
</details>
