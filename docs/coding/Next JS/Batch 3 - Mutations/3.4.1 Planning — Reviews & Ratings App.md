## What We're Building

A **Reviews & Ratings App** — where users can review products.

Think of Zomato — you look at a restaurant, see reviews from other users, and leave your own. Some reviews have 5 stars, others have 3. "Great food!" or "Average experience." You can also add your own review — write text, give a rating, submit.

That's what we're building — a simplified version. No real restaurants, no real users — just **2 products** with reviews on them.

**Why this project?** It brings together all of Batch 3's concepts:
- **Route Handlers** — building API endpoints (GET, POST, PUT, DELETE)
- **Server Actions** — forms calling server functions directly
- **HTTP Methods** — each operation uses its appropriate method
- **useActionState** — pending state and success/error messages
- **Revalidation** — data refresh after mutations

## Data Shape — What the UI Needs

Before writing code, let's think about what the UI needs to display:

**List page:**
- Product name (Product 1, Product 2)
- Reviews for each product
- Each review shows: text, rating (1-5 stars), date
- Form to add a new review (textarea + rating select + submit)

**Detail page:**
- Full review text
- Rating stars
- Date
- Edit button → opens a form
- Delete button

Now, what data fields do we need for each review?

| Field | Type | Why it exists |
|---|---|---|
| `id` | number | Needed for edit/delete — identifies which review |
| `productId` | number | Links review to a product — for filtering |
| `text` | string | The actual review content |
| `rating` | number | 1-5 stars |
| `createdAt` | string | When the review was added |

**Every field has a purpose:**
- Without `id`, we can't edit or delete — there's no way to identify the specific review
- Without `productId`, we can't show "Product 1's reviews" vs "Product 2's reviews"
- `text` and `rating` are the actual review content
- `createdAt` tells users when the review was posted

## Data Flow

You've seen this pattern before. In 3.1, the server had a Route Handler that called the data layer. In 3.3, the form directly called a Server Action. Same flow — just different connection.

**Data lives in a JSON file** — `reviews.json`. We haven't learned databases yet, so files handle the persistence. The `fs` module reads and writes (learned in 3.2).

**Functions in `lib/reviews.ts`:**
- `getAllReviews()` — fetch all reviews
- `getReviewsByProduct(id)` — filter by product
- `addReview(data)` — create a new review
- `updateReview(id, data)` — edit a review
- `deleteReview(id)` — remove a review

**Two versions to build:**
1. **Route Handler version** — API endpoints, client fetches with axios
2. **Server Actions version** — Direct function calls, no API needed

Both use the same data layer — only the connection method changes. We start with Route Handlers (the fundamental approach), then refactor to Server Actions for comparison.

## In Your Own Words

<details>
<summary>Question 1: Why is planning important before coding?</summary>
<p><strong>Answer:</strong> Planning lets you think through the data shape, routes, and flow before writing code. If you jump straight to coding, you'll likely need to restructure mid-way — which wastes time. A plan is like a blueprint: it shows you where everything goes before you start building.</p>
</details>

<details>
<summary>Question 2: Why does the data shape match the UI?</summary>
<p><strong>Answer:</strong> The UI determines what data we need. The list page needs to display review text, stars, and date — so those become fields in our data. If you design the data first without looking at the UI, you might end up with fields the UI doesn't use, or missing fields the UI needs.</p>
</details>

<details>
<summary>Question 3: Why build two versions of the same feature?</summary>
<p><strong>Answer:</strong> Route Handlers are fundamental — they work everywhere and are necessary for external APIs. Server Actions are a Next.js shortcut — less code, more convenience. Building both shows you the tradeoffs directly: where Server Actions shine (less boilerplate) and where Route Handlers are necessary (external access, complex operations).</p>
</details>

<details>
<summary>Question 4: Why use a JSON file instead of a database?</summary>
<p><strong>Answer:</strong> Databases haven't been introduced yet. JSON files are simple — just use `fs` to read and write. The pattern is the same: when you later switch to a database, only the data layer functions change, not the rest of the app.</p>
</details>

<details>
<summary>Question 5: Why do we need both `id` and `productId`?</summary>
<p><strong>Answer:</strong> `id` identifies the review itself — needed for edit/delete ("which review?"). `productId` links the review to a product — needed for filtering ("show me Product 1's reviews"). They serve different purposes: `id` is the review's identity, `productId` is its relationship to a product.</p>
</details>
