# Summary — What Did We Refactor? (3.3.5)

## Where We Left Off

In 3.3.4, we converted the edit operation to a Server Action and turned the detail page into a Server Component. That was the last mutation to convert. From start to finish, the entire comments project has been refactored from Route Handlers to Server Actions.

Let's take a step back and see the complete picture — what we started with, what we ended with, and what was gained.

## Refactor Recap

| File (3.3.x) | What We Converted | Result |
|---|---|---|
| 3.3.1 | POST (add comment) | `addCommentAction` + `<form action>` + `useActionState` + `sonner` toast |
| 3.3.2 | GET (list) | `page.tsx` Server Component + `getAllComments()` + `revalidatePath` |
| 3.3.3 | DELETE (delete) | `deleteCommentAction` + form + hidden input |
| 3.3.4 | PUT (edit) + GET (detail) | Server Component + `updateCommentAction` + `notFound()` |

Each step converted one operation from Route Handlers to Server Actions. Unused route handlers were deleted immediately. By the end, **the entire `app/api/` folder was deleted.**

**What changed:**
- `app/api/` — **completely deleted** (4 HTTP handlers gone)
- `page.tsx` + detail page — Client → Server Component
- **3 Client Components remain** — but only for interaction/hooks:
  - `CommentForm.tsx` (form + `useActionState`)
  - `ShowComments.tsx` (list props + delete form)
  - `EditCommentForm.tsx` (edit toggle)

None of these Client Components do data fetching anymore — that's handled by Server Components.

## Code Comparison — How Much Boilerplate Was Eliminated?

### Data Fetching — The Biggest Win

**Before:**
```tsx
// Client Component — ~12 lines to fetch data
"use client";
import { useEffect, useState } from "react";
const [allComments, setAllComments] = useState([]);
useEffect(() => {
  const fetchComments = async () => {
    const res = await fetch("/api/comments");
    const comments = await res.json();
    setAllComments(comments);
  };
  fetchComments();
}, []);
```

**After:**
```tsx
// Server Component — 1 line to read data
import { getAllComments } from "@/lib/comments";
const comments = getAllComments();
```

**12 lines → 1 line.** And no loading state, no `useEffect`, no `useState`.

### Form Submission — Consistent Pattern

All three mutations (add, delete, update) now follow the **same pattern**:

```tsx
// Server Action (actions.ts)
export async function actionName(
  prevState: FormState,
  formData: FormData
): Promise<FormState> {
  const value = formData.get("name");   // 1. Extract data
  // validation...
  const result = libFunction(value);     // 2. Call data layer
  revalidatePath("/");                   // 3. Revalidate after mutation
  return { success: true, message: "..." };  // 4. Return state
}
```

```tsx
// Client Component (form)
const [state, formAction, isPending] = useActionState(actionName, initialState);

useEffect(() => {
  if (state.message) {
    state.success ? toast.success(state.message) : toast.error(state.message);
  }
}, [state]);

<form action={formAction}>
  <input name="..." />
  <input type="hidden" name="id" value={item.id} />
  <button disabled={isPending}>{isPending ? "Saving..." : "Save"}</button>
</form>
```

**One pattern, used everywhere.** Once you learn it, you can apply it to any form.

### Loading States — Simplified

```tsx
// Before: manual loading + empty check
if (!comment) return <p>Loading...</p>;

// After: not needed
// Server Component has data at render time
```

## Key Patterns Learned

1. **Server Component reads, Server Action writes.** Read data with a Server Component (direct `lib` calls). Write data with a Server Action (`action={formAction}`).

2. **The `name` ↔ `formData.get("name")` rule.** The form input's `name` attribute must match what you pass to `formData.get()` on the server.

3. **Hidden input for server-only values.** Need to pass an ID that the user doesn't type? Use `<input type="hidden" name="id" value={item.id} />`.

4. **`revalidatePath` after every mutation.** After `addComment()`, `deleteComment()`, or `updateComment()`, call `revalidatePath("/")` to trigger a fresh render. The user sees changes immediately.

5. **Split: Server Component for data, Client Component for interaction.** The page and data reading stay Server Components. Forms and buttons that need hooks (`useState`, `useActionState`) stay Client Components.

## Common Mistakes

- **Forgetting `"use server"`** — without it, the function isn't a Server Action
- **Using controlled inputs unnecessarily** — `defaultValue` works for Server Actions; you don't need `value` + `onChange`
- **Not calling `revalidatePath` after mutations** — the data changes on the server but the UI never updates
- **Putting `"use client"` on the page** — if the page only reads data (no hooks), keep it a Server Component

<p><strong>Answer:</strong> The entire folder was deleted. Once all four operations (GET, POST, PUT, DELETE) were converted to Server Actions (3.3.1–3.3.4), the route handlers became unused. (2) Client component uses `useActionState` to get `formAction`, wires it to `<form action={formAction}>`, uses `isPending` for loading state, and shows toast on `state` changes.</p>

## Bridge to Next — Advanced Form Patterns

Now you know the core Server Actions pattern: `"use server"`, `FormData`, `useActionState` for pending/error feedback, `revalidatePath` for cache refresh.

But `useActionState` has a limitation: the `isPending` state lives **where you call the hook**. If your submit button is in a separate component deep in the tree, you would need to pass `isPending` down through props. There are better tools.

File 3.3.6 covers **`useFormStatus`** and **`next/form`** — read form status without props drilling and get progressive enhancement for free. Then 3.3.7 covers **`useOptimistic`** — update the UI instantly while the server works in the background.

After those two, the combined project (3.4) builds the Reviews & Ratings App — implementing everything with both Route Handlers and Server Actions.
