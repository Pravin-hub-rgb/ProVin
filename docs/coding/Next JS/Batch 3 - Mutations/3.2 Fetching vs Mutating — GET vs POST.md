# Fetching vs Mutating — GET vs POST vs PUT vs DELETE (3.2)

## Where We Left Off

In the previous topic (3.1), you learned about Route Handlers — building REST API endpoints that accept different HTTP methods. You built a comments API with GET (read all) and POST (create new). But one question likely arose: **what's the difference between GET and POST? When should you use which?**

This isn't just a Next.js concept — it's the **HTTP protocol itself**. Every web server, every API, every website follows these same rules.

## Broader Goal

Think about your phone. You do two main things:

1. **Consume** — you read texts, look at photos, scroll through feeds
2. **Produce** — you send texts, post photos, write new content

The web works exactly the same way:

- **GET** — read data (don't change anything)
- **POST** — create new data (something changes)

Let's map this out clearly.

## The Four HTTP Methods

Here are the four most common HTTP methods you'll use. Think of them like restaurant actions:

| Method | Restaurant Action | What It Does |
|--------|-------------------|--------------|
| **GET** | Read the menu | Read existing data (safe, doesn't change anything) |
| **POST** | Place a new order | Create new data |
| **PUT** | Modify your existing order | Replace existing data entirely |
| **DELETE** | Cancel your order | Remove data |

## GET vs POST — Quick Revision

You've already seen both in the previous topic. Remember — data comes from a JSON file (`lib/comments.ts`):

```tsx
// app/api/comments/route.ts
import { NextResponse } from "next/server";
import { getAllComments, addComment } from "@/lib/comments";

// GET — read all comments
export async function GET() {
  return NextResponse.json(getAllComments());
}

// POST — create a new comment
export async function POST(request: Request) {
  const body = await request.json();
  const newComment = addComment(body.text);
  return NextResponse.json(newComment, { status: 201 });
}
```

**GET** just sends data. **POST** receives data and saves it. Data comes from `lib/comments.ts` (JSON file).

## Now Let's Add PUT and DELETE

GET and POST should be clear. Now let's cover the other two — PUT (update) and DELETE (remove). First, the JavaScript array methods you'll need:

### `findIndex()` — Finding the Position

`findIndex()` returns the **index** (position) of an element in an array:

```tsx
const comments = [
  { id: 1, text: "First" },
  { id: 2, text: "Second" },
  { id: 3, text: "Third" },
];

const index = comments.findIndex((c) => c.id === 2);
console.log(index);  // 1 (second position)

const notFound = comments.findIndex((c) => c.id === 99);
console.log(notFound);  // -1 (not found)
```

`.find()` vs `.findIndex()` — `.find()` returns the element itself, `.findIndex()` returns the position. Why do we need position? Because to update or delete, we need to know **where** the element is.

### Spread Operator (`...`) — Copy and Overwrite

When updating an object, copy old properties and overwrite new ones:

```tsx
const comment = { id: 1, text: "First", createdAt: "2025-01-15" };

const updated = { ...comment, text: "Updated!" };
// { id: 1, text: "Updated!", createdAt: "2025-01-15" }
```

See — `...comment` copies all properties, then `text: "Updated!"` overwrites just that one. Without the spread operator, you'd need 3 lines.

### `splice()` — Removing Elements

To remove an element from an array:

```tsx
const fruits = ["apple", "banana", "cherry"];

fruits.splice(1, 1);  // remove 1 element starting at index 1
console.log(fruits);  // ["apple", "cherry"]
```

`splice(index, count)` — `index` = where to start, `count` = how many to remove.

## PUT — Updating a Comment (Route Handler)

Until now, `lib/comments.ts` only had read functions (`getAllComments`, `addComment`, `getCommentById`). We need an update function — `updateComment`. Same read → change → write pattern:

```ts
// lib/comments.ts — add updateComment() after addComment()
export function updateComment(id: number, text: string) {
  const comments = getAllComments();                          // 1. Read file
  const index = comments.findIndex((c) => c.id === id);       // 2. Find position

  if (index === -1) return null;                              // 3. Not found → null

  comments[index].text = text.trim();                         // 4. Update
  writeFileSync(filePath, JSON.stringify(comments, null, 2)); // 5. Write file
  return comments[index];                                     // 6. Return updated
}
```

**Notice:** All the array manipulation is in `lib/` — the route handler just calls the function:

```tsx
// app/api/comments/[id]/route.ts
import { NextResponse } from "next/server";
import { updateComment } from "@/lib/comments";

export async function PUT(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  const body = await request.json();

  // Validation — empty text not allowed
  if (!body.text || !body.text.trim()) {
    return NextResponse.json(
      { error: "Text cannot be empty" },
      { status: 400 }
    );
  }

  const updated = updateComment(Number(id), body.text);

  if (!updated) {
    return NextResponse.json({ error: "Not found" }, { status: 404 });
  }

  return NextResponse.json(updated);
}
```

The route handler parses the URL parameter (`id`), validates the body, calls `updateComment()`, and handles the response. But **all data manipulation lives in `lib/comments.ts`** — the route handler is just a thin layer that translates HTTP requests into function calls.

### Client-to-Server Mapping — Understanding PUT's Flow

Here's how the client and server connect for a PUT request:

**Client (`app/comments/[id]/page.tsx`):**
```tsx
const handleUpdate = async (id: number) => {
  const res = await fetch(`/api/comments/${id}`, {
    method: "PUT",
    body: JSON.stringify({ text: editText }),
    headers: { "Content-Type": "application/json" },
  });
};
```

**Server (`route.ts`):**
```tsx
export async function PUT(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  const body = await request.json();
}
```

**Here's how everything maps:**

```
Client                                          Server
────────────────────────────────────────────────────────────────
fetch(`/api/comments/${id}`)     →    URL is parsed → /api/comments/1
         ↓                                        ↓
params: { id: "1" }              →    comes in via { params } parameter
                                               ↓
                                       const { id } = await params
                                               ↓
                                       id = "1" (string → Number() to convert)

method: "PUT"                    →    export async function PUT()

body: JSON.stringify({...})      →    request.json() parses it
```

**Key insight:** The `id` in the URL (`/comments/1`) becomes `params.id` on the server. This is Next.js's **dynamic routing** — whatever you put in brackets (`[id]`) becomes a key in `params`.

## PUT — Editing a Comment (UI)

The route handler is built. Now we need the UI to call it. But here's an important design decision: **where should the edit UI go?**

Think about WhatsApp — when you edit a message, you don't open a separate full-screen editor. You tap and hold on that specific message, and an inline editor appears right there. The edit UI is tied to that specific item.

Same principle here — the edit UI should appear **on the same page where the item lives**. We already have a dynamic detail page: `/comments/[id]`. When a user clicks a comment, that page opens. We'll put the edit button right there.

Let's build it step by step — first add an "Edit" button to the detail page that opens a form:

```tsx
// app/comments/[id]/page.tsx
"use client";

import { useEffect, useState } from "react";

export default function CommentPage({ params }: { params: Promise<{ id: string }> }) {
  const [comment, setComment] = useState<{ id: number; text: string } | null>(null);
  const [editing, setEditing] = useState(false);   // edit mode toggle
  const [editText, setEditText] = useState("");    // form input value

  useEffect(() => {
    params.then(({ id }) => {
      const load = async () => {
        const res = await fetch(`/api/comments/${id}`);
        const data = await res.json();
        setComment(data);
        setEditText(data.text);  // pre-fill with current text
      };
      load();
    });
  }, [params]);

  if (!comment) return <p>Loading...</p>;

  return (
    <div className="p-4 border rounded max-w-md mx-auto">
      {editing ? (
        <form onSubmit={handleSubmit} className="flex flex-col gap-2">
          <input
            value={editText}
            onChange={(e) => setEditText(e.target.value)}
            className="border p-2 rounded"
          />
          <div className="flex gap-2">
            <button type="submit" className="bg-green-500 text-white px-4 py-2 rounded">
              Save
            </button>
            <button type="button" onClick={() => setEditing(false)} className="text-gray-500 text-sm">
              Cancel
            </button>
          </div>
        </form>
      ) : (
        <>
          <p className="text-lg">{comment.text}</p>
          <button
            onClick={() => setEditing(true)}
            className="mt-3 bg-blue-500 text-white px-4 py-2 rounded"
          >
            Edit
          </button>
        </>
      )}
    </div>
  );
}
```

What's new here:
1. **`editing`** — `false` shows view mode (comment + Edit button), `true` shows edit mode (form)
2. **Edit button** — clicking `setEditing(true)` opens the form
3. **`editText` pre-filled** — the input shows the current comment text so you don't edit blind
4. **`params.then`** — same pattern from the previous topic. Page loads → fetch from `/api/comments/${id}`

**Why just a boolean for editing?** Because the detail page shows only ONE comment. There's no need to track *which* item is being edited (unlike a list where multiple items might be editable). When there are multiple items, you'd need to track the `editingId`. But a single item just needs an on/off toggle.

**Test it now:** Visit `/comments/2` → click "Edit" → form appears with old text pre-filled → click "Cancel" → back to view. But the PUT request isn't wired up yet — that's the next step.

#### Step 2: Add the Actual PUT Request

Add `handleUpdate` — when the form saves, send a PUT request:

```tsx
// app/comments/[id]/page.tsx

const handleUpdate = async (e: React.FormEvent) => {
  e.preventDefault();

  const res = await fetch(`/api/comments/${comment.id}`, {
    method: "PUT",
    body: JSON.stringify({ text: editText }),
    headers: { "Content-Type": "application/json" },
  });

  const updated = await res.json();
  console.log("Updated:", updated);

  // Show new comment + close edit mode
  setComment(updated);
  setEditing(false);
};
```

And wire it to the form:

```tsx
<form onSubmit={handleUpdate} className="flex flex-col gap-2">
```

Here's the full flow: `e.preventDefault()` stops the page reload. The `id` comes from the **dynamic route page itself** — there's only one comment on this page, so `comment.id` is what we use. `method: "PUT"` triggers the PUT route handler. The response gives us the `updated` comment — `setComment(updated)` shows the new text and `setEditing(false)` closes the form.

**Important ordering gotcha:** The `if (!comment) return <p>Loading...</p>` check must come **before** defining `handleUpdate`. The `comment` state has type `{ id, text } | null` — it starts as `null`. TypeScript's control-flow narrowing works at the moment the closure is created: if you define `handleUpdate` before the null check, TypeScript still sees `comment` as nullable inside the closure → you get "Parameter 'comment' is possibly 'null'."

**Delete uses the same pattern** — the only difference: DELETE removes with `filter()` while PUT updates with `setComment(updated)`. DELETE passes no body (just URL for the id), while PUT passes a body with new data.

## DELETE — Removing a Comment (Route Handler)

PUT is done — let's add DELETE. The `lib/comments.ts` `deleteComment` function uses the same pattern but removes with `splice()`:

```ts
// lib/comments.ts — add deleteComment()
export function deleteComment(id: number) {
  const comments = getAllComments();                          // 1. Read file
  const index = comments.findIndex((c) => c.id === id);       // 2. Find position

  if (index === -1) return false;                             // 3. Not found → false

  comments.splice(index, 1);                                  // 4. Remove
  writeFileSync(filePath, JSON.stringify(comments, null, 2)); // 5. Write file
  return true;
}
```

And the route handler:

```tsx
// app/api/comments/[id]/route.ts
import { NextResponse } from "next/server";
import { deleteComment } from "@/lib/comments";

export async function DELETE(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  const deleted = deleteComment(Number(id));

  if (!deleted) {
    return NextResponse.json({ error: "Not found" }, { status: 404 });
  }

  return NextResponse.json({ message: "Deleted successfully" });
}
```

DELETE is even simpler than PUT — `deleteComment()` does everything: reads file, finds position with `findIndex()`, removes with `splice(index, 1)`, and writes back. The route just checks if it was successful and returns a message.

**Key difference with DELETE:** DELETE has no body — it just needs the `id` from the URL. So there's no `request.json()` call — just `params`.

## DELETE — Removing a Comment (UI)

The handler is built — now the UI. We'll use the `ShowComments.tsx` component from the previous topic and add a Delete button to each comment.

#### Step 1: Just Hit the Route First

First, let's just add a Delete button and hit the endpoint — we'll worry about removing from the UI after confirming the route works:

```tsx
// app/components/ShowComments.tsx
const handleDelete = async (id: number) => {
  const res = await fetch(`/api/comments/${id}`, { method: "DELETE" });
  const data = await res.json();
  console.log("Deleted:", data);
};

// ...in the map:
<button onClick={() => handleDelete(comment.id)} className="text-red-500 hover:underline text-sm">
  Delete
</button>
```

Click it → the API returns "Deleted successfully" in console. The comment **stays on screen** because we haven't updated the UI yet — but this confirms the route works.

#### Step 2: Remove from UI

Now add one line to actually remove it from the list:

```tsx
const handleDelete = async (id: number) => {
  const res = await fetch(`/api/comments/${id}`, { method: "DELETE" });
  const data = await res.json();
  console.log("Deleted:", data);

  // Remove from list
  setAllComments((prev) => prev.filter((c) => c.id !== id));
};
```

`filter()` creates a new array excluding the deleted comment.

## DELETE vs PUT — Same Pattern, Different Purpose

| | DELETE | PUT |
|---|---|---|
| `fetch()` method | `DELETE` | `PUT` |
| What removes/updates | `splice()` removes | Spread updates |
| Client update approach | `filter()` to remove | `map()` to replace |

## When to Use Which Method?

| Scenario | Method | Why? |
|----------|--------|------|
| Viewing product listing | GET | You're only reading |
| Reading a blog post | GET | You're only reading |
| Adding a comment | POST | You're creating new data |
| Submitting a form | POST | You're sending data to server |
| Updating your profile | PUT | You're replacing existing data |
| Deleting your account | DELETE | You're removing data |

**Simple rule:** Only reading → **GET**. Changing something → **POST/PUT/DELETE**.

## Status Codes — What the Server Tells You

Every response from the server includes a **status code** — a three-digit number that tells the client what happened:

| Status Code | Meaning | When |
|-------------|---------|------|
| 200 | OK | GET successful |
| 201 | Created | POST successful |
| 400 | Bad Request | Client sent invalid data |
| 404 | Not Found | Resource doesn't exist |
| 500 | Server Error | Something broke on the server |

You send these with `NextResponse.json(data, { status: code })` — the second argument is the options object.

## What It Is NOT

- **Status codes are NOT the same as HTTP methods** — methods are requests (GET, POST), status codes are responses (200, 404). Don't confuse them.
- **GET is not "always safe"** in theory — technically you could change data in a GET request. But in practice, GET should never modify data. Keep it read-only.
- **PUT is not the only way to update** — PATCH also updates but partially. PUT replaces entirely, PATCH modifies specific fields.

## In Your Own Words

<details>
<summary>Question 1: What's the difference between PUT and POST? Give a real-world example.</summary>
<p><strong>Answer:</strong> POST creates a brand-new resource (like submitting a new review), while PUT updates an existing resource (like editing your review text). After POST, you typically get back a new resource with a new ID. With PUT, you're modifying something that already has an ID.</p>
</details>

<details>
<summary>Question 2: Should you send a status code of 200 or 201 after a successful POST?</summary>
<p><strong>Answer:</strong> Use 201 (Created) after POST because a new resource was successfully created. While 200 would technically work, 201 is more precise and follows REST conventions.</p>
</details>

<details>
<summary>Question 3: Why does `params` need to be awaited in Next.js route handlers?</summary>
<p><strong>Answer:</strong> In Next.js 15, `params` is a Promise — it's resolved asynchronously. This allows Next.js to optimize rendering. The `{ params: Promise<{ id: string }> }` type makes this explicit. You must `await params` before accessing `.id`.</p>
</details>

<details>
<summary>Question 4: What's the difference between `find()` and `findIndex()`?</summary>
<p><strong>Answer:</strong> `find()` returns the element itself, while `findIndex()` returns the position (index) of the element. When you need to update or delete an item from an array, `findIndex()` is what you need — you can't splice or replace by value, you need the index.</p>
</details>
