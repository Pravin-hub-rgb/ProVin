# Server Actions — Next.js's Shortcut (3.3)

## Where We Left Off

In the previous topics (3.1 and 3.2), you learned how to build a comments system using Route Handlers — REST API endpoints that handle GET, POST, PUT, and DELETE operations. The code worked, but it was verbose. Every operation required a route file, a `fetch()` call with headers and JSON.stringify, and manual state management.

Look at what you wrote just to make a form work:

```tsx
// Route Handler — lots of boilerplate
// 1. Create route file (app/api/comments/route.ts)
// 2. Write function (POST)
// 3. Parse request body (await request.json())
// 4. Client calls it with fetch()
```

**4 steps** for every form. If you have 10 forms, you write this 10 times.

The detail page (`comments/[id]`) from the previous topic was even worse — a full Client Component with `useState`, `useEffect`, `params.then()`, `fetch()`, and a loading state. All that boilerplate just to display one comment and let the user edit it.

**Server Actions solve this — reducing all that to 1 step.**

## Broader Goal

Remember how simple forms were in plain HTML?

```html
<form action="/submit" method="POST">
  <input name="comment" />
  <button type="submit">Submit</button>
</form>
```

You just set the `action` attribute and the browser handled the rest. No JavaScript needed.

**What if your form could work that way — but call a server function directly?**

```tsx
<form action={addComment}>
  <input name="comment" />
  <button type="submit">Submit</button>
</form>
```

No `fetch()`, no API endpoint, no boilerplate. The form directly calls the server function. **This is what Server Actions give you.**

## How Server Actions Work

Server Actions are a **built-in feature** of Next.js — a form can directly call a server function.

Here's how it works under the hood: when you add `"use server"` above a function, Next.js automatically creates a hidden API endpoint (you never see it). When the form submits, Next.js routes it to the server, the function executes, and the response comes back.

The key insight: **you never write an API endpoint file.** Next.js handles that for you.

## What a Server Action Looks Like

Before we apply this to our real project, let's see the shape of a basic Server Action:

```tsx
// app/actions.ts
"use server";

export async function addComment(formData: FormData) {
  const text = formData.get("comment") as string;
  return { success: true, message: "Comment added!" };
}
```

```tsx
<form action={addComment}>
  <input name="comment" placeholder="Write a comment..." />
  <button type="submit">Submit</button>
</form>
```

Just `"use server"` directive, a function that takes `FormData`, and a form with `action`. That's it — no API routes, no `fetch()`.

The function above is just a **shape** — it doesn't actually save the comment yet. We'll connect it to our real `addComment` from `lib/comments.ts` in the next topic.

## Client-to-Server Mapping — The FormData Rule

One question you might have: **where does `formData.get("comment")` get "comment" from?**

**Client (form):**
```tsx
<input name="comment" />
```

**Server (action):**
```tsx
const text = formData.get("comment") as string;
```

**The rule is simple:** the `<input>` `name` attribute must match the string passed to `formData.get()`.

```tsx
<input name="comment" />   →  formData.get("comment")     ✅
<input name="review"  />  →  formData.get("review")      ✅
<input name="text"    />  →  formData.get("text")        ✅

<input name="comment" />   →  formData.get("text")        ❌ (names don't match!)
```

**Compare with Route Handlers:** Route Handlers receive the entire body as one object via `request.json()`. Server Actions let you extract individual fields with `formData.get("fieldName")`.

## Route Handler vs Server Actions — Same Goal, Different Paths

**Route Handler (from 3.1):**
```
Client → fetch("/api/comments", { method: "POST" }) → Route Handler → Response
```

The client knows it's making an API call. You write `fetch()`, set headers, handle JSON.stringify.

**Server Action:**
```
Client → Form action={addComment} → Next.js (automatically) → Server Function → Response
```

The client has no idea an API call is happening. Just set `action` and go — minimal boilerplate.

## Two Ways to Call a Server Action

### Method 1: Form `action` attribute (simple, causes full page reload)

```tsx
<form action={addComment}>
  <input name="comment" />
  <button type="submit">Submit</button>
</form>
```

This is the simplest — just the `action` attribute. But it causes a full page reload (standard HTML behavior).

### Method 2: Call from JavaScript (no reload, more control)

```tsx
"use client";

const handleSubmit = async (formData: FormData) => {
  const result = await addComment(formData);
  setMessage(result.message);
};

<form action={handleSubmit}>
  <input name="comment" />
  <button type="submit">Submit</button>
  <p>{message}</p>
</form>
```

Here, the `action` receives a client-side function (`handleSubmit`) that calls the server action. This gives you more control — you can show loading states, success/error messages, etc.

## Where to Define Server Actions

**Option 1: Separate file (recommended)**
```tsx
// app/actions.ts
"use server";
export async function addComment(formData: FormData) { ... }
```

**Option 2: In the page itself**
```tsx
// app/page.tsx
async function addComment(formData: FormData) {
  "use server";
  // ...
}
```

Both work, but a separate file is cleaner — separation of concerns.

## What You Can Do Inside a Server Action

Server Actions run **on the server** — so you can:
- Access the database (Prisma, Supabase)
- Read and write files
- Access environment variables
- Call third-party APIs

What you **cannot** do: access browser APIs like `localStorage` or `window`. Those only exist in the browser.

### Database Access Example

In development, we've been using in-memory storage (`let comments = [...]`), which disappears on server restart. In production, you'd use a database with an ORM like Prisma:

```ts
// Without ORM (raw SQL)
INSERT INTO comments (text) VALUES ('New comment');

// With Prisma ORM (JavaScript)
await prisma.comment.create({
  data: { text: "New comment" },
});
```

You'll learn database setup in Batch 5 — for now, just understand that Server Actions can access any server-side resource.

## Error Handling

If an error occurs in a Server Action:

```tsx
// app/actions.ts
"use server";

export async function addComment(formData: FormData) {
  const text = formData.get("comment") as string;

  if (!text) {
    return { success: false, message: "Comment text is required" };
  }

  // ... save the comment
}
```

On the client side, use `try/catch` when calling the action from JavaScript, or handle the returned state if using `useActionState` (which you'll learn in 3.3.1).

## What It Is NOT

- **Server Actions are not a replacement for REST APIs** — they only work within Next.js. If you need an API for mobile apps or third-party services, you still need Route Handlers.
- **Server Actions are not "better" than Route Handlers** — they're a convenience for specific use cases. Route Handlers give you more control.
- **Server Actions are not insecure** — they're server-side, so they're actually more secure than exposing API endpoints. But you still need to validate inputs.

## Nutshell

Server Actions are Next.js's shortcut for form submissions — a form directly calls a server function without needing an API route. Just add `"use server"` to your function, set `action` on your form, and you're done. Less boilerplate, faster development. But remember: they're Next.js-specific, not a universal solution.

## Common Mistakes

- **`"use server"` directive omitted** — without it, the function runs on the client
- **Using browser APIs in Server Actions** — `localStorage`, `window`, and `document` don't exist on the server
- **Not exporting the function** — you need `export async function`
- **Putting `"use server"` in the wrong place** — it goes at the top of the file or above a function declaration
