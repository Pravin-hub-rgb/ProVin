# Data Layer — JSON File + fs Module (3.4.3)

## Where We Left Off

In 3.4.2, we built the static UI with hardcoded reviews. But the data was embedded directly in the page — not scalable, not persistent, and not testable independently. Now we extract the data layer.

## What Is a Data Layer?

Think of a data layer as a librarian. You don't go to the shelf yourself — you ask the librarian (call a function), and they get the book (data) for you.

The data layer abstracts **where** data comes from. The page doesn't know if data is in a JSON file, a database, or fetched from an external API. It just calls `getAllReviews()` and gets an array back.

**Why this matters:** Later, if you switch from JSON files to a database, only the data layer changes. The pages stay exactly the same.

## Step 3: File Path Setup

```ts
// lib/reviews.ts
import { readFileSync, writeFileSync } from "fs";
import path from "path";

const filePath = path.join(process.cwd(), "lib", "reviews.json");
```

`readFileSync` reads the file, `writeFileSync` writes it. `process.cwd()` gives the project root directory so the path works regardless of where the code runs.

## Step 4: Read Functions

```ts
// lib/reviews.ts

// Get all reviews
export function getAllReviews(): Review[] {
  const data = readFileSync(filePath, "utf-8");
  return JSON.parse(data);
}

// Get reviews for a specific product
export function getReviewsByProduct(productId: number): Review[] {
  return getAllReviews().filter((r) => r.productId === productId);
}

// Get a single review by ID
export function getReviewById(id: number): Review | null {
  return getAllReviews().find((r) => r.id === id) || null;
}
```

## Step 5: Write Functions (Create, Update, Delete)

```ts
// lib/reviews.ts

// Create a new review
export function addReview(
  data: Omit<Review, "id" | "createdAt">
): Review | null {
  const text = data.text?.trim();
  const rating = data.rating;

  // Validation
  if (!text) return null;
  if (!rating || rating < 1 || rating > 5) return null;

  const reviews = getAllReviews();
  const newReview: Review = {
    ...data,
    id: reviews.length > 0 ? Math.max(...reviews.map((r) => r.id)) + 1 : 1,
    createdAt: new Date().toISOString().split("T")[0],
  };
  reviews.push(newReview);
  writeFileSync(filePath, JSON.stringify(reviews, null, 2));
  return newReview;
}

// Update an existing review
export function updateReview(
  id: number,
  data: { text: string; rating: number }
): Review | null {
  const reviews = getAllReviews();
  const index = reviews.findIndex((r) => r.id === id);

  if (index === -1) return null;

  const updated: Review = {
    ...reviews[index],
    ...data,
    text: data.text.trim(),
  };
  reviews[index] = updated;
  writeFileSync(filePath, JSON.stringify(reviews, null, 2));
  return updated;
}

// Delete a review
export function deleteReview(id: number): boolean {
  const reviews = getAllReviews();
  const index = reviews.findIndex((r) => r.id === id);

  if (index === -1) return false;

  reviews.splice(index, 1);
  writeFileSync(filePath, JSON.stringify(reviews, null, 2));
  return true;
}
```

### Key Patterns

**`Omit<Review, "id" | "createdAt">`** for `addReview` — the caller doesn't provide `id` or `createdAt`; those are auto-generated:
- `id` is the next sequential number based on existing IDs
- `createdAt` is today's date

**`findIndex()`** for update/delete — returns the position (index) of the element. Use `find()` to get the element itself, `findIndex()` to get its position.

**`splice(index, 1)`** for delete — removes 1 element at the given index.

**Spread operator `{ ...reviews[index], ...data }`** for update — copies existing properties, then overwrites with new data. Preserves `id`, `productId`, and `createdAt` that aren't in `data`.

### Why Validation Returns `null`

When validation fails, we return `null`. This is a convention — the caller checks `if (!result)` to handle failures. It's cleaner than throwing exceptions for expected failures (like empty input).

import path from "path";

const filePath = path.join(process.cwd(), "lib", "reviews.json");

  productId: number;
  text: string;

## Test It — Terminal Session

You can test the data layer without a browser — use the terminal with `npx tsx`:

```bash
npx tsx
```

Then import and test:

```ts
import { getAllReviews, getReviewById, addReview, updateReview, deleteReview } from "./lib/reviews";

// 1. Read all reviews
getAllReviews();
// → returns array of 4 reviews

// 2. Read a single review
getReviewById(1);
// → returns the first review

// 3. Add a new review
addReview({ productId: 1, text: "Great product!", rating: 5 });
// → returns the new review with auto-generated id and createdAt

// 4. Update a review
updateReview(1, { text: "Updated text", rating: 4 });
// → returns the updated review

// 5. Delete a review
deleteReview(4);
// → returns true (success)

// 6. Verify deletion
getAllReviews();
// → now only 3 reviews

// Exit
.exit
```

**Data persistence:** Each time you call `readFileSync`, you get the current state of the file — including any changes made by previous operations in the same session. Each `writeFileSync` immediately persists changes.

## What It Is NOT

- **The data layer is not "just for JSON files"** — when you switch to a database (like MongoDB with Prisma), the function signatures stay the same. Only the implementation changes (replace `readFileSync` with DB queries).
- **`readFileSync` is not "always the right choice"** — in production, you'd use async file reads (`readFile`) or connection pools. Synchronous reads are fine for development simplicity.
- **Validation here is not "complete security"** — server-side validation is the last defense, but you should also validate on the client for better UX.

## In Your Own Words

<details>
<summary>Question 1: Why is the data layer separated from the page components?</summary>
<p><strong>Answer:</strong> Separation of concerns. The page doesn't need to know whether data comes from a JSON file, a database, or an API. It just calls functions. When the data source changes, only the data layer file changes — all pages stay the same.</p>
</details>

<details>
<summary>Question 2: What does `Omit<Review, "id" | "createdAt">` do, and why use it?</summary>
<p><strong>Answer:</strong> It's a TypeScript utility type that creates a new type from `Review` but excludes `id` and `createdAt`. We use it for `addReview` because the caller shouldn't provide those fields — they're auto-generated. This prevents the caller from setting an ID manually, which could cause conflicts.</p>
</details>

<details>
<summary>Question 3: Why use `findIndex()` instead of `find()` for update and delete?</summary>
<p><strong>answer:</p>
<p>`find()` returns the element itself — but to update or delete, we need its position in the array. `findIndex()` returns the position (index), which we can use with `splice()` to remove or with bracket notation `reviews[index] = updated` to replace.</p>
</details>

<details>
<summary>Question 4: What's the pattern that every write function follows?</summary>
<p><strong>Answer:</strong> Every write function follows "read → modify → write": (1) Read the file with `getAllReviews()`, (2) modify the array in memory (push, splice, or replace by index), (3) write the modified array back with `writeFileSync`. This ensures we never overwrite data we haven't read.</p>
</details>
