# Route Handlers — Building Your First REST API (3.1)

## Where We Left Off

In the previous topic (3.0), we learned about the two approaches for mutating data: Route Handlers (REST API) and Server Actions (Next.js shortcut). We understood when to use each — Route Handlers for external clients and complex operations, Server Actions for simple forms in a Next.js-only app.

Now we'll build our first Route Handler — a REST API endpoint that handles GET and POST operations. This is the foundation for the entire comments project.

## Broader Goal

Remember how React apps worked before Next.js? You'd build a backend with Express or another framework, create API endpoints, and then call them from React with `fetch()`. The backend was a separate server.

Next.js changes this — **Route Handlers** let you create API endpoints directly in your Next.js app. No separate backend needed. The API lives alongside your frontend, in the same project.

By the end of this topic, you'll have:
1. A working API at `/api/comments` that can GET all comments and POST new ones
2. A form on the frontend that calls this API
3. A data layer (`lib/comments.ts`) that reads and writes to a JSON file

## The Data Layer — lib/comments.ts

Before building the API, let's create the data layer — the functions that actually read and write data. This is where all data manipulation logic lives, separate from HTTP concerns.

**File:** `lib/comments.ts`

```ts
// lib/comments.ts — Data layer (pure functions, no HTTP)
import { readFileSync, writeFileSync } from "fs";
import { join } from "path";

const filePath = join(process.cwd(), "lib", "comments.json");

// Read all comments
export function getAllComments() {
  const fileContent = readFileSync(filePath, "utf-8");
  return JSON.parse(fileContent);
}

// Read a single comment by ID
export function getCommentById(id: number) {
  const comments = getAllComments();
  return comments.find((c: { id: number; text: string }) => c.id === id) || null;
}

// Create a new comment
export function addComment(text: string) {
  const comments = getAllComments();
  const newComment = {
    id: Date.now(),  // Simple unique ID
    text,
    createdAt: new Date().toISOString(),
  };
  comments.push(newComment);
  writeFileSync(filePath, JSON.stringify(comments, null, 2));
  return newComment;
}
```

The data layer follows a simple pattern: **Read → Change → Write**. Every function reads the JSON file, manipulates the data, and writes it back. No HTTP, no `NextResponse` — just pure data operations.

## Step 1: Create the Route Handler

Route Handlers live in the `app/api/` directory. The file name becomes the URL path.

**File:** `app/api/comments/route.ts`

```ts
// app/api/comments/route.ts
import { NextResponse } from "next/server";
import { getAllComments, addComment } from "@/lib/comments";

// GET — read all comments
// Fetch all comments from /api/comments
export async function GET() {
  const comments = getAllComments();
  return NextResponse.json(comments);
}

// POST — create a new comment
// Send { text: "New comment" } to /api/comments
export async function POST(request: Request) {
  const body = await request.json();

  // Validation — don't allow empty comments
  if (!body.text || !body.text.trim()) {
    return NextResponse.json(
      { error: "Comment cannot be empty" },
      { status: 400 }
    );
  }

  const newComment = addComment(body.text);
  return NextResponse.json(newComment, { status: 201 });
}
```

### How Route Handlers Work

- `route.ts` is the special filename — Next.js recognizes it as an API route
- Each HTTP method is a separate exported function: `GET`, `POST`, `PUT`, `DELETE`
- `NextResponse.json()` sends a JSON response (like `res.json()` in Express)
- `request` is the incoming HTTP request — use `await request.json()` to read the body
- `{ status: 201 }` — status codes are passed as the second argument

## Client-to-Server Mapping — Understanding the Flow

Here's how the client and server connect:

**Client:**
```tsx
const res = await fetch("/api/comments", {
  method: "POST",
  body: JSON.stringify({ text: "Hello world" }),
  headers: { "Content-Type": "application/json" },
});
const newComment = await res.json();
```

**Server:**
```tsx
export async function POST(request: Request) {
  const body = await request.json();
  const newComment = addComment(body.text);
  return NextResponse.json(newComment, { status: 201 });
}
```

The mapping:
- `fetch("/api/comments", { method: "POST" })` → triggers the `POST` function in `route.ts`
- `body: JSON.stringify({ text })` → `await request.json()` parses it
- `res.json()` → `NextResponse.json()` sends the response

## Step 2: Wire Up the Frontend

Now let's create the comment form and list components that connect to this API.

**File:** `app/components/CommentForm.tsx`

```tsx
// app/components/CommentForm.tsx
"use client";

import { useState } from "react";

export default function CommentForm() {
  const [text, setText] = useState("");

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();

    const res = await fetch("/api/comments", {
      method: "POST",
      body: JSON.stringify({ text }),
      headers: { "Content-Type": "application/json" },
    });

    if (res.ok) {
      setText("");
      // List doesn't auto-update yet — see 3.3.2 for the fix
      console.log("Comment added!");
    }
  };

  return (
    <form onSubmit={handleSubmit} className="mb-4">
      <input
        value={text}
        onChange={(e) => setText(e.target.value)}
        placeholder="Write a comment..."
        className="border p-2 rounded mr-2"
      />
      <button type="submit" className="bg-blue-500 text-white px-4 py-2 rounded">
        Submit
      </button>
    </form>
  );
}
```

**File:** `app/components/ShowComments.tsx`

```tsx
// app/components/ShowComments.tsx
"use client";

import Link from "next/link";
import { useEffect, useState } from "react";

export default function ShowComments() {
  const [comments, setComments] = useState<{ id: number; text: string }[]>([]);

  useEffect(() => {
    const fetchComments = async () => {
      const res = await fetch("/api/comments");
      const data = await res.json();
      setComments(data);
    };
    fetchComments();
  }, []);

  return (
    <div className="p-4 border rounded">
      <h2 className="text-xl font-bold mb-4">Comments</h2>
      <ul className="space-y-2">
        {comments.map((comment) => (
          <li key={comment.id} className="border-b pb-2">
            <Link href={`/comments/${comment.id}`} className="hover:underline">
              {comment.text}
            </Link>
          </li>
        ))}
      </ul>
    </div>
  );
}
```

## What's Happening Behind the Scenes

```
Browser                        Next.js Server
───────────────────────────────────────────────────────────────
fetch("/api/comments")     →   Route Handler GET() → getAllComments()
       res.json()          ←   return NextResponse.json(comments)

fetch("/api/comments")     →   Route Handler POST() → addComment(text)
       res.json()          ←   return NextResponse.json(newComment, {status: 201})
```

Each `fetch()` call goes through the HTTP stack — through network, through Route Handler, through the response. It works, but it's a lot of code for a simple operation. We'll see a simpler approach in 3.3.

## Common Patterns in Route Handlers

### Reading Request Data

```tsx
export async function POST(request: Request) {
  // For JSON bodies
  const body = await request.json();

  // For form data (multipart/form-data)
  const formData = await request.formData();
  const text = formData.get("text");

  // For URL query params
  const { searchParams } = new URL(request.url);
  const page = searchParams.get("page");
}
```

### Dynamic Routes — params

For routes with dynamic segments (like `/api/comments/1`):

**File:** `app/api/comments/[id]/route.ts`

```tsx
export async function GET(
  request: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  const comment = getCommentById(Number(id));
  return NextResponse.json(comment);
}
```

The `[id]` in the folder name becomes `params.id`. In Next.js 15, `params` is a Promise — it must be awaited.

### Error Handling

```tsx
export async function POST(request: Request) {
  try {
    const body = await request.json();
    const comment = addComment(body.text);
    return NextResponse.json(comment, { status: 201 });
  } catch (error) {
    return NextResponse.json(
      { error: "Something went wrong" },
      { status: 500 }
    );
  }
}
```

## What It Is NOT

- **Route Handlers are not "API-only"** — they can return HTML, redirects, or any response type
- **You don't always need `request.json()`** — only if your client sends JSON. For form submissions, use `request.formData()`
- **Status codes are not "optional"** — always use 201 for created, 400 for bad request, 404 for not found
- **Route Handlers are not "legacy"** — they're still essential for REST APIs and external clients

## In Your Own Words

<details>
<summary>Question 1: What file becomes the API route, and what's the naming convention?</summary>
<p><strong>Answer:</strong> Any file named `route.ts` (or `route.js`) inside the `app/api/` directory becomes an API endpoint. The folder path becomes the URL — so `app/api/comments/route.ts` is accessible at `/api/comments`, and `app/api/comments/[id]/route.ts` is accessible at `/api/comments/1` (where `1` is dynamic).</p>
</details>

<details>
<summary>Question 2: How does the client know which HTTP method handler to hit?</summary>
<p><strong>Answer:</strong> The `method` property in the `fetch()` call determines which exported function runs. A `fetch({ method: "POST" })` triggers the `POST` function in route.ts, while a `fetch({ method: "GET" })` triggers the `GET` function. The URL determines which route file handles the request.</p>
</details>

<details>
<summary>Question 3: What's the read → change → write pattern, and why is it important?</summary>
<p><strong>Answer:</strong> Every data layer function reads the JSON file, modifies the data in memory, then writes back. This pattern is important because file operations are not atomic — if you write without reading first, you could lose existing data. Always read first, modify, then write the complete file.</p>
</details>

<details>
<summary>Question 4: Why should you delete Route Handlers when removing their operations?</summary>
<p><strong>Answer:</strong> Unused route handlers are dead code that adds confusion and potential security surface. If a POST handler exists but nothing calls it, a third-party could still hit that endpoint. Cleaning up unused routes during refactoring is a best practice — it keeps the API surface minimal and secure.</p>
</details>
