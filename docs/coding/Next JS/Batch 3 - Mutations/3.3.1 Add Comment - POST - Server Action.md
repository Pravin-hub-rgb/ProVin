## Step 1: Server Actions File Banao — `app/actions.ts`

3.3 mein dekha — Server Actions alag file mein rakhte hain, usme `"use server"` directive hota hai. Wahi file banate hain, bas ab usme **asli kaam** karenge — `lib/comments.ts` ke existing `addComment()` function ko call karenge.

**File:** `app/actions.ts`

```tsx
// app/actions.ts — NAYI FILE (3.3 ka concept, ab asli use)
"use server";

import { addComment } from "@/lib/comments";

export async function addCommentAction(formData: FormData) {
  const text = formData.get("comment") as string;

  // Validation — wahi jo route handler mein tha
  if (!text || !text.trim()) {
    return; // khali comment — kuch mat karo
  }

  // lib/comments.ts ka asli function
  addComment(text);
}
```

Dekho kya hai — ye **3.1 ke route handler ki jagah** hai. Par fark note karo:

| Route Handler (3.1 wala) | Server Action (ab wala) |
|---|---|
| `request.json()` se data milta hai | `formData.get("comment")` se data milta hai |
| `NextResponse.json()` se response jaata hai | Koi response nahi — bas function call |
| `addComment()` function call hota hai | `addComment()` function call hota hai |
| Status codes dene padte hain | Koi status code nahi |

**Notice kiya — action kuch return nahi karta.** Kyun? Kyunki jab action ko directly `action={...}` mein use karte ho, toh TypeScript usse `void` return karne ko kehta hai. Agar object return karoge (jaise `{ success, message }`), toh **ye error aata hai**:

```
Type '(formData: FormData) => Promise<{ success: ... } | { success: ... }>'
is not assignable to type 'string | ((formData: FormData) => void | Promise<void>)'
```

Isliye Step 1 mein action `void` return karta hai. Success/error message return karne ke liye humein `useActionState` chahiye — Step 4 mein aayega.

**Ek baat pehle hi bata doon** — abhi action sirf comment add karta hai. Submit karke dekho toh `comments.json` mein naya comment aa jayega, par **page pe list mein nahi dikhega** (list — `ShowComments.tsx` — abhi bhi wahi purana data dikha rahi hogi). Ye **expected hai** — mutation hone ke baad Next.js ko batana padta hai ki data badla hai. Iska pura solution do cheezein milakar aayega: **`revalidatePath`** (Step 5 mein seekhenge — cache invalidate hota hai) **+ list ka data Server Component se aana** (3.3.2 mein — tabhi naya comment list mein dikhega). Abhi bas mutation pe focus karo — JSON check karke confirm karo ki add ho raha hai.

**`addComment` kahan se aaya?** Wahi function jo 3.1 mein `lib/comments.ts` mein banaya tha — `comments.json` file se padhta hai, naya comment add karta hai, file mein likhta hai. **Data layer bilkul nahi badla** — sirf usko call karne ka tareeka badla hai. Isliye `import { addComment } from "@/lib/comments"` kiya.

**`"use server"` kyun?** 3.3 mein padha — ye batata hai ki ye function server pe run hoga. Bina iske ye function client pe bhi accessible ho jaata — aur phir `fs` import fail ho jaata. Isliye sabse upar.

**`formData.get("comment")`** — form mein jo input `name="comment"` hoga, uski value yahan milti hai. Naam match hona zaroori hai — wahi 3.3 mein padha mapping rule.

## Step 4: Feedback Wapas Lao — useActionState + Toast

Ab ek aur cheez hai jo humne Step 2 mein **gawa di** — user feedback. Step 2 ke end mein humne dekha tha: "addCommentAction ka return value kahan dikh raha hai? **Kahin nahi.**"

Socho — user form submit karta hai. Usse kya chahiye?
1. **Pending state** — button "Adding..." dikhe jab tak server kaam kar raha hai
2. **Success message** — "Comment add ho gaya!" dikhe
3. **Error message** — "Comment khali nahi ho sakta!" dikhe agar fail ho

3.1 / 3.2 mein ye sab `useState` se karte the. Server Actions ke saath React ek **built-in hook** deta hai — `useActionState` — jo pending state aur return value **dono** deta hai. Aur message dikhane ke liye **toast** use karenge — ek nayi cheez bhi seekhne ko milegi.

### useActionState — Action Ko State Se Jodo

Pehle ek simple baat clear karte hain: **`useActionState` ko `useState` ka form version samjho.**

`useState(0)` mein `0` hota hai state ki starting value. Ab imagine karo — ek state jiski value submit ke baad **apne aap badal jaye**, aur nayi value wo ho jo action server se return kare. Bas yahi hai `useActionState`:

```tsx
const [state, formAction, isPending] = useActionState(action, initialState);
```

Teeno parts — ek-ek karke:

**1. `action` pass kyun kiya?** Hook ko batana padta hai ki submit pe **kaunsa function chalana hai**. Ye wahi `addCommentAction` hai. Hook hi usko form submit pe call karega.

**2. `initialState` pass kyun kiya?** Kyunki `state` ko submit se pehle bhi ek value chahiye. Form abhi submit nahi hua — toh `state` mein kya rakhein? Wo `initialState`. Bilkul `useState(0)` ki tarah starting value. Hamara starting value hoga `{ success: false, message: "" }` — matlab "abhi kuch hua nahi". Asli value pehli submit ke baad hi aayegi.

**3. Hook teen cheezein return karta hai:**
- `state` — action ka return value. Submit se pehle `initialState`, submit ke baad action jo bhi return kare (`success` + `message`).
- `formAction` — ye wo action hai jo form mein lagana hai. Kyun ki seedha `addCommentAction` nahi lag sakta — abhi isi ka explain aayega.
- `isPending` — boolean. Action abhi server pe chal raha hai → `true`; khatam → `false`. Isi se button "Adding..." banayenge.

Ab action file mein do cheezein badalni hain taaki ye hook kaam kare.

```tsx
// app/actions.ts — UPDATED (useActionState ke liye FormState type + prevState)
"use server";

import { addComment } from "@/lib/comments";

export type FormState = {
  success: boolean;    // true ya false hoga
  message: string;     // text hoga
};

export async function addCommentAction(
  prevState: FormState,
  formData: FormData
): Promise<FormState> {
  const text = formData.get("comment") as string;

  if (!text || !text.trim()) {
    return { success: false, message: "Comment khali nahi ho sakta!" };
  }

  addComment(text);

  return { success: true, message: "Comment add ho gaya!" };
}
```

Dekho kya badla:

**Action ab kuch return karta hai** — Step 1 mein `void` return karta tha, ab `FormState` object return karta hai. Kyun? Kyunki ab action ka result `state` banna hai — jo return karo, wahi `state` ke andar jayega. Step 1 ka wo TS error yaad hai? Jab action object return karta tha aur seedha `action={...}` pe lagaya, toh error aata tha. `useActionState` usi problem ka ilaaj hai — return value ab wahi jaati hai jahan use karni hai (`state` mein), na ki form ko confuse karte hue.

**`FormState` type** — bas batata hai ki return ka shape kya hai: `success` (boolean) + `message` (string). Isi shape ka `initialState` bhi hoga — **dono ka shape match hona chahiye**, warna TypeScript error. (Yahan log aksar phas jaate hain — type mismatch ka error mile toh pehle initialState aur return type dono dekho.)

**`prevState: FormState`** — pehla argument. `useActionState` ka rule hai: hook action ko `(prevState, formData)` form mein call karta hai. Hum isko abhi **use nahi karte** — add action ko purana state nahi chahiye — par **iske bina** hook action ko call hi nahi kar sakta. Ye signature ka mandatory hissa hai, bas likhna padta hai.

**`: Promise<FormState>`** — return type declaration. Hook isi se jaanta hai ki action ka response kaise dikhega. `Promise` isliye — server action async hai.

### `formAction` — Adapter Jo Form Ko Action Se Milata Hai

Ab wo sawaal jo naturally aata hai: **form mein `action={formAction}` kyun, seedha `action={addCommentAction}` kyun nahi?**

Wajah ek simple **argument mismatch** hai. `<form action={...}>` ka rule hai — submit pe browser us function ko **sirf 1 argument** ke saath call karta hai: `formData`. Par ab hamara action 2 arguments maangta hai:

```
(formData)              ← form (action={fn}) ko jo milta hai
(prevState, formData)   ← addCommentAction ko jo chahiye
```

Seedha `action={addCommentAction}` likhoge toh submit pe browser sirf `formData` dega — `prevState` kahan se aayega? Action galat tarike se call hoga.

**`formAction` yehi mismatch fix karta hai.** `useActionState` ne tumhare action ko **wrap** kiya hai. Jab form submit hota hai:
1. `formAction` form se `formData` leta hai
2. khud `prevState` bhar ke `addCommentAction(prevState, formData)` call karta hai
3. action ka return value `state` mein store kar deta hai

**`formAction` = tumhara action, lekin hook-friendly version.** Hook ka poora point yahi hai — action ka result kisi state mein pakadna. Bina hook ke wo result kahan jaata? Kahin nahi — Step 2 ka wahi sawaal.

Yaad rakhne ka sabse simple tareeka:

> **`action={addCommentAction}` = action bhaaga, result gum. `action={formAction}` = action bhaga, result state mein aaya.**

### Toast — Message Dikhane Ka Modern Tarika

Action ka return value form tak `useActionState` se aata hai. Par woh message **user ko kaisa dikhega?** Toast se — wo chhote popup notifications jo screen ke kone mein dikhte hain (bottom-right, top-right, etc.) aur khud fade ho jaate hain.

Hum **`sonner`** library use karenge — ek halki, modern toast library jo React 19 ke saath perfect chalti hai. Setup:

1. Install karo: `bun add sonner`
2. Layout mein `<Toaster />` laga do — ye toast display karta hai:

```tsx
// app/layout.tsx — UPDATED (Toaster add)
import { Toaster } from "sonner";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        {children}
        <Toaster position="bottom-right" />
      </body>
    </html>
  );
}
```

`<Toaster />` ek provider hai — jahan bhi `toast.success()` / `toast.error()` call hoga, wahan notification dikhti hai. Layout mein ek baar lagao, poori app mein kaam karta hai.

### Form Mein useActionState + Toast Lagao

Ab `CommentForm.tsx` mein teen kaam karte hain — ek-ek karke, phir poora jodenge.

**Kaam 1 — initialState + hook call:**

```tsx
const initialState: FormState = {
  success: false,     // Abhi kuch hua nahi
  message: "",        // Abhi message nahi hai
};

const [state, formAction, isPending] = useActionState(
  addCommentAction,
  initialState
);
```

`initialState` humne `FormState` type se banaya — submit se pehle `state` yahi hai. `addCommentAction` batata hai kaunsa action chalna hai. Ab teeno cheezein ready: `state` (result yahan aayega), `formAction` (adapter jo form mein lagayenge), `isPending` (loading ke liye).

**Kaam 2 — result ko toast mein dikhana:**

```tsx
useEffect(() => {
  if (state.message) {
    if (state.success) toast.success(state.message);
    else toast.error(state.message);
  }
}, [state]);
```

Submit ke baad `state` action ka return value ban jaata hai — `{ success: true, message: "Comment add ho gaya!" }` ya error wala. Ye `useEffect` watch karta hai: jab bhi `state` badle, agar `message` hai toh dikhao — `success: true` → green `toast.success`, warna red `toast.error`.

**`useEffect` mein toast kyun?** `state.message` ko render ke andar bhi dikha sakte the (`{state.message && <p>...}`) — par toast ek **side-effect** hai (notification dikhana). Side-effects render ke andar nahi chahiye — isliye `useEffect` mein. Plus toast khud fade ho jaata hai — inline message ko manually hatana padta. **`[state]` dependency** kyun? Sirf jab `state` badle tabhi toast fire ho — har render pe nahi.

**Kaam 3 — form + button:**

```tsx
<form action={formAction} className="mb-4">
  <input
    name="comment"
    placeholder="Apna comment likho..."
    className="border p-2 rounded mr-2"
  />
  <button
    type="submit"
    disabled={isPending}
    className="bg-blue-500 text-white px-4 py-2 rounded disabled:bg-gray-400"
  >
    {isPending ? "Adding..." : "Submit"}
  </button>
</form>
```

- `action={formAction}` — wahi adapter. Form submit → hook `addCommentAction` chalaata hai → result `state` mein. (Seedha `addCommentAction` nahi — wo mismatch wala problem hai, upar samjha.)
- `disabled={isPending}` — jab action chal raha hai, button kaam nahi karega (double submit nahi hoga).
- `{isPending ? "Adding..." : "Submit"}` — loading pe label badal jaata hai. Yehi `isPending` ka use hai.

**Poora component — teeno kaam milakar:**

```tsx
// app/components/CommentForm.tsx — UPDATED (useActionState + sonner toast)
"use client";

import { useEffect, useActionState } from "react";
import { toast } from "sonner";
import { addCommentAction, FormState } from "../actions";

const initialState: FormState = {
  success: false,     // Abhi kuch hua nahi
  message: "",        // Abhi message nahi hai
};

export default function CommentForm() {
  const [state, formAction, isPending] = useActionState(
    addCommentAction,
    initialState
  );

  useEffect(() => {
    if (state.message) {
      if (state.success) toast.success(state.message);
      else toast.error(state.message);
    }
  }, [state]);

  return (
    <form action={formAction} className="mb-4">
      <input
        name="comment"
        placeholder="Apna comment likho..."
        className="border p-2 rounded mr-2"
      />
      <button
        type="submit"
        disabled={isPending}
        className="bg-blue-500 text-white px-4 py-2 rounded disabled:bg-gray-400"
      >
        {isPending ? "Adding..." : "Submit"}
      </button>
    </form>
  );
}
```

**Server Action ka return type aur `initialState` ka shape same hona chahiye** — warna TypeScript error aayega. `useState` ki tarah, state ka type ek hi hai — chahe initial ho ya action ka return.

### Flow

```
1. User "Submit" click karta hai
         ↓
2. isPending = true → Button "Adding..." + disabled
         ↓
3. Server pe addCommentAction chalta hai (prevState, formData ke saath)
         ↓
4. Server response bhejta hai → { success: true, message: "Comment add ho gaya!" }
         ↓
5. useActionState → state update hota hai → useEffect trigger hota hai
         ↓
6. toast.success("Comment add ho gaya!") → green popup dikhta hai
         ↓
7. isPending = false → Button wapas "Submit"
```

Notice kiya? **User ab exactly jaanta hai ki kya ho raha hai** — loading, success, error. Yehi feedback 3.1 ke `useState` version mein tha, phir Step 2 mein gayab ho gaya, aur ab **isi file mein turant wapas aa gaya** — kisi aur chapter ka wait nahi.

**`useFormState` kyun nahi?** Purani React versions mein `useFormState` (`react-dom` se) use hota tha — wo ab **deprecated** hai. React 19 mein iska naam badal kar `useActionState` (`react` se) hua, aur isme `isPending` bhi extra mila. Naya naam yaad rakho — **`useActionState`**.

> **⚠️ Deprecation Warning (React 19 / Next.js 16)**
> - **`useFormState`** — `react-dom` se — ab **deprecated**. React 19 mein removed/deprecated ho chuka hai; naye code mein error ya deprecation warning dega.
> - **`useActionState`** — `react` se — **naya naam**, wahi kaam + `isPending` extra.
> - `useFormStatus` (`react-dom` se) abhi bhi **valid hai** — ye deprecated nahi hai. Sirf iska use tab karo jab button form ke andar deep ho aur `isPending` ko props se pass karna na chaho. Simple forms mein `useActionState` ka `isPending` hi kaafi hai.
> - Rule of thumb: koi bhi form action state chahiye → hamesha **`useActionState`** use karo.

### Toast vs Inline Message — Kab Kya?

| Tarika | Kaisa dikhta hai | Kab use karein |
|--------|------------------|----------------|
| Inline message (`<p>`) | Form ke andar text | Simple, ek jagah ka message, koi library nahi |
| Toast (`sonner`) | Screen kone mein popup | Global notification, auto-dismiss, modern UX |

Humein toast isliye — same pattern delete/edit (3.3.3 / 3.3.4) aur 3.4 wale combined app mein bhi reuse kar sakte hain.

## Step 5: Data Refresh — Purana Data Dikhta Hai Toh?

Ab wo problem solve karte hain jo Step 1 mein dikhi thi — **mutation ke baad page purana kyun dikhata hai?**

Action chal gaya, `comments.json` mein comment add ho gaya, par UI update nahi hua. Kyun? Kyunki mutation ke baad Next.js ko khud nahi pata ki page ka data purana ho gaya hai. Batana padta hai — **revalidation.**

Kyun kabhi purana data dikhta hai? Jab Next.js data ko **cache** karta hai (2.3 mein seekha tha — build time pe ek baar). Cache mein purana data hai toh page re-render hone pe bhi purana hi dikhega. Isko fix karta hai `revalidatePath` / `revalidateTag` — dono `next/cache` se.

### revalidatePath — Ek Path Ka Cache Hatao

`revalidatePath(path)` — specified path ka cache invalidate karta hai. Server Action ke andar, mutation ke baad:

```tsx
// app/actions.ts — UPDATED (ab revalidatePath add kiya)
"use server";

import { revalidatePath } from "next/cache";
import { addComment } from "@/lib/comments";

export type FormState = {
  success: boolean;
  message: string;
};

export async function addCommentAction(
  prevState: FormState,
  formData: FormData
): Promise<FormState> {
  const text = formData.get("comment") as string;

  if (!text || !text.trim()) {
    return { success: false, message: "Comment khali nahi ho sakta!" };
  }

  addComment(text);

  // Cache invalidate karo — seedha comment list wale page ka
  revalidatePath("/");

  return { success: true, message: "Comment add ho gaya!" };
}
```

**Flow:** User comment add → Server pe save → `revalidatePath("/")` call → Next.js wo path ka cache hata deta hai → Page dobara render hota hai.

**Ek catch:** `revalidatePath` Server Components ko dobara render karta hai. Abhi hamari list (`ShowComments`) client side **khud fetch** karti hai (`useEffect([])`) — isliye revalidatePath lagane pe bhi naya comment list mein **nahi dikhega**. Wo dikhega **3.3.2** mein — jab list ka data `page.tsx` (Server Component) se aayega. Tab `revalidatePath` sahi se kaam karega (wahi 3.1 mein router.refresh wala point tha).

### revalidateTag — Saare Pages Ka Cache Hatao

`revalidateTag(tag)` — ek specific tag ke saare cached responses hata deta hai. Ye tab kaam aata hai jab `fetch()` mein tag lagate ho:

```tsx
// Next.js extended fetch — tag ke saath
const res = await fetch("https://api.example.com/comments", {
  next: { tags: ["comments"] },  // Next.js specific option
});
```

Jab baad mein `revalidateTag("comments")` call karte ho, toh Next.js sabhi `fetch()` calls ko dhoondhta hai jinhe "comments" tag diya gaya hai — unka cache hata deta hai.

**Example:**
- `/comments` page pe `fetch()` hai with tag `"comments"`
- `/dashboard` page pe bhi `fetch()` hai with tag `"comments"`
- Tumne `revalidateTag("comments")` call kiya
- **Dono pages ka cache hat gaya!**

Agar sirf `revalidatePath("/comments")` karte, toh sirf `/comments` ka cache hota. `revalidateTag` se saare pages jo same data use karte hain, unka bhi.

### revalidatePath vs revalidateTag — Kab Kya?

| Function | Kab use karein |
|----------|----------------|
| `revalidatePath("/")` | Sirf ek specific page ka data refresh karna ho |
| `revalidateTag("comments")` | Saare pages jo ye data use karte hain, unka refresh karna ho |

**Simple rule:** Ek page hai → `revalidatePath`. Kayi pages hain jo same data use karte hain → `revalidateTag`.

### `.bind()` Bhi Kara Hoga — Ye Kya Hai?

Form mein `action={deleteComment}` likh sakte ho — par agar function ko **arguments** bhi bhejne ho, toh `.bind()` use hota hai:

```tsx
// Simple action - koi argument nahi
<form action={addComment}>

// Action with argument - .bind() use karo
<form action={deleteComment.bind(null, c.id)}>
```

`bind()` function ka **naya version** banata hai jisme arguments pehle se set ho. Delete step (3.3.3) mein iska use apna dikhega — hidden input wale pattern ke saath bhi.

**Yahan se aage ke saare mutation actions mein revalidatePath lagayenge** — delete (3.3.3) aur update (3.3.4) mein bhi wahi pattern chalega, chahe data cache ho ya direct file se aaye. `revalidateTag` wala case (cached `fetch()` data) combined project (3.4.x) mein aayega — wahan multiple pages ka cache ek saath clear hoga.

## Kya Badla? — Ab Tak Ka Summary

| | 3.1 / 3.2 (Route Handler) | Ab (Server Action) |
|---|---|---|
| **Server code** | `app/api/comments/route.ts` POST | `app/actions.ts` `addCommentAction` |
| **Client code** | `fetch("/api/comments", { method: "POST", ... })` | `<form action={formAction}>` + `useActionState` |
| **Feedback** | `useState` se manual pending/message | `useActionState` (`isPending`) + `sonner` toast |
| **Data format** | JSON string travel | Seedha function arguments |
| **Refresh** | Manual reload (3.1) | Mutation ke baad `revalidatePath` |

**Boilerplate kya hata:** route handler ka POST function (server), `fetch()` + `method` + `headers` + `JSON.stringify` (client), `request.json()` (server), manual `useState` feedback. Ye sab replace hua — `action={formAction}` + do hooks.

1. Server Action ko `lib/comments.ts` ka existing `addComment` function call karna pada — kyunki data layer wahi hai. Route Handler usi set-up pe kya extra karta tha?

<details>

Server Action seedha function call karta hai — data layer se direct. Actually HTTP layer hat jaati hai jab sirf Next.js app hi client hai.

</details>

2. `name="comment"` aur `formData.get("comment")` ka kya connection hai?

<details>
<summary>Sample Jawab</summary>

Form ke input ka `name` attribute wahi string hota hai jo server action mein `formData.get()` ko di jaati hai. `name="comment"` input ki value `formData.get("comment")` ke through nikalta hai. Naam dono jagah match hona chahiye — warna `null` milta hai.

</details>

3. Humne route handler ka POST function delete kyon kiya?

<details>
<summary>Sample Jawab</summary>

Kyunki ab form seedha server action ko use karta hai — `fetch("/api/comments")` kahin nahi hai. Jo code koi use nahi karta, wo dead weight hai. Refactor ka hissa hi hai ki one-by-one unused cheezein hatate jao.

</details>

4. `action={addCommentAction}` form ko kaise mutate karta hai?

<details>
<summary>Sample Jawab</summary>

Browser form submit karta hai → Next.js usko ek server action call mein convert karta hai → `addCommentAction()` server pe run hota hai → naya comment JSON file mein save ho jaata hai. Client ko pata tak nahi chalta ki "API call" ho rahi hai — wo sochta hai form component directly server se baat kar raha hai.

</details>

5. `useActionState` kya return karta hai? `action={addCommentAction}` se kya farak hai?

<details>
<summary>Sample Jawab</summary>

`useActionState` teen cheezein return karta hai: `state` (action ka return value), `formAction` (form action), `isPending` (loading state). Direct `action={addCommentAction}` mein action ko `void` return karna hota hai aur koi message/pending state nahi milta. `useActionState` se action return value de sakta hai aur `isPending` se loading button milta hai.

</details>

6. `useActionState` ko action mein `prevState` parameter kyun chahiye?

<details>
<summary>Sample Jawab</summary>

`useActionState` action ko `(prevState, formData)` form mein call karta hai — purana state (ya `initialState`) automatically pass hota hai. `prevState` se naya return value banata hai jo form ko wapas milta hai. Bina `prevState` param ke action `useActionState` ke saath kaam nahi karega.

</details>

7. `revalidatePath("/")` aur `revalidateTag("comments")` mein kya fark hai?

<details>
<summary>Sample Jawab</summary>

`revalidatePath("/")` sirf us specific path ka cache hata hai. `revalidateTag("comments")` saare pages jo "comments" tag use karte hain, unka cache hata deta hai. Ek page → path, kayi pages → tag.

</details>

## What It Is NOT

**Server Action = "route handler replace karta hai" nahi.** Sirf specific form submissions ke liye shortcut hai. Agar external client ho (mobile app, third party), toh route handler abhi bhi chahiye — 3.3.5 ke end mein detail.

**Server Action = "always better" nahi.** Boilerplate kam karta hai, par control bhi kam deta hai. Debug karna (network tab dekho) thoda mushkil ho jaata hai kyunki request charon taraf SPREAD lagta hai.

**`action={...}` = "fetch ka replace" nahi.** Ye sirf forms ke liye hai. Agar kisi button se (bina form ke) server data mutate karna ho, toh bhi form wrap karte hain — hidden input ke saath. Ye delete wale step mein dikhega.

**`useActionState` = "automatic error handling" nahi.** Ye sirf return value + pending deta hai. Error handle (jaise khali comment ka check) tumhe action ke andar khud likhna hai.

**Toast = "form ka hissa" nahi.** Toast ek global notification system hai — layout mein `<Toaster />` lagao aur kahin se bhi `toast.success()/toast.error()` call karo. Form inline message se independent hai.

**Revalidation = "real-time updates" nahi.** Revalidation tab hota hai jab mutation hota hai (form submit). Real-time ke liye WebSockets ya polling use karo.
