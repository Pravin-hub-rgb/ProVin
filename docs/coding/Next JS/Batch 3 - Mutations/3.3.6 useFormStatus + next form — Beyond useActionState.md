# useFormStatus + next/form — Beyond useActionState (3.3.6)

## Where We Left Off

In 3.3.5 we finished the Server Actions refactor: `"use server"` directives, `useActionState` for pending/error states, `revalidatePath` for cache refresh, and a clean Server Component → Client Component split.

The pattern works, but it has a structural limitation. Look at the comment form from 3.3.1:

```tsx
export default function CommentForm() {
  const [state, formAction, isPending] = useActionState(addCommentAction, { message: "" });

  return (
    <form action={formAction}>
      <input {...register("comment")} />
      <button type="submit" disabled={isPending}>  // ← isPending is right here, no problem
        {isPending ? "Adding..." : "Add Comment"}
      </button>
    </form>
  );
}
```

`isPending` is in the same component that renders the button — no issue. But what if your submit button lives in a **separate component** — maybe it's in a shared `<SubmitButton>` used across 10 different forms? You would need to pass `isPending` down through props. That is props drilling.

## The Problem: Props Drilling for Form State

Imagine this structure:

```tsx
// A shared submit button used by multiple forms
function SubmitButton({ isPending }: { isPending: boolean }) {
  return (
    <button type="submit" disabled={isPending}>
      {isPending ? "Saving..." : "Save"}
    </button>
  );
}

// Every form must thread isPending down
function CommentForm() {
  const [state, formAction, isPending] = useActionState(addCommentAction, { message: "" });

  return (
    <form action={formAction}>
      <input name="comment" />
      <SubmitButton isPending={isPending} />  // ← props drilling!
    </form>
  );
}

// And the review form must do the same
function ReviewForm() {
  const [state, formAction, isPending] = useActionState(addReviewAction, { message: "" });

  return (
    <form action={formAction}>
      <textarea name="review" />
      <SubmitButton isPending={isPending} />  // ← again!
    </form>
  );
}
```

Every form has to remember to pass `isPending` to `SubmitButton`. If you add a third form and forget the prop, the button never shows a loading state.

## `useFormStatus` — Read Form State Without Props

React's `useFormStatus` hook **reads the status of the nearest parent form** automatically — no props needed:

```tsx
// components/SubmitButton.tsx — reusable across any form
'use client';

import { useFormStatus } from 'react';

export default function SubmitButton({ children }: { children: React.ReactNode }) {
  const { pending, data, action, method } = useFormStatus();

  return (
    <button type="submit" disabled={pending}>
      {pending ? "Saving..." : children}
    </button>
  );
}
```

Now any form can use it without threading props:

```tsx
// app/comments/page.tsx
function CommentForm() {
  const [state, formAction] = useActionState(addCommentAction, { message: "" });

  return (
    <form action={formAction}>
      <input name="comment" />
      <SubmitButton>Add Comment</SubmitButton>  // ← no isPending prop needed!
    </form>
  );
}
```

What `useFormStatus` gives you:

| Return value | Type | Use case |
|---|---|---|
| `pending` | `boolean` | Disable button while form submits |
| `data` | `FormData \| null` | Show what's being submitted |
| `action` | `string \| function` | Read the form's action |
| `method` | `string` | "GET" or "POST" |

> **Remember:** `useFormStatus` only works in components that are rendered **inside** a `<form>`. If there is no parent form, it returns `pending: false`.

## `next/form` — Progressive Enhancement for Server Actions

Plain HTML `<form action={formAction}>` works, but if JavaScript fails to load, the user gets a full page reload with no feedback. Next.js ships a `<Form>` component from `next/form` that integrates with Next.js navigation:

```tsx
import { Form } from 'next/form';

export default function CommentForm() {
  const [state, formAction, isPending] = useActionState(addCommentAction, { message: "" });

  return (
    <Form action={formAction}>
      <input name="comment" />
      <SubmitButton>Add Comment</SubmitButton>
    </Form>
  );
}
```

The difference between `<Form>` and `<form>`:

| | `<form>` (HTML) | `<Form>` (next/form) |
|---|---|---|
| JS fails to load | Still works — full page reload | Still works — falls back to `<form>` behavior |
| JS loads | Full page reload | Client-side navigation, no reload |
| Server Action call | Works | Works — same `action` prop |
| URL updates | On reload | Via `pushState` (if configured) |

For a Server Action form, `<Form>` gives you the best of both: progressive enhancement (works without JS) + client-side navigation (smooth SPA feel when JS loads).

## When to Reach for Each

| Situation | Tool |
|---|---|
| Submit button in a deeply nested component | `useFormStatus` (no props drilling) |
| Form needs to work without JavaScript | `next/form` `<Form>` |
| Simple form, button is co-located with `useActionState` | Plain `<form action={formAction}>` + `useActionState` (as you learned in 3.3.1) |
| Need to react to form state from a non-button component | `useFormStatus` in a custom hook |

## Common Mistakes

- ❌ **Using `useFormStatus` outside a form** — returns `pending: false` always. It must be inside a `<form>` tree.
- ❌ **Forgetting `'use client'` on the component using the hook** — `useFormStatus` is a React hook, so the component must be a client component.
- ❌ **Mixing `useFormStatus` and `useActionState` for the same `pending` state** — they read the same form, so using both is redundant. Pick one.

## What It Is NOT

- **`useFormStatus` is not `useActionState`.** `useActionState` gives you the action's **return value** (errors, messages). `useFormStatus` gives you the form's **submission state** (pending, data, method). Different concerns.
- **It is not React 18's `useFormState`.** In React 19, `useFormState` was renamed to `useActionState`. `useFormStatus` is a separate hook — use it to read the nearest form's submission state from anywhere inside it.

## In Your Own Words

1. How does `useFormStatus` find the right form if your button is in a separate component?

<details>
<summary>Sample Answer</summary>

**Answer:** `useFormStatus` reads the **nearest ancestor form** — React tracks which form currently contains the component calling the hook. It doesn't matter how deep the component is nested; as long as it is somewhere inside a `<form>`, it gets that form's status.

</details>

2. What extra does `next/form`'s `<Form>` give you over plain `<form action={...}>`?

<details>
<summary>Sample Answer</summary>

**Answer:** Progressive enhancement — if JavaScript fails, it degrades to a normal HTML form submission (full page reload). When JavaScript loads, it intercepts the submission and does client-side navigation instead. The `action` prop works the same way either way (it still calls your Server Action).

</details>

3. Can a single `<Form>` have both `useActionState` on the parent AND `useFormStatus` on a child button?

<details>
<summary>Sample Answer</summary>

**Answer:** Yes — but it is redundant for the `pending` state. `useActionState` gives the parent the action's return value (errors/messages). `useFormStatus` gives the child the form's pending state. They read different things. However, if you only need `pending`, using both means the child gets it from `useFormStatus` and you don't need to pass `isPending` as a prop anymore — that is the actual win.

</details>

- `useActionState` → get the action's return value (errors, messages)
- `useFormStatus` → get form pending state without props drilling
- `next/form` → progressive enhancement for Server Action forms
- `useOptimistic` → update UI instantly, reconcile on server response
