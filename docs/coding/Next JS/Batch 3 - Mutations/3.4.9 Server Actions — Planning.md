# Server Actions — Planning & Overview (3.4.9)

## Where We Left Off

In 3.4.1–3.4.8, we built the **Route Handler version** of the Reviews & Ratings App — a complete CRUD app with separate API routes and axios calls from the client. It works, but it has a lot of boilerplate.

Now we'll build the **Server Actions version** — the exact same features, but using Server Actions instead of Route Handlers. Before diving in, let's plan what changes.

## The Problem: Too Much Boilerplate

Route Handler version requires 5 things for every mutation:

1. **Route file** — `app/api/reviews/route.ts` with GET/POST/PUT/DELETE functions
2. **Client axios call** — `axios.post()`, `axios.put()`, `axios.delete()` with full URLs
3. **Manual pending state** — `useState(false)`, `setPending(true)` before call, `setPending(false)` in `finally`
4. **Manual error handling** — `try/catch` for every axios call
5. **Manual page refresh** — `window.location.reload()` after every mutation

**Server Actions eliminate all 5.** Let's see how each maps:

| Route Handler Version | Server Actions Version |
|----------------------|----------------------|
| `axios.post("/api/reviews", data)` | `action={addReviewAction}` on the form |
| `useState` for pending | `isPending` from `useActionState` |
| `useState` for messages | `state.message` from `useActionState` |
| `window.location.reload()` | `revalidatePath("/reviews")` in the action |
| Route file (`/api/reviews/route.ts`) | `app/actions.ts` with functions only |
| `try/catch` + `if (!res.ok)` | Return `{ success: false, message: "error" }` from action |

## The New Project Structure

```
app/
  actions.ts                    ← Server Actions (all mutations)
  reviews/
    page.tsx                    ← Server Component (list + form)
    [id]/
      page.tsx                  ← Server Component (detail + edit)
  components/
    ReviewListServer.tsx        ← Server Component (review list)
    ReviewFormServer.tsx        ← Client Component (add form)
    DeleteButtonServer.tsx      ← Client Component (delete button)
    EditReviewForm.tsx          ← Client Component (edit form)
lib/
  reviews.ts                    ← Data layer (unchanged!)
  reviews.json                  ← Data (unchanged!)
```

**Notice:** `app/api/` is gone. The Server Actions file (`actions.ts`) replaces all four route files.

## Server Actions — The Key Pattern

Every Server Action follows this structure:

```tsx
// Server Action
export async function myAction(
  prevState: FormState,
  formData: FormData
): Promise<FormState> {
  const value = formData.get("fieldName");  // Extract data from form
  // validation...
  libFunction(value);                        // Call data layer
  revalidatePath("/route");                  // Refresh affected pages
  return { success: true, message: "..." };  // Return result
}
```

```tsx
// Client Component
const [state, formAction, isPending] = useActionState(myAction, initialState);

<form action={formAction}>
  <input name="fieldName" />
  <button disabled={isPending}>{isPending ? "Loading..." : "Submit"}</button>
</form>
```

**The flow:**
1. Form has `action={formAction}` — not `onSubmit={handler}`
2. Form fields use `name` (not `value` + `onChange`)
3. `useActionState` wraps the action, providing `state`, `formAction`, and `isPending`
4. The action runs on the server with `formData` as argument
5. Return value becomes `state` on the client
6. `revalidatePath` triggers a fresh render

## What Changes When Moving to Server Actions?

1. **No API routes** — The action file (`actions.ts`) replaces all route handlers
2. **Uncontrolled forms** — Forms use `name` attributes and `defaultValue`, not `value` + `onChange`
3. **One pattern everywhere** — All mutations use the same structure: `useActionState` + `formAction` + `isPending` + `revalidatePath`
4. **Server reads, action writes** — Server Components read data directly; Server Actions write data

## In Your Own Words

<details>
<summary>Question 1: What are the 5 things eliminated by Server Actions?</summary>
<p><strong>Answer:</strong> Route files, axios calls, manual pending state, manual error handling, and manual page refresh. Instead: action function, `action={formAction}`, `isPending` from hook, return-based errors, and `revalidatePath` inside the action.</p>
</details>

<details>
<summary>Question 2: What's the core difference between `<form onSubmit={handler}>` and `<form action={serverAction}>`?</summary>
<p><strong>Answer:</strong> `onSubmit` calls a client-side handler you write. `action` directly triggers a server function — Next.js handles the network request automatically. No axios, no fetch, no manual promise management.</p>
</details>

<details>
<summary>Question 3: What role does `useActionState` play?</summary>
<p><strong>Answer:</strong> It connects a Server Action to React state. It returns the action's return value as `state`, provides a wrapped `formAction` for the form's `action` attribute, and tracks `isPending` during execution. It also handles the `(prevState, formData)` calling convention.</p>
</details>

<details>
<summary>Question 4: What is the read → write split with Server Actions?</summary>
<p><strong>Answer:</strong> Server Components handle reads (they call `getReviewsByProduct()` directly, since they run on the server and can access `fs`). Server Actions handle writes (they run form data through the data layer's create/update/delete functions). The data layer (`lib/reviews.ts`) stays unchanged.</p>
</details>
