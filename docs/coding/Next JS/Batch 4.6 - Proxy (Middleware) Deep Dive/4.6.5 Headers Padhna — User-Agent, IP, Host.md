4.6.4 mein URL padhna seekha — `pathname` se user kahan ja raha hai. Ab **headers** — request ke saath aane wali extra information. Courier analogy se shuru karte hain: parcel ka **body** andar ka samaan hai (data), aur **label** (sender, receiver, "Fragile", "Urgent") woh information hai jo parcel ke baare mein batati hai — bina andar dekhe. Headers wahi hain — request ka data hone se pehle hi uske baare mein batate hain.

---

## Headers Kya Hote Hain

Jab browser server se kuch maangta hai, request ke saath **key-value pairs** ki ek list jaati hai — headers:

```
User-Agent: Mozilla/5.0 (iPhone; ...) Mobile Safari
Host: localhost:3000
Accept: text/html
Cookie: session=abc123
```

Har request mein yeh aate hain (browser khud bhejta hai, hum likhte nahi). Proxy inhe **padh** sakta hai — aur yahi se bahut saari cheezein pata chalti hai: user ka device, IP, browser, language...

Proxy mein read karte hain `request.headers.get("name")` se:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const userAgent = request.headers.get("user-agent")
  console.log("User agent:", userAgent)
  return NextResponse.next()
}
```

`headers.get("user-agent")` — header ka naam do, value milti hai. Missing header pe `null` aata hai (4.6.4 ke `searchParams.get` jaisa hi).

---

## Step 1 — Device Detection (User-Agent)

Sabse common use: **user ka device**. Browser `User-Agent` header mein batata hai ki kaunsa browser/device hai. Mobile detection:

```ts
export function proxy(request: NextRequest) {
  const userAgent = request.headers.get("user-agent")

  if (userAgent?.includes("Mobile")) {
    console.log("Mobile device se request aa rahi hai")
  }

  return NextResponse.next()
}
```

`.includes("Mobile")` — string method — "kya string ke andar yeh text hai?" — `true`/`false`. `userAgent?.includes(...)` — optional chaining (`?.`) — agar `userAgent` null ho (header missing), toh `.includes` call ki jagah `undefined` — crash nahi. (4.1 mein optional chaining seekha tha — yahan sahi use case.)

**Test:** Phone browser se open karo → "Mobile device" log. Desktop se → kuch nahi.

**Use case socho:** mobile pe alag page design bhejna ho (aajkal responsive se kaam chalta hai — par yahi technique purane m-dot sites mein use hoti thi, aur aaj bhi device-specific features ke liye).

---

## Step 2 — IP Padhna (X-Forwarded-For)

Dusra kaam ka header: **`x-forwarded-for`** — request kis IP se aa rahi hai.

> **Thoda concept:** Proxy/v1 structure mein browser seedha app server pe request nahi bhejta — beech mein **load balancer / CDN** hota hai. Server ko request to uss beech wale machine se aati hai — asli user ka IP kahan? Usse `x-forwarded-for` header mein daal ke aage bheja jata hai.

```ts
export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  console.log("IP:", ip)
  return NextResponse.next()
}
```

`?? "unknown"` — nullish coalescing (4.5.4 wala) — header missing pe crash nahi, `"unknown"` fallback.

**Test karo (curl se spoof karke):**

```bash
curl -H "X-Forwarded-For: 49.36.10.5" http://localhost:3000/
```

Terminal: `IP: 49.36.10.5`. Dev mein localhost se aati request pe `::ffff:127.0.0.1` jaisi values bhi aayengi (IPv6-mapped IPv4) — dono "localhost" hain.

**Yeh IP hi aage ka base hai:** 4.6.13 (rate limiting — "is IP se kitni requests?") aur 4.6.14 (geo blocking — "yeh IP kahan hai?").

---

## Step 3 — Host Aur Baaki Headers

`.get("host")` — request kis domain pe aa rahi hai:

```ts
const host = request.headers.get("host")
console.log("Host:", host) // → "localhost:3000"
```

Host ka use: multiple domains ek hi app pe ho toh alag content (jo bhi logic chahiye). Baaki headers bhi `.get()` se padhe ja sakte hain — rule ek hi hai.

---

## What It Is NOT

- **Headers read karne se data modify nahi hota** — `headers.get` sirf padhta hai. Response mein headers add karna (4.6.10) alag cheez hai.
- **`x-forwarded-for` ka value hamesha ek IP nahi hota** — kuch setups mein comma-separated list aati hai (`1.2.3.4, 5.6.7.8` — har hop ka IP). **Aur important: yeh header client spoof kar sakta hai** (curl mein humne khud daala!). Production mein trusted proxy/load balancer ise overwrite karta hai. Learning ke liye fine — par jaan lo ki raw header pe 100% bharosa security nahi hai.
- **User-Agent bhi spoofable hai** — device detection "best effort" hai, hard security rule nahi.

## Common Mistakes

- **`?.` bhoolna** — `userAgent.includes(...)` pe header missing ho toh crash. `userAgent?.includes(...)` ya pehle null-check.
- **IP raw use karna** — 4.6.13 mein dekhenge: rate limiting ke liye IP ka normalization + spoofing ka dhyan rakhna padta hai.
- **Header names ka case** — `.get("User-Agent")` aur `.get("user-agent")` dono chalta hai (headers case-insensitive), par convention lowercase hai.
- **Missing header pe `null` ignore karna** — `searchParams` jaisa hi rule: result ko fallback do ya check karo.

## Nutshell

`request.headers.get("name")` — request ka label padhna. User-Agent → device detection (`includes("Mobile")`), `x-forwarded-for` → IP (`?? "unknown"`), host → domain. In dono pe hi rate limiting aur geo blocking banege — spoofable hain, isliye production me trusted proxies se.

4. `?? "unknown"` kyu — headers ke context mein kya guarantee deta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Header missing hone pe `get` returns `null` — bina fallback ke `ip` variable null ho sakta tha aur aage (logging, rate limit) null values se errors. `?? "unknown"` nullish coalescing: null/undefined pe default value deta hai — ab `ip` hamesha string hai, kabhi null nahi. Proxy mein har request pe code chalta hai — har edge case (missing header) handle karna padta hai.

</details>

5. User-Agent se device detection — kya yeh "hard rule" hai ya "best effort"? Kyun?

Device detection ka use UX optimization ke liye hai (alag layout/features), security ke liye nahi. Headers ki spoofability ka dhyan rakhte hue decisions lena — yahi production ka mindset hai.
