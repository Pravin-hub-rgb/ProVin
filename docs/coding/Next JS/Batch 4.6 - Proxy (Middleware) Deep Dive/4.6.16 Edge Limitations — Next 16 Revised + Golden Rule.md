4.6.15 mein concept + bada correction mila: Next 16 mein proxy Node.js pe chalti hai — fs jaise built-ins ab kaam karte hain. Ab isse kya matlab: **4.6.16 mein purane middleware ke "known failures" ko check karenge** (jo ab hua), aur asli golden rules — **jo ab bhi apply hote hain** (kyunki capability badalne se responsibility nahi badli). Yahan ek cheez aur clear hogi jo series ke liye important hai: proxy mein kya **kabhi** nahi karna chahiye.

## Purane Middleware (≤15) Ke Known Edge Failures — Ab Kya Hua?

**Pehle (middleware.ts + Edge default) mein yeh sab error deta tha:**

**1. `fs` — file system**

```ts
import { readFileSync } from "fs"   // ❌ Edge pe error

// Module not found: Can't resolve 'fs'
// ya — Edge Runtime does not support Node.js built-in modules
```

**Ab (proxy.ts + Node default):** ✅ **chalta hai** — humne Next 16.3 mein verify kiya — `readFileSync` se file read karke log aaya. (4.6.13 ke `requestCounts` wale in-memory pattern mein file-persistence bhi add kar sakte the technically — par zaroori nahi, concept yahi hai.)

**2. Prisma / databases**

```ts
import { PrismaClient } from "@prisma/client"   // ❌ Edge pe error

// PrismaClient is unable to run in this environment...
// edge runtime does not support Node.js built-in modules
```

**Ab:** technically proxy mein database query ab chal sakti hai (Node runtime) — **par karna nahi chahiye** (golden rule niche). Database ka kaam Server Components/actions ka hai.

**3. bcrypt (native) vs bcryptjs**

```ts
import bcrypt from "bcrypt"   // ❌ Edge pe — native crypto support nahi

// The edge runtime does not support Node.js 'crypto' module
// ✅ Alternative: bcryptjs (pure JS) — chal jaata tha
```

**Ab:** bcrypt (native) ab technically chalega — par yahi yaad rakho: **password verification proxy mein nahi karni** (golden rule). Auth 4.6.12 mein hi decide ho chuka hai — layout/actions.

**4. `jsonwebtoken` vs `jose`** — JWT verify wala pattern (Batch 4 ka JWT concept yaad karo — signed token): `jsonwebtoken` Edge pe nahi chalta tha, `jose` (Edge-compatible) chalta tha:

```ts
import { jwtVerify } from "jose"   // Edge-compatible JWT verification

const { payload } = await jwtVerify(token, secret)
```

Ab jose ka use zaroori nahi (Node hai), par yeh pattern aata hona chahiye — tumhare DukaanOS mein bhi use ho sakta hai.

## Golden Rule — Proxy Mein Kya Karna Chahiye (Ab Bhi Wahi)

Next 16 ka runtime change **capability** badalta hai, **design principles** nahi. Proxy mein:

**✅ Karna chahiye (light, per-request infra):**
- Routing (redirect/rewrite — 4.6.8/4.6.9)
- Cookie/header padhna (4.6.5/4.6.6)
- Request info log (4.6.11)
- Rate limiting (4.6.13) / geo checks (4.6.14)
- A/B routing, maintenance page

**❌ Kabhi nahi (golden rule):**
- **Heavy computation / database queries** — har request pe chalta hai — slow = har page slow. Database = components/actions.
- **Verified auth/security decisions** — 4.6.12 wala why-not (CVE-2025-29927 + spoofable). Auth = layout `auth()`.
- **Secrets/environment access jahan browser dekhe** — proxy code server-side hai, par iska matlab "cautious" — data har request pe jaata hai.
- **Large data processing** — response body handle karna proxy ka kaam nahi (log/track light data).

**Ek line golden rule:** *proxy mein sirf cookie/header padho + simple condition + redirect/rewrite. Heavy logic → API routes / Server Components.*

## ⚠️ `export const runtime = "nodejs"` — Purana Escape Hatch, Ab Throw

Tumhare pehle ke notes (5.2) mein tha: "proxy Edge pe hai, Node chahiye toh `export const runtime = "nodejs"` lagao." — **Next 16 mein yeh bhi galat hai:**

- Middleware (≤15) ke liye `runtime: "edge"` / `runtime: "nodejs"` config ka hissa tha (nodejs stable 15.5+)
- Next 16 proxy mein runtime option **removed** — `runtime: "edge"` toh build error deta hai (4.6.15 mein verify kiya), `runtime: "nodejs"` bhi ab irrelevant/unrecognized hai

Proxy **hamesha Node.js hai** — runtime specify karna hi nahi padta. Purane notes ke hisaab se code likhoge toh error/confusion.

---

## What It Is NOT

- **"Ab sab kuch proxy mein karo" nahi** — capability ≠ recommendation. fs technically chalta hai — par "proxy light" ka rule performance + architecture hai (4.6.15).
- **Database "proxy mein try" mat karna** — woh chalta bhi hai to har request pe connection + query — pooling issues, latency, aur security boundary bhi nahi hai. Components/actions.
- **Golden rule "Edge ke wajah se" nahi** — woh rule 4.6.15 wale reasons se hai (har-request + boundary). Edge ke hone/na hone se independent.
- **jose/bcryptjs "ab unnecessary" nahi** — chahiye toh use karo; bas yeh jaan lo ki unka **edge-compat reason** ab proxy pe valid nahi.

## Common Mistakes

- **Purane notes se `runtime` export copy karna** — Next 16 build error (verified). Delete karo.
- **Proxy mein database call lagana** — "Node hai ab toh chalega" — galat: har request pe DB = performance disaster. Data layers components mein.
- **Proxy ko security boundary banana** — 4.6.12 wala complete logic (CVE) — ab bhi valid, runtime change se kuch nahi badla.
- **Heavy sync work (loop/parse) proxy mein** — har request block hoga — har page slow.

## Nutshell

Purane edge-failures (fs/Prisma/bcrypt) Next 16 proxy mein technically solve — Node default (verified). Par golden rule ab bhi: proxy = light (cookie/header + condition + redirect/rewrite). Heavy logic/database = components/actions. Auth proxy mein nahi (CVE). `runtime` export removed — throw karta hai.
