# Manual Auth v1 — Protect + Logout

## Where We Left Off

5.1 built the manual auth pieces end to end: `bcryptjs` hashing, the `users.json` data layer, a register action, a login action, and a session cookie set with `httpOnly`, `secure`, and `sameSite`. A cookie that is set but never **read** is just bytes in the browser. This file completes the loop: a `getSession()` helper that reads the cookie back and resolves it to a user, a **protected layout** that redirects anyone without a session, and a **logout** that deletes the cookie.

## Step 1 — The Session Reader: `getSession()`

The session pattern from 5.0, implemented: cookie ID → server-side record → user.

### Stage 1 — Read the cookie ID

Cookie access in Next.js comes through `cookies()` from `next/headers`. In Next 15+ that function is **async**, so it must be awaited.

```ts
// app/lib/session.ts
import { cookies } from "next/headers";

export async function getSession() {
  const cookieStore = await cookies();
  const sessionId = cookieStore.get("sessionId")?.value;
  if (!sessionId) return null;
  // userId lookup next
}
```

- `cookieStore.get("sessionId")` returns the cookie object or `undefined`; `?.value` extracts the ID safely, yielding `undefined` if absent.
- `if (!sessionId) return null` — no cookie means logged out. `null` is the contract: a caller can branch on "user or no user" clearly.

### Stage 2 — Resolve the ID to a user

The ID is a string (cookies are strings) but `users.json` stores `id` as a number. Convert before lookup:

```ts
import { getUserById } from "./users";

export async function getSession() {
  const cookieStore = await cookies();
  const sessionId = cookieStore.get("sessionId")?.value;
  if (!sessionId) return null;

  const userId = Number(sessionId);
  return getUserById(userId);
}
```

`getUserById` returns the matching user or `null`. Note the full type: the function is async (because of `await cookies()`), so callers always `await getSession()`.

That is the full helper. It lives in `lib/session.ts` so every server component shares one correct implementation instead of re-parsing cookies.

## Step 2 — Protecting a Route with a Layout

Protect `/secret`. A route-group layout (`secret/layout.tsx`) is the right place — it guards every page under that folder in one spot:

```tsx
// app/secret/layout.tsx
import { redirect } from "next/navigation";
import { getSession } from "../lib/session";

export default async function SecretLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const user = await getSession();
  if (!user) {
    redirect("/login");
  }
  return <>{children}</>;
}
```

This is the core protection pattern, stated once: read the session, redirect if absent. Putting it in a **layout** (not the page) means any future child of `/secret` inherits the guard automatically — forget once on one file, and that file is exposed.

Why server-side and not client-side: a check inside a Client Component runs after the page renders — the protected content has already streamed to the browser. Server-side (in the layout), the redirect fires before render, so protected data never reaches an unauthenticated client.

## Step 3 — Logout: delete the cookie

Logout is the inverse of login's cookie set. Delete the cookie, then redirect:

```ts
// app/actions.ts — add after loginAction
export async function logoutAction() {
  const cookieStore = await cookies();
  cookieStore.delete("sessionId");
  redirect("/login");
}
```

Deleting the cookie is what makes logout real. Redirecting alone leaves the cookie in the browser — the next `/secret` visit still looks logged in. After deletion, the next request has no `sessionId`, and `getSession()` returns `null`.

## Step 4 — Showing the Logged-in State

A page that uses the session, so the whole cycle is visible:

```tsx
// app/secret/page.tsx
import { getSession } from "../lib/session";
import { logoutAction } from "../actions";

export default async function SecretPage() {
  const user = await getSession();

  return (
    <main>
      <h1>Secret Page</h1>
      <p>Logged in as: {user?.email ?? "guest"}</p>
      <form action={logoutAction}>
        <button type="submit">Logout</button>
      </form>
    </main>
  );
}
```

This closes the loop end to end, using only the manual primitives — no library.

## Test — Full Cycle

1. Visit `/secret` without logging in → redirected to `/login`.
2. Register an account → login → redirected back to `/secret`.
3. `/secret` shows `Logged in as: pravin@example.com` (from the session record).
4. Click Logout → redirected to `/login`; `/secret` redirects again.

Build output also confirms the dynamic nature: `/secret` renders as **ƒ (Dynamic)** because it reads a cookie, so it can't be prerendered. Session-guarded routes are dynamic by nature.

## What It Is NOT

- **`getSession()` returning `null` is not an error.** It is the normal "logged out" signal. Every caller is expected to branch on it — a layout redirects, a page shows public content. Treating absence as an exception forces try/catch everywhere.
- **A layout guard and a page guard are not equivalent.** The layout protects its entire subtree once; a page-level guard must be remembered on each page and is easy to skip on the next one.
- **Deleting the cookie is what logs the user out.** The `redirect("/login")` is just the UX.

## Common Mistakes

- **Guarding pages but not layouts.** Each new page under a protected area needs its own check and is easy to forget. Guard once at the layout.
- **Forgetting `Number(sessionId)`.** Cookies are strings; the user `id` is a number. Without conversion, `find((u) => u.id === "1")` never matches.
- **Checking sessions client-side.** A `useEffect` check renders the page first — protected data and a flash of content leak to the client. Server-side guard redirects before render.
- **Logout without deleting the cookie.** The redirect is cosmetic; the next `/secret` still sees the cookie and treats the user as logged in.
- **Awaiting `auth()`/`getSession()` without an async context.** Both are async; forgetting to make the component async breaks.

## Nutshell

`getSession()` lives in `lib/session.ts`: it reads the `sessionId` cookie, converts the string to a number, and looks up the user — returning `null` when there is no session. Protection lives in a **layout**: `await getSession()` then `if (!user) redirect("/login")`, so every child is guarded, server-side, before render. Logout is a Server Action that **deletes** the cookie then redirects. Manual auth is now complete from register through session, protection, and logout.

## In Your Own Words

<details>
<summary>1. Why does `getSession()` return `null` instead of throwing when there is no session?</summary>

**Sample Answer:** Being logged out is a normal, expected state — not an error. Returning `null` lets each caller decide what "no session" means: a protected layout redirects, a public page shows a guest view, an action returns a 401. Throwing would force try/catch at every call site and frame a routine condition as exceptional.

</details>

<details>
<summary>2. Why protect via a layout rather than each page?</summary>

**Sample Answer:** A layout wraps every page beneath it in that folder. One guard, all children. Guarding per-page means remembering to add the same check to each file, and forgetting once exposes that page. Layout-first protection is "default-on": a new protected page is protected the moment it is added.

</details>

<details>
<summary>3. Why must the session check run server-side, not in a Client Component?</summary>

**Sample Answer:** Client-side checks run after the page renders — protected content has already streamed to the browser by the time a `useEffect` fires a redirect. Server-side guards run during rendering, before any response body is sent, so protected data never reaches an unauthenticated client. Security decisions must precede the response.

</details>

<details>
<summary>4. What does logout actually do, and why is deleting the cookie the essential part?</summary>

**Sample Answer:** Logout deletes the session cookie and redirects to login. Deleting is essential: without it, the browser still holds the `sessionId`, and the next request to a protected route reads it and considers the user logged in. The redirect is only the user-facing part.

</details>

<details>
<summary>5. Why is `/secret` marked dynamic (ƒ) and not statically prerendered?</summary>

**Sample Answer:** It reads a cookie, whose value differs per request. Static rendering caches one output for everyone; a per-user session can't be cached. Next.js marks such routes as dynamic so each request is rendered with its own session — the price of per-user data.

</details>
