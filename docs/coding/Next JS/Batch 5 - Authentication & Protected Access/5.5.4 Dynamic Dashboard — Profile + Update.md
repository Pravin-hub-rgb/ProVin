# Dynamic Dashboard — Profile + Update

## Where We Left Off

In 5.5.3 the auth scaffold was in place: login works, routes are protected, and the navbar reflects the real user. But the dashboard and profile still rendered static "Pravin" data for whoever ever signs in. Now we bring in the real data sources from the 5.5.1 plan: **identity from the session** (name, email, avatar — GitHub's data) and **bio from `profiles.json`** (app-side data), plus the **bio update** flow using Batch 3's Server Action pattern.

## Step 1 — Data Layer: `profiles.json` + `profiles.ts`

The second data source from 5.5.1: where the bio is stored. Following the file-based data layer pattern. Building it stage by stage — read first, then write.

### Stage 1 — Read: `getProfileByEmail`

**THINK:** The data layer's first job is to find a user's bio by their email. `find()` with a `?? null` fallback — the 4.2/4.3 pattern.

**CODE:**

```ts
// app/lib/profiles.ts
import { readFileSync } from "fs";
import path from "path";

const filePath = path.join(process.cwd(), "app", "lib", "profiles.json");

export type Profile = {
  email: string;
  bio: string;
};

export function getProfileByEmail(email: string): Profile | null {
  const data = readFileSync(filePath, "utf-8");
  const profiles: Profile[] = JSON.parse(data);
  return profiles.find((p) => p.email === email) ?? null;
}
```

**TEST:** Add one record to `profiles.json` and call it — it returns. A missing email returns `null`.

### Stage 2 — Write: `saveProfile` (Upsert)

**THINK:** Now the bio needs to persist. One function that does both: insert if the record doesn't exist, update if it does. Check with `findIndex`.

**CONCEPT:** The name `saveProfile` signals an *upsert* — find the record's index in the array. Index `-1` (not found) → `push` (insert). Found → `profiles[index] = updated` (update). One operation covers both insert and update.

**CODE** — full current file (new parts marked `// NEW`):

```ts
// app/lib/profiles.ts
import { readFileSync, writeFileSync } from "fs";   // NEW: writeFileSync added
import path from "path";

const filePath = path.join(process.cwd(), "app", "lib", "profiles.json");

export type Profile = {
  email: string;
  bio: string;
};

export function getProfileByEmail(email: string): Profile | null {
  const data = readFileSync(filePath, "utf-8");
  const profiles: Profile[] = JSON.parse(data);
  return profiles.find((p) => p.email === email) ?? null;
}

// NEW: add this function
export function saveProfile(email: string, bio: string): Profile {
  const data = readFileSync(filePath, "utf-8");
  const profiles: Profile[] = JSON.parse(data);
  const index = profiles.findIndex((p) => p.email === email);

  const updated: Profile = { email, bio };

  if (index === -1) {
    profiles.push(updated);
  } else {
    profiles[index] = updated;
  }

  writeFileSync(filePath, JSON.stringify(profiles, null, 2));
  return updated;
}
```

**TEST:** First save → a record appears in `profiles.json` (email + bio). Second save → it updates, no duplicate line. `getProfileByEmail` on a missing email → `null`.

**Why email, not a user ID?** Auth.js does issue a user id (`session.user.id` — surfaced by extending the JWT type back in 5.4.2). But email is the key common to both sources here — it comes from the session *and* it's the key in our file. A fully-typed id-based lookup (the 5.4.2 JWT-extend pattern) would add type safety, but email works immediately. For a learning project, email is the right call.

## Step 2 — Server Action: `updateProfileAction`

**File:** `app/actions.ts` (update — replace the old `logoutAction` from 4.3 with this)

```ts
// app/actions.ts — replace logoutAction with:
"use server";

import { redirect } from "next/navigation";
import { revalidatePath } from "next/cache";
import { auth } from "@/auth";
import { saveProfile } from "./lib/profiles";

export type ProfileState = {
  message?: string;
  error?: string;
};

export async function updateProfileAction(
  prevState: ProfileState,
  formData: FormData
): Promise<ProfileState> {
  const session = await auth();
  if (!session?.user?.email) {
    redirect("/login");
  }

  const bio = formData.get("bio");
  if (typeof bio !== "string") {
    return { error: "Bio is invalid" };
  }
  if (bio.length > 200) {
    return { error: "Bio must be 200 characters or fewer" };
  }

  saveProfile(session.user.email, bio.trim());
  revalidatePath("/profile");

  return { message: "Profile saved!" };
}
```

Line by line:

- **`const session = await auth()`** — a Server Action runs on the server, so `auth()` is available (the 5.4.2 server-side pattern). The session provides **identity** — which bio to save — without asking the form.
- **`if (!session?.user?.email) redirect("/login")`** — defense in depth: even though the form lives on a protected page, the action must not run without a session. A form can be spoofed; the action stands guard.
- **`formData.get("bio")` + type + length check** — Batch 3's validation pattern. The 200-char cap mirrors the form's `maxLength` (double layer).
- **`saveProfile(session.user.email, bio.trim())`** — note the email comes from the **session**, not the form. A user cannot submit another person's email and overwrite their bio.
- **`revalidatePath("/profile")`** — after a save, the page's cached server data is stale; this flags it for a fresh render (Batch 3).
- **Return state** — `message` / `error` for `useActionState` to surface to the UI.

## Step 3 — Dashboard: From Hardcoded to Dynamic

**File:** `app/(protected)/dashboard/page.tsx` (update — replace the static values)

```tsx
// app/(protected)/dashboard/page.tsx
import { auth } from "@/auth";
import { getProfileByEmail } from "../../lib/profiles";
import Link from "next/link";

export default async function DashboardPage() {
  const session = await auth();
  const email = session?.user?.email ?? "";
  const profile = getProfileByEmail(email);

  return (
    <main>
      <h1>Dashboard</h1>
      {session?.user?.image && (
        <img src={session.user.image} width={80} height={80} alt="avatar" />
      )}
      <p>Name: {session?.user?.name}</p>
      <p>Email: {email}</p>
      <p>Bio: {profile?.bio ?? "No bio yet — go update it on the profile page"}</p>
      <Link href="/profile">Edit Profile</Link>
    </main>
  );
}
```

What changed versus the static 5.5.2 dashboard:

| Static (5.5.2) | Dynamic (now) | Source |
|---|---|---|
| `<img src="https://github.com/pravin.png">` | `session.user.image` | GitHub session |
| `Name: Pravin` | `session?.user?.name` | GitHub session |
| `Email: pravin@example.com` | `session?.user?.email` | GitHub session |
| `Bio: ...` | `profile?.bio ?? fallback` | `profiles.json` |

- **`profile?.bio ?? "No bio yet..."`** — nullish coalescing: if no record exists in the file (the user never saved), show a helpful fallback. `profile?.bio` guards against a missing record; `??` supplies the default.
- **`session?.user?.image && <img .../>`** — the avatar URL is GitHub-sourced (that's the whole OAuth advantage); `&&` skips rendering when no image exists.
- The avatar comes from GitHub's avatar URL carried in the session — this is why using a provider is handy for display data.

## Step 4 — Profile Page: Dynamic Data + Client Form

**File:** `app/(protected)/profile/page.tsx` (update)

```tsx
// app/(protected)/profile/page.tsx
import { auth } from "@/auth";
import { getProfileByEmail } from "../../lib/profiles";
import ProfileForm from "../../components/ProfileForm";

export default async function ProfilePage() {
  const session = await auth();
  const email = session?.user?.email ?? "";
  const profile = getProfileByEmail(email);

  return (
    <main>
      <h1>Profile</h1>
      <p>Email: {email}</p>
      <p>Name: {session?.user?.name}</p>
      <ProfileForm initialBio={profile?.bio ?? ""} />
    </main>
  );
}
```

Server Component: gathers data (email + bio) and hands the form an **initial value**. The form itself is a Client Component — it needs interactivity to show pending/error/success states (the Batch 3 reason).

**File:** `app/components/ProfileForm.tsx` (new — following the LoginForm pattern from 5.4.2 and the form pattern from 5.5.2)

```tsx
// app/components/ProfileForm.tsx
"use client";

import { useActionState } from "react";
import { updateProfileAction, ProfileState } from "../actions";

const initialState: ProfileState = {};

export default function ProfileForm({ initialBio }: { initialBio: string }) {
  const [state, formAction, isPending] = useActionState(
    updateProfileAction,
    initialState
  );

  return (
    <form action={formAction}>
      <label>
        Bio
        <textarea
          name="bio"
          defaultValue={initialBio}
          rows={4}
          maxLength={200}
        />
      </label>
      <button type="submit" disabled={isPending}>
        {isPending ? "Saving..." : "Save"}
      </button>
      {state.message && <p style={{ color: "green" }}>{state.message}</p>}
      {state.error && <p style={{ color: "red" }}>{state.error}</p>}
    </form>
  );
}
```

- **`useActionState` + `isPending`** — Batch 3's three-state handling (pending / error / success): the button reads "Saving…" and is disabled while the action runs.
- **`defaultValue={initialBio}`** — render once with the saved bio from the server. This is an *uncontrolled* input (not `value` + `onChange`): there's no reason to mirror every keystroke into React state when `FormData` reads the final value at submit.
- **`maxLength={200}`** — client-side cap that mirrors the action's server-side check: defense in depth.
- **`state.message` green / `state.error` red** — distinct colors so success and error are unambiguous.

## Test — The Full Loop

Run `npm run dev` and exercise this sequence:

1. Sign in → `/dashboard` — should show the GitHub name, email, avatar, and either the saved bio or the "No bio yet" fallback.
2. Navigate to `/profile`, type a bio, and click Save.
3. Return to `/dashboard` — the bio should now appear (revalidate + `getProfileByEmail` read the updated file).
4. Return to `/profile` — the textarea should pre-fill with the saved bio (the initial value).
5. Clear the bio, save, and verify the empty/fallback path renders.
6. Sign out → attempt `/dashboard` → expect redirect back to `/login`.

**Upsert check** (run once if testing the data layer): first save inserts a record into `profiles.json`; a second save updates the same record (no duplicate line); `getProfileByEmail` on a never-saved email returns `null`.

## What It Is NOT

- **Bio equals identity.** Bio lives in the file; name/email/avatar live in the session. We never persist session identity into our own store — GitHub is always the fresh source. That boundary is the architecture: auth-provided data vs. app-owned data.
- **`saveProfile` as insert-only.** It is an upsert: first save inserts, later saves update the same record.
- **Form values always matching server state.** `defaultValue` only seeds the field on the initial render. If two tabs are open and one saves, the other still shows its pre-save value — `revalidatePath` doesn't force a re-render of an already-loaded client view.

## Common Mistakes

- **Reading email from the form.** Never do `formData.get("email")` and feed it to `saveProfile` — the request body is user-controlled and forgeable. The email must come from `auth()`. Rule: **identity from session, data from form.**
- **Skipping the optional chain on profile data.** Writing `profile.bio` directly crashes when the record is absent. Chain both: `profile?.bio` and a `??` fallback.
- **Omitting `auth()` inside the action.** The form sits on a protected page, but requests can be spoofed; the action must re-verify the session itself.
- **Mismatched return types from the action.** The action must return `Promise<ProfileState>`, and that must line up with what `useActionState` expects — otherwise TypeScript complains.
- **Forgetting `revalidatePath`.** The file updates but the page shows stale cached data until revalidation.

## Nutshell

Dynamic phase: create `profiles.json` (empty array) and `profiles.ts` with `getProfileByEmail` (read) and `saveProfile` (upsert) → add `updateProfileAction` in `actions.ts` (email from session, bio from form, validated, saved, `revalidatePath`, state returned) → make the dashboard pull name/email/avatar from `auth()` and bio from the file → make the profile page a server-rendered data fetch feeding a client `ProfileForm` (`useActionState`, `defaultValue`, triple-state) → remove the obsolete `/secret` demo. Every user now sees their own dashboard and can persist a bio.

## In Your Own Words

<details>
<summary>1. Why does the action read email from the session, and what's the risk of reading it from the form?</summary>

**Sample Answer:** The session is server-verified — whatever email is in it is the authenticated user's. The form body is user-controlled and forgeable: an attacker could submit `email: "someone.else@example.com"` and overwrite that person's bio. Reading email from `auth()` means the email can't be tampered with, because it's derived from the verified session cookie, not from request input. Rule: identity from the session, data from the form.

</details>

<details>
<summary>2. Why is `saveProfile` called an upsert, and how does one function handle both insert and update?</summary>

**Sample Answer:** It handles two cases with a single function: `findIndex` locates the record by email in the array. A result of `-1` (not found) triggers `profiles.push(updated)` — a new record is inserted. A found index triggers `profiles[index] = updated` — the existing record is overwritten. So the first save inserts, and every save after updates the same record. No separate insert/update APIs needed.

</details>

<details>
<summary>3. On the dashboard, what do `?.` and `??` each do in `profile?.bio ?? "No bio yet..."`?</summary>

**Sample Answer:** `profile?.bio` is optional chaining — the user may have no record in the file yet, so `profile` itself can be `null`; without `?.`, accessing `.bio` throws. The `?.` safely yields `undefined` instead. `??` is nullish coalescing — it steps in when the left side is `null` or `undefined` and supplies the fallback string. So `?.` prevents a crash, and `??` supplies the default display value.

</details>

<details>
<summary>4. Why does the form use `defaultValue` (uncontrolled) instead of `value` (controlled)?</summary>

**Sample Answer:** The form doesn't need to mirror every keystroke into React state — the only value that matters is the one read at submit via `FormData`. `defaultValue` seeds the field once from the server's `initialBio` and then the browser owns the input's state. Going controlled (`value` + `onChange`) would add a state setter and handler for no benefit, and it introduces the complexity of keeping controlled state and server data in sync. `defaultValue` is the right, simple choice for "load once, edit freely."

</details>

<details>
<summary>5. How does saving the bio update the dashboard, given the data lives in a file?</summary>

**Sample Answer:** The action writes to the file via `saveProfile`, then calls `revalidatePath("/profile")`, which tells Next.js the profile route's cached server-rendered output is stale. On the next navigation (or a manual back/refresh), the profile's server component re-runs, calls `getProfileByEmail` again, and reads the freshly written file. The dashboard works the same way — it also calls `getProfileByEmail`, so it picks up the new bio whenever it re-renders after revalidation. The shared data layer + revalidation is what keeps both views consistent.

</details>
