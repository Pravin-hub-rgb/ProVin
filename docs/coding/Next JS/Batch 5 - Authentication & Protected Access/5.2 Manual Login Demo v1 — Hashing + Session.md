## Step 1: Password Hashing — Password Ka Kya Hota Hai

### Concept — Plaintext Kyon Galat Hai

Soch ek app jisme passwords seedhe save hote hain (`password: "super-secret-123"`). Ab wahan **data breach** ho jata hai — hacker ko users ki file mil jaati hai. Uske paas ab **har user ka actual password** hai. Aur dikkat yeh hai ki log ek hi password har jagah use karte hain — toh hacker woh password unke Gmail pe bhi try kar sakta hai. Ek breach, sab jagah talaash.

Solution ka naam hai **hashing.** Hash ek **one-way function** hai — isme password se ek jumble string ban jaati hai, par us jumble se wapas password nahi ban sakta. Toh agar breach ho bhi jaye, hacker ko sirf jumble strings milti hain — **woh useless hain** agar password strong hai.

Ab ek chhota problem — agar do log same password use karein (`"password123"`), toh unke hashes bhi same honge. Hacker yeh pattern dekh ke anjaam laga sakta hai ("yeh dono accounts ka password same hai"). Iske liye **salt** hota hai — har user ke liye ek random string hash se pehle mila di jaati hai. Same password, different salt → different hash. Aur precomputed tables se bachne ke liye bhi (yeh rainbow-table attack hota hai — hacker pehle se popular passwords ke hashes bana ke rakh leta hai aur match karta hai; salt se woh table bekar ho jaati hai).

### Library — `bcryptjs`

Hash banane ke liye **bcryptjs** use karenge — sabse popular password hashing library. `bcryptjs` (pure JavaScript version) isliye chunenge kyunki isme native compilation nahi hoti — kisi bhi system pe turant chal jaati hai. (`bcrypt` naam ki doosri library bhi hai jisme C code compile hota hai — isliye woh kabhi-kabhi setup mein problem deti hai.)

Install karo:

```bash
npm install bcryptjs
```

### Syntax — Do Functions

bcryptjs ka poora kaam do functions mein hai:

```ts
bcrypt.hash(password, saltRounds)      // hash banata hai (async)
bcrypt.compare(password, hash)         // check karta hai: password hash se match karta hai? (async)
```

`saltRounds` ek number hai jo batata hai hash banana **kitna mehenga** hai — 12 ka matlab hash banana intentionally slow hai (lagbhag 250ms). Slow isliye chahiye kyunki agar hacker ko hashes mil bhi jayein, toh brute-force (har password try karna) bhi utna slow hoga. **Kabhi 10 se kam mat rakhna, 12 standard hai.**

### Code — `app/lib/password.ts`

Har project mein ek jagah se hashing handle karna chahiye — do cheezein: hash banana, aur compare karna. Wahi DRY wala 3.4.1 pattern hai.

**File:** `app/lib/password.ts` (nayi file)

```ts
import bcrypt from "bcryptjs";

export async function hashPassword(password: string): Promise<string> {
  const saltRounds = 12;
  const hashedPassword = await bcrypt.hash(password, saltRounds);
  return hashedPassword;
}

export async function comparePasswords(
  password: string,
  hashedPassword: string
): Promise<boolean> {
  const isMatch = await bcrypt.compare(password, hashedPassword);
  return isMatch;
}
```

Notice kiya? Dono functions **async** hain — bcrypt ka hashing intentionally slow hai (saltRounds ki wajah se), toh yeh heavy kaam hai jo async block karta hai. Toh `await` zaroori hai — bina await ke tumhe promise milega, match nahi.

### Test — Apna Pehla Hash

Chal ek baar console mein dekh lete hain hash kaisa dikhta hai. `node` kholo (ya terminal mein `node -e`):

```bash
node -e "const b=require('bcryptjs'); b.hash('super-secret-123', 12).then(h => console.log(h))"
```

Aur yeh jo hash hai — isse wapas `super-secret-123` nahi nikal sakta. Ek tarfa hai. **Register flow mein `hashPassword()` yeh hash automatically banayega — Step 3 mein wahi use karenge.**

### Stage D — Hash + Save (Yahan `addUser` Banti Hai)

**SOCH:** Email free hai. Ab password ko hash karke save karna hai. **Yahan `hashPassword()` ka asli use hua** — manually hash banane ki zaroorat khatam, har naye user ka hash isi helper se banega.

**CONCEPT:** `hashPassword(password)` — Step 1 ka helper, ~250ms slow, isliye `await`. `addUser(email, passwordHash)` — yeh function abhi exist nahi karta, hume Step 2 ki `users.ts` mein **add** karna hoga. Isme **likhna** padta hai — isliye ab `writeFileSync` ka import bhi add hoga (abhi tak sirf read tha).

**CODE — pehle `users.ts` mein `addUser` add karo** (poore file ka state — naya hissa `// NEW` se mark hai):

```ts
// app/lib/users.ts
import { readFileSync, writeFileSync } from "fs";   // writeFileSync ab add hua
import path from "path";

const filePath = path.join(process.cwd(), "app", "lib", "users.json");

export type User = {
  id: number;
  email: string;
  passwordHash: string;
};

export function getAllUsers(): User[] {
  const data = readFileSync(filePath, "utf-8");
  return JSON.parse(data);
}

export function getUserByEmail(email: string): User | null {
  const users = getAllUsers();
  return users.find((u) => u.email === email) ?? null;
}

// NEW: yeh function add karo
export function addUser(email: string, passwordHash: string): User | null {
  const users = getAllUsers();
  if (users.some((u) => u.email === email)) return null;

  const newUser = { id: users.length + 1, email, passwordHash };
  users.push(newUser);
  writeFileSync(filePath, JSON.stringify(users, null, 2));
  return newUser;
}
```

- **`users.some(...)`** — array mein koi ek element condition match kare toh `true`. Data layer mein bhi duplicate check — action wala check UX ke liye (fast fail, hash se pehle), yeh **safety net** ke liye (agar koi action bypass karke seedha data layer use kare). Do jagah check = defense in depth.
- **`id: users.length + 1`** — auto-increment jaisa: naye user ko agla number.
- **`JSON.stringify(users, null, 2)`** — pretty print, file insaan ke padhne ke liye readable rahe. (Batch 3 mein bhi wahi tha.)

**CODE — ab `actions.ts` mein hash + save** (poore file ka state — imports bhi accumulate ho rahe hain, same module se do functions):

```ts
// app/actions.ts
"use server";

import { getUserByEmail, addUser } from "./lib/users";   // addUser ab add hua
import { hashPassword } from "./lib/password";           // NEW: import

export type RegisterState = {
  error?: string;
};

export async function registerAction(prevState: RegisterState, formData: FormData) {
  const email = formData.get("email");
  const password = formData.get("password");

  if (typeof email !== "string" || typeof password !== "string" || !email.trim() || !password) {
    return { error: "Email aur password dono chahiye" };
  }

  const normalizedEmail = email.trim();
  if (getUserByEmail(normalizedEmail)) {
    return { error: "Yeh email pehle se registered hai" };
  }

  // NEW: hash + save
  const passwordHash = await hashPassword(password);
  addUser(normalizedEmail, passwordHash);
}
```

Register se user ban gaya. Ab login — wo user hai, password sahi hai, toh **session cookie set** karna hai. 4.1 mein bola tha: **cookie set karne ki permission sirf Server Actions aur Route Handlers ko hai.** Yahan wahi hota hai.

### Stage D — Session Cookie Set (4.1 Ka Concept Yahi Laga)

**SOCH:** Password sahi hai. Ab login success ko yaad rakhna hai — **session cookie set karni hai.** Yahan 4.1 ke teeno safety attributes asli mein lagte hain.

**CONCEPT:** `cookies()` — `next/headers` se, Next 15+ mein **async** hai (isliye `await`). `cookieStore.set("sessionId", ...)` — name, value, options. Value sirf `String(user.id)` — cookie mein user ka data nahi, sirf id. Asli record (`users.json`) server ke paas hai (session pattern — 4.1). Options: `httpOnly: true` (JavaScript se chura nahi sakta), `secure: process.env.NODE_ENV === "production"` (production mein HTTPS pe hi jaayegi), `sameSite: "lax"` (CSRF se bachao), `maxAge: 60*60*24*7` = 7 din.

**CODE** — do cheezein: top pe import, aur `loginAction` ke andar `isMatch` check ke baad:

```ts
// app/actions.ts — sabse top pe (existing imports ke saath)
import { cookies } from "next/headers";
```

```ts
// app/actions.ts — loginAction ke andar, isMatch check ke baad
  const isMatch = await comparePasswords(password, user.passwordHash);
  if (!isMatch) {
    return { error: "Email ya password galat hai" };
  }

  const cookieStore = await cookies();

    httpOnly: true,

```

```ts
// app/actions.ts — final
"use server";

import { getUserByEmail, addUser } from "./lib/users";
import { hashPassword, comparePasswords } from "./lib/password";
import { redirect } from "next/navigation";
import { cookies } from "next/headers";

export type RegisterState = {
  error?: string;
};

export async function registerAction(prevState: RegisterState, formData: FormData) {
  const email = formData.get("email");
  const password = formData.get("password");

  if (typeof email !== "string" || typeof password !== "string" || !email.trim() || !password) {
    return { error: "Email aur password dono chahiye" };
  }

  const normalizedEmail = email.trim();
  if (getUserByEmail(normalizedEmail)) {
    return { error: "Yeh email pehle se registered hai" };
  }

  const passwordHash = await hashPassword(password);
  addUser(normalizedEmail, passwordHash);

  redirect("/login");
}

export type LoginState = {
  error?: string;
};

export async function loginAction(prevState: LoginState, formData: FormData) {
  const email = formData.get("email");
  const password = formData.get("password");

  if (typeof email !== "string" || typeof password !== "string" || !email.trim() || !password) {
    return { error: "Email aur password dono chahiye" };
  }

  const user = getUserByEmail(email.trim());
  if (!user) {
    return { error: "Email ya password galat hai" };
  }

  const isMatch = await comparePasswords(password, user.passwordHash);
  if (!isMatch) {
    return { error: "Email ya password galat hai" };
  }

  const cookieStore = await cookies();
  cookieStore.set("sessionId", String(user.id), {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    maxAge: 60 * 60 * 24 * 7,
  });

  redirect("/");
}
```

## What It Is NOT

- **Hashing ≠ encryption.** Encryption reversible hai — encrypted data ko key se wapas original bana sakte ho. Hashing one-way hai — wapas nahi banta. Password ke liye hash hi sahi hai kyunki server ko kabhi bhi original password nahi janna chahiye.
- **Yeh production auth nahi hai.** Isme koi rate limiting nahi (hacker infinite tries kar sakta hai), koi real session store nahi (session id ka record file ke id hi hai), koi lockout nahi. **Isliye roadmap isse "sirf samajhne ke liye" kehta hai** — 4.4 mein Auth.js isko production-grade banayega.
- **`bcryptjs` ≠ `bcrypt`.** Dono almost same API dete hain, par `bcrypt` mein native (C) code compile hota hai. Installation issues se bachne ke liye `bcryptjs` use kar rahe hain.

## Common Mistakes

- **Password plaintext store karna** — sabse badi galti. Data breach = sab passwords leaked. Hash hamesha.
- **`saltRounds` kam rakhna** — 10 se kam ka matlab brute-force aasaan. 12 standard hai.
- **`await` bhoolna** — `bcrypt.compare` async hai. Bina await ke `isMatch` ek promise hai, aur `if (promise)` hamesha truthy — matlab galat password bhi pass ho jaayega!
- **Cookie mein user ka data daalna** — cookie browser ke control mein hai, user khud edit kar sakta hai. Sirf id.
- **`cookies()` bina `await`** — Next 15+ mein async hai, compile error milega.
- **Alag-alag login errors** — "email nahi mila" vs "password galat" do — hacker ko yeh pata chal jaata hai ki kaunsa email registered hai (email-list discovery).
- **Duplicate email check bhoolna** — register mein pehle `getUserByEmail()` karo, warna ek email ke do accounts ban jayenge (aur login mein confusion: kaunsa match kare).
- **Register mein bina trim ke store karna** — `"praveen@x.com "` aur `"praveen@x.com"` alag users ban jaate hain. Normalize pehle, store baad mein.
- **Ek saath poora code likhna** — isliye humne har action/form ko stage-wise banaya. Koi bhi chhoti feature pehle static, phir gradual upgrade — ek baar mein sab dump karne se galti ka pata nahi chalta.

## Nutshell

Password kabhi plaintext store nahi hota — `bcryptjs` se hash hota hai (one-way, salt ke saath, slow intentionally). `password.ts` mein do helpers: `hashPassword` (register) aur `comparePasswords` (login). Users `users.json` file mein hash ke saath rehte hain — **register flow se bante hain**, manually nahi. Register Server Action: email normalize + duplicate check → `hashPassword()` → `addUser()` → redirect `/login`. Login Server Action: email se user dhoondo → `comparePasswords` se password check karo → `cookies().set("sessionId", userId, {httpOnly, secure, sameSite})` → redirect. Cookie mein sirf user ki id hoti hai — record server ke paas.

**In Your Own Words**

1. Password hashing kyun zaroori hai — agar encryption bhi password ko safe rakh sakti hai, toh hash hi kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Hashed password wapas original mein convert nahi ho sakta — encryption hota hai. Yahi iska fayda hai: server ko kabhi original password janna hi nahi chahiye. Agar breach ho jaye, toh hacker ke paas sirf hash honge jo strong password ke liye bekaar hain (aur salt ki wajah se precomputed tables bhi kaam nahi karti). Agar encryption use karte, toh key ke saath hacker saare passwords unlock kar sakta tha — ek breach, sab kuch.

</details>

2. `saltRounds: 12` ka kya matlab hai, aur yeh "slow" wala design intent kyun hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** SaltRounds batata hai hash banana kitna mehenga hai — 12 ka matlab lagbhag 250ms intentional delay. Yeh design by intention hai: legitimate user login pe ek baar 250ms wait karega, koi dikkat nahi. Par hacker ko hash crack karne ke liye har password guess pe 250ms lagenge — ek second mein sirf 4 tries, toh brute-force practically bekaar ho jaata hai. Fast hashing hacker ke kaam ko aasaan banati, isliye bcrypt slow hai.

</details>

3. Login mein email-galat aur password-galat ka error same kyun rakha? (Agar alag hota toh kya galat hota?)

<details>
<summary>Show Answer</summary>

**Sample Answer:** Agar error alag hote — "email nahi mila" vs "password galat" — toh koi bhi try kar sakta tha email list banane ke liye: har email pe login attempt, agar "email nahi mila" aaya toh wo email registered nahi hai, agar "password galat" aaya toh registered hai. Isse attacker ko pata chal jaata ki kaunse emails ka account hai (account enumeration) — phir unhi pe phishing ya brute-force karna. Same error se attacker ko yeh information nahi milti.

</details>

4. Session cookie mein sirf `userId` kyun rakhi — poora user object (naam, email) kyun nahi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Cookie browser ke control mein hai — user DevTools se apni cookie edit kar sakta hai. Agar cookie mein poora user object ho ("email: x, admin: true"), toh user usse badal ke apna fayda kar sakta hai — server ko pata nahi chalega ki cookie fake hai. Sirf id rakho toh user id ko koi bhi badal de, server har request pe file se fresh user record padh ke maan lega ki "yeh id ka user data file se aaya, cookie se nahi."

</details>

5. `useActionState` ka `isPending` login form mein kya kaam karta hai — aur bina iske kya problem hoti?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `isPending` submit ke waqt `true` hota hai — isse hum button disable karte hain aur "Login ho raha hai..." dikhaate hain. Bina iske user double-click kar ke do baar login action trigger kar sakta hai (do sessions/cookies), aur kabhi kabhi slow network pe user ko lagta hai ki form hang ho gaya. Pending state se yeh dono problems solve hoti hain.

</details>

6. Register mein duplicate email check **hash se pehle** kyun kiya? (Agar baad mein karte toh kya problem hoti?)

<details>
<summary>Show Answer</summary>

**Sample Answer:** `hashPassword` intentionally slow hai (saltRounds 12 = lagbhag 250ms). Agar pehle hash banaya aur phir email already registered mila, toh wo 250ms bekaar chale jaate. Duplicate check pehle karo — email already hai toh seedha error, koi hashing nahi. `addUser` ke andar bhi ek check hai (`some()`) — wo safety net hai agar koi action se bypass karke seedha data layer use kare. Pehle wala check performance ke liye, andar wala security ke liye.

</details>
