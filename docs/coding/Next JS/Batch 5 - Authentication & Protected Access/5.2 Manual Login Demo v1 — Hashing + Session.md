# Manual Auth v1 — Hashing & Session Cookie

## Where We Left Off

In 5.0 we learned that the cookie holds only a session ID while the server keeps the real mapping, and that passwords must be hashed, never stored in plaintext. Now we build exactly that — **Login Demo v1**, by hand, end to end. Before that, one question most people never ask: when a site says "register" and you type a password, what actually happens to that password on the server?

## Step 1 — Password Hashing: Why Plaintext Is Dead

### Concept — Never Store Plaintext

Suppose an app stored passwords as-is: `password: "super-secret-123"`. A data breach leaks the user file. Now the attacker has **every user's actual password**. Worse, people reuse passwords — that one leak unlocks their Gmail, their bank, everywhere.

The solution is **hashing**. A hash is a **one-way function** — it turns a password into an irreversible jumble of characters. If that same leak later exposes only hashes, the attacker has jumbles they cannot use (assuming the passwords were strong).

### Salt — Defeating Pattern Attacks

If two people use the same password, naive hashing gives the same hash — easy to spot. **Salt** fixes this: each user gets a unique random string mixed in before hashing, so identical passwords produce different hashes. Salt also defeats **rainbow tables** — precomputed lists an attacker might try first. bcrypt generates and stores the salt as part of the hash.

### Library — `bcryptjs`

Install it:

```bash
npm install bcryptjs
```

Why `bcryptjs` and not `bcrypt`? `bcryptjs` is a pure-JavaScript implementation — no native compilation — so it runs anywhere without setup. (`bcrypt` uses native C code; it is faster but can fail to build in some environments.) For this course, `bcryptjs` removes the setup friction.

The API is two functions:

```ts
bcrypt.hash(password, saltRounds)      // produce a hash (async)
bcrypt.compare(password, hash)         // check a password against a hash (async)
```

`saltRounds` controls how expensive hashing is. `12` means roughly 250 ms of work — intentionally slow. That slowness is the point: a stolen hash is useless to crack if each guess costs a quarter-second. **Never go below 10; 12 is the safe default.**

### The Helper — `app/lib/password.ts`

Centralize hashing in one place, so the salt rounds and logic live in exactly one spot:

```ts
import bcrypt from "bcryptjs";

export async function hashPassword(password: string): Promise<string> {
  const saltRounds = 12;
  const hashedPassword = await bcrypt.hash(password, saltRounds);
  return hashedPassword;
}

export async function comparePasswords(
  password: string,
  hashedPassword: string
): Promise<boolean> {
  const isMatch = await bcrypt.compare(password, hashedPassword);
  return isMatch;
}
```

Both functions are `async` — hashing is deliberately slow (by the salt rounds), so it must not block. The `await` is required: without it you get a promise, and `if (promise)` is always truthy.

### A Hash in the Wild

The output of `bcrypt.hash` looks like:

```
$2b$12$he0m9/YAyIfU4Te9XJaDfeCCx4RHmqREcaZDoH2o1MmBwW2CYdaYu
```

- `$2b$` — bcrypt's version tag.
- `12` — the salt rounds.
- The rest — salt + hash, combined and opaque.

You cannot reverse this back to the original password. The register flow will call `hashPassword()` so this is produced automatically — and `users.json` will contain only these strings, never plaintext.

## Step 2 — Users Data Layer (`users.json` + `lib/users.ts`)

Batch 3 taught the file-based data layer (`comments.json` + `lib/comments.ts`). Same pattern for users; a database is coming in Batch 6.

**`app/lib/users.json`** starts empty — records are created **by the register flow**, which writes hashes (never plaintext):

```json
[]
```

**`app/lib/users.ts`** — the read-only functions first, with the model already encoding the rule (a `passwordHash` field exists, but there is no `password` field to hold one by mistake):

```ts
import { readFileSync } from "fs";
import path from "path";

const filePath = path.join(process.cwd(), "app", "lib", "users.json");

export type User = {
  id: number;
  email: string;
  passwordHash: string;
};

export function getAllUsers(): User[] {
  const data = readFileSync(filePath, "utf-8");
  return JSON.parse(data);
}

export function getUserByEmail(email: string): User | null {
  const users = getAllUsers();
  return users.find((u) => u.email === email) ?? null;
}
```

`find()` returns the first match or `undefined`; the `?? null` makes the caller's job unambiguous: user found, or `null`. The type keeps the hash as `passwordHash`, so the absence of a plaintext field is enforced at the type level.

Note: only `readFileSync` is imported here. Writing comes in Step 3 when `addUser` is actually needed — import only what you use.

## Step 3 — Register Server Action: Where `hashPassword()` Is Actually Used

Why register before login? Because login needs a user to exist. Register creates that user, and this is where `hashPassword()` finally does its job (it has been defined but not called yet).

**File:** `app/actions.ts` — add to it. Start with the directive and a skeleton:

```ts
"use server";

export type RegisterState = {
  error?: string;
};

export async function registerAction(prevState: RegisterState, formData: FormData) {
  const email = formData.get("email");
  const password = formData.get("password");
}
```

### Stage A — Skeleton: read the fields

`formData.get("name")` returns each input's value (3.3.1). The `(prevState, formData)` signature is the `useActionState` pattern. Verify with `console.log(email, password)` — it lands in the **server terminal**, not the browser.

### Stage B — Validation: reject empty input

Passwords should never be empty; an empty account guarantees broken logins. Validate before any expensive work:

```ts
  if (typeof email !== "string" || typeof password !== "string" || !email.trim() || !password) {
    return { error: "Email aur password dono chahiye" };
  }
```

The `typeof` check matters: `formData.get()` returns `null` when the field is missing, so treat the value as a string only after confirming it.

### Stage C — Duplicate email check (before hashing)

```ts
import { getUserByEmail } from "./lib/users";
```

```ts
  const normalizedEmail = email.trim();
  if (getUserByEmail(normalizedEmail)) {
    return { error: "Yeh email pehle se registered hai" };
  }
```

This check runs **before hashing** because hashing is intentionally slow (~250 ms). No point paying that cost if the email is already taken. (This is the user-facing fast-fail; the data layer gets its own guard in `addUser` for defense in depth.)

### Stage D — Hash + save (where `hashPassword()` is finally used)

First, extend the data layer with a writer. `addUser` includes a duplicate check of its own — so the data layer is safe even if an action bypassed the earlier guard:

```ts
// app/lib/users.ts — add after getUserByEmail
export function addUser(email: string, passwordHash: string): User | null {
  const users = getAllUsers();
  if (users.some((u) => u.email === email)) return null;

  const newUser = { id: users.length + 1, email, passwordHash };
  users.push(newUser);
  writeFileSync(filePath, JSON.stringify(users, null, 2));
  return newUser;
}
```

The import line gains `writeFileSync`. Then the action:

```ts
import { getUserByEmail, addUser } from "./lib/users";
import { hashPassword } from "./lib/password";
import { redirect } from "next/navigation";

// ...inside registerAction, after the duplicate check:
  const passwordHash = await hashPassword(password);
  addUser(normalizedEmail, passwordHash);

  redirect("/login");
```

`hashPassword(password)` runs (~250 ms, hence `await`), then `addUser` writes the hash to `users.json`, and the user lands on `/login`. Inspect `users.json` afterward — the entry contains only the bcrypt hash string, never the plaintext.

## Step 4 — Login Server Action: verify and SET the cookie

Login follows the same skeleton, but ends at verification + cookie, not hashing.

```ts
// app/actions.ts — add after registerAction
export type LoginState = { error?: string };

export async function loginAction(prevState: LoginState, formData: FormData) {
  const email = formData.get("email");
  const password = formData.get("password");

  if (typeof email !== "string" || typeof password !== "string" || !email.trim() || !password) {
    return { error: "Email aur password dono chahiye" };
  }

  const user = getUserByEmail(email.trim());
  if (!user) {
    return { error: "Email ya password galat hai" };
  }

  const isMatch = await comparePasswords(password, user.passwordHash);
  if (!isMatch) {
    return { error: "Email ya password galat hai" };
  }
  // cookie set below
}
```

A security note on the error message: it is deliberately the **same** whether the email doesn't exist or the password is wrong. Distinct messages ("email not found" vs "wrong password") enable account enumeration — an attacker probing which addresses are registered. Same message, no information leak.

### Setting the session cookie — 5.0's rules in practice

```ts
import { cookies } from "next/headers";

// inside loginAction, after verification succeeds:
  const cookieStore = await cookies();
  cookieStore.set("sessionId", String(user.id), {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    maxAge: 60 * 60 * 24 * 7, // 7 days
  });
  redirect("/");
```

This is the moment 5.0 pays off:
- `httpOnly: true` — JavaScript can't read it (XSS defense).
- `secure` — HTTPS-only in production (`process.env.NODE_ENV === "production"`).
- `sameSite: "lax"` — CSRF defense.
- `maxAge: 7 days` — "remember me" duration.
- The value is `String(user.id)` — **just the ID**, not the user object. The record lives in the data layer; the cookie is only the key.

Next.js rules the write: setting cookies is allowed only in Server Actions and Route Handlers — exactly where this code is. The cookie is sent as `Set-Cookie` on the redirect response, so the browser stores it and returns it on every subsequent request.

## Test — Register → Login → Cookie

1. Visit `/register`, create an account → land on `/login`.
2. Inspect `app/lib/users.json` — the new entry holds a bcrypt **hash**, not the plaintext.
3. At `/login`, log in with the same credentials → redirect to `/`.
4. DevTools → Application → Cookies: the `sessionId` cookie is present with `HttpOnly`, `SameSite: lax`, and a 7-day expiry.
5. Wrong password → the same generic error; no cookie is set.
6. Duplicate email on register → the duplicate check fires.

## What It Is NOT

- **Hashing is not encryption.** Encryption is reversible with a key; hashing is one-way. Passwords must stay one-way: the server never needs to know the original, only to verify a candidate against the stored hash.
- **This is not production auth.** No rate limiting (brute force is free), no real session store (the ID is the row's primary key, not an unguessable token), no lockout. The roadmap itself calls this "for understanding only." Auth.js hardens all of this.
- **`bcryptjs` and `bcrypt` are not interchangeable in spirit.** They share an API; `bcryptjs` trades speed for zero-build setup. The hashing concepts are identical.

## Common Mistakes

- **Storing plaintext passwords** — a single breach exposes everything. Hash every password, always.
- **Running salt rounds below 10.** Below 10 is brute-forceable; 12 is the safe default.
- **Forgetting `await` on `bcrypt.compare`.** It is async; without `await`, the result is a promise, and `if (promise)` is always truthy — a wrong password would slip through.
- **Putting user data in the cookie.** The cookie holds only the ID. Anything else is forgery bait.
- **Calling `cookies()` without `await`.** In Next 15+ it returns a promise; ignoring that breaks the code.
- **Distinct login errors ("email not found" vs "wrong password").** That is account enumeration — keep them identical.
- **Logging in without a duplicate-email check.** Two accounts can share an email; login then can't know which to trust.

## Nutshell

Password is never stored — `bcryptjs` hashes it with a salt (`hashPassword`, ~250 ms at 12 rounds); `comparePasswords` verifies without ever reversing. Users live in `users.json`, each record storing only `passwordHash` (no plaintext column). Register validates, checks for duplicates, hashes, saves, then redirects to login. Login looks the user up by email, verifies the hash, and sets an `httpOnly` + `secure` + `sameSite: lax` cookie holding only the user ID, then redirects. Every rule from 5.0 — don't store data in cookies, defend with attributes, keep errors uniform — is exercised here.

## In Your Own Words

<details>
<summary>1. Why hash passwords instead of encrypting them?</summary>

**Sample Answer:** Hashing is one-way — you can confirm a password matches a hash, but you cannot recover the original from the hash. Encryption is reversible with a key. Since the server never needs the original password, hashing is the right tool: a stolen-database leak yields only hashes, not usable credentials.

</details>

<details>
<summary>2. What does `saltRounds: 12` actually control, and why is slowness the feature?</summary>

**Sample Answer:** It sets the computational cost of producing a hash. `12` means roughly 250 ms per hash. That slowness protects users if hashes are stolen: a brute-force attack would try thousands of candidate passwords, each one paying that 250 ms — so cracking becomes economically infeasible. A legitimate login pays the cost once; an attacker pays it for every guess.

</details>

<details>
<summary>3. Why does login return the same error for "unknown email" and "wrong password"?</summary>

**Sample Answer:** Distinct messages leak which addresses are registered. An attacker can sweep a list of emails against the login form; "email not found" tells them that address is unused, "wrong password" tells them it is registered. With one identical error, neither outcome is distinguishable, so the attack gets no information.

</details>

<details>
<summary>4. Why does the cookie hold only the user ID, not the whole user object?</summary>

**Sample Answer:** The cookie lives in the browser, under the user's control. A user can open DevTools and edit their own cookies. If the cookie held `{ id, email, role: "admin" }`, the user could flip `role` to admin and the server might trust it. Storing only the ID means the user holds a key with no meaning of its own; the server looks that ID up in its own store every time, using trusted data.

</details>

<details>
<summary>5. What is the `useActionState` "pending" state for, and what breaks without it?</summary>

**Sample Answer:** `isPending` is `true` during form submission. The button disables and shows "Signing in..." — preventing double-submits (which could issue two session cookies) and signaling progress on slow networks. Without it, a second click races the first, and nothing tells the user the request is in flight.

</details>

But a cookie that is never **read** is just bytes in the browser. 5.1's final act: a `getSession()` helper that reads the cookie back and resolves it to a user — and a protected layout that redirects anyone without a session, plus a **logout** that deletes the cookie. This completes the manual auth loop.
