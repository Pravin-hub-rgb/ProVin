# Hardcoded UI + Auth Scaffold

## Where We Left Off

In 5.5.1 we planned the Member Dashboard: routes, the two data sources (GitHub identity via session, app-side bio via `profiles.json`), and the update flow through a Server Action. Execution starts now. And series rule #1 from 3.4.1 holds: **data layer comes after UI.** Building dynamic data and UI together means an error could be in the UI or in the data layer and you can't tell which. So we start with **hardcoded UI** — confirm the look with static data, then wire real auth in 5.5.3, then dynamic data in 5.5.4.

## Step 1 — Create the Project

Fresh project — not a blog (the roadmap rule). Make the folder:

```bash
npx create-next-app@latest member-dashboard
```

Setup prompts: TypeScript **yes**, App Router **yes**, Tailwind **yes** (or no — styling is minor here; your call), and leave the `@/*` import alias as default.

Then install the one dependency we'll need shortly:

```bash
npm install next-auth@beta
```

Project scaffold: make a `components/` folder — `app/components/` — for the pieces shared across routes.

## Step 3 — Home Page (Public)

Home is **public** — everyone sees it, no sign-in required. `Link` handles navigation client-side (the Batch 1 concept) without a full reload. The job of this page: say what the app is, then point to login.

## Step 6 — Profile Page (Static Form)

**File:** `app/profile/page.tsx` (new)

```tsx
export default function ProfilePage() {
  return (
    <main>
      <h1>Profile</h1>
      <p>Email: pravin@example.com</p>

        <label>
```

Profile page: email display + editable bio form. The form is **static** — no `action`, so submitting does nothing (just a reload). `defaultValue` pre-fills the textarea so the layout is confirmed. 5.5.4 connects it to `updateProfileAction`.

## Problems This Phase Exposes — Why the Next Step Matters

Three issues are now obvious:

1. **Data is duplicated** — the email and bio are hardcoded in both dashboard and profile. Change one, the other goes stale. 5.5.4 introduces the data layer and session to replace both.
2. **Login button is fake** — there's no auth at all. 5.5.3 wires GitHub OAuth.
3. **Nothing is protected** — `/dashboard` is open to everyone. 5.5.3 adds the `(protected)` group and layout check.

Design is locked in. Now bring in the real pieces.

## What It Is NOT

- **This as a usable app.** It's a static mock — no auth, no protection, no persistence. It only proves the pages look right.
- **Skipping static data for dynamic too early.** Doing identity + bio + auth + actions all at once makes a broken save indistinguishable from a broken layout. One concern per phase.
- **Ignoring duplication on purpose.** Hardcoding the same value in two pages is intentional only to confirm the UI — it must be replaced by a shared source (session + data layer) in 5.5.4.

## Common Mistakes

- **Wiring auth into the static pages immediately.** Resist it — you lose the guarantee that the UI works before auth/identity enters the picture.
- **Leaving duplicated values past this phase.** Treat hardcoded data like scaffolding: it must come down once the real data layer is in.
- **Building the protected group after the pages.** Plan the `(protected)` group early (done in 5.5.1) so pages drop in with protection already structured.
- **Starting with Server Actions on a static form.** The submit did nothing in 5.5.2; the action arrives in 5.5.4. Mixing an untested form shape with a new action obscures which one is wrong.
- **Not replacing hardcoded values.** A common trap: the app works statically, looks "good enough," and the hardcoded values stay in production forever — serving static data to every user.

## Nutshell

5.5.2 confirms the UI with static data so the layout and pages are validated before any dynamic behavior is added. The navbar, home, login, dashboard, and profile pages all render their look; login button is non-functional, Save does nothing, nothing is protected, and identity + bio are duplicated across pages — all expected, all to be replaced. Next: 5.5.3 wires the real auth scaffold (`auth.ts`, route handler, env, `SessionProvider` + dynamic navbar, real login page, the `(protected)` group + layout, and `proxy.ts` routing).

## In Your Own Words

<details>
<summary>1. What is the value of a hardcoded UI phase, and what problem does jumping straight to dynamic cause?</summary>

**Sample Answer:** It isolates one concern at a time. If UI and dynamic data are built together and something breaks, you can't tell whether the bug is in the UI or in the data layer, and you can't test the page's shape without a working backend. The static phase confirms the design first (avatar, name, email, bio all render) so that when the data layer is connected, a failure is unambiguously a data-layer issue, not a layout issue.

</details>

<details>
<summary>2. Why is the login button intentionally non-functional here, and what's missing for it to work?</summary>

**Sample Answer:** This phase is about look only, not behavior — confirming the button's placement and text before the auth machinery exists. To actually work, it needs the full auth stack: `auth.ts` config, the `[...nextauth]` route handler, env vars (`AUTH_SECRET`, `AUTH_GITHUB_ID`, `AUTH_GITHUB_SECRET`), and a `signIn("github")` action. That wiring is 5.5.3's scope.

</details>

<details>
<summary>3. Which fields were hardcoded on the dashboard, and what are their real sources per the 5.5.1 plan?</summary>

**Sample Answer:** Name, email, avatar, and bio were all hardcoded. Per the plan: name, email, and avatar come from the **session** (GitHub, via `auth()`), and bio comes from the **data layer** (`profiles.json`). That is why the next two phases matter — 5.5.3 brings the session (identity), and 5.5.4 brings the data layer (bio).

</details>

<details>
<summary>4. Why is the home page public rather than protected?</summary>

**Sample Answer:** The home page's purpose is to explain the app and route to sign-in. If it were protected, no one could learn what the app is without logging in first — defeating the entrance point. Public pages (home, login) are the entryway; only pages exposing **user-specific data** (dashboard, profile) are worth protecting.

</details>

<details>
<summary>5. The profile form has no `action` — what happens on submit now, and what pattern will replace it?</summary>

**Sample Answer:** With no action, submitting is a plain HTML form submission → a page reload that saves nothing and validates nothing. In 5.5.4 it gets the Batch 3 treatment: an `updateProfileAction` Server Action, `useActionState` for pending/error/success states, and `revalidatePath` so the page refreshes with saved data — the same pattern as the comments action from Batch 3.

</details>
