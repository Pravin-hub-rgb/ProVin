## Problem Highlight — Ab Kyun Agla Part

Hardcoded phase ki teen problems clear ho gayi:

1. **Data do jagah hardcoded hai** — dashboard pe `pravin@example.com` + bio, profile pe bhi. Ek jagah badlo toh doosri purani rehti — 4.5.4 mein data layer + session se replace.
2. **Login button fake hai** — koi auth nahi. 4.5.3 mein GitHub OAuth wiring.
3. **Kuch protected nahi** — bina login dashboard khul raha hai. 4.5.3 mein `(protected)` group + layout check.

**Ab tak ka kaam solid hai — design confirm. Ab asli cheezein jodte hain.**

**In Your Own Words**

1. Hardcoded UI phase ka kya fayda — seedha dynamic banane se kya problem hoti?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Ek problem ek time pe test hoti hai. Agar dynamic data + UI ek saath banate, toh error aane pe pata nahi chalta ki UI mein galti hai ya data layer mein — do cheezein ek saath test karni mushkil. Hardcoded pehle se: UI ka design confirm hota hai (avatar, naam, email, bio — sab dikh gaya), data shape validate hota hai. Baad mein data layer ki galti easily identify hoti hai kyunki UI pehle se kaam kar raha hai.

</details>

2. Is phase mein login button "fake" kyun rakha — uske kaam karne ke liye kya missing hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Login kaam karne ke liye poora auth stack chahiye: `auth.ts` config, `[...nextauth]` route handler, env vars (AUTH_SECRET, AUTH_GITHUB_ID/SECRET), aur `signIn("github")` wala Server Action. Yeh sab 4.5.3 ka scope hai. Hardcoded phase mein sirf design dikhana hai — button ka look (text, position) confirm hoga. Ek phase mein ek cheez — pehle design, phir wiring.

</details>

3. Dashboard pe kaunse data hardcoded the, aur plan ke hisaab se unka asli source kya hoga?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Naam, email, avatar, bio — charo hardcoded the. Plan (4.5.1) ke hisaab se: naam/email/avatar ka source **session** hai (GitHub se auth() ke through), aur bio ka source **profiles.json** hai (app-side data layer). Isliye 4.5.3 mein auth wiring (session aane lagega) aur 4.5.4 mein data layer (bio file se) — tab hardcoded values replace ho jayengi.

</details>

4. Home page public kyun hai — kya woh bhi protected nahi hona chahiye?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Home page ka kaam hi hai visitors ko batana ki app kya hai aur login pe le jana — agar woh protected hota, toh bina login koi bhi app ke baare mein jaanta hi nahi aur sabko pehle login karna padta. Public pages (home, login) sehuliyat ke liye khule rehte hain; **sensitive pages** (dashboard, profile) protected hote hain. Protection ka fayda wahi hota hai jahan data user-specific ho.

</details>

5. Profile page ka form abhi `action` ke bina hai — submit pe kya hota hai, aur kaunsa pattern ise jodega?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Bina `action` ke form submit hone pe page refresh ho jaata hai (default HTML behavior) — koi data save nahi hota, koi validation nahi. 4.5.4 mein ise Batch 3 ke pattern se jodenge: `updateProfileAction` Server Action + `useActionState` (pending/error/success) + `revalidatePath` (save ke baad page auto-refresh) — wahi pattern jo comments app mein useActionState + toast se dekha tha.

</details>
