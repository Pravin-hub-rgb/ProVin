## Step 2 — Protecting a Route — Server Side

With Auth.js (5.4.3), you did:

```tsx
// Auth.js approach
import { auth } from '@/auth';
import { redirect } from 'next/navigation';

export default async function DashboardLayout({ children }) {
  const session = await auth();
  if (!session?.user) redirect('/sign-in');
  return <div>{children}</div>;
}
```

With Clerk, the equivalent is:

```tsx
// Clerk approach — app/dashboard/layout.tsx
import { currentUser } from '@clerk/nextjs/server';  // server-side import
import { redirect } from 'next/navigation';

export default async function DashboardLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const user = await currentUser();  // server-side — gets the full user object

  if (!user) {
    redirect('/sign-in');  // not authenticated → send to login
  }

  return (
    <div>
      <nav className="p-4 border-b">
        Welcome, {user.firstName}  // user object from Clerk
      </nav>
      {children}
    </div>
  );
}
```

**Line-by-line:**

- **`import { currentUser } from '@clerk/nextjs/server'`** — server-side import. This runs on the server, not the client. It fetches the full user object from Clerk's API.
- **`await currentUser()`** — returns `null` if no session, or the full `User` object if authenticated. This is the Clerk equivalent of Auth.js's `await auth()`.
- **`redirect('/sign-in')`** — this is the **same** `redirect` from `next/navigation` you used in 5.4.3. Next.js's redirect is framework-level, not Clerk-specific.
- **`user.firstName`** — Clerk's `User` object has `firstName`, `lastName`, `emailAddresses`, `primaryemailAddressId`, and more.

> **Important:** `currentUser()` is a **server function** — it only works in Server Components, route handlers, or middleware. For Client Components, use `useAuth()` or `useUser()` (see below).

## Step 3 — Showing Auth State on the Client

If you need auth state in a **Client Component** (like a nav bar with a Sign Out button), use `useUser`:

```tsx
// components/auth-button.tsx
'use client';  // Client Component — uses hooks

import { useUser, SignOutButton } from '@clerk/nextjs';

export function AuthButton() {
  const { isLoaded, isSignedIn, user } = useUser();

  if (!isLoaded) return <div>Loading...</div>;  // Clerk is initializing
  if (!isSignedIn) return <button onClick={() => window.location.href = '/sign-in'}>Sign In</button>;

  return (
    <div>
      Hello, {user.firstName}!
      <SignOutButton />  // Clerk's built-in sign-out button
    </div>
  );
}
```

**Line-by-line:**

- **`useUser()`** — Clerk's client-side hook. Returns `isLoaded` (SDK ready), `isSignedIn` (has session), and `user` (full user object or null).
- **`SignOutButton`** — Clerk's pre-built sign-out component. Just renders a button that calls `signOut()` and clears the session.
- **`'use client'`** — this component uses `useUser` (a hook), so it must be a Client Component.

## Step 4 — Route Groups for Protected Sections

You can use Next.js **route groups** to organize protected routes, just like Auth.js did in 5.5.3:

```tsx
// app/(auth)/layout.tsx — wraps /sign-in, /sign-up
export default function AuthLayout({ children }: { children: React.ReactNode }) {
  return (
    <div className="min-h-screen flex items-center justify-center bg-gray-50">
      {children}
    </div>
  );
}

// app/(protected)/layout.tsx — wraps /dashboard, /profile
import { currentUser } from '@clerk/nextjs/server';
import { redirect } from 'next/navigation';

export default async function ProtectedLayout({ children }: { children: React.ReactNode }) {
  const user = await currentUser();
  if (!user) redirect('/sign-in');

  return (
    <div>
      <nav>Protected nav — {user.firstName}</nav>
      {children}
    </div>
  );
}
```

Then any route inside `(protected)/` automatically has auth protection. Any route inside `(auth)/` gets the centered auth layout.

## Nutshell

| Concern | Clerk Solution |
|---|---|
| Sign-in page | `<SignIn />` component (drop-in) |
| Sign-up page | `<SignUp />` component (drop-in) |
| Protect a route (server) | `const user = await currentUser()` → `if (!user) redirect(...)` |
| Auth state (client) | `useUser()` hook → `{ isLoaded, isSignedIn, user }` |
| Sign out | `<SignOutButton />` or `signOut()` |

## Common Mistakes

- ❌ **Using `currentUser()` in a Client Component** — it only works server-side. Use `useUser()` in Client Components.
- ❌ **Importing from `@clerk/nextjs` instead of `@clerk/nextjs/server`** for `currentUser()` — the wrong import causes SSR errors. Remember: `currentUser` is in the `/server` subpath.
- ❌ **Forgetting `isLoaded` check** — Clerk initializes async. Before `isLoaded`, `isSignedIn` is `false`. Always check `isLoaded` first.
- ❌ **Putting protection in middleware only** — middleware is for redirects. The real protection belongs in the layout (`currentUser()` + `redirect()`), just like Auth.js (5.4.3).

## What It Is NOT

- **It is not Auth.js.** The pattern is the same (check user → redirect), but the SDK calls differ. Clerk handles the auth infrastructure as a service.
- **It is not zero-config for customization.** The drop-in components are great, but deep customization requires Clerk's UI components (not covered here).
- **It is not free.** Clerk's free tier supports 1,000 MAUs. Beyond that, it is paid.

## In Your Own Words

1. What is the Clerk equivalent of Auth.js `await auth()`?

<details>
<summary>Sample Answer</summary>

**Answer:** `await currentUser()` from `@clerk/nextjs/server`. It returns the full User object if authenticated, or `null` if not. The pattern is identical: check the return value, redirect if null.

</details>

2. When do you use `useUser()` vs `currentUser()`?

<details>
<summary>Sample Answer</summary>

**Answer:** `currentUser()` is a server-side async function — use it in layouts, pages, or route handlers (Server Components). `useUser()` is a client-side hook — use it in Client Components (`'use client'`) to react to auth state changes in the browser.

</details>

3. What is a route group, and why use it with Clerk?

<details>
<summary>Sample Answer</summary>

**Answer:** A route group `(protected)` or `(auth)` is a way to group routes with shared layouts — the parentheses are not part of the URL. You can put auth protection in `(protected)/layout.tsx` so every route inside automatically checks `currentUser()`.

</details>

4. Why must you check `isLoaded` before `isSignedIn` in `useUser()`?

<details>
<summary>Sample Answer</summary>

**Answer:** Clerk's SDK initializes asynchronously. Before it loads, `isSignedIn` is `false` — not because there's no session, but because Clerk hasn't checked yet. Checking `isLoaded` first prevents showing the "Sign In" screen briefly before the real auth state is known.

</details>
