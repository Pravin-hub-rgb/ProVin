# Auth.js — The Authentication Library

## Where We Left Off

5.1–5.2 built auth by hand — `bcryptjs`, a `users.json` layer, login/register actions, a session cookie set with the right attributes, a `getSession()` reader, a protected layout, and logout. It works, and it taught the internal parts. But the roadmap called it "for understanding only." Now we reach for a real library: **Auth.js** (the Auth.js v6 successor to NextAuth), which absorbs the pieces we just wrote by hand into a thin configuration.

## Auth.js in One Paragraph

Auth.js is an authentication/authorization library for Next.js. Give it:

- which providers to allow (GitHub, Google, email/password, etc.),
- where the session should live (JWT by default),
- and where sign-in/sign-out live,

and it hands back a complete, secure system: sign-in flows, session tokens, cookie management (`httpOnly`, `secure`, `sameSite` all handled), and helpers (`signIn`, `signOut`, `auth`, `handlers`). Where the manual version needed hundreds of lines of hashing, cookie, and protection code, Auth.js needs a config file and a couple of helper calls.

Auth.js supports two families of auth:

- OAuth providers (GitHub, Google, etc.) — "Sign in with GitHub."
- Credentials (email/password) — the same flow we built manually, but handled by the library.

We use GitHub OAuth, because that is the "real external setup" experience and the one in tutorials. (The credentials flow is mechanically parallel; 5.3.4 compares them.)

## OAuth — Why "Sign in with GitHub" Needs No Password From Your App

Before the library, the **concept**. OAuth's core idea: **the application does not need the user's password.** The password lives only between the identity provider (GitHub) and the user. The app receives a **token** — granted by the user — and uses it to fetch the user's profile. That token, not a password, is how the app recognizes the user.

"OAuth" literally stands for **Open Authorization** — open standard (anyone can implement it), authorization-focused (the token grants access to specific resources). Login verification happens inside the flow; the name just reflects the grant, not the identity proof.

Three parties: the identity provider (GitHub, which knows the user), the application (your site, which must not see the password), and the user. The dance:

1. User clicks "Sign in with GitHub" in your app.
2. Your app redirects the user to GitHub.
3. The user logs into GitHub and approves.
4. GitHub redirects the user back to your app, **with an authorization code**.
5. Your app exchanges that code (server-to-server) for an **access token**.
6. Your app uses the access token to fetch the user's profile.
7. Your app creates a session and signs the user in.

**Crucial:** through this whole flow your application never sees the user's GitHub password. It only sees a short-lived token. That is precisely why OAuth removes the password-storage problem entirely.

## Two Different Tokens (The Common Confusion)

This is where people get tangled, so it is stated explicitly. Two things are called "token," and they do different jobs:

- **GitHub's access token.** Obtained during the callback (step 5). Used **once**, to fetch the profile, then discarded. It never leaves your server, and never rides along on subsequent requests. It is GitHub ⇄ your app only.
- **Auth.js session token** (a JWT). Created **after** login. Stored in a cookie (`authjs.session-token`) that the **browser sends on every request**. This is the thing that says "I am logged in" on each page load. It is your app ⇄ the browser.

The access token is ephemeral and internal. The session JWT is the user's persistent identity for your app. Auth.js, by default, uses JWT strategy for sessions (covered in 5.3.2), which is why there is no server-side session store to query.

## Installing and Configuring

```bash
npm install next-auth@beta
```

> Use `@beta` — that tracks Auth.js v6, which targets Next.js 16. Stable tags lag.

### The environment variables

Auth.js is driven by convention-based env vars:

```
AUTH_SECRET=<generated-random-secret>                    # signs the session JWT
AUTH_GITHUB_ID=<github-oauth-app-client-id>
AUTH_GITHUB_SECRET=<github-oauth-app-client-secret>
```

Generate the signing secret with:

```bash
npx auth secret     # writes into .env.local for you
```

Then create a **GitHub OAuth App** (Settings → Developer settings → OAuth Apps → New). Required fields: application name (anything), homepage URL (`http://localhost:3000`), and the **callback URL** — exactly:

```
http://localhost:3000/api/auth/callback/github
```

After registering, GitHub gives a Client ID and reveals a Client Secret **once** — copy both into `.env.local`.

### The config file — `auth.ts` at the project root

```ts
import NextAuth from "next-auth";
import GitHub from "next-auth/providers/github";

export const { handlers, signIn, signOut, auth, updateSession } = NextAuth({
  providers: [GitHub],
  secret: process.env.AUTH_SECRET,
  session: { strategy: "jwt" },
});
```

The named exports are what the rest of the app uses:

| Export | Purpose |
|---|---|
| `handlers` | HTTP handlers for the route handler (next step) |
| `signIn` | Starts a sign-in flow |
| `signOut` | Ends the session |
| `auth` | Reads the current session |
| `updateSession` | Refreshes session data |

### The route handler — `app/api/auth/[...nextauth]/route.ts`

```ts
import { handlers } from "@/auth";

export const { GET, POST } = handlers;
```

`[...nextauth]` is a catch-all dynamic route (Batch 1). It serves `/api/auth/signin`, `/api/auth/callback/github`, `/api/auth/session`, `/api/auth/signout`, and more — all from one file. Note that this file lives under `app/api/auth/`, so it must **not** be confused with a proxy file.

## What It Is NOT

- **Auth.js is not only OAuth.** It also supports credentials (email/password). We use GitHub because it is the clearest external demo.
- **`auth()` is not a proxy.** It is a server-side helper that reads and verifies the session. It does not sit in front of every request.
- **OAuth does not mean "passwords are optional forever."** OAuth delegates password handling to the provider. If you use credentials auth, you still hash passwords (Auth.js can do it, or you bring your own).
- **Auth.js handles authentication, not authorization.** It tells you *who* the user is. Whether that user may access `/dashboard` vs `/admin/settings` is still decided by your own route guards.

## Common Mistakes

- **Wrong callback URL.** GitHub rejects redirects to anything other than the registered URL. On `localhost`, that is `http://localhost:3000/api/auth/callback/github`. A port change (e.g., 3001) means updating GitHub's app settings too.
- **`.env.local` added without a server restart.** Environment variables are read at process start. Always restart `npm run dev` after editing `.env.local`.
- **Reusing one OAuth app across environments.** A production app needs a separate GitHub OAuth App (different callback URLs). Treat dev/staging/prod as separate registrations.
- **Forgetting `secret`.** Without `AUTH_SECRET`, sessions cannot be signed — they fail or are insecure. `npx auth secret` writes it for you.
- **Putting the Client Secret in code or committing `.env.local`.** The secret is a credential; if leaked, anyone can impersonate the OAuth app.

## Nutshell

Auth.js is the recommended auth library for Next.js. Install `next-auth@beta`, set `AUTH_SECRET`, `AUTH_GITHUB_ID`, and `AUTH_GITHUB_SECRET`, register a GitHub OAuth App with callback `http://localhost:3000/api/auth/callback/github`, write a root `auth.ts` config, and add the route handler `app/api/auth/[...nextauth]/route.ts`. It replaces the hand-written hashing, cookie, and session code with `signIn`, `signOut`, and `auth` — and, critically, absorbs the security details we had to handle manually (cookie attributes, token signing, expiry). OAuth itself is a provider concern: the app never sees the user's password, only a token that proves who they are.

<summary>1. In one sentence, why reach for Auth.js instead of the manual version we wrote?</summary>

**Sample Answer:** Auth.js absorbs the security-critical, easy-to-get-wrong parts — password hashing, session storage, signed cookies, expiry, OAuth flow — into a configured library, so you ship correct auth without being the expert on every detail.

</details>

<details>
<summary>2. Why does your app never learn the user's GitHub password during OAuth?</summary>

**Sample Answer:** The OAuth flow never routes the password through your app. The user authenticates directly with GitHub; your app receives back an authorization code, which it exchanges (server-to-server) for an access token. The password stays between GitHub and the user. Your app only ever sees the token.

</details>

<details>
<summary>3. What is the difference between the GitHub access token and the session JWT?</summary>

**Sample Answer:** The GitHub access token is obtained once at sign-in (for fetching profile data) and discarded — it never travels on subsequent requests. The session JWT is created by Auth.js after sign-in, stored in a cookie, and sent by the browser on every request as proof of identity. One is ephemeral and internal; the other is the persistent identity.

</details>

<details>
<summary>summary>4. What would happen if the callback URL registered at GitHub did not match the app's own callback route?</summary>

**Sample Answer:** GitHub would refuse to redirect the user back, breaking the "return from GitHub" stage of the flow. The user would be stuck on GitHub (or see an error), and the authorization code would never arrive at your app — so no session would ever be created.

</details>

<details>
<summary>5. What do the named exports from `auth.ts` each provide to the app?</summary>

**Sample Answer:** `handlers` becomes the route-handler pair (`GET`, `POST`) for `/api/auth/[...nextauth]`. `signIn` starts a provider flow. `signOut` ends the session. `auth` is the server-side session reader. `updateSession` refreshes session data. Together they are the entire public surface the rest of the app needs.

</details>
