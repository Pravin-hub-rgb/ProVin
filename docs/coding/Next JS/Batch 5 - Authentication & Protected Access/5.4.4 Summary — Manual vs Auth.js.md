# Summary — Manual vs Auth.js

## Where We Left Off

In 5.4.1 we built Login Demo v2 end-to-end with Auth.js + GitHub OAuth, and in 5.4.2 and 5.4.3 we saw how sessions flow (server `auth()`, client `useSession()`) and how routes are protected (layout `auth()` + redirect, plus proxy routing). In 4.x we built Login Demo v1 by hand: bcryptjs hashing, a `users.json` file, manually-set/read session cookies, protected layout, and logout.

**Same goal, two paths.** That's exactly the "Manual → Better" pairing from 5.0 — build it once by hand to learn what each piece is for, then see the library do the same thing so every config option stops looking like magic. Now we step back and compare the two side by side, and decide **when to use which**.

## Recap — What Both Versions Built

| | Login Demo v1 (Manual) | Login Demo v2 (Auth.js) |
|---|---|---|
| **Hashing** | `bcryptjs` yourself | Library handles it (OAuth has no password hashing at all) |
| **Users** | `users.json` file + lookup functions | GitHub holds them (profile fetched during OAuth) |
| **Session cookie** | Set manually with cookie attributes | `authjs.session-token`, set by Auth.js |
| **Session read** | Custom `getSession()` | `auth()` on the server / `useSession()` on the client |
| **Login page** | Email/password form | "Sign in with GitHub" button |
| **Protection** | Layout check + redirect | Layout check + redirect + proxy routing |
| **Logout** | `cookies().delete()` | `signOut()` |

Both accomplish the same surface job — authenticating a user — but one was written line by line, the other delegated to a library.

## What's New in Auth.js — The Extra Pieces

| Capability | v1 (manual) | v2 (Auth.js) — new |
|---|---|---|
| **OAuth flow** | None | GitHub redirect → approval → callback → token → profile |
| **External setup** | None | GitHub OAuth App, Client ID/Secret, callback URL |
| **JWT session** | Plain session id in cookie | Signed JWT in cookie |
| **Proxy routing** | None | `proxy.ts` — redirect a signed-in user away from `/login` |
| **Client session** | Server-read only | `SessionProvider` + `useSession()` — for interactive navbar UX |

## Manual vs Auth.js — When to Use Which

| Situation | Choose | Why |
|---|---|---|
| Learning — "what actually happens inside login" | **Manual** | Libraries hide the internals; here you see every step. |
| Any production application | **Auth.js** (or another established library) | Security edge cases are hard; libraries have already solved them. |
| App needs external login ("Sign in with Google/GitHub") | **Auth.js + OAuth provider** | No password system to build or maintain. |
| App needs email/password accounts of its own | **Auth.js + Credentials** | Library handles session/safety; you only store users. |
| Routing-level redirects only | **`proxy.ts`** | Runs before render, as a single interception point. |
| Route security | **Layout/Server Component `auth()`** | Bypass-proof — the official guidance since CVE-2025-29927. |

### OAuth vs Credentials — The Other Decision

- **OAuth** — users never manage a password, and the app never stores or secures one. "Sign in with Google/GitHub" is a ~5-minute setup, with the entire security burden on the provider.
- **Credentials** — the app owns its own accounts (email + password). Even then, you don't roll your own: use a library with `bcryptjs`-style hashing and proper session handling. You store only the user record; the library owns the safe parts.

Both are legitimate choices — **the app's requirements pick the winner, not "which is better."**

## JWT vs Server Session — The Trade-off Now Clear

Back in 5.1 we previewed the session pattern, and in 5.4 we met JWT properly (the problem it solves — lookup — through to its structure). Now the trade-off is concrete:

| | Server Session (from 5.3) | JWT (Auth.js default) |
|---|---|---|
| **Where data lives** | A server-side record | Inside the signed token |
| **Per request** | Record lookup | Signature verification (fast) |
| **Logout / revoke** | Immediate — delete the record | Token stays valid until expiry |
| **Sensitive data** | Safe on the server | Visible in the token (signed, not encrypted) |
| **Use when** | Immediate revocation matters | Statelessness and scalability matter |

### "Token" Means Two Different Things

One confusion from 5.4 that paid off here: a **token** is not one thing.

- **GitHub's access token** — issued once, during the OAuth callback, used only to fetch the profile, then discarded. It never touches the browser.
- **Auth.js's session JWT** (`authjs.session-token` cookie) — issued after login, sent by the browser on every request, and that is what represents the user's identity.

They're not interchangeable: the access token is GitHub↔app; the session JWT is browser↔app.

> Auth.js supports both session strategies: `session.strategy: "jwt"` (default) or `"database"` (server-side records). The "database" strategy appears later in this batch. For now, JWT is the right default.

## What It Is NOT

- **"Manual was bad and Auth.js is the best."** Manual wasn't the wrong answer — it delivered the "why" that makes Auth.js's options (`httpOnly`, `strategy`, `pages`) meaningful rather than magical. The "Manual → Better" pairing from 5.0 remains the right framing.
- **Auth.js as a security guarantee.** It provides **authentication** (who you are); **authorization** (what you're allowed to do) is still the app's responsibility — the layout `auth()` check from 5.4.3 was hand-written.
- **"OAuth is automatically more secure."** OAuth is an option, not a guarantee. Credentials can be secure too, when built on a library with proper hashing/sessions.
- **JWT meaning "no server."** A JWT still lives in a cookie and is still verified by the server. The difference is *record lookup* versus *signature verification* — not client-side-only.

## Nutshell

Batch 5's core: auth's **why** came from the manual build (HTTP statelessness, what cookies actually are and why `httpOnly`/`secure`/`sameSite` matter, the session pattern and why, hashing and why it's one-way with a salt, why protection lives in a layout and not the proxy, and after CVE-2025-29927 why auth enforcement does *not* go in `proxy.ts`). Auth.js's **how** delivers all of that ready-made — OAuth flow, JWT, `auth()`/`useSession()`, and proxy routing. Understanding the "why" is what makes configuring the "how" intentional instead of guesswork. Decision guide: learning → manual; production → Auth.js; external login → OAuth provider; app-owned accounts → Credentials; route security → layout `auth()`; routing redirects → `proxy.ts`.

## In Your Own Words

<details>
<summary>1. Someone asks, "How do I build a login?" — which three questions do you ask to point them at the right approach?</summary>

**Sample Answer:** First: "Is this for learning, or for production?" — production means Auth.js. Second: "Do users need their own app email/passwords, or is signing in with Google/GitHub acceptable?" — external is fine means an OAuth provider; app-owned accounts means Credentials. Third: "Do you need session revocation to be immediate?" — yes means a server session, no means JWT. Those three questions resolve almost every decision.

</details>

<details>
<summary>2. OAuth vs Credentials — which situation calls for which, and how can both be "correct"?</summary>

**Sample Answer:** OAuth when external login is acceptable — users don't manage a password, the app never stores or secures one, and the burden sits on the provider. Credentials when the app needs its own accounts internally (an internal tool, for instance). Both are correct because the choice comes from requirements: "how will users sign in" is decided by the app's nature, not by one being universally better.

</details>

<details>
<summary>3. What's the trade-off between JWT and a server session, and why does logout expose the difference?</summary>

**Sample Answer:** A server session stores data in a server record and looks up the session id on each request; a JWT stores data inside a signed token and verifies the signature on each request. Logout reveals it: deleting the server record invalidates the session immediately, while JWT logout only clears the client cookie — a token that's leaked or replayed stays valid until it expires. So if immediate revocation matters, server session wins; if statelessness and per-request speed matter, JWT wins.

</details>

<details>
<summary>4. "Auth.js did the authentication, but authorization is still your job" — what does that mean, and give an example from 5.4.3.</summary>

**Sample Answer:** Authentication is "who are you?" — Auth.js answers that via GitHub login and session verification. Authorization is "what are you allowed to do?" — that's still the app's code. From 5.4.3, `dashboard/layout.tsx` is the example: `auth()` returns the session (authentication happened), but the decision "a signed-out user hitting `/dashboard` gets sent to `/login`" is a rule we wrote by hand. Auth.js never knows which routes are protected — that policy lives in your code.

</details>

<details>
<summary>5. Summarize this batch's 5.1–5.4.3 in one "why → how" sentence.</summary>

**Sample Answer:** 5.1–5.3 deliver the **why**: HTTP statelessness, what a cookie actually is and why `httpOnly`/`secure`/`sameSite` matter, the session pattern and why, hashing and why it's one-way with a salt, why protection lives in the layout and not the proxy, and after CVE-2025-29927 why auth enforcement does *not* go in `proxy.ts`. 5.4.x delivers the **how**: Auth.js builds all of that for you — OAuth, JWT, `auth()`/`useSession()`, proxy routing. Knowing the "why" makes configuring the "how" intentional instead of magical, so you reach for Manual when learning and Auth.js when shipping.

</details>
