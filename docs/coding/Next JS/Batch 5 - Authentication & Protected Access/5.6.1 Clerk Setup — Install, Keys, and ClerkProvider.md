# Clerk Setup — Install, Keys, and ClerkProvider (5.6.1)

## Where We Left Off

In 5.6 we learned what Clerk is — a fully managed auth platform — and why teams choose it over self-hosted Auth.js. Now, let's set it up from scratch.

## Broader Goal

By the end of this file, you will have:
- Installed `@clerk/nextjs`
- Configured environment variables (publishable + secret keys)

## Manual → Better

| Approach | Steps |
|---|---|
| Manual (5.1–5.3) | `npm install bcryptjs`, create `/api/auth/login`, `/api/auth/register`, set cookies, build `getSession()` — all by hand |
| Auth.js (5.4) | `npm install @auth/sveltekit`, export `handlers` as `/api/auth/[...all]/route.ts`, configure providers |
| Clerk | `npm install @clerk/nextjs`, paste 2 keys in `.env.local`, wrap app in `<ClerkProvider>` |

## Step 1 — Install the Package

```bash
npm install @clerk/nextjs
```

Clerk's Next.js SDK is a single package — no separate auth server, no `next-auth` config file. Everything is handled client-side + server-side by the SDK.

## Step 2 — Get Your Keys from the Clerk Dashboard

Sign up at [clerk.com](https://clerk.com) and create an application. Then go to **API Keys** in the dashboard. You will get two keys:

- **Publishable key** (`pk_test_...`) — safe to expose in client bundles. This is how the browser talks to Clerk.
- **Secret key** (`sk_test_...`) — keep this **server-only**. Never prefix with `NEXT_PUBLIC_`.

Add them to your `.env.local`:

```env
# .env.local — never commit .env to git
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_your_publishable_key_here
CLERK_SECRET_KEY=sk_test_your_secret_key_here
```

> **Critical:** `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` has the `NEXT_PUBLIC_` prefix — it is intentionally exposed to the browser. `CLERK_SECRET_KEY` does **not** — it stays server-only. If you prefix the secret key with `NEXT_PUBLIC_`, it leaks into the client bundle.

## Step 3 — Wrap the App in ClerkProvider

The `ClerkProvider` goes in your **root layout** — it provides auth state to every component in the app, just like `AuthProvider` (5.4) or `SessionProvider`:

```tsx
// app/layout.tsx
import { ClerkProvider } from '@clerk/nextjs';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <ClerkProvider>
      <html lang="en">
        <body>
          {children}
        </body>
      </html>
    </ClerkProvider>
  );
}
```

**Line-by-line:**

- **`ClerkProvider`** — the same pattern as Auth.js's provider (5.4.1) or React's Context Provider. It makes auth state available throughout the component tree.
- The publishable key is read automatically from `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` in your env — no need to pass it as a prop.
- Like `StoreProvider` in Batch 9 (Redux), `ClerkProvider` is a **Client Component** — but the layout itself can still be a Server Component.

## Step 4 — Configure Sign-In / Sign-Up Routes

Clerk needs to know where your sign-in and sign-up pages live. You configure this in the **Clerk Dashboard** under "User & Email" (or via `clerk.config` object). For now, create placeholder routes:

```
app/
├── sign-in/
│   └── [[...sign-in]]/
│       └── page.tsx    →  /sign-in/*  (Clerk's catch-all for multi-step flows)
├── sign-up/
│   └── [[...sign-up]]/
│       └── page.tsx    →  /sign-up/*  (same pattern)
├── (protected)/
│   └── dashboard/
│       └── page.tsx    →  /dashboard  (protected content)
└── api/
    └── [...]
```

> The `[[...sign-in]]` pattern uses a **catch-all segment** (`[[...slug]]`). This is a Next.js convention that catches all URLs starting with `/sign-in/`, including sub-paths like `/sign-in/factor1` (for MFA). You don't need to understand the internals — just name the folder this way and Clerk handles the rest.

## Verify the Setup

Run `npm run dev` and visit any page. You should see no errors — `ClerkProvider` initialized successfully. The provider is now wrapping your app, but no routes are protected yet. In 5.6.2, we will add the sign-in/sign-up components and protect the dashboard.

## Common Mistakes

- ❌ **Forgetting `NEXT_PUBLIC_` on the publishable key** — the browser can't initialize without it.
- ❌ **Prefixing the secret key with `NEXT_PUBLIC_`** — this leaks `CLERK_SECRET_KEY` into the client bundle. Security disaster.
- ❌ **Putting `ClerkProvider` in `page.tsx`** instead of `layout.tsx` — routes outside `/sign-in` won't have auth context.
- ❌ **Not creating the catch-all route** — `[[...sign-in]]` — Clerk's multi-step flows (MFA, password reset) won't work without it.

## What It Is NOT

- **It is not configuration-complete yet.** This file only sets up the provider. Sign-in/sign-up UI and route protection come next in 5.6.2.
- **It is not self-hosted.** The keys connect to Clerk's servers, not your own. Your app talks to Clerk's API, not a local auth database.

## In Your Own Words

1. Why does `CLERK_SECRET_KEY` NOT have the `NEXT_PUBLIC_` prefix?

<details>
<summary>Sample Answer</summary>

**Answer:** `NEXT_PUBLIC_` variables are exposed to the browser. The secret key must stay server-only — it would let anyone impersonate your Clerk backend if leaked. The publishable key (`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`) is safe to expose because Clerk designed it only for client initialization.

</details>

2. Where should `ClerkProvider` go — `layout.tsx` or `page.tsx`?

<details>
<summary>Sample Answer</summary>

**Answer:** In `app/layout.tsx` — the root layout. This wraps every route in the app with auth context. If you put it in a single `page.tsx`, only that route's tree gets auth.

</details>

3. What does `[[...sign-in]]` mean?

<details>
<summary>Sample Answer</summary>

**Answer:** It's a catch-all dynamic segment. The `[[...sign-in]]` folder catches all URLs starting with `/sign-in/`, including sub-paths like `/sign-in/factor1` for MFA setup. This lets Clerk handle multi-step auth flows without you defining each sub-route manually.

</details>
