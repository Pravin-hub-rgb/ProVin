# Cookies & Sessions — Authentication's Foundation

## Where We Left Off

5.0 opened the central question: HTTP is stateless, so after login the server forgets who you are between requests. The answer is **cookies and sessions.** Before any login code, we settle the concept: what a cookie is, how it travels, and where its safety comes from.

When the server recognizes you (e.g., after login), it sends a small piece of data to the browser via the `Set-Cookie` response header. The browser stores it and sends it back on _every subsequent request_, until the site remembers you again. This file covers that mechanism end to end, plus the `httpOnly`, `secure`, and `sameSite` attributes that make session cookies safe.

## The Problem — HTTP Has No Memory

HTTP's core design is that every request is **independent**. When you call `GET /reviews`, the server has no idea you also called `GET /products` five minutes earlier. The server treats each request like a new stranger.

This is the property called **stateless** — there is no request-to-request memory. HTTP treats every request as self-contained, carrying no prior context.

But applications need state — being "logged in" is literally a state. So the real question becomes: _how do you remember identity in a stateless world?_ The cookie answers that.

## Cookie — A Tiny Piece of Data

A **cookie** is a small piece of data that the **server gives to the browser, and the browser stores and returns on every later request** — but only to the site that set it.

The flow, step by step:

1. First request — the server responds with: `Set-Cookie: remember_me=yes` (a response header).
2. The browser **stores** the cookie.
3. On every later request, the browser automatically sends: `Cookie: remember_me=yes`.
4. The server reads it and knows: "ah, this is the same person."

```
Browser                          Server
   │ 1. GET /page                   │
   │ ──────────────────────────→    │
   │                                │← 2. "Set-Cookie: remember_me=yes"
   │ ←──────────────────────────    │
   │ 3. cookie stored                │
   │ 4. GET /page (Cookie: remember_me=yes)
   │ ──────────────────────────→    │← 5. "yep, same person"
```

Cookies are **domain-scoped** — YouTube's cookies go to YouTube, not Instagram. The browser only returns a cookie to the site that originally set it.

## Cookie Attributes — Why They Matter

When setting a cookie you can also attach **attributes** — safety settings. Three matter for sessions:

### httpOnly

With `httpOnly`, the **browser's JavaScript cannot read the cookie** — only the server can.

Why? If a cookie is readable by JavaScript, a cross-site scripting (XSS) attack (an attacker's script running on your page) can steal it. `httpOnly` means the script cannot read the cookie — theft fails. **Session cookies must always be `httpOnly`.** Rule.

### secure

With `secure`, the cookie is sent **over HTTPS only**, never plain HTTP. Over HTTP data travels unencoded, so anyone on the network can read it. HTTPS keeps it scrambled. Sessions should set `secure` in production.

### sameSite

With `sameSite`, the cookie is sent **only on same-site requests**, never cross-site. Why care? The classic **CSRF** attack: you are logged into one tab, a malicious site in another tries to submit a "change password" request with your cookie attached. `sameSite: "lax"` prevents the cookie riding along on cross-site requests, breaking the attack.

### expires / maxAge

How long the cookie lives — for the browser session, or for a fixed duration (`expires`). Login uses `maxAge` to grant "remember me for 7 days."

One thing stands out: `httpOnly`, `secure`, and `sameSite` require **no extra library**. They are just attributes sent when the cookie is created. That ease is also the danger — it is trivial to forget them. The mindset should be: session cookies get these three by default.

## Sessions — The Record on the Server

Here is the question every student hits: if cookies live in the browser, why not just put `"loggedIn: true, user: Pravin"` in the cookie?

**Because the user can edit their own cookies.** Open DevTools and change `loggedIn` to `true`, or `user` to `admin`. The server will believe it. Storing real data in a cookie is the #1 session mistake — never store user-editable data in a cookie.

The correct approach is the **session** pattern:

- **Cookie holds only a random session ID** — an arbitrary token with no meaning of its own.
- The **server keeps the real mapping** — session ID → user, with an expiry.
- On each request, the server reads the ID from the cookie and looks it up in its record.

Since the cookie only contains a meaningless random ID, the user cannot forge a session by editing it — they would have to guess the random ID (and each ID is unguessable). And session IDs expire, so even a stolen ID has a shelf life.

The full flow:

```
1. User submits the login form (email + password).
2. Server verifies email and password — they are correct.
3. Server creates an entry in its session store: sessionId → userId.
4. Server sends the browser a cookie: "sessionId=abc123" (with httpOnly + secure + sameSite).
5. On every later request, the browser sends that cookie.
6. The server reads the sessionId and looks it up in its store — identity restored.
7. On logout: delete the cookie **and** delete the server-side record — the session is over.
```

## JWT — The Session Alternative (Preview)

The session pattern above has a cost: the server must **look something up on every request** ("session `abc123` — which user?"). For a small app that lookup against a file or in-memory map is fine. For high-scale apps with millions of users, that lookup is a database hit on every request — slow.

The alternative is **JWT (JSON Web Token)** — the session data is stored **inside a signed token** instead of in a server-side record. The server doesn't look anything up; it just verifies the signature. Auth.js uses JWT by default. We will see that structure in 5.3.3; for now, the core contrast is enough: sessions store identity on the server and key the lookup by cookie ID; JWTs store identity in the token itself, signed so it cannot be forged.

## Cookies and Sessions — Two Halves of One System

One frequent confusion: "cookie is client-side, session is server-side." Partially right, but incomplete. Cookies are correct that they **live in the browser** — that part is true. But the cookie is **set by the server** (via `Set-Cookie`), and the browser only **holds onto it** and **returns it to the server** on each request. So the cookie lives on the client, but its purpose is server-side communication — it carries the session ID to the server.

The **session is server-side state** — the mapping of session ID to user data lives on the server. But the session's identity — the random ID itself — **travels in a cookie** on the client.

So cookies and sessions are not two different things on two sides — they are **two halves of one system.** The cookie is the transport that carries the session ID. The session is the record that gives that ID meaning. Without the cookie the server never learns who the request is from. Without the session store the cookie is just a random string with no meaning.

## What It Is NOT

- **A cookie is not `localStorage`.** Both store data in the browser, but only cookies are **automatically returned on every request**; `localStorage` data sits in the browser and must be sent manually. And `localStorage` is always readable by JavaScript, whereas a cookie with `httpOnly` is not. For auth, `httpOnly` cookies are safer; `localStorage` is exposed.
- **`httpOnly` and `secure` are not substitutes.** `httpOnly` shields from JavaScript (XSS); `secure` shields from network sniffing (HTTP). They defend against different attacks; both are needed.
- **Cookies are not only for auth.** Preferences (theme, language, cart) live in cookies too. Sessions are the most security-critical user, which is why they get the full attribute treatment.

## Using Cookies in Next.js — `cookies()`

In Next.js, cookie access is through a function, `cookies()`, imported from `next/headers`. **In Next 15+ it is async**, so you write `await cookies()` — the old synchronous `cookies().get()` no longer compiles.

We only need to know that here. We set cookies by hand in 5.1, and we see when reading vs writing is allowed. The key rule: **only Server Actions and Route Handlers may write** cookies; Server Components may only read. The reason shows up in 5.1 — writing mutates the response, which only a Server Action (running server-side, on a form submission) is allowed to do.

## Nutshell

A cookie is data the server places in the browser; the browser returns it on every later request to that site. HTTP is stateless; cookies are how state survives between requests. In the session pattern, the cookie holds **only a random session ID**, while the server holds the real mapping (ID → user). Passwords and user records never live in the cookie. The `httpOnly`, `secure`, and `sameSite` attributes defend against XSS, network sniffing, and CSRF respectively.

## In Your Own Words

<details>
<summary>1. HTTP is stateless — how does a cookie fix that?</summary>

**Sample Answer:** HTTP treats every request as independent — the server has no built-in memory that "this request came from the same person as the last." A cookie is the fix: the server gives the browser a token, the browser stores it, and returns it on every later request. The server reads that token and recognizes the person. Stateless protocol, stateful experience — via the cookie.

</details>

<details>
<summary>2. Why store only a random session ID in the cookie, not the user's actual data?</summary>

**Sample Answer:** Because cookies live in the browser, where the user is in full control. A user can open DevTools and change any cookie value. If the cookie said `loggedIn: true, user: admin`, the user could flip it themselves and the server would have to trust it. A random session ID is meaningless on its own — the user might set it to `abc`, but the server looks `abc` up in its own store and finds nothing. The real data stays on the server, referenced by an unguessable key.

</details>

<details>
<summary>3. What does each attribute protect against — one line each?</summary>

**Sample Answer:** `httpOnly` stops JavaScript from reading the cookie (defeats XSS theft). `secure` ensures the cookie only travels over HTTPS (defeats network sniffing). `sameSite: "lax"` stops the cookie being sent on cross-site requests (defeats CSRF). Three different attacks, three different attributes.

</details>

<details>
<summary>4. Cookie vs localStorage — why is a cookie the right tool for sessions?</summary>

**Sample Answer:** Two reasons. First, cookies are returned **automatically** on every request — `localStorage` data stays in the browser and must be attached to requests manually. Second, cookies can be `httpOnly` (invisible to JavaScript), whereas `localStorage` is always readable by any script — including an attacker's via XSS. Automatic transmission + script-invisibility is exactly what a session needs.

</details>

<details>
<summary>5. If a session cookie is not `httpOnly`, what is the concrete risk?</summary>

**Sample Answer:** Any XSS vulnerability on the site (an attacker's script executing on your page) could read the cookie via `document.cookie` and exfiltrate it. If that cookie is the session token, the attacker now has the victim's session — account takeover without stealing a password. That is why session cookies must be `httpOnly`: they must never be readable from JavaScript.

</details>
