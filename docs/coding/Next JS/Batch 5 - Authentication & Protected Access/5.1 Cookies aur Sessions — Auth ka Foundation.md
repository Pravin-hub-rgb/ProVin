In 5.0 we left a question: after you log in, how does the site remember who you are, when HTTP forgets everything on every request? The answer is the **cookie** — a tiny piece of data that the **server sends to the browser, and the browser stores and sends back with every subsequent request, but only to that same site.** Today we will understand what that data is, how it travels, and where the safety comes from.

When the server knows who you are — like after a login — it sends that data to the browser via the `Set-Cookie` header. The browser stores it and sends it back on future requests via the `Cookie` header. Let's break down that mechanism step by step.

# Cookies and Sessions — Authentication's Foundation

## Problem — HTTP Has No Memory

HTTP's fundamental design is this: **every request is independent.** When you visit `GET /reviews`, the server has no idea that you are the same person who sent `GET /products` five minutes earlier. The server treats each request like a stranger.

This problem is called **stateless** — the server has no memory (no state) between requests. HTTP treats every request as complete on its own, carrying no context from previous ones.

But apps need state — "logged in" is state. So the question is: *how do you maintain identity without memory?* The answer comes from cookies.

## What Is a Cookie — A Tiny Piece of Data

**A cookie** is a small piece of data that the **server sends to the browser, and the browser stores and sends back with every subsequent request — but only to the same site that set it.**

Here is how it works, step by step:

1. On the first request, the server says: "Set-Cookie: `remember_me=yes`" (in the response header)
2. The browser **stores** that cookie
3. On every following request, the browser automatically sends: "Cookie: `remember_me=yes`"
4. The server reads the request and understands — "yes, this is the same person"

```
Browser                          Server
   │ 1. GET /page                   │
   │ ──────────────────────────→    │
   │                                │← 2. "Set-Cookie: remember_me=yes"
   │ ←──────────────────────────    │
   │ 3. cookie stored               │
   │ 4. GET /page (Cookie: remember_me=yes)
   │ ──────────────────────────→    │← 5. "yes, it's the same person"
```

A cookie is **domain-specific** — YouTube's cookie goes only to YouTube, not Instagram. The browser sends cookies only to the site that set them.

## Cookie Attributes — Why They Matter

When you set a cookie, you can attach **attributes** — safety settings. Each has its own job, and for auth, three are critical:

### httpOnly

The `httpOnly` attribute means: **the browser's JavaScript cannot see this cookie.** Only the server can read it; the page's JavaScript cannot.

Why? Because if a cookie is readable by JavaScript, any XSS attack (a hacker's script running on your page) can steal the cookie via `document.cookie`. With `httpOnly`, that theft is impossible — the script never has access to the cookie at all. **Session cookies should always be `httpOnly`.** This is a rule.

### secure

The `secure` attribute means: **the cookie is sent only over HTTPS connections**, not plain HTTP. Because on HTTP, data travels unencrypted — anyone on the network can read it. On HTTPS, the data is scrambled so it can't be intercepted.

### sameSite

The `sameSite` attribute means: **the cookie is sent only with requests from the same site** — not from a different site making a cross-site request.

Why? There is a classic attack called **CSRF**: you have a tab open where you're logged into YouTube, and on another tab a malicious site silently sends a "change password" request with your YouTube cookie attached. With `sameSite: "lax"`, that cross-site request won't carry the cookie — the attack fails.

### expires / maxAge

How long the cookie lives — either until the browser closes (`session` cookie) or until a set time (`expires`). For login, a `maxAge` of 7 days gives the "log in for 7 days" experience.

One thing to notice — `httpOnly`, `secure`, `sameSite` are not extra libraries. They are attributes you set on the cookie. But they are easy to forget — so treat these three as a default mindset for session cookies.

## Sessions — The Server Keeps the Record

Now the key question: what do you **store** in the cookie? The tempting shortcut: put "user: pravin, loggedIn: true" right in there. But that is dangerous — the cookie is in the browser, and the user can edit their own cookies! Open DevTools, change "loggedIn: true" to "role: admin" — and the server might just believe it. **Never store trusted user data in the cookie.**

The correct approach is the **session** pattern:

- Store only a **random session ID** in the cookie — a meaningless string with no inherent value
- Keep a **record** on the server — a mapping of session ID to user: "id `abc123` = user Pravin, expires in 7 days"
- When a request comes in, the server extracts the ID from the cookie and looks it up in its own record — "this ID maps to this user"

Because only a random ID is in the cookie, the user can edit their cookie all they want but they can't forge user data — the ID has no meaning on its own. And the ID is **random** so it can't be guessed, and has an **expiry** so a stolen ID doesn't last forever.

The full session flow, end to end:

```
1. User submits the login form (email + password)
2. Server verifies email/password — correct
3. Server creates a record: sessionId → userId
4. Server sends the browser a cookie: "sessionId=abc123" (httpOnly + secure + sameSite)
5. On every subsequent request, the browser sends this cookie
6. Server extracts sessionId from the cookie and checks its record — user found
7. On logout: delete the cookie + delete the server-side record — the request is unauthenticated again
```

## JWT — The Other Session Pattern (Preview)

The record-lookup pattern has a downside: **the server must look up the record on every request** ("id `abc123` — which user is that?" — a database hit). Fine for small apps, but in production with hundreds of thousands of users, that hit on every request is **slow**.

The alternative is **JWT (JSON Web Token)** — where the session data is **digitally signed and packed inside the token itself**, with no server-side record. The server doesn't need to look anything up — **the token is the proof.** We are not using JWT in 5.2–5.3 (we'll build the record-based pattern by hand) — but Auth.js in 5.4 uses JWT by default, so it will appear in detail there. For now: the session pattern does a lookup; JWT packs everything into a signed token.

## Cookie vs Session — Two Parts of One System

A common confusion: "cookies are client-side, sessions are server-side." That is half true, but incomplete. Here is the accurate picture: **the cookie lives in the browser (client)** — that part is true. But the cookie is **set by the server** (via the `Set-Cookie` response header), and the browser just stores it and **sends it back to the server** with every request. So the cookie lives on the client, but its purpose is server-side — it carries the session identity from the client back to the server.

**The session is server-side state** — the record mapping session ID to user data lives on the server. But the session's identity — that session ID — **lives in the cookie** in the browser.

So cookies and sessions are not two different sides — **they are two parts of one system.** The cookie is the transport that carries identity back to the server; the session is the user state stored on the server. Without a cookie, the server never knows which request belongs to whom; without a session, the cookie (a random ID) has no meaning of its own. They work together — the ID travels in the cookie and gets its meaning from the session on the server.

## What It Is NOT

- **Cookie ≠ localStorage.** Both store data in the browser, but local storage is **not sent automatically** with every request — only cookies are. And everything in localStorage is readable by JavaScript; a cookie with `httpOnly` can't be read by JS at all. For auth, the `httpOnly` cookie is safe and localStorage is not.
- **httpOnly cookie ≠ secure cookie.** `httpOnly` protects against JavaScript (XSS), `secure` protects against network interception (HTTP sniffing). Two different threats, both need protection.
- **Cookies are not only for auth** — themes, cart contents, language preferences also live in cookies. But auth cookies are the most critical, which is why those safety attributes exist.

## Next.js — The `cookies()` API

In Next.js, the cookies API is a single function — `cookies()` — imported from `next/headers`. **In Next 15+, `cookies()` is async** — you must `await cookies()`; you can't call `cookies().get()` directly.

For now, just know the basics: **in 5.2 we'll set cookies by hand** and see when they can be read and when they can only be written. A preview: only **Server Actions and Route Handlers** can write cookies — Server Components can only read them. We will cover why in 5.2.

## Nutshell

A cookie is a tiny piece of data the server gives the browser, and the browser sends it back on every subsequent request. HTTP is stateless, and the cookie is what makes identity "stick." In the session pattern, the cookie holds only a random ID and the server holds the record — user data never enters the cookie. The `httpOnly`, `secure`, and `sameSite` attributes protect session cookies against XSS, network interception, and CSRF. In Next.js, `cookies()` is async, and writes are allowed only in Server Actions and Route Handlers.

1. Why is HTTP stateless, and how does a cookie solve that?

<details>
<summary>Show Answer</summary>

**Sample Answer:** HTTP treats every request as independent — the server has no built-in memory of "this is the same user who made the earlier request." A cookie solves this: the server gives the browser a token, the browser stores it and sends it back with every subsequent request. The server reads the token and says, "ah yes, this is the same person."

</details>

2. Why store only a random ID in the cookie, not the full user data?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The cookie lives in the browser, under the user's control. A user can open DevTools and edit their own cookies. If the cookie held "loggedIn: true, user: admin," the user could change `role` to admin and the server might trust it. So the cookie holds only a random ID that has no meaning on its own, and the real mapping (ID → user) stays on the server. The ID is random so it can't be guessed.

</details>

3. `httpOnly`, `secure`, `sameSite` — what attack does each prevent, in one sentence?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `httpOnly` keeps JavaScript from reading the cookie, preventing XSS from stealing the session. `secure` ensures the cookie only travels over HTTPS, preventing network interception. `sameSite: "lax"` stops the cookie from being sent on cross-site requests, preventing CSRF. Three different attacks, three different attributes.

</details>

4. Both cookies and localStorage store data in the browser — so why use cookies for auth?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Two reasons. First: cookies are sent automatically with every request — localStorage data is not, you'd have to manually attach it. Second: cookies can be `httpOnly`, meaning JavaScript can't read them; localStorage is always readable by JavaScript, so any XSS script can steal it. For session identity — which the server itself trusts — the `httpOnly` cookie is the right tool.

</details>

5. If a site sets a cookie without `httpOnly`, what is the risk?

<details>
<summary>Show Answer</summary>

**Sample Answer:** If the cookie is readable by JavaScript, any XSS vulnerability on the page — a hacker's code running on your site — can read the cookie with `document.cookie` and exfiltrate it. If it is a session cookie, the attacker now has the session ID and can hijack the account without even knowing the password. Session cookies must always be `httpOnly`.

</details>
