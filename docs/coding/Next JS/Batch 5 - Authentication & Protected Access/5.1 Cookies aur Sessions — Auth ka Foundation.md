4.0 mein maine ek sawaal chhoda tha — site login ke baad tujhe kaise yaad rakhti hai, jabki HTTP har request ke saath sab kuch bhool jaata hai. Iska jawab hai **cookie** — ek chhota sa piece of data jo **server browser ko bhejta hai, aur browser usse yaad rakh kar har aage wali request ke saath wapas bhejta hai.** Aaj hum samjhenge ki woh data kya hai, kaise jaata hai, aur usme **safety** kahan se aati hai.

Jab server tujhe pehchanta hai — jaise login ke baad — woh browser ko `Set-Cookie` header se yeh data bhejta hai. Browser usse store kar leta hai aur aage ki requests mein `Cookie` header ke saath wapas bhejta hai. Yeh mechanism aaj step by step dekhenge.

# Cookies aur Sessions — Auth Ka Foundation

## Problem — HTTP Ko Kuch Yaad Nahi

HTTP protocol ka fundamental design yeh hai: **har request independent hai.** Jab tu `GET /reviews` karta hai, server ko nahi pata ki tu hi woh banda hai jisne 5 minute pehle `GET /products` kiya tha. Server har request ko ek naye ajnabi ki tarah treat karta hai.

Is problem ka naam hai **stateless** — server ke paas request-to-request koi state (yaad) nahi hoti. HTTP har request ko khud mein complete maanta hai, koi pehle ka context carry nahi hota.

Par apps ko state chahiye — "login kiya hua" toh ek state hai hi. Toh problem yeh hai: *bina yaad ke, yaad kaise rakhein?* Iska jawab aata hai cookie se.

## Cookie — Chhota Sa Data

**Cookie** ek chhota sa piece of data hai jo **server browser ko bhejta hai, aur browser usse yaad rakh kar har aage wali request ke saath wapas bhejta hai** — par sirf usi website ko.

Kaise hota hai, step by step:

1. Pehli request pe server bolta hai: "Set-Cookie: `remember_me=yes`" (response header mein)
2. Browser yeh cookie **store** kar leta hai
3. Agli har request pe browser automatically header bhejta hai: "Cookie: `remember_me=yes`"
4. Server request padh ke samajhta hai — "haan, yeh wahi banda hai"

```
Browser                          Server
   │ 1. GET /page                   │
   │ ──────────────────────────→    │
   │                                │← 2. "Set-Cookie: remember_me=yes"
   │ ←──────────────────────────    │
   │ 3. cookie store ho gayi        │
   │ 4. GET /page (Cookie: remember_me=yes)
   │ ──────────────────────────→    │← 5. "haan, yeh wahi hai"
```

Cookie **domain-specific** hoti hai — YouTube ki cookie YouTube ko hi jaati hai, Instagram ko nahi. Matlab browser bhejta hai cookie sirf usi site ko jisne set ki thi.

## Cookie Attributes — Kyun Zaroori

Cookie ko set karte waqt hum uske saath kuch **attributes** bhi bol sakte hain — yeh uski safety settings hain. Har ek ka apna kaam hai, aur auth ke liye teen sabse important hain:

### httpOnly

`httpOnly` attribute ka matlab: **browser ke JavaScript ko yeh cookie dikhti hi nahi.** Sirf server padh sakta hai, page ka JS nahi.

Kyun? Kyunki agar cookie JavaScript se readable hai, toh koi bhi XSS attack (hacker ka script tumhari page pe chala jaye) cookie ko chura kar le ja sakta hai. `httpOnly` cookie ke saath woh chori nahi ho sakti — JS ko cookie milti hi nahi. **Session cookies hamesha `httpOnly` honi chahiye** — yeh rule hai.

### secure

`secure` attribute ka matlab: **cookie sirf HTTPS connection pe bheji jaayegi**, HTTP pe nahi. Kyunki HTTP pe data bina encryption ke travel karta hai — koi bhi beech mein (network pe) cookie padh sakta hai. HTTPS pe woh scramble rehti hai.

### sameSite

`sameSite` attribute ka matlab: **cookie sirf usi site ki requests ke saath bhejo** — doosri site se aayi request ke saath nahi.

Kyun? Ek classic attack hai **CSRF** — tumhara ek tab YouTube pe logged-in hai, doosre tab mein ek bad site hai jo chupchaap "change password" request bhej deti hai tumhari YouTube cookie ke saath. `sameSite: "lax"` se aisi cross-site requests mein cookie nahi jaati — attack fail ho jaata hai.

### expires / maxAge

Cookie kitni der tak yaad rahegi — jab tak browser band ho (`session` cookie), ya ek time ke baad khatam (`expires`). Login ke liye `maxAge` se 7 din jaisi duration dete hain — "log in for 7 days" wala option.

Ek baat notice karo — `httpOnly`, `secure`, `sameSite` koi **extra library nahi** maangte. Ye bas attributes hain jo hum cookie set karte waqt bol dete hain. Lekin inko bhoolna aasaan hai — isliye session cookies ke liye yeh teeno **default mindset** honi chahiye.

## Sessions — Server Pe Record

Ab ek sawaal — cookie mein **kya** rakhein? Seedha solution lagega: cookie mein hi daal do "user: pravin, loggedIn: true." Par yeh dangerous hai — cookie browser ke paas hai, user khud apni cookie edit kar sakta hai! F12 kholo, cookie badlo, "loggedIn: true" bana do — aur server maan jayega. **Kabhi bhi user ka data cookie mein mat rakho.**

Sahi tareeka hai **session** pattern:

- Cookie mein sirf ek **random session id** rakho — ek bekaar sa number, jiska khud koi matlab nahi
- Server ke paas ek **record** ho — session id ka mapping: "id `abc123` = user Pravin, expires 7 din mein"
- Jab request aaye, server cookie se id nikaal ke apne record mein dekhta hai — "yeh id hai toh yeh user hai"

Cookie mein sirf random id hoti hai isliye user apni cookie edit karke data nahi badal sakta (id ka khud koi matlab nahi). Aur id **random** hoti hai taaki koi guess na kar sake, **expiry** wali hoti hai taaki pehchaan hamesha ke liye na ho jaaye.

Session ka poora flow, sab jod ke:

```
1. User login form submit karta hai (email + password)
2. Server email/password verify karta hai — sahi hai
3. Server apne record mein entry banata hai: sessionId → userId
4. Server browser ko cookie bhejta hai: "sessionId=abc123" (httpOnly + secure + sameSite)
5. Ab har request pe browser yeh cookie bhejta hai
6. Server cookie se sessionId nikaal ke apne record mein check karta hai — user mil gaya
7. Logout pe: cookie delete + server-side record delete — ab request phir se unauth hai
```

## JWT — Session Ka Doosra Pattern (Preview)

Ab tak wale session pattern ki ek problem hai — **server ko har request pe record/file mein lookup karna padta hai** ("id `abc123` ka user kaun hai?" — dhoondhna). Chhote app ke liye theek hai, par production mein yeh lookup **database hit** hoti hai — lakhs users, har request pe hit — **slow ho sakta hai.**

Iska doosra pattern hai **JWT (JSON Web Token)** — jisme session ka data **khud token ke andar** digitally signed hota hai, server pe record nahi. Server ko lookup nahi karna padta — **token hi proof hai.** **4.2-4.3 mein yeh use nahi hoga** (wahan record-wala pattern khud banaenge) — par **4.4 mein Auth.js session JWT se hi banata hai**, isliye wahan detail mein dikhega. Ab ke liye itna hi: session pattern lookup karta hai, JWT token ke andar sab rakhta hai. (Full structure + comparison 4.4 ke "JWT Strategy" section aur 4.4.4 ke summary mein milega.)

## Cookie vs Session — Ek Hi System Ke Do Hisse

Ek aam confusion hai — "cookie client side hai, session server side hai." Thoda sahi hai, par incomplete. Sahi baat yeh hai: **cookie browser (client) pe store hoti hai** — yeh sahi hai. Par cookie **server set karta hai** (`Set-Cookie` header ke saath), aur browser sirf usse yaad rakh ke har request ke saath **server ko wapas bhejta hai**. Matlab cookie client pe rehti hai, par uska purpose server ke liye hai — wo request ke saath server tak pehchaan (session id) pahunchaati hai.

**Session server ka state hai** — session id ka record (id → user data) server ke paas hota hai. Par session ki pehchaan — woh session id — **cookie mein** browser ke paas hoti hai.

Toh cookie aur session alag-alag sides ki cheezein nahi hain — **dono ek hi system ke do hisse hain.** Cookie = server tak pehchaan pahunchane ka transport. Session = server pe rakhi hui us user ki state. Cookie ke bina server ko pata nahi chalta request kiski hai; session ke bina cookie (random id) ka koi matlab nahi. Woh id dono ko jodti hai — cookie mein travel karti hai, session server pe uska matlab rakhta hai.

## What It Is NOT

- **Cookie ≠ localStorage.** Dono browser mein data store karte hain, par local storage mein jo data hai woh **har request ke saath automatically nahi jaata** — cookie jaati hai. Aur localStorage JavaScript se hamesha readable hai — cookie `httpOnly` ho toh JS padh hi nahi sakta. Auth ke liye cookie (httpOnly wali) isliye safe hai, localStorage nahi.
- **httpOnly cookie ≠ secure cookie.** `httpOnly` JavaScript se bachata hai, `secure` HTTP se bachata hai — do alag cheezein, dono chahiye.
- **Cookies sirf auth ke liye nahi hain** — theme, cart, language preferences bhi cookies mein rehti hain. Par auth wali cookie sabse critical hai — isliye usi ke liye yeh safety attributes banaye gaye hain.

## Next.js Mein — `cookies()`

Next.js mein cookies ka API ek function hai — `cookies()` — jo `next/headers` se import hota hai. **Next 15+ mein yeh async hai** — matlab `await cookies()` karna padta hai, direct `cookies().get()` nahi chalega.

Abhi yeh sirf jaanna hai — **4.2 mein khud set karenge** aur dekhenge ki kab read hoti hai aur kab write. Ek preview: cookies ko set ya delete karne ki permission sirf **Server Actions aur Route Handlers** ko hai — Server Components sirf read kar sakte hain. Kyun, yeh 4.2 mein samjhenge.

## Nutshell

Cookie = server ki taraf se browser ko diya gaya chhota sa data, jo har request ke saath wapas jaata hai. HTTP stateless hai, cookie usse "yaad" deti hai. Session pattern mein cookie mein sirf random id hoti hai, aur server ke paas us id ka record — user ka data kabhi cookie mein nahi. `httpOnly`, `secure`, `sameSite` teen attributes session cookies ki safety hain — XSS, HTTP sniffing aur CSRF se bachate hain. Next.js mein `cookies()` async hai aur write sirf Server Actions/Route Handlers se hota hai.
