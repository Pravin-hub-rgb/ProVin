Think about any website you've ever used — there's one thing that's almost always there: **login**. YouTube, GitHub, Instagram, Gmail — they all say "sign in." And after you log in, the site remembers you — it shows "Hello, Pravin," your name, your profile. But here's something to think about: HTTP, the protocol that powers the web, has no memory. It forgets who you are on every single request. The site doesn't come with a built-in "oh, this is Pravin" feature. So how does the site remember you after you log in? That's the question this batch answers, and it all starts with **cookies and sessions**.

In Batch 3, we learned how to **change** data — using Route Handlers (REST) and Server Actions. We practiced by building a Reviews & Ratings app. Now a new problem arises. The reviews app works as long as anyone can post a review. But when data becomes **user-specific** — a dashboard, a profile, "just my draft" — the server needs to know **who is making the request**. This is called **authentication** — and it's the most real-world part of this course, because every production app has it.

## Two Projects — "Manual → Better" Pair

The end of the roadmap has a summary table — "Manual → Better" pairs. This is the same pattern as the React course: **first feel the problem, then understand the solution.** Authentication is the perfect example, because in the "Manual" approach you build the real things that matter:

**Manual (5.2–5.3):** **Login Demo v1** — password hashing (bcryptjs), a users store, setting and reading a session cookie by hand. This is not for production — it's for **understanding**. It contains everything that happens inside "login" that libraries usually hide.

**Better (5.4.x):** **Login Demo v2** — Auth.js (NextAuth) + GitHub OAuth. This is the version you see in YouTube tutorials — real external OAuth setup, a "Sign in with GitHub" button, proper session handling. The library handles security edge cases that are easy to miss when building manually.

**Remember the framing (same as Batch 3):** Manual isn't bad — it's the **foundation**. Auth.js is "better" because authentication is so critical in production that building it yourself is an expensive mistake. First understand *what is happening* with the manual approach, then see *how much the library shortcuts* with Auth.js.

## Login Demo v1 — Manual (5.2, 5.3)

The roadmap says: *"very basic — set and read a cookie-based session by hand (for understanding only, not for production)."*

- **5.2** — Hashing: passwords are never stored in plaintext. Hash them with `bcryptjs` (what a salt is, and why it protects against rainbow tables), store users in a `users.json` file, and build a **register** Server Action that creates a new user with `hashPassword()` (with a duplicate-email check). Then a **login** Server Action that verifies with `comparePasswords`, and sets the session cookie.
- **5.3** — **Read** the cookie to protect a `/secret` route (layout-level check — "redirect if not logged in"), implement logout, and cover security notes (httpOnly, sameSite, secure).

## Login Demo v2 — Auth.js + GitHub OAuth (5.4.x)

The roadmap says: *"same feature, but with a proper auth library (OAuth provider or credentials)."* We'll use **GitHub OAuth**:

- **Real external setup** — create a GitHub OAuth app (Settings → Developer settings), get the client ID + secret, configure the callback URL. This is exactly what the YouTube tutorials show.
- **5.4.1** — install `next-auth`, configure root `auth.ts`, set up the `[...nextauth]` route handler, and build a custom login page.
- **5.4.2** — Read sessions on the server (`auth()`) and on the client (`SessionProvider` + `useSession`) — show "Hello, [name]" in the navbar.
- **5.4.3** — The **recommended** way to protect routes: main security in `layout.tsx` with `auth()` + `redirect()`, and `proxy.ts` for routing only. We'll also cover why **auth doesn't belong in the proxy** (CVE-2025-29927 — after Next 16, this is officially discouraged). The roadmap fix is reflected here.

## Combined Project #4 — Member Dashboard (5.5.x)

The roadmap says: *"users log in (Auth.js), view their dashboard/profile (protected routes), and unauthorized access is blocked. **Fresh project — not a blog.**"*

So we'll build a **new project** — `member-dashboard` — with:

1. **Login** — GitHub OAuth (using the 5.4.1 pattern)
2. **Protected dashboard** — without a session, visiting `/dashboard` redirects to `/login`
3. **Profile page + update** — the logged-in user updates their name/bio (Server Actions — **the Batch 3 mutation pattern returns here**)
4. **Navbar** — shows the logged-in user's name/avatar, with a logout button

A 5-part series builds this (planning → hardcoded UI → auth wiring → dynamic → testing), practicing the same "how to write a project in series" process.
