Ek second ruk ke peeche dekho — **dono versions ban gaye.** Login Demo v1 mein khud likha: bcryptjs hashing, users file, session cookie set/read, protected layout, logout. Login Demo v2 mein Auth.js se: GitHub OAuth app, config, route handler, `auth()` server mein, `useSession()` client mein, proxy routing, layout protection. **Same kaam — do alag raste.** Ab wo kaam karna hai jo 4.0 mein wada kiya tha — dono ko side by side rakh ke samjho **kab kya use karna hai.** Yahi "Manual → Better" pair ka payoff hai.

# Summary — Manual vs OAuth

## Kya Banaya Tha — Recap

| | Login Demo v1 (Manual) | Login Demo v2 (Auth.js) |
|---|---|---|
| **Hashing** | `bcryptjs` khud | Library (OAuth mein toh hai hi nahi) |
| **Users** | `users.json` file + lookup functions | GitHub ke paas (profile fetch) |
| **Session cookie** | Khud `cookies().set()` attributes ke saath | `authjs.session-token` khud |
| **Session read** | Khud `getSession()` | `auth()` / `useSession()` |
| **Login page** | Email/password form | "Sign in with GitHub" button |
| **Protection** | Layout check + redirect | Layout check + redirect + proxy routing |
| **Logout** | `cookies().delete()` | `signOut()` |

Dono ne wahi chizein ki — ek ne haath se, ek ne library se.

## Ab Kiya Seekha — Naya Kya Aaya

| Cheez | v1 mein | v2 mein (naya) |
|---|---|---|
| **OAuth flow** | Nahi tha | GitHub redirect → approve → callback → token → profile |
| **External setup** | Nahi | GitHub OAuth App + Client ID/Secret + callback URL |
| **JWT session** | Sirf id wali cookie | JWT signed token cookie |
| **Proxy routing** | Nahi | `proxy.ts` — logged-in user ko `/login` se hatana |
| **Client session** | Nahi (sirf server read) | `SessionProvider` + `useSession()` — navbar UX |

## Manual vs Auth.js — Kab Kya?

| Situation | Kya use karein | Kyun |
|---|---|---|
| Learning — "login ke andar kya hota hai" | **Manual** | Libraries chhupa deti hain; yahan dikhta hai |
| Production app (koi bhi) | **Auth.js** (ya koi established library) | Security edge-cases library ke paas; khud likhne ki galti mehengi |
| App jisme external login chahiye ("Sign in with Google/GitHub") | **Auth.js + OAuth provider** | Password system ki zaroorat hi nahi |
| App jisme user accounts email/password ke saath chahiye | **Auth.js + Credentials** | Library handles session/safety; tum sirf users store karo |
| Sirf routing-level redirects | **proxy.ts** | Request render se pehle, ek jagah |
| Route security | **Layout/Server Component `auth()`** | Bypass-proof — CVE-2025-29927 ke baad recommended |

**Ek aur decision jo ab samajh mein aata hai — OAuth vs Credentials:**

- **OAuth** — user ko password yaad nahi rakhna, app ko password store/safety manage nahi karni. Bas "Google/GitHub se login" — 5 minute ka setup, security ka poora burden provider ke paas.
- **Credentials** — app ke andar user accounts chahiye (jaise kisi ki apni app ka email/password system). Tab bhi hashing + session library se, khud nahi.

Dono sahi hain — **yeh app ki requirement decide karti hai, "acha/bura" nahi.**

## JWT vs Server Session — Jo Abhi Samajh Mein Aata Hai

4.1 mein session pattern preview hua tha, 4.4 mein JWT properly introduce hua (session ki problem — lookup — se lekar structure tak). Ab dono ka trade-off samajh aa raha hai:

| | Server Session (4.3 wala) | JWT (Auth.js default) |
|---|---|---|
| **Data kahan** | Server ka record | Token ke andar (signed) |
| **Har request pe** | Record lookup | Signature verify (fast) |
| **Logout/revoke** | Turant — record delete | Token valid rehta hai jab tak expire na ho |
| **Sensitive data** | Server pe safe | Token ke andar (dikh sakta hai, par signed) |
| **Kab use** | Session revocation zaroori ho | Stateless + scalability chahiye |

**Ek aur confusion jo 4.4 mein clear hui — "token" ke naam pe do alag cheezein.** GitHub ka **access token** OAuth flow ke callback mein ek baar milta hai, sirf profile fetch ke liye use hota hai, aur khatam — **har request mein nahi jaata.** Aur Auth.js ka **session JWT** (`authjs.session-token` cookie) login ke baad banta hai, aur **har request mein browser se server jaata hai** — yahi user ki pehchaan hai. Dono ko ek mat samjho — access token GitHub↔app ke beech tha, session JWT browser↔app ke beech hai.

Auth.js dono support karta hai (`session.strategy: "jwt"` ya `"database"` — database wala Batch 5 ke baad kaam aayega). Ab ke liye default JWT hi theek hai — chhote/mid apps ke liye.

## What It Is NOT

- **"Manual bekaar tha, Auth.js best" nahi** — Manual ne "why" diya jiske bina Auth.js ke config options (httpOnly, strategy, pages) sirf magic lagte. 4.0 wala "Manual → Better" pair hi sahi framing hai.
- **Auth.js = security ka guarantee nahi** — authentication deta hai, authorization (kya allowed) tumhari code ki zimmedari hai (4.4.3 wala layout check khud likhna pada).
- **"OAuth = sabse secure" nahi** — OAuth ek option hai, security guarantee nahi. Credentials bhi secure ho sakta hai agar library se properly kiya jaye.
- **JWT "bina server ke" nahi** — JWT mein bhi cookie hoti hai, server verify karta hai. Sirf "record lookup" ki jagah "signature verify" hai.

## Nutshell

Batch 4 ka core: auth ka "why" manual se aaya (cookie, session, hashing, protection), "how" Auth.js se (OAuth, JWT, `auth()`/`useSession()`, proxy routing). Decision guide: learning → manual; production → Auth.js; external login → OAuth provider; app ke apne accounts → Credentials; route security → layout `auth()`; routing redirects → proxy. Dono approaches ka matlab samajhna hi is batch ka asli seekh hai.
