Take a step back — **both versions are done.** In Login Demo v1 we built from scratch: bcryptjs hashing, a users file, session cookie set/read, protected layout, logout. In Login Demo v2 we used Auth.js: a GitHub OAuth app, configuration, route handler, `auth()` on the server, `useSession()` on the client, proxy routing, and layout protection. **Same job — two different paths.** Now comes what 5.0 promised — put them side by side and decide **when to use which.** This is the payoff of the "Manual → Better" pair.

# Summary — Manual vs OAuth

## What We Built — Recap

| | Login Demo v1 (Manual) | Login Demo v2 (Auth.js) |
|---|---|---|
| **Hashing** | `bcryptjs` by hand | Library (OAuth doesn't even involve passwords) |
| **Users** | `users.json` file + lookup functions | GitHub holds the data (profile fetch) |
| **Session cookie** | Set by hand with `cookies().set()` and attributes | `authjs.session-token` set by the library |
| **Session read** | Hand-written `getSession()` | `auth()` / `useSession()` |
| **Login page** | Email/password form | "Sign in with GitHub" button |
| **Protection** | Layout check + redirect | Layout check + redirect + proxy routing |
| **Logout** | `cookies().delete()` | `signOut()` |

Both did the same things — one by hand, one with a library.

## What Was New

| Thing | v1 had | v2 (new) |
|---|---|---|
| **OAuth flow** | Not present | GitHub redirect → approve → callback → token → profile |
| **External setup** | None | GitHub OAuth App + Client ID/Secret + callback URL |
| **JWT session** | Just an id-based cookie | JWT signed-token cookie |
| **Proxy routing** | None | `proxy.ts` — sends logged-in users away from `/login` |
| **Client session** | None (server read only) | `SessionProvider` + `useSession()` — navbar UX |

## Manual vs Auth.js — When to Use Which

| Situation | What to Use | Why |
|---|---|---|
| Learning — "what happens inside login" | **Manual** | Libraries hide the details; here you see them |
| Production app (any app) | **Auth.js** (or any established library) | Security edge cases are the library's job; building it yourself is an expensive mistake |
| App that needs external login ("Sign in with Google/GitHub") | **Auth.js + OAuth provider** | No password system needed at all |
| App with its own email/password accounts | **Auth.js + Credentials** | The library handles sessions and safety; you just store users |
| Only routing-level redirects | **proxy.ts** | Before the request renders, in one place |
| Route security | **Layout/Server Component `auth()`** | Bypass-proof — recommended after CVE-2025-29927 |

**Another decision that becomes clear now — OAuth vs Credentials:**

- **OAuth** — the user doesn't manage a password, and the app doesn't store or protect one. "Sign in with Google/GitHub" — a 5-minute setup, with the entire security burden on the provider.
- **Credentials** — the app has its own user accounts (like an internal tool or app-specific email/password). Even then, use hashing + session library — don't build it yourself.

Both are valid — **the requirement decides, not a "better/worse" ranking.**

## JWT vs Server Session — Trade-offs Now Clear

In 5.1 we previewed the session pattern, and in 5.4 JWT was introduced properly (from the session problem — the lookup — through its structure). Now the trade-off is clear:

| | Server Session (5.3) | JWT (Auth.js default) |
|---|---|---|
| **Data lives** | In a server record | Inside the token itself (signed) |
| **On every request** | Record lookup | Signature verification (fast) |
| **Logout/revoke** | Immediate — delete the record | The token stays valid until it expires |
| **Sensitive data** | Safe on the server | Inside the token (readable, but signed) |
| **When to use** | When immediate revocation matters | When you need statelessness + scalability |

**One more confusion cleared in 5.4 — "token" refers to two different things.** GitHub's **access token** arrives once in the OAuth callback and is only used to fetch the profile — it is never sent with each request. Auth.js's **session JWT** (`authjs.session-token` cookie) is created after login and **travels with every request** from browser to server — it is the user's identity. Don't confuse them: the access token lives between GitHub ↔ app; the session JWT lives between browser ↔ app.

Auth.js supports both (`session.strategy: "jwt"` or `"database"` — the database strategy comes later in Batch 5). For now, the default JWT is fine — good for small/mid-sized apps.

## What It Is NOT

- **"Manual was bad, Auth.js is best" is not the framing.** Manual gave us the *why* that Auth.js config options (httpOnly, strategy, pages) would just feel like magic without. 5.0's "Manual → Better" framing stands.
- **Auth.js is not a security guarantee.** It handles *authentication*; *authorization* (what is allowed) is still your code's responsibility (the 5.4.3 layout check you wrote yourself).
- **"OAuth is the most secure" is not true.** OAuth is one option, not a security guarantee. Credentials can also be secure when built with a library.
- **JWT doesn't mean "no server."** JWT still uses a cookie, and the server still verifies it. The difference is "record lookup" vs "signature verification."

## Nutshell

Batch 4's core: auth's *why* came from the manual approach (cookies, sessions, hashing, protection), and *how* came from Auth.js (OAuth, JWT, `auth()`/`useSession()`, proxy routing). Decision guide: learning → manual; production → Auth.js; external login → OAuth provider; app's own accounts → Credentials; route security → layout `auth()`; routing redirects → proxy. Understanding what each approach means is the real takeaway of this batch.

1. Someone asks "how do I build a login?" — which 3 questions do you ask to pick the right approach?

<details>
<summary>Show Answer</summary>

**Sample Answer:** First: "Is this for learning or production?" — production means Auth.js. Second: "Do users need their own app email/password accounts, or is Google/GitHub login fine?" — external is fine → OAuth provider; own accounts → Credentials. Third: "Do you need sessions to revoke immediately on logout?" — yes → server session; no → JWT. These three questions resolve almost every decision.

</details>

2. OAuth vs Credentials — which situation calls for which, and how can both be valid?

<details>
<summary>Show Answer</summary>

**Sample Answer:** OAuth is for when external login is acceptable — the user doesn't manage a password, the app doesn't store or protect one, and the entire security burden is on the provider. Credentials is for when the app needs its own user accounts (like an internal tool or app-specific accounts). Both are valid because the answer comes from the requirement: how users log in is decided by the app's nature, not a universal "best."

</details>

3. JWT vs server session — what's the trade-off, and why does the logout scenario show the difference?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Server session stores data in a server record; JWT stores it inside the signed token itself. On logout the server session deletes the record immediately — the session is gone. A JWT stays valid until it expires — logout only deletes the client-side cookie, but the token technically still verifies if anyone holds it. So when immediate revocation matters (sensitive apps, admin logout) server sessions win; when statelessness and performance matter (no per-request DB lookup) JWT wins.

</details>

4. "Auth.js did the authentication, authorization is your responsibility" — what does that mean, with the example from 5.4.3?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Authentication = "who are you?" — Auth.js does that (GitHub login, session verification). Authorization = "what are you allowed to do?" — that is still your code's job. The example is `dashboard/layout.tsx` from 5.4.3: `auth()` gets the session (authentication), but the decision "send logged-out users to `/login`" is an authorization rule you wrote yourself. Auth.js never knows which routes belong to whom — that is always a code decision.

</details>

5. How do you frame the 5.1–5.4.3 sequence in the "why → how" framework?

<details>
<summary>Show Answer</summary>

**Sample Answer:** 5.1–5.3 cover the *why*: HTTP is stateless, cookies carry identity (httpOnly/secure/sameSite matter), the session pattern exists (id in cookie, record on server), hashing is one-way with a salt, protection belongs in layout (bypass-proof), and the proxy shouldn't carry auth after CVE-2025-29927. 5.4.x covers the *how*: Auth.js does all of that ready-made — OAuth flow, JWT, `auth()`/`useSession()`, proxy routing. Knowing the *why* means you can configure the library with understanding instead of treating it as magic.

</details>
