# Auth.js + GitHub OAuth — Login Demo v2

## Where We Left Off

In 5.3 we configured Auth.js in principle — the providers, the session strategy, the named exports (`handlers`, `signIn`, `auth`, `signOut`), and the route handler pattern. Now we do the **real external setup**: create a GitHub OAuth App, fill `.env.local`, and turn the theory into a working "Sign in with GitHub" button. This is the part with outside systems — GitHub's UI, a client secret revealed once, a callback URL that must match exactly.

## Step 1 — Create the GitHub OAuth App

This is the only step that leaves the editor. Open GitHub:

1. Profile picture (top-right) → **Settings**.
2. Sidebar → **Developer settings** → **OAuth Apps** → **New OAuth App**.
3. Fill in:

| Field | What to enter | Why |
|---|---|---|
| Application name | `Member Dashboard` | Shown to the user on GitHub's consent screen; anything readable |
| Homepage URL | `http://localhost:3000` | Your app's origin |
| Authorization callback URL | `http://localhost:3000/api/auth/callback/github` | **Where GitHub sends the user back after they approve.** Must match your route handler exactly |

4. Click **Register application**.

GitHub now shows:

- **Client ID** — public; not secret.
- **Generate a client secret** → click it → a secret appears. **Copy it now; it will not be shown again.** Treat it like a password.

> These two values are GitHub's proof that a given app is really yours during the OAuth handshake. If the secret leaks, anyone can impersonate your OAuth app. Never commit it.

## Step 2 — Environment Variables

Create `.env.local` at the project root (if `create-next-app` did not already):

```
AUTH_SECRET=<generated-signing-secret>
AUTH_GITHUB_ID=<the-client-id-from-github>
AUTH_GITHUB_SECRET=<the-client-secret-from-github>
```

Generate the signing secret:

```bash
npx auth secret
```

It writes a random key straight into `.env.local` under `AUTH_SECRET`. This key signs the session JWT — without it, sessions can't be verified.

## Step 3 — Install next-auth

```bash
npm install next-auth@beta
```

> `@beta` tracks Auth.js v6 (the current Next.js 16 release). Stable tags lag behind.

## Step 4 — The Config File: `auth.ts` at the Root

This file owns the auth configuration and re-exports the helpers. It must sit at the **project root** (next to `package.json`), **not** inside `app/`, so that imports resolve cleanly.

```ts
import NextAuth from "next-auth";
import GitHub from "next-auth/providers/github";

export const { handlers, signIn, auth, signOut } = NextAuth({
  providers: [GitHub],
  secret: process.env.AUTH_SECRET,
  session: { strategy: "jwt" },
  pages: {
    signIn: "/login",
  },
});
```

Reading the options:

- `providers: [GitHub]` — enables "Sign in with GitHub." GitHub provider reads `AUTH_GITHUB_ID` and `AUTH_GITHUB_SECRET` from the environment by convention.
- `secret` — the JWT signing key (from `AUTH_SECRET`).
- `session: { strategy: "jwt" }` — sessions are stored as signed JWTs in the cookie (not in a server-side store). Stateless, so no DB lookup per request.
- `pages: { signIn: "/login" }` — when a protected area redirects to sign-in, send the user to our custom `/login` page instead of Auth.js's default.

The named exports are the app's entire auth API: `handlers` (route handler), `signIn` (start a flow), `signOut` (end a session), and `auth` (read the session).

## Step 5 — The Route Handler: `app/api/auth/[...nextauth]/route.ts`

```ts
import { handlers } from "@/auth";

export const { GET, POST } = handlers;
```

`[...nextauth]` is a **catch-all dynamic route** (Batch 1). Auth.js serves everything Auth-related from `/api/auth/*`: sign-in start, the GitHub callback, the session endpoint, sign-out. Two lines cover all of it.

The import `@/auth` points at the root `auth.ts`. That resolution is why the config file lives at the root — `@` maps to the project root in `create-next-app`.

## Step 6 — The Login Page

```tsx
// app/login/page.tsx
import { signIn, auth } from "@/auth";
import { redirect } from "next/navigation";

export default async function LoginPage() {
  const session = await auth();
  if (session) {
    redirect("/");
  }

  return (
    <main>
      <h1>Sign In</h1>
      <form
        action={async () => {
          "use server";
          await signIn("github");
        }}
      >
        <button type="submit">Sign in with GitHub</button>
      </form>
    </main>
  );
}
```

- `await auth()` — server-side session check. Already signed in? Bounce to the app instead of showing the login form.
- The form is an **inline Server Action**: clicking the button calls `signIn("github")`, which redirects the user to GitHub. GitHub returns them to the callback URL, which hits the route handler from Step 5, which completes the exchange and establishes the session.
- No email/password form, no hashing, no cookie handling here — all that machinery already happened in the library. The page only decides "who goes where": already-in users go to `/`, strangers go to GitHub.

## Step 7 — Try It (and Confirm It Really Worked)

1. `npm run dev`.
2. Visit `/login` → "Sign in with GitHub".
3. Click it → GitHub's consent screen → authorize.
4. You are returned to `/` (because of the `redirect("/")`).

Verify the session was established — check **Application → Cookies** for `authjs.session-token`. It is `HttpOnly` by default, and present on subsequent requests. The `auth()` helper on the server will now resolve it to a user object containing `name`, `email`, and `image` from GitHub.

## What Went Where

| Concern | Where it lives now |
|---|---|
| Provider selection | `auth.ts` `providers` |
| Callback route | `app/api/auth/[...nextauth]/route.ts` |
| Environment | `.env.local` |
| Start sign-in | `signIn("github")` in the login action |
| Read session | `auth()` on the server, `useSession()` on the client |
| Protect routes | `pages.signIn` (redirect) + a layout guard (5.3.3) |

## What It Is NOT

- **A "Sign in with GitHub" button is not a security policy.** The button starts OAuth; protecting the route still requires an explicit guard. Auth.js does not auto-lock every route.
- **The session cookie being present does not prove the user is who they claim without verification.** Auth.js verifies the signed JWT. We will build the actual route guard that consumes it next.
- **This step is not idempotent across environments.** The same GitHub OAuth App cannot serve `localhost:3000` and production with one callback URL. Separate registrations are the norm.
- **`npx auth secret` is not optional in production.** Without `AUTH_SECRET`, there is no signing key — sessions fail or can be forged.

## Common Mistakes

- **Callback URL mismatch.** Exact match is required: `http://localhost:3000/api/auth/callback/github`. A trailing slash or wrong port breaks the return.
- **Not restarting after editing `.env.local`.** Environment is read at process start; a stale server still sees the old or missing values.
- **Committing `.env.local`.** It contains the client secret. A `create-next-app` `.gitignore` already excludes it — but verify.
- **Placing `auth.ts` inside `app/`.** The root-relative `@/` import then fails. Root placement is the convention for this config.
- **Confusing `signIn` with `auth`.** `signIn` starts a flow; `auth` reads a session. They are complementary, not interchangeable.

## Nutshell

To wire GitHub OAuth: register a GitHub OAuth App with callback `http://localhost:3000/api/auth/callback/github`, copy the client ID and secret into `.env.local`, generate `AUTH_SECRET` with `npx auth secret`, install `next-auth@beta`, write root `auth.ts` with `providers: [GitHub]` and the `signIn`/`signOut`/`auth`/`handlers` exports, add `app/api/auth/[...nextauth]/route.ts` re-exporting `handlers`, and build a login page that calls `signIn("github")`. After authorizing at GitHub, a signed `authjs.session-token` cookie is set automatically — the foundation the rest of the app reads from.

## In Your Own Words

<details>
<summary>1. Why is the GitHub callback URL required during OAuth App creation, and where must it point?</summary>

**Sample Answer:** After the user authorizes the app at GitHub, GitHub needs to send them back to your app with the authorization code. The callback URL registered at GitHub must be exactly where Auth.js expects to receive that code. Any mismatch and GitHub refuses to redirect, aborting the login.

</details>

<details>
<summary>2. What is the difference between `AUTH_GITHUB_ID` and `AUTH_SECRET`, and why does each matter?</summary>

**Sample Answer:** `AUTH_GITHUB_ID` and `AUTH_GITHUB_SECRET` prove that your app is the legitimate owner of the GitHub OAuth registration — GitHub checks them during the handshake to prevent impersonation. `AUTH_SECRET` is Auth.js's own key used to sign the session JWT. One pair authenticates your app to GitHub; the other secures your app's sessions. Both are sensitive, but they protect different things.

</details>

<details>
<summary>3. Why must the `auth.ts` config live at the project root rather than in `app/`?</summary>

**Sample Answer:** It is imported as `@/auth`, and `@` resolves to the project root. Placing it inside `app/` breaks that resolution and can confuse route-handler and provider discovery. Root placement is also the Next.js/Auth.js convention for the config that backs `/api/auth/*`.

</details>

<details>
<summary>4. How does `signIn("github")` differ from `auth()`?</summary>

**Sample Answer:** `signIn("github")` initiates the OAuth handoff — it redirects the user to GitHub. `auth()` is the opposite direction: it reads the session that already exists after a sign-in (or returns null). One starts the flow; the other observes its result.

</details>

<details>
<summary>5. Where do you verify that the login actually succeeded?</summary>

**Sample Answer:** In the browser's cookie store — look for `authjs.session-token`, which is `HttpOnly` and set automatically after a successful OAuth exchange. Its presence (and that `auth()` resolves to a user object) confirms the session was established.

</details>

---

Login works and a signed session cookie is in the browser. But that session is only useful if two things read it correctly: **Server Components** (which render the protected pages) and **Client Components** (which run the interactive navbar). Reading a session is not symmetric across the two — it never has been. 5.3.2 covers the divide.
