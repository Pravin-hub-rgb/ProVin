# Clerk vs Auth.js — When to Choose What (5.6.3)

## Where We Left Off

In 5.6.2 we set up Clerk: sign-in/sign-up drop-in components, protected routes via `currentUser()`, client-side auth via `useUser()`, and route groups for organization. Everything mirrors what Auth.js taught in 5.4–5.5.5 — same mental model, different SDK.

Now the decision question: **when do you choose one over the other?**

## Broader Goal

- Compare Auth.js and Clerk across real-world criteria
- Know the **decision matrix** — cost, control, complexity, team size
- Leave with confidence on which to use for your project

## Manual → Better → Production

| Stage | What you hand-code | What the library provides | What Clerk provides |
|---|---|---|---|
| Manual (5.1–5.3) | bcrypt, session cookies, auth() reader, protected layout | — | — |
| Auth.js (5.4–5.5.5) | — | Providers config, `auth()`, `signIn()`, `signOut()` | — |
| Clerk (5.6) | — | — | Drop-in UI, managed sessions, MFA, passwordless |

## Feature Comparison — Side by Side

| Feature | Auth.js (self-hosted) | Clerk (managed) |
|---|---|---|
| **Setup time** | ~30 minutes (install, configure, wire handlers) | ~5 minutes (install, paste keys, wrap provider) |
| **Login UI** | You build forms, error handling, password reset UI | Drop-in `<SignIn />`, `<SignUp />` — fully styled |
| **OAuth providers** | Add each provider in code config (5.4.1) | Enable in Clerk dashboard — no code changes |
| **MFA (multi-factor)** | Not supported — you'd build TOTP/SMS yourself | Built-in — TOTP, SMS, WebAuthn (passkeys) |
| **Passwordless** | Not supported | Built-in — magic links, SMS, email code |
| **Session management** | You handle JWT, cookie rotation, refresh | Managed — Clerk handles token lifecycle |
| **Session invalidation** | You build a token blacklist | Clerk dashboard — revoke sessions per-user |
| **User management** | You build `/profile`, `/change-password` | `<UserProfile />` component — complete UI |
| **Multi-device sessions** | You track sessions yourself | Built-in — users see "active sessions" and revoke |
| **Vendor lock-in** | None | Yes — your users live in Clerk's database |
| **Cost** | Free | Free tier (1000 MAU), then paid |
| **Self-hosting** | Your server | Clerk's infrastructure |
| **Custom domain** | You configure | Clerk configures |

## Decision Matrix

Use this checklist to decide:

### Choose Clerk when ANY apply:

1. **You need MFA or passwordless** — TOTP, SMS, magic links. Building these yourself is weeks of security work.
2. **Auth is not your core product** — you'd rather spend time on your actual features than auth infrastructure.
3. **You want sign-in UI immediately** — `<SignIn />` out of the box, no design work.
4. **You have a budget for SaaS tools** — Clerk charges per MAU, but saves engineering time.
5. **Your team lacks auth security expertise** — session fixation, token rotation, CSRF protection are handled.

### Choose Auth.js when ANY apply:

1. **You need zero vendor dependencies** — everything runs on your server, in your control.
2. **You have an existing user database** — users stored in your own DB, not Clerk's.
3. **You're bootstrapping / self-hosted only** — no budget for paid SaaS tools.
4. **You need a provider Clerk doesn't support** — Auth.js supports dozens of OAuth providers; Clerk supports fewer.
5. **You need full control over the auth flow** — custom branding, non-standard OAuth, unusual redirect logic.

## Hybrid Approach — Use Both?

You **can** use both in the same codebase:

- **Clerk** for customer-facing auth (sign-in, MFA, passwordless)
- **Auth.js** for internal admin tooling (separate auth flow, no MFA needed)

This is uncommon but valid. The key is keeping them **separate** — don't mix Clerk and Auth.js in the same route tree.

## Migration — Auth.js to Clerk

| Concept | Auth.js | Clerk |
|---|---|---|
| Check session | `const session = await auth()` | `const user = await currentUser()` |
| Redirect if no session | `if (!session?.user) redirect('/sign-in')` | `if (!user) redirect('/sign-in')` |
| Sign out | `await signOut()` | `<SignOutButton />` or `signOut()` |
| User's name | `session.user.name` | `user.firstName + " " + user.lastName` |
| User's email | `session.user.email` | `user.emailAddresses[0].emailAddress` |

The migration is mostly mechanical — the patterns are the same, just different property names.

| | Auth.js | Clerk |
|---|---|---|

## Common Mistakes

- ❌ **Choosing based on "which is easier"** — both solve auth, but the operational concerns (infrastructure, cost, expertise) matter more.
- ❌ **Switching mid-project** — Auth.js and Clerk store users differently. Migration requires re-creating user data.
- ❌ **Underestimating Clerk's cost** — at scale, Clerk's MAU pricing can exceed the engineering time to maintain Auth.js.

## What It Is NOT

- **It is not a one-size-fits-all decision.** The right choice depends on your team, budget, and timeline — not technical dogma.
- **It is not permanent.** You can switch from Auth.js to Clerk (or vice versa), but it requires intentional migration — not a 5-minute change.
- **It is not about features.** Both provide OAuth, sessions, and protected routes. The difference is **where** the complexity lives.

## In Your Own Words

1. You are building a B2B SaaS product with MFA requirements, a 3-person engineering team, and a budget for SaaS tools. Auth.js or Clerk?

<details>
<summary>Sample Answer</summary>

**Answer:** Clerk. MFA is built-in (no weeks of security implementation), the drop-in UI saves frontend time, and with a small team that budget is better spent on the product itself than auth infrastructure.

</details>

2. You are bootstrapping a side project with zero budget, you already have a user database in PostgreSQL, and you don't need MFA. Auth.js or Clerk?

<details>
<summary>Sample Answer</summary>

**Answer:** Auth.js. It's free, works with your existing PostgreSQL database, and you control the auth flow. Clerk's free tier would work too, but you'd have to migrate your existing users into Clerk's system — unnecessary complexity for a side project.

</details>

3. What is the #1 operational difference between Auth.js and Clerk?

<details>
<summary>Sample Answer</summary>

**Answer:** Who operates the infrastructure. Auth.js runs on your server — you deploy it, you secure it, you handle session refresh/cookie rotation. Clerk is a managed service — they handle all of that on their infrastructure. You trade control for convenience.

</details>
