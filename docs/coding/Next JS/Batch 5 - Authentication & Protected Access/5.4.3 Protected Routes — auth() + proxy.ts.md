# Protected Routes — Layout `auth()` + `proxy.ts`

## Where We Left Off

In 5.4.1 we wired Auth.js + GitHub OAuth end-to-end and the dashboard shows the session (name on the navbar, email on the dashboard). But one serious gap remains: **no route is actually protected.** Open `/dashboard` without signing in and it still renders (just with an empty email) — any request can reach protected data without a session. Now we add the guard: if no session, redirect to `/login`.

This file covers two things. First — **layout-level `auth()` check** that locks down `/dashboard` (this is the real security; the same pattern from 4.3, now with Auth.js). Second — **`proxy.ts`**, Next.js 16's renamed `middleware.ts`, which handles routing-level concerns (e.g. send an already-logged-in user away from `/login` back to `/dashboard`). Critically, we do **not** put auth enforcement in the proxy — that's a deliberate choice driven by **CVE-2025-29927**, after which Next.js's official guidance moved auth checks out of the proxy layer. We'll cover why below, and the roadmap was updated to match.

## Step 1: Layout Protection — The Real Security

In 4.3 we protected routes with `getSession()` + `redirect("/login")`. Same pattern, now using `auth()`. Create `/dashboard/layout.tsx`:

**File:** `app/dashboard/layout.tsx` (new)

```tsx
// app/dashboard/layout.tsx
import { redirect } from "next/navigation";
import { auth } from "@/auth";

export default async function DashboardLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const session = await auth();
  if (!session) {
    redirect("/login");
  }
  return <>{children}</>;
}
```

- **`await auth()`** — session check. `null` means logged out.
- **`if (!session) redirect("/login")`** — the core protection from 4.3, now via Auth.js: **server-side check before any protected data is rendered.** The dashboard content (email, etc.) never reaches the client if the user is signed out — the request is rerouted to `/login` immediately.
- **Layout, not page** — this single guard covers every sub-route under `/dashboard` (`/dashboard`, and later `/dashboard/settings`, etc.). Same reason as 4.3: protect the whole subtree, not every page individually.

> **This layout check is the actual security boundary.** The proxy routing added next is a convenience layer — UX polish, not protection.

## Step 2: Proxy Routing — Don't Show the Login Page to a Signed-In User

New problem: a logged-in user manually navigates to `/login`. In 5.4.1 we handled it with a client-side `useEffect` on the login page (`if (session) redirect("/")`). That works for the login page, but only the login page. A **global, pre-render layer** that makes these routing decisions for every request is what the proxy is for.

### Concept — What `proxy.ts` Is

**`proxy.ts`** is a special file in Next.js that runs **before any route renders**, on every matching request. In it you inspect the incoming request and decide: redirect the user, short-circuit with a custom response, or let the request proceed to the route normally.

Version note — in Next.js 16 the file `middleware.ts` was renamed to `proxy.ts` (same concept, new name; the old name is deprecated). It's the same file used for rate-limiting back in the `4_proxy` project — same mechanism, now with auth in the picture.

Request flow:

```
Incoming request (/login)
   → proxy.ts runs (before render)
   → "Is this user signed in AND heading to /login? → send to /dashboard"
   → otherwise, let the request proceed
   → route renders
```

**File:** `proxy.ts` (project root — alongside `auth.ts`, outside `app/`)

We'll build it stage by stage: the wrapper skeleton, then the routing rule, then the matcher.

### Stage 1 — The Wrapper Skeleton

**THINK:** The proxy needs to know the session (logged-in?). Does it parse cookies itself? No — Auth.js provides a wrapper.

**CONCEPT:** `export default auth((req) => {...})` — Auth.js's special wrapper. Here `auth()` is being used as a **proxy wrapper**, and it injects the session into `req.auth`. (Without the wrapper, the proxy has to parse and verify the cookie itself.)

**CODE:**

```ts
// proxy.ts (project root)
import { auth } from "@/auth";

export default auth((req) => {
  // for now, do nothing — let the request pass through
});
```

**TEST:** App behaves exactly as before, no routes change — the wrapper has nothing to do yet.

### Stage 2 — The Routing Rule

**THINK:** Now the real logic: if the user is signed in and hits `/login`, redirect to `/dashboard`. Two checks needed — is the user signed in, and is this the login page.

**CONCEPT:** `req.nextUrl.pathname.startsWith("/login")` — pathname check (`startsWith` so any future subpaths of `/login` are covered too). `NextResponse.redirect(...)` — the proxy's short-circuit response: the request doesn't continue; the browser is redirected. When the rule does **not** return anything, the proxy simply passes the request through (default behavior).

**CODE** — full file up to this point (new parts marked `// NEW`):

```ts
// proxy.ts (project root)
import { auth } from "@/auth";
import { NextResponse } from "next/server";   // NEW: import

export default auth((req) => {
  // NEW: routing rule
  const isLoggedIn = !!req.auth;
  const isLoginPage = req.nextUrl.pathname.startsWith("/login");

  if (isLoggedIn && isLoginPage) {
    return NextResponse.redirect(new URL("/dashboard", req.nextUrl));
  }
});
```

- **`const isLoggedIn = !!req.auth`** — `req.auth` is the session object or `null`. Coerced with `!!` into a boolean: `true` if a session exists.
- **`if (isLoggedIn && isLoginPage)`** — the rule: **a signed-in user should not be shown the login page.**

**TEST:** Sign in, then manually visit `/login` → you get redirected to `/dashboard`. Signed out → `/login` loads normally.

### Stage 3 — The Matcher (Which URLs the Proxy Runs On)

**THINK:** Next problem — the proxy runs on *every* request right now, including static assets (images, CSS, fonts), where session logic is meaningless. `config.matcher` declares which URL patterns the proxy should run on.

**CONCEPT:** `matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"]` — "match everything except Next.js's static file prefixes." Keeps the proxy off static assets (performance).

**CODE** — final full file (matcher marked `// NEW`):

```ts
// proxy.ts (project root) — final
import { auth } from "@/auth";
import { NextResponse } from "next/server";

export default auth((req) => {
  const isLoggedIn = !!req.auth;
  const isLoginPage = req.nextUrl.pathname.startsWith("/login");

  if (isLoggedIn && isLoginPage) {
    return NextResponse.redirect(new URL("/dashboard", req.nextUrl));
  }
});

// NEW: matcher config
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**TEST:** Build output shows a `ƒ Proxy (Middleware)` entry, and the proxy does nothing for static assets (no runtime cost on images/styles).

### Notice: No Auth Enforcement in the Proxy

Did you catch it? The proxy is **not** blocking unauthenticated access to `/dashboard` — that's the layout's job (Step 1). The proxy only handles UX: keeping a signed-in user off the login page. That split isn't accidental. And the next section explains why.

## Step 3: Why Auth Does Not Live in the Proxy — CVE-2025-29927

By now anyone who has watched YouTube (or built their own `3_auth_js` project) has seen the middleware-based protection pattern: check `isProtectedRoute && !isLoggedIn`, then redirect. It works — and you've run it in your own project. But in 2025, a critical vulnerability landed: **CVE-2025-29927**, where Next.js's middleware could be **bypassed** with a forged header (`x-middleware-subrequest`). Meaning: an attacker could reach a protected route without signing in, because the middleware that enforced protection was skipped entirely.

The consequence: **Next.js's official guidance changed.** Auth checks should not live in the proxy/middleware. **Auth enforcement belongs in layouts, Server Components, Route Handlers, or Server Actions** — i.e. application code that the request-routing layer cannot bypass. Next.js 16 renamed the file from `middleware.ts` to `proxy.ts` and clarified the docs: proxy is for routing/redirects, **not for auth enforcement**.

That's why our split is correct:

| Layer | Responsibility | Why here |
|---|---|---|
| **`layout.tsx` + `auth()`** | Security — redirect to `/login` without session | Application code; cannot be bypassed by routing headers |
| **`proxy.ts`** | Routing — redirect a signed-in user away from `/login` | Convenience layer only; auth is not its job |

This is also **defense in depth**: even if the proxy were bypassed or a new exploit emerged, the layout check still stands. Two locks on the door — if one fails, the other holds. (The roadmap was updated for this too — the "proxy auth check" concept became "layout `auth()` protection + proxy routing" after this fix.)

## Deep Dive — Same Code, Different Layer

One thing almost everyone notices when comparing Step 1 and Step 2: both use `auth()`, both check "logged in?", both redirect. If the code looks the same, what's the difference? The answer is **not in the code, but in the layer** — and that's exactly the confusion that keeps people putting auth in the proxy. So let's compare against the old, vulnerable pattern.

**This is the pre-CVE pattern — the one that lived in tutorials and probably in your own project:**

```tsx
// OLD: app/dashboard/layout.tsx — empty! just wraps children
export default function DashboardLayout({ children }) {
  return <>{children}</>;
}
```

```ts
// OLD: app/middleware.ts — protection ONLY here
export function middleware(request: NextRequest) {
  const isLoggedIn = request.cookies.has("session");
  const isProtected = request.nextUrl.pathname.startsWith("/dashboard");

  if (isProtected && !isLoggedIn) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
}
```

- Layout has **nothing** — just wraps children, no session, no check.
- All protection is in middleware: `isLoggedIn` (cookie present?) and `isProtected` (heading to dashboard?). Both must be true → redirect.

**The attack — CVE-2025-29927, at its simplest:**

```bash
curl -H "x-middleware-subrequest: middleware" http://localhost:3000/dashboard
```

Internally, Next.js had a "subrequest" concept: when the app itself makes an internal request, middleware should not re-run (avoid duplicates). That special header fooled the framework: Next.js thought "middleware already ran on this request" → **middleware is skipped.** And the layout was empty → no other check existed → **the page opened without a session. One enforcement point existed, that point was skipped, protection collapsed.**

**The fix is exactly what Step 1 did — move the check into the layout:**

```tsx
// NEW: app/dashboard/layout.tsx — check lives HERE now
export default async function DashboardLayout({ children }) {
  const session = await auth();
  if (!session) {
    redirect("/login");
  }
  return <>{children}</>;
}
```

Run the same attack again — let middleware/proxy be skipped; it no longer matters (no security was ever in the proxy) — the layout **still runs**, because the layout is part of rendering that page, not a filter in front of it.

**Mental model — filter vs. page fragment:**

```
Request for /dashboard
   │
   ├─ proxy.ts ──► a separate filter in FRONT of the app ──► can be skipped (CVE case)
   │
   └─ layout.tsx ──► part of the page's RENDER ──► cannot be skipped
        │
        └─ page.tsx
```

The proxy is an optional filter standing in front of the app — CVE's header skips that filter. The layout is part of what renders the page — there's no path to a page under `/dashboard` that doesn't go through its layout, because the layout is what wraps the page during render. Sending `x-middleware-subrequest` cannot remove the layout — the layout is "must render," not a filter.

**Same code, different layer — the stakes:**

| Check | Layer | If bypassed / broken, consequence |
|---|---|---|
| `req.auth` → routing rule | `proxy.ts` | Just a UX glitch — a signed-in user might briefly see the login page. No data leaks. |
| `auth()` → redirect | `layout.tsx` | **Data breach** — unauthenticated access to protected data. This is the real security. |

One rule sums it up: **"If a page is protected, that page's own layout must hold the check — putting it elsewhere means it can be skipped."** The proxy's auth check is a feature (UX routing); the layout's auth check is a security control.

## What It Is NOT

- **Proxy as a security boundary.** The proxy *can* be bypassed (see CVE) — that's why security lives in the layout. The proxy is routing convenience only.
- **`proxy.ts` being just a rename of `middleware.ts`.** In Next 16 it runs on the Node runtime and the docs deliberately scope it to routing. Same mechanism, clarified role.
- **`auth()` wrapper in proxy doing "full auth on every request."** The wrapper does a fast session verification and exposes `req.auth`. But keep the proxy lightweight — heavy logic belongs in layouts and actions, since the proxy runs on every matched request.
- **Layout + proxy being a duplicate.** Different jobs: the layout enforces security (bypass-proof); the proxy handles UX (don't show login to a signed-in user).

## Common Mistakes

- **Only enforcing auth in the proxy, leaving the layout empty** — the CVE-2025-29927 pattern. If the proxy gets skipped and the layout has no check, the protected page opens to everyone. The layout check is mandatory.
- **Forgetting `matcher`.** Without it the proxy runs on every request including static assets — slowdowns.
- **Login ↔ dashboard redirect loops.** If both "protected route → `/login`" and "sign-in → `/dashboard`" live in the proxy, an edge case can loop. Keep the proxy rule one-directional: "signed-in + `/login` → `/dashboard`."
- **Putting heavy work in the proxy.** It runs on every request, including images if the matcher is too wide. Keep it trivial — routing only.
- **Manually parsing cookies instead of using the `auth()` wrapper.** `export default auth(...)` gives you `req.auth`; rolling your own cookie/JWT verification in the proxy is both wrong and insecure.

## Nutshell

Protected routes' recommended pattern: **layout-level `await auth()` + `if (!session) redirect("/login")`** — that is the actual security (bypass-proof, server-side). The **`proxy.ts`** (Next 16's middleware) is routing-only: the `auth()` wrapper hands it `req.auth`, and it redirects a signed-in user away from `/login` to `/dashboard`. Both layers touch `auth()` — but the layer is what matters, not the code: the proxy is a front filter that can be skipped (CVE), while the layout is part of the page's render and cannot be skipped. After CVE-2025-29927, auth enforcement stopped going in the proxy and moved to layout/server code.

**Sample Answer:** In CVE-2025-29927, Next.js middleware could be bypassed with a forged header (`x-middleware-subrequest`) — the framework thought middleware had "already run" and skipped it, so a protected route opened without a session. Because the proxy/middleware *can* be skipped, it cannot be the security boundary. </details>

<summary>2. Both the layout and the proxy read the session with `auth()` and redirect — the code looks identical. What's the real difference, and what survived the old (pre-CVE) pattern once the bypass happened?</summary>

**Sample Answer:** The code looks the same but the *layer* differs. The proxy is a separate filter standing in front of the app — CVE's header skipped exactly that filter. The layout is part of *rendering* the page — every route under `/dashboard` must go through its layout to render, so it cannot be skipped. The old pattern had an empty layout (only wrapped children) and all protection in middleware. When the bypass skipped middleware, the layout had nothing to fall back to, so the page leaked. The lesson: protect a page with *that page's own layout* — a check placed elsewhere can be skipped. The proxy's check is UX; the layout's check is security.

</details>

<details>
<summary>3. What does the `auth()` wrapper give the proxy, and why not parse cookies manually?</summary>

**Sample Answer:** The `auth()` wrapper injects the verified session into `req.auth` — the proxy instantly knows whether the request is signed in. Without the wrapper, the proxy would have to manually parse the cookie, decode the JWT, and verify it against `AUTH_SECRET` on every request. That logic is internal to Auth.js; re-implementing it in the proxy is both unnecessary and risky.

</details>

<details>
<summary>4. What is the difference between returning from the proxy and not returning, and what does each produce?</summary>

**Sample Answer:** Returning from the proxy is the proxy asserting itself — `NextResponse.redirect()` ends the request at the proxy and the browser is sent elsewhere. Not returning means the proxy has no objection, so the request passes through and the normal route renders. That's why routing rules are written conditionally: return when the rule fires (stop and redirect), otherwise fall through to normal rendering.

</details>

<details>
<summary>5. "Defense in depth" — how does it look in this layout + proxy setup?</summary>

**Sample Answer:** Defense in depth = multiple independent security layers so one failure doesn't collapse everything. Here: the proxy routing rule (keep a signed-in user off `/login`) is a convenience layer; the layout `auth()` check + redirect is the security layer. If the proxy is ever bypassed or misbehaves, the layout check still blocks unauthenticated access. Two locks on one door — if the first fails, the second holds.

</details>
