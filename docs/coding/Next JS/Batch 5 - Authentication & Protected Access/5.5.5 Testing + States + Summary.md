## Part 2 — Bug Hunt (When Something Breaks)

Projects almost always surface these at build time. Know them before they waste you:

**1. "Module not found" after a move/delete**
```
Cannot find module '.../app/secret/page.js'
```
A stale `.next` cache after a folder was moved/deleted (the `/secret` removal in 5.5.4, or the route-group move in 5.5.3). Fix:

```bash
rm -rf .next
npm run build    # or npm run dev
```

**2. Login redirects back to `/login`**

- The GitHub OAuth app's callback URL must be exactly `http://localhost:3000/api/auth/callback/github`. A different port makes GitHub refuse the redirect.
- After editing `.env.local`, **restart** the dev server — env vars are not hot-reloaded.
- Verify the app is enabled in GitHub: Settings → Developer settings → OAuth Apps → your app → Client ID/Secret match `.env.local`.

**3. "OAuthAccountNotLinked":** one email linked to two GitHub accounts — Auth.js refuses to merge. Fix: enable `allowDangerousEmailAccountLinking` (risky — don't in production) or make the user pick one account. For learning, just know the message.

**4. Bio doesn't update after save**

- Confirm `revalidatePath("/profile")` exists in the action, after the save.
- Two open tabs show stale vs. fresh because `revalidatePath` re-renders at the server — a tab already open won't auto-update until refresh.

**5. `ƒ Proxy (Middleware)` missing from build output**

- `proxy.ts` must live at the project **root** (not inside `app/`), with the exact name `proxy.ts`. Mixing names (`.js`, `middleware.ts`) silently disables it. Next 16: `proxy.ts` is current, `middleware.ts` is deprecated.

**6. "Missing `AUTH_SECRET`" warning**

- Generate it: `npx auth secret`; it writes to `.env.local`. In production this secret signs sessions — a leak lets anyone forge a session.

## Part 3 — Batch 5 Summary (The Whole Journey)

One table captures the entire arc — comparison only lands now that each concept is learned individually:

| Concern | Manual (v1 — 5.2, 5.3) | Auth.js (v2 — 5.4.x, 5.5.x) |
|---|---|---|
| Setup | Write hashing, session, cookie logic yourself | Config file + a route handler |
| Passwords | `bcryptjs` hash + compare, all hand-written | None — OAuth |
| Session persistence | `cookies().set()` / read / delete, hand-managed | Owned by Auth.js (`auth()` / `useSession()`) |
| Security reasoning | You decide attributes (`httpOnly`, `sameSite`, `secure`) | Library defaults + CVE-2025-29927 rules (no auth in proxy) |
| Control | Total | Within the library's abstractions |
| Best for | Learning; tiny apps where you want full control | Fast setup; GitHub/Google login |
| Data storage | Hardcoded or simple file | Still a file here — swaps to a DB next batch |

### Mental models earned in Batch 5

1. **HTTP is stateless; cookies are the bridge** (5.1) — without a cookie, "logged in" is forgotten between requests.
2. **Hashing is one-way; encryption is reversible** (5.2) — never store plaintext, compare hashes instead.
3. **Auth.js is a kit, not a magic box** (5.4) — providers, sessions, callbacks are configurable parts.
4. **Sessions read on the server, subscribed to on the client** (5.4.2) — `auth()` in Server Components, `useSession()` in Client Components.
5. **Security's right layer is the layout, not the proxy** (5.4.3) — CVE-2025-29927 made proxy-based auth bypassable, so enforcement lives in `layout.tsx`.
6. **Identity from session, app data from a store** (5.5.4) — bio is app data in `profiles.json`; name/email/avatar are GitHub identity via the session. Email is the shared key.

### Final project structure

```
member-dashboard/
├── auth.ts                  # Auth.js config (GitHub provider, JWT session)
├── proxy.ts                 # Routing only: signed-in + /login → /dashboard
├── .env.local               # AUTH_SECRET + GitHub ID/Secret
└── app/
    ├── api/auth/[...nextauth]/route.ts
    ├── actions.ts           # updateProfileAction
    ├── components/          # Navbar (useSession), ProfileForm (useActionState)
    ├── login/page.tsx       # signIn("github")
    ├── (protected)/         # layout: auth() + redirect
    │   ├── dashboard/page.tsx
    │   └── profile/page.tsx
    └── lib/
        ├── profiles.json    # app data (bio), keyed by email
        └── profiles.ts      # getProfileByEmail / saveProfile (upsert)
```

## Part 4 — What Carries Forward

The architecture patterns are batch-independent; next batch only swaps the data source:

- **Batch 6 — Database:** `profiles.json` becomes PostgreSQL. That buys real user IDs, relations, and concurrent-safe writes (file writes race under load). Session state would also move to a database-backed store for production. The *pattern* (data layer in `lib/`, Server Actions in `actions.ts`, revalidation on save) stays identical.
- **Ideas to explore on your own:** add a second provider (Google is one line next to GitHub); combine Credentials + OAuth; replace manual validation in actions with `zod`; add rate limiting on sign-in to resist brute force; add email verification on sign-up.

## In Your Own Words

<details>
<summary>1. Test checklist item 17 — pasting `/dashboard` in a signed-out window: what happens, and what does it prove?</summary>

**Sample Answer:** The browser lands on `/login` — the `(protected)/layout.tsx` `auth()` check redirects. It proves protection is **server-side, not client-side**: a refresh, a hard paste, or a raw `curl` all hit the same server-side check before the page renders. No URL, however typed, bypasses it.

</details>

<details>
<summary>2. When does `.next` go stale, and what's the fix?</summary>

**Sample Answer:** When the folder structure changes — moving pages into the `(protected)` group, or deleting the `/secret` folder. The dev/build cache still references the old paths ("Cannot find module..."). The fix is `rm -rf .next` then re-run `npm run dev` or `npm run build` so Next regenerates types. Stale build errors should be your first repro step.

</details>

<details>
<summary>3. What do upsert + `revalidatePath` guarantee together?</summary>

**Sample Answer:** Upsert keeps the file correct — first save inserts, later saves update the same record, no duplicates. `revalidatePath` keeps the rendered page correct — no stale cached bio. Together they guarantee that **on save, both the store and the UI are consistent** — the user always sees their latest bio. One without the other is incomplete: upsert without revalidate = new data, stale UI.

</details>

<details>
<summary>4. "Identity from session, data from form" — where is that rule visible in this project?</summary>

**Sample Answer:** On the dashboard, name/email/avatar come from `auth()` (GitHub identity — the user can't change them locally), while bio comes from `profiles.json` (app data — the user edits it). On the profile form, bio is an input field, but the action never reads an email field — it takes `session.user.email` directly. If email came from the form, someone could submit another user's email and overwrite their data. Identity is server-trusted (session); data is user-input (form) — hence the split.

</details>

<details>
<summary>5. From the tiny demo projects (Login v1/v2) to this full Member Dashboard — what architectural pattern repeated?</summary>

**Sample Answer:** The same one every time: data layer isolated in `lib/`, Server Actions in `actions.ts`, Server Components reading data and rendering, Client Components handling only UI and transient state (pending/error), and `revalidatePath` after every write. The demos had three files (hash/session/actions); the project expanded that exact pattern — an `auth.ts`, a data layer, an actions file, and client forms. Batch 6 keeps the pattern; only the data source swaps from file to database.

</details>
