## Part 2: Agar Kuch Na Chale — Bug Hunt

Project karte waqt yeh sabse common issues aayenge — pehle se jaan lo, test mein time bachta hai:

**1. "Module not found" build error**

```
Cannot find module '../../../app/secret/page.js'
```

Ye `.next` cache ka stale type-check hai — jab folder move/delete karte ho (4.5.4 mein `/secret` hataya, 4.5.3 mein folder move). Fix:

```bash
rm -rf .next
npm run build   # ya npm run dev
```

**2. Login ke baad wapas `/login` pe aa rahe ho**

- Callback URL mismatch: GitHub OAuth app mein callback `http://localhost:3000/api/auth/callback/github` hona chahiye — agar port alag ho (3001 etc.), GitHub redirect deny karega.
- `.env.local` change ke baad dev server **restart** karo — env vars hot-reload nahi hote.
- GitHub app ka status check karo: Settings → Developer settings → OAuth Apps → app → wahi Client ID/Secret env mein.

**3. Sign in button pe error "OAuthAccountNotLinked"** (edge case)

Ek email do alag GitHub accounts se linked. Auth.js conflict — account already kisi aur user se linked. Fix options: `allowDangerousEmailAccountLinking: true` (dangerous — na karo) ya user ko ek account choose karne ko bolo. Learning ke liye bas jaan lo.

**4. Bio save hone ke baad purani dikh rahi**

- `revalidatePath` likha hai? Action ke andar, save ke baad.
- Agar do tabs — stale tab purana dikhaata hai (browser client-side state, `revalidatePath` server render naya karta hai, par tab already open hai). Refresh karo.

**5. Build mein `ƒ Proxy (Middleware)` nahi dikh raha**

`proxy.ts` project **root** mein hai (`app/` ke andar nahi), aur file ka naam exactly `proxy.ts` — `.js`/`middleware.ts` mix mat karo. (Next 16: `proxy.ts` new, `middleware.ts` deprecated.)

**6. `AUTH_SECRET` missing warning**

Startup pe Auth.js shikayat karega. `npx auth secret` run karo ya `.env.local` mein daalo. Production mein yeh hi secret sessions sign karta hai — leaked toh koi bhi sessions forge kar sakta hai.

## Part 3: Batch 4 — Poora Summary

Ek table mein poora safar (ab sab concepts clear hain — compare/contrast table **ab** ban sakta hai):

| Cheez | Manual (v1 — 4.2, 4.3) | Auth.js (v2 — 4.4.x) |
|---|---|---|
| Setup | Khud sab likhna (hash, session, cookie) | Config file + route handler |
| Password | `bcryptjs.hash` + compare (sab khud) | Koi password nahi — OAuth |
| Session | Khud cookie set/read/delete (`cookies()`) | Auth.js manage karta hai (`auth()` / `useSession()`) |
| Security | Khud sochna (httpOnly, sameSite, secure) | Built-in defaults + hardcoded rules (middleware CVE) |
| Customization | 100% control | Auth.js ki abstractions ke andar |
| Use-case | Simple apps, full control chahiye | Quick setup, OAuth/GitHub login chahiye |

**Key mental models jo Batch 4 mein mile:**

1. **Cookies = state of the web** (4.1) — HTTP stateless, cookie bina koi "login" yaad nahi rehta.
2. **Hashing vs encryption** (4.2) — password never reversible; compare karte ho, decrypt nahi.
3. **Auth.js = kit** (4.4) — providers, sessions, callbacks — configure karo, reinvent mat karo.
4. **Session: server se read, client se subscribe** (4.4.2) — `auth()` server components, `useSession()` client.
5. **Security ki sahi layer** (4.4.3) — layout `auth()` + redirect main, proxy sirf routing. CVE-2025-29927 — proxy-based security bypassable, isliye no.
6. **Identity vs data** (4.5.4) — session se identity, file/db se app data, email common key.

**Is project ke final pieces:**

```
member-dashboard/
├── auth.ts                  # Auth.js config (GitHub provider, JWT session)
├── proxy.ts                 # Routing: logged-in + /login → /dashboard
├── .env.local               # AUTH_SECRET + AUTH_GITHUB_ID/SECRET
└── app/
    ├── api/auth/[...nextauth]/route.ts
    ├── actions.ts           # updateProfileAction
    ├── components/          # Navbar (useSession), ProfileForm (useActionState)
    ├── login/page.tsx       # signIn("github")
    ├── (protected)/         # layout: auth() + redirect
    │   ├── dashboard/page.tsx
    │   └── profile/page.tsx
    └── lib/profiles.json + profiles.ts   # data layer
```

**In Your Own Words**

1. Test checklist ka point 17 — logged-out browser mein URL paste karke kya hoga, aur isse kya prove hota hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `/dashboard` paste karne pe `/login` pe redirect hoga — `(protected)/layout.tsx` ka `auth()` check. Isse prove hota hai ki protection client-side nahi, server-side hai — browser refresh/paste/curl sab pe check chalta hai, kyunki redirect har request pe server render karne se pehle hota hai. URL paste karke koi bhi protected page pe access nahi kar sakta.

</details>

2. `.next` folder kab corrupt dikhta hai, aur fix kya hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Jab folder structure change hota hai — route groups mein move (4.5.3) ya folder delete (4.5.4 mein `/secret` hataya) — to `dev` aur `build` ke types stale ho jaate hain ("Cannot find module..."). Fix: `rm -rf .next` aur dobara `npm run dev` ya `npm run build` — Next types fresh generate karega. Bas build fail hone pe sabse pehle yeh try karna.

</details>

3. Upsert + `revalidatePath` ka combination — dono milke kya guarantee dete hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Upsert file ka data sahi karta hai (pehli baar add, baad mein update — duplicates nahi). `revalidatePath` server render ka cache sahi karta hai (purana bio nahi dikhegi). Dono milke: **save karte hi, file aur UI dono consistent** — user ko hamesha apna latest bio dikhta hai. Ek ke bina dusra adhoora: upsert without revalidate = data naya, UI purana.

</details>

4. "Identity session se, data form se" — is rule ka matlab project mein kahan dikhta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Dashboard pe naam/email/avatar session se aate hain (GitHub ka data, user change nahi kar sakta), bio file se (app ka data, user update kar sakta hai). Profile form mein bhi: bio input se aati hai (form), par `session.user.email` action se — form mein email input hi nahi hai. Agar form se email aata, koi doosri entry update kar sakta tha. Identity trusted source hai (session), data untrusted (form) — isliye alag.

</details>

5. Batch 4 mein chhote projects (Login Demo v1/v2) se full project tak — architecture ka kya pattern repeat hua?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Har baar wahi pattern: data layer alag (`lib/` files), server actions alag (`actions.ts`), server components data read karte hain, client components sirf UI + state (pending/error), revalidation har mutation ke baad. Demo mein 3 files (hash/session/actions), project mein wahi pattern expand hua — data file + auth config + actions + client forms. Yahi cheez Batch 5 mein bhi rahegi — bas data layer ka source badlega (file → database), pattern same.

</details>
