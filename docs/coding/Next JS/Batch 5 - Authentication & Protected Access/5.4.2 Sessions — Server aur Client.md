# Session Strategy — JWT

## Where We Left Off

In 5.3.1 we set `session: { strategy: "jwt" }` in the Auth.js config and moved on. This file explains why that line exists, what JWT strategy actually means for the app, and the practical consequences we will lean on in 5.3.3 and 5.4 — especially that **reading the session is a per-request verification**, and the cookie is a signed token, not a server-side row.

## Why Sessions Need a Strategy

Auth.js supports two ways to persist the session that exists after login:

- **JWT strategy** (the default and what we configured) — the session data (user id, name, email, image, expiry) is serialized into a **signed JWT** and stored in the cookie. No server-side record.
- **Database (server) strategy** — session data lives in a database row keyed by a random, opaque session ID kept in the cookie. The server must look that ID up on every request.

Both produce the same `session` object for application code — the difference is purely where the data lives and what the per-request cost is.

## JWT Strategy — The Token in the Cookie

Under JWT strategy:

1. After sign-in, Auth.js builds a payload: `{ user: { id, name, email, image }, exp: <expiry> }`.
2. It **signs** that payload with `AUTH_SECRET` and base64-encodes header + payload + signature into the `authjs.session-token` cookie.
3. On every subsequent request, the browser sends that cookie back. `auth()` decodes the JWT, verifies the signature against `AUTH_SECRET`, and returns the session.

So the session is **stateless**: there is no session table to query. The token carries its own proof — and tampering with any byte breaks the signature.

### What you can read from the session

The object returned by `auth()` is consistent and predictable:

```ts
{
  user: {
    name: string,
    email: string,
    image: string,   // GitHub avatar URL
  },
  expires: string,   // ISO timestamp where the JWT expires
}
```

`name`, `email`, and `image` arrive from GitHub during the OAuth callback; the application does not store them — they come fresh from the provider on each session construction. So the session object is identity, sourced and signed.

## Server Components — `auth()`

`auth()` is designed for the server. It reads the cookie from the request headers and verifies the JWT there. It is `async`, so it is used in `async` Server Components and Server Actions:

```tsx
import { auth } from "@/auth";

export default async function DashboardPage() {
  const session = await auth();

  if (!session) {
    // Not signed in — handle it.
  }

  return <p>Welcome, {session.user.name}</p>;
}
```

This is the privileged path: cookie → decode → verify → identity. Because it runs on the server, the signing secret never reaches the client, and the verification cannot be faked by the user.

## Client Components — `useSession()`

A Client Component executes in the browser. It cannot, and should not, hold `AUTH_SECRET` to verify the JWT itself. Auth.js exposes the data a different way: it provides a **`/api/auth/session` endpoint** that the server reads (it has the secret) and returns the verified session JSON. The Client Component gets that data through React Context, populated by `SessionProvider`:

```tsx
"use client";
import { SessionProvider, useSession, signIn, signOut } from "next-auth/react";

export default function Navbar() {
  const { data: session, status } = useSession();

  if (status === "loading") return <p>Loading...</p>;
  if (status === "unauthenticated") return <button onClick={() => signIn()}>Sign in</button>;
  return <span>{session.user.name} — <button onClick={() => signOut()}>Sign out</button></span>;
}
```

`useSession()` returns `{ data: session | null, status }` where `status` is one of `"loading"`, `"unauthenticated"`, or `"authenticated"`. That `loading` state is important: the client side starts empty and learns the session over a fetch, so a brief "who am I?" moment is expected.

`SessionProvider` must wrap any tree whose Client Components will call `useSession`. Typically that is the root layout:

```tsx
// app/layout.tsx
import { SessionProvider } from "next-auth/react";

export default function RootLayout({ children }) {
  return (
    <SessionProvider>{children}</SessionProvider>
  );
}
```

## The Divide, in One Sentence

- `auth()` — **server truth**: reads the signed cookie, verifies it, and the result is authoritative.
- `useSession()` — **client convenience**: trusts the server's verdict delivered via the session endpoint and Context; useful for UI, never for authorization.

## What About the Data Itself?

Because the session is a signed JWT, everything you read from `auth()` is **self-attested and signed**. You can rely on it because the signature is unforgeable without `AUTH_SECRET`. But it is also **encoded, not encrypted** — anyone can decode the payload. Never put secrets (internal IDs you don't want exposed, roles you don't want read) into it. Auth.js's own fields (name, email, image) are provider-sourced and fine; application secrets need server lookups or a separate store.

## What It Is NOT

- **A signed JWT that can be forged.** Tampering with the payload invalidates the signature; verification fails and `auth()` returns `null`.
- **`useSession()` as a security primitive.** The client can be reloaded, offline, or tampered with; the session endpoint answer is a view of server-side truth, not its source.
- **Identity stored persistently by the app.** The app receives identity from GitHub on each sign-in; Auth.js signs it. There is no persistent user row here.
- **JWT encryption.** The payload is visible. Signed ≠ encrypted.

## Nutshell

JWT strategy keeps the session in a signed cookie — stateless, no server record — and `auth()` verifies that signature on the server to produce the session object (`user.name`, `user.email`, `user.image`, `expires`). Server Components use `auth()` (authoritative, async). Client Components use `useSession()` via `SessionProvider` because they cannot verify the JWT themselves — they read the server-verified verdict from the session endpoint. `status` cycles through `loading` → `unauthenticated`/`authenticated`. The cookie carries signed identity, not app secrets.

## In Your Own Words

<details>
<summary>1. What does `session: { strategy: "jwt" }` change versus leaving it unset?</summary>

**Sample Answer:** It makes the session a signed JWT stored in the cookie, rather than an opaque ID that the server must look up in a database/session store. Every request is then self-verifying — no per-request DB round trip — at the cost of server-side revocation (the token lives until expiry regardless of server state).

</details>

<details>
<summary>2. Why can a Client Component not verify the session cookie the same way a Server Component can?</summary>

**Sample Answer:** Verifying the JWT requires `AUTH_SECRET`, which must never leave the server. A Client Component runs in the browser, where its code (including any embedded secret) is exposed. So the client cannot verify; instead the server verifies via the `/api/auth/session` endpoint and shares the verdict through Context, which `useSession()` reads.

</details>

<details>
<summary>3. What are the three `useSession` statuses and what does each mean for rendering?</summary>

**Sample Answer:** `loading` — the session hasn't been fetched yet; render a neutral state. `unauthenticated` — no valid session; show sign-in. `authenticated` — a session exists; show the user's data and sign-out. Handling `loading` explicitly prevents a flash of "signed out" content before the fetch resolves.

</details>

<details>
<summary>4. Why is a signed JWT "encoded, not encrypted," and what must that never contain?</summary>

**Sample Answer:** The payload is base64-encoded for transport and integrity-signed, but anyone can decode and read it. So it must never contain secrets — internal database IDs, roles, tokens, anything the user shouldn't see. Auth.js's own fields (name, email, image from the provider) are safe; application secrets need server lookups instead.

</details>

<details>
<summary>5. In one sentence, when to use `auth()` versus `useSession()`?</summary>

**Sample Answer:** Use `auth()` (server-side) for protection and trusted identity; use `useSession()` (client-side) only for interactive UI that needs to react to who the user is.**
