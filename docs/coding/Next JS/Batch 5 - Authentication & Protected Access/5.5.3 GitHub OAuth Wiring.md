## Step 4: Navbar — Static Se Dynamic

4.5.2 ka static Navbar (sirf links) ab **session-aware** version se replace karo — 4.4.2 wala pattern. **Poora file state** (naya hissa `// NEW` se mark hai):

**File:** `app/components/Navbar.tsx` (update)

```tsx
"use client";                                            // NEW

import { useSession, signIn, signOut } from "next-auth/react";   // NEW: imports

export default function Navbar() {
  const { data: session, status } = useSession();        // NEW

  return (
    <nav style={{ display: "flex", justifyContent: "space-between", padding: 12 }}>
      <span style={{ fontWeight: "bold" }}>MemberHub</span>
      <div style={{ display: "flex", gap: 12, alignItems: "center" }}>
        <a href="/">Home</a>
        <a href="/dashboard">Dashboard</a>
        <a href="/profile">Profile</a>
        {status === "loading" && <span>Loading...</span>}             {/* NEW */}
        {status === "unauthenticated" && <a href="/login">Login</a>}  {/* NEW */}
        {status === "authenticated" && (                              {/* NEW */}
          <button onClick={() => signOut()}>Logout ({session?.user?.name})</button>
        )}
      </div>
    </nav>
  );
}
```

**Kya badla:**
- Static "Login" link → **teen states**: loading / Login link / Logout + naam
- Logout button `signOut()` se — 4.5.2 mein koi logout nahi tha
- `session?.user?.name` — GitHub ka naam, authenticated state mein

## Step 6: `(protected)` Route Group — Dashboard + Profile Lock Karna

4.5.1 ke plan mein kaha tha — dashboard aur profile dono `(protected)` group mein, ek layout dono ko protect karega. Ab move karte hain:

```bash
# dashboard aur profile ko group ke andar le jao
mkdir app/(protected)
# app/dashboard/* ko app/(protected)/dashboard/ mein move karo
# app/profile/* ko app/(protected)/profile/ mein move karo
```

**(Folder move ka matlab kya?)** Route group (Batch 1 ka concept) — parentheses wala folder URL mein nahi dikhta. `/dashboard` waise hi khulega, bas file ab `app/(protected)/dashboard/page.tsx` hai. Organization + ek parent layout milega.

**File:** `app/(protected)/layout.tsx` (nayi file — 4.4.3 wala protection, ab group level pe)

```tsx
// app/(protected)/layout.tsx
import { redirect } from "next/navigation";
import { auth } from "@/auth";

export default async function ProtectedLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const session = await auth();
  if (!session) {
    redirect("/login");
  }
  return <>{children}</>;
}
```

**Notice kiya?** 4.4.3 mein `/dashboard/layout.tsx` tha — ab wahi check `(protected)/layout.tsx` mein hai, aur **dashboard + profile dono ko cover karta hai.** Naya protected page banao toh usme bhi automatically lagu. Yehi route group ka payoff hai.

## What It Is NOT

- **Ye phase "dynamic data" nahi hai** — dashboard/profile mein abhi bhi hardcoded Pravin data dikhega (sirf ab lock hai). Asli session data 4.5.4 mein aayega. Wiring aur data alag steps — confusion na ho.
- **Login hone ka matlab profile ka data sahi nahi** — abhi bio file se nahi aa rahi, hardcoded hai. 4.5.4.
- **Route group `(protected)` "hidden route" nahi** — yeh sirf organization hai; URL wahi rehta hai. Security layout check se hai, group se nahi.

## Common Mistakes

- **Move karte waqt URLs/imports** — folder move ke baad pages ke imports (agar relative ho) fix karo. `@/` alias use karte ho toh problem nahi.
- **`(protected)` group ke andar `page.tsx` mat banao** — group ka layout sirf layout hai; group URL `/` pe koi page nahi banata. Pages `(protected)/dashboard` wagera mein.
- **Proxy ka rule sirf "logged-in + /login → dashboard"** — reverse (dashboard → /login) proxy mein mat karo, woh layout karta hai. Loop bachta hai (4.4.3 wala point).
- **Env vars ke baad dev server restart** — `.env.local` change pe `npm run dev` dobara.

## Nutshell

Auth wiring: env vars (`AUTH_SECRET` + GitHub creds) → root `auth.ts` + `[...nextauth]` route handler → layout mein `SessionProvider` → Navbar session-aware (3 states) → login page real `signIn("github")` → dashboard/profile `(protected)` group mein move + group layout mein `auth()` + redirect → `proxy.ts` routing. Ab sab pages locked hain — par data abhi hardcoded.

**In Your Own Words**

1. Dashboard aur profile ko `(protected)` group mein move karne se kya mila — bina group ke kya karna padta?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Bina group ke har protected folder ka apna `layout.tsx` banana padta — dashboard ka layout, profile ka layout, aur naye protected page pe phir se. Group `(protected)` dono ko ek parent ke under laata hai jisme ek hi layout hai — `auth()` check ek baar, dashboard + profile dono protected, aur future protected pages automatically cover. URL pe koi fark nahi — `/dashboard` waise hi hai, route group sirf folder organization hai.

</details>

2. Navbar teen states wali UI kyun — static "Login" link se kya problem thi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Static link har user ko dikhta tha — logged-in user ko bhi "Login" dikhana galat hai (woh toh already login hai). Session-aware navbar alag-alag situation alag dikhaata hai: loading (session abhi fetch ho raha), unauthored (Login link), authenticated (naam + Logout). Yahi UX hai jo real apps mein hoti hai — user ko uski state ke hisaab se sahi action dikhta hai. `useSession()` ka `status` hi teeno states deta hai.

</details>

3. Login page mein `if (session) redirect("/dashboard")` — aur proxy mein bhi "logged-in + /login → dashboard" — yeh dono check duplicate nahi hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Nahi — alag layers hain. Login page ka check sirf login page render hone se pehle chalta hai (server component level). Proxy har request pe sab routes ke liye chalta hai (routing level, render se pehle). Dono same result dete hain, par proxy se redirect faster (render hi nahi hota) aur ek jagah global hota hai. Yehi defense-in-depth hai — 4.4.3 wala pattern. Jabki security wala check (bina login /dashboard) sirf layout mein hai, proxy mein nahi — woh CVE rule.

</details>

4. `(protected)/layout.tsx` mein `auth()` check ka matlab — profile page ko alag check ki zaroorat kyun nahi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Layout `(protected)` group ke saare children ko wrap karta hai — dashboard aur profile dono. Layout render hone pe pehle `auth()` chalta hai, session nahi toh redirect — **children (pages) render hi nahi hote.** Toh profile page khud check nahi karta kyunki woh kabhi bina login render ho hi nahi sakta — layout ne pehle hi roka. Ek jagah check, sab pages protected.

</details>

5. Is phase ke end mein dashboard ka data abhi bhi hardcoded kyun — "wiring done" hone ke baad bhi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Kyunki phase ka kaam sirf auth wiring hai — login kaam karta hai, routes locked hain, navbar session dikhaata hai. Abhi data ka source session aur file banana baaki hai — woh 4.5.4 ka scope (dynamic data). Ek phase ek kaam: 4.5.2 design, 4.5.3 auth wiring, 4.5.4 data. Agar sab ek saath karte, toh error aane pe pata nahi chalta ki wiring mein hai ya data mein — wahi hardcoded-first ka logic.

</details>
