### Route Grouping — `(protected)`

In 5.4.3 we protected `/dashboard` with `/dashboard/layout.tsx`. Now both dashboard and profile must be gated by the same check — so they share one layout via a **route group**:

```
app/(protected)/
  layout.tsx          ← single auth() check + redirect
  dashboard/page.tsx
  profile/page.tsx
```

Route groups (the Batch 1 concept) don't appear in the URL — `/dashboard` and `/profile` are still their real paths — but they let **one layout protect both pages**. Adding a new protected page later slides into the group and inherits protection automatically.

```
app/
  (protected)/
    layout.tsx        ← one auth() + redirect
    dashboard/page.tsx
    profile/page.tsx
  components/
    Navbar.tsx
  lib/
    profiles.ts
    profiles.json
  actions.ts
  layout.tsx          ← SessionProvider + Navbar (root layout)
  login/page.tsx
  page.tsx            ← Home
```

## Question 3 — What Is the Data Shape?

Rule from 3.4.1 and 4.5.1: **data shape follows the UI, never the reverse.** Think about what each page renders.

- **Dashboard** shows: name, email, avatar (GitHub photo), and bio. Name/email/avatar come from the **session** (`auth()`) — GitHub provided them. No app-side copy needed; that's exactly the OAuth advantage from 5.4.
- **Profile** shows the same details plus an **editable bio field**. Here a new need appears: where does the bio live?

GitHub's profile has a bio, but it isn't part of the session (Auth.js fetches only name/email/image), and even if it were, editing it in *our* app can't write back to GitHub (OAuth scope doesn't permit it). So bio must be stored **app-side** — the same file-store pattern from Batch 3:

```json
// lib/profiles.json
[
  { "email": "pravin@example.com", "bio": "Learning Next.js" }
]
```

```ts
// Profile type — each field justified by the UI
export type Profile = {
  email: string;   // why: the user's identity; session provides it; profile is keyed by it
  bio: string;     // why: the only editable app-specific field
};
```

Field reasoning:

- **`email`** — the user's identity, sourced from the session. The profile file is keyed by email so we can look up a user's bio without storing identity in our own file.
- **`bio`** — the only piece of data the user edits *within this app*. Everything else (name, avatar) is display-only and fresh from GitHub.

## Question 4 — How Does Data Flow?

```
IDENTITY (who they are)              APP DATA (bio)
GitHub → Auth.js → auth() session    profiles.json → profiles.ts
        ↓                            ↓
   dashboard / profile pages        profile edit form
   (name, email, avatar)            updateProfileAction (Server Action)
                                         ↓
                                    writeFileSync + revalidatePath
```

Identity and app data come from **two different sources**:

- **Identity** — from GitHub, through the session. Never duplicate it into app storage (the source of truth is the provider; `auth()` returns it fresh each request).
- **App data** — the `bio`. This is the one thing the user edits here and now, and it uses Batch 3's Server Action pattern for mutation.

Profile-update flow, step by step:

1. User submits the bio form on the profile page.
2. `updateProfileAction` (Server Action) reads `auth()` to get the email — the session is verified server-side, so the email is trusted. The user never types it.
3. The action upserts into `profiles.json` by email (insert on first save, update thereafter) via `writeFileSync`.
4. `revalidatePath("/profile")` triggers a re-render so the saved bio appears.
5. `useActionState` supplies the `pending` state and surfaces success/error messages to the UI.

## Why Plan Before Code?

Skip planning and you restructure mid-build. That's sharper here than most, because identity (GitHub) and app data (file) live in **two separate stores**. Deciding up front which piece comes from where means the code is execution only — no structural rework. It also locks in the `(protected)` route group so pages aren't shuffled between folders later. 5.5.2 builds the hardcoded UI first (confirm the look with static data), then 5.5.3 wires real auth, then 5.5.4 swaps in dynamic data and the update action.

## In Your Own Words

<details>
<summary>1. Why does identity (name/email/avatar) come from GitHub and not from an app file — what does "two sources" mean here?</summary>

**Sample Answer:** Name, email, and avatar have GitHub as the **source of truth** — the user edits them there, and `auth()` returns them fresh on every request. Storing a copy in an app file creates duplication and drift: if the user renames themselves on GitHub, the copy stays stale. Application data (the bio) is different — it's data the user edits *only in this app*, so this app's file is the correct source of truth for it. Identity comes from the provider; application data comes from your store.

</details>

<details>
<summary>2. Why group both dashboard and profile under `(protected)` instead of just `/dashboard/layout.tsx`?</summary>

**Sample Answer:** `/dashboard/layout.tsx` only guards the dashboard subtree — profile sits in its own folder and would need a second layout. A `(protected)` route group puts both under one parent layout that runs the single `auth()` + redirect check, so **one layout protects both pages**. New protected pages dropped into the group inherit protection automatically. The group isn't a folder in the URL — `/dashboard` and `/profile` are still their real paths; only the organization changes.

</details>

<details>
<summary>3. Profile only stores `email` and `bio` — why not name and avatar too?</summary>

**Sample Answer:** Because data shape follows the UI. Name and avatar are **display-only** values that come fresh from the session — copying them into file storage creates redundant data with no benefit, and risks going stale. Only data the UI lets the user **edit** and that doesn't come from the provider belongs in storage — here, just the bio, keyed by the session email. Add a field only when the UI needs it *and* the provider can't supply it.

</details>

<details>
<summary>4. Why does `updateProfileAction` read the email from the session rather than from the form?</summary>

**Sample Answer:** Email is identity. If it came from a form field, a user could type another person's email and attempt to overwrite their profile. The Server Action calls `auth()`, which reads the verified session cookie server-side — that email is trustworthy and not user-input. The form supplies only the data the user is permitted to edit (the bio); identity always comes from the server.

</details>

<details>
<summary>5. What's the biggest payoff of planning before coding in this project?</summary>

**Sample Answer:** The two-source split (GitHub identity vs. file-based app data) is resolved *before* any code is written, so there's no temptation to duplicate identity into storage or to fetch the wrong thing in the wrong place. The route structure is also locked early — the `(protected)` group is decided, so pages aren't shuffled between folders mid-build. Planning fixes the decisions; the code then only executes.

</details>
