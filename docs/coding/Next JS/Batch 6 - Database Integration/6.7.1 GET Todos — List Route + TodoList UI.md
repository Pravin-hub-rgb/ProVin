In 6.6, the API design was thought through — resources, methods, status codes, error shapes. Now we implement that design **practically**. But one thing has changed significantly.

**So far, in every project you've built — you created an API route and tested it with curl/browser, seeing raw JSON. But think — does any real project get built like this?** Does any user run `curl` against a site, or stare at raw JSON in the browser? The user sees a **page** — a list, buttons, forms. Backend and frontend run **together**.

So 6.7 is a small series — **from 6.7.1 to 6.7.4**. In each file: we'll build a specific route, **and the UI that talks to that route**. By the end of each step, the browser shows a **real project** — not raw JSON.

# GET /api/todos — List Route + TodoList UI

## Step 1 — Route: Fetch All Todos

**THINK:** The simplest thing first — display a list. If `/api/todos` receives a GET request, how do we fetch all todos from the database and send them back as JSON? The model is ready (6.5), the connection is ready (6.4) — now just wire them together.

**CONCEPT:** Before writing the route handler file, think about the fundamental question: where does the data come from? The database. Each piece is solved one-by-one, then combined:

**Question 1 — Where does the connection come from, and should we create a new one each time?** Database queries need a connection — without it, nothing works. But if each route creates its own fresh connection, every request pays the cost — that's wasteful. That's why in 6.4, `connectDB()` was made a **singleton** — the first call opens connection, all subsequent calls reuse it. So each route just calls `await connectDB()` as its first line — calling it repeatedly is safe, only one connection is ever created.

**Question 2 — How do we fetch all todos?** Mongoose gives every model methods — `Todo.find()` returns **all** documents in the collection. The name says it all — "find" = search and return everything.

**Question 3 — In what order?** `find()` returns data in raw order — we don't know which comes first. The user wants the newest todos first. So `.sort({ createdAt: -1 })` — sorts by the `createdAt` field, with `-1` meaning **descending** (newest first). (Ascending would be `1`, but here the use case is "newest first".)

**Question 4 — What does the response look like?** `NextResponse.json(todos, { status: 200 })` — converts the todo array to JSON body with a status code. A successful GET = **200** (we decided this in 6.6.)

**Question 5 — What if the database is down?** The query can fail — connection failure, network issue. So everything goes inside a `try`, and in `catch` we return **500** — the server's fault (6.6 design). `console.error` logs the error server-side for debugging. The user never sees the log — only `{ error }` JSON.

**File:** `app/api/todos/route.ts` (new file — `route.ts` is the convention we learned in Batch 3: the folder path becomes the API endpoint.)

We'll understand the code in two parts — first the file's top (imports), then the full function. Each snapshot shows the **complete file** so the connection is visible.

**First — imports (top of file):**

```ts
// app/api/todos/route.ts
import { NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";
```

Three imports at once — first three lines of the file. Explained line-by-line:

- **`NextResponse`** — for sending responses. `NextResponse.json()` sets JSON body + status code (the same pattern as Batch 3.1.)
- **`connectDB`** — the singleton connection from 6.4. **Why the path `@/app/lib/db`?** Because `db` file lives at `app/lib/db.ts` in your project (created in 6.4). `@/` is the project root, so `@/app/lib/db` → `app/lib/db.ts`.
- **`Todo`** — the model from 6.5 (`app/models/Todo.ts`). Its methods (`find`, `create`) are what actually talk to the database.

**Now — imports + full GET function (complete file):**

```ts
// app/api/todos/route.ts
import { NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";

export async function GET() {
  try {
    await connectDB();
    const todos = await Todo.find().sort({ createdAt: -1 });
    return NextResponse.json(todos, { status: 200 });
  } catch (error) {
    console.error("Todos fetch error:", error);
    return NextResponse.json({ error: "Unable to fetch todos" }, { status: 500 });
  }
}
```

Same imports — below them now the full `GET` function. Explanation line-by-line:

- **`export async function GET()`** — The Route Handler contract: the exported function's name IS the HTTP method. It's `async` because we'll `await` database calls inside.
- **`try`** — the start. Talking to a database can throw errors — everything goes here so `catch` can handle it (Question 5).
- **`await connectDB()`** — connection ready first (Question 1). The query won't run without it — 6.4's singleton, so calling on every route is safe.
- **`Todo.find().sort({ createdAt: -1 })`** — fetch all todos, newest first (Question 2-3). `await` is required — this returns a Promise, the data takes time to arrive from the database.
- **`NextResponse.json(todos, { status: 200 })`** — send the todo array as JSON with 200 (Question 4).
- **`catch` + 500** — any error (database down, connection failure) lands here. `console.error` logs server-side (Question 5), and the user gets `{ error }` with 500.

**TEST:** Run `npm run dev`, open `http://localhost:3000/api/todos` in the browser. If the database still has 6.5's "First real todo", it should appear. If empty, you'll see `[]`. The route works — now for the real task: **hook this route up to the UI.**

## Step 2 — UI: Display Todos on a Page

**THINK:** Now when you open `/api/todos` in the browser, you see raw JSON. But does any user look at that? No — they need a **page** where todos appear as a list. Which means: a component that fetches `/api/todos` on page load and renders the data. Remember Batch 3.1's `ShowComments`? Same pattern — `fetch` inside `useEffect`, store in `useState`, then render.

**CONCEPT:** Think about file structure before diving in — instead of stuffing everything in one component, **split into separate components** (Batch 3 already did this — list and form were separate). That's how real projects are structured:

```
app/
├── page.tsx                 ← Server Component — renders TodoApp
├── types.ts                 ← Shared type — Todo's shape, imported everywhere
└── components/
    ├── TodoApp.tsx          ← Client — "brain": owns state + fetch all here
    └── TodoList.tsx         ← Presentational — just displays (receives data via props)
```

**Question 1 — What's in `page.tsx`?** The home page is still 6.5's test page — which auto-ran `Todo.create({ title: "First todo" })` on every reload (causing accidental duplicate todos!). We replace that — now the page renders **TodoApp**. `page.tsx` needs no React hooks — it just renders a component — so it stays a **Server Component** (the default).

**Question 2 — Where to store the data?** The data changes (loading → fetched → error), so **`useState`** is needed — three states: `todos` (the data), `loading` (currently fetching), `error` (something broke). All of this lives in `TodoApp.tsx`.

**Question 3 — How does the fetch on page load happen?** `useEffect` with an empty dependency array `[]` — runs once, on mount. This pattern was used in Batch 3.1. And one important point: **`loadTodos` is a separate function** — because in 6.7.2 (after POST/DELETE/PUT), we'll need to **call it again** to refresh the list. For now it runs on mount — later, after mutations too.

**Question 4 — How does TodoList get the data?** Via props. `TodoApp` owns the state and passes `<TodoList todos={todos} loading={loading} error={error} />`. `TodoList` never fetches on its own — it just renders. This split exists because one component should reason about data, another should just render. (Batch 3.3.2 used this same split — the list received data via props.)

**Question 5 — Why doesn't `TodoList` need `"use client"`?** Because it's imported by `TodoApp` (a client component) — children of a client component automatically end up in the client bundle. `"use client"` only needs to be on the file where hooks actually live (that's `TodoApp` here). `TodoList` has no hooks — just renders props — so no directive needed.

### 2.2 `TodoApp.tsx` — Brain: State + Fetch

**File:** `app/components/TodoApp.tsx` (new file — create the `components/` folder.)

But first — a small piece of work: the **shared home of the Todo type**. The `Todo` shape is needed in **two** places: `TodoApp` (for state) and later `TodoList` (for props). Copy the shape in two files? No — **define once, import everywhere** (the same DRY concept from Batch 1's data layer). So first we create `app/types.ts`:

```ts
// app/types.ts
export type Todo = {
  _id: string;
  title: string;
  done: boolean;
  createdAt: string;
  updatedAt: string;
};
```

**`export type Todo`** — `export` so other files can import it. The shape matches exactly what the model from 6.5 defines — and the API returns the same fields, so the UI and database shapes align. Any component can now do `import type { Todo } from "@/app/types"` — defined in one place, consistent everywhere.

**Now the top of TodoApp — imports + states + `loadTodos`:**

```tsx
"use client";

import { useEffect, useState } from "react";
import TodoList from "./TodoList";
import type { Todo } from "@/app/types";

export default function TodoApp() {
  const [todos, setTodos] = useState<Todo[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  const loadTodos = async () => {
    try {
      const res = await fetch("/api/todos");
      if (!res.ok) throw new Error("API error");
      const data = await res.json();
      setTodos(data);
      setError(null);
    } catch {
      setError("Unable to load todos");
    } finally {
      setLoading(false);
    }
  };
```

Explained line-by-line:

- **`"use client"`** — this file has React hooks (`useState`, `useEffect`) — hooks only run on the client, so this directive is required (the rule from Batch 3).
- **Imports** — `useState`/`useEffect` from React, `TodoList` from this app's own component, and the **`Todo` type from `@/app/types`**. `import type` — purely for types; after compilation, no trace of it exists in runtime code.
- **Three states (Question 2)** — `todos` array (starts empty), `loading` (initially `true` — spinner shows immediately on page open, fetch already starting), `error` (`null` — no error yet). TypeScript types each state.
- **`loadTodos` function (Question 3)** — explained step by step:
  - `await fetch("/api/todos")` — sends a GET to our own route (relative URL — same app). This is a **client-side fetch** — request goes browser → server.
  - `if (!res.ok) throw ...` — `fetch` does NOT throw on HTTP errors — a 500 still resolves as "ok". So checking manually: `res.ok === false` (on 4xx/5xx) → throw.
  - `await res.json()` — parses the JSON response body into a JS array (Batch 3 pattern).
  - `setTodos(data)` — store in state.
  - `setError(null)` — on success, clear any previous error. **Note: why not `setLoading(true)` at the start?** Two reasons: (1) `loading` already starts as `true`, so the spinner shows without needing a reset; (2) a linting concern — `set-state-in-effect` — React's linter flags synchronous `setState` inside an effect. The rule is conservative: it can't tell that `setLoading(true)` would be after an `await`. But here's an honest note: `setLoading(true)` at the top of `loadTodos` would actually be fine because of the `await` before any React render cycle closes — but the linter doesn't track that, so we just rely on the initial `true` state. This same pattern appears in mutation handlers in 6.7.2–6.7.4.
  - `catch` — any error (network failure, 500) → `setError` with a message.
  - `finally { setLoading(false) }` — whether it succeeded or failed, **loading always stops** (`finally` runs in both cases.)

**A note on the lint warning:** After this pattern, you may see a lint error on the `loadTodos()` line inside the effect — *"Setting state synchronously within an effect."* This is **not a bug** — it's a known false positive of the `set-state-in-effect` lint rule (React's GitHub issue #34905). The rule's linter can't track that `setState` calls happen after an `await` within an async function. We'll put a small `eslint-disable-next-line` comment above that line — just to silence the linter on that one flagged line, while keeping all other hook rules active.

**Now the `useEffect` + render — full component:**

```tsx
"use client";

import { useEffect, useState } from "react";
import TodoList from "./TodoList";
import type { Todo } from "@/app/types";

export default function TodoApp() {
  const [todos, setTodos] = useState<Todo[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  const loadTodos = async () => {
    try {
      const res = await fetch("/api/todos");
      if (!res.ok) throw new Error("API error");
      const data = await res.json();
      setTodos(data);
      setError(null);
    } catch {
      setError("Unable to load todos");
    } finally {
      setLoading(false);
    }
  };

  useEffect(() => {
    // eslint-disable-next-line react-hooks/set-state-in-effect
    loadTodos();
  }, []);

  return (
    <div>
      <h1>Todo List</h1>
      <TodoList todos={todos} loading={loading} error={error} />
    </div>
  );
}
```

The code above is identical — now two more things join it:

- **`useEffect` with `[]`** — calls `loadTodos()` once, on mount. **Why `[]`?** An empty dependency array = runs only on mount. `loadTodos` is not in the array — we don't want to re-run whenever the function reference changes, only on first mount. (Same pattern as Batch 3.1.) The `eslint-disable-next-line` comment above — recall the note about the `set-state-in-effect` false positive? That's what this comment addresses — the linter's conservative tracking of async state updates.
- **Render** — heading + `TodoList` receiving all three states as props (Question 4). `TodoApp` reasons about data; `TodoList` just renders.


**Props destructuring** — receives `todos`, `loading`, `error` from the parent. This is the **same shared type** defined in `app/types.ts` — imported here, not redefined. The inline type annotation declares the prop types alongside the destructure. (Data arrives via props, this component doesn't fetch anything itself — Questions 4-5.)

**Now — full signature + render logic (complete component):**

```tsx
import type { Todo } from "@/app/types";

export default function TodoList({
  todos,
  loading,
  error,
}: {
  todos: Todo[];
  loading: boolean;
  error: string | null;
}) {
  if (loading) return <p>Loading...</p>;

  if (error) return <p>{error}</p>;

  if (todos.length === 0) return <p>No todos yet — add one in 6.7.2.</p>;

  return (
    <ul>
      {todos.map((todo) => (
        <li key={todo._id}>
          <span>{todo.title}</span>
          {todo.done && <em> (done)</em>}
        </li>
      ))}
    </ul>
  );
}
```

Same signature — below: **the three states + render logic.** Explained:

- **Loading state** — while the fetch is running, just show "Loading..." — don't render the list, there's no data yet.
- **Error state** — if something went wrong (database down, network), show the error message instead of the list.
- **Empty state** — if the database is empty, show "no todos yet" — a friendly empty message instead of a blank list. (This is the 6.6 rule: an empty list returns `[]`, not a 404 error.)
- **List render** — `todos.map()` renders each todo in an `<li>`. **`key={todo._id}`** — React needs a unique identifier per item (Batch 1 rule) — Mongo's `_id` is perfect (unique + permanent). `todo.done && ` renders "(done)" after todos that are marked complete — for now it's display-only; the toggle button comes in 6.7.4.

**TEST:** Open `http://localhost:3000` in the browser. No more raw JSON — a page now displays the todo list. If the database still has 6.5's "First real todo", it'll show in the list. You'll see a brief "Loading..." flash, then the data. This is the real-project pattern — the user sees a page, not an API response.

## Nutshell

GET route: `Todo.find().sort({ createdAt: -1 })` fetches all todos (newest first), returns 200. UI: `TodoApp` (client component) calls `fetch("/api/todos")` in `useEffect([])`, stores results in `useState` (three states — data/loading/error), and passes them to `TodoList` (presentational) via props. `TodoList` renders states in order — loading, error, empty, then the list. `page.tsx` (a Server Component) just renders `<TodoApp />`.

## What It Is NOT

- **Client-side fetch is always wrong** — that's not true. In Batch 3.3, Server Components were better _in that context_ (internal Next app data). Here, we're explicitly practicing **frontend↔backend integration** through a REST API — client fetch is the pattern for this batch. The right-vs-wrong decision gets explained in 6.12.
- **`TodoList` doesn't need `"use client"`** — it's imported by a client component (`TodoApp`), so it automatically lands in the client bundle. The directive only needs to be on the file where hooks live.
- **Checking `res.ok` is optional** — it's not. `fetch` doesn't throw on HTTP errors — a 500 still resolves. Without the check, broken data from a failed request could corrupt the UI instead of showing an error.
- **`finally` is unnecessary** — it's not. `loading` must stop on both success AND failure. `finally` guarantees it runs in both branches. Omitting it leaves the spinner spinning forever on error.
- **UI replaces the API** — not true. The route handler still exists and is independently testable via Postman (6.8). The UI is just one consumer of the API — a mobile app would consume it the same way.

**In Your Own Words**

1. `page.tsx` stays a Server Component, but `TodoApp.tsx` needs `"use client"` — why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `page.tsx` has no React hooks — it just renders `<TodoApp />`. A Server Component that renders without hooks is fine and is actually preferred (less client bundle). `TodoApp` has `useState` and `useEffect` — hooks only run on the client, so `"use client"` is required. The rule: put the directive on the file where hooks _live_, not "this is a page so it's a client component."

</details>

2. `TodoList` has no `"use client"` — will it break?

<details>
<summary>Show Answer</summary>

**Sample Answer:** No — because `TodoList` is imported by `TodoApp` (a client component). Children of a client component are automatically bundled for the client — the boundary is inherited. `TodoList` has no hooks of its own, it just renders props — so it doesn't need its own directive. `"use client"` marks the boundary; that boundary is already established by `TodoApp`.

</details>

3. `useEffect(() => { loadTodos(); }, [])` — what does `[]` do, and why not put `loadTodos` in the dependency array?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The empty array `[]` means the effect runs exactly once — on mount. `loadTodos` isn't in the array because we don't want it to re-run every time the function reference changes — we only want the initial fetch on mount. (React creates a new function reference on every render; `[]` ensures it only executes the first time.) Refetching after mutations happens in 6.7.2 via direct calls, not through this effect.

</details>

4. Why write `if (!res.ok) throw new Error("API error")` — doesn't `fetch` throw on its own?

<details>
<summary>Show Answer</summary>

**Sample Answer:** No — `fetch` only throws on **network-level** failures (server unreachable). HTTP errors (404, 500) still resolve as "successful" — `res.ok` becomes `false`. Without this manual check, a 500 error response's JSON body might get passed to `setTodos(data)` and break the UI. You have to check `res.ok` yourself — this is the standard practice when integrating with REST APIs.

</details>

5. `TodoList` receives `todos` via props — why doesn't it fetch its own data?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Separation of concerns. `TodoApp` owns all the data state — and in 6.7.2–6.7.4 it will also handle mutations (create/delete/toggle) and refreshing the list after them — so the data logic lives in one place. `TodoList` just renders — it doesn't know or care whether the data came from a database, an API, or test fixtures. These are called **presentational components** — they receive data via props and don't care about the source. This split makes adding the delete button (6.7.3) trivial later.

</details>
