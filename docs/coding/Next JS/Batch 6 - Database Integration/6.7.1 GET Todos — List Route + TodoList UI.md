# GET /api/todos — List Route + TodoList UI

## Step 1 — Route: Saare Todos Fetch Karna

**SOCH:** Sabse basic — list dikhana. `/api/todos` pe GET aaye toh database se saare todos nikalo aur JSON mein bhejo. Model ready hai (6.5), connection ready hai (6.4) — bas jodna hai.

**CONCEPT:** Route handler file banane se pehle socho — data kahan se aayega? Database se. Ek-ek cheez problem ke saath samjho, phir code:

**Sawaal 1 — connection kahan se aayega, aur kya har baar naya banana padega?** Query database pe chalti hai — connection ke bina kuch nahi hoga. Par agar har route apna naya connection banaye, toh har request pe naya connection = heavy. Isliye 6.4 mein humne `connectDB()` ko **singleton** banaya tha — pehli call pe ek connection banta hai, baaki calls wahi reuse karte hain. Isliye har route ki pehli line `await connectDB()` hoti hai — baar-baar call karna safe hai, connection ek hi banta hai.

**Sawaal 2 — saare todos kaise nikalein?** Mongoose har model pe methods deta hai — `Todo.find()` collection ke **saare** documents return karta hai. Naam hi sab kuch bol raha hai — "find" = dhoondho aur sab nikaal lo.

**Sawaal 3 — kis order mein dikhenge?** `find()` raw order mein data deta hai — kaunsa pehle, pata nahi. User ko naye todos pehle chahiye. Isliye `.sort({ createdAt: -1 })` — `createdAt` par sort karo, `-1` matlab **descending** — naye pehle. (Ascending ke liye `1` hota, par yahan use-case "newest first" hai.)

**Sawaal 4 — response kaisa bhejenge?** `NextResponse.json(todos, { status: 200 })` — array ko JSON body mein convert karke bhejta hai, status ke saath. GET successful = **200** (6.6 wala design — tumne decide kiya tha).

**Sawaal 5 — agar database down ho toh?** Query fail ho sakti hai — connection fail, network issue. Isliye pura kaam `try` ke andar, aur `catch` mein **500** — server ki galti (6.6 design). `console.error` se error server-side log hota hai — debugging ke liye. User ko log nahi dikhta, sirf `{ error }` JSON.

**File:** `app/api/todos/route.ts` (nayi file — `route.ts` wahi convention jo Batch 3 mein seekha: folder ka path = API endpoint)

Code ko do hisson mein samjhenge — pehle file ka top (imports), phir poora function. Har snapshot **poori file** dikhata hai, isliye pata rahega code kahan aur kaise judta hai.

**Pehle — imports (file ka top):**

```ts
// app/api/todos/route.ts
import { NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";
```

Teen imports ek saath — file ki pehli teen lines. Line-by-line:

- **`NextResponse`** — response bhejne ke liye. `NextResponse.json()` se JSON body + status code set hota hai (3.1 wala wahi pattern).
- **`connectDB`** — 6.4 wala singleton connection. **Path kyun `@/app/lib/db`?** Kyunki tumhare project mein db file `app/lib/db.ts` pe hai (6.4 mein banayi thi). `@/` root folder hai, isliye `@/app/lib/db` = `app/lib/db.ts`.
- **`Todo`** — 6.5 wala model (`app/models/Todo.ts`). Iske methods (`find`, `create`) hi database se baat karte hain.

**Ab — imports + poora GET function (complete file):**

```ts
// app/api/todos/route.ts
import { NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";

export async function GET() {
  try {
    await connectDB();
    const todos = await Todo.find().sort({ createdAt: -1 });
    return NextResponse.json(todos, { status: 200 });
  } catch (error) {
    console.error("Todos fetch error:", error);
    return NextResponse.json({ error: "Todos fetch nahi ho sake" }, { status: 500 });
  }
}
```

Imports wahi rahe — unke neeche ab poora `GET` function juda. Function line-by-line:

- **`export async function GET()`** — Route Handler ka contract: exported function ka naam hi HTTP method hai. `async` isliye kyunki andar database ka `await` karenge.
- **`try`** — shuruaat. Database se baat karte waqt error ho sakta hai — sab kuch iske andar, taaki `catch` pakad sake (Sawaal 5).
- **`await connectDB()`** — pehle connection ready (Sawaal 1). Bina iske query nahi chalegi — 6.4 wala singleton, isliye har route pe call karna safe hai.
- **`Todo.find().sort({ createdAt: -1 })`** — saare todos nikaalo, naye pehle (Sawaal 2-3). `await` zaroori — yeh Promise return karta hai, data database se aane mein time lagta hai.
- **`NextResponse.json(todos, { status: 200 })`** — todos array JSON mein, 200 ke saath (Sawaal 4).
- **`catch` + 500** — koi bhi error (database down, connection fail) yahan aayega. `console.error` se server-side log (Sawaal 5), user ko `{ error }` JSON 500 ke saath.

**TEST:** `npm run dev` chalao, browser mein `http://localhost:3000/api/todos` kholo. Agar database mein 6.5 ka "First real todo" hai, woh dikhna chahiye. Agar khali hai toh `[]`. Route kaam kar raha hai — ab asli kaam: **is route ko UI se jodna**.

## Step 2 — UI: Todos Ko Ek Page Pe Dikhana

**SOCH:** Ab browser mein `/api/todos` kholne par raw JSON dikh raha hai. Par koi user aisa dekhta hai? Nahi — user ko ek **page** chahiye jisme todos ek list ki tarah dikhe. Matlab: ek component jo page load pe `/api/todos` se data fetch kare aur render kare. Batch 3.1 ka `ShowComments` yaad hai? Wahi pattern — `useEffect` mein `fetch()`, data `useState` mein, phir render.

**CONCEPT:** Pehle structure socho — kaunsi files banengi? Ek component mein sab daalne ki jagah, **separate components** banate hain (Batch 3 mein bhi form/list alag the). Yeh real project ka structure hai:

```
app/
├── page.tsx                 ← Server Component — TodoApp ko render karta hai
├── types.ts                 ← Shared type — Todo ka shape, sab import karte hain
└── components/
    ├── TodoApp.tsx          ← Client — "brain": state + fetch sab yahan
    └── TodoList.tsx         ← Presentational — sirf dikhata hai (props se data)
```

**Sawaal 1 — `page.tsx` kyun, aur usme kya hoga?** Home page abhi 6.5 ka test page hai — jo har reload pe `Todo.create()` karta tha (accidental todos ban rahe the!). Usse hata ke ab page ko **TodoApp** dikhana hai. `page.tsx` ko React hooks nahi chahiye — bas ek component render karna hai — isliye **Server Component** (default) rahega.

**Sawaal 2 — data kahan rakhenge?** Data change hota hai (loading → mil gaya → error), isliye **`useState`** chahiye — teen states: `todos` (data), `loading` (abhi fetch ho raha hai), `error` (kuch gadbad). Yeh sab `TodoApp.tsx` mein hoga.

**Sawaal 3 — page load pe fetch kaise hoga?** `useEffect` + empty dependency array `[]` — mount hote hi ek baar chalta hai. Batch 3.1 mein yehi pattern tha. Aur ek important cheez: **`loadTodos` ko alag function** banate hain — kyunki 6.7.2 se POST/DELETE/PUT ke baad **dobara** ise call karna hai (list refresh). Abhi mount pe chalega, baad mein mutations ke baad bhi.

**Sawaal 4 — TodoList ko data kaise milega?** Props se. `TodoApp` state rakhta hai aur `<TodoList todos={todos} loading={loading} error={error} />` pass karta hai. `TodoList` khud fetch **nahi** karta — sirf dikhata hai. Yeh split isliye: ek component ka kaam data sochna, doosre ka sirf render karna. (Batch 3.3.2 mein bhi yahi kiya tha — list ko props di thi.)

**Sawaal 5 — TodoList mein `"use client"` kyun nahi likhna?** Kyunki woh `TodoApp` (client component) se import hota hai — parent client hai toh child bhi client bundle mein jaata hai automatically. `"use client"` sirf **usse file pe** likhna padta hai jahan hooks hain (yahi `TodoApp` mein hai). `TodoList` mein koi hook nahi — sirf props render — isliye directive ki zaroorat nahi.

### 2.2 `TodoApp.tsx` — Brain: State + Fetch

**File:** `app/components/TodoApp.tsx` (nayi file — `components/` folder banao)

Par pehle ek chhota kaam — **Todo type ka shared ghar**. `Todo` shape ab do jagah chahiye: `TodoApp` mein (state) aur aage `TodoList` mein (props). Do files mein same shape copy karein? Nahi — **ek jagah define, sab jagah import** (wahi DRY concept jo 1.5 ke data layer se seekha). Isliye pehle `app/types.ts` banate hain:

```ts
// app/types.ts
export type Todo = {
  _id: string;
  title: string;
  done: boolean;
  createdAt: string;
  updatedAt: string;
};
```

**`export type Todo`** — `export` isliye taaki doosri files import kar sakein. Shape wahi jo 6.5 ke model mein hai — API se bhi wahi fields aate hain, isliye UI aur database ki shape match. Ab koi bhi component `import type { Todo } from "@/app/types"` se use karega — ek jagah define, har jagah consistent.

**Ab TodoApp ka top — imports + states + `loadTodos`:**

```tsx
"use client";

import { useEffect, useState } from "react";
import TodoList from "./TodoList";
import type { Todo } from "@/app/types";

export default function TodoApp() {
  const [todos, setTodos] = useState<Todo[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  const loadTodos = async () => {
    try {
      const res = await fetch("/api/todos");
      if (!res.ok) throw new Error("API error");
      const data = await res.json();
      setTodos(data);
      setError(null);
    } catch {
      setError("Todos load nahi ho sake");
    } finally {
      setLoading(false);
    }
  };
```

Line-by-line:

- **`"use client"`** — is file mein React hooks hain (`useState`, `useEffect`) — yeh sirf client pe chalte hain, isliye directive zaroori (Batch 2 ka rule).
- **Imports** — `useState`/`useEffect` React se, `TodoList` apne component se, aur **`Todo` type `@/app/types` se**. `import type` — sirf type ke liye; compile ke baad runtime code mein iska koi trace nahi rehta.
- **Teen states (Sawaal 2)** — `todos` array (khali se shuru), `loading` (initially `true` — pehli baar page khulte hi fetch shuru), `error` (`null` — koi error nahi abhi). TypeScript har state ka type bata raha hai.
- **`loadTodos` function (Sawaal 3)** — line-by-line:
  - `await fetch("/api/todos")` — GET request hamare hi route pe (relative URL — same app). **Client-side fetch** — browser se server ko request jaati hai
  - `if (!res.ok) throw ...` — `fetch` HTTP errors pe khud throw nahi karta — 500 aaye toh bhi resolve hota hai. Isliye khud check: `res.ok` false (4xx/5xx) = error throw karo
  - `await res.json()` — response body JSON string se JS array banati hai (Batch 2 ka pattern)
  - `setTodos(data)` — data state mein
  - `setError(null)` — success pe purana error saaf (agar pehle fetch fail hua tha). **Dhyaan do — function `setLoading(true)` se kyun shuru nahi karta?** Do wajah: (1) `loading` initial state pehle se `true` hai, isliye mount pe spinner dikhta hai bina reset ke; (2) naya React lint rule (`set-state-in-effect`) effect ke synchronous path mein setState ko flag karta hai — isliye saare setState pehle `await` ke **baad** rakhe hain, kyunki woh asynchronous context mein hain. Abhi itna jaan lo, 6.7.2 ke mutation handlers mein yehi pattern aage dikhega.

**Ek honest note about lint:** is pattern ke baad bhi aapko `useEffect` ke andar `loadTodos()` wali line pe ek lint error dikh sakta hai — *"Calling setState synchronously within an effect"*. Yeh **code ka bug nahi hai**; `set-state-in-effect` rule ka ek known false positive hai (React's GitHub issue #34905). Rule ko React Compiler chalta hai, aur stable version mein compiler `loadTodos` jaise async function ko effect se call karte waqt track nahi kar paata ki setState `await` ke baad ho raha hai — woh use "synchronous" maan leta hai. (Fix React ke canary builds mein aa chuka hai, par abhi stable version mein nahi.) Isliye hum call wali line ke upar ek chhota `eslint-disable-next-line` comment lagate hain — taaki lint green rahe aur baaki rules active rahen. Jab aap kabhi `eslint-plugin-react-hooks` update karo, fix aa chuka hoga to yeh comment hata sakte ho.
  - `catch` — koi bhi error (network fail, 500) yahan aata hai → `setError` message
  - `finally { setLoading(false) }` — success ho ya fail, **loading hamesha band** (finally har case mein chalta hai)

**Ab `useEffect` + render — component complete:**

```tsx
"use client";

import { useEffect, useState } from "react";
import TodoList from "./TodoList";
import type { Todo } from "@/app/types";

export default function TodoApp() {
  const [todos, setTodos] = useState<Todo[]>([]);
```

Upar wala code wahi hai — neeche ab do aur cheezein judi hain:

- **`useEffect` + `[]`** — component mount hote hi `loadTodos()` ek baar chalata hai. **`[]` kyun?** Dependency array khali = sirf pehli baar. `[]` mein `loadTodos` likhne ki zaroorat nahi — function har render pe naya banta hai, aur humein sirf mount pe chahiye. (3.1 mein yehi pattern tha.) Aur upar wala `eslint-disable-next-line` comment — yaad hai abhi `loadTodos` wale note mein bataya tha? Yeh rule ka known false positive hai; `loadTodos` async hai aur setState `await` ke baad, phir bhi stable lint version ise flag karta hai. Comment sirf use line ke liye lint ko chupata hai.
- **Render** — heading + `TodoList` ko **teeno states props mein** pass kiya (Sawaal 4). `TodoApp` data sochta hai, `TodoList` sirf dikhata hai.

```tsx
export default function TodoList({
  todos,
  loading,
  error,

  todos: Todo[];

  error: string | null;
```

```tsx
  if (loading) return <p>Loading...</p>;
```

- **Empty state** — database khali toh "koi todo nahi" — khali list ki jagah friendly message. (Yeh 6.6 wala rule hai: list khali = `[]`, koi 404 nahi.)

## Nutshell

GET route: `Todo.find().sort({ createdAt: -1 })` se saare todos (naye pehle) + 200. UI: `TodoApp` (client) `useEffect([])` mein `fetch("/api/todos")` se data laake `useState` mein rakhta hai, `TodoList` (presentational) ko props mein deta hai. Load/error/empty — teen states. `page.tsx` (server) sirf `<TodoApp />` render karta hai.

## What It Is NOT

- **"Client fetch = hamesha galat" nahi.** Batch 3.3 mein Server Components better the **us context mein** (Next.js app ka internal data). REST API exercise mein client fetch hi pattern hai — frontend↔backend integration yahi sikhata hai. Decision 6.12 mein.
- **`TodoList` mein `"use client"` chhodo** — client component se import ho raha hai toh client bundle mein auto jaata hai. Directive sirf us jagah jahan hooks hain (`TodoApp`).
- **`res.ok` check optional nahi.** `fetch` 500 pe throw nahi karta — agar `!res.ok` check na ho, toh error page pe dikhega hi nahi, data ke liye galat cheez render hogi.
- **`finally` hamesha chahiye** — `loading` ko band karna success aur error dono ke baad hona hai. `finally` hi guarantee deta hai.
- **UI = API ka replace nahi.** Route abhi bhi hai aur Postman se test hoga (6.8). UI bas usi API ka ek consumer hai — jaise koi mobile app hoga.

4. `if (!res.ok) throw new Error("API error")` kyun likha — `fetch` khud error throw karta hai na?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Nahi. `fetch` sirf **network-level** errors pe throw karta hai (server hi nahi mila). HTTP errors (404, 500) pe woh successfully resolve hota hai — `res.ok` false hota hai. Agar check na ho, toh 500 wala `{ error }` JSON bhi `setTodos(data)` mein chala jaata aur UI toot jaata. Isliye khud check karna padta hai — yeh REST integration ka ek common pattern hai.

</details>
