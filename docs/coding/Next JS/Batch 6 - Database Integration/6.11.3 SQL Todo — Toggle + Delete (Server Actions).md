# SQL Todo — Part 3: Toggle + Delete (Server Actions)

## Step 5 — Toggle + Delete

**THINK:** The remaining operations in a Todo app — toggling `done` and deleting a todo. **In Mongo**, this was done via `PUT`/`DELETE` route + `fetch`. **Here?** Two more Server Actions. For toggle, a **checkbox** (same pattern as Mongo — tick/untick); for delete, a button + form. The two approaches differ: a checkbox's `onChange` runs on the client (a Server Component cannot handle it) — so we create a small client component; delete uses a button + form that passes data to the action.

One question: **how does the id reach the action, and how does a string become a number?** The delete form carries the id as a string (all form data is strings), but the SQL column is a number (SERIAL — see 6.11.1 Step 1) — so `Number(formData.get("id"))` conversion is necessary. Toggle takes a different path — the checkbox's `onChange` calls the action with a **direct numeric id** (no form, no string — no conversion needed). **This differs from 6.7.x!** Another question: **which row to update/delete — how do we tell Drizzle?** `where(eq(todos.id, id))` — **`eq()` is a function with two arguments** — which column (`todos.id`) and which value (`id`) — it forms the "these are equal" condition, imported from `drizzle-orm`. Without `where`, update/delete hits **every row** — that's an SQL rule (in Mongo, `findByIdAndUpdate(id, ...)` took the id as a function parameter, so SQL's `where` must be specified explicitly).

**File:** `app/actions.ts` — joining toggle/delete alongside `createTodo` (from 6.11.2). Following step-by-step — the existing file is shown, new lines tagged `// NEW`.

First task — import `eq` (from `drizzle-orm` — we've used `desc` so far, now we use `eq`). Other imports stay the same:

```ts
// app/actions.ts
"use server";

import { db } from "@/db";
import { todos } from "@/db/schema";
import { eq } from "drizzle-orm";           // NEW
import { revalidatePath } from "next/cache";

export async function createTodo(formData: FormData) {
  const title = formData.get("title") as string;

  if (!title || title.trim() === "") {
    return;
  }

  await db.insert(todos).values({ title: title.trim() });

  revalidatePath("/");
}
```

**`eq` import** — new line, from `drizzle-orm` — Drizzle's equality operator. `createTodo` is the same as in 6.11.2.

Now `toggleTodo` — **signature: `(id: number)`** — not from a form, but called directly from the checkbox's `onChange` (shown in the ToggleTodo component below). So `id` arrives directly as a number — no `Number()` conversion needed. **`db.update(todos)`** — starts an update query (the argument is which table). **`.set({ done: not(todos.done) })`** — what to change (column → new value) — **`not()` is a function with one argument** (what to flip) — SQL's `NOT` operator: turns `true` into `false`, `false` into `true`. **That's exactly what "toggle" means** — the opposite of the current value, not always setting to `true`. **`.where(eq(todos.id, id))`** — which row (a condition built by the `eq(column, value)` function). The full chain becomes SQL `UPDATE drizzle_todos SET done = NOT done WHERE id = ...` — `eq(todos.id, id)` means "the row whose id equals this value". `not` is also imported from `drizzle-orm` (along with `eq`):

```ts
// app/actions.ts
"use server";

import { db } from "@/db";
import { todos } from "@/db/schema";
import { eq, not } from "drizzle-orm";      // NEW — not for toggle
import { revalidatePath } from "next/cache";

export async function createTodo(formData: FormData) {
  const title = formData.get("title") as string;

  if (!title || title.trim() === "") {
    return;
  }

  await db.insert(todos).values({ title: title.trim() });

  revalidatePath("/");
}

export async function toggleTodo(id: number) {    // NEW — direct id, called from checkbox
  await db
    .update(todos)
    .set({ done: not(todos.done) })
    .where(eq(todos.id, id));

  revalidatePath("/");
}
```

**`toggleTodo`** — the new action. **`(id: number)`** — the signature is different: not from a form, a direct call from the checkbox's `onChange` (in the `ToggleTodo` component below) — so `id` comes directly as a number, no `Number()` conversion needed. **`db.update(todos)`** (which table) + **`.set({ done: not(todos.done) })`** (what to change — `not(column)` is SQL `NOT` = the opposite flip, that's the toggle) + **`.where(eq(todos.id, id))`** (which row) — SQL `UPDATE drizzle_todos SET done = NOT done WHERE id = ...`. `revalidatePath("/")` — the same pattern as 6.11.2. **`eq` and `not` imported together** — `import { eq, not } from "drizzle-orm"` — both are SQL operators expressed as JS functions.

Now `deleteTodo` — same shape: convert id → query → revalidate. **`db.delete(todos)`** — starts a delete query (the argument is which table to delete from). **`.where(eq(todos.id, id))`** — which row (the same `eq` condition function). The whole chain becomes SQL `DELETE FROM drizzle_todos WHERE id = ...`. **`where()` is needed here too** — without it, **all rows** get deleted:

```ts
// app/actions.ts
"use server";

import { db } from "@/db";
import { todos } from "@/db/schema";
import { eq, not } from "drizzle-orm";

export async function createTodo(formData: FormData) {
  const title = formData.get("title") as string;

  if (!title || title.trim() === "") {
    return;
  }

  await db.insert(todos).values({ title: title.trim() });

  revalidatePath("/");
}

export async function toggleTodo(id: number) {
  await db
    .update(todos)
    .set({ done: not(todos.done) })
    .where(eq(todos.id, id));

  revalidatePath("/");
}

export async function deleteTodo(formData: FormData) {    // NEW
  const id = Number(formData.get("id"));

  await db.delete(todos).where(eq(todos.id, id));

  revalidatePath("/");
}
```

**`deleteTodo`** — the new action. **`Number(formData.get("id"))`** — form data is always a string, the `id` column is numeric (SERIAL) — conversion is necessary (the question above). **`db.delete(todos)`** (which table) + **`.where(eq(todos.id, id))`** (which row) — SQL `DELETE FROM drizzle_todos WHERE id = ...`. `where()` is needed here too — without it **all rows** get deleted.

**File:** `app/page.tsx` — join the delete form + checkbox for each todo. Following step-by-step — the existing file is shown, new lines tagged `// NEW`.

First, create a new **client component**: `ToggleTodo` — a checkbox that, when clicked, toggles a todo's `done` value. This is a separate file because the page (a Server Component) can't run event handlers — `onChange` runs on the client (like Mongo's 6.7.4 `TodoItem`, but here there's no fetch — the server action is called directly):

```tsx
// app/components/ToggleTodo.tsx
"use client";

import { toggleTodo } from "../actions";

export default function ToggleTodo({
  id,
  done,
}: {
  id: number;
  done: boolean;
}) {
  return (
    <input
      type="checkbox"
      checked={done}
      onChange={() => toggleTodo(id)}
    />
  );
}
```

**`"use client"`** — there's an event handler (`onChange`). **Import `toggleTodo` action** — a server action, called directly from a client component (no form needed — that's why the action receives `(id: number)` directly, not `formData`). **`checked={done}`** — the checkbox mirrors the server data — `done` true = checked. **`onChange={() => toggleTodo(id)}`** — every check/uncheck calls the server action — `id` is a number, no conversion. The server action runs, the database updates, `revalidatePath` re-renders the page.

## Nutshell

Toggle + Delete in the SQL phase: `toggleTodo(id: number)` — the checkbox (`ToggleTodo` client component) `onChange` calls it directly, `db.update(todos).set({ done: not(todos.done) }).where(eq(todos.id, id))` — `not()` is SQL `NOT` (flips the current value, that's what toggle means). `deleteTodo(formData)` — from a form, `Number(formData.get("id"))` converts the id (form data is a string, the SQL column is numeric), `db.delete(todos).where(eq(todos.id, id))` — `where` is essential, without it **all rows** get hit, `revalidatePath("/")` refreshes. On the page, each `<li>` has a `<ToggleTodo />` (checkbox) + a delete form (`<input type="hidden" name="id">` carries the id to the action).

## What It Is NOT

- **`db.update().set()` without `where` = "updates the whole table"** is not wrong — it's exactly right, which is why it's dangerous. SQL applies update/delete to all rows without `where`. `eq(todos.id, id)` is needed. Mongo's `findByIdAndUpdate(id, ...)` handled this automatically — SQL requires an explicit `where`.
- **`Number(formData.get("id"))` is optional** is not true. Form data is always a string — the SQL `id` column is numeric. Without `Number()`, `eq(todos.id, "3")` is a type mismatch and the query fails. (Toggle doesn't need this conversion — there `toggleTodo(id: number)` receives a number directly, no form involved.)
- **Hidden input = "something for the user"** is not true. `<input type="hidden">` is not visible to the user — its value goes into `formData` on form submit, the action reads it. `name="id"` is that field's key. (Only the delete form needs it — toggle's checkbox `onChange` passes the id directly, no form needed.)
- **`ToggleTodo` = "part of the page"** is not true. It's a separate client component — the checkbox's `onChange` runs on the client, a Server Component can't handle events. So it's a small island: the component lives on the client, the action lives on the server — two files working together.
- **`not(todos.done)` = "always set to true"** is not true. `not()` is SQL's `NOT` — it flips the current value. `true` becomes `false`, `false` becomes `true`. That's what makes it a toggle, not a one-way switch.

**In Your Own Words**

1. In Mongo we used `findByIdAndUpdate(id, ...)`, but in SQL we use `db.update().set(...).where(eq(...))` — why does SQL need `where` separately?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Mongo's method makes the id special — passing an id automatically knows which document to update. SQL's update/delete is generic — `where()` specifies which rows it applies to. Without `where`, the update/delete hits **all rows**. SQL's rules are explicit.

</details>

2. `Number(formData.get("id"))` — why convert in the delete action, but not in toggle?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Form data is always a string — `formData.get("id")` returns a string. The SQL `id` column is numeric (SERIAL). `Number()` converts the string to a number — without it, `eq(todos.id, "3")` is a type mismatch and the query fails. Toggle doesn't use a form — `toggleTodo(id: number)` receives a number directly from the `ToggleTodo` component, so no conversion needed. In Mongo, `_id` was a string, so no conversion was ever needed.

</details>

3. How does `<input type="hidden" name="id" value={todo.id} />` get the id to the action?

<details>
<summary>Show Answer</summary>

**Sample Answer:** When the form submits, all inputs' key-value pairs go into `formData` — including the hidden input. `name="id"` is the key, `value={todo.id}` is this todo's id. In the action, `formData.get("id")` retrieves that same value. Each todo's form carries its own id — so only the matching todo gets updated or deleted.

</details>

4. What does `db.delete(todos)` without `where()` do, and why is it dangerous?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Without `where()`, delete hits **all rows** — the entire table becomes empty. `where(eq(todos.id, id))` specifies which single row to delete. In Mongo, `findByIdAndDelete(id)` took the id directly — in SQL, an explicit `where()` is required.

</details>

5. Why does `toggleTodo` get called from the checkbox's `onChange` directly (`toggleTodo(id: number)`), but `deleteTodo` from a form?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A checkbox's job is literally to toggle — the user expects it to flip immediately with every click. The checkbox's `onChange` event runs on the client, so a small client component (`ToggleTodo`) is needed that calls the server action directly — using a form + submit button for every toggle would be an unnecessarily heavy flow. Delete uses a button + form because the user makes an explicit action, and the form's hidden input carries the id to the action (where `Number()` conversion also happens). Both patterns are valid — the choice depends on what the user intends to do.

</details>
