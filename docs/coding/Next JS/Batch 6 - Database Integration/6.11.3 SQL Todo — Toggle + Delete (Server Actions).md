6.11.2 mein Create ready hai — form se todo add ho raha hai, `revalidatePath` se UI refresh. Ab do aur operations baaki hain — **done toggle karna aur todo delete karna.** 6.7.3/6.7.4 (Mongo) mein PUT/DELETE routes the, TodoItem mein checkbox + button. Yahan wahi kaam do aur **Server Actions** se — `toggleTodo` aur `deleteTodo`, aur is phase ka ek important SQL rule seekhenge jo 6.7.x se bilkul alag hai.

# SQL Todo — Part 3: Toggle + Delete (Server Actions)

## Step 5 — Toggle + Delete

**SOCH:** Todo app ke baaki operations — done toggle karna, todo delete karna. **Mongo mein** `PUT`/`DELETE` route + fetch. **Yahan** — do aur server actions. Toggle ke liye **checkbox** (Mongo wala hi pattern — tick/untick), delete ke liye button + form. Dono ka tarika alag: checkbox ka `onChange` client pe chalta hai (server component nahi chala sakta) — isliye chhota client component; delete ka button form se action ko `formData` deta hai.

Ek sawaal: **id action tak kaise jaati hai, aur string hai toh number kaise?** Delete form se id jaati hai — form ka data hamesha string hota hai, SQL column number hai (SERIAL — 6.11.1 Step 1) — isliye `Number(formData.get("id"))` convert zaroori. Toggle mein alag tarika — checkbox `onChange` se **direct `id: number`** call hoga (koi form nahi, koi string nahi — conversion ki zaroorat nahi). **Yeh 6.7.x se alag hai!** Ab ek aur sawaal: **kaunsi row update/delete karni hai, Drizzle ko kaise batayenge?** `where(eq(todos.id, id))` — **`eq()` ek function hai jiske do arguments hain** — kaunsa column (`todos.id`) aur kaunsi value (`id`) — "dono equal hain" wali condition banata hai, `drizzle-orm` se import. Bina where ke update/delete **saari rows** pe lag jaata — SQL ka rule (Mongo mein `findByIdAndUpdate(id, ...)` id function parameter mein tha, isliye SQL mein where explicit dena padta hai).

**File:** `app/actions.ts` — createTodo (6.11.2 wala) ke saath toggle/delete jodne hain. Ab step-by-step — purani file dikh rahi hai, nayi lines pe `// NEW`.

Pehla kaam — `eq` import karna (`drizzle-orm` se — abhi tak `desc` use kiya tha, ab `eq`). Baaki imports wahi:

```ts
// app/actions.ts
"use server";

import { db } from "@/db";
import { todos } from "@/db/schema";
import { eq } from "drizzle-orm";           // NEW
import { revalidatePath } from "next/cache";

export async function createTodo(formData: FormData) {
  const title = formData.get("title") as string;

  if (!title || title.trim() === "") {
    return;
  }

  await db.insert(todos).values({ title: title.trim() });

  revalidatePath("/");
}
```

**`eq` import** — nayi line, `drizzle-orm` se — Drizzle ka equality operator. `createTodo` 6.11.2 wala wahi hai.

Ab `toggleTodo` — **signature: `(id: number)`** — form ke saath nahi, checkbox ke `onChange` se direct call hoga (neeche ToggleTodo component mein). Isliye `id` seedha number aata hai — `Number()` conversion ki zaroorat nahi. **`db.update(todos)`** — update query shuru karta hai (argument = kis table mein). **`.set({ done: not(todos.done) })`** — kya change karna hai (column → nayi value) — **`not()` ek function hai jiska ek argument hai** (kya flip karna hai) — SQL ka `NOT` operator: `true` ko `false`, `false` ko `true` kar deta hai. **Yehi "toggle" ka matlab hai** — current value ka opposite, hamesha `true` set karna nahi. **`.where(eq(todos.id, id))`** — kaunsi row pe (condition — `eq(column, value)`). Poora chain SQL `UPDATE drizzle_todos SET done = NOT done WHERE id = ...` — `eq(todos.id, id)` = "jis row ki id equals hai". `not` bhi `drizzle-orm` se import hota hai (`eq` ke saath):

```ts
// app/actions.ts
"use server";

import { db } from "@/db";
import { todos } from "@/db/schema";
import { eq, not } from "drizzle-orm";      // NEW — not toggle ke liye
import { revalidatePath } from "next/cache";

export async function createTodo(formData: FormData) {
  const title = formData.get("title") as string;

  if (!title || title.trim() === "") {
    return;
  }

  await db.insert(todos).values({ title: title.trim() });

  revalidatePath("/");
}

export async function toggleTodo(id: number) {    // NEW — direct id, checkbox se call
  await db
    .update(todos)
    .set({ done: not(todos.done) })
    .where(eq(todos.id, id));

  revalidatePath("/");
}
```

**`toggleTodo`** — naya action. **`(id: number)`** — signature alag: form se nahi, checkbox ke `onChange` se direct call hoga (neeche ToggleTodo component) — isliye `id` seedha number aata hai, `Number()` conversion nahi. **`db.update(todos)`** (kis table mein) + **`.set({ done: not(todos.done) })`** (kya change — `not(column)` SQL `NOT` = opposite flip, toggle ki asli kaam) + **`.where(eq(todos.id, id))`** (kaunsi row) — SQL `UPDATE drizzle_todos SET done = NOT done WHERE id = ...`. `revalidatePath("/")` — wahi 6.11.2 wala pattern. **`eq` ke saath `not` import** — `import { eq, not } from "drizzle-orm"` — dono SQL operators ke JS counterparts.

Ab `deleteTodo` — same shape: id convert → query → revalidate. **`db.delete(todos)`** — delete query shuru karta hai (argument = kis table se). **`.where(eq(todos.id, id))`** — kaunsi row (wahi `eq` condition function). Poora chain SQL `DELETE FROM drizzle_todos WHERE id = ...`. `where()` yahan bhi zaroori — bina where ke **saari rows** delete ho jaati:

```ts
// app/actions.ts
"use server";

import { db } from "@/db";
import { todos } from "@/db/schema";
import { eq, not } from "drizzle-orm";
import { revalidatePath } from "next/cache";

export async function createTodo(formData: FormData) {
  const title = formData.get("title") as string;

  if (!title || title.trim() === "") {
    return;
  }

  await db.insert(todos).values({ title: title.trim() });

  revalidatePath("/");
}

export async function toggleTodo(id: number) {
  await db
    .update(todos)
    .set({ done: not(todos.done) })
    .where(eq(todos.id, id));

  revalidatePath("/");
}

export async function deleteTodo(formData: FormData) {    // NEW
  const id = Number(formData.get("id"));

  await db.delete(todos).where(eq(todos.id, id));

  revalidatePath("/");
}
```

**`deleteTodo`** — naya action. **`Number(formData.get("id"))`** — form data string, `id` number column — convert zaroori (upar wala sawaal). **`db.delete(todos)`** (kis table se) + **`.where(eq(todos.id, id))`** (kaunsi row) — SQL `DELETE FROM drizzle_todos WHERE id = ...`. `where()` yahan bhi zaroori — bina where ke **saari rows** delete ho jaati.

**File:** `app/page.tsx` — har todo ke saath action buttons/checkbox jodne hain. Ab step-by-step — purani file dikh rahi hai, nayi lines pe `// NEW`.

Pehla kaam — ek naya **client component** banate hain: `ToggleTodo` — checkbox jispe click karne se todo complete/undo hota hai. Isse alag file mein rakhte hain kyunki page (Server Component) pe event handler nahi chalta — checkbox ka `onChange` client pe chalta hai (Mongo ke 6.7.4 `TodoItem` jaisa, par yahan fetch nahi — direct server action call):

```tsx
// app/components/ToggleTodo.tsx
"use client";

import { toggleTodo } from "../actions";

export default function ToggleTodo({
  id,
  done,
}: {
  id: number;
  done: boolean;
}) {
  return (
    <input
      type="checkbox"
      checked={done}
      onChange={() => toggleTodo(id)}
    />
  );

```

**`"use client"`** — is file mein event handler (`onChange`) hai — client chahiye (Batch 2 ka rule). **`toggleTodo` import** — server action, client component se direct call hota hai (form ki zaroorat nahi — isliye action mein `(id: number)` signature tha). **`checked={done}`** — checkbox server data ka mirror hai — `done` true toh tick. **`onChange={() => toggleTodo(id)}`** — har tick/untick pe server action call — `id` seedha number, convert nahi. Server action chalega, database update hoga, `revalidatePath` page refresh karega.

## Nutshell

Toggle + Delete SQL phase mein: `toggleTodo(id: number)` — checkbox (`ToggleTodo` client component) ke `onChange` se direct call, `db.update().set({ done: not(todos.done) }).where(eq(todos.id, id))` (not = SQL `NOT` — current value flip, toggle isi se hota hai). `deleteTodo(formData)` — form se, `Number(formData.get("id"))` se id convert (form string, SQL column number), `db.delete(todos).where(eq(todos.id, id))` — `where` bina saari rows pe lag jaata hai, `revalidatePath("/")` se refresh. Page mein har todo ke `<li>` ke andar `<ToggleTodo />` (checkbox) + delete form (`<input type="hidden" name="id">` se action ko id milti hai).

## What It Is NOT

- **`db.update().set()` bina `where()` = "pura table update" nahi.** Bilkul — SQL mein bina where ke update/delete saari rows pe apply hota hai. `eq(todos.id, id)` zaroori hai. Mongo ka `findByIdAndUpdate(id, ...)` yeh automatically handle karta tha — SQL mein explicit.
- **`Number(formData.get("id"))` = optional nahi.** Form data hamesha string hota hai — SQL column number. Bina Number() ke `eq(todos.id, "3")` type error/query fail — convert zaroori. (Toggle mein yeh conversion nahi chahiye — wahan `id: number` direct call hai, form hi nahi.)
- **Hidden input = "user ke liye koi cheez" nahi.** `<input type="hidden">` user ko dikhta nahi — bas form submit pe uski value `formData` mein jaati hai, action use padhta hai. `name="id"` us field ki key hai. (Delete form mein hi chahiye — toggle checkbox ke `onChange` se direct id leta hai, form ki zaroorat nahi.)
- **`ToggleTodo` = "page ka hissa" nahi.** Yeh alag client component hai — checkbox ka `onChange` client pe chalta hai, page (Server Component) event handler nahi chala sakta. Isliye chhota island: component client, action server — dono alag files, ek saath kaam.

**In Your Own Words**

1. Mongo mein `findByIdAndUpdate(id, ...)` tha, SQL mein `db.update().set({...}).where(eq(todos.id, id))` — `where()` kyun alag se dena padta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Mongo ka method id ko special karta hai — id dete hi pata chal jaata hai kaunsi document update karni hai. SQL mein update/delete generic hai — `where()` batata hai kaunsi rows pe apply karna hai. Bina where ke update/delete saari rows pe lag jaata hai. SQL ke rules explicit hain.

</details>

2. `Number(formData.get("id"))` — delete action mein `Number()` kyun lagana padta hai (aur toggle mein kyun nahi)?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Form ka data hamesha string hota hai — `formData.get("id")` string deta hai. SQL ka `id` column number hai (SERIAL). `Number()` string ko number mein convert karta hai — bina iske `eq(todos.id, "3")` type mismatch — query fail. Toggle mein form hi nahi hai — `toggleTodo(id: number)` ko `ToggleTodo` component seedha number deta hai, isliye conversion nahi chahiye. Mongo mein `_id` string tha isliye conversion kabhi nahi chahiye tha.

</details>

3. `<input type="hidden" name="id" value={todo.id} />` — yeh action tak id kaise pahunchata hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Form submit hote hi saare inputs ki key-value pairs `formData` mein jaati hain — hidden input bhi. `name="id"` key hai, `value={todo.id}` us todo ki id. Action mein `formData.get("id")` wahi value deta hai. Har todo ke form mein uski apni id hoti hai — isliye sirf wahi todo update/delete hota hai.

</details>

4. `db.delete(todos)` bina `where()` ke kya karta hai, aur kyun dangerous hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Bina `where()` ke delete **saari rows** pe lag jaata hai — poora table khali. `where(eq(todos.id, id))` batata hai sirf woh row delete karni hai. Mongo ka `findByIdAndDelete(id)` id se hi karta tha — SQL mein explicit `where()` dena padta hai.

</details>

5. `toggleTodo` ko form ki jagah checkbox ke `onChange` se direct call kyun kiya (`toggleTodo(id: number)`), aur `deleteTodo` form se kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Checkbox ka kaam hi tick/untick hai — user har click pe turant toggle chaahta hai. Checkbox ka `onChange` event client pe chalta hai, isliye ek chhota client component (`ToggleTodo`) chahiye jo server action ko direct call kare — form + submit button ka flow unnaturally heavy hai (har tick pe alag button dabana). Delete mein button + form sahi hai — user explicit action karta hai, aur form ka hidden input action ko `formData` se id deta hai (wahan `Number()` bhi chahiye). Dono patterns valid hain — kya use karna user ke intent pe depend karta hai.

</details>
