# SQL vs NoSQL — Table vs Document

## Pehle Ek Hi Data, Do Alag Structures Mein

Socho humein ek Todo app ka data store karna hai — `title` aur `done` field wale todos.

**SQL mein yeh data table mein aata hai** — rows aur columns:

```
| id | title          | done  |
|----|----------------|-------|
| 1  | Homework        | false |
| 2  | Exercise        | true  |
| 3  | Study SQL       | false |
```

**NoSQL mein yeh data documents mein aata hai** — JSON jaisa:

```json
{ "_id": "abc123", "title": "Homework", "done": false }
{ "_id": "def456", "title": "Exercise", "done": true }
```

Dono same data rakhte hain, par structure bilkul alag. **Table** mein structure pehle define hota hai (columns), phir data daalta hai. **Document** mein har record apni shape ka ho sakta hai. Isi ek fark se baaki sab kuch nikalta hai.

## SQL — Table Wali Database

**SQL database** mein data tables mein store hota hai — rows (har ek record) aur columns (har ek field). Examples: **PostgreSQL, MySQL, SQLite.**

Table define karte waqt structure **pehle se fix** hota hai — kaunse columns hain, har column ka type kya hai, kaun sa not-null hai:

```sql
CREATE TABLE todos (
  id SERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  done BOOLEAN DEFAULT false
);
```

- `id SERIAL` — har row ko automatically 1, 2, 3... count karta hai (MongoDB ke `_id` jaisa unique identifier, par SQL mein database khud auto-increment karta hai)
- `title TEXT NOT NULL` — title column text hai, aur null nahi ho sakta (har todo ko title chahiye)
- `done BOOLEAN DEFAULT false` — done true/false hai, default false

**Iska matlab kya hai practically?** Jab tum structure pehle define karte ho, toh **galat data save hi nahi ho sakta.** Koi todo bina `title` ke daalna chahe — database mana kar dega, kyunki `title` NOT NULL hai. Koi `done` mein number daalna chahe — database mana karega, kyunki `BOOLEAN` hai. **Data consistency guarantee hoti hai** — structure hi enforce karta hai.

Extra column chahiye (jaise `priority`) toh table badalni padti hai:

```sql
ALTER TABLE todos ADD COLUMN priority TEXT;
```

Yeh sahi hai — par structure badalna ek **explicit action** hai. SQL mein structure fix rehta hai jab tak tum khud badlo.

## NoSQL — Document Wali Database

**NoSQL database** mein data documents mein store hota hai — JSON jaisi objects. Examples: **MongoDB** (Batch 6 mein yahi), Firebase, CouchDB.

MongoDB mein schema define karte hain (Mongoose mein — 6.5 mein detail), par **structure flexible rehta hai:**

```js
// Schema define — par strict enforcement nahi
{ title: 'Homework', done: false }
// Extra field add kar sakte hain — schema mein nahi likha toh bhi chalta hai
{ title: 'Homework', done: false, priority: 'high' }
```

**Iska matlab kya hai practically?** Har document apni shape ka ho sakta hai. Ek todo mein `priority` hai, doosre mein nahi — chalta hai. Aaj koi naya field add karna ho — seedha daalo, koi `ALTER TABLE` nahi. **Flexibility guarantee hoti hai** — data ki shape unke saath evolve ho sakti hai.

Iski price hai — **koi enforcement nahi.** Structure ko tum code mein enforce karte ho (Mongoose schema), par database khud se galat data nahi rokta. Consistent data maintain karna **tumhari zimmedari** hai.

## SQL vs NoSQL — Compare Table

Ab dono clear hain — ek-ek concept. Abhi compare table meaningful hai:

| Baat | SQL (PostgreSQL) | NoSQL (MongoDB) |
|---|---|---|
| Data structure | Tables — rows + columns | Documents — JSON jaisa |
| Structure | Pehle define, phir data — **strict** | Flexible — har document apni shape ka |
| Structure badalna | `ALTER TABLE` explicit action | Seedha naya field — koi migration action nahi |
| Data consistency | **Database enforce karta hai** (types, NOT NULL) | Tumhe code mein enforce karni padti hai |
| Unique identifier | `id` (auto-increment) | `_id` (MongoDB automatically banata hai) |
| Relations | **First-class** — foreign keys, join queries | Manually — reference/embed (6.12 mein detail) |
| Queries | SQL language (SELECT, WHERE, JOIN) | MongoDB query methods |
| Scale karna | Vertical pehle, sharding baad mein | Horizontal sharding easy by design |

## Kab Kya Use Karein

Yeh "SQL better hai" ya "NoSQL better hai" nahi hai — dono alag cheezein solve karte hain.

**SQL jab use karo** jab data **structured + related** ho aur consistency critical ho:
- E-commerce — orders, products, users — sab relate karte hain
- Banking/finance — transactions, accounts — consistency non-negotiable
- Koi bhi app jisme user ke data ke beech relations hain (users → orders → items)

**NoSQL jab use karo** jab data **flexible** ho ya **scale-out** karna ho:
- User-generated content jiski shape evolve hoti hai (comments, posts)
- Real-time analytics / log data (bade volume, variable shape)
- App jisme schema pehle se clear nahi (prototyping)

Ek practical note — **production mein SQL zyada common hai** kyunki most apps mein data structured + related hota hai. Batch 6 ka final project (Task Board) bhi SQL + Prisma pe hai — isi reason se. NoSQL ko hum isliye seekhenge kyunki flexibility wale use-cases mein wo first choice hai, aur tumhare DukaanOS-style apps mein dono ko judge karna aana chahiye.

## Nutshell

SQL database table mein data rakhti hai — structure pehle define hota hai, strict, database khud consistency enforce karta hai, relations first-class hain. NoSQL database documents mein data rakhti hai — JSON jaisa, flexible, har document apni shape ka ho sakta hai, par consistency tumhe khud enforce karni padti hai. Structured + related + consistency-critical data → SQL. Flexible + scale-out + evolving shape → NoSQL.

## What It Is NOT

- **SQL = Microsoft/table wala, NoSQL = JSON wala — galat mental model.** Dono databases hain, dono data store karte hain. Fark structure ka hai: rows/columns (strict) vs documents (flexible).
- **"NoSQL means no queries."** NoSQL mein bhi queries hoti hain — bas SQL language ki jagah uski apni query methods hoti hain. Naam ka "NoSQL" matlab "Not Only SQL" — SQL ke alawa bhi.
- **MongoDB = sirf bade scale ke liye.** NoSQL scale-out ki advantage deta hai, par uska primary use-case flexibility hai. Chhota app ho toh bhi flexible data ka case banta hai.
- **SQL strict hai = bura, NoSQL flexible hai = acha (ya ulta).** Dono trade-offs hain. Strict = consistency milti hai, flexibility nahi. Flexible = freedom milti hai, enforcement nahi. Kaunsa choose karna data ki nature pe depend karta hai, "better" pe nahi.
