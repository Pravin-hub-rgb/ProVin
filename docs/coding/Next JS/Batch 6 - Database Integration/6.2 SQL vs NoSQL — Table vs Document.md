# SQL vs. NoSQL — Tables vs. Documents

## Where We Left Off

In 6.1 we established what a database actually owns: atomic writes, indexed queries, and relations that the storage layer enforces. But databases are not one thing — they come in two dominant families, and the one you pick changes how you model data. This file pins down the two: **SQL (table-based)** and **NoSQL (document-based)**, comparing them so the choice is deliberate.

Batch 6 uses both: MongoDB (NoSQL) in 6.4–6.8, PostgreSQL (SQL) in 6.9–6.12 — so the abstraction stays grounded in code rather than taxonomy.

## Same Data, Two Structures

Think about storing a todo — a `title` and a `done` flag. The same information lands in two different shapes depending on the database family:

**In SQL, it is a table** — rows and columns:

```
| id | title          | done  |
|----|----------------|-------|
| 1  | Homework        | false |
| 2  | Exercise        | true  |
| 3  | Study SQL       | false |
```

**In NoSQL, it is a document** — JSON-shaped:

```json
{ "_id": "a1b2c3", "title": "Homework", "done": false }
{ "_id": "d4e5f6", "title": "Exercise", "done": true }
```

Same information. Radically different structure. In a table, the shape is fixed up front; in a document, each record can differ. That single decision is the source of almost every practical difference that follows.

## SQL — The Table Database

A **SQL database** stores records as rows within tables, where columns define the shape. Examples: PostgreSQL, MySQL, SQLite.

The schema is declared *before* data is inserted:

```sql
CREATE TABLE todos (
  id SERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  done BOOLEAN DEFAULT false
);
```

What that buys you:

- `id SERIAL` — each row gets an auto-incrementing unique identifier (the SQL counterpart to MongoDB's `_id`).
- `title TEXT NOT NULL` — the column is text and rejecting nulls is mandatory.
- `done BOOLEAN DEFAULT false` — type is strict (`BOOLEAN`), and the default is built into the schema.

The practical consequence: **the database itself rejects malformed data.** Insert a todo without a `title`? It is refused. Store a string in `done`? It is refused. Structure is a guarantee, not a convention.

Adding a column is an *explicit* operation — this is by design:

```sql
ALTER TABLE todos ADD COLUMN priority TEXT;
```

The schema is a real, named thing that must be migrated. That rigidity pays off the moment multiple services share the table, but it is a step that documents every shape change.

## NoSQL — The Document Database

A **NoSQL database** stores records as documents — JSON-shaped objects, typically in MongoDB. The schema lives in code (for example, a Mongoose schema in 6.5), but the shape is *flexible*.

```ts
{ title: "Homework", done: false }
// later, without any migration:
{ title: "Homework", done: false, priority: "high" }
```

That buys you something different:

- Each document can carry its own fields. A new attribute is just written; no migration.
- The database does not enforce structure — that becomes the application's job, via the code-level schema.
- The trade-off is visible immediately: flexibility is free, but consistency is yours to maintain and yours to lose.

So the contrast is sharp: SQL gives you correctness-by-construction and makes change formal; NoSQL gives you shape-on-write agility and makes change free. Both are legitimate — the right one depends on what your data looks like and how much it moves.

## SQL vs. NoSQL — Side by Side

Now that both are concrete, the comparison table is meaningful:

| Dimension | SQL (PostgreSQL) | NoSQL (MongoDB) |
|---|---|---|
| Shape | Rows + columns (table) | Documents (JSON) |
| Schema | Declared up front, strict | Flexible, document-by-document |
| Changing shape | `ALTER TABLE` (explicit) | Add the field, done |
| Consistency | Enforced by the database | Enforced by the application |
| Identifier | `id` (auto-increment) | `_id` (auto-generated by MongoDB) |
| Relations | First-class — foreign keys, joins | Manual — references or embedding |
| Query language | SQL (`SELECT ... WHERE ... JOIN`) | MongoDB query methods |
| Scaling | Vertical first, sharding later | Horizontal sharding by design |

A few of these deserve emphasis, because they are the real decision drivers:

- **Relations.** In SQL, a foreign key ties a row to its parent and the database will refuse a dangling reference; MongoDB documents hold either an embedded copy or a manual id with no enforcement. The 6.12 system-design section returns to this heavily.
- **Scaling model.** SQL scales up (bigger machine) first, then shards; NoSQL is designed to shard across machines from the start. For this batch that mostly stays conceptual — the production-relevant takeaway is "know which you have."
- **Query ergonomics.** SQL is a language you write; NoSQL is method calls on a model. Drizzle (6.10) and Prisma (6.13) make SQL feel like methods too — but the underlying model is still tabular.

## When to Use Which

This is not a "which is better" question — it is "which matches the job."

Use **SQL** when data is **structured, related, and consistency is non-negotiable** — e-commerce (orders → items → users), finance (accounts and transactions), or any app where entities reference each other and wrong links are worse than inconvenient.

Use **NoSQL** when data is **variable-shaped or the access pattern is document-keyed** — content that evolves (posts, comments, user-generated fields), catalogs with sparse optional attributes, or real-time/log-style ingestion where writes are frequent and schema drift is expected.

Honest production framing: most business applications are structured and related, so SQL ends up the default — which is exactly why the capstone Task Board (6.13) standardizes on PostgreSQL + Prisma. NoSQL is learned because its strengths are real and frequent in modern apps; you need to be able to *judge* it, ideally better than "it's the new hot one."

## Nutshell

SQL databases store tabular rows and columns with a schema fixed up front, so the database rejects malformed data and manages relations as a first-class feature. NoSQL databases store JSON-like documents with a flexible shape, so new fields are cheap and the database trusts the application to keep things consistent. Structured + related + consistency-critical data points to SQL; variable-shaped + document-keyed + write-heavy data points to NoSQL.

## What It Is NOT

- SQL being "Microsoft's rigid thing" vs. NoSQL being "the flexible JSON store" — both are databases managing records; the axis is table-with-fixed-schema vs. document-with-flexible-schema.
- "NoSQL means no queries." NoSQL has queries; they are just its own query methods, not SQL. "NoSQL" literally means "Not Only SQL."
- MongoDB being "only for scale." Its primary strength is shape flexibility; horizontal scaling is an additional benefit, not the reason to reach for it.
- Flexibility being free or correctness being bad. Flexible schemas trade enforcement for ease; strict schemas trade migrations for guarantees. Neither is "better" — they serve different data shapes.

## In Your Own Words

<details>
<summary>1. The same todo in SQL vs. MongoDB — what is the structural difference, and why does it matter?</summary>

**Sample Answer:** SQL stores it as a row in a table where columns (and their types) are fixed up front; MongoDB stores it as a JSON document where each record can differ. SQL makes shape changes explicit (`ALTER TABLE`) and enforces them; MongoDB makes adding a field free but leaves consistency to the app. The difference matters at every migration and every write-validation decision thereafter.

</details>

<details>
<summary>2. In `title TEXT NOT NULL`, what is the guarantee, and how does NoSQL provide (or not provide) an equivalent?</summary>

**Sample Answer:** `NOT NULL` is a constraint the database enforces — no row can be saved without a value for `title`. In NoSQL, the database does not enforce this; you'd provide the equivalent with a Mongoose schema (`required: true`), but that is the application layer, not the storage layer. SQL pushes the check into the database; NoSQL puts it in code.

</details>

<details>
<summary>3. Why does adding a column require `ALTER TABLE` in SQL but not in MongoDB?</summary>

**Sample Answer:** In SQL the table's shape is a real, defined thing — columns are fixed until you explicitly change them, and `ALTER TABLE` is that explicit change. In MongoDB documents are independent, so there is no central shape to migrate; a new field is simply written into a document. SQL's rigidity is what makes the guarantee possible; MongoDB's freedom is what makes the migration unnecessary.

</details>

<details>
<summary>4. Why does an e-commerce app fit SQL better than NoSQL?</summary>

**Sample Answer:** Because the data is highly related — users place orders, orders contain items, items reference products. SQL relations are first-class and consistency is enforced, so a dangling reference or a partial update is structurally impossible. In MongoDB those relations would be hand-managed and the application would have to enforce the invariants that SQL provides for free.

</details>

<details>
<summary>5. "NoSQL" is a strange name — what does it literally mean, and why does the phrase mislead people?</summary>

**Sample Answer:** Literally "Not Only SQL" — databases that need not use SQL to query. It misleads because people hear "no SQL" and assume NoSQL systems can't do structured queries. They can — they have their own query APIs. The name describes the query approach, not the absence of one.

</details>
