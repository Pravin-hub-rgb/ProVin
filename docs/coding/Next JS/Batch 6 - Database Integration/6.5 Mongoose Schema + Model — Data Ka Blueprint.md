# Mongoose Schema + Model — Defining Document Shape

## Where We Left Off

In 6.4 the connection was wired (`connectDB()` singleton) and Atlas was reachable. A connection alone isn't useful yet — before any data can be saved, the application needs to agree on **what a record looks like.** MongoDB documents are flexible, but that flexibility is only a virtue if the app can still describe, with certainty, what fields a Todo has and which are required. This file defines that agreement with a **Mongoose schema and model**.

## Why Define a Shape at All?

MongoDB won't refuse a document just because it is missing a field or has the wrong type. That can look liberating, but it quickly becomes painful: a function reads `todo.done` expecting `boolean`, gets `undefined`, and breaks. Or worse, `done` is stored as the string `"false"` and truthy checks pass. Flexibility without agreement produces silent, hard-to-trace data rot.

The schema is the **agreement between code and database**: it states what fields exist, which are required, what types they take, and what defaults apply. The database stays flexible, while the application layer provides the guardrails. That is exactly the "application enforces consistency" trade the 6.2 comparison described.

## Step 1 — The Schema (Blueprint)

Define a Todo shape: a `title` (required string), a `done` flag (boolean, default false), and timestamps (when created, when updated). Think through each field deliberately rather than just listing:

- **`title` required** — a todo with no title is meaningless. Rejecting it at the schema level prevents junk from ever being stored.
- **`title` trimmed** — user input commonly carries stray leading/trailing spaces (`"  milk  "`). Storing it that way breaks equality lookups later. Trimming on write keeps data clean.
- **`done` defaults to `false`** — a newly created todo is, by definition, pending. Don't force every caller to pass `done: false`.
- **Timestamps automatic** — don't make the caller supply `createdAt`/`updatedAt`. Mongoose can maintain them if asked.

That gives the schema. File: `app/models/Todo.ts`.

```ts
// app/models/Todo.ts
import { Schema } from "mongoose";

const TodoSchema = new Schema(
  {
    title: {
      type: String,
      required: [true, "Title is required"],
      trim: true,
    },
    done: {
      type: Boolean,
      default: false,
    },
  },
  {
    timestamps: true,
  }
);

export default TodoSchema;
```

Read it field by field:

- `type: String` — a validator and serializer, not just a type hint. Mongoose coerces and enforces.
- `required: [true, "Title is required"]` — the message is returned to the caller when validation fails, which matters for error handling in 6.7.2.
- `trim: true` — the cleaner-on-write behavior decided above.
- `default: false` — the pending default, so the field is never absent.
- The second argument, `{ timestamps: true }`, is **model-level** (applies to the whole document), distinct from the field-level options. Mongoose then manages `createdAt` and `updatedAt` automatically.

Notice two things being deliberately *not* done: no database connection here (that lived in `lib/db.ts`), and no `mongoose.model(...)` yet. The schema is just the shape; the model is what bridges it to the database.

## Step 2 — The TypeScript Contract

Mongoose can coerce and validate at runtime, but it cannot tell TypeScript what a Todo looks like. That is the job of a TypeScript interface:

```ts
// app/models/Todo.ts (additions)
import type { Document, Model } from "mongoose";

export interface ITodo extends Document {
  title: string;
  done: boolean;
  createdAt: Date;
  updatedAt: Date;
}
```

Two subtleties this resolves:

- **Why not list `_id` here?** Extending `Document` already supplies the built-in fields (`_id`, `__v`, and the document methods). Listing `_id` again is redundant — and worse, it invites a collision if the manual type drifts from Mongoose's own. Take the built-ins for free via `Document`.
- **Why list `createdAt`/`updatedAt`?** These are *not* on `Document`. They are added by the `{ timestamps: true }` option from Step 1, so this interface must declare them. They were earned by an explicit choice (timestamps), so they earn an explicit declaration here.

The interface is the compile-time contract; the schema is the runtime guard. They describe the same thing from two angles — and both are needed, because the database never sees the interface.

## Step 3 — The Model (Schema + Database)

The schema describes the shape; the **model** is what actually reads and writes the collection. It is Mongoose's "clerk" that takes the blueprint and uses it against a real collection:

```ts
// app/models/Todo.ts (additions)
import mongoose from "mongoose";

// ...schema + interface as above...

const TodoModel: Model<ITodo> =
  (mongoose.models.Todo as Model<ITodo>) ||
  mongoose.model<ITodo>("Todo", TodoSchema);

export default TodoModel;
```

Reading this:

- **`mongoose.model<ITodo>("Todo", TodoSchema)`** — names the model `Todo`, binds it to the schema, and parametrizes it with `ITodo` so queries return typed documents. The collection name in MongoDB becomes `todos` (lowercased, pluralized) automatically.
- **`mongoose.models.Todo || ...`** — the guard against redefinition. In Next.js development, hot reload can run the module again; without the guard, Mongoose throws `OverwriteModelError` ("Cannot overwrite `Todo` model."). The existing model is reused if present; otherwise it is created once.
- **`as Model<ITodo>`** — a typed view so the cached model is still type-checked as `ITodo`, not a loose reference.

The three pieces are now distinct and individually meaningful: schema = shape, interface = TypeScript view, model = the live, typed accessor. Together they give the rest of the app a single import — `import Todo from "@/models/Todo"` — that is already connected, validated, and typed.

## The Complete File

```ts
// app/models/Todo.ts
import { Schema, type Document, type Model } from "mongoose";
import mongoose from "mongoose";

export interface ITodo extends Document {
  title: string;
  done: boolean;
  createdAt: Date;
  updatedAt: Date;
}

const TodoSchema = new Schema<ITodo>(
  {
    title: {
      type: String,
      required: [true, "Title is required"],
      trim: true,
    },
    done: {
      type: Boolean,
      default: false,
    },
  },
  {
    timestamps: true,
  }
);

const TodoModel: Model<ITodo> =
  (mongoose.models.Todo as Model<ITodo>) ||
  mongoose.model<ITodo>("Todo", TodoSchema);

export default TodoModel;
```

Now every other file imports `TodoModel` and gets a typed, schema-guarded accessor: `TodoModel.find()`, `TodoModel.create(...)`, `TodoModel.findByIdAndUpdate(...)` — all already returning `ITodo`-shaped data.

## Verify With a Write

Quick check that the whole stack — connection (6.4), schema, model — works together. Temporarily write a record:

```bash
# From a route handler or a guarded page (temporary):
await TodoModel.create({ title: "Schema works" });
```

Then inspect Atlas → your database → `todos` collection: the document should contain `title`, `done: false` (the default applied), and `createdAt`/`updatedAt` (timestamps applied) — none of which were explicitly passed. That confirms schema behavior end to end: the defaults and timestamps were earned, not hand-supplied.

## Nutshell

In Mongoose, three things compose a typed data accessor: a **schema** (runtime shape — types, required, defaults, timestamps), a **TypeScript interface** (compile-time shape — `extends Document` for built-ins, plus the timestamp fields the schema adds), and a **model** (`mongoose.model<ITodo>("Todo", schema)` — the live, typed bridge to the collection). The model is guarded with `mongoose.models.Todo || ...` so hot reload doesn't redefine it.

## What It Is NOT

- The schema is not optional because MongoDB is "schemaless." Flexible storage does not mean un-modeled data; the schema is what keeps data sane, and this batch depends on it.
- The interface does not replace the schema. It is a compile-time view; the database never sees it. Validation at runtime comes from the schema.
- `timestamps` is not a field you write into. It is an option on the schema object — a second argument to `new Schema(...)`. Putting it inside the fields object is a syntax error.
- `mongoose.model(...)` is not called fresh on every use. It is called once, then the cached model is reused — both for correctness (no `OverwriteModelError`) and for performance.
- The connection does not belong in the model file. The model describes shape; `connectDB()` in `lib/db.ts` describes connectivity. Keeping them separate is what lets the model be imported anywhere without side-effecting a connection.

## In Your Own Words

<details>
<summary>1. If MongoDB is "schemaless," why does this file define a schema at all?</summary>

**Sample Answer:** "Schemaless" describes MongoDB's storage flexibility, not the application's data needs. The schema is the application-side agreement that keeps data sane: required fields, types, trimmed values, defaults, and timestamps. Without it, silent rot creeps in (undefined flags, `"false"` strings, missing titles), which is exactly why the 6.2 comparison said NoSQL pushes consistency to the application.

</details>

<details>
<summary>2. Why does the interface extend `Document` and then list `createdAt`/`updatedAt` — aren't those already covered?</summary>

**Sample Answer:** `Document` provides MongoDB's built-ins (`_id`, `__v`, methods) — so `_id` is deliberately *not* re-declared. But `createdAt`/`updatedAt` are *not* on `Document`; they are added by the `{ timestamps: true }` option chosen in the schema. Since the schema opted into them, the interface must declare them — otherwise TypeScript would reject reading a property that the schema silently produces.

</details>

<details>
<summary>3. What is `OverwriteModelError`, and why does `mongoose.models.Todo || ...` prevent it?</summary>

**Sample Answer:** In Next.js development, hot reload can re-run a module. Without a guard, `mongoose.model("Todo", ...)` runs again and Mongoose refuses to overwrite an already-registered model. The `||` checks the existing registry first (`mongoose.models.Todo`) and reuses it if present, creating it only once — so the model is defined exactly once per process.

</details>

<details>
<summary>4. How does the schema "earn" `done: false` and the timestamps without the caller providing them?</summary>

**Sample Answer:** The caller invokes `TodoModel.create({ title: "..." })` providing only the title. The schema's `default: false` fills in `done`, and `{ timestamps: true }` fills in `createdAt`/`updatedAt` automatically — both at write time, inside Mongoose. The caller's minimal input plus the schema's own behavior produces the complete document.

</details>

<details>
<summary>5. Why is the connection logic in `lib/db.ts` and not in `models/Todo.ts`?</summary>

**Sample Answer:** To keep shape and connectivity separate. The model describes what a Todo is and how to access the collection; the connection module manages sockets and reuse. Mixing them would couple import-time connectivity (with side effects) into every place that just wants the model, and it would break the "single source of truth for credentials" idea we established in 6.4.

</details>
