Par socho — kisi bhi list ka dusra aadha hissa kya hai? **Remove.** Abhi tumse koi todo hata hi nahi sakta. Database mein jo 6.5 ka "First real todo" hai, wo **hamesha** list mein rahega.

Kisi real Todo app mein user ko delete ka button chahiye. Aur yahan pehli baar ek naya pattern aata hai: **kaunsa todo hatana hai?** Har todo ka apna `_id` hai — but URL hamesha `/api/todos` hi hai, ek hi todo kaise target karein?

Jawab hai **dynamic route** — URL ka ek part variable. `DELETE /api/todos/abc2` = "abc2 wala todo hatao". `[id]` folder se yeh banta hai. Aage kisi bhi app mein yeh pattern har jagah milega — profile page `/users/[id]`, blog `/posts/[slug]`. Abhi ise Todo app mein seekhte hain:

- **Route:** `DELETE /api/todos/[id]` — id se todo dhoondh ke delete (6.6 design: 404 galat id pe, 200 + message success pe)
- **UI:** Har todo ke saath **delete button** — `TodoItem` component (abhi tak list ke items `TodoList` mein hi render hote the, ab unhe apna component milega)

# DELETE /api/todos/[id] — Delete Route + TodoItem UI

## Step 1 — Route: Ek Todo Hatana

**SOCH:** Ab delete — lekin kaunsa todo? **ID chahiye.** URL mein ID bhejte hain: `DELETE /api/todos/abc2` = "abc2 wala hatao." Isliye ek **dynamic route** chahiye — `[id]` folder.

**CONCEPT:** Delete karne se pehle pehla sawaal — **kaunsa todo?** "Ek todo hatana" ke liye uski **ID** chahiye. URL mein ID bhejte hain: `DELETE /api/todos/abc2` = "abc2 wala hatao." Problem-first:

**Sawaal 1 — URL ka middle part variable kaisa banega?** `/api/todos/abc2` mein `abc2` har request pe badal sakta hai (kabhi `abc3`, kabhi `xyz`). Aisa URL jo fix nahi, uske liye **dynamic route** chahiye — folder ke naam mein **square brackets** = variable URL part. `app/api/todos/[id]/route.ts` sab `/api/todos/anything` handle karta hai — `[id]` har value pakad leta hai.

**Sawaal 2 — URL se ID kaise milegi?** Function ka **second parameter** `context.params` — URL ke variable parts wahan aate hain. `/api/todos/abc2` → `params = { id: "abc2" }`. Aur **Next.js 15+ mein params async hai** — woh Promise return karta hai. Isliye `await context.params` karna padta hai (Batch 1 ka `params` pattern yaad hai — wahi).

**Sawaal 3 — delete kaise karein?** `Todo.findByIdAndDelete(id)` — Mongoose method — id se document dhoondhta hai aur delete kar deta hai. Delete hua document return karta hai — aur agar id galat hai (todo exist hi nahi karta) toh **`null`**.

**Sawaal 4 — galat id pe kya?** `null` aaya = resource nahi mila = **404** (6.6 design: galat id = 404, galat body = 400). Success pe **200 + message** — delete ke baad koi data bhejna nahi (todo gaya), bas confirm message. (Kuch APIs 204 No Content dete hain — par message ke saath 200 humare design mein clear hai.)

**File:** `app/api/todos/[id]/route.ts` (nayi file — folder `[id]` banao)

Ab code do hisson mein — pehle imports, phir imports + poora DELETE function. Har snapshot complete file ka — pata rahega code kahan jaa raha hai.

**Pehle — imports (file ka top):**

```ts

import { NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";
```

Teen imports ek saath — file ki pehli teen lines. Line-by-line:

- **`NextResponse`** — response ke liye.
- **`connectDB`** + **`Todo`** — wahi `connectDB` (6.4) aur `Todo` (6.5). **`NextRequest` nahi chahiye** — DELETE mein body nahi aati.

**Ab — imports + poora DELETE function (complete file):**

```ts
// app/api/todos/[id]/route.ts
import { NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";

export async function DELETE(
  _request: Request,
  context: { params: Promise<{ id: string }> }
) {
  try {
    await connectDB();
    const { id } = await context.params;

    const deleted = await Todo.findByIdAndDelete(id);

    if (!deleted) {
      return NextResponse.json({ error: "Todo nahi mila" }, { status: 404 });
    }

    return NextResponse.json({ message: "Todo delete ho gaya" }, { status: 200 });
  } catch (error) {
    console.error("Todo delete error:", error);
    return NextResponse.json({ error: "Todo delete nahi ho saka" }, { status: 500 });
  }
}
```

Imports wahi rahe — unke neeche ab poora `DELETE` function juda. Function line-by-line:

- **`DELETE(_request, context)`** — method ka naam DELETE. `_request: Request` — **underscore prefix** ka matlab: "yeh parameter use nahi karunga" (DELETE mein body nahi hai, request ki zaroorat nahi). `context: { params: Promise<{ id: string }> }` — Sawaal 2 — URL ke variable parts. Type batata hai: params Promise hai, usme `id` string hogi.
- **`try` + connection** — wahi pattern — pehle connection, phir kaam.
- **`const { id } = await context.params`** — params ka wait karo (async hai — Sawaal 2), phir `id` nikaalo.
- **`Todo.findByIdAndDelete(id)`** — dhoondho + delete (Sawaal 3). Deleted document `deleted` mein, kuch na mila toh `null`.
- **`if (!deleted)` → 404** — id galat = todo exist nahi = 404 (Sawaal 4).
- **Success — 200 + message** — delete confirm (Sawaal 4). Data nahi bhejna — todo ab exist hi nahi karta.
- **`catch` + 500** — wahi pattern — database error pe server-side log + 500.

## Step 2 — UI: TodoItem + Delete Button

**SOCH:** Ab list ke har todo ke saath ek **delete button** chahiye. Click → `fetch` DELETE `/api/todos/[id]` → todo database se gaya → list refresh. Abhi tak list ke items `TodoList` mein seedha render hote the (`todos.map` ke andar `<li>`). Button + uski state add karne pe woh logic bada ho jaayega — isliye ek **`TodoItem` component** banate hain jo ek todo leta hai aur usse render karta hai (title + delete button).

**CONCEPT:** Socho ek restaurant menu — pura menu ek saath nahi padhte, har dish ka apna card hota hai jisme details + order button. Waise hi — list = cards ka collection, har card = ek todo ka display + uske actions. React mein isi liye **item-level components** banate hain (batch 3 mein `ShowComments` ka har comment bhi aise hi render hota tha). Problem-first:

**Sawaal 1 — delete button kis component mein hoga?** `TodoItem` mein — kyunki button ka kaam "yeh specific todo hatao" hai, aur `TodoItem` hi us todo ko jaanta hai (props mein milta hai). `TodoList` sirf map karke har todo ke liye ek `TodoItem` render karega.

**Sawaal 2 — button click pe delete kaise hoga?** `TodoItem` ek `onDelete` function props mein leta hai (wahi pattern jo `AddTodoForm` ka `onAdd` tha — 6.7.2). Click → `onDelete(todo._id)` — id ke saath parent ko call. Asli `fetch` DELETE `TodoApp` ke `deleteTodo` mein hoga — kyunki list refresh wahan hona hai.

**Sawaal 3 — DELETE ka `_id` kahan se?** Har todo ke paas `_id` hai — `TodoItem` ko props mein pura todo milta hai, isliye `todo._id` directly use kar sakte hain. URL banaate hain template literal se: `` `/api/todos/${todo._id}` `` — string ke beech variable.

**Sawaal 4 — POST aur DELETE mein kya farak hai?** POST mein body bheji thi (`JSON.stringify({ title })`) aur headers. DELETE mein **body nahi hoti** — sirf URL mein id jaati hai. Isliye `fetch` mein sirf `method: "DELETE"` — koi headers, koi body nahi. (6.6 design mein yehi tha — kaunsa todo URL se, kya karna method se.)

**Sawaal 5 — delete ke baad list refresh?** Wahi pattern — `deleteTodo` fetch ke baad `loadTodos()` call karta hai (6.7.2 mein addTodo ne yehi kiya). DELETE success → todo database se gaya → re-fetch → list mein ab nahi dikhega.

## Nutshell

DELETE route: dynamic route `[id]` folder, `await context.params` se id (Next.js 15+ async params), `Todo.findByIdAndDelete(id)`, galat id pe `null` → 404, success pe 200 + message. UI: `TodoItem` component har todo render karta hai (title + done marker + **Delete button**), `onClick` → `onDelete(todo._id)` → `TodoApp.deleteTodo` → `fetch DELETE /api/todos/[id]` → `loadTodos()` re-fetch. `TodoList` ab items ko `TodoItem` se render karta hai, `onDelete` ko forward karta hai.

## What It Is NOT

- **Dynamic route sirf API ke liye nahi** — `[id]` folder pattern kisi bhi page pe chalta hai (`/users/[id]`, `/posts/[slug]`). Yahi Next.js ka core routing feature hai (Batch 1 mein pages pe tha, ab route handlers pe).
- **`await context.params` = kabhi skip nahi** — Next.js 15+ mein params Promise hai — bina `await` ke id nahi milegi. 6.13 ke Task Board mein bhi yahi pattern use hoga.
- **DELETE mein body nahi hoti** — id URL mein jaati hai, isliye `NextRequest` nahi chahiye (aur `_request` underscore batata hai "use nahi karunga"). POST mein body thi isliye `NextRequest` tha.
- **`TodoItem` = "doosra `TodoList`" nahi** — `TodoItem` ek todo, `TodoList` pura list. Har cheez ka apna scope — yehi component design hai jo list ko maintainable rakhta hai.

**In Your Own Words**

1. Dynamic route `[id]` folder mein ID kaise milti hai, aur `await` kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Folder ka naam `[id]` = URL ka variable part. Function ka `context.params` usse leta hai — `/api/todos/abc2` → `{ id: "abc2" }`. Next.js 15+ mein params Promise hai (async), isliye `await context.params` karna padta hai — bina await ke id nahi milegi, Promise hi milta.

</details>

2. `DELETE` ka function `_request: Request` leta hai aur `NextRequest` nahi — kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** POST mein body aati thi (title), isliye `request.json()` ke liye `NextRequest` chahiye tha. DELETE mein body nahi hoti — sirf URL mein id jaati hai. Isliye request parameter ki zaroorat hi nahi — `_request` (underscore) batata hai "declare karna parda kyunki signature format hai, par use nahi karunga". Dynamic route handler ka standard signature: `(request, context)` — dono parameters position se aate hain.

</details>

3. `TodoItem` ko `onDelete` prop mein function milta hai — form (6.7.2) mein `onAdd` tha. Yeh pattern kya hai, aur parent data kaise handle karta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Yeh **props-based callback** pattern hai — child apne paas ka data (yahan todo id) parent ke function ko deta hai, aur parent asli kaam (fetch + list refresh) karta hai. Child ko pata hi nahi chalta delete kaise hota hai — wo sirf event + data forward karta hai. Data ka owner `TodoApp` hai (sab state wahan), isliye saare mutations wahi handle hote hain aur list refresh ka control ek jagah hai.

</details>

4. Delete ke baad list refresh kaise hoti hai, aur `loadTodos()` re-fetch kyun (directly local list se todo hata ke kyun nahi)?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `deleteTodo` DELETE success ke baad `await loadTodos()` karta hai — server se fresh list. Direct local removal (`setTodos(todos.filter(...))`) se bhi UI se todo hat jaata, par server state ko verify nahi karta. Agar delete fail hua ho ya server ne kuch aur change kiya ho, local removal galat state dikha deta. Server se re-fetch = hamesha server ki truth.

</details>

5. Agar kisi todo ka delete button dobara click karo — to kya hoga?

<details>
<summary>Show Answer</summary>

**Sample Answer:** UI pe dobara click nahi ho sakta — todo gayab ho chuka hai, button bhi chala gaya. Par agar wahi id curl/Postman se DELETE karo — 404 milega (`Todo nahi mila`), kyunki todo exist nahi karta. Yahi idempotency hai: **system ki final state dono baar same** ("todo exist nahi"), bhale response alag ho (pehli baar 200 + message, doosri baar 404). 404 proof hai ki system sahi state mein hai — violation nahi.

</details>
