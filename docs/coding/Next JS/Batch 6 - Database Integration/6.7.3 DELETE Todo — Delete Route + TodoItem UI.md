In 6.7.2, todos are being added — type a title in the form, it goes to POST /api/todos, and the list re-fetches and updates instantly. But think — what's the other half of any list? **Remove.** Right now you can't delete any todo. The 'First real todo' from 6.5 will always remain in the list.

In any real Todo app, the user needs a delete button. And here comes a pattern for the first time: **how do we target a specific todo to delete?** Each todo has its own _id — but the URL is always `/api/todos`, how do we target a single one?

**Answer: dynamic routes** — a variable part of the URL. `DELETE /api/todos/abc2` = "delete todo abc2". The `[id]` folder makes this work. You'll see this pattern everywhere — profile page `/users/[id]`, blog `/posts/[slug]`. Learning it here with the Todo app:

# DELETE /api/todos/[id] — Delete Route + TodoItem UI

## Step 1 — Route: Deleting One Todo

**THINK:** Now delete — but which one? **The ID is needed.** Send the ID in the URL: `DELETE /api/todos/abc2` = "delete todo abc2". So we need a **dynamic route** — the `[id]` folder.

**CONCEPT:** To delete, first the question — **which todo?** To delete "one todo", its **ID** is needed. Send the ID in the URL: `DELETE /api/todos/abc2` = "delete todo abc2". That's why a **dynamic route** is needed — folder named with **square brackets** = variable URL part. `app/api/todos/[id]/route.ts` handles all `/api/todos/anything` — `[id]` captures every value. Problem-first:

**Question 1 — how does the variable part of the URL become?** In `/api/todos/abc2`, `abc2` can be different on every request (sometimes `abc3`, sometimes `xyz`). A URL that's not fixed needs a **dynamic route** — folder name with **square brackets** = variable URL part. `app/api/todos/[id]/route.ts` handles all `/api/todos/anything` — `[id]` captures every value.

**Question 2 — how do we get the ID from the URL?** The function's **second parameter** is `context.params` — variable parts of the URL come here. `/api/todos/abc2` → `params = { id: "abc2" }`. And **Next.js 15+ params are async** — it returns a Promise. So `await context.params` is needed (Batch 1 `params` pattern — same one).

**Question 3 — how to delete?** `Todo.findByIdAndDelete(id)` — Mongoose method — finds the document by id and deletes it. The deleted document is returned — and if the id is wrong (todo doesn't exist at all) then **`null`**.

**Question 4 — wrong id?** Same as Step 3 — `null` = resource not found = **404** (6.6 design: wrong id = 404, wrong body = 400). On success **200 + message** — nothing to send back from a delete (the todo is gone), just a confirmation. (Some APIs return 204 No Content — but with a message, 200 is clearer in our design.)

```ts
// app/api/todos/[id]/route.ts
import { NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";

export async function DELETE(
  _request: Request,
  context: { params: Promise<{ id: string }> }
) {
  try {
    await connectDB();
    const { id } = await context.params;

    const deleted = await Todo.findByIdAndDelete(id);

    if (!deleted) {
      return NextResponse.json({ error: "Todo not found" }, { status: 404 });
    }

    return NextResponse.json({ message: "Todo deleted" }, { status: 200 });
  } catch (error) {
    console.error("Todo delete error:", error);
    return NextResponse.json({ error: "Unable to delete todo" }, { status: 500 });
  }
}
```

Imports stay the same — below is the complete `DELETE` function. Function line-by-line:

- **`DELETE(_request, context)`** — method name is DELETE. `_request: Request` — the **underscore prefix** means "this parameter I won't use" (DELETE has no body, request isn't needed). `context: { params: Promise<{ id: string }> }` — Question 2 — variable parts of the URL. The type says: params is a Promise, it has `id` which is a string.
- **`try` + connection** — same pattern — first make connection, then work.
- **`const { id } = await context.params`** — wait for params (it's async — Question 2), then extract `id`.
- **`Todo.findByIdAndDelete(id)`** — find + delete (Question 3). Deleted document in `deleted`, not found returns `null`.
- **`if (!deleted)` → 404** — wrong id = todo doesn't exist = 404 (Question 4).
- **Success — 200 + message** — delete confirmed (Question 4). No data to send back — todo no longer exists.
- **`catch` + 500** — same pattern — database error gets server-side log + 500.

## Step 2 — UI: TodoItem + Delete Button

**THINK:** Now each todo in the list needs a **delete button**. Click → `fetch` DELETE `/api/todos/[id]` → todo removed from database → list refreshes. Until now the list items were rendered directly inside `TodoList` (`todos.map` wrapped in `<li>`). Adding button + its state there would make the logic bloated — so we make a **`TodoItem` component** that takes one todo and renders it (title + delete button).

**CONCEPT:** Think of a restaurant menu — you don't read the whole menu at once, each dish has its own card with details + order button. Same here — the list = a collection of cards, each card = one todo's display + its actions. In React, **item-level components** are made this way (in Batch 3, each comment in `ShowComments` was also rendered this way). Problem-first:

**Question 1 — which component has the delete button?** `TodoItem` — because the button's job is "delete this specific todo", and `TodoItem` knows that todo (gets it via props). `TodoList` just maps and renders a `TodoItem` for each.

**Question 2 — how does delete work on click?** `TodoItem` takes an `onDelete` function as props (same pattern as `AddTodoForm`'s `onAdd` from 6.7.2). Click → `onDelete(todo._id)` — call parent with this id. The actual `fetch` DELETE is done by `TodoApp`'s `deleteTodo` — because the list refresh needs to happen there.

**Question 3 — where does DELETE get the `_id`?** Every todo has `_id` — `TodoItem` receives the full todo as props, so `todo._id` is used directly. Build the URL with template literal: `` `/api/todos/${todo._id}` `` — the variable inside a string.

**Question 4 — what's different between POST and DELETE?** POST sent a body (`JSON.stringify({ title })`) + headers. DELETE has **no body** — the id goes in the URL. So `fetch` only needs `method: "DELETE"` — no headers, no body. (6.6 design — which resource in URL, what to do in method.)

**Question 5 — how does the list refresh after delete?** The same pattern — `deleteTodo` refetches after `fetch` — just like `addTodo` did in 6.7.2. DELETE succeeds → todo removed from database → refetch → todo no longer shows in list.

## Nutshell

DELETE route: dynamic route `[id]` folder, `await context.params` gets the id (Next.js 15+ async params), `Todo.findByIdAndDelete(id)`, wrong id returns `null` → 404, success returns 200 + message. UI: `TodoItem` component renders each todo (title + done marker + **Delete button**), `onClick` → `onDelete(todo._id)` → `TodoApp.deleteTodo` → `fetch DELETE /api/todos/[id]` → `loadTodos()` refetch. `TodoList` now renders items via `TodoItem`, forwards `onDelete`.

## What It Is NOT

- **Dynamic route is only for APIs** is wrong — `[id]` folder pattern works on any page — `/users/[id]`, `/posts/[slug]`. This is Next.js core routing (Batch 1 had it on pages, now route handlers).
- **`await context.params` can be skipped** is wrong — in Next.js 15+ params is a Promise — without `await` you don't get the id. In 6.13 Task Board the same pattern is used.
- **DELETE has a body** is wrong — the id goes in the URL, so `NextRequest` isn't needed (and `_request` underscore signals "I receive this but won't use it"). POST had a body so it needed `NextRequest`.
- **`TodoItem` = "another `TodoList`"** is wrong — `TodoItem` renders one todo, `TodoList` renders the whole list. Each component has its own scope — this is what keeps a list maintainable.
- **Delete button client-side = no server safety** is true — anyone can delete on the UI. In production permission checks happen on the server (auth). Fine for learning — in 6.8 Postman can also DELETE, same API.

**In Your Own Words**

1. Dynamic route `[id]` — how is the id captured, and why `await`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Folder named `[id]` = the variable part of the URL. The function's `context.params` extracts it — `/api/todos/abc2` → `{ id: "abc2" }`. In Next.js 15+ params is a Promise (async), so `await context.params` is needed — without it you get a Promise, not the id.

</details>

2. `DELETE`'s function takes `_request: Request` but not `NextRequest` — why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In POST, there was a body (the title) — so `request.json()` needed `NextRequest`. DELETE has no body — the id goes in the URL. So the request parameter isn't needed — `_request` (underscore) signals "this must be declared because that's the signature format, but I won't use it". The dynamic route handler's standard signature is `(request, context)` — both params come in order.

</details>

3. `TodoItem` receives `onDelete` as a prop (function) — same as form's `onAdd` in 6.7.2. What pattern is this, and how does the parent handle the data?

<details>
<summary>Show Answer</summary>

**Sample Answer:** This is the **props-based callback** pattern — the child does its part and forwards its own data (here, the todo id) to a parent function; the parent does the real work (fetch + list refresh). The child has no idea how delete works — it just emits an event + data. The data owner is `TodoApp` (all state is there), so all mutations are handled there and list refresh control is in one place.

</details>

4. After delete, how does the list refresh, and why refetch instead of filtering locally (`setTodos(todos.filter(...))`)?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `deleteTodo` refetches after DELETE succeeds — fresh data from the server. Filtering locally (`setTodos(todos.filter(...))`) would remove it from the UI, but you don't verify the server actually deleted it. If the delete failed or the server changed something, local filtering shows incorrect state. Refetching from the server = always the truth the server knows.

</details>

5. If you click delete on a todo again — what happens?

<details>
<summary>Show Answer</summary>

**Sample Answer:** You can't click again on the UI — the todo is gone, its button went with it. But if you DELETE that same id via curl/Postman again — you get a 404 (`Todo not found`), because the todo no longer exists. This is idempotency: **the system's final state is the same both times** ("todo doesn't exist"). First call 200 + message, second call 404 — but state is the same. The 404 proves the system is in the correct state — not a violation.

</details>
