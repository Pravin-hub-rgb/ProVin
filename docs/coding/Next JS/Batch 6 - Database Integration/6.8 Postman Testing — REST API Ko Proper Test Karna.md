# Postman Testing — Testing REST API the Proper Way

## What is Postman (First Time)

**Postman** is an **API testing tool** — a desktop app (or browser version). In it you create requests — method, URL, body — send them, and see the response: status code, headers, JSON body. And all requests are **saved** — in one place, to test again.

Why Postman, not curl? Curl is raw terminal — you type the full command every time, no response formatting, no history. Postman gives you:

- Requests saved (collections)
- Readable JSON responses
- Clear status codes
- Same request sent again with one click

Download: **https://www.postman.com/downloads/** — install the desktop app.

## Setup — Start App, Start Project

1. `npm run dev` — start the project (Mongo Todo API is running)
2. Open Postman
3. Create a **new request** (New → HTTP Request)

Now test each endpoint in order — **the same order as 6.7.1 to 6.7.4**.

## Test 1 — GET /api/todos (List)

**Method:** GET, **URL:** `http://localhost:3000/api/todos`, click **Send**.

**Expectation:** 200 OK + todos as a JSON array.

**Check:**

- **Status:** `200 OK`
- **Body:** JSON array — `[ { "_id": ..., "title": ..., "done": ... }, ... ]`
- If the database is empty, you'll see `[]`

This is the same data you see in the UI list (6.7.1) — **200 = GET successful** (6.6 design).

## Test 2 — POST /api/todos (Create)

**Method:** POST, **URL:** `http://localhost:3000/api/todos`.

In the **Body** tab:

1. Select **raw**
2. From the type dropdown, select **JSON**
3. Paste this:

```json
{
  "title": "Todo created from Postman"
}
```

Click **Send**.

**Expectation:** 201 Created + the new todo as JSON, with **auto-generated `_id`, `done: false`, `createdAt`/`updatedAt`**.

**Check:**

- **Status:** `201 Created` — new resource created (6.6 design — POST successful = 201)
- **Body:** the new todo — `_id` generated by MongoDB, `done` defaults to false, timestamps appear

**Save this response** — copy the `_id`, you'll need it for the next tests (in the URL).

## Test 3 — Error Case: POST Without Title

**THINK:** Now test error handling — design (6.6) says "wrong body = 400." In Postman you also test **negative cases**, not just success.

**Method:** POST, **URL:** `http://localhost:3000/api/todos`, **Body:**

```json
{}
```

Click **Send**.

**Expectation:** `400 Bad Request` + `{ "error": "Title is required" }`.

**Check:**

- **Status:** `400` — client's mistake (6.6 design)
- **Body:** error shape is consistent — `{ "error": "message" }` (6.6 standard)

**Important point:** This error test is important because it verifies the design — when bad data comes in, the server returns 400 (not 500). The client's mistake should be clearly communicated to the client.

## Test 4 — GET /api/todos/[id] (Detail)

Now test a single todo — via the dynamic route. In 6.7.3/6.7.4 we didn't build a detail GET (the list GET + UI was enough), but per REST design, `GET /api/todos/:id` is a standard endpoint — **rarely used, so we add it now.** First, see how.

**CONCEPT:** `Todo.findById(id)` — one document by id. Not found → null → 404.

**File:** `app/api/todos/[id]/route.ts` — add GET at the top (alongside PUT/DELETE):

```ts
// app/api/todos/[id]/route.ts — add at the top
export async function GET(
  _request: Request,
  context: { params: Promise<{ id: string }> }
) {
  try {
    await connectDB();
    const { id } = await context.params;

    const todo = await Todo.findById(id);

    if (!todo) {
      return NextResponse.json({ error: "Todo not found" }, { status: 404 });
    }

    return NextResponse.json(todo, { status: 200 });
  } catch (error) {
    console.error("Todo fetch error:", error);
    return NextResponse.json({ error: "Unable to fetch todo" }, { status: 500 });
  }
}
```

`findById(id)` — one document by id. Wrong id → null → 404. Correct id → 200 + todo.

**In Postman:**

**Method:** GET, **URL:** `http://localhost:3000/api/todos/<YOUR_ID>` (from Test 2's `_id`).

**Expectation:** `200` + that todo as JSON. Wrong id → `404` + `{ "error": "Todo not found" }`.

## Postman Collections — Save Once, Use Forever

Postman's power is saving requests as **collections** — all the endpoints in one place, send again with one click.

1. Click **Save** (next to the request)
2. **Create new collection** → name it `Mongo Todo API`
3. Name the request — "List todos", "Create todo", "Create todo (error)", "Update todo", "Delete todo"
4. Save

Now anytime you can test the whole API in one place — no retyping. **Collections are API testing muscle memory.**

## Nutshell

Postman is an API testing tool — requests are saved (collections), responses show readable JSON. The testing pattern for CRUD: check **each endpoint's success case** (correct status code + body) and **error cases** (bad data gets the correct error code + consistent error shape). 400 vs 404, 200 vs 201 — verify against the design (6.6).

## What It Is NOT

- **Postman = just "a button to send requests" is wrong.** The real value is the testing methodology — systematically checking success + error cases, verifying status codes. The tool is just the medium.
- **Postman testing = production testing** is wrong. Postman verifies API behavior — not performance, load, or security. This is functional testing.
- **`GET /api/todos/:id` (detail) = optional extra** is wrong. It's a REST standard endpoint — when a client needs a single resource, this is how it gets it. We added it late (gradual), but it's part of the design.
- **400 = bad server behavior** is wrong. 400 means the server correctly told the client what went wrong — that's **good design**. 500 (thrown without validation) is the problem.
- **Postman = only for backend developers** is wrong. Frontend developers also need to know what the API does — Postman first, then code.

**In Your Own Words**

1. POST success returns 201, GET success returns 200 — what's the difference, and how do you verify in Postman?

<details>
<summary>Show Answer</summary>

**Sample Answer:** 200 = general "OK", 201 = specifically "new resource created". POST creates a new resource, so 201; GET reads data, so 200. In Postman, the response's status area shows the code clearly — you match it against the expected code (201 for POST).

</details>

2. Why test error cases (like POSTing `{}`) — aren't success tests enough?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Success tests show the happy path works — but not what happens with bad data. Error tests verify that a client mistake returns 400 (not 500) and the error shape is consistent. Without error tests, you don't know how the server behaves with invalid input — and bad input happens every day in production.

</details>

3. Wrong body → 400, wrong id → 404 — how are these two tested differently in Postman?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Wrong body — send POST with `{}` — the server should return 400 ("client sent bad data"). Wrong id — send GET/PUT/DELETE with some random id (`/api/todos/abc`) — the server returns 404 ("resource doesn't exist"). Two tests, two different expectations — 400 is about the body, 404 is about the resource's existence.

</details>

4. What is a Postman collection, and how does it help in production?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A collection is a saved group of requests — all the API's endpoints in one place, sendable again with one click. In any project, whenever the API changes, run the whole collection as a regression test — if any endpoint broke, you know immediately. Shared collections let the whole team use the same requests.

</details>

5. `GET /api/todos/:id` (detail) wasn't there in 6.7.x, but we added it now — what's the benefit of this gradual approach?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In 6.7.x the focus was the core CRUD (list, create, update, delete) — one thing at a time. The detail endpoint naturally comes up when you're API-testing and need to check a single todo's response. Building gradually means each addition has a clear reason, and you're not confused by too many endpoints at once.

</details>
