# System Design — Thinking About Relations, Indexes, Performance

## Step 1 — The Problem: One Table Isn't Enough

**THINK:** Right now `drizzle_todos` is a single table. Tomorrow we need a new thing — **which user a todo belongs to**. Share one todo list with many users? No — each user should have their own. The data structure changes:

- One **user** has multiple **todos**
- This is a **1:N (one-to-many) relation** — 1 user → N todos

If you dump everything in one table, you get duplicate data — every todo row also carries the user's full name — and if the user's name changes, all those rows need updating. **Data needs to be normalized** — separate tables, connected by relations.

## Step 2 — Primary Key and Foreign Key

**CONCEPT:** Relations in SQL are made with **keys**. Remember two keys:

- **Primary Key** — each row's unique id in a table (6.10 had `serial('id').primaryKey()` — the same).
- **Foreign Key** — a reference to another table's primary key — this is how relations are formed.

**Users table** (new — thinking only, no code here):

```
users table
| id (PRIMARY KEY) | name  |
|------------------|-------|
| 1                | Vin   |
| 2                | Riya  |
```

**Todos table** (the current one — with a new column `user_id`):

```
drizzle_todos table
| id (PK) | title         | user_id (FK → users.id) |
|---------|---------------|-------------------------|
| 1       | Homework      | 1                       |
| 2       | Gym           | 1                       |
| 3       | Call          | 2                       |
```

- **`user_id`** — foreign key — "this todo belongs to which user". Todos 1 and 2 belong to Vin (`user_id: 1`), todo 3 belongs to Riya (`user_id: 2`).
- Relation: **1 user → N todos** (users.id appears once, drizzle_todos.user_id appears N times.)

**What this solves:** the user's name lives in one place (users table). Change the name, update one row. Todos don't repeat the name — just carry `user_id`. **Normalized data — no duplication.**

## Step 3 — Query: Getting Related Data

**THINK:** Now we need to get data — "show me Vin's todos." Related data is fetched with a **join**.

**CONCEPT (this is a concept file — code in Drizzle comes in 6.13.3, just the idea here):** `SELECT * FROM drizzle_todos WHERE user_id = 1` — a simple filtered query. But sometimes you want "Vin AND his todos" together — then you need a JOIN:

```sql
SELECT * FROM users JOIN drizzle_todos ON users.id = drizzle_todos.user_id WHERE users.id = 1;
```

**In Drizzle** this is done with `.leftJoin()`/`.innerJoin()` methods, or Drizzle relations (`relations` config) — Prisma makes relation fields (`user: { include: { todos: true } }` — seen in 6.13.4). **For now, just the concept:** relation → keys → JOIN — data comes from two tables.

The opposite of 1:N is also there — N:N (many-to-many) — like a Task Board where a task and a tag — two users sharing the same task? No, in Task Board there's one user, the board's user. N:N needs a **join table**. **Details in 6.13** when we build the Prisma schema. For now, just understand 1:N — the most common relation.

## Step 4 — Indexes: Making Lookups Fast

**THINK:** In a Todo app, a query like `WHERE user_id = 5`. If there's a lot of data — 100k rows — PostgreSQL scans the entire table? **That's slow.** The solution — **indexes**.

**CONCEPT:** An index is the database's **"index of a book"** equivalent. Instead of scanning the table row by row, look at the index — "where is user_id 5?" — jump straight to it. An index is built on one or more columns of a table.

**In Drizzle:**

```ts
export const todos = pgTable('drizzle_todos', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  user_id: integer('user_id').references(() => users.id),
  done: boolean('done').default(false).notNull(),
}, (table) => ({
  userIdx: index('user_idx').on(table.user_id),
}))
```

- **`.references(() => users.id)`** — foreign key — tells Drizzle that `user_id` references `users.id`.
- **`index('user_idx').on(table.user_id)`** — an index on `user_id` — queries with `WHERE user_id = 5` run fast.

**What indexes do:** lookup time doesn't grow with table size — if an index is used, you jump straight to it. **What indexes don't do:** each insert/update gets slightly slower (the index must be updated too). That's why **only index columns that appear in WHERE/JOIN of queries** — over-indexing is also a problem.

**Auto-indexing:** PostgreSQL automatically indexes the primary key — querying by `id` is fast by default. Foreign keys need **manual** indexes (shown above).

## Step 5 — Read vs Write Patterns

Now let's think about data access patterns — in 6.11.1/6.11.2/6.11.3 we saw both (SC reads + SA writes). At the design level, the difference matters:

- **Read-heavy** (displaying lists, showing details) — Server Components — query on the server, cached render (`revalidatePath`), no client round-trip. Fast and simple. That's why SC reads are the default.
- **Write-heavy** (form submissions, toggles, deletes) — Server Actions — direct server function, revalidate and get a fresh render. **Here, a POST route + fetch is an unnecessary layer** when the data only comes from this same app.
- **When REST is actually needed** — when external clients consume the data (mobile app, public API, third-party integration). Then URL-based API is the right choice — Server Actions don't expose URLs.

**One more thought — the N+1 problem** (interview favorite): rendering a user's todos, querying for each row individually? N queries — slow. **JOIN (or ORM relation include)** gets everything in one query. In 6.13.4 with Prisma you'll see this.

## Step 6 — Decision Framework: When to Use What

| Scenario | Use | Why |
|---|---|---|
| App's own UI data (reads) | Server Component + `db.select()` | Query on server, no extra layer |
| App's own forms (writes) | Server Action + `revalidatePath` | Direct server call, no API surface |
| Public API / mobile / 3rd party | REST Route Handler | URL-based, testable with Postman |
| Related data | JOIN / relation include | Avoids N+1, single query |
| Search/filter query (`WHERE user_id`) | Index | Fast lookup, no table scan |
| 1 user → N todos | Foreign key (`user_id`) | Normalized data, no duplication |

**But an important point:** indexes, relations — none of this is needed in this app right now. **What matters is the thinking** — how the system has problems when it grows, and what the solution patterns are. Right now straight `db.select()` on Todo is fine. Building this habit = system design.

## Nutshell

System design: data connects through relations (1:N user→todos, foreign key `user_id` references users.id), and JOIN or relation include fetches them together. Indexes make searches fast (only index columns that appear in WHERE/JOIN). Reads go in Server Components (server-side query), writes in Server Actions (direct call), REST only when external clients. The N+1 problem — a query per row — is solved by JOIN.

## What It Is NOT

- **Foreign key = "just a column"** is not accurate. `user_id` column plus `.references()` enforces the relation — you can't insert a `user_id` that doesn't exist (the constraint rejects it). Just the column without it means the database has no idea about the relation.
- **Index = "put it on every column"** is not accurate. Indexes speed up reads but slow writes (index must update). PostgreSQL auto-indexes primary keys, foreign keys need manual indexing. Only index columns that WHERE/JOIN queries use.
- **JOIN = "separate query to another table"** is not accurate. JOIN is a single query that combines tables by key — it's the opposite of N+1 (a query per row). The first JOIN might feel expensive, but for bulk data it's the most efficient approach.
- **N:N = 1:N in disguise** is not accurate. 1:N keeps the foreign key in the same table. N:N (tasks↔tags) needs a **join table** (both ids). Different pattern — details in 6.13, but knowing it's different is useful.
- **"System design" = "designing big systems"** is not accurate. It's a way of thinking — data structure, queries, performance — applied to any app of any size. Small apps have simple queries, but the thinking is the same — "what if it grows?"

**In Your Own Words**

1. In a 1:N relation, what's the difference between primary key and foreign key?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The primary key is the unique id within its own table (users.id). The foreign key is a reference to another table's primary key (todos.user_id → users.id). The reference is what forms the relation — "this todo belongs to which user". The primary key appears once, the foreign key can appear N times (one user, N todos).

</details>

2. Why is data normalization necessary? Give an example.

<details>
<summary>Show Answer</summary>

**Sample Answer:** If the user's name is repeated in every todo row, then changing the name requires updating every row — duplication + inconsistency. Normalizing (separate users table + only `user_id` in todos) means the name exists in one place — one update reflects everywhere.

</details>

3. How do indexes work, and why only on some columns?

<details>
<summary>Show Answer</summary>

**Sample Answer:** An index is the database's lookup structure (like a book's index) — with `WHERE user_id = 5`, instead of scanning the whole table, the index tells you where the data is. Only index columns that WHERE/JOIN queries use, because every index is updated on each write — over-indexing slows down writes.

</details>

4. What is the N+1 problem, and how does JOIN solve it?

<details>
<summary>Show Answer</summary> 

**Sample Answer:** N+1 = first one query for the list, then a separate query per item (N queries) — slow. JOIN is a single query that connects tables by key — all data in one round-trip. An ORM's `include` does this internally — avoids N+1.

</details>

5. For our app's own forms, use Server Actions rather than REST — why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Server Actions are direct server function calls — no API URL, no fetch, no JSON parsing — the form submits and the action runs, then `revalidatePath` refreshes the UI. REST is when external clients consume the data (mobile, public API) — then URL-based access is needed. For our own UI, Server Actions remove the unnecessary API layer.

</details>
