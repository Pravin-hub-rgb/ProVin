# Drizzle Schema + Client — Data Blueprint (SQL Version)

## Why Schema First?

To use the database, a **connection file** is needed (`db/index.ts`) — which connects to Neon and exports a `db` variable. But that connection file **imports the schema** — so Drizzle knows the table structure:

```
db/index.ts → imports schema → db/schema.ts
```

So first the schema (table structure), then the connection file — complete in one go.

## Why `db/` Folder, Not `lib/`?

With Mongo we made `lib/mongodb.ts` (`lib/` = general helpers). **`db/` specifically for database** — schema + connection, both here. This is the convention used in Drizzle community. Create at project root (where `app/` is):

```
sql-todo/
├── app/
├── db/              ← new folder
├── .env
└── package.json
```

## `db/schema.ts` — Define the Table

In 6.9 we tested with raw SQL. The SQL structure of a table looks like this:

```sql
CREATE TABLE drizzle_todos (
  id    SERIAL   PRIMARY KEY,
  title TEXT     NOT NULL,
  done  BOOLEAN  DEFAULT false
);
```

Now the same thing in TypeScript — **in Drizzle's syntax**. Column types come from `drizzle-orm/pg-core` (`pg` = PostgreSQL — Drizzle's PostgreSQL part). Understand the concepts before the code:

**`pgTable`** — Drizzle's version of SQL `CREATE TABLE` — "define a PostgreSQL table." First argument is the table name, second is the columns object.

**Column types:** `serial` — SQL's `SERIAL` — auto 1, 2, 3... — for ids. `text` — SQL's `TEXT` — string data. `boolean` — SQL's `BOOLEAN` — true or false.

**Why the table name `drizzle_todos` and not `todos`?** To avoid name conflict — remember 6.9, we manually created tables in Neon? If Drizzle also names it `todos`, then `push` gets confused — which table was created by whom. `drizzle_todos` is clear.

**Each field's options:** on `id` we put `.primaryKey()` — SQL `PRIMARY KEY` — auto-increment + unique identifier. On `title` we put `.notNull()` — SQL `NOT NULL` — can't be empty. On `done` we put `.default(false)` — SQL `DEFAULT false` — if no value given, defaults to `false`.

**What is `InferSelectModel`?** In 6.5 we manually wrote the `ITodo` interface. The problem — if the schema changed, the type had to be updated separately — if forgotten, bugs. `InferSelectModel` looks at the schema and **extracts the type itself** — schema changes, type updates automatically.

Now create the file — one line at a time, so the reason for each is clear. **File:** `db/schema.ts`

First, import the four column types (`pgTable`, `serial`, `text`, `boolean`) from `drizzle-orm/pg-core` (the PostgreSQL part — the concept above), and `InferSelectModel` to extract types from the core package:

```ts
// db/schema.ts
import { pgTable, serial, text, boolean } from 'drizzle-orm/pg-core'
import { InferSelectModel } from 'drizzle-orm'
```

**Import the column types** — all four from `drizzle-orm/pg-core` (the PostgreSQL part — the concept above). **Import `InferSelectModel`** — the type-extracting helper from the core package (instead of writing interfaces manually like 6.5).

Now define the table — `pgTable('drizzle_todos', {...})` — the table name in the database is `drizzle_todos` (name conflict reason). Inside, each column:

```ts
// db/schema.ts
import { pgTable, serial, text, boolean } from 'drizzle-orm/pg-core'
import { InferSelectModel } from 'drizzle-orm'

export const todos = pgTable('drizzle_todos', {    // NEW
```

**`pgTable('drizzle_todos', {...})`** — define table — database name is `drizzle_todos` (name conflict reason). Inside, each column:

```ts
// db/schema.ts
import { pgTable, serial, text, boolean } from 'drizzle-orm/pg-core'
import { InferSelectModel } from 'drizzle-orm'

export const todos = pgTable('drizzle_todos', {
  id: serial('id').primaryKey(),                   // NEW
```

**`serial('id').primaryKey()`** — SQL `id SERIAL PRIMARY KEY` — auto 1, 2, 3... + unique identifier. `'id'` is the column name.

```ts
// db/schema.ts
import { pgTable, serial, text, boolean } from 'drizzle-orm/pg-core'
import { InferSelectModel } from 'drizzle-orm'

export const todos = pgTable('drizzle_todos', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),                  // NEW
```

**`text('title').notNull()`** — SQL `title TEXT NOT NULL` — string, cannot be empty.

```ts
// db/schema.ts
import { pgTable, serial, text, boolean } from 'drizzle-orm/pg-core'
import { InferSelectModel } from 'drizzle-orm'

export const todos = pgTable('drizzle_todos', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  done: boolean('done').default(false).notNull(),  // NEW
})
```

**`boolean('done').default(false).notNull()`** — SQL `done BOOLEAN DEFAULT false` — value defaults to `false`.

Now extract the type — `InferSelectModel` looks at the schema and extracts a type — in 6.5 we manually wrote the interface, here the schema extracts it itself:

```ts
// db/schema.ts
import { pgTable, serial, text, boolean } from 'drizzle-orm/pg-core'
import { InferSelectModel } from 'drizzle-orm'

export const todos = pgTable('drizzle_todos', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  done: boolean('done').default(false).notNull(),
})

export type Todo = InferSelectModel<typeof todos>  // NEW
```

**`export type Todo = InferSelectModel<typeof todos>`** — type extracted from schema — in 6.5 we manually wrote the interface, here the schema extracts it itself.

Internally, `Todo` becomes:

```ts
type Todo = {
  id: number      // serial → number
  title: string   // text → string
  done: boolean   // boolean → boolean
}
```

Compare with 6.5 — manually written interface vs schema-derived:

```ts
// 6.5 MongoDB — manual interface
export interface ITodo {
  _id: string
  title: string
  done: boolean
}

// 6.10 Drizzle — automatic from schema
export type Todo = InferSelectModel<typeof todos>
```

## `db/index.ts` — Connection + Db Client

**Why we need it:** In a Next.js app, the database is used in many places (pages, actions). If each file opens its own connection, we'd have the same connection code everywhere — repetition. **Create the connection once — import everywhere.** That's what `db/index.ts` does.

Understand three things first:

**Raw connection (`neon`)** — the 6.9 `neon` function — `neon(process.env.DATABASE_URL!)` creates a raw connection from the connection string. `!` — TypeScript is guaranteed: "it's in `.env`, definitely not undefined".

**`import * as schema`** — imports all exports from schema.ts at once as a `schema` object (`schema.todos`, `schema.Todo`). Drizzle needs this to know types.

**`drizzle()` is a function with two arguments:**
- **First argument = connection** (`sql`) — *how to talk to the database* — which driver, where to connect. This is the 6.9 raw Neon connection.
- **Second argument = a config object** (`{ schema }`) — *what's in the database* — which tables, which types. Drizzle makes queries type-safe with this.

The result is a **`db` client object** — with query methods inside (`db.select()`, `db.insert()`). We **export this as `db`** — imported everywhere.

And an import question — **why `drizzle-orm/neon-http` and not just `drizzle-orm`?** Inside Drizzle, there are different connectors for different databases:

```
drizzle-orm/neon-http    ← for Neon
drizzle-orm/postgres-js  ← for local PostgreSQL
drizzle-orm/mysql2       ← for MySQL
```

We use Neon — so `neon-http`.

Now create the file — one line at a time, so the reason for each is clear. **File:** `db/index.ts`

First, import — `neon` for raw connection (seen in 6.9), `drizzle` from the Neon connector (the reason above), and `* as schema` imports all exports from schema.ts at once (not just `todos` — future new tables come from here too):

```ts
// db/index.ts
import { neon } from '@neondatabase/serverless'
import { drizzle } from 'drizzle-orm/neon-http'
import * as schema from './schema'
```

**`neon` import** — for raw connection (seen in 6.9). **`drizzle` import** — from the Neon connector — the reason above (`neon-http`). **`* as schema`** — import all exports from schema.ts at once — not just `todos`, future new tables will come from here too.

Now create the raw connection — `neon(process.env.DATABASE_URL!)` creates it (connection string from `.env`):

```ts
// db/index.ts
import { neon } from '@neondatabase/serverless'
import { drizzle } from 'drizzle-orm/neon-http'
import * as schema from './schema'

const sql = neon(process.env.DATABASE_URL!)    // NEW
```

**`const sql`** — raw connection created (connection string from `.env`).

Now turn this into a Drizzle client — `drizzle()` function takes two arguments: first `sql` (connection — how to talk to the database), second `{ schema }` (config object — what's in the database). The result is `db` — `export const db` makes it importable everywhere — `db.select()`, `db.insert()`, etc:

```ts
// db/index.ts
import { neon } from '@neondatabase/serverless'
import { drizzle } from 'drizzle-orm/neon-http'
import * as schema from './schema'

const sql = neon(process.env.DATABASE_URL!)

export const db = drizzle(sql, { schema })    // NEW
```

**`export const db`** — the result of `drizzle()`. First argument `sql` = connection (how to talk). Second `{ schema }` = config object — **the whole schema why?** Because `* as schema` put all exports into one object (table definitions + types) — Drizzle needs the full model, so it:
- **Types are checked** — on `db.select().from(todos)`, TypeScript knows the columns and what values are right (seen in 6.11.1).
- **New tables are auto-available in future** — if you create a `users` table later, it shows up in the `schema` object — nothing changes in this file.
- **Relational queries (`db.query`)** — Drizzle's relational API runs on this schema (in 6.13.4, Prisma `include` equivalent — Drizzle's `db.query.todos.findMany()`).

Just passing `todos` means Drizzle knows only one table — passing the whole schema means the full model is registered.

**Compare with Mongo** (6.4's `lib/mongodb.ts`):

```ts
// 6.4 MongoDB — lib/mongodb.ts
// async/await + readyState check needed
async function connectDB() {
  if (mongoose.connection.readyState === 1) return
  await mongoose.connect(MONGODB_URI)
}

// 6.10 Drizzle — db/index.ts
// Neon is serverless — auto-connects per query — just 3 lines
const sql = neon(process.env.DATABASE_URL!)
export const db = drizzle(sql, { schema })
```

With Mongo, the connection was persistent — connect once, reuse. Neon is serverless — queries auto-connect/disconnect — so `db` is exported directly, no need to await `connectDB()`.

## `drizzle.config.ts` — Tell Drizzle-Kit Everything

`drizzle-kit` doesn't know anything yet: "where's the schema file? which database? how to connect?" — all goes in the config file. Four options:

**`schema`** — where the schema file is (table structure — `./db/schema.ts`).
**`out`** — where to save migrations (`./drizzle` folder — drizle-kit creates it).
**`dialect: 'postgresql'`** — which database (Drizzle supports MySQL/SQLite/PostgreSQL — we use `postgresql`).
**`dbCredentials.url`** — connection string to connect to Neon (to create tables).

Now create the file — one line at a time, so the reason for each is clear. **File:** `drizzle.config.ts` (project root — `drizzle-kit` command looks for it automatically here)

First import — **`defineConfig` is a function** — takes a config object (argument) and returns a typed config (`drizzle-kit` reads it). Just know that config makes it understandable to `drizzle-kit`:

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'
```

**`defineConfig` import** — a function: takes a config object argument, returns a typed config — `drizzle-kit` reads it. Now create the config object — `defineConfig({...})` — four options one by one:

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({                   // NEW
```

**`export default defineConfig({...})`** — config object — four options inside.

First — `schema` — where the table structure is:

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema: './db/schema.ts',                     // NEW
```

**`schema`** — where the table structure is (`./db/schema.ts`).

Second — `out` — where to save migrations (`drizzle/` folder — drizle-kit creates it):

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema: './db/schema.ts',
  out: './drizzle',                             // NEW
```

**`out`** — where to save migrations (`drizzle/` folder — drizle-kit creates it).

Third — `dialect` — which database — `postgresql` (Drizzle supports MySQL/SQLite/PostgreSQL):

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema: './db/schema.ts',
  out: './drizzle',
  dialect: 'postgresql',                        // NEW
```

**`dialect`** — which database — `postgresql` (Drizzle supports MySQL/SQLite/PostgreSQL).

And last — `dbCredentials.url` — connection string for Neon (to create tables). `!` — TypeScript is guaranteed — it's in `.env`:

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema: './db/schema.ts',
  out: './drizzle',
  dialect: 'postgresql',
  dbCredentials: {                              // NEW
    url: process.env.DATABASE_URL!,
  },
})
```

**`dbCredentials.url`** — connection string for Neon (to create tables). `!` — TypeScript is guaranteed — it's in `.env`.

> **What is a migration?** Today we're creating a table. Tomorrow we need a new column (`createdAt`). The database already has the table — can't change directly. First create a "change record" (a migration file), then apply it. `drizzle-kit` saves these files in the `drizzle/` folder. In production, this is how schema changes are tracked. (Details in 6.13.3 — Prisma migrate — for now just the idea.)

## Create Table in Neon — `npx drizzle-kit push`

Now create the actual table in Neon. First, understand — **`npx` kya?** Runs installed packages from the terminal (remember `npx create-next-app`? same thing). This is how `drizzle-kit` runs.

What happens behind the command? `drizzle.config.ts` is read → schema file is read → connects to Neon → checks "does the `drizzle_todos` table already exist?" → if not, runs `CREATE TABLE` SQL. Now in terminal:

```bash
npx drizzle-kit push
# for bun users (seen in 6.4) — same command, via bun:
bunx drizzle-kit push
```

In terminal: `[✓] Changes applied`. In Neon dashboard, "Tables" → `drizzle_todos` appears.

> **One easy mistake to avoid (save for later):** Keep `DATABASE_URL` in `.env` (Next.js and drizzle-kit both read `.env`), not in `.env.local`. Why? Next.js (the app) reads `.env.local`, but **drizzle-kit's dotenv only reads `.env`**. If you keep it in `.env`, both can read it — one place, both work. If you get an error — "Either connection url or host, database are required" — that means drizzle-kit didn't get `DATABASE_URL` (it was only in `.env.local`). Fix: put the connection string in `.env` file.

## Nutshell

In Drizzle: `db/schema.ts` defines a table with `pgTable` + column types (serial/text/boolean), `InferSelectModel` extracts types. `db/index.ts` creates `neon()` connection + `drizzle(sql, { schema })` which gives a `db` client (simpler than Mongo's `connectDB`). `drizzle.config.ts` tells the tool which file which database. `npx drizzle-kit push` creates the actual table in Neon.

## What It Is NOT

- **`pgTable` = creates a table in the database** is wrong. `pgTable` is just a TypeScript definition. The actual table is created in Neon by running `npx drizzle-kit push`. Running the app without `push` → error — "relation does not exist."
- **`InferSelectModel` = magic typing** is wrong. It looks at the schema's columns and generates a type — convenience, not magic. The types (number/string/boolean) are the same either way.
- **`db` = the connection** is wrong. `db` is the Drizzle client object that has query methods (`db.select()`, `db.insert()`) — the actual connection is `sql`, hidden. Users use `db` — `sql` is internal.
- **`drizzle.config.ts` = runtime code** is wrong. It's only for `drizzle-kit` (dev tool) — not imported in the app. That's why `drizzle-kit` is a dev dependency, not a production dependency.
- **`npx drizzle-kit push` = production migration tool** is wrong. `push` is for quickly syncing in development. Production-grade changes are migrations (`out` folder). In 6.13.3, Prisma's migrate system is shown.
