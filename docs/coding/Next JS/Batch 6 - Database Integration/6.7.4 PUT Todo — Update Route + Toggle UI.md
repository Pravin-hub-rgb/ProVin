# PUT /api/todos/[id] — Update Route + Toggle UI

## Step 1 — Route: Updating a Todo

**THINK:** Now update — toggle a todo's `done`, or change its `title`. In 6.6 we decided to use **PUT**. Same dynamic route — add the PUT function to it.

**CONCEPT:** The update question — toggle `done` or change `title`. In 6.6 we decided to use **PUT**. An update needs two things: **which todo** (id — the dynamic route from Step 3) and **what to update** (data — in the body). Problem-first:

**Question 1 — data from where?** PUT also has a body (new title, new done) — so `NextRequest` is needed again, exactly like POST (6.7.2). `request.json()` extracts `{ title, done }`.

**Question 2 — how to update?** `Todo.findByIdAndUpdate(id, updateData)` — find by id, update the data. Two arguments: first **which one** (id), second **what** (`{ title: ..., done }`).

**Question 3 — `{ new: true }`? (gotcha!)** This is the trickiest part. Without it, `findByIdAndUpdate` **returns the old (pre-update) document** — the data before the update. The user thinks the update failed, when the database has already changed. **`{ new: true }`** means: "return the updated document." So three arguments: id, updateData, options. `{ new: true }` is this method's most common bug.

**Question 4 — wrong id?** Same as Step 3 — `null` → **404**. And on success **200 + updated document**.

```ts
// app/api/todos/[id]/route.ts
import { NextRequest, NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";

export async function DELETE(
  _request: Request,
  context: { params: Promise<{ id: string }> }
) {
  try {
    await connectDB();
    const { id } = await context.params;

    const deleted = await Todo.findByIdAndDelete(id);

    if (!deleted) {
      return NextResponse.json({ error: "Todo not found" }, { status: 404 });
    }

    return NextResponse.json({ message: "Todo deleted" }, { status: 200 });
  } catch (error) {
    console.error("Todo delete error:", error);
    return NextResponse.json({ error: "Unable to delete todo" }, { status: 500 });
  }
}

export async function PUT(
  request: NextRequest,
  context: { params: Promise<{ id: string }> }
) {
  try {
    await connectDB();
    const { id } = await context.params;
    const body = await request.json();
    const { title, done } = body;

    const updated = await Todo.findByIdAndUpdate(
      id,
      { title: title.trim(), done },
      { new: true }
    );

    if (!updated) {
      return NextResponse.json({ error: "Todo not found" }, { status: 404 });
    }

    return NextResponse.json(updated, { status: 200 });
  } catch (error) {
    console.error("Todo update error:", error);
    return NextResponse.json({ error: "Unable to update todo" }, { status: 500 });
  }
}
```

The code is the same — the import line now has `NextRequest`, and below is the `PUT` function. PUT line-by-line:

- **`import { NextRequest, NextResponse }`** — `NextRequest` is the answer to Question 1 — PUT has a body, so we need the request. (Same as 6.7.2's import change.)
- **`PUT(request, context)`** — new function on the same dynamic route. `request` — to read the body (Question 1). `context` — same params pattern (6.7.3).
- **Same start** — connection + `await context.params` (6.7.3 pattern).
- **Body read + destructuring** — same as POST (6.7.2) — `request.json()`, then extract `title` and `done`.
- **`Todo.findByIdAndUpdate(id, { title: title.trim(), done }, { new: true })`** — find by id, `{ title: title.trim(), done }` update the data (Question 2). **`{ new: true }`** — return the updated document (Question 3 — the gotcha!).
- **`if (!updated)` → 404** — wrong id → `null` (Question 4).
- **200 + updated document** — update successful (Question 4). Response has the **updated** todo — new `done`, `updatedAt` timestamp also updates (6.5 schema).
- **`catch` + 500** — same pattern — error gets server-side log + 500.

## Step 2 — UI: Checkbox Toggle

**THINK:** The user needs a **checkbox** — check it → todo done, uncheck → back to pending. Click sends `PUT /api/todos/[id]` with `{ done: !todo.done }` — the **opposite** of what it currently is (a true toggle). The checkbox goes in `TodoItem` — because it knows each todo (6.7.3 built it).

**CONCEPT:** Think of a light switch — flip it and it goes on/off, inverting whatever state it was in. A checkbox works the same — every click needs the **opposite** of `done`. Problem-first:

**Question 1 — how to bind the checkbox value?** `<input type="checkbox" checked={todo.done}>` — `checked` prop gets `todo.done`. Whenever the list refreshes (`loadTodos`), the server's new `done` value is shown — the checkbox is a **mirror of server state**.

**Question 2 — what to send on click?** `PUT` with body `{ done: !todo.done }` — **toggle**. Currently `false`, send `true`; currently `true`, send `false`. And the title? PUT is a full update (6.6) — the title also needs to be sent (future title changes are possible). Body: `{ title: todo.title, done: !todo.done }` — the full todo data, just `done` flipped.

**Question 3 — `onChange` and not `onClick`?** Checkbox change event fires when its value toggles. `onChange={() => onToggle(todo)}` — fires on every check/uncheck. (`onClick` also works on checkboxes but is unpredictable with keyboard, label clicks — `onChange` is the standard.)

**Question 4 — how does PUT route use the id?** Same dynamic route pattern — `[id]` folder (6.7.3) — `context.params` has the id. `TodoApp`'s `toggleDone(id, todo)` puts the id into the fetch URL — `` `/api/todos/${id}` ``.

**Question 5 — how does the list refresh after toggle?** The same pattern — refetch after the fetch — as `addTodo` did in 6.7.2 and `deleteTodo` in 6.7.3. Now it's an established pattern: **after every mutation, refetch from server.** That's exactly why `loadTodos` was made into a separate function in 6.7.1 — it's now reused in three places.

```ts
// app/api/todos/route.ts
import { NextRequest, NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";

export async function GET() {
  try {
    await connectDB();
    const todos = await Todo.find().sort({ createdAt: -1 });
    return NextResponse.json(todos, { status: 200 });
  } catch (error) {
    console.error("Todos fetch error:", error);
    return NextResponse.json({ error: "Unable to fetch todos" }, { status: 500 });
  }
}

export async function POST(request: NextRequest) {
  try {
    await connectDB();

    const body = await request.json();
    const { title } = body;

    if (!title || title.trim() === "") {
      return NextResponse.json({ error: "Title is required" }, { status: 400 });
    }

    const newTodo = await Todo.create({
      title: title.trim(),
      done: false,
    });

    return NextResponse.json(newTodo, { status: 201 });
  } catch (error) {
    console.error("Todo create error:", error);
    return NextResponse.json({ error: "Unable to create todo" }, { status: 500 });
  }
}
```

```ts
import { NextRequest, NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";

export async function DELETE(
  _request: Request,
  context: { params: Promise<{ id: string }> }
) {
  try {
    await connectDB();
    const { id } = await context.params;

    const deleted = await Todo.findByIdAndDelete(id);

    if (!deleted) {
      return NextResponse.json({ error: "Todo not found" }, { status: 404 });
    }

    return NextResponse.json({ message: "Todo deleted" }, { status: 200 });
  } catch (error) {
    console.error("Todo delete error:", error);
    return NextResponse.json({ error: "Unable to delete todo" }, { status: 500 });
  }
}

  request: NextRequest,
  context: { params: Promise<{ id: string }> }
) {

    await connectDB();

    const { title, done } = body;

    const updated = await Todo.findByIdAndUpdate(
      id,
      { title: title.trim(), done },
      { new: true }
    );

    if (!updated) {
      return NextResponse.json({ error: "Todo not found" }, { status: 404 });

    return NextResponse.json(updated, { status: 200 });
```

## Nutshell

PUT route: same `[id]` dynamic route with `PUT(request, context)` — `request.json()` reads `{ title, done }`, `Todo.findByIdAndUpdate(id, { title, done }, { new: true })` — **`{ new: true }` returns the updated document** (without it you get the old one — the most common Mongoose bug), wrong id → 404, success 200 + updated. UI: checkbox `checked={todo.done}` + `onChange={() => onToggle(todo)}` → `TodoApp.toggleDone` → PUT (done flipped) → `loadTodos()`. The full CRUD UI is now running — data persists to database.

## What It Is NOT

- **`{ new: true }` = optional** is wrong. Without it, `findByIdAndUpdate` **returns the old document** — not the updated one. This is the most common bug. To get the new document, `{ new: true }` is required.
- **PUT's body "just the changed part" is wrong** — PUT is a **full update** (6.6). To toggle `done`, the `title` also needs to be in the body (`{ title, done }`) because PUT replaces the entire resource. Partial updates use PATCH — we decided in 6.6 that PUT is enough.
- **Checkbox = "the component's own state" is wrong** — `checked={todo.done}` — it mirrors server data coming from `todos` state. No local `useState`. Change → server → refetch → new server data renders. Stays the same on refresh because the database stored it.
- **`onClick` is standard for checkboxes** is wrong — use `onChange` (fires when the value toggles). `onClick` also works but is unpredictable with keyboard, label clicks.
- **Toggle = "just UI flair" is wrong** — this is a real PUT request to the database. That's why in 6.8 Postman can also test the same route — it's the same API the UI uses.

**In Your Own Words**

1. `Todo.findByIdAndUpdate(id, data, { new: true })` — what does `{ new: true }` do, and what happens without it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `{ new: true }` returns the **updated** document. Without it, Mongoose returns the **old (pre-update)** document — you see old data in the response even though the database changed. The user thinks the update failed. To get the new document, `{ new: true }` is required. This is the most common bug of this method.

</details>

2. The checkbox uses `checked={todo.done}` — why isn't this the component's own state?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because `checked` mirrors server data — whatever `loadTodos()` fetched into `todos` state. The checkbox has no local `useState` of its own. When you check it → PUT → refetch → a new `todo.done` value comes from the server → `checked` updates. So it survives a page refresh (`F5`) — the data is in the database, not in ephemeral state.

</details>

3. `onToggle` receives the full `todo` (not just `id` like `onDelete`) — why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because toggling needs the `todo.done`'s **current value** — to send `done: !todo.done` (the opposite) in the body. With just the id, the current `done` value wouldn't be known. Delete only needed the id — "which to delete" is enough. So `onDelete: (id) => void` and `onToggle: (todo) => void` — each callback gets exactly what it needs.

</details>

4. Why send `title` in the body when only `done` is being toggled?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because PUT is a **full update** (decided in 6.6). If you only send `{ done: true }`, the server might overwrite `title` to undefined (or fail required validation). Toggling `done` means flipping `done`, but `title` stays the same — so both go in the body: `{ title: todo.title, done: !todo.done }`.

</details>

5. Notice that add/delete/toggle — all three call `loadTodos()` afterwards. What does this pattern teach?

<details>
<summary>Show Answer</summary>

**Sample Answer:** After a mutation, **refetch from the server** — the server is the source of truth. Instead of manually updating local state, get fresh data every time. That's exactly why `loadTodos` was made into a separate function in 6.7.1 — it's now reused in three places. The UI always shows what the server actually knows, no mismatches.

</details>
