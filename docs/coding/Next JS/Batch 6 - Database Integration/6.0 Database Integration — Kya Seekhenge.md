Soch — Batch 5 ke end mein humne `profiles.json` file mein user ka bio save kiya tha. Save hone ke baad sab theek lagta tha, par asli duniya mein is file wale approach ki kai problems hain. Kya hota agar do users ek saath apna bio update karein? Kya hota agar profile page pe "sirf whi users jinki bio mein 'developer' hai" dhoondhna ho? Kya hota agar app deploy ho aur server kisi aur machine pe ho — file kahan rahegi? Yeh sab sawaal isliye uthte hain kyunki **file storage ek adhoora solution hai**. Isi adhoorepan ka jawab hai Batch 6 ka core topic — **databases.**

Batch 5 mein humne authentication seekha — server ko batana ki request kiski aa rahi hai. Batch 3 mein mutations seekhe — data banana, update karna, delete karna (Route Handlers + Server Actions). Par dono mein data ka ghar tha **files aur in-memory arrays** — jahan se reboot pe sab ud jaata tha. Ab us data ko ek **permanent, structured, query-able jagah** deni hai — yahi database hai. Aur yahan se tumhara asli **backend** shuru hota hai.

## Do Mini-Projects, Do Alag Data-Flow Patterns

Roadmap ke "Manual → Better" philosophy ke hisaab se — pehle purana tareeka, phir better. Batch 6 mein yeh pattern double hai, kyunki database ek bada topic hai:

**Mini-Project 1 — MongoDB (6.4–6.8):** **REST API pattern.** Yahan data MongoDB mein store hoga, aur app ke API routes (`route.ts`) database se baat karenge — client `fetch()` se. Isi phase mein **API design** (6.6) aur **Postman testing** (6.8) bhi milega, kyunki REST + Postman ek natural pair hain. Batch 3 ka REST pattern (3.1) yahan real database ke saath wapas aata hai.

**Mini-Project 2 — PostgreSQL + Drizzle (6.9–6.12):** **Server Components + Server Actions pattern.** Yahan hum database se **sach mein** directly baat karenge — reads Server Component mein (koi API layer nahi, roadmap ka rule), mutations Server Actions se (Batch 3 ka 3.3 pattern). Isi phase mein **system design** (6.12) — relations aur indexes — kyunki tables ke saath hi relations ka concept natural lagta hai.

> **Ek baat pakki:** Hum REST ko pehle phase mein isliye rakhenge kyunki yeh **fundamental** hai — kisi bhi production app mein, jab tumhari API ko koi aur client use karega (mobile app, third-party), tab REST chahiye. Server Actions sirf app ke apne forms ke liye hai. Batch 3 ka 3.3.5 comparison (Route Handler vs Server Actions — Kab Kya) yahan practice mein aayega.

## Is Batch Mein Kya NAHI Hoga

Scope clear rakhna zaroori hai:

- **Full-fledged DBA/Admin course nahi** — hum database ko app ke saath use karte hain, database ko khud administer nahi karte. Indexing, transactions, aur replication ka deep duniya — halka sa concept level, production ke liye baad mein.
- **Do alag DB systems ka "production comparison" nahi** — hum dono ko use karte hain taaki samajh aaye, par final project (Task Board) SQL + Prisma pe hai kyunki production ke liye wahi recommend hota hai.
- **Database se auth integrate nahi** — Batch 5 ka Auth.js apna kaam karta hai; yahan DB se user model ka real integration is batch ke scope mein nahi hai (aage capstone mein).
- **Hosting/database deployment nahi** — Vercel deploy Batch 8 mein hai. Yahan cloud DB (Atlas/Neon) use hoga, par local development ke liye.
