## Why Two Patterns, Two Data Flows

Batch 6 doubles the "Manual → Better" principle because databases are large territory. We run two mini-projects, each on a different stack, so the contrast is felt, not just told:

**Mini-Project 1 — MongoDB (6.4–6.8): the REST API pattern.** Data lives in MongoDB, and the app's `route.ts` handlers talk directly to it — the frontend calls the API with `fetch()`. This phase also covers API design (6.6) and Postman testing (6.8), because REST and Postman are a natural pair. The Route Handler pattern from Batch 3 returns here, now against a real database.

**Mini-Project 2 — PostgreSQL + Drizzle (6.9–6.12): the native Next.js pattern.** Here the database is read *directly* in Server Components (no API layer — the roadmap's rule) and mutated in Server Actions (the Batch 3 pattern). System design (6.12) lives here too, because relations and foreign keys come naturally with tables.

> One invariant: we learn REST first even though Server Actions exist, because REST is *fundamental* — any external client (mobile app, third party) needs an HTTP API. Server Actions serve only the app's own forms. The Route Handler vs. Server Action trade-off from Batch 3 lands here in practice.

## The Fifth Project — Task Board

The roadmap calls for: *"Task Board — Prisma/Supabase, real CRUD, list straight from the DB in a Server Component, add/edit/delete in Server Actions, no dummy data."* A fresh project — `task-board` — using a real PostgreSQL database (Neon) and a production-grade ORM (Prisma):

1. A real database — PostgreSQL on Neon + Prisma.
2. The list comes straight from the database in a Server Component (no API layer).
3. Add/edit/delete persist through Server Actions.
4. No dummy data left behind — everything lives in the database.

The two mini-projects above explore Mongo (REST) and SQL (Server Components + Actions) with their own data flows. The Task Board combines the production-grade versions of everything into a single five-part series (planning → hardcoded UI → data layer → dynamic → testing), using the same project-writing process from earlier batches.

## Out of Scope

Boundaries keep this batch tight:

- Not a DBA course — the app consumes a database, we don't administer one. Indexes, transactions, replication stay conceptual; production deep-dives come later.
- No "which DB wins in production" verdict — both are used so you feel the difference, but the final project uses SQL + Prisma, matching the production recommendation.
- No database-auth integration this batch — Auth.js from Batch 5 stays as-is; wiring the user model to a real store is the capstone's job.
- No hosting deployment this batch — Vercel deploy is Batch 8. We use cloud databases (Atlas/Neon) for local development and will wire Vercel env vars later.

## Nutshell

Batch 6 introduces **database integration** — moving data from files into a permanent, structured, queryable store. Two mini-projects exercise two data flows: **MongoDB + REST** (API design + Postman) and **PostgreSQL + Drizzle** (Server Components + Server Actions + system design). The batch ends on the **Task Board** — a fresh project, Prisma + Neon, real CRUD, no dummy data. We start with the question the file-store approach can't fully answer: what is a database, and how does it differ from a file?

## What It Is NOT

- A database administration course. We consume databases, not run them.
- A "SQL vs. NoSQL, pick a champion" debate. Both are used; the final project picks SQL by recommendation, not because NoSQL is wrong.
- A claim that databases are only for big apps. Even single-user apps hit concurrency and persistence, which a database handles from day one.
- A magic "no more code" promise. We still write queries — either raw SQL, a query builder, or through an ORM's typed methods.

## In Your Own Words

<details>
<summary>1. Why is a database a meaningful upgrade even if a JSON file is "permanent storage"?</summary>

**Sample Answer:** A file stores bytes, but a database *manages* records — it guarantees atomicity across concurrent writers, executes indexed queries without loading everything into memory, enforces relations and constraints, and survives app redeploys and restarts without per-instance state. The "permanent" property alone doesn't buy you correctness under load or queryability at scale.

</details>

<details>
<summary>2. Between the MongoDB REST mini-project and the PostgreSQL Drizzle mini-project, which pattern is closer to "idiomatic Next.js," and why do we still teach REST first?</summary>

**Sample Answer:** The PostgreSQL + Server Components/Actions pattern is more idiomatic — data is read directly where it's rendered and mutated directly where it's triggered. REST is taught first because it's the universal interface: a mobile client or third-party service can't call your Server Actions, only HTTP. Learning REST also makes the Action pattern a deliberate choice rather than the only path you've seen.

</details>

<details>
<summary>3. The Task Board uses Prisma, but we touched Mongoose and Drizzle first. Is that redundant, or does it pay off?</summary>

**Sample Answer:** Not redundant — each tool teaches a different shape. Mongoose forces you to think in documents with flexible schemas and embedded/manual references. Drizzle teaches SQL tables, strict types, and `pgTable`-first schemas. Prisma then becomes "the production-graded version of everything learned" — its client and generated types click because the underlying SQL concepts were already earned.

</details>

<details>
<summary>4. Why keep the route-handler-based REST pattern in a batch that also teaches Server Actions (the "better" Next.js way)?</summary>

**Sample Answer:** Because "better" is contextual. Server Actions excel within the app's own Server Components. REST/Route Handlers are required whenever the consumer is outside the app — another client, an integration partner, a mobile app. Teaching both means you can pick by constraint, not habit.

</details>

<details>
<summary>5. If the Task Board is the capstone of this batch, what is the pedagogical role of Mongo and SQL mini-projects before it?</summary>

**Sample Answer:** They isolate each decision. Mongo surfaces "how do I model data in documents?" REST surfaces "how do I design an API contract?" SQL + Drizzle surfaces "how do tables and relations map to code?" Without these isolating exercises, the Task Board would be a tangle of first-time mistakes; by then you've already felt each failure mode and can focus on combining the correct pieces.

</details>
