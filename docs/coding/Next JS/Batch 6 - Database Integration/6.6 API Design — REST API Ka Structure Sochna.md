# API Design — Designing REST API Structure

## First — What is an API (Quick Recap)

Batch 3.1 had details — quick recap in one line: **API (Application Programming Interface)** is a middleman — takes a request from browser/app, gets the work done with the database, sends the response back. In Next.js it's built with `app/api/.../route.ts`.

Now the question is — **how do we design this API?** Which endpoints, which methods, what response on a bad request, how does an error look? This is **API design** — and it's a fundamental skill that works on any framework.

## REST — The Standard for API Design

**REST (Representational State Transfer)** is an API design style — today almost all web APIs are built on it. Its core idea is simple: **represent your data resources (like "todos") with URLs, and perform operations on them with HTTP methods (GET/POST/PUT/DELETE).**

REST has two basic rules:

1. **Identify a resource with URL** — `/api/todos` = todos collection, `/api/todos/123` = one specific todo
2. **Perform operation with HTTP method** — GET = read, POST = create, PUT = update, DELETE = remove

That's the whole API design — which URL, which method, what response.

## Resources — How to Design URLs

First question: **what resources do we have and what are their URLs?**

In a Todo app there's one resource — `todos`. URL design:

| URL | What it represents |
|---|---|
| `/api/todos` | All todos (collection) |
| `/api/todos/123` | A specific todo (single resource) |

URL naming rules:

- **Use plural nouns** — `/api/todos`, `/api/users`, `/api/products`. Not `/api/todo` — plural is natural for collections.
- **Lowercase + hyphens** — `/api/todo-items`. No camelCase (`todoItems`) or snake_case (`todo_items`) — convention is lowercase-hyphen.
- **Nested resources for relations** — `/api/users/1/todos` = todos of user 1. Remember the pattern `/api/comments/[id]` from Batch 3 — that's what expands here.
- **No verbs in URL** — `/api/getTodos` is wrong. The method (GET) already tells what to do. URL only indicates the resource.

## HTTP Methods — Mapping Operations

Now which operations on resources? Map CRUD to methods:

| Operation | Method | URL | What happens |
|---|---|---|---|
| View all todos | **GET** | `/api/todos` | Returns list |
| View one todo | **GET** | `/api/todos/123` | Returns single |
| Create new todo | **POST** | `/api/todos` | Data comes in body, creates new |
| Update todo | **PUT** | `/api/todos/123` | Replaces entirely |
| Partially update | **PATCH** | `/api/todos/123` | Updates only given fields |
| Delete todo | **DELETE** | `/api/todos/123` | Removes it |

In **Batch 3 we did GET/POST/DELETE** — here I'll also clarify the difference between PUT/PATCH:

- **PUT** — **replaces the entire** resource. Send the complete todo in body — title too, done too. Fields not in body might get reset.
- **PATCH** — **partially updates** the resource. Send just `done: true` — title stays as is, only done changes.

Practically PUT is stricter, PATCH is flexible. In this batch's project we'll use **PUT** (simpler — a Todo has only 2 fields, partial update isn't needed), but knowing both is important.

**Another scenario — custom action.** So far all methods are CRUD (create/read/update/delete). What if the server needs to do something that doesn't fit CRUD? Think — "archive it" or "clone it". POST's real meaning isn't "create", it's **"let the server do some action"** — it's the open-ended method in REST. Custom actions have routes like: `POST /api/todos/123/archive`. We don't have custom actions in the Todo project — but real apps have these "actions" all the time, so this pattern is important to know. (We'll use Server Actions in 6.13 Task Board — those are also "actions", but from a client-side form, not REST route.)

## Status Codes — How a Request Says "Yes/No"

Every API response comes with an **HTTP status code** — a three-digit number that says what happened to the request. In Batch 3.1 we saw 200/201/404 — here's the full set:

| Code | Meaning | When |
|---|---|---|
| **200** | OK | GET successful |
| **201** | Created | POST — new resource created |
| **204** | No Content | DELETE successful (nothing to return) |
| **400** | Bad Request | Client sent bad data (required field missing) |
| **404** | Not Found | Resource not found (wrong id) |
| **500** | Internal Server Error | Something went wrong on server |

**Rules that make design professional:**

- **200 vs 201** — GET successful = 200, POST successful = 201. Small difference but it's standard.
- **404 vs 400** — wrong id (`/api/todos/abc`) = **404** (resource doesn't exist). Wrong body (no title) = **400** (client's mistake). Two different problems, two different codes.
- **DELETE successful = 204 standard, but in our project we use 200 + message.** 204 = No Content — "deleted, nothing to return". But in Todo project we'll use **200 + message** (`{ "message": "Todo deleted" }`) — simple, and that's the code in 6.7.3. Knowing the standard is important, but decisions can be project-specific — both are correct as long as consistent.
- **List API never returns 404.** `GET /api/todos` with no data — don't return 404 — empty list means "no data", not "resource not found". Return `[]` + 200. 404 only when client asks for a **specific** resource that doesn't exist (`/api/todos/abc`). You already did this in the GET list in 6.7.1 — now it's an explicit rule.
- **500 only for server's fault** — if it's the client's fault return 400/404, not 500. 500 means "unexpected error on server" — gives no information to client.

## Error Response — Keep the Shape Standard

When an error occurs, status code alone is not enough — **response body should also have a message** telling the client what went wrong. Keep one consistent shape across the whole API:

```json
{ "error": "Todo title is required" }
```

Simple, but **consistency** is key — every error response in this same shape. This way client (you in Postman) can handle every error the same way. In Batch 3 we saw `NextResponse.json({ error: "..." }, { status: 400 })` — same pattern.

**Success response shape?** GET returns list or object directly as JSON. POST returns the newly created resource — so client can use it immediately.

**Sane defaults — don't depend on client.** In 6.5 we set schema default `done: false` — same thinking applies at API level. If client sends no optional field, let the server assume a sensible default (like `page=1`, `limit=10`) — don't throw errors. This makes the API easier to use. Real list APIs have this pattern for pagination — not needed in Todo project now, but the concept connects with 6.5.

## Idempotency — The Real Difference Between PUT and POST

Another concept that matters in design — **idempotency.** And here's a common confusion that you too might have had — idempotent doesn't mean **"same response every time."**

> **Nutshell:** An idempotent operation is one that you can call any number of times and **the system's final state remains the same.** The response may differ — idempotency is measured by the side effect (state), not the response.

- **GET** is idempotent — call 100 times, data is the same.
- **PUT** is idempotent — calling twice with same data = same replacement = same state.
- **DELETE** — here's where confusion arises, let's think it through. `DELETE /api/todos/123` called twice:
  - **First time** — todo found, deleted → `200` (you could return the deleted object too).
  - **Second time** — todo no longer exists → `404` error.
  - Responses are different (200 vs 404) — **but the system state is the same**: both times after, "todo doesn't exist". First time state **changed** (existed → gone), second time no new change (already gone). **Same side effect = idempotent.**
  - So 404 appearing is proof of idempotency, not a violation — 404 just means "nothing more to delete, state already as expected".
- **POST** is not idempotent — two calls = two new todos. Each call creates a new resource, state changes each time.

From this comes a design rule: **use POST for creating new resources, use PUT for replacing.** Because POST means "create new", PUT means "change this specific thing."

## REST API Design — Nutshell

In REST, represent resources with URLs, operate with HTTP methods. Core design decisions: plural-noun URLs, CRUD → method mapping, proper status codes (200/201/204/400/404/500), consistent error shape (`{ error }`), and idempotency awareness (POST = new, PUT/DELETE = specific). All of this will be applied to the Mongo Todo API in 6.7.1 to 6.7.4.

## What It Is NOT

- **API design ≠ just writing URLs.** URL design is one part of it — real design is a consistent system of methods, status codes, error shapes, and response structure.
- **REST ≠ just some "Coursera standard".** REST is the de facto standard for today's web APIs — every backend framework uses it. This is a universal skill.
- **Exact status codes = "just to follow rules".** Using standard codes lets clients (and frameworks) use built-in behavior — 404 automatically means "resource not found" to clients.
- **Using all of PUT/PATCH/GET/POST everywhere = required.** Use what the project needs. In Todo, POST (create), GET (read), DELETE (delete) is basic — PUT for update. Using all methods everywhere is not a design requirement.
- **Idempotent = "same 200 response every time" isn't true.** Idempotent means the system state stays the same — delete twice: first time 200, second time 404, but state is same both times ("todo doesn't exist"). Response differing doesn't break idempotency — you look at side effects, not responses.
- **API design = substitute for writing code.** Design is the "what will be" thinking. Code comes in 6.7.1 to 6.7.4, following this design.
