# API Design — REST API Ka Structure Sochna

## Pehle — API Kya Hai (Quick Recap)

Batch 3.1 mein detail thi — ek line recap: **API (Application Programming Interface)** ek middleman hai — browser/app ki request leta hai, database se kaam karwata hai, response wapas bhejta hai. Next.js mein `app/api/.../route.ts` se banta hai.

Ab sawaal yeh hai — **yeh API kaise design karein?** Kaunse endpoints banayein, kaunse methods, galat request pe kya response, error kaisa dikhe? Yahi **API design** hai — aur yeh bilkul fundamental skill hai jo kisi bhi framework pe kaam aati hai.

## REST — API Design Ka Standard

**REST (Representational State Transfer)** ek API design style hai — aaj ke almost sab web APIs isi pe banti hain. Iska core idea simple hai: **tumhare data ke resources (jaise "todos") ko URLs se represent karo, aur HTTP methods (GET/POST/PUT/DELETE) se unpe operations karo.**

REST ke do basic rules:

1. **Resource ko URL se identify karo** — `/api/todos` = todos collection, `/api/todos/123` = ek specific todo
2. **Operation ko HTTP method se batayo** — GET = padho, POST = banao, PUT = badlo, DELETE = hatao

Yehi soch poora API design hai — kaunsa URL, kaunsa method, kya response.

## Resources — URLs Kaise Design Karein

Sabse pehla sawaal: **API mein kaunse resources hain aur unke URLs kya honge?**

Todo app mein ek hi resource hai — `todos`. URL design:

| URL | Kya represent karta hai |
|---|---|
| `/api/todos` | Saare todos (collection) |
| `/api/todos/123` | Ek specific todo (single resource) |

URL naming ke rules:

- **Plural nouns use karo** — `/api/todos`, `/api/users`, `/api/products`. `/api/todo` nahi — collection ke liye plural natural hai.
- **LowerCase + hyphens** — `/api/todo-items`. CamelCase (`todoItems`) ya snake_case (`todo_items`) URL mein nahi — convention lowercase hyphen hai.
- **Nested resources relation ke liye** — `/api/users/1/todos` = user 1 ke todos. Batch 3 mein `/api/comments/[id]` ka pattern yaad hai — wahi yahan expand hota hai.
- **Verb URL mein nahi** — `/api/getTodos` galat hai. Method (GET) hi batata hai ki kya karna hai. URL sirf resource batata hai.

## HTTP Methods — Operations Ka Mapping

Ab resources pe kaunse operations? CRUD ko methods se map karo:

| Operation | Method | URL | Kya hota hai |
|---|---|---|---|
| Saare todos dekho | **GET** | `/api/todos` | List return |
| Ek todo dekho | **GET** | `/api/todos/123` | Single return |
| Naya todo banao | **POST** | `/api/todos` | Data body se, naya banata hai |
| Todo update karo | **PUT** | `/api/todos/123` | Poora replace karta hai |
| Todo partially update | **PATCH** | `/api/todos/123` | Sirf diye fields badalta hai |
| Todo delete karo | **DELETE** | `/api/todos/123` | Hata deta hai |

**Batch 3 mein GET/POST/DELETE kiya tha** — yahan PUT/PATCH ka fark bhi clear karta hoon:

- **PUT** — resource ko **poora replace** karta hai. `PUT /api/todos/123` mein body mein poora todo bhejo — title bhi, done bhi. Jo fields body mein nahi, woh reset ho sakte hain.
- **PATCH** — resource ko **partially update** karta hai. Sirf `done: true` bhejo — title chhota rahega, sirf done badlega.

Practically PUT zyada strict hai, PATCH flexible. Batch 6 ke project mein hum **PUT** use karenge (simpler — Todo mein sirf 2 fields hain, partial ki zaroorat nahi), par dono ka fark jaanna zaroori hai.

## Status Codes — Response Ka "Haan/Nahi" Batana

Har API response ke saath ek **HTTP status code** aata hai — teen-digit number jo batata hai request ka result kya hua. Batch 3.1 mein 200/201/404 dekhe the — ab poora set:

| Code | Matlab | Kab |
|---|---|---|
| **200** | OK | GET successful |
| **201** | Created | POST — naya resource ban gaya |
| **204** | No Content | DELETE successful (kuch return nahi) |
| **400** | Bad Request | Client ne galat data bheja (required field missing) |
| **404** | Not Found | Resource nahi mila (galat id) |
| **500** | Internal Server Error | Server pe kuch galat hua |

**Rules jo design ko professional banate hain:**

- **200 vs 201** — GET successful = 200, POST successful = 201. Chhota fark hai par standard hai.
- **404 vs 400** — galat id (`/api/todos/abc`) = **404** (resource exist nahi karta). Galat body (bina title) = **400** (client ki galti). Dono alag problems hain, alag codes.
- **500 sirf server ki galti pe** — agar client ki galti hai toh 400/404 do, 500 nahi. 500 ka matlab "server pe unexpected error" hai — client ke liye koi information nahi hota.

## Error Response — Shape Standard Rakhna

Jab error aaye, sirf status code kaafi nahi — **response body mein message bhi hona chahiye** jo client ko bataye kya galat hua. Ek consistent shape rakho — poore API mein same:

```json
{ "error": "Todo title required hai" }
```

Simple hai, par **consistent** hona zaroori hai — har error response isi shape mein. Isse client (ya Postman mein tum khud) har error ko same tarah handle kar sakte ho. Batch 3 mein `NextResponse.json({ error: "..." }, { status: 400 })` ka pattern yaad hai — wahi.

**Success response ka shape?** GET pe list ya object seedha JSON mein. POST pe naya bana hua resource — taaki client turant use kar sake.

## Idempotency — PUT vs POST Ka Asli Fark

Ek aur concept jo design mein farak daalta hai — **idempotency.**

> **Nutshell:** Idempotent operation woh hai jise kitni bhi baar call karo, result same hota hai — pehli baar ka jaisa, 5vi baar ka bhi waisa.

- **GET** idempotent hai — 100 baar GET karo, data same.
- **PUT/DELETE** idempotent hain — `DELETE /api/todos/123` do baar call karo: pehli baar todo gaya, doosri baar 404 (wahi resource ab exist nahi karta). Side effect same "todo exist nahi karta" state.
- **POST** idempotent nahi hai — 2 baar POST = 2 naye todos. Har call naya resource banata hai.

Isi se design ka rule nikalta hai: **naya resource banane ke liye POST, replace karne ke liye PUT** — kyunki POST ka matlab "naya banao", PUT ka "yeh specific ek ko badlo."

## REST API Design — Nutshell

REST mein resources ko URLs se represent karte ho, operations HTTP methods se. Design ke core decisions: plural nouns ke URLs, CRUD → methods ka mapping, sahi status codes (200/201/204/400/404/500), consistent error shape (`{ error }`), aur idempotency ka dhyan (POST = naya, PUT/DELETE = specific). Yahi sab 6.7 mein Mongo Todo API pe apply hoga.

## What It Is NOT

- **API design ≠ sirf URL likhna.** URL design ka ek hissa hai — asli design methods, status codes, error shapes, aur response structure ka consistent system hai.
- **REST ≠ sirf ek standard "coursera wala".** REST aaj ke web APIs ka de facto standard hai — har backend framework use karta hai. Yehi universal skill hai.
- **200/201/404 exact codes = "marke nahi dena."** Standard codes use karne se clients (aur frameworks) built-in behavior de sakte hain — 404 automatically "resource nahi" samajhta hai.
- **PUT/PATCH/GET/POST ko "sab use karna zaroori hai" nahi.** Jo project ko chahiye wahi use karo. Todo mein POST (create), GET (read), DELETE (delete) basic hai — PUT update ke liye. Saare methods har jagah use karna design requirement nahi hai.
- **API design = code likhne ka substitute nahi.** Design soch hai — "kya-banega" wali. Code 6.7 mein likhenge, design ke hisaab se.
