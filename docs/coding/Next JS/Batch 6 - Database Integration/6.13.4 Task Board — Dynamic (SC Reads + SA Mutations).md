# Task Board — Part 4: Dynamic (Server Components + Server Actions)

## Where We Left Off

In 6.13.2, the UI was built with hardcoded data — `board/[id]/page.tsx` had `const tasks = [...]` and `/page.tsx` had `const boards = [...]`. In 6.13.3 Prisma was set up — schema defined, migrated, client singleton ready. Now those two things connect: the hardcoded arrays in the page become live database queries. The UI code stays nearly identical — only where the data comes from changes.

## Step 1 — Replace Hardcoded Queries with Server Component Reads

In 6.13.2, `app/page.tsx` had a static `boards` array. The **exact same UI** works if that array comes from the database instead. The page is a Server Component by default, so the database query happens directly — no API route, no fetch (6.11.1 pattern — SC direct database read).

**Before (hardcoded):**

```tsx
const boards = [
  { id: 1, name: "Website Launch" },
  { id: 2, name: "Learning Plans" },
];
```

**After (database):**

```tsx
const boards = await prisma.board.findMany({
  orderBy: { createdAt: 'desc' },
});
```

**`prisma.board.findMany()`** — returns all boards (SC — server side, data ready before client gets the page). **`orderBy`** — default newest first. The `await` keyword works because the page is an async Server Component (Next.js 15 default — the page function can be async).

**What changes:** just the data source. `{ boards.map(...) }` — same code — now each `board.name` comes from `Board.name` (schema string), `board.id` matches `Int id @id`.

## Step 2 — Dynamic Board Page

In `board/[id]/page.tsx`, two things change:

### 6.13.3 (Part 3) — Schema

First, the Prisma schema for Task Board had three models: User, Board, and Task. The Task model defined task id, title, description, status (enum TaskStatus BACKLOG/IN_PROGRESS/DONE), order within column, and boardId as foreign key referencing Board. Board had its own id, name, createdAt with @default(now()), and userId foreign key. Relations were set up one-to-many: User→Board via boards array, Board→Task via tasks array, each with @relation specifying fields and references.

### Step 2 — Board Page (Single Page, Two Responsibilities)

Page 2: board detail — /board/[id]. In the planning phase (6.13.1), this page showed columns (Backlog, In Progress, Done) and tasks grouped by column. The dynamic data version of this page (6.13.4) has two jobs — read all tasks for this board (server component), and handle mutations to move a task between columns or delete a task.

For mutations, this is a dynamic route page — boardId comes from the URL via await params then passed to server actions as a hidden input. Moving a task between columns uses a server action called moveTask that takes taskId, newStatus, and boardId — it updates the status and revalidates the board page path so the UI refreshes without a manual reload. Deleting a task uses another server action with just taskId and boardId.

The server actions themselves live in a separate file — app/board/[id]/actions.ts — exported from there as plain functions that take FormData. The key difference from REST routes: there is no request response cycle, no JSON serialization needed, no fetching from the client — the action runs the mutation directly and returns.

The board page is async, so it waits for params with const { id } = await params, then fetches tasks filtered by boardId. Tasks are grouped by column in a helper function, and each group is sorted by order — both the filter and sort happen server side in the Server Component. Each mutation form includes a hidden input with the boardId value, using the boardId from params that was fetched earlier.

### Step 2 — Board Page Read + Dynamic Route Params

Page 2: board detail (`/board/[id]`). In 6.13.1 planning, this page showed columns + tasks — grouped by `status`, sorted by `order`. The dynamic version reads the board id from the route params:

```tsx
// app/board/[id]/page.tsx
const { id } = await params;
```

**`await params`** — dynamic route (6.7.3 pattern) — `id` is now a real string from the URL (was placeholder before).

Fetch the board + its tasks (relation — 6.12 single query, no N+1):

```tsx
const board = await prisma.board.findUnique({
  where: { id: Number(id) },
  include: { tasks: true },
});
```

**`prisma.board.findUnique({ where: { id: ... }, include: { tasks: true } })`** — finds one board by id, `include` brings the tasks in the same query (JOIN internally — 6.12's N+1 solution). The result is `board.name` (heading) + `board.tasks` (array).

> **Type note:** `include: { tasks: true }` — Prisma auto-types the result — `board` is `Board & { tasks: Task[] }` — so `board.tasks` is typed automatically. If `board` is null (invalid id), must handle it.

## Step 3 — Server Actions (Replacing the Form Placeholders)

Recall the hardcoded UI from 6.13.2 had forms with no action yet — home page had a "Create Board" form (`name="name"`), board page had "Add" form (`name="title"`) + Move/Delete buttons (`type="button"`). Those placeholders now get server actions.

**Server Actions in files** — convention for the batch was `app/board/[id]/actions.ts` (or `lib/actions.ts`) — functions exported and imported directly into the page.

### Create Board (home page)

```tsx
// app/actions.ts
'use server'

import { prisma } from '@/lib/prisma'

export async function createBoard(formData: FormData) {
  const name = formData.get('name') as string
  await prisma.board.create({
    data: { name, userId: 1 }, // User 1 — see note below
  })
}
```

**`'use server'`** — marks this as a server action (not run on client). **`formData.get('name')`** — input name from 6.13.2 planning. **`prisma.board.create`** — mutation (6.3 Prisma pattern). 

> Hardcoded `userId: 1` here — this batch has no auth (6.13.1 note: User model exists for relations, auth is forward-thinking). In a real app, `auth().user.id` would go here. The data shape (relation) is ready — auth plugs in where `1` is.

Connect to home page form:

```tsx
<form action={createBoard}>
  <input name="name" placeholder="New board..." />
  <button type="submit">Create Board</button>
</form>
```

**`action={createBoard}`** — form's action attribute = the server action function (not a string URL). On submit, the action runs, then add revalidate (below).

### Create Task + Move + Delete — Board Page

In `app/board/[id]/actions.ts`:

```tsx
// app/board/[id]/actions.ts
'use server'
import { prisma } from '@/lib/prisma'
import { revalidatePath } from 'next/cache'

export async function createTask(boardId: number, formData: FormData) {
  const title = formData.get('title') as string
  const maxOrder = await prisma.task.count({
    where: { boardId, status: 'BACKLOG' },
  })
  await prisma.task.create({
    data: {
      title,
      boardId,
      status: 'BACKLOG',
      order: maxOrder + 1,
    },
  })
  revalidatePath(`/board/${boardId}`)
}

export async function moveTask(taskId: number, boardId: number, newStatus: string) {
  await prisma.task.update({
    where: { id: taskId, boardId },
    data: { status: newStatus as any },
  })
  revalidatePath(`/board/${boardId}`)
}

export async function deleteTask(taskId: number, boardId: number) {
  await prisma.task.delete({
    where: { id: taskId, boardId },
  })
  revalidatePath(`/board/${boardId}`)
}
```

**`createTask`** — `formData.get('title')` (6.13.2 name attr), `order` from count + 1 (6.12 design — `order` field's purpose — new task at end of column). `revalidatePath` — refreshes only this path.

**`moveTask`** — update `status` (column change). `newStatus as any` — string input to enum (validation note below).

**`deleteTask`** — `prisma.task.delete`.

### Connecting Actions to the UI — Hidden Inputs for Route Params

The board page has dynamic `[id]` in the URL. Actions need `boardId` — how do they get it? The page knows `boardId` (from `await params`). Pass it via **hidden form input**:

```tsx
{/* create task form */}
<form action={createTask}>
  <input type="hidden" name="boardId" value={Number(id)} />
  <input name="title" placeholder="New task..." />
  <button type="submit">Add</button>
</form>
```

**`type="hidden" name="boardId"`** — passes `id` through the form. Server action reads `formData.get('boardId') as number` (or parse with `Number()`). This is the pattern 6.13.2 planned — `id` value passed through form.

For delete/move buttons — each needs `taskId` + `boardId`:

```tsx
<button
  formAction={deleteTask}
>
  <input type="hidden" name="taskId" value={task.id} />
  <input type="hidden" name="boardId" value={Number(id)} />
  Delete
</button>
```

**`formAction`** on a `<button>` — same as `action` on `<form>` — the button's action when clicked. Hidden inputs inside pass `taskId` + `boardId`. No client-side fetch — direct server action.

## Step 4 — Data Flow Summary (The Big Loop)

This is the full data cycle — the pattern that matters. **Write it out.**

```
[User clicks "Move"]
     │
     ▼
<form action={moveTask}> (formAction on button)
     │  hidden inputs → taskId, boardId, newStatus as FormData
     ▼
Server runs moveTask(formData):
  ├─ formData.get("taskId"), formData.get("boardId"), etc.
  ├─ prisma.task.update(...) → PostgreSQL (Neon)
  └─ revalidatePath(`/board/${boardId}`)
     │
     ▼
Next caches invalidated → page re-fetches on next visit:
  └─ prisma.board.findUnique({ include: { tasks } })
     │
     ▼
[UI re-renders with new order] — automatic, no client fetch
```

**Key points:**

1. **FormData** — the bridge between forms and server actions (not JSON, not fetch — `FormData`).
2. **`revalidatePath`** — tells Next "this path's cached data is stale" — forces fresh fetch on the SC, which re-renders (not the action — the page re-renders). Without it, the page shows stale data even after mutation.
3. **SC + SA combo** — Server Components read (on server, before client), Server Actions mutate (on server, after event). No client-side fetch in between — the framework handles refetch.

> This is the **production pattern** — no separate API layer (`pages/api/todos` from REST phase), data flows through the framework. Compare to 6.7.x (Mongo REST) — that needed fetch + useState + refetch. Here, zero client state.

## Step 5 — Handling Edge Cases

### 404 / Not Found (invalid board id)

If `board` is null (no board with that id):

```tsx
if (!board) {
  notFound()  // from next/navigation
}
```

**`notFound()`** — shows the 404 page. (6.13.5 deep-dive.) The `board` null check is needed — `findUnique` returns `Board | null`.

### Input Validation / Enum Safety

`newStatus as any` — risky (string → enum). Better: use the `TaskStatus` type from Prisma:

```ts
import { TaskStatus } from '@prisma/client'

export async function moveTask(taskId: number, boardId: number, newStatus: TaskStatus) {
  await prisma.task.update({
    where: { id: taskId, boardId },
    data: { status: newStatus },
  })
  revalidatePath(`/board/${boardId}`)
}
```

**`TaskStatus`** — imported type from Prisma — validates the enum. In the UI, the select's value is the enum string (`BACKLOG`/`IN_PROGRESS`/`DONE`) — matches.

## Nutshell

Dynamic phase: hardcoded arrays replaced with `prisma.findMany` (home page) and `prisma.board.findUnique` with `include: { tasks: true }` (board page — JOIN in one query, no N+1). Forms get `action={serverAction}` with `<input type="hidden" name="boardId">` to pass route params through FormData. Three server actions created: `createBoard` (home), `createTask`/`moveTask`/`deleteTask` (`board/[id]/actions.ts`). After each mutation → `revalidatePath` → page re-renders automatically. Full cycle: click → form action → server mutates DB → revalidate → page re-fetches → UI updates. Same SC+SA pattern from 6.11, now Prisma queries.

## What It Is NOT

- **`revalidatePath` = "manual refetch"** is not true. It **marks the cache stale** — the *next visit* to that path re-fetches and re-renders. It's not a client-side fetch — no `useEffect`, no `useState`. The framework handles it on the Server Component.
- **Server Actions = "same as REST handlers"** is not true. REST (6.7.x) = URL + JSON + client fetch. Server Actions = function called directly by the form — no URL, no JSON parsing, the framework serializes FormData → function args.
- **Hidden inputs = "hack"** is not true. This is the **documented pattern** for passing non-form data (route params) to server actions. The page knows `id` (from params) — it passes it through a hidden input so the action receives it.
- **`as any` for enum = "acceptable"** is not true. It silences the type checker but bypasses safety — `TaskStatus` from `@prisma/client` should be imported and used as the action's typed argument. Type safety is one of Prisma's strengths — don't throw it away.

1. What's the difference between a Server Component data fetch and a REST API call from 6.7.x?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In the Mongo REST phase (6.7.x), data was fetched over HTTP — a route handler (`route.ts`) queried Mongo, the client used `fetch("/api/todos")` + `useState`/`useEffect`, re-fetching after every mutation + manual cache update. Here in Task Board, the Server Component calls `prisma.findMany()` directly on the server — the data is ready in the HTML before the client loads. No fetch URL, no client-side state, no manual refetch. Server Actions + `revalidatePath` complete the loop — after a mutation, only the stale path re-renders; there's no client fetch to manage.

</details>

2. Why are `hidden` inputs needed on the dynamic route forms (`<input type="hidden" name="boardId">`)?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Server actions receive data via FormData — they don't have access to the URL params directly (they're just functions called by the form). The page knows `boardId` (from `await params`), so it passes it through a hidden input — the action reads `formData.get("boardId")`. This closes the loop: `params` → hidden input → action argument. No client JS needed.

</details>

3. What does `include: { tasks: true }` do in the `prisma.board.findUnique` call, and why is this better than querying tasks separately?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `include` tells Prisma to bring the related `tasks` in the same query — internally a JOIN. Better than a separate `prisma.task.findMany({ where: { boardId }})` because... 6.12's N+1: querying the board (1 query) then looping to fetch each board's tasks (N queries) = N+1 round-trips. With `include`, it's always 1 query regardless of how many tasks. It also auto-types the result — `board.tasks` is typed as `Task[]`.

</details>

4. What happens after `revalidatePath('/board/1')` is called? Trace the full update cycle.

<details>
<summary>Show Answer</summary>

**Sample Answer:** `revalidatePath` marks the cached data for `/board/1` as stale — it does NOT refetch immediately. On the next request/visit — the Server Component (`prisma.board.findUnique`) runs again with fresh data, the HTML is regenerated with the new task order, and the browser receives the updated render. No client-side refetch, no `useState` — Next's incremental cache handles it. Stale data is gone on the next load, automatically.

</details>

5. The schema has a `User` model and `userId` on `Board`, but the page action hardcodes `userId: 1` — does this violate the relation design?

<details>
<summary>Show Answer</summary>

**Sample Answer:** No — it doesn't violate the design. The **schema relation is intact** (`Board.userId` → `User.id`). The `1` is just a **placeholder value for now** because this batch has no auth (6.13.1 explicitly noted: User model exists for relations, auth is forward-thinking design). The relation is structurally ready — when auth is added, `userId: 1` becomes `userId: auth().user.id`. The schema doesn't change — just the value source. This is why the plan kept User in the schema even with only one user.
