## Nutshell

Dynamic: Home pe `prisma.board.findMany()`, Board page pe `prisma.board.findUnique({ where, include: { tasks: true } })` (relation data — N+1 se bacha, 6.12). `await params` se id (6.7.3 pattern), `Number(id)` convert. Actions: `prisma.board.create/task.create/update/delete` + `revalidatePath`. Prisma query style object-based — Drizzle chain-based. UI code 6.13.2 wala — sirf data source badla.

## What It Is NOT

- **`findUnique` vs `findMany` = same nahi.** `findMany()` saare records (SELECT *). `findUnique` ek record id/unique field se (SELECT ... WHERE id). Board page ek board chahiye — isliye `findUnique`.
- **`include: { tasks: true }` = "dusri query" nahi.** Yeh ek hi Prisma query hai jo relations internal JOIN karke laata hai — N+1 se bachta hai (6.12). Bina include ke `board.tasks` empty/error — tasks board ke saath nahi aate.
- **`where` update/delete mein = optional nahi.** `prisma.task.update({ where: { id }, data })` — bina where saari rows update. Prisma enforce karta hai (`where` required) — SQL ka rule, ORM style.
- **`.returning()` abhi chahiye = nahi.** Drizzle mein insert ke baad row wapas lene ke liye `.returning()` lagana padta tha. Prisma `create()` hamesha naya record return karta hai — internally handle — tumhe sochna nahi padta.
- **`user_id: 1` = "auth ka replacement" nahi.** Abhi single user hai isliye hardcoded. 6.13.3 ka design aisa ki auth aane pe yahan real user id aayegi. Forward-thinking — yahi 6.12 ki relation design ki value.

**In Your Own Words**

1. `findUnique({ where: { id }, include: { tasks: true } })` — `where` aur `include` alag kya karte hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `where` filter karta hai — kaunsa board (`WHERE id = ...`), ek record. `include` relation data laata hai — board ke saath uske tasks bhi (internal JOIN). `where` = kaunsa, `include` = aur kya saath mein. Board page pe ek board + uske tasks — dono ek query mein.

</details>

2. `await params` aur `Number(id)` — dono kyun zaroori hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `await params` — Next.js 15+ mein params async hai (Promise) — bina await ke id nahi milegi (6.7.3 wala pattern). `Number(id)` — params se id string aati hai (`"3"`), Prisma ka `id` Int column hai — `where: { id: Number(id) }` type-safe. String bhejo toh type error/query fail.

</details>

3. Prisma `task.create()` ko `.returning()` kyun nahi chahiye — Drizzle mein kyun lagana padta tha?

<details>
<summary>Show Answer</summary>

**Sample Answer:** PostgreSQL INSERT ke baad row automatically wapas nahi deta — isliye Drizzle mein `.returning()` force karna padta tha. Prisma ne yeh complexity internally handle ki hai — `create()` hamesha naya created record return karta hai automatically. ORM layer ne SQL detail chhupayi.

</details>

4. "UI ka code nahi badla, sirf data source badla" — 6.13.2 vs 6.13.4 mein iska kya matlab hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** 6.13.2 mein UI `const boards = [...]` (hardcoded) se render hota tha. 6.13.4 mein wahi JSX, wahi map/filter/sort — par data `await prisma.board.findMany()` se aata hai. UI ka structure wahi — bas data ki source badli. Yahi data layer abstraction ka fayda — pages ko pata nahi data kahan se aata hai, isliye source change pe UI nahi badla.

</details>

5. Task Board mein N+1 problem se kaise bache — `include` kya guarantee karta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Bina include ke board page pe har column ke liye alag query chalti (ya `board.tasks` ki N queries) — N+1, slow. `include: { tasks: true }` Prisma ko ek hi query mein board + saare tasks laane ko bolta hai (internal JOIN) — ek round-trip, N+1 nahi. 6.12 ka JOIN pattern — ORM `include` wahi karta hai.

</details>
