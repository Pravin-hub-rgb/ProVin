## Step 2 — Read: Fetch in a Server Component

**THINK:** The Todo app's home page = show a list. **In the Mongo phase** we built `/api/todos` route, frontend `fetch()`ed it, client component state held the data. **What's different here?** Server Components can fetch data on the server — **directly from the database** — no API layer needed. Make `app/page.tsx` `async`, put `db.select()` in it, and render the data directly.

**CONCEPT:** Server Component (learned in Batch 1) = renders on the server. The database is also on the server. So the page can run a query straight against the database — one request, no client round-trip.

The first question: **why doesn't the page need an `/api/todos` URL?** Because fetch was a client-side problem — the client is on a different machine, so a network call was needed to reach the server. Here, the page that renders is already on the server, the database is also on the server — both in the same place. There's no network path, so the page can just run the query. Make `app/page.tsx` `async`, put `db.select()` in it, and render the data directly.

**File:** `app/page.tsx` — creating it now, one line at a time, so the reason for each line is clear.

First, the imports — `db` (the 6.10 Drizzle client, ready to export), `todos` (6.10's schema export, a TypeScript variable — the database table is actually named `drizzle_todos`, accessed in TypeScript as `todos` — one table, two names), and `desc` (ordering helper, from `drizzle-orm`):

```tsx
// app/page.tsx
import { db } from "@/db";
import { todos } from "@/db/schema";
import { desc } from "drizzle-orm";
```

**`db` import** — the 6.10 Drizzle client, ready to export. With Mongo (6.4), we awaited `connectDB()` for the connection; here the client is serverless-ready — no need to wait for a connection. **`todos` import** — 6.10's schema export, a TypeScript variable. **`desc` import** — ordering helper, from `drizzle-orm`.

Now make the page `async` and run the query. **A query is a chain — methods of `db`, one after another:** `db.select()` starts the query (what we want — all columns). `.from(todos)` — which table (argument is the table, 6.10's `todos`). `.orderBy(desc(todos.id))` — how to order (argument is the `desc()` function that takes a column, id descending). The whole chain becomes SQL `SELECT * FROM drizzle_todos ORDER BY id DESC` — Drizzle builds this itself, you don't write raw SQL:

```tsx
// app/page.tsx
import { db } from "@/db";
import { todos } from "@/db/schema";
import { desc } from "drizzle-orm";

export default async function Home() {                        // NEW
  const allTodos = await db.select().from(todos).orderBy(desc(todos.id));   // NEW
```

**`async` Server Component** — the page can be async because it renders on the server, and `await db` requires this. Compared to 6.4-6.5's `connectDB` await — there we awaited the connection, here `db` is ready directly, we only await the query. **Query chain** — `db.select()` (what we want), `.from(todos)` (which table — `todos` is the argument), `.orderBy(desc(todos.id))` (how to order — `desc()` takes a column, id descending). The full chain is SQL `SELECT * FROM drizzle_todos ORDER BY id DESC` — newest todo first. Drizzle builds this SQL itself — you don't write raw SQL.

## Nutshell

Read operation in the SQL phase: make `app/page.tsx` `async`, query with `db.select().from(todos).orderBy(desc(todos.id))` for all todos (newest first) + 200 status. No API route, no fetch, no client state — Server Components are on the server, the database is too, so direct query.

## What It Is NOT

- **Server Component = "async render" is not the point.** Server Components can fetch data because they're on the server — the database is also on the server — so a direct query is possible, no network round-trip. This is an architectural choice, not just syntax.

1. In the SQL phase, the page didn't need an `/api/todos` route, but in the Mongo phase it did — why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In the Mongo phase, the client (browser) was on a different machine from the server — data needed a URL + fetch + client state, stored in state. In the SQL phase, the page is a Server Component — it renders on the server, the database is also on the server — both in the same place. There's no network path, so the page can just run `db.select()` directly.

</details>

2. Why does `app/page.tsx` need to be `async`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because `await db.select()` runs inside it — the query's result takes time to arrive. Only an `async` function can `await`. When rendering on the server, the query runs, and once results arrive the page finishes rendering.

</details>

3. What does `db.select().from(todos)` do, and what changes with `.orderBy(desc(todos.id))`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `db.select().from(todos)` is SQL `SELECT * FROM drizzle_todos` — all rows of the table. `.orderBy(desc(todos.id))` orders them by id descending — newest first. Drizzle builds this SQL itself — you don't write raw SQL.

</details>

4. `todos` and `drizzle_todos` — both refer to the same table, why the different names?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `drizzle_todos` is the actual table name in the database. In TypeScript, the same table is accessed as the `todos` variable (the schema export from 6.10). One table, two names — one for the database, one for code.

</details>
