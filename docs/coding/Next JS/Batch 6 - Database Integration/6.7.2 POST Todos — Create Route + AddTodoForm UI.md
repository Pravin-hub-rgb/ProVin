# POST /api/todos — Create Route + AddTodoForm UI

## Step 1 — Route: Creating a New Todo

**THINK:** Now we need to **send data** — a new todo arrives from the frontend (`{ title: "..." }`), and we save it to the database. Here, the request body must be read — in POST, data comes **inside** the `request` object.

**CONCEPT:** In POST, data **arrives** — the frontend sends `{ title: "..." }`. This introduces a new concept: **the request body**. Problem-first:

**Question 1 — where does the data come from?** In GET, nothing was sent — so there's no parameter. In POST, data **lives inside the request object**. Over the network, it's a text (JSON string). `request.json()` converts that text into a **JavaScript object**. That's why the POST function needs a `request: NextRequest` parameter, and the `NextRequest` import must be added (6.7.1 only had `NextResponse`).

**Question 2 — what about a todo without a title?** Data arrived, but quality check: if `title` is missing, empty, or just spaces (`"   "`) — a worthless todo is created. Don't allow that. Validation — reject on `!title || title.trim() === ""` with **400**. 400 = the client's mistake (6.6 design — wrong body = 400).

**Question 3 — how to save?** `Todo.create({...})` — creates and saves a new document in one step. Schema validation applies on `create` (6.5 — required/default checks). **`title.trim()`** — strips leading/trailing spaces (the schema also has `trim: true` — double layer). **`done: false`** explicit — a new todo always starts as pending (schema has the default too, but explicit makes the intention clear).

**Question 4 — status code?** A new resource **was created** — **201 Created** (6.6 design). GET succeeded with 200, create succeeded with 201 — different because 201 clearly says "a new thing was created."

```ts
// app/api/todos/route.ts
import { NextRequest, NextResponse } from "next/server";
import { connectDB } from "@/app/lib/db";
import Todo from "@/app/models/Todo";

export async function GET() {
  try {
    await connectDB();
    const todos = await Todo.find().sort({ createdAt: -1 });
    return NextResponse.json(todos, { status: 200 });
  } catch (error) {
    console.error("Todos fetch error:", error);
    return NextResponse.json({ error: "Unable to fetch todos" }, { status: 500 });
  }
}

export async function POST(request: NextRequest) {
  try {
    await connectDB();

    const body = await request.json();
    const { title } = body;

    if (!title || title.trim() === "") {
      return NextResponse.json({ error: "Title is required" }, { status: 400 });
    }

    const newTodo = await Todo.create({
      title: title.trim(),
      done: false,
    });

    return NextResponse.json(newTodo, { status: 201 });
  } catch (error) {
    console.error("Todo create error:", error);
    return NextResponse.json({ error: "Unable to create todo" }, { status: 500 });
  }
}
```

The code above is the same — the `NextRequest` import was added up top, and the `POST` function below. POST explained line-by-line:

- **`import { NextRequest, NextResponse }`** — `NextRequest` is the answer to Question 1. POST needs to read the body, so `NextRequest` is needed. `NextResponse` stays the same. (Other imports — `connectDB` from 6.4 and `Todo` from 6.5 — unchanged, nothing new.)
- **`export async function POST(request: NextRequest)`** — the new function, name = HTTP method. `request` parameter — data arrives inside it (Question 1).
- **`try` + `await connectDB()`** — the same pattern — connection ready first, then the work.
- **`await request.json()`** — read the request body (Question 1). Over the network, data is text — `json()` converts it to a JS object. `await` — data takes time to arrive.
- **`const { title } = body`** — destructuring — naming `body.title` as `title` (Batch 3 pattern).
- **Validation — 400** — reject missing title, empty title, or spaces-only title (Question 2). Send `{ error }` JSON with 400 — the client's mistake.
- **`Todo.create({...})`** — create + save (Question 3). `title.trim()` — strips spaces; `done: false` — a new todo starts pending.
- **`{ status: 201 }`** — Created (Question 4). The response body is the saved document — with `_id` and timestamps (remember from 6.5).
- **`catch` + 500** — the same pattern — server-side log on error + 500.

## Step 2 — UI: AddTodoForm Component

**THINK:** The user needs a form — a text input + submit button. When they submit, `fetch` POSTs to `/api/todos`, and the new todo is created. **And the most important thing:** the new todo should appear **in the list** — the list needs to refresh. In 6.7.1 the list was fetched only on page load (`useEffect` with `[]`). Now, when the form submits, how does the list refresh? This is the real teaching point of this file.

**CONCEPT:** In Batch 3.1, `CommentForm` and `ShowComments` were separate components, and there was a problem then — after POST, the list didn't refresh (`useEffect([])` only ran on mount). That same problem comes back here. The clean solution: **let the form not own data — after submit, call a function on `TodoApp` (parent), and `TodoApp` refreshes the list.** Because the data owner is `TodoApp` (decided in 6.7.1 — "the brain"). Problem-first:

**Question 1 — which component owns the form's input data?** The form has a text input — its value is needed. We'll store `title` in `useState` (React's standard controlled input pattern). But this state is **only for the form's own** — not the list data. The form's job: show what the user types + submit.

**Question 2 — what happens on submit?** `onSubmit` handler: `fetch("/api/todos", { method: "POST", headers, body })`. POST sends a body — `JSON.stringify({ title })` converts object to JSON string, and `Content-Type: application/json` header tells the server the body is JSON.

**Question 3 — how does the form's data reach `TodoApp`?** The form receives a function as **props** from `TodoApp` — `onAdd(title)`. When the form submits, it calls `onAdd(title)` — which triggers `TodoApp`'s `addTodo` function. This is the standard parent-child communication pattern in any React app — **child does its thing, but data changes flow through the parent.**

**Question 4 — how does the list refresh after POST? (the real question)** `TodoApp`'s `addTodo`: first send POST, then **call `loadTodos()` again** — the same function that ran on mount in 6.7.1. Since `loadTodos` does `fetch("/api/todos")`, calling it again gets **fresh data from the server** — including the new todo. This is the "refetch from server" pattern: **after a mutation, the server is the source of truth, get fresh data from it.** (Not updating local state with the item directly — because the server added `_id`/timestamps, and future ordering/sorting is decided by the server.)

**Question 5 — `res.ok` check and `AddTodoForm`'s `"use client"`?** `AddTodoForm` has hooks (`useState`, event handlers) — so it needs `"use client"`. And we'll check `res.ok` on fetch errors — same pattern as `loadTodos` in 6.7.1.

```tsx
"use client";

import { useState } from "react";

export default function AddTodoForm({
  onAdd,
}: {
  onAdd: (title: string) => void;
}) {
  const [title, setTitle] = useState("");

  const handleSubmit = async (e: React.FormEvent<HTMLFormElement>) => {
    e.preventDefault();
    if (!title.trim()) return;
    onAdd(title);
    setTitle("");
  };

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="What needs to be done?"
      />
      <button type="submit">Add</button>
    </form>
  );
}
```

The code is the same — now the new parts are tied in:

- **`handleSubmit`** — line-by-line:
  - `e.preventDefault()` — **stop the form's default behavior.** Without this, submitting reloads the page (browser default) — we want JavaScript to handle it, no page reload.
  - `if (!title.trim()) return` — empty/space-only title = don't submit (client-side validation too — stop early, before hitting server's 400)
  - `onAdd(title)` — the real work: calls `TodoApp`'s `addTodo` function (Question 3)
  - `setTitle("")` — clear the input (user can type the next todo)
- **Form JSX** — `onSubmit={handleSubmit}` — handler runs when the form submits. **`input`** — `value` from state, `onChange` updates state (controlled). **`button type="submit"`** — clicking it submits the form, which triggers `handleSubmit`.

> **Notice:** `AddTodoForm` has **no `fetch`!** The form just calls `onAdd(title)`. The fetch work is done by `TodoApp`'s `addTodo`. This is intentional — the form is presentational, data logic lives in the parent (Question 3).

## Nutshell

POST route: `request.json()` reads body, `!title || title.trim() === ""` returns 400, `Todo.create({ title: title.trim(), done: false })` saves, **201 Created**. UI: `AddTodoForm` (client) controlled input stores title, on submit calls `onAdd(title)`. `TodoApp`'s `addTodo` sends POST, then **`loadTodos()` refetches** — after mutation we get fresh data from server. The data flow forms a loop: form → onAdd → POST → refetch → render.

## What It Is NOT

- **`AddTodoForm` should have `fetch`** is wrong — the form's job is just input + submit call, data logic lives in `TodoApp`. That split is what keeps code clean.
- **`e.preventDefault()` is optional** is wrong — without it the page reloads, React state resets, and our fetch POST flow gets interrupted. In JS form handling, the first line is always this.
- **`res.ok` check isn't needed in POST** is wrong — 400 (empty title) and 500 both resolve in `fetch`. Check needed or the UI flow breaks.
- **"updating local state directly after POST" = not a valid shortcut** is true — the server gives `_id`/timestamps, and ordering is also decided by the server. Refetching from server = always correct state.
- **`JSON.stringify` = just "make body look like JSON"** is wrong — the object must be turned into a string, because fetch's body requires a string. Passing an object directly sends `[object Object]`.

Todos are being added and the list refreshes — now the next question: **how does the user remove an incorrect todo?** Right now you can't delete anything. The "First real todo" from 6.5 will always stay in the list.

In any real Todo app, each todo needs a **delete button**. And here's a new pattern we hit for the first time: **which todo to delete?** Each todo has its own `_id` — but the URL is always `/api/todos`, how to target a specific one?

The answer is a **dynamic route** — a variable part of the URL. `DELETE /api/todos/abc2` = "delete todo abc2". The `[id]` folder makes this work. You'll see this pattern everywhere in real apps — profile page `/users/[id]`, blog `/posts/[slug]`. Learning it here with the Todo app:

- **Route:** `DELETE /api/todos/[id]` — find the todo by id and delete it (6.6 design: 404 for wrong id, 200 + message for success)
- **UI:** A **delete button** on each todo — a `TodoItem` component (until now, list items were rendered directly inside `TodoList`, now they get their own component)
