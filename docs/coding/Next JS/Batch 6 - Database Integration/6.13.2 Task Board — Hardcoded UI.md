In 6.13.1 we planned the Task Board — two pages (`/` and `/board/[id]`), data shape (User/Board/Task with status + order), and the flow (SC reads + SA mutations). But before code, there's one thing to build first: **the UI.**

In 6.13.2 we build the Task Board's UI with **hardcoded data** — static arrays, no database. Why build it hardcoded first? If you build dynamic data + UI at the same time and an error appears, you can't tell if the bug is in the UI or in the data. Two things tested at once — hard to debug. Hardcode first: the design is confirmed, the data shape is validated, and you isolate one problem at a time.

## TEST + Problem Highlight

**TEST:** Visit `/` to see the boards list; visit `/board/1` to see columns + tasks. The design is confirmed — columns laid out in a row, each column has an add form + sorted tasks.

**The problem — data lives in two places (DRY violation):**

Right now the tasks are hardcoded **inside the page.** What's the problem? 6.13.1's plan said the Task Board's data would come from the **database** (via Prisma). To make this UI dynamic:

- Remove the hardcoded array
- Fetch data from the database
- Connect the forms to server actions

These three things happen in 6.13.3 (data layer) + 6.13.4 (dynamic). **The UI code stays mostly the same** — only the data source changes. This is the payoff of planning + building hardcoded first: the UI is confirmed, the data layer just plugs in.

Hardcoded UI: on `/` a boards list (`{ id, name }` mapped + form); on `/board/[id]`, columns (filter by `status` + sort by `order`) with an add form in each column + tasks. The dynamic route `[id]` structure is ready (`params` async — same as 6.7.3). Data is hardcoded **in the page** — one place, but it needs to be replaced by database-fetched data in 6.13.4.

## What It Is NOT

- **Hardcoded UI = "final data"** is not true. This is a static demo — built to validate the UI design and data shape. The real data comes from the database (6.13.4). This file is about UI patterns, not data.
- **Buttons with `type="button"` = "working"** is not true. No action is attached yet — Move/Delete get connected to server actions in 6.13.4. `type="button"` is there specifically because a plain button would submit the form.
- **The `params as any` hack = "correct pattern"** is not true. It's a temporary placeholder. The correct approach is `await params` (learned in 6.7.3) — in 6.13.4 the file will be clean. This does hint at the future: even in the hardcoded phase, the dynamic route structure is set up.
- **Layout = "copy it into every page"** is not true. A layout is defined once — both pages render inside it. The header is the shared brand for the board app. (Layout concept from Batch 1.)
- **Client-side filter/sort = "final logic"** is not true. Right now JS filter/sort runs client-side. Database-side filtering/sorting comes in 6.13.4. But the concept is the same here — tasks belonging to a column, in order.

<summary>Show Answer</summary>

**Sample Answer:** `.filter` matches tasks to the column — only tasks belonging to this column (`t.status === column`). `.sort` orders the tasks from smallest to largest `order` — the user-defined rank within the column. Together: the tasks in this column, sorted by order.

</details>
