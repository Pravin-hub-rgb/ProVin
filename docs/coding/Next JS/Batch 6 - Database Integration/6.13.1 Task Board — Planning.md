# Task Board — Part 1: Planning

## Question 1 — What Are We Building?

**Task Board** — a simplified project management app (like Jira/Trello). The user creates tasks and arranges them into **columns** — "Backlog", "In Progress", "Done". Each task belongs to a column. There's one board (single user — this batch has no auth, but data shape is designed so a user can be added — 6.12 relation thinking).

**Why this project:** This is the capstone pattern of the batch — two mini-projects (Mongo, Drizzle) taught different things. Task Board shows **everything at once** the production-grade way:

| Concept (batch) | Where in Task Board |
|---|---|
| Relations 1:N (6.12) | User → Boards → Tasks |
| Prisma ORM (6.3) | Schema + client + queries |
| Migrations (6.10 hint) | `prisma migrate dev` — record of schema changes |
| SC reads (6.11.1) | Board page fetched on server |
| SA mutations (6.11.2/6.11.3) | Create/update/delete tasks + columns |
| RevalidatePath (6.11.2) | Refresh after every mutation |

## Question 2 — Which Pages Do We Need?

A board-based app — few pages, but each page does a lot. Routes table:

| Route | What it shows | Batch concept |
|---|---|---|
| `/` | Home — list of boards (with a form to create a new board) | SC read + SA create |
| `/board/[id]` | One board — columns (Backlog/In Progress/Done) + tasks in each column | Dynamic route (params — 6.7.3 pattern), SC read, SA mutations (create/update/delete tasks, change column) |

**Just two pages.** A board's content is on one page — columns + tasks — because moving a task (column change) happens on the same page. No detail task page needed (tasks are small).

> **Remember the data shape rule (series prompt):** First think "what should the page show", then make the data match. Every field has a reason.

## Question 3 — What's the Data Shape?

Decide the data from the UI — never the reverse.

**What the home page shows:** List of boards — each board's **name**. (Name + id is enough — clicking navigates to the detail page.)

**What the board page shows:** Columns (Backlog/In Progress/Done) — tasks in each column. Each task has **title** (what to do), **description** (optional detail), **status/column** (which column), **order** (ordering within the column).

So the schema shape (Prisma models — defined in 6.13.3):

```
User (one user for now, but for relations)
  id, name, boards[]

Board
  id, name, createdAt
  user_id → User, tasks[]

Task
  id, title, description?, status (Backlog | InProgress | Done)
  order (for sorting within the column)
  board_id → Board
```

**Every field has a reason:**

- **`User.id`, `Board.id`, `Task.id`** — primary keys, unique identifiers (Prisma `@id @default(autoincrement())`)
- **`Board.user_id` → User** — **foreign key (6.12)** — 1 User → N Boards. There's one user now, but the relation is designed so authentication can be added smoothly — **forward-thinking design**
- **`Task.board_id` → Board** — foreign key — 1 Board → N Tasks
- **`Task.status`** — the column (enum: Backlog/InProgress/Done) — where the task is
- **`Task.order`** — ordering within the column — keeps the order stable no matter how many tasks
- **`description`** — optional (`String?`) — task detail, small tasks may have no description

**Think of this relation tree (6.12 system design):**

```
User 1 ── N Board 1 ── N Task
        (user_id)    (board_id, status, order)
```

Three models, two foreign keys, one enum. **No N:N needed** (6.12 explained when a join table is needed — here, a task belongs to one board, a board belongs to one user — everything is 1:N).

## Question 4 — How Does Data Flow?

Per the batch pattern (6.11.1-6.11.4) — SC reads + SA mutations:

| Operation | Pattern | Where |
|---|---|---|
| List of boards | SC read — `prisma.board.findMany()` | directly in the `/` page |
| Board + columns + tasks | SC read — `prisma.board.findUnique({ include: { tasks } })` | `/board/[id]` page |
| Create board | SA — `createBoard(formData)` + `revalidatePath("/")` | form on `/` |
| Create task | SA — `createTask(boardId, formData)` + revalidate | form on the board page |
| Move task (change column) | SA — `moveTask(id, newStatus)` + revalidate | each task's move control |
| Delete task | SA — `deleteTask(id)` + revalidate | each task's delete button |

**Prisma query style (6.3 + current docs):** Drizzle had `db.select().from(todos)` — Prisma has `prisma.board.findMany()`. Related data via `.findUnique({ include: { tasks: true } })` — **6.12's JOIN/N+1 pattern** — board + tasks in one query (no N+1).

**Data flow diagram:**

```
Server Component (/board/[id])
   │  prisma.board.findUnique({ include: tasks })
   ▼
Board + Columns + Tasks (data ready on server)
   ▼
UI render (columns, tasks in each column)
   │
   └── form submit → Server Action → prisma mutation → revalidatePath → re-render
```

**`lib/prisma.ts`** — Prisma client singleton (global instance — no new connections on hot reload) — details in 6.13.3.

## Nutshell

Task Board planning: the project = boards → columns → tasks. Two pages (`/`, `/board/[id]`). Data shape decided from the UI — User/Board/Task models, two foreign keys (1:N), Task has status + order. Flow = Server Components reads (`prisma.board.findMany`, `findUnique` + `include`) + Server Actions mutations + revalidatePath. All three models are 1:N — no join table needed for N:N.

## What It Is NOT

- **Planning = "just list the files"** is not accurate. In planning, **every field has a reason** — data shape comes from the UI. Adding fields without a reason is a bad start.
- **Task Board = "clone of a kanban app"** is not the point. It's a production-pattern example — relations, migrations, SC+SA — practice the concepts, don't copy features.
- **`User` model = authentication's job** is not quite right. The User model exists for relations (1:N design), no auth in this batch. But the schema is designed so authentication can be added smoothly — forward-thinking design.
- **`order` field = "extra"** is not true. The `order` field stores the user's chosen position within a column — without it, every render sorts randomly. The UI shows sorting — the `order` field is its data.
- **Planning = "just the first part"** is not true. Planning is the most important part — the rest of the series flows from here. Hardcoded UI (6.13.2) comes directly from planning.

**In Your Own Words**

1. "Data shape is decided from the UI" — what does that mean, with an example?

<details>
<summary>Show Answer</summary>

**Sample Answer:** First decide what the page should show, then make the data match. In Task Board — the board page shows columns (Backlog/In Progress/Done), and within each column, tasks — so the data needs a `status` (which column) and `order` (the position within the column). Whatever the UI shows becomes the fields in the data — no random fields.

</details>

2. In Task Board, all relations are 1:N — when would N:N (join table) be needed?

<details>
<summary>Show Answer</summary>

**Sample Answer:** 1 user → N boards, 1 board → N tasks — "one entity to its multiple" — that's 1:N, foreign key in the same table. N:N is when two independent things link to multiple of each other (like tasks and tags — one task has multiple tags, one tag is on multiple tasks) — then a join table is needed. Here it's not needed.

</details>

3. Why keep the `Task.order` field — can't we just sort when rendering?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `order` stores the user's chosen position within a column — "put this task at this position in this column". Sorting on render is just the algorithm — the data for it comes from `order`. Without `order`, the tasks' positions are random every time.

</details>

4. In Prisma, `findUnique({ include: { tasks: true } })` — how does this relate to the N+1 problem from 6.12?

<details>
<summary>Show Answer</summary>

**Sample Answer:** N+1 = first fetch the board, then a separate query for each board's tasks (N queries) — slow. `include: { tasks: true }` tells Prisma to get the board + all its tasks in a single query (internal JOIN) — one round-trip. That's exactly the 6.12 JOIN pattern — the ORM's `include` does the same thing.

</details>

5. Task moves happen on the same page — why not a detail page for each task?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Tasks are small — moving a task (Backlog → In Progress) is a drag/click action that naturally happens on the board page. A detail page is only needed when a resource has its own view (screenshots, comments, large content). Here the data is small — an extra page is just navigation overhead with no value. Data shape follows the UI — that's the rule.

</details>
