# Task Board — Part 1: Planning

## Sawaal 1 — Kya Banana Hai?

**Task Board** — ek project management app jaisa simple version (Jira/Trello jaisa). User tasks banata hai, unhe **columns** mein arrange karta hai — "Backlog", "In Progress", "Done". Har task ek column mein hota hai. Board ek hi hota hai (single user — is batch mein auth nahi, lekin data shape aise banayenge ki user add ho sake — 5.12 wala relation soch).

**Kyun ye project:** Yeh batch ka capstone pattern hai — do mini-projects (Mongo, Drizzle) alag-alag cheezein sikha rahe the. Task Board **sab kuch ek saath** dikhata hai production-grade tarike se:

| Concept (batch) | Task Board mein kahan |
|---|---|
| Relations 1:N (5.12) | User → Boards → Tasks |
| Prisma ORM (5.3) | Schema + client + queries |
| Migrations (5.10 hint) | `prisma migrate dev` — schema changes ka record |
| SC reads (5.11) | Board page server pe fetch |
| SA mutations (5.11) | Create/update/delete tasks + columns |
| RevalidatePath (5.11) | Har mutation ke baad UI refresh |

## Sawaal 2 — Kaunse Pages Chahiye?

Board-based app hai — pages kam, par har page pe kafi kaam. Routes table:

| Route | Kya dikhta hai | Batch concept |
|---|---|---|
| `/` | Home — boards ki list (naya board banane ka form) | SC read + SA create |
| `/board/[id]` | Ek board — columns (Backlog/In Progress/Done) + har column mein tasks | Dynamic route (params, 5.7 wala pattern), SC read, SA mutations (task create/update/delete, column change) |

**Bas do pages.** Board ka content ek hi page pe — columns + tasks — kyunki task move karna (column change) same page pe hota hai. Detail task page nahi chahiye (tasks chhote hain).

> **Data shape rule yaad rakho (series prompt):** Pehle socho "page pe kya dikhega", phir data wahi banao. Har field ka reason.

## Sawaal 3 — Data Ka Shape Kya Hai?

UI dekh ke data decide karte hain — ulta nahi.

**Home page pe kya dikhta hai:** Boards ki list — har board ka **name**. (Naam + id hi kaafi — detail page pe navigate hoga.)

**Board page pe kya dikhta hai:** Columns (Backlog/In Progress/Done) — har column mein tasks. Har task mein **title** (kya karna hai), **description** (optional detail), **status/column** (kaunsa column), **order** (column ke andar kram).

So schema shape (Prisma models — 5.13.3 mein detail):

```
User (ek hi user abhi, par relation ke liye)
  id, name, boards[]

Board
  id, name, createdAt
  user_id → User, tasks[]

Task
  id, title, description?, status (Backlog | InProgress | Done)
  order (column ke andar sorting ke liye)
  board_id → Board
```

**Har field ka reason:**

- **`User.id`, `Board.id`, `Task.id`** — primary keys, unique identifiers (Prisma `@id @default(autoincrement())`)
- **`Board.user_id` → User** — **foreign key (5.12)** — 1 User → N Boards. Abhi ek user hai, par relation aise design kiya ki auth aane pe seedha kaam karega
- **`Task.board_id` → Board** — foreign key — 1 Board → N Tasks
- **`Task.status`** — column (enum: Backlog/InProgress/Done) — task ka position
- **`Task.order`** — column ke andar sorting — kitna bhi tasks ho, kram stable
- **`description`** — optional (`String?`) — task detail, chhote tasks mein empty ho sakta hai

**Yeh relation tree socho (5.12 system design):**

```
User 1 ── N Board 1 ── N Task
        (user_id)    (board_id, status, order)
```

Teen models, do foreign keys, ek enum. **N:N nahi chahiye** (5.12 mein bataya tha join table kab chahiye — yahan task ek board ka hai, board ek user ka — sab 1:N).

## Sawaal 4 — Data Flow Kaise Hoga?

Batch ke pattern (5.11) ke hisaab se — SC reads + SA mutations:

| Operation | Pattern | Kahan |
|---|---|---|
| Boards ki list | SC read — `prisma.board.findMany()` | `/` page mein seedha |
| Board + columns + tasks | SC read — `prisma.board.findUnique({ include: { tasks } })` | `/board/[id]` page |
| Board banana | SA — `createBoard(formData)` + `revalidatePath("/")` | `/` pe form |
| Task banana | SA — `createTask(boardId, formData)` + revalidate | Board page pe form |
| Task move (column) | SA — `moveTask(id, newStatus)` + revalidate | Har task ka move control |
| Task delete | SA — `deleteTask(id)` + revalidate | Har task ka delete button |

**Prisma query style (5.3 + abhi source docs):** Drizzle mein `db.select().from(todos)` tha — Prisma mein `prisma.board.findMany()`. Relation wala data `.findUnique({ include: { tasks: true } })` se — **5.12 ka JOIN/N+1 wala pattern** — ek query mein board + tasks (no N+1).

**Data flow diagram:**

```
Server Component (/board/[id])
   │  prisma.board.findUnique({ include: tasks })
   ▼
Board + Columns + Tasks (data server pe ready)
   ▼
UI render (columns, har column mein tasks)
   │
   └── form submit → Server Action → prisma mutation → revalidatePath → re-render
```

**`lib/prisma.ts`** — Prisma client singleton (global instance — hot reload pe naye connections nahi) — 5.13.3 mein detail.

## Nutshell

Task Board planning: project = boards → columns → tasks. Do pages (`/`, `/board/[id]`). Data shape UI se decide hota hai — User/Board/Task models, do foreign keys (1:N), Task mein status + order. Flow = Server Components reads (`prisma.board.findMany`, `findUnique` + `include`) + Server Actions mutations + revalidatePath. Teeno models mein sab 1:N — N:N ka join table nahi chahiye.

## What It Is NOT

- **Planning = "ek file list bana do" nahi.** Planning mein har field ka **reason** hai — data shape UI se decide hota hai. Bina reason ka field add karna hi galat shuruat hai.
- **Task Board = "kanban ka clone" nahi.** Yeh production-pattern example hai — relations, migrations, SC+SA — concepts apply karna hai, features copy karna nahi.
- **`User` model = auth ka kaam nahi.** User model relation ke liye hai (1:N design), auth is batch mein nahi. Lekin schema aisa ki auth aane pe add ho jaaye — forward-thinking design.
- **`order` field = "extra" nahi.** Column ke andar tasks ka kram stable chahiye — bina `order` ke har render pe sorting random. UI dikhta hai sort ho raha hai — order field uska data hai.
- **Planning = "sirf pehla part" nahi.** Planning sabse important part hai — isi se baaki series chalti hai. Hardcoded UI (5.13.2) seedha planning se niklega.

2. Task Board mein sab relations 1:N kyun hain — N:N (join table) kab chahiye hota?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Ek user ke N boards, ek board ke N tasks — har cheez "ek se uske multiple" — isliye 1:N, foreign key usi table mein. N:N tab hota jab do independent cheezein aapas mein multi-jude hon (jaise task aur tag — ek task ke multiple tags, ek tag ke multiple tasks) — tab join table chahiye. Yahan nahi chahiye.

</details>

3. `Task.order` field kyun rakha — sort karke render kyu nahi kar sakte?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `order` field user ka decided kram store karta hai — "is task ko is column mein is position pe rakhna hai". Render pe sort karna toh bas ek algorithm hai — usme user ki chosen position ka data kahan se aayega? Order data hai, render uska reflection. Bina order ke tasks ka order stable nahi rahega.

</details>

4. Prisma mein relation wala data `findUnique({ include: { tasks: true } })` se — 5.12 ki N+1 problem se kaise related?

<details>
<summary>Show Answer</summary>

**Sample Answer:** N+1 problem = pehle board fetch karo, phir har board ke tasks ke liye alag query (N queries) — slow. `include: { tasks: true }` Prisma ko ek hi query mein board + uske tasks laane ko bolta hai (internal join) — ek round-trip. Wahi 5.12 ka JOIN pattern — ORM ka include wahi kar raha hai.

</details>

5. Task move (column change) same page pe hota hai — detail page kyun nahi banaya?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Tasks chhote hain — move karna (Backlog → In Progress) ek column ke drop/click jaisa action hai jo board page pe hi hota hai. Detail page tab banta jab kisi resource ke liye alag view chahiye (screenshots, comments, bade content). Yahan data small hai — extra page sirf navigation overhead hota, koi value nahi. Data shape UI ke hisaab se — yahi rule.

</details>
