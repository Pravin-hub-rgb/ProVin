## Schema — User/Board/Task Models (6.12 ka Design)

**File:** `prisma/schema.prisma` — boilerplate ke baad models add karo.

Drizzle mein schema TypeScript thi (`pgTable`), Prisma mein **apni alag language** hai — **PSL** (Prisma Schema Language). Types capital hain (`Int`, `String`, `Boolean`). 6.3 ka compare yaad hai — wahi ab likhenge.

**User model (relation root):**

**Concept:** Relation tree ka root — User. 6.12 ka design yaad hai — User → Board (1:N). Prisma mein model ek block hai — fields + unke options. **File:** `prisma/schema.prisma` — ab step-by-step.

Pehla kaam — User model — **`id Int @id @default(autoincrement())`** — primary key + auto 1,2,3... (Drizzle `serial('id').primaryKey()` — same kaam, alag syntax):

```prisma
// prisma/schema.prisma
model User {
  id   Int    @id @default(autoincrement())
```

**`id Int @id @default(autoincrement())`** — primary key + auto 1,2,3... (Drizzle `serial('id').primaryKey()` — same kaam, alag syntax).

Ab `name` aur relation field — **`name String`** — user ka naam — simple field. **`boards Board[]`** — relation field — "User ke multiple boards" — **yeh Prisma ki relation syntax hai** (1:N). Database mein column nahi banti — Prisma ko relation batati hai. Doosri taraf (`Board.user`) explicit define karni padti hai:

```prisma
// prisma/schema.prisma
model User {
  id     Int     @id @default(autoincrement())
  name   String

```

**`name String`** — user ka naam — simple field. **`boards Board[]`** — relation field — "User ke multiple boards" — **yeh Prisma ki relation syntax hai** (1:N). Database mein column nahi banti — Prisma ko relation batati hai. Doosri taraf (`Board.user`) explicit define karni padti hai.

**Board model (1:N dono taraf):**

**Concept:** Board do relations mein hai — ek upar (User → Board, foreign key `user_id`), ek neeche (Board → Task, `tasks`). 6.12 ka design — do foreign keys — isliye is model mein dono taraf ki cheezein hain. Ab step-by-step — User model upar dikh raha hai.

Board ka header — `id` (wahi autoincrement pattern) + `name` + **`createdAt DateTime @default(now())`** — banane ka time — `@default(now())` — MySQL `DEFAULT NOW()` jaisa — board banate waqt date khud set hoti hai, hum nahi bhejte:

```prisma
// prisma/schema.prisma
model User {
  id     Int     @id @default(autoincrement())

  boards Board[]

model Board {                                     // NEW
  id        Int      @id @default(autoincrement())  // NEW
  name      String                                // NEW
  createdAt DateTime @default(now())              // NEW
```

**`createdAt DateTime @default(now())`** — banane ka time — `@default(now())` — MySQL `DEFAULT NOW()` jaisa — board banate waqt date khud set hoti hai, hum nahi bhejte.

Ab foreign key — **`user_id Int`** — **foreign key column** — 6.12 ka `user_id` hi hai. Database mein asli column. **`user User @relation(fields: [user_id], references: [id])`** — relation define — "Board.user_id → User.id" — Prisma ko batata hai foreign key kaunsa hai, kahan reference karta hai:


**`user_id Int`** — **foreign key column** — 6.12 ka `user_id` hi hai. Database mein asli column. **`user User @relation(fields: [user_id], references: [id])`** — relation define — "Board.user_id → User.id" — Prisma ko batata hai foreign key kaunsa hai, kahan reference karta hai.

## Migrate — Tables Database Mein Banao

Drizzle mein `npx drizzle-kit push` chalaya tha (6.10). Prisma mein **`npx prisma migrate dev`** — yeh production-grade hai, **changes ka record rakhta hai** (migration files).

**Concept — Push vs Migrate (6.10 hint + ab detail):** **`push`** seedha schema dekh ke database update karta hai — koi record nahi (dev ke liye quick). **`migrate dev`** schema padhta hai, **ek SQL file banata hai** (`prisma/migrations/.../migration.sql`), phir database update karta hai — **history rehti hai**. Task Board production pattern hai isliye migrate. Code:

```bash
npx prisma migrate dev --name init
```

**`migrate dev`** — schema padhta hai, `migration.sql` file banata hai, phir database update karta hai — **history rehti hai**. **`--name init`** — migration ko naam deta hai — changes trackable.

```
prisma/
├── schema.prisma
└── migrations/
    └── 20250815_init/
        └── migration.sql    ← Prisma ne khud SQL likhi
```

**`migration.sql` mein kya hai (sample — Prisma khud banata hai):**

```sql
CREATE TABLE "User" (
  "id" SERIAL PRIMARY KEY,
  "name" TEXT NOT NULL
);
CREATE TABLE "Board" (
  "id" SERIAL PRIMARY KEY,
  "name" TEXT NOT NULL,
  "createdAt" TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  "user_id" INTEGER NOT NULL,
  CONSTRAINT "Board_user_id_fkey" FOREIGN KEY ("user_id") REFERENCES "User"("id")
);
CREATE TABLE "Task" (
  "id" SERIAL PRIMARY KEY,
  "title" TEXT NOT NULL,
  "description" TEXT,
  "status" TEXT NOT NULL,
  "order" INTEGER NOT NULL DEFAULT 0,
  "board_id" INTEGER NOT NULL,
  CONSTRAINT "Task_board_id_fkey" FOREIGN KEY ("board_id") REFERENCES "Board"("id")
);
```

**Migration ka value:** team mein koi naya developer aaye — `prisma migrate dev` chalaye — saari migrations ek-ek karke chalein — uska database exact same tera jaisa. Aaj board table banayi, kal naya column — migration 2, parso — migration 3. **History + reproducibility.**

Terminal output: `✔ Generated Prisma Client` + `✔ Your database is now in sync with your Prisma schema.` — tables ban gayi + Prisma Client generate hua (types + functions — 6.13.4 mein `prisma.board.findMany()` type-safe hoga).

Neon mein verify — SQL Editor mein:

```sql
SELECT * FROM "Board";
```

`(0 rows)` — table ban gayi, khali hai. (Capital naam `"Board"` — PostgreSQL case-sensitive, quotes chahiye — Prisma aise hi banata hai.)

## Client — `lib/prisma.ts` Singleton

`@prisma/client` se `PrismaClient` milta hai — **`PrismaClient` ek class hai, `new PrismaClient()` uske functions (`prisma.board.findMany()`) se queries chalata hai** — Drizzle ke `db` client jaisa. Par **ek problem** — Next.js dev hot reload pe baar-baar `new PrismaClient()` chalega — naye connections — Neon ka limit exhaust. Solution — **global singleton** (6.4 `connectDB` cache jaisa idea, Prisma version).

**Concept:** Client ko global object mein store karo — hot reload pe naya client banane ki jagah wahi purana mil jaye — ek connection, baar-baar reuse. **File:** `lib/prisma.ts` — ab step-by-step.

Pehla kaam — import + global slot — **`globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined }`** — global object mein `prisma` slot — `globalThis` browser/Node dono mein kaam karta hai. TypeScript ko batao slot exist karta hai (`as unknown as`):

```ts
// lib/prisma.ts
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};
```

**`globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined }`** — global object mein `prisma` slot — `globalThis` browser/Node dono mein kaam karta hai. TypeScript ko batao slot exist karta hai (`as unknown as`).

Ab client banao — **`new PrismaClient()`** — class ka naya instance = ek client object jiske functions se queries chalti hain (Drizzle ke `db` jaisa). **`globalForPrisma.prisma ?? new PrismaClient()`** — `??` (nullish coalescing): pehli baar — undefined → naya client banao. Dobara — purana client hai → wahi use karo. **Hot reload pe naya connection nahi:**

```ts
// lib/prisma.ts
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

const prisma = globalForPrisma.prisma ?? new PrismaClient();   // NEW
```

**`new PrismaClient()`** — class ka naya instance = queries wala client object. **`globalForPrisma.prisma ?? new PrismaClient()`** — `??` (nullish coalescing): pehli baar — undefined → naya client banao. Dobara — purana client hai → wahi use karo. **Hot reload pe naya connection nahi.**

Ab global mein store — **`if (process.env.NODE_ENV !== "production")`** — sirf dev mein global mein store (production mein hot reload nahi hota — server restart nahi — problem nahi):

```ts
// lib/prisma.ts
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

const prisma = globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== "production") {                  // NEW
  globalForPrisma.prisma = prisma;                           // NEW
}
```

**`if (process.env.NODE_ENV !== "production")`** — sirf dev mein global mein store (production mein hot reload nahi hota — server restart nahi — problem nahi).

Aur last — **`export default prisma`** — poori app mein import (default export — naam import pe khud rakhte hain):

```ts
// lib/prisma.ts
import { PrismaClient } from "@prisma/client";

  prisma: PrismaClient | undefined;
};

  globalForPrisma.prisma = prisma;
}

```

**`export default prisma`** — poori app mein import (default export — naam import pe khud rakhte hain).

**Drizzle vs Prisma — connection compare (6.10 vs ab):**

```ts

// Prisma — lib/prisma.ts
```

## Nutshell

Data layer: `prisma/schema.prisma` mein PSL (Prisma Schema Language) mein models — `User`, `Board`, `Task` — relations `@relation(fields, references)` + relation fields (`boards Board[]`, `tasks Task[]`) — 6.12 ka 1:N design. `npx prisma migrate dev --name init` — migrations folder mein SQL file + Neon mein tables. `lib/prisma.ts` — PrismaClient global singleton (hot reload pe naye connections nahi). Enum `Status` — Backlog/InProgress/Done.

## What It Is NOT

- **PSL = TypeScript nahi.** Prisma Schema Language apni alag language hai (capital types: `Int`, `String`, `Boolean`). Prisma isse TypeScript types **generate** karta hai — tum manual `interface` nahi likhte (6.10 `InferSelectModel` wala benefit, Prisma style).
- **`boards Board[]` = database column nahi.** Yeh relation field hai — Prisma ko batata hai "User ke multiple boards". Database mein column nahi banta. Asli foreign key column `user_id` hai (dusri taraf). Dono taraf define karna zaroori — `Board[]` + `@relation(fields, references)`.
- **`migrate dev` = `push` ka doosra naam nahi.** Push seedha schema sync karta hai bina record. Migrate ek **migration file** banata hai — changes ki history — team/production mein reproducible. Task Board production pattern hai isliye migrate.
- **`new PrismaClient()` = ek baar banao matlab bas hai.** Hot reload pe har baar naya client banega toh connections leak — global singleton `??` pattern zaroori hai. Bas `export default new PrismaClient()` nahi chalega dev mein.
- **`@default(now())` = hum date nahi bhejte.** Board banate waqt `createdAt` khud Prisma set karta hai — `@default(now())` — hum insert mein include nahi karte.
