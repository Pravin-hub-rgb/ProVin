# Task Board — Part 3: Data Layer (Prisma)

## Step 1 — Install Prisma

**CONCEPT (refresher 6.3):** ORM = Object-Relational Mapping — database ko object-friendly banata hai. Drizzle (6.10) tha — Prisma is same job, **bada ecosystem, schema-first** (database ka design config file mein likho, migrate generate karega). Prisma config file — `schema.prisma`.

Task Board project (`task-board` — 6.13.2 ne banaya) mein Prisma install karo:

```bash
npm i -D prisma
npm i @prisma/client
```

**Two packages, two jobs:**

- `prisma` — **dev dependency** — CLI tool (migrate, studio, generate) — sirf development/testing mein, production mein nahi chahiye.
- `@prisma/client` — **runtime dependency** — generated client — code mein `import { PrismaClient } from '@prisma/client'` use karta hai — production mein chahiye.

> **Note:** Drizzle mein `npm i drizzle-orm @neondatabase/serverless` tha — Drizzle ka PostgreSQL driver ne tha (`pg` equivalent). Prisma ke pas **apna built-in driver system** hai (Node.js drivers internally — `pg` PostgreSQL ke liye). Prisma ke pas package.json mein explicit driver nahi hota — Prisma ke andar built-in hai. Dono same kaam karte hain.

## Step 2 — Define Schema

**CONCEPT:** Prisma ka **schema-first approach** — sabse pehle database ka structure (`schema.prisma` file) likho, migrate se actual database banao. Yeh Drizzle se match karti hai (6.10 mein SQL blueprint tha) — schema = database ka blueprint. Yeh 6.13.1 ka plan (User/Board/Task models, relations 1:N) ko implement karta hai.

**File:** `prisma/schema.prisma`

Ab model likho — **User, Board, Task** — 6.13.1 ka data shape:

```prisma
// prisma/schema.prisma
model User {
  id     Int     @id @default(autoincrement())
  name   String
  boards Board[]
}

model Board {
  id        Int      @id @default(autoincrement())
  name      String
  createdAt DateTime @default(now())
  userId    Int
  user      User     @relation(fields: [userId], references: [id])
  tasks     Task[]
}

model Task {
  id          Int      @id @default(autoincrement())
  title       String
  description String?
  status      TaskStatus @default(BACKLOG)
  order       Int
  boardId     Int
  board       Board    @relation(fields: [boardId], references: [id])
}

enum TaskStatus {
  BACKLOG
  IN_PROGRESS
  DONE
}
```

**`model User`** — `id` (primary key `@id`), `name`, `boards` (relation — 1 User → N Boards).

**`model Board`** — `name`, `createdAt` (`@default(now())` — auto timestamp), `userId` + `@relation(fields: [userId], references: [id])` — **foreign key (6.12)** — User se juda hua hai, `boardId` → Task relation — 1 Board → N Tasks.

**`model Task`** — `title`, `description String?` (optional — 6.13.1 ka `String?`), `status TaskStatus` (enum — `@default(BACKLOG)` — new tasks backlog mein shuru hote hain), `order` (sorting — 6.13.1 Sawaal 3), `boardId` + `@relation` (Board se juda hua).

**`enum TaskStatus`** — BACKLOG / IN_PROGRESS / DONE — 6.13.1 ka enum. Yeh TypeScript enum jaise hoti hai — values uppercase (by convention) — UI mein labels milengi.

**Step-by-step schema — every keyword explained:**

- **`@id`** — primary key — unique identifier — rows ka identity. Drizzle mein `primaryKey()` tha — Prisma mein `@id`.
- **`@default(autoincrement())`** — ID automatic increment hota hai — 1, 2, 3... — manually set nahi karo. Drizzle mein `serial(...).primaryKey()` tha (auto-increment in PostgreSQL).
- **`String?`** — `?` = optional field — description ho sakta ya nahi — Drizzle mein `.optional()` tha.
- **`@default(now())`** — agar createdAt diya nahi, current time set karo — timestamp.
- **`@relation(fields: [userId], references: [id])`** — **foreign key definition (6.12)** — `userId` column `User.id` se reference karta hai — relation. Fields = local column, references = target column.

> **Thinking point:** Relation syntax (`user: User @relation(...)`) two things — the **field** (`userId: Int` — the actual column) and the **relation** (`user: User` — the typed navigation). Dono ek saath hone chahiye — relation ke liye field + relation object.

## Step 3 — Connect Database (PostgreSQL / Neon)

Yeh 6.9 ka exact same pattern hai — Neon + DATABASE_URL env var. Prisma bhi environment variable se connect karta hai. **File:** `.env` (project root)

```
DATABASE_URL="postgresql://...neon.tech?sslmode=require"
```

Schema ke upar datasource block — Prisma ko batao PostgreSQL use karo:

```prisma
// prisma/schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User { ... }
```

**`generator client`** — jab migrate/generate hoga, Prisma client generate karega (TypeScript types ke saath).

**`datasource db`** — `provider = "postgresql"`, `url = env("DATABASE_URL")` — 6.9 ka Neon. `env(...)` schema file se process.env.DATABASE_URL read karta hai.

> **Same as 6.9** but Prisma instead of Drizzle. Dono PostgreSQL use karte hain, dono Neon-compatible — dono migrations use karte hain (`db push` alternative).

## Step 4 — Migrate — From Schema to Database

**CONCEPT (migration refresher 6.10):** Migration = database ka historical record — schema badalne par ek migration file generate hoti hai — jo team members ko database update karne deta hai. Dono Drizzle aur Prisma isi pattern follow karte hain. `migrate dev` = dev environment ke liye — database + client dono update karta hai.

Run migration:

```bash
npx prisma migrate dev --name init
```

**`--name init`** — migration file ka name — `init` = first migration. Prisma `prisma/migrations/2024xxxxx_init/` folder create karega — SQL file with CREATE TABLE statements. Database (Neon) pe apply karega.

**Kya hota hai migration mein:**

1. Schema file parse hoti hai
2. SQL migration file generate hoti hai (CREATE TABLE USER, BOARD, TASK, etc.)
3. Database (Neon) pe apply hoti hai — tables banati hai
4. `@prisma/client` regenerate hota hai — **TypeScript types milte hain** (`Board`, `Task`, `TaskStatus` types)

> **Note:** Agar `DATABASE_URL` galat hai ya Neon project delete ho gaya, migrate fail hoga — `.env` double-check karo. 6.9 ka same Neon URL use karo.

## Step 5 — Client Singleton

**CONCEPT:** Prisma client ko singleton bana ke rakho — agar har request par `new PrismaClient()` karo, toh connections leak hoti hain — server hot reload par bhi. **Global singleton pattern** use karo — same pattern har framework ke saath.

**File:** `lib/prisma.ts`

```ts
// lib/prisma.ts
import { PrismaClient } from '@prisma/client'

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined
}

export const prisma = globalForPrisma.prisma ?? new PrismaClient()

if (process.env.NODE_ENV !== 'production') globalForPrisma.prisma = prisma
```

**`globalForPrisma`** — global `this` pe Prisma instance store karo — hot reload par nayi instance nahi banegi.

**`?? new PrismaClient()`** — agar global pe nahi hai, toh nayi banao.

**`if (process.env.NODE_ENV !== 'production')`** — sirf development mein global pe store karo — production mein serverless (Neon) ke liye alag pattern hota hai — but yehi standard pattern kaam karega.

> **Same concept as Drizzle** (6.10 mein `db` singleton export tha) — dono ek hi cheez karte hain. Prisma ke official docs bhi ye use karte hain.

## Nutshell

Prisma data layer: `npm i -D prisma` + `npm i @prisma/client` (CLI vs runtime). `prisma/schema.prisma` mein User/Board/Task models + relations (1:N, foreign keys via `@relation`) + `TaskStatus` enum. `.env` se `DATABASE_URL` (Neon — 6.9 pattern), `datasource db` block. `npx prisma migrate dev --name init` generates SQL migration + applies to Neon + regenerates client (TypeScript types). `lib/prisma.ts` ek global singleton — connections leak na ho. 6.9 ka schema-first + migration pattern, Prisma syntax mein.

## What It Is NOT

- **Prisma client = "runtime dependency nahi chahiye"** is not true. `@prisma/client` runtime pe chahiye — code mein `import` karta hai. `prisma` dev-only (CLI — migrate/studio/generate). Dono install karo, dono alag roles.
- **Enum values = "case-insensitive"** is not true. `BACKLOG` uppercase defined hai (convention), TypeScript strict hota hai — `BACKLOG` hi likhna padega. UI mein label ("Backlog") mapping kaam aapni hai.
- **`@relation` without the field** = valid nahi. `userId Int` column + `user: User @relation(fields: [userId], references: [id])` — dono chahiye. Field the column (DB level), relation the typed navigation (code level). Sirf ek nahi chalega.
- **Migrate = "schema sync"** is not true. Migrate *history* maintain karta hai — har migration ek versioned file. `db push` schema ko seedha database mein force karega (dev-only). Migrate team collaboration ke liye — every schema change is a migration.
- **Studio = "production database view"** is not true. Studio local/dev GUI hai — read/write capabilities hai. Sensitive environments mein use mat karo — just local debugging.

**In Your Own Words**

1. `npm i -D prisma` and `npm i @prisma/client` — why are these two separate packages with different roles?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `prisma` is the **CLI tool** (migrate, studio, generate) — used at **build/dev time only** — marked as dev dependency (`-D`). `@prisma/client` is the **generated client library** — used at **runtime** — code does `import { PrismaClient } from '@prisma/client'`. Production deploys need `@prisma/client` (running server), not `prisma`(CLI only runs during build).

</details>

2. What's the difference between the `@relation` field and the column it references? Why are both needed?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `userId Int` is the **actual database column** (the foreign key value stored). `user: User @relation(fields: [userId], references: [id])` is the **typed relation** — `@relation(fields:...)` links the column to the target (`references: [id]`), and `user: User` is the relation field for code navigation. Both are needed: the column (`userId`) stores the value so it persists in the DB, and the `@relation` gives Prisma the typed navigation so `prisma.board.findUnique({ include: { user: true }})` works. Without the column, nothing is stored; without `@relation`, Prisma has no typed relation.

</details>

3. Why does Prisma use a global singleton for the client? What problem does it solve?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Each `new PrismaClient()` opens database connections — on hot reload (development), multiple client instances would be created, leaking **connections** (too many open, server rejects new ones). The global singleton pattern (`globalThis.prisma ?? new PrismaClient()`) reuses one instance across reloads — the client is set on the first render, and subsequent renders find it on `globalThis`. Production (serverless — 6.9 Neon) handles this differently (single connection per instance), but the singleton pattern is the standard practice and works everywhere.

</details>

4. In migration, what happens in the 4 steps when we run `prisma migrate dev --name init`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** 1. The `schema.prisma` is parsed into an internal data model. 2. Prisma generates a **SQL migration file** (`prisma/migrations/..._init/migration.sql`) with `CREATE TABLE` statements — this file is the **history record**. 3. The SQL is applied to the database (Neon) — tables get created. 4. The Prisma Client is **regenerated** with TypeScript types from the schema — so `Board`, `Task`, `TaskStatus` are auto-typed.

</details>

5. `String?` in Prisma schema — how does this connect to the UI logic from 6.13.2's `{task.description && <small>...</small>}`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `String?` means description is optional — a task can have or not have one. At the type level, `description` becomes `string | null`. In 6.13.2 `{task.description && }` handled that case — when the DB returns `description: null` (no description), the `&&` short-circuits and only renders the title. So the schema's `String?` flows directly to the UI's conditional render — the same field, from DB to UI, the whole path is consistent.

</details>
