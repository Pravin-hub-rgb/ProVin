# Task Board — Part 3: Data Layer (Prisma)

## Step 1 — Install Prisma

**CONCEPT (refresher 6.3):** ORM = Object-Relational Mapping — it makes the database object-friendly. We saw Drizzle (6.10) do this job — Prisma does the same job, but with a **larger ecosystem and a schema-first approach** (write the database design in a config file, and migrations generate the actual database). Prisma's config file is `schema.prisma`.

Install Prisma in the task-board project (created in 6.13.2):

```bash
npm i -D prisma
npm i @prisma/client
```

**Two packages, two jobs:**

- `prisma` — **dev dependency** — CLI tool (migrate, studio, generate) — only needed at build/dev time, not in production.
- `@prisma/client` — **runtime dependency** — the generated client — your code imports it: `import { PrismaClient } from '@prisma/client'` — needed at runtime.

> **Note:** In Drizzle it was `npm i drizzle-orm @neondatabase/serverless` — Drizzle had its own PostgreSQL driver (`@neondatabase/serverless`, equivalent to `pg`). Prisma has a **built-in driver system** (uses Node.js drivers internally — `pg` for PostgreSQL). There's no explicit driver in your package.json — it's bundled inside Prisma. Both do the same job.

## Step 2 — Define Schema

**CONCEPT:** Prisma uses a **schema-first approach** — first write the database structure in `schema.prisma`, then generate the actual database via migration. This matches Drizzle (6.10's SQL blueprint) — the schema is the database blueprint. This is the implementation of 6.13.1's plan (User/Board/Task models, 1:N relations).

**File:** `prisma/schema.prisma`

Now define the models — **User, Board, Task** — the data shape from 6.13.1:

```prisma
// prisma/schema.prisma
model User {
  id     Int     @id @default(autoincrement())
  name   String
  boards Board[]
}

model Board {
  id        Int      @id @default(autoincrement())
  name      String
  createdAt DateTime @default(now())
  userId    Int
  user      User     @relation(fields: [userId], references: [id])
  tasks     Task[]
}

model Task {
  id          Int      @id @default(autoincrement())
  title       String
  description String?
  status      TaskStatus @default(BACKLOG)
  order       Int
  boardId     Int
  board       Board    @relation(fields: [boardId], references: [id])
}

enum TaskStatus {
  BACKLOG
  IN_PROGRESS
  DONE
}
```

**`model User`** — `id` (primary key `@id`), `name`, `boards` (relation — 1 User → N Boards).

**`model Board`** — `name`, `createdAt` (`@default(now())` — auto-timestamped), `userId` + `@relation(fields: [userId], references: [id])` — **foreign key (6.12)** — linked to User, plus `tasks` relation — 1 Board → N Tasks.

**`model Task`** — `title`, `description String?` (optional — 6.13.1's `String?`), `status TaskStatus` (enum — `@default(BACKLOG)` — new tasks start in backlog), `order` (sorting — 6.13.1's Question 3), `boardId` + `@relation` (linked to Board).

**`enum TaskStatus`** — BACKLOG / IN_PROGRESS / DONE — 6.13.1's enum. This is like a TypeScript enum — values are uppercase (convention) — the UI will map them to labels.

**Schema walkthrough — every keyword explained:**

- **`@id`** — primary key — unique identifier — identifies each row. Drizzle had `primaryKey()` — Prisma uses `@id`.
- **`@default(autoincrement())`** — the ID auto-increments — 1, 2, 3... — don't set it manually. Drizzle had `serial(...).primaryKey()` (auto-increment in PostgreSQL).
- **`String?`** — the `?` means optional — description may or may not exist — Drizzle had `.optional()`.
- **`@default(now())`** — if `createdAt` isn't provided, use the current time — timestamp.
- **`@relation(fields: [userId], references: [id])`** — **foreign key definition (6.12)** — `userId` references `User.id` — creates the relation. `fields` = local column, `references` = target column.

> **Thinking point:** The relation syntax (`user: User @relation(...)`) expresses two things — the **column** (`userId: Int` — the actual database column) and the **relation** (`user: User` — the typed navigation). Both are needed together — for a relation you need the field AND the relation object.

## Step 3 — Connect the Database (PostgreSQL / Neon)

This is the exact same pattern from 6.9 — Neon + `DATABASE_URL` env var. Prisma also connects via environment variable. **File:** `.env` (project root)

```
DATABASE_URL="postgresql://...neon.tech?sslmode=require"
```

Add a `datasource` block to the schema — tell Prisma to use PostgreSQL:

```prisma
// prisma/schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User { ... }
```

**`generator client`** — when you migrate/generate, Prisma generates the client (with TypeScript types).

**`datasource db`** — `provider = "postgresql"`, `url = env("DATABASE_URL")` — same as 6.9's Neon. `env(...)` reads `process.env.DATABASE_URL` from the schema file.

> **Same as 6.9** but with Prisma instead of Drizzle. Both use PostgreSQL, both are Neon-compatible, both use migrations (`db push` is the alternative).

## Step 4 — Migrate — From Schema to Database

**CONCEPT (migration refresher 6.10):** A migration is a historical record of the database — every schema change generates a migration file that team members use to update their database. Both Drizzle and Prisma follow this pattern. `migrate dev` is for development — it updates both the database and the client.

Run the migration:

```bash
npx prisma migrate dev --name init
```

**`--name init`** — the name of the migration file — `init` means first migration. Prisma creates `prisma/migrations/2024xxxxx_init/` with a SQL file containing `CREATE TABLE` statements, and applies it to the database (Neon).

**What happens inside a migration:**

1. The schema file is parsed
2. A SQL migration file is generated (`CREATE TABLE USER, BOARD, TASK, etc.`)
3. It's applied to the database (Neon) — tables get created
4. `@prisma/client` is regenerated — you get **TypeScript types** (`Board`, `Task`, `TaskStatus`)

> **Note:** If `DATABASE_URL` is wrong or the Neon project was deleted, the migration fails — double-check `.env`. Use 6.9's same Neon URL.

## Step 5 — Client Singleton

**CONCEPT:** Keep the Prisma client as a singleton — if you create `new PrismaClient()` on every request, connections leak — even on hot reload. Use the **global singleton pattern** — the same pattern works across every framework.

**File:** `lib/prisma.ts`

```ts
// lib/prisma.ts
import { PrismaClient } from '@prisma/client'

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined
}

export const prisma = globalForPrisma.prisma ?? new PrismaClient()

if (process.env.NODE_ENV !== 'production') globalForPrisma.prisma = prisma
```

**`globalForPrisma`** — store the Prisma instance on global `this` — no new instance on hot reload.

**`?? new PrismaClient()`** — if it's not on global yet, create one.

**`if (process.env.NODE_ENV !== 'production')`** — only store on global during development — production (serverless — 6.9 Neon) uses a different pattern, but this standard pattern works everywhere.

> **Same concept as Drizzle** (6.10 exported a `db` singleton) — both do the same thing. Prisma's official docs use this exact pattern.

## Nutshell

Prisma data layer: `npm i -D prisma` + `npm i @prisma/client` (CLI vs runtime). Define `User`/`Board`/`Task` models + relations (1:N, foreign keys via `@relation`) + `TaskStatus` enum in `prisma/schema.prisma`. `.env` provides `DATABASE_URL` (Neon — 6.9 pattern), with a `datasource db` block. `npx prisma migrate dev --name init` generates the SQL migration + applies it to Neon + regenerates the client (TypeScript types). `lib/prisma.ts` exports a global singleton — prevents connection leaks. This is 6.9's schema-first + migration pattern, now in Prisma syntax.

## What It Is NOT

- **Prisma client = "no runtime dependency needed"** is false. `@prisma/client` is a runtime dependency — your code imports it. `prisma` is dev-only (CLI — migrate/studio/generate). Install both, they have different roles.
- **Enum values = "case-insensitive"** is false. `BACKLOG` is defined uppercase (convention), and TypeScript is strict — you must write `BACKLOG`, not `Backlog`. Mapping to UI labels (e.g., "Backlog") is up to you.
- **`@relation` without the column** is not valid. You need both `userId Int` (the column) and `user: User @relation(fields: [userId], references: [id])` (the typed relation). The column stores the value; `@relation` gives Prisma typed navigation. One without the other doesn't work.
- **Migrate = "schema sync"** is false. Migration *maintains history* — each migration is a versioned file. `db push` force-overwrites schema to database (dev-only). Migrations enable team collaboration — every schema change is a migration.
- **Studio = "production database view"** is false. Studio is a local/dev GUI — it can read and write. Don't use it in sensitive environments — just for local debugging.

**In Your Own Words**

1. Why are `npm i -D prisma` and `npm i @prisma/client` two separate packages with different roles?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `prisma` is the **CLI tool** (migrate, studio, generate) — needed at **build/dev time only** — installed as a dev dependency (`-D`). `@prisma/client` is the **generated client library** — needed at **runtime** — your code imports it: `import { PrismaClient } from '@prisma/client'`. Production deployments need `@prisma/client` (running server), not `prisma` (the CLI only runs during build).

</details>

2. What's the difference between the `@relation` field and the column it references? Why are both needed?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `userId Int` is the **actual database column** (the foreign key value stored). `user: User @relation(fields: [userId], references: [id])` is the **typed relation** — `@relation(fields:...)` links the column to its target (`references: [id]`), and `user: User` is the relation field for code navigation. Both are needed: the column (`userId`) stores the value so it persists in the DB, and `@relation` gives Prisma the typed navigation so `prisma.board.findUnique({ include: { user: true } })` works. Without the column, nothing is stored; without `@relation`, Prisma has no typed relation.

</details>

3. Why does Prisma use a global singleton for the client? What problem does it solve?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Each `new PrismaClient()` opens database connections — on hot reload (development), multiple client instances would be created, leaking **connections** (too many open, server rejects new ones). The global singleton pattern (`globalThis.prisma ?? new PrismaClient()`) reuses one instance across reloads — the client is set on first render, and subsequent renders find it on `globalThis`. Production (serverless — 6.9 Neon) handles this differently (single connection per instance), but the singleton pattern is standard practice and works everywhere.

</details>

4. In a migration, what happens in the 4 steps when we run `prisma migrate dev --name init`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** 1. The `schema.prisma` is parsed into Prisma's internal data model. 2. Prisma generates a **SQL migration file** (`prisma/migrations/..._init/migration.sql`) with `CREATE TABLE` statements — this file is the **history record**. 3. The SQL is applied to the database (Neon) — tables get created. 4. The Prisma Client is **regenerated** with TypeScript types from the schema — so `Board`, `Task`, `TaskStatus` are auto-typed.

</details>

5. How does `String?` in the Prisma schema connect to 6.13.2's UI logic `{task.description && <small>...</small>}`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `String?` means the description is optional — a task may or may not have one. At the type level, `description` becomes `string | null`. In 6.13.2, `{task.description && }` handled that case — when the DB returns `description: null` (no description), the `&&` short-circuits and only the title renders. So the schema's `String?` flows directly to the UI's conditional render — the same field, from DB to UI, fully consistent.

</details>
