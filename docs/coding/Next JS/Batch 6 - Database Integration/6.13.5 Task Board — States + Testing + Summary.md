## Where We Left Off

## Step 1 — States: Loading, Error, and 404 (NotFound)

### Loading (Server Component Loading State)

In 6.13.2, the hardcoded UI showed data instantly. With a real database query (`await prisma.board.findUnique(...)`), there is a delay — the page must wait for the server response. During that delay, a loading indicator keeps the user informed.

In Next.js, since 6.13.4's pages are async Server Components awaiting data, two patterns exist: the `loading.tsx` convention (file-based) and the `React Suspense` boundary — both pause rendering and show a fallback. 

#### The `loading.tsx` Convention

Next.js has a special file — `loading.tsx` — that Next shows automatically while a sibling `page.tsx` is awaiting data. If `app/board/[id]/loading.tsx` exists, Next renders it until `page.tsx` finishes its async work. 

File: `app/board/[id]/loading.tsx`

```tsx
export default function Loading() {
  return <div>Loading board...</div>
}
```

No special wrapper needed — Next detects the `loading.tsx` file. This is built-in to Next's routing.

#### React Suspense (Alternative)

```tsx
import { Suspense } from 'react';

<Suspense fallback={<p>Loading board...</p>}>
  <BoardDetail />
</Suspense>
```

Suspense pauses the render tree until `<BoardDetail />` (the slow component) finishes — shows `fallback` meanwhile. This is the more granular control option.

### Error Boundary

When a Server Component throws (e.g., Prisma query fails), the entire request fails — without a boundary, the user sees a blank page or a crash. The `error.tsx` convention wraps the route: if any component in the route throws, Next catches it and renders `error.tsx` instead of crashing.

File: `app/board/[id]/error.tsx`

```tsx
'use client'; // Error boundaries must be client components — hooks require it
import { useEffect } from 'react';

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    console.error(error); // Log to monitoring service (Sentry, LogRocket)
  }, [error]);

  return (
    <p>
      Something went wrong — please try again.
      <button onClick={() => reset()}>Retry</button>
    </p>
  );
}
```

#### Key: `'use client'` is mandatory

Unlike `loading.tsx` and `page.tsx` — `error.tsx` **must** be marked `'use client'`. The reason: it uses `useEffect` (hooks must be client components) and the `reset()` function needs event handlers (`onClick` — also client-side). React calls this an **error boundary** — it lives on the client side so it can recover and re-render.

#### Logging to a service

The `error` object should be sent to an error tracking service — `console.error(error)` is just the placeholder. In production, replace it with the service's SDK call:

- **Vercel** — built-in (no config needed — errors auto-report in the dashboard).
- **Other hosts** — add Sentry or LogRocket SDK, replace `console.error` with `Sentry.captureException(error)`.

### 404 (NotFound Handler)

When `prisma.board.findUnique` returns `null` (invalid id — route `/board/999` with no matching board), the page must not crash or render empty — it must show the 404 page.

File: `app/board/[id]/page.tsx`

```tsx
import { notFound } from 'next/navigation';
import { prisma } from '@/lib/prisma';

async function getBoard(id: string) {
  return await prisma.board.findUnique({
    where: { id: Number(id) },
    include: { tasks: true },
  });
}

export default async function BoardPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const board = await getBoard(id);

  if (!board) {
    notFound(); // Shows the 404 page — built into Next
  }

  // ...render with board and board.tasks
}
```

- `notFound()` — imported from `next/navigation` — triggers Next's 404 page automatically (built-in `app/not-found.tsx`).
- The null check (`if (!board)`) is required because `findUnique` returns `Board | null` — TypeScript enforces this check.

## Step 2 — Testing the Data Layer

### Why Mock the Database? The `prisma` Test Problem

When tests call `prisma.board.create()`, they hit the real database — tests become slow, flaky, and need a database URL. The solution: **mock Prisma** so tests use fake data — fast and deterministic.

The tool: `jest-mock-extended` — generates a mock client where every method (`findMany`, `create`, `update`, `delete`) is a spy you can control:

```bash
npm i jest
npm i jest-environment-jsdom
npm i -D jest-mock-extended
```

### Pattern (File Structure)

The key insight: the server actions from 6.13.4 **import `prisma` as a named import from `@/lib/prisma`** — the exact same import. Tests mock **that module's `prisma`** so when the action calls `prisma.board.create()`, it hits the mock, not the DB:

| File | Role |
|---|---|
| `app/actions.ts` | Imports `prisma` from `@/lib/prisma` |
| `lib/prisma.ts` | Exports the real PrismaClient — **mocked in tests** |
| `app/actions.test.ts` | Imports prisma mock + action, asserts calls |

### Code (Server Action — from 6.13.4)

```ts
// app/actions.ts
'use server';
import { prisma } from '@/lib/prisma';

export async function createBoard(formData: FormData) {
  const name = formData.get('name') as string;
  await prisma.board.create({ data: { name, userId: 1 } });
}
```

### Code (Test File)

```ts
// app/actions.test.ts
import { mockDeep, mockReset } from 'jest-mock-extended';
import { prisma } from '@/lib/prisma';
import { createBoard } from './actions';

// Mock the prisma module — every method is a spy
jest.mock('@/lib/prisma', () => ({
  __esModule: true,
  prisma: mockDeep<typeof prisma>(),
}));

const mockedPrisma = prisma as unknown as jest.Mocked<typeof prisma>;

// After each test, reset the mock — clean slate (no calls carry over)
beforeEach(() => mockReset(mockedPrisma));

test('createBoard calls prisma with the name and userId', async () => {
  const formData = new FormData();
  formData.append('name', 'My Board');

  await createBoard(formData);

  expect(mockedPrisma.board.create).toHaveBeenCalledWith({
    data: { name: 'My Board', userId: 1 },
  });
});
```

### Breakdown — Every Line Explained

- `mockDeep<typeof prisma>()` — auto-generates a typed mock where every Prisma method is a Jest spy — fully typed (knows `board.create` exists).
- `jest.mock('@/lib/prisma', ...)` — the setup — replaces the module globally for this test file — **the action still does `import { prisma } from '@/lib/prisma'`** (unchanged) — Jest intercepts that import here.
- `mockedPrisma` — the typed mock instance — what assertions run against.
- `beforeEach(() => mockReset(...))` — clears all mock call history between tests — prevents false positives.
- `mockedPrisma.board.create.toHaveBeenCalledWith(...)` — the assertion — verifies the server action passed the correct object.

### Integration Tests (End-to-End)

For **integration tests** (the full flow — does the page actually render with data?): tools and when to use them:

- **Playwright** — full browser automation (headless Chrome) — real clicks, form submits, navigation. Catches integration issues Jest + mocks would miss (e.g., form doesn't connect to the action).
- **Vitest + React Testing Library** — lighter — renders components with mocked data (no full browser). Better for testing the UI layer + mocked Prisma.

#### Playwright Example — Full Board Flow

```bash
npm i -D @playwright/test
npx playwright test
```

Test file: `e2e/board-flow.spec.ts`

```ts
import { test, expect } from '@playwright/test';

test('full board flow — create board, add task, move, delete', async ({ page }) => {
  await page.goto('/');
  await page.getByPlaceholder('New board...').fill('Test Board');
  await page.getByText('Create Board').click();
  // ...assertions + task interactions
});
```

#### When to use what:

| Test Type | Tool | Use Case | Speed |
|---|---|---|---|
| Unit (server logic) | Jest + jest-mock-extended | Verify action calls prisma correctly with right args | Fast (ms) |
| Integration / UI | Vitest + RTL | Component renders correctly with mocked data | Medium |
| E2E flow | Playwright | Full flow: real database, real browser, user journey | Slowest (s) |

The database for E2E tests must be **separate** — a test database URL in `.env.test` — never production/staging credentials in tests.

### The Production Pattern (Task Board)

The full cycle one last time:

```
[User clicks "Move Task to Done"]
  ↓ (formAction={moveTask})
Server: moveTask(taskId, boardId, newStatus)
  ├─ prisma.task.update(...)     ← database write
  └─ revalidatePath('/board/1')  ← cache invalidation
  ↓ (page re-renders on next visit)
[Server Component re-fetches: prisma.board.findUnique({ include: tasks })]
  ↓
[Browser re-renders: task now in Done column]
```

No client-side fetch. No `useState` for the list. No manual cache busting. The framework handles the data flow through **Server Component + Server Action + revalidation** — and the database is the single source of truth, queried on the server.

## Nutshell

States: handle loading (built-in `loading.tsx` + `Suspense` fallback), error boundary (`error.tsx` — must be `'use client'`), and 404 (`notFound()` for invalid ids). Testing strategy — **two layers** — Jest + `jest-mock-extended` for server actions (mock prisma, assert args) and Playwright for E2E (real browser + real DB flow). The full batch recap — SQL vs NoSQL → REST (Mongo) → SC + SA (Drizzle/Prisma) → system design → Task Board capstone. The production pattern: user action → server action mutates DB → revalidatePath → page re-renders. Database is the single source of truth, no client state needed.

## What It Is NOT

- **`error.tsx` = "must be server component"** is not true — it **must be `'use client'`** because it uses `useEffect` and `reset()`.
- **Loading states = "useEffect + useState"** is not true — `loading.tsx` (file-based) and `React.Suspense` (component wrapper) handle this **automatically** — no manual state needed.
- **404 = "custom logic"** is not true — `notFound()` is a Next function that triggers the built-in 404 page — no custom page needed (just `app/not-found.tsx` optionally).
- **Mocking = "complex setup"** is not true — `jest.mock` replaces the module — the server action code doesn't change — only the import resolves to the mock at test runtime.
- **Playwright = "fast"** is not true — it launches a real browser (`npx playwright install` → headless Chromium) — slowest tier (~seconds), but catches integration issues Jest + mocks can't.
- **E2E tests hit the production database** is not true — use a separate test DB (`.env.local` / `.env.test`) — never production credentials in tests.

**In Your Own Words**

1. Why must `error.tsx` be a client component (`'use client'`) while `loading.tsx` and `page.tsx` are server components?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `error.tsx` uses `useEffect` (needs a client component — hooks can't run in server components) and the `reset()` function requires an event handler (`onClick` — also client-only). React calls this an "error boundary" and it lives on the client so it can recover and re-render after an error. `loading.tsx` and `page.tsx` don't use hooks (they're rendering/data-fetching logic) — so they stay server components.

</details>

2. How does mocking work — the server action still does `import { prisma } from '@/lib/prisma'`, but doesn't touch the real DB. How?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The server action's import is **unchanged** (`import { prisma } from '@/lib/prisma'`). In the test file, `jest.mock('@/lib/prisma', ...)` tells Jest — replace that entire module with a mock. So when the action runs `import { prisma }`, Jest **intercepts the import** and gives the mock object instead of the real `PrismaClient`. The action calls `prisma.board.create()` — which hits the mock spy, not the database. The production code stays clean — only the test changes the import resolution.

</details>

3. What's the difference between a unit test (Jest) and an E2E test (Playwright) — when to use each?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Unit (Jest) — mocks Prisma, tests the server action in isolation — "did the call to `prisma.board.create` happen with correct args?" Fast (ms), deterministic. E2E (Playwright) — no mocks, real browser + real database — "can a user actually create a board, add tasks, and see them move?" Slow (s), catches integration bugs. Unit for logic, E2E for the flow — both needed.

</details>

4. Trace the production pattern: when a user clicks "Move to Done", describe what happens step by step with no client-side fetch.

<details>
<summary>Show Answer</summary>

**Sample Answer:** 1. The button (with `formAction={moveTask}`) submits — no JavaScript, regular form POST. 2. Server runs `moveTask` — reads taskId/boardId, calls `prisma.task.update` — writes to database (Neon). 3. Calls `revalidatePath('/board/1')` — marks the page's cache as stale. 4. On the next page load, the Server Component re-runs `prisma.board.findUnique` — fresh data from DB. 5. The browser receives new render HTML (server-rendered, with the task now in Done) — no client fetch, no `useState`, no manual refetch. The database was the single source of truth throughout.

</details>
