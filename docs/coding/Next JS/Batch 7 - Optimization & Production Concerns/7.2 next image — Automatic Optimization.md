# next/image — Automatic Image Optimization

## THINK — What "Better" Really Means

Recall the problems from 7.1:

1. **No optimization** — every screen downloads the full file
2. **Layout shift (CLS)** — no dimensions means text jumps
3. **srcset must be managed manually** — different sizes need different files
4. **Lazy loading has limits** — without dimensions, lazy makes shift worse

What if there were a **component** that: automatically optimizes the image, manages dimensions itself, generates responsive versions for you, and handles lazy loading too? That's exactly `next/image` — a component imported from `next/image`. Use `<Image>` instead of `<img>`, and Next.js handles the rest.

## CONCEPT — How `next/image` Works

`next/image` is not just a "better `<img>`." There's real machinery under the hood — it's an **Image Optimization API**:

- **Request-time optimization** — when the browser requests an image, Next.js generates an optimized version on the server (right width for the screen, modern format like WebP/AVIF). What the client receives is a **small, optimized file** — never the bloated original.
- **Automatic srcset** — Next.js generates multiple sizes and injects the `srcset` attribute for you. You never need to create different files manually.
- **Layout shift control** — with `width`/`height` or `fill`, the browser knows the dimensions upfront. No CLS.
- **Lazy loading by default** — `Image` has `loading="lazy"` built in (loads when near the viewport), and because dimensions are known, the shift doesn't happen.
- **Priority** — the image at the very top of the page (the LCP image) can use the `priority` prop to preload.

One line: **`next/image` generates an optimized image on the server, produces the right srcset, and renders shift-free + lazy on the client.**

## Step 0 — Where Images Come From (Download + Dimensions)

The examples above use `/photos/cat.jpg`, `/photos/dog.jpg`, `/photos/bird.jpg` — **you add those files yourself.** Create a `public/photos/` folder (the `public/` folder already exists) and drop in 3 **landscape** images. Easiest source — **picsum.photos** (a placeholder image service) — you can put a size right in the URL:

```
https://picsum.photos/seed/cat/800/600   → save as public/photos/cat.jpg
https://picsum.photos/seed/dog/800/600   → save as public/photos/dog.jpg
https://picsum.photos/seed/bird/800/600  → save as public/photos/bird.jpg
```

The `seed/cat` part makes it deterministic — **the same seed gives you the same image** (it doesn't change every time). Open the URL in a browser → the image appears → right-click → "Save image as..." → save as `cat.jpg`, `dog.jpg`, `bird.jpg` in `public/photos/`.

**Where do dimensions come from?** The `800/600` in the URL is the image's **actual size**. So below, the array uses `width: 800, height: 600` — **exact values, not guesses.** (If you use your own image, on Windows right-click → Properties → Details to check the real width/height, then update the array.) The `width`/`height` need to match the **actual aspect ratio** — wrong values make `next/image` warn and reserve the wrong space (causing CLS).

## CODE — First Step: `<img>` → `<Image>`

Take the 7.1 gallery and swap `<img>` for `<Image>`:

**File:** `app/gallery/page.tsx`

**Concept:** Each photo card has a fixed-height cell (`h-40 w-full`) — the image should fill the cell — use the **`fill`** pattern (same as 7.2). A `relative` parent is required. The `sizes` prop tells the browser how wide the image will be (enables srcset optimization):

**File:** `app/gallery/page.tsx` — step by step.

First, the import — **`import Image from "next/image"`** — the `Image` component from `next/image` (7.2):

```tsx
// app/gallery/page.tsx
import Image from "next/image";

const photos = [
  { id: 1, src: "/photos/cat.jpg", alt: "Cat sleeping", width: 800, height: 600 },
  { id: 2, src: "/photos/dog.jpg", alt: "Dog running", width: 800, height: 600 },
  { id: 3, src: "/photos/bird.jpg", alt: "Bird flying", width: 800, height: 600 },
];
```

**`import Image from "next/image"`** — the `Image` component (7.2).

Now the JSX — `<img>` → `<Image>` with **`fill`** — the image fills its parent (the cell, `h-40 w-full`). **`className="object-cover"`** — crop. **`sizes="(max-width: 768px) 400px, 1600px"`** — responsive widths (the browser uses this to optimize srcset). Add `relative` to the parent:

```tsx
// app/gallery/page.tsx
import Image from "next/image";

const photos = [
  { id: 1, src: "/photos/cat.jpg", alt: "Cat sleeping", width: 800, height: 600 },
  { id: 2, src: "/photos/dog.jpg", alt: "Dog running", width: 800, height: 600 },
  { id: 3, src: "/photos/bird.jpg", alt: "Bird flying", width: 800, height: 600 },
];

export default function GalleryPage() {
  return (
    <div className="grid grid-cols-3 gap-4">
      {photos.map((photo) => (
        <div key={photo.id} className="relative h-40 w-full">
          <Image
            src={photo.src}
            alt={photo.alt}
            fill
            sizes="(max-width: 768px) 400px, 1600px"
            className="object-cover"
          />
        </div>
      ))}
    </div>
  );
}
```

**`<Image fill ...>`** — the image fills the parent cell. `sizes` — responsive width hint for srcset optimization. `className="object-cover"` — crop. The parent `relative h-40 w-full` reserves the space (CLS prevention from 7.1's Problem 2). `key={photo.id}` — React list requirement.

> **Important — first run will error:** "Image with src /photos/cat.jpg has either width or height modified, but not the other..." or "width/height not specified." This is by design — Next.js **forces you to prevent layout shift.** Fix: either provide `width`/`height`, or use `fill`.

### Local vs Remote Images — `fill` + `remotePatterns`

Above, images are in the `/public` folder (local). Two cases:

**1. Local images (public folder):**

```tsx
<Image
  src="/photos/cat.jpg"
  alt="Cat sleeping"
  width={800}
  height={600}
/>
```

**2. Remote images (from a URL like Unsplash):** Now Next.js needs to know **which domains are allowed** — a **security feature**. Configure in `next.config.ts`:

```ts
// next.config.ts
const nextConfig = {
  images: {
    remotePatterns: [
      {
        protocol: "https",
        hostname: "images.unsplash.com",
      },
    ],
  },
};

export default nextConfig;
```

**`remotePatterns`** — an allowlist — Next.js will only fetch and optimize from this domain. Any random domain is blocked. (We use this in 7.7.4 for the Photo Gallery.)

**3. `fill` — when you don't know the dimensions:**

```tsx
<div className="relative h-40 w-full">
  <Image
    src="/photos/cat.jpg"
    alt="Cat sleeping"
    fill
    className="object-cover"
  />
</div>
```

**`fill`** — the image stretches to fill its parent. The parent needs `relative`. The parent's size reserves the space — no CLS (`object-cover` crops).

## Nutshell

`next/image` (`Image` component) solves all four problems from 7.1: **server-side automatic optimization** (right width, modern WebP/AVIF), **automatic srcset** (multiple sizes generated), **`width`/`height` or `fill` prevent layout shift**, and **default lazy loading** that's shift-safe. Remote images need a `remotePatterns` allowlist. `<img>` is manual, `next/image` is better — that's the roadmap pattern.

## What It Is NOT

- **`next/image` is not just "a wrapper component."** There's real machinery — server-side optimization, image pipeline, srcset generation. It's not just renaming `<img>`.
- **`next/image` is not "CSS shrink-to-fit."** CSS only changes how the image *appears*. `next/image` optimizes the actual downloaded file.
- **`width`/`height` is not "hardcoded dimensions."** These exist so the browser can reserve layout space (aspect ratio) — CSS overrides are fine (`w-full`, `h-40`). It's about reservation, not styling.
- **`fill` is not a hack.** It's the **designed pattern** when image dimensions are unknown (remote URLs). The parent's size becomes the layout reservation — which prevents CLS. `relative` is required so `fill` can position absolutely.
- **`remotePatterns` is not "allow any URL."** It's a security allowlist — only `images.unsplash.com` is allowed. Any other domain throws an error until added. Intentional — external images aren't trusted by default.

**In Your Own Words**

1. What does it mean for `next/image` to "optimize" an image — and how much bandwidth difference does it make?

<details>
<summary>Show Answer</summary>

**Sample Answer:** When the browser requests an image, Next.js generates an optimized version on the server — right width for the screen + modern format (WebP/AVIF). Instead of downloading an 800KB original, the client gets a ~30KB optimized file. The bandwidth savings are huge — same image, much smaller file, much faster page.

</details>

2. Why are `width` + `height` (or `fill`) necessary with `next/image` — what breaks without them?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The browser needs to reserve layout space before the image loads — `width`/`height` (or `fill` + a sized parent) gives it those dimensions. Without them, Next.js throws an error (by design) and layout shift happens — exactly Problem 2 from 7.1. These dimensions are about layout reservation, not final visual styling.

</details>

3. Why must a remote image like Unsplash be added to `remotePatterns` — what happens without it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `remotePatterns` is a security allowlist — Next.js only fetches and optimizes from listed domains. Without it, a remote image throws an error ("hostname is not configured"). It prevents any random external image from being optimized through your server — you explicitly trust each domain.

</details>

4. When is `fill` used instead of `width`/`height`, and why does the parent need `relative`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `fill` is used when you don't know the image's exact dimensions (remote URLs, dynamic sizes) but you do know the container's size — the image fills the parent. The parent needs `relative` so that `fill` (which uses `position: absolute` internally) is positioned relative to that container. Without `relative`, the image doesn't know what to fill.

</details>

5. In the before/after test, ~70-80% smaller files — how is that reduction actually achieved?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `next/image` optimizes on request — re-encoding the image to a modern format (WebP/AVIF), resizing to the requested width (from `sizes`), and compressing at the right quality. An 800px-wide original becomes a 200px thumbnail in WebP — drastically smaller. The browser still gets a sharp, correctly-sized image, just as a much smaller file.

</details>
