# Photo Gallery — Part 4: next/image + next/font

## Step 1 — next/font: Inter, Project-Wide

**THINK (7.4):** The font is still the default — no brand personality. Add **Inter** — but **not** the manual Google Fonts `<link>` (7.3's problems). Use `next/font` — self-hosted, preloaded, zero layout shift.

**File:** `app/layout.tsx`

**Concept (7.4 pattern):** `Inter` from `next/font/google`, with `subsets: ["latin"]` (only needed characters — smaller file), `variable: "--font-inter"` (expose as CSS variable on `<html>`). Then in CSS, `font-family: var(--font-inter)`.

**File:** `app/layout.tsx` — step by step.

First, import + configure — **`import { Inter } from "next/font/google"`** — Inter from Next.js's Google Fonts collection. **`const inter = Inter({ subsets: ["latin"], variable: "--font-inter" })`** — latin subset (smaller) + expose as CSS variable:

```tsx
// app/layout.tsx
import Link from "next/link";
import { Inter } from "next/font/google";
import "./globals.css";

const inter = Inter({ subsets: ["latin"], variable: "--font-inter" });
```

**`import { Inter } from "next/font/google"`** — Inter (same pattern as 7.4). **`const inter = Inter({ subsets: ["latin"], variable: "--font-inter" })`** — latin subset + CSS variable.

Now apply on `<html>` — **`<html className={inter.variable}>`** (7.4's pattern):

```tsx
// app/layout.tsx
import Link from "next/link";
import { Inter } from "next/font/google";
import "./globals.css";

const inter = Inter({ subsets: ["latin"], variable: "--font-inter" });

export default function RootLayout({
  children,
}: Readonly<{ children: React.ReactNode }>) {
  return (
    <html lang="en" className={inter.variable}>
      <body>
        <header className="border-b p-4">
          <Link href="/" className="text-lg font-semibold">
            Photo Gallery
          </Link>
        </header>
        <main className="mx-auto max-w-4xl p-4">{children}</main>
      </body>
    </html>
  );
}
```

**`<html className={inter.variable}>`** — the CSS variable is available across the whole app. Then apply it in CSS:

**File:** `app/globals.css`

```css
/* app/globals.css */
body {
  font-family: var(--font-inter), Arial, sans-serif;
}
```

**`font-family: var(--font-inter)`** — the self-hosted Inter. **`, Arial, sans-serif`** — fallback (already adjusted by `next/font` — no layout shift, 7.4).

**TEST:** `npm run dev` → Inter font appears (subtle visual change, cleaner look). Network tab → Font filter → Inter loads from **your own server** (`/_next/static/media/...`), not Google's CDN.

## Step 2 — next/image: Remote Image Config

**THINK (7.2):** The photos come from **Unsplash (remote URLs)** — `next/image` won't fetch them without an allowlist. Configure `remotePatterns`.

**File:** `next.config.ts`

**Concept (7.2):** `remotePatterns` is a security allowlist — Next.js only optimizes images from listed domains. Without it, Unsplash images throw an error.

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  images: {
    remotePatterns: [
      {
        protocol: "https",
        hostname: "images.unsplash.com",
      },
    ],
  },
};

export default nextConfig;
```

**`remotePatterns`** — allowlist — Next.js fetches + optimizes only from `images.unsplash.com`. Any other domain is blocked until explicitly added.

```tsx

```

**`import Image from "next/image"`** — the `Image` component (7.2).

Now the JSX — `<img>` → `<Image fill>` — the image fills the card. The card gets `relative` (7.2 pattern). `sizes` tells the browser the width:

```tsx
// app/page.tsx
import Image from "next/image";
import Link from "next/link";
import prisma from "@/lib/prisma";

export default async function Home() {
  const photos = await prisma.photo.findMany();

  return (
    <section>
      <h1 className="text-2xl font-bold">Photo Gallery</h1>
      <p className="text-zinc-600">A showcase of curated photography.</p>

      <div className="mt-6 grid grid-cols-3 gap-4">
        {photos.map((photo) => (
          <Link
            key={photo.id}
            href={`/photo/${photo.id}`}
            className="relative block h-40"
          >
            <Image
              src={photo.src}
              alt={photo.alt}
              fill
              sizes="(max-width: 768px) 100vw, 33vw"
              className="rounded object-cover"
            />
            <p className="mt-1 text-sm font-medium">{photo.title}</p>
          </Link>
        ))}
      </div>
    </section>
  );
}
```

**`<Image fill ...>`** — the image fills the parent card. The `Link` card gets `relative block h-40` — the size reservation (prevents CLS). `sizes="(max-width: 768px) 100vw, 33vw"` — mobile gets full width, desktop gets ~1/3 (grid). `className="rounded object-cover"` — crop + border radius.

**File:** `app/photo/[id]/page.tsx` — detail

**Concept:** The detail page shows a large image — not a fixed-height card. Use a sized **container** (`relative h-96 w-full`) with `fill` — the container reserves the space (CLS-free), the image fills and crops:

```tsx
// app/photo/[id]/page.tsx
import type { Metadata } from "next";
import Image from "next/image";
import Link from "next/link";
import { notFound } from "next/navigation";
import prisma from "@/lib/prisma";

async function getPhoto(id: number) {
  return prisma.photo.findUnique({ where: { id } });
}

export async function generateMetadata({
  params,
}: {
  params: Promise<{ id: string }>;
}): Promise<Metadata> {
  const { id } = await params;
  const photo = await getPhoto(Number(id));

  if (!photo) {
    return { title: "Photo Not Found" };
  }

  return {
    title: photo.title,
    description: photo.description ?? photo.alt,
  };
}

export default async function PhotoPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const photo = await getPhoto(Number(id));

  if (!photo) {
    notFound();
  }

  return (
    <section>
      <Link href="/" className="text-sm text-zinc-500">
        &larr; Back to gallery
      </Link>

      <div className="relative mt-4 h-96 w-full">
        <Image
          src={photo.src}
          alt={photo.alt}
          fill
          sizes="(max-width: 768px) 100vw, 700px"
          className="rounded-lg object-cover"
        />
      </div>
      <h1 className="mt-4 text-2xl font-bold">{photo.title}</h1>
      <p className="mt-1 text-zinc-600">{photo.description}</p>
    </section>
  );
}
```

**`<div className="relative mt-4 h-96 w-full">`** — the detail image container — `relative` (for `fill`) + `h-96` (fixed height — reserves space, no CLS). **`<Image fill sizes="...700px">`** — fills the container, max ~700px wide on desktop. `object-cover` crops. The `generateMetadata` + data fetch are **unchanged** — only the image got optimized.

## Nutshell

Optimization applied: `next/font/google` for Inter — `variable: "--font-inter"` on `<html>`, `font-family: var(--font-inter)` in CSS — self-hosted, no CLS. `next/image` — `remotePatterns` (Unsplash) configured, then `<Image fill>` on the grid (`sizes="(max-width: 768px) 100vw, 33vw"`, parent `relative h-40`) and on the detail page (`sizes="...(max-width: 768px) 100vw, 700px"`, parent `relative h-96`). ## What It Is NOT

- **`<Image fill>` is not just "an `<img>` rename."** `next/image` optimizes on the server, generates srcset, controls layout shift. It's the real machinery from 7.2, not a tag swap.
- **`fill` + `relative` container is not a hack.** It's `next/image`'s designed pattern when exact dimensions are unknown (remote URLs). The parent's size becomes layout reservation — which prevents CLS.
- **`sizes` is not "optional."** It tells the browser how wide the image renders — Next.js uses it to serve the right file size. Wrong `sizes` = downloading a large image for a small slot = wasted bandwidth.
- **`remotePatterns` is not "allow any URL."** Security allowlist — only `images.unsplash.com` is permitted. Any other domain errors until added.
- **Self-hosting fonts is not "slower than CDN."** Your server serves the font directly — no external latency or downtime risk. A third-party CDN is outside your control.

**In Your Own Words**

1. Grid cards use `<Image fill>` but what does the parent container need, and why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `fill` makes the image stretch to fill its **parent** — so the parent must have a defined size and `relative` positioning. The grid card sets `relative block h-40` — `h-40` reserves the height (no CLS), `relative` lets `fill` position the image correctly. Without a sized parent, `fill` has nothing to fill and can collapse.

</details>

2. How does the `sizes` prop determine which image file the browser downloads?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `sizes` tells the browser "this image renders at X width given the current viewport." For `(max-width: 768px) 100vw, 33vw`, a mobile browser downloads a full-width image, a desktop browser downloads a ~1/3-width image. Next.js generates matching srcset entries and the browser picks the best one — a 33vw slot never downloads a full-width file.

</details>

3. Why are images on the detail page wrapped in a `relative h-96` div instead of using `width`/`height` directly?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The image source is a remote Unsplash URL — we don't know its exact display dimensions ahead of time. A fixed `h-96` container reserves the vertical space (preventing CLS), and `fill` makes the image cover that container with `object-cover`. Using explicit `width`/`height` would work too, but `fill` + container is the go-to when the exact display size is layout-driven, not source-driven.

</details>

4. What did `next/font` change about how the font loads vs 7.3's `<link>` approach?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The font is **self-hosted** — downloaded at build time and bundled with the app. No request goes to Google Fonts at runtime. The font loads from your own server, is preloaded, and the fallback is adjusted to prevent layout shift (no FOUC/CLS). You're no longer dependent on Google's CDN.

</details>

5. After the before/after test, ~70-80% smaller images — what's the user-facing benefit?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Faster page loads, especially on mobile/slow networks. 120KB → 30KB per image means a grid of 6 photos drops from ~700KB to ~180KB. The page renders quicker, the browser burns less data, and the Lighthouse LCP score improves. The visual is identical — just a much smaller payload.

</details>
