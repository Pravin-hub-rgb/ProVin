## Photo Detail Page — Full Page (Hardcoded)

**THINK:** `/photo/[id]` shows one photo's full detail — large image, title, description. The plan's data: `{ id, title, description, src, alt }`.

**File:** `app/photo/[id]/page.tsx` (create the `photo/[id]` folder)

**Concept:** This page matches the photo from `params` — URL `/photo/1` → id `1` → find in the photos array. Dynamic route `[id]` — same pattern from 6.7.3 / 6.13.2. For now it matches from the hardcoded array; database comes in 7.7.3. If the photo isn't found → `notFound()` — pattern from 6.13.5 (we can show it here too — the concept already exists). **File:** `app/photo/[id]/page.tsx` — step by step.

**`params: Promise<{ id: string }>`** — the dynamic route `[id]`. In Next.js 15+, params is async — the **same pattern from 6.7.3**. **`const { id } = await params`** — now actually using it. **`photos.find((p) => p.id === Number(id))`** — match photo by id — `Number(id)` because the URL gives a string (`"1"`) but the array has numbers (`1`) — convert before comparing.

Now the missing-photo check — **`if (!photo) notFound()`** — show a 404 when the photo doesn't exist. `find` returns `undefined` when nothing matches — so the check is necessary:

```tsx
// app/photo/[id]/page.tsx
import Link from "next/link";
import { notFound } from "next/navigation";

const photos = [
  { id: 1, title: "Misty Mountains", description: "Morning fog rolling over the peaks.", src: "https://images.unsplash.com/photo-1506905925346-21bda4d32df4?w=800&q=80", alt: "Misty mountain peaks at sunrise" },
  { id: 2, title: "City Lights", description: "Downtown at dusk, long exposure.", src: "https://images.unsplash.com/photo-1477959858617-67f85cf4f1df?w=800&q=80", alt: "City skyline at night with lights" },
  { id: 3, title: "Forest Path", description: "A quiet trail through the pines.", src: "https://images.unsplash.com/photo-1441974231531-c6227db76b6e?w=800&q=80", alt: "Sunlight through forest trees" },
];

export default async function PhotoPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const photo = photos.find((p) => p.id === Number(id));

  if (!photo) {
    notFound();
  }

  return (
    <section>
      <Link href="/" className="text-sm text-zinc-500">
        &larr; Back to gallery
      </Link>

      <img
        src={photo.src}
        alt={photo.alt}
        className="mt-4 w-full rounded-lg"
      />
      <h1 className="mt-4 text-2xl font-bold">{photo.title}</h1>
      <p className="mt-1 text-zinc-600">{photo.description}</p>
    </section>
  );
}
```

**`if (!photo) notFound()`** — photo not found → 404 (`notFound()` from `next/navigation`, same as 6.13.5). **`<Link href="/">`** — back to the gallery. **`<img className="w-full rounded-lg">`** — the large detail image. **`<h1>` + `<p>`** — title + description.

## TEST + Problem Highlight

**TEST:** On `/`, hero + grid (3 photos). On `/photo/1`, full detail. On `/photo/999`, 404. Design is confirmed.

**The problem — data is duplicated across two places (DRY violation):**

Right now the photos array is **copied in both pages** — same data, two arrays. And the bigger problem: per 7.7.1, the Photo Gallery's data lives in the **database** (Prisma + Neon). To make it real:

- Delete the duplicated arrays
- Fetch data from the database (`prisma.photo.findMany()` / `findUnique()`)
- Optimize the images (`next/image` — 7.7.4)
- Optimize the font (`next/font` — 7.7.4)

That's 7.7.3 (data layer) + 7.7.4 (optimization). **The UI code stays mostly the same** — only the data source changes. This is the payoff of planning + building hardcoded first: the UI is confirmed, the data layer just plugs in.

## Nutshell

Hardcoded UI: on `/` a hero + grid (`{ id, title, description, src, alt }` mapped, `Link` to `/photo/[id]`), on `/photo/[id]` full detail (`params` async — `const { id } = await params` + `photos.find` + `if (!photo) notFound()`). Images are plain `<img>` (next/image comes in 7.7.4). Data is **duplicated across two pages** — a DRY violation that needs replacing with database reads — that's 7.7.3's job.

## What It Is NOT

- **Hardcoded UI is not "the final data."** It's a static demo — built to validate the UI design and data shape. Real data comes from the database (7.7.3). This file is about UI patterns, not data.
- **Plain `<img>` is not "the final image approach" for this project.** The focus here is the UI, not optimization. `next/image` comes in 7.7.4 — then images get optimized. Kept simple on purpose.
- **Duplicating the photos array is not "good practice."** It's a DRY violation — the same data in two places. 7.7.3's data layer (single source of truth) fixes this — both pages call one query function.
- **`photos.find` + `Number(id)` is not "final data lookup."** Right now it's a JS array. In 7.7.3 it becomes `prisma.photo.findUnique({ where: { id } })`. The concept is the same — look up by id — but the source changes.
- **Layout is not "copy into every page."** Defined once — both pages render inside it. The header is the shared brand for the gallery app.

**In Your Own Words**

1. Why build hardcoded UI first instead of going straight to database-driven dynamic code?

<details>
<summary>Show Answer</summary>

**Sample Answer:** If you build dynamic data and UI at the same time and an error appears, you can't tell whether the bug is in the UI or the data layer — debugging two unknowns at once. Building hardcoded first confirms the UI design and validates the data shape. Then in 7.7.3 you only swap the data source, and the UI is already tested. One problem at a time.

</details>

2. `photos.find((p) => p.id === Number(id))` — why is `Number(id)` necessary?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The URL gives `id` as a **string** (`"/photo/1"` → `"1"`), but the array has `id` as a **number** (`1`). `Number(id)` converts the string to a number before comparing. Otherwise `"1" === 1` is `false` and the photo would never match.

</details>

3. What does `if (!photo) notFound()` do — and when does `find` return `undefined`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `find` returns `undefined` when no element matches the condition. So `!photo` is `true` when the id doesn't match any photo. `notFound()` (from `next/navigation`) then renders a 404 page. Opening `/photo/999` triggers this — no photo with id 999, so the user sees a "not found" page instead of a blank screen.

</details>

4. Why is duplicating the photos array across two pages a problem?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It's a DRY violation — the same data lives in two places. To add a new photo, you'd need to update both arrays — miss one and the pages become inconsistent. 7.7.3's data layer (single source of truth) fixes this — one query function, both pages call it.

</details>

5. Why does `/photo/999` show a 404 without a custom error page?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `notFound()` triggers Next.js's **default 404 page** — you don't need to build a custom one first. In 7.7.6, a custom `not-found.tsx` is added for a photo-specific message, but the default works as-is for now.

</details>
