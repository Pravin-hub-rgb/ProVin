In 7.7.5 the modal is live — Parallel + Intercepting Routes in a real implementation. The Photo Gallery is functionally complete. But a production app needs more: **loading states** (when the DB query is running), **error states** (something went wrong), and **not-found states** (invalid URL). # Photo Gallery — Part 6: Streaming + States + Testing + Summary

## Step 1 — Streaming: Progressive Grid Loading

**THINK (7.5):** The home page grid does `await prisma.photo.findMany()` — the whole page blocks until that query resolves. With Neon network latency + 6 remote images, that's a noticeable wait — the hero heading is stuck too. **Streaming with Suspense** fixes this — the hero renders immediately, the grid shows a skeleton, then photos stream in.

**File:** `app/page.tsx`

**Concept (7.5 recap):** Pull the slow logic into its own `async` component, wrap in `<Suspense>` with a skeleton fallback, and the page becomes synchronous — it renders right away.

**File:** `app/page.tsx` — step by step.

First, extract the grid into its own async component — **`async function PhotoGrid()`**:

```tsx
// app/page.tsx
import Image from "next/image";
import Link from "next/link";
import { Suspense } from "react";
import prisma from "@/lib/prisma";

async function PhotoGrid() {
  const photos = await prisma.photo.findMany();

  return (
    <div className="mt-6 grid grid-cols-3 gap-4">
      {photos.map((photo) => (
        <Link
          key={photo.id}
          href={`/photo/${photo.id}`}
          className="relative block h-40"
        >
          <Image
            src={photo.src}
            alt={photo.alt}
            fill
            sizes="(max-width: 768px) 100vw, 33vw"
            className="rounded object-cover"
          />
          <p className="mt-1 text-sm font-medium">{photo.title}</p>
        </Link>
      ))}
    </div>
  );
}

function PhotoGridSkeleton() {
  return (
    <div className="mt-6 grid grid-cols-3 gap-4">
      {Array.from({ length: 6 }).map((_, i) => (
        <div key={i} className="h-40 animate-pulse rounded bg-zinc-200" />
      ))}
    </div>
  );
}

export default function Home() {
  return (
    <section>
      <h1 className="text-2xl font-bold">Photo Gallery</h1>
      <p className="text-zinc-600">A showcase of curated photography.</p>

      <Suspense fallback={<PhotoGridSkeleton />}>
        <PhotoGrid />
      </Suspense>
    </section>
  );
}
```

**`async function PhotoGrid()`** — the slow query lives here (7.5 pattern). **`function PhotoGridSkeleton()`** — 6 gray pulsing boxes, same layout as the grid (`grid-cols-3 gap-4 h-40`). **`<Suspense fallback={<PhotoGridSkeleton />>}>`** — while `PhotoGrid` awaits the DB, the skeleton shows. **`Home` is now synchronous** (no `async`) — the hero renders instantly.

**Result:** `h1` + hero text shows **immediately.** The grid area shows the skeleton (pulsing gray boxes). When `findMany()` resolves, the skeleton is replaced with the real photos. The user never sees a blank screen.

## Step 3 — Error: Something Went Wrong

A runtime error — database down, unexpected failure — is handled by **`error.tsx`** (pattern from Batch 3 / 6.13.5):

**File:** `app/photo/[id]/error.tsx`

```tsx
// app/photo/[id]/error.tsx
"use client";

export default function PhotoError({
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <section className="text-center">
      <h2 className="text-xl font-bold">Something went wrong</h2>
      <p className="mt-2 text-zinc-600">Failed to load the photo. Please try again.</p>
      <button
        onClick={reset}
        className="mt-4 rounded bg-blue-600 px-4 py-2 text-white hover:bg-blue-700"
      >
        Try Again
      </button>
    </section>
  );
}
```

- **`"use client"`** — the error boundary needs client-side interactivity (the `reset` button), so it's a Client Component (same reason as 6.13.5).
- **`reset`** — Next.js provides this; it retries rendering the page.
- The modal doesn't need an `error.tsx` — it returns `null` when a photo is missing, which is the right behavior for an overlay.

**Try it:** Temporarily break the `prisma` import → the error boundary shows. Fix the import → it recovers.

The detail page is async (it fetches from the DB) — while that query runs, show a loading state:

```tsx

  return (
    <section>
      <p className="text-zinc-500">Loading photo...</p>
    </section>
  );
}
```

- `loading.tsx` — the route segment's automatic loading UI (Batch 1). While `/photo/[id]` is awaiting the async query, this shows. When the data arrives, the real page renders.

**The Next.js state pipeline (same as 6.13.5):**

```
Request → loading.tsx (while data loads)
         ↓ error occurs
         error.tsx (with reset option)
Bad ID → not-found.tsx
```

- **404 vs error are different:** a bad id is a **user error** (wrong URL — predictable) → `notFound()` → `not-found.tsx`. An unexpected failure is a **system error** (recoverable) → `error.tsx` with retry. One is predictable (404), the other isn't (500).

## What It Is NOT

- **Suspense + skeleton is not "lazy loading."** Lazy loading defers images (7.2). Streaming **renders page sections independently** — if the grid is slow, only the grid waits (skeleton), the rest of the page is already there.
- **`not-found.tsx` is not a copy of `error.tsx`.** `not-found` = predictable missing resource (bad URL). `error.tsx` = unexpected failure (recoverable, with retry). One is "you typed a wrong URL," the other is "something broke, try again."
- **`error.tsx` needs `"use client"`** — not because of lazy loading, but because the `reset` button needs interactivity. The boundary mechanism is Next.js's; the file being a Client Component is for the interactive retry.
- **The test table is not "just a checklist."** Each row verifies a behavior — especially the modal tests (click = modal, direct = full page). That's the proof that 7.6's pattern works end to end.
- **Batch 7 is not "four independent features."** All four concepts follow **one pattern**: find the manual approach, see its problems, then apply the Next.js solution. That mindset — optimization-first, understanding the "why" — is the real takeaway.
