# Manual Images — The Problems with `<img>`

## THINK — The Cost of Displaying One Photo

You've used images like this — a single `<img>` tag:

```html
<img src="/cat.jpg" alt="A cat" />
```

That's one line. What does the browser do with it? **The entire image file is downloaded** — however many MB it is. An 8MB image loading on 3G mobile — what happens? The user opens the page, nothing shows for 5 seconds while the image loads. And the same image — tablet, laptop, 4K monitor — **the same 8MB file everywhere.** No intelligence.

This file covers four real problems that `<img>` causes in production. Understand each one, because next file `next/image` solves them one by one.

## CONCEPT — Four Problems of `<img>`

### Problem 1 — No Automatic Optimization

When you write `<img src="/cat.jpg">`, the browser downloads **the file as-is.** If the photographer gave you a 4000×3000 full-resolution image (8MB) and your screen is only 400px wide, the browser still downloads **all 8MB.** No browser thinks "I only need 400px — give me 400px." It just takes the whole file.

The name of this problem is **file size / bandwidth.** Download 8MB for every image and your page becomes 50MB. On the web, file size = speed, period.

### Problem 2 — Layout Shift (CLS)

This is the most annoying issue you've definitely seen. Open a news site and scroll — **text jumps slightly** when images load in. What's happening?

In HTML, `<img src="/cat.jpg">` — the browser has **no idea how big that image is** (width × height). Until the file downloads, it has no space for it. So the browser renders the page without the image, then when the image arrives, the **entire layout shifts down**. This is **CLS — Cumulative Layout Shift.** Google treats this as a ranking factor (that's the SEO angle, but for now we focus on UX). Text jumping mid-sentence is very annoying.

You can fix this with `width` + `height` attributes (or CSS `aspect-ratio`) — but you need to know the proper dimensions, and it's tedious to do manually for every image. Then it gets trickier with responsive images.

### Problem 3 — No srcset/sizes

One image, different screens — phone (small), tablet (medium), desktop (large). The proper solution is to give the browser **different-sized images** (800px, 1600px, 3200px) and let it pick the right one. This is **srcset** — a built-in HTML feature:

```html
<img
  src="/cat.jpg"
  srcset="/cat-800.jpg 800w, /cat-1600.jpg 1600w, /cat-3200.jpg 3200w"
  sizes="(max-width: 600px) 400px, 1600px"
  alt="A cat"
/>
```

But the problem is — **you have to generate all those different-sized images.** `/cat-800.jpg`, `/cat-1600.jpg`, `/cat-3200.jpg` — you create them, name them, wire up the URLs. 10 photos means 30 files. Maintaining this manually is tedious.

### Problem 4 — `loading="lazy"` Has Limits

A simple performance trick — **lazy loading.** Load the image only when the user scrolls near it, not upfront:

```html
<img src="/cat.jpg" loading="lazy" alt="A cat" />
```

This is built-in HTML and does work. But there's a catch — the browser needs to **know where the image is** to lazy-load it, and that's exactly the problem from before — `<img>` with no dimensions. Lazy loading only works well when dimensions are known. And more important — **without width/height, lazy-loaded images cause even more layout shift.**

There are also edge cases — `loading="lazy"` only considers the browser's viewport, and in complex layouts the browser can't always figure it out. The limits of manual approaches.

## CODE — The Manual Approach in Practice

A small example — a photo grid built with `<img>` (in 7.7.2 we build this same thing, but simplified):

> **Image files:** Put `cat.jpg`, `dog.jpg`, `bird.jpg` into `public/photos/` (see 7.2's **Step 0** for download + dimensions).

```tsx
// app/gallery/page.tsx
const photos = [
  { id: 1, src: "/photos/cat.jpg", alt: "Cat sleeping" },
  { id: 2, src: "/photos/dog.jpg", alt: "Dog running" },
  { id: 3, src: "/photos/bird.jpg", alt: "Bird flying" },
];

export default function GalleryPage() {
  return (
    <div className="grid grid-cols-3 gap-4">
      {photos.map((photo) => (
        <img
          key={photo.id}
          src={photo.src}
          alt={photo.alt}
          className="h-40 w-full object-cover"
        />
      ))}
    </div>
  );
}
```

See — `className="h-40 w-full object-cover"` sets the size via **CSS**, but the `<img>` has no `width`/`height` attributes. That means the browser doesn't know the dimensions until the file arrives — **layout shift.** And the full file downloads for every image — no optimization.

## TEST — See the Problem Yourself

Run `npm run dev`, open the gallery page, then open browser DevTools → **Network** tab → filter by **Img**. Click on any image and look at the **Size** column — the full file downloads, whether it's a small phone or a big desktop. Then switch to the **Performance** tab → "Experience" section → look at the CLS score — you'll see the layout shift as images load.

## Nutshell

The `<img>` tag causes four problems in production: **no automatic optimization** (every screen downloads the full file), **layout shift (CLS)** (no dimensions means text jumps when images load), **srcset/sizes must be managed manually** (different sizes need different files), and **lazy loading has limits** (without dimensions, lazy loading actually makes shift worse). Next.js's `next/image` solves all of these — coming next.

## What It Is NOT

- **`<img>` is not a "wrong tag."** It's valid HTML and works fine for small/static images. But in production apps, images scale — manual management becomes a headache. Next.js provides a better solution, which is why we use it.
- **`loading="lazy"` is not a "complete fix."** It's basic lazy loading, but without dimensions it doesn't address layout shift and breaks in complex cases. Next.js's `next/image` handles both lazy + dimensions.
- **Image optimization is not "shrinking with CSS."** CSS makes an image *appear* smaller, but the full file is still downloaded. Real optimization generates a **smaller file on the server** that the browser actually downloads.
- **srcset is not "optional."** Yes, it's built into HTML, but you still have to generate and manage all the different files yourself. `next/image` does this automatically.
