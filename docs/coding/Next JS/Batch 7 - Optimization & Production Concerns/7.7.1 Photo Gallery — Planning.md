# Photo Gallery — Part 1: Planning

## Sawaal 1 — Kya Banana Hai?

**Photo Gallery** — ek media showcase app jaisa simple (Unsplash/Instagram-jaisa). Home pe photos ki grid — har photo pe click → **photo detail**. Detail do tareeke se khul sakta hai: **modal** (grid se click karne pe — 7.6 wala pattern) ya **full page** (URL direct kholne pe). Yeh Instagram ka exactly wahi pattern hai jo 7.6 mein concept level pe dekha.

**Kyun ye project:** Yeh batch ka capstone pattern hai — chaaro concepts ek project mein:

| Concept (batch) | Photo Gallery mein kahan |
|---|---|
| `next/image` (7.2) | Har photo optimized Image component se + before/after size compare (7.7.4) |
| `next/font` (7.4) | Project-wide Inter font — no layout shift (7.7.4) |
| Streaming with Suspense (7.5) | Gallery grid slow query — skeleton + progressive load (7.7.6) |
| Parallel + Intercepting Routes (7.6) | Photo modal `@modal` + `(.)photo/[id]` (7.7.5) |
| Prisma + Neon (Batch 6) | Photo data Neon database se (7.7.3) |
| SEO/metadata (2.4) | Home + photo detail pe generateMetadata (7.7.3) |

**Read-only showcase project** — photos sirf **dikhana** hai, koi add/edit/delete nahi. Server Actions (mutation) Batch 6 mein learn ho gaye. Yeh project intentionally **read-only** hai — focus optimization + routing patterns par hai, mutation par nahi.

## Sawaal 2 — Kaunse Pages Chahiye?

Gallery app — pages kam, par routing pattern advanced hai. Routes table:

| Route | Kya dikhta hai | Batch concept |
|---|---|---|
| `/` | Home — hero heading + gallery grid (saari photos) | SC read (photos list), `next/font`, `next/image`, streaming grid |
| `/photo/[id]` | Full photo detail page — bada photo + title + description | Dynamic route (params), SC read (single photo), `generateMetadata` (SEO), 404 agar photo nahi |
| `@modal/(.)photo/[id]` | **Photo modal** — grid se click karne pe khulta hai | Parallel slot `@modal` + intercepting `(.)photo` (7.6) |

**Modal vs full page ka trick (7.6):** `/photo/1` ka URL **dono** ke liye same. Grid se click → `@modal/(.)photo/[id]` render (modal overlay, URL `/photo/1`). URL direct kholo / refresh → `photo/[id]` full page. Yeh distinction hi Intercepting Routes ka signature hai.

## Sawaal 3 — Data Ka Shape Kya Hai?

UI dekh ke data decide karte hain — ulta nahi (6.13.1 wala rule, series prompt).

**Home grid pe kya dikhta hai:** Har photo ka **thumbnail** (chhoti image) + **title** (caption). Click → detail.

**Photo detail page pe kya dikhta hai:** **Bada photo** (full image), **title**, **description** (optional), **createdAt** (date). 

So Prisma schema shape (detail 7.7.3 mein):

```
Photo
  id
  title
  description?
  src            ← image ka URL (remote — Unsplash)
  alt            ← accessibility + SEO
  createdAt
```

**Har field ka reason:**

- **`Photo.id`** — primary key, unique identifier (`@id @default(autoincrement())`) — URL mein `/photo/[id]` ke liye
- **`Photo.title`** — grid + detail dono pe caption
- **`Photo.description`** — optional (`String?`) — detail page pe extra context; chhote captions mein empty ho sakta hai
- **`Photo.src`** — image ka **remote URL** (Unsplash se) — isse `remotePatterns` (7.2) + `next/image` ki optimization ka use-case milta hai
- **`Photo.alt`** — **accessibility + SEO** — screen readers + search engines ko batata hai image mein kya hai
- **`Photo.createdAt`** — date — detail page pe dikhega (+ future sorting)

**Relations chahiye? Nahi.** Ek photo sirf khud hai — koi user, koi album (nahi bana rahe). Relation ke bina simple single-model database — is project ka focus optimization + routing hai, relations nahi (wo 6.12/6.13 mein tha). Model simple = project focused.

## Sawaal 4 — Data Flow Kaise Hoga?

Read-only project — sirf **Server Component reads** (Batch 6 ka SC pattern), koi mutations nahi:

| Operation | Pattern | Kahan |
|---|---|---|
| Saari photos (grid) | SC read — `prisma.photo.findMany()` | `/` page grid mein (Suspense wrapped — 7.7.6) |
| Ek photo (detail) | SC read — `prisma.photo.findUnique({ where: { id } })` | `/photo/[id]` + `@modal/(.)photo/[id]` |
| Photo nahi mila | `notFound()` (1.4/6.13.5 wala pattern) | `/photo/[id]` — 404 |
| SEO | `generateMetadata` (2.4) — har photo ka title + description | `/` + `/photo/[id]` |

**Prisma query style (6.13.3 se same):**

- Grid: `prisma.photo.findMany()` — saare photos
- Detail: `prisma.photo.findUnique({ where: { id: Number(params.id) } })` — ek photo, id se

**`lib/prisma.ts`** — 6.13.3 mein banaya tha — yahan reuse (copy). Prisma client singleton — global instance, hot reload pe naye connections nahi.

**Data flow diagram:**

```
Neon DB (Photo table)
   │  prisma.photo.findMany() / findUnique()
   ▼
Server Component (page / photo page)
   │
   ├── grid → Suspense boundary → skeleton → photos (streaming)
   └── photo → notFound() agar nahi mila
   │
   ▼
UI render (optimized: next/image + next/font)
```

**Seed data:** Photos Neon mein manually/drizzle se add — Unsplash ke 6-8 photo URLs (title/alt ke saath). 7.7.3 mein detail.

## Nutshell

Photo Gallery planning: project = grid + photo detail (modal + full page — 7.6 pattern). Tin "pages": `/` (grid), `/photo/[id]` (full page), `@modal/(.)photo/[id]` (modal). Data shape UI se decide — single `Photo` model (id, title, description?, src, alt, createdAt) — relations nahi chahiye (focus optimization). Flow = read-only SC reads (`findMany`, `findUnique`) + `notFound()` + `generateMetadata`; no Server Action mutations. Optimization (next/image/font), streaming (grid Suspense), modal (parallel+intercepting) — chaaron concepts ek project mein.

## What It Is NOT

- **Photo Gallery = "Unsplash clone" nahi.** Yeh production-pattern example hai — optimization + routing patterns apply karna hai, photo-sharing features copy karna nahi. Read-only by design.
- **`Photo.src` = "local file path" nahi.** Remote URL (Unsplash) hai — taaki `remotePatterns` (7.2) + `next/image` optimization ka real use-case mile. Local images ka pattern 7.2 mein already cover ho chuka.
- **Photo modal = "sirf ek CSS popup" nahi.** Modal ka core URL handling hai (7.6) — back button, shareable URL, click vs direct distinction. Overlay styling secondary hai.
- **Read-only = "galti se mutations nahi likh rahe" nahi.** Read-only ek **decision** hai — is project ka focus optimize + routing hai. Mutations (Server Actions) Batch 6 mein already proven hain — yahan repeat karna unnecessary hai.
- **Single Photo model = "data layer simple hai" ka matlab weak nahi.** Simple model by design — focus routing pattern + optimization par. Relations 6.12/6.13 mein alag se sikhe — yahan repeat nahi.
