## Question 1 — What Are We Building?

**Photo Gallery** — a simple media showcase app (Unsplash/Instagram-style). The home page shows a grid of photos — clicking a photo shows **photo detail.** The detail can open two ways: **as a modal** (click from the grid — 7.6's pattern) or **as a full page** (open the URL directly). This is exactly the same pattern we saw at the concept level in 7.6 — now in code.

**Why this project:** It's the batch's capstone — all four concepts in one project:

| Concept (batch) | Where in Photo Gallery |
|---|---|
| `next/image` (7.2) | Every photo optimized via `Image` + before/after size comparison (in 7.7.4) |
| `next/font` (7.4) | Project-wide Inter font — no layout shift |
| Streaming with Suspense (7.5) | Slow gallery grid loads progressively |
| Parallel + Intercepting Routes (7.6) | Photo modal `@modal` + `(.)photo/[id]` |
| Prisma + Neon (Batch 6) | Photo data from the database (starting in 7.7.3) |
| SEO/metadata (2.4) | Home + photo detail use `generateMetadata` |

**Read-only showcase project** — photos are just **displayed**, no add/edit/delete. Server Actions (mutations) were learned in Batch 6. This project is intentionally **read-only** — the focus is optimization + routing patterns, not mutations.

## Question 2 — What Pages Do We Need?

Gallery apps have few pages, but the routing pattern is advanced. Routes table:

| Route | What it shows | Batch concept |
|---|---|---|
| `/` | Home — hero heading + gallery grid (all photos) | SC read (photos list), `next/font`, `next/image`, streaming grid |
| `/photo/[id]` | Full photo detail page — large image + title + description | Dynamic route (params), SC read (single photo), `generateMetadata` (SEO), 404 if not found |
| `@modal/(.)photo/[id]` | **Photo modal** — opens on click from grid | Parallel slot `@modal` + intercepting `(.)photo/[id]` (7.6) |

**The modal vs. full page trick (7.6):** `/photo/[id]` is the **same URL** for both. Click from the grid → `@modal/(.)photo/[id]` renders (modal). Open the URL directly → `photo/[id]` renders (full page). That distinction is what Intercepting Routes gives you.

## Question 3 — What Is the Data Shape?

We decide data by looking at the UI (not the other way around — the same rule from 6.13.1).

**On the home grid:** each photo shows its **thumbnail** (small image) + **title** (caption). Click → detail.

**On the photo detail page:** **large image** (full size), **title**, **description** (optional), **createdAt** (date).

So the Prisma schema shape (details in 7.7.3):

```
Photo
  id
  title
  description?
  src            ← image URL (remote — Unsplash)
  alt            ← accessibility + SEO
  createdAt
```

**Why each field:**

- **`Photo.id`** — primary key, unique identifier (`@id @default(autoincrement())`) — for the URL `/photo/[id]`
- **`Photo.title`** — caption on both grid and detail
- **`Photo.description`** — optional (`?`) — extra context on detail page; small captions might be empty (matching 7.7.2's UI)
- **`Photo.src`** — image **remote URL** (Unsplash) — this is what gives `next/image` a real use-case for `remotePatterns` in 7.7.4
- **`Photo.alt`** — **accessibility + SEO** — tells screen readers and search engines what's in the image
- **`Photo.createdAt`** — date — shown on detail page (+ future sorting)

**Do we need relations? No.** A photo stands on its own — no user, no album (not building those). A relation-less, simple single-model database — because the project's focus is optimization + routing, not relations (those were covered in 6.12/6.13). A simple model = a focused project.

## Question 4 — How Does Data Flow?

Read-only project — only **Server Component reads** (same pattern as Batch 6), no mutations:

| Operation | Pattern | Where |
|---|---|---|
| All photos (grid) | SC read — `prisma.photo.findMany()` | `/` page grid (wrapped in Suspense — 7.7.6) |
| One photo (detail) | SC read — `prisma.photo.findUnique({ where: { id } })` | `/photo/[id]` + `@modal/(.)photo/[id]` |
| Photo not found | `notFound()` (pattern from 1.4 / 6.13.5) | `/photo/[id]` → 404 |
| SEO | `generateMetadata` (2.4) — each photo's title + description | `/` + `/photo/[id]` |

**Prisma query style (same as 6.13.3):**

- Grid: `prisma.photo.findMany()` — all photos
- Detail: `prisma.photo.findUnique({ where: { id } })` — one photo, by id

**`lib/prisma.ts`** — the same client singleton from 6.13.3 (copy it) — reuses the global instance, no new connections on hot reload (Neon has limits).

**Data flow diagram:**

```
Neon DB (Photo table)
   │  prisma.photo.findMany() / findUnique()
   ▼
Server Component (page / photo page)
   │
   ├── grid → Suspense boundary → skeleton → photos (streaming)
   └── photo → notFound() if not found
   │
   ▼
UI render (optimized: next/image + next/font)
```

**Seed data:** Add real photos manually (or via seed script) — 6-8 Unsplash photo URLs with title/alt. Details in 7.7.3.

## Nutshell

Photo Gallery planning: project = grid + photo detail (modal + full page — the 7.6 pattern). Three "pages": `/` (grid), `/photo/[id]` (full detail), `@modal/(.)photo/[id]` (modal). Data shape is UI-driven — a single `Photo` model (id, title, description?, src, alt, createdAt) — no relations needed (by design, focus is optimization + routing). Data flow = read-only SC reads (`findMany`, `findUnique`) + `notFound()` + `generateMetadata`. Optimization (next/image + next/font), streaming (grid Suspense), modal (parallel + intercepting) — all four concepts combined in one project.

## What It Is NOT

- **Photo Gallery is not an "Unsplash clone."** It's a production-pattern example — you learn optimization + routing patterns, not photo-sharing features. Read-only by design.
- **`Photo.src` is not a "local file path."** It's a remote URL (Unsplash) — which gives `next/image` a real use-case for `remotePatterns` (7.2). Local images were already covered in 7.2.
- **The photo modal is not "just a CSS popup."** The core of the modal is URL handling (7.6) — back button, shareable URL, click vs. direct distinction. Overlay styling is secondary.
- **Read-only is not "we forgot mutations."** It's a **deliberate decision** — the project focus is optimization + routing. Mutations (Server Actions) were proven in Batch 6 — no need to repeat.
- **A single Photo model is not "weak data design."** Relations are needed when things are connected (user → boards → tasks). Here a photo stands alone — no user/album. Simple model = focused project. Relations were covered in 6.12/6.13 — no need to repeat.

**In Your Own Words**

1. Opening a photo shows a modal on click but a full page on direct URL visit — how? What makes this possible?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The same URL `/photo/1` maps to two different renders. Click from the grid → Intercepting Routes trigger — the `@modal/(.)photo/[id]` component renders (modal overlay, no reload). Open the URL directly (or refresh) → no interception — the `photo/[id]` component renders (full page). The click vs. direct distinction comes from the `(.)` intercept marker in 7.6.

</details>

2. Why does the `Photo` model have no relations — isn't that "missing" from 6.12?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Relations exist when things are connected (user has boards, boards have tasks). A photo stands on its own — there's no user or album to relate to. The project focus is optimization + routing, not relations. Single model = focused scope. Relations were thoroughly covered in 6.12/6.13 — repeating them here would dilute the learning.

</details>

3. Why does `Photo.src` use a remote Unsplash URL — how does that tie into `next/image`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A remote URL gives `next/image` a real use-case for `remotePatterns` (7.2). That's the security allowlist — only listed domains can be optimized. With a local file you'd use `width`/`height` directly; with a remote URL you need `remotePatterns` configured. It's the production-realistic scenario.

</details>

4. Why is the project read-only — no Server Action for adding photos?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It's an intentional scope decision — this project teaches optimization (next/image, next/font), streaming (Suspense), and routing (parallel + intercepting). Mutations (Server Actions) were fully covered in Batch 6 with the Task Board. Mixing in mutations would split focus. Each project has a clear learning goal.

</details>

5. Why wrap the grid's photo list in `<Suspense>` (7.7.6) — the data is just a DB query?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Even a DB query has latency (Neon round-trip + 6 remote image sizes). Without Suspense, the entire page (hero included) blocks until all photos load — blank screen. With Suspense, the hero renders instantly, a skeleton shows for the grid, and photos stream in progressively. The slow section stays localized — the rest of the page is already interactive.

</details>
