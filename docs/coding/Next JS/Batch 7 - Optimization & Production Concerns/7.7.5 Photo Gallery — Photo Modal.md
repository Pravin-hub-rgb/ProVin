# Photo Gallery — Part 5: Photo Modal (Parallel + Intercepting)

## THINK — What We're Building

This is 7.6's concept — now in code. **Two concepts, one pattern:**

1. **Parallel Routes** — two independent screens on one URL: `@main` (the grid) + `@modal` (the modal slot)
2. **Intercepting Routes** — navigate to `/photo/1` **from inside** the app (click) → show the modal. Visit `/photo/1` directly → full page (already built in 7.7.4).

The key insight: **`/photo/[id]/page.tsx` doesn't need to change** — it's the full page shown on direct visit. The new `@modal` slot is what renders the modal on click.

## Folder Structure Preview

```
app/
├── layout.tsx                ← update: add `modal` slot
├── page.tsx                  ← main grid (unchanged from 7.7.4)
├── photo/[id]/page.tsx       ← full detail page (unchanged from 7.7.4)
└── @modal/
    ├── default.tsx           ← null (no modal state)
    └── (.)photo/
        └── [id]/
            └── page.tsx      ← intercepted modal (new)
```

## Step 1 — Layout: Add `modal` Slot

**THINK (7.6):** Parallel routes need the layout to render the slot — `{children}` (the main page) + `{modal}`. Update the root layout.

**File:** `app/layout.tsx`

**Concept:** The layout gains a `modal` prop alongside `children`. Next.js passes the `@modal` slot as `modal` to the layout — folder `@modal` → prop `modal`.

**File:** `app/layout.tsx` — step by step.

Update the signature — **`RootLayout({ children, modal })`** — now two props. Add `modal` to the types:

```tsx
// app/layout.tsx
import Link from "next/link";
import { Inter } from "next/font/google";
import "./globals.css";

const inter = Inter({ subsets: ["latin"], variable: "--font-inter" });

export default function RootLayout({
  children,
  modal,
}: Readonly<{
  children: React.ReactNode;
  modal: React.ReactNode;
}>) {
  return (
    <html lang="en" className={inter.variable}>
      <body>
        <header className="border-b p4">
          <Link href="/" className="text-lg font-semibold">
            Photo Gallery
          </Link>
        </header>
        <main className="mx-auto max-w-4xl p-4">{children}</main>
        {modal}
      </body>
    </html>
  );
}
```

**`{modal}`** — rendered after `</main>` so the modal overlays on top of the main content. During normal navigation (no modal), `@modal` renders `null` via `default.tsx` — nothing extra shows.

## Step 2 — `@modal/default.tsx`: No Modal State

**THINK (7.6):** Every parallel slot needs a `default.tsx` — the fallback when no route matches. During normal page visits (no modal), the `@modal` slot should render nothing.

**File:** `app/@modal/default.tsx`

**Concept:** `default.tsx` is the fallback for a parallel slot — when no matching route exists in that slot, this renders. No modal → `null`. (7.6 explains that without this, the build fails.)

```tsx
// app/@modal/default.tsx
export default function ModalDefault() {
  return null;
}
```

**`return null`** — the slot is empty during normal navigation. This file is **mandatory** — skip it and you get a build error.

## Step 3 — `@modal/(.)photo/[id]/page.tsx`: The Intercepted Modal

**THINK (7.6):** This is the interception — `(.)photo/[id]` means when the user navigates to `/photo/1` **from within the app** (clicking from the grid), Next.js intercepts and renders this file as a **modal.** A direct visit or refresh hits `photo/[id]` (the full page from 7.7.4, unchanged).

**File:** `app/@modal/(.)photo/[id]/page.tsx` (create folders `@modal/(.)photo/[id]`)

**Concept:** The modal content is the photo detail (image + title + description) shown **as an overlay** — `fixed inset-0` (full screen), `bg-black/70` (dark backdrop), content centered. The photo data comes from `getPhoto(id)` — same query as the full page. The close button → `Link` to `/` — the modal slot empties and the grid returns.

**File:** `app/@modal/(.)photo/[id]/page.tsx` — step by step.

Imports + data fetch — **`Image`** (optimized), **`Link`** (to close), **`prisma`** (to fetch). **`getPhoto`** — same helper (7.7.3) — one photo by id:

```tsx
// app/@modal/(.)photo/[id]/page.tsx
import Image from "next/image";
import Link from "next/link";
import prisma from "@/lib/prisma";

async function getPhoto(id: number) {
  return prisma.photo.findUnique({ where: { id } });
}

export default async function PhotoModal({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const photo = await getPhoto(Number(id));

  if (!photo) {
    return null;
  }

  return (
    <div className="fixed inset-0 z-50 flex items-center justify-center bg-black/70">
      <div className="relative w-full max-w-lg rounded-lg bg-white p-4 shadow-xl">
        <Link
          href="/"
          className="absolute right-3 top-3 rounded-full bg-zinc-200 px-2 text-zinc-600"
        >
          X
        </Link>

        <Image
          src={photo.src}
          alt={photo.alt}
          width={800}
          height={600}
          className="rounded object-cover"
        />
        <h2 className="mt-3 text-lg font-semibold">{photo.title}</h2>
        <p className="text-zinc-600">{photo.description}</p>
      </div>
    </div>
  );
}
```

**`if (!photo) return null`** — if not found, don't render a modal (no 404 page inside a modal — that would be jarring). **`fixed inset-0 z-50 bg-black/70`** — the overlay — full screen, dark backdrop, on top (same pattern as 7.6's example). **`Link href="/"`** — the **close button** — navigating to `/` empties the `@modal` slot, the grid returns. **`<Image width={800} height={600}>`** — inside the modal, dimensions are known (fixed modal) so `width`/`height` work directly — no `fill` needed.

> **DRY note — `getPhoto` exists in two files** (the full page 7.7.3 + the modal). For this small project, that's acceptable. In production, move it to a shared file (`lib/photos.ts`) — the data-layer pattern from the series.

## Step 4 — TEST: Modal Behavior

**TEST (7.6's expected behaviors):**

1. **Click from grid:** Click a photo on `/` → a **modal opens** (overlay, dark backdrop) — URL becomes `/photo/1` — **no page reload** (the grid stays visible underneath).
2. **Back button:** Browser back → **modal closes**, back to the grid (URL `/`).
3. **Direct visit:** Open `/photo/1` in a **new tab** → you get the **full page** (header + large image + title, from 7.7.4) — not a modal.
4. **Close button:** Click X in the modal → back to grid.
5. **Refresh with modal open:** Modal is open (`/photo/1`) and you refresh → you get the **full page** (refresh = direct visit, interception doesn't apply).

This is the proof of 7.6's pattern — **click = modal, direct/refresh = full page.**

## Nutshell

Photo Modal: the root layout gains a **`modal` slot** (`{children}` + `{modal}`). `app/@modal/default.tsx` → `return null` (no modal state — mandatory). `app/@modal/(.)photo/[id]/page.tsx` → the intercepted modal — renders when clicking from the grid (fixed overlay, dark backdrop, photo + close `Link`); direct visit or refresh hits `photo/[id]` (the full page, unchanged). Close = `Link` to `/`. If the photo is missing → `return null` (no 404 in a modal). Back button closes the modal. **Click = modal, direct/refresh = full page.**

## What It Is NOT

- **The modal is not "a new route duplicating the full page."** Both are views of the same `/photo/[id]` — the full page on direct visit, the modal on click. Same data, different presentation.
- **`(.)` prefix is not "hiding a folder."** It's an **intercept marker** — "intercept this segment when navigation comes from within the app." The `(.)` is stripped from the URL. The click vs. direct distinction comes entirely from this marker.
- **`return null` for a missing photo is not the same as `notFound()`.** The full page shows a proper 404 (it's the photo's own page). The modal is transient — a 404 overlay is awkward, so we render nothing and the user stays on the grid.
- **The close button is not the only way to close.** Browser back also closes (the history had `/` before `/photo/1`). The close button does it via `Link`, back does it via history — same result, different mechanism.
- **`@modal` is not a "URL path."** The `@` prefix marks a **slot** — it doesn't appear in the URL. The real URL is still `/photo/1`. The slot is just where in the layout the modal renders.

**In Your Own Words**

1. How does the modal get the `modal` prop in the layout — what connects `@modal` to `layout.tsx`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Next.js automatically passes parallel route slots as props to the root layout. The folder `@modal` becomes the prop `modal`, and `RootLayout({ children, modal })` receives it. The layout renders `{modal}` after the main content. No import needed — the `@` prefix is the slot marker, and Next.js wires it to the layout automatically.

</details>

2. What makes `(.)photo/[id]` render a modal on click but a full page on direct visit — same URL?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `(.)` is an **intercept marker** — "intercept when navigation comes from within the page." When you click a Link to `/photo/1` while already on the site, Next.js intercepts and renders the `@modal/(.)photo/[id]` component (the modal). When you open the URL directly or refresh, no interception happens — the `photo/[id]` page renders (the full page). Same URL, different render, no reload in the intercepted case.

</details>

3. Why does `@modal/default.tsx` return `null` — what would happen without it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `default.tsx` is the fallback — what renders when no route matches the `@modal` slot (i.e., on normal page visits, no photo is selected). Returning `null` means the slot is empty — nothing shows. Without this file, Next.js throws a build error: the slot has no fallback. Every parallel slot requires a `default.tsx`.

</details>

4. Why does the modal use `return null` when a photo is missing, while the full page uses `notFound()`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Different contexts. The full page is the photo's own page — a missing photo should show a proper 404. The modal is a transient overlay on top of the grid — a 404 page in a modal is jarring. Instead, we render nothing (the slot stays empty, the user is still looking at the grid).

</details>

5. After closing the modal and opening it again — does the component re-mount each time? Why or why not?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Yes, roughly — each time you click a photo, the URL `/photo/[id]` is the same, but the intercepted modal component re-renders with the new `params`. The `default.tsx` (null) acts as the "empty" state between opens. It's not a full page lifecycle (no reload), but the modal component does re-instantiate for the new photo.

</details>
