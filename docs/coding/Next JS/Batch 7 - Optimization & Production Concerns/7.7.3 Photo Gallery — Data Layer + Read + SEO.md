## Schema — Single Photo Model

**File:** `prisma/schema.prisma` — boilerplate ke baad model add karo.

**Concept (7.7.1 ka decision):** Task Board mein 3 models + relations the (6.12 design). **Photo Gallery mein sirf ek `Photo` model** — koi user, koi album nahi (planning mein socha). Relation ke bina model simple hai — is project ka focus optimization + routing hai. 6.13.3 ke `@relation` patterns yahan repeat nahi honge.

Photo model — **`id Int @id @default(autoincrement())`** — primary key (wahi pattern). **`title String`** — grid + detail dono pe caption. **`description String?`** — optional (`?`) — 7.7.2 UI mein detail page ka paragraph — chhote captions mein empty:

```prisma
// prisma/schema.prisma
model Photo {
  id          Int     @id @default(autoincrement())
  title       String
  description String?
```

**`id Int @id @default(autoincrement())`** — primary key (wahi pattern). **`title String`** — caption. **`description String?`** — `?` = optional — chhote captions mein detail nahi hoti (7.7.2 UI ka `<p>`).

Ab image fields — **`src String`** — image ka remote URL (Unsplash) — 7.7.2 mein seedha `<img src>` tha, 7.7.4 mein `next/image` ise optimize karega. **`alt String`** — accessibility + SEO — screen readers + search engines. **`createdAt DateTime @default(now())`** — date — `@default(now())` khud set hoti hai (wahi 6.13.3 pattern):

```prisma
// prisma/schema.prisma
model Photo {
  id          Int      @id @default(autoincrement())
  title       String
  description String?
  src         String
  alt         String
  createdAt   DateTime @default(now())
}
```

**`src String`** — image URL (remote). **`alt String`** — accessibility + SEO. **`createdAt DateTime @default(now())`** — date khud set (wahi pattern).

**Poora model — har field ka reason (7.7.1 Sawaal 3):**

```
Photo
  id          Int      @id @default(autoincrement())   ← URL /photo/[id] ke liye
  title       String                                   ← grid + detail caption
  description String?                                  ← detail extra context (optional)
  src         String                                   ← remote image URL (next/image 7.7.4)
  alt         String                                   ← accessibility + SEO
  createdAt   DateTime @default(now())                 ← date (detail + future sort)
```

**Enum chahiye? Nahi.** Task Board mein `Status` enum tha (columns fixed the). Photo Gallery mein aisa koi fixed-set field nahi — title/description/src/alt sab free-form. Simple fields hi enough — planning ka decision.

### SEO — generateMetadata (2.4 ka reinforcement)

**Concept (planning Sawaal 4):** Photo Gallery mein **SEO reinforce** karna hai — 2.4 (Metadata API) ka concept yahan apply. Photo detail page ki title/description search engines + social share ke liye dynamic honi chahiye — har photo ka apna title.

**File:** `app/photo/[id]/page.tsx` — `generateMetadata` add karo

**Concept:** `generateMetadata` — Next.js ka function jo **dynamic metadata** banata hai — params se. Search engine page render hone se pehle yeh metadata padhta hai — title/description page-specific. (2.4 mein static metadata tha — `export const metadata`; yahan dynamic — `generateMetadata` — params depend karta hai.) Photo nahi mila toh `notFound()` — metadata mein bhi check:

```tsx
// app/photo/[id]/page.tsx
import type { Metadata } from "next";
import Link from "next/link";
import { notFound } from "next/navigation";
import prisma from "@/lib/prisma";

async function getPhoto(id: number) {
  return prisma.photo.findUnique({ where: { id } });
}

export async function generateMetadata({
  params,
}: {
  params: Promise<{ id: string }>;
}): Promise<Metadata> {
  const { id } = await params;
  const photo = await getPhoto(Number(id));

  if (!photo) {
    return { title: "Photo Not Found" };
  }

  return {
    title: photo.title,
    description: photo.description ?? photo.alt,
  };
}

export default async function PhotoPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const photo = await getPhoto(Number(id));

  if (!photo) {
    notFound();
  }

  return (
    <section>
      <Link href="/" className="text-sm text-zinc-500">
        &larr; Back to gallery
      </Link>

      <img
        src={photo.src}
        alt={photo.alt}
        className="mt-4 w-full rounded-lg"
      />
      <h1 className="mt-4 text-2xl font-bold">{photo.title}</h1>
      <p className="mt-1 text-zinc-600">{photo.description}</p>
    </section>
  );
}
```

**`async function getPhoto(id)`** — shared helper — generateMetadata aur page dono ko photo chahiye — **duplicate query logic se bachne** ke liye ek function (DRY). **`generateMetadata`** — dynamic metadata — `title: photo.title` (har photo ka apna), `description: photo.description ?? photo.alt` (description na ho toh alt — fallback). **Photo nahi mila** — `notFound()` metadata mein direct nahi chalta — isliye `return { title: "Photo Not Found" }` — safe fallback.

## What It Is NOT

- **Photo model = "relations ke bina weak" nahi.** Relations tab chahiye jab cheezein jude hon. Yahan ek photo independent hai — user/album nahi (7.7.1 decision). Simple model by design — focus optimization + routing. Relations 6.13 mein alag se proven.
- **`prisma.photo.findMany()` = Drizzle ke `db.select()` jaisa hi nahi.** Same concept (ORM read), alag syntax (Prisma style). `findMany` = multiple, `findUnique` = ek (primary key). Drizzle ka `select` vs Prisma ka `findMany` — 6.3 ka compare — API alag, idea same.
- **Seed script = "production data" nahi.** Seed development data hai — testing ke liye. Production mein seed nahi chalti (manually/elsewhere data aata hai). `createMany` bulk insert — ek query, multiple rows.
- **`generateMetadata` = static `export const metadata` jaisa nahi.** Static metadata compile-time fixed hai. `generateMetadata` **params-dependent dynamic** hai — har photo ka apna title. Detail page pe metadata = dynamic (photo-specific), home pe static — dono 2.4 ka hissa.
- **`getPhoto` helper = "unnecessary function" nahi.** generateMetadata + page dono ko photo chahiye — ek function se DRY + single source. Duplicate query logic do jagah = galti ke chances do jagah.
