In 4.2 we built `proxy.ts` and saw that it runs on every request — we excluded static files with a matcher, but **the regex was copied without understanding it.** Now we learn the matcher properly: simple route, multiple routes, children routes, and the negative matcher — and which pattern to use when.

---

## Problem — What's Wrong Now

Right now the proxy runs on **every** request (the negative matcher version). That causes two problems:

1. **Performance** — the proxy is wasted on CSS, JS, images
2. **Wrong place** — we only want to check on the routes where it matters

The matcher's job: decide **"where the proxy runs, where it doesn't."** One pattern for each route, understood up front.

---

## Step 1 — Simple Matcher (One Route)

Update the matcher in `proxy.ts`:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  console.log("Proxy running:", request.nextUrl.pathname)
  return NextResponse.next()
}

export const config = {
  matcher: "/dashboard",
}
```

**Test:** visit `/dashboard` — **nothing prints!**

Why? — **Next.js didn't restart.** Config changes require a dev server restart (`Ctrl+C`, then `npm run dev`). Function body changes hot-reload, but `config` does not — one rule to remember: **matcher changed → restart the server.**

After restarting:

```
http://localhost:3000/dashboard → "Proxy running: /dashboard" ✅
http://localhost:3000/about     → nothing ✅
```

---

## Step 2 — Multiple Routes (Array)

To cover two, three routes — use an **array** instead of a string:

```ts
export const config = {
  matcher: ["/dashboard", "/profile", "/settings"],
}
```

**Test:**

```
/dashboard → runs ✅
/profile   → runs ✅
/settings  → runs ✅
/about     → doesn't run ✅
```

Simple rule: the proxy runs on **only** those exact three paths.

---

## Step 3 — Children Routes (`:path*`)

But think about this — `/dashboard` likely has pages inside it:

- `/dashboard/settings`
- `/dashboard/analytics`
- `/dashboard/users/123`

Just writing `"/dashboard"` means the proxy runs **only** on the exact `/dashboard` path — not on its children. Why? Because the matcher compares the path as a string — `/dashboard/settings` is a different string than `/dashboard`.

To cover children, add `:path*`:

```ts
export const config = {
  matcher: ["/dashboard/:path*"],
}
```

The `*` means **"zero or more"** — anything after `/dashboard`, or nothing at all. `:path` is just a named wildcard — the name means nothing; `:anything*` works the same. Think of the pattern like this:

```
/dashboard           → match (zero extra) ✅
/dashboard/settings  → match (one extra)  ✅
/dashboard/users/123 → match (two extra)  ✅
/about               → no match           ❌
```

---

## Step 4 — The Problem That Arises: Static Files

Add `/dashboard/:path*` and visit `/dashboard` — **the page won't load!**

Why? Because Next.js makes **extra requests** on every page load:

- `/_next/static/...` — JS/CSS files
- `/_next/image/...` — optimized images
- `/favicon.ico` — browser icon

And from the matcher's perspective... `/_next/static/...` does not start with `/dashboard` — that's wrong. **Wait** — Next.js 16 changed the static assets URL structure (prefixed paths), but the problem is the same: there are paths you do **not** want to match, and they fall into the `:path*` pattern's logic. The real rule:

**`:path*` + a specific route can accidentally match static assets** — because the pattern is prefix-based. So you need an alternative that says "run on everything EXCEPT these things" — that is the **negative matcher**.

---

## Step 5 — Negative Matcher (Run Everywhere, Except...)

The **negative matcher** = "run everywhere EXCEPT these":

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"],
}
```

Now let's actually break down that regex (in 4.2 it was copy-pasted):

```
"/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"
```

Piece by piece:

| Part | Meaning |
|---|---|
| `/` | The path starts with `/` |
| `(...)` | A group — wraps the whole thing as one unit |
| `(?!...)` | **Negative lookahead** — "if it is NOT this" (checks without consuming) |
| `_next/static\|_next/image\|favicon.ico\|.*\\.svg` | `\|` = OR. These are the paths to **exclude** |
| `.*` | Zero or more of any character — everything else |

**Read it as:** "After `/`, whatever comes — if it is NOT `_next/static`, `_next/image`, `favicon.ico`, or a `.svg` file — then match."

So `/about` matches (no excluded item found), but `/_next/static/css/xyz.css` does not match (it's in the excluded list).

---

## Step 6 — Real Scenario: Exclude Login and API Routes

In a real app, more things need excluding — the **login page** (otherwise an infinite redirect loop — detailed in 4.8) and **API routes** (API routes have their own auth layer):

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|login|api).*)"],
}
```

**Test:**

```
/              → runs ✅
/dashboard     → runs ✅
/login         → doesn't run — it's public ✅
/api/anything  → doesn't run — it's an API route ✅
```

---

## Step 7 — Which Pattern When? (Rule of Thumb)

```
If few protected routes (2-3) → list them specifically
  matcher: ["/dashboard/:path*", "/profile/:path*"]

If many protected routes      → use negative matcher
  matcher: ["/((?!login|api|_next/static|_next/image|favicon.ico).*)"]
```

**In real apps** the negative matcher is more common — there tend to be more protected routes, and maintaining a list is painful. (This series uses the negative matcher throughout.)

---

## What It Is NOT

- **The matcher is not the proxy "logic."** The matcher is just a routing decision (which paths reach the proxy function). The real logic lives inside `proxy()`. The matcher can be more complex too (comma-separated conditions are supported — but that is outside this series' scope; the baseline above handles it).
- **`startsWith` is not used — it is exact-path matching.** `"/dashboard"` does not match `/dashboard/settings` (children need `:path*`). Forget string-prefix logic — the matcher has its own pattern language.
- **Regex appears only in the negative matcher.** Simple strings and `:path*` patterns have no regex. A matcher can mix both types.

## Common Mistakes

- **Not restarting after a matcher change** — the most common mistake. The function body hot-reloads, the config does not. Changed it? Restart.
- **Forgetting children.** Set a matcher for `/dashboard` and it won't run on `/dashboard/settings` — you need `:path*`.
- **Accidentally matching static files with `:path*`** — use the full negative matcher pattern.
- **Copying regex without understanding it.** Now you do: `(?!...)` means "except", `|` means OR, `.*` means "everything else."

## Nutshell

The matcher controls **where the proxy runs**. One route (string), multiple (array), children (`:path*`), everything-except (negative regex `(?!...)`). Rule: few routes → specific list; many → negative. Config changes require a server restart.

**In Your Own Words**

1. What is the difference between matcher `"/dashboard"` and `"/dashboard/:path*"`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `"/dashboard"` is an exact string match — the proxy runs only on `/dashboard`, not on `/dashboard/settings` (a different string entirely). `"/dashboard/:path*"` is a prefix pattern — `*` means "zero or more", so it runs on `/dashboard` and all its children (`/dashboard/settings`, `/dashboard/users/123`). Without `:path*` you'd need a separate entry for each child; one pattern covers them all.

</details>

2. Explain the negative matcher `"/((?!_next/static|_next/image|favicon.ico).*)"` in your own words — what does `(?!...)`, `|`, and `.*` do?

<details>
<summary>Show Answer</summary>

**Sample Answer:** This regex says "run everywhere EXCEPT these": the path starts with `/`, `(?!...)` is a negative lookahead — "if it is NOT this" — `|` is OR joining the exclusion list (`_next/static` OR `_next/image` OR `favicon.ico`), and `.*` is "zero or more of any character" — everything else. In total: if the path is not in the excluded list, match it. This is how you prevent the proxy from running on every tiny JS/CSS file.

</details>

3. Why do you have to restart the dev server after changing the matcher?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because the `config` (and its matcher) is read at startup — Next.js decides at boot time which paths reach the proxy. The `proxy()` function body hot-reloads (via dev HMR), but the config does not — it loads once when the server starts. So: matcher changed → restart is required. That rule comes from 4.2 as well: config change, restart.

</details>

4. In a real app, why are `login` and `api` excluded from the negative matcher?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `login` is excluded because the login page must be public — if the proxy runs its auth check on `/login`, a logged-out user visiting `/login` gets redirected to `/login` → infinite redirect loop (demonstrated fully in 4.8). `api` is excluded because API routes have their own auth/validation layer — a page-level proxy check is irrelevant there (and unnecessary overhead). The exclude list is really "don't run the proxy where it doesn't belong."

</details>

5. When do you use a specific route list vs. a negative matcher?

<details>
<summary>Show Answer</summary>

**Sample Answer:** When there are few protected routes (2-3), use a specific list — `["/dashboard/:path*", "/profile/:path*"]` — it's clear and predictable. When there are many routes, use the negative matcher — a list becomes painful to maintain, and the "run everywhere except some public paths" model fits real apps better. Real apps tend to use the negative matcher. Both can coexist in the same matcher array.

</details>

## Where We Left Off

In 4.3 we learned the matcher — control over where the proxy runs. Now **what arrives inside the proxy** — the request data is the input for all decisions. First, the most obvious: the URL. The entire URL is in `request.nextUrl` — today we read `pathname` and `searchParams`, and the `.startsWith()` pattern for checks.

---

## What Is `request.nextUrl`?

Inside the proxy, you receive a `request` — of type `NextRequest` — and inside it is a property: **`nextUrl`** — a parsed URL object. First, log it to see the real data:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  console.log(request.nextUrl)
  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
}
```

Visit in the browser:

```
http://localhost:3000/dashboard?tab=settings&user=123
```

You will see something like this in the terminal:

```js
URL {
  href: 'http://localhost:3000/dashboard?tab=settings&user=123',
  pathname: '/dashboard',
  search: '?tab=settings&user=123',
  searchParams: URLSearchParams { 'tab' => 'settings', 'user' => '123' },
  ...
}
```

There are many properties (href, host, origin, protocol...) — in this series, `pathname` and `searchParams` will do the work.

---

## `pathname` — The Path Part of the URL

The URL structure:

```
http://localhost:3000/dashboard?tab=settings
                       ↑              ↑
                   pathname        search (query string)
```

The `pathname` is everything after the domain and before the `?`:

```ts
const pathname = request.nextUrl.pathname
console.log(pathname) // → "/dashboard"
```

**Practical use** — find out where the user is going:

```ts
export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  console.log("User is heading to:", pathname)
  return NextResponse.next()
}
```

```
/          → "User is heading to: /"
/dashboard → "User is heading to: /dashboard"
/profile   → "User is heading to: /profile"
```

---

## `searchParams` — The Query Parameters

Everything after the `?` — `searchParams`:

```
http://localhost:3000/products?category=shoes&color=red
                                  ↑
                           these are searchParams
```

Pull out any parameter with `.get()`:

```ts
export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const category = request.nextUrl.searchParams.get("category")
  console.log("pathname:", pathname)
  console.log("category:", category)
  return NextResponse.next()
}
```

`searchParams.get("category")` — pass the parameter name as a string, get its value. If the parameter is **not present in the URL** — you get `null`:

```
/products?category=shoes → category: "shoes"
/products               → category: null
```

---

## Combined — Checking Conditions on the Path

Now combine it — make decisions based on the path:

```ts
export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname

  if (pathname.startsWith("/dashboard")) {
    console.log("User is on a dashboard route")
  }

  return NextResponse.next()
}
```

`.startsWith("/dashboard")` — a string method — "does this string start with `/dashboard`?" — returns `true`/`false`.

```
/dashboard          → "User is on a dashboard route" ✅
/dashboard/settings → "User is on a dashboard route" ✅  (prefix match)
/about              → nothing ✅
```

`startsWith` is useful here because `/dashboard/settings` and other child paths are also covered — prefix checks, not exact comparisons. (4.3's matcher handled `:path*` at the URL level; `startsWith` does it at the logic level.)

---

## What It Is NOT

- **`searchParams` is not a plain object.** It is a `URLSearchParams` instance. Use `.get("key")`, not `searchParams.category`.
- **`pathname` does not include the query string.** For `/dashboard?tab=settings`, the `pathname` is just `/dashboard`. The domain is not part of it either — just the path.
- **`request.url` and `request.nextUrl` are not the same thing.** `request.url` is the raw URL string; `nextUrl` is Next.js's parsed object (pathname, searchParams ready to use). Proxy code uses `nextUrl`.

## Common Mistakes

- **Comparing `pathname` exactly.** `pathname === "/dashboard"` misses `/dashboard/settings`. Use `startsWith` for prefix checks.
- **Forgetting to null-check `searchParams.get()`.** When the parameter is missing you get `null` — handle it with a fallback or check (the `?? "default"` pattern comes up again with headers in 4.5).
- **Forgetting that the matcher filters first.** If the matcher only allows `/dashboard` and your code checks for `/about`, the code never runs. Think of matcher and logic together.

## Nutshell

`request.nextUrl` is a parsed URL object. `pathname` is the path (`/dashboard`), `searchParams.get("key")` returns a query value (missing → `null`), and `startsWith()` is for prefix checks. This is the proxy's input for "where is the user going."

1. What part of the URL does `request.nextUrl.pathname` give you — with an example?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Everything after the domain and before the `?` — just the path. Example: for `http://localhost:3000/dashboard?tab=settings`, the `pathname` is only `/dashboard` — neither the query (`?tab=settings`) nor the domain. On every request the proxy knows which page the user is heading to.

</details>

2. What does `searchParams.get("category")` return — and when the parameter is absent from the URL?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The value as a string — `"shoes"` for `?category=shoes`. If the parameter is not in the URL at all (`/products` with no query), it returns `null`. Because of that, always handle the result with a fallback (`?? "default"`) or an explicit check — using the raw null value causes silent bugs in logic.

</details>

3. Why is `startsWith("/dashboard")` better than `=== "/dashboard"` for proxy checks?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because `===` is an exact string match — `/dashboard/settings` fails (it is a different string). `startsWith` is a prefix check — `/dashboard`, `/dashboard/settings`, `/dashboard/users/123` all return true. For protected-route checks you want that coverage: one root path, all children included. Exact comparison only makes sense when one specific page matters.

</details>

4. `request.url` vs `request.nextUrl` — what is the difference?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `request.url` is the raw URL string — the full `http://localhost:3000/dashboard?tab=settings` as one string. `request.nextUrl` is Next.js's parsed URL object — with pathname, searchParams, href, and other properties ready to use. The proxy needs the parsed version (to pull path and query separately) — so `nextUrl` is preferred. `url` is useful as a base for `new URL(path, request.url)` in 4.8.

</details>

5. What is the relationship between the matcher and the `startsWith` check in code?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The matcher decides first whether the request even reaches the proxy (a routing-level filter), then the `startsWith` check in code decides what to do with it (a logic-level decision). If the matcher is limited to `/dashboard` and the code checks for `/about`, that code never runs. Keep them consistent: the matcher handles "where", and the code handles "what" for paths already allowed through.

</details>
