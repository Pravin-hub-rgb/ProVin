# Reading Cookies — The Session Check
554: 
555: ## Where We Left Off
556: 
557: In 4.5 we read headers — `user-agent` for devices, `x-forwarded-for` for IP, `host` for domain. But headers cover more than that: cookies travel inside the `Cookie` header. Because they are so central to request-level state, Next.js exposes them through a dedicated `request.cookies` API rather than forcing you to parse the header string. Cookies are the browser↔server data channel that persists across requests (a session ID, a preference). We learn to read them here and build the seed of the login check that 4.8 turns into redirects.
558: 
559: ## Cookies Travel Inside the `Cookie` Header
560: 
561: When the browser sends a request, it attaches stored cookies in one header:
562: 
563: ```
564: Cookie: session=abc123; theme=dark
565: ```
566: 
567: Parsing that string into individual cookies — splitting on `;`, then on `=` — is error-prone if done by hand. `request.cookies` does it for you and exposes two helpers.
568: 
569: ## Step 1 — Reading a Cookie's Value (`.get`)
570: 
571: `.get("name")` returns the cookie object `{ name, value }` or `null`:
572: 
573: ```ts
574: import { NextRequest, NextResponse } from "next/server"
575: 
576: export function proxy(request: NextRequest) {
577:   const sessionCookie = request.cookies.get("session")
578:   console.log("Session cookie:", sessionCookie)
579:   return NextResponse.next()
580: }
581: ```
582: 
583: When the cookie `session=abc123` is present:
584: 
585: ```js
586: Session cookie: { name: 'session', value: 'abc123' }
587: ```
588: 
589: Note it returns an **object**, not a string — pull `.value` to use the data:
590: 
591: ```ts
592: const value = sessionCookie?.value   // → "abc123"
593: ```
594: 
595: The `?.` matters because `.get()` returns `null` when the cookie is absent — the same defensive pattern from 4.5.
596: 
597: ## Step 2 — Checking Presence (`.has`)
598: 
599: Often you only need to know existence, not the value. `.has("name")` returns `true` or `false`:
600: 
601: ```ts
602: export function proxy(request: NextRequest) {
603:   const hasSession = request.cookies.has("session")
604: 
605:   if (!hasSession) {
606:     console.log("No session — needs redirect to login")
607:   } else {
608:     console.log("Has session — let through")
609:   }
610: 
611:   return NextResponse.next()
612: }
613: ```
614: 
615: ```
616: no cookie               → "No session — needs redirect to login"
617: Cookie: session=abc123  → "Has session — let through"
618: ```
619: 
620: ## Step 3 — The Login-Check Skeleton
621: 
622: This is the shape every auth-style proxy builds on. Wire it up now; 4.8 fills in the redirect; 4.12 fills in the full flow:
623: 
624: ```ts
625: export function proxy(request: NextRequest) {
626:   const hasSession = request.cookies.has("session")
627: 
628:   if (!hasSession) {
629:     // TODO: redirect to login (4.8)
630:     console.log("No session")
631:   } else {
632:     console.log("Has session")
633:   }
634: 
635:   return NextResponse.next()
636: }
637: ```
638: 
639: What matters here is the pattern: read session presence once, branch on it, leave a TODO for the redirect. That two-branch shape is the skeleton of protected routes.
640: 
641: ## Testing Manually — Plant a Cookie in DevTools
642: 
643: To exercise the session-present branch, drop a cookie manually:
644: 
645: ```
646: F12 → Application → Cookies → localhost:3000 → (+)
647: Name: session
648: Value: abc123
649: ```
650: 
651: Reload — the proxy runs against the cookie you placed. Delete it to return to the no-session branch.
652: 
653: ## What It Is NOT
654: 
655: - **`request.cookies` only reads.** Setting cookies on the *response* (4.10 covers `response.cookies.set()`) is the reverse direction. Inside the proxy you only observe incoming cookies.
656: - **Cookie presence is not verified auth.** Finding a `session` cookie proves a cookie exists, not that it is valid. DevTools lets anyone plant `session=anything`. Real auth checks the value against the session store — 4.12 explains why the proxy is not where that belongs. This is a demo check.
657: - **`request.cookies` and `cookies()` from `next/headers` are not the same thing.** `request.cookies` comes with the proxy's request object. `cookies()` is the API inside Server Components and Route Handlers — related, different context.
658: 
659: ## Common Mistakes
660: 
661: - **Treating `.get()` as returning a string.** It returns `{ name, value }` — use `.value`.
662: - **Forgetting `?.value`.** A missing cookie makes `.get()` return `null` — accessing `.value` on `null` throws.
663: - **Using `.get()` where `.has()` is clearer.** Both test existence; `.has()` reads as intent when you only need a boolean.
664: - **Trusting cookie presence as authentication.** This is a demo check. Verified auth validates the value (4.12).
665: 
666: ## Nutshell
667: 
668: `request.cookies.get("name")` → `{ name, value }` (or `null` when absent). `request.cookies.has("name")` → `true`/`false`. The login check reads presence and branches. Presence is a demo check, not verified auth — that distinction is central to 4.12.

670: ## In Your Own Words
671: 
672: <details>
673: <summary>1. Why does `request.cookies` exist when cookies arrive as a header?</summary>
674: 
675: **Sample Answer:** Cookies arrive inside the `Cookie` header as one string — splitting it into name/value pairs with `split(";")` then `split("=")` is repetitive and buggy. `request.cookies` parses once and exposes `.get()` and `.has()`, so every proxy file reads cookies directly instead of hand-rolling string parsing.
676: 
677: </details>
678: 
679: <details>
680: <summary>2. What does `.get("session")` return, and what does `.has("session")` return?</summary>
680: 
681: **Sample Answer:** `.get("session")` returns the cookie object `{ name, value }` (or `null`), so you also get the value. `.has("session")` returns a boolean — `true` if the cookie exists, `false` if it does not. Use `.has()` when you only need to know whether the cookie is there.
682: 
683: </details>
684: 
685: <details>
686: <summary>3. What is the login-check skeleton, and how does it branch?</summary>
687: 
687: **Sample Answer:** Read session presence with `request.cookies.has("session")`, then branch: if absent, handle the unauthenticated case (redirect — added in 4.8); if present, let the request continue with `NextResponse.next()`. That two-branch shape is the foundation every protected-route proxy expands on.
688: 
689: </details>
690: 
691: <details>
692: <summary>4. Why is "cookie presence" not the same as "verified session"?</summary>
692: 
693: **Sample Answer:** Presence only proves a cookie named `session` exists — its value is not checked against the store. DevTools lets anyone plant `session=anything`, and presence passes. A verified session checks the value (via `auth()` / the session store) to confirm it was actually issued. The proxy presence check is a demo; verified auth is a separate layer (4.12).
693: 
694: </details>
695: 
696: <details>
700: <summary>5. What is the difference between `request.cookies` and `cookies()`?</summary>
700: 
701: **Sample Answer:** Context. `request.cookies` is available in the proxy alongside the request object — the request carries the cookies. `cookies()` from `next/headers` is the API for Server Components and Route Handlers, where there is no direct request object in scope. Same task, different locations.
705: 
706: </details>
