# Matcher — Which Routes Does the Proxy Run On?

## Where We Left Off

In 4.2 we got a working proxy running on every request — but the matcher regex was still copy-pasted without understanding. That means the proxy runs on **everything**, including static assets. Now we learn to control **where** it runs: a single exact route, an array of routes, children routes with `:path*`, and the negative matcher that excludes built-in assets.

## The Problem — Too Broad

With the catch-all matcher, the proxy runs on every request. That creates two problems:

1. **Performance** — proxy logic runs for CSS, JS, and image requests that don't need it.
2. **Wrong targets** — checks meant for pages may fire on routes they were never intended for.

The matcher's job is to answer one question: **on which paths should the proxy run?** Understanding it means you stop excluding paths by accident (or including paths you didn't mean to).

## Step 1 — Exact Single Route

Switch the matcher to a single path:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  console.log("Proxy running:", request.nextUrl.pathname)
  return NextResponse.next()
}

export const config = {
  matcher: "/dashboard",
}
```

Test it: visiting `/dashboard` prints nothing. Why? The dev server did not restart. Function bodies hot-reload in dev, but **the `config` object is read at startup** — matcher changes require a restart (`Ctrl+C`, then `npm run dev` again).

After restarting:

```
http://localhost:3000/dashboard → "Proxy running: /dashboard" ✅
http://localhost:3000/about     → nothing ✅
```

The proxy ran **only** on `/dashboard`.

## Step 2 — Multiple Routes (Array)

Two or three paths? Use an array instead of a string:

```ts
export const config = {
  matcher: ["/dashboard", "/profile", "/settings"],
}
```

```
/dashboard → ran ✅
/profile   → ran ✅
/settings  → ran ✅
/about     → did not run ✅
```

The rule is simple: the string must match **exactly**. `"/dashboard"` will not match `/dashboard/settings`.

## Step 3 — Children Routes (`:path*`)

Now imagine `/dashboard` has children:

- `/dashboard/settings`
- `/dashboard/analytics`
- `/dashboard/users/123`

With `"/dashboard"` alone, **none** of those match — the matcher treats paths as strings, and `/dashboard/settings` is a different string. You need the wildcard:

```ts
export const config = {
  matcher: ["/dashboard/:path*"],
}
```

`:path*` means **zero or more** path segments after `/dashboard`:

```
/dashboard           → match ✅  (zero extra segments)
/dashboard/settings  → match ✅  (one extra)
/dashboard/users/123 → match ✅  (two extra)
/about               → no match ❌
```

The `:path` part is just a name for the wildcard — `:anything*` works identically. Read the pattern as: "anything starting with `/dashboard`, optionally followed by more segments."

## Step 4 — The Problem This Creates: Static Assets

Add `:path*` and visit `/dashboard` — and the page **won't load**.

Why? Next.js issues several extra requests just to render a page:

- `/_next/static/...` — JS and CSS bundles
- `/_next/image/...` — optimized images
- `/favicon.ico` — the browser icon

In Next 16, the asset URL structure changed slightly (prefixed paths), but the problem is the same: some paths you **never** want to intercept, and `:path*` patterns can catch them.

The solution is the **negative matcher** — "run on everything **except** these."

## Step 5 — Negative Matcher (Exclude by Name)

The standard negative matcher:

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"],
}
```

This is the regex most tutorials copy without explanation — now we decode it:

```
/((?!_next/static|_next/image|favicon.ico|.*\.svg).*)
```

| Fragment | Meaning |
|---|---|
| `/` | paths start after the leading slash |
| `( ... )` | wraps everything into one group so the lookahead applies to the whole path |
| `(?!...)` | **negative lookahead** — "only match if this does **not** follow" (it checks without consuming the characters) |
| `_next/static\|_next/image\|favicon.ico\|.*\\.svg` | the `\|` alternatives — the paths to **exclude** |
| `.*` | "any characters" — matches the rest of the path if it survived the lookahead |

Read it aloud: "Any path that is not `_next/static`, `_next/image`, `favicon.ico`, or a `.svg`."

Result: `/about` matches (it is not in the exclusion list), but `/_next/static/css/xyz.css` does not (it is excluded).

## Step 6 — Real App: Exclude Login and API Routes

Real applications also exclude public pages and API routes:

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|login|api).*)"],
}
```

```
/              → ran ✅
/dashboard     → ran ✅
/login         → skipped ✅  (public page)
/api/anything  → skipped ✅  (API handles its own checks)
```

## Step 7 — Which Pattern When

```
Few protected routes (2–3) → specific list:
  matcher: ["/dashboard/:path*", "/profile/:path*"]

Many protected routes      → negative matcher:
  matcher: ["/((?!login|api|_next/static|...).*)"]
```

Real apps most often use the negative form — listing every protected route is tedious, and "run everywhere except public/internal paths" is a cleaner model. (This series uses negative matchers the majority of the time.)

## What It Is NOT

- **The matcher is not proxy logic** — it only decides which requests **reach** the proxy function. The real decisions live inside `proxy()`.
- **Matcher matching is not `startsWith`** — `"/dashboard"` matches only that exact path string, not `/dashboard/settings`. That needs `:path*`.
- **Regex only applies to negative matchers** — plain strings and `:path*` are not regex. A single matcher array can mix both types.

## Common Mistakes

- **Changing the matcher without restarting the dev server** — the single most common mistake. The function body hot-reloads; the matcher does not. Always restart after a matcher change.
- **Forgetting children** — `/dashboard` does not cover `/dashboard/settings`. Use `:path*` for prefix groups.
- **Letting `:path*` accidentally catch static assets** — that is why the negative matcher carries the full exclusion list.
- **Copy-pasting the regex without understanding it** — now you can read it: `(?!...)` is "except," `|` is "or," `.*` is "rest."

## Nutshell

The matcher controls where the proxy runs. Exact single path: `"/dashboard"`. Multiple: `["/a", "/b"]`. Children: `":path*"`. Exclude assets: negative regex `(?!...)` with the standard `_next/static | _next/image | favicon.ico | .svg` list. Few protected routes → specific list. Many → negative matcher. Remember: matcher changes require a server restart.

<summary>3. Why must you restart the dev server after changing the matcher?</summary>

**Sample Answer:** The `config` object — including the matcher — is read when the dev server starts up. The proxy function's body hot-reloads on save, but the routing table derived from `config` does not rebuild until a restart. A matcher change without a restart just does nothing.

</details>

<details>
<summary>4. Why exclude `login` and `api` from the matcher in a real app?</summary>

</details>

<summary>5. Single route list vs. negative matcher — when to use each?</summary>

**Sample Answer:** Use a specific list when only a few routes need the proxy — it is explicit and predictable. </details>

## Where We Left Off

In 4.3 we learned how to control **where** the proxy runs via the matcher. Now we look at **what** the proxy has access to when it runs. The `request` object passed to the proxy is a `NextRequest`, and it carries `nextUrl` — a parsed URL. We read two parts today: `pathname` (the path) and `searchParams` (the query string), plus the `startsWith` pattern for prefix checks.

## `request.nextUrl` — The Parsed URL

Log the full thing to see what Next.js gives you:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  console.log(request.nextUrl)
  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
}
```

Open in the browser:

```
http://localhost:3000/dashboard?tab=settings&user=123
```

Terminal shows a structured URL object:

```js
URL {
  href: 'http://localhost:3000/dashboard?tab=settings&user=123',
  pathname: '/dashboard',
  search: '?tab=settings&user=123',
  searchParams: URLSearchParams { 'tab' => 'settings', 'user' => '123' },
  ...
}
```

There are many properties (href, host, origin, protocol ...) — this series uses `pathname` and `searchParams`, the two that actually drive decisions.

## `pathname` — The Path Portion

A URL breaks down as:

```
http://localhost:3000/dashboard?tab=settings
                       ↑              ↑
                   pathname        search
```

`pathname` is everything after the host and before the `?`:

```ts
const pathname = request.nextUrl.pathname
console.log(pathname) // → "/dashboard"
```

In practice it answers the question: **where is the user trying to go?**

```ts
export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  console.log("User heading to:", pathname)
  return NextResponse.next()
}
```

```
/          → "User heading to: /"
/dashboard → "User heading to: /dashboard"
/profile   → "User heading to: /profile"
```

## `searchParams` — The Query String

Everything after the `?` is query data:

```
http://localhost:3000/products?category=shoes&color=red
                                  ↑
                          searchParams here
```

Pull any parameter out with `.get()`:

```ts
export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const category = request.nextUrl.searchParams.get("category")
  console.log("pathname:", pathname)
  console.log("category:", category)
  return NextResponse.next()
}
```

`.get("category")` takes the parameter name and returns its value. If that parameter is entirely absent from the URL, `.get()` returns `null`:

```
/products?category=shoes → category: "shoes"
/products               → category: null
```

## Combined — Deciding Based on the URL

Now combine reading and deciding:

```ts
export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname

  if (pathname.startsWith("/dashboard")) {
    console.log("User is heading to the dashboard area")
  }

  return NextResponse.next()
}
```

`.startsWith("/dashboard")` is a string method — "does this string begin with `/dashboard`?" — returning `true` or `false`.

```
/dashboard          → "User is heading to the dashboard area" ✅
/dashboard/settings → "User is heading to the dashboard area" ✅  (prefix match)
/about              → nothing ✅
```

`startsWith` is the tool for prefix checks — where 4.3's `:path*` handled it at the matcher level, `startsWith` handles it inside the proxy logic. For protected-route checks, you almost always want the prefix form, not strict equality.

## What It Is NOT

- **`searchParams` is not a plain object** — it is a `URLSearchParams` instance. Use `.get()`, not `searchParams.category`.
- **`pathname` does not include the query string** — for `/dashboard?tab=settings`, `pathname` is just `/dashboard`. The host is not in `pathname` either.
- **`request.url` and `request.nextUrl` are not the same** — `request.url` is the raw URL string; `nextUrl` is Next.js's parsed object with `pathname` and `searchParams` already split out. Proxy logic uses `nextUrl`.

## Common Mistakes

- **Strict equality on `pathname` where a prefix is needed** — `pathname === "/dashboard"` misses `/dashboard/settings`. Use `startsWith` for groups.
- **Ignoring the `null` return from `searchParams.get`** — a missing parameter yields `null`. Use a fallback (`?? "default"`) or an explicit check.
- **Misaligning the matcher with the logic** — the matcher filters which requests even reach the proxy; logic then decides what to do. If the matcher never lets `/about` through, any check for `/about` never runs. Keep both consistent.

## Nutshell

`request.nextUrl` is the parsed URL. `pathname` is the path (`/dashboard`); `searchParams.get("key")` is a query value (missing → `null`); `startsWith()` handles prefix checks. That is how the proxy answers "where is the user going, and what did they include?"

## Where We Left Off

In 4.4 we learned to read the URL itself — `pathname` and `searchParams`. But the request also carries extra information **around** the URL in its headers. Think of a parcel: the package body is the request data, but the label (sender, receiver, "Fragile", "Urgent" stickers) describes the parcel without opening it. Headers are that label — request metadata the proxy can read before any page logic runs.

## What Are Headers?

When the browser asks for something, it attaches key-value pairs — headers:

```
User-Agent: Mozilla/5.0 (iPhone; ...) Mobile Safari
Host: localhost:3000
Accept: text/html
Cookie: session=abc123
```

Every request carries these (the browser sends them automatically). The proxy can read them with `request.headers.get("name")`:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const userAgent = request.headers.get("user-agent")
  console.log("User-Agent:", userAgent)
  return NextResponse.next()
}
```

`headers.get("user-agent")` returns the value as a string, or `null` if the header is absent (the same `null`-unless-present rule as `searchParams.get`).

## Step 1 — Device Detection via `User-Agent`

The most common use is detecting the visitor's device. The browser reports itself in `User-Agent`, so you can spot mobile traffic:

```ts
export function proxy(request: NextRequest) {
  const userAgent = request.headers.get("user-agent")

  if (userAgent?.includes("Mobile")) {
    console.log("Request came from a mobile device")
  }

  return NextResponse.next()
}
```

`.includes("Mobile")` is a string method — "does the string contain this substring?" — returning `true` or `false`. Notice `userAgent?.includes(...)` — the `?.` is optional chaining: if `userAgent` is `null`, rather than throwing, the expression short-circuits to `undefined`. This was shown in 4.1 as defensive coding; here it is doing real work — a missing header never crashes the proxy.

Try it: open from a phone → "mobile" logs. From desktop → nothing logs.

Today, responsive design handles most device differences, but knowing how to read `User-Agent` is a recurring skill — for device-specific features, legacy redirects, or server-rendered device detection.

## Step 2 — Reading the IP (`x-forwarded-for`)

The other header that keeps coming up is **`x-forwarded-for`** — the client's IP.

> **A concept worth anchoring:** in this app's architecture, the browser does not talk directly to your application server. Traffic passes through an intermediate machine — a load balancer or CDN. The server sees a connection from that middle machine, not from the user. The middle layer records the real client IP in the `x-forwarded-for` header and forwards it on.

```ts
export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  console.log("IP:", ip)
  return NextResponse.next()
}
```

`?? "unknown"` is nullish coalescing: if the header is `null` (absent), fall back to `"unknown"` instead of logging `null`.

Testing with curl (spoofing an IP):

```bash
curl -H "X-Forwarded-For: 49.36.10.5" http://localhost:3000/
```

```
IP: 49.36.10.5
```

Locally on `localhost`, you will often see values like `::ffff:127.0.0.1` — that is an IPv6-mapped IPv4 address; it is still just localhost.

That IP becomes the key for later features: 4.13 (rate limiting — "how many requests from this IP?") and 4.14 (geo blocking — "where is this IP?").

## Step 3 — Host and Anything Else

`.get("host")` tells you which domain the request targeted:

```ts
const host = request.headers.get("host")
console.log("Host:", host) // → "localhost:3000"
```

Host matters when one application serves multiple domains. Every other header follows the same `.get()` pattern — one method, any header name.

## What It Is NOT

- **Reading a header is not modifying it.** `headers.get` only reads. Adding headers to the response (4.10) is a separate operation.
- **`x-forwarded-for` is not trustworthy on its own** — it is set by the intermediate layer, but a client can include it too (as the curl test shows). Production setups have the trusted proxy overwrite it; never trust the raw, client-supplied value for security decisions.
- **`User-Agent` is not authoritative either** — it is client-controlled. Treat it as a hint for UX, not a hard security signal.

## Common Mistakes

- **Forgetting `?.` on optional headers** — `userAgent.includes(...)` throws when the header is `null`. `userAgent?.includes(...)` is safe.
- **Using the raw IP without a fallback** — `?? "unknown"` keeps logs clean when the header is absent.
- **Assuming header names are case-sensitive** — they are not. `"user-agent"`, `"User-Agent"`, `"USER-AGENT"` all resolve to the same header; lowercase is the convention.
- **Logging sensitive headers** — never write `authorization`, `cookie`, or tokens to logs.

## Nutshell

`request.headers.get("name")` reads request headers. `user-agent` → device detection (`includes("Mobile")`, guarded with `?.`); `x-forwarded-for` → client IP (`?? "unknown"`); `host` → domain. Headers are spoofable — treat as hints, not proof. The IP from `x-forwarded-for` becomes the key for rate limiting (4.13) and geo blocking (4.14).

## Where We Left Off

In 4.5 we read headers — `user-agent` for devices, `x-forwarded-for` for IP, `host` for domain. But headers cover more than that: cookies travel inside the `Cookie` header. Because they are so central to request-level state, Next.js exposes them through a dedicated `request.cookies` API rather than forcing you to parse the header string. Cookies are the browser↔server data channel that persists across requests (a session ID, a preference). We learn to read them here and build the seed of the login check that 4.8 turns into redirects.

## Cookies Are Headers — So Why the Dedicated API?

Strictly speaking, cookies arrive as a single `Cookie` header:

```
Cookie: session=abc123; theme=dark
```

But splitting that string into individual cookies — `split(";")`, then `split("=")` — is tedious and error-prone on every file. `request.cookies` does that parsing for you and exposes the results directly.

## Step 1 — Reading a Cookie's Value

`.get("name")` returns an object `{ name, value }`:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const sessionCookie = request.cookies.get("session")
  console.log("Session cookie:", sessionCookie)
  return NextResponse.next()
}
```

When a `session=abc123` cookie is present:

```js
Session cookie: { name: 'session', value: 'abc123' }
```

Note the return is an **object**, not a string — pull `.value` to use the actual data:

```ts
const value = sessionCookie?.value  // → "abc123"
```

The `?.` is there because `.get()` returns `null` when the cookie is absent — the same defensive pattern from 4.5.

## Step 2 — Existence Check with `.has()`

Often you only need to know whether a cookie exists, not its value. `.has("name")` returns `true` / `false`:

```ts
export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has("session")

  if (!hasSession) {
    console.log("No session — should send to login")
  } else {
    console.log("Has session — let through")
  }

  return NextResponse.next()
}
```

```
no cookie              → "No session — should send to login"
Cookie: session=abc123 → "Has session — let through"
```

## Step 3 — The Login-Check Skeleton

This is the shape every auth-style proxy builds on. Hook it up now; 4.8 supplies the redirect, 4.12 supplies the full flow:

```ts
export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has("session")

  if (!hasSession) {
    // TODO: redirect to login (4.8)
    console.log("No session")
  } else {
    console.log("Has session")
  }

  return NextResponse.next()
}
```

**What matters here:** read the session presence once, branch on it, and leave a TODO for the redirect. That two-branch shape is the skeleton of protected routes.

## Setting Cookies for Testing (Manual)

To test the session-present path, set a cookie in the browser:

```
F12 → Application → Cookies → localhost:3000 → (+)
Name: session
Value: abc123
```

Then reload — the proxy's branch runs against the cookie you planted. Delete it to return to the no-session path.

## What It Is NOT

- **`request.cookies` only reads.** Setting cookies on the *response* (4.10 covers `response.cookies.set()`) is a different direction. Inside the proxy you only observe incoming cookies.
- **Cookie presence ≠ verified session.** Finding a `session` cookie proves a cookie exists, not that it is valid. A user can plant any cookie value via DevTools. Verified auth — checking the value against the session store — happens later (4.12 explains why the proxy is not where that belongs). This is a demo-level check.
- **`request.cookies` and `cookies()` from `next/headers` are different.** `request.cookies` arrives with the proxy's `request` object. `cookies()` is the API used inside Server Components and Route Handlers — a related tool, different context.

## Common Mistakes

- **Treating `.get()` as returning a string** — it returns `{ name, value }`. Use `.value`.
- **Forgetting `?.value`** — a missing cookie makes `.get()` return `null`; accessing `.value` on `null` throws.
- **Using `.get()` where `.has()` is clearer** — both can test existence, but `.has()` reads as intent when you only need a boolean.
- **Trusting cookie presence as authentication** — this is a demo check only. Real auth verifies the value (4.12).

## Nutshell

`request.cookies.get("name")` → `{ name, value }` (or `null` when absent). `request.cookies.has("name")` → `true`/`false`. The login check reads session presence and branches on it. Cookie presence is a demo check, not verified auth — that distinction is central to 4.12.

## In Your Own Words

<details>
<summary>1. Why does `request.cookies` exist when cookies are just a header?</summary>

**Sample Answer:** Cookies do arrive inside the `Cookie` header as one string — parsing that into individual name/value pairs with `split(";")` and `split("=")` is repetitive and buggy. `request.cookies` parses it once and exposes `.get()` and `.has()`, so every proxy file can read cookies directly instead of hand-rolling string parsing.

</details>

<details>
<summary>2. What is the difference between `.get("session")` and `.has("session")`?</summary>

**Sample Answer:** `.get("session")` returns the cookie object `{ name, value }` (or `null`), so you get the value too. `.has("session")` returns a boolean — `true` if the cookie exists, `false` otherwise. Use `.has()` when you only need to know whether the cookie is there.

</details>

<details>
<summary>3. What is the login-check skeleton, and how does it branch?</summary>

**Sample Answer:** Read session presence with `request.cookies.has("session")`, then branch: if absent, handle the unauthenticated case (redirect — added in 4.8); if present, let the request continue with `NextResponse.next()`. That two-branch shape is the foundation every protected-route proxy expands on.

</details>

<details>
<summary>4. Why is "cookie presence" not the same as "verified session"?</summary>

**Sample Answer:** Presence only proves a cookie named `session` exists — its value is not checked against the store. DevTools lets anyone plant `session=anything`, and presence would pass. A verified session checks the value (via `auth()` / the session store) to confirm it was actually issued by the app. The proxy presence check is a demo; verified auth is a separate layer (4.12).

</details>

<details>
<summary>5. How do `request.cookies` and `cookies()` from `next/headers` differ?</summary>

**Sample Answer:** Context. `request.cookies` is available in the proxy alongside the `request` object — the request itself carries the cookies. `cookies()` from `next/headers` is the API for Server Components and Route Handlers, where there is no direct `request` object in scope. Same task, different locations.

</details>
