4.5 mein headers padhe — IP, user-agent. Ab **cookies** — jo technically ek header hi hain (`Cookie` header), par itne special hain ki Next.js ne inke liye dedicated API banayi hai: `request.cookies`. Cookies ka simple concept: browser aur server ke beech chhota sa data jo har request ke saath apne aap chala jaata hai (jaise "user ka session id"). Yahan iska pura concept seekhenge aur phir wahi cookies **proxy ke andar se** padhenge, aur login-check ka pattern banayenge jo 4.8 mein redirect ke saath complete hoga.

---

## Cookies Technically Headers Hain — Phir Alag API Kyun?

Browser ki taraf se cookie `Cookie` naam ke header mein jaati hai:

```
Cookie: session=abc123; theme=dark
```

Lekin har cookie ko string se parse karna (`split(";")`, phir `split("=")`...) bekar hai — isliye Next.js ne `request.cookies` API banayi jo khud parse kar ke ready objects deti hai.

---

## Step 1 — Cookie Ki Value Nikalna

`.get("name")` — cookie ka naam do, ek object milta hai `{ name, value }`:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const sessionCookie = request.cookies.get("session")
  console.log("Session cookie:", sessionCookie)
  return NextResponse.next()
}
```

Visit karo (cookie ke saath):

```
http://localhost:3000
```

Terminal:

```js
Session cookie: { name: 'session', value: 'abc123' }
```

`.get()` returns ek object — `{ name, value }`. Value nikalni ho toh:

```ts
const value = sessionCookie?.value  // → "abc123"
```

`?.` isliye — cookie **na ho toh** `null` milta hai (4.5 wala same pattern).

---

## Step 2 — Existence Check: `.has()`

Kai baar sirf yeh janna hai ki **cookie hai ya nahi** — value nahi chahiye. `.has("name")` — `true`/`false`:

```ts
export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has("session")

  if (!hasSession) {
    console.log("Session nahi hai — login pe bhejo")
  } else {
    console.log("Session hai — aage jaane do")
  }

  return NextResponse.next()
}
```

```
Bina cookie              → "Session nahi hai — login pe bhejo"
Cookie: session=abc123   → "Session hai — aage jaane do"
```

---

## Step 3 — Login Check Ka Pattern (Log-Only Version)

4.8 mein redirect se jodenge — abhi sirf check ka pattern dekho, jo **har auth-ish proxy** ka skeleton hai:

```ts
export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has("session")

  if (!hasSession) {
    // TODO: redirect karna (4.8)
    console.log("Session nahi hai")
  } else {
    console.log("Session hai")
  }

  return NextResponse.next()
}
```

Do branch — session hai / nahi — aur dono mein kya karna hai woh aage ke notes mein. **Yahi chahiye tha**: proxy mein cookies padhna = login state jaanna = auth-ish decisions ka base.

## What It Is NOT

- **`request.cookies` sirf padhti hai** — set/delete response ke through hota hai (4.10 mein `response.cookies.set()` dekhenge). Proxy ke andar `request.cookies.set()` nahi hota.
- **Cookie ka value verified nahi hota** — `session=abc123` ka matlab sirf "cookie hai" — woh asli session hai ya nahi, verified nahi. Rule yaad rakho: **cookie-presence = "demo check", verified auth = `auth()`/layout** (woh system Batch 5 mein aayega). 4.12 mein isi ka full why-not.
- **`cookies()` (next/headers) alag cheez hai** — Server Component/Route Handler ke andar ka API hai. Proxy mein `request.cookies` milta hai (request object ke saath) — dono alag contexts.

## Common Mistakes

- **`.get()` ka result object hai, string nahi** — `.value` property bhi chahiye. Sirf `sessionCookie` print karoge toh object dikhega.
- **`?.value` bhoolna** — cookie missing pe `.get()` returns null, `.value` pe crash. `sessionCookie?.value`.
- **`.has()` vs `.get() !== undefined`** — dono chalenge, `.has()` readable hai. Rule: sirf existence chahiye → `.has()`, value chahiye → `.get()`.
- **Cookie ko "verified session" samajhna** — demo hai. Verified auth 4.12 ke why-not + Batch 5 ke `auth()` se.

## Nutshell

`request.cookies.get("name")` → `{ name, value }` (missing → null), `request.cookies.has("name")` → true/false. Login-check pattern: `if (!hasSession) { ... } else { ... }`. Cookie-presence = demo check; verified session auth library/layout se.

**In Your Own Words**

1. Cookies header hain toh `request.cookies` API kyun — manual parsing kya hota?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Browser cookie ko `Cookie: session=abc123; theme=dark` jaise ek string header mein bhejta hai. Manual parsing matlab khud `split(";")` aur `split("=")` karke alag cookies nikalna — har proxy mein yeh karna bekar. `request.cookies` khud parse kar ke `{ name, value }` objects aur `.has()`/`.get()` methods deti hai — ready-made, galti-prone parsing se bachat.

</details>

2. `.get("session")` aur `.has("session")` kab kaunsa — ek example situation do?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `.has()` tab jab sirf jaanna hai ki cookie hai ya nahi — jaise login check: "session cookie hai?" — true/false hi kaafi hai. `.get()` tab jab value bhi chahiye — jaise "session cookie ki value kya hai?" — `{ name, value }` object. Rule: existence → has, value → get. (Get bhi null de sakta hai missing pe — `?.value` ya check lagao.)

</details>

3. Proxy mein login-check ka basic pattern kya hai — do branches kya karte hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `const hasSession = request.cookies.has("session")` — phir `if (!hasSession) { // kuch nahi — login pe bhejo } else { // hai — aage jaane do }`. Pehli branch logged-out user handle karti hai (redirect — 4.8 mein), dusri logged-in (next()). Yahi skeleton hai jo 4.12 ke protected routes mein full ho jayega.

</details>

4. "Cookie-presence = demo check" — verified session se kya farak hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Cookie-presence sirf yeh check karta hai ki `session` naam ki cookie **hai** ya nahi — koi bhi browser DevTools mein `session=abc123` bana sakta hai, woh check pass kar jayegi (koi verification nahi). Verified session (`auth()` / Auth.js — aage Batch 5 mein) cookie ki value ko **verify** karta hai — signature/JWT check — ki woh hamari app ne bani thi ya nahi. Isliye production security layout/auth se, proxy cookie-check sirf demo (4.12 mein why-not detail).

</details>

5. `request.cookies` aur `cookies()` from `next/headers` — dono alag kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Context alag hai. `request.cookies` — proxy mein, request object ke andar milta hai (woh request usi ka data hai). `cookies()` from `next/headers` — Server Components/Route Handlers ke andar ka API — wahan request object direct nahi hota, next/headers se access karte ho. Dono "cookies padhne" ke tools hain, par alag-alag context ke liye — proxy mein `request.cookies`, component mein `cookies()`.

</details>
