# `NextResponse` — Next vs Redirect vs Rewrite

## Where We Left Off

Through 4.6 the proxy has been a **reader** of the request — URL (`pathname`, `searchParams`), headers (`user-agent`, IP), and cookies (`has`, `get`). But reading without acting is useless. The real power is the proxy **answering** the request. That happens through `NextResponse` — the class for building the proxy's decision. There are three core tools: `next()`, `redirect()`, and `rewrite()`. The difference between them is the difference between what the proxy can do.

## `NextResponse` — The Response Builder

`NextResponse` is the class for constructing what the proxy sends back. Every proxy function must return a response, and that response is built with `NextResponse`. It comes from `next/server`:

```ts
import { NextResponse } from "next/server"
```

Three core methods, three different decisions:

| Method | Meaning | What the browser sees |
|---|---|---|
| `NextResponse.next()` | "Check complete — forward to destination" | The same URL, the same page |
| `NextResponse.redirect(url)` | "Go to this URL instead" | **The URL changes** — browser loads the new URL |
| `NextResponse.rewrite(url)` | "Serve content from this URL, keep the URL" | The **same URL** — content swapped silently |

## The Shopping-Mall Security Analogy

A mall guard can give three kinds of instructions:

**`next()` — "Looks good, proceed."**
The visitor enters normally — nothing changes. This is the proxy's default, "pass-through" answer.

**`redirect()` — "Go to this entrance instead."**
The guard sends the visitor to a different entrance. The visitor **sees the new entrance** — the address changed — and walks that way. If a user opens `/dashboard` without being logged in, the guard sends them to `/login`; the browser's URL becomes `/login`, and `/dashboard` is left behind.

**`rewrite()` — "Step aside, I'll get your item."**
The guard stops the visitor at the same entrance but fetches the item from a different location. The visitor **never sees the switch** — they stay at the original entrance, but receive different content. If you open `/home` and the guard swaps in the `/home-v2` layout, the URL bar stays `/home` while the page content is actually from `home-v2`.

**One-line distinction:** redirect = change the URL; rewrite = change the content, keep the URL.

## Side by Side in Code

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname

  // 1. forward — normal flow, no change
  if (pathname === "/about") {
    return NextResponse.next()
  }

  // 2. redirect — browser navigates to a new URL
  if (pathname === "/dashboard") {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  // 3. rewrite — same URL, different content
  if (pathname === "/home") {
    return NextResponse.rewrite(new URL("/home-v2", request.url))
  }

  return NextResponse.next()
}
```

(The `new URL(path, base)` syntax in 4.8 — for now, just note the shape: pass a URL object.)

## `NextResponse` Also Carries Headers and Cookies

Beyond the three factories, `NextResponse` lets you attach data to the outgoing response:

```ts
const response = NextResponse.next()        // build the response first
response.headers.set("x-hello", "world")    // attach a custom header (4.10)
response.cookies.set("theme", "dark")       // attach a cookie
return response
```

**Notice the pattern:** build the response into a variable first, then attach things, then return. You can't chain `.headers.set()` straight onto `return NextResponse.next()` — you need the variable in between.

## What It Is NOT

- **`NextResponse` is not proxy-only.** Route Handlers use the same class to build API responses (`NextResponse.json()`). Same tool, different context.
- **Redirect and rewrite are not "both change something visible" to the user.** The differentiator is the URL: redirect makes the URL change; rewrite keeps it the same and silently swaps content.
- **`next()` does not mean "render the page."** It means "continue to whatever the destination was" — whether that is a page, an API route, or nothing. It is "no decision," not "make a page."

## Common Mistakes

- **Using `rewrite` where the URL should change.** Login flows must redirect so the browser shows `/login` — rewriting there hides the navigation and confuses the user.
- **Returning without a response.** Every code path must return `next`, `redirect`, or `rewrite`. Falling off the end returns `undefined`, and the request hangs.
- **Trying to chain on `NextResponse.next()` directly.** `return NextResponse.next().headers.set(...)` does not work — assign to a variable first.
- **Confusing these with each other at a glance.** Keep the shopping-mall analogy: redirect = send to another door; rewrite = swap the contents behind the same door.

## Nutshell

`NextResponse` builds the proxy's answer. `next()` forwards unchanged; `redirect()` makes the browser go to a new URL; `rewrite()` keeps the URL but swaps the content. Headers and cookies can be attached by building the response into a variable first. Every path returns one of these.

## Where We Left Off

In 4.7 we learned the three response tools: `next()` (forward), `redirect()` (browser navigates), and `rewrite()` (silent content swap). We also saw `new URL(path, request.url)` used in the redirect example but didve into it. Now we implement **redirect for real** with a working protected-route example. We cover three things: the `new URL(path, base)` syntax, the infinite-loop problem (and how to avoid it), and the `protectedRoutes` array with `.some()` + `startsWith`.

## Step 1 — The Redirect Syntax

4.6 logged the no-session case; now we redirect:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has("session")

  if (!hasSession) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|login).*)"],
}
```

Two new pieces compared to 4.7:

- `return NextResponse.redirect(...)` replaces the `console.log`. The `return` ends the function — the redirect response is sent immediately.
- `login` is added to the matcher's exclusion list.

## `new URL(path, base)` — Building the Target URL

```ts
new URL("/login", request.url)
```

The built-in `URL` constructor takes two arguments:

1. `path` — where to redirect: `"/login"`
2. `base` — the base URL to resolve against: `request.url` (the full incoming URL)

**Why the base?** `NextResponse.redirect` needs an absolute URL (with origin). Passing only `"/login"` leaves the origin ambiguous. By giving `request.url` as the base — `http://localhost:3000/dashboard` in dev — the URL constructor resolves `/login` against it, producing `http://localhost:3000/login`. Same code in production resolves against `https://myapp.com`, so the redirect is always correct for whatever environment it runs in.

The `new` keyword is because `URL` is a class — you are constructing an instance, not calling a plain function.

## The Infinite-Loop Problem

The matcher excludes `login`. Here is why that matters. Suppose it did not:

```
browser → /login
   ↓ (no exclusion)
proxy runs, sees no session
   ↓
redirects back to /login
   ↓
proxy runs again, sees no session
   ↓
redirects back to /login
   ↓
...forever (or until the browser gives up)
```

The guard analogy: the guard at the building entrance sends you to reception, but the guard **at reception** also sends you to reception — you never reach it.

**The fix** is the rule from 4.1's analogy made concrete: **exclude the redirect target from the matcher.** The `|login` entry means `/login` never enters the proxy at all, so no redirect fires there, and the user lands on the login page safely:

```ts
matcher: ["/((?!_next/static|_next/image|favicon.ico|login).*)"]
```

## Step 2 — Redirecting Only Protected Routes

The example above redirects on **any** missing session — including `/about`, which is public. Better: redirect only when the route is protected. Define a list and check it:

```ts
const protectedRoutes = ["/dashboard", "/profile", "/settings"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const hasSession = request.cookies.has("session")
  const isProtected = protectedRoutes.some((route) =>
    pathname.startsWith(route)
  )

  if (isProtected && !hasSession) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}
```

Reading the new pieces:

- `protectedRoutes.some((route) => ...)` — `.some()` is an array method: it returns `true` if **any** element satisfies the predicate. Here the predicate is `pathname.startsWith(route)`.
- `.startsWith(route)` does prefix matching, so `/dashboard/settings` matches the `/dashboard` entry — children are covered by one array slot.
- `isProtected && !hasSession` — redirect only when **both** are true: the route requires auth **and** the user lacks a session. Public routes like `/about` have `isProtected` false, so they pass through untouched.

## Step 3 — Sending Them Back Where They Came From

A better UX: when redirecting to `/login`, tell the login page where the user was trying to go, so after signing in they return there:

```ts
if (isProtected && !hasSession) {
  const loginUrl = new URL("/login", request.url)
  loginUrl.searchParams.set("callbackUrl", pathname)
  return NextResponse.redirect(loginUrl)
}
```

- `loginUrl` is a `URL` object (so we can mutate its query string).
- `searchParams.set("callbackUrl", pathname)` adds a `?callbackUrl=/dashboard` query — `searchParams.set` handles URL-encoding automatically.
- The browser lands on `/login?callbackUrl=/dashboard`, and the login page can read `callbackUrl` to send the user back to `/dashboard` after success.

## What It Is NOT

- **A redirect is the final auth decision.** This example only checks cookie presence — a spoofable demo (4.12 explains why verified auth lives elsewhere). The redirect itself is correct; the check behind it is not production-grade.
- **`startsWith` is not strict.** `"/dashboard"` also matches `/dashboardevil`. For learning that's fine; production wants boundary checks or exact-prefix-with-separator logic.
- **The `callbackUrl` itself is secure.** It's just a UX hint — the server still validates the destination before honoring it.

## Common Mistakes

- **Forgetting to exclude redirect targets in the matcher.** `/login` included in the matcher while redirecting to `/login` creates an infinite loop.
- **Using `includes` instead of `.some()` + `startsWith`.** `protectedRoutes.includes(pathname)` is exact-match — `/dashboard/settings` fails. `.some()` with `startsWith` covers prefixes and children.
- **Redirecting on every missing session.** Public routes must pass through. Only redirect when the route is protected.
- **Redirecting on every missing session (again, differently).** The `&&` order matters: `isProtected && !hasSession` short-circuits so public routes never reach the redirect branch.

## Nutshell

`NextResponse.redirect(new URL("/login", request.url))` sends the browser to a new URL. Exclude the redirect target from the matcher to prevent infinite loops. Protect a group with `protectedRoutes.some((route) => pathname.startsWith(route))` — prefix matching covers children. Redirect only when `isProtected && !hasSession`. Send the original path as `callbackUrl` so login can return the user.

## Where We Left Off

In 4.8 we built redirects with `new URL(path, request.url)`, learned the infinite-loop rule (exclude the redirect target in the matcher), and made prefix-based protection work with `protectedRoutes.some()` + `startsWith`. Now the third response tool: **`rewrite()`** — "keep the URL, swap the content." We put `NextResponse.rewrite()` to work on two canonical real-world uses: A/B testing and maintenance pages.

## Rewrite — 30-Second Recap

```ts
NextResponse.rewrite(new URL("/home-v2", request.url))
```

The browser requests `/home` → the proxy serves the `/home-v2` content → the browser's address bar still says `/home`. The visitor never sees the switch. Rewrite is server-side content swap; the URL is untouched.

**Redirect vs. rewrite, one sentence:** redirect = the browser goes to a new address (URL changes); rewrite = the browser stays put but receives different content (URL stays).

## Step 1 — A/B Testing (Real Use Case)

**Scenario:** Two versions of the home page exist — `/home` (old design) and `/home-v2` (new design). Send 50% of visitors to v2 to measure results.

Create both pages:

```tsx
// app/home/page.tsx
export default function Home() {
  return <h1>Home (V1 — old design)</h1>
}

// app/home-v2/page.tsx
export default function HomeV2() {
  return <h1>Home V2 (new design)</h1>
}
```

Then split traffic in the proxy:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname

  if (pathname === "/home") {
    const showV2 = Math.random() < 0.5
    if (showV2) {
      return NextResponse.rewrite(new URL("/home-v2", request.url))
    }
  }

  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
}
```

Reading the logic:

- `Math.random()` returns a number in `[0, 1)`. `Math.random() < 0.5` is `true` roughly half the time — the 50/50 split.
- `showV2` true → rewrite to `/home-v2`: same URL `/home`, new content.
- `showV2` false → `next()`: the original `/home` renders.

**Test:** refresh `/home` repeatedly — sometimes "Home (V1)", sometimes "Home V2". The URL bar stays `/home` the entire time.

**Why rewrite and not redirect here:** if it redirected, the browser would show `/home-v2` — visitors would notice the variant they got, biasing behavior and analytics. Rewrite keeps the URL consistent so the test stays clean.

## Step 2 — Maintenance Page (Second Use Case)

**Scenario:** The site is temporarily down for maintenance. Every request should show a maintenance page, but the original URL should stay in the address bar so users and analytics know where they were headed.

Create the maintenance page:

```tsx
// app/maintenance/page.tsx
export default function Maintenance() {
  return (
    <main>
      <h1>Site Under Maintenance</h1>
      <p>We are working on it — please check back soon.</p>
    </main>
  )
}
```

Then route everything to it with a rewrite (temporary proxy):

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  return NextResponse.rewrite(new URL("/maintenance", request.url))
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|maintenance).*)"],
}
```

- `rewrite(new URL("/maintenance", ...))` serves the maintenance page for **every** matched request.
- `maintenance` is excluded in the matcher — applying the same loop rule as 4.8: the rewrite target must not itself be rewritten, or it loops forever.

**Test:** visit `/`, `/about`, `/dashboard` — all show the maintenance page. The URL bar keeps showing the original path.

When maintenance is over, remove or comment out the single `rewrite` line — the site is live again from one edit.

## Rewrite vs Redirect — Final Table

| | Redirect | Rewrite |
|---|---|---|
| URL | **Changes** | Stays the same |
| Browser knows? | Yes — the URL updates | No — silent swap |
| Status code | 307 (or 302) | 200 (normal) |
| When to use | Navigation must be visible (login flow, moved pages) | Content should swap silently (A/B test, maintenance) |
| Loop risk | If the target is also redirected | If the target is also rewritten |
| Exclude target from matcher? | Yes | Yes |

## What It Is NOT

- **Rewrite is not permanent routing.** For a permanent URL move you want redirect (and SEO value flows to the new URL). Rewrite is for temporary, silent swaps.
- **Rewrite is not only for pages.** It works on any route — 4.14 uses it to serve a geo-block page while keeping the blocked URL visible.
- **`Math.random()` is not production A/B logic.** It is only a demo. Real A/B tests assign variants deterministically (by user ID or cookie) so a user sees the same variant across sessions — otherwise the experiment is meaningless.
- **Excluding the target is optional.** It is mandatory. `/maintenance` rewritten to `/maintenance` is an infinite loop, exactly like the redirect loop in 4.8.

## Common Mistakes

- **Using rewrite where the URL change matters.** Login flows must redirect so the address bar shows `/login`; rewriting there hides navigation.
- **Forgetting to exclude the rewrite target.** `/maintenance` in the matcher while rewriting to `/maintenance` causes a loop — same rule as redirect.
- **Letting one branch fall through with no return.** If `showV2` is false and nothing returns, the function returns `undefined` — the request hangs. Every branch returns.
- **Random without a real assignment strategy.** `Math.random()` every request means a user sees different variants on each refresh — useless for a real test.

## Nutshell

`NextResponse.rewrite(new URL("/target", request.url))` keeps the original URL but serves content from `/target`. A/B testing (50/50 split, URL stays clean) and maintenance pages (every URL shows maintenance, original URL stays) are two canonical uses. The redirect loop rule applies in reverse: exclude the rewrite target from the matcher, or it loops.

## Where We Left Off

Through 4.9 the proxy could **read** the request — URL, headers, cookies — and **decide** what to do: `next()`, `redirect()`, or `rewrite()`. Now the last power: the proxy can also **modify the response** — attaching its own headers and cookies. We cover attaching a custom header in the proxy and reading it back inside a layout using the `headers()` API — a pattern that solves a long-standing friction: letting Server Components learn the current route.

## Response Headers vs Request Headers

Request headers travel browser → server (User-Agent, Cookie — covered in 4.5 and 4.6). **Response headers** travel server → browser — things like status, content-type, cache-control. You can also add your own. The convention for custom headers is the `x-` prefix (`x-hello`, `x-pathname`) — a signal that "this is not a standard HTTP header, it is app-specific."

## Step 1 — Adding a Custom Header from the Proxy

Build the response into a variable, then attach the header, then return — the "build, decorate, return" pattern:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const response = NextResponse.next()
  response.headers.set("x-hello", "world")
  response.headers.set("x-pathname", request.nextUrl.pathname)
  return response
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
}
```

- `const response = NextResponse.next()` — create the response object so it can be mutated.
- `response.headers.set("x-hello", "world")` — a static value.
- `response.headers.set("x-pathname", request.nextUrl.pathname)` — a dynamic value: each request carries its own path.

Verify with curl (which dumps headers):

```bash
curl -D - http://localhost:3000/about | grep "x-"
```

```
x-hello: world
x-pathname: /about
```

Both headers appear on the response. The client can read them too — custom headers are visible in DevTools.

## Step 2 — Reading the Header in a Layout: `headers()`

Now the layout learns the current path without each page passing it down:

```tsx
// app/layout.tsx
import { headers } from "next/headers"

export default async function RootLayout({
  children,
}: Readonly<{ children: React.ReactNode }>) {
  const headersList = await headers()
  const pathname = headersList.get("x-pathname")

  return (
    <html lang="en">
      <body>
        <div>Current pathname: {pathname ?? "unknown"}</div>
        {children}
      </body>
    </html>
  )
}
```

New pieces:

- `import { headers } from "next/headers"` — the API for reading request data (and proxy-attached headers) inside Server Components and Route Handlers. Same family as the `cookies()` API from Batch 3.
- `await headers()` — in Next 15+, `headers()` is async; it returns a promise. The `await` is required.
- `headersList.get("x-pathname")` — the same `.get()` pattern from 4.5. The proxy attached the value; here we read it.

**Test:** visiting `/about` shows "Current pathname: /about" in the layout; `/dashboard` shows `/dashboard`.

## Why This Is a Power Move — Layouts Learning the Route

A Server Component (like a layout) does not have `window.location`, and `usePathname()` is a client hook — so historically a layout had no way to know the current route. The old workarounds were painful: every page threaded `pathname` through as a prop, or a client component was used just to read the URL.

The proxy already knows the path (from `request.nextUrl.pathname`). Instead of making every page declare it, the proxy drops it as a response header and the layout reads it once. One place defines it; every component sees it.

## Setting Cookies on the Response (Bonus)

The same build-decorate pattern works for cookies:

```ts
const response = NextResponse.next()
response.cookies.set("theme", "dark", {
  httpOnly: true,
  maxAge: 60 * 60 * 24 * 30,   // 30 days in seconds
  sameSite: "lax",
})
return response
```

`cookies.set` writes a `Set-Cookie` header on the response. Options like `httpOnly`, `maxAge`, and `sameSite` control how the cookie behaves in the browser. This is the write side of what 4.6 read — the full cycle.

## What It Is NOT

- **Not every header is readable.** Headers the framework or a CDN sets at the edge may be filtered before they reach the component; custom `x-` headers are the safe bet for proxy ↔ component communication.
- **`headers()` is server-only.** It does not run in Client Components. If a client needs the value, pass it down as a prop from a server component.
- **Custom headers are not secret.** They are visible in the browser — never put API keys, tokens, or internal data in an `x-` header.
- **Reading proxy headers makes the page dynamic.** Any `await headers()` call opts the component out of static caching — it renders per request. That is the trade-off for reading live values.

## Common Mistakes

- **Forgetting `await` on `headers()`.** In Next 15+ it returns a promise; without `await` you get a promise object, not the data.
- **Making the layout non-async by mistake.** If you `await` inside the layout, the layout must be declared `async`.
- **`return NextResponse.next().headers.set(...)` in one line.** That tries to set a header on a value you returned immediately — `headers.set` returns `void`, and the original `NextResponse` is returned before mutation. Build, decorate, return.
- **Putting secrets in custom headers.** Headers travel to the browser; keep secrets server-side or in `httpOnly` cookies.

## Nutshell

The proxy can decorate its response: build a `NextResponse`, call `response.headers.set("x-name", value)` and `response.cookies.set(...)`, then return. Server Components read it back with `await headers()` then `.get("x-name")`. This closes the gap of layouts needing route awareness — the proxy already has the path, so it shares it via a header. Keep custom headers public (never secrets) and accept that reading them disables static caching.

## In Your Own Words

<details>
<summary>1. What is the "build, decorate, return" pattern, and why can't you chain it?</summary>

**Sample Answer:** `const response = NextResponse.next()` creates a mutable object. Then `response.headers.set(...)` and `response.cookies.set(...)` modify it. Finally `return response` sends it. You can't chain because `return NextResponse.next()` resolves the return immediately; the object is gone before `.set()` runs.

<details>
<summary>2. How does `headers()` let a layout know the current path?</summary>

</details>

<details>

<details>

## Why Log — The Production Story

A user reports: "Yesterday evening the dashboard showed wrong data." You look at your code, nothing is wrong. You ask when — they say around 8 PM.

## What It Is NOT

- **Logs do not need to be sensitive.** Never log passwords, session tokens, request bodies, or `authorization` headers. Metadata (method, path, IP, timestamp) is fair game.

## Common Mistakes

- **Forgetting the timestamp.** A log line without a time is almost useless when debugging.
- **Not falling back on the IP.** Without `?? "unknown"`, a missing header logs `IP: null`, which is less clear than a deliberate default.
- **Logging every request without excluding assets.** The negative matcher (4.3) keeps static files out — otherwise the log fills with `_next/static` noise.
- **Logging secrets by over-including.** Printing `request.headers` raw dumps cookies and auth headers into the log file.

## Nutshell

## Demo Goal

Build the full flow:

1. An unauthenticated user visiting `/dashboard` is sent to `/login`, with a `callbackUrl` so they return afterward.
2. A logged-in user visiting `/login` is sent back to `/dashboard`.

## Step 1 — Cookie Check + Redirect

Combine 4.6's presence check with 4.8's redirect:

```ts
import { NextRequest, NextResponse } from "next/server"

const protectedRoutes = ["/dashboard", "/profile"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const hasSession = request.cookies.has("session")
  const isProtected = protectedRoutes.some((route) =>
    pathname.startsWith(route)
  )

  if (isProtected && !hasSession) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}
```

Familiar: `.some()` + `startsWith` for prefix matching (4.8), `request.cookies.has("session")` for the presence check (4.6).

## Step 2 — Sending Them Back: `callbackUrl`

After login the user should land back where they started, not on a hardcoded homepage. Encode the original path into the redirect target:

```ts
if (isProtected && !hasSession) {
  const loginUrl = new URL("/login", request.url)
  loginUrl.searchParams.set("callbackUrl", pathname)
  return NextResponse.redirect(loginUrl)
}
```

- `new URL("/login", request.url)` — build a mutable URL (4.8).
- `searchParams.set("callbackUrl", pathname)` — append `?callbackUrl=/dashboard`. `set` handles encoding automatically.
- The browser lands on `/login?callbackUrl=/dashboard`.

> **What happens next** is the login form itself: when it succeeds, it reads `callbackUrl` from the query and sends the user there. Auth.js (Batch 5) handles `callbackUrl` automatically; a hand-rolled login form reads it with `useSearchParams`.

## Step 3 — Public-Only Routes: Don't Show Login to Logged-In Users

`/login` should be invisible to logged-in users — send them to `/dashboard`:

```ts
const protectedRoutes = ["/dashboard", "/profile"]
const publicOnlyRoutes = ["/login"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const hasSession = request.cookies.has("session")

  const isProtected = protectedRoutes.some((route) =>
    pathname.startsWith(route)
  )
  const isPublicOnly = publicOnlyRoutes.some((route) =>
    pathname.startsWith(route)
  )

  if (isProtected && !hasSession) {
    const loginUrl = new URL("/login", request.url)
    loginUrl.searchParams.set("callbackUrl", pathname)
    return NextResponse.redirect(loginUrl)
  }

  if (isPublicOnly && hasSession) {
    return NextResponse.redirect(new URL("/dashboard", request.url))
  }

  return NextResponse.next()
}
```

**New:** `isPublicOnly && hasSession` — a logged-in user hitting `/login` is redirected to `/dashboard`. Same `.some()` + `startsWith` shape, different list.

## Matcher Analysis — Why `login` No Longer Needs Excluding

4.8's loop rule said: exclude the redirect target. But here `/login` is no longer a blind redirect — it has a **defined** behavior:

- Logged-in user hits `/login` → redirected to `/dashboard`.
- Logged-out user hits `/login` → no condition matches → `next()` → login page renders.

Neither case loops. So, unlike the 4.8 demo, the matcher can omit the `login` exclusion:

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"],
}
```

**Key insight:** the loop rule protects against **unconditional** redirects. When every branch has a defined outcome, the proxy terminates naturally — no exclusion needed.

## Why This Is a Demo — Not Production Security

This is where the series gets honest. The mechanics are correct, but the **trust model** is not. Three reasons:

### 1. Cookie presence is spoofable

`request.cookies.has("session")` only checks that a cookie named `session` exists — it does not verify the value. Open DevTools:

```
Application → Cookies → localhost → New: session = anything
```

Now `hasSession` is `true`. No login, no verification — the proxy treats a self-planted cookie as a session. Real auth verifies the cookie's value against the session store (Batch 5: `auth()`).

### 2. CVE-2025-29927 — proxy bypass via header

Next.js middleware historically had a bypass: an attacker could send a special header that made the framework treat the proxy as already invoked, skipping it entirely. The result: proxy-side auth checks were skipped.

Next.js patched it, but the lesson is structural:

> The proxy is an optimization and routing layer. It can be bypassed. It must not be the **only** security check.

### 3. The fix: security lives in components, not the proxy

Production pattern (Batch 5):

```
Proxy (routing / UX)        — nice-to-have, bypassable
  ↓
Layout / Server Component    — `auth()` + `redirect()` — verified, bypass-proof
```

The proxy can still route (`/login` with session → `/dashboard`) and improve UX (callbackUrl). But **verified** auth — checking that the session value is genuinely valid and issued by your app — must run in layout/Server Components, where requests cannot be skipped.

## What It Is NOT

- **The proxy is not the auth layer.** It is a routing/UX layer that can be bypassed.
- **`callbackUrl` is not secure by itself.** It is a UX pointer — the destination must still be validated before redirecting (to prevent open-redirects).
- **A public-only redirect is not a logout.** Sending `/login` users to `/dashboard` does not clear the session cookie.
- **`protectedRoutes` as a JS array is not Route Groups.** This is runtime checking; `(protected)` folders (Batch 5) are filesystem-level.

## Common Mistakes

- **Trusting cookie presence as authentication.** The demo does it on purpose to teach mechanics; never ship it.
- **Not excluding redirect targets in matchers — for loops.** This demo avoids the loop via defined behavior. A blind unconditional redirect still loops.
- **Over-redirecting.** Forgetting `isProtected` and redirecting on any missing session blocks public pages.
- **Not URL-encoding `callbackUrl`.** `searchParams.set` handles encoding; manually building `?callbackUrl=` + raw path risks malformed redirects.

We build a fixed-window limiter from scratch.<tool_call>write<arg_key>content</arg_key><arg_value># Rate Limiting — Per-IP Limits with a 429 Response

## Where We Left Off

In 4.12 we built full protected-route flows and were honest about their limits: the proxy is a routing/UX layer, and cookie presence is not authentication. Now a case where the proxy **is** the right place: **rate limiting** — capping how many requests a single IP can make in a time window. This is real infrastructure work (brute-force protection, API abuse, scraping), and the proxy is exactly where it belongs because it sees every request before it lands.

## The Problem — Too Many Requests

Imagine a script firing 500 requests per second at your API. Or a brute-force attack trying thousands of passwords. Each request costs something — a database hit, computation, auth. Too many and the server collapses, or a vulnerable endpoint is abused.

**Solution:** give each IP a quota within a time window. Exceed it → respond with **429 Too Many Requests** and stop the request before it reaches the page.

## Step 0 — Storage Must Survive Across Requests

Counts cannot live inside the `proxy()` function body — that function is recreated fresh on every request, so a `let count = 0` inside it resets to zero every call. The counter would always be 1.

Instead, declare the store **at module level** — outside the function, so it is created once when the module loads and shared across all requests:

```ts
const requestCounts = {}

export function proxy(request: NextRequest) {
  // read and update requestCounts — same object on every call
}
```

**Module lifetime:** the object lives as long as the server process runs. Restart wipes it — fine for dev and learning; production uses a shared store (see the honest limitation at the end).

## Step 1 — Typing the Store: `Record<K, V>`

Each entry holds a count and the timestamp at which the window resets:

```ts
const requestCounts: Record<string, { count: number; resetTime: number }> = {}
```

**`Record<K, V>`** is a TypeScript utility type — "an object whose keys are of type K and whose values are of type V." Here: string keys (IP addresses) mapped to objects `{ count: number; reset: number }`:

```ts
// Example contents:
{
  "49.36.10.5":  { count: 7, resetTime: 1720000000000 },
  "8.8.8.8":     { count: 2, resetTime: 1720000001000 },
}
```

`resetTime` is a timestamp in milliseconds. `Date.now()` returns the current time in milliseconds since the epoch — the unit to use. A window is "now + duration":

```ts
Date.now()                    // → 1720000000000 (ms)
resetTime: Date.now() + WINDOW_MS
```

## Step 2 — Increment Logic

```ts
import { NextRequest, NextResponse } from "next/server"

const RATE_LIMIT = 10            // max requests per window
const WINDOW_MS = 60 * 1000      // 1 minute, in milliseconds

const requestCounts: Record<string, { count: number; resetTime: number }> = {}

export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  const now = Date.now()

  if (!requestCounts[ip]) {
    requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }
  } else {
    requestCounts[ip].count++
  }

  console.log(`IP: ${ip} — Count: ${requestCounts[ip].count}`)
  return NextResponse.next()
}
```

- `RATE_LIMIT` and `WINDOW_MS` as named constants make the policy easy to read and change.
- `!requestCounts[ip]` detects a first request from this IP — create an entry with count `1`.
- Otherwise, increment.

## Step 3 — Window Expiry — Resetting the Count

Without expiry, the count climbs forever. The fix: when `now` has passed `resetTime`, the window is over — start fresh:

```ts
if (!requestCounts[ip] || now > requestCounts[ip].resetTime) {
  requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }  // fresh window
} else {
  requestCounts[ip].count++                                    // count up
}
```

The `||` (OR) gives two fresh-start triggers: the IP has never been seen (`!requestCounts[ip]`), or the old window has expired (`now > resetTime`).

Visualizing against a clock:

| Scenario | `now` vs `resetTime` | Result |
|---|---|---|
| Window active | `now < resetTime` | increment |
| Window expired | `now > resetTime` | fresh — count 1 |
| New IP | no entry | fresh — count 1 |

## Step 4 — Enforcing the Limit: 429

Now block requests past the limit:

```ts
const RATE_LIMIT = 10

export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  const now = Date.now()

  if (!requestCounts[ip] || now > requestCounts[ip].resetTime) {
    requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }
  } else {
    requestCounts[ip].count++
  }

  if (requestCounts[ip].count > RATE_LIMIT) {
    return new NextResponse("Too Many Requests", { status: 429 })
  }

  return NextResponse.next()
}
```

- `count > RATE_LIMIT` — the 11th request exceeds the limit of 10.
- `new NextResponse("Too Many Requests", { status: 429 })` — the `NextResponse` constructor builds a response with a body and a status. (The `.next()` / `.redirect()` / `.rewrite()` methods are convenient factories; here we need a custom status, so we use the constructor directly.)
- **429 = "Too Many Requests"** — the HTTP status code specifically for rate limiting, so clients can distinguish "blocked for speed" from "forbidden" (403) or "server error" (500).

Verification:

```
10 requests → 200 ×10
11th request → 429
12th+ → 429 (until the window resets)
Different IP → 200 (per-IP counting; other users are unaffected)
```

## Honest Limitation — In-Memory, Single Instance

This implementation is correct for a single dev server. In production there is one fatal gap: `requestCounts` lives in **this machine's** memory. Production apps scale across many instances — each instance has its own `requestCounts`:

```
User makes 8 requests → Instance A (count 8)
                         Instance B (count 8, separate memory)
Total: 16 requests with no 429 — the limit was multiplied by the instance count.
```

The effective limit becomes `RATE_LIMIT × number of instances`. To fix it, the counter must live in a **shared store** — Redis being the standard choice. The concept (count per IP per window) is identical; only the storage moves externally:

```
Proxy → Redis: INCR ip_key, EXPIRE window — shared across all instances
```

This series does not cover Redis in depth here; the concept stands. In-memory works for learning and dev; shared storage is the production rule.

## What It Is NOT

- **Rate limiting is not authentication.** It caps request volume; it does not verify identity.
- **Per-IP is not per-user.** Behind a shared network (office, NAT), many users share one IP and share a quota. Production sometimes keys on user ID when available.
- **A 429 is a signal, not a punishment.** It tells the client to slow down. APIs usually pair it with a `Retry-After` header so the client knows when to try again.
- **The in-memory store is not durable.** Restart clears it; that's acceptable for dev, not for production.

## Common Mistakes

- **Placing the counter inside the function body** — it resets every request. Module level is mandatory.
- **Omitting the window-expiry check** — `count` only ever grows after the first window, and the IP is permanently blocked.
- **Returning `200` instead of `429`** on the limit — the client has no signal that it was throttled.
- **Logging every request including static assets** — the matcher already excluded assets (4.3); the rate counter should be in the same scope or it counts CSS files against the user.
- **Trusting `x-forwarded-for` blindly in production** — it is client-spoofable (4.5). Trusted proxies must overwrite it.

## Nutshell

Rate limit in the proxy: module-level `requestCounts` (must survive across requests), keyed by IP (`x-forwarded-for ?? "unknown"`), value `{ count, resetTime }`. Fresh window when the entry is absent or `now > resetTime`. Block with `new NextResponse("...", { status: 429 })`. In-memory works for dev; production needs Redis (shared across instances).

## In Your Own Words

<details>
<summary>1. Why must `requestCounts` be declared at module level, not inside `proxy()`?</summary>

**Sample Answer:** The `proxy()` function is re-invoked fresh on every request. A `let count = 0` inside it resets to 0 each time — the increment never accumulates. A module-level variable is created once when the module loads and is the same object every request references, so counts accumulate correctly across requests.

</details>

<details>
<summary>2. What is `Record<string, { count: number; resetTime: number }>` describing?</summary>

**Sample Answer:** A TypeScript object type — keys are strings (IP addresses), values are objects with two numbers: `count` (requests so far) and `resetTime` (when the window expires, as a millisecond timestamp). `Record<K, V>` is the utility type for "object with K keys and V values."

</details>

<details>
<summary>3. What triggers a fresh counting window?</summary>

**Sample Answer:** Two cases, combined with `||`: the IP has no entry yet (`!requestCounts[ip]`), or the current time has passed the stored `resetTime` (`now > requestCounts[ip].resetTime`). Either case resets `count` to 1 and sets a new `resetTime`.

</details>

<details>

**Sample Answer:** `NextResponse.next()` forwards to the destination with a 200. The constructor builds a custom response — here a 429 status with a text body. The proxy answers the request directly, the page never renders, and the client receives the "slow down" signal.

</details>

<details>
<summary>5. Why is the in-memory store production-unsafe, and what replaces it?</summary>

**Sample Answer:** Each server instance has its own memory — a count split across instances means the true total is under-enforced (effective limit = `RATE_LIMIT × instances`). ## Where We Left Off

In 4.13 we built a real rate limiter in the proxy — per-IP quotas, a 429 response, and an honest note about shared storage in production. Now another request-level concern where the proxy is the right place: **geo blocking** — allowing a service only in certain countries. ## The Problem — Geographic Restrictions

Some services are licensed or available only in certain countries (gaming, streaming, finance, compliance). A visitor from Russia should see a notice, not the product. The proxy is the right place because it sees every request and can answer "where is this from?" before any page renders.

## Step 1 — Reading the Country Header

4.13 read the client IP from `x-forwarded-for`. Country is one step further: from IP to country. The naive approach — maintaining a geolocation database — is heavy setup. Vercel offers a shortcut: when deployed on Vercel, every request arrives with an automatic header:

```
x-vercel-ip-country: IN
```

Vercel detects the country from the incoming IP and attaches it. The proxy just reads it:

```ts
const country = request.headers.get("x-vercel-ip-country")
```

The value is an **ISO 3166-1 alpha-2** two-letter code: `IN` (India), `US`, `GB`, `RU`, `DE`...

> **Honest note:** this header does not exist in local development. The proxy will see `null` on `localhost`. The code below falls back to `"IN"` for local dev, and tests simulate the header with curl. Production deployments receive real values.

## Step 2 — Allowlist + Hard 403

An allowlist is safer than a blocklist: new countries are blocked by default until explicitly allowed.

```ts
import { NextRequest, NextResponse } from "next/server"

const ALLOWED_COUNTRIES = ["IN", "US", "GB"]

export function proxy(request: NextRequest) {
  const country = request.headers.get("x-vercel-ip-country") ?? "IN"

  if (!ALLOWED_COUNTRIES.includes(country)) {
    return new NextResponse("This service is not available in your region.", {
      status: 403,
    })
  }

  return NextResponse.next()
}
```

- `ALLOWED_COUNTRIES` — the allowlist. Adding a country is one line.
- `.includes(country)` — array method: "is this exact value in the list?" Exact match: `IN` matches, `RU` does not, and `IND` would not (codes are two letters).
- `!ALLOWED_COUNTRIES.includes(country)` — not in the allowlist → blocked.
- `new NextResponse("...", { status: 403 })` — 4.13's constructor response pattern. `403 Forbidden` tells the client access was denied for identity/geography reasons (as opposed to `404`, which says "this does not exist").

Testing locally (curl sets the header to simulate a country):

```bash
curl -H "X-Vercel-Ip-Country: IN" http://localhost:3000/    # 200 — allowed
curl -H "X-Vercel-Ip-Country: RU" http://localhost:3000/    # 403 — blocked
```

## Step 3 — Friendly Blocked Page (Rewrite Version)

A 403 with plain text is functional but rude. Serve a proper page instead — and keep the URL consistent using `rewrite` (4.9):

```tsx
// app/blocked/page.tsx
export default function Blocked() {
  return (
    <main>
      <h1>Not Available in Your Region</h1>
      <p>This service is not available in your country. Please check back from an allowed region.</p>
    </main>
  )
}
```

```ts
export function proxy(request: NextRequest) {
  const country = request.headers.get("x-vercel-ip-country") ?? "IN"

  if (!ALLOWED_COUNTRIES.includes(country)) {
    return NextResponse.rewrite(new URL("/blocked", request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: [
    "/((?!_next/static|_next/image|favicon.ico|blocked|.*\\.svg).*)",
  ],
}
```

- `rewrite(new URL("/blocked", ...))` serves the blocked page. The visitor's URL stays exactly what they typed — no redirect, no URL change.
- `blocked` is excluded from the matcher — applying the same loop rule as 4.8 and 4.9. If `/blocked` itself entered the proxy, it would be rewritten to `/blocked` again → loop.

Why rewrite over redirect here? A redirect would show `/blocked` in the address bar, inviting the visitor to refresh or navigate and wonder why they're stuck. Rewrite keeps the URL they expected, with a clear message overlaid.

## Why `.includes()` and Not `.startsWith()` Here

Compare to 4.12's protected routes. There, `pathname.startsWith(route)` matched prefixes because `/dashboard` should cover `/dashboard/settings`. Here, country codes are exact two-letter values — `IN`, `US`, `GB`. `IN` is not a prefix of anything meaningful; `RU` should never match `IN`. Use exact matching (`.includes`) where the key is a fixed symbol, prefix matching (`.startsWith`) where the key is a path group.

- **Geo blocking is not authentication.** It is not checking identity; it is checking region. The two layers are independent.

## Where We Left Off

Through 4.14 the proxy has handled four real scenarios: logging, protected routes, rate limiting, and geo blocking. All of that assumed the proxy could use things like `Date.now()`, `URL`, `headers`, `cookies`, and `console.log`. But what environment **is** the proxy running in? That question mattered a lot for old middleware, and changes in Next.js 16. This file answers it: what the Edge Runtime is, how middleware historically related to it, and the **key change in Next.js 16** that moved the proxy to Node.js by default.

## What Is the Edge Runtime?

**Edge = distributed compute nodes around the world.** Your application server might live in one region (say, the US), and users everywhere. A visitor in Mumbai sends a request that crosses to the US server and back — the round trip adds latency. Cloud providers (Vercel, Cloudflare) mitigate this by running lightweight code on nodes near the user.

The **Edge Runtime** is that lightweight JavaScript environment — it runs on those distributed nodes. Its purpose is to handle a request as close to the user as possible: low latency, minimal cold-start. Its cost: it is lightweight, not a full Node.js.

| Feature | Node.js (server) | Edge Runtime |
|---|---|---|
| Location | Single server region | Distributed edge nodes |
| `fs` / `path` / `crypto` (Node built-ins) | ✅ full | ❌ unavailable |
| Database drivers (Prisma, etc.) | ✅ | ❌ unavailable |
| `fetch()` | ✅ | ✅ |
| Web APIs (URL, Headers, etc.) | ✅ | ✅ |
| Latency from a global user | High (round-trip to server) | Low (nearest node) |

The tradeoff is size and speed versus API surface. Edge is designed for fast request-level logic — exactly the kind of thing a proxy does.

## Middleware's Edge Relationship (Next ≤ 15)

Historically, Next.js middleware ran on the Edge. That was deliberate: the proxy's job is to check a request **before** it reaches a page, and doing that check at the nearest edge node minimized latency. So middleware was Edge-only by default, and you had to write Edge-safe code:

- Use `fetch`, not Node's `http`.
- Avoid `fs`, `crypto`, databases.
- Prefer Edge-compatible libraries (`bcryptjs` over `bcrypt`, `jose` over `jsonwebtoken`).

This is why tutorials of that era emphasized "Edge-compatible" packages — it wasn't style, it was a hard constraint.

## Next.js 16 — The Proxy Now Runs on Node.js

This is the correction the series needed to state up front. Starting in Next.js 16, the proxy (renamed from `middleware`) **defaults to the Node.js runtime**, not Edge. From the official changelog:

```
v16.0.0 — Middleware is deprecated and renamed to Proxy.
          Proxy defaults to the Node.js runtime.
```

What that means in practice, verified in Next 16.3:

1. `import { readFileSync } from "fs"` inside the proxy **runs** — it reads a file and logs it. Under Edge, this threw "Module not found: Can't resolve 'fs'".
2. Setting `export const runtime = "edge"` in `proxy.ts` now **throws a build error**:

   ```
   Error: Next.js can't recognize the exported `config` field in route.
   Proxy does not support Edge runtime.
   ```

So the old constraint ("middleware must be Edge-safe") no longer applies by default. The proxy is Node.js unless you explicitly choose otherwise — and even then, the Edge option has been removed from the proxy path.

> The Edge runtime itself still exists as a Next.js feature. It applies to other runtimes (Edge Functions, etc.). What changed is that the proxy is no longer one of them by default.

## What Changes Because of This?

The capabilities table from the last section flips on its head for the proxy:

- `fs`, Node built-ins — now available.
- Database drivers — now available.
- Native `bcrypt` — now available.

But "available" is not "appropriate." The reasons to keep the proxy light — performance (it runs on every request) and responsibility (it is an infra layer) — were never about Edge restrictions. They are about architecture. That is what 4.16 makes precise.

## What It Is NOT

- **The proxy running on Node.js does not mean "do everything in it."** Capability is not an invitation.
- **The Edge runtime is gone.** It still exists; only the proxy's default runtime changed. Edge Functions remain a feature elsewhere.
- **`runtime: "nodejs"` is needed.** No — Node is the default; setting that export is now unrecognized and errors.
- **Everything that worked on Edge now behaves identically.** Edge optimized for cold-start and distributed execution; Node is a different deployment model. Same APIs, different performance characteristics.

## Common Mistakes

- **Copying `export const runtime = "edge"` from old tutorials.** In Next 16 it is a build-time error. Delete it.
- **Assuming "Node runtime = put the database query in the proxy."** The proxy runs per-request; a DB call there affects every request. Data access belongs in Server Components and Actions, not the interception layer.
- **Reading old "Edge-compatible" library guidance as still binding.** For the proxy, it is no longer a constraint. For actual Edge Functions, it is. Know which you are writing.
- **Confusing "runtime" with "environment."** Runtime = where code executes (Node vs Edge). Environment = the deployment topology. Both matter, but they are independent concerns.

## Nutshell

The Edge Runtime is distributed, lightweight compute for low-latency request handling — at the cost of a smaller API surface (no `fs`, databases, or native crypto). Old middleware ran on Edge, so it had to be Edge-safe. **Next.js 16: the proxy defaults to Node.js**, so those restrictions no longer apply — but the architectural reasons to keep the proxy thin (per-request execution, infra-layer role) remain. Setting `runtime: "edge"` now causes a build error and should be removed.

These were hard errors under Edge that now pass under Node 16.

### 1. File System (`fs`)

## Golden Rules — Still Hard Rules

### ❌ Never put heavy work or data access in the proxy

- **Why it runs on every request** — any latency in the proxy multiplies across every route. A 100 ms DB call in the proxy makes every page 100 ms slower.
- **It is the wrong layer** — the proxy is for request-level infra (routing, inspection, forwarding), not for resolving business data. Data access belongs in Server Components and Actions.

This was true under Edge too, but there it was reinforced by a runtime error — a forced constraint. Now it is only by discipline. Discipline matters more, so treat it as non-negotiable.

### ❌ Never put verified auth in the proxy

From 4.12: the proxy is bypassable (CVE-2025-29927) and cookie presence is spoofable. Even with Node, even with `fs` and Prisma available, **verified authentication** must not live in the proxy. Security decisions belong in layout/Server Components, where the request cannot be sidestepped.

- The proxy can **route** (send an unauthenticated user to `/login`).
- The proxy can **flag** (set a header the layout reads).
- The proxy can **never be the sole authority** on whether a request is allowed.

### ❌ Never accumulate unbounded state in memory

4.13's rate limiter used a module-level object — and admitted it does not scale across instances. That weakness is real regardless of runtime: the proxy should not be the source of truth for stateful business data. Shared stores (Redis, the database) handle cross-instance state. Use the proxy for ephemeral, request-scoped computation only.

## Official Stance — Use It Sparingly

The Next.js team's guidance on the proxy (formerly middleware) is explicit and conservative:

> "We recommend users avoid relying on Middleware unless no other options exist. Our goal is to give them APIs with better ergonomics so they can achieve their goals without Middleware."

Translated: the proxy is a **tool of last resort**, not a default. The team would rather you use a dedicated feature than intercept every request in a function.

Why the caution, given how useful the proxy looks in this series?

- **It can be bypassed** (CVE-2025-29927, discussed in 4.12) — a request can arrive without the proxy having run. So it is unsafe to depend on it for guarantees.
- **It runs on every request** — slow logic in the proxy is paid on every page, every API call.
- **It reinvents features** Next.js already provides more directly — redirects, headers, rewrites all have dedicated configuration (`next.config.js`) or Server Component APIs.
- **It is confused easily** — as 4.1 noted, people import Express mental models of "middleware" and misapply them to a framework-level feature.

So: default to the dedicated tool. Reach for the proxy only when the dedicated tool cannot do what you need.

## Decision Table — Pick the Right Tool

| Task | Best tool | Why |
|---|---|---|
| Auth check + redirect for logged-out users | Server Components: `auth()` + `redirect()` | Verified session (Batch 5); the proxy is bypassable and spoofable (4.12) |
| Route redirects (moved pages) | `next.config.js` `redirects()` or `redirect()` in a Server Component | Dedicated, declarative, no proxy runtime cost |
| Setting response headers | `next.config.js` `headers()` or `generateMetadata` | Config-level, predictable, cached |
| **Rate limiting per IP** | Proxy ✅ | Needs every request, before routing — the proxy is the one place |
| **Geo blocking** | Proxy ✅ | Needs every request + country header — the proxy is the one place |
| **Request logging** | Proxy ✅ | One place, every request, before any branch — ideal |
| A/B routing, maintenance pages | Proxy ✅ (`rewrite`) | Request-time decision that must happen before content |
| Verified auth / data protection | Server Components + Actions (`auth()`) | Secure, bypass-proof; proxy cannot be the authority |

The pattern is consistent:

- **If it is a verified decision or business data** → put it where the request cannot skip it: Server Components and Actions.
- **If it is request-level infra** (inspecting, routing, or throttling traffic before content) → the proxy, because it is the one place that sees everything.

"Auth proxy mein" (from the table) is the trap this table warns against — the proxy can look at a cookie, but it cannot **verify** it.

## Best-Practice Checklist (Final)

1. **Keep the proxy thin** — read headers/cookies/URL, apply a condition, redirect/rewrite/next. Nothing heavier.
2. **Tight, explicit matcher** — run only where needed; always exclude static assets, the favicon, and `api` routes unless you intend to intercept them.
3. **Exclude every redirect/rewrite target** from the matcher, or risk the loop (applied to redirect 4.8, rewrite 4.9, geo 4.14).
4. **Verified auth in components, not the proxy** — cookie presence is a hint, not identity.
5. **Shared storage for any state** — in-memory objects do not scale across instances (4.13).
6. **Simulate production headers locally** — `x-vercel-ip-country`, `x-forwarded-for` are not present on `localhost`.
7. **Version-aware** — Next 16 uses `proxy.ts` + `export function proxy`; drop `runtime` exports; they error now.
8. **Secret-free logs and headers** — never log or set auth tokens, sessions, or request bodies.

## In Your Own Words

<details>
<summary>1. Why does Next.js recommend avoiding the proxy unless necessary?</summary>

**Sample Answer:** Because it runs on every request (latency cost), it can be bypassed (security cannot rely on it — CVE-2025-29927), and it often duplicates features Next.js provides more directly (redirects, headers via config). The recommendation is: use the dedicated tool first, the proxy only when that isn't enough.

</details>

<details>
<summary>2. When is the proxy the right tool (and when is it not)?</summary>

**Sample Answer:** Right: request-level infra every request needs — rate limiting, geo blocking, logging, A/B routing. Not: verified decisions and business data — auth, data fetching, redirects that could be `next.config` redirects. Rule of thumb: needs every request + no dedicated API → proxy; otherwise, use the dedicated feature or a Server Component.

</details>

<details>
<summary>3. Why can't the proxy be the auth check, even with `fs`/Prisma now available?</summary>

**Sample Answer:** Even though Node APIs now work in the proxy, the proxy can be bypassed via header tricks (CVE-2025-29927), and a cookie that merely exists is not a cookie that was **issued by your app**. Auth needs identity verification against the session store — in a component where the request cannot be skipped. The proxy can route based on that, but it cannot be the authority.

</details>

<details>
<summary>4. What is the single most important matcher rule, and why?</summary>

**Sample Answer:** Exclude every redirect or rewrite target — the redirect target in 4.8, the rewrite target in 4.9, the blocked page in 4.14. A target that is also matched sends requests back into the proxy, creating an infinite loop (or a 404 in some setups). The matcher must describe where to enter the proxy, not what to do inside it.

</details>

<details>
<summary>5. How does this series bridge to Batch 5's authentication?</summary>

**Sample Answer:** Batch 4 showed the **shape** of an auth flow — cookie presence check, redirect to `/login`, callbackUrl. Batch 5 fills in the **trust**: a real session, `auth()` verifying the value, and a `(protected)` layout where the check runs on a code path the request cannot skip. The proxy keeps the routing job; the component takes the security job.

</details>
