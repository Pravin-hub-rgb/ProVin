## Official Stance — What Next.js Says

Next.js's official documentation (the middleware-to-Edge migration note) states plainly:

> **"We recommend users avoid relying on Middleware unless no other options exist. Our goal is to give them APIs with better ergonomics so they can achieve their goals without Middleware."**

Why this conservative stance? We saw it ourselves in this series:

- **The proxy can be bypassed** (CVE-2025-29927 — see 4.12)
- **It runs on every request** — heavy logic means every page slows down (4.16)
- **It reinvents things** — for redirects and headers, the framework already provides dedicated configs (in the table below) with better ergonomics
- **It causes confusion** — the old Express-middleware mindset applies here, which is exactly why the rename happened (4.1)

In short: **the proxy is not the default choice — it is a last resort, used when no other tool fits.** Think of it like a wrench: you do not reach for a wrench to turn a screw. Each tool has its job.

## Decision Table — Which Job Where?

| Job | Best Location | Why |
|---|---|---|
| **Auth check / redirect (logged-out → login)** | Server Components: `auth()` + `redirect()` (the layout pattern from Batch 5) | Verified session — the proxy is spoofable and bypassable (see 4.12) |
| **Conditional redirects** | Server Components `redirect()` or `next.config` `redirects()` | Dedicated configs exist; no proxy runtime needed |
| **Setting headers** | `next.config` `headers()` or Server Components | Config-level solution; the proxy is unnecessary here |
| **Rate limiting** | Proxy ✅ | A request-level check — the proxy is the right place (4.13) |
| **Geo blocking** | Proxy ✅ | Every request needs a country check — the proxy is the place (4.14) |
| **Logging (request-level)** | Proxy ✅ | Recording every request in one place (4.11) |
| **A/B routing / maintenance page** | Proxy ✅ (via rewrite) | Request-time decisions the proxy handles (4.9) |
| **Verified auth (protecting data)** | Layout / Server Components `auth()` | The security layer does not belong in the proxy (CVE) |

**Read the pattern:** identity-verification and data-protection tasks → **components and actions** (verified, bypass-proof). Infrastructure and request-inspection tasks → **the proxy** (as shown in 4.13/4.14/4.11). Anyone who puts "auth in the proxy" is reading the wrong column — that is exactly the "why not" from 4.12.

---

## Best Practices — Final Checklist

1. **Keep the proxy thin** — read cookies/headers, apply a condition, return a decision. Heavy logic belongs in components/actions (4.16).
2. **Tighten the matcher** — run only on the routes that need it; static assets always excluded (4.3).
3. **Exclude the redirect/rewrite target from the matcher** — prevents infinite loops (4.8/4.9).
4. **Never put verified auth in the proxy** — use the `auth()` + layout pattern (4.12).
5. **Shared store for rate-limit state in production** — Redis, not in-process memory (4.13).
6. **Simulate geo headers locally** — `x-vercel-ip-country` is production-only (4.14).
7. **Never log secrets** — logs are evidence that gets stored (4.11).
8. **Be version-aware** — Next 16 changed the proxy to Node.js by default, and the `runtime` export was removed (4.15/4.16).
