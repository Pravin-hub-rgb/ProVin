# Proxy Kya Hai — Request Lifecycle

## Where We Left Off

In Batches 1–3, we built up the app layer by layer: routing and layouts (Batch 1), data fetching with Server and Client Components (Batch 2), and mutations through both Route Handlers and Server Actions (Batch 3). Every file so far has been at the page level — a request comes in, Next.js matches it to a route, and a component (or API route) renders. Now a new layer enters, one that runs **before** any route is matched: **Proxy** (Next.js's request interception layer). This project begins fresh with the question: what if you need to do something with **every** incoming request, before it ever reaches a page?

## The Problem — Repeated Checks on Every Page

Imagine a 10-page app and you need to run a few common checks on **every** request:

- Is the user logged in?
- Which country is the request coming from?
- How many requests has this IP sent (rate limit)?
- Should this request be logged?

Without a proxy, you end up copy-pasting the same boilerplate into each page:

```tsx
// app/dashboard/page.tsx
export default async function DashboardPage() {
  // check auth
  // check country
  // check rate limit
  // log request
  return <h1>Dashboard</h1>;
}

// app/profile/page.tsx — same 4 checks repeated
```

One page forgets the check? That page is unprotected. And the duplication (echoing Batch 1.5.2's pain) grows. This is the problem the proxy solves — by doing it all in one place, **before** any route runs.

## What Is a Proxy — The Security Guard Analogy

Think of a building with a **security guard** at the entrance. No one gets in without passing through that single checkpoint:

- ID check? (auth)
- Visitor pass? (rate limit)
- Sign the visitor book? (logging)

Inside the building, each room doesn't have its own guard — **one guard, at the door**. That is the proxy: Next.js's single file that runs **before every page renders**. The lifecycle is simple:

```
Request → Proxy → Page
```

The proxy decides what to do:

- **Let it through** ("looks good, proceed")
- **Redirect** ("wrong entrance — go to `/login`")
- **Block** ("slow down — 429 Too Many Requests")

Write the check once, and it covers every route. No other file needs to know about it.

## Naming: `proxy.ts` (Not `middleware.ts`)

In middleware (Next.js ≤ 15), this file was called `middleware.ts`. Starting in Next.js 16, it was renamed — the file is now `proxy.ts` (or `proxy.js`), and the export changed from `export function middleware` to `export function proxy`. Both names point at the same feature; the change is version, not concept.

When upgrading older codebases, Next.js emits a deprecation warning:

```
⚠ The "middleware" file convention is deprecated. Please use "proxy" instead.
```

There is also an official codemod that handles the rename automatically:

```bash
npx @next/codemod@canary middleware-to-proxy .
```

## Why a Proxy — Rejecting the Alternatives

To appreciate the proxy, consider two alternatives that fall short:

**Alternative 1 — Check inside each page (or a root layout).** A route-group layout can hold auth checks, but page-level logic like logging and geo still has to repeat per page — and a missed page is an unprotected page.

**Alternative 2 — A `<ProtectedRoute>` wrapper component.** You wrap every page in it, but that is still manual wiring on every page, and the check only runs at render time — not at the route level.

The proxy sits at **route level**, in **one file**, for **every** request — before any component renders. That is the difference it makes.

> **Note:** Express middleware is a different thing. In Express, it is a function manually chained alongside your routes — it lives inside your route declarations. Next.js's proxy is framework-level: it runs automatically on every incoming request, outside your route code. Same spirit of intercepting requests, different level of control.

## What It Is NOT

- **The proxy is not the main security layer.** That distinction belongs to verified auth (coming in Batch 5). As CVE-2025-29927 shows (4.12), a proxy can be bypassed; real security belongs in layouts and Server Components. The proxy is an infra-level convenience layer.
- **The proxy is not a Route Handler.** A Route Handler (`route.ts`) is an endpoint — the client calls it directly and gets a response. The proxy is the layer **between** the client and the route — it intercepts, decides, and forwards.
- **The proxy doesn't "also" run on the page.** It runs **before** the page renders, once, and its decision precedes rendering. Lifecycle: Request → Proxy → Page.

## Common Mistakes

- **Using old `middleware.ts` syntax in new projects** — Next 16 wants `export function proxy` in `proxy.ts`. Copying old docs blindly yields a file that is never picked up.
- **Running Node-only modules (`fs`, `bcrypt`, Prisma) for years under the old Edge assumption** — 4.15 and 4.16 cover how Next 16 changed this. For now, just remember that the proxy runs somewhere specific, and assumptions about that environment matter.
- **Doing heavy work in the proxy** — it runs on every request. Slow proxy = slow every page. This shows up repeatedly, so treat it as a rule of thumb now.

## Nutshell

A proxy (`proxy.ts`, one file, project root) runs on every request, before any page. It reads the request and decides: let it through (`NextResponse.next()`), redirect the browser, or block the request. One place, all routes. Auth, logging, rate limiting, geo — anything per-request — belongs here. Verified security does not (that is Batch 5).

## In Your Own Words

<details>
<summary>1. Why not just do per-page checks? What breaks?</summary>

**Sample Answer:** Without a proxy, every page repeats the same checks (auth, logging, geo). That is duplication, and the easy mistake is forgetting one — that page becomes unprotected. The proxy centralizes it: one check, every route.

</details>

<details>
<summary>2. Walk the request lifecycle from browser to rendered page.</summary>

**Sample Answer:** The browser sends a request → it hits the proxy first → the proxy decides (next / redirect / block) → only after that does Next.js match the route and render the page. The proxy always runs before rendering.

</details>

<details>
<summary>3. `middleware.ts` vs `proxy.ts` — what actually changed?</summary>

**Sample Answer:** Same feature, new naming convention. Next 16 renamed the export (`middleware` → `proxy`) and the file (`middleware.ts` → `proxy.ts`). Upgrading code triggers a deprecation warning, and an official codemod can migrate it automatically.

</details>

<details>
<summary>4. Why is the proxy "not the main security layer"?</summary>

**Sample Answer:** Proxies can be bypassed (CVE-2025-29927) and cookie-presence is spoofable. The proxy's job is routing and infra-level concerns; verified auth — checking that a session is genuinely valid — belongs in layouts and Server Components (Batch 5).

</details>

<details>
<summary>5. Express middleware vs Next.js proxy — same thing?</summary>

**Sample Answer:** No. Express middleware is a function you chain manually inside route declarations — it is inside your control. Next.js's proxy is framework-level and automatic: it runs on every request before routing, outside your route code. Same idea of intercepting requests, different scope and control.

</details>
