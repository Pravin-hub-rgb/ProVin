In 4.12 we saw a protected-routes demo — and the honest note that a cookie-presence check is not real auth. **Now a use case where the proxy's check is production-valid: rate limiting.** More than 10 requests per second from a single IP — block it. Brute-force login attempts, API spam, scraping — all stopped here. In 4.12 we called it a "demo"; this is the real pattern (with one limitation at the end).

---

## The Problem — Too Many Requests

Imagine a script blasting 500 requests per second at your API. Or a brute-force login attempt trying 1,000 passwords. Each request is expensive (database hit, auth check) — server load, and who knows the intent behind it.

**Solution:** give each IP a fixed limit within a time window. Exceed it → respond with **429 Too Many Requests**.

---

## Step 0 — Storage Design (The Most Important Part)

Where to store the counts? **Not inside the `proxy()` function** — because it runs **again on every request**, resetting any local variable:

```ts
export function proxy(request: NextRequest) {
  let count = 0            // fresh 0 on every request!
  count++                  // always ends up 1 — counting is broken
  ...
}
```

**The fix:** define counts **outside** the function, at module level. The module loads once, the variable persists, and every request accesses the same object:

```ts
const requestCounts = {}   // module-level — persists between requests

export function proxy(request: NextRequest) {
  // read and update requestCounts — every request sees the same object
}
```

**Lifetime of a module-level variable:** as long as the server runs, the variable lives on. (A restart resets everything — fine for dev/testing; production needs an external store, explained at the end.)

---

## Step 1 — The Data Shape: `Record<K, V>`

Each IP needs an entry: a count and when its window resets. In TypeScript:

```ts
const requestCounts: Record<string, { count: number; resetTime: number }> = {}
```

**`Record<K, V>` is a TypeScript utility type** — "an object whose keys are of type K and whose values are of type V":

```ts
// Record<string, number> — string keys, number values
const scores: Record<string, number> = {
  player1: 10,
  player2: 25,
}

// Our case — the value is itself an object
// Record<string, { count: number; resetTime: number }>
const requestCounts = {
  "49.36.10.5":  { count: 7, resetTime: 1720000000000 },
  "8.8.8.8":     { count: 2, resetTime: 1720000001000 },
  //    ^ IP (string key)      ^ count     ^ when to reset (timestamp)
}
```

`resetTime` is a timestamp in milliseconds — "now plus the window." `Date.now()` gives you the current time in milliseconds:

```ts
Date.now()           // → 1720000000000 (ms since 1970)
```

"When does the window end?" — `resetTime: now + WINDOW_MS` — a minute from now.

---

## Step 2 — The Increment Logic (First Request)

Inside the window, the first request creates the entry:

```ts
import { NextRequest, NextResponse } from "next/server"

const RATE_LIMIT = 10
const WINDOW_MS = 60 * 1000

const requestCounts: Record<string, { count: number; resetTime: number }> = {}

export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  const now = Date.now()

  if (!requestCounts[ip]) {
    requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }
  } else {
    requestCounts[ip].count++
  }

  console.log(`IP: ${ip} — Count: ${requestCounts[ip].count}`)
  return NextResponse.next()
}
```

- `!requestCounts[ip]` — no entry for this IP yet → first request → `{ count: 1, resetTime: now + 60000 }`
- `else` — entry exists → `count++`
- `WINDOW_MS = 60 * 1000` — 60 seconds in milliseconds (60000 ms = 1 minute)

---

## Step 3 — Window Expiry (Time to Reset)

After the window ends, the count should reset — otherwise it grows forever. The check: **"has the resetTime passed? → start fresh":**

```ts
if (!requestCounts[ip] || now > requestCounts[ip].resetTime) {
  requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }   // fresh start
} else {
  requestCounts[ip].count++                                       // increment
}
```

Two conditions joined by OR (`||`): no entry **or** the window expired → fresh start. Then log the status:

```ts
const status = now <= requestCounts[ip].resetTime ? "Active" : "Expired"
console.log(`IP: ${ip} — Count: ${requestCounts[ip].count} — Window: ${status}`)
```

**Visualizing the window (clock metaphor):**

| Scenario | now vs resetTime | Result |
|---|---|---|
| Window active — 10:00:30, reset at 10:01:00 | now < reset | `count++` |
| Window expired — 10:01:10, reset was 10:01:00 | now > reset | fresh start (count 1) |
| New IP — no entry yet | — | fresh start |

---

## Step 4 — Block: `RATE_LIMIT` and 429

Now enforce the limit — block on the 11th request:

```ts
const RATE_LIMIT = 10

export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  const now = Date.now()

  if (!requestCounts[ip] || now > requestCounts[ip].resetTime) {
    requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }
  } else {
    requestCounts[ip].count++
  }

  if (requestCounts[ip].count > RATE_LIMIT) {
    return new NextResponse("Too Many Requests", { status: 429 })
  }

  return NextResponse.next()
}
```

- `count > RATE_LIMIT` — once it exceeds 10 (the 11th request), block.
- `new NextResponse("Too Many Requests", { status: 429 })` — a brand-new response with body and status. This is the **`NextResponse` constructor itself**, not the `next()` / `redirect()` / `rewrite()` factory methods.
- **429 = "Too Many Requests"** — the HTTP status code specifically for rate limiting. It tells the client: slow down, you have sent too many.

**Test it:**

```
First 10 requests → 200 ×10
11th request → 429
12th onward → 429 (until the window expires)
A different IP → 200 (per-IP counting — other users are not limited)
```

> **Note:** `new NextResponse(...)` here is a blocking response in the proxy — the page does not render. The client gets the plain "Too Many Requests" text (or you can return JSON or a custom body).

## Honest Limitation — In-Memory, Single Instance

**This pattern is correct for dev/learning — but it has one production problem:**

`requestCounts` lives in this one **machine's (instance) memory.** On Vercel or any cloud host your app runs across **multiple instances** when scaling — each instance has its own `requestCounts`:

```
Instance A: user made 8 requests — count 8
Instance B: user made 8 requests — count 8
Total 16 — the limit of 10 is hit by design, but neither instance saw 429
```

The effective limit becomes `RATE_LIMIT × instances` — the control is gone. **Production fix: a shared store** — **Redis** (or a database). Every instance reads and updates the same counter. Same concept, shared storage:

```
Proxy → Redis GET / INCR → rate-limit check
```

(Redis setup comes later, in Batch 6 of your course — here you only need the concept: in-memory works on one instance, but production needs shared storage.)

## What It Is NOT

- **Rate limiting ≠ auth/security in the auth sense.** It protects against DoS and spam — it does not verify who the user is. Identity verification is a separate layer (the "why not" from 4.12).
- **This is per-IP, not per-user.** Many users can share one IP (office networks) and be limited collectively. Production can use finer keys (user ID) when the user is already authenticated.
- **Blocking is not "punishing the user."** Rate limiting is a legitimate part of the request flow; a 429 just means "slow down." Production polish adds a `Retry-After` header so the client knows when to try again.
- **Counts are not persistent.** A server restart resets everything (in-memory). Even with a shared store, you need an expiry policy — this code handles count-expiry via the window, but memory is still held by inactive IP entries.

## Common Mistakes

- **Putting `count` inside the proxy function.** It resets on every request (Step 0). Module-level is required.
- **Forgetting the window-expiry check.** Without `now > resetTime`, the count never resets — the user is permanently blocked after the first 10 requests.
- **Forgetting the 429 status.** `new NextResponse("...")` defaults to 200. You must pass `{ status: 429 }`.
- **Ignoring IP spoofing.** `x-forwarded-for` can be set by the client directly (4.5) — in production, a trusted proxy or load balancer normalizes the real IP.
- **Counting every request.** Static files are already excluded by the matcher (4.3) — otherwise CSS and image requests inflate the count.

## Nutshell

Module-level `requestCounts` (not inside the function — it resets). The type `Record<string, { count, resetTime }>` maps each IP to its entry. Fresh start when there is no entry **or** the window expired (`now > resetTime`). Exceeding the limit returns `new NextResponse("Too Many Requests", { status: 429 })`. Per-IP + fixed window + in-memory = dev-grade; production swaps in a shared store like Redis.

**In Your Own Words**

1. Why is the count stored outside the proxy function — not as a local variable?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `proxy()` is re-invoked on every request, so a local variable `let count = 0` gives a fresh zero each time and `count++` never gets past 1. Storing the object at module level means it is created once at load time and **every request reads and updates the same object** — counts persist across requests. Its lifetime is tied to the process: it lives as long as the server runs and resets on restart (fine for dev, external store for production).

</details>

2. What does `Record<string, { count: number; resetTime: number }>` describe, and how do you read one entry?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `Record<K, V>` means "an object whose keys are K and values are V." Here the keys are strings (IP addresses) and each value is an object `{ count: number; resetTime: number }`. An entry looks like `{ "49.36.10.5": { count: 7, resetTime: 1720000000000 } }` — the IP as key, the request count and the timestamp when this window resets. `resetTime` is `Date.now() + WINDOW_MS`.

</details>

3. For the window-expiry check `!requestCounts[ip] || now > requestCounts[ip].resetTime`, when does each branch trigger a fresh start?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Two cases trigger a fresh start (joined by `||`): (a) `!requestCounts[ip]` — no entry exists for this IP yet (first request or after a server restart), (b) `now > resetTime` — the entry exists but the window has already expired. In both cases the count restarts at 1. Otherwise (window still active) the count is incremented. Without this expiry check, the count grows forever and the user is permanently blocked after the first window.

</details>

4. How is `new NextResponse("Too Many Requests", { status: 429 })` different from `NextResponse.next()` — and what does 429 mean?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `next()`, `redirect()`, and `rewrite()` are factory methods for common scenarios. `new NextResponse(body, options)` is the response **constructor** — you choose the body text and the status yourself. Here the body is "Too Many Requests" and `{ status: 429 }` sets the HTTP status. 429 is the standard "Too Many Requests" code — the client knows it has been rate-limited. The page does not render; the client gets the response directly.

</details>

5. Why is in-memory rate limiting not enough in production — why Redis?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The `requestCounts` object lives in one instance's memory. Cloud apps run across multiple instances — each instance has its own counter. A user making 8 requests on instance A and 8 on instance B sees 8 + 8 = 16, but neither instance reaches the limit of 10 on its own, so no 429 is returned. The effective limit becomes `RATE_LIMIT × number_of_instances` — the control erodes. Redis is a shared store: every instance reads and updates the same counter, so the limit is enforced consistently across the whole application. Same concept, shared storage.

</details>
