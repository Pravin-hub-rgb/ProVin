4.12 mein protected routes ka demo hua — aur wahan ek honest note bhi tha: cookie-presence check auth ke liye nahi hai. **Ab ek use case aata hai jahan proxy ka check production-valid hai: rate limiting.** Ek IP se 10 requests/second se zyada — block. Brute-force login attempts, API spam, scraping — sab isi se rokte ho. Yahan 4.12 wala "demo" nahi — yeh pattern real hai (bas ek limitation hai, end mein).

---

## Problem — Bahut Saari Requests

Socho koi script 500 requests/second bhej raha hai tumhare API pe. Ya brute-force login attempt — 1000 passwords try kar raha hai. Har request expensive hai (database hit, auth check) — server pe load, aur kya pata kaunsi bad intention.

**Solution:** har IP ko ek limit do — ek time window mein fixed requests. Zyada → **429 Too Many Requests** block.

---

## Step 0 — Storage Ka Design (Sabse Important)

Counts kahan rakhne hain? **`proxy()` function ke andar nahi** — kyunki woh **har request pe dobara chalta hai** — local variable har call pe reset:

```ts
export function proxy(request: NextRequest) {
  let count = 0            // har request pe naya 0!
  count++                  // hamesha 1 rahega — counting galat
  ...
}
```

**Fix:** counts **function ke bahar**, module-level — module load hota hai ek baar, variable wahi rehta hai, har request pe same object access:

```ts
const requestCounts = {}   // module-level — requests ke beech persist

export function proxy(request: NextRequest) {
  // yahan requestCounts ko read/update — har request pe same object
}
```

**Module-level variable ka lifetime:** server chalu rahe toh variable bhi rahe. (Restart = sab zero — dev/testing ke liye okay, production mein external store — end mein.)

---

## Step 1 — Data Ka Shape: `Record<K, V>`

Har IP ki entry chahiye: count + window kab reset hoga. TypeScript type:

```ts
const requestCounts: Record<string, { count: number; resetTime: number }> = {}
```

**`Record<K, V>` kya hai** — TypeScript ka utility type — "ek object jiske keys K type ki, values V type ki":

```ts
// Record<string, number> — keys strings, values numbers
const scores: Record<string, number> = {
  player1: 10,
  player2: 25,
}

// Hamara case — value khud object hai
// Record<string, { count: number; resetTime: number }>
const requestCounts = {
  "49.36.10.5":  { count: 7, resetTime: 1720000000000 },
  "8.8.8.8":     { count: 2, resetTime: 1720000001000 },
  //    ^ IP (string key)     ^ count ^ jab reset hoga (timestamp)
}
```

`resetTime` timestamp hai — milliseconds mein (abhi + window). `Date.now()` — abhi ka time milliseconds mein:

```ts
Date.now()           // → 1720000000000 (ms since 1970)
```

"Window kab khatam?" — `resetTime: now + WINDOW_MS` — abhi se ek minute aage.

---

## Step 2 — Increment Logic (Pehli Request)

Window ke andar pehli request — entry banao:

```ts
import { NextRequest, NextResponse } from "next/server"

const RATE_LIMIT = 10
const WINDOW_MS = 60 * 1000

const requestCounts: Record<string, { count: number; resetTime: number }> = {}

export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  const now = Date.now()

  if (!requestCounts[ip]) {
    requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }
  } else {
    requestCounts[ip].count++
  }

  console.log(`IP: ${ip} — Count: ${requestCounts[ip].count}`)
  return NextResponse.next()
}
```

- `!requestCounts[ip]` — is IP ki koi entry nahi → pehli request → `{ count: 1, resetTime: now + 60000 }`
- `else` — entry hai → `count++`
- `WINDOW_MS = 60 * 1000` — 60 second, milliseconds mein (60000 ms = 1 minute)

---

## Step 3 — Window Expiry (Agla Step)

Window khatam hone ke baad count reset hona chahiye — warna count hamesha badhta rahega. Check: **"resetTime guzar gaya? → nayi entry"**:

```ts
if (!requestCounts[ip] || now > requestCounts[ip].resetTime) {
  requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }   // fresh start
} else {
  requestCounts[ip].count++                                       // count++
}
```

Do condition OR (`||`): entry nahi **ya** window expired → fresh start. Status bhi log karo:

```ts
const status = now <= requestCounts[ip].resetTime ? "Active" : "Expired"
console.log(`IP: ${ip} — Count: ${requestCounts[ip].count} — Window: ${status}`)
```

**Windows ko visualize karo (clock metaphor):**

| Scenario | now vs resetTime | Result |
|---|---|---|
| Window active — 10:00:30, reset 10:01:00 | now < reset | `count++` |
| Window expired — 10:01:10, reset 10:01:00 | now > reset | fresh start (count 1) |
| Naya IP — koi entry nahi | — | fresh start |

## Step 4 — Block: `RATE_LIMIT` + 429

Ab limit enforce karo — 11th request block:

```ts
const RATE_LIMIT = 10

export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  const now = Date.now()

  if (!requestCounts[ip] || now > requestCounts[ip].resetTime) {
    requestCounts[ip] = { count: 1, resetTime: now + WINDOW_MS }
  } else {
    requestCounts[ip].count++
  }

  if (requestCounts[ip].count > RATE_LIMIT) {
    return new NextResponse("Too Many Requests", { status: 429 })
  }

  return NextResponse.next()
}
```

- `count > RATE_LIMIT` — 10 ke baad (11th request se) block
- `new NextResponse("Too Many Requests", { status: 429 })` — naya response banao — body + status. **`NextResponse` seedha bhi bana sakte ho** — `next()`/`redirect()`/`rewrite()` hi methods nahi hain — response constructor hai.
- **429 = "Too Many Requests"** — HTTP status code specifically rate limiting ke liye (client ko batao: zyada bheja, thoda ruko).

**Test:**

```
10 requests → 200 ×10
11th request → 429
12th+ → 429 (window khatam tak)
Alag IP → 200 (per-IP counting — doosre users limited nahi)
```

> **Note:** `new NextResponse(...)` proxy mein block response hai — page render nahi hota. Client ko seedha "Too Many Requests" text milta hai (ya custom body/JSON likho).

## Honest Limitation — In-Memory, Single Instance

**Yeh pattern dev/learning ke liye sahi hai — production mein ek problem hai:**

`requestCounts` **is machine (instance) ka memory** hai. Vercel/cloud pe app **multiple instances** pe chalti hai (scaling) — har instance ka apna `requestCounts`:

```
Instance A: user ne 8 requests ki — count 8
Instance B: user ne 8 requests ki — count 8
Total 16 — limit 10 ho gayi by design, par kisi ne 429 nahi dekha
```

Effective limit = RATE_LIMIT × instances — control khatam. **Production solution: shared store** — **Redis** (ya database) — sab instances ek hi counter read/update karte hain. Concept wahi, storage shared:

```
Proxy → Redis GET count / INCR → limit check
```

(Redis full setup aage Batch 6/tumhare DukaanOS mein aayega — yahan bas concept: in-memory single-instance hai, production ko shared chahiye.)

## What It Is NOT

- **Rate limiting ≠ security layer (auth wali)** — yeh DoS/spam se bachata hai, user identity nahi verify karta. Security ka apna layer (auth) alag — 4.12 wala why-not.
- **Yeh per-user limit nahi** — per-IP. Ek IP ke peeche multiple users ho sakte hain (office network) — woh collectively limited ho jayenge (production mein granular keys: user-id based bhi hoti hain).
- **Blocking = user "punish" nahi** — rate limit legit flow ka hissa hai; 429 ka matlab "thoda ruko" (Retry-After header wala polish production mein hota hai).
- **Counts persistent nahi** — server restart = sab zero (in-memory). Production shared store mein bhi cleanup/expiry policy chahiye (yahan window expiry se stale entries khud zero ho jati hain count-wise, par entries memory mein rehti hain).

## Common Mistakes

- **Count variable function ke andar** — har request pe reset (Step 0) — module-level zaroori.
- **Window expiry check bhoolna** — bina `now > resetTime` ke count hamesha badhta rahega — pehli 10 ke baad user hamesha block.
- **`429` status bhoolna** — `new NextResponse("...")` default 200 hota — `{ status: 429 }` daalna zaroori.
- **IP spoofing ka dhyan nahi** — `x-forwarded-for` raw client daal sakta hai (4.5) — production mein trusted proxy/load balancer se normalized IP lete hain.
- **Har request pe counting** — matcher se static files already excluded (4.3) — warna CSS requests bhi count hoti.

## Nutshell

Module-level `requestCounts` (function ke andar nahi — reset hota). `Record<string, {count, resetTime}>` — har IP ki entry. Fresh start: entry nahi **ya** window expired (`now > resetTime`). `count > RATE_LIMIT` → `new NextResponse("...", { status: 429 })`. Per-IP + fixed window + in-memory = dev-grade; production = Redis (shared store).

2. `Record<string, { count: number; resetTime: number }>` — is type ka structure batao, ek example ke saath?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `Record<K, V>` — object jiske keys K type ke, values V type ke. Yahan keys string (IP address), values object `{ count: number, resetTime: number }`. Example: `{ "49.36.10.5": { count: 7, resetTime: 1720000000000 } }` — IP → uski entry (kitni requests + window kab reset). resetTime timestamp hai milliseconds mein — `Date.now() + WINDOW_MS`.

</details>

3. Window expiry ka logic — `!requestCounts[ip] || now > requestCounts[ip].resetTime` — do conditions kab trigger hoti hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `||` ke saath do fresh-start triggers: (a) `!requestCounts[ip]` — is IP ki entry hai hi nahi (naya user / phir se server mein), (b) `now > resetTime` — entry hai par window khatam ho gaya (abhi ka time reset ke baad). Dono mein count 1 se fresh. Else — window active — `count++`. Bina expiry check ke count kabhi reset nahi hota — pehle 10 requests ke baad user hamesha blocked.

</details>

4. `new NextResponse("Too Many Requests", { status: 429 })` — yeh `next()`/`redirect()` se kaise alag hai — aur 429 kya hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `next()`/`redirect()`/`rewrite()` — predefined behaviors wale factory methods. `new NextResponse(body, options)` — response ka **constructor** — tum khud body + status decide karte ho. Yahan "Too Many Requests" body + status 429 — page render nahi hota, client ko seedha block message. 429 HTTP ka official "Too Many Requests" code hai — client ko signal: zyada bheja, rate limit hit.

</details>

5. In-memory store ki production limitation kya hai — Redis kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `requestCounts` us instance ki memory hai. Cloud apps multiple instances pe chalti hain — har instance ka apna counter — user 8 requests instance A pe, 8 instance B pe — total 16 par kisi ko 429 nahi aaya (effective limit = RATE_LIMIT × instances). Redis shared store hai — sab instances ek hi counter read/update karte hain — limit consistent. Concept same, storage shared — production ka rule: rate limit state shared jagah.

</details>
