4.2 mein `proxy.ts` banaya aur dekha ki woh har request pe chal raha hai — matcher se static files exclude kiye, par **woh regex pattern seedha copy-paste kiya tha, samjha nahi tha.** Ab matcher ko properly samjhenge: simple route, multiple routes, children routes, negative matcher — aur kab kaunsa pattern use karna chahiye.

---

## Problem — Abhi Kya Galt Hai

Abhi proxy **har** request pe chalta hai (matcher negative wala). Isme do problems:

1. **Performance** — CSS, JS, images pe proxy bekar chal raha hai
2. **Galt page pe check** — hamein sirf un routes pe check chahiye jahan kaam hai

Matcher ka kaam: **"proxy kahan chale, kahan na chale"** ka decision. Ek route ko alag karte hain aur pehle wahi samjhte hain.

---

## Step 1 — Simple Matcher (Ek Route)

`proxy.ts` mein matcher badlo:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  console.log("Proxy chal raha hai:", request.nextUrl.pathname)
  return NextResponse.next()
}

export const config = {
  matcher: "/dashboard",
}
```

**Test karo:** `/dashboard` visit karo — **kuch print nahi hoga!**

Kyun? — **Next.js server restart nahi hua.** `config` change karne ke baad dev server restart karna padta hai (`Ctrl+C`, phir `npm run dev`). `proxy.ts` ke function body changes hot-reload hote hain, `config` nahi — ek rule yaad rakho: **matcher badla → server restart.**

Restart ke baad:

```
http://localhost:3000/dashboard → "Proxy chal raha hai: /dashboard" ✅
http://localhost:3000/about     → kuch nahi ✅
```

---

## Step 2 — Multiple Routes (Array)

Do teen routes pe chalana hai — string ki jagah **array**:

```ts
export const config = {
  matcher: ["/dashboard", "/profile", "/settings"],
}
```

**Test:**

```
/dashboard → chala ✅
/profile   → chala ✅
/settings  → chala ✅
/about     → nahi chala ✅
```

Simple rule: sirf **exact** yehi teen paths pe chalega.

---

## Step 3 — Children Routes (`:path*`)

Ab socho — `/dashboard` ke andar bhi pages hain:

- `/dashboard/settings`
- `/dashboard/analytics`
- `/dashboard/users/123`

Sirf `"/dashboard"` likhne se **sirf exact** `/dashboard` pe chalega — children pe nahi. Kyun? Kyunki matcher path ko string ki tarah match karta hai — `/dashboard/settings` toh `/dashboard` se alag string hai.

Children bhi cover karne ke liye `:path*` lagao:

```ts
export const config = {
  matcher: ["/dashboard/:path*"],
}
```

`*` ka matlab: **"zero ya zyada"** — `/dashboard` ke baad kuch bhi ho ya kuch na ho. `:path` ek named wildcard hai — naam se koi matlab nahi, `:anything*` bhi chalega. Pattern kuch aisa samjho:

```
/dashboard           → match (zero extra) ✅
/dashboard/settings  → match (ek extra)  ✅
/dashboard/users/123 → match (do extra)  ✅
/about               → nahi               ❌
```

---

## Step 4 — Problem Aayegi: Static Files

`/dashboard/:path*` lagao aur `/dashboard` visit karo — **page load nahi hoga!**

Kyun? Kyunki Next.js har page load pe **extra requests** karta hai:

- `/_next/static/...` — JS/CSS files
- `/_next/image/...` — optimized images
- `/favicon.ico` — browser icon

Aur matcher ke nazriye se... `/_next/static/...` toh `/dashboard` se shuru nahi hota — galat. **Ruko** — Next.js 16 mein static assets ka URL structure changed hua hai (prefixed paths), lekin problem same rehti hai: kuch paths tum match karna nahi chahte aur woh `:path*` wale pattern ke zehniyat mein aate hain. Real rule yahi hai:

**`:path*` + specific route = static assets ko bhi match kar sakta hai** — kyunki pattern prefix-based hai. Isliye ek alternate chahiye jo "sab pe chale EXCEPT yeh cheezein" bata sake — woh hai **negative matcher**.

---

## Step 5 — Negative Matcher (Sab Pe Chalo, Except...)

**Negative matcher** = "in cheezon ko chhod ke baaki sab pe chalao":

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"],
}
```

Ab is regex ko **actually todenge** (4.2 mein copy-paste ki thi, ab samjhte hain):

```
"/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"
```

Piece by piece:

| Part | Matlab |
|---|---|
| `/` | Path `/` se shuru hota hai |
| `(...)` | Ek group — poori cheez ko ek unit banata hai |
| `(?!...)` | **Negative lookahead** — "agar yeh na ho toh" (turant check, consume nahi karta) |
| `_next/static\|_next/image\|favicon.ico\|.*\\.svg` | `\|` = OR. Yehi cheezein **exclude** karni hain |
| `.*` | Zero ya zyada koi bhi characters — baaki sab |

**Read karo:** "`/` ke baad jo aayega — agar woh `_next/static`, `_next/image`, `favicon.ico`, ya `.svg` wali cheez na ho — toh match."

Isliye `/about` match hota hai (negative lookahead fail nahi — koi excluded cheez nahi), aur `/_next/static/css/xyz.css` match nahi hota (excluded list mein hai).

## Step 6 — Real Scenario: Login Aur API Routes Exclude

Real app mein aur cheezein exclude karni padti hain — **login page** (warna infinite redirect loop — iska detail 4.8 mein) aur **API routes** (API pe auth check alag hota hai):

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|login|api).*)"],
}
```

**Test:**

```
/              → chala ✅
/dashboard     → chala ✅
/login         → nahi — public hai ✅
/api/anything  → nahi — API route hai ✅
```

---

## Step 7 — Kaunsa Pattern Kab? (Rule of Thumb)

```
Agar kam protected routes hain (2-3) → specific list karo
  matcher: ["/dashboard/:path*", "/profile/:path*"]

Agar zyada protected routes hain      → negative matcher
  matcher: ["/((?!login|api|_next/static|_next/image|favicon.ico).*)"]
```

**Real apps mein** negative matcher zyada common hai — kyunki protected/checked routes zyada hote hain, aur list maintain karna muskil. (Batch 4 ki series mein bhi mostly negative hi use karenge.)

---

## What It Is NOT

- **Matcher = middleware "logic" nahi** — matcher sirf routing ka decision hai (kaunse paths proxy function tak poochenge). Asli logic `proxy()` ke andar hai. Matcher bhi badha sakta hai (comma-separated conditions bhi support karta hai — par series ke scope se bahar hai, baseline isi se kaam chalta hai).
- **`startsWith` nahi, exact-path matching hai** — `"/dashboard"` se `/dashboard/settings` match nahi hota (children ke liye `:path*` chahiye). String prefix logic ko bhool jao — matcher apna pattern language hai.
- **Regex sirf negative matcher mein hai** — simple strings aur `:path*` patterns mein regex nahi hota. Mixed matcher mein dono types ho sakte hain.

## Common Mistakes

- **Matcher change ke baad server restart nahi** — sabse common! Function body hot-reload hota hai, `config` nahi. Badla → restart.
- **Children bhoolna** — `/dashboard` matcher lagao aur `/dashboard/settings` pe proxy nahi chali — `:path*` chahiye.
- **Static files ko `:path*` se accidentally match karna** — isliye negative matcher ka full path pattern use karte hain.
- **Regex copy-paste bina samjhe** — ab aata hai: `(?!...)` = "except", `|` = OR, `.*` = "baaki sab".

## Nutshell

Matcher = proxy kahan chale ka control. Ek route (string), multiple (array), children (`:path*`), sab-except (negative regex `(?!...)`). Rule: kam routes → specific list; zyada → negative. Config change pe restart zaroori.

**In Your Own Words**

1. Matcher `"/dashboard"` aur `"/dashboard/:path*"` mein kya farak hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `"/dashboard"` exact string match karta hai — sirf `/dashboard` pe proxy chalega, `/dashboard/settings` pe nahi (woh alag string hai). `"/dashboard/:path*"` prefix pattern hai — `*` ka matlab "zero ya zyada" — `/dashboard` pe bhi chalega aur uske saare children (`/dashboard/settings`, `/dashboard/users/123`) pe bhi. Har page ke liye alag entry likhni padti thi — `:path*` ek pattern se sab cover.

</details>

2. Negative matcher `"/((?!_next/static|_next/image|favicon.ico).*)"` ko apne words mein explain karo — `(?!...)`, `|`, `.*` kya karte hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Yeh regex "sab pe chalo EXCEPT yeh" ka matlab likhti hai: `/` se path shuru hota hai, `(?!...)` negative lookahead hai — "agar yeh na ho toh" — `|` OR hai jo excluded list banata hai (`_next/static` ya `_next/image` ya `favicon.ico`), aur `.*` "zero ya zyada koi bhi characters" matlab baaki sab. Total: agar path excluded list mein nahi hai toh match karo. Static assets ko chunkne ka tareeka — proxy har choti JS/CSS file pe bekar na chale.

</details>

3. Matcher change karne ke baad dev server restart kyun karna padta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Kyunki `config` (aur usme matcher) startup time pe read hota hai — Next.js routing decide karta hai ki kaunse paths proxy tak jayenge. `proxy()` function ka body hot-reload hota hai (dev HMR), par config nahi — wo server boot pe load hota hai. Isliye matcher badla → restart zaroori. Yeh rule 4.2 se bhi aata hai: config change, restart.

</details>

4. Real app mein negative matcher mein `login` aur `api` kyun exclude karte hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `login` exclude karte hain kyunki login page public hona chahiye — agar proxy uspe bhi auth check chalaye toh logged-out user ko `/login` se `/login` pe redirect karta rahega (infinite loop, 4.8 mein poora demo). `api` exclude karte hain kyunki API routes ka apna auth/validation layer hota hai — page-level proxy checks wahan irrelevant hain (aur performance ke liye bhi). Exclude list = "jahan proxy ka kaam nahi wahan mat jao".

</details>

5. Kaunsa matcher kab — specific list ya negative?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Kam checked routes (2-3) hon toh specific list — `["/dashboard/:path*", "/profile/:path*"]` — clear aur predictable. Zyada routes hon toh negative matcher — list maintain karna muskil hota hai aur "sab pe chalo except kuch public cheezein" wala model real apps ke zyada fit hota hai. Real apps mein negative common hai. Mixed bhi ho sakta hai — both patterns in same matcher array.

</details>

Matcher ka control aata gaya — proxy kahan chalega decide karna easy. Ab **andar kya milta hai** — 4.4 se request ko padhna shuru: URL (`pathname`, `searchParams`), phir headers, phir cookies. Proxy ke andar ka data hi asli decisions ka input hai.
