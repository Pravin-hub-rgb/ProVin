# Reading Headers — User-Agent, IP, Host (4.5)

## Where We Left Off

In 4.4 we read the URL — `pathname` to know where the user is going. Now **headers** — extra information that travels with the request. We start with the courier-parcel analogy: the parcel's **contents** (the request body/data) and the **label** (sender, receiver, "Fragile", "Urgent") — information about the parcel without opening it. Headers are that label — they describe the request before its body is even processed.

---

## What Are Headers

When the browser asks the server for something, a list of **key-value pairs** travels with the request — the headers:

```
User-Agent: Mozilla/5.0 (iPhone; ...) Mobile Safari
Host: localhost:3000
Accept: text/html
Cookie: session=abc123
```

Every request includes them (the browser sends them automatically; you never write them by hand). The proxy can **read** them — and from them, a lot is discoverable: the user's device, IP, browser, language...

Read headers in the proxy with `request.headers.get("name")`:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const userAgent = request.headers.get("user-agent")
  console.log("User agent:", userAgent)
  return NextResponse.next()
}
```

`headers.get("user-agent")` — pass the header name, get its value. A missing header returns `null` (same behavior as `searchParams.get` in 4.4).

---

## Step 1 — Device Detection (User-Agent)

The most common use: **the user's device.** The browser sends a `User-Agent` header describing which browser and device it is. Mobile detection:

```ts
export function proxy(request: NextRequest) {
  const userAgent = request.headers.get("user-agent")

  if (userAgent?.includes("Mobile")) {
    console.log("Request from a mobile device")
  }

  return NextResponse.next()
}
```

`.includes("Mobile")` — a string method — "does this string contain the text 'Mobile'?" — `true`/`false`. The `userAgent?.includes(...)` uses **optional chaining** (`?.`) — if `userAgent` is `null` (header missing), `.includes` is not called and `undefined` is returned instead — no crash. (This was introduced in 4.1 — a correct use case.)

**Test:** open on a phone browser → the mobile log appears. On desktop → nothing.

**A thought exercise:** serve a different design to mobile users (these days responsive CSS handles most of this, but the technique is still used for device-specific features).

---

## Step 2 — Reading the IP (X-Forwarded-For)

Another useful header: **`x-forwarded-for`** — which IP the request came from.

> **A concept worth noting:** in the proxy architecture, the browser does not send requests directly to your app server — a **load balancer or CDN** sits in between. The server receives the request from that middle machine, not from the real user — so where is the real user's IP? The middle layer puts it into the `x-forwarded-for` header and forwards it along.

```ts
export function proxy(request: NextRequest) {
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  console.log("IP:", ip)
  return NextResponse.next()
}
```

`?? "unknown"` — the **nullish coalescing** operator (from 4.5.4) — if the header is missing, fall back to `"unknown"` instead of crashing.

**Test (spoofing with curl):**

```bash
curl -H "X-Forwarded-For: 49.36.10.5" http://localhost:3000/
```

In the terminal: `IP: 49.36.10.5`. In local dev, requests from `localhost` may show values like `::ffff:127.0.0.1` (IPv6-mapped IPv4) — both are just localhost.

**This IP is the foundation for:** 4.13 (rate limiting — "how many requests from this IP?"), and 4.14 (geo blocking — "where is this IP?").

---

## Step 3 — Host and Other Headers

`.get("host")` — which domain the request is for:

```ts
const host = request.headers.get("host")
console.log("Host:", host) // → "localhost:3000"
```

The host is useful when multiple domains resolve to the same app and you want to serve different content. Every other header works the same way with `.get()`.

---

## What It Is NOT

- **Reading headers does not modify data.** `headers.get` only reads — adding headers to the response (4.10) is a separate operation.
- **`x-forwarded-for` does not contain a single trusted IP.** Some setups return a comma-separated list (`1.2.3.4, 5.6.7.8` — one per hop). And critically: **this header can be spoofed by the client** (we set it ourselves with curl above). In production, a trusted proxy or load balancer overwrites it. For learning it is fine — just know you cannot fully trust the raw header for security.
- **User-Agent is also spoofable.** Device detection from the user-agent is "best effort," not a hard security rule.

## Common Mistakes

- **Forgetting `?.`.** Calling `.includes(...)` on a missing header crashes. Use `userAgent?.includes(...)` or check for null first.
- **Using raw IP for security.** 4.13 covers this: IP must be normalized and spoofing considered for rate limiting.
- **Header name case.** `.get("User-Agent")` and `.get("user-agent")` both work (HTTP headers are case-insensitive), but conventionally lowercase is used.
- **Ignoring missing headers.** Same rule as `searchParams`: provide a fallback or check the result.

## Nutshell

`request.headers.get("name")` — read the request's metadata. User-Agent → device detection (`includes("Mobile")`), `x-forwarded-for` → IP (`?? "unknown"`), host → domain. These two — IP and user-agent — become the basis for rate limiting and geo blocking later. Headers are spoofable, so in production trust a trusted proxy for the real values.

**In Your Own Words**

1. The courier analogy for headers — what is a parcel's "label"?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The parcel's contents = the actual goods = the request data (body). The label = information printed on the outside that tells you about the parcel without opening it — sender, receiver, "Fragile" or "Urgent" stamps = headers (User-Agent, Host, x-forwarded-for). Just by reading the label, you know where the parcel came from, what is inside it, and special handling notes — just like headers tell you, without reading the body, where the request came from and what kind it is.

</details>

2. What does `request.headers.get("user-agent")` return — and why use `?.`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The header's value as a string — when the header is present. If the header is missing (not every request sends all headers), it returns `null`. Use `?.` for optional chaining because `userAgent?.includes("Mobile")` returns `undefined` instead of calling `.includes` on a null value — avoiding a TypeError crash.

</details>

3. What is `x-forwarded-for` — and why doesn't the browser send the IP directly?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In real-world deployments the browser does not send requests directly to the app server — a load balancer or CDN sits in the middle. The server receives the request from that intermediate machine, so its own IP is not the user's. That layer puts the real user's IP into the `x-forwarded-for` header and forwards it. The header lets the server see the real client IP. (Caveat: the client can also send this header themselves — in production, a trusted proxy overwrites it; do not trust the raw value blindly.)

</details>

4. Why use `?? "unknown"` for headers — what does it guarantee?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `get()` returns `null` when a header is missing — without a fallback, the `ip` variable could be null and break downstream logic (logging, rate-limiting). `?? "unknown"` is nullish coalescing: it substitutes a default when the value is null or undefined. After it, the variable is always a string — null can never leak into the logic. The proxy runs on every request, so every edge case (including missing headers) must be handled.

</details>

5. Device detection from User-Agent — is it a hard rule or best effort? Why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Best effort. The User-Agent header is client-controlled — browsers can be spoofed (change it in DevTools, or send a custom header with curl — as done in the test). Device detection is for UX optimization (different layout or features), not for security. The spoofability of headers is something to keep in mind when making decisions — that is the production mindset.

</details>
