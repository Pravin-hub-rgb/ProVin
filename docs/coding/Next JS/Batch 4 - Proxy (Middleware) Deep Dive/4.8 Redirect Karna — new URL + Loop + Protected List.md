4.7 mein teen methods ka fark samjha — `next` vs `redirect` vs `rewrite`. Ab pehla practical: **`redirect()` properly implement karna** — real protected-route example ke saath. Yahan kuch aata hai jo abhi tak nahi dekha: `new URL(path, base)` syntax, **infinite loop** problem, aur `protectedRoutes` array + `.some()` wala pattern.

---

## Step 1 — Redirect Ka Syntax

4.6 mein login-check log-only kiya tha — ab actual redirect:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has("session")

  if (!hasSession) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|login).*)"],
}
```

**Kya badla:**

- `return NextResponse.redirect(...)` — console.log ki jagah actual redirect. `return` = "function yahin khatam, yeh response bhejo".
- Matcher mein `login` add kiya — `|login` negative list mein.

Do naye elements samjhte hain — `new URL()` aur `login` exclusion.

---

## `new URL(path, base)` — URL Object Banate Hain

```ts
new URL("/login", request.url)
```

`URL` — JavaScript ki built-in class — URLs banane/parse karne ke liye. Do arguments:

1. `path` — kahan redirect karna hai — `"/login"`
2. `base` — base URL — `request.url` (incoming request ka poora URL)

**Kyun base mein `request.url`?** Taaki Next.js sahi domain pe redirect kare. Dev mein `http://localhost:3000/login` banega, production mein `https://myapp.com/login`. Base tumhara "jahan se shuru karo" hai — path usme join hota hai.

`new` keyword — class ka naya instance banane ke liye (URL object bana rahe ho, string nahi).

Phir `NextResponse.redirect(url)` — URL object le kar response banata hai: "browser, is URL pe jaao" — response mein `Location` header ke saath **307 status** (4.7 mein verify kiya tha — curl se 307 + Location dikha).

---

## Infinite Loop — Login Page Ko Exclude Karna

**Socho kya hoga agar matcher mein `login` exclude na ho:**

```
/login visit kiya
    ↓
Proxy chala — session nahi hai
    ↓
/login pe redirect kiya
    ↓
Proxy chala — session nahi hai
    ↓
/login pe redirect kiya
    ↓
...infinite loop 🔄
```

**Security guard analogy:** building ke entrance pe guard — tumhare paas ID nahi — guard bolta hai "reception se ID lao" — reception pe pahunchte hi **guard wahan bhi hai** aur phir bolta hai "reception se ID lao"... tum kabhi ID nahi la sakte.

**Fix:** guard sirf entrance pe hai, reception pe nahi — matlab `/login` pe proxy ka check hi nahi chalna chahiye:

```ts
matcher: ["/((?!_next/static|_next/image|favicon.ico|login).*)"]
```

`|login` = negative list mein add. Ab `/login` pe proxy nahi chalta — check nahi, redirect nahi, loop nahi.

> **Rule yaad rakho:** jis page pe redirect kar rahe ho, usse matcher se exclude karo. Yahi rule aage bhi use hoga — `/login` wale redirects mein (4.12 mein poora login-flow demo).

## Step 2 — Sirf Protected Routes Pe Redirect

Abhi `!hasSession` pe **har** route redirect ho raha hai — `/about` pe bhi — jo public hona chahiye. Protected routes ki list define karo:

```ts
import { NextRequest, NextResponse } from "next/server"

const protectedRoutes = ["/dashboard", "/profile", "/settings"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const isProtected = protectedRoutes.some((route) =>
    pathname.startsWith(route)
  )

  if (isProtected && !request.cookies.has("session")) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|login|api).*)"],
}
```

**Naye pieces:**

- `protectedRoutes` — array, protected paths ki list. Isme change karna = protection ka map update.
- `.some((route) => pathname.startsWith(route))` — array method — "kya array mein **koi ek** element yeh condition satisfy karta hai?" — `true`/`false`:

```js
["/dashboard", "/profile"].some((route) => "/dashboard/settings".startsWith(route))
// → true — kyunki "/dashboard/settings" startsWith "/dashboard"
```

- `isProtected && !request.cookies.has("session")` — do conditions dono true tabhi redirect: route protected hai **aur** session nahi hai. `/about` public → isProtected false → redirect skip → `next()`.
- Matcher mein `api` bhi add kiya — API routes apna kaam karte hain, page-level check wahan nahi.

## Step 3 — Test Karna

**Test matrix (4.6 wala cookie trick + curl):**

```
Bina cookie: /dashboard       → 307 → /login ✅
Bina cookie: /dashboard/settings → 307 → /login ✅ (children bhi covered)
Bina cookie: /about           → 200 — public ✅
Bina cookie: /login           → koi redirect nahi — loop-safe ✅
Cookie: session=abc123 → /dashboard → 200 ✅
```

(Chhota note: `startsWith` prefix check hai — `/dashboardevil` jaisa path bhi `startsWith("/dashboard")` true dega. Real apps mein boundary check chahiye — learning ke liye fine, 4.12 mein iska dhyan rakhna.)

## What It Is NOT

- **Redirect = "user ko block karna" nahi** — redirect user ko sahi jagah le jaata hai (login pe), woh flow ka hissa hai, punishment nahi.
- **`new URL` optional nahi** — `NextResponse.redirect("/login")` string ke saath bhi chalega kuch versions mein, par `new URL(path, base)` correct + production-safe hai (domain ke saath absolute URL).
- **"Har check ke liye redirect" nahi** — redirect tab hi jab route protected ho. Public routes (about, home, login) ko untouched `next()`.
- **Proxy redirect = auth security nahi** — yahan cookie-presence se redirect ho raha hai, verified session nahi. Demo hai (4.12 mein why-not full).

## Common Mistakes

- **Redirect wale page ko matcher mein exclude bhoolna** — infinite loop (sabse common + sabse nasty bug — server crash nahi, bas loop).
- **`startsWith` bina `.some()` ke seedha array check** — `protectedRoutes.includes(pathname)` sirf exact match deta hai, children miss. `.some()` + `startsWith` = prefix match.
- **Public pages ko redirect list mein daalna** — `/about` protected bana diya toh visitors sab login pe pahunch jayenge. Protected = sirf jahan data user-specific hai.
- **Redirect ke baad `NextResponse.next()` return karna** — `return` early hai — redirect ke baad code ka next() kabhi reach na ho (saala logic order).

## Nutshell

`NextResponse.redirect(new URL("/login", request.url))` — browser naye URL pe jata hai (307 + Location). Redirect jis page pe ja raha ho use matcher se exclude karo (loop). `protectedRoutes` array + `.some()` + `startsWith` — prefix-based protection. `isProtected && !hasSession` — dono conditions. Demo — verified auth nahi (4.12).

**In Your Own Words**

1. `new URL("/login", request.url)` — dono arguments kya karte hain, aur base kyun zaroori?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Pehla argument path hai — kahan redirect karna hai (`/login`). Dusra base hai — request ka poora URL (`http://localhost:3000/dashboard?tab=settings`). URL class base ke domain pe path join karke absolute URL banata hai. Base zaroori hai kyunki redirect ko absolute URL chahiye — base se dev (`localhost:3000`) aur production (`myapp.com`) dono pe sahi domain milta hai — hardcoded `http://localhost:3000/login` production mein toot jaata.

</details>

2. Infinite loop kab hota hai — matcher ka `login` exclude ise kaise rokta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Jab proxy `/login` pe bhi chalta hai aur `!hasSession` check bhi — logged-out user `/login` pe aata hai, proxy use `/login` pe redirect karta hai, phir se proxy, phir se redirect... loop. Matcher mein `|login` likhne se `/login` wali requests proxy tak pahunchti hi nahi — isliye check kabhi chalta nahi, user login page pe rehta hai aur form bhar sakta hai. Rule: jis page pe redirect ho, use matcher se exclude.

</details>

3. `protectedRoutes.some((route) => pathname.startsWith(route))` kya kar raha hai — bina `.some()` ke kya problem?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `.some()` array ke har element pe callback chala ke batata hai "koi ek bhi true?" — yahan har route pe `startsWith` check — `/dashboard/settings` startsWith `/dashboard` → true. Bina `.some()` ke `includes("/dashboard")` exact match deta — `/dashboard/settings` pe false — children unprotected reh jaate. `.some()` + `startsWith` se ek entry se root + saare children cover.

</details>

4. `isProtected && !request.cookies.has("session")` — do conditions kyun, ek nahi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Sirf `!hasSession` hota toh public pages (`/about`) pe bhi redirect hota — kyunki session nahi hai matlab sab jagah redirect. Sirf `isProtected` hota toh session wale users bhi redirect hote — kyunki route protected hai par user logged in hai. Dono zaroori: route protected **aur** session missing — tabhi redirect. `/about` → isProtected false → 200. Logged-in user → hasSession true → 200.

</details>

5. Test matrix mein `/login` pe 404 kyun aata hai — kya yeh galat hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Scratch demo mein `/login` ka page banaya hi nahi tha — isliye 404. Important point yeh hai ki **redirect nahi hua** — matcher ne proxy ko `/login` se exclude kar diya tha, isliye check/redirect loop nahi chala. Real app mein `/login` page hota hai → 200 milega. Loop-safe hone ka proof: bina login pe `/login` pe kabhi redirect na aaye.

</details>
