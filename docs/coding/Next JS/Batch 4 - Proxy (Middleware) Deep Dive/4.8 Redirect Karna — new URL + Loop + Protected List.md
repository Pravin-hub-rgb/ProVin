# Redirecting — `new URL`, Loops, and Protected Lists (4.8)

## Where We Left Off

In 4.7 we learned the three response tools: `next()` (forward), `redirect()` (the browser navigates), and `rewrite()` (silent content swap). ## Step 1 — The Redirect Syntax

In 4.6 we logged the no-session case; now we redirect:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has("session")

  if (!hasSession) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|login).*)"],
}
```

**What changed:**

- `return NextResponse.redirect(...)` replaces the `console.log`. The `return` ends the function — the redirect response is sent immediately.
- `login` is added to the matcher's exclusion list (`|login` in the negative lookahead).

Let's understand the two new pieces — `new URL()` and the `login` exclusion.

---

## `new URL(path, base)` — Building the Target URL

```ts
new URL("/login", request.url)
```

`URL` is a **JavaScript built-in class** for constructing and parsing URLs. It takes two arguments:

1. `path` — where to redirect: `"/login"`
2. `base` — the base URL to resolve against: `request.url` (the full incoming URL)

**Why the base?** `NextResponse.redirect` needs an absolute URL (with origin). Passing only `"/login"` leaves the origin ambiguous. By giving `request.url` as the base — `http://localhost:3000/dashboard` in development — the URL constructor resolves `/login` against it, producing `http://localhost:3000/login`. Same code in production resolves against `https://myapp.com`, so the redirect is always correct for whatever environment it runs in.

The `new` keyword is because `URL` is a class — you are constructing an instance, not calling a plain function.

Then `NextResponse.redirect(url)` takes that URL object and produces a response with a `Location` header and a **307 status** — "browser, go to this URL."

---

## Infinite Loop — Exclude the Redirect Target

**Imagine what would happen if `login` were not excluded from the matcher:**

```
browser → /login
   ↓ (not excluded)
proxy runs, sees no session
   ↓
redirects back to /login
   ↓
proxy runs again, sees no session
   ↓
redirects back to /login
   ↓
...forever (or until the browser gives up)
```

**The security-guard analogy:** the guard at the building entrance says, "Go to reception to get your ID." But the **guard at reception says the same thing** — so you can never actually reach reception.

**The fix:** the guard should only be at the entrance, not at reception. In matcher terms: the redirect target must **not** enter the proxy at all. The `|login` entry means `/login` never runs through the proxy — so no redirect fires on `/login`, and the user lands on the login page safely:

```ts
matcher: ["/((?!_next/static|_next/image|favicon.ico|login).*)"]
```

> **Rule to remember:** the page you redirect **to** must be excluded from the matcher. This rule applies everywhere — all the redirect scenarios in 4.12 follow it.

## Step 2 — Redirect Only on Protected Routes

The example above redirects on **any** missing session — including `/about`, which should be public. Better: redirect only when the route is protected. Define a list and check it:

```ts
import { NextRequest, NextResponse } from "next/server"

const protectedRoutes = ["/dashboard", "/profile", "/settings"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const isProtected = protectedRoutes.some((route) =>
    pathname.startsWith(route)
  )

  if (isProtected && !request.cookies.has("session")) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}
```

New pieces:

- `protectedRoutes.some((route) => ...)` — `.some()` is an array method: it returns `true` if **any** element satisfies the predicate. The predicate here is `pathname.startsWith(route)`.
- `.startsWith(route)` does prefix matching, so `/dashboard/settings` matches the `/dashboard` entry — children are covered by one array slot.
- `isProtected && !request.cookies.has("session")` — redirect only when **both** are true: the route requires auth **and** the user lacks a session. Public routes like `/about` have `isProtected` false, so they pass through untouched.

---

## Step 3 — Sending Them Back Where They Came From

Better UX: when redirecting to `/login`, tell the login page where the user was trying to go, so they return there after signing in:

```ts
if (isProtected && !request.cookies.has("session")) {
  const loginUrl = new URL("/login", request.url)
  loginUrl.searchParams.set("callbackUrl", pathname)
  return NextResponse.redirect(loginUrl)
}
```

- `loginUrl` is a `URL` object (so we can mutate its query string).
- `searchParams.set("callbackUrl", pathname)` appends `?callbackUrl=/dashboard`. `searchParams.set` handles URL-encoding automatically.
- The browser lands on `/login?callbackUrl=/dashboard`, and the login page can read `callbackUrl` to send the user back to `/dashboard` after success.

---

## What It Is NOT

- **A redirect is the final auth decision.** This example checks only cookie **presence** — a spoofable demo (4.12 explains why verified auth lives elsewhere). The redirect itself is correct; the check behind it is not production-grade.
- **`startsWith` is not strict enough.** `"/dashboard"` also matches `/dashboardevil`. For learning that's fine; production wants boundary checks or exact-prefix-with-separator logic.
- **The `callbackUrl` is not secure by itself.** It is just a UX pointer — the server still validates the destination before honoring it.

## Common Mistakes

- **Forgetting to exclude redirect targets in the matcher.** `/login` included in the matcher while redirecting to `/login` creates an infinite loop.
- **Using `includes` instead of `.some()` + `startsWith`.** `protectedRoutes.includes(pathname)` is exact-match — `/dashboard/settings` fails. `.some()` with `startsWith` covers prefixes and children.
- **Redirecting on every missing session.** Public routes must pass through. Only redirect when the route is protected.
- **Forgetting `return` after redirect.** `return` is early — code after a redirect branch should not fall through to `next()`.

## Nutshell

`NextResponse.redirect(new URL("/login", request.url))` sends the browser to a new URL (307 + Location header). Exclude the redirect target from the matcher to prevent infinite loops. Protect a group with `protectedRoutes.some((route) => pathname.startsWith(route))` — prefix matching covers children. Redirect only when `isProtected && !hasSession`. Send the original path as `callbackUrl` so login can return the user.

**In Your Own Words**

1. Why does `new URL("/login", request.url)` take two arguments?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `NextResponse.redirect` needs an absolute URL with an origin. `"/login"` alone has no origin. The second argument, `request.url`, provides the base (`http://localhost:3000/dashboard` in development) so the constructor resolves `/login` against it — producing a correct absolute URL in any environment.

</details>

2. How does excluding `login` from the matcher prevent an infinite loop?

<details>
<summary>Show Answer</summary>

**Sample Answer:** If `/login` is in the matcher, the proxy runs on it, sees no session, and redirects back to `/login`, which runs the proxy again — forever. Excluding `login` means the proxy never runs on `/login`, so no redirect fires there, and the user lands on the login page.

</details>

3. What does `protectedRoutes.some((route) => pathname.startsWith(route))` do?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `.some()` returns `true` if any element satisfies the predicate. The predicate checks whether the current path starts with that route — so `/dashboard` matches `/dashboard`, and `/dashboard/settings` also matches `/dashboard`. One entry covers the root and all children.

</details>

4. Why require `isProtected && !hasSession` instead of just `!hasSession`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Just `!hasSession` redirects every unauthenticated request — including public pages like `/about` and `/login` itself. Requiring `isProtected` too means only routes that need auth get redirected. Public routes pass through with `next()`.

</details>

5. What role does `callbackUrl` play, and why is `searchParams.set` used for it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `callbackUrl` remembers where the user was going so the login page can send them back after signing in — better UX than a hardcoded landing page. `searchParams.set` adds it as a query parameter and handles URL-encoding automatically.

</details>

Redirects work and stay loop-free. Now the inverse: **rewrite** (4.9) — "same URL, different content." The proxy intercepts a request for one route and serves content from another without the browser noticing. The canonical uses are A/B testing and maintenance pages.
