In 4.10 we learned to read the request and build responses. Now we enter the **real scenarios** phase — where the proxy earns its keep in production. The simplest and most universally useful: **logging.** Every request recorded — what was requested, when, from where. The "logs = evidence" mindset arrives here, and the proxy is the perfect place for it because every request passes through.

---

## Why Logs — A Production Story

A user reports: "Last night at 11 PM our site broke, the dashboard showed wrong data." You check — nothing looks wrong, no errors.

**Without logs:** you have no proof. What happened, when, on which request? All unknown.

**With logs:** `"11:04 PM — GET /dashboard — IP: 49.36.x.x"` — a record of the request. Investigation starts there. **Logs = evidence.** That is why production systems log every request.

---

## Step 1 — Basic Logging: Method + Pathname

The proxy receives the full `request` — the most basic combination:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const method = request.method
  const pathname = request.nextUrl.pathname

  console.log(`${method} ${pathname}`)
  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
}
```

- `request.method` — the HTTP method — `GET`, `POST`, `DELETE`... (covered in Batch 3's API context, now in the proxy)
- `request.nextUrl.pathname` — from 4.4
- Template literal (`` `${method} ${pathname}` ``) — used in 4.10 too

**Terminal:**

```
GET /dashboard
GET /about
POST /api/comments
```

---

## Step 2 — Add a Timestamp

"When did it happen?" — a timestamp in the log is essential. `new Date().toISOString()` gives it:

```ts
export function proxy(request: NextRequest) {
  const method = request.method
  const pathname = request.nextUrl.pathname
  const time = new Date().toISOString()

  console.log(`[${time}] ${method} ${pathname}`)
  return NextResponse.next()
}
```

- `new Date()` — the current moment (a JS Date object)
- `.toISOString()` — the time as an ISO-format string — `2026-08-15T12:26:48.836Z` — **UTC** (the `Z` means UTC), sortable, and unambiguous — the standard log format. The `Z` suffix means UTC time, not local time.

---

## Step 3 — Add the IP

"From where?" — the IP from 4.5's `x-forwarded-for`:

```ts
export function proxy(request: NextRequest) {
  const method = request.method
  const pathname = request.nextUrl.pathname
  const ip = request.headers.get("x-forwarded-for") ?? "unknown"
  const time = new Date().toISOString()

  console.log(`[${time}] ${method} ${pathname} — IP: ${ip}`)
  return NextResponse.next()
}
```

**The final log line:**

```
[2026-08-15T12:26:48.836Z] GET /dashboard — IP: 49.36.10.5
```

When testing locally you might see IPs like `::ffff:127.0.0.1` — that is an IPv6-mapped IPv4 address; it is still just localhost.

---

## Bonus — Logging in Local Time

ISO UTC is machine-readable, but humans understand local time faster:

```ts
const localTime = new Date().toLocaleString("en-IN", {
  timeZone: "Asia/Kolkata",
  hour12: false,
})
```

```
15/08/2026, 17:56:48   ← IST local time
```

Helpful for development/debugging. Production logs mostly stay UTC (for consistent cross-region comparison) — both have their place.

## What It Is NOT

- **Logging is not a security check.** Logs are just records. 4.12 (protected routes) and 4.13 (rate limiting) hold the actual checks — logging is separate from deciding.
- **Logs do not live in the terminal forever.** Production logs go to log-management services (Vercel Logs, Datadog, Loki). `console.log` is just the interface — the destination is infrastructure.
- **`console.log` does not leak user data — but never log sensitive things anyway.** Passwords, tokens, secrets in logs become permanent records that get stored and can be breached.
- **Don't log every request blindly.** Static files must be excluded by the matcher (4.3) — otherwise CSS and image requests flood the logs.

## Common Mistakes

- **Forgetting the `${}` in template literals.** `console.log(method + " " + pathname)` works, but template literals are more readable — keep it consistent.
- **Logging IP without a fallback.** The `?? "unknown"` from 4.5 — without it, a missing header prints `null`.
- **Logging without the matcher.** Static files flood the logs — the negative matcher keeps it clean (4.3).
- **Logging sensitive data.** Never log request bodies, authorization headers, or tokens — logs are stored evidence.

## Nutshell

Logging produces: ``[${new Date().toISOString()}] ${request.method} ${request.nextUrl.pathname} — IP: ${ip ?? "unknown"}``. The proxy is the ideal logging point — every request passes through it. UTC ISO timestamps are the standard; local time is for readability. Remember: logs are records, not security controls — checks live in 4.12 and 4.13.

**In Your Own Words**

1. Why are logs called "evidence" — what is impossible without them?

<details>
<summary>Show Answer</summary>

**Sample Answer:** When a problem is reported ("the site broke last night at 11 PM"), without logs you have no proof — you cannot tell what happened, when, or on which request. Logs record each request (time, method, path, IP) — the investigation starts from the same timestamp the user reported. Logs are the only record of what the system did, so production debugging depends on them.

</details>

2. What does `new Date().toISOString()` produce — and why is it the standard for logs?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The current moment as an ISO-format string — `2026-08-15T12:26:48.836Z`. It is UTC (the `Z` suffix), precise to the millisecond. It is the standard because: (a) it is unambiguous — UTC is one time standard, no timezone confusion; (b) it is sortable — string order is chronological order; (c) it is machine-readable — log management tools parse it automatically. Local-time formatting (`toLocaleString`) is for human reading; ISO is the default.

</details>

3. In the final log line, where does each piece of data come from?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `time` = `new Date().toISOString()` (the current moment, UTC). `method` = `request.method` (the HTTP method — GET/POST). `pathname` = `request.nextUrl.pathname` (which route, from 4.4). `ip` = `request.headers.get("x-forwarded-for") ?? "unknown"` (which client, from 4.5). Everything comes from the proxy's `request` object — one place, a full record on every request.

</details>

4. Why is logging not the same as a security check — which files handle the actual checks?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Logging only records what happened — it does not stop anything. It does not block, redirect, or verify identity. The actual checks live elsewhere in the series: 4.12 handles protected routes and verified auth (the security decision), and 4.13 handles rate limiting (the throttling decision). Logs are the journal; checks are the guard.

</details>

5. Why should secrets never be logged — and why "logs are also stored files"?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Logs are written to files or cloud log services and retained indefinitely — they are not temporary terminal output. If you log a password, API token, or personal data, it persists in a stored record that could be exposed in a breach. Never log secrets — only safe metadata like method, path, IP, and status. The data inside a request body is not something to print.

</details>
