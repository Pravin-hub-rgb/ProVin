In 4.13 we rate-limited per IP — too many requests from one address means block. Now a geo-level scenario: **country blocking.** Some services are available only in certain countries (licensing, regional content, compliance). We need to derive the country from the IP — and the proxy has a **Vercel special header** that does exactly this automatically. We also pick up a new pattern: serving a **blocked page via rewrite** — the tool from 4.9, a new use case.

---

## The Problem — Country-Based Access

The service is available only in `IN`, `US`, and `GB`. A request from Russia arrives — what do you do?

- **Hard block** (403) — a bit rude; the user has no idea why it failed
- **Show a blocked page** — "this service is not available in your region" — a clean experience

Both patterns appear here.

---

## Step 1 — How to Know the Country: `x-vercel-ip-country`

In 4.13 we read the IP from `x-forwarded-for`. Now we need the IP's **country**. The manual approach is an IP-to-geo database lookup (MaxMind, etc.) — heavy setup.

**Vercel's shortcut:** once deployed on Vercel, a header appears automatically:

```
x-vercel-ip-country: IN
```

Vercel inspects the request IP, detects the country, and injects this header — inside the proxy you only read it:

```ts
const country = request.headers.get("x-vercel-ip-country")
```

The value follows **ISO 3166-1 alpha-2** — two-letter country codes: `IN` (India), `US`, `GB`, `RU`, `DE`...

> **Honest note:** this header does not appear in local dev. There you use a fallback like `?? "IN"` or a simulated value (see the test section). Production on Vercel gives you the real data.

---

## Step 2 — Allowlist and Block

```ts
import { NextRequest, NextResponse } from "next/server"

const ALLOWED_COUNTRIES = ["IN", "US", "GB"]

export function proxy(request: NextRequest) {
  const country = request.headers.get("x-vercel-ip-country") ?? "IN"

  if (!ALLOWED_COUNTRIES.includes(country)) {
    return new NextResponse("This service is not available in your region.", {
      status: 403,
    })
  }

  return NextResponse.next()
}
```

- `ALLOWED_COUNTRIES` — an **allowlist**. An allowlist is safer than a blocklist: a new, unknown country is blocked by default.
- `.includes(country)` — an array method — "is this value in the list?" (`.includes` is the exact-match version of the `startsWith` / `.some()` patterns from 4.13.)
- `!ALLOWED_COUNTRIES.includes(country)` — country not in the list → block.
- `new NextResponse("...", { status: 403 })` — the constructor from 4.13 — **403 = Forbidden**, telling the client access is denied.

**Test (simulated — set the header yourself):**

```bash
curl -H "X-Vercel-Ip-Country: IN" http://localhost:3000/    # 200 — allowed
curl -H "X-Vercel-Ip-Country: RU" http://localhost:3000/    # 403 — blocked
```

## Step 3 — Blocked Page (The Rewrite Version)

Instead of a raw 403, serve a proper blocked page — using **rewrite** from 4.9:

`app/blocked/page.tsx`:

```tsx
export default function Blocked() {
  return (
    <main>
      <h1>Blocked</h1>
      <p>This service is not available in your region.</p>
    </main>
  )
}
```

`proxy.ts`:

```ts
import { NextRequest, NextResponse } from "next/server"

const ALLOWED_COUNTRIES = ["IN", "US", "GB"]

export function proxy(request: NextRequest) {
  const country = request.headers.get("x-vercel-ip-country") ?? "IN"

  if (!ALLOWED_COUNTRIES.includes(country)) {
    return NextResponse.rewrite(new URL("/blocked", request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|blocked|.*\\.svg).*)"],
}
```

**What changed:**

- Instead of 403, we use `NextResponse.rewrite(new URL("/blocked", request.url))` — the rewrite from 4.9. The content is the blocked page, but the URL stays the user's original URL. A smooth experience: no matter which URL was opened, the blocked page is shown.
- **`blocked` is in the matcher exclusion list** — the loop rule from 4.9: the URL you rewrite to must be excluded. `blocked` never enters the proxy, so the blocked page does not block itself.

**The URL-consistency advantage:** with a redirect, the user would see `/blocked` in the URL bar and try navigating back to the original — confused. With rewrite, the blocked page appears on every URL, no confusion about where they are.

```
X-Vercel-Ip-Country: RU  → 200 (URL stays), content = Blocked page ✅
direct /blocked          → 200 — loop-safe ✅ (excluded by matcher)
```

(A note on status: a rewrite returns 200 — it is a content swap at the HTTP level. The raw 403 version is for API clients that need the status code; the rewrite version is for real users.)

## What It Is NOT

- **`x-vercel-ip-country` does not exist in local dev.** It only appears on Vercel deployments. That is why you test with a fallback (`?? "IN"`) and a simulated header in curl — there is no magic.
- **Geo blocking is not 100% precise.** IP geolocation is approximate — VPN or proxy users can mask their real country. For licensing and compliance, geo is one layer, not a guarantee.
- **Allowlist vs. blocklist.** An allowlist is safer: a new country is blocked by default. A blocklist leaves new countries open unless explicitly listed — easy to miss.
- **This is an infra check, not auth.** Geo restriction controls content access by region — it does not verify the user's identity (the layering lesson from 4.12).

## Common Mistakes

- **Confusing `includes` with `startsWith`.** `ALLOWED_COUNTRIES.includes(country)` is an exact match — `IN` is not `IND`. Country codes are standardized at two letters, so exact match is correct. `startsWith` would be wrong here.
- **Not excluding the rewrite target in the matcher.** `blocked` must be excluded — the loop rule from 4.9.
- **Expecting the real header in local dev.** It will not be there. Simulate it.
- **Forgetting the UX of a 403.** A raw text block is rude to a human visitor. Use the rewrite to a proper page.

## Nutshell

`x-vercel-ip-country` is Vercel's automatic country header (ISO 3166-1 alpha-2). `ALLOWED_COUNTRIES.includes(country)` — allowlist check; block → `new NextResponse("...", { status: 403 })` for APIs, or `rewrite(new URL("/blocked"))` for humans. Exclude the rewrite target (`blocked`) from the matcher. Local dev = simulate; production = real header. Geo blocking is an infra layer, not auth.

**In Your Own Words**

1. What is `x-vercel-ip-country` and why is it absent in local dev?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It is a header that Vercel injects automatically on deployment — Vercel reads the request IP, maps it to a country (ISO 3166-1 alpha-2 codes like `IN`, `US`, `GB`), and sets the header. In local development there is no Vercel infrastructure, so the header never appears. You handle this with a fallback (`?? "IN"` provides a default) and by simulating the header with curl (`-H "X-Vercel-Ip-Country: RU"`) — production has the real header; in dev you create it yourself.

</details>

2. Why is an allowlist safer than a blocklist — and what does `!ALLOWED_COUNTRIES.includes(country)` do?

<details>
<summary>Show Answer</summary>

**Sample Answer:** An allowlist permits only listed countries and blocks everything else by default — a new or unknown country is blocked automatically. A blocklist blocks only the listed countries and lets everything else through — a new country is allowed unless you remembered to add it. `!ALLOWED_COUNTRIES.includes(country)` returns true when the country is **not** in the list, so that request is blocked. `.includes` is an exact match — country codes are two-letter standard codes, so `"IN"` is matched exactly, never partially.

</details>

3. When do you use a 403 response vs. a blocked-page rewrite?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `new NextResponse("...", { status: 429 })` — a raw block — is for API clients that need a status code to react to programmatically (they branch on 403). Rewrite to `/blocked` — is for human visitors: it returns a proper page with a friendly message, and the URL does not change, so there is no confusion about where they are. The decision is about who is consuming the response: machines need codes, humans need pages.

</details>

4. Why must you exclude `/blocked` from the matcher when using rewrite — can a loop actually happen?

<details>
<summary>Show Answer</summary>

**Sample Answer:** If the proxy also runs on `/blocked`, then a user from a blocked country visiting `/blocked` triggers the rewrite to `/blocked`, which triggers the proxy again, which rewrites again — an infinite loop (the 4.9 rule, now for geo blocking). Excluding `blocked` from the matcher makes the proxy skip that URL entirely, so the rewrite happens exactly once with no loop. The rule: whatever URL you redirect or rewrite to, exclude it from the matcher.

</details>

5. Why is geo blocking not considered a full-proof security measure — and how do VPN users bypass it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** IP geolocation is approximate, not exact. A user can connect through a VPN or proxy server in a different country, and the server sees the VPN's IP — it looks like the allowed country. So geo blocking is not a strong security boundary; it is a compliance and content-access layer. It does not verify the user's identity either — that is a separate concern (the auth/security layering from 4.12). Geo is "block this region," not "verify this user."

</details>
