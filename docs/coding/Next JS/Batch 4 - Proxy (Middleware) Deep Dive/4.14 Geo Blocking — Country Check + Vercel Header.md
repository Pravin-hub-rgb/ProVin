4.13 mein per-IP limit lagayi — ek IP se zyada requests roknа. Ab ek aur geo-level scenario: **country blocking.** Kuch services sirf kuch countries mein available hain (licensing, regional content, compliance). Yahan IP se country nikalni hai — aur proxy mein **Vercel ka special header** kaam aata hai jo ise automatic bana deta hai. Aur ek naya pattern bhi milega: blocked page ke liye **rewrite** — 4.9 wala tool, naya use case.

---

## Problem — Country-Based Access

Service sirf IN, US, GB mein available hai. Russia se request aayi — kya karna?

- **Sirf block** (403) — thoda rude, user ko samajh nahi aata kya hua
- **Blocked page** dikhao — "yeh service aapke region mein available nahi" — clean experience

Dono patterns yahan milenge.

---

## Step 1 — Country Kaise Pata Chale: `x-vercel-ip-country`

4.13 mein IP ka `x-forwarded-for` padha tha — ab IP se **country** chahiye. Manual approach: IP → geolocation database lookup (MaxMind wagera) — heavy setup.

**Vercel ka shortcut:** Vercel pe deploy karne pe automatically ek header aata hai:

```
x-vercel-ip-country: IN
```

Vercel request ke IP se country detect karke yeh header daal deta hai — proxy mein bas read karna hai:

```ts
const country = request.headers.get("x-vercel-ip-country")
```

Value **ISO 3166-1 alpha-2** format — 2-letter country codes: `IN` (India), `US`, `GB`, `RU`, `DE`...

> **Honest note:** Local dev mein yeh header nahi hota — wahan `?? "IN"` jaisa fallback ya simulated value use karte hain (test section mein). Production mein Vercel ka real data.

---

## Step 2 — Allowed List + Block

```ts
import { NextRequest, NextResponse } from "next/server"

const ALLOWED_COUNTRIES = ["IN", "US", "GB"]

export function proxy(request: NextRequest) {
  const country = request.headers.get("x-vercel-ip-country") ?? "IN"

  if (!ALLOWED_COUNTRIES.includes(country)) {
    return new NextResponse("This service is not available in your region.", {
      status: 403,
    })
  }

  return NextResponse.next()
}
```

- `ALLOWED_COUNTRIES` — allowlist (blocklist ke bajaye allowlist safer hai — nayi country by default blocked)
- `.includes(country)` — array method — "yeh value list mein hai?" (4.13 mein `startsWith`/`.some()` dekhe — `.includes` exact match ka simple version)
- `!ALLOWED_COUNTRIES.includes(country)` — country allowed nahi → block
- `new NextResponse("...", { status: 403 })` — 4.13 wala constructor pattern — **403 = Forbidden** (user ko pata chale: access denied)

**Test (simulated — header khud daal ke):**

```bash
curl -H "X-Vercel-Ip-Country: IN" http://localhost:3000/    # 200 — allowed
curl -H "X-Vercel-Ip-Country: RU" http://localhost:3000/    # 403 — blocked
```

## Step 3 — Blocked Page (Rewrite Version)

403 raw text ke bajaye ek accha blocked page dikhao — **rewrite** se:

`app/blocked/page.tsx`:

```tsx
export default function Blocked() {
  return (
    <main>
      <h1>Blocked</h1>
      <p>This service is not available in your region.</p>
    </main>
  )
}
```

`proxy.ts`:

```ts
import { NextRequest, NextResponse } from "next/server"

const ALLOWED_COUNTRIES = ["IN", "US", "GB"]

export function proxy(request: NextRequest) {
  const country = request.headers.get("x-vercel-ip-country") ?? "IN"

  if (!ALLOWED_COUNTRIES.includes(country)) {
    return NextResponse.rewrite(new URL("/blocked", request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|blocked|.*\\.svg).*)"],
}
```

**Kya badla:**

- 403 ke bajaye `NextResponse.rewrite(new URL("/blocked", request.url))` — 4.9 wala rewrite — content blocked page ka, URL wahi. User ko smooth experience: jo bhi URL khola, blocked page dikha.
- **Matcher mein `blocked`** — 4.9 wala loop rule: jis URL pe rewrite ho use exclude. `blocked` pe proxy nahi chalta → block page khud block nahi hota.

**URL consistency ka fayda:** redirect use karte toh user `/blocked` URL dekh ke wapas original URL try karta... rewrite se hamesha blocked page, koi confusion nahi.

## Test Matrix

```
X-Vercel-Ip-Country: IN  → 200, normal page ✅
X-Vercel-Ip-Country: RU  → 200 (URL wahi), content = Blocked page ✅
/blocked direct          → 200 — loop-safe ✅ (matcher excluded)
```

(Status code note: rewrite pe 200 hi aata hai — HTTP level pe content swap hai, block nahi. 403 wala version raw-response use-cases ke liye, rewrite wala UX-wale ke liye.)

## What It Is NOT

- **`x-vercel-ip-country` local dev mein nahi milta** — sirf Vercel deployment pe. Isliye simulation (`?? "IN"` ya curl header) se test karte hain — honest, no magic.
- **Geo blocking = "100% precise" nahi** — IP geolocation approximate hai (VPN/proxy users bypass kar sakte hain). Licensing/compliance mein yeh ek layer hai, full-proof nahi.
- **Allowlist vs blocklist** — allowlist safer: nayi country default blocked. Blocklist me nayi country default allowed — miss ho sakta.
- **Yeh bhi proxy-infra kaam hai, auth nahi** — geo restriction content access ka hai, identity verify nahi karta (4.12 wala layering).

## Common Mistakes

- **`includes` vs `startsWith` confuse** — `ALLOWED_COUNTRIES.includes(country)` exact match (IN ≠ IND) — country codes 2-letter standard hain, exact match hi sahi. `startsWith` yahan galat.
- **Rewrite target matcher mein include** — `blocked` exclude karna (loop rule, 4.9).
- **Local mein real header expect karna** — dev mein header nahi aata — fallback/simulation se test.
- **403 raw response ke saath bhi UX sochna** — text block "rude" hai; blocked page (rewrite) user-friendly.

## Nutshell

`x-vercel-ip-country` — Vercel ka auto header (ISO 2-letter country). `ALLOWED_COUNTRIES.includes(country)` — allowlist check; block → `new NextResponse("...", { status: 403 })` ya `rewrite(new URL("/blocked"))`. Matcher mein blocked exclude. Local = simulate, production = real header. Geo = infra layer, auth nahi.

**In Your Own Words**

1. `x-vercel-ip-country` kya hai — local dev mein kyun nahi dikhta?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Vercel deployment pe automatic aane wala request header — Vercel IP se country detect karke daal deta hai (ISO 3166-1 alpha-2 — `IN`, `US`, `GB`). Local dev mein Vercel infra nahi hai — isliye header nahi hota. Isliye code mein `?? "IN"` fallback (default country) aur curl se simulated header (`-H "X-Vercel-Ip-Country: RU"`) — production mein real header, dev mein hum banate hain.

</details>

2. Allowlist blocklist se kyun better hai — `!ALLOWED_COUNTRIES.includes(country)` ka behavior?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Allowlist mein sirf listed countries allowed — nayi/unknown country by default blocked (safe default). Blocklist mein listed blocked, nayi country allowed — koi nayi country add karni ho toh blocklist update karna padta, miss ho sakta. `!ALLOWED_COUNTRIES.includes(country)` — country list mein nahi → block. `.includes` exact match hai — codes 2-letter standard, `IN` ≠ `IND`.

</details>

3. 403 response vs blocked-page rewrite — kab kaunsa?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `new NextResponse("...", { status: 403 })` — raw block — API clients ko chahiye (JSON/status codes — client code status pe react karega). Rewrite `/blocked` — UX wala — real users ko accha blocked page dikhta hai, URL wahi rehta hai (redirect se URL change hota — user confuse + wapas try karta). Rule: API/human-dono context dekho — humans ke liye page, clients ke liye status.

</details>

4. Rewrite use karne pe matcher mein `blocked` kyun — loop kaise banta?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Agar `/blocked` pe bhi proxy ka geo check chalta, toh blocked country ka user `/blocked` kholta → proxy usse wapas `/blocked` pe rewrite karta → phir se proxy → phir se rewrite — infinite loop (4.9 wala rule, har rewrite target ke liye). Matcher mein `|blocked` se woh URL proxy se excluded — rewrite ek baar, loop nahi. Jis URL pe rewrite/redirect ho, use hamesha matcher se exclude.

</details>

5. Geo blocking "full-proof" kyun nahi — VPN users ko kya hota?

<details>
<summary>Show Answer</summary>

**Sample Answer:** IP geolocation approximate hai — VPN/proxy users apna IP doosre country ka use karte hain — server unhe wahan ka country dikhata hai, block bypass ho jaata. Isliye geo blocking compliance/licensing ka ek layer hai (best effort), security ka strong rule nahi. Aur yeh auth nahi hai — sirf location check — identity/verified access alag layer (4.12 wala layering) se.

</details>
