In 4.7, a glimpse: `response.headers.set()` — modifying the response. Now we implement it in practice — and a power move: reading those same values inside a **Server Component using the `headers()` API.** This solves a problem that used to be impossible: **the layout can now know the current pathname.**

---

## What Are Response Headers

Request headers flow browser→server (the 4.5 ones). **Response headers** flow server→browser — the opposite direction. Just as requests have a label (headers), responses do too: status code, content-type, cache controls... and you can **add your own custom headers.**

The convention for custom headers is the `x-` prefix (like `x-hello`, `x-pathname`) — it signals "this is not a standard HTTP header, it is our custom one."

---

## Step 1 — Adding Custom Headers in the Proxy

Recall the pattern from 4.7 — **save the response first, then modify, then return it:**

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const response = NextResponse.next()
  response.headers.set("x-hello", "world")
  response.headers.set("x-pathname", request.nextUrl.pathname)
  return response
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
}
```

- `NextResponse.next()` is saved to a variable because we need to modify it (the point from 4.7).
- `response.headers.set("x-hello", "world")` — a static value.
- `response.headers.set("x-pathname", request.nextUrl.pathname)` — a **dynamic value** — each request's own pathname.

**Verify with curl:**

```bash
curl -D - http://localhost:3000/about | grep "x-"
```

```
x-hello: world
x-pathname: /about
```

Both headers appear in the response — the browser/client can see them.

---

## Step 2 — Reading in a Server Component: The `headers()` API

Now the question: **how do Server Components read these custom headers?** — use `headers()` from `next/headers`:

```tsx
// app/layout.tsx
import { headers } from "next/headers"

export default async function RootLayout({
  children,
}: Readonly<{ children: React.ReactNode }>) {
  const headersList = await headers()
  const pathname = headersList.get("x-pathname")

  return (
    <html lang="en">
      <body>
        <div>Current pathname: {pathname ?? "unknown"}</div>
        {children}
      </body>
    </html>
  )
}
```

**New pieces:**

- `import { headers } from "next/headers"` — the API for accessing request data inside Server Components and Route Handlers (the same family as `cookies()` from Batch 3).
- `await headers()` — an **async call** (the Next 15+ API — older tutorials show it without `await`). The layout itself becomes `async` too.
- `headersList.get("x-pathname")` — the familiar `.get()` pattern from 4.5 — returns the value or `null`.

**Test:** open `/about` → the layout shows "Current pathname: /about". Open `/dashboard` → shows `/dashboard`.

---

## Why This Is a Power Move — The Layout Learns the Pathname

Think about it: the layout renders on **every** page — but how does the layout know which page is rendering? `usePathname()` is a **client-side** hook (it does not run in a server layout), and `window.location` is browser-only (not available on the server). So how does the server-side layout learn the current route?

One option: each page passes its pathname as a prop — 10 pages, 10 repetitions. Tedious.

**The proxy way:** the proxy already knows the pathname (4.4) → it puts the value into a response header → the layout reads it with `headers()`. **One source, every page.** This is the pattern: whatever the proxy knows, push it into a header so any component can read it — without each component having to discover it themselves.

---

## `response.cookies.set()` — Bonus

The same pattern works for cookies on the response side — response cookies are **set** here, while 4.6 was about reading request cookies:

```ts
const response = NextResponse.next()
response.cookies.set("theme", "dark", {
  httpOnly: true,
  maxAge: 60 * 60 * 24 * 30,   // 30 days
  sameSite: "lax",
})
return response
```

`cookies.set` adds a `Set-Cookie` header to the response. The options (httpOnly, maxAge, sameSite) are the cookie attributes — the same ones covered when reading request cookies in 4.6. The context differs: in a Server Action or Route Handler you use `cookies().set` (that is where login lives in Batch 5); in the proxy you set cookies on every response, at the request level.

---

## What It Is NOT

- **`headers()` does not only read response headers.** Strictly, it reads request headers; but headers that the proxy set on the *response* are accessible in the same flow (Next.js passes them into the render context). The practical takeaway: **set in the proxy → read in the layout — it just works.** (Edge case: the framework may filter some headers — `x-` custom ones are safe.)
- **`headers()` does not run in client components.** It is a server-only API. If a client component needs the value, have the server pass it down.
- **Custom headers are visible to the browser.** `x-` headers are public (visible in DevTools). Never put secrets in them.
- **Calling `headers()` on every request forces dynamic rendering.** The layout will no longer be cached at the edge — it re-renders per request. Use this only when a dynamic per-request value is genuinely needed (like the pathname).

## Common Mistakes

- **Forgetting `await headers()`.** In Next 15+ it returns a Promise — without `await` you get a Promise object, not the list.
- **Forgetting to make the layout `async`.** If you `await` inside it, it has to be `async`.
- **Chaining on `NextResponse.next()` directly.** `return NextResponse.next().headers.set(...)` does not work — save to a variable, modify, then return.
- **Putting secrets in custom headers.** Headers are visible in the browser — API keys and tokens stay server-side (env vars).
- **Wrong import path.** `headers` comes from `next/headers`, not `next/server`.

## Nutshell

In the proxy: `response.headers.set("x-name", value)` adds a response header — static or dynamic. In a Server Component: `await headers()` then `.get("x-pathname")`. The pattern is: the proxy knows something (pathname) → puts it in a header → the component reads it. Bonus: `response.cookies.set(...)` works the same way, at the response-cookie level.

**In Your Own Words**

1. What direction do request headers and response headers flow — and what does the `x-` prefix signal?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Request headers flow browser→server (User-Agent, Cookie — from 4.5/4.6) and carry info about the incoming request. Response headers flow server→browser and carry status, content-type, and `Set-Cookie`. The `x-` prefix is a convention for custom headers — it signals "this is not a standard HTTP header, it's our own." Seeing `x-pathname`, you instantly know Next.js didn't set it — the proxy did.

</details>

2. In `response.headers.set("x-pathname", request.nextUrl.pathname)`, where does the dynamic value come from?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The proxy receives the `request` object, and `request.nextUrl.pathname` (from 4.4) gives each request its own path — `/about` for `/about`, `/dashboard` for `/dashboard`. A static value like `"world"` is the same for every request; a dynamic value like `pathname` differs per request. That is why one proxy can set the correct pathname header for every page.

</details>

3. How does the layout get the pathname from the proxy — and what had to be done without the proxy?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The proxy reads the pathname and puts it into a response header (`x-pathname`). The layout calls `await headers()` and reads `.get("x-pathname")`. Without the proxy, the layout cannot get the pathname: `usePathname()` is a client hook (the layout is a server component), and `window.location` only exists in the browser. The fallback is having each of the 10 pages pass its pathname as a prop — repetitive and error-prone. The proxy gives every component the value from one place.

</details>

4. Why is `await headers()` async — and why must the layout be async too?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In Next 15 and later, `headers()` returns a Promise rather than a plain object, so it must be awaited. And since `await` appears inside the layout, the layout itself must be declared `async`. The practical rule: `await headers()` + `async function RootLayout` go together. Do not compare against older tutorials that omitted `await`.

</details>

5. Why should secrets not be put in custom headers — and what does dynamic rendering cost?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Response headers travel to the browser and are visible in DevTools — anyone can read them. An API key or token placed in a custom header is exposed and exploitable, so secrets stay server-side (env vars). As for cost: reading `headers()` makes the page dynamic — it re-renders on every request instead of being cached at the edge. Use it only when a per-request value is genuinely needed (like the pathname).

</details>
