In 4.14 we geo-blocked by country — another production-shaped task in the proxy. Before that, a foundational question we have been side-stepping: **where does the proxy actually run?** At the start of this series we assumed it runs on "light things only." Let's now understand that environment properly: what the **Edge Runtime** is, how it related to middleware, and what changed in **Next.js 16** (yes — there is a surprise that contradicts older notes, and we verified it ourselves).

---

## The Edge Runtime — Concept

Imagine users around the world. The application server sits in one place (say, the US). An Indian user sends a request — it travels to the US server, and the response travels back. The longer the distance, the higher the **latency** — the time the user waits.

**Edge = compute nodes distributed around the world.** Cloud providers (Vercel, Cloudflare) place machines in many regions:

```
US user    → US edge node      → ~20ms
India user → Mumbai edge node  → ~20ms  (never crosses oceans)
```

An **edge runtime** is a lightweight JavaScript runtime that executes on those nodes. It processes the request close to the user, cutting latency. The tradeoff: because it is lightweight, **not every Node.js API is available** — some are deliberately left out.

---

## How Middleware Related to the Edge (Next ≤ 15)

**The old model (middleware.ts, through Next 15):** middleware ran on the **edge runtime by default.** That was its whole purpose — the proxy intercepts the request **before** the page renders, so if that check runs on a node near the user, the response is as fast as possible. That meant:

- Middleware got **global low latency** for free
- But it also got a **restricted API surface** — only what the edge environment exposes

That is why every pattern in this series so far (reading cookies and headers, redirects, rewrites, rate limiting) used edge-safe APIs. That is also why older tutorials say "you cannot use `fs` in middleware" and "bcrypt does not work" — those were edge restrictions.

**Node vs. Edge capability comparison (the old model):**

| | Node.js Runtime | Edge Runtime |
|---|---|---|
| Environment | A server machine | Distributed edge nodes |
| Node built-ins (`fs`, `path`, `crypto`...) | ✅ Full access | ❌ Restricted or unavailable |
| Databases (Prisma, etc.) | ✅ Full | ❌ Not supported |
| `bcrypt` (native crypto) | ✅ | ❌ (but `bcryptjs` works) |
| `fetch()` | ✅ | ✅ |
| NextResponse / request API | ✅ | ✅ |
| Latency (worldwide) | Server region → user | Edge node → user (near) |

This is why, in the old world, you had to choose edge-compatible libraries (`bcryptjs` instead of `bcrypt`, `jose` instead of `jsonwebtoken`) for anything the middleware needed.

---

## ⚠️ The Big Change in Next 16 — The Proxy Now Runs on Node.js

**Pay attention — this correction is important.** Up to now we assumed the edge restriction, because that is what older tutorials and earlier notes describe. But in Next 16, things changed. According to the official Next.js version history:

```
v16.0.0 — Middleware is deprecated and renamed to Proxy.
            Proxy defaults to the Node.js runtime
```

**The proxy (Next 16+) runs on the Node.js runtime by default — not the edge.**

We verified this from scratch in a Next 16.3 app:

1. Imported `fs` and called `readFileSync` inside the proxy — **it worked** (read a file and logged it). On the edge, this would have thrown.
2. Added `runtime: "edge"` to the config — **build error:**

```
Error: Next.js can't recognize the exported `config` field in route.
Proxy does not support Edge runtime.
```

So: the old advice that "the proxy runs on the edge, so `fs`/`bcrypt`/`Prisma` won't work" is **no longer true in Next 16** — the Node.js runtime means the built-in modules are available. The `runtime` export is now thrown away — remove it.

> **The edge runtime has not disappeared.** It still exists as a concept and a feature (edge functions and similar APIs use it). Only the **proxy's default runtime changed** — it now defaults to Node.js instead of Edge.

---

## What This Means Practically

**Before (Next ≤ 15):** the proxy ran on Edge = restricted APIs = "keep it light" was a hard technical constraint.

**Now (Next 16+):** the proxy runs on Node.js = full Node APIs (`fs`, `crypto`, etc.) are available. **There is no hard technical constraint anymore.**

But one rule **remains unchanged** — the "keep the proxy light" rule — and now it is about **performance and architecture**, not technical impossibility:

- The proxy runs on every request — heavy logic means every request is slow
- The proxy is the routing/infra layer — database queries and heavy computation belong elsewhere
- It is not a security boundary (the CVE/layering lesson from 4.12)

So in 4.16 we look at the real limitations that still apply, which old errors are now gone, and the "golden rules" for the final time — the rules that decide whether something belongs in the proxy at all.

---

## What It Is NOT

- **The edge runtime is not what the proxy runs on.** In Next 16 the proxy defaults to Node.js. The edge is still a concept (used by edge functions), but `runtime: "edge"` in the proxy config now throws.
- **"Edge-compatible" packages are no longer required for the proxy.** Node is available, so even native `bcrypt` would work. (That only applies to the proxy file — pages and actions run in a different context.)
- **"Now I can do everything in the proxy" is wrong.** `fs` technically works — but because the proxy runs on every request, heavy logic still slows every page. The light-weight rule is about performance and architecture, not just API availability.
- **The edge runtime is not useless.** The low-latency concept is still valuable, and Next.js still uses edge execution for other features — only the proxy's default switched.

## Common Mistakes

- **Copy-pasting `runtime: "edge"` from old middleware tutorials.** On Next 16 this causes a build error ("Proxy does not support Edge runtime") — delete the `runtime` key entirely.
- **"If `fs` works, the proxy can do file/database work."** Yes it works — but that does not make it a good idea. Every request pays the cost. Put data work in Server Components and actions.
- **Confusing the edge and Node runtimes as interchangeable.** They are different runtimes with different capabilities and different latency profiles. Know which one your code is using.
- **Following old tutorials blindly.** The rename from `middleware` to `proxy` came with a runtime change. Always check the version notes.

## Nutshell

The edge runtime is a lightweight JavaScript runtime on globally distributed nodes — low latency, but a restricted API surface. Middleware (through Next 15) ran on the edge by default, which is why older code limited itself to edge-safe APIs. **Next 16 renamed middleware to "proxy" and defaults it to the Node.js runtime** (verified: `fs` works, `runtime: "edge"` throws). The edge still exists for other features, but the proxy itself is now Node. The "keep it light" rule survives — now for performance and architecture reasons, not API restrictions.
