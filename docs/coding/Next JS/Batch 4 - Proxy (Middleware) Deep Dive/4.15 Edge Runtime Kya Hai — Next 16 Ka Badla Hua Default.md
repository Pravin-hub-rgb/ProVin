4.14 tak proxy ke saare practical kaam ho gaye — logging, routing, rate limit, geo. Ab ek fundamental sawaal: **proxy kis environment mein chalti hai?** Is series ki shuruaat mein humne assume kiya ki proxy light-cheezein hi kar sakti hai — ab ise properly samjhenge: **Edge Runtime** kya hai, middleware/proxy ka usse kya rishta tha, aur **Next.js 16 mein kya badal gaya** (ha — yahan ek surprise hai, jo tumhare purane notes ke against bhi hai — hum verify karke batayenge).

## Edge Runtime Kya Hai — Concept

Socho duniya bhar ke users. App ka server ek hi jagah hai (jaise US). India ka user request kare — request US server tak jaati hai, response wapas — **latency**: dori jitni lambi, utna zyada time.

**Edge = duniya bhar mein distributed compute nodes.** Cloud providers (Vercel/Cloudflare) ki machine har region mein hain:

```
US ka user  → US edge node      → 20ms
India user  → Mumbai edge node  → 20ms (koi US jaana nahi)
```

**Edge runtime** = un nodes pe chalta hua ek **lightweight JavaScript runtime** — request ko user ke paas wale node pe process karta hai — latency low, fast response. Iska tradeoff: Node.js ke saare APIs available nahi (lightweight hone ke liye unhe chhoda).

---

## Middleware Ka Edge Se Rishta (Next ≤ 15)

**Purana model (middleware.ts, Next 15 tak):** middleware **Edge runtime pe default** chalta tha — kyunki uska purpose hi request ko page render hone se **pehle** check karna hai — woh check user ke paas wale node pe ho toh response sabse fast. Isliye:

- Middleware ko **global low latency** milta tha
- Par **restricted API surface** — jo Edge mein hai wahi use kar sakte the

**Isliye Batch 4 ki series mein** abhi tak jo kiya (cookies/headers padhna, redirect, rewrite, rate-limit) — sab Edge-safe APIs the. Isliye purani tutorials mein milta hai: "middleware mein fs use nahi kar sakte", "bcrypt kaam nahi karta"...

**Node vs Edge — capability comparison (woh purana model):**

| | Node.js Runtime | Edge Runtime |
|---|---|---|
| Environment | Server machine | Distributed edge nodes |
| Node built-ins (fs, path, crypto...) | ✅ Full | ❌ Restricted |
| Databases (Prisma...) | ✅ Full | ❌ Nahi |
| bcrypt (native crypto) | ✅ | ❌ (bcryptjs chal sakta hai) |
| `fetch()` | ✅ | ✅ |
| NextResponse/request APIs | ✅ | ✅ |
| Latency (duniya bhar) | Server region se | User ke paas se |

Yahi wajah thi ki middleware ke liye "Edge-compatible" packages chunne padte the (bcryptjs vs bcrypt, jose vs jsonwebtoken).

## ⚠️ Next 16 Ka Bada Change — Proxy Ab Node.js Pe Chalti Hai

**Yahan dhyan do — kyunki yeh correction important hai:**

Next.js 16 mein `middleware.ts` → `proxy.ts` rename hua — **aur sath mein runtime bhi badal gaya.** Official Next.js docs ke version history ke according:

```
v16.0.0 — Middleware is deprecated and renamed to Proxy.
          Proxy defaults to the Node.js runtime
```

**Proxy (Next 16+) = Node.js runtime pe chalti hai, default.** Edge nahi.

Humne ise **scratch app (Next 16.3) mein verify** kiya:

1. `fs` import + `readFileSync` proxy mein — **chal gaya** (file read karke log kiya) — Edge pe yeh error deta
2. `runtime: "edge"` config mein lagao — **build error**:

```
Error: Next.js can't recognize the exported `config` field in route.
Proxy does not support Edge runtime.
```

Matlab: purani tutorials/tumhare pehle ke notes ka "proxy Edge pe chalti hai, isliye fs/bcrypt/Prisma nahi chalega" **Next 16 pe ab valid nahi** — Node runtime hone se built-ins available hain. `runtime` export ab **throw** karta hai — hata dena.

> **Edge runtime khud gayab nahi hua** — woh concept/feature ab bhi hai (Vercel functions, edge functions use kar sakte ho). Sirf **proxy ka default runtime badal gaya** — ab woh Node.js pe hai, Edge pe nahi.

## Toh Kya Badla Practically

**Pehle (≤15):** middleware = Edge pe = restricted APIs = "light hi rakhna hai" constraint.

**Ab (16+):** proxy = Node.js pe = full Node APIs (fs, crypto...) available. **Koi hard constraint nahi.**

Par ek cheez **unchanged** rehti hai — **"proxy light rakho" ka rule** — lekin ab woh **performance/architecture** ki wajah se hai, technical impossibility nahi:

- Proxy har request pe chalta hai — heavy logic = har request slow
- Proxy = routing/infra layer — database queries, heavy computation wahan nahi
- Security boundary nahi hai (4.12 wala CVE/layering)

Isliye aage 4.16 mein: kya **practical limitations** abhi bhi hain, kya ab work karta hai, aur "kya kabhi proxy mein nahi karna" wali golden rules.

---

## What It Is NOT

- **Edge runtime = proxy ka runtime (ab) nahi** — Next 16 mein proxy Node.js pe default hai. Edge concept alag feature hai (edge functions wagera). `runtime: "edge"` proxy mein throw.
- **"Edge-compatible" packages ka zaroorat nahi (proxy ke liye)** — ab Node available hai — bcrypt (native) bhi chalega. Par woh baat sirf proxy file ki hai — pages/actions alag context.
- **Proxy = "ab heavy sab kar sakta hai" nahi** — technically fs chalta hai, par har-request performance + architecture ka rule ab bhi: light rakho. Capability ≠ recommendation.
- **Edge runtime "useless" nahi** — concept valuable hai (latency), aur Next.js ke doosre features mein use hota hai — sirf proxy ka default ab Node hai.

## Common Mistakes

- **Purani middleware docs se `runtime: "edge"` copy karna** — Next 16 mein build error ("Proxy does not support Edge runtime") — `runtime` key hata do.
- **"Proxy edge pe hai isliye fs nahi chalega" sochna** — ab Node default hai — fs chalega (hamne verify kiya). Par phir bhi light rakhna.
- **Edge aur Node ko "ek hi cheez" samajhna** — do alag runtimes hain — capability table alag, latency behavior alag.
- **Purani tutorials blindly follow karna** — middleware→proxy rename ke saath runtime bhi badla — version check karna.

## Nutshell

Edge runtime = distributed nodes pe lightweight JS — user ke paas, low latency, restricted APIs. Middleware (≤15) Edge pe default tha. **Next 16: proxy = Node.js default** (verified: fs chalta hai, `runtime: "edge"` throw karta hai). Edge concept ab bhi hai — bas proxy ka default badla. "Light proxy" rule performance ki wajah se ab bhi.
