4.8 mein redirect se protected routes ka base bana tha. Ab use **complete** karte hain — poora login-flow pattern: cookie check, callbackUrl (login ke baad wapas wahi page), aur public-only routes (logged-in user `/login` pe na jaye). **Aur sabse zaroori:** is demo ke baad ek section hai — "why yeh proxy-auth **demo** hai, production mein nahi" — CVE-2025-29927 wali baat, jo isi section mein detail se samjhenge.

---

## Problem Demo — Phir Se

4.8 ke end tak humne protected routes banaye — par do cheezein missing hain:

1. User ko `/dashboard` se `/login` bheja — par login ke baad user **wapis wahi page** pe kahan jayega? (Ab `dashboard` pe wapas nahi jaata — default page pe!)
2. Logged-in user `/login` khole toh kya? — Login page dikhega — par woh already logged in hai!

Dono fix karte hain.

---

## Step 1 — Cookie Check (Log + Redirect)

4.6 wala check + 4.8 wala redirect — combine:

```ts
import { NextRequest, NextResponse } from "next/server"

const protectedRoutes = ["/dashboard", "/profile"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const hasSession = request.cookies.has("session")

  const isProtected = protectedRoutes.some((route) => pathname.startsWith(route))

  if (isProtected && !hasSession) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}
```

Abhi tak familiar — `.some()` + `startsWith` (4.8), cookie presence (4.6).

---

## Step 2 — CallbackUrl — Login Ke Baad Wapis Wahi Page

**Problem:** `/dashboard/settings` ka user `/login` pe gaya — login karke kahan jayega? Agar sabko `/` pe bheja toh user ka context khoya (usko phir se navigate karna padega). Best UX: login ke baad **wahi page** jahan se aaya tha.

**Solution:** `/login` ko bata do ki wapas kahan jana hai — URL ke query mein:

```ts
if (isProtected && !hasSession) {
  const loginUrl = new URL("/login", request.url)
  loginUrl.searchParams.set("callbackUrl", pathname)
  return NextResponse.redirect(loginUrl)
}
```

- `loginUrl` — URL object (4.8 wala `new URL` pattern)
- `loginUrl.searchParams.set("callbackUrl", pathname)` — 4.4 wala searchParams — ab **set** karte hain (get padhna aata tha) — URL mein query add: `?callbackUrl=/dashboard/settings`

**Result redirect:**

```
/login?callbackUrl=%2Fdashboard%2Fsettings
```

(`%2F` = URL-encoded `/` — URL safe format. Browser URL bar mein `/login?callbackUrl=/dashboard/settings` dikhega.)

**Ab login page ka kaam:** login success ke baad `callbackUrl` padh ke usi page pe redirect karna. (Woh hissa auth library ka kaam hai — Auth.js mein callbackUrl automatically handle hota hai — iska detail aage Batch 5 mein aayega.)

---

## Step 3 — Public-Only Routes — Logged-In User /login Pe Na Jaye

**Problem:** logged-in user `/login` khole — login form dikhega? Woh already logged in hai — bekar + confusing. Rule: **public-only routes (login, signup) pe logged-in user ko wapas bhej do:**

```ts
const protectedRoutes = ["/dashboard", "/profile"]
const publicOnlyRoutes = ["/login"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const hasSession = request.cookies.has("session")

  const isProtected = protectedRoutes.some((route) => pathname.startsWith(route))
  const isPublicOnly = publicOnlyRoutes.some((route) => pathname.startsWith(route))

  if (isProtected && !hasSession) {
    const loginUrl = new URL("/login", request.url)
    loginUrl.searchParams.set("callbackUrl", pathname)
    return NextResponse.redirect(loginUrl)
  }

  if (isPublicOnly && hasSession) {
    return NextResponse.redirect(new URL("/dashboard", request.url))
  }

  return NextResponse.next()
}
```

**Naya piece:** `isPublicOnly && hasSession` — login route pe + session hai → `/dashboard` pe redirect. Wohi `.some()` + `startsWith` pattern, alag list.

---

## Matcher — Loop Ka Naya Analysis

4.8 mein kaha tha: "jis URL pe redirect ho use matcher se exclude" — aur abhi matcher mein `login` exclude hai. **Ruko — Step 3 ke saath yeh matcher galat hai:**

```
/login WITH cookie → proxy chala hi nahi (matcher exclude) → publicOnly redirect kabhi nahi chala
```

**Ise samjho:** loop tab hota hai jab redirect **unconditional** hai (4.8: `!hasSession` → hamesha `/login`). Step 3 ke baad `/login` ka behavior **defined** hai:

- Logged-out `/login` → `isProtected` false, `isPublicOnly && hasSession` false → `next()` → login page render — **koi loop nahi**
- Logged-in `/login` → publicOnly redirect → `/dashboard` — ek baar, `/dashboard` pe proxy phir normal

Toh ab `login` ko matcher se **hata sakte ho** — conditions loop ko naturally rok deti hain:

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"],
}
```

**Yahi sikhne wali cheez hai:** exclusion sirf unconditional redirects ke liye zaroori hai. Jahan har case ka defined output hai — loop nahi hota, matcher ko tight list karne ki zaroorat nahi.

## ⚠️ Why Not — Proxy Authentication = Demo, Production Mein Nahi

Ab woh baat jo 4.8 ke redirect se shuru hui thi — yahan pura logic:

**1. Cookie-presence check spoofable hai.**

```ts
request.cookies.has("session")
```

Ye sirf check karta hai ki `session` **naam ki** cookie hai ya nahi. Koi bhi browser mein DevTools khol ke manually cookie set kar sakta hai:

```
F12 → Application → Cookies → Name: session, Value: anything → refresh
```

`hasSession` → `true`. Proxy ne redirect nahi kiya — **user "logged in" ban gaya — koi verification nahi hui** ki yeh cookie hamari app ne banayi thi. (Aage Batch 5 mein manual session banaenge — wahan `getSession()` cookie ke value ko `users.json` se verify karta hai. Ye demo woh verification nahi karta.)

**2. CVE-2025-29927 — Proxy bypass ho sakti hai.**

2025 mein Next.js middleware/proxy mein ek vulnerability mili — attacker ek **special header** bhej kar proxy ko skip kar sakta hai. Matlab: har request proxy se bahar nikal sakti hai — proxy mein rakhi auth check bypass. Next.js ne ise patch kiya, par **lesson permanent hai:** proxy ko security ka main layer mat banao — kyunki woh ek optimization/infra layer hai, gurantee nahi.

Code se samjho — CVE se pehle ka vulnerable pattern (jo tutorials mein chalta tha):

```tsx
// OLD: app/dashboard/layout.tsx — KHAALI, sirf children wrap
export default function DashboardLayout({ children }) {
  return <>{children}</>;
}
```

```ts
// OLD: app/middleware.ts — protection SIRF yahan
export function middleware(request: NextRequest) {
  const isLoggedIn = request.cookies.has("session");
  if (request.nextUrl.pathname.startsWith("/dashboard") && !isLoggedIn) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
}
```

Attack — Next.js ke "subrequest" system ko fool karta hua header:

```bash
curl -H "x-middleware-subrequest: middleware" http://localhost:3000/dashboard
```

Next ko lagta hai "middleware already chala" → **middleware skip** → layout khaali hai, check kuch nahi → page bina login khul gaya. Isliye fix: **check layout mein** — kyunki layout page render ka hissa hai (skip impossible), proxy saamne ka filter hai (skip ho sakta hai). (Iska deep-dive Batch 5 mein jab asli auth system banayenge.)

**3. Verified auth components mein hai — wahi security hai.**

Yahi production pattern Batch 5 mein aayega: `(protected)/layout.tsx` mein `auth()` + `redirect` — wahan session **verify** hota hai (Auth.js signature check). Proxy sirf routing (logged-in /login → /dashboard). Layer-wise:

```
Proxy (routing/infra — bypass-able)     → skip nahi karna chahiye, par ho sakta hai
Layout/Server Component (auth() verify) → asli security
```

**Toh yeh demo kyun sikhaya?** Kyunki proxy mein checks likhna aata hona chahiye (kuch checks proxy ke liye sahi hain — 4.13 rate limiting, 4.14 geo) — aur "cookie check = login" ka mental model correct hai infra level pe. Par production app mein auth = `auth()` + layout. **Demo as demo, production pattern Batch 5 mein.**

---

## What It Is NOT

- **callbackUrl = login security nahi** — sirf UX hai (login ke baad wapas bhejna). Verification still needed.
- **publicOnly = "logout" nahi** — logged-in user ko `/login` se hataata hai, session khatam nahi karta.
- **Proxy protected routes = production auth nahi** — demo (spoofable + CVE). Production = layout `auth()`.
- **`protectedRoutes` list = Route Group nahi** — yeh sirf JS array hai; (protected) group folder-level hai (Batch 5 mein aayega), yeh check-level.

## Common Mistakes

- **Matcher mein `login` exclude karna Step 3 ke baad bhi** — publicOnly redirect kabhi fire nahi hoga (test matrix mein dikha). Conditions defined hon toh matcher exclusion nahi chahiye.
- **callbackUrl bina URL-encode** — `searchParams.set` khud encode karta hai — manual `?callbackUrl=` + raw path mat banाओ.
- **Cookie check ko verified session samajhna** — production mein yahi sabse bada mistake (why-not section).
- **Proxy mein heavy auth logic** — demo level okay, production auth layout mein (verify) + proxy mein nahi.

## Nutshell

Full demo: `protectedRoutes` + cookie check → redirect with callbackUrl; `publicOnlyRoutes` + session → dashboard redirect. Matcher exclusion sirf unconditional redirects ke liye (defined behaviors loop nahi banate). **Demo hai** — cookie-presence spoofable, CVE-2025-29927 proxy bypass karta hai — production auth = layout `auth()` (Batch 5 mein), proxy sirf routing/infra.
