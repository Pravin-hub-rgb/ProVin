## Problem Recap

By the end of 4.8, protected routes existed — but two things were missing:

1. A user hitting `/dashboard` gets redirected to `/login` — but after logging in, where do they go back to? (Not back to `dashboard` — the default page!)
2. A logged-in user opens `/login` — the login form shows, but they're already logged in!

Both get fixed here.

---

## Step 1 — Cookie Check (Log In + Redirect)

Combining the 4.6 check and the 4.8 redirect:

```ts
import { NextRequest, NextResponse } from "next/server"

const protectedRoutes = ["/dashboard", "/profile"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const hasSession = request.cookies.has("session")

  const isProtected = protectedRoutes.some((route) => pathname.startsWith(route))

  if (isProtected && !hasSession) {
    return NextResponse.redirect(new URL("/login", request.url))
  }

  return NextResponse.next()
}
```

Familiar so far — the `.some()` + `startsWith` from 4.8, the cookie presence from 4.6.

---

## Step 2 — CallbackUrl — Sending the User Back to Where They Were

**Problem:** The user was on `/dashboard/settings` but gets sent to `/login`. After logging in, they get sent... somewhere generic? If everyone lands on `/`, the user's context is lost (they have to navigate back manually). Best UX: after login, send them **back to the page they were trying to reach.**

**Solution:** Tell `/login` where to send them back — via a query param:

```ts
if (isProtected && !hasSession) {
  const loginUrl = new URL("/login", request.url)
  loginUrl.searchParams.set("callbackUrl", pathname)
  return NextResponse.redirect(loginUrl)
}
```

- **`loginUrl`** — a `URL` object (the 4.8 `new URL` pattern).
- **`loginUrl.searchParams.set("callbackUrl", pathname)`** — writing to `searchParams`, the 4.4 pattern (you read with `.get()`); adds a query: `?callbackUrl=/dashboard/settings`.

The redirect result:

```
/login?callbackUrl=%2Fdashboard%2Fsettings
```

(`%2F` is the URL-encoded `/` — safe URL format. The browser's address bar shows `/login?callbackUrl=/dashboard/settings`.)

**Now the login page's job:** after a successful sign-in, read `callbackUrl` and redirect there. (That's auth-library territory — Auth.js handles `callbackUrl` automatically; the details come in Batch 5.)

---

## Step 3 — Public-Only Routes — Don't Send Logged-In Users to Login

**Problem:** A logged-in user opens `/login` — the login form shows? They're already logged in. Wasteful and confusing. Rule: **public-only routes (login, signup) should bounce logged-in users back.**

```ts
const protectedRoutes = ["/dashboard", "/profile"]
const publicOnlyRoutes = ["/login"]

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname
  const hasSession = request.cookies.has("session")

  const isProtected = protectedRoutes.some((route) => pathname.startsWith(route))
  const isPublicOnly = publicOnlyRoutes.some((route) => pathname.startsWith(route))

  if (isProtected && !hasSession) {
    const loginUrl = new URL("/login", request.url)
    loginUrl.searchParams.set("callbackUrl", pathname)
    return NextResponse.redirect(loginUrl)
  }

  if (isPublicOnly && hasSession) {
    return NextResponse.redirect(new URL("/dashboard", request.url))
  }

  return NextResponse.next()
}
```

**The new piece:** `isPublicOnly && hasSession` — the `/login` path, and there's a session → redirect to `/dashboard`. The same `.some()` + `startsWith` pattern, just a second list.

---

## Matcher — A Loop Analysis

In 4.8 it was said: "exclude the redirect destination from the matcher." And `login` was excluded. But **wait — Step 3 makes this matcher wrong:**

```
/login WITH cookie → proxy never runs (matcher excludes it) → publicOnly redirect never fires
```

**Why this loop exists:** redirects cause loops when they're unconditional (4.8: `!hasSession` → always `/login`). After Step 3, `/login`'s behavior is **defined**:

- Logged-out `/login` → `isProtected` is false, `isPublicOnly && hasSession` is false → `next()` → the login page renders — **no loop.**
- Logged-in `/login` → publicOnly redirect → `/dashboard` — once. `/dashboard` then runs the proxy normally.

So now `login` can be **removed from the matcher** — the conditions stop loops naturally:

```ts
export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"],
}
```

**The lesson:** matcher exclusions are only needed for *unconditional* redirects. Where every case has a defined output, no loop forms and you don't need a tight matcher.

## ⚠️ Why Not — Proxy Authentication Is a Demo, Not Production

This is the thread that started in 4.8's redirect. The full logic:

**1. The cookie-presence check is spoofable.**

```ts
request.cookies.has("session")
```

This only checks whether a cookie **named** `session` exists — it never validates the cookie's *content*. Anyone can open DevTools and manually create one:

```
F12 → Application → Cookies → Name: session, Value: anything → refresh
```

`hasSession` becomes `true`. No redirect happens — the user is "logged in" with zero verification that the app actually issued this cookie. (Batch 5 builds a real session store — there, `getSession()` verifies the cookie value against `users.json`. This demo does no such verification.)

**2. CVE-2025-29927 — the proxy can be bypassed.**

In 2025, a vulnerability was found in Next.js middleware/proxy — an attacker sends a **special header** to make the proxy skip itself. Meaning: every request can exit before the auth check runs. Next.js patched it, but the lesson is permanent: don't make the proxy your *main* security layer — it's an optimization/infra layer, not a guarantee.

The vulnerable pattern (common in tutorials before the fix):

```tsx
// OLD: app/dashboard/layout.tsx — EMPTY, just wraps children
export default function DashboardLayout({ children }) {
  return <>{children}</>;
}
```

```ts
// OLD: app/middleware.ts — protection lives ONLY here
export function middleware(request: NextRequest) {
  const isLoggedIn = request.cookies.has("session");
  if (request.nextUrl.pathname.startsWith("/dashboard") && !isLoggedIn) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
}
```

The attack — fooling Next.js's "subrequest" system with a forged header:

```bash
curl -H "x-middleware-subrequest: middleware" http://localhost:3000/dashboard
```

Next.js thinks "middleware already ran" → **middleware skipped** → the layout is empty, no check → the page opens without login. The fix: **put the check in the layout** — because the layout is part of the page render (unskippable), while the proxy is a front filter (skippable). (The deep-dive on real auth is in Batch 5.)

**3. Verified auth components are where real security lives.**

This is the production pattern that arrives in Batch 5: a `(protected)/layout.tsx` that calls `auth()` + `redirect` — there, the session is **verified** (Auth.js signature check). The proxy only does routing (logged-in user hits `/login` → redirect to `/dashboard`). Layered:

```
Proxy (routing/infra — bypassable)     → don't rely on it; it can be skipped
Layout / Server Component (auth())     → real security
```

**So why teach this demo?** Because writing checks in the proxy is a skill you need — some checks belong in the proxy (4.13 rate limiting, 4.14 geo-blocking) — and modeling "cookie presence = logged in" is correct at the infrastructure level. But in a production app, auth = `auth()` + layout, not a cookie check. **Learn the demo as a demo; adopt the production pattern in Batch 5.**

---

## What It Is NOT

- **`callbackUrl` is not "login security"** — it's pure UX (send the user back where they came from). It doesn't verify identity at all.
- **`publicOnly` is not "logout"** — it bounces a logged-in user off `/login`; it doesn't destroy the session.
- **Proxy-protected routes are not "production auth"** — demo only (spoofable + CVE-bypassable). Production auth lives in the layout via `auth()`.
- **The `protectedRoutes` list is not "Route Groups"** — it's a plain JS array. The `(protected)` folder-level group arrives in Batch 5; this is a check, not a structure.

## Common Mistakes

- **Keeping `login` excluded in the matcher after Step 3** — the publicOnly redirect will never fire (the test matrix shows it). Once behaviors are defined, matcher exclusions are unnecessary.
- **Manually building `callbackUrl` URLs** — `searchParams.set` already encodes the value. Don't hand-roll `?callbackUrl=` + raw path.
- **Treating a cookie-presence check as verified auth** — the single biggest production mistake (see the Why-Not section).
- **Putting heavy auth logic in the proxy** — fine for a demo, wrong for production. Auth verifies in the layout; the proxy does routing.

## Nutshell

Full demo: `protectedRoutes` + cookie presence → redirect with `callbackUrl`; `publicOnlyRoutes` + session → redirect to `/dashboard`. Matcher exclusions matter only for unconditional redirects — once behaviors are defined, loops stop naturally. **This is a demo:** the cookie-presence check is spoofable, and CVE-2025-29927 shows the proxy can be bypassed — true auth happens in the layout via `auth()` (Batch 5), with the proxy doing only routing/infra.
