In 4.8 we implemented redirects in practice — the URL changed and the browser was sent to `/login`. Now another tool: **`rewrite()`** — where the URL **does not change** and only the content swaps. At first this seems odd ("change content but keep the URL — why?"), but two real use-cases arrive today: **A/B testing** and **maintenance pages**. In 4.7 we saw the rewrite overview — now in actual code.

---

## Rewrite — 30-Second Recap

```ts
NextResponse.rewrite(new URL("/home-v2", request.url))
```

The browser requests `/home` → the proxy serves `/home-v2`'s content → the browser sees **the same `/home` URL** with `/home-v2`'s content. The browser has no idea it pulled content from elsewhere.

**Redirect vs rewrite in one sentence:** redirect tells the browser to load a new URL (the URL changes); rewrite silently swaps content server-side (the URL stays the same).

---

## Step 1 — A/B Testing (Practical Use Case)

**Scenario:** the home page has two versions — `/home` (old) and `/home-v2` (new design). Show the new one to 50% of users, the old one to the remaining 50% — for testing.

Create two pages:

`app/home/page.tsx`:

```tsx
export default function Home() {
  return <h1>Home (V1 — old design)</h1>
}
```

`app/home-v2/page.tsx`:

```tsx
export default function HomeV2() {
  return <h1>Home V2 (new design)</h1>
}
```

Now the 50/50 split in the proxy:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  const pathname = request.nextUrl.pathname

  if (pathname === "/home") {
    const showV2 = Math.random() < 0.5
    if (showV2) {
      return NextResponse.rewrite(new URL("/home-v2", request.url))
    }
  }

  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
}
```

- `Math.random() < 0.5` — 50% chance of true (Math.random generates a random number between 0 and 1).
- `showV2 === true` → rewrite to `/home-v2` — new content, URL stays `/home`.
- `showV2 === false` → `next()` — the old `/home` renders.

**Test:** refresh `/home` repeatedly — sometimes "Home (V1)", sometimes "Home V2" — the URL bar always shows `/home`.

> **This is the point of rewrite:** if you used redirect, the browser URL bar would show `/home-v2` — the user knows a new version loaded, and analytics get biased. With rewrite the URL stays consistent — the test is clean.

## Step 2 — Maintenance Page (Another Use Case)

**Scenario:** the site is under maintenance — route every request to a maintenance page. Using redirect would change the URL to `/maintenance`, and when the user refreshes, they land back on the original URL and fail again. With rewrite, every URL shows the maintenance content while keeping its own URL.

`app/maintenance/page.tsx`:

```tsx
export default function Maintenance() {
  return (
    <main>
      <h1>Site Under Maintenance</h1>
      <p>Come back tomorrow — we're working on it.</p>
    </main>
  )
}
```

`proxy.ts` (temporary — remove when maintenance is done):

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  return NextResponse.rewrite(new URL("/maintenance", request.url))
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|maintenance).*)"],
}
```

**Why is `maintenance` excluded from the matcher?** — the rule from 4.8 also applies to rewrite: a rewrite **can create the same loop** as a redirect — rewriting `/maintenance` to `/maintenance` means the maintenance page itself gets rewritten... Again, **exclude** the URL you are rewriting to.

**Test:** open any URL — `/`, `/about`, `/dashboard` — all show the maintenance page, each keeping its own URL.

## Rewrite vs Redirect — Final Comparison

Both are now practical — here is the comparison table:

| | Redirect | Rewrite |
|---|---|---|
| URL | **Changes** | Stays the same |
| Does the browser know? | Yes (new page loads) | No (content swapped silently) |
| Status code | 307 | 200 (normal) |
| When to use? | Login flow, route moved | A/B testing, maintenance, content swap |
| Loop risk | Exclude target in matcher | **Same rule** |

---

## What It Is NOT

- **Rewrite is not a "hijack."** There is no malicious intent — it has legitimate uses (A/B testing, maintenance). The URL staying the same is the advantage — a consistent user experience.
- **Rewrite is not only for pages.** It works on any route. (Geo blocking in 4.14 also uses it.)
- **Rewrite is not the same as `next.config` `redirects()`.** That is config-level and works at build/request time differently; the proxy rewrite works at request time with conditions from your logic. Out of scope here — mentioning just in case.
- **`Math.random()` A/B is not production-ready.** Real A/B testing needs deterministic assignment (give each user a consistent version — via cookies or feature flags). Random is fine for learning; it just demonstrates the concept.

## Common Mistakes

- **Forgetting to exclude the rewrite target from the matcher.** A `/maintenance` rewrite on `/maintenance` creates a loop (the rule from 4.8, applicable to rewrite too).
- **Using rewrite where redirect is needed.** Login flows require the URL to change — the user must see `/login` — so rewrite is wrong there.
- **Letting code continue after rewrite.** The `return` happens before — `next()` becomes unreachable (the same return pattern from 4.8).
- **Forgetting the `next()` fallback in the A/B split.** If `showV2` is false and nothing is returned → hang. Every branch must return.

## Nutshell

`NextResponse.rewrite(new URL("/target", request.url))` — URL stays the same, content comes from the target route. A/B testing (50/50 split) and maintenance pages (rewrite everywhere) are two solid use cases. Rule: exclude the rewrite target from the matcher (to avoid loops). Redirect = change the URL; rewrite = change the content.

**In Your Own Words**

1. In a rewrite, the URL does not change — why is this important for A/B testing?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Rewrite is a server-side content swap — the browser does not know the content came from `/home-v2`. For A/B testing this matters: if you used redirect, the browser URL bar would show `/home-v2` — the user knows a new version loaded, which biases their behavior and feedback, and contaminates analytics data. With rewrite, the URL always stays `/home` — the user has a consistent experience and the test data is clean.

</details>

2. Why is rewrite better than redirect for a maintenance page?

<details>
<summary>Show Answer</summary>

**Sample Answer:** With redirect, the browser goes to `/maintenance` — the URL changes. When the user manually re-types the original URL later, they get redirected again — and if the redirect is not removed, old URLs keep breaking even after maintenance is over. With rewrite, every URL shows the maintenance content while keeping its own URL — the user feels the site is still "in the same place," just under maintenance. It is cleaner, and you toggle it from one place (the proxy) and remove it when done.

</details>

3. Why must you exclude the rewrite target (`|maintenance`) from the matcher — can a loop actually happen?

<details>
<summary>Show Answer</summary>

**Sample Answer:** If the proxy also runs on `/maintenance`, then the request for `/maintenance` gets rewritten to `/maintenance` — which runs the proxy again — which rewrites again — an infinite loop (the same rule from 4.8, now with rewrite). Excluding the target from the matcher means the proxy never runs on that URL, so the rewrite happens exactly once with no loop. The rule: whatever URL you redirect or rewrite to, always exclude it.

</details>

4. Redirect vs rewrite — give two decision rules for when to use which.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Rule 1 — if the user needs to **see the URL change**, use redirect. Example: login flow (`/dashboard` → `/login`, the user must know they are on the login page) — redirect. Rule 2 — if you want to **silently swap content** and keep the URL the same, use rewrite. Example: A/B testing or maintenance pages — the URL stays consistent. General hint: URL changes are visible to the user → redirect; content changes are invisible → rewrite.

</details>

5. Why isn't the `Math.random() < 0.5` A/B split production-ready — what is better?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Random splitting decides on every request — the same user might see V1 on one refresh and V2 on the next, creating an inconsistent experience and biased analytics (you cannot tell if the user's behavior was due to design or just randomness). Production A/B testing uses deterministic assignment — each user gets a consistent version, stored in a cookie or feature flag, and the traffic split is controlled and trackable. Random is just a concept demo — real A/B tests need consistency.

</details>
