In 4.15 we learned the big Next 16 change: the proxy now runs on Node.js, not the edge. That means the old "edge failures" (fs, Prisma, bcrypt) are technically unblocked. **Now the question is: which of those do we still avoid, and which new limitations remain?** Plus the golden rules — the final list every production decision should be measured against.

---

## Old Edge Failures (Next ≤ 15) — What Happened to Them?

**Back when middleware ran on the edge, these all threw errors:**

**1. `fs` — the file system**

```ts
import { readFileSync } from "fs"   // ❌ Edge: "Module not found: Can't resolve 'fs'"
                                    // ❌ Edge: "Edge Runtime does not support Node.js built-in modules"
```

**Now (proxy.ts + Node.js default):** ✅ **It works.** We verified in Next 16.3 — reading a file with `readFileSync` and logging it succeeded. (Technically you could even layer file-persistence onto the 4.13 in-memory counting pattern — though there is no reason to; the concept is what matters.)

**2. Prisma / databases**

```ts
import { PrismaClient } from "@prisma/client"   // ❌ Edge: "PrismaClient is unable to run in this environment..."
```

**Now:** technically you *can* run a database query inside the proxy (Node runtime). **But you should not** (see the golden rule below). Database work belongs in Server Components and actions.

**3. `bcrypt` (native) vs `bcryptjs`**

```ts
import bcrypt from "bcrypt"   // ❌ Edge: "Edge runtime does not support Node.js 'crypto' module"
                              // ✅ Alternative (old): bcryptjs — pure JS, ran fine
```

**Now:** native `bcrypt` technically works. **But remember the golden rule:** password verification does **not** belong in the proxy. Authentication was already decided in 4.12 — it lives in the layout and actions.

**4. `jsonwebtoken` vs `jose`** — JWT verification (the JWT concept — signed tokens — gets its full treatment in Batch 5):

```ts
import { jwtVerify } from "jose"   // Edge-compatible JWT verification
const { payload } = await jwtVerify(token, secret)
```

**Now:** `jose` is no longer required (Node is available), but the **pattern** is worth knowing — `await jwtVerify` is the standard shape for JWT verification, and your course will use it.

## Golden Rule — What Belongs in the Proxy (Still the Same)

The runtime change altered **capabilities**, not **design principles**. The proxy still has clear boundaries:

**✅ Keep it light (infra tasks, per-request):**

- Routing — redirects and rewrites (4.8/4.9)
- Reading cookies and headers (4.5/4.6)
- Logging request metadata (4.11)
- Rate limiting (4.13) and geo checks (4.14)
- A/B routing and maintenance pages (4.9)

**❌ Never put these here (the golden rule):**

- **Heavy computation or database queries** — the proxy runs on *every* request. Heavy logic here means every page slows down. Database work = Server Components and actions.
- **Verified auth/security decisions** — the "why not" from 4.12 (CVE-2025-29927 and spoofable cookies). Authentication = `auth()` in the layout (Batch 5).
- **Secret data exposed to the browser** — the proxy code is server-side, but its results travel to the client on every request. Be cautious about what crosses that boundary.
- **Large data processing** — parsing or modifying response bodies is not what the proxy is for (log and track *light* metadata only).

**One-line summary of the rule:** *Read a cookie or header, apply a simple condition, return a redirect or rewrite — that is all. Anything heavier goes to API routes or Server Components.*

## ⚠️ `export const runtime = "nodejs"` — The Old Escape Hatch, Now Obsolete

Your earlier notes (from the middleware era) probably said: *"the proxy runs on the edge; if I need Node, use `export const runtime = "nodejs"`."* **In Next 16, that is wrong:**

- Through Next 15, `runtime: "edge"` / `runtime: "nodejs"` were config options (and `nodejs` became stable in 15.5+).
- In Next 16, the runtime option was **removed** from the proxy — `runtime: "edge"` now causes a build error (verified in 4.15), and `runtime: "nodejs"` is unrecognized and irrelevant.

The proxy is **always Node.js** now. There is nothing to configure — and copying old "escape hatch" code will only cause errors.

---

## What It Is NOT

- **"Now I can put everything in the proxy."** The ability to run `fs` or a database does not make it a good idea. The light-proxy rule survived for performance and architecture reasons (it was an API restriction before; now it is a design principle).
- **A database call in the proxy is OK because Node supports it.** It technically works — but that does not make it a good idea. Every request opens a connection and pays the cost. Data layers belong in components and actions, where they are cached, pooled, and tested.
- **The golden rule comes from edge restrictions.** It does not — the reasons (per-request overhead, architectural layering, security boundaries) existed long before Edge and are independent of the runtime.
- **`jose` or `bcryptjs` are now unnecessary.** You can still use them; just know that the *reason* (edge incompatibility) no longer applies to the proxy. The library choice is no longer constrained by the runtime.

## Common Mistakes

- **Copy-pasting the `runtime` export from old middleware tutorials.** On Next 16 this causes a build error — remove it entirely.
- **Putting a database call in the proxy "because Node supports it now."** Wrong trade-off: every request hits the DB, with connection-pool and latency cost. Keep data work in components.
- **Treating the proxy as a security boundary.** The CVE and bypass argument from 4.12 is unchanged by the runtime switch — verified auth still belongs in the layout.
- **Running heavy synchronous work (parsing, looping, crypto) in the proxy.** It blocks every request — every page suffers.

## Nutshell

The old edge-only failures (`fs`, Prisma, `bcrypt`) are technically resolved in Next 16 — the proxy runs on Node.js. The **golden rule does not change**: the proxy stays light (cookies + headers + a simple condition + redirect/rewrite). Heavy logic and database work go to Server Components and actions. Verified auth stays in the layout — the CVE lesson is unchanged. And the `runtime` export is now obsolete — delete it.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Even though Node supports it, the proxy runs on every request. A database call on every request means a connection and query per visitor — connection-pool exhaustion, added latency on every page, and no caching. Data access (including rate-limit state in 4.13's production Redis pattern) belongs in components and actions, where pooling and caching are built in.

5. Why is verified auth still not in the proxy even after the Node runtime switch?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The runtime switch fixed API availability — it did not fix security. The proxy is bypassable (CVE-2025-29927, as shown in 4.12) and cookie values are spoofable. Verifying identity requires checking credentials against a trusted store — that logic lives in the layout via `auth()`. The proxy handles routing; the layout handles security. The boundary between them is a security concern, not a runtime concern.

</details>
