## Where We Left Off

In 0.5 we learned that `fetch()` is cached by default in Next.js, enabling static generation. But caching at the fetch level only gets us so far — what if the entire page could be static at build time, and then refresh itself periodically? That is **Incremental Static Regeneration (ISR)**.

## Broader Goal

This file explains ISR — the technique that gives you the speed of static pages (SSG) with the freshness of dynamic data. You will understand:

- What ISR is and how it works
- How to enable it with `revalidate`
- The timing of when a page refreshes
- How it compares to SSG and SSR

## ISR — Incremental Static Regeneration

**Incremental Static Regeneration (ISR):** a static page (generated at build time, like SSG) that **refreshes itself on an interval** in the background. You get SSG's speed, but the content does not stay stale forever.

```tsx
// app/blog/[slug]/page.tsx — ISR page
export const revalidate = 60;   // this page refreshes every 60 seconds

export default async function BlogPost({ params }) {
  const post = await getPost(params.slug);
  return <Article>{post.title}</Article>;
}
```

With `export const revalidate = 60`, the page is **served from cache for 60 seconds**. Every 60 seconds (on the next request), Next.js **regenerates it in the background** with fresh data. The user **never waits** — stale content is served while the fresh version generates in the background.

### Is `revalidate` a Special Syntax?

A common confusion: is `revalidate` a keyword? A special language feature? No — it is a **special export name** that Next.js recognizes.

```tsx
export const revalidate = 60;
```

Syntactically, this is just a regular exported constant. But Next.js's build system looks for specific named exports inside page components (`revalidate`, `dynamic`, `fetchCache`, `runtime`, and others). When it finds `revalidate`, it treats the page as ISR with that interval. You are not configuring — you are declaring, in the page itself, what behavior you want. This is **convention over configuration**.

## How ISR Timing Works

```
t=0s   build → page is generated statically (SSG)
t=30s  request comes in → cached copy is served (fast, stale)
t=70s  request comes in → 60s have passed, so background re-generation is triggered
         stale version is served immediately; fresh version generates in the background
t=70s+ once regeneration finishes → cache is updated → fresh version is served
```

> **Key point:** the user is **never blocked**. On a cache miss after expiry, the stale version is served first, and the fresh version generates behind the scenes.

## ISR vs SSG vs SSR — Quick Comparison

| | SSG | ISR | SSR |
|---|---|---|---|
| **When ready** | Build time | Build time + interval revalidation | Every request |
| **Freshness** | Stale after deploy | Refreshes on interval | Always fresh |
| **Speed** | Fastest | Fast (cache serve, background refresh) | Per-request server work |
| **Best for** | Never changes | Content changes occasionally | Data must be fresh per user |

## Real-World Use Cases

ISR is ideal for content that updates occasionally but should still load fast — blogs and news sites where new posts publish every few hours or days, e-commerce catalogs where prices or inventory change a few times per day, marketing pages that content editors update infrequently. In all these cases, you want the speed of static delivery, but the content cannot be stuck at "deploy time" forever.

## Page-Level vs Fetch-Level Revalidation

One thing often causes confusion: `revalidate` appears at two levels:

- **Page-level** — `export const revalidate = 60` inside a page file. This makes the **entire page** ISR.
- **Fetch-level** — `next: { revalidate: 60 }` inside a `fetch()` call. This revalidates just that one data fetch.

Both work on the same underlying data cache in Next.js, so they achieve similar results. The difference is scope: page-level applies to the whole route; fetch-level applies to a single `fetch` call.

## What It Is NOT

⚠️ **The page is fully static, so `revalidate = 60` means the page regenerates at exactly 60 seconds.** It means "the cached copy is considered fresh for up to 60 seconds, then the *next request* triggers a background regeneration." It is not a cron job that fires at an exact second.

⚠️ **ISR is for everything.** It gives you the speed of static delivery with periodic freshness. But for user-specific or truly live data (dashboards, real-time feeds), you still need SSR / dynamic rendering — that is covered in later modules.

⚠️ **You need to redeploy to update ISR pages.** The `revalidate` interval handles it automatically — you do not need to redeploy just because content changed.

## Summary

- **ISR** = SSG speed + periodic background regeneration
- `export const revalidate = 60` → page is cached for 60 seconds, then regenerates on the next request
- Stale content is served while fresh content generates in the background — the user never waits
- Perfect for blogs, news, catalogs — content that changes occasionally but should load fast
- For per-user / live data, SSR / dynamic rendering is still needed

2. Why does the user never have to wait with ISR?

<details>
<summary>Sample Answer</summary>

**Answer:** Because the stale cached version is served instantly while the fresh version regenerates in the background. The user sees content immediately, and Next.js updates the cache asynchronously — no request ever blocks on a slow regeneration.

3. What does `export const revalidate = 60` do?

<details>
<summary>Sample Answer</summary>

**Answer:** It turns the page into an ISR page — the HTML is cached for 60 seconds. After 60 seconds, the next request triggers a background regeneration with fresh data, while the stale cached version is served immediately.

</details>

4. When is ISR a better choice than pure SSG, and when is it still not enough?

<details>
<summary>Sample Answer</summary>

**Answer:** ISR is better when content changes occasionally (a blog that publishes new posts, a product catalog) — SSG would require a full rebuild/deploy for every change. But ISR is still not enough for per-user or truly live data (a personal dashboard, real-time stock prices) where every request must be fresh — that still requires SSR or dynamic rendering.

</details>
