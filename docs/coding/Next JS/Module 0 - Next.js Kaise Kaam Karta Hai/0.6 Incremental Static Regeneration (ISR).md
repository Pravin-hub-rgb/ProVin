0.5 mein humne sunna ki `fetch` caching model mein `next: { revalidate: 60 }` jaise options hain. Par asli power tab aati hai jab yeh caching **page level pe** lagti hai — aur isi se ek strategy banti hai jo static aur dynamic ka best combination banati hai. Yehi hai **Incremental Static Regeneration (ISR)**.

Ek bakery ka example — 0.2 mein SSG ka biscuit wala example yaad tha? Ab usko thoda upgrade karte hain.

## Bhole-Baala Bakery — Ab "Seedhi Samsth" Mood

0.2 mein humne bola — bakery subah biscuits bana ke rakh deti hai (SSG), par recipe badli toh aaj purane hi milenge. Isliye `revalidate` — bakery ko batado:

**"Har 60 second mein check karo, agar recipe/data badla hai toh fresh biscuits banao, nahi toh pehle wale hi do."**

Yehi hai ISR — **static page jo khud time-to-time refresh ho jata hai.** SSG ki fast delivery rehti hai, par stale nahi rehta.

## ISR Define Kar Lete Hain

**Incremental Static Regeneration (ISR):** Aise static pages jinhe time-to-time revalidate kiya ja sake — build time pe ready (fast), phir specified interval ke baad **background mein** fresh data se dobara generate hota hai.

```tsx
// app/blog/[slug]/page.tsx — ISR page
export const revalidate = 60;   // 60 sec pe page khud refresh

export default async function BlogPost({ params }) {
  const post = await getPost(params.slug);   // fetch/cache behaviour + revalidate
  return <Article>{post.title}</Article>;
}
```

`export const revalidate = 60` — page **60 seconds tak** static/cached rahega. User request kare toh cached copy (fast). 60 sec guzre + request aaye → Next.js background mein wo page dobara generate karta hai (fresh data), aur cache update. **User ko kabhi wait nahi karna padta** — refresh background hota hai.

## How ISR Timing / Cache Works

```
t=0s   build → page static generated (SSG)
t=30s  request → cached copy serve (fast)   ← user ko turant
t=70s  request → 60s guzre, toh *trigger* background regen
       cached old serve immediately; fresh regen in background
t=70s+ jab regen done → cache updated → ab fresh serve
```

> **Key point:** User ko kabhi **wait nahi** karna padta — request pe stale serve hota hai, aur background mein refresh hota rehta hai.

## ISR vs SSG vs SSR (Quick)

| | SSG | ISR | SSR |
|---|---|---|---|
| Kab ready | Build time | Build + interval revalidate | Har request pe |
| Freshness | Stale after deploy | Interval ke baad refresh | Always fresh |
| Speed deliv | Fastest | Fast (cache serve) | Server per request |
| Use | Never changes | Data changes occasionally | Data always/per user |

## Real Use Cases — Kahan ISR Perfect

- **Blog / news** — posts aate jaate rehte hain, hours ya days baad update → revalidate 60/3600
- **E-commerce catalog** — product prices/inventory occasionally change → revalidate
- **Marketing pages** — content editors update rarely, fast serve chahiye

## Terminology Confession

- **`revalidate`** (page-level, `export const revalidate = 60`) → **ISR**
- **`next: { revalidate: 60 }`** (fetch-level, 0.5) → same revalidation concept, but per-fetch cache
- Next.js App Router mein dono same data-cache pe kaam karte hain — `revalidate` page har tarah ko is not-different laga sakte, but hears page-level vs data-level.

## What It Is NOT

⚠️ **ISR = real-time nahi.** Web live (0.6) nahi — interval ke basis pe refresh, exact second pe update nahi. (Real-time/streaming ke liye aage Modules mein dynamic rendering dekhenge.)

⚠️ **ISR = jevni hamesha fast static nahi matlab bloat page.** Ye static flexibility + freshness combine karta — sab content ke liye nahi (user data abhi bhi SSR/dynamic).

⚠️ **ISR = deploy-har-baar chahiye nahi.** `revalidate` ho toh page khud refresh hota hai, baar deploy nahi karna padta.

## Summary

- **ISR** = SSG (fast) + periodic regen (fresh)
- `export const revalidate = 60` → page interval ke baad background mein refresh
- Serve hamesha fast; stale-cache on trigger, regen background
- Blog/news/catalog ke liye perfect (occasionally-changing content)
- SSR still chahiye per-user/live data ke liye
