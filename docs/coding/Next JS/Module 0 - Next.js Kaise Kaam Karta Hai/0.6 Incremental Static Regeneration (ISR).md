0.5 mein humne dekha ki `fetch` caching model mein `next: { revalidate: 60 }` jaise options hain. Par asli power tab aati hai jab yeh caching **page level pe** lagti hai — aur isi se ek strategy banti hai jo static aur dynamic ka best combination banati hai. Yehi hai **Incremental Static Regeneration (ISR)**.

ISR ka core idea: ek **static page** (jo SSG ki tarah build time pe ready hota hai) **specified interval ke baad khud dobara generate** ho jaata hai. Matlab — SSG ki fast delivery rehti hai, par content stale nahi rehta.

## ISR Define Kar Lete Hain

**Incremental Static Regeneration (ISR):** Aise static pages jinhe time-to-time revalidate kiya ja sake — build time pe ready (fast), phir specified interval ke baad **background mein** fresh data se dobara generate hota hai.

```tsx
// app/blog/[slug]/page.tsx — ISR page
export const revalidate = 60;   // 60 sec pe page khud refresh

export default async function BlogPost({ params }) {
  const post = await getPost(params.slug);   // fetch/cache behaviour + revalidate
  return <Article>{post.title}</Article>;
}
```

`export const revalidate = 60` — page **60 seconds tak** static/cached rahega. User request kare toh cached copy (fast). 60 sec guzre + request aaye → Next.js background mein wo page dobara generate karta hai (fresh data), aur cache update. **User ko kabhi wait nahi karna padta** — refresh background hota hai.

## How ISR Timing / Cache Works

```
t=0s   build → page static generated (SSG)
t=30s  request → cached copy serve (fast)   ← user ko turant
t=70s  request → 60s guzre, toh *trigger* background regen
       cached old serve immediately; fresh regen in background
t=70s+ jab regen done → cache updated → ab fresh serve
```

> **Key point:** User ko kabhi **wait nahi** karna padta — request pe stale serve hota hai, aur background mein refresh hota rehta hai.

## ISR vs SSG vs SSR (Quick)

| | SSG | ISR | SSR |
|---|---|---|---|
| Kab ready | Build time | Build + interval revalidate | Har request pe |
| Freshness | Stale after deploy | Interval ke baad refresh | Always fresh |
| Speed deliv | Fastest | Fast (cache serve) | Server per request |
| Use | Never changes | Data changes occasionally | Data always/per user |

## Real Use Cases — Kahan ISR Perfect

Ab practical context dekho — ISR kahan perfect hai. Blog/news sites jahan posts aate jaate rehte hain aur hours ya days baad update hoti hain — wahan `revalidate: 60` ya `3600` lagao. E-commerce catalog jahan product prices/inventory occasionally badalte hain — wahan bhi revalidate perfect fit hai. Aur marketing pages jahan content editors rarely update karte hain par fast serve chahiye — wahan bhi.

## Ek Clarity — Page-level vs Fetch-level `revalidate`

Ek cheez clear kar lete hain, kyunki `revalidate` do levels pe lagta hai. **Page-level** `export const revalidate = 60` wala directly ISR banata hai. Aur 0.5 ka **fetch-level** `next: { revalidate: 60 }` same revalidation concept hai, par sirf us ek fetch ki cache pe. Next.js App Router mein dono same data-cache pe kaam karte hain, isliye same lag sakte hain — par fark yehi hai: **page-level vs data-level** revalidation.

## What It Is NOT

⚠️ **ISR = real-time nahi.** Interval ke basis pe refresh hota hai — exact second pe update nahi. (Real-time/streaming ke liye aage Modules mein dynamic rendering dekhenge.)

⚠️ **ISR = har cheez ke liye nahi.** Ye static ki speed + freshness combine karta hai — par user-specific/live data ke liye nahi (woh abhi bhi SSR/dynamic chahiye).

⚠️ **ISR = deploy-har-baar nahi chahiye.** `revalidate` ho toh page khud refresh hota hai, baar-baar deploy nahi karna padta.

## Summary

- **ISR** = SSG (fast) + periodic regen (fresh)
- `export const revalidate = 60` → page interval ke baad background mein refresh
- Serve hamesha fast; stale-cache on trigger, regen background
- Blog/news/catalog ke liye perfect (occasionally-changing content)
- SSR still chahiye per-user/live data ke liye
