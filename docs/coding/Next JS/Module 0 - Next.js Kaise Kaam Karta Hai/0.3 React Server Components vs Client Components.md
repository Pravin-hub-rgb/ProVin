## Where We Left Off

In 0.2 we compared the three rendering strategies — SSR, SSG, and CSR — and saw that Next.js lets you mix them on a single page. But "component level" was a phrase I used without explaining it. How does Next.js decide, for each component, whether it runs on the server or in the browser? That is the topic of this file: **React Server Components**.

## Broader Goal

This file answers the core question of Next.js architecture:

- What is a **Server Component** and what is a **Client Component**
- Which environment each type runs in
- What you can and cannot do in each
- How the two mix on a single page

The mental model you build here is the single most important skill for using Next.js effectively. Everything in the course after this builds on it.

## The Decision Is at Component Level, Not Page Level

In the comparison table from 0.2, I said you mix SSR/SSG/CSR per component. The place where that decision happens is **Server Components vs Client Components**. The key distinction is the **environment** where the code runs:

| | Server environment | Client environment |
|---|---|---|
| **Runs on** | The server (Node.js runtime) | The browser (user's machine) |
| **When** | During request, before the page is served | After the page loads in the browser |
| **Can do** | `async`/`await` data fetch, direct DB/API, server secrets | State, events, hooks, browser APIs |
| **Cannot do** | Hooks, events, browser APIs | Direct backend access, secrets |

## Server Components — The New React Architecture

**React Server Components (RSC)** are components that render **on the server**. They are the default in Next.js's App Router.

```tsx
// app/page.tsx — Server Component (default!)
export default async function HomePage() {
  const posts = await getPosts();   // fetch data directly on the server
  return <div>{posts.map(p => <Post key={p.id} {...p} />)}</div>;
}
```

This component is an `async` function that fetches data with `await`. That code **never runs in the browser** — it runs on the server, produces HTML, and sends that HTML to the browser. No client-side loading state is needed — the data is already there when the page renders.

### What Server Components Can Do

- **Fetch data directly** with `async`/`await` — no `useEffect`, no loading spinner
- **Read directly from the database** or call internal APIs
- **Use server-only secrets** — environment variables, API keys never leave the server

### What Server Components Cannot Do

Server Components can **not** use React hooks (`useState`, `useEffect`), browser APIs (`window`, `document`), or event handlers (`onClick`). Those require a browser environment — and Server Components run on the server.

> **Think about it this way:** Server Components handle **what the user sees** (data + HTML). Client Components handle **what the user does** (interactions + events).

## Client Components — When Interactivity Is Needed

When a component needs to be **interactive in the browser** — state changes, click handlers, `useEffect`, browser APIs — add the `"use client"` directive at the top of the file.

```tsx
// components/Counter.tsx — Client Component
"use use client";
import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

The `"use client"` directive means: **this component (and its subtree) runs in the browser** — its JavaScript is bundled and sent to the client. The button works, the state changes, clicks are handled. All of that happens in the user's browser.

## Rules for Mixing Server and Client

The mixing rules are simple but important:

1. **A Server Component can import and render a Client Component.** This is valid — the Client Component renders as a placeholder on the server, and its full JavaScript loads and hydrates in the browser.

2. **A Client Component cannot import a Server Component directly.** This would pull server code into the client bundle — potentially leaking secrets or sending heavy server-only code to the browser. The safe alternative is to pass a Server Component as a **child** (props.children).

3. The `"use client"` directive must be the **first statement** in the file — no imports or comments before it.

Let me show you the full flow:

```
Server Component (layout.tsx)
│
├── HTML is built: <html><body>...
│   └── <Navbar placeholder>     ← just a reserved spot
│   └── {children}               ← the page content
│
└── Client Bundle (Navbar)
    └── everything below "use client"
        └── React hydrates on the client
            └── placeholder becomes the real Navbar
```

## A Concrete Example — Mixing a Client Navbar into a Server Layout

```tsx
// components/Navbar.tsx — Client Component
"useuse client";
import { useState } from "react";

export default function Navbar() {
  const [menuOpen, setMenuOpen] = useState(false);
  return (
    <nav onClick={() => setMenuOpen(!menuOpen)}>
      {/* menu logic */}
    </nav>
  );
}
```

```tsx
// app/layout.tsx — Server Component (default, no "use client")
import Navbar from '@/components/Navbar';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <body>
        <Navbar />       {/* Client Component — gets a placeholder on the server */}
        {children}
      </body>
    </html>
  );
}
```

Step by step:

| Step | Where | What happens |
|---|---|---|
| 1 | Server | `layout.tsx` renders → HTML is built |
| 2 | Server | `<Navbar />` produces just a **placeholder** in the HTML (a reserved spot) |
| 3 | Server | everything else (`<html>`, `<body>`, `{children}`) renders as full HTML |
| 4 | Browser | HTML arrives — Navbar's spot shows a placeholder |
| 5 | Browser | Navbar's JavaScript bundle downloads |
| 6 | Browser | React hydrates — the placeholder becomes the real interactive Navbar |

The boundary is always clear: **above `"use client"` = server, below = client.** The two never actually mix — they sit side by side in the same HTML, and React makes the client part interactive.

> **Memory aid:** "use client" is a **boundary marker** — everything below that line in that file goes to the client bundle. Above the line stays on the server. This is how one page can have both server-rendered data and interactive buttons.

---

## What It Is NOT

⚠️ **`"use server"` is not the opposite of `"use client"`.** `"use server"` marks a function as a Server Action (a POST endpoint) — it is about functions, not component boundaries.

⚠️ **Server Components are not slower — they are faster.** Since server code is never sent to the browser, client bundles stay small. Users on slow devices download less JavaScript.

⚠️ **Server Components only exist in the App Router.** The old Pages Router had a different model. The `"use client"` boundary is also an App Router concept.

## Summary

- **App Router** — every component is a **Server Component by default**
- **Server Components** — render on the server, return HTML, can use `async`/`await` and read databases/secrets
- **Client Components** — marked with `"use client"`, run in the browser, can use hooks and handle events
- **Server Component**: data fetching, database, secrets | **Client Component**: state, effects, interactivity
- You mix them on one page — Server Components pass data, Client Components handle UI interactions

## In Your Own Words

1. In the App Router, which type of component is the default — Server or Client?

<details>
<summary>Sample Answer</summary>

**Answer:** Server Component is the default. Any component or page you create without opting out is a Server Component. It renders on the server and sends HTML to the browser. You only get a Client Component when you add `"use client"` at the top of the file.

</details>

2. Give two things Server Components can do and two they cannot.

<details>
<summary>Sample Answer</summary>

**Answer:** Server Components **can**: (1) fetch data directly with `await fetch()` — no hooks needed, (2) read from a database or call internal APIs with secrets. They **cannot**: (1) use React hooks like `useState` or `useEffect`, (2) use browser APIs like `window` or `document` and respond to events like `onClick`.

</details>

3. What does `"use client"` actually do?

<details>
<summary>Sample Answer</summary>

**Answer:** It marks the component (and everything below it in that file) to run in the browser instead of on the server. The component's JavaScript gets bundled and sent to the client, making it interactive. It is a boundary marker — above the line is server, below the line is client.

</details>

4. Can a Server Component import a Client Component, or vice versa? Which direction is safe?

<details>
<summary>Sample Answer</summary>

**Answer:** A Server Component **can** import and render a Client Component — this is safe and common (e.g., a Client Component button inside a Server Component page). The reverse is **not safe by default** — a Client Component cannot directly import a Server Component, because that would pull server code into the client bundle. The safe pattern is to pass the Server Component as a `children` prop.

</details>

---

Now we understand Server vs Client Components. But here is the gap: Server Components send **HTML** (static, no behavior). Client Components send **HTML + JavaScript** (interactive). How does that JavaScript "attach" itself to the HTML the server already sent? That is **hydration**, and it is the topic of 0.4.
