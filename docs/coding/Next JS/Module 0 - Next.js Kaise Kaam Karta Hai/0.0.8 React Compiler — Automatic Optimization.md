# React Compiler — Automatic Optimization (0.0.8)

## Where We Left Off

In 0.0.5 you learned `React.memo`, `useMemo`, and `useCallback` (Section 15) — the traditional way to prevent unnecessary re-renders. But it is **tedious, error-prone, and easy to get wrong**. Forget a `useMemo` dependency and you get a stale closure. Over-memoize and you waste memory. Misapply `React.memo` and you might as well not bother.

What if React could **automatically** figure out which components and values can be memoized — without you writing a single `useMemo`?

## Broader Goal

- Understand what React Compiler does (and what it does not do)
- Learn how to enable it in Next.js
- See before/after code: your manual optimizations vs. the compiler's automatic ones
- Know when it can break on existing projects

## The Problem: Manual Optimization

Here is a parent component with a child that re-renders on every parent update — even when the child's props never change:

```tsx
// Before: you hand-write React.memo + useMemo + useCallback everywhere
const ExpensiveChild = React.memo(function ExpensiveChild({ data }) {
  const processed = useMemo(() => expensiveTransform(data), [data]);
  return <div>{processed}</div>;
});

function Parent({ count }) {
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>Count: {count}</button>
      <ExpensiveChild data="same string" />  // still re-renders without memo
    </div>
  );
}
```

You have to remember to wrap in `React.memo`, wrap expensive values in `useMemo`, and wrap callbacks in `useCallback`. Miss one and you get a re-render you didn't intend.

## The Solution: React Compiler

**React Compiler** is React's new build-time optimizer. Instead of you hand-writing `useMemo`/`useCallback`/`React.memo`, the compiler reads your code, figures out what is memoizable, and generates the optimizations automatically.

```tsx
// After: React Compiler handles it — your code stays clean
function ExpensiveChild({ data }) {
  const processed = expensiveTransform(data);
  return <div>{processed}</div>;
}

function Parent({ count }) {
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>Count: {count}</button>
      <ExpensiveChild data="same string" />
    </div>
  );
}
```

No `React.memo`, no `useMemo`, no `useCallback` — the compiler inserts the equivalent optimizations based on static analysis of your code.

## How It Works

The compiler runs **at build time** (not runtime — it adds zero overhead to your deployed app):

1. It parses your component into an **AST** (Abstract Syntax Tree).
2. It identifies which variables depend on which props/state.
3. It determines **memo boundaries** — "if `data` doesn't change, `processed` can be skipped."
4. It inserts `useMemo`/`useCallback` equivalents behind the scenes.

The result: the same optimization you would have hand-written — but guaranteed correct because the compiler sees the whole picture.

## Enabling React Compiler in Next.js

```bash
npm install babel-plugin-react-compiler
```

```ts
// next.config.ts
export default {
  reactCompiler: true,
};
```

Restart your dev server. That is it. From now on, every build runs the compiler.

## Demo: Click Parent, Child Should Not Re-render

Here is a test you can run after enabling the compiler:

```tsx
'use client';

import { useState } from 'react';

function Child() {
  console.log('Child rendered');  // <-- this should STOP after compiler kicks in
  return <p>I am the child</p>;
}

export default function Parent() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>Count: {count}</button>
      <Child />
    </div>
  );
}
```

**Before compiler (no `React.memo` on Child):** Click the button → `console.log` fires every time.

**After compiler (with `reactCompiler: true`):** Click the button → `console.log` **stops firing** after the first render. The compiler detected that `Child` has no props and no state, so it skips re-rendering.

## Nutshell

| Manual optimization | React Compiler |
|---|---|
| You write `useMemo`, `useCallback`, `React.memo` | Compiler generates them automatically |
| Easy to forget, misuse, or get wrong | Correct by construction |
| Each project hand-optimized — inconsistent | Every file gets the same treatment |
| Risky to add to existing code | **Only for fresh projects** — existing hand-optimized code may break |

## When It Breaks

The compiler is **opt-in and conservative.** Enabling it on an **existing project** that already uses `useMemo`/`useCallback` can cause issues:

- The compiler may **reorder or remove** code it thinks is unnecessary — but your `useMemo` already handles it differently.
- Some patterns the compiler does not recognize yet may get **different behavior** than your manual optimization.

**Rule:** only enable React Compiler on **new projects**, or on projects where you have removed all manual `useMemo`/`useCallback`/`React.memo` first.

## What It Is NOT

- **It is not a bundler.** Unlike Turbopack (which we will see in 15), the compiler does not bundle or transpile JSX — it adds optimization passes on top.
- **It is not a runtime library.** It adds zero code to your bundle — optimizations happen at build time.
- **It is not a magic fix for slow algorithms.** If your component does `n^2` work, the compiler won't fix that — you still need algorithmic improvements. It only fixes **unnecessary re-renders**.

## In Your Own Words

1. Does React Compiler add JavaScript to your bundle? Why or why not?

<details>
<summary>Sample Answer</summary>

**Answer:** No. The compiler runs at **build time** — it reads your source, determines memoization boundaries statically, and rewrites the component to insert `useMemo`/`useCallback` equivalents. The final bundle contains the same runtime behavior, just with correct memoization already in place.

</details>

2. Why is React Compiler risky to enable on an existing project?

<details>
<summary>Sample Answer</summary>

**Answer:** Existing projects already have hand-written `useMemo`/`useCallback`/`React.memo`. The compiler's interpretation might differ from yours — it could skip a memoization you depended on, or conflict with a manual one you wrote. It is safer to enable on fresh projects or after stripping all manual optimizations.

</details>

3. What is the manual optimization that React Compiler replaces?

<details>
<summary>Sample Answer</summary>

**Answer:** `React.memo` (prevents component re-render when props don't change), `useMemo` (caches a computed value), and `useCallback` (caches a function reference). The compiler auto-generates all three through static analysis — no manual work needed.

</details>

4. Does React Compiler fix algorithmic performance problems?

<details>
<summary>Sample Answer</summary>

**Answer:** No — it only prevents unnecessary re-renders. If your component does genuinely expensive work (like an `O(n^2)` algorithm), you still need to optimize the algorithm itself. The compiler won't make a slow algorithm fast; it just stops it from running when the inputs haven't changed.

</details>
