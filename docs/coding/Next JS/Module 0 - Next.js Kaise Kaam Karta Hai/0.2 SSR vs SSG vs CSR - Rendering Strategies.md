0.1 mein problem clear hui — CSR app mein user ko content dekhne ke liye browser ko bundle download + execute + data-fetch ka wait karna padta hai, aur SEO/social-preview ko bhi dikkat (server ke HTML mein content tha hi nahi). Humne idea paaya — *"kya server hi ready HTML bhej de?"*

Is file ka kaam: woh idea (server-rendered HTML) alag-alag tariko se ho sakta hai. Har tarike ko pehle **individual** samjhenge, aur **compare sabse last mein** karenge — taaki pehle sab clear ho jaye. Teeno strategies hain: **SSR**, **SSG**, aur **CSR** (CSR toh 0.1 se jaante hain).

## Build aur Deploy — Pehle Ye Clear Kar Lete Hain

SSG samajhne se pehle do terms clear kar lete hain, kyunki SSG inhi pe based hai:

- **Build** = jab tum `npm run build` chalate ho, toh app ka production version banata hai (minified HTML/CSS/JS files). Ye ek **time-bound step** hai — build hone tak app ki files ready ho jaati hain.
- **Deploy** = woh built files ko server/CDN pe daalna — jahan se real users access karte hain.

Inke context mein SSG ka matlab hai: HTML **build ke waqt hi** ready ban kar store ho jaata hai.

## SSR — Server-Side Rendering

**Definition:** Server **har request pe** page ka HTML **fresh banakar** bhejta hai. Data DB/API se usi request ke waqt milta hai, HTML usi data se banta hai, aur user ko ready content milta hai.

Har request pe ye steps repeat hote hain:

```
[1] User /blog/post-1 kholta hai
[2] Server request receive karta hai
[3] Server data fetch karta hai (DB/API) — fresh, isi waqt ka
[4] Server us data se HTML render karta hai
[5] Ready HTML response mein milta hai → content turant dikhta hai
```

Ab is process se naturally ye sawaal aata hai — *yeh kis content ke liye sahi hai?* SSR tab kaam aata hai jab **data har request pe naya/unique** hona chahiye, kyunki server har baar fresh fetch karta hai. Iska sabse common example woh data jo user ke hisaab se alag hota hai — user ka "mera profile" page (har user ka apna data). Aur jo data live badalta rehta hai — live stock prices, search results, real-time social feed.

Aur isi approach ke fayda-nuksaan bhi isi wajeh se aate hain. Kyunki har request pe fresh data milta hai, fayda hai — **latest + personalized** content. Par yahi cheez uska alag side bhi hai — har request pe server ko poora kaam karna padta hai (fetch + render), isliye thodi latency aur har request pe server ka load hota hai.

## SSG — Static Site Generation

**Definition:** Page ka HTML **build time pe pehle se bana kar store** kar diya jaata hai. Request aane pe ready HTML turant serve hota hai — server us request ke waqt koi computation nahi karta.

Steps:

```
Build time (ek baar):
[1] Server data fetch karta hai
[2] Us data se HTML bana kar store kar deta hai

Request time (har baar):
[3] User URL kholta hai → ready HTML turant milta hai (koi server computation nahi)
```

To yeh kis type ke content ke liye fit hai? Kyunki HTML ek baar bana ke fixed ho jaata hai, SSG tab best hai jab content **rarely change** hota hai aur **public** hai — jaise blog post (publish ke baad kabhi-kabhi badalta hai), marketing/docs pages, product catalog. Inke liye fast delivery sabse zaroori hai — aur ready HTML CDN pe pehle se para hai, isliye turant milta hai.

Iski fayda-nuksaan bhi naturally samajh aate hain. Fayda — **sabse fast** delivery: CDN se ready HTML turant milta hai aur har request pe server ka koi kaam nahi. Nuksaan — content deploy ke baad **khud update nahi** hota: agar data badla toh pura rebuild/deploy karna padta (taaki change aaye) — isko 0.6 mein `revalidate` se fix karenge.

## CSR — Client-Side Rendering (0.1 se Recap)

0.1 se yaad: browser khali HTML + JS bundle download karta hai, phir JS execute karke content khud banata hai. Server ke HTML mein content pehle se nahi hota.

Toh CSR tab sahi hai jab **user ki interactivity** hi sabse bada point ho — jaise dashboards, chat UI, editors, sorting/filtering UI, jahan UI baar-baar badalti rehti hai. Kyunki sara render browser mein hota hai, interactivity ke liye perfect hai (static shell ke upar). Par ulta side — agar yehi default main render ho toh SEO/performance issues (0.1 se yaad).

## Compare Kar Lete Hain — Ek Table Mein

Ab jab teeno individual clear ho gaye, compare karte hain:

| Strategy | HTML kaun banata hai | Kab banta hai | Serve speed | Freshness |
|---|---|---|---|---|
| **SSR** | Server | Har request pe | Slow-ish (har request compute) | Always fresh |
| **SSG** | Server | Build time pe, ek baar | Fastest (CDN se cached) | Stale after deploy |
| **CSR** | Browser (JS se) | User kholne ke baad | Slow first paint (bundle) | Browser pe hi |

### SSG vs SSR — Fark Sirf Timing Ka

SSG aur SSR dono **server pe** HTML banate hain. Fark sirf ek hai: **kab banate hain.**

- **SSG** = build time pe bana ke store kar liya → baad mein har request pe sirf ready copy serve hoti hai (fast, par stale ho sakta hai)
- **SSR** = har request pe fresh banata hai → data hamesha latest (par har request pe server kaam)

Decide aise: content rarely badlta hai → **SSG**. Data har request pe live/unique chahiye → **SSR**.

## Kab Kaunsa Use Karein

| Situation | Strategy | Kyon |
|---|---|---|
| Blog post, marketing page (rarely changes, public) | **SSG** | Fastest, CDN se turant |
| User profile, live prices, search (fresh per request) | **SSR** | Har request pe latest data |
| Dashboard, chat, editors (highly interactive) | **CSR** | Browser-side interactivity |
| Blog jo occasionally update hota hai (hours/days baad) | **ISR** — 0.6 mein | SSG ki speed + periodic refresh |

## Ek Page Pe Teeno — Real Example

Next.js ka power: **ya-ya nahi, aur-aur.** Ek hi page pe teeno strategies ek saath kaam kar sakti hain:

- **Static shell** (layout, header) → SSG — build time pe ready
- **Dashboard data** (user-specific numbers) → SSR — har request pe fresh
- **Interactions** (tab switching, sorting, chart animation) → CSR components — browser pe

Isi ko Next.js kaise allow karta hai — woh 0.3 (Server vs Client Components) mein. Abhi concept clear: **teeno strategies ko ek page pe milana possible hai.**

## What It Is NOT

⚠️ **SSG = "user ke browser mein runtime pe banta hai" ka matlab nahi.** SSG ka HTML build time pe built hota hai; deploy ke baad bhi update/augment ho sakta hai (revalidation — 0.6).

⚠️ **SSR = always-slower nahi hai.** Jab har request pe fresh content chahiye, thodi latency reasonable hai — aur modern SSR optimized hai.

⚠️ **Compare ka matlab "ek strategy chunna" nahi.** Ye teeno competing selection nahi hain — Next.js teeno ko ek page pe per-component/per-page allow karta hai.

## Summary

- **CSR** — browser JS se content banata hai, user kholne ke baad — interactive apps ke liye
- **SSR** — server har request pe HTML fresh banata hai — live/personalized data ke liye
- **SSG** — HTML build time pe ready, CDN se turant — rarely-changing public content ke liye (fastest)
- Ye teeno **competing nahi** — ek page pe SSG + SSR + CSR milke kaam karte hain
- Next.js inko **per-page/per-component** allow karta hai
