0.1 mein problem clear hui — CSR mein user ko content ke liye bundle download, execute aur data-fetch ka wait karna padta hai, aur SEO/social-preview ko bhi dikkat. Aur humne idea paaya — *"kya server ready HTML bhej de?"* Yeh idea hi is file ka subject hai.

Lekin ruko — ek hi strategy hone ki zaroorat nahi. Pata hai photo thodi **agreement ke baad** banti hai.

## Photo Studio Wala Example — Brandenburg Gate pe Mat Jaao

Soch tum do film stars ki photo chaho:

1. **Pehli:** Ek photo jo tumne **pehle se** tyaar karke rakh di thi, koi bhi abhi bhi le jaye — ready. (Static)
2. **Dusri:** Ek photo jo **har baar naya photographer tab click karta hai jab koi maange** — thodi si delay, par har baar fresh. (Server)
3. **Teesri:** Ek photo jo customer khud apne laptop pe bana kar dikhata hai. (Client)

Teeno wahi "photo" hain, zero difference user ko content mein. Par **kab kaunsa choose karoge**? Yehi CSR vs SSG vs SSR ka asli sawaal hai — **content wahi, kaun kab banata hai, aur kab banta hai.**

## Teeno Define Kar Lete Hain (Ghar Wali Language)

| Strategy | Kya hota hai | Kaha banta hai | Kab banta hai |
|---|---|---|---|
| **CSR** (Client-Side) | Khali HTML + JS → browser content banata hai | Browser mein | User kholne ke baad, har baar (client-side data ke saath) |
| **SSR** (Server-Side) | Har request pe server HTML fresh banakar bhejta hai | Server pe | Har request pe, live |
| **SSG** (Static Site Generation) | Build time pe HTML pehle se ban kar file/edge pe rakh diya | Build time (deploy pe) | Pehle se — deploy ke waqt ek baar |

### SSR aur SSG ka Biscuit Example

Ek bakery socho:

- **SSG:** Bakery **subah 5 baje saare biscuits bana kar** rakhti hai. Din bhar koi bhi aaye — turant milta hai, fast. Par agar recipe kal badli, toh aaj ke biscuits wahi purane honge. (Ready pehle se, real-time nahi)
- **SSR:** Har customer ke aane pe bakery **tab fresh bana ke** deti hai. Har order latest hai, garam. Par thoda wait karna padta hai — bakery har baar kaam karti hai. (Fresh, par slow-ish)

Sawaal: Bakery ko kaunsa chahiye? Depends — agar din bhar wahi biscuits bikne hain aur kuch rare hi badalta hai, toh **SSG** perfect (fast). Agar har order pe alag topping chahiye matlab data live/fresh hona chahiye har baar, toh **SSR** (fresh).

## Real Context — Kab Kaunsa Use Karna

### SSG (Static) — Pehle Se Ready 🥇
- **Kab:** Content jo rarely change hota hai aur public hai
- **Examples:** Blog post (likha, publish kiya, kabhi spaar change hoga), marketing/docs pages, product catalog pages
- **Pros:** Sabse fast — CDN se turant serve, no server computation per request
- **Cons:** Real-time nahi — content deploy baad update nahi hota (agar hum isko revalidate nahi karte — yeh 0.6 mein dekhenge)

### SSR (Server) — Har Baar Fresh 🥔
- **Kab:** Content jo har request pe naya/unique ho
- **Examples:** User-specific "mera profile" page, live stock prices, search results, real-time social feed
- **Pros:** Har request pe **fresh + personalized**
- **Cons:** Har request pe server kaam karta hai — thoda slow, per-user og par load

### CSR (Client) — Browser Mein 💻
- **Kab:** Highly interactive, logged-in pieces
- **Examples:** Dashboards, chat UI, editors, sorting/filtering UI
- **Pros:** On top of static shell, interactivity ke liye perfect
- **Cons:** (0.1 se yaad — SEO/performance issues agar default main render)

> **Key samajh:** Ye **ya-ya nahi, aur-aur** hai. Next.js tumhe **teeno ek saath** use karne deta hai **page/page basis pe** — koi ek page static (SSG), koi server (SSR), koi client dynamic hook. Yeh mix-and-match hi Next.js ka power hai. Client vs Server ka exact control 0.3 mein aayega, hydration (server HTML + client animation) 0.4 mein.

## Common Dashboard Ki Kahani (Jodne Ke Liye)

Ek simple "user dashboard" page dekho — kitne strategies milke kaam kar rahi hain:

- **Static shell** (layout, header) → SSG — pehle se ready
- **Dashboard data** (agra user-specific numbers) → SSR (Server Component fetch) — fresh
- **Interactions** (tab switching, sorting, chart animation) → CSR components — client pe

Isi ko kaise Next.js allow karta hai — woh baad mein (0.3, 0.7). Abhi concept clear ho — **"saari strategies ko ek page pe milana possible hai."**

## What It Is NOT

⚠️ **SSG = `Static HTML` nahi, matlab built once.** Deploy ke baad bhi bana-firbana / augment hota hai (revalidation — 0.6). Static ka matlab "user ke browser me runtime pe bana" nahi.

⚠️ **SSR = always-slower ka matlab nahi.** Slow-tab thodi difference hai jab content fresh chahiye ho. Modern SSR optimized hai.

⚠️ **"aur-aur" yaad rakho:** Tumse koi bole "ek website ka rendering fast chahiye" toh uska matlab ek hi strategy chose karoge — galat. Next.js mein chaar strategies ek page pe coexist karti hain.

## Summary

- **CSR:** Browser banata hai, user kholne ke baad — interactive, logged-in apps
- **SSR:** Server har request pe fresh banata hai — live/personalized data
- **SSG:** Build time pe pehle se ready — rarely-changing public content (fastest)
- Yeh **competing selection nahi**; tum eka page dekhte SSG + SSR + CSR milke kaam karte hain
- Next.js inko **per-page/per-component** pe allow karta hai
