## Where We Left Off

In 0.1 we saw how Client-Side Rendering works: the browser downloads an empty HTML shell and a JavaScript bundle, then builds the content itself. The fix is clear: the server should send ready-made HTML. But there are different ways to do that. This file introduces the three rendering strategies — **SSR**, **SSG**, and **CSR** — and how they compare.

## Build vs Deploy — A Quick Distinction

Before we define static rendering, let us clear up two terms that get mixed up:

- **Build** — when you run `npm run build`, Next.js creates the production version of your app (minified HTML, CSS, and JS files). This is a one-time step that produces the deployable artifacts.
- **Deploy** — taking those built files and putting them on a server or CDN so real users can access them.

With these definitions in mind, "static" means the HTML is generated once at **build time** and stored, ready to serve.

## SSR — Server-Side Rendering

**Definition:** The server generates the HTML **fresh on every request** — fetching data, rendering, and sending the complete HTML back to the browser.

Steps on every request:

```
[1] User opens /blog/post-1
[2] Server receives the request
[3] Server fetches data (from DB / API) — fresh, right now
[4] Server renders HTML from that data
[5] Complete HTML arrives in the response → content is visible immediately
```

**When does it help?** SSR is the right choice when the data must be **fresh on every single request** — because the server fetches and renders it each time. The most common case is user-specific content: your profile page (your data is different from everyone else's), live stock prices, real-time search results, or a personalized social media feed.

And with fresh data comes the trade-off naturally: the advantage is that content is always current and personalized, but the cost is that the server must do work (fetch + render) on every request — so there is a small per-request latency, and the server handles more load.

## SSG — Static Site Generation

**Definition:** The HTML is generated **at build time** and stored. When a request comes in, the pre-built HTML is served instantly — the server does zero computation.

Steps:

```
Build time (once):
[1] Server fetches data
[2] Generates HTML and stores it

Request time (every time):
[3] User opens the URL → pre-built HTML is served instantly (no server work)
```

**When does SSG help?** Since HTML is built once and stays fixed, SSG is ideal for content that **rarely changes** and is **public** — like a blog post (published and only edited occasionally), marketing pages, documentation, or a product catalog. Speed is the biggest win: the HTML is already on the CDN, so it is delivered from the edge with zero server computation.

The trade-off is clear: the upside is the fastest possible delivery with zero per-request server work. The downside is that the content does not update until you **redeploy** — change the data, rebuild, deploy again. That limitation is solved with ISR in 0.6.

## CSR — Client-Side Rendering (Recap from 0.1)

From 0.1: the browser downloads an empty HTML shell and a JavaScript bundle, then builds the content itself by executing JavaScript. The HTML does not contain content — the browser constructs it.

CSR is the right choice when **interactivity** is the priority — dashboards, chat UIs, editors, sort/filter interfaces — because all rendering happens in the browser, which gives the most responsive interactions. But the downside returns: slow first paint, SEO issues, and broken social previews (covered in 0.1).

## Compare Them — One Table

Now that each strategy is clear on its own, let us compare them side by side:

| Strategy | Who generates HTML | When it is generated | Serve speed | Data freshness |
|---|---|---|---|---|
| **SSR** | Server | On every request | Slower (server computes each time) | Always fresh |
| **SSG** | Server | Build time, once | Fastest (CDN serves cached) | Stale after deploy |
| **CSR** | Browser (JavaScript) | After the user opens the URL | Slow first paint (bundle download) | Client-side, only |

### SSG vs SSR — The Only Difference Is Timing

Both SSG and SSR generate HTML on the server. The only difference is **when**:

- **SSG** = generated at build time, stored, and served as-is → fast, but can go stale
- **SSR** = generated fresh on every request → always current, but slower per request

Decision rule: content rarely changes → **SSG**. Data that must be live or personalized on every visit → **SSR**.

## When to Use Which

| Situation | Strategy | Why |
|---|---|---|
| Blog post, marketing page (rarely changes, public) | **SSG** | Fast, served from CDN |
| User profile, live prices, search (needs to be fresh per request) | **SSR** | Latest data on every visit |
| Dashboard, chat, editor (highly interactive) | **CSR** | Full browser-side interactivity |
| Blog that is updated occasionally (hours or days later) | **ISR** — see 0.6 | SSG speed + periodic refresh |

## One Page, Three Strategies — Real Example

This is the power of Next.js: you do **not** pick one strategy for the whole app. You mix and match per page, per component:

- **Static shell** (layout, header, footer) → SSG — built once, served from CDN
- **Dashboard data** (user-specific numbers) → SSR — fresh on every request
- **Interactions** (tab switching, sorting, chart animation) → CSR components — browser-side

How this mixing works at the component level — that is the topic of 0.3 (Server vs Client Components). For now, just absorb the concept: **you can combine all three strategies on a single page.**

## What It Is NOT

⚠️ **SSG does not mean "rendered in the user's browser at runtime."** SSG's HTML is generated at build time; it does not update at runtime unless you set up revalidation (0.6, ISR).

⚠️ **SSR is not always slower.** When the priority is fresh data on every visit, the small latency is reasonable — and modern SSR is heavily optimized.

⚠️ **These three are not competing choices.** Next.js lets you use all three on one page — per component, per route. It is not "pick one."

## Summary

- **CSR** — browser builds content from JavaScript after the page loads — interactive apps
- **SSR** — server generates HTML fresh on every request — live, personalized data
- **SSG** — HTML is generated at build time and served instantly — rarely-changing public content (fastest)
- These are **not** exclusive — you mix them per page / per component in Next.js

**Answer:** In SSG, HTML is generated **at build time** — once, then stored and served from cache. In SSR, HTML is generated **on every request** — the server fetches data and renders fresh HTML each time a user visits.

2. For a blog post, which strategy makes the most sense (before learning about ISR in 0.6)?

<details>
<summary>Sample Answer</summary>

**Answer:** SSG — because a blog post rarely changes and is public content. It is generated at build time, served instantly from the CDN, and delivers the fastest experience. (If the blog gets new posts occasionally, ISR in 0.6 adds automatic periodic refresh.)

</details>

3. What is the main trade-off of SSR?

<details>
<summary>Sample Answer</summary>

**Answer:** The upside is that data is always fresh and personalized on every request. The downside is that the server must do work (fetch + render) on every visit, adding a small latency and increasing server load.

</details>

4. "The three strategies are not exclusive" — what does this mean in Next.js?

<details>
