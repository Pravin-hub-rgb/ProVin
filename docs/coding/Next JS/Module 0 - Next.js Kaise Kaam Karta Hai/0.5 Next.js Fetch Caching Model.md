0.4 tak humne jaana — server ready HTML bhejta hai, client interactivity jodta hai. Par **server woh data kahan se laata hai?** Database/API se toh har baar thodi der lagti hai. Next.js isko handle karta hai apne **fetch caching model** se.

## Caching Ka Base — Cache Define Kar Lete Hain

**Cache** = ek storage jahan koi cheez pehle se store hoti hai, taaki dobara compute karna na pade.

**Fetch caching** ka matlab: Server Component jis API/DB se data laata hai, uska result ek jagah store kar do. Agli baar wahi request aaye toh **server se dobara nahi jana** — cached copy turant milti hai.

> **Key:** Caching ka fayda = **speed** (server/data-source pe load kam, response fast). Lekin downside = **data stale** ho sakta hai (jab tak invalidate na karein).

## Next.js Default Fetch Behavior (App Router)

`fetch()` Server Component mein use hota hai toh Next.js default mein **cache** karta hai — data **build time pe** fetch + cached hota hai (static). Yeh SSG (0.2) ko enable karta hai — pehle se ready.

```tsx
// app/page.tsx — DEFAULT
export default async function Page() {
  const res = await fetch("https://api.example.com/posts");
  const posts = await res.json();
  return <PostList posts={posts} />;
}
```

By default (App Router, Next 15+) `fetch` **cached** hai. Matlab pehli baar run pe data API se aaya aur store hua — baad ke requests cached copy use karenge.

### Kab Cache Nahi Karna Chahiye

Agar data har baar fresh chahiye (live stock, real-time) — `cache: 'no-store'`:

```tsx
const res = await fetch("https://api.example.com/prices", {
  cache: "no-store",   // har request pe fresh — server se
});
```

Agar thodi der ke liye revalidate karna hai (e.g. 60 seconds pe refresh) — `next: { revalidate: 60 }`:

```tsx
const res = await fetch("https://api.example.com/posts", {
  next: { revalidate: 60 },  // 60 sec baad dobara fetch
});
```

(Full `revalidate` + ISR mechanism 0.6 mein clearly samjhenge — yahan bas formats dikha rahe hain.)

## Data Fetching Options — Quick Table

| Karne Ka Tarika | Kya Hota Hai | Kab Use |
|---|---|---|
| Default `fetch()` | Cached (static), build time pe | Rarely-changing public data (blogs, catalog) |
| `cache: 'no-store'` | Har request pe fresh | Live data (prices, notifications, user-specific) |
| `next: { revalidate: 60 }` | 60s tak cached, phir refresh | Data jo thoda der mein refresh hota (ISR — 0.6) |

## Kya Cache Karo, Kya Nahi — Decide Kaise

Ab decide karne ka simple rule samajh lo. Jis data ko **rarely badalta hai** — jaise retail product info, help docs, blog posts — usko cache karo, kyunki SSG ka fayda milta hai. Aur jis data ko **har visitor ke liye alag** hota hai — user dashboard, cart, personalized feed — usko cache NA karo, `no-store` se fresh rakho.

> Hamesha yehin trade-off yaad rakho — cache karne se performance badhti hai par data stale ho sakta hai; `no-store` se data fresh rehta hai par server load badhta hai.

## What It Is NOT

⚠️ **Caching = har jagah static HTML nahi.** Request ko data ke liye har baar source jane ki jagah stored copy serve karne wala pattern hai — static ya dynamic dono ho sakta hai.

⚠️ **Cache = browser cache ke same nahi bol sakte.** Browser cache client pe hota hai; yeh Next.js server-side fetch cache hai — alag purpose ke liye (server/backend load reduce karta hai).

⚠️ **`no-store` = bura nahi hai.** Iska matlab data source pe har baar jana — ek dynamic endpoint. ISR bhi `revalidate` se hi use hota hai (0.6).

## Summary Humne Jani

- **Cache** = dobara compute na karke store copy use karna (speed + low load)
- Next.js App Router `fetch()` **default cached** hai (static/SSG)
- `cache: 'no-store'` → **har request pe fresh**
- `next: { revalidate: 60 }` → thodi der ke liye cached, phir refresh
- Decide: rarely-changing → cache; per-user/live → no-store
