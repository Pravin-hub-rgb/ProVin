## 1. JSX — HTML + JavaScript, Together

JSX looks like HTML, but under the hood it is JavaScript. Whatever you `return` inside a component is what gets rendered to the screen.

```tsx
function Greeting() {
  return <h1>Hello, {name}!</h1>;  // {} embeds a JavaScript variable
}
```

> **Remember:** inside `{}`, you can write any JavaScript expression — variables, function calls, ternary conditions. The attribute `class` in HTML becomes `className` in JSX (because `class` is a reserved keyword in JavaScript).

## 2. Components + Props

A component is a function that returns a piece of UI. Props are the inputs passed into a component.

```tsx
interface CardProps {
  title: string;
  count: number;
}

function Card({ title, count }: CardProps) {
  return <div>The {title} has {count} items</div>;
}

<Card title="To-Do" count={3} />  // use it as many times as you want
```

## 3. `useState` — Remembering Data That Changes

React needs to know when a value has changed so the UI can update — a plain variable does not tell React anything. That is why `useState` exists.

```tsx
const [count, setCount] = useState(0);
// count = current value, setCount = the function that updates it

<button onClick={() => setCount(count + 1)}>+</button>
```

> **Remember:** always update state using the setter (`setCount`), never by reassigning the variable directly. React only re-renders when the setter is called.

## 4. Lists + Keys

When rendering an array of items, React uses `.map()`. Each item must have a unique `key` so React can track it during re-renders (this was covered in the React module on reconciliation):

```tsx
<ul>
  {items.map((item) => (
    <li key={item.id}>{item.name}</li>
  ))}
</ul>
```

## 5. Conditional Rendering

Inside JSX, you cannot use an `if` statement directly. Instead, use ternary operators (`? :`) and `&&` (which renders the element only when the condition is true):

```tsx
{isLoading ? <p>Loading...</p> : <p>{data}</p>}
{isAdmin && <button>Delete</button>}  // button renders only if isAdmin is true
```

## 6. `useEffect` — Side Effects (API, Timers, Storage)

`useEffect` handles work that happens outside React's render cycle — fetching data, setting timers, accessing browser APIs. The dependency array (`[]`) controls when the effect re-runs.

```tsx
useEffect(() => {
  fetch("/api/users").then((r) => r.json()).then(setUsers);
}, []);  // [] — runs only once on mount
```

> **Important:** in Next.js Server Components, you will not need `useEffect` for data fetching — that is what 0.3 is about. But for client-side interactivity, it is still used.

## 7. React Router — A Generic Refresher

In the React course, client-side routing was handled by React Router. Here are the core patterns:

| Tool | What it does |
|---|---|
| `<BrowserRouter>` / `<Routes>` / `<Route>` | Set up routing and define routes |
| `<Route path="/about" element={<About/>} />` | Render `<About/>` at URL `/about` |
| `<Link to="/about">` | Navigate without a full page reload |
| `path="/movies/:id"` + `useParams()` | Dynamic route — extract a variable from the URL (`:id`) |
| `useNavigate()` | Navigate programmatically from code (`navigate("/login")`) |
| Nested routes `/parent/child` | Build nested route structure |
| Protected routes | Show a route only to logged-in users (auth-check wrapper) |

> **Remember:** this is a *generic* concept. Next.js uses **file-based routing** (create a folder + `page.tsx`) instead of `<Route>` configs. The concepts are the same — dynamic segments, navigation, nested routes — just implemented differently. We will see the details in 0.7.

## 8. Forms — Controlled Inputs (Generic)

In React, a "controlled input" means the input's value comes from state and is updated via an `onChange` handler:

```tsx
const [email, setEmail] = useState("");
<input value={email} onChange={(e) => setEmail(e.target.value)} />
```

When you are ready to take forms further, **React Hook Form (RHF)** reduces re-renders, and **Zod** provides schema-based validation (with automatic type inference):

```tsx
// RHF + Zod shape (you will use this exact pattern in Next.js)
const schema = z.object({ email: z.string().email() });
const { register, handleSubmit } = useForm({ resolver: zodResolver(schema) });

<form onSubmit={handleSubmit(onSubmit)}>
  <input {...register("email")} />
  <button type="submit">Submit</button>
</form>
```

## 9. State Management — Context API and Zustand (Generic)

- **Context API:** Share global state across components without prop drilling (`createContext` + `useContext`).
- **Zustand:** A lightweight alternative — create a store, read and update it from any component, with minimal boilerplate compared to Context.

Both are used in Next.js for **client-side reactive state**. Server-side data (fetching from DB/API) is managed differently — we will cover that in 0.3.

## 10. `useRef` — Grabbing a DOM Element Directly

When you need to interact with a DOM element — focus an input, measure its size, play a video — you need a way to **reach into the DOM** and grab that element directly. `useRef` creates a mutable container that persists across re-renders, and you attach it to a DOM element with the `ref` attribute.

```tsx
function FocusInput() {
  const inputRef = useRef<HTMLInputElement>(null);

  return (
    <>
      <input ref={inputRef} type="text" />
      <button onClick={() => inputRef.current?.focus()}>Focus the input</button>
    </>
  );
}
```

**How it works:**

1. **`const inputRef = useRef<HTMLInputElement>(null)`** — creates a mutable container. `.current` starts as `null` (the TypeScript generic says "this will eventually be an HTMLInputElement").
2. **`ref={inputRef}`** — this attribute tells React: "link this ref to that DOM element." After mount, `inputRef.current` points to the actual `<input>` DOM node.
3. **`inputRef.current?.focus()`** — calls the DOM `focus()` method directly. The optional chaining (`?.`) guards against `null` (the ref is only set after the component mounts).

> **Remember:** `useRef` does **not** trigger a re-render when `.current` changes. It is a silent, persistent container — perfect for holding DOM nodes, but **not** for storing values that should re-render the UI. For display values, use `useState`; for DOM references, use `useRef`.

## 11. `useEffect` vs `useLayoutEffect` — Before Paint vs. After Paint

In 0.0.5 we introduced `useEffect` for side effects. But there is a timing nuance that matters for visual correctness. Both hooks run side effects, but **when** they fire differs:

- **`useEffect`** — fires **after** the browser paints the screen. The user might see a flicker if you read/manipulate layout here.
- **`useLayoutEffect`** — fires **synchronously before** the browser paints. You can read and mutate layout without the user seeing a glitch.

```tsx
function Tooltip({ targetId }) {
  const tooltipRef = useRef<HTMLDivElement>(null);
  const targetRef = useRef<HTMLButtonElement>(null);

  useEffect(() => {
    // After paint — you might see a flash before tooltip repositions
    if (tooltipRef.current && targetRef.current) {
      const rect = targetRef.current.getBoundingClientRect();
      tooltipRef.current.style.top = `${rect.bottom + 10}px`;
      tooltipRef.current.style.left = `${rect.left}px`;
    }
  });

  useLayoutEffect(() => {
    // Before paint — position is set before the user sees anything
    if (tooltipRef.current && targetRef.current) {
      const rect = targetRef.current.getBoundingClientRect();
      tooltipRef.current.style.top = `${rect.bottom + 10}px`;
      tooltipRef.current.style.left = `${rect.left}px`;
    }
  }, []);

  return (
    <>
      <button ref={targetRef}>Hover me</button>
      <div ref={tooltipRef} style={{ position: 'absolute' }}>Tooltip</div>
    </>
  );
}
```

**When to use which:**

| Hook | Fires | Use case |
|---|---|---|
| `useEffect` | After paint (visible to user) | Data fetching, timers, subscriptions — anything that can happen invisibly |
| `useLayoutEffect` | Before paint (hidden from user) | Reading layout, measuring DOM, synchronously positioning elements |

> **Important:** `useLayoutEffect` is **not safer** than `useEffect` — it **blocks painting**. If you do expensive work in it, the page will freeze. Only use it when you need to measure or mutate layout before the user sees it. In Next.js Server Components, neither runs on the server — both are client-only hooks.

## 12. Child → Parent — Sending Data Upward with Callbacks

In React, state flows **down** (parent → child via props). But what if the child needs to tell the parent something — "user typed X" or "item was deleted"? You pass a **function down** (a callback), and the child **calls it**:

```tsx
// Parent — owns the state and passes the callback
function Dashboard() {
  const [todos, setTodos] = useState<Todo[]>(initialTodos);

  // This is the "send data up" function
  const addTodo = (newTodo: Todo) => {
    setTodos([...todos, newTodo]);
  };

  return <AddTodoForm onAdd={addTodo} />;
}

// Child — calls the callback when the form is submitted
function AddTodoForm({ onAdd }: { onAdd: (todo: Todo) => void }) {
  const [text, setText] = useState('');

  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault();
    onAdd({ id: Date.now(), text, completed: false });
    setText('');
  };

  return (
    <form onSubmit={handleSubmit}>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <button type="submit">Add</button>
    </form>
  );
}
```

**The flow:** the parent owns the state (`todos`), passes `addTodo` as `onAdd`, and the child calls `onAdd(input)` to send data upward. The child stays focused on the UI; the parent owns the logic.

## 13. Sibling Sharing — Lifting State Up

When **two sibling components** need to share the same data, the trick is to move the shared state **up** to their closest common parent, then pass it down to both:

```tsx
// Parent — holds the shared state and passes it to both children
function ThemeDashboard() {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');
  return (
    <>
      <ThemeToggle theme={theme} onToggle={() => setTheme(theme === 'light' ? 'dark' : 'light')} />
      <ThemeDisplay theme={theme} />
    </>
  );
}

// Sibling 1 — reads theme, can toggle it
function ThemeToggle({ theme, onToggle }: { theme: string; onToggle: () => void }) {
  return <button onClick={onToggle}>Switch to {theme === 'light' ? 'dark' : 'light'}</button>;
}

// Sibling 2 — reads theme
function ThemeDisplay({ theme }: { theme: string }) {
  return <p>Current theme: {theme}</p>;
}
```

**`ThemeToggle` and `ThemeDisplay` are siblings** — they both read from `theme`. The parent `ThemeDashboard` holds the state and passes it down. This is called **"lifting state up"** — you move state to the nearest common ancestor when siblings need to share it.

> **Remember:** React has no built-in "sibling to sibling" communication. Lifting state up is the React-idiomatic way to share data between siblings. (In the React course, we will cover Context and Zustand as alternatives for when lifting becomes unwieldy.)

## 14. What Causes a Re-render — The 4 Triggers

Your component re-renders when any of these four things happen:

| # | Trigger | What it means |
|---|---|---|
| 1. State change | `setCount(5)` — the setter was called | This component re-renders |
| 2. Parent re-renders | `App` re-renders → `<Header>` and `<Header>` children all re-run too | Children inherit the cascade unless memoized |
| 3. Same props, forced parent | Even if props didn't change, a parent re-render forces children to re-run (return the same JSX) | React doesn't bail unless you `React.memo` |
| 4. Context change | `useContext(MyContext)` — any provider update triggers all consumers | All consumers re-render |

The big takeaway: **parent re-renders always cascade down.** If `App` re-renders for any reason, every child re-runs — even ones whose props didn't change. That is why `React.memo` exists (Section 15).

## 15. `React.memo` vs `useMemo` vs `useCallback` — Memo One, Two, Three

Three "memo" tools, three different jobs. Don't mix them up:

```tsx
// React.memo — prevents a COMPONENT from re-rendering if props didn't change
const ExpensiveChild = React.memo(function ExpensiveChild({ count }: { count: number }) {
  return <div>{count}</div>;
});

// useMemo — remembers a COMPUTED VALUE across re-renders
function UserProfile({ userId }: { userId: string }) {
  const user = useMemo(() => computeExpensiveValue(userId), [userId]);
  return <div>{user.name}</div>;
}

// useCallback — remembers a FUNCTION reference across re-renders
function Parent() {
  const [count, setCount] = useState(0);

  const handleClick = useCallback((n: number) => {
    setCount(n);
  }, []); // same function reference every render — children with React.memo won't re-render

  return <ExpensiveChild count={count} onUpdate={handleClick} />;
}
```

| Tool | What it memoizes | What it prevents |
|---|---|---|
| `React.memo` | The component's render output | Re-render if props are shallow-equal |
| `useMemo` | A **value** (computed result) | Re-computation on every render |
| `useCallback` | A **function reference** | Breaking referential equality of callbacks |

> **Remember:** `useMemo` and `useCallback` are **optimization hints**, not guarantees. React may discard them. Only use them when there is a real performance cost (expensive computation, referential equality for memoized children).

## 16. Higher-Order Components (HOC) — The Wrapper Pattern

A **Higher-Order Component** is a function that takes a component and returns a **new component** with extra props/logic injected. The classic use case: "wrap a component so it checks auth before rendering."

```tsx
// HOC — takes a component, returns a guarded version
function withAuth<P>(Component: React.ComponentType<P>) {
  return function AuthenticatedComponent(props: P) {
    const { user, loading } = useAuth();

    if (loading) return <div>Loading...</div>;
    if (!user) return <div>Please log in</div>;

    return <Component {...props} />;  // inject nothing extra — just gate access
  };
}

// Usage — wrap any component
const ProtectedDashboard = withAuth(Dashboard);
```

**The flow:** `withAuth(Dashboard)` → returns `AuthenticatedComponent` → checks auth → either blocks (login message) or renders the real `Dashboard`. The HOC pattern is older — hooks have largely replaced it for new code. But you will still see HOCs in libraries (Redux's old `connect()`, auth libraries). In the React course we cover HOCs as a transitional pattern that led to hooks.

## 17. Render Props — "Here, You Render It"

Before hooks, if a component wanted to share logic ("fetch data, then render whatever you want with it"), the **render props** pattern passed a **function** as `children`:

```tsx
// DataProvider — fetches data, lets the caller decide what to render
class DataProvider extends React.Component {
  state = { data: null };

  componentDidMount() {
    fetchData().then(data => this.setState({ data }));
  }

  render() {
    return this.props.children(this.state.data); // children is a FUNCTION here
  }
}

// Usage — the function decides what HTML to show
<DataProvider>
  {(user) => <UserCard user={user} />}
</DataProvider>
```

`DataProvider` does the fetching. The **caller** decides the UI via the function `(user) => <UserCard user={user} />`. This pattern is now mostly replaced by **custom hooks** (e.g. `useUserData()` returning `{ data }` directly), which are cleaner. But you will still see render props in older libraries.

## 18. Portals — Render Outside the DOM Tree

Sometimes you need to render a component somewhere **other than where it lives in the JSX tree** — a modal, a tooltip, a toast notification that should escape parent overflow styles. `createPortal` renders a component into a DOM node **outside** the React root:

```tsx
import { createPortal } from 'react-dom';

function Modal({ children }: { children: React.ReactNode }) {
  const modalRoot = document.getElementById('modal-root');
  if (!modalRoot) return null;

  return createPortal(
    <div className="modal-overlay">
      <div className="modal">{children}</div>
    </div>,
    modalRoot  // renders into <div id="modal-root">, not inside the React root
  );
}
```

**Step by step:**

1. You need a portal target in `public/index.html` (or equivalent): `<div id="modal-root"></div>` outside the main root.
2. `createPortal(element, container)` takes the JSX to render and the DOM node to render it into.
3. The modal now renders **outside** any `overflow: hidden` parent — so `z-index: 999` works.

> **Remember:** Portals do not break React's tree — they extend it. Events from portaled elements still bubble to the React tree for handling. And in Next.js, you need a guard for SSR (the code above checks `if (!modalRoot) return null` because the DOM doesn't exist on the server).

## Common Mistakes (Review-Specific)

- ❌ Do not come here to re-learn React — this is a quick refresh, not a replacement.
- ❌ Do not import React Router — Next.js has file-based routing built in.
- ❌ Do not sprinkle `useEffect` everywhere — in Server Components, data fetching happens on the server (0.3).
- ❌ Do not use Context or Zustand for server-side data — those are for client-side reactive state.
- ❌ Do not skip `React.memo` for children of frequently-changing parents (Section 14).
- ❌ Do not store DOM references in `useState` — use `useRef` (Section 10).

## In Your Own Words

1. Why does React need `useState` — why is a plain variable not enough?

<details>
<summary>Sample Answer</summary>

**Answer:** A plain variable does not notify React that a value has changed. React only knows to re-render when the state setter function (`setCount`) is called. If you reassign a plain variable, React has no idea the value changed and the UI does not update.

</details>

2. How did React Router handle a dynamic route like `/movies/:id`, and how did you extract the value?

<details>
<summary>Sample Answer</summary>

**Answer:** You defined a route with `path="/movies/:id"` — the `:id` was a placeholder. Then you called `const { id } = useParams()` inside the component to extract the value from the URL. Next.js's equivalent is a dynamic folder `[slug]` and the `params` prop.

</details>

3. What is a "controlled input"?

<details>
<summary>Sample Answer</summary>

**Answer:** The input's value comes from React state (`value={email}`) and is updated via `onChange` (`onChange={(e) => setEmail(e.target.value)}`). React controls the input's value — user types, state updates, value re-renders. The component is "controlled" by React.

</details>

4. In one line, what do Context API and Zustand each do?

<details>
<summary>Sample Answer</summary>

**Answer:** Both share global state across components without prop drilling — Context is built-in (more boilerplate), Zustand is a lightweight library (less boilerplate).

</details>

5. What is the difference between `useRef` and `useState`?

<details>
<summary>Sample Answer</summary>

**Answer:** `useState` stores a value that, when updated, triggers a re-render. `useRef` stores a mutable `.current` value that persists across renders but does **not** trigger a re-render when it changes. Use `useRef` for holding DOM node references; use `useState` for values the UI depends on.

</details>

6. What causes a parent re-render to cascade to children?

<details>
<summary>Sample Answer</summary>

**Answer:** React has no way to know whether a child's output changed without re-running it. When a parent re-renders, React must re-run every child's function (unless `React.memo` is applied). The parent cascade is the #2 re-render trigger (after direct state changes).

</details>

7. How does `createPortal` help with modals?

<details>
<summary>Sample Answer</summary>

**Answer:** Modals often get clipped by a parent with `overflow: hidden` or appear behind other elements due to `z-index` stacking. `createPortal` renders the modal into a DOM node outside the React root (e.g. `<div id="modal-root">`), so it escapes parent constraints and can be positioned freely.

</details>
