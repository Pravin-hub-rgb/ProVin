5.11 mein SQL Todo app ban gayi — reads SC, mutations SA. Par ab tak sab kuch ek hi table mein hai — `drizzle_todos`. Asli apps aisi nahi hoti. **Ek todo ka user hota hai.** Users bhi table mein hain. Todo user se kaise judta hai? Yeh 5.12 ka pehla sawaal — **relations**.

5.12 mein **system design** soch: relations (kaise data aapas mein jude), indexes (data dhoondhna fast), read/write patterns (kaunsa query kab), aur kuch aise scenarios jo abhi simple lage par bade apps mein matter karte hain. **Koi nayi database nahi, koi naya framework nahi** — sochne ka file.

# System Design — Relations, Indexes, Performance Soch

## Step 1 — The Problem: Ek Table Kafi Nahi

**SOCH:** Abhi `drizzle_todos` ek table hai. Kal ek cheez chahiye — **kaunse user ka todo hai**. Tum do users ko ek hi todo list share karwaoge? Nahi — har user ka apna todo list. Data ka structure badal gaya:

- Ek **user** ke multiple **todos** hote hain
- Yeh **1:N (one-to-many) relation** hai — 1 user → N todos

Agar sab ek table mein rakho toh duplicate data banta — har todo ke saath user ka pura naam bhi — user ka naam badla toh saari rows update karni padti. **Data normalise karna padta hai** — alag tables, relation se judi.

## Step 2 — Primary Key Aur Foreign Key

**CONCEPT:** Relation SQL mein **keys** se banta hai. Do keys yaad rakho:

- **Primary Key** — table mein har row ka unique id (5.10 mein `serial('id').primaryKey()` — yahi).
- **Foreign Key** — doosre table ki primary key ka reference — isi se relation banta hai.

**Users table** (nayi — abhi soch rahe hain, koi code nahi):

```
users table
| id (PRIMARY KEY) | name  |
|------------------|-------|
| 1                | Vin   |
| 2                | Riya  |
```

**Todos table** (abhi wali — ek naya column `user_id`):

```
drizzle_todos table
| id (PK) | title         | user_id (FK → users.id) |
|---------|---------------|-------------------------|
| 1       | Homework      | 1                       |
| 2       | Gym           | 1                       |
| 3       | Call          | 2                       |
```

- **`user_id`** — foreign key — "yeh todo kis user ka hai". Todo 1 aur 2 Vin ke (`user_id: 1`), todo 3 Riya ke (`user_id: 2`).
- Relation: **1 user → N todos** (users.id ek baar, drizzle_todos.user_id N baar).

**Yeh kya solve karta hai:** user ka naam ek hi jagah (users table). Badalna hai toh ek row update. Todos mein naam repeat nahi hota — sirf `user_id` number. **Normalised data — no duplication.**

## Step 3 — Query: Relation Se Data Nikalna

**SOCH:** Ab data nikalna hai — "Vin ke saare todos dikhao." Relation se data join hota hai. SQL mein yeh **JOIN** hai.

**CONCEPT (concept file hai — code Drizzle mein 5.13.3 mein detail, abhi idea):** `SELECT * FROM drizzle_todos WHERE user_id = 1` — ek simple filtered query. Par kabhi "Vin + uske todos" saath mein chahiye — tab JOIN:

```sql
SELECT * FROM users JOIN drizzle_todos ON users.id = drizzle_todos.user_id WHERE users.id = 1;
```

**Drizzle mein** yeh `.leftJoin()`/`.innerJoin()` jaise methods se hota hai, ya Drizzle relations (`relations` config) se — Prisma mein relation field bana deta hai (`user: { include: { todos: true } }` — 5.13.4 mein yahi milega). **Abhi bas concept:** relation → keys → JOIN — data dono tables se aata hai.

**1:N ka opposite bhi hota hai** — N:N (many-to-many) — jaise Task Board mein task aur tag — do users ka same task? Nahi, Task Board mein ek user hai, board ka user. N:N ke liye ek **join table** banti hai. **Detail 5.13 mein** jab Prisma schema banayenge. Abhi 1:N hi samajh lo — sabse common relation.

## Step 4 — Indexes: Data Dhoondhna Fast Karna

**SOCH:** Todo app mein ek query — `WHERE user_id = 5`. Data bada ho toh — 10 lakh rows — PostgreSQL pura table padhta hai? **Dhoondhna slow.** Iska solution — **indexes**.

**CONCEPT:** Index = database ki **"book ka index"** jaisi cheez. Table ko hai-hai karke dhoondhne ki jagah, index ko dekho — "user_id 5 kahan hai" — seedha milta hai. Table ke ek ya multiple columns pe index banta hai.

**Drizzle mein:**

```ts
export const todos = pgTable('drizzle_todos', {
  id: serial('id').primaryKey(),
  title: text('title').notNull(),
  user_id: integer('user_id').references(() => users.id),
  done: boolean('done').default(false).notNull(),
}, (table) => ({
  userIdx: index('user_idx').on(table.user_id),
}))
```

- **`.references(() => users.id)`** — foreign key — Drizzle ko batata hai `user_id` users.id ko reference karta hai.
- **`index('user_idx').on(table.user_id)`** — `user_id` pe index — `WHERE user_id = 5` wali queries fast.

**Kya index karta hai:** search time table size ke saath badhta nahi — index use hota hai toh seedha milta hai. **Index kya nahi karta:** har insert/update thoda slow karta hai (index bhi update hota hai). Isliye **sirf wahi columns index karo jo queries mein where/join pe aate hain** — over-indexing bhi problem hai.

**Auto-index:** primary key pe PostgreSQL automatically index bana deta hai — `id` pe query fast by default. Foreign keys pe **manually** index banate hain (upar wala).

## Step 5 — Read vs Write Patterns

Ab data access ke patterns sochte hain — 5.11 mein dono dekhe the (SC read + SA write). Design level pe kya fark padta hai:

- **Read-heavy** (list dikhani hai, details dikhani hain) — Server Components — server pe query, cached render (`revalidatePath`), no client round-trip. Fast + simple. Isliye SC reads default hai.
- **Write-heavy** (form submit, toggle, delete) — Server Actions — direct server function, revalidate ke baad fresh render. **Yahan POST route + fetch unnecessary layer hai** jab data sirf isi app ka hai.
- **When REST actually** — jab data external client consume karega (mobile app, public API, 3rd party integration). Tab URL-based API hi sahi — Server Actions URL nahi dete.

**Ek aur soch — N+1 problem** (interview favourite): ek user ke todos render karte waqt, har todo ke liye alag query? N queries — slow. **JOIN (ya ORM relation include)** se ek query mein sab. 5.13.4 mein Prisma ke saath yahi dikhega.

## Step 6 — Kab Kya Use Karein — Soch Ka Final Shape

| Scenario | Use | Kyun |
|---|---|---|
| Apni app ka UI data (reads) | Server Component + `db.select()` | Server pe query, koi layer nahi |
| Apni app ke forms (writes) | Server Action + `revalidatePath` | Direct server call, no API surface |
| Public API / mobile / 3rd party | REST Route Handler | URL-based, Postman-testable |
| Relation wala data | JOIN / relation include | N+1 se bachta hai, ek query |
| Search/filter query (`WHERE user_id`) | Index | Fast lookup, table scan nahi |
| 1 user → N todos | Foreign key (`user_id`) | Normalised data, no duplication |

**Par ek baat clear karein:** indexes, relations — sab is app ke liye abhi zaroori nahi. **Design yeh samajhna hai ki system grow hone pe kahan problem hogi aur solution kya pattern hai.** Abhi todo app mein seedha `db.select()` thik hai. Aise hi sochne ka habit = system design.

## Nutshell

System design: data aapas mein relations se judta hai (1:N user→todos, foreign key `user_id` references users.id), JOIN ya relation include se saath mein nikalta hai. Indexes search fast karte hain (sirf wahi columns jo where/join pe aate hain). Reads Server Components (server pe query), writes Server Actions (direct), REST sirf jab external clients. N+1 problem — har row ke liye query — JOIN se solve hota hai.

## What It Is NOT

- **Foreign key = "sirf column" nahi.** `user_id` column plus `.references()` relation ko enforce karta hai — galat user_id daal hi nahi sakta (constraint). Sirf column rakhoge toh relation database ko pata hi nahi.
- **Index = "har column pe laga do" nahi.** Index reads fast karta hai par writes slow (index update). Primary key auto-indexed hai, foreign keys manually. Sirf queries jo where/join use karti hain — unke columns pe.
- **JOIN = "dusri table ki query" nahi.** JOIN ek hi query hai jo tables ko key se jodti hai — N+1 (har row ke liye alag query) ka opposite. Pehli baar mein expensive lag sakti hai, par bulk data ke liye sabse efficient.
- **N:N = 1:N ka alag version nahi, alag cheez.** 1:N mein foreign key usi table mein hoti hai. N:N (task↔tag) mein ek **join table** chahiye (dono ids). 5.13 mein detail, par abhi se pata ho alag pattern hai.
- **"System design" = "bade system ka design" nahi.** Yeh sochne ka pattern hai — data structure, queries, performance — kisi bhi size ke app pe. Chhoti app mein simple queries, par soch wahi — "agar grow hua toh?"
