# Postman Testing — REST API Ko Proper Tarike Se Test Karna

## Postman Kya Hai (Pehli Baar)

**Postman** ek **API testing tool** hai — desktop app (ya browser version). Isme tum request banaate ho — method, URL, body — bhejte ho, aur response dekhte ho: status code, headers, JSON body. Aur sab requests **save** rehti hain — ek hi jagah, dobara dobara test karne ke liye.

Kyun Postman, curl nahi? Curl raw terminal hai — har baar poora command type karna padta hai, response formatting nahi hoti, koi history nahi. Postman mein:

- Requests save rehti hain (collection)
- Response readable JSON mein
- Status codes clearly dikhte hain
- Same request dobara bhejna ek click

Download: **https://www.postman.com/downloads/** — desktop app install karo.

## Setup — App Chalao, Project Chalao

1. `npm run dev` — project chalao (Mongo Todo API pe)
2. Postman kholo
3. Ek **new request** banao (New → HTTP Request)

Ab ek-ek endpoint test karte hain — **wahi order jo 5.7 mein banaya**.

## Test 1 — GET /api/todos (List)

**Method:** GET, **URL:** `http://localhost:3000/api/todos`, **Send** click karo.

**Expectation:** 200 OK + todos ka array JSON mein.

**Kya check karna hai:**

- **Status:** `200 OK`
- **Body:** JSON array — `[ { "_id": ..., "title": ..., "done": ... }, ... ]`
- Agar database khali hai toh `[]`

Yeh 5.7 ke "First real todo" jaisa data dikhana chahiye (jo tumne save kiya tha). **200 = GET successful** (5.6 design).

## Test 2 — POST /api/todos (Create)

**Method:** POST, **URL:** `http://localhost:3000/api/todos`.

Body tab mein:

1. **Body** → **raw** select karo
2. Type dropdown mein **JSON** select karo
3. Yeh paste karo:

```json
{
  "title": "Postman se bana todo"
}
```

**Send** karo.

**Expectation:** 201 Created + naya todo JSON mein, jisme **auto-generated `_id`, `done: false`, `createdAt`/`updatedAt`** honge.

**Kya check karna hai:**

- **Status:** `201 Created` — naya resource bana (5.6 design — POST successful = 201)
- **Body:** naya todo — `_id` MongoDB ne banaya, `done` default se false, timestamps aaye

**Yeh response save karo** — `_id` copy karo, agle tests mein chahiye hoga (URL mein).

## Test 3 — Error Case: POST Bina Title

**SOCH:** Ab error handling test karte hain — design (5.6) kehti hai "galat body = 400." Postman mein aise **negative cases** bhi test karte hain, sirf success nahi.

**Method:** POST, **URL:** `http://localhost:3000/api/todos`, **Body:**

```json
{}
```

**Send** karo.

**Expectation:** `400 Bad Request` + `{ "error": "Title dena zaroori hai" }`.

**Kya check karna hai:**

- **Status:** `400` — client ki galti (5.6 design)
- **Body:** error shape consistent — `{ "error": "message" }` (5.6 wala standard)

**Bada point:** Yeh error test isliye important hai kyunki woh design verify karta hai — galat data pe server 500 nahi, **400** deta hai. Client ki galti ko client ko clearly batana chahiye.

## Test 4 — GET /api/todos/[id] (Detail)

Ab single todo test karte hain — dynamic route. 5.7 mein detail GET banaya nahi tha (list GET kafi tha), par REST design mein `GET /api/todos/:id` ek standard endpoint hai — **bahut kam hai, isliye ab add karte hain.** Pehle jaanna hai kaise.

**CONCEPT:** `Todo.findById(id)` — ek document id se. Nahin mila toh null → 404.

**File:** `app/api/todos/[id]/route.ts` — sabse upar GET add karo (PUT/DELETE ke saath):

```ts
// app/api/todos/[id]/route.ts — sabse upar add karo
export async function GET(
  _request: Request,
  context: { params: Promise<{ id: string }> }
) {
  try {
    await connectDB();
    const { id } = await context.params;

    const todo = await Todo.findById(id);

    if (!todo) {
      return NextResponse.json({ error: "Todo nahi mila" }, { status: 404 });
    }

    return NextResponse.json(todo, { status: 200 });
  } catch (error) {
    console.error("Todo fetch error:", error);
    return NextResponse.json({ error: "Todo fetch nahi ho saka" }, { status: 500 });
  }
}
```

`findById(id)` — ek document id se. Galat id → null → 404. Sahi id → 200 + todo.

**Postman mein:**

**Method:** GET, **URL:** `http://localhost:3000/api/todos/<YOUR_ID>` (Test 2 ka `_id`).

**Expectation:** `200` + woh todo JSON mein. Galat id se `404` + `{ "error": "Todo nahi mila" }`.

**Method:** PUT, **URL:** `http://localhost:3000/api/todos/<YOUR_ID>`, **Body:**

```json
{
  "title": "Updated via Postman",
  "done": true
```

**Send** karo.

**Expectation:** `200` + updated todo — `title` "Updated via Postman", `done: true`, `updatedAt` naya.

**Kya check karna hai:**

- **Status:** `200`
- **Body:** `done: true` — update apply hua
- **`updatedAt`:** purana se naya — timestamps ne update record kiya

## Test 6 — DELETE /api/todos/[id] (Delete)

**Method:** DELETE, **URL:** `http://localhost:3000/api/todos/<YOUR_ID>` (Test 2 wala todo).

**Send** karo.

**Expectation:** `200` + `{ "message": "Todo delete ho gaya" }`.

**Verify:** wahi todo ab `/api/todos` mein nahi dikhna chahiye. GET bhejke confirm karo.

## Full CRUD Flow — Test Table

Ek jagah saara record — yeh table har test ka expectation bataata hai. Aage ke projects mein bhi yahi pattern hai.

| Test | Method + URL | Body | Expected |
|---|---|---|---|
| List | `GET /api/todos` | — | `200`, array |
| Create | `POST /api/todos` | `{ title }` | `201`, naya todo |
| Create (error) | `POST /api/todos` | `{}` | `400`, `{ error }` |
| Detail | `GET /api/todos/:id` | — | `200`, todo / `404` |
| Update | `PUT /api/todos/:id` | `{ title, done }` | `200`, updated |
| Delete | `DELETE /api/todos/:id` | — | `200`, message |

## Postman Collections — Ek Baar Save Karo, Hamesha Use Karo

Postman ki power yeh hai ki requests **save** karke collection mein rakho — dobara sab kuch test karne ke liye ek click.

1. **Save** button (request ke paas)
2. **Create new collection** → `Mongo Todo API`
3. Request ko naam do — "List todos", "Create todo", "Create todo (error)", "Update todo", "Delete todo"
4. Save karo

Ab kisi bhi time poora API ek jagah test kar sakte ho — dobara type karna nahi. **Collections API testing ki muscle memory hain.**

## Nutshell

Postman API testing ka tool hai — requests save rehti hain (collections), responses readable hain. CRUD test ka pattern: har endpoint ka **success case** (sahi status code + body) aur **error case** (galat data pe sahi error code + consistent error shape) dono check karo. 400 vs 404, 200 vs 201 — design (5.6) ke hisaab se verify.

## What It Is NOT

- **Postman = sirf "request bhejne ka button" nahi.** Asli value testing methodology mein hai — success + error cases dono systematically check karna, status codes verify karna. Tool sirf medium hai.
- **Postman testing = production testing.** Postman API ke behavior verify karta hai — performance, load, security wahi nahi. Yeh functional testing hai.
- **`GET /api/todos/:id` = optional "extra" nahi.** REST design mein detail endpoint standard hai — client ko single resource chahiye toh yehi use hota hai. 5.7 mein deliberately later add kiya (gradual), par design ka hissa hai.
- **400 = server ka bura behavior nahi.** 400 matlab server ne client ko sahi tarike se bataya ki kya galat hai — yeh **good design** hai. 500 (jo bina validation ke aata) wo problem hai.
- **Postman sirf backend developers ke liye nahi.** Frontend developer ko bhi API ke behavior ke saath kaam karna hai — Postman se pehle samajh aata hai API kya karegi, phir code.
