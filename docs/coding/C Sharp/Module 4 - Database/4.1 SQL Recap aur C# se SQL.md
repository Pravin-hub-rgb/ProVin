# SQL Crash Recap + SQL from C#

## SQL — back in 5 minutes

Quick revision of the DBMS course (the detail is there):

```sql
-- Create a table
CREATE TABLE Students (
    Id INT PRIMARY KEY IDENTITY(1,1),
    Name NVARCHAR(100),
    Marks INT
);

-- Insert data
INSERT INTO Students (Name, Marks) VALUES ('Vin', 90);

-- Read
SELECT Name, Marks FROM Students WHERE Marks >= 80;

-- Update
UPDATE Students SET Marks = 95 WHERE Name = 'Vin';

-- Delete
DELETE FROM Students WHERE Name = 'Old';
```

5 commands — **INSERT, SELECT, UPDATE, DELETE** (CRUD) + `CREATE`. These run every day. Joins/aggregates are covered in detail in the DBMS course — pick them up from there.

One thing tied to the DB — **IDENTITY(1,1)** means: Id keeps increasing on its own (1, 2, 3...) — this same value lands in the C# object's `Id`, no need to set it manually.

## C# to database — three ways (and why we'll choose EF)

**Way 1: ADO.NET (raw SQL)** — the oldest, most direct:

```csharp
// Pseudo-structure — for understanding
using (var conn = new SqlConnection(connectionString))
{
    await conn.OpenAsync();
    var cmd = new SqlCommand("SELECT Name FROM Students WHERE Marks >= @min", conn);
    cmd.Parameters.AddWithValue("@min", 80);       // ⭐ parameterized
    var reader = await cmd.ExecuteReaderAsync();
    while (await reader.ReadAsync())
        Console.WriteLine(reader.GetString(0));
}
```

This code still runs today, but there's so much boilerplate for every query. And notice **`@min`**:

```csharp
// ❌ Never do this — SQL INJECTION
string name = userInput;
var cmd = new SqlCommand("SELECT * FROM Users WHERE Name = '" + name + "'", conn);
```

If the user typed `' OR '1'='1`, the query breaks — all records leak. **That's why always use a parameterized query** (`@name` + `Parameters.AddWithValue`) — parameters treat the value as data, not code. This is a fundamental security rule.

**Way 2: Dapper** — a small wrapper over raw SQL, for small tasks.

**Way 3: Entity Framework Core (EF Core)** — .NET's own **ORM** (Object-Relational Mapper): it handles the mapping between C# class ↔ DB table itself. **Most real-world projects today are built with this** — so the detail is here.

```csharp
// EF Core style — you don't write SQL at all
var toppers = await db.Students
    .Where(s => s.Marks >= 80)     // ← LINQ! from module 3
    .OrderBy(s => s.Marks)
    .ToListAsync();
```

See? **LINQ itself becomes SQL.** `Where → WHERE`, `OrderBy → ORDER BY`, `Select → SELECT`. Module 3's LINQ comes in handy right here.

## SQL and C# type mapping

DB and C# both have different names for types:

| SQL | C# |
|---|---|
| INT | `int` |
| NVARCHAR(100) | `string` |
| BIT | `bool` |
| DECIMAL(18,2) | `decimal` (for money — not double!) |
| DATETIME2 | `DateTime` |
| NULL-able INT | `int?` |

**Use `decimal` for money** — `double` makes floating-point errors (the 0.1 + 0.2 pain). In banking/accounting code only `decimal` is used — for money it's the default.

## What this is NOT

- **EF Core ≠ a database** — EF Core is the driver/mapper, the database is separate (SQL Server/PostgreSQL/SQLite). Like React is the UI and the backend is separate.
- **No queries via string concatenation** — SQL injection. Always parameters/EF.
- **Program stops ≠ data gone** — DB is on disk (no JSON-file pain). Program stops, data stays — that's the whole point of a DB.
- **`double` ≠ money** — use `decimal`.

## In Your Own Words

1. What is SQL injection and how do you prevent it in C#?

<details>
<summary>Sample Answer</summary>

**Answer:** Joining user input into the query string, which can break/alter the query (`' OR '1'='1`). Prevention: parameterized queries (`@name` + `AddWithValue`) — the value is treated as data, not code. In EF Core, parameterization happens automatically.

</details>

2. Why is an ORM (Entity Framework) different from raw SQL — name one advantage.

<details>
<summary>Sample Answer</summary>

**Answer:** The ORM handles the mapping between C# class and DB table itself — you don't write SQL, you work with LINQ/objects (`db.Students.Where(...)`). Advantage: no SQL to write, refactoring is safe, type-safe — changes are caught at compile time.

</details>

3. For a money (salary/price) column, which C# type and why not `double`?

<details>
<summary>Sample Answer</summary>

**Answer:** `decimal` — because double makes floating-point rounding errors (0.1+0.2 = 0.30000000000000004), which can create a 1-paisa error in money. `decimal` is exact fixed-point — designed for banking/DB (DECIMAL/NUMERIC) use.

</details>

4. What's the relationship between SQL's `IDENTITY(1,1)` and the `Id` field of a C# object?

<details>
<summary>Sample Answer</summary>

**Answer:** IDENTITY means the DB auto-increments the Id (1, 2, 3...) when a new row is inserted. In EF Core you just fill the object and insert — the DB auto-generates the Id and that same value comes back into the object's Id property (no need to assign it yourself).

</details>
