## MCQ

Q: What's the right way to prevent SQL injection?
A. Keep user input short
B. Concatenate input into the query string with quotes
C. Use a parameterized query (`@name` + parameters) or EF Core
D. Turn off error messages
> C. String concatenation (`"...Name = '" + input + "'"`) lets the user break the query. In a parameterized query the value is treated as data, not code — EF Core creates parameters automatically. This is the real protection.

---

Q: What does an ORM (Entity Framework) do?
A. Installs the database
B. Maps C# objects to database tables — converts LINQ to SQL and sends it to the DB
C. Renders HTML
D. Compiles code
> B. Object-Relational Mapper — converts a LINQ query like `db.Students.Where(...)` into SQL, sends it to the DB, and turns the rows back into C# objects. No need for you to write SQL.

---

Q: What happens in the DB after `db.Students.Add(student)`?
A. The row is inserted
B. Nothing — the INSERT goes to the DB only when you call `SaveChangesAsync()`
C. The table is created
D. The program crashes
> B. EF only tracks changes in memory in the change tracker. The pending changes go to the DB as SQL only on `SaveChanges()`/`SaveChangesAsync()` (in a transaction). Add = intent, Save = commit.

Q: For money (salary/price), which C# type — and why not `double`?
A. `double` is best
B. `float`
C. `decimal` — doesn't make floating-point rounding errors
D. `int`
> C. Double gives errors like 0.1+0.2 = 0.300000000000004, which can create a 1-paisa difference in money. `decimal` is exact fixed-point — that's why money columns use DECIMAL + C# decimal.

Q: What does `.Include(x => x.Class)` do in EF Core?
A. Deletes the class
B. Loads related data (SQL JOIN) — without it `student.Class` would be null
C. Creates a new table
D. Loads config
> B. Eagerly loads the navigation property — a JOIN is generated in SQL and the related table's data comes along. Without Include, EF doesn't fetch related data on its own (null), so unnecessary queries don't run.

Q: In a real project, where should the connection string be?
A. String literal in `Program.cs`
B. In `appsettings.json`, with real secrets in `user-secrets`/env vars
C. Hardcoded comment
D. Copied into every file
> B. Keep it in the config file (it changes), and put secrets in `dotnet user-secrets` or environment variables — because appsettings.json goes into git. Never put passwords in code/config.

---

Q: What happens with `dotnet ef migrations add X` and `dotnet ef database update`?
A. Package install
B. A migration file is created (schema diff), then update applies it to the DB
C. Server restart
D. Code format
> B. Migrations = version control for DB schema. On `add`, EF looks at your model changes and creates a migration file; on `database update` it executes on the DB (CREATE TABLE/ALTER COLUMN). Like git, but for the database.

## TrueFalse

Q: EF Core loads the whole table into memory when you add `Where()`, then filters.
- True
- False
> False. With `Where()`, a `WHERE` is generated in SQL and filtering happens on the DB — only matching rows come into memory. EF sends the query (translated) to the DB thoughtfully.

---

Q: You should write the password in `appsettings.json` because that file is safe in git.
- True
- False
> False. `appsettings.json` goes into git — no secrets there. Secrets go in `user-secrets` (local) or environment variables (server), which stay outside git.

---

Q: With an `IDENTITY(1,1)` column, the DB auto-increments the Id on a new row, and EF Core brings that same value into the object's `Id` property.
- True
- False
> True. The DB auto-increments the Id; after `SaveChanges`, EF sets the newly generated Id back into your object — your C# code doesn't have to assign the Id.

---

Q: `EnsureCreated()` is a full replacement for migrations in real projects — you should use it even when the schema changes.
- True
- False
> False. `EnsureCreated` only creates tables the first time; it doesn't handle later schema changes (new column). Real projects use migrations — version-controlled changes applied via `database update`.

---

Q: The `decimal` type is specifically recommended for finance/money because it keeps exact values.
- True
- False
> True. Floating-point (float/double) makes rounding errors — wrong money. `decimal` is exact fixed-point — that's why SQL DECIMAL columns pair with C# decimal (banking standard).
