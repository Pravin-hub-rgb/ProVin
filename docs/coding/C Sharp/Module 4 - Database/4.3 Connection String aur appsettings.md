In the last file we wrote the connection string directly in code: `UseSqlite("Data Source=school.db")`. But in a real project that's where **passwords and server addresses** go — write them in code and they go into git for everyone to see. In the JS world this was `.env` — in C#/.NET the same job is done by **`appsettings.json`**.

# Connection String and appsettings.json

## The problem — config doesn't belong in code

```csharp
// ❌ This is not how production code looks
.UseSqlServer("Server=prod-db.company.com;Database=App;Password=Secret123")
```

Push to git → the whole world gets the password. And if the server changes, you change code, recompile, redeploy — painful. **That's why config goes in a separate file, and code only reads it.**

JS comparison:

```javascript
// JS — .env
DB_URL=postgres://...
console.log(process.env.DB_URL)     // code only reads
```
```jsonc
// C# — appsettings.json
{
  "ConnectionStrings": {
    "Default": "Server=...;Database=..."
  }
}
```

Difference: `.env` was plain key=value text, here it's a **JSON** file — and .NET even turns it into strongly-typed settings.

## appsettings.json — the project's config envelope

Every .NET web project has it (at the root):

```json
{
  "Logging": {
    "LogLevel": { "Default": "Information" }
  },
  "ConnectionStrings": {
    "SchoolDb": "Data Source=school.db"
  },
  "Jwt": {
    "Secret": "this-is-a-secret-key",
    "ExpiryMinutes": 60
  }
}
```

A section for each thing — logging, DB, auth. **This file goes into git** (secrets are separate — ahead).

## Reading from code — the Options pattern (standard way)

**Way 1 (small, for scripts/apps):**

```csharp
using Microsoft.Extensions.Configuration;

var config = new ConfigurationBuilder()
    .SetBasePath(AppContext.BaseDirectory)
    .AddJsonFile("appsettings.json", optional: false)
    .Build();

string conn = config.GetConnectionString("SchoolDb");   // value from the section
```

`GetConnectionString("SchoolDb")` — pulls the value from the `ConnectionStrings` section.

**Way 2 (ASP.NET Core — used in module 5):** config is available automatically, and in `Program.cs`:

```csharp
builder.Services.AddDbContext<SchoolDb>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("SchoolDb")));
```

`builder.Configuration` = the same `appsettings.json` reader, running with the request. For now just understand this — **code doesn't know the connection string, config provides it.**

## Secrets — the real password stuff

If the connection string has a password, don't put `appsettings.json` into git. .NET's tool:

```bash
dotnet user-secrets init                              // turn on the project secret vault
dotnet user-secrets set "ConnectionStrings:SchoolDb" "Server=...;Password=RealPass"
```

These values live in `secrets.json` — **never go into git**. Every developer has their own on their dev machine. In production the connection string comes from an **environment variable** (set on the server) — .NET picks up both (`user-secrets`, env vars) automatically through `builder.Configuration`.

**Understand the layers:**

```
Production:  env var (server)     ─┐
Dev:         user-secrets         ─┼→  builder.Configuration  →  code
Default:     appsettings.json     ─┘
```

The higher one wins. Code doesn't change — only config changes.

## Project anatomy — understand the folder structure

In a small `dotnet new console` everything was in one place. In a real web project:

```
MyApp/
├── Program.cs              ← entry point (now small — startup is here)
├── appsettings.json        ← config
├── Controllers/ or Endpoints/  ← API routes (module 5)
├── Models/ or Data/        ← classes (Student, DbContext)
├── MyApp.csproj             ← project file (like package.json)
└── obj/ bin/
```

The naming conventions already look C#-ish — `Models/`, `Services/`, `Controllers/`. `.csproj` has the packages:

```xml
<Project Sdk="Microsoft.NET.Sdk.Web">
  <ItemGroup>
    <PackageReference Include="Microsoft.EntityFrameworkCore.SqlServer" Version="8.0.0" />
  </ItemGroup>
</Project>
```

`<PackageReference>` = the `dependencies` part of package.json. `dotnet add package` adds it here itself. **NuGet = npm, .csproj = package.json.**

## A complete example — config + EF

```json
// appsettings.json
{
  "ConnectionStrings": {
    "SchoolDb": "Data Source=school.db"
  }
}
```

```csharp
// Program.cs
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;

var config = new ConfigurationBuilder()
    .SetBasePath(Directory.GetCurrentDirectory())
    .AddJsonFile("appsettings.json")
    .Build();

var options = new DbContextOptionsBuilder<SchoolDb>()
    .UseSqlite(config.GetConnectionString("SchoolDb"))   // from config!
    .Options;

using var db = new SchoolDb(options);
db.Database.EnsureCreated();
Console.WriteLine("DB connected: " + db.Students.Count());
```

Now the connection string is **outside the code** — if you need to change it, just fix the JSON file, no C# recompile.

> To avoid path issues on the server (Linux), production prefers `SetBasePath(AppContext.BaseDirectory)` — for now the above works.

## What this is NOT

- **`appsettings.json` ≠ a secret file like `.env`** — it goes into git. Only necessary config in `appsettings.json`; secrets go in `user-secrets` or env vars.
- **Config file is still hardcoded** — the difference is it's **changeable** (no code recompile) and different values can exist in different places (dev/prod).
- **Not a separate NConfig library** — `Microsoft.Extensions.Configuration` is built into .NET, nothing extra to install (web projects get it anyway).

## In Your Own Words

1. Why keep the connection string in `appsettings.json` instead of code — 2 reasons?

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Security — code goes into git, passwords shouldn't be there; secrets can be kept separate (user-secrets). (2) Flexibility — if the server changes, just change the config, no code recompile/redeploy. Dev and prod can have different values.

</details>

2. What are the 3 layers of .NET configuration and which higher one wins?

<details>
<summary>Sample Answer</summary>

**Answer:** appsettings.json (default), user-secrets (dev local), environment variable (production server). The higher layer overrides — if an env var is set, that value is used, otherwise user-secrets, otherwise appsettings.json. Code always reads through `builder.Configuration`.

</details>

3. What's the relationship between a NuGet package and `<PackageReference>` in `.csproj` — compare with JS.

<details>
<summary>Sample Answer</summary>

**Answer:** NuGet = npm registry, `dotnet add package X` = `npm install X`, and `.csproj`'s `<PackageReference Include="X" Version="...">` = the dependencies entry in package.json. When you open the project, .NET restores the packages on its own (like npm install).

</details>

4. Why the `Controllers/`, `Models/` folder structure — why not everything in Program.cs?

<details>
<summary>Sample Answer</summary>

**Answer:** If everything (routes, data, logic) is in one file, it gets hard to manage as it grows. C# projects keep each concern separate (models separate, routes separate, services separate) — easier to read, easier team work (fewer conflicts), and easier to test. Namespace + folders keep the code organized.

</details>
