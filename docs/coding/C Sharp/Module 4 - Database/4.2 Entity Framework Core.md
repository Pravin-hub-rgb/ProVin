In the last file we decided — instead of raw SQL, **EF Core**. Now the real work: write a C# class and it becomes a DB table on its own; write LINQ and it runs as SQL in the DB. This is the magic of an ORM — and module 3's LINQ now applies directly to the database.

# Entity Framework Core (EF Core)

## What EF Core is — an analogy

**EF Core = a translator.** On one side is your C# world (classes, objects, LINQ), on the other is the database world (tables, rows, SQL). You speak in C#, it explains it to the DB in SQL, and brings the result back as C# objects.

```
You (C# + LINQ)  ←→  EF Core (translator)  ←→  DB (SQL tables)
db.Students.Where(...)   →   SELECT * FROM Students WHERE ...
```

**ORM = Object-Relational Mapper** — this is the term, remember it.

## 4 operations (CRUD) — in one file

```csharp
// Model — this class becomes a DB table
class Student
{
    public int Id { get; set; }          // PK (naming convention: Id)
    public string Name { get; set; }
    public int Marks { get; set; }
}

// Context — "the door that connects to the DB"
class SchoolDb : DbContext
{
    public SchoolDb(DbContextOptions<SchoolDb> options) : base(options) { }
    public DbSet<Student> Students { get; set; }    // ← table handle
}

// --- CRUD ---
// CREATE
db.Students.Add(new Student { Name = "Vin", Marks = 90 });
await db.SaveChangesAsync();       // ❗ only here does it reach the DB

// READ
List<Student> all = await db.Students.ToListAsync();
Student one = await db.Students.FindAsync(1);          // by Id
var top = await db.Students.Where(s => s.Marks >= 80)
                           .OrderByDescending(s => s.Marks)
                           .ToListAsync();

// UPDATE
Student s = await db.Students.FindAsync(1);
s.Marks = 95;                       // property changed
await db.SaveChangesAsync();        // UPDATE runs in the DB

// DELETE
db.Students.Remove(s);
await db.SaveChangesAsync();        // DELETE runs
```

**Golden rule: without `SaveChangesAsync()` nothing reaches the DB.** `Add`/`Remove`/property-change only get tracked in memory — on save, EF sends the SQL at once (in a transaction).

## Install — NuGet packages

EF Core is **not in the BCL**, it comes from **NuGet** (Nuget = npm for C#):

```bash
# In the terminal (from the project folder)
dotnet add package Microsoft.EntityFrameworkCore
dotnet add package Microsoft.EntityFrameworkCore.SqlServer   # for SQL Server
# For practice:
dotnet add package Microsoft.EntityFrameworkCore.Sqlite      # SQLite (file-based)
```

`npm install` kind of feel — just the name `dotnet add package`. It gets added to `.csproj`.

## Program.cs — first working setup (SQLite practice)

```csharp
// Program.cs
using Microsoft.EntityFrameworkCore;

class Student
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int Marks { get; set; }
}

class SchoolDb : DbContext
{
    // where the connection comes from — from Program.cs
    public DbSet<Student> Students => Set<Student>();
}

class Program
{
    static void Main()
    {
        // SQLite file-based DB — easiest for practice
        var options = new DbContextOptionsBuilder<SchoolDb>()
            .UseSqlite("Data Source=school.db")
            .Options;

        using var db = new SchoolDb(options);
        db.Database.EnsureCreated();     // create table if it doesn't exist

        // CREATE
        db.Students.Add(new Student { Name = "Vin", Marks = 90 });
        db.Students.Add(new Student { Name = "Rahul", Marks = 85 });
        db.SaveChanges();                // sync version — fine in a simple program

        // READ (LINQ)
        var top = db.Students.Where(s => s.Marks >= 88)
                             .OrderByDescending(s => s.Marks)
                             .ToList();

        foreach (var s in top)
            Console.WriteLine($"{s.Name}: {s.Marks}");

        // UPDATE
        var vin = db.Students.First(s => s.Name == "Vin");
        vin.Marks = 95;
        db.SaveChanges();

        Console.WriteLine("Total: " + db.Students.Count());
    }
}
```

`dotnet run` → a file `school.db` is created — table + data inside. **C# class → DB table, LINQ → SQL — without writing SQL.**

## Migrations — the way to change tables

`EnsureCreated()` is fine for small practice, but in a real project the schema **keeps changing** (adding an `Email` column later). That's **migrations** — version-controlled schema changes:

```bash
dotnet tool install --global dotnet-ef     # once
dotnet ef migrations add InitialCreate     # create the migration (like a code diff)
dotnet ef database update                  # apply to the DB
```

Flow: change the model class → `migrations add Name` (EF figures out the diff itself) → `database update` (column added in the DB). **Like git, but for the database** — full history stays. This is what runs in team projects.

If the connection string is in `appsettings.json` (next file), the commands are:

```bash
dotnet ef migrations add InitialCreate --startup-project .
```

## Relationships — one table to another (like real DB)

```csharp
class Student
{
    public int Id { get; set; }
    public string Name { get; set; }
    public int ClassId { get; set; }          // FK
    public SchoolClass Class { get; set; }    // navigation — the class they belong to
}

class SchoolClass
{
    public int Id { get; set; }
    public string Title { get; set; }
    public List<Student> Students { get; set; } = new();   // students of that class
}
```

- `ClassId` = **Foreign Key** (the same as in SQL)
- `Class` / `Students` = **navigation property** — to move around the object graph

And the magic — **eager loading** (like JS `include`):

```csharp
var s = await db.Students
    .Include(x => x.Class)      // ⭐ fetch class along (JOIN)
    .FirstOrDefaultAsync(x => x.Id == 1);

Console.WriteLine(s.Class.Title);   // data ready without another query
```

Without `Include`, `s.Class` would be null (EF didn't know). `Include = JOIN` — real SQL underneath.

## What this is NOT

- **`Add()` doesn't hit the DB immediately** — only tracked. `SaveChangesAsync()` is the commit (for those who don't use async, sync `SaveChanges` works too).
- **EF doesn't load all rows on every query** — with `.Where()`, a SQL `WHERE` is generated and filtering happens on the DB; the whole table never comes into memory (lazy = SQL goes thoughtfully).
- **`EnsureCreated` ≠ migration** — migration is the normal work; EnsureCreated doesn't handle later changes. Fine for small practice.
- **Navigation property ≠ DB column** — `public SchoolClass Class` creates no column, it's only EF's link; the `ClassId` column is what gets created.

## In Your Own Words

1. What is an ORM — between which two worlds does EF Core act as a translator?

<details>
<summary>Sample Answer</summary>

**Answer:** ORM (Object-Relational Mapper) handles the mapping between C# objects and database tables. EF Core converts your C# + LINQ into SQL for the DB, and turns rows back into C# objects — you don't write SQL at all.

</details>

2. What happens right after `db.Students.Add(x)` — when does the commit happen?

<details>
<summary>Sample Answer</summary>

**Answer:** Nothing happens on Add — EF only tracks the change in memory. On `SaveChangesAsync()` call, all pending changes go to the DB together as SQL (INSERT/UPDATE/DELETE), inside a transaction.

</details>

3. Why is `.Include(x => x.Class)` necessary — what happens without it?

<details>
<summary>Sample Answer</summary>

**Answer:** Include loads related data (SQL JOIN). Without it, `student.Class` is null — EF only fetches from the related table when you explicitly ask. This also prevents suddenly loading too much data.

</details>

4. Migrations vs `EnsureCreated()` — which one in a real project and why?

<details>
<summary>Sample Answer</summary>

**Answer:** Migrations — because the schema keeps growing in a project. A migration is a version-controlled schema change (`migrations add` creates the diff, `database update` applies it). `EnsureCreated` only creates tables the first time and doesn't handle later changes — fine for practice, not for production.

</details>
