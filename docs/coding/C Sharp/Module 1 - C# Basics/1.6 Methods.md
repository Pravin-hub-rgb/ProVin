In the previous file's report-card program you saw — the loop to find the total, the work to find the average, everything piled up in one place. As programs grow, `Program.cs` becomes one long khichdi. In JS we managed this with functions — in C# the same job, just a different name: **methods**.

# Methods (Functions)

## Making a method — JS vs C#

In JS:

```javascript
function namaste(naam) {
  return "Hello " + naam;
}
console.log(namaste("Vin"));
```

In C#:

```csharp
string Namaste(string naam)
{
    return "Hello " + naam;
}

Console.WriteLine(Namaste("Vin"));
```

Understand the pattern — instead of JS you now have to write **4 things**:

```csharp
ReturnType MethodName(parameters)
{
    // work
    return value;
}
```

1. **Return type** — what the method will return (`string`, `int`, `void` if nothing)
2. **Name** — in C# a method's name is **PascalCase** (`Namaste`, `GetTotal`) — in JS it was `camelCase`. The convention is strict; the IDE will auto-write it this way too
3. **Parameters** — `(string naam)` — every param's type must be written
4. **`return`** — same as before

> In C#, functions are called **methods** (they live inside a class — module 2). When speaking, just say "method" — that's the word used in C#.

## void — the one that returns nothing

```csharp
void Namaste(string naam)      // return type void
{
    Console.WriteLine("Hello " + naam);
    // no return needed — we're giving nothing back
}
```

In JS a function implicitly returned `undefined`. In C# you **must write `void` explicitly** — "this method returns nothing". And if you wrote `void`, then `return "kuch";` gives an error.

One-line methods (C# 10+ shorthands):

```csharp
int Add(int a, int b) => a + b;    // expression body — return is implicit
void Hi() => Console.WriteLine("Hi");
```

`=>` (fat arrow) — the JS arrow function feel, just the return type written outside.

## Parameters vs arguments

```csharp
int Multiply(int a, int b)   // these are PARAMETERS (names)
{
    return a * b;
}

Multiply(4, 5);              // these are ARGUMENTS (actual values)
```

That's all — both words come up, know the difference.

## Default parameters and named arguments — JS-style convenience

```csharp
void Greet(string naam, string salutation = "Namaste")   // = "..." = default
{
    Console.WriteLine(salutation + " " + naam);
}

Greet("Vin");                    // Namaste Vin — default used
Greet("Vin", "Hello");           // Hello Vin — override
Greet("Vin", salutation: "Hey"); // named — order doesn't matter
```

`salutation = "Ji"` — just like JS's `function greet(naam, sal = "Ji")`. Default ones must come **at the end** (required first, then default).

## out — returning more than one value

In JS you sometimes returned an array/object to "manage two values". C# has **`out`**:

```csharp
void Divide(int a, int b, out int result, out int remainder)
{
    result = a / b;
    remainder = a % b;
}

Divide(17, 5, out int quotient, out int rem);   // 3, 2
Console.WriteLine($"{quotient} remainder {rem}");
```

An `out` parameter means — the method **fills it in**. When calling you have to write `out` again (or declare directly with `out int x`). Feels weird the first time, but sometimes you need to return 2 related values (like `int.TryParse` did earlier — success + number both).

## Ref — working on the reference (optional)

```csharp
void Increment(ref int n)
{
    n = n + 1;    // the real variable is changing
}

int count = 5;
Increment(ref count);   // count is now 6 — the change shows
```

`ref` = not a copy of the value, but a **reference to the real variable**. Difference from `out`: with `out` the method must assign a value; with `ref` both sides can work. Used rarely in basics — know it, not daily.

## Recursive — calling yourself

```csharp
int Factorial(int n)
{
    if (n <= 1) return 1;         // base case — stop here
    return n * Factorial(n - 1);  // calling itself
}

Console.WriteLine(Factorial(5));   // 120
```

`5 * 4 * 3 * 2 * 1 = 120`. Same logic as JS. The **base case is essential** — otherwise stack overflow (in C# too, `StackOverflowException`).

## Early return — ending the pain of nested ifs

In module 3's conditions I left nested ifs — here's the solution with functions:

```csharp
// ❌ Deep nested if — hard to read
void Process(int umar, bool loggedIn)
{
    if (loggedIn)
    {
        if (umar >= 18)
        {
            Console.WriteLine("Chalega");
        }
    }
}

// ✅ Early return — first chase away the wrong cases
void Process(int umar, bool loggedIn)
{
    if (!loggedIn) { Console.WriteLine("Login karo"); return; }
    if (umar < 18)  { Console.WriteLine("Bachcha"); return; }

    Console.WriteLine("Chalega");   // clean last line
}
```

After every guard clause (`if (...) return;`), the function gets shorter and cleaner. This is the most common pattern in production code — it's called "early return".

## Scope — JS's `{}`

```csharp
int x = 10;
if (true)
{
    int y = 20;
    Console.WriteLine(x + y);   // ✅ the outer one is visible inside
}
Console.WriteLine(y);           // ❌ y doesn't go outside — error
```

This is JS's block scope (`let`/`const`-style). Made inside, gone outside. Variables inside a function don't go outside the function.

## One complete program — everything in methods

```csharp
// Program.cs
int ReadNumber(string prompt)
{
    Console.Write(prompt);
    return int.Parse(Console.ReadLine());
}

int Sum(List<int> numbers)
{
    int total = 0;
    foreach (int n in numbers) total += n;
    return total;
}

double Average(List<int> numbers)
{
    if (numbers.Count == 0) return 0;      // guard — don't divide by 0
    return (double)Sum(numbers) / numbers.Count;   // reuse the other method!
}

void Report(List<int> numbers)
{
    Console.WriteLine($"Count: {numbers.Count}");
    Console.WriteLine($"Sum: {Sum(numbers)}");
    Console.WriteLine($"Avg: {Average(numbers):F2}");
}

// --- the real program (3 lines) ---
List<int> marks = new List<int>();
int n = ReadNumber("Kitne marks: ");
for (int i = 0; i < n; i++) marks.Add(ReadNumber($"Mark {i + 1}: "));
Report(marks);
```

See what happened — input's job in one method, maths in a method, report in a method, and the **real program is only 3 lines**. `Average` called `Sum` (methods can use each other). This is the structure in big codebases — all long code breaks into small-small methods.

What this is NOT:

- **Method name isn't camelCase like JS** — in C# method/class are PascalCase (`GetTotal`), parameters are camelCase (`firstNumber`). Follow the convention; the IDE expects it too.
- **`void` ones have no return value** — `return 5;` is an error. And a non-void method must have a return on every path (the compiler checks).
- **Functions don't "accept anything"** — every parameter's type is fixed. Unlike JS, you can't pass anything (number or string) into one parameter.

## In Your Own Words

1. Name four structural differences between a JS function and a C# method.

<details>
<summary>Sample Answer</summary>

**Answer:** (1) You must write the return type (`void` if nothing), (2) the name is PascalCase, (3) every parameter's type is mandatory, (4) no implicit undefined — `return`/`void` must be explicit. Arrow functions exist too (`=>`) but the return type is still written outside.

</details>

2. In which scene is the `out` parameter useful — explain with the `int.TryParse` example.

<details>
<summary>Sample Answer</summary>

**Answer:** When you need to return more than one related value. `int.TryParse("42", out int n)` gives two things — success (bool) in the direct return, and the parsed number through `out n`. The method "fills in" the value.

</details>

3. What is the "early return" pattern and why use it?

<details>
<summary>Sample Answer</summary>

**Answer:** Returning immediately on wrong/early conditions, so the rest of the work isn't nested. `if (!loggedIn) return;` — the code after only runs when everything is right. This makes code shorter, easier to read, and with fewer bugs.

</details>

4. Why did the `Average` method call `Sum` — what's the benefit?

<details>
<summary>Sample Answer</summary>

**Answer:** The total logic is written in one place (`Sum`), and it's useful in two places — average is built from it. No duplicate code (DRY), and if the total logic changes, you only change one place.

</details>
