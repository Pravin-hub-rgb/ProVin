# CRUD Endpoints — BookController

## Pehle DTOs (5.2 wala rule — ab project mein)

`Models/BookDtos.cs`:

```csharp
namespace LibraryApi.Models;

// Client se aane wala (POST/PUT)
public record CreateBookDto(
    string Title,
    string Author,
    string? Genre,
    decimal Price,
    int Available
);

// Bahar jaane wala (response)
public record BookDto(int Id, string Title, string Author, string? Genre, decimal Price, int Available);
```

> Validation attributes Model (`Book`) pe lage hue hain (6.1) — `[ApiController]` unhe DTO pe bhi check karta hai jab tak types match karti hain. Extra safety ke liye DTO pe bhi laga sakte ho, project mein Model wale kaafi hain.

## Controller — poora CRUD

`Controllers/BooksController.cs`:

```csharp
using LibraryApi.Data;
using LibraryApi.Models;
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;

namespace LibraryApi.Controllers;

[ApiController]
[Route("api/books")]           // /api/books — "Books" controller ka default [controller] trick bhi chalega
public class BooksController : ControllerBase
{
    private readonly LibraryDbContext _db;

    public BooksController(LibraryDbContext db)   // DI — 5.2 wala
    {
        _db = db;
    }

    // GET /api/books
    [HttpGet]
    public async Task<IActionResult> GetAll()
    {
        var books = await _db.Books
            .OrderBy(b => b.Title)
            .Select(b => new BookDto(b.Id, b.Title, b.Author, b.Genre, b.Price, b.Available))
            .ToListAsync();

        return Ok(books);
    }

    // GET /api/books/5
    [HttpGet("{id:int}")]       // constraint: sirf number
    public async Task<IActionResult> GetById(int id)
    {
        var book = await _db.Books.FindAsync(id);
        if (book is null) return NotFound(new { error = "Book not found" });

        return Ok(new BookDto(book.Id, book.Title, book.Author, book.Genre, book.Price, book.Available));
    }

    // POST /api/books
    [HttpPost]
    public async Task<IActionResult> Create(CreateBookDto dto)
    {
        var book = new Book
        {
            Title = dto.Title,
            Author = dto.Author,
            Genre = dto.Genre,
            Price = dto.Price,
            Available = dto.Available
        };

        _db.Books.Add(book);
        await dbSave();          // neeche helper — agla point

        var outDto = new BookDto(book.Id, book.Title, book.Author, book.Genre, book.Price, book.Available);
        return CreatedAtAction(nameof(GetById), new { id = book.Id }, outDto);   // 201
    }

    // PUT /api/books/5
    [HttpPut("{id:int}")]
    public async Task<IActionResult> Update(int id, CreateBookDto dto)
    {
        var book = await _db.Books.FindAsync(id);
        if (book is null) return NotFound(new { error = "Book not found" });

        book.Title = dto.Title;          // fields update (EF change tracker pakad lega)
        book.Author = dto.Author;
        book.Genre = dto.Genre;
        book.Price = dto.Price;
        book.Available = dto.Available;

        await dbSave();
        return Ok(new BookDto(book.Id, book.Title, book.Author, book.Genre, book.Price, book.Available));
    }

    // DELETE /api/books/5
    [HttpDelete("{id:int}")]
    public async Task<IActionResult> Delete(int id)
    {
        var book = await _db.Books.FindAsync(id);
        if (book is null) return NotFound(new { error = "Book not found" });

        _db.Books.Remove(book);
        await dbSave();
        return NoContent();              // 204 — kuch nahi wapas, kaam ho gaya
    }

    private async Task dbSave()
    {
        try
        {
            await _db.SaveChangesAsync();
        }
        catch (DbUpdateException ex)
        {
            // DB level galti (constraint waghera)
            Console.WriteLine(ex.Message);
            throw;   // middleware 500 de dega (5.3 wala)
        }
    }
}
```

**Har endpoint ka pattern same hai** (yaad rakhne wala formula):

```
[HttpMethod("{params}")] → DbContext se dhoondho → null? NotFound → kaam karo → SaveChanges → status ke saath response
```

Status codes ka khel:

| Situation | Response |
|---|---|
| GET mil gaya | `200 Ok` + data |
| GET/PUT/DELETE nahi mila | `404 NotFound` |
| POST bana | `201 Created` + Location header |
| PUT/DELETE ho gaya | `200 Ok` / `204 NoContent` |
| Validation fail | `400 BadRequest` (auto) |

`CreatedAtAction` — 201 ke saath header mein bhi deta hai ki nayi resource kahan milti hai (`/api/books/3`) — REST ka polite tareeka.

## Smell check — ek galti jo tune ki

Upar `Create` mein `await dbSave()` likha tha — actually **`await _db.SaveChangesAsync()`** hi likhna hai (jo 6.1/5.2 mein tha). `dbSave()` helper optional hai — simple rakhna ho toh seedha:

```csharp
await _db.SaveChangesAsync();
```

Har jagah try-catch ki zaroorat nahi — error middleware (5.3) sab jagah cover karta hai. **Keep it simple** — crash course ka motto.

## Yeh kya NAHI hai

- **Har endpoint mein `Select(BookDto...)` optional nahi hai — par strongly recommended** — seedha `Ok(book)` karoge toh aane wale din `Book` mein `CreatedById`/internals add hote hain, woh bhi bahar chale jaate. DTO boundary = contract.
- **PUT = full update** (poora object), PATCH = partial (advanced, abhi chhodo). Interview mein farq poochha jaaye toh bata dena.
- **`DbUpdateException` catch karke chup nahi** — log/throw kiya (middleware sambhal lega). Swallow = bug chhupana.

## In Your Own Words

1. Ek CRUD endpoint ka 5-step formula batao (GET se DELETE tak ka pattern).

<details>
<summary>Sample Jawab</summary>

**Jawab:** (1) Route + HTTP method attribute, (2) DbContext se data lao (`FindAsync`/`ToListAsync`), (3) Nahi mila toh `NotFound()` — early return, (4) Kaam karo (create/update/remove) + `SaveChangesAsync()`, (5) Sahi status ke saath response (Ok/Created/NoContent) + DTO mein data.

</details>

2. `CreatedAtAction` POST mein kyun — aur kya bhejta hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** 201 Created ke saath `Location` header — nayi resource ka URL (`/api/books/3`). REST convention hai: client ko pata chalta hai ki nayi cheez kahan milti hai (aage GET karne ke liye) — plain 200 se zyada informative.

</details>

3. Response mein seedha `Book` object dene ki jagah `BookDto` kyun — abhi kya bigad sakta hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Model badalta rehta hai — kal `InternalNotes`, `VendorPassword` jaisa field aa gaya toh seedhe `Ok(book)` se woh bhi API pe leak ho jaayega. DTO ek stable contract hai — sirf jo dikhana hai wahi jaata hai, aur model/DB ka andar ka structure chhupa rehta hai.

</details>

4. `DELETE` ke baad `200` vs `204` — kya farak aur kya chalega?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `204 NoContent` = kaam ho gaya, kuch data wapas nahi (DELETE/PUT mein common); `200 Ok` = data/response body bhi bheji. Dono valid hain — 204 zyada precise hai jab body ki zaroorat hi nahi.

</details>
