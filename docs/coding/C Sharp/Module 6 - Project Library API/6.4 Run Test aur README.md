# Search, Pagination and Error Handling

## Search — via Query Parameter (the 5.2 Concept)

New endpoint in `BooksController`:

```csharp
// GET /api/books/search?q=kurtzweil&genre=Programming&maxPrice=600
[HttpGet("search")]
public async Task<IActionResult> Search(
    [FromQuery] string? q,
    [FromQuery] string? genre,
    [FromQuery] decimal? maxPrice)
{
    var query = _db.Books.AsQueryable();      // "nothing sent yet"

    if (!string.IsNullOrWhiteSpace(q))
        query = query.Where(b =>
            b.Title.Contains(q) || b.Author.Contains(q));

    if (!string.IsNullOrWhiteSpace(genre))
        query = query.Where(b => b.Genre == genre);

    if (maxPrice is not null)
        query = query.Where(b => b.Price <= maxPrice);

    var books = await query
        .OrderBy(b => b.Title)
        .Select(b => new BookDto(b.Id, b.Title, b.Author, b.Genre, b.Price, b.Available))
        .ToListAsync();

    return Ok(books);
}
```

See what got learned:

- **`[FromQuery]`** — value comes from the URL `?q=` (it binds without it too, but explicit = clear)
- **`IQueryable` = lazy query builder** (the lazy LINQ from module 3.1!) — `.Where()` only adds a condition to the SQL, the DB is hit only on `.ToListAsync()`. All conditions join together — **one query goes out as SQL `WHERE q AND genre AND price`**
- **`||` (OR)** on title or author

`string.Contains` → `LIKE '%q%'` in SQL — EF translates it itself.

## Pagination — Don't Load 1000 Books

```csharp
// GET /api/books?page=2&pageSize=10
[HttpGet]                    // this version replaces the earlier GetAll
public async Task<IActionResult> GetAll(
    [FromQuery] int page = 1,
    [FromQuery] int pageSize = 10)
{
    page = Math.Max(1, page);                 // 0 or negative → 1
    pageSize = Math.Clamp(pageSize, 1, 50);   // between 1-50 — ⭐ protects against abuse

    var total = await _db.Books.CountAsync();   // how many total

    var books = await _db.Books
        .OrderBy(b => b.Id)
        .Skip((page - 1) * pageSize)         // skip this many
        .Take(pageSize)                      // take this many
        .ToListAsync();

    return Ok(new
    {
        page,
        pageSize,
        total,
        items = books
    });
}
```

**`Skip/Take` = SQL `LIMIT/OFFSET`** — the page is built on the DB, not all books in memory. Response envelope:

```json
{
  "page": 2, "pageSize": 10, "total": 37,
  "items": [ ...10 books... ]
}
```

**`Math.Clamp(pageSize, 1, 50)`** — if the client sends `pageSize=99999`, the DB won't get loaded — capping input = simple security/performance (an extension of 5.3's validation).

## Errors — Structured and Consistent

So far we wrote `new { error = "..." }` in different places — now one helper:

`Infrastructure/ApiResult.cs` (or whatever name you like):

```csharp
namespace LibraryApi.Infrastructure;

public static class Errors
{
    public static IResult NotFound(string what) =>
        Results.NotFound(new { error = $"{what} not found" });

    public static IResult BadRequest(string message) =>
        Results.BadRequest(new { error = message });

    // Validation errors — against one field
    public static IResult Invalid(string field, string message) =>
        Results.BadRequest(new { error = message, field });
}
```

Now in endpoints:

```csharp
if (book is null) return Errors.NotFound("Book");
```

**Consistent shape** (5.3): `{ "error": "...", "field": "..." }` — React handles it in one place:

```javascript
const data = await res.json();
if (!res.ok) setMessage(data.error);    // always the same format
```

And the global middleware once (the 5.3 version — Program.cs):

```csharp
app.UseExceptionHandler(err => err.Run(async ctx =>
{
    ctx.Response.StatusCode = 500;
    await ctx.Response.WriteAsJsonAsync(new { error = "Something went wrong" });
}));
```

Now errors look the same everywhere — 400 (client's fault), 404 (not found), 500 (server, generic).

## What This Is NOT

- **Pagination without `Skip/Take` is fake** — if you do `.ToListAsync()` first and then slice `[0..10]` from the list, the whole table loads — do Skip/Take on the DB (`IQueryable`), not after.
- **Don't leave `pageSize` to the client** — clamp/limit is mandatory, otherwise a `pageSize=1000000` request can bring down the server.
- **No internals in error messages** — never "SQL syntax error at line 4"; generic + log on the server.

## In Your Own Words

1. What's the benefit of calling `.Where()` repeatedly on an `IQueryable` — when does the query actually hit the DB?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Each `.Where()` only **adds** an SQL condition (lazy), no DB hit. On `.ToListAsync()`/`.Count()` all conditions become one SQL `WHERE ... AND ...` and go out as **a single query**. So 3 filters = 1 round-trip, and the filter runs on the DB (not the whole table in memory).

</details>

2. Why `Math.Clamp(pageSize, 1, 50)` — what happens if the client sends `pageSize=999999`?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Otherwise the client can request the whole DB (or a huge number of rows) in one request — load on server/memory, DoS-like misuse. The clamp fixes the limit (max 50) — the whole point of pagination is small pages; capping input = performance + security.

</details>

3. In the search endpoint, `q`, `genre`, `maxPrice` are optional — how does the code handle them, and what SQL results?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Each parameter is added only when it has a value (`if (!string.IsNullOrWhiteSpace(...))` / `if (x is not null)`); otherwise the filter is left off (optional behavior). Only the supplied filters join with `AND` in SQL — if everything is empty, all books come back.

</details>

4. What's the benefit of the structured error `{error, field}` for the frontend?

<details>
<summary>Sample Jawab</summary>

**Jawab:** The client can handle it in one place — `if (!res.ok) show(data.error)`, and `field` lets it show the message under the specific input. With random HTML/text messages you'd have to parse differently everywhere — consistency = maintainable frontend.

</details>
