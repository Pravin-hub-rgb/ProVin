The last file left a problem — C# has **single inheritance**: a class can inherit from only one class (`class Student : Person`). But sometimes a rule applies to many different families — "whatever gets saved keeps a `Save()` method", whether it's `Student` or `Product` or `Order`. The solution is **interface**.

# Interfaces and Namespaces

## Interface — only the rule, no implementation

An interface is a **contract**: "whoever implements this must have these methods". The inside code is yours — only the signature:

```csharp
interface ISaveable               // starts with I = naming convention
{
    void Save();                  // no body — just the rule
    string GetId();
}

class Student : ISaveable         // implement = signed the contract
{
    public string Name;

    public void Save()
    {
        Console.WriteLine(Name + " saved to DB");
    }

    public string GetId()
    {
        return "STU-" + Name.Length;
    }
}

class Product : ISaveable         // another family — same contract
{
    public void Save() => Console.WriteLine("Product saved");
    public string GetId() => "PRD-001";
}
```

Difference from inheritance:

| | Class inherit | Interface |
|---|---|---|
| What you get | code (fields + methods) | only signature (rule) |
| How many | **only one** parent | **as many as you want** (`: ISaveable, IComparable`) |
| Body | exists | none — write it yourself |
| Purpose | reusability | capability/"can-do" |

`ISaveable` means "can be saved" — `Student` already inherits from `Person`, and can still take `ISaveable`. **That's the benefit** — rules across different families together.

## Real .NET interfaces — you'll meet them daily

You don't create these; .NET's ready-made ones are used a lot:

```csharp
// IEnumerable — "you can loop over this" (the foreach rule)
foreach (var item in myObject) { }   // if IEnumerable is implemented → works

// IEquatable<Student> — "two students can be compared"
// IComparable — "can be sorted"
```

And in module 5, ASP.NET Core interfaces (`IActionResult`, `IService`) will come — then this word will feel familiar. For now just remember: **interface = the shape of a plug.** Whether your device is Samsung or Sony, if the plug shape is the same, the system (electricity) fits it into everything.

## Interface vs Abstract class — when which

- **Abstract class** when there's shared code for **one family** (like all employees' common `RaiseRequest()`), and there's state too.
- **Interface** when you want to give **different families** one rule (`ISaveable`, `ILoginable`), or multiple capabilities are needed.
- C#: one abstract parent + as many interfaces — both can run together.

```csharp
class Manager : Person, ISaveable, IPromotable   // one class, two contracts
{
}
```

## Default interface methods (C# 8+) — a small extra

```csharp
interface ILogger
{
    void Log(string msg);

    void LogError(string msg) => Log("[ERROR] " + msg);   // body can exist here too
}
```

Whoever implements must write `Log`; for `LogError`, override if you want, otherwise the default runs. Advanced — just know it exists.

## Namespaces — name-saving like a folder system

Whenever `Console`, `Math` etc. appear in C# — they live in some **namespace**. That's what's written at the top of the file:

```csharp
using System;                 // System namespace's items, directly
using System.Collections.Generic;   // List<>
```

```csharp
Console.WriteLine("hi");      // actually System.Console.WriteLine — using made it short
List<int> l = new List<int>(); // actually System.Collections.Generic.List<int>
```

**`using` = JS's `import`** (direction reversed — in JS you import "react", in C# you "use" the namespace). Without `using`, you'd have to write the full name: `System.Console.WriteLine(...)`.

Make your own namespaces — to avoid name collisions in large projects:

```csharp
namespace SchoolApp.Domain          // hierarchy with dots, like folders
{
    class Student { }
}

// use:
// using SchoolApp.Domain;
// SchoolApp.Domain.Student s = new SchoolApp.Domain.Student();
```

Classes inside a `namespace` — like a JS module where "SchoolApp.Domain's `Student`" and "School's `Student`" are different. Large solutions (.NET's own) stay organized this way.

> Modern C# also supports file-scope namespace (`namespace SchoolApp.Domain;` as one line at the top of the file) — you'll find both in codebases.

## What It Is NOT

- **No data/fields inside an interface** — only method/property signatures (C# 8's default methods give behaviour, but no field). For state, you need a class.
- **Interface ≠ abstract class** — one gives a rule, the other partial code too. Multiple inheritance comes only via interfaces, not classes.
- **`using` is not JS-style import** — no file is downloaded; it just shortens the name. Packages (NuGet) are a different thing — module 3.
- **The name need not start with `I`**, but the .NET convention is this (`IList`, `IDisposable`) — the moment you see `I`, know it's an interface.

## A complete program — contract-based design

```csharp
// Program.cs
using System;
using System.Collections.Generic;

interface IExportable
{
    string Export();          // every exportable thing returns a CSV string
}

class Report : IExportable
{
    public string Title;
    public Report(string t) { Title = t; }

    public string Export() => $"Report: {Title}, date: {DateTime.Now:yyyy-MM-dd}";
}

class Invoice : IExportable
{
    public double Amount;
    public Invoice(double a) { Amount = a; }

    public string Export() => $"Invoice, amount: {Amount}";
}

// --- one code, different types ---
List<IExportable> items = new List<IExportable>
{
    new Report("Monthly Sales"),
    new Invoice(2500)
};

foreach (IExportable it in items)
{
    Console.WriteLine(it.Export());   // each own Export ran
}
```

`List<IExportable>` — now `Report` fits, `Invoice` fits, and any new type that comes later fits too — as long as it implements `IExportable`. **This is the extension pattern that shows up everywhere in the .NET codebase.**

## In Your Own Words

1. Give three differences between an interface and class inheritance.

<details>
<summary>Sample Answer</summary>

**Answer:** Class inheritance gives code (fields+methods), interface gives only signature/rule. A class can have only one parent, but as many interfaces as you want. An interface has no body (mostly) — the implementer writes it; parent class code runs directly.

</details>

2. When do you create something like `ISaveable` — why doesn't "IS-A" work?

<details>
<summary>Sample Answer</summary>

**Answer:** When the rule applies to different families — Student gets saved, Product gets saved too. Student is not "a" Saveable (no family relation), but "can be saved" (capability). Multiple classes can take this capability, which single inheritance couldn't do.

</details>

3. What does `using System;` do — what happens without it?

<details>
<summary>Sample Answer</summary>

**Answer:** It lets you use the `System` namespace's types (`Console`, `Math`) directly. Without `using`, you'd write the full name — `System.Console.WriteLine(...)`. Not an import (file load) — just a name-shortening facility.

</details>

4. Interface vs abstract class — how would you decide in a project?

<details>
<summary>Sample Answer</summary>

**Answer:** Shared code/state within one family → abstract class (like common code for all employees). Giving one rule/capability to different families, or needing multiple capabilities → interface. .NET gives both — use as needed.

</details>
