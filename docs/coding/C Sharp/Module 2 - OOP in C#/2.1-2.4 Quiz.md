## MCQ

Q: What is the correct relationship between a class and an object?
A. A class is an object; only the name differs
B. A class is a blueprint, an object is an instance built from it
C. An object is a blueprint, a class is an instance built from it
D. Both replace each other
> B. A class is a blueprint (what it will have — fields, methods), and objects created with `new` are its real instances carrying their own data. One `Student` (class) can have many `s1`, `s2` objects.

---

Q: What is C#'s main pattern to avoid directly changing data like `s1.marks = -500`?
A. A public field is best
B. Make the field private and provide a public property (get/set) with validation
C. Make marks a string
D. Seal the class
> B. Encapsulation: the field is `private` (can't leave the class), outside access only through the property's path — whose `set` carries validation (checks `value`). So -500 never gets inside.

---

Q: What does writing `Student : Person` mean?
A. Student gets no benefit from Person
B. Person inherits from Student
C. Student inherits from Person — it can use its public/protected members
D. Both classes merge
> C. The one after the colon is the **parent/base**. `Student : Person` = Student is the child — it can reuse Person's code (fields, methods), and also calls the parent constructor via `base(...)`.

---

Q: What is needed for polymorphism to work in C#?
A. Just the method names being the same
B. `virtual` in the parent, `override` in the child
C. Both classes must be `abstract`
D. An interface is required
> B. C# doesn't override silently (unlike JS). The parent method is marked `virtual`, the child writes `override`. Then at run time the correct method for the object runs.

---

Q: What's inside an interface?
A. Complete code that children receive
B. Only method/property signatures (the rule) — no implementation
C. Data fields and constructor
D. A database query
> B. An interface is a contract — "whoever implements this must have these methods". There's mostly no body; each implementer writes its own. So different families (Student, Product) can follow the same rule together.

---

Q: How many classes can a C# class inherit from?
A. As many as you want
B. No more than two
C. Only one — but as many interfaces as you want
D. Zero — there's no inheritance
> C. C# has single inheritance (one parent class). For multiple capabilities, use interfaces — `class M : Person, ISaveable, IComparable` works. That's the real benefit of interfaces.

---

Q: What does `using System.Collections.Generic;` do?
A. Installs a NuGet package
B. Lets you use types like `List<>` without the full name (`System.Collections.Generic.List`)
C. Compiles the code
D. Saves the file
> B. `using` gives the namespace's items a short name (JS `import` goes the opposite direction — there it comes in, here the namespace is "used"). Package installation is NuGet's job, covered in module 3.

## True/False

Q: `class Student : Address` is a correct inheritance example because a student has an address.
- True
- False
> False. That's a "has-a" relation — a student has an address, a student is not an address. Inheritance is only for "IS-A" (`Student : Person`). For has-a, take a simple field (`Address address` field).

---

Q: A parent's `private` field is directly accessible in the child class.
- True
- False
> False. `private` is only inside that class. If the child needs it, the parent should use `protected` (class + children) or a public property. Encapsulation applies to parent-child too.

---

Q: You can create an object of an `abstract class` directly with `new`, just like a normal class.
- True
- False
> False. An abstract class is half-incomplete (abstract methods without bodies) — creating its object gives a compiler error. Only child classes can be made that implement all abstract methods.

---

Q: Fields (data) can be kept inside an interface.
- True
- False
> False. An interface is only a contract — method/property signatures. To keep data state, you need a class (an interface's default method only gives behaviour, not a field).

---

Q: Breaking a long file's code into small methods is part of encapsulation and is standard practice in production code.
- True
- False
> True. Each small method does one job (single responsibility), is easy to read/test/fix, and other methods can reuse them (like Average using Sum). This is the DRY + clean code practice.
