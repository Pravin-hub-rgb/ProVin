The last file left a problem — by putting `public` fields, we let everyone get inside. If someone writes `s1.marks = -500`, the whole data breaks. If a bank's balance could be changed from outside like that, what kind of bank would it be? That's the problem, and C#'s answer to it is — **encapsulation**.

# Properties and Encapsulation

## Problem — the data is left open

```csharp
class Student
{
    public int marks;
}

Student s = new Student();
s.marks = -500;    // ❌ it worked! nothing stopped it
```

Encapsulation means: **lock the data inside, and give the outside only controlled paths.** Make the field private, so outside code can only touch it through methods/properties — where you can add validation.

## Private field + public property — C#'s main pattern

```csharp
class Student
{
    private int _marks;    // direct outside access BANNED

    public int Marks       // this is the PUBLIC path (property)
    {
        get { return _marks; }             // on read
        set
        {
            if (value < 0 || value > 100)
                Console.WriteLine("Marks should be between 0-100!");
            else
                _marks = value;            // on write — validation here
        }
    }
}
```

```csharp
Student s = new Student();
s.Marks = 95;       // ✅ set ran → checked → _marks = 95
s.Marks = -500;     // ⚠️ set ran → rejected! -500 didn't reach _marks
Console.WriteLine(s.Marks);   // get ran → 95
```

3 things:

1. **`private int _marks`** — the field is hidden. Outside, `s._marks` gives an error. (The `_` prefix is just a convention — it says "this is a private inside thing".)
2. **`public int Marks`** — a **property**. Outside code writes `s.Marks`, but inside, `get`/`set` blocks run — like a receptionist who takes your request and goes inside.
3. **`value`** — in `set`, `value` holds whatever someone wrote (`s.Marks = 95` → `value = 95`). Validation happens right here.

**This is encapsulation:** data inside, controlled door outside. JS had nothing like this (objects were open) — if you know Python's `@property`, recall that; otherwise C# is your first proper property language.

## Auto-property — the everyday shortcut

If you don't need validation, no need for the long form:

```csharp
class Student
{
    public string Naam { get; set; }      // the compiler did all the work itself
    public int Marks { get; set; }
}
```

`{ get; set; }` — the compiler creates a private backing field on its own. **This is used 90% of the time** — use the long form where validation is needed, auto-property everywhere else.

```csharp
Student s = new Student { Naam = "Vin", Marks = 95 };   // object initializer — like a JS object literal
```

`new Student { ... }` — C#'s way of filling fields right after the constructor (the JS `{ naam: "Vin" }` feeling).

## Read-only property — read only, don't change

```csharp
public double Balance
{
    get { return _balance; }     // no set — outside can only read
}
```

Or in auto form, only `get`:

```csharp
public string CreatedAt { get; } = DateTime.Now.ToString("yyyy-MM-dd");
```

Things that shouldn't be changed from outside (ID, creation date) — those are read-only.

## Naming convention — the C# team's way

```csharp
class Course
{
    private string _title;              // field: _camelCase (underscore)
    private int _duration;

    public string Title                 // property: PascalCase
    {
        get => _title;
        set => _title = value?.Trim() ?? "Untitled";   // expression form
    }

    public int Duration
    {
        get => _duration;
        set => _duration = value > 0 ? value : 1;      // validation + default
    }
}
```

`get => ...; set => ...;` — expression-bodied form, compact for small properties. Things like `value?.Trim()` (null-conditional) are like JS `?.` — C# has them too.

**Convention:** field `_naam`, property `Naam`, method `GetNaam`. This is the standard naming in C# — break it and the code feels awkward.

## Quick decision — where to use what

- **Read-only from outside** (ID, timestamp): `{ get; }`
- **Normal data, no check** (naam, title): `{ get; set; }` (auto)
- **Data that needs checking** (marks, balance, age): `_field` + long property with validation
- **Completely inside secret**: `private` field without a property

## A complete program — Bank account v2 (the safe one)

```csharp
// Program.cs
class Account
{
    private string _owner;
    private double _balance;

    public string Owner
    {
        get => _owner;
        set => _owner = string.IsNullOrWhiteSpace(value) ? "Unknown" : value;
    }

    public double Balance { get; private set; }   // outside can only read

    public Account(string owner, double opening)
    {
        Owner = owner;                            // through the property — validation applies
        _balance = opening >= 0 ? opening : 0;
    }

    public void Deposit(double amt)
    {
        if (amt <= 0) { Console.WriteLine("Galat amount"); return; }
        _balance += amt;
    }

    public void Withdraw(double amt)
    {
        if (amt <= 0 || amt > _balance) { Console.WriteLine("Nahi ho sakta"); return; }
        _balance -= amt;
    }
}

// --- program ---
Account a = new Account("Vin", 1000);
a.Deposit(500);
// a.Balance = 99999;     // ❌ compile error — set is private! can't change directly
Console.WriteLine(a.Balance);   // 1500 — can only read
```

Look how safe it got — balance changes only through `Deposit`/`Withdraw`, both with checks. No one from outside can cheat. **This is what clean encapsulated code looks like** — all fields private (locked in the box inside), outside only well-thought-out paths.

## What It Is NOT

- **`public` field ≠ encapsulation** — in `public int marks` there's no chance for validation. The point of a property is to sit between get/set.
- **A property is not a method** — outside you write `s.Marks` (no `()`). get/set run inside; from outside it feels like a direct field.
- **Not every private needs a property** — if a field is only used inside the class (helper state), leave it plain private. Make a property only when it's needed outside.

<details>
<summary>Sample Answer</summary>

**Answer:** `value` = the number that got assigned (95). `s.Marks = 95` doesn't go straight into the field — the `set` block runs, where `value` is checked (validation) and then put into the private field.

</details>

3. When should you use an auto-property `{ get; set; }` vs a full property (`_field` + get/set)?

<details>
<summary>Sample Answer</summary>

**Answer:** No validation or logic → auto-property (short, compiler makes the backing field itself). Check needed (marks 0-100, balance positive) → `_field` + long property with get/set. Read-only → just `{ get; }`.

</details>

4. What does `public double Balance { get; private set; }` mean for an outside developer?

<details>
<summary>Sample Answer</summary>

**Answer:** Balance can be read from outside (`a.Balance`), but not set — because `private set`. The value changes only through methods inside the class. Writing `a.Balance = 999` from outside gives a compile error.

</details>
