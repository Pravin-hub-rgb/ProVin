Until now every class did all its own work alone. But in the world everything is **reusable** — a car's steering, brakes, engine are common across models, only a few things differ. Same in programming: `Student` and `Teacher` both have name, ID, and print work the same. Writing once and using twice — that's **inheritance**, and with it comes **polymorphism**.

# Inheritance and Polymorphism

## Inheritance — one class takes everything from another

```csharp
class Person
{
    public string Naam;

    public Person(string naam)
    {
        Naam = naam;
    }

    public void Introduce()
    {
        Console.WriteLine("Main " + Naam + " hoon");
    }
}

class Student : Person        // ❗ colon = "inherit from Person"
{
    public int Marks;

    public Student(string naam, int marks) : base(naam)   // base = parent's constructor
    {
        Marks = marks;
    }
}
```

```csharp
Student s = new Student("Vin", 90);
s.Introduce();      // ✅ got Person's method too!
Console.WriteLine(s.Marks);   // Student's own field
```

Syntax breakdown:

- **`class Student : Person`** — after the colon comes the parent. `Student` (**derived/child**) gets all of `Person`'s (**base/parent**) public/protected things.
- **`: base(naam)`** — the child constructor calls the parent constructor (the parent has its own work to do too). In JS it was `super(...)` — this is the same thing, name is `base`.

So `Student` now has `Naam` + `Introduce()` too, without writing them again. Reuse done.

## When to inherit — the "IS-A" test

Only when the relationship is **"X is a Y"**:

- `Student` **is a** `Person` ✅
- `Car` **is a** `Vehicle` ✅
- `Employee` **is a** `Person` ✅
- `Student` **is a** `Address` ❌ (this is "has a" — it holds an address)

For a "has a" relationship, no inheritance — take a simple field (`Student` has an `Address address` field). This is a basic design rule.

## Access — introduction to protected

What's accessible inside the parent:

- `public` — for everyone ✅
- `private` — only for its own class ❌ (not even the child!)
- `protected` — for its own class + **its children** ❌ not for outsiders

```csharp
class Person
{
    private string secret;      // only inside Person
    protected string familyId;  // Person + Student/Teacher both
    public string naam;         // for everyone
}
```

This is the next level of encapsulation — keep data inside, and use `protected` when children need it.

## Polymorphism — one name, different work

Now the real magic. Do **method overriding**:

```csharp
class Person
{
    public string Naam;
    public Person(string n) { Naam = n; }

    public virtual void Work()              // virtual = allow overriding
    {
        Console.WriteLine(Naam + " kaam kar raha hai");
    }
}

class Student : Person
{
    public Student(string n) : base(n) { }

    public override void Work()             // override = change the parent's
    {
        Console.WriteLine(Naam + " padh raha hai");
    }
}

class Teacher : Person
{
    public Teacher(string n) : base(n) { }

    public override void Work()
    {
        Console.WriteLine(Naam + " padha raha hai");
    }
}
```

Now run them all from one place:

```csharp
Person p1 = new Student("Vin");
Person p2 = new Teacher("Rahul");

p1.Work();    // Vin padh raha hai   ← Student's ran
p2.Work();    // Rahul padha raha hai ← Teacher's ran
```

**This is polymorphism** — wrote `p1.Work()`, and at actual run time the right method runs based on which object it really is. Rules:

- Mark the method **`virtual`** in the parent (won't happen silently — not like JS)
- Write **`override`** in the child
- The outside variable can be of `Person` type — still the Student/Teacher's own version runs

**Benefit:** if a new type comes (say `Admin`), and it also overrides `Work()` — **the old code (which loops over a `Person` list) keeps running as-is**, no need to change it. Large systems stand on this principle.

## abstract class — incomplete blueprint

Sometimes the parent itself isn't complete — it only gives the rule "this work must be done", the actual code is written by the child:

```csharp
abstract class Shape                    // abstract = no direct object
{
    public abstract double Area();      // no body — just the signature
    public void Display()               // normal method can exist too
    {
        Console.WriteLine("Area: " + Area());
    }
}

class Circle : Shape
{
    double r;
    public Circle(double r) { this.r = r; }

    public override double Area()      // ❗ must implement
    {
        return 3.14 * r * r;
    }
}

// Shape s = new Shape();      // ❌ compile error — no object of abstract
Shape s = new Circle(5);
s.Display();                  // Area: 78.5 — Circle's Area ran
```

`abstract class` = half a blueprint — its object can't be made; children complete it. `abstract method` = "whoever inherits must write this". Until `Circle` writes it, the compiler won't let the code run.

## sealed — only up to here

```csharp
sealed class FinalClass     // no one can inherit from this
{
}
```

A class that shouldn't be changed (like `string`) — mark it `sealed`. `sealed` methods exist too (override blocked). Rare for now — just remember the name.

## What It Is NOT

- **Not every class is inheritable** — abstract can't make an object, sealed can't have a child.
- **`override` doesn't happen silently** — in JS the child's method would just cover the parent's; in C# `virtual` + `override` are explicit (no chance of mistakes).
- **Private parent field doesn't reach the child** — only `protected`/`public` come through. Encapsulation stays intact.
- **Inheritance isn't copying** — the child gets the **right to run** the parent's code; the data in memory stays separate.

## A complete program — all together

```csharp
// Program.cs
abstract class Employee
{
    public string Naam;
    public Employee(string n) { Naam = n; }

    public abstract double Salary();          // every employee must get a salary

    public virtual void Describe()
    {
        Console.WriteLine(Naam + " employee hai");
    }
}

class FullTime : Employee
{
    double monthly;
    public FullTime(string n, double m) : base(n) { monthly = m; }

    public override double Salary() => monthly;
}

class Intern : Employee
{
    double stipend;
    public Intern(string n, double s) : base(n) { stipend = s; }

    public override double Salary() => stipend;

    public override void Describe()          // extra one overridden too
    {
        Console.WriteLine(Naam + " intern hai — seekh raha hai");
    }
}

// --- run via polymorphism ---
List<Employee> team = new List<Employee>
{
    new FullTime("Vin", 50000),
    new Intern("Rahul", 10000)
};

foreach (Employee e in team)
{
    Console.WriteLine($"{e.Naam}: {e.Salary()}");   // each own Salary ran
    e.Describe();                                   // each own Describe
}
```

Add a new employee type — the `team` loop runs as-is. That's the power.

## In Your Own Words

1. What is the "IS-A" test for inheritance — why does `Student : Person` pass but `Student : Address` doesn't?

<details>
<summary>Sample Answer</summary>

**Answer:** Inherit only when the child is itself a type of the parent — Student **is a** Person (became a student as a person). Student is not an Address — it holds an address (has-a), so use a field for that, not inheritance.

</details>

2. Why must `virtual` and `override` be written — how is it different from JS?

<details>
<summary>Sample Answer</summary>

**Answer:** In JS the child's method silently covered the parent's. In C# the parent must first say `virtual` "can be changed", and the child `override` "I'm changing". Without `virtual`, override is an error — no chance of mistakes.

</details>

3. What's the benefit of polymorphism — why doesn't old code change when a new type is added?

<details>
<summary>Sample Answer</summary>

**Answer:** When the outside variable/list is of `Employee` type, the call `e.Salary()` checks the object's real type at run time and runs the right override. Add a new `Contract` employee and it just goes into the list — the loop and other code were written against the `Employee` type, so they run as-is.

</details>

4. `abstract class` vs normal class — when which?

<details>
<summary>Sample Answer</summary>

**Answer:** A normal class is complete — an object can be made. An abstract class is half — it has methods without bodies (`abstract`), so its object can't be made; children must implement those methods. Use abstract when you want to give a rule + shared code both.

</details>

Families are formed through inheritance — but sometimes the relation is of "extension": rules like `IMovable`, `ISerializable` that many different classes follow. In C# that happens through **interfaces** — the most-used part of .NET.
