Ab tak har class akeli apna sab kuch karti thi. Par duniya mein sab kuch **reusable** hota hai — car ka steering, brake, engine sab models mein common hote hain, bas kuch cheezein alag. Programming mein bhi: `Student` aur `Teacher` dono mein naam, ID, print ka kaam same hai. Ek jagah likh kar do jagah use karna — yahi **inheritance** hai, aur uske saath aata hai **polymorphism**.

# Inheritance aur Polymorphism

## Inheritance — ek class doosri se sab cheez le le

```csharp
class Person
{
    public string Naam;

    public Person(string naam)
    {
        Naam = naam;
    }

    public void Introduce()
    {
        Console.WriteLine("Main " + Naam + " hoon");
    }
}

class Student : Person        // ❗ colon = "Person se inherit"
{
    public int Marks;

    public Student(string naam, int marks) : base(naam)   // base = parent ka constructor
    {
        Marks = marks;
    }
}
```

```csharp
Student s = new Student("Vin", 90);
s.Introduce();      // ✅ Person wala method bhi mila!
Console.WriteLine(s.Marks);   // Student ka apna field
```

Syntax ka hisaab:

- **`class Student : Person`** — colon ke baad parent. `Student` (**derived/child**) ko `Person` (**base/parent**) ki saari public/protected cheezein mil jaati hain.
- **`: base(naam)`** — child constructor parent constructor ko call karta hai (parent ko bhi toh apna kaam karna hai). JS mein `super(...)` tha — yahi wahi hai, naam `base`.

Matlab `Student` ke paas ab `Naam` + `Introduce()` bhi hai, bina dobara likhe. Reuse ho gaya.

## Kab inherit karna chahiye — "IS-A" test

Sirf tabhi jab relationship **"X is a Y"** ho:

- `Student` **is a** `Person` ✅
- `Car` **is a** `Vehicle` ✅
- `Employee` **is a** `Person` ✅
- `Student` **is a** `Address` ❌ (ye "has a" hai — address *rakh*ta hai)

"Has a" relationship mein inheritance nahi — simple field lo (`Student` ke paas `Address address` field). Yeh design ka basic rule hai.

## Access — protected ka introduction

Parent ke andar access kya hoga:

- `public` — sab ke liye ✅
- `private` — sirf apni class ke liye ❌ (child ko bhi nahi!)
- `protected` — apni class + **apni children** ko ❌ bahar wale ko nahi

```csharp
class Person
{
    private string secret;      // sirf Person ke andar
    protected string familyId;  // Person + Student/Teacher dono ke andar
    public string naam;         // sab ke liye
}
```

Yehi encapsulation ka next level hai — data ko andar rakho, children ko dena ho toh `protected`.

## Polymorphism — ek naam, alag-alag kaam

Ab asli magic. **Method overriding** karo:

```csharp
class Person
{
    public string Naam;
    public Person(string n) { Naam = n; }

    public virtual void Work()              // virtual = override karne do
    {
        Console.WriteLine(Naam + " kaam kar raha hai");
    }
}

class Student : Person
{
    public Student(string n) : base(n) { }

    public override void Work()             // override = parent wale ko badal do
    {
        Console.WriteLine(Naam + " padh raha hai");
    }
}

class Teacher : Person
{
    public Teacher(string n) : base(n) { }

    public override void Work()
    {
        Console.WriteLine(Naam + " padha raha hai");
    }
}
```

Ab ek jagah se saare chalao:

```csharp
Person p1 = new Student("Vin");
Person p2 = new Teacher("Rahul");

p1.Work();    // Vin padh raha hai   ← Student wala chala
p2.Work();    // Rahul padha raha hai ← Teacher wala chala
```

**Yahi polymorphism hai** — `p1.Work()` likha, aur asli run-time mein object kaunsa hai uske hisaab se sahi wala method chala. Rules:

- Parent mein method ko **`virtual`** mark karo (chup-chaap override nahi hoga — JS ki tarah na chale)
- Child mein **`override`** likho
- Bahar wala variable `Person` type ka rakh sakte ho — phir bhi Student/Teacher ka apna wala chalega

**Fayda:** naya type aaye (say `Admin`), usne bhi `Work()` override kiya — **purana code (jo `Person` ke list pe loop karta hai) waise ka waise chalega**, badalne ki zaroorat nahi. Bade systems isi principle pe tikte hain.

## abstract class — incomplete blueprint

Kabhi kabhi parent khud complete nahi hota — sirf rule deta hai ki "ye kaam karna hi padega", banane ka code child likhega:

```csharp
abstract class Shape                    // abstract = direct object nahi banega
{
    public abstract double Area();      // body nahi — sirf signature
    public void Display()               // normal method bhi ho sakta hai
    {
        Console.WriteLine("Area: " + Area());
    }
}

class Circle : Shape
{
    double r;
    public Circle(double r) { this.r = r; }

    public override double Area()      // ❗ implement karna hi padega
    {
        return 3.14 * r * r;
    }
}

// Shape s = new Shape();      // ❌ compile error — abstract ka object nahi
Shape s = new Circle(5);
s.Display();                  // Area: 78.5 — Circle wala Area chala
```

`abstract class` = aadha naksha — khud se object nahi banta, children se poora hota hai. `abstract method` = "jo inherit kare wo ye likhega hi likhega". Jab tak `Circle` ye na likhe, compiler nahi chalne dega.

## sealed — yahan tak hi

```csharp
sealed class FinalClass     // isse koi inherit nahi kar payega
{
}
```

Jis class ko badalna hi nahi (jaise `string`) — uspe `sealed`. `sealed` method bhi hota hai (override band). Abhi rare hai — naam yaad rakho.

## Yeh kya NAHI hai

- **Har class inheritable nahi** — abstract ka object nahi banta, sealed ka child nahi banta.
- **`override` bina chup-chaap nahi hota** — JS mein child ka method seedha parent ko dhak leta tha; C# mein `virtual` + `override` explicit chahiye (galti ka chance nahi).
- **Private parent field child ko nahi milta** — `protected`/`public` hi aata hai. Encapsulation bana rehta hai.
- **Inheritance ka matlab copy nahi** — child ke paas parent ka **code chalne ka hak** hai, memory mein data alag hota hai.

## Ek complete program — sab ek saath

```csharp
// Program.cs
abstract class Employee
{
    public string Naam;
    public Employee(string n) { Naam = n; }

    public abstract double Salary();          // har employee ko salary dena hi hai

    public virtual void Describe()
    {
        Console.WriteLine(Naam + " employee hai");
    }
}

class FullTime : Employee
{
    double monthly;
    public FullTime(string n, double m) : base(n) { monthly = m; }

    public override double Salary() => monthly;
}

class Intern : Employee
{
    double stipend;
    public Intern(string n, double s) : base(n) { stipend = s; }

    public override double Salary() => stipend;

    public override void Describe()          // extra wala bhi override
    {
        Console.WriteLine(Naam + " intern hai — seekh raha hai");
    }
}

// --- polymorphism se chalao ---
List<Employee> team = new List<Employee>
{
    new FullTime("Vin", 50000),
    new Intern("Rahul", 10000)
};

foreach (Employee e in team)
{
    Console.WriteLine($"{e.Naam}: {e.Salary()}");   // apna-apna Salary chala
    e.Describe();                                   // apna-apna Describe
}
```

Naya employee type add karo — `team` wala loop waisa ka waisa chalega. Yahi power hai.

## In Your Own Words

1. Inheritance "IS-A" test kya hai — `Student : Person` pass karta hai, `Student : Address` kyun nahi?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Inheritance tabhi jab child parent ka hi ek type ho — Student **is a** Person (person hote hue student ban gaya). Student Address nahi hai — uske paas address hai (has-a), isliye uske liye field use karte hain, inheritance nahi.

</details>

2. `virtual` aur `override` kyun likhna padta hai — JS ke mukable kya fark hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** JS mein child ka method chup-chaap parent ko dhak deta tha. C# mein parent ko pehle `virtual` se bolna padta hai "badla ja sakta hai", child ko `override` se "main badal raha hoon". Bina `virtual` ke override error hai — mistake ka chance nahi.

</details>

3. Polymorphism ka faayda kya hai — naya type add karne se purana code kyun nahi badalta?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Jab bahar wala variables/list `Employee` type ki hai, toh `e.Salary()` call pe run-time pe object ka asli type dekh kar sahi override chalta hai. Naya `Contract` employee banaye toh bas list mein add hoga — loop aur baaki code `Employee` type ke against likha tha, waisa hi chalega.

</details>

4. `abstract class` aur normal class — kab kaunsa?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Normal class complete hai — object ban sakta hai. Abstract class aadhi hai — usme kuch methods bina body ke (`abstract`) hote hain, isliye uska object nahi ban sakta; children ko wo methods implement karne hi padte hain. Rule dene + shared code dono chahiye toh abstract.

</details>

Inheritance se families ban gayin — par kabhi kabhi relation "extension" wala hota hai: `IMovable`, `ISerializable` jaise rules jo kai alag-alag classes follow karein. C# mein yeh hota hai **interfaces** ke through — jo .NET ka sabse roz wala hissa hai.
