Until now you've been keeping everything in separate variables — `naam`, `umar`, `salary` all separate. But when a student has 10 attributes and there are 100 students, that won't work. In JS you created objects (`{ naam: "Vin", umar: 25 }`) and in React you wrote `function Student()` components — that same idea is now **class**, but more structured.

# Class and Object

## What a class is — analogy first

A class is a **blueprint**. Think of a "Student" blueprint — it says every student will have a name, age, roll number, and a way to `Print()`. A blueprint alone does nothing — it's of no use by itself. But from that blueprint you can create as many **objects** as you want — each object (each student) is the real thing, with its own data.

Blueprint = **Class**. Made from blueprint = **Object** (also called an instance).

JS had the same thing — `function Student()` = blueprint, `new Student()` = object. The syntax in C# is just more explicit.

## First class

```csharp
class Student
{
    // data (fields) — like JS object properties
    string naam;
    int umar;
    int marks;

    // work (methods) — like JS object methods
    void Print()
    {
        Console.WriteLine(naam + " | " + umar + " | " + marks);
    }
}
```

Now use it:

```csharp
// create an object — JS: const s = new Student()
Student s1 = new Student();
s1.naam = "Vin";      // put a value inside the object
s1.umar = 25;
s1.marks = 90;
s1.Print();            // Vin | 25 | 90

Student s2 = new Student();
s2.naam = "Rahul";
s2.umar = 26;
s2.marks = 85;
s2.Print();            // Rahul | 26 | 85
```

**This is the benefit** — one blueprint, two objects, separate data. `s1.naam` and `s2.naam` are independent of each other (the JS object feeling).

> Modern C#: instead of `Student s1 = new Student();` you can also write `Student s1 = new();` (target-typed new) — the type is already written on the left side. Both work; the first one is clearer for now.

## Constructor — fill in the data while creating the object

Above, you had to write 3 separate lines for each object. With a **constructor**, it all happens at creation time:

```csharp
class Student
{
    string naam;
    int umar;
    int marks;

    // constructor — same name as class, no return type
    public Student(string naam, int umar, int marks)
    {
        this.naam = naam;    // this = current object
        this.umar = umar;
        this.marks = marks;
    }

    void Print()
    {
        Console.WriteLine($"{naam} | {umar} | {marks}");
    }
}
```

```csharp
Student s1 = new Student("Vin", 25, 90);
Student s2 = new Student("Rahul", 26, 85);
s1.Print();
```

3 new things:

1. **Constructor** — the method with the class name (`public Student(...)`), runs automatically on `new`. No return type (the object itself is being created).
2. **`this`** — "the object currently being worked on". `this.naam = naam` means: fill the object's `naam` field, the `naam` inside is the parameter. JS had `this` for the object — the same idea, but more predictable (none of that JS `this` drama here).
3. **`public`** — access keyword, next point:

## What `public` is (a little teaser for module 2.2)

`public` means anyone from outside can use it. Without `public`, it stays limited to **inside** the class (default "private"). For now remember this — **make fields `public` until you've learned encapsulation**:

```csharp
class Student
{
    public string naam;    // can be set from outside
    public int marks;
}
```

Otherwise `s1.naam = "Vin"` will throw an error. Detail in the next file — securing data through encapsulation.

## A complete program — Bank account

```csharp
// Program.cs
class Account
{
    public string owner;
    public double balance;

    public Account(string owner, double opening)
    {
        this.owner = owner;
        this.balance = opening;
    }

    public void Deposit(double amt)
    {
        if (amt <= 0) { Console.WriteLine("Galat amount"); return; }
        balance += amt;
        Console.WriteLine($"+{amt} → {balance}");
    }

    public void Withdraw(double amt)
    {
        if (amt > balance) { Console.WriteLine("Balance kam"); return; }
        balance -= amt;
        Console.WriteLine($"-{amt} → {balance}");
    }
}

// --- the real program ---
Account a1 = new Account("Vin", 1000);
a1.Deposit(500);        // 1500
a1.Withdraw(200);       // 1300
Console.WriteLine(a1.owner + ": " + a1.balance);
```

Look what happened — data (`owner`, `balance`) and the work done on it (`Deposit`, `Withdraw`) are **joined in one place**. Each account has its own separate state. This is OOP's core: **data + behaviour together**.

JS comparison:

```javascript
// JS
const a1 = {
  owner: "Vin",
  balance: 1000,
  deposit(amt) { this.balance += amt; }
};
```

The same thing, except here there's a blueprint class, it's type safe, and code stays organized in large teams.

## What It Is NOT

- **Class ≠ object** — a class is a blueprint, an object is built from it. `Student` (class) ≠ `s1` (object).
- **`this` is not unpredictable like JS** — in JS, `this` changed between arrow vs normal functions. In C#, `this` is always the current object — no drama.
- **Not everything is a class** — small utilities (like `Math.Abs(5)`) work without classes. Create a class when **state + work** go together (Account, Student, Product).

<summary>Sample Answer</summary>

3. In the line `this.naam = naam`, what does `this` point to, and why is it needed?

<details>
<summary>Sample Answer</summary>

**Answer:** `this` = the object just created (like s1). The parameter had the same name as the field (`naam`), so `this.naam` said "the left one is the object's field, the right one is the parameter's value". Without `this`, both same-named things would confuse each other.

</details>

4. What's the benefit of `Deposit` and `Withdraw` methods having data and behaviour in one place (Account)?

<details>
<summary>Sample Answer</summary>

**Answer:** The balance data and the rule for changing it (the check) live in one place — no one from outside can do `balance -= 100000` directly; it must go through the method. Each object's state stays separate, and the code stays organized and replaceable.

</details>
