## MCQ

Q: What does LINQ's `.Where()` do in the JS world?
A. `.map()`
B. `.filter()` — keeps items where the condition holds
C. `.find()`
D. `.sort()`
> B. `.Where(u => u.Age >= 18)` = filters items where the condition is true — exactly `arr.filter(u => u.age >= 18)`. `.Select()` is map and `.FirstOrDefault()` is find.

---

Q: Why is `FirstOrDefault()` preferred over `First()` in user-searching code?
A. FirstOrDefault is faster
B. First() returns nothing
C. First() throws an exception if no match; FirstOrDefault returns null that you can check
D. Both are the same
> C. `First()` crashes the program on no match (InvalidOperationException). `FirstOrDefault()` returns null — handled with `if (x == null)`. For a new developer, the former is always safer.

Q: What does an `async Task<int>` method mean in C#?
A. The method immediately returns an int
B. The method returns "not now, later via Task" — extract with `await`
C. The method's name is int
D. The method blocks the thread
> B. `Task<int>` = a pending result carrying an int. `int x = await CountAsync()` gets the value. Without `await` you have a Task (wrapped), not an int — type error.

---

Q: What happens with `await Task.Delay(2000)`?
A. The whole program stops for 2 sec
B. The thread blocks until the delay ends
C. This method pauses and the thread is freed to do other work, resuming after 2 sec
D. An error occurs
> C. That's the point of `await` — while waiting, the thread is released (other requests get served). Like the event loop in JS; in C# it's thread-pool continuation. The rest of the program doesn't stop.

---

Q: What's the C# equivalent of `Promise<T>`?
A. `Future<T>`
B. `Task<T>`
C. `Thread<T>`
D. `async<T>`
> B. JS `Promise<T>` = C# `Task<T>`, `Promise.all` = `Task.WhenAll`, `await` is the same in both. This mapping must stay in memory — JS async concepts translate directly into C#.

---

Q: Why write `<Person>` in `JsonSerializer.Deserialize<Person>(json)`?
A. It's just syntax, no meaning
B. Because C# must be told which type to parse the JSON into — unlike JS's free-for-all `JSON.parse`
C. To display the Person class name
D. Otherwise JSON won't print
> B. JS's `JSON.parse` made an object without a type (left as `any`). C# is type-safe — `<Person>` says which class to build, and wrong JSON fails earlier.

---

Q: What is `T` in a generic class `MyList<T>`?
A. A specific class name
B. A placeholder — the real type is given when creating (`MyList<int>`)
C. A template file
D. Always the method's return type
> B. `T` is a type-parameter — like a function takes a value parameter, a generic takes a type. `MyList<int>` makes `T=int`, `MyList<string>` makes `T=string` — one code, with type safety.

## True/False

Q: Writing `async` makes the code run faster — the work finishes sooner.
- True
- False
> False. `async`'s job isn't to make it fast — it's to **avoid blocking**. Total time stays the same (a 2 sec delay is still 2), but the thread stays free and other work runs. That's where concurrency comes from on a server.

---

Q: Writing `async void` methods is common practice in C# and always fine.
- True
- False
> False. Avoid `async void` — its Task can't be tracked, errors inside don't surface outside, testing is hard. Always use `Task`/`Task<T>` (except event handlers).

---

Q: LINQ's `.Where()` runs the filter immediately on call — just like JS's `.filter()`.
- True
- False
> False. LINQ is lazy — `.Where()` only builds the query plan. It runs when the result is consumed (`ToList()`, `foreach`, `Count()` etc.). JS's `.filter()` made a new array immediately.

---

Q: The `...Async`-suffixed version (like `File.ReadAllTextAsync`) is used when the work can block (disk/network).
- True
- False
> True. Disk I/O, HTTP, DB query — all blocking work; their `...Async` versions keep the thread free. No need for async on instant work like `Console.WriteLine`.

---

Q: Generics are only for performance — they have nothing to do with type checking.
- True
- False
> False. Generics do both — compile-time type safety (`MyList<int>.Add("hi")` is an error) and performance (no boxing/unboxing, unlike the old object-based approach).
