# What a Web API is — your first API

## First understand — what an API sends back

You've done `fetch('/api/products')` in React — behind it something was running on the server that returned JSON. That "something" is a **Web API** — a program that listens to HTTP requests (GET/POST/PUT/DELETE) and talks to the database to send back **JSON**. No UI, only data.

```
React app  --fetch("/api/students")-->  ASP.NET Core API  --EF Core-->  DB
        <------ JSON response -----------  (this is what you'll build)
```

**Frontend (React) = showing. Backend (API) = data + rules.** You know both — now the backend is built in C#.

## What ASP.NET Core is — the name is confusing itself

- **ASP.NET** — Microsoft's old name for the web framework (been around for ages)
- **Core** — the new cross-platform version (runs on Linux)
- **.NET Core / .NET 8 / .NET 9** — the same platform whose setup you did in module 0

In daily talk, **"ASP.NET Core"** = "the web framework built on .NET". And **Web API** = the part inside it for making endpoints that give data. There's also MVC for rendering HTML, but today mostly APIs are built because the frontend is separate (React).

## First project — `dotnet new webapi`

```bash
dotnet new webapi -n SchoolApi
cd SchoolApi
dotnet run
```

Look inside the folder:

```
SchoolApi/
├── Program.cs           ← startup — everything connects here (like Next.js layout/server entry)
```

`dotnet run` → the URL shows in the terminal (`http://localhost:5000` or 5231). Open it in the browser — the API is running! If a `swagger` page shows up, even better — you can test with it (next file).

> Depending on the template you get **minimal API** (endpoints directly in Program.cs) or **controllers**. Modern .NET prefers minimal API, but both are found in old/new codebases — so we'll see both: start with minimal (simple), then controllers (classic style).

## Minimal API — first endpoint in 5 lines

In `Program.cs`:

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/", () => "Hello, API!");              // GET / → simple text
app.MapGet("/api/health", () => new { status = "ok", time = DateTime.Now });

app.Run();
```

`dotnet run` → `http://localhost:5000/api/health` in the browser:

```json
{"status":"ok","time":"2026-09-25T10:30:00"}
```

Line by line:

1. `WebApplication.CreateBuilder(args)` — the app is being built (config, logging, all ready)
2. `builder.Build()` — the app is built from the builder
3. `MapGet("/route", () => ...)` — "when a GET request comes on this path, do this" — arrow function, JS feel
4. `app.Run()` — server starts (the `npm run dev` line — server now stays up)

**The first API is running.** The request-response flow:

```
Browser/React:  GET http://localhost:5000/api/health
Server:         MapGet caught it → lambda ran → object created
Response:       JSON (auto) + HTTP 200
```

The `Console.WriteLine` world is now in the HTTP world.

## JSON auto — where's the magic

You only returned an object from the lambda, who made the JSON? **ASP.NET Core automatically** turns object → JSON (for the response) and JSON → object (for the request body). No need to write `JSON.stringify` — in JS it was `res.json()`, here the serialization is done by the backend itself.

## Controller style — the classic way

Now the same work with **controllers** (you'll mostly find this in big projects):

```csharp
// Controllers/HealthController.cs
using Microsoft.AspNetCore.Mvc;

[ApiController]                    // "this is an API controller" — auto validation, JSON etc.
[Route("api/[controller]")]        // /api/health (from the name)
public class HealthController : ControllerBase
{
    [HttpGet]                      // handle GET requests
    public IActionResult Get()
    {
        return Ok(new { status = "ok", time = DateTime.Now });   // 200 + JSON
    }
}
```

And in `Program.cs` (if the template doesn't already have it):

```csharp
builder.Services.AddControllers();
...
app.MapControllers();
```

Mapping:

| Minimal API | Controller |
|---|---|
| `MapGet("/api/health", ...)` | `[HttpGet]` + class `[Route("api/...")]` |
| All routes in Program.cs | Class in `Controllers/` folder |
| Small-simple | Organized in big systems |

**You need both.** For now understand with minimal, and in the project (module 6) we'll use controllers with folder-based structure.

## How routing matches (the logic)

A request arrives `GET /api/students/5`:

1. Look at the path → which route matches `api/students/5`?
2. `api/students` + `5` → the `/api/students/{id}` endpoint caught it
3. `5` was put into the **parameter** (`int id`)
4. Method check → the GET action ran
5. Response JSON + status code

If no match → **404**. Wrong data type (`abc` where `int` 5 was needed) → **400**. These are the status codes: 200 OK, 201 Created, 400 Bad Request, 404 Not Found, 500 Server Error. The REST recap is in your WEB-DEV course — pick it up from there.

## What this is NOT

- **Web API ≠ a website** — it doesn't send an HTML page, it sends JSON. React (your frontend) sends the HTML.
- **`dotnet run` ≠ a production server** — for development. Production uses IIS/Kestrel/Docker separately (deploy module 6.4).
- **A controller isn't mandatory** — minimal APIs are real too (modern .NET pushes them). But the concept is the same for both: route → handler → JSON.
- **No API key/DB yet** — first the route + response skeleton must be clear, then in the next files we'll add EF, auth, validation.
