Pichhle file mein DTO se ye control ho gaya ki kaun si fields andar aayengi — par abhi koi check nahi hai: client ne `marks = -500` bhej diya toh seedha DB mein chala jaayega. Aur agar code ne exception feka toh user ko `500 Internal Server Error` ka akela page dikhega. API mein **validation** (galat data pehle roko) aur **error handling** (tootne pe sahi jawab do) — yehi do cheezein professional aur amateur API alag karti hain.

# Validation aur Error Handling

## Validation — pehli line of defence

**Client pe validation ≠ API pe validation.** JS form mein sab theek bhi likh lo, API ko phir bhi khud check karna chahiye — kyunki API ko koi bhi (Postman, attacker, purana app) seedha bhej sakta hai.

### Tareeka 1: DTO attributes (sabse aam)

```csharp
using System.ComponentModel.DataAnnotations;

record CreateStudentDto(
    [property: Required, StringLength(100)] string Name,
    [property: Range(0, 100)] int Marks,
    [property: EmailAddress, Required] string Email
);
```

Sirf itna — `[ApiController]` automatically check karta hai:

- `Name` khali aaya → **400** + message `"Name is required."`
- `Marks = -500` → **400** + `"Marks must be between 0 and 100."`
- Bina koi code likhe!

> **Syntax note:** record parameters pe `[property: ...]` prefix chahiye (parameter pe lag nahi sida). Class properties pe seedha `[Required]` chalta hai.

Common attributes:

| Attribute | Kaam |
|---|---|
| `[Required]` | khali nahi hona chahiye |
| `[StringLength(100)]` | max length |
| `[Range(0,100)]` | number range |
| `[EmailAddress]` | format check |
| `[RegularExpression(@"^\d{10}$")]` | custom pattern (10-digit phone) |

### Tareeka 2: manual check (jab logic ho)

```csharp
app.MapPost("/api/students", async (CreateStudentDto dto, SchoolDb db) =>
{
    if (db.Students.Any(s => s.Email == dto.Email))
        return Results.BadRequest(new { error = "Email already exists" });   // 400

    // ... save
});
```

Business rules (duplicate email, balance enough) attributes se nahi hote — seedha `if` + `BadRequest`. Dono tareeke milte hain — attributes format ke liye, `if` logic ke liye.

### Response ka format — error object

Har jagah error aisa bhejo:

```csharp
return Results.BadRequest(new { error = "Email already exists", field = "Email" });
```

```json
{ "error": "Email already exists", "field": "Email" }
```

Frontend (`React`) isi se form message dikhayega. **Consistent shape** rakho — kabhi `{error}`, kabhi `{message}`, kabhi plain text nahi — toh frontend ka code tootega.

## Error Handling — exception hua toh?

C# mein galti pe **exception** fekte hain (parse fail, DB down, divide by zero). Agar handle na karo:

- ASP.NET Core dev mein toh detail page, **production mein `500 Internal Server Error`** — koi useful message nahi (achha hai security ke liye)
- Par tumhe pata chale ki kahan galti — wahi chahiye **try-catch + logging**

```csharp
app.MapGet("/api/students/{id}", async (int id, SchoolDb db) =>
{
    try
    {
        var s = await db.Students.FindAsync(id);
        return s is null ? Results.NotFound() : Results.Ok(s);
    }
    catch (Exception ex)
    {
        // log karo (server pe dikhta hai)
        Console.WriteLine(ex);      // asli project: ILogger
        return Results.Problem("Something went wrong", statusCode: 500);
    }
});
```

`Results.Problem(...)` = RFC-7807 problem+json format — modern API standard.

### Har jagah try-catch? Nahi — middleware se ek jagah

Bade project mein har endpoint mein try-catch likhna boring hai. ASP.NET ka **exception middleware**:

```csharp
// Program.cs — startup pe ek baar
app.UseExceptionHandler(errorApp =>
{
    errorApp.Run(async context =>
    {
        context.Response.StatusCode = 500;
        context.Response.ContentType = "application/json";
        await context.Response.WriteAsJsonAsync(new { error = "Server error" });
    });
});
```

**Middleware = request ke raaste mein laga hook** (Next.js `middleware.ts` wala feel). Koi bhi endpoint pe exception → yeh ek jagah pakad ke 500 JSON bhej deta hai. Har handler saaf rehta hai.

Aur ek — **404 middleware**:

```csharp
app.Use(async (ctx, next) =>
{
    await next();                                  // baaki chalne do
    if (ctx.Response.StatusCode == 404)
    {
        ctx.Response.ContentType = "application/json";
        await ctx.Response.WriteAsJsonAsync(new { error = "Route not found" });
    }
});
```

`app.Use(...)` — middleware register. Pipeline mein order matter karta hai (jaise Express wale middleware).

## Validation pipeline ka flow (kaise chalta hai)

```
Request aayi (JSON)
   ↓
[Model binding] JSON → CreateStudentDto object
   ↓
[Validation] attributes check → fail? → 400 + errors (endpoint chala hi nahi)
   ↓
[Endpoint] tumhara code → business check (if) → save
   ↓
[Response] object → JSON + status
```

Fail hone par endpoint ka code **chalta hi nahi** — pehle hi 400. Yahi `FluentValidation` jaisi libraries bhi karti hain (advanced validation) — companies use karti hain, par built-in attributes 80% kaam ke.

## Dev vs Production wala farq

```csharp
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();   // dev mein detailed error dikhe
}
else
{
    app.UseExceptionHandler(...);      // prod mein generic 500 JSON
}
```

`appsettings.json` mein `"Environment": "Development"` — dev pe detail (debug), prod pe sirf generic message (detail leak nahi). **Yehi security best practice hai** — internal error message/stack trace kabhi client ko nahi.

## Yeh kya NAHI hai

- **Validation = frontend validation nahi** — dono karo. Frontend UX ke liye, API security ke liye (Postman se bypass ho jaata hai).
- **try-catch sab jagah = solution nahi** — jahan exception ho sakta hai wahan ya middleware mein ek jagah. Jaan-boojh ke `catch` karke chup nahi karna (swallow) — log zaroor karo.
- **500 dene ka matlab failure nahi** — kabhi-kabhi server galti hai; important hai ki **client ko structured JSON mile**, HTML error page nahi. Consistency = frontend aaram se handle kar sake.

## In Your Own Words

1. Client-side form validation hone ke baad bhi API pe validation kyun chahiye?

<details>
<summary>Sample Jawab</summary>

**Jawab:** API ko koi bhi hit kar sakta hai — Postman, attacker, purana app. Frontend validation sirf UI hai, bypass ho jaata hai. API ko har input khud check karna chahiye (attributes/`if`) — warna galat/naqli data seedhe DB mein chala jaayega.

</details>

2. `[Range(0,100)] int Marks` — galti (`-500`) aane pe kya hota hai, endpoint ka code chalta hai kya?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `[ApiController]` model validation khud karta hai — fail hone pe 400 Bad Request + validation messages return karta hai, aur **endpoint ka code chalta hi nahi**. Isliye galat data kabhi business logic/DB tak nahi pahunchta.

</details>

3. Exception handling ek jagah (middleware) karne ka fayda kya hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Har endpoint mein try-catch copy-paste nahi karna padta — ek hi middleware sab exceptions pakad ke consistent 500 JSON deta hai. Code saaf rehta hai, naya developer bhool jaaye toh bhi protection bani rehti hai, aur logging ek jagah hoti hai.

</details>

4. Production mein developer exception page (detail wala) kyun band hota hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Usme stack trace, query strings, server path sab dikhta hai — attacker ko free information. Production mein generic `{error: "Server error"}` + 500 jaata hai, detail sirf server logs mein. Dev mein detail chahiye debugging ke liye — dono ka environment alag.

</details>

API safe hai — data validate hota hai, errors structured aate hain. Par abhi koi bhi (bina password ke) API call kar sakta hai. Company ke APIs pe **login chahiye** — aur web ka standard hai **JWT**. Agla file: authentication.
