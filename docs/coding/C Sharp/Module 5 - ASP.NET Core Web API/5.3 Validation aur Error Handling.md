In the last file, DTOs controlled which fields come in — but there's no check yet: if the client sent `marks = -500`, it goes straight into the DB. And if the code threw an exception, the user would see a bare `500 Internal Server Error` page. In an API, **validation** (stop bad data first) and **error handling** (give the right answer when things break) — these two things separate a professional API from an amateur one.

# Validation and Error Handling

## Validation — first line of defence

**Client-side validation ≠ API-side validation.** Even if everything's perfect in the JS form, the API must check on its own — because anyone (Postman, an attacker, an old app) can send directly to the API.

### Way 1: DTO attributes (most common)

```csharp
using System.ComponentModel.DataAnnotations;

record CreateStudentDto(
    [property: Required, StringLength(100)] string Name,
    [property: Range(0, 100)] int Marks,
    [property: EmailAddress, Required] string Email
);
```

That's all — `[ApiController]` checks automatically:

- `Name` came empty → **400** + message `"Name is required."`
- `Marks = -500` → **400** + `"Marks must be between 0 and 100."`
- Without writing any code!

> **Syntax note:** on record parameters you need the `[property: ...]` prefix (can't apply directly to the parameter). On class properties, `[Required]` works directly.

Common attributes:

| Attribute | Job |
|---|---|
| `[Required]` | must not be empty |
| `[StringLength(100)]` | max length |
| `[Range(0,100)]` | number range |
| `[EmailAddress]` | format check |
| `[RegularExpression(@"^\d{10}$")]` | custom pattern (10-digit phone) |

### Way 2: manual check (when there's logic)

```csharp
app.MapPost("/api/students", async (CreateStudentDto dto, SchoolDb db) =>
{
    if (db.Students.Any(s => s.Email == dto.Email))
        return Results.BadRequest(new { error = "Email already exists" });   // 400

    // ... save
});
```

Business rules (duplicate email, enough balance) can't be attributes — straight `if` + `BadRequest`. Both ways mix — attributes for format, `if` for logic.

### Response format — the error object

Send errors everywhere like this:

```csharp
return Results.BadRequest(new { error = "Email already exists", field = "Email" });
```

```json
{ "error": "Email already exists", "field": "Email" }
```

The frontend (React) shows the form message from this. **Keep a consistent shape** — sometimes `{error}`, sometimes `{message}`, sometimes plain text never — or the frontend code breaks.

## Error Handling — what if an exception happens?

In C#, when something goes wrong it **throws an exception** (parse fail, DB down, divide by zero). If you don't handle it:

- In dev, a detail page; **in production `500 Internal Server Error`** — no useful message (good for security)
- But you want to know where it broke — that's where **try-catch + logging** comes in

```csharp
app.MapGet("/api/students/{id}", async (int id, SchoolDb db) =>
{
    try
    {
        var s = await db.Students.FindAsync(id);
        return s is null ? Results.NotFound() : Results.Ok(s);
    }
    catch (Exception ex)
    {
        // log it (shows on the server)
        Console.WriteLine(ex);      // real project: ILogger
        return Results.Problem("Something went wrong", statusCode: 500);
    }
});
```

`Results.Problem(...)` = RFC-7807 problem+json format — modern API standard.

### try-catch everywhere? No — one place via middleware

In a big project, writing try-catch in every endpoint is boring. ASP.NET's **exception middleware**:

```csharp
// Program.cs — once at startup
app.UseExceptionHandler(errorApp =>
{
    errorApp.Run(async context =>
    {
        context.Response.StatusCode = 500;
        context.Response.ContentType = "application/json";
        await context.Response.WriteAsJsonAsync(new { error = "Server error" });
    });
});
```

**Middleware = a hook in the request's path** (Next.js `middleware.ts` kind of feel). Any endpoint throwing an exception → this one place catches it and sends a 500 JSON. Every handler stays clean.

And one more — **404 middleware**:

```csharp
app.Use(async (ctx, next) =>
{
    await next();                                  // let the rest run
    if (ctx.Response.StatusCode == 404)
    {
        ctx.Response.ContentType = "application/json";
        await ctx.Response.WriteAsJsonAsync(new { error = "Route not found" });
    }
});
```

`app.Use(...)` — register middleware. Order matters in the pipeline (like Express middleware).

## Validation pipeline flow (how it runs)

```
Request arrives (JSON)
   ↓
[Model binding] JSON → CreateStudentDto object
   ↓
[Validation] attributes check → fail? → 400 + errors (endpoint doesn't run at all)
   ↓
[Endpoint] your code → business check (if) → save
   ↓
[Response] object → JSON + status
```

On failure the endpoint code **doesn't run at all** — 400 comes first. Libraries like `FluentValidation` do the same thing (advanced validation) — used in big projects, but built-in attributes cover 80% of the work.

## Dev vs Production difference

```csharp
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();   // detailed error in dev
}
else
{
    app.UseExceptionHandler(...);      // generic 500 JSON in prod
}
```

In `appsettings.json`, `"Environment": "Development"` — detail on dev (debug), only generic message on prod (no detail leak). **This is the security best practice** — internal error message/stack trace never goes to the client.

## What this is NOT

- **Validation ≠ frontend validation** — do both. Frontend for UX, API for security (gets bypassed via Postman).
- **try-catch everywhere ≠ the solution** — put it where an exception can happen, or in one place in middleware. Don't catch and swallow on purpose — always log.
- **Returning 500 ≠ failure** — sometimes it's a server mistake; what matters is that **the client gets a structured JSON**, not an HTML error page. Consistency = frontend can handle it easily.

## In Your Own Words

1. Why is API-side validation needed even after client-side form validation?

<details>
<summary>Sample Answer</summary>

**Answer:** Anyone can hit the API — Postman, an attacker, an old app. Frontend validation is only UI, it gets bypassed. The API must check every input itself (attributes/`if`) — otherwise bad/fake data goes straight into the DB.

</details>

2. With `[Range(0,100)] int Marks`, if a mistake (`-500`) comes, what happens — does the endpoint code run?

<details>
<summary>Sample Answer</summary>

**Answer:** `[ApiController]` does model validation itself — on failure it returns 400 Bad Request + validation messages, and **the endpoint code doesn't run at all**. So bad data never reaches business logic/the DB.

</details>

3. What's the benefit of handling exceptions in one place (middleware)?

<details>
<summary>Sample Answer</summary>

**Answer:** No copy-paste try-catch in every endpoint — one middleware catches all exceptions and gives a consistent 500 JSON. Code stays clean, even if a new developer forgets, protection remains, and logging happens in one place.

</details>

4. Why is the developer exception page (with detail) turned off in production?

<details>
<summary>Sample Answer</summary>

**Answer:** It shows stack trace, query strings, server path — free information for an attacker. Production sends a generic `{error: "Server error"}` + 500, detail only in server logs. In dev you need detail for debugging — the environments are separate.

</details>
