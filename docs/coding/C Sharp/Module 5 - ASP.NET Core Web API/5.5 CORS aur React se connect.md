With JWT your API is protected — but one problem still remains. Your React app runs at `localhost:3000`, the API at `localhost:5000` — the browser treats them as **different origins** and blocks a direct fetch. This problem is **CORS**, and after that the whole flow that was in your Next.js projects (env, API base URL, error handling) — from the API side.

# CORS and connecting from React

## The problem — why the browser blocks it

You wrote `fetch('http://localhost:5000/api/students')` in React, and in the console:

```
Access to fetch at 'http://localhost:5000/...' from origin
'http://localhost:3000' has been blocked by CORS policy
```

**CORS = Cross-Origin Resource Sharing.** Browser security rule: one page may request data from another "origin" (domain + port + protocol) — **the server must grant permission first.** This restriction is **only in the browser** — the same API runs fine from Postman/curl (that's why debugging feels different).

The logic: an `evil.com` page shouldn't be able to use your `bank.com` session cookie/data — that's why the browser blocks by default. The API must say "yes, allow `localhost:3000`".

## Server-side fix — 3 lines

```csharp
// Program.cs — before builder.Build()
builder.Services.AddCors(options =>
{
    options.AddPolicy("Frontend", policy =>
        policy.WithOrigins("http://localhost:3000")     // only your React dev URL
              .AllowAnyHeader()                          // Authorization header etc.
              .AllowAnyMethod());                        // POST/PUT/DELETE
});

// ...after Build(), before endpoints:
app.UseCors("Frontend");
```

Two places: **create the policy** in the service (on the builder), **apply the middleware** (`UseCors`) — before the endpoints so the header gets added to every response.

The server response now carries this header:

```
Access-Control-Allow-Origin: http://localhost:3000
```

Now the browser is happy — fetch from React works.

### Also understand preflight

When the request isn't a simple GET (custom header, POST with `Content-Type: application/json`), the browser first sends an **OPTIONS request** — "tell me first, can I send this?" The server answers with `Allow-Origin`/`Allow-Headers`, then the real request goes. `.AllowAnyHeader/Method` is for this preflight. No need to write an OPTIONS handler — the middleware does it itself.

### In production

```csharp
.WithOrigins("https://tumsiwebsite.com")     // not the dev URL, the real domain
```

Or multiple:

```csharp
.WithOrigins("https://app.example.com", "https://admin.example.com")
```

**`AllowAnyOrigin()` allows everyone** — works in dev, fails security review in production. Always specific origins.

## React side — the complete flow (your world)

```javascript
// .env (React side)
VITE_API_URL=http://localhost:5000        // Next.js: NEXT_PUBLIC_API_URL

// api.js — base URL in one place
const API = import.meta.env.VITE_API_URL;

export async function getStudents() {
  const token = localStorage.getItem("token");
  const res = await fetch(`${API}/api/students`, {
    headers: { "Authorization": `Bearer ${token}` },
  });
  if (!res.ok) throw new Error("API fail");     // handle status code
  return res.json();
}

export async function login(email, password) {
  const res = await fetch(`${API}/api/login`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email, password }),
  });
  if (!res.ok) return null;                     // 401
  const { token } = await res.json();
  localStorage.setItem("token", token);
  return token;
}
```

**Look what got added:**

1. **Base URL in `.env`** — no hardcoded `localhost:5000` (module 4.3's rule, from the other side)
2. **`Authorization: Bearer`** header — the JWT flow (5.4)
3. **`res.ok` check** — `throw` on 400/404/500, otherwise wrong data in the UI
4. **`res.json()`** — the same thing the backend was auto-sending as JSON

This is the same pattern that was in your Next.js API routes — only the roles are reversed: **your React is the client, and the backend is ASP.NET Core.**

## Debugging checklist (when it doesn't work)

1. **CORS error in console?** → API side `UseCors` policy + `UseCors` before endpoints. Hit OPTIONS request from Postman — are headers coming?
2. **401?** → missing/expired token — check `Authorization` header, check `UseAuthentication` order
3. **404?** → route match (`/api/...`), trailing slash, wrong port
4. **400?** → JSON body shape must match the DTO (`Content-Type: application/json` forgotten → won't bind)
5. **Request not even showing in Network tab?** → check URL/port, or CORS preflight failed

CORS policy changed in dev → **restart the API** (`dotnet run` again) — the policy is built at startup.

## What this is NOT

- **CORS ≠ API security** — CORS only blocks the **browser**. From Postman/curl everything works. Real security = JWT + validation (5.3/5.4). `AllowAnyOrigin` doesn't give "security".
- **CORS error ≠ backend code** — the API is perfectly fine, it's a browser policy issue. That's why "works in Postman, not in browser" = 99% CORS.
- **No secrets in React `.env`** — `NEXT_PUBLIC_`/`VITE_` values are visible to the browser (anyone can see). Only public config (URL) — secret keys never on the frontend. Secrets stay with the API.

## In Your Own Words

1. Why does the CORS error happen — and why only in the browser (not in Postman)?

<details>
<summary>Sample Answer</summary>

**Answer:** React at `localhost:3000` calls the API at `localhost:5000` (different origin). The browser blocks cross-origin requests by default (to prevent data theft), and the server must grant permission via the `Access-Control-Allow-Origin` header. Postman isn't a browser, so this rule doesn't apply there.

</details>

2. What are the 2 steps (service + middleware) to enable CORS on the API side?

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Create the policy in `builder.Services.AddCors()` (`WithOrigins("http://localhost:3000")`, allow header/method), (2) `app.UseCors("Frontend")` — before endpoints. Both are needed, otherwise the header doesn't go out.

</details>

3. What's the benefit of keeping the API URL in `.env` — and why no secrets in frontend `.env`?

<details>
<summary>Sample Answer</summary>

**Answer:** Changing the URL (dev/prod) only needs the env file changed, not code — and different environments get different endpoints. But frontend env values get bundled into the build and anyone can see them in the browser — so only public stuff (URL), secrets (DB/API keys) always in the API's user-secrets/server env.

</details>

4. Steps to `POST /api/login` from React — from request to using the token.

<details>
<summary>Sample Answer</summary>

**Answer:** (1) `fetch` with `method: POST`, `Content-Type: application/json`, body = JSON-stringified credentials, (2) `res.json()` to get the token from the response, (3) store the token (localStorage/memory), (4) `Authorization: Bearer <token>` header on every protected request, (5) backend `AddJwtBearer` middleware verifies and grants access.

</details>
