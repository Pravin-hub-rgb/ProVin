Until now your API was open — anyone could do `POST /api/students` from Postman. In a real app it's not like that: only a logged-in user should get data, and the admin endpoint only for admins. The standard web authentication you may have done in React projects with cookies/sessions — here you'll learn **JWT (JSON Web Tokens)**.

# JWT Auth

## The concept first — how do you know who it is after login?

HTTP is stateless — every request is separate. The server must know "who is this" every time. Two ways:

**Session/Cookie (the React/Next way):** login → server creates a session ID → browser stores it in a cookie → every request sends the cookie. Server looks it up. **Tightly coupled** — server needs a session store (Redis/DB), hard to scale horizontally.

**JWT (the API way):** login → server gives a **signed token** → client sends it with every request → server **checks the signature** and understands who it is on its own. **Stateless** — server stores nothing. Mobile apps + distributed APIs standard.

> Cookie-based still works (still used in browser apps today), but in mobile/SPA APIs **JWT is the standard**.

## What a token looks like

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJ1c2VyIn0.abc123signature
```

**3 parts, separated by dots:**

1. **Header** — says which algorithm (HS256)
2. **Payload** — **claims** (data): `sub` (user id), `role`, `exp` (expiry). Base64 — **not encrypted, it gets decoded!** Secret/password never goes in the payload.
3. **Signature** — a hash made from header + payload + secret — **tamper it and it's rejected**

The idea is simple: **the data is with you, the seal is with you** — the server only verifies with the secret that the token is genuine and unchanged.

## Flow — from login to a protected endpoint

```
1. POST /api/login {email, password}
2. Server checks → correct? → made the JWT (signed with secret) → sent in response
3. Client saves the token (localStorage/memory)
4. Every request:  Authorization: Bearer <token>
5. Server middleware verifies → user data in context → endpoint runs
```

## Implementation — 3 steps

### Step 1: Login endpoint + making the token

```csharp
// NuGet: Microsoft.AspNetCore.Authentication.JwtBearer
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using Microsoft.IdentityModel.Tokens;
using System.Text;

app.MapPost("/api/login", async (LoginDto dto, SchoolDb db) =>
{
    var user = await db.Users.FirstOrDefaultAsync(u => u.Email == dto.Email);
    if (user is null || !BCrypt.Net.BCrypt.Verify(dto.Password, user.PasswordHash))
        return Results.Unauthorized();                       // 401

    var claims = new[]
    {
        new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
        new Claim(ClaimTypes.Email, user.Email),
        new Claim(ClaimTypes.Role, user.Role)
    };

    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(
        builder.Configuration["Jwt:Secret"]!));             // secret from appsettings ⭐

    var token = new JwtSecurityToken(
        issuer: "MyApp",
        audience: "MyAppClients",
        claims: claims,
        expires: DateTime.UtcNow.AddMinutes(60),
        signingCredentials: new SigningCredentials(key, SecurityAlgorithms.HmacSha256));

    return Results.Ok(new { token = new JwtSecurityTokenHandler().WriteToken(token) });
});
```

Line by line:

- **Never check password in plain** — compare with `PasswordHash` (`BCrypt.Verify`). Store a hash in the DB, never plain (security rule).
- **Claims** = payload data (who, what role). `ClaimTypes.Role` is used in authorization.
- **Secret** is in `appsettings.json` + user-secrets — not in code (module 4.3's rule).
- `expires` — token dies after 60 min. Short expiry = less risk if leaked.

### Step 2: Verifying on the server (middleware)

```csharp
// Program.cs — startup
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(opt =>
    {
        opt.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidIssuer = "MyApp",
            ValidAudience = "MyAppClients",
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(builder.Configuration["Jwt:Secret"]!))
        };
    });
builder.Services.AddAuthorization();

// ...after builder.Build():
app.UseAuthentication();    // verify token first
app.UseAuthorization();     // then permission check
```

**Wrong/expired/missing signature → the middleware itself returns 401** — your endpoint code doesn't run at all. Same middleware pattern (like module 5.3) — no need to write the check everywhere.

### Step 3: Protected endpoint

```csharp
app.MapPost("/api/students", async (CreateStudentDto dto, ClaimsPrincipal user, SchoolDb db) =>
{
    var userId = user.FindFirstValue(ClaimTypes.NameIdentifier);   // came from the token!
    // ... save with userId
}).RequireAuthorization();      // ⭐ only for token holders

app.MapGet("/api/admin/users", async (SchoolDb db) =>
    Results.Ok(await db.Users.ToListAsync()))
   .RequireAuthorization(policy => policy.RequireRole("Admin"));   // only Admin
```

- `.RequireAuthorization()` — without a token, 401
- `.RequireRole("Admin")` — checks the role in the token
- `ClaimsPrincipal user` — injected, claims (user id, role) are pulled from inside

**Client side (in React):**

```javascript
fetch("/api/students", {
  headers: { "Authorization": `Bearer ${token}` }
});
```

The header name is fixed: **`Authorization: Bearer <token>`** — this is what the backend expects.

## What JWT is NOT (very important)

- **Data isn't hidden in the token** — it's Base64, anyone can decode and read it. **Secret/password/any private thing never goes in the payload.** Only identifying claims.
- **JWT verifies, doesn't encrypt** — signature = "it's genuine" (integrity), not hiding (confidentiality). https is still required.
- **No session store in the DB** — that's its benefit (stateless). But that means: revoking a token (server-side logout) is hard — keep expiry short or use a blacklist (advanced).
- **Hash ≠ encryption** — password hash (BCrypt) is one-way; the plain can't be recovered. JWT's signature is also a hash, but the data is open.

## What this is NOT (practice)

- **`app.UseAuthentication` missing → `RequireAuthorization` won't work** — order matters (authn first, then authz).
- **Expiry isn't optional** — without `exp` the token runs forever — leak = forever danger. 15-60 min typical (refresh token = advanced).
- **The login endpoint has no authorization** — it must be open (that's where people come to get the token).

## In Your Own Words

1. Difference between JWT and session/cookie in terms of statefulness, and why JWT for APIs?

<details>
<summary>Sample Answer</summary>

**Answer:** In sessions the server stores (stateful — Redis/DB lookup), in JWT the server stores nothing — the token itself has data + signature, verify and you're done (stateless). JWT is used in APIs/mobile apps because every client (app/web) sends the same header, and when scaling the server there's no need for a shared session store.

</details>

2. Why shouldn't secret/password go in the JWT payload — what's the real structure of a token?

<details>
<summary>Sample Answer</summary>

**Answer:** The payload is Base64 — anyone can decode and read it (not encrypted). Token = header + claims (identity, role, expiry) + signature (with secret). The secret is only for **creating/verifying** — never inside the token; put it inside and everyone sees it.

</details>

3. What setup is needed in `Program.cs` before writing `.RequireAuthorization()` — and what happens with a wrong token?

<details>
<summary>Sample Answer</summary>

**Answer:** `AddAuthentication` + `AddJwtBearer` (validation parameters: key, issuer, audience) and `app.UseAuthentication/UseAuthorization` middleware. With a wrong/missing/expired token, the middleware itself returns **401** — the endpoint code doesn't run.

</details>

4. How is the password checked at login and what's stored in the DB?

<details>
<summary>Sample Answer</summary>

**Answer:** The DB stores the password **hash** (BCrypt), never plain. At login, the entered password is checked via `BCrypt.Verify(hash, input)` — match means token, otherwise 401. The hash is one-way, so even if the DB leaks the password can't be recovered.

</details>
