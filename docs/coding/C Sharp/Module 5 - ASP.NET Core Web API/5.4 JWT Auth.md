Ab tak tumhari API koi bhi khulla tha — Postman se koi bhi `POST /api/students` kar sakta hai. Asli app mein aisa nahi hota: sirf login kiye hue user ko data milna chahiye, aur admin wala endpoint sirf admin ko. Web ka standard authentication hai jo shayad tumne React projects mein cookie/session se kiya hoga — yahan seekhoge **JWT (JSON Web Tokens)**.

# JWT Auth

## Pehle concept — login ke baad kaise pehchante ho?

HTTP stateless hai — har request alag. Server ko har baar pata hona chahiye "ye kaun hai". Do tareeke:

**Session/Cookie (React/Next wala):** login → server ek session ID banata → browser cookie mein rakhta → har request cookie bhejta hai. Server lookup karta hai. **Tightly coupled** — server ko session store chahiye (Redis/DB), horizontal scaling mein dikkat.

**JWT (API wala):** login → server ek **signed token** deta → client use har request mein bhejta hai → server **signature check** karke khud hi samajh jaata hai kaun. **Stateless** — server kuch store nahi karta. Mobile apps + distributed APIs mein standard.

> Cookie wala bhi chalta hai (browser apps mein aaj bhi hota hai), par job interview aur mobile/SPA APIs mein **JWT hi poochha jaata hai**.

## Token kaise dikhta hai

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJ1c2VyIn0.abc123signature
```

**3 parts, dots se:**

1. **Header** — algorithm batata hai (HS256)
2. **Payload** — **claims** (data): `sub` (user id), `role`, `exp` (expiry). Base64 — **encrypted nahi, decode ho jaata hai!** Secret/password kabhi payload mein nahi.
3. **Signature** — header + payload + secret se bana hash — **chheda toh reject**

Idea simple: **data bhi tumhare paas, seal bhi tumhare paas** — server sirf secret se verify karta hai ki token asli hai aur kisi ne badla nahi.

## Flow — login se lekar protected endpoint tak

```
1. POST /api/login {email, password}
2. Server check → sahi? → JWT banaya (secret se sign) → response mein bheja
3. Client token save (localStorage/memory)
4. Har request mein:  Authorization: Bearer <token>
5. Server middleware verify → user ka data context mein → endpoint chalao
```

## Implementation — 3 step

### Step 1: Login endpoint + token banana

```csharp
// NuGet: Microsoft.AspNetCore.Authentication.JwtBearer
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using Microsoft.IdentityModel.Tokens;
using System.Text;

app.MapPost("/api/login", async (LoginDto dto, SchoolDb db) =>
{
    var user = await db.Users.FirstOrDefaultAsync(u => u.Email == dto.Email);
    if (user is null || !BCrypt.Net.BCrypt.Verify(dto.Password, user.PasswordHash))
        return Results.Unauthorized();                       // 401

    var claims = new[]
    {
        new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
        new Claim(ClaimTypes.Email, user.Email),
        new Claim(ClaimTypes.Role, user.Role)
    };

    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(
        builder.Configuration["Jwt:Secret"]!));             // appsettings se secret ⭐

    var token = new JwtSecurityToken(
        issuer: "MyApp",
        audience: "MyAppClients",
        claims: claims,
        expires: DateTime.UtcNow.AddMinutes(60),
        signingCredentials: new SigningCredentials(key, SecurityAlgorithms.HmacSha256));

    return Results.Ok(new { token = new JwtSecurityTokenHandler().WriteToken(token) });
});
```

Line by line:

- **Password kabhi plain check nahi** — `PasswordHash` se compare (`BCrypt.Verify`). DB mein hash rakho, plain kabhi nahi (DBMS/interview wala point).
- **Claims** = payload ka data (kaun, role kya). `ClaimTypes.Role` authorization mein kaam aayega.
- **Secret** `appsettings.json` + user-secrets mein — code mein nahi (module 4.3 wala rule).
- `expires` — 60 min baad token dead. Short expiry = leak hone pe kam khatra.

### Step 2: Server pe verify karna (middleware)

```csharp
// Program.cs — startup
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(opt =>
    {
        opt.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidIssuer = "MyApp",
            ValidAudience = "MyAppClients",
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(builder.Configuration["Jwt:Secret"]!))
        };
    });
builder.Services.AddAuthorization();

// ...builder.Build() ke baad:
app.UseAuthentication();    // pehle token verify ho
app.UseAuthorization();     // phir permission check
```

**Signature galat/expired/missing → middleware khud 401** de deta hai — tumhare endpoint ka code chalta hi nahi. Yahi middleware pattern (module 5.3 jaisa) — har jagah check nahi likhna padta.

### Step 3: Protected endpoint

```csharp
app.MapPost("/api/students", async (CreateStudentDto dto, ClaimsPrincipal user, SchoolDb db) =>
{
    var userId = user.FindFirstValue(ClaimTypes.NameIdentifier);   // token se mila!
    // ... save with userId
}).RequireAuthorization();      // ⭐ sirf token wale ko

app.MapGet("/api/admin/users", async (SchoolDb db) =>
    Results.Ok(await db.Users.ToListAsync()))
   .RequireAuthorization(policy => policy.RequireRole("Admin"));   // sirf Admin
```

- `.RequireAuthorization()` — bina token 401
- `.RequireRole("Admin")` — token mein role check
- `ClaimsPrincipal user` — inject ho gaya, andar se claims (user id, role) nikalte hain

**Client side (React mein):**

```javascript
fetch("/api/students", {
  headers: { "Authorization": `Bearer ${token}` }
});
```

Header ka naam fix hai: **`Authorization: Bearer <token>`** — yehi backend expect karta hai.

## JWT kya NAHI hai (bahut zaroori)

- **Token mein data chhupa nahi** — Base64 hai, koi bhi decode karke sab padh sakta hai. **Secret/password/koi bhi private cheez payload mein kabhi nahi.** Sirf pehchan wale claims.
- **JWT verify karta hai, encrypt nahi** — signature = "asli hai" (integrity), chhupana nahi (confidentiality). https zaroori rehta hai.
- **DB mein session store nahi hota** — yahi iska faayda hai (stateless). Par iska matlab: token revoke karna mushkil (logout server-side) — expiry short rakho ya blacklist (advanced).
- **Hash = encryption nahi** — password hash (BCrypt) one-way hai; plain wapas nahi milta. JWT ka signature bhi hash hai, data khula hai.

## Yeh kya NAHI hai (practice)

- **`app.UseAuthentication` ke bina `RequireAuthorization` kaam nahi karta** — order matter karta hai (pehle authn, phir authz).
- **Expiry optional nahi** — bina `exp` token hamesha chalega — leak = hamesha khatra. 15-60 min typical (refresh token = advanced).
- **Login endpoint pe authorization nahi** — woh khulla hona chahiye (wahi toh token lene aate hain).

## In Your Own Words

1. JWT aur session/cookie — statefulness ke hisaab se farq, aur APIs mein JWT kyun?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Session mein server store karta hai (stateful — Redis/DB lookup), JWT mein server kuch nahi rakhta — token me hi data + signature hota hai, verify karke chal dete hain (stateless). APIs/mobile apps mein JWT isliye kyunki har client (app/web) same header bhej deta hai, aur server scale karne pe shared session store ki zaroorat nahi.

</details>

2. JWT payload mein password/secret kyun nahi rakhna chahiye — token ka asli structure kya hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Payload Base64 hai — koi bhi decode karke padh sakta hai (encryption nahi). Token = header + claims (pehchan, role, expiry) + signature (secret se). Secret sirf **banane/verify** ke liye hota hai, token ke andar nahi — andar daala toh sab dekh lenge.

</details>

3. `.RequireAuthorization()` likhne se pehle `Program.cs` mein kya setup chahiye — aur galat token pe kya hota hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `AddAuthentication` + `AddJwtBearer` (validation parameters: key, issuer, audience) aur `app.UseAuthentication/UseAuthorization` middleware. Galat/missing/expired token pe middleware hi **401** de deta hai — endpoint ka code chalta hi nahi.

</details>

4. Login pe password kaise check kiya jaata hai aur DB mein kya rakha jaata hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** DB mein password **hash** (BCrypt) rakha jaata hai, plain kabhi nahi. Login pe user ka entered password `BCrypt.Verify(hash, input)` se check hota hai — match toh token, warna 401. Hash one-way hai, DB leak hone pe bhi password wapas nahi milta.

</details>

Auth se tumhari API ab guarded hai — par ek last problem: tumhara React app `localhost:3000` se call karega aur API `localhost:5000` pe hai — **browser cross-origin requests rok deta hai**. Yahi hai agla file: **CORS** — aur uske saath React se API connect karne ka poora flow.
