In the last file we ran the first GET endpoint — but it was static. A real API has to do 4 things: **find data by ID, take new data (POST), change it (PUT), remove it (DELETE)** — and the objects going in/out in between must be kept in **DTOs**. This file has all of it.

# Endpoints, Routing and DTOs

## The 4 CRUD endpoints — in one place

For a students resource:

```
GET    /api/students       → list all
GET    /api/students/5     → one (Id=5)
POST   /api/students       → create new
PUT    /api/students/5     → update
DELETE /api/students/5     → remove
```

This is the **REST** pattern (covered in detail in the WEB-DEV course) — URLs by resource name, work by HTTP method. Now in C#:

```csharp
// Program.cs (minimal API style) — with EF
app.MapGet("/api/students", async (SchoolDb db) =>
    await db.Students.ToListAsync());

app.MapGet("/api/students/{id}", async (int id, SchoolDb db) =>
    await db.Students.FindAsync(id) is Student s
        ? Results.Ok(s)
        : Results.NotFound());          // 404

app.MapPost("/api/students", async (CreateStudentDto dto, SchoolDb db) =>
{
    var student = new Student { Name = dto.Name, Marks = dto.Marks };
    db.Students.Add(student);
    await db.SaveChangesAsync();
    return Results.Created($"/api/students/{student.Id}", student);   // 201
});
```

Look at the **routing syntax**:

- `{id}` — **route parameter**: that part of the URL becomes a variable (`/api/students/5` → `id = 5`)
- **lambda parameters get injected**: `(int id, SchoolDb db)` — `id` from the URL, `db` from the server (DI, next point)

And the **HTTP status codes** game:

```csharp
Results.Ok(data)           // 200 — all good
Results.Created(url, data) // 201 — new thing created
Results.NotFound()         // 404 — not found
Results.BadRequest(msg)    // 400 — client's mistake
```

The JS `res.status(201)` kind of work — here it's clear from method names.

## DTO — Data Transfer Object

**Question:** on `POST /api/students` the client can send anything:

```json
{ "name": "Vin", "marks": 90, "isAdmin": true, "salary": 999999 }
```

If you use the DB's `Student` class directly, where do `isAdmin`, `salary` go? **Mass assignment** mistake — the user made themselves admin. **That's why a separate class — only what's needed:**

```csharp
// Coming in from the client — input only
record CreateStudentDto(string Name, int Marks);

// Going out to the client — output only (hide sensitive)
record StudentDto(int Id, string Name, int Marks);
```

`record` = small data class (the most popular form of DTO in C#). Now:

```csharp
app.MapPost("/api/students", async (CreateStudentDto dto, SchoolDb db) =>
{
    var student = new Student { Name = dto.Name, Marks = dto.Marks };  // only needed ones
    db.Students.Add(student);
    await db.SaveChangesAsync();

    var outDto = new StudentDto(student.Id, student.Name, student.Marks);
    return Results.Created($"/api/students/{outDto.Id}", outDto);
});
```

**Rule:** `CreateXxxDto`/`UpdateXxxDto` for input, `XxxDto` for output, and the model is for the DB. 3 classes feel heavy, but you get security + a clear API — this is the pattern in every big project.

One more benefit — **DB stuff doesn't go out:** password hash, internal flags — none of them exist in `StudentDto`.

## The same thing in controller style

```csharp
[ApiController]
[Route("api/students")]
public class StudentsController : ControllerBase
{
    private readonly SchoolDb _db;
    public StudentsController(SchoolDb db) { _db = db; }   // DI — next section

    [HttpGet]
    public async Task<IActionResult> GetAll() =>
        Ok(await _db.Students.ToListAsync());

    [HttpGet("{id:int}")]                       // ⭐ constraint: only int
    public async Task<IActionResult> Get(int id)
    {
        var s = await _db.Students.FindAsync(id);
        return s is null ? NotFound() : Ok(s);
    }

    [HttpPost]
    public async Task<IActionResult> Create(CreateStudentDto dto)
    {
        var student = new Student { Name = dto.Name, Marks = dto.Marks };
        _db.Students.Add(student);
        await _db.SaveChangesAsync();
        return CreatedAtAction(nameof(Get), new { id = student.Id }, student);
    }
}
```

Differences: `Ok/NotFound` (ControllerBase methods), `[HttpGet("{id:int}")]` route constraint, and `SchoolDb _db` in the class constructor — this is **Dependency Injection**:

```csharp
builder.Services.AddDbContext<SchoolDb>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("SchoolDb")));
```

**What DI means:** you don't `new` a `SchoolDb` — it's already built at server startup, and gets **injected** into the constructor. A fresh connection + config per request — this is **.NET's most everyday pattern** (`builder.Services.Add...` + constructor). Next.js context/config kind of feel.

## Query parameters — filter/sort (the `?` in the URL)

```csharp
// GET /api/students?minMarks=80&sort=desc
app.MapGet("/api/students", async (int? minMarks, string? sort, SchoolDb db) =>
{
    var q = db.Students.AsQueryable();
    if (minMarks is not null) q = q.Where(s => s.Marks >= minMarks);
    if (sort == "desc") q = q.OrderByDescending(s => s.Marks);
    return await q.ToListAsync();
});
```

`?minMarks=80` — **query string** parameters. `int?` (nullable) because they're optional. In JS it was `new URLSearchParams(location.search)`, here the framework parses and gives the parameter itself. Pagination (`page`, `pageSize`), search (`q`), filter — all come here.

## Routing rules (common mistakes)

- Route is case-insensitive (`/api/Students` ≈ `/api/students`) but keep consistency — all lowercase
- Add a **constraint** like `{id:int}` — if `abc` comes, 404/400, the handler doesn't run
- **Conflict** on a route (two GETs on same path) → error at startup
- **HTTP method match** — a GET on a `[HttpPost]` endpoint gives 405

## What this is NOT

- **DTO ≠ DB model** — model is for the DB, DTO is for the client contract. Keep them separate — production rule (security + flexibility).
- **Route parameter `{id}` ≠ query parameter `?id=`** — the path one identifies the resource (`/students/5`), the query one gives filter/options (`?minMarks=80`).
- **`CreatedAt` (201) not everywhere** — 201 on POST (new thing), 200 otherwise. Conventions are REST's — swagger generates from these too.

## In Your Own Words

1. The 4 HTTP methods of REST CRUD and their jobs — against a students resource.

<details>
<summary>Sample Answer</summary>

**Answer:** `GET /api/students` = list (read), `POST /api/students` = new row (201 Created), `PUT /api/students/5` = full update, `DELETE /api/students/5` = delete. The path says which resource, the method says what to do — that's the REST contract.

</details>

2. Why DTOs — what's the danger of taking the `Student` model directly in the POST body?

<details>
<summary>Sample Answer</summary>

**Answer:** Mass assignment danger — the client sends fields like `isAdmin`, `salary`, `id` and they go straight into the DB. `CreateStudentDto` has only allowed fields — extras ignored. Also, sensitive fields (password) get hidden on the way out via `StudentDto`.

</details>

3. `{id}` route parameter vs `?minMarks=80` query parameter — when which?

<details>
<summary>Sample Answer</summary>

**Answer:** `{id}` = part of the URL path — identifies the resource (`/students/5` = which student), required. Query param after `?` — gives filter/options (`minMarks`, `sort`, `page`), optional, and one path can serve different views.

</details>

4. What does Dependency Injection (`builder.Services.AddDbContext` + constructor) do?

<details>
<summary>Sample Answer</summary>

**Answer:** The service (like SchoolDb) is **given** through the constructor — you don't `new` it. It's registered at startup (`AddDbContext`), and the framework injects it on every request. Config lives in one place, testing is easy, and the server controls the dependency.

</details>
