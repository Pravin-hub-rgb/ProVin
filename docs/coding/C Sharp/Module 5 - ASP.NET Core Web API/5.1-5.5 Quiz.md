## MCQ

Q: Web API aur React frontend ka rishta kya hai?
A. Dono browser mein chalte hain
B. React UI dikhata hai aur API call karta hai; API JSON data deta hai (database se)
C. API HTML render karta hai jo React dikhata hai
D. React hi backend hai
> B. Division of labour: React = client UI (browser), ASP.NET Core API = data + logic (server). HTTP se baat karte hain, JSON mein data aata-jata hai. Tumhara Next.js API route bhi yahi karta tha — bas backend framework alag.

---

Q: `POST /api/students` banane ke liye kaunsa HTTP method + route sahi hai?
A. `GET /api/students`
B. `POST /api/students` — body ke saath nayi resource
C. `GET /api/students/new`
D. `PUT /api/students`
> B. REST pattern: GET = padhna, POST = nayi banao (201 Created), PUT = update, DELETE = hatana. Path resource ka naam (`/students`), method kaam (`POST`) — yahi contract hai.

Q: DTO (CreateStudentDto) kyun use karte hain — seedha `Student` model lene se kya dikkat hai?
A. DTO fast hai
B. Mass assignment — client extra fields (isAdmin, salary) bhej sakta hai jo seedhe DB mein chali jaati; aur sensitive fields bahar leak ho sakti hain
C. Model se JSON banta nahi
D. DTO bina compile chalta hai
> B. DTO client ka contract set karta hai — sirf allowed fields andar, aur output DTO mein sirf jo dikhana hai. Security (mass assignment, data leak) + clear API dono milte hain.

Q: `[Range(0,100)] int Marks` mein client ne `-500` bheja toh kya hoga?
A. `-500` DB mein chala jaayega
B. Endpoint chalega par warning de dega
C. 400 Bad Request + validation error, endpoint ka code chalega hi nahi
D. Program crash
> C. `[ApiController]` model validation automatically check karta hai — fail pe 400 + messages, aur handler execute hi nahi hota. Yahi defense-in-depth hai (frontend validation ke baad backend wala check).

Q: Production mein developer exception page (stack trace wala) kyun nahi dikhana chahiye?
A. Dikhne mein bura lagta hai
B. Usme internal details (paths, queries) hoti hain jo attacker ko free info deti hain — generic 500 + server logs do
C. Wo slow hai
D. Browser support nahi karta
> B. Stack trace/server path query leak karna security risk hai. Production: structured generic `{error}` + 500, detail sirf server-side logs mein. Dev mein detail debugging ke liye theek.

Q: JWT payload mein kya rakh sakte hain — aur kya nahi?
A. Password/secret rakh sakte hain kyunki token sealed hai
B. Sirf claims (user id, role, expiry) — payload Base64 hai khula, secret/password kabhi nahi
C. File attach kar sakte hain
D. Kuch bhi, encrypt hota hai
> B. JWT payload decode ho jaata hai (encryption nahi, sirf signed) — isliye sensitive data kabhi nahi. Sirf pehchan wale claims + expiry. Secret sirf banane/verify ke liye, token ke andar nahi.

Q: `.RequireAuthorization()` endpoint pe 401 kahan se aata hai?
A. Endpoint ka apna if-check
B. `AddJwtBearer` + `UseAuthentication` middleware token verify kar deta hai — fail toh handler chalta hi nahi
C. React khud check karta hai
D. Database
> B. Middleware pipeline mein token verify hota hai (signature, expiry, key) — galat toh 401 khud return, tumhara endpoint code touch hi nahi hota. `.RequireAuthorization()` sirf bolta hai "is route pe yeh check chahiye".

Q: React `localhost:3000` se API `localhost:5000` call karne pe CORS error kyun?
A. API crash hoti hai
B. Browser cross-origin request by-default rokta hai; API ko `Access-Control-Allow-Origin` se permission deni padti hai
C. React CORS nahi samajhta
D. Port same hone chahiye
> B. Browser ki security policy — origin (domain+port) alag ho toh server ko pehle allow karna padta hai (AddCors + UseCors). Sirf browser mein — Postman mein yeh restriction hi nahi.

## TrueFalse

Q: REST mein `GET /api/students/5` ka matlab hai student with Id=5 padhna, aur `DELETE /api/students/5` wahi resource hatana.
- True
- False
> True. Path resource ko identify karta hai (`/students/5` = kaun), HTTP method kaam batata hai (GET=padh, DELETE=hatao). Yahi REST ka core contract hai — resource URLs + verb actions.

---

Q: Query parameter `?minMarks=80&sort=desc` aur route parameter `{id}` ka kaam same hai.
- True
- False
> False. Route parameter URL path ka part hai (resource identify, required); query parameter `?` ke baad filter/options deta hai (optional) — ek hi endpoint se alag-alag views (filter/sort/pagination) milte hain.

---

Q: `app.UseAuthentication()` ke bina `.RequireAuthorization()` bhi theek se kaam karta hai.
- True
- False
> False. Pehle token verify hona chahiye (UseAuthentication → JWT middleware), phir authorization check (UseAuthorization). Order galat ho toh identity hi nahi banti — `RequireAuthorization` ke paas check karne ko kuch nahi hoga.

---

Q: JWT mein logout server-side se karne ka matlab hai token ko turant invalid karna — stateless hone ke kaaran yeh bilkul aasan hai.
- True
- False
> False. Stateless ka fayda tha — server store kuch nahi rakhta, isliye ek active token ko beech mein khatam karna mushkil (DB mein blacklist/revoke alag se banana padta hai). Isliye short expiry (15-60 min) rakhi jaati hai.

---

Q: `AllowAnyOrigin()` production CORS solution hai — hamesha use karo.
- True
- False
> False. Dev mein theek, par production mein specific origins (`WithOrigins("https://yourapp.com")`) — AllowAnyOrigin ka matlab koi bhi website tumhari API use kar sakti hai, security review mein fail hota hai.
