## MCQ

Q: What's the relationship between a Web API and a React frontend?
A. Both run in the browser
B. React shows the UI and makes API calls; the API gives JSON data (from the database)
C. The API renders HTML that React shows
D. React is the backend
> B. Division of labour: React = client UI (browser), ASP.NET Core API = data + logic (server). They talk over HTTP, data comes/goes as JSON. Your Next.js API route did the same thing — only the backend framework is different.

---

Q: Which HTTP method + route is correct for creating `POST /api/students`?
A. `GET /api/students`
B. `POST /api/students` — with a body, for a new resource
C. `GET /api/students/new`
D. `PUT /api/students`
> B. REST pattern: GET = read, POST = create new (201 Created), PUT = update, DELETE = remove. The path is the resource name (`/students`), the method is the action (`POST`) — that's the contract.

Q: Why use a DTO (CreateStudentDto) — what's the problem with taking the `Student` model directly?
A. DTO is fast
B. Mass assignment — the client can send extra fields (isAdmin, salary) that go straight into the DB, and sensitive fields can leak out
C. JSON isn't created from the model
D. DTO runs without compiling
> B. A DTO sets the client's contract — only allowed fields come in, and the output DTO only has what should be shown. You get both security (mass assignment, data leak) and a clear API.

---

Q: If the client sends `-500` for `[Range(0,100)] int Marks`, what happens?
A. `-500` goes into the DB
B. The endpoint runs but gives a warning
C. 400 Bad Request + validation error, the endpoint code doesn't run at all
D. The program crashes
> C. `[ApiController]` checks model validation automatically — on failure, 400 + messages, and the handler doesn't execute at all. This is defense-in-depth (the backend check after frontend validation).

Q: Why shouldn't the developer exception page (with stack trace) be shown in production?
A. It looks bad
B. It contains internal details (paths, queries) that give an attacker free info — give a generic 500 + server logs
C. It's slow
D. Browsers don't support it
> B. Stack trace/server path/query leak is a security risk. Production: structured generic `{error}` + 500, detail only in server-side logs. In dev, detail is fine for debugging.

Q: What can you put in a JWT payload — and what can't you?
A. Password/secret can be put because the token is sealed
B. Only claims (user id, role, expiry) — the payload is Base64 in the open, never secret/password
C. You can attach a file
D. Anything, it's encrypted
> B. The JWT payload gets decoded (not encrypted, only signed) — so sensitive data never goes in. Only identifying claims + expiry. The secret is only for creating/verifying, not inside the token.

Q: Where does the 401 come from when `.RequireAuthorization()` is on an endpoint?
A. The endpoint's own if-check
B. `AddJwtBearer` + `UseAuthentication` middleware verifies the token — on failure the handler doesn't run at all
C. React checks it itself
D. The database
> B. The token gets verified in the middleware pipeline (signature, expiry, key) — if wrong, 401 is returned on its own, your endpoint code never gets touched. `.RequireAuthorization()` only says "this route needs that check".

---

Q: Why does a CORS error happen when React at `localhost:3000` calls the API at `localhost:5000`?
A. The API crashes
B. The browser blocks cross-origin requests by default; the API must give permission via `Access-Control-Allow-Origin`
C. React doesn't understand CORS
D. The ports must be the same
> B. Browser security policy — if the origin (domain+port) differs, the server must allow it first (AddCors + UseCors). This restriction is only in the browser — Postman has no such restriction.

## TrueFalse

Q: In REST, `GET /api/students/5` means read the student with Id=5, and `DELETE /api/students/5` removes that same resource.
- True
- False
> True. The path identifies the resource (`/students/5` = which one), the HTTP method says the action (GET=read, DELETE=remove). This is the core contract of REST — resource URLs + verb actions.

---

Q: Query parameter `?minMarks=80&sort=desc` and route parameter `{id}` do the same job.
- True
- False
> False. The route parameter is part of the URL path (identifies the resource, required); the query parameter comes after `?` and gives filter/options (optional) — one endpoint can give different views (filter/sort/pagination).

---

Q: Without `app.UseAuthentication()`, `.RequireAuthorization()` still works fine.
- True
- False
> False. The token must be verified first (UseAuthentication → JWT middleware), then the authorization check (UseAuthorization). If the order is wrong, no identity is created — `RequireAuthorization` has nothing to check.

---

Q: Logging out of a JWT server-side means instantly invalidating the token — and because it's stateless, this is completely easy.
- True
- False
> False. The benefit was stateless — the server stores nothing, so killing an active token midway is hard (you have to build a separate blacklist/revoke in the DB). That's why short expiry (15-60 min) is kept.

---

Q: `AllowAnyOrigin()` is the production CORS solution — always use it.
- True
- False
> False. Fine in dev, but in production specific origins (`WithOrigins("https://yourapp.com")`) — AllowAnyOrigin means any website can use your API, which fails security review.
