Last time locked the definition — a model trained on huge text that predicts what comes next — and ended on a promise: three hard limits, each one the reason something else exists. Let's take them one at a time.

**Limit one: it cannot act.**

An LLM only produces text. That's its entire output: words. It can say "search the web for this" — and nothing happens. No search runs, no file opens, no API gets called, unless other code actually does it. Think of a brain in a jar: it can think and write, but it has no hands. It can't click, it can't search, it can't run anything.

Say an app is asked to check today's weather. The LLM writes out *"I need the weather tool for this city."* Something else — a controller — reads that, calls the real weather service, passes the answer back, and the LLM turns it into the reply you see. The split is clean: **the LLM decides, the controller does.**

Your word for it was better than mine: *puppet*. The LLM has the voice; the strings get pulled from outside.

**Limit two: its knowledge is frozen.**

An LLM learned everything during training — and then training stopped on a certain date. That date has a name: the **knowledge cutoff**. After it, the model learns nothing new by itself. Last week's news? Never saw it. Your company's private documents? Never saw those either.

And here's the sharp part: it will answer anyway — outdated and still confident. When it makes something up like that, the word for it is **hallucination**. It isn't lying; it's pattern-matching its way to an answer it was never given, fluently, with full confidence.

So a controller helps here too: it can fetch fresh or private information and put it in front of the LLM *for that one question*. One precision — it doesn't update the model's knowledge for good. The LLM stays frozen. Hand the fact over for this question, and you'll be handing it over again next time.

**Limit three: it has no memory.**

Every message, the LLM starts completely fresh. No idea who you are, nothing from earlier. So how does a chat app *seem* to remember? The controller re-sends the whole conversation every single time — your first message, its reply, your second — bundled with the new one. The model sees it all as one fresh input each turn.

But "all of it" has a size limit, and you already know its name: the **context window** — the working table the model sees. Its slots are measured in *tokens*, those small chunks of text; the full token story gets its own phase later. For now: table slots.

Your 10-slot picture is exactly right, so let's run it. "hello" fills slot one — whole table goes to the LLM. "what are you doing?" fills slot two — whole table goes again. Keep talking: ten of ten, full. Ask something about your first message? Still there, still answered — it's on the table. One more message and it overflows. Something has to give: the controller either cuts the oldest stuff or squeezes it into a short recap. That squeezing is **compaction**. Modern chat apps do it automatically — which is why long chats get a "continuing from earlier summary" moment, and why after compaction the model remembers the *summary* of the early messages, not their exact words. Small details can get lost.

Your bed question fits here too: come back to the same chat after two days — is the table emptier? No. The context window is about how much text is on the table, not about time. A break changes nothing; everything you left is still there, just as full. What a break might refill — in some apps — is a separate thing: your usage allowance. Table fullness and usage limits are two different knobs.

All three, together: **it cannot act; its knowledge is frozen; it has no memory beyond the table.** And notice the pattern — every fix is *never* inside the LLM. Every fix is code around the model. Which raises the obvious question: what do we call that code?

The nots, before they stick wrong: none of these three are fixable by more training — they're properties of how LLMs work, not bugs awaiting a patch. Hallucination is not lying — no intent, just fluent pattern-matching. Compaction is not the model remembering better — it's the controller summarizing so the table fits. And the controller is not part of the model — it's separate code, which means every fix is optional, configurable, swappable.

<details>
<summary>Show Answer</summary>

**Sample Answer:** The knowledge cutoff is the date training stopped — after that, the model has simply never seen newer or private information. Hallucination is what happens when the model answers anyway: it pattern-matches its way to a fluent, confident-sounding response it was never given. The cutoff is the boundary of what it knows; hallucination is the confident output when it doesn't know.

So every fix lives in code around the model: tools, fetching, history management.
