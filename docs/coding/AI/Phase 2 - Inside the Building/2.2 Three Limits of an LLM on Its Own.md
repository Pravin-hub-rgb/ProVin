Three limits, one at a time, each checked before the next. By the end, you'll see why the whole middle layer of the building had to be built.

---

## Limit 1 — It Cannot Act

An LLM only produces text. That's its entire output: words.

So it can *say* "search the web for this" — but nothing happens. No search runs, no file opens, no API gets called, unless other code actually does it. The LLM is a brain in a jar: it can think and write, but it has no hands. It can't click, search, or run anything.

Say an app is asked to check today's weather. The LLM writes out something like *"I need the weather tool for this city."* **Something else** — a controller — reads that, calls the real weather service, and passes the answer back. Then the LLM turns it into a reply for you.

The split is clean: **the LLM decides, the controller does.**

Your own word for it fits perfectly: a puppet. The LLM is the puppet — it has the voice, but the strings get pulled by something else.

**Quick check:** an agent edits your code. Where did the actual file-editing happen — inside the LLM, or somewhere else?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Somewhere else. The LLM only produced text — instructions saying which edit to make. A controller read that text and performed the real edit with actual code. The LLM decides; the controller does. No hands inside the model.

</details>

## Limit 2 — Its Knowledge Is Frozen

An LLM learned everything during training — and then **training stopped on a certain date.** That date has a name: the **knowledge cutoff**.

After the cutoff, the model learns nothing new by itself. So:

- Something happened last week? It never saw it.
- Your company's private documents? Never saw those either.

And here's the sharp part: it will often answer anyway — **outdated and still confident.** When it makes something up like that, the word for it is **hallucination**. The model isn't lying; it's pattern-matching its way to an answer it was never given, and doing it fluently.

Why does a controller help here too? It can fetch fresh or private information and put it in front of the LLM *for that one question*.

One precision: the controller doesn't update the model's knowledge for good. The LLM stays frozen — each new fact gets handed over per question, and has to be handed over again next time.

**Quick check:** what's a knowledge cutoff, and why can an LLM sound confident while being wrong?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The knowledge cutoff is the date training stopped — after it, the model learns nothing new by itself, so it has never seen anything that happened later (or anything private). It answers anyway by pattern-matching from what it did learn, and because it always predicts fluent, likely-sounding text, a wrong answer comes out just as confident as a right one. That confident fabrication is hallucination.

</details>

## Limit 3 — It Has No Memory

Every message, the LLM starts **completely fresh.** No idea who you are, nothing remembered from earlier in the conversation.

So how does a chat app *seem* to remember? The controller re-sends the whole conversation every single time — your first message, its reply, your second message, all bundled with the new one. The model sees it all as one fresh input each turn.

But "all of it" has a size limit, and that limit has the name you've been waiting for: the **context window** — the working table the model sees. Measured, as everything in this world is, in **tokens** (small chunks of text — the full story is a later phase; for now, think slots on the table).

Your 10-slot table picture is exactly how it works:

1. "hello" fills slot 1. Whole table goes to the LLM.
2. "what are you doing?" fills slot 2. Whole table goes again.
3. Keep going — 10 of 10 slots full.
4. Ask something about the first message? Still there, still answered — it's on the table.
5. One more message and the table overflows. Something has to give.

When it's full, the controller either **cuts** the oldest stuff or **summarizes** it — squeezing the early slots into a short recap and freeing space. That squeezing has a name: **compaction**. Modern chat apps do it automatically, which is exactly why long chats get a "continuing from earlier summary" moment — and why, after compaction, the model remembers the *summary* of early messages, not their exact words. Small details can get lost.

So the third job for the controller: **manage what the LLM sees, so it fits and stays relevant.**

**Quick check:** you come back to the same chat after two days. Is the table emptier?

<details>
<summary>Show Answer</summary>

**Sample Answer:** No — the context window is about how much text is on the table, not time. A break changes nothing; everything you left is still there, just as full. What a fresh *chat* does is give an empty table; what a break might refill (in some apps) is a separate thing — your usage allowance. Table fullness and usage limits are two different knobs.

</details>

## The Three Limits, Together

| # | Limit | The fix (preview) |
|---|---|---|
| 1 | It cannot act — text only, no hands | Tools + a controller that executes |
| 2 | Its knowledge is frozen — cutoff, hallucination | A controller that fetches fresh info (RAG for your documents, tools for live data) |
| 3 | No memory — fresh every message, finite table | Memory handling: re-send history, manage the context window, compact |

Notice what all three have in common: **the fix is never inside the LLM.** Every fix is code *around* the model — which raises the obvious question: what do we call that code?

---

## What the Limits Are NOT

- **Not fixable by more training.** These are properties of how LLMs work, not bugs awaiting a patch.
- **Hallucination is not lying.** No intent — it's fluent pattern-matching producing an answer it was never given.
- **Compaction is not the model remembering better.** It's the controller summarizing so the table fits; the model still just reads whatever's on it.
- **The controller is not part of the model.** It's separate code — which means every fix is optional, configurable, and swappable. That's next.

2. A chatbot remembers your name from ten messages ago. Is the LLM recalling it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** No. The model starts fresh every message. The controller re-sends the whole conversation each time, so your name is physically present in the input the model reads — it "remembers" only because the wrapper stitches the history in. If the conversation outgrows the context window and gets compacted, even that memory degrades to a summary.

</details>

3. What's the difference between the knowledge cutoff and hallucination?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The knowledge cutoff is the date training stopped — after that, the model has simply never seen newer or private information. Hallucination is what happens when the model answers anyway: it pattern-matches its way to a fluent, confident-sounding response it was never given. The cutoff is the boundary of what it knows; hallucination is the confident output when it doesn't know.

</details>

4. Why can't any of the three limits be fixed by training the model more?

<details>
<summary>Show Answer</summary>

**Sample Answer:** They're structural, not gaps in the training data. Acting requires hands — a text-producing model has no way to execute no matter how much it trains. Knowledge will always have a cutoff because training always ends on some date. Memory is inherent to a stateless prediction call — each call sees only its input. So every fix lives in code around the model: tools, fetching, history management.

</details>
