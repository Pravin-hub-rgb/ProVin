---

## One Sentence First

> **RAG is the string that fetches knowledge.**

When you ask a question, the controller first looks up relevant information — from your documents, your database — and puts it on the table *with* your question. Then the LLM answers using that fresh material.

That's it. RAG fetches. The LLM reads and answers.

One disambiguation, because these two got tangled once: RAG is **not** memory handling. Memory is the string that manages the conversation history. RAG is only about fetching knowledge the LLM doesn't have. Different strings, different jobs.

---

## The Name, Word by Word

**RAG** stands for **Retrieval Augmented Generation**:

- **Retrieval** — fetching information first.
- **Augmented** — boosted, added to.
- **Generation** — the LLM producing the answer.

So: retrieve first, then generate the answer *with* the retrieved material. The generation gets boosted by what was retrieved. The order in the name is the order in the flow.

---

## The Company Policy Example

Say you ask an LLM-powered app: *"What's our company's leave policy?"*

The LLM never saw your company documents. Alone, it would guess — fluent, confident, possibly wrong (limit 2 in action).

With RAG:

1. The controller searches your company's documents.
2. It finds the leave policy page.
3. It puts that text on the table next to your question.
4. The LLM reads it and answers correctly.

**RAG is looking things up before answering** — fetching the right material so the answer has something true to stand on.

---

## The Classic RAG Flow — Order Matters

You once sketched this flow with the LLM asking for data first: *"I don't have this, fetch it."* That instinct — the model requesting what it needs — is real, but it's how **agents** work (a later phase). Classic RAG has a different, simpler order, and the difference is the key point:

> **In classic RAG, the LLM doesn't ask first. The controller acts before the LLM ever sees your question.**

The full order:

```
question → controller searches the database → controller bundles
         → ONE package to the LLM: question + retrieved text
         → LLM reads the package and writes the answer
```

Three consequences of that order:

- **The LLM never knew data was missing.** It just reads one package and answers.
- **The search happens in the database, before the LLM.** The model does no searching, no sorting of the database.
- **The LLM does look through the retrieved text** — it reads the package carefully and pulls out the relevant part — it just never touches the database itself.

So: question, controller searches, controller bundles, LLM answers.

## Why Do We Even Need the LLM?

Fair question: RAG found the policy page — why not just show that?

Because **RAG only fetches.** What it brings back is raw pieces of documents — a stack of pages, maybe the right paragraph buried in three wrong ones. The LLM is the one that:

- reads the pages,
- understands your *actual* question,
- pulls out the relevant part,
- and writes a clear answer in plain language.

The clean split: **RAG is the librarian who brings the right books. The LLM is the reader who explains what's in them.**

And one forward note so the map stays honest: the search is a bit smarter than exact-word matching — it finds pieces by *meaning*, using something called embeddings. That's the whole next file.

## Two Doors Into Outside Information

While we're here — one boundary that settles a confusion from your own questioning:

- **RAG** brings in information from **your stored collection** — documents you loaded ahead of time, searched by meaning.
- **Tools** bring in **live stuff** — the web, GitHub, an API. That text comes back as plain text and goes straight to the LLM. It was never fingerprinted, never in a database.

Two doors, two jobs: RAG for your library, tools for the live world. (The tools string itself gets pulled in Phase 3.)

---

## What RAG Is NOT

- **Not memory.** Memory manages conversation history; RAG fetches knowledge. Different strings.
- **Not the LLM asking for help.** In classic RAG the controller acts *before* the model sees the question — no request, no back-and-forth.
- **Not a search engine for the whole internet** (in classic form). It searches *your* stored collection; live data comes via tools.
- **Not a product — it's an idea.** You can build RAG with LangChain, other libraries, or by hand. The concept is the flow; the toolkit is just one way to implement it.
