The last file ended with a riddle: all three fixes for the LLM's limits live in *code around the model* — so what do we call that code?

Time to name it. But names land better on a structure, so first the structure: the building you sketched when you picked ChatGPT as your example — input box at the top, LLM at the bottom, mystery stuff in the middle.

Three floors. Let's label them bottom to top.

---

## Floor by Floor

**Bottom floor — the LLM.** The model itself: the trained file, the one skill, the three limits. Everything we've learned so far lives down here.

**Middle floor — the orchestration layer.** The code that sits between the application and the LLM and coordinates everything: it prepares your message, fetches extra information, manages tools, keeps the history. This is the floor that fixes the three limits.

**Top floor — the application.** The product the user sees: the chat window, the input box, the send button. ChatGPT-as-you-use-it lives up here.

So the picture you had — top: application, bottom: LLM, middle: the stuff you couldn't order yet — was exactly right. And now the middle has its name.

---

## Naming the Middle Floor

The middle layer has a few names, and they all point at the same thing:

- **Orchestration layer** — the most common in practice. *Orchestration* means coordinating: deciding what goes to the LLM, when to call a tool, what to do with the result. Like a conductor, not a player.
- **Controller** — the word that makes the limits click: it's the hands the LLM doesn't have.
- **Harness** — all the code wrapped around the LLM that makes it usable. You'll hear this one especially around agents.
- In casual talk: "the app logic" or "the backend."

Controller, orchestration layer, harness — same floor, different names.

---

## The Puppet Strings

Your puppet picture organizes this perfectly. The LLM is the puppet: it has the voice, but strings get pulled from above.

Inside the middle floor, the strings run **side by side** — not stacked, siblings. Each string is one *job* the controller does:

1. **Memory handling** — manages the context window: re-sends history, cuts or compacts when the table fills. (Fixes limit 3.)
2. **Fetching knowledge** — brings information the LLM doesn't have: your documents, your data. This string's name is **RAG** — next file. (Fixes limit 2.)
3. **Using tools** — performs actions: searches, runs code, calls APIs. The string that lets the puppet move. (Fixes limit 1.)

One layer, three parallel jobs. And where do the buzzwords LangChain and LangGraph fit?

**They're not strings, and not a floor.** They're *construction kits* — ready-made code developers use to build the middle floor faster, strings included. They sit *beside* the layer as the material it's built from, not inside it as one of its jobs. Full treatment in file 2.6.

**Quick check:** a developer says "our app uses LangChain for RAG." Untangle the three words — which is a floor, which is a string, which is a kit?

## What the Orchestration Layer Is NOT

- **Not part of the LLM.** It's separate code — which is why it's optional, swappable, and where all the interesting engineering happens.
- **LangChain is not a layer or a job.** It's a library used to *build* the layer — material, not structure.
- **The strings are not stacked with priority.** They run side by side — three parallel jobs the controller can call as needed.
- **The application is not where intelligence lives.** It's the window; the intelligence is on the bottom floor, coordinated by the middle.
