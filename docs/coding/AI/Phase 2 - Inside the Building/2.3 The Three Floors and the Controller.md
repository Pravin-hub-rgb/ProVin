Three limits, three fixes — and all the fixes are code around the model. You already sketched the shape of that code once: pick ChatGPT, input box at the top, LLM at the bottom, and the stuff in the middle you couldn't order yet. Time to label all three floors, bottom to top.

**Bottom — the LLM.** The model itself: trained file, one skill, three limits. Everything we've learned so far lives down here.

**Middle — the orchestration layer.** The code between the application and the LLM that coordinates everything: prepares your message, fetches extra information, manages tools, keeps the history. This is the floor that fixes the three limits.

**Top — the application.** The product the user sees: chat window, input box, send button. ChatGPT-as-you-use-it lives up here.

So your picture — app on top, LLM at the bottom, middle stuff in between — was exactly right. The middle just needed a name, and it has a few, all pointing at the same thing. **Orchestration layer** is the common one in practice: *orchestration* means coordinating — deciding what goes to the LLM, when to call a tool, what to do with the result. **Controller** is the one that makes the limits click: it's the hands the LLM doesn't have. **Harness** is all the code wrapped around the LLM that makes it usable — you'll hear it especially around agents. In casual talk: the app logic, the backend.

Now your puppet picture, because it organizes the rest perfectly. The LLM is the puppet — the voice. Inside the middle floor, the strings run **side by side**: not stacked, siblings. Each string is one job the controller does. **Memory handling**: manages the context window — re-sends history, cuts or compacts when the table fills. That's limit three's fix. **Fetching knowledge**: brings information the LLM doesn't have — your documents, your data. This string has a name you already know: **RAG** — limit two's fix, next file. **Using tools**: performs actions — searches, runs code, calls APIs — limit one's fix, Phase 3.

One layer, three parallel jobs. And here's the confusion worth catching before it happens, because it happened in real time: do LangChain and LangGraph sit *on top of* these strings, stacked above RAG like another floor? No. They're not strings, and they're not a floor. They're **construction kits** — ready-made code developers use to build the middle floor faster, strings included. They sit *beside* the layer as the material it's built from, not inside it as one of its jobs. File 2.6 gets them fully.

One picture, everything placed:

```
┌─────────────────────────────────────┐
│  TOP:    Application (chat window)  │
├─────────────────────────────────────┤
│  MIDDLE: Orchestration layer        │
│          ├─ memory (context window) │  ← built with kits:
│          ├─ RAG (fetch knowledge)   │    LangChain, LangGraph
│          └─ tools (take actions)    │
├─────────────────────────────────────┤
│  BOTTOM: LLM (the model, 3 limits)  │
└─────────────────────────────────────┘
```

Every word now has a home. Chatbot and agent are top floor — Phase 1 called them applications, now they have their floor. RAG, tools, memory: strings on the middle floor. LangChain, LangGraph: construction kits beside it. The LLM and its limits: bottom floor.

The nots: the orchestration layer is *not* part of the LLM — separate code, which is why it's optional and swappable. LangChain is *not* a layer or a job — material, not structure. The strings are *not* ranked — they run side by side, three parallel jobs. And the application is *not* where intelligence lives — it's the window; the intelligence is on the bottom floor, coordinated by the middle.
