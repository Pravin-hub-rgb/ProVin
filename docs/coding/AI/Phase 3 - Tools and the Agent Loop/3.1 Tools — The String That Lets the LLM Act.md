The last file of Phase 2 parked two things: the *tools* string, and the agent loop it powers. Phase 2 gave you the puppet picture — the LLM as the voice, the controller as the hand pulling strings — and named three strings side by side: memory, RAG, and tools. Memory and RAG got pulled already. Time to pull the third, the one that finally gives the LLM hands.

A **tool** is one thing the LLM can ask for help with, because it can't do it by itself. The LLM only produces text, so anything that needs the outside world — checking today's weather, reading a file, running code — has to happen through a tool. A weather lookup is a tool. So is editing a file. So is searching the web. Each one is a separate little ability, like a screwdriver in a toolbox.

The first thing to lock down is who actually uses the tool. The LLM never touches it. It can only write text, so it writes a request like *"I need the weather for Mumbai."* The controller reads that request, runs the real weather lookup, and hands the result back to the LLM. **The LLM asks; the controller does the work.** The LLM is the brain that decides what's needed and speaks the request. The controller is the body that moves. And the tools are the hands that actually reach into the outside world. The brain never uses a hand directly — it only speaks, and the body moves.

So the controller is the worker, and it owns a toolbox. One tool is web search, another reads a file, another edits one, another runs code. When the LLM asks for one, the controller takes that tool out and uses it. RAG fits this picture the same way: it isn't what the controller *is*, it's a job the controller does with one particular hand, the one that reaches into the vector database. The controller is always the controller; tools and RAG are things it uses.

Counting tools works exactly as you'd expect. One agent might have five, another six — the sixth being, say, web surfing, one more kind of action. The abilities aren't baked into the LLM either. The model ships as patterns; the application offers the toolbox and runs the loop. Swap the tools, same LLM.

Now the part that makes it work: how does the LLM know which hands exist? Before it answers anything, the controller gives it a short menu — a list of the available tools, each with a name and a one-line description, like *"web search: looks up current information"* or *"read file: opens a file and returns its text."* The LLM reads that menu as part of its text, the same table as your question, and then it can ask for one by name. So the LLM only knows a tool exists because the controller told it in text.

And how does it actually ask? It writes a small, structured piece of text instead of a normal reply — something like *tool name: web search, input: weather in Mumbai*. That structured request is called a **tool call**. The controller spots that the LLM wrote a tool call rather than a normal answer, so it pauses, runs the real tool, and gets a result. Then it puts that result back on the table, and the LLM reads it and continues. The LLM gets called twice for this one question: once to ask for the tool, once to answer using the result. That round trip — ask, run, read, answer — is the heart of how agents work, and it's what the next file pulls apart.

The nots, so nothing sticks wrong. A tool is *not* inside the LLM — the model comes with its patterns; the application offers the toolbox. The LLM is *not* executing anything — it only writes requests; the controller does the doing. A tool call is *not* a normal reply — it's a structured request the controller intercepts. And RAG is *not* a tool — it's a job the controller performs with a particular hand, reaching into your stored collection instead of the outside world.
