In 3.4, you saw how TradeStack scans 2000 stocks in parallel on historical data. But markets move live — during trading hours, prices tick every second. Scanning end-of-day data won't tell you what's happening *right now*. That's where streaming comes in: Upstox pushes live ticks, TradeStack fans them out to the frontend. Let's read the pattern.

# 3.5 Streaming — Upstox WebSocket, Live Price Ticks, SSE to Frontend

## Think — A Radio Station vs A Newspaper

A newspaper is batched: printed once a day, delivered in the morning. That's REST + historical cache (3.3, 3.4). A radio station broadcasts continuously; you tune in and hear what's happening *now*. That's WebSocket streaming. You don't ask the radio "what's playing?" every 10 seconds — it just plays, and you listen.

TradeStack's streaming is a radio station: one upstream connection to Upstox (the broadcaster), many downstream listeners (browser tabs, dashboards), filtered by symbol.

## Concept — Why Streaming Exists (The Polling Problem)

Without streaming, the frontend would poll `GET /api/price/RELIANCE` every second. Problems:

- 1000 clients × 1 req/sec = 1000 req/sec hammering your server.
- Each request opens/closes a connection (HTTP overhead).
- You're always 1 second behind (polling interval).
- Broker APIs have rate limits; polling Upstox directly for 2000 symbols is impossible.

WebSocket streaming flips this: connect once, subscribe, and the broker **pushes** ticks as they happen. Server fans out to clients. Zero polling, near-real-time, one upstream connection.

## Concept — The Architecture (Two Layers)

TradeStack has two streaming layers:

1. **Backend (Python) — proxy/fan-out** (described in Phase 2.4): `streaming.py` connects to Upstox WebSocket, receives ticks, fans out to subscribed frontend clients by symbol. (Note: in the actual repo, the backend exposes REST + the frontend connects to Upstox directly via the JS SDK; the pattern is identical either way.)

2. **Frontend (TypeScript) — `streamer.ts`**: Uses the Upstox JS SDK's `MarketDataStreamerV3` to connect to Upstox directly, receives protobuf-encoded ticks, decodes them, and calls `onTick` callbacks that feed the live trader and UI.

The concepts are the same in both: subscribe by symbol, fan out ticks, handle reconnects, clean up dead connections.

## Concept — Tick Processing (What a Tick Looks Like)

An Upstox tick (decoded) carries:

```python
# Python-side representation (conceptual)
tick = {
    "instrumentKey": "NSE_EQ|INE002A01018",
    "symbol": "RELIANCE",
    "ltp": 2450.50,        # last traded price
    "ltt": 1699084503000,  # last traded time (ms)
    "ltq": 50,              # last traded quantity
    "cp": 2440.00,          # close price (previous day)
    "atp": 2448.30,         # average traded price
    "vtt": 1234567,         # volume traded today
    "ohlc": [{"open": 2442, "high": 2455, "low": 2438, "close": 2450.5, "interval": "1d"}],
    "timestamp": datetime.now(),
}
```

The frontend's `handleFeedResponse` (in `streamer.ts`) decodes the protobuf `FeedResponse`, iterates `response.feeds`, maps instrument key → symbol via `symbolMap`, and emits a `TickData` to `onTick`.

## Concept — The Backend Fan-Out Pattern (Python)

Even though TradeStack's actual live streaming runs in the frontend, the backend proxy pattern is the canonical one and is what you'd build if the broker token must stay server-side. Here's the Python version (matches Phase 2.4):

```python
import json, asyncio
from fastapi import WebSocket
from collections import defaultdict

class MarketStreamManager:
    def __init__(self):
        self.subscribers: dict[str, set[WebSocket]] = defaultdict(set)  # symbol -> clients
        self.latest: dict[str, dict] = {}                               # symbol -> last tick
        self.upstream_ws = None

    async def subscribe(self, websocket: WebSocket, symbol: str):
        await websocket.accept()
        self.subscribers[symbol].add(websocket)
        if symbol in self.latest:
            await websocket.send_text(json.dumps(self.latest[symbol]))  # instant current price

    def unsubscribe(self, websocket, symbol):
        self.subscribers[symbol].discard(websocket)

    async def on_tick(self, tick: dict):
        symbol = tick["symbol"]
        self.latest[symbol] = tick
        dead = []
        for ws in list(self.subscribers[symbol]):
            try:
                await ws.send_text(json.dumps(tick))
            except Exception:
                dead.append(ws)
        for ws in dead:
            self.subscribers[symbol].discard(ws)

    async def broadcast_all(self, message: str):
        for symbol, subs in self.subscribers.items():
            for ws in list(subs):
                try:
                    await ws.send_text(message)
                except Exception:
                    subs.discard(ws)
```

And the endpoint that parses subscribe/unsubscribe commands:

```python
@app.websocket("/ws/market")
async def market_endpoint(websocket: WebSocket):
    await websocket.accept()
    subscribed = set()
    try:
        while True:
            raw = await websocket.receive_text()
            cmd = json.loads(raw)
            if cmd["action"] == "subscribe":
                symbol = cmd["symbol"]
                manager.subscribers[symbol].add(websocket)
                subscribed.add(symbol)
                if symbol in manager.latest:
                    await websocket.send_text(json.dumps(manager.latest[symbol]))
            elif cmd["action"] == "unsubscribe":
                symbol = cmd["symbol"]
                manager.subscribers[symbol].discard(websocket)
                subscribed.discard(symbol)
    except WebSocketDisconnect:
        for symbol in subscribed:
            manager.subscribers[symbol].discard(websocket)
```

## Concept — SSE to Frontend (Server-Sent Events)

Not everything needs a WebSocket. For one-way server→client streams where the client never sends back (live scan progress, breadth updates, log tails), **SSE** is simpler:

```python
from fastapi.responses import StreamingResponse
import asyncio, json

async def event_stream(operation_id: str):
    while True:
        op = active_operations.get(operation_id)
        if not op:
            yield f"data: {json.dumps({'error': 'not found'})}\n\n"
            break
        yield f"data: {json.dumps(op)}\n\n"
        if op["status"] in ("completed", "error"):
            break
        await asyncio.sleep(1)

@app.get("/api/stream/{operation_id}")
def stream_progress(operation_id: str):
    return StreamingResponse(event_stream(operation_id), media_type="text/event-stream")
```

SSE reuses HTTP (no upgrade handshake), auto-reconnects in the browser via `EventSource`, and is one-way. TradeStack uses polling (`GET /status/{id}`) today, but SSE is the natural upgrade for "live" dashboards. Rule of thumb: **WebSocket** for bidirectional (chat, subscribe/unsubscribe, live trader commands); **SSE** for one-way server pushes (progress, ticks, logs).

## Concept — Reconnects & Resilience

Live streams break: network blips, server restarts, token expiry. The frontend `streamer.ts` handles this:

- `reconnectAttempts` counter with max 5.
- Exponential backoff: `5 * 2^(attempt-1)` seconds.
- On `close` event, if not intentional, call `reconnect()`.
- On reconnect success, re-subscribe to all active instruments.
- Lock file per bot type (`reversal_bot.lock` / `continuation_bot.lock`) prevents two instances streaming the same symbols (duplicate orders).

## Concept — SSE vs WebSocket vs Polling

| Approach | Direction | Reconnect | Use case |
|---|---|---|---|
| Polling (`GET /status`) | Client pulls | Manual | Job progress (simple) |
| SSE (`EventSource`) | Server pushes, one-way | Auto (browser) | Live progress, logs, ticks (read-only) |
| WebSocket | Bidirectional | Manual (you code it) | Chat, subscribe/unsubscribe, live trader |

## Concept — Compare with Phase 2

| Phase 2 (mini) | TradeStack (production) |
|---|---|
| Single chat room | Symbol-keyed subscriptions |
| Clients send messages | Clients send subscribe/unsubscribe commands |
| Relay (client→client) | Gateway (Upstox→server→clients) |
| No reconnect logic | Exponential backoff + lock files |
| In-memory only | Latest-tick cache + reconnect-resubscribe |

## What It Is NOT

- ❌ **Not a broker** — TradeStack doesn't generate prices. It proxies Upstox. Exchange is source of truth.
- ❌ **Not persistent** — ticks are ephemeral. Need history? Store in time-series DB or `.pkl` cache. The stream layer remembers only the latest tick per symbol.
- ❌ **Not a replacement for REST** — "give me yesterday's OHLC" or "place an order" still need REST endpoints. WebSocket is for the live stream only.
- ❌ **Not scalable on one machine** — one process holds all subscriptions. Real scale needs Redis pub/sub between instances.

## Nutshell

**Streaming = one upstream Upstox WebSocket → server fans ticks out to subscribers keyed by symbol, with a latest-tick cache and reconnect logic. Use WebSocket for bidirectional subscribe/unsubscribe, SSE for one-way server pushes, polling for simple progress. The plumbing is identical to chat (Phase 2); only the data direction and subscription key change.**

## Common Mistakes

- ❌ **"Each client connects to Upstox directly"** — no. One upstream connection feeds all clients (broker connection limits).
- ❌ **"Ticks are stored like chat messages"** — no. Only the latest tick per symbol is cached. Storing every tick OOMs the server.
- ❌ **"Subscription is global"** — no, per-symbol. One client can watch 10 symbols.
- ❌ **"Forgetting cleanup on disconnect"** — dead sockets must be removed from every subscribed symbol's set.
- ❌ **"Treating it as chat"** — clients don't broadcast ticks to each other. Data flows upstream → server → clients only.

## In Your Own Words

1. In one sentence, what's the difference between a chat WebSocket and a trading WebSocket?

<details>
<summary>Sample Answer</summary>

**Answer:** Chat is many-to-many relay (any client sends, all in room receive); trading is one-to-many gateway (one upstream feed fanned out to subscribers of a symbol). Same WebSocket plumbing, different data direction and subscription model.

</details>

2. Why does the server keep only ONE upstream connection to Upstox instead of one per client?

<details>
<summary>Sample Answer</summary>

**Answer:** Broker connection limits and efficiency. One upstream connection receives all ticks; the server fans them out to its many clients. Otherwise N clients = N broker connections, which brokers don't allow and which wastes bandwidth.

</details>

3. What's the `latest` tick cache for, and how is it different from chat's message history?

<details>
<summary>Sample Answer</summary>

**Answer:** `latest[symbol]` holds the most recent tick so a newly subscribed client immediately gets the current price instead of waiting for the next tick. Chat history keeps the last N messages (a list); trading keeps only the single latest value per symbol (current state, not a log).

</details>

4. When would you choose SSE over WebSocket for a live feature?

<details>
<summary>Sample Answer</summary>

**Answer:** When the flow is one-way server→client (live progress, log tails, read-only ticks) and the client never sends back. SSE reuses HTTP, auto-reconnects in the browser via `EventSource`, and is simpler. Use WebSocket when the client must send commands (subscribe/unsubscribe, chat, live trader actions).

</details>

5. Name the five things to look for when reading a streaming module.

<details>
<summary>Sample Answer</summary>

**Answer:** (1) a dict keyed by symbol holding connection sets, (2) an upstream task connecting to the broker, (3) a fan-out loop sending ticks to subscribers, (4) cleanup of dead sockets, (5) a cache of the latest tick per symbol.

</details>
