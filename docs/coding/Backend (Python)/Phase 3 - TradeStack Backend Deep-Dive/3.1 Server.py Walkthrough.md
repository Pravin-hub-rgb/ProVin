# 3.1 Server.py Walkthrough — How 930 Lines Are Organized

## Think — A Restaurant Kitchen

Imagine a restaurant kitchen. There isn't one giant chef doing everything. There's a station for prep, a station for the grill, a station for plating, and an expediter who coordinates orders. Each station has its own tools, but they all share the same kitchen space.

`server.py` is that kitchen. It's 930 lines, but it's not 930 lines of chaos. It's organized into stations: imports at the top, logging setup, the FastAPI app + middleware, then route groups (health, data pipeline, token, scanner, stock list, breadth, trades…), then background task functions, then the entry point. You read it top-to-bottom like reading a menu: "what's available, how it's made, how to start the kitchen."

## Concept — The Skeleton of server.py

Here's the skeleton (simplified). Notice the order — it matters:

```python
# --- 1. Imports ---
import logging, threading, time, uuid
from contextlib import asynccontextmanager
from fastapi import FastAPI, BackgroundTasks, HTTPException, Request
from fastapi.middleware.cors import CORSMiddleware
...
from src.cache_manager import cache_manager
from src.db import (get_cache_stats, add_stock_to_list, ...)
from src.scanner import ContinuationScanner, ReversalScanner
...

# --- 2. Logging setup ---
logger = logging.getLogger(__name__)
from src.logging_config import setup_logging
try:
    setup_logging(level=settings_get("log_level") or "INFO")
except Exception:
    setup_logging(level="INFO")

# --- 3. Middleware ---
class AccessLogMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        ...

# --- 4. Lifespan (startup / shutdown) ---
@asynccontextmanager
async def lifespan(app: FastAPI):
    stats = get_cache_stats()
    if stats["stock_count"] == 0:
        cache_manager.rebuild_index()
    yield
    # shutdown: nothing heavy

# --- 5. App creation ---
app = FastAPI(title="TradeStack", version="0.1.0", lifespan=lifespan)
app.add_middleware(CORSMiddleware, ...)
app.add_middleware(AccessLogMiddleware)
app.add_exception_handler(Exception, unhandled_exception_handler)

# --- 6. In-memory operation tracking ---
active_operations: dict = {}

# --- 7. Route groups ---
@app.get("/")
def root(): ...

@app.post("/api/scanner/continuation")
def trigger_continuation_scan(...): ...

# --- 8. Background task functions ---
def _run_continuation_scan(operation_id, params, scan_date): ...

# --- 9. Entry point ---
if __name__ == "__main__":
    import uvicorn
    uvicorn.run("server:app", host="127.0.0.1", port=8001, reload=False)
```

Each numbered section has one job. Read them in order and the file stops being scary.

## Concept — Why the Order Matters

FastAPI executes top-to-bottom at import time. So:

- **Imports first** — `from src.scanner import ...` runs the module; if `scanner.py` has a syntax error, the server won't even start.
- **Logging next** — set up logging before anything else logs, so early errors aren't lost.
- **Middleware before routes** — middleware wraps every request; it must be registered before routes are defined (registration order = execution order).
- **Lifespan before `app = FastAPI(...)`** — the lifespan function is passed into the constructor, so it must exist first.
- **`app = FastAPI(...)`** — this is where the app object is born. Everything after attaches to it.
- **Routes** — decorators like `@app.get` attach endpoints to `app`. They can be defined anywhere after `app` exists.
- **Background tasks** — plain functions, defined later, referenced by name in routes.
- **Entry point** — only runs when you execute `python server.py` directly (`__name__ == "__main__"`).

## Concept — Route Registration (How 48 Endpoints Stay Organized)

There's no separate router file. Routes are grouped by **comment banners** inside `server.py`:

```python
# --- Health ---
@app.get("/")
def root(): return {"status": "ok", "service": "TradeStack"}

@app.get("/health")
def health(): return {"status": "healthy"}


# --- Data Pipeline API ---
@app.post("/api/data/update-bhavcopy")
def trigger_update(...): ...

@app.get("/api/data/cache-info")
def get_cache_info(): ...


# --- Token Management API ---
@app.get("/api/token/status")
def get_token_status(): ...


# --- Scanner API ---
@app.post("/api/scanner/continuation")
def trigger_continuation_scan(request: Optional[ScanRequest] = None): ...


# --- Trade Log API ---
@app.post("/api/trades/log-entry")
def log_trade_entry(body: TradeLogEntry): ...
```

So the "14 modules" aren't 14 files in `server.py` — they're 14 logical sections separated by comment banners. When you need an endpoint, you `Ctrl+F` the banner name. That's the whole navigation strategy.

## Concept — Middleware (Two Layers)

Two middlewares are stacked:

1. **CORSMiddleware** — allows the frontend (running on `localhost:3000`) to call the backend (on `localhost:8001`). Without this, the browser blocks every request with a CORS error.

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000", "http://127.0.0.1:3000"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

2. **AccessLogMiddleware** (custom, `BaseHTTPMiddleware`) — logs every request and adds an `X-Process-Time` header:

```python
class AccessLogMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        start = time.perf_counter()
        try:
            response = await call_next(request)
        except Exception:
            logger.exception(f"Unhandled error on {request.method} {request.url.path}")
            raise
        duration_ms = (time.perf_counter() - start) * 1000
        response.headers["X-Process-Time"] = f"{duration_ms:.1f}ms"
        logger.info("access %s %s -> %d (%.1f ms)", request.method, request.url.path, response.status_code, duration_ms)
        return response
```

`call_next(request)` is the magic call — it passes the request down the chain (to the next middleware or the route handler) and returns the response. You wrap it with timing/logging.

There's also a global exception handler that converts any unhandled exception into a consistent JSON 500:

```python
@app.exception_handler(Exception)
def unhandled_exception_handler(request, exc):
    logger.exception(f"Unhandled exception on {request.method} {request.url.path}")
    detail = f"Internal server error: {exc.__class__.__name__}"
    return JSONResponse(status_code=500, content={"detail": detail})
```

This is why the frontend always reads `detail` from error responses.

## Concept — Lifespan (Startup / Shutdown)

FastAPI's modern way to run startup/shutdown code is `@asynccontextmanager`:

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # --- STARTUP ---
    stats = get_cache_stats()
    if stats["stock_count"] == 0:
        logger.info("Cache index is empty — rebuilding from .pkl files...")
        count = cache_manager.rebuild_index()
        logger.info(f"Cache index rebuilt: {count} entries")
    else:
        logger.info(f"Cache index has {stats['stock_count']} entries — no rebuild needed")
    logger.info("Startup complete")
    yield
    # --- SHUTDOWN ---
    logger.info("Shutdown complete")
```

Code before `yield` = startup (runs when server boots). Code after `yield` = shutdown (runs when server stops). The `yield` hands control to FastAPI to serve requests in between.

TradeStack uses startup to rebuild the SQLite `cache_index` if it's empty (first boot or recovery). Shutdown does nothing heavy — connections are thread-local and cleaned up by the OS.

## Concept — In-Memory Operation Tracking

Long-running jobs (bhavcopy update, scan, historical download) take minutes. HTTP can't hold a connection that long reliably, so TradeStack uses a **polling pattern**:

```python
active_operations: dict = {}

@app.post("/api/scanner/continuation")
def trigger_continuation_scan(request=None):
    operation_id = f"scan_{datetime.now().strftime('%Y%m%d_%H%M%S')}_{uuid.uuid4().hex[:6]}"
    active_operations[operation_id] = {
        "operation_id": operation_id,
        "type": "continuation_scan",
        "status": "starting",
        "progress": 0,
        "message": "Scanning...",
        "logs": [...],
    }
    t = threading.Thread(target=_run_continuation_scan, args=(operation_id, params, scan_date), daemon=True)
    t.start()
    return {"status": "started", "operation_id": operation_id}

@app.get("/api/scanner/status/{operation_id}")
def get_scan_status(operation_id: str):
    op = active_operations.get(operation_id)
    if not op:
        raise HTTPException(status_code=404, detail="Operation not found")
    return op
```

Flow: client POSTs → gets `operation_id` → polls GET `/status/{id}` every second → reads `progress`, `message`, `logs` → stops when `status` is `completed`/`error`.

Note the mix: some jobs use `BackgroundTasks` (FastAPI's built-in, runs after response in the same event loop thread pool) and some use `threading.Thread` (manual, for CPU-bound scans). Both update the same `active_operations[op_id]` dict in place — that's how progress streams to the polling client.

## Concept — Background Tasks (Two Styles)

Style A — `BackgroundTasks` (FastAPI native):

```python
@app.post("/api/data/update-bhavcopy")
def trigger_update(background_tasks: BackgroundTasks, request=None):
    ...
    background_tasks.add_task(_run_bhavcopy_update, operation_id, target)
    return {"status": "started", "operation_id": operation_id}
```

FastAPI runs `_run_bhavcopy_update` after sending the response. Good for I/O-bound work.

Style B — `threading.Thread` (manual):

```python
t = threading.Thread(target=_run_continuation_scan, args=(operation_id, params, scan_date), daemon=True)
t.start()
```

Used for the scanner because it's CPU-bound and blocking; a thread keeps the event loop free. `daemon=True` means the thread dies with the process (no zombie threads on shutdown).

## Concept — Pydantic Models for Request Bodies

Every POST with a body declares a model:

```python
class ScanRequest(BaseModel):
    date: Optional[str] = None
    filters: Optional[ScanFilters] = None

class ScanFilters(BaseModel):
    min_price: Optional[int] = None
    max_price: Optional[int] = None
    ...
```

FastAPI validates the JSON automatically. If the client sends `{"filters": {"min_price": "abc"}}`, FastAPI returns 422 before your handler runs. This is the same Pydantic you learned in Phase 1 — just more fields.

## What It Is NOT

- ❌ **Not one giant function** — it's sections (health, data, token, scanner, stock list, breadth, trades) glued together by comment banners.
- ❌ **Not a router-per-file** — there's no `routers/` folder; everything lives in `server.py`. TradeStack chose simplicity over modularity.
- ❌ **Not async everywhere** — routes are sync `def` (FastAPI runs them in a thread pool). Only lifespan and middleware are `async`.
- ❌ **Not stateless** — `active_operations` is in-memory; a server restart wipes in-flight job progress.

## Nutshell

**server.py = imports → logging → middleware → lifespan → app → active_operations → route groups → background tasks → entry point. Read top-to-bottom. Routes are grouped by comment banners (Ctrl+F the banner). Long jobs use the operation_id + polling pattern.**

## Common Mistakes

- ❌ **"I need to read all 930 lines before understanding anything"** — no. Read the skeleton first (imports, app, middleware, lifespan), then jump to the section you care about.
- ❌ **"BackgroundTasks and threading.Thread are the same"** — no. BackgroundTasks runs in FastAPI's thread pool after the response; threading.Thread is manual and you manage it. TradeStack uses both deliberately.
- ❌ **"active_operations persists across restarts"** — no, it's a plain dict in memory. Restart = gone.
- ❌ **"Routes must be async"** — no. Sync `def` routes are fine and common for blocking work; FastAPI handles the thread pool.
- ❌ **"The 14 modules are 14 files"** — no, they're 14 logical sections inside one file (plus the `src/` modules they import).

## In Your Own Words

1. What are the 9 sections of `server.py` in order, and why does the order matter?

<details>
<summary>Sample Answer</summary>

**Answer:** Imports → logging → middleware → lifespan → app creation → active_operations → route groups → background tasks → entry point. Order matters because FastAPI executes top-to-bottom at import time: logging must exist before anything logs, middleware must be registered before routes, lifespan must be defined before being passed to `FastAPI(...)`, and `app` must exist before routes attach to it.

</details>

2. What does the `lifespan` function do at startup, and why is it an `asynccontextmanager`?

<details>
<summary>Sample Answer</summary>

**Answer:** At startup it checks `get_cache_stats()`; if the cache index is empty (0 stocks), it rebuilds the index from `.pkl` files via `cache_manager.rebuild_index()`. It's an `asynccontextmanager` so code before `yield` runs on startup and code after `yield` runs on shutdown, with `yield` handing control to FastAPI to serve requests in between.

</details>

3. How does the frontend track a long-running scan's progress?

<details>
<summary>Sample Answer</summary>

**Answer:** It POSTs to trigger the scan, receives an `operation_id`, then polls `GET /api/scanner/status/{operation_id}` every second. The server stores a dict in `active_operations[op_id]` with `status`, `progress`, `message`, and `logs`, updated in place by the background thread. Polling stops when `status` becomes `completed` or `error`.

</details>

4. What's the difference between `BackgroundTasks` and `threading.Thread` in this codebase, and which jobs use which?

<details>
<summary>Sample Answer</summary>

**Answer:** `BackgroundTasks` is FastAPI-native — runs after the response in FastAPI's thread pool, used for I/O-bound jobs like bhavcopy update. `threading.Thread` is manual — you create/start it yourself, used for CPU-bound scans so the event loop stays free. Both update the same `active_operations` dict for progress polling.

</details>

5. Why is there a global `@app.exception_handler(Exception)`?

<details>
<summary>Sample Answer</summary>

**Answer:** To convert any unhandled exception into a consistent JSON 500 with `{"detail": "Internal server error: <ExceptionClass>"}`. The frontend reads `detail` from every error response, so this guarantees a stable error shape no matter where the crash happens.

</details>
