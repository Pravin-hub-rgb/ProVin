In 3.5, you saw how live prices stream into TradeStack. Now the live trader consumes those ticks and decides: enter, hold, exit, reject. Those decisions must never contradict each other — you can't exit a position you never entered, or enter twice. A **state machine** is what prevents that. Let's look at `frontend/src/lib/live-trader/reversal/state-machine.ts` (and its continuation twin).

# 3.6 State Machine — Live Trader Logic, Order State Transitions

## Think — A Traffic Light

A traffic light isn't a boolean "go/stop". It has states: RED, YELLOW, GREEN. And transitions are constrained: GREEN → YELLOW → RED → GREEN. You can't jump GREEN → RED directly, and "GREEN" means something specific (you may go). The state tells you what's allowed next.

A state machine is exactly that: a fixed set of states, and explicit rules for which transitions are legal. Your code checks the current state before doing anything, and the state changes only through defined transitions.

## Concept — What a State Machine Is

A state machine = (states, transitions, current state). Three rules:

1. **Finite states** — a small, enumerated set (not free-form strings).
2. **Transitions are explicit** — `enter_position()` moves INITIALIZED → ENTERED; nothing else does.
3. **Actions are gated by state** — `exit_position()` only makes sense if state is ENTERED.

TradeStack's live trader defines 12 states (`StockStateEnum`):

```python
# Python equivalent of the TS enum
from enum import Enum

class StockStateEnum(Enum):
    INITIALIZED = "initialized"
    WAITING_FOR_OPEN = "waiting_for_open"
    GAP_VALIDATED = "gap_validated"
    QUALIFIED = "qualified"
    SELECTED = "selected"
    WAITING_FOR_ENTRY = "waiting_for_entry"
    ENTERED = "entered"
    NOT_SELECTED = "not_selected"
    REJECTED = "rejected"
    UNSUBSCRIBED = "unsubscribed"
    EXITED = "exited"
```

And a `transitionTo(newState, reason)` method that logs every change:

```python
def transitionTo(self, new_state, reason=""):
    old = self.state
    self.state = new_state
    msg = f"[{self.symbol}] State: {old} -> {new_state}" + (f" ({reason})" if reason else "")
    print(msg)
```

Every transition is logged. When a trade goes wrong at 9:47 AM, you replay the log and see exactly which state it was in and why it moved.

## Concept — Order States (The Simpler View)

For orders specifically, the classic state machine has 4 states:

```
PENDING → OPEN → FILLED
              ↘ CANCELLED
```

- **PENDING**: order created, not yet sent to broker.
- **OPEN**: sent to broker, waiting for fill.
- **FILLED**: broker confirmed execution.
- **CANCELLED**: order cancelled (by user or system) before fill.

Transitions:
- `PENDING → OPEN` (submit)
- `OPEN → FILLED` (broker fill)
- `OPEN → CANCELLED` (cancel)
- `PENDING → CANCELLED` (cancel before submit)

Illegal: `FILLED → OPEN`, `CANCELLED → FILLED`, `FILLED → CANCELLED`. A state machine enforces these by only defining the legal transitions.

## Concept — A Runnable Python State Machine (Orders)

Here's a complete, runnable example you can paste and run:

```python
from enum import Enum

class OrderState(Enum):
    PENDING = "pending"
    OPEN = "open"
    FILLED = "filled"
    CANCELLED = "cancelled"

class Order:
    def __init__(self, symbol, qty, price):
        self.symbol = symbol
        self.qty = qty
        self.price = price
        self.state = OrderState.PENDING
        self._history = [OrderState.PENDING]

    def _transition(self, new_state):
        legal = {
            OrderState.PENDING: {OrderState.OPEN, OrderState.CANCELLED},
            OrderState.OPEN: {OrderState.FILLED, OrderState.CANCELLED},
            OrderState.FILLED: set(),
            OrderState.CANCELLED: set(),
        }
        if new_state not in legal[self.state]:
            raise ValueError(f"Illegal transition: {self.state.value} -> {new_state.value}")
        self.state = new_state
        self._history.append(new_state)
        print(f"[{self.symbol}] {self._history[-2].value} -> {new_state.value}")

    def submit(self):
        self._transition(OrderState.OPEN)

    def fill(self, fill_price):
        self._transition(OrderState.FILLED)
        self.price = fill_price

    def cancel(self):
        self._transition(OrderState.CANCELLED)

# Demo
o = Order("RELIANCE", 10, 2450.0)
o.submit()          # pending -> open
o.fill(2451.5)      # open -> filled
try:
    o.cancel()      # raises: filled is terminal
except ValueError as e:
    print("Blocked:", e)

o2 = Order("TCS", 5, 3800.0)
o2.submit()
o2.cancel()         # open -> cancelled
print("History:", [s.value for s in o2._history])
```

Run it: `pending -> open -> filled`, then `cancel()` raises. That's the bug prevented: you can't cancel a filled order.

## Concept — TradeStack's Real State Machine (Stocks, Not Orders)

TradeStack's state machine isn't about orders — it's about **stocks being evaluated for entry** during a live session. Each stock object mixes in `StateMachineMixin` (from `orb-base.ts`) and holds a `state: StockStateEnum`.

The flow (reversal example):

```
INITIALIZED
  → (open price arrives) WAITING_FOR_OPEN
  → validateGap() → GAP_VALIDATED   (or REJECTED if gap too flat / too high)
  → checkLowViolation() → QUALIFIED  (or REJECTED if low violated)
  → prepareEntry() → SELECTED → WAITING_FOR_ENTRY
  → (entry trigger fires) → ENTERED
  → (exit trigger fires) → EXITED
```

Key methods, each gated by state:

```typescript
transitionTo(newState, reason = "") { ... }   // the only way state changes
reject(reason) { isActive=false; isSubscribed=false; transitionTo(REJECTED) }
validateGap(): boolean { ... }                 // INITIALIZED-ish -> GAP_VALIDATED or REJECTED
checkLowViolation(): boolean { ... }           // -> QUALIFIED or REJECTED
prepareEntry(): void { if state==QUALIFIED: transitionTo(SELECTED); ... }
enterPosition(price, ts) { ... transitionTo(ENTERED) }
exitPosition(price, ts, reason) { ... transitionTo(EXITED) }
```

Notice `prepareEntry()` checks `if (this.state === StockStateEnum.QUALIFIED)` before transitioning to SELECTED. And `enterPosition`/`exitPosition` don't check state explicitly but are only called by the tick processor when the state is right. The state is the single source of truth for "what phase is this stock in".

## Concept — Why State Machines Prevent Bugs

Without a state machine, you'd write:

```python
if not entered and price > entry_high:
    enter()
if entered and price < stop_loss:
    exit()
```

This breaks when:
- A tick arrives out of order (exit before enter).
- Two ticks arrive simultaneously (double enter).
- A reconnect replays old ticks (re-enter after exit).

With a state machine, the state itself is the guard:

```python
def on_tick(self, price):
    if self.state == StockStateEnum.WAITING_FOR_ENTRY and price >= self.entry_price:
        self.enterPosition(price, now())
    elif self.state == StockStateEnum.ENTERED and price <= self.entry_sl:
        self.exitPosition(price, now(), "stop loss")
    # any other state: do nothing — the tick is irrelevant
```

The `elif` chain on `self.state` means an ENTERED stock never re-enters, and a non-entered stock never exits. The state is the memory of "what has happened"; you don't need separate boolean flags like `entered`, `exited` (though TradeStack keeps them for convenience — the state is authoritative).

## Concept — State vs Flags (The Tempting Mistake)

TradeStack's mixin keeps both: `state: StockStateEnum` AND booleans (`entered`, `entryReady`, `gapValidated`). This is slightly redundant but pragmatic — booleans are fast to check in hot tick paths, and `state` is the audit trail. Rule: **if they disagree, trust `state`**. The booleans are caches; the state is truth.

## Concept — Terminal States

Some states are terminal — no transitions out:

- `REJECTED` (stock failed a check; never trade it)
- `EXITED` (position closed; done)
- `NOT_SELECTED` / `UNSUBSCRIBED`

Terminal states protect you from "zombie" re-evaluation. Once rejected, a stock stays rejected for the session; a tick can't revive it. This is crucial during reconnects: replayed ticks don't re-trigger entries.

## Concept — Compare with Phase 1/2

| Phase 1-2 | TradeStack (production) |
|---|---|
| Booleans (`is_connected`, `entered`) | Enum state + booleans |
| Ad-hoc `if` checks | Gated transitions via `transitionTo` |
| No transition log | Every transition logged with reason |
| No terminal states | REJECTED/EXITED are terminal |
| Single flag per concern | One state machine per stock object |

## What It Is NOT

- ❌ **Not a database state** — this is in-memory per stock, per session. Restarts reset all states.
- ❌ **Not a workflow engine** — no persistence, no retries, no sagas. Just an enum + transition method.
- ❌ **Not thread-safe by default** — the state machine assumes single-threaded tick processing per stock. Concurrent ticks on the same stock would race; the tick processor serializes them.
- ❌ **Not the order state** — TradeStack's machine tracks *stock evaluation phase*, not broker order lifecycle. (Orders are logged to SQLite `trade_log` separately.)

## Nutshell

**State machine = finite enum of states + explicit legal transitions + state-gated actions + logged transitions + terminal states. It replaces ad-hoc boolean flags and prevents illegal sequences (exit-before-enter, double-enter, zombie revival). TradeStack uses `StockStateEnum` (12 states) per stock; the simpler order version uses PENDING/OPEN/FILLED/CANCELLED.**

## Common Mistakes

- ❌ **"Use booleans instead of an enum"** — booleans compose badly (3 booleans = 8 states, most illegal). An enum makes illegal states unrepresentable.
- ❌ **"Allow any transition"** — defeats the purpose. Define `legal` map and raise on illegal.
- ❌ **"Forget terminal states"** — without them, a rejected stock can be revived by a stray tick.
- ❌ **"Skip transition logging"** — when a live trade misbehaves at 9:47 AM, the log is the only evidence.
- ❌ **"Trust booleans over state"** — booleans are caches; `state` is truth. If they disagree, state wins.

1. What is a state machine, and what are its three core rules?

<details>
<summary>Sample Answer</summary>

**Answer:** A state machine is a finite set of states with explicit legal transitions and state-gated actions. Three rules: (1) states are a small enumerated set, not free-form; (2) transitions are explicit — only defined moves are allowed; (3) actions check the current state before running. It prevents illegal sequences like exit-before-enter or double-enter.

</details>

2. Write the legal transition map for an order with states PENDING, OPEN, FILLED, CANCELLED.

<details>
<summary>Sample Answer</summary>

**Answer:** PENDING → {OPEN, CANCELLED}; OPEN → {FILLED, CANCELLED}; FILLED → {} (terminal); CANCELLED → {} (terminal). So you can submit or cancel a pending order, fill or cancel an open one, and once filled or cancelled, nothing further happens.

</details>

3. Why does TradeStack keep both `state: StockStateEnum` and booleans like `entered`? Which wins on disagreement?

<details>
<summary>Sample Answer</summary>

**Answer:** Booleans are fast caches for hot tick paths; `state` is the audit trail and single source of truth. If they disagree, trust `state`. The booleans are convenience; the enum is authoritative.

</details>

4. What are terminal states, and why do they matter during reconnects?

<details>
<summary>Sample Answer</summary>

**Answer:** Terminal states (REJECTED, EXITED, NOT_SELECTED, UNSUBSCRIBED) have no outgoing transitions. They matter during reconnects because replayed ticks can't revive a rejected or exited stock — preventing duplicate entries or re-trading a closed position.

</details>

5. How does gating actions on `self.state` prevent bugs that ad-hoc boolean checks don't?

<details>
<summary>Sample Answer</summary>

**Answer:** An `elif` chain on `self.state` ensures each tick is handled by exactly one branch matching the current phase. A stock in ENTERED never re-enters; a stock not in WAITING_FOR_ENTRY never enters. Booleans can drift (two flags both true) or be checked in the wrong order; a single enum state can't be in two places at once.

</details>
