In 3.1, you saw how `server.py` is organized — routes, middleware, lifespan, background tasks. But every route that touches data ends up calling into `src/db.py`. That file is the database layer. Phase 1's SQLite was a single connection in a single thread. TradeStack's is multi-threaded, WAL-mode, with 9 tables and migrations. Let's see the difference.

# 3.2 DB Layer — SQLite in Production

## Think — One Notebook vs A Shared Whiteboard

Phase 1 SQLite was like one person with one notebook. You open it, write, close it. No concurrency, no drama.

TradeStack's SQLite is like a shared whiteboard in an office. Multiple people (threads) want to write at the same time. If everyone grabs the same marker, you get smudged text and arguments. So you give each person their own marker (thread-local connection) but the same whiteboard (one `.db` file on disk). And you turn on "WAL mode" so readers don't block writers and writers don't block readers — like a whiteboard with a transparent overlay sheet.

## Concept — Thread-Local Connections

FastAPI runs sync routes in a thread pool. Background tasks run in their own threads. If all threads share ONE `sqlite3.Connection`, you get "SQLite objects created in a thread can only be used in that thread" errors.

TradeStack's fix: `threading.local()`:

```python
_local = threading.local()

def get_connection() -> sqlite3.Connection:
    if not hasattr(_local, "conn") or _local.conn is None:
        DB_PATH.parent.mkdir(parents=True, exist_ok=True)
        _local.conn = sqlite3.connect(str(DB_PATH), timeout=10)
        _local.conn.row_factory = sqlite3.Row
        _local.conn.execute("PRAGMA journal_mode=WAL")
        _local.conn.execute("PRAGMA synchronous=NORMAL")
        _local.conn.execute("PRAGMA busy_timeout=5000")
        logger.debug(f"SQLite connection opened for thread {threading.current_thread().name}")
    return _local.conn
```

Each thread gets its own connection, lazily created on first use, cached in `_local`. All connections point at the same on-disk file. No cross-thread sharing, no errors.

The pragmas:
- `journal_mode=WAL` — Write-Ahead Logging. Writers append to a `-wal` file; readers read the main DB. Readers and writers don't block each other.
- `synchronous=NORMAL` — fsync less often. Faster writes, tiny risk on power loss (acceptable for this app).
- `busy_timeout=5000` — if a write lock is held, wait up to 5 seconds instead of failing immediately. Handles the rare collision.

## Concept — Schema (The 9 Tables)

`SCHEMA_SQL` creates tables if they don't exist (`CREATE TABLE IF NOT EXISTS`). The key ones:

| Table | Purpose |
|---|---|
| `cache_index` | Metadata index for `.pkl` cache files (symbol, row_count, first/last date, file size) |
| `upstox_config` | Upstox token + api key/secret (key-value) |
| `settings` | All app settings with type/category/label/validation metadata |
| `settings_meta` | Settings schema version tracking |
| `stock_list_items` | Trading lists (continuation/reversal picks) with close, trend_context, period |
| `breadth_results` | Market breadth per date (up/down counts, above/below MA) |
| `trade_log` | Paper trade entries with entry/exit, P&L |
| (others) | supporting |

The clever part: `cache_index` is a **metadata index** for `.pkl` files, not the data itself. The actual OHLCV data lives in `data/cache/RELIANCE.pkl`. SQLite only stores "RELIANCE has 180 rows, last date 2026-11-03, file size 42 KB". This makes "list all cached symbols" instant (one SQL query) instead of globbing 2000 files.

## Concept — The db.py Pattern (CRUD by Domain)

`db.py` is organized by domain, each section with its own functions:

```python
# --- Cache Index CRUD ---
def upsert_cache_index(symbol, row_count, first_date, last_date, file_size_bytes): ...
def get_cache_stats() -> dict: ...
def list_symbols_from_index() -> list[str]: ...
def rebuild_cache_index(cache_dir): ...

# --- Upstox Config CRUD ---
def upstox_get(key) -> Optional[str]: ...
def upstox_set(key, value): ...

# --- Settings CRUD ---
def settings_get_all() -> list[dict]: ...
def settings_get(key) -> Optional[dict]: ...
def settings_upsert(...): ...
def settings_set_value(key, value): ...

# --- Stock List CRUD ---
def add_stock_to_list(list_type, symbol, ...): ...
def get_stock_list(list_type): ...

# --- Breadth Results CRUD ---
def upsert_breadth(...): ...
def get_all_breadth(): ...

# --- Trade Log CRUD ---
def add_trade_log(...): ...
def get_trade_logs(...): ...
def update_trade_log(trade_id, exit_date, exit_price): ...
```

Every function follows the same shape: get connection → execute SQL with `?` placeholders → commit → return. No ORM, no query builder. Raw SQL with parameterized queries (safe from SQL injection).

## Concept — Batch Operations (Commit Control)

For bulk inserts, committing per row is slow. So there's a batch variant:

```python
def upsert_cache_index(symbol, ...):
    conn = get_connection()
    conn.execute("INSERT ... ON CONFLICT DO UPDATE ...", (...))
    conn.commit()          # commits immediately

def upsert_cache_index_batch(symbol, ...):
    conn = get_connection()
    conn.execute("INSERT ... ON CONFLICT DO UPDATE ...", (...))
    # NO commit — caller commits later

def commit_cache_index():
    get_connection().commit()
```

`cache_manager.save()` uses `commit=True` by default but passes `commit=False` during bulk rebuilds, then commits once at the end. This turns 2000 commits into 1.

## Concept — Migrations (Schema Evolution)

Old databases don't have new columns. Instead of a migration framework, TradeStack does lazy column adds:

```python
def _run_migrations():
    conn = get_connection()
    for col, dtype in [("exit_date", "TEXT"), ("pnl_type", "TEXT"), ("pnl_amount", "REAL"),
                       ("trade_type", "TEXT"), ("exit_price", "REAL"), ("quantity", "INTEGER DEFAULT 100")]:
        try:
            conn.execute(f"ALTER TABLE trade_log ADD COLUMN {col} {dtype}")
        except Exception:
            pass  # column already exists
    conn.commit()
```

Try to add the column; if it exists, the exception is swallowed. Run on import (`init_db()` then `_run_migrations()`). Simple, idempotent, good enough for a single-file DB.

## Concept — Init on Import

```python
# --- Initialize on import ---
init_db()
_run_migrations()
```

At the bottom of `db.py`. The moment any module does `from src.db import ...`, the DB is created and migrated. `server.py` imports `db` early, so by the time routes run, tables exist. `DB_PATH` can be overridden via `TRADESTACK_DB_PATH` env var (used by tests to isolate from prod data).

## Concept — Compare with Phase 1

| Phase 1 (mini) | TradeStack (production) |
|---|---|
| Single connection, single thread | Thread-local connections, one per thread |
| No WAL (default journal mode) | WAL mode + busy_timeout + synchronous=NORMAL |
| One table (`stocks`) | 9 tables (cache_index, settings, stock_list, breadth, trade_log, ...) |
| `CREATE TABLE` once | `CREATE TABLE IF NOT EXISTS` + lazy migrations |
| Commit every write | Batch commit for bulk ops |
| Direct sqlite3 calls in route | Domain-grouped CRUD functions in `db.py` |
| No env override | `TRADESTACK_DB_PATH` for test isolation |

The pattern is the same (raw SQL, parameterized queries, commit). The difference is concurrency safety and scale.

## What It Is NOT

- ❌ **Not an ORM** — no SQLAlchemy, no models. Raw SQL with `?` placeholders.
- ❌ **Not a server process** — SQLite is a file; no separate DB server to run.
- ❌ **Not multi-process safe by default** — thread-local connections handle threads in one process. Multiple server processes would need separate DB files or a real DB.
- ❌ **Not a cache for the OHLCV data** — SQLite stores metadata (cache_index) and config (settings, lists, trades). The price data is in `.pkl` files.

## Nutshell

**TradeStack DB = one SQLite file, thread-local connections, WAL mode, 9 tables, domain-grouped CRUD, lazy migrations, batch commits, env-overridable path. Same raw-SQL pattern as Phase 1, hardened for multi-threaded production.**

## Common Mistakes

- ❌ **"Share one connection across threads"** — SQLite will throw "created in a thread can only be used in that thread". Use `threading.local()`.
- ❌ **"Forget WAL mode"** — readers block writers (or vice versa) under default journal mode; production gets lock errors.
- ❌ **"Commit per row in bulk"** — 2000 commits = slow. Use batch variants + single commit.
- ❌ **"Hardcode the DB path"** — tests can't isolate. Use env var override.
- ❌ **"Run migrations as a separate step"** — TradeStack runs them on import, so they can't be forgotten.

## In Your Own Words

1. Why does TradeStack use `threading.local()` for SQLite connections?

<details>
<summary>Sample Answer</summary>

**Answer:** FastAPI runs sync routes in a thread pool and background tasks run in their own threads. A single shared `sqlite3.Connection` raises "SQLite objects created in a thread can only be used in that thread". `threading.local()` gives each thread its own connection (lazily created, cached), all pointing at the same file. No cross-thread sharing, no errors.

</details>

2. What does WAL mode do, and why does it matter here?

<details>
<summary>Sample Answer</summary>

**Answer:** Write-Ahead Logging writes changes to a separate `-wal` file instead of the main DB, so readers read the main DB while writers append to the WAL. Readers and writers don't block each other. Combined with `busy_timeout=5000` (wait up to 5s on a lock) and `synchronous=NORMAL`, this keeps a multi-threaded FastAPI app from hitting "database is locked" errors.

</details>

3. What is `cache_index` and why does it exist instead of just globbing the cache folder?

<details>
<summary>Sample Answer</summary>

**Answer:** `cache_index` is a SQLite table storing metadata about each `.pkl` file (symbol, row count, first/last date, file size). Listing 2000 symbols via SQL is instant; globbing 2000 files and unpickling each to read metadata is slow. The actual price data stays in `.pkl` files; SQLite only indexes it.

</details>

4. How does TradeStack handle schema changes (new columns) without a migration framework?

<details>
<summary>Sample Answer</summary>

**Answer:** Lazy column adds in `_run_migrations()`: for each (column, type) pair it runs `ALTER TABLE ... ADD COLUMN ...` inside a try/except, swallowing the "column already exists" error. It's idempotent and runs on import, so migrations can't be forgotten. Good enough for a single-file DB.

</details>

5. Compare Phase 1's SQLite usage with TradeStack's. What's the same and what changed?

<details>
<summary>Sample Answer</summary>

**Answer:** Same: raw SQL with `?` placeholders, explicit commit, `CREATE TABLE` DDL, one file on disk. Changed: thread-local connections (was single), WAL mode (was default), 9 tables (was one), domain-grouped CRUD functions (was inline), batch commits (was per-write), lazy migrations (was none), env-overridable path (was hardcoded). The pattern survived; concurrency safety and scale were added.

</details>
