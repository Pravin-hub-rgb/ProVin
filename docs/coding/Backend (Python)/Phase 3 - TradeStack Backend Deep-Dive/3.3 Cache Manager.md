In 3.2, you saw that SQLite stores metadata about cached stocks in `cache_index`. But the actual price data — 2000 stocks × ~180 trading days of OHLCV — lives in `.pkl` files on disk, managed by `src/cache_manager.py`. This file is the bridge between the database (fast metadata) and the filesystem (bulk data). Let's read it.

# 3.3 Cache Manager — Pickle Cache, .pkl Files, Invalidation

## Think — A Library Card Catalog

Imagine a library with 2000 books. You could walk the shelves every time someone asks "do we have RELIANCE?" — but that's slow. Instead, the librarian keeps a card catalog (SQLite `cache_index`): one card per book with title, page count, last checked date. The actual book sits on the shelf (the `.pkl` file). You look up the card first (instant), then fetch the book only if needed.

`cache_manager.py` is the librarian. `save()` writes the book AND updates the card. `load()` fetches the book. `stats()` reads the card catalog. `list_symbols()` reads the card catalog. The filesystem is the shelf; SQLite is the catalog.

## Concept — Why a Cache Exists at All

TradeStack scans 2000 stocks × 13 indicators. If every scan read from the Upstox API, you'd hit rate limits, pay for bandwidth, and wait minutes per scan. Instead:

- Historical OHLCV is downloaded **once** (bhavcopy / Upstox historical) and stored as `.pkl` files.
- Scans, charts, and the stock list all read from these files.
- Only **new** data (today's bhavcopy) is appended.

So the cache is the whole point of the app's speed. Without it, TradeStack is just a slow API proxy.

## Concept — Pickle Serialization

Python's `pickle` module serializes Python objects to bytes and back. A pandas DataFrame (with a DatetimeIndex and typed columns) pickles to a single file and unpickles to an identical DataFrame:

```python
import pickle
import pandas as pd

# SAVE
with open("RELIANCE.pkl", "wb") as f:
    pickle.dump(df, f)        # df -> bytes on disk

# LOAD
with open("RELIANCE.pkl", "rb") as f:
    data = pickle.load(f)     # bytes -> DataFrame
```

`cache_manager` wraps this:

```python
class CacheManager:
    def __init__(self, cache_dir=None):
        ...
        self.cache_dir = Path(cache_dir)
        self.cache_dir.mkdir(parents=True, exist_ok=True)

    def get_cache_path(self, symbol):
        return self.cache_dir / f"{symbol.upper()}.pkl"

    def load(self, symbol):
        path = self.get_cache_path(symbol)
        if not path.exists():
            return None
        try:
            with open(path, "rb") as f:
                data = pickle.load(f)
            if isinstance(data, pd.DataFrame) and not data.empty:
                return data
            return None
        except Exception as e:
            logger.warning(f"Failed to load cache for {symbol}: {e}")
            return None

    def save(self, symbol, data, commit=True):
        path = self.get_cache_path(symbol)
        try:
            with open(path, "wb") as f:
                pickle.dump(data, f)
            self._update_index(symbol, data, path, commit=commit)
            logger.debug(f"Saved cache for {symbol}: {len(data)} rows")
        except Exception as e:
            logger.error(f"Failed to save cache for {symbol}: {e}")
            raise
```

Two things happen on `save()`: (1) write the `.pkl` file, (2) upsert a row in `cache_index`. If step 1 succeeds but step 2 fails, the file exists but the index doesn't know — `rebuild_index()` fixes that.

## Concept — The Dual Source of Truth

There are two stores:

1. **Filesystem** (`data/cache/*.pkl`) — the source of truth for price data.
2. **SQLite `cache_index`** — a derived index for fast metadata queries.

Every read prefers SQLite and falls back to the filesystem:

```python
def stats(self):
    result = db.get_cache_stats()
    if result["stock_count"] > 0:
        return result
    # fallback: glob
    files = list(self.cache_dir.glob("*.pkl"))
    total_size = sum(f.stat().st_size for f in files)
    latest_date = self.get_latest_cache_date()
    return {"stock_count": len(files), "total_size_mb": total_size / (1024*1024), "latest_date": ...}

def list_symbols(self):
    symbols = db.list_symbols_from_index()
    if symbols:
        return symbols
    return sorted(f.stem for f in self.cache_dir.glob("*.pkl"))
```

This means the app keeps working even if the index is stale or empty — it just gets slower. And `rebuild_index()` repopulates the index by scanning all `.pkl` files (used on first boot and recovery).

## Concept — Updating / Merging Data

When new bhavcopy data arrives, you don't replace the whole file — you merge:

```python
def update(self, symbol, new_data, commit=True):
    self.update_with_data(symbol, new_data, commit=commit)

def update_with_data(self, symbol, new_data, existing=None, commit=True):
    if existing is None:
        existing = self.load(symbol)
    if existing is not None and not existing.empty:
        combined = pd.concat([existing, new_data])
        combined = combined[~combined.index.duplicated(keep="last")]   # dedup, keep newer
        combined = combined.sort_index()
    else:
        combined = new_data
    combined["last_updated"] = pd.Timestamp.now()
    self.save(symbol, combined, commit=commit)
```

`pd.concat` stacks old + new rows. The dedup line (`~index.duplicated(keep="last")`) drops duplicate dates keeping the newer value. `sort_index()` keeps dates in order. Then `save()` writes the merged DataFrame back to `.pkl` and updates the index.

## Concept — Invalidation (When to Throw Away Cache)

Cache invalidation is the hard part. TradeStack's strategies:

1. **Age-based** — `needs_update(symbol, max_age_days=3)`: if the last cached date is older than 3 days, re-fetch.
2. **Manual delete** — `fix-stock` endpoint unlinks the `.pkl` file and re-downloads from Upstox.
3. **Gap detection** — `detect_gaps()` finds stocks whose cached series has holes (missing trading days); `fix-gap-stocks` re-downloads those.
4. **Full rebuild** — `rebuild_index()` rescans all `.pkl` files if the index is empty/corrupt.
5. **`last_updated` column** — every merged row gets a `last_updated` timestamp, so you can see when data was last touched.

There's no TTL or auto-expiry. Invalidation is explicit: age check, manual fix, or gap scan. This is deliberate — financial data shouldn't silently disappear; you want to know when you're re-downloading.

## Concept — Reading from Cache (Helpers)

```python
def get_last_date(self, symbol):
    data = self.load(symbol)
    if data is None or data.empty: return None
    last_idx = data.index[-1]
    return last_idx.date() if hasattr(last_idx, "date") else last_idx

def get_last_close(self, symbol):
    data = self.load(symbol)
    if data is None or data.empty or "close" not in data.columns: return None
    val = data["close"].iloc[-1]
    if pd.isna(val): return None
    return float(val)

def get_date_range(self, symbol, start=None, end=None):
    data = self.load(symbol)
    if data is None or data.empty: return pd.DataFrame()
    if not isinstance(data.index, pd.DatetimeIndex):
        data.index = pd.to_datetime(data.index)
    if start: data = data[data.index >= pd.Timestamp(start)]
    if end:   data = data[data.index <= pd.Timestamp(end)]
    return data
```

`get_last_close` is used by the stock-list "resolved" endpoint to show live cached closes. `get_date_range` powers charts (fetch last N days).

## What It Is NOT

- ❌ **Not a distributed cache** — it's local files on one machine. No Redis, no Memcached.
- ❌ **Not automatic expiry** — nothing auto-deletes stale files. Invalidation is explicit.
- ❌ **Not a database** — `.pkl` files aren't queryable. You load the whole DataFrame or nothing.
- ❌ **Not safe to share across processes** — pickle files are read/written without file locks; one writer at a time per symbol is assumed.

## Nutshell

**cache_manager = pickle-based per-stock `.pkl` files in `data/cache/`, indexed by SQLite `cache_index`. save() writes file + index. load() reads file. update() merges new rows (dedup + sort). Invalidation: age check, manual delete, gap detection, full rebuild. Two stores (filesystem data + SQLite metadata) with fallbacks.**

## Common Mistakes

- ❌ **"pickle is human-readable"** — no, it's binary. Open it in a text editor and you'll see garbage. Use `pickle.load` or `pd.read_pickle`.
- ❌ **"The index is the source of truth"** — no, the `.pkl` files are. The index is a derived cache; rebuild it any time with `rebuild_index()`.
- ❌ **"save() only writes the file"** — no, it also upserts `cache_index`. If you bypass `save()` and write the file directly, the index goes stale.
- ❌ **"update() replaces data"** — no, it merges (concat + dedup keep-last + sort). Replacing would lose history.
- ❌ **"Cache auto-expires"** — no. Nothing auto-deletes. Use `needs_update()` or manual fix endpoints.

## In Your Own Words

1. What does `cache_manager.save()` do, and why are there two stores (filesystem + SQLite)?

<details>
<summary>Sample Answer</summary>

**Answer:** `save()` writes the DataFrame to a `.pkl` file AND upserts a metadata row in SQLite's `cache_index`. The filesystem holds the actual price data (queryable only by loading the whole file); SQLite holds metadata (symbol, row count, date range, file size) for instant queries like "list all symbols" or "latest cache date". Two stores because each is good at what the other is bad at.

</details>

2. How does `update_with_data()` merge new data without losing history or creating duplicates?

<details>
<summary>Sample Answer</summary>

**Answer:** It loads the existing DataFrame, `pd.concat`s old + new, drops duplicate index entries keeping the last (newer) value with `~index.duplicated(keep="last")`, sorts by index, then saves. So new rows are added, conflicting dates take the newer value, and history is preserved.

</details>

3. Name the four invalidation strategies TradeStack uses and when each applies.

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Age-based `needs_update(max_age_days=3)` — re-fetch if last cached date is older than N days. (2) Manual delete via `fix-stock` endpoint — unlink `.pkl` and re-download one stock. (3) Gap detection — `detect_gaps()` finds holes; `fix-gap-stocks` re-downloads those. (4) Full rebuild — `rebuild_index()` rescans all `.pkl` files when the index is empty/corrupt.

</details>

4. Why does `stats()` fall back to globbing the filesystem if SQLite returns 0?

<details>
<summary>Sample Answer</summary>

**Answer:** Because the index is derived, not authoritative. If the DB is fresh, corrupted, or the index wasn't rebuilt yet, the app should still report how many `.pkl` files exist. Fallback to glob keeps the app usable; `rebuild_index()` can repopulate the index later.

</details>

5. Compare Phase 1's data access with TradeStack's cache. What's the key difference in approach?

<details>
<summary>Sample Answer</summary>

**Answer:** Phase 1 read from SQLite/DB/API on every request with no cache. TradeStack persists OHLCV as `.pkl` files once and reads from them, with SQLite indexing metadata. The shift is from "fetch on demand" to "download once, read many" — essential for scanning 2000 stocks × 13 indicators without hammering the broker API.

</details>
