In 3.3, you saw how 2000 stocks' price data is stored as `.pkl` files and indexed by SQLite. Now the question: how do you scan all 2000 stocks × 13 indicators fast enough to be useful? Phase 1's scan was a simple `for` loop over 4 stocks. TradeStack uses `ProcessPoolExecutor` to parallelize across CPU cores. Let's read `src/scanner.py`.

# 3.4 Scanner — ProcessPoolExecutor, 2000 Stocks, 13 Indicators

## Think — One Cook vs A Kitchen Brigade

Phase 1's scan was one cook chopping 4 vegetables — fast enough. TradeStack's scan is one cook chopping 2000 vegetables with 13 different cuts each. One cook would take forever. So you split the vegetables into bowls, hand each bowl to a different cook (process), and they chop in parallel. When all bowls are done, you combine the results.

That's `ProcessPoolExecutor`: split 2000 symbols into N chunks, run each chunk in a separate process, collect results. Python's GIL means threads can't truly parallelize CPU work — processes can.

## Concept — Why Processes, Not Threads

Python has the Global Interpreter Lock (GIL): only one thread executes Python bytecode at a time. For I/O (waiting on network), threads help. For CPU (computing indicators), threads don't — they just take turns.

`ProcessPoolExecutor` spawns separate Python processes, each with its own GIL and memory. True parallelism on multi-core machines. Trade-off: processes can't share memory, so arguments/results must be **picklable** (serialized across process boundaries).

This is why `_run_chunk` is a module-level function (not a method) and re-imports inside:

```python
def _run_chunk(symbols: list, params: dict, scan_date, mode: str) -> list[dict]:
    """Process a chunk of symbols in a worker process (module-level for pickling)."""
    from src.cache_manager import cache_manager
    from src.indicators import compute_all_indicators
    ...
```

Module-level = picklable. The re-imports inside are because the worker process doesn't have `cache_manager` imported yet — it starts fresh.

## Concept — The Scanner Structure

```python
class ContinuationScanner:
    def __init__(self, params: dict):
        self.params = params

    def run(self, progress_callback=None, num_workers=None, scan_date=None) -> list[dict]:
        if scan_date is None:
            scan_date = _detect_scan_date()
        symbols = cache_manager.list_symbols()
        total = len(symbols)
        if total == 0:
            return []

        if num_workers is None:
            num_workers = min(os.cpu_count() or 4, total)

        chunk_size = max(1, total // num_workers)
        chunks = [symbols[i:i + chunk_size] for i in range(0, total, chunk_size)]

        results = []
        processed = 0

        with ProcessPoolExecutor(max_workers=num_workers) as pool:
            future_map = {pool.submit(_run_chunk, ch, self.params, scan_date, "continuation"): len(ch) for ch in chunks}
            for future in as_completed(future_map):
                chunk_len = future_map[future]
                try:
                    chunk_results = future.result()
                    results.extend(chunk_results)
                except Exception as e:
                    logger.error(f"Continuation chunk failed: {e}")
                processed += chunk_len
                if progress_callback:
                    pct = int((processed / total) * 100)
                    progress_callback(pct, f"Scanned {processed}/{total} stocks, found {len(results)} candidates")

        results.sort(key=lambda r: r["symbol"])
        return results
```

Steps:
1. Detect scan date (latest trading date in cache) if not given.
2. Get all symbols from cache index.
3. Pick worker count = `min(cpu_count, total)` (don't spawn more processes than stocks).
4. Split symbols into chunks (one per worker).
5. Submit each chunk to the pool → get a `Future`.
6. As each chunk finishes (`as_completed`), collect its results.
7. Update progress callback (so the polling frontend sees movement).
8. Sort final results by symbol.

`ReversalScanner` is identical except mode="reversal" and its own `_analyze_pattern`.

## Concept — What `_run_chunk` Does Per Stock

```python
def _run_chunk(symbols, params, scan_date, mode):
    is_continuation = mode == "continuation"
    min_rows = params.get("cont_min_data_rows" if is_continuation else "rev_min_data_rows", 50)

    scanner = ContinuationScanner(params) if is_continuation else ReversalScanner(params)

    ind_params = {
        "sma_period": params.get("sma_period", 20),
        "adr_period": params.get("adr_period", 14),
        "high_low_period": params.get("high_low_period", 20),
        "ma_angle_points": params.get("ma_angle_points", 5),
        "price_change_periods": params.get("price_change_periods", [1, 5, 20]),
    }

    results = []
    for symbol in symbols:
        try:
            data = cache_manager.load(symbol)
            if data is None or len(data) < min_rows:
                continue
            if scan_date is not None and not _stock_has_date(data, scan_date):
                continue
            if scan_date is not None:
                data = data[data.index <= pd.Timestamp(scan_date)]   # no lookahead
                if len(data) < min_rows: continue

            data = compute_all_indicators(data, indicator_params=ind_params)
            latest = data.iloc[-1]

            if scanner._passes_filters(latest, data):
                hit = scanner._analyze_pattern(data)  # or _analyze_pattern(data, scan_date)
                if hit is not None:
                    results.append({**hit, "symbol": symbol, "close": round(float(latest["close"]), 2)})
        except Exception:
            pass
    return results
```

Per stock: load `.pkl` → check enough rows → check scan date present → slice to scan date (prevents lookahead bias) → compute indicators → filter → pattern analysis → append hit. Exceptions are swallowed (one bad stock shouldn't kill the scan).

## Concept — Indicators (13 of them)

`compute_all_indicators` (in `src/indicators.py`) adds columns to the DataFrame. The scanner uses: SMA (20), ADR (14-day avg daily range), high/low over 20 days, MA angle, price change over 1/5/20 days. Phase 1 had 2 (SMA, RSI). TradeStack has 13 — but the scanner only needs a subset; the rest are used by other features (breadth, volume profile).

## Concept — Filters vs Pattern Analysis

Two stages per stock:

1. **`_passes_filters(latest, data)`** — cheap rejection. Price range, ADR minimum, liquidity (volume + movement days). Most stocks fail here and are skipped before expensive pattern work.

2. **`_analyze_pattern(data)`** — the real logic. For continuation: detect a 3-phase pattern (Phase 1 high above MA → Phase 2 decline below MA → Phase 3 recovery near MA, with rising MA). For reversal: find the best decline period (N consecutive red days, ≥10% decline) and classify trend context.

This two-stage design keeps the scan fast: filters are O(1) per stock, pattern analysis is O(lookback window).

## Concept — No Lookahead Bias

```python
if scan_date is not None:
    data = data[data.index <= pd.Timestamp(scan_date)]
```

When scanning historical dates, the scanner only sees data up to that date. Without this, a scan for "last Tuesday" would secretly use Wednesday's prices — cheating. Phase 1 didn't bother; production must.

## Concept — Progress Callback + Polling

The scanner takes a `progress_callback(pct, msg)` and calls it after each chunk. The route wraps it:

```python
def progress(pct, msg):
    op["progress"] = pct
    op["message"] = msg

scanner = ContinuationScanner(params)
results = scanner.run(progress_callback=progress, scan_date=scan_date)
```

The frontend polls `/api/scanner/status/{op_id}` and reads `progress`/`message`. Since chunks finish out of order (`as_completed`), progress jumps in steps, not smoothly — that's fine.

## Concept — Compare with Phase 1

| Phase 1 (mini) | TradeStack (production) |
|---|---|
| 4 stocks | ~2000 stocks |
| 2 indicators (SMA, RSI) | 13 indicators |
| Simple `for` loop | `ProcessPoolExecutor` (N processes) |
| No chunking | Symbols split into N chunks |
| No progress reporting | `progress_callback` per chunk |
| No date slicing | Slice to `scan_date` (no lookahead) |
| One scanner | Two scanners (continuation + reversal) |
| Sync, blocking | Runs in a `threading.Thread` (event loop stays free) |

## What It Is NOT

- ❌ **Not threads** — `ProcessPoolExecutor`, not `ThreadPoolExecutor`. CPU-bound work needs processes.
- ❌ **Not shared memory** — each process loads its own copy of the cache from disk. That's the cost of true parallelism.
- ❌ **Not deterministic order** — `as_completed` returns chunks in finish order, not submission order. Results are sorted at the end.
- ❌ **Not fault-tolerant per stock** — exceptions are swallowed (`pass`), so a corrupt `.pkl` just skips that stock. No per-stock error reporting.

## Nutshell

**Scanner = split 2000 symbols into N chunks → run each in a separate process (ProcessPoolExecutor) → per stock: load .pkl → slice to scan date → compute indicators → filter → pattern analysis → collect hits → sort. Progress via callback per chunk. Two-stage (cheap filter, then pattern) keeps it fast.**

## Common Mistakes

- ❌ **"Use threads for CPU-bound scans"** — GIL prevents parallelism. Use processes.
- ❌ **"Put the scanner logic in a class method and pass `self` to the pool"** — not picklable. Use a module-level function.
- ❌ **"Forget to re-import inside the worker"** — worker processes start fresh; `cache_manager` isn't imported. Re-import inside `_run_chunk`.
- ❌ **"Skip the scan_date slice"** — lookahead bias. Always slice `data.index <= scan_date`.
- ❌ **"Let one bad stock crash the whole scan"** — wrap per-stock work in try/except and `pass`. The scan must complete.

<details>
<summary>Sample Answer</summary>

**Answer:** Scanning is CPU-bound (computing indicators over 2000 stocks). Python's GIL lets only one thread run Python bytecode at a time, so threads don't parallelize CPU work. Processes each have their own GIL and memory, giving true multi-core parallelism. Trade-off: arguments/results must be picklable.

</details>

2. Why is `_run_chunk` a module-level function that re-imports `cache_manager` inside?

<details>
<summary>Sample Answer</summary>

**Answer:** Module-level functions are picklable, so `ProcessPoolExecutor` can send them to worker processes. Methods bound to `self` are not. The re-import is needed because worker processes start with a fresh Python interpreter — `cache_manager` isn't imported there yet.

</details>

3. What are the two stages of per-stock processing, and why split them?

<details>
<summary>Sample Answer</summary>

**Answer:** (1) `_passes_filters` — cheap rejection by price range, ADR, liquidity. (2) `_analyze_pattern` — expensive pattern detection (3-phase continuation or best-decline reversal). Splitting them keeps the scan fast: most stocks fail the cheap filter and never reach pattern analysis.

</details>

4. What is "lookahead bias" and how does the scanner prevent it?

<details>
<summary>Sample Answer</summary>

**Answer:** Lookahead bias is using future data when analyzing a past date (e.g., scanning "last Tuesday" with Wednesday's prices). The scanner prevents it by slicing `data = data[data.index <= pd.Timestamp(scan_date)]` so each stock only sees data up to the scan date.

</details>

<details>
