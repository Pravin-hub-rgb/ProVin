# 3.7 One Experiment — One Isolated Change to Understand the System

## Think — Tasting the Soup

You can read a recipe 10 times, but you only *know* the dish when you cook it once and taste it. The goal isn't to add a feature — it's to poke the system and see it react. One change, one observation, one lesson.

## Concept — Why One Small Experiment

Big changes teach nothing (too many variables). Zero changes teach nothing (you never see the system move). One small, isolated, reversible change teaches a lot:

- You see which files actually run (vs. which are dead code).
- You see the data flow (request → route → db/cache → response).
- You see the logging (what gets printed, when).
- You see the error paths (what happens when you break something).

The point is **understanding through observation**, not shipping a feature.

## Concept — Pick Your Experiment (Choose ONE)

Pick the smallest experiment that touches a layer you want to understand. Suggestions, easiest first:

1. **Add a log line** to a route (e.g., in `/health` or `/api/data/cache-info`). See request flow.
2. **Add a new tiny endpoint** (e.g., `GET /api/debug/echo/{msg}`) that returns the msg + server time. See route registration + Pydantic-less path params.
3. **Modify a scanner param default** (e.g., `price_min` from 100 to 500) and run a scan. See params flow from settings → scanner → results.
4. **Add a column to a table** via migration and read it back. See the migration pattern.
5. **Change cache invalidation threshold** (`max_age_days=3` → `1`) and observe re-fetches.
6. **Add a state transition** log in the live trader (frontend) and watch a simulated tick.

Pick ONE. Don't do all six — you'll learn less, not more.

## Concept — The Experiment Loop (5 Steps)

Every experiment follows the same loop:

```
1. Hypothesis  — "If I add X, then Y should happen."
2. Change      — edit ONE file, ONE spot, minimal diff.
3. Run         — start the server / run the scan / trigger the endpoint.
4. Observe     — read logs, response, DB state.
5. Revert or keep — git diff, then revert (this is learning, not shipping).
```

Always run `git diff` before and after so you know exactly what changed. Always revert unless you intend to ship.

## Concept — Experiment 1: Add a Log Line (Backend)

**Hypothesis:** Adding a log in `/health` will print on every health check, proving the route runs on each request.

**Change** in `backend/server.py`:

```python
@app.get("/health")
def health():
    logger.info("health check hit")
    return {"status": "healthy"}
```

**Run:**
```bash
cd TradeStack/backend
python server.py
# in another terminal:
curl http://127.0.0.1:8001/health
curl http://127.0.0.1:8001/health
```

**Observe:** `data/logs/backend.log` (or console) shows `health check hit` twice. Also `X-Process-Time` header is present (middleware runs). You've now seen: route runs per request, middleware wraps it, logging works.

**Revert:** `git checkout backend/server.py` (or undo the edit).

## Concept — Experiment 2: Add a Tiny Endpoint (Backend)

**Hypothesis:** A new endpoint with a path param and query param works end-to-end and shows up in `/docs`.

**Change** in `backend/server.py` (add near the Health section):

```python
@app.get("/api/debug/echo/{msg}")
def debug_echo(msg: str, times: int = 1):
    logger.info(f"echo msg={msg} times={times}")
    return {"echo": msg, "times": times, "server_time": datetime.now().isoformat()}
```

**Run:** server + `curl "http://127.0.0.1:8001/api/debug/echo/hello?times=3"`. Open `http://127.0.0.1:8001/docs` — your endpoint is listed and testable (FastAPI auto-generates Swagger).

**Observe:** response has the echo, times, and server_time. The `/docs` page proves FastAPI introspected your function signature (path param `msg`, query param `times` with default).

**Revert.**

## Concept — Experiment 3: Change a Scanner Param (Backend)

**Hypothesis:** Lowering `price_min` from 100 to 10 includes cheaper stocks and increases result count.

**Change:** edit the default in settings (or pass via the request body):

```bash
# via curl with filters
curl -X POST http://127.0.0.1:8001/api/scanner/continuation \
  -H "Content-Type: application/json" \
  -d '{"filters": {"min_price": 10}}'
```

Then poll:
```bash
curl http://127.0.0.1:8001/api/scanner/status/<operation_id>
```

**Observe:** `result.count` changes; `logs` show "Scanned 2000/2000 stocks, found N candidates". You've seen params flow from request → `ScanFilters` → `params` dict → `_run_chunk` → `_passes_filters`.

**Revert:** none needed (request body, not code).

## Concept — Experiment 4: Add a Migration (Backend)

**Hypothesis:** Adding a column via `_run_migrations` pattern works idempotently.

**Change** in `backend/src/db.py`, inside `_run_migrations`:

```python
for col, dtype in [..., ("experiment_note", "TEXT")]:
    try:
        conn.execute(f"ALTER TABLE trade_log ADD COLUMN {col} {dtype}")
    except Exception:
        pass
```

**Run:** restart server (import triggers migration). Check:
```bash
cd TradeStack/backend
python -c "import src.db as d; c=d.get_connection(); print([r[1] for r in c.execute('PRAGMA table_info(trade_log)').fetchall()])"
```

**Observe:** `experiment_note` appears in the column list. Restart again — no error (idempotent, exception swallowed). You've seen lazy migrations.

**Revert.**

## Concept — Experiment 5: Cache Invalidation (Backend)

**Hypothesis:** Changing `needs_update(max_age_days=3)` to `max_age_days=1` makes more stocks report "needs update".

**Change** a quick script in `TradeStack/backend/`:

```python
# experiment.py
from src.cache_manager import cache_manager
symbols = cache_manager.list_symbols()[:20]
for s in symbols:
    print(s, cache_manager.needs_update(s, max_age_days=1), cache_manager.needs_update(s, max_age_days=3))
```

**Run:** `python experiment.py`. Compare counts. You've seen age-based invalidation.

**Revert:** delete `experiment.py`.

## Concept — Experiment 6: State Transition Log (Frontend)

**Hypothesis:** Adding a `console.log` in `transitionTo` shows every state change for a stock during a live session.

**Change** in `frontend/src/lib/live-trader/reversal/state-machine.ts`:

```typescript
transitionTo(newState, reason = ""): void {
    const old = this.state;
    this.state = newState;
    console.log(`[${this.symbol}] ${old} -> ${newState} (${reason})`);
    // existing log already there; add a timestamp:
    console.log(new Date().toISOString(), this.symbol, old, "->", newState);
}
```

**Run:** start the frontend dev server, open the live trader, watch the browser console during market hours (or replay a recorded tick file).

**Observe:** every transition printed with timestamp. You've seen the state machine in action.

**Revert.**

## Concept — What to Observe (Checklist)

For any experiment, capture:

- **Logs** — `data/logs/backend.log` or console. Did your line print? When?
- **Response** — status code, body, `X-Process-Time` header.
- **DB state** — query the table before/after.
- **File state** — did a `.pkl` get created/modified? (`ls -la data/cache/`)
- **Errors** — if it broke, read the traceback. The error *is* the lesson.

## Concept — Safety Rules

- **One change at a time.** Two changes = two variables = no conclusion.
- **Never edit production data.** Use `TRADESTACK_DB_PATH` env var to point at a scratch DB for DB experiments.
- **Never commit experiments.** Revert before committing. Use `git diff` to verify.
- **Don't touch the live trader during market hours with real money.** Paper-trade only.
- **Back up before destructive experiments** (deleting `.pkl` files, dropping tables).

## Concept — The Payoff

After one experiment you'll know more than 10 hours of reading:

- Which file actually executes for a given feature (vs. dead code).
- The exact data flow and where to add logging.
- How errors propagate (route → exception handler → JSON 500).
- Where the slow parts are (timing via `X-Process-Time`).

That's the real skill: not memorizing the codebase, but knowing how to interrogate it.

## What It Is NOT

- ❌ **Not a feature request** — you're not shipping. You're learning.
- ❌ **Not a refactor** — don't "clean up while you're in there". One change, one observation.
- ❌ **Not a test suite** — experiments are throwaway. Write real tests separately (see `tests/`).
- ❌ **Not permission to skip reading** — experiments work *because* you read first. They confirm understanding, not replace it.

## Nutshell

**One experiment = hypothesis → one minimal change → run → observe (logs/response/DB/files) → revert. Pick ONE from the list. Keep it isolated, reversible, and safe (scratch DB, paper trading). The goal is understanding, not shipping.**

## Common Mistakes

- ❌ **"Change 5 things at once to save time"** — you learn nothing; you can't attribute the result.
- ❌ **"Forget to revert"** — your experiment becomes a half-baked feature. Use `git diff` to verify clean tree.
- ❌ **"Skip the hypothesis"** — without a prediction, any result feels like learning. Write it down first.
- ❌ **"Edit the prod DB"** — use `TRADESTACK_DB_PATH` env var for scratch DBs.
- ❌ **"Run experiments during market hours on live money"** — paper-trade only; observe, don't trade.

## In Your Own Words

1. What's the 5-step experiment loop?

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Hypothesis — predict what will happen. (2) Change — one file, one spot, minimal diff. (3) Run — start server / trigger endpoint / run scan. (4) Observe — logs, response, DB state, file state, errors. (5) Revert or keep — verify with `git diff`; revert unless shipping.

</details>

2. Why should you make only ONE change per experiment?

<details>
<summary>Sample Answer</summary>

**Answer:** With two changes, you can't attribute the result to either one. Isolation is what makes the observation meaningful — you learn which change caused which effect. One variable, one conclusion.

</details>

3. How do you keep a DB experiment from corrupting production data?

<details>
<summary>Sample Answer</summary>

**Answer:** Set the `TRADESTACK_DB_PATH` environment variable to a scratch `.db` file before running. `db.py` reads this env var and uses it instead of the default `data/settings.db`. Your experiment touches only the scratch file.

</details>

4. Name three things you can observe to confirm your experiment worked.

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Logs — your line printed, with correct timing. (2) HTTP response — status code, body, `X-Process-Time` header. (3) DB/file state — column exists, `.pkl` created, row count changed. Errors (tracebacks) are also observations — often the best ones.

</details>

5. What's the difference between an experiment and a feature?

<details>
<summary>Sample Answer</summary>

**Answer:** An experiment is temporary, isolated, and reverted — its goal is understanding. A feature is permanent, integrated, and shipped — its goal is user value. Experiments inform features but are not themselves features. Don't commit experiments.

</details>
