# 2.4 TradeStack WebSocket — How Production Streaming Uses the Same Pattern

## Think — A News Ticker vs A Group Chat

Imagine two scenarios:

**Scenario A (chat):** 5 friends in a room. Anyone can speak. Everyone hears everyone. Messages are text. No one is "subscribing" to anything — they're just present.

**Scenario B (trading):** 5 clients watching RELIANCE. The server connects to Upstox (the exchange feed), receives price ticks, and pushes them to those 5 clients. The clients don't speak. They only listen. And a client watching TCS shouldn't receive RELIANCE ticks.

The difference is the **direction of data** and the **subscription model**. Chat is many-to-many (anyone sends, everyone receives). Trading is one-to-many from a single upstream source (Upstox -> server -> subscribers), filtered by symbol.

Same WebSocket plumbing. Different application logic on top.

## Concept — Upstox WebSocket for Live Price Ticks

Upstox (and most brokers) expose a WebSocket endpoint for live market data. Instead of you polling "what's the price now?" every second, you connect once, subscribe to symbols, and the broker **pushes** ticks to you as they happen.

A tick looks roughly like:

```json
{
  "type": "tick",
  "symbol": "RELIANCE",
  "ltp": 2450.50,
  "volume": 12345,
  "timestamp": "2026-11-04T09:15:03+05:30"
}
```

Your server does two jobs:
1. **Upstream:** connect to Upstox WebSocket, receive ticks.
2. **Downstream:** forward relevant ticks to your connected clients (browsers, dashboards).

This is a **proxy/fan-out** pattern: one upstream connection feeds many downstream connections.

## Concept — ConnectionManager in Production

TradeStack's `streaming.py` uses a ConnectionManager that looks familiar. Here's a simplified, readable version of the pattern (not the exact production code):

```python
# streaming.py (simplified for reading)
import json
import asyncio
from fastapi import WebSocket
from collections import defaultdict

class MarketStreamManager:
    def __init__(self):
        # symbol -> set of client WebSockets subscribed to it
        self.subscribers: dict[str, set[WebSocket]] = defaultdict(set)
        # symbol -> latest tick (cache so new subscribers get current price)
        self.latest: dict[str, dict] = {}
        # upstream connection to Upstox (one for the whole server)
        self.upstream_ws = None

    async def subscribe(self, websocket: WebSocket, symbol: str):
        await websocket.accept()
        self.subscribers[symbol].add(websocket)
        # Send cached latest tick immediately so client isn't blank
        if symbol in self.latest:
            await websocket.send_text(json.dumps(self.latest[symbol]))

    def unsubscribe(self, websocket: WebSocket, symbol: str):
        self.subscribers[symbol].discard(websocket)

    async def on_tick(self, tick: dict):
        # Called when Upstox pushes a new tick
        symbol = tick["symbol"]
        self.latest[symbol] = tick
        # Fan out to only subscribers of THIS symbol
        dead = []
        for ws in list(self.subscribers[symbol]):
            try:
                await ws.send_text(json.dumps(tick))
            except Exception:
                dead.append(ws)
        for ws in dead:
            self.subscribers[symbol].discard(ws)

    async def broadcast_all(self, message: str):
        # For system messages (market open/close, errors) -> all clients
        for symbol, subs in self.subscribers.items():
            for ws in list(subs):
                try:
                    await ws.send_text(message)
                except Exception:
                    subs.discard(ws)
```

Mapping to what you know:
- `subscribe()` ≈ `connect()` from 2.2/2.3 — accept handshake, store connection.
- `subscribers: symbol -> set[WebSocket]` ≈ rooms, but keyed by **symbol** instead of room_id.
- `unsubscribe()` ≈ `disconnect()`.
- `on_tick()` ≈ `broadcast(room_id)` — but triggered by upstream data, not by a client message.
- `latest` cache ≈ message history, but it's "current state" not "last N messages".

The shape is identical to RoomManager. Only the trigger changes: in chat, a client message triggers broadcast; in trading, an upstream tick triggers broadcast.

## Concept — Chat vs Trading: The Real Differences

| Aspect | Chat (2.3) | Trading (streaming.py) |
|--------|-----------|------------------------|
| Who sends data | Any client | Upstream broker (Upstox) |
| Who receives | All in room | Subscribers of that symbol |
| Client -> server messages | Yes (chat text) | Rare (subscribe/unsubscribe commands) |
| Data direction | Many-to-many | One-to-many (fan-out) |
| History | Last N messages | Latest tick (current state) |
| Subscription key | room_id | symbol |
| Ordering | Message order matters | Latest wins (stale ticks dropped) |

The biggest conceptual shift: in chat, the server is a **relay** (pass messages between clients). In trading, the server is a **gateway/proxy** (one upstream feed fanned out to many clients). The WebSocket plumbing is the same; the role of the server changes.

## Concept — Reading the Real Pattern (What to Look For)

When you open TradeStack's `streaming.py`, look for these five things and you'll understand it:

1. **A dict keyed by symbol** (or channel) holding connection sets — this is the "rooms" equivalent.
2. **An upstream task** — an `asyncio` task that connects to Upstox and loops on `receive()`. This is the data source.
3. **A fan-out loop** — on each upstream tick, iterate subscribers and `send_text`. This is `broadcast()`.
4. **A cleanup path** — `try/except` around sends, removing dead sockets. Same as 2.2/2.3.
5. **A cache of latest state** — so a late-joining client immediately gets the current price instead of waiting for the next tick.

If you can find these five, you understand the file. Everything else (auth, reconnect logic, heartbeat) is plumbing.

## Concept — Subscribe/Unsubscribe Commands

In trading, clients don't just connect and receive everything. They send commands like:

```json
{ "action": "subscribe", "symbol": "RELIANCE" }
{ "action": "unsubscribe", "symbol": "RELIANCE" }
```

The endpoint parses these and calls `manager.subscribe()` / `manager.unsubscribe()`. This is the chat equivalent of "join room" / "leave room" — but here the client can subscribe to multiple symbols on one connection, and the server filters ticks per symbol.

A minimal endpoint:

```python
@app.websocket("/ws/market")
async def market_endpoint(websocket: WebSocket):
    await websocket.accept()
    subscribed = set()
    try:
        while True:
            raw = await websocket.receive_text()
            cmd = json.loads(raw)
            if cmd["action"] == "subscribe":
                symbol = cmd["symbol"]
                manager.subscribers[symbol].add(websocket)
                subscribed.add(symbol)
                if symbol in manager.latest:
                    await websocket.send_text(json.dumps(manager.latest[symbol]))
            elif cmd["action"] == "unsubscribe":
                symbol = cmd["symbol"]
                manager.subscribers[symbol].discard(websocket)
                subscribed.discard(symbol)
    except WebSocketDisconnect:
        # Clean up ALL subscriptions for this client
        for symbol in subscribed:
            manager.subscribers[symbol].discard(websocket)
```

Notice: one connection can subscribe to many symbols. Cleanup on disconnect must remove it from every symbol's set — hence the `subscribed` set tracking what this client asked for.

## What It Is NOT

- ❌ **Not a broker** — TradeStack doesn't generate prices. It proxies Upstox's feed. The exchange is the source of truth.
- ❌ **Not a chat** — clients don't send market data to each other. Data flows upstream -> server -> clients only.
- ❌ **Not persistent** — ticks are ephemeral. If you need history, store ticks in a time-series DB (or at least cache latest). The WebSocket layer itself remembers nothing.
- ❌ **Not a replacement for REST** — you still need REST endpoints for "give me yesterday's OHLC" or "place an order". WebSocket is only for the live stream.
- ❌ **Not scalable on one machine** — one process holds all subscriptions. For real scale, use Redis pub/sub between server instances so a tick received by instance A reaches clients on instance B.

## Nutshell

**Trading WebSocket = same plumbing as chat, different role. Server is a gateway: one upstream feed (Upstox) fanned out to subscribers keyed by symbol. subscribe/unsubscribe = join/leave room. latest-tick cache = message history. Read streaming.py by finding the 5 things: symbol dict, upstream task, fan-out loop, cleanup, latest cache.**

## Common Mistakes (when reading or writing this)

- ❌ **"Each client connects to Upstox directly"** — no. One upstream connection on the server feeds all clients. Otherwise you'd hit broker connection limits.
- ❌ **"Ticks are stored like chat messages"** — no. Only the latest tick per symbol is cached. Storing every tick in memory would OOM the server.
- ❌ **"A client subscribes once globally"** — no. Subscription is per-symbol. One client can watch 10 symbols.
- ❌ **"Forgetting cleanup on disconnect"** — if you don't remove the socket from every subscribed symbol's set, dead sockets accumulate and `send_text` throws forever.
- ❌ **"Treating it as chat"** — don't let clients broadcast ticks to each other. Data direction is upstream -> server -> clients only.

## In Your Own Words

1. In one sentence, what's the difference between a chat WebSocket and a trading WebSocket?

<details>
<summary>Sample Answer</summary>

**Answer:** Chat is many-to-many relay (any client can send, all in room receive); trading is one-to-many gateway (one upstream feed fanned out to subscribers of a symbol). Same WebSocket plumbing, different data direction and subscription model.

</details>

2. Why does the server keep only ONE upstream connection to Upstox instead of one per client?

<details>
<summary>Sample Answer</summary>

**Answer:** Broker connection limits and efficiency. One upstream connection receives all ticks; the server fans them out to its many clients. Otherwise N clients = N broker connections, which brokers don't allow and which wastes bandwidth.

</details>

3. What's the `latest` cache for, and how is it different from chat's message history?

<details>
<summary>Sample Answer</summary>

**Answer:** `latest[symbol]` holds the most recent tick so a newly subscribed client immediately gets the current price instead of waiting for the next tick. Chat history keeps the last N messages (a list); trading keeps only the single latest value per symbol (current state, not a log).

</details>

4. A client subscribed to RELIANCE and TCS disconnects. What must cleanup do?

<details>
<summary>Sample Answer</summary>

**Answer:** Remove that WebSocket from BOTH `subscribers["RELIANCE"]` and `subscribers["TCS"]`. That's why the endpoint tracks a `subscribed` set per connection — so disconnect can iterate and clean up every symbol.

</details>

5. Name the five things to look for when reading TradeStack's `streaming.py`.

<details>
<summary>Sample Answer</summary>

**Answer:** (1) dict keyed by symbol holding connection sets, (2) an upstream asyncio task connecting to Upstox, (3) a fan-out loop sending ticks to subscribers, (4) cleanup of dead sockets, (5) a cache of latest tick per symbol.

</details>
