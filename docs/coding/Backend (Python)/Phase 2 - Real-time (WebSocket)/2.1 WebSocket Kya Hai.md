In Phase 1, every interaction was request-response: the client asks, the server answers, and then the connection closes. The client has to ask again for new data. That works for loading a page or submitting a form. But what about a chat app? You don't want to refresh the page every second to check for new messages.

That's where **WebSockets** come in. A WebSocket is a persistent connection — the client and server shake hands once, and then either side can send data anytime without asking permission first.

# 2.1 WebSocket Kya Hai — Persistent Connection vs HTTP

## Think — Phone Call vs Letter

Imagine you want to talk to your friend. Two options:

**Option 1: Letters (HTTP).** You write a letter, send it, wait for a reply. Each letter is a separate trip. You can't send another letter until you get a reply. That's request-response.

**Option 2: Phone call (WebSocket).** You dial once, the call connects, and then you both can talk anytime. No need to dial again. Either person can speak first. That's a persistent connection.

HTTP is letters. WebSocket is a phone call.

## Concept — What Is a WebSocket

A **WebSocket** is a communication protocol that provides a full-duplex (two-way), persistent connection between a client and server over a single TCP connection.

The key differences from HTTP:

| Thing | HTTP (request-response) | WebSocket (persistent) |
|-------|----------------------|----------------------|
| Connection | Opens and closes per request | Opens once, stays open |
| Who speaks first | Client always initiates | Either side can send anytime |
| Overhead | Headers sent every request | Headers only during handshake |
| Use case | Loading pages, form submission | Chat, live prices, notifications |

## The Handshake — How WebSocket Starts

WebSocket doesn't replace HTTP. It **starts** with HTTP. The client sends an HTTP request with a special header: `Upgrade: websocket`. The server responds with `101 Switching Protocols`. After that, the connection is no longer HTTP — it's WebSocket.

```
Client: "Hey server, can we upgrade to WebSocket?"
Server: "Sure, switching now."
[Connection is now WebSocket — both sides can send freely]
```

This is why WebSocket works through firewalls and proxies — it starts as regular HTTP.

## Code — First WebSocket in FastAPI

FastAPI has built-in WebSocket support. Here's the simplest example:

```python
from fastapi import FastAPI, WebSocket

app = FastAPI()

# WebSocket endpoint — note: no HTTP method, just @app.websocket
@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    # Accept the connection (completes the handshake)
    await websocket.accept()
    
    # Loop: receive and echo
    while True:
        # Wait for a message from the client
        data = await websocket.receive_text()
        # Send it back
        await websocket.send_text(f"Echo: {data}")
```

Each line:
- `@app.websocket("/ws")` — registers a WebSocket endpoint at `/ws` (no GET/POST method)
- `await websocket.accept()` — completes the handshake, connection is now open
- `await websocket.receive_text()` — waits for the client to send a message (blocks until received)
- `await websocket.send_text(...)` — sends a message to the client
- `while True` — keeps the connection alive, listening for messages

## What WebSocket Is NOT

- ❌ **Not HTTP** — after the handshake, it's a different protocol
- ❌ **Not for everything** — don't use WebSocket for loading pages or simple CRUD. HTTP is simpler and caches better.
- ❌ **Not automatically scalable** — each connection holds server memory. 10,000 connections = 10,000 open sockets.

## Nutshell

**WebSocket = persistent two-way connection. Handshake starts as HTTP, then switches. Either side can send anytime. Use it for real-time (chat, live prices, notifications).**

## Common Mistakes

- ❌ **"WebSocket replaces HTTP"** — no. WebSocket is for real-time. HTTP is for everything else.
- ❌ **"You don't need accept()"** — you must call `await websocket.accept()` or the connection never opens.
- ❌ **"receive_text() returns immediately"** — no, it blocks until a message arrives. That's the point.
