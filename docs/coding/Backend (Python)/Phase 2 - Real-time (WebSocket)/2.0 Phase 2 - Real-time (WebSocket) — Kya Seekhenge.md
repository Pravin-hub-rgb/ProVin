In Phase 1, you built a complete REST API — stocks CRUD, SQLite persistence, Pydantic validation, and a pandas-powered scanner. Everything was request-response: the client asks, the server answers.

Now imagine you're building a chat app. Someone sends a message. How does the other person see it instantly? They can't keep refreshing the page every second. They need a **live connection** — the server pushes data to the client without the client asking.

That's what **WebSockets** do. And that's what Phase 2 is about.

# 2.0 Phase 2 — Real-time (WebSocket) — Kya Seekhenge

## Who Is This Phase For

You've built request-response APIs. You know HTTP, CRUD, SQLite. But real-time is a different world — the server talks first, not the client. This phase starts from that gap and builds up to a working chat app.

## What You'll Build

A **Chat Room App** — like WhatsApp, but simple. Multiple browser tabs connect to one room. When someone sends a message, everyone in that room sees it instantly. No refresh needed.

This is the same concept as TradeStack's live trader (Upstox live prices) — the server pushes price updates to the client in real-time.

## What This Phase Is NOT

- ❌ **Production chat app** — no auth, no persistence, no scaling
- ❌ **WebSocket deep dive** — just the basics needed for real-time
- ❌ **TradeStack code changes** — we only read and understand, don't modify production code

## Prerequisites

- Phase 1 complete (1.0 → 1.5.5)
- FastAPI basics understood (routes, Pydantic, SQLite)
- Python basics (variables, functions, loops, dicts)

## What Happened So Far

In Phase 1, you built a request-response API. Every interaction was: client asks → server answers. The client always initiates.

In Phase 2, the server initiates too. The client opens a connection once, and the server pushes data whenever it wants. This is the foundation of every real-time feature — chat, live prices, notifications, collaborative editing.
