## Kaunse Endpoints Chahiye?

Ye tumhara **API surface** hai — browser ke `/docs` me jo dikhega. Hoshiyari se socho, kyunki yahi tumhara **interview pitch** banega.

| # | Endpoint | Method | Kya karta hai | Kaunsa tool |
|---|----------|--------|---------------|-------------|
| 1 | `/health` | GET | Server zinda hai? `{status: ok}` | 1.0 ka pehla app |
| 2 | `/api/stocks` | GET | Stocks ki list (filter + limit) | 1.1 (query) + 1.3 (Read) + 1.4 (SQLite) |
| 3 | `/api/stocks` | POST | Naya stock add | 1.2 (body) + 1.3 (Create) + 1.4 (SQLite) |
| 4 | `/api/settings/{key}` | GET | Ek setting ka value | 1.1 (path) + 1.3 (Read) |
| 5 | `/api/settings/{key}` | PUT | Setting update | 1.3 (Update) + 1.4 (SQLite) |
| 6 | `/api/indicators/{symbol}` | GET | Ek stock ka SMA + RSI | pandas (naya) + 1.1 (path) |
| 7 | `/api/scan` | GET | RSI < 30 (oversold) stocks list | Sab combine + Pydantic response |

**Bas 7 endpoints.** Real TradeStack me 48 hain — par wo 6 mahine me bane, har ek ka apna kaam. Yahan **core shape** dikhana hai.

**Note kuch endpoints ke baare me:**
- `/health` — koi bhi service me hota hai. DukaanOS/TradeStack dono me hai. Interviewer poochhe *"health check kyu?"* — jawab: *"load balancer ko pata chalna chahiye service zinda hai ya nahi, bina manual check kiye."*
- `/api/settings/{key}` — **path param** ka clean use. TradeStack me bilkul yahi hai (`@app.get("/api/settings/{key}")`). Key se value — jaise `?rsi_period=14` type.
- `/api/scan` — ye tumhara **"wow" endpoint"** hai. TradeStack ka `scanner` ka simple version.

## Data Ka Shape Kya Hai?

Ye **sabse important** step hai. Socho — database me kya-kya tables honge, har table me kaunse columns.

### Table 1: `stocks`

Ye tumhari **main list** hai — kis kis stock ko track kar rahe ho.

| Column | Type | Kyun hai |
|--------|------|---------|
| `id` | INTEGER PRIMARY KEY | Har stock ka unique number (auto) |
| `symbol` | TEXT NOT NULL UNIQUE | NSE code (RELIANCE, TCS). Unique kyunki ek hi symbol dobara nahi aana chahiye |
| `name` | TEXT NOT NULL | Company ka naam — UI me dikhega |
| `sector` | TEXT | Filter ke liye (IT, Oil, Banking) |
| `last_price` | REAL | Aakhri price — calculation ke liye |
| `active` | INTEGER DEFAULT 1 | 1 = track ho raha hai, 0 = hataya. Soft delete |

**Har field ka reason:**
- `id` — update/delete ke liye chahiye (URL se kaunsa stock)
- `symbol` UNIQUE — ek hi symbol dobara na aaye (409 Conflict — 1.4 me test kiya tha)
- `name` — UI dikhata hai
- `sector` — `?sector=IT` filter ke liye
- `last_price` — calculations ke liye (next step me use hoga)
- `active` — soft delete. `del` karne ke bajaye `active=0` karo, taaki purana data bache (history). Real TradeStack me bhi ye hota hai.

### Table 2: `settings`

Ye tumhari **configuration** hai — scanner ki settings. TradeStack me bhi bilkul yahi (`settings` table).

| Column | Type | Kyun hai |
|--------|------|---------|
| `key` | TEXT PRIMARY KEY | Setting ka naam (jaise `rsi_period`) |
| `value` | TEXT NOT NULL | Setting ki value (jaise `14`) |

**Ye key-value table kyun?** Kyunki naye settings bina schema change ke add ho jaate hain. Ek `rsi_period`, ek `sma_period`, ek `oversold_threshold` — sab ek hi table me. Naya setting chahiye to **bas row add karo**, schema touch karne ki zaroorat nahi. Ye real pattern hai (TradeStack `settings.py` bilkul ye karta hai).

### Table 3: `prices` (optional, par recommended)

Ye thoda sochna hai. Indicators (SMA, RSI) **time series** chahiye — matlab ek stock ke **kai dinon ke prices**. Sirf `stocks.last_price` se indicator nahi banega (wo to ek hi din ka price hai).

| Column | Type | Kyun hai |
|--------|------|---------|
| `id` | INTEGER PRIMARY KEY | Auto |
| `symbol` | TEXT NOT NULL | Kis stock ka price |
| `date` | TEXT NOT NULL | Kab ka price (YYYY-MM-DD) |
| `open` | REAL | Din ka opening price |
| `high` | REAL | Din ka high |
| `low` | REAL | Din ka low |
| `close` | REAL | Din ka closing price — **ye indicator me chalta hai** |

**Isliye ek `prices` table chahiye** jisme har stock ke **kai dinon ka** data ho. Ek stock ka 60 din ka data = 60 rows.

**Realistic soch:** TradeStack me 2000 stocks × 60+ din ka data hota hai, aur wo **pickle cache** me hota hai (CSV nahi). Par chhote project me **SQLite table** kaafi hai — concept wahi hai: *"ek stock ke time-series prices store karo, indicator unpe compute karo."*

## Data Flow Kaise Hoga?

Ab socho — data kahaan se aayega, kahan jayega. Yahi 1.5 me banayenge, par **sochna abhi**.

```
Browser /docs ya koi client
       ↓ (HTTP request)
FastAPI endpoint (1.1-1.3 kaam)
       ↓ (SQL query, ? placeholder se)
SQLite database (stocks, settings, prices tables)
       ↓ (rows)
Pydantic response model (1.2 validation)
       ↓ (JSON)
Browser me JSON dikhta hai
```

**Data ke 3 raaste hain project me:**
1. **Input (Create/Update)** — browser JSON body bhejta hai → Pydantic validate → SQL `INSERT`/`UPDATE` → SQLite me save
2. **Output (Read)** — SQL `SELECT` → rows → dict → Pydantic response model → JSON → browser
3. **Compute (Scan)** — `prices` table se data padho → pandas me SMA/RSI compute → filter → return

**Ek important decision:** prices ka data kahaan se aayega? 3 options:
- (a) Manually CSV se import karo (recommended — simple, real feel)
- (b) `POST /api/prices` se bhejo (extra endpoint, extra kaam)
- (c) Random generate karo (placeholder, real nahi lagta)

**Recommend (a)** — ek chhoti CSV file banayi jisme 3-5 stocks ke 60 din ke prices hain (hum khud se realistic numbers daal denge). Phir ek function usse SQLite me daalta hai. Ye real TradeStack ke "bhavcopy ingest" ka simple version hai.
