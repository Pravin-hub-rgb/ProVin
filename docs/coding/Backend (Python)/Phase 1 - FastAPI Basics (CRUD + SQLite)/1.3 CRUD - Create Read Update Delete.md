In 1.2 you learned how to send data (body) and how validation works (Pydantic). Now let's open an important topic that's often skipped from the start.

Back to DukaanOS. Item got added (Create). Now show the item's data (Read). But the shop owner also wants to **update the price** (Update), and **remove an old item** that sold out (Delete). All four together make **CRUD**.

Each has its own **HTTP method** — GET, POST, PUT, DELETE. These aren't just names, they're **semantics**. Putting the right method in the wrong place = bad design.

---

## Think (Something to Think About)

DukaanOS counter. Manager has **4 tasks** every day:

1. **Add new item** — "Parle-G, 10 rupees, 50 stock." This is **Create**.
2. **View item data** — "What's RELIANCE's price?" This is **Read**.
3. **Update item** — "Change Parle-G's price from 10 to 12, stock from 50 to 30." This is **Update**.
4. **Remove item** — "This item is discontinued, delete it." This is **Delete**.

**C**reate, **R**ead, **U**pdate, **D**elete — **CRUD**. Every data-driven app (DukaanOS, TradeStack, Instagram, anything) runs on these four. Instagram: new post = Create. Viewing feed = Read. Editing post = Update. Deleting post = Delete. That's it.

---

## Manual Method (painful way)

If FastAPI didn't exist, you'd make 4 separate endpoints — each its own way. Here's the pain of each method:

```python
# Manual (avoid these)

@app.post("/items")          # Create
def create(data): ...

@app.get("/items/{id}")      # Read
def read(id): ...

@app.post("/items/update")   # Update  <- POST?? because PUT wasn't known
def update(id, data): ...

@app.post("/items/delete")   # Delete  <- POST??
def delete(id): ...
```

**Problem 1:** Update and Delete used `POST /items/update` and `POST /items/delete` — because the framework didn't accept methods or you didn't know them. Result: **everything became POST** — semantics lost. Looking at the URL in browser, you can't tell what will happen.

**Problem 2:** Everything built the same way, **no validation** — wrong ID also returns 200, wrong data also returns 200. No proper **status codes** (200/201/204/404).

**Problem 3:** No **consistency** — sometimes update at `/items/update`, sometimes `/items/5`. No rule.

FastAPI + REST conventions give you all this **standard** — each method has its own standard URL, its own status code, its own validation. You just write the logic.

## Concept: What Each Method Does

This table is also asked in interviews. Remember it:

| Method | Job | Body data? | Safe? | Real DukaanOS example |
|--------|-----|------------|-------|----------------------|
| **GET** | **R**ead — get data | No (path/query) | Yes (reads only) | Check item price |
| **POST** | **C**reate — make new | Yes (whole item) | No (changes data) | Add new item |
| **PUT** | **U**pdate — replace all | Yes (whole item) | No | Price 12, stock 30 |
| **PATCH** | Partial update | Yes (only changed fields) | No | Just change price |
| **DELETE** | **D**elete — remove | No usually | No | Delete item |

**What does safe mean?** GET only reads, doesn't change data — so you can bookmark it in browser and open repeatedly. POST/PUT/PATCH/DELETE change data — so clicking them again can cause problems.

This isn't just theory — this **CRUD mapping** is asked directly in interviews: *"user updated profile, which method?"* → **PUT/PATCH**. *"user viewed profile?"* → **GET**. Simple map to remember.

---

## Concept: Status Codes — Each Operation Has Its Own

This isn't obvious at first, but asked a lot in interviews. Each operation has its own **status code** that says *"what happened"*:

| Code | Meaning | When sent |
|------|---------|-----------|
| **200** | OK — everything fine | GET, PUT, DELETE successful |
| **201** | Created — new thing made | POST creates new item |
| **204** | No Content — fine, but no data | DELETE successful (empty body) |
| **400** | Bad Request — wrong format | Missing required field |
| **404** | Not Found — nothing found | ID doesn't exist |
| **422** | Unprocessable — validation fail | Wrong type, Pydantic rejected |

**Think DukaanOS:**
- New item created → **201** (and location too — `/api/items/1`)
- Get item data → **200**
- Item updated → **200**
- Item deleted → **204**
- **404** — asked for ID 999 which doesn't exist
- **422** — sent price `"abc"` (Pydantic caught it)

In 1.1 and 1.2 you got **422 automatically** from FastAPI. Now the rest you'll state yourself — `HTTPException(404, "Item not found")`.

---

## Concept: PUT vs PATCH (most confusing one)

Both look like "update" but they're **different**:

**PUT = replace everything.** Make new item, send all fields. Fields not sent → **deleted**.

**PATCH = change only some things.** Fields you send get changed. Fields not sent → **left alone**.

```python
# PUT — replacing everything
@app.put("/api/items/{item_id}")
def update_item(item_id: int, data: ItemUpdate):   # ItemUpdate: name, price, category, stock — all
    item = items[item_id]
    item.name = data.name          # all overwritten
    item.price = data.price
    item.category = data.category
    item.stock = data.stock
    return item

# PATCH — only changing price
@app.patch("/api/items/{item_id}")
def patch_item(item_id: int, data: ItemPatch):     # ItemPatch: only price (rest optional)
    item = items[item_id]
    if data.price is not None:      # whatever was sent, change it
        item.price = data.price
    return item
```

**Real example:** DukaanOS employee wants to update **only price**, keeping name/category same — **PATCH** is right. If they want to **replace whole item** with new specification — **PUT**.

In practice nobody is 100% strict — many apps just use PUT. But in interview if you can tell the difference, it's a **plus point**.

## Code: Complete CRUD (Step by Step)

A small, realistic **stocks API** (like DukaanOS scanner). Each method separate, each code correct:

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Trading Backend Basic")


# --- Models ---

class StockCreate(BaseModel):
    symbol: str
    name: str
    sector: str | None = None
    last_price: float

class StockUpdate(BaseModel):
    name: str | None = None
    sector: str | None = None
    last_price: float | None = None

class Stock(StockCreate):
    id: int
    active: bool = True


# In-memory (SQLite in 1.4)
stocks: dict[int, Stock] = {}
next_id = 1


# --- CREATE (201) ---

@app.post("/api/stocks", response_model=Stock, status_code=201)
def create_stock(data: StockCreate):
    global next_id
    stock = Stock(id=next_id, **data.model_dump())
    stocks[next_id] = stock
    next_id += 1
    return stock


# --- READ single (200) ---

@app.get("/api/stocks/{stock_id}", response_model=Stock)
def get_stock(stock_id: int):
    if stock_id not in stocks:
        raise HTTPException(status_code=404, detail="Stock not found")
    return stocks[stock_id]


# --- READ list (200) ---

@app.get("/api/stocks", response_model=list[Stock])
def list_stocks(limit: int = 20, sector: str | None = None, active_only: bool = False):
    result = list(stocks.values())
    if sector:
        result = [s for s in result if (s.sector or "").lower() == sector.lower()]
    if active_only:
        result = [s for s in result if s.active]
    return result[:limit]


# --- UPDATE (200) ---

@app.put("/api/stocks/{stock_id}", response_model=Stock)
def update_stock(stock_id: int, data: StockUpdate):
    if stock_id not in stocks:
        raise HTTPException(status_code=404, detail="Stock not found")
    stock = stocks[stock_id]
    if data.name is not None:
        stock.name = data.name
    if data.sector is not None:
        stock.sector = data.sector
    if data.last_price is not None:
        stock.last_price = data.last_price
    return stock


# --- DELETE (204, empty body) ---

@app.delete("/api/stocks/{stock_id}", status_code=204)
def delete_stock(stock_id: int):
    if stock_id not in stocks:
        raise HTTPException(status_code=404, detail="Stock not found")
    del stocks[stock_id]
    # 204 = No Content, no body sent
```

**Two new things not in 1.2:**

1. **`HTTPException(404, ...)`** — now we need to **send proper status codes ourselves**. In 1.2 FastAPI gave 422 automatically for validation, but "item doesn't exist" — that's application logic, FastAPI doesn't know. **We** state it.

2. **`status_code=201` and `status_code=204`** — specified in decorator what this endpoint's default code is. GET's default is 200, POST's default is also 200 — but semantically POST should be **201**. Now made **explicit**.

## Test: How to Verify (From Browser)

Run server, open `/docs`. **Run in this order** (data dependencies exist):

1. **CREATE (201):** `POST /api/stocks` with body:
   ```json
   { "symbol": "RELIANCE", "name": "Reliance", "sector": "Oil", "last_price": 1420 }
   ```
   Expect **201 Created** in response (watch response code), new item with `id`.

2. **READ (200):** `GET /api/stocks/1` — item came back, **200**.
3. **READ list (200):** `GET /api/stocks?sector=Oil&limit=5` — filtered list.
4. **UPDATE (200):** `PUT /api/stocks/1` with `{"last_price": 1450}` (only price). Then `GET /api/stocks/1` again — price 1450, name same.
5. **DELETE (204):** `DELETE /api/stocks/1` — response **204 No Content** (empty body).
6. **404 test (important):** `GET /api/stocks/1` again — now **404 "Stock not found"** because we deleted it. **This is proper error handling** — before `{"error": "not found"}` came with 200 (wrong). Now proper code + proper message.

Watch response codes carefully at each step (200/201/204/404) — that's what you learn here. Difference between 201 vs 200 isn't just a number, it's **semantic**.

## Nutshell

- **CRUD** = Create (POST), Read (GET), Update (PUT/PATCH), Delete (DELETE). Every data-driven app's base.
- Each method has its **own standard URL** — `/api/stocks` (create), `/api/stocks/{id}` (read/update/delete).
- **Status codes** each operation's own — 201 (create), 200 (read/update), 204 (delete, no body), 404 (not found), 422 (validation).
- **`HTTPException(404, "msg")`** — send proper error yourself, not `{"error": "..."}` with 200.
- **PUT** replaces everything, **PATCH** only changed fields.

---

## Common Mistakes

1. **Doing Update/Delete with `POST`.** `POST /api/stocks/update` is wrong — `PUT /api/stocks/{id}` and `DELETE /api/stocks/{id}` are right. Each method has its own standard, follow it.

2. **Not setting POST status code to 201.** Default stays 200. But semantically creating new resource = **201 Created**. Interviewers notice this.

3. **Sending body with DELETE.** 204 No Content = no body. After deleting data, don't return anything. If you need to send something use **200**, not 204.

4. **Not sending 404.** `return {"error": "not found"}` — this goes with **200 status**! FastAPI doesn't automatically fix this. Use **HTTPException(404)**, only then the correct code goes. Client handles error **differently** on 404 vs 200.

5. **Forgetting PUT vs PATCH difference.** PUT deletes what wasn't sent (real PUT), PATCH leaves it alone. Asked in interviews.

6. **Sending ID in body during update.** ID is in URL (`/api/stocks/{id}`), not body. Sending it in body is confusing — comes from two places.

7. **Returning HTTPException instead of raising.** In FastAPI `raise HTTPException(...)`, don't `return`. `return` sends a dict with 200 status.

## In Your Own Words

<details>
<summary>1. What does each of CRUD's four methods do? One line each.</summary>

**C**reate (POST) — create new data (adding new item). **R**ead (GET) — fetch existing data (viewing item price). **U**pdate (PUT/PATCH) — change existing data (changing price). **D**elete (DELETE) — remove data (removing item). These four together form every data-driven app's base — Instagram, DukaanOS, TradeStack, all of them.

</details>

<details>
<summary>2. What's the difference between 201 and 200 status codes? Which should POST return?</summary>

**200 OK** = request successful, data came back. **201 Created** = new resource **successfully created**. POST means creating new thing, so semantically the right code is **201 Created**, not 200. FastAPI keeps POST default as 200, so you explicitly write `status_code=201` in decorator.

</details>

<details>
<summary>3. How do you send 404? Why doesn't `return {"error": "not found"}` work?</summary>

Use `raise HTTPException(status_code=404, detail="Stock not found")`. The `return {"error": ...}` problem is that it's a **normal return** — FastAPI treats it as success and sends **200 OK** status. Status code stays 200, only error text goes in body. `raise HTTPException` tells FastAPI "this is an error, send 404" — then the correct code goes. Client handles error **differently** on 404 vs 200.

</details>

<details>
<summary>4. What's the difference between PUT and PATCH? Give real example.</summary>

**PUT = replace everything.** What wasn't sent gets deleted. **PATCH = change only sent fields.** What wasn't sent is left alone. Real example — DukaanOS employee says "just change price to 12, keep everything else same." That's **PATCH** because other fields (name, category) shouldn't change. But if employee says "replace this whole item with new price, new name, new category" — that's **PUT** because whole item is new.

</details>

<details>
<summary>5. Why send 204 on DELETE? Why not 200?</summary>

**204 No Content** means "request successful, but no response body." DELETE removed data, nothing to send back — so body is empty and 204 is the right code. Use 200 when you want to send something **after** delete (like "item deleted, 3 items remaining" message). Simple: DELETE's default is 204 because delete's nature is "remove, return nothing."

</details>

<details>
<summary>6. Why `if data.name is not None` in update endpoint? What happens without it?</summary>

This is PATCH-style update — "change only what was sent." `if data.name is not None` means "if user sent name (not `None`), only then change name." Without this check, if user only sends `last_price` (not name), `data.name` defaults to `None` and gets **directly set** `item.name = None` — name wiped out! This guard prevents that. This pattern is used in every "partial update".

</details>

## What It Is NOT

- ❌ **Not a database** — `stocks` dict is in memory, disappears on restart. SQLite (1.4) fixes this.
- ❌ **No auth** — anyone can update/delete anything. Real would verify token.
- ❌ **No bulk operations** — one item at a time update. Real would have "update 50 stocks at once" endpoint.
- ❌ **Not soft delete** — `del stocks[id]` permanently removes. Real systems mark `active: false` (for history), like `Stock` model's `active` field.
- ❌ **No pagination** — `limit` exists but no `offset`/`page`. Real needs pagination for 2000-stock lists.
