1.2 me tumne seekha — data bhejte kaise hain (body) aur validate kaise hota hai (Pydantic). Ab ek zaroori baat kholte hain jo shuru se skip hoti hai.

DukaanOS wapas. Item add ho gaya (Create). Ab us item ka data dikha (Read). Par shop waale ko ab **price update** bhi karna hai (Update), aur **purana item hatana** bhi hai jo ab bik gaya (Delete). Ye chaaron milke **CRUD** banate hain.

Ab har cheez ka apna **HTTP method** hai — GET, POST, PUT, DELETE. Ye sirf naming nahi hai, ye **semantics** hai. Sahi method galat jagah lagana = galat design.

## Sochо (Sochne Wala Scene)

DukaanOS ka counter. Manager ke paas **4 tasks** hain roz:

1. **Naya item add karo** — "Parle-G, 10 rupaye, 50 stock." Ye **Create** hai.
2. **Item ka data dekho** — "RELIANCE ka price kitna hai?" Ye **Read** hai.
3. **Item update karo** — "Parle-G ki price 10 se 12 kar do, stock 50 se 30." Ye **Update** hai.
4. **Item hatao** — "Ye item band ho gaya, delete kar do." Ye **Delete** hai.

**C**reate, **R**ead, **U**pdate, **D**elete — **CRUD**. Har data-driven app (DukaanOS, TradeStack, Instagram, kuch bhi) in chaaron pe chalti hai. Instagram pe naya post = Create. Feed dekhna = Read. Post edit = Update. Post delete = Delete. Bas.

## Manual Tareeka (dard wala)

Agar FastAPI na hota, to 4 alag endpoint banane padte — har ek apne tareeke se. Ye dikhata hai har method ka dard:

```python
# Manual (inse bache)

@app.post("/items")          # Create
def create(data): ...

@app.get("/items/{id}")      # Read
def read(id): ...

@app.post("/items/update")   # Update  <- POST?? kyunki PUT nahi pata tha
def update(id, data): ...

@app.post("/items/delete")   # Delete  <- POST?? 
def delete(id): ...
```

**Problem 1:** Update aur Delete ke liye `POST /items/update` aur `POST /items/delete` likhna pada — kyunki ye framework method nahi maanta tha ya aapko nahi pata tha. Iska matlab **har ek cheez POST ho gayi** — semantics khatam. Browser me URL dekhke pata hi nahi chalta ki kya hoga.

**Problem 2:** Sab kuch same tarike se bana, koi **validation nahi** — galat ID pe bhi 200 return ho jaata, galat data pe bhi 200. Proper **status codes** nahi (200/201/204/404).

**Problem 3:** Koi **consistency** nahi — kabhi update `/items/update` pe, kabhi `/items/5`. Koi rule nahi.

FastAPI + REST conventions ye **saara standard** de dete hain — har method ka apna standard URL, apna status code, apni validation. Tumhe sirf logic likhna hai.

## Concept: Har Method Ka Kaam

Ye table interview me bhi poochha jaata hai. Yaad karo:

| Method | Kaam | Body me data? | Safe? | Real DukaanOS example |
|--------|------|--------------|-------|----------------------|
| **GET** | **R**ead — data lao | Nahi (path/query) | Haan (sirf padta) | Item ka price dekha |
| **POST** | **C**reate — naya banao | Haan ( pura item) | Nahi (badalta hai) | Naya item add kiya |
| **PUT** | **U**pdate — pura badlo | Haan (pura item) | Nahi | Price 12, stock 30 kiya |
| **PATCH** | Partial update | Haan (sirf badle fields) | Nahi | Sirf price badli |
| **DELETE** | **D**elete — hatao | Nahi usually | Nahi | Item delete kiya |

**Safe matlab kya?** GET sirf padhta hai, koi data change nahi karta — isliye browser me bookmark karke baar baar khol sakte ho. POST/PUT/PATCH/DELETE data badalta hai — isliye inhe dobara click karne se problem hoti hai.

Ye sirf theory nahi hai — **CRUD mapping** interview me seedha poochha jaata hai: *"user ne profile update kiya, kaunsa method?"* → **PUT/PATCH**. *"user ne profile dekha?"* → **GET**. Simple map yaad rakh.

## Concept: Status Codes — Har Operation Ka Apna

Ye shuru me nahi dikhta, par interview me bahut poochha jaata hai. Har operation ka apna **status code** hota hai jo batata hai *"kya hua"*:

| Code | Matlab | Kab bhejte hain |
|------|--------|-----------------|
| **200** | OK — sab theek | GET, PUT, DELETE successful |
| **201** | Created — naya ban gaya | POST se naya item bana |
| **204** | No Content — theek, par data nahi | DELETE successful (body khaali) |
| **400** | Bad Request — galat format | Missing required field |
| **404** | Not Found — kuch nahi mila | ID exist nahi karta |
| **422** | Unprocessable — validation fail | Type galat, Pydantic reject |

**DukaanOS me soch:**
- Naya item bana → **201** (aur location bhi batao — `/api/items/1`)
- Item ka data lao → **200**
- Item update kiya → **200**
- Item delete kiya → **204**
- **404** — ID 999 maanga jo exist nahi karta
- **422** — price `"abc"` bheja (Pydantic ne pakda)

1.1 aur 1.2 me tumne 422 **automatically** FastAPI se mila tha. Ab baaki codes **khud** bologein — `HTTPException(404, "Item not found")`.

## Concept: PUT vs PATCH (sabse confusing wala)

Ye dono "update" lagte hain, par **alag** hain:

**PUT = poora badlo.** Naya item bana, sab fields bhej de. Purane fields jo nahi bheje gaye → **delete** ho jate hain.

**PATCH = sirf badalna hai kuch.** Jo fields bheje, wo change karo. Jo nahi bheje, wo **chhod do**.

```python
# PUT — poori jagah badal raha hai
@app.put("/api/items/{item_id}")
def update_item(item_id: int, data: ItemUpdate):   # ItemUpdate: name, price, category, stock — sab
    item = items[item_id]
    item.name = data.name          # sab overwrite
    item.price = data.price
    item.category = data.category
    item.stock = data.stock
    return item

# PATCH — sirf price badal raha hai
@app.patch("/api/items/{item_id}")
def patch_item(item_id: int, data: ItemPatch):     # ItemPatch: sirf price (baaki optional)
    item = items[item_id]
    if data.price is not None:      # jo bheja, wo badlo
        item.price = data.price
    return item
```

**Real example:** DukaanOS me agar employee **sirf price** update karna chahta hai aur name/category same rakhna hai — to **PATCH** sahi hai. Agar wo **poora item** naya specification ke saath replace karna chahta hai — to **PUT**.

Real mein koi nahi 100% strict hai — bahut se apps sirf PUT use karti hain. Par interview me ye farak bata sakte ho to **plus point** hai.

## Code: Complete CRUD (Step by Step)

Ek chhota, realistic **stocks API** (DukaanOS ke scanner jaisa). Har method alag, har code sahi:

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Trading Backend Basic")


# --- Models ---

class StockCreate(BaseModel):
    symbol: str
    name: str
    sector: str | None = None
    last_price: float

class StockUpdate(BaseModel):
    name: str | None = None
    sector: str | None = None
    last_price: float | None = None

class Stock(StockCreate):
    id: int
    active: bool = True


# In-memory (1.4 me SQLite)
stocks: dict[int, Stock] = {}
next_id = 1


# --- CREATE (201) ---

@app.post("/api/stocks", response_model=Stock, status_code=201)
def create_stock(data: StockCreate):
    global next_id
    stock = Stock(id=next_id, **data.model_dump())
    stocks[next_id] = stock
    next_id += 1
    return stock


# --- READ single (200) ---

@app.get("/api/stocks/{stock_id}", response_model=Stock)
def get_stock(stock_id: int):
    if stock_id not in stocks:
        raise HTTPException(status_code=404, detail="Stock not found")
    return stocks[stock_id]


# --- READ list (200) ---

@app.get("/api/stocks", response_model=list[Stock])
def list_stocks(limit: int = 20, sector: str | None = None, active_only: bool = False):
    result = list(stocks.values())
    if sector:
        result = [s for s in result if (s.sector or "").lower() == sector.lower()]
    if active_only:
        result = [s for s in result if s.active]
    return result[:limit]


# --- UPDATE (200) ---

@app.put("/api/stocks/{stock_id}", response_model=Stock)
def update_stock(stock_id: int, data: StockUpdate):
    if stock_id not in stocks:
        raise HTTPException(status_code=404, detail="Stock not found")
    stock = stocks[stock_id]
    if data.name is not None:
        stock.name = data.name
    if data.sector is not None:
        stock.sector = data.sector
    if data.last_price is not None:
        stock.last_price = data.last_price
    return stock


# --- DELETE (204, body khaali) ---

@app.delete("/api/stocks/{stock_id}", status_code=204)
def delete_stock(stock_id: int):
    if stock_id not in stocks:
        raise HTTPException(status_code=404, detail="Stock not found")
    del stocks[stock_id]
    # 204 = No Content, koi body nahi bhejte
```

**Do naye cheezein jo 1.2 me nahi thi:**

1. **`HTTPException(404, ...)`** — ab hume **khud proper status codes** bhejne hain. 1.2 me FastAPI khud 422 de deta tha validation pe, par "item exist nahi karta" — ye application logic hai, FastAPI ko nahi pata. Ye **hum** bolte hain.

2. **`status_code=201`** aur **`status_code=204`** — decorator me specify kiya ki is endpoint ka default code kya hai. GET ka default 200 hai, POST ka bhi 200 hota hai by default — par semantically POST = 201 hona chahiye. Ye ab **explicit** kar diya.

## Test: Kaise Verify Karein (Browser Se)

Server chalao, `/docs` kholo. **Sequence ye order me chalao** (data dependencies hain):

1. **CREATE (201):** `POST /api/stocks` with body:
   ```json
   { "symbol": "RELIANCE", "name": "Reliance", "sector": "Oil", "last_price": 1420 }
   ```
   Response me **201 Created** dikhna chahiye (response code pe dhyan dena), aur naya item with `id`.

2. **READ (200):** `GET /api/stocks/1` — item wapas mila, **200**.
3. **READ list (200):** `GET /api/stocks?sector=Oil&limit=5` — filtered list.
4. **UPDATE (200):** `PUT /api/stocks/1` with `{"last_price": 1450}` (sirf price). `GET /api/stocks/1` phir se karo — price 1450, name same.
5. **DELETE (204):** `DELETE /api/stocks/1` — response **204 No Content** (body khaali).
6. **404 test (important):** `GET /api/stocks/1` phir — ab **404 "Stock not found"** aayega, kyunki humne delete kar diya. **Ye proper error handling hai** — pehle `{"error": "not found"}` 200 pe aata tha (galat). Ab sahi code + sahi message.

Har step pe response code (200/201/204/404) **dhyan se dekhna** — yahi seekhne ka maal hai. 201 vs 200 ka difference sirf number nahi, **semantic** hai.

## Nutshell

- **CRUD** = Create (POST), Read (GET), Update (PUT/PATCH), Delete (DELETE). Har data-driven app ka base yahi hai.
- Har method ka **apna standard URL** — `/api/stocks` (create), `/api/stocks/{id}` (read/update/delete).
- **Status codes** har operation ka apna — 201 (create), 200 (read/update), 204 (delete, no body), 404 (not found), 422 (validation).
- **`HTTPException(404, "msg")`** — khud proper error bhejo, `{"error": "..."}` 200 pe nahi.
- **PUT** poora badalta hai, **PATCH** sirf badle fields.

## Common Mistakes

1. **Update/Delete ko `POST` se karna.** `POST /api/stocks/update` galat — `PUT /api/stocks/{id}` aur `DELETE /api/stocks/{id}` sahi. Har method ka apna standard hai, usse follow karo.

2. **POST ka status code 201 na rakhna.** Default 200 hi rehta hai. Par semantically naya resource bana = **201 Created**. Interviewer notice karta hai.

3. **DELETE me body bhejna.** 204 No Content = koi body nahi. Data delete karne ke baad kuch return mat karo. Agar kuch bhejna hai to **200** use karo, 204 nahi.

4. **404 na dena.** `return {"error": "not found"}` — ye **200 status** ke saath jayega! FastAPI ko ye automatically theek nahi karta. **HTTPException(404)** use karo, tabhi sahi code jayega.

5. **PUT aur PATCH ka fark bhoolna.** PUT me jo nahi bheja wo delete hota hai (real PUT), PATCH me chhoda jaata hai. Interview me ye poochha jaata hai.

6. **Update me ID body me bhejna.** ID URL me hai (`/api/stocks/{id}`), body me nahi. Body me dena confusing hai — do jagah se aayega.

7. **Loop me HTTPException raise karna.** FastAPI me `raise HTTPException(...)` karo, `return` mat karo. `return` karne se wo dict ban ke 200 pe chala jayega.

## In Your Own Words

<details>
<summary>1. CRUD ke chaaron methods ka kaunsa kaam hai? Ek-ek line me.</summary>

**C**reate (POST) — naya data banano (naya item add karna). **R**ead (GET) — existing data laana (item ki price dekhna). **U**pdate (PUT/PATCH) — existing data badalna (price change karna). **D**elete (DELETE) — data hataana (item hatana). Ye chaaron milke har data-driven app ka base banate hain — Instagram, DukaanOS, TradeStack, sab.

</details>

<details>
<summary>2. 201 aur 200 status code me kya farak hai? POST me kaunsa aana chahiye?</summary>

**200 OK** = request successful, data wapas aaya. **201 Created** = naya resource successfully **create** ho gaya. POST ka matlab hi naya cheez banana hai, isliye semantically sahi code **201 Created** hai, 200 nahi. FastAPI POST ka default code 200 rakhta hai, isliye decorator me `status_code=201` explicitly likhna padta hai.

</details>

<details>
<summary>3. 404 kaise bhejte ho? Kyun `return {"error": "not found"}` kaam nahi karta?</summary>

`raise HTTPException(status_code=404, detail="Stock not found")` use karo. `return {"error": ...}` wala issue ye hai ki wo ek **normal return** hai — FastAPI use samajhta hai aur **200 OK** status ke saath bhej deta hai. Status code 200 rehta hai, sirf body me error text jaata hai. `raise HTTPException` FastAPI ko bol deta hai "ye error hai, 404 bhej" — tab sahi status code jaata hai. Client ko error **differently** handle karna hota hai 404 pe vs 200 pe.

</details>

<details>
<summary>4. PUT aur PATCH me kya farak hai? Real example do.</summary>

**PUT = poora badlo.** Jo nahi bheja, wo delete ho jata hai. **PATCH = sirf badle fields badlo.** Jo nahi bheja, wo chhoda jaata hai. Real example — DukaanOS me employee ne bola "sirf price 12 kar do, baaki same rakho." Ye **PATCH** hai kyunki baaki fields (name, category) change nahi hone chahiye. Par agar employee ne bola "ye item naye price, naye name, naye category ke saath pura replace kar do" — ye **PUT** hai kyunki poora item naya ho raha hai.

</details>

<details>
<summary>5. DELETE pe 204 kyun bhejte hain? 200 nahi kyun?</summary>

**204 No Content** ka matlab hai "request successful, lekin koi response body nahi hai." DELETE me data hat gaya, kuch wapas bhejne ko nahi hai — isliye body khaali hoti hai aur 204 sahi code hai. 200 tab use karte ho jab delete ke baad kuch **wapas bhejna ho** (jaise "item deleted, 3 items bache" message). Simple: DELETE ka default 204 hai kyunki delete ka nature hi "hata dena, wapas kuch nahi" hai.

</details>

<details>
<summary>6. Update endpoint me `if data.name is not None` kyun likha? Bina iske kya hoga?</summary>

Ye PATCH-style update hai — "sirf jo bheja wo badlo." `if data.name is not None` ka matlab "agar user ne name bheja hai (aur `None` nahi hai), tabhi name badlo." Agar ye check na ho, to jab user sirf `last_price` bheje (name nahi bheje), to `data.name` ka default `None` hoga aur wo **seedha set ho jayega** `item.name = None` — aur name khatam! Ye guard isse rokta hai. Ye pattern har "partial update" me use hota hai.

</details>

## What It Is NOT

- ❌ **Ye database nahi hai** — `stocks` dict memory me hai, restart pe gayab. SQLite (1.4) se fix hoga.
- ❌ **Ye auth nahi** — koi bhi update/delete kar sakta hai. Real me token verify hoga.
- ❌ **Ye bulk operations nahi** — ek ek item update. Real me "50 stocks ek saath update" ka endpoint bhi hota hai.
- ❌ **Ye soft delete nahi** — `del stocks[id]` permanently hatata hai. Real systems me `active: false` mark karte hain (history ke liye), jaise Stock model me `active` field hai.
- ❌ **Ye pagination nahi** — `limit` to hai par `offset`/`page` nahi. Real me pagination zaroori hai 2000 stocks jaisi list pe.

## Agle Step Mein Kya Hoga?

Ab CRUD complete hai — Create, Read, Update, Delete sab. Par ek bada problem **abhi bhi hai**: data `stocks` dict me hai, jo sirf memory me hai. **Server restart karo, sab data gayab.**

DukaanOS me imagine karo — subah shop khuli, 200 items database me hain. Raat ko server restart hua. Subah sab kuch gayab. Yeh real me nahi hota — isliye database hota hai.

SQLite wohi hai — **file-based database** jo restart pe bhi data rakhta hai. Aur DukaanOS/TradeStack dono me SQLite use hota hai. To ab hum SQLite seekhenge — table banana, data insert karna, query karna, aur CRUD ko database se jodna.
