## Think (Something to Think About)

You've been showing DukaanOS's data for 3 days. Added 10 items daily, everything working. But at night the server **restarted** — Next.js also crashed.

Next morning you open `/api/stocks` — **empty**. 30 items gone. Why? Because `stocks: dict[int, Stock] = {}` is a **temporary variable in RAM**. Like an unsaved notepad document — close it, it's gone.

**You have two options:**

**Option 1 — Save with notepad.** Write every add to a `.txt` file. But what about 10,000 items? Reading file on every read is slow. Opening, writing, closing file on every write — painful. And writing to same place from two places at once causes corruption.

**Option 2 — Use a database.** SQLite is a **library** built into Python that works like: data stays safely in a **file**, queries are **fast**, and two programs can safely work on the same file.

**SQLite is Option 2 — the same one TradeStack and DukaanOS use.** Why? Because sqlite3 comes **with Python** (no install needed), and it's just a simple `.db` **file** on disk. No server, no setup. Perfect for small to medium projects.

## Manual Method (painful way)

Trying to make a "database" without SQLite — meaning a **JSON file**. This is actually a real method (used in Next.js too), and important to see how far it can go and where it **breaks**.

```python
# Manual JSON file "database"
import json
from pathlib import Path

DB_FILE = Path("data/stocks.json")

def load_all():
    if not DB_FILE.exists():
        return []
    return json.loads(DB_FILE.read_text())

def save_all(stocks):
    DB_FILE.parent.mkdir(parents=True, exist_ok=True)
    DB_FILE.write_text(json.dumps(stocks, indent=2))

# Create
stocks = load_all()
stocks.append({"id": 1, "symbol": "RELIANCE"})
save_all(stocks)          # rewrite whole file every time!

# Read — filter in Python
stocks = load_all()
it_sector = [s for s in stocks if s["sector"] == "IT"]

# Update — find, change, rewrite whole file
for s in stocks:
    if s["id"] == 1:
        s["last_price"] = 1450
save_all(stocks)          # whole file again!
```

This **works for small projects.** But as data grows, it starts **breaking**:

**Pain 1 — Rewrite whole file on every write.** Add one item = rewrite 2000 items file again. 2000 items = slow.

**Pain 2 — Filtering in Python, not database.** To filter `sector == "IT"`, load **all 2000 items into Python**, then filter. In reality you'd filter in the DB — this gets very slow.

**Pain 3 — Concurrency (two programs at once).** If **two** requests come at same time (double-click browser, or two tabs), both do `load_all()` → `save_all()` → one **overwrites** the other's data. File corrupt. Database handles this with **transactions**.

**Pain 4 — Incomplete structure.** Nothing enforces that `sector` is a string. No guarantee that `id` is unique. Database has **schema** — define types, enforce unique, validate relations.

**That's why a database.** Now let's see **how**.

## Concept: What Is SQLite (Simple Language)

SQLite is a **library** — Python's built-in `sqlite3` module. Its job: **store structured data in a file**, and read/write it **safely, fast, reliably**.

**File-based** — just one `.db` file. No server, no install, no config. Like a smart Excel file.

**Smaller than PostgreSQL/MySQL.** Those two run a **server** and database is a separate service. In SQLite everything is in one file. So:
- Small projects, personal tools, offline apps, mobile → **SQLite**
- Big production systems, multiple servers → **PostgreSQL/MySQL**

**TradeStack uses SQLite** because it's a **personal trading tool**, one user, local machine. No point running a server when data fits in one file and is fast.

---

## Concept: What Is a Table

Database data lives in **tables** — like an Excel sheet. Table rows = records, columns = fields.

```sql
CREATE TABLE stocks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    name TEXT NOT NULL,
    sector TEXT,
    last_price REAL,
    active INTEGER DEFAULT 1
);
```

**Every column has a type.** This is important — in Excel you can put anything in any cell, but in database **no**. `symbol TEXT NOT NULL` means — it's text, and it can never be empty.

**`PRIMARY KEY AUTOINCREMENT`** — `id` automatically increases 1, 2, 3, 4... for every new row. You don't need to think of IDs yourself.

This is all SQL. **SQL** = Structured Query Language — the language to talk to databases. SQLite uses SQL. Every database (Postgres, MySQL) also uses SQL — just slightly different dialect.

---

## Concept: Python with SQLite (sqlite3 Module)

You'll write SQL directly through `sqlite3`. Three things happen for every query:

1. **Connect** — join the file
2. **Cursor** — a helper that runs queries
3. **Execute + commit** — run query, make changes permanent

```python
import sqlite3
from pathlib import Path

DB_PATH = Path(__file__).parent / "data" / "stocks.db"

def get_conn():
    conn = sqlite3.connect(DB_PATH)
    return conn

# CREATE
conn = get_conn()
cursor = conn.cursor()
cursor.execute("""
    CREATE TABLE IF NOT EXISTS stocks (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        symbol TEXT NOT NULL,
        name TEXT NOT NULL,
        sector TEXT,
        last_price REAL,
        active INTEGER DEFAULT 1
    )
""")
conn.commit()      # REQUIRED — without commit, changes won't save
conn.close()
```

**`conn.commit()` means — "make what I did permanent."** Without commit, changes stay only in memory, not written to file. Forget this once and data is gone — this concept clearly comes up in 1.5.3 project.

## Concept: CRUD in SQL (SQL for each method)

Every CRUD method has one SQL query. Remember this table — useful in interviews too:

| Operation | SQL | Meaning |
|-----------|-----|---------|
| **Create** | `INSERT` | Insert new row |
| **Read** | `SELECT` | Get data |
| **Update** | `UPDATE` | Change row |
| **Delete** | `DELETE` | Remove row |

**These 4 are enough** for a database. Everything else — filter, join, count — is extension of these 4.

```python
# CREATE
cursor.execute(
    "INSERT INTO stocks (symbol, name, sector, last_price) VALUES (?, ?, ?, ?)",
    ("RELIANCE", "Reliance Industries", "Oil", 1420.50)
)
conn.commit()

# READ (all)
cursor.execute("SELECT * FROM stocks")
rows = cursor.fetchall()      # get all rows

# READ (one)
cursor.execute("SELECT * FROM stocks WHERE symbol = ?", ("RELIANCE",))
row = cursor.fetchone()       # one row only

# READ (filter + limit)
cursor.execute("SELECT * FROM stocks WHERE sector = ? LIMIT ?", ("IT", 20))
rows = cursor.fetchall()

# UPDATE
cursor.execute(
    "UPDATE stocks SET last_price = ? WHERE id = ?",
    (1450.0, 1)
)
conn.commit()

# DELETE
cursor.execute("DELETE FROM stocks WHERE id = ?", (1,))
conn.commit()
```

---

## Concept: `?` Placeholders (Very Important)

Notice every query above has **`?`**. This is a **placeholder**. Write `?` for values, pass actual values as a **tuple** to `execute()`.

**Why is this important?** Protection from SQL injection. Understanding this is **very important** for interviews too.

**Wrong way (dangerous):**
```python
symbol = "RELIANCE'; DROP TABLE stocks; --"   # malicious input
cursor.execute(f"SELECT * FROM stocks WHERE symbol = '{symbol}'")
# WHAT HAPPENED? SQL became: SELECT * FROM stocks WHERE symbol = 'RELIANCE'; DROP TABLE stocks; --'
# WHOLE TABLE GONE! 😱
```

**Right way (safe):**
```python
cursor.execute("SELECT * FROM stocks WHERE symbol = ?", (symbol,))
# `?` gets the value filled — and that value is NOT interpreted as SQL.
# Malicious string stays just a string, doesn't become a command.
```

This is Python `sqlite3`'s security feature. If someone asks in interview *"how do you prevent SQL injection?"* — answer: **parameterized queries, `?` placeholders, never build SQL with f-strings.**

## Concept: Getting Rows as Dict

One thing to note. `cursor.fetchall()` returns **tuples** — `(1, "RELIANCE", "Reliance Industries", "Oil", 1420.50)`. These can't directly go into FastAPI's JSON response — tuples aren't JSON.

So we convert to **dict** — so FastAPI can convert to Pydantic model:

```python
import sqlite3

def row_to_dict(cursor, row):
    """Convert row to dict — with column names."""
    return dict(zip([col[0] for col in cursor.description], row))

# Use
cursor.execute("SELECT * FROM stocks WHERE id = ?", (1,))
row = cursor.fetchone()
if row:
    stock = row_to_dict(cursor, row)
    # stock = {"id": 1, "symbol": "RELIANCE", "name": "...", ...}
```

`cursor.description` tells which columns exist. `dict(zip(names, values))` joins them into a clean dict. **This same pattern is in real TradeStack** — rows come from SQLite and get converted to dict.

## Code: Complete Example (CRUD + SQLite)

Now the same stocks API from 1.3 — but with **database**. Same endpoints, only storage changed:

```python
import sqlite3
from pathlib import Path
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Trading Backend Basic")

DB_PATH = Path(__file__).parent / "data" / "stocks.db"
DB_PATH.parent.mkdir(parents=True, exist_ok=True)


def get_conn():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row     # <-- rows come back dict-like
    return conn


def init_db():
    conn = get_conn()
    conn.execute("""
        CREATE TABLE IF NOT EXISTS stocks (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            symbol TEXT NOT NULL UNIQUE,
            name TEXT NOT NULL,
            sector TEXT,
            last_price REAL,
            active INTEGER DEFAULT 1
        )
    """)
    conn.commit()
    conn.close()


init_db()


# --- Models (from 1.2) ---

class StockCreate(BaseModel):
    symbol: str
    name: str
    sector: str | None = None
    last_price: float

class StockUpdate(BaseModel):
    name: str | None = None
    sector: str | None = None
    last_price: float | None = None

class Stock(StockCreate):
    id: int
    active: bool = True


# --- CREATE ---

@app.post("/api/stocks", response_model=Stock, status_code=201)
def create_stock(data: StockCreate):
    conn = get_conn()
    try:
        cursor = conn.execute(
            "INSERT INTO stocks (symbol, name, sector, last_price) VALUES (?, ?, ?, ?)",
            (data.symbol, data.name, data.sector, data.last_price)
        )
        conn.commit()
        new_id = cursor.lastrowid
        row = conn.execute("SELECT * FROM stocks WHERE id = ?", (new_id,)).fetchone()
        return dict(row)
    except sqlite3.IntegrityError:
        raise HTTPException(status_code=409, detail="Symbol already exists")
    finally:
        conn.close()


# --- READ single ---

@app.get("/api/stocks/{stock_id}", response_model=Stock)
def get_stock(stock_id: int):
    conn = get_conn()
    row = conn.execute("SELECT * FROM stocks WHERE id = ?", (stock_id,)).fetchone()
    conn.close()
    if not row:
        raise HTTPException(status_code=404, detail="Stock not found")
    return dict(row)


# --- READ list (filter + limit) ---

@app.get("/api/stocks", response_model=list[Stock])
def list_stocks(limit: int = 20, sector: str | None = None, active_only: bool = False):
    conn = get_conn()
    query = "SELECT * FROM stocks WHERE 1=1"
    params = []
    if sector:
        query += " AND sector = ?"
        params.append(sector)
    if active_only:
        query += " AND active = 1"
    query += " LIMIT ?"
    params.append(limit)
    rows = conn.execute(query, params).fetchall()
    conn.close()
    return [dict(r) for r in rows]


# --- UPDATE ---

@app.put("/api/stocks/{stock_id}", response_model=Stock)
def update_stock(stock_id: int, data: StockUpdate):
    conn = get_conn()
    existing = conn.execute("SELECT * FROM stocks WHERE id = ?", (stock_id,)).fetchone()
    if not existing:
        conn.close()
        raise HTTPException(status_code=404, detail="Stock not found")

    fields = data.model_dump(exclude_none=True)
    if fields:
        set_clause = ", ".join(f"{k} = ?" for k in fields)
        values = list(fields.values()) + [stock_id]
        conn.execute(f"UPDATE stocks SET {set_clause} WHERE id = ?", values)
        conn.commit()

    row = conn.execute("SELECT * FROM stocks WHERE id = ?", (stock_id,)).fetchone()
    conn.close()
    return dict(row)


# --- DELETE ---

@app.delete("/api/stocks/{stock_id}", status_code=204)
def delete_stock(stock_id: int):
    conn = get_conn()
    cursor = conn.execute("DELETE FROM stocks WHERE id = ?", (stock_id,))
    conn.commit()
    deleted = cursor.rowcount
    conn.close()
    if deleted == 0:
        raise HTTPException(status_code=404, detail="Stock not found")
```

**Three new concepts here:**

1. **`sqlite3.Row`** — `conn.row_factory = sqlite3.Row` makes rows come back so you can use `row["symbol"]` (dict-like). Then `dict(row)` makes clean JSON.

2. **`WHERE 1=1`** — looks weird but is smart. You add filter conditions one by one: `AND sector = ?` etc. `WHERE 1=1 AND sector = ? AND ...` — gives you a starting point. Without it you'd have to think about `AND`/`OR` logic for every filter.

3. **`conn.close()` every time** — closing connection is important. New connection per request, close after use.

## Test: How to Verify (From Browser + Restart Test)

Run server, open `/docs`. Same sequence — Create, Read, Update, Delete.

**But this time there's an EXTRA test that wasn't possible before — SQLite's biggest advantage:**

1. **Add data:** `POST` 2-3 items (`/api/stocks`).
2. **VERIFY restart:** **Stop** the server (`Ctrl+C`), then run `uvicorn` again. `GET /api/stocks` — **data is still there!** 🎉

Before (memory dict), this data **disappeared**. Now it's in the database — restart safe.

3. **UNIQUE test:** Add same symbol again (`RELIANCE` again). Now **409 Conflict** — because `symbol TEXT NOT NULL UNIQUE` was set. (Before, it would add again, creating duplicate.) Proof of real constraint — database itself rejected it.

4. **DELETE + 404:** Delete an item, then `GET` it — **404** comes.

5. **Look in browser:** Download `sqlitebrowser.org` or use VS Code's "SQLite Viewer" extension to open `data/stocks.db` — see the table. Data will show what the API returned. **This is data in database, not memory.**

## Nutshell

- **SQLite** = Python's built-in `sqlite3` module, data in one file. No server, no install. TradeStack and DukaanOS both use it.
- **Table** = structure (columns + types), **row** = one record. `PRIMARY KEY AUTOINCREMENT` = ID auto-increases.
- **CRUD = 4 SQL commands**: `INSERT` (create), `SELECT` (read), `UPDATE`, `DELETE`.
- **`?` placeholders** = protection from SQL injection. Never build SQL with f-strings.
- **`conn.commit()`** = make changes permanent. **`conn.close()`** = close connection.

---

## Common Mistakes

1. **Forgetting `conn.commit()`.** Query runs but data **doesn't save**. Server restart = all gone. Most common mistake.

2. **Building SQL with f-strings.** `f"...WHERE symbol = '{symbol}'"` — **wide open to SQL injection**. Always use `?` placeholder and tuple.

3. **Not calling `conn.close()`.** Close connection in `finally` block of every endpoint, otherwise **connection leak** — file handles stay open, performance drops.

4. **Not setting `PRIMARY KEY`.** Without it, duplicate IDs possible, and update/delete might hit wrong row. This is the foundation.

5. **Not setting `row_factory`.** Default returns tuples. Hard to make JSON response. Set `sqlite3.Row`, use `dict(row)`.

6. **Confusing `active` INTEGER vs boolean.** SQLite has no boolean type — `True`/`False` stored as `1`/`0`. Pydantic converts back to boolean.

7. **Not checking `CREATE TABLE` before creating.** Use `CREATE TABLE IF NOT EXISTS` — otherwise every server restart gives "table already exists" error.

## In Your Own Words

<details>
<summary>1. Why use SQLite? How is it different from PostgreSQL?</summary>

SQLite is a **file-based** database — data in one `.db` file, no server, comes built-in with Python (nothing to install). Perfect for small projects and personal tools — TradeStack and DukaanOS are both single-user/local tools like this. PostgreSQL/MySQL run a separate **server** that hosts the database — needed when multiple servers/apps access the same database (production scale). Simple rule: **small/local project = SQLite, big/multi-user production = PostgreSQL.**

</details>

<details>
<summary>2. Why is `?` placeholder important? Why is f-string SQL wrong?</summary>

`?` placeholder protects from **SQL injection**. Because it keeps SQL and values separate — the value is never interpreted as SQL code. With f-strings, if user sends `'; DROP TABLE stocks; --`, it becomes a complete SQL statement and deletes the table. With `?`, that dangerous string stays just a **normal text value**, not a command. Simple rule: **never put user data in SQL via f-string/concatenation, always use `?` and parameterized queries.**

</details>

<details>
<summary>3. Why is `conn.commit()` necessary? What happens without it?</summary>

In SQLite, whenever you **change** data (INSERT/UPDATE/DELETE), the change stays pending in memory first. `conn.commit()` makes it permanent on disk in the file. **Without commit** data shows only during that connection, but on **server restart or program close it disappears** (some versions also rollback on connection close). So `conn.commit()` after every write operation is essential.

</details>

<details>
<summary>4. What's the benefit of `WHERE 1=1`? Why does it look weird?</summary>

`WHERE 1=1` is initially a **dummy condition** that's always true. Its benefit: when you add filters (like sector, active_only), you can always append `AND ...` without worrying about what the first condition was. `WHERE 1=1 AND sector = ? AND active = 1` — always correct structure, whether one filter or ten. This pattern is very common in dynamic queries with optional conditions.

</details>

<details>
<summary>5. Tuples don't work — how to get dict? What does `sqlite3.Row` do?</summary>

By default `sqlite3` returns rows as **tuples** — `(1, "RELIANCE", ...)`. These can't go into JSON, so FastAPI can't make a response. `conn.row_factory = sqlite3.Row` makes rows **dict-like** where you can use `row["symbol"]`. Then `dict(row)` gives clean JSON-ready data that goes into Pydantic `response_model`.

</details>

<details>
<summary>6. When does 409 Conflict come? How to test it in real life?</summary>

When a constraint is violated — like `symbol TEXT NOT NULL UNIQUE` and user tries to add same symbol again. Database rejects the duplicate and FastAPI gets `sqlite3.IntegrityError`, which you catch in `except` block and send `HTTPException(409, "Symbol already exists")`. Test by adding one item, then adding with the **same symbol again** — 409 Conflict comes. Shows database enforced data integrity itself, application code didn't need to.

</details>

## What It Is NOT

- ❌ **Not PostgreSQL** — SQLite is single-user. Multi-server production needs PostgreSQL. Perfect for single-user/local right now.
- ❌ **Not an ORM** — you're writing raw SQL. Real uses SQLAlchemy, but **learning raw SQL is essential** — interviews ask about it and complex queries are clearer than ORM.
- ❌ **Not teaching relationships** — foreign keys, joins, one-to-many. That's Phase 3 or real project. Right now single table.
- ❌ **Not teaching migrations** — schema changes are manual right now. Real needs Alembic-like tool.
- ❌ **Not async** — `sqlite3` is synchronous. FastAPI is async but sync is fine for SQLite in small projects. (For async DB there's `aiosqlite`.)
