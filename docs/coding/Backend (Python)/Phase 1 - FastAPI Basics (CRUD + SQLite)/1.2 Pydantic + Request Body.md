In 1.1 you learned how **single values** come from the URL (path + query). Now let's go one step further.

Back to DukaanOS. Customer did billing. Now the staff sitting at the counter starts **typing** the data — product name, quantity, price. This data can't come in the URL — it comes in the **body**. And if staff mistakenly types price as `"abc"`, the system shouldn't accept it.

That's what Pydantic + Request Body does.

---

## Think (Something to Think About)

You're running DukaanOS's counter. An action is happening — **"add a new item."**

1. Staff types: item name **"Parle-G"**, category **"Biscuit"**, price **"10"**, stock **"50"**.
2. These 4 things are in staff's hands, being **sent** from a browser form to the server.
3. The server needs all 4 values at once, and each one's type needs to be checked — `price` should be a number, `name` should be a string.

Now the question — **how does this data reach the server?**

In 1.1 we learned a single value comes from the URL (`?limit=10`). But here **4 values** exist, and an item needs to be described. Putting it in the URL is absurd — `POST /api/items?name=Parle-G&category=Biscuit&price=10&stock=50`. Messy, length limits, and you'd change the URL for every new field.

So there's a **separate place** for data — **Request Body**. That's the same JSON you read in Phase 0's `0.3 API and JSON`. Browser sends JSON in the body, FastAPI reads it.

---

## Manual Method (painful way)

If FastAPI didn't exist, you'd read the body manually. FastAPI's predecessor (Starlette) style, or raw bytes:

```python
# Manual (never do this)
from starlette.requests import Request
import json

@app.post("/api/items")
async def add_item(request: Request):
    raw = await request.body()          # raw bytes
    data = json.loads(raw)              # manually JSON parse

    # Now validate manually... separate `if` for each field
    if "name" not in data:
        raise ValueError("name required")
    if "price" not in data:
        raise ValueError("price required")
    try:
        price = float(data["price"])    # manually convert
    except (ValueError, TypeError):
        raise ValueError("price must be a number")
    if price < 0:
        raise ValueError("price cannot be negative")

    return {"name": data["name"], "price": price}
```

See the pain:

- **`raw = await request.body()`** — raw bytes came, you had to manually parse with `json.loads`.
- **Separate `if` for each field** — `name` needed, `price` needed, `stock` needed. 4 fields = 8+ lines. And every new field = 2 more lines.
- **Manual type conversion** — `float(data["price"])`, then `try/except` to catch errors.
- **Custom error messages** — separate message for each field. And wrong error format — user won't get proper "field required" message, just a raw exception.
- **This repeats on every endpoint** — 48 endpoints and you'd write the same code 48 times.

Pydantic eliminates **all this pain in one line**.

---

## Concept: Pydantic Model = Data's Blueprint

In Pydantic you define a **class** that says — **"this endpoint's data should look like this."** This class is your data's **contract**.

```python
from pydantic import BaseModel

class ItemCreate(BaseModel):
    name: str
    category: str
    price: float
    stock: int = 0        # default — optional
```

Now use this class:

```python
@app.post("/api/items")
def add_item(item: ItemCreate):
    # item is now a validated object
    return {
        "name": item.name,
        "category": item.category,
        "price": item.price,
        "stock": item.stock,
    }
```

**What happened here?** As soon as you wrote `def add_item(item: ItemCreate)`, FastAPI automatically:
1. **Read JSON from body** — saved you `await request.body()` and `json.loads`
2. **Validate each field** — is `name` a string? `price` a number? `stock` an int? Wrong → **422 reject**
3. **Convert types** — if `"price": "10"` sent (string number), Pydantic converts it to `10` (float). You don't need `float()`.
4. **Accept in response** — now `item` is a proper object, `item.price` directly gives a float.

**Type hints (`name: str`, `price: float`) do the validation work.** Just like 1.1 where type hints worked for path/query params, type hints work for body too.

---

## Concept: Request Body vs Path/Query — Which One When?

This is the most important decision. Clear rule:

| Data comes from | How it's sent | FastAPI | Example |
|-----------------|---------------|---------|---------|
| **Which resource** (identity) | URL path | Path param `{symbol}` | `/api/stocks/RELIANCE` |
| **What you want** (options/filter) | URL `?` after | Query param `?limit=10` | `/api/stocks?limit=10` |
| **New data** (create/update) | Request **body** (JSON) | Pydantic model | `POST /api/items` with JSON |

Understand from DukaanOS:
- *"Show me RELIANCE's data"* → **GET** `/api/stocks/RELIANCE` — not sending data, just asking. Query param optional (like `?days=90`).
- *"Add a new item"* → **POST** `/api/items` + **body** `{name, category, price}` — sending new data, it goes in body.

**POST/PUT data always comes from body. GET/DELETE data always comes from URL.** This rule is asked in interviews too — remember it.

---

## Concept: Optional Fields and Defaults

In 1.1 you learned `limit: int = 20`. Same rule in body — required field is simple, optional uses default or `| None`.

```python
class ItemCreate(BaseModel):
    name: str                  # required — string needed
    price: float               # required — number needed
    category: str | None = None    # optional — default None
    stock: int = 0             # optional — default 0
    discount: float = 0.0      # optional — default 0.0
```

**Two ways to make optional:**
- `stock: int = 0` — default value given (number, but specific)
- `category: str | None = None` — either string or `None` (don't know what it'll be)

If the user sends only `{name, price}`, Pydantic **automatically** fills `category=None, stock=0, discount=0.0`. You don't need any `if` to check "missing field".

## Concept: Response Models (bonus, 2 min)

So far we've learned **input** validation. **Output** can also be validated — and very useful.

```python
class Item(BaseModel):
    id: int
    name: str
    price: float
    stock: int

@app.get("/api/items/{item_id}", response_model=Item)
def get_item(item_id: int):
    return {"id": item_id, "name": "Parle-G", "price": 10.0, "stock": 50, "secret": "delete_me"}
```

`response_model=Item` means — **only these 4 fields go in response**. The `secret` field is automatically **filtered out** because it's not in the `Item` model.

This does two things:
1. **Response shape guaranteed** — if you accidentally send `password`, it won't leak.
2. **Exact schema in docs** — Swagger shows the correct response structure.

Real TradeStack does the same — scanner responses go through typed models.

## Code: Complete Example (Step by Step)

A small, realistic items API — DukaanOS feel:

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="Trading Backend Basic")


# --- Models (data shape) ---

class ItemCreate(BaseModel):
    name: str
    price: float
    category: str | None = None
    stock: int = 0

class Item(BaseModel):
    id: int
    name: str
    price: float
    category: str | None = None
    stock: int


# In-memory storage (for now — 1.4 replaces with SQLite)
items: dict[int, Item] = {}
next_id = 1


# --- Endpoints ---

@app.post("/api/items", response_model=Item)
def create_item(data: ItemCreate):
    """Create a new item."""
    global next_id
    item = Item(
        id=next_id,
        name=data.name,
        price=data.price,
        category=data.category,
        stock=data.stock,
    )
    items[next_id] = item
    next_id += 1
    return item


@app.get("/api/items/{item_id}", response_model=Item)
def get_item(item_id: int):
    """Get one item by id (path param from 1.1)."""
    if item_id not in items:
        return {"error": "not found"}   # simple for now; proper 404 in 1.3
    return items[item_id]


@app.get("/api/items", response_model=list[Item])
def list_items(limit: int = 20, category: str | None = None):
    """List items, with filter + limit (query params from 1.1)."""
    result = list(items.values())
    if category:
        result = [i for i in result if (i.category or "").lower() == category.lower()]
    return result[:limit]
```

**See what happened:**

- `create_item` has **no validation `if`**. `data` is already validated — `price` is float, `name` is string. `data.stock` defaults to `0` if not sent.
- `get_item` has **no `int()` conversion** — `item_id` is already int (from 1.1).
- `list_items` has **no query parsing** — `limit`, `category` come directly.

Only **business logic remains** — storing in dict, filtering, incrementing ID. Everything else is the framework. That's FastAPI's promise — saving this work on 48 endpoints matters.

## Test: How to Verify (From Browser)

Run server `uvicorn app.main:app --reload`, then open `http://localhost:8000/docs`.

**Test sequence (for 1.2):**

1. **`POST /api/items`** — click "Try it out", put in body:
   ```json
   { "name": "Parle-G", "price": 10, "category": "Biscuit" }
   ```
   `stock` not sent — see response with `"stock": 0` **automatically** (default). Hit Execute.

2. **Type conversion test:** send `"price": "25"` in body (number as string). Response will show `"price": 25.0` — became a **number**. Pydantic converted it, without any code from you.

3. **Validation test (most important):** send `"price": "abc"` in body, or omit `name`. See FastAPI give **422** with field-level error — *"field required"* or *"not a valid number"*. **This is Pydantic's proof** — you didn't write any `if`, yet bad data was rejected.

4. **`GET /api/items/1`** — get item by path param. `GET /api/items?category=Biscuit&limit=5` — filter with query param.

At each step hit "Execute", see **both response and status code**. 200 = fine, 422 = validation worked.

## Nutshell

- **Request body** = new/complex data coming as JSON (POST/PUT).
- **Pydantic model** = data's contract. Write type hints → validation, conversion, docs **automatic**.
- Model for body, `{param}` for path, `?param=` for query — **three different places, three different jobs**.
- `field: type` = required, `field: type = default` or `field: type | None = None` = optional.
- Bad data gets **422** rejected — no `if` needed in your code.

---

## Common Mistakes

1. **Making body fields path params.** `POST /api/items/{name}/{price}` is wrong. Body fields (name, price, category) **always go in body**, not path. Path is only for identity.

2. **Making optional field required.** Write `category: str` and it becomes **required** — user omits it and gets 422. If optional, write `str | None = None`.

3. **Accepting `dict` body directly.** `def create(data: dict)` — nothing validated, no type safety. Always create a Pydantic model for shape.

4. **Mixing up body and query.** Filter (like `?sector=IT`) is query param. Only new data goes in body. Don't confuse them.

5. **Sending sensitive field in response.** Without `response_model`, the whole object could go (password leak). Add `response_model` or manually send only safe fields.

6. **Forgetting `from pydantic import BaseModel`.** This import goes at top — without it `BaseModel` is undefined and you'll get an error.

## In Your Own Words

<details>
<summary>1. Why make a Pydantic model? How is it better than manual validation?</summary>

A Pydantic model is data's **contract** — a class where type hints show each field's type. With manual validation you'd write separate `if` for each field, manually convert types, write custom error messages for each field, and repeat this on every endpoint. With Pydantic, write one class and FastAPI automatically **parses, validates, converts, and generates docs** — and the same code works on all 48 endpoints. Validation is defined once, applied everywhere automatically.

</details>

<details>
<summary>2. What's the difference between request body and query parameter? Which one when?</summary>

Request body sends new or complex data — what the client is **sending** (like new item: name, price, category), and it comes as JSON in POST/PUT body. Query parameter is for **filters/options** — what the client is **asking for** (like `?limit=10`, `?sector=IT`), and comes after `?` in GET. Rule: **new data = body, filter/options = query, identity = path.**

</details>

<details>
<summary>3. You wrote `price: float`, user sent `"price": "10"` (string). What happens?</summary>

Pydantic **automatically converts**. It sees `"10"` string, with `float` type hint, creates `10.0` float — app accepts it. Manual method was harder because you'd call `float()` yourself. **But** if user sends `"price": "abc"` (not a number), Pydantic can't convert and gives **422 error** — because `"abc"` isn't a valid float. That's validation at work.

</details>

<details>
<summary>4. How to make optional fields? Difference between `stock: int = 0` and `stock: int | None = None`?</summary>

Both are optional — user sends it or not, either works. `stock: int = 0` means "use default 0 if not sent" — field always stays a number (0 or something else). `stock: int | None = None` means "default None, and it's legitimately allowed to be None" (like "stock info unknown"). Simple: if you want a **specific default value** use `= value`, if the semantics are "might or might not exist" use `| None = None`.

</details>

<details>
<summary>5. What does `response_model=Item` do? Is it for validation or just output shape?</summary>

`response_model` mainly controls **output shape** — FastAPI only sends **defined fields** in response, filtering out the rest. It's also important for **security** (password field doesn't accidentally leak) and **docs** (Swagger shows exact schema). It doesn't work like input validation — that's what `ItemCreate` model (function parameter) does. Response just validates that correct fields exist.

</details>

<details>
<summary>6. Why doesn't GET request have a body?</summary>

GET means "give me something" — read-only. No logical reason to send data in body — URL params are cleaner, bookmarkable in browser, and caching works. Technically you could send body in GET (just don't use `async def`), but it's an **anti-pattern** — many clients and proxies ignore GET bodies. So the rule: **GET/DELETE data = URL (path/query), POST/PUT data = body.**

</details>

## What It Is NOT

- ❌ **Not storing data** — `items` dict is in memory, disappears on restart. SQLite (1.4) fixes this.
- ❌ **No authentication** — anyone can create any item. Real would check tokens (Phase 2/3).
- ❌ **Not complex validation** — like "price and stock both can't be zero together." That's Pydantic's advanced validators, later.
- ❌ **Not nested objects** — you can send `metadata: dict` or list of objects in Pydantic, but right now we're learning simple flat fields.
