## What Is the Data Shape?

This is the **most important** step. Think — what tables in database, what columns in each table.

### Table 1: `stocks`

This is your **main list** — which stocks you're tracking.

| Column | Type | Why it's there |
|--------|------|---------------|
| `id` | INTEGER PRIMARY KEY | Unique number for each stock (auto) |
| `symbol` | TEXT NOT NULL UNIQUE | NSE code (RELIANCE, TCS). Unique because same symbol shouldn't appear twice |
| `name` | TEXT NOT NULL | Company name — shows in UI |
| `sector` | TEXT | Filtering (IT, Oil, Banking) |
| `last_price` | REAL | Last price — for calculations |
| `active` | INTEGER DEFAULT 1 | 1 = being tracked, 0 = removed. Soft delete |

**Reason for each field:**
- `id` — needed for update/delete (which stock from URL)
- `symbol` UNIQUE — same symbol shouldn't appear again (409 Conflict — tested in 1.4)
- `name` — shown in UI
- `sector` — for `?sector=IT` filter
- `last_price` — for calculations (used in next step)
- `active` — soft delete. Instead of `del`, set `active=0`, so old data stays (history). Real TradeStack also does this.

### Table 2: `settings`

This is your **configuration** — scanner settings. TradeStack also has this exactly (`settings` table).

| Column | Type | Why it's there |
|--------|------|---------------|
| `key` | TEXT PRIMARY KEY | Setting name (like `rsi_period`) |
| `value` | TEXT NOT NULL | Setting value (like `14`) |

**Why a key-value table?** Because new settings can be added without schema change. One `rsi_period`, one `sma_period`, one `oversold_threshold` — all in one table. Need a new setting? **Just add a row**, no schema touch. This is a real pattern (TradeStack's `settings.py` does exactly this).

### Table 3: `prices` (optional, but recommended)

This needs some thought. Indicators (SMA, RSI) need **time series** — meaning multiple days of prices for one stock. Just `stocks.last_price` won't make an indicator (that's just one day's price).

| Column | Type | Why it's there |
|--------|------|---------------|
| `id` | INTEGER PRIMARY KEY | Auto |
| `symbol` | TEXT NOT NULL | Which stock's price |
| `date` | TEXT NOT NULL | Which day's price (YYYY-MM-DD) |
| `open` | REAL | Day's opening price |
| `high` | REAL | Day's high |
| `low` | REAL | Day's low |
| `close` | REAL | Day's closing price — **this goes into indicator** |

**So we need a `prices` table** with **multiple days** of data for each stock. One stock's 60 days of data = 60 rows.

**Realistic thinking:** TradeStack has 2000 stocks × 60+ days of data, stored in **pickle cache** (not CSV). But for our small project, **SQLite table is enough** — concept is the same: *"store time-series prices for one stock, compute indicators on top."*

## How Will Data Flow?

Now think — where does data come from, where does it go. This is what we'll build in 1.5, but **think about it now**.

```
Browser /docs or some client
       ↓ (HTTP request)
FastAPI endpoint (1.1-1.3 work)
       ↓ (SQL query, ? placeholder)
SQLite database (stocks, settings, prices tables)
       ↓ (rows)
Pydantic response model (1.2 validation)
       ↓ (JSON)
Browser shows JSON
```

**Three data paths in this project:**
1. **Input (Create/Update)** — browser sends JSON body → Pydantic validates → SQL `INSERT`/`UPDATE` → saves to SQLite
2. **Output (Read)** — SQL `SELECT` → rows → dict → Pydantic response model → JSON → browser
3. **Compute (Scan)** — read data from `prices` table → pandas SMA/RSI compute → filter → return

**One important decision:** where does price data come from? 3 options:
- (a) Manually import from CSV (recommended — simple, real feel)
- (b) Send via `POST /api/prices` (extra endpoint, extra work)
- (c) Generate randomly (placeholder, doesn't feel real)

**Recommend (a)** — create a small CSV file with 3-5 stocks' 60 days of prices (we'll put realistic numbers ourselves). Then a function imports it into SQLite. This is a simple version of real TradeStack's "bhavcopy ingest."

## What Will the Folder Structure Look Like?

This also needs thought — where do files go.

```
trading-backend-basic/
  app/
    main.py          # FastAPI app + all endpoints
    db.py            # SQLite connection + init + helper functions
    models.py        # Pydantic models (Stock, StockCreate, ScanResult...)
    indicators.py    # pandas functions (SMA, RSI)
    seed.py          # script to import prices from CSV
  data/
    stocks.db        # SQLite database file (auto-created)
    prices.csv       # sample price data (you create this)
  README.md
  requirements.txt
```

**Why separate files?** So code stays **organized**. `main.py` has only endpoints, `db.py` has only database, `indicators.py` has only math. Real TradeStack is also like this (`server.py`, `src/db.py`, `src/indicators.py`). This structure is interview-worthy — *"I organize code, each file has one job."*
