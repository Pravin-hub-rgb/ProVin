Server is up, `/health` is running, `/docs` is opening (1.5.2). Now the **real work** — creating data and serving it. This is Part 1's biggest and most important part.

But keep in mind — we won't build **everything at once**. Pain comes when you write everything together: 3 tables, 7 endpoints, seed script — and nothing works, you don't know **why** it's not working.

So we'll do **one table, one endpoint** at a time. Test at every step. Confirm at every step *"this works."* Then move on. This makes every step **safe**.

---

## Think (Something to Think About)

DukaanOS counter. Manager says — *"add these 5 new items to the database, and then I need their filtered list."*

You have the server (from 1.5.2), but no **data store**. If you build `GET /api/stocks` now, it won't return anything (where would data come from? nowhere).

So **first you need to build data's home** (table), then add data to it (insert), then read it (query). That's the **data layer**.

Understand the pain: Think if you're building **endpoints without tables**. You'd manually write `stocks = [...]` inside every endpoint (in memory). That works — but data disappears on restart, and for 100 stocks you'd write 1000 lines. **Table = data's permanent home.** Build once, then all endpoints read from that same home.

## Step 1: Create `app/db.py` — Database's Home

First, don't put everything in `main.py`. **Database work goes in a separate file.** We planned this separation — now applying it.

Create new file `app/db.py`:

```python
"""
Database layer — SQLite connection, table setup, and helper functions.
This file only talks to the database. No endpoints here.
"""
import sqlite3
from pathlib import Path

# Where the database file will be
DB_PATH = Path(__file__).parent.parent / "data" / "stocks.db"


def get_conn():
    """Create a new connection to the database."""
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row   # rows will be dict-like
    return conn


def init_db():
    """Create table if it doesn't exist. Called once on server start."""
    DB_PATH.parent.mkdir(parents=True, exist_ok=True)   # create data/ folder if missing

    conn = get_conn()
    conn.execute("""
        CREATE TABLE IF NOT EXISTS stocks (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            symbol TEXT NOT NULL UNIQUE,
            name TEXT NOT NULL,
            sector TEXT,
            last_price REAL,
            active INTEGER DEFAULT 1
        )
    """)
    conn.commit()
    conn.close()
```

**Line by line:**

- `DB_PATH` — file location. `Path(__file__).parent.parent` = `app/` folder's **parent** = project root. Then `data/stocks.db`. This is an **absolute path** — works from anywhere you run.
- `get_conn()` — new connection. `row_factory = sqlite3.Row` (learned in 1.4) — rows come back dict-like.
- `init_db()` — `IF NOT EXISTS` (learned in 1.4) — safe on every restart. `mkdir` creates data folder first. `CREATE TABLE` builds the schema. `commit()` makes it permanent.

**Why `IF NOT EXISTS`?** Because `init_db()` runs on every server restart. Without `IF NOT EXISTS`, you'd get error *"table already exists"* every time. This guard does what `CREATE TABLE IF NOT EXISTS` does.

## Step 2: Create `app/models.py` — Data's Shape

Second file — Pydantic models (learned in 1.2). Create `app/models.py`:

```python
"""
Pydantic models — data's shape and validation.
"""
from pydantic import BaseModel


class StockCreate(BaseModel):
    """For adding a new stock — what the client sends."""
    symbol: str
    name: str
    sector: str | None = None
    last_price: float


class Stock(StockCreate):
    """Stock that comes from database — also has id and active."""
    id: int
    active: bool = True
```

**Notice what happened:** `class Stock(StockCreate)` — `Stock` **inherits** from `StockCreate`. So `Stock` has all inherited fields (`symbol`, `name`, `sector`, `last_price`), plus extra `id` and `active`. This is **inheritance** — avoids writing same fields again and again. (This is standard in Pydantic docs, and real TradeStack too.)

## Step 4: First Endpoint — POST (Add New Stock)

Now the first **real** endpoint — adding a new stock (Create). Add to `main.py`:

```python
@app.post("/api/stocks", response_model=Stock, status_code=201)
def create_stock(data: StockCreate):
    """Add a new stock to database."""
    conn = get_conn()
    try:
        cursor = conn.execute(
            "INSERT INTO stocks (symbol, name, sector, last_price) VALUES (?, ?, ?, ?)",
            (data.symbol, data.name, data.sector, data.last_price)
        )
        conn.commit()
        new_id = cursor.lastrowid          # new ID given by autoincrement

        # Read back the same row (learned row->dict in 1.4)
        row = conn.execute("SELECT * FROM stocks WHERE id = ?", (new_id,)).fetchone()
        return dict(row)                   # becomes JSON

    except sqlite3.IntegrityError:
        # symbol is UNIQUE — duplicate gives 409 (tested in 1.4)
        raise HTTPException(status_code=409, detail="Symbol already exists")
    finally:
        conn.close()   # close connection (learned in 1.4)
```

**This uses 3 tools together — 1.2, 1.3, 1.4:**
- **1.2 (Pydantic)** — `data: StockCreate` automatically validated. `symbol` is string, `last_price` is float, `sector` is optional. Bad data → 422.
- **1.3 (CRUD/Create)** — `POST` + `status_code=201` (created → 201).
- **1.4 (SQLite)** — `INSERT` query, `?` placeholders, `commit()`, row→dict, `close()`.

**Forgot `sqlite3` import?** Yes — need to add `import sqlite3` to `main.py` too (with `from .db import`). Needed for `except sqlite3.IntegrityError`.

**What is `cursor.lastrowid`?** When you `INSERT`, SQLite automatically increments the new row's ID. `lastrowid` tells you what that ID was. That's the `id` we use to `SELECT` and read back.

Run server (`uvicorn app.main:app --reload`), open `/docs`.

**`POST /api/stocks` — "Try it out" → Execute. Put in body:**
```json
{
  "symbol": "RELIANCE",
  "name": "Reliance Industries",
  "sector": "Oil",
  "last_price": 1420.50
}
```

**Expect:**
- Response code **201** (Create)
- Response: `{"id": 1, "symbol": "RELIANCE", ..., "active": true}`

**Extra tests (these are important):**

1. **Optional field:** Remove `sector` from body. Response will show `"sector": null` — because `sector: str | None = None`. Default kicked in.

2. **Validation (422):** Send `"last_price": "abc"` (string, not number). FastAPI/Pydantic gives **422** — because `last_price: float` and `"abc"` isn't a float. Pydantic's work, no `if` in your code.

3. **UNIQUE (409):** Send **the same body again** (same `symbol: RELIANCE`). Now **409 Conflict** — *"Symbol already exists"* — because `symbol` was UNIQUE and duplicate was rejected.

**Three different codes (201, 422, 409) — this is 1.3's status code concept showing up in real life.**

## Step 6: Second Endpoint — GET (View List)

Now the **Read** endpoint — stocks list. Add to `main.py`:

```python
@app.get("/api/stocks", response_model=list[Stock])
def list_stocks(limit: int = 20, sector: str | None = None, active_only: bool = False):
    """Stocks list — with filter and limit."""
    conn = get_conn()

    query = "SELECT * FROM stocks WHERE 1=1"      # learned in 1.4 — dummy condition
    params = []

    if sector:
        query += " AND sector = ?"
        params.append(sector)

    if active_only:
        query += " AND active = 1"                 # boolean -> SQLite uses 1/0 (learned in 1.4)

    query += " LIMIT ?"
    params.append(limit)

    rows = conn.execute(query, params).fetchall()
    conn.close()

    return [dict(r) for r in rows]     # convert each row to dict
```

**This combines 1.1 (query params) + 1.3 (Read) + 1.4 (SQLite SELECT):**
- **1.1** — `limit`, `sector`, `active_only` are query params. `limit` defaults to 20, `sector` is optional.
- **1.3** — `GET` = Read, default 200.
- **1.4** — dynamic SQL (`WHERE 1=1` + filters), `?` placeholders.

**What does `list[Stock]` mean?** Response model is a **list of Stock**. FastAPI checks that every dict has `symbol`, `name`, etc., otherwise it errors.

One more endpoint — get a specific stock by ID. This is 1.1's **path param**:

@app.get("/api/stocks/{stock_id}", response_model=Stock)
def get_stock(stock_id: int):

## Common Mistakes

1. **Forgetting `commit()`.** Data shows but doesn't save — disappears on restart. Every `INSERT`/`UPDATE`/`DELETE` needs `conn.commit()` after.

2. **Not calling `close()`.** Close connection in every endpoint — `finally: conn.close()` or at the end. Otherwise **connection leak** — file handles stay open.

3. **Forgetting `from .db import`.** Wrote endpoint but didn't import `get_conn` — NameError. All imports at top.

4. **Not importing `sqlite3`** when using `except sqlite3.IntegrityError`. Need `import sqlite3` at top too.

5. **Writing `Stock` instead of `list[Stock]`.** You're returning a list, so `response_model=list[Stock]` is needed, otherwise FastAPI expects one dict and errors.

6. **Sending empty `params` list with `WHERE 1=1`.** `conn.execute(query, params)` needs `params` as a list. When adding filters, don't forget `params.append()`, otherwise `?` and values won't match.

7. **Testing GET before adding data.** First add 3-4 stocks with different sectors via POST, then test `?sector=` filter. Otherwise nothing will show in tests.

- **After every write do `commit()`, after every endpoint do `close()`.**

## In Your Own Words

<details>
<summary>1. Why make `init_db()` a separate function, not call it in every endpoint?</summary>

`init_db()` is needed only **once** — when server starts, create the table. If you put `CREATE TABLE` in every endpoint, every request would unnecessarily check for the table. So it's a separate function, called only once in `main.py` (when module loads). `CREATE TABLE IF NOT EXISTS` makes it safe too (if table exists, skip). Keeping `db.py` separate keeps code organized — when project grows, all database work stays in one place.

</details>

<details>
<summary>2. What does `cursor.lastrowid` do and where does it come from?</summary>

When you `INSERT` and `id INTEGER PRIMARY KEY AUTOINCREMENT` is set, SQLite automatically increments the new row's ID (1, 2, 3...). `cursor.lastrowid` tells you what ID was created for this particular insert. It's needed because we want the new stock's ID so we can `SELECT` and return the full row (user wants the whole object, not just the ID).

</details>

<details>
<summary>3. How does `sector` filter get added to the query? What's `?`'s role?</summary>

Query starts as `SELECT * FROM stocks WHERE 1=1` (dummy). If user sends `?sector=Oil`, then `if sector:` is true, and `query += " AND sector = ?"` happens, and `params.append(sector)` adds the value. Final query: `SELECT * FROM stocks WHERE 1=1 AND sector = ?`. This is **dynamic SQL building** — filters added based on user input. `?` is a placeholder (learned in 1.4) — user's sector value goes as just a value, not as SQL command (SQL injection safe).

</details>

<details>
<summary>4. How is `active_only=true` handled in SQL, and why?</summary>

SQLite has no boolean type. `active` column is INTEGER (1 or 0). User sends `?active_only=true` — FastAPI converts it to Python boolean `True` (learned in 1.1). Then code checks `if active_only:` and adds `AND active = 1` to SQL. Since SQLite stores/reads `True` as `1`, this works. Python automatically treats `if active_only:` `True` as truthy.

</details>

<details>
<summary>5. Which response codes appeared in this part — 201, 409, 422, 404 — and when?</summary>

**201** — when a new stock is successfully created (`POST`). **422** — when validation fails, like `"last_price": "abc"` (FastAPI/Pydantic rejects it). **409** — when `symbol` UNIQUE constraint is violated (duplicate symbol). **404** — when `GET /api/stocks/999` and that ID doesn't exist. **200** — normal successful GET. All learned in 1.3 as status codes — now showing up practically.

</details>

<details>
<summary>6. Why is data still available after server restart, unlike the dict before?</summary>

Before, data was in a Python dict — only in RAM, gone on restart. Now data is written to a SQLite **file** (`data/stocks.db`) — permanently on disk. Restarting keeps the file safe, and `get_conn()` opens that same file and returns the same data. That's SQLite's core benefit — **disk-based persistence, zero config**.

</details>
