## Part 2 â€” Verify Data Persistence (The Important Test)

This is the test that proves the volume mount actually works. Do it deliberately; don't skip it.

```bash
# 1. Make sure DOCKER stock exists (from Step 3 above)
curl -s http://localhost:8000/api/stocks | python -m json.tool

# 2. Check the DB file on the host
ls -la data/
# Expected: settings.db (timestamp = just now)

# 3. Take the container DOWN (removes container, keeps data/)
docker compose down

# 4. Confirm container is gone
docker compose ps
# Expected: no services running

# 5. Confirm DB file is STILL on host (this is the proof)
ls -la data/
# Expected: settings.db still present

# 6. Start again (no --build; reuse image)
docker compose up -d

# 7. Is the data back?
curl -s http://localhost:8000/api/stocks | python -m json.tool
# Expected: DOCKER stock still present -> persistence works
```

**Pass condition:** Step 7 returns the DOCKER stock. If it's gone, your volume mount path doesn't match where the app writes the DB. Re-check `app/db.py`'s `DB_PATH` against the mount target `./data:/app/data`.

### Extra: prove it survives container deletion too

```bash
# Find the container id
docker ps -a

# Delete the container entirely (not just stop)
docker rm <container_id>

# Start fresh from the image
docker compose up -d

# Data should still be there (volume mount = host disk)
curl -s http://localhost:8000/api/stocks
```

This proves the data is **not** inside the container â€” it's on the host. The container is disposable; the data is not.

## Part 3 â€” What Breaks Inside a Container?

Common failures and fixes, drawn from real containerization mistakes:

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| `500 Internal Server Error` on POST | DB path relative issue / folder missing | Verify `DB_PATH` lands in `/app/data`; `os.makedirs(DATA_DIR, exist_ok=True)` |
| `Connection refused` on localhost:8000 | Port not published | Check `ports: "8000:8000"` and container is running (`docker compose ps`) |
| Port 8000 already in use | Host conflict | `docker compose down` first, or use `"8001:8000"` |
| `Permission denied` on `data/` | Linux file ownership mismatch | `chmod -R 777 data/` on host, or run container as matching user |
| `/health` works but `/api/scan` fails | Missing package in container | Add to `requirements.txt`, rebuild with `--build` |
| DB file not visible inside container | Volume mount path wrong | Double-check `./data:/app/data` matches app's write path |
| Image huge (500MB+) | `venv/` or `__pycache__/` copied | Add them to `.dockerignore`, rebuild |
| Code changes not reflected | Forgot `--build` | `docker compose up --build` |
| Container exits immediately | CMD error / import error | `docker compose logs backend` to see traceback |

Debugging toolkit:

```bash
docker compose logs backend          # stdout/stderr from app
docker compose exec backend bash     # shell inside running container
docker compose exec backend python -c "import app.main; print('import ok')"
docker inspect trading-backend-basic # full container config
```

### TradeStack-specific notes

- **WAL mode SQLite** (`trades.db`): SQLite with WAL creates `trades.db-wal` and `trades.db-shm` sidecar files in the same folder. The volume mount `./data:/app/data` captures all of them, so persistence still works. Just don't delete individual sidecar files.
- **Larger dependency set**: TradeStack's `requirements.txt` includes more (pandas, numpy, possibly TA-lib). Build will be slower; layer caching (4.2) keeps rebuilds fast.
- **Port 5000 vs 8000**: TradeStack convention is 5000. Map host 5000 â†’ container 8000 (app still listens on 8000 inside).
- **Frontend not included**: This phase containerizes the backend only. Frontend (Next.js) gets its own Dockerfile later â€” out of scope here.

## In Your Own Words

1. How do you verify that data persistence actually works?

<details>
<summary>Sample Answer</summary>

**Answer:** Seed data via API, run `docker compose down`, confirm the DB file still exists in `./data/` on the host, run `docker compose up -d`, then query the API again. If the seeded data returns, the volume mount is working. For extra proof, delete the container entirely with `docker rm` and restart â€” data should still survive.

</details>

2. Why might an endpoint work on your host but fail inside the container?

<details>
<summary>Sample Answer</summary>

**Answer:** Usually one of: a package missing from `requirements.txt` (works on host because installed globally), a wrong DB path that lands outside the volume mount, a port binding to `127.0.0.1` instead of `0.0.0.0`, or file-permission issues on Linux. Check `docker compose logs` for the traceback.

</details>

3. What changes when moving the Dockerfile from the Phase 1 project to TradeStack?

<details>
<summary>Sample Answer</summary>

**Answer:** Three things: the CMD entry point changes from `app.main:app` to `server:app`; the build context changes from `.` to `./backend` (since the Dockerfile lives in `backend/`); and the host port changes from 8000 to 5000. The Dockerfile instructions themselves stay identical.

</details>

4. Why does SQLite WAL mode not break the volume mount?

<details>
<summary>Sample Answer</summary>

**Answer:** WAL mode creates sidecar files (`trades.db-wal`, `trades.db-shm`) in the same directory as the main DB. Since the whole `data/` folder is mounted, all sidecar files are captured together. As long as you mount the folder (not a single file), persistence works.

</details>

5. What's the difference between `docker compose down` and `docker compose down -v`?

<details>
<summary>Sample Answer</summary>

**Answer:** `down` stops and removes containers but keeps bind-mounted host folders (`./data`) and named volumes. `down -v` also removes named volumes. Bind mounts (our `./data:/app/data`) are never removed by either â€” they live on the host. So our SQLite data survives both.

</details>
