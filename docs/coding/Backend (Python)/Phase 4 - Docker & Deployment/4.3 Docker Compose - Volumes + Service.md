In 4.2 you built the image with a `Dockerfile` and ran it with `docker run -p 8000:8000`. That works, but typing that every time is annoying, and worse â€” when the container is removed, any data written inside it (your SQLite DB) is **gone forever**. Docker Compose solves both: one YAML file declares how to run the service, and **volume mounts** let SQLite data live on your host machine so it survives container restarts.

# 4.3 Docker Compose â€” Volumes + Service

## Think â€” The Launch Button

Imagine your app needs three things to start: build the image, map ports, mount a data folder. Doing these by hand (`docker build`, `docker run -p ... -v ...`) is like starting a car by hot-wiring it each morning. Docker Compose is the **ignition key** â€” one turn (`docker compose up`) does all of it, every time, identically. The `docker-compose.yml` file is the key's blueprint.

## Step 1 â€” Write `docker-compose.yml`

Create `docker-compose.yml` in the project root (next to `Dockerfile`):

```yaml
version: "3.8"

services:
  backend:
    build: .
    container_name: trading-backend-basic
    ports:
      - "8000:8000"
    volumes:
      - ./data:/app/data
    environment:
      - PYTHONUNBUFFERED=1
    restart: unless-stopped
```

## Step 2 â€” Understand Every Line

### `version: "3.8"`

- Declares the Compose file format version. `3.8` is stable and supported by modern Docker. Newer Compose (v2) even ignores this line, but keeping it is harmless and documents intent.

### `services:`

- Top-level key listing the containers (services) to run. We have one: `backend`.
- TradeStack would have two: `backend` + `redis` (see preview below).

### `backend:`

- The service name. Used as the DNS hostname when services talk to each other (e.g., backend can reach `redis` by name).

### `build: .`

- Tells Compose to build the image from the `Dockerfile` in the current directory (`.`).
- Equivalent to `docker build -t ... .`. Compose tags it automatically.
- Alternative: `build: { context: ., dockerfile: Dockerfile }` â€” same thing, more verbose.

### `container_name: trading-backend-basic`

- Fixes the container's name. Without it, Docker generates a random name like `trading-backend-basic-backend-1` or `focused_hodgkin`.
- A fixed name makes `docker logs trading-backend-basic` and `docker stop trading-backend-basic` predictable.

### `ports:` / `- "8000:8000"`

- **Port mapping**: `"HOST:CONTAINER"`.
- Host (your laptop) port `8000` â†’ container port `8000`.
- So `http://localhost:8000` on your laptop reaches the app inside the container.
- If host 8000 is busy, change to `"8001:8000"` (host 8001 â†’ container 8000). The app inside still thinks it's on 8000.

### `volumes:` / `- ./data:/app/data`

- **The persistence line.** Mounts host folder `./data` to container folder `/app/data`.
- Bidirectional: files written in container's `/app/data` appear on host's `./data`, and vice versa.
- Your Phase 1 code writes SQLite to `./data/settings.db`. Inside the container that path becomes `/app/data/settings.db` â€” which is the mounted folder. So the DB is actually written to your **host** disk.
- Delete the container, the DB survives. That's the whole point.

### `environment:` / `- PYTHONUNBUFFERED=1`

- Sets environment variables inside the container. Here, unbuffered Python output so logs appear immediately.
- For secrets, use an `.env` file: `env_file: .env` (never commit `.env`).

### `restart: unless-stopped`

- Restart policy: if the container crashes (or Docker daemon restarts), Compose brings it back up.
- `unless-stopped` = restart on crash, but stay down if you explicitly `docker compose stop`/`down`.
- Alternative `always` = restart even after manual stop (used for daemons). `no` = never restart (default).

## Step 3 â€” Make Sure DB Path Matches

Your Phase 1 code must write the SQLite DB to a path that lands inside the mounted folder. Check `app/db.py`:

```python
import os

# Resolve to ./data/settings.db relative to project root
BASE_DIR = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
DATA_DIR = os.path.join(BASE_DIR, "data")
DB_PATH = os.path.join(DATA_DIR, "settings.db")

os.makedirs(DATA_DIR, exist_ok=True)
```

Inside the container, `BASE_DIR` = `/app`, so `DATA_DIR` = `/app/data` â€” exactly the mount target. If your code instead writes to a different path (e.g., `/tmp/settings.db`), the volume mount won't capture it and data won't persist. **The mount target must match where the app writes.**

## Step 4 â€” Run and Test

### Start (build + run):

```bash
docker compose up --build
```

- `--build` = rebuild the image first (needed when Dockerfile or code changed).
- First run builds; later runs use cache.

### Start in background (detached):

```bash
docker compose up -d
```

### Test endpoints:

```bash
# Health check
curl http://localhost:8000/health

# Swagger UI
# open http://localhost:8000/docs

# Scan endpoint
curl "http://localhost:8000/api/scan?min_rsi=0&max_rsi=30"
```

### Seed data:

```bash
curl -X POST http://localhost:8000/api/stocks \
  -H "Content-Type: application/json" \
  -d '{"symbol": "DOCKER", "name": "Docker Test", "sector": "IT"}'
```

### Verify persistence (the key test):

```bash
# 1. Check DB file appeared on host
ls -la data/
# Expected: settings.db (created by the app, written to host via mount)

# 2. Stop and remove the container
docker compose down

# 3. Start again (no --build needed)
docker compose up -d

# 4. Is the data still there?
curl http://localhost:8000/api/stocks
# Expected: DOCKER stock still present -> volume mount works
```

If `DOCKER` comes back after `down`/`up` â†’ persistence is working. If it's gone â†’ check the mount path matches your DB path.

### Logs and status:

```bash
docker compose logs -f backend     # follow logs
docker compose ps                  # service status
docker compose restart backend     # restart just this service
```

### Stop:

```bash
docker compose down                # stop + remove containers (volumes/data stay)
docker compose down -v             # also remove named volumes (NOT bind mounts; data/ stays)
```

Note: `down` removes containers but **not** the bind-mounted `./data` folder. Your DB survives.

## Step 5 â€” Multi-Service Preview (TradeStack)

TradeStack needs a backend + Redis (for caching/pub-sub). The compose file grows:

```yaml
version: "3.8"

services:
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    container_name: tradestack-backend
    ports:
      - "5000:8000"            # TradeStack port 5000
    volumes:
      - ./data:/app/data       # TradeStack's data/ folder
    environment:
      - REDIS_URL=redis://redis:6379
    depends_on:
      - redis
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    container_name: tradestack-redis
    ports:
      - "6379:6379"
    restart: unless-stopped
```

Key additions:
- **`build.context: ./backend`** â€” Dockerfile lives in `backend/`, not root.
- **`depends_on`** â€” Redis starts before backend. (Note: `depends_on` only controls start order, not readiness; add healthchecks for real readiness.)
- **`image: redis:7-alpine`** â€” use a pre-built image instead of building. `alpine` = tiny (~30MB).
- **`REDIS_URL=redis://redis:6379`** â€” hostname `redis` resolves to the redis service container. No IP needed.
- Port mapping `5000:8000` â€” host 5000 (TradeStack convention) â†’ container 8000.

## Common Mistakes

1. **Wrong volume mount direction** â€” `./data:/app/data` means host `./data` â†’ container `/app/data`. Reversing breaks everything.
2. **Mount target doesn't match DB path** â€” app writes to `/app/db.sqlite` but mount is `/app/data`. Data not persisted. Align them.
3. **Port conflict on host** â€” another process on 8000. Use `8001:8000` or stop the conflict.
4. **Forgetting `--build` after Dockerfile change** â€” Compose uses cached image; changes don't appear. Always `--build` when Dockerfile changes.
5. **`restart: always` in dev** â€” container keeps restarting while you're debugging. Use `unless-stopped` or `no` in dev.
6. **Committing `.env`** â€” secrets leak. Add `.env` to `.gitignore` and use `env_file`.
7. **`depends_on` assumed to mean "ready"** â€” it only means "started." Add healthchecks for true readiness.
8. **Thinking `docker compose down` deletes data** â€” bind mounts (`./data`) survive. Named volumes need `-v`.

## What It Is NOT

- âŒ **Production deployment** â€” no reverse proxy, SSL, or load balancer here.
- âŒ **Secrets management** â€” `.env` files only; real prod uses vaults.
- âŒ **Database as separate service** â€” SQLite is a file; Postgres/MySQL would be their own service.
- âŒ **Kubernetes** â€” Compose runs on one machine; K8s orchestrates many.

## Nutshell

- `docker-compose.yml` declares service: build, ports, volumes, env, restart.
- `./data:/app/data` volume mount = SQLite persists across `down`/`up`.
- One command: `docker compose up --build` starts everything.
- TradeStack = same YAML + `context: ./backend` + `depends_on: redis` + port 5000.

## In Your Own Words

1. What does a volume mount do, and why do we need it for SQLite?

<details>
<summary>Sample Answer</summary>

**Answer:** A volume mount maps a host folder into the container (`./data:/app/data`). The app writes the SQLite DB into that folder, but the file actually lives on the host. So when the container is deleted, the DB survives and reappears on next run. Without it, the DB lives inside the container's writable layer and is lost on `docker compose down`.

</details>

2. What's the difference between `docker compose up` and `docker compose up --build`?

<details>
<summary>Sample Answer</summary>

**Answer:** `up` starts containers from the existing (cached) image. `up --build` rebuilds the image from the Dockerfile first, then starts. Use `--build` whenever you change the Dockerfile or dependencies; plain `up` is fine for code-only changes if using volume-mounted source (not here, since we COPY code into image).

</details>

3. What does `restart: unless-stopped` mean?

<details>
<summary>Sample Answer</summary>

**Answer:** The container restarts automatically if it crashes or if Docker restarts, but stays stopped if you explicitly stop it with `docker compose stop`/`down`. Use `always` for daemons that must run after manual stops; `no` (default) for dev where you don't want auto-restart.

</details>

4. Why is `depends_on` alone not enough for service readiness?

<details>
<summary>Sample Answer</summary>

**Answer:** `depends_on` only controls start order â€” it ensures Redis starts before backend. It does NOT wait for Redis to be ready to accept connections. The backend might start and fail to connect. Add a `healthcheck` to Redis and `condition: service_healthy` in depends_on for true readiness.

</details>

5. How would you change the host port if 8000 is already in use?

<details>
<summary>Sample Answer</summary>

**Answer:** Change the left side of the mapping: `"8001:8000"`. Host (your browser) uses 8001; container (app) still uses 8000. The app is unaware of the change. Access via `http://localhost:8001`.

</details>
