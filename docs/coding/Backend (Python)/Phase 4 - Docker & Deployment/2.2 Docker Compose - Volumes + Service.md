The image is built with Dockerfile. Now running it with `docker-compose.yml` is easier — one command to start, one to stop. And with **volume mount**, SQLite data persists outside the container too.

---

## Step 1: Write `docker-compose.yml`

Create `docker-compose.yml` in your project folder root:

```yaml
version: "3.8"

services:
  backend:
    build: .
    container_name: trading-backend-basic
    ports:
      - "8000:8000"
    volumes:
      - ./data:/app/data
    environment:
      - PYTHONUNBUFFERED=1
    restart: unless-stopped
```

---

## Understand Each Line

```yaml
version: "3.8"
```
- Compose file version. `3.8` = Docker's stable version. Works on most setups.

```yaml
services:
  backend:
```
- One service: `backend`. TradeStack would have 2 services (backend + frontend), but here only backend.

```yaml
    build: .
```
- `.` = use the current folder's `Dockerfile` for building.
- Alternatively `build: { context: ., dockerfile: Dockerfile }` works too, but `.` shortcut works fine.

```yaml
    container_name: trading-backend-basic
```
- Fix the container's name. If not set, Docker gives a random name ("focused_hodgkin" etc.). Debugging is easier with a fixed name.

```yaml
    ports:
      - "8000:8000"
```
- **Port mapping**: `host:container`.
  - Host (your laptop) = `8000`
  - Container (inside image) = `8000`
  - Means: browser `http://localhost:8000` reaches the container.

```yaml
    volumes:
      - ./data:/app/data
```
- **Volume mount**: `./data` (host) → `/app/data` (container).
  - Whatever is in your host's `./data` folder shows up in container's `/app/data`.
  - SQLite DB — if your code writes DB to `./data/settings.db` (seen in Phase 1), it goes to `/app/data/settings.db` inside the container too.
  - Even if container is deleted, DB stays on the host.

```yaml
    environment:
      - PYTHONUNBUFFERED=1
```
- Logs show immediately (reduces buffering). Helps debugging.
- `PYTHONUNBUFFERED=1` makes Python flush stdout/stderr immediately.

```yaml
    restart: unless-stopped
```
- If container crashes, it restarts automatically. `docker stop` or system shutdown will stop it.

## Step 2: Check SQLite DB Path Connection

In the Phase 1 project (from `1.5.2` to `1.5.5`), what's the DB path? Check:

```python
# See in app/db.py or app/models.py from Phase 1
DB_PATH = os.path.join(os.path.dirname(__file__), "..", "data", "settings.db")
```

If the DB path is `./data/settings.db`, the volume mount `./data:/app/data` will work. The DB is written on the host's `./data/` folder too.

## Step 3: Run and Test

### Start:

```bash
docker compose up --build
```
- `--build` = rebuild image first (when Dockerfile changes).
- First time it builds, later times it uses cache.

### Test endpoints:

```bash
# Health check
curl http://localhost:8000/health

# API docs (Swagger)
open http://localhost:8000/docs

# Scan endpoint
curl "http://localhost:8000/api/scan?min_rsi=0&max_rsi=30"
```

### Verify data persistence:

```bash
# Seed some data through API
curl -X POST http://localhost:8000/api/stocks -H "Content-Type: application/json" -d '{"symbol":"TEST","name":"Test Stock","sector":"IT"}'

# Check host machine: was DB created in data/ folder?
ls -la data/

# Stop container
docker compose down

# Start again — where did the data go?
docker compose up

# DB comes back because of volume mount
curl http://localhost:8000/api/stocks
```

Expected: `TEST` stock still shows even after `docker compose down`.

## Common Mistakes

1. **Wrong volume mount path** — `./data:/app/data` means `./data` is host path, `/app/data` is container path. Must match your Phase 1 project structure.
2. **`build: .` vs `build:`** — both work. Compose auto-detects `Dockerfile`.
3. **Port conflict** — if host port 8000 is used by another process, you get an error. You can use `8001:8000`.
4. **DB file permissions** — on Linux, Docker user might be different. If permission denied, run `chmod -R 777 data/`.
5. **`restart: always` vs `unless-stopped`** — `always` = starts even on system reboot. `unless-stopped` = stays until manually stopped.
6. **Missing environment variable** — if your app needs `DATABASE_URL` env var (Phase 1 doesn't), add it.

## Multi-service Extension (Preview — TradeStack)

TradeStack's compose looks like:

```yaml
services:
  backend:
    build: ./backend
    ports:
      - "5000:8000"
    volumes:
      - ./backend/data:/app/data
    depends_on:
      - redis

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
```

- `depends_on` = specifies order. Redis starts first, then backend.
- TradeStack's `docker-compose.yml` looks like this (minus frontend for now).

---

## What It Is NOT

- ❌ **Production deployment config** — no nginx, no SSL, no healthcheck
- ❌ **Secrets management** — manage via `.env` files only
- ❌ **Database as separate service** — SQLite = file-based. Postgres/MySQL would be separate services

---

## Nutshell

- `docker-compose.yml` = build config, ports, volumes, env all in one file.
- `./data:/app/data` volume mount = SQLite data persists across container restarts.
- `docker compose up --build` → `curl localhost:8000/health` verify → seed → `docker compose down` → `up` again → data persists.
- TradeStack bridge = same YAML, just `./backend` context, `depends_on`, and different port.
