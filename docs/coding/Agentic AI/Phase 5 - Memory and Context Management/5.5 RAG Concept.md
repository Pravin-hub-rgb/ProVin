You have system prompts for instructions. You have conversation history for recent context. But what if your agent needs to know about a thousand-page document? Or your entire codebase? Or a library's full API reference? That stuff will never fit in a context window.

Enter **RAG — Retrieval Augmented Generation**. The idea is simple: instead of stuffing everything into the prompt, store your documents in a database and retrieve only the relevant parts when the agent needs them.

Here's the mental model. Imagine you're a mechanic. A customer walks in with a weird engine noise. You don't carry the entire service manual for every car model in your head. But you have a computer where you can search for "Honda Civic 2018 engine knock diagnosis" and get exactly the page you need. That's RAG. You don't memorize everything — you search for what's relevant at the moment.

![RAG Flow — Query → Embed → Search Vector DB → Retrieve Relevant Chunks → Inject into Prompt → LLM Answers](/diagrams/agenticai/rag-flow.svg)

Technically, RAG works like this. You take your documents, split them into chunks, and store each chunk in a vector database along with an embedding (a numerical representation of the text). When the agent gets a question, you convert that question into an embedding too, then find the chunks whose embeddings are most similar. Those chunks get injected into the prompt alongside the system message and conversation history.

The agent never sees the whole document. It only sees the chunks you retrieved — usually just a few thousand tokens' worth. That's enough to answer the question without overflowing the context window.

You've seen this in action already. When Cline or opencode searches your project files to understand your codebase before making a change, that's RAG. It retrieves relevant files, reads them, and uses that context to answer your question. Same with tools like ChatGPT's "upload a file" feature — it chunks your document and retrieves relevant pieces as you ask questions.

Why does this matter for you as an agent builder? Because RAG is how you make agents that can work with knowledge bases that would never fit in a prompt. Your agent doesn't need to know everything upfront. It just needs to know how to find what's relevant when it needs it.

You now know the pieces: models, agents, tool calling, memory. In Phase 6, we'll build three real working agents that use all of this together — no more theory, just code.

## What It Is NOT

RAG is **not** a model, an API, or a service. It's an architecture pattern — a way of connecting a retrieval system (like a vector database) with a generative model. You don't "buy RAG" or "use RAG API." You build it. You can implement RAG with any LLM, any embedding model, and any database. It's also not a replacement for fine-tuning — they solve different problems. RAG is about giving the model access to documents at query time; fine-tuning changes the model's weights permanently.

### In Your Own Words

<details>
<summary>1. What problem does RAG solve that conversation history and system prompts can't?</summary>

**Sample Answer:** RAG solves the problem of needing access to information that's too large to fit in the context window — like a thousand-page manual, an entire codebase, or a library of support articles. Conversation history handles recent turns, and system prompts handle instructions, but neither can give the agent access to a massive knowledge base on demand.

</details>

<details>
<summary>2. Describe RAG in one sentence to someone who has never heard of it.</summary>

**Sample Answer:** RAG is a technique where you search a database for relevant information and inject it into the model's prompt so it can answer based on real documents instead of relying solely on what it learned during training.

</details>

<details>
<summary>3. How is RAG different from just putting a document in the system prompt?</summary>

**Sample Answer:** RAG retrieves only the most relevant chunks instead of sending the entire document every time. It's like having a librarian fetch the right page for you versus carrying the whole library on your back. This makes it efficient, scalable, and able to work with document collections that dwarf any context window.

</details>

<details>
<summary>4. Can you think of a situation where RAG would give a wrong or misleading answer?</summary>

**Sample Answer:** If the retrieval step returns irrelevant chunks (poor embeddings, bad chunking, or an ambiguous query), the model will try to answer based on unrelated information. It's like asking a librarian for a book on engines and getting a cookbook — the model will try to make it work but the answer won't make sense. Garbage in, garbage out applies to retrieval too.

</details>

<details>
<summary>5. When would you NOT use RAG and just put the information in the prompt instead?</summary>

**Sample Answer:** When the information is small, stable, and used every single time — like a short style guide, a few API signatures, or a company tone-of-voice document. If it fits in the context window and doesn't change, put it in the system prompt. RAG adds complexity (database, embeddings, retrieval logic) that isn't worth it for a few paragraphs of static text.

</details>
