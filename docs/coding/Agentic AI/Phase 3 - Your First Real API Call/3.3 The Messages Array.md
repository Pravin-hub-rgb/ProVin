That first call worked. You sent a message, the model replied. Simple on the surface. But the real magic is in that `messages` array we passed to the API. That array is the entire conversation — and understanding how it works is the key to everything else: multi-turn conversations, system prompts, tool calling, agents.

Let's take it apart properly.

# 3.3 The Messages Array

The most important part of that API call was the `messages` array. Let's understand it properly, because everything else we build — multi-turn conversations, system prompts, tool calling — depends on getting this right.

## Why an Array?

A single prompt-response exchange isn't very useful. You want to have a conversation, where each new message builds on everything said before. The `messages` array represents that history. Each element is one turn in the conversation.

The model doesn't remember anything between API calls. That's not a limitation — it's by design. Every request is stateless. If you want the model to know what was said earlier, you have to include it in the `messages` array. This is called **providing context**.

![The Messages Array Growing — Each Turn Appends User and Assistant Messages](/diagrams/agenticai/messages-array.svg)

Let's see what this looks like in practice with the dark/theme example from Phase 1. Here's how the messages array grows as you talk:

**Turn 1 — Your first request:**
```json
[
  { "role": "user", "content": "Create a dark theme and a light theme for this website." }
]
```

**Turn 2 — After Cline responds with the dark theme CSS:**
```json
[
  { "role": "user", "content": "Create a dark theme and a light theme for this website." },
  { "role": "assistant", "content": "Here's the dark theme CSS: ..." },
  { "role": "user", "content": "Make the dark background slightly lighter." }
]
```

**Turn 3 — After Cline updates it and you follow up:**
```json
[
  { "role": "user", "content": "Create a dark theme and a light theme for this website." },
  { "role": "assistant", "content": "Here's the dark theme CSS: ..." },
  { "role": "user", "content": "Make the dark background slightly lighter." },
  { "role": "assistant", "content": "Updated the background to #1a1a3e." },
  { "role": "user", "content": "Now do the same for the light theme." }
]
```

Each turn, YOU are responsible for appending both the assistant's response and your new message. The API never does this for you. If you forget to include a turn, the model acts like it never happened. This is why every chat UI — including Cline and opencode — maintains the conversation history on its end and sends it with every request.

Think of it like email. Each time you send an email to someone, you might include the previous email thread below your new message. Without that thread, the recipient has no idea what you're talking about. The `messages` array is your email thread. You're the one who keeps the thread going.

## Roles

Each message has a `role` field. Two roles matter right now:

- **`"user"`**: Something a human said. That's you.
- **`"assistant"`**: Something the model said. That's the AI.

The model learns from the alternating pattern. You send user, it responds assistant. You send user again, it responds assistant again. The conversation alternates.

Here's what a two-turn conversation looks like:

```javascript
import Groq from "groq-sdk";
import dotenv from "dotenv";
dotenv.config();

const client = new Groq({ apiKey: process.env.GROQ_API_KEY });

const completion = await client.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: [
    { role: "user", content: "What's the capital of France?" },
    { role: "assistant", content: "The capital of France is Paris." },
    { role: "user", content: "What's the population of that city?" }
  ],
});

console.log(completion.choices[0].message.content);
```

The model sees the full history: its previous answer, your follow-up question, and the context of what "that city" refers to. Without the assistant's previous response in the array, the model wouldn't know what "that city" meant.

Try removing the assistant's turn and see what happens.

## Building a Conversation Manually

In a real app, you'd build the messages array dynamically. Here's a simple chat loop:

```javascript
import Groq from "groq-sdk";
import dotenv from "dotenv";
dotenv.config();

const client = new Groq({ apiKey: process.env.GROQ_API_KEY });
const conversation = [];

async function ask(question) {
  conversation.push({ role: "user", content: question });

  const response = await client.chat.completions.create({
    model: "llama-3.3-70b-versatile",
    messages: conversation,
  });

  const reply = response.choices[0].message.content;
  conversation.push({ role: "assistant", content: reply });
  return reply;
}

const answer1 = await ask("Name three programming languages.");
console.log("First answer:", answer1);

const answer2 = await ask("Which one is best for beginners?");
console.log("Second answer:", answer2);
```

Each call appends to `conversation`, so the model always has full context. This is exactly how every chatbot works at the most basic level.

## The System Prompt

You might have noticed the `messages` array so far only has `"user"` and `"assistant"` roles. There's a third role: `"system"`. The **system prompt** is a special instruction that sets the model's behavior — it's placed at the very start of the messages array and applies to the entire conversation.

Unlike Anthropic's API (which has a separate `system` parameter), Groq uses the OpenAI-compatible format where the system prompt is just another message with role `"system"`:

```javascript
const completion = await client.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: [
    { role: "system", content: "You are a grumpy librarian. Answer every question with a sigh and some mild annoyance." },
    { role: "user", content: "What's the capital of France?" }
  ],
});
```

The system prompt influences the model's tone, personality, constraints, and capabilities. It's where you'd put things like "You are a helpful coding assistant" or "Answer only in Spanish" or "Never mention that you're an AI."

The key difference: the **system prompt** stays constant across the whole conversation, while **messages** evolve turn by turn. Most AI coding tools put their entire personality and instruction set in the system prompt. Cline and opencode's system prompts are paragraphs long — they define the tool schema, the thinking protocol, the output format. Everything.

Now you know the input side. Let's look at the output — what the model actually sends back.

---

## What It Is NOT

The messages array is NOT stored by the API server. Each API call is completely stateless — the server processes what you send and forgets it immediately. If you send the same array twice, the server has no memory of the first call. This is by design: it keeps the architecture simple, scalable, and privacy-friendly. You are responsible for maintaining your own conversation history, just like you keep your own email inbox.

The messages array is also NOT a transcript the model "reads" like a human would. It's input data the model processes as context tokens. The model doesn't have a memory that "remembers" past turns; it's just seeing more text in the prompt window with each new message.

### In Your Own Words

<details>
<summary>1. What happens if you send two user messages in a row without an assistant response in between? Try it.</summary>

**Sample Answer:** The model will treat the two user messages as a single combined turn and respond once. It might get confused about which question to answer, or try to address both at once. The API expects alternating roles — user, assistant, user, assistant — and breaking that pattern can produce unpredictable responses, like two people talking at the same time in a meeting.

</details>

<details>
<summary>2. Why do you think the API requires you to send the full conversation history instead of maintaining state server-side?</summary>

**Sample Answer:** Stateless design is simpler, more scalable, and more reliable. If the server maintained state, you'd need session management, cleanup for abandoned conversations, and state syncing across multiple servers. It's like email vs a phone call — email requires you to include the thread each time, but you can forward it, archive it, and reference it anywhere without depending on the other person's server.

</details>

<details>
<summary>3. The conversation array keeps growing. What problems might that cause for long conversations?</summary>

**Sample Answer:** Every message costs tokens, and models have a maximum context window (typically 100K-200K tokens). Long conversations eventually hit this limit, forcing you to either truncate old messages, summarize earlier turns, or use techniques like sliding windows. Longer inputs also mean slower responses and higher costs — you pay for every token you send, not just the ones the model generates.

</details>

<details>
<summary>4. Some APIs (like Anthropic) have a dedicated `system` parameter separate from the messages array. In Groq's format, the system prompt is just another message with `role: "system"`. What advantage does the dedicated parameter approach have? What's simpler about putting it in messages?</summary>

**Sample Answer:** A dedicated `system` parameter keeps the instruction structurally separate from conversation turns, making it clearer which content is behavioral guidance vs user input. But putting it in the messages array (like Groq does) is simpler because there's only one data structure to manage — you just prepend a system message to your array and everything stays uniform. Both achieve the same result; it's a design preference by the API provider.

</details>

<details>
<summary>5. If you wanted the model to never say "I don't know", where would you put that instruction — in the system prompt or in a user message? Why?</summary>

**Sample Answer:** In the system prompt, because it's a persistent behavioral rule that should apply to every turn. A user message only applies to that specific exchange, and if the conversation moves on, the model might forget the instruction. The system prompt is like a job description — it sets expectations for the entire engagement — while a user message is like a single task request.

</details>
