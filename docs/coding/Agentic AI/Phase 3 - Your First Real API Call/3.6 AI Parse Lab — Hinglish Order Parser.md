## What We're Building

Ek simple Python script jo Hinglish order messages (like WhatsApp orders) ko structured format mein parse karega using OpenAI API.

**Example orders:**
- "Maine 2kg aalu aur 1 litr dudh mangi hai"
- "2 packets chai, 1 kg mangal sutra dhoti bhi chahiye"

**Goal:** Extract item name, quantity, and unit from messy Hinglish text.

## Step 2: Define the Data Model

Hum Pydantic use karenge — it ensures our parsed output is structured correctly.

```python
# 3.6-parse-lab.py
from pydantic import BaseModel, Field
from typing import List
import os
from openai import OpenAI

# Our structured output model
class OrderItem(BaseModel):
    item_name: str = Field(description="Name of the item in English (transliterated)")
    quantity: str = Field(description="Quantity as mentioned in the message (e.g., '2', '1', 'thoda sa')")
    unit: str = Field(description="Unit of measurement (e.g., 'kg', 'litre', 'packet', 'bottle')")

    model_config = {
        "json_schema_extra": {
            "examples": [
                {"item_name": "aalu", "quantity": "2", "unit": "kg"},
                {"item_name": "dudh", "quantity": "1", "unit": "litre"},
            ]
        }
    }

class OrderParseResponse(BaseModel):
    items: List[OrderItem]
```

## Step 3: The System Prompt

Yeh prompt batata hai model ko ki hum kya chahte hain — structured JSON return kare.

```python
SYSTEM_PROMPT = """
You are a Hinglish order parser. Parse the given Hinglish text message into structured order items.

For each item mentioned, extract:
- item_name: The name of the item (transliterated to English if in Hindi/Devanagari)
- quantity: The quantity as mentioned (e.g., "2", "1", "thoda sa", "bohot")
- unit: The unit of measurement (e.g., "kg", "litre", "packet", "bottle", "gmt", "no.")

Rules:
- If quantity is not explicitly mentioned, return "1" as default
- Normalize units: "litr" → "litre", "kg" stays "kg"
- For items without clear units, return "no." (meaning "number of items")
- Handle mixed scripts (Hinglish) gracefully

Return ONLY valid JSON matching the response schema. No extra text.
"""
```

## Step 4: The API Call

Ab hum Phase 3 ke concepts use karenge — messages array, JSON mode, response parsing.

```python
def parse_order(message: str) -> OrderParseResponse:
    client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))
    
    response = client.chat.completions.create(
        model="gpt-4o-2024-08-06",
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": message}
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name": "OrderParseResponse",
                "schema": {
                    "type": "object",
                    "properties": {
                        "items": {
                            "type": "array",
                            "items": {
                                "type": "object",
                                "properties": {
                                    "item_name": {"type": "string"},
                                    "quantity": {"type": "string"},
                                    "unit": {"type": "string"},
                                },
                                "required": ["item_name", "quantity", "unit"],
                            },
                        }
                    },
                    "required": ["items"],
                },
            }
        },
        temperature=0.1,  # low temperature for consistency
    )
    
    # Parse the response (Phase 3.4 concepts)
    content = response.choices[0].message.content
    return OrderParseResponse.model_validate_json(content)
```

## What This Teaches You

### JSON Schema Mode (Phase 3.5 Connection)
We use `response_format` with JSON Schema — this guarantees structured output. No more string parsing!

### Error Handling (Phase 3.5 Connection)
```python
try:
    result = parse_order("invalid message")
except Exception as e:
    print(f"Parse failed: {e}")
```

### Messages Array (Phase 3.3 Connection)
We have exactly 2 messages: system prompt + user message. This is the minimal pattern.

## What It Is NOT

- **NOT a complete ordering system.** We're only parsing — no database, no payment
- **NOT 100% accurate.** Models can hallucinate units. Production has validation rules after parsing
- **NOT optimized for speed.** Each call is sequential. Production uses batch processing

## In Your Own Words

<details>
<summary>1. Why do we use JSON Schema response format instead of asking the model to return JSON in the prompt?</summary>

JSON Schema enforces structure at the API level — if the model returns invalid JSON or missing fields, the API rejects it. In-prompt JSON parsing is unreliable.
</details>

<details>
<summary>2. What's the purpose of the SYSTEM_PROMPT vs. the user message?</summary>

System prompt defines the model's role and rules (always applied). User message is the actual input to parse. This separation keeps prompts clean and testable.
</details>

<details>
<summary>3. How would you handle an order with 50 items?</summary>

The API handles lists natively — we'd just get a larger `items` array back. No code changes needed. Production might limit to top-N or use pagination.
</details>

<details>
<summary>4. What does temperature=0.1 do here?</summary>

Low temperature makes the model more deterministic and consistent in parsing. High temperature might produce varied field names or structures — bad for structured data extraction.
</details>

<details>
<summary>5. How does this connect to what we learned in Phase 3.3-3.5?</summary>

Phase 3.3 taught us the messages array pattern. Phase 3.4 taught us to read raw response. Phase 3.5 taught us error handling. This lab combines all three: structured messages → JSON response → validation with error handling.
</details>
