The raw response tells you when everything went right — here's your text, here are your tokens, everything's fine. But real code needs to handle when things don't go right. API calls fail. Your key could be wrong, you could hit rate limits, the network could drop, the server could be overloaded. If you don't handle these, your app crashes with a cryptic error and your users see a stack trace.

Let's build some resilience into our code.

# 3.5 Handling Errors

Things will go wrong. Your API key will be invalid. You'll hit rate limits. The network will drop. The model will be overloaded. If you don't handle these gracefully, your app crashes and your users see a cryptic error message.

Let's look at what goes wrong and how to handle it.

## Wrong API Key

Run this:

```javascript
import Groq from "groq-sdk";
import dotenv from "dotenv";
dotenv.config();

const client = new Groq({ apiKey: "gsk-not-a-real-key" });

const completion = await client.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: [
    { role: "user", content: "Say hello." }
  ],
});
```

You'll get something like:

```
GroqError: 401 {"error":{"message":"Invalid API Key","type":"invalid_request_error","code":"invalid_api_key"}}
```

A `401` status code means "unauthorized". The API got your request but doesn't recognize your key. This is an **authentication error** — your key is wrong, expired, or missing.

## Rate Limits

If you hammer the API with too many requests too quickly, you'll get a `429` status code:

```
GroqError: 429 {"error":{"message":"Rate limit exceeded","type":"rate_limit_error"}}
```

Rate limits exist so one user can't overload the service. They vary by tier (free vs paid) and model. When you hit one, you need to wait and retry.

## Basic Error Handling with try/catch

The simplest way to handle errors is a `try/catch` block:

```javascript
import Groq from "groq-sdk";
import dotenv from "dotenv";
dotenv.config();

const client = new Groq({ apiKey: process.env.GROQ_API_KEY });

async function askModel(prompt) {
  try {
    const completion = await client.chat.completions.create({
      model: "llama-3.3-70b-versatile",
      messages: [
        { role: "user", content: prompt }
      ],
    });
    return completion.choices[0].message.content;
  } catch (error) {
    console.error("API call failed:", error.message);
    return "I'm sorry, I couldn't process that request.";
  }
}

const response = await askModel("What is the meaning of life?");
console.log(response);
```

The `try` block attempts the API call. If it succeeds, the function returns the response text. If it throws an error (network failure, invalid key, rate limit), execution jumps to the `catch` block, where we log the error and return a fallback message.

This is the absolute minimum. In a real app, you'd want to do different things for different error types.

## Handling Specific Errors

The Groq SDK throws `GroqError` objects with a `status` property. Let's handle each case differently:

```javascript
import Groq from "groq-sdk";
import dotenv from "dotenv";
dotenv.config();

const client = new Groq({ apiKey: process.env.GROQ_API_KEY });

async function askModel(prompt) {
  try {
    const completion = await client.chat.completions.create({
      model: "llama-3.3-70b-versatile",
      messages: [
        { role: "user", content: prompt }
      ],
    });
    return completion.choices[0].message.content;
  } catch (error) {
    if (error.status === 401) {
      return "Your API key is invalid. Check your .env file.";
    }
    if (error.status === 429) {
      console.warn("Rate limited. Waiting 5 seconds...");
      await new Promise(resolve => setTimeout(resolve, 5000));
      return askModel(prompt);
    }
    if (error.status === 400) {
      return "Bad request. Check your parameters.";
    }
    return `Unexpected error: ${error.message}`;
  }
}

const response = await askModel("What is the capital of Japan?");
console.log(response);
```

Here's what's going on:

- **401**: The API key is wrong. There's no point retrying — the user needs to fix the key.
- **429**: Rate limited. We wait 5 seconds (with a simple `setTimeout` wrapped in a Promise), then **retry the function recursively**. This is a basic retry strategy. In production you'd use exponential backoff and cap the number of retries.
- **400**: Bad request — your prompt may be too long, or your parameters invalid.
- **Everything else**: Network errors, server errors (5xx), etc. Log it and return a generic message.

## Why This Matters for Agents

When you build an agent (Phase 4 territory), it might make dozens or hundreds of API calls in sequence. If any one of those calls fails and you're not handling errors, the whole chain breaks. Rate limits are especially common when an agent is rapidly calling tools and feeding results back to the model.

Good error handling is what separates a demo from something you'd actually run in production.

---

Now you can talk to a model for free. You can pass conversation history, read the response, and handle failures. But talking isn't acting. An agent doesn't just chat — it calls functions, runs code, and affects the real world.

That's what Phase 4 is about: tool calling.

---

## What It Is NOT

Error handling is NOT about preventing errors — it's about recovering from them gracefully. You cannot prevent a network outage, a rate limit, or an invalid key rotation. What you can control is what your users see and whether your application keeps running. Good error handling turns a cryptic crash into a helpful message, like a pilot announcing a delay instead of silently cutting off the cabin lights.

A `try/catch` block is also NOT a substitute for input validation. If you can check whether a value is valid before making the API call (like verifying your API key isn't empty), do that instead. `try/catch` is a safety net, not a first line of defense.

### In Your Own Words

<details>
<summary>1. The retry code for rate limits calls `askModel(prompt)` recursively. What happens if you get rate limited 10 times in a row? How would you fix that?</summary>

**Sample Answer:** The function recurses 10 times, potentially hitting Node.js's call stack limit or taking an impractically long time. You'd fix it by adding a retry counter — pass an attempt number and stop after 3-5 retries. Also use exponential backoff (wait 1s, then 2s, then 4s...) instead of a fixed 5s delay to be kinder to the API server and more effective.

</details>

<details>
<summary>2. Why is a 401 error not worth retrying, but a 429 error is?</summary>

**Sample Answer:** A 401 means your API key is invalid — no amount of retries will fix a wrong key. A 429 means you're temporarily over the rate limit, which will resolve once you wait long enough. Retrying a 401 is like pressing the elevator button harder; retrying a 429 is like waiting for the next train.

</details>

<details>
<summary>3. What's another type of error you might encounter when making network requests? (Think outside the API itself.)</summary>

**Sample Answer:** DNS failures (can't resolve the API hostname), TCP connection timeouts (server unreachable), TLS/SSL errors (certificate issues), and proxy errors (corporate networks blocking the request). These aren't HTTP status codes — they're network-level failures that throw different types of errors, like `TypeError` or `FetchError`, which won't have a `status` property at all.

</details>

<details>
<summary>4. If you're building an agent that makes 50 API calls, would you rather have each call handle its own errors, or have a central error handler? Why?</summary>

**Sample Answer:** A central error handler is better because it keeps error handling logic in one place — consistent logging, retry logic, and fallback messages. If each call handles its own errors, you'll duplicate code and inevitably miss edge cases. Think of it like a building's fire alarm system vs individual smoke detectors in every room: you want both, but the central system provides coordinated response.

</details>

<details>
<summary>5. How would you test your error handling without actually making invalid API calls?</summary>

**Sample Answer:** You can mock the API call using a library like `vi.mock()` (Vitest) or `jest.mock()` (Jest) to throw specific errors without hitting the network. For a quick manual test, set your `.env` key to an invalid value or pass a deliberately wrong model name. You can also simulate a rate limit by making rapid requests in a loop — just be careful not to get your key temporarily blocked.

</details>
