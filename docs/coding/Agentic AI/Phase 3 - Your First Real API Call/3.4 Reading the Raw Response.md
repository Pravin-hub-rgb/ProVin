# 3.4 Reading the Raw Response

We already glimpsed the response object in 3.2. Now let's take it apart properly. Understanding the raw response is what separates people who think AI is magic from people who know it's just a JSON API.

## Log the Whole Thing

Run this:

```javascript
import Anthropic from "@anthropic-ai/sdk";
import dotenv from "dotenv";
dotenv.config();

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

const message = await client.messages.create({
  model: "claude-sonnet-4-20250514",
  max_tokens: 1024,
  messages: [
    { role: "user", content: "List three colors." }
  ],
});

// Dump everything
console.log(JSON.stringify(message, null, 2));
```

The `JSON.stringify(message, null, 2)` formats the object with 2-space indentation so it's readable. You'll see something like:

```json
{
  "id": "msg_01ABC123DEF456",
  "type": "message",
  "role": "assistant",
  "content": [
    {
      "type": "text",
      "text": "Here are three colors:\n\n1. Red\n2. Blue\n3. Green"
    }
  ],
  "model": "claude-sonnet-4-20250514",
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "usage": {
    "input_tokens": 10,
    "output_tokens": 24
  }
}
```

## Walking Through Every Field

### `id`
A unique identifier for this message response. Anthropic generates it server-side. It's useful for logging, debugging, and support tickets — if something goes wrong, you can reference this ID.

### `type`
Always `"message"` for this endpoint. There are other endpoint types (streaming events, etc.), but for a basic `messages.create()` call, this is what you get.

### `role`
The role of the entity that produced this content. It's `"assistant"` because the model is the assistant. This matters when you append the response to your conversation array — you'll push `{ role: message.role, content: message.content[0].text }` back into the array so the model sees its own previous response in the next turn.

### `content`
This is the payload you actually care about. It's an array of **content blocks**. Each block has a `type` field:

- **`"text"`**: Plain text output. The model's words. This is what you'll display to the user 90% of the time.
- **`"tool_use"`**: A request to call a tool. We'll cover this in Phase 4.

Each content block has block-specific fields. For text blocks, it's just `text`. For tool_use blocks, it's `name`, `input`, and `id`.

You access the text like this:

```javascript
message.content[0].text
```

But if there are multiple content blocks (e.g., text followed by a tool call), you'd need to iterate:

```javascript
for (const block of message.content) {
  if (block.type === "text") {
    console.log("Model says:", block.text);
  }
  if (block.type === "tool_use") {
    console.log("Model wants to call:", block.name);
  }
}
```

### `model`
Confirms which model produced the response. If you're trying different models, check this field to verify you're hitting the right one.

### `stop_reason`
Why the model stopped generating. This is useful for debugging:

| Value | Meaning |
|-------|---------|
| `"end_turn"` | The model finished its response naturally |
| `"max_tokens"` | The response was cut off because it hit your `max_tokens` limit |
| `"stop_sequence"` | The model encountered a custom stop sequence you defined |
| `"tool_use"` | The model is requesting to use a tool (more in Phase 4) |

If you see `"max_tokens"`, your response was truncated. Increase `max_tokens` or make your prompt more specific.

### `stop_sequence`
If you passed a `stop_sequences` parameter in your request (e.g., `stop_sequences: ["\n\n"]`), and the model stopped because it hit one, this field tells you which sequence it hit. Otherwise it's `null`.

### `usage`
Your bill. `input_tokens` is what you sent (your prompt + conversation history), `output_tokens` is what the model generated. Multiply by the per-token rate for your model to get the cost.

## What Cline and Kodu See

Every time Cline or Kodu or opencode calls a model, it gets back a response object just like this. It extracts `content[0].text`, checks `stop_reason` to see if the model finished or hit a limit, reads `usage` to track costs, and uses `role` to format the next request.

There's no secret sauce. It's the same JSON you're looking at right now. The difference is that coding tools wrap this in loops — they send a message, get a tool call, execute the tool, send the result back, get another response, and repeat until the task is done.

You now understand the bottom layer. Everything else is just orchestration.

Of course, orchestration doesn't matter if your code crashes. Let's look at what can go wrong.
