Now you know how to structure your input — the messages array with user and assistant roles, system prompts setting the tone. But what comes back? When the model responds, it sends a JSON object packed with useful information. Not just the text reply, but token counts, stop reasons, model metadata. The kind of stuff that demystifies how Cline, opencode, and other tools work.

Let's open the hood and look at the full response.

# 3.4 Reading the Raw Response

We already glimpsed the response object in 3.2. Now let's take it apart properly. Understanding the raw response is what separates people who think AI is magic from people who know it's just a JSON API.

## Log the Whole Thing

Run this:

```javascript
import Anthropic from "@anthropic-ai/sdk";
import dotenv from "dotenv";
dotenv.config();

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

const message = await client.messages.create({
  model: "claude-sonnet-4-20250514",
  max_tokens: 1024,
  messages: [
    { role: "user", content: "List three colors." }
  ],
});

// Dump everything
console.log(JSON.stringify(message, null, 2));
```

The `JSON.stringify(message, null, 2)` formats the object with 2-space indentation so it's readable. You'll see something like:

```json
{

  "type": "message",
  "role": "assistant",
  "content": [
    {
      "type": "text",
      "text": "Here are three colors:\n\n1. Red\n2. Blue\n3. Green"

  }
```

## Walking Through Every Field

### `id`
A unique identifier for this message response. Anthropic generates it server-side. It's useful for logging, debugging, and support tickets — if something goes wrong, you can reference this ID.

### `type`
Always `"message"` for this endpoint. There are other endpoint types (streaming events, etc.), but for a basic `messages.create()` call, this is what you get.

### `role`
The role of the entity that produced this content. It's `"assistant"` because the model is the assistant. This matters when you append the response to your conversation array — you'll push `{ role: message.role, content: message.content[0].text }` back into the array so the model sees its own previous response in the next turn.

### `content`
This is the payload you actually care about. It's an array of **content blocks**. Each block has a `type` field:

- **`"text"`**: Plain text output. The model's words. This is what you'll display to the user 90% of the time.
- **`"tool_use"`**: A request to call a tool. We'll cover this in Phase 4.

Each content block has block-specific fields. For text blocks, it's just `text`. For tool_use blocks, it's `name`, `input`, and `id`.

You access the text like this:

```javascript
message.content[0].text
```

But if there are multiple content blocks (e.g., text followed by a tool call), you'd need to iterate:

```javascript
for (const block of message.content) {
  if (block.type === "text") {
    console.log("Model says:", block.text);
  }
  if (block.type === "tool_use") {
    console.log("Model wants to call:", block.name);
  }
}
```

### `model`
Confirms which model produced the response. If you're trying different models, check this field to verify you're hitting the right one.

### `stop_reason`
Why the model stopped generating. This is useful for debugging:

| Value | Meaning |
|-------|---------|
| `"end_turn"` | The model finished its response naturally |
| `"max_tokens"` | The response was cut off because it hit your `max_tokens` limit |
| `"stop_sequence"` | The model encountered a custom stop sequence you defined |
| `"tool_use"` | The model is requesting to use a tool (more in Phase 4) |

If you see `"max_tokens"`, your response was truncated. Increase `max_tokens` or make your prompt more specific.

### `stop_sequence`
If you passed a `stop_sequences` parameter in your request (e.g., `stop_sequences: ["\n\n"]`), and the model stopped because it hit one, this field tells you which sequence it hit. Otherwise it's `null`.

### `usage`
Your bill. `input_tokens` is what you sent (your prompt + conversation history), `output_tokens` is what the model generated. Multiply by the per-token rate for your model to get the cost.

## What Cline, opencode, and Kodu See

Every time Cline or Kodu or opencode calls a model, it gets back a response object just like this. It extracts `content[0].text`, checks `stop_reason` to see if the model finished or hit a limit, reads `usage` to track costs, and uses `role` to format the next request.

There's no secret sauce. It's the same JSON you're looking at right now. The difference is that coding tools wrap this in loops — they send a message, get a tool call, execute the tool, send the result back, get another response, and repeat until the task is done.

You now understand the bottom layer. Everything else is just orchestration.

Of course, orchestration doesn't matter if your code crashes. Let's look at what can go wrong.

---

## What It Is NOT

The response object is NOT just the text the model generated. It's a structured envelope with metadata that's critical in production. The `stop_reason` tells you if the response was truncated (`"max_tokens"`), the `usage` object is your billing receipt, and `model` confirms which engine processed your request. Ignoring these fields is like driving a car while only looking at the speedometer — you'll miss the fuel gauge and check engine light.

`JSON.stringify()` is also NOT something you'd use in a production app. It's a debugging tool to inspect what the API returns. In real code you'd access specific fields like `message.content[0].text` or iterate over content blocks, not dump the entire object.

### In Your Own Words

<details>
<summary>1. What would `message.content[0].type` be if the model wanted to call a function instead of returning text?</summary>

**Sample Answer:** It would be `"tool_use"` instead of `"text"`. The content block would also include fields like `name`, `input`, and `id` — the function name, its arguments, and a unique identifier. You'd check the `type` field before deciding how to handle each block, since text and tool calls need completely different processing.

</details>

<details>
<summary>2. If you see `"stop_reason": "max_tokens"`, what are two different ways to fix it?</summary>

**Sample Answer:** You can increase `max_tokens` in your request to give the model more room to finish, or make your prompt more specific so the model gives a shorter answer. If the model keeps hitting the limit, it might be trying to generate a longer response than you anticipated — think of it like a suitcase that's too small for everything you're trying to pack.

</details>

<details>
<summary>3. The `usage` object shows you input and output tokens. How would you calculate the total cost of a conversation with 5 turns?</summary>

**Sample Answer:** Sum the `input_tokens` and `output_tokens` across all 5 responses, then multiply by the per-token rate for your model. Each turn's `input_tokens` includes the entire conversation history so far, so costs grow with each turn. It's like a taxi meter — the fare increases not just for distance traveled, but for every mile driven total.

</details>

<details>
<summary>4. Why does the response include a `model` field? When would it be different from what you requested?</summary>

**Sample Answer:** The `model` field confirms which model actually processed your request. It might differ from what you requested if Anthropic performs automatic failover — if the model you requested is overloaded, they might route your request to a fallback model. The field is also useful for logging and auditing, especially if you're switching between models for A/B testing.

</details>

<details>
<summary>5. How would you extract *all* the text from a response that has multiple content blocks of different types?</summary>

**Sample Answer:** Iterate over `message.content` and collect text from only the blocks where `type === "text"`, joining them together. A for loop with a conditional check gives you full control: `for (const block of message.content) { if (block.type === "text") { result += block.text; } }`. This way you skip tool calls and other non-text blocks while capturing every word the model said.

</details>
