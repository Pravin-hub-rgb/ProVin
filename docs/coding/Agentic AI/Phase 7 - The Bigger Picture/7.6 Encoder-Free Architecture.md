From computer-use agents and long-horizon tasks, let's zoom into a quieter but equally important shift in how modern models are built. You've learned about agents, tools, memory — the software layer. But the models themselves are changing too. And one of the most interesting architectural shifts right now is something called **encoder-free architecture**.

You've probably used models that can "see" images or "hear" audio — showing ChatGPT a screenshot, or asking Claude to describe a diagram. But how does a model — which is fundamentally a text predictor — handle images and audio? The answer depends on how the model is built.

Most multimodal models use **separate encoders**. An encoder is like a translator — it takes a non-text input (an image, audio) and converts it into embeddings that the language model can understand. But newer models are moving toward a different approach where the same transformer handles everything. Let's understand both, because this distinction matters for where AI is heading.

# Traditional Multimodal Architecture (Encoder + LLM)

Older multimodal models usually have **separate encoders** for each modality.

```
Image
   │
Vision Encoder (CNN / ViT)
   │
Image Embeddings
   │
      ┌──────────────┐
Text ─►     LLM      ├──► Output
      └──────────────┘

Audio
   │
Audio Encoder
   │
Audio Embeddings
   │
      LLM
```

For example:
- Text → goes directly into the language model
- Image → first passes through a Vision Transformer (ViT)
- Audio → first passes through an audio encoder like Whisper

The LLM **never sees raw pixels or raw audio**. It only receives embeddings produced by those encoders. The encoder is doing the heavy lifting of converting pixels or waveforms into a language-like representation.

## Encoder-Free Architecture

In an encoder-free design, there is **no large, separate vision or audio encoder**.

Instead, the multimodal inputs are converted into tokens (or patches), and the **same transformer** processes everything alongside text.

```
Image
   │
Image Patches
   │
Tokenization
   │
      ┌─────────────────────┐
Text ─►                     │
Audio►     One Transformer  ├──► Output
Image►                     │
      └─────────────────────┘
```

The model learns to understand text, images, and audio using **one unified network** instead of multiple specialized networks.

### Image Example

Suppose you upload a picture of a dog sitting on grass.

**Traditional:**
```
Image → Vision Encoder → Embedding Vector → LLM → "This is a dog."
```

**Encoder-Free:**
```
Image → Split into patches → Patch Tokens → Transformer → "This is a dog."
```

The transformer itself learns what those image patches mean, without a separate vision model in front of it.

### Audio Example

**Traditional:**
```
Audio → Whisper Encoder → Embeddings → LLM
```

**Encoder-Free:**
```
Raw Audio → Audio Frames → Audio Tokens → Same Transformer
```

No separate audio model is needed. The same transformer processes audio tokens just like it processes text tokens.

## Why Is This Useful?

### 1. Simpler Architecture

Instead of managing three separate models — vision encoder, audio encoder, LLM — you have one model. One set of weights, one training process, one deployment.

### 2. Better Cross-Modal Reasoning

Since text, images, and audio are processed together in the same transformer, the model can naturally connect information across modalities. For example:

> "Look at this graph and explain why the speaker sounds surprised."

The model jointly reasons about both the graph and the audio because there's no encoder boundary between them.

### 3. End-to-End Training

Everything is trained together. The model doesn't rely on a separate pretrained encoder to extract features. The entire network learns from scratch (or from a unified pretraining objective), which can lead to more coherent representations.

### 4. Lower Latency

Fewer separate models to run means less inference overhead. No need to call a vision encoder, wait for its output, then feed that into the LLM. The encoder step is eliminated entirely.

## What Does "Raw" Input Actually Mean?

When people say models "ingest raw audio and image patches directly," they don't mean completely unprocessed bytes. Here's what actually happens:

- **Images** become small patches (like splitting a photo into a 16×16 grid of squares)
- **Audio** becomes short frames (splitting a waveform into tiny time chunks)

These are then turned into tokens — just like text tokens — that the transformer processes directly. The key point is that there's no large, pretrained vision or audio encoder sitting in front of the transformer. The tokenization step is minimal — it's about formatting, not understanding.

## A Real-World Analogy

Imagine you're learning from a textbook.

**Traditional approach:** You have three teachers — an English teacher, an Art teacher, and a Music teacher. Each teacher explains their subject to you separately, and then you combine what they said in your head.

**Encoder-free approach:** You learn directly from text, pictures, and sounds using the same brain. Over time, you naturally build connections between all three types of information because your brain processed all of them together, not through separate interpreters.

## In the Context of Gemma 4

When Google says Gemma 4 uses an **encoder-free architecture**, they're highlighting that its multimodal design doesn't depend on separate heavyweight vision or audio encoders. Instead, the model can process tokenized image patches and audio representations within a unified transformer, enabling multimodal understanding and reasoning in a single architecture. This can make training and deployment simpler while improving how the model integrates information across text, images, and audio.

This is where models are heading — not just smarter at text, but natively multimodal. And for someone building agents, this matters because future models will naturally understand images, audio, and video without extra plumbing. Your agent won't need to "describe" a screenshot to a separate vision model — it will just see it.

## What It Is NOT

Encoder-free architecture is not about removing all preprocessing — images still get split into patches, audio still gets chunked into frames. The input still needs to be tokenized into the format the transformer expects.

It's also not automatically "better" than encoder-based approaches. Encoders bring specialized knowledge — a vision encoder trained on billions of images already knows a lot about visual concepts. An encoder-free model has to learn all of that from scratch, which requires more data and compute during training. It's a trade-off, not a free upgrade.

And finally, encoder-free is not the same as "the model can understand any modality." The model still needs to be trained on that modality. You can't take a text-only model, add image patches, and expect it to understand them. The architecture enables multimodality, but training data makes it work.

<summary>1. What's the fundamental difference between an encoder-based multimodal model and an encoder-free one? Use the "teachers" analogy to explain.</summary>

**Sample Answer:** In an encoder-based model, each modality has its own specialist (a vision encoder for images, an audio encoder for sound) that translates the input into embeddings for the LLM. Like having three separate teachers who each explain their subject in their own way before you combine the information. In an encoder-free model, there's just one transformer that processes everything — text tokens, image patches, audio frames — all as tokens. Like learning directly from text, pictures, and sounds using the same brain without separate interpreters.

</details>

<details>
<summary>2. Why might an encoder-free model be better at cross-modal reasoning (e.g., "look at this chart and explain the tone of this audio")?</summary>

**Sample Answer:** Because there's no encoder boundary between modalities. In an encoder-based model, the vision encoder extracts visual features and hands them to the LLM as embeddings — the LLM never sees the raw image structure. In an encoder-free model, image patches and text tokens live in the same transformer, at the same level. The model can attend across them directly, making it easier to connect visual details with audio tone or textual context. It's like having all three sources in the same language instead of needing translations.

</details>

<details>
<summary>3. What's a scenario where an encoder-based approach might still be better than encoder-free?</summary>

**Sample Answer:** When you have a specialized modality where pretrained encoders already excel. For example, medical imaging — a vision encoder trained on millions of X-rays already knows what to look for. An encoder-free model would need to relearn those visual patterns from scratch during training, requiring significantly more data and compute. The encoder acts like a specialist who already has years of domain experience.

</details>

<details>
<summary>4. When someone says an encoder-free model processes "raw" image patches, how raw is the input actually?</summary>

**Sample Answer:** Not truly raw bytes. The image is split into small patches (like a 16×16 grid of squares), and each patch is flattened and projected into the transformer's embedding space through a minimal, learned linear projection. There's no large pretrained vision encoder extracting high-level features — just a simple patch-to-token conversion. The "rawness" refers to skipping the heavy encoder, not skipping all preprocessing.

</details>

<details>
<summary>5. Why should someone building AI agents care about encoder-free architecture?</summary>

**Sample Answer:** Because future models will natively understand images, audio, and video without extra infrastructure. Right now, if you want your agent to analyze a screenshot, you either need a separate vision model or a tool that describes the image in text. With encoder-free models, the agent's underlying model can process the screenshot directly — the same way it processes text. That means simpler agent architectures, fewer API calls, and lower latency for multimodal tasks.

</details>
