You now understand the pieces: the model predicts tokens, those tokens fit in a context window. But when you type a message and hit enter, what actually happens between your keyboard and the response appearing on screen?

Let's trace the full path, step by step.

# 1.4 How a Request Actually Travels: From Keyboard to Data Center and Back

**Step 1: You type a message**

Your AI tool (Cline, opencode, ChatGPT web — doesn't matter) takes whatever you wrote and collects the context. That means your current message plus the conversation history, system prompt, any attached files. Everything that needs to fit in the context window.

**Step 2: Tokenization**

That raw text gets converted into tokens. The tool runs it through a tokenizer — remember those sub-word chunks from earlier — and produces a sequence of numbers. Because models don't read text. They read numbers. Every token maps to a numeric ID.

**Step 3: The API call**

Here's where the magic of modern AI shows up. The model isn't running on your laptop. It's running on a server in a data center somewhere — owned by OpenAI, Anthropic, Google, or whoever provides the model. To talk to that server, your tool sends an **API request**. Think of it like ordering food delivery: your kitchen (your laptop) doesn't have the ingredients, so you call a restaurant (the API server), place an order (send your prompt), and they deliver the finished meal (the response).

API stands for Application Programming Interface. In plain English: it's a door. Your tool knocks on a specific URL (like `api.anthropic.com/v1/messages`) and hands over a structured package of data.

That package looks something like this (simplified):

```json
{
  "model": "claude-sonnet-4-20250514",
  "messages": [
    {"role": "system", "content": "You are a senior software engineer..."},
    {"role": "user", "content": "Write a function that sorts an array"}
  ],
  "max_tokens": 4096,
  "temperature": 0.3
}
```

This is the request body. It's JSON — a simple data format. It says which model to use, what the conversation is, how long the response can be, and how creative it should be (more on that last one soon).

**Step 4: Authentication and billing**

Your API key is in the header of that request. It's how the provider knows it's you, that you have credits, and that you haven't hit your rate limit. No API key? No response. That's also why you should never, ever commit an API key to a public repo — anyone who steals it can bill you.

**Step 5: The model processes**

The provider's server receives the tokens, feeds them through the model, and starts generating a response — one token at a time, the same "what comes next" prediction we talked about in file 1.1.

**Step 6: Streaming the response**

Most modern AI tools use something called **streaming**. Instead of waiting for the full response to be ready, the server sends tokens back as soon as they're generated — like watching someone type in real time. That's why you see the response appear word by word instead of all at once. Your tool receives each token, converts it back to text, and displays it.

**Step 7: Your tool shows it to you**

The tokens are decoded back into readable text, and the response appears in your chat window. One round trip complete.

The whole sequence usually takes a few seconds. From your keyboard, to a data center possibly across the world, through billions of calculations, and back to your screen.

## What It Is NOT

This request is NOT a live conversation with a "brain" that's thinking about your question. The model isn't running continuously, waiting for your input — each request is a stateless computation. The model receives your tokens, runs a single forward pass through its neural network, and produces output. It's more like putting a coin in a vending machine than calling a friend. The model has no memory of you between requests; your conversation history only persists because your tool bundles it up and sends it again every single time.

One more thing: because this all happens over HTTP (the same protocol websites use), it can fail just like a website can. Network timeout, server overload, API rate limit exceeded — you've probably seen some of these errors in your tool. Now you know exactly where in the pipeline they happen.

The request body I showed you had a field called `temperature`. That's one of the most important knobs you can turn when working with AI. It controls how deterministic or creative the model's predictions are. That's its own topic, and a good one to end Phase 1 with.

### In Your Own Words

<details>
<summary>1. Draw the request flow from memory: what happens from the moment you press enter to when you see the first word of the response?</summary>

**Sample Answer:** Your tool collects the conversation context, tokenizes it into numbers, sends an API request with your key to the provider's server, the model processes the tokens and generates a response one token at a time, the server streams those tokens back, and your tool decodes them into text on screen. Each step is like an assembly line: raw materials (your prompt) go in one end, pass through stations (tokenization, API call, model inference), and come out the other end as a finished product (the response).

</details>

<details>
<summary>2. Why does the tool need to send the entire conversation history with every request? Why can't the model just "remember" from the last call?</summary>

**Sample Answer:** Each API call is stateless — the model doesn't have a "memory" of previous calls. Think of it like a calculator: when you enter 2 + 2 and get 4, then enter 5 × 3, the calculator doesn't remember you just did 2 + 2. Every calculation starts fresh. Your tool has to send the full conversation history every time because the model resets to a blank state after each response.

</details>

<details>
<summary>3. If you're on a slow internet connection, which part of this flow would be most affected? What would you notice?</summary>

**Sample Answer:** The longest delay would be the API call itself — sending the tokenized input and receiving the streamed response. You'd notice a longer delay between pressing enter and seeing the first word appear, and potentially choppy streaming as each chunk of tokens takes longer to arrive. The model's actual processing time stays the same — the bottleneck is the data traveling across the internet, like ordering a pizza that takes 30 minutes to arrive even though the actual cooking is only 5 minutes.

</details>

<details>
<summary>4. What does an API key actually protect? Think about it from the provider's perspective — why not just let anyone call the model for free?</summary>

**Sample Answer:** An API key protects the provider from abuse and unpaid usage. Every API call costs the provider real money — GPU compute time, electricity, infrastructure. Without keys, anyone could run unlimited requests, and the provider would have no way to bill, rate-limit, or shut down bad actors. It's like a subway turnstile: the key proves you paid your fare, and without it, the system would be overrun with free riders and unable to sustain itself.

</details>
