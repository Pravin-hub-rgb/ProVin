A calculator is useful, but an agent with only one tool isn't much of an agent. The real power comes when the model can choose between multiple tools — and sometimes chain them together.

Let's build an agent with three tools: `calculator`, `get_current_date`, and `search_web`. The model will decide which tool fits the user's question.

### Step 1: Define Multiple Tools

```javascript
const tools = [
  {
    type: "function",
    function: {
      name: "calculator",
      description: "Evaluate a mathematical expression. Use this for any arithmetic or numeric computation.",
      parameters: {
        type: "object",
        properties: {
          expression: {
            type: "string",
            description: "The math expression to evaluate"
          }
        },
        required: ["expression"]
      }
    }
  },
  {
    type: "function",
    function: {
      name: "get_current_date",
      description: "Get today's date. Use this when the user asks for the current date, day of week, or what day it is.",
      parameters: {
        type: "object",
        properties: {}
      }
    }
  },
  {
    type: "function",
    function: {
      name: "search_web",
      description: "Search the web for information. Use this for questions about current events, facts, or things you don't know.",
      parameters: {
        type: "object",
        properties: {
          query: {
            type: "string",
            description: "The search query"
          }
        },
        required: ["query"]
      }
    }
  }
];
```

Each tool has a clear description that tells the model when to use it. Notice `get_current_date` has an empty `properties` object — it takes no parameters. The model will still call it, just with no input.

### Step 2: The Tool Functions

```javascript
function calculator(expression) {
  try {
    return String(eval(expression));
  } catch (err) {
    return `Error: ${err.message}`;
  }
}

function getCurrentDate() {
  return new Date().toISOString().split("T")[0];
}

async function searchWeb(query) {
  // In a real app, you'd call a search API here
  return `Simulated search result for "${query}": The sky is blue, water is wet.`;
}
```

Three functions, each matching one tool. When the model calls `get_current_date`, our code runs `getCurrentDate()` and returns the date string. The search is simulated here — in production you'd hit a real search API.

### Step 3: Route Tool Calls to the Right Function

![Multiple Tools Routing — Model Chooses, Dispatcher Routes to the Right Implementation](/diagrams/agenticai/multiple-tools-routing.svg)

We need a dispatcher — code that looks at the tool name and calls the right function:

```javascript
async function executeToolCall(toolName, input) {
  switch (toolName) {
    case "calculator":
      return calculator(input.expression);
    case "get_current_date":
      return getCurrentDate();
    case "search_web":
      return await searchWeb(input.query);
    default:
      return `Unknown tool: ${toolName}`;
  }
}
```

This switch statement is the bridge between the model's output and your real code. The model says `calculator`, we run `calculator()`. The model says `search_web`, we run `searchWeb()`. This pattern is how every agent system routes tool calls.

### Step 4: The Agent Loop (Manual Version)

```javascript
import Groq from "groq-sdk";

const client = new Groq();

const messages = [
  { role: "system", content: "You are a helpful assistant with tools." },
  { role: "user", content: "What is 15% of 200? And what day is it today?" }
];

const response = await client.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: messages,
  tools: tools
});

const message = response.choices[0].message;

// Check what the model wants to do
if (message.content) {
  console.log("Assistant:", message.content);
}

if (message.tool_calls) {
  for (const toolCall of message.tool_calls) {
    const args = JSON.parse(toolCall.function.arguments);
    console.log(`Tool called: ${toolCall.function.name}`, args);

    // Execute the right tool
    const result = await executeToolCall(toolCall.function.name, args);

    // Add to conversation history
    messages.push({
      role: "assistant",
      content: message.content || "",
      tool_calls: message.tool_calls
    });
    messages.push({
      role: "tool",
      content: result,
      tool_call_id: toolCall.id
    });

    // Call again with results
    const finalResponse = await client.chat.completions.create({
      model: "llama-3.3-70b-versatile",
      messages: messages,
      tools: tools
    });

    console.log("Assistant:", finalResponse.choices[0].message.content);
  }
}
```

### What You'll See

Run this with the question "What is 15% of 200? And what day is it today?" and the model might output **two tool_calls** in the same response:

```
message.tool_calls: [
  { function: { name: "calculator", arguments: '{"expression": "15/100 * 200"}' } },
  { function: { name: "get_current_date", arguments: "{}" } }
]
```

The model figured out it needs both tools and called them both at once. Your code handles each one, sends both results back, and the model combines them into a single answer:

```
Assistant: 15% of 200 is 30. Today's date is 2026-06-14.
```

### Chaining Tool Calls

Sometimes the model needs to call tools in sequence — using the result of one as input to another. For example: "How many days until Christmas?"

The model might first call `get_current_date`, see today is June 14, then call `calculator` to compute the difference. But that requires multiple rounds. Our current code only handles one round of tool calls.

That brings us to the real agent loop — the while loop that keeps going until the model is done.

### How Tool Choice Works

Behind the scenes, the model estimates: "Which tool's description best matches what the user is asking?" It's not random. Each description acts like a signpost. If you say "search the web" vaguely, the model might use it for questions it could answer from its own training. If you say "use this for current events or things after your training cutoff", the model will reserve it for those cases.

The descriptions are your UI. Spend time on them.

---

## What It Is NOT

Multiple tools does **not** mean the model runs them in parallel on its own. The model may *suggest* multiple tools in one response, but your code still executes each one and sends each result back. The model doesn't coordinate the tools — it just lists what it wants. Think of it like ordering at a restaurant: you can ask for a burger AND fries in one sentence, but the kitchen still prepares them separately and brings both to your table.

Also, the model does **not** automatically know when to use each tool. It relies entirely on your descriptions. If the descriptions are unclear, the model will guess wrong. You're not hiring a mind-reader; you're writing signposts.

### In Your Own Words

<details>
<summary>1. What happens if the model calls two different tools in the same response? How does your code handle it?</summary>

**Sample Answer:** The model returns multiple tool_calls in `message.tool_calls`. Your code loops through each one, runs the matching function via the switch statement, and sends each result back as a separate `role: "tool"` message with its own `tool_call_id`. It's like a waiter taking a full order — soup, main course, dessert — all at once, then the kitchen cooks each dish separately.

</details>

<details>
<summary>2. Why do we use a switch statement for routing tool calls? What are the alternatives?</summary>

**Sample Answer:** The switch statement maps tool names (strings from the model) to actual JavaScript functions. Alternatives include an object map (like `{ calculator: calculatorFn, search_web: searchWebFn }`) or dynamic dispatch. A switch is simple and readable, but an object map is cleaner when you have many tools — you just look up the function by name instead of writing a case for each one.

</details>

<details>
<summary>3. If the user asks "What was the weather yesterday?", which tool should the model call? What if the user asks "What is the weather going to be like tomorrow?"</summary>

**Sample Answer:** For both, the model should call `search_web` with a query about the weather for the relevant date — because a language model doesn't know real-time or past weather data. With a `get_current_date` tool, the model could first get today's date, calculate yesterday's or tomorrow's date, and include that in the search query. The model might chain `get_current_date` with `search_web` to be more precise.

</details>

<details>
<summary>4. What would happen if you gave `get_current_date` an empty `properties` object and the model tried to pass a parameter anyway?</summary>

**Sample Answer:** The API would reject it or ignore the extra parameter — the schema says "no parameters allowed." The model sometimes tries anyway if it's confused, but the API enforces the schema. It's like trying to put a square peg in a round hole: the schema won't let extra parameters through. Your switch statement should also be prepared to handle unexpected input gracefully.

</details>

<details>
<summary>5. Describe a scenario where the model would need to chain two tools — call one, get the result, then call another.</summary>

**Sample Answer:** "How many days until my birthday?" The model first calls `get_current_date` to find out today's date. Then it uses the current date to figure out the birthday date, and calls `calculator` to compute the difference. It needs the result of the first tool to know what input to give the second one. It's like first checking the calendar, then doing the math.

</details>
