Now the first new concept introduced in this capstone: **Databases.** Until you can store data, your "daily news aggregator" starts empty-handed every day — it won't even know what has already been scraped. The database is the answer to that.

## What a Database Is — A Home Example

A **database** is a structured storage where data lives in tables. Think of an **Excel spreadsheet** with different sheets — one sheet "Articles", one "Digests". Each sheet has columns (title, url, date) and rows (actual articles). Postgres is exactly that, but **production-grade** — on the internet, thousands of users, secure, fast.

**Supabase** = a free hosted version of Postgres, **with a visual table editor**. You can open it in the browser, create tables, see rows — you can literally watch rows appear as scraping happens. A god-send for someone learning backend.

## Think in Tables — Table, Columns, Rows

| id | source | title | url | published_at |
|---|---|---|---|---|
| 1 | youtube | "MCP Explained" | https://.../123 | 2026-08-07 |
| 2 | anthropic | "Agentic coding" | https://.../456 | 2026-08-08 |

- **Table** = `articles`
- **Columns** = id, source, title, url, published_at (they define the data's type)
- **Rows** = each article is one row

## Our Schema — The `articles` Table

Open the SQL editor in the Supabase dashboard (or via a PostgreSQL client) and run this:

```sql
CREATE TABLE articles (
  id SERIAL PRIMARY KEY,
  source TEXT NOT NULL,
  title TEXT NOT NULL,
  url TEXT UNIQUE NOT NULL,
  published_at TIMESTAMP,
  raw_content TEXT,
  score INT,
  reason TEXT,
  ranked BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE digests (
  id SERIAL PRIMARY KEY,
  content TEXT NOT NULL,
  created_at TIMESTAMP DEFAULT NOW()
);
```

## Understand Each Column

```sql
id SERIAL PRIMARY KEY
```
- `SERIAL` = auto-incrementing number — every new row gets 1, 2, 3... You don't send it, the database gives it itself
- `PRIMARY KEY` = unique identifier — the identity of every row

```sql
source TEXT NOT NULL
```
- `TEXT` = string type
- `NOT NULL` = this column can't be empty (every article must have some source)

```sql
url TEXT UNIQUE NOT NULL
```
- `UNIQUE` = **this is our dedup mechanism** — two articles can't have the same url
- Meaning when you insert, if a duplicate url comes, the database will refuse (or silently ignore — with `ON CONFLICT`)

```sql
score INT, reason TEXT
```
- `score` = the Aggregator Agent's 1-10 rating (int)
- `reason` = one line explaining why (text)

```sql
ranked BOOLEAN DEFAULT FALSE
```
- `BOOLEAN` = true/false
- `DEFAULT FALSE` = when a new row comes, by default `ranked = false` — meaning "not ranked yet"
- The row the Aggregator Agent processes gets `ranked = true` — so next time we know which ones are new

```sql
created_at TIMESTAMP DEFAULT NOW()
```
- `TIMESTAMP` = date + time
- `DEFAULT NOW()` = automatically put the current time at insert time

## INSERT — Putting Data In

```sql
INSERT INTO articles (source, title, url, published_at, raw_content)
VALUES (
  'youtube',
  'MCP Explained',
  'https://www.youtube.com/watch?v=abc123',
  NOW(),
  'Transcript snippet here...'
);
```

Notice — we didn't send `id`, `ranked`, `created_at` — the database fills them itself (SERIAL, DEFAULT FALSE, DEFAULT NOW()).

## Dedup — `ON CONFLICT DO NOTHING`

This is the real magic of the capstone. If that YouTube video was **already scraped yesterday**, don't insert it again today:

```sql
INSERT INTO articles (source, title, url, published_at, raw_content)
VALUES ('youtube', 'MCP Explained', 'https://.../abc123', NOW(), '...')
ON CONFLICT (url) DO NOTHING;
```

- `ON CONFLICT (url)` = when there's a conflict on the unique constraint (same url already exists)
- `DO NOTHING` = silently skip, don't throw an error

That's why we set `url TEXT UNIQUE NOT NULL` — **this is the dedup mechanism.** You don't have to check the whole database before every scrape — the database handles the conflict itself.

## SELECT — Reading Data

```sql
-- All articles
SELECT * FROM articles;

-- Only new (unranked) articles
SELECT * FROM articles WHERE ranked = false;

-- Top 5 highest-scored
SELECT * FROM articles WHERE ranked = true ORDER BY score DESC LIMIT 5;
```

These queries will be used in the Aggregator and Digest agents.

## ORM vs Raw SQL — Manual → Better

Now that raw SQL makes sense, there's a **better** option — **ORM** (Object-Relational Mapping). With tools like Prisma/Drizzle, you work with JavaScript objects instead of writing SQL:

```javascript
// Raw SQL (pg)
await client.query('INSERT INTO articles (source, title, url) VALUES ($1, $2, $3)');

// Drizzle ORM
await db.insert(articlesTable).values({ source, title, url });
```

- **Manual (`pg` + raw SQL):** Direct SQL, full control, concepts clear
- **Better (Drizzle):** TypeScript types, less boilerplate, safer

In this capstone we'll use **`pg` + raw SQL** — so the concepts are understood directly first. Switching to an ORM later is easy.

## Common Mistakes

- ❌ Forgetting the `UNIQUE` constraint — dedup will never work, duplicate articles will be inserted
- ❌ Writing the wrong column in `ON CONFLICT (url)` — conflicts only happen on unique columns
- ❌ Inserting without sending `NOT NULL` fields — error will come
- ❌ Manually tracking `ranked` — `BOOLEAN DEFAULT FALSE` in the schema is the right mechanism
- ❌ Putting database credentials in code — use `DATABASE_URL` from `.env`

1. What role does the `UNIQUE` constraint play in this project?

<details>

**Answer:** Dedup mechanism — two articles can't have the same url. So when something gets scraped again that already exists, `ON CONFLICT (url) DO NOTHING` silently skips the insert. You don't have to check manually every time.

<details>
<summary>Sample Answer</summary>

**Answer:** Every new article is by default `ranked = false` — meaning "the Aggregator hasn't ranked it yet". After the Aggregator processes it, it sets `ranked = true`. That's how we find "which ones are new" (`WHERE ranked = false`).

</details>

<details>
<summary>Sample Answer</summary>

**Answer:** `SERIAL` is an auto-incrementing number (each row gets 1, 2, 3...) and `PRIMARY KEY` is the unique identifier. `DEFAULT NOW()` automatically puts the current timestamp in `created_at` at insert time. Neither needs to be sent during insert.

</details>

4. What's the difference between raw SQL and an ORM?

<details>
<summary>Sample Answer</summary>

**Answer:** In raw SQL (`pg`) you write SQL queries directly — full control, concepts clear. In an ORM (Drizzle/Prisma) you work with JS objects — `db.insert(...).values({...})`, TypeScript types, less boilerplate. We'll understand with raw first, then switch to better.

</details>

## What It Is NOT

⚠️ **Database = not just "storage", it's a model.** Schema design (which columns, what constraints) is what makes the system right. Things like `UNIQUE` or `ranked` are logic, not just storage.

⚠️ **Postgres = not SQLite.** SQLite is a small file-based DB, Postgres is a full server-based production DB. We use Postgres (Supabase).

⚠️ **`ON CONFLICT DO NOTHING` = not a silent failure.** This is intentional dedup. It doesn't throw an error because you explicitly said "if there's a conflict, ignore it."

⚠️ **ORM = "no need to learn SQL" = NO.** Inside an ORM there are still SQL concepts (tables, relations). Understand raw SQL first, then use an ORM.
