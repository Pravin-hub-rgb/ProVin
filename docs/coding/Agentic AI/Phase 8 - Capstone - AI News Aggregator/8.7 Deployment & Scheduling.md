By 8.6 the whole system's code is ready — scrape → store → rank → digest. But right now it **only runs on your laptop.** You have to manually run `node index.js`. A real system runs **automatically every day, without you touching it** — somewhere in the cloud. That's **Deployment + Scheduling** — the last (and most important) part of the system.

## What Deployment Is — Making Code Live on the Internet

**Deployment** = taking your code out of your laptop and putting it on a **cloud server** that runs 24/7. Think — if your laptop shuts down, the system stops. In the cloud it stays available always.

Here we'll use **Render** (free tier) — it deploys code from GitHub. But there's one problem:

## Scheduling — The Most Important Decision

The system needs to **run at 7am every day**. Options:

| Option | How | Pros | Cons |
|---|---|---|---|
| Render's own cron | Schedule from Render dashboard | Everything in one place | **Free tier sleeps** — not reliable |
| **GitHub Actions cron** (we pick this) | YAML workflow in `.github/workflows/` | 100% free, reliable, secrets built-in | Code also on Render? |

**We choose GitHub Actions** because:
- Render's free tier **sleeps** the machine — schedule can be missed
- GitHub Actions' scheduled workflows (cron) **always run reliably**
- Secrets (`GROQ_API_KEY`, `DATABASE_URL`) are built into GitHub Actions

## Step 1 — Push Code to GitHub

If there's no GitHub repo yet:

```bash
git init
git add .
git commit -m "AI News Aggregator capstone"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/ai-news-aggregator.git
git push -u origin main
```

**Critical:** `.gitignore` must have `.env` and `node_modules` (created in 8.1) — verify `.env` wasn't pushed:

```bash
git ls-files | grep ".env"   # nothing should show
```

## Step 2 — Create the GitHub Actions Workflow

Create the file `.github/workflows/daily-digest.yml`:

```yaml
# .github/workflows/daily-digest.yml
name: Daily AI Digest

on:
  schedule:
    - cron: "0 7 * * *"   # every day at 7:00 AM UTC
  workflow_dispatch: {}   # manual trigger also allowed

jobs:
  run-pipeline:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install dependencies
        run: npm install

      - name: Run pipeline
        env:
          GROQ_API_KEY: ${{ secrets.GROQ_API_KEY }}
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
        run: node index.js
```

**Understand the workflow:**
- `on: schedule: cron: "0 7 * * *"` — triggers every day at 7:00 AM UTC
- `cron: "0 7 * * *"` format: `minute hour day month weekday` → 0 minute, 7 hour, * = every day
- `workflow_dispatch` — can also run manually from the GitHub UI (for testing)
- `runs-on: ubuntu-latest` — GitHub's free Linux machine
- Steps: get code → set up Node → install deps → `node index.js` (whole pipeline)
- `env:` — maps secrets into environment variables

## Step 3 — Set Secrets (GitHub)

Now put `GROQ_API_KEY` and `DATABASE_URL` into GitHub Actions secrets:

1. Open the GitHub repo
2. **Settings → Secrets and variables → Actions**
3. Create a **New repository secret**:
   - Name: `GROQ_API_KEY`, Value: your key
   - Name: `DATABASE_URL`, Value: your connection string

These secrets are now not in the code but in **GitHub's secure vault** — they reach the workflow via `${{ secrets.GROQ_API_KEY }}`.

> **Why secrets here:** `.env` is for the local machine. On the cloud (GitHub Actions), secrets are kept in GitHub's encrypted storage. Never hardcode them in YAML.

## Step 4 — Test It (Manually First)

Before the cron triggers, run the workflow **manually**:

1. GitHub repo → **Actions** tab
2. "Daily AI Digest" workflow → **Run workflow** button
3. Let it run — you'll see logs: "Step 1: Scraping...", "Step 2: Aggregating...", "Step 3: Digesting...", "Done!"

If a green tick appears — the system is working in the cloud.

## Step 5 — Verify Scheduling

Testing the cron is impossible (you'd have to be there at 7am). But you can confirm:
- The workflow file has correct syntax
- The manual run is green
- In the **GitHub Actions tab**, the schedule plan is visible (Actions → workflow → schedule tab)

And a smart move — run **2-3 manual runs** on different days, so system consistency gets checked.

## Bonus — Web Service on Render (Optional)

If you want to share the digest on the **web** (access via URL), deploy on Render:

1. Render dashboard → **New → Web Service**
2. Connect the GitHub repo
3. Set environment variables (`GROQ_API_KEY`, `DATABASE_URL`) in the Render dashboard
4. Build: `npm install`, Start: `node index.js`
5. Render runs the pipeline on every deploy

**Note:** Render web service runs on requests — we need GitHub Actions for cron. The web service is optional (only if you want an HTTP endpoint).

## Common Mistakes

- ❌ Pushing `.env` — secrets stay **encrypted** in GitHub Actions logs, but if the `.env` file is directly in the repo, it's public. Verify `.gitignore`.
- ❌ Wrong cron syntax — `"0 7 * * *"` is `minute hour day month weekday`. You can test it on `crontab.guru`.
- ❌ Hardcoding secrets in YAML — always use `${{ secrets.NAME }}`, never a literal value.
- ❌ Relying on the schedule without testing the workflow — first verify with `workflow_dispatch` manual run.
- ❌ Node version mismatch — set up the same Node (20) on both local and GitHub.

## What It Is NOT

⚠️ **Deployment = not "just uploading code", it's a lifecycle.** Code GitHub → workflow build → secrets inject → cloud run → schedule. Every piece matters.

⚠️ **Cron = not a guarantee of "exact second".** GitHub Actions cron gives ~minute-level accuracy. Perfect for a daily digest, not for real-time.

⚠️ **Render = not a replacement for GitHub Actions.** We use both — GitHub Actions for scheduling, Render (optional) for web exposure. Different jobs.

⚠️ **Secrets = not "hidden in code".** They're in encrypted storage — injected as environment variables at runtime. They should never be printed in logs.
