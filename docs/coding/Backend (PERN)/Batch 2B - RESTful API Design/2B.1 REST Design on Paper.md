## Problem — How Do You Design a Clean REST API?

REST design starts on paper, before code. Resources are nouns, methods are verbs. First bad vs good API, then nesting rules, then design on paper.

**Bad API (verbs in paths):**

```
POST /createBookmark
POST /getBookmark
POST /deleteBookmark
```

**Good API (nouns + methods):**

```
POST   /bookmarks        → create
GET    /bookmarks        → list
GET    /bookmarks/:id    → get one
PUT    /bookmarks/:id    → replace
PATCH  /bookmarks/:id    → partial update
DELETE /bookmarks/:id    → delete
```

- Resources are nouns (plural): `/bookmarks`, not `/bookmark`.
- Methods are verbs: GET, POST, PUT, PATCH, DELETE.
- Nesting: `/bookmarks/:id/tags` — but avoid deep nesting (max 2 levels).

**Design on paper:** before writing code, write the endpoint table: resource, method, path, success status, error statuses.

## What It Is NOT

- Verbs in paths are **not** RESTful.
- Everything as POST is **not** RESTful.
- Deep nesting is **not** recommended (max 2 levels).

---

## Common Mistakes

- Using verbs in paths (`/createBookmark`).
- Everything as POST.
- Deep nesting (`/users/1/posts/2/comments/3`).
