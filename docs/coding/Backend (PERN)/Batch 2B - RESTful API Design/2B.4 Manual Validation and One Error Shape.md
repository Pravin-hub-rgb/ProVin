## Problem — How Do You Validate Input by Hand? What Shape Should Errors Have?

Check types, lengths, formats with plain `if` statements. All errors share one JSON shape so the React app can handle them with one piece of code. First the checks, then the error shape, then the awkwardness (setup for Zod).

```ts
function validateBookmark(body: unknown): { url: string; title: string } {
  if (typeof body !== "object" || body === null) {
    throw new ValidationError("Body must be an object");
  }
  const b = body as Record<string, unknown>;
  if (typeof b.url !== "string" || !b.url.startsWith("http")) {
    throw new ValidationError("url must be a valid URL");
  }
  if (typeof b.title !== "string" || b.title.length < 1 || b.title.length > 200) {
    throw new ValidationError("title must be 1-200 characters");
  }
  return { url: b.url, title: b.title };
}
```

**One error shape:**

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "title must be 1-200 characters", "details": { "field": "title" } } }
```

- `code`: machine-readable error code.
- `message`: human-readable message.
- `details`: optional extra info.

**The awkwardness:** checks pile up, repeat, and drift out of sync with TypeScript types. This is the deliberate setup for Zod (Batch 5).

## What It Is NOT

- Manual validation is **not** a replacement for Zod — it is the pain that motivates Zod.
- Error shapes are **not** optional — consistency matters for the frontend.
- `throw` is **not** `return` — it stops execution.

---

## Common Mistakes

- Inconsistent error shapes across routes.
- Not validating all fields.
- Swallowing validation errors.
