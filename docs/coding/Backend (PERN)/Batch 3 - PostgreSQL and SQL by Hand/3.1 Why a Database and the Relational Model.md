## Problem — Why Not Just Files or In-Memory Maps?

Files and in-memory maps are not enough: no durability, no concurrent access, no querying. First why a database, then the relational model.

```
In-memory Map (Batch 2)          PostgreSQL (Batch 3+)
┌─────────────────────┐          ┌─────────────────────┐
│  Lost on restart    │          │  Durable on disk    │
│  No querying        │          │  SQL queries        │
│  No constraints     │          │  Constraints        │
│  Single process     │          │  Concurrent access  │
└─────────────────────┘          └─────────────────────┘
```

- **Durability:** data survives restarts.
- **Concurrent access:** multiple clients read/write safely.
- **Querying:** SQL to filter, sort, aggregate.
- **Constraints:** database refuses bad data even if app forgets.

**Relational model:**

- **Table:** a collection of rows (like a spreadsheet).
- **Row:** one record.
- **Column:** one field with a type.
- **Primary key:** uniquely identifies a row.
- **Foreign key:** references another table's primary key.

## What It Is NOT

- Files are **not** durable enough for production.
- In-memory maps are **not** for concurrent access.
- NoSQL is **not** always better — relational wins for business data.

---

## Common Mistakes

- Using files for production data.
- No primary keys.
- No foreign keys (orphaned data).
