## Problem — How Does a Server Remember Who You Are?

HTTP is stateless. Something must travel with each request to prove identity. Authentication answers "who are you?" (401). Authorization answers "what may you do?" (403 or 404).

```
Authentication (who are you?)          Authorization (what may you do?)
┌──────────────────────┐              ┌──────────────────────┐
│  Login → token/cookie│              │  Check permissions   │
│  401 if not auth     │              │  403/404 if denied  │
└──────────────────────┘              └──────────────────────┘
```

**Server sessions vs signed tokens:**

- **Sessions:** server stores session data, client gets a session ID (cookie). Server looks up session on each request.
- **Tokens:** server signs a token (JWT), client sends it. Server verifies signature, no lookup needed.

**Two words kept apart:**

- Authentication = "who are you?" → 401.
- Authorization = "what may you do?" → 403 (or 404 when hiding existence).

## What It Is NOT

- Authentication is **not** authorization — who you are vs what you may do.
- 401 is **not** 403 — 401 = not authenticated, 403 = not authorized.
- Tokens are **not** sessions — tokens are stateless, sessions are stateful.

---

## Common Mistakes

- Confusing authentication and authorization.
- Returning 403 when 401 is correct (or vice versa).
- Thinking tokens are the same as sessions.
