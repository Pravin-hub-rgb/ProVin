# Doc 5.10 — Folder Structure by Feature

## Cheat Sheet (Quick Recall)

- Organize by feature, not by technical type.
- Each feature: routes, controller, service, repository, schemas.
- `bookmarks/`, `tags/`, `auth/` folders.
- Easier to navigate and scale.

## Where We Are So Far

In 5.9 we saw the response envelope. Now folder structure by feature — organizing code.

## Broader Goal

The goal of Batch 5 is to make the API refuse bad input consistently and clean up structure. Current step: folder structure.

---

Organize by feature (`bookmarks/`, `tags/`) rather than by technical type (`controllers/`, `services/`, `repositories/`). Each feature holds its own routes, controller, service, repository, and schemas.

```
src/
├── bookmarks/
│   ├── bookmarks.routes.ts
│   ├── bookmarks.controller.ts
│   ├── bookmarks.service.ts
│   ├── bookmarks.repository.ts
│   └── bookmarks.schema.ts
├── tags/
│   ├── tags.routes.ts
│   ├── tags.controller.ts
│   ├── tags.service.ts
│   ├── tags.repository.ts
│   └── tags.schema.ts
└── shared/
    ├── middleware/
    ├── errors/
    └── config/
```

- By feature: easier to find all code for one feature.
- By technical type: scattered across folders.
- Each feature is self-contained.

## What It Is NOT

- By technical type is **not** recommended for growing apps.
- Feature folders are **not** for tiny apps (overkill for 2 routes).
- Shared code is **not** in feature folders — put in `shared/`.

---

## Common Mistakes

- Organizing by technical type (controllers/, services/).
- Putting shared code in feature folders.
- Too many small folders for tiny apps.
