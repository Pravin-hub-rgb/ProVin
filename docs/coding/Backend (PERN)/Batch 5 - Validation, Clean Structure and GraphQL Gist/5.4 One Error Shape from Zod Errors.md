# Doc 5.4 — One Error Shape from Zod Errors

## Cheat Sheet (Quick Recall)

- Map Zod issues into the shared error shape: `{ error: { code, message, details } }`.
- `details` is a field-by-field list.
- Decide status code (400 or 422) and stick to it.
- Consistency is a gift to the frontend.

---

Map Zod issues into the shared error shape from 2B.4 with a field-by-field `details` list. Decide the status code (400 or 422) and stick to it.

```ts
function zodErrorToResponse(err: z.ZodError) {
  return {
    status: 400,
    body: {
      error: {
        code: "VALIDATION_ERROR",
        message: "Invalid input",
        details: err.issues.map((i) => ({
          field: i.path.join("."),
          message: i.message,
        })),
      },
    },
  };
}
```

- `code`: machine-readable error code.
- `message`: human-readable message.
- `details`: field-by-field list of issues.

**Status code decision:** 400 (Bad Request) or 422 (Unprocessable Entity). Pick one and stick to it across the API.

## What It Is NOT

- Inconsistent error shapes are **not** acceptable — frontend needs one shape.
- `details` is **not** optional — it helps the frontend show field-level errors.
- Zod errors are **not** HTTP errors — you map them.

---

## Common Mistakes

- Different error shapes from different routes.
- Not including field-level details.
- Switching between 400 and 422.
