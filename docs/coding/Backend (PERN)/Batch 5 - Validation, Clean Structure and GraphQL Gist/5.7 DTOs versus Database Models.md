# Doc 5.7 — DTOs versus Database Models

## Cheat Sheet (Quick Recall)

- API shape ≠ database shape.
- Never return raw database objects.
- Shape responses with a response schema (DTO).
- Hide internal fields (password hash, etc.).

## Where We Are So Far

In 5.6 we saw layered architecture. Now DTOs vs database models — what leaves the server.

## Broader Goal

The goal of Batch 5 is to make the API refuse bad input consistently and clean up structure. Current step: DTOs.

---

The API shape and the database shape are different things. Never return raw database objects. Choose what leaves the server. Shape responses with a response schema.

```ts
// Database model (Prisma)
type BookmarkRow = {
  id: string;
  url: string;
  title: string;
  note: string | null;
  createdAt: Date;
  updatedAt: Date;
  userId: string;  // internal
};

// DTO (what the API returns)
type BookmarkDTO = {
  id: string;
  url: string;
  title: string;
  note: string | null;
  createdAt: string;  // ISO string
};

// Mapper
function toDTO(row: BookmarkRow): BookmarkDTO {
  return {
    id: row.id,
    url: row.url,
    title: row.title,
    note: row.note,
    createdAt: row.createdAt.toISOString(),
  };
}
```

- **Database model:** Prisma-generated, includes all fields.
- **DTO:** API response shape, only what the client needs.
- **Mapper:** converts database row to DTO.

## What It Is NOT

- Raw database objects are **not** for clients — they leak internals.
- DTO is **not** the same as the database model.
- Mapping is **not** optional — always shape responses.

---

## Common Mistakes

- Returning raw Prisma objects (leaks internals).
- No DTO (inconsistent API).
- Forgetting to convert dates to ISO strings.
