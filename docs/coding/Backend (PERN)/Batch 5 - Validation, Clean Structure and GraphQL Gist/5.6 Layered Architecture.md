# Doc 5.6 — Layered Architecture

## Cheat Sheet (Quick Recall)

- Three layers: controller (HTTP), service (business logic), repository (database).
- Dependencies point one way: controller → service → repository.
- Controller: no Prisma calls. Service: no `req`/`res`.
- Diagram the flow of one request through all three.

## Where We Are So Far

In 5.5 we saw config validation. Now layered architecture — separating concerns.

## Broader Goal

The goal of Batch 5 is to make the API refuse bad input consistently and clean up structure. Current step: layers.

---

Three layers, each with one job:

```
Request → Controller (HTTP) → Service (business rules) → Repository (database) → Response
```

- **Controller:** HTTP in, HTTP out. Parses request, calls service, sends response. No Prisma calls.
- **Service:** business rules. Validation, logic, orchestration. No `req`/`res`.
- **Repository:** database access through Prisma. SQL/Prisma calls only.

**Break it on purpose:**

- Controller reaches directly into Prisma → hard to test.
- Business rule depends on `req` → hard to reuse.

**Mini-project:** move one endpoint (`POST /bookmarks`) through the three layers.

## What It Is NOT

- Controller is **not** for business logic — that is the service.
- Service is **not** for HTTP — that is the controller.
- Repository is **not** for business rules — that is the service.

---

## Common Mistakes

- Controller with Prisma calls (hard to test).
- Service with `req`/`res` (hard to reuse).
- Repository with business logic (wrong layer).
