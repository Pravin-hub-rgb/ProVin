# Doc 7.4 — Rate Limiting

## Cheat Sheet (Quick Recall)

- `express-rate-limit` for rate limiting.
- Strict limiter on login/registration.
- Looser limiter elsewhere.
- 429 status + `Retry-After` header.
- `trust proxy` when behind a proxy.

## Where We Are So Far

In 7.3 we saw CORS in depth. Now rate limiting — preventing abuse.

## Broader Goal

The goal of Batch 7 is to make the API hard to abuse and easy to observe. Current step: rate limiting.

---

Rate limiting prevents brute force, scraping, and accidental floods.

```ts
import rateLimit from "express-rate-limit";

const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 min
  max: 5,                    // 5 attempts
  message: { error: { code: "RATE_LIMITED", message: "Too many attempts" } },
});

const apiLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 100,
});

app.use("/auth", authLimiter);
app.use(apiLimiter);
```

- `windowMs`: time window.
- `max`: max requests in window.
- `429` status + `Retry-After` header.
- `trust proxy`: when behind a proxy (nginx, Heroku), use `app.set("trust proxy", 1)`.

**Default store:** in-memory (works for one process). Shared store (Redis) is PREVIEW (Batch 12).

**Break it on purpose:** hammer the login route until it blocks.

## What It Is NOT

- Rate limiting is **not** authentication — it limits requests, not identity.
- In-memory store is **not** for multi-process — use Redis for that.
- `trust proxy` is **not** optional behind a proxy — without it, all users share one IP.

---

## Common Mistakes

- Not setting `trust proxy` behind a proxy (all users share one IP).
- Using wildcard CORS + credentials.
- Not returning 429 with `Retry-After`.
