# Doc 7.7 — Failing Safely in Production

## Cheat Sheet (Quick Recall)

- Operational errors: expected, handled, mapped to status codes.
- Programmer errors: bugs, logged, answered with generic 500.
- Never send stack traces or DB errors to clients.
- Process-level handlers: log, then exit, let platform restart.

Operational errors (expected, handled, mapped to status codes) versus programmer errors (bugs, logged, answered with generic 500).

```ts
// Operational error: expected, handled
class NotFoundError extends Error {
  statusCode = 404;
}

// Programmer error: bug, logged, generic 500
process.on("unhandledRejection", (reason) => {
  logger.error(reason, "Unhandled rejection");
  process.exit(1); // let platform restart
});

process.on("uncaughtException", (err) => {
  logger.error(err, "Uncaught exception");
  process.exit(1);
});
```

- **Operational errors:** expected (validation, not found, auth). Mapped to status codes.
- **Programmer errors:** bugs (null reference, type error). Logged, answered with generic 500.
- **Never send** stack traces or database errors to clients.
- **Process-level handlers:** log, then exit. Let the platform (Docker, PM2) restart.

## What It Is NOT

- Stack traces are **not** for clients — log them, don't send them.
- Catching all errors as 500 is **not** helpful — distinguish operational vs programmer.
- Process-level handlers are **not** for recovery — log and exit.

---

## Common Mistakes

- Sending stack traces to clients.
- Catching programmer errors and continuing (corrupt state).
- Not exiting on unhandled rejection.
