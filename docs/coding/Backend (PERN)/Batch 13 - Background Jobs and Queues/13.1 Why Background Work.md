# Doc 13.1 — Why Background Work

## Cheat Sheet (Quick Recall)

- Slow work should not block the request.
- Work that can fail and retry.
- Work that must run on a schedule.
- Background jobs: producer, queue, worker.

The goal of Batch 13 is to make work reliable and non-blocking. Current step: why background work.

---

Some work must not make a user wait, and some work must happen on a schedule. First the cost of slow requests, then retryable work, then scheduled work.

```ts
// Slow endpoint (bad)
app.post("/enrich", async (req, res) => {
  const result = await fetchAndParseUrl(req.body.url); // slow!
  res.json(result);
});
```

- **Slow request:** user waits, timeout risk.
- **Retryable work:** can fail and retry (e.g., external API call).
- **Scheduled work:** must run on a schedule (e.g., nightly cleanup).

**The pattern:** producer (API) → queue → worker (background process).

## What It Is NOT

- Background work is **not** optional for slow operations.
- `setInterval` is **not** a job system.
- Slow requests are **not** acceptable for users.

---

## Common Mistakes

- Doing slow work in the request handler.
- No retry on failure.
- No scheduling mechanism.
