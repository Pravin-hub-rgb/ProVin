# Doc 11.3 — Isolation Levels

## Cheat Sheet (Quick Recall)

- Read committed: default, sees committed data.
- Repeatable read: same query returns same rows.
- Serializable: full isolation, no anomalies.
- Anomalies: lost update, non-repeatable read, phantom read.

## Where We Are So Far

In 11.2 we saw ACID. Now isolation levels — how concurrent transactions interact.

## Broader Goal

The goal of Batch 11 is to understand what goes wrong when many requests touch the same data. Current step: isolation levels.

---

Isolation levels control what concurrent transactions see. Read committed, repeatable read, serializable — each allows/prevents different anomalies.

```sql
-- Set isolation level
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM accounts WHERE id = 1;
-- ... another transaction updates ...
SELECT * FROM accounts WHERE id = 1; -- same result (repeatable read)
COMMIT;
```

- **Read committed (default):** sees only committed data. Allows non-repeatable reads.
- **Repeatable read:** same query returns same rows. Allows phantoms.
- **Serializable:** full isolation, no anomalies. Slowest.

**Anomalies:**

- **Lost update:** two transactions update same row, one overwrites the other.
- **Non-repeatable read:** same query returns different rows (another transaction committed).
- **Phantom read:** new rows appear (another transaction inserted).

**Reproduce each anomaly with two `psql` sessions side by side.**

## What It Is NOT

- Read committed is **not** safe from lost updates.
- Serializable is **not** the default — it is slowest.
- Isolation is **not** locking — they are different mechanisms.

---

## Common Mistakes

- Assuming default (read committed) protects against everything.
- Not testing isolation levels.
- Confusing isolation with locking.
