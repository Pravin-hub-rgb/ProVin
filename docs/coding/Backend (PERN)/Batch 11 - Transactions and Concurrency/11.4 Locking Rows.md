# Doc 11.4 — Locking Rows

## Cheat Sheet (Quick Recall)

- `SELECT ... FOR UPDATE` locks rows.
- Blocks other transactions from updating.
- Fixes lost update (pessimistic locking).
- Cost: slower, potential deadlocks.

## Where We Are So Far

In 11.3 we saw isolation levels. Now locking rows — pessimistic locking.

## Broader Goal

The goal of Batch 11 is to understand what goes wrong when many requests touch the same data. Current step: locking.

---

`SELECT ... FOR UPDATE` locks rows so other transactions cannot update them. This fixes the lost update problem.

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- locks row
-- another transaction trying to update id=1 blocks here
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;  -- releases lock
```

- `FOR UPDATE` acquires a row lock.
- Other transactions trying to update the same row block.
- Lock released on `COMMIT`/`ROLLBACK`.
- Fixes the 11.1 bug (lost update).

**Cost:** slower (transactions wait), potential deadlocks.

## What It Is NOT

- `FOR UPDATE` is **not** `FOR SHARE` — FOR UPDATE blocks writes, FOR SHARE blocks writes but allows reads.
- Locking is **not** free — it slows down concurrent transactions.
- `FOR UPDATE` is **not** the only solution — optimistic concurrency (11.5) is an alternative.

---

## Common Mistakes

- Locking too broadly (table locks).
- Holding locks across slow operations (deadlock risk).
- Not using locks when needed (lost updates).
