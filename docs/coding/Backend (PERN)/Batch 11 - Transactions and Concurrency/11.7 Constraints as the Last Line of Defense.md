# Doc 11.7 — Constraints as the Last Line of Defense

## Cheat Sheet (Quick Recall)

- CHECK constraints: `CHECK (balance >= 0)`.
- Unique indexes: enforce uniqueness at DB level.
- Constraints make invalid state impossible, no matter what code does.
- Callback to 3.4 and 3.12.

## Where We Are So Far

In 11.6 we saw deadlocks. Now constraints — the last line of defense.

## Broader Goal

The goal of Batch 11 is to understand what goes wrong when many requests touch the same data. Current step: constraints.

---

Constraints make an invalid state impossible no matter what the code does. Check constraints and unique indexes.

```sql
-- Non-negative balance
ALTER TABLE accounts ADD CONSTRAINT balance_non_negative CHECK (balance >= 0);

-- Unique email
CREATE UNIQUE INDEX idx_users_email ON users(email);
```

- **CHECK:** custom validation at DB level.
- **UNIQUE:** enforces uniqueness.
- **Last line of defense:** even if code forgets, DB refuses.

## What It Is NOT

- Constraints are **not** optional — they protect data integrity.
- CHECK is **not** application-level — it is database-level.
- Constraints are **not** a replacement for code validation — both needed.

---

## Common Mistakes

- Relying only on code validation (code can have bugs).
- Missing CHECK constraints.
- Not using unique indexes (duplicate data).
