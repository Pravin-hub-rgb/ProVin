# Doc 11.6 — Deadlocks

## Cheat Sheet (Quick Recall)

- Postgres detects and aborts one.
- Habit: lock in consistent order.
- Retry the aborted transaction.

## Broader Goal

---

Two transactions lock resources in opposite order → deadlock. Postgres detects and aborts one.

```sql
-- Transaction A
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- locks 1
SELECT * FROM accounts WHERE id = 2 FOR UPDATE;  -- waits for B

-- Transaction B (concurrent)
BEGIN;
SELECT * FROM accounts WHERE id = 2 FOR UPDATE;  -- locks 2
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- waits for A → DEADLOCK
```

- **Deadlock:** A waits for B, B waits for A → circular wait.
- **Postgres detects:** aborts one transaction (the "victim").
- **Habit:** lock in consistent order (always lock lower ID first).
- **Retry:** the aborted transaction must be retried.

**Break it on purpose:** cause a deadlock, then fix with consistent lock order.

## What It Is NOT

- Deadlock is **not** a timeout — it is a circular wait.
- Postgres does **not** prevent deadlocks — it detects and aborts.
- Consistent order is **not** optional — it prevents deadlocks.

---

## Common Mistakes

- Locking in inconsistent order.
- Holding locks across slow operations.
- Not retrying aborted transactions.
