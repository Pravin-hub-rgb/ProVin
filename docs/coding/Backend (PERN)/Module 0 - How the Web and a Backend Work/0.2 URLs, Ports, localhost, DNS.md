## Problem — How Does the Browser Know Where to Send a Request?

You type `https://google.com/maps?q=paris` and hit enter. But what does that actually mean? How does the browser know which machine to talk to, which program on that machine, and what to ask for?

A URL is an address. It has five parts, and each one answers a different question.

```
https://google.com:443/maps?q=paris
  │        │       │    │      │
  │        │       │    │      └── query (data)
  │        │       │    └── path (what you want)
  │        │       └── port (service number)
  │        └── host (server name)
  └── scheme (protocol)
```

- **Scheme** — `http` or `https` (http + TLS encryption).
- **Host** — the server name (google.com) or an IP address.
- **Port** — which service on that machine (443 for HTTPS, 80 for HTTP, 3000/5173 for dev).
- **Path** — what you want (`/maps`).
- **Query** — extra data (`?q=paris`).

**localhost** is your own machine. `http://localhost:3000` means "the service on port 3000 on this machine." When you run a backend locally, it listens on a port (e.g., 3000) and you access it via localhost.

**DNS (Domain Name System)** turns a name (google.com) into an IP address (142.250.80.46). Humans remember names; computers use numbers. DNS is the phone book of the internet.

**Same origin:** `localhost:3000` and `localhost:5173` are different origins because the ports differ. Browsers treat them as separate sites — this is why CORS exists (covered in Batch 2B).

## What It Is NOT

- `localhost` is **not** the internet — it is your own machine.
- Different ports are **not** the same origin — `localhost:3000` ≠ `localhost:5173`.
- DNS is **not** a search engine — it is a name-to-IP lookup service.

---

## Common Mistakes

- Mixing up port and path.
- Thinking `localhost` is the internet.
- Treating different ports as the same origin.
