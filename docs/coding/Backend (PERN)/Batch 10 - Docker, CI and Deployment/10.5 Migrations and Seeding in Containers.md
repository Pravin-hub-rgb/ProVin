# Doc 10.5 — Migrations and Seeding in Containers

## Cheat Sheet (Quick Recall)

- `prisma migrate deploy` for production (not `migrate dev`).
- Run migrations as startup step or separate job.
- Seeding: dev only, not production.
- Clean machine → working stack in one command.

## Where We Are So Far

## Broader Goal

The goal of Batch 10 is to package and deploy the stack. Current step: migrations in containers.

---

`prisma migrate deploy` for production (not `migrate dev`). Run as startup step or separate job. Seeding: dev only.

```dockerfile
# In Dockerfile or entrypoint
CMD ["sh", "-c", "npx prisma migrate deploy && node dist/server.js"]
```

- **`migrate deploy`:** applies existing migrations (production).
- **`migrate dev`:** creates + applies (development only).
- **Startup step:** run migrations before starting the app.
- **Separate job:** run migrations as a one-off job (safer in prod).
- **Seeding:** dev only (`prisma db seed`). Never seed production.

**Clean machine → working stack:**

```bash
docker compose up
# → DB starts, migrations run, API starts, web starts
```

## What It Is NOT

- `migrate dev` is **not** for production — use `deploy`.
- Seeding is **not** for production — dev only.
- Migrations are **not** automatic — you must run them.

---

## Common Mistakes

- Using `migrate dev` in production.
- Seeding production data.
- Migrations racing with multiple app instances.

---

## Try It Yourself

1. Add `migrate deploy` to Dockerfile/entrypoint.
2. Run `docker compose up` from clean machine.
3. Verify migrations applied.
