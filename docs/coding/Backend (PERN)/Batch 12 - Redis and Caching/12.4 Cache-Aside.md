# Doc 12.4 — Cache-Aside

## Cheat Sheet (Quick Recall)

- Read from cache; on miss, read DB and fill cache.
- Measure latency before and after.
- Cache key: per-user (`user:123:bookmark:456`).
- TTL on cache entries.

## Where We Are So Far

In 12.3 we saw ioredis. Now cache-aside — the most common caching pattern.

## Broader Goal

The goal of Batch 12 is to make reads faster and shared state possible. Current step: cache-aside.

---

Cache-aside: read from cache; on miss, read DB and fill cache.

```ts
async function getBookmark(id: string, userId: string): Promise<Bookmark> {
  const key = `user:${userId}:bookmark:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const bookmark = await prisma.bookmark.findUnique({ where: { id } });
  if (!bookmark) throw new NotFoundError("Bookmark not found");

  await redis.set(key, JSON.stringify(bookmark), "EX", 300); // 5 min TTL
  return bookmark;
}
```

- **Read from cache:** `redis.get(key)`.
- **On miss:** read DB, fill cache with TTL.
- **Per-user keys:** `user:${userId}:bookmark:${id}` (never share between users).
- **Measure:** latency before and after (benchmark).

## What It Is NOT

- Cache-aside is **not** write-through — you fill on read, not write.
- Shared keys are **not** safe for per-user data.
- Cache is **not** the source of truth — DB is.

---

## Common Mistakes

- Shared cache key for per-user data (leak).
- No TTL (memory grows).
- Not measuring before/after (no proof).
