When data changes, how stale is acceptable? TTL vs explicit deletion.

```ts
// Explicit invalidation on update
async function updateBookmark(id: string, userId: string, data: UpdateInput) {
  const updated = await prisma.bookmark.update({ where: { id }, data });
  // invalidate cache
  await redis.del(`user:${userId}:bookmark:${id}`);
  return updated;
}

// TTL-based: cache expires after 5 min, no explicit invalidation needed
await redis.set(key, JSON.stringify(bookmark), "EX", 300);
```

- **TTL:** cache expires after N seconds (simple, but stale window).
- **Explicit deletion:** delete cache on write (no stale, but more code).
- **Per-user keys:** `user:${userId}:bookmark:${id}` (never share).

**Break it on purpose:** serve stale data after an update.

## What It Is NOT

- Invalidation is **not** automatic — you must handle it.
- TTL is **not** zero stale — there is a stale window.
- Shared keys are **not** safe for per-user data.

---

## Common Mistakes

- Forgetting to invalidate on every write path.
- Shared cache key for per-user data (leak).
- No TTL (memory grows forever).
