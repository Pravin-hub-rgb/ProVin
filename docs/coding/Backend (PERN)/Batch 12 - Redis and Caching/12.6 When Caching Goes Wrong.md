# Doc 12.6 — When Caching Goes Wrong

## Cheat Sheet (Quick Recall)

- Cache stampede: many requests miss at once.
- Caching errors: don't cache errors.
- Caching private data: per-user keys required.
- When not to cache: rarely read, frequently written.

## Where We Are So Far

In 12.5 we saw invalidation. Now when caching goes wrong — stampedes, errors, private data.

## Broader Goal

The goal of Batch 12 is to make reads faster and shared state possible. Current step: caching pitfalls.

---

Caching has pitfalls. First stampede, then errors, then private data, then when not to cache.

**Cache stampede:** many requests miss at once → all hit DB simultaneously. Fix: lock or stale-while-revalidate.

**Caching errors:** don't cache 404/500 responses → they become "sticky."

**Caching private data:** per-user keys required (never share between users).

**When not to cache:**

- Rarely read data.
- Frequently written data.
- User-specific data without per-user keys.

## What It Is NOT

- Caching is **not** always good — measure first.
- Stampede is **not** harmless — it can overwhelm DB.
- Caching errors is **not** recommended.

---

## Common Mistakes

- Caching per-user data under a shared key (leak).
- No expiry (memory grows forever).
- Forgetting to invalidate on every write path.
- Treating Redis as source of truth.
- Caching before measuring (premature optimization).

## Summary

- Stampede: many misses at once.
- Don't cache errors.
