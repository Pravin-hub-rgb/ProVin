# Doc 8.5 — A Real Postgres in Tests

## Cheat Sheet (Quick Recall)

- Testcontainers: throwaway Postgres in Docker.
- Apply migrations in test setup.
- Share one container across the suite (speed).
- Isolate each test (truncate or rollback).
- Docker is USED here (taught in Batch 10).

A real database in tests is a deliberate choice: mocking the database tests the mock, not the queries, constraints, or migrations you actually wrote.

```ts
import { PostgreSqlContainer } from "@testcontainers/postgresql";
import { execSync } from "child_process";

let container: PostgreSqlContainer;
let pool: Pool;

beforeAll(async () => {
  container = await new PostgreSqlContainer().start();
  pool = new Pool({ connectionString: container.getConnectionUri() });
  // apply migrations
  execSync("npx prisma migrate deploy", { env: { ...process.env, DATABASE_URL: container.getConnectionUri() } });
});

afterAll(async () => {
  await pool.end();
  await container.stop();
});

beforeEach(async () => {
  // truncate tables
  await pool.query("TRUNCATE TABLE bookmarks, users CASCADE");
});
```

- **Testcontainers:** starts a throwaway Postgres in Docker.
- **Migrations:** applied in setup.
- **Shared container:** one container for the whole suite (speed).
- **Isolation:** truncate tables or rollback transaction per test.

**Break it on purpose:** let two tests share data and watch them interfere.

## What It Is NOT

- Docker is **not** taught here — USED (taught in Batch 10).
- Mocking the database is **not** recommended — tests the mock.
- One container per test is **not** needed — share for speed.

---

## Common Mistakes

- Tests sharing data (interference).
- Starting a container per test (slow).
- Not applying migrations.
- Not isolating tests.
