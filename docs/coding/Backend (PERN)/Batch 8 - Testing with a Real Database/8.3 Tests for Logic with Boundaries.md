Mocks and fakes for things you don't own (clock, email, third-party). Do not fake your own database.

```ts
// Manual fake (hand-written)
class FakeClock {
  now = new Date("2026-01-01");
  advance(ms: number) { this.now = new Date(this.now.getTime() + ms); }
}

// Library mock
vi.mock("node:fs", () => ({
  readFileSync: vi.fn(() => "mocked content"),
}));
```

- **Fake:** hand-written implementation (e.g., in-memory clock).
- **Mock:** library-provided (e.g., `vi.mock`).
- **Rule of thumb:** fake what you don't own (clock, email, third-party). Don't fake your own database.

## What It Is NOT

- Mocking is **not** always good — it can test the mock, not the code.
- Faking your own database is **not** recommended — use a real one.
- Mocks are **not** a replacement for integration tests.

---

## Common Mistakes

- Mocking the database (tests the mock).
- Over-mocking (tests prove nothing).
- Not faking boundaries (clock, email).
