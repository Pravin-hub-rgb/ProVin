# Doc 0.1 — How JavaScript Becomes Native Views

## Cheat Sheet (Quick Recall)

- JS bundle runs in a JS engine (Hermes) inside a native app shell.
- React renders a virtual tree; the renderer turns it into native view instructions.
- Instructions cross JS↔native via Bridge (old) or JSI (new architecture).
- Native side creates/updates real native views (Android `View`, iOS `UIView`).
- Events (tap, scroll) flow back to JS, triggering re-render.

## Main Content

### THINK

In React Native you write JS/TS, but the phone only understands native code. So the question is: how does JS code become a real app on screen? If this pipeline is not understood, performance issues, debugging, and limits will not make sense. So first look at the pipeline — code comes later.

### CONCEPT

A React Native app involves three things:

1. **Your JavaScript code** — components, state, logic.
2. **Native app shell** — a thin native (Kotlin/Swift) app that hosts a JavaScript engine.
3. **Phone's UI toolkit** — real native views (Android `View`, iOS `UIView`).

JS never touches the screen directly. JS describes what should be on screen; the native side draws it.

Pipeline (6 steps):

1. **Bundle your JS.** Code is bundled into a single JS file (the bundle). In dev, Metro serves it; in production it ships inside the app.
2. **Start the JavaScript engine.** The native app starts Hermes (modern RN). Your bundle runs inside it.
3. **Render to a virtual tree.** React runs as usual — components return elements. The RN renderer turns this into instructions: "create a View with these styles, put a Text inside it".
4. **Send instructions to native.** Instructions cross from JS to native. In the old architecture via the Bridge (async JSON messages); in the new architecture via JSI (direct, synchronous-ish calls).
5. **Native draws real views.** The native side creates/updates real native views. The phone's compositor draws them on screen.
6. **Events flow back.** On tap, the native view sends an event back to JS, which runs your `onPress` handler, updates state, and re-renders.

### CODE (gradual)

There is no app code in this doc — it is pipeline theory. The first code appears in Batch 1. But here is a small example that shows what the pipeline does:

```tsx
// This JS component describes "what should be on screen"
function Greeting() {
  return (
    <View>
      <Text>Hello</Text>
    </View>
  );
}
```

Line by line:

- `function Greeting()` — defines a component.
- `return (...)` — describes a View with a Text inside it.
- `<View>` / `<Text>` — these are not HTML; they are native building blocks. The RN renderer converts them into native instructions.

## Common Mistakes

- Thinking React Native uses a WebView — no, it renders real native views.
- Confusing Bridge and JSI — Bridge is async + serialized; JSI is direct + synchronous-ish.
- Doing heavy JS work on the main thread — it blocks UI thread communication.

## Try It Yourself

1. Run `npx create-expo-app pipeline-demo`, open `app/index.tsx`, change a `Text`, save — watch the phone update. This is step 6 of the pipeline (events/re-render) live.
2. Open the debugger (shake phone → "Open JS Debugger") and check the console — confirms the JS engine (Hermes).

## Summary

- JS bundle → Hermes engine → React virtual tree → native instructions (Bridge/JSI) → real native views → events back to JS.
- React Native is not a WebView; real native views are rendered.
- Understanding the pipeline helps with debugging and performance.

**Answer:** JS runs in an engine (Hermes), React renders a virtual tree, instructions cross to native (via bridge/JSI), and native creates real views (Android View / iOS UIView) that the phone draws.

2. Why is React Native not just a WebView app?

<details>
<summary>Sample Answer</summary>

**Answer:** Because it renders real native views using the OS's UI toolkit, not HTML in a browser, so scrolling, animations, and gestures feel native.

</details>

3. What is the "bundle"?

<details>
<summary>Sample Answer</summary>

**Answer:** The single JavaScript file containing all your app code, served by Metro in dev and shipped inside the app in production.

</details>

4. Where does your `onPress` handler actually run?

<details>
<summary>Sample Answer</summary>

**Answer:** In the JavaScript engine; the native view sends the tap event back to JS, which runs the handler and re-renders.

</details>

5. Name one thing that can still require native code even in React Native.

**Answer:** Deep platform features not exposed by React Native/Expo (e.g., a custom native SDK or very specific hardware access).

</details>

## What It Is NOT

- ❌ React Native is **not a WebView** — real native views are rendered.
- ❌ JS does **not** directly touch the screen — the native side draws.
- ❌ The pipeline is **not magic** — understanding it helps with debugging and performance.
