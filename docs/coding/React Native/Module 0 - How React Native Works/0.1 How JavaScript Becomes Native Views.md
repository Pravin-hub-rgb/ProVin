# Doc 0.1 — How JavaScript Becomes Native Views

## Cheat Sheet (Quick Recall)

- JS bundle runs in a JS engine (Hermes) inside a native app shell.
- React renders a virtual tree; renderer turns it into native view instructions.
- Instructions cross JS↔native via Bridge (old) or JSI (new architecture).
- Native side creates/updates real native views (Android `View`, iOS `UIView`).
- Events (tap, scroll) flow back to JS, triggering re-render.

## Main Content

### SOCH

React Native mein hum JS/TS likhte hain, lekin phone sirf native code samajhta hai. Toh sawaal: JS code kaise screen pe real native view ban jata hai? Agar yeh pipeline nahi samjhe, toh performance issues, debugging, aur limits samajh nahi aayenge. Isliye pehle pipeline dekhna hai — code baad mein.

### CONCEPT

React Native app mein teen cheezein involved hoti hain:

1. **Your JavaScript code** — components, state, logic.
2. **Native app shell** — thin native (Kotlin/Swift) app jo JS engine host karta hai.
3. **Phone's UI toolkit** — real native views (Android `View`, iOS `UIView`).

JS screen ko directly touch nahi karta. JS describe karta hai "screen pe kya hona chahiye"; native side draw karta hai.

Pipeline (6 steps):

1. **Bundle your JS.** Code ek single JS file (bundle) mein bundle hota hai. Dev mein Metro serve karta hai; production mein app ke andar ship hota hai.
2. **Start JS engine.** Native app Hermes (modern RN) start karta hai. Bundle uske andar run hota hai.
3. **Render to virtual tree.** React as usual run hota hai — components elements return karte hain. RN renderer isse instructions mein convert karta hai: "View banao in styles ke saath, Text andar daalo."
4. **Send instructions to native.** Instructions JS se native tak cross hoti hain. Old architecture mein Bridge (async JSON messages) se; new architecture mein JSI (direct, synchronous-ish calls) se.
5. **Native draws real views.** Native side real native views create/update karta hai. Phone ka compositor screen pe draw karta hai.
6. **Events flow back.** Tap par native view event JS ko bhejta hai, JS `onPress` chalata hai, state update hota hai, re-render hota hai.

### CODE

Is doc mein koi app code nahi — yeh pipeline theory hai. Pehla code Batch 1 mein aayega. Lekin ek chhota example jo pipeline dikhata hai:

```tsx
// Yeh JS component describe karta hai "screen pe kya hona chahiye"
function Greeting() {
  return (
    <View>
      <Text>Hello</Text>
    </View>
  );
}
```

Line-by-line:

- `function Greeting()` — ek component define kiya.
- `return (...)` — describe kiya View ke andar Text hona chahiye.
- `<View>` / `<Text>` — ye HTML nahi hain, native building blocks hain. RN renderer inhe native instructions mein convert karega.

## Common Mistakes

- Sochna ki React Native WebView use karta hai — nahi, real native views render hoti hain.
- Bridge aur JSI ko same samajhna — Bridge async + serialized; JSI direct + synchronous-ish.
- Heavy JS work main thread pe karna — UI thread communication block hoti hai.

## Khud Try Karo

1. `npx create-expo-app pipeline-demo` chalao, `app/index.tsx` open karo, ek `Text` change karo, save karo — phone update hota hai. Yeh pipeline ka step 6 (events/re-render) live dekh lo.
2. DevTools (shake phone → "Open JS Debugger") mein console dekho — JS engine (Hermes) confirm hoga.

## Summary

- JS bundle → Hermes engine → React virtual tree → native instructions (Bridge/JSI) → real native views → events back to JS.
- React Native is not WebView; real native views render hoti hain.
- Pipeline samajhna debugging aur performance ke liye zaroori hai.

**In Your Own Words**

1. In your own words, how does JavaScript become a native view on screen?

<details>
<summary>Sample Answer</summary>

**Answer:** JS runs in an engine (Hermes), React renders a virtual tree, instructions cross to native (via bridge/JSI), and native creates real views (Android View / iOS UIView) that the phone draws.

</details>

2. Why is React Native not just a WebView app?

<details>
<summary>Sample Answer</summary>

**Answer:** Because it renders real native views using the OS's UI toolkit, not HTML in a browser, so scrolling, animations, and gestures feel native.

</details>

3. What is the "bundle"?

<details>
<summary>Sample Answer</summary>

**Answer:** The single JavaScript file containing all your app code, served by Metro in dev and shipped inside the app in production.

</details>

4. Where does your `onPress` handler actually run?

<details>
<summary>Sample Answer</summary>

**Answer:** In the JavaScript engine; the native view sends the tap event back to JS, which runs the handler and re-renders.

</details>

5. Name one thing that can still require native code even in React Native.

<details>
<summary>Sample Answer</summary>

**Answer:** Deep platform features not exposed by React Native/Expo (e.g., a custom native SDK or very specific hardware access).

</details>

## What It Is NOT

- ❌ React Native is **not a WebView** — real native views render hoti hain.
- ❌ JS does **not** directly touch the screen — native side draw karta hai.
- ❌ Pipeline is **not** magic — understanding it helps with debugging and performance.
