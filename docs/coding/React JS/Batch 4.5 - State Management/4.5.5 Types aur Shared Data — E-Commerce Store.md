## Step 5 — Shared Types & Data

The `products` array lives in two files now — `App.tsx` and `ProductDetail.tsx`. It works. That's exactly what makes it dangerous.

### 5.1 "What's the real cost of the copy-paste?"

Walk the bug: the client adds a 4th product. You update `App.tsx` — the card shows on the store. You forget `ProductDetail.tsx`. Click the new card → `/product/4` → "Product not found". **A product that visibly exists returns 404.** The client loses trust; you lose an hour finding two "identical" arrays that drifted apart.

**Decision:** one source of truth. DRY — Don't Repeat Yourself — isn't a style preference; it's this exact bug wearing a philosophy costume.

### 5.2 "What shape is a product — and who says so?"

Two files need to agree on a Product's fields. When agreement is written by hand, it drifts. TypeScript enforces it — **Decision:** a `Product` interface in its own file:

`src/types.ts`:

```ts
export interface Product {
  id: number
  name: string
  price: number
  image: string
  category: string
}
```

Notice `category` — the arrays already had it; the card's props interface (4.5.3) didn't. Types aren't just documentation — they *catch* what a hand-written props list misses.

### 5.3 "Where does the data live?"

**Decision:** one data file:

`src/data.ts`:

```ts
import type { Product } from './types'

export const products: Product[] = [
  { id: 1, name: "Wireless Headphones", price: 2499, image: "https://images.unsplash.com/photo-1505740420928-5e560c06d30e?w=400&h=400&fit=crop&q=80", category: "electronics" },
  { id: 2, name: "Cotton T-Shirt", price: 799, image: "https://images.unsplash.com/photo-1521572163474-6864f9cf17ab?w=400&h=400&fit=crop&q=80", category: "clothing" },
  { id: 3, name: "Running Shoes", price: 3999, image: "https://images.unsplash.com/photo-1542291026-7eec264c27ff?w=400&h=400&fit=crop&q=80", category: "footwear" },
]
```

`import type { Product }` — the `type` keyword says "this import exists for the compiler, not the browser bundle." TypeScript interfaces vanish at runtime; `import type` makes that explicit and keeps the bundle clean.

Then delete the array from `App.tsx` and `ProductDetail.tsx`:

```tsx
// App.tsx
import { products } from './data'

// ProductDetail.tsx
import { products } from '../data'
```

One array, two importers. Add product 4 in `data.ts` and both pages see it instantly — the 404 bug is structurally impossible now.

### 5.4 "What changes in ProductCard?"

The card's hand-written props interface (`id: number; name: string...`) now duplicates the Product type — the same DRY crime in miniature. **Decision:** the card takes the whole `Product` object, typed by the shared interface:

```tsx
import { Link } from 'react-router-dom'
import type { Product } from '../types'

interface ProductCardProps {
  product: Product
}

export default function ProductCard({ product }: ProductCardProps) {
  return (
    <Link to={`/product/${product.id}`} className="block border rounded-lg overflow-hidden shadow-sm hover:shadow-md transition-shadow focus-visible:ring-2 focus-visible:ring-blue-400">
      <img src={product.image} alt={product.name} className="w-full h-64 object-cover" />
      <div className="p-4">
        <h2 className="text-lg font-semibold">{product.name}</h2>
        <p className="text-xl font-bold text-green-600">{product.price}</p>
      </div>
    </Link>
  )
}

```

Same card as 4.5.4 — only the signature changed, and every reference inside now goes through `product.`.

Why one `product` prop instead of `{...product}`? **Explicit beats silent.** The interface says "a Product, whole" — add a field to `Product` and this component still compiles, still works. With a spread, a renamed field fails *somewhere* with a vague error. The object prop is a contract; the spread is a mystery bag.

```tsx
<ProductCard key={product.id} product={product} />
```

**TEST:** store renders identically. Click any card — detail works. Add a product to `data.ts` by hand: it appears in the grid AND opens a working detail page. That's one source of truth, proven.

## Common Mistakes (Senior Dev Blind Spots)

- **Two sources of truth:** "it works" is not the bar — *one copy* is. Two arrays drifted apart is a production incident in waiting.
- **Hand-duplicating types:** if a props interface re-lists Product's fields, it's a second Product type. Reuse the interface.
- **`import type` vs `import`:** both work, but `import type` documents intent and guarantees nothing runtime leaks into the bundle.
- **Extracting data before it's duplicated:** one copy in one file is *fine*. Extraction pays when the second copy appears — 4.5.4 created that moment.

## Try It Yourself (Active Recall)

1. Add product 4 to `data.ts` only. Where does it show up? What breaks? (Nothing — that's the point.)
2. In `ProductCardProps`, try changing `product: Product` to `product: string` — read the error. Which line does TypeScript point to?
3. 4.5.2 hardcoded the product array straight inside `App.tsx`; 4.5.5 extracts it into `data.ts` with a shared type. Why is hardcoding fine for a quick demo but wrong once two components need the same data? (One usage vs two; no shared shape to enforce.)

## Summary (The Developer's Mental Model)

| Concept | Developer's Thought |
|---|---|
| DRY = bug prevention | Two copies drift; one copy can't |
| Types as contracts | The interface is the agreement both files sign |
| `import type` | For the compiler, not the bundle |
| Explicit prop > spread | `product: Product` is a contract; `{...product}` is a mystery bag |
