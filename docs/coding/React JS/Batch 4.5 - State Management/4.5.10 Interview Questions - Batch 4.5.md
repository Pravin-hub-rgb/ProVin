### 45. When should you use `useReducer`?

**Answer:** When state logic is complex — multiple related sub-values, or the next state depends on the previous state **and** an action (forms, carts, wizards). The reducer is a pure function, so transitions are predictable and trivial to test.

**Likely follow-up:** *vs `useState`?* — one or two simple values → `useState`; interdependent updates where ad-hoc setters tangle → `useReducer` (and it's the same pattern Redux uses, easing the move to a store).

### E1. What is a reducer, and why must it stay pure?

**Answer:** A reducer is a pure function `(state, action) => newState`—it reads the current state and the dispatched action, and returns the next state. Every possible transition lives in one typed `switch`, so the whole state machine is readable in one place. It must stay pure because React may call it more than once for the same dispatch (Strict Mode double-invokes in development); impure reducers (API calls, `localStorage`, `Math.random()`) make results unpredictable and untestable. Side effects belong in components—a `useEffect` reacting to the state change.

**Likely follow-up:** *Where did you put the persistence logic in your store?*—the cart reducer only transitions state; any save-to-`localStorage` happens in a `useEffect` that watches the cart state.

### E2. How do TypeScript discriminated unions make actions safe?

**Answer:** Each action shape shares one discriminant property (`kind`) with a literal type, and the union `CartAction = | { kind: 'ADD_ITEM'; product: Product } | { kind: 'REMOVE_ITEM'; id: number } | ...` lists every legal shape. Inside `switch (action.kind)`, TypeScript narrows the action to exactly one member per `case`—so `action.product` in the `REMOVE_ITEM` case is a compile error, autocomplete shows only the payload fields that exist, and dispatching with a missing payload fails before the app ever runs.

**Likely follow-up:** *Why `kind` and not `type`?*—`type` is also a TS keyword; both work as the property name, but `kind` avoids the visual collision (Redux convention is `type`—same mechanics).

### E3. How do useReducer and Context combine into a mini-store?

**Answer:** One provider component owns the `useReducer` and hands `{ items, dispatch }` (state + the dispatch function) through Context's `value`. Any component in the tree calls the custom hook (`useCart()`) and can read the state or dispatch an action—no prop threading. The reducer stays the single brain; Context is just the delivery network. It's the pattern for when multiple distant components share one state machine, and it maps directly onto Redux/Zustand later—provider = store, dispatch = dispatch, reducer = reducer.

**Likely follow-up:** *Cost?*—every consumer re-renders on any state change; fine at this scale, and the Batch 5 tools (`memo`/`useMemo`/`useCallback`) or Zustand's selector subscriptions are the escalation path.

### E4. In the E-Commerce Store, why Context instead of prop drilling?

**Answer:** The cart state had to reach components that props couldn't reach cleanly: `ProductCard` is a deep child of the store page, and the cart drawer / checkout are sibling *routes*—`Routes` renders them independently, so threading props through `App.tsx` into route elements would mean wiring state through components that never use it. Context fixed delivery (write once in the provider, read anywhere) and `useReducer` fixed the logic (four action shapes—add, remove, quantity, clear—centralized in one typed reducer with the quantity-floor rule enforced in exactly one place).

**Likely follow-up:** *Why not just `useState` in `App.tsx`?*—`App` would become a prop relay and every mutation rule would scatter across call sites; the reducer+Context pair keeps the brain in one file and delivery out of the component tree entirely.
