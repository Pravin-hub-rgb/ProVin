**3. Decide folder structure.** The gym was one page — everything went into `components/`. This project has **URLs** (`/product/1`, `/checkout`) — URLs mean routing, and routed views live in `pages/`. Cart state will be shared by four components — shared state gets its own folder:

```
src/
  components/     ProductCard.tsx, CartDrawer.tsx
  pages/          ProductDetail.tsx, Checkout.tsx, OrderConfirmed.tsx
  context/        CartContext.tsx
  data.ts         the products array
  types.ts        Product, CartItem
  App.tsx         the routes
```

> **Key insight:** I once dumped every view into `components/` out of habit — then spent an afternoon hunting which file rendered which URL. **Structure follows the project's shape, not your habit.** Pages for routes, components for reusable pieces, context for shared state.

## Step 1 — Project Setup

Three questions: new project or existing? Is Tailwind actually wired? Where do files go? One at a time.

### 1.1 "New project or existing?"

**Decision:** a fresh Vite + React project. Not the gym, not the To-Do — one client, one repo.

```bash
npx create-vite@latest ecommerce-store --template react-ts
# bun: bunx create-vite@latest ecommerce-store --template react-ts
cd ecommerce-store
npm run dev
# bun: bun run dev
```

Browser shows Vite's default page. Open `src/App.tsx`, wipe the boilerplate, keep a heading:

```tsx
function App() {
  return <h1 className="text-3xl font-bold p-8">E-Commerce Store</h1>
}

export default App
```

### 1.2 "Is the Tailwind setup right? Verify."

Tailwind v4 needs exactly three pieces (the full converter story lives in 4.1.1): **install** the packages, **register** the Tailwind plugin in `vite.config.ts` so Vite knows to process Tailwind classes, and **import** Tailwind once in `src/index.css` so its utilities actually load:

```bash
npm install tailwindcss @tailwindcss/vite
# bun: bun add tailwindcss @tailwindcss/vite
```

```ts
// vite.config.ts — register the plugin
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  plugins: [react(), tailwindcss()],
})
```

```css
/* src/index.css — import once, everything after is classes */
@import "tailwindcss";
```

**TEST:** the heading renders big and bold = Tailwind is wired. Unstyled text = recheck the plugin registration in `vite.config.ts` before writing one more line.

### 1.3 "Where do files go?"

Decided already in the first move. Create the empty folders now — `components/`, `pages/`, `context/`. Leave `data.ts` and `types.ts` for later: they appear in 4.5.5, when real code needs them.

> **Key insight:** don't create files you have no code for. An empty `data.ts` is noise; a folder is cheap scaffolding you'll fill this series. Feel the difference — folders = plan, files = code.

**TEST:** dev server running, styled heading visible, three folders created.

## Common Mistakes (Senior Dev Blind Spots)

- **Reusing the gym repo:** two clients in one project = merged CSS, broken imports, git history soup. One client, one repo.
- **Skipping the verify:** you write five files, everything's unstyled, and now you're debugging CSS setup with a forest of components. Verify Tailwind with ONE styled element first.
- **Folders as decoration:** a `utils/` folder you never fill is clutter. Create structure when the shape demands it — that's why `data.ts` waits for 4.5.5.

## Summary (The Developer's Mental Model)

| Decision | Thought |
|---|---|
| One project per client | Separate repos keep CSS, state, and git history clean |
| Structure follows shape | URLs → `pages/`; reusable UI → `components/`; shared state → `context/` |
| Verify setup early | One styled element before five unstyled files |
| Folders before files | Plan in folders; files appear when code exists |
