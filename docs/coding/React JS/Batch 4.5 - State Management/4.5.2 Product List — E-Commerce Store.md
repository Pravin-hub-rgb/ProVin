## Step 2 — Product List

The store page shows products. Two decisions hide in that sentence: where does product data live, and how does the layout respond to screen size? Same discipline as the gym — decide first, type second.

### 2.1 "Where does the data live?"

**Decision:** hardcode a `products` array inside `App.tsx` — for now. Three reasons this is the right *first* move:

1. **The UI is still unknown.** Hardcoded data means you see real cards on screen in minutes.
2. **Three products is small.** Extracting to a separate file has a cost — imports, file hops. Pay it only when duplication starts to hurt (that moment arrives in 4.5.4).
3. **It matches the SRD exactly.** The client listed these three products.

Each field earns its place: `id` becomes React's `key` in a second, `price` is a **number** because the cart will multiply price × quantity, `image` is a URL, `category` labels the card.

### 2.2 "One column, two, three — how does the grid decide?"

Tailwind grids work mobile-first: the unprefixed classes (grid-cols-1) are the **base** — they apply at every screen size, so they describe the phone layout. The prefixed classes (sm:grid-cols-2, lg:grid-cols-3) are **overrides** that switch on once the screen crosses that breakpoint. Describe the smallest layout first, then let bigger screens upgrade it — one component serves every screen size, and no hand-written media queries anywhere.

```
375px  → 1 column (stacked cards)
640px  → 2 columns (sm:)
1024px → 3 columns (lg:)
```

```tsx
{products.map((product) => (
  <div key={product.id} className="border rounded-lg overflow-hidden shadow-sm hover:shadow-md transition-shadow">
    <img src={product.image} alt={product.name} className="w-full h-64 object-cover" />
    <div className="p-4">
      <h2 className="text-lg font-semibold">{product.name}</h2>
      <p className="text-xl font-bold text-green-600 mt-2">₹{product.price}</p>
    </div>
  </div>
))}
```

Class by class:
- `grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-6` — the responsive switch. Mobile stacks, tablet goes 2-up, desktop 3-up.
- `key={product.id}` — React identifies each card by `id`, not position. When the cart re-renders the list, keys stop React from confusing cards.
- `w-full h-64 object-cover` — photo fills a fixed-height box; `object-cover` **crops** to fit instead of stretching. Different-shaped photos, identical-looking cards.
- `hover:shadow-md transition-shadow` — card lifts on hover. Desktop polish only — mobile has no hover, so this never fires there.

Note the card has no button — the demo's store page is display-only: you click a product to reach its detail page, and add to cart from there (the detail page's button gets wired to a cart in 4.5.6). The grid is for looking; the detail page is for buying.

One detail about the demo embedded in 4.5.1: its product grid uses `@container` on the wrapper and `@md:grid-cols-2 @xl:grid-cols-3` on the grid — **container queries**, not viewport breakpoints. (`@md` = the container is at least 448px wide, `@xl` = at least 576px.) Why different from the code you just wrote? The demo lives inside the notes app's narrow content column — the browser window can be wide while the demo itself is squeezed against the sidebar. Viewport breakpoints like `sm:` ask "how wide is the browser?" — the answer stays "wide", so the cards never stack. Container queries ask "how wide is MY box?" — the cards respond to the space they actually get. When you build the project yourself as a full-page app, stick with `sm:`/`lg:`; viewport breakpoints are the right tool there.

```tsx
function App() {
  const products = [
    { id: 1, name: "Wireless Headphones", price: 2499, image: "https://images.unsplash.com/photo-1505740420928-5e560c06d30e?w=400&h=400&fit=crop&q=80", category: "electronics" },
    { id: 2, name: "Cotton T-Shirt", price: 799, image: "https://images.unsplash.com/photo-1521572163474-6864f9cf17ab?w=400&h=400&fit=crop&q=80", category: "clothing" },
    { id: 3, name: "Running Shoes", price: 3999, image: "https://images.unsplash.com/photo-1542291026-7eec264c27ff?w=400&h=400&fit=crop&q=80", category: "footwear" },
  ]

  return (
    <div className="max-w-6xl mx-auto p-8">
      <h1 className="text-3xl font-bold mb-8">E-Commerce Store</h1>
      <div className="grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-6">
        {products.map((product) => (
          <div key={product.id} className="border rounded-lg overflow-hidden shadow-sm hover:shadow-md transition-shadow">
            <img src={product.image} alt={product.name} className="w-full h-64 object-cover" />
            <div className="p-4">
              <h2 className="text-lg font-semibold">{product.name}</h2>
              <p className="text-xl font-bold text-green-600 mt-2">₹{product.price}</p>
            </div>
          </div>
        ))}
      </div>
    </div>
  )
}

export default App
```

`max-w-6xl mx-auto p-8` — the container pattern: `max-w-*` caps the width so content lines stay readable on huge screens, `mx-auto` centers whatever space is left, `p-*` pads it. This trio is the standard wrapper for full pages — you will reach for it in every project.

**TEST:** drag the window. 375px → one stack. 768px → two up. 1280px → three up. Photos crop cleanly — nothing squashed, nothing stretched.

## Common Mistakes (Senior Dev Blind Spots)

- **Prices as strings:** `"₹2499"` displays fine and breaks every later calculation. Number in data, `₹` in JSX.
- **Missing `key`:** React warns in the console. A static list tolerates it; a cart (add/remove) will not.
- **`object-cover` forgotten:** the default `object-fill` stretches a photo into any box shape — squash city.
- **`alt` skipped or generic:** `alt="image"` makes a screen reader say "image" three times. The product's name IS the alt text.
