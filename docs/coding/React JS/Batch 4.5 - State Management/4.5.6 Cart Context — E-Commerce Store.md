## Step 6 — Cart Context

Products work; buttons don't. "Add to Cart" needs a cart — and the cart is needed by four components at once: the detail page's button, the drawer, the header count, and checkout. Before typing `useState`, decide *where state lives*.

### 6.1 "Why not just useState in App and pass props down?"

Try the thought experiment. Cart state in `App.tsx`:

- `ProductCard` (deep child) needs the dispatch → prop through `HomePage` → `ProductCard`.
- `HomePage`'s header needs the count → same prop, also for `CartDrawer`.
- Checkout (a sibling route) needs items *and* dispatch → but `Routes` renders it from `App` — pass through again.

That's **prop drilling**: every intermediate component carries props it doesn't use, and any state change re-renders the whole chain. With two levels it's ugly; with five it's unmaintainable.

**Decision:** React's built-in answer for *app-wide* state — **Context**. One provider at the top; any component underneath reads it directly, no threading.

### 6.2 "useState or useReducer?"

A pile of `setCart(...)` calls scatters the change logic across components — every button writes its own update code. A **reducer** collects every transition into one function — the same tool you learned in 4.5.0. On paper, the cart has four actions:

| Action | Rule | Built when |
|---|---|---|
| `ADD` | exists → quantity +1; new → append with quantity 1 | now — its buttons already exist |
| `REMOVE` | drop the item | 4.5.7 — the drawer's Remove button |
| `UPDATE_QTY` | set quantity | 4.5.7 — the drawer's +/- buttons |
| `PLACE_ORDER` | empty the cart | 4.5.8 — checkout |

See the pattern: **each case is built together with the button that calls it.** Today only `ADD` has a button (the detail page — the demo's flow is Store — Detail — Add to Cart, so the grid carries no button) — so today the reducer gets one case. The rest arrive with their UI.

And `CartItem` joins `Product` in `src/types.ts`:

```ts
export interface CartItem {
  productId: number
  name: string
  price: number
  image: string
  quantity: number
}
```

Why `productId` and not `id`? The cart item is *derived from* a Product — the distinct name says "this is the cart's handle," and avoids two `id` fields colliding in one object.

### 6.3 The reducer — one case, and no UI needed

`src/context/cartReducer.ts`:

```tsx
import type { CartItem } from '../types'

export type CartAction =
  | { kind: 'ADD'; product: { id: number; name: string; price: number; image: string } }

export function cartReducer(state: CartItem[], action: CartAction): CartItem[] {
  switch (action.kind) {
    case 'ADD': {
      const existing = state.find(i => i.productId === action.product.id)
      if (existing) {
        // already in the cart - bump quantity instead of adding a second row
        return state.map(i =>
          i.productId === action.product.id
            ? { ...i, quantity: i.quantity + 1 }
            : i
        )
      }
      // not there yet - a new array with the product appended
      return [...state, { ...action.product, productId: action.product.id, quantity: 1 }]
    }
    default:
      return state
  }
}
```

One member today. Notice what the second argument's type really says: `action: CartAction` is not one fixed shape - `CartAction` is the registry of every action this app can ever send. When a future case needs completely different data, the function signature does not change; the need joins the union as a new member:

```tsx
| { kind: 'REMOVE'; id: number }    // future (4.5.7): an id instead of a whole product
```

Dispatch must match at least one member, and the switch's narrowing from 4.5.0 keeps every case honest: inside `case 'REMOVE'`, TypeScript knows this action is the REMOVE member, so `action.product` does not exist there - `action.id` does. The signature stays `CartAction`; the union grows.
One case. Compare it to the counter reducer from 4.5.0 — same shape, three differences:

1. `state` is an array now (the cart items), not a number
2. The action carries a payload: `product` — exactly the payload idea from the discriminated unions (`kind` picks the case, the other fields ride along)
3. The body has two paths: already in the cart? `map` a new array with quantity bumped. Not there? spread the product into a new object (`productId: action.product.id` — the rename from `id` to `productId` happens right here) and append.

**Where does `action.product` come from? Follow the object.**

`onClick={() => dispatch({ kind: 'ADD', product })}` - that shorthand is `{ kind: 'ADD', product: product }`, and `product` is the detail page's own variable: the object `useParams` + `find` pulled out of the URL in 4.5.4. The clicked product travels *inside* the object you dispatch.

Now the wire, and it is short: `dispatch(x)` means exactly one thing - React calls `cartReducer(currentState, x)`. The object you pass to dispatch becomes the reducer's second argument; the reducer just names it `action`. So `action.kind` is the `kind` you sent, and `action.product` is the product you sent. Same object, new name - nothing sits in between.

And the `find` line: `state` is the cart array so far, and `find` walks it asking one question per item - does this item's `productId` equal the clicked product's `id`? If some item matches, `find` returns it (already in the cart - the quantity-bump path). If the array ends with no match, `find` returns `undefined` (not there - the append path). One line, two outcomes.

Full trace - first click on `/product/1`:

```
click → dispatch({ kind: 'ADD', product: { id: 1, name: 'Wireless Headphones', ... } })
      → cartReducer([], { kind: 'ADD', product: { id: 1, ... } })   // state = [] (empty cart)
         existing = [].find(i => i.productId === 1)                  // nothing to match → undefined
      → append → [{ productId: 1, name: 'Wireless Headphones', price: 2499, quantity: 1 }]
```

Second click, same product:

```
click → cartReducer([{ productId: 1, quantity: 1 }], { kind: 'ADD', product: { id: 1, ... } })
         existing = found (productId 1 === 1)
      → map → quantity 1 + 1 = 2
```
Every case returns a **new** array (`map`, spread) — never `state.push(...)` or `item.quantity++`. React detects change by *reference*, and a mutated array looks "unchanged" to it.

**TEST the reducer with no UI at all** — the same proof you saw in 4.5.0 with `array.reduce`:

```tsx
import { cartReducer } from './context/cartReducer'
import { products } from './data'

const actions = [
  { kind: 'ADD', product: products[0] },
  { kind: 'ADD', product: products[0] },
  { kind: 'ADD', product: products[1] },
]

const items = actions.reduce(cartReducer, [])
// items = one entry with quantity 2, one entry with quantity 1
```

A reducer is a plain function — it needs no component, no button, no screen. That is why we build it first: the brain works before anything can click it.

### 6.4 The context — the pipe

The reducer works, but no component can call it: each component calling `useReducer` would get its OWN private cart (two components = two separate carts). One cart, reachable from anywhere = Context.

Three small pieces, one at a time.

**Piece 1 — the pipe itself.** `src/context/CartContext.tsx`:

```tsx
import { createContext } from 'react'
import type { CartItem } from '../types'
import type { CartAction } from './cartReducer'

interface CartContextType {
  items: CartItem[]
  dispatch: React.Dispatch<CartAction>
}

const CartContext = createContext<CartContextType | null>(null)
```

`createContext` makes the pipe object. The `null` is the default value when nobody has provided anything yet — which the guard in Piece 3 turns into a clear error.

**Piece 2 — the provider.** Append to the same file (update the React import to add `useReducer` and `type ReactNode`):

```tsx
import { createContext, useReducer, type ReactNode } from 'react'
import { cartReducer } from './cartReducer'

export function CartProvider({ children }: { children: ReactNode }) {
  const [items, dispatch] = useReducer(cartReducer, [])

  return <CartContext value={{ items, dispatch }}>{children}</CartContext>
}
```

Recognize the line from 4.5.0: `useReducer(cartReducer, [])` — same call as `useReducer(reducer, 0)`, except the state is an array and the starting value is `[]` (an empty cart). The provider owns the ONE reducer instance and hands `{ items, dispatch }` to everyone below.

(Note: `<CartContext value={...}>` is React 19 syntax — the context object itself acts as the provider. On React 18 you would write `<CartContext.Provider value={...}>`. The Vite template this project uses ships React 19, so the shorthand works.)

**Piece 3 — the hook with the guard.** Append:

```tsx
import { useContext } from 'react'

export function useCart() {
  const context = useContext(CartContext)
  if (!context) throw new Error('useCart must be used within CartProvider')
  return context
}
```

Without the guard, a missing provider returns `null` and the crash happens five files away from the cause. Fail at the scene.

### 6.5 Wrap the app in it

`main.tsx` — provider above everything, same position logic as `BrowserRouter`:

```tsx
import { CartProvider } from './context/CartContext'

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <BrowserRouter>
      <CartProvider>
        <App />
      </CartProvider>

  </StrictMode>

```

Two spots change in `ProductDetail.tsx` — the rest stays exactly as 4.5.4 built it:

What you do NOT have yet: no way to SEE the cart (the navbar button and the drawer do not exist — that is 4.5.7, and the `REMOVE`/`UPDATE_QTY` cases arrive right there with their buttons, as the table promised). `PLACE_ORDER` waits for checkout in 4.5.8.

## Common Mistakes (Senior Dev Blind Spots)

- **Mutating state:** `state.push(item)` "works" — and React renders nothing. Reducers must return new arrays/objects. Every case above uses `map`, `filter` or spread for exactly this reason.
- **Context without the null guard:** a missing provider returns `null` from `useContext`, and the crash happens in some unrelated component five files away. The guard throws at the scene: "useCart must be used within CartProvider".
- **Reducer as a dumping ground:** formatting? totals? No — the reducer only transitions state. Derived values (totals) are computed where displayed: `items.reduce((sum, i) => sum + i.price * i.quantity, 0)`.
- **Two components calling `useReducer` directly:** two private carts — adding from one page updates nothing anywhere else. One cart = one `useReducer`, owned by the provider.
