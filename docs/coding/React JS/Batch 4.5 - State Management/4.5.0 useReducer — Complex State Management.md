## The Ceiling of useState

Through Batch 4, `useState` carried every piece of state you built: form fields, toggles, the whole auth session. One hook call, one value, one setter. It earned that trust. But every tool has a ceiling, and you can see this one coming with the tiniest state that starts to grow *rules*: a counter.

---
## Starting Small — A Counter, First With useState

We start with `useState` — judge for yourself where it stops being enough.

```tsx
// Counter.tsx
import { useState } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <button onClick={() => setCount(c => c - 1)}>-</button>
      <button onClick={() => setCount(0)}>Reset</button>
    </div>
  )
}
```

Be honest: this is *fine*. One variable, three actions, nothing scattered. If a counter stayed like this forever, there'd be nothing to fix — and that's worth saying out loud, because `useReducer` is not a "better `useState`" you should reach for everywhere. It's a tool for when state grows **rules**.

### Now Six Actions

The app grows. The counter needs increment, decrement, reset, add5, double and halve:

```tsx
// ❌ still useState — change logic scattered everywhere
export default function Counter() {
  const [count, setCount] = useState(0)

  const increment = () => setCount(c => c + 1)
  const decrement = () => setCount(c => c - 1)
  const reset = () => setCount(0)
  const add5 = () => setCount(c => c + 5)
  const double = () => setCount(c => c * 2)
  const halve = () => setCount(c => Math.floor(c / 2))

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={increment}>+</button>
      <button onClick={decrement}>-</button>
      <button onClick={reset}>Reset</button>
      <button onClick={add5}>+5</button>
      <button onClick={double}>×2</button>
      <button onClick={halve}>÷2</button>
    </div>
  )
}
```

And again — be honest: **this still works.** Nothing breaks at runtime. So what's actually wrong? Not the running code — the *shape of the knowledge*. The question "what can happen to the count, and what does each possibility do?" has no single answer in this file. It's smeared across six one-liners, wherever there happened to be space. A teammate has to read the whole component to rebuild the list. Every new action means another function, in yet another spot.

What we want is one place where every possible change lives. And there is a bigger principle underneath — **related state belongs under one roof.** On this counter the roof holds one value, `count`, with six rules for changing it. Bigger state makes the roof matter even more, because the state itself comes in related pieces that must move together — this batch's cart holds items, coupon and discount, and they change as a unit (its reducer arrives in 4.5.6). Scattering related pieces across separate `useState` calls means nothing ties them together. Under one roof, every relationship lives in exactly one function — and the hook that holds the state plus its rules together is `useReducer`.

## useReducer — What It Is

You already know this line from the counter:

```tsx
const [count, setCount] = useState(0)
```

```tsx
const [count, dispatch] = useReducer(reducer, 0)
```

Two arguments, same as `useState` — but look closely at what each one is:

- `0` — the starting value. Same as always.
- `reducer` — YOUR function, the one you defined above. Not built-in, not imported — you wrote it in this file, like any other function.

About the name: `cal`, `updateCount`, `handleChange` — any name works. You pass whatever you named it:

```tsx
function cal(count, action) {
  if (action.kind === 'increment') return count + 1
}

const [count, dispatch] = useReducer(cal, 0)   // pass the name you chose
```

React never checks the name. It only checks what the function does: takes the current state plus one action, returns the new state. `reducer` is simply the name everyone uses — a convention, like `handleClick` for click handlers. Follow it so your code looks familiar to other devs (and future you), but know that it is your choice, not a React rule.

And the return is the same shape as `useState` too: `[count, dispatch]` — the value you render, and the way to change it.

One more thing that may feel new: passing a FUNCTION to React. You already have, twice — `useEffect(() => { ... })` and `setCount(c => c + 1)` both pass functions. The only difference here: instead of writing the function inline, you define it outside (named, with a body for every change) and React calls it every time a `dispatch` happens.

And the one equation to hold onto: **`setCount` = `dispatch` + `reducer`**.

Now let me spell out every part fully, with examples.

You have been writing this line since Batch 1:

```tsx
setCount(c => c + 1)
```

Look at it once more. The part after the arrow — `c + 1` — is the code that actually produces the new value: take the current count, add 1. In JavaScript, that part has a name: it is the **function body** (the code a function runs to produce its result). "Body" is nothing special — it just means the code that does the work.

And notice WHERE you wrote that body: directly inside the `setCount(...)` call. And that setter call itself sits inside your component function (`Counter` — the function that returns JSX). It is not saved in any other function or file. That is what "written inline" means — in the same line, at the same spot where you call the setter.

(Yes, you can also move the body out and call a separate function from the click: `function increment() { setCount(c => c + 1) }`. That works — but every such function still lives inside the component, and you write one per change.)

**With `useReducer`, all these bodies move into ONE function — the reducer.**

You already know this pattern — one function, an argument picks which part runs:

```tsx
function applyChange(count: number, which: string) {
  if (which === 'increment') return count + 1
  if (which === 'decrement') return count - 1
}

applyChange(count, 'increment')   // 'increment' picks the branch
```

`useReducer` is exactly this, with three small changes:

1. The function is named `reducer` — same kind of function, different name
2. Instead of a plain string, you pass a small object — `{ kind: 'increment' }` — so extra data can ride along when needed
3. You do not call it directly; React calls it for you when you call `dispatch`

```tsx
function reducer(count, action) {
  if (action.kind === 'increment') return count + 1   // the body for increment
  if (action.kind === 'decrement') return count - 1   // the body for decrement
}
```

Each `if` line is one body — the code that produces the new value for that one change.

**What is `dispatch` then?**

`dispatch` contains no body at all. It is only the way the component calls the reducer. Here is the counter component doing exactly that:

```tsx
export default function Counter() {
  const [count, dispatch] = useReducer(reducer, 0)   // the reducer from above

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => dispatch({ kind: 'increment' })}>+</button>
    </div>
  )
}
```

The click calls `dispatch`, and what you pass it is just the name of the change you want:

```tsx
dispatch({ kind: 'increment' })
//        ^^^^^^^^^^^^^^^^^^^^ just the name of the change — no body here
```

React takes `{ kind: 'increment' }`, runs the reducer with it, the reducer's `if (action.kind === 'increment')` line matches, and that line's body runs: `count + 1`.

The object `{ kind: 'increment' }` is called an **action**. It does NOT contain the new value — `increment` is not `2` or `5`. It only names the change; the body that produces the new value is in the reducer.

So the equation, spelled out in words: **`setCount` = `dispatch` + `reducer`**. With `setCount`, the body is written inside the setter call, every single time. With `useReducer`, every body is written once, inside the reducer, and `dispatch({ kind })` is how the component asks for one of those bodies to run.

Follow one click: button click → `dispatch({ kind: 'increment' })` → React calls `reducer(currentCount, action)` → reducer returns the new count → UI updates. That is the whole loop.

Why does this matter? Because one function answers "what can happen to this state?" in one place — exactly what the scattered six-action counter was missing.
### Why "Reducer"? The Name Means Something

The name is not random. It comes from `reduce` — the same shape JavaScript already ships as `array.reduce`:

```tsx
const numbers = [1, 2, 3, 4]
const total = numbers.reduce((sum, n) => sum + n, 0)
// reduce = walk the list, fold each item into one running result
```

`reduce` uses a function `(accumulator, currentItem) => nextAccumulator` and folds a whole list into one value. Now look at the reducer's shape:

```tsx
function reducer(state: number, action: Action): number {
  // (currentState, oneEvent) => nextState
}
```

Same shape. `state` is the accumulator — each dispatched action is the next item being folded in. You can prove it by running the counter without React at all:

```tsx
const actions = [
  { kind: 'add5' },
  { kind: 'double' },
  { kind: 'increment' },
]

const finalCount = actions.reduce(reducer, 0)
// the same reducer function, unchanged — (state, action) => newState
```

So the name now makes full sense: `reduce` — just like `array.reduce` folds a list of numbers into one total, the reducer folds one action after another into one state. Click by click, the state ends up holding the result of every action so far. And this arrangement of one function, run again and again with the current value in and the next value out, is older than React — `array.reduce` above was doing the same thing, and React simply reused it in `useReducer`.

And the hook's name? Split it in two: `use` + `Reducer`. Every hook starts with `use` (`useState`, `useEffect`, `useRef`...) — that part never changes. The second part names the job: the hook runs YOUR reducer function for you, on every `dispatch`. So `useReducer` = "use my reducer to manage this state". And notice: even if you named your function `cal`, the hook is still called `useReducer` — the hook's name follows the convention (the kind of function you pass it), not your personal function name.

## The Counter, Converted — Step by Step

### Step 1 — Import

```tsx
import { useReducer } from 'react'
```

### Step 2 — List the Actions

```tsx
type Action =
  | { kind: 'increment' }
  | { kind: 'decrement' }
  | { kind: 'reset' }
  | { kind: 'add5' }
  | { kind: 'double' }
  | { kind: 'halve' }
```

Each action is an object with a `kind` field — it says which function to run. The `Action` type is a **union**: *one of these six shapes*, never two at once. (Unions are a topic of their own — the next section opens them up properly. For now: `kind` says which action, and that's all you need to keep reading.)

### Step 3 — The Reducer (All the Function Bodies)

```tsx
function reducer(state: number, action: Action): number {
  switch (action.kind) {
    case 'increment': return state + 1
    case 'decrement': return state - 1
    case 'reset':     return 0
    case 'add5':      return state + 5
    case 'double':    return state * 2
    case 'halve':     return Math.floor(state / 2)
  }
}
```

The reducer takes the current state and the action, and returns the next state. The `switch` reads `action.kind` and jumps to the matching case. Notice what this function *is*: it's the answer to "what can happen to the count?" — the very question the `useState` version could not answer in one place. Each `case` is one function body — the body for that one change. `dispatch` picks which body runs.

### Step 4 — Call useReducer

```tsx
const [count, dispatch] = useReducer(reducer, 0)
```

Two arguments — the reducer function, and the starting value (`0`). It returns the current state (`count`, like before) and `dispatch` — the way you call the reducer from the UI. Where `setCount` took the *new value*, `dispatch` takes an *action* — which says which function to run.

### Step 5 — Dispatch in the JSX

```tsx
return (
  <div>
    <p>Count: {count}</p>
    <button onClick={() => dispatch({ kind: 'increment' })}>+</button>
    <button onClick={() => dispatch({ kind: 'decrement' })}>-</button>
    <button onClick={() => dispatch({ kind: 'reset' })}>Reset</button>
    <button onClick={() => dispatch({ kind: 'add5' })}>+5</button>
    <button onClick={() => dispatch({ kind: 'double' })}>×2</button>
    <button onClick={() => dispatch({ kind: 'halve' })}>÷2</button>
  </div>
)
```

Follow one click: button → `dispatch({ kind: 'increment' })` → React calls `reducer(0, { kind: 'increment' })` → returns `1` → state updates → re-render → UI shows `1`.

And click again? React stores the last result, and the next dispatch starts from it. Second click: `dispatch({ kind: 'increment' })` → React calls `reducer(1, { kind: 'increment' })` — the 1 is the state the first click left behind — reducer returns 2, UI shows 2. The first argument is always *what the state is right now*, never a hardcoded number. That is why the reducer needs the current state at all.

Compared to the `useState` version:

| useState | useReducer |
|----------|-----------|
| 6 scattered `setCount(c => ...)` calls | One `dispatch({ kind })` — same pattern everywhere |
| New action = write a new function somewhere | New action = add a `kind` + one `case` |
| "What can happen?" — smeared across the component | "What can happen?" — exactly one function |

## Why This Batch Needs This

So far, so small — but you have now seen the shape of the ceiling. When state has *rules* — changes that must check the state itself, or move several fields together — scattered `set` calls cannot hold those rules. One function can.

You are about to build exactly that kind of state. This batch's project is an **E-Commerce Store**, and its cart is rules all the way down: "add" must check whether the product is already in (otherwise the same phone shows up as two separate rows — the bug you have seen on janky shops), and "apply coupon" must move the coupon and the discount together — forget one field and the header says `SAVE10` while the total never drops. That is not a pile of independent `useState` boxes — that is one function holding every change.

The project builds exactly that cart on `useReducer` — its own reducer arrives in **4.5.6**, wrapped in a Context. The rest of this file sharpens the tool for that job — starting with proper TypeScript for actions, because real actions carry data ("add *this* product", "set quantity to *this*"), and loose types are not enough.
## TypeScript's Discriminated Unions

The counter's actions were all identical in shape — just `kind`, no extra data. Real apps aren't. "Add item" needs to know *which item*. "Change quantity" needs an id and a number. This section gives actions proper types.

### What a Union Is

"Union" doesn't mean "all of these at once" — it means **"one of these."**

```tsx
type Status = 'loading' | 'success' | 'error'
// Status is 'loading' OR 'success' OR 'error'
// One value at a time — never all three
```

The `|` (pipe) means **or**. The same works with objects:

```tsx
type Action =
  | { kind: 'increment' }
  | { kind: 'decrement' }
```

(Putting the `|` at the start of each line is just formatting — TypeScript reads it identically.)

### `type` the Keyword vs `kind` the Property

Two `type`-looking words appear here, and they do different jobs:

```tsx
type  CartAction  =  { kind: 'ADD_ITEM'; product: Product }
 ↑ keyword          ↑ property name — could be anything
```

- `type CartAction =` — TypeScript's **keyword** for creating a new type
- `{ kind: 'ADD_ITEM' }` — an ordinary **object property**; you could name it `kind`, `type`, `actionType` — anything

We use `kind` so the word `type` doesn't mean two things on the same line. (Redux-style projects conventionally name this property `type` — same idea, different word.)

### Why "Discriminated"?

"Discriminate" means *to tell apart*. The `kind` property is the **discriminant** — the field that identifies *which member of the union* this object currently is. Every member shares the same discriminant property, each with a unique value — that's the one rule. (If one member used `kind` and another used `type`, TypeScript couldn't tell which property identifies them.)

### Payload

Any property besides the discriminant is **payload** — the data that rides along with the action. Like a function call: `kind` picks which function to run, payload supplies its arguments.

| Action | Discriminant | Payload |
|--------|--------------|---------|
| `ADD_ITEM` | `kind: 'ADD_ITEM'` | `product` |
| `REMOVE_ITEM` | `kind: 'REMOVE_ITEM'` | `id` |
| `UPDATE_QTY` | `kind: 'UPDATE_QTY'` | `id`, `quantity` |
| `CLEAR_CART` | `kind: 'CLEAR_CART'` | none — "empty it" is enough |

### How TypeScript Narrows Inside the Switch

When you `switch (action.kind)`, TypeScript knows exactly which shape the action has inside each `case`:

```tsx
function cartReducer(state: CartState, action: CartAction) {
  switch (action.kind) {
    case 'ADD_ITEM':
      // TypeScript knows: action = { kind: 'ADD_ITEM'; product: Product }
      action.product  // ✅ exists
      action.id       // ❌ error — ADD_ITEM has no id

    case 'REMOVE_ITEM':
      // action = { kind: 'REMOVE_ITEM'; id: number }
      action.id       // ✅
      action.product  // ❌
  }
}
```

Three payoffs: mistakes are caught at compile time, autocomplete shows only what exists in *this* case, and changing a payload flags every wrong usage.

Visual summary:

```
CartAction — a union of possible shapes
    │
    ├── { kind: 'ADD_ITEM'; product: Product }
    ├── { kind: 'REMOVE_ITEM'; id: number }
    ├── { kind: 'UPDATE_QTY'; id: number; quantity: number }
    ├── { kind: 'APPLY_COUPON'; code: string }
    └── { kind: 'CLEAR_CART' }

switch (action.kind) — inside each case, the shape is known exactly
```

## useReducer vs useState — Which One When

**`useState` when:**
- the state is simple (a number, a string, a boolean)
- one or two *independent* values
- one action changes one thing

**`useReducer` when:**
- the state has multiple related fields
- actions must change several fields together (coupon + discount)
- a change must *check the state itself* first (add-to-cart)
- you want every possible change in one function

## What useReducer Is NOT

- **Not a state library.** It's a hook — its state is private to the component that calls it. Two components each calling `useReducer` get two *separate* states. Sharing one state across components is Context's job — which is exactly what 4.5.6 does for the project's cart.
- **Not a replacement for every `useState`.** `const [isOpen, setIsOpen] = useState(false)` stays `useState` forever — simple, independent, no rules.
- **Not Redux.** Redux Toolkit (Batch 6.7) is a separate, heavier library built on this same reducer pattern. Don't confuse the pattern with the library — we meet the library much later, properly.

## Common Mistake — Side Effects in the Reducer

The reducer must be a **pure function** — take state + action, return new state. No API calls, no localStorage writes, no `Math.random()`. React may even call the reducer more than once for the same dispatch, so impurities make results unpredictable:

```tsx
// ❌ Wrong — side effect inside the reducer
function reducer(state, action) {
  case 'SAVE':
    localStorage.setItem('cart', JSON.stringify(state)) // ❌ side effect!
    return { ...state, saved: true }
}

// ✅ Correct — reducer only decides state, side effects live in the component
function reducer(state, action) {
  case 'SAVE':
    return { ...state, saved: true }
}

// In the component:
useEffect(() => {
  localStorage.setItem('cart', JSON.stringify(cart))
}, [cart])
```

## Try It Yourself (Active Recall)

1. What two things does `useReducer` return, and what does each one do?
2. In `dispatch({ kind: 'increment' })`, what does the object contain — the new value, or something else? And what does the reducer do with it?
3. What is the discriminant, and what one rule must every member of a union follow about it?
4. What does "payload" mean, and what does TypeScript know about the payload inside each `case` of the switch?
5. Why must the reducer stay pure — and where do side effects like saving to localStorage go instead?

<details><summary>Sample Answers</summary>

1. `[count, dispatch]` — `count` is the current value (what you render), `dispatch` is how the component calls the reducer: `dispatch({ kind: 'increment' })` hands the reducer the name of the change to run.
2. Only the NAME of the change (`kind: 'increment'`), never the new value. The reducer takes the current state plus that action, finds the matching case, and that case's body produces the new value (`count + 1`).
3. The discriminant is the shared property (`kind`) whose value tells TypeScript which union member an object currently is. The rule: every member must use the same discriminant property — if one used `kind` and another `type`, TypeScript could not tell them apart.
4. Any property besides the discriminant — the data that rides along with the action (like `product` or `id`). Inside each `case`, TypeScript knows the exact shape: `action.product` is allowed in `ADD_ITEM`, while `action.id` there is an error, because that member has no `id`.
5. React may call the reducer more than once for the same dispatch, and its only job is `(state, action) => newState`. Impurities (API calls, localStorage, `Math.random()`) make results unpredictable and untestable. Side effects go in a `useEffect` inside the component, reacting to state changes.

</details>

## Summary (The Developer's Mental Model)

✅ **useReducer** — one central function holding every change
✅ **The equation** — `setCount` = `dispatch` + `reducer`
✅ **Action** — an object with a `kind` (the discriminant) plus optional payload
✅ **dispatch(action)** — how the component calls the reducer
✅ **Reducer** — a pure function: `(state, action) => newState`
✅ **Discriminated unions** — TypeScript narrows every case and catches payload mistakes
✅ `useState` for simple independent state; `useReducer` when state has rules
✅ Side effects never inside the reducer — `useEffect` in the component
