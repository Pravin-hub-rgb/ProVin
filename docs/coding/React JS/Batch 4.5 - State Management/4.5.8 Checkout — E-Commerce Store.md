## Step 8 - Checkout

The drawer's Checkout link points to `/checkout` - a route that doesn't exist yet. Click it right now and you get the routing contract from 4.5.4: the URL changes, the page goes blank.

Where the store stands: products render (4.5.2-4.5.5), clicking a card opens its detail page, Add to Cart fills the cart through the `ADD` case (4.5.6), and the drawer's `[-]`/`[+]`/Remove buttons move items through `UPDATE_QTY` and `REMOVE` (4.5.7). The customer can build a cart - and then the flow stops: there is no way to actually buy anything. This step closes that gap with the **checkout page**.

The feature: a form - name, email, address, pincode - where nothing is accepted until validation passes, and a **Place Order** button that empties the cart through one last reducer case (`PLACE_ORDER`) and navigates forward. Two files: a new `src/pages/Checkout.tsx` holding the form (schema, validation wiring, submit logic), and one `<Route>` line added to `App.tsx` so `/checkout` finally renders something. When this step is done, the drawer's Checkout link lands on a working form; valid input empties the cart and the browser moves to `/order-confirmed` - which shows nothing, because 4.5.9 builds that final page.

And the validation is not new work - 4.4 already built the exact tool for this job.

### 8.1 "Manual validation again, or reuse 4.4?"

**Decision:** React Hook Form + Zod — the 4.4.x pairing. Why not the manual `useState` approach from 4.3? Count the costs: four fields × touched-tracking × error wiring × submit validation. The manual version took 4.3 a whole doc for *two* fields. RHF collapses registration and error wiring; Zod holds all rules in one schema. When you've already paid for the tool, use the tool.

```bash
npm install zod react-hook-form @hookform/resolvers
# bun: bun add zod react-hook-form @hookform/resolvers
```

One last action is missing: `PLACE_ORDER`. 4.5.7 built `REMOVE` and `UPDATE_QTY` with their drawer buttons - checkout's button gets the same treatment. This one needs no payload: "empty the cart" is the whole instruction - the kind is the complete message (4.5.0's payload table said exactly this for `CLEAR_CART`).

In `src/context/cartReducer.ts` - the union grows by one member:

```tsx
export type CartAction =
  | { kind: 'ADD'; product: { id: number; name: string; price: number; image: string } }
  | { kind: 'REMOVE'; productId: number }
  | { kind: 'UPDATE_QTY'; productId: number; quantity: number }
  | { kind: 'PLACE_ORDER' }
```

And the case joins the switch:

```tsx
case 'PLACE_ORDER':
  return []
```

No payload to read, no state to inspect - a fresh empty array is the entire body. Order matters here: extending the union *first* means the dispatch below type-checks. That's the discriminated union doing its job - the compiler knows exactly which shapes exist.

### 8.2 "What are the rules?"

**Decision:** one schema, all rules in one place:

```tsx
const checkoutSchema = z.object({
  name: z.string().min(1, "Name is required"),
  email: z.email("Invalid email"),
  address: z.string().min(1, "Address is required"),
  pincode: z.string().min(6, "Enter 6-digit pincode").max(6),
})
```

Rule by rule:
- `min(1)` on name and address — empty strings are the #1 form input. `.min(1)` is the standard "required."
- `z.email()` — Zod v4's top-level method from 4.4.4 (the old `z.string().email()` is deprecated). Format checking without a regex.
- `pincode` with `min(6).max(6)` — exactly six characters. It's a *string* on purpose: pincodes aren't math, and `Number("011001")` drops the leading zero. Strings for identifiers, numbers for quantities — same rule as prices, mirrored.

### 8.3 The form

`src/pages/Checkout.tsx`:

```tsx
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'
import { Link, useNavigate } from 'react-router-dom'
import { useCart } from '../context/CartContext'

const checkoutSchema = z.object({
  name: z.string().min(1, "Name is required"),
  email: z.email("Invalid email"),
  address: z.string().min(1, "Address is required"),
  pincode: z.string().min(6, "Enter 6-digit pincode").max(6),
})

type CheckoutForm = z.infer<typeof checkoutSchema>

export default function Checkout() {
  const { items, dispatch } = useCart()
  const navigate = useNavigate()
  const { register, handleSubmit, formState: { errors } } = useForm<CheckoutForm>({
    resolver: zodResolver(checkoutSchema),
  })

  const total = items.reduce((sum, i) => sum + i.price * i.quantity, 0)

  const onSubmit = (data: CheckoutForm) => {
    console.log('Order placed:', { ...data, items, total })
    dispatch({ kind: 'PLACE_ORDER' })
    navigate('/order-confirmed')
  }

  if (items.length === 0) {
    return (
      <div className="p-8 text-center" role="alert">
        <h2 className="text-2xl font-bold">Cart is empty</h2>
        <Link to="/" className="text-blue-500 underline mt-4 inline-block">Continue Shopping</Link>
      </div>
    )
  }

  return (
    <div className="max-w-2xl mx-auto p-8">
      <Link to="/" className="text-blue-500 underline mb-6 inline-block">&larr; Back to Store</Link>
      <h1 className="text-3xl font-bold mb-8">Checkout</h1>

      <form onSubmit={handleSubmit(onSubmit)} className="space-y-6" noValidate>
        <div>
          <label htmlFor="name" className="block text-sm font-medium mb-1">Full Name</label>
          <input id="name" {...register('name')} className="border rounded px-3 py-2 w-full focus:outline-none focus:ring-2 focus:ring-blue-400" />
          {errors.name && <p className="text-red-500 text-sm mt-1" role="alert">{errors.name.message}</p>}
        </div>

        <div>
          <label htmlFor="email" className="block text-sm font-medium mb-1">Email</label>
          <input id="email" type="email" {...register('email')} className="border rounded px-3 py-2 w-full focus:outline-none focus:ring-2 focus:ring-blue-400" />
          {errors.email && <p className="text-red-500 text-sm mt-1" role="alert">{errors.email.message}</p>}
        </div>

        <div>
          <label htmlFor="address" className="block text-sm font-medium mb-1">Address</label>
          <textarea id="address" rows={3} {...register('address')} className="border rounded px-3 py-2 w-full focus:outline-none focus:ring-2 focus:ring-blue-400" />
          {errors.address && <p className="text-red-500 text-sm mt-1" role="alert">{errors.address.message}</p>}
        </div>

        <div>
          <label htmlFor="pincode" className="block text-sm font-medium mb-1">Pincode</label>
          <input id="pincode" {...register('pincode')} className="border rounded px-3 py-2 w-full focus:outline-none focus:ring-2 focus:ring-blue-400" />
          {errors.pincode && <p className="text-red-500 text-sm mt-1" role="alert">{errors.pincode.message}</p>}
        </div>

        <div className="border-t pt-4">
          <div className="flex justify-between text-xl font-bold">
            <span>Total</span>
            <span>₹{total}</span>
          </div>
          <button type="submit" className="mt-4 w-full bg-green-600 text-white py-3 rounded hover:bg-green-700 focus:outline-none focus:ring-2 focus:ring-green-400">
            Place Order
          </button>
        </div>
      </form>
    </div>
  )
}
```

The 4.4 machinery, applied:
- `z.infer<typeof checkoutSchema>` — the form's TypeScript type comes *from the schema*. Change a rule, the type follows. One source of truth, again.
- `{...register('name')}` — RHF wires the input: value tracking, ref, change events. No `value`, no `onChange` — that's RHF's whole pitch.
- `formState: { errors }` — Zod messages surface as `errors.field.message`, each with `role="alert"` so screen readers announce failures the moment they appear.
- `noValidate` — the browser's own validation bubbles are *off*; Zod owns every message. Two systems writing error text = inconsistency.
- `handleSubmit(onSubmit)` — Zod validates first; `onSubmit` only runs with valid, typed data. The empty-cart guard (`role="alert"`) catches URL-snoopers who reach checkout with nothing to pay for.

And in `onSubmit`: log the order (simulating the backend call), `dispatch({ kind: 'PLACE_ORDER' })` empties the cart, `navigate('/order-confirmed')` moves forward.

## Common Mistakes (Senior Dev Blind Spots)

- **Dispatching before the action exists:** the reducer's `default` swallows unknown actions *silently* — the cart never empties and nothing errors. Extend the union first; TypeScript then refuses illegal dispatches.
- **Skipping `noValidate`:** the browser's English bubbles fight Zod's messages. One validator, one voice.
- **Pincode as number:** `Number("011001")` → `11001`. Identifiers are strings; only quantities are numbers.
- **Manual validation for multi-field forms:** four `useState` + four error states + one submit handler = the 4.3 tax. RHF + Zod is the paid-off tool.
- **Forgetting the empty-cart guard:** checkout with an empty cart is a support ticket. Guard early, `role="alert"` it.
