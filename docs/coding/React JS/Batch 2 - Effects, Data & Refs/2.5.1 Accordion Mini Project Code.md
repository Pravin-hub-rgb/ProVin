

## Goal

We'll build a simple accordion. First just one section that opens/closes. Then add a second section — and we'll see "oh wait, both opened?" Then we'll fix it by lifting state. Let's start from 0.

---

### Step 1 — Static HTML (single section)

**Think:** One section — a heading and content. No state, no button. Just HTML.

```tsx
function App() {
  return (
    <div>
      <h1>Accordion</h1>
      <h2>What is React?</h2>
      <p>React is a JavaScript library for building user interfaces.</p>
    </div>
  );
}
```

**Test:** The browser shows content. ✅

---

### Step 2 — Turn h2 into a button (make clickable)

**Think:** Right now `<h2>` just displays — the user can't click it. We want the user to click and toggle content. So replace `<h2>` with a `<button>`. The text stays the same, just becomes clickable now.

```tsx
function App() {
  return (
    <div>
      <h1>Accordion</h1>
      <button>What is React? ▼</button>
      <p>React is a JavaScript library for building user interfaces.</p>
    </div>
  );
}
```

The arrow (▼) visually indicates this is an expandable section — closed shows ▼, open shows ▲.

**Test:** Button visible? Clicking does nothing yet — logic comes in the next step. ✅

---

### Step 3 — Button onClick + useState (toggle logic)

**Think:** Clicking the button should toggle content visibility. For this we need `useState` to track whether it's currently open. `false` = closed, `true` = open. On click, set to the opposite of current value.

**Concept — useState:** `useState(false)` — `false` means starts hidden. `setIsActive(!isActive)` — set to the opposite (true → false, false → true).

**Concept — Conditional rendering:** `{isActive && <p>...</p>}` — if `isActive` is true, `<p>` renders. If false, it doesn't. The `&&` operator: left side is true → right side executes.

```tsx
import { useState } from "react";

function App() {
  const [isActive, setIsActive] = useState(false);

  return (
    <div>
      <h1>Accordion</h1>
      <button onClick={() => setIsActive(!isActive)}>
        What is React? {isActive ? "▲" : "▼"}
      </button>
      {isActive && <p>React is a JavaScript library for building user interfaces.</p>}
    </div>
  );
}
```

**Test:** Click → content toggles on/off? Do ▲/▼ also change? ✅

---

### Step 4 — Create Panel component (pattern reuse)

**Think:** This pattern (button + toggle + conditional content) will be reused. Extract it into a separate `Panel` component. Take `title` and `children` props.

**Concept — Component extraction:** When the same HTML pattern repeats, extract a component. `children` is a special prop — whatever you put between `<Panel>` tags ends up in `{children}`.

```tsx
function Panel({ title, children }: { title: string; children: React.ReactNode }) {
  const [isActive, setIsActive] = useState(false);

  return (
    <div>
      <button onClick={() => setIsActive(!isActive)}>
        {title} {isActive ? "▲" : "▼"}
      </button>
      {isActive && <div>{children}</div>}
    </div>
  );
}
```

Now `App` is clean:

```tsx
function App() {
  return (
    <div>
      <h1>Accordion</h1>
      <Panel title="What is React?">
        <p>React is a JavaScript library for building user interfaces.</p>
      </Panel>
    </div>
  );
}
```

**Test:** Same behavior — button click toggles. But the component is reusable now. ✅

---

### Step 5 — Add a Second Panel (discover the problem)

**Think:** Now add a second section — "What is Lifting State Up?". Reuse the same `Panel` component. Copy-paste.

```tsx
function App() {
  return (
    <div>
      <h1>Accordion</h1>
      <Panel title="What is React?">
        <p>React is a JavaScript library for building user interfaces.</p>
      </Panel>
      <Panel title="What is Lifting State Up?">
        <p>Moving state to a common parent so siblings can share data.</p>
      </Panel>
    </div>
  );
}
```

**Test:**
1. Click Panel 1 → content shows ✅
2. Click Panel 2 → that also shows ✅
3. But — **both are open at the same time!** ❌

This isn't an accordion. An accordion should have only one panel open. But right now each panel has its own `useState` — they don't know about each other.

```
Panel 1 — const [isActive, setIsActive] = useState(false)  ← its own state
Panel 2 — const [isActive, setIsActive] = useState(false)  ← its own state, different!
```

**Problem:** React data flows top → bottom. Siblings (Panel 1 and Panel 2) can't communicate directly. So state needs to live in a common parent (`App`).

---

### Step 6 — Lift State to App (Obvious Approach — But Wrong)

**Think:** Problem is clear — each Panel has its own `useState`, so they're independent. Lifting State Up pattern, right? Pull state out of child, into the common parent. First obvious attempt: `useState` in `App`, pass the same `isActive` boolean to both panels.

But first, make `Panel` controlled — no own state, controlled by props:

```tsx
function Panel({ title, children, isActive, onToggle }: { title: string; children: React.ReactNode; isActive: boolean; onToggle: () => void }) {
  return (
    <div>
      <button onClick={onToggle}>
        {title} {isActive ? "▲" : "▼"}
      </button>
      {isActive && <div>{children}</div>}
    </div>
  );
}
```

Now a single `isActive` state in `App`:

```tsx
export default function App() {
  const [isActive, setIsActive] = useState(false);

  return (
    <div>
      <h1>Accordion</h1>
      <Panel title="What is React?" isActive={isActive} onToggle={() => setIsActive(!isActive)}>
        <p>React is a JavaScript library for building user interfaces.</p>
      </Panel>
      <Panel title="What is Lifting State Up?" isActive={isActive} onToggle={() => setIsActive(!isActive)}>
        <p>Moving state to a common parent so siblings can share data.</p>
      </Panel>
    </div>
  );
}
```

**Test:**
1. Click Panel 1 → both open ❌
2. Click Panel 2 → both close ❌

**Problem:** `isActive` is a single boolean — both panels share it. A boolean can only say "all open" or "all closed." It can't distinguish "Panel 1 is open, Panel 2 is closed."

This is the pattern of Lifting State Up done halfway — state is in the right place (`App`, the common parent) but it can't carry the *which*. Location isn't the whole story — the shape of the state has to fit what we're trying to remember.

---

### Step 7 — What behavior do we actually want?

**Think:** Before writing another line, what is this accordion *supposed* to do? Not "lift state" — that's the mechanism. The **behavior**:

| Situation | Expected result |
|---|---|
| Page opens (initial) | Both panels closed |
| Click Panel 1 while nothing is open | Panel 1 expands, Panel 2 stays closed |
| Click Panel 2 while Panel 1 is open | Panel 1 closes, Panel 2 expands — never both open at once |
| Click Panel 2 while Panel 2 is open | Panel 2 closes |
| Click Panel 2 while nothing is open | Panel 2 expands, Panel 1 stays closed |
| Click Panel 1 while Panel 1 is open | Panel 1 closes |
| Click Panel 1 while Panel 2 is open | Panel 2 closes, Panel 1 expands |

That's the target. State it before writing — if we don't, we'll lift the wrong shape of state and wonder why the UI lies to us.

And notice a design constraint we haven't said out loud yet: **`Panel` is intentionally dumb.** Panel doesn't know how many other panels exist. Panel sees only its own `isActive` prop and its own `onToggle` callback — it doesn't share anything with its siblings.

So there are two jobs to do: (1) hold *which panel is open* in one place, and (2) let each panel see only its own yes/no. Step 6 failed job (1) — one boolean cannot tell the two panels apart.

Both jobs use nothing new — just better state. Step by step.

---

### Step 8 — The idea: one number, `number | null`

**Think:** What if, instead of separate true/false flags, we keep exactly ONE piece of state — a number that says WHICH panel is open — and `null` when none is?

| Value | Meaning |
|---|---|
| `null` | No panel is open |
| `0` | Panel 1 (index 0) is open |
| `1` | Panel 2 (index 1) is open |

`null` buys us two things: (1) an "all closed" state without inventing a sentinel number, and (2) the correct initial value — both panels closed.

And we don't want TWO states here — we're replacing the one from Step 6, not bolting a second one on:

```tsx
const [activeIndex, setActiveIndex] = useState<number | null>(null);
// One piece of state — says WHICH panel is open, or null. Replaces `isActive` from Step 6.
```

Why `useState<number | null>(null)` and not `useState(null)`? Because TS would lock the type to exactly `null` — nothing else could ever be assigned. We want a `number | null` marriage: `null` to mean "none", a number to mean "this one".

---

### Step 9 — Derive each panel's boolean: `activeIndex === 0` / `=== 1`

**Think:** Panel's contract never changed — Panel lives off a yes/no `isActive`. What changes is *what the parent passes in*. Same prop name, same `Panel` component, but the parent passes a comparison — computed fresh every render:

```tsx
<Panel isActive={activeIndex === 0} ... />   // Panel 1: true only when activeIndex === 0
<Panel isActive={activeIndex === 1} ... />   // Panel 2: true only when activeIndex === 1
```

What if we passed `activeIndex` raw instead? Panel receives `0`, `1`, or `null` where `true`/`false` is expected. JavaScript truthiness decides inside Panel — `0` is falsy, `1` is truthy — and Panel 1 would never bind to the active state. The condition has to live where the knowledge is — in App.

`===` is a JavaScript operator, not a React feature. `activeIndex === 0` evaluates to `true` or `false` — exactly the yes/no Panel needs. The parent evaluates once per render, hands down booleans, and Panel keeps its simple, index-blind logic.

---

### Step 10 — How each panel knows it was the one clicked

**Think:** The two `onToggle` functions look similar, but they are NOT the same function. Each one *remembers its own number* — Panel 1's toggle closes over `0`, Panel 2's over `1`.

```tsx
<Panel isActive={activeIndex === 0} onToggle={() => setActiveIndex(activeIndex === 0 ? null : 0)} ... />
<Panel isActive={activeIndex === 1} onToggle={() => setActiveIndex(activeIndex === 1 ? null : 1)} ... />
```

**`a === b ? value1 : value2` — the ternary operator**, in plain words:

```
result = (condition is true) ? value_if_true : value_if_false
```

Applied to Panel 1 (`activeIndex === 0 ? null : 0`):

```
if (activeIndex === 0) setActiveIndex(null);   // I'm already open → close
else                   setActiveIndex(0);        // I'm not → open me
```

Panel 2, same idea with `1`.

**Walk every click — what `activeIndex` holds before the click, what the ternary does, what re-renders:**

| # | activeIndex (before) | Click | Ternary | setActiveIndex gets | Rendered: Panel 1 | Rendered: Panel 2 |
|---|---|---|---|---|---|---|
| S0 | `null` | panel 1 | `null === 0` → false → `0` | `0` | `0 === 0` → open | `0 === 1` → closed |
| S1 | `0` | panel 2 | `0 === 1` → false → `1` | `1` | `1 === 0` → closed | `1 === 1` → open |
| S2 | `1` | panel 2 again | `1 === 1` → true → `null` | `null` | closed | closed |
| S3 | `1` | panel 1 | `1 === 0` → false → `0` | `0` | open | closed |

So Panel 1 clicking: *"if I'm the open one, close me; otherwise, make me the open one."* Clicking Panel 2 from S0? Panel 2's row reads the same — independent, same shape, own number.

That's why each panel only needs `isActive` and `onToggle` — it doesn't know its siblings exist. All the intelligence lives in `App`.

---

### Step 11 — `activeIndex: number | null` in the code

**Think:** Assemble the answer. From Step 6 we keep: Panel as a controlled component (`title`, `children`, `isActive`, `onToggle`) and the lift — state stays in `App`. From Steps 8–10 we add: the number, the derived booleans, and the closure-over-index toggles. Full code, then the verification checklist.

```tsx
export default function App() {
  const [activeIndex, setActiveIndex] = useState<number | null>(null);

  return (
    <div>
      <h1>Accordion</h1>
      <Panel
        title="What is React?"

        // Tells UI: should this panel be shown open
        isActive={activeIndex === 0}

        // Updates activeIndex on button click
        onToggle={() => setActiveIndex(activeIndex === 0 ? null : 0)}
      >
        <p>React is a JavaScript library for building user interfaces.</p>
      </Panel>
      <Panel
        title="What is Lifting State Up?"
        isActive={activeIndex === 1}
        onToggle={() => setActiveIndex(activeIndex === 1 ? null : 1)}
      >
        <p>Moving state to a common parent so siblings can share data.</p>
      </Panel>
    </div>
  );
}
```

**Test:**
1. Panel 1 click → opens ✅
2. Panel 2 click → Panel 1 closes, Panel 2 opens ✅
3. Panel 2 click again → closes ✅
4. Both never open at the same time ✅

## Final Code

```tsx
import { useState } from "react";

function Panel({ title, children, isActive, onToggle }: { title: string; children: React.ReactNode; isActive: boolean; onToggle: () => void }) {
  return (
    <div>
      <button onClick={onToggle}>
        {title} {isActive ? "▲" : "▼"}
      </button>
      {isActive && <div>{children}</div>}
    </div>
  );
}

export default function App() {
  const [activeIndex, setActiveIndex] = useState<number | null>(null);

  return (
    <div>
      <h1>Accordion</h1>
      <Panel
        title="What is React?"

        // Tells UI: should this panel be shown open
        isActive={activeIndex === 0}

        // Updates activeIndex on button click
        onToggle={() => setActiveIndex(activeIndex === 0 ? null : 0)}
      >
        <p>React is a JavaScript library for building user interfaces.</p>
      </Panel>
      <Panel
        title="What is Lifting State Up?"
        isActive={activeIndex === 1}
        onToggle={() => setActiveIndex(activeIndex === 1 ? null : 1)}
      >
        <p>Moving state to a common parent so siblings can share data.</p>
      </Panel>
    </div>
  );
}
```

## What It Is NOT

- **Not global state** — state is in `App` (the common parent), not in a global store. Each accordion instance has its own `activeIndex` if they appear on different pages.
- **Boolean is not enough** — `isActive: boolean` can't distinguish between panels. The state shape matters, not just the location.
- **Hardcoded indices are not a final solution** — `activeIndex === 0` and `activeIndex === 1` must be written manually. Later we'll see how to do this automatically with arrays.
- **Not a solution for prop drilling** — this is only 2 levels deep. For deep trees, Context API is needed.

---

## Common Mistakes

1. **Not changing state shape when lifting** — If `isActive` (boolean) is lifted to App and passed to both panels, both panels toggle at the same time. Both the state location AND shape matter.
2. **Duplicating an index by mistake** — If both panels check `activeIndex === 0`, they'll both open together (same as the boolean problem).
3. **Forgetting the ternary operator** — `setActiveIndex(0)` only sets, doesn't toggle. You must first check if it's already active.
4. **Forgetting the type** — Write `useState(null)` instead of `useState<number | null>(null)` → TypeScript infers `null` type, then `activeIndex === 0` gives a type error.

## In Your Own Words

1. Why was `activeIndex` (number | null) used instead of `isActive` (boolean)?

   <details>
   <summary>Sample Answer</summary>

   A boolean can only say "open" or "closed" — the same value for both panels. When we lifted `isActive` to App, both panels toggled together. `activeIndex` says WHICH panel is open — `0` = panel 1, `1` = panel 2, `null` = none open. Each panel compares its own index (`=== 0`, `=== 1`), so only one can be active at a time.

   </details>

2. What are the two steps of Lifting State Up that were done in this file?

   <details>
   <summary>Sample Answer</summary>

    Step 1: State (useState) was pulled from Panel and moved to App. Step 2: Data was passed as props (`isActive`, `onToggle`) — Panel became a controlled component (no own state, parent controls it). This was done in Step 6. Then the state shape was changed (boolean → activeIndex) because boolean can't distinguish between panels — that's Steps 8–10.

   </details>

3. What does `null` mean in `activeIndex: number | null`?

   <details>
   <summary>Sample Answer</summary>

   `null` means "no panel is open." This is the initial state — everything closed. When the user clicks an already-open panel, `null` is set again (to close it). If there were three panels, `0`, `1`, `2` would be the open states, and `null` means all closed.

   </details>

4. How does the ternary `activeIndex === 0 ? null : 0` work?

   <details>
   <summary>Sample Answer</summary>

   This is an inline if-else. First, the condition is checked: `activeIndex === 0` (is this panel already active?). If true → `null` is returned (close it). If false → `0` is returned (activate it). Toggle logic: if already open, close it; if closed, open it.

   </details>

5. If there are 4 panels (activeIndex 0, 1, 2, 3), what changes in the code?

   <details>
   <summary>Sample Answer</summary>

   Only three things change: (1) `useState<number | null>(null)` stays the same — `number` type has no limit. (2) Each new panel needs `isActive={activeIndex === N}` and `onToggle={() => setActiveIndex(activeIndex === N ? null : N)}` — where N = 0, 1, 2, 3. (3) The state logic is the same — one number tracking which panel is active. That's why `number | null` scales — boolean doesn't.

   </details>
