### 18. How do sibling components share data?

**Answer:** Three options by complexity — lift state up (best for 2 siblings: state lives in the common parent, passed down as props/callbacks), Context API (many consumers, no drilling), or a shared store like Redux/Zustand (app-wide complex state).

**Likely follow-up:** *Tabs where clicking a tab updates a panel?* — lift `activeTab` into the parent; tab buttons and panel both read it from props.

---

### 26. How does `useEffect` replace class lifecycle methods?

**Answer:** Empty deps `[]` ≈ `componentDidMount`, a deps array ≈ `componentDidUpdate` for those values, and returning a cleanup function ≈ `componentWillUnmount`. One hook covers all three phases.

**Likely follow-up:** *Any timing difference?* — class mount methods run after DOM mutation; `useEffect` runs after paint (fire-and-forget) — use `useLayoutEffect` when pre-paint is needed.

---

### 27. What is props drilling, and how do you solve it?

**Answer:** Threading props through many intermediate components that don't even use them just to reach a nested child (theme, auth, locale). Solutions: Context API (direct access via `useContext`), a state library (Redux/Zustand), or composition (pass a render function instead of data).

**Likely follow-up:** *When is drilling fine?* — 2–3 levels; beyond that, Context or a store. Also mention composition: `<Header renderNavbar={() => <Navbar theme="dark" />} />`.

---

### 37. What does `useEffect` do, and how does the dependency array work?

**Answer:** Side effects run after render. No array = every render; `[]` = mount only; `[a, b]` = mount + whenever a/b change. Deps must include everything the effect reads (the linter's `exhaustive-deps` enforces it). Effects run after paint — `useLayoutEffect` for pre-paint work.

**Likely follow-up:** *What if you leave a dep out?* — stale closure: the effect keeps seeing old values and never re-runs when it should.

---

### 38. When is `useEffect` cleanup necessary?

**Answer:** Whenever the effect creates something that must be torn down — subscriptions, timers, listeners, sockets, in-flight fetches. The cleanup runs before the next effect run (deps changed) and on unmount, preventing leaks and stale updates.

**Likely follow-up:** *Show the pattern.* — `useEffect(() => { const id = setInterval(...); return () => clearInterval(id); }, [roomId])`, plus an `AbortController` or `cancelled` flag for fetches.

---

### 39. `useEffect` vs `useLayoutEffect`?

**Answer:** `useEffect` runs asynchronously **after the browser paints** (non-blocking — good for fetch/analytics/subscriptions). `useLayoutEffect` runs synchronously **after DOM mutation but before paint** — for measuring/positioning where showing the wrong position first would flicker.

**Likely follow-up:** *When would you actually use `useLayoutEffect`?* — tooltips/popovers that must be measured and positioned before the user sees them; everything else stays in `useEffect`.

---

### 40. What does `useContext` do?

**Answer:** Consumes a Context directly in any component — no `<Context.Provider>` wrapper needed in between (and no `.Consumer` boilerplate). It's the standard fix for prop drilling on global data like theme, auth and locale.

**Likely follow-up:** *What's the performance caveat?* — every consumer re-renders when the provider value changes (see Q52/Q53).

---

### 41. What are the main `useRef` use cases?

**Answer:** Two: (a) access a DOM element directly (`inputRef.current.focus()`, measurements), and (b) store a mutable value that should **not** trigger re-renders — interval IDs, previous values, render counts.

**Likely follow-up:** *`useRef` vs `useState` for a counter?* — `useRef` when the UI never displays it; `useState` when the UI must update.

---

### 52. How do you fix the Context re-render performance issue?

**Answer:** Split contexts by concern — a rarely-changing `HeaderContext` separate from a frequently-changing `DataContext`, small value objects. When you need stronger optimization (stabilize value references), Batch 5 — Performance — covers `useMemo`/`useCallback`; Batch 6 — Zustand/Redux with selective subscriptions — is the bigger jump.

**Likely follow-up:** *Which first?* — split contexts for simple apps; jump to a real store once updates are frequent and consumers many.

---

### 53. What are the limitations of the Context API?

**Answer:** It re-renders **all** consumers on any value change, has no devtools/time-travel/action log, no middleware, no built-in persistence, and no action traceability — so debugging at scale is hard. It suits simple, infrequent global data.

**Likely follow-up:** *So when does Context lose to Redux/Zustand?* — frequent updates, complex state logic, or a need for devtools/middleware.

### 101. How do memory leaks happen in React, and how do you avoid them?

**Answer:** Leaving timers/listeners/subscriptions running after unmount, or setting state on an unmounted component. Fix: return a cleanup from `useEffect` (unsubscribe, `clearInterval`, abort fetches) so everything is torn down on unmount or deps change.

**Likely follow-up:** *Does React still warn about setState on unmounted components?* — the old warning was removed in React 18, but the underlying leak is still real.

---

### 103. When should you "lift state up"?

**Answer:** When two or more sibling components need to share and sync the same data — move the state to their closest common parent and pass it down via props + callbacks (the Celsius/Fahrenheit converter is the classic example).

**Likely follow-up:** *What's the alternative when the consumers are far apart?* — Context (many consumers) or a store (app-wide).

---

### 104. How do you decide where state should live?

**Answer:** The "closest common ancestor" rule — list every component needing the state, find their nearest common parent, put the state there, and pass down props/callbacks. If that parent is basically the root, the state is app-wide → Context or a store.

**Likely follow-up:** *Example?* — modal visibility used by toolbar + content: state goes in their common parent, not duplicated in both.

---

### 106. What is the "single source of truth" principle?

**Answer:** Every piece of data should have exactly one authoritative owner in the tree — don't store the same value twice; compute/derive from the one source instead, so the copies can never disagree.

**Likely follow-up:** *Where does this show up daily?* — filtering: keep one `todos` array + a `query`, derive `filtered = todos.filter(...)` during render rather than storing both.

---

### 107. What is the "derived state" anti-pattern?

**Answer:** Copying props into `useState` and then manually syncing when props change — the state goes stale and sync bugs appear. Better: compute the value directly from props during render, or use the `key` prop to reset the component.

**Likely follow-up:** *Give a concrete example.* — `const [list] = useState(props.list)` when `props.list` updates later; just use `props.list` (or `filter` it in render).

---

### 112. What is the "waterfall" data-fetching problem?

**Answer:** Nested components fetch sequentially — a child waits for its parent's fetch to finish before starting its own — so load times add up. Fixes: parallel fetching, data libraries that dedupe/parallelize (TanStack Query), or Server Components.

**Likely follow-up:** *How does TanStack Query help?* — it caches, dedupes identical requests, and lets sibling queries run in parallel (Q113).

---

### 113. How does React Query / TanStack Query differ from React state management?

**Answer:** It manages **server state** — async, remote data — with caching, background refetch, stale-while-revalidate and request deduplication. Redux/Context manage **client state** (local UI state). Complementary tools, not competitors.

**Likely follow-up:** *Where does the auth token go?* — client state (store/context); API responses live in the Query cache.

---

### 123. What is the Event Loop?

**Answer:** JavaScript's scheduling machine: the call stack runs code; when it empties, **microtasks** (Promise callbacks) drain first, then **macrotasks** (`setTimeout`), and the browser may render in between. That's where all async code resumes.

**Likely follow-up:** *Why does the UI stay responsive?* — long synchronous stacks block rendering; async breaks work into chunks the loop can interleave.

---

### 124. Precedence in the Event Loop — which runs first, `Promise()` or `setTimeout()`?

**Answer:** The Promise callback (microtask) runs first, even against `setTimeout(..., 0)` (macrotask) — the microtask queue fully drains before the next macrotask. Order: sync code → `.then` callbacks → `setTimeout` callback.

**Likely follow-up:** *Two setTimeouts with 0 delay?* — they run in scheduling order; a Promise queued between them still jumps ahead of both.

---

### 125. Difference between `setTimeout()` and `setInterval()`?

**Answer:** `setTimeout(fn, ms)` runs **once** after the delay; `setInterval(fn, ms)` repeats every interval until cleared. For effects, prefer `setTimeout` chains or clear intervals in cleanup — intervals can pile up if a run takes longer than the gap.

**Likely follow-up:** *Why avoid `setInterval` for fetching?* — overlapping requests and drift; recursive `setTimeout` schedules the next run only after the previous finished.
