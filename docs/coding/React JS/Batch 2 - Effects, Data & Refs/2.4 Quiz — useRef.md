
## MCQ

Q: What does `useRef(0)` return when called?
A. An object `{ current: 0 }` — with a `current` property holding the initial value
B. A number `0` — the value directly, not wrapped in an object
C. An array `[0, setValue]` — like useState, value and setter function
D. A function `() => 0` — calling it returns the initial value
> A. `useRef` returns a plain JavaScript object — `{ current: initialValue }`. This object has two key properties: (1) persistence — it doesn't reset between renders, (2) no re-render — React doesn't watch `useRef` like it does `useState`.

---

Q: What is the most important difference between `useState` and `useRef`?
A. `useState` can only store numbers, `useRef` can store anything
B. `useState` change → re-renders, `useRef` change → no re-render
C. `useState` value persists between renders, `useRef` value doesn't
D. `useRef` is only for DOM elements, `useState` is only for data
> B. `useState` is on React's "watchlist" — calling `setState` signals React → re-render. `useRef` is not on the watchlist — `ref.current = x` is just a normal JavaScript object property change, React doesn't know about it.

---

Q: When `useRef`'s initial value is `null` (like `useRef<HTMLInputElement>(null)`), how does TypeScript treat `.current`?
A. Writable — you can assign any value to `.current`
B. Readonly — you can't manually assign to `.current`, only React assigns it
C. Optional — `.current` is always undefined, never gets a value assigned
D. Dynamic — the type is decided at runtime, TypeScript doesn't interfere
> B. When initial value is `null`, TypeScript infers a DOM ref (RefObject). `.current` is readonly — React assigns the DOM node automatically via the `ref` attribute. You can't assign to it manually. If the initial value is non-null, it becomes a mutable reference (MutableRefObject) where `.current` is writable.

---

Q: Which JSX attribute do you use to connect a `useRef` to a DOM element?
A. `element={inputRef}` — custom element attribute, React connects it to the DOM
B. `ref={inputRef}` — ref attribute, tells React to store the DOM element's reference
C. `connect={inputRef}` — connect prop, React internally assigns DOM node to ref
D. `bind={inputRef}` — bind attribute, links DOM element and ref object
> B. `<input ref={inputRef} />` — the `ref` attribute tells React: "when you create this `<input>` in the DOM, store its reference in `inputRef.current`." After render completes, `.current` is filled with the actual DOM node. The `ref` attribute doesn't work on custom components — `forwardRef` is needed for those.

Q: If you read `inputRef.current` at the top level of a component (before JSX return), what do you get?
A. The actual `<input>` DOM element — because the ref is immediately populated
B. `null` — because the component function is running during render, DOM isn't built yet
C. `undefined` — React initializes refs as undefined
D. An error — can't access ref during render
> B. The component function runs during render — the DOM hasn't been created yet. `inputRef.current` only gets populated after React creates the actual DOM elements (after render completes). That's why you should read `.current` in event handlers or `useEffect`.

Q: What problem occurs if you store a timer ID from `setInterval` in `useState`?
A. Timer ID is a number — `useState` can't store numbers, only objects and arrays
B. `setTimerId(id)` triggers a state change → unnecessary re-render — timer ID has nothing to do with UI, only needed for `clearInterval`
C. `useState` with timer ID causes a syntax error — React doesn't allow this
D. `useRef` is always faster than `useState` — so all values should be in ref
> B. Timer ID is only needed for `clearInterval` — it doesn't need to be displayed. Storing it in `useState` means `setTimerId(id)` triggers a re-render — which is unnecessary. `useRef` is perfect here: store the ID in ref, use it when `clearInterval` is needed, and no extra re-render happens.

Q: Why is `inputRef.current?.focus()` important with the `?.` optional chaining?
A. `?.` provides TypeScript type safety — without it, compilation fails
B. If `inputRef.current` is null (element unmounted or conditionally rendered), calling `.focus()` would throw an error — `?.` makes it safe
C. `?.` makes the focus asynchronous — stays in sync with the render cycle
D. `?.` isn't necessary — `.current` is never null, always a DOM element
> B. If the element is conditionally rendered (like `{show && <input ref={inputRef} />}`) and `show` is false, the DOM element doesn't exist — `inputRef.current` is null. Without `?.`, calling `null.focus()` throws a runtime error. `?.` checks: "if null/undefined, don't proceed with the function call."

Q: What is the difference between `.current` in a mutable ref vs a DOM ref?
A. Mutable ref's `.current` is writable — you can assign to it. DOM ref's `.current` is readonly — only React assigns it
B. Mutable ref's `.current` only stores numbers, DOM ref only stores DOM elements
C. Mutable ref's `.current` is always undefined, DOM ref's `.current` is always null
D. They're the same — no difference, just naming convention
> A. Initial value non-null → MutableRefObject → you can manually assign/change `.current` (like `intervalRef.current = setInterval(...)`). Initial value `null` → RefObject → `.current` is readonly — React assigns the DOM node via the `ref` attribute.

Q: What is the correct sequence in the previous-value pattern with ref and state?
A. First update state (`setCount`), then store old value in ref
B. First store current value in ref, then update state — `prevCount.current = count; setCount(count + 1)`
C. Just store in ref, no state needed — use ref for UI updates
D. Just store in state, no ref needed — extract previous value from state
> B. First `prevCount.current = count` (backup current to ref), then `setCount(count + 1)` (update state). Ref change doesn't cause re-render — when state triggers re-render, the UI displays "Previous: X → Current: Y".

## TrueFalse

Q: Changing a `useRef` value causes the component to re-render — so you can use `useRef` for UI-updating values.
- True
- False
> False. Changing `useRef` does NOT cause a re-render. `ref.current = x` is just a normal JavaScript object property change — React doesn't watch it. For UI updates, you need `useState` which triggers re-renders. `useRef` is for values that shouldn't appear on screen.

---

Q: A `useRef` value persists between renders — even though the component function runs fresh on every render.
- True
- False
> True. A plain variable (`let x = 0`) resets on every render because the function starts over. But `useRef`'s object is stored internally by React and returned as the same object on every render — same reference, same `current` value carried over.

---

Q: In a DOM ref (`useRef<HTMLInputElement>(null)`), you can manually assign any value to `.current` — like `inputRef.current = document.createElement('div')`.
- True
- False
> False. A DOM ref (initial value `null`) has `.current` as readonly — only React assigns it. You'll get a TypeScript error if you try to assign manually. If the initial value is non-null, `.current` becomes writable.

---

Q: The `ref` attribute only works on built-in HTML elements (`<input>`, `<div>`, `<video>`) — not on custom React components.
- True
- False
> True. The `ref` attribute was designed for React's built-in elements. To use `ref` on custom components, you need `forwardRef` — which forwards the ref to a DOM element inside the custom component.

---

Q: Reading `ref.current` at the top level of a component (before JSX returns) is safe — it always returns the actual DOM element.
- True
- False
> False. The component function runs during render — the DOM hasn't been created yet. `ref.current` only gets populated after render completes and React creates the DOM elements. Reading it at the top level gives you `null`. Read it in event handlers or `useEffect` instead.

---

Q: Storing a timer ID in `useState` is wasteful — `setTimerId(id)` causes a re-render even though the ID has nothing to do with the UI.
- True
- False
> True. A timer ID is only needed for `clearInterval` — it doesn't need to be on screen. Storing it in `useState` means every `setTimerId(id)` call triggers a re-render — which is unnecessary work. `useRef` is the right tool: store in `intervalRef.current`, use it when `clearInterval` is needed, no re-render triggered.

## Short Answer

Q: What are the three fundamental differences between `useState` and `useRef`? When should you use each? Explain with an example.

<details>
<summary>Sample Answer</summary>

**Three fundamental differences:**

| Feature | useState | useRef |
|---|---|---|
| Re-render on change | Yes — `setState` → signal → re-render | No — `ref.current = x` is just a normal JS property change |
| Return type | `[value, setValue]` — value + setter function | `{ current: initialValue }` — object with `current` property |
| When to use | UI-visible state (count, input, toggle) | Background values (timer ID, DOM ref, previous value) |

**When to use each:**

- **useState** — when the value changing should update the screen. Example: `<p>Count: {count}</p>` — the user sees the count change.
- **useRef** — when the value should only be "remembered", not displayed. Example: `intervalRef.current = setInterval(...)` — the ID is only needed for `clearInterval`, never on screen.

**Code example — using both together:**

```tsx
function Stopwatch() {
  const [seconds, setSeconds] = useState(0);        // Shown on UI — state
  const intervalRef = useRef<ReturnType<typeof setInterval> | null>(null);  // Background — ref

  const handleStart = () => {
    intervalRef.current = setInterval(() => {
      setSeconds((prev) => prev + 1);
    }, 1000);
  };

  const handleStop = () => {
    if (intervalRef.current) {
      clearInterval(intervalRef.current);            // Ref used for cleanup
      intervalRef.current = null;
    }
  };

  return <h1>⏱️ {seconds}s</h1>;                     // State shown in UI
}
```

**Rule of thumb:** Value needs to be on screen → `useState`. Value only needs background bookkeeping → `useRef`.

</details>

Q: Explain the complete `useRef` pattern for DOM element access. Include the `ref` attribute, optional chaining (`?.`), and the timing of `.current`. Use an auto-focus input as an example.

<details>
<summary>Sample Answer</summary>

**Three steps:**

```tsx
// Step 1 — Create ref object
const inputRef = useRef<HTMLInputElement>(null);

// Step 2 — Add ref attribute in JSX
<input ref={inputRef} type="text" placeholder="Auto focus..." />

// Step 3 — Call DOM method in event handler
const handleFocusClick = () => {
  inputRef.current?.focus();
};
```

**What's happening step by step:**

**Step 1:** `useRef<HTMLInputElement>(null)` returns `{ current: null }`. The DOM hasn't been built yet. TypeScript treats `.current` as readonly (initial value is `null`).

**Step 2:** `<input ref={inputRef} />` — React internally does this:
```
React creates: const domElement = document.createElement('input')
Then: inputRef.current = domElement   ← React assigns it itself
```
After render completes, `.current` is filled with the actual `<input>` DOM node.

**Step 3:** On button click, `inputRef.current?.focus()` is called. `.focus()` is a browser built-in method that moves the cursor into the input.

**Why `?.` is important:**

```tsx
// ❌ Without optional chaining
inputRef.current.focus();  // Error if current is null

// ✅ With optional chaining
inputRef.current?.focus(); // Safe — if null, nothing happens
```

If the element is conditionally rendered:
```tsx
{showInput && <input ref={inputRef} />}
```
When `showInput = false`, the DOM element doesn't exist — `inputRef.current` is null. Without `?.`, `null.focus()` throws a runtime error. `?.` checks: "if null/undefined, don't proceed with the call."

**Timing — what happens when:**
- **During render** (before JSX returns): `inputRef.current` = `null` (DOM not built yet)
- **After render completes**: `inputRef.current` = actual `<input>` DOM element
- **In event handler** (button click): `.current` is already populated — safe to access

</details>
