## Cheat Sheet (Quick Recall)

```ts
// Mount-time fetch: useEffect with []
useEffect(() => {
  async function fetchData() {
    const res = await fetch(url);
    const data = await res.json();
    setState(data);
  }
  fetchData();
}, []);

// Button click fetch: call handleSearch directly
async function handleSearch() {
  setIsLoading(true);
  const res = await fetch(url);
  const data = await res.json();
  setState(data);
  setIsLoading(false);
}
```

- **3 states**: `data`, `loading`, `error` — keep them separate
- **Loading** = set `setIsLoading(true)` at fetch start, `false` at end (in `finally`)
- **Error** = `try { fetch } catch { setError } finally { setIsLoading(false) }`
- **Empty state** = `recipes.length === 0 ? "No results" : recipes.map(...)`
- **Button disable** = `disabled={isLoading}` — prevent user spam
- **`??`** = `data.meals ?? []` — null becomes empty array

Now we do the same thing in React — fetch from the URL and log to console.

**First, understand three new concepts:**

---

**1. `fetch` function — browser's built-in API caller**

`fetch` is a JavaScript function that the browser provides. Its job: send a request to a URL and get the response back. It's not a React feature — it's a direct part of the browser's JavaScript engine.

```js
const response = fetch("https://api.example.com/data");
```

But `fetch` returns a **Promise**.

**What is a Promise?** An object that represents a future value. Two states: `resolve` (success — value arrived) or `reject` (failure — error occurred). Until it resolves or rejects, the Promise is in "pending" state. You wait for it with `await`.

```
fetch(url) → returns a Promise
             |
             ├── resolve → got the response ✅
             └── reject  → network error ❌
```

---

**2. `async` and `await` — waiting for a Promise**

While the Promise hasn't resolved, we need to wait. In JavaScript, waiting is done with `await`:

```js
const response = await fetch("https://api.example.com/data");
// JavaScript pauses here — doesn't continue until fetch completes
// Fetch completes → response variable gets the actual value
```

But there's one rule: **`await` can only be used inside an `async` function.** That's why:

```js
async function getData() {
  const response = await fetch("https://api.example.com/data");
  // ✅ allowed — function is async
}

function getData() {
  const response = await fetch("https://api.example.com/data");
  // ❌ error — function is not async
}
```

Put `async` before the function — meaning "this function will do time-consuming work, and `await` can be used inside."

---

**3. `res.json()` — convert response to a JavaScript object**

The data we get from the network comes as a string (JSON text). `res.json()` converts that string into a JavaScript object/array.

And guess — `res.json()` also returns a **Promise**. Because reading the response body can take time (if data is large). So `await` is needed there too:

```js
const res = await fetch(url);       // 1. Call the URL, wait for response
const data = await res.json();      // 2. Parse the body, wait for data
console.log(data);                    // 3. Now use the data
```

**All three concepts together — the flow:**

```
handleSearch click
  ↓
async → function will take time
  ↓
await fetch(url)  →  Promise → browser makes the API call
  ↓                       ↓
  pauses              response arrived
  ↓                       ↓
await res.json()  →  Promise → body is being parsed
  ↓                       ↓
  pauses              data ready
  ↓
console.log(data)
```


`const data: SearchResponse` — TypeScript now knows that `data.meals` is of type `Recipe[] | null`. If you access a wrong property (like `data.recipes`), TypeScript will error. Not adding state yet — just type-checking that the interface is correct. ✅

## Step 10 — Loading State: Disable Button + Spinner

There's a problem now — search takes 1-2 seconds. The screen freezes. The user doesn't know if the app is working or hung.

Think about it — right after the button click, we need visual feedback that "a fetch is happening, please wait."

The solution is a **loading state** — a boolean called `isLoading`. Set to `true` at fetch start, `false` when finished. Simple.

**First, add the state:**

```tsx
const [isLoading, setIsLoading] = useState(false);
```

**Now toggle loading on/off in `handleSearch` — true before, false after:**


**Nutshell:** Loading state is a boolean flag — `true` means a fetch is in progress, `false` means it's done. It lets us give the user feedback.

1. **Disable the button** — while loading, the user can't click repeatedly (prevents spam)
2. **Show a spinner** — a visual cue that "the app is working"

`disabled={isLoading}` — when `isLoading` is true, the button is disabled. Text also changed — "Search" to "Searching..." so the user knows the click was registered.

## Step 11 — Error State: Try/Catch

Loading is handled. But there's another problem — what if the network fails? Server is down? API rate limit exceeded?

Right now, if the network fails, `fetch` throws, and the code doesn't crash but nothing is shown — just a blank screen. We need to handle errors.

**First, add the error state — store a string, null means no error:**

```tsx
const [error, setError] = useState<string | null>(null);
```

**Now wrap `handleSearch` in `try/catch/finally`:**

```tsx
const handleSearch = async () => {
  if (!searchInput.trim()) return;

  setIsLoading(true);
  setError(null);

  try {
    const res = await fetch(
      `https://www.themealdb.com/api/json/v1/1/search.php?s=${searchInput.trim()}`
    );
    const data: SearchResponse = await res.json();
    setRecipes(data.meals ?? []);
  } catch (err) {
    setError(err instanceof Error ? err.message : "Something went wrong");
    setRecipes([]);
  } finally {
    setIsLoading(false);
  }
};
```

Three parts to understand:

**The `try` block** — code that might fail: `fetch` and `res.json()`. If it succeeds, `setRecipes(data)` runs.

**The `catch` block** — runs when an error occurs inside `try` — network failure, server down, anything unexpected. Two things to understand here:

**First — what is `err`?** In JavaScript, anything can be thrown — an Error object, a string, a number, anything. When `fetch` fails, it throws an `Error` object that has a `message` property (like `"Failed to fetch"`). But sometimes other code throws something else.

**Second — what does `instanceof` do?** It checks whether a value is an instance of a specific class. `err instanceof Error` means "is this `err` value actually an `Error` object?"

```ts
// Example to understand:
const someError = new Error("Network failure");
console.log(someError instanceof Error); // true — because it's from the Error class

const someString = "whatever error";
console.log(someString instanceof Error); // false — it's a string, not an Error
```

**Why check this?** If `err` is truly an `Error` instance, it has a `.message` property with human-readable error text. If it's not (someone threw a string/number), we provide a safe fallback: `"Something went wrong"`.

```
err instanceof Error ?
  → true:  use err.message  (like "Failed to fetch")
  → false: "Something went wrong" (fallback, because we don't know what was thrown)
```

**The `finally` block** runs no matter what — whether `try` succeeded or `catch` triggered. So `setIsLoading(false)` here is safe — loading always stops, no matter what happens.

**Display the error in UI:**

```tsx
{error && <p style={{ color: "red" }}>❌ {error}</p>}
```

**The full flow now:**

```
Button click
  ↓
setIsLoading(true), setError(null)
  ↓
fetch url
  │
  ├── Success → setRecipes(data)
  │
  └── Error → setError(message), setRecipes([])
  │
  ↓
setIsLoading(false)  ← finally, always runs
```

## Step 12 — useEffect's Real Need: Show Data on Mount

Through Step 11, everything works — dynamic search, loading, error, all handled. But one thing irritates me...

Open the app, and "No recipes found. Try a different search." is shown. Of course — `recipes` is an empty array, the ternary matched. The user hasn't done anything yet and we're telling them "nothing found." A bit rude, isn't it?

Here's what we want — **when the app opens, immediately show some interesting recipes.** Chicken recipes, by default. Then the user can search on their own.

But there's a problem — `handleSearch` is triggered by button click. How do we fetch data when the app mounts?

This is where `useEffect` shows its real purpose.

### Think: What is useEffect?

In 2.1 we learned — `useEffect` tells React "after render, do this work." We saw it with timers. Now we see it with API fetches.

`useEffect`'s fundamental use case is this — **when the component mounts (or a dependency changes), run a side effect.** Side effect = anything outside the render cycle — API call, timer, localStorage, etc.

### First, import useEffect

Until now `useEffect` wasn't imported because it wasn't needed. Now we need it:

```tsx
import { useState, useEffect } from "react";
```

### Empty dependency array — runs only on mount

```tsx
useEffect(() => {
  // This only runs when the component first appears on screen (mount)
}, []);
```

`[]` means "this effect doesn't depend on anything." React's rule: anything in the dependency array, if it changes, the effect re-runs. `[]` has nothing in it, so nothing can change — the effect runs only **once**, after the component mounts.

### Now fetch inside the effect — same pattern we used in handleSearch:

```tsx
useEffect(() => {
  const fetchDefault = async () => {
    const res = await fetch(
      "https://www.themealdb.com/api/json/v1/1/search.php?s=chicken"
    );
    const data: SearchResponse = await res.json();
    setRecipes(data.meals ?? []);
  };

  fetchDefault();
}, []);
```

Notice we didn't write `useEffect(async () => ...)` directly. Why? Because `useEffect`'s callback should return either nothing or a cleanup function, not a Promise. An async function always returns a Promise. So we define an async function inside and call it. This is the official pattern recommended by the docs.

**Nutshell:** `useEffect(() => { ... }, [])` means "React, do this work only the first time the component appears on screen." After that, it never runs again (unless the component is destroyed and remounted).

### Test it

Refresh the app — chicken recipes are loading automatically? ✅ Click Search — search still works? ✅

Now the doc title makes sense — "API Fetching with useEffect." We fetched on mount using `useEffect`.

```tsx
        <div style={{ display: "grid", gridTemplateColumns: "1fr 1fr 1fr", gap: "16px", marginTop: "20px" }}>
          {recipes.map((recipe) => (
            <div key={recipe.idMeal} style={{ border: "1px solid #ddd", borderRadius: "8px", padding: "12px" }}>
              <img src={recipe.strMealThumb} alt={recipe.strMeal} style={{ width: "100%", borderRadius: "4px" }} />
              <h3>{recipe.strMeal}</h3>
              <p>{recipe.strCategory} — {recipe.strArea}</p>
            </div>
          ))}
        </div>
      )}
    </div>
  );
}
```

## Try It Yourself

1. Without scrolling, answer: why does `handleSearch` need to be `async`?

   <details>
   <summary>Sample Answer</summary>
   Because `fetch` returns a Promise. To work with a Promise, you need `await`. And `await` can only be used inside an `async` function.
   </details>

2. Write code — a function that fetches from `https://api.example.com/users`, handles loading state, handles error, and disables the button.

   <details>
   <summary>Sample Answer</summary>

   ```tsx
   const [users, setUsers] = useState<User[]>([]);
   const [isLoading, setIsLoading] = useState(false);
   const [error, setError] = useState<string | null>(null);

   const fetchUsers = async () => {
     setIsLoading(true);
     setError(null);
     try {
       const res = await fetch("https://api.example.com/users");
       const data = await res.json();
       setUsers(data);
     } catch (err) {
       setError(err instanceof Error ? err.message : "Failed to fetch");
     } finally {
       setIsLoading(false);
     }
   };
   ```
   </details>

3. Predict — if `setIsLoading(false)` isn't written in `finally`, only at the end of `try`, what happens if the fetch fails?

   <details>
   <summary>Sample Answer</summary>
   The error goes to the catch block, but `setIsLoading(false)` is never called. The loading state stays `true` forever — the spinner never stops. This is why putting loading-off in `finally` is essential.
   </details>

## Summary

| Concept | Understanding |
|---|---|
| API | Interface that lets a React app retrieve data from a server — send request, get response |
| fetch + async/await | `const res = await fetch(url)` → `const data = await res.json()` |
| useEffect with `[]` | Runs only on mount — used for initial data loading |
| Loading State | `isLoading` → `true` at fetch start, `false` at end (in `finally`) |
| Error State | `error` → set in catch block, reset to `null` at fetch start |
| Button Disable | `disabled={isLoading}` — prevent user spam while loading |
| Empty State | `recipes.length === 0` → show "No results found" message |
| ?? (Nullish Coalescing) | `data.meals ?? []` — null becomes empty array, unlike `||` which also catches 0, "", false |
