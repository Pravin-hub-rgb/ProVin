
## MCQ

Q: What are the three basic steps of Context API?
A. createContext → Provider → useContext — create container, provide value, consume value
B. useState → useEffect → useRef — these are hooks, not Context API steps
C. createStore → dispatch → subscribe — this is the Redux pattern
D. createContext → useRef → useMemo — create container, create ref, memoize
> A. The three steps of Context API are: (1) `createContext<T>(default)` creates a container, (2) `<Context value={val}>` provides the value, (3) `useContext(Context)` consumes the value. B is wrong because those are hooks, not Context API steps. C is wrong because that's Redux. D is wrong because useRef and useMemo are not Context API steps.

If you export both a context (non-component) and a component in the same file, you get a warning: "Fast refresh only works when a file only exports components." A, C, and D are all wrong — there's no performance or location connection with Context API.

Q: Why do we use the guard pattern (`if (!ctx) throw Error`) in a custom hook?
A. Bundle size is optimized — dead code is eliminated
B. If used outside a Provider, you get a clear error message

D. The component is automatically highlighted in React DevTools
> B. If a component accidentally calls useContext outside its Provider, it gets `undefined`. The guard pattern checks if `ctx` is undefined and throws an error. This makes debugging easier and TypeScript knows the return type is not undefined. A, C, and D are all wrong.

Q: When and why do you use `useMemo` with Context API?
A. `useMemo` keeps the context value reference stable until dependencies change — prevents unnecessary re-renders of children
B. `useMemo` reduces the size of the context value — memory optimization
C. `useMemo` automatically imports the context file — no manual import needed
D. `useMemo` stores the Provider's value in browser cache — persists on refresh
> A. Context values are objects/functions. Every time the Provider renders, a new object reference is created → all consuming components re-render, even if the value didn't change. `useMemo` returns the same reference until dependencies change. B, C, and D are all wrong.

## TrueFalse

Q: Context API is a global state management tool — it provides a store/cache just like Redux and Zustand.
- True
- False
> False. Context API is a dependency injection mechanism, not global state management. Redux/Zustand have their own stores with cached data. Context just passes values through the React component tree without props — no store, no cache.

---

Q: In a custom hook, `useContext` is called first, then a guard check is performed to see if the context is undefined.
- True
- False
> True. The custom hook pattern: `const ctx = useContext(Context)` gets the value first, then `if (!ctx) throw new Error(...)` checks the guard. If used outside a Provider, a clear error message appears. The safe value is then returned.

---

Q: The Provider component must wrap all consuming children — using a component outside its Provider causes `useContext` to return `undefined`.
- True
- False
> True. If a component is outside its Provider, `useContext` returns the default value (which we set to `undefined`). This is why all consuming components must be rendered inside the Provider. The custom hook guard catches this condition.

---

Q: Keeping the context in a separate file is not just best practice — it's mandatory, otherwise the code won't compile.
- True
- False
> False. Keeping context in its own file is best practice, not mandatory. You can write everything in one file. But to avoid the Fast Refresh warning, it's better to separate them. The code compiles either way.

---

Q: `useMemo` keeps the context value reference stable — the same object reference is returned until dependencies change.
- True
- False
> True. With `useMemo(() => ({ theme, toggleTheme }), [theme])`, the same object reference is returned as long as `theme` doesn't change. Consuming components don't re-render until the actual value changes.

---

Q: Context API is suitable for high-frequency updates (like real-time stock prices, animations) because it's efficient.
- True
- False
> False. Context API is **not** suitable for high-frequency updates. Each update causes the entire consuming subtree to re-render (reference changes). For real-time stock prices and animations, Zustand or external stores are better.

## ShortAnswer

Q: Explain the three-step process of Context API. What happens in each step and include a code example.

<details>
<summary>Sample Answer</summary>

**Step 1 — createContext:** Create a container that can travel through the component tree. Keep the default value as `undefined` so we can use the guard pattern later.

```tsx
const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);
```

**Step 2 — Provide:** In App or a wrapper component, give all children the value via `<Context value={...}>`. The state lives here and flows into the context.

```tsx
<ThemeContext value={{ theme, toggleTheme }}>
  <Navbar />
  <MainContent />
</ThemeContext>
```

**Step 3 — Consume + Guard:** Any child component calls `useContext` to get the value out. Check the guard to ensure it's not undefined.

```tsx
const ctx = useContext(ThemeContext);
if (!ctx) throw new Error("Must be inside Provider");
return ctx;
```

The custom hook pattern wraps all three steps into one function — `useTheme()` calls useContext, runs the guard, and returns the safe value. Components simply call `const { theme } = useTheme()`.

</details>

Q: What is prop drilling, and how does Context API solve it? Explain with an example.

<details>
<summary>Sample Answer</summary>

**Prop drilling:** When state needs to reach a component 3+ levels deep, every middle component has to receive and pass through the prop — even though they don't use it themselves.

```
App (theme state lives here)
  └── Layout ← theme prop (doesn't use it, just passes through)
      └── Sidebar ← theme prop (doesn't use it, just passes through)
          └── Navbar ← finally uses theme
```

```tsx
function Layout({ theme }: { theme: string }) {
  return <Sidebar theme={theme} />;  // Just pass-through
}
function Sidebar({ theme }: { theme: string }) {
  return <Navbar theme={theme} />;   // Just pass-through
}
function Navbar({ theme }: { theme: string }) {
  return <nav className={theme}>...</nav>;  // Actually uses it
}
```

**Context API solution:** Put the Provider at App, and any child can directly call `useContext` — middle components don't need to pass props.

```tsx
function App() {
  return (
    <ThemeContext value={{ theme, toggleTheme }}>
      <Layout />
    </ThemeContext>
  );
}
// Layout and Sidebar don't know about theme at all
function Navbar() {
  const { theme } = useTheme(); // Direct access
  return <nav className={theme}>...</nav>;
}
```

Context API frees middle components from prop drilling — data flows directly from source to consumer.

</details>

Q: What is the custom hook pattern in Context API and why is the guard important? Explain with code.

<details>
<summary>Sample Answer</summary>

**Custom hook pattern:** Instead of writing `useContext` and the guard check in every component, wrap them in a reusable function.

```tsx
export function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within a ThemeProvider");
  return ctx;
}
```

**Why the guard matters:**
1. **TypeScript safety:** Without the guard, `ctx` has type `ThemeContextValue | undefined`. Every component would need to handle `undefined`. After the guard, the return type is just `ThemeContextValue` — TypeScript knows it's never undefined.
2. **Clear error messages:** If you forget to wrap a component in its Provider, instead of getting a cryptic `"Cannot read properties of undefined"` error, you get a clear message: "useTheme must be used within a ThemeProvider."
3. **Reusability:** Write the hook once, use it everywhere. If you ever migrate to Zustand later, you only change the implementation in one place.

```tsx
// Using it in a component — clean, no boilerplate
function Navbar() {
  const { theme, toggleTheme } = useTheme();
  return <button onClick={toggleTheme}>{theme}</button>;
}
```

</details>
