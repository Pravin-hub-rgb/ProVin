# 2.6 Quiz — Context API

## MCQ

Q: Context API ki teen basic steps kya hain?
A. createContext → Provider → useContext — container banao, value do, value lo
B. useState → useEffect → useRef — state, effect aur ref teen steps
C. createStore → dispatch → subscribe — Redux pattern teen steps
D. createContext → useRef → useMemo — container banao, ref lo, memoize karo
> A. Context API ke teen steps hain: (1) `createContext<T>(default)` se container banao, (2) `<Context value={val}>` se value provide karo, (3) `useContext(Context)` se value consume karo. B galat hai kyunki yeh hooks hain, Context API nahi. C galat hai kyunki Redux ka pattern hai. D galat hai kyunki useRef aur useMemo Context API ke steps nahi hain.

Q: `createContext` ka default value parameter kyu important hai?
A. Server-side rendering mein default value hi render hota hai
B. Jab koi component Provider ke bahar useContext call kare, tab default value milta hai
C. Default value hi browser ke localStorage mein save hoti hai — page refresh pe preserve rehti hai
D. Default value se TypeScript automatically type infer kar leta hai — generic ki zaroorat nahi
> B. Default value tab use hota hai jab koi component bina Provider ke useContext call kare. Isliye hum undefined pass karte hain — taaki guard pattern laga saken. A galat hai kyunki SSR se koi connection nahi. C galat hai kyunki localStorage Context API ka feature nahi hai. D galat hai kyunki generic type hamesha dena padta hai.

Q: Context file ko alag rakhna best practice kyun hai?
A. Alag file rakhi toh bundle size chhoti rehti hai

C. Alag file rakhi toh TypeScript faster compile karta hai

Context (non-component) aur component ek file mein export karoge toh warning aati hai: "Fast refresh only works when a file only exports components." A, C, D — yeh sab galat hain, Context API ka file structure se koi performance/location connection nahi.

Q: Provider component ka kya kaam hai?
A. Provider component tree mein context value distribute karta hai — saare children access kar sakte hain
B. Provider ek wrapper hai jo props ko automatically merge karta hai — prop drilling solve ho jati hai
C. Provider ek built-in component hai jo useState replace karta hai — global state management deta hai
D. Provider sirf class components mein kaam karta hai — functional components mein use nahi ho sakta
> A. `<Context value={val}>` tree ke andar saare children ko value provide karta hai. B galat hai — Provider props merge nahi karta, context value provide karta hai. C galat hai — Provider useState replace nahi karta, uske saath kaam karta hai. D galat hai — Provider functional components mein bhi kaam karta hai.

Q: Custom hook mein guard pattern (if (!ctx) throw Error) kyu lagate hain?
A. Bundle size optimize hota hai — dead code eliminate ho jata hai
B. Provider ke bahar use ho toh clear error message deta hai
C. TypeScript automatically generic type infer kar leta hai
D. Component React DevTools mein automatically highlight hota hai
> B. Agar koi component accidentally Provider ke bahar useContext call kare, toh `undefined` milega. Guard pattern check karta hai ki ctx undefined hai ya nahi — agar hai toh error throw karta hai. Isse debugging aasan hoti hai aur TypeScript ko bhi pata chal jata hai ki return type undefined nahi hai. A, C, D galat hain.

Q: Provider component ko alag component mein extract karne ka kya fayda hai?

B. Layout view alag, state management alag — separation of concerns
C. Extracting se lines of code automatically reduce ho jati hain
D. Bundle size 50% kam ho jata hai — production optimized hota hai
> B. Separation of concerns — Provider ka kaam sirf state manage karna aur context provide karna hai, App ka kaam layout banana hai. A galat hai — extract karne se useMemo ki zaroorat khatam nahi hoti. C galat hai — lines of code reduce nahi hoti, just reorganized hoti hain. D galat hai — bundle size pe koi effect nahi.

Q: Context API mein `useMemo` kab aur kyun use karte hain?
A. `useMemo` se context value ka reference stable rehta hai jab tak dependencies change na hon — unnecessary child re-renders prevent hota hai
B. `useMemo` se context value ka size chhota ho jata hai — memory optimization hoti hai
C. `useMemo` se context file ka import automatically hota hai — manual import ki zaroorat nahi
D. `useMemo` se Provider ki value browser cache mein store ho jati hai — page refresh pe preserve rehti hai
> A. Context value mein object/function hota hai. Har Provider render pe naya object reference banta hai → saare consuming components re-render hote hain, chahe value change na hui ho. `useMemo` purana reference deta hai jab tak dependencies change na hon. B, C, D galat hain.

Q: Context API ko global state management tool kyun nahi keh sakte?
A. Yeh dependency injection mechanism hai — Redux/Zustand jaisa store/cache nahi hai
B. Yeh sirf production build mein kaam karta hai — development mode disabled hai
C. Yeh React Native mein kaam nahi karta — React Native ka apna state system hai
D. Yeh TypeScript ke bina use nahi kar sakte — JavaScript compatible nahi hai
> A. Context API ek dependency injection mechanism hai, global state management nahi. Redux/Zustand ka apna store/cache hota hai, Context ka nahi. Context sirf React component tree ke andar value pass karta hai bina props ke. B, C, D galat hain.

Q: Kab Context API use karna avoid karna chahiye?
A. Jab data chhota ho — sirf 1-2 values — tab Context use karne ka koi fayda nahi
B. Jab data high-frequency update hota hai (animations, real-time) — poora consuming subtree har update pe re-render hota hai
C. Jab app chhoti ho — 5-10 components — tab Context zaroori nahi, lifting state up kaafi hai

A, C, D bhi partially sahi ho sakte hain, lekin high-frequency update **sabse critical problem** hai jo Context avoid karne ka sabse strong reason hai.

## ShortAnswer

Q: Context API ka teen-step process explain karo. Har step mein kya hota hai aur code example do.

<details>
<summary>Sample Answer</summary>

**Step 1 — createContext:** Container banao jo component tree mein travel karega. Default value undefined rakho taaki guard pattern laga sako.

```tsx
const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);
```

**Step 2 — Provide:** App ya wrapper component mein `<Context value={...}>` se saare children ko value do. State yahan rakho jo context mein jayegi.

```tsx
<ThemeContext value={{ theme, toggleTheme }}>
  <Navbar />
  <MainContent />
</ThemeContext>
```

**Step 3 — Consume + Guard:** Kisi bhi child component mein `useContext(Context)` se value lo. Guard check karo ki undefined toh nahi.

```tsx
const ctx = useContext(ThemeContext);
if (!ctx) throw new Error("Must be inside Provider");
return ctx;
```

Custom hook pattern teeno steps ko ek saath wrap karta hai — `useTheme()` ek function hai jo useContext + guard + return ek saath karta hai. Component sirf `const { theme } = useTheme()` call karta hai.

</details>

Q: Prop drilling kya hai, aur Context API isse kaise solve karta hai? Example ke saath samjhao.

<details>
<summary>Sample Answer</summary>

**Prop drilling:** Jab state ko 3+ level deep child tak bhejna ho, toh har middle component ko woh prop receive karna padta hai chahe unhe zaroorat na ho.

```
App (theme state yahan)
  └── Layout ← theme prop (use nahi karta, sirf pass through)
      └── Sidebar ← theme prop (use nahi karta, sirf pass through)
          └── Navbar ← finally theme use karta hai
```

```tsx
function Layout({ theme }: { theme: string }) {
  return <Sidebar theme={theme} />;  // Sirf pass through
}
function Sidebar({ theme }: { theme: string }) {
  return <Navbar theme={theme} />;   // Sirf pass through
}
function Navbar({ theme }: { theme: string }) {
  return <nav className={theme}>...</nav>;  // Asli use
}
```

**Context API solution:** Provider App mein lagao, koi bhi child directly useContext se value le sakta hai — middle components prop nahi dekhte.

```tsx
function App() {
  return (
    <ThemeContext value={{ theme, toggleTheme }}>
      <Layout />
    </ThemeContext>
  );
}
// Layout aur Sidebar ko theme ka pata nahi
function Navbar() {
  const { theme } = useTheme(); // Direct access
  return <nav className={theme}>...</nav>;
}
```

Context API middle components ko prop se mukt karta hai — data directly source se consumer tak jata hai.

</details>

Q: Custom hook pattern kya hai Context API mein? Guard kyu important hai? Code ke saath samjhao.

<details>
<summary>Sample Answer</summary>

**Custom hook pattern:** Har component mein `useContext` aur guard check likhne se bachne ke liye ek reusable wrapper function banate hain.

```tsx
export function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within a ThemeProvider");
  return ctx;
}
```

**Guard kyu important:**
1. **TypeScript safety:** Guard ke bina `ctx` ka type `ThemeContextValue | undefined` hota hai. Har component mein undefined check karna padta. Guard ke baad return type sirf `ThemeContextValue` hai — TypeScript jaanta hai ki undefined nahi aayega.
2. **Clear error messages:** Component ko Provider mein wrap karna bhool gaye toh `"Cannot read properties of undefined"` jaisa cryptic error nahi aayega. Custom hook guard clear message deta hai: "useTheme must be used within a ThemeProvider."
3. **Reusability:** Custom hook ek baar likho, sab components use karo. Agar future mein implementation change karni ho (jaise Zustand migrate), toh ek jagah change karo.

```tsx
// Component mein use karna
function Navbar() {
  const { theme, toggleTheme } = useTheme(); // Clean — no boilerplate
  return <button onClick={toggleTheme}>{theme}</button>;
}
```

</details>
