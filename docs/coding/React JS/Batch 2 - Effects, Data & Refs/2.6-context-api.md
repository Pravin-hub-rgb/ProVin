## Where We Left Off

In 2.5.0, we learned Lifting State Up — when siblings share state, a common parent holds it, and props flow down + callbacks flow up. That works for siblings. But sometimes the component tree is deep and many levels need the same data — theme, current user, locale. Passing the prop through every middle component that doesn't care about it — called **prop drilling** — gets painful fast.

This doc solves that with **Context API** — React's built-in way to make a value available anywhere in the tree, without props. We'll build a Theme Switcher.

## Broader Goal

**Broader goal:** Build a Theme Switcher where a `<Navbar />`-like component and any other component can read the current theme directly — with no prop passing.

Wait — no `<Navbar />` yet? We'll create it. And a second consumer, a `<ThemedBox />`, so we can see both working from the same provider.

**Roadmap:**
1. Feel the problem — prop drilling with no escape
2. Create the context file + a container with `createContext`
3. Provide the value with `<ThemeContext>` in App
4. Consume the value in `Navbar` with `useContext`
5. Wrap the same code in a custom hook, `useTheme()`
6. Extract the provider logic into `ThemeProvider` — App becomes clean
7. Add a second consumer, `ThemedBox` — build it phase by phase
8. Context API: when to use, when to avoid
9. Performance preview — context creates a new value object on every render (fixed in Batch 5)

**One file, three passes** — before writing code, here's the shape of where we're going, so nothing surprises you halfway. Everything context needs ends up in ONE file: `src/contexts/ThemeContext.tsx`. We just won't write it all at once:

1. **Step 2** — the container. Empty. That's all the file has at first.
2. **Step 5** — the `useTheme()` hook, added to the same file.
3. **Step 6** — the `ThemeProvider` component, added to the same file again.

So when `ThemeContext.tsx` shows up again later, the file isn't repeating itself — it's growing. By the end it holds exactly three things: the container, the hook, and the provider.

And one rule to hold onto the whole way: **data enters context through `value=`, and data leaves context through `useContext`.** Two doors, one container. Every step ahead just places those two doors.

## Step 1 — Feel the Problem: Prop Drilling Without Escape

**Think:** We want a dark/light theme. Every component on screen needs to know the theme — background color, text color, border — everything. If we lift state up using the 2.5.0 pattern, `App` holds `theme` and every component gets it via props passed through each parent in between.

Props have one hard rule here: they move **exactly one hop — parent to direct child**, nothing else. A component receives data only if its direct parent hands it over. No skips, no shortcuts. Keep that rule in mind — every pain below comes straight from it.

A small example tree (these are placeholder names — we won't actually build these components):

```
App (holds theme state)
  ├── Navbar
  │     └── ThemeButton    ← needs theme
  └── ThemedBox            ← needs theme
```

So far only 2 components in 3 levels. Add 8 more components — `Header → Page → Section → Card → Row → Cell → Checkbox → Label` — and now every component in the middle has `theme={theme}` in its props even though it does nothing except forward it. The only way out: put the `theme` somewhere global.

**Problem you'll always hit:**
```
App                theme="dark"
  └── Layout        theme="dark" (pass-through, doesn't use it)
       └── Sidebar  theme="dark" (pass-through, doesn't use it)
            └── MenuItem  theme="dark" ← finally used!
```

**Context API is the solution** — data from one place, read anywhere below it, no props in between. The three steps:

1. **Create** a container with `createContext`
2. **Provide** the value on a parent
3. **Consume** it inside children with `useContext`

Why does context work when props hurt? Because the two routes move data differently. Props travel through direct parent-child links, one hop at a time. Context travels by tree position: a value attached at one point in the tree is readable by everything rendered **below** that point — no middle component has to touch it. That's the second route React gives us.

We'll do all three now — in this order, one step at a time.

## Step 2 — Create the context (in a separate file)

**Think:** We need a place to keep the theme value. `createContext` builds that place. Make a new file — `src/contexts/ThemeContext.tsx` — and put it there. Keeping context in its own file avoids two problems: circular imports (file exports both a component and a non-component), and a Vite warning: *"Fast refresh only works when a file only exports components."*

**File: `src/contexts/ThemeContext.tsx`**

```tsx
import { createContext } from "react";

export type Theme = "light" | "dark";

export interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);
```

**Line by line:**

- `import { createContext } from "react"` — React built-in that makes a container for any value
- `export type Theme = "light" | "dark"` — union type; `export` so other files can use it
- `export interface ThemeContextValue` — the TYPE of the values that will be provided
  - `theme: Theme` — the current theme
  - `toggleTheme: () => void` — the function we'll call to flip it
- `export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined)` — the container itself
  - Generic type: `ThemeContextValue | undefined` — either a proper object or `undefined`
  - `undefined` default — if someone consumes without a Provider, they get `undefined`
  - `export` — mandatory; without it nothing in other files can import it

**Test:** No console output yet — we only created the container, nothing provides a value yet. ✅

**What we have right now — and what we don't:**

The container exists. It's empty — no theme, no toggle function. Creating a container never fills it; a provider does that, in Step 3.

Two things to lock in now, because Step 4 builds directly on them:

- **Importing this file never hands you the data.** It hands you the same container object, in every file that imports it. That's all the import does.
- **One container, imported everywhere — never created twice.** In Step 4, `useContext(ThemeContext)` will need this exact object so React knows which container to read. If a file calls `createContext` again instead of importing, it makes a second, new, empty container — and no provider ever fills that one.

## Step 3 — Provide the value (in App.tsx)

**Think:** The container exists. Now we need to put a real value inside it. `App` currently holds the theme state from Step 1's thought experiment — actually let's write that now.

**File: `src/App.tsx`**

```tsx
import { useState } from "react";
import { ThemeContext, type Theme } from "./contexts/ThemeContext";
import Navbar from "./components/Navbar";
import ThemedBox from "./components/ThemedBox";

function App() {
  const [theme, setTheme] = useState<Theme>("light");

  const toggleTheme = () => setTheme((prev) => (prev === "light" ? "dark" : "light"));

  return (
    <ThemeContext value={{ theme, toggleTheme }}>
      <Navbar />
      <ThemedBox />
    </ThemeContext>
  );
}

export default App;
```

**Line by line:**

- `import { ThemeContext, type Theme } from "./contexts/ThemeContext"` — using the context + the type. Neither works without both
- `import Navbar from "./components/Navbar"` and `import ThemedBox from "./components/ThemedBox"` — the two consumers from Step 1. We create them in Steps 4 and 7
- `const [theme, setTheme] = useState<Theme>("light")` — state starts as `"light"`; type locked to `Theme`
- `toggleTheme` — flips light ↔ dark with `setTheme((prev) => ...)` callback form so we never read a stale value
- `<ThemeContext value={{ theme, toggleTheme }}>` — **this is the provider.** Everything inside it can read the value
  - `value={{ theme, toggleTheme }}` — one object with both the data and the setter
  - **Why two pairs of curly braces `{{ }}`?** — the **outer** `{ }` marks a JSX *expression* (everything between `{` and `}` in JSX is evaluated as JavaScript). The **inner** `{ }` is a plain JavaScript object literal — creating an object with two shorthand properties: `theme` and `toggleTheme`. Same shorthand you already know from `const obj = { theme, toggleTheme }` — key name defaults to the variable name, no need to write `theme: theme`. So `value={{ theme, toggleTheme }}` reads as: "JSX prop, value is an object holding `theme` and `toggleTheme`." If you prefer clarity, `value={{ theme: theme, toggleTheme: toggleTheme }}` is exactly the same thing — just not needed.
  - **React 19 syntax**: no `.Provider` needed; the context object itself is the provider

**Two things to notice before moving on:**
- `<Navbar />` and `<ThemedBox />` are the tree from Step 1 — the components that will *read* this context
- Don't import `ThemeContext` and then also `<ThemeContext.Provider>` — in React 19 give `<ThemeContext value={...}>` directly

**Test:** Nothing renders yet — the browser shows an import error until `Navbar.tsx` and `ThemedBox.tsx` exist. We'll fix that in the next two steps. ✅

**How the value actually reaches Navbar — no hidden step:**

`value={{ theme, toggleTheme }}` attaches the data at this exact position in the tree React renders. That's the whole delivery system. Any component rendered **below** this point can read the value; anything **above** it, or rendered **after** the closing tag, reads nothing. React doesn't send the value anywhere — the value just sits at that position, and components under the provider pull from there.

Which sets up the question Step 4 answers properly: if the value sits at App's position in the tree, why will `Navbar.tsx` import `ThemeContext` again? Short answer — the import is not for the value; it's how Navbar names WHICH container it wants to read. Step 4 shows it.

## Step 4 — Consume the value (`Navbar.tsx`)

**Think:** Navbar is wrapped in the provider — now Navbar pulls the theme out of the context container with `useContext`. If it's used outside the provider, the value is `undefined` — guard with a throw.

**File: `src/components/Navbar.tsx`**

```tsx
import { useContext } from "react";
import { ThemeContext } from "../contexts/ThemeContext";

export default function Navbar() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("Navbar must be inside <ThemeContext>");

  return (
    <nav style={{ background: ctx.theme === "dark" ? "#333" : "#eee", padding: "1rem" }}>
      <h1>My App</h1>
      <button onClick={ctx.toggleTheme}>
        Switch to {ctx.theme === "light" ? "Dark" : "Light"} Mode
      </button>
    </nav>
  );
}
```

**Line by line:**

- `useContext(ThemeContext)` — one argument: the container. One return: whatever the provider passed in `value`
- `if (!ctx) throw ...` — guard; message includes the component name so bugs are obvious
- `ctx.theme === "dark" ? "#333" : "#eee"` — conditional style derived from context
- `ctx.toggleTheme` — button's click target; toggles the entire tree's theme from one click

**Wait — App already imported `ThemeContext`. Why does Navbar import it again?**

Because the import and the data are two different things.

The import gives Navbar the **same container object** that App used — nothing more. There is no data inside the import.

The data moves a different way — through the tree. Watch the two jobs side by side:

- **App's job** — put the value into the tree: `<ThemeContext value={{ theme, toggleTheme }}>`. The import matters here because App needs the container object to attach the value to.
- **Navbar's job** — take the value out: `useContext(ThemeContext)`. The import matters here because `useContext` needs to know WHICH container to read — it can't guess. `ThemeContext` is that name.

Now follow what React does when Navbar calls `useContext(ThemeContext)`. It starts at Navbar's position in the rendered tree and walks up, one parent at a time — the climb — until it meets the first `ThemeContext` that has a value. It stops there and hands back that value:

```
<ThemeContext value={{ theme, toggleTheme }}>   ← the climb stops here
  <Navbar />                                     ← the climb starts here
</ThemeContext>
```

That's why the same import line sits in both files with two different uses: App fills the container, Navbar names the container while reading. The import itself never carries the data.

And the mistake to never make: calling `createContext` again inside Navbar. That creates a second container — brand new, empty, and no provider above it ever fills it, so `useContext` on it returns `undefined` forever. One container. Import it. Never recreate it.

**Why the guard matters:**

If a component calls `useContext(ThemeContext)` and there is NO `ThemeContext` with a value anywhere above it in the tree, the climb walks all the way to the root and finds nothing. Then `useContext` returns the container's default — the `undefined` we set in Step 2. Reading `ctx.theme` on that crashes with `Cannot read properties of undefined` — true, but useless. The guard turns that hidden crash into a clear sentence: `Navbar must be inside <ThemeContext>`.

**Creating ThemedBox — same pattern, different component:**

**File: `src/components/ThemedBox.tsx`**

```tsx
import { useContext } from "react";
import { ThemeContext } from "../contexts/ThemeContext";

export default function ThemedBox() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("ThemedBox must be inside <ThemeContext>");

  return (
    <div
      style={{
        padding: "40px",
        background: ctx.theme === "dark" ? "#1a1a2e" : "#fff",
        color: ctx.theme === "dark" ? "#fff" : "#000",
      }}
    >
      <h2>Current theme: {ctx.theme}</h2>
      <button onClick={ctx.toggleTheme}>Switch theme</button>
      <p style={{ marginTop: "12px" }}>This box uses context — no props drilled to get here.</p>
    </div>
  );
}
```

**Test:**
1. The browser loads — white page, light navbar tone
2. Click "Switch to Dark Mode" in the navbar — whole app flips: nav background, box background, colors
3. Click "Switch to Light Mode" — back to light

✅

## Step 5 — The same code, twice: custom hook

**Think:** First, notice the file itself — Step 2 gave `ThemeContext.tsx` the container, this step adds the hook to the same file, and Step 6 will add the provider there too. Same file, growing one export at a time.

Now the hook. Look at what Navbar and ThemedBox both wrote, character for character:

```tsx
const ctx = useContext(ThemeContext);
if (!ctx) throw new Error("<ComponentName> must be inside <ThemeContext>");
```

That guard doesn't change. The only thing across every consumer is the component name inside the message. We're repeating ourselves — solve it with a custom hook.

**Concept — custom hook:** a function starting with `use` that itself calls React hooks. It's a wrapper — it composes `useContext` + the guard.

**Update: `src/contexts/ThemeContext.tsx`**

```tsx
import { createContext, useContext } from "react";

export type Theme = "light" | "dark";

export interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within <ThemeContext>");
  return ctx;
}
```

**Line by line:**

- Now `useContext` is imported too
- `useTheme()` — starts with `use`, so React treats it as a hook
- Return type `ThemeContextValue` — guaranteed a valid value object, never `undefined`
- Guard inside — every consumer gets it free
- `ThemeContext` lives in the same file — no re-import needed for it, only for `useContext`

**Rewrite Navbar and ThemedBox to use it:**

```tsx
import { useTheme } from "../contexts/ThemeContext";

export default function Navbar() {
  const { theme, toggleTheme } = useTheme();
  // same JSX as before — now without useContext or the guard
}
```

```tsx
import { useTheme } from "../contexts/ThemeContext";

export default function ThemedBox() {
  const { theme, toggleTheme } = useTheme();
  // same JSX as before
}
```

Nothing in the JSX changes — only the line above it.

**Test:** Click the toggle — app still works, same as before. The gain is repetition: one hook, always the same guard, every consumer short. ✅

## Step 6 — Extract `ThemeProvider` — App shrinks

**Think:** App currently holds state and the toggle logic *and* renders layout. That's two jobs. Extract the state + provider wiring into a `ThemeProvider` component — App just renders layout.

**Add to: `src/contexts/ThemeContext.tsx`**

```tsx
import { createContext, useContext, useState, type ReactNode } from "react";

export type Theme = "light" | "dark";

export interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within <ThemeContext>");
  return ctx;
}

interface ThemeProviderProps {
  children: ReactNode;
}

export function ThemeProvider({ children }: ThemeProviderProps) {
  const [theme, setTheme] = useState<Theme>("light");

  const toggleTheme = () => setTheme((prev) => (prev === "light" ? "dark" : "light"));

  return <ThemeContext value={{ theme, toggleTheme }}>{children}</ThemeContext>;
}
```

**Line by line:**

- `useState` moves in — the state and toggle handler now live where the provider is
- `ReactNode` — every child type can be passed (`children: ReactNode`)
- `ThemeProvider` renders `<ThemeContext value={{ theme, toggleTheme }}>` around whatever it wraps

**Where does `children` come from? This is the part that trips everyone.**

Look at what App is about to render:

```tsx
<ThemeProvider>
  <Navbar />
  <ThemedBox />
</ThemeProvider>
```

`children` is exactly what App wrote **between the tags** — `<Navbar />` and `<ThemedBox />`. React hands that JSX to ThemeProvider as a normal prop. ThemeProvider places it at `{children}` inside its own return — and that slot sits **inside** `<ThemeContext value=...>`. So Navbar ends up below the provider in the tree for one simple reason: it was written between the tags. Nobody moves anything.

And notice where the climb stops now. ThemeProvider itself is NOT the stop — it's just a component, no value sits on it. The value is attached at the `<ThemeContext value=...>` element that ThemeProvider renders:

```
App writes:     <ThemeProvider>                      ← a component, not the stop
ThemeProvider
renders:        <ThemeContext value={{...}}>         ← the stop — the value is attached HERE
                  <Navbar />                          ← Navbar really exists here, inside
                </ThemeContext>
```

When React climbs from `Navbar`, the element right above it is that `ThemeContext` with the value — stop, value found. And note: the state moved into this FILE, but files mean nothing to the climb. React only looks at the rendered tree and stops at the first matching container with a value above the reader, wherever in the tree that lands.

**Update: `src/App.tsx`**

```tsx
import { ThemeProvider } from "./contexts/ThemeContext";
import Navbar from "./components/Navbar";
import ThemedBox from "./components/ThemedBox";

function App() {
  return (
    <ThemeProvider>
      <Navbar />
      <ThemedBox />
    </ThemeProvider>
  );
}

export default App;
```

**Line by line:**

- `<ThemeProvider>` wraps the whole app — one line, all state + provider plumbing encapsulated
- Gone: `useState`, `toggleTheme`, `ThemeContext` import — App only imports ThemeProvider + children

**Test:** Reload — app looks and behaves exactly as before. The difference is separation: `App` arranges the layout; `contexts/ThemeContext.tsx` runs the theme. ✅

## Step 7 — One more consumer, built phase by phase

Step 7 was previously the biggest, jankiest section — building a separate component "from 0" with incremental phases that re-used Context API content. Now the entire flow already exists: we have a provider, two consumers (`Navbar` and `ThemedBox`), and a custom hook. The remaining “build from 0” step doesn't teach anything new — so we replace it with a **shorter** phase-driven build of one piece from 0.

**Build a `<UserBadge />` — my avatar + my theme, phased from zero.**

*Phase 1 — Skeleton:* render a placeholder avatar div. No theme yet, just static HTML.

```tsx
export default function UserBadge() {
  return <div style={{ width: 48, height: 48, borderRadius: "50%", background: "#555" }} />;

```

*Phase 2 — Connect context:* pull `{ theme }` from useTheme, make the background dark or light.

```tsx
import { useTheme } from "../contexts/ThemeContext";

    <div
      style={{

        height: 48,
```

## Step 8 — Context API: When to Use, When to Avoid

**Think for yourself before reading:** contexts that just diffuse values create a rendering dependency the compiler can't eliminate — every consumer re-renders on any value change. That's the cost.

### Use Context For
- Theme (dark/light)
- Auth user + logged-in status
- Locale/language
- Any data needed throughout the tree

### Avoid Context For
- High-frequency updates — animations, real-time data → every consumer re-renders
- Data only 2-3 components need — just prop it, or lift state
- Complex state logic — Zustand handles it better (Batch 6)

---

## Step 9 — Performance Preview (Batch 5)

Every render of `ThemeProvider` creates a fresh `{ theme, toggleTheme }` object — new reference — and every component that called `useTheme()` re-renders, even if the theme itself didn't change. That's how Context works by design: it doesn't compare values, it broadcasts.

For this small app that doesn't matter. When your app gets big and every keystroke re-renders the whole tree, that's the point when optimization becomes necessary — and that's exactly what **Batch 5 — Performance** teaches: `useMemo` (memoize the value object so consumers don't re-render on unrelated renders) and `useCallback` (memoize the function reference so children that receive it don't re-render).

**Nothing to implement yet — those hooks are Batch 5.** Just know the cost:

```
ThemeProvider renders → new {theme, toggleTheme} object
→ every useTheme() consumer re-renders
→ even if theme didn't change
```

**If Context starts hurting in real apps — split concerns:**

- `HeaderContext` — rarely-changing values (logo, app title)
- `DataContext` — frequently-changing values (live data)

Each consumer only subscribes to the context it uses. When Context still isn't enough, Batch 6 — Zustand/Redux — is the upgrade.

---

## What Context API Is NOT

- It's not a global variable everything can read — the value lives at one position in the rendered tree, and only components below that position can read it.
- It's not protection from re-renders — every consumer re-renders whenever the value object changes (Step 9).
- It's not free to wire up wrongly — one container only, imported everywhere. A second `createContext` call makes a new, empty container that connects to nothing.
- It's not for data one or two props could handle — props stay simpler for short distances (Step 8).

---

## Trade-off: Context vs Alternatives

| Pattern | Use Case | Problem |
|---|---|---|
| **Lifting State Up** | 2-3 siblings share state | Prop drilling in deep trees |
| **Composition** | Middle components don't need data | Can't work for every case |
| **Context API** | Theme, auth, locale, tree-wide values | High-frequency updates → full subtree re-render |
| **Zustand/Redux** (Batch 6) | Complex state, high perf | Extra boilerplate — use when Context struggles |

**Rule of thumb:** Lift first. Compose second. Context third. Zustand when Context's re-renders become a problem.

---

## Common Mistakes

1. **Forgetting the Provider** — context value stays `undefined`. The guard hook gives an obvious error
2. **Too much in context** — only tree-wide, low-frequency data belongs here; lifting state is simpler otherwise
3. **High-frequency updates** — use Zustand or an external store instead
4. **Context value recreated every render** — every render of the provider creates a fresh object, so all consumers re-render even if the data didn't change. Batch 5 (useMemo/useCallback) covers the fix — don't reach for it here.
5. **Re-creating the context in a consumer file** — `createContext` called twice makes two different containers. The second one is empty and nothing above ever fills it — `useContext` on it returns `undefined` forever. Import the one container instead.

## Summary

| Concept | In Essence |
|---|---|
| `createContext<T>(default)` | Creates the container — export it |
| `<ThemeContext value={val}>{children}</ThemeContext>` | Provider — makes the value available to all descendants |
| `useTheme()` / `useContext(Context)` | Read the value + optional guard |
| `ThemeProvider` component | Hold the state, render `<ThemeContext>` — single responsibility |
| Prop drilling | Middle components forward props they don't use |
| File structure | Context in its own file — no Fast Refresh warning, no import loops |
| Consumer re-renders | Value change re-renders all consumers |
| `value=` in, `useContext` out | Data enters through the provider's `value=`, exits through `useContext` — same object, two doors |
| The climb | `useContext` walks up the rendered tree to the FIRST matching container with a value |
| The import | Gives the same container object in every file — the tree carries the value, not the import |

## Cheat Sheet (Quick Recall)

**The problem:** lift state to a shared parent, but when the tree is deep, every middle component must forward props it doesn't use — theme, auth, locale — painful to write, painful to refactor.

**The fix — Context API:** declare a Provider once near the root, every descendant reads the same value via hooks — zero props drilled through middle layers.

**Setup (once, in `src/contexts/ThemeContext.tsx`):**

```tsx
import { createContext, useContext, useState, type ReactNode } from "react";

export type Theme = "light" | "dark";
export interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}
export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within <ThemeContext>");
  return ctx;
}

export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");
  const toggleTheme = () => setTheme(p => p === "light" ? "dark" : "light");
  return <ThemeContext value={{ theme, toggleTheme }}>{children}</ThemeContext>;
}
```

**Wrap the app (or any subtree):**

```tsx
// main.tsx
import { createRoot } from "react-dom/client";
import App from "./App";
import { ThemeProvider } from "./contexts/ThemeContext";

createRoot(document.getElementById("root")!).render(
  <ThemeProvider><App /></ThemeProvider>
);
```

**Use it anywhere below:**

```tsx
import { useTheme } from "../contexts/ThemeContext";
const { theme, toggleTheme } = useTheme();
<button onClick={toggleTheme}>Switch to {theme === "light" ? "Dark" : "Light"} Mode</button>
```

**That's it. One provider, any number of consumers across the tree. No prop passing at any level.**

**How the value travels (memorize this):** data goes in through `value=` on the provider and comes out through `useContext(Container)` in any component below it. React finds it by walking up from the consumer to the first matching container above. The import shares that one container object everywhere; a second `createContext` call creates a different, empty container that connects to nothing.

**Rules of thumb:**
- Reach for it when the value is needed by **3+ levels** and is **tree-wide, low-frequency** — theme, locale, auth
- Skip it for **keystroke-frequency** updates — every consumer re-renders each change
- Skip it for **1-2 levels** — props are clearer
- If Context feels cramped, Zustand (Batch 6) takes over — same mental model, more efficient
