# 2.3 Quiz — TanStack React Query

## MCQ

Q: `useQuery` hook kin chaar cheezo ko return karta hai?
A. `data`, `isLoading`, `isError`, `error` — teeno states ek saath, manually sync karne ki zaroorat nahi
B. `data`, `loading`, `error`, `success` — loading boolean, error string, success boolean alag
C. `response`, `pending`, `failed`, `message` — response object, pending status, failed flag, error text
D. `result`, `isFetching`, `hasError`, `errorMessage` — result data, fetching flag, error flag, error string
> A. `useQuery` chaar cheezein return karta hai: `data` (actual API response), `isLoading` (pehli baar fetch), `isError` (fetch fail), `error` (Error object). Sab internally sync hain — ek badla toh doosra auto adjust hota hai.

Q: `queryKey` ka kya kaam hai TanStack React Query mein?
A. Query ko uniquely identify karta hai — caching, deduplication, aur refetch isi key ke basis par hota hai
B. Query ka priority level set karta hai — zyada priority wali pehle execute hoti hain
C. Query ka timeout duration define karta hai — kitni der baad fetch automatically cancel ho
D. Query ka HTTP method decide karta hai — GET, POST, PUT, DELETE
> A. `queryKey` ek unique identifier hai. `["recipes", "chicken"]` — isi key se cache store hota hai, deduplication hoti hai, aur refetch control hota hai. Same key = cache hit, different key = new fetch. Pehla element resource type (`"recipes"`), baaki identifiers.

---

Q: `enabled` option `useQuery` mein kya control karta hai?
A. Data ko UI mein render karne ki permission deta hai — false hai toh data dikhega nahi
B. Fetch trigger ko control karta hai — true hai tab fetch chalega, false hai tab nahi chalega chahe key change ho
C. Internet connectivity check karta hai — automatically detect karta hai ki user online hai ya nahi
D. Button ki enabled/disabled state set karta hai — button disable ho jata hai
> B. `enabled` ek boolean flag hai. `true` → fetch chalega (jab key change ho, cache miss ho). `false` → fetch nahi chalega — chahe key change ho, component re-render ho, kuch bhi ho. `enabled: !!query` se empty string pe fetch block hota hai.

Q: Agar API fetch trigger ko directly input field ke saath bind kar diya jaye (har keystroke pe `queryKey` change ho), toh kya problem hogi?
A. Har character type karne par naya network request jayega — wasteful API calls hongi
B. Koi problem nahi — React Query automatically debounce kar deta hai har request ko
C. Input field ka value update hona band ho jayega — React crash karega
D. Sirf ek baar fetch chalega — `queryKey` change hone ke bawajood duplicate requests nahi aati
> A. Agar fetch trigger directly input se bound ho toh har keystroke pe `queryKey` change hogi → cache miss → naya fetch chalega. "pasta" type karte waqt 5 requests jayengi. Solution: do states rakho — ek input binding ke liye (har keystroke pe update), doosra fetch trigger ke liye (sirf submit pe update).

Q: `QueryClientProvider` kyun zaroori hai TanStack React Query mein?
A. Yeh React app ko routing provide karta hai — query results ke hisaab se pages navigate kar sakte hain
B. Yeh CSS-in-JS styling provide karta hai — query ke naam se custom styles apply ho jaate hain
C. Yeh `useQuery` ko `QueryClient` instance provide karta hai — jahan cache store hota hai aur saara management hota hai
D. Yeh error boundary ka kaam karta hai — query fail ho to fallback UI dikhata hai
> C. `QueryClientProvider` ek wrapper component hai jo Context API ke through `QueryClient` instance provide karta hai. `QueryClient` mein saara cache store hota hai — woh dictionary jahan `{ '["recipes","chicken"]': { data: [...] } }` stored hai. Iske bina `useQuery` ko cache/store pata nahi hoga — error aayega.

Q: Agar do alag components same `queryKey` use karein, toh kitne network requests jayengi?
A. Sirf ek — React Query deduplicate karta hai, dono same cache share karenge
B. Do — har component ka apna fetch chalega lekin cache alag store hoga
C. Zero — same key use nahi kar sakte, error throw karta hai
D. Har render pe naya fetch — component independent hain toh caching share nahi hoti
> A. React Query key-based deduplication karta hai. Do components same `["recipes", "chicken"]` key use karein toh sirf ek network request jayegi. Dono components same data receive karenge — cache se. Isse performance improve hoti hai aur network bandwidth bachti hai.

Q: `isLoading` aur `isFetching` mein kya fark hai?
A. `isLoading` true hai jab pehli baar fetch ho raha hai (cache mein kuch nahi), `isFetching` true hai jab koi bhi fetch chal raha hai (background refetch bhi)
B. Dono same hain — sirf alag names hain, same meaning
C. `isLoading` initial mount ke liye hai, `isFetching` button click ke liye hai
D. `isLoading` async operations ke liye hai, `isFetching` synchronous ke liye hai
> A. `isLoading` sirf pehli baar true hota hai jab cache mein data nahi hai aur network request chal rahi hai. `isFetching` har baar true hota hai — chahe pehli baar ho ya background refetch. Example: `staleTime` cross karne ke baad auto-refetch — `isLoading` false rahega (cache hai), lekin `isFetching` true hoga.

Q: `!!query` ka `enabled` option mein kya matlab hai?
A. Double NOT operator — `""` empty string ko `false` convert karta hai, `"chicken"` ko `true`
B. TypeScript type assertion — `query` ko boolean type mein cast karta hai
C. Null check operator — `query` null hai toh error throw karta hai
D. Optional chaining — `query` undefined hai toh default value provide karta hai
> A. `!!` double NOT operator hai. `!!"chicken"` — `"chicken"` truthy hai, NOT true = false, NOT false = true → result `true`. `!!""` — `""` falsy hai, NOT false = true, NOT true = false → result `false`. Is tarah non-empty value pe fetch enable hota hai, empty pe disable.

Q: `useQuery` kis type ke state ke liye use hota hai?
A. Client state — theme toggle, form input, modal open/close, sidebar visibility
B. Server state — API se aane wala data, jiska lifecycle (loading/fetch/cache/refetch) manage karna hai
C. Global state — poore app mein accessible data, Redux ki tarah koi bhi component read/write kar sake
D. URL state — browser URL par base kiya hua state, query parameters aur path segments
> B. `useQuery` specifically server state (API data) ke liye hai. Client state ke liye `useState` use karo. Global state management (Redux/Zustand) nahi hai — sirf API data lifecycle manage karta hai. Isko `useEffect` ka replacement bhi nahi samajhna chahiye.

## TrueFalse

Q: `useQuery`, `useState` ka replacement hai — `useState` ki jagah `useQuery` use kar sakte hain kisi bhi state ke liye.
- True
- False
> False. `useQuery` sirf server state (API data) ke liye hai. Client state (theme toggle, form input, modal) ke liye `useState` ka use karo. Dono alag problems solve karte hain — `useState` client ke liye, `useQuery` server ke liye.

---

Q: Agar do components same `queryKey` use karein toh sirf ek network request jayegi — React Query deduplicate karta hai.
- True
- False
> True. React Query internally keys ka map maintain karta hai. Jab ek key ke liye fetch chal raha hai aur doosra component same key request karta hai, toh React Query dusra fetch nahi karega — pehle wale ka result dono ko provide karega. Isse duplicate network requests prevent hoti hain.

---

Q: `searchInput` ko directly `useQuery` ki `queryKey` mein daalna sahi practice hai — is tarah real-time search implement hota hai.
- True
- False
> False. `searchInput` har keystroke pe update hota hai, toh `queryKey` har character ke saath change hogi aur har baar naya fetch chalega — wasteful API calls. Best practice: do states pattern — `searchInput` for input binding, `query` for fetch trigger (sirf submit pe update).

---

Q: `QueryClientProvider` wrap nahi kiya toh `useQuery` "No QueryClient set" error dega.
- True
- False
> True. `useQuery` internally React Context API use karta hai — `QueryClientProvider` woh context provide karta hai. Provider nahi hai toh `useQuery` ko `QueryClient` instance nahi milega aur error throw karega.

---

Q: `useQuery` sirf API data fetching ke liye nahi hai — yeh timer, event listener, aur kisi bhi side effect ke liye use ho sakta hai.
- True
- False
> False. `useQuery` specifically server state (API data) ke lifecycle ke liye hai — loading, caching, refetch, retry. Timer, event listener, localStorage — yeh sab `useEffect` ka kaam hai. `useQuery` `useEffect` ka replacement nahi hai.

---

Q: `enabled: false` karne se chahe `queryKey` change ho, component re-render ho, fetch nahi chalega.
- True
- False
> True. `enabled: false` ka matlab hai "fetch permanently disabled." Chahe key change ho, component re-render ho, koi bhi trigger aaye — React Query fetch nahi chalayega. Jab manually `enabled` true karo tab hi fetch chalega.

## ShortAnswer

Q: TanStack React Query ka `useQuery` hook kaise kaam karta hai? Setup (installation + QueryClientProvider) se lekar UI mein data dikhane tak ka poora flow explain karo. `queryKey`, `queryFn`, `enabled`, aur return values ke saath code example do.

<details>
<summary>Sample Answer</summary>

**Step 1 — Install:**
```bash
npm install @tanstack/react-query
```

**Step 2 — Setup QueryClientProvider in main.tsx:**
```tsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'

const queryClient = new QueryClient()

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <App />
    </QueryClientProvider>
  </StrictMode>,
)
```
`QueryClient` = cache ka storage. `QueryClientProvider` = Context Provider ki tarah — andar ke components ko client accessible banata hai.

**Step 3 — Fetch function define karo:**
```ts
async function fetchRecipes(query: string): Promise<Recipe[]> {
  const res = await fetch(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`
  );
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const data = await res.json();
  return data.meals ?? [];
}
```

**Step 4 — Component mein useQuery call karo:**
```tsx
const { data: recipes, isLoading, isError, error } = useQuery({
  queryKey: ["recipes", query],   // unique identifier for caching
  queryFn: () => fetchRecipes(query), // actual fetch function
  enabled: !!query,                // empty string pe fetch block
});
```

**Return values:**
| Variable | Type | Kab kya hota hai |
|---|---|---|
| `data` | `Recipe[] \| undefined` | Initially undefined. Fetch success ke baad actual API response |
| `isLoading` | `boolean` | `true` jab pehli baar fetch chal raha hai (no cache) |
| `isError` | `boolean` | `true` jab fetch fail ho (network down, 404) |
| `error` | `Error \| null` | `null` initially. Error aane par actual Error object |

**Step 5 — UI mein 4 states handle karo:**
```tsx
{isLoading && <p>⏳ Loading...</p>}
{isError && <p style={{ color: "red" }}>❌ {error.message}</p>}
{!isLoading && !isError && query && recipes?.length === 0 && <p>No recipes found.</p>}
{recipes?.map(r => <div key={r.idMeal}>...</div>)}
```

Manual approach (2.2) mein 4 `useState` + try/catch/finally + cleanup chahiye tha. TanStack Query mein sirf 1 `useQuery` — loading/error/caching/retry sab auto.

</details>

Q: Do states pattern (`searchInput` vs `query`) kyun zaroori hai? Agar submit button ki jagah `searchInput` ko directly `useQuery` ki `queryKey` mein daalein toh kya hoga? Example ke saath explain karo.

<details>
<summary>Sample Answer</summary>

**Problem — Direct searchInput useQuery mein:**

```tsx
// ❌ Galat — har keystroke pe naya fetch
const [searchInput, setSearchInput] = useState("chicken");

const { data: recipes } = useQuery({
  queryKey: ["recipes", searchInput],  // har character change pe key change
  queryFn: () => fetchRecipes(searchInput),
});
```

User "pasta" type kare toh kya hoga:
```
"p" type kiya → queryKey ["recipes", "p"] → cache miss → fetch
"pa" type kiya → queryKey ["recipes", "pa"] → cache miss → fetch
"pas" → key change → fetch
"past" → key change → fetch
"pasta" → key change → fetch
```
**5 network requests sirf type karne se.** Yeh wasteful hai — hum chahte hain sirf submit button dabane pe ek request.

**Solution — Do states pattern:**

```tsx
const [searchInput, setSearchInput] = useState("chicken"); // UI binding
const [query, setQuery] = useState("chicken");             // fetch trigger

const { data: recipes } = useQuery({
  queryKey: ["recipes", query],       // query use ho raha hai, searchInput nahi
  queryFn: () => fetchRecipes(query),
  enabled: !!query,
});

const handleSearch = (e: React.FormEvent) => {
  e.preventDefault();
  setQuery(searchInput.trim());  // sirf submit pe query update
};
```

**Flow:**
- User type karta hai → `searchInput` update hota hai (UI binding)
- `query` wahi rehta hai → `queryKey` nahi badla → **fetch nahi chalega**
- User submit dabata hai → `setQuery(searchInput.trim())` → `query` change hua
- `queryKey` badla → React Query dekhta hai "yeh key cache mein nahi" → **fetch chalta hai**

| Scenario | searchInput | query | Fetch? |
|---|---|---|---|
| User "p" type kare | "p" | "chicken" | ❌ |
| User "pasta" type kare | "pasta" | "chicken" | ❌ |
| User submit dabaye | "pasta" | "pasta" | ✅ |
| User empty search kare | "" | "" | ❌ (`enabled: false`) |

Do states ka pattern ensure karta hai ki sirf tab fetch ho jab user actually search karna chahe — har character pe nahi.

</details>
