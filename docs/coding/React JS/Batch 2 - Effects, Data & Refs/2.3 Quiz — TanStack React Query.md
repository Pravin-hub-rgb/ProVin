
## MCQ

Q: What four things does the `useQuery` hook return?
A. `data`, `isLoading`, `isError`, `error` — all three states at once, no need to sync manually
B. `data`, `loading`, `error`, `success` — loading boolean, error string, success boolean separately
C. `response`, `pending`, `failed`, `message` — response object, pending status, failed flag, error text
D. `result`, `isFetching`, `hasError`, `errorMessage` — result data, fetching flag, error flag, error string
> A. `useQuery` returns four things: `data` (actual API response), `isLoading` (first-time fetch), `isError` (fetch failed), `error` (Error object). They're all internally in sync — when one changes, the others auto-adjust.

Q: What does `queryKey` do in TanStack React Query?
A. Uniquely identifies the query — caching, deduplication, and refetch happen based on this key
B. Sets the priority level of the query — higher priority ones execute first
C. Defines the timeout duration — after how long fetch automatically cancels
D. Decides the HTTP method — GET, POST, PUT, DELETE
> A. `queryKey` is a unique identifier. `["recipes", "chicken"]` — the cache is stored based on this key, deduplication happens, and refetch is controlled. Same key = cache hit, different key = new fetch. The first element is the resource type (`"recipes"`), the rest are identifiers.

Q: What does the `enabled` option control in `useQuery`?
A. Grants permission to render data in the UI — false means data won't show
B. Controls the fetch trigger — true means fetch runs, false means it won't even if key changes
C. Checks internet connectivity — automatically detects whether user is online
D. Sets a button's enabled/disabled state — button gets disabled
> B. `enabled` is a boolean flag. `true` → fetch runs (when key changes, cache miss). `false` → fetch won't run — even if key changes, component re-renders, nothing triggers it. `enabled: !!query` blocks fetch on empty string.

Q: If the API fetch trigger is bound directly to an input field (queryKey changes on every keystroke), what problem arises?
A. Every character typed sends a new network request — wasteful API calls
B. No problem — React Query automatically debounces every request
C. The input field's value stops updating — React crashes
D. Only one fetch runs — despite key changing, no duplicate requests
> A. If the fetch trigger is directly bound to input, queryKey changes on every keystroke → cache miss → a new fetch runs. Typing "pasta" sends 5 requests. Solution: keep two states — one for input binding (updates on every keystroke), another for fetch trigger (updates only on submit).

Q: Why is `QueryClientProvider` necessary in TanStack React Query?
A. It provides routing to the React app — navigate pages based on query results
B. It provides CSS-in-JS styling — custom styles applied by query name
C. It provides the `QueryClient` instance to `useQuery` — where the cache is stored and all management happens
D. It acts as an error boundary — shows fallback UI when query fails
> C. `QueryClientProvider` is a wrapper component that provides the `QueryClient` instance via Context API. Without it, `useQuery` won't know the cache/store — an error will be thrown.

Q: If two different components use the same `queryKey`, how many network requests are sent?
A. Only one — React Query deduplicates, both share the same cache
B. Two — each component fetches independently, cache stored separately
C. Zero — can't use the same key, throws an error
D. New fetch on every render — components are independent, caching isn't shared
> A. React Query deduplicates based on keys. Two components using the same `["recipes", "chicken"]` key send only one network request. Both receive the same data — from cache. This improves performance and saves network bandwidth.

Q: What's the difference between `isLoading` and `isFetching`?
A. `isLoading` is true only on first-time fetch (nothing in cache), `isFetching` is true on any fetch (including background refetch)
B. They're the same — just different names, same meaning
C. `isLoading` is for initial mount, `isFetching` is for button click
D. `isLoading` is for async operations, `isFetching` is for synchronous
> A. `isLoading` is true only the first time when there's no data in cache and a network request is running. `isFetching` is true every time — whether first-time or a background refetch. Example: after `staleTime` expires and auto-refetch — `isLoading` stays false (cache exists), but `isFetching` is true.

Q: What does `!!query` mean in the `enabled` option?
A. Double NOT operator — `""` empty string becomes `false`, `"chicken"` becomes `true`
B. TypeScript type assertion — casts `query` to boolean type
C. Null check operator — throws error if `query` is null
D. Optional chaining — provides default value if `query` is undefined
> A. `!!` is the double NOT operator. `!!"chicken"` — "chicken" is truthy, NOT true → false, NOT false → true → result `true`. `!!""` — "" is falsy, NOT false → true, NOT true → false → result `false`. This way fetch is enabled on non-empty values, disabled on empty.

Q: What type of state is `useQuery` used for?
A. Client state — theme toggle, form input, modal open/close, sidebar visibility
B. Server state — data from API, whose lifecycle (loading/fetch/cache/refetch) needs managing
C. Global state — data accessible across the whole app, like Redux where any component can read/write
D. URL state — state based on browser URL, query parameters and path segments
> B. `useQuery` is specifically for server state (API data). Use `useState` for client state. It's not global state management (Redux/Zustand) — it just manages API data lifecycle. It shouldn't be mistaken as a replacement for `useEffect`.

## TrueFalse

Q: `useQuery` is a replacement for `useState` — you can use `useQuery` in place of `useState` for any state.
- True
- False
> False. `useQuery` is only for server state (API data). Use `useState` for client state (theme toggle, form input, modal). They solve different problems — `useState` for client, `useQuery` for server.

---

Q: If two components use the same `queryKey`, only one network request is sent — React Query deduplicates.
- True
- False
> True. React Query internally maintains a map of keys. When a fetch is running for one key and another component requests the same key, React Query won't fetch again — the first one's result is provided to both. This prevents duplicate network requests.

---

Q: Putting `searchInput` directly into `useQuery`'s `queryKey` is correct practice — this is how real-time search is implemented.
- True
- False
> False. `searchInput` updates on every keystroke, so `queryKey` changes with every character and a new fetch runs every time — wasteful API calls. Best practice: the two-state pattern — `searchInput` for input binding, `query` for fetch trigger (update only on submit).

---

Q: If `QueryClientProvider` is not wrapped, `useQuery` will throw "No QueryClient set" error.
- True
- False
> True. `useQuery` internally uses React Context API — `QueryClientProvider` is what provides this context. Without a Provider, `useQuery` won't receive a `QueryClient` instance and will throw an error.

---

Q: `useQuery` is not just for API data fetching — it can be used for timers, event listeners, and any side effect.
- True
- False
> False. `useQuery` is specifically for the lifecycle of server state (API data) — loading, caching, refetch, retry. Timers, event listeners, localStorage — all that is `useEffect`'s job. `useQuery` is not a replacement for `useEffect`.

---

Q: Setting `enabled: false` means fetch won't run — even if `queryKey` changes or component re-renders.
- True
- False
> True. `enabled: false` means "fetch permanently disabled." Even if the key changes, the component re-renders, or any other trigger occurs — React Query won't fetch. Fetch only runs when you manually set `enabled` to true.

## ShortAnswer

Q: How does TanStack React Query's `useQuery` hook work? Explain the complete flow from setup (installation + QueryClientProvider) to displaying data in the UI. Include a code example with `queryKey`, `queryFn`, `enabled`, and return values.

<details>
<summary>Sample Answer</summary>

**Step 1 — Install:**
```bash
npm install @tanstack/react-query
```

**Step 2 — Setup QueryClientProvider in main.tsx:**
```tsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'

const queryClient = new QueryClient()

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <App />
    </QueryClientProvider>
  </StrictMode>,
)
```
`QueryClient` = the cache storage. `QueryClientProvider` = like a Context Provider — makes the client accessible to inner components.

**Step 3 — Define the fetch function:**
```ts
async function fetchRecipes(query: string): Promise<Recipe[]> {
  const res = await fetch(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`
  );
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const data = await res.json();
  return data.meals ?? [];
}
```

**Step 4 — Call useQuery in the component:**
```tsx
const { data: recipes, isLoading, isError, error } = useQuery({
  queryKey: ["recipes", query],   // unique identifier for caching
  queryFn: () => fetchRecipes(query), // actual fetch function
  enabled: !!query,                // blocks fetch on empty string
});
```

**Return values:**
| Variable | Type | What happens when |
|---|---|---|
| `data` | `Recipe[] \| undefined` | Initially undefined. After fetch success, the actual API response |
| `isLoading` | `boolean` | `true` when fetching for the first time (no cache) |
| `isError` | `boolean` | `true` when fetch fails (network down, 404) |
| `error` | `Error \| null` | `null` initially. When an error occurs, the actual Error object |

**Step 5 — Handle 4 states in the UI:**
```tsx
{isLoading && <p>⏳ Loading...</p>}
{isError && <p style={{ color: "red" }}>❌ {error.message}</p>}
{!isLoading && !isError && query && recipes?.length === 0 && <p>No recipes found.</p>}
{recipes?.map(r => <div key={r.idMeal}>...</div>)}
```

In the manual approach (2.2), we needed 4 `useState` + try/catch/finally + cleanup. In TanStack Query, just 1 `useQuery` — loading/error/caching/retry all automatic.

</details>

Q: Why is the two-state pattern (`searchInput` vs `query`) necessary? If you put `searchInput` directly into `useQuery`'s `queryKey` instead of using a submit button, what happens? Explain with an example.

<details>
<summary>Sample Answer</summary>

**Problem — Using searchInput directly in useQuery:**

```tsx
// ❌ Wrong — new fetch on every keystroke
const [searchInput, setSearchInput] = useState("chicken");

const { data: recipes } = useQuery({
  queryKey: ["recipes", searchInput],  // key changes with every character
  queryFn: () => fetchRecipes(searchInput),
});
```

If the user types "pasta":
```
"p" typed → queryKey ["recipes", "p"] → cache miss → fetch
"pa" typed → queryKey ["recipes", "pa"] → cache miss → fetch
"pas" → key change → fetch
"past" → key change → fetch
"pasta" → key change → fetch
```
**5 network requests just for typing.** This is wasteful — we want only one request when the submit button is pressed.

**Solution — Two-state pattern:**

```tsx
const [searchInput, setSearchInput] = useState("chicken"); // UI binding
const [query, setQuery] = useState("chicken");             // fetch trigger

const { data: recipes } = useQuery({
  queryKey: ["recipes", query],       // uses query, not searchInput
  queryFn: () => fetchRecipes(query),
  enabled: !!query,
});

const handleSearch = (e: React.FormEvent) => {
  e.preventDefault();
  setQuery(searchInput.trim());  // update query only on submit
};
```

**Flow:**
- User types → `searchInput` updates (UI binding)
- `query` stays the same → `queryKey` doesn't change → **no fetch**
- User presses submit → `setQuery(searchInput.trim())` → `query` changes
- `queryKey` changes → React Query checks "is this key in cache?" → **fetch runs**

| Scenario | searchInput | query | Fetch? |
|---|---|---|---|
| User types "p" | "p" | "chicken" | ❌ |
| User types "pasta" | "pasta" | "chicken" | ❌ |
| User presses submit | "pasta" | "pasta" | ✅ |
| User empty search | "" | "" | ❌ (`enabled: false`) |

The two-state pattern ensures fetch happens only when the user actually wants to search — not on every character.

</details>
