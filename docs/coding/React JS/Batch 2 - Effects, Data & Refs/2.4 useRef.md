
## Where We Left Off

So far we've learned 3 hooks — `useState` (client state), `useEffect` (timers + API fetches), and `useQuery` (server data). They all share a common pattern: **state change → re-render → UI update.** But some values aren't related to the UI — they shouldn't be displayed on screen, just kept in the background. For those, we need something different.

---

## Broader Goal

Learn the `useRef` hook — it does two things:

1. **Store a value without triggering a re-render** — timer ID, render count, previous value
2. **Directly access a DOM element** — input focus, video play, scroll position

First we'll understand **why a different tool is needed** (comparison demo), then the syntax, then real use cases.

---

## Step 1 — useState vs useRef: Visual Comparison

Think about it: when we use `useState`, React "subscribes" to it — "if this state changes → re-render the component, update the UI." But sometimes we want to store a value that shouldn't trigger a UI update. A real example: **previous value comparison** — the current count is displayed on screen (`useState`). But to show "Previous: 5 → Current: 6", we also need the previous count. If that's stored in `useState` too, the previous value changing triggers a re-render — infinite loop or unnecessary renders.

If you use a plain variable (`let prevCount = 0`), it resets on every render. `useRef` solves both — persists across renders and doesn't trigger re-render.

**First, let's see the visual difference — two buttons, two counters:**

**Let's see both at once — in the same component, two buttons, two counters:**

```tsx
import { useState, useRef } from "react";

function CompareDemo() {
  const [stateCount, setStateCount] = useState(0);
  const refCount = useRef(0);

  const handleStateClick = () => {
    setStateCount(stateCount + 1);
    console.log("State count:", stateCount + 1);
  };

  const handleRefClick = () => {
    refCount.current = refCount.current + 1;
    console.log("Ref count:", refCount.current);
  };

  return (
    <div>
      <h2>useState vs useRef</h2>

      <button onClick={handleStateClick}>State Button</button>
      <p>State count: {stateCount}</p>

      <button onClick={handleRefClick}>Ref Button</button>
      <p>Ref count: (check console)</p>
    </div>
  );
}
```

⚠️ **Why not `{refCount.current}` in JSX instead of "(check console)"?** Because `useRef` changes never re-render — if the UI bound to the ref, it would stay stale on screen. And even when *some other* state change triggers a re-render, a fresh value isn't guaranteed at the moment JSX reads it. So we keep the ref's value on the console here — the "correct" display is the console, not JSX.

**TEST — there are two buttons, click and observe:**

| Click # | State Button → Console | State Button → UI | Ref Button → Console | Ref Button → UI |
|---|---|---|---|---|
| 1st click | `State count: 1` | Shows **1** | `Ref count: 1` | **(check console)** |
| 2nd click | `State count: 2` | Shows **2** | `Ref count: 2` | Still **(check console)** |
| 3rd click | `State count: 3` | Shows **3** | `Ref count: 3` | Still **(check console)** |
| 5 clicks | `State count: 5` | Shows **5** | `Ref count: 5` | Still **(check console)** |

What do you see?

- **State Button** click → `<p>State count: N</p>` **updates on screen** with every click.
- **Ref Button** click → Console prints `1, 2, 3, 4, 5` (the value inside is changing), **but nothing updates on screen.**

**Why?** `refCount.current = refCount.current + 1` doesn't send any signal to React. React only "watches" `useState`. The `useRef` value changes, but React doesn't know about it — no re-render, no UI update. The console reads the JS variable directly, so it shows the latest value.

> **Nutshell:** `useState` = tells React "something changed, re-render." `useRef` = silently stores, React doesn't know. Don't put `.current` in JSX — React doesn't guarantee the value will be up-to-date.

## Step 2 — What Does "Ref" Mean?

**Concept:** Calling `useRef(0)` makes React return an object — `{ current: 0 }`. Just a plain JavaScript object with a single property called `current`.

```ts
const refCount = useRef(0);
// refCount = { current: 0 }
```

This object has two key properties:

### 1. Persistence — Doesn't Reset Between Renders

React components are functions that get re-called on every render. If you write `let x = 0` inside a component, `x` resets to 0 on every render — because the function is running fresh.

The object created by `useRef` **does not reset.** React stores it internally and returns the same object on every render — same reference, same `current` value left from the last render.

```
Render 1: refCount = { current: 0 }
  → refCount.current = 5  (manually set)
Render 2: refCount = { current: 5 }  ← same object, value persists
  → refCount.current = 10
Render 3: refCount = { current: 10 }  ← still same object
```

### 2. No Re-render Trigger — React Isn't "Watching"

`setState(5)` triggers React's internal system → "something changed, re-render."

`refCount.current = 5` → just a normal JavaScript object property change, like `myObj.name = "Vin"`. React isn't watching that object. So no signal is sent, no re-render occurs.

React only re-renders when a `useState` setter is called. `useRef` is not on that list — changing `.current` is a plain JS property update, React has no knowledge of it.

### Why Is It Called "Ref"?

Ref = **Reference**. It's not the value itself — it's an object with a `current` property that holds a value or DOM element reference. `useRef` returns `{ current: initialValue }` — you read and write through `.current`.

> **Nutshell:** `useRef(initialValue)` returns a `{ current: initialValue }` object that stays the same reference across renders. Changing `.current` does **not** trigger a re-render — because React doesn't watch useRef. It's perfect for values that aren't related to the UI.

## Step 3 — TypeScript Typing: DOM Ref vs Mutable Ref

`useRef` creates two different TypeScript types depending on the initial value.

### DOM Ref — `useRef<HTMLInputElement>(null)`

When the initial value is `null`, TypeScript understands "this is a reference to a DOM element":

```ts
const inputRef = useRef<HTMLInputElement>(null);
// typeof inputRef → RefObject<HTMLInputElement | null>
// .current → HTMLInputElement | null (READONLY)
```

Here, `<HTMLInputElement>` is a **generic type** that says which DOM element this ref points to — `<input>`, `<video>`, `<div>`, etc. React automatically fills `.current` with the actual DOM node — so `.current` is **readonly** (you can't assign to it, only React does).

`null` as default value means: "the DOM element hasn't rendered yet, so it's null. After render, React fills it with the actual DOM node."

### Mutable Ref — `useRef<number>(0)`

When the initial value is a non-null value, TypeScript understands "this is a mutable value storage":

```ts
const intervalRef = useRef<number | null>(null);
// typeof intervalRef → MutableRefObject<number | null>
// .current → number | null (WRITABLE — you can manually change this)

const renderCount = useRef(0);
// typeof renderCount → MutableRefObject<number>
```

Here you manually specify the type (`<number | null>`). `.current` is **writable** — `intervalRef.current = 5` works because React doesn't auto-assign it.

### Key Insight

| Initial value | Ref type | `.current` | Who assigns the value |
|---|---|---|---|
| `null` | DOM ref (RefObject) | Readonly | React automatically (DOM node) |
| Anything non-null | Mutable ref (MutableRefObject) | Writable | You manually |

```ts
const domRef = useRef<HTMLInputElement>(null);   // DOM ref — readonly .current
const valRef = useRef(0);                         // mutable ref — writable .current
const valRef2 = useRef<string>("hello");           // mutable ref — writable .current
```

## Step 4 — First Use Case: DOM Access (Input Autofocus)

Now that `useRef`'s mechanism is clear, let's see how to access DOM elements.

**Think:** Page loads, and we want the input field to automatically receive focus — cursor blinking inside, no clicks needed. That's the goal of this entire Step. We'll get there in two rounds:

1. First round — **Phases 1–5**: build the *button-focus* version. It teaches the whole mechanism on a button someone deliberately clicks: create the ref, connect it with `ref={...}`, and call `.focus()` on demand.
2. Second round — **Phase 6**: the same mechanism, wired to page load with `useEffect` — because the original goal never involved a button at all. The button was the teaching vehicle (we needed `.focus()` to exist in our hands first); page-load is the actual goal.

**Phase 1 — Static UI:** Just input + button, no ref:

```tsx
function AutoFocusInput() {
  return (
    <div>
      <input type="text" placeholder="Auto-focused..." />
      <button>Focus</button>
    </div>
  );
}
```

**Phase 2 — Create ref object with useRef:**

First import `useRef` and create a ref variable. `useRef<HTMLInputElement>(null)` means: "create a box that will hold a reference to an `<input>` element. Nothing there yet, so `null`."

`inputRef` is an object: `{ current: null }`. Just one property `current` that's currently null. Later, React fills it with the actual DOM element.

```tsx
import { useRef } from "react";

function AutoFocusInput() {
  const inputRef = useRef<HTMLInputElement>(null);
  console.log(inputRef); // { current: null } — DOM not built yet

  return (
    <div>
      <input type="text" placeholder="Auto-focused..." />
      <button>Focus</button>
    </div>
  );
}
```

`HTMLInputElement` is React's built-in type that represents an HTML `<input>` element. So TypeScript knows that `.current` will eventually be an `<input>` DOM node — or `null`.

**Phase 3 — Connect with `ref={inputRef}`:**

Now we tell React: "this `inputRef` object — put the `<input>` element's reference in it."

To do this, add the `ref={inputRef}` attribute to the `<input>` in JSX. This tells React:

> "When you create the `<input>` element in the actual DOM, put its reference into `inputRef.current`."

**What React does internally — simplified:**

```
Your JSX: <input ref={inputRef} />

React creates:
  → const domElement = document.createElement('input')
  → inputRef.current = domElement   ← React does this itself
```

React itself fills `inputRef.current` with the actual DOM element. You don't do anything.

```tsx
<input ref={inputRef} type="text" placeholder="Auto-focused..." />
```

Now `inputRef.current` is no longer null — it's the actual `<input>` DOM node (after render).

> The `ref` attribute only works on built-in HTML elements (`<input>`, `<div>`, `<video>`). It doesn't work on custom components — those need `forwardRef` (later).

**Phase 4 — Verify with console.log that ref works:**

Now we add an event handler. When the button is clicked, print `inputRef.current` to the console — to see if the `<input>` element really got stored in the ref.

First, create the handler function:

```tsx
const handleFocusClick = () => {
  console.log("Ref current value:", inputRef.current);
};
```

Then add `onClick` to the button:

```tsx
return (
  <div>
    <input ref={inputRef} type="text" placeholder="Auto-focused..." />
    <button onClick={handleFocusClick}>Focus</button>
  </div>
);
```

Full component code:

```tsx
function AutoFocusInput() {
  const inputRef = useRef<HTMLInputElement>(null);
  console.log("Before render:", inputRef.current); // null — DOM not built yet

  const handleFocusClick = () => {
    console.log("On click:", inputRef.current); // <input> element — DOM is ready
  };

  return (
    <div>
      <input ref={inputRef} type="text" placeholder="Auto-focused..." />
      <button onClick={handleFocusClick}>Focus</button>
    </div>
  );
}
```

Notice: at the top level of the component, `inputRef.current` is `null` because the component function is executing during render — the DOM hasn't been created yet. But after clicking the button — when the DOM is ready — `inputRef.current` shows the actual `<input>` DOM element.

**Verify:** Click the button → does the console print the `<input>` element? ✅

**Phase 5 — Actual logic: call `.focus()`:**

Every DOM element has built-in browser methods — `.focus()`, `.click()`, `.play()` (video). `.focus()` is a browser default method that moves the cursor into the input:

```tsx
const handleFocusClick = () => {
  inputRef.current?.focus();
};
```

`?.` (optional chaining) is used because if `inputRef.current` is null (e.g., element unmounted), `.focus()` won't be called and no error occurs.

**Phase 5 code — button version complete:**

```tsx
import { useRef } from "react";

function AutoFocusInput() {
  const inputRef = useRef<HTMLInputElement>(null);

  const handleFocusClick = () => {
    inputRef.current?.focus();
  };

  return (
    <div>
      <input ref={inputRef} type="text" placeholder="Auto-focused..." />
      <button onClick={handleFocusClick}>Focus</button>
    </div>
  );
}
```

**Verify:** Click the button → cursor starts blinking in the input field? ✅

**Phase 6 — Page-Load Autofocus (useEffect + `[]`):**

Now here is the thing nobody said out loud until now: everything above built a *button*, but the goal from the very first line of this Step was **page loads → input is already focused**. Nobody should have to find a "Focus" button just to start typing. The event handler was a teaching step — we needed to know that `.focus()` works and that the ref holds the DOM node by the time anyone interacts with it. Now we wire the same two facts to page load.

The difference is timing. A button calls `.focus()` *when something happens (a click)* — that's what event handlers are for. Page load isn't an event we handle — it's **after the render completes**. That's precisely what `useEffect` (from 2.1) exists for: code that runs automatically after React finishes rendering, with no user action involved.

| Situation | When it runs | Tool |
|---|---|---|
| Button version (Phases 4–5) | Only when the user clicks | Event handler containing `.focus()` |
| Page-load version (Phase 6) | Once, right after the first render | `useEffect` containing `.focus()` |

```tsx
import { useEffect, useRef } from "react";

function AutoFocusInput() {
  const inputRef = useRef<HTMLInputElement>(null);

  useEffect(() => {
    inputRef.current?.focus();
  }, []);

  return (
    <div>
      <input ref={inputRef} type="text" placeholder="Auto-focused..." />
    </div>
  );
}
```

Line by line:

- `import { useEffect, useRef } from "react";` — two hooks now: `useRef` for the element, `useEffect` for "run something after render".
- `useEffect(() => { ... }, [])` — the `[]` (empty dependency array) means "run this once, right after the first ever render — and never again". Same shape as the categories fetch from 2.7 and the mount-fetch pattern from 2.2.
- **Why this works when the plain render couldn't do it:** inside `useEffect`, React has *already finished* building the DOM. So `inputRef.current` is the actual `<input>` element by the time `.focus()` is called — not `null`. The button version only needed user cooperation; the effect version needs nothing at all except a render that already happened.
- **The button is gone on purpose.** If you want both — autofocus on load *and* a button that re-focuses on demand — keep the button too. The effect does its job at mount; the handler does its job on clicks. Nothing about them conflicts.

**Verify:** Hard reload the page — cursor already blinking inside the input, no click needed? ✅

> **Nutshell:** To access a DOM element: (1) create `const elRef = useRef<HTMLInputElement>(null)`, (2) add `<input ref={elRef} />` — React automatically fills `.current` with the DOM node after render, (3) call `elRef.current?.focus()` — from an event handler (at the user's request) or from `useEffect(() => { ... }, [])` (at page load). Event handler = *user* triggers it; `useEffect` with `[]` = *render* triggers it.

## Step 5 — Second Use Case: Mutable Value (Stopwatch)

**Think:** Stopwatch — Start button, `setInterval` ticks every second incrementing the seconds. Stop button, interval cleared. Reset button, seconds back to 0.

Three things needed: `seconds` (shown on screen), `isRunning` (to enable/disable buttons). But the **interval ID** — shouldn't be shown on screen, only needed to call `clearInterval`. So not state, but **store in a ref**.

**Phase 1 — Static UI:**

```tsx
function Stopwatch() {
  return (
    <div>
      <h1>⏱️ Stopwatch: 0s</h1>
      <button>Start</button>
      <button disabled>Stop</button>
      <button>Reset</button>
    </div>
  );
}
```

**Phase 2 — Add State (seconds + isRunning):**

```tsx
const [seconds, setSeconds] = useState(0);
const [isRunning, setIsRunning] = useState(false);
```

`seconds` will be displayed on screen — that's why it's state. `isRunning` enables/disables buttons — that's why it's state.

**Phase 3 — Ref for interval ID:**

```tsx
const intervalRef = useRef<ReturnType<typeof setInterval> | null>(null);
```

`ReturnType<typeof setInterval>` — TypeScript utility that extracts `setInterval`'s return type (`number` in browser TypeScript).

Interval ID is only needed for cleanup — not for display. If stored in state, `setTimerId(id)` → state change → unnecessary re-render. Ref is perfect here.

**Phase 4 — Handlers:**

```tsx
const handleStart = () => {
  setIsRunning(true);
  intervalRef.current = setInterval(() => {
    setSeconds((prev) => prev + 1);
  }, 1000);
};

const handleStop = () => {
  setIsRunning(false);
  if (intervalRef.current) {
    clearInterval(intervalRef.current);
    intervalRef.current = null;
  }
};

const handleReset = () => {
  setSeconds(0);
  setIsRunning(false);
  if (intervalRef.current) {
    clearInterval(intervalRef.current);
    intervalRef.current = null;
  }
};
```

**Phase 5 — Bind UI:**

```tsx
return (
  <div>
    <h1>⏱️ Stopwatch: {seconds}s</h1>
    <button onClick={handleStart} disabled={isRunning}>Start</button>
    <button onClick={handleStop} disabled={!isRunning}>Stop</button>
    <button onClick={handleReset}>Reset</button>
  </div>
);
```

**Full code:**

```tsx
import { useState, useRef } from "react";

function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  const [isRunning, setIsRunning] = useState(false);
  const intervalRef = useRef<ReturnType<typeof setInterval> | null>(null);

  const handleStart = () => {
    setIsRunning(true);
    intervalRef.current = setInterval(() => {
      setSeconds((prev) => prev + 1);
    }, 1000);
  };

  const handleStop = () => {
    setIsRunning(false);
    if (intervalRef.current) {
      clearInterval(intervalRef.current);
      intervalRef.current = null;
    }
  };

  const handleReset = () => {
    setSeconds(0);
    setIsRunning(false);
    if (intervalRef.current) {
      clearInterval(intervalRef.current);
      intervalRef.current = null;
    }
  };

  return (
    <div>
      <h1>⏱️ Stopwatch: {seconds}s</h1>
      <button onClick={handleStart} disabled={isRunning}>Start</button>
      <button onClick={handleStop} disabled={!isRunning}>Stop</button>
      <button onClick={handleReset}>Reset</button>
    </div>
  );
}
```

**Verify:** Start → seconds increasing? Stop → stops? Reset → 0? ✅

> **Nutshell:** Use `useRef` for mutable values that don't need to be on screen — just "background bookkeeping" (timer ID, interval handle, previous value). Use `useState` when the value changing should update the UI.

## Step 6 — Bonus: Previous Value Pattern

**Think:** Count is displayed on screen (`useState`). Now we want to show "Previous: X → Current: Y". We need to store the previous count too — but if that's in `useState`, the previous value changing triggers a re-render. Store in a ref instead — no extra render.

```tsx
import { useState, useRef } from "react";

function PrevValueDemo() {
  const [count, setCount] = useState(0);
  const prevCount = useRef(0);

  const handleClick = () => {
    prevCount.current = count;    // current value becomes the previous
    setCount(count + 1);          // new count
  };

  return (
    <div>
      <p>Previous: {prevCount.current} → Current: {count}</p>
      <button onClick={handleClick}>Increment</button>
    </div>
  );
}
```

**Why `{prevCount.current}` is OK here:** the assignment order is deliberate — `prevCount.current = count` runs **before** `setCount(count + 1)`. By the time React re-renders, the ref already holds the pre-increment value, so the JSX read is fresh. This ordering is the sanctioned way to use the "previous value" pattern — if the ref were updated *after* the state change (or during the render), the screen would lag behind by a render. And as a blanket rule: still don't read refs in JSX anywhere else.

**Verify:** Click the button. "Previous: 0 → Current: 1", then "Previous: 1 → Current: 2"... ✅

**What's happening?**
- State change (`setCount`) → re-render
- Ref change (`prevCount.current = count`) → **no re-render**
- Previous value is only "remembered" — the UI displays it when the state-triggered re-render happens

> **Nutshell:** Previous value pattern — store the current value in a ref **before** updating state. The ref persists, doesn't trigger re-render. The screen displays the previous value when the state change causes a re-render. This is a real practical use case for `useRef`.

## What It Is NOT

- **Not a replacement for `useState`** — Values that need to be on screen should use `useState`. `useRef` can't update the UI because it doesn't trigger re-renders.
- **Not a DOM manipulation tool** — `useRef` just gives a "reference" to a DOM element. Actual manipulation (focus, play, scroll) is done with normal browser JS APIs.
- **Not global** — A ref is specific to a component instance. Another component can't access your ref without prop drilling or context.

---

## Common Mistakes

1. **Reading `ref.current` during render** (before JSX returns in the top-level) — you'll get `null` because the DOM isn't built yet. Always read it in event handlers or `useEffect`.
2. **Using `useRef` for UI-updating values** — If the value needs to be on screen, use `useState`. `useRef` won't update the UI.
3. **Calling `.current?.focus()` without optional chaining** — If the element is conditionally rendered (e.g. `{show && <input ref={inputRef} />}`) and `show` is false, `inputRef.current` is null — calling `.focus()` throws an error. Always use `?.`.
4. **Forgetting the `null` initial value** — `useRef<HTMLInputElement>()` (without initial value) causes a TypeScript error. Always write `useRef<Type>(null)`.
5. **Expecting autofocus from the button-style code** — a handler only runs when the user clicks. Page-load focus belongs in `useEffect(() => { inputRef.current?.focus(); }, [])` — the effect runs after the DOM is built and the ref is populated.


| Return type | `{ current: initialValue }` | `[value, setValue]` |
| Re-render on change | ❌ No | ✅ Yes |
| Persists across renders | ✅ Yes | ✅ Yes |
| DOM access | ✅ via `ref` attribute | ❌ Possible via ref callback but wasteful |
| Best for | Background values, DOM refs | UI-visible state |
