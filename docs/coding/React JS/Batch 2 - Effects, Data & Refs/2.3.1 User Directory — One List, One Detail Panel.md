## Goal

We'll build a **User Directory** — a list of users on the left, and a detail panel on the right. Click a user in the list, the panel shows their full profile (photo, email, company).

You already know everything needed: `useQuery`, `queryKey`, `queryFn`, `enabled`, `isLoading`, `isFetching` — all from **2.3 TanStack React Query**. This app is only about seeing those same tools work on a *different* API with a *different* shape of screen. Same pattern, new world.

**The new skill:** two `useQuery` calls in the same component, on two different keys — the *list* and the *detail*. The list fetches once. The detail fetches only when a user is selected. Clicking the same user again? No request at all — it comes from the cache.

We'll use the public **DummyJSON** API — 208 fake-but-real users, no key needed:

```text
GET https://dummyjson.com/users?limit=10        → { users: [...], total: 208, skip: 0, limit: 10 }
GET https://dummyjson.com/users/1               → { id: 1, firstName: "Emily", ... }
```

Same project setup as 2.3: a fresh Vite + TypeScript project called `user-directory` (`bun create vite user-directory --template react-ts`), `bun add @tanstack/react-query`, and `main.tsx` with `<QueryClientProvider>` already wired (recap the exact setup from 2.3 Step 3 if your `main.tsx` doesn't look like that).

## Step 2 — Hardcoded List (State Plumbing Before Server Data)

**Think:** Before we fetch anything, prove the *click* works with data we control. Hardcode 3 users, map over them, and on click log the id to the console.

```tsx
import { useState } from "react";

const hardcodedUsers = [
  { id: 1, firstName: "Emily", lastName: "Johnson" },
  { id: 2, firstName: "Michael", lastName: "Williams" },
  { id: 3, firstName: "Sophia", lastName: "Brown" },
];

function UserDirectory() {
  const [selectedId, setSelectedId] = useState<number | null>(null);

  return (
    <div>
      <h1>User Directory</h1>
      <div className="directory">
        <div className="list">
          <h2>Users</h2>
          <ul>
            {hardcodedUsers.map((user) => (
              <li key={user.id}>
                <button onClick={() => setSelectedId(user.id)}>
                  {user.firstName} {user.lastName}
                </button>
              </li>
            ))}
          </ul>
        </div>
        <div className="detail">
          <h2>Details</h2>
          <p>Selected id: {selectedId ?? "none yet"}</p>
        </div>
      </div>
    </div>
  );
}
```

Line by line, what's happening:

- `useState<number | null>(null)` — `selectedId` starts as `null` because at first nobody has been selected. Type is `number | null` — TS knows it can be a real id or the empty state.
- `{hardcodedUsers.map(...)}` — the familiar list render: one `<li>` per user. The `key` is `user.id`.
- `<button onClick={() => setSelectedId(user.id)}>` — clicking a name writes that user's id into state.
- `selectedId ?? "none yet"` — nullish coalescing: show `"none yet"` while nothing is selected.

**Test:** Click "Emily Johnson" → console shows the detail panel text change to "Selected id: 1". Click "Michael Williams" → "Selected id: 2". ✅

## Step 3 — List from the Server (`useQuery` for the List)

**Think:** Hardcoded data is a stepping stone. Now replace it with the real thing — DummyJSON's user list. This is the *exact* 2.3 pattern; the only thing that changed is the URL and the shape of the response.

```tsx
import { useState } from "react";
import { useQuery } from "@tanstack/react-query";

interface DummyUser {
  id: number;
  firstName: string;
  lastName: string;
  email: string;
  username: string;
  image: string;
}

function UserDirectory() {
  const [selectedId, setSelectedId] = useState<number | null>(null);

  const { data, isLoading, isError, error } = useQuery({
    queryKey: ["users"],
    queryFn: async () => {
      const res = await fetch("https://dummyjson.com/users?limit=10");
      const json = await res.json();
      return json.users as DummyUser[];
    },
  });

  if (isLoading) return <p>Loading users...</p>;
  if (isError) return <p>Error: {error.message}</p>;

  return (
    <div>
      <h1>User Directory</h1>
      <div className="directory">
        <div className="list">
          <h2>Users</h2>
          <ul>
            {data.map((user) => (
              <li key={user.id}>
                <button onClick={() => setSelectedId(user.id)}>
                  {user.firstName} {user.lastName}
                </button>
              </li>
            ))}
          </ul>
        </div>
        <div className="detail">
          <h2>Details</h2>
          <p>Selected id: {selectedId ?? "none yet"}</p>
        </div>
      </div>
    </div>
  );
}
```

What's new compared to 2.3, line by line:

- `interface DummyUser` — TypeScript describing one user. We only type the fields we actually show. The API sends a lot more (company, address, bank...), but unused fields don't matter for now.
- `queryFn` does the fetch and then plucks `.users` out of the response (`{ users, total, skip, limit }`). The raw JSON has that wrapper — components shouldn't deal with it, so the function returns just the array.
- `queryKey: ["users"]` — the literal first position is the notebook's name here. No second position because this query doesn't depend on anything changing — one list, one key, always the same.
- The early returns (`isLoading` / `isError`) come *before* the main JSX — no `if` spaghetti inside JSX.

**Test:** Page loads → real names from DummyJSON appear in the list. Click any name → detail panel still says "Selected id: N". Check the Network tab — exactly one request to `dummyjson.com/users?limit=10`. ✅

## Step 4 — Detail Panel (Second `useQuery`, Different Key)

**Think:** The list is live now. The detail panel needs its own data — full profile of the selected user, from `/users/:id`. Here's the heart of this project: **add a second `useQuery`, with a key that includes the id.**

```tsx
import { useState } from "react";
import { useQuery } from "@tanstack/react-query";

interface DummyUser {
  id: number;
  firstName: string;
  lastName: string;
  email: string;
  username: string;
  image: string;
  phone: string;
  company: { name: string; title: string; department: string };
}

function UserDirectory() {
  const [selectedId, setSelectedId] = useState<number | null>(null);

  const listQuery = useQuery({
    queryKey: ["users"],
    queryFn: async () => {
      const res = await fetch("https://dummyjson.com/users?limit=10");
      const json = await res.json();
      return json.users as DummyUser[];
    },
  });

  const detailQuery = useQuery({
    queryKey: ["users", selectedId],
    queryFn: async () => {
      const res = await fetch(`https://dummyjson.com/users/${selectedId}`);
      if (!res.ok) throw new Error("User not found");
      return res.json() as Promise<DummyUser>;
    },
    enabled: selectedId !== null,
  });

  if (listQuery.isLoading) return <p>Loading users...</p>;
  if (listQuery.isError) return <p>Error: {listQuery.error.message}</p>;

  return (
    <div>
      <h1>User Directory</h1>
      <div className="directory">
        <div className="list">
          <h2>Users</h2>
          <ul>
            {listQuery.data.map((user) => (
              <li key={user.id}>
                <button onClick={() => setSelectedId(user.id)}>
                  {user.firstName} {user.lastName}
                </button>
              </li>
            ))}
          </ul>
        </div>
        <div className="detail">
          {detailQuery.isLoading && <p>Loading details...</p>}
          {detailQuery.isFetching && !detailQuery.isLoading && (
            <p>Refreshing...</p>
          )}
          {detailQuery.isError && <p>Couldn't load that user.</p>}
          {detailQuery.data && (
            <div>
              <img src={detailQuery.data.image} alt={detailQuery.data.username} width={96} height={96} />
              <h2>{detailQuery.data.firstName} {detailQuery.data.lastName}</h2>
              <p>Email: {detailQuery.data.email}</p>
              <p>Phone: {detailQuery.data.phone}</p>
              <p>Company: {detailQuery.data.company.name}</p>
              <p>Role: {detailQuery.data.company.title} ({detailQuery.data.company.department})</p>
            </div>
          )}
          {!selectedId && <p>Select a user to see details</p>}
        </div>
      </div>
    </div>
  );
}
```

Line by line:

- `queryKey: ["users", selectedId]` — the same notebook (`"users"`), a different second position per selection: `["users", 1]`, `["users", 2]`, ... The fingerprint rule does the work: each id has its own key, so each user's detail gets fetched only once ever.
- `enabled: selectedId !== null` — this is why the project works with *no* detail selected: before any click, `selectedId` is `null`, `enabled` is `false`, and no fetch fires. If we forgot this, the first render would fetch `/users/null`.
- `listQuery` / `detailQuery` — naming the two `useQuery` calls differently. Two queries, same component — totally legal. They are independent: one fails, the other doesn't care.
- `detailQuery.isLoading` — true only the first time a *given* user is ever fetched (nothing in cache). `isFetching` — true whenever any request is running, including background refetches. That's why the detail panel shows "Loading details..." only once per user, and "Refreshing..." only if a background refetch happens.

**Test:**

1. Open the app → list of names from the Network tab (`/users?limit=10`). No detail request yet. ✅
2. Open DevTools Network tab. Click "Emily" → one request to `/users/1`. Click "Michael" → one request to `/users/2`. ✅
3. Click "Emily" again → **no request at all.** The Network tab stays quiet. That's the cache doing its job — same key `["users", 1]`, straight from the notebook. ✅
4. Reload the page (hard refresh) → click "Emily" → request fires again (cache clears on refresh — memory, not disk).

## What You Just Learned — Two Queries, Two Jobs

Notice the pattern: **one `useQuery` per data need, keyed by what that data depends on.** The list doesn't depend on the click; the detail does. So they are two queries with two different keys — not one mega-fetch that grabs everything, not a single key reused for both.

This is the most common real-world React Query layout: a "grid page" with a "detail panel". E-commerce product pages, admin dashboards, chat windows — all this shape.

## Common Mistakes

1. **Forgetting `enabled` on the detail query** — first render fetches `/users/null`. The `enabled` guard is what keeps "nothing selected" from being an API call.
2. **Using one shared key for list and detail** (e.g. both `["users"]`) — now clicking a user would *replace* the list?! No — worse, two queries share one cache entry and React Query would treat them as the same query. Separate keys, separate entries.
3. **Fetching all 208 users up front** (`/users` without limit) — slow and pointless; we show 10. Fetch what you render.
4. **Storing the whole user object in `useState` for the detail panel** — the server owns the data; `useState` holding a stale copy is the exact anti-pattern 2.2 taught against. `useQuery` keeps it fresh by itself.
5. **`isLoading` spam on the detail panel** — showing "Loading..." for cached users confuses the user. `isLoading` is first-ever fetch per key; use `isFetching && !isLoading` for the "refresh in the background" case.

## What It Is NOT

- **NOT client-side state.** The server owns the user data; we only hold authorized views of it. `selectedId` (*which* user) is client state; the user records themselves are server state.
- **NOT one query with extra params.** This is two independent queries on two keys — don't squeeze them into one key like `["users", selectedId, "all"]`.
- **NOT a need to pick between `useEffect` and `useQuery` here.** There is no `useEffect` in this project at all — that's the 2.2 story, already behind us.
- **NOT safe to treat DummyJSON as production auth or data.** It's a practice API — fake users, no auth, no rate limits worth building on.

## In Your Own Words

1. Why does the list live in one query and the detail in another?

<details>
<summary>Sample Answer</summary>

Because they depend on different things. The list does not depend on any click — it's the same for everyone, so one key (`["users"]`) is enough. The detail depends on which user is selected, so its key has to carry the id (`["users", id]`). One key can't express both — and one query can't be in two states at once.
</details>

2. What would happen without `enabled: selectedId !== null`?

<details>
<summary>Sample Answer</summary>

The detail query would fire on the very first render, with `selectedId` being `null`, making a request to `/users/null`. That's a broken API call we'd have to handle, purely because React renders once before any click. `enabled` is the gate — fetch only when there's a real id to fetch.
</details>

3. You click user 1, then user 2, then user 1 again. How many network requests happen in total? Why?

<details>
<summary>Sample Answer</summary>

Two requests: `/users/1`, then `/users/2`, and nothing on the second visit to user 1. The second click of the SAME user hits the cache — same key `["users", 1]` — so React Query returns the stored copy without a network request. That's the whole point of keying by id.
</details>

4. What's the difference between `isLoading` and `isFetching` on the detail panel?

<details>
<summary>Sample Answer</summary>

`isLoading` is true only the first time a user is ever requested — nothing cached yet, request running. `isFetching` is true every time any request is running, including background refetches. So a cached user shows `isFetching: true, isLoading: false` during a refetch — show "Refreshing...", not "Loading...".
</details>

5. If you wanted the list to also re-sort when the user clicks a column header, would you put the sort order in the queryKey? Why or why not?

<details>
<summary>Sample Answer</summary>

No — the sort can happen on the client, on data that's already here. Query keys are for things that must go back to the **server**. Sorting 10 items doesn't need the server, so it stays a `useState` + `Array.prototype.sort`. QueryKey is for server-relevant differences only (`["users", page]` later, `["users", id]` here).
</details>
