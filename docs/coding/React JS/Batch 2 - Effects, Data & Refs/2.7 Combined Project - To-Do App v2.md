In 2.6, we learned Context API — Theme Switcher, `useTheme()` with its guard. In 2.5.0, Lifting State Up. In 2.4 useRef. Now we use all of them — upgrading the Batch 1 To-Do app to v2.

|---|---|---|

## Step 1 — The Client Brief

Before touching code, imagine a client walks in and asks you to build them a task manager. This is what they tell you:

> "I want a to-do list. I should be able to type a task and press Add. The task shows up in the list. I can check it off as done. Strikethrough the done ones. I want to delete tasks — maybe a ✕ button next to each one. I also want to filter — show All, only Active, only Completed.
>
> And I want a dark mode toggle — invert the colors of EVERYTHING, all of it should look and feel like a dark app. Not just the background."

Break it into actual requirements:

1. **Add a task** — type text, click Add, task lands in the list
2. **See all tasks** — a list, each row shows: the text, a checkbox, a delete button
3. **Toggle done / not done** — click the checkbox, task strikes through
4. **Delete a task** — click ✕ next to a row, row disappears
5. **Filter** — a row of buttons: All / Active / Completed — pick one, list updates
6. **Show stats** — how many done, how many remaining, total
7. **Dark / light toggle** — one button flips the **entire app** — text, borders, buttons, background, inputs, everything

Now — step 2 is the data model. Derived from this exact brief. Nothing invented.

## Step 5 — Build the Theme Switcher

Thread theme across the entire tree from day 1. Everything after this inherits the invert for free.

And this `ThemeContext.tsx` is nothing new — it's the finished version of the file 2.6 grew step-by-step: the container (Step 2 there), the `useTheme()` hook (Step 5 there), the `ThemeProvider` component (Step 6 there) — all three together in one file. Read it once from top to bottom; you've already built every piece of it.

**`src/context/ThemeContext.tsx`**

```tsx
import { useState, createContext, useContext, type ReactNode } from "react";

type Theme = "light" | "dark";
interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be inside ThemeProvider");
  return ctx;
}

export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");
  const toggleTheme = () => setTheme((prev) => (prev === "light" ? "dark" : "light"));
  return <ThemeContext value={{ theme, toggleTheme }}>{children}</ThemeContext>;
}
```

**`src/components/ThemeToggle.tsx`**

```tsx
import { useTheme } from "../context/ThemeContext";

export default function ThemeToggle() {
  const { theme, toggleTheme } = useTheme();
  return (
    <button
      onClick={toggleTheme}
      style={{
        background: theme === "dark" ? "#fff" : "#000",
        color: theme === "dark" ? "#000" : "#fff",
        padding: "6px 14px",
        borderRadius: "4px",
        border: "none",
        cursor: "pointer",
        fontSize: "14px",
      }}
    >
      {theme === "light" ? "🌙 Dark" : "☀️ Light"}
    </button>
  );
}
```

**`src/App.tsx`** — now the shell:

```tsx
import { ThemeProvider } from "./context/ThemeContext";
import ThemeToggle from "./components/ThemeToggle";

export default function App() {
  return (
    <ThemeProvider>
      <div style={{ padding: "20px" }}>
        <h1>📋 To-Do App v2</h1>
        <ThemeToggle />
      </div>
    </ThemeProvider>
  );
}
```

**How the value gets to ThemeToggle — one look at the climb:**

App wrote `<ThemeToggle />` between `<ThemeProvider>` and `</ThemeProvider>` — so it lands below the provider in the rendered tree. ThemeProvider's output IS the wrap: `<ThemeContext value={{ theme, toggleTheme }}>{children}</ThemeContext>`. When ThemeToggle calls `useTheme()` → `useContext(ThemeContext)`, React walks up from ThemeToggle, one parent at a time: div → `<ThemeContext value=...>` — stop. The exact object the provider attached at `value=` is what comes out.

```
<ThemeProvider>                        ← a component — NOT the stop (no value on it)
  └── <ThemeContext value={{...}}>      ← the stop — value attached at this tree position
        └── <div>                       ← children — App's JSX written between the tags
              <ThemeToggle />            ← climb starts here
```

**Checkpoint:** save → **🌙 Dark** button appears top-right. Click → button visually flips; the page is still white (we'll wire that next). ✅

## Step 6 — Make the Page Flip to Dark and Back

Now App.tsx reads `theme` and flips its own colors — and the ThemeToggle actually matters.

```tsx
import { ThemeProvider, useTheme } from "./context/ThemeContext";
import ThemeToggle from "./components/ThemeToggle";

function ToDo() {
  const { theme } = useTheme();
  return (
    <div
      style={{
        padding: "20px",
        maxWidth: "600px",
        margin: "0 auto",
        minHeight: "100vh",
        background: theme === "dark" ? "#1a1a2e" : "#fff",
        color: theme === "dark" ? "#fff" : "#000",
        transition: "all 0.3s",
      }}
    >
      <h1>📋 To-Do App v2</h1>
      <ThemeToggle />
    </div>
  );
}

export default function App() {
  return <ThemeProvider><ToDo /></ThemeProvider>;
}
```

**Wait — why did App split into two components, `App` and `ToDo`?**

`App` now has ONE job: wrap everything in `<ThemeProvider>`. No state, no theme reading — the wrapper stays clean. `ToDo` is the real page component, defined in the same `App.tsx` file, and it sits INSIDE the wrap — which is exactly why it's allowed to call `useTheme()` (2.6 Step 4's rule: only components below the provider can read the value).

From here on, `ToDo` is the page: TaskInput, TaskItem, FilterBar, TaskStats all get composed inside it, and the task list state will live in it too. So when a later step says "state in ToDo" — that means this page component inside `App.tsx`, not App itself.

**Checkpoint:** toggle Dark — full app background flips navy, text white. Toggle Light — back to white. ThemeToggle works AND the page shell already inverts. ✅

## Step 7 — Build the Add Box (TaskInput)

Every component reads `useTheme()` and themes itself. No exemptions.

**`src/components/TaskInput.tsx`**

```tsx
import { useState, useRef, useEffect } from "react";
import { useTheme } from "../context/ThemeContext";

export default function TaskInput({ onAdd }: { onAdd: (text: string) => void }) {
  const [text, setText] = useState("");
  const inputRef = useRef<HTMLInputElement>(null);
  const { theme } = useTheme();

  useEffect(() => { inputRef.current?.focus(); }, []);

  const handleClick = () => {
    if (text.trim() === "") return;
    onAdd(text.trim());
    setText("");
    inputRef.current?.focus();
  };

  return (
    <div style={{ display: "flex", gap: "8px", marginTop: "16px" }}>
      <input
        ref={inputRef}
        value={text}
        onChange={(e) => setText(e.target.value)}
        placeholder="Add a task..."
        style={{
          flex: 1,
          padding: "10px 14px",
          fontSize: "16px",
          borderRadius: "6px",
          border: theme === "dark" ? "1px solid #444" : "1px solid #ddd",
          background: theme === "dark" ? "#2a2a40" : "#fff",
          color: theme === "dark" ? "#fff" : "#000",
          outline: "none",
        }}
      />
      <button
        onClick={handleClick}
        style={{
          padding: "10px 20px",
          borderRadius: "6px",
          border: "none",
          background: theme === "dark" ? "#5a5af0" : "#4f46e5",
          color: "#fff",
          cursor: "pointer",
        }}
      >
        Add
      </button>
    </div>
  );
}
```

### Phase 2 — Pill styling (still static)

**Now style them.** The three buttons get the same look — padding, rounded corners, same colors. Only ONE thing differs — the selected button looks filled, the other two look outlined.

Writing the style object 3 times by hand — twice identical, once different — means copying the same CSS 3 times.

Instead: write the styles ONCE, as a function. The function takes one input — `true` or `false` (selected or not) — and hands back the matching styles:

```tsx
// what the function does (full code below):
pill(true)    // → styles for the SELECTED look (filled)
pill(false)   // → styles for the NOT-selected look (outlined)

// using it on the buttons:
<button style={pill(true)}>all</button>
<button style={pill(false)}>active</button>
```

That's all `pill` is — a plain function that answers "selected or not?" with a ready-made style object. No new React concept here — just a function that returns an object:

```tsx
import type { CSSProperties } from "react";
import { useTheme } from "../context/ThemeContext";

export default function FilterBar() {
  const { theme } = useTheme();

  const pill = (active: boolean): CSSProperties => ({
    padding: "8px 16px",
    borderRadius: "20px",
    border: active
      ? (theme === "dark" ? "1px solid #5a5af0" : "1px solid #4f46e5")
      : `1px solid ${theme === "dark" ? "#444" : "#ddd"}`,
    background: active ? (theme === "dark" ? "#5a5af0" : "#4f46e5") : "transparent",
    color: active ? "#fff" : (theme === "dark" ? "#ccc" : "#333"),
    cursor: "pointer",
  });

  return (
    <div style={{ display: "flex", gap: "8px", marginTop: "16px" }}>
      <button style={pill(true)}>all</button>
      <button style={pill(false)}>active</button>
      <button style={pill(false)}>completed</button>
    </div>
  );
}
```

**Line by line:**

- `const pill = (active: boolean): CSSProperties => ({ ... })` — a function, NOT a component. One boolean in, one style object out. `CSSProperties` is React's type for inline style objects
- Every line inside asks the same two yes/no questions in a row: Q1 — am I the selected pill? Q2 — is the app dark? Take `background` and read it as plain if/else: *not active → `transparent`; else if dark → `#5a5af0`; else → `#4f46e5`.* Same pattern for `border` and `color`
- `pill(true)` on the first button is **hardcoded for now** — just to SEE the filled look. Phase 3 makes it real
- `useTheme()` — the same theme from the same provider every other component reads (Step 5)

**Checkpoint:** save → the **all** pill renders filled (white text), the other two outlined. Toggle the theme — pill colors flip with the app. ✅

### Phase 3 — Props: the parent decides which pill is active

The hardcoded `pill(true)` is fake. The PARENT should decide which filter is selected — that's how everything works so far: state lives in the `ToDo` component (in `App.tsx`), children display it.

**In `App.tsx`, inside the `ToDo` component, next to `tasks` — one more state:**

```tsx
const [filter, setFilter] = useState<FilterStatus>("all");
```

- `FilterStatus` — the union from `types.ts` (Step 8): only `"all" | "active" | "completed"` are possible, a typo is a compile error
- `"all"` default — first render shows everything
- This is a second state in the `ToDo` component (App.tsx). Filter clicks will change THIS one — `tasks` stays untouched

**In FilterBar — same file as Phase 2, three changes:**

```tsx
import type { CSSProperties } from "react";
import type { FilterStatus } from "../types";
import { useTheme } from "../context/ThemeContext";

export default function FilterBar({ current }: { current: FilterStatus }) {
```

```tsx
      {(["all", "active", "completed"] as FilterStatus[]).map((f) => (
        <button key={f} style={pill(f === current)}>{f}</button>
      ))}
```

(pill helper unchanged from Phase 2)

**What changed:**

- `{ current }: { current: FilterStatus }` — data DOWN: the parent tells the child which filter is selected. The child only displays it
- The three handwritten buttons become ONE `.map` over the names:
  - `(["all", "active", "completed"] as FilterStatus[])` — the three valid values; the union type forces TS to allow only valid filters in the array
  - `key={f}` — same list rule as the task rows in Step 9
  - `style={pill(f === current)}` — for EACH button asks: "is THIS one the selected filter?" With `filter === "all"` in App.tsx, the "all" button gets `pill(true)` and the other two get `pill(false)`. The highlighting is now driven by state, not hardcoded

**Wire it:** `<FilterBar current={filter} />` in `App.tsx`, inside ToDo's return.

**Checkpoint:** save → looks identical to Phase 2 ("all" filled) — but now it's state-driven. Prove it: change the default to `useState<FilterStatus>("active")` → the **active** pill fills instead. Set it back to `"all"`. ✅

### Phase 4 — Clicks: report up, derive the list

Two ends to connect: the click data travels UP, the new list is computed DOWN. Both route through one place — the `ToDo` component in `App.tsx` — because that's where the state lives.

**UP — the callback.** FilterBar gets a second prop, and each button reports its own click:

```tsx
export default function FilterBar({ current, onChange }: { current: FilterStatus; onChange: (f: FilterStatus) => void }) {
```

```tsx
        <button key={f} onClick={() => onChange(f)} style={pill(f === current)}>{f}</button>
```

- `onChange` — a function prop, same callback-up pattern as `onAdd` (Step 7) and `onToggle`/`onDelete` (Step 8). Clicking a button calls it with THAT button's name
- The child never sets filter state itself — it doesn't own it. It reports; the parent decides

**DOWN — the derived list.** In `App.tsx`, inside the `ToDo` component:

```tsx
const filteredTasks = tasks.filter((t) => {
  if (filter === "active") return !t.completed;    // keep not-done
  if (filter === "completed") return t.completed;  // keep done
  return true;                                     // "all" — keep everything
});
```

- `filteredTasks` is derived data: a NEW array recomputed on every render from `tasks` + `filter`
- `tasks` itself is never modified — that's why switching back to "all" brings every row back

**Two render changes in `App.tsx`, inside ToDo's return:**

```tsx
{filteredTasks.map((task) => (<TaskItem key={task.id} ... />))}
<FilterBar current={filter} onChange={setFilter} />
```

- `tasks.map(...)` → **replaced by** `filteredTasks.map(...)` — rows now render from the derived list
- `onChange={setFilter}` — passing setState directly works because `setFilter` already has the exact shape the prop wants: `(f: FilterStatus) => void`. Writing `onChange={(f) => setFilter(f)}` would be the same thing

**The full loop:**

```
click "active" → onChange("active") → setFilter("active")
→ ToDo (in App.tsx) re-renders with filter === "active"
→ filteredTasks recomputed = only not-done rows
→ rows update + "active" pill renders filled (current changed too)
```

**Checkpoint:** click **active** — only pending rows show, the **active** pill is filled with white text. Click **completed** — only done rows. Click **all** — everything back. Flip the theme mid-way — pills still theme correctly. ✅

2. Persist tasks to `localStorage` with `useEffect`.

   <details>
   <summary>Sample Answer</summary>

   In `App.tsx`, inside the `ToDo` component: `useEffect(() => { localStorage.setItem("tasks", JSON.stringify(tasks)); }, [tasks]);` saves on every change, and lazy-init loads on first render: `useState<Task[]>(() => JSON.parse(localStorage.getItem("tasks") ?? "[]"))`. Every tasks change gets saved; the next visit loads what was saved last time.
   </details>

3. Trace it — inside `TaskStats`, what does `useTheme()` return, and where exactly does that object come from?

   <details>
   <summary>Sample Answer</summary>

   It returns the same object `ThemeProvider` attached with `value={{ theme, toggleTheme }}` — `TaskStats` pulls out `{ theme }`. The where: when `TaskStats` calls `useTheme()` → `useContext(ThemeContext)`, React walks up from `TaskStats`, one parent at a time, until it hits the first `ThemeContext` with a value — ThemeProvider's rendered output — and hands back that object. Every component below the provider gets the same value because they all import the same container object. Note that `total`/`completed`/`remaining` still arrive as normal props — context only carries theme.
   </details>

4. When you click the **active** filter button, what happens to `tasks` — and what exactly is `filteredTasks`?

   <details>
   <summary>Sample Answer</summary>

   Nothing happens to `tasks` — filtering never touches it. What changes is `filter` (the second state, via `setFilter`). `filteredTasks` is not a second state — it's derived data: a NEW array recomputed on every render from `tasks` + `filter`, because `.filter()` returns a new array and leaves the original alone. That's why clicking **all** brings every row back — the original list was never modified.
   </details>
