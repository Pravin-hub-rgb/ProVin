# Doc 2.3 — TanStack React Query

## Abhi Tak Kya Hua

2.2 mein **Recipe Finder** banaya — `useEffect + fetch` se API call, manually 4 states manage kiye (`searchInput`, `recipes`, `isLoading`, `error`), try/catch, cleanup. Kaam toh ho gaya, lekin har naye API feature ke liye wahi pattern repeat karna padega — boilerplate bahut hai.

Ab ek library seekhenge jo yeh sab automatically handle karti hai.

---

## Broader Goal

**Wahi Recipe Finder** banayenge — same input, same button, same MealDB API. Lekin **TanStack React Query** ke saath. 4 useState + try/catch + cleanup ki jagah sirf **1 hook (`useQuery`)** — aur loading/error/caching/retry sab auto.

**SOCH:** Ab fetch function. Ek async function jo URL ko fetch kare, response check kare, JSON parse kare, aur `Recipe[]` return kare. Agar `meals: null` aaye (invalid search), toh empty array return kare.

```ts
async function fetchRecipes(query: string): Promise<Recipe[]> {

}
```

`res.ok` — HTTP status 200-299 range mein hai kya. `?? []` — null aaya toh empty array.

## Step 3 — useQuery: Ab 4 useState Ki Zaroorat Nahi

**SOCH:** 2.2 mein har API call ke liye 4 states manually manage kiye — `recipes`, `isLoading`, `error`, plus try/catch, cleanup. Bohot boilerplate. Koi aisa ho jo ek saath loading/error/data handle kare?

**Pehle install karo:**

```bash
npm install @tanstack/react-query
```

**CONCEPT:** React Query ka **`useQuery`** hook. Do parameters dete ho:

### 1. `queryKey` — Array, Unique Identity

Haan, tumne sahi guess kiya:

- **Pehla element `"recipes"` = resource type.** Batao ki kis type ka data fetch kar rahe ho. Agar car API hoti toh `"car"` likhte. Agar users API hoti toh `"users"`. Isse grouping hoti hai — saare recipe-related queries ek group mein.
- **Doosra element `searchInput` = specific identifier.** Kaunsa specific data chahiye. "chicken" search kiya toh `["recipes", "chicken"]`, "pasta" search kiya toh `["recipes", "pasta"]`.

**Combination ek unique fingerprint banata hai:** `["recipes", "chicken"]` ek unique key hai, `["recipes", "pasta"]` doosri. Dono ka apna alag data store hoga.

**Cache kahan store hota hai?** React Query internally ek plain JavaScript object (dictionary) maintain karta hai. Yeh object tumhare `QueryClient` instance ke andar rehta hai — jo tumne `new QueryClient()` karke banaya tha. Jab tak app chal rahi hai, yeh memory mein hai. App band karo toh cache clear (browser refresh pe bhi khatam).

**Kaam kaise karta hai?** Jab `["recipes", "chicken"]` key ke saath useQuery call hota hai:

| Scenario | Kya hoga |
|---|---|
| Pehli baar "chicken" search | Cache mein nahi → Network request → Data aaya → Cache mein store: `{ '["recipes","chicken"]': { data: [...], status: "success" } }` |
| Phir "pasta" search | Different key → Network request → Cache mein naya entry |
| Wapas "chicken" search | **Cache hit** — same key pehle se hai → No network request → Directly cached data return |

Exactly tumne jo socha wahi.

### 2. `queryFn` — Fetch Function

Actual async function jo data fetch karega. React Query ise call karta hai jab:
- Pehli baar key use hui (cache miss)
- Data stale ho gaya (staleTime cross)

### 3. `enabled` — Fetch Trigger Control

Boolean flag jo batata hai ki **useQuery ko fetch trigger karna hai ya nahi.**

```ts
useQuery({
  queryKey: ["recipes", query],
  queryFn: () => fetchRecipes(query),
  enabled: !!query,   // 👈 yeh dekho
})
```

- `enabled: true` → Fetch chalega (jab conditions meet hoon — cache miss, key change, etc.)
- `enabled: false` → **Fetch nahi chalega.** Chahe key change ho, chahe component re-render ho, chahe kuch bhi ho — React Query fetch nahi karega.

**Humein `enabled: !!query` kyun chahiye?**

`!!query` ka matlab:
- `query = "chicken"` → `!!"chicken"` = `true` → fetch allowed
- `query = ""` → `!!""` = `false` → fetch blocked

Agar user ne kuch search nahi kiya (empty string), toh fetch karna waste hai. `enabled: false` se React Query fetch hi nahi karega. Jab user submit dabayega tab `query` ki value set hogi, `enabled: true` hoga, aur fetch chalega.

**Yeh 4 cheezein return karta hai — automatically, bina kisi setState ke:**

| Variable | Type | Kab kya hota hai |
|---|---|---|
| `data` | `Recipe[] \| undefined` | Initially `undefined`. Fetch success ke baad actual API response |
| `isLoading` | `boolean` | `true` jab pehli baar fetch chal raha hai aur cache mein kuch nahi |
| `isError` | `boolean` | `true` jab fetch fail ho (network down, 404, 500) |
| `error` | `Error \| null` | `null` initially. Error aane par actual Error object |

**Yeh chaar ek saath kyun return karta hai?** Kyunki loading/error/data teeno ek cycle ke hissa hain — ek badla toh doosra automatically adjust hota hai. 2.2 mein teen alag useState kar rahe the aur manually sync karna padta tha — yahan sab internal sync hai.

**CODE:** Component mein useQuery call karte hain. Pehle sirf console.log se verify:

```tsx

    queryKey: ["recipes", searchInput],
    queryFn: () => fetchRecipes(searchInput),
  });

  console.log({ isLoading, isError, recipes });

  // ...form JSX...

```

Notice kaise `queryKey` ka first element `"recipes"` hai (resource type) aur second `searchInput` (identifier — "chicken", "pasta"). Dono milke ek unique key banate hain. Agar `searchInput` change hua, toh key change hogi — React Query naya fetch chalayega aur naye data ko cache karega alag entry mein.

**⚠️ Provider chahiye — warna error aayega.** Yeh code run karo toh "Could not find dependency" ya blank screen aayegi. Kyun? TanStack Query do cheezein maangta hai:

1. **`QueryClient`** — ek instance jo saara cache manage karega. Jab bhi useQuery fetch karega, data isi ke andar store hoga (woh dictionary jiski baat ki thi — `{ ["recipes","chicken"]: { data: [...] } }`). Iske bina React Query ko pata nahi ki cache kahan rakhna hai.

2. **`QueryClientProvider`** — ek wrapper component. Jo bhi component iske andar hai, use `QueryClient` accessible ho jayega (jaise Context API ka Provider kaam karta hai). `QueryClient` ko `client` prop ke through pass karte hain.

Dono ek saath kaam karte hain: `QueryClient` = cache ka storage, `QueryClientProvider` = woh storage ko sab components tak pahunchata hai.

## Step 4 — Problem: Har Keystroke Pe Fetch! Solution: Do States

**SOCH — Network tab mein dekha na?** "pa" type karte hi fetch, "pas" pe fetch, "pasta" pe fetch. Aisa kyun ho raha hai? Chain samajhte hain:

```
User "p" type karta hai
  → onChange fires → setSearchInput("p") 
  → Component re-render hota hai
  → useQuery dobara call hota hai (har render pe hook call hota hai)
  → React Query check karta hai: "kya queryKey badla?"
  → Pehle ["recipes", "chicken"] tha, ab ["recipes", "p"] hai
  → Key change hui → "yeh data cache mein nahi hai" → **fetch chal gaya**
  
User "pa" type karta hai
  → onChange → setSearchInput("pa") → re-render
  → useQuery fir se call hota hai
  → Ab key ["recipes", "pa"] — pehle ["recipes", "p"] tha
  → Key change hui → **phir se fetch**

User "pas" type karta hai → wahi cycle → **fetch**
User "pasta" type karta hai → wahi cycle → **fetch**
```

**4 network requests sirf type karne se.** Aur hum chahte hain sirf **submit button dabane pe ek request**.

**Solution kya hai?** Do states.

| State | Role | Kab update hota hai |
|---|---|---|
| `searchInput` | Input buffer — sirf UI binding ke liye | Har keystroke pe |
| `query` | Fetch trigger — sirf `useQuery` isko use karega | Sirf form submit pe |

Ab `queryKey: ["recipes", query]` hoga — `searchInput` nahi. Toh jab user type karega:
- `searchInput` change hoga → UI update hoga (input value dikhega)
- Lekin `query` wahi rahega
- `queryKey` nahi badla → **fetch nahi chalega**

Jab user submit dabayega:
- `handleSearch` call hoga → `setQuery(searchInput.trim())`
- `query` change hoga → re-render → useQuery dekhega key badli → **fetch chalega**

**CODE:**

**CODE:**

```tsx
const [searchInput, setSearchInput] = useState("chicken"); // input bind
const [query, setQuery] = useState("chicken");             // fetch trigger

const { data: recipes, isLoading, isError, error } = useQuery({
  queryKey: ["recipes", query],
  queryFn: () => fetchRecipes(query),
  enabled: !!query,
});

const handleSearch = (e: React.FormEvent) => {
  e.preventDefault();
  setQuery(searchInput.trim());  // submit pe hi query update
};
```

- `enabled: !!query` — `""` → `false` (fetch nahi chalega), `"chicken"` → `true` (fetch chalega). Empty string pe fetch rokta hai.
- `data: recipes` — useQuery ke `data` ko rename kar diya taaki component mein `recipes` naam se use kar sakein.

**TEST — do kaam karo:**

Pehla — Console: `isLoading: false, recipes: [...]` dikh raha hai? ✅

Doosra — **Wapas Network tab kholo.** "pasta" type karo — ab Network tab mein koi request nahi jaa rahi. Sirf **Submit** button dabao — tab request jayegi. ✅

Fark clear hai na? Ek character pe request jaana vs sirf submit pe.

> **Nutshell:** `searchInput` UI binding ke liye (har type pe update), `query` fetch trigger ke liye (sirf submit pe update). `enabled` control karta hai ki fetch kab chalna chahiye.

## Step 5 — UI Mein Recipes Dikhao

**SOCH:** Ab loading, error, empty, aur data — chaaron states handle karni hain UI mein. Ek aur edge case: **user ne input kuch nahi diya aur submit dabaya toh?** `query` empty hai → `enabled: false` → fetch nahi chalega. Lekin React Query **purana data delete nahi karta** — `recipes` mein abhi bhi pichle search ka data hoga. Toh user empty search kare aur purana data dikhe — yeh confusing hai.

**CONCEPT:** Chaaron states ek conditional rendering pattern follow karte hain. Plus ek extra check — agar `!query` hai toh "Search karo" message dikhao, purana data mat dikhao:

| Condition | UI |
|---|---|
| `!query` | "Type kuch aur search karo" — purana data nahi dikhana |
| `isLoading` | Loading spinner/message |
| `isError` | Red error message with `error.message` |
| `!isLoading && !isError && recipes?.length === 0` | "No results" |
| `recipes?.length > 0` | Recipe grid |

**CODE:**

```tsx
return (
  <div>
    <h1>🍳 Recipe Finder v2</h1>
    <form onSubmit={handleSearch}>
      <input
        value={searchInput}
        onChange={(e) => setSearchInput(e.target.value)}
        placeholder="Search recipes..."
      />
      <button type="submit">Search</button>
    </form>

    {!query && <p>🔍 Kuch search karo upar — yeh purana data hai, relevant nahi hai</p>}
    {isLoading && <p>⏳ Loading...</p>}
    {isError && <p style={{ color: "red" }}>❌ {error.message}</p>}
    {!isLoading && !isError && !query && <p>Type karo aur search dabao</p>}
    {!isLoading && !isError && query && recipes?.length === 0 && <p>No recipes found.</p>}

    <div style={{ display: "grid", gridTemplateColumns: "1fr 1fr 1fr", gap: "16px" }}>
      {recipes?.map((r) => (
        <div key={r.idMeal}>
          <img src={r.strMealThumb} alt={r.strMeal} style={{ width: "100%" }} />
          <h3>{r.strMeal}</h3>
          <p>{r.strCategory} — {r.strArea}</p>
        </div>
      ))}
    </div>
  </div>
);
```

`recipes?.map` — optional chaining (`?.`) isliye kyunki `recipes` `undefined` ho sakta hai jab fetch chal raha ho. `key={r.idMeal}` — har recipe unique hai, React ko list render mein help chahiye.

### `src/App.tsx`

```tsx
import { useState } from "react";
import { useQuery } from "@tanstack/react-query";

interface Recipe {
  idMeal: string;
  strMeal: string;
  strMealThumb: string;
  strCategory: string;
  strArea: string;
}

async function fetchRecipes(query: string): Promise<Recipe[]> {
  const res = await fetch(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`
  );
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const data = await res.json();
  return data.meals ?? [];
}

function RecipeFinderV2() {
  const [searchInput, setSearchInput] = useState("chicken");
  const [query, setQuery] = useState("chicken");

  const { data: recipes, isLoading, isError, error } = useQuery({
    queryKey: ["recipes", query],
    queryFn: () => fetchRecipes(query),
    enabled: !!query,
  });

  const handleSearch = (e: React.FormEvent) => {
    e.preventDefault();
    setQuery(searchInput.trim());
  };

  return (
    <div>
      <h1>🍳 Recipe Finder v2</h1>
      <form onSubmit={handleSearch}>
        <input
          value={searchInput}
          onChange={(e) => setSearchInput(e.target.value)}
          placeholder="Search recipes..."
        />
        <button type="submit">Search</button>
      </form>

      {!query && <p>🔍 Kuch search karo — purana data hai, relevant nahi</p>}
      {isLoading && <p>⏳ Loading...</p>}
      {isError && <p style={{ color: "red" }}>❌ {error.message}</p>}
      {!isLoading && !isError && query && recipes?.length === 0 && <p>No recipes found.</p>}

      <div style={{ display: "grid", gridTemplateColumns: "1fr 1fr 1fr", gap: "16px" }}>
        {recipes?.map((r) => (
          <div key={r.idMeal}>
            <img src={r.strMealThumb} alt={r.strMeal} style={{ width: "100%" }} />
            <h3>{r.strMeal}</h3>
            <p>{r.strCategory} — {r.strArea}</p>
          </div>
        ))}
      </div>
    </div>
  );
}

export default function App() {
  return <RecipeFinderV2 />;
}
```

## What It Is NOT

- **useState ka replacement nahi hai** — `useState` client state ke liye hai (theme, form input, toggle). `useQuery` server state ke liye (API data). Dono alag problems solve karte hain.
- **Global state management nahi hai** — Redux/Zustand ki tarah iska apna koi store/cache nahi hai jisme koi bhi data daal do. Sirf API data ke lifecycle (loading/fetch/cache/refetch) manage karta hai.
- **useEffect ka replacement nahi hai (sirf API ke liye)** — `useEffect` general purpose hai (timer, event listener, any side effect). `useQuery` specifically server state ke liye.

---

## Common Mistakes

1. **queryKey galat dena** — Key unique nahi toh cache collisions. Hamesha `["entity", ...identifiers]`. Jaise `["recipes", "chicken"]` aur `["recipes", "pasta"]` — dono alag keys hain.

2. **searchInput ko directly useQuery mein daalna** — Har keystroke pe API call jayegi. Hamesha `query` state use karo jo sirf submit pe update ho.

3. **Provider bhoolna** — `QueryClientProvider` wrap nahi kiya toh "No QueryClient set" error aayega.

4. **isLoading vs isFetching confuse** — `isLoading` true tab jab pehli baar fetch ho raha hai (no cache). `isFetching` true jab koi bhi fetch chal raha hai (background refetch bhi).

---

## Cheat Sheet (Quick Recall)

```ts
const { data, isLoading, isError, error } = useQuery({
  queryKey: ["recipes", query],   // unique identifier — cache isi se hota hai
  queryFn: () => fetchRecipes(query), // actual fetch function
  enabled: !!query,                // kab fetch trigger karna hai
});
```

- `queryKey` = har query ki unique identity — same key = cache hit, different key = new fetch
- `isLoading` = first fetch (no cache). `isFetching` = koi bhi fetch chal raha hai
- `searchInput` vs `query` — input buffer vs submit trigger (do states pattern)
- `QueryClientProvider` wrap karna bhoolna mat

   <details>
   <summary>Sample Answer</summary>
   `data` — fetch success ke baad actual API response; undefined initially. `isLoading` — true jab pehli baar fetch chal raha hai aur cache mein kuch nahi; false jab data ya error aaya. `isError` — true jab fetch fail ho; false jab success ho. `error` — null initially; error aane par actual Error object jisme message hota hai.
   </details>

2. `searchInput` aur `query` — dono state kyun rakhte hain? Ek kyun nahi chalega?

   <details>
   <summary>Sample Answer</summary>
   `searchInput` input binding ke liye hai — har keystroke pe update hota hai. `query` fetch trigger ke liye — sirf submit pe update hota hai. Agar sirf `searchInput` use karein toh har character type karte hi API call chali jayegi — wasteful. `enabled: !!query` ensure karta hai ki empty string pe fetch na chale.
   </details>

3. `queryKey` ka kya kaam hai? Kya hoga agar do components same `queryKey` use karein?

   <details>
   <summary>Sample Answer</summary>
   `queryKey` unique identifier hai — isi se cache hota hai. Same key = same cache. Do components same key use karein toh sirf ek network request jayegi, dono same cached data share karenge. Isko **deduplication** kehte hain.
   </details>

4. `enabled: !!query` ka kya matlab hai? Agar `query = ""` ho toh kya hoga?

   <details>
   <summary>Sample Answer</summary>
   `!!query` — `""` (empty string) falsy value hai, `!!""` = `false`. Toh `enabled: false` → fetch nahi chalega. `"chicken"` truthy hai, `!!"chicken"` = `true` → fetch chalega. Iska fayda yeh hai ki user ne kuch type nahi kiya toh API call waste nahi hogi.
   </details>

5. `QueryClientProvider` kyun zaroori hai? Agar bhool jayein toh kya error aayegi?

   <details>
   <summary>Sample Answer</summary>
   `useQuery` internally Context API use karta hai — `QueryClientProvider` woh context provide karta hai jisme `QueryClient` instance rehta hai. Agar bhool jayein toh "No QueryClient set" error aayega kyunki `useQuery` ko apna client nahi mil raha.
   </details>
