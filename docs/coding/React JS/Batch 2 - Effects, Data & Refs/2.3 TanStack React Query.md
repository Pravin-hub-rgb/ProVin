## The One Idea Behind the Whole Library — Memoization for API Calls

You've already seen this pattern — in the JS course, Phase 4 (Memoization): `memoize(fn)` returns a new function that keeps a notebook. The first call does the slow work and writes the answer in the notebook. Every later call with the same input is answered straight from the notebook — the slow work is never repeated. The notebook is the **cache**, and the input is the **key**.

React Query is that exact same idea, pointed at **API calls** instead of normal JavaScript functions:

- Your "input" is `["recipes", "chicken"]` — the **queryKey**
- The "slow work" is the fetch to the server
- The "notebook" is the **cache** — it lives inside the `QueryClient` we'll create in a minute
- First time searching "chicken" → wait for the network → remember the answer
- Search "chicken" again → instant, straight from the cache — no network call at all

There are two differences, and both exist because the internet is involved, not because the idea changed:

1. **Notebook entries can go stale.** A function's answer never changes, but the server's data changes all the time. React Query treats each entry as fresh for a while (this is `staleTime` — we'll use it later), and then silently refetches in the background to keep it up to date.
2. **It also reports the status.** `isLoading`, `isError` — your JS notebook never had to say "still thinking", but a server always takes a moment, so React Query tracks that for you too.

That's the gist of the whole library. Everything else in this doc — `queryKey`, `queryFn`, `enabled`, the Provider dance from Step 3 — is just the details of how this one notebook works. Keep it in the back of your mind as we build.

## Step 2 — Interface and Fetch Function

Search bar is ready. Now how do we get data from the API? First, let's see what the data format looks like:

```json
{

      "idMeal": "52772",
      "strMeal": "Chicken Handi",
      "strMealThumb": "https://...",
      "strCategory": "Chicken",
      "strArea": "Indian"
    }
  ]
}
```

Based on this format, we define TypeScript interfaces for type safety.

**Think about it:** `data.meals` is an array where each item has id, name, image, category, area. So the interface looks like this:

```ts
interface Recipe {
  idMeal: string;
  strMeal: string;
  strMealThumb: string;
  strArea: string;
  strCategory: string;
}
```

**Think:** Now the fetch function. An async function that calls a URL, checks the response, parses JSON, and returns `Recipe[]`. If `meals: null` is returned (invalid search), return an empty array.

```ts
async function fetchRecipes(query: string): Promise<Recipe[]> {
  const res = await fetch(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`
  );
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const data = await res.json();
  return data.meals ?? [];
}
```

`res.ok` — checks if HTTP status is in the 200-299 range. `?? []` — null becomes empty array.

**Good habit — why this function lives outside the component:** It's a pure helper. It takes a query and returns data — it touches no props, no state, no hooks, so it has no business being defined inside. Staying outside means it's created once (not on every render), it's reusable, and you can import and test it on its own. If the day comes when you *do* need something from the component (a prop, a token from context), pass it in as an argument — `fetchRecipes(query, token)` — instead of moving the function inside.

**Console test:** Call it in handleSearch and see:

## Step 3 — useQuery: No More 4 useState

**Think:** In 2.2, we manually managed 4 states for every API call — `recipes`, `isLoading`, `error`, plus try/catch/finally and a cleanup (ignore pattern). Lots of boilerplate. Is there something that handles loading/error/data all at once?

Yes — that something exists: a hook called **`useQuery`**, from the **TanStack React Query** library. Let's not lecture you on it first. Same pattern as everything else in this course — install, build, observe, and *then* dissect how it works.

**First, install it:**

```bash
npm install @tanstack/react-query
```

**Build it first, theory after — call useQuery in the component, and verify with console.log:**

```tsx
import { useQuery } from "@tanstack/react-query";

function RecipeFinderV2() {
  const [searchInput, setSearchInput] = useState("chicken");

  const { data: recipes, isLoading, isError, error } = useQuery({
    queryKey: ["recipes", searchInput],
    queryFn: () => fetchRecipes(searchInput),
  });

  console.log({ isLoading, isError, recipes });

  // ...form JSX...
}
```

Don't worry about what `queryKey` means yet — just know it's the label React Query uses to store and find your data (we'll dissect it properly in the theory section right after). Run the code — and you'll hit an interesting error before any magic happens:

**⚠️ Provider required — error without it.** If you run the code now, you'll see an error like `No QueryClient set, use QueryClientProvider to set one` in the console (or a blank screen). This happens on the very first run — it's normal, and we'll fix it right away. But first, let's understand *why* it happens, because that's where the actual lesson is.

**Why does TanStack Query need two extra things?**

Here's the plain truth. Your components — all of them, anywhere in the app — will want server data. But `useQuery` can't just fetch data and remember it all by itself. Somewhere, there has to be **one place** where all fetched data lives. Otherwise every component would fetch the same thing separately, and nothing would remember what was fetched last time.

So TanStack Query gives you two tools:

**1. `QueryClient` — the box that holds the data.**

`QueryClient` is the tool that creates **one box**. All the server data your app fetches lives inside this one box. When a component asks for the same data again, it gets it from the box instead of hitting the network again. This box is what we call the **cache** — in simple words, a copy of the data you already fetched, kept around temporarily so you don't have to fetch it again and again.

**2. `QueryClientProvider` — the thing that hands the box to your components.**

Just making a box is not enough. A React component can't see that box just because it exists somewhere in the file — you have to *share* it with them. `QueryClientProvider` is a component whose only job is: take the box, and make it available to every component inside it. It works exactly like Context API's `Provider` — Context's `Provider` hands down the context value, this one hands down the box.

That's why you need **both**:

- `QueryClient` makes the box
- `QueryClientProvider` hands the box to everyone

If you create the box but never hand it out, your components can't reach it — and `useQuery` throws `No QueryClient set`, because no box was shared with it. Exactly the error we're seeing.

**Step-by-step fix — in `src/main.tsx`:**

**Open the main file (`src/main.tsx`). You'll see something like this:**

```tsx
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import './index.css'
import App from './App.tsx'

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

We'll add the two tools, one by one — with the *why* behind each step, not just the *what*.

**1. Import the two tools:**
```ts
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
```
`@tanstack/react-query` is the library we installed. It has many things inside it, but we only need these two right now:

- `QueryClient` — the tool that creates the box
- `QueryClientProvider` — the component that hands the box to the app

One import, two tools — because we need one to *make* the box and one to *share* it.

**2. Create the box — once, before the app starts:**
```ts
const queryClient = new QueryClient()
```
This line actually creates the box. Three things to notice:

- **Why is it placed outside the components?** Because we want the box created **once**, when the app starts — not recreated every time a component re-renders. If you created it inside a component, every re-render would build a brand-new empty box and throw away everything cached so far.
- **Why `new QueryClient()`?** `QueryClient` just tells JavaScript *how* to build the box — it's a recipe, not the box itself. `new QueryClient()` is where the box actually gets built and stored in the `queryClient` variable.
- **Why is it placed between the imports and `createRoot`?** Because the box must exist *before* we hand it to `<App />` — the app can't use a box that hasn't been built yet.

**3. Wrap the whole app in the Provider — and pass the box to it:**
```tsx
createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <App />
    </QueryClientProvider>
  </StrictMode>,
)
```
Two things to notice here:

- **Why wrap `<App />`?** Only components that live *inside* `<QueryClientProvider>` can reach the box. Every page and every component in our app will use `useQuery`, so we wrap the entire app once, right at the top — so everything below it is covered.
- **Why `client={queryClient}`?** The Provider doesn't know which box you built. You could create two boxes, five boxes, whatever you want. So you have to tell the Provider which one to share — and you do that through a prop named **`client`** (that's the fixed name — you can't call it anything else), with your box as its value. Read `client={queryClient}` as: *"Here is my box, Provider — share this exact one with everyone inside you."* The left side (`client`) is the fixed prop name the Provider expects; the right side (`queryClient`) is the variable holding the box you made in step 2.

**Final `main.tsx` — read it top to bottom:**

```tsx
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import './index.css'
import App from './App.tsx'

const queryClient = new QueryClient()

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <App />
    </QueryClientProvider>
  </StrictMode>,
)
```

What every line is doing:

| Line | What it does |
|---|---|
| `import { StrictMode } from 'react'` | React's dev-time double-check helper — already there, not ours |
| `import { createRoot } from 'react-dom/client'` | React's way to attach to the actual DOM — already there, not ours |
| `import { QueryClient, QueryClientProvider } from '@tanstack/react-query'` | Our two tools: build the box, share the box |
| `import './index.css'` | Styles — already there, not ours |
| `import App from './App.tsx'` | Our main component — the root of our whole UI |
| `const queryClient = new QueryClient()` | The one box for the whole app — created once, before anything renders |
| `<StrictMode>` | Wraps the app for dev-time checks — already there, not ours |
| `<QueryClientProvider client={queryClient}>` | Hands our one box to every component inside it |
| `<App />` | The app itself — everything rendered inside it can now reach the box with `useQuery` |

Provider is set up. Refresh the browser — the `No QueryClient set` error should be gone.

**Now — the how, in detail. What does `useQuery` actually do behind the scenes?**

`useQuery` takes **two things** — a `queryKey` (which data you're asking for) and a `queryFn` (the function that fetches it). Plus one **optional** third — `enabled` — which decides *when* the fetch is allowed to fire (we'll actually use it in Step 4).

### 1. `queryKey` — Array, Unique Identity

The `queryKey` is the fingerprint of the data — React Query uses it to decide whether to fetch from the network or hand you cached data instead. The key we use throughout this doc is `["recipes", searchInput]`. Let's pick apart why it has **two elements** — it's not decoration, it solves a real problem.

**What could go wrong with a single-element key?**

Say the Recipe Finder used the key with only the input:

```tsx
useQuery({ queryKey: ["chicken"], queryFn: () => fetchRecipes("chicken") });
```

That works fine today. Now a few weeks later, this same app needs a **Users** screen — search people by name. Someone types "chicken" there too:

```tsx
useQuery({ queryKey: ["chicken"], queryFn: () => fetchUsers("chicken") });
```

Now look at the cache dictionary after both run:

| Fetch | Key | What the cache stores |
|---|---|---|
| Recipes search "chicken" | `["chicken"]` | `{ "chicken": recipeData }` |
| Users search "chicken" | `["chicken"]` | `{ "chicken": userData }` — overwrites the recipe data! |

That's the **collision**: two unrelated APIs, one key, wrong data served. The cache matches on the key alone — it has no idea the two functions are different. So your Recipe Finder would suddenly show **user data**, with no error, no warning — the worst kind of bug.

**The fix — first say WHICH notebook, then which page of it:**

```tsx
useQuery({ queryKey: ["recipes", "chicken"], queryFn: () => fetchRecipes("chicken") }); // notebook 1
useQuery({ queryKey: ["users", "chicken"],   queryFn: () => fetchUsers("chicken") });   // notebook 2
```

```text
// the cache dictionary now has room for both — no overwriting:
{
  '["recipes","chicken"]': { data: [/* recipes */] },
  '["users","chicken"]':   { data: [/* users   */] },
}
```

Two entries, sitting side by side, never touching each other. Same input, two different keys — so both cached copies survive. That's why the array is shaped like this:

- **First element `"recipes"` = the notebook's name — WHICH API/resource this is.** It never changes for that resource, and that's the point — it stamps every recipes entry as "this is a recipes entry". Adding a new API means a new notebook: `["cars", ...]`, `["users", ...]`.
- **Second element `searchInput` = the specific item inside the notebook.** `"chicken"`, `"pasta"`, `"dal"` — the exact entry you want.

**The combination creates a unique fingerprint:** `["recipes", "chicken"]` is one unique key, `["recipes", "pasta"]` is another, `["users", "chicken"]` is another. Each has its own cached data — nothing overwrites anything else.

**One more benefit of the shared first position:** since every recipes entry starts with `["recipes", ...]`, you can grab the *whole class* at once — tell the cache "forget every recipes entry", or just eyeball them grouped together — without touching users or cars. That's what the first slot buys you: operations on the whole notebook, not just one entry.

**Where does the cache live?** Remember the box — `QueryClient`? React Query keeps a plain JavaScript object (a dictionary) with everything you've fetched, and that object lives inside the box you created with `new QueryClient()`. As long as the app is running, the box stays in memory. App closes (or browser refreshes) → box is emptied, and everything is fetched again.

**How it works:** When `useQuery` is called with key `["recipes", "chicken"]`:

| Scenario | What happens |
|---|---|
| First time searching "chicken" | Cache miss → Network request → Data arrives → Cache stores it: `{ '["recipes","chicken"]': { data: [...], status: "success" } }` |
| Then searching "pasta" | Different key → Network request → New cache entry |
| Back to "chicken" | **Cache hit** — key was seen before → No network request → Returns cached data directly |

Exactly what you'd expect.

### 2. `queryFn` — Fetch Function

The actual async function that fetches data. React Query calls this when:
- The key is used for the first time (cache miss)
- Data becomes stale (staleTime crosses)

### 3. `enabled` — Fetch Trigger Control

A boolean flag that says whether **`useQuery` should trigger a fetch or not.**

Look at the example below — it uses `query`, a state **we don't have yet** (we add it in Step 4). Don't worry about the missing piece — the `enabled: !!query` line is all that matters for now:

```ts
useQuery({
  queryKey: ["recipes", query],
  queryFn: () => fetchRecipes(query),
  enabled: !!query,   // 👈 pay attention to this
})
```

- `enabled: true` → Fetch happens (when conditions are met — cache miss, key change, etc.)
- `enabled: false` → **Fetch does NOT happen.** No matter what — key changes, component re-renders, whatever — React Query won't fetch.

**Why do we need `enabled: !!query`?**

`!!query` means:
- `query = "chicken"` → `!!"chicken"` = `true` → fetch allowed
- `query = ""` → `!!""` = `false` → fetch blocked

If the user hasn't entered a search yet (empty string), fetching for an empty search is wasteful. `enabled: false` blocks it. When the user submits, `query` gets its value, `enabled` flips to `true`, and the fetch triggers. (Again — the `query` state arrives in Step 4.)

**Here's what these four things return — automatically, without any setState:**

| Variable | Type | What happens |
|---|---|---|
| `data` | `Recipe[] \| undefined` | Initially `undefined`. After fetch success, the actual API response |
| `isLoading` | `boolean` | `true` when the first fetch is running and cache has nothing |
| `isError` | `boolean` | `true` when fetch fails (network down, 404, 500) |
| `error` | `Error \| null` | `null` initially. When an error occurs, the actual Error object |

**Why return all four at once?** Because loading, error, and data are all part of the same cycle — when one changes, the others adjust automatically. In 2.2 we managed three separate `useState` calls and manually synced them — here, it's all internal sync.

> **Nutshell:** `useQuery` is a hook that returns loading/error/data states all at once for server state (API data). `queryKey` handles caching, `queryFn` holds the fetch logic — the library manages everything automatically.

## Step 4 — Problem: A Request Per Keystroke! Solution: Two States

**Think — saw the Network tab?** "pa" sent a request, "pas" sent one, "pasta" sent one. Why? Let's trace the chain:

```
User types "p"
  → onChange fires → setSearchInput("p")
  → Component re-renders
  → useQuery is called again (hooks run every render)
  → React Query checks: "did the queryKey change?"
  → Was ["recipes", "chicken"], now ["recipes", "p"]
  → Key changed → "this isn't in cache" → **fetch triggered**

User types "pa"
  → onChange → setSearchInput("pa") → re-render
  → useQuery called again
  → Now key is ["recipes", "pa"] — was ["recipes", "p"]
  → Key changed → **fetch again**

User types "pas" → same cycle → **fetch**
User types "pasta" → same cycle → **fetch**
```

**Four network requests just from typing.** And we want only **one request when the submit button is pressed**.

**Solution: Two states.**

| State | Role | When it updates |
|---|---|---|
| `searchInput` | Input buffer — only for UI binding | Every keystroke |
| `query` | Fetch trigger — only `useQuery` uses this | Only on form submit |

Now `queryKey: ["recipes", query]` — not `searchInput`. So when user types:
- `searchInput` changes → UI updates (input value shown)
- But `query` stays the same
- `queryKey` doesn't change → **no fetch**

When the user submits:
- `handleSearch` fires → `setQuery(searchInput.trim())`
- `query` changes → re-render → useQuery sees the key changed → **fetch triggered**

**Code:**

```tsx
const [searchInput, setSearchInput] = useState("chicken"); // input binding
const [query, setQuery] = useState("chicken");             // fetch trigger

const { data: recipes, isLoading, isError, error } = useQuery({
  queryKey: ["recipes", query],
  queryFn: () => fetchRecipes(query),
  enabled: !!query,
});

const handleSearch = (e: React.FormEvent) => {
  e.preventDefault();
  setQuery(searchInput.trim());  // query updates only on submit
};
```

- `enabled: !!query` — `""` → `false` (fetch blocked), `"chicken"` → `true` (fetch runs). Empty string triggers no fetch.
- `data: recipes` — renamed `useQuery`'s `data` to `recipes` so we can use it in the component.

**TEST — two things:**

First — Console: `isLoading: false, recipes: [...]` showing? ✅

Second — **Open the Network tab again.** Type "pasta" — no requests going out. Now click **Submit** — that's when a request goes out. ✅

The difference is clear: per-character requests vs. only on submit.

> **Nutshell:** `searchInput` is for UI binding (updates on every keystroke), `query` is the fetch trigger (updates only on submit). `enabled` controls when fetch should happen.

## Step 5 — Display Recipes in UI

**Think:** Now we need to handle loading, error, empty, and data states in the UI. One edge case: **if the user submits an empty query?** `query` is empty → `enabled: false` → no fetch. But React Query **doesn't delete old data** — `recipes` still holds the previous search results. If old data shows on an empty search, that's confusing.

**Concept:** All four states follow a conditional rendering pattern. Plus an extra check: if `!query`, show "Search something" message instead of old data.

| Condition | UI |
|---|---|
| `!query` | "Search something above — this is old data, not relevant" |
| `isLoading` | Loading spinner/message |
| `isError` | Red error message with `error.message` |
| `!isLoading && !isError && recipes?.length === 0` | "No results" |
| `recipes?.length > 0` | Recipe grid |

**Code:**

```tsx
return (
  <div>
    <h1>🍳 Recipe Finder v2</h1>
    <form onSubmit={handleSearch}>
      <input
        value={searchInput}
        onChange={(e) => setSearchInput(e.target.value)}
        placeholder="Search recipes..."
      />
      <button type="submit">Search</button>
    </form>

    {!query && <p>🔍 Search something above — this is old data, not relevant</p>}
    {isLoading && <p>⏳ Loading...</p>}
    {isError && <p style={{ color: "red" }}>❌ {error.message}</p>}
    {!isLoading && !isError && !query && <p>Type something and click search</p>}
    {!isLoading && !isError && query && recipes?.length === 0 && <p>No recipes found.</p>}

    <div style={{ display: "grid", gridTemplateColumns: "1fr 1fr 1fr", gap: "16px" }}>
      {recipes?.map((r) => (
        <div key={r.idMeal}>
          <img src={r.strMealThumb} alt={r.strMeal} style={{ width: "100%" }} />
          <h3>{r.strMeal}</h3>
          <p>{r.strCategory} — {r.strArea}</p>
        </div>
      ))}
    </div>
  </div>
);
```

`recipes?.map` — optional chaining (`?.`) because `recipes` can be `undefined` during fetch. `key={r.idMeal}` — each recipe is unique, React needs a key for list rendering.

- Clear input and submit — "Search something" message showing, old data not displayed? ✅

### `src/App.tsx`

```tsx
import { useState } from "react";
import { useQuery } from "@tanstack/react-query";

interface Recipe {
  idMeal: string;
  strMeal: string;
  strMealThumb: string;
  strCategory: string;
  strArea: string;
}

async function fetchRecipes(query: string): Promise<Recipe[]> {
  const res = await fetch(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`
  );
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const data = await res.json();
  return data.meals ?? [];
}

function RecipeFinderV2() {
  const [searchInput, setSearchInput] = useState("chicken");
  const [query, setQuery] = useState("chicken");
```

## What It Is NOT

- **Not a replacement for `useState`** — `useState` is for client state (theme toggle, form input, modal open/close). `useQuery` is for server state (API data). They solve different problems.
- **Not global state management** — Unlike Redux/Zustand which have a store/cache where you can put anything, it has no storage for arbitrary data. It only manages the lifecycle of API data (loading/fetch/cache/refetch).
- **Not a replacement for `useEffect`** — `useEffect` is general-purpose (timers, event listeners, any side effect). `useQuery` is specifically for server state.

---

## Common Mistakes

1. **Wrong `queryKey`** — If the key isn't unique, cache collisions happen. Always use `["entity", ...identifiers]`. Like `["recipes", "chicken"]` and `["recipes", "pasta"]` — both different keys.
2. **Directly using `searchInput` in `useQuery`** — Each keystroke sends an API call. Always use a `query` state that updates only on submit.
3. **Forgetting the Provider** — If `QueryClientProvider` isn't wrapped, you'll get "No QueryClient set" error.
4. **Confusing `isLoading` vs `isFetching`** — `isLoading` is true only on the first fetch (no cache). `isFetching` is true whenever any fetch is happening (including background refetch).

## Try It Yourself

1. What's the difference between `staleTime: 0` and `staleTime: 60000`?

   <details>
   <summary>Answer</summary>
   `staleTime: 0` → refetches every time. `staleTime: 60000` → cached data for 1 minute, no refetch within that window.
   </details>

2. Fetch `GET /api/posts` with `useQuery` — in just 2 lines.

   <details>
   <summary>Answer</summary>

   ```tsx
   const { data: posts, isLoading } = useQuery({
     queryKey: ["posts"],
     queryFn: () => fetch("/api/posts").then(r => r.json()),
   });
   ```
   </details>

3. If two components use the same `queryKey`, how many network requests will be sent?

   <details>
   <summary>Answer</summary>
   Just one. The query library deduplicates — both components share the same cache.
   </details>

## In Your Own Words

1. What four things does `useQuery` return? What does each one mean?

   <details>
   <summary>Sample Answer</summary>
   `data` — the actual API response after fetch succeeds; `undefined` initially. `isLoading` — `true` when the first fetch is running and cache has nothing. `isError` — `true` when fetch fails. `error` — `null` initially; the actual Error object when an error occurs, which has a `message` property.
   </details>

2. Why keep two states — `searchInput` and `query`? Wouldn't one be enough?

   <details>
   <summary>Sample Answer</summary>
   `searchInput` is for input binding — it updates on every keystroke. `query` is the fetch trigger — it updates only on submit. If you use just `searchInput` directly in `queryKey`, every character typed causes a new API call. `enabled: !!query` also ensures that fetching doesn't happen on an empty string.
   </details>

3. What is `queryKey` for? What happens if two components use the same `queryKey`?

   <details>
   <summary>Sample Answer</summary>
   `queryKey` is a unique identifier — caching is based on it. Same key = same cache. If two components use the same `queryKey`, only one network request is sent — both components share the cached data. This is called **deduplication**.
   </details>

4. What does `enabled: !!query` mean? What happens if `query` is an empty string?

   <details>
   <summary>Sample Answer</summary>
   `!!query` — empty string is a falsy value, `!!""` = `false`. So `enabled: false` → no fetch happens. `"chicken"` is truthy, `!!"chicken"` = `true` → fetch happens. The benefit is that when the user hasn't typed anything, no API call is wasted.
   </details>

5. Why is `QueryClientProvider` necessary? What error appears if you forget it?

   <details>
   <summary>Sample Answer</summary>
    `useQuery` works using React Context behind the scenes — `QueryClientProvider` hands down the box (`QueryClient`), and `useQuery` looks inside it to find what it needs. If you forget the Provider, there's no box anywhere `useQuery` can reach, so it throws the error "No QueryClient set."
   </details>

## Cheat Sheet (Quick Recall)

**The problem:** manual fetch = 4 state hooks + try/catch/finally + ignore flags + retry logic — rewritten in every component, wrong in the same spots every time.

**The fix — TanStack React Query:** cache keys, fetch function, auto loading/error/caching/retry — one hook. Your job: `useQuery({ queryKey, queryFn })`, React Query does the rest.

```ts
const { data, isLoading, isError, error } = useQuery({
  queryKey: ["recipes", query],   // unique identifier - cache is based on this
  queryFn: () => fetchRecipes(query), // actual fetch function
  enabled: !!query,                // controls when fetch should trigger
});
```

**Setup (once, in `main.tsx` — exactly what you do the first time):**

```tsx
// 1. Import both
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";

// 2. Create the client — once, before the app
const queryClient = new QueryClient();

// 3. Wrap <App /> in the provider — it feeds the cache to every component
createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <App />
    </QueryClientProvider>
  </StrictMode>,
);
```

Once wrapped, every component inside can call `useQuery` — no more passing data down or fetching manually. `QueryClientProvider` is required — forgetting it throws "No QueryClient set".

- `queryKey` = unique identity of each query - same key = cache hit, different key = new fetch
- `isLoading` = first fetch (no cache). `isFetching` = any fetch is running
- `searchInput` vs `query` - input buffer vs submit trigger (two-states pattern)
- Don't forget to wrap with `QueryClientProvider` (the "No QueryClient set" error if forgotten)
