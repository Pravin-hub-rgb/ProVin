
## MCQ

Q: What are the two arguments of the `useEffect` hook?
A. Setup function and dependency array — setup runs after render, deps control when it re-runs
B. Callback function and delay — sets time interval for the effect like setInterval
C. Component name and props — registers the component in React's lifecycle
D. State variable and setter — alternative syntax for managing state inside the effect
> A. `useEffect(fn, [deps])` — the first argument is the setup function containing the side effect code. The second is the dependency array that controls when the effect re-runs. The setup function executes after render.

Q: When does `useEffect` execute in the component lifecycle?
A. Before the component renders — the side effect runs before DOM updates
B. Immediately after render — the DOM updates first, then the useEffect setup runs
C. Only when the component unmounts — when the component leaves the UI
D. Whenever any state update happens — runs regardless of whether render occurs
> B. `useEffect` runs after render. The order is: component function executes → JSX returned → DOM updated → useEffect setup runs. This pattern is called "render-first verification" — the screen is ready first, then the side effect.

Q: What are side effects in React's context?
A. CSS styling and animations applied within React components that create visual effects
B. Operations that happen outside the render cycle — timer, API call, browser API, localStorage
C. Changes to props in React components that affect child components
D. Effects triggered by user interaction — button clicks, form submissions, hover
> B. Side effects are operations that happen **outside** React's render cycle — `setInterval`, `fetch`, `localStorage`, `document.title`. React's render cycle guarantees same props + same state = same JSX, but side effects break this purity because they interact with external systems.

Q: When does an empty dependency array `[]` cause useEffect to run?
A. After every render — empty means no restriction, runs every time
B. Only on mount — when the component first appears on screen, runs one time
C. Whenever any state changes — React automatically detects which state is needed
D. Never runs — React interprets the empty array as "effect is disabled"
> B. `[]` means "run only on mount." React checks that no value in the array can change — since there are none, the effect runs only once. Button clicks or state changes won't trigger it again.

Q: Will `useEffect(() => { setCount(count + 1) }, [count])` cause an infinite loop?
A. No — useEffect only runs once regardless of the dependency
B. Yes — count changes → effect re-runs → count increments → effect re-runs → count increments...
C. Only if the initial value is 0, otherwise no
D. No, because `setCount` is React's internal function and isn't included in dependencies
> B. This will cause an infinite loop. `[count]` means "re-run when count changes." Inside the effect, `setCount(count + 1)` increments count. Count increments → effect re-runs → count increments → effect re-runs... This chain reaction should be avoided.

Q: When is the cleanup function in useEffect executed?
A. Only on unmount — when the component leaves the UI entirely
B. Only when the component mounts — after the first render
C. On unmount and before re-run — both scenarios trigger cleanup
D. Never automatically — the developer must call it manually
> C. React calls the cleanup function in two cases: (1) On unmount — to release resources. (2) Before the effect re-runs — cleans up the old effect before starting the new one. Cleanup ensures no resource (timer, subscription) stays alive.

Q: What is a stale closure with useEffect?
A. When a component unmounts but a state update is attempted — React throws an error
B. When the function inside useEffect captures the variable value from a previous render and doesn't use the latest value
C. When too many values are put in the dependency array — React becomes slow
D. When the cleanup function is forgotten — timers or listeners keep running in the background
> B. A stale closure occurs when the function inside `useEffect` captures the variable value from a **previous render** (JavaScript closure) and doesn't see the latest value after state changes. When `setInterval` captures `seconds = 0` on mount, it keeps referencing that old value even after state updates create a new `seconds = 1` variable.

Q: What is the correct way to fix stale closure with a timer?
A. Define the timer in global scope — the closure problem resolves automatically
B. Declare the variable with `var` — JavaScript hoisting provides the latest value
C. Use functional update — `setSeconds(prev => prev + 1)` — React provides the latest value itself
D. Make the effect `async` — async functions resolve the closure problem
> C. Functional update `setSeconds(prev => prev + 1)` fixes stale closure. Here, `prev` is provided by React from its internal storage — whatever the latest state is, it comes through `prev`. Only `setSeconds` itself is captured, which is a stable React function.

Q: What does `setInterval(() => console.log("Tick"), 1000)` return?
A. A boolean — `true` if the interval was successfully set up, `false` if the component unmounted
B. A string — the interval's unique name stored in browser memory
C. A numeric ID — the interval's unique identifier, used to stop it with `clearInterval(id)`
D. A function object — with a method to cancel the interval attached directly
> C. `setInterval` returns a numeric ID (like 1, 2, 3...). This ID is the interval's "identity card." When you want to stop it, you pass this ID to `clearInterval(id)`. If the ID is never stored, the interval can't be stopped — this is called a memory leak.

## TrueFalse

Q: `useEffect` starts before the render completes — the side effect executes before DOM updates.
- True
- False
> False. `useEffect` runs after render. The order is: component function executes → JSX returned → DOM updated → `useEffect` setup runs. If `useEffect` ran before render, the DOM wouldn't be safe to access — just like `DOMContentLoaded` ensures the DOM is ready.

---

Q: An empty dependency array `[]` causes `useEffect` to run after every render, since there's nothing in it.
- True
- False
> False. An empty array `[]` means "run only on mount." React sees that nothing in the array changes — so the effect runs once. To run after every render, don't pass an array at all: `useEffect(() => {...})`.

---

Q: Cleanup function only runs on unmount, not before a re-run.
- True
- False
> False. The cleanup function runs in two cases: (1) When the component unmounts — to release resources. (2) Before the effect re-runs — cleans up the old effect before starting the new one. When `[count]` is passed and count changes, the old cleanup runs first, then the new effect.

---

Q: The dependency array is just for performance optimization — it has no behavioral impact.
- True
- False
> False. The dependency array **defines behavior** — "when should this effect run." `[]` = only on mount. `[count]` = mount + when count changes. No array = every render. It's not an optimization — it's a behavior definition. Any reactive value used inside should be in the dependencies array, whether it affects performance or not.

---

Q: `useEffect(async () => { await fetchUsers() }, [])` — making the useEffect callback async directly is fine.
- True
- False
> False. `useEffect`'s callback expects to return either `void` or a cleanup function. An `async` function always returns a Promise — not a cleanup function. React cannot treat a Promise as cleanup. Solution: define an async function inside and call it.

---

Q: Without cleanup, `setInterval` can keep running in the background after the component unmounts — causing memory leaks.
- True
- False
> True. If `useEffect` starts a `setInterval` and cleanup doesn't call `clearInterval`, the interval keeps running after unmount. React doesn't automatically stop timers. The interval's reference stays in memory — garbage collector can't free it. This is called a memory leak.

## Short Answer

Q: Explain the three cases of the useEffect dependency array. When does each run, what's the use case, and give an example.

<details>
<summary>Sample Answer</summary>

**Case 1 — Empty Array `[]`: Only on Mount**
- **When it runs:** Only when the component first appears on screen (mount). Never again.
- **Use case:** Initial API fetch, third-party library setup, starting a timer
- **Example:** `useEffect(() => { fetchUsers() }, [])`

**Case 2 — With Value `[count]`: Mount + Dependency Change**
- **When it runs:** On mount + whenever `count` changes
- **Use case:** Syncing with state/props, updating document title
- **Example:** `useEffect(() => { document.title = `${count} new messages` }, [count])`

**Case 3 — No Array: After Every Render (Rare)**
- **When it runs:** After every render (mount + every state/prop change)
- **Use case:** Only debugging/logging. Avoid in production
- **Example:** `useEffect(() => { console.log("Component rendered") })` — no array passed

**Rule of thumb:** Any reactive value (state/prop) used inside `useEffect` should be in the dependency array. If `count` is used inside but `[]` is passed, stale closure occurs — the effect always sees the mount-time value (0).

</details>

Q: What is a stale closure? How does it occur with useEffect and how does functional update (`setX(prev => prev + 1)`) fix it? Explain with code.

<details>
<summary>Sample Answer</summary>

**What is a stale closure?**

A stale closure happens when a function inside `useEffect` captures the variable from a **previous render** (via JavaScript closure), but keeps referencing that old value after state changes create a new variable.

**The problem in useEffect:**

```tsx
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds(seconds + 1);  // ❌ captured `seconds = 0` on mount
    }, 1000);
  }, []);

  return <p>Timer: {seconds}s</p>;
}
```

**What happens:**
1. Mount → a `seconds = 0` variable is created
2. `useEffect` runs → `setInterval` captures `seconds = 0`
3. `setSeconds(0 + 1)` → seconds becomes 1 → re-render
4. Re-render creates a new `seconds = 1` variable
5. But `setInterval` still references the old `seconds = 0`
6. `setSeconds(0 + 1)` → always sets to 1
7. Timer gets stuck at 1 ❌

**Fix — Functional Update:**

```tsx
useEffect(() => {
  const id = setInterval(() => {
    setSeconds((prev) => prev + 1);  // ✅ no variable captured
  }, 1000);
  return () => clearInterval(id);
}, []);
```

**Why it fixes it?**
- `prev` is provided by React from its internal storage — whatever the latest state is, it comes through `prev`
- Only `setSeconds` itself is captured, which is a stable React function
- No external variable is captured, so no stale closure issue

**Comparison:**

| Code | What happens | Problem? |
|---|---|---|
| `setSeconds(seconds + 1)` | captures `seconds` variable → 0 | Stale closure ❌ |
| `setSeconds(prev => prev + 1)` | no variable captured, `prev` from React | ✅ |

</details>

Q: Write a Countdown Timer app using useEffect, cleanup function, and dependency array. With Set, Start, Pause, Reset buttons.

<details>
<summary>Sample Answer</summary>

```tsx
import { useState, useEffect } from "react";

function CountdownApp() {
  const [timeLeft, setTimeLeft] = useState(0);
  const [isRunning, setIsRunning] = useState(false);
  const [initial, setInitial] = useState(10);

  // Timer effect — only runs when isRunning is true
  useEffect(() => {
    if (!isRunning) return;
    const id = setInterval(() => {
      setTimeLeft((prev) => {
        if (prev <= 1) {
          setIsRunning(false);
          return 0;
        }
        return prev - 1;
      });
    }, 1000);
    return () => clearInterval(id);  // cleanup on unmount or re-run
  }, [isRunning]);

  // Time up detection
  useEffect(() => {
    if (timeLeft === 0 && isRunning) {
      setIsRunning(false);
      alert("Time's up! 🛎️");
    }
  }, [timeLeft, isRunning]);

  return (
    <div>
      <h1>Countdown: {timeLeft}s</h1>
      <input
        type="number"
        value={initial}
        onChange={(e) => setInitial(Number(e.target.value))}
      />
      <button onClick={() => { setTimeLeft(initial); setIsRunning(false); }}>
        Set
      </button>
      <button onClick={() => setIsRunning(true)} disabled={isRunning || timeLeft <= 0}>
        Start
      </button>
      <button onClick={() => setIsRunning(false)} disabled={!isRunning}>
        Pause
      </button>
      <button onClick={() => { setTimeLeft(0); setIsRunning(false); }}>
        Reset
      </button>
    </div>
  );
}
```

**Key concepts used:**
- `useEffect` with `[isRunning]` — timer only runs when isRunning is true, cleanup stops it on pause
- Functional update `setTimeLeft(prev => ...)` — prevents stale closure
- Cleanup `clearInterval(id)` — stops timer on unmount or re-run
- Second `useEffect` — detects time up and shows alert

</details>
