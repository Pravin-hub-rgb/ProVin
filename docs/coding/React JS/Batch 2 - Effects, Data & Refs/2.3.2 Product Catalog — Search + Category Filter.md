## Goal

We'll build a **Product Catalog** — a grid of products with a search box on top and a row of category pills. Type "phone", hit Search, and the grid swaps to phone results. Tap the "laptops" pill, and the grid swaps to that category. Clear it, and you land back on the default catalog.

You already wrote this exact app in **2.3** — same search box, same two-states pattern, same `enabled` idea. The only things that change are the API (**DummyJSON** instead of MealDB), the data shape, and the UI. That's deliberate. The skill this week isn't "learn React Query again" — it's seeing that the pattern **transfers to any server**: different URL, different JSON, same two hooks doing the same jobs.

We'll use a new fake-but-real API, no key required:

```text
GET https://dummyjson.com/products?limit=12              → { products: [...], total: 194 }
GET https://dummyjson.com/products/search?q=phone&limit=12   → { products: [...], total: 23 }
GET https://dummyjson.com/products/categories            → [ { "slug": "laptops", "name": "Laptops", ... }, ... ]
GET https://dummyjson.com/products/category/laptops?limit=12 → { products: [...] }
```

Same project setup as 2.3: Vite + TypeScript called `product-catalog`, `bun add @tanstack/react-query`, and `main.tsx` with `<QueryClientProvider>` already wired.

## Step 3 — The Default Catalog (First `useQuery`)

**Think:** Replace the hardcoded array with the real thing — the default `/products` list. This is where we also prove the JSON wrapper: the response is `{ products: [...], total, skip, limit }`, not a bare array, so the `queryFn` must pluck `.products`.

```tsx
import { useQuery } from "@tanstack/react-query";

interface DummyProduct {
  id: number;
  title: string;
  price: number;
  thumbnail: string;
  category: string;
  rating: number;
}

function ProductCatalog() {
  const { data: products, isLoading, isError, error } = useQuery({
    queryKey: ["products"],
    queryFn: async () => {
      const res = await fetch("https://dummyjson.com/products?limit=12");
      if (!res.ok) throw new Error("Failed to load products");
      const json = await res.json();
      return json.products as DummyProduct[];
    },
  });

  if (isLoading) return <p>Loading products...</p>;
  if (isError) return <p>Error: {error.message}</p>;

  return (
    <div>
      <h1>Product Catalog</h1>
      <form>
        <input placeholder="Search products (e.g. phone)..." />
        <button type="submit">Search</button>
      </form>
      <div className="grid">
        {products.map((p) => (
          <div key={p.id} className="card">
            <img src={p.thumbnail} alt={p.title} width={120} />
            <p>{p.title}</p>
            <p>${p.price} · ★{p.rating}</p>
          </div>
        ))}
      </div>
    </div>
  );
}
```

**Test:** Reload → 12 real products appear with `title`, `price`, and rating. Network tab shows a single `products?limit=12` request. ✅

## Step 4 — Category Pills (Second `useQuery`, Key Changes)

**Think:** The pills come from the server too — `/products/categories`. Fetch once at mount with `["categories"]`, then render one pill per category (first six, so the row stays readable) plus an "All" pill. Clicking a pill must do two things: (1) switch the grid to that category, (2) make sure the search box doesn't fight it — we clear the search input.

```tsx
import { useState } from "react";
import { useQuery } from "@tanstack/react-query";

interface DummyProduct { /* same as Step 3 */ }
interface DummyCategory { slug: string; name: string; url: string }

function ProductCatalog() {
  const [category, setCategory] = useState("all");
  const [searchInput, setSearchInput] = useState("");
  const [query, setQuery] = useState("");

  const categoriesQuery = useQuery({
    queryKey: ["categories"],
    queryFn: async () => {
      const res = await fetch("https://dummyjson.com/products/categories");
      if (!res.ok) throw new Error("Failed to load categories");
      return res.json() as Promise<DummyCategory[]>;
    },
  });

  const productsQuery = useQuery({
    queryKey: ["products", query, category],
    queryFn: async () => {
      const url = query
        ? `https://dummyjson.com/products/search?q=${encodeURIComponent(query)}&limit=12`
        : category === "all"
          ? "https://dummyjson.com/products?limit=12"
          : `https://dummyjson.com/products/category/${category}?limit=12`;
      const res = await fetch(url);
      if (!res.ok) throw new Error("Failed to load products");
      const json = await res.json();
      return json.products as DummyProduct[];
    },
  });

  function handleSearch(e: React.FormEvent<HTMLFormElement>) {
    e.preventDefault();
    setQuery(searchInput.trim());
    setCategory("all");
  }

  function handleCategory(slug: string) {
    setCategory(slug);
    setQuery("");
    setSearchInput("");
  }

  // ...isLoading/isError checks for BOTH queries before JSX...

  return (
    <div>
      <h1>Product Catalog</h1>
      <form onSubmit={handleSearch}>
        <input value={searchInput} onChange={(e) => setSearchInput(e.target.value)} placeholder="Search products..." />
        <button type="submit">Search</button>
      </form>

      <div className="pills">
        <button onClick={() => handleCategory("all")} className={category === "all" && !query ? "active" : ""}>All</button>
        {categoriesQuery.data?.slice(0, 6).map((c) => (
          <button key={c.slug} onClick={() => handleCategory(c.slug)} className={category === c.slug ? "active" : ""}>
            {c.name}
          </button>
        ))}
      </div>

      <div className="grid">
        {productsQuery.data?.map((p) => (
          <div key={p.id} className="card">
            <img src={p.thumbnail} alt={p.title} width={120} />
            <p>{p.title}</p>
            <p>${p.price} · ★{p.rating}</p>
          </div>
        ))}
      </div>
    </div>
  );
}
```

Line by line on the new parts:

- **The two-states pattern is back, deliberately.** `searchInput` = what the user is typing right now; `query` = the last thing submitted. The form submit flips the switch. Every Recipe Finder muscle memory from 2.3 applies exactly as it was.
- **`["products", query, category]`** — a queryKey can carry more than one changing value. Whatever combination of "what the user searched" + "which pill is active" fully describes *what the user wants* — and that whole triple is the fingerprint. `["products", "", "all"]` ≠ `["products", "phone", "all"]` ≠ `["products", "", "laptops"]` — three different cache entries.
- **`encodeURIComponent(query)`** — real user input goes into a URL. If someone searches "salt & pepper", the raw `&` would be interpreted as a parameter separator. `encodeURIComponent` turns it into `%26`. Any time you stick user text into a URL this way — never raw.
- **`handleCategory` resets `searchInput` and `query`** — so pill-clicking and searching can never both be active at once. Search always wins over pills (`if (query)` branch first), and clicking a pill always clears the search. One source of truth, one branch order, predictable UI.
- **`slice(0, 6)`** — DummyJSON ships 25 categories. First six keeps the pill row on one line; feel free to raise it, nothing depends on six.

**Test:**
1. Page loads → default products + category pills in the row. (One request to `/products/categories`, one to `/products?limit=12` — both fire once.)
2. Click "Laptops" pill → grid switches to laptops (`/products/category/laptops?limit=12`). Click "All" → default grid returns. ✅
3. Type "phone" → click Search → grid swaps to phone-search results (`/products/search?q=phone&limit=12`). The pills clear their active state. ✅
4. Search "salt & pepper" → watch the Network tab, URL shows `salt%20%26%20pepper` — encoded. ✅
5. Search "phone" → click "Laptops" pill → you're back to the laptops catalog, not a mix. ✅

## The Interesting Part — One Hook, Three URLs

Here's the thing to notice, because it's the whole lesson of this project: **`useQuery` never knew which endpoint you were hitting.** The URL lives inside `queryFn` — the branch is plain JavaScript. The hook's job is only: this key changed → run the function → give me loading/error/data states. Where the data comes from is your function's problem, not the hook's.

That's why the pattern "transfers to any server": swap the URLs, keep everything else. The recipe search in 2.3 and this product search are the same two hooks in / out doorway — different rooms.

## Common Mistakes

1. **Searching without `encodeURIComponent`** — `&` or `%` in the input corrupts the URL silently. The server just returns wrong (or empty) results.
2. **Query and pill fighting each other** — if both `query` and `category` are live and your branch order is "search wins", then clicking a pill that doesn't clear `query` does *nothing* visible. Reset one when the other activates.
3. **`category` hardcoded in the queryKey but not in the queryFn branch** — key says `laptops`, fetch still goes to `/products?limit=12`. The key is the label; the function is the truth — keep them in sync, always.
4. **This grid trying to load all 194 products** — `limit=12` is deliberate UI sense, not laziness. A catalog page doesn't need everything; it needs *something fast*.
5. **Forgetting the category objects are `{slug, name}` not bare strings** — `c.name` for the label, `c.slug` for the URL. Hardcoding `"laptops"` as a pill label works only until the server renames `slug`.

## What It Is NOT

- **NOT a shopping cart.** The grid renders products; add/remove-to-cart state is local client state (`useState`) and never talks to the network here.
- **NOT two-step filtering built into the server.** DummyJSON has no "AND" query — searching inside a category isn't a thing — so the app clears one mode when the other activates. That's our UI choice, not React Query magic.
- **NOT totals/counts.** We ignore `total` and `skip` from the response for now (pagination is the next project — 2.3.3).
- **NOT a second Recipe Finder.** It shares the pattern on purpose — same two hooks, new server — that's the transfer-of-pattern lesson.

## In Your Own Words

1. Why does the queryKey carry BOTH `query` and `category`?

<details>
<summary>Sample Answer</summary>

Because the grid shows what the *combination* asks for, not either alone. `["products", "phone", "all"]` is a different screen than `["products", "", "laptops"]` — same hook, different cache entries, different requests, different data. Each fingerprint = one exact picture of "what the user wants right now".
</details>

2. Why does submitting the search clear the selected pill?

<details>
<summary>Sample Answer</summary>

So only one "question" is ever active. Recipe-finder-style searching and pill-browsing both want to own the URL branch. If the search is live and someone clicks a pill without clearing it, the visible UI would be inconsistent with what `["products", query, category]` fingerprint actually fetched — promise broken by code, not by React.
</details>

3. Where does `encodeURIComponent` protect us, and what exactly happens without it?

<details>
<summary>Sample Answer</summary>

It encodes user input that goes into a URL. Searching "salt & pepper" — the raw `&` would split the query string into two parameters: `q=salt ` and ` pepper`. The server would return nonsense with no error from React Query at all. Encoding turns `&` into `%26` so it's treated as part of the search term.
</details>

4. How does one `useQuery` end up fetching from three different URLs without anyone calling three hooks?

<details>
<summary>Sample Answer</summary>

The URL is assembled inside `queryFn` — a plain function the hook calls whenever the key changes. The hook doesn't know or care what the URL is. It only compares keys: same key → reuse cache and render; different key → run the function again. The branch inside the function is the whole "magic" — three URLs, one entry point.
</details>

5. What's the benefit of the categories coming from the server instead of a hardcoded list of pill labels?

<details>
<summary>Sample Answer</summary>

It can't go stale. DummyJSON can add or rename categories tomorrow — a hardcoded pill row would silently offer categories that 404, or never offer new ones. The server is the source of truth for the server's own taxonomy; one `["categories"]` fetch keeps the UI honest forever.
</details>
