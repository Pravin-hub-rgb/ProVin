
## MCQ

Q: Which built-in function do you use to make an API call in React?
A. `fetch()` — browser's built-in function that makes network requests
B. `axios()` — React's built-in HTTP library that comes with the project
C. `getJSON()` — JavaScript's built-in function that parses JSON directly
D. `request()` — Node.js style function that also works in the browser
> A. `fetch()` is a browser built-in API — it has no connection to React. It's a direct part of the browser's JavaScript engine. You use the exact same thing inside React apps. No extra library to install.

---

Q: What does the `fetch()` function return?
A. An already-parsed JavaScript object — data is ready to use immediately
B. A Promise — which will eventually resolve and give you the response
C. A string — containing the response in JSON format
D. A callback function — that fires automatically when the response arrives
> B. `fetch()` returns a Promise. A Promise is an object representing a value that may be available now, or in the future, or never. `await` waits for that Promise to resolve — then you get the actual Response object.

Q: Inside which type of function can you use the `await` keyword?
A. Only regular functions — `async` is optional
B. Only `async` functions — `await` is only allowed inside async
C. Any function — `await` is a global keyword that works everywhere
D. Only arrow functions — regular functions don't support `await`
> B. `await` can only be used inside `async` functions. This is a JavaScript syntax rule. `async` marks a function as "time-consuming work happens here, and `await` can be used inside."

---

Q: What does `res.json()` return?
A. A JavaScript object — parsed immediately without waiting
B. A Promise — because reading the response body may take time
C. A string — JSON text that must be manually parsed
D. A number — the HTTP status code of the response
> B. `res.json()` also returns a Promise. Reading the response body may take time (if data is large or network is slow). That's why `await` is needed there too. Full chain: `const res = await fetch(url)` → `const data = await res.json()`.

Q: If the API returns `meals: null` when no recipe is found, what does `data.meals ?? []` mean?
A. If `data.meals` is null, return empty array; otherwise return the meals array
B. If `data.meals` is empty (length 0), return null; otherwise return original value
C. `??` always sets a default value regardless of what's on the left
D. This syntax causes a TypeScript error — can't null-check this way
> A. `??` (nullish coalescing) means: "if the left side is null or undefined, use the right side." `data.meals ?? []` — if API returns null, use empty array; otherwise use the actual array. It differs from `||` because `??` only triggers on null/undefined, not on empty string (""), 0, or false.

Q: How do you disable a button while loading to prevent the user from making multiple fetches?
A. `<button lock={isLoading}>` — lock prop prevents clicks
B. `<button disabled={isLoading}>` — disabled attribute prevents clicks when true
C. `<button prevent={isLoading}>` — prevent prop avoids double clicks
D. `<button loading={isLoading}>` — loading state auto-disables the button
> B. `disabled={isLoading}` — when `isLoading` is true, the button becomes disabled. The user can't click repeatedly. The button text is also changed — `{isLoading ? "Searching..." : "Search"}` — so the user gets feedback that the click was registered.

Q: Where is the safest place to call `setIsLoading(false)`?
A. Only inside the try block — turning off loading after success makes sense
B. Only inside the catch block — turn off loading after an error
C. In the finally block — loading always turns off, whether success or error
D. In both try and catch separately — finally is redundant
> C. The finally block runs no matter what — whether `try` succeeded or `catch` triggered. If `setIsLoading(false)` is only in `try` and an error occurs, loading stays `true` forever — spinner keeps spinning. Finally ensures loading always turns off, no matter what happens.

Q: How do you correctly use an async function inside useEffect for API fetching?
A. `useEffect(async () => { const data = await fetch(url) }, [])` — pass async callback directly
B. `useEffect(() => { async function fn() { await fetch(url) }; fn(); }, [])` — define inside, then call
C. `useEffect(() => { await fetch(url) }, [])` — await works without async keyword
D. `useEffect(() => { return async () => { await fetch(url) } }, [])` — return the async cleanup
> B. `useEffect`'s callback expects to return either `undefined` or a cleanup function — not a Promise. An `async` function always returns a Promise. So define an async function inside and call it immediately. This is the official recommended pattern.

---

Q: Why check `err instanceof Error` in the catch block?
A. Because `err` in catch blocks is sometimes undefined — check is necessary
B. Because in JavaScript, anything can be thrown — an Error object, a string, a number
C. Because without the check, TypeScript compilation always fails
D. Because fetch errors sometimes have `.message` and sometimes don't
> B. In JavaScript, you can throw anything — `new Error("fail")`, `"some string"`, `42`. `err instanceof Error` checks whether `err` is actually an `Error` instance. If it is, `.message` is safe to use. If not (a string or number was thrown), a fallback message like "Something went wrong" is used.

Q: Why is `meals: Recipe[] | null` defined in the TypeScript interface for the API response?
A. Because the API always returns an array — null is just a type safety exercise
B. Because when a search yields no results, the API returns `meals: null`
C. Because in TypeScript, array types can always be null — it's default behavior
D. Because `| null` makes the property optional — passing meals becomes optional
> B. When a search yields no results (like `?s=xyzzzzz`), the API returns `meals: null`. TypeScript needs to know that `meals` can be null sometimes. If you only wrote `Recipe[]`, then using `data.meals ?? []` would cause a TypeScript error — "cannot assign null to Recipe[]."

- True
- False
> False. `await` can only be used inside `async` functions. This is a JavaScript syntax rule — `await` means "pause here, wait for the Promise to resolve." But the permission to pause is only given to `async` functions.

---

Q: `data.meals ?? []` means — if `data.meals` is null or undefined, return an empty array.
- True
- False
> True. `??` (nullish coalescing) only triggers on null/undefined. If `data.meals` is an empty array (length 0), `??` doesn't trigger — the empty array is returned as-is. This is safer than `||` which also triggers on falsy values like 0, "", false.

---

Q: Putting `setIsLoading(false)` only at the end of try is sufficient — if an error occurs, loading automatically turns off.
- True
- False
> False. If an error occurs, the catch block runs and the rest of try does NOT execute. If `setIsLoading(false)` is only in try, loading stays `true` forever when an error occurs — the spinner never stops. Putting it in `finally` is the safest approach, because finally always runs.

---

Q: `useEffect(async () => { await fetch(url) }, [])` — making the useEffect callback async directly is correct.
- True
- False
> False. `useEffect`'s callback expects to return either `void` or a cleanup function. An `async` function always returns a Promise — not a cleanup function. React cannot treat a Promise as cleanup. The solution is to define an async function inside and call it.

Q: Disabling the button while loading is best practice — prevents the user from triggering multiple fetches.
- True
- False
> True. `disabled={isLoading}` — when a fetch is in progress, the user can't click repeatedly. Multiple fetches would increase server load and potentially make the UI inconsistent. Changing the button text to "Searching..." also gives the user feedback that the click was registered.

## Short Answer

Q: Explain the full flow from button click to displaying data on screen. How do you handle loading, error, and empty states? With code example.

<details>
<summary>Sample Answer</summary>

**States setup:**
```tsx
const [recipes, setRecipes] = useState<Recipe[]>([]);
const [isLoading, setIsLoading] = useState(false);
const [error, setError] = useState<string | null>(null);
```

**Flow — button click to UI:**
```
Button click
  ↓
setIsLoading(true), setError(null)   ← loading starts, error reset
  ↓
try {
  const res = await fetch(url)       ← API call (Promise)
  const data = await res.json()      ← Parse JSON (Promise)
  setRecipes(data.meals ?? [])       ← Store data
} catch (err) {                      ← Network fail / server down
  setError(err instanceof Error ? err.message : "Something went wrong")
  setRecipes([])
} finally {
  setIsLoading(false)                ← Loading off — always runs
}
```

**UI — handling 4 states:**

```tsx
// Loading state — button disable + spinner
<button onClick={handleSearch} disabled={isLoading}>
  {isLoading ? "Searching..." : "Search"}
</button>
{isLoading && <p>⏳ Loading recipes...</p>}

// Error state — red message
{error && <p style={{ color: "red" }}>❌ {error}</p>}

// Empty state — no results
{!isLoading && !error && recipes.length === 0 && (
  <p>No recipes found. Try a different search.</p>
)}

// Success state — recipe grid
{recipes.length > 0 && recipes.map(recipe => (
  <div key={recipe.idMeal}>
    <img src={recipe.strMealThumb} alt={recipe.strMeal} />
    <h3>{recipe.strMeal}</h3>
    <p>{recipe.strCategory} — {recipe.strArea}</p>
  </div>
))}
```

**Key points:**
- **Loading**: true at fetch start, false at end (in `finally` — safest)
- **Error**: set in catch block, reset to null at fetch start
- **Empty**: `recipes.length === 0` → "No results" message with guard `!isLoading && !error`
- **Button disable**: `disabled={isLoading}` — prevents user spam
- **Nullish coalescing**: `data.meals ?? []` — null-safe

</details>

Q: How do you use useEffect to load initial data on mount? Explain the async function pattern and why you shouldn't make useEffect directly async.

<details>
<summary>Sample Answer</summary>

**useEffect with `[]` for mount fetch:**

```tsx
useEffect(() => {
  const fetchDefault = async () => {
    const res = await fetch(
      "https://www.themealdb.com/api/json/v1/1/search.php?s=chicken"
    );
    const data: SearchResponse = await res.json();
    setRecipes(data.meals ?? []);
  };

  fetchDefault();
}, []);
```

**Why it works:**
- `[]` (empty dependency) — the effect runs only on mount, once
- The component appears on screen and chicken recipes load automatically
- The user doesn't need to search first — initial data is ready

**Async function pattern — why define inside:**

```tsx
// ❌ Wrong — direct async callback
useEffect(async () => {
  const data = await fetch(url);
}, []);

// ✅ Correct — define inside and call
useEffect(() => {
  async function fn() { await fetch(url); }
  fn();
}, []);
```

**Why is direct async wrong?**
- `useEffect`'s callback expects to return either `undefined` or a cleanup function
- An `async` function always returns a `Promise` — not a cleanup function
- React can't treat a Promise as cleanup
- Even if you wrote a cleanup: `useEffect(async () => { ... return () => cleanup }, [])` — the `async` wraps the return in a Promise, so React never gets the cleanup function

**Rule: Never make `useEffect`'s callback `async`. Define an async function inside and call it immediately.**

</details>
