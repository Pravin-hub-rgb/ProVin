# 2.2 Quiz — API Fetching with useEffect

## MCQ

Q: API call karne ke liye React mein kaunsa built-in function use karte hain?
A. `fetch()` — browser ka built-in function hai jo network request karta hai
B. `axios()` — React ki built-in HTTP library hai jo project ke saath aati hai
C. `getJSON()` — JavaScript ka built-in function hai jo seedha JSON parse karta hai
D. `request()` — Node.js style function hai jo browser mein bhi kaam karta hai
> A. `fetch()` browser ka built-in API hai — iska React se koi connection nahi. Yeh seedha browser JavaScript engine ka part hai. React app ke andar bhi yahi use karte hain. Koi extra library install karne ki zaroorat nahi.

---

Q: `fetch()` function kya return karta hai?
A. Ek already-parsed JavaScript object — seedha data use kar sakte ho
B. Ek Promise — jo eventually resolve hoga aur response dega
C. Ek string — jo JSON format mein response contain karti hai
D. Ek callback function — jo response aane par automatically call hota hai
> B. `fetch()` ek Promise return karta hai. Promise ek object hai jo future mein available value ko represent karta hai. `await` us Promise ke resolve hone ka wait karta hai — tab actual Response object milta hai.

---

Q: `await` keyword kis type ke function ke andar use kar sakte hain?
A. Sirf normal function ke andar — `async` keyword optional hai
B. Sirf `async` function ke andar — `await` sirf async mein allowed hai
C. Kisi bhi function mein — `await` ek global keyword hai har jagah kaam karta hai
D. Sirf arrow function ke andar — regular functions mein await nahi lagta
> B. `await` sirf `async` function ke andar use ho sakta hai. Yeh JavaScript ka syntax rule hai. `async` function ko mark karta hai ki "yeh function time lene wala kaam karega aur iske andar `await` use ho sakta hai."

---

Q: `res.json()` kya return karta hai?
A. Ek JavaScript object — turant parsed ho jata hai bina wait kiye
B. Ek Promise — kyunki response body read karna time le sakta hai
C. Ek string — JSON text jise manually parse karna padta hai
D. Ek number — response ka HTTP status code
> B. `res.json()` bhi ek Promise return karta hai. Response body ko read karna time le sakta hai (agar data bada ho ya network slow ho). Isliye iske aage bhi `await` lagana padta hai. Full chain: `const res = await fetch(url)` → `const data = await res.json()`.

---

Q: API response mein agar koi recipe nahi milti toh `meals: null` aata hai. `data.meals ?? []` ka kya matlab hai?
A. Agar `data.meals` null hai toh empty array return karo, nahi toh meals array
B. Agar `data.meals` khali hai (length 0) toh null return karo, nahi toh original value
C. `??` hamesha default value set karta hai chahe koi bhi value ho left side par
D. Yeh syntax TypeScript mein error dega — null check nahi kar sakte is tarah
> A. `??` (nullish coalescing) ka matlab: "agar left side null ya undefined hai, toh right side use karo." `data.meals ?? []` — agar API null return kare toh empty array, nahi toh actual array. Ye `||` se different hai kyunki `??` sirf null/undefined pe trigger hota hai, empty string (""), 0, ya false pe nahi.

Q: Button ko loading ke dauran disable kaise karte hain taake user multiple fetches na kare?
A. `<button lock={isLoading}>` — lock prop button ko click hone se rokta hai
B. `<button disabled={isLoading}>` — disabled attribute true hai toh click nahi ho sakta
C. `<button prevent={isLoading}>` — prevent prop double click avoid karta hai
D. `<button loading={isLoading}>` — loading state button ko auto-disable kar deta hai
> B. `disabled={isLoading}` — jab `isLoading` true hai, button disabled ho jata hai. User baar-baar click nahi kar sakta. Button ka text bhi change karte hain — `{isLoading ? "Searching..." : "Search"}` — taake user ko pata chale ki click register ho gaya.

Q: try/catch/finally mein `setIsLoading(false)` kahan pe daalna safest hai?
A. Sirf try ke andar — success ke baad loading band karna logical hai
B. Sirf catch ke andar — error ke baad loading band karna logical hai
C. Finally block mein — har haal mein loading band hoga, chahe success ho ya error
D. Dono try aur catch mein alag-alag — finally use karna redundant hai
> C. Finally block har haal mein chalega — chahe try success ho ya catch trigger ho. Agar `setIsLoading(false)` sirf try mein daala aur error aaya toh loading hamesha true rahega — spinner atak jayega. Finally ensures loading hamesha band hoga, chahe kuch bhi ho jaye.

Q: `useEffect` ke andar API fetch karne ke liye async function kaise likhna sahi hai?
A. `useEffect(async () => { const data = await fetch(url) }, [])` — seedha async callback do
B. `useEffect(() => { async function fn() { await fetch(url) }; fn(); }, [])` — andar define karo, call karo
C. `useEffect(() => { await fetch(url) }, [])` — async keyword ki zaroorat nahi, await directly use karo
D. `useEffect(() => { return async () => { await fetch(url) } }, [])` — return karo async cleanup
> B. `useEffect` ka callback cleanup function (ya undefined) return karta hai, Promise nahi. `async` function hamesha Promise return karta hai. Isliye andar async function define karo aur turant call karo — `useEffect(() => { async function fn() {...}; fn(); }, [])`. Yeh official pattern hai.

---

Q: Error handling mein `err instanceof Error` kyun check karte hain?
A. Kyunki catch block mein `err` kabhi-kabhi undefined hota hai — check zaroori hai
B. Kyunki JavaScript mein kuch bhi throw ho sakta hai — Error object, string, number — sab kuch
C. Kyunki instanceof check ke bina TypeScript compilation fail karti hai har baar
D. Kyunki fetch ke error mein kabhi `.message` property hoti hai kabhi nahi
> B. JavaScript mein kuch bhi throw kar sakte ho — `new Error("fail")`, `"some string"`, `42`. `err instanceof Error` check karta hai ki kya yeh sach mein `Error` class ka instance hai. Agar hai toh `.message` property safe hai. Agar nahi hai (string/number throw hua), toh fallback `"Something went wrong"` use karte hain.

---

Q: TypeScript interface `SearchResponse` mein `meals: Recipe[] | null` kyun define kiya gaya?
A. Kyunki API hamesha array return karti hai — null sirf type safety exercise ke liye hai
B. Kyunki jab search ka koi result nahi milta, API `meals: null` return karti hai
C. Kyunki TypeScript mein array type hamesha null ho sakta hai — default behaviour hai
D. Kyunki `| null` optional property banata hai — meals pass karna optional ho jata hai
> B. Jab search ka koi result nahi milta (jaise `?s=xyzzzzz`), API `meals: null` return karti hai. TypeScript ko yeh batana zaroori hai ki `meals` kabhi null bhi ho sakta hai. Agar sirf `Recipe[]` likhte toh `data.meals ?? []` use karne par bhi TypeScript error deta — "null assign nahi kar sakte Recipe[] ko."

- True
- False
> False. `await` sirf `async` function ke andar use ho sakta hai. Yeh JavaScript ka syntax rule hai — `await` ka matlab hai "yahan ruko, Promise resolve hone do." Lekin rukne ka permission sirf `async` function ko milta hai.

Q: `data.meals ?? []` ka matlab hai — agar `data.meals` null ya undefined hai, toh empty array return karo.
- True
- False
> True. `??` (nullish coalescing) sirf null/undefined pe trigger hota hai. Agar `data.meals` empty array hai (length 0), toh `??` trigger nahi hoga — empty array hi return hoga. Yeh `||` se safe hai kyunki `||` falsy values (0, "", false) pe bhi trigger hota hai.

---

Q: Loading state ko sirf try block ke end mein `setIsLoading(false)` kar dena sufficient hai — error case mein automatically band ho jata hai.
- True
- False
> False. Error case mein catch block chalega, try ka baaki code nahi chalega. Agar `setIsLoading(false)` sirf try mein hai, toh error aane par loading hamesha true rahega — spinner atak jayega. Finally block mein loading off karna safest hai, kyunki finally har haal mein chalta hai.

Q: `useEffect(async () => { await fetch(url) }, [])` — useEffect ke callback ko seedha async banana sahi hai.
- True
- False
> False. `useEffect` ka callback cleanup function (ya undefined) return karta hai. Async function hamesha Promise return karta hai — cleanup function nahi. React Promise ko cleanup treat nahi kar sakta. Solution: andar async function define karo aur call karo.

Q: Loading ke dauran button disable karna best practice hai taake user multiple fetches trigger na kar sake.
- True
- False
> True. `disabled={isLoading}` — jab fetch chal raha hai, user baar-baar click nahi kar sakta. Multiple fetches se server par load badhega aur UI inconsistent ho sakta hai. Button text bhi "Search" se "Searching..." change karna user ko feedback deta hai ki click register ho gaya.

## ShortAnswer

Q: Button click se lekar UI mein data dikhne tak ka poora flow explain karo. Loading, error, aur empty states kaise handle karte hain? Code example ke saath samjhao.

<details>
<summary>Sample Answer</summary>

**States setup:**
```tsx
const [recipes, setRecipes] = useState<Recipe[]>([]);
const [isLoading, setIsLoading] = useState(false);
const [error, setError] = useState<string | null>(null);
```

**Flow — Button click se UI tak:**
```
Button click
  ↓
setIsLoading(true), setError(null)   ← loading start, error reset
  ↓
try {
  const res = await fetch(url)       ← API call (Promise)
  const data = await res.json()      ← Parse JSON (Promise)
  setRecipes(data.meals ?? [])       ← Data store
} catch (err) {                      ← Network fail / server down
  setError(err instanceof Error ? err.message : "Something went wrong")
  setRecipes([])
} finally {
  setIsLoading(false)                ← Loading band — har haal mein
}
```

**UI — 4 states handle karna:**

```tsx
// Loading state — button disable + spinner
<button onClick={handleSearch} disabled={isLoading}>
  {isLoading ? "Searching..." : "Search"}
</button>
{isLoading && <p>⏳ Loading recipes...</p>}

// Error state — red message
{error && <p style={{ color: "red" }}>❌ {error}</p>}

// Empty state — no results
{!isLoading && !error && recipes.length === 0 && (
  <p>No recipes found. Try a different search.</p>
)}

// Success state — recipe grid
{recipes.length > 0 && recipes.map(recipe => (
  <div key={recipe.idMeal}>
    <img src={recipe.strMealThumb} alt={recipe.strMeal} />
    <h3>{recipe.strMeal}</h3>
    <p>{recipe.strCategory} — {recipe.strArea}</p>
  </div>
))}
```

**Key points:**
- **Loading**: fetch se pehle true, finally mein false (sabse safe)
- **Error**: catch block mein set, fetch shuru pe null karo
- **Empty**: `recipes.length === 0` — no results message with guard `!isLoading && !error`
- **Button disable**: `disabled={isLoading}` — user spam prevent
- **Nullish coalescing**: `data.meals ?? []` — null safe

</details>

Q: `useEffect` mount pe initial data load karne ke liye kaise use karte hain? Async function ka pattern explain karo aur `useEffect` ko seedha async banane se kyun bachna chahiye?

<details>
<summary>Sample Answer</summary>

**useEffect with `[]` for mount fetch:**

```tsx
useEffect(() => {
  const fetchDefault = async () => {
    const res = await fetch(
      "https://www.themealdb.com/api/json/v1/1/search.php?s=chicken"
    );
    const data: SearchResponse = await res.json();
    setRecipes(data.meals ?? []);
  };

  fetchDefault();
}, []);
```

**Kyun kaam karta hai:**
- `[]` (empty dependency) — effect sirf mount pe chalega, ek baar
- Component screen par aate hi chicken recipes load ho jayengi
- User ko kuch search karne ki zaroorat nahi — initial data ready hai

**Async function pattern — kyun andar define karte hain:**

```tsx
// ❌ Galat — seedha async callback
useEffect(async () => {
  const data = await fetch(url);
}, []);

// ✅ Sahi — andar define + call
useEffect(() => {
  async function fn() { await fetch(url); }
  fn();
}, []);
```

**Kyun galat hai seedha async banana?**
- `useEffect` ka callback expect karta hai: ya toh `undefined` return karo, ya cleanup function
- `async` function hamesha ek `Promise` return karta hai — chahe andar `await` ho ya na ho
- React Promise ko cleanup function treat nahi kar sakta
- Agar cleanup likhoge toh bhi issue: `useEffect(async () => { ... return () => cleanup }, [])` — `async` function ne return ko Promise mein wrap kar diya, React ko cleanup nahi milega

**Rule: `useEffect` ke callback ko kabhi `async` mat banao. Andar async function define karo aur turant call karo.**

</details>
