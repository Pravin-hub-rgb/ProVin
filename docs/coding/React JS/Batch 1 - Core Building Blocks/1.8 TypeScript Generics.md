## Where We Left Off

In 1.7, we learned the `useState` hook — storing state and handling events. When we wrote `useState(0)`, TypeScript automatically inferred the type as `number`. But sometimes TypeScript can't infer — that's when we use syntax like `useState<Item[]>([])`. That `<Item[]>` in angle brackets is a **generic**. This chapter starts from the very basics.

## Broader Goal

TypeScript has a powerful feature called **generics**. When the specific type isn't known yet, you can use a generic type variable instead. Think of a function that reverses an array of any type — `number[]`, `string[]`, `User[]` — one function, all types. Generics make this possible.

## Step 1 — Feel the Problem

Think: "I need a function that returns the first element of an array. But the array might contain numbers, strings, objects..."

Without generics, you'd write separate functions:

```typescript
// Just for numbers
function getFirstNumber(arr: number[]): number | undefined {
  return arr[0];
}

// Just for strings
function getFirstString(arr: string[]): string | undefined {
  return arr[0];
}

// Just for booleans
function getFirstBoolean(arr: boolean[]): boolean | undefined {
  return arr[0];
}
```

All three functions do the same thing — only the type differs. Why write them again? You could use `any`:

```typescript
function getFirstAny(arr: any[]): any {
  return arr[0];
}
```

With `any`, TypeScript's entire benefit disappears — no type safety. Pass in a string array, get back a number, and TypeScript won't say anything.

**Solution — Generics:** A pattern where the type itself is a variable. Just as a function parameter accepts a value (`function add(a, b)`), a generic `<T>` accepts a type. The actual type is decided when the function is called.

**Real-world analogy:** A storage box that can hold anything — books, clothes, toys. The box shape stays the same; what's inside changes. Generics work the same way — the code structure stays the same, the type can change.

## Step 2 — Generic Function: First Example

```typescript
function getFirst<T>(arr: T[]): T | undefined {
  return arr[0];
}
```

**Definition — Generics:** A TypeScript feature where `<T>` is a placeholder type. The actual type is decided when the function is called. That's why it's called "generic" — not a specific type, but a general-purpose one.

Here, `<T>` is a **type variable** — just as a function parameter `arr` accepts a value, `<T>` accepts a type. When you call the function, that's when `T`'s actual type gets decided.

```typescript
const firstNum = getFirst<number>([10, 20, 30]);
// T = number → return type number | undefined
// firstNum = 10

const firstStr = getFirst<string>(["a", "b", "c"]);
// T = string → return type string | undefined
// firstStr = "a"

const firstBool = getFirst<boolean>([true, false]);
// T = boolean → return type boolean | undefined
// firstBool = true
```

**Line by line:**

1. `function getFirst<T>` — function keyword, name `getFirst`, and `<T>` as a generic type parameter
2. `(arr: T[])` — the function takes a parameter `arr` whose type is `T[]` (an array of T)
3. `: T | undefined` — return type: `T` or `undefined` (when the array is empty)
4. `<number>([10, 20, 30])` — when calling, specify `<number>` to say T = number

Without generics, you'd write three functions. With generics, one function handles all types.

### TypeScript Type Inference with Generics

Writing `<number>` explicitly is fine. But TypeScript can **infer** it:

```typescript
const firstNum = getFirst([10, 20, 30]);
// TypeScript: "[10, 20, 30] → number[] → T = number"
// No need to write <number> explicitly
```

TypeScript looks at the argument `[10, 20, 30]` and infers `T = number`. So `getFirst([10, 20, 30])` works without writing `<number>`.

```typescript
const firstStr = getFirst(["x", "y"]);  // infers → string
const firstBool = getFirst([true]);      // infers → boolean
```

Inference works when TypeScript can deduce the type from actual values. For complex cases, you need to specify a generic explicitly — like `useState<User | null>(null)` in React.

### Breakdown

```
function getFirst<T>(arr: T[]): T | undefined {
      //            ↑     ↑       ↑
      //            |     |       return type: T or undefined
      //            |     parameter: T array
      //            generic type parameter
  return arr[0];
}

getFirst<number>([10, 20, 30])
//       ↑
//       explicit: T = number
```

### Common Variable Names for Generics

| Variable | Meaning |
|----------|---------|
| `T` | Type (default, most common) |
| `U` | a second type |
| `V` | a third type |
| `TItem` | meaningful name (array item type) |

In React, you'll see this: `ChangeEvent<HTMLInputElement>` — `<HTMLInputElement>` is the specific type replacing `<T>`.

## Step 3 — T Accepts Any Type

So far `T` could be anything — number, string, boolean, object, array. What if you want to **restrict** `T` to only types with certain properties? Like "only types that have a `.length` property."

When you need that, use **constraints**:

```typescript
function getLength<T extends { length: number }>(item: T): number {
  return item.length;
}
```

`T extends { length: number }` means "T can only be a type that has a `length: number` property." Strings and arrays both have `length`:

```typescript
getLength("Hello");      // 5 — strings have length
getLength([1, 2, 3]);    // 3 — arrays have length
// getLength(123);       // ❌ Error – numbers don't have length
```

**For now, that's enough to know.** Generics are used mainly in event handlers in React — `ChangeEvent<HTMLInputElement>` where `HTMLInputElement` is the specific DOM element type as the generic parameter.

## Step 4 — Multiple Type Parameters

A function can have more than one generic parameter:

```typescript
function pair<T, U>(first: T, second: U): [T, U] {
  return [first, second];
}

const result = pair<string, number>("age", 25);
// result = ["age", 25] — type: [string, number]
```

TypeScript can also infer this:

```typescript
const result = pair("age", 25);  // infers → [string, number]
```

Multiple generics are rare in React. Most of the time there's just one generic parameter — `useState<T>`, `useRef<T>`, `ChangeEvent<T>`.

## Step 5 — Generics in TypeScript Types (Interfaces)

Generics aren't just for functions — they work with types and interfaces too:

```typescript
interface Box<T> {
  value: T;
}

const numberBox: Box<number> = { value: 42 };
const stringBox: Box<string> = { value: "hello" };
```

`Box<T>` is a generic interface. `T` can be any type. This is common in React — like `Array<T>`, which is actually a generic interface:

```typescript
// These are the same thing:
const nums1: number[] = [1, 2, 3];
const nums2: Array<number> = [1, 2, 3];
```

`number[]` is shorthand for `Array<number>`. TypeScript generics appear everywhere in React — let's see them in component types now.

## Step 6 — Generics in React

React uses generics extensively. Here are some common examples.

### First, Understand – T Can Be Simple or Complex

In Step 2, we saw `getFirst<number>` → T = number, `getFirst<string>` → T = string. Both simple types.

But **T can be any type** — simple or complex:

```typescript
// T = number[] (array of numbers)
getFirst<number[]>([1, 2, 3]);

// T = Item[] (array of Items) – Item is an interface
interface Item {
  id: number;
  text: string;
}
getFirst<Item[]>([{ id: 1, text: "Hello" }]);

// T = string | null (union type)
getFirst<string | null>([null, "a", null]);
```

Same `<T>` syntax, but `T` can be an array, object, union type – anything.

### useState

Same pattern in `useState`:

```typescript
// T = number – same as getFirst<number>
const [count, setCount] = useState(0);

// T = string – same as getFirst<string>
const [name, setName] = useState("");

// T = Item[] – (Item interface defined in "First, Understand")
const [items, setItems] = useState<Item[]>([]);
```

When the initial value makes the type clear (`useState(0)` → number), inference works. When it's complex (empty array, nullable value), you need an explicit generic type:

```typescript
interface User {
  id: number;
  name: string;
}

const [user, setUser] = useState<User | null>(null);
// null alone can't tell TypeScript that User type is expected
```

### Event Types

```typescript
const handleChange = (event: React.ChangeEvent<HTMLInputElement>) => {
  // ChangeEvent<HTMLInputElement> – generic type
  // HTMLInputElement is the specific DOM element type
};
```

`React.ChangeEvent<T>` is a generic type. `<HTMLInputElement>` is the specific type telling you which DOM element triggered the event. `HTMLTextAreaElement`, `HTMLSelectElement`, `HTMLFormElement` — these are all specific DOM element types used as the generic parameter.

### T's Flow – Recap

```
getFirst<number>           → T = number
getFirst<string>           → T = string
getFirst<Item[]>           → T = Item[]
useState<number>(0)        → T = number       (same pattern)
useState<Item[]>([])       → T = Item[]       (same pattern)
ChangeEvent<HTMLInputElement> → T = HTMLInputElement  (same pattern)
```

At this point in Batch 1, generics appear in three places — `useState<T>`, `ChangeEvent<T>`, and `Array<T>` (which is the alternative syntax for `T[]`).

## Step 7 — Generics vs Inference: When to Use What

| Situation | Need Generics? | Example |
|-----------|----------------|---------|
| Initial value makes type clear | ❌ Inference is enough | `useState(0)` |
| Empty array – type unclear | ✅ Explicit generic | `useState<Item[]>([])` |
| Null/undefined as initial value | ✅ Explicit generic | `useState<User \| null>(null)` |
| Function accepting any type | ✅ Generic function | `getFirst<T>(arr: T[])` |
| Event handler – specific element | ✅ Generic type | `ChangeEvent<HTMLInputElement>` |
| Simple prop types | ❌ Regular interface | `interface Props { name: string }` |

## Summary

- **Generics** – a type variable that becomes a specific type when used
- **Syntax:** `<T>` – angle brackets + type variable name
- **Conventions:** `T`, `U`, `V` or meaningful names like `TItem`
- **Functions:** `function name<T>(arg: T): T`
- **Types/Interfaces:** `interface Box<T> { value: T }`
- **React:** `useState<T>()`, `ChangeEvent<T>`, `Array<T>`
- **Inference** – TypeScript deduces the type automatically (usually enough)
- **Explicit** – needed when inference isn't enough (empty arrays, nullable values)
- **Constraints:** `T extends { length: number }` – restricts what T can be

## Mini-Project 1 – Explicit `useState` Practice

Think: "In 1.7 we wrote `useState(0)` and TypeScript inferred the type as `number`. But that only works when the initial value makes the type clear. What happens when it doesn't — like `useState(null)` or `useState([])`?"

**Goal:** Build an app with three state variables — one using inference, two using explicit generics. We'll see when inference works and when you need to write the type explicitly.

### What We're Building

The app has three sections:

| Section | State Type | Initial Value | UI |
|---------|-----------|---------------|-----|
| Name | `string` | `""` | Input + display text |
| Nickname | `string \| null` | `null` | Input + "(not set)" when empty |
| Tags | `string[]` | `[]` | Input + Add button + comma-separated list |

**Final UI looks like:**

```
┌─────────────────────────────────┐
│  useState Type Practice          │
│                                   │
│  Inference (state = "")          │
│  [Enter name...]                  │
│  Name: "John"                     │
│                                   │
│  Explicit (state = string | null) │
│  [Enter nickname...]              │
│  Nickname: (not set)              │
│                                   │
│  Explicit (state = string[])      │
│  [Enter tag...] [Add Tag]         │
│  Tags: react, typescript          │
└─────────────────────────────────┘
```

Let's build it step by step.

### Step 1 – Inferring State

The simplest case: the initial value makes the type clear.

```tsx
import { useState } from "react";

function App() {
  const [name, setName] = useState(""); // TypeScript: initial value "" → infer → string

  return (
    <div>
      <input value={name} onChange={(e) => setName(e.target.value)} placeholder="Name" />
      <p>Name: "{name}"</p>
    </div>
  );
}
```

**Why does this work?** `""` is a string. TypeScript sees it and infers "this state will always be type string." Inference works. For simple values, you don't need to write `<string>` explicitly.

### Step 2 – Null as Initial Value – Need Explicit Generic

Think: "What happens if the initial value is `null`?"

```tsx
const [nickname, setNickname] = useState(null); // infer → null
```

From `null`, TypeScript infers the type is just `null` — nothing else. You can't assign a string. That's a problem.

**Solution:** Provide an explicit generic — tell TypeScript "yes, the initial value is null, but this can also be a string":

```tsx
const [nickname, setNickname] = useState<string | null>(null);
//      ↑                          ↑
//      state type                 explicit: string or null allowed
```

`<string | null>` means "T = string | null." It's a union type — both are allowed. Now you can set either:

```tsx
<input
  value={nickname ?? ""}
  onChange={(e) => setNickname(e.target.value || null)}
  placeholder="Nickname"
/>
```

`e.target.value || null` – if the value is empty, set null; otherwise set the string. TypeScript won't complain because the type is `string | null`.

**UI behavior:** Type in the input → nickname displays. Clear the input → "(not set)" shows (because it became null).

### Step 3 – Empty Array – Need Explicit Generic

Think: "What about an empty array? `useState([])`?"

```tsx
const [tags, setTags] = useState([]); // infer → never[]
// never[] means: "empty array that can never hold anything"
```

`never[]` means you can't put anything in the array. That's wrong.

**Solution:** Specify explicitly that this is a `string[]`:

```tsx
const [tags, setTags] = useState<string[]>([]); // T = string[]
```

**Now let's build the UI.** We need an input + button – the user types, clicks Add, and the tag gets added to the list. The list renders as comma-separated below.

```tsx
const [inputTag, setInputTag] = useState("");

const handleAddTag = () => {
  if (inputTag.trim() === "") return;
  setTags([...tags, inputTag.trim()]);
  setInputTag(""); // clear input after add
};

return (
  <div>
    <input
      value={inputTag}
      onChange={(e) => setInputTag(e.target.value)}
      placeholder="Enter a tag..."
    />
    <button onClick={handleAddTag}>Add Tag</button>
    <p>Tags: {tags.join(", ") || "(empty)"}</p>
  </div>
);
```

**How it works:**

1. User types "react" in input → `inputTag` state updates
2. Click Add Tag → `handleAddTag` runs
3. `inputTag.trim()` checks if it's empty
4. `setTags([...tags, inputTag.trim()])` – spread the old array, add new tag
5. `setInputTag("")` – clears the input field
6. `tags.join(", ")` – joins all array strings with commas for display

**UI flow:**

```
[Enter a tag...] [Add Tag]    ← inputTag=""
User types "react"
[react] [Add Tag]              ← inputTag="react"
User clicks Add Tag
[Enter a tag...] [Add Tag]     ← inputTag="" (cleared)
Tags: react                     ← tags=["react"] displayed
```

### Final Code – Mini-Project 1

```tsx
import { useState } from "react";

export default function App() {
  // ✅ Inference – initial value "" makes the type clear

  const [nickname, setNickname] = useState<string | null>(null);

  // ✅ Explicit – <string[]> because [] infers "never[]"
  const [tags, setTags] = useState<string[]>([]);

  const [inputTag, setInputTag] = useState("");

  const handleAddTag = () => {
    if (inputTag.trim() === "") return;
    setTags([...tags, inputTag.trim()]);
    setInputTag("");
  };

  return (
    <div>
      <h2>1. useState Type Practice</h2>

      <div>
        <h3>Inference (state = "")</h3>
        <input value={name} onChange={(e) => setName(e.target.value)} placeholder="Name" />
        <p>Name: "{name}"</p>
        <small>TypeScript inferred: string</small>
      </div>

      <div>
        <h3>Explicit (state = string | null)</h3>
        <input
          value={nickname ?? ""}
          onChange={(e) => setNickname(e.target.value || null)}
          placeholder="Nickname"
        />
        <p>Nickname: {nickname ?? "(not set)"}</p>
        <small>TypeScript expects: string | null</small>
      </div>

      <div>
        <h3>Explicit (state = string[])</h3>
        <input
          value={inputTag}
          onChange={(e) => setInputTag(e.target.value)}
          placeholder="Enter a tag..."
        />
        <button onClick={handleAddTag}>Add Tag</button>
        <p>Tags: {tags.join(", ") || "(empty)"}</p>
        <small>TypeScript expects: string[]</small>
      </div>
    </div>
  );
}
```

### Test

1. Type in the name input → value updates, displays below
2. Clear the nickname input → "(not set)" shows. Type something → value displays
3. Type "react" in tags input → click Add Tag → "react" appears in the list. Add "typescript" → "react, typescript" displays
4. Open console – three state variables each have different types

## Mini-Project 2 – Recognizing the Generic Pattern

Think: "In Mini-Project 1 we wrote `useState<string | null>` – angle brackets `<...>`, replacing `T`. We also saw `ChangeEvent<HTMLInputElement>` – that also has angle brackets. Is this the same `<T>` pattern? But why do we have to write it? Can't TypeScript auto-detect it?"

Good question. Let's find out.

### Step 1 – Inline `onChange` (TypeScript auto-infers)

When you write the event handler **inline** – right inside the JSX – TypeScript knows it's attached to an `<input>`, so it auto-infers the event type:

```tsx
import { useState } from "react";

function App() {
  const [text, setText] = useState("");

  return (
    <div>
      <input
        value={text}
        onChange={(e) => setText(e.target.value)} // ← TypeScript infers: e: ChangeEvent<HTMLInputElement>
        placeholder="Type here..."
      />
      <p>Text: {text}</p>
    </div>
  );
}
```

**See?** You wrote `(e)` with no type. And it works. TypeScript looks at the `<input>` and infers that `e` has type `ChangeEvent<HTMLInputElement>`. Auto-detected.

**So then:** If it auto-detects inline, when do you need the explicit `<HTMLInputElement>`? When you **extract** the function.

### Step 2 – Extracting the Handler Triggers an Error

Now say you want to pull the inline handler into its own function – for readability:

```tsx
// ❌ TypeScript error – what type is `e`?
const handleInput = (e) => {
  setText(e.target.value);
};
```

**Why the error?** This is a standalone function declaration – it's not attached to an `<input>` yet. TypeScript has no idea when or where this function will be called. So it can't infer `e`'s type.

**Developer thinking:** "But it's the same function I'm using on `<input>`! Why can't it auto-detect?"

**Answer:** TypeScript doesn't look at where functions are *used* – only at where they are *declared*. At declaration time, `e` is an unknown type. That information only becomes available when the function is attached to a specific element.

### Step 3 – Solution: Apply the `<T>` Pattern – Explicit Type

So what do we do? Apply the same `<T>` pattern we learned in Mini-Project 1 – explicitly set `T`'s value:

```tsx
// ✅ Explicit type – ChangeEvent<HTMLInputElement>
// This is the same <T> pattern – T = HTMLInputElement
const handleInput = (e: React.ChangeEvent<HTMLInputElement>) => {
  setText(e.target.value);
};
```

**How does this work?**

`ChangeEvent<T>` is a generic type. It means "this is a change event, but `<T>` takes the specific DOM element type."

| Code | T = | e.target type |
|------|-----|---------------|
| `ChangeEvent<HTMLInputElement>` | `HTMLInputElement` | Input element (value, placeholder, etc.) |
| `ChangeEvent<HTMLTextAreaElement>` | `HTMLTextAreaElement` | Textarea element (value, rows, etc.) |
| `ChangeEvent<HTMLSelectElement>` | `HTMLSelectElement` | Select element (value, options, etc.) |

**So the full code:**

```tsx
import { useState } from "react";

function App() {
  const [text, setText] = useState("");

  const handleInput = (e: React.ChangeEvent<HTMLInputElement>) => {
    setText(e.target.value);
  };

  return (
    <div>
      <input value={text} onChange={handleInput} placeholder="Type here..." />
      <p>Text: {text}</p>
    </div>
  );
}
```

**`e.target` is now `HTMLInputElement` type – that's why `.value` is accessible.**

### Step 4 – Same Pattern, Different T (Textarea)

For a textarea, `T` changes – now it's `HTMLTextAreaElement`:

```tsx
const [bio, setBio] = useState("");

// ChangeEvent<HTMLTextAreaElement> – for textareas
// Same <T> pattern, just T's value changed
const handleTextarea = (e: React.ChangeEvent<HTMLTextAreaElement>) => {
  setBio(e.target.value);
};
```

This is the same `ChangeEvent<T>` generic – just `T = HTMLTextAreaElement`. Now `e.target` gives textarea-specific properties like `rows`, `cols`.

### Step 5 – Same Pattern, Different T (Select)

For a select dropdown, the same pattern – `T = HTMLSelectElement`:

```tsx
const [role, setRole] = useState("user");

// ChangeEvent<HTMLSelectElement> – for dropdowns
const handleSelect = (e: React.ChangeEvent<HTMLSelectElement>) => {
  setRole(e.target.value);
};
```

### Pattern Recognition – At a Glance

Both mini-projects show the angle brackets `<...>` pattern. Three contexts:

| Context | Generic | T's value |
|---------|---------|-----------|
| `useState` – Mini-Project 1 | `useState<T>` | `string`, `string \| null`, `string[]` |
| `ChangeEvent` – Mini-Project 2 | `ChangeEvent<T>` | `HTMLInputElement`, `HTMLTextAreaElement`, `HTMLSelectElement` |
| `Array` – Recap | `T[]` = `Array<T>` | `string`, `number`, etc. |

**Rule:** Wherever you see angle brackets `<...>` – it's a generic. `<T>` is a placeholder. The actual type comes later.

**Inline vs Extracted rule:** Inline, TypeScript auto-infers (works without a type). Extracted function, you need to write the type explicitly.

### Final Code – Mini-Project 2

```tsx
import { useState } from "react";

export default function App() {
  const [text, setText] = useState("");
  const [bio, setBio] = useState("");
  const [role, setRole] = useState("user");

  // ChangeEvent<HTMLInputElement>
  const handleInput = (e: React.ChangeEvent<HTMLInputElement>) => {
    setText(e.target.value);
  };

  // ChangeEvent<HTMLTextAreaElement>
  const handleTextarea = (e: React.ChangeEvent<HTMLTextAreaElement>) => {
    setBio(e.target.value);
  };

  // ChangeEvent<HTMLSelectElement>
  const handleSelect = (e: React.ChangeEvent<HTMLSelectElement>) => {
    setRole(e.target.value);
  };

  return (
    <div>
      <h2>2. ChangeEvent Type Practice</h2>

      <div>
        <h3>Input (ChangeEvent&lt;HTMLInputElement&gt;)</h3>
        <input value={text} onChange={handleInput} placeholder="Type here..." />
        <p>Text: {text}</p>
      </div>

      <div>
        <h3>Textarea (ChangeEvent&lt;HTMLTextAreaElement&gt;)</h3>
        <textarea value={bio} onChange={handleTextarea} placeholder="Your bio..." rows={3} />
        <p>Bio: {bio}</p>
      </div>

      <div>
        <h3>Select (ChangeEvent&lt;HTMLSelectElement&gt;)</h3>
        <select value={role} onChange={handleSelect}>
          <option value="user">User</option>
          <option value="admin">Admin</option>
          <option value="moderator">Moderator</option>
        </select>
        <p>Role: {role}</p>
      </div>
    </div>
  );
}
```

### Test

1. Type in the input → text updates (inline auto-inference works)
2. Type in the textarea → bio updates
3. Change the dropdown → role updates
4. Each handler is extracted – that's why explicit types were needed. Inline, they'd auto-detect.
