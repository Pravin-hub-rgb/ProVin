
## MCQ

Q: What is the purpose of a TypeScript interface?
A. Defines the shape of an object — what properties it has and their types
B. Defines the body of a function — how its code will execute
C. Defines the UI design of a component — how it looks
D. Defines a file's module system — what to export and import
> A. An interface defines an object's "shape" — `{ name: string; age: number }`. TypeScript enforces that any object typed with this interface has exactly those properties with the correct types. A wrong property = compile-time error.

Q: What naming convention do you follow for a props interface?
A. `ComponentNameProps` — append `Props` to the component name — standard convention
B. `PropsComponentName` — prefix with `Props` — the convention
C. `IComponentName` — prefix with `I` — C# style convention
D. No convention — any name works without a pattern
> A. The convention is `ComponentNameProps` — like `ProfileCardProps`, `AlertButtonProps`. It's standard in the React ecosystem. Optional, but makes code easier to read.

Q: What is the correct import syntax for using an interface from another file?
A. `import interface { User } from "./types"` — special keyword with interface
B. `import User from "./types"` — default import without curly braces
C. `import type { User } from "./types"` — type-only import, doesn't enter runtime bundle
D. `import { interface User } from "./types"` — interface keyword in braces
> C. `import type` tells the bundler this is a type-only import. Types are stripped at compile time, so they never enter the runtime bundle — keeping bundle size small.

Q: What are props in React?
A. A global state management system shared across all components
B. Function arguments that pass data from parent component to child
C. A CSS-in-JS library for styling components
D. A browser API that connects React components to native elements
> B. Props work just like function parameters — when you write `<ProfileCard name="Vin" />`, React creates an object `{ name: "Vin" }` and passes it into the component via props.

Q: What is the main difference between inline type and interface?
A. Inline type runs faster at runtime; interface is slower
B. Interface can be reused across multiple places; inline type cannot
C. Inline type only works in class components; interface only in function components
D. Interface only works in TypeScript strict mode; inline type works everywhere
> B. An inline type `(props: { name: string })` can only be used in one component. An interface `interface Props { name: string }` can be `export`ed and imported in other files.

Q: How do you mark a property as optional in an interface?
A. Prefix the property with `opt_` — `opt_name: string`
B. Wrap the property in square brackets — `[name]: string`
C. Add `?` after the property — `role?: string`
D. Add `| undefined` to the type — `role: string | undefined`
> C. `role?: string` — the `?` after the property name makes it optional. If it's not passed, it's `undefined`. Use `||` for a fallback — `props.role || "No role specified"`.

Q: What does destructuring do when used with props?
A. Makes props automatically immutable — they can never be changed
B. Runtime type checking for props
C. Eliminates the need to write `props.` — use the property name directly
D. Improves component performance by reducing re-renders
> C. `function Card({ name, role }: Props)` — now you use `name` and `role` directly, not `props.name`. Destructuring is syntactic sugar — it makes code shorter and more readable.

Q: How do you set default values with destructuring?
A. `function Card({ name, role = "Default" }: Props)` — assign default inside destructuring
B. `function Card({ name, role }: Props = { role: "Default" })` — default the entire props object
C. `function Card(props: Props = { role: "Default" })` — function parameter default value
D. Default values can't be used with destructuring — handle separately
> A. `role = "Default"` — assign a default value right inside the destructuring. If `role` is undefined, this default is used. This is standard practice in professional React code.

Q: What are callback props?
A. Props that run once and then get automatically destroyed
B. Props whose type is a function — the child notifies the parent of something
C. Props that fire automatically at a specific time interval
D. Props that only work in class components, not function components
> B. Props aren't just data (strings, numbers, booleans) — they can also be functions. A callback prop is a function passed as a prop. The child component calls `props.onAlert()` when a button is clicked, and the parent's function runs.

Q: What prefix convention is used for callback props?
A. `handle` prefix — `handleClick`, `handleSubmit`, `handleDelete`
B. `cb` prefix — `cbClick`, `cbSubmit`, `cbDelete`
C. `on` prefix — `onClick`, `onSubmit`, `onDelete` — consistent with React's built-in events
D. `callback` prefix — `callbackClick`, `callbackSubmit`
> C. The `on` prefix — `onClick`, `onAlert`, `onSend` — matches React's built-in events (`onClick`, `onChange`). Just by reading the prop name, you know it's a child → parent callback.

Q: What is the benefit of reusing an interface across multiple functions?
A. Writing separate interfaces for each function provides more type safety
B. Interface reuse keeps consistency — the same type is enforced everywhere
C. Interface reuse significantly improves runtime performance
D. Interface reuse has no practical benefit — inline types are always better
> B. Reusing an interface keeps things consistent — the same `User` interface can be used by 10 different functions. If you change a property in one place, it reflects everywhere. With inline types, you'd have to update each one separately.

B. No — `props` is just a convention; you can use `data`, `p`, or anything else
C. `props` is only required in class components, not function components
D. `props` only works in TypeScript projects, not in plain JavaScript
> B. `props` is just a parameter name, not a keyword. You can name it `data`, `p`, or anything. But the entire industry standard is `props` — when you see `props` in code, you immediately know it's a React component.

Q: For conditional rendering, which operator is used?
A. `{sender && <p>{sender}</p>}` — renders only if `sender` exists
B. `{if (sender) { <p>{sender}</p> }}` — `if` statement with conditional render
C. `{sender ?: <p>{sender}</p>}` — a short form of ternary operator
D. `{sender ?? <p>{sender}</p>}` — nullish coalescing operator for rendering
> A. `{sender && <p>{sender}</p>}` — the JavaScript `&&` operator. When `sender` is undefined or null, React renders nothing. When `sender` has a value, the `<p>` renders. You can't use `if` statements directly in JSX.

Q: What does `() => void` mean as a callback prop type?
A. A function with no parameters that returns nothing — it just does work
B. A function that takes one void parameter and returns nothing
C. A function with no parameters that returns the number 0 by default
D. A function that takes multiple parameters and always returns a string
> A. `() => void` — `()` means no parameters, `void` means no return value. The function just does work — like `alert()`, `console.log()`. `onSend: (message: string) => void` — takes a string parameter, returns nothing.

Q: How does a child component send data back to the parent via callback props?
A. Callback props can't take parameters — the child can only signal, not send data
B. The parent defines the parameter type, and the child passes the value when calling
C. The child can't send data — data always flows from parent to child only
D. The child must make a separate API call to send data back to the parent
> B. The parent defines the callback's parameter type — like `onSend: (message: string) => void`. The child calls it with an actual value — `onSend("Hello from child!")`. The parent's function receives that string as its parameter.

## TrueFalse

Q: Interfaces exist at runtime — the browser executes them when the program runs.
- True
- False
> False. Interfaces are a TypeScript-only, compile-time feature. They don't exist at runtime. The browser executes plain JavaScript — TypeScript strips all types after compilation.

---

Q: The `props` parameter must always be named `props` — nothing else works.
- True
- False
> False. `props` is a convention, not a requirement. You can use `data`, `p`, or any name. The entire industry uses `props` anyway — when you see it, you instantly know it's a React component.

---

Q: If you forget to make an optional property in the interface, a runtime error occurs when the browser runs the code.
- True
- False
> False. The error is caught at compile time, not runtime. TypeScript's superpower is catching these mistakes during development — before the browser ever sees the code.

---

Q: Callback props carry data from the parent component to the child component.
- True
- False
> False. Callback props carry **child → parent** signals. The parent passes a function as a prop. The child calls it when something happens. Regular props carry data **parent → child** (data down). Callback props carry signals **child → parent** (signal up).

---

Q: Destructuring is universal practice in React components — every professional codebase uses it.
- True
- False
> True. Destructuring is standard in React — `function Card({ name, role }: Props)`. No more writing `props.name`, just `name`. Makes code shorter, more readable, and more maintainable.

---

Q: Interface names should be PascalCase nouns — like `User`, `Product`, `ProfileCardProps`.
- True
- False
> True. Interface naming convention: PascalCase (`User`, not `user`), a noun (`Config`, not `configure`). For props interfaces: `ComponentNameProps` — like `ProfileCardProps`, `AlertButtonProps`. These are conventions, not rules — but they're standard in the React ecosystem.

---

Q: Callback props always have the type `() => void` — they can never take parameters.
- True
- False
> False. Callback props can take parameters. `onSend: (message: string) => void` — the parent defines what parameter type the callback accepts. The child passes the actual value when calling — `onSend("Hello from child!")`.

---

Q: `function Card({ name, role }: Props)` and `function Card(props: Props)` both work — the only difference is syntax.
- True
- False
> True. Both do exactly the same thing. Destructuring gives you direct access to `name` and `role`. Without it, you access via `props.name` and `props.role`. Destructuring is just syntactic sugar — shorter and more readable.

## ShortAnswer

Q: What is a TypeScript interface, and how is it used with React props? Explain with an example.

<details>
<summary>Sample Answer</summary>

**An interface** defines the shape of an object — what properties it has and what types they should be.

**Using it with React props:**

```tsx
// 1. Define the interface
interface ProfileCardProps {
  name: string;
  role: string;
}

// 2. Use the interface as the props type
function ProfileCard({ name, role }: ProfileCardProps): JSX.Element {
  return (
    <div>
      <h2>{name}</h2>
      <p>{role}</p>
    </div>
  );
}

// 3. Use the component
<ProfileCard name="Vin" role="React Developer" />
```

**Key points:**
- Name it `ProfileCardProps` — convention is `ComponentNameProps`
- `export interface` lets you reuse it in other files
- `import type { ProfileCardProps }` — it won't enter the runtime bundle
- If you pass the wrong property, TypeScript catches it at compile time — it never reaches the browser
- Inline type vs interface: inline `(props: { name: string })` is fine for tiny props; interface is better for complex, reusable components

</details>

Q: What are callback props, and how does data flow between parent and child? Include the `on` prefix convention with an example.

<details>
<summary>Sample Answer</summary>

**Callback props** are props whose value is a function. When a child component needs to tell its parent something (like a button click), the parent passes a function as a prop, and the child calls it.

**Parent vs Child Flow:**

```
PARENT (App):
  → Defines the handleClick function
  → Passes it to child: onAlert={handleClick}
  → Executes when called by child

CHILD (AlertButton):
  → Receives props.onAlert = handleClick
  → User clicks the button
  → Calls onAlert()
  → Notifies parent: "click happened"
```

**Example:**

```tsx
// Child component
interface AlertButtonProps {
  label: string;
  onAlert: (message: string) => void;
}

function AlertButton({ label, onAlert }: AlertButtonProps) {
  return (
    <button onClick={() => onAlert(`Button "${label}" was clicked!`)}>
      {label}
    </button>
  );
}

// Parent component
function App() {
  const handleAlert = (msg: string) => {
    console.log(msg);
    alert(msg);
  };

  return (
    <div>
      <AlertButton label="Save" onAlert={handleAlert} />
      <AlertButton label="Delete" onAlert={handleAlert} />
    </div>
  );
}
```

**Direction:**
- Regular props: **Parent → Child** (data flows down)
- Callback props: **Child → Parent** (signal flows up)

**`on` prefix convention:** `onClick`, `onAlert`, `onSend` — matches React's built-in events like `onClick`, `onChange`.

</details>
