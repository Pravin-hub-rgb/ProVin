## Where We Left Off

In 1.6, we learned the children prop and composition pattern — built `Card` and `Container` layout components. Everything has been static though — no interactivity. Buttons can be clicked but nothing happens.

## Broader Goal

We'll learn React's most important concept — **state**. Without state, an app can't remember anything. How many times did the user click? Which tasks are complete? All stored in state.

We'll build a Counter mini-project — increment, decrement, reset. We'll also learn event handling with TypeScript typing, and create an input form that's controlled by state.

## Step 1 — Feel the Problem

Think: "Pressing a button increments the count. But when the component re-renders, the variable resets. How do I keep the count?"

Try this in `App.tsx`:

```tsx
function App() {
  let count = 0;

  const handleClick = () => {
    count = count + 1;
    console.log(count); // console: 1, 2, 3...
  };

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={handleClick}>Increment</button>
    </div>
  );
}
```

The count increments in the console, but the screen always shows `Count: 0`. Why?

**The problem:** `let count = 0` is a local variable. Every time the component re-renders, it resets to `0`. React has no idea the value changed, because it's outside React's tracking system.

That's why we need **state** — we need to tell React "track this value, and re-render the component when it changes."

### Before Hooks: What Even is a Hook?

Before `useState`, let's understand **what a hook is in React:**

**A hook** is a special React function that lets you use React's features (like state, lifecycle) inside **function components**. Think of it as "hooking into" React's power.

<details>
<summary><strong>Bonus — Function vs Class Component (History)</strong></summary>

React has two ways to write components:

**1. Function Component (what you've been writing):**
```tsx
function App() {
  return <h1>Hello</h1>;
}
```
A plain JavaScript function. Receives props, returns JSX.

**2. Class Component (the old way):**
```tsx
class App extends React.Component {
  render() {
    return <h1>Hello</h1>;
  }
}
```
A JavaScript class. Extends `React.Component`, returns JSX from a `render()` method.

**Before React 16.8 (2019):**
- Only **class components** could hold state (count, input value, etc.)
- **Function components** were "stateless" — they could only display UI, couldn't remember anything

**React 16.8 introduced hooks:**
- `useState` and friends brought state to function components
- Today, everyone uses **function components + hooks**
- Class components are nearly extinct — you'll only see them in old codebases

You don't need this history for daily work, but it helps to understand why hooks exist.

</details>

### Hook Rules and Conventions

**The `use` prefix:** Every React hook starts with `use`. React uses this naming convention to identify them:
- `useState` — for state
- `useEffect` — for side effects (we'll cover later)
- `useContext` — for context (we'll cover later)

If you write a custom hook, it must also start with `use`. That's a React rule.

**Rules of Hooks (and why):**

1. **Call hooks at the top level** — never inside `if`, `for`, or nested functions.

   **Why:** React internally tracks hooks by **call order**. Every time a component renders, hooks must be called in the same order. If you put one inside an `if`:
   ```tsx
   if (count > 0) {
     useEffect(...);  // ❌ sometimes called, sometimes not — order changes
   }
   ```
   React's internal linked list depends on call order. First render had hooks [A, B, C]. Second render has [A, C] — React thinks hook B's state disappeared. That's why hooks must always be top-level: same order on every render.

2. **Call hooks only from function components or custom hooks** — not from regular JS functions.

   **Why:** React only tracks hooks during the component's render cycle. A regular function isn't tied to React's render lifecycle:
   ```tsx
   function handleClick() {
     const [count, setCount] = useState(0);  // ❌ React doesn't know when this runs
   }
   ```
   React needs to know which component and which render cycle this hook belongs to. That context only exists when a function component is being rendered.

### Analogy: The Electrical Outlet

Think of React's state system as **electrical wiring** in a wall. You don't rewire the house every time you want to plug something in — you use an outlet (plug point).

**Hooks are those outlets:**
- `useState` is an outlet for **state power**
- You call `useState` in your component → you're plugged into React's state system
- You don't implement state yourself — React handles the wiring

```
React [State System]  ←→  useState (outlet)  ←→  Your Component
```

Without `useState`, your component isn't connected to React's state system. That's why a plain `let count = 0` doesn't trigger re-renders.

## Step 2 — The `useState` Hook

**Concept:** `useState` is a React hook that creates a state variable. When the state changes, the component automatically re-renders.

### Step-by-Step

**Step 1 — Call `useState`, pass an initial value:**

```tsx
useState(0)
```

`useState` is a function. You pass it an **initial value** — what shows up on the first render. Here, `0` is the initial value.

**Step 2 — What does `useState` return?**

Calling `useState(0)` returns an **array with two elements**:

```
useState(0) → [0, setterFunction]
                ↑          ↑
                |          setter — the function that updates the value
                |
                current value — whatever initial value you passed
```

- **First element** — the current value (right now it's `0`)
- **Second element** — a function that updates the value (the "setter" function)

**Step 3 — Destructure the array:**

```tsx
const [count, setCount] = useState(0);
```

This is array destructuring — pulling the two elements into separate variables. From 1.5.3, you learned this pattern. Here:

- `count` = current value (0)
- `setCount` = the function that will update `count`
- `useState(0)` = starts at 0

If you don't use array destructuring:

```tsx
const stateArray = useState(0);
const count = stateArray[0];       // first element — current value
const setCount = stateArray[1];    // second element — setter function
```

But destructuring `[count, setCount]` does it in one line. The React community always uses `[value, setValue]` — `count`/`setCount`, `name`/`setName`, `items`/`setItems`.

**Step 4 — Update with the setter:**

```tsx
setCount(count + 1);  // count was 0 → becomes 1
```

`setCount` tells React "the new value is 1." React stores the new value and **re-renders** the component. Now `count` is `1`.

### Full Code

```tsx
import { useState } from "react";   // Step 0 — import

function App() {
  const [count, setCount] = useState(0);   // Step 1-3 — create state

  const handleClick = () => {
    setCount(count + 1);   // Step 4 — update state
  };

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={handleClick}>Increment</button>
    </div>
  );
}
```

**Flow — what happens when you click:**

```
Initial render
  → useState(0) → count = 0
  → Screen: "Count: 0"

Button Click
  → setCount(0 + 1) → count is now 1
  → React re-renders
  → useState() → React remembers count is now 1
  → count = 1
  → Screen: "Count: 1"

Button Click again
  → setCount(1 + 1) → count is now 2
  → React re-renders
  → count = 2
  → Screen: "Count: 2"
```

Before, the count incremented in the console but not on screen (because `let` is local and resets). Now with `useState`, React tracks it and re-renders when it changes.

### Breakdown (One More Time)

| Code | Meaning |
|------|---------|
| `useState(0)` | Create state, initial value is 0 |
| `[count, setCount]` | Array destructuring — `count` (current value), `setCount` (setter) |
| `count` | Current value — display it in the HTML |
| `setCount(count + 1)` | New value — React re-renders the component |

## Step 3 — TypeScript Type Inference

Think: "How did TypeScript know `count` is a `number` from `useState(0)`?"

**Answer:** TypeScript **infers** the type from the initial value. You don't need to write `<number>` explicitly — TypeScript sees the `0` and infers "this is a number."

```tsx
const [count, setCount] = useState(0);
// TypeScript sees: "0 is a number → count is type number"
// setCount now only accepts numbers — you can't pass a string
```

This works automatically:

| Code | TypeScript infers |
|------|-------------------|
| `useState(0)` | `number` |
| `useState("")` (empty string) | `string` |
| `useState("Hello")` | `string` |
| `useState(false)` or `useState(true)` | `boolean` |
| `useState(0.5)` | `number` |

```tsx
const [name, setName] = useState("");       // → string
const [isDone, setIsDone] = useState(false); // → boolean
const [price, setPrice] = useState(99.99);   // → number
```

**Exception — when the initial value can't determine the type:**

```tsx
const [items, setItems] = useState([]); // → never[]
// "never[]" means "empty array, nothing can be added"
```

An empty array's type isn't clear — are the items strings? Numbers? Objects? So you need to specify the type explicitly. We'll cover that soon.

**Rule:** Always start with `useState(0)` or `useState("")` — TypeScript infers the type for you. Only write an explicit type when the initial value doesn't say enough (like empty arrays, nullable values). The `<Type>` generic syntax comes in 1.8 — for now, inference is enough.

## Step 4 — Counter Mini-Project

Think: "Let's build a proper Counter — with increment, decrement, reset, and preventing negative values."

`src/components/Counter.tsx`:

```tsx
import { useState } from "react";

function Counter(): JSX.Element {
  const [count, setCount] = useState(0);   // infer → number

  const increment = () => {
    setCount(count + 1);
  };

  const decrement = () => {
    if (count > 0) {
      setCount(count - 1);
    }
  };

  const reset = () => {
    setCount(0);
  };

  return (
    <div>
      <h2>Counter: {count}</h2>
      <button onClick={increment}>+1</button>
      <button onClick={decrement}>-1</button>
      <button onClick={reset}>Reset</button>
    </div>
  );
}

export default Counter;
```

`App.tsx`:

```tsx
import Counter from "./components/Counter";

function App() {
  return (
    <div>
      <h1>Mini Projects</h1>
      <Counter />
    </div>
  );
}
```

**Event handling breakdown:**

`onClick={increment}` — `onClick` is a prop that accepts a function. When the button is clicked, React calls that function.

If you write:

```tsx
<button onClick={setCount(count + 1)}>+1</button> // ❌ Wrong
```

This calls `setCount` immediately during render — not on click. You always pass a function reference, never call it:

```tsx
<button onClick={() => setCount(count + 1)}>+1</button> // ✅ Correct
```

## Step 5 — TypeScript Event Typing

Think: "The counter has +1, -1, and Reset buttons. But what if the user could type a number directly — like 5, 100, or 42 — instead of clicking +1 fifty times?"

### Step 5a — Add an Input (Just the UI)

Below the buttons, add an input field:

```tsx
<input type="number" placeholder="Set count..." />
```

Check the browser — you see the input. You can type in it. But nothing happens on submit — there's no handler.

### Step 5b — The `onChange` Handler

Think: "As the user types, I need to capture the input."

**Concept — `onChange` event:** HTML elements fire an `onChange` event on every character change. In React, this captures every keystroke from the user.

First, just log to console — verify the event is firing:

```tsx
const handleChange = (event) => {
  console.log(event.target.value);
};
```

Add `onChange={handleChange}` to the `<input>`. Open browser console, type in the input — every character prints to the console.

TypeScript will complain: **Parameter `event` implicitly has an `any` type**. We haven't specified the event type.

### Step 5c — Add the Event Type

React has a specific TypeScript type for every event. For input `onChange`:

```tsx
const handleChange = (event: React.ChangeEvent<HTMLInputElement>) => {
  console.log(event.target.value);
};
```

This type means:
- `ChangeEvent` — React's generic type for "change" events
- `<HTMLInputElement>` — the specific DOM element: an input field

No more TypeScript error. `event.target.value` is the current value of the input — whatever the user is typing.

### Step 5d — Store in State Instead of Console

Think: "The value prints to console. Now I need to store it in state so React re-renders and the screen updates."

**First task:** Create a new state variable for the input value:

```tsx
const [inputValue, setInputValue] = useState("");  // infer → string
```

**Second task:** Update `handleChange` — replace `console.log` with `setInputValue`:

```tsx
// Before: console.log(event.target.value);
// After:
const handleChange = (event: React.ChangeEvent<HTMLInputElement>) => {
  setInputValue(event.target.value);
};
```

Every character change calls `setInputValue` → the state updates → React re-renders.

**Third task:** Make the input **controlled** — add `value={inputValue}`:

```tsx
<input
  type="number"
  value={inputValue}
  onChange={handleChange}
  placeholder="Set count..."
/>
```

Now the input's value is controlled by React state. User types → `handleChange` → `setInputValue` → state updates → React re-renders → input reflects the new value.

This is the **controlled input** pattern — React state is the single source of truth, not the HTML input.

---

**⚠️ Common Mistake — `setCount(event.target.value)`**

You might think: "I want to set the count, so why not just call `setCount` directly with the input value?"

```tsx
// ❌ WRONG — setting count directly from input
const handleChange = (event: React.ChangeEvent<HTMLInputElement>) => {
  setCount(event.target.value);
};
```

It *seems* like it should work. But there's a bug:

- `event.target.value` is always a **string** — even with `type="number"`
- `useState(0)` makes `count` infer as `number`
- You're passing a string → `count` becomes a string

Now `count + 1` becomes string concatenation instead of numeric addition:

| Action | `count` value | Why? |
|--------|----------------|------|
| Typed "5" in input | `"5"` (string!) | `event.target.value` is always string |
| Clicked +1 | `"51"` | `"5" + 1` → concatenation, not addition |
| Clicked +1 again | `"511"` | `"51" + 1` → more concatenation |

**Why a separate state?**

| State | Type | For what? |
|-------|------|-----------|
| `count` | `number` | The actual count value — displayed and used in calculations |
| `inputValue` | `string` | The raw text the user is typing — might be invalid (like "abc") |

Separate states mean the user can type anything in the input, and you only set `count` when the value is validated. We'll do that in Step 5e.

### Step 5e — Set Button

Think: "I need a 'Set' button that takes the number from the input and sets it as the count."

```tsx
const setFromInput = () => {
  const num = parseInt(inputValue, 10);
  if (!isNaN(num)) {
    setCount(num);
    setInputValue("");
  }
};
```

Line by line:
- `parseInt(inputValue, 10)` — converts string "25" to number 25. The `10` is the radix — decimal system
- `!isNaN(num)` — "is Not a Number." Only set if it's a valid number. "abc" → `isNaN` is true → don't set
- `setCount(num)` — update the count
- `setInputValue("")` — clear the input

Add `onClick={setFromInput}` to the button.

### Full Counter Now Looks Like This

```tsx
import { useState } from "react";

function Counter(): JSX.Element {
  const [count, setCount] = useState(0);
  const [inputValue, setInputValue] = useState("");

  const handleChange = (event: React.ChangeEvent<HTMLInputElement>) => {
    setInputValue(event.target.value);
  };

  const setFromInput = () => {
    const num = parseInt(inputValue, 10);
    if (!isNaN(num)) {
      setCount(num);
      setInputValue("");
    }
  };

  return (
    <div>
      <h2>Counter: {count}</h2>
      <button onClick={() => setCount(count + 1)}>+1</button>
      <button onClick={() => setCount(count > 0 ? count - 1 : 0)}>-1</button>
      <button onClick={() => setCount(0)}>Reset</button>
      <div>
        <input
          type="number"
          value={inputValue}
          onChange={handleChange}
          placeholder="Set count..."
        />
        <button onClick={setFromInput}>Set</button>
      </div>
    </div>
  );
}
```

Test in browser — type "25", click Set → count becomes 25. Type "abc" → nothing happens (invalid number). Try it.

### Common Event Types — Quick Reference

| Event | TypeScript Type |
|---|---|
| Input change | `React.ChangeEvent<HTMLInputElement>` |
| Button click | `React.MouseEvent<HTMLButtonElement>` |
| Form submit | `React.FormEvent<HTMLFormElement>` |
| Key press | `React.KeyboardEvent<HTMLInputElement>` |

All React event types live in the `React` namespace. The `<HTMLInputElement>` generic part — which DOM element triggered the event. We'll dive into generics in 1.8.

## Step 6 — Controlled Input Form

Think: "State and events learned in one component. But in real apps, form data needs to flow to a parent — controlled input + callback pattern."

### Step 6a — Just Build the UI (No State, No Props)

Build a form component. First just the UI — no state, no functionality:

`src/components/GreetingForm.tsx`:

```tsx
function GreetingForm() {
  return (
    <div>
      <input type="text" placeholder="Enter your name..." />
      <button>Submit</button>
    </div>
  );
}

export default GreetingForm;
```

`App.tsx` imports it:

```tsx
import Counter from "./components/Counter";
import GreetingForm from "./components/GreetingForm";

function App() {
  return (
    <div>
      <h1>Mini Projects</h1>
      <Counter />
      <GreetingForm />
    </div>
  );
}
```

Check the browser — you see the input and button. You can type, but Submit does nothing.

### Step 6b — Add State (Controlled Input)

Think: "I need to capture the input value. On submit, send it to the parent."

First, make the input controlled — state + `onChange`:

```tsx
import { useState } from "react";

function GreetingForm() {
  const [name, setName] = useState("");  // infer → string

  return (
    <div>
      <input
        type="text"
        value={name}
        onChange={(e) => setName(e.target.value)}
        placeholder="Enter your name..."
      />
      <button>Submit</button>
    </div>
  );
}
```

- `value={name}` — input value comes from React state
- `onChange={(e) => setName(e.target.value)}` — user types → `setName` updates → React re-renders

### Step 6c — Add Callback Prop

Think: "Data is captured. But when Submit is clicked, how do I send it to the parent?"

From 1.5.4, a callback prop — the parent passes a function, the child calls it:

```tsx
interface GreetingFormProps {
  onSubmit: (name: string) => void;
}

function GreetingForm({ onSubmit }: GreetingFormProps) {
  // ...
}
```

`onSubmit` is a callback that sends a string to the parent. The parent decides what to do with the data.

### Step 6d — Submit Handler

Think: "On Submit click: validate, call callback, clear the input."

```tsx
const handleSubmit = () => {
  if (name.trim() !== "") {
    onSubmit(name);
    setName("");
  }
};
```

- `name.trim()` — strips whitespace (`"  Vin  "` → "Vin")
- `!== ""` — only submit if not empty
- `onSubmit(name)` — sends data to parent
- `setName("")` — clears the input

Add `onClick={handleSubmit}` to the button.

### Final GreetingForm

```tsx
import { useState } from "react";

interface GreetingFormProps {
  onSubmit: (name: string) => void;
}

function GreetingForm({ onSubmit }: GreetingFormProps) {
  const [name, setName] = useState("");

  const handleSubmit = () => {
    if (name.trim() !== "") {
      onSubmit(name);
      setName("");
    }
  };

  return (
    <div>
      <input
        type="text"
        value={name}
        onChange={(e) => setName(e.target.value)}
        placeholder="Enter your name..."
      />
      <button onClick={handleSubmit}>Submit</button>
    </div>
  );
}

export default GreetingForm;
```

### Use in App.tsx

```tsx
function App() {
  const handleGreeting = (name: string) => {
    alert(`Hello, ${name}!`);
  };

  return (
    <div>
      <h1>Mini Projects</h1>
      <Counter />
      <GreetingForm onSubmit={handleGreeting} />
    </div>
  );
}
```

Test in browser — type "Vin", click Submit → "Hello, Vin!" alert. Input clears automatically. Try submitting empty — validation blocks it.

### Recap — Controlled Input Form

| Concept | Code | What it does |
|---------|------|--------------|
| Controlled input | `value={name}` + `onChange` | Input value comes from React state |
| Trim validation | `name.trim() !== ""` | Prevents empty submissions |
| Clear after submit | `setName("")` | Clears input for next entry |
| Callback | `onSubmit(name)` | Child sends data to parent |

## Summary

- **`useState`** — creates a state variable; updates trigger a re-render
- **Syntax:** `const [state, setState] = useState(initialValue)` — TypeScript infers the type
- **Array destructuring** — `state` (current value), `setState` (update function)
- **Event types:** `React.ChangeEvent<HTMLInputElement>`, `React.MouseEvent<HTMLButtonElement>`
- **Controlled input:** `value` + `onChange` — React state controls the input
- **Type inference:** TypeScript infers from the initial value (usually enough)
