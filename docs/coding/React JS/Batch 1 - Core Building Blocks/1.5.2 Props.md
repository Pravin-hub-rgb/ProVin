## Where We Left Off

In 1.5.1, we learned interfaces — how to define an object's shape, use `export interface`, and `import type`. Now we apply this to React **props**. The component becomes dynamic — it can render with different data each time.

## Broader Goal

So far ProfileCard was static — every instance shows the same "Vin — React Developer." The whole point of component reusability is when **one component renders with different data**. Props is React's mechanism for passing data. We start with inline types, then upgrade to interfaces.

## Step 1 — Feel the Problem

Think: "Three ProfileCards rendered — all with the same data — 'Vin', 'React Developer'. Do I need a separate component for each?"

```tsx
// Would you need something like this?
function VinCard() { return <div>Vin — React Developer</div>; }
function PriyaCard() { return <div>Priya — Designer</div>; }
function RajCard() { return <div>Raj — Backend Dev</div>; }
```

100 cards means 100 components? No. That's why **props** exist — a way to pass data into a component.

## Step 2 — Props = Function Arguments

**Concept:** Just as a function takes parameters, a component takes **props**. They're the same thing — just called "props" in React.

```tsx
// Regular function
function greet(name: string) {
  return `Hello, ${name}`;
}
greet("Vin");

// React component with props
function ProfileCard(props: { name: string; role: string }) {
  return (
    <div>
      <h2>{props.name}</h2>
      <p>{props.role}</p>
    </div>
  );
}
<ProfileCard name="Vin" role="React Developer" />
```

Here's what's happening: when you write `<ProfileCard name="Vin" role="React Developer" />`, React creates an object `{ name: "Vin", role: "React Developer" }` and passes it as the `props` parameter into the component. Inside the component, you access `props.name` and `props.role`.

### `props` is Not a Keyword

`props` is not a React keyword — it's just a function parameter name. You can use anything:

```tsx
function ProfileCard(data: { name: string; role: string }) {
  return <h2>{data.name}</h2>;
}

function ProfileCard(p: { name: string; role: string }) {
  return <h2>{p.name}</h2>;
}

function ProfileCard(customProp: { name: string; role: string }) {
  return <h2>{customProp.name}</h2>;
}
```

All three work. But **convention** is to use `props` — when you read someone else's code and see `props`, you immediately know it's a React component. That's why the entire industry uses `props`.

## Step 3 — Props with Interface

Now using the interface from 1.5.1. Instead of an inline type, define a `ProfileCardProps` interface:

```tsx
interface ProfileCardProps {
  name: string;
  role: string;
}

function ProfileCard(props: ProfileCardProps): JSX.Element {
  return (
    <div>
      <h2>{props.name}</h2>
      <p>{props.role}</p>
    </div>
  );
}

export default ProfileCard;
```

`App.tsx`:

```tsx
import ProfileCard from "./components/ProfileCard";

function App() {
  return (
    <div>
      <h1>My Team</h1>
      <ProfileCard name="Vin" role="React Developer" />
      <ProfileCard name="Priya" role="Designer" />
      <ProfileCard name="Raj" role="Backend Dev" />
    </div>
  );
}
```

The browser renders three different cards. One component, different data — that's **component reusability**.

### Interface Naming Convention

The interface is named `ProfileCardProps`. This is a convention: **`ComponentNameProps`** — append `Props` to the component name. It's optional, but standard in the React ecosystem.

### Inline Type vs Interface

| | Inline Type | Interface |
|---|---|---|
| Syntax | `props: { name: string }` | `interface Props { name: string }` then `props: Props` |
| Reuse | Not reusable | Can use in multiple places |
| Readability | Fine for small props | Better for complex components |
| Export | Not possible | `export interface` — can import elsewhere |

Inline types work fine for small components (< 3-4 props). But in real projects, interfaces are preferred — they're extensible, reusable, and the type definition lives on its own line.

## Summary

- Props = function arguments for components
- `<ProfileCard name="Vin" />` → React creates a props object `{ name: "Vin" }`
- Inline type: `(props: { name: string })` — for simple cases
- Interface: `interface ProfileCardProps { name: string }` — the professional pattern
- Convention: name it `ComponentNameProps`
- One component, different data = component reusability
