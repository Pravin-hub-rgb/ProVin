## Broader Goal

We'll build a **To-Do** app (the classic "cross off done items" pattern). The final screen looks like this:

```
┌─────────────────────────────────────────┐
│  To-Do                                  │
│                                         │
│  [ Add item...          ] [Add]         │
│                                         │
│  [All] [Active] [Completed]             │
│                                         │
│  ☐  Milk                               │
│  ☑  Eggs (strikethrough, gray)         │
│  ☐  Bread                              │
│                                         │
│  Completed: 1 / 3 items                 │
└─────────────────────────────────────────┘
```

- Each item has a **checkbox** — click to toggle done (`☐` ↔ `☑`); completed items get strikethrough + gray text.
- **Filter buttons** — All / Active / Completed, the active one is bold.
- **Item count** — "Completed: X / Y items" (only when items exist).

But we won't build the whole app at once. First we'll build a **static UI** (hardcoded) — confirm what shows on screen. Then we'll make things **functional one at a time**: input → Add button → items (as objects) → toggle → conditional rendering → filter → count. We'll verify in the browser/console after every step.

In this file we'll learn:
- **Interface** — defining the shape of an object (`Item { id, text, completed }`)
- **`.map()` with condition** — update a specific item, leave the rest unchanged
- **Ternary `? :`** — inline conditional in JSX
- **`&&` operator** — render only when truthy
- **Union type** — `"all" | "active" | "completed"`
- **`.filter()` by property** — filtering objects by a property

## Step 2 — Make the Input Functional (Stage 2/3: State + UI Binding)

THINK: The user will type in the input. If we store the value in a plain JS variable, React won't know it changed — the UI won't update. We need React's own "memory" mechanism. We know `useState` from 1.7.

CONCEPT: `useState("")` takes a starting value (empty string) and returns two things: the current value (`input`) and an update function (`setInput`). Controlled input: `value={input}` makes the input controlled by state, and `onChange` fires on every keystroke so we can update state.

CODE — make only the input functional, keep the rest static:

```tsx
import { useState } from "react";

export default function App() {
  const [input, setInput] = useState("");

  return (
    <div>
      <h1>To-Do</h1>

      <div>
        <input
          value={input}
          onChange={(e) => setInput(e.target.value)}
          placeholder="Add item..."
        />
        <button>Add</button>
      </div>

      {/* rest of the static skeleton from Step 1 stays the same */}
      <div>
        <button>All</button>
        <button>Active</button>
        <button>Completed</button>
      </div>

      <div>
        <div>
          <input type="checkbox" />
          <span>Milk</span>
          <button>Delete</button>
        </div>
      </div>

      <p>Completed: 0 / 1 items</p>
    </div>
  );
}
```

TEST: Type in the input → is `input` printing correctly? (Temporarily add `console.log(input)` to check, then remove it.) Does the input field update as you type? If not, check `value`/`onChange`.

**Nutshell:** A controlled input is one whose `value` comes from React state and whose every change goes through `onChange` to update that state — the React state and the input field stay in sync.

## Step 4 — Why Items Must Become Objects (The Problem)

THINK: Now we need to store items — and this time as **objects**, not strings, because we need a `completed` (done/not-done) property per item. A string can't hold that: "Milk" is a string, you can't put `completed: true` inside it. Items must become `{ text: "Milk", completed: false }`. Try an object without a type first — see what problem arises.

CONCEPT: An interface is TypeScript's contract — it defines the shape of an object. `interface Item { id: number; text: string; completed: boolean }`. Why `id`? A unique identity for each item (needed for key, delete, toggle). Why `completed` boolean? True/false (done or not). Without an interface, a typo hides (TypeScript doesn't catch it). With an interface, you get a compile error if a field is missing or has the wrong type.

Problem-first — see the issue:

```tsx
// ❌ Without a type — typo hides
const newItem = { id: 1, txt: "Milk", completed: false }; // "txt" typo, no error
setItems([...items, newItem]); // TypeScript doesn't catch it

// ✅ With an interface — compile error
const newItem: Item = { id: 1, txt: "Milk", completed: false };
// Error: Property 'text' is missing, 'txt' does not exist
```

CONCEPT — File structure: Now create `src/types.ts`. Why? To avoid type duplication — define once, import everywhere (DRY for types). Where? `src/types.ts` (convention: a central types file). Named `types.ts` because more types will land here later (e.g. `FilterStatus`).

CODE — create `src/types.ts` (only the interface, nothing else yet):

```ts
export interface Item {
  id: number;
  text: string;
  completed: boolean;
}
```

TEST: File created. No App.tsx change yet — we just defined the shape. Next step: use it in state.

**Nutshell:** An interface is the TypeScript construct that defines an object's shape (which fields, which types) — it catches missing/wrong fields at compile time. It does nothing at runtime; it's only type-checking.

## Step 6 — `handleAdd` Creates an `Item` Object

THINK: State is now `Item[]`. But `handleAdd` still only does `console.log` (Step 3). Now replace it with real logic: create an `Item` object (`id`, `text`, `completed`) and push it. This is where the interface pays off — TypeScript checks the object matches `Item`.

CONCEPT: `Date.now()` gives a unique id (timestamp). `completed: false` default (new items aren't done). Spread `[...items, newItem]` creates a new array reference (immutability). Then clear input.

CODE — replace `handleAdd`:

```tsx
const handleAdd = () => {
  if (input.trim() === "") return;
  const newItem: Item = {
    id: Date.now(),        // unique id (timestamp)
    text: input.trim(),
    completed: false,      // default not done
  };
  setItems([...items, newItem]);
  setInput("");
};
```

TEST: Type "Milk" → Add. Check `items` in console — should show `[{ id: ..., text: "Milk", completed: false }]`. Input clears. Add "Eggs" → two objects. State now holds `Item` objects.

## Step 7 — `handleDelete` by `id` + Render Items

THINK: Items are objects now. Delete by index (1.9 style) is fragile — after reorder/filter, indices shift. Delete by unique `id` is stable. And render must read `item.text` (not `item`) and use `key={item.id}` (not index).

CONCEPT: `items.filter((item) => item.id !== id)` — keep everything except the item with matching id. New array reference. Render: `items.map((item) => ...)` with `key={item.id}`, display `item.text`. (The `key` prop rationale — Virtual DOM diffing, why index is bad — was covered in 1.10 Step 2.)

CODE — add `handleDelete` and render the list:

```tsx
const handleDelete = (id: number) => {
  setItems(items.filter((item) => item.id !== id));
};

// In JSX (replace the "items not rendered yet" comment):
{items.length === 0 ? (
  <p>No items yet. Add one above!</p>
) : (
  items.map((item) => (
    <div key={item.id}>
      <span>{item.text}</span>
      <button onClick={() => handleDelete(item.id)}>Delete</button>
    </div>
  ))
)}

<p>Completed: 0 / {items.length} items</p>
```

TEST: Add "Milk", "Eggs". Delete "Milk" → only "Eggs" remains. Delete all → empty state shows. Console `items` shows objects with `id`, `text`, `completed`.

## Step 8 — Toggle Complete (`.map()` with Condition)

THINK: On checkbox click, `completed` should flip `true` ↔ `false` (cross off / un-cross). Try direct mutation — `items[0].completed = true; setItems(items)` — what happens? Same reference issue (from 1.9: React compares by reference, same reference → no re-render). Immutability rule: we need a new array.

CONCEPT — `.map()` with a condition: `.map()` iterates over every element and returns something for each. You can add a condition — change only the matching element, leave the rest as-is:

```js
const nums = [1, 2, 3, 4, 5];

const result = nums.map((n) => {
  if (n > 2) return n * 10;  // matches condition → change
  return n;                    // otherwise → unchanged
});

console.log(result); // → [1, 2, 30, 40, 50]
```

Only elements matching the condition (`n > 2`) get changed.

Apply to the app — `handleToggleComplete`:

```tsx
const handleToggleComplete = (id: number) => {
  setItems(
    items.map((item) => {
      if (item.id === id) {
        return { ...item, completed: !item.completed };
      }
      return item;
    })
  );
};
```

`...item` means "copy all existing properties of item." Then override just `completed` with the flipped value `!item.completed`. The other items keep the same reference (React skips them — an optimization).

Verify with console.log:

```tsx
const handleToggleComplete = (id: number) => {
  const updated = items.map((item) => {
    if (item.id === id) return { ...item, completed: !item.completed };
    return item;
  });
  console.log("Before:", items);
  console.log("After:", updated);
  setItems(updated);
};
```

TEST: Add an item. Copy its `id` from the console. Call `handleToggleComplete(thatId)` (temporarily wire it to an `onChange`). In the console, only that item's `completed` flips from `false` to `true`.

Wire the checkbox:

```tsx
{items.map((item) => (
  <div key={item.id}>
    <input
      type="checkbox"
      checked={item.completed}
      onChange={() => handleToggleComplete(item.id)}
    />
    <span>{item.text}</span>
    <button onClick={() => handleDelete(item.id)}>Delete</button>
  </div>
))}
```

TEST: Click the checkbox → `completed` flips in the console. The checkbox visual updates (controlled by `checked={item.completed}`). Next step: conditional rendering for strikethrough.

**Nutshell:** `.map()` with a condition iterates over every item; the matching item returns a new object (spread + override), the rest return the original reference — React only re-renders the changed item.

## Step 9 — Conditional Rendering Concepts (Ternary + `&&`)

THINK: The toggle logic is ready. Now the UI must show different things based on conditions — strikethrough + gray for completed items. The same elements render different styles. This is the core use case for conditional rendering. First standalone examples, then apply to the app.

CONCEPT — Ternary Operator `? :`:

```js
const age = 20;
const label = age >= 18 ? "Adult" : "Minor";
console.log(label); // → "Adult"
```

Pattern: `condition ? valueIfTrue : valueIfFalse`. In React JSX:

```tsx
const isMorning = true;
return <p>{isMorning ? "🌅" : "🌙"}</p>;
```

This is an inline JSX expression — used directly inside `{ }`.

CONCEPT — `&&` Operator:

```js
const isLoggedIn = true;
isLoggedIn && console.log("Welcome!");
// → "Welcome!"
```

`&&` means: if the left side is truthy, evaluate the right. If falsy, short-circuit and skip. In React: "show this only when the condition is true":

```tsx
const hasNotification = true;
return <div>{hasNotification && <span>🔔</span>}</div>;
```

Both of these show up everywhere in React code. Now apply them to the app.

## Step 11 — Filter Buttons (Union Type + `.filter()`)

THINK: All items show up. But the user might want to see only active items, or only completed ones. We need filtering. We need to track which filter is active, and render items accordingly.

Problem: there's no filtering. We need to track which filter is active, and render items accordingly.

We need three possible filter values:
- `"all"` — all items
- `"active"` — only not-done items
- `"completed"` — only done items

TypeScript uses **union types** to enforce that only these three string values are allowed.

CONCEPT — Union Type:

```ts
type TrafficLight = "red" | "yellow" | "green";

let light: TrafficLight = "red";  // ✅
light = "blue";                    // ❌ TypeScript error
```

`|` means "or" — the value can be one of these. Only the specified values are allowed.

CONCEPT — `.filter()` by property (review from 1.9, now with objects):

In 1.9 we filtered strings. Now we check object properties:

```ts
const items: Item[] = [
  { id: 1, text: "Milk", completed: true },
  { id: 2, text: "Eggs", completed: false },
];

const completedItems = items.filter((item) => item.completed);
console.log(completedItems); // → [Milk]

const activeItems = items.filter((item) => !item.completed);
console.log(activeItems); // → [Eggs]
```

CODE — add the filter state to `App.tsx`:

```tsx
type FilterStatus = "all" | "active" | "completed";

function App() {
  const [items, setItems] = useState<Item[]>([]);
  const [filter, setFilter] = useState<FilterStatus>("all");
  const [input, setInput] = useState("");
  // ...
}
```

Note the union type's initial value is `"all"` — at first, all items show.

CODE — add the filter logic, before the return, inside App:

```tsx
const filteredItems = items.filter((item) => {
  if (filter === "completed") return item.completed;
  if (filter === "active") return !item.completed;
  return true; // "all" — keep everything
});

console.log("Current filter:", filter, "Filtered:", filteredItems); // verify
```

CODE — add three filter buttons, between the input and the list:

```tsx

    style={{ fontWeight: filter === "all" ? "bold" : "normal" }}

    All
  </button>
  <button
    onClick={() => setFilter("active")}
    style={{ fontWeight: filter === "active" ? "bold" : "normal" }}
  >
    Active

  <button
    onClick={() => setFilter("completed")}

    Completed
```

This is a new use case for conditional styling — whichever filter is active appears bold.

## Step 13 — Item Count (`&&` Conditional Rendering)

THINK: The user wants a summary — how many items, how many completed. Show the count. Only show it when items exist (showing a count with zero items is pointless).

## Common Mistakes

- **Mutating the array** (`items.push(...)`, `items[0].completed = true`) → React sees the same reference, no re-render. Always create a new array with `.map`/`.filter`/spread.
- **Using index as key** (`key={index}`) → on reorder/filter, React gets confused and updates the wrong DOM. Use a unique stable id (`key={item.id}`).
- **`useState([])` without a generic** → TypeScript infers `never[]`, and pushing later fails. Pass `<Item[]>` explicitly.
- **Typo in a union value** (`setFilter("done")`) → compile error (that's good). Don't bypass it with `as any` — you lose the type safety.
- **Forgetting `return` in `.filter()`** — every branch must return something, otherwise `undefined` (falsy) → the item gets dropped.
- **Forgetting `...item` in the toggle** — `{ completed: !item.completed }` loses the other fields (`id`, `text`). Spread first, then override.
- **Forgetting `.length` for the count** — `items.filter(...)` returns an array; you need `.length` to get a number.

## Summary

- **Interface** — defines an object's shape (`Item { id, text, completed }`); compile-time type safety
- **`.map()` with condition** — update a specific item, leave the rest unchanged; immutability
- **Ternary `? :`** — `condition ? valueIfTrue : valueIfFalse` inline in JSX
- **`&&` operator** — `condition && <JSX>` renders only when truthy
- **Union type** — `"all" | "active" | "completed"` limits allowed values
- **`.filter()` by property** — filter objects by a property
- **Conditional styling** — `style={{ prop: condition ? value1 : value2 }}`
- **Immutability** — `.map()`/`.filter()`/spread create new arrays, never mutate
- **File structure** — types in one central file (`src/types.ts`), DRY
- **Static first** — confirm the hardcoded UI first, then make things functional one at a time

## What It Is NOT

- **The checkbox is not just CSS** — `completed` is a real state property (boolean); the UI derives from it. CSS is only the display.
- **Filter doesn't mutate items** — `.filter()` creates a new array; the original `items` is untouched. Changing the filter changes the view, not the data.
- **`key={item.id}` is not optional** — React needs the identity for efficient diffing. Use an index and you get bugs on reorder/filter.
- **An interface is not runtime validation** — TypeScript checks at compile time, nothing at runtime. For runtime validation you need other tools (Zod, etc.) — covered later.
- **A union type is not an enum** — it's a string literal union; at runtime it's a plain string. Enums are a different thing (covered later).

## In Your Own Words

1. What's the difference between the ternary operator and the `&&` operator? When should you use which?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The ternary `? :` gives both branches — condition true → value A, false → value B. Use it when both cases render something (e.g. strikethrough + gray text for completed items). `&&` gives only one branch — condition truthy → render, falsy → nothing. Use it when you only want "show when true" and nothing otherwise (e.g. empty-state message, item count). Ternary is "either/or", `&&` is "show or skip". Note: the checkbox's own checked/unchecked visual is handled natively by `checked={item.completed}`, so no ternary needed there.

</details>

2. Why doesn't `items[0].completed = true; setItems(items)` work for toggling done? What's the correct approach?

<details>
<summary>Show Answer</summary>

**Sample Answer:** React compares state by reference. `items[0].completed = true` mutates the existing array — same reference. `setItems(items)` passes the same old reference. React thinks "same reference → nothing changed → no re-render." Correct approach: create a new array with `.map()` — the matching item returns `{...item, completed: !item.completed}` (new object), the rest return the original reference. New array reference → React re-renders. Immutability rule.

</details>

3. What's the real benefit of a union type like `"all" | "active" | "completed"`? What problem arises if you just use `string`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A union type restricts the value to only those three. With plain `string`, `setFilter("done")` (typo) or `setFilter("random")` would compile fine — the bug surfaces at runtime. With a union type, you get a compile error immediately. Plus VS Code gives autocomplete with the three options. The benefit of type safety: an invalid value can never enter state.

</details>

4. What's the difference between `.filter()` by property (`item.completed`) and `.filter()` by index (`i !== index`)? When do you use each?

<details>
<summary>Show Answer</summary>

**Sample Answer:** By index: position-based removal — "remove the item at position X." Fragile: after reorder/filter, indices shift, so the wrong item can get deleted. By property/id: identity-based — "remove the item with id X." Stable and reorder-safe. Always use a unique id for deletion. By property (like `item.completed`) is for filtering — "keep only the completed items." Different purposes: index = position, property = condition.

</details>

5. Why build the static UI first? Why not go straight to dynamic?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Static first: the UI design gets confirmed without logic, the data shape gets validated (fields actually work), and there's one problem at a time (data-layer bugs are easy to spot later). Going straight to dynamic: UI + data + logic + state all at once → when an error appears, you can't tell whether it's in the UI, the data, or the state. Static first builds confidence that each step works, and makes the "what got added now" diff clear.

</details>

## Cheat Sheet (Quick Recall)

**The problem:** React doesn't understand `if/else` inside JSX — and manually hiding/showing or mutating DOM nodes contradicts everything React is about.

**The fix — render conditionally:** `&&`, ternary `? :`, union-typed filter values, and `.map()`/`.filter()` — the same idioms you already know from plain JS, just inside JSX.

- **Ternary `? :`** → `condition ? valueIfTrue : valueIfFalse` — inline conditional in JSX
- **`&&`** → `condition && <JSX>` — render only when condition is truthy
- **`.map()` with condition** → update one specific item, leave the rest as-is: `{...item, completed: !item.completed}`
- **Union type** → `"all" | "active" | "completed"` — a limited set of allowed values
- **`.filter()` by property** → `items.filter(item => item.completed)` — filter objects by a property
- **Interface** → `interface Item { id; text; completed }` — the shape of an object
