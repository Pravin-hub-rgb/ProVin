## Where We Left Off

In 1.5.1 we learned interfaces, 1.5.2 taught us props, 1.5.3 covered optional props and destructuring, and 1.5.4 covered callback props — passing functions as props with the `on` prefix convention. We built a GreetingCard and understood the `onAdd` callback pattern.

## Broader Goal

Every component we've built so far — `ProfileCard`, `GreetingCard`, `TaskInput` — has been **self-closing**: `<ProfileCard />`, `<GreetingCard ... />`. But in real apps, components contain other components inside them:

```tsx
<Card>
  <h1>Title</h1>
  <p>Content</p>
</Card>
```

This is the **composition** pattern — passing content into a component from the inside. React uses the **`children`** prop for this.

## Step 1 — Feel the Problem

Think: "I need a `Card` component that wraps any content with a border and shadow. But the content changes every time — what goes inside?"

If we pass content as a prop:

```tsx
function Card({ content }: { content: string }) {
  return <div className="card">{content}</div>;
}

<Card content="<h1>Title</h1><p>Content</p>" />
```

The problem — `content` is a string, so the HTML doesn't render. Passing objects would be complex. And JSX?

**Plain JavaScript — no destructuring, no TypeScript:**

```tsx
function Card(props) {
```

`props` is an object like `{ content: "Hello" }`. Access the value with `props.content`.

**Add destructuring (still just JavaScript):**

```tsx
function Card({ content }) {

```

`{ content }` means "pull the `content` property out of the props object into a variable." Now you use `content` directly, not `props.content`. This is the same destructuring pattern from 1.5.3.


TypeScript is saying: "props is an object that has a property `content` of type `string`."

| Code | Meaning |
|------|---------|
| `{ content }` (destructuring) | Pull the `content` property out of props into a variable |

### React Escapes Strings

When you write `<Card content="<h1>Title</h1>" />`, `content` is a string — `<h1>` and `</h1>` are just text characters, not actual HTML elements.

React escapes strings in JSX to prevent **XSS (Cross-Site Scripting)** attacks. You'd literally see the text `<h1>Title</h1>` on screen, not a rendered heading.

`dangerouslySetInnerHTML` exists, but React deliberately named it scary — "this is dangerous, use only if you're sure."

**The real solution:** Pass JSX directly, not as a string:

```tsx
// ❌ String — won't render as HTML
<Card content="<h1>Title</h1>" />

// ✅ JSX direct — but how?
<Card>
  <h1>Title</h1>
</Card>
```

This pattern is made possible with the `children` prop. Let's see how in Step 2.

## Step 2 — The Children Prop

Think: "In HTML, `<div>` can contain anything between its tags and it just renders. Does React have that?"

**Concept:** `children` is a special prop — whatever you place between a component's opening and closing tags automatically becomes `children`.

```tsx
<Card>
  <h1>Hello</h1>    {/* this is children */}
  <p>World</p>       {/* this too */}
</Card>
```

Inside the `Card` component, this content is received via `props.children`.

`src/components/Card.tsx`:

```tsx
function Card({ children }: { children: React.ReactNode }): JSX.Element {
  return (
    <div style={{ border: "1px solid #ccc", padding: "16px", borderRadius: "8px" }}>
      {children}
    </div>
  );
}

export default Card;
```

`React.ReactNode` — a TypeScript type that says `children` can be anything React can render: a string, number, JSX, an array of JSX, `null`, `undefined`.

`App.tsx`:

```tsx
import Card from "./components/Card";

function App() {
  return (
    <div>
      <Card>
        <h2>Welcome!</h2>
        <p>This is inside a Card component.</p>
      </Card>
      <Card>
        <p>Another card with different content.</p>
      </Card>
    </div>
  );
}
```

Notice — the content is different, but the Card styling (border, padding, borderRadius) stays the same. This is a **layout component** — it provides structure, not content.

### Is `children` a Keyword or Convention?

`children` is neither a JavaScript keyword nor a React reserved keyword. It's a **special prop name** — React looks inside the opening and closing tags of a component, and automatically assigns that content to the `children` prop.

Can you rename `children`? Yes, but then auto-assignment stops working:

```tsx
// If you rename it to `content`:
function Card({ content }: { content: React.ReactNode }) {
  return <div className="card">{content}</div>;
}
```

Now `<Card><h1>Hi</h1></Card>` would leave `content` as `undefined`. React only auto-assigns to `children`. With a custom name, you must pass content explicitly like a normal prop:

```tsx
<Card content={<h1>Hi</h1>} />  // explicit — like a normal prop
```

But that defeats the purpose. Always use `children` to get the auto-assignment behavior.

### Normal Prop vs Children Prop — What's the Difference?

| Feature | Normal Prop | Children Prop |
|---------|-------------|---------------|
| How you pass it | `<Card title="Hello" />` | `<Card>Hello</Card>` |
| How you receive it | `props.title` | `props.children` |
| Auto-assigned by React? | ❌ Must write it as an attribute | ✅ React grabs content between tags automatically |
| Name convention | Anything — `label`, `action`, `onClick`, `count` | Only **`children`** — no other name gets auto-assigned |
| When to use | Specific data (string, number, function, boolean) | Arbitrary JSX content to wrap inside the component |

### Normal Props + Children — Together

A React component can take both: specific data via normal props, and wrapped content via `children`:

```tsx
interface CardProps {
  children: React.ReactNode;
  title?: string;
}

function Card({ children, title }: CardProps) {
  return (
    <div className="card">
      {title && <h3>{title}</h3>}
      {children}
    </div>
  );
}
```

```tsx
<Card title="Today's Tasks">   {/* normal prop — specific data */}
  <p>Review PR</p>              {/* children — auto-assigned */}
  <p>Write tests</p>            {/* children — part of wrapped content */}
  <p>Deploy to staging</p>      {/* children — more wrapped content */}
</Card>
```

Here:
- `title="Today's Tasks"` — a **normal prop** — explicitly passed, accessed via `props.title`
- `<p>Review PR</p>` etc — **children** — React auto-assigned, accessed via `props.children`

The Card component combines both: the title heading and the wrapped content rendered inside the card layout.

### Normal Props vs Children — When to Pass JSX

Think: "What if I pass JSX through a normal prop AND through children?"

```tsx
// Passing JSX as a normal prop — works, but awkward
<Card content={<h1>Hi</h1>} />

// Passing JSX as children — natural, React style
<Card>
  <h1>Hi</h1>
</Card>
```

Both work. But the children pattern is more readable — it looks like HTML (content between tags). Passing JSX as a prop value (`<Card content={<h1>Hi</h1>} />`) means nesting JSX inside JSX — it works but looks messy.

### Quick Reference — When to Use What

| Situation | Use |
|-----------|-----|
| Button text | `children` — `<Button>Click</Button>` |
| Card wrapping content | `children` — `<Card><p>Content</p></Card>` |
| Specific value (user ID) | Normal prop — `<Profile userId={1} />` |
| Callback function | Normal prop — `<TaskInput onAdd={handleAdd} />` |
| Optional heading or title | Normal prop — `<Card title="Notes">...</Card>` |

**Rule of thumb:** Anything between the opening and closing tags is `children`; anything in the opening tag as an attribute is a normal prop. Think like HTML — the content inside `<div>` vs the attributes like `<img src="..." />`.

## Step 3 — Composition Pattern: Like Lego Blocks

Think: "So children works. But what's the real benefit? Isn't wrapping just composition?"

No — composition is a broader pattern: **building bigger components by combining smaller ones**, like Lego blocks.

### Composition in HTML Already

You use composition every day in HTML — you just don't call it that:

```html
<div>
  <header>
    <h1>Title</h1>
    <nav>Home | About</nav>
  </header>
  <main>
    <p>Content here</p>
  </main>
</div>
```

Small elements (`<h1>`, `<p>`, `<nav>`) combine into bigger structures (`<header>`, `<main>`, `<div>`). React does the same thing — just with **components** instead of elements.

### Composition in React — Two Ways

#### 1. Via Props (Data Passing)

One component composes another by passing props:

```tsx
// Small component 1 — just renders an avatar
function Avatar({ name }: { name: string }) {
  return <img src={`https://api.dicebear.com/7.x/initials/svg?seed=${name}`} alt={name} />;
}

// Small component 2 — just renders info
function Info({ name, role }: { name: string; role: string }) {
  return (
    <div>
      <h3>{name}</h3>
      <p>{role}</p>
    </div>
  );
}

// Big component — composes Avatar + Info via props
function UserCard({ name, role }: { name: string; role: string }) {
  return (
    <div className="card">
      <Avatar name={name} />
      <Info name={name} role={role} />
    </div>
  );
}
```

Here `UserCard` combines `Avatar` and `Info` by **passing them props**. `UserCard` doesn't know what Avatar renders internally — it just knows Avatar needs a `name`.

#### 2. Via Children (Wrapping)

The other approach — create a wrapper component that accepts any content through children:

```tsx
// Card just provides layout — doesn't know or care what's inside
function Card({ children }: { children: React.ReactNode }) {
  return <div className="card">{children}</div>;
}

// Put anything inside — that's composition
<Card>
  <UserCard name="Vin" role="Developer" />
</Card>
```

Here `Card` doesn't know what's inside — it just provides layout. `UserCard` doesn't know it's inside a Card. They're **loosely coupled** — that's the benefit of composition.

### Using Both Together

In real apps, both approaches are used together:

```tsx
// Two small components — one for avatar, one for user info
function Avatar({ name }: { name: string }) {
  return <img src={`https://api.dicebear.com/7.x/initials/svg?seed=${name}`} alt={name} />;
}

interface InfoProps {
  name: string;
  role: string;
  status?: "online" | "offline";
}

function Info({ name, role, status }: InfoProps) {
  return (
    <div>
      <h3>{name}</h3>
      <p>{role} {status === "online" ? "🟢" : "⚪"}</p>
    </div>
  );
}

// UserCard — composes Avatar + Info via props
function UserCard({ name, role, status }: InfoProps) {
  return (
    <div className="card">
      <Avatar name={name} />
      <Info name={name} role={role} status={status} />
    </div>
  );
}

// App — composes UserCard inside Card via children
function App() {
  return (
    <Card>
      <UserCard name="Vin" role="React Developer" status="online" />
      <UserCard name="Priya" role="Designer" status="offline" />
    </Card>
  );
}
```

The composition tree:

```
App
└── Card (children-based — wrapper)
    ├── UserCard (props-based — composes Avatar + Info)
    │   ├── Avatar
    │   └── Info
    └── UserCard
        ├── Avatar
        └── Info
```

### Composition Over Inheritance

If you studied OOP (Object-Oriented Programming) in school or college, you learned **inheritance** — `class Dog extends Animal`. React doesn't work that way. React's philosophy is **composition over inheritance**.

| Inheritance (OOP) | Composition (React) |
|---|---|
| Class extends another class | Component wraps another component |
| "Inherit properties from parent" | "Build from smaller blocks" |
| Tight coupling | Loose coupling |
| Rigid hierarchy | Flexible, flat structure |

React docs say: "Use composition instead of inheritance."

### Quick Reference — Composition in React

| What | How | Example |
|------|-----|---------|
| Build a specific component | Pass props | `<Avatar name="Vin" />` |
| Build a layout | Accept children | `<Card>content</Card>` |
| Combine both | Props + children | `<Card title="Users"><Avatar name="Vin" /></Card>` |

## Step 4 — Deep Dive: React.ReactNode

Think: "What is `React.ReactNode`? Can I just write `string | JSX.Element | null` myself?"

**Concept:** `React.ReactNode` is a TypeScript type representing a union of everything React can render:

```tsx
type ReactNode = 
  | string 
  | number 
  | boolean 
  | null 
  | undefined 
  | JSX.Element 
  | ReactNode[] // array of nodes
  | ReactPortal;
```

Writing this union manually would be very long. That's why `React.ReactNode` is used — one type covers everything.

One caveat — use `React.ReactNode` only when children can be truly anything (flexible). If children should be a specific type (like just `string`), use an explicit type instead:

```tsx
interface ButtonProps {
  children: string; // only strings allowed
}
```

## Step 5 — Layout Component: Container

Think: "I need a container component that centers the app content with a max width."

`src/components/Container.tsx`:

```tsx
interface ContainerProps {
  children: React.ReactNode;
}

function Container({ children }: ContainerProps): JSX.Element {
  return (
    <div style={{ maxWidth: "600px", margin: "0 auto", padding: "20px" }}>
      {children}
    </div>
  );
}

export default Container;
```

Now put all app content inside Container in `App.tsx`:

```tsx
import Container from "./components/Container";

function App() {
  return (
    <Container>
      <h1>My App</h1>
      <p>This content is centered with max-width 600px.</p>
    </Container>
  );
}
```

Check in browser — the content is now centered, max 600px wide, 20px padding on all sides.

## Step 6 — Single Child vs Multiple Children

Think: "What if there's one child vs multiple children inside the component. Does it matter?"

React handles both automatically:

```tsx
// Single child → children is a single element
<Card>
  <p>Hello</p>
</Card>
// children = <p>Hello</p> (JSX.Element)

// Multiple children → children becomes an array
<Card>
  <h1>Title</h1>
  <p>Content</p>
</Card>
// children = [<h1>Title</h1>, <p>Content</p>] (array)
```

`React.ReactNode` handles both cases. That's why it's flexible.

## Step 7 — Card Component with TypeScript Interface

Rewrite `src/components/Card.tsx` with a proper interface:

```tsx
interface CardProps {
  children: React.ReactNode;
  title?: string;
}

function Card({ children, title }: CardProps): JSX.Element {
  return (
    <div style={{ border: "1px solid #ccc", padding: "16px", borderRadius: "8px" }}>
      {title && <h3>{title}</h3>}
      {children}
    </div>
  );
}

export default Card;
```

Now Card accepts an optional title:

```tsx
<Card title="Tasks">
  <p>Task 1</p>
  <p>Task 2</p>
</Card>
```

`{title && <h3>{title}</h3>}` is conditional rendering shorthand — if `title` exists, render the `<h3>`, otherwise render nothing. We'll dive deeper into conditional rendering in 1.7.
