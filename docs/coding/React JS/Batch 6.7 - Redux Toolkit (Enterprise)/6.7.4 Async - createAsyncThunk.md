## STAGE 1 — Why Can't the Reducer Be Async? (Concept First)

### THINK

You might think — `reducers: { fetchCategories: async (state) => { const res = await fetch(...); state.items = await res.json() } }` — just fetch inside the reducer. But `6.7.1` told us reducers are **pure** — same `state + action` must always give the same `newState`, no `fetch`, `Date.now()`, `Math.random()`. How would time-travel work with an `await` in between? How would DevTools show the "pending -> fulfilled" history? That's why the reducer stays synchronous, async happens **outside** in a thunk, and the reducer only updates state based on that result.

### CONCEPT

A thunk is a **function that returns a function** — you can give `dispatch` an async function instead of an action object, and the middleware (built-in `redux-thunk` in RTK) runs that function with `dispatch` and `getState`. Manually, a thunk needs 3 actions: `fetch/pending` (loading true), `fetch/fulfilled` (save data), `fetch/rejected` (error). Every async needs 3 action types + 3 cases + try/catch — that's the boilerplate RTK's `createAsyncThunk` compresses into 1 function.

**Nutshell:** Thunk is the middleware pattern that lets you `dispatch` an async function instead of an action object, so the reducer stays pure and the async result arrives via 3 actions (pending/fulfilled/rejected).

## STAGE 2 — The Pain of Manual Async (without createAsyncThunk, for understanding)

### THINK

If you just hand someone `createAsyncThunk`, they'd wonder "3 actions auto, why?" — see the 3-action pain manually first, then you'll appreciate the automation.

### CODE

Manual thunk — not in `counterSlice.ts`, in a separate `categoriesManual.ts` (without RTK) — just for understanding, don't write this in production:

```ts
// src/manual-redux/categoriesManual.ts — ❌ Manual, tedious
interface CatState { items: string[]; status: "idle"|"loading"|"succeeded"|"failed"; error: string|null }

type CatAction =
  | {type:"categories/fetch/pending"}
  | {type:"categories/fetch/fulfilled", payload: string[]}
  | {type:"categories/fetch/rejected", payload: string};

const initial: CatState = { items: [], status:"idle", error: null };

export function catReducer(state=initial, action: CatAction): CatState {
  switch(action.type){
    case "categories/fetch/pending": return {...state, status:"loading", error:null}
    case "categories/fetch/fulfilled": return {...state, status:"succeeded", items: action.payload}
    case "categories/fetch/rejected": return {...state, status:"failed", error: action.payload}
    default: return state;
  }
}

// Thunk function (give dispatch a function)
export const fetchCategoriesManual = () => async (dispatch: any) => {
  dispatch({type:"categories/fetch/pending"});
  try {
    const res = await fetch("https://www.themealdb.com/api/json/v1/1/categories.php");
    const json = await res.json();
    const items = json.categories.map((c:any)=>c.strCategory).slice(0,5);
    dispatch({type:"categories/fetch/fulfilled", payload: items});
  } catch(e:any){
    dispatch({type:"categories/fetch/rejected", payload: e.message});
  }
};
```

| Line | Why |
|------|------|
| `CatAction` 3 types | Each stage has its own action — pending/fulfilled/rejected |
| `switch` 3 cases | Loading on pending, data on fulfilled, error on rejected |
| `fetchCategoriesManual = () => async (dispatch)` | Thunk — give dispatch a function, middleware runs it |

Boilerplate: 1 async needs 1 type union (3), 1 reducer (3 cases), 1 thunk (try/catch + 3 dispatch). 5 async = 50 lines.

### TEST

In a component:

```ts

// DevTools will show 3 actions: pending -> fulfilled
```

It works, but every async repeats this same 3-step — the same DRY violation from `6.2`.

## STAGE 3 — createAsyncThunk's Improvement (1 function = 3 actions auto)

### THINK

The manual 3-step pattern is the same for every async — `pending -> try fetch -> fulfilled/rejected`. Imagine a factory: "Give me the URL and return value, I'll handle the 3 actions + dispatch + error handling myself" — that's `createAsyncThunk`.

### CONCEPT

`createAsyncThunk("categories/fetch", async () => { return data })` — the first argument is `typePrefix` (`categories/fetch`), the second is the async `payloadCreator`. It returns 1 thunk function that automatically creates 3 action creators: `fetchCategories.pending`, `fetchCategories.fulfilled`, `fetchCategories.rejected` — handle them in the slice's `extraReducers` with `builder.addCase`.

### CODE

New slice `src/rtk/categoriesSlice.ts` — created in this stage (not before, now it's needed):

```ts
// src/rtk/categoriesSlice.ts — STAGE 3 minimal
import { createSlice, createAsyncThunk } from "@reduxjs/toolkit";

interface CatState {
  items: string[];
  status: "idle" | "loading" | "succeeded" | "failed";
  error: string | null;
}

const initialState: CatState = { items: [], status: "idle", error: null };

export const fetchCategories = createAsyncThunk(
  "categories/fetch",
  async () => {
    const res = await fetch("https://www.themealdb.com/api/json/v1/1/categories.php");
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    const json = await res.json();
    return json.categories.map((c: any) => c.strCategory).slice(0, 5) as string[];
  }
);

const categoriesSlice = createSlice({
  name: "categories",
  initialState,
  reducers: {}, // no sync reducers in this slice, just async
  extraReducers: (builder) => {
    builder
      .addCase(fetchCategories.pending, (state) => {
        state.status = "loading";
        state.error = null;
      })
      .addCase(fetchCategories.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.items = action.payload;
      })
      .addCase(fetchCategories.rejected, (state, action) => {
        state.status = "failed";
        state.error = action.error.message ?? "Something went wrong";
      });
  },
});

export default categoriesSlice.reducer;
```

Every line:

| Code | Why |
|------|------|
| `createAsyncThunk("categories/fetch", async () => ...)` | `typePrefix` auto-generates 3 types: `categories/fetch/pending` etc. |
| `async () => { fetch... return items }` | Whatever you `return` becomes `fulfilled`'s `payload` — arrives in `action.payload` |
| `extraReducers: (builder) =>` | `reducers` is for sync, `extraReducers` is for the external thunk's 3 cases |
| `builder.addCase(fetchCategories.pending, ...)` | On pending, `status="loading"` — Immer-style mutation |
| `state.error = action.error.message` | On rejected, error is in `action.error`, not `action.payload` — `createAsyncThunk` puts thrown errors into `rejected` |

**Add to store:**

## Common Mistakes

*   **Wrote `fetchCategories` in `reducers` instead of `extraReducers`:** `reducers` is only for sync `state =>` reducers, the 3 cases of `createAsyncThunk` go in `extraReducers` with `builder.addCase` — putting it in `reducers` gives TS error `Property 'pending' does not exist`.
*   **`dispatch(fetchCategories)` without `()`:** the return of `createAsyncThunk` is a **thunk function**, `dispatch` needs the result of calling `fetchCategories()` — `dispatch(fetchCategories)` dispatches the function object itself, the fetch won't run.
*   **Async/await inside a reducer:** `reducers: { fetch: async (state)=>{await fetch...}}` — reducer is no longer pure, DevTools time-travel breaks, RTK throws `A non-serializable value was detected`.
*   **Confusing `action.payload` and `action.error`:** in `fulfilled`, data is in `payload`; in `rejected`, error is in `error.message` — `rejected` doesn't have `payload` unless you use `rejectWithValue`.

## What It Is NOT

*   **NOT a `useFetch` replacement:** `useFetch` (6.2) is a simple hook, RTK async caches in the global store — if you need `categories` in 3 components, keep it in the store; if in 1 component, `useFetch` is enough.
*   **NOT `RTK Query`:** RTK Query is a separate data-fetching layer (caching, deduplication) — `createAsyncThunk` is just a thunk + 3 actions, you implement caching yourself. In interviews, `TanStack Query` vs `RTK Query` is a common comparison question — here we only learned `createAsyncThunk`.
*   **NOT fetch in a reducer:** always `fetch` in the thunk, in the reducer only set `state.status/items/error`.

## Summary

*   A reducer can't be async — it must stay pure, async goes in a thunk.
*   Manual async = 3 action types + switch + thunk (~25 lines).
*   `createAsyncThunk("prefix", async()=>return)` = 1 function, 3 actions auto, handle in `extraReducers` with `builder.addCase(pending/fulfilled/rejected)`.
*   `store.dispatch(fetchCategories())` -> `pending` -> `fulfilled/rejected`, traceable in DevTools.

## In Your Own Words

1. Why can't you use `await fetch` inside a reducer? What's the connection to pure-function time-travel?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A reducer is `(state, action) => newState` and must be pure — same input always gives same output, no `fetch` or `Date.now()`. If a reducer had `await fetch`, the same `fetchCategories` action would sometimes be `pending`, sometimes `fulfilled` — same input, different output, not pure. DevTools time-travel replays every action to rebuild state — an async reducer would re-fire fetch on every replay, the network could fail, history gets corrupted. That's why async lives in a thunk (outside), and the reducer only updates state on the 3 results (pending/fulfilled/rejected).

</details>

2. Manual 3 actions vs `createAsyncThunk`'s 3 actions — the names are the same, but how are they created differently? Explain with the example `categories/fetch/pending`.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Manually, you write the `type CatAction = {type:"categories/fetch/pending"} | {type:"categories/fetch/fulfilled", payload:string[]} | ...` union, a `switch` with 3 cases in `catReducer`, and `fetchCategoriesManual = () => async (dispatch)=>{dispatch({type:"categories/fetch/pending"}); try{...dispatch({type:"categories/fetch/fulfilled", payload})} catch...}` thunk by hand. With RTK, `createAsyncThunk("categories/fetch", async()=>return items)` is a single call — the `typePrefix` `"categories/fetch"` auto-generates 3 types (`categories/fetch/pending` etc.), `fetchCategories.pending/fulfilled/rejected` action creators are auto-created, the thunk function is auto-generated, and in `extraReducers` you only handle them with `builder.addCase`. 25 lines become 8.

</details>

3. `dispatch(fetchCategories)` vs `dispatch(fetchCategories())` — what's the difference of those parentheses, and what happens if you get it wrong?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `createAsyncThunk` returns a **thunk creator** — calling `fetchCategories()` produces the `async (dispatch)=>{...}` thunk function that `redux-thunk` middleware runs. `dispatch(fetchCategories)` dispatches the creator function itself — the middleware doesn't understand it, the fetch never runs, and in DevTools you won't even see `categories/fetch/pending`. `dispatch(fetchCategories())` is correct — the thunk function is dispatched, middleware runs it: `dispatch(pending)` -> `fetch` -> `dispatch(fulfilled/rejected)` automatically.

</details>
