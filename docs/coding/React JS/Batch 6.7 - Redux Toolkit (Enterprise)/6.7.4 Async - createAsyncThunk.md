So far `increment`/`decrement` were synchronous — a button click directly did `state.count++`. In a real app, `6.5:310` `useFetch` fetched categories from an API — `isLoading`, `error`, `data` were 3 states. How does async work in an RTK store? You can't just write `reducer: async (state) => { await fetch... }` — reducers are **pure**, they can't be async. So how? In this doc, first the **manual** thunk pain, then `createAsyncThunk` as the better alternative — not a dump, stage by stage.

# Doc 6.7.4 — Async — createAsyncThunk (Better Than Manual Try/Catch)

## Where We Left Off

In `6.7.2` we learned `createSlice` + `configureStore`, in `6.7.3` we connected `Provider` + the typed `useAppSelector` (dispatch was still plain `useDispatch`). A synchronous counter is running. Now async — the enterprise pattern for fetching data into the store — and along the way, the store finally gets its typed dispatch.

## Broader Goal

In this doc we'll understand async with a **problem-first** approach: first think about why a reducer can't be async, then feel the 3-action boilerplate in manual code, then see how `createAsyncThunk` automates 3 actions in 1 function. This async is the foundation for the `categories` slice in the `6.7.5` project.

---

You might think — `reducers: { fetchCategories: async (state) => { const res = await fetch(...); state.items = await res.json() } }` — just fetch inside the reducer. But `6.7.1` told us reducers are **pure** — same `state + action` must always give the same `newState`, no `fetch`, `Date.now()`, `Math.random()`. How would time-travel work with an `await` in between? How would DevTools show the "pending -> fulfilled" history? That's why the reducer stays synchronous, async happens **outside** in a thunk, and the reducer only updates state based on that result.

A thunk is a **function that returns a function** — you can give `dispatch` an async function instead of an action object, and the middleware (built-in `redux-thunk` in RTK) runs that function with `dispatch` and `getState`. Manually, a thunk needs 3 actions: `fetch/pending` (loading true), `fetch/fulfilled` (save data), `fetch/rejected` (error). Every async needs 3 action types + 3 cases + try/catch — that's the boilerplate RTK's `createAsyncThunk` compresses into 1 function.

**Nutshell:** Thunk is the middleware pattern that lets you `dispatch` an async function instead of an action object, so the reducer stays pure and the async result arrives via 3 actions (pending/fulfilled/rejected).

---

Your own way first — and it's a legitimate one. The `6.5` pattern: inside a `useEffect`, `await fetch(...)`, check `res.ok`, then `dispatch(setCategories(data))`, where `setCategories` is a normal reducer in your slice. Plenty of people ship exactly that, and it works with everything built so far.

What it leaves behind: the loading and error states are yours to manage — dispatch a `loading` action before the fetch, then success/failure after, with try/catch, in *every* component that fetches — and the fetch logic itself gets scattered, copied wherever the data is needed. A thunk just moves that same code out of the component and next to the slice.

But hand-moving it means hand-writing the 3 actions (`pending`/`fulfilled`/`rejected`) yourself — see that pain below first, then you'll appreciate what `createAsyncThunk` automates. "3 actions auto, why?" — because you'll have just written all 3 yourself.

Manual thunk — in a separate `categoriesManual.ts` (written by hand, without RTK) — just for understanding, don't create this file in your project:

```ts
// categoriesManual.ts — ❌ read-only example, tedious on purpose
interface CatState { items: string[]; status: "idle"|"loading"|"succeeded"|"failed"; error: string|null }

type CatAction =
  | {type:"categories/fetch/pending"}
  | {type:"categories/fetch/fulfilled", payload: string[]}
  | {type:"categories/fetch/rejected", payload: string};

const initial: CatState = { items: [], status:"idle", error: null };

export function catReducer(state=initial, action: CatAction): CatState {
  switch(action.type){
    case "categories/fetch/pending": return {...state, status:"loading", error:null}
    case "categories/fetch/fulfilled": return {...state, status:"succeeded", items: action.payload}
    case "categories/fetch/rejected": return {...state, status:"failed", error: action.payload}
    default: return state;
  }
}

// Thunk function (give dispatch a function)
export const fetchCategoriesManual = () => async (dispatch: any) => {
  dispatch({type:"categories/fetch/pending"});
  try {
    const res = await fetch("https://www.themealdb.com/api/json/v1/1/categories.php");
    const json = await res.json();
    const items = json.categories.map((c:any)=>c.strCategory).slice(0,5);
    dispatch({type:"categories/fetch/fulfilled", payload: items});
  } catch(e:any){
    dispatch({type:"categories/fetch/rejected", payload: e.message});
  }
};
```

| Line | Why |
|------|------|
| `CatAction` 3 types | Each stage has its own action — pending/fulfilled/rejected |
| `switch` 3 cases | Loading on pending, data on fulfilled, error on rejected |
| `fetchCategoriesManual = () => async (dispatch)` | Thunk — give dispatch a function, middleware runs it |

Boilerplate: 1 async needs 1 type union (3), 1 reducer (3 cases), 1 thunk (try/catch + 3 dispatch). 5 async = 50 lines.

In a component:

```ts
dispatch(fetchCategoriesManual() as any);
// DevTools will show 3 actions: pending -> fulfilled
```

It works, but every async repeats this same 3-step — the same DRY violation from `6.2`.

---

The manual 3-step pattern is the same for every async — `pending -> try fetch -> fulfilled/rejected`. `createAsyncThunk` folds that same 3-step into one function — you pass a URL and an async payload creator, and it handles the 3 action creators + dispatch + error handling automatically.

`createAsyncThunk("categories/fetch", async () => { return data })` — the first argument is `typePrefix` (`categories/fetch`), the second is the async `payloadCreator`. It returns 1 **thunk creator** that automatically creates 3 action creators: `fetchCategories.pending`, `fetchCategories.fulfilled`, `fetchCategories.rejected` — handle them in the slice's `extraReducers` with `builder.addCase`. And `builder.addCase` is just the modern spelling of the manual `switch`'s `case` from Stage 2 — same job: *when this action type arrives, run this reducer* — chained instead of stacked. (Calling the creator — `fetchCategories()` — produces the actual thunk function; `6.7.1`'s vocabulary, now live.)

Before any code — the plan, in order. (Jumping into state before looking at the API is exactly the wrong order; the shape of the data decides the types.)

1.  **Look at the API first** — open `https://www.themealdb.com/api/json/v1/1/categories.php` in the browser. Top level: an object with one key, `categories`, whose value is an array. Each item: `idCategory`, `strCategory`, `strCategoryThumb`, `strCategoryDescription` — four fields, all strings (even the id).
2.  **Define the types from what we see** - the API gives back full objects, not names, so `items: string[]` is not a blind guess. There is a real choice here: store the **full objects** (all four fields - faithful to the API, can show images later without refetching) or store **only the names** (smaller state, but data thrown away). This course keeps **names only** (`string[]`), because that is what the `6.7.5` Expense Tracker project renders and it keeps the state small. Either works - the `.map((c) => c.strCategory)` below is where the decision shows up in code. Then the status union `idle | loading | succeeded | failed`, then the state type.
3.  **Write the state and the slice** — starting state, then `createSlice`.
4.  **Write the thunk** — `createAsyncThunk`, the function that fetches.
5.  **Connect the thunk to the slice** — the `extraReducers` cases for pending/fulfilled/rejected.
6.  **Register the slice in the store.**
7.  **Use it in the UI** — `useEffect` dispatches the thunk; the screen shows loading, error, or the list.

Following that order — new slice `src/rtk/categoriesSlice.ts` (created in this stage, not before, now it's needed):

```ts
// src/rtk/categoriesSlice.ts — STAGE 3 minimal
import { createSlice, createAsyncThunk } from "@reduxjs/toolkit";

interface CatState {
  items: string[];
  status: "idle" | "loading" | "succeeded" | "failed";
  error: string | null;
}

const initialState: CatState = { items: [], status: "idle", error: null };

export const fetchCategories = createAsyncThunk(
  "categories/fetch",
  async () => {
    const res = await fetch("https://www.themealdb.com/api/json/v1/1/categories.php");
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    const json = (await res.json()) as { categories?: Array<{ strCategory: string }> };
    return (json.categories ?? []).map((c) => c.strCategory).slice(0, 5);
  }
);

const categoriesSlice = createSlice({
  name: "categories",
  initialState,
  reducers: {}, // no sync reducers in this slice, just async
  extraReducers: (builder) => {
    builder
      .addCase(fetchCategories.pending, (state) => {
        state.status = "loading";
        state.error = null;
      })
      .addCase(fetchCategories.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.items = action.payload;
      })
      .addCase(fetchCategories.rejected, (state, action) => {
        state.status = "failed";
        state.error = action.error.message ?? "Something went wrong";
      });
  },
});

export default categoriesSlice.reducer;
```

Every line:

| Code | Why |
|------|------|
| `createAsyncThunk("categories/fetch", async () => ...)` | `typePrefix` auto-generates 3 types: `categories/fetch/pending` etc. |
| `async () => { fetch... return items }` | Whatever you `return` becomes `fulfilled`'s `payload` — arrives in `action.payload` |
| `extraReducers: (builder) =>` | `reducers` is for sync, `extraReducers` is for the external thunk's 3 cases |
| `builder.addCase(fetchCategories.pending, ...)` | On pending, `status="loading"` — Immer-style mutation |
| `state.error = action.error.message` | On rejected, error is in `action.error`, not `action.payload` — `createAsyncThunk` puts thrown errors into `rejected` |

Two exports, two audiences: the **default** export is the reducer — that's the line that goes into the store's `reducer: {categories}`. The **named** export `fetchCategories` is the thunk creator — that's what components dispatch. Same file, one reader per line.

First attempt — wire it up with what `6.7.3` actually gave us: typed `useAppSelector`, plain `useDispatch`:

```tsx
// src/rtk/CategoriesDemo.tsx — first attempt (plain dispatch)
import { useEffect } from "react";
import { useDispatch } from "react-redux";
import { useAppSelector } from "./hooks";
import { fetchCategories } from "./categoriesSlice";

export function CategoriesDemo() {
  const { items, status, error } = useAppSelector((s) => s.categories);
  const dispatch = useDispatch();

  useEffect(() => {
    dispatch(fetchCategories()); // ❌ hover this
  }, [dispatch]);

  if (status === "loading") return <p>⏳ Loading categories...</p>;
  if (status === "failed") return <p style={{color:"red"}}>❌ {error}</p>;
  return <p>Categories: {items.join(", ")}</p>;
}
```

Red underline on `dispatch(fetchCategories())` — the message: `Argument of type 'AsyncThunkAction<...>' is not assignable to parameter of type 'UnknownAction'`. Sync actions like `increment()` passed because plain `useDispatch()` types as `Dispatch<UnknownAction>` — it knows ordinary action **objects** like `{type:"counter/increment"}`. A thunk isn't an object, it's a function, so TypeScript says it isn't a known action. (The code would actually run — the store *does* accept thunks; TypeScript just doesn't know it yet.)

This is the loose end `6.7.3` flagged: `AppDispatch` was left out because nothing used it then. Now the problem has shown up, so it's back. Two small steps:

**Step 1 — `store.ts`, at the bottom next to `RootState`:**

```ts
export type AppDispatch = typeof store.dispatch;   // the store's own dispatch — thunk support included
```

The type lives in `store.ts` because it's taken *from* the store — not `hooks.ts`, which is only where we *use* it.

**Step 2 — `hooks.ts`, add the typed dispatch:**

```ts
// src/rtk/hooks.ts — updated
import { useDispatch, useSelector } from "react-redux";
import type { RootState, AppDispatch } from "./store";

export const useAppSelector = useSelector.withTypes<RootState>();
export const useAppDispatch = useDispatch.withTypes<AppDispatch>();
```

`useAppDispatch` is `useDispatch` with `AppDispatch` already filled in — the same trick as `useAppSelector` — so it knows thunks are allowed.

**Step 3 — swap one line in `CategoriesDemo`:**

```tsx
import { useAppSelector, useAppDispatch } from "./hooks";   // instead of useDispatch from react-redux
const dispatch = useAppDispatch();                          // underline gone
```

Render `CategoriesDemo` in `App.tsx`, run `bun run dev` -> `⏳ Loading...` -> `Categories: Beef, Chicken...` In DevTools: `categories/fetch/pending` -> `categories/fetch/fulfilled` with the payload array. Heads-up — `main.tsx` wraps the app in `React.StrictMode`, and in dev its double-mount runs the effect twice, so you'll see the pair **doubled** (4 actions). That's StrictMode's double-invoke, not a double-fetch bug; production runs once.

One thing worth noticing: the component never checks `status === "succeeded"` — it handles `loading` and `failed` with early returns and lets everything else fall through to the list. That's fine here, but it means `idle` (before the fetch) also renders an empty list for a moment. `succeeded` earns its place because it's the only way to tell "haven't asked yet" (`idle`, empty) apart from "asked and got nothing" (`succeeded`, empty) — and later it gates re-fetching (`if (status === "idle") dispatch`) and shows old data during a refresh. Both the short fall-through and an explicit `if (status === "succeeded")` work; pick explicit when the distinction matters.

And here's the beat worth pausing on — this is exactly what `6.5`'s `useFetch` did: fetch from a URL, with loading, success, and error states. Same idea, one difference: **where the states live.** In `useFetch` the three states sat **inside the component** (`isLoading/error/data`); here they sit **in the slice** as one `status` that moves `idle -> loading -> succeeded -> failed` — plus `error` and `items`. That's why 3 components reading categories all see the same loading flag now: the state moved from component memory into the store.

| **5 async** | ~75 lines | ~25 lines |

## Common Mistakes

*   **Wrote `fetchCategories` in `reducers` instead of `extraReducers`:** `reducers` is only for sync `state =>` reducers, the 3 cases of `createAsyncThunk` go in `extraReducers` with `builder.addCase` — putting it in `reducers` gives TS error `Property 'pending' does not exist`.
*   **`dispatch(fetchCategories)` without `()`:** the return of `createAsyncThunk` is a **thunk creator**, `dispatch` needs the result of calling `fetchCategories()` — `dispatch(fetchCategories)` dispatches the creator function itself, the fetch won't run.
*   **Async/await inside a reducer:** `reducers: { fetch: async (state)=>{await fetch...}}` — the core problem is **purity**: same input must give same output, but an `await` means the same action could produce different states (network result varies), and DevTools time-travel replay would re-run the fetch every time it rewinds. The `A non-serializable value was detected` warning you'd also see is just a side effect of a Promise sitting in state — not the reason reducers must stay sync.
*   **Confusing `action.payload` and `action.error`:** in `fulfilled`, data is in `payload`; in `rejected`, error is in `error.message` — `rejected` doesn't have `payload` unless you use `rejectWithValue`.
*   **Kept plain `useDispatch()` after thunks arrived:** it types as `Dispatch<UnknownAction>` — fine for `increment()`, but `dispatch(fetchCategories())` errors because a thunk is a function, not an action object. The store does accept them; `AppDispatch` is how you tell TypeScript. Fix = the two steps from TEST: `export type AppDispatch = typeof store.dispatch;` in `store.ts`, then `useAppDispatch` in `hooks.ts`.

## What It Is NOT

*   **NOT a `useFetch` replacement:** `useFetch` (6.2) is a simple hook, RTK async caches in the global store — if you need `categories` in 3 components, keep it in the store; if in 1 component, `useFetch` is enough.
*   **NOT `RTK Query`:** RTK Query is a separate data-fetching layer (caching, deduplication) — `createAsyncThunk` is just a thunk + 3 actions, you implement caching yourself. In interviews, `TanStack Query` vs `RTK Query` is a common comparison question — here we only learned `createAsyncThunk`.
*   **NOT fetch in a reducer:** always `fetch` in the thunk, in the reducer only set `state.status/items/error`.

## Summary

*   A reducer can't be async — it must stay pure, async goes in a thunk.
*   Manual async = 3 action types + switch + thunk (~25 lines).
*   `createAsyncThunk("prefix", async()=>return)` = 1 function, 3 actions auto, handle in `extraReducers` with `builder.addCase(pending/fulfilled/rejected)`.
*   Plain `useDispatch()` only knows action objects — the first `dispatch(fetchCategories())` is what earns `AppDispatch` (`typeof store.dispatch`, thunk support included) and `useAppDispatch`.
*   `store.dispatch(fetchCategories())` -> `pending` -> `fulfilled/rejected`, traceable in DevTools.

## In Your Own Words

1. Why can't you use `await fetch` inside a reducer? What's the connection to pure-function time-travel?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A reducer is `(state, action) => newState` and must be pure — same input always gives same output, no `fetch` or `Date.now()`. If a reducer had `await fetch`, the same `fetchCategories` action would sometimes be `pending`, sometimes `fulfilled` — same input, different output, not pure. DevTools time-travel replays every action to rebuild state — an async reducer would re-fire fetch on every replay, the network could fail, history gets corrupted. That's why async lives in a thunk (outside), and the reducer only updates state on the 3 results (pending/fulfilled/rejected).

</details>

2. Manual 3 actions vs `createAsyncThunk`'s 3 actions — the names are the same, but how are they created differently? Explain with the example `categories/fetch/pending`.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Manually, you write the `type CatAction = {type:"categories/fetch/pending"} | {type:"categories/fetch/fulfilled", payload:string[]} | ...` union, a `switch` with 3 cases in `catReducer`, and `fetchCategoriesManual = () => async (dispatch)=>{dispatch({type:"categories/fetch/pending"}); try{...dispatch({type:"categories/fetch/fulfilled", payload})} catch...}` thunk by hand. With RTK, `createAsyncThunk("categories/fetch", async()=>return items)` is a single call — the `typePrefix` `"categories/fetch"` auto-generates 3 types (`categories/fetch/pending` etc.), `fetchCategories.pending/fulfilled/rejected` action creators are auto-created, the thunk function is auto-generated, and in `extraReducers` you only handle them with `builder.addCase`. 25 lines become 8.

</details>

3. `dispatch(fetchCategories)` vs `dispatch(fetchCategories())` — what's the difference of those parentheses, and what happens if you get it wrong?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `createAsyncThunk` returns a **thunk creator** — calling `fetchCategories()` produces the `async (dispatch)=>{...}` thunk function that `redux-thunk` middleware runs. `dispatch(fetchCategories)` dispatches the creator function itself — the middleware doesn't understand it, the fetch never runs, and in DevTools you won't even see `categories/fetch/pending`. `dispatch(fetchCategories())` is correct — the thunk function is dispatched, middleware runs it: `dispatch(pending)` -> `fetch` -> `dispatch(fulfilled/rejected)` automatically.

</details>

## Cheat Sheet (Quick Recall)

**`createAsyncThunk` = one function that generates 3 action types automatically** — `pending` → `fulfilled` | `rejected`. Dispatch it like a normal action; the slice responds via `extraReducers`.

```ts
export const fetchCategories = createAsyncThunk(
  "categories/fetch",                    // typePrefix — RTK generates `categories/fetch/pending` etc.
  async () => {                          // payloadCreator — async function, return value = action payload
    const res = await fetch("...");
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    const json = await res.json();
    return json.categories.slice(0, 5);
  }
);

// in the slice — reducers is for sync state changes; extraReducers responds to the thunk
const categoriesSlice = createSlice({
  name: "categories",
  initialState,
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchCategories.pending, (s) => { s.status = "loading" })
      .addCase(fetchCategories.fulfilled, (s, a) => { s.status = "succeeded"; s.items = a.payload })
      .addCase(fetchCategories.rejected, (s, a) => { s.status = "failed"; s.error = a.error.message ?? "Something went wrong" });
  },
});

// in a component — dispatch the thunk, not the creator
dispatch(fetchCategories());
```

**Where it lives:** the thunk stays with the slice that owns the data (one file `categoriesSlice.ts`). `pending` dispatches before the fetch fires; `fulfilled`/`rejected` fire with the result. `action.error` carries any thrown error; `action.payload` carries the return value (or `rejectWithValue`’s payload).
