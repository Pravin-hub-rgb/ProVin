### 54. What is the core Redux flow?

**Answer:** Single store → **actions** (plain objects describing what happened) → **reducers** (pure functions that return the new state) → store updates → components re-render via `useSelector`. One direction, no surprises — which is exactly what makes it debuggable.

**Likely follow-up:** *Why "pure" reducers?* — same input always gives the same output, no side effects inside; that's what lets devtools time-travel and lets you test reducers with plain function calls.

---

### 55. Why is Redux Toolkit (RTK) better than plain Redux?

**Answer:** Plain Redux drowns you in boilerplate (action types, action creators, switch statements, spread everything). RTK fixes each pain: `createSlice` auto-generates actions + reducers, `configureStore` ships sensible defaults (thunk, devtools), Immer handles immutability inside reducers, and RTK Query caches/fetches data.

**Likely follow-up:** *What does Immer let you do?* — write `state.push(...)`-style mutable code that produces an immutable update under the hood — no manual spreads in every case.

---

### 59. What is middleware in react-redux?

**Answer:** Code that sits between `dispatch(action)` and the reducer — it can intercept, transform or delay actions before they reach the store. Thunk is the standard example: it lets you dispatch functions that fetch data first, then dispatch the real action with the result. Configured in `configureStore({ middleware })`.

**Likely follow-up:** *Give another use.* — logging, analytics, error reporting, attaching auth tokens to actions — anything that must run on every dispatched action.

---

### 60. How do you handle asynchronous operations and side effects in react-redux?

**Answer:** With middleware — specifically **thunk action creators** (`createAsyncThunk` in RTK): dispatch a function that calls the API, and it dispatches `pending` → `fulfilled`/`rejected` for you, which the slice's `extraReducers` handles.

**Likely follow-up:** *Where does the UI show loading?* — from the thunk's lifecycle flags in the slice state (`isLoading`, `error`), read via `useSelector` — not from component-local booleans.

---

### E1. What does `<Provider>` do, and why typed hooks?

**Answer:** `Provider` (with `store={store}`) puts the store on React context so any component can `useSelector`/`useDispatch` without prop-passing — wrap the app once in `main.tsx`. Plain `useDispatch()` returns `any`, so app-wide typed hooks (`useAppDispatch`/`useAppSelector` built from `RootState`/`AppDispatch`) give autocomplete and catch wrong selector shapes at compile time.

**Likely follow-up:** *What breaks if you forget the Provider?* — hooks throw "could not find react-redux context value"; and hooks typed wrong silently lose type safety across every component.

---

### E2. How does redux-persist keep state alive across reloads?

**Answer:** `persistReducer` wraps the root reducer and `persistStore(store)` drives it; a `PersistGate` waits for rehydration before rendering. State is written to `localStorage` (key like `persist:trackit`, with a `version` for migrations) and reloaded on startup — so TrackIt's habits survive F5.

**Likely follow-up:** *What should and shouldn't be persisted?* — durable domain state (habits, streaks) yes; transient state (loading flags, open modals) no — rehydrating stale `isLoading: true` would wedge the UI.
