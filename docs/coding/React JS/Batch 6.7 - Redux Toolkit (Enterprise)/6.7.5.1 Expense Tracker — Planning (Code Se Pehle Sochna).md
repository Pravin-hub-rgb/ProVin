## 1. What Are We Building? — Purpose

Expense Tracker — note down daily expenses (tea, bus, lunch), filter by category (Food/Travel), see how much was spent in total. Why this project? Because this combines **all RTK concepts we've learned so far** in one place:

| RTK Concept (from batch) | Where It Applies |
|---|---|
| `createSlice` sync `reducers` | `addExpense` / `deleteExpense` / `setFilter` |
| `createAsyncThunk` | `fetchCategories` — API categories (Beef, Chicken...) |
| `useAppSelector` selective | Calculate total, filtered list |
| `configureStore` + `Provider` | Central store, entire app |
| `PayloadAction<T>` | `addExpense` payload is `Expense` |

The Zustand `To-Do v3 (6.5)` had the same idea — but there, `set` was direct, here every change needs a `dispatch` from the store. The back-to-back comparison will be in Part 3.

Connection to DukaanOS? In DukaanOS, `stock` + `sale` + `udhaar` are also separate slices — the same pattern here with `expenses` + `categories` slices.

## 3. What Is the Data Shape? — Decided by UI (Not the Other Way)

`how to write project in series prompt.md:64` says — **data is decided by UI, not the other way around.** First think about what appears on the list, then create the field.

What appears on the list? Each row: `“Chai — ₹20 (Food) [Delete]”`. This means each expense needs **title**, **amount**, **category**. Plus `id` (React `key` + for delete), `date` (not shown now, but can be extended later in `6.7.5.5` for “today's expenses” filter).

| Field | Type | Why (UI reason) | Example |
|---|---|---|---|
| `id` | `string` | `key` + `deleteExpense(id)` for uniqueness | `"exp-1703-abc"` |
| `title` | `string` | Title text in list | `"Chai"` |
| `amount` | `number` | `₹amount` in list + sum in Stats | `20` |
| `category` | `string` | Category badge + filter from FilterBar | `"Food"` |
| `date` | `string` (ISO) | Not shown now, but kept for future filter | `"2026-08-25"` |

Type:

```ts
// this type will become a real file in 6.7.5.3, here only for planning
interface Expense {
  id: string;
  title: string;
  amount: number;
  category: string;
  date: string; // ISO string, not displayed now but stored
}
type FilterStatus = "all" | string; // "all" or some category name
```

**Every field has a reason — not random.** `amount` is `number`, not `string`, because the total needs `expenses.reduce((sum, e) => sum + e.amount, 0)` — a numeric sum. If string, `"20" + "50" = "2050"` bug.

What about the shape of Categories? `string[]` — `["Beef","Chicken","Dessert"]` fetched from `6.7.4`'s `fetchCategories`, stored as `items: string[]` in `categoriesSlice`.

## 4. How Does Data Flow? — Separate File = DRY

In `6.7.1`, we saw the store's `getState/dispatch/subscribe`, in `6.7.3`, the `Provider`. Here the flow:

```
src/
├── rtk/
│   ├── store.ts               # configureStore({reducer:{expenses, categories}})
│   ├── hooks.ts               # useAppSelector, useAppDispatch (from 6.7.3)
│   ├── expensesSlice.ts       # Expense + FilterState + add/delete/setFilter
│   └── categoriesSlice.ts     # fetchCategories thunk (copy from 6.7.4, adapt)
├── components/
│   ├── ExpenseForm.tsx        # dispatch(addExpense)
│   ├── ExpenseList.tsx        # useAppSelector filtered + dispatch(delete)
│   ├── FilterBar.tsx          # dispatch(setFilter)
│   └── Stats.tsx              # useAppSelector total
└── App.tsx                    # Provider already in main.tsx, categories useEffect dispatch
```

**Why do functions live in separate files?** In `6.7.5.3`, `expensesSlice` will have `addExpense(state, action: PayloadAction<Expense>)` — the page doesn't know how the `state.items.push` (Immer) works, it just dispatches `addExpense(expense)`. Tomorrow, if we need to add validation to `amount` (`amount > 0`), only the slice changes, not the components — that's the payoff of abstraction in `how to write project in series prompt.md:130`.

## Common Mistakes (Even in Planning)

*   **Data shape copied from API, not UI:** If the API returns `strCategory`, we kept `strCategory` as the field name — the UI needs `category`, not the API's name. In `categoriesSlice`, do `map(c => c.strCategory)` to create clean `string[]` — we did the same in `6.7.4`.
*   **`amount` stored as `string`:** Input gives `e.target.value` as string, but store `number` — convert with `Number(value)` before dispatching. Otherwise, the `reduce` total has a bug.
*   **Everything dumped into one slice:** `expenses + categories + filter` in one slice — the slice's `name` means an entirely different section (the registered section). `expensesSlice` (items+filter) and `categoriesSlice` (items+status) should be separate — combine in `store` with `combineReducers`.

## In Your Own Words

1. In planning, why is the data shape decided by UI, not copied directly from the API? Explain with the `strCategory` vs `category` example.

<details>
<summary>Show Answer</summary>

**Sample Answer:** The UI needs a `category` badge, but the API returns the `strCategory` key. If we store the API key directly, every component uses `expense.strCategory` — the UI's name becomes tightly coupled to the API's name. In `categoriesSlice`, we do `map(c => c.strCategory)` to create clean `string[]`, and in `Expense`, we use `category: string`. If the API changes tomorrow (`categoryName`), only the slice's mapping changes, not the components. Starting from UI makes the field's purpose clear — `amount` is a number (for the total sum), `id` is for `key` and delete — no random fields.

</details>

2. Why is keeping all the UI on a single page a good decision for RTK learning — what gets distracted if we add routing?

<details>
<summary>Show Answer</summary>

**Sample Answer:** This batch's goal is to learn `createSlice` + `createAsyncThunk` + `useAppSelector`, not routing. On a single page, the flow of both `expenses` and `categories` slices shows in one place — under the `Provider` in `App.tsx`, the Form/List/Stats. If we add routing (`/expenses/:id`), then `App Router`/`react-router` is an extra concept, parameters, layouts — it distracts from RTK. The `To-Do` in `6.5` was also single page, making comparison easy — same scope, different library.

</details>

3. Why are slices in `src/rtk/` separate files, not inside `App.tsx`? Connect this to the DRY point from `6.1`.

<details>
<summary>Show Answer</summary>

**Sample Answer:** In `6.1`, we extracted `useToggle` into `hooks/` so 2 components could reuse it, keeping it DRY. Same idea here — the `addExpense`/`deleteExpense` logic lives in one place in `expensesSlice`, and `ExpenseForm`, `ExpenseList`, `Stats` all reuse via `dispatch`/`selector`. If the slice were in `App.tsx`, then each component would need prop drilling or import from `App.tsx` — `App.tsx` grows to 200 lines. Separate file = single source of truth; if we need to add `amount` validation tomorrow, only 1 file changes.

</details>
