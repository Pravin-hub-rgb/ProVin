
## MCQ

Q: In Redux's three core words — store, action, reducer — what does each one do?
A. Store holds the state, action says what happened, reducer decides the new state
B. Store decides the new state, action holds the state, reducer says what happened
C. Store says what happened, action holds the state, reducer decides the new state
D. Store, action, and reducer all hold the same state — they are three copies

> A. The store is the single state container, an action is a plain object describing the event, and the reducer is the pure function that computes the next state from state + action. B, C, and D shuffle the roles — the reducer never "describes what happened", it reacts to it.

Q: Why did the industry move from plain Redux to Redux Toolkit?
A. Plain Redux required writing action type strings, switch statements, and store wiring by hand — RTK generates them from one `createSlice`
B. Plain Redux couldn't run in browsers older than 5 years — RTK added browser support
C. RTK is a completely different library with a different store — plain Redux was abandoned
D. Plain Redux only worked with JavaScript — RTK added TypeScript support

> A. The complaint since 2015 was boilerplate: unions, switches, hand-rolled returns, separate store wiring. `createSlice` + `configureStore` collapse all of that into one object. B is wrong — both run everywhere. C is wrong — RTK *is* Redux, same store and concepts, official modern style. D is wrong — plain Redux had TypeScript support too.

Q: Which timeline of Redux's history is correct?
A. Redux core 2015 → react-redux connector close behind in 2015 → Redux Toolkit 2019
B. Redux Toolkit 2015 → Redux core 2017 → react-redux 2019
C. react-redux 2015 → Redux Toolkit 2016 → Redux core 2018
D. Redux core and RTK both launched in 2015 — react-redux came much later

> A. Core + its connector landed together in 2015; the boilerplate complaints lasted until the official answer, RTK, arrived in 2019. B, C, and D flip the order — RTK came *after* years of manual-style complaints.

Q: When you "cross the wall" from old-style Redux to RTK, what stays the same?
A. The react-redux connector — `<Provider>` + `useSelector`/`useDispatch` work exactly as before
B. Everything — RTK changed the store, the actions, and the connector
C. Only the action types — the reducer style had to change completely
D. Nothing — RTK projects don't install `react-redux` at all

> A. Toolkit only replaces *how you write* the store and reducers (`createSlice`, `configureStore`). The connector (react-redux) shipped in 2015 and was never replaced — that's why RTK projects still install both `@reduxjs/toolkit` and `react-redux`. B, C, and D are wrong — the three ideas (store/action/reducer) and the connector are unchanged.

Q: In an old-style reducer, why is `state.count++` a bug?
A. It mutates the same object and returns the same reference — Redux/React see no change, so the UI never re-renders
B. The `++` operator is not allowed inside a switch statement
C. It makes the reducer async, which Redux forbids
D. It only works when there is more than one reducer

> A. Plain reducers have no Immer — `state.count++` changes the object in place and the reference stays `===`, so change detection sees nothing. B is syntactically fine. C — `++` has nothing to do with async. D — it's broken with any number of reducers.

Q: What three things does `createSlice({name, initialState, reducers})` generate for you?
A. Reducer function, action creators, and action type strings — from one object
B. The store, the Provider, and the typed hooks
C. The network layer, the cache, and the persistence file
D. Component files, folder structure, and test files

B — those come from `configureStore` and react-redux, separate steps. C — RTK core doesn't fetch or persist on its own. D — `createSlice` doesn't touch files.

Q: Inside a `createSlice` reducer, `state.count += 1` looks like mutation but is safe. What makes it safe?
A. Immer wraps the state in a draft proxy and produces a new immutable object under the hood
B. RTK disables React's change detection for slices
C. The reducer is called twice — the second call fixes the mutation
D. Redux compares values instead of references, so mutation doesn't matter

> A. Immer records your changes on the draft and returns a brand-new object — mutation-looking code, immutable result. B — change detection is very much on. C — reducers are not called twice. D — Redux still compares references; Immer is what changes the reference.

Q: What does `configureStore({reducer: {counter: counterReducer}})` give you beyond `createStore`?
A. DevTools, default middleware (thunk + serializable checks), and auto `combineReducers` — built in
B. The React `<Provider>` wrapper for free
C. Automatic localStorage persistence
D. A built-in `createSlice` call for every reducer

> A. One call wires the store *and* turns on DevTools, the default middleware (thunk + dev-only serializability checks), and combines the object form of reducers. (Immer is not its job — `createSlice` is what wraps your reducers with Immer, learned in `6.7.2`.) B — Provider is react-redux, still your job (`6.7.3`). C — persist needs `redux-persist` (`6.7.5.5`). D — you still call `createSlice` yourself.

Q: What does `PayloadAction<Expense>` do in `addExpense: (state, action: PayloadAction<Expense>) => ...`?
A. Types `action.payload` as `Expense` — a wrong payload shape is a compile-time error
B. Serializes the payload to JSON before dispatch
C. Tells the reducer to skip this action
D. Stores the payload in localStorage

> A. It's a TypeScript generic — you write the payload's type once and `action.payload` is fully typed, typos caught by the compiler. B — Redux DevTools handles serialization display; no JSON conversion here. C — the action runs normally. D — nothing persists automatically.

Q: Why does the app need `<Provider store={store}>` in `main.tsx`?
A. It hands the one store down through React Context — without it, `useSelector` throws
B. It creates the store — without it there is no Redux state at all
C. It subscribes every component to the store automatically
D. It replaces `useSelector` and `useDispatch` with simpler versions

> A. The store is a plain file export — the Provider makes it reachable via context so the hooks can talk to it. B — `configureStore` creates the store; the Provider only distributes it. C — components subscribe *individually* when they use `useSelector`. D — the hooks still do the reading and dispatching.

Q: When does a component re-render after using `useSelector((s) => s.counter.count)`?
A. Only when the selected value changes (by reference) — other store changes don't re-render it
B. On every store dispatch, regardless of what the selector returned
C. Never — `useSelector` reads once and caches forever
D. Only when the component dispatches an action itself

> A. Selective subscription is the whole point: the component re-renders only if its own selected slice changes. B describes the naive subscribe-everything approach that `useSelector` replaces. C — the subscription stays live. D — reading components re-render too when their slice changes.

Q: Why does the store file export `RootState` and `AppDispatch` types?
A. `RootState = ReturnType<typeof store.getState>` derives state typing from the store — selectors and dispatch are fully typed, no hand-written interface
B. They are required fields that `configureStore` validates at runtime
C. They are cache keys for React Query
D. They replace the `slice.reducer` export

> A. Both types are *derived from the store itself* — `RootState` gives every selector its `s.` autocomplete (wrapped by `useAppSelector`), and `AppDispatch = typeof store.dispatch` carries the thunk middleware, so `useAppDispatch` accepts `dispatch(fetchCategories())` while plain `useDispatch` (typed `Dispatch<UnknownAction>`) rejects the function. B — runtime doesn't check type exports. C — unrelated to RTK. D — reducers are still exported separately.

Q: Why can't a reducer contain `await fetch(...)`?
A. Reducers must be pure — same input gives same output, and DevTools time-travel replays actions to rebuild state; an async reducer would re-fire fetches during replay
B. `await` is not supported in TypeScript reducers
C. Redux only allows async code inside components
D. The store would lose the action object if a reducer were async

> A. Purity + time-travel replay are the two reasons: an await means the same action could produce different states, and replaying history would hit the network again. B — syntax is fine, semantics aren't. C — async lives in thunks, not components specifically. D — the action isn't the issue.

Q: What does `createAsyncThunk("categories/fetch", payloadCreator)` automatically generate?
A. One thunk plus three action creators — `.pending`, `.fulfilled`, `.rejected` — handled in `extraReducers`
B. Three separate reducer files, one per action
C. A `useEffect` hook that fetches for you
D. A loading spinner component

> A. The `typePrefix` generates the three action types, the creators are attached to the thunk, and you wire them in `extraReducers` with `builder.addCase`. B — it's one slice. C — dispatching is still your `useEffect`'s job. D — you render the spinner from `status`.

Q: What's the correct dispatch of an async thunk?
A. `dispatch(fetchCategories())` — call it, so the thunk function runs
B. `dispatch(fetchCategories)` — pass the creator, Redux will call it
C. `fetchCategories()` alone — thunks dispatch themselves
D. `dispatch({type: "categories/fetch"})` only — thunks can't be dispatched

> A. `createAsyncThunk` returns a *thunk creator* — calling it produces the async function that redux-thunk middleware runs (`pending` → fetch → `fulfilled`/`rejected`). B — the creator itself is dispatched, the fetch never runs, no `pending` appears in DevTools. C — nothing runs without `dispatch`. D — manual types work but throw away all the automation — that's the point of the thunk.

Q: For persistence, why is Zustand's `persist({name})` called simpler than RTK's option?
A. Zustand needs one wrapper; RTK needs `redux-persist` + `persistStore` + `PersistGate` + ignored serializable actions
B. Zustand stores data in cookies; RTK can only use files
C. RTK cannot persist state at all
D. Zustand persists automatically without any configuration

> A. One middleware wrapper vs a whole library with a provider gate and 6 ignored actions — the trade-off of RTK's enterprise machinery. B — both use localStorage. C — `redux-persist` exists. D — you still wrap with `persist(...)`.

## TrueFalse

Q: Redux Toolkit is a different library from Redux — an RTK project does not use the same store/actions/reducers concepts.
- True
- False
> False. RTK *is* Redux — official modern writing style, same store, actions, and reducers. What's obsolete is the manual boilerplate, not Redux itself. RTK projects still install `react-redux` too.

---

Q: With `useSelector((s) => s.counter.count)`, the component re-renders on every store dispatch — even when some other slice changes.
- True
- False
> False. `useSelector` subscribes selectively — the component re-renders only when *its* selected value changes by reference. A dispatch on `categories` doesn't touch `counter.count`, so no re-render.

---

Q: In the categories slice, the three async cases go in `reducers` alongside `addExpense`-style functions.
- True
- False
> False. `reducers` is for sync, locally-triggered actions. The thunk's cases (`pending`/`fulfilled`/`rejected`) come from *outside* the slice, so they go in `extraReducers` with `builder.addCase` — putting them in `reducers` is a TS error.

---

Q: `dispatch(fetchCategories)` and `dispatch(fetchCategories())` behave the same way.
- True
- False
> False. Without `()`, you dispatch the creator function itself — middleware doesn't run it, no fetch happens, DevTools never shows `pending`. The parentheses call the creator and produce the thunk that actually runs.

---

Q: Building the Hardcoded UI before the Data Layer helps because a non-updating list can be blamed on the UI first, not the slice.
- True
- False
> True. That's why Part 2 comes before Part 3 — with hardcoded data, a broken `map`/`key` is visibly a UI bug; once slices arrive, you're only changing one layer at a time instead of debugging two at once.
