## 1. Start with the Familiar — The Corner Store Register

You've seen `DukaanOS` — a corner store's accounts. Imagine an old register where each page tracks something different — one page for stock, another for credit, a third for daily sales. Whenever you need to change anything, you have to find the right page, and if one page changes but another doesn't match, the whole account falls apart.

Now imagine a new system — a single **central register** with its own **section (slice)** for each account — a stock section, a credit section, a sales section. Each section has one rule: "anything you want to change, write a **slip (action)** and hand it over — 'add 5kg to stock' — and the clerk (reducer) will update the account based on that slip." Nobody writes directly in the register; everything goes through slips. That way the account history is preserved — which slip came in when, what changed.

Redux Toolkit's `store` is that central register, `slice` is a section, `action` is a slip, and `reducer` is the clerk who reads the slip and updates the account. In Zustand you write directly, `set({count: count+1})` — like writing straight in the register. In RTK you call `dispatch(inc())` — you send a slip, and the reducer figures out what to do. Big difference, and that's where predictability comes from.

---

## 2. What Is RTK — Concept

**Concept:** Redux is a **predictable state container**. That means — the entire app's global state lives in a single `store`, you never mutate state directly, you always send an `action` (a plain object `{type, payload}`), and a **pure function** `reducer` (state + action -> new state) produces the new state. Redux Toolkit (RTK) is Redux's **official, less-boilerplate** way — with `createSlice`, actions and reducers come together, and `configureStore` gives you DevTools + Immer + middleware out of the box.

In original Redux, every piece had to be written separately — `action type` string, `action creator` function, `reducer` switch-case, `store` creation — 4 files. RTK said, "just use `createSlice` and I'll handle the rest."

**Nutshell:** Redux Toolkit is the library that holds the entire app's global state in a central `store` and makes every change predictable through the `action -> reducer` (slip -> clerk) pattern, cutting down boilerplate with `createSlice` and `configureStore`.

## 3. When to Use What — Decision First, Code Later

`docs/coding/WEB-DEV/00-MIND-MAP/webdev-tools-docs/01-frontend-state.md:163` already tags it for us:

| Situation | What To Use | Why |
|---|---|---|
| New project, 1-3 devs, ship fast | **Zustand** | 1KB, no provider, selective re-render built-in |

| **Enterprise, 10+ devs, 40+ slices, time-travel, strict pattern needed, existing codebase** | **Redux Toolkit** | Strict slip-system, DevTools, middleware ecosystem, hiring-familiar |

## 4. Visual — Zustand vs RTK Flow

```
Zustand (direct):
Component -> useStore.set({count: count+1}) -> store update -> selective subscribers re-render
(no slip, direct write)

Redux Toolkit (slip-system):
Component -> dispatch(inc()) --slip--> store -> reducer(state, action) -> new state -> useSelector subscribers re-render
(Immer lets you write like mutating, but creates a new object)
```

Both are central stores, both can do selective re-rendering (Zustand with built-in selector, RTK with `useSelector` + `React.memo`). The only difference is **how you update** — direct vs through a slip.

## Common Mistakes

*   **"Every app needs RTK"** — Small app paying for 40 lines of boilerplate and 12KB bundle — overkill. Remember `6.4:528` "What Zustand Is NOT" — Zustand isn't for everywhere either.
*   **Putting everything in the store** — If you shove form input values, `isModalOpen`, and other local state into the global store, you'll have to think through re-renders on every keystroke. Only put in the store what 3+ unrelated components actually share.
*   **Thinking RTK = Zustand's replacement** — It's not a replacement, it's an alternative for enterprise-scale. The capstone still uses Zustand.

## What It Is NOT

*   **NOT Zustand killer:** Both coexist — new startup Zustand, legacy enterprise RTK.
*   **NOT lightweight alternative:** RTK ~12KB (Zustand 1KB) — expensive for small apps.
*   **NOT server-state solution:** For API caching, `TanStack Query` (Batch 2.3) is still better — RTK is for client global state only.

## Summary

*   Zustand = modern, simple, the default for new projects. RTK = enterprise, predictable, what you'll find in legacy code.
*   Redux core = `store` (central register), `action` (slip `{type, payload}`), `reducer` (clerk, pure function).
*   RTK = Redux's official, less-boilerplate approach — `createSlice` + `configureStore`.
