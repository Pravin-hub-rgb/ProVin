## The History - Redux, react-redux, Toolkit

Redux core landed in **2015** — a tiny framework-agnostic library: one `store`, `dispatch(action)`, pure `reducer` functions. Close behind it in the same year came **react-redux**, the connector: `<Provider>` to hand the store to the tree, first a helper called `connect`, later the `useSelector`/`useDispatch` hooks. Then in **2019**, Redux Toolkit arrived — the official answer to everyone's complaint about boilerplate.

Picture it as your wall:

- **Old side (2015):** Redux core **plus its connector** (react-redux — Provider, selectors). People did *not* hand-build stores like our old exercise did — real apps used the real connector from day one. What they *did* write by hand was the boring repeated part: the action type strings, the `switch` statements, the reducer boilerplate.
- **New side (2019, today):** Toolkit only replaces *how you write* the store and reducers — `createSlice`, `configureStore`. It does not replace the connector. You cross the wall and keep using Provider and the hooks exactly as they are. That's why an RTK project still installs two packages: `@reduxjs/toolkit` and `react-redux`.

The connector living on the old side is the part that confuses everyone: it looks like "Redux stuff", but Toolkit never took it away — it's still what connects your store to React in `6.7.3`.

## The Three Ideas in Old-Style Code

The three ideas didn't change across the wall — only the typing did. Here's what they looked like in 2015. **Read it; don't memorize it:**

```ts
// The old style - for reading, not for writing.

// 1. What an action can be — a union of plain objects
type CounterAction =
  | { type: "counter/increment" }
  | { type: "counter/decrement" }
  | { type: "counter/addBy"; payload: number };

// 2. The reducer — one pure function, a switch per action type
function counterReducer(state = { count: 0 }, action: CounterAction) {
  switch (action.type) {
    case "counter/increment":
      return { count: state.count + 1 };      // hand-rolled new object every time
    case "counter/decrement":
      return { count: state.count - 1 };
    case "counter/addBy":
      return { count: state.count + action.payload };  // payload carries data
    default:
      return state;                            // unknown action -> state unchanged
  }
}

// 3. The store + listening by hand
const store = createStore(counterReducer);
store.dispatch({ type: "counter/increment" });  // -> count: 1

const unsub = store.subscribe(() => {           // hand-written listener:
  console.log(store.getState());                // runs after every dispatch
});
```

Line by line: the **union type** pins the action to known strings (a typo like `"counter/incremnet"` fails at compile time instead of silently hitting `default`). The **switch** is the reducer deciding the new state from the action — notice every branch *returns* a brand-new object, never `state.count++`. `createStore` wires reducer and state together — and note: **`createStore` is deprecated in Redux 5**, kept in this exhibit only as a history picture; you'll never write it yourself (`6.7.2`'s `configureStore` is its replacement). `subscribe` is the listen-by-hand mechanism — every component that cared about the store had to register a listener itself (that job becomes `useSelector` in `6.7.3`).

What Toolkit collapses it into:

| Old, hand-written | Toolkit (from `6.7.2` on) |
|---|---|
| action type union + `switch` + action creators | `createSlice({ name, initialState, reducers })` |
| hand-rolled `return { ... }` new objects | `state.count++` directly — **Immer** makes the new object |
| `createStore(...)` factory | `configureStore({ reducer })` — DevTools + middleware included |
| `subscribe(...)` per component | `<Provider>` + `useSelector` (`6.7.3`) |

One honest detail so nothing surprises you later: in *that* manual switch, `state.count++` would be a **bug** — same object reference, React never re-renders. Inside a `createSlice`, the exact same line is **correct**, because Immer proxies the state and produces a new object under the hood. Same three ideas, different rules about how the new state appears.

## Why We Stop Here

Nobody hires you to write that switch — the industry answer has been "just use Redux Toolkit" since 2019, and plain-Redux tutorials have mostly vanished. You also won't retain hand-written boilerplate; you *will* retain the three ideas, because `6.7.2` rebuilds them in Toolkit form with your same counter.

What the exhibit bought us, in one breath: the vocabulary keeps showing up. `6.7.4`'s `extraReducers` is still a map of cases per action; interview question "why is RTK better than plain Redux?" only makes sense if you've *seen* the plain version; and reading a legacy codebase means recognizing `case "slice/event"` when you meet it. Read once, keep the words, move on.

## Common Mistakes

*   **"I should master manual Redux before RTK."** The direction is backwards — Toolkit is the skill; the old style exists so Toolkit's docs make sense. This doc is a reading assignment, not a gate.
*   **Copying `state.count++` into a manual reducer.** That's the one real bug hiding in the old style — no Immer there, so mutation means a stale UI. The line only becomes safe inside `createSlice`.
*   **Reading the wall as "RTK is a different library."** RTK *is* Redux — same store, same actions, same reducers, official modern writing style. What died on the old side is the boilerplate, not Redux itself.

## What It Is NOT

*   **NOT a skill lesson:** nothing to build, nothing to install. The counter was never meant to be typed out — you already did the hard version once, that's enough forever.
*   **NOT "Redux is dead":** RTK is Redux, maintained by the Redux team. The *manual style* is what's obsolete.
*   **NOT the connector:** Provider/`useSelector` came from react-redux in 2015 and survives the wall untouched — you meet it in `6.7.3`.

## Summary

*   Timeline: Redux core 2015 -> react-redux (the connector) close behind -> Redux Toolkit 2019. The wall replaced the *writing style* (`createSlice`/`configureStore`), never the connector.
*   Three ideas, unchanged: `store` holds state, `action` says what happened, `reducer` decides the new state.
*   Old style = union + switch + `createStore` + hand-rolled new objects. Toolkit = slice + `configureStore` + Immer. Keep the words, skip the typing.

<details>

**Sample Answer:** The manual reducer has no Immer — `state.count++` mutates the existing object and returns the *same reference*. Mutation-looking code, immutable result — only on the Toolkit side of the wall.
