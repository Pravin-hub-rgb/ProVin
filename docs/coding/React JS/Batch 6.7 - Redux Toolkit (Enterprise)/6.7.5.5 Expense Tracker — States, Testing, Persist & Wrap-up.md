## STAGE 1 — States: Loading, Error, Empty (Why, Where, When)

### Imagine

In Dynamic `6.7.5.4`, there was a `status` check, but imagine — if the API is slow, the user sees a blank `FilterBar` and won't know categories are loading. If the API fails, blank `select` with no error visible. Filtering by `Shopping` with no expenses shows a blank list — "nothing exists" vs "no results for this filter". Every state needs its own UI — like Next.js `loading.tsx`/`error.tsx`/`not-found.tsx` from `1.4`, here via `status`.

### CONCEPT

The `status` of `categoriesSlice` has 4 values: `idle` (initial, fetch not started), `loading` (fetching), `succeeded` (items arrived), `failed` (error). For `expenses`, `filtered.length===0` means empty. Each state has its own JSX.

### CODE

`status` check already existed in `App.tsx` from `6.7.5.4 STAGE 3` — refine it here + add empty state in `ExpenseList`:

```tsx
// src/App.tsx — STAGE 1 states refined (existing App.tsx update, only new parts highlighted)
import { useEffect } from "react";
import { useAppSelector, useAppDispatch } from "./rtk/hooks";
import { fetchCategories } from "./rtk/categoriesSlice";
import { ExpenseForm } from "./components/ExpenseForm";
import { FilterBar } from "./components/FilterBar";
import { ExpenseList } from "./components/ExpenseList";
import { Stats } from "./components/Stats";

export default function App() {
  const dispatch = useAppDispatch();
  const { status, error } = useAppSelector((s) => s.categories);

  useEffect(() => {
    if (status === "idle") dispatch(fetchCategories());
  }, [status, dispatch]);

  return (
    <main style={{ maxWidth: 640, margin: "0 auto", padding: 16 }}>
      <h1>💰 Expense Tracker — RTK (States)</h1>
      <Stats />
      {status === "loading" && <p>⏳ Loading categories...</p>}
      {status === "failed" && <p style={{ color: "red" }}>❌ {error} — <button onClick={() => dispatch(fetchCategories())}>Retry</button></p>}
      {status === "succeeded" && <p style={{ color: "#666", fontSize: 13 }}>Categories loaded ✓</p>}
      <ExpenseForm />
      <FilterBar />
      <ExpenseList />
    </main>
  );
}
```

`ExpenseList.tsx` already had the empty state in `6.7.5.4` — verify here:

```tsx
// src/components/ExpenseList.tsx — empty state (already in 6.7.5.4, verify here)
if (filtered.length === 0) return <p>No expenses for {filter}. Add one via form above.</p>;
```

| Code | Why |
|------|------|
| `status==="idle"` check in `useEffect` | Fetch only when `idle` — not again on `loading`/`succeeded`, `createAsyncThunk` from `6.7.4` is idempotent |
| `status==="failed"` + `Retry` | On `fetchCategories` failure, `error.message` is in the store, user can retry — `rejected` case from `6.7.4` |
| `filtered.length===0` | When `Shopping` has 0 items in `expensesSlice`, show empty message — `No expenses for {filter}` from `6.7.5.2` |

### TEST

*   Network throttling with `Slow 3G` → show `⏳ Loading categories...`, then `Categories loaded ✓` + `Beef...` in `FilterBar`.
*   With a wrong API URL `.../categories.php?x=1`, `dispatch(fetchCategories())` → `❌ HTTP 404` + `Retry` button, click `Retry` → back to `loading`.
*   `Shopping` filter → `No expenses for Shopping.` Switch to `Food` → back to `2 expenses`.

## STAGE 3 — Persist (Optional — Zustand vs RTK Trade-off)

### Imagine

In `6.7.5.4`, new expenses reset on refresh — the Zustand `persist` middleware in `6.5` auto-synced to `localStorage` with 1 line `persist({name:"todo-tasks"})` from `6.4:478`. In RTK, manual `localStorage` sync? There's a `redux-persist` library but it needs extra setup + serializable check warnings. Let's look at the trade-off — which for a new project, what legacy gets.

### CONCEPT

*   **Zustand persist:** `create(persist((set)=>..., {name:"key"}))` — 1 wrapper, JSON stringify auto, `partialize` also works.
*   **RTK persist:** `redux-persist` `persistReducer` + `persistStore` + `FLUSH/REHYDRATE` serializable ignore — in `configureStore`, set `middleware: getDefault => getDefault({serializableCheck:{ignoredActions:[...]}})`.

In a nutshell: Persist is the middleware that auto-saves/restores store state to `localStorage` — 1 line in Zustand like built-in, extra lib + config in RTK.

### CODE

**Option A — Simple like Zustand (not recommended for RTK enterprise, but for demo):**

```ts
// src/rtk/store.ts — with redux-persist (add in this stage, not before)
import { configureStore } from "@reduxjs/toolkit";
import { persistStore, persistReducer, FLUSH, REHYDRATE, PAUSE, PERSIST, PURGE, REGISTER } from "redux-persist";
import storage from "redux-persist/lib/storage"; // localStorage
import expensesReducer from "./expensesSlice";
import categoriesReducer from "./categoriesSlice";
import { combineReducers } from "@reduxjs/toolkit";

const rootReducer = combineReducers({ expenses: expensesReducer, categories: categoriesReducer });
const persistedReducer = persistReducer({ key: "expense-rtk", storage, whitelist: ["expenses"] }, rootReducer);

export const store = configureStore({
  reducer: persistedReducer,
  middleware: (getDefault) => getDefault({
    serializableCheck: { ignoredActions: [FLUSH, REHYDRATE, PAUSE, PERSIST, PURGE, REGISTER] },
  }),
});
export const persistor = persistStore(store);
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

```tsx
// src/main.tsx — PersistGate wrap
import { PersistGate } from "redux-persist/integration/react";
import { persistor } from "./rtk/store";
<Provider store={store}>
  <PersistGate loading={null} persistor={persistor}>
    <App />
  </PersistGate>
</Provider>
```

**Trade-off:** `redux-persist` + `PersistGate` + 6 ignored actions — 5x more config than Zustand's `persist({name})`. That's why `plan-03-architecture-cheatsheet.md:69` says `Zustand = sweet spot`; if enterprise already has RTK persist setup, leave it, use Zustand for new projects.

**Option B — Simple manual (if no persist lib):** `store.subscribe` + `localStorage.setItem` from `6.7.1` — like `6.2`'s `useLocalStorage`, can also do manually in RTK — 10 lines.

## Common Mistakes (States + Persist)

*   **Fetch loop in `useEffect` without `status==="idle"` check:** In `useEffect(()=>{dispatch(fetchCategories())},[status])`, the `status` dependency re-fetches on `pending → fulfilled` — without the `idle` check, infinite loop. The `if(status==="idle")` guard is essential.
*   **Forgot `PersistGate`:** Without wrapping `PersistGate` in `redux-persist`, `App` renders before `REHYDRATE` — `expenses.items` is empty, then filled by `persist` but `Stats` flickers. Wait for rehydrate with `PersistGate loading={null}`.
*   **Ignored serializability warning:** If `ignoredActions` not set in `configureStore`, console shows `A non-serializable value was detected` warning — `redux-persist`'s `FLUSH` actions are non-serializable, must be ignored.
*   **Skipped test table:** Saying "Add works" without verifying `Food`/`Beef` filter + `Total` + DevTools — misses the `6.7.5.2` `Reduce` bug `\"2050\"`.

## In Your Own Words

1. In the 4 values of `status` (`idle/loading/succeeded/failed`), what does `idle` do, and how is it different from `loading`? Why the `if(status==="idle")` guard?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `idle` = fetch hasn't started yet (initial), `loading` = fetching after `pending` dispatch. The `idle` guard ensures `useEffect` dispatches `fetchCategories` only the first time — not on `loading/succeeded/failed`. Without the guard and with deps `[status]`, a `status` change from `pending → succeeded` re-triggers `useEffect`, causing an infinite loop. The 3 actions `pending/fulfilled/rejected` from `createAsyncThunk` in `6.7.4` drive the `status`.

</details>

2. Why `PersistGate` in `redux-persist`, and what flicker happens without it inside `Provider`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `redux-persist` sends an async `REHYDRATE` action from `localStorage` — `persistStore` reads `localStorage.getItem("expense-rtk")` and dispatches `REHYDRATE` to the store. `PersistGate` blocks `App` rendering until `REHYDRATE` (`loading={null}`), so it doesn't render with empty `[]` initial state. Without `PersistGate`, `App` first shows `No expenses` with empty `items`, then `Maggie` appears after `REHYDRATE` — flicker. Zustand's `persist` has this gate built-in.

</details>

3. Why verify both UI + DevTools for test table row 3 (`Maggie ₹40 Food` Add)? What could be missed by checking UI only?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Seeing `Maggie — ₹40 (Food)` in UI means the `addExpense` payload looks correct, but if `amount` is string `\"40\"`, it still renders `— ₹40` (string rendering). The `reduce` string concat bug `\"2040\"` would show as `₹2040` in `Total: ₹90` — caught by UI, but the `amount` type bug is saved as `string` in the store. In DevTools, `expenses/addExpense`'s `payload` shows `{amount: \"40\"}` as string — a violation of the `PayloadAction<Expense>` `amount: number` contract. Confirming `amount` as number via both UI + DevTools — the `Number(amount)` conversion is correct.

</details>
