
```ts
// Redux Toolkit (what we'll learn)
```

## 1. Start with Something Familiar — The Corner Store Register

You've seen `DukaanOS` — a corner store billing app. Picture an old register where every page has a different ledger — one page for stock, another for credit, another for daily sales. Need to switch pages? You fumble for the right one. Change something on one page and the other goes out of sync — the whole account gets messed up.

Now imagine a better system — one **central register** where every ledger has its own **section (slice)** — a stock section, a credit section, a sales section. Each section has one rule: "anything you change, write it on a **slip (action)** — 'add 5kg to stock' — and the register clerk (reducer) updates the ledger based on that slip." Nobody writes directly on the register page; everything goes through slips. And you get a history too — which slip came in when, and what changed.

Redux Toolkit's `store` is that central register, `slice` is the section, `action` is the slip, and `reducer` is the register clerk who reads the slip and updates the ledger. In Zustand you wrote directly — `set({count: count+1})` — like writing on the register page. In RTK you `dispatch(inc())` — you send a slip, the reducer figures out the rest. That's the difference — and that's where predictability comes from.

---

## 2. What Is RTK? — Concept

**Concept:** Redux is a **predictable state container**. That means — your entire app's global state lives in one place (the `store`); you never mutate state directly, you always dispatch an `action` (a plain object `{type, payload}`), and a **pure function** `reducer` (`state + action → new state`) produces the new state. Redux Toolkit (RTK) is Redux's **official, less-boilerplate** approach — in `createSlice`, actions and reducers are defined together; `configureStore` provides DevTools + Immer + middleware built-in.

In original Redux, every piece was written separately — the `action type` string, the `action creator` function, the `reducer` with its `switch`, and the `store` creation — spread across 4 files. RTK said: "put it all in one `createSlice`."

**Nutshell:** Redux Toolkit is the library that holds your entire app's global state in a central `store` and makes every change flow through the `action → reducer` (slip → clerk) pattern predictably, while `createSlice` and `configureStore` strip away the boilerplate.

## 3. When to Use Which — Decide Before Code

`docs/coding/WEB-DEV/00-MIND-MAP/webdev-tools-docs/01-frontend-state.md:163` already tags this:

| Situation | What To Use | Why |
|---|---|---|
| New project, 1-3 devs, ship fast | **Zustand** | 1KB, no Provider, selective re-render built-in |
| Medium, 5-8 devs, cart/filters update often | **Zustand** | Same reason, separate stores, persist easy |
| **Enterprise, 10+ devs, 40+ slices, need time-travel, strict pattern, existing codebase** | **Redux Toolkit** | Strict slip-system, DevTools, middleware ecosystem, familiar in hiring |

**Trade-off line:** Zustand's alternatives included `Jotai, Context`; RTK's included `MobX, XState`. We chose **Zustand = new default** because `docs/coding/WEB-DEV/Project Understanding/plan-03-architecture-cheatsheet.md:63` marks `Zustand 🟢 Recommended`, RTK `🟡 Enterprise` — for consistency in choices. The interview line: *"New project → Zustand, legacy enterprise → RTK."*

I made the same mistake myself at first — thought Redux was needed everywhere, wrapped even a small To-Do in `Provider`, created 3 slices, then realized 15 lines of Zustand did it in 50. Totally normal to be confused if the use-cases aren't crystal clear — it took me time too.

## 4. Visual — Zustand vs RTK Flow

```
Zustand (direct):
Component -> useStore.set({count: count+1}) -> store update -> selective subscribers re-render
(no slip, wrote directly)

Redux Toolkit (slip-system):
Component -> dispatch(inc()) --slip--> store -> reducer(state, action) -> new state -> useSelector listeners re-render
(Immer lets you write like you're mutating, but a new object is produced underneath)
```

Both are central stores, both can selective re-render (Zustand with built-in selector, RTK with `useSelector` + `React.memo`). The only difference is the **update mechanism** — direct vs slip.

## Common Mistakes

*   **"RTK everywhere"** — In a small app, the boilerplate (~40 lines, 12KB bundle) is overkill. Remember `6.4:528` `What Zustand Is NOT` — Zustand isn't everywhere either.
*   Shoving everything into the store — form input `value`, `isModalOpen` kind of local state — if you put it in the global store, you'll think about re-render logic on every keystroke. Only put in store what 3+ unrelated components share.
*   Thinking RTK replaces Zustand — it's not a replacement, it's an alternative for enterprise. The Capstone still uses Zustand.

## What It Is NOT

*   **NOT a Zustand killer:** Both coexist — new startups use Zustand, old enterprise uses RTK.
*   **NOT a lighter alternative:** RTK is ~12KB (Zustand 1KB) — expensive for small apps.
*   **NOT a server-state solution:** For API caching, `TanStack Query` (Batch 2.3) is still better — RTK only handles client global state.

## Summary

*   Zustand = modern, simple, new project default. RTK = enterprise, predictable, shows up in legacy.
*   Redux core: `store` (central register), `action` (slip `{type, payload}`), `reducer` (clerk's pure function).
*   RTK = Redux's official less-boilerplate approach — `createSlice` + `configureStore`.
