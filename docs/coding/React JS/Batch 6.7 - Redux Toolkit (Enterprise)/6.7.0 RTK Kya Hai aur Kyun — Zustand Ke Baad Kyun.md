## 1. Start with the Familiar — The Corner Store Register

You've seen DukaanOS — a corner store's ledger. Imagine an old register where each page is a different account — one page for stock, another for credit, a third for daily sales. To change anything you have to find the right page, and if one page gets changed but another doesn't, the whole ledger goes out of sync.

Now imagine a new system — a single central register where each account has its own section (slice) — a stock section, a credit section, a sales section. Each section has one rule: "to change anything, just write a slip (action) — 'add 5kg to stock' — and the register keeper will look at that slip and update the ledger." Nobody writes directly on the register page; everything goes through slips. The ledger keeps a history too — which slip came when, what changed.

Redux Toolkit's `store` is that central register, `slice` is a section, `action` is a slip, and `reducer` is the register keeper who updates the ledger based on the slip. In Zustand you go straight to `set({count: count+1})` — like writing directly on the register page. In RTK you call `dispatch(inc())` — you send a slip; the reducer will figure out what to do. A small difference, but that's where predictability comes from.

---

## 2. What is RTK — Concept

**Concept:** Redux is a predictable state container. In other words — the entire app's global state lives in one place, the `store`; you never mutate state directly, you always dispatch an `action` (a plain object `{type, payload}`), and a **pure function** called a `reducer` (`state + action -> newState`) produces the new state. Redux Toolkit (RTK) is Redux's official, low-boilerplate way — `createSlice` generates action creators and reducers together, and `configureStore` comes with DevTools + Immer + middleware built-in.

In original Redux, you had to write everything separately — an action type string, an action creator function, a reducer with switch-cases, and the store creation — across 4 files. RTK said, "do it all in one `createSlice`."

**Nutshell:** Redux Toolkit is the library that holds global state in a central `store` and makes every change predictable through the `action -> reducer` (slip -> register keeper) pattern, chopping the boilerplate down with `createSlice` and `configureStore`.

## 3. When to Use What — Decide First, Code Later

`docs/coding/WEB-DEV/00-MIND-MAP/webdev-tools-docs/01-frontend-state.md:163` already tags it:

| Situation | What to Use | Why |
|---|---|---|
| New project, 1-3 devs, need to ship fast | **Zustand** | 1KB, no provider, selective re-render built-in |
| Medium, 5-8 devs, cart/filters frequent updates | **Zustand** | Same, separate stores, persist easy |
| **Enterprise, 10+ devs, 40+ slices, time-travel debugging, strict pattern needed, legacy codebase** | **Redux Toolkit** | Strict slip-system, DevTools, middleware ecosystem, familiar in hiring |

**Trade-off line:** Zustand's alternatives were `Jotai`, `Context`, and RTK's alternatives were `MobX`, `XState`. We chose **Zustand = new default** because `docs/coding/WEB-DEV/Project Understanding/plan-03-architecture-cheatsheet.md:63` marks `Zustand 🟢 Recommended` and `RTK 🟡 Enterprise` — for consistency in choices. In interviews say this line: *"New project Zustand, legacy enterprise RTK"*.

## 4. Visual — Zustand vs RTK Flow

```
Zustand (direct):
Component -> useStore.set({count: count+1}) -> store update -> selective subscribers re-render
(no slips, wrote directly)

Redux Toolkit (slip-system):
Component -> dispatch(inc()) --slip--> store -> reducer(state, action) -> new state -> useSelector subscribers re-render
(Immer lets you write as if mutating, but a new object is created)
```

Both are central stores; both can do selective re-render (Zustand built-in selector, RTK `useSelector` + `React.memo`). The only difference is the update method — direct vs slip-based.

## Common Mistakes

*   **"RTK everywhere":** A small app would get 40 lines of boilerplate, 12KB bundle — overkill. Remember `6.4:528` "What Zustand Is NOT" — Zustand isn't needed everywhere either.
*   **Putting everything in the store:** If you shove every little local state into the global store — like a form input's `value`, or `isModalOpen` — then logic has to think about re-rendering the whole app on every keystroke. Only put in the store what 3+ unrelated components share.
*   **Thinking RTK replaces Zustand:** It's not a replacement, it's an alternative for enterprise use. The capstone still uses Zustand.

## What It Is NOT

*   **NOT a Zustand killer:** Both coexist — new startups use Zustand, legacy enterprise uses RTK.
*   **NOT a lightweight alternative:** RTK ~12KB (Zustand 1KB) — expensive for small apps.
*   **NOT a server-state solution:** For API caching `TanStack Query` (Batch 2.3) is still better — RTK is only for client global state.

*   Zustand = modern, simple, new project default. RTK = enterprise, predictable, found in legacy.
