## 1. Start with the Familiar — The Problem RTK Solves

You've seen global state kept in separate pieces — user slice, cart slice, products slice. The problem: when one piece changes but another piece that depends on it doesn't update, the whole state becomes inconsistent. Redux Toolkit solves this by centralizing all global state into a single `store`. The store has sections (slices) for each domain. Each section has one rule: anything you want to change, send an `action` (a plain object `{type, payload}`), and a `reducer` (a pure function) produces the new state based on that action. Nobody mutates state directly; everything goes through actions. That way the state history is preserved — which action changed what.

Redux Toolkit's `store` is that central state container, `slice` is a section, `action` is a plain object describing what happened, and `reducer` is the pure function that takes (state, action) and returns new state. In Zustand you write directly, `set({count: count+1})` — direct mutation. In RTK you call `dispatch(inc())` — you send an action, and the reducer figures out what to do. Big difference, and that's where predictability comes from.

---

## 2. What Is RTK — Concept

**Concept:** Redux is a **predictable state container**. That means — the entire app's global state lives in a single `store`, you never mutate state directly, you always send an `action` (a plain object `{type, payload}`), and a **pure function** `reducer` (state + action -> new state) produces the new state. Redux Toolkit (RTK) is Redux's **official, less-boilerplate** way — with `createSlice`, actions and reducers come together, and `configureStore` gives you DevTools + Immer + middleware out of the box.

In original Redux, every piece had to be written separately — `action type` string, `action creator` function, `reducer` switch-case, `store` creation — 4 files. RTK said, "just use `createSlice` and I'll handle the rest."

**Nutshell:** Redux Toolkit is the library that holds the entire app's global state in a central `store` and makes every change predictable through the `action -> reducer` pattern, cutting down boilerplate with `createSlice` and `configureStore`.

## 4. Visual — Zustand vs RTK Flow

```
Zustand (direct):
Component -> useStore.set({count: count+1}) -> store update -> selective subscribers re-render
(direct write)

Redux Toolkit (action-reducer):
Component -> dispatch(inc()) -> store -> reducer(state, action) -> new state -> useSelector subscribers re-render
(Immer lets you write like mutating, but creates a new object)
```

Both are central stores, both can do selective re-rendering (Zustand with built-in selector, RTK with `useSelector` + `React.memo`). The only difference is **how you update** — direct write vs dispatching an action to a reducer.

## Cheat Sheet (Quick Recall)

**The problem:** you write Zustand freely; the codebase you join uses Redux Toolkit. Same tasks — different API.

**The fix — compare both side by side on the same counter:**

```ts
// Zustand (this course, Batch 6.4)
const useStore = create<Store>((set) => ({ count: 0, inc: () => set(s => ({ count: s.count + 1 })) }));
const count = useStore(s => s.count);

// Redux Toolkit (this batch — what enterprise uses)
const slice = createSlice({ name: "counter", initialState: { count: 0 }, reducers: { inc: (s) => { s.count++ } } });
const store = configureStore({ reducer: { counter: slice.reducer } });
const count = useSelector((s: RootState) => s.counter.count);
```

**What to remember instantly:**
- `store = central state object, action = plain object, reducer = (state, action) => newState`
- `createSlice` = reducers + actions generated together
- `configureStore` = mounts one or many slice reducers into `store`
- `Provider` + `useSelector` / `useAppDispatch` connect the store to the component tree

**Which to use when:** new project → Zustand; legacy codebase → RTK; interviews → expect RTK questions.

**Go deeper:** syntax is identical in 6.7.2 (createSlice) and 6.7.3 (Provider + typed hooks).
