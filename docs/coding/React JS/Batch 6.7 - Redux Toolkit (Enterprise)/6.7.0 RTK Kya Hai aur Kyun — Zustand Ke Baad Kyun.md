## 1. Start with the Familiar — The Problem RTK Solves

You've seen global state kept in separate pieces — user slice, cart slice, products slice. Here's the honest problem RTK targets: in a big codebase, **many developers write to the same state, all the time.** When everyone can change shared state however they like, you get no history, no audit trail, no way to answer "who changed what, and when?" What you want is **one auditable path that every change must take.**

RTK's path is `dispatch(action)` — one door every change must pass, so the state history *is* the list of changes. All global state lives in a single `store` with sections (slices) per domain, and nobody writes to state directly. The three words behind that door — `store`, `action`, `reducer` — get their proper introduction in the next section, one at a time.

And before we compare: a precision that matters in interviews. **Zustand's `set` is not mutation either.** `set({count: count+1})` shallow-merges your partial into a **new** state object — immutable-style, same as RTK under the hood. The real difference is this: in RTK the change is **named** — an action with a `type` like `"counter/increment"` — so it's traceable: what happened, in what order, what the reducer produced. In Zustand the change just... happens. Both are safe; only one keeps a log you can read. That naming is what team-scale conventions (and debugging tools) are built on.

## 2. What Is RTK — Concept

**Concept:** Redux is a **predictable state container** — one `store`, changes only through named `action`s, next state computed by a pure `reducer`. Redux Toolkit (RTK) is Redux's **official, less-boilerplate** way — with `createSlice`, actions and reducers come together (Immer inside every reducer), and `configureStore` gives you DevTools + middleware out of the box. The three words themselves — one at a time, built from pieces you've already met — come right below.

In original Redux, every piece was written separately by hand — the `action type` string, the `action creator` function, the `reducer` switch-case, the `store` creation — each one its own chore, repeated for every feature. RTK said, "just use `createSlice` and I'll handle the rest."

But here's a detail that confuses almost everyone the first time — it confused me too. Open any RTK getting-started guide and you'll see **two** packages being installed: `@reduxjs/toolkit` *and* `react-redux`. Two? We asked for one thing — Redux. Why does a second package appear?

The answer is the single most useful fact in this whole batch: **Redux itself doesn't know React exists.** Redux core is a framework-agnostic JavaScript library — the same `store`, `dispatch`, `getState`, `subscribe` would run in plain Node.js, vanilla JS, even Angular. None of it is React. Which raises the obvious question: if Redux doesn't know React, how do React components ever read from it? Someone has to build the bridge. That bridge is a **separate package** — `react-redux`, the official bindings, giving React the `<Provider>` wrapper and the `useSelector`/`useDispatch` hooks (we reach them in 6.7.3). And RTK? RTK is neither the bridge nor a different state system — it's the modern **authoring layer** on top of Redux core: it changes *how you write* the store and slices, not *how* React connects to them.

So the three names thrown around in every interview are actually three different layers:

| Layer | Package | What it is |
|---|---|---|
| Redux (the state library) | `redux` (inside RTK) | Single store, `dispatch(action)`, pure reducers — React-agnostic |
| React-Redux (the bridge) | `react-redux` | `<Provider>`, `useSelector`, `useDispatch` — connects the store to React |
| Redux Toolkit (the authoring layer) | `@reduxjs/toolkit` | `createSlice`, `configureStore`, `createAsyncThunk` — the official modern way to write Redux |

That's why an RTK project installs **both** packages — RTK writes the store, react-redux connects it to React, and neither can replace the other. Keep this map in your head for the whole batch: 6.7.1 keeps the history short — the three words once, in old-style code; 6.7.2 writes the store with RTK (`createSlice` + `configureStore`); 6.7.3 builds the react-redux bridge; 6.7.4 adds async.

### The Three Words, One at a Time

This is an intro, not a coding doc. By the end you should know **why RTK exists, when to use it vs Zustand, and three words: `store`, `action`, `reducer`** — all from pieces you already have: Zustand and `useReducer`.

**Piece 1 — the difference, on your own counter.** In your Zustand store, the button calls the logic directly: `onClick={decrement}`, and `decrement` lives in the store and does the job. In RTK, the *same* increment/decrement logic exists, but the component doesn't call it. The component calls a function named **`dispatch`** and says "run increment" — and Redux runs it for you. Same logic, different trigger: Zustand calls it directly; RTK asks dispatch to call it. **Dispatch is the middleman.**

**Piece 2 — what dispatch carries.** The button doesn't hand dispatch the whole function. It hands over a tiny note that just says what happened — something like `{ type: "counter/decrement" }`. That note is an **action**. The order: the button creates the action, dispatch carries it, the store runs the matching logic (the reducer). `useDispatch` is just React's handle for grabbing that middleman (via the react-redux bridge).

**Piece 3 — you've met these before.** These three words aren't new — `useReducer` gave you exactly them, scoped to one component. The **reducer** is the one function holding all the logic (state + action → new state); the **action** is the name you pass, like `"add"`; **dispatch** is what carries that name to the reducer. Your calculator app did precisely this: a button dispatched an action, a reducer switch decided the new state. RTK uses the **same three words for the whole app** instead of one component.

**And the store.** The store is the same idea as your Zustand box: one central place holding the app's state that any component reads from. Not a cloud — a plain JavaScript object living in memory inside your running app. What your "cloud" feeling *did* capture is the important part: it sits **outside the component tree**, so no parent has to own the state. That's true for both Zustand and Redux. The one real difference from Zustand: you can't write to this box directly. Every change must go through dispatch → action → reducer.

The three one-liners, in their final form:

- **Store** — the central container that holds the app's whole global state.
- **Action** — a plain object describing what happened, with a `type` and optionally a payload, like "add five".
- **Reducer** — a function that takes the current state plus an action, and returns the new state, without changing the old state directly.

Say them back in your own words — that's this doc's finish line. (And the roadmap ahead: 6.7.1 is a short history note — the three words once, old-style, read-only; 6.7.2 goes straight to `createSlice` + `configureStore`; 6.7.3 connects it to React; at the end, the Expense Tracker series — and the `TrackIt` capstone on top.)

**Nutshell:** Redux Toolkit is the library that holds the entire app's global state in a central `store` and makes every change predictable through the `action -> reducer` pattern, cutting down boilerplate with `createSlice` and `configureStore`.

## 3. When to Use What — Decision First, Code Later

| Situation | What To Use | Why |
|---|---|---|
| New project, 1-3 devs, ship fast | **Zustand** | 1KB, no provider, selective re-render built-in |
| Medium, 5-8 devs, cart/filters frequent update | **Zustand** | Same, separate stores, persist easy |
| **Large team / long-lived codebase — many writers, strict reviews, inherited code** | **Redux Toolkit** | Enforced action-reducer conventions everyone follows, middleware ecosystem (RTK Query, listener middleware), and hiring familiarity — most devs already know it |

**The honest advantages of RTK** (the version that survives an interview): it's not "Zustand has no DevTools" — Zustand ships a `devtools` middleware that talks to the *same* Redux DevTools, and even a redux-style middleware for dispatch/reducer patterns. What RTK really offers: **conventions a whole team is forced to follow** (every change is a named action, in every slice, by every developer), a middleware + ecosystem layer (RTK Query, listener middleware), and the fact that every new hire already knows it. Zustand trades that structure for freedom — perfect for a small team, risky for a big one.

The decision line stays simple — **"New project = Zustand, legacy enterprise = RTK."** (Zustand's neighbors in this choice: Jotai and Context. Redux's: MobX. Different tools, same job.)

I made this mistake myself — thought Redux was needed everywhere, wrapped a small To-Do in `Provider`, created 3 slices, only to realize Zustand did it in 15 lines. It's normal to be confused when the use-cases aren't clear — it took me time too.

## 4. Visual — Zustand vs RTK Flow

```
Zustand (direct call):
Component -> inc() { set(s => ({ count: s.count + 1 })) } -> store (shallow-merges a NEW state)
            -> selector subscribers re-render
(the change works, but nothing names what happened)

Redux Toolkit (named action):
Component -> dispatch(counterSlice.actions.inc()) -> store -> reducer(state, action) -> new state
            -> useSelector subscribers re-render
(every change arrives under a name — log it, audit it, replay it)
```

Both are central stores, and both do selective re-rendering — Zustand via the selector you pass to `useStore(...)` (which **re-checks** the selected value after each update), RTK via `useSelector` (which re-renders a component only when *its* selected value changes). No `React.memo` needed for either — `React.memo` solves a different problem (stopping re-renders caused by a parent passing unchanged props) and doesn't belong in this comparison.

The only real difference is **how a change is requested** — call a setter yourself, vs dispatch a named action to a reducer. (And under the hood, both are immutable-style: Zustand merges into a new object; RTK uses Immer so you *write* like mutation but get a new object.)

## Common Mistakes

*   **"Every app needs RTK"** — Small app paying for 40 lines of boilerplate and 12KB bundle — overkill. 6.4's "What Zustand Is NOT" says the same in reverse: Zustand isn't for everywhere either.
*   **"RTK has DevTools, Zustand doesn't"** — Wrong, and an interviewer will catch it. Zustand's `devtools` middleware connects to Redux DevTools. RTK's real edge is enforced team-wide conventions and its ecosystem.
*   **Putting everything in the store** — If you shove form input values, `isModalOpen`, and other local state into the global store, you'll have to think through re-renders on every keystroke. Only put in the store what 3+ unrelated components actually share.
*   **Thinking RTK = Zustand's replacement** — It's not a replacement, it's an alternative for enterprise-scale. Kanban stays on Zustand; TrackIt (the capstone) applies RTK end to end.

## Cheat Sheet (Quick Recall)

**The problem:** you write Zustand freely; the codebase you join uses Redux Toolkit. Same tasks — different API.

**The fix — compare both side by side on the same counter:**

```ts
// Zustand (this course, Batch 6.4)
const useStore = create<Store>((set) => ({ count: 0, inc: () => set(s => ({ count: s.count + 1 })) }));
const count = useStore(s => s.count);

// Redux Toolkit (this batch — what enterprise uses)
const slice = createSlice({ name: "counter", initialState: { count: 0 }, reducers: { inc: (s) => { s.count++ } } });
const store = configureStore({ reducer: { counter: slice.reducer } });
const count = useSelector((s: RootState) => s.counter.count);
```

**What to remember instantly:**
- `store = central state object, action = plain object, reducer = (state, action) => newState`
- `createSlice` = reducers + actions generated together
- `configureStore` = mounts one or many slice reducers into `store`
- `Provider` + `useSelector` / `useDispatch` connect the store to the component tree

**Which to use when:** new project → Zustand; legacy codebase → RTK; interviews → expect RTK questions.

**Where this lands:** the `createSlice` / `configureStore` syntax above is written for real in 6.7.2; the `Provider` + `useSelector` / `useDispatch` connection is 6.7.3.
