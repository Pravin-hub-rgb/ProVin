## Cheat Sheet (Quick Recall)

```ts
// Zustand (jo abhi seekha)
const useStore = create<Store>((set) => ({ count: 0, inc: () => set(s => ({count: s.count+1})) }))
const count = useStore(s => s.count)

// Redux Toolkit (ab seekhenge)
const slice = createSlice({ name: "counter", initialState: {count: 0}, reducers: { inc: (s) => { s.count++ } }})
const store = configureStore({ reducer: { counter: slice.reducer }})
const count = useSelector((s: RootState) => s.counter.count)
```

## 1. Familiar Se Start — Kirana Shop Ka Register

Tumne `DukaanOS` dekha hai na — kirana shop ka hisaab. Socho purana register jisme har page pe alag hisaab likha hai — ek page pe stock, doosre pe udhaar, teesre pe daily sale. Koi bhi page change karna ho toh tumhe sahi page dhoondna padta hai, aur ek jagah ka change doosri jagah mismatch kar de toh pura hisaab gadbad.

Ab socho ek naya system — ek hi **central register** jisme har hisaab ka alag **section (slice)** hai — stock ka section, udhaar ka section, sale ka section. Har section ka **ek hi rule** hai: “kuch bhi change karna hai toh ek **parchi (action)** likh ke do — ‘stock me 5kg dal add karo’ — register wala hi us parchi ko dekh ke hisaab update karega.” Koi seedha register pe pen nahi chalata, sab parchi se hota hai. Isse hisaab ka history bhi rehta hai — kaunsi parchi kab aayi, kya badla.

Redux Toolkit ka `store` wahi central register hai, `slice` wahi section, `action` wahi parchi, aur `reducer` wahi register wala jo parchi dekh ke hisaab badalta hai. Zustand me tum seedha `set({count: count+1})` kar dete ho — jaise register pe seedha likh diya. RTK me tum `dispatch(inc())` karte ho — parchi bhejte ho, reducer samjhega kya karna hai. Thom bada difference, isi se predictability aati hai.

---

## 2. RTK Kya Hai — Concept

**Concept:** Redux ek **predictable state container** hai. Matlab — poori app ka global state ek jagah `store` me rehta hai, state ko seedha mutate nahi karte, hamesha ek `action` (plain object `{type, payload}`) bhejte ho, aur ek **pure function** `reducer` (state + action -> naya state) naya state banata hai. Redux Toolkit (RTK) Redux ka **official, kam boilerplate wala** tareeka hai — `createSlice` me action + reducer ek saath ban jaate hain, `configureStore` me DevTools + Immer + middleware built-in.

Pehle `Redux (original)` me har cheez alag likhni padti thi — `action type string`, `action creator function`, `reducer switch-case`, `store create` — 4 files. RTK ne bola “ek `createSlice` me sab banao”.

**Nutshell:** Redux Toolkit woh library hai jo ek central `store` me global state rakhti hai aur har change ko `action -> reducer` (parchi -> register wala) pattern se predictable banati hai, `createSlice` aur `configureStore` se boilerplate ghata ke.

## 3. Kab Kya — Decision Pehle, Code Baad Me

| Situation | Kya Use Karo | Kyun |
|---|---|---|
| Naya project, 1-3 dev, jaldi ship karna | **Zustand** | 1KB, no provider, selective re-render built-in |
| Medium, 5-8 dev, cart/filters frequent update | **Zustand** | Same, alag stores, persist easy |
| **Enterprise, 10+ dev, 40+ slices, time-travel, strict pattern chahiye, purana codebase** | **Redux Toolkit** | Strict parchi-system, DevTools, middleware ecosystem, hiring me familiar |

**Trade-off line:** Zustand ke alternatives `Jotai, Context` bhi the, RTK ke alternatives `MobX, XState` bhi. Hum **Zustand = naya default** isliye chune kyunki `docs/coding/WEB-DEV/Project Understanding/plan-03-architecture-cheatsheet.md:63` `Zustand 🟢 Recommended` hai, RTK `🟡 Enterprise` — choices me consistency ke liye. ## 4. Visual — Zustand vs RTK Flow

```
Zustand (direct):
Component -> useStore.set({count: count+1}) -> store update -> selective subscribers re-render
(no parchi, seedha likh diya)

Redux Toolkit (parchi-system):
Component -> dispatch(inc()) --parchi--> store -> reducer(state, action) -> naya state -> useSelector wale re-render
(immer andar mutate jaisa likhne deta hai, par naya object banta hai)
```

Dono central store hain, dono selective re-render kar sakte hain (Zustand built-in selector, RTK `useSelector` + `React.memo`). Farak sirf **update ka tareeka** — direct vs parchi.

## Common Mistakes

*   **“Har app me RTK chahiye”** — Chhote app me 40 lines ka boilerplate, 12KB bundle — overkill. `6.4:528` `What Zustand Is NOT` yaad karo — Zustand bhi har jagah nahi.
*   **Store ko har cheez daal dena** — form input ka `value`, `isModalOpen` jaise local state ko global store me daal doge toh har keystroke pe poora app re-render logic sochna padega. Sirf jo 3+ unrelated components share karte hain wahi store me.
*   **RTK = Zustand ka replacement samajhna** — Yeh replacement nahi, alternative hai enterprise ke liye. Capstone me phir bhi Zustand use hoga.

## What It Is NOT

*   **NOT Zustand killer:** Dono co-exist karte hain — naya startup Zustand, purana enterprise RTK.
*   **NOT heavy ka alternative:** RTK ~12KB (zustand 1KB) — chhote app me mehenga.
*   **NOT server-state solution:** API caching ke liye abhi bhi `TanStack Query` (Batch 2.3) better — RTK sirf client global state.

## Summary

*   Zustand = modern, simple, naya project default. RTK = enterprise, predictable, legacy me milega.
*   Redux ka core: `store` (central register), `action` (parchi `{type, payload}`), `reducer` (register wala pure function).
*   RTK = Redux ka kam-boilerplate official tareeka — `createSlice` + `configureStore`.
*   Is batch me basics se seekhenge, series me, dump nahi — agla doc `6.7.1` me `store/action/reducer` ko code me dekhenge bina `createSlice` ke, taaki problem mehsoos ho.
