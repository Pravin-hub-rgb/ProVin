# Doc 6.7.2 — createSlice + configureStore (A Better Alternative to Manual)

## Cheat Sheet (Quick Recall)

```ts
// What you'll learn in this doc — get it in one read
import { createSlice, configureStore } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { count: 0 },
  reducers: { increment: (state) => { state.count += 1 } }, // Immer = write mutate-style, new state auto
});
export const { increment } = counterSlice.actions; // action creator auto

export const store = configureStore({ reducer: { counter: counterSlice.reducer } });
export type RootState = ReturnType<typeof store.getState>;
```

## Where We Left Off

In `6.7.1`, we felt the pain of manual Redux — a `switch` reducer + `CounterAction` union + `createStore` factory. It worked but was verbose, repeating the same pattern in every slice, and `state.count++` caused bugs. Now we'll rewrite that same counter using RTK's 2 APIs — `createSlice` and `configureStore` — in just 15 lines.

## STAGE 1 — Before createSlice: How Much Manual Boilerplate Existed

### THINK

In the manual `counterReducer`, 3 things were separate — `initialState`, the `CounterAction` type, and the `switch` cases. They all needed the `counter/` prefix manually, and a single typo meant a silent failure. Imagine a tool that said, "Give me name + initialState + reducers object, I'll handle the rest" — that's `createSlice`. Let's understand the concept first.

### CONCEPT

`createSlice` is a **factory function**. You just give it an object:

*   `name: "counter"` — each action type's prefix is auto-generated (`counter/increment`)
*   `initialState: {count: 0}` — starting state
*   `reducers: { increment: (state) => {state.count++} }` — each key is a **case reducer**, the key itself becomes the action's name

Returns 3 things:

*   `slice.reducer` — the full reducer function (the `switch` is auto-generated)
*   `slice.actions` — for each reducer, an **action creator** function is auto-generated (`increment()` -> `{type:"counter/increment"}`)
*   `slice.name` — the same name

**In a nutshell:** `createSlice` is the factory that takes a `name + initialState + reducers` object and generates `reducer + action creators + action types` all at once — replacing manual's 3 separate pieces with a single object.

## STAGE 2 — Minimal createSlice (just increment, nothing else)

### THINK

Don't show all 3 reducers at once — start with just `increment`, minimal, so the flow is clear.

### CODE

Create a new file `src/rtk/counterSlice.ts` — a `rtk/` folder next to the `manual-redux/` folder:

```ts
// src/rtk/counterSlice.ts — STAGE 2 minimal
import { createSlice } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { count: 0 },
  reducers: {
    increment: (state) => {
      state.count += 1;
    },
  },
});

// Action creator export
export const { increment } = counterSlice.actions;

// Reducer export (for use in store)
export default counterSlice.reducer;
```

Why each line:

| Code | Why |
|------|------|
| `createSlice({` | Factory call — replaces manual's `interface + type + switch` |
| `name: "counter"` | Auto prefix — the `increment` action's type becomes `counter/increment` |
| `initialState: {count: 0}` | Same `initialState` as manual's `const initialState` |
| `increment: (state) => { state.count += 1 }` | Written **mutate-style** — `state.count++`! This was a bug in manual, here it's **safe** — why? Because of **Immer** |
| `export const { increment } = counterSlice.actions` | Action creator auto — calling `increment()` creates a `{type:"counter/increment"}` object |
| `export default counterSlice.reducer` | We pass this reducer to the store |

**What Immer is (1-line):** Immer is a library that turns `state` into a **draft proxy**. You write `state.count++` as if you're mutating, but Immer internally creates a copy and returns a new object. That's why in manual you had to `return {count: state.count+1}`, and in RTK `state.count++` just works. `configureStore` has Immer built-in — no separate install.

### CODE — Add 2 more reducers (build up, don't dump)

Now **update** this same file — add `decrement` and `reset`, one at a time:

```ts
// src/rtk/counterSlice.ts — updated
import { createSlice, type PayloadAction } from "@reduxjs/toolkit";

interface CounterState {
  count: number;
}

const initialState: CounterState = { count: 0 };

const counterSlice = createSlice({
  name: "counter",
  initialState,
  reducers: {
    increment: (state) => {
      state.count += 1;
    },
    decrement: (state) => {
      state.count -= 1;
    },
    reset: (state) => {
      state.count = 0;
    },
    // Payload example — will be used in stage 4
    addBy: (state, action: PayloadAction<number>) => {
      state.count += action.payload;
    },
  },
});

export const { increment, decrement, reset, addBy } = counterSlice.actions;
export default counterSlice.reducer;
```

*   `PayloadAction<number>` — a TS type that says `action.payload` is a number. `addBy(5)` -> `{type:"counter/addBy", payload: 5}`. In manual, this `payload` was defined separately in the `type CounterAction` union, here it's a generic.
*   `addBy` will be used again in `6.7.4` — for now just note the syntax.

### TEST

No UI yet, check action creators with `console.log`:

```ts
// temporary test — src/rtk/testSlice.ts
import { increment, addBy } from "./counterSlice";
console.log(increment()); // {type: "counter/increment", payload: undefined}
console.log(addBy(5));    // {type: "counter/addBy", payload: 5}
```

Just call `increment()` and the action object is created — no need to manually write the string type, typo risk eliminated.

## STAGE 3 — configureStore (the better version of manual createStore)

### THINK

In manual, `createStore(counterReducer)` was a separate factory, and you managed the `listeners` array yourself. RTK's `configureStore` creates the store in one line + DevTools + Immer + auto `combineReducers`. Let's understand the concept.

### CONCEPT

`configureStore` takes a `reducer` object — key = slice name, value = slice reducer. This object becomes the shape of `RootState`: `{counter: {count: number}}`. DevTools, middleware, `getState/dispatch/subscribe` are all built-in.

### CODE

```ts
// src/rtk/store.ts
import { configureStore } from "@reduxjs/toolkit";
import counterReducer from "./counterSlice";

export const store = configureStore({
  reducer: {
    counter: counterReducer,
  },
});

// Types — needed in the next doc 6.7.3 for Typed Hooks
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

Why each line:

| Code | Why |
|------|------|
| `configureStore({` | Replaces manual `createStore` — DevTools + middleware auto |
| `reducer: { counter: counterReducer }` | Object form = auto `combineReducers` — gives the `state.counter.count` shape |
| `RootState = ReturnType<typeof store.getState>` | TS utility — extracts type from the store's shape, no manual interface |
| `AppDispatch = typeof store.dispatch` | Type of dispatch — needed to create `useAppDispatch` in `6.7.3` |

Test:

```ts
import { store } from "./store";
import { increment } from "./counterSlice";

console.log(store.getState()); // {counter: {count:0}}
store.dispatch(increment());
console.log(store.getState()); // {counter: {count:1}}
```

The 25-line manual `storeManual.ts` factory became a 7-line `configureStore`. Note the nested shape — `store.getState().counter.count` — the `useSelector((s) => s.counter.count)` in the next doc uses the same path.

## STAGE 4 — Manual vs RTK Comparison (table LAST — AGENTS.md rule)

| Feature | Manual (`6.7.1`) | RTK (`createSlice`) |
|---------|----------------|---------------------|
| **Action type** | `type CounterAction` union manual, typo silently fails | `name` + `reducers` keys auto-generate `counter/increment`, TS error if wrong |
| **Reducer** | `switch` + `return {count: ...}` returns new object | `state.count++` mutate-style — safe via Immer |
| **Action creator** | Separate `const increment = () => ({type: ...})` | `slice.actions.increment` auto |
| **Store** | `createStore` factory ~25 lines, listeners manual | `configureStore({reducer:{counter}})` one call, DevTools auto |
| **Boilerplate for counter** | ~40 lines | ~15 lines |
| **5 slices** | ~200 lines | ~75 lines |

**Trade-off note:** Between `plain Redux` vs `RTK` — RTK is chosen because `docs/coding/WEB-DEV/00-MIND-MAP/webdev-tools-docs/01-frontend-state.md:186` says "New project? Use Redux Toolkit, not plain Redux" — the official recommendation, less boilerplate, same predictability.

## Common Mistakes

*   **`state = {count: 0}` reassigned inside the reducer:** If you assign `state = ...` inside `createSlice`, Immer's draft won't be replaced — bug. Either mutate with `state.count = 0`, or `return {count: 0}` — pick one, don't mix. `reset: (state) => {state.count = 0}` is correct, `reset: (state) => { state = {count:0} }` is wrong.
*   **`PayloadAction` type not given:** In `addBy: (state, action) => {state.count += action.payload}`, `action`'s type becomes `any` — TS won't help you with `action.payload`. Always explicitly use `PayloadAction<number>`.
*   **`configureStore` has `reducer` written as `reducers` (plural):** The API uses `reducer` singular — `configureStore({reducer: {...}})` — an extra `s` gives a TS error: `Object literal may only specify known properties`.

## What It Is NOT

*   **NOT magic:** `createSlice` is still building the same `switch` + `action creator` internally — code is being generated for you, the concept is still the same as `6.7.1`.
*   **NOT direct Zustand-style:** You still need to dispatch `increment()`. Zustand's `set` is more direct and less verbose, but Redux keeps everything traceable.
*   **NOT plain Redux:** Plain Redux doesn't have `createSlice` — it's all manual like `6.7.1`. RTK is Redux's official shortcut.

## Summary

*   `createSlice` = `name + initialState + reducers` -> `reducer + actions` auto.
*   `configureStore` = store factory + DevTools + Immer + `RootState` type.
*   `state.count++` is safe in RTK because of Immer, was a bug in manual.
*   Counter boilerplate 40 -> 15 lines, for 5 slices 200 -> 75.

1. `createSlice` merged which 3 separate pieces of manual code into one object? Name each piece that was separate in manual.

<details>
<summary>Show Answer</summary>

**Sample Answer:** In manual, 3 pieces were separate — (1) `initialState` variable, (2) `CounterAction` union type (the action types), and (3) the `counterReducer` switch function. Plus action creator functions, written separately. With `createSlice({name, initialState, reducers})`, all three are in one object — `name` auto-generates the action type prefix, `initialState` sets the starting state, and `reducers` object's keys auto-generate action names + reducer cases. Action creators come auto from `slice.actions`. That's why 40 lines became 15.

</details>

2. In manual, `return {count: state.count+1}` was needed, but RTK's `state.count++` works — both give the same result, but what's different about the mechanism inside? What does Immer do?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In manual, the reducer is a pure function — if you do `state.count++` directly, the same object reference stays, and Redux can't detect the change ( `===` would still be equal). So you had to return a new object. With RTK, `createSlice` gives Immer a draft proxy — you write `state.count++` as if mutating, but Immer tracks the draft and returns a new immutable object internally. From the outside it looks like mutation, inside it's a new object. That's why the code is shorter and still safe.

</details>

3. `configureStore` replaced manual `createStore` — and where did DevTools come from?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In manual, `createStore` required writing the `state` variable, `listeners` array, and `getState/dispatch/subscribe` yourself — about 25 lines. `configureStore({reducer:{counter}})` creates the store in one call, auto `combineReducers` (from the object form), `subscribe` built-in, and **Redux DevTools** auto-connects — time-travel debugging with zero extra code. The `RootState` type also comes auto from `ReturnType<typeof store.getState>`, no manual interface needed.
