# Doc 6.7.2 — createSlice + configureStore — Manual's Better Version

## Cheat Sheet (Quick Recall)

```ts
// What we're learning in this doc — understand it once
import { createSlice, configureStore } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { count: 0 },
```

## STAGE 1 — Before createSlice: How Much Manual Did We Save?

### SOCH

In the manual `counterReducer`, 3 separate things had to be written — `initialState`, the `CounterAction` type, and the `switch` cases. Each also needed the `counter/` prefix manually. One typo and it fails silently. What if there was a tool that took "name + initialState + reducers object" and handled the rest? That is `createSlice`. Let us understand the concept first.

### CONCEPT

`createSlice` is a **factory function**. You just pass an object:

*   `name: "counter"` — every action type gets this as a prefix automatically (`counter/increment`)
*   `initialState: {count: 0}` — starting state
*   `reducers: { increment: (state) => {state.count++} }` — each key is a **case reducer**, the key itself becomes the action name

And it returns 3 things:

*   `slice.reducer` — the full reducer function (switch auto-built)
*   `slice.actions` — **action creator** functions for each reducer (`increment()` -> `{type:"counter/increment"}`)
*   `slice.name` — the name itself

**Nutshell:** `createSlice` is the factory that takes `name + initialState + reducers` and auto-generates `reducer + action creators + action types` — replacing manual's 3 separate pieces with one object.

## STAGE 2 — Minimal createSlice (only increment, nothing else)

### SOCH

Don't show all 3 reducers at once — start with just `increment`, minimal, so the flow is clear.

### CODE

New file `src/rtk/counterSlice.ts` — next to `manual-redux/`, in the `rtk/` folder:

```ts
// src/rtk/counterSlice.ts — STAGE 2 minimal
import { createSlice } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { count: 0 },
  reducers: {
    increment: (state) => {
      state.count += 1;
    },
  },
});

// Action creator export
export const { increment } = counterSlice.actions;

// Reducer export (used in store)
export default counterSlice.reducer;
```

Why each line:

| Line | Why |
|------|------|
| `createSlice({` | Factory call — one call replaces manual's `interface + type + switch` |
| `name: "counter"` | Auto prefix — `increment` action gets type `counter/increment` |
| `initialState: {count: 0}` | Same `initialState` as the manual `const initialState` |
| `increment: (state) => { state.count += 1 }` | **Writing like you are mutating** — `state.count++`! That was a bug in manual, here it is **safe** — why? **Immer** |
| `export const { increment } = counterSlice.actions` | Action creator auto — calling `increment()` produces `{type:"counter/increment"}` |
| `export default counterSlice.reducer` | We pass this reducer to the store |

**Immer in one line:** Immer is a library that turns `state` into a **draft proxy**. You write `state.count++` like you are mutating, Immer tracks the changes on the draft and produces a new immutable object underneath. That is why in manual you had to `return {count: state.count+1}`, but in RTK `state.count++` works. `configureStore` has Immer built-in — no install needed.

### CODE — Add 2 more reducers (build up, don't dump)

Now **update** this same file — add `decrement` and `reset`, one at a time:

```ts
// src/rtk/counterSlice.ts — updated
import { createSlice, type PayloadAction } from "@reduxjs/toolkit";

interface CounterState {
  count: number;
}

const initialState: CounterState = { count: 0 };

const counterSlice = createSlice({
  name: "counter",
  initialState,
  reducers: {
    increment: (state) => {
      state.count += 1;
    },
    decrement: (state) => {
      state.count -= 1;
    },
    reset: (state) => {
      state.count = 0;
    },
    // Payload example — used in stage 4
    addBy: (state, action: PayloadAction<number>) => {
      state.count += action.payload;
    },
  },
});

export const { increment, decrement, reset, addBy } = counterSlice.actions;
export default counterSlice.reducer;
```

*   `PayloadAction<number>` — TS type saying `action.payload` is a `number`. `addBy(5)` -> `{type:"counter/addBy", payload: 5}`. In manual, `payload` had to be defined separately in the `CounterAction` union; here the generic handles it.
*   `addBy`'s usage comes in `6.7.4` — for now, just the syntax.

## STAGE 3 — configureStore (manual createStore's better version)

### SOCH

In manual, `createStore(counterReducer)` was a separate factory, and you managed the `listeners` array yourself. RTK's `configureStore` creates the store in one line — plus DevTools, Immer, and auto `combineReducers`. Let us see the concept.

### CONCEPT

Pass `configureStore` a `reducer` object — key = slice name, value = slice reducer. This object also becomes the shape of `RootState`: `{counter: {count: number}}`. DevTools, middleware, `getState/dispatch/subscribe` — all built-in.

### CODE

```ts
// src/rtk/store.ts
import { configureStore } from "@reduxjs/toolkit";
import counterReducer from "./counterSlice";

export const store = configureStore({
  reducer: {
    counter: counterReducer,
  },
});

// Types — needed for Typed Hooks in next doc 6.7.3
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

Each line:

| Code | Why |
|------|------|
| `configureStore({` | Replaces manual `createStore` — DevTools + middleware auto |
| `reducer: { counter: counterReducer }` | Object form = auto `combineReducers` — `state.counter.count` shape |
| `RootState = ReturnType<typeof store.getState>` | TS utility — pulls the type from the store's shape, no manual interface |
| `AppDispatch = typeof store.dispatch` | dispatch's type — for `useAppDispatch` in `6.7.3` |

### TEST

```ts
import { store } from "./store";
import { increment } from "./counterSlice";

console.log(store.getState()); // {counter: {count:0}}
store.dispatch(increment());
console.log(store.getState()); // {counter: {count:1}}
```

The ~25-line `storeManual.ts` factory is now 7 lines of `configureStore`. And note `store.getState().counter.count` — the nested shape matters, next doc's `useSelector((s) => s.counter.count)` will use this exact path.

## Common Mistakes

*   **Reassigned `state = {count: 0}` inside a reducer:** If you assign `state = ...` inside `createSlice`, Immer's draft doesn't get replaced — bug. Either mutate `state.count = 0`, or `return {count: 0}` — pick one, don't mix. `reset: (state) => {state.count = 0}` is correct; `reset: (state) => { state = {count:0} }` is wrong.
*   **No `PayloadAction` type:** In `addBy: (state, action) => {state.count += action.payload}` without `PayloadAction<number>`, `action` becomes `any` — no TS help on `action.payload`. Always annotate explicitly.
*   **Wrote `reducers` (plural) in `configureStore`:** The API key is `reducer` singular — `configureStore({reducer: {...}})` — extra `s` and TS throws `Object literal may only specify known properties`.

## What It Is NOT

*   **NOT magic:** `createSlice` internally still builds the same `switch` + `action creator` — it's generating code for you, the concept is identical to `6.7.1`.
*   **NOT Zustand-style direct:** You still call `dispatch(increment())` to send a slip — more verbose than Zustand's `set`, but traceable.
*   **NOT plain Redux:** Plain Redux has no `createSlice` — everything is manual like `6.7.1`. RTK = Redux's official shortcut.

## Summary

*   `createSlice` = `name + initialState + reducers` -> auto `reducer + actions`.
*   `configureStore` = store factory + DevTools + Immer + `RootState` type.
*   `state.count++` is safe in RTK thanks to Immer, was a bug in manual.
*   Counter boilerplate 40 -> 15 lines, 5 slices 200 -> 75 lines.

**Sample Answer:** Manual had 3 separate pieces — (1) the `initialState` variable, (2) the `CounterAction` union type (action types), (3) the `counterReducer` switch function. Plus action creator functions written separately. `createSlice({name, initialState, reducers})` puts them all in one object — `name` auto-generates the action type prefix, `initialState` sets the starting state, `reducers` object keys auto-create action names + reducer cases. `slice.actions` also auto-generates creators. That's why 40 lines became 15.

2. Manual needed `return {count: state.count+1}`, RTK allows `state.count++` — same final result, how different is the mechanism underneath? What does Immer do?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In manual, the reducer is a pure function — if you `state.count++` directly, you mutate the same `state` object, the reference stays the same, and Redux can't detect the change (`===` check passes). So you must return a new object. In RTK, `createSlice` wraps the reducer with Immer, which provides a draft proxy — you write `state.count++` like you're mutating, Immer tracks the changes on the draft and produces a new immutable object under the hood. From the outside it looks like mutation, inside a new object is created. Less code, equally safe.

</details>

3. What did `configureStore` replace from manual `createStore`, and where did DevTools come from?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In manual `createStore` — the `state` variable, `listeners` array, and `getState/dispatch/subscribe` — all had to be written by hand, ~25 lines. `configureStore({reducer:{counter}})` creates the store in one call, auto `combineReducers` (from the object form), built-in `subscribe`, and **Redux DevTools** auto-connects — time-travel debugging with zero extra code. `RootState` type also auto-extracts via `ReturnType<typeof store.getState>`, no manual interface needed.
