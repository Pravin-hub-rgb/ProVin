The previous doc `6.7.2` created a store — `configureStore({reducer:{counter}})` + `increment` from `counterSlice` that mutates but stays safe thanks to Immer. Now the question — how will React components know the store's `count` changed? In `6.7.1` we did manual `store.subscribe(() => setCount(store.getState().count))` in every component — the same boilerplate repeated over and over. In RTK, there are 2 hooks for React — `useSelector` (read from store) and `useDispatch` (send slips) — but without a `Provider`, they'll throw an error. And in TypeScript, how does `s` in `useSelector((s) => s.counter.count)` get its type? In this doc, we'll cover these same 3 things STAGE by STAGE — not a dump.

# Doc 6.7.3 — Provider + Typed Hooks — Connecting the Store to React

## Cheat Sheet (Quick Recall)

```ts
// Store created (from 6.7.2)
export const store = configureStore({ reducer: { counter: counterSlice.reducer } });
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;

// Typed hooks (in this doc)
export const useAppSelector = useSelector.withTypes<RootState>();
export const useAppDispatch = useDispatch.withTypes<AppDispatch>();

// Usage
const count = useAppSelector((s) => s.counter.count);
const dispatch = useAppDispatch();
dispatch(increment());
```

## Where We Left Off

In `6.7.1` we built a manual reducer + store factory, in `6.7.2` `createSlice` + `configureStore` gave us the same counter in 15 lines with Immer + `RootState`. The store is ready, but it's not yet **connected** to React — components can't read `store.getState()` directly (how to subscribe?), and the type would be `any`. Now we connect it.

## Broader Goal

In this doc, 3 steps: **STAGE 1 Provider (why) -> STAGE 2 Minimal useSelector/useDispatch (without types) -> STAGE 3 Typed Hooks (proper)**. Each stage follows `THINK -> CONCEPT -> CODE -> TEST` — gradually, not dumping provider + typed hooks all at once. At the end, we'll compare with Zustand's `6.4:92` selective subscription, and common mistakes (forgetting Provider, returning an object in `useSelector`).

## STAGE 1 — Why the Provider Is Needed (the store's "switchboard")

### THINK

The store is a single export in `src/rtk/store.ts` — `import {store} from "../rtk/store"` can be used anywhere, right? So why `Provider`? Imagine — in every component you'd repeat the same `6.7.1 STAGE 3` boilerplate: `import {store}` + `store.subscribe` + `useEffect` + `useState`. 10 components = 10 subscribes, 10 useEffects. There should be one central way to hand over the store, and components just ask for it via `useSelector` — that's `Provider`.

I first thought this myself — "In Zustand there was no Provider, so why in RTK?" Then I understood: Zustand's store is a singleton created by `create` that handles subscribe internally within hooks, RTK's store is a plain object that needs to be passed to the React tree via context — `Provider` is that context.

### CONCEPT

`Provider` is a component from `react-redux` that injects `store` throughout the React tree via Context. Internally it handles `store.subscribe`, and `useSelector` reads from that same context. Once you wrap once in `main.tsx`, any component can read any slice via `useSelector` — without `import {store}`.

**Nutshell:** `Provider` is the wrapper that makes the Redux `store` available across the entire app through React Context, so `useSelector/useDispatch` can talk to the store without direct import + manual subscribe.

### CODE

First install `react-redux` (if not already done):

```bash
bun add @reduxjs/toolkit react-redux
# or npm install @reduxjs/toolkit react-redux
```

Now apply the `Provider` — in `src/main.tsx` (Vite):

```tsx
// src/main.tsx
import React from "react";
import ReactDOM from "react-dom/client";
import { Provider } from "react-redux";
import { store } from "./rtk/store";
import App from "./App";

ReactDOM.createRoot(document.getElementById("root")!).render(
  <React.StrictMode>
    <Provider store={store}>
      <App />
    </Provider>
  </React.StrictMode>
);
```

| Line | Why |
|------|------|
| `import {Provider} from "react-redux"` | Import in this stage only — not before, only now when it's needed |
| `import {store} from "./rtk/store"` | The `configureStore` store from `6.7.2` |
| `<Provider store={store}>` | A single prop `store` — put it in context, now all `App` children can access it |

### TEST

`bun run dev` — no `useSelector` yet, just the Provider wrap. There should be no error in the App. If you don't add `Provider` and use `useSelector` in the next stage, the error: `could not find react-redux context value; please ensure the component is wrapped in a <Provider>` — that's the proof of why Provider is needed.

## STAGE 2 — Minimal useSelector + useDispatch (no types, just flow)

### THINK

Provider is set up, now we need to read the store's `count` in a component and send `increment` slips via `dispatch`. In Zustand it was `useStore(s=>s.count)` and `useStore(s=>s.increment)`. In RTK there are 2 separate hooks — one for reading, one for sending. First let's see the minimal version without types, types come in the next stage.

### CONCEPT

*   `useSelector(selectorFn)` — `selectorFn` gets `RootState` and returns whatever value. Internally it subscribes and memoizes the value — if the value stays the same, re-render is skipped (like Zustand's selective subscription).
*   `useDispatch()` — returns the `dispatch` function, use it to `dispatch(increment())` slips.

### CODE

New component `src/rtk/CounterRTK.tsx` — minimal, just RTK:

```tsx
// src/rtk/CounterRTK.tsx — STAGE 2 minimal (without typed hooks)
import { useSelector, useDispatch } from "react-redux";
import { increment, decrement, reset } from "./counterSlice";

export function CounterRTK() {
  const count = useSelector((state: any) => state.counter.count);
  const dispatch = useDispatch();

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => dispatch(increment())}>+1</button>
      <button onClick={() => dispatch(decrement())}>-1</button>
      <button onClick={() => dispatch(reset())}>Reset</button>
    </div>
  );
}
```

```tsx
// src/App.tsx — temporarily
import { CounterRTK } from "./rtk/CounterRTK";
export default function App() {
  return <main><h1>RTK Counter — Minimal</h1><CounterRTK /></main>;
}
```

Every line:

| Code | Why |
|------|------|
| `useSelector((state: any) => state.counter.count)` | `state` is typed `any` — because `RootState` type wasn't passed yet, TS can't help. `state.counter.count` path comes from `reducer: {counter}` in `6.7.2` |
| `useDispatch()` | The `dispatch` function — wraps the `increment()` action creator and sends it |
| `dispatch(increment())` | `increment()` -> `{type:"counter/increment"}`, dispatch -> store -> reducer -> new state -> `useSelector` triggers re-render |

### TEST

Click `+1` in the browser -> `Count: 0 -> 1` should increase. Open the Redux DevTools extension — every click shows `counter/increment` action, and the time-travel slider lets you undo. In Zustand you had to add the `devtools` middleware `6.4:438`, in RTK it's built into `configureStore`.

**Problem here:** `state: any` — when you type `state.counter.` there's no autocomplete, a typo like `state.countre` won't error. This is the problem that typed hooks solve in the next stage. Notice? Problem felt first, solution later — the cause-effect chain from `Dost-to-Dost Style.md:30`.

## STAGE 3 — Typed Hooks (Proper — Now TS Will Help)

### THINK

With `any`, you have to remember the `state.counter.count` path by string, and a wrong path gives `undefined` at runtime. In `6.7.2` we already created the `RootState` type using `ReturnType<typeof store.getState>` — how do we pass it to `useSelector`? Writing `useSelector((state: RootState) => ...)` in every component repeats. Create one typed wrapper once, use it everywhere — that's `useAppSelector`.

### CONCEPT

RTK's `withTypes` helper — `useSelector.withTypes<RootState>()` returns a new hook whose `state` param is auto-typed as `RootState`. Same with `useDispatch.withTypes<AppDispatch>()` so `dispatch` knows which action types are allowed (useful for thunks in `6.7.4`).

Keep this in a separate `hooks.ts` file — the convention is `src/rtk/hooks.ts`.

### CODE

```ts
// src/rtk/hooks.ts — STAGE 3 typed hooks (created in this stage, not before)
import { useDispatch, useSelector } from "react-redux";
import type { RootState, AppDispatch } from "./store";

export const useAppSelector = useSelector.withTypes<RootState>();
export const useAppDispatch = useDispatch.withTypes<AppDispatch>();
```

Now update `CounterRTK` to use typed hooks — remove `any`:

```tsx
// src/rtk/CounterRTK.tsx — updated with typed hooks
import { useAppSelector, useAppDispatch } from "./hooks";
import { increment, decrement, reset, addBy } from "./counterSlice";

export function CounterRTK() {
  const count = useAppSelector((state) => state.counter.count);
  const dispatch = useAppDispatch();

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => dispatch(increment())}>+1</button>
      <button onClick={() => dispatch(decrement())}>-1</button>
      <button onClick={() => dispatch(reset())}>Reset</button>
      <button onClick={() => dispatch(addBy(5))}>+5</button>
    </div>
  );
}
```

| Line | Why |
|------|------|
| `useAppSelector((state) => state.counter.count)` | Hover over `state` now — TS shows `RootState`, `state.counetr` typo gives error, `state.counter.` autocompletes `count` |
| `useAppDispatch()` | If you `dispatch(addBy("five"))` TS errors `string not assignable to number` — `PayloadAction<number>` enforced from `6.7.2` |
| `import from "./hooks"` | Path is `./hooks` because `CounterRTK.tsx` and `hooks.ts` are in the same `src/rtk/` folder |

### TEST

*   Type `state.` — `counter` should be suggested, `counter.` then `count`.
*   Write `dispatch(addBy("hi"))` and hover — error should appear, on the correct `addBy(5)` it won't.
*   Click `+5` in the browser -> `count` increases by 5, DevTools shows `counter/addBy` with payload `5`.

## STAGE 4 — Selective Subscription Difference (compared with Zustand)

`6.4:92` Zustand selective was — `useCounterStore(s=>s.count)` re-renders only when `count` changes. RTK's `useSelector` works the same — `useAppSelector(s=>s.counter.count)` re-renders only when `count` changes. But there's one trap:

```tsx
// ❌ Wrong — new object every render, selector always gets a new reference, re-renders on every dispatch
const { count, theme } = useAppSelector((s) => ({ count: s.counter.count, theme: s.counter.theme }));

// ✅ Correct — separate selectors, or `shallowEqual`
const count = useAppSelector((s) => s.counter.count);
const theme = useAppSelector((s) => s.counter.theme);
```

In Zustand, `useStore()` without a selector would subscribe to the whole store `6.4:286`. In RTK, if you return an object, shallow compare fails — re-renders every time. That's why **always use primitive/selective** selectors.

## Common Mistakes

*   **Forgot the Provider:** calling `useAppSelector` outside a `Provider` throws `could not find react-redux context value` — every test file also needs `<Provider store={store}>` wrapping (we'll do this in `6.7.5.5` testing).
*   **Returning an object in `useSelector`:** `useSelector(s => ({count: s.counter.count}))` — new object every render -> unnecessary re-renders. The `React.memo` lesson from `Batch 5.1` applies here too.
*   **Didn't create typed hooks, repeated `state: RootState` everywhere:** it works but violates DRY — create `hooks.ts` once, every component reuses `useAppSelector` — same pattern as `6.1 Custom Hooks`.
*   **Dispatching a thunk without `AppDispatch`:** in `6.7.4` when you dispatch `createAsyncThunk`, if you use `useDispatch()` its type becomes `any` and TS won't error on `dispatch(fetchCategories())` — `useAppDispatch` gives the correct type.

## What It Is NOT

*   **NOT provider-free like Zustand:** In RTK the Provider is required — Zustand's `create` is a singleton, RTK's store comes through context.
*   **NOT `useSelector` === `useStore` same thing:** In Zustand, `useStore(s=>s.count)` included `set` in the same hook, in RTK `useSelector` is read-only, `useDispatch` is separate — that's the separation.
*   **NOT every component should import the store:** the manual `import {store}` + `store.getState()` pattern from `6.7.1` — after the Provider, never import the store directly in components.

## Summary

*   `Provider` = the store's switchboard — wrap once in `main.tsx`, `useSelector/useDispatch` can access anywhere.
*   `useSelector` (read) + `useDispatch` (send slips) — the minimal flow works but with `any` TS can't help.
*   `useAppSelector/useAppDispatch` (`withTypes<RootState/ AppDispatch>`) = typed wrappers — autocomplete + payload type safety.
*   Keep selective selectors — returning objects is a re-render trap.

## In Your Own Words

1. In Zustand there was no Provider, but in RTK it's necessary. Explain where each store lives.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Zustand creates a singleton store with `create(() => ({count}))` that manages its own `subscribe` internally — components just `import {useCounterStore}` and subscribe directly, no Context needed. RTK's `configureStore` is a plain object store, and to pass it to the React tree you need Context — `Provider` is that Context provider. `Provider` is wrapped once in `main.tsx` giving the store to the tree, and `useSelector` reads from that Context. That's why forgetting the Provider in RTK throws `could not find context value`.

</details>

2. Which 2 problems does `useAppSelector` solve compared to `useSelector((state: any) => ...)`? Give a typo example.

<details>
<summary>Show Answer</summary>

**Sample Answer:** (1) Autocomplete — `state.` suggests `counter`, `state.counter.` suggests `count`. (2) Type safety — `state.counetr.count` typo gives a TS error, with `any` it silently returns `undefined`. Plus payload safety — `dispatch(addBy("five"))` errors on string because `useAppDispatch` knows from `PayloadAction<number>` that `addBy` takes a number. With `any` this check doesn't happen, and at runtime `count += "five"` becomes `NaN`.

</details>

3. Why is returning `useSelector(s => ({count: s.counter.count}))` an object a trap? How is it similar to the Zustand trap from `6.4:286`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `useSelector` does a shallow `===` comparison between the old and new return value. `{count: ...}` creates a new object on every render (different reference) — even if the value stays `0`, the reference is new, so `useSelector` thinks it changed and the component re-renders on every dispatch. Same in Zustand, `useStore()` without a selector subscribed to the whole store, and returning an object had the same trap. Fix — separate selectors `const count = useAppSelector(s => s.counter.count)` or pass `shallowEqual` as the second argument.

</details>
