## STAGE 2 — STATE + REDUCER (heart of the slip-system)

### THINK

In the static version, count is hardcoded `0`. Now we need to store it and change it — but not Zustand-style direct `set`, through the **slip-system**. One place holds `state`, and every change sends an `action` object (a slip), and the `reducer` function produces the new state. Why this extra step? So every change is traceable — which slip changed what. Let us see how this looks in manual code.

### CONCEPT

Remember 3 words:

*   **Store:** An object holding `state` — `{count: 0}`. Single source of truth for the whole app.
*   **Action:** A plain object `{type: "counter/increment"}` — a slip. The `type` string tells everything that happened. Send data with `payload` — `{type: "counter/add", payload: 5}`.
*   **Reducer:** A pure function `(state, action) => newState`. Look at just `state` and `action` and return new state — never mutate `state.count++` directly (manual Redux does not allow it, RTK's Immer handles it — the difference we will see next doc).

### CODE

Now make `CounterStatic` dynamic — but still without React, just in TS to understand:

```ts
// src/manual-redux/counterManual.ts

// 1. Shape of state
interface CounterState {
  count: number;
}

// 2. Actions — slip types
type CounterAction =
  | { type: "counter/increment" }
  | { type: "counter/decrement" }
  | { type: "counter/reset" };

// 3. Initial state
const initialState: CounterState = { count: 0 };

// 4. Reducer — the clerk
export function counterReducer(
  state: CounterState = initialState,
  action: CounterAction
): CounterState {
  switch (action.type) {
    case "counter/increment":
      return { count: state.count + 1 };
    case "counter/decrement":
      return { count: state.count - 1 };
    case "counter/reset":
      return { count: 0 };
    default:
      return state;
  }
}
```

Look at why each line exists:

| Line | Why |
|------|------|
| `interface CounterState` | TS knows what is in state — typos caught at compile time |
| `type CounterAction` | Union type — `type` can only be one of these 3 strings; write `"counter/incremnet"` and you get an error |
| `switch(action.type)` | Each slip gets its own case — what to do for which slip |
| `return { count: state.count + 1 }` | **New object** returned — not `state.count++`, because manual reducers can not mutate (otherwise React will not detect the change, reference stays the same) |
| `default: return state` | Unknown slip comes in, state stays the same |

### TEST

No UI yet, verify with `console.log`:

```ts
// src/manual-redux/testManual.ts
import { counterReducer } from "./counterManual";

let state = { count: 0 };
console.log(state); // {count:0}

state = counterReducer(state, { type: "counter/increment" });
console.log(state); // {count:1}

state = counterReducer(state, { type: "counter/increment" });
console.log(state); // {count:2}

console.log(state); // {count:0}
```

No `bun run` in terminal, just save the file and think — on every action the reducer created a **new object**. Remember the point from `6.4:58` — Zustand's `set` does a shallow merge, here the reducer returns a whole new state.

**Common Mistake here:** `case "counter/increment": state.count++; return state;` — if you do this, you have **mutated** — no new object. In manual Redux this is a **bug** — UI will not re-render because the object reference is the same. In `createSlice`, you can write `state.count++` because **Immer** creates a new object underneath — the difference we will see next doc. I was confused by this myself the first time — I thought "why does the same thing work in one place and not the other?"

## STAGE 3 — STORE + DISPATCH + VIEW (connecting everything)

### THINK

Reducer is just a function — where do we store the state? And how does the component know state changed? We need a **store** — holds `state`, receives slips via `dispatch`, calls the reducer, and notifies subscribers.

### CONCEPT

Minimal shape of a manual store:

*   `getState()` — give me current state
*   `dispatch(action)` — accept a slip, call reducer, set new state
*   `subscribe(listener)` — notify listener when state changes (this is what `useSelector` does in React)

In React we pass this store through the whole tree with a `Provider`, but in this doc we will build a minimal store without React first, so the flow is clear.

### CODE

```ts
// src/manual-redux/storeManual.ts
import { counterReducer } from "./counterManual";
import type { CounterState } from "./counterManual";

type CounterAction =
  | { type: "counter/increment" }
  | { type: "counter/decrement" }
  | { type: "counter/reset" };

function createStore(reducer: typeof counterReducer) {
  let state: CounterState = reducer(undefined as any, { type: "@@INIT" } as any);
  const listeners: (() => void)[] = [];

  return {
    getState: () => state,
    dispatch: (action: CounterAction) => {
      state = reducer(state, action);
      listeners.forEach((l) => l());
    },
    subscribe: (listener: () => void) => {
      listeners.push(listener);
      return () => {
        const idx = listeners.indexOf(listener);
        if (idx >= 0) listeners.splice(idx, 1);
      };
    },
  };
}

export const store = createStore(counterReducer);
```

Now a React component that uses this store — **stage by stage, not all at once**:

```tsx
// src/manual-redux/CounterManual.tsx — STAGE 3 final
import { useEffect, useState } from "react";
import { store } from "./storeManual";

export function CounterManual() {
  const [count, setCount] = useState(store.getState().count);

  useEffect(() => {
    const unsub = store.subscribe(() => {
      setCount(store.getState().count);
    });
    return unsub;
  }, []);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => store.dispatch({ type: "counter/increment" })}>+1</button>
      <button onClick={() => store.dispatch({ type: "counter/decrement" })}>-1</button>
      <button onClick={() => store.dispatch({ type: "counter/reset" })}>Reset</button>
    </div>
  );
}
```

Why each line:

| Code | Why |
|------|------|
| `useState(store.getState().count)` | Initial UI state comes from the store |
| `store.subscribe(() => setCount(...))` | When store changes, trigger component re-render — otherwise UI goes stale |
| `store.dispatch({type: ...})` | Send a slip, reducer produces new state, subscribers get triggered |

### TEST

Render `CounterManual` in `App.tsx`, click `+1` — count should increase. Check `console.log` — every click dispatches a `counter/increment` slip.

## The Pain We Just Felt (Reason for the Next Doc)

So far, just for the counter:

*   1 interface + 1 union type + 1 reducer switch + 1 store factory = **~40 lines**
*   Every new feature (like `addAmount` with a `payload`) needs a new union in the type, a new case in the reducer, and a separate action creator function.
*   With 5 slices, that's 5 reducers + `combineReducers` + the same boilerplate in every file.

This is the pain RTK was built to solve — `createSlice` lets you write `name + initialState + reducers` in one place, auto-generating action creators and action types. The next doc `6.7.2` does the same counter in **15 lines** — that is when "ah, RTK was worth it" clicks.

> **Nutshell:** Reducer is the pure function that returns `(state, action) -> newState` — never mutate, always a new object. Store is the container that holds state, accepts actions via `dispatch`, calls the reducer to update state, and notifies subscribers.

---

## Common Mistakes

*   **Mutated in the reducer:** `state.count++; return state;` — UI will not update — no Immer in manual. Always return `{count: state.count + 1}`, a new object.
*   **Typo in action type:** Writing `"counter/increment"` as `"counter/incremnet"` — falls through to the `default` case, state does not change, no error. That is why the `type CounterAction` union is crucial — TS catches the typo.
*   **Forgot subscribe cleanup:** If you do not `return unsub` in `useEffect`, listeners leak after unmount — memory leak: unmount -> listener reference alive in array -> GC can not collect -> memory leak, same chain as `Dost-to-Dost Style.md:34`.

## What It Is NOT

*   **NOT RTK:** This manual pattern is just for understanding — in production you never write `createStore` like this, you use `configureStore`.
*   **NOT Zustand-style:** In Zustand `set` is direct, here every change goes through a slip. The manual pattern is verbose on purpose — every step is explicit.

## Summary

*   Redux core = `store` (state holder) + `action` (slip `{type,payload}`) + `reducer` (pure function).
*   Manual, every slice needs its own type + switch + store factory — ~40 lines boilerplate for just the counter.
*   Common pitfalls: mutate, typo, subscribe leak.

## In Your Own Words

1. In a manual reducer, why `return {count: state.count+1}` instead of `state.count++; return state;`? Where is the object reference different in each?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `state.count++` mutates the same `state` object — reference stays the same. React/Redux checks with `===` — old vs new state, if the reference is the same, it thinks "nothing changed" and will not re-render. `return {count: state.count+1}` creates a new object — reference is different, change is detected. Manual Redux has no Immer, so you always need a new object. In RTK, `state.count++` works because Immer creates a new object under the hood using a proxy.

</details>

2. Why define action types as a `string` union (`type CounterAction`) instead of a plain `string`? What is the typo risk?

<details>
<summary>Show Answer</summary>

**Sample Answer:** With a plain `string`, the typo `"counter/incremnet"` would be accepted — it would fall through to the `default` case and fail silently. With the union `type CounterAction = {type:"counter/increment"} | ...`, TS throws an error at compile time — `Type '"counter/incremnet"' is not assignable`. This catches slips with wrong names before runtime. With `createSlice`, this union is auto-generated, no need to write it manually.

</details>

3. What does `subscribe` do in the store? Why did we subscribe in `useEffect` in `CounterManual.tsx`, instead of just calling `store.getState()` directly in the render?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `store.getState()` only gives the current snapshot — it has no idea about future updates. `subscribe` registers a listener that runs after every `dispatch`. Wrapping `subscribe(() => setCount(store.getState().count))` inside `useEffect` means — when the store changes, `setCount` triggers a React re-render. If you do not subscribe, `+1` does update the store's count, but the component never finds out — the UI stays stuck at 0. `useSelector` (next doc) does this subscription internally.

</details>
