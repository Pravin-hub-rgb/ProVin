## Step 1 — useLocalStorage Tests

`useLocalStorage` ko test karte hain. Nayi file banao — `src/hooks/__tests__/useLocalStorage.test.tsx`:

```tsx
// src/hooks/__tests__/useLocalStorage.test.tsx
import { renderHook, act } from "@testing-library/react";
import { beforeEach, describe, it, expect } from "vitest";
import { useLocalStorage } from "../useLocalStorage";

describe("useLocalStorage", () => {
  beforeEach(() => {
    localStorage.clear();
  });

  it("localStorage khali ho toh initial value return karta hai", () => {
    const { result } = renderHook(() =>
      useLocalStorage("todos", [])
    );

    expect(result.current[0]).toEqual([]);
  });

  it("state update hone pe localStorage mein save hota hai", () => {
    const { result } = renderHook(() =>
      useLocalStorage<string[]>("todos", [])
    );

    act(() => {
      result.current[1](["Buy milk", "Pay bills"]);
    });

    expect(result.current[0]).toEqual(["Buy milk", "Pay bills"]);

    // localStorage mein bhi save ho gaya
    const saved = localStorage.getItem("todos");
    expect(saved).not.toBeNull();
    expect(JSON.parse(saved as string)).toEqual(["Buy milk", "Pay bills"]);
  });

  it("localStorage mein saved value ho toh woh load hoti hai", () => {
    localStorage.setItem("todos", JSON.stringify(["Old task"]));

    const { result } = renderHook(() =>
      useLocalStorage<string[]>("todos", [])
    );

    expect(result.current[0]).toEqual(["Old task"]);
  });
});
```

**Kya test kar rahe hain:**

| Test | Behaviour |
|------|-----------|
| `localStorage khali ho toh` | Default initial value |
| `state update hone pe` | Update state + localStorage sync hota hai |
| `saved value load` | Refresh scenario — existing data load hota hai |

`beforeEach(() => localStorage.clear())` — har test se pehle localStorage fresh. Kyunki jsdom ke localStorage tests ke beech shared rehta hai — ise clear nahi kiya toh ek test doosre ko affect karega.

## Step 2 — useFetch Tests

`useFetch` ko test karte hain. Nayi file banao — `src/hooks/__tests__/useFetch.test.tsx`:

```tsx
// src/hooks/__tests__/useFetch.test.tsx
import { renderHook, act, waitFor } from "@testing-library/react";
import { describe, it, expect, vi, beforeEach } from "vitest";
import { useFetch } from "../useFetch";

describe("useFetch", () => {
  beforeEach(() => {
    vi.restoreAllMocks();
  });

  it("success — data set hota hai, isLoading false", async () => {
    vi.spyOn(globalThis, "fetch").mockResolvedValue(
      new Response(JSON.stringify({ name: "Chicken" }), {
        headers: { "Content-Type": "application/json" },
      })
    );

    const { result } = renderHook(() =>
      useFetch<{ name: string }>("https://api.example.com/recipe")
    );

    // shuru mein loading
    expect(result.current.isLoading).toBe(true);

    // fetch complete hone ka wait karo
    await waitFor(() => {
      expect(result.current.isLoading).toBe(false);
    });

    expect(result.current.data).toEqual({ name: "Chicken" });
    expect(result.current.error).toBeNull();
  });

  it("error — error state set hota hai", async () => {
    vi.spyOn(globalThis, "fetch").mockRejectedValue(new Error("Network fail"));

    const { result } = renderHook(() =>
      useFetch<{ name: string }>("https://api.example.com/recipe")
    );

    await waitFor(() => {
      expect(result.current.error).toBe("Network fail");
    });

    expect(result.current.data).toBeNull();
    expect(result.current.isLoading).toBe(false);
  });
});
```

**Kya ho raha hai:**

| Cheez | Kyun |
|-------|------|
| `vi.spyOn(globalThis, "fetch")` | Asli network call ki jagah **mock** fetch — real API ko test mein hit nahi karte (slow + unreliable) |
| `new Response(JSON.stringify(...))` | Fake API response — jaise asli server ne JSON bheja |
| `mockResolvedValue` | Fetch **successfully** resolve karega |
| `mockRejectedValue` | Fetch **error** throw karega |
| `waitFor` | Async render complete hone ka wait — loading se data pe transition |
| `vi.restoreAllMocks()` | Har test ke baad mocks reset — ek test doosre ko na affect kare |

**Note:** `useFetch` mock karna padta hai kyunki real network test slow aur flaky hai. Isi liye mock fetch pattern industry standard hai — `vi.spyOn(globalThis, "fetch")`.

## Step 3 — Zustand Store Tests

Zustand store ko test karte hain — 6.4 ka counter store. Nayi file banao — `src/stores/__tests__/counterStore.test.ts`:

```ts
// src/stores/__tests__/counterStore.test.ts
import { describe, it, expect, beforeEach } from "vitest";
import { useCounterStore } from "../counterStore";

describe("counterStore", () => {
  beforeEach(() => {
    // har test se pehle store reset — taaki state clean ho
    useCounterStore.setState({ count: 0 });
  });

  it("increment count badhaata hai", () => {
    useCounterStore.getState().increment();
    useCounterStore.getState().increment();

    expect(useCounterStore.getState().count).toBe(2);
  });

  it("decrement count ghatata hai", () => {
    useCounterStore.getState().increment();
    useCounterStore.getState().decrement();

    expect(useCounterStore.getState().count).toBe(0);
  });

  it("reset count 0 karta hai", () => {
    useCounterStore.getState().increment();
    useCounterStore.getState().reset();

    expect(useCounterStore.getState().count).toBe(0);
  });
});
```

**Store tests — components se alag kyun?**

| | Component test | Store test |
|---|---|---|
| Access | `render` + UI interact | `getState()` + action call |
| Assert | DOM se | `getState().count` se |
| State update | `userEvent` (UI se) | `getState().increment()` (direct) |

Zustand store test karne ke liye component render karne ki zaroorat **nahi hai** — `useCounterStore.getState().increment()` direct call karo, aur `getState().count` se verify. Fast + isolated.

`beforeEach` mein `setState({ count: 0 })` — state reset karta hai, kyunki store module-level singleton hai aur tests ke beech shared rehta hai.

## Step 4 — Component Tests: TodoApp

7.3 mein `TodoApp.test.tsx` pehla test likha tha. Ab usme aur test add karte hain — delete aur toggle behaviour. `src/components/__tests__/TodoApp.test.tsx` ko update karo:

```tsx
// src/components/__tests__/TodoApp.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, it, expect, beforeEach } from "vitest";
import TodoApp from "../TodoApp";

describe("TodoApp", () => {
  beforeEach(() => {
    localStorage.clear();
  });

  it("naya task add karta hai", async () => {
    const user = userEvent.setup();
    render(<TodoApp />);

    await user.type(screen.getByPlaceholderText("Add a task..."), "Buy milk");
    await user.click(screen.getByRole("button", { name: "Add" }));

    expect(screen.getByText("Buy milk")).toBeInTheDocument();
  });

  it("task complete toggle karta hai", async () => {
    const user = userEvent.setup();
    render(<TodoApp />);

    await user.type(screen.getByPlaceholderText("Add a task..."), "Pay bills");
    await user.click(screen.getByRole("button", { name: "Add" }));

    const checkbox = screen.getByRole("checkbox", { name: "Pay bills" });
    await user.click(checkbox);

    expect(checkbox).toBeChecked();
  });

  it("task delete karta hai", async () => {
    const user = userEvent.setup();
    render(<TodoApp />);

    await user.type(screen.getByPlaceholderText("Add a task..."), "Temp task");
    await user.click(screen.getByRole("button", { name: "Add" }));

    await user.click(screen.getByRole("button", { name: "Delete" }));

    expect(screen.queryByText("Temp task")).not.toBeInTheDocument();
  });
});
```

**Kya notice karo:**

| Pattern | Kya |
|---------|-----|
| `getByRole("checkbox", { name: "Pay bills" })` | Checkbox accessible name se — label se |
| `expect(checkbox).toBeChecked()` | jest-dom matcher — checked state |
| `queryByText(...).not.toBeInTheDocument()` | **queryBy** (null return) + negative assertion — "exists nahi" check |
| Har test mein `beforeEach` localStorage.clear | Tests isolated |

**getBy vs queryBy ka fark yahan dikhta hai:** `getByText` error throw karta hai agar element na ho. `queryByText` null return karta hai — isliye "element REMOVE ho gaya" check karne ke liye `queryBy` use karte ho.

## In Your Own Words

1. Real API ke bajaye `vi.spyOn(globalThis, "fetch")` kyun use karte hain tests mein?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Real network call tests ko slow aur flaky banata hai — network delay, server down, rate limit, random failures. Test deterministic hone chahiye — har baar same result. Mock fetch (`vi.spyOn`) real API ki jagah controlled response deta hai — success ya error exactly hum control karte hain. Isse test fast, reliable aur isolated hota hai. Test mein asli server pe depend karna kabhi bhi best practice nahi hai.

</details>

2. Hook tests mein `renderHook` aur `act` ka role kya hai? Store tests mein dono ki zaroorat kyun nahi?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `renderHook` hook ko bina component ke render karta hai, aur `result.current` se uski return value access hoti hai. Jab hook ki state update hoti hai (jaise `result.current[1](newValue)`), `act` React ko re-render ke liye batata hai — taaki assertion updated value pe chale. Store tests mein dono ki zaroorat nahi kyunki Zustand store React render cycle se bahar hai — `useCounterStore.getState().increment()` direct action call karta hai aur `getState().count` direct value deta hai. No render, no act.

</details>

3. `getByText` vs `queryByText` — kya fark hai, aur delete-test mein `queryByText` kyun?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `getByText` element nahi mila toh **error throw** karta hai — "exists" check karne ke liye. `queryByText` element nahi mila toh **null** return karta hai — "exists nahi" check karne ke liye. Delete test mein hum verify karte hain ki task GAYA hai — `queryByText("Temp task")` null return karega (agar delete hua hai), aur `expect(...).not.toBeInTheDocument()` null pe pass hota hai. Agar `getByText` use karte toh delete hone ke baad error throw — hume "task remove ho gaya" ke bajaye "element nahi mila" ka error milta, jo test ka intent galat hota.

</details>

4. Har test se pehle `localStorage.clear()` / `setState({ count: 0 })` kyun zaroori hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Kyunki jsdom ka `localStorage` aur Zustand ka store **module-level singletons** hain — wo tests ke beech shared rehte hain. Ek test ne value save ki, agar clean-up nahi kiya toh agla test wahi value dekhega aur uske assertions fail ho sakte hain. `beforeEach` mein cleanup ensure karta hai ki **har test isolated** hai — fresh state se shuru hota hai, kisi doosre test ke data pe depend nahi karta. Isolated tests deterministic hote hain.

</details>

5. Store tests components ke tests se kyun zyada fast aur simple hote hain? Kab store test karna better hai vs component test?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Store test mein component render nahi hota, DOM nahi hota, user interaction simulate nahi hota — bas `getState().action()` call karke state verify karo. Isliye fast aur simple. Component test tab useful hai jab UI interaction verify karna ho — button click pe kya dikhta hai. Best practice: **store ka logic store test mein, UI ka logic component test mein**. Store mein business logic (increment, decrement, reset) pure JavaScript hai — waha component ka overhead bekar hai. Component mein render behaviour test karo (task dikhta hai, checkbox checked hota hai).

</details>
