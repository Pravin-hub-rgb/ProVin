## Problem Pehle — White Screen of Death

Koi scenario socho. Tumhari app live hai. Ek user profile page khol raha hai, aur ek user ka `email` missing aaya (database mein khali). Component ne `email.toUpperCase()` karne ki koshish ki — aur `undefined.toUpperCase()` **TypeError** dega. Error render ke andar throw hua.

**React ka default behaviour kya hai?** Ye dekho:

```
Component render karte waqt error throw hota hai
        │
        ▼
React poori component tree ko unmount kar deta hai
        │
        ▼
User ko SIRF WHITE SCREEN dikhta hai
```

Poori app. Ek chhote se missing field ke karan. User refresh kare toh bhi wahi error, wahi white screen. Isko **"White Screen of Death"** kehte hain.

**Coder mindset:** "User ko blank screen nahi dikhani chahiye. Kuch toh dikhna chahiye — aur baaki app (jo crash nahi hui) chalti rehni chahiye."

Yahi problem Error Boundaries solve karti hain. Ab chalo ise step by step banate hain.

## Error Boundary Kya Hai

**Error Boundary** ek component hai jo apne andar ke subtree mein render errors ko **catch** karta hai — aur uski jagah ek **fallback UI** dikhata hai.

```
Error Boundary
    │
    ├── [Crash hua component]   ← error yahan aaya
    │
    ▼
Boundary catch karti hai → fallback UI dikhati hai → baaki app safe
```

**Important:** Error boundary khud React component hai, lekin **class component** hona zaroori hai. Kyun? Kyunki error boundaries ko React ke lifecycle methods ki zaroorat hoti hai, aur woh methods class components mein hi hote hain:

| Class method | Kaam |
|-------------|------|
| `static getDerivedStateFromError()` | Error aane pe state update karo → fallback render hoga |
| `componentDidCatch()` | Error ko log karo (side effects — console, API call) |

Ye bilkul aisa rare case hai jahan class component **only** option hai (React team abhi hook API pe kaam kar rahi hai). Baaki app modern React (hooks) mein hi likhi jayegi.

### Step 4a — Pahli File, Sirf Structure

Pehli file banate hain — `src/components/ErrorBoundary.tsx` (folder `components` already ho sakta hai, nahi toh banao).

**Code se pehle kya logic sochni hai:**

- **`Component` kya hai?** React ki premade class — jisse class components *derive* karte hain. Tumhari class `Component` jo functionality deta hai inherit karti hai (state, `render`, lifecycle). Isliye `extends Component` likhte ho — "meri class Component ki saari shaktiyan use karti hai".
- **`ReactNode` kya hai?** `children` ka type. `children` = jo elements tum component ke andar daalo (`<ErrorBoundary><UserCard/></ErrorBoundary>` mein `<UserCard/>`). `ReactNode` ka matlab — "children kuch bhi ho sakta hai: text, element, ya array". Isliye type safe hai.
- **`Props` aur `State` kyun?** Class component ki do types hoti hain — jo tum andar se data ho (props) aur jo state track karni hai. Error boundary ko ek hi prop chahiye (`children`) aur ek hi state (`hasError`).

Ab code — `src/components/ErrorBoundary.tsx`:

```tsx
// src/components/ErrorBoundary.tsx
import { Component, type ReactNode } from "react";

interface ErrorBoundaryProps {
  children: ReactNode;
}

interface ErrorBoundaryState {
  hasError: boolean;
}

export class ErrorBoundary extends Component<
  ErrorBoundaryProps,
  ErrorBoundaryState
> {
  constructor(props: ErrorBoundaryProps) {
    super(props);
    this.state = { hasError: false };
  }

  render() {
    return this.props.children;
  }
}
```

**Har line ka matlab — line by line:**

| Code | Matlab |
|------|--------|
| `import { Component, type ReactNode } from "react"` | React se `Component` (class banane ke liye) aur `ReactNode` (children ka type) leke aao |
| `interface ErrorBoundaryProps` | Props ka shape — is boundary ko `children` milta hai |
| `interface ErrorBoundaryState` | State ka shape — ek boolean `hasError` |
| `class ErrorBoundary extends Component<Props, State>` | Nayi class jo React ki `Component` se banti hai; `<>` mein do types — pahle Props, phir State |
| `constructor(props)` | Jab bhi is component ka instance banta hai, yahan initial state set karte ho |
| `super(props)` | `Component` ka apna constructor call karo (React ko props de do). **Iske bina class theek connect nahi hoti.** |
| `this.state = { hasError: false }` | Initial state — abhi koi error nahi, isliye `false` |
| `render()` | Har class component mein hamesha `render()` hota hai — yeh decide karta hai kya UI dikhega. Abhi toh bas `children` return karta hai |
| `return this.props.children` | "jo bhi mere andar daala, wahi dikhao" |

**Abhi ye boundary kuch nahi karti** — bas children pass karti hai (jaise koi normal wrapper). Structure kaam kar raha hai. Ab isme error handling add karte hain — lekin pehle ek concept.

### Step 4b — getDerivedStateFromError + Fallback

**Concept pehle — `static` kya hai?**

Class ke andar do tarah ke methods hote hain:

| Tarah | Kiske liye | Example |
|-------|-----------|--------|
| **`static` method** | Class khud — instance (object) nahi chahiye | `Math.round()` — `Math` ki instance nahi banate, direct call |
| **Normal method** | Specific instance — usi riwai `this` access karta hai | `obj.method()` |

Static ka matlab — yeh method **kisi specific component instance se nahi juda**. React ise **directly call karta hai bina component instance banaye**. Aur isliye iska koi `this` nahi hota — tum `this.state` nahi likh sakte, `this` kisi instance ko point nahi karta. Yehi tension hoti hai.

**Concept — `getDerivedStateFromError` ka naam samjho:**

```
getDerivedState  →  "State derived karo"  →  error se state banao
fromError        →  yeh error se AA RAHA hai
```

React ko dikh raha hai ki environment mein error hai. Woh is method ko call karta hai. Tum uska kaam karte ho: "is error se mere state ka `hasError` = `true` kar do." Naye state ka object return karte ho — React woh state apply kar deta hai.

**Kyun render mein check karte hain?** Kyunki ab tak state `hasError: false` thi. Error aane pe `getDerivedStateFromError` use `true` kar deta hai. Ab `render()` kya dikhega woh us check pe depend karta hai:

```
hasError?  →  TRUE  →  fallback UI dikhao ("Kuch galat ho gaya")
          →  FALSE →  children dikhao (normal)
```

Ab code — wahi file `ErrorBoundary.tsx`, yeh add karo:

```tsx
// src/components/ErrorBoundary.tsx (update — yeh dono add karo)
  static getDerivedStateFromError(): ErrorBoundaryState {
    return { hasError: true };
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="error-fallback">
          <h2>Kuch galat ho gaya 😅</h2>
          <p>Try refresh karke dekho. Agar wahi error aaye, toh humein report karo.</p>
        </div>
      );
    }

    return this.props.children;
  }
```

Ek-ek karke:

- `static getDerivedStateFromError()` — **static** (upar samjhaya) + `ErrorBoundaryState` return type.
- `return { hasError: true }` — error se derive hui state. React use apply karta hai.
- `if (this.state.hasError)` — ab agla render: check karta hai error hua ya nahi.
- `<h2>Kuch galat ho gaya 😅</h2>` — fallback UI. User ko blank screen ki jagah maloom padta hai ki problem hai.
- `return this.props.children` — warna (no error) normal children dikhao.

### Step 4c — componentDidCatch (Logging)

Fallback sirf aadha kaam hai — **kya dikhana hai**. Doosra aadha kaam — **kya hua, uska trace** (tumhe debugging ke liye chahiye). Isliye `componentDidCatch`.

**Concept — naam kyun dho pata hai:** "Did Catch" = "catch kar liya". React ne error catch kiya, aur tumhe bata raha hai by calling this method. `componentDidCatch` ek lifecycle method hai — yeh automatically chal jata hai error catch hone ke baad.

**Kyun ek alag method?** Kyon logic split rakhte hain — `getDerivedStateFromError` sirf UI state (render ke live) handle karta hai, aur `componentDidCatch` side effects (logging, reporting) — kyunki side effects yahan chala sakte ho, `getDerivedStateFromError` ke andar nahi.

Ab code — wahi file add karo:

```tsx
// src/components/ErrorBoundary.tsx (update — yeh method add karo)
  componentDidCatch(error: Error, info: { componentStack: string }) {
    console.error("💥 Error caught:", error.message, info.componentStack);
  }
```

Params samjho:

- **`error: Error`** — jo actual error object aaya (`.message`, `.stack` uspar hote hain).
- **`info: { componentStack: string }`** — batata hai kis component tree mein error aaya. Debugging ke liye golden.
- `console.error` — abhi local log kaafi. Real app mein yahan tum Sentry/LogRocket jaisi service ko bhejte ho:

```ts
// concept — real app mein aisa reporting hoti hai
sendToErrorService({
  message: error.message,
  stack: error.stack,
  componentStack: info.componentStack,
  url: window.location.href,
});
```

`componentDidCatch` humne abhi yahan add kiya, par yaad rakho — **fallback woh `getDerivedStateFromError` + `render` se aata hai, `componentDidCatch` sirf logging ke liye hai.**

### Poore ErrorBoundary Ka Complete Picture — Flow

Ab yeh teenon pieces ek saath aise kaam karte hain:

```
Child subtree render karte waqt error
        │
        ▼
React getDerivedStateFromError() call karta hai (static, bina instance)
        │
        ▼
state.hasError = true
        │
        ▼
render() → fallback UI dikhata hai ("Kuch galat ho gaya")
        │
        ▼
componentDidCatch(error, info) → error log hota hai
        │
        ▼
Baaki tree (boundary ke bahar) continue render
```

Dekho — **kya step-by-step banaya**: Step 4a mein structure (sirf class, kuch nahi karta), Step 4b mein fallback, Step 4c mein logging. Har step chhota, har step samajh aata hai, aur har nayi concept apne code se pehle explain hui.

### Pura Code — Sab Ek Saath

Teeno pieces (4a + 4b + 4c) ek file mein mile hue, aisa dikhta hai. Copy-paste karke chala sakte ho:

```tsx
// src/components/ErrorBoundary.tsx
import { Component, type ReactNode } from "react";

interface ErrorBoundaryProps {
  children: ReactNode;
}

interface ErrorBoundaryState {
  hasError: boolean;
}

export class ErrorBoundary extends Component<
  ErrorBoundaryProps,
  ErrorBoundaryState
> {
  constructor(props: ErrorBoundaryProps) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(): ErrorBoundaryState {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: { componentStack: string }) {
    console.error("💥 Error caught:", error.message, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="error-fallback">
          <h2>Kuch galat ho gaya 😅</h2>
          <p>Try refresh karke dekho. Agar wahi error aaye, toh humein report karo.</p>
        </div>
      );
    }

    return this.props.children;
  }
}
```

Order yaad rakhne ka trick: **"Error aaya → state update (`getDerivedStateFromError`) → kya dikhaye (`render`) → kya log kare (`componentDidCatch`)"** — React isi order mein inko call karta hai.

## Granularity — Kahan Wrap Karna Hai

Yahi level hai jo production apps ko alag karta hai — **har error boundary same nahi hoti**. Decision: kahan wrap karo?

| Wrap Kahan | Fayda | Problem |
|-----------|-------|---------|
| Poora app | Sabse safe — koi crash blank screen nahi | Ek chhote section ke error pe poori app fallback mein chali jaati hai |
| Specific section | Crash section isolate hota hai — baaki app chalti hai | Har section ko wrap karna padta hai |

**Industry pattern:** Layered — top-level + feature-level:

```
ErrorBoundary (top-level — blank screen se bachao)
    │
    └── App
          ├── Header (no boundary — simple, kabhi crash nahi hota)
          ├── ErrorBoundary → UserList      ← feature boundary
          ├── ErrorBoundary → UserProfile   ← duniya ka sabse risky section
          └── Footer (no boundary)
```

Top-level boundary = **last line of defence**. Feature-level boundaries = **isolate crash**, baaki app live.

**Rule of thumb:** Jo section bahar se data leta hai (API, user input) — wahan boundary lagao. Jo static UI hai — usme lagana bekar hai.

## What Error Boundaries Are NOT

Error boundaries har error nahi catch karte. Ye dekhna zaroori hai:

| Scenario | Boundary catch karta hai? |
|----------|--------------------------|
| Render error (component function ke andar) | ✅ Haan |
| Lifecycle error (useEffect ke andar) | ✅ Haan (React 16+ se) |
| Event handler error (`onClick` ke andar) | ❌ Nahi — React handlers ko try/catch se wrap nahi karta |
| Async error (setTimeout, Promise ke andar) | ❌ Nahi — event loop ke bahar hai |
| Server-side rendering error | ❌ Nahi |
| Boundary ka apna error | ❌ Nahi — boundary khud crash nahi ho sakti |

**Event handler ke errors ka kya?** Woh boundary tak nahi pohonchte — React unhe console mein log karta hai. Agar unhe handle karna ho toh apne handler mein try/catch lagao:

```tsx
const handleClick = () => {
  try {
    // risky logic
  } catch (err) {
    console.error("Click handler error:", err);
  }
};
```

**Takeaway:** Error boundary = **render + lifecycle** errors ka net. Async/event-handler errors ke liye alag handling chahiye.

Error boundaries React apps ka **safety net** hai. Class component hota hai — hooks se nahi banta. Do kaam karta hai: fallback dikhana (`getDerivedStateFromError`) aur error log karna (`componentDidCatch`). White screen se bachata hai, aur baaki app ko chalta rehne deta hai.
