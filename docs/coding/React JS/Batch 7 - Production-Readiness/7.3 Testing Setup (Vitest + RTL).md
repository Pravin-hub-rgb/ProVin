## Problem Pehle — Regression Ka Darr

Scenario socho. App hai. Kal tumne "filter" feature add kiya. Aaj tum "dark theme" laga rahe ho. Kya guarantee hai ki filter ab bhi kaam karta hai? Tumne 2 minute pehle manually test kiya — kyunki filter tumhare dimaag mein tha.

Lekin 3 hafte baad — koi naya developer, ya tum khud — filter logic change karta hai. Filter kisi tarah tut gaya. **Aur kisi ko pata bhi nahi chala** kyunki koi test tha hi nahi.

```
Code change (theme, new feature)
        │
        ▼
Purani feature (filter) tut gayi — REGRESSION
        │
        ▼
Kisi ko pata nahi — kyunki koi test nahi tha
```

**Automated tests isi problem ko solve karte hain:** Ek baar test likho ki "filter kaam karta hai". Har baar code change ke baad — tests chalao. Agar filter tuta hai, test **red** ho jata hai, tumhe turant pata chal jaata hai. Regression ka darr khatam.

## Vitest Kya Hai — Aur Jest Se Kya Fark

**Vitest** ek JavaScript testing framework hai — **Vite ke upar built**. Kyunki tumhara project Vite se bana hai, Vitest ka integration ekdum smooth hai.

| | Jest (purana standard) | Vitest (naya, Vite-native) |
|---|---|---|
| **Setup** | Alag config, Babel/ts-jest | Vite config reuse karta hai — near-zero config |
| **Speed** | Slow (har baar rebuild) | Fast (Vite's native ESM + on-demand) |
| **TypeScript** | ts-jest / babel se | Native — Vite already handle karta hai |
| **Hot reload** | Nahi | HMR tests ke liye bhi |

Jest industry ka purana standard hai — tumhe iska naam interview mein mil sakta hai. Lekin naye Vite projects mein **Vitest** best practice hai — Vite team ka hi product. Yehi hum use karenge.

## Step 2 — Test Karne Ke Liye Chhota App

Testing seekhne ke liye bada app nahi chahiye. Ek **Counter** banate hain — ek number, ek button. Simple cheez = simple test = focus testing pe, app pe nahi.

### Counter Ki Structure — Teeno Files

Counter mein 3 cheezein hongi: component, uske logic wala hook, aur App jo counter render kare.

Nayi file banao — `src/hooks/useCounter.ts` (counter ki logic — count + increment):

```ts
// src/hooks/useCounter.ts
import { useState } from "react";

export function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);

  const increment = () => setCount((c) => c + 1);

  return { count, increment };
}
```

**Kya yeh karta hai:** ek custom hook — `count` (state) aur `increment` (count +1 karne wala function) return karta hai. `initial` default 0. Custom hook ka concept 6.1 se yaad hai — state wala logic jo kisi bhi component use kar sakta hai.

Nayi file banao — `src/components/Counter.tsx` (component jo hook use karta hai):

```tsx
// src/components/Counter.tsx
import { useCounter } from "../hooks/useCounter";

export function Counter() {
  const { count, increment } = useCounter(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={increment}>Increment</button>
    </div>
  );
}
```

**Kya yeh karta hai:** counter ko render karta hai — ek heading jisme current count, aur ek "Increment" button. Click karo → `increment()` → count badh jata hai.

Ab `src/App.tsx` mein Counter render karo:

```tsx
// src/App.tsx
import { Counter } from "./components/Counter";

function App() {
  return <Counter />;
}

export default App;
```

Browser mein test karo — count 0 dikh raha hai, button click karo, 1, 2, 3... kaam kar raha hai. **Ab yeh wahi app hai jo hum test karenge** — ek component aur ek hook. Itna hi kaafi hai.

## Step 3 — Testing Packages Install Karna

React project ki testing ke liye 5 packages chahiye. Install karo:


**Kya install hua — har package ka ek kaam:**

| Package | Kaam |
|---------|------|
| `vitest` | Testing framework — tests chalata hai |
| `jsdom` | Browser simulation in Node — DOM APIs ka fake browser |
| `@testing-library/react` | React components render karna + query karna |
| `@testing-library/user-event` | Realistic user interaction (typing, clicking) |

**Chhote shabd mein:** vitest test chala raha hai, jsdom usse browser ka sapna de raha hai (React components ko fake browser mein render karta hai), testing-library React ko render aur query karne mein help karta hai, aur jest-dom assertion likhne ka easy language deta hai.

## Step 4 — Config: Vitest Ko Batana

Teen choti cheezein chahiye — Vitest ko test environment batana, jest-dom register karna, aur test script banana.

Pehla — `vitest.config.ts` banao (project root mein, package.json ke paas):

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "jsdom",
    setupFiles: "./src/test/setup.ts",
  },
});
```

**Kya likha hai:** `environment: "jsdom"` — tests browser simulate karke chalenge (React components DOM chahiye). `setupFiles` — har test chalu hone se pehle yeh file run hogi (yahan jest-dom register hoga).

Doosra — nayi file banao `src/test/setup.ts`:

```ts
// src/test/setup.ts
import "@testing-library/jest-dom/vitest";
```

Sirf ek line — jest-dom ke extra matchers (`toBeInTheDocument`) har test mein available.

Teesra — `package.json` mein test script add karo:

```json
// package.json (scripts section mein yeh add karo)
{
  "scripts": {
    "test": "vitest"
  }
}
```

Ab run karo: `bun run test` — abhi koi test nahi hai toh "No test files found" ayega. Theek hai — ab test likhte hain.

## Pehla Test — Kya Likhte Hain?

Testing ka ek fundamental pattern: **AAA — Arrange, Act, Assert**

```
ARRANGE — setup: kya test karna hai (component render, data)
ACT      — kaam: user kya karta hai (click, type)
ASSERT   — verify: kya expect karte hain (result present?)
```

Nayi file banao — `src/components/__tests__/Counter.test.tsx` (folder `__tests__` nayi banega):

```tsx
// src/components/__tests__/Counter.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, it, expect } from "vitest";
import { Counter } from "../Counter";

describe("Counter", () => {
  it("shuruaat mein count 0 dikhata hai", () => {
    // ARRANGE — component render
    render(<Counter />);

    // ASSERT — heading mein 0 hona chahiye
    expect(screen.getByRole("heading", { name: "Count: 0" })).toBeInTheDocument();
  });

  it("Increment click karne pe count badh jata hai", async () => {
    // ARRANGE — render + user simulation setup
    const user = userEvent.setup();
    render(<Counter />);

    // ACT — button click
    await user.click(screen.getByRole("button", { name: "Increment" }));

    // ASSERT — count 1 ho gaya
    expect(screen.getByRole("heading", { name: "Count: 1" })).toBeInTheDocument();
  });
});
```

**Har part kya kar raha hai:**

| Cheez | Kya Hai |
|-------|---------|
| `describe("Counter", ...)` | Test group — Counter ke saare tests yahan |
| `it("...", ...)` | Ek test case — matlab ek behaviour |
| `userEvent.setup()` | Realistic user simulation setup |
| `render(<Counter />)` | Component ko fake DOM (jsdom) mein render karo |
| `screen.getByRole("heading", { name: "Count: 0" })` | Heading dhundho — role + accessible name se |
| `screen.getByRole("button", { name: "Increment" })` | Button dhundho — role se (accessible) |
| `await user.click(...)` | User click karta hai |
| `expect(...).toBeInTheDocument()` | Assertion — element DOM mein hona chahiye |

**Kyun `getByRole` use karte hain?** Kyunki yeh **accessibility-first** query hai — button ko uske accessible name se dhundho. Screen reader bhi wahi dhundta hai. Testing Library ka philosophy: **jis tarah user use karta hai, usi tarah test karo** — DOM structure nahi, user experience test karo.

## Jest-DOM Matchers — Assertion Ki Language

`@testing-library/jest-dom` kuch handy matchers deta hai jo plain assertions se zyada readable hain:

| Matcher | Check karta hai | Counter mein |
|---------|----------------|--------------|
| `toBeInTheDocument()` | Element DOM mein hai | Heading dikh rahi hai |
| `toHaveTextContent("...")` | Element ke andar text | `expect(screen.getByRole("heading", { name: "Count: 1" }))` |
| `toBeDisabled()` / `toBeEnabled()` | Button disabled/enabled | Form buttons |
| `toHaveValue("...")` | Input ki value | Form inputs |
| `toHaveClass("...")` | Class attribute | Styling |

**Matchers ka fayda:** assertion padhne mein likhi hui English jaise lagti hai — "is element ko document mein hona chahiye". Test kitna clear ho, isi par dependable ho jaata hai.

## Hooks Test Karna — renderHook

Components test karte hain `render` se. Hooks (jaise humara `useCounter`) ka apna alag helper hai — **`renderHook`**. Nayi file banao — `src/hooks/__tests__/useCounter.test.ts`:

```tsx
// src/hooks/__tests__/useCounter.test.ts
import { renderHook, act } from "@testing-library/react";
import { describe, it, expect } from "vitest";
import { useCounter } from "../useCounter";

describe("useCounter", () => {
  it("initial value deta hai jab koi default nahi diya", () => {
    const { result } = renderHook(() => useCounter());

    expect(result.current.count).toBe(0);
  });

  it("increment call karne pe count badh jata hai", () => {
    const { result } = renderHook(() => useCounter(5));

    act(() => {
      result.current.increment();
    });

    expect(result.current.count).toBe(6);
  });
});
```

**Fark — components vs hooks tests:**

| | Component test | Hook test |
|---|---|---|
| Helper | `render(<Component />)` | `renderHook(() => useHook(...))` |
| Result | DOM se query karo | `result.current` |
| State update | `userEvent` se | `act(() => result.current.increment())` |
| Assertion | `screen.getBy...` | `result.current.count` |

`act()` — React ko batata hai ki "state update ho raha hai, ab re-render karo". Hooks test mein jab state update karte ho, `act` mein wrap karo.

## Common Testing Patterns

### Pattern 1 — getByRole vs getByText

```tsx
// Accessible — role + name (recommended)
screen.getByRole("button", { name: "Increment" })

// Text se (kabhi specific element chahiye)
screen.getByText("Increment")
```

### Pattern 2 — Query Errors

Testing Library ke queries **element nahi mila toh error throw karte hain**:

- `getBy...` — mila nahi toh **error** (test fail) — most common
- `queryBy...` — mila nahi toh **null** return (check "exists nahi" ke liye)
- `findBy...` — async wait karta hai (loading ke baad)

```tsx
it("loading ke baad data dikhta hai", async () => {
  render(<RecipeList />);
  expect(screen.queryByText("Loading...")).not.toBeInTheDocument();
  expect(await screen.findByText("Chicken Soup")).toBeInTheDocument();
});
```

`findByText` **wait** karta hai async render ke liye — fetch wale components ke liye perfect. (Agar koi component aisa ho jo API se data laata hai — jaise 2.2 mein banaya tha.)

### Pattern 3 — Multiple Behaviours, Multiple `it`

```tsx
describe("Counter", () => {
  it("initial count 0 dikhata hai", () => { ... });
  it("Increment pe count badhta hai", () => { ... });
});
```

Har `it` = ek behaviour. Poora "Counter sahi hai" ek test mein nahi — alag-alag test, alag-alag verify.

## What Testing Is NOT

- ❌ Testing ka matlab **har line of code** ke tests likhna nahi — core behaviours ko cover karo
- ❌ Tests sirf **assertions** nahi hain — wo behaviour ka documentation hai ("agar user X kare, toh Y dikhe")
- ❌ `getByRole` sirf **class/id** ke liye nahi hai — accessible queries use karo (screen reader wala fark)
- ❌ Tests **deterministic** hone chahiye — koi timing guess, koi "random" — har baar same result
- ❌ Test ka success matlab app **production-ready** nahi — tests ek layer hai, manual QA + E2E bhi chahiye

## So Here's the Takeaway

Testing koi "bonus" nahi — production app ka **required part** hai. Vitest + React Testing Library se components aur hooks dono test ho jaate hain. Pattern hamesha same: **AAA**. Philosophy same: **user jaisa interact karta hai waise test karo**. Ab ek test likha, use chalao — aur ek baar ka confidence ki app tuti nahi.

**Aur is baar ki khaas baat:** Humne purana project nahi uthaya — fresh project banaaya, chhota sa Counter banaya, aur uspe testing seekhi. Yeh hi tarika hai — nayi cheez seekhni ho toh chhote se shuru karo, na ki purane complex code pe.

<details>
<summary>Show Answer</summary>

4. `getByRole` vs `getByText` — kab kaunsa use karo, aur `getByRole` kyun recommended hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `getByRole` element ko uske ARIA role + accessible name se dhundhta hai — jaise `getByRole("button", { name: "Increment" })`. Ye recommended hai kyunki yeh accessibility-first hai — screen reader bhi wahi identify karta hai. Isse tests user experience test karte hain, DOM structure nahi — structure badlo toh test nahi tootega. `getByText` use karo jab role se identify karna unnatural ho (jaise paragraph ka specific text). Rule: pehle role query try karo, phir text.

</details>

5. `render` aur `renderHook` mein kya fark hai, aur hook test mein `act()` kyun jaruri hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `render` components ko fake DOM mein render karta hai — result DOM se `screen` ke queries se check karte ho. `renderHook` custom hooks ko render karta hai bina component ke — result `result.current` se access karte ho (object jo hook return karta hai). `act()` jaruri hai kyunki jab hook ka state update hota hai (jaise `result.current.increment()`), React ko re-render ke liye batana padta hai — `act()` wahi "re-render batch" provide karta hai. Bina act ke React warn karega aur assertion purani value pe chal sakta hai.
