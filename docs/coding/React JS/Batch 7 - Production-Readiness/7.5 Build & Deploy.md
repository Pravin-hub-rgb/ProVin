## Problem First — Dev Server Is Only for You

You've built a to-do app. It works on your computer through the local dev server. You'd probably want to show it to a friend. But what happens if you just send them the link you see in your browser — `http://localhost:5173`?

`localhost` means "this computer." On your friend's machine, it points to *their* own computer, not yours. The app lives only on yours. Two real options: send them the whole source code, or put it somewhere on the internet that gives him a link.

Sending the source means they'd have to install tools and run the dev server themselves. Not great. So we need to put it online — somewhere that just serves files to anyone who visits.

But here's the catch: a place like Vercel is basically a computer on the internet whose only job is to hand files to anyone who visits. It doesn't run your dev server. It just serves files to the browser. And your project folder holds TypeScript and TSX files, which a browser can't read on its own.

So what do you think has to happen to your project before the browser can use it?

---

## Step 1 — Production Build

Your project is written in TypeScript. The browser only understands JavaScript. So it needs converting first. That conversion is called **the build**. You run one command, and the tool takes your whole project and produces a folder of browser-ready files.

```bash
bun run build
# npm: npm run build
```

**What happens:**

```
Source code (TSX, TS, CSS)
        │
        ▼
Vite: bundling + minification + optimization
        │
        ▼
dist/ folder — production-ready files
├── index.html
├── assets/
│   ├── index-abc123.js   → minified JS bundle
│   ├── index-xyz456.css  → minified CSS
│   └── ...
```

**What each step does:**

| Step | What it does |
|------|-----|
| **Bundling** | Combines all JS/TSX files into one (or a few) small files |
| **Minification** | Shorter variable names (`a`, `b`), removes spaces and comments — smaller file |
| **Tree-shaking** | Removes unused code (unused imports, dead code) from the bundle |
| **Code splitting** | Separates lazy parts (from 7.5.1) — only loaded when needed |
| **Hash filenames** | `index-abc123.js` — cache busting, new file on every update |

**Result:** The `dist/` folder holds optimized files that load quickly in the browser.

Notice the start of the command — `tsc -b` checks your TypeScript for errors first. Only if that passes does Vite do the actual build, so a type error would stop it before anything gets made.

---

## Step 2 — Checking the Production Build (Preview)

After building, test the production build locally with the `preview` command:

```bash
bun run preview
# npm: npm run preview
```

This serves the production build locally — like a real production experience. The dev server uses one port, preview uses another (4173). It's still only on your computer, but now it's the real built version, not the dev server.

Check here: routing works? lazy loading works? The build is ready to deploy?

**Build check is important:** Pay attention to bundle size:

```bash
bun run build
# npm: npm run build
```

Vite reports the bundle size in output:

```
dist/index.html                    0.52 kB → gzip: 0.31 kB
dist/assets/index-DcP2b5sB.js  212.35 kB → gzip: 68.21 kB
```

**Why bundle size matters:** 68KB gzipped JS — about 1 second load time on Indian 4G. 2MB gzipped — 15+ seconds, users leave. Performance = user retention.

**Order matters:** Build first, preview second, every time you change something. Preview only serves what's already in `dist/`, so if you skip the build, there's either nothing to show or an old version.

## Step 3 — GitHub (Prerequisite for Deploy)

A place like Vercel connects to GitHub, so instead of you uploading files by hand, it watches your repo and builds automatically. That also gives you a nice bonus: every time you push a change to GitHub, Vercel rebuilds and updates your live site automatically.

The first step is putting your project on GitHub, done with Git. Have you used Git before (`git init`, `git commit`)? If so, the steps are:

```bash
git init
git add .
git commit -m "init: custom hooks demo"
git remote add origin https://github.com/yourname/custom-hooks-demo.git
git push -u origin main
```

One thing to check before you push: make sure your `node_modules` folder and the `dist` folder are ignored. Vite's starter usually includes a `.gitignore` that already covers both.

---

## Step 4 — Deploy (Vercel)

**Vercel** is the most popular deploy platform for React/Vite projects (free tier). Two ways: push to GitHub and connect Vercel (auto-deploy), or use the CLI.

### GitHub + Vercel (Recommended)

1. Sign up at [vercel.com](https://vercel.com) (with GitHub)
2. Click "Add New Project" → select your repo
3. Framework: **Vite** (Vercel auto-detects)
4. Add env vars (if you have any — see Step 5)
5. Click Deploy — you'll get a URL like `https://custom-hooks-demo.vercel.app`

**Auto-deploy magic:** Every push to GitHub → Vercel auto-builds + auto-deploys. This is **Continuous Deployment** — you push code, the app updates. If the build fails, Vercel keeps serving the last working version, so a broken push won't take your live site down.

### Vercel CLI

```bash
bunx vercel
```

After CLI prompts, it deploys directly.

## Step 5 — Env Vars in Production

In 7.2 we learned `.env` + `VITE_` prefix. Here's how it works in production builds:

**Build-time injection:** Vite injects env vars **at build time** into the bundle. Not at runtime.

```
At build time (bun run build):
  import.meta.env.VITE_QUOTE_API_URL → "https://api.quotable.io/random"
                                        ↓ written directly into the bundle

Then the bundle runs in the browser — with that URL hardcoded
```

**What this means:** Set production env vars *before* deploying. Two ways:

**Method 1 — `.env.production` file:**

```
# .env.production
VITE_QUOTE_API_URL=https://api.quotable.io/random
```

Vite automatically uses `.env.production` at build time (when you run `bun run build`).

**Method 2 — Platform env settings:** Set env vars in Vercel/Netlify dashboard.

**The secret warning:** Because `VITE_` variables are baked into the bundle, anything in them is public. Anyone can open the browser's dev tools, look at your JavaScript file, and read the value. So `VITE_` variables are fine for public things like an API address, but never for secrets like passwords or API keys.

## Step 7 — Deploy (GitHub Pages) — Alternative

**GitHub Pages** is GitHub's free static hosting. Setup differs slightly from Vercel — Pages needs static files.

**First**, set `base` in `vite.config.ts` — for the repo subdirectory:

```ts
// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  // GitHub Pages serves the app in a repo subfolder
  base: "/custom-hooks-demo/",
});
```

**Then build + deploy:**

```bash
bun run build
# npm: npm run build
```

Upload the `dist/` folder to GitHub Pages — manually, or via GitHub Actions (a workflow file).

## Vercel vs GitHub Pages — When to Use What

| | Vercel | GitHub Pages |
|---|---|---|
| **Setup** | Auto (framework detection) | Manual (base path config) |
| **Env vars** | Easy on the dashboard | Set at build time |
| **Continuous Deploy** | Auto on every GitHub push | Via GitHub Actions |
| **Best for** | Professional portfolio projects | Small static projects |

**Recommendation:** For portfolio/capstone projects, **Vercel** — cleanest setup + auto-deploy. GitHub Pages also works but needs extra config (base path, Actions).

## Post-Deploy — Verification Checklist

After deploying, verify production quality:

| Check | What to do |
|-------|-----|
| **Live URL test** | Open on mobile — responsive? |
| **Hard refresh** | New bundle loaded, not cached version? |
| **Console check** | Any errors in DevTools console? |
| **Lighthouse / PageSpeed Insights** | Performance/accessibility score (Google PageSpeed Insights works in any browser) |
| **Build env vars** | Production API URL is correct? |

**Console check:** Open your live link, press F12, click the Console tab. Anything in red is an error, yellow is a warning. If it's empty or only has grey info lines, that's a good sign.

**Lighthouse:** Google PageSpeed Insights runs Lighthouse for you in any browser — paste your URL and click Analyze. It scores four areas out of 100: Performance (how fast your page loads), Accessibility (screen readers, color contrast, button labels), Best Practices (security, modern APIs), and SEO (search engine visibility). Green is 90+, orange is middle, red is low.
