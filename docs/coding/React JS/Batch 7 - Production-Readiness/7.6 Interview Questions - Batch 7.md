### 75. What are Error Boundaries?

**Answer:** Class components (`getDerivedStateFromError` + `componentDidCatch`) that catch JavaScript errors **in their child tree** and render a fallback UI instead of crashing the whole app. You cannot build one with hooks yet.

**Likely follow-up:** *Where do you place them?* — around risky sections (checkout, chat, a whole route), not just one global wrapper — so one broken widget degrades gracefully instead of white-screening everything.

---

### 76. What do Error Boundaries NOT catch?

**Answer:** Errors in event handlers, async code (`setTimeout`, Promises), server-side rendering errors, and errors inside the boundary itself. Those still need manual `try/catch` (or `.catch()` on promises).

**Likely follow-up:** *A click handler throws — boundary useless?* — yes; the boundary only watches render/lifecycle paths. Wrap the handler body in `try/catch` and set error state yourself.

### 22. What is `dangerouslySetInnerHTML`, and what's the risk?

**Answer:** A deliberate escape hatch that injects a raw HTML string into the DOM. The risk is **XSS** (cross-site scripting): if the content is user-generated and unsanitized, an attacker's script runs with your app's privileges. Sanitize with DOMPurify before ever using it.

**Likely follow-up:** *Doesn't React escape by default?* — yes, and that's your first line of defense; this prop is the opt-out, which is why the API name literally says "dangerously".

### 110. How do you handle environment-specific configuration in React?

**Answer:** Build-tool env variables — Vite: `import.meta.env.VITE_*` from `.env` files — and **never expose secrets in the client bundle**. Anything shipped to the browser is public; sensitive keys stay on the backend/server.

**Likely follow-up:** *So where does an API secret go?* — only server-side (route/server action/proxy); the client gets an endpoint that has the key server-side.

### 77. What is the philosophy of React Testing Library?

**Answer:** "Test the way users use your app" — query by role/label (`getByRole`, `getByLabelText`) and drive real interactions (`userEvent`), asserting on rendered output. Never reach into internal state or implementation details, so tests survive refactors.

**Likely follow-up:** *Why role-based queries?* — they mirror what assistive tech sees, so your test doubles as an accessibility check.

---

### 78. What roles do Jest (or Vitest) and React Testing Library play?

**Answer:** The test **runner + assertion library** (runs test files, provides `expect()`) vs the **render/query/interact utilities** (render components, query the DOM, fire events). Two different jobs, used together — this course pairs Vitest with RTL.

**Likely follow-up:** *Why Vitest over Jest?* — native ES modules and Vite-speed, sharing your Vite config; the RTL API is identical either way.

---

### 79. What is snapshot testing, and what's its risk?

**Answer:** It saves a string of the component's rendered output and fails when it changes. The risk is **rubber-stamping**: developers update snapshots without reviewing them, so the check becomes a false green. Use sparingly, prefer explicit assertions.

**Likely follow-up:** *When are snapshots fine?* — stable, low-volatility output (serialized config, generated markup), always with reviewed diffs; never as your only test for complex UI.
