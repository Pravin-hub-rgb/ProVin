## Abhi Tak Kya Hua

7.1 mein **Error Boundaries** seekha — render errors ko catch karna, fallback UI dikhana, `componentDidCatch` se logging. App ab crash se bacha payegi.

Ab app ko aur ek cheez se bachana hai — **attackers se**. Batch 7 ka doosra topic: **security**. React app ke context mein iska matlab hai — XSS (Cross-Site Scripting), env vars (secrets), aur safe rendering.

Toh aisa scene hai...

---

## Problem Pehle — User Data Ka Bharosa

Ek comment section socho. User comment likhta hai:

> **Normal user:** "Yeh app bhout badhiya hai! 👍"

> **Malicious user:** `<script>window.location = "https://evil-site.com"</script>`

Ab agar tum woh comment directly page pe render kar do, toh kya hoga? Browser `<script>` ko asli JavaScript ki tarah treat karega aur usse **execute** kar dega. User ka browser (aur uski private data) evil site pe redirect ho jayega. Isi ko **XSS — Cross-Site Scripting** kehte hain.

```
User comment: <script>steal cookies → evil site</script>
        │
        ▼
Tumne use directly render kar diya
        │
        ▼
Browser script execute karta hai
        │
        ▼
Attacker ko user ka data mila 😟
```

**Pehla sawaal — "Lekin main toh normal JavaScript likh raha hoon, yaar?"** Haan, aur wahi tumhara bachaav hai. React default mein **HTML escaping** karta hai. Dekhte hain kaise.

---

## React Default Escaping — Tumhara Pehla Bachaav

Jab tum React mein koi value JSX ke andar `{}` mein dallte ho, React usko **escape** kar deta hai. Matlab HTML special characters ko text mein badal deta hai taaki browser unhe code na samjhe.

```tsx
// src/components/Comment.tsx
function Comment({ text }: { text: string }) {
  return <p>{text}</p>;
}

// text = '<script>alert("hack")</script>'
// React render karta hai as TEXT, script ke roop mein NAHI
```

React `<script>` ko `&lt;script&gt;` mein convert kar deta hai — browser ko text dikhta hai, script execute nahi hota. Yeh default behaviour hai — **kuch karna nahi padta**. Jaise hi tum value JSX mein `{}` se dallte ho, React usse render-safe bana deta hai.

**Yehi reason hai ki React apps default mein (bahut se) XSS attacks se safe hote hain** — jab tak tum built-in safety ko bypass nahi karte.

---

## Problem — dangerouslySetInnerHTML Se Bypass

React mein ek prop hai: `dangerouslySetInnerHTML`. Naam hi sab kuch bataata hai — **dangerously**. Yeh built-in escaping ko bypass karta hai, aur raw HTML seedha DOM mein daalta hai.

```tsx
// ⚠️ DANGEROUS — yeh HTML ko as-is render karta hai
function RichContent({ html }: { html: string }) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />;
}
```

**Kyun koi ise use kare?** Real-world cases — CMS se aaya HTML content (blog post), rich text editor ka output, koi legacy format. Inme user ke alawa bhi source ho sakta hai.

**Problem kya hai:** Agar woh HTML tumhare control mein nahi hai — user-generated hai — toh `dangerouslySetInnerHTML` us script ko **execute** kar dega. Tumne React ka safety net hata diya.

```
User-uploaded HTML + dangerouslySetInnerHTML
        │
        ▼
React escaping BYPASS
        │
        ▼
Raw HTML DOM mein → script execute → XSS
```

---

## Safe Alternative — Sanitization (DOMPurify)

Agar tumhe raw HTML render karna hi hai, toh pehle usko **sanitize** karo — matlab script tags, event handlers (`onclick=`), dangerous attributes ko nikaal do. Industry-standard library: **DOMPurify**.

```bash
bun add dompurify
```

```tsx
// src/components/RichContent.tsx
import DOMPurify from "dompurify";

function RichContent({ html }: { html: string }) {
  const safeHtml = DOMPurify.sanitize(html);
  return <div dangerouslySetInnerHTML={{ __html: safeHtml }} />;
}
```

DOMPurify HTML leta hai, usme se script, event handlers, `javascript:` URLs nikaalta hai, aur safe HTML return karta hai. Phir usi safe HTML ko `dangerouslySetInnerHTML` mein dallo.

```
Raw HTML ──→ DOMPurify.sanitize ──→ Safe HTML ──→ render
   │                                  │
<script>...</script>                  script tags removed ✅
onclick="..."                          event handlers removed ✅
```

**Rules of thumb:**

| Scenario | Kya karo |
|----------|----------|
| User text jo `{}` mein render ho | Kuch nahi — React default escape karta hai ✅ |
| Raw HTML jo trusted source se ho | `dangerouslySetInnerHTML` theek hai (apne CMS) |
| Raw HTML jo user se aata ho | **DOMPurify se sanitize karo** — hamesha |

**Golden rule:** `dangerouslySetInnerHTML` = last resort. Default escaping pe bharosa karo, aur agar bypass karna hi ho toh pehle sanitize.

## Env Vars — Secrets Ka Sahi Tareeka

Ab ek alag security problem — **secrets**. Tumhare app ko koi API key chahiye (TanStack Query, auth, koi service). Usko kahan rakho?

**Galat tareeka — hardcoded:**

```ts
// ⚠️ DANGEROUS — API key source code mein
const API_KEY = "sk_live_ABC123secretSecret";
```

Yeh commit ho jayegi, GitHub pe dikhegi, koi bhi access kar sakta hai. **Kabhi nahi.**

**Sahi tareeka — `.env` file + Vite's `import.meta.env`:**

React/Vite apps mein ek `.env` file banati hai aur secrets ko `VITE_` prefix ke saath rakhte hain:

```
# .env
VITE_QUOTE_API_URL=https://api.quotable.io/random
```

```
# .env.local
# Local-only secrets — ise .gitignore mein daalna
VITE_PRIVATE_KEY=local_dev_secret
```

Tumse code mein env vars aise access karoge:

```ts
// src/hooks/useQuote.ts
const API_URL = import.meta.env.VITE_QUOTE_API_URL;
```

**`VITE_` prefix kyun?** Vite sirf `VITE_` se shuru hone wale vars ko **client bundle mein expose** karta hai. Ye intentional safety — tumhare `.env` mein koi bhi var ho, sirf `VITE_` wale hi browser tak pohnchenge.

> **"We'll explore this in detail in the next topic"** — `import.meta.env` ka lifetime aur production build (7.5 mein) wahan cover hoga: env vars build time pe bundle mein kaise aa jaate hain. Abhi bas concept samjho — secrets `.env` mein, code mein `import.meta.env` se.

---

## Critical — Client Mein Secrets Kabhi Nahi Pohnchte

Ek bhout important baat — **React frontend hai, aur uska poora code browser mein chalta hai.** Browser ka matlab — user dekh sakta hai.

```
Kabhi bhoolna nahi:
Code bundle → browser → koi bhi DevTools khol ke dekh sakta hai
Client bundle mein koi bhi secret → sabke saamne
```

`VITE_` prefix secrets ko browser tak pohncha sakta hai (agar tumne khud use kiya). **Real sensitive secrets (database passwords, admin keys, payment secrets) frontend mein kabhi nahi rakhte** — who backend mein rehna chahiye, jahan user access nahi kar sakta.

**Ye samajhna production thinking hai:**

| Cheez | Kahan rakho |
|-------|------------|
| Public URL (API endpoint, public keys) | Frontend `.env` mein `VITE_` ke saath ✅ |
| Private secrets (DB password, admin keys) | **Kabhi frontend nahi** — backend/secret manager mein 🔒 |

**Post-7.5 note:** Humne abhi tak React frontend hi seekha hai. Production mein pure frontend ke sath usually koi backend/service hoti hai jo sensitive secrets handle karti hai. TrackIt capstone mein hum apna env `VITE_` se hi rakhenge (public URL — quote API), koi private secret nahi.

## Safe Rendering — Type Safety Se Bhi Madad

Security ka ek aur layer — **TypeScript type safety**. Jab tum API response ko type karte ho, toh tum accident mein galat data render nahi karoge.

```ts
// src/types/quote.ts
export interface Quote {
  content: string;
  author: string;
}
```

```ts
// src/hooks/useQuote.ts
import { useFetch } from "../hooks/useFetch";

// T = Quote — TypeScript enforce karta hai ki shape sahi hai
const { data, isLoading, error } = useFetch<Quote>(
  "https://api.quotable.io/random"
);
```

**Isse XSS nahi rukta directly** (script HTML mein aa sakta hai chahe type sahi ho), lekin `dangerouslySetInnerHTML` ki galti use karne ke chances kam ho jaate hain — kyunki TypeScript batata hai ki kaunsa field string text hai vs HTML. **Defense in depth** — multiple layers, har layer ek kamzor kar deta hai attacker ko.

---

## What Security Is NOT

- ❌ Security ka matlab **sirf** `dangerouslySetInnerHTML` avoid karna nahi — yeh ek part hai
- ❌ Security ka matlab `VITE_` prefix laga dena aur khatam nahi — frontend mein private secrets rakhna **kabhi** theek nahi
- ❌ TypeScript type safety **XSS ka ilaaj nahi** — yeh accidental bugs rokta hai, deliberate attacks ke liye sanitization chahiye
- ❌ `DOMPurify` **hamesha** jaruri nahi — agar tum `{}` se text render kar rahe ho, React default escape kar raha hai, sanitization bekar hai

---

## What This Topic Taught Us

1. **React default escaping** — `{}` mein values render-safe hoti hain, XSS ka pehla bachaav
2. **`dangerouslySetInnerHTML`** — intentional bypass, sirf trusted/sanitized HTML ke liye
3. **Sanitization** — DOMPurify se raw user HTML safe banao
4. **Env vars** — secrets `.env` mein, `VITE_` prefix, `import.meta.env` se access
5. **Client reality** — frontend bundle sab dekh sakte hain, private secrets kisi bhi condition mein frontend mein nahi
6. **Defense in depth** — escaping + sanitization + type safety, multiple layers

---

## So Here's the Takeaway

Security ek attitude hai, koi feature nahi. React tumhara default bachaav karta hai (`{}` = escape, `.env` = secrets, hooks = clean). Tumhari job hai us bachaav ko **bypass karna mat**, aur jab bypass karna hi ho (rich HTML) toh pehle **sanitize** karna. Aur sabse badi baat — jo secret browser tak pohncha, woh ab secret nahi. Private secrets frontend mein kabhi nahi.

Agle topic mein **testing** — Vitest + React Testing Library. Ab jab app crash-proof (7.1) aur safe (7.2) hai, toh usse **verify** karna seekhenge — code change pe tests, taaki regressions na aayein.
