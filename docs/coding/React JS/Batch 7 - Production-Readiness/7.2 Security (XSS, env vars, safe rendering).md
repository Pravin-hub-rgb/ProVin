So here's the situation...

---

## Problem First — Trusting User Data

Imagine a comment section. A user writes a comment:

> **Normal user:** "This app is awesome! 👍"

> **Malicious user:** `<script>window.location = "https://evil-site.com"</script>`

Now if you render that comment directly on the page, what happens? The browser treats `<script>` as real JavaScript and **executes** it. The user's browser (and their private data) gets redirected to the evil site. This is called **XSS — Cross-Site Scripting**.

```
User comment: <script>steal cookies → evil site</script>
        │
        ▼
You render it directly
        │
        ▼
Browser executes the script
        │
        ▼
Attacker gets the user's data 😟
```

**First question — "But I'm just writing normal JavaScript, right?"** Yes, and that's exactly your defense. React does **HTML escaping** by default. Let's see how.

---

## React's Default Escaping — Your First Line of Defense

When you put a value inside JSX with `{}`, React **escapes** it. It converts HTML special characters into text so the browser doesn't interpret them as code.

```tsx
// src/components/Comment.tsx
function Comment({ text }: { text: string }) {
  return <p>{text}</p>;
}

// text = '<script>alert("hack")</script>'
```

React renders it as **TEXT**, not as a script.

```tsx
// src/components/Comment.tsx
function Comment({ text }: { text: string }) {
  return <p>{text}</p>;
}

// text = '<script>alert("hack")</script>'
// React renders it as TEXT, not as a script
```

React converts `<script>` into `&lt;script&gt;` — the browser sees it as text, the script doesn't execute. This is default behavior — **you don't have to do anything.** As soon as you put a value in `{}` in JSX, React makes it render-safe.

**That's the reason React apps are (reasonably) safe from XSS attacks by default** — as long as you don't bypass that safety.

---

## Problem — Bypassing with dangerouslySetInnerHTML

React has a prop called `dangerouslySetInnerHTML`. The name says it all — **dangerously**. It bypasses React's built-in escaping and dumps raw HTML directly into the DOM.

```tsx
// ⚠️ DANGEROUS — renders HTML as-is
function RichContent({ html }: { html: string }) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />;
}
```

**Why would anyone use it?** Real-world cases — HTML content from a CMS (blog post), output from a rich text editor, or some legacy format. In these cases the source might not be the user.

**The problem:** If that HTML is not under your control — if it's user-generated — then `dangerouslySetInnerHTML` will **execute** that script. You've torn down React's safety net.

```
User-uploaded HTML + dangerouslySetInnerHTML
        │
        ▼
React escaping BYPASSED
        │
        ▼
Raw HTML into DOM → script executes → XSS
```

---

## Safe Alternative — Sanitization with DOMPurify

If you must render raw HTML, **sanitize** it first — strip out `<script>` tags, event handlers (`onclick=`), and dangerous attributes. The industry-standard library for this is **DOMPurify**.

```bash
bun add dompurify
```

```tsx
// src/components/RichContent.tsx
import DOMPurify from "dompurify";

function RichContent({ html }: { html: string }) {
  const safeHtml = DOMPurify.sanitize(html);
  return <div dangerouslySetInnerHTML={{ __html: safeHtml }} />;
}
```

DOMPurify takes HTML, strips scripts, event handlers, `javascript:` URLs, and returns safe HTML. Then you pass that safe HTML into `dangerouslySetInnerHTML`.

```
Raw HTML ──→ DOMPurify.sanitize ──→ Safe HTML ──→ render
   │                                  │
<script>...</script>                  script tags removed ✅
onclick="..."                          event handlers removed ✅
```

**Rules of thumb:**

| Scenario | What to do |
|----------|----------|
| User text rendered with `{}` | Nothing — React escapes by default ✅ |
| Raw HTML from a trusted source | `dangerouslySetInnerHTML` is fine (your own CMS) |
| Raw HTML from users | **Sanitize with DOMPurify** — always |

**Golden rule:** `dangerouslySetInnerHTML` = last resort. Trust the default escaping, and if you must bypass it, sanitize first.

## Env Vars — The Right Way to Handle Secrets

Now a different security problem — **secrets**. Your app needs an API key (TanStack Query, auth, some service). Where do you put it?

**Wrong way — hardcoded:**

```ts
// ⚠️ DANGEROUS — API key in source code
const API_KEY = "sk_live_ABC123secretSecret";
```

That gets committed, shows up on GitHub, anyone can access it. **Never.**

**Right way — `.env` file + Vite's `import.meta.env`:**

In React/Vite apps, you create a `.env` file and keep secrets with the `VITE_` prefix:

```
# .env
VITE_QUOTE_API_URL=https://api.quotable.io/random
```

```
# .env.local
# Local-only secrets — add to .gitignore
VITE_PRIVATE_KEY=local_dev_secret
```

You access env vars in code like this:

```ts
// src/hooks/useQuote.ts
const API_URL = import.meta.env.VITE_QUOTE_API_URL;
```

**Why `VITE_` prefix?** Vite only **exposes** vars that start with `VITE_` to the client bundle. This is intentional safety — whatever is in your `.env`, only `VITE_`-prefixed ones reach the browser.

> **"We'll explore this in detail in the next topic"** — the lifetime of `import.meta.env` and production build (7.5) will cover how env vars get injected into the bundle at build time. For now, just understand the concept: secrets live in `.env`, code accesses them via `import.meta.env`.

---

## Critical — Secrets Never Reach the Client

One extremely important fact — **React is frontend, and all its code runs in the browser.** Browser means anyone can look.

```
Never forget:
Code bundle → browser → anyone can open DevTools and see it
Any secret in client bundle → visible to everyone
```

`VITE_` prefix sends secrets to the browser (if you used it yourself). **Real sensitive secrets (database passwords, admin keys, payment secrets) never live in the frontend** — they belong on the backend, where the user can't access them.

**This is production thinking:**

| Thing | Where to keep it |
|-------|------------|
| Public URL (API endpoint, public keys) | Frontend `.env` with `VITE_` ✅ |
| Private secrets (DB password, admin keys) | **Never frontend** — backend/secret manager 🔒 |

**Post-7.5 note:** We've only learned React frontend so far. In production, a frontend usually comes with a backend or service that handles sensitive secrets. In the TrackIt capstone, we'll keep our env with `VITE_` (just a public URL — the quote API), no private secrets.

## Safe Rendering — Type Safety Helps Too

Another layer of security — **TypeScript type safety**. When you type your API responses, you don't accidentally render garbage data.

```ts
// src/types/quote.ts
export interface Quote {
  content: string;
  author: string;
}
```

```ts
// src/hooks/useQuote.ts
import { useFetch } from "../hooks/useFetch";

// T = Quote — TypeScript enforces that the shape is correct
const { data, isLoading, error } = useFetch<Quote>(
  "https://api.quotable.io/random"
);
```

**This doesn't stop XSS directly** (a `<script>` can come through even if the type is correct), but it prevents you from accidentally using `dangerouslySetInnerHTML` — TypeScript tells you which field is plain text versus HTML. **Defense in depth** — multiple layers, each making it a little harder for an attacker.

---

## What Security Is NOT

- ❌ Security isn't just **avoiding** `dangerouslySetInnerHTML` — that's only part of it
- ❌ Security isn't slapping `VITE_` prefix on everything — putting private secrets in the frontend is **never** OK
- ❌ TypeScript type safety is **not** a fix for XSS — it prevents accidental bugs, sanitization is needed for deliberate attacks
- ❌ `DOMPurify` isn't **always** needed — if you're rendering text with `{}`, React escapes by default, sanitization is useless

---

## What This Topic Taught Us

1. **React default escaping** — values in `{}` are render-safe, the first line of XSS defense
2. **`dangerouslySetInnerHTML`** — intentional bypass, only for trusted or sanitized HTML
3. **Sanitization** — DOMPurify turns raw user HTML into safe HTML
4. **Env vars** — secrets in `.env`, `VITE_` prefix, accessed via `import.meta.env`
5. **Client reality** — frontend bundle is visible to everyone, private secrets never in frontend
6. **Defense in depth** — escaping + sanitization + type safety, multiple layers

---

## So Here's the Takeaway

Security is an attitude, not a feature. React is your default guard (`{}` = escape, `.env` = secrets, hooks = clean). Your job is to **not bypass** that guard, and when you must bypass it (rich HTML), **sanitize first**. And the biggest point — whatever secret reaches the browser, is no longer a secret. Private secrets never go in the frontend.

## In Your Own Words

1. If you render `<script>alert(1)</script>` inside `{}` in JSX, what happens?

<details>
<summary>Show Answer</summary>

**Sample Answer:** React escapes it — it converts `<script>` into `&lt;script&gt;`, rendering it as plain text. The browser sees text, not an actual HTML tag. The script doesn't execute. This is React's default XSS protection — as long as you don't bypass it with `dangerouslySetInnerHTML`, values in `{}` stay render-safe.

</details>

2. When should you use `dangerouslySetInnerHTML`, and what must you do before using it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Only when you actually need to render raw HTML (CMS content, rich text) and React's default escaping won't work. But before using it, sanitize — use DOMPurify to strip `<script>` tags, event handlers (`onclick=`), and `javascript:` URLs. `dangerouslySetInnerHTML` bypasses React's safety net, so it's only safe for trusted or sanitized HTML. Never put unsanitized user-uploaded HTML in it.

</details>

3. What does `VITE_` prefix mean? Without the prefix, does the env var reach the client bundle?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `VITE_` prefix means Vite will **expose** that variable to the client bundle. Only vars starting with `VITE_` reach the browser (via `import.meta.env.VITE_...`). Vars without the prefix can exist in `.env`, but won't reach the client. This is intentional safety — keep anything in `.env`, only the `VITE_`-prefixed ones are visible to users.

</details>

4. "Never keep private secrets in the frontend" — why? What kind of secrets are we talking about?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because frontend code runs in the browser and anyone can look — via DevTools or bundled JS source. If you put a database password or admin API key in the client, any user can extract it. React only exposes *public* values through `VITE_` (public API URLs, public keys). Private secrets (DB passwords, payment/admin keys) stay in the backend or secret manager — outside the user's reach. A pure frontend app simply cannot have such secrets.

</details>

5. Why doesn't TypeScript type safety stop XSS, and why is it still helpful?

<details>
<summary>Show Answer</summary>

**Sample Answer:** If a `<script>` string comes through, TypeScript will still render it — the type system doesn't prevent attacks, it enforces data shapes. But type safety is still helpful as "defense in depth": correct types (`string` vs `HTML`) reduce accidental `dangerouslySetInnerHTML` mistakes, and the API shape stays consistent. Security needs multiple layers — React escaping + sanitization + type safety — each layer makes it harder for the attacker, no single layer is 100% guaranteed.

</details>
