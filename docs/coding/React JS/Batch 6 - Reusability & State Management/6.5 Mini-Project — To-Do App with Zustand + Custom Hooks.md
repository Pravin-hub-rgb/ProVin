## Step 1 — Theme Store (Context → Zustand)

Replace the old ThemeContext with a simple Zustand store:

```ts
// stores/themeStore.ts
import { create } from "zustand";
import { persist } from "zustand/middleware";

type Theme = "light" | "dark";

interface ThemeStore {
  theme: Theme;
  toggleTheme: () => void;
}

export const useThemeStore = create<ThemeStore>()(
  persist(
    (set) => ({
      theme: "light",
      toggleTheme: () =>
        set((state) => ({
          theme: state.theme === "light" ? "dark" : "light",
        })),
    }),
    { name: "todo-theme" }
  )
);
```

**Compare with the old ThemeContext:**

| Aspect | Context API (~45 lines) | Zustand (~15 lines) |
|--------|------------------------|--------------------|
| **createContext** | Required | No |
| **Provider component** | Required | No |
| **useMemo for value** | Required (else re-renders) | No (selective subscription) |
| **useCallback** | Optional (else re-renders) | No (built-in stable refs) |
| **Custom hook guard** | Required (`!ctx` throw) | No (store always exists) |
| **Persistence** | Manual (useEffect + localStorage) | Built-in (persist middleware) |

## Step 2 — Tasks Store (State + Actions)

The old App.tsx had tasks state, event handlers, and computed values all together. Now create a separate tasks store:

```ts
// stores/tasksStore.ts
import { create } from "zustand";
import { persist } from "zustand/middleware";
import type { Task, FilterStatus } from "../types";

interface TasksStore {
  tasks: Task[];
  filter: FilterStatus;
  addTask: (text: string, category: string) => void;
  toggleTask: (id: number) => void;
  deleteTask: (id: number) => void;
  setFilter: (filter: FilterStatus) => void;
}

export const useTasksStore = create<TasksStore>()(
  persist(
    (set) => ({
      tasks: [],
      filter: "all",

      addTask: (text, category) =>
        set((state) => ({
          tasks: [
            ...state.tasks,
            { id: Date.now(), text, completed: false, category },
          ],
        })),

      toggleTask: (id) =>
        set((state) => ({
          tasks: state.tasks.map((t) =>
            t.id === id ? { ...t, completed: !t.completed } : t
          ),
        })),

      deleteTask: (id) =>
        set((state) => ({
          tasks: state.tasks.filter((t) => t.id !== id),
        })),

      setFilter: (filter) => set({ filter }),
    }),
    { name: "todo-tasks" }
  )
);
```

**Notice:** With `persist` middleware, tasks are automatically saved to localStorage. **Tasks persist even after page refresh** — no `useEffect`, no `JSON.parse` needed.

## Step 3 — Categories with useFetch

The old categories fetch had `useEffect` + ignore pattern + manual state. Now we will use `useFetch<string[]>`:

```ts
// hooks/useFetch.ts — same hook from 6.2
import { useState, useEffect } from "react";

export function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    let ignore = false;

    async function fetchData() {
      setIsLoading(true);
      setError(null);
      try {
        const res = await fetch(url);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const json = await res.json();
        const categories = json.categories.map((c: any) => c.strCategory).slice(0, 5);
        if (!ignore) setData(categories as T);
      } catch (err) {
        if (!ignore) {
          setError(err instanceof Error ? err.message : "Something went wrong");
        }
      } finally {
        if (!ignore) setIsLoading(false);
      }
    }

    fetchData();
    return () => { ignore = true; };
  }, [url]);

  return { data, isLoading, error };
}
```

Now update the components — use the Zustand store directly instead of Context:

### ThemeToggle — Before vs After

```tsx
// Reference: old ThemeToggle.tsx (Context API) — compare only, do not type
import { useTheme } from "../context/ThemeContext";
function ThemeToggle() {
  const { theme, toggleTheme } = useTheme();

    </button>
  );
}

// New ThemeToggle.tsx (Zustand) — write this in src/components/ThemeToggle.tsx:
import { useThemeStore } from "../stores/themeStore";
function ThemeToggle() {
  const theme = useThemeStore((s) => s.theme);
  const toggleTheme = useThemeStore((s) => s.toggleTheme);
  return (
    <button onClick={toggleTheme}>
      {theme === "light" ? "🌙 Dark" : "☀️ Light"}
    </button>
  );
}
```

The difference? The Context version's `useTheme()` takes the entire object — if another property is added to the context value, the component re-renders. The Zustand version does selective subscription.

### TaskInput — Simpler, Same Pattern

Create a new file `src/components/TaskInput.tsx` (refactor the old one):

```tsx
// src/components/TaskInput.tsx
import { useRef, useState, useEffect } from "react";
import { useTasksStore } from "../stores/tasksStore";

function TaskInput() {
  const [text, setText] = useState("");
  const inputRef = useRef<HTMLInputElement>(null);
  const addTask = useTasksStore((s) => s.addTask);

  useEffect(() => {
    inputRef.current?.focus();
  }, []);

  const handleAdd = () => {
    if (text.trim()) {
      addTask(text.trim(), "General");
      setText("");
      inputRef.current?.focus();
    }
  };

  return (
    <div>
      <input ref={inputRef} value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleAdd}>Add</button>
    </div>
  );
}
```

`addTask` now comes from the store, not props. TaskInput no longer needs an `onAdd` prop.

### App.tsx — Dramatically Cleaner

The old App.tsx was ~80 lines — state management, event handlers, computed values, fetch logic, JSX all together. The new App.tsx (replace `src/App.tsx`):

```tsx
// src/App.tsx
import { useTasksStore } from "./stores/tasksStore";
import { useThemeStore } from "./stores/themeStore";
import { useFetch } from "./hooks/useFetch";
import TaskInput from "./components/TaskInput";
import TaskItem from "./components/TaskItem";
import FilterBar from "./components/FilterBar";
import TaskStats from "./components/TaskStats";
import ThemeToggle from "./components/ThemeToggle";

function App() {
  const theme = useThemeStore((s) => s.theme);
  const { tasks, filter, toggleTask, deleteTask, setFilter } = useTasksStore();
  const { data: categories, isLoading, error } = useFetch<string[]>(
    "https://www.themealdb.com/api/json/v1/1/categories.php"
  );

  const filteredTasks = tasks.filter((t) => {
    if (filter === "active") return !t.completed;
    if (filter === "completed") return t.completed;
    return true;
  });

  const completedCount = tasks.filter((t) => t.completed).length;
  const remainingCount = tasks.length - completedCount;

  return (
    <div className={theme === "dark" ? "dark" : "light"}>
      <div>
        <h1>📋 To-Do App v3</h1>
        <ThemeToggle />
      </div>

      {isLoading && <p>⏳ Loading categories...</p>}
      {error && <p style={{ color: "red" }}>❌ {error}</p>}
      {categories && (
        <p style={{ fontSize: "13px", color: "#888" }}>
          Categories: {categories.join(", ")}
        </p>
      )}

      <TaskInput />
      <FilterBar currentFilter={filter} onFilterChange={setFilter} />

      <div>
        {filteredTasks.map((task) => (
          <TaskItem key={task.id} task={task} onToggle={toggleTask} onDelete={deleteTask} />
        ))}
        {filteredTasks.length === 0 && <p>No tasks to show.</p>}
      </div>

      <TaskStats total={tasks.length} completed={completedCount} remaining={remainingCount} />
    </div>
  );
}

export default App;
```

**What is no longer visible:**

| Missing From New App.tsx | Where It Went |
|------------------------|------------|
| `useState` for tasks | Into Zustand store |
| `useState` for theme | Into Zustand store |
| `useState` for categories | Into `useFetch` hook |
| `useEffect` for categories fetch | Into `useFetch` hook |
| `handleAdd/toggle/delete` functions | Into Zustand store actions |
| `ThemeProvider` wrapper | No longer needed — Zustand has no provider |
| `localStorage.getItem` for tasks | Zustand persist middleware |

## Step 5 — New Addition: Category Select

Now that categories come from the API, add a dropdown in TaskInput so the user can select a category. Update the same `src/components/TaskInput.tsx` file:

```tsx
// src/components/TaskInput.tsx
function TaskInput() {
  const [text, setText] = useState("");
  const [selectedCategory, setSelectedCategory] = useState("General");
  const inputRef = useRef<HTMLInputElement>(null);
  const addTask = useTasksStore((s) => s.addTask);
  const { data: categories } = useFetch<string[]>(
    "https://www.themealdb.com/api/json/v1/1/categories.php"
  );

  useEffect(() => { inputRef.current?.focus(); }, []);

  const handleAdd = () => {
    if (text.trim()) {
      addTask(text.trim(), selectedCategory);
      setText("");
      inputRef.current?.focus();
    }
  };

  return (
    <div>
      <input ref={inputRef} value={text} onChange={e => setText(e.target.value)} />
      <select value={selectedCategory} onChange={e => setSelectedCategory(e.target.value)}>
        <option value="General">General</option>
        {categories?.map(cat => (
          <option key={cat} value={cat}>{cat}</option>
        ))}
      </select>
      <button onClick={handleAdd}>Add</button>
    </div>
  );
}
```

Notice? TaskInput fetches its own categories — no need to pass categories as a prop from App. `useFetch` brings categories in one line. This is the power of custom hooks — **the component that needs the data is the one that fetches it.**

## Before vs After — Migration Summary

**Architecture change:**

```
Before (Batch 2):
App.tsx (state + handlers + fetch + JSX)
  ├── ThemeContext (provider wraps App)
  ├── TaskInput (onAdd prop)
  ├── TaskItem (onToggle prop, onDelete prop)
  ├── FilterBar (filter prop, onFilterChange prop)
  └── TaskStats (total/completed/remaining props)

After (Batch 6):
App.tsx (JSX only — lean)
  ├── themeStore (independent Zustand)
  ├── tasksStore (independent Zustand)
  ├── useFetch hook (categories)
  ├── TaskInput (no props — self-contained)
  ├── TaskItem (onToggle, onDelete — from store)
  ├── FilterBar (filter, onFilterChange)
  └── TaskStats (total/completed/remaining)
```

**Key changes:**
- ThemeContext → `useThemeStore` (provider-free, auto-persist)
- App.tsx state → `useTasksStore` (actions + persist)
- useEffect fetch → `useFetch<string[]>` (loading + error built-in)
- Manual localStorage → `persist` middleware (zero boilerplate)

## So Here's the Takeaway

The To-Do App v2 → v3 migration showed:

1. **Zustand removed ~45 lines of Context boilerplate** — no provider, no `useMemo`, no guard
2. **`useFetch` removed ~15 lines of useEffect** — loading + error + cleanup all automatic
3. **`persist` middleware removed ~10 lines of localStorage** — data safe across refreshes
4. **Components became self-contained** — TaskInput fetches its own data
5. **App.tsx is just JSX layout** — state management lives in stores, fetching in hooks

Look at the journey so far: In Batch 2, we learned Context API (the manual approach). In Batch 6, we solved the same problem with Zustand (the better approach). This is the industry pattern — **"learn the manual way first, then the better tool."**

## In Your Own Words

1. In Batch 2's To-Do App v2, the ThemeContext had a custom hook guard (`if (!ctx) throw`). Why was this needed? Why is it not needed in Zustand?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The Context API guard pattern was needed because a component could call `useTheme()` **outside** the `ThemeProvider`. If a component uses `useTheme()` but is rendered outside the `ThemeProvider`, `useContext` returns `undefined` and you get an error when accessing properties. The guard ensures a clear error message. In Zustand, the store is independent — there is no provider, no context tree. A component imports the store directly, regardless of where it renders. The store always exists, so no guard is needed.

</details>

2. What problem did the `persist` middleware in `useTasksStore` solve that existed in Batch 2's To-Do App v2?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In Batch 2's To-Do App v2, tasks were not saved to localStorage — all tasks reset on page refresh. If implemented manually, you would need `useState` lazy initializer + `localStorage.getItem` + `JSON.parse` (for loading) and `useEffect` + `localStorage.setItem` + `JSON.stringify` (for saving) — at least 10 lines. The `persist` middleware handled all of this in a single wrapper — automatic serialization, deserialization, and localStorage sync. Plus built-in error handling for corrupt data.

</details>

3. In the new App.tsx, categories are not passed as a prop — TaskInput calls `useFetch` itself. How is this possible, and what is the benefit?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Any component that calls `useFetch` manages its own fetch. TaskInput fetches categories directly via `useFetch` — App.tsx does not need to pass categories as a prop. The benefit: (a) **self-contained components** — the component that needs the data fetches it itself, no need to ask the parent; (b) **reduces prop drilling** — categories don't need to be passed through multiple components; (c) **reusability** — TaskInput can be used in any app and it will fetch its own data. However, if multiple components need the same data, storing it in a store is better.

</details>

4. The new App.tsx is ~40 lines vs ~80 lines in Batch 2. Which 40 lines were eliminated?

<details>
<summary>Show Answer</summary>

**Sample Answer:** (1) `useState` declarations for tasks + filter (3 lines), (2) event handlers — handleAdd, handleToggle, handleDelete (~15 lines), (3) useEffect for categories fetch + ignore pattern (~10 lines), (4) ThemeContext import + `useTheme` call (2 lines), (5) styles object (~8 lines), (6) Provider wrapper in export (~3 lines). Total ~41 lines. All of this moved to Zustand store actions, the `useFetch` hook, and `themeStore`. App.tsx now only handles JSX layout and computed values.

</details>

5. When would this approach fail? When would Context be better than Zustand?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Zustand fails when: (a) the app is very small (2-3 components, 1 global value) — the extra dependency is not worth it; (b) the team is comfortable with React Context and there are no performance issues; (c) there are library restrictions (company policy may not allow extra dependencies). Context is better when: there are only 1-2 values that change infrequently (theme, locale), the app is small, and provider nesting is not a problem. Decision criteria: if you have "provider hell" + "unnecessary re-renders" + "boilerplate" issues, go with Zustand — otherwise Context is also fine.

</details>
