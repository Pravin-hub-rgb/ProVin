## Recipe Finder — Batch 2 Code Recap

This was our old code (from Batch 2.2). The entire component, manually managing loading/error/data states:

```tsx
// Reference: Batch 2's RecipeFinder.tsx — do NOT type this, just read it (it is reusable)
import { useState, useEffect } from "react";

interface Recipe {
  idMeal: string;
  strMeal: string;
  strMealThumb: string;
  strCategory: string;
  strArea: string;
}

interface SearchResponse {
  meals: Recipe[] | null;
}

function RecipeFinder() {
  const [searchInput, setSearchInput] = useState("");
  const [recipes, setRecipes] = useState<Recipe[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const fetchDefault = async () => {
      setIsLoading(true);
      const res = await fetch(
        "https://www.themealdb.com/api/json/v1/1/search.php?s=chicken"
      );
      const data: SearchResponse = await res.json();
      setRecipes(data.meals ?? []);
      setIsLoading(false);
    };
    fetchDefault();
  }, []);

  const handleSearch = async () => {
    if (!searchInput.trim()) return;
    setIsLoading(true);
    setError(null);
    try {
      const res = await fetch(
        `https://www.themealdb.com/api/json/v1/1/search.php?s=${searchInput.trim()}`
      );
      const data: SearchResponse = await res.json();
      setRecipes(data.meals ?? []);
    } catch (err) {
      setError(err instanceof Error ? err.message : "Something went wrong");
      setRecipes([]);
    } finally {
      setIsLoading(false);
    }
  };

  return (
    <div>
      <h1>🍳 Recipe Finder</h1>
      <input value={searchInput} onChange={e => setSearchInput(e.target.value)} />
      <button onClick={handleSearch} disabled={isLoading}>
        {isLoading ? "Searching..." : "Search"}
      </button>
      {isLoading && <p>⏳ Loading...</p>}
      {error && <p style={{ color: "red" }}>❌ {error}</p>}
      {!isLoading && recipes.length === 0 ? (
        <p>No recipes found.</p>
      ) : (
        <div className="grid">
          {recipes.map(recipe => (
            <RecipeCard key={recipe.idMeal} recipe={recipe} />
          ))}
        </div>
      )}
    </div>
  );
}
```

**Identify the problems:**

| Problem | Line Count |
|---------|------------|
| `useState` triplets | 3 lines |
| `handleSearch` + fetch | ~20 lines |
| `useEffect` + fetch | ~12 lines |
| Manual loading/error toggle | 6+ places |

Total: ~50 lines just for state + fetch logic. The actual UI is only ~25 lines.

## Refactor Step 1 — Replace with useFetch<Recipe[]>

First, remove the manual fetch logic. Use `useFetch<Recipe[]>` — the hook we built in 6.2. Create a new file `RecipeFinder.tsx` in `src/components/` and import the hook:

```tsx
// src/components/RecipeFinder.tsx
import { useState } from "react";
import { useFetch } from "../hooks/useFetch";

function RecipeFinder() {
  const [searchInput, setSearchInput] = useState("chicken");
  const { data: recipes, isLoading, error } = useFetch<Recipe[]>(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${searchInput}`
  );
  // ...
}
```

**Let's see what changed:**

| Old | New |
|--------|------|
| 3 `useState` calls | 0 — all hidden in the hook |
| 1 `useEffect` with fetch function | 0 — the hook handles it |
| `handleSearch` with try/catch/finally | 0 — the hook handles it |
| Manual loading toggle | Auto — hook returns `isLoading` |
| Manual error toggle | Auto — hook returns `error` |
| `SearchResponse` interface | Not needed — hook is generic |
| `??` null check | Not needed — `T | null` is handled by the hook |

But there is a problem — `searchInput` is still managed with `useState` and the search button needs to trigger a change. What to do?

**How does the search trigger work:** `useFetch` fetches inside its effect, and the effect re-runs when the URL changes. So if we change `searchInput`, the URL changes, and the effect re-runs. But we want it to change on button click, not on every character.

Solution — **keep a separate query state** that only updates on button click (in the same `src/components/RecipeFinder.tsx`):

```tsx
// src/components/RecipeFinder.tsx
import { useState } from "react";
import { useFetch } from "../hooks/useFetch";

function RecipeFinder() {
  const [searchInput, setSearchInput] = useState("chicken");
  const [query, setQuery] = useState("chicken");

  const { data: recipes, isLoading, error } = useFetch<Recipe[]>(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`
  );

  const handleSearch = () => {
    if (!searchInput.trim()) return;
    setQuery(searchInput.trim());
  };

  return (
    <div>
      <input value={searchInput} onChange={e => setSearchInput(e.target.value)} />
      <button onClick={handleSearch}>Search</button>
      {/* ... */}
    </div>
  );
}
```

**Flow:** User types → `searchInput` updates (but no fetch yet) → User clicks button → `query` updates → URL changes → `useFetch`'s effect re-runs → fetch happens → UI updates.

## Refactor Step 2 — Favorites Feature with useLocalStorage

Add a new feature — **Favorites**. Users can mark a recipe as favorite, and it will be saved to localStorage.

If we did not use `useLocalStorage`, here is what it would look like (for reference, do not type this):

```tsx
// Reference: manual localStorage approach — don't write this boilerplate
const [favorites, setFavorites] = useState<Recipe[]>(() => {
  const saved = localStorage.getItem("favorites");
  return saved ? JSON.parse(saved) : [];
});

useEffect(() => {
  localStorage.setItem("favorites", JSON.stringify(favorites));
}, [favorites]);
```

— Same boilerplate, every time.

Now with `useLocalStorage` (add the import in the same `src/components/RecipeFinder.tsx`):

```tsx
// src/components/RecipeFinder.tsx
import { useLocalStorage } from "../hooks/useLocalStorage";

function RecipeFinder() {
  const [favorites, setFavorites] = useLocalStorage<Recipe[]>("favorites", []);
  // ...
}
```

One line. No `useEffect`, no `JSON.parse`, no `localStorage.getItem`.

## Complete Code (Refactored Recipe Finder)

Here is the entire file — write all of this in `src/components/RecipeFinder.tsx` (create `RecipeCard.tsx` separately first):

```tsx
// src/components/RecipeFinder.tsx
import { useState } from "react";
import { useFetch } from "../hooks/useFetch";
import { useLocalStorage } from "../hooks/useLocalStorage";
import { RecipeCard } from "./RecipeCard";

interface Recipe {
  idMeal: string;
  strMeal: string;
  strMealThumb: string;
  strCategory: string;
  strArea: string;
}

function RecipeFinder() {
  const [searchInput, setSearchInput] = useState("chicken");
  const [query, setQuery] = useState("chicken");
  const [favorites, setFavorites] = useLocalStorage<Recipe[]>("favorites", []);

  const { data: recipes, isLoading, error } = useFetch<Recipe[]>(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`
  );

  function toggleFavorite(recipe: Recipe) {
    const exists = favorites.some(fav => fav.idMeal === recipe.idMeal);
    if (exists) {
      setFavorites(favorites.filter(fav => fav.idMeal !== recipe.idMeal));
    } else {
      setFavorites([...favorites, recipe]);
    }
  }

  return (
    <div>
      <h1>🍳 Recipe Finder</h1>

      <input
        value={searchInput}
        onChange={e => setSearchInput(e.target.value)}
        placeholder="Search recipes..."
      />
      <button onClick={() => setQuery(searchInput.trim())} disabled={isLoading}>
        {isLoading ? "Searching..." : "Search"}
      </button>

      {isLoading && <p>⏳ Loading...</p>}
      {error && <p style={{ color: "red" }}>❌ {error}</p>}

      {!isLoading && (recipes?.length === 0 || !recipes) ? (
        <p>No recipes found.</p>
      ) : (
        <div className="grid">
          {recipes.map(recipe => (
            <RecipeCard
              key={recipe.idMeal}
              recipe={recipe}
              isFavorite={favorites.some(fav => fav.idMeal === recipe.idMeal)}
              onToggleFavorite={toggleFavorite}
            />
          ))}
        </div>
      )}
    </div>
  );
}
```

Compare it with the old code. **Custom hooks removed ~35 lines of boilerplate.** A new feature (favorites) was added, and the code is still shorter. This is the power of custom hooks — less code, more features, cleaner structure.

## What Batch 6.3 Taught Us

1. **Custom hooks eliminate duplicate patterns** — write once, use everywhere
2. **`useFetch<T>` removed ~25 lines of manual fetch logic**
3. **`useLocalStorage<T>` removed ~8 lines + made adding new features easy**
4. **Components focus on *what*, hooks handle *how***
5. **TypeScript generics ensure types stay consistent**

## In Your Own Words

1. In the old Recipe Finder, `handleSearch` had try/catch/finally. Why is it missing in the refactored version?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because that logic is now hidden inside the `useFetch` hook. The hook internally handles try/catch/finally, automatically manages loading and error states, and returns clean data to the component. The component now just destructures `{ data, isLoading, error }` — the implementation detail is hidden inside the hook. This is the benefit of abstraction — the component's code is smaller and readable.

</details>

2. In the refactored version, why are `searchInput` and `query` two separate states? Why can't a single state work?

<details>
<summary>Show Answer</summary>

**Sample Answer:** With a single state, every keystroke would trigger a fetch (because `useFetch` re-fetches when the URL changes). This is wasteful — the user doesn't need an API call on every character typed. So `searchInput` is for the user's typing (local state, no side effects), and `query` only updates when the user clicks the button. This pattern is called "controlled trigger" — fetch is triggered only when the user explicitly wants it (button click, Enter key), not on every keystroke.

</details>

3. What problem does `useLocalStorage<Recipe[]>("favorites", [])` solve that was missing from the old code?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The old Recipe Finder didn't have a favorites feature at all. If implemented manually, it would require `useState` + lazy initializer + `useEffect` + `localStorage.getItem` + `JSON.parse` + `JSON.stringify` — at minimum 8-10 lines. `useLocalStorage` handles everything in one line. The state persists even after browser refresh, with no boilerplate. Whenever `setFavorites` is called, localStorage updates automatically — no extra effect needed.

</details>

4. Why is the `SearchResponse` interface not visible in the refactored code? Why was it needed in the old code?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The `SearchResponse` interface defined the full shape of the API response (`{ meals: Recipe[] | null }`). In the old code, we manually fetched and parsed the response, so the interface was necessary. `useFetch` is generic — we call `useFetch<Recipe[]>`, and the hook internally casts the JSON as `T`. The hook directly casts the JSON response to the `T` type. So the component doesn't need to know about `SearchResponse` at all — the hook handles that abstraction.

</details>

5. Even after using custom hooks, the component still handles `loading` and `error` states. So what is the actual difference?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `isLoading` and `error` now come from the hook, the component doesn't manage them itself. The difference is: in the old code, the component manually called `setIsLoading(true/false)` everywhere, managed try/catch/finally itself. Now the component only *consumes* the values, it doesn't *manage* them. If you need to change the implementation (like adding a delay to loading, or changing error format), just modify the `useFetch` hook — all components update automatically. This is **separation of concerns** — the component is responsible for UI, the hook for state management.

</details>
