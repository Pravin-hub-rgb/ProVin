## Where We Left Off

## useDocumentTitle — A Side-Effect-Only Hook

### The Problem

Every page in an app wants the browser tab to show its own title. Profile → "Vin's Profile". Settings → "Settings". Without a hook, each page writes the same effect:

```tsx
function SettingsPage() {
  useEffect(() => {
    document.title = "Settings";
  }, []);

  // ...
}
```

One `useEffect` per page — only the string changes. And there's a visible symptom when you forget a page: navigate from Settings to Home, the tab still says "Settings". Stale, because nothing on Home resets it. Every page needs the same effect, so every page needs the same fix — unless the effect lives in one place.

### The Hook

```ts
// src/hooks/useDocumentTitle.ts
import { useEffect } from "react";

export function useDocumentTitle(title: string) {
  useEffect(() => {
    document.title = title;
  }, [title]);
}
```

| Line | What it does |
|------|--------------|
| `title: string` | The title this page wants in the tab |
| `useEffect(..., [title])` | Re-run whenever the title changes — navigate to a new page, new string, effect fires |
| **Return?** | Nothing. This hook only performs a side effect |

That last row is the new idea: **custom hooks don't have to return anything.** `useToggle` handed back a value and a function; this one just *does its job* and gives nothing to the destructuring — there is no destructuring.

Usage, one line per page:

```tsx
// src/components/SettingsPage.tsx
import { useDocumentTitle } from "../hooks/useDocumentTitle";

export function SettingsPage() {
  useDocumentTitle("Settings");

  return <div>This is a settings page</div>;
}
```

```tsx
// src/components/ProfilePage.tsx
import { useDocumentTitle } from "../hooks/useDocumentTitle";

export function ProfilePage({ username }: { username: string }) {
  useDocumentTitle(`${username}'s Profile`);

  return <div>This is a profile page</div>;
}
```

No `useEffect` visible in either component. The component says *what* — "this page's title is Settings" — and the hook handles *how*. Give Home its own call too (`useDocumentTitle("Home")`), or the stale-title problem comes back the moment you navigate there.

### Common Mistake — Hook Inside a Nested Function

A natural first draft wraps the effect in a helper:

```ts
// ❌ Breaks the Rules of Hooks
export function useDocumentTitle() {
  function changeTitle(label: string) {
    useEffect(() => {
      document.title = label;
    }, []);
  }

  return [changeTitle];
}
```

It can even *appear* to work — if `changeTitle` happens to be called exactly once per render at the top level. But the `useEffect` now sits inside a nested function, which violates the **top-level rule** from 6.1. The linter flags it; on a refactor — an early return, a condition — the call order breaks for real, and React matches slots to the wrong hooks.

The fix is also the simpler design: take the title as the parameter, call the effect at the hook's own top level, return nothing. Exactly the code in The Hook section above.

Rule of thumb from 6.1, now with a body: *if you find yourself reaching for a hook inside a helper function, the helper is the wrong shape — move the parameters up to the hook itself.*

## usePrevious — The Hard One

### The Problem

A counter goes from 5 to 6. The component knows the current value — but React gives you no built-in way to ask *"what was this on the last render?"* Once the new value replaces the old one, the old one is gone.

Real uses: show "Before: 5" next to "Now: 6"; a stock ticker flashing green or red (up vs down needs the previous price); scroll-to-top when a search query changes; animating a number from the old value to the new one.

(Honest sizing: it's a niche hook — many teams barely use it. It's in the course because the *timing trick* it teaches shows up all over hook-land.)

So: where can the old value live so it survives from one render to the next? You've met both candidates — `useState` and `useRef`.

### Why Not useState — Two Failures

**Failure 1: the handler trick only works when you own the change.**

If the component itself changes the value, you can save the old one first:

```tsx
const [a, setA] = useState(1);
const [b, setB] = useState<number | null>(null);

function increment() {
  setB(a);      // save the current a...
  setA(a + 1);  // ...then change it
}
```

Both updates batch into a single re-render: Now: 2, Before: 1. Click again: Now: 3, Before: 2. Works perfectly — *for this one handler*.

But if the value arrives as a **prop**, the change happens in the parent:

```tsx
function Child({ value }: { value: number }) {
  // Now: {value}   Before: ???
}
```

Child has no handler, no setter — no "moment before the change" where it could call `setB`. By the time Child renders, the new value has already arrived and the old one is gone. And if the value can change from several places (two buttons, a timer, a reset), you'd have to remember `setB(a)` before *every* `setA` — miss once, wrong previous value forever.

**Failure 2: updating in an effect costs a render — and loses anyway.**

The "obvious" fix: a second state, updated after render:

```tsx
useEffect(() => {
  setPrev(value); // runs AFTER render — value is already the new one
}, [value]);
```

By the time the effect runs, the old value is gone — `setPrev` stores the *current* value, so `prev` always equals `current`, one render late, then overwritten. Plus every save triggers its own extra render: on a live stock feed, double renders forever, for pure bookkeeping.

(And writing the setter directly in the component body during render? That loops immediately: render → set → render → set...)

So `useState` either doesn't catch the old value, or catches it at the cost of renders the screen never needed.

### useRef — A Box That Doesn't Re-render

`useRef` gives you a box that:

- survives between renders
- you read and write through `.current`
- **changing `.current` does NOT cause a re-render**

That last property is the whole reason. Saving the previous value is bookkeeping — the screen never needs to repaint because of it.

But a ref doesn't update itself. Re-rendering doesn't touch what's inside the box. So *when* do we write the new value in?

### The Timing Trick

Here's the order React actually runs things when `value` goes 10 → 11:

```
1. Parent sends 11. Child's function runs top-to-bottom with value = 11.
   - The ref line runs: same box as before, still holding 10.
   - The effect line runs — but only REGISTERS its callback, doesn't execute it.
   - The return runs: reads ref.current → 10.        ← previous value, on screen
2. React puts that screen in the browser.
3. Only NOW does the effect callback execute: ref.current = 11.
```

The key fact: **`useEffect` does not run its callback when the line is reached during render.** That line only tells React — "remember this function, run it after the screen is committed." Register, not execute. So during the render, the box still holds the old value: you read it, you show it, and only after the screen is up does the effect overwrite it with the new value — ready for the next render.

Console proof you can run in two minutes:

```tsx
useEffect(() => {
  console.log("effect");
  prev.current = value;
}, [value]);

console.log("render");
```

Even though `effect` is written *above*, the console prints `render` first, then `effect`. Every time.

Division of labor:

| When | What happens |
|------|--------------|
| **During render** | Read `ref.current` — it still holds the old value. That's your previous value. |
| **After render** (effect) | Write the new value into the ref — ready for next time. |

And because writing `.current` doesn't re-render, the screen stays on the old value until the *next* change arrives — always exactly one step behind, which is precisely what "previous" means.

### The Hook

```ts
// src/hooks/usePrevious.ts
import { useRef, useEffect } from "react";

export function usePrevious<T>(value: T): T | undefined {
  const ref = useRef<T | undefined>(undefined);

  useEffect(() => {
    ref.current = value;
  }, [value]);

  return ref.current;
}
```

| Line | What it does |
|------|--------------|
| `<T>` | Generic type — works for number, string, object, anything (generics properly in 6.2) |
| `useRef<T \| undefined>(undefined)` | The box. Starts `undefined` — nothing exists yet on the very first render |
| `useEffect(..., [value])` | After each render, write the current value into the box |
| `return ref.current` | During *this* render, the box still holds the **previous** value |

Note what's **not** there: no array wrapper. Only one thing comes back, so there's nothing to destructure — `const prev = usePrevious(count)`, done.

Flow:

```
First render: value = 5
  ref.current = undefined  →  return undefined
  (after) effect: ref.current = 5

Second render: value = 6
  ref.current = 5          →  return 5   ← previous!
  (after) effect: ref.current = 6

Third render: value = 10
  ref.current = 6          →  return 6   ← previous!
  (after) effect: ref.current = 10
```

Usage:

```tsx
// src/components/Counter.tsx
import { useState } from "react";
import { usePrevious } from "../hooks/usePrevious";

export function Counter() {
  const [count, setCount] = useState(0);
  const prevCount = usePrevious(count);

  return (
    <div>
      <p>Now: {count}</p>
      <p>Before: {prevCount ?? "—"}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
    </div>
  );
}
```

First render: Before shows "—" — there is no previous yet, and that's correct. Every click: Now climbs, Before shows exactly what Now was one click ago.

## In Your Own Words

1. In `usePrevious`, the ref is updated *after* the render, but the hook returns *during* the render. How does that give you the previous value? What goes wrong if you use `useState` instead of `useRef`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The order is everything. During render, the function reads `ref.current` — the effect hasn't run yet for this value, so the box still holds the old one. That's the previous value, shown on screen. Only after React commits the screen does the effect write the new value into the ref, ready for next time. With `useState`, the effect would call a setter — which triggers an *extra* render, and worse, by the time the effect runs the old value is already gone, so it saves the *current* value: prev always equals current, one render late, then overwritten. Plus that extra render is pure bookkeeping the screen never needed. A ref updates silently with no re-render, which is why it's the right tool.

</details>

2. When a component renders, `useEffect` appears in the code *above* the return. Why doesn't it run at that point? What does that line actually do?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Reaching a `useEffect` line during render only *registers* the callback — it tells React "run this function after you've put the screen on the page." It does not execute the callback right there. So the full order is: function runs top-to-bottom (create refs, register effects, build the return), React shows the screen, *then* effects run. You can prove it with a `console.log("render")` above the return and one inside the effect: even if the effect is written first in the file, the console prints `render` then `effect`. This is exactly why `usePrevious` works — the render reads the ref while it still holds the old value, and the effect overwrites it only afterwards.

</details>

3. `useToggle` returns `[value, toggle]`, but `useDocumentTitle` returns nothing at all. Is a hook that returns nothing allowed, and when would you write one?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Yes — a custom hook is just a function that uses hooks; returning a value is optional. `useToggle` has state the component needs to read (the boolean) and an action it needs to call (the flip), so it returns both. `useDocumentTitle` only performs a side effect — setting `document.title` — so the component has nothing to read or call; the call itself *is* the usage: `useDocumentTitle("Settings")`. Side-effect-only hooks are common: anything whose whole job is "when this component is here, do that" (set title, subscribe to something, log a visit) returns nothing.

</details>
