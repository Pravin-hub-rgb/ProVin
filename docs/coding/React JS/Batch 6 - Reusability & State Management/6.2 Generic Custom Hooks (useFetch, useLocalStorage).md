## Where We Left Off

6.1 ended with four hooks — `useToggle`, `useDocumentTitle`, `usePrevious`, `useBoolean` — and one honest limitation: every one of them is **specific**. A boolean here, a string there.

The real world wants `useFetch` that works with *any* response type, and `useLocalStorage` that persists *any* data. Recipes, tasks, users, preferences — same hook, different shapes. That needs TypeScript generics, and that's this topic.

Same project as 6.1 (`custom-hooks-demo`): new hooks go in `src/hooks/`, the components that use them in `src/components/`.

## The Problem — One Hook, Many Shapes

Remember the five-components problem that opened 6.1? Five components, same fetch wiring, only the URL changes. A `useFetch` hook would fix that in one line per component...

...until you look at what comes back.

Your Recipes page fetches a list of meals. Your Tasks page fetches a list of tasks. A "fetch one task by id" call gets a single object, not even an array. Now try typing the hook. If `useFetch` is typed for recipes, TypeScript complains the moment a tasks component uses it. If you type it as `any`, you've thrown away every benefit TypeScript gave you. And writing a separate hook per data type is the duplication problem again — this time in the types, not the logic.

The logic is identical across all of those hooks. Only the type changes. That's the exact shape of problem generics solve, so before any hook code, one small idea.

---

## Generics — T Is a Label the Caller Hands In

Say you type a function that returns the first item of an array, for numbers:

```ts
function first(arr: number[]): number {
  return arr[0];
}
```

`first([1, 2, 3])` works. `first(["a", "b"])` is a type error — strings aren't numbers. So you'd write `firstString` with the same body, then one for booleans, and so on. Same logic, copied per type. The fix is a **generic**:

```ts
function first<T>(arr: T[]): T {
  return arr[0];
}

const num = first([1, 2, 3]); // T inferred as number
const str = first(["a", "b"]); // T inferred as string
```

`<T>` after the function name is a **type parameter** — a placeholder for a type, usually written `T`. Think of it like a function parameter, except it takes a *type* instead of a value. The caller decides what `T` is: pass numbers, `T` becomes `number`; pass strings, `T` becomes `string`. TypeScript can often infer it without you writing the angle brackets at all.

Now the hook version of the same idea. `useFetch` doesn't know what data it will bring back — one call is recipes, another is tasks. So the hook declares a placeholder, and each caller fills it in:

```ts
function useFetch<T>(url: string) { ... }

// in the Recipes page:
const { data } = useFetch<MealResponse>(url);   // T = MealResponse
// in the Tasks page:
const { data } = useFetch<Task[]>(url);         // T = Task[]
```

One hook, and each caller hands it a label saying what's inside. That's all generics do here.

And before the hook body exists, it's worth defining what comes *out*. The hook hands three things back: the data, a loading flag, an error message. That package gets its own type:

```ts
// src/hooks/useFetch.ts
type FetchState<T> = {
  data: T | null;        // T or null — before the fetch finishes, there's no data yet
  isLoading: boolean;
  error: string | null;
};
```

`FetchState<T>` is generic too — its `data` field is whatever `T` turns out to be. This type is optional (TypeScript could infer the return shape from the code), but writing it out first keeps `T` connected from the hook's input to its output. Define what you send back, then build the hook that sends it.

## Feel the Pain First — Plain fetch

Before the hook, one fetch by hand — so the hook's value is felt, not just claimed.

Create `src/components/RecipeList.tsx`:

```tsx
// src/components/RecipeList.tsx
import { useEffect } from "react";

export default function RecipeList() {
  useEffect(() => {
    const fetchData = async () => {
      const res = await fetch(
        "https://www.themealdb.com/api/json/v1/1/search.php?s=mushroom"
      );
      const result = await res.json();
      console.log(result);
    };
    fetchData();
  }, []);

  return <div>Recipes</div>;
}
```

Two things to notice. The effect callback itself can't be `async`, so the async work lives in a function defined *inside* it, called right away. And there's no state, no loading, no error yet — just the raw call.

Run it, open the browser console. You'll see an object with a field called `meals`, holding an array of recipes — each with fields like `strMeal`, `strMealThumb`, `strCategory`. (TheMealDB wraps the list in an object, it's not a plain array. And `idMeal` comes as text — `"52940"` with quotes — even though it looks like a number.)

Now hover over `result` in your editor. TypeScript says: `any`.

That's the pain. `result.mealz` — a typo — gets no underline, no warning, nothing until the app breaks at runtime. So: name the shape, then annotate.

```ts
// above the component
interface Meal {
  idMeal: string;
  strMeal: string;
  strMealThumb: string;
  strCategory: string;
}

type MealResponse = {
  meals: Meal[] | null;   // null — a search with no matches sends null, not []
};

// inside fetchData
const result: MealResponse = await res.json();
```

Only the four fields you'll actually use — an interface is a name for a shape, and twenty unused fields help nobody. Then the deliberate typo test: write `result.mealz`. Red underline. Fix it back.

But here's the catch that makes this exercise worth doing. Earlier, a learner wrote the outer field as `Meals` — capital M. TypeScript said **nothing**. You told it the response has a `Meals` field, and it trusts you. An annotation is a **promise, not a check** — TypeScript can't call the API and verify. At runtime, `result.Meals` would be `undefined`. Your types must match the real data exactly, which is exactly why that first `console.log` earned its place.

---

## Interface vs Type — The Quick Refresher

Both `interface Meal` and `type Meal = { ... }` did the same job above, and the mix-up is worth two minutes because it keeps resurfacing.

An **interface** and a **type alias** are both just names for a shape. For plain object shapes they behave almost identically — missing field, misspelled field, same red underline. You can annotate with either one: the colon-and-name after a variable (a *type annotation*) works no matter how the name was declared.

The differences that actually matter:

- A **type** can name things that aren't objects — most importantly a union ("one of several options"): `type Status = "loading" | "success" | "error"`, or `type MaybeMeal = Meal | null`. An interface can't *be* a union by itself (though a *field* inside an interface can have a union type — `meals: Meal[] | null` is fine).
- An **interface** can be declared twice and the fields merge, or build on another with `extends`. Two types can't share a name; they combine with `&` instead.

Interview-grade trivia, day-to-day noise. Rule of thumb: interface for object shapes, type when you need a union — or just pick one style and stay consistent.

## useFetch<T> — Build It

Pain felt, types named. Now the hook, one small piece at a time.

**Step 1 — the function line.** In `src/hooks/useFetch.ts`:

```ts
export function useFetch<T>(url: string) {
  // body next
}
```

`<T>` after the name (the generic), `url: string` (a normal parameter). That's the whole signature.

**Step 2 — the three states:**

```ts
import { useState } from "react";

export function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);
  // ...
  return { data, isLoading, error };
}
```

Inside the hook, `T` is just a stand-in for whatever the caller chooses — `useState<T | null>` means "this holds the real type, or null before it arrives." When RecipeList calls `useFetch<MealResponse>(...)`, that same `T` flows into `useState`, into `FetchState<T>`. The return is an object (three values — objects read better than arrays here), so the component pulls them out by name.

One fix that trips everyone: inside an *annotation*, `T` goes bare — `const result: T = ...`. Angle brackets only appear when *declaring* or *calling* a generic (`function useFetch<T>`, `useFetch<MealResponse>`).

**Step 3 — the fetch, inside an effect:**

```ts
import { useEffect, useState } from "react";

export function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    async function fetchData() {
      setIsLoading(true);   // reset — the url may have just changed
      setError(null);

      try {
        const res = await fetch(url);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const result: T = await res.json();
        setData(result);
      } catch (err) {
        setError(err instanceof Error ? err.message : "Something went wrong");
      } finally {
        setIsLoading(false);
      }
    }

    fetchData();
  }, [url]);

  return { data, isLoading, error };
}
```

Every line earns its place:

- **`useEffect` with `[url]`** — call `fetchData()` directly in the hook body and it runs on every render; `setData` re-renders, which fetches again, forever. The effect ties the fetch to the url.
- **`res`, not `data`** — name the fetched response `res`. Call it `data` and it shadows the `data` state declared a few lines above, and the confusion starts there.
- **Reset at the top** — when the url changes mid-life, `isLoading` would still be `false` from the last fetch. Set loading true, error null, before each attempt.
- **try/catch/finally *inside* the async function** — the classic bug is wrapping the `fetchData()` *call* in try/catch. Calling an async function returns immediately, so `finally` would flip loading off before the fetch even finished. The blocks must wrap the `await` lines.
- **`res.ok`** — next section.
- **`err instanceof Error ? err.message : "..."`** — in a catch block TypeScript types `err` as `unknown`, because JavaScript lets you `throw` anything (`throw 5`, `throw "oops"`). Until you prove it's an `Error`, reading `.message` is a red underline. The ternary says: if it's an Error, use its message; otherwise a fallback.

Also decide your export style once: `export function useFetch` (import with curly braces) or `export default function useFetch` (import bare). Both work — mismatching them gives "no exported member" or `undefined`.

## Status Codes — Why res.ok Exists

The `if (!res.ok) throw` line deserves a proper explanation, because fetch's behavior here surprises everyone.

Every reply from a server carries a **status code** — a three-digit number, sorted into families by the first digit:

- **200s — success.** 200 is "here's what you asked for."
- **400s — you made a mistake.** 404 is "I can't find that" (wrong URL), 401 is "you're not logged in."
- **500s — the server broke.** 500 is "something went wrong on my side."

`res.ok` is a shortcut: `true` for the whole 200 family (200–299), `false` for everything else.

Now the surprising part. **Fetch only throws for network-level failures** — you're offline, the address doesn't exist. When the server answers with a 404 or 500, fetch says "I got a response" and hands it over happily. Without the check, a 404 page would sail into `res.json()` and you'd treat an error page as real data.

So the check, and what `throw` does:

```ts
const res = await fetch(url);
if (!res.ok) throw new Error(`HTTP ${res.status}`);
```

When `res.ok` is false, `throw` means: **stop right here, skip every remaining line in the try block** (the JSON step, `setData`), and jump straight to `catch`. There, `setError` updates the state, the component re-renders, and your error UI shows.

`new Error(...)` is just JavaScript's built-in blueprint for error objects — you pass a message, it stores it as `.message`. And `finally` runs in every case, success or failure, so `isLoading` always goes false.

The payoff: one catch block now handles *both* kinds of failure — network down, and server said no. The `throw` converts "the server said no" into the same path.

## Using It — RecipeList

The component shrinks to this:

```tsx
// src/components/RecipeList.tsx
import { useFetch } from "../hooks/useFetch";

interface Meal {
  idMeal: string;
  strMeal: string;
  strMealThumb: string;
  strCategory: string;
}

type MealResponse = { meals: Meal[] | null };

export default function RecipeList() {
  const { data, isLoading, error } = useFetch<MealResponse>(
    "https://www.themealdb.com/api/json/v1/1/search.php?s=mushroom"
  );

  if (isLoading) return <p>Loading...</p>;
  if (error) return <p>Couldn't load recipes. Please try again.</p>;
  if (!data?.meals) return <p>No recipes found.</p>;

  return (
    <div>
      {data.meals.map((meal) => (
        <div key={meal.idMeal}>
          {meal.strMeal}
          <img src={meal.strMealThumb} alt={meal.strMeal} />
        </div>
      ))}
    </div>
  );
}
```

No `useState`, no `useEffect`, no try/catch — one hook call, and the whole fetch lifecycle is handled. TypeScript knows `data` is `MealResponse | null`, `isLoading` is a boolean, everything is type-safe.

The early returns deserve one beat. When `isLoading` is true, the function returns the loading text and **stops** — it never reaches the bottom return. That's the point. When the fetch finishes, the hook's state changes, React re-renders, and RecipeList runs again from the top: first check skipped (not loading), second skipped (no error), and the code finally reaches the list. The component runs many times, once per state change; each run returns exactly one thing. Early returns also guarantee loading and the list never show at the same time.

And the messages are friendly on purpose — raw "HTTP 404" means nothing to a user. The empty case (`meals` is null, not an error) gets its own line, so a no-match search isn't a blank page.

## The Race Condition — When the Old Response Wins

`useFetch` works. Until two requests overlap.

The user searches **mushroom**. Your hook sends request A — slow, 5 seconds. The user changes to **chickpea**. Request B goes out — fast, 1 second.

```
t=0s  Request A starts (mushroom)
t=1s  Request B starts (chickpea)
t=2s  Request B responds → setData(chickpea)   ✅ screen shows chickpea
t=5s  Request A responds → setData(mushroom) ❌ screen flips to mushroom
```

The search box says chickpea. The screen shows mushroom. This is a **race condition** — two requests racing, and the wrong one wins by finishing last.

And no, the old request is *not* cancelled by default. Nothing in fetch says "a new request replaces the old one." Both travel to the server, both come back, and the late one overwrites. Fast local networks hide this; production on slow connections exposes it.

The rule that fixes it: **an outdated request must not touch state.** Not `setData`, not `setError`, not `setIsLoading`. Two tools enforce it — the `ignore` flag (simple) and `AbortController (real cancellation). Start with the flag.

---

## The Ignore Flag

```ts
useEffect(() => {
  let ignore = false;   // fresh variable, created inside THIS run

  async function fetchData() {
    setIsLoading(true);
    setError(null);
    try {
      const res = await fetch(url);
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const result: T = await res.json();
      if (!ignore) setData(result);
    } catch (err) {
      if (!ignore) {
        setError(err instanceof Error ? err.message : "Something went wrong");
      }
    } finally {
      if (!ignore) setIsLoading(false);
    }
  }

  fetchData();

  return () => {
    ignore = true;      // cleanup — marks THIS run as outdated
  };
}, [url]);
```

Walk through mushroom and chickpea.

**Mushroom's run starts.** `let ignore = false` creates a brand-new variable — one per run. The fetch begins, and React *stores* the cleanup function the effect returned. Nothing runs yet — and note what does **not** happen: the cleanup does not run right after the effect finishes. It waits for one of two moments — the next url change (React calls it just before the new run) or unmount.

**Chickpea's url arrives.** Before React runs the effect again, it first calls the cleanup from mushroom's run. That cleanup was created *inside* mushroom's run, so it holds a link to mushroom's own `ignore` — and flips it to `true`. Then chickpea's run starts: brand new `ignore = false`, new fetch.

**Responses arrive.** Chickpea's finishes first, reads its own `ignore` — still `false` — and calls `setData`. Mushroom's straggles in later, reads *its* `ignore` — now `true` — and skips everything.

So chickpea never touches mushroom's variable. React simply says "mushroom run, time to clean up," and mushroom's cleanup marks mushroom's own flag. The name for that link — a function remembering the variables from its own run — is a **closure**, and it's why `ignore` must be a plain `let` inside the effect: every run gets its own copy, and each cleanup can only reach its own.

Three details that matter:

- **All three setters get the guard.** A stale request that *fails* late would otherwise slam an error onto a screen that's showing correct chickpea data. A stale `finally` would flip loading off while chickpea is still loading. Outdated means touching nothing.
- **Why not `useState` for the flag?** State updates are async and tied to renders — the cleanup would read a stale value, and every flip would cause an extra render. A plain `let` through closure is the right tool.
- **Same cleanup protects unmount.** Navigate away mid-fetch? The response arrives, sees `ignore = true` (set by the unmount cleanup), and drops itself instead of updating a component that's gone.

The limitation: `ignore` only throws away the *response*. The old request still travels the network; the server still does the work.

## AbortController — Actually Cancel

`AbortController` replaces the ignore flag — use one, not both. The idea is identical (cleanup marks the old run as outdated), but now the cleanup cancels the *request*.

```ts
useEffect(() => {
  const controller = new AbortController();   // 1. one controller per run

  async function fetchData() {
    setIsLoading(true);
    setError(null);
    try {
      const res = await fetch(url, { signal: controller.signal }); // 2. wire it up
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const result: T = await res.json();
      setData(result);
    } catch (err) {
      if (err instanceof DOMException && err.name === "AbortError") return;
      setError(err instanceof Error ? err.message : "Something went wrong");
    } finally {
      if (!controller.signal.aborted) setIsLoading(false);
    }
  }

  fetchData();
  return () => {
    controller.abort();   // 3. cleanup cancels this run's request
  };
}, [url]);
```

Three spots, same as the flag: the controller is created at the top of the run, its `signal` goes into the fetch call (the controller stays with you — the signal is what fetch listens to), and the cleanup calls `abort()`. When url changes, React runs mushroom's cleanup → mushroom's controller aborts → mushroom's fetch *stops mid-flight* and throws an `AbortError`. The catch sees `AbortError`, knows it was cancellation on purpose, and returns quietly — not a real failure, nothing to show. Finally checks `signal.aborted` so a cancelled run doesn't switch the spinner off while the new request is still going.

Two separate runs, two separate controllers — chickpea's signal never fires, so chickpea carries on normally.

| | `ignore` flag | `AbortController` |
|---|---|---|
| Stops stale state updates | ✅ | ✅ |
| Cancels the network request | ❌ | ✅ |
| Complexity | Very simple | Slightly more (handle AbortError) |

For most cases the flag is enough. Reach for the controller when requests are heavy and you want to save the bandwidth — cancel the mushroom request the moment chickpea starts.

## useLocalStorage — The Problem

Second hook, same method: feel the pain first.

A to-do app. User adds three tasks, they live in `useState`. Then they refresh. `useState` lives only in memory — refresh wipes it, the list starts empty, the three tasks are gone. The browser has a storage box that survives refreshes: **localStorage**.

Doing it by hand, every component needs two chunks:

```ts
const [tasks, setTasks] = useState<Task[]>(() => {
  const saved = localStorage.getItem("tasks");
  return saved ? JSON.parse(saved) : [];
});

useEffect(() => {
  localStorage.setItem("tasks", JSON.stringify(tasks));
}, [tasks]);
```

Tasks, theme, a draft message — repeat three times. Same as the fetch problem from 6.1: only the key and the type change.

What localStorage *is*, quickly: a per-site key-value box in the browser — your app can only see its own box. `setItem` to save, `getItem` to read, `removeItem` to delete. It only ever holds **text**, until someone clears it, a few megabytes at most. Which gives the conversion rule: objects and arrays can't go in directly — `JSON.stringify` packs them into text on the way in, `JSON.parse` unpacks them on the way out.

So the hook sits in the middle and translates. The component hands it a real array; it stores text. It reads text; it hands the component a real array. The component never sees text; storage never sees objects.

And the division of labor: **state is the working copy, localStorage is the backup copy.** When you click Add, the component updates the array it already has in state — no reading from storage at that moment. After the render, a `useEffect` quietly stringifies the new value and saves it. Parsing happens once, at startup. Storage is read once, then state is the source of truth while the app runs; every change writes a fresh backup.

---

## The Lazy Initializer

The startup read has a timing problem, and useState has a built-in answer.

Read localStorage in a `useEffect`, and the order is: component renders with a placeholder (empty array) → user sees an empty list → *then* the effect runs, reads storage, calls setState → second render with the real tasks. Two renders, a flicker of empty content. Worse: the save effect also runs on that first render and can overwrite the saved tasks with the empty array before the read lands.

Or read it *before* the first screen:

```ts
const [storedValue, setStoredValue] = useState<T>(() => {
  const item = localStorage.getItem(key);
  return item ? (JSON.parse(item) as T) : initialValue;
});
```

Pass a **function** to useState instead of a value. React calls that function once — on the very first render only — and uses whatever it returns as the starting state. Every later render, React ignores it completely. That's why it's *lazy*: the work (getItem + parse) happens once, when it's actually needed, and the component's first paint already has the real tasks. No flicker, no race with the save effect.

This is built into React — nothing to install, nothing to write yourself.

---

## Why T Needs a Real initialValue

Notice the hook takes two parameters:

```ts
function useLocalStorage<T>(key: string, initialValue: T) {
```

**The key** is the label in the storage dictionary — "tasks" for the to-do page, "user" for login, "theme" for settings. Each component passes its own, so they never overwrite each other, and it's how the hook finds *its* data later.

**The initialValue** is the fallback for the very first visit, when `item` is null — nothing saved yet. For tasks, an empty array; for a theme, `"light"`.

The question that makes the second parameter obvious: *we already passed `T` in the angle brackets — why can't the hook build an empty `T` itself?*

Because **types exist only while you write code.** `T` is a sticky note for TypeScript — "this will be a Todo array." TypeScript reads the note, checks everything matches, and then the note is thrown away: the JavaScript that runs in the browser has no types in it at all. At runtime the hook has no idea what was in the angle brackets, so it can't construct an empty one. And even if it could, only the component knows what a sensible starting value *is* — empty array for tasks, `"light"` for a theme, a stub user for login.

Type tells TypeScript the *shape*. `initialValue` gives the hook a real *value*. First visit only — after the first save, the saved data wins.

## useLocalStorage — The Full Hook

Putting it together:

```ts
// src/hooks/useLocalStorage.ts
import { useState, useEffect } from "react";

export function useLocalStorage<T>(key: string, initialValue: T) {
  const [storedValue, setStoredValue] = useState<T>(() => {
    try {
      const item = localStorage.getItem(key);
      return item ? (JSON.parse(item) as T) : initialValue;
    } catch {
      return initialValue;   // corrupt or blocked storage — fall back
    }
  });

  useEffect(() => {
    try {
      localStorage.setItem(key, JSON.stringify(storedValue));
    } catch (err) {
      console.error("Could not save to localStorage:", err);
    }
  }, [key, storedValue]);

  return [storedValue, setStoredValue] as const;
}
```

- **Lazy initializer with try/catch** — the read is one ternary: `item ? (JSON.parse(item) as T) : initialValue`. Read it as a question with two answers: `item` is the question, the part before `:` is the yes (something saved — parse it, `as T` because `JSON.parse` gives back untyped data), the part after is the no (nothing saved — `initialValue`). The catch is the safety net: localStorage is text anyone can edit (dev tools, an older app version), and broken text makes `JSON.parse` throw — without the catch, your app crashes on load.
- **Save effect** — runs whenever `storedValue` changes. The dependency array holds `key` *and* `storedValue`: the rule is anything from outside the effect that the effect *uses* goes in. `storedValue` is what actually changes; `key` almost never does, but listing it is honest. The write's catch covers the other failure modes — private-mode browsers that block storage entirely, or a full quota (only a few megabytes).
- **`return [storedValue, setStoredValue] as const`** — same shape as `useState`, so it swaps in naturally: `const [tasks, setTasks] = useLocalStorage<Todos>("tasks", [])`. The `as const` pins the pair (value, setter) so destructuring gets exact types.

In the component, `handleClick` doesn't change at all — it still calls `setTodos([...todos, newTask])`. The state updates, the screen re-renders, and the hook's effect quietly saves the backup. Read once at the start, save after every change. That's the whole loop.

## Both Hooks Together

They're independent — two tools sitting side by side in the same component, not talking to each other:

```tsx
const { data, isLoading } = useFetch<DashboardData>("/api/dashboard");
const [preferences, setPreferences] = useLocalStorage<Preferences>(
  "dashboard-prefs",
  { theme: "dark", widgets: ["stats", "chart"] }
);
```

`useFetch` gets server data (changes when the url changes). `useLocalStorage` stores what the user chose (survives refreshes). The component uses both in its JSX — fetched content, styled by the saved theme. TypeScript infers each `T` separately.

A more connected idea — caching fetched results into localStorage — is *not* what this snippet does, and `useFetch` itself does no caching. The real both-hooks build arrives in the next topic, where the Recipe Finder gets refactored.

## What useFetch Is NOT

- **Not a caching solution.** It fetches again on every mount or url change and remembers nothing. For caching, use TanStack Query.
- **Not a retry solution.** A failed request shows the error and stops. TanStack Query retries automatically.
- **Not a mutation solution.** `useFetch` runs inside an effect — automatically, on load. POST/PUT/DELETE change the server and should happen only when the user *chooses* (a button click), which needs a `mutate` function you call manually — `useFetch` doesn't give you one. That's TanStack Query's `useMutation`.

`useFetch` is for simple GETs: fetch the data, handle loading and error. For anything bigger, use a library.

## So Here's the Takeaway

Generics made the hooks from 6.1 scale: `useFetch<T>` fetches *any* shape — the caller hands in the label, TypeScript keeps every page checked against its own data. `useLocalStorage<T>` persists *any* shape — read once through the lazy initializer, saved after every change, with try/catch on both sides. And under both: the lifecycle lessons — early returns, race conditions, cleanup functions, status codes — that the walk-through made concrete.

Next topic: the Recipe Finder refactor. Old code and new code side by side — the manual fetch block collapses into one `useFetch<Meal[]>` line, and the localStorage wiring into one `useLocalStorage` line. That's where the difference stops being theory.

## In Your Own Words

1. Why does `useFetch` need the generic `T`? What's the limit without it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Without generics, the hook is typed for one shape — a hook built for `MealResponse` can't be used by a tasks page, so you'd write a near-identical copy per data type, duplicating the logic in the types. With `T`, the caller decides: `useFetch<MealResponse>(url)` on the recipes page, `useFetch<Task[]>(url)` on tasks. One hook serves everything, and TypeScript still knows exactly what `data` is — autocomplete and error checking intact.

</details>

2. Why must the try/catch/finally live *inside* the async `fetchData` function rather than wrapping the `fetchData()` call? What goes wrong otherwise?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Calling an async function returns immediately — it doesn't wait for the fetch. If try/catch/finally wrap only the call, `finally` runs right away: `isLoading` flips to false before data arrives (spinner disappears instantly), and any fetch error happens after the catch has already finished, so it slips past. The blocks must wrap the `await` lines inside the async function so they actually wait for the request.

</details>

3. Why does fetch need the `res.ok` check — what does fetch itself treat as a failure?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Fetch only throws for network-level failures — offline, DNS doesn't resolve. When a server answers with 404 or 500, fetch considers the request *successful* (a response arrived) and hands the body over, so an error page would sail into `res.json()` and be treated as real data. `res.ok` is true only for the 200–299 family; `if (!res.ok) throw` converts "server said no" into a jump to the catch, so one catch handles both network failures and HTTP errors.

</details>

4. What's the race condition the `ignore` flag prevents, and why is it a plain `let` inside the effect instead of a `useState`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Two requests in flight — the slow old one finishes last and its `setData` overwrites the newer, correct data (user searched chickpea, sees mushroom). Each effect run creates its own `ignore`; when the url changes, React runs the previous run's cleanup, which flips *that run's own* flag (a closure), so the stale response sees `ignore === true` and skips all three setters. It can't be `useState`: state updates are async and tied to renders, so the cleanup would read a stale value, and each flip would trigger an extra render. A plain `let` per run is exactly right.

</details>

5. Why does `useLocalStorage` pass a *function* to `useState`, and why does the hook still need `initialValue` when it already has `T`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The function is the lazy initializer — React calls it once on the first render only, so localStorage is read and parsed a single time (a plain value would re-run the read every render, and reading in a `useEffect` shows a placeholder first — the empty-list flicker — and risks the save effect overwriting stored data before the read). `initialValue` is needed because `T` exists only at compile time: types are erased before the code runs, so at runtime the hook can't build an empty value from the angle brackets — and only the component knows the sensible default (empty array for tasks, `"light"` for a theme). `T` gives TypeScript the shape; `initialValue` gives the hook a real value for the first visit.

</details>
