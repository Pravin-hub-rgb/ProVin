## Where We Left Off

6.1 gave us the concept — a custom hook is a `use`-named function that extracts repeated hook logic, shares logic but not state, and follows the call-order rules. Now we build the simplest one, and learn the actual mechanics of writing a hook.

**Project goal first, before any hook code:** an Accordion — click the header, the content expands; click again, it collapses. We'll render it multiple times on the page, and **each accordion is independent** — opening one does nothing to the others.

That's different from an accordion where opening one panel closes the others — that version needs *shared* state, something that knows which panel is open. Not this one. Here each panel only knows its own open/closed, so a single boolean is enough.

This is also our first live test of "shares logic, not state": every accordion will call the same hook and get its own separate value.

## Step 2 — Why Hooks Return Arrays

Before writing the hook, one idea you already use every day without thinking about it. When you write:

```tsx
const [count, setCount] = useState(0);
```

`useState` hands back an **array** with two things: the value at position 0, the setter at position 1. The square brackets are just destructuring — they let *you* pick the names. `count` and `setCount` in one component, `name` and `setName` in another, same hook, no extra effort.

If `useState` returned an object instead, you'd be stuck with whatever property names the React team chose, or renaming on every call. And when the same hook is used twice in one component — one toggle for a modal, one for a menu — arrays let you name each pair independently.

Our `useToggle` will return the same shape: the current true/false value, and a function that flips it.

| Shape | Best when |
|-------|-----------|
| **Array** | Small hooks returning 2 things — caller picks the names (the `useState` pattern) |
| **Object** | Hooks returning 3+ things — order becomes impossible to remember, so names are fixed by the hook |

You'll see the object side of this table in 6.1.3 with `useBoolean`.

## Step 3 — Plain Accordion First

Same teaching approach we'll use for every hook in this batch: **build it plain first, then extract.** You need to see the logic live inside the component before you can see it move out.

```tsx
// src/components/Accordion.tsx
import { useState } from "react";

export function Accordion() {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div>
      <button onClick={() => setIsOpen(prev => !prev)}>
        {isOpen ? "Close" : "Open"} Details
      </button>
      {isOpen && <p>This was hidden, now it is visible.</p>}
    </div>
  );
}
```

Render it three times in `App.tsx` — each one flips independently:

```tsx
// src/App.tsx
import { Accordion } from "./components/Accordion";

export function App() {
  return (
    <main>
      <h1>Custom Hooks Demo</h1>
      <Accordion />
      <Accordion />
      <Accordion />
    </main>
  );
}
```

Open one — the other two don't care. Three components, three separate `useState` slots.

An honest note before we go further: **this component doesn't need a custom hook.** The logic is two lines, used in one place. We're extracting it as practice — to watch the logic move out of the component and into a hook, with the behavior staying pixel-identical. In a real project, the Rule of Three from 6.1 says leave it. Real extraction pressure starts with fetch and localStorage, in 6.2.

## Step 4 — Extract into useToggle

The logic that moves out is exactly two lines: the `useState` call, and the function that flips it. Into `useToggle.ts`:

```ts
// src/hooks/useToggle.ts
import { useState } from "react";

export function useToggle(initial = false) {
  const [value, setValue] = useState(initial);
  const toggle = () => setValue(v => !v);
  return [value, toggle] as const;
}
```

Line by line:

| Line | What it does |
|------|--------------|
| `initial = false` | Optional starting value — defaults to `false` (closed) |
| `useState(initial)` | The state itself, same as in the component |
| `toggle = () => setValue(v => !v)` | Flip: take the old value, return the opposite |
| `return [value, toggle] as const` | Hand both back as a fixed pair |

### The `as const` problem — see the error first

Try it *without* `as const` — write `return [value, toggle];` and use it:

```tsx
// src/components/Accordion.tsx
import { useToggle } from "../hooks/useToggle";

export function Accordion() {
  const [isOpen, toggleOpen] = useToggle(false);

  return (
    <div>
      <button onClick={toggleOpen}>  {/* ❌ error here */}
        {isOpen ? "Close" : "Open"} Details
      </button>
      {isOpen && <p>This was hidden, now it is visible.</p>}
    </div>
  );
}
```

Error:

```
Type 'boolean | (() => void)' is not assignable to type 'MouseEventHandler<HTMLButtonElement> | undefined'.
  Type 'boolean' is not assignable to type 'MouseEventHandler<HTMLButtonElement>'.
```

**What TypeScript sees:** without `as const`, `[value, toggle]` is a *loose array* — any length, every slot the same union type:

```
(boolean | (() => void))[]
```

Both destructured names get that union. `isOpen` might be a boolean *or* a function; `toggleOpen` might be a function *or* a boolean. TypeScript can't guarantee `toggleOpen` is callable, so `onClick={toggleOpen}` fails.

**The fix:**

```ts
return [value, toggle] as const;
```

Now TypeScript reads a **fixed tuple**, exactly as written:

```
readonly [boolean, () => void]
```

Position 0 is always boolean, position 1 is always `() => void`:

```tsx
const [isOpen, toggleOpen] = useToggle(false);
// isOpen: boolean        ✅
// toggleOpen: () => void ✅
```

| Code | What TypeScript thinks |
|------|------------------------|
| `return [value, toggle]` | `(boolean \| (() => void))[]` — loose array, union in every slot |
| `return [value, toggle] as const` | `readonly [boolean, () => void]` — fixed pair, exact type per position |

**Why doesn't `useState` need `as const`?** Fair question — you write it every day without it. Because `useState`'s return type is *declared by the React team* in their type definitions: TypeScript already knows it's `[S, Dispatch<SetStateAction<S>>]`, a tuple. But `useToggle` is **your** function — TypeScript doesn't know your intent, it just sees an array literal. You have to tell it. Rule: **whenever a custom hook returns an array, add `as const`.**

## Step 5 — Wire It into the Accordion

Replace the two logic lines in the component with one hook call:

```tsx
// src/components/Accordion.tsx
import { useToggle } from "../hooks/useToggle";

export function Accordion() {
  const [isOpen, toggle] = useToggle(false);

  return (
    <div>
      <button onClick={toggle}>
        {isOpen ? "Close" : "Open"} Details
      </button>
      {isOpen && <p>This was hidden, now it is visible.</p>}
    </div>
  );
}
```

No `useState`, no flip function. Two ways to write the onClick, both correct:

```tsx
<button onClick={toggle}>        {/* passes the function — React calls it on click */}
<button onClick={() => toggle()}> {/* wraps it in an arrow — also fine */}
```

What you must **not** write: `onClick={toggle()}` with parentheses — that calls the function *during render*, flipping the state before anyone clicks.

The behavior is identical to Step 3. Open one accordion, the others stay put. The logic moved files; nothing else changed.

## Where Does the State Live?

A confusion that hits almost everyone at this point: the `useState` call sits in `useToggle.ts`, but `isOpen` is read in `Accordion.tsx`. How does the component "have" state that was created in another file?

Step by step, in the order React actually runs it:

```tsx
// Accordion.tsx
const [isOpen, toggle] = useToggle();
```

1. `Accordion` renders. That line calls `useToggle()` — a **normal function call**.
2. Inside the hook, `useState` runs. React attaches that state to **the component currently rendering** — `Accordion`. The file path where the call is written doesn't matter; only *who is rendering* matters.
3. The hook returns `[value, toggle]`, and your destructuring names them: `isOpen` is just your label for position 0. It could be called anything.
4. Click → `toggle()` runs → `setValue` updates that state → React re-renders `Accordion` → `useToggle()` is called again → this time `value` is the new one → `isOpen` shows the new value.

So the hook file is just where the code is *written*. The state belongs to the component that called it. And because each `Accordion` instance makes its own call, each gets its own slot — three accordions on the page, three independent booleans. That's the "shares logic, not state" rule from 6.1, working in front of you.

## Bonus — Second Use: Modal

The same hook, a new component:

```tsx
// src/components/ModalExample.tsx
import { useToggle } from "../hooks/useToggle";

export function ModalExample() {
  const [isModalOpen, toggleModal] = useToggle(false);

  return (
    <div>
      <button onClick={toggleModal}>Open Modal</button>
      {isModalOpen && (
        <div className="modal">
          <p>Modal content</p>
          <button onClick={toggleModal}>Close</button>
        </div>
      )}
    </div>
  );
}
```

Add it to `App.tsx` next to the Accordions. Same one-line call, different names (`isModalOpen`, `toggleModal`), completely separate state — the modal's boolean has nothing to do with any accordion's.

Without the hook, these two lines would be copy-pasted into every component that ever needs a toggle:

```tsx
const [isOpen, setIsOpen] = useState(false);
const toggle = () => setIsOpen(v => !v);
```

Two lines is nothing — until it's five components, then ten. With the hook: the flip logic exists once, in one file. Fix a bug or add a feature (say, a callback on toggle) — change it in `useToggle.ts` and every user gets the fix.

## In Your Own Words

1. Why does `useToggle` return an array, and why does that array need `as const`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Array because it's the `useState` pattern — a small fixed pair where the caller picks the names, so `const [isOpen, toggle]` in one place and `const [isDark, toggleTheme]` in another, no renaming needed. `as const` because TypeScript otherwise sees a loose array `(boolean | (() => void))[]` — both slots get the union type, so it can't guarantee `toggle` is a function and `onClick={toggle}` errors. `as const` locks it as the tuple `readonly [boolean, () => void]`. `useState` doesn't need it because React's own type definitions already declare that tuple shape — but your function's return type is your responsibility to tell TypeScript.

</details>

2. The `useState` call is in `useToggle.ts`, but `Accordion.tsx` reads `isOpen`. Where does the state actually live?

<details>
<summary>Show Answer</summary>

**Sample Answer:** It belongs to the component that called the hook — `Accordion`. When Accordion renders, `useToggle()` is just a normal function call; inside it, `useState` runs, and React attaches that state to the component currently rendering, regardless of which file the call is written in. The hook returns `[value, toggle]`, and your destructuring just names the positions — `isOpen` is a label for position 0. Each Accordion instance calls the hook separately, so each gets its own state slot. The file is where the code lives; the state lives with the component.

</details>

3. You render the same `<Accordion />` three times. Do they share one boolean, or does each have its own?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Three independent booleans. Each rendered Accordion is a separate component instance, and each one calls `useToggle()` separately — which means `useState` runs separately inside each call, creating three distinct state slots. Opening the first accordion flips only its slot; the other two don't notice. This is the "shares logic, not state" rule from 6.1 in action: the *code* is shared (one `useToggle.ts` file), the *state* is created fresh per call. If you wanted all three to open together, that would need shared state — a prop, Context, or a store — not a custom hook.

</details>
