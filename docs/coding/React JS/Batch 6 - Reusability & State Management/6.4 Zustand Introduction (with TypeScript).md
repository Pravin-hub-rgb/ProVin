## Where We Left Off

In 6.1–6.3, we learned about custom hooks — extracting logic with `useFetch<T>` and `useLocalStorage<T>`. But there is still a problem — **global state**. When two components need to share the same state (theme, user, cart), custom hooks don't work (remember? Each component gets its own separate state).

Until now, we used **Context API** for global state (Batch 2.6). But Context has some problems. Let's look at a better alternative — **Zustand**.

So here is the scenario...

---

## Problem — Context API Problems

First, let's understand what problems Context has. Take a simple Theme Context (like the one we built in Batch 2.6):

```tsx
// context/ThemeContext.tsx
import { createContext, useContext, useState, type ReactNode } from "react";

type Theme = "light" | "dark";

interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");
  const toggleTheme = () => setTheme(t => t === "light" ? "dark" : "light");

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within ThemeProvider");
  return ctx;
}
```

This works. But it has some problems:

### Problem 1 — Provider Nesting

When you have multiple contexts:

```tsx
function App() {
  return (
    <ThemeProvider>
      <AuthProvider>
        <CartProvider>
          <SettingsProvider>
            <RouterProvider>
              <AppContent />
            </RouterProvider>
          </SettingsProvider>
        </CartProvider>
      </AuthProvider>
    </ThemeProvider>
  );
}
```

This is "provider hell". Each new context adds a new nesting layer. Visually ugly, and mental overhead grows — provider order matters (e.g., AuthProvider might need to access ThemeProvider).

### Problem 2 — Unnecessary Re-renders

As soon as `theme` changes, **all** children of `ThemeProvider` re-render — even those that don't use `theme`. When the context value changes, **all** consumers inside the provider re-render:

```tsx
// When theme changes, Header + Footer + Sidebar all re-render
function AppContent() {
  return (
    <>
      <Header />    {/* uses theme — re-render needed */}
      <Sidebar />   {/* doesn't use theme — still re-renders */}
      <Footer />    {/* doesn't use theme — still re-renders */}
    </>
  );
}
```

In Batch 5.1, we saw that `React.memo` can fix this, but wrapping everything with `React.memo` is also boilerplate. **Zustand solves this problem by default.** Only the component that subscribes to a specific slice of state re-renders.

### Problem 3 — Boilerplate

For every context:

1. Define an interface
2. `createContext` with a default value / undefined
3. Create a Provider component
4. Build a value object (ideally with `useMemo`/`useCallback`)
5. Create a custom hook with a guard

That is 30-40 lines for every context. Five contexts = 150-200 lines of pure boilerplate.

---

## Zustand — What Is It

**Zustand is a lightweight state management library.** In German, "zustand" means "state". What it does: you create a global store, and any component can subscribe to any part of that store — without a provider, without boilerplate.

**Philosophy:** "A small, fast and flexible (and battle-tested) hook-based state manager."

Zustand's approach is simple — you create a store (using the `create` function), and components read from the store directly. No provider, no context tree, no wrapper component.

### Installation

```bash
npm install zustand
```

## Mini Project — Counter with Three Components

The diagram showed A, B, C sharing a store — now let's make it **real**. We will create a counter store and have **three different components** use it. Run the code and you will see that changing one component updates the others — because the store is **central**.

We continue with the `custom-hooks-demo` project from 6.1/6.2. We will create a new folder `src/stores/` — Zustand stores go here.

### Step 1 — Create the Store: src/stores/counterStore.ts

Create a new file in `src/stores/`:

```ts
// src/stores/counterStore.ts
import { create } from "zustand";

interface CounterStore {
  count: number;
  increment: () => void;
  decrement: () => void;
  reset: () => void;
}

const useCounterStore = create<CounterStore>((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
  reset: () => set({ count: 0 }),
}));
```

**What is happening:**

| Line | What It Is |
|------|---------|
| `create<CounterStore>()` | Generic function — creates a type-safe store |
| `(set) => ({ ... })` | Callback that receives the `set` function |
| `count: 0` | Initial state |
| `set((state) => ({ count: state.count + 1 }))` | State update — return an object, it will be merged |
| `set({ count: 0 })` | Can also pass a direct value — partial merge |

Note: the store is created with `create` only — no provider, no wrapper. The store is an **independent entity** that can be imported anywhere.

### Step 2 — Component A: src/components/CounterA.tsx

Create a new component — `src/components/CounterA.tsx` — and import the store from `../stores/counterStore`:

```tsx
// src/components/CounterA.tsx
import { useCounterStore } from "../stores/counterStore";

export function CounterA() {
  const count = useCounterStore((state) => state.count);
  const increment = useCounterStore((state) => state.increment);

  return (
    <div>
      <p>Count (A): {count}</p>
      <button onClick={increment}>+1</button>
    </div>
  );
}
```

### Step 3 — Component B: src/components/CounterB.tsx

Create a second component — **same store**, but with a `-1` button:

```tsx
// src/components/CounterB.tsx
import { useCounterStore } from "../stores/counterStore";

export function CounterB() {
  const count = useCounterStore((state) => state.count);
  const decrement = useCounterStore((state) => state.decrement);

  return (
    <div>
      <p>Count (B): {count}</p>
      <button onClick={decrement}>-1</button>
    </div>
  );
}
```

### Step 4 — Component C: src/components/CounterC.tsx

Create a third component — **same store**, with a `Reset` button:

```tsx
// src/components/CounterC.tsx
import { useCounterStore } from "../stores/counterStore";

export function CounterC() {
  const count = useCounterStore((state) => state.count);
  const reset = useCounterStore((state) => state.reset);

  return (
    <div>
      <p>Count (C): {count}</p>
      <button onClick={reset}>Reset</button>
    </div>
  );
}
```

### Step 5 — Render All in App.tsx

Open `src/App.tsx`, remove the default Vite content, and import all three components:

```tsx
// src/App.tsx
import { CounterA } from "./components/CounterA";
import { CounterB } from "./components/CounterB";
import { CounterC } from "./components/CounterC";

export default function App() {
  return (
    <main>
      <h1>Zustand Counter — Central Store Demo</h1>
      <CounterA />
      <CounterB />
      <CounterC />
    </main>
  );
}
```

### Step 6 — The Proof (Run It)

Now run `bun run dev` and open your browser. You will see three components — all showing the **same count**:

```
Count (A): 0    [+1]
Count (B): 0    [-1]
Count (C): 0    [Reset]
```

**Now click `+1` in CounterA.** What happens?

```
Count (A): 1    [+1]
Count (B): 1    [-1]     ← ALSO UPDATED!
Count (C): 1    [Reset]  ← ALSO UPDATED!
```

**All three show `1`!** Now click `-1` in CounterB → all three show `0`. Reset works the same way.

**Why?** The three components are **not holding separate state** — they are all subscribed to the **SAME store** (`useCounterStore`). The store is a single instance. Any call to `set()` anywhere → state changes in the store → **all subscribers** receive the new value.

**This is what "central store" means.** In the diagram above where A, B, C were connected to a store — that is now **real**. Component B doesn't need to know that A was clicked — they both show the same count because they both read from the same store.

If we had done this with `useState` — each component would have its own separate state, and all three would show different counts. **This is Zustand's core advantage — sharing state without a provider.**

### Selective Subscription (The Real Difference)

Above, we used different selectors in each component:

```tsx
const count = useCounterStore((state) => state.count);
const increment = useCounterStore((state) => state.increment);
```

Each line selects a **specific slice**. Or get everything in one call:

```tsx
const { count, increment, decrement, reset } = useCounterStore();
```

**But here is the difference:** With the first approach, the component only re-renders when `count` changes. With the second, any state change (even unrelated ones) triggers a re-render. Zustand supports **selective subscription** automatically — the selector function decides which state the component depends on. That is why `CounterA` only subscribes to `count` — when `reset` is called, `CounterA` does not re-render (its `count` value just updates).

## Visual Mapping — Context vs Zustand

Above in the mini project, we saw the central store concept — now understand it through this diagram. A, B, C = CounterA, CounterB, CounterC that we just built:

```
Context API:
┌─────────────────────────────────────┐
│  App (Provider wraps everything)    │
│  ┌─────┐ ┌─────┐ ┌─────┐          │
│  │  A  │ │  B  │ │  C  │          │
│  │uses │ │uses │ │uses │          │
│  │theme│ │cart │ │auth │          │
│  └─────┘ └─────┘ └─────┘          │
│  ─── theme change → A re-renders   │
│  ─── B and C ALSO re-render (❌)   │
└─────────────────────────────────────┘

Zustand:
┌─────────────────────────────────────┐
│  Store (independent, no provider)   │
│  { count, increment, ... }          │
│                                     │
│  ┌─────┐ ┌─────┐ ┌─────┐          │
│  │  A  │ │  B  │ │  C  │          │
│  │sub  │ │sub  │ │sub  │          │
│  │count│ │count│ │count│          │
│  └─────┘ └─────┘ └─────┘          │
│  ─── count change → A re-renders   │
│  ─── B and C ALSO re-render (✅)   │
└─────────────────────────────────────┘
```

In Zustand, there is no provider. The store is a separate entity — components use it directly. **Right now all three counter components subscribe to the same store — so when `count` changes, all three re-render (and all receive the same value).** When a part of the store changes, only the components that subscribed to that specific part re-render.

## Zustand vs Context — Comparison

| Feature | Context API | Zustand |
|---------|-------------|---------|
| **Provider needed** | Yes — must wrap component tree | No — store is independent |
| **Selective re-renders** | No — all consumers of provider re-render | Yes — only the subscribed slice re-renders |
| **Boilerplate** | 30-40 lines per context | 10-15 lines per store |
| **Multiple stores** | Multiple providers = nesting nightmare | Multiple stores = independent, no nesting |
| **TypeScript** | Manual typing needed | Built-in generic `create<T>` |
| **Bundle size** | Built-in (0 KB) | ~1 KB (gzipped) |
| **Async actions** | Extra code needed | First-class support |
| **Persistence** | Manual (localStorage effect) | Built-in `persist` middleware |
| **Learning curve** | Minimal (but footguns later) | Minimal |

## Zustand Store Patterns

### Pattern 1 — Separate State and Actions

You can divide the store into two parts — state and actions. This improves readability:

```ts
interface AuthStore {
  // State
  user: User | null;
  isLoading: boolean;
  error: string | null;

  // Actions
  login: (email: string, password: string) => Promise<void>;
  logout: () => void;
}

const useAuthStore = create<AuthStore>((set) => ({
  user: null,
  isLoading: false,
  error: null,

  login: async (email, password) => {
    set({ isLoading: true, error: null });
    try {
      const res = await fetch("/api/login", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ email, password }),
      });
      if (!res.ok) throw new Error("Login failed");
      const user = await res.json();
      set({ user, isLoading: false });
    } catch (err) {
      set({
        error: err instanceof Error ? err.message : "Something went wrong",
        isLoading: false,
      });
    }
  },

  logout: () => set({ user: null }),
}));
```

**In the component:**

```tsx
function LoginForm() {
  const { login, isLoading, error } = useAuthStore();

  // Only subscribes to login + isLoading + error
  // If another store property changes, no extra re-render
}
```

**What is happening:**

| Thing | What It Is |
|-------|---------|
| `login: async (email, password) => { ... }` | Async action — fetch logic lives inside the store itself |
| `set({ isLoading: true, error: null })` | Partial state update — only these values change |
| `set({ user, isLoading: false })` | Success — set user, stop loading |
| `set({ error: "...", isLoading: false })` | Error — set error, stop loading |

### Pattern 2 — Multiple Stores

You can create multiple stores — each independent, no nesting:

```ts
const useThemeStore = create<ThemeStore>((set) => ({ ... }));
const useAuthStore = create<AuthStore>((set) => ({ ... }));
const useCartStore = create<CartStore>((set) => ({ ... }));

// In a component:
function App() {
  const theme = useThemeStore((s) => s.theme);
  const user = useAuthStore((s) => s.user);
  const items = useCartStore((s) => s.items);

  // Selective subscriptions from each store
}
```

No "provider hell". Each store can live in a separate file, handling different logic.

### Pattern 3 — One Store with Slices

For large apps, you can put everything in one store with **slices** — separate functions that handle specific parts of state:

```ts
import { create } from "zustand";
import { devtools } from "zustand/middleware";

// Slice types
interface UserSlice {
  user: User | null;
  login: (email: string, pw: string) => Promise<void>;
  logout: () => void;
}

interface ThemeSlice {
  theme: "light" | "dark";
  toggleTheme: () => void;
}

// Combined type
interface AppStore extends UserSlice, ThemeSlice {}

// Slice creators
const createUserSlice = (set: any): UserSlice => ({
  user: null,
  login: async (email, pw) => { ... },
  logout: () => set({ user: null }),
});

const createThemeSlice = (set: any): ThemeSlice => ({
  theme: "light",
  toggleTheme: () => set((s: any) => ({ theme: s.theme === "light" ? "dark" : "light" })),
});

// Combined store
const useAppStore = create<AppStore>()((set) => ({
  ...createUserSlice(set),
  ...createThemeSlice(set),
}));
```

I personally recommend the **multiple stores** approach (Pattern 2) — it is simple, predictable, and aligns with Zustand's design philosophy.

## Zustand Middleware — Persist

Zustand's `persist` middleware automatically syncs the store to localStorage — without any `useEffect`.

```ts
import { create } from "zustand";
import { persist } from "zustand/middleware";

interface PreferencesStore {
  theme: "light" | "dark";
  fontSize: number;
  setTheme: (theme: "light" | "dark") => void;
  setFontSize: (size: number) => void;
}

const usePrefStore = create<PreferencesStore>()(
  persist(
    (set) => ({
      theme: "light",
      fontSize: 16,
      setTheme: (theme) => set({ theme }),
      setFontSize: (fontSize) => set({ fontSize }),
    }),
    {
      name: "app-preferences", // localStorage key
    }
  )
);
```

Just wrap with `persist` middleware and give it a `name`. The store now automatically syncs to localStorage. **No `useEffect`, no `JSON.parse`/`stringify`, no `localStorage.getItem`.**

## How Zustand Works (Simple Understanding)

Zustand uses a **subscriber pattern** internally:

1. **Store creation** — define initial state + actions
2. **`useStore(selector)`** — component subscribes to a specific part of the store
3. **`set()` call** — state changes
4. Zustand checks — which component used which selector
5. **Only** components whose selected value actually changed — re-render

This is how selective re-rendering works without `React.memo`. Zustand does a **shallow comparison** internally — if the selector's output is the same, re-render is skipped.

---

## What Zustand Is NOT

- **NOT a replacement for Context in every case:** If you have truly local state (form inputs, toggle states), `useState` is still better. Zustand is for **global** state that multiple components need.
- **NOT a server-state solution:** For API data caching, refetching, deduplication — TanStack Query is better. Zustand is for client state (UI state, user preferences, auth state).
- **NOT a Redux killer:** Redux has a different philosophy (immutable updates, middleware ecosystem, devtools). Zustand is simpler but Redux is more structured for very large teams.
- **NOT heavy:** ~1 KB gzipped. The lightest state management library out there.

---

## So Here's the Takeaway

Zustand is simple: `create` a store, `set` to update, `useStore(selector)` to read. No provider, no boilerplate, no unnecessary re-renders. Selective subscription is built-in. The `persist` middleware handles localStorage. Multiple stores for separation of concerns.

## In Your Own Words

1. What are the three problems of Context API? How does Zustand solve them?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Three problems: (1) Provider nesting — each context needs a wrapper component. In Zustand, there is no provider, the store is independent. (2) Unnecessary re-renders — when the context value changes, all consumers re-render. Zustand does selective subscription — only the component whose selector changed re-renders. (3) Boilerplate — interface, context creation, provider, value object with `useMemo`, custom hook with guard — 30-40 lines per context. A Zustand store is 10-15 lines.

</details>

2. In Zustand's `set` function, what happens when you return a partial object? How is this different from Redux reducers?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Zustand's `set` does a **shallow merge**. `set({ isLoading: true })` only changes the `isLoading` property; all other properties remain unchanged. In Redux, you have to manually spread: `{ ...state, isLoading: true }`. Zustand's merge behavior is similar to React's `setState` (from class components). This makes the code shorter — you only write the properties you want to change, everything else is automatically preserved.

</details>

3. How does selective subscription work in Zustand? What is the difference between `useStore(selector)` and `useStore()`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `useStore(selector)` — the component subscribes only to the output of the selector function. For example, `useStore((s) => s.count)` — the component only re-renders when `count` changes. `useStore()` — without a selector — subscribes to the entire store. Any property change triggers a re-render. Best practice is to always use a selector — only take what the component needs. This improves performance because unrelated state changes don't cause the component to re-render.

</details>

4. What advantage does Zustand's `persist` middleware have over Context API for localStorage persistence?

<details>
<summary>Show Answer</summary>

**Sample Answer:** With Context API, you need manual code for localStorage persistence — `useEffect` with `localStorage.setItem`, initial state with `localStorage.getItem` + `JSON.parse`. This code repeats for every context. Zustand's `persist` middleware is a simple wrapper — just `persist(store, { name: "key" })` and everything is automatic. Serialization, deserialization, and sync are all built-in. If localStorage is corrupt, it handles the error too. Plus, persisting multiple stores is easy.

</details>

5. When should you use Context vs Zustand? What are the decision criteria?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Use Context when: (a) you only have 1-2 global values, (b) they change infrequently (theme, locale), (c) provider nesting is not an issue, (d) the app is small and the extra dependency isn't justified. Use Zustand when: (a) you have frequently-updating global state, (b) selective re-renders matter (performance-sensitive), (c) you need multiple stores (separation of concerns), (d) you need persistence, (e) you want to reduce boilerplate. Decision matrix: "Will provider nesting be annoying?" + "Will unnecessary re-renders be a problem?" + "Is the app medium/large?" — if any of these are yes, go with Zustand.

</details>
