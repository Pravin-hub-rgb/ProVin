## Problem — Context API Ki Problems

Pehle samajhte hain ki Context mein kya problems hain. Ek simple Theme Context lete hain (jaise Batch 2.6 mein banaya tha):

```tsx
// context/ThemeContext.tsx
import { createContext, useContext, useState, type ReactNode } from "react";

type Theme = "light" | "dark";

interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");
  const toggleTheme = () => setTheme(t => t === "light" ? "dark" : "light");

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used within ThemeProvider");
  return ctx;
}
```

Yeh kaam karta hai. Lekin ismein kuch problems hain:

### Problem 1 — Provider Nesting

Jab tumhare paas multiple contexts ho:

```tsx
function App() {
  return (
    <ThemeProvider>
      <AuthProvider>
        <CartProvider>
          <SettingsProvider>
            <RouterProvider>
              <AppContent />
            </RouterProvider>
          </SettingsProvider>
        </CartProvider>
      </AuthProvider>
    </ThemeProvider>
  );
}
```

Yeh "provider hell" hai. Har naya context naya nesting layer. Code visually ugly, aur mental overhead badhta hai — provider order bhi matter karta hai (agar AuthProvider ThemeProvider ke andar access kare).

### Problem 2 — Unnecessary Re-renders

Jaise hi `theme` change hota hai, `ThemeProvider` ke saare children re-render hote hain — chahe woh sirf `theme` use karte hain ya nahi. Context value change hone se us provider ke andar ke **sabhi** consumers re-render hote hain.

```tsx
// Jab theme change hota hai, Header + Footer + Sidebar sab re-render hote hain
function AppContent() {
  return (
    <>
      <Header />    {/* theme use karta hai — re-render chahiye */}
      <Sidebar />   {/* theme use nahi karta — phir bhi re-render */}
      <Footer />    {/* theme use nahi karta — phir bhi re-render */}
    </>
  );
}
```

Batch 5.1 mein humne dekha tha — `React.memo` se fix ho sakta hai, lekin har jagah `React.memo` lagana bhi boilerplate hai. **Zustand yeh problem by default solve karta hai.** Sirf woh component re-render hota hai jisne specific slice of state subscribe kiya hai.

### Problem 3 — Boilerplate

Har context ke liye:

1. Interface define karo
2. `createContext` karo with default value / undefined
3. Provider component banao
4. Value object banao (aur ideally useMemo/useCallback lagao)
5. Custom hook banao with guard

Har context ke liye 30-40 lines. 5 contexts ho toh 150-200 lines sirf boilerplate.

## Zustand — Kya Hai

**Zustand ek lightweight state management library hai.** German mein "zustand" ka matlab "state" hai. Kaam: ek global store banate ho, aur koi bhi component us store ka koi bhi part subscribe kar sakta hai — bina provider ke, bina boilerplate ke.

**Philosophy:** "A small, fast, and scalable bearbones state management solution."

Zustand ka approach simple hai — ek store banate ho (create function se), aur components seedha store access karte hain. Koi provider nahi, koi context tree nahi, koi wrapper component nahi.

### Installation

```bash
npm install zustand
```

### Pehla Store

```ts
import { create } from "zustand";

interface CounterStore {
  count: number;
  increment: () => void;
  decrement: () => void;
  reset: () => void;
}

const useCounterStore = create<CounterStore>((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
  reset: () => set({ count: 0 }),
}));
```

**Dekhte hain kya ho raha hai:**

| Line | Kya Hai |
|------|---------|
| `create<CounterStore>()` | Generic function — type safe store banata hai |
| `(set) => ({ ... })` | Callback jo `set` function deta hai |
| `count: 0` | Initial state |
| `set((state) => ({ count: state.count + 1 }))` | State update — object return karo, merge ho jayega |
| `set({ count: 0 })` | Direct value bhi de sakte ho — partial merge |

**Component mein istemal:**

```tsx
function Counter() {
  const count = useCounterStore((state) => state.count);
  const increment = useCounterStore((state) => state.increment);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={increment}>+1</button>
    </div>
  );
}
```

Ya ek hi call mein sab kuch le lo:

```tsx
const { count, increment, decrement, reset } = useCounterStore();
```

**Lekin yeh fark hai:** Pehle tareeke mein sirf `count` change hone pe component re-render hota hai. Doosre mein koi bhi state change (chahe unrelated ho) pe re-render hota hai. Zustand automatically **selective subscription** support karta hai — selector function decide karta hai ki component kis state pe depend karta hai.

## Visual Mapping — Context vs Zustand

```
Context API:
┌─────────────────────────────────────┐
│  App (Provider wraps everything)    │
│  ┌─────┐ ┌─────┐ ┌─────┐          │
│  │  A  │ │  B  │ │  C  │          │
│  │uses │ │uses │ │uses │          │
│  │theme│ │cart │ │auth │          │
│  └─────┘ └─────┘ └─────┘          │
│  ─── theme change → A re-renders   │
│  ─── B and C ALSO re-render (❌)   │
└─────────────────────────────────────┘

Zustand:
┌─────────────────────────────────────┐
│  Store (independent, no provider)   │
│  { theme, cart, auth }              │
│                                     │
│  ┌─────┐ ┌─────┐ ┌─────┐          │
│  │  A  │ │  B  │ │  C  │          │
│  │sub  │ │sub  │ │sub  │          │
│  │theme│ │cart │ │auth │          │
│  └─────┘ └─────┘ └─────┘          │
│  ─── theme change → A re-renders   │
│  ─── B and C stay same (✅)        │
└─────────────────────────────────────┘
```

Zustand mein koi provider nahi. Store ek alag entity hai — component seedha use karta hai. Jab store ka koi part change hota hai, sirf woh components re-render hote hain jinhone us specific part ko subscribe kiya hai.

## Zustand vs Context — Comparison

| Feature | Context API | Zustand |
|---------|-------------|---------|
| **Provider needed** | Haan — component tree mein wrap karna padta hai | Nahi — store independent hai |
| **Selective re-renders** | Nahi — provider ke sab consumers re-render | Haan — sirf subscribed slice re-render |
| **Boilerplate** | 30-40 lines per context | 10-15 lines per store |
| **Multiple stores** | Multiple providers = nesting | Multiple stores = independent, no nesting |
| **TypeScript** | Manual typing | Built-in generic `create<T>` |
| **Bundle size** | Built-in (0 KB) | ~1 KB (gzipped) |
| **Async actions** | Extra code needed | First-class support |
| **Persistence** | Manual (localStorage effect) | Built-in `persist` middleware |
| **Learning curve** | Minimal (but footguns later) | Minimal |

## Zustand Store Patterns

### Pattern 1 — Separate State and Actions

Store ko do parts mein divide kar sakte ho — state aur actions. Isse readability improve hoti hai:

```ts
interface AuthStore {
  // State
  user: User | null;
  isLoading: boolean;
  error: string | null;

  // Actions
  login: (email: string, password: string) => Promise<void>;
  logout: () => void;
}

const useAuthStore = create<AuthStore>((set) => ({
  user: null,
  isLoading: false,
  error: null,

  login: async (email, password) => {
    set({ isLoading: true, error: null });
    try {
      const res = await fetch("/api/login", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ email, password }),
      });
      if (!res.ok) throw new Error("Login failed");
      const user = await res.json();
      set({ user, isLoading: false });
    } catch (err) {
      set({
        error: err instanceof Error ? err.message : "Kuch gadbad hui",
        isLoading: false,
      });
    }
  },

  logout: () => set({ user: null }),
}));
```

**Component mein:**

```tsx
function LoginForm() {
  const { login, isLoading, error } = useAuthStore();

  // Sirf login + isLoading + error subscribe kiya
  // Koi aur store property change hoti hai — re-render nahi hoga
}
```

**Kya ho raha hai:**

| Cheez | Kya Hai |
|-------|---------|
| `login: async (email, password) => { ... }` | Async action — store ke andar hi fetch logic |
| `set({ isLoading: true, error: null })` | Partial state update — sirf yeh values change |
| `set({ user, isLoading: false })` | Success — user set karo, loading band karo |
| `set({ error: "...", isLoading: false })` | Error — error set karo, loading band karo |

### Pattern 2 — Multiple Stores

Zustand mein multiple stores bana sakte ho — har store independent, koi nesting nahi:

```ts
const useThemeStore = create<ThemeStore>((set) => ({ ... }));
const useAuthStore = create<AuthStore>((set) => ({ ... }));
const useCartStore = create<CartStore>((set) => ({ ... }));

// Component mein:
function App() {
  const theme = useThemeStore((s) => s.theme);
  const user = useAuthStore((s) => s.user);
  const items = useCartStore((s) => s.items);

  // Har store se selective subscription
}
```

Isse koi "provider hell" nahi. Har store alag file mein ho sakta hai, alag logics handle kar sakta hai.

### Pattern 3 — One Store with Slices

Badi app ke liye ek hi store mein **slices** bana sakte ho — alag functions jo state ke specific part handle karein:

```ts
import { create } from "zustand";
import { devtools } from "zustand/middleware";

// Slice types
interface UserSlice {
  user: User | null;
  login: (email: string, pw: string) => Promise<void>;
  logout: () => void;
}

interface ThemeSlice {
  theme: "light" | "dark";
  toggleTheme: () => void;
}

// Combined type
interface AppStore extends UserSlice, ThemeSlice {}

// Slice creators
const createUserSlice = (set: any): UserSlice => ({
  user: null,
  login: async (email, pw) => { ... },
  logout: () => set({ user: null }),
});

const createThemeSlice = (set: any): ThemeSlice => ({
  theme: "light",
  toggleTheme: () => set((s: any) => ({ theme: s.theme === "light" ? "dark" : "light" })),
});

// Combined store
const useAppStore = create<AppStore>()((set) => ({
  ...createUserSlice(set),
  ...createThemeSlice(set),
}));
```

Multiple stores approach (Pattern 2) personally recommend karta hoon — simple, predictable, aur Zustand ke design philosophy ke saath align hai.

## Zustand Middleware — Persist

Zustand ka `persist` middleware localStorage mein automatic store sync karta hai. Bina kisi `useEffect` ke.

```ts
import { create } from "zustand";
import { persist } from "zustand/middleware";

interface PreferencesStore {
  theme: "light" | "dark";
  fontSize: number;
  setTheme: (theme: "light" | "dark") => void;
  setFontSize: (size: number) => void;
}

const usePrefStore = create<PreferencesStore>()(
  persist(
    (set) => ({
      theme: "light",
      fontSize: 16,
      setTheme: (theme) => set({ theme }),
      setFontSize: (fontSize) => set({ fontSize }),
    }),
    {
      name: "app-preferences", // localStorage key
    }
  )
);
```

Bas ikhtiar — `persist` middleware wrap kiya, `name` diya. Store ab automatic localStorage sync hota hai. **Koi useEffect nahi, koi JSON.parse/stringify nahi, koi localStorage.getItem nahi.**

## Zustand Kaise Kaam Karta Hai (Simple Understanding)

Zustand internally ek **subscriber pattern** use karta hai:

1. Store creation — initial state + actions define karo
2. `useStore(selector)` — component subscribe karta hai store ke specific part se
3. `set()` call — state change hoti hai
4. Zustand checks — kis component ne kaunsa selector use kiya
5. Sirf woh components jinka selected value actually changed hai — re-render

Isliye selective re-render possible hai bina `React.memo` ke. Zustand internally shallow comparison karta hai — agar selector ka output same hai, toh re-render skip.

---

## What Zustand Is NOT

- **NOT a React-Context replacement in all cases:** If you have truly local state (form inputs, toggle states), `useState` is still better. Zustand for **global** state that multiple components need.
- **NOT a server-state solution:** For API data caching, refetching, deduplication — TanStack Query is better. Zustand is for client state (UI state, user preferences, auth state).
- **NOT a Redux killer:** Redux has a different philosophy (immutable updates, middleware ecosystem, devtools). Zustand is simpler but Redux is more structured for very large teams.
- **NOT heavy:** ~1 KB gzipped. Lightest state management library.

---

## So Here's the Takeaway

Zustand is simple: `create` a store, `set` to update, `useStore(selector)` to read. No provider, no boilerplate, no unnecessary re-renders. Selective subscription by default. Persist middleware for localStorage. Multiple stores for separation of concerns.

Ab agle topic mein To-Do App v2 ko Context se Zustand mein migrate karenge. Asli fark tab pata chalega jab tum side-by-side code dekhoge — Context ka provider + boilerplate vs Zustand ka clean store.

## In Your Own Words

1. Context API ki teen problems kya hain? Zustand unhe kaise solve karta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Teen problems: (1) Provider nesting — har context ke liye naya wrapper component. Zustand mein koi provider nahi, store independent hai. (2) Unnecessary re-renders — context value change pe saare consumers re-render. Zustand selective subscription karta hai — sirf woh component re-render jiska selector change hua. (3) Boilerplate — interface, context creation, provider, value object with useMemo, custom hook with guard — 30-40 lines per context. Zustand store 10-15 lines mein ban jaata hai.

</details>

2. Zustand store ke `set` function mein partial object return karne se kya hota hai? Redux ke reducer se kya fark hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Zustand ka `set` automatic shallow merge karta hai. `set({ isLoading: true })` sirf `isLoading` property change karega, baaki properties unchanged rahengi. Redux mein tumhe manually spread karna padta hai: `{ ...state, isLoading: true }`. Zustand ka merge behavior React's `setState` jaisa hai (class components mein). Isse code chhota hota hai — sirf woh properties likho jo change karni hain, baaki automatically preserve ho jaati hain.

</details>

3. Zustand mein selective subscription kaise kaam karta hai? `useStore(selector)` vs `useStore()` mein kya fark hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `useStore(selector)` — component sirf selector function ki output pe subscribe karta hai. Jaise `useStore((s) => s.count)` — sirf `count` change pe re-render hoga. `useStore()` — bina selector ke — poori store pe subscribe karta hai. Koi bhi property change pe re-render hoga. Best practice hai hamesha selector use karo — sirf utna le lo jitna component ko chahiye. Isse performance better rehti hai kyunki unrelated state changes component ko re-render nahi karte.

</details>

4. Zustand ka `persist` middleware Context API ke comparison mein kya advantage deta hai?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Context API ke saath localStorage persistence ke liye manual code chahiye — `useEffect` mein `localStorage.setItem`, initial state ke liye `localStorage.getItem` + `JSON.parse`. Har context ke liye yahi code repeat karna padta hai. Zustand ka `persist` middleware ek wrapper hai — bas `persist(store, { name: "key" })` likho, sab automatic ho jata hai. Serialization, deserialization, sync — sab built-in. Agar localStorage corrupt ho toh bhi error handle hota hai. Plus multiple stores ko persist karna easy hai.

</details>

5. Kab Context use karna chahiye aur kab Zustand? Decision criteria kya hain?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Context use karo jab: (a) sirf 1-2 global values hain, (b) infrequently change hoti hain (theme, locale), (c) provider nesting se problem nahi hai, (d) app chhoti hai aur extra dependency justify nahi karti. Zustand use karo jab: (a) frequently-updating global state hai, (b) selective re-renders matter karte hain (performance-sensitive), (c) multiple stores chahiye (separation of concerns), (d) persistence chahiye, (e) boilerplate kam karna hai. Decision matrix: "Will provider nesting be annoying?" + "Will unnecessary re-renders be a problem?" + "Is app medium-large?" — agar teeno ka haan, toh Zustand lo.

</details>
