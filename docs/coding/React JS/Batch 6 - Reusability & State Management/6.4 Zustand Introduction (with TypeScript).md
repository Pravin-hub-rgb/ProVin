## Where We Left Off

In 6.1–6.3, we extracted fetch logic, localStorage logic, and toggles into reusable custom hooks — but a custom hook shares **logic, not state**. Two components calling the same hook still get two separate copies. The moment theme, user, or cart has to be *the same value* in many components, we need global state — and until now that meant **Context API** (Batch 2.6).

Quick revision of that journey: state lives in a top component, a button five levels down needs it, and without Context you pass it as a prop through every component in between — even the ones that don't care — that's **prop drilling**. Context fixes it: put the value in a shared spot, wrap your components in a provider, and any component inside grabs the value directly, skipping all the middle layers.

That works. But Context has real pains — and they're the reason this file exists. So here is the scenario...

## Problem — When Context Hurts

### Pain 1 — One Value, No Partial Listening

A context usually holds one object with several fields inside:

```tsx
// context/ShopContext.tsx — one context, two fields
import { createContext, useContext, useState, type ReactNode } from "react";

type Theme = "light" | "dark";

interface ShopContextValue {
  theme: Theme;          // Header only cares about this
  cart: string[];        // CartButton only cares about this
  toggleTheme: () => void;
  addToCart: (item: string) => void;
}

const ShopContext = createContext<ShopContextValue | undefined>(undefined);

export function ShopProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");
  const [cart, setCart] = useState<string[]>([]);

  const toggleTheme = () => setTheme(t => (t === "light" ? "dark" : "light"));
  const addToCart = (item: string) => setCart(c => [...c, item]);

  return (
    <ShopContext value={{ theme, cart, toggleTheme, addToCart }}>
      {children}
    </ShopContext>
  );
}

export function useShop() {
  const ctx = useContext(ShopContext);
  if (!ctx) throw new Error("useShop must be used within ShopProvider");
  return ctx;
}
```

Component `Header` reads this context for `theme`. Component `CartButton` reads the *same* context for `cart`. Now the user adds an item to the cart...

...`Header` re-renders too. Header never uses the cart — but Context has no way to say "only wake me up when theme changes." React doesn't track which *field* of the object changed. It just sees that the whole context value is a new object, so it re-renders **every component reading that context**.

One precise correction to a common overstatement: it is *not* "all children of the provider re-render." A Sidebar that never touches the context doesn't wake up from a context change (it re-renders only if its own parent re-renders, or if it also calls the hook). The real problem is narrower and still fatal: **every consumer of the context re-renders when *any* field of the value changes**, because there are no selectors.

For a theme that changes once in a while, nobody notices. But imagine a cart that updates on *every* item add — every consumer re-renders on every click. That's wasted work.

### Can't Memoization Fix This?

A fair question — we met `React.memo`, `useMemo`, and `useCallback` in Batch 5.

`React.memo` stops a component from re-rendering when its **props** didn't change. But a component that reads a **context** ignores that protection: when the context value changes, it re-renders anyway, memo or not.

What `useMemo`/`useCallback` *do* help with is the provider side — they keep the value object from being recreated on every provider render, so consumers don't re-render for no reason when nothing actually changed. But when a field really changes, the whole value is genuinely new, so every consumer still re-renders.

So memoization reduces *extra* re-renders — it cannot make Header listen to only `theme`. That's the gap Zustand fills.

### The DIY Fix — Split the Contexts

Another idea that actually works: don't hold `theme` and `cart` in one context. Give each its own context, so Header only subscribes to the Theme context and CartButton only to the Cart context. When cart changes, Header stays quiet.

But here's the catch: each context needs its own type, its own `createContext`, its own provider, and its own custom hook with a guard. Ten pieces of state means ten contexts and ten providers. Splitting trades the re-render problem for a setup problem.

### Pain 2 — Provider Nesting

That setup problem shows up as a ladder. Each context adds a nesting layer:

```tsx
function App() {
  return (
    <ThemeProvider>
      <AuthProvider>
        <CartProvider>
          <SettingsProvider>
            <RouterProvider>
              <AppContent />
            </RouterProvider>
          </SettingsProvider>
        </CartProvider>
      </AuthProvider>
    </ThemeProvider>
  );
}
```

This is "provider hell". Visually ugly, mental overhead grows, and order can matter — one provider might need to read from another one above it. The more global state you have, the deeper the ladder gets.

### Pain 3 — Boilerplate

For every context, you write:

1. Define an interface
2. `createContext` with a default value / undefined
3. Create a Provider component
4. Build a value object (ideally with `useMemo`/`useCallback`)
5. Create a custom hook with a guard

That is 30–40 lines for every context. Five contexts = 150–200 lines of pure boilerplate.

Three pains, one theme: Context gives everyone the whole value, every time, wrapped in ceremony. What we want is precision — each component asks for exactly what it needs — with none of the wrapping. That's Zustand.

## Zustand — The Idea Before Any Code

**Zustand is a lightweight state management library.** In German, "zustand" means "state". Its philosophy: *"A small, fast and flexible (and battle-tested) hook-based state manager."*

Before any code, the picture — because this is where Context and Zustand part ways:

With Context, the data lives **inside** React's component tree, and the provider hands the whole value to everyone under it. Zustand does it differently. The data lives in a **store** — a little box of data that sits **outside** React. No provider, no wrapper component around your app.

Components don't receive the data from a parent. Instead, each component goes to the box and says: *"I only want X, and tell me when X changes."* That request is called a **selector**.

The box keeps a **ledger** of who asked for what. Now the cart changes — the box checks its list: Header asked only for theme, and theme didn't change, so Header isn't told anything and doesn't re-render. CartButton asked for cart, so CartButton gets updated.

That's the fix: the store remembers who asked for what, and only notifies the ones whose piece changed.

## Redux, Redux Toolkit, and Zustand

Before we build, one family tree — because you'll hear these three names together.

**Redux, Redux Toolkit, and Zustand solve the same problem:** a global store outside React that any component can use, without prop drilling or a Context provider tree. The base idea is identical — a box outside React that holds state, components subscribe to it. They differ in how much setup and structure you write around it.

The order they arrived: **Redux first**, then Redux Toolkit and Zustand around roughly the same time (years aren't worth memorizing — the flow is: Redux → then Redux Toolkit and Zustand together).

Plain Redux needed a lot of boilerplate — action types, action creators, reducers, setup code. The Redux team then built **Redux Toolkit**, which cuts most of that down and is now the official recommended way; if you ever learn Redux, go straight to Redux Toolkit. Plain Redux mostly survives in older codebases.

So why does Zustand exist when Redux Toolkit already fixed the boilerplate? Different libraries, different people: Redux comes from the React team's circle; Zustand was made by an independent open-source group (the same people behind a library called Jotai). And even with Redux Toolkit there's still more setup — you configure a store, write slices, and wrap your app in a provider. Zustand wanted something much smaller: no provider at all, almost no boilerplate — just `create` a store and use it.

Does Redux Toolkit still have provider hell? Not really — you wrap your app in **one** provider, no matter how many pieces of state you have (they all live in that single store). One ladder-free wrapper — which is one more than Zustand needs, but nowhere near the Context ladder.

When to use which:

- **Zustand, by default.** Simple, quick to set up, fits most apps — small or medium: a to-do app, a blog dashboard, a small online store (10–30 screens, one to three developers, a handful of global things: the logged-in user, the cart, the theme). Zustand handles this easily with one small store per thing.
- **Redux Toolkit for big apps.** A banking app or a large company admin system — hundreds of screens, 20+ developers, tons of shared state that many teams touch at once. One developer changing state carelessly can break another team's feature. Redux Toolkit forces everyone to change state the same strict way, and its devtools show exactly what changed and when. The extra setup is the price of keeping a big team consistent.

The difference isn't really the size of the code — it's how many people are working on it, and how much you need rules to keep them from stepping on each other. For learning and your own projects: start with Zustand.

## Mini Project — Counter with Three Components

Here's what we're building: a tiny counter — one paragraph showing a number, three buttons. Component A has **+1**, component B has **-1**, component C has **Reset**. All three show the same count.

The key idea: **nobody owns the count.** It lives in the box, the Zustand store. Click +1 in A, and B and C update too — because all three are watching the same box. That's the proof that the box is shared.

Picture a whiteboard on a wall with a number on it, starting at zero. Three people stand in front of it — one can add one, one can subtract one, one can wipe it back to zero. Everyone sees the same number, because there's only one whiteboard. The whiteboard is the Zustand box; the three people are the three components.

To build it, four things in order:

1. **Create the box** — holds the count and the three actions (increase, decrease, reset)
2. **Build three small components** — each asks the box for the count and one action
3. **Put them all in App**
4. **Run it and click around**

One connection before we start: this whiteboard looks a lot like `useReducer` — state plus actions like increment, decrement, and reset. You remembered it right, and the whiteboard *is* that pattern. The difference is **where it lives**: `useReducer`'s state belongs to one component, and you'd pass it down to share it; the Zustand box is the same idea — state plus actions — but it sits outside React, so any component reaches it directly. (And `useReducer` solves a *different* problem — grouping scattered update logic, like a calculator's add/subtract/divide functions all poking state from different places. `useReducer` organizes *how* state changes; Zustand solves *sharing* state without a provider.)

We continue with the `custom-hooks-demo` project from 6.1–6.3. New folder: `src/stores/` — Zustand stores live there.

### Step 1 — Install

```bash
npm install zustand
# bun add zustand
```

Zustand is a separate library — not built into React.

### Step 2 — Create the File

Inside `src`, make a new folder called `stores`. Inside it, create `counterStore.ts`. Leave it empty — we'll write it line by line.

### Step 3 — The Import

```ts
import { create } from "zustand";
```

`create` is the function that makes the box. We'll use it in the next line.

### Step 4 — The First Line (and One Word You Can't Forget)

```ts
export const useCounterStore = create(() => ({
  count: 0,
}));
```

| Line | What It Is |
|------|-----------|
| `export` | **The box must be exported.** Without it, `import { useCounterStore }` in every component fails — the store exists in its file, but no one else can see it. (This exact missing-`export` bug was found in the first draft of this lesson — we're not repeating it.) |
| `useCounterStore` | The name `create` hands back starts with `use` because **it's a hook**. Components call it to read from the box. The store is both the box *and* the way to reach into it. |
| `create(() => ({ ... }))` | `create` builds the box. The arrow function's parentheses wrapped around curly braces means "return this object directly" — the object is the box's contents. |
| `count: 0` | The initial contents. Right now: just the count. |

Whatever we define inside `create` is the contents of the box. Actions come next.

### Step 5 — `set`, the Box's Marker

The box can't change itself by magic. Zustand gives us a function called `set` and passes it to our function as a parameter:

```ts
export const useCounterStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
}));
```

Think of the whiteboard: `set` is the marker. `set({ count: 5 })` is like walking up and writing 5 on the board.

If you've used `useState`, this is the same idea — you got a setter like `setCount`, and calling it changes the state. `set` is the box's setter. Two differences:

1. **`set` updates the whole box** — it can change any value inside it, not just one.
2. **It's a partial update** — you only pass the pieces you want to change, and Zustand leaves everything else alone. `set({ count: 5 })` on a box with `count` and `name` changes only the count; the name stays exactly as it was. (Different from `useState` with objects, where you'd copy the old values yourself.)

Now the increment line, one piece at a time:

```ts
increment: () => set((state) => ({ count: state.count + 1 })),
```

- **`increment` is a function that lives inside the box**, right next to `count` — the box holds both the data and the actions.
- When you pass a **function** to `set`, Zustand hands you the current contents of the box — we call that `state`. So `state.count` means "the count that's in the box right now." (`state` includes `increment` itself too — it's all in the box — but we only use `state.count`.)
- We return the new count: old count plus one.
- The empty parentheses on `increment: () =>` mean it takes no input.

### Step 6 — TypeScript Enters

Type this state of the code and you'll get two errors:

- **"Cannot find name 'set'"** — `set` is missing from the parentheses after `create`. It must be `create((set) => ({`.
- **"state implicitly has type 'any'"** — TypeScript doesn't know what's in the box, because we never described it.

The fix: **describe the box once** with an interface and hand it to `create`:

```ts
import { create } from "zustand";

interface CounterStore {
  count: number;
  increment: () => void;
}

export const useCounterStore = create<CounterStore>((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
}));
```

There's a tempting wrong fix: annotate the type by hand inside every action — `set((state: CounterStore) => ...)`. It compiles, but you repeat the label in each action, and when the box changes you must update every copy. The better way is what's above: **say it once, right after `create`**, so the whole box is typed in one place — and remove any per-action annotations. This also fixes the "state is unknown" warning you might see in components.

A quick generics refresher, since this trips up everyone:

- The **angle brackets** are called *generics* — a type you hand to a function, like a label for the kind of thing it works with. `create<CounterStore>` means "build a box, and the box has the shape `CounterStore`."
- A **colon after the parentheses** would be different — that's the *return* type, what the function gives back (`: number`). Not what we're doing here.
- And how does `state` know what it is? The interface *describes* the box; `create<CounterStore>` connects that description to everything inside the store — so `state` automatically knows it's the whole box: `count`, the functions, all of the interface.

### Step 7 — The Other Two Actions

Update the interface and the box:

```ts
// src/stores/counterStore.ts
import { create } from "zustand";

interface CounterStore {
  count: number;
  increment: () => void;
  decrement: () => void;
  reset: () => void;
}

export const useCounterStore = create<CounterStore>((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
  reset: () => set({ count: 0 }),
}));
```

Notice `reset` is different — it doesn't need the current count, so we pass `set` a plain object, like writing zero straight on the whiteboard.

**The box is done.** Next: the components that reach into it.

### Step 8 — Component A: src/components/CounterA.tsx

```tsx
// src/components/CounterA.tsx
import { useCounterStore } from "../stores/counterStore";

export function CounterA() {
  const count = useCounterStore((state) => state.count);
  const increment = useCounterStore((state) => state.increment);

  return (
    <div>
      <p>Count (A): {count}</p>
      <button onClick={increment}>+1</button>
    </div>
  );
}
```

Each `useCounterStore(...)` line is a **selector** (spelled S-E-L-E-C-T-O-R) — the component telling the box, "I want only this piece." The first line asks for the count; the second asks for the increment action.

This is different from `useState`, which hands you an array you unpack in one go. With Zustand, you make **one request per piece**, and each request says exactly what you want. That's also what makes selective updates work: the box keeps in its ledger that CounterA asked for `count` and `increment` and nothing else. When something changes, it checks — did the value this component asked for change? For `count`, going 0 → 1 is a change, so CounterA re-renders. For `increment`, the function never changes, so it never triggers a re-render.

Two small syntax notes:

- **`export function` vs `export default`** — both work. With `export default`, your App import has no curly braces (`import CounterA from "./components/CounterA"`); curly braces only match named exports. Your editor's auto-import knows this: type the component name, accept the suggestion, and it writes the right import style for you.
- **`onClick={increment}`** — no parentheses. You're handing the button the function *itself*, and the button calls it when clicked. If you wrote `increment()`, it would run immediately on every render.

### Step 9 — Components B and C

CounterB follows the same pattern, but asks for `decrement`:

```tsx
// src/components/CounterB.tsx
import { useCounterStore } from "../stores/counterStore";

export default function CounterB() {

  const decrement = useCounterStore((state) => state.decrement);
```

```tsx

      <h1>Zustand Counter — Central Store Demo</h1>
```

(If you used `export default` in B and C, drop the curly braces on those two imports — match the style you wrote.)

Run `bun run dev` and open the browser:

```

Count (B): 0    [-1]
Count (C): 0    [Reset]
```

**Now click `+1` in CounterA.**

```
Count (A): 1    [+1]
Count (B): 1    [-1]     ← ALSO UPDATED!
Count (C): 1    [Reset]  ← ALSO UPDATED!
```

All three show `1`. Click `-1` in CounterB → all three show `0`. Reset works the same way.

**Why?** The three components have **no connection to each other** — no props, no parent passing anything down. They all read from the **same box** (`useCounterStore`, a single instance). Any call to `set()` → state changes in the box → every subscriber whose selected piece changed gets the new value.

You've just built what Context does — sharing one value across components — **without a single provider.**

One clarification, because it looks like a contradiction with everything above: all three re-rendered here *on purpose*. All three asked for the same thing — the count. When the count changes, of course all three update; that's what sharing means. The "don't wake the others" behavior only matters when components ask for **different** things — so let's prove that next.

## Selective Re-render Demo — The Real Difference

The notes only *describe* selective subscription; this demo makes it visible. We'll watch who re-renders with `console.log`, then change something nobody asked for.

### Watch the Renders

Add this line right above the `return` in CounterA, and similar ones in B and C (change the name each time):

```tsx
console.log("CounterA rendered");
```

Open the browser console. Initial render → all three logs. Click `+1` → all three logs again. Click `-1` → all three. This is the sharing behavior we just proved.

### Discovery — A Reset That Changes Nothing

Click `Reset` when the count is already `0`... and **nothing logs.**

Why? `set({ count: 0 })` writes the same value that's already there. The box compares old and new, sees no change, and tells nobody. No change, no notification.

Now increment a couple of times, then reset — all three logs appear, because the value *really* changed (something → 0). First reset works, second doesn't. The box isn't guessing; it's comparing.

### Add a Field Nobody Asked For

Add `name` to the box. In the interface:

```ts
name: string;
setName: (name: string) => void;
```

In the store:

```ts
name: "Pravin",
setName: (name) => set({ name }),
```

`setName` takes one input — whatever you pass when you call it, like `setName("Rahul")`. Inside, `set({ name })` is shorthand for `set({ name: name })`: the left side is the box's `name` field, the right side is the input you received. The box's name changes from "Pravin" to "Rahul"; the count stays untouched.

Add a **Change name** button in App:

```tsx
const setName = useCounterStore((s) => s.setName);
// ...
<button onClick={() => setName("Rahul")}>Change name</button>
```

Click it. **Watch the console — A, B, C stay completely silent.**

That's the ledger working: none of the three asked for `name`, so none of them gets told. With Context, every component reading that context would have re-rendered — Context hands everyone the whole value. Here, only the ones who asked for *what changed* do.

### The Opposite Test — Grab the Whole Box

Now prove the other side. In CounterA, delete the two selector lines and replace them with one:

```tsx
const { count, increment } = useCounterStore();
```

Look at the parentheses after `useCounterStore` — they're **empty, with no selector**. That means "give me the whole box," and then we pull `count` and `increment` out of it.

Yes — even though we only *use* two fields, we've subscribed to **everything**: decrement, reset, name, all of it. Click **Change name** again.

- **CounterA logs a re-render.** It subscribed to the whole box, so any change to anything inside wakes it up.
- **B and C stay quiet.** They still use selectors.

That's the whole lesson in one test. **The rule: always use a selector — ask only for what the component needs.** Undo that change in CounterA, putting back the two selector lines, and remove the console.logs.

## Zustand vs Context — Comparison

| Feature | Context API | Zustand |
|---------|-------------|---------|
| **Provider needed** | Yes — must wrap component tree | No — store is independent |
| **Selective re-renders** | No — any field change wakes every consumer | Yes — only components whose selected slice changed |
| **Boilerplate** | 30–40 lines per context | 10–15 lines per store |
| **Multiple stores** | Multiple providers = nesting nightmare | Multiple stores = independent, no nesting |
| **TypeScript** | Manual typing needed | Built-in generic `create<T>` |
| **Bundle size** | Built-in (0 KB) | ~1 KB (gzipped) |
| **Async actions** | Extra code needed | First-class support |
| **Persistence** | Manual (localStorage effect) | Built-in `persist` middleware |
| **Learning curve** | Minimal (but footguns later) | Minimal |

## Zustand Store Patterns

### Pattern 1 — Separate State and Actions

You can divide a store into two parts — state and actions — for readability:

```ts
interface AuthStore {
  // State
  user: User | null;
  isLoading: boolean;
  error: string | null;

  // Actions
  login: (email: string, password: string) => Promise<void>;
  logout: () => void;
}

const useAuthStore = create<AuthStore>((set) => ({
  user: null,
  isLoading: false,
  error: null,

  login: async (email, password) => {
    set({ isLoading: true, error: null });
    try {
      const res = await fetch("/api/login", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ email, password }),
      });
      if (!res.ok) throw new Error("Login failed");
      const user = await res.json();
      set({ user, isLoading: false });
    } catch (err) {
      set({
        error: err instanceof Error ? err.message : "Something went wrong",
        isLoading: false,
      });
    }
  },

  logout: () => set({ user: null }),
}));
```

**In the component — and this is where the selective-subscription rule gets tested:**

```tsx
function LoginForm() {
  // WRONG — no selector, so this subscribes to the WHOLE store:
  // const { login, isLoading, error } = useAuthStore();

  // RIGHT — one selector per piece:
  const login = useAuthStore((s) => s.login);
  const isLoading = useAuthStore((s) => s.isLoading);
  const error = useAuthStore((s) => s.error);
}
```

The destructured one-liner is tempting — and wrong. With no selector, the component subscribes to the entire store, so *any* field change (even one LoginForm never uses) re-renders it. That contradicts everything the selector sections above taught. If you want the convenience of one line, hand Zustand an object selector wrapped in `useShallow` (coming up under *How Zustand Works*) — but one selector per piece is the default habit.

**What is happening:**

| Thing | What It Is |
|-------|-----------|
| `login: async (email, password) => { ... }` | Async action — fetch logic lives inside the store itself |
| `set({ isLoading: true, error: null })` | Partial state update — only these values change |
| `set({ user, isLoading: false })` | Success — set user, stop loading |
| `set({ error: "...", isLoading: false })` | Error — set error, stop loading |

### Pattern 2 — Multiple Stores

You can create multiple stores — each independent, no nesting:

```ts
const useThemeStore = create<ThemeStore>((set) => ({ ... }));
const useAuthStore = create<AuthStore>((set) => ({ ... }));
const useCartStore = create<CartStore>((set) => ({ ... }));

// In a component:
function App() {
  const theme = useThemeStore((s) => s.theme);
  const user = useAuthStore((s) => s.user);
  const items = useCartStore((s) => s.items);

  // Selective subscriptions from each store
}
```

No "provider hell". Each store can live in a separate file, handling different logic. I personally recommend this approach for most apps — simple, predictable, and it aligns with Zustand's design philosophy.

### Pattern 3 — One Store with Slices

For large apps, you can put everything in one store with **slices** — separate functions that each handle a specific part of state. Here's the properly typed version (the `any`s you'll see in older examples would undermine this file's "with TypeScript" promise — this is the real typing):

```ts
// src/stores/appStore.ts
import { create, type StateCreator } from "zustand";

interface User {
  email: string;
}

interface UserSlice {
  user: User | null;
  login: (email: string) => void;
  logout: () => void;
}

interface ThemeSlice {
  theme: "light" | "dark";
  toggleTheme: () => void;
}

// Combined type — the store IS both slices
interface AppStore extends UserSlice, ThemeSlice {}

// Each creator receives AppStore's machinery, but only promises its own slice:
const createUserSlice: StateCreator<AppStore, [], [], UserSlice> = (set) => ({
  user: null,
  login: (email) => set({ user: { email } }),
  logout: () => set({ user: null }),
});

const createThemeSlice: StateCreator<AppStore, [], [], ThemeSlice> = (set) => ({
  theme: "light",
  toggleTheme: () =>
    set((state) => ({ theme: state.theme === "light" ? "dark" : "light" })),
});

// create<AppStore>()(fn) — the extra () is the form Zustand wants for
// composition: first call fixes the store's type, second passes the function
export const useAppStore = create<AppStore>()((...a) => ({
  ...createUserSlice(...a),
  ...createThemeSlice(...a),
}));
```

Read `StateCreator<AppStore, [], [], UserSlice>` as: "I live inside an `AppStore`, I apply no extra middleware, and I promise to only add `UserSlice`'s fields." The `...a` spread passes the same machinery (here, `set`) to every slice without losing the combined type.

For most apps, though — Pattern 2 (multiple stores) is enough. Reach for slices when one store genuinely must be shared and split by responsibility.

## Zustand Middleware — Persist

Zustand's `persist` middleware automatically syncs the store to localStorage — without any `useEffect`.

```ts
// src/stores/preferencesStore.ts
import { create } from "zustand";
import { persist } from "zustand/middleware";

interface PreferencesStore {
  theme: "light" | "dark";
  fontSize: number;
  setTheme: (theme: "light" | "dark") => void;
  setFontSize: (size: number) => void;
}

const usePrefStore = create<PreferencesStore>()(
  persist(
    (set) => ({
      theme: "light",
      fontSize: 16,
      setTheme: (theme) => set({ theme }),
      setFontSize: (fontSize) => set({ fontSize }),
    }),
    {
      name: "app-preferences", // localStorage key
    }
  )
);
```

Just wrap with `persist` and give it a `name`. The store now automatically syncs to localStorage — **serialization and rehydration are handled for you**: no `useEffect`, no `JSON.parse`/`stringify`, no `localStorage.getItem` by hand.

## How Zustand Works (Simple Understanding)

Zustand uses a **subscriber pattern** internally:

1. **Store creation** — define initial state + actions
2. **`useStore(selector)`** — component subscribes to a specific part of the store; the box notes it in the ledger
3. **`set()` call** — state changes
4. Zustand checks the ledger — which component asked for which value
5. **Only** components whose selected value actually changed — re-render

Step 4–5 is where the comparison happens, and one precision matters: Zustand's **default comparison is strict equality** — `Object.is` — on the selector's **output**. It is *not* a shallow comparison by default. Shallow comparison only happens if you **opt in** with `useShallow` (or the `shallow` function).

Why that matters: if your selector returns a **new object or array every time** —

```tsx
// Every render builds a fresh object → Object.is sees a new reference
// → re-renders even when nothing inside changed
const { login, isLoading, error } = useAuthStore(
  useShallow((s) => ({
    login: s.login,
    isLoading: s.isLoading,
    error: s.error,
  }))
);
```

— strict equality would treat it as changed on every render, and your component re-renders forever. `useShallow` compares the *fields* inside instead: same field values → no re-render. That's the honest fix for the "one line, many fields" style — selectors returning primitives (`s => s.count`) never need it.

This is also how selective re-rendering works without `React.memo`: if the selector's output is the same (`Object.is`), the re-render is skipped.

---

## What Zustand Is NOT

- **NOT a replacement for Context in every case:** If you have truly local state (form inputs, toggle states), `useState` is still better. Zustand is for **global** state that multiple components need.
- **NOT a server-state solution:** For API data caching, refetching, deduplication — TanStack Query is better. Zustand is for client state (UI state, user preferences, auth state).
- **NOT a Redux killer:** Redux has a different philosophy (immutable updates, middleware ecosystem, devtools). Zustand is simpler but Redux is more structured for very large teams — and Redux Toolkit remains the right call for big, many-developer codebases.
- **NOT heavy:** ~1 KB gzipped. The lightest state management library out there.

---

## So Here's the Takeaway

Zustand is simple: `create` a store, `set` to update, `useStore(selector)` to read. No provider, no boilerplate, no ladder. Selective subscription is built-in — the box keeps a ledger of who asked for what, and only wakes the components whose piece actually changed. Always use a selector; an empty `useStore()` subscribes to everything. The `persist` middleware handles localStorage sync for you. Multiple stores for separation of concerns; Redux Toolkit only when a big team needs strict structure.

## In Your Own Words

1. What are the three problems of Context API? How does Zustand solve them?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Three problems: (1) **One value, no partial listening** — when any field of the context value changes, every consumer re-renders, because Context has no selectors (it's not that all children re-render — only context consumers — but consumers can't pick just one field). Zustand fixes this with selectors: each component asks for only its piece, and the store's ledger only notifies those whose piece changed. (2) **Provider nesting** — every context adds a wrapper, and more state means a deeper ladder (provider hell). Zustand has no provider at all; the store lives outside React. (3) **Boilerplate** — interface, createContext, provider, value object with useMemo, custom hook with guard = 30–40 lines per context. A Zustand store is 10–15 lines.

</details>

2. In Zustand's `set` function, what happens when you return a partial object? How is this different from Redux reducers?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Zustand's `set` does a **shallow merge**. `set({ isLoading: true })` only changes the `isLoading` property; all other properties remain unchanged. In Redux, you have to manually spread: `{ ...state, isLoading: true }`. Zustand's merge behavior is similar to React's `setState`. This makes the code shorter — you only write the properties you want to change, everything else is automatically preserved.

</details>

3. How does selective subscription work in Zustand? What is the difference between `useStore(selector)` and `useStore()`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `useStore(selector)` — the component subscribes only to the output of the selector function. For example, `useStore((s) => s.count)` — the component only re-renders when `count` changes. `useStore()` — without a selector — subscribes to the **entire store**: any property change triggers a re-render, even fields the component never uses (destructuring `const { login, isLoading } = useAuthStore()` with no selector does *not* subscribe to "just those" — it subscribes to everything). Best practice is to always use a selector — only take what the component needs. One caveat: if a selector returns a fresh object each time, wrap it in `useShallow`, since the default comparison is strict equality (`Object.is`).

</details>

4. What advantage does Zustand's `persist` middleware have over Context API for localStorage persistence?

<details>
<summary>Show Answer</summary>

**Sample Answer:** With Context API, you need manual code for localStorage persistence — `useEffect` with `localStorage.setItem`, initial state with `localStorage.getItem` + `JSON.parse`. This code repeats for every context. Zustand's `persist` middleware is a simple wrapper — just `persist(store, { name: "key" })` and everything is automatic: serialization and rehydration are handled for you. No hand-written parse/stringify, and persisting multiple stores is just as easy.

</details>

5. When should you use Context vs Zustand? And when does Redux Toolkit come in?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Use Context when: (a) you only have 1–2 global values, (b) they change infrequently (theme, locale), (c) the app is small and the extra dependency isn't justified. Use Zustand when: (a) you have frequently-updating global state, (b) selective re-renders matter, (c) you need multiple stores, (d) you need persistence, (e) you want to cut boilerplate — this is the default for most apps. Reach for **Redux Toolkit** when the app is *big* and many developers share it — hundreds of screens, 20+ people touching the same state — because its strict structure and devtools keep teams from stepping on each other. The deciding factor isn't code size; it's how many people work on it and how much you need rules.

</details>
