## Problem — Duplicate Logic Across Components

React's built-in hooks (`useState`, `useEffect`, `useRef`) are very powerful. But they are **generic** — they are not built for any specific use-case. You end up writing the same logic over and over in every component.

Real example. Remember in Batch 2, we built a Recipe Finder:

```tsx
function RecipeFinder() {
  const [recipes, setRecipes] = useState<Meal[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState("");

  async function fetchRecipes(query: string) {
    setIsLoading(true);
    setError("");
    try {
      const res = await fetch(`https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`);
      const data = await res.json();
      setRecipes(data.meals ?? []);
    } catch {
      setError("Something went wrong");
    } finally {
      setIsLoading(false);
    }
  }

  // ... UI
}
```

And in the Batch 2 To-Do App v2, the **same pattern** — loading, error, data states, try/catch/finally:

```tsx
function ToDoApp() {
  const [categories, setCategories] = useState<string[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState("");

  useEffect(() => {
    setIsLoading(true);
    fetch("/api/categories")
      .then(res => res.json())
      .then(data => {
        setCategories(data.categories);
        setIsLoading(false);
      })
      .catch(() => {
        setError("Failed to load categories");
        setIsLoading(false);
      });
  }, []);
}
```

Notice? **Three states** — `data`, `isLoading`, `error` — plus a `fetch` call. This pattern repeats in every app. And even within a single app, it can appear in multiple places. The code is being duplicated.

**Another example** — localStorage. In To-Do apps, tasks are saved using localStorage:

```tsx
const [tasks, setTasks] = useState<Task[]>(() => {
  const saved = localStorage.getItem("tasks");
  return saved ? JSON.parse(saved) : [];
});

useEffect(() => {
  localStorage.setItem("tasks", JSON.stringify(tasks));
}, [tasks]);
```

This code also repeats in every project. Only the key name and data type change.

**Why is this a problem?** React is very flexible — you can follow any pattern you want. But this flexibility creates a problem: the "do it however you like" approach leads to inconsistent code, harder debugging, and more time for new developers to understand.

### Another Example — Common Patterns

Sometimes components contain common patterns that are not directly supported by any built-in hook:

1. **Toggle** — a boolean state that needs to be flipped (dark mode, modal, accordion)
2. **Document Title** — changing the page title on component mount
3. **Previous Value** — tracking the previous value of a prop or state
4. **Boolean Operations** — setTrue, setFalse, toggle all at once

These are things you end up writing over and over. The same `useState`, the same function definitions. The code becomes very repetitive.

If you are building a recipe app where 5 components make different API calls, every component has the same `useState` triplets (data, loading, error) plus try/catch/finally plus cleanup logic. The code becomes 3x longer unnecessarily.

Let's see how we solve this...

## Custom Hook — What Is It

**A custom hook is a JavaScript function that uses React hooks.** Nothing more. Just a function whose name starts with `use` and that calls `useState`, `useEffect`, `useRef`, or some other hook inside it.

Yes, it is that simple.

React's documentation says "custom hooks let you extract component logic into reusable functions." Which means — the logic from a component (that uses hooks) is extracted into a separate function, and that function can be reused in other components.

So the duplicate logic we saw above — extract it into a custom hook, and call that hook everywhere you need it. Write once, use everywhere.

Syntax:

```ts
function useHookName() {
  // You can use React hooks here
  // Return some value, array, or object
  return something;
}
```

That's it. No magic, no special API. Just a function convention.

**Why must the name start with `use`?** It is a React rule — hook names must start with `use`. This is how React knows that the function uses hooks, and React can enforce its internal rules (like — hooks cannot be conditional). This is not just convention — **the linter enforces it**. If a custom hook does not start with `use` and calls `useState`, ESLint will throw an error.

Visual mapping:

```
Component A            Component B
    │                      │
    ├── useToggle() ───────┤
    │                      │
    ▼                      ▼
[value, toggle]      [value, toggle]
      │                      │
   (A's own          (B's own
    state, different)     state, different)
```

And here is one very important point that beginners often misunderstand:

**What It Is NOT:** A custom hook does **not share state** between components. Each component that calls a custom hook gets its **own separate state**. A custom hook shares **logic**, not state. If you need to share state, you need tools like Context or Zustand (we will see this in 6.4). A custom hook only extracts the logic that you end up writing repeatedly — like toggle logic, fetch logic, localStorage logic.

## First Custom Hook — useToggle (Mini Project)

The simplest possible custom hook. A boolean state that needs to be "flipped". With this, we will build an **Accordion** (expand/collapse) component. We are not showing the entire project at once — **step by step, with each code block having a file path**.

First, let's understand one thing — **why do hooks return arrays** (Step 2). This is exactly the issue that `as const` solves — and you will see the problem arise in Step 3 and the solution in the same step.

> **Note:** Vite's default structure has `src/App.tsx` and `src/main.tsx`. The `hooks/` and `components/` folders must be **created by you**. Convention is — custom hooks in `hooks/`, reusable components in `components/`.

### Step 2 — Why Hooks Return Arrays

Before writing a hook, understand this. **Start with something familiar** — you have used `useState` so many times:

```tsx
const [count, setCount] = useState(0);
```

See that? `useState` returns an **array** where position 0 has the value (`count`), and position 1 has the setter function (`setCount`). Destructuring gives names to both. Each position has a **fixed type** — `[number, function]` — which TypeScript calls a **tuple**.

In Batch 1, we learned — a tuple means "fixed length, each position has a different type". A normal array is like `string[]` — all same type, any length. A tuple is like `[string, number]` — position 0 is string, position 1 is number.

This tuple pattern is a **convention in React** — custom hooks follow the same pattern: position 0 is state, position 1 is functions. So `useToggle` will also return an array. Moving to Step 3 — we will see why writing it this way causes a **problem** and how `as const` solves it.

### Step 3 — Create the Hook: src/hooks/useToggle.ts

Create the hook file first — but **intentionally wrong** (without `as const`), so you can see the problem yourself:

```ts
// src/hooks/useToggle.ts
// ❌ Wrong — TypeScript doesn't know it's a tuple
import { useState } from "react";

export function useToggle(initial = false) {
  const [value, setValue] = useState(initial);
  const toggle = () => setValue(v => !v);
  return [value, toggle];  // ❌ No `as const`
}
```

Now use it in a component — in Step 4 we will build the Accordion, but first let me show the error:

```tsx
// src/components/Accordion.tsx
// ❌ Error will occur
import { useToggle } from "../hooks/useToggle";

export function Accordion() {
  const [isOpen, toggleOpen] = useToggle(false);

  return (
    <div>
      <button onClick={toggleOpen}>  {/* ❌ Error here */}
        {isOpen ? "Close" : "Open"} Details
      </button>
      {isOpen && <p>This was hidden, now it is visible.</p>}
    </div>
  );
}
```

Error:

```
Type 'boolean | (() => void)' is not assignable to type 'MouseEventHandler<HTMLButtonElement> | undefined'.
  Type 'boolean' is not assignable to type 'MouseEventHandler<HTMLButtonElement>'.
```

**Understanding the error — array vs tuple inference:**

Without `as const`, TypeScript treats `[value, toggle]` as a **normal array**. A normal array means — any length, each element is either `boolean` **or** a function. Its type is:

```
(boolean | (() => void))[]
```

This means a **mixed box** — you put whatever you want in it, and you don't know what you will get out.

Now when the component destructures:

```tsx
const [isOpen, toggleOpen] = useToggle(false);
```

TypeScript pulls both variables out of the mixed box and gives them both the union type — `isOpen` is also `boolean | (() => void)`, `toggleOpen` is also `boolean | (() => void)`. Now TypeScript thinks `toggleOpen` could also be a boolean! And when you pass a boolean to `onClick` (which only accepts functions) — **error**.

**Understand with analogies:**

- **Normal array** = a mixed box. Everything is jumbled together. You don't know what you will pull out — number or string.
- **Tuple** = train reserved seats. Seat 0 always has a boolean, seat 1 always has a function. You know exactly what each seat gives you.

**Fix — add `as const`:**

```ts
// src/hooks/useToggle.ts
// ✅ Correct — with `as const`
import { useState } from "react";

export function useToggle(initial = false) {
  const [value, setValue] = useState(initial);
  const toggle = () => setValue(v => !v);
  return [value, toggle] as const;
}
```

`as const` tells TypeScript: "this is not a mixed box, this is a **fixed tuple** — position 0 is always `boolean`, position 1 is always `() => void`." Now with destructuring:

- `isOpen: boolean` ✅
- `toggleOpen: () => void` ✅

Error disappears. `onClick` now gets a guaranteed function.

| Code | What TypeScript Thinks |
|------|----------------------------|
| `return [value, toggle]` | `(boolean \| (() => void))[]` — mixed box, each element could be anything |
| `return [value, toggle] as const` | `readonly [boolean, () => void]` — fixed tuple, exact types per position |

**A question you might have — `useState` works fine without `as const`, why do we need it here?**

Because `useState`'s return type is **declared by the React team**. In TypeScript's type definitions, `useState` returns `[S, Dispatch<SetStateAction<S>>]` — a tuple. TypeScript already knows this from React's types.

But `useToggle` is **our** function. TypeScript doesn't know your intent — it saw `[value, toggle]` and assumed it's a normal array. So you have to tell it "this is a tuple" — by adding `as const`. **Whenever you write a custom hook that returns an array, always add `as const`.**

**Let's see what is happening in the final hook:**

| Line | What It Is |
|------|---------|
| `useState(initial)` | Default value is `false` (or whatever you pass) |
| `toggle = () => setValue(v => !v)` | Take the old value, flip it (true → false, false → true) |
| `return [value, toggle] as const` | Return array — value and toggle function |
| `as const` | Tells TypeScript "this is an exact tuple, not `(boolean \| (() => void))[]`" |

**Flow — When a Component Calls useToggle:**

```
Component render
    │
    ▼
useToggle(false) — first call
    │
    ├── useState(false) → value = false
    ├── toggle = () => setValue(v => !v)
    │
    ▼
return [false, toggle]
    │
    ▼
In component: const [isOpen, toggleOpen] = useToggle()
                    │              │
                    ▼              ▼
                  false          toggle()
                                    │
                              click → toggleOpen()
                                    │
                                    ▼
                           useToggle called again
                                    │
                            value becomes !false = true
                                    │
                                    ▼
                            return [true, toggle]
                                    │
                                    ▼
                            Component re-renders
```

## Second Custom Hook — useDocumentTitle

Changing the browser tab's title. Not complex — just a wrapper around `useEffect`.

Problem: you end up writing `useEffect` + `document.title` in every component. Three places, same code. Create a custom hook once.

Minimal code:

```ts
// src/hooks/useDocumentTitle.ts
import { useEffect } from "react";

export function useDocumentTitle(title: string) {
  useEffect(() => {
    document.title = title;
  }, [title]);
}
```

**What is happening:**

| Line | What It Is |
|------|---------|
| `title: string` | The title to set |
| `useEffect(() => { document.title = title }, [title])` | When `title` changes, update the title |
| **Return?** | Nothing — this hook does not return any value, it just performs a side effect |

The hook returns nothing — it just does its job. Custom hooks are not required to return anything.

Usage:

```tsx
// src/components/ProfilePage.tsx
import { useDocumentTitle } from "../hooks/useDocumentTitle";

export function ProfilePage({ username }: { username: string }) {
  useDocumentTitle(`${username}'s Profile`);

  return <div>...</div>;
}
```

```tsx
// src/components/SettingsPage.tsx
import { useDocumentTitle } from "../hooks/useDocumentTitle";

export function SettingsPage() {
  useDocumentTitle("Settings");

  return <div>...</div>;
}
```

Each page sets its own title, but the implementation lives in one place — `useDocumentTitle`. No `useEffect` is visible in the components. Clean.

**Without custom hooks:**

```tsx
function ProfilePage() {
  useEffect(() => {
    document.title = `${username}'s Profile`;
  }, [username]);
  // ...
}

function SettingsPage() {
  useEffect(() => {
    document.title = "Settings";
  }, []);
  // ...
}
```

Same `useEffect` pattern repeated. The custom hook made the **intention clear** — "set the title" in one line. The `useEffect` implementation is now hidden from the component.

## Third Custom Hook — usePrevious

Sometimes you need the **previous** value of something. Like — "count went from 5 to 6, but what was it before?" React does not have a built-in hook for this.

Solution? Custom hook:

```ts
// src/hooks/usePrevious.ts
import { useRef, useEffect } from "react";

export function usePrevious<T>(value: T): T | undefined {
  const ref = useRef<T>();

  useEffect(() => {
    ref.current = value;
  }, [value]);

  return ref.current;
}
```

**What is happening:**

| Line | What It Is |
|------|---------|
| `<T>` | Generic type — can be any type (number, string, object) |
| `useRef<T>()` | A ref to store the previous value |
| `useEffect(() => { ref.current = value }, [value])` | After each render, save the current value in the ref |
| `return ref.current` | During the **current** render, the ref still holds the **previous** value (because the effect runs after render) |

**Understand the flow:**

```
First Render: value = 5
    │
    ├── ref.current = undefined (initial)
    ├── return undefined
    │
    ▼
    useEffect runs → ref.current = 5
    │
    ▼
Second Render: value = 6
    │
    ├── ref.current = 5 (not updated yet)
    ├── return 5 ← this is the previous value!
    │
    ▼
    useEffect runs → ref.current = 6
    │
    ▼
Third Render: value = 10
    │
    ├── ref.current = 6
    ├── return 6 ← previous value!
```

Notice? `useEffect` runs **after** render, so when we return `ref.current` during render, the ref still holds the **previous render's** value. The current value hasn't been stored yet — that happens when the effect runs.

Usage:

```tsx
// src/components/Counter.tsx
import { useState } from "react";
import { usePrevious } from "../hooks/usePrevious";

export function Counter() {
  const [count, setCount] = useState(0);
  const prevCount = usePrevious(count);

  return (
    <div>
      <p>Now: {count}</p>
      <p>Before: {prevCount ?? "—"}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
    </div>
  );
}
```

Each click shows the current count as "Now" and the previous count as "Before". Without `usePrevious`, you would write the same `useEffect` + `useRef` pattern. Now it is one line.

## Fourth Custom Hook — useBoolean

Sometimes a simple toggle is not enough. You need more operations — `setTrue`, `setFalse`, `toggle`, `reset`. Like for modals, confirmation dialogs, tooltips.

`useToggle` only taught us to flip. `useBoolean` gives us more operations:

```ts
// src/hooks/useBoolean.ts
import { useState, useCallback } from "react";

export function useBoolean(initial = false) {
  const [value, setValue] = useState(initial);

  const setTrue = useCallback(() => setValue(true), []);
  const setFalse = useCallback(() => setValue(false), []);
  const toggle = useCallback(() => setValue(v => !v), []);
  const reset = useCallback(() => setValue(initial), [initial]);

  return { value, setTrue, setFalse, toggle, reset };
}
```

Notice we used `useCallback` — so the functions are not recreated on every render. Important for performance (we learned this in Batch 5).

Usage:

```tsx
// src/components/ConfirmationDialog.tsx
import { useBoolean } from "../hooks/useBoolean";

export function ConfirmationDialog() {
  const { value: isOpen, setTrue: open, setFalse: close } = useBoolean(false);

  return (
    <div>
      <button onClick={open}>Delete Item</button>
      {isOpen && (
        <div className="dialog">
          <p>Are you sure?</p>
          <button onClick={close}>Cancel</button>
          <button onClick={() => { /* delete */ close(); }}>Delete</button>
        </div>
      )}
    </div>
  );
}
```

Just from the names — `open` opens the modal, `close` closes it. The code is readable. And if you need to reset (like returning to initial state after a form submission), `reset` is available too.

## Rules of Custom Hooks

Custom hooks are React hooks — so the **Rules of Hooks** still apply:

| Rule | Meaning |
|------|--------|
| **Top-level call** | Do not call hooks inside loops, conditions, or nested functions |
| **Only in React functions** | Call hooks only inside React function components or custom hooks |
| **`use` prefix** | The custom hook name must start with `use` — otherwise the linter will complain |

**Why these rules?** React internally tracks hooks by their **call order**. Hooks must be called in the same order on every render. If you put a hook inside a condition, the call order could change between renders — React gets confused.

---

## When to Create a Custom Hook

Custom hook decision matrix:

| Scenario | Create Custom Hook? |
|----------|-------------|
| Unique logic in a single component | Don't keep it |
| Same pattern in two components | **Yes** — extract it |
| Pure UI abstraction (layout, styling) | Create a component, not a hook |
| Need to reuse stateful logic | Create a hook |
| Want to wrap a built-in hook | Create a hook |
| Used only once and not needed in the future | Don't create unnecessary abstraction |

Senior developers' rule: **"Rule of Three"** — if the same pattern appears three or more times, then create a custom hook. Creating one for one or two instances can be over-engineering. But for very common patterns (toggle, fetch, localStorage), even two instances is enough — because it will likely be used in more places.

---

## So Here's the Takeaway

A custom hook is a function that uses React hooks. It extracts logic, enables reuse, and keeps code clean. In the component, only **what** is visible, not **how**.

So far we have created simple hooks — `useToggle`, `useDocumentTitle`, `usePrevious`, `useBoolean`. These all work with specific types (boolean, string, number). But what if you need a generic hook that works with **any type**? Like `useFetch<T>` — fetch any data type? Or `useLocalStorage<T>` — save any type to localStorage?

We will see this in the next topic — **Generic Custom Hooks**.

1. What is the difference between a custom hook and a regular function? Do the React hook rules apply here?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A regular function is any JavaScript function that can do anything. A custom hook is also a function, but it **calls React hooks** (like `useState`, `useEffect`). That is why its name must start with `use` — so React knows it uses hooks and can enforce Rules of Hooks (top-level calls, no conditions, etc.). If you call `useState` inside a regular function (not a component or custom hook), React will error because it is not a React function.

</details>

2. Does a custom hook share state or logic between components? Give an example.

<details>
<summary>Show Answer</summary>

**Sample Answer:** A custom hook shares **logic**, not state. If two components call `useToggle()`, each gets its **own separate** `value` and `toggle` function. One component's toggle does not affect the other's state. If you need to share state, you need state management tools like Context API or Zustand. A custom hook only extracts code that you end up writing repeatedly — like toggle logic, fetch logic, localStorage logic.

</details>

3. In `usePrevious`, the value updates after render while the return happens during render. How does this work? What problem would arise if we used `useState` instead of `useRef`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The secret is the timing of the render cycle. `useRef` holds a mutable object throughout the component's lifetime, and `useEffect` runs **after** render. So when we return `ref.current` during render, it still holds the **previous render's** value. The current value gets stored when the effect runs afterward. If we used `useState` instead, state changes would trigger a re-render, creating an infinite loop — setState → render → setState → render...

</details>

4. What is the "Rule of Three"? When should you avoid creating a custom hook?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The "Rule of Three" means — if the same pattern appears three or more times, then create a custom hook. Creating one for one or two instances can be over-engineering — the cost of abstraction (extra file, extra indirection) may outweigh the benefits. Avoid creating a custom hook when: (a) the logic is unique to a single component, (b) abstraction is created just "in case it might be useful in the future", (c) the logic is UI/layout-related (a component is better than a hook).

</details>

5. How did the custom hook change the component's code? Give a specific example.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Without custom hooks, toggle logic was: `const [isOpen, setIsOpen] = useState(false); const toggle = () => setIsOpen(v => !v);` — two lines. With custom hook: `const [isOpen, toggle] = useToggle(false)` — one line. But the difference is more than just line count. The custom hook made the **intent clear** — `useToggle` describes exactly what we want. `useState` and the function definition are no longer visible in the component. The "how" (implementation) is hidden inside the hook, and the component only shows the "what" (intent). This makes the code readable, maintainable, and testable.

</details>
