This whole batch is about that. And the first tool is something you have been wishing for without knowing its name.

## Problem — Duplicate Logic Across Components

React's built-in hooks (`useState`, `useEffect`, `useRef`) are powerful but **generic** — they don't know what you're building. So the same wiring gets typed out again and again.

Picture five components in a recipe app, each hitting a different API endpoint. Different URLs, different UI — but every single one needs the same three states:

```tsx
function Recipes() {
  const [recipes, setRecipes] = useState<Meal[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState("");

  async function fetchRecipes(query: string) {
    setIsLoading(true);
    setError("");
    try {
      const res = await fetch(`https://api.example.com/recipes?q=${query}`);
      const data = await res.json();
      setRecipes(data.meals ?? []);
    } catch {
      setError("Something went wrong");
    } finally {
      setIsLoading(false);
    }
  }

  // ... UI
}
```

Copy that block into component two, three, four, five. Only the URL changes. (The Recipe Finder and To-Do app from earlier batches are full of exactly this pattern — but you don't need them to see the problem.)

Same story with localStorage. Every project that persists data reads on mount and writes on change:

```tsx
const [tasks, setTasks] = useState<Task[]>(() => {
  const saved = localStorage.getItem("tasks");
  return saved ? JSON.parse(saved) : [];
});

useEffect(() => {
  localStorage.setItem("tasks", JSON.stringify(tasks));
}, [tasks]);
```

Only the key name and the data type change between projects.

**Why it hurts:** find a bug in the fetch handling → fix it in five places, forget the sixth. New developer joins → reads the same block five times. Five places to keep in sync, forever.

And it's not just fetch and localStorage. Common patterns with no built-in hook keep showing up:

1. **Toggle** — a boolean that flips (accordion, modal, dark mode)
2. **Document title** — set the browser tab title for the current page
3. **Previous value** — what did this prop/state hold on the last render?
4. **Boolean operations** — setTrue, setFalse, toggle, reset as named actions

Same `useState`, same helper functions, typed out component after component.

There has to be a way to write this logic **once**...

## Custom Hook — What Is It

**A custom hook is a JavaScript function that uses React hooks.** That's the whole definition. A function whose name starts with `use`, that calls `useState`, `useEffect`, `useRef`, or another hook inside it.

```ts
function useSomething() {
  // React hooks are allowed in here
  // return whatever the caller needs
  return something;
}
```

No special API, no config, no registration. Just a function that follows one naming rule.

**Why must the name start with `use`?** Two audiences, one prefix:

1. **The linter.** `eslint-plugin-react-hooks` uses the prefix to recognize "this function is allowed to call hooks" — and flags violations when hooks appear in plain functions, loops, or conditions. React's real rule (next section) is about call order; the prefix is how tooling spots who's allowed to call what.
2. **Humans.** `useToggle` reads as "a hook that toggles" before you open the file. The name is the documentation.

One precision: React itself doesn't check names at runtime. The prefix is a signal that tooling enforces, sitting on top of React's actual machinery. The rule is real; the enforcement is split between the linter and React's call-order matching.

React's own docs put it as: *"custom hooks let you extract component logic into reusable functions."* The duplicate logic from the last section — extract it into a hook, call it wherever you need. Write once, use everywhere.

Visual mapping — two components, one hook, separate states:

```
Component A            Component B
    │                      │
    ├── useToggle() ───────┤
    │                      │
    ▼                      ▼
[value, toggle]      [value, toggle]
      │                      │
  (A's own state)       (B's own state)
```

---

## What It Is NOT — Shares Logic, Not State

The single most common misconception, so it gets its own section.

**A custom hook shares logic, not state.**

If Component A and Component B both call `useToggle()`, each call creates its **own** `value` and its **own** `toggle`. Flip A's — B doesn't notice. There is no hidden channel between them.

Why? Because a custom hook is built out of `useState` and friends — and you already know how those behave: every component that calls `useState` gets a fresh slot. The hook is only a way of *grouping* those calls into one named function; nothing in that grouping shares anything across components.

The same rule applies even harder *inside one component*: call `useBoolean` twice in the same file and you get two independent booleans. You'll hit this as a real bug in 6.1.3 — one call wired to two features, and toggling one toggled the other.

If two components genuinely need to share the **same** value (theme, cart, auth), that's a different job — Context, Zustand, or Redux. We'll get there in 6.4. A custom hook is for reusing the *code*, not the *data*.

## Rules of Custom Hooks

Custom hooks are hooks, so the **Rules of Hooks** apply to them fully:

| Rule | Meaning |
|------|---------|
| **Top-level only** | Never call a hook inside a loop, condition, or nested function |
| **React functions only** | Call hooks only from React function components or other custom hooks |
| **`use` prefix** | Name must start with `use` — the linter uses this to enforce the first two |

**Why does call order matter?** React doesn't identify hooks by name. It identifies them by the **order they're called in**.

Each component has an internal list of hook slots. On the first render, React sees your calls in order: the first `useState` goes in slot 1, the second in slot 2, the `useEffect` in slot 3, and so on. On every re-render, React walks through the component again and matches each hook call to its slot **by position**.

So the order must be identical on every render. Put a hook inside an `if`, a loop, or a nested function, and on some renders that call gets skipped or runs a different number of times — everything after it shifts, and React hands the wrong state to the wrong variable, or throws.

Interview one-liner: *"React tracks hooks by call order, not by name, so hooks must run in the same order on every render. Conditions, loops, and nested functions can change that order and break the mapping."*

You'll meet a real version of this mistake while building `useDocumentTitle` in 6.1.2 — a `useEffect` tucked inside a helper function. It can even *look* like it works, which is exactly what makes it dangerous.

## When to Create a Custom Hook

Not every repeated line deserves extraction. Two questions:

**1. Is it logic or UI?**
- Reusing how something *looks* (a card with border and title) → **component**
- Reusing *stateful logic* (fetch handling, toggle, persistence) → **hook**

**2. How many times has it actually repeated?** — the **Rule of Three**:

| Times seen | Action |
|------------|--------|
| Once | Leave it inline |
| Twice | Tolerate it (or extract if the pattern is very common) |
| **Three times** | **Extract into a custom hook** |

Why wait? A hook created too early is over-engineering: an extra file, an extra layer to read, and you often guess the wrong shape before you've seen how the logic is really used. Wait for real repetition.

**The exception:** very common patterns — toggle, fetch, localStorage — where two copies is enough, because you already know you'll need it a third time.

Decision matrix:

| Scenario | Create a hook? |
|----------|----------------|
| Unique logic, one component | No |
| Same pattern in two components | Yes (or wait for the third, per Rule of Three) |
| Pure UI/layout reuse | No — component |
| Reusing stateful logic | Yes |
| Wrapping a built-in hook with a better name or shape | Yes |
| "Might need it someday" | No — wait for real repetition |

## In Your Own Words

1. What is the difference between a custom hook and a regular function? Do the Rules of Hooks apply to it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A regular function is any JavaScript function — it can do anything, but it cannot call hooks. A custom hook is also a function, but it *calls* React hooks (`useState`, `useEffect`, ...) inside it. That's why its name must start with `use`: the linter uses the prefix to recognize it as a function that's allowed to call hooks, and to flag hooks called in the wrong places. Yes, the Rules of Hooks fully apply to custom hooks — because a custom hook is made of hooks: top-level calls only, same order every render, only called from components or other hooks. If you call `useState` inside a plain non-hook function, React throws an error — there's no component to own that state and no guaranteed call order.

</details>

2. Does a custom hook share state or logic between components? Give an example.

<details>
<summary>Show Answer</summary>

**Sample Answer:** A custom hook shares **logic**, not state. If two components both call `useToggle()`, each call creates its own separate `value` and `toggle` — flipping one doesn't affect the other. The same applies twice in one component: call `useBoolean` twice and you get two independent booleans. This works because the hook is built out of `useState`, and every `useState` call gets a fresh slot per component per render — the hook only groups those calls into one named function. If you actually want components to share the same value (theme, cart), you need Context, Zustand, or Redux — not a custom hook.

</details>

3. What is the "Rule of Three"? When should you avoid creating a custom hook?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The Rule of Three: if the same pattern appears three times, extract it into a custom hook. One copy stays inline; two you can tolerate; the third repetition is the signal. Avoid creating a hook when: (a) the logic lives in only one component — the hook just adds an extra file and layer for nothing; (b) you're creating it "just in case" you might need it later — that's guessing, and you often guess the wrong shape; (c) what you're reusing is how something *looks* — that's a component, not a hook. Exception: very common patterns like toggle, fetch, or localStorage, where even two copies is enough because you already know a third is coming.

</details>

4. Why does React track hooks by call order instead of by name? What breaks if a hook sits inside a condition?

<details>
<summary>Show Answer</summary>

**Sample Answer:** React matches each hook call to an internal slot by its position in the call sequence — the first call gets slot 1, the second slot 2, and so on — and it does this on every render. If a hook sits inside an `if`, on renders where the condition is false that call is skipped, so every hook after it shifts up one slot. React then hands the wrong state to the wrong variable, or throws. Tracking by name wouldn't help either, because names can be aliased, shadowed, or called through wrappers — position is the only thing React can match reliably across renders. That's also why the `use` prefix matters: it's how the linter knows to flag these placements before React crashes at runtime.

</details>
