## Where We Left Off

Three hooks in: `useToggle` taught extraction and tuples, `useDocumentTitle` taught side-effect-only hooks and top-level calls, `usePrevious` taught the render-reads / effect-writes timing trick. Last one — `useBoolean` — and it starts with a bug you can reproduce in ten seconds.

---

## The Problem — Flip Is Not Enough

`useToggle` flips: true ↔ false, whatever the state was. Fine for an accordion — flip is all an accordion ever does.

Now a confirmation dialog:

- **Delete Item** → should *open* the dialog. Always. Even if it's somehow already open.
- **Cancel** → should *close* it. Always.
- **Yes** → run the delete, then close.

Wire the buttons to a flip and try it: click Delete Item (opens), click Delete Item again — **it closes.** A button labeled "Delete Item" just toggled your dialog shut. The flip doesn't know *intent* — it only knows "do the opposite of whatever the state is."

For modals, dialogs, tooltips, you want separate, clearly named actions:

- `setTrue` — always open
- `setFalse` — always close
- `toggle` — flip (still right for switches and accordions)
- `reset` — back to the starting value (useful when the initial isn't `false`, or a form dialog should clear itself on close)

That's `useBoolean`.

---

## Plain First — ConfirmationDialog with useState

Same approach as the Accordion: write it plain, feel the bug, then extract.

```tsx
// src/components/ConfirmationDialog.tsx
import { useState } from "react";

export function ConfirmationDialog() {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div>
      <button onClick={() => setIsOpen(true)}>Delete Item</button>
      {isOpen && (
        <div>
          <p>Are you sure you want to delete this?</p>
          <button onClick={() => setIsOpen(false)}>Cancel</button>
          <button
            onClick={() => {
              console.log("deleted");
              setIsOpen(false);
            }}
          >
            Yes
          </button>
        </div>
      )}
    </div>
  );
}
```

Notice: with plain state you naturally reached for `setIsOpen(true)` and `setIsOpen(false)` — real sets, not flips. Click Delete Item twice: it stays open. Correct behavior, already — you just wrote the logic of `useBoolean` by hand.

Render it in `App.tsx` and click through: Delete opens, Cancel closes, Delete again still open, Yes logs "deleted" and closes.

## The Hook

```ts
// src/hooks/useBoolean.ts
import { useState } from "react";

export function useBoolean(initial = false) {
  const [value, setValue] = useState(initial);

  const setTrue = () => setValue(true);
  const setFalse = () => setValue(false);

  return { value, setTrue, setFalse };
}
```

| Line | What it does |
|------|--------------|
| `initial = false` | Starting value — passed in, defaults to `false` |
| `useState(initial)` | The live boolean. Named `value` because the hook doesn't know what it's for |
| `setTrue` / `setFalse` | Named actions — no flip, no guessing |
| `return { ... }` | An **object**, not an array — see the next section |

Usage:

```tsx
// src/components/ConfirmationDialog.tsx
import { useBoolean } from "../hooks/useBoolean";

export function ConfirmationDialog() {
  const { value: isOpen, setTrue: open, setFalse: close } = useBoolean(false);

  return (
    <div>
      <button onClick={open}>Delete Item</button>
      {isOpen && (
        <div>
          <p>Are you sure you want to delete this?</p>
          <button onClick={close}>Cancel</button>
          <button
            onClick={() => {
              console.log("deleted");
              close();
            }}
          >
            Yes
          </button>
        </div>
      )}
    </div>
  );
}
```

`value: isOpen` — "take the property called `value` from the object, call it `isOpen` in this component." The hook stays generic; the component knows it's a dialog, so the component picks the name. Same for `setTrue: open` and `setFalse: close` — the JSX now reads `onClick={open}` and `onClick={close}`, almost like plain English.

Delete Item twice → stays open. The names say what they mean: `open` only ever opens.

For the Yes button: `setFalse` (aliased as `close`) is the right call — your intent is "close the dialog," and the name says exactly that. `reset` would also work here (the start value is `false`), but the name would make a reader wonder *what* is being reset. `reset` earns its keep when the starting value isn't obvious — a hook created with `true` as the start, or a form dialog where closing should also wipe the fields back to defaults.

## Array or Object — When to Use Which

You've now seen both return shapes across this batch:

| | `useToggle` | `useBoolean` |
|---|---|---|
| Returns | `[value, toggle] as const` | `{ value, setTrue, setFalse }` |
| Naming | Caller picks: `const [isOpen, toggle] = ...` | Hook fixes names, caller renames: `const { value: isOpen } = ...` |
| Best when | 2 things — order is easy to remember | 3+ things — order becomes impossible |

With two items, position is memorable — everyone knows value-first, function-second; it's the `useState` shape you've written a hundred times. With four (`value, setTrue, setFalse, toggle`), every caller must destructure in *exactly* that order even if they only want the last one — get one position wrong and you're calling a boolean as a function. Objects let the caller pull only what they need, in any order, and ignore the rest completely.

Rule of thumb: **small fixed pair → array; named set of actions → object.**

You can add the rest of the actions when a real use case appears — `toggle` for a dark-mode switch where flipping is right, `reset` for the form dialog above. Same lesson as the Rule of Three from 6.1, applied *inside* a hook: don't ship actions nobody calls.

## The Bug — One Hook, Two Purposes

Add a dark-mode toggle to the same component, reusing the same call:

```tsx
// ❌ Both features wired to ONE boolean
const { value: isOpen, setTrue, setFalse, toggle } = useBoolean(false);

<button onClick={toggle}>{isOpen ? "Dark" : "Light"}</button>
// ...and the dialog also reads isOpen
```

Click the theme button — the confirmation dialog opens too. One `useBoolean` call = one boolean; both features are attached to it, so toggling one toggles the other.

The fix is **not** to change the hook. Call it twice:

```tsx
const { value: isOpen, setTrue: open, setFalse: close } = useBoolean(false);
const { value: isDark, toggle: toggleTheme } = useBoolean(false);
```

Two calls, two independent booleans. The dialog's state and the theme's state never touch each other. That's the "shares logic, not state" rule from 6.1 — now you've hit it as a real bug instead of reading it in a diagram, which is why it'll stick.

Naming helped the bug happen, too: `isOpen` described the dialog, and reusing it for the theme is what let the confusion creep in. Name each call for its purpose and the two stay apart on their own.

## So Here's the Takeaway

A custom hook is a function that uses React hooks. It extracts logic, enables reuse, keeps components clean — **what** in the component, **how** in the hook.

Four hooks, four lessons:

| Hook | What it taught |
|------|----------------|
| `useToggle` | Extraction mechanics, tuples, `as const` |
| `useDocumentTitle` | Side-effect-only hooks, top-level calls |
| `usePrevious` | Render-reads / effect-writes timing, `useRef` |
| `useBoolean` | Named actions, object returns, one call = one state |

All four are **specific** — boolean, string, number. But the real world wants `useFetch` that works with *any* response type, and `useLocalStorage` that persists *any* data. That needs TypeScript generics — the next topic, **6.2 Generic Custom Hooks**.
