### 31. What are Pure Components?

**Answer:** `React.PureComponent` (class) or `React.memo` (function) — they skip re-rendering when props/state are **shallowly** equal. A performance tool, but it silently fails when props are inline objects/functions, because those create new references every render.

**Likely follow-up:** *When does memo do nothing?* — when the parent passes `{...}` or `() => {...}` inline; fix by memoizing those values with `useMemo`/`useCallback`.

---

### 42. What does `useMemo` do?

**Answer:** Memoizes (caches) the result of an expensive computation and only recomputes when its dependencies change — e.g. filtering 10k rows doesn't re-run on every unrelated render.

**Likely follow-up:** *When should you NOT use it?* — cheap computations; memoization itself costs (memory + dependency comparison).

---

### 43. What does `useCallback` do?

**Answer:** Memoizes a **function reference** — it returns the same function instance as long as dependencies haven't changed. Its main job is keeping a stable reference so `React.memo` children' shallow comparison actually passes.

**Likely follow-up:** *Why does the child care?* — a new function prop each render = "props changed" = memo defeated = unnecessary re-render.

---

### 44. Difference between `useMemo` and `useCallback`?

**Answer:** `useMemo` caches a computed **value**; `useCallback` caches a **function** reference. `useCallback(fn, deps)` is literally equivalent to `useMemo(() => fn, deps)` — same mechanism, different return.

**Likely follow-up:** *And `React.memo`?* — memo caches a **component render**; useMemo caches values; useCallback caches functions.

---

### 45. When should you use `useReducer`?

**Answer:** When state logic is complex — multiple related sub-values, or the next state depends on the previous state **and** an action (forms, carts, wizards). The reducer is a pure function, so transitions are predictable and trivial to test.

**Likely follow-up:** *vs `useState`?* — one or two simple values → `useState`; interdependent updates where ad-hoc setters tangle → `useReducer` (and it's the same pattern Redux uses, easing the move to a store).

---

### 49. What does `useTransition` do?

**Answer:** Marks a state update as **non-urgent** (a transition) so urgent updates like typing aren't blocked by it, and exposes an `isPending` flag to show a spinner while the transition completes.

**Likely follow-up:** *When?* — filtering a huge list as the user types: input stays responsive, the heavy filter runs as the transition.

---

### 50. What does `useDeferredValue` do?

**Answer:** Returns a "deferred" version of a value that updates with a slight delay — expensive renders (search results for a large dataset) use the stale deferred value for one frame while the urgent input stays current.

**Likely follow-up:** *vs `useTransition`?* — transition wraps the **update**; deferredValue wraps the **value** you pass down. Same priority idea, different API shape.

---

### 61. How do you optimize a React app from re-renders?

**Answer:** **Profiler first** (React DevTools highlight updates or `why-did-you-render`) — never guess. Then: `React.memo` for heavy children, `useMemo`/`useCallback` for unstable references, colocate state in the smallest component that needs it, virtualize giant lists, code-split heavy routes.

**Likely follow-up:** *What causes re-renders?* — state setter, new props, parent re-render (default), Context value change — and inline object/array/function props defeating memo.

---

### 62. Does a parent re-render always cause its child to re-render?

**Answer:** **Yes, by default** — children re-render whenever the parent does. `React.memo` stops it when props are shallowly equal; inline props (`[1,2,3]`, `() => {}`) create new references, so memo says "changed" and re-renders anyway.

**Likely follow-up:** *So the fix is?* — memoize the props (`useMemo` for the array, `useCallback` for the handler), then memo the child.

---

### 63. What is code splitting, and how do you do it?

**Answer:** Breaking the bundle into smaller chunks loaded on demand instead of shipping everything up front. `React.lazy(() => import('./Dashboard'))` wrapped in `<Suspense fallback={<Loader />}>` — route-level or component-level splitting cuts initial load time.

**Likely follow-up:** *Route-level vs component-level?* — routes split pages; component-level lazy-loads modals/heavy widgets on first open.

---

### 64. How do `React.lazy` and `Suspense` work together?

**Answer:** `lazy` turns a dynamic `import()` into a component; `<Suspense>` is the boundary that shows the fallback while that chunk is loading, then renders the component when it arrives.

**Likely follow-up:** *Is Suspense only for lazy loading?* — no — see Q102; in React 19 it also suspends on promises via `use()`.

---

### 65. What is list virtualization?

**Answer:** Rendering only the rows visible in the viewport instead of the whole list (via `react-window` etc.) — thousands of rows become a few dozen DOM nodes. Essential for large tables/feeds.

**Likely follow-up:** *When is it overkill?* — lists under a couple hundred simple rows; it adds scroll-offset complexity you don't need yet.

---

### 66. How do you debug unnecessary re-renders?

**Answer:** React DevTools Profiler (highlight updates) or `why-did-you-render`, or a simple render-count log in dev. Profile → find the wasteful component → colocate state or memoize → virtualize if it's a giant list, code-split if it's bundle size, cache with TanStack Query if it's refetching.

**Likely follow-up:** *Most common culprit?* — inline props (objects/arrays/functions) breaking shallow comparison, and Context value objects recreated every render.

---

### 67. What does the React Compiler (React 19) do?

**Answer:** A build-time tool that automatically applies memoization (`useMemo`/`useCallback`/`React.memo`) without you writing it — it analyzes components and generates re-render skipping, dramatically reducing manual memoization.

**Likely follow-up:** *Does that make Batch 5 obsolete?* — no; you still need to *understand* re-renders to place state correctly and avoid the traps the compiler can't fix (bad state placement, Context misuse).

---

### 69. What is the benefit of Concurrent Rendering?

**Answer:** React can interrupt, pause and resume render work by priority — high-priority updates (typing) don't block low-priority ones (rendering a large list), keeping the UI responsive. It's the foundation under `useTransition`, `useDeferredValue` and Suspense.

**Likely follow-up:** *Does it make rendering faster?* — no, it makes it *interruptible*; total work may be the same, but urgent work never waits behind it.

---

### 95. What are the traps of memoization in React?

**Answer:** Two: (1) inline objects/arrays/functions create new references each render, so shallow comparison always says "changed" and memo never works; (2) over-memoizing — adding `useMemo`/`useCallback` everywhere costs memory and comparison overhead without real benefit.

**Likely follow-up:** *Rule of thumb?* — memoize only when profiling shows a real hotspot; stabilize references first, blame React last.

---

### 102. Is Suspense only for lazy loading?

**Answer:** No — Suspense is also used for data fetching (libraries/frameworks that support it), and in React 19 it works with the `use()` hook to suspend on promises until they resolve. The fallback UI mechanism is shared across all of these.

**Likely follow-up:** *Can a component suspend during an event handler?* — no; suspension happens during render — event handlers must manage their own pending state.

---

### 114. What are common performance anti-patterns in React?

**Answer:** Creating new objects/arrays/functions during render (inline props), rendering huge lists without virtualization, Context re-rendering all consumers on every change, deeply nested state that re-renders the whole tree, and missing/wrong `key` strategy (index keys on dynamic lists).

**Likely follow-up:** *What's the general pattern behind all of them?* — either unstable references breaking memo, or state/updates that are wider than they need to be.
