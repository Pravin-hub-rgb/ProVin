## What We've Covered So Far

In 5.1, 5.2, and 5.3, we learned three hooks: `React.memo`, `useMemo`, and `useCallback`. In 5.4, we saw the React Compiler do all of that memoization for us automatically. So why build a project by hand now? Because automation is only trustworthy once you have watched what it automates. This project is deliberately built the manual way — every skip and every render visible, nothing hidden behind a compiler.

The idea is simple: an app that shows the render count for each component, so that the difference the Profiler shows is clearly visible.

`tailwindcss()` is a function call, sitting in the `plugins` array next to `react()` — and it needs the import at the top, or the name is not recognized.


## Step 1 — The Visualizer Component

First, let's create a helper component that tracks render counts. This will be used inside every component.

**Let's try the intuitive approach first — increment a counter on every render:**

```tsx
// ❌ Won't work
export default function RenderCount({ label }: { label: string }) {
  let count = 0
  count++ // Local variable — resets to 0 on every render
  return <p>{label} rendered: {count} times</p>
}
```

`let count = 0` is inside the component function — it resets to `0` on every render. `count++` is useless. The count will always show 1.

**Try a module-level variable — outside the component:**

```tsx
// ❌ React 19 error
const counts: Record<string, number> = {}

export default function RenderCount({ label }: { label: string }) {
  counts[label] = (counts[label] ?? 0) + 1 // Error!
  return <p>{label} rendered: {counts[label]} times</p>
}
```

React 19 throws an error: *"Modifying a variable defined outside a component is not allowed."* React wants components to stay **pure** during the render phase — only read props and state, don't perform any side effects.

**Try useRef — persistent storage inside the component:**

```tsx
// ❌ React 19 error
import { useRef } from 'react'

export default function RenderCount({ label }: { label: string }) {
  const count = useRef(0)
  count.current++          // Error: Cannot access refs during render
  return <p>{label} rendered: {count.current} times</p>
}
```

React 19: *"Cannot access refs during render."* `ref.current` can only be accessed in event handlers or effects — not during render.

**Try useEffect — increment after render:**

```tsx
// ❌ Infinite loop
import { useEffect, useState } from 'react'

export default function RenderCount({ label }: { label: string }) {
  const [count, setCount] = useState(0)

  useEffect(() => {
    setCount(c => c + 1) // Effect → setState → re-render → effect → ...
  })

  return <p>{label} rendered: {count} times</p>
}
```

`useEffect` runs after every render. `setCount` changes state → the component re-renders → the effect runs again → `setCount` is called again → **infinite loop**. React crashes.

**Quick refresher — `useRef`, since it is about to matter.** You have used `useRef` exactly once so far, for focusing an input (2.4): a box React keeps between renders, read and written through `.current`, whose change does **not** cause a re-render. That last property is what separates it from state, and it is worth the one-line revision now:

| | Survives re-renders? | Changing it causes a re-render? | Screen updates? |
|---|---|---|---|
| `useState` | yes | yes | yes |
| `useRef` | yes | no | not by itself |

Both remember values between renders. The decision question is: **do I want the screen to update when this value changes?** Yes → state. No → ref.

**Try the ref version — it works, but it lies:**

```tsx
// ⚠️ No loop, counts every render — but the display lags one step behind
import { useEffect, useRef } from 'react'

export default function RenderCount({ label }: { label: string }) {
  const count = useRef(0)

  useEffect(() => {
    count.current = count.current + 1
    console.log('rendered:', count.current)
  })

  return <p>{label} rendered: {count.current} times</p>
}
```

Run it and watch two screens at once — the UI and the console:

- **No infinite loop.** The effect runs after every render and bumps the ref; changing a ref causes no re-render, so nothing loops. The console number climbs with every click.
- **But the UI lags one step behind.** On first load the screen shows `0` while the console already shows `1`: the paragraph read the ref *during* render, while it was still `0`; the effect bumped it to `1` only *after* the screen was drawn; and nothing re-renders to show the new value. Click the App button once — the screen finally shows `1`, while the ref is already at `2`. The display always reads the value as it was at the moment of the last render, and the bump happens after.
- **A mystery number on first load:** with the dev server as-is, the console may show `1` and then `2` with zero clicks — and if you kept an empty `[]` after the effect, the count gets stuck at exactly `2` forever. That has one culprit: **StrictMode**, the next section.

So the ref version counts honestly in the background but cannot paint its own number — state loops, and a ref lags. That deadlock is what pushes us to the Profiler below. But first, the mystery number deserves its own answer.

## StrictMode — Why the Numbers Look Wrong in Development

Open `main.tsx` and look at what the Vite template wrapped your app in:

```tsx
<StrictMode>
  <App />
</StrictMode>
```

**StrictMode** is a development-only wrapper React gives you. Its job is to catch bugs early by deliberately running some things **twice**: component function bodies render twice, and on the first load each effect runs, cleans up, and runs again. If your code is written correctly, doubling changes nothing — you never notice. If something is wrong, the bug surfaces right away in development instead of hiding until production.

That explains the mystery exactly. The ref version's effect has no dependency array, so on mount StrictMode ran it twice — setup, cleanup, setup — and the ref went from `0` to `2` with zero clicks. That is why the console showed `1` then `2`, and why the count with an empty `[]` froze at `2`: the effect only ever ran once for real, but that once was doubled.

Two details worth knowing:

- **It only exists in development.** The production build runs everything once. When you saw the count jump by two on first load, that was the dev build doing its job.
- **The classic bug it catches:** an effect that starts a timer or opens a connection but never cleans up. StrictMode runs it twice, so you end up with two timers or two connections running at once — and you notice immediately. The fix is a **cleanup function**: return `() => clearInterval(...)` (or `socket.disconnect()`) from the effect, so each run undoes the previous one. Our RenderCount has no cleanup because a counter bumping a ref is harmless to double.

**Try the experiment once:** remove the `<StrictMode>` wrapper, reload — the console now shows exactly `1`, while the UI still shows `0` (that is the lag, unchanged). Then **put StrictMode back**. It catches real bugs in development, and you want it on in every real project.

And one tempting fix that is not a fix: starting the ref at `1` instead of `0` makes the first render's display look right, but the screen would still lag one step behind on every later render. It patches one symptom and leaves the cause untouched.

---

Mystery solved — but it does not change the deadlock: state loops, and a ref lags. So how do you track render counts in React 19?

First, understand this: React's rendering happens in **two phases**.

### Phase 1: Render Phase (Creating the Blueprint)

When your component function is called and JSX is returned — React decides "what needs to change."

This is where **no side effects** (modifying variables, API calls, `console.log`) are allowed. React wants this phase to be **pure** — just read props/state and produce JSX.

If you modify a module-level variable during the render phase, React throws an error: *"Modifying a variable defined outside a component is not allowed."*

### Phase 2: Commit Phase (Actual Construction)

React has decided what needs to change. Now it updates the actual DOM. This is where side effects are allowed — `useEffect` runs here, and `Profiler`'s `onRender` callback runs here too. Render phase: calculate changes (no side effects). Commit phase: apply changes to DOM (side effects allowed).

### The Solution

React has a built-in `Profiler` component with an `onRender` callback that fires in the **commit phase** — meaning the blueprint has already been drawn and actual construction is underway. You can safely modify module-level variables here:

```tsx
// ✅ React 19 compatible
import { Profiler } from 'react'

const counts: Record<string, number> = {}

export default function RenderCount({ label }: { label: string }) {
  return (
    <Profiler id={label} onRender={() => { counts[label] = (counts[label] ?? 0) + 1 }}>
      <div className="text-xs text-gray-400 mb-1">
        {label} rendered: {counts[label] ?? 0} times
      </div>
    </Profiler>
  )
}
```

Here's why no error is thrown:

| Step | Which Phase | What's happening |
|------|-------------|------------------|
| 1️⃣ | **Render** | Component function is called → `<div>` is evaluated → `{counts[label] ?? 0}` is **read** (not modified) ✅ |
| 2️⃣ | **Commit** | React inserts `<div>` into the DOM → `onRender` fires → `counts[label]++` is **modified** ✅ |

Two different phases — read during render, write during commit. React is happy.

And it stays honest even with StrictMode back on. StrictMode renders the component function twice, but **commits once** — a double render does not produce a double commit — so `onRender` fires exactly once per real screen update, in dev and in production alike. That is the whole reason the Profiler wins where the ref version wobbled: its count is accurate no matter what the development build is doing.

A word on what the Profiler actually is, because we are borrowing it for a non-obvious purpose. It is React's built-in **measuring tool** — think of a stopwatch strapped to a component. Wrap it around anything, and every time React updates that part of the screen it reports back with numbers: its normal use is finding the slow parts of an app. The `onRender` callback receives those numbers as parameters — `id` (the name you gave it), `phase` (`"mount"` on the first render, `"update"` after), and `actualDuration` (how long the render took):

```tsx
// The measuring use — play with it once, then switch back to counting
<Profiler
  id={label}
  onRender={(id, phase, actualDuration) => console.log(id, phase, actualDuration)}
>
```

Run that version and you will see `Sidebar mount 1.2`-style lines in the console.

It connects to what you already know from Module 0: the render phase is where React calls your components and builds the new Virtual DOM, reconciliation compares it against the old tree to find what changed, and the **commit** is when React applies those changes to the real DOM. `onRender` fires right after that commit — the moment React actually did the work, which is exactly the moment a render counter wants to count.

Two boundaries: you could technically run any code inside `onRender`, but it is a measuring callback, not a general-purpose hook — data fetching belongs in `useEffect` or a data library. And it is not a substitute for React DevTools' Profiler tab (used at the end of this file) — one is a component in your code, the other is a browser tool; they share only the name.

**One small caveat — the display lags one step behind.** The paragraph reads the count *during* render, but the commit's increment happens *after* the screen is drawn. So on first load you see `0` (the count is already `1`), and after the first click you see `1` (the count is already `2`) — the number shown is always accurate for the commits completed *before* the current render, and it catches up on the next one. For a dev tool whose real signal lives in the console and the climbing pattern, that one-step lag costs nothing — the counts stop climbing when memo works, and that is the part you watch.

## Step 2 — Showing the Problem (Without Optimization)

Let's build the version without any optimizations first, so the problem is clearly visible:

```tsx
// App.tsx
import { useState } from 'react'
import RenderCount from './RenderCount'

function ExpensiveCard({ value }: { value: number }) {
  return (
    <div className="border p-4 rounded">
      <RenderCount label="ExpensiveCard" />
      <p>Value: {value}</p>
    </div>
  )
}

function Sidebar() {
  return (
    <div className="border p-4 rounded bg-gray-50">
```

- `ExpensiveCard` — value didn't change, yet it's re-rendering
- `Sidebar` — nothing changed, yet it's re-rendering

## Step 3 — Add React.memo

Let's memoize `Sidebar` first — it has no props, so it should never re-render:

```tsx
// App.tsx
import { memo } from 'react'

const Sidebar = memo(function Sidebar() {
  return (
    <div className="border p-4 rounded bg-gray-50">
      <RenderCount label="Sidebar" />
      <p>Sidebar — nothing changes here</p>
    </div>
  )
})
```

Now let's also memoize `ExpensiveCard`:

```tsx
// App.tsx
interface ExpensiveCardProps {
  value: number
}

const ExpensiveCard = memo(function ExpensiveCard({ value }: ExpensiveCardProps) {
  return (
    <div className="border p-4 rounded">
      <RenderCount label="ExpensiveCard" />
      <p>Value: {value}</p>
    </div>
  )
})
```

**Two real mistakes made while wrapping `Sidebar` — both produce confusing errors if you hit them:**

```tsx
// ❌ import type { memo } from 'react'
```
`import type` imports only the *type* of a name, not the actual value — and `memo` is a function you call, not a type. TypeScript treats `import type { memo }` as "I only promise to use this in type positions", so calling it errors out. `memo` is a real function — plain `import { memo } from 'react'`.

```tsx
// ❌ export default memo(<SideBar />)
```
`memo` receives the **component itself**, not a rendered tag. `<SideBar />` is already a React element — the rendered output. `memo(SideBar)` hands over the function so memo can guard its future renders. If you find yourself passing JSX into `memo`, you have gone one step too far.

**What you observe after this step:** click "Re-render App" — the Card's count stops climbing while the App's climbs. `Sidebar`'s count may look stuck at `0` the whole time — that is not memo failing, that is the one-step lag: Sidebar never re-renders again, so its display never gets a chance to refresh. The count object behind it did tick to `1` on the mount commit. A frozen display here is actually the success sign.

Test now:

- First render — all render once
- Click "Re-render App" — only `App` renders. `ExpensiveCard` and `Sidebar` are skipped. See it? `value` didn't change, so memo skipped the render.
- Click "Change Value" — `App` re-renders, `ExpensiveCard` re-renders (because `value` changed), `Sidebar` is skipped.

## Step 4 — The Problem — Inline Function Breaks Memo

Now let's add an `onClick` prop to `ExpensiveCard` — like a real app would have event handlers. We see the full component here — along with the problem it creates:

```tsx
// App.tsx
import { memo, useState } from 'react'
import RenderCount from './RenderCount'

const ExpensiveCard = memo(function ExpensiveCard({
  value, onClick
}: {
  value: number
  onClick: () => void
}) {
  return (
    <div className="border p-4 rounded">
      <RenderCount label="ExpensiveCard" />
      <button
        onClick={onClick}
        className="bg-red-500 text-white px-4 py-2 rounded m-2 cursor-pointer"
      >
        Expensive Card Click
      </button>
      <p>Value: {value}</p>
    </div>
  )
})

export default function App() {
  const [count, setCount] = useState(0)
  const [value, setValue] = useState(42)

  const handleClick = () => {                // ❌ New function on every render
    console.log('card clicked')
  }

  return (
    <div className="p-8 space-y-4">
      <RenderCount label="App" />

      <div className="space-x-2">
        <button onClick={() => setCount(c => c + 1)}>
          Re-render App ({count})
        </button>
        <button onClick={() => setValue(v => v + 1)}>
          Change Value ({value})
        </button>
      </div>

      <ExpensiveCard value={value} onClick={handleClick} />
      <Sidebar />
    </div>
  )
}
```

A bug from the first draft of this code, worth keeping visible: `onClick` sat on **both** the outer `<div>` and the inner `<button>`. Browser events **bubble** — a click on the button also travels up through every ancestor element — so one click ran `handleClick` twice (two console lines). The fix: keep the handler on the button only, as the code above now shows.

Click "Re-render App" — `ExpensiveCard` is re-rendering again! `Sidebar` is fine (nothing changed about it) but `ExpensiveCard`'s memo broke.

**Why?** `handleClick` is a regular function defined inside `App()`. Every time `App` re-renders, a new `handleClick` function is created in memory. New reference = new `onClick` prop = `Object.is(oldFn, newFn)` → false → memo re-renders.

Memo only skips the render when props have the **same** reference. Inline functions get a new reference on every render — memo is useless.

---

## Step 5 — Fix with useCallback

```tsx
// App.tsx
import { useCallback } from 'react'

const handleClick = useCallback(() => {
  console.log('card clicked')
}, []) // No dependencies — never changes
```

Test now — `ExpensiveCard` stops re-rendering. The function reference is stable.

## Step 6 — useMemo — Caching Derived Data

Now let's add a heavy calculation — a function that takes a lot of time:

```tsx
// App.tsx
function slowCalculation(num: number): number {
  console.log('⚡ slow calculation is running')
  let result = 0
  for (let i = 0; i < 10000000; i++) {
    result += num * i
  }
  return result
}

function App() {
  const [count, setCount] = useState(0)
  const [value, setValue] = useState(42)

  const computed = slowCalculation(value) // ❌ Runs on every render

  return (
    // ...
    <p>Computed: {computed}</p>
    // ...
  )
}
```

Every time "Re-render App" is clicked, `slowCalculation` runs — even though `value` hasn't changed. The browser freezes.

Fix with useMemo:

```tsx
const computed = useMemo(() => slowCalculation(value), [value])
```

Now `slowCalculation` only runs when `value` changes. Count change → cached result is used — and the freeze on count clicks is gone.

Four details worth pinning down from this step:

**The function sits above `App`, at module level.** A function defined inside `App()` would be rebuilt on every render — harmless, but pointless for something this heavy. Module level builds it once for the whole file.

**`const` is a per-render promise, not a forever promise.** `computed` is declared with `const`, yet `value` changes and `computed` follows it. No contradiction: every render rebuilds the variable fresh from the current `value`, and within that one render it is assigned exactly once — which is all `const` promises.

**The console is the proof, not the screen.** Before the fix, click "Re-render App" — the Computed number on screen never changes, so the display proves nothing either way. The ⚡ message is the only witness that the loop ran. After the fix: count click → silent console; value click → message prints and the number changes.

**Pass the arrow, not the call.** `useMemo(slowCalculation(value), [value])` — without the `() =>` wrapper — calls the function immediately during render and hands `useMemo` the finished number. The slow loop runs on every render anyway, and the cache never gets a chance to exist. The first argument must be a function React can choose *not* to call.

**Why not `useCallback` here?** Fair question — we just used it in Step 5. The two hooks cache different things:

| | What it caches | What it prevents |
|---|---|---|
| `useMemo(() => slowCalculation(value), [value])` | the **return value** (the number) | the slow loop from *running* |
| `useCallback(() => slowCalculation(value), [value])` | the **function reference** | the reference from *changing* |

This function isn't passed to anyone — no memo'd child receives it, so no reference is ever compared; it "just sits there". And even if we did reach for `useCallback`, it wouldn't help: `computed` would become a stable *function*, and calling `computed()` in the render would still run the slow loop every time. A stable reference does not stop execution.

The problem in Step 4 was a changing reference → cache the function → `useCallback`. The problem here is needless re-running work → cache the value → `useMemo`.

(Mental shortcut: `useCallback(fn, deps)` ≈ `useMemo(() => fn, deps)` — `useCallback` is literally `useMemo` specialized for functions.)

## Step 7 — Final Component Tree with All Optimizations

One difference from Step 6: the loop now lives directly inside the `useMemo` callback instead of a separate named function — same behavior, one less name to track. Both versions are correct.

```tsx
import { useState, useMemo, useCallback, memo } from 'react'

const Sidebar = memo(function Sidebar() {
  return (
    <div className="border p-4 rounded bg-gray-50">
      <RenderCount label="Sidebar" />
      <p>Sidebar — static content</p>
    </div>
  )
})

const ExpensiveCard = memo(function ExpensiveCard({
  value, onClick
}: {
  value: number
  onClick: () => void
}) {
  return (
    <div className="border p-4 rounded">
      <RenderCount label="ExpensiveCard" />
      <p>Value: {value}</p>
    </div>
  )
})

export default function App() {
  const [count, setCount] = useState(0)
  const [value, setValue] = useState(42)

  const handleClick = useCallback(() => {
    console.log('card clicked')
  }, [])

  const computed = useMemo(() => {
    console.log('⚡ heavy calculation')
    let result = 0
    for (let i = 0; i < 10000000; i++) result += value * i
    return result
  }, [value])

  return (
    <div className="p-8 space-y-4">
      <button onClick={() => setCount(c => c + 1)}>
        Re-render App ({count})
      </button>
      <button onClick={() => setValue(v => v + 1)}>
        Change Value ({value})
      </button>
      <p>Computed: {computed}</p>
      <ExpensiveCard value={value} onClick={handleClick} />
      <Sidebar />
    </div>
  )
}
```

Check the render counts:

| Action | App | ExpensiveCard | Sidebar | slowCalculation |
|--------|-----|---------------|---------|-----------------|
| Initial render | 1 | 1 | 1 | ran |
| Re-render App | 2 | 1 (skip) | 1 (skip) | didn't run |
| Change Value | 3 | 2 | 1 (skip) | ran (value changed) |
| Re-render App | 4 | 2 (skip) | 1 (skip) | didn't run |

## Verify with React DevTools Profiler

This is the browser extension — not the `<Profiler>` component inside our RenderCount. Same name, different tool.

1. Install **React Developer Tools** (Chrome Web Store, or the Firefox add-ons store — both have it). On Firefox, don't confuse it with the browser's own **Performance** tab — that profiles the whole page's work, not React components.
2. Reopen DevTools — two new tabs appear: **Components** and **Profiler**.
3. In Profiler, hit the round record button, click the count button twice, the value button once, then the count button once more, and stop recording.
4. The flamegraph appears — one small bar per **commit** (one real screen update) along the top right; click through them with the arrows.

Read the bars color-first:

- **Yellow/green** — the component rendered; the more yellow, the more time it took. `App` is yellow on every commit.
- **Grey / hatched** — skipped. Hovering a hatched bar says *"did not render"* — that is memo doing its job on the count clicks.
- **Blue** — rendered, but trivially fast (cheap wrapper work like a plain `div`).
- A bar named **`_c memo`** is React's internal marker for a memo-wrapped component, not one of your components — read its color, ignore its name.
- **Sidebar may not appear at all** — in newer versions a skipped memo component is often absent from the flamegraph instead of drawn grey. Missing = skipped; same signal.

The first time I used the Profiler, I didn't understand what the grey bars meant. So compare commits: count-click commits show only `App`; the value-click commit shows `ExpensiveCard` too — its `RenderCount` child appears alongside it. The flamegraph ends up agreeing with the render counts and the console — three witnesses, same verdict.
