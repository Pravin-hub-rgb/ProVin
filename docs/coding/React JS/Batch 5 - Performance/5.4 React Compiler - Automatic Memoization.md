## What We've Covered So Far

In 5.1, we learned `React.memo` — it caches a component. In 5.2, `useMemo` — it caches a value. In 5.3, `useCallback` — it caches a function. Together they form a sequence: find a heavy component, wrap it in `memo`, audit every prop, and stabilize whatever breaks the audit with `useMemo` or `useCallback`.

That sequence works. It is also the part of React nobody enjoys: wrapping, auditing, re-auditing every time a new prop appears, and breaking everything silently with one missed reference. We learned it by hand because you cannot trust what you cannot do manually.

Now the question that changes everything: if the logic is mechanical enough to learn, why are we still typing it by hand?

The **React Compiler** is an official React tool that does this memoization FOR you — automatically, at build time. In this topic we'll see what it is, how it changes the code you write, how it works under the hood, and, importantly, when you still need the manual hooks from 5.1-5.3.

---

## The Problem - Manual Memoization Is a Constant Cost

Let's list what manual memoization costs, using our own 5.1-5.3 experience:

1. **Every new prop means a re-audit.** In 5.1, adding a prop to a memoized component meant asking "does this break memo?" against every parent render. Now multiply that question by every memoized component in a real app.
2. **One missed dependency is a silent slowdown.** The 5.3 filter-button lesson: an inline `onToggle={() => ...}` produced no error and no warning — memo just quietly stopped working for that component. You find out when the app feels slow, or never.
3. **The code gets noisy.** Every real codebase is full of `memo(...)`, `useMemo(...)`, `useCallback(...)` wrappers that exist purely for performance. Reading such code means unwrapping every layer mentally before you reach the actual logic.

Skipping memoization is not an option either — 5.1 showed exactly how expensive unnecessary re-renders are. The cost is real; paying it by hand is the problem.

The React Compiler's answer: a build tool does this work for you. But before we meet the tool, the first item on that list — the word **audit** — needs pinning down, because everything that follows stands on it.

---

## The Word "Audit" - What It Actually Means

We keep using the word **audit** — so let's pin it down, because it is doing a lot of work in these notes. An audit means: **checking each prop you pass to a memoized component and asking, "will this keep the same reference between parent renders?"**

Why that question? Because `memo` compares props with `Object.is` (5.1's premise). A prop that gets recreated on every render — an inline object, an inline arrow function, a freshly built array — gets a new reference each time, so `memo` thinks something changed and re-renders the child anyway. A component with five props means checking all five. When someone adds a sixth prop next month, you check again — that is the **re-audit**. And if that new prop is an inline function, `memo` quietly stops working and nothing warns you.

Let's see the whole cycle as three stages, one at a time.

**Stage 1 — one prop, the audit passes:**

```tsx
import { memo, useState } from 'react'

// A memoized child. It only re-renders if its props change.
const FilterButton = memo(function FilterButton({ label }: { label: string }) {
  console.log('FilterButton rendered')
  return <button>{label}</button>
})

function Parent() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Clicked {count}</button>
      <FilterButton label="Filter" />
    </div>
  )
}
```

Read it: `FilterButton` is wrapped in `memo`, takes one prop `label`, and prints a log line so we can spy on it. `Parent` renders a counter button and the `FilterButton`. Every click re-renders `Parent` — but `FilterButton`'s only prop is the string `"Filter"`, which is the same value every time. `memo` compares, sees no change, and skips. The console prints `FilterButton rendered` **once, at the start, and never again**, no matter how many clicks. One prop, and it is stable: the audit passes.

**Stage 2 — someone adds a second prop, inline:**

```tsx
import { memo, useState } from 'react'

const FilterButton = memo(function FilterButton({
  label,
  onToggle,
}: {
  label: string
  onToggle: () => void
}) {
  console.log('FilterButton rendered')
  return <button onClick={onToggle}>{label}</button>
})

function Parent() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Clicked {count}</button>
      <FilterButton label="Filter" onToggle={() => console.log('toggled')} />
    </div>
  )
}
```

The only change is the new `onToggle` prop, written **inline** — the arrow function sits directly inside `Parent`'s JSX. Now every click re-renders `Parent`, that JSX line runs again, and a **brand new arrow function** is created. It looks identical, but it is a different object at a different address. `memo` compares with `Object.is`, sees two different functions, concludes the prop changed — and `FilterButton` re-renders on every click. `FilterButton rendered` prints again and again. No error, no warning: the silent slowdown, exactly the 5.3 lesson. Adding one prop forced you to re-check whether `memo` still works. That is the re-audit.

**Stage 3 — the manual fix, `useCallback`:**

```tsx
import { memo, useState, useCallback } from 'react'

const FilterButton = memo(function FilterButton({
  label,
  onToggle,
}: {
  label: string
  onToggle: () => void
}) {
  console.log('FilterButton rendered')
  return <button onClick={onToggle}>{label}</button>
})

function Parent() {
  const [count, setCount] = useState(0)

  const handleToggle = useCallback(() => {
    console.log('toggled')
  }, [])

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Clicked {count}</button>
      <FilterButton label="Filter" onToggle={handleToggle} />
    </div>
  )
}
```

Two changes: the arrow function moved out of the JSX into `const handleToggle = useCallback(...)`, and `FilterButton` now receives `onToggle={handleToggle}`. `useCallback` creates the function on the first render and hands back the **same stored reference** on every later render — the empty `[]` says it depends on nothing. So `memo` compares and finds the same reference: `FilterButton` prints once and stays quiet.

That is the full manual cycle: **add a prop → notice it breaks memo → stabilize it by hand.** Every new prop means doing it again. Now the compiler enters.

## React Compiler - What It Is

**Definition.** The React Compiler is an official React tool, built by the React team at Meta and stable since October 2025, that reads your component code at **build time** and automatically adds memoization wherever it can prove it is safe and useful.

"Compiler" here means the same category of tool as `tsc` or Babel: a program that transforms source code before it runs. TypeScript transforms `.ts` into `.js`; the React Compiler transforms plain components into memoized ones. The transformation happens when you build — never in the browser, never at runtime.

"Automatically adds memoization" means one tool doing the three jobs you did by hand:

| Manual tool (5.1-5.3) | What the compiler does instead |
|---|---|
| `memo()` wraps a component | Every component gets generated caching for its render output |
| `useMemo` caches a value | Values created during render get cached — the inline-object case from 5.2 |
| `useCallback` stabilizes a function | Function references get cached — the `handleToggle` case from 5.3 |

Two things go beyond what hooks can do:

1. **Memoization after an early return.** Hooks must run in the same order every render, so a `useMemo` after a conditional `return` is illegal. The compiler generates caching code at build time — the order constraint does not apply to it.
2. **Finer granularity.** `memo()` compares whole component props. The compiler tracks individual values, so it can keep parts of a render cached even when the function exits early.

And one clarification worth stating, because it often surprises people: the compiler does not need the `memo` wrapper. It handles plain components on its own — the `memo`-wrapped version above was kept only to make the stage 1-3 comparison easy. In compiler-enabled code you drop `memo`, `useMemo`, and `useCallback` entirely and write plain.

**What It Is NOT:**
- Not a new hook or wrapper component — you write nothing new to use it.
- Not runtime magic — all caching logic is generated code, decided at build time.
- Not a way to skip understanding references — correctness cases still need manual memoization (covered below).
- Not a speed-up for necessary work — a 10,000-row list still needs virtualization (5.1's Profiler lesson); removing unnecessary renders was never the same as making necessary renders cheap.

The numbers from Meta's production use: the Quest Store loads up to 12% faster, and some interactions run up to 2.5 times faster — from memoization alone.

## Minimal Code - The Same TodoList, Plain

Here is 5.3's TodoList with every manual optimization stripped out:

```tsx
import { useState } from 'react'

type Todo = { id: number; text: string; done: boolean }

const initialTodos: Todo[] = [
  { id: 1, text: 'Learn memo', done: false },
  { id: 2, text: 'Learn useMemo', done: false },
  { id: 3, text: 'Learn useCallback', done: false },
]

function TodoItem({ todo, onToggle }: { todo: Todo; onToggle: (id: number) => void }) {
  console.log('TodoItem rendered:', todo.text)
  return (
    <label>
      <input
        type="checkbox"
        checked={todo.done}
        onChange={() => onToggle(todo.id)}
      />
      {todo.text}
    </label>
  )
}

function TodoList() {
  const [todos, setTodos] = useState<Todo[]>(initialTodos)

  function handleToggle(id: number) {
    setTodos(prev => prev.map(t =>
      t.id === id ? { ...t, done: !t.done } : t
    ))
  }

  return (
    <div>
      {todos.map(t => (
        <TodoItem key={t.id} todo={t} onToggle={handleToggle} />
      ))}
    </div>
  )
}
```

Read it slowly: `initialTodos` is a small array of three todos that feeds the state on the first render. No `memo()` wrapper on `TodoItem`, no `useCallback` around `handleToggle`, no `useMemo` anywhere. This is exactly how a beginner would write it.

Now run the same two actions from 5.3 and watch the console, with the compiler enabled in your build setup (the Setup section below):

| Action | 5.3's manual hooks printed | The plain code with the compiler |
|---|---|---|
| Filter button click | 2 lines — list and button, items skipped | The same — items skipped |
| Checkbox toggle | 1 line — only the toggled item | The same — only the toggled item |

Identical behavior, zero memoization code written by hand. That is the whole point of the React Compiler in one table.

This also settles 5.1's inline-function trap — the lesson where an inline `onToggle={() => ...}` silently broke `memo` with no error and no warning. With the compiler, that trap is simply handled, because the compiler caches the function reference itself. This trap is so common that the compiler's own documentation uses it as its main example.

## Flow - One Click, Same Skip, Nobody Typed It

Take the checkbox toggle with the compiler on:

1. You click a checkbox. `setTodos` runs — state changed, so `TodoList` re-renders. React's one guarantee: a state change always re-runs the component function.
2. The render body executes — but the compiler wraps the **creation of `handleToggle` itself** in a cache check. `handleToggle` depends only on `setTodos`, which is stable across renders, so the check always passes: the function is created once, on the first render, and reused on every render after. Nothing is recreated and thrown away — which is a different mental model from 5.3, where a new function object was built every render and `useCallback` existed to throw away the new one and hand back the old.
3. Each `TodoItem` goes through the generated cache: compare `todo` with `Object.is` (reference comparison, 5.1's logic), compare `onToggle` against the cached reference. Nine unchanged todos skip. The one toggled todo re-renders.

Same visible outcome as 5.3, item for item — but the mechanism underneath is different: no discarded objects, no manual wrapper, just cache checks generated around the code you already wrote.

## Setup - Turning the Compiler On

The compiler is a Babel plugin — a build-step extension that hooks into the code transformation pipeline. (What Babel is, exactly, gets its own section below.)

```bash
npm install babel-plugin-react-compiler
```

For a Vite project, enable it in `vite.config.ts`:

```ts
import react from '@vitejs/plugin-react'

export default {
  plugins: [
    react({
      babel: {
        plugins: [['babel-plugin-react-compiler', {}]],
      },
    }),
  ],
}
```

Reading it from the outside in: `plugins: [...]` is Vite's list of plugins, and `react(...)` is the standard React plugin. Inside it, `babel: { plugins: [...] }` lets you add extra Babel plugins to the build step. `['babel-plugin-react-compiler', {}]` is the compiler itself — the empty `{}` means default settings.

After this, `npm run dev` and `npm run build` automatically compile your components with memoization added. Nothing extra in your code: restart the dev server once so Vite picks up the new config, and from then on you just write plain components like normal.

**React 17 and 18 need two more things.** React 19 works out of the box. On 17 or 18, add a `target` option telling the compiler which runtime to generate code for, and install a small compatibility package:

```bash
npm install react-compiler-runtime
```

```ts
plugins: [['babel-plugin-react-compiler', { target: '18' }]],
```

**Gradual adoption, if you want it.** By default the compiler processes every component it can prove safe. If you would rather turn it on component by component, set a compilation mode:

```ts
plugins: [['babel-plugin-react-compiler', { compilationMode: 'annotation' }]],
```

With `annotation`, the compiler only compiles components that carry a `"use memo"` directive at the top of the function — everything else is left plain until you opt it in. Useful for adopting in a large existing codebase one file at a time.

Other environments have dedicated support: Next.js exposes a `reactCompiler` config flag, Expo ships the compiler by default from SDK 54, and Bun supports it natively from 1.4 — built into the bundler itself (`bun build --react-compiler` or `Bun.build({ reactCompiler: true })`), no Babel plugin needed.

## Under the Hood - What Babel Is and How the Compiler Works

Until now the compiler has been magic: you enabled it and memoization appeared. For interviews — and for trusting what it does — you need the mechanism. It is learnable without being a compiler engineer, but it starts one step earlier: **what Babel itself is**.

**The premise.** The browser only runs JavaScript — it cannot run JSX at all, because JSX (a mix of JavaScript and HTML-like syntax, not CSS) is not valid JavaScript. Babel is a tool that transforms the code you write into code the browser can run: it turns JSX into plain JavaScript function calls — the `createElement`-style calls you saw when JSX was introduced — and React then takes those calls and builds the actual HTML elements on the page. So the chain is: **JSX → Babel converts it to JavaScript → React turns that into HTML in the browser.** Babel is called a compiler, more precisely a **transpiler**, because it converts code from one form to another at the same level. It works in three steps: **parse** your code into a tree, **transform** that tree using plugins, then **print** it back out as code.

The React Compiler is one of those transform plugins. Babel parses your component, hands the tree to the compiler plugin, which rewrites it with cache checks added, and out comes plain JavaScript.

Now the pipeline, one step at a time:

**Step 1 — Parsing.** Your component is just text. Babel reads it and turns it into a tree where every piece of code becomes a **node**. A node is just a plain JavaScript object: it has a `type` property saying what kind of code it represents, plus other properties describing the piece, some of which hold other nodes — and that nesting is what makes it a tree. Take `const x = 5`: Babel turns it into an object of `type: 'VariableDeclaration'`, holding a child node of `type: 'VariableDeclarator'`, which itself holds a node for the name `x` and a node for the number `5`. The outermost parent is a node of `type: 'File'`, and inside it a `Program` node representing your whole file — then every import, every function, every variable hangs off `Program` as children. (If your instinct says "the outermost parent is `document` or `window`" — that is the DOM, a tree of the *page's elements*. Babel's tree is a different tree: a tree of your *code's pieces*. Both are trees with one root and nested children, but they describe different things.) Now the compiler can walk your code like a map instead of squinting at text.

**Step 2 — Building its internal form.** Babel's tree describes syntax, not data. So the compiler converts it into its own representation where it can follow every value around: where was this value created, what other values did it use, where does it go next? Babel's tree says "there is a variable called `handleToggle`, and it holds a function." The compiler's version also records "this function uses `setTodos`, and it gets passed into each `TodoItem` as `onToggle`." It is the difference between a list of ingredients and a recipe showing what goes into what — and this is where props flowing into child components are tracked too, with each value's origin and dependencies, not its type.

**Step 3 — Working out what can change.** This is dependency tracking — the same job you did by hand when writing a `useCallback` dependency array. `setTodos` from `useState` is known to be stable. `todos` is state, so it can change. A function that only uses stable things is itself stable — so `handleToggle` is stable. A value built from `todos` changes whenever `todos` does. The compiler works this out for every value created during render — not just functions: objects, arrays, and the JSX itself.

**Step 4 — Checking safety.** The compiler verifies the component follows the Rules of React (stated in full in the Rules of React section below): no mutating values during render, no reading mutable globals, output depending only on props and state. If something fails that check, it skips the whole component, silently.

**Step 5 — Generating code.** For each piece of work, the compiler wraps the result in a **cache check**. Each component gets a small storage array — a row of numbered boxes that survives between renders — and the generated code says, for each box: have the inputs changed since last render, compared with `Object.is`? If not, reuse the stored result. If yes, recompute and store the new one. This is literally what `useMemo` and `useCallback` do under the hood — written automatically, and at a finer level, since every cached value gets its own box instead of one per hook call.

So the one-liner for an interview: **the React Compiler statically analyzes data flow in your components, then inserts cache checks keyed on the values each piece depends on.**

One boundary of the mechanism, so the one-liner stays honest: the compiler removes *unnecessary* work — renders that repeat for no reason. It never makes *necessary* work cheaper. Think of it as a helper who stops you doing the same work twice: if a component already rendered and nothing about it changed, it says "skip it, you already have the answer." But if a 10,000-row list's data genuinely did change, the helper has nothing to reuse — all 10,000 rows must render, and the fix for that is virtualization (5.1's Profiler lesson), a separate technique.

## What Stays Manual - When Memoization Is About Correctness

Here is the part that keeps 5.1-5.3 essential. The compiler's goal is to remove unnecessary re-renders. But some memoization exists for a different reason: a reference must stay stable because something OUTSIDE React's render depends on it. The compiler cannot always know that — it only understands what happens inside your component's render. It can see that a value is created and passed along, but it cannot see that an effect will break if the reference changes, or that a library is quietly storing the object you gave it. Those consequences live outside the render, and only you know about them. So memoization for correctness stays manual, with a comment saying why.

**1. Effects that must not re-run.**

```tsx
import { useEffect, useCallback } from 'react'

function ChatRoom({ roomId }: { roomId: string }) {
  // Manual on purpose: the effect below depends on this exact reference
  const handleMessage = useCallback((msg: string) => {
    console.log('New message in', roomId, ':', msg)
  }, [roomId])

  useEffect(() => {
    const socket = connect(roomId)
    socket.on('message', handleMessage)
    return () => socket.disconnect()
  }, [roomId, handleMessage])

  return <p>Chatting in {roomId}</p>
}
```

Read it: `handleMessage` is created with `useCallback([roomId])`, so its reference changes only when `roomId` changes. It sits in the effect's dependency array along with `roomId`. If it were a new function on every render, the effect would re-run on every render — disconnecting and reconnecting the socket each time. That is a real bug, not a slowdown, so the reference is pinned by hand. (`connect` is a made-up helper; the shape is what matters.)

**2. Custom hooks that promise stability.**

```tsx
import { useState, useCallback } from 'react'

function useCounter() {
  const [count, setCount] = useState(0)

  // Manual on purpose: callers may put `increment` in an effect's dependency array
  const increment = useCallback(() => setCount(c => c + 1), [])

  return { count, increment }
}
```

Read it: the hook returns `count` and `increment`. Anyone using `useCounter` may assume `increment` never changes and put it in a dependency array. That assumption is an unwritten contract, and as the hook author you are the only one who knows about it — so you keep it with a manual `useCallback`.

**3. Non-React libraries.**

```tsx
import { useRef, useEffect, useMemo } from 'react'

function Chart() {
  const ref = useRef<HTMLDivElement>(null)

  // Manual on purpose: the chart library stores this object
  const options = useMemo(() => ({ color: 'blue', animate: true }), [])

  useEffect(() => {
    const chart = new FancyChart(ref.current!, options)
    return () => chart.destroy()
  }, [options])

  return <div ref={ref} />
}
```

Read it: `FancyChart` is a plain JavaScript library React knows nothing about (the vanilla-JS side-effect world from 2.1). It receives `options` and stores it. If `options` were a new object on every render, the effect would destroy and rebuild the whole chart each time — so the object is stabilized with `useMemo` and the chart is created once. (`ref.current!` — the `!` tells TypeScript the div exists by the time the effect runs.)

In all three cases the stable reference matters for **correctness**, not just fewer renders — and each carries a comment saying why. That comment is what stops a teammate from deleting the hook as "unnecessary" later.

The decision rule, stated once:

- Memoization so that renders happen less → the compiler handles it. Write plain code.
- Memoization so that a reference stays stable for something outside render → write it manually, with a comment explaining why.

If both apply, do both: manual for correctness, and the compiler covers the rest.

## The Rules of React - How the Compiler Proves It Is Safe

The compiler does not memoize blindly. It memoizes only what it can PROVE is safe, and its proof standard is the Rules of React — the rules React's docs have always stated for render correctness:

- Render output must depend only on props and state: same input, same output.
- Do not mutate values created during render, and do not read or write mutable globals during render.
- Side effects belong in effects, not in render.

Here is the practical part: when the compiler cannot prove a component is safe, it does not error and does not warn. It **silently skips** that component and compiles the rest. Your app still works — just without automatic memoization for that component.

How do you find out? `eslint-plugin-react-hooks`, the official React lint plugin, includes diagnostics for exactly these cases: it flags the code patterns the compiler cannot prove. Enable that lint config whenever you enable the compiler. In practice it looks like this: the linter runs inside your editor, so the code the compiler cannot handle gets underlined — a squiggly line below the offending pattern — and hovering shows a message explaining which rule it breaks. The same messages appear in your terminal and in build checks.

And there is now a faster alternative: **Oxlint**, the Rust-based linter, added 22 React Compiler-powered rules in v1.79 (August 2026) — the same diagnostics, produced by the compiler's own validation passes, at Rust speed. For interviews, the safe answer is that `eslint-plugin-react-hooks` is the official route, and Oxlint is a faster alternative that now covers the same rules.

## Compiler vs Manual Hooks - Both Have a Place

If the compiler adds `memo` for you, why did we spend three topics on manual memoization? Because the manual knowledge matters for four reasons:

1. **Correctness cases** (the What Stays Manual section): the compiler removes render work; it cannot decide reference contracts for you.
2. **You will read this code everywhere.** Existing codebases are full of `memo`, `useMemo`, `useCallback`, and the compiler's own generated output uses the same patterns. If you do not know why an inline `onToggle` breaks memo (5.1), you cannot debug anyone's app.
3. **Existing manual memo stays.** The compiler does not remove your `useMemo`/`useCallback`/`memo` code. Removing it could change behavior — you may have memoized for a library contract the compiler cannot see — so it preserves yours. Manual hooks remain your option for these cases.
4. **The mental model does not change.** Every re-render question still answers the same way: `Object.is` on references (5.1). The compiler just does the work you used to do by hand.

New code: write it plain and let the compiler optimize. Reach for the hooks only when correctness requires them.

---

## Common Mistake - Treating the Compiler as Permission to Skip the Fundamentals

The mistake sounds like this: "memo, useMemo, useCallback are obsolete — I can stop thinking about references."

It is wrong twice.

First, the correctness cases above still need the hooks. Delete a `useCallback` that is holding an effect dependency stable and you have reintroduced a bug no compiler will catch.

Second, you still have to READ memoized code — in every codebase you join, in interviews, and in the compiler's own generated output. The compiler automates the typing, not the understanding.

We learned manual memoization first on purpose. That is why this topic comes after 5.1-5.3, not instead of them.

## Interview-Ready Answers

Two questions this topic must answer cleanly. First, memorize the distinction in the wording, not just the idea: the word is **memoize** — cache a result for reuse — not *memorize*.

**Q: What is the React Compiler, and when does it do its work?**

> It is a build-time Babel plugin that automatically memoizes React components. React has a known cost: when a parent renders, every child renders too, even when its props did not change — and the manual fix was `memo`, `useMemo`, and `useCallback`, which is tedious and easy to get silently wrong. The compiler does that work during the build, not in the browser: it parses the code into a tree, tracks what each value depends on, proves the component follows the Rules of React, and generates cache checks keyed on those dependencies — so unchanged values are reused instead of recomputed, and your source stays plain.

**Q: What can the compiler NOT do for you?**

> Three things. First, it removes unnecessary work, never necessary work — a 10,000-row list whose data genuinely changed still has to render, and that needs virtualization. Second, it optimizes for fewer renders, but it cannot know when a stable reference is needed for correctness OUTSIDE the render — an effect that must not re-run, a custom hook's promised contract, a non-React library storing a config object — so those stay manual `useCallback`/`useMemo`, with a comment saying why. Third, it only memoizes components it can prove follow the Rules of React; anything it cannot prove is silently skipped, and `eslint-plugin-react-hooks` (or Oxlint, since v1.79) is how you find out which ones.

## Summary

- The **React Compiler** is an official React tool — a Babel plugin — stable since October 2025.
- It works at **build time**: it reads your components and adds memoization where it can prove it is safe. Your source stays plain — no `memo`, `useMemo`, `useCallback` needed, even for the inline-function trap.
- **Audit** means checking each prop of a memoized component for stable references; **re-audit** means doing it again for every new prop. The compiler deletes the whole cycle.
- Under the hood: parse the code into a tree (nodes = plain objects; root = `File` → `Program`), track what each value depends on, prove it is safe, then insert **cache checks** (per-component boxes, compared with `Object.is`). Interview one-liner: it statically analyzes data flow and inserts cache checks keyed on dependencies.
- Setup: install the plugin, add it to the build config. React 17/18 also need `target: '18'` and `react-compiler-runtime`. `compilationMode: 'annotation'` opts components in one at a time via `"use memo"`. Bun 1.4+ has it built in.
- Memoization for **correctness** stays manual: effect dependencies, custom-hook contracts, non-React libraries — with a comment explaining why.
- Decision rule: fewer renders → the compiler; a stable reference outside render → manual hooks.
- Components that violate the **Rules of React** are silently skipped, not errored — `eslint-plugin-react-hooks` is the official diagnostic (squiggly lines in your editor); Oxlint v1.79+ (August 2026) covers the same rules faster.
- Existing manual memoization is **preserved**, not removed.
- It removes unnecessary work, never necessary work — virtualization and Profiler measurement (5.1) still matter.
- Meta's production numbers: the Quest Store loads up to 12% faster and some interactions run up to 2.5 times faster.
