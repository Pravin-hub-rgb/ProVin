---

## The Problem — When useState Becomes Insufficient

Imagine a shopping cart:

```tsx
const [items, setItems] = useState<CartItem[]>([])
const [isOpen, setIsOpen] = useState(false)
const [coupon, setCoupon] = useState('')

function addItem(product: Product) {
  setItems(prev => [...prev, { ...product, quantity: 1 }])
}

function updateQuantity(id: number, qty: number) {
  setItems(prev => prev.map(item =>
    item.id === id ? { ...item, quantity: qty } : item
  ))
}

function applyCoupon(code: string) {
  // validation
  // update discount
  // maybe clear some items?
  // three things need to change at once
}
```

See the issue? `items`, `isOpen`, `coupon` — three separate `useState` calls. But some actions change multiple states at once. The state gets scattered, and debugging becomes a nightmare.

**Why is this a problem?** `useState` is for independent variables. React doesn't know that these three belong together. When one action changes multiple states, the logic gets scattered — `setItems` here, `setCoupon` there. Bugs creep in easily.

---

## Starting with useState — A Simple Counter

Let's start with a simple counter with three actions: increment, decrement, reset:

```tsx
// Counter.tsx
import { useState } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <button onClick={() => setCount(c => c - 1)}>-</button>
      <button onClick={() => setCount(0)}>Reset</button>
    </div>
  )
}
```

Here, `useState` works perfectly fine. One variable, simple logic — not scattered, no problem.

**Now imagine 6 actions** — increment, decrement, reset, add5, double, halve. With `useState`, it looks like:

```tsx
// ❌ useState — 6 actions, logic scattered
export default function Counter() {
  const [count, setCount] = useState(0)

  const increment = () => setCount(c => c + 1)
  const decrement = () => setCount(c => c - 1)
  const reset = () => setCount(0)
  const add5 = () => setCount(c => c + 5)
  const double = () => setCount(c => c * 2)
  const halve = () => setCount(c => Math.floor(c / 2))

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={increment}>+</button>
      <button onClick={decrement}>-</button>
      <button onClick={reset}>Reset</button>
      <button onClick={add5}>+5</button>
      <button onClick={double}>×2</button>
      <button onClick={halve}>÷2</button>
    </div>
  )
}
```

All those `setCount(...)` calls are scattered inside the component. There's no single place that says "here are all the possible actions for the counter and how state changes." Adding a new action means writing a new function in the component.

The solution to this is **`useReducer`** — it keeps all the state change logic in one central function (a reducer). Let's see how it works.

## useReducer — What It Is

`useReducer` is a hook that manages complex state logic in a central place. There are three things involved:

1. **State** — the entire state object, all at once
2. **Action** — an object that says "do this"
3. **Reducer** — a function that changes state based on the action

Syntax:

```tsx
// Counter.tsx
const [state, dispatch] = useReducer(reducer, initialState)

// state — current state
// dispatch(action) — how to send an action
// reducer — function that decides how state changes
```

**What's happening internally?** When you call `dispatch(action)`, React internally calls `reducer(currentState, action)`. Whatever the reducer returns becomes the new state. Simple.

Visual mapping:

```
View (UI)
  │ dispatch({ kind: 'increment' })
  ▼
reducer(state, action)
  │ switch(action.kind)
  ▼
New state
  │
  ▼
Component re-renders
```

## Minimal Code — Counter with useReducer

We've seen the scattered `useState` version — 6 actions, 6 different `setCount` calls, logic all over the place. Now let's build the same counter with `useReducer`, step by step.

### Step 1 — Import

```tsx
// Counter.tsx
import { useReducer } from 'react'
```

`useReducer` is a hook. You give it two things — a reducer function and an initial state. It returns `[state, dispatch]`.

### Step 2 — Define Action Types

```tsx
type Action = 
  | { kind: 'increment' }
  | { kind: 'decrement' }
  | { kind: 'reset' }
  | { kind: 'add5' }
  | { kind: 'double' }
  | { kind: 'halve' }
```

An action is an object with a `kind` property — this says "which action should be performed."

`Action` here is a **union type** — 6 possible shapes. The meaning: `Action` is either `{ kind: 'increment' }`, or `{ kind: 'decrement' }`, or `{ kind: 'add5' }`, etc. Only one can be true at a time.

In TypeScript, `|` (pipe) means **"or"** — `'loading' | 'success'` = 'loading' **or** 'success'.

### Step 3 — The Reducer Function (Central Logic)

```tsx
function reducer(state: number, action: Action): number {
  switch (action.kind) {
    case 'increment': return state + 1
    case 'decrement': return state - 1
    case 'reset':     return 0
    case 'add5':      return state + 5
    case 'double':    return state * 2
    case 'halve':     return Math.floor(state / 2)
  }
}
```

The reducer takes two parameters:
1. **Current state** (`state: number`) — the current value
2. **Action** (`action: Action`) — which action to perform

Inside, a `switch` statement checks `action.kind`. Match the action, return the result. `increment` → `state + 1`. `add5` → `state + 5`. Simple.

**Important:** A reducer should be a **pure function** — take in state + action, return new state. Don't make API calls, don't write to localStorage, don't use `Math.random()` inside the reducer. Just calculations.

### Step 4 — Call useReducer

```tsx
const [count, dispatch] = useReducer(reducer, 0)
```

Two arguments:
1. **Reducer** — the `reducer` function (just created)
2. **Initial state** — `0` (the starting count)

Returns:
- `count` — the current state value (like `useState`'s count)
- `dispatch` — a function to send actions (like `useState`'s `setCount`, but takes an action object, not a direct value)

### Step 5 — Dispatch in JSX

```tsx
return (
  <div>
    <p>Count: {count}</p>
    <button onClick={() => dispatch({ kind: 'increment' })}>+</button>
    <button onClick={() => dispatch({ kind: 'decrement' })}>-</button>
    <button onClick={() => dispatch({ kind: 'reset' })}>Reset</button>
    <button onClick={() => dispatch({ kind: 'add5' })}>+5</button>
    <button onClick={() => dispatch({ kind: 'double' })}>×2</button>
    <button onClick={() => dispatch({ kind: 'halve' })}>÷2</button>
  </div>
)
```

Button click → `dispatch({ kind: 'increment' })` → React calls `reducer(0, { kind: 'increment' })` → reducer returns `1` → state updates → component re-renders → UI shows `1`.

Compared to the `useState` version:

| useState | useReducer |
|----------|-----------|
| 6 scattered `setCount(c => ...)` calls | One `dispatch({ type })` — all the same pattern |
| New action = write a new function | New action = add a type + case |
| Logic can be anywhere (scattered) | Logic is **exactly** in the reducer (one place) |

## TypeScript + Discriminated Unions

So far the counter's actions only had `kind`. But in real apps, actions come with extra data — like a product, or an ID, or a quantity. This is where TypeScript's **discriminated unions** come in handy.

### First, Understand — What Is a Union

"Union" doesn't mean "all of these at once" — it means **"one of these."**

```tsx
// With primitives
type Status = 'loading' | 'success' | 'error'
// Status is 'loading' OR 'success' OR 'error'
// Only one value at a time — not all three simultaneously
```

The `|` (pipe) means **"or"** — `'loading' | 'success'` = 'loading' **or** 'success'.

The same pattern works with objects, we just put `|` at the start of the next line for readability:

```tsx
type Action =
  | { kind: 'increment' }
  | { kind: 'decrement' }
```

Both work the same way — `'loading' | 'success'` is the same as `| { kind: 'increment' }`. It's just a formatting choice. TypeScript treats both identically.

### `type` Keyword vs Property `kind` — Know the Difference

Notice there are two different `type` words here that look the same but do different things:

```tsx
type  CartAction  =  { kind: 'ADD_ITEM'; product: Product }
 ↑ keyword            ↑ property name — can be anything
```

- **`type CartAction =`** — this is **TypeScript's keyword**. It's reserved. You use it to create a new type.
- **`{ kind: 'ADD_ITEM' }`** — this is an **object property**. It's just a name. You could call it `kind`, `type`, `actionType` — anything.

Here we use `kind` as the property name (to avoid confusion with the `type` keyword). Convention-wise, React/Redux projects use `type`, but `kind` is perfectly valid — both do the same thing.

### So Why Call It "Discriminated"?

"Discriminate" means **"to tell apart"** or **"to identify."** Like how police identify a suspect — "this is the one, that's not."

Here, the `kind` property is the **identifier** that tells you **which action** it is:

```tsx
type CartAction =
  | { kind: 'ADD_ITEM'; product: Product }
  // ↑ This is the action where kind = 'ADD_ITEM'
  | { kind: 'REMOVE_ITEM'; id: number }
  // ↑ This is the action where kind = 'REMOVE_ITEM'
```

The `kind` property is the **discriminant** (identifier). Just like each person has a unique Aadhaar number, each action has a unique `kind`. When TypeScript sees the value of `kind`, it immediately knows "this is which action."

A discriminated union is a union that has a common property (the discriminant) which tells you which member is currently active.

### What Is Payload?

Besides `kind`, any other properties are **payload** — the extra data that goes along with the action. "Payload" simply means **"the extra data sent with the action"** — the actual thing you want to work with.

Like a delivery person who carries a parcel with an address label (discriminant) and the actual package inside (payload):

| Action | Discriminant (identifier — `kind`) | Payload (extra data) |
|--------|-----------------------------------|---------------------|
| `ADD_ITEM` | `kind: 'ADD_ITEM'` | `product: Product` |
| `REMOVE_ITEM` | `kind: 'REMOVE_ITEM'` | `id: number` |
| `UPDATE_QTY` | `kind: 'UPDATE_QTY'` | `id: number, quantity: number` |
| `CLEAR_CART` | `kind: 'CLEAR_CART'` | No payload |

Payload is optional — some actions have extra data, some don't. `CLEAR_CART` doesn't need any extra data — just "empty the cart" is enough.

### One Important Rule

The discriminant property (`kind`, `type`, `actionType` — whatever you call it) must be **common across every member** of the union. If one action has `kind` and another has `type`, TypeScript gets confused — it doesn't know which property is the discriminant.

### How TypeScript Narrows Types

When you write `switch (action.kind)`, TypeScript narrows the action's structure inside each `case` — it knows exactly which properties are available for that specific action:

```tsx
function cartReducer(state: CartState, action: CartAction) {
  switch (action.kind) {
    case 'ADD_ITEM':
      // Here action = { kind: 'ADD_ITEM'; product: Product }
      // TypeScript knows: action.product exists ✅
      // action.id ❌ — error, this action doesn't have an id
      return { ...state, items: [...state.items, action.product] }

    case 'REMOVE_ITEM':
      // Here action = { kind: 'REMOVE_ITEM'; id: number }
      // action.id exists ✅, action.product ❌
      return { ...state, items: state.items.filter(i => i.id !== action.id) }

    case 'CLEAR_CART':
      // Here action = { kind: 'CLEAR_CART' }
      // No extra properties — just kind
      return initialState
  }
}
```

The benefits:
1. **Catches mistakes** — if you write `action.product` inside the `REMOVE_ITEM` case, TypeScript errors out because `REMOVE_ITEM` doesn't have a `product`
2. **Auto-complete** — typing `action.` shows only the properties that exist in that particular action
3. **Refactor-safe** — if you change an action's payload (like removing `product` from `ADD_ITEM`), every place that uses it incorrectly will show an error

### Visual Summary

```
CartAction is a union — multiple possible shapes
    │
    ├── { kind: 'ADD_ITEM'; product: Product }        ← discriminant: 'ADD_ITEM'
    ├── { kind: 'REMOVE_ITEM'; id: number }            ← discriminant: 'REMOVE_ITEM'
    ├── { kind: 'UPDATE_QTY'; id: number; qty: number } ← discriminant: 'UPDATE_QTY'
    ├── { kind: 'APPLY_COUPON'; code: string }         ← discriminant: 'APPLY_COUPON'
    └── { kind: 'CLEAR_CART' }                         ← discriminant: 'CLEAR_CART'

switch (action.kind) {
  case 'ADD_ITEM': → TypeScript narrows to { kind: 'ADD_ITEM'; product: Product }
  case 'REMOVE_ITEM': → TypeScript narrows to { kind: 'REMOVE_ITEM'; id: number }
}
```

## Real Example — Shopping Cart (Step by Step)

We've covered discriminated unions in theory. Now let's build a real shopping cart — but we won't dump code all at once. We'll build it step by step, understanding the reasoning behind each decision.

### Step 1 — Think First: What Do We Need?

Think like a developer. Someone says "build a cart." What do you do? First, think — what data do we need, what actions do we need.

**What goes in state?**
- Items the user has added
- Coupon code, if one is applied
- Discount percentage

**What actions will there be?**
- Add an item
- Remove an item
- Change quantity
- Apply a coupon
- Clear the cart

That's the thinking before we write any code.

### Step 2 — The Shape of One Item: CartItem (Why `interface`?)

The developer now thinks: "what fields does an item have?" Each cart item has:

```tsx
// src/types/cartTypes.ts
interface CartItem {
  id: number       // product unique id
  name: string     // product name (for display)
  price: number    // per unit price
  quantity: number  // how many units are in the cart
}
```

**Why `interface` and not `type`?**

Both can do the job, but they're better for different use cases:
- **`interface`** — use this when you want to describe the shape of an object. "This is what the object looks like." Using `interface` for objects is a common pattern in React.
- **`type`** — use this when you need a union (like `CartAction` which has multiple shapes).

Rule of thumb: if you're describing an object's structure → use `interface`. If you're creating a union → use `type`.

### Step 3 — CartState: All State in One Place

Whereas before we had multiple scattered `useState` calls, now we bundle all state into **one interface**:

```tsx
// src/types/cartTypes.ts
interface CartState {
  items: CartItem[]    // array of CartItem
  coupon: string       // coupon code, if applied
  discount: number     // discount % (0 means no discount)
}
```

**Why does the developer do this?** Because when all state is in one place, you get:
1. Easier debugging — everything shows up in one object
2. Easy to reset — just `return initialCart`, everything clears
3. Actions can modify multiple fields at once

### Step 4 — Initial State

```tsx
// src/reducers/cartReducer.ts
const initialCart: CartState = {
  items: [],
  coupon: '',
  discount: 0,
}
```

Just the starting values — nothing in the cart yet.

### Step 5 — Defining Actions (Omit Explained)

Now comes the interesting part — the actions. There are 5 actions, each with different payload (extra data):

```tsx
// src/types/cartTypes.ts
type CartAction =
  | { kind: 'ADD_ITEM'; product: Omit<CartItem, 'quantity'> }
  | { kind: 'REMOVE_ITEM'; id: number }
  | { kind: 'UPDATE_QTY'; id: number; quantity: number }
  | { kind: 'APPLY_COUPON'; code: string }
  | { kind: 'CLEAR_CART' }
```

**Understand each action:**

| Action | kind | Payload | Why? |
|--------|------|---------|------|
| ADD_ITEM | `'ADD_ITEM'` | `product: Omit<CartItem, 'quantity'>` | User just sends product info — the reducer decides the quantity |
| REMOVE_ITEM | `'REMOVE_ITEM'` | `id: number` | Only the id is needed to remove an item |
| UPDATE_QTY | `'UPDATE_QTY'` | `id: number, quantity: number` | Quantity change — needs the id and the new quantity |
| APPLY_COUPON | `'APPLY_COUPON'` | `code: string` | The coupon code — the reducer validates it |
| CLEAR_CART | `'CLEAR_CART'` | None | Just "empty the cart" is enough |

**Now understand `Omit`** — it's a TypeScript utility type.

```tsx
Omit<CartItem, 'quantity'>
```

Means: "Take the `CartItem` type, but remove the `quantity` property from it."

Since `CartItem` is:
```tsx
interface CartItem { id: number; name: string; price: number; quantity: number }
```

`Omit<CartItem, 'quantity'>` results in:
```tsx
{ id: number; name: string; price: number }
```

The quantity gets added by the reducer itself.

**Why does the developer use `Omit`?** No need to duplicate types. `CartItem` is already defined. Just remove `quantity` — `Omit` handles it. Later, if you add a new field to `CartItem` (like `imageUrl`), `Omit<CartItem, 'quantity'>` automatically includes it — no need to update anywhere else.

Without `Omit`, the developer would have to maintain a separate type:
```tsx
interface ProductInput { id: number; name: string; price: number }
```

Two places to maintain. With `Omit`, no duplication.

### Step 6 — The Reducer Function (Where the Logic Lives)

Now we write the reducer — **this is where the developer's thinking matters most** because it's the central logic.

```tsx
// src/reducers/cartReducer.ts
import { useReducer } from 'react'

// --- Types (imported from src/types/cartTypes.ts) ---

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.kind) {
    case 'ADD_ITEM': {
      // Developer thinks: "First check if the item is already in the cart"
      const existing = state.items.find(i => i.id === action.product.id)

      if (existing) {
        // ✅ Already there — increment the quantity (add 1)
        // Other items stay unchanged
        return {
          ...state,
          items: state.items.map(i =>
            i.id === action.product.id
              ? { ...i, quantity: i.quantity + 1 }
              : i
          ),
        }
      }

      // ✅ New item — add to cart, quantity starts at 1
      return {
        ...state,
        items: [...state.items, { ...action.product, quantity: 1 }],
      }
    }

    case 'REMOVE_ITEM':
      // Remove the item by filtering it out — the one whose id matches gets removed
      return {
        ...state,
        items: state.items.filter(i => i.id !== action.id),
      }

    case 'UPDATE_QTY':
      // Change the quantity of a specific item
      return {
        ...state,
        items: state.items.map(i =>
          i.id === action.id ? { ...i, quantity: action.quantity } : i
        ),
      }

    case 'APPLY_COUPON':
      // Check the coupon code — if valid, apply discount
      return {
        ...state,
        coupon: action.code,
        discount: action.code === 'SAVE10' ? 10 : 0,
      }

    case 'CLEAR_CART':
      // Back to initial state — everything resets
      return initialCart

    default:
      return state
  }
}
```

**The reducer's pattern to understand:** In every case:
1. Copy the state (`...state`) — immutability
2. Change only the field related to the action (items, coupon, discount)
3. Leave everything else unchanged

### Step 7 — Using It in a Component

Now the component is simple — read state, dispatch actions:

```tsx
// src/components/Cart.tsx
export default function Cart() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart)

  return (
    <div>
      <h2>Cart ({cart.items.length} items)</h2>

      {cart.items.map(item => (
        <div key={item.id}>
          <p>
            {item.name} × {item.quantity} = ${item.price * item.quantity}
          </p>
          <button onClick={() => dispatch({ kind: 'REMOVE_ITEM', id: item.id })}>
            Remove
          </button>
        </div>
      ))}

      {cart.coupon && <p>Coupon: {cart.coupon} — {cart.discount}% off</p>}

      <button onClick={() => dispatch({ kind: 'CLEAR_CART' })}>
        Clear Cart
      </button>
    </div>
  )
}
```

Notice: every `dispatch` call sends **only the data that action needs**:
- `REMOVE_ITEM` → just `id`
- `CLEAR_CART` → nothing, just `kind`

Get `REMOVE_ITEM` wrong and forget the `id` — TypeScript errors: "id is required for REMOVE_ITEM." That's the value of the discriminated union.

### The Developer's Perspective — The Full Flow

1. The user clicks "Add" → the component calls `dispatch({ kind: 'ADD_ITEM', product })`
2. React internally calls `cartReducer(currentState, action)`
3. The reducer enters the `switch (action.kind)` block and goes to `case 'ADD_ITEM':`
4. It checks — is the product already in the cart?
   - ✅ Yes → increment quantity
   - ❌ No → add new item (quantity: 1)
5. A new state object is returned (immutable update)
6. React compares the state — did it change? → component re-renders
7. The new item is reflected in the UI

## useReducer vs useState — Which One to Use When

**Use `useState` when:**
- The state is simple (number, string, boolean)
- There are one or two independent state variables
- The state logic is simple — one action, one variable changes

**Use `useReducer` when:**
- The state object is complex (multiple fields)
- Multiple actions change the same state
- Actions have dependencies between them (one action changes multiple fields)
- You want to centralize state logic for easier debugging

---

## Common Mistake — Side Effects in the Reducer

The reducer should be a **pure function**. Don't make API calls, write to localStorage, or use `Math.random()` inside it:

```tsx
// ❌ Wrong — side effect in the reducer
function reducer(state, action) {
  case 'SAVE':
    localStorage.setItem('cart', JSON.stringify(state)) // ❌ side effect!
    return { ...state, saved: true }
}

// ✅ Correct — side effect in the component, reducer only changes state
function reducer(state, action) {
  case 'SAVE':
    return { ...state, saved: true }
}

// In the component:
useEffect(() => {
  localStorage.setItem('cart', JSON.stringify(cart))
}, [cart])
```

## Summary

✅ **useReducer** — for complex state — one central function handles all state changes  
✅ **Action** — an object with a `type` and optional payload  
✅ **dispatch(action)** — the way to send an action  
✅ **Reducer** — a pure function — `(state, action) => newState`  
✅ **TypeScript + discriminated unions** — proper typing for each action type  
✅ useState for simple cases, useReducer for complex cases  
✅ Keep the reducer pure — side effects go elsewhere
