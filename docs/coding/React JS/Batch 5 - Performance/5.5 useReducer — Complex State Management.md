## Problem — Jab useState Mushkil Ho Jaata Hai

Socho ek shopping cart:

```tsx
const [items, setItems] = useState<CartItem[]>([])
const [isOpen, setIsOpen] = useState(false)
const [coupon, setCoupon] = useState('')

function addItem(product: Product) {
  setItems(prev => [...prev, { ...product, quantity: 1 }])
}

function updateQuantity(id: number, qty: number) {
  setItems(prev => prev.map(item =>
    item.id === id ? { ...item, quantity: qty } : item
  ))
}

function applyCoupon(code: string) {
  // validation
  // update discount
  // maybe clear some items?
  // teen cheezein ek saath change karni hain
}
```

Dekh rahe ho? `items`, `isOpen`, `coupon` — teen alag `useState` calls. Lekin kuch actions ek saath multiple states change karte hain. Toh state scattered ho jati hai, aur debugging mushkil ho jati hai.

**Yeh problem kyun hai?** `useState` independent variables hai. React ko pata nahi ki yeh teeno ek saath belong karte hain. Koi action multiple states change kare toh logic scattered ho jata hai — ek jagah `setItems`, doosri jagah `setCoupon`. Bugs aana easy hai.

## Pehle useState Se Counter Dekhte Hain

Ek simple counter — teen actions: increment, decrement, reset:

```tsx
// Counter.tsx
import { useState } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <button onClick={() => setCount(c => c - 1)}>-</button>
      <button onClick={() => setCount(0)}>Reset</button>
    </div>
  )
}
```

Yahan `useState` perfectly kaam karta hai. Ek variable, simple logic — scattered bhi nahi hai, koi problem nahi.

**Ab imagine karo 6 actions hote** — increment, decrement, reset, add5, double, halve. useState se kaisa dikhega:

```tsx
// ❌ useState — 6 actions, logic scattered
export default function Counter() {
  const [count, setCount] = useState(0)

  const increment = () => setCount(c => c + 1)
  const decrement = () => setCount(c => c - 1)
  const reset = () => setCount(0)
  const add5 = () => setCount(c => c + 5)
  const double = () => setCount(c => c * 2)
  const halve = () => setCount(c => Math.floor(c / 2))

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={increment}>+</button>
      <button onClick={decrement}>-</button>
      <button onClick={reset}>Reset</button>
      <button onClick={add5}>+5</button>
      <button onClick={double}>×2</button>
      <button onClick={halve}>÷2</button>
    </div>
  )
}
```

Dekh rahe ho? Saari `setCount(...)` calls component ke andar scattered hain. Koi ek jagah nahi hai jo bataye "counter ke saare possible actions kya hain aur state kaise change hoti hai." Naya action add karna hai toh component mein naya function banana padega.

Is problem ka solution hai **`useReducer`** — jo saari state change logic ko ek central function (reducer) mein rakh deta hai. Neeche dekhte hain kaise kaam karta hai.

## useReducer — Kya Hai

`useReducer` ek hook hai jo complex state logic ko ek central jagah manage karta hai. Teen cheezein hoti hain:

1. **State** — poora state object ek saath
2. **Action** — ek object jo batata hai "kya karna hai"
3. **Reducer** — ek function jo action ke according state change karta hai

Syntax:

```tsx
// Counter.tsx
const [state, dispatch] = useReducer(reducer, initialState)

// state — current state
// dispatch(action) — action bhejne ka tarika
// reducer — function jo decide karta hai state kaise change hogi
```

**Kya hota hai internally?** Jab `dispatch(action)` call karte ho, React internally `reducer(currentState, action)` call karta hai. Jo bhi reducer return karta hai — woh nayi state ban jati hai. Simple.

Visual mapping:

```
View (UI)
  │ dispatch({ kind: 'increment' })
  ▼
reducer(state, action)
  │ switch(action.kind)
  ▼
New state
  │
  ▼
Component re-renders
```

## Minimal Code — Counter with useReducer

Abhi scattered useState version dekha — 6 actions, 6 alag `setCount` calls, logic bikhra hua. Ab useReducer se same counter banate hain, step by step.

### Step 1 — Import

```tsx
// Counter.tsx
import { useReducer } from 'react'
```

`useReducer` ek hook hai. Isko do cheezein do — reducer function aur initial state. Yeh `[state, dispatch]` return karta hai.

### Step 2 — Action Type Define Karo

```tsx
type Action = 
  | { kind: 'increment' }
  | { kind: 'decrement' }
  | { kind: 'reset' }
  | { kind: 'add5' }
  | { kind: 'double' }
  | { kind: 'halve' }
```

Action ek object hai jisme `kind` property hota hai — yeh batata hai "kya action karna hai."

Yahan `Action` ek **union type** hai — 6 possible shapes. Iska matlab: Action ya toh `{ kind: 'increment' }` ho sakta hai, ya `{ kind: 'decrement' }`, ya `{ kind: 'add5' }`, etc. Ek baar mein sirf ek hi type (shape) ho sakta hai.

TypeScript union ko `|` (pipe) se likhte hain — "yeh ya woh" padho.

### Step 3 — Reducer Function (Central Logic)

```tsx
function reducer(state: number, action: Action): number {
  switch (action.kind) {
    case 'increment': return state + 1
    case 'decrement': return state - 1
    case 'reset':     return 0
    case 'add5':      return state + 5
    case 'double':    return state * 2
    case 'halve':     return Math.floor(state / 2)
  }
}
```

Reducer do parameters leta hai:
1. **Current state** (`state: number`) — abhi ki value
2. **Action** (`action: Action`) — kaunsa action karna hai

Andar `switch` statement `action.kind` check karta hai. Jaise action, waisa return. `increment` → `state + 1`. `add5` → `state + 5`. Simple.

**Important:** Reducer **pure function** hona chahiye — input do (state + action), output do (naya state). Andar API call mat karo, localStorage mat likho, `Math.random()` mat karo. Sirf calculation.

### Step 4 — useReducer Call Karo

```tsx
const [count, dispatch] = useReducer(reducer, 0)
```

Do arguments:
1. **Reducer** — `reducer` function (jo abhi banaya)
2. **Initial state** — `0` (count start value)

Return karta hai:
- `count` — current state value (jaise useState ka count)
- `dispatch` — function, action bhejne ke liye (jaise useState ka setCount, lekin action leta hai, direct value nahi)

### Step 5 — JSX Mein Dispatch Karo

```tsx
return (
  <div>
    <p>Count: {count}</p>
    <button onClick={() => dispatch({ kind: 'increment' })}>+</button>
    <button onClick={() => dispatch({ kind: 'decrement' })}>-</button>
    <button onClick={() => dispatch({ kind: 'reset' })}>Reset</button>
    <button onClick={() => dispatch({ kind: 'add5' })}>+5</button>
    <button onClick={() => dispatch({ kind: 'double' })}>×2</button>
    <button onClick={() => dispatch({ kind: 'halve' })}>÷2</button>
  </div>
)
```

Button click → `dispatch({ kind: 'increment' })` → React calls `reducer(0, { kind: 'increment' })` → reducer returns `1` → state update → component re-render → UI mein `1` dikhta hai.

Compare karo useState version se:

| useState | useReducer |
|----------|-----------|
| 6 alag `setCount(c => ...)` calls scattered | Ek `dispatch({ type })` — sab same pattern |
| Naya action = naya function banana padega | Naya action = type + case add karo, bas |
| Logic kahin bhi ho sakti hai (scattered) | Logic **exactly** reducer mein hai (ek jagah) |

## TypeScript Ke Saath — Discriminated Unions

Abhi counter mein 6 actions ka `Action` type banaya — sabka sirf `kind` tha (`{ kind: 'increment' }`). Lekin real app mein actions ke saath extra data bhi aata hai — jaise product, id, quantity. TypeScript ka **discriminated union** yahan kaam aata hai.

### Pehle Samjho — Union Type Kya Hai

Union ka matlab "ek saath kaai cheezein" nahi, balki **"inmein se koi ek"**.

```tsx
// Primitives ke saath union
type Status = 'loading' | 'success' | 'error'
// Status ya toh 'loading' HO SAKTA HAI, ya 'success', ya 'error'
// Ek baar mein sirf ek value hogi — teeno ek saath nahi ho sakte
```

Yahan `|` (pipe) ka matlab hai **"ya"** — `'loading' | 'success'` = 'loading' **ya** 'success'.

Ab dekho — primitives mein `|` middle mein likhte hain:

```tsx
type Status = 'loading' | 'success' | 'error'
```

Objects ke saath bhi yahi pattern hai, bas readability ke liye `|` ko **next line ki shuruaat** mein likhte hain:

```tsx
type Action =
  | { kind: 'increment' }
  | { kind: 'decrement' }
```

Dono same kaam hai — `'loading' | 'success'` waisa hi hai jaise `| { kind: 'increment' }`. Sirf formatting ka fark hai. TypeScript dono ko ek tarah treat karta hai.

### `type` Keyword vs Property `kind` — Fark Samjho

Dekho, do alag `type` words hain jo same dikhte hain but different kaam karte hain:

```tsx
type  CartAction  =  { kind: 'ADD_ITEM'; product: Product }
 ↑ keyword            ↑ property name — kuch bhi ho sakta hai
```

- **`type CartAction =`** — yeh **TypeScript ka keyword** hai. Reserved hai. Isse naya type banate hain.
- **`{ kind: 'ADD_ITEM' }`** — yeh **object ki property** hai. Sirf ek naam hai. Tum `kind`, `type`, `actionType` — kuch bhi rakh sakte ho.

Hum yahan `kind` use kar rahe hain property naam ke liye (taaki `type` keyword se confuse na ho). Convention mein React/Redux projects `type` use karte hain, but `kind` bhi perfectly valid hai — dono same kaam karte hain.

### Ab Samjho — "Discriminated" Kyun Kehte Hain?

"Discriminate" ka matlab hai **"fark karna"** ya **"pehchanna"**. Jaise police criminal ko "discriminate" karti hai — "yeh wohi hai, yeh nahi hai."

Yahan `kind` property woh **pehchaan** hai jo batati hai ki **kaunsa action hai**:

```tsx
type CartAction =
  | { kind: 'ADD_ITEM'; product: Product }
  // ↑ Yeh action hai jisme kind = 'ADD_ITEM' hai
  | { kind: 'REMOVE_ITEM'; id: number }
  // ↑ Yeh action hai jisme kind = 'REMOVE_ITEM' hai
```

`kind` property ko **discriminant** (pehchaan) kehte hain. Jaise har insaan ka Aadhar number unique hota hai — waise hi har action ka `kind` alag hota hai. TypeScript `kind` ki value dekh ke turant pehchaan leta hai "yeh kaunsa action hai."

Discriminated union ka matlab — union jisme ek common property (discriminant) hai jo batati hai "abhi kaunsa member active hai."

### Payload Kya Hai?

`kind` ke alawa jo bhi properties hain — woh **payload** hai. "Payload" ka simple matlab **"extra data jo action ke saath bheja gaya"** — woh actual cheez jispe kaam karna hai.

Jaise delivery wala parcel leta hai jisme address likha hota hai (discriminant) aur andar actual product hota hai (payload):

| Action | Discriminant (pehchaan — `kind`) | Payload (extra data) |
|--------|----------------------------------|---------------------|
| `ADD_ITEM` | `kind: 'ADD_ITEM'` | `product: Product` |
| `REMOVE_ITEM` | `kind: 'REMOVE_ITEM'` | `id: number` |
| `UPDATE_QTY` | `kind: 'UPDATE_QTY'` | `id: number, quantity: number` |
| `CLEAR_CART` | `kind: 'CLEAR_CART'` | Koi payload nahi |

Payload optional hai — kuch actions mein extra data hota hai, kuch mein nahi. `CLEAR_CART` ko koi extra data nahi chahiye — bas "cart khaali karo" ka action kaafi hai.

### Ek Rule Hai

Jo bhi property discriminant banani ho (`kind`, `type`, `actionType` — kuch bhi), woh **har union member mein common** honi chahiye. Agar kisi action mein `kind` hai aur kisi mein `type`, toh TypeScript confuse ho jayega — usse pata nahi chalega ki discriminant kaunsa property hai.

### TypeScript Kaise Discriminate Karta Hai?

Jab tum `switch (action.kind)` likhte ho, TypeScript har `case` ke andar action ka structure **narrow** (specific) kar deta hai — matlab sirf woh properties allow karta hai jo us particular action mein hain:

```tsx
function cartReducer(state: CartState, action: CartAction) {
  switch (action.kind) {
    case 'ADD_ITEM':
      // Yahan action = { kind: 'ADD_ITEM'; product: Product }
      // TypeScript jaanta hai: action.product exists ✅
      // action.id ❌ — error, is action mein id nahi hai
      return { ...state, items: [...state.items, action.product] }

    case 'REMOVE_ITEM':
      // Yahan action = { kind: 'REMOVE_ITEM'; id: number }
      // action.id exists ✅, action.product ❌
      return { ...state, items: state.items.filter(i => i.id !== action.id) }

    case 'CLEAR_CART':
      // Yahan action = { kind: 'CLEAR_CART' }
      // Koi extra property nahi — sirf kind
      return initialState
  }
}
```

Iska fayda:
1. **Galti pakad leta hai** — `REMOVE_ITEM` case mein `action.product` likhoge toh TypeScript error dega kyunki `REMOVE_ITEM` mein product hai hi nahi
2. **Auto-complete** — `action.` type karte hi sirf wahi properties dikhengi jo us action mein hain
3. **Refactor safe** — kisi action ka payload change kiya (jaise `product` remove kiya) toh har jagah error dikhega jahan galat use ho raha hai

### Visual Summary

```
CartAction ek union hai — multiple possible shapes
    │
    ├── { kind: 'ADD_ITEM'; product: Product }        ← discriminant: 'ADD_ITEM'
    ├── { kind: 'REMOVE_ITEM'; id: number }            ← discriminant: 'REMOVE_ITEM'
    ├── { kind: 'UPDATE_QTY'; id: number; qty: number } ← discriminant: 'UPDATE_QTY'
    ├── { kind: 'APPLY_COUPON'; code: string }         ← discriminant: 'APPLY_COUPON'
    └── { kind: 'CLEAR_CART' }                         ← discriminant: 'CLEAR_CART'

switch (action.kind) {
  case 'ADD_ITEM': → TypeScript narrows to { kind: 'ADD_ITEM'; product: Product }
  case 'REMOVE_ITEM': → TypeScript narrows to { kind: 'REMOVE_ITEM'; id: number }
}
```

## Real Example — Shopping Cart (Step by Step)

Abhi tak discriminate unions ka theory padha. Ab ek real shopping cart banate hain — lekin code dump nahi karenge. **Step by step banayenge, har decision ke peeche ka logic samjhenge.**

### Step 1 — Socho: Kya Chahiye?

Coder ki tarah socho. Koi bole "cart banao." Tum kya karte ho? Pehle sochte ho — kaunsa data chahiye, kaunsa actions chahiye.

**State mein kya hoga?**
- Items jo user ne add kiye
- Coupon code agar lagaya hai
- Discount percentage

**Actions kya honge?**
- Item add karein
- Item remove karein
- Quantity change karein
- Coupon lagayein
- Cart khaali karein

Yeh sochne ke baad hi code likhna shuru karte hain.

### Step 2 — Ek Item Ka Shape: CartItem (interface kyun?)

Coder ab sochta hai: "Item mein kya fields honge?" Har cart item mein yeh hoga:

```tsx
// src/types/cartTypes.ts
interface CartItem {
  id: number       // product unique id
  name: string     // product name (display ke liye)
  price: number    // per unit price
  quantity: number  // kitne units cart mein hain
}
```

**Yahan `interface` kyun, `type` kyun nahi?**

Dono kaam karte hain, lekin different use cases ke liye better hain:
- **`interface`** — object ka shape define karna ho tab use karo. Interface ka matlab "yeh object kaise dikhega." React mein objects ke liye interface common pattern hai.
- **`type`** — union banana ho tab use karo (jaise `CartAction` jisme multiple shapes hain).

Rule of thumb: Agar object ka structure describe karna hai → `interface`. Agar union banana hai → `type`.

### Step 3 — CartState: Pura State Ek Saath

Abhi tak multiple `useState` calls scattered thi. Ab saara state **ek interface** mein bundle karte hain:

```tsx
// src/types/cartTypes.ts
interface CartState {
  items: CartItem[]    // array of CartItem
  coupon: string       // coupon code, agar lagaya toh
  discount: number     // discount % (0 means no discount)
}
```

**Coder kyun aisa karta hai?** Kyunki jab saara state ek jagah ho, toh:
1. Debugging easy — ek object mein sab dikhta hai
2. Reset karna easy — `return initialCart` karo, sab reset
3. Actions multiple fields ek saath change kar sakte hain

### Step 4 — Initial State

```tsx
// src/reducers/cartReducer.ts
const initialCart: CartState = {
  items: [],
  coupon: '',
  discount: 0,
}
```

Bas initial values — kuch nahi hai cart mein abhi.

### Step 5 — Actions Define Karna (Omit Samjho)

Ab aata hai interesting part — actions. 5 actions hain. Har action ka alag payload (extra data) hai:

```tsx
// src/types/cartTypes.ts
type CartAction =
  | { kind: 'ADD_ITEM'; product: Omit<CartItem, 'quantity'> }
  | { kind: 'REMOVE_ITEM'; id: number }
  | { kind: 'UPDATE_QTY'; id: number; quantity: number }
  | { kind: 'APPLY_COUPON'; code: string }
  | { kind: 'CLEAR_CART' }
```

**Har action ko detail mein samjho:**

| Action | kind | Payload | Kyun? |
|--------|------|---------|-------|
| ADD_ITEM | `'ADD_ITEM'` | `product: Omit<CartItem, 'quantity'>` | User sirf product info bhejta hai — quantity reducer decide karega |
| REMOVE_ITEM | `'REMOVE_ITEM'` | `id: number` | Item hatane ke liye sirf id chahiye |
| UPDATE_QTY | `'UPDATE_QTY'` | `id: number, quantity: number` | Quantity change karni hai, id + nayi quantity |
| APPLY_COUPON | `'APPLY_COUPON'` | `code: string` | Coupon code — reducer validate karega |
| CLEAR_CART | `'CLEAR_CART'` | Kuch nahi | Sirf "cart khaali karo" ka action |

**Ab Omit samjho** — yeh ek TypeScript utility type hai.

```tsx
Omit<CartItem, 'quantity'>
```

Iska matlab: "CartItem ka type lo, lekin usme se `quantity` property hata do."

Kyunkar `CartItem` mein quantity hai:
```tsx
interface CartItem { id: number; name: string; price: number; quantity: number }
```

Lekin jab user koi product add karta hai, toh woh quantity nahi bhejta — "yeh product daal do" kehta hai. Kitne quantity? **Reducer decide karega** — agar already hai toh increment, nahi toh 1 se start.

Isliye `Omit<CartItem, 'quantity'>` ka result hota hai:
```tsx
{ id: number; name: string; price: number }
```

Quantity apne aap add ho jayegi reducer mein.

**Coder kyun Omit use karta hai?** Duplicate type banane ki zaroorat nahi. `CartItem` already defined hai. Usme se sirf quantity hata do — `Omit` karo. TypeScript automatic adjust karega. Baad mein `CartItem` mein koi naya field add kiya (jaise `imageUrl`), toh `Omit<CartItem, 'quantity'>` automatically include karega — alag se update nahi karna padega.

Without Omit, coder ko alag type banana padta:
```tsx
interface ProductInput { id: number; name: string; price: number }
```
Do jagah maintain karna padta. Omit se duplication nahi hota.

### Step 6 — Reducer Function (Ab Logic Likho)

Ab reducer banate hain — **coder ka dimaag yahan sabse zyada lagta hai** kyunki yahi central logic hai.

```tsx
// src/reducers/cartReducer.ts
import { useReducer } from 'react'

// --- Types (src/types/cartTypes.ts se import karenge) ---

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.kind) {
    case 'ADD_ITEM': {
      // Coder sochta hai: "Pehle check karo ki item already cart mein hai ya nahi"
      const existing = state.items.find(i => i.id === action.product.id)

      if (existing) {
        // ✅ Already hai — quantity increment karo (1 aur add)
        // Baaki items unchanged
        return {
          ...state,
          items: state.items.map(i =>
            i.id === action.product.id
              ? { ...i, quantity: i.quantity + 1 }
              : i
          ),
        }
      }

      // ✅ Naya item hai — cart mein add karo, quantity 1 se start
      return {
        ...state,
        items: [...state.items, { ...action.product, quantity: 1 }],
      }
    }

    case 'REMOVE_ITEM':
      // Item ko filter out karo — jiska id match kare, woh hat jayega
      return {
        ...state,
        items: state.items.filter(i => i.id !== action.id),
      }

    case 'UPDATE_QTY':
      // Specific item ki quantity change karo
      return {
        ...state,
        items: state.items.map(i =>
          i.id === action.id ? { ...i, quantity: action.quantity } : i
        ),
      }

    case 'APPLY_COUPON':
      // Coupon code check karo — valid hai toh discount apply karo
      return {
        ...state,
        coupon: action.code,
        discount: action.code === 'SAVE10' ? 10 : 0,
      }

    case 'CLEAR_CART':
      // Wapas initial state — saab kuch reset
      return initialCart

    default:
      return state
  }
}
```

**Reducer ka pattern samjho:** Har case mein:
1. State copy karo (`...state`) — immutability
2. Sirf woh field change karo jo action se related hai (items, coupon, discount)
3. Baaki fields unchanged rehne do

### Step 7 — Component Mein Use Karo

Ab component simple hai — state read karo, dispatch karo:

```tsx
// src/components/Cart.tsx
export default function Cart() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart)

  return (
    <div>
      <h2>Cart ({cart.items.length} items)</h2>

      {cart.items.map(item => (
        <div key={item.id}>
          <p>
            {item.name} x {item.quantity} = ${item.price * item.quantity}
          </p>
          <button onClick={() => dispatch({ kind: 'REMOVE_ITEM', id: item.id })}>
            Remove
          </button>
        </div>
      ))}

      {cart.coupon && <p>Coupon: {cart.coupon} — {cart.discount}% off</p>}

      <button onClick={() => dispatch({ kind: 'CLEAR_CART' })}>
        Clear Cart
      </button>
    </div>
  )
}
```

Dekh rahe ho? Har dispatch call mein **sirf wohi data bhej rahe hain jo us action ko chahiye**:
- `REMOVE_ITEM` → sirf `id`
- `CLEAR_CART` → kuch nahi, bas `kind`

Agar galti se `dispatch({ kind: 'REMOVE_ITEM' })` bina `id` ke likha, toh TypeScript error dega — "REMOVE_ITEM mein id required hai." Yahi discriminated union ka fayda hai.

### Coder's Perspective — Pooora Flow

1. User "Add" click karta hai → component `dispatch({ kind: 'ADD_ITEM', product })` call karta hai
2. React Internally `cartReducer(currentState, action)` call karta hai
3. Reducer `switch (action.kind)` mein case 'ADD_ITEM' enter karta hai
4. Check karta hai — product already exists?
   - ✅ Ha → quantity increment
   - ❌ Nahi → new item add (quantity: 1)
5. Naya state object return karta hai (immutable update)
6. React state compare karta hai — change hai? → component re-render
7. UI mein naya item reflect hota hai

## useReducer vs useState — Kab Kya Use Karein

**useState use karo jab:**
- State simple ho (number, string, boolean)
- Ek ya do independent state variables ho
- State logic simple ho — ek action ek variable change kare

**useReducer use karo jab:**
- State object complex ho (multiple fields)
- Multiple actions same state ko change karte hoon
- Actions ke beech dependencies hoon (ek action multiple fields change kare)
- State logic ko centralize karna ho (debugging easy)

## Common Mistake — Reducer Mein Side Effects

Reducer **pure function** hona chahiye. Andar API call mat karo, localStorage mat likho, `Math.random()` mat karo:

```tsx
// ❌ Galat — side effect reducer mein
function reducer(state, action) {
  case 'SAVE':
    localStorage.setItem('cart', JSON.stringify(state)) // ❌ side effect!
    return { ...state, saved: true }
}

// ✅ Sahi — side effect component mein, reducer sirf state change kare
function reducer(state, action) {
  case 'SAVE':
    return { ...state, saved: true }
}
```

## Summary

✅ **useReducer** — complex state ke liye — ek central function saare state changes handle karta hai  
✅ **Action** — object jisme `type` hota hai aur optional payload  
✅ **dispatch(action)** — action bhejne ka tarika  
✅ **Reducer** — pure function — `(state, action) => newState`  
✅ **TypeScript + discriminated unions** — har action type ke hisaab se proper typing  
✅ useState simple ke liye, useReducer complex ke liye  
✅ Reducer pure rakhna — side effects bahar karo
