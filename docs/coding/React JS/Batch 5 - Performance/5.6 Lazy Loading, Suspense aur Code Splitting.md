## What We've Covered So Far

In 5.5, we built the Re-render Visualizer — `memo`, `useMemo`, and `useCallback` skipping work the user never sees — and in 5.4, the React Compiler doing all of that memoization automatically. All of those make React do **less work after the app has loaded**.

This topic flips to the other half: making the app **load faster in the first place**. When the app grows, the bundle gets big, and the user waits longer staring at a blank screen. The solution: code splitting.

---

## The Problem — Everything in One Bundle

First, what a bundler is. Your React app is spread across dozens of files — components, helpers, styles, libraries. Browsers don't want to fetch hundreds of tiny files, so tools like Vite or Webpack gather them all and combine them into one big JavaScript file (or a few). That combined file is the **bundle**.

Think of a restaurant that, the moment you sit down, hands you one giant book with the starters menu, mains menu, desserts menu, and drinks menu all glued together — even if you only wanted coffee. You have to carry the whole book before you can order anything.

That's your app. When someone opens the login page, their browser downloads the code for the dashboard, the charts, the settings — all of it — before the login page even shows up. On a slow connection, that's a long wait staring at nothing.

**Why does the bundler do this?** Because at build time it has no idea which page the user will visit first, so it plays safe and puts everything in. There's no concept of "this component isn't needed right now, download it later" — until you use code splitting.

---

## So Why Doesn't the React Compiler Fix This Automatically?

A fair question after 5.4. The React Compiler can automate memoization because that problem only needs the compiler to read your code and figure out what depends on what — a data-flow question, answerable from the source itself.

Code splitting is a different question: "which page will the user visit, and when?" That's about human behavior, not code. No tool can know whether people open the dashboard right away or never touch settings. And splitting too aggressively can make things *worse* — lots of tiny downloads and loading spinners everywhere.

So the decision stays with you. The ecosystem has automated parts of it — frameworks like Next.js and tools like React Router's framework mode split code by route automatically, so you don't write the lazy calls yourself — but that's the framework on top of React, not React itself.

Before we meet React's own tools for this, one timeline question first: when does this bundling actually happen?

---

## Build Time vs Run Time — When Bundling Actually Happens

There are two separate moments, and mixing them up makes everything else confusing:

**Build time** — on your machine, or on Vercel's build machine when you push your project. You run the build command, the bundler reads all your files, and produces the final JavaScript files. Those files land in a folder called `dist` (short for *distribution* — exactly what gets uploaded to a server).

**Run time** — when a user opens your site from anywhere, their browser downloads those files from the server, and React starts running inside the browser.

Vercel does the build for you on every push and copies your files to servers around the world, so the download comes from one near the user. But the *size* of the bundle is the same everywhere — a big bundle is still slow, no matter which server it comes from.

Here's the key link: code splitting changes what happens at **build time** (several smaller files instead of one), so that at **run time** the browser only fetches the ones it needs.

---

## Code Splitting — Break the Bundle into Chunks

The idea, at the concept level: instead of one big bundle, tell the bundler to split it into smaller pieces, called **chunks**. The login page gets its own small chunk, the dashboard gets its own chunk, and so on.

Then the browser only downloads the chunk for the page the user is visiting. The dashboard chunk waits on the server until someone actually goes to the dashboard.

Two benefits:
1. **Faster initial load** — only the code for what the user sees right now is downloaded
2. **On-demand loading** — other chunks load later, when the user navigates to that page or feature

That whole idea is called **code splitting**. Now the practical question it raises: how do we tell the bundler *where* to split?

---

## Dynamic Import — How the Bundler Knows Where to Split

We don't configure the bundler directly. We change one thing: how we import a component.

Normally you write a regular import at the top of the file:

```tsx
// Regular import — the bundler says "needed from the start" → main bundle
import HeavyChart from './HeavyChart'
```

A **dynamic import** looks different. It says "load this file *later*, when I ask for it":

```tsx
// Dynamic import — the bundler says "needed later" → its own chunk
const chart = await import('./HeavyChart')
```

`import()` returns a promise — just like fetching a URL — so you `await` it until the file arrives. When the bundler sees a dynamic import anywhere in your code, it automatically puts that file in its own separate chunk. That one line is what tells the bundler where to split.

But bundling is only the build-time half. At run time, when React is about to render the component and its chunk isn't downloaded yet, React needs to know: trigger the import, wait for it, then render. That's a React problem — and React has a tool for it.

---

## React.lazy — Turning the Dynamic Import into a Component

`React.lazy` is the small wrapper that connects the dynamic import to React's rendering. It takes a function that returns a dynamic import, and gives you back something you can treat as a component:

```tsx
import { lazy } from 'react'

const HeavyChart = lazy(() => import('./HeavyChart'))
```

When `HeavyChart` is first rendered, React internally calls that `import()` — the download starts at that moment, not before. The code only crosses the network when the component is actually about to appear.

And the rendering side doesn't change at all — you still write `<HeavyChart />` wherever you want it. Only the import line is different. The bundler sees the dynamic import inside `lazy`, splits the chunk, and React handles the waiting.

But that waiting raises the next question: the first time React renders that component, the chunk isn't there yet. A download takes a moment — what does the user see in that gap?

---

## Suspense — What the User Sees While the Chunk Downloads

You've seen the answer to this question before, outside React: a skeleton screen, a spinner, or just "Loading..." text while content is on its way. **Suspense** is the React component that shows exactly that during the wait.

You give it a `fallback` prop — whatever you want displayed while the chunk is downloading:

```tsx
import { Suspense } from 'react'

<Suspense fallback={<div>Loading...</div>}>
  <HeavyChart />
</Suspense>
```

The full flow:

1. Something causes `HeavyChart` to render
2. Its chunk isn't downloaded yet — React can't render it
3. React says "I can't render this yet" — Suspense catches that and shows the fallback
4. Chunk finishes downloading → fallback disappears → `HeavyChart` renders

Visual mapping:

```
React is about to render a lazy component
    │
    ├── Chunk already loaded?
    │   ├── Yes → Render immediately
    │   └── No → Show Suspense fallback, start download
    │
    ▼
Chunk downloaded
    │
    ▼
Component renders, fallback disappears
```

Two things worth pinning down here:

**The chunk downloads only once.** Hide the chart, show it again — no second download. The first render fetched it; from then on it's already there.

**A lazy component must always be inside a Suspense.** If React tries to suspend with nothing to fall back on, it throws an error. We'll see that mistake in detail later.

And one scope note: with lazy loading, the thing being waited on is *code downloading*, not data. Suspense can also handle data fetching in some setups — for today, just think of it as waiting for the code.

Now let's see the whole thing in code — at the component level first, then scaled up to routes.

---

## Minimal Code — A Lazy Component

Two files. First, the heavy component — this becomes its own chunk:

```tsx
// HeavyChart.tsx
export default function HeavyChart() {
  return <div>This is the heavy chart</div>
}
```

Then the component that uses it — with a button, so the chart isn't needed on first render:

```tsx
import { lazy, Suspense, useState } from 'react'

// Lazy import — HeavyChart goes into a separate chunk
const HeavyChart = lazy(() => import('./HeavyChart'))

export default function Dashboard() {
  const [showChart, setShowChart] = useState(false)

  return (
    <div>
      <button onClick={() => setShowChart(true)}>
        Show Chart
      </button>

      {showChart && (
        <Suspense fallback={<div className="p-4 text-gray-500">Chart is loading...</div>}>
          <HeavyChart />
        </Suspense>
      )}
    </div>
  )
}
```

Walk through the two lazy-related lines. `lazy(() => import('./HeavyChart'))` tells React to fetch the chart's chunk only when it's about to render. The `<Suspense>` wrapper around it shows the loading text during that fetch. Everything else — the button, the state, the conditional render — is plain React.

Open the browser's Network tab and click the button — a new `.js` file downloads at that moment. That's the `HeavyChart` chunk. It wasn't there before the click — it loads on demand, right when it's needed.

---

## Flow — What Happens When You Click the Button

Let's trace that click moment by moment:

1. `showChart` state becomes `true`
2. React tries to render `HeavyChart`
3. `React.lazy` triggers — an internal `import()` call starts
4. The browser downloads the `HeavyChart` chunk
5. React shows the Suspense fallback (loading text)
6. Download completes → Suspense fallback is removed → `HeavyChart` renders

That's component-level splitting. The same trick scales up to whole pages — which is where code splitting becomes truly worth it.

---

## Building Up — Route-Level Splitting

In a real app, the most common use of code splitting is splitting by route — each page becomes its own chunk and only loads when someone visits it.

A mixed example first — one route lazy, one normal, so you can see both behaviors side by side:

```tsx
import { lazy, Suspense } from 'react'
import { BrowserRouter, Routes, Route, Link } from 'react-router-dom'
import Movies from './routes/Movies'

const Library = lazy(() => import('./routes/Library'))

export default function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/movies">Movies</Link>
        <Link to="/library">Library</Link>
      </nav>

      <Suspense fallback={<div>Loading...</div>}>
        <Routes>
          <Route path="/movies" element={<Movies />} />
          <Route path="/library" element={<Library />} />
        </Routes>
      </Suspense>
    </BrowserRouter>
  )
}
```

Walk through it. Movies is a normal import — the bundler glues it into the main bundle, so it downloads upfront with everything else. Library's lazy line tells the bundler to give it its own chunk. The routes and the rendering are completely normal — only the import style differs. When a user visits `/movies`, everything is already there; visiting `/library` triggers the chunk download, and Suspense shows "Loading" until it arrives.

One requirement worth noting: `lazy` expects the imported module to have a **default export** — `export default function Library() { ... }` — because that default export is what React renders.

One wording point, from the timeline earlier: this splitting decision was made at **build time** on the build machine. When the user later visits `/library`, the browser is only downloading a chunk that already sat on the server.

In a real app, most routes get the lazy treatment:

```tsx
const Home = lazy(() => import('./routes/Home'))
const Dashboard = lazy(() => import('./routes/Dashboard'))
const Analytics = lazy(() => import('./routes/Analytics'))
const Settings = lazy(() => import('./routes/Settings'))
```

The JSX stays exactly as it was above — the nav, the Suspense around Routes, the Route definitions. The only thing that changed is the import lines. Now the user opens `/` — only the Home chunk downloads. Navigate to `/dashboard` — only then the Dashboard chunk downloads. Initial load stays fast.

---

## When to Use Lazy Loading — And When Not To

The decision question for any component or route: **is it needed immediately, and how heavy is it?** Three cases to sharpen the judgment:

- **A small button on the home page** — no. It's tiny *and* needed right away, so a separate download would cost more than it saves.
- **A rich text editor that only opens when the user clicks Compose** — yes, perfect candidate. Heavy, and most sessions never touch it.
- **A settings page** — yes. Most users visit rarely, if at all, so splitting it out keeps the first load lean.

The full lists:

**❌ Don't use lazy loading when:**
- The component is small — the overhead of lazy loading outweighs the benefit
- The component is needed on the initial render — lazy just adds unnecessary delay
- In SSR environments — older React (17 and before) couldn't lazy-load server-side. React 18+ supports `lazy` and `Suspense` on the server too, and frameworks like Next.js handle it with their own conventions. We're focused on the client side here.

**✅ Use lazy loading when:**
- Heavy components (charts, rich text editors, image editors)
- Routes the user visits later
- Conditional components (modals, drawers, tab content)
- Third-party libraries that are heavy (like `moment.js`, `lodash`)

Which brings us to the mistake almost everyone makes at least once.

---

## Common Mistake — Forgetting Suspense

A lazy component must be used inside `Suspense`, or you get an error:

```tsx
// ❌ Wrong — no Suspense
const HeavyChart = lazy(() => import('./HeavyChart'))
function App() {
  return <HeavyChart /> // Error: A component suspended while rendering
}

// ✅ Correct — wrap in Suspense
function App() {
  return (
    <Suspense fallback={<p>Loading...</p>}>
      <HeavyChart />
    </Suspense>
  )
}
```

Here's what makes this mistake sneaky: **it's a run-time error, not a build-time one.** The build succeeds — the code is perfectly valid — and ESLint won't normally catch it either. The problem only shows up when the app runs and React first tries to render the lazy component. It throws "A component suspended while rendering" with no fallback to show, and in many setups that blanks the page.

On a full page refresh, everything resets and the error comes back. If the chunk already loaded — say the component rendered successfully somewhere earlier — it might render without complaining on a revisit. But don't rely on that: the first attempt without a fallback is a real bug, even if it sometimes seems to recover.

So the only protection is remembering the rule, or testing the page.

---

## Summary

✅ **Code splitting** — breaking the bundle into smaller chunks at build time, so the browser only downloads what it needs  
✅ **Dynamic import** — creates the chunk at build time, and downloads it on demand at run time  
✅ **React.lazy** — wraps the dynamic import so React treats it as a component, starting the import the first time it renders  
✅ **Suspense** — shows the `fallback` while the chunk downloads; lazy components must live inside it  
✅ **Route-level splitting** — the most common pattern — each route gets its own chunk  
✅ Lazy-load heavy, later-needed components — not small or first-render ones
