## The Problem — Parent Re-renders → Child Re-renders Too

Take a simple component:

```tsx
function ExpensiveCard() {
  console.log('ExpensiveCard render')
  return <div className="p-4 border rounded">I am expensive</div>
}

function Dashboard() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
      <ExpensiveCard />
    </div>
  )
}
```

Notice something? Every time `Dashboard` re-renders (when count changes) — `ExpensiveCard` re-renders too, even though nothing about it changed.

Open your browser console — every click prints "ExpensiveCard render".

**Why is this a problem?** It's React's default behavior — when the parent renders, the child renders too. React has no way to know that `ExpensiveCard`'s props didn't change. It just runs the render.

For a small component, this doesn't matter. But if `ExpensiveCard` has a heavy calculation inside, or if it's a list item (100 items), re-rendering unnecessarily every single time is wasteful.

---

## Higher-Order Component (HOC) — Understanding This First

`React.memo` is called a "higher-order component." Let's understand what that means first.

You probably know about **higher-order functions** in JavaScript — things like `map`, `filter`, `setTimeout`. These either take a function as an argument or return a function:

```tsx
function multiplier(factor) {
  return function (value) {
    return value * factor
  }
}
const double = multiplier(2)
console.log(double(5)) // 10
```

`multiplier` is a higher-order function because it returns another function.

A **Higher-Order Component (HOC)** is the same pattern, but for React components. An HOC is a function that:
1. Takes a component (as an argument)
2. Adds some extra functionality
3. Returns a new component

```tsx
const EnhancedComponent = withExtraFeature(WrappedComponent)
```

Think of it like a gift wrapping service. You hand over a gift (a component). They wrap it up and hand back a wrapped gift (an enhanced component). The original gift is still there — it just has wrapping added.

**What It Is NOT:** An HOC is not a built-in React API. Only `React.memo` is built-in. Other HOCs (like Redux's `connect()`, `withRouter()`) are patterns that developers create themselves.

### Component Types in React

In React, there are technically only two component types:

| Type | What It Is |
|------|------------|
| **Functional Component** | A function that returns JSX. Hooks can be used. This is modern React. |
| **Class Component** | A `class extends React.Component`. Uses lifecycle methods. Legacy / older code. |

Beyond these, there are **patterns** that enhance or modify components:

| Pattern | What It Does |
|---------|--------------|
| **HOC** | Takes a component, returns an enhanced component |
| **React.memo** | Built-in HOC — skips render if props haven't changed |
| **React.PureComponent** | Built-in shallow comparison for class components |

Now let's get into React.memo — which is a **built-in HOC**...

---

## React.memo — What It Is

It's straightforward: React.memo "remembers" (memoizes) a component's output. When the parent re-renders, memo checks — "have this component's props changed since last time?" If no — skip the render, return the cached output.

Syntax:

```tsx
const ExpensiveCard = React.memo(function ExpensiveCard() {
  console.log('ExpensiveCard render')
  return <div className="p-4 border rounded">I am expensive</div>
})
```

Or define the functional component separately, then wrap it with memo:

```tsx
function ExpensiveCard() {
  console.log('ExpensiveCard render')
  return <div className="p-4 border rounded">I am expensive</div>
}

export default React.memo(ExpensiveCard)
```

**What's happening internally?** `React.memo` wraps the component. When the parent's render triggers, memo internally uses `Object.is` to compare props. If props are the same — React reuses the previously rendered output, the component function doesn't even get called.

**Note:** Writing `React.memo(...)` everywhere gets repetitive. So from here on, we'll use `import { memo } from 'react'` and just write `memo(...)` — both do exactly the same thing, importing `memo` directly is just a shorter way to write it.

Visual mapping:

```
Parent re-renders
    │
    ▼
React.memo(Child)
    │
    ├── Props same? → Skip render (cached output)
    │
    └── Props different? → Normal render
```

## Minimal Code — Add Memo, See the Difference

```tsx
import { useState, memo } from 'react'

const ExpensiveCard = memo(function ExpensiveCard() {
  console.log('render')
  return <div className="p-4 border rounded">I am expensive</div>
})

export default function Dashboard() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
      <ExpensiveCard />
    </div>
  )
}
```

Now check the console — change count and "render" will only print once, on the first render. On subsequent clicks, only `count` updates, `ExpensiveCard` doesn't render.

Notice? Memo skipped the render because props weren't passed (and `Object.is(undefined, undefined)` = true). A simple case.

---

## Memo with Props

When a component receives props, memo does its job when props are **the same**:

```tsx
const Greeting = memo(function Greeting({ name }: { name: string }) {
  console.log('Greeting render:', name)
  return <p>Hello, {name}!</p>
})

function App() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>Clicked: {count}</button>
      <Greeting name="Vin" />
    </div>
  )
}
```

Every click changes `count` → `App` re-renders → `Greeting`'s props are checked. `name` is the same ("Vin") → memo skips the render. Only the first time "Greeting render: Vin" prints.

But if `name` changes:

```tsx
<Greeting name={count > 5 ? 'Vin' : 'Guest'} />
```

Once count crosses 5, `name` changes — memo re-renders because props changed.

---

## Flow — What Happens on Button Click

1. `count` state changes
2. `App` re-renders
3. `Greeting` component begins to render (because it's inside `App`)
4. But `Greeting` is wrapped in memo — React internally compares props using `Object.is`
5. Previous `name` ("Vin") === new `name` ("Vin") → true
6. React reuses the cached output — `Greeting`'s function is never called
7. "Greeting render:" never prints to the console

## Real Scenario — Todo List

Imagine a list — 100 items. Each item is its own component. Without memo, if the parent list's state changes (like deleting one item), all 100 items re-render. Add memo — only the item whose actual data changed will re-render.

```tsx
const TodoItem = memo(function TodoItem({ todo, onToggle }: {
  todo: { id: number; text: string; done: boolean }
  onToggle: (id: number) => void
}) {
  console.log('TodoItem render:', todo.id)
  return (
    <li>
      <input type="checkbox" checked={todo.done} onChange={() => onToggle(todo.id)} />
      {todo.text}
    </li>
  )
})
```

Notice the key takeaway here? All the examples so far pass **primitive** props — strings (`name="Vin"`), numbers (`count`), booleans. Primitive types are compared directly by **value** in React. `"Vin" === "Vin"` is always true — so memo skips the render.

But in the real world, objects, arrays, and functions also come in as props. And for these, comparison is done by **reference**, not by value. This is where memo stops working.

---

## When Memo Won't Work — The Reference Equality Problem

### Reference vs Value — Understanding This First

In JavaScript, there are two types of comparisons:

**Value comparison** — for primitive types:
```tsx
console.log("Vin" === "Vin")           // true
console.log(25 === 25)                  // true
console.log(true === true)              // true
```
React compares these directly by value — simple.

**Reference comparison** — for objects, arrays, functions:
```tsx
const obj1 = { name: 'Vin' }
const obj2 = { name: 'Vin' }
console.log(Object.is(obj1, obj2))      // false ❌

const arr1 = [1, 2, 3]
const arr2 = [1, 2, 3]
console.log(Object.is(arr1, arr2))      // false ❌

function fn1() {}
function fn2() {}
console.log(Object.is(fn1, fn2))        // false ❌
```

They look the same, but JavaScript treats them as **different**. Why? Because objects/arrays/functions get a unique **address** in memory. `Object.is` compares those addresses, not the contents.

**Analogy:** Two people can have the same Aadhaar number — impossible. Even if they're identical twins, their Aadhaar numbers are different. React does the same thing — it checks the Aadhaar number (reference), not the physical appearance (value).

Now back to memo. Internally, `React.memo` uses `Object.is` to compare props. When primitive props were involved, everything was fine — value matching worked. But when objects/functions/arrays come in as props, `Object.is` returns `false` even if the values are identical. And memo thinks "props changed → render."

---

### Case 1: Inline Objects / Arrays

When you pass an object directly as a prop:

```tsx
<Profile user={{ name: 'Vin', age: 25 }} />
```

Every time the parent re-renders, a **new object** is created in memory. New memory address = new reference = `Object.is` returns `false` = memo is useless.

Same problem with arrays:
```tsx
<List items={['a', 'b', 'c']} />
```

---

### Case 2: Inline Functions

This is the most common mistake:

```tsx
<TodoItem onToggle={(id) => toggleTodo(id)} />
```

The arrow function `(id) => toggleTodo(id)` creates a new function object on every render. New reference → memo re-renders.

If you define `onToggle` outside the render or use `useCallback` (covered in detail in 5.3), the reference stays stable and memo does its job:

```tsx
// ❌ New function on every render — memo useless
<TodoItem onToggle={(id) => toggleTodo(id)} />

// ✅ Reference is stable
<TodoItem onToggle={toggleTodo} />
```

---

### Case 3: The Children Prop

This is the most subtle case:

```tsx
<Card>
  <p>Hello</p>
</Card>
```

`children` is also a prop. And JSX gets converted into `React.createElement`:

```tsx
React.createElement(Card, null, React.createElement('p', null, 'Hello'))
```

Every render calls `createElement` — creating a **new React element object**. New reference = memo always re-renders.

The takeaway: if you're passing `children` to a component wrapped in memo, there's no benefit from memo. (Solutions: also memoize the children, don't pass children, or use a separate wrapper component.)

---

### So Is Memo Useless?

No. Memo works when:
- Primitive props are involved (strings, numbers, booleans) — the most common case
- Object/function props are **stabilized** (via `useMemo`/`useCallback`, or defined in the parent's scope)

The problem is only with **inline** objects/functions/children. In all other cases, memo works perfectly.

The solution to this problem is `useMemo` and `useCallback` — these hooks stabilize values/refs so that a new reference isn't created on every render. We'll cover those in detail in 5.2 and 5.3.

---

## When to Use Memo — And When Not To

**❌ Don't use when:**
- The component is trivial (a simple `<span>` or `<div>`)
- The component always receives different props
- Premature optimization — measure first, then apply memo

**✅ Use when:**
- The component is heavy (charts, tables, lists)
- The component renders repeatedly with the same props
- The Profiler clearly shows that memo makes a difference

---

## Common Mistake — "Memo Means It Will Never Re-render"

Wrong. Memo only skips the render when props are **the same**. If any prop changes — memo renders normally. It's not a "magic bullet" that stops all re-renders.

---

## Summary

✅ **React.memo** — a higher-order component that "remembers" a component's output  
✅ Props are the same → skip render, reuse cached output  
✅ Internally compares props using `Object.is`  
✅ Becomes useless with inline objects/functions/children  
✅ Use when the component is heavy, rendering repeatedly with same props  
✅ Don't over-optimize — measure with the Profiler first
