## What We've Covered So Far

In 5.1, we learned `React.memo` — it caches a component, skipping re-renders when props haven't changed. But there was a problem: inline objects create new references on every render, so memo breaks.

Now let's talk about caching **values**.

---

## The Problem — Unrelated State Change → Unnecessary Calculation

Imagine a component with two unrelated states — a `search` and a `count`. They have nothing to do with each other:

```tsx
function Dashboard({ items }: { items: number[] }) {
  const [search, setSearch] = useState('')
  const [count, setCount] = useState(0)

  const filteredItems = items.filter(item => {
    console.log('filter is running')
    return item.toString().includes(search)
  })

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
      <input value={search} onChange={e => setSearch(e.target.value)} />
      <ul>
        {filteredItems.map(item => <li key={item}>{item}</li>)}
      </ul>
    </div>
  )
}
```

Two scenarios here:

**Scenario 1 — Type in the input:** `search` changes → component re-renders → `filter` runs. This makes sense — search changed, so the filtered list should update too.

**Scenario 2 — Click the count button:** Only `count` changes → component re-renders → but `filter` **also** runs! The console prints "filter is running".

This is unnecessary. What does count have to do with the filter? Neither `search` nor `items` changed.

**Why does this happen?** React doesn't know that `items.filter` has no relationship with `count`. React executes the component function top-to-bottom on every render. The `filter` line executes too — whether it's needed or not.

If `items` is an array of 10,000 elements, every count increment re-filters all 10,000 items. A total waste.

---

## useMemo — What It Is

`useMemo` is a hook that **caches (memoizes) a value**. As long as the dependency array hasn't changed, it returns the previously cached value — no re-computation.

Syntax:

```tsx
const cachedValue = useMemo(
  () => computeExpensiveValue(input),
  [input] // dependencies
)
```

**What's happening internally?** On the first render, `useMemo` calls the callback function and caches the result. On subsequent renders — it checks the dependencies. If they're the same (using `Object.is`, same as memo) — it skips calling the callback and returns the cached value. If a dependency changed — it calls the callback again, caches the new result, and returns it.

Visual mapping:

```
Render triggered
    │
    ▼
useMemo(() => compute, [items, search])
    │
    ├── items === oldItems && search === oldSearch?
    │   └── Yes → Return cached value (no compute)
    │
    └── No → Call compute(), cache the new value, return it
```

## Minimal Code — Caching the Filter

Let's fix it with useMemo. The hook tells React — "run this calculation only when these dependencies change":

```tsx
import { useState, useMemo } from 'react'

function Dashboard({ items }: { items: number[] }) {
  const [search, setSearch] = useState('')
  const [count, setCount] = useState(0)

  const filteredItems = useMemo(
    () => {
      console.log('filter is running')
      return items.filter(item => item.toString().includes(search))
    },
    [items, search]
  )

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
      <input value={search} onChange={e => setSearch(e.target.value)} />
      <ul>
        {filteredItems.map(item => <li key={item}>{item}</li>)}
      </ul>
    </div>
  )
}
```

**Check the console now:**

| Action | Filter runs? | Why? |
|--------|-------------|------|
| Click count button | ❌ No | `items` same, `search` same → reuse cached value |
| Type in input | ✅ Yes | `search` changed → dependency change → filter runs |

Click the count button first — nothing prints in the console. Filter didn't run. That's because `useMemo` checked `[items, search]` — both are the same as the previous render — it returned the cached `filteredItems`.

Now type something — console prints "filter is running". Because `search` changed → the dependency list changed → React re-ran the filter.

That's the real power of `useMemo`: expensive calculations only run when their dependencies actually change. On all other re-renders, the cached result is returned.

---

## Flow — Two Scenarios

**Scenario A — Count Button Click (unrelated state change):**
1. `count` state changes
2. `Dashboard` re-renders
3. `useMemo` line executes
4. React checks dependencies: `items` same? Yes. `search` same? Yes.
5. No dependency changed → callback is not called
6. Cached `filteredItems` is returned — no calculation
7. Component renders — UI updates the count, list stays the same

**Scenario B — Type in Input (relevant dependency change):**
1. `search` state changes
2. `Dashboard` re-renders
3. `useMemo` line executes
4. React checks dependencies: `items` same, `search` changed
5. Dependency changed → callback is called → new `filteredItems` is calculated
6. Component renders with the new filteredItems

## useMemo vs Direct Code

Direct code runs on every single render:

```tsx
const result = slowFunction(data)  // called every render
```

`useMemo` only runs when dependencies change:

```tsx
const result = useMemo(() => slowFunction(data), [data])  // only runs when data changes
```

## Building Up — Sorting + Filtering Combo

```tsx
function ProductList({ products }: { products: Product[] }) {
  const [sortBy, setSortBy] = useState('name')
  const [maxPrice, setMaxPrice] = useState(1000)

    return filtered.sort((a, b) => {
      if (sortBy === 'name') return a.name.localeCompare(b.name)
      return a.price - b.price
    })
  }, [products, sortBy, maxPrice])

  // Only runs when products, sortBy, or maxPrice change
  return <div>{/* render processed items */}</div>
}
```

## useMemo + React.memo Combo

In 5.1, we learned `React.memo` — it caches a component, skipping re-renders when props haven't changed. But the issue was: inline objects/arrays create new references on every render, so `Object.is` returns false, and memo re-renders.

This is where `useMemo` comes in — it stabilizes object/array references.

### ❌ Before — Inline Object, Memo Is Useless

```tsx
import { memo, useState } from 'react'

const Profile = memo(function Profile({ user }: { user: { name: string; age: number } }) {
  console.log('Profile render')
  return <div>{user.name}</div>
})

export default function App() {
  const [count, setCount] = useState(0)
  const user = { name: 'Vin', age: 25 } // ❌ New object on every render

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
      <Profile user={user} />
    </div>
  )
}
```

Click the count button — `Profile` renders again. Why? `{ name: 'Vin', age: 25 }` is a new reference on every render. `Object.is(oldUser, newUser)` → false → memo re-renders.

### ✅ After — Stable Reference with useMemo

```tsx
import { memo, useState, useMemo } from 'react'

const Profile = memo(function Profile({ user }: { user: { name: string; age: number } }) {
  console.log('Profile render')
  return <div>{user.name}</div>
})

export default function App() {
  const [count, setCount] = useState(0)
  const user = useMemo(() => ({ name: 'Vin', age: 25 }), []) // ✅ Create once, cache it

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
      <Profile user={user} />
    </div>
  )
}
```

Click the count button — `App` renders, `Profile` doesn't. `useMemo` created the object once, returns the same reference on every render. `Object.is` → true → memo skips.

The chain:
```
Inline object → new reference → Object.is false → memo useless ❌
useMemo → stable reference → Object.is true → memo works ✅
```

## When to Use useMemo — And When Not To

**❌ Don't use when:**
- The calculation is trivial (summing two numbers, simple `map`/`filter` on a small array)
- The component rarely re-renders
- Premature optimization — measure first

**✅ Use when:**
- Heavy calculation (large array operations, complex math)
- Referential stability is needed (passing objects/arrays to memo'd components)
- Derived state that gets recalculated unnecessarily on every render

## Common Mistake — Wrapping Everything in useMemo

```tsx
// ❌ Unnecessary — this is trivial
const doubled = useMemo(() => count * 2, [count])

// ✅ Direct — it's so simple that useMemo's overhead is worse
const doubled = count * 2
```

`useMemo` has overhead too — creating the dependency array, comparing dependencies. For trivial calculations, direct code is better.

## Summary

✅ **useMemo** — caches a value — for expensive calculations  
✅ Dependencies haven't changed → cached value, no calculation  
✅ Dependency changed → re-calculate, update cache  
✅ Works with React.memo — pass stable object references  
✅ Don't over-use — trivial calculations don't need it  
✅ Measure first with the Profiler, then optimize

## React.memo vs useMemo — The Fundamental Difference

Both have "memo" in the name, so it's natural to be confused. But they work at different levels:

| | React.memo (5.1) | useMemo (5.2) |
|---|---|---|
| **What does it target?** | A Component | A Value (calculation result) |
| **What is it?** | Higher-Order Component (HOC) | A Hook |
| **What does it prevent?** | A component from re-rendering | A calculation from re-executing |
| **What does it check?** | Did props change? | Did dependencies change? |
| **Syntax** | `memo(Component)` | `useMemo(() => val, [deps])` |

**React.memo** — component-level optimization. "Props didn't change → don't re-render this component."

**useMemo** — value-level optimization. "Dependencies didn't change → don't re-run this calculation, return the cached value."

So the short version:
- **Need to cache a variable/calculation?** → `useMemo`
- **Need to prevent a component from unnecessary re-renders?** → `React.memo`
- **Both together?** — `React.memo` prevents the component from re-rendering, `useMemo` provides stable references so that `React.memo`'s `Object.is` comparison works correctly.
