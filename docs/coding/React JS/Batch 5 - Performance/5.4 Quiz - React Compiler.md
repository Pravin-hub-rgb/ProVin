## MCQ

Q: What is the React Compiler?
A. A build-time tool that automatically memoizes React components - the memoization code is added for you during the build
B. A new hook that replaces `useMemo` and `useCallback` - call it once and every value is cached
C. A browser feature that speeds up JavaScript execution without any code changes
D. A component library with pre-optimized components - import them instead of writing your own

> A. The React Compiler is a Babel plugin, a build-time tool. It reads your component code during the build and adds memoization where it can prove it is safe. B is wrong - it is not a hook, you never call it in your code. C is wrong - it has nothing to do with the browser. D is wrong - it works on your own components, it is not a library.

Q: With the compiler enabled, what happens to the inline arrow function trap from 5.1 (`<Item onClick={() => handleClick(item)} />`)?
A. It is handled automatically - the compiler caches the function reference, so memoized items still skip re-renders
B. It still breaks memo - inline functions must always be replaced with `useCallback`
C. The build fails - the compiler rejects inline arrow functions in props
D. The function gets converted to a string, losing its behavior

> A. This trap is the main example in the compiler's own documentation: the compiler tracks the function reference the way `useCallback` would, automatically. B is wrong - that is exactly the work the compiler now does for you. C is wrong - no build error; the code compiles and works. D is wrong - functions are never converted to strings.

Q: With the compiler enabled, what happens to your EXISTING `memo`, `useMemo`, and `useCallback` code?

B. It is automatically removed and replaced with compiler-generated code
C. The build fails - you cannot mix manual and automatic memoization
D. It is ignored at runtime - React skips it entirely

> A. The compiler preserves existing manual memoization. Removing it could change behavior - you may have memoized for a library contract the compiler cannot see - so yours stays. B is wrong - nothing is removed. C is wrong - they work together fine. D is wrong - your manual memoization still runs exactly as before.

Q: Which kind of memoization stays MANUAL even with the compiler enabled?
A. Memoization for correctness - a reference must stay stable for something outside React's render, like a `useEffect` dependency or a non-React library
B. Memoizing components that receive the same props repeatedly - the common re-render case
C. Memoizing values created during render - the inline-object case from 5.2
D. Memoizing function references passed as props - the `handleToggle` case from 5.3

> A. The compiler removes unnecessary re-renders. When a stable reference is required for correctness - effects that must not re-run, non-React libraries, custom-hook contracts - memoization stays manual. B is wrong - that is the compiler's core job. C is wrong - the compiler caches render-created values. D is wrong - function props are handled automatically.

A. Renders happening less → the compiler; reference stability outside render → manual hooks
B. Heavy components → manual hooks; light components → the compiler
C. Production apps → the compiler; development apps → manual hooks
D. There is no rule - always use manual hooks for everything

> A. If the goal is fewer renders, the compiler handles it and you write plain code. If the goal is a stable reference for something outside render - effect deps, library contracts - do it manually. B is wrong - weight does not decide it. C is wrong - both work in production. D is wrong - the rule exists and matters for correctness.

Q: What does the compiler do with a component that violates the Rules of React?

D is wrong - nothing is added to your component.

Q: What can the compiler memoize that manual hooks CANNOT?
A. Code that runs after an early return - the compiler is not bound by the Rules of Hooks' order requirement
B. Values stored in global variables
C. Class components
D. Server-side code

> A. A `useMemo` placed after a conditional `return` is illegal because hooks must run in the same order every render. The compiler generates caching code at build time and has no such order constraint, so it can memoize after early returns. B is wrong - globals are exactly what the compiler cannot prove safe. C is wrong - class components are not what the compiler targets here. D is wrong - it works on your client component code.

## TrueFalse

Q: The React Compiler works at build time - your source code stays plain and the memoization logic is generated when the app is built.
- True
- False
> True. It is a Babel plugin: the transformation happens during the build, never in the browser. Same category of tool as TypeScript's build step.

---

Q: With the compiler enabled, you should immediately delete all existing `useMemo`, `useCallback`, and `memo` code.
- True
- False
> False. The compiler preserves manual memoization - removing it could change behavior when it was added for correctness (a library contract, an effect dependency). New code can be written plain; existing code stays until you can verify the change.

---

Q: The compiler can memoize code that runs after an early return, which manual hooks cannot do.
- True
- False
> True. Hooks must run in the same order every render, so a `useMemo` after a conditional `return` is illegal. The compiler generates caching code at build time and has no such constraint.

---

Q: Relying on memoization for correctness - instead of only for performance - is the main way the compiler can break an app.
- True
- False
> True. If your code assumes a reference never changes (an effect dependency, a library holding a callback) and the compiler does not know that assumption, behavior can change. That is why correctness memoization stays manual and explicit.

---

Q: The compiler shares one memoization cache across all components of the app.
- True
- False
> False. Each component gets its own generated caching logic, the same way `memo`'s comparison is per component instance.

---

Q: Enabling the compiler changes how you write new components - you now wrap every component in `memo()` as before.
- True
- False
> False. New code is written plain, with no wrappers. The compiler adds the memoization during the build. You write manual memoization only for the correctness cases.

---

Q: With the compiler enabled, a function like `handleToggle` is still a new object in memory on every render - the compiler just hides it.
- True
- False
> False. That was the manual model. The compiler wraps the function's creation in a cache check - because it depends only on stable values, it is created once and reused, not recreated and discarded.

---

Q: Babel converts JSX into HTML before the browser renders it.
- True
- False
> False. Babel converts JSX into plain JavaScript function calls. React takes those calls and builds the actual HTML elements in the browser - Babel never produces HTML.

---

Q: The compiler's generated cache checks compare inputs with `Object.is`, the same comparison memo uses.
- True
- False
> True. Every generated cache check asks "have the inputs changed since last render?" with `Object.is` - the same reference comparison from 5.1. Unchanged inputs mean reuse; changed inputs mean recompute.

---

Q: Bun supports the React Compiler natively from version 1.4 - built into the bundler, no Babel plugin needed.
- True
- False
> True. Bun 1.4 integrates the compiler into its own build (`bun build --react-compiler` or `Bun.build({ reactCompiler: true })`), without the Babel pipeline.

## ShortAnswer

Q: Walk the compiler's five-step pipeline in order, one line per step.

<details>
<summary>Sample Answer</summary>

> **Sample Answer:** 1. Parsing - Babel turns your component's text into a tree of nodes (plain objects with a `type`), rooted at `File` → `Program`. 2. Internal form - the compiler converts that tree into its own representation that tracks every value's origin, dependencies and flow (who creates it, what it uses, where it is passed). 3. Dependency tracking - it works out what can change: state changes, stable values stay stable, and values built only from stable things are stable - the same job a `useCallback` dependency array does by hand. 4. Safety check - it verifies the Rules of React; anything it cannot prove is silently skipped. 5. Code generation - each piece of work is wrapped in a cache check: a per-component box of stored results, compared with `Object.is` each render - reuse if unchanged, recompute if changed.

</details>

---

Q: Explain the audit cycle using the three FilterButton stages, and say which stage the compiler removes.

<details>
<summary>Sample Answer</summary>

> **Sample Answer:** Stage 1: FilterButton is memoized with one string prop - the string is stable, so memo skips it on every parent render; the audit passes. Stage 2: someone adds an inline `onToggle` arrow in the JSX - a new function object on every render, so memo sees a changed reference and re-renders the child with no error or warning; the audit now fails. Stage 3: the manual fix - move the function into `useCallback` with the right dependency array so the reference stays stable. The cycle - add a prop, re-check every prop's reference stability, fix by hand - is the audit, and repeating it for each new prop is the re-audit. The compiler removes the entire cycle: it tracks each value's dependencies at build time and generates the cache checks, so stage 2's plain code just works.

</details>
