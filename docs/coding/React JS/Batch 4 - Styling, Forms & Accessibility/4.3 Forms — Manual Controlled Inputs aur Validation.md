## Submit — What Happens?

Click the button — **the page reloads.**

Why? Browser's default behavior — when a form submits, the browser reloads the page. In React, we don't want that. We want to handle it ourselves.

---
## `onSubmit` — Intercept the Form Submission

`onSubmit` is an event on the form — fires whenever the form is submitted.

You pass a function to `onSubmit` — that function runs when the form is submitted. And the browser automatically passes an **event object** to that function — `e`.

---
## What Is `e`?

Whenever an event happens in the browser — a click, a submit, a keystroke — the browser creates an **event object** with all the details ("which element, what time, what's the default behavior?").

That object is automatically handed to your function — you don't have to ask for it.

And that object has a method — `preventDefault()` — "browser, don't do your default thing."

For a form, the default thing is a page reload. `e.preventDefault()` stops it.

---
## Add `onSubmit`

```tsx
export default function ContactForm() {

  function handleSubmit(e: React.SyntheticEvent<HTMLFormElement>) {
    e.preventDefault()
    console.log('Form submitted!')
  }

  return (
    <form onSubmit={handleSubmit} className="flex flex-col gap-4">
      <div>
        <label className="block text-sm font-medium mb-1">Name</label>
        <input
          type="text"
          placeholder="Enter your name"
          className="border border-gray-300 rounded px-3 py-2 w-full"
        />
      </div>
      <div>
        <label className="block text-sm font-medium mb-1">Email</label>
        <input
          type="email"
          placeholder="Enter your email"
          className="border border-gray-300 rounded px-3 py-2 w-full"
        />
      </div>
      <button
        type="submit"
        className="bg-blue-500 text-white px-4 py-2 rounded hover:bg-blue-600"
      >
        Submit
      </button>
    </form>
  )
}
```

Click the button — no page reload. Browser console shows:

```
Form submitted!
```

✅ Form submission intercepted.

## TypeScript Warning — Why the Type on `e` Matters

You get a TypeScript warning on `function handleSubmit(e)` — `e` has no type. TypeScript doesn't know what `e` is, so it might error on `e.preventDefault()` too.

TypeScript's job is to check types. `e` is an event object, but which event? Form submit? Click? Keyboard? You have to tell TypeScript.

**Type it manually:**

```tsx
function handleSubmit(e: React.SyntheticEvent<HTMLFormElement>) {
  e.preventDefault()
  console.log('Form submitted!')
}
```

`React.SyntheticEvent<HTMLFormElement>` — telling TypeScript: "this is a form submit event, from an `HTMLFormElement`." Now `e.preventDefault()` doesn't error.

**Or write it inline — TypeScript infers it for you:**

```tsx
<form
  onSubmit={(e) => {
    e.preventDefault()
    console.log('Form submitted!')
  }}
>
```

When you write it inline, TypeScript looks at the context — "this is `onSubmit`, which means it's a form submit event." The type is inferred automatically from React's type definitions. `React.SyntheticEvent<HTMLFormElement>` — that's the type that comes through.

**Both approaches are fine.** If you have a separate function, type it manually. If you write it inline, TypeScript infers it. Separate functions are better when there's more logic — they're more readable and testable.

## How Do We Get the Values?

"Form is being submitted — but where are the name and email values?"

Add `useState` — one state for each input:

```tsx
import { useState } from 'react'

export default function ContactForm() {
  const [name, setName] = useState('')
  const [email, setEmail] = useState('')

  return (
    <form
      onSubmit={(e) => {
        e.preventDefault()
        console.log({ name, email })
      }}
      className="flex flex-col gap-4"
    >
      <div>
        <label className="block text-sm font-medium mb-1">Name</label>
        <input
          type="text"
          value={name}
          onChange={(e) => setName(e.target.value)}
          placeholder="Enter your name"
          className="border border-gray-300 rounded px-3 py-2 w-full"
        />
      </div>
      <div>
        <label className="block text-sm font-medium mb-1">Email</label>
        <input
          type="email"
          value={email}
          onChange={(e) => setEmail(e.target.value)}
          placeholder="Enter your email"
          className="border border-gray-300 rounded px-3 py-2 w-full"
        />
      </div>
      <button
        type="submit"
        className="bg-blue-500 text-white px-4 py-2 rounded hover:bg-blue-600"
      >
        Submit
      </button>
    </form>
  )
}
```

`value={name}` — the input's value comes from state.

`onChange={(e) => setName(e.target.value)}` — every time the user types, state updates. And `e` is inline here — TypeScript knows this is an input change event, so `e.target.value` gives you the typed string.

Type "Pravin" into name, "pravin@gmail.com" into email, submit. Browser console:

```
{ name: 'Pravin', email: 'pravin@gmail.com' }
```

✅ Got the values.

## The Problem — What If We Add More Fields?

Right now there are just two fields — two `useState` calls. Fine.

But think real-world forms:

```
name, email, phone, address, city, pincode, message...
```

Seven fields — seven `useState` calls, seven `onChange` handlers. It starts looking like this:

```tsx
const [name, setName] = useState('')
const [email, setEmail] = useState('')
const [phone, setPhone] = useState('')
const [address, setAddress] = useState('')
const [city, setCity] = useState('')
const [pincode, setPincode] = useState('')
const [message, setMessage] = useState('')
```

Each with its own `value` and `onChange`. Extremely repetitive. Extremely messy.

---
## Manage It All with One `useState` — The Object Approach

Store all values in one object:

```tsx
const [formData, setFormData] = useState({
  name: '',
  email: ''
})
```

Then a single `handleChange` function — handles all of them. But the input needs a `name` attribute — so we know which field changed:

```tsx
<input
  type="text"
  name="name"       // ← add this
  value={formData.name}
  onChange={handleChange}
/>
```

Now `handleChange`:

```tsx
function handleChange(e) {
  setFormData({
    ...formData,
    [e.target.name]: e.target.value
  })
}
```

Break this down —

`...formData` — the spread operator — copies all the existing values into the new object: `{ name: 'Pravin', email: '' }`

`[e.target.name]: e.target.value` — **computed property**. `e.target.name` is the `name` attribute on the input — `"name"` or `"email"`. Only that one field gets updated, everything else stays the same.

Full updated code:

```tsx
import { useState } from 'react'

export default function ContactForm() {
  const [formData, setFormData] = useState({
    name: '',
    email: ''
  })

  function handleChange(e) {
    setFormData({
      ...formData,
      [e.target.name]: e.target.value
    })
  }

  return (
    <form
      onSubmit={(e) => {
        e.preventDefault()
        console.log(formData)
      }}
      className="flex flex-col gap-4"
    >
      <div>
        <label className="block text-sm font-medium mb-1">Name</label>
        <input
          type="text"
          name="name"
          value={formData.name}
          onChange={handleChange}
          placeholder="Enter your name"
          className="border border-gray-300 rounded px-3 py-2 w-full"
        />
      </div>
      <div>
        <label className="block text-sm font-medium mb-1">Email</label>
        <input
          type="email"
          name="email"
          value={formData.email}
          onChange={handleChange}
          placeholder="Enter your email"
          className="border border-gray-300 rounded px-3 py-2 w-full"
        />
      </div>
      <button
        type="submit"
        className="bg-blue-500 text-white px-4 py-2 rounded hover:bg-blue-600"
      >
        Submit
      </button>
    </form>
  )
}
```

Submit — same result. But now just one `useState` and one `handleChange` ✅

## Add Validation — Manually

So far the form submits — but no validation. Leave both fields empty and submit — `{ name: '', email: '' }` lands in the console. No error.

Now we add validation — manually, with `if` checks.

### Create an Error State

```tsx
const [errors, setErrors] = useState({
  name: '',
  email: ''
})
```

### Validate in `handleSubmit`

Add validation to `handleSubmit` — if there are errors, set them and return:

```tsx
<form
  onSubmit={(e) => {
    e.preventDefault()

    const newErrors = { name: '', email: '' }
    if (!formData.name.trim()) {
      newErrors.name = 'Name is required'
    }
    if (!formData.email.trim()) {
      newErrors.email = 'Email is required'
    }

    if (newErrors.name || newErrors.email) {
      setErrors(newErrors)
      return
    }

    setErrors({ name: '', email: '' })
    console.log(formData)
  }}
  className="flex flex-col gap-4"
>
```

Flow:

```
Submitted
  → name empty? → newErrors.name = 'Name is required'
  → email empty? → newErrors.email = 'Email is required'
  → any error exists? → setErrors, return (stop here)
  → no errors? → clear errors, console.log(formData)
```

### Show Errors in the UI

Show the error under each input — a red message:

```tsx
<div>
  <label className="block text-sm font-medium mb-1">Name</label>
  <input
    type="text"
    name="name"
    value={formData.name}
    onChange={handleChange}
    placeholder="Enter your name"
    className={`border rounded px-3 py-2 w-full ${
      errors.name ? 'border-red-500' : 'border-gray-300'
    }`}
  />
  {errors.name && (
    <p className="text-red-500 text-sm mt-1">{errors.name}</p>
  )}
</div>
```

`{errors.name && <p>...</p>` — if `errors.name` is not empty, render the `<p>`.

Submit with an empty name — "Name is required" shows on screen ✅

Same for email:

```tsx
{errors.email && (
  <p className="text-red-500 text-sm mt-1">{errors.email}</p>
)}
```

## The Problem — Only Two Fields

Look at how much code this is — just for name and email:

- Two `useState` calls — one for formData, one for errors
- `if` checks inside `handleSubmit`
- Error `<p>` under each input
- Conditional `className` for the red border

If there were 10 fields — 10 `if` checks, 10 error paragraphs. Repetitive code for every field.

**Manual validation doesn't scale.**
