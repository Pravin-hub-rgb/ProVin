## What We've Covered So Far

The guard works - logged-out visitors bounce, logged-in users land, deep links return them where they meant to go. But refresh the page and you are logged out again. Last mile of the project: **persist the session**, **wire logout properly**, run the full journey - and close Batch 4 with the map to what comes next.

## Why the Session Dies on Refresh

`useState` lives in memory. A refresh tears down the whole JavaScript world - every component, every context, every piece of state - and rebuilds from scratch. The new world starts with `user: null` because nothing told it otherwise. localStorage, meanwhile, survives refreshes (that's its job) - and the *users* database already proves it: register, refresh, login still works.

So the fix is symmetric with the bug: the session shape (`User | null`) stays exactly as designed; it just gets a persistent memory.

## Persisting the Session - AuthContext v2

Three changes to `src/context/AuthContext.tsx`:

```tsx
// src/context/AuthContext.tsx (updated pieces)
import type { User } from '../authStorage'

const SESSION_KEY = 'auth-demo-session'

function readSession(): User | null {
  const raw = localStorage.getItem(SESSION_KEY)
  return raw ? (JSON.parse(raw) as User) : null
}

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(() => readSession())

  const login = (u: User) => {
    localStorage.setItem(SESSION_KEY, JSON.stringify(u))
    setUser(u)
  }

  const logout = () => {
    localStorage.removeItem(SESSION_KEY)
    setUser(null)
  }

  // ...the JSX return is unchanged
```

How to read the three changes:

- **`readSession()`** - same guard shape as `getUsers()`: missing key → `null` (nobody logged in), present key → parsed user. (If you want belt-and-braces: a `try/catch` around the parse handles hand-tampered storage - a nice self-challenge.)
- **`login` writes, `logout` removes** - storage writes live **inside the event handlers**. `login`/`logout` are functions the user's clicks trigger - the correct home for side effects. Nothing writes to storage during render.
- **`useState<User | null>(() => readSession())`** - the interesting one. Next section.

## Why `() => readSession()` - the Lazy Initializer

Three spellings, only one is idiomatic:

```tsx
useState(readSession())    // — calls readSession() NOW, on every render; React uses only the first result
useState(readSession)      // works: React calls a function-typed initial value once - but the intent is hidden
useState(() => readSession())  // works, and says what it means: "one-time initializer"
```

- **First form** - `readSession()` has parentheses, so it *executes* immediately, on **every render**, and each result gets thrown away except the first. Wasted storage reads, forever. The classic `() => myFunc` vs `myFunc()` trap - here it bites on state initialization.
- **Second form** - React's rule: a function-typed initial value is a **lazy initializer**, called exactly once at mount. Correct behavior, invisible intent.
- **Third form** - identical behavior, but the arrow makes "runs once, on purpose" legible to every future reader. That's why it's the idiom.

**What the initializer buys:** storage is read **once** at startup - the session rehydrates on refresh - and never re-read afterward. Runtime truth stays context state (the guard in 4.4.11 reads it); storage is just where truth survives the night.

## The Logout Button - Dashboard v2

```tsx
// src/pages/Dashboard.tsx (updated pieces)
import { useNavigate } from 'react-router-dom'
import { useAuth } from '../context/AuthContext'

export default function Dashboard() {
  const { user, logout } = useAuth()
  const navigate = useNavigate()
  if (!user) return null

  return (
    <div className="mx-auto mt-10 max-w-md p-4">
      <h1 className="text-2xl font-bold">Dashboard</h1>
      <p className="mt-2">Welcome, {user.name}.</p>
      <button
        onClick={() => { logout(); navigate('/login') }}
        className="mt-6 rounded bg-gray-800 p-2 text-white"
      >
        Log out
      </button>
    </div>
  )
}
```

- **Two calls, one order:** `logout()` clears state + storage, `navigate('/login')` sends them home. Reverse the order and logout still wins (state clears before the unmount) - but the stated order reads like the story: leave the building, then close the door.
- **`navigate()` here, not `<Navigate>`** - event-driven navigation (a click handler) uses the function; render-driven ("this visit isn't allowed") uses the component. 4.4.11's guard needed the component; this button needs the function.

## Common Mistakes (Senior Dev Blind Spots)

- **Forgetting `removeItem` on logout** - state clears, storage survives; refresh resurrects the "logged out" user. The ghost session. Clear both, always.
- **`useState(readSession())`** - the parentheses read storage on *every* render. The arrow `() => readSession()` is the whole fix.
- **"Checking" login with `readSession()` in a render body** - now storage is a second truth racing the context. Derive from context; the initializer already loaded it once.

## Try It Yourself (Active Recall)

1. Refresh kills the session - what exactly is lost, and which line restores it?
2. Why does the initializer need the arrow - what would `useState(readSession())` do differently?
3. Why do the storage writes live inside `login`/`logout` rather than beside the `useAuth` calls in components?

<details><summary>Sample Answers</summary>

1. The in-memory `user` state (the whole JS world is rebuilt). `useState(() => readSession())` restores it - at mount, the initializer reads `auth-demo-session` once and seeds the state with the persisted user.
2. With parentheses, `readSession()` executes during every render of the provider - each result discarded except the first. The arrow defers execution: React calls it exactly once at mount, and the intent ("one-time initializer") stays visible in the code.
3. Because `login`/`logout` are the session's only doors - callers get state changes *and* persistence together, in the right order, with no component able to update one and forget the other. Side effects belong in event-triggered functions, not scattered through render bodies.

</details>
