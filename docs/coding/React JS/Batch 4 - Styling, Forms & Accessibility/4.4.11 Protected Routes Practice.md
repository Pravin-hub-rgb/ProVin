## What We've Covered So Far

The session lives in context, login navigates to `/dashboard` - which is blank, because no route maps that URL yet. Now the payoff: the **route**, the **guard**, and the **return trip**. This is 3.3's `ProtectedRoute` pattern re-practiced in a real app - with one upgrade: the guard reads a **real session** (`User | null` from context) instead of a hardcoded boolean.

## The Route First - App.tsx

```tsx
// src/App.tsx
import { Routes, Route } from 'react-router-dom'
import Register from './pages/Register'
import Login from './pages/Login'
import Dashboard from './pages/Dashboard'
import ProtectedRoute from './components/ProtectedRoute'

export default function App() {
  return (
    <Routes>
      <Route path="/register" element={<Register />} />
      <Route path="/login" element={<Login />} />
      <Route path="/dashboard" element={
        <ProtectedRoute>
          <Dashboard />
        </ProtectedRoute>
      } />
    </Routes>
  )
}
```

Two routes are open to everyone; one is wrapped. The wrapping is the whole idea: `ProtectedRoute` sits between the router and the page, and decides whether the page gets to render at all.

## ProtectedRoute.tsx - The Guard

```tsx
// src/components/ProtectedRoute.tsx
import { Navigate, useLocation } from 'react-router-dom'
import type { ReactNode } from 'react'
import { useAuth } from '../context/AuthContext'

export default function ProtectedRoute({ children }: { children: ReactNode }) {
  const { user } = useAuth()
  const location = useLocation()

  if (!user) {
    return <Navigate to="/login" replace state={{ from: location.pathname }} />
  }

  return <>{children}</>
}
```

Line by line, because every choice here carries weight:

- **`{ children }: { children: ReactNode }`** - the wrapper pattern. The guard doesn't know or care *what* it protects; whatever the route gives it, it either forwards (`<>{children}</>`) or blocks. That's why one guard protects one page today and a dozen tomorrow - no repetition, no per-page if-checks.
- **`<Navigate to="/login" ... />`** - a component that redirects *by rendering*. The moment it appears in the output, React Router navigates. "Block" = "render a redirect instead of the children."
- **`replace`** - the quiet hero. Without it, the blocked visit pushes `/dashboard` into history; after logging in, pressing Back returns you to a page that bounces you again - a back-button bounce loop, and a history full of pages you were never allowed to see. With `replace`, the failed visit *overwrites* the history entry: Back from `/login` goes to wherever you were before, never to the blocked page.
- **`state={{ from: location.pathname }}`** - attaches a small note to the navigation: *"this is the page they actually wanted."* Login will read it in the next section and send them there after success - the **return trip**.

## The Return Trip - Login Reads `state.from`

One upgrade to `Login.tsx`:

```tsx
import { useLocation } from 'react-router-dom'

// inside the component:
const location = useLocation()
const from = (location.state as { from?: string } | null)?.from

// in onSubmit, after login(user):
navigate(from ?? '/dashboard')
```

Reading it:

- `location.state` is typed as unknown - React Router can't know what you stuffed in there, so you cast: `as { from?: string } | null`. The cast says "I'm the one who wrote this shape."
- `?.from` - if there's no state (user typed `/login` directly), `from` is `undefined`.
- `from ?? '/dashboard'` - came here redirected from a protected page? Back to it. Came straight to login? The default home. The `??` operator (1.x lesson) earns its keep: "left side if it exists, right side otherwise."

## Dashboard.tsx - The Promised Land

```tsx
// src/pages/Dashboard.tsx
import { useAuth } from '../context/AuthContext'

export default function Dashboard() {
  const { user } = useAuth()
  if (!user) return null

  return (
    <div className="mx-auto mt-10 max-w-md p-4">
      <h1 className="text-2xl font-bold">Dashboard</h1>
      <p className="mt-2">Welcome, {user.name}.</p>
      <button className="mt-6 rounded bg-gray-800 p-2 text-white">
        Log out
      </button>
    </div>
  )
}
```

About `if (!user) return null` - the **trust gap**: at runtime, `ProtectedRoute` guarantees a user exists before Dashboard renders. But TypeScript can't know that; `useAuth()`'s type honestly says `User | null`. So the component guards anyway. The type system describes the contract honestly; the wrapper makes the guarantee. Both exist on purpose - removing the `if` "because it can't happen" is how crashes happen.

(The **Log out** button renders but does nothing yet - 4.4.12 wires it. In a real team, a dead button in a PR gets flagged; here it's a placeholder with a known next step.)

**TEST:** logged out, type `/dashboard` → instant bounce to `/login` (URL flips, no flash of dashboard). Log in → you land **back on `/dashboard`** - the return trip delivered. Log out of nothing yet, but: refresh on `/dashboard` → back to `/login` (the session is memory-only - 4.4.12 fixes exactly this). And `/register`, `/login` stay open to everyone.

## Common Mistakes (Senior Dev Blind Spots)

- **Guarding with a localStorage check inside `ProtectedRoute`** - `localStorage.getItem` isn't reactive: the guard reads it once at render and goes stale, and logout (which clears state) wouldn't re-render anything. Context state is the runtime truth the UI reads; storage is persistence (next file's job).
- **`<Navigate>` without `replace`** - every blocked visit pollutes history and arms the back-button bounce loop.
- **Guarding inside Dashboard instead of wrapping the route** - works for one page, then copy-pasted across five. The wrapper protects N pages with zero repetition, and the guard logic stays in exactly one place.
- **Skipping the cast on `location.state`** - either a TS error, or `any` sneaking in. Cast + optional chain + `??` default is the honest shape.

## Try It Yourself (Active Recall)

1. What specific user-facing bug does `replace` prevent?
2. What is `state.from` for, who writes it, and who reads it?
3. Why does Dashboard keep `if (!user) return null` when `ProtectedRoute` already guarantees a user?

<details><summary>Sample Answers</summary>

1. The back-button bounce loop: without `replace`, each blocked `/dashboard` visit is a history entry - Back from `/login` returns to the blocked page, which immediately bounces to `/login` again. `replace` overwrites the entry, so history never contains a page the user wasn't allowed to see.
2. It records *where the user wanted to go*. `ProtectedRoute` writes it (`state={{ from: location.pathname }}`) when bouncing; `Login` reads it after a successful login and navigates there (`from ?? '/dashboard'`). Without it, deep links always dump you at the default page.
3. Because the type system is honest: `useAuth()` returns `User | null` and TS can't see through the wrapper. The `if` bridges the trust gap - the guarantee exists at runtime, the type still tells the truth. Cheap insurance against future edits that break the wrapper assumption.

</details>

## Summary (The Developer's Mental Model)

— Guard = a wrapper that forwards children or renders a redirect - never both
— `replace` = the failed visit never enters history
— `state.from` = the deep-link return trip, written by the guard, read by login
— Context state = runtime truth; storage = persistence - never confuse the two
— TS can't see through wrappers - guard anyway, honestly
