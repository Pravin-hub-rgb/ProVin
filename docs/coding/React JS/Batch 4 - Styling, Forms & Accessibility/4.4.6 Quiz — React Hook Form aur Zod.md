
## MCQ

Q: In controlled form inputs, which React state hook stores the input's current value, and how is it updated?
A. A `useRef` reference stores the value, read from the DOM on submit
B. A `useState` hook stores the value, updated via `onChange` handler
C. A `useReducer` hook manages form state, updated via `dispatch`
D. The browser's built-in form state handles it automatically; React just listens for events
> B. In controlled inputs, React state is the single source of truth. `useState` stores the value, and `onChange` updates state when the input changes. A is wrong — `useRef` is used for uncontrolled inputs. C is wrong — `useReducer` is possible but not standard; `useState` is simpler. D is wrong — React manages state, not the browser.

Q: What is the standard pattern for displaying errors in manual form validation?
A. Store errors in an array, display all errors at once on submit
B. Each field has its own error state variable, validate with if-else on submit, set the error
C. Wrap the form in an Error Boundary that detects invalid inputs
D. Rely on the browser's built-in validation (`required`, `type` attributes)
> B. Manual validation uses an error state for each field, runs if-else checks on submit, sets errors, and renders them with `{error && <p>}`. A is wrong — an array is possible but not standard. C is wrong — Error Boundaries catch runtime errors, not validation. D is wrong — browser validation is hard to control.

Q: How do you connect `register()`'s returned object to an input element in React Hook Form?
A. `register` returns a CSS class with styling, applied via `className`
B. `register` returns an object with `onChange`, `onBlur`, `ref` — spread it onto the input
C. `register` returns a string, set it as the input's `name` attribute
D. `register` directly mutates the input, inside the React component
> B. `register` returns an object containing RHF's internal handlers. `{...register('name')}` spreads all those properties onto the input so RHF can track it. A is wrong — `register` doesn't return CSS classes. C is wrong — it returns an object, not just a string. D is wrong — React doesn't mutate; it connects via props.

D. Upgrades RHF's built-in validators to accept Zod's syntax
> C. `zodResolver` comes from `@hookform/resolvers`. You pass it as the `resolver` to `useForm`. On submit, Zod runs the validation, and the errors populate RHF's `formState.errors`. A is wrong — it doesn't convert. B is wrong — it doesn't log. D is wrong — RHF's validators aren't upgraded; they're replaced.

Q: When using RHF with Zod, what is the issue with keeping both a manual `FormFields` type and a Zod schema?
A. Zod schema and the RHF type can't be used together — they conflict
B. `FormFields` is only for RHF; there's no connection to the Zod schema
C. Both define the same fields — duplication, you have to maintain the same info in two places
D. The `FormFields` type should only be defined in the Zod schema, not RHF
> C. The manual type (`type FormFields = { name: string }`) and the Zod schema (`z.object({ name: z.string() })`) define the same structure. Adding a field means updating both — error-prone. `z.infer` is the solution. A is wrong — they can be used together. B is wrong — the lack of connection is the problem. D is wrong — RHF needs the type too.

Q: What does `.min(1, 'message')` do in Zod?
A. Sets a minimum length of 1 character — rejects empty strings
B. Sets the field's minimum numeric value to 1 — used for numbers
C. Validates the schema a minimum of 1 time — a performance optimization
D. Requires the form to have at least 1 field — rejects empty forms
> A. `.min(1)` checks the string's length. An empty string `""` has length 0, so `.min(1)` rejects it. You can also provide a custom message. B is wrong — `.min()` works for numbers too but the context is a string. C is wrong — there's no validation count concept. D is wrong — it's field-level, not form-level.

## TrueFalse

Q: In manual form validation, instead of a separate `useState` for each field's error, you can use a single object state (`{ name: '', email: '' }`) to store all errors.
- True
- False
> True. One object state can hold all errors. Instead of multiple `useState` variables, a single object avoids that. You do need to spread when updating — `setErrors({ ...errors, name: 'error' })` — so you don't overwrite other fields.

---

Q: RHF's `register` function converts uncontrolled inputs into controlled inputs.
- True
- False
> False. RHF follows an uncontrolled approach — the input's value lives in the DOM, and RHF reads it via `ref`. Controlled inputs store the value in React state and update via `onChange`. RHF does it differently.

---

Q: You can use RHF's built-in validation and `zodResolver` at the same time — both will validate each field.
- True
- False
> False. Once you add a `zodResolver`, RHF disables its built-in validators. Zod handles everything. They don't run side by side.

---

Q: `z.string()` means the field cannot be empty — if it's a string type, it must have content.
- True
- False
> False. `z.string()` only checks the type — whether the value is a string. An empty string `""` is still a valid string. To reject empty strings, you need `.min(1)`.

---

Q: In Zod v4, `z.email()` is a top-level method — you don't need to call `z.string()` first.
- True
- False
> True. `z.email()` is a top-level method in Zod v4. You can call it directly without chaining off `z.string()`. The old `z.string().email()` syntax from Zod v3 is deprecated.

---

Q: `z.infer` only works at development time (compile time) — nothing from it ends up in the production bundle.
- True
- False
> True. `z.infer` is a TypeScript utility type. It runs at compile time for type checking, and produces nothing in the runtime JavaScript bundle. It's not a Zod runtime function.
