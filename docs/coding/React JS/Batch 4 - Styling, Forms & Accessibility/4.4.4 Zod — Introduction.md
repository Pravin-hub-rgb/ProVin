## What We've Covered So Far

In 4.4.3 we used React Hook Form's built-in validation — putting `required` and `pattern` rules inside `register`.

It works — but for email format check we had to write:
```tsx
pattern: {
  value: /^[^\s@]+@[^\s@]+\.[^\s@]+$/,
  message: 'Email is not in the right format'
}
```

That regex is hard to read. And for more complex rules — it only gets worse.

**What if validation rules were written in plain, readable language?**

That's exactly what **Zod** does.

---
## What We'll Do In This Doc

Our goal — connect Zod to the form so Zod handles validation.

Two things to do:
1. **Create a Zod schema** — define what fields the form has and their types
2. **Connect the schema to RHF** — so Zod validates on submit

First we'll understand what a schema is — then connect it.

---
## What Is a Schema?

A schema is a **blueprint of what your data should look like**.

In Zod, you write it like this:

```ts
z.object({
  name: z.string(),
  email: z.string()
})
```

For now, it's just `z.string()` — "this field should be a string." We'll add specific validation rules (like email format checks) in 4.4.5.

## Install

Two packages needed:

```bash
npm install zod @hookform/resolvers
```

**`zod`** — the library for writing schemas

**`@hookform/resolvers`** — this is a bridge. Zod and RHF are two separate libraries. This package connects them.

## Start Writing the Schema

In `ContactForm.tsx`, import `z` and start writing a simple schema outside the component:

```tsx
import { z } from 'zod'

const formSchema = z.object({
  name: z.string()
})

console.log(formSchema)
```

Browser console will show a Zod object. Remove the console.log.

Now add the rest of the fields:

```tsx
const formSchema = z.object({
  name: z.string(),
  email: z.string()
})
```

For now, just types — rules come later.

## Connect to RHF — `zodResolver`

Before connecting, one thing to do — define the `FormFields` type.

Previously (in 4.4.1 and 4.4.3) we manually created a type for RHF — `name: string`, `email: string`. Now we have a Zod schema with the same structure — `name: z.string()`, `email: z.string()`.

We're defining the same thing in two places. So let's keep them together:

```tsx
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'

// Manual Type — tells RHF what fields exist
type FormFields = {
  name: string
  email: string
}

// Zod Schema — for validation
const formSchema = z.object({
  name: z.string(),
  email: z.string()
})

export default function ContactForm() {
  const { register, handleSubmit, formState: { errors } } = useForm<FormFields>({
    resolver: zodResolver(formSchema)
  })
  // ...
}
```

`useForm<FormFields>({ resolver: zodResolver(formSchema) })` — now `useForm` knows both the type (which fields exist) and the resolver (how to validate).

`resolver: zodResolver(formSchema)` — telling RHF: "when the form is submitted, let Zod do the validation." From now on, RHF won't use its built-in validators — **Zod** checks every field. If Zod finds a field invalid (like a number where it expected a string), the error automatically flows into RHF's `formState.errors` — the same `errors` object you learned about in 4.4.3.

**One important thing** — remove the rules from `register`:

```tsx
// Old — remove this
{...register('name', { required: 'Name is required' })}

// Now just this
{...register('name')}
```

RHF's built-in validators and `zodResolver` don't work together. Zod handles all the validation now.

`formState: { errors }` — same as it was in 4.4.3. That's where the error messages show up.

---
## The Problem — Defining Things in Two Places

Here's what's happening:

| Where | What's written |
|-------|----------------|
| `type FormFields` | `name: string`, `email: string` |
| Zod schema | `name: z.string()`, `email: z.string()` |

Same fields, defined twice. If tomorrow you need to add a `phone` field — you'd have to change it in both places. Forget one, get a bug.

**Zod's solution** — `z.infer`. It auto-generates the TypeScript type from the schema. Schema in one place, type generated automatically. No duplication.

We'll see `z.infer` in 4.4.6. For now, keep the manual type.

## Submit — See What Happens

Right now the schema only has `z.string()` — no validation rules.

```ts
z.object({
  name: z.string(),     // → just needs to be a string
  email: z.string()     // → just needs to be a string
})
```

`z.string()` means — "this value must be a string." An empty string `""` is still a string. `null` or `undefined` is not.

So try submitting:

```tsx
onSubmit={handleSubmit((data) => {
  console.log(data)
})}
```

Submit with both fields empty — the form submits, console shows `{ name: '', email: '' }`, and `errors` stays empty.

**Why no error?** — No rules were defined. The schema only checks types — "is it a string?" Empty strings are strings — so no error.

This is correct — we're just connecting the pieces. In 4.4.5 we'll add validation rules — then errors will start appearing.

## Summary

✅ **Zod** — you write schemas — "this is what the data should look like"  
✅ `z.object({})` — an object schema — define your fields  
✅ `z.string()` — a type check — "this should be a string"  
✅ `@hookform/resolvers` — bridges Zod and RHF  
✅ `resolver: zodResolver(formSchema)` — pass to `useForm`, "let Zod validate on submit"  
✅ `useForm<FormFields>({ resolver })` — type info AND resolver both passed in  
✅ `formState: { errors }` — works exactly as in 4.4.3  
✅ Remove built-in validators from `register` — Zod handles everything  
✅ Just `z.string()` won't catch empty fields — need rules for that  
⚠️ **Manual type + Zod schema = duplication** — `z.infer` solves this (in 4.4.6)
