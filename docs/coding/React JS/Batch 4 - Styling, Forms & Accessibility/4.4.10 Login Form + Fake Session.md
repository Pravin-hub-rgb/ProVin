## What We've Covered So Far

Register works - validates, collects, and then... throws the account into a `console.log`, where it evaporates. 4.4.10 fixes that with two pieces: a **fake database** (localStorage helpers) and the **session** (`AuthContext` - the exact shape 4.4.7 promised). Plus the form that checks *truth*, not just shape: Login.

## The Fake Database - `src/authStorage.ts`

```ts
// src/authStorage.ts
export type User = { name: string; email: string }
export type StoredUser = User & { password: string }

const USERS_KEY = 'auth-demo-users'

export function getUsers(): StoredUser[] {
  const raw = localStorage.getItem(USERS_KEY)
  return raw ? (JSON.parse(raw) as StoredUser[]) : []
}

export function saveUser(user: StoredUser): void {
  const users = getUsers()
  users.push(user)
  localStorage.setItem(USERS_KEY, JSON.stringify(users))
}

export function findUser(email: string): StoredUser | undefined {
  return getUsers().find((u) => u.email === email)
}
```

Every decision explained:

- **Two shapes, on purpose.** `StoredUser` (the database record) has the password. `User` (the session) does not - a logged-in session never needs to carry a password around, so it never does.
- **`getUsers()` with the `raw ?` guard** - first visit ever: the key doesn't exist, `getItem` returns `null`, and `JSON.parse(null)` would crash. The guard turns "no data" into `[]`.
- **`findUser` returns `StoredUser | undefined`** - not-found is a *value*, not an exception. The caller decides what "no user" means.
- **Plaintext warning, once and honestly:** this demo stores raw passwords. A real backend **hashes** them server-side before storage - that's server territory, outside this course. Demo scope: fine. Anything real: never.

## Register Gets a Memory

One update to `Register.tsx` - the submit stops evaporating:

```tsx
import { useNavigate } from 'react-router-dom'
import { saveUser } from '../authStorage'

// inside the component:
const navigate = useNavigate()

const onSubmit = (data: RegisterFields) => {
  saveUser({ name: data.name, email: data.email, password: data.password })
  navigate('/login')
}
```

Why navigate to `/login` instead of auto-logging-in? **Deliberate.** The flow register → login → dashboard is the classic path, and auto-login would skip the login form you're about to build. (Real products often auto-login - for this demo, walking the full path is the point. Demo scope note: duplicate emails are allowed; a real backend enforces uniqueness. Adding a `findUser` check before `saveUser` is a good self-challenge.)

## The Session - `src/context/AuthContext.tsx`

Same pattern 3.3 taught - `createContext` + a provider + a guard hook - now holding a real `User | null` instead of a hardcoded boolean:

```tsx
// src/context/AuthContext.tsx
import { createContext, useContext, useState } from 'react'
import type { ReactNode } from 'react'
import type { User } from '../authStorage'

type AuthContextType = {
  user: User | null
  login: (user: User) => void
  logout: () => void
}

const AuthContext = createContext<AuthContextType | undefined>(undefined)

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null)

  const login = (u: User) => setUser(u)
  const logout = () => setUser(null)

  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  )
}

export function useAuth(): AuthContextType {
  const ctx = useContext(AuthContext)
  if (!ctx) throw new Error('useAuth must be used inside AuthProvider')
  return ctx
}
```

- `user: User | null` - the one source of truth 4.4.7 designed. Nobody is logged in, or exactly one person is.
- `login`/`logout` are the **only** ways state changes - components never call `setUser` directly; they ask.
- The `useAuth()` guard: context `undefined` means the Provider is missing - fail loudly at the mistake site, not three components away. (Same guard pattern as 3.3.)

`main.tsx` gets the provider, inside `BrowserRouter`:

```tsx
<BrowserRouter>
  <AuthProvider>
    <App />
  </AuthProvider>
</BrowserRouter>
```

## Login.tsx - The Form That Checks Truth

Zod validated **shape** in Register (is this a real email? long enough password?). Login adds a second question: **truth** - does this person actually exist, with this password? Two different questions, two different error sources:

```tsx
// src/pages/Login.tsx
import { useState } from 'react'
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { useNavigate } from 'react-router-dom'
import { loginSchema, type LoginFields } from '../authSchemas'
import { findUser } from '../authStorage'
import { useAuth } from '../context/AuthContext'

export default function Login() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<LoginFields>({
    resolver: zodResolver(loginSchema),
  })

  const [authError, setAuthError] = useState<string | null>(null)
  const { login } = useAuth()
  const navigate = useNavigate()

  const onSubmit = (data: LoginFields) => {
    const found = findUser(data.email)

    if (!found || found.password !== data.password) {
      setAuthError('Email or password does not match')
      return
    }

    setAuthError(null)
    const { password: _pw, ...user } = found
    login(user)
    navigate('/dashboard')
  }

  return (
    <form onSubmit={handleSubmit(onSubmit)} className="mx-auto mt-10 flex max-w-sm flex-col gap-4 p-4">
      <h1 className="text-2xl font-bold">Log in</h1>

      <div>
        <label htmlFor="email" className="mb-1 block text-sm font-medium">Email</label>
        <input
          id="email"
          {...register('email')}
          className="w-full rounded border p-2"
          aria-invalid={!!errors.email}
          aria-describedby={errors.email ? 'email-error' : undefined}
        />
        {errors.email && (
          <span id="email-error" role="alert" className="mt-1 block text-sm text-red-600">
            {errors.email.message}
          </span>
        )}
      </div>

      <div>
        <label htmlFor="password" className="mb-1 block text-sm font-medium">Password</label>
        <input
          id="password"
          type="password"
          {...register('password')}
          className="w-full rounded border p-2"
          aria-invalid={!!errors.password}
          aria-describedby={errors.password ? 'password-error' : undefined}
        />
        {errors.password && (
          <span id="password-error" role="alert" className="mt-1 block text-sm text-red-600">
            {errors.password.message}
          </span>
        )}
      </div>

      {authError && (
        <p role="alert" className="rounded bg-red-50 p-2 text-sm text-red-600">
          {authError}
        </p>
      )}

      <button type="submit" className="rounded bg-blue-600 p-2 font-medium text-white hover:bg-blue-700">
        Log in
      </button>
    </form>
  )
}
```

The interesting parts:

- **Two error sources, two displays.** `errors.email`/`errors.password` = shape problems, per-field, from Zod via the resolver. `authError` = a truth problem, one box for the whole attempt, from the lookup. Notice the truth error is deliberately vague - "email or password" - because telling *which one* failed helps attackers; vague is the correct UX here.
- **`const { password: _pw, ...user } = found`** - rest destructuring: `_pw` catches the password and throws it away, `...user` collects everything else = exactly `{ name, email }`, a clean `User`. The session keeps no secrets.
- **4.4.8's promise lands:** login schema stayed presence-only, and the *match* check lives here in the lookup - shape and truth each in their own home.

## The Blank Dashboard Moment

`navigate('/dashboard')` runs, the URL changes... and the page is **blank**. Not a bug - routing's contract: a URL renders only what a `<Route>` maps, and no route maps `/dashboard` yet. The route - and its guard - arrive in 4.4.11. (The user *is* logged in right now; you can see it in React DevTools via the context value. The page is just homeless.)

**TEST:** register an account → lands on `/login`. DevTools → Application → Local Storage → `auth-demo-users` shows your record (plaintext password - the demo warning, visible). Wrong password → the single vague alert box. Correct credentials → URL becomes `/dashboard`, page blank, nobody errors.

## Common Mistakes (Senior Dev Blind Spots)

- **Persisting the session to localStorage right now** - memory first. Storage is a *persistence* decision (4.4.12), not a state-shape decision. Jumping early couples the UI to storage and creates two competing truths.
- **Zod-ifying the wrong-credentials case** - putting `min(8)` on login's password to "help" locks out users with older short passwords. Shape validation belongs to the schema; existence belongs to the lookup.
- **Letting the password ride in the session** - `User` (no password) vs `StoredUser` (with password) is the boundary. The rest-destructure exists precisely so nobody "just passes `found`" and leaks it into context.

## Try It Yourself (Active Recall)

1. Login has two error displays. What decides which one a user sees on a given failed attempt?
2. What exactly does `const { password: _pw, ...user } = found` produce - and why not just `login(found)`?
3. Why does `AuthProvider` wrap the app in `main.tsx` instead of living inside `Login`?

<details><summary>Sample Answers</summary>

1. **Shape vs truth.** Bad format (not-an-email, empty password) → Zod's per-field errors under the fields. Well-shaped credentials that don't match a real user → the single `authError` box. The resolver handles the first question, `findUser` handles the second.
2. It produces a `User` without the password: `_pw` captures the password (unused on purpose), `...user` gathers the remaining keys (`name`, `email`). `login(found)` would copy the plaintext password into context state - pointless exposure in a session that never needs it.
3. Because the session must be reachable from *anywhere* the app will need it - Login, Dashboard, and soon `ProtectedRoute`. A provider inside Login would make `useAuth()` throw everywhere else; context lives at the highest component that needs to hand it down.

</details>

## Summary (The Developer's Mental Model)

— Two types, one boundary: `StoredUser` (with password) in the fake DB, `User` (clean) in the session
— Context = the session's single home; `login`/`logout` = its only doors
— Shape errors (Zod, per-field) and truth errors (lookup, one box) are different species
— The vague "email or password" message is correct UX, not laziness
— Register → login by design: walk the whole path in a demo
