## What We've Covered So Far

The scaffold is ready (4.4.7) - three pages planned, session shape decided (`User | null`). Now, before a single form field gets typed, we write the contract both forms will obey: two Zod schemas, one file.

You already know the pieces from 4.4.3-4.4.5: `z.object({...})` describes the fields, validation rules chain onto each field, and `z.infer` auto-generates the TypeScript type so the form never hand-maintains a duplicate. One idea here is genuinely new: a rule that needs to see **two fields at once**.

## The Register Schema

Four fields, three with plain field-level rules:

```tsx
// src/authSchemas.ts
import { z } from 'zod'

export const registerSchema = z.object({
  name: z.string().min(2, 'Name needs at least 2 characters'),
  email: z.email('Email is not in the right format'),
  password: z
    .string()
    .min(8, 'Password needs at least 8 characters')
    .regex(/[0-9]/, 'Password needs at least one number'),
  confirmPassword: z.string(),
})
```

Read the decisions:

- **name: min(2)** - one character isn't a name; "A" alone fails, "Ajay" passes.
- **email: z.email()** - Zod v4's top-level email checker (4.4.4's syntax).
- **password: min(8) + regex** - two rules chained on one field. The regex `/[0-9]/` just asks "is there any digit anywhere?" - nothing fancier. Password *strength politics* can wait; this demo needs rules a user can actually understand.
- **confirmPassword: z.string()** - deliberately *plain*. It has no rule of its own, because its rule depends on another field. That's the next section.

## Cross-Field Validation - `.refine`

Here's the problem: "confirm password must equal password" needs to see **both** fields. A rule chained onto `confirmPassword` only sees `confirmPassword` - it has no idea what `password` contains. Zod's answer is `.refine` on the whole object:

```tsx
export const registerSchema = z
  .object({
    name: z.string().min(2, 'Name needs at least 2 characters'),
    email: z.email('Email is not in the right format'),
    password: z
      .string()
      .min(8, 'Password needs at least 8 characters')
      .regex(/[0-9]/, 'Password needs at least one number'),
    confirmPassword: z.string(),
  })
  .refine((data) => data.password === data.confirmPassword, {
    message: 'Passwords do not match',
    path: ['confirmPassword'],
  })
```

How to read it:

- `.refine((data) => ...)` - receives the **whole parsed object** (`data.password` and `data.confirmPassword` together). Return `true` = pass, `false` = fail.
- `message` - the human-readable error when it fails.
- `path: ['confirmPassword']` - *where* to attach the error. Without `path`, an object-level failure attaches to the object itself, and the form has no `errors.confirmPassword` to show. With `path`, the error lands exactly where the user is looking: the confirm field. That's why the form in 4.4.9 will render `errors.confirmPassword.message` and this all just works.

## The Login Schema - Deliberately Simpler

```tsx
export const loginSchema = z.object({
  email: z.email('Email is not in the right format'),
  password: z.string().min(1, 'Password is required'),
})
```

Notice what's *missing*: no `min(8)`, no regex. On purpose.

Registration validates **creation rules** - "if you're making a new password, it must be strong." Login validates **presence** - "did you type something?" If login demanded `min(8)`, a user whose old password predates a new strength rule could never sign in. The two schemas enforce different moments, so they have different strictness. Copying the register rules onto login is a classic over-validation bug.

(The real "email or password wrong" check isn't Zod's job at all - it happens in 4.4.10 when login looks the user up in the store. Zod checks *shape*; the lookup checks *truth*.)

## Types via `z.infer` - One File, Two Types

```tsx
export type RegisterFields = z.infer<typeof registerSchema>
export type LoginFields = z.infer<typeof loginSchema>
```

Same pattern as 4.4.5: the schema is the single source of truth, and the types fall out of it. `RegisterFields` = `{ name: string; email: string; password: string; confirmPassword: string }`, generated, never hand-typed.

## Common Mistakes (Senior Dev Blind Spots)

- **Chaining the match rule onto `confirmPassword`** - a field-level rule can't see its sibling field. The comparison must live in an object-level `.refine`, or it simply can't work.
- **Dropping `path: ['confirmPassword']`** - the refine fires, but the error attaches to the object, `errors.confirmPassword` stays undefined, and the user sees nothing. The rule worked; the display didn't.
- **Cloning register's password rules onto login** - locks out anyone whose password was created under older rules.

## Try It Yourself (Active Recall)

1. Why can't the password-match rule be chained onto the `confirmPassword` field?
2. What does `path: ['confirmPassword']` change about where the error shows up?
3. Why is the login schema weaker than the register schema - what breaks if you copy the strength rules over?

<details><summary>Sample Answers</summary>

1. A rule chained on a field only receives that one field's value. "Confirm equals password" needs both values, so only an object-level `.refine` - which receives the whole data object - can express it.
2. Without `path`, the failure attaches to the whole object and `errors.confirmPassword` never populates, so the form can't show it under the field. With `path`, the error is placed on that exact key and displays where the user typed.
3. Registration validates creation rules (new password must be strong); login validates presence (something was typed). If login demanded the strength rules, any user with a password created before those rules existed could never log in again.

## Summary (The Developer's Mental Model)

— Schemas before forms - the contract exists before the UI that obeys it
— Field-level rules see one field; object-level `.refine` sees everything
— `path:` decides where a refine error lands - put it where the user is looking
— Register validates creation; login validates presence - different strictness by design
— `z.infer` exports the types; the forms in 4.4.9/4.4.10 never hand-write them
