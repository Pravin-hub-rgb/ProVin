## What We've Covered So Far

The contract exists (4.4.8) - `registerSchema` with its cross-field `.refine`, and `RegisterFields` generated by `z.infer`. Now build the form that obeys it: four fields wired through `register()`, validation handed entirely to `zodResolver`, and errors displayed the accessible way - the `aria-invalid` + `role="alert"` pattern from 4.2.3, now powered by real rules.

## The Form's Job - and What It Doesn't Do

One mental shift before the code, because it explains why this component stays calm:

- The form **renders fields and collects values** - `{...register('name')}` wires each input.
- The form does **not validate**. `zodResolver(registerSchema)` means every rule lives in 4.4.8's schema file. New rule? Edit the schema - the form never changes.
- The form only decides **what happens on success** - `handleSubmit`'s callback fires only when the whole schema passed.

Compare that to 4.3's manual form, where validation logic, error state, and submit handling were all tangled in one component. Here the same three concerns live in three homes: **schema = the rules, resolver = the glue, form = the display.**

## Register.tsx - Full Code

```tsx
// src/pages/Register.tsx
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { registerSchema, type RegisterFields } from '../authSchemas'

export default function Register() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<RegisterFields>({
    resolver: zodResolver(registerSchema),
  })

  const onSubmit = (data: RegisterFields) => {
    console.log('Account created:', data)
  }

  return (
    <form onSubmit={handleSubmit(onSubmit)} className="mx-auto mt-10 flex max-w-sm flex-col gap-4 p-4">
      <h1 className="text-2xl font-bold">Create your account</h1>

      <div>
        <label htmlFor="name" className="mb-1 block text-sm font-medium">Name</label>
        <input
          id="name"
          {...register('name')}
          className="w-full rounded border p-2"
          aria-invalid={!!errors.name}
          aria-describedby={errors.name ? 'name-error' : undefined}
        />
        {errors.name && (
          <span id="name-error" role="alert" className="mt-1 block text-sm text-red-600">
            {errors.name.message}
          </span>
        )}
      </div>

      <div>
        <label htmlFor="email" className="mb-1 block text-sm font-medium">Email</label>
        <input
          id="email"
          {...register('email')}
          className="w-full rounded border p-2"
          aria-invalid={!!errors.email}
          aria-describedby={errors.email ? 'email-error' : undefined}
        />
        {errors.email && (
          <span id="email-error" role="alert" className="mt-1 block text-sm text-red-600">
            {errors.email.message}
          </span>
        )}
      </div>

      <div>
        <label htmlFor="password" className="mb-1 block text-sm font-medium">Password</label>
        <input
          id="password"
          type="password"
          {...register('password')}
          className="w-full rounded border p-2"
          aria-invalid={!!errors.password}
          aria-describedby={errors.password ? 'password-error' : undefined}
        />
        {errors.password && (
          <span id="password-error" role="alert" className="mt-1 block text-sm text-red-600">
            {errors.password.message}
          </span>
        )}
      </div>

      <div>
        <label htmlFor="confirmPassword" className="mb-1 block text-sm font-medium">Confirm password</label>
        <input
          id="confirmPassword"
          type="password"
          {...register('confirmPassword')}
          className="w-full rounded border p-2"
          aria-invalid={!!errors.confirmPassword}
          aria-describedby={errors.confirmPassword ? 'confirm-error' : undefined}
        />
        {errors.confirmPassword && (
          <span id="confirm-error" role="alert" className="mt-1 block text-sm text-red-600">
            {errors.confirmPassword.message}
          </span>
        )}
      </div>

      <button type="submit" className="rounded bg-blue-600 p-2 font-medium text-white hover:bg-blue-700">
        Sign up
      </button>
    </form>
  )
}
```

Read it once with attention, and the rest of the project becomes pattern repetition:

- `useForm<RegisterFields>` - the generic is **`z.infer`'s payoff**. The type came from the schema (4.4.8), not from hand-writing an interface. `register('name')`, `errors.name` - everything autocompletes and type-checks against the schema's keys.
- `resolver: zodResolver(registerSchema)` - the glue. Every validation call `handleSubmit` makes goes through the schema.
- `{...register('name')}` - spreads `onChange`, `onBlur`, `ref`, `name` onto the input. That's the whole wiring.
- The error `<span>` block - identical shape on all four fields: `id` matching `aria-describedby`, `role="alert"` so screen readers announce it the moment it appears. (4.2.3 taught this wiring with a made-up error; now a real schema fills it.)

## What `handleSubmit` Actually Does

When the user clicks **Sign up**, `handleSubmit(onSubmit)` runs a pipeline:

```
click → collect all registered values → zodResolver validates against registerSchema
     → pass? → onSubmit(data) - data is fully typed
     → fail? → errors populated, onSubmit never runs
```

Two consequences worth noticing:

- **`data` inside `onSubmit` is validated data.** No `?? ''` paranoia, no re-checking - the schema already said yes.
- **Errors appear after the first submit attempt** (RHF's default mode). That's the right default for a signup form - nobody wants to be scolded mid-typing. (RHF can validate on blur/change too - a knob you already met in 4.4.2; leave it default here.)

## The confirmPassword Error Path - Full Trace

The cross-field rule gets its moment. Type `hello123` in password, `hello124` in confirm, submit:

1. The object-level `.refine` runs: `data.password === data.confirmPassword` → false.
2. Because 4.4.8 passed `path: ['confirmPassword']`, Zod attaches the message to that key.
3. `zodResolver` copies it into `errors.confirmPassword.message`.
4. The confirm field's `<span>` renders: **"Passwords do not match"** - under the exact field the user is looking at.

Four steps, zero code in the form component. That trace is the whole schema-first idea working end to end.

**TEST:** empty submit → **three** errors (name, email, password) - and NOT confirm. Why? `confirmPassword`'s field rule is plain `z.string()`, and the match-refine compares `'' === ''` - true. Its error only appears when both fields have content and disagree. Then: short password with a digit → min-8 message; long password with no digit → regex message; two different passwords → the confirm error; valid data → console shows the account object.

## Common Mistakes (Senior Dev Blind Spots)

- **`register('confirmPassword')` typo'd or missing while the schema expects it** - the field never joins the form's data, the refine compares against `undefined`, and "Passwords do not match" shows even when they match. The safety net: `useForm<RegisterFields>` makes a bad key a TypeScript error - respect that error instead of reaching for `any`.
- **Skipping the aria wiring because "the red text shows anyway"** - sighted users see it; screen readers get silence. The `id` + `aria-describedby` + `role="alert"` trio is not decoration (4.2.3's lesson, still true).
- **Mirroring values into a `useState` copy** - then `onSubmit` reads the copy while the form reads its own state, and two sources of truth drift. Trust `handleSubmit`'s `data`.

## Try It Yourself (Active Recall)

1. A new rule arrives: "password needs an uppercase letter." Which file changes, and how many lines in the form component?
2. Empty submit shows three errors, not four - which error is missing, and what does that reveal about how the schema was designed?
3. Trace the mismatch flow: from `.refine` to the pixels. Which schema line decided *where* the message lands?

<details><summary>Sample Answers</summary>

1. `authSchemas.ts` only - add `.regex(/[A-Z]/, 'Password needs an uppercase letter')` to the password chain. The form component changes **zero lines**; it displays whatever the schema decides.
2. The confirm-password error. `confirmPassword` has no field-level rule of its own (plain `z.string()`), and the cross-field refine passes on two empty strings (`'' === ''`). The error exists only for genuine mismatches - the schema was designed so an empty confirm isn't scolded twice.
3. `.refine((data) => data.password === data.confirmPassword, { path: ['confirmPassword'] })` → Zod attaches the failure to the `confirmPassword` key → zodResolver copies it to `errors.confirmPassword` → the `<span id="confirm-error">` renders it. `path:` decided the landing spot.

## Summary (The Developer's Mental Model)

— Three homes: schema holds the rules, resolver glues them, form only displays
— `data` in `onSubmit` is validated, typed data - trust it
— The mismatch trace: refine → `path:` → `errors.confirmPassword` → pixels - no form-code involved
— Accessibility wiring is per-field and mechanical: `htmlFor`/`id`, `aria-invalid`, `aria-describedby`, `role="alert"`
— Empty submit shows 3 errors by design - the schema thinks before it scolds
