Wait - auth? Didn't 3.3 already teach protected routes? It did - with a hardcoded boolean and a throwaway demo. You learned the *pattern* there. This project makes it real: actual forms creating actual accounts, a session you can hold, and a dashboard you genuinely cannot open while logged out. RHF + Zod finally get a full-time job.

## Client SRD - Auth Demo

```
Pages:      Register, Login, Dashboard (protected)
Register:   name, email, password, confirm password - RHF + Zod validation
Login:      email + password - checked against the registered user
Session:    fake - the "logged in" user lives in app state (Context)
Protect:    Dashboard only when logged in; otherwise redirect to Login
Flow:       Register → Login → Dashboard → Logout → Login
Must be:    Accessible (labels, aria-invalid, role="alert"), styled with Tailwind
```

One honest note before anything: there is **no backend here**. A real login needs a server checking passwords, and servers are outside this course's scope. So the auth layer is a client-side fake: registered users get saved to `localStorage`, login checks that store, and the session is just React state behind a Context. The forms, the validation, the session logic, and the route guarding are all real - only the server's trust is pretend. (And no, storing raw passwords like this is never okay in production - a real backend hashes them server-side. 4.4.10 flags this properly.)

## A Developer's First Move

Before any code, two things:

**1. Extract the views and the flow.** Three pages, one guard. A visitor registers, logs in, lands on the dashboard, logs out - and the dashboard stays out of reach until the next login. Each page gets its own file.

**2. Decide the session shape.** One piece of state carries the whole story:

```tsx
type User = { name: string; email: string }
// session = User | null
// null = nobody logged in; an object = this person is logged in
```

Why one state, not two booleans? `isLoggedIn` + `userName` can disagree (`isLoggedIn: true, userName: undefined` - logged in as nobody?). One `User | null` cannot disagree with itself. That single decision prevents a whole class of bugs.

The component tree:

```
App
 → AuthProvider (owns the session - coming in 4.4.10)
 → Routes
      → /register   → Register
      → /login      → Login
      → /dashboard  → ProtectedRoute → Dashboard
```

## Setup

Scaffold and install:

```bash
npm create vite@latest auth-demo -- --template react-ts
# bun: bunx create-vite@latest auth-demo -- --template react-ts

npm install react-router-dom react-hook-form @hookform/resolvers zod
# bun: bun add react-router-dom react-hook-form @hookform/resolvers zod
```

Tailwind v4 needs exactly three pieces (the full converter story lives in 4.1.1): **install** the packages, **register** the plugin, **import** once:

```bash
npm install tailwindcss @tailwindcss/vite
# bun: bun add tailwindcss @tailwindcss/vite
```

```ts
// vite.config.ts - register the plugin
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  plugins: [react(), tailwindcss()],
})
```

```css
/* src/index.css - import once, everything after is classes */
@import "tailwindcss";
```

And `BrowserRouter` goes around the app in `src/main.tsx` - you can't use `Link` or routes without it (3.1's rule, still true):

```tsx
import { BrowserRouter } from 'react-router-dom'
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import './index.css'
import App from './App'

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <BrowserRouter>
      <App />
    </BrowserRouter>
  </StrictMode>
)
```

Folders, only where code is about to exist: `src/pages/` (Register, Login, Dashboard) and `src/context/` (AuthContext, coming in 4.4.10). `ProtectedRoute` joins `src/components/` in 4.4.11. Don't create empty files for them yet - folders are cheap scaffolding, empty files are noise.

**TEST:** `npm run dev` - the default Vite page renders styled (big bold heading = Tailwind is wired). Unstyled = recheck the plugin registration.

## Common Mistakes (Senior Dev Blind Spots)

- **Installing `react-hook-form` but not `@hookform/resolvers/zod`** - `zodResolver` lives in the resolvers package. One install, two packages, always together.
- **Skipping the Tailwind plugin registration** - the install alone does nothing; Vite never learns to scan your classes.
- **Designing two booleans for the session** - `isLoggedIn` and `currentUser` drift apart the first time someone updates one and forgets the other.

## Try It Yourself (Active Recall)

1. Which routes will this app have, and which one is guarded?
2. Why is the session `User | null` instead of `isLoggedIn: boolean`?
3. Where does the "logged in user" live after login succeeds - localStorage, or Context? Why the difference matters? (Hint: one of them is the runtime truth; the other is coming later for persistence.)

<details><summary>Sample Answers</summary>

1. Three: `/register`, `/login`, `/dashboard` - and only `/dashboard` is guarded, because only the dashboard requires being logged in.
2. Because one variable cannot disagree with itself. Two booleans (`isLoggedIn` + a name) can drift out of sync; `User | null` makes "is someone logged in" and "who" the same fact.
3. In Context (app state) - that's the runtime truth the UI reads. localStorage persistence is a separate concern arriving in 4.4.12; mixing them too early couples the UI to storage.
