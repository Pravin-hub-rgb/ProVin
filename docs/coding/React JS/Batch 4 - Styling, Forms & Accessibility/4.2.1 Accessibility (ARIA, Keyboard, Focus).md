
## Cheat Sheet (Quick Recall)

```tsx
// ARIA Basics
<button aria-label="Close menu">✕</button>
<nav aria-label="Main navigation">...</nav>
<button aria-expanded={isOpen} onClick={() => setIsOpen(!isOpen)}>
  {isOpen ? "✕" : "☰"}
</button>
<div role="dialog" aria-modal="true" aria-labelledby="modal-title">...</div>

// Form labels
<label htmlFor="email">Email</label>
<input id="email" type="email" aria-required="true" />
<span id="email-error" role="alert">Invalid email</span>
<input aria-describedby="email-error" aria-invalid={hasError} />

// Focus Management
<button ref={firstFocusableRef} autoFocus>OK</button>
// tabindex="0" → keyboard accessible (natural order)
// tabindex="-1" → programmatically focusable (Tab se nahi)
// tabindex="-1" usually used with .focus() in JS

// Keyboard
<button onKeyDown={(e) => e.key === "Escape" && close()}>✕</button>

// Visual focus
className="focus:outline-none focus:ring-2 focus:ring-blue-500 focus:ring-offset-2"
```

## Abhi Tak Kya Hua

4.1.2 mein Gym landing page banayi — Tailwind se responsive design, utility classes, hover effects, grid layouts. Sab kuch Tailwind se styling kiya. App achi dikhti hai, colors hain, spacing hai, responsive hai.

Lekin ek problem hai, aur yeh problem bahut log ignore karte hain (maine bhi pehle ignore kiya tha).

**Apni Gym site kholo. Mouse uthao. Sirf keyboard se use karne ki koshish karo.**

- Tab press karo — navbar links pe focus hota hai? Pata kaise chalega kaun focus mein hai?
- Hamburger button pe Enter dabao — menu khulta hai. Lekin screen reader use kar raha ho toh usse pata chalega ki menu khula ya band?
- Contact form hai toh — labels hain? Screen reader "yeh input email ke liye hai" kaise batayega?
- Agar koi modal (popup) ho — focus modal ke andar atka rahega ya backdrop ke peeche chala jayega?

Yeh sab **accessibility** (ya a11y — a + 11 letters + y, industry mein shorthand) ke questions hain. Aur honestly — maine khud apne pehle projects mein accessibility ko "extra feature" samjha tha. Baad mein realise kiya ki yeh **essential** hai. Ek app jo sab use kar sake — keyboard users, screen reader users, motor disabilities wale — wahi truly "working" app hai.

Is doc mein accessibility seekhenge — specifically React apps mein. ARIA attributes, keyboard navigation, focus management, screen reader support. Aur jo Gym site 4.1 mein banayi hai, use **accessible** banayenge.

Specifically kya hoga:
- **ARIA basics** — labels, roles, states kaise use karte hain

## Step 2 — ARIA Ka Concept

### Step 2.1 — Concept: ARIA Kya Hai

ARIA = **Accessible Rich Internet Applications**. Lamba naam hai, lekin kaam simple — HTML elements ko screen readers ke liye zyada descriptive banana.

Socho — ek `<div>` hai jisme `<button>` ki tarah click handler hai. Browser ko pata hai ki yeh div hai. Screen reader ko pata nahi ki yeh button ki tarah behave karta hai. ARIA attributes batate hain:

```html
<!-- Screen reader: "Yeh ek div hai" — not helpful -->
<div onClick={handleClick}>Click me</div>

<!-- Screen reader: "Yeh ek button hai" — now user knows it's clickable -->
<div role="button" onClick={handleClick} tabIndex={0}>Click me</div>
```

ARIA ka fundamental rule: **Pehle semantic HTML use karo. ARIA sirf tab use karo jab native HTML element enough na ho.** Matlab — `<button>` use kar sakte ho toh `role="button"` mat daalo. Native `<nav>` use kar sakte ho toh `<div role="navigation">` mat daalo. ARIA tab use karo jab custom component bana rahe ho jiska koi native HTML element nahi hai (jaise tab panel, accordion, modal).

### Step 2.2 — ARIA ke 3 Types

ARIA attributes broadly teen categories mein aate hain:

1. **Roles** — element ka type batate hain: `role="navigation"`, `role="dialog"`, `role="alert"`
2. **Properties** — element ke baare mein extra info: `aria-label="Close"`, `aria-describedby="error-msg"`
3. **States** — element ki current state: `aria-expanded="true"`, `aria-invalid="true"`, `aria-hidden="true"`

### Step 2.3 — Visual Mapping: Screen Reader Kaise Interpret Karta Hai

Jab screen reader kisi element pe pahunchta hai, yeh sequence hota hai:

```
Element → role detect → name/properties read → state announce → interact
```

Example — ek button jisme `aria-label="Close menu"` aur `aria-expanded="true"` hai:
```
Screen Reader: "Close menu button, expanded. Double tap to activate."
```

Bina ARIA ke sirf "✕ button" bolta — user ko pata nahi ✕ kya karta hai.

### Step 2.4 — Minimal Code: ARIA in Action

```tsx
function IconButton({ label, icon, isOpen, onClick }) {
  return (
    <button
      aria-label={label}         // screen reader ko batata hai ki yeh button kya karta hai
      aria-expanded={isOpen}     // batata hai ki koi menu/drawer khula hai ya nahi
      onClick={onClick}
      className="p-2"
    >
      {icon}
    </button>
  );
}

// Use: <IconButton label="Toggle menu" icon={isOpen ? "✕" : "☰"} isOpen={isOpen} />
```

Screen Reader: "Toggle menu button, expanded" ya "Toggle menu button, collapsed" — state ke hisaab se.

### Step 2.5 — Flow: Jab User Tab Press Karta Hai

```
1. User Tab press karta hai
2. Browser focus next focusable element pe move karta hai
3. Screen reader element ka role, name, state detect karta hai
4. Screen reader announcement karta hai (voice ya braille)
5. User decide karta hai — interact karna hai ya next pe jaana hai
```

## Step 3 — Gym Navbar Ko Accessible Banana

Chal 4.1 ke Navbar ko accessible banate hain. Original code tha:

```tsx
<button className="md:hidden text-2xl" onClick={() => setIsOpen(!isOpen)}>
  {isOpen ? "✕" : "☰"}
</button>
```

Problem — screen reader sirf "✕ button" ya "☰ button" bolega. User ko pata nahi chalega ki yeh menu toggle hai ya kuch aur.

**Accessible version:**

```tsx
<button
  className="md:hidden text-2xl"
  onClick={() => setIsOpen(!isOpen)}
  aria-label={isOpen ? "Close menu" : "Open menu"}
  aria-expanded={isOpen}
>
  {isOpen ? "✕" : "☰"}
</button>
```

Ab screen reader bolega "Open menu button, collapsed" ya "Close menu button, expanded". User ko clearly pata hai button ka purpose aur menu ki state.

**Aur `aria-expanded` ka exactly kya kaam hai?**

Yeh ek **state attribute** hai — batata hai ki button ke associated menu ka abhi kya haal hai.

| `aria-expanded` value | Matlab | Screen reader bolega |
|---|---|---|
| `true` | Menu khula hai | "expanded" |
| `false` | Menu band hai | "collapsed" |
| Attribute hi nahi hai | Screen reader assume karega ki yeh button koi menu control nahi karta | Sirf "button" |

Agar screen reader ko `aria-expanded` nahi milega, toh woh assume karega ki button koi state maintain nahi karta. User click karega, menu khulega, lekin screen reader kuch nahi bolega — "kya hua? pata nahi."

Yahan `isOpen` React state ka true/false seedha `aria-expanded` mein ja raha hai. Jab state change hogi, React re-render karega — `aria-expanded` update ho jayega — screen reader turant naya state announce karega. **Bina koi extra code likhe.**

Bina `aria-expanded`:
```
Screen Reader: "Close menu button"
User: "Button hai. Par kya abhi menu khula hai ya band? Pata nahi."
```

Saath `aria-expanded={isOpen}`:
```
Screen Reader: "Close menu button, collapsed"
User: "Button hai, menu band hai. Click karunga toh khulega."
```

### Nav Links Mein ARIA

Mobile menu ke links mein bhi ARIA add kar sakte hain — mobile menu ko `aria-label` dena helpful hai:

```tsx
{isOpen && (
  <div
    className="md:hidden bg-gray-800 px-4 py-4 flex flex-col gap-4"
    role="navigation"
    aria-label="Mobile navigation"
  >
    <a href="#" className="hover:text-blue-400">Home</a>
    <a href="#" className="hover:text-blue-400">Features</a>
    <a href="#" className="hover:text-blue-400">Pricing</a>
    <a href="#" className="hover:text-blue-400">Contact</a>
  </div>
)}
```

Notice kiya — `<nav>` ki jagah `<div>` use kiya kyunki `<nav>` visually same hota hai but semantic difference hai. Logic yeh hai ki desktop aur mobile dono ke liye alag-alag `<nav>` elements hain. Lekin humne yahan simple rakhne ke liye div + role use kiya. Real mein better approach hai — desktop nav ko `<nav>` mein wrap karo, mobile ko alag `<nav>` mein, dono ko `aria-label` se differentiate karo.

### Focus Visible

Step 1 mein humne `*:focus { outline: none }` daal kar deliberately focus outline hata di thi. Ab wapas laate hain — lekin browser default outline se better.

Tailwind ka `focus:` prefix use karo — custom focus style banane ke liye:

```tsx
<nav className="bg-gray-900 text-white" role="navigation" aria-label="Main navigation">
  {/* Logo */}
  <div className="text-2xl font-bold">💪 GymPro</div>

  {/* Desktop Links */}
  <div className="hidden md:flex gap-8 font-medium">
    <a
      href="#"
      className="hover:text-blue-400 transition-colors focus:outline-none focus:ring-2 focus:ring-blue-400 focus:ring-offset-2 focus:ring-offset-gray-900 rounded"
    >
      Home
    </a>
    {/* ... more links */}
  </div>
</nav>
```

`focus:outline-none` — browser ka default dotted outline hatao (kyunki ab hum `focus:ring` de rahe hain, jo better dikhta hai).
`focus:ring-2 focus:ring-blue-400` — blue ring dikhao focus pe.
`focus:ring-offset-2 focus:ring-offset-gray-900` — ring aur element ke beech gap, jo dark background pe acha dikhta hai.
`rounded` — ring ko bhi rounded corners milte hain.

**Important:** Ab `src/index.css` se `*:focus { outline: none; }` hata do. Woh sirf test ke liye tha. Ab har element ko individually `focus:outline-none focus:ring-2` de rahe hain — intentional aur accessible.

**Mobile menu links pe bhi same focus classes lagao.** Desktop aur mobile link ka focus indicator same hona chahiye — keyboard user ke liye consistency. Sirf `focus:ring-offset-gray-800` istemal karo (kyunki mobile menu ka bg `gray-800` hai — offset usi ke according set karna hota hai):

```tsx
{isOpen && (
```

## Step 4 — Focus Management

### Step 4.1 — tabindex Ka Concept

Har focusable element ka ek **Tab order** hota hai. Browser natural order follow karta hai — DOM mein jo pehle aata hai, pehle focus hota hai. `tabindex` se is order ko control kar sakte ho.

```html
tabindex="0"  → Natural order mein aayega (default)
tabindex="-1" → Tab se nahi pahunch sakte, but JS se .focus() kar sakte ho
tabindex="1"  → Custom order (avoid — 0 ya -1 hi use karo)
```

**Real use case — mobile menu:** Jab user mobile menu kholta hai, focus automatically first link pe jana chahiye. Jab band karta hai, focus hamburger button pe wapas aana chahiye.

```tsx
import { useRef, useEffect } from "react";

export default function Navbar() {
  const [isOpen, setIsOpen] = useState(false);
  const menuRef = useRef<HTMLDivElement>(null);
  const buttonRef = useRef<HTMLButtonElement>(null);

  // Jab menu khule, pehle link pe focus karo
  useEffect(() => {
    if (isOpen && menuRef.current) {
      const firstLink = menuRef.current.querySelector("a");
      firstLink?.focus();
    }
  }, [isOpen]);

  // Escape key se menu band karo
  const handleKeyDown = (e: React.KeyboardEvent) => {
    if (e.key === "Escape") {
      setIsOpen(false);
      buttonRef.current?.focus(); // wapas button pe focus
    }
  };

  return (
    <nav className="bg-gray-900 text-white" aria-label="Main navigation">
      <div className="max-w-6xl mx-auto px-4 py-4 flex justify-between items-center">
        <div className="text-2xl font-bold">💪 GymPro</div>

        <div className="hidden md:flex gap-8">
          {/* desktop links */}
        </div>

        <button
          ref={buttonRef}
          className="md:hidden text-2xl"
          onClick={() => setIsOpen(!isOpen)}
          aria-label={isOpen ? "Close menu" : "Open menu"}
          aria-expanded={isOpen}
        >
          {isOpen ? "✕" : "☰"}
        </button>
      </div>

      {isOpen && (
        <div
          ref={menuRef}
          className="md:hidden bg-gray-800 px-4 py-4 flex flex-col gap-4"
          onKeyDown={handleKeyDown}
          role="navigation"
          aria-label="Mobile navigation"
        >
          <a href="#" className="hover:text-blue-400 focus:ring-2 focus:ring-blue-400 rounded px-2 py-1">
            Home
          </a>
          <a href="#" className="hover:text-blue-400 focus:ring-2 focus:ring-blue-400 rounded px-2 py-1">
            Features
          </a>
          <a href="#" className="hover:text-blue-400 focus:ring-2 focus:ring-blue-400 rounded px-2 py-1">
            Pricing
          </a>
          <a href="#" className="hover:text-blue-400 focus:ring-2 focus:ring-blue-400 rounded px-2 py-1">
            Contact
          </a>
        </div>
      )}
    </nav>
  );
}
```

### Step 4.2 — Flow: Jab User Menu Kholta Hai

```
1. User hamburger button pe Enter dabata hai
2. setIsOpen(!isOpen) → isOpen = true
3. useEffect trigger hota hai → menuRef.current.querySelector("a")?.focus()
4. Focus automatically pehle link pe chala jata hai
5. User Tab daba sakta hai doosre links pe jaane ke liye

Jab Escape dabata hai:
1. handleKeyDown mein e.key === "Escape" check
2. setIsOpen(false) + buttonRef.current?.focus()
3. Menu band, focus wapas hamburger pe — user confident hai ki "ab main yahan hoon"
```

Yeh pattern **focus management** kehlata hai. Keyboard user ke liye critical hai — agar focus automatically manage nahi hota, toh user Tab barabar dabata rahega aur pata nahi chalega ki menu khula bhi hai ya nahi.

## Step 5 — Additional Accessibility Patterns

### Skip to Content Link

Accessibility ka ek common pattern — **skip link**. Yeh ek hidden link hota hai jo screen reader aur keyboard users ko navbar/header skip karke directly main content pe jaane deta hai. Bina skip link ke, har page pe user ko 10-15 Tab presses karni padti hain navbar navigate karne ke liye.

```tsx
export default function SkipLink() {
  return (
    <a
      href="#main-content"
      className="sr-only focus:not-sr-only focus:absolute focus:top-4 focus:left-4 focus:bg-white focus:text-blue-600 focus:px-4 focus:py-2 focus:rounded focus:z-50"
    >
      Skip to main content
    </a>
  );
}
```

`sr-only` — Tailwind utility class jo visually hidden karti hai lekin screen reader readable. `focus:not-sr-only` — jab focus ho, tab visible ho jata hai. Yeh pattern implement karo Gym site mein — `#main-content` id hero section pe daalo.

### Color Contrast

WCAG (Web Content Accessibility Guidelines) ke hisaab se:
- Normal text: contrast ratio **4.5:1** minimum
- Large text (18px+ bold ya 24px+ regular): **3:1** minimum
- Tailwind ka default color palette generally compliant hai, lekin halke shades (gray-100, gray-200) white background pe contrast fail kar sakte hain

Check karne ka tool: [webaim.org/contrastchecker](https://webaim.org/contrastchecker). APne colors yahan daal ke dekh sakte ho.

## What It Is NOT

- **Accessibility sirf screen readers ke liye nahi hai.** Keyboard navigation, focus visible, color contrast, motion sensitivity — sab iska hissa hai.
- **ARIA se HTML "magically" accessible nahi ho jata.** ARIA sirf **missing semantics** add karta hai. Pehle semantic HTML use karo (native `<button>`, `<nav>`, `<label>`), phir ARIA sirf wahan lagao jahan native element enough nahi hai.
- **`aria-label` har jagah mat daalo.** Sirf tab use karo jab visual label exist nahi karta. Agar button mein text "Close" likha hai toh `aria-label="Close"` redundant hai.
- **Focus-trap sirf modal/drawer ke liye hai.** Har component mein focus-trap mat daalo. Sirf tab use karo jab user ko ek confined area mein rokna ho (modal, mobile menu).
- **Accessibility "ek baar mein perfect" nahi hoti.** Real projects mein gradually improve karte hain. First pass: keyboard navigation kaam kare. Second pass: ARIA labels. Third pass: screen reader testing.

## In Your Own Words

<details>
<summary>ARIA kya hai aur iska fundamental rule kya hai?</summary>

ARIA (Accessible Rich Internet Applications) ek set of attributes hai jo HTML elements ki semantics improve karte hain screen readers ke liye. Fundamental rule: **Pehle native semantic HTML use karo (like `<button>`, `<nav>`, `<label>`). ARIA sirf tab use karo jab native element enough na ho** — jaise custom tab panels, modals, accordions. Agar native element available hai toh ARIA mat daalo.
</details>

<details>
<summary>aria-expanded, aria-label, aria-invalid — yeh teen attributes kab use karte hain?</summary>

`aria-expanded` — toggle buttons pe (hamburger menu, accordion). Batata hai ki associated section khula hai (true) ya band (false). `aria-label` — tab use karo jab element ka visual label nahi hai, jaise icon-only button (✕ → "Close menu"). `aria-invalid` — form inputs pe jab validation fail ho. Screen reader "Name, invalid entry" bolega, user ko pata chalega ki error hai.
</details>

<details>
<summary>Focus-trap pattern kya hai aur kab use karte hain?</summary>

Focus-trap ka matlab — user ka focus ek specific area (modal, drawer) ke andar cycle karta hai aur bahar nahi ja sakta. Tab dabane se pehle focusable element se last tak cycle hota hai aur wapas first pe aata hai. Escape se modal band hota hai aur focus wapas modal open karne wale element pe jaata hai. Yeh pattern modals, side drawers, aur mobile menus mein use hota hai.
</details>

<details>
<summary>Skip to Content link kya hai aur kyun important hai?</summary>

Skip to Content ek hidden link hota hai jo page ke sabse top mein hota hai. Jab keyboard user Tab dabata hai, yeh pehle focus hota hai. Enter karne se focus directly main content pe chala jata hai, navbar/header ke saare links skip karke. Bina iske, screen reader users ko har page pe 10-15 baar Tab dabana padta hai navbar navigate karne ke liye — frustrating aur time-consuming.
</details>

<details>
<summary>WCAG contrast ratio kya hai aur Tailwind ke saath ise kaise ensure karein?</summary>

WCAG ke hisaab se normal text ka contrast ratio 4.5:1 minimum hona chahiye, large text ke liye 3:1. Tailwind ke dark shades generally compliant hain (text-gray-800 on bg-white passes). Lekin light shades (text-gray-400 on bg-white) fail ho sakti hain. Check karne ke liye WebAIM Contrast Checker use karo. Jab bhi color combination doubt ho — contrast checker mein daal kar dekh lo.
</details>
