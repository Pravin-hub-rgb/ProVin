```tsx
<label htmlFor="email">Email</label>

// tabindex="-1" → programmatically focusable (skip in Tab order)

// Keyboard
<button onKeyDown={(e) => e.key === "Escape" && close()}>✕</button>

// Visual focus
className="focus:outline-none focus:ring-2 focus:ring-blue-500 focus:ring-offset-2"
```

## What We've Covered So Far

In 4.1.2 we built the Gym landing page — responsive Tailwind design, utility classes, hover effects, grid layouts. Everything is styled. The app looks good, has colors, spacing, and is responsive across mobile, tablet, and desktop.

But there's one thing we can't see at a glance.

Open the Gym site in your browser. Put your mouse away. Use only the keyboard.

- Tab over to the nav links — can you tell which one has focus?
- Click the hamburger button with Enter — did the screen reader announce "menu opened"?
- Is there a contact form — do the labels properly associate with their inputs?
- If there's a modal (popup) — does focus stay trapped inside, or does it leak to the background?

These are **accessibility** (often abbreviated **a11y** — "a", 11 letters, "y") questions. And honestly, I used to treat accessibility as an "extra credit" feature. Later I realized — **it's not optional.** An app that only works with a mouse — for people who can use a mouse — isn't a fully "working" app. It needs to work with keyboards, screen readers, and other assistive tech too.

## Broader Goal

In this doc, we'll learn accessibility in React apps. ARIA attributes, keyboard navigation, focus management, screen reader support. And we'll take the Gym site from 4.1 and make it accessible.

Specifically, we'll cover:
- **ARIA basics** — how to use labels, roles, and states
- **Keyboard navigation** — Tab order, focus indicators, keyboard event handling

- **Focus-trap pattern** — keeping focus inside a modal/drawer
- **Accessible forms** — labels, `aria-invalid`, `aria-describedby`
- **Making the Gym site accessible** — mobile nav, contact form, book-a-trial modal

And one more thing — accessibility isn't just about screen readers. Keyboard navigation, color contrast, visible focus states — those are all part of it too. Let's get started.

## Step 2 — The ARIA Concept

### Step 2.1 — Concept: What Is ARIA?

ARIA = **Accessible Rich Internet Applications**. Long name, simple job — make HTML elements more descriptive for screen readers.

Think about it — you have a `<div>` with an `onClick` handler. The browser knows it's a div. The screen reader doesn't know it behaves like a button. ARIA attributes tell it:

```html
<!-- Screen reader: "It's a div" — not helpful -->
<div onClick={handleClick}>Click me</div>

<!-- Screen reader: "It's a button" — now the user knows it's clickable -->
<div role="button" onClick={handleClick} tabIndex={0}>Click me</div>
```

ARIA's golden rule: **Start with semantic HTML. Use ARIA only when native HTML isn't enough.** If you can use `<button>`, don't add `role="button"`. If you can use `<nav>`, don't use `<div role="navigation">`. ARIA is for custom components with no native HTML equivalent — like tab panels, accordions, modals.

### Step 2.2 — The 3 Types of ARIA Attributes

ARIA attributes broadly fall into three categories:

1. **Roles** — describe what the element is: `role="navigation"`, `role="dialog"`, `role="alert"`
2. **Properties** — provide extra information: `aria-label="Close"`, `aria-describedby="error-msg"`
3. **States** — describe the element's current condition: `aria-expanded="true"`, `aria-invalid="true"`, `aria-hidden="true"`

### Step 2.3 — Visual Mapping: How a Screen Reader Interprets an Element

When a screen reader lands on an element, this sequence runs:

```
Element → Detect role → Read name/properties → Announce state → Interact
```

Example — a button with `aria-label="Close menu"` and `aria-expanded="true"`:
```
Screen Reader: "Close menu button, expanded. Double tap to activate."
```

Without ARIA, it just says "✕ button" — the user doesn't know what ✕ does.

### Step 2.4 — Minimal Code: ARIA in Action

```tsx
function IconButton({ label, icon, isOpen, onClick }) {
  return (
    <button
      aria-label={label}         // tells the screen reader what this button does
      aria-expanded={isOpen}     // tells whether the associated menu/drawer is open
      onClick={onClick}
      className="p-2"
    >
      {icon}
    </button>
  );
}

// Use: <IconButton label="Toggle menu" icon={isOpen ? "✕" : "☰"} isOpen={isOpen} />
```

With that, the screen reader announces "Toggle menu button, expanded" or "Toggle menu button, collapsed" — state changes are automatically reflected.

### Step 2.5 — Flow: What Happens When the User Presses Tab

```
1. User presses Tab
2. Browser moves focus to the next focusable element
3. Screen reader detects the element's role, name, state
4. Screen reader announces (voice or braille)
5. User decides — interact, or keep navigating
```

## Step 3 — Making the Gym Navbar Accessible

Let's apply what we learned to the Gym navbar from 4.1.2. The original code was:

```tsx
<button className="md:hidden text-2xl" onClick={() => setIsOpen(!isOpen)}>
  {isOpen ? "✕" : "☰"}
</button>
```

Problem — the screen reader just says "✕ button" or "☰ button". No context about purpose or state.

**Accessible version:**

```tsx
<button
  className="md:hidden text-2xl"
  onClick={() => setIsOpen(!isOpen)}
  aria-label={isOpen ? "Close menu" : "Open menu"}
  aria-expanded={isOpen}
>
  {isOpen ? "✕" : "☰"}
</button>
```

Now the screen reader says "Open menu button, collapsed" or "Close menu button, expanded". The user knows exactly what the button does and what state the menu is in.

**What does `aria-expanded` actually do?**

It's a **state attribute** — it tells the screen reader the current state of the associated menu/drawer.

| `aria-expanded` value | Meaning | Screen reader says |
|---|---|---|
| `true` | Menu is open | "expanded" |
| `false` | Menu is closed | "collapsed" |
| Attribute missing | Screen reader assumes the button doesn't control a menu | Just "button" |

Without `aria-expanded`, the screen reader assumes the button doesn't manage any state. The user clicks, the menu opens, but the screen reader says nothing — "what just happened? I don't know where I am."

Here, `isOpen` is a React boolean — `true`/`false` — and it flows directly into `aria-expanded`. When the state changes, React re-renders, `aria-expanded` updates, and the screen reader picks it up instantly. No extra code needed.

**Without `aria-expanded`:**
```
Screen Reader: "Close menu button"
User: "It's a button. But is the menu open or closed? I have no idea."
```

**With `aria-expanded={isOpen}`:**
```
Screen Reader: "Close menu button, collapsed"
User: "Button controls the menu. Menu is closed. I'll click to open it."
```

### Adding ARIA to Nav Links

The mobile menu links can also get ARIA — give the mobile nav a label so the screen reader can distinguish it from the desktop nav:

```tsx
{isOpen && (
  <div
    className="md:hidden bg-gray-800 px-4 py-4 flex flex-col gap-4"
    role="navigation"
    aria-label="Mobile navigation"
  >
    <a href="#" className="hover:text-blue-400">Home</a>
    <a href="#" className="hover:text-blue-400">Features</a>
    <a href="#" className="hover:text-blue-400">Pricing</a>
    <a href="#" className="hover:text-blue-400">Contact</a>
  </div>
)}
```

Note — I used a `<div>` with `role="navigation"` instead of a `<nav>` here. The logic is that desktop and mobile are two separate navigation regions. I kept it simple with a div + role. In a real app, you'd wrap each in its own `<nav>` and use `aria-label` to differentiate.

### Focus Visible

Back in Step 1, we deliberately removed focus outlines with `*:focus { outline: none; }`. Now we restore them — but better than the default.

Use Tailwind's `focus:` prefix to create a custom focus style:

```tsx
<nav className="bg-gray-900 text-white" role="navigation" aria-label="Main navigation">
  {/* Logo */}
  <div className="text-2xl font-bold">💪 GymPro</div>

  {/* Desktop Links */}
  <div className="hidden md:flex gap-8">
    <a
      href="#"
      className="hover:text-blue-400 transition-colors focus:outline-none focus:ring-2 focus:ring-blue-400 focus:ring-offset-2 focus:ring-offset-gray-900 rounded"
    >
      Home
    </a>
    {/* ... more links */}
  </div>
</nav>
```

- `focus:outline-none` — removes the browser's default dotted outline (because we're about to add our own).
- `focus:ring-2 focus:ring-blue-400` — shows a 2px blue ring when focused.
- `focus:ring-offset-2 focus:ring-offset-gray-900` — gap between the ring and the element, in the background's color (dark gray). Works especially well on dark backgrounds.
- `rounded` — the ring inherits the element's border radius.

**Important:** Remove `*:focus { outline: none; }` from `src/index.css`. That was just a test. Now every focusable element gets its own intentional focus style.

**Apply the same focus classes to mobile menu links** too. Desktop and mobile links need consistent focus indicators — keyboard users need the same visual feedback everywhere:

```tsx
{isOpen && (
  <div
    className="md:hidden bg-gray-800 px-4 py-4 flex flex-col gap-4"
    role="navigation"
    aria-label="Mobile navigation"
  >
    <a
      href="#"
      className="hover:text-blue-400 focus:outline-none focus:ring-2 focus:ring-blue-400 focus:ring-offset-2 focus:ring-offset-gray-800 rounded px-2 py-1"
    >
      Home
    </a>
    <a
      href="#"
      className="hover:text-blue-400 focus:outline-none focus:ring-2 focus:ring-blue-400 focus:ring-offset-2 focus:ring-offset-gray-800 rounded px-2 py-1"
    >
      Features
    </a>
    <a
      href="#"
      className="hover:text-blue-400 focus:outline-none focus:ring-2 focus:ring-blue-400 focus:ring-offset-2 focus:ring-offset-gray-800 rounded px-2 py-1"
    >
      Pricing
    </a>
    <a
      href="#"
      className="hover:text-blue-400 focus:outline-none focus:ring-2 focus:ring-blue-400 focus:ring-offset-2 focus:ring-offset-gray-800 rounded px-2 py-1"
    >
      Contact
    </a>
  </div>
)}
```

Note: `focus:ring-offset-gray-800` for mobile (gray-800 background), `focus:ring-offset-gray-900` for desktop (gray-900 background). The offset color matches the background so the ring looks clean.

## Step 4 — Focus Management

### Step 4.1 — The tabindex Concept

Every focusable element has a **Tab order**. Browsers follow the natural DOM order — whichever element appears first in the HTML gets focus first. The `tabindex` attribute lets you control this.

```html
tabindex="0"  → Gets focus in natural DOM order (default for buttons, inputs)
tabindex="-1" → Can be focused with `.focus()` (keyboard), but NOT via Tab key
tabindex="1"  → Custom Tab order (avoid — only use 0 or -1)
```

**Real-world use case — mobile menu:** When the user opens the mobile menu, focus should jump to the first menu link. When they close it, focus should return to the hamburger button.

```tsx
import { useRef, useEffect } from "react";

export default function Navbar() {
  const [isOpen, setIsOpen] = useState(false);
  const menuRef = useRef<HTMLDivElement>(null);
  const buttonRef = useRef<HTMLButtonElement>(null);

  // When menu opens, focus the first link
  useEffect(() => {
    if (isOpen && menuRef.current) {
      const firstLink = menuRef.current.querySelector("a");
      firstLink?.focus();
    }
  }, [isOpen]);

  // Close on Escape
  const handleKeyDown = (e: React.KeyboardEvent) => {
    if (e.key === "Escape") {
      setIsOpen(false);
      buttonRef.current?.focus(); // return focus to the button
    }
  };

  return (
    <nav className="bg-gray-900 text-white" aria-label="Main navigation">
      <div className="max-w-6xl mx-auto px-4 py-4 flex justify-between items-center">
        <div className="text-2xl font-bold">💪 GymPro</div>

        <div className="hidden md:flex gap-8">
          {/* desktop links */}
        </div>

        <button
          ref={buttonRef}
          className="md:hidden text-2xl"
          onClick={() => setIsOpen(!isOpen)}
          aria-label={isOpen ? "Close menu" : "Open menu"}
          aria-expanded={isOpen}
        >
          {isOpen ? "✕" : "☰"}
        </button>
      </div>

      {isOpen && (
        <div
          ref={menuRef}
          className="md:hidden bg-gray-800 px-4 py-4 flex flex-col gap-4"
          onKeyDown={handleKeyDown}
          role="navigation"
          aria-label="Mobile navigation"
        >
          <a href="#" className="hover:text-blue-400 focus:ring-2 focus:ring-blue-400 rounded px-2 py-1">
            Home
          </a>
          <a href="#" className="hover:text-blue-400 focus:ring-2 focus:ring-blue-400 rounded px-2 py-1">
            Features
          </a>
          <a href="#" className="hover:text-blue-400 focus:ring-2 focus:ring-blue-400 rounded px-2 py-1">
            Pricing
          </a>
          <a href="#" className="hover:text-blue-400 focus:ring-2 focus:ring-blue-400 rounded px-2 py-1">
            Contact
          </a>
        </div>
      )}
    </nav>
  );
}
```

### Step 4.2 — Flow: When the User Opens the Menu

```
1. User presses Enter on the hamburger button
2. setIsOpen(!isOpen) → isOpen = true
3. useEffect fires → menuRef.current.querySelector("a")?.focus()
4. Focus automatically jumps to the first link
5. User can press Tab to move through the remaining links

When Escape is pressed:
1. handleKeyDown checks e.key === "Escape"
2. setIsOpen(false) + buttonRef.current?.focus()
3. Menu closes, focus returns to the hamburger — user knows they're back
```

This is called **focus management**. It's critical for keyboard users — without it, focus just disappears when the menu opens/closes, and the user has no idea where they are on the page.

## Step 5 — More Accessibility Patterns

### Skip to Content Link

A common accessibility pattern — a **skip link**. It's a hidden link at the top of the page that lets keyboard and screen reader users jump straight to the main content, bypassing the entire navigation. Without a skip link, users have to Tab through every single nav link on every page.

```tsx
export default function SkipLink() {
  return (
    <a
      href="#main-content"
      className="sr-only focus:not-sr-only focus:absolute focus:top-4 focus:left-4 focus:bg-white focus:text-blue-600 focus:px-4 focus:py-2 focus:rounded focus:z-50"
    >
      Skip to main content
    </a>
  );
}
```

`sr-only` — Tailwind class that visually hides the element but keeps it readable by screen readers. `focus:not-sr-only` — when it receives focus (first Tab press), it becomes visible. Implement this on the Gym site — add `id="main-content"` to the hero section.

### Color Contrast

WCAG (Web Content Accessibility Guidelines) requires:
- Normal text: contrast ratio of at least **4.5:1**
- Large text (18px+ bold or 24px+ regular): **3:1** minimum

Tailwind's default palette is generally compliant, but lighter shades like `gray-100` and `gray-200` on white backgrounds can fail. Check tool: [webaim.org/contrastchecker](https://webaim.org/contrastchecker). Paste your colors in to verify.

## What It Is NOT

- **Accessibility isn't only for screen readers.** Keyboard navigation, focus visibility, color contrast, motion sensitivity — they're all part of it.
- **ARIA doesn't magically make HTML accessible.** ARIA only **fills in missing semantics**. Use native semantic HTML first (`<button>`, `<nav>`, `<label>`), then add ARIA only when no native element exists.
- **Don't slap `aria-label` everywhere.** Use it only when there's no visible text — like an icon-only button (✕ → "Close menu"). If the button already says "Close", adding `aria-label="Close"` is redundant.
- **Focus-trap isn't for every component.** Use it where you need to lock the user into a confined space — modals, side drawers, mobile menus. Don't add it everywhere.
- **Accessibility isn't "get it perfect on day one."** It's iterative. First pass: make keyboard navigation work. Second pass: add ARIA labels. Third pass: test with a screen reader.

<details>
<summary>What is ARIA and what's its golden rule?</summary>

ARIA (Accessible Rich Internet Applications) is a set of attributes that make HTML elements more descriptive for screen readers. The golden rule: **Use semantic HTML first. Only add ARIA when native HTML isn't sufficient** — like custom tab panels, modals, or accordions. If you can use a `<button>`, don't add `role="button"`. If you can use a `<nav>`, don't wrap a `<div role="navigation">`. ARIA only fills in the gaps where native elements don't exist.
</details>

<details>
<summary>When do you use aria-expanded, aria-label, and aria-invalid?</summary>

`aria-expanded` goes on toggle buttons — elements that open and close a section (hamburger menus, accordions). It tells the screen reader "this button controls a section, and here's whether it's open (true) or closed (false)." `aria-label` goes on elements that have no visible text — icon-only buttons, for instance. `aria-invalid` goes on form inputs when validation fails — the screen reader announces "invalid entry" so the user knows there's an error.
</details>

<details>
<summary>What is the focus-trap pattern and when do you use it?</summary>

Focus-trap means the user's focus cycles within a specific container — a modal, a drawer — and can't escape to the background. Tabbing moves through the container's focusable elements and wraps around from last to first (and first to last with Shift+Tab). Escape closes the modal and returns focus to the trigger button. You use this pattern for modals, side drawers, and mobile menus where you want to keep the user's attention confined.
</details>

<details>
<summary>What is a skip link and why is it important?</summary>

A skip link is a hidden link at the very top of the page. When keyboard users press Tab, it's the first thing that gets focus. Press Enter and focus jumps directly to the main content, bypassing all the navigation links. Without it, screen reader and keyboard users have to Tab through every single nav link on every page — tedious and time-consuming. It's a small addition with a big impact.
</details>

<details>
<summary>What is the WCAG contrast ratio requirement, and how do you check it?</summary>

WCAG requires a contrast ratio of at least 4.5:1 for normal text and 3:1 for large text (18px+ bold or 24px+ regular). Tailwind's default palette is mostly compliant, but lighter shades like gray-100/gray-200 on white can fail.
