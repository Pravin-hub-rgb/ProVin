# 4.1.1 Quiz — Tailwind CSS aur Responsive Design

## MCQ

Q: Utility-first approach mein component styling kaise ki jaati hai?
A. Har component ke liye alag CSS file mein custom classes likhi jaati hain
B. Single-purpose utility classes ko combine karke component banaya jaata hai
C. Ek hi CSS class mein saari styling ek saath define ki jaati hai
D. Styling JavaScript functions ke through runtime pe apply ki jaati hai
> B. Utility-first approach pehle se bani chhoti classes (bg-white, p-4, rounded-lg) combine karta hai — jaise LEGO blocks. A galat — alag CSS file utility-first ka opposite hai. C galat — single class mein sab kuch traditional CSS approach hai. D galat — runtime styling Tailwind ka tareeka nahi hai.

---

Q: Tailwind setup mein PostCSS ka kya kaam hai?
A. Browser directly Tailwind classes ko interpret karta hai bina conversion ke
B. JSX files ko scan karta hai aur unka production bundle banata hai
C. Plugins ko run karta hai jo Tailwind syntax ko plain CSS mein convert karte hain
D. Dev server ko restart karta hai jab bhi postcss.config.js file change ho
> C. PostCSS ek tool hai jo plugins run karta hai. @tailwindcss/postcss plugin Tailwind syntax ko plain CSS mein convert karta hai. A galat — browser Tailwind directly nahi samajhta. B galat — scanning kaam tailwindcss engine karta hai. D galat — PostCSS dev server restart nahi karta.

---

Q: Production build mein Tailwind ka CSS size traditional CSS frameworks se chhota kyun hota hai?
A. Kyunki Tailwind CSS ko gzip compression se automatically compress kar deta hai
B. Kyunki Tailwind sirf unhi utility classes ka CSS generate karta hai jo use hui hain
C. Kyunki Tailwind CSS ko JavaScript bundle mein merge karke serve karta hai
D. Kyunki Tailwind browser par runtime CSS inject karta hai, CSS file nahi banti
> B. Tailwind tree-shaking karta hai — source files scan karta hai, sirf use ki hui classes ka CSS generate hota hai. A galat — compression alag step hai. C galat — CSS aur JS alag bundles hain. D galat — build time pe CSS generate hoti hai, runtime nahi.

Q: Tailwind mein `p-7` class kyun exist nahi karti jabki `p-6` aur `p-8` exist karti hain?
A. Kyunki 7 ka number spacing scale se intentionally remove kiya gaya hai
B. Kyunki spacing scale sirf 0.25rem ke specific multiples mein aati hai
C. Kyunki `p-7` ka matlab 7px hota hai jo Tailwind ki minimum unit se chhota hai
D. Kyunki `p-7` syntax galat hai — sahi syntax `p-07` hai leading zero ke saath
> B. Tailwind constraint-based system hai — spacing 0, 0.5, 1, 2, 3, 4, 5, 6, 8, 10... ke predefined scale mein hoti hai. 7 scale mein nahi hai. A galat — "intentionally remove" nahi, scale ka part hi nahi. C galat — p-4 ka matlab 16px hai, p-7 ka fixed px nahi. D galat — leading zero ka concept nahi hai.

Q: `text-blue-600` class mein 600 ka kya matlab hai?
A. Color ki brightness percentage hai — 600% bright shade
B. Color ka opacity level hai — 60% opaque blue color
C. Shade scale 50-900 mein se ek predefined shade level
D. Hexadecimal color code ka numeric part — #600 blue
> C. Tailwind shades 50 (halka) se 900 (dark) tak predefined hain. 600 medium-dark shade hai, primary color ke liye common. A galat — percentage brightness nahi hai. B galat — opacity nahi represent karta. D galat — hex code se koi relation nahi.

Q: Tailwind ke spacing system mein `p-4` kitni actual padding deta hai?
A. 4px — CSS native unit ke hisaab se directly 4 pixels
B. 1rem (16px) — 0.25rem ke 4 units se milkar banta hai
C. 4rem (64px) — kyunki number directly rem value hoti hai
D. 4% — parent container ki width ke percentage ke hisaab se
> B. Tailwind spacing 0.25rem (4px) ke multiples mein hota hai. p-4 = 4 × 0.25rem = 1rem = 16px. A galat — 4px nahi, 16px. C galat — number direct rem nahi hota. D galat — percentage-based spacing nahi hai.

Q: `md:` prefix wali class (jaise `md:grid-cols-2`) kis minimum screen width se apply hoti hai?
A. 640px — small devices ke liye sm breakpoint
B. 768px — tablets ke liye md breakpoint
C. 1024px — laptops ke liye lg breakpoint
D. 1280px — desktops ke liye xl breakpoint
> B. md breakpoint 768px se apply hota hai — tablets aur upar. A galat — 640px sm hai. C galat — 1024px lg hai. D galat — 1280px xl hai.

Q: Tailwind ke mobile-first approach mein bina breakpoint prefix wali class (jaise `text-base`) kab apply hoti hai?
A. Sirf mobile screens pe — baaki breakpoints pe override ho jaati hai
B. Sirf desktop screens pe — mobile ke liye alag class likhni padti hai
C. Sabhi screen sizes pe — jab tak breakpoint prefix override na kare
D. Sirf tab jab koi aur breakpoint class bhi define na ki gayi ho
> C. Mobile-first mein default (bina prefix) styling sabhi screen sizes pe apply hoti hai. Breakpoints sirf override karte hain. A galat — sirf mobile pe nahi. B galat — desktop default hi hota hai. D galat — condition define na karne ka concept nahi hai.

Q: Component state ke hisaab se Tailwind classes conditionally badalne ka standard tareeka kya hai?
A. Alag CSS file mein .active aur .inactive classes define karna
B. useState mein className string store karna aur useEffect se update karna
C. Template literal ke andar ternary operator use karna className mein
D. React Router ke through alag component render karna har state ke liye
> C. Standard pattern: `` className={`baseClasses ${condition ? 'active' : 'inactive'}`} ``. A galat — alag CSS file utility-first approach ke against hai. B galat — className useState mein store karna antipattern hai. D galat — Router navigation styling ke liye nahi hai.

Q: `hidden md:flex` class combination se element ka behavior kya hoga?
A. Mobile pe flex container, desktop aur tablet pe hidden ho jayega
B. Sabhi screen sizes pe hidden rahega — md:flex override nahi karega
C. Mobile pe hidden rahega, tablet aur desktop pe flex container banega
D. Sirf tablet screens (md) pe hidden rahega, baaki sab pe flex dikhega
> C. `hidden` = display: none (sabhi pe). `md:flex` = 768px+ pe display: flex override. Isliye mobile pe chhup jaata hai, bade screens pe flex container ban jaata hai. A galat — opposite behavior. B galat — md:flex override karta hai. D galat — md breakpoint pe show hota hai, hide nahi.

## TrueFalse

Q: Tailwind CSS inline CSS ki tarah hi hai kyunki dono mein styles element par directly likhe jaate hain aur koi design system enforce nahi hota.
- True
- False
> False. Tailwind inline CSS nahi hai. Tailwind ka predefined scale (text-xs to text-4xl, p-0 to p-16) ek consistent design system enforce karta hai. Inline CSS mein koi constraint nahi, koi consistency nahi.

---

Q: Tailwind setup mein `@import "tailwindcss"` PostCSS ko trigger karta hai Tailwind syntax ko plain CSS mein convert karne ke liye.
- True
- False
> True. `@import "tailwindcss"` PostCSS ko signal deta hai. PostCSS @tailwindcss/postcss plugin call karta hai, jo tailwindcss engine ko trigger karta hai — scanning + CSS generation.

---

Q: Tailwind use karne se sab websites ek jaisi dikhti hain kyunki sab same utility classes use karte hain.
- True
- False
> False. Tailwind sirf ek framework hai. Tum colors, spacing, typography customize kar sakte ho. Design system uniqueness decide karta hai, framework nahi.

---

Q: `rounded-full` class se element ke saare corners circular ho jaate hain — square element circle aur rectangle pill shape ban jaata hai.
- True
- False
> True. `rounded-full` border-radius: 9999px set karta hai. Square element circle ban jayega, rectangle pill shape.

---

Q: PostCSS khud CSS generate karta hai bina kisi plugin ke — sirf PostCSS install karna kaafi hai setup ke liye.
- True
- False
> False. PostCSS khud kuch nahi karta. Yeh sirf plugins ko run karne ka tareeka hai. Config mein @tailwindcss/postcss plugin register karna padta hai tabhi Tailwind syntax convert hoga.

---

Q: `hover:` prefix browser mein JavaScript hover event listener add karta hai.
- True
- False
> False. `hover:` ek CSS pseudo-class (:hover) hai — JavaScript event nahi. Browser CSS engine handle karta hai. JavaScript event listener alag cheez hai (onMouseEnter).
