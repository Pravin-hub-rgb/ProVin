
## MCQ

Q: How is component styling done in a utility-first approach?
A. Custom CSS classes are written in a separate CSS file for each component
B. Single-purpose utility classes are combined to build a component
C. All styling is defined in a single CSS class
D. Styling is applied via JavaScript at runtime
> B. The utility-first approach combines pre-existing utility classes (like `bg-white`, `p-4`, `rounded-lg`) to build components — like assembling LEGO blocks. A is wrong — a separate CSS file is the opposite of utility-first. C is wrong — putting everything in one class is traditional CSS. D is wrong — runtime styling isn't Tailwind's approach.

Q: What is PostCSS's role in the Tailwind setup?
A. The browser interprets Tailwind classes directly without any conversion
B. PostCSS scans JSX files and bundles them for production
C. PostCSS runs plugins that convert Tailwind syntax into plain CSS
D. PostCSS restarts the dev server when `postcss.config.js` changes
> C. PostCSS is a tool that runs plugins. The `@tailwindcss/postcss` plugin converts Tailwind syntax into plain CSS. A is wrong — the browser can't read Tailwind classes directly. B is wrong — scanning is done by the tailwindcss engine. D is wrong — PostCSS doesn't restart servers.

Q: Why is the CSS bundle smaller in production when using Tailwind compared to traditional CSS frameworks?
A. Tailwind is automatically gzip-compressed, shrinking the CSS bundle
B. Tailwind only generates CSS for utility classes that are actually used
C. Tailwind is merged into the JavaScript bundle, not served as a separate CSS file
D. Tailwind injects CSS at runtime, so no CSS file is ever generated
> B. Tailwind tree-shakes the output — it scans source files and only generates CSS for classes that are actually used. A is wrong — compression is a separate step. C is wrong — CSS and JS are separate bundles. D is wrong — CSS is generated at build time, not runtime.

Q: Why doesn't a `p-7` class exist in Tailwind when `p-6` and `p-8` do?
A. The value 7 was intentionally removed from the spacing scale
B. The spacing scale only includes specific 0.25rem multiples
C. 7 means 7px, which is below Tailwind's minimum spacing unit
D. The correct syntax is `p-07` with a leading zero
> B. Tailwind uses a constraint-based system — spacing follows a predefined scale (0, 0.5, 1, 2, 3, 4, 5, 6, 8, 10, 12...). 7 is not part of that scale. A is wrong — it was never in the scale to be "removed." C is wrong — p-4 means 16px, not direct px values. D is wrong — there's no leading zero convention.

Q: What does the `600` in `text-blue-600` mean?
A. The color's brightness as a percentage — 600% bright shade
B. The opacity level — 60% opaque blue
C. A predefined shade on the 50-900 scale
D. A numeric part of the hexadecimal color code
> C. Tailwind shades range from 50 (lightest) to 900 (darkest). 600 is a medium-dark shade, commonly used for primary colors. A is wrong — it's not a percentage. B is wrong — it doesn't represent opacity. D is wrong — there's no direct hex mapping.

Q: How much padding does `p-4` apply in Tailwind?
A. 4px — the number directly maps to CSS pixels
B. 1rem (16px) — 4 units of 0.25rem each
C. 4rem (64px) — the number maps directly to rem
D. 4% of the parent container's width
> B. Tailwind spacing is based on 0.25rem (4px) multiples. `p-4` = 4 × 0.25rem = 1rem = 16px. A is wrong — it's 16px, not 4px. C is wrong — the number isn't a direct rem value. D is wrong — spacing isn't percentage-based.

Q: At what minimum screen width does an `md:` prefixed class (like `md:grid-cols-2`) take effect?
A. 640px — the `sm` breakpoint for small devices
B. 768px — the `md` breakpoint for tablets
C. 1024px — the `lg` breakpoint for laptops
D. 1280px — the `xl` breakpoint for desktops
> B. The `md` breakpoint activates at 768px and above — tablets and larger. A is wrong — 640px is the `sm` breakpoint. C is wrong — 1024px is `lg`. D is wrong — 1280px is `xl`.

Q: In Tailwind's mobile-first approach, when does a class without a breakpoint prefix (like `text-base`) get applied?
A. Only on mobile screens — overridden by larger breakpoints
B. Only on desktop screens — mobile requires its own prefixed class
C. On all screen sizes — until a breakpoint prefix overrides it
D. Only when no other breakpoint class is defined
> C. In mobile-first, the default (no prefix) applies to all screen sizes. Breakpoint prefixes just override. A is wrong — it's not mobile-only. B is wrong — desktop is not the default. D is wrong — there's no "no other class" condition.

Q: What is the standard approach for conditionally changing Tailwind classes based on component state?
A. Define `.active` and `.inactive` classes in a separate CSS file
B. Store className strings in useState and update via useEffect
C. Use template literals with ternary operators inside className
D. Render a separate component for each state via React Router
> C. The standard pattern is template literals with ternaries: `` className={`base ${isActive ? 'active' : 'inactive'}`} ``. A is wrong — a separate CSS file contradicts utility-first. B is wrong — storing className in state is an anti-pattern. D is wrong — React Router isn't for styling states.

Q: What happens with a `hidden md:flex` class combination?
A. Flex container on mobile, hidden on tablet and desktop
B. Hidden on all screen sizes — `md:flex` doesn't override
C. Hidden on mobile, becomes a flex container on tablet and desktop
D. Hidden only on tablet screens, flex on all others
> C. `hidden` = display: none (all sizes). `md:flex` = display: flex at 768px+. So the element is hidden on mobile, then becomes a flex container on tablet/desktop. A is wrong — the behavior is reversed. B is wrong — `md:flex` does override. D is wrong — `md` shows, doesn't hide.

## TrueFalse

Q: Tailwind is just like inline CSS because both write styles directly on elements and enforce no design system.
- True
- False
> False. Tailwind is not inline CSS. Tailwind's predefined scale (text-xs through text-4xl, p-0 through p-16) enforces a consistent design system. Inline CSS has no constraints and no consistency.

---

Q: The `@import "tailwindcss"` directive triggers PostCSS to convert Tailwind syntax into plain CSS.
- True
- False
> True. `@import "tailwindcss"` signals PostCSS. PostCSS calls the `@tailwindcss/postcss` plugin, which triggers the tailwindcss engine — scanning and CSS generation.

---

Q: Using Tailwind makes all websites look the same since everyone uses the same utility classes.
- True
- False
> False. Tailwind is just a framework. You can customize colors, spacing, and typography. The design system determines uniqueness, not the framework.

---

Q: The `rounded-full` class makes all corners of an element circular — a square becomes a circle and a rectangle becomes a pill shape.
- True
- False
> True. `rounded-full` sets `border-radius: 9999px`. A square element becomes a circle, a rectangle becomes a pill.

---

Q: PostCSS generates CSS on its own — just installing PostCSS is enough for the setup.
- True
- False
> False. PostCSS doesn't do anything by itself. It only runs plugins. You need to register the `@tailwindcss/postcss` plugin in the config before Tailwind syntax gets converted.

---

Q: The `hover:` prefix adds a JavaScript hover event listener to the element.
- True
- False
> False. `hover:` compiles to a CSS `:hover` pseudo-class — no JavaScript involved. The browser's CSS engine handles it. A JavaScript event listener (like `onMouseEnter`) is a completely different mechanism.
