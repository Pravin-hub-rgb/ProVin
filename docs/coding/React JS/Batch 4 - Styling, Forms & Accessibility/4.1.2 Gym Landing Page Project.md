## Step 2 — Navbar

The client's SRD shows a navbar with logo, 4 links, and a hamburger. Let's build it.

### 2.1 "Get content in first. Worry about styling later."

Just HTML. No Tailwind classes. No styling at all. Just the structure.

`src/components/Navbar.tsx`:
```tsx
function Navbar() {
  return (
    <nav>
      <div>
        <div>GymPro</div>
        <div>
          <a href="#">Home</a>
          <a href="#">Features</a>
          <a href="#">Pricing</a>
          <a href="#">Contact</a>
        </div>
        <button>☰</button>
      </div>
    </nav>
  )
}

export default Navbar
```

Import in `App.tsx`:
```tsx
import Navbar from "./components/Navbar"

function App() {
  return (
    <div>
      <Navbar />
    </div>
  )
}

export default App
```

**Check the browser** — black text, white background, blue links, button shows as a button. 2010 vibes. Now let's add styling, one decision at a time.

### 2.2 "Brand identity — dark background, light text. Gym vibe."

`bg-gray-900` — the darkest gray, almost black. On the 50-900 scale, 900 is the extreme.
`text-white` — for contrast.

```tsx
<nav className="bg-gray-900 text-white">
```

**Browser:** Background goes black, text goes white. Just two classes.

> **Note:** I originally thought there'd be a `bg-dark` or `bg-primary` — no. It's `bg-gray-900`. The scale system. 900 = darkest, 50 = lightest.

### 2.3 "Content shouldn't stretch full width. Center it, cap the width."

`max-w-6xl` — maximum width of 72rem (1152px). Content wider than that gets capped.
`mx-auto` — margin left/right set to auto. Centers horizontally.
`px-4 py-4` — 1rem padding all around.

```tsx
<div className="max-w-6xl mx-auto px-4 py-4">
  {/* logo, links, hamburger */}
</div>
```

### 2.4 "How does this look on mobile (375px)?"

This is the mobile-first **moment of decision**. Take the phone screen width (375px) and ask:

> "Logo, 4 links, hamburger — can all of these fit in one row? At 375px, there's no room for nav links. So what do we keep? Just the logo and the hamburger. Links? Hide them. They'll show up on desktop."

```
┌────────────────────┐
│ 💪 GymPro     [≡]  │  ← Logo + hamburger only
│                    │  ← Links: hidden
└────────────────────┘
```

Base classes define the **mobile design**:

- `flex justify-between items-center` — logo on the left, button on the right, same row.
- Links get `hidden` — display: none on mobile. Because there's no room for them at 375px.

```tsx
<div className="max-w-6xl mx-auto px-4 py-4 flex justify-between items-center">
  <div className="text-2xl font-bold">GymPro</div>
  <div className="hidden">
    <a href="#">Home</a>
    <a href="#">Features</a>
    <a href="#">Pricing</a>
    <a href="#">Contact</a>
  </div>
  <button className="text-2xl">☰</button>
</div>
```

**TEST:** Shrink browser to 375px. Only logo + hamburger visible ✅

> **Senior dev rule:** First decide what **shouldn't** show on mobile. That decision forces you to pick a breakpoint. If everything is visible on mobile, you never need responsive breakpoints.

### 2.5 "Now stretch the browser. What breaks at 768px?"

Mobile design is done. Now the developer stretches the browser viewport wider and watches for breakage.

**768px (the `md` breakpoint).** At this width, we have room for the links. So:

> "Mobile hid the links. At 768px+, show them. And the hamburger should hide — there's space for the real links now."

```
                    Mobile (base: 0-767px)    Desktop (md+: 768px+)
Links               hidden                    flex
Hamburger           block (default)           hidden
```

This is the mobile-first pattern: base classes define mobile behavior, breakpoint prefixes override for larger screens.

```tsx
// Links — base: hidden. md override: flex
<div className="hidden md:flex gap-8 font-medium">
  <a href="#">Home</a>
  <a href="#">Features</a>
  <a href="#">Pricing</a>
  <a href="#">Contact</a>
</div>

// Hamburger — base: block (mobile shows). md override: hidden
<button className="md:hidden text-2xl">☰</button>
```

Notice — no hover classes yet. Just layout and responsive. Hover effects come as polish in the next step.

**Links note:** This is a static page — no routing. So `<a>` tags are fine. In a real app (like the To-Do app later), you'd use `<Link>` (basic navigation) or `<NavLink>` (active state styling). Choice depends on: "Do you need to highlight the active link?"

**TEST:** 375px → logo + hamburger only. 768px+ → links appear, hamburger disappears ✅

> **Revelation:** I used to think `md:` meant "apply on mobile." But it's the opposite. `md:` means "apply at 768px and above." Base classes = mobile. Breakpoints = overrides for larger screens.

### 2.6 "Now add hover — it's polish time."

The links show on desktop. Now add hover for visual feedback when the mouse is over them.

Hover is a **desktop-only interaction** — touch devices don't have hover. So we build layout and responsive first, then add hover as polish. This order matters because hover isn't accessible on mobile — don't rely on it for functionality.

```tsx
<a href="#" className="hover:text-blue-400 transition-colors">Home</a>
```

- `hover:text-blue-400` — on hover, text turns blue-400.
- `transition-colors` — smooths the transition. Default 150ms. Without it, the color change feels instant and jarring.

Apply to all links:

```tsx
<div className="hidden md:flex gap-8 font-medium">
  <a href="#" className="hover:text-blue-400 transition-colors">Home</a>
  <a href="#" className="hover:text-blue-400 transition-colors">Features</a>
  <a href="#" className="hover:text-blue-400 transition-colors">Pricing</a>
  <a href="#" className="hover:text-blue-400 transition-colors">Contact</a>
</div>
```

**TEST:** At 768px+, links visible. Hover — color smoothly shifts to blue ✅

> **Senior dev rule:** Never make critical actions hover-only. Mobile users can't access them. Hover is polish, not functionality.

### 2.7 "The hamburger needs to be clickable. Use state, not CSS hacks."

Problem: clicking the hamburger should open a mobile menu. The developer thinks:

> "Menu visibility needs to be tracked. CSS `display` toggle? No — this is React's domain. Component state."

```
Click → setIsOpen(!isOpen) → State flips
State true → Moblie menu renders
State false → Mobile menu hides
```

```tsx
import { useState } from "react"

function Navbar() {
  const [isOpen, setIsOpen] = useState(false)

  return (
    <nav className="bg-gray-900 text-white">
      <div className="max-w-6xl mx-auto px-4 py-4 flex justify-between items-center">
        <div className="text-2xl font-bold">💪 GymPro</div>

        <div className="hidden md:flex gap-8 font-medium">
          <a href="#" className="hover:text-blue-400 transition-colors">Home</a>
          <a href="#" className="hover:text-blue-400 transition-colors">Features</a>
          <a href="#" className="hover:text-blue-400 transition-colors">Pricing</a>
          <a href="#" className="hover:text-blue-400 transition-colors">Contact</a>
        </div>
        <button
          className="md:hidden text-2xl"
          onClick={() => setIsOpen(!isOpen)}
        >
          {isOpen ? "✕" : "☰"}
        </button>
      </div>

      {/* Mobile menu — renders only when isOpen is true */}
      {isOpen && (
        <div className="md:hidden bg-gray-800 px-4 py-4 flex flex-col gap-4">
          <a href="#" className="hover:text-blue-400">Home</a>
          <a href="#" className="hover:text-blue-400">Features</a>
          <a href="#" className="hover:text-blue-400">Pricing</a>
          <a href="#" className="hover:text-blue-400">Contact</a>
        </div>
      )}
    </nav>
  )
}
```

**Why not CSS `display: block/none`?** React owns state management. CSS direct manipulation bypasses React's virtual DOM. Use `useState` — React knows "re-render needed."

**TEST:** Click hamburger → menu appears. Click again → menu disappears ✅

### 3.2 "Background pattern — dark gradient."

The Hero needs to be visually impactful. Give it a gradient background:

```tsx
<section className="bg-gradient-to-r from-gray-900 via-gray-800 to-gray-900 text-white">
```

- `bg-gradient-to-r` — left-to-right gradient. Tailwind generates `background-image: linear-gradient(to right, ...)`. Just syntax, no magic.
- `from-gray-900 via-gray-800 to-gray-900` — start: darkest, middle: slightly lighter (creates gradient depth), end: darkest.

`text-white` — all text is white.

### 3.3 "Container + centering. Same pattern as before."

```tsx
<div className="max-w-6xl mx-auto px-4 py-24 md:py-32 text-center">
```

`py-24 md:py-32` — 6rem padding on mobile, 8rem on desktop. Slightly tighter spacing on mobile.

### 3.4 "Responsive heading — small on mobile, big on desktop."

Decision tree:

> "The heading is the most important element. 375px needs 4xl. At 768px, a bit bigger. At 1024px, even bigger."

```tsx
<h1 className="text-4xl md:text-5xl lg:text-6xl font-bold mb-4">
  Transform Your <span className="text-blue-500">Body</span>
</h1>
```

- `text-4xl` (36px) — base, targets mobile.
- `md:text-5xl` (48px) — tablet override.
- `lg:text-6xl` (60px) — desktop override.

`text-blue-500` — just highlights "Body". Brand color. Blue-500 is the middle shade — ideal for primary actions.

Paragraph:
```tsx
<p className="text-lg md:text-xl text-gray-300 max-w-2xl mx-auto mb-8">
  Join the best gym in town. Personal training, group classes, and
  nutrition plans — all under one roof.
</p>
```

- `text-gray-300` — light gray. Not pure white — more subtle, less emphasis than the heading.
- `max-w-2xl mx-auto` — caps width at 42rem, centers it. Paragraphs shouldn't stretch full width — readability drops.

### 3.5 "Two buttons — primary solid, secondary outline."

```tsx
<div className="flex gap-4 justify-center">
  <button className="bg-blue-600 hover:bg-blue-700 text-white px-8 py-3 rounded-lg font-semibold transition-colors">
    Get Started
  </button>
  <button className="border-2 border-white hover:bg-white hover:text-gray-900 text-white px-8 py-3 rounded-lg font-semibold transition-colors">
    Learn More
  </button>
</div>
```

**Primary (solid):** `bg-blue-600 hover:bg-blue-700` — the action button. Hover darkens it. But even without hover, it's clearly the primary action.

**Secondary (outline):** `border-2 border-white hover:bg-white hover:text-gray-900` — less prominent. On hover, it inverts — white background with gray text.

> **Senior dev rule:** Never put two equally prominent buttons side by side. One primary, one secondary. The user needs to know which one to click first.

## Common Mistakes (Senior Dev Blind Spots)

- **Forgetting `mx-auto`:** You'll add a container but forget `mx-auto`, and content stays left-aligned. Check every section — does `max-w-6xl` have `mx-auto`?
- **Missing `key` in map():** React throws a warning. Check DevTools. Static array → `index` is fine. Dynamic array → use a unique `id`.
- **Mobile-first confusion:** `md:` means "768px and above," not "on mobile." Base classes = mobile behavior. Breakpoints = overrides. `hidden md:flex` = hidden on mobile, flex on desktop.
- **Forgetting hamburger visibility:** Remember to hide the hamburger on desktop — `md:hidden` on the button. Forget it and the hamburger shows up on desktop too.
- **Data vs hardcode decision:** Three or more repetitive elements? Switch to array + `.map()`. Copy-paste is a trap.
- **Primary vs secondary button:** Two buttons side by side, both visually equal. Make one dominant, one subtle. The user needs to know what to click first.

## Summary (The Developer's Mental Model)

| Concept | Developer's Thought |
|---|---|
| Folder structure | `components/` — one file per component. `App.tsx` composes them. |
| Mobile-first | Base class = mobile. Breakpoint = override. Decide mobile first. |
| Container pattern | `max-w-6xl mx-auto px-4` — cap width, center, pad. Same everywhere. |
| Responsive grid | `grid-cols-1 md:grid-cols-2 lg:grid-cols-3` — mobile 1, tablet 2, desktop 3. |
| Responsive hide/show | `hidden md:flex` — hide on mobile, show on desktop. |
| State-based toggle | `useState` for menu visibility. CSS display toggles belong to React, not CSS. |
| Hover effects | Polish, not functionality. Mobile has no hover. |
| Data-driven UI | Repetitive elements → array + `.map()`. It scales. |
