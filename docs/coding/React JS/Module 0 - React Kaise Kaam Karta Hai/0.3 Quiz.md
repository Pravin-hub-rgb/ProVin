
## MCQ

Q: Reconciliation ka matlab kya hai?
A. React ka internal engine jo rendering ko pause aur resume karne deta hai
B. React ka process jo naye aur purane tree ko compare karta hai aur changes decide karta hai
C. React ka feature jo multiple state updates ko ek saath group karta hai
D. React ka syntax extension jo HTML-like code ko JavaScript mein compile karta hai
> B. Reconciliation means comparing old and new Virtual DOM trees to figure out what changed. It's the process that decides which real DOM nodes to update, not the engine (that's Fiber), not batching (that's... batching), and not compilation (that's Babel).

---

Q: Agar React do trees ko brute-force compare kare, toh time complexity kya hogi?
A. O(n) — matlab nodes ki count ke barabar comparisons
B. O(log n) — matlab nodes ki count ka logarithm
C. O(n²) — matlab nodes ki count ka square
D. O(n³) — matlab nodes ki count ka cube
> D. Brute-force tree comparison O(n³) hota hai — har node ko har node se compare karo. 1000 nodes ke liye 1 billion comparisons. Isliye React ne assumptions banakar O(n) mein laa diya.

---

Q: React ka diffing algorithm O(n) mein kaam karne ke liye kaun si assumptions banata hai?
A. Pehla — identical parent types ignore karo, doosra — text changes ko priority do
B. Pehla — different type poora tree rebuild karo, doosra — key prop stable identity deta hai
C. Pehla — sirf root element ka nested structure check karo, doosra — children ka type match karo
D. Pehla — har node ko doosre tree ke sabhi nodes se compare karo, doosra — depth limit 3 rakho
> B. React two assumptions: (1) Different type = completely different tree (destroy + rebuild), (2) `key` prop gives stable identity across re-renders. These assumptions make O(n³) → O(n).

---

Q: Parent element ka type div se span change ho jaye toh React kya karega?
A. Sirf parent ka tag name change karega, children untouched rahenge
B. Poore subtree ko destroy karega aur naya build karega
C. Div aur span dono block elements hain toh kuch nahi badlega
D. React error degi kyunki type change directly allowed nahi hai
> B. Jab parent type change hota hai, React purana poora subtree destroy kar deta hai aur naya build karta hai. Andar jo bhi components the (jaise `<Counter />`), unka state reset ho jayega.

---

Q: Same type ke elements mein React kya compare karta hai?
A. Sirf children ko compare karta hai, props ko ignore karta hai
B. Sirf text content ko compare aur update karta hai
C. Sirf props ko compare karta hai aur jo change hui unhe apply karta hai
D. Kuch nahi kyunki same type ke elements hamesha complete ignore kiye jaate hain
> C. Same type ke elements mein React sirf props compare karta hai aur jo props change hui hain, unhe real DOM mein update karta hai. DOM element destroy nahi hota, sirf properties update hoti hain.

---

Q: List items ko bina key ke render karne par React kaise compare karta hai?
A. Har item ke actual text content se compare karta hai
B. Har item ki array position ya index se compare karta hai
C. Har item ke HTML structure aur nesting pattern se compare karta hai
D. Randomly compare karta hai — koi fixed rule nahi hai iske liye
> B. Bina `key` ke React position/index se compare karta hai. Position 1 ka element ab kya hai, position 2 ka ab kya hai, etc. Items reorder ho jayein toh React galat elements ko update kar deta hai.

---

Q: `key` prop React ko kya information deti hai?
A. Element ko CSS mein kaise style karna hai
B. Element ko DOM tree mein kahan position karna hai
C. Element same hai ya alag hai across different renders
D. Element kab render karna hai aur kab skip karna hai
> C. `key` React ko stable identity deti hai — "ye element actually wahi hai jo pichli baar tha, sirf position badli hai." Bina key ke React position se compare karta hai jo bugs de sakta hai.

---

Q: `key` prop ke liye index kyun galat hai?
A. Kyunki index 0 se start hota hai aur React index 0 ko root treat karta hai
B. Kyunki index array position hai — list change par index bhi change ho jata hai
C. Kyunki index number hota hai jabki key string type ka hona chahiye
D. Kyunki index use karne par React performance warning deta hai lekin kaam sahi hota hai
> B. Index stable nahi hai. List se 'A' delete kiya toh jo pehle index 1 tha ('B'), ab index 0 ho jayega. React sochega ki index 0 wala element same hai — toh 'B' ko wo state mil jayegi jo 'A' ki thi. Index sirf static lists ke liye safe hai.

## TrueFalse

Q: React ka reconciliation process hamesha perfect hota hai — manually optimize karne ki kabhi zaroorat nahi padti.
- True
- False
> False. Reconciliation React ka "best-effort" hai. Complex cases mein manual optimization ki zaroorat pad sakti hai — jaise `React.memo` ya `useMemo` ka use. Reconciliation efficient hai, lekin perfect nahi.

---

Q: Agar koi list absolutely static ho (kabhi change nahi hoti, kabhi reorder nahi hoti), toh `key` ke liye index use karna safe hai.
- True
- False
> True. Static list mein items kabhi add/remove/reorder nahi hote — index stable rehta hai, koi shifting nahi hoti. Lekin jaise hi list dynamic hoti hai (delete/insert/reorder), index unsafe ho jata hai.

---

Q: Agar same type ke element ke sirf className change ho (jaise "old" se "new"), toh React poora DOM element destroy karke naya banata hai.
- True
- False
> False. Agar type same hai, React DOM element ko destroy nahi karta. Sirf jo props change hui hain (in this case className), unhe update karta hai. Element wahi purana hai, sirf uski properties badli hain.

---

Q: Fragment (`<>`) bhi React.createElement(React.Fragment) mein compile hota hai, isliye uski bhi reconciliation hoti hai.
- True
- False
> True. Fragment bhi ek React element hai — bas extra DOM node nahi banata. Toh reconciliation ke time React Fragment ka bhi type check karta hai. Agar Fragment → div change ho, toh subtree rebuild hoga.

## ShortAnswer

Q: React ka diffing algorithm O(n³) se O(n) mein kaise aaya? Do assumptions explain karo jo React banata hai.

<details>
<summary>Sample Answer</summary>

React do assumptions banata hai jo brute-force comparison (O(n³)) ko linear time (O(n)) mein badal dete hain:

**Assumption 1 — Different Type = Different Tree**
Agar parent element ka type change ho (div → span, ya ComponentA → ComponentB), toh React poora purana subtree destroy kar deta hai aur naya build karta hai. Is assumption ki wajah se React ko har node ko har doosri node se nahi compare karna padta — bas type dekhte hi decide ho jata hai.

**Assumption 2 — `key` Prop = Stable Identity**
Same type ke elements mein `key` se React ko pata chal jata hai ki kaunsa element actually same hai across re-renders. Agli baar jab same type ka element with same key dikhe, React samajh leta hai "ye wahi element hai" — chahe position change ho gayi ho. Is assumption ki wajah se lists mein React ko har item ko content se nahi compare karna padta.

In dono assumptions ki madad se React O(n) mein kaam kar leta hai — 1000 nodes ke liye sirf 1000 comparisons.

</details>

Q: List ke items mein `key` prop na dene par kya problem hoti hai? Example ke saath explain karo.

<details>
<summary>Sample Answer</summary>

Bina `key` ke React position (index) se compare karta hai. Iski wajah se list change hone par bugs aate hain.

**Example — List reorder:**

Before:
```
<ul>
  <li>Apple</li>     // position 1
  <li>Mango</li>     // position 2
  <li>Banana</li>    // position 3
</ul>
```

After (Banana pehle aa gaya):
```
<ul>
  <li>Banana</li>    // position 1 — pehle Apple tha
  <li>Apple</li>     // position 2 — pehle Mango tha
  <li>Mango</li>     // position 3 — pehle Banana tha
</ul>
```

Bina key ke: React position se compare karega → 3 updates (har position ka text badal gaya).
`key` ke saath: React key se pata laga lega ki elements same hain, sirf order change hua → 0 updates, sirf reorder.

**Example — Input field state bug:**

Agar list mein input fields hain:
```
<li key={index}><input /></li>  // ['A', 'B', 'C']
```
'A' delete karne par ['B', 'C'] — jo input state 'A' ki thi, wo 'B' ko transfer ho jayegi kyunki index 0 ab 'B' ka hai.

Isliye stable, unique `key` chahiye — jaise `item.id`.

</details>
