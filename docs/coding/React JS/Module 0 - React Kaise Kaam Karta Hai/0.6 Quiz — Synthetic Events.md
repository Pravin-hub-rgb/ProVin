
## MCQ

Q: When you write `<button onClick={handleClick}>` in React, how is the event listener actually attached?
A. React directly injects `onclick` into each button's HTML attributes
B. React attaches a listener at the root element and catches events through bubbling
C. React calls `addEventListener` for each button at build time
D. React attaches event listeners server-side, the client never receives them
> B. React doesn't add a separate `addEventListener` to every button. It attaches a single listener at the root element (`<div id="root">`). When a button is clicked, the event bubbles up to the root, and React determines which component's `onClick` handler should fire.

Q: What is the difference between Native Event and SyntheticEvent?
A. Native Event is created by React, SyntheticEvent is from the browser — both work the same
B. Native Event is the browser's original event, SyntheticEvent is React's wrapper for cross-browser consistency
C. Native Event is only server-side, SyntheticEvent is only client-side
D. Native Event and SyntheticEvent are the same thing — just different names
> B. Native Event is the browser's original event (received via `addEventListener`). SyntheticEvent is React's wrapper object built on top of the native event — `event.target`, `event.preventDefault()` all work the same across browsers. That's what SyntheticEvent ensures.

Q: Why did React create its own SyntheticEvent system?
A. Because the browser's native events are too slow
B. Because React needed its own events that also work on the backend
C. Because different browsers behaved differently for the same event — for cross-browser consistency
D. Because the browser doesn't support `addEventListener`
> C. In older browsers, the same event behaved differently — some had `event.target`, others had `event.srcElement`. React created SyntheticEvent so that developers get the same properties in every browser. Just like jQuery provided cross-browser consistency, React's SyntheticEvent does the same.

Q: What does "Event Delegation" mean?
A. React creates a separate listener for each element and prioritizes them
B. React keeps a single listener at the root element and determines which component the event is for
C. React delegates server-side events to client-side components
D. React copies event listeners from child components to parent components
> B. Event Delegation means React doesn't call `addEventListener` for every button or input. It keeps a single listener at the root element (`<div id="root">`). When an event bubbles up to the root, React identifies which component's handler to invoke. This is memory-efficient.

---

Q: What does "Event Bubbling" mean?
A. The event travels from the parent element to the child element
B. The event travels from the child element to the parent element
C. The event stays on a single element — it doesn't travel
D. The event visits all elements in random order
> B. Event Bubbling is the browser's mechanism where an event fires first on the target element, then travels up to its parent, then to the parent's parent, all the way to the root. React's Event Delegation takes advantage of this bubbling behavior.

---

Q: What does `event.nativeEvent` give you in a SyntheticEvent?
A. React's internal state object
B. The browser's original native event object
C. The component's props object
D. A reference to the DOM element that triggered the event
> B. Inside a SyntheticEvent, the `nativeEvent` property contains the browser's original native event object (like MouseEvent, KeyboardEvent). SyntheticEvent is the wrapper; `nativeEvent` is the actual browser event. Usually SyntheticEvent's own properties are enough, and `nativeEvent` is rarely needed.

Q: What was Event Pooling?
A. Storing event objects in a database for later use
B. Clearing SyntheticEvent objects after the handler for reuse in future events
C. Grouping multiple events together to handle with a single listener
D. Queuing events and processing them in a separate thread
> B. Event Pooling was a React 17 optimization. After an event handler finished, React would clear the SyntheticEvent object (set all properties to null) and reuse it for future events. This reduced memory allocation, but broke asynchronous code where the event had already been cleared.

---

Q: What did `event.persist()` do in React 17?
A. Permanently attached the event to the DOM
B. Removed the SyntheticEvent from the pool so it wouldn't be cleared
C. Created a separate version of the event handler for each browser
D. Saved the event's properties to localStorage
> B. `event.persist()` in React 17 removed the SyntheticEvent from the event pool. This meant React wouldn't clear the object, so asynchronous code (setTimeout, Promise) could safely access it. React 18 removed pooling, so `persist()` is no longer needed.

## TrueFalse

Q: Event Bubbling and Event Delegation are both React concepts — the browser has no role in them.
- True
- False
> False. Event Bubbling is a browser mechanism — the event travels from the child up to the parent. Event Delegation is React's technique that takes advantage of this browser behavior. Without the browser's bubbling mechanism, Event Delegation wouldn't be possible.

---

Q: In React 18, SyntheticEvent behaves like a normal JavaScript object — asynchronous code can access it freely.
- True
- False
> True. React 18 removed event pooling. Now each event gets its own SyntheticEvent object that stays in memory until garbage-collected. So you can access events in setTimeout, Promise, async/await — no `persist()` needed.

---

Q: If you use `addEventListener` instead of React's event system, you still get SyntheticEvent.
- True
- False
> False. SyntheticEvent is only available in React's event handlers (`onClick`, `onChange`, `onSubmit`, etc.). If you use `addEventListener` directly, you get the browser's native event — not SyntheticEvent. That's why React's event system is recommended.

---

Q: In React 17, event pooling caused problems even in synchronous code.
- True
- False
> False. Event pooling only caused problems in asynchronous code — setTimeout, Promise, async/await. In synchronous code, the handler finishes before the event is cleared, so all properties are accessible. The problem only occurred when accessing the event after the handler had already finished.

## ShortAnswer

Q: Explain the full flow of a click event in React — from the user clicking a button to your `onClick` handler running. Include Event Delegation and Bubbling.

<details>
<summary>Sample Answer</summary>

**Step-by-step flow:**

1. The user clicks a button inside a React app
2. The browser generates a native click event
3. The event bubbles up — button → div → body → document → root (`<div id="root">`)
4. React's single event listener at the root catches this event
5. React identifies: "which component did this click come from? which `onClick` handler should fire?"
6. React wraps the native event into a SyntheticEvent object (cross-browser consistent)
7. The SyntheticEvent is passed to your `onClick` handler
8. Your handler runs with `event.target`, `event.preventDefault()`, etc. available

**Event Delegation:** React doesn't add a listener to every button. One listener at the root handles all events. This is efficient — 1000 buttons still means just 1 listener, not 1000.

**Event Bubbling:** This is what makes delegation possible. Without bubbling, the root would never know about a button click.

</details>

Q: What was Event Pooling in React 17, what problem did it cause, and what changed in React 18?

<details>
<summary>Sample Answer</summary>

**Why pooling existed (React 17):**
It was a memory optimization. Instead of creating a new SyntheticEvent object for every click, React reused one object. Once the handler finished, React would null out all the object's properties and use it again for the next event.

**The problem:**
If you accessed the event in asynchronous code (setTimeout, Promise), the object had already been cleared — all properties were null.

```jsx
function handleClick(event) {
  setTimeout(() => {
    console.log(event.type); // ❌ null — object already cleared
  }, 1000);
}
```

**The workaround was `persist()`:**
```jsx
event.persist(); // Remove object from the pool
```

**What changed in React 18:**
Modern JavaScript engines are fast enough that pooling isn't needed. React 18 removed pooling — each event now gets its own SyntheticEvent object that stays in memory until garbage-collected. Asynchronous code works without `persist()`.

</details>
