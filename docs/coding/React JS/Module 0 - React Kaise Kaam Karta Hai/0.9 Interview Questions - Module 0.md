### 1. What is React, and why do we need it?

**Answer:** A JavaScript library for building UIs through components. It solves manual DOM manipulation and state-UI sync by being declarative — you describe what the UI looks like for each state, and React updates the DOM efficiently.

**Likely follow-up:** *What problems does it solve?* — manual DOM manipulation (error-prone/slow), keeping UI in sync with state, reusable components, efficient updates via the Virtual DOM.

---

### 2. What is an SPA (Single-Page Application)?

**Answer:** The browser loads the app once; after that, navigation and UI updates happen client-side — the URL changes, the component swaps, no new HTML document is fetched. That's why it feels app-like.

**Likely follow-up:** *Is React an SPA?* — No. React is a UI library; you add React Router to build an SPA with it.

---

### 3. What are React's main features and advantages?

**Answer:** Components (reusable pieces), Virtual DOM (fast updates), declarative style (no manual DOM poking), unidirectional data flow (predictable), hooks (state in functions), and a rich ecosystem (routing, state, testing).

**Likely follow-up:** *Which one matters most for performance?* — the Virtual DOM + reconciliation, which patches only what changed.

---

### 4. Library or framework — which is React?

**Answer:** A library. It only owns the UI layer — routing, state management and HTTP calls need external tools (React Router, Redux/Zustand, fetch/Axios). Angular is a framework: opinionated, everything built in.

**Likely follow-up:** *So what does a full React app need?* — React Router for routes, a state tool for shared state, and a data layer (fetch or TanStack Query).

---

### 5. What is the Virtual DOM?

**Answer:** A lightweight in-memory copy of the real DOM. When state changes, React updates the Virtual DOM, diffs it against the previous version, and applies only the changed parts to the real DOM — avoiding expensive full-DOM operations.

**Likely follow-up:** *Real DOM vs Virtual DOM?* — direct manipulation/slow vs declarative/targeted/fast; browser-native object vs plain JS object.

---

### 6. What is Reconciliation?

**Answer:** The diffing algorithm that compares the old and new trees in two phases — render (compute what changed) and commit (apply it to the DOM). Heuristics: different types → full replace, same type → update attributes/children, same type + key → reuse the instance.

**Likely follow-up:** *Why do keys matter here?* — they let React match list items across renders; without them it guesses by position.

---

### 7. How does React update the UI when state or props change?

**Answer:** A state setter, new props, or a parent re-render triggers a re-render → React builds a new Virtual DOM → diffs it → patches only the changed DOM nodes, batching multiple updates into one pass.

**Likely follow-up:** *Is the whole app re-rendered?* — No, only the component (and its children); the DOM changes are minimal and batched.

---

### 8. What is React Fiber?

**Answer:** React's reconciliation engine since React 16. It splits rendering work into small units that can be interrupted, so urgent updates (typing) don't wait behind low-priority work (rendering a huge list) — the foundation of concurrent rendering.

**Likely follow-up:** *What does Fiber enable?* — transitions, Suspense, and priority-based rendering (covered in 0.4).

---

### 9. What is JSX?

**Answer:** JavaScript XML — HTML-like syntax inside JavaScript. Babel compiles it into `React.createElement()` calls at build time, which produce plain objects; browsers never see JSX.

**Likely follow-up:** *Can a browser run JSX directly?* — No; it must be compiled first (that's what Vite/Babel do).

---

### 20. What are Synthetic Events?

**Answer:** React's cross-browser wrapper around native DOM events giving one consistent API everywhere. Since React 17 they're attached to the root container (event delegation), not `document`.

**Likely follow-up:** *Why attach to the root instead of document?* — memory efficiency and multiple React versions can coexist on one page.

---

### 73. How is event delegation implemented in React?

**Answer:** All events attach to a single root DOM container rather than each element (or `document`). One listener serves the whole tree — memory-efficient, and it lets multiple React versions run on the same page.

**Likely follow-up:** *Which version changed this?* — React 17 (before that, events lived on `document`).

---

### 84. What are Server Components?

**Answer:** Components that render on the server and send only the resulting HTML/data to the client — shrinking the client JS bundle and allowing direct backend access without a separate API layer. They can't hold event handlers or interactivity.

**Likely follow-up:** *So where do click handlers live?* — in Client Components imported by (or importing) Server Components.

---

### 85. Server Components vs Client Components?

**Answer:** Server Components (default in Next.js App Router): no hooks, no interactivity, smaller bundle. Client Components (`'use client'`): interactive — hooks, state, effects — and they hydrate in the browser.

**Likely follow-up:** *Which can import which?* — a Server Component can render a Client Component; a Client Component cannot make a Server Component interactive.

---

### 86. What are React 19 Actions?

**Answer:** Async functions that handle form submissions and mutations, automatically managing pending, error and optimistic states — wired into `useActionState` and `useOptimistic`, eliminating manual loading-state boilerplate.

**Likely follow-up:** *How do you use one?* — pass it to `<form action={...}>` or call it from an event handler.

---

### 87. What does `useActionState` do?

**Answer:** Tracks a form action's result, pending state and errors in a single hook — replacing multiple `useState` calls for loading, error and data.

**Likely follow-up:** *How is it different from `useState`?* — it's bound to an async action and reports its status, not just a value you set.

---

### 88. What does `useOptimistic` do?

**Answer:** Shows a predicted final state before the async action completes (a like button fills instantly), and rolls back automatically if the action fails.

**Likely follow-up:** *When should you NOT use it?* — when the optimistic UI would mislead (payments, irreversible actions).

---

### 89. What is the `use` hook?

**Answer:** Reads a Promise or Context directly during render — the component suspends until the promise resolves (integrates with Suspense). Unlike other hooks, it can be called conditionally, even inside loops.

**Likely follow-up:** *How is it different from `useContext`?* — `useContext` reads a value synchronously; `use()` also works with promises and is the one condition-callable hook.

---

### 90. What are Server Actions?

**Answer:** Async functions marked with `'use server'` that the client can call directly (through a form action or event handler) without manually building an API route — React's RPC layer handles the communication.

**Likely follow-up:** *Where do they execute?* — on the server, close to your data and secrets.

---

### 91. What is Hydration?

**Answer:** The process of making server-sent static HTML interactive on the client by attaching event listeners — without re-rendering the HTML. React 19 improves mismatch reporting and partial/streaming hydration.

**Likely follow-up:** *What causes hydration errors?* — server and client output mismatch, e.g. `Date.now()` rendered during SSR (fix with `useEffect`).

---

### 92. What is the difference between CSR and SSR?

**Answer:** CSR renders in the browser from the JS bundle — slower first paint, SEO waits for JS. SSR sends HTML with data already inside — fast first paint, SEO-friendly — then hydrates for interactivity.

**Likely follow-up:** *Which for which app?* — SSR for marketing/SEO pages, CSR for dashboards and app-heavy UIs.

---

### 98. What does Strict Mode do?

**Answer:** A development-only wrapper that double-invokes renders to surface bad side effects, warns about deprecated APIs and adds extra checks. It has no effect in production builds.

**Likely follow-up:** *Why doesn't it double-fire in prod?* — it only activates in development builds.

---

### 105. What is batching in React?

**Answer:** Combining multiple `setState` calls into a single re-render. React 18+ batches everywhere — promises, `setTimeout`, native handlers — where before it only happened inside React event handlers.

**Likely follow-up:** *Does batching change the values?* — No; every update still applies in order, there are just fewer renders.

---

### 108. What are ref cleanup functions in React 19?

**Answer:** A ref callback can now return a cleanup function — like `useEffect` — that runs when the element unmounts or the ref changes, replacing manual `ref.current = null` assignments.

**Likely follow-up:** *How does it compare to effect cleanup?* — same lifecycle: setup, then cleanup before the next run and on unmount.

---

### 111. Why is TypeScript popular with React in interviews?

**Answer:** Compile-time type safety, better autocomplete, explicit prop/state shapes and safer refactoring in large codebases — senior roles expect TypeScript fluency.

**Likely follow-up:** *What does it catch that PropTypes can't?* — everything at compile time, plus generics and whole-app refactors; PropTypes is runtime and dev-only.

---

### 115. What should "React internals" interview answers cover?

**Answer:** The Fiber architecture (interruptible rendering), the reconciliation/diffing algorithm (O(n) heuristics on type and key), the render vs commit phases, and a mental model of concurrent features (transitions, Suspense).

**Likely follow-up:** *Explain render vs commit.* — render computes the diff with no DOM writes; commit applies it to the real DOM.

---

### 119. What is hoisting in JS?

**Answer:** The engine's habit of moving declarations to the top of their scope during the memory-creation phase — which is why you can call a function before the line where it's declared.

**Likely follow-up:** *Is it the same as physically moving code?* — No; only declarations are hoisted, not assignments.

---

### 120. How does hoisting work?

**Answer:** In the compile/memory phase, declarations get registered in scope first; execution happens after. Function declarations hoist fully, `var` hoists as `undefined`, and `let`/`const` hoist but stay inaccessible until their line (the TDZ).

**Likely follow-up:** *What's the TDZ?* — temporal dead zone: accessing a `let`/`const` before its declaration throws a `ReferenceError`.

---

### 121. Does hoisting work with all variables?

**Answer:** No. Function declarations hoist fully; `var` hoists as `undefined`; `let`/`const` are hoisted but blocked until their declaration line (TDZ) — and `const` can't be reassigned at all.

**Likely follow-up:** *What happens if you use a `let` before its line?* — `ReferenceError` (TDZ), not `undefined`.

---

### 122. Difference between `let` and `var`?

**Answer:** `let` is block-scoped (braces create scope), doesn't allow redeclaration, and has no initialization hoisting. `var` is function-scoped, hoists as `undefined`, and allows redeclaration — use `let`/`const` by default.

**Likely follow-up:** *And `const`?* — same as `let` but reassignment is forbidden (object contents can still mutate).

---

### 126. Which ES6 features have you used?

**Answer:** Arrow functions, `let`/`const`, template literals, destructuring, spread/rest, Promises, classes, `import`/`export` modules, `Map`/`Set`, `for...of` — the everyday set. Answer with where you used them in a project.

**Likely follow-up:** *Which do you use most?* — destructuring and spread for props/arrays (name the project).

---

### 127. Where do you mostly use the rest operator?

**Answer:** Collecting remaining function arguments (`function f(...args)`), destructuring leftovers (`const { a, ...rest } = obj`), and merging arrays/objects (`[...arr]`, `{ ...obj }`).

**Likely follow-up:** *Rest vs spread?* — same `...` syntax: rest **collects**, spread **expands**.

---

### 128. What is the difference between `package.json` and the lock file (`bun.lock` / `package-lock.json`)?

**Answer:** `package.json` is the wish list - it declares dependencies with ranges (`react: ^19.3.1` means "19.3.1 or any compatible newer version"). The lock file is auto-generated at install time and records the **exact** versions that actually got downloaded. For example: `zod: ^4` in `package.json` is a hint - "version 4 or greater" - but the lock file pins exactly which one, say `4.1.23`, to the dot. The next `install` reads the lock file, so every teammate gets the identical tested versions - reproducible installs. Never edit a lock file by hand; do commit it to git.

**Likely follow-up:** *Can you delete the lock file?* - yes, it regenerates on the next install. The recipe lives in `package.json`; the lock file is just the receipt of what was actually cooked.

---

### 129. Your project has both `package-lock.json` and `bun.lock` - what happened, and what do you fix?

**Answer:** Two package managers ran in the same project - someone used `npm install` and later someone used `bun install` (or vice versa). Both created their own lock file, so the "one manager = one lock file" guarantee is broken and installs may not be reproducible across machines. Fix: pick one manager for the project, delete the other's lock file and the `node_modules` folder, and run a fresh `install` with the chosen manager.

**Likely follow-up:** *Which lock file belongs to which tool?* - npm creates `package-lock.json`, Bun creates `bun.lock`, pnpm creates `pnpm-lock.yaml`.
