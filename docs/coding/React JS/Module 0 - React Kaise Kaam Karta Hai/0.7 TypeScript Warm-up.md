In 0.6, we finished Module 0's theory section — from the Virtual DOM to Events, React's internal model is clear. But before we start writing React code with TypeScript, one thing needs to be settled — **what is TypeScript and how does it work?**

The good news: if you already know JavaScript, 80% of TypeScript will feel familiar. It just adds an extra layer of types on top. This chapter's goal isn't to cover the entire TypeScript language. We'll only learn the TypeScript features that are **immediately** needed for writing React. Advanced concepts (Generics, advanced types) come up naturally later.

## Setup — How to Run TypeScript

TypeScript cannot run directly in Node.js or the browser. It must be **compiled** (transpiled) to plain JavaScript first. Here is the basic setup:

### Step 1 — Install TypeScript

```bash
npm install -g typescript
# bun: bun add -g typescript
```

Or use `npx` without installing globally:

```bash
npx tsc --version
```

### Step 2 — Create your TypeScript file

Create `main.ts`:

```ts
function add(a: number, b: number): number {
  return a + b;
}

console.log(add(5, "10"));
```

### Step 3 — Compile with `tsc`

Run the TypeScript compiler:

```bash
tsc main.ts
```

This does two things:
1. **Type checks** — If there is a type error (like passing `"10"` where `number` is expected), `tsc` prints an error and stops. **No `.js` file is created.**
2. **Transpiles** — If there are no errors, it creates `main.js` with the types stripped out.

### Step 4 — Run with Node

```bash
node main.js
```

This runs the compiled JavaScript. Node.js never sees your TypeScript code — it only sees the plain JavaScript output.

## Why Type Errors Don't Show at Runtime

This is the most important thing to understand:

**TypeScript types exist only at development time. They are erased when the code is compiled to JavaScript.**

Your code:

```ts
function add(a: number, b: number): number {
  return a + b;
}
add(5, "10");
```

After `tsc` compiles it (if you bypass the error), the JavaScript looks like this:

```js
function add(a, b) {
  return a + b;
}
add(5, "10");
```

The `: number` annotations are gone. At runtime, JavaScript sees `5 + "10"` and performs string coercion, producing `"510"`. **No error.**

This is why:

| Step | What Happens | Type Error? |
|------|-------------|-------------|
| `tsc main.ts` | TypeScript checks types | ✅ Catches `string` is not assignable to `number` |
| `node main.js` | Node runs plain JavaScript | ❌ No type checking — runs as JavaScript |

**Always run `tsc` first.** If `tsc` reports errors, fix them before running `node`. TypeScript's job is to catch mistakes before your code runs — not while it runs.

## What is TypeScript?

TypeScript = JavaScript + Types. That's the only difference.

```js
// JavaScript — no type checking
function add(a, b) {
  return a + b;
}
add(5, "10"); // "510" — a bug, but JavaScript doesn't care
```

```ts
// TypeScript — types defined
function add(a: number, b: number): number {
  return a + b;
}
add(5, "10"); // ❌ Error — string is not assignable to number
```

TypeScript catches errors **at development time** — before the code ever reaches the browser.

## Basic Types

```ts
let name: string = "Vin";
let age: number = 25;
let isLearning: boolean = true;
```

`string` for text, `number` for numbers, `boolean` for true/false. The type comes after a colon (`:`) on each line.

## Type Inference

TypeScript is smart enough to **infer the type from the value itself**. When you assign a value right away, you don't need to write the type annotation:

```ts
let name = "Vin";        // TypeScript automatically infers: string
let age = 25;            // number
let isLearning = true;   // boolean
```

TypeScript guessed the type from the value. This is called **Type Inference**.

### When do you need to write annotations?

When a variable is **declared without a value** — assigned later:

```ts
let name: string;  // Need to specify the type — no value to infer from
name = "Vin";      // Value comes later, but the type is already set
```

And **function parameters** always need annotations:

```ts
function greet(name: string) { ... }  // Need to specify the parameter type
```

The reason: when you define a function, you don't know what value the parameter will receive — that comes later when someone calls the function (`greet("Vin")`). TypeScript has no value to infer from, so you have to specify the type.

### Rule of Thumb

| Scenario | Type annotation needed? | Example |
|----------|------------------------|---------|
| Variable + value assigned | ❌ Optional (inferred) | `let name = "Vin"` |
| Variable declared, value later | ✅ Required | `let name: string` |
| Function parameter | ✅ Required | `(name: string) =>` |
| Function return type | ❌ Optional (inferred) | `function sum(a, b) { return a + b }` |
| Interface / object property | ✅ Required | `{ name: string }` |

> **In React:** Component props and interfaces are always written with type annotations (they're just shapes, no values). But local variables inside a component — like `const name = "Vin"` — you can let inference handle them. Professional codebases follow this pattern too.

## Arrays

```ts
let numbers: number[] = [1, 2, 3];
let fruits: string[] = ["apple", "mango", "banana"];
```

`number[]` means — **this variable is an array, and every element must be of type `number`.**

Allowed:
```ts
numbers.push(4);
numbers.push(10);
```

Not allowed:
```ts
numbers.push("hello"); // ❌ Error — the array only accepts numbers
```

> **Note:** This same type can also be written as `Array<number>`. They mean exactly the same thing. But `Array<number>` is a **Generic** syntax — we'll cover that later. For now, stick with `number[]`.

## Objects

```ts
let user: { name: string; age: number } = {
  name: "Vin",
  age: 25,
};
```

Define the type of each property in the object. If you assign a wrong type, TypeScript errors:

```ts
user.age = "twenty-five"; // ❌ Error — expected number, got string
```

## Functions

```ts
// Parameter types + return type
function add(a: number, b: number): number {
  return a + b;
}

// TypeScript can infer the return type too
function multiply(a: number, b: number) {
  return a * b; // TypeScript automatically understands: return type is number
}
```

Write the type after the parameter name using a colon. The return type goes after the closing parenthesis with `): type`.

### React component return type — `JSX.Element` is optional

When you write a React component that returns JSX, you **do not need** to write `: JSX.Element` as the return type. TypeScript infers it automatically:

```tsx
// ✅ No explicit return type needed — TypeScript infers JSX.Element automatically
function ProfileCard() {
  const name = "Vin";
  const role = "React Developer";

  return (
    <div>
      <h2>{name}</h2>
      <p>{role}</p>
    </div>
  );
}
```

**`JSX.Element` comes from `@types/react`**, not from JavaScript itself. If TypeScript says:

```
Cannot find namespace 'JSX'.
```

it means `@types/react` isn't being loaded in your `tsconfig.json`. This commonly happens when `tsconfig.json` has a `types` array like `"types": ["vite/client"]` — that restricts TypeScript to only those packages and skips `@types/react`.

**Fixes:**
1. **Remove the return type** — just write `function ProfileCard() { ... }`. TypeScript infers `JSX.Element` automatically. This is the modern React + TypeScript convention.
2. **Or explicitly import the type:**
   ```tsx
   import type { JSX } from "react";
   function ProfileCard(): JSX.Element { ... }
   ```
3. **Or add `"react"` to your `tsconfig.json` `types` array:**
   ```json
   "types": ["vite/client", "react"]
   ```

React 19 does ship `JSX.Element` in `@types/react`, but it still needs to be loaded by TypeScript's config — it's not a built-in JavaScript keyword.

## Optional Properties

```ts
function greet(name: string, greeting?: string): string {
  return `${greeting || "Hello"}, ${name}`;
}
```

The question mark (`?`) means — this parameter is optional. If not passed, it's `undefined`.

This works for object properties too:

```ts
let user: { name: string; age?: number } = {
  name: "Vin",
  // age is optional, so this is valid
};
```

## Union Types

**Union** means "combination" — combining two or more types into one. When a variable in TypeScript has the type `string | number`, it means the variable can hold **either a string or a number** — not both at once, just one value, but that value can be of either type.

### Syntax

```
let variableName: Type1 | Type2 | Type3 = value;
```

The `|` symbol is a **pipe** (or pipe operator). "Pipe" means **"or" (OR)** — it works at the type level. The type on the **left** **or** the type on the **right** — both are valid.

```ts
let id: string | number = "abc123";
id = 456; // ✅ valid — number is also valid
id = true; // ❌ Error — boolean is not part of the union
```

`string | number` — `id` is a string here, but could be a number on the next line. Both work because both are in the union. `boolean` is not in the union, so it errors.

## Interface

An **Interface** defines the shape of an object — what properties it will have and what type each is:

```ts
interface User {
  name: string;
  age: number;
}

let user: User = {
  name: "Vin",
  age: 25,
};
```

An interface defines the **shape** of an object — what properties it will have and what type each is:

```ts
interface User {
  name: string;
  age: number;
}

let user: User = {
  name: "Vin",
  age: 25,
};
```

An interface defines the shape of an object — what properties an object must have and what type each property is. For example, `interface User { name: string; age: number; }` means any object typed as `User` must have `name` (string) and `age` (number).

```
Interface — shape of an object
     │
     ▼
{
  name: string;
  age: number;
}
     │
     ▼
let user: User = {
  name: "Vin",   // ✅ string
  age: 25        // ✅ number
};
```

If you pass the wrong type, TypeScript errors:

```ts
let user: User = {
  name: "Vin",
  age: "twenty-five", // ❌ Error — expected number, got string
};
```

You'll use interfaces regularly in React to **define component props**. So get familiar with them now.

**In Your Own Words**

1. How is TypeScript different from JavaScript? Give an example.

<details>
<summary>Sample Answer</summary>

**Answer:** In JavaScript, function parameters don't need types — you write `function add(a, b)` and can pass anything. In TypeScript, you define the types — `function add(a: number, b: number): number`. If someone calls `add(5, "10")`, TypeScript throws an error. This catches bugs during development, not in production.

</details>

2. What does `number[]` mean? Why isn't `Array<number>` confusing?

<details>
<summary>Sample Answer</summary>

**Answer:** `number[]` means "an array where every element is a `number`." `Array<number>` is exactly the same — just different syntax. `Array<number>` is a Generic syntax that we'll cover later. For now, use `number[]`. Both represent "array of numbers."

</details>

3. What is an Interface? Give a real-world example.

<details>
<summary>Sample Answer</summary>

**Answer:** An interface defines the shape of an object — what properties it has and what type each is. For example: `interface User { name: string; age: number; }` — now any object typed as `User` must have those exact properties with those exact types.

</details>

4. What is Type Inference? When can you skip the type annotation?

<details>
<summary>Sample Answer</summary>

**Answer:** Type Inference means TypeScript automatically figures out the type from the assigned value, without you writing it explicitly. When you immediately assign a value — `let name = "Vin"` — TypeScript infers that `name` is a `string`. You can skip the annotation. But when a variable is declared without a value (`let name: string`), or when it's a function parameter (`function greet(name: string)`), you need to write the annotation because there's no value to infer from.

</details>

5. When do you use union types? Show an example.

<details>
<summary>Sample Answer</summary>

**Answer:** Union types are used when a value could be one of several types. Example: `let id: string | number` — the `id` could be a string ("abc123") or a number (456). The pipe `|` means "or" at the type level. If you try to assign a `boolean`, TypeScript errors because it's not in the union.

</details>
