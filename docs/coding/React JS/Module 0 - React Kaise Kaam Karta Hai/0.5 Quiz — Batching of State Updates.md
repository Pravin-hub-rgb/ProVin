
## MCQ

Q: What does "state batching" mean?
A. Every setState call independently triggers its own component re-render
B. Grouping multiple setState calls into a single re-render
C. Delaying state updates so the browser gets processing time
D. Saving state to localStorage so it survives page refresh
> B. Batching means React groups multiple state updates together and performs a single re-render instead of one per setState call. This improves performance and avoids showing inconsistent intermediate states to the user.

---

Q: In React 17, where did batching automatically apply?
A. Only inside event handlers — onClick, onChange, onSubmit, etc
B. Inside setTimeout and setInterval callbacks
C. Inside Promise chains and async/await functions
D. Inside native DOM event listeners (addEventListener)
> A. In React 17, batching only happened inside event handlers. `setTimeout`, Promises, and native events were not batched — each `setState` triggered its own separate re-render.

---

Q: How does React 18's "Automatic Batching" differ from React 17?
A. React 18 only batches click events, React 17 batched everywhere
B. React 18 removed batching — each setState now triggers a separate render
C. React 18 batches everywhere — event handlers, setTimeout, Promises, native events
D. There is no difference — both work the same way
> C. In React 17, batching was limited to event handlers. React 18's "Automatic Batching" means batching happens everywhere — `setTimeout`, Promises, async/await, and native event listeners all batch now. In React 17, those places each `setState` triggered a separate render.

---

Q: When there are two setState calls inside an event handler, what does React do internally?
A. The first setState is processed immediately, then the second — two separate renders
B. Both updates are stored in a queue and processed together when the handler completes
C. Only the first setState is kept, the second is ignored
D. A new thread is spawned and both updates are processed in parallel
> B. React doesn't process updates immediately. It stores them in an internal queue. When the current execution context (the event handler, the `setTimeout` callback) completes, React processes the queue — all updates at once, in a single re-render.

---

Q: What does the `flushSync` function do?
A. Delays state updates so the browser can finish its current render
B. Breaks batching — the update is processed immediately
C. Cancels all pending state updates
D. Saves state updates to a file for debugging
> B. `flushSync` is a React 18 function that breaks batching. Any `setState` calls inside it are processed immediately — each triggers a separate render immediately. It's used in rare cases where you need to read DOM state after an update (`scrollHeight`, `getBoundingClientRect()`).

---

Q: What is the most important benefit of batching?
A. The code becomes easier to write since setState syntax is simpler
B. The component's state is automatically saved to localStorage
C. Multiple state updates are applied at once — the user never sees a half-updated UI
D. setState can be written without curly braces — less boilerplate
> C. Batching ensures all updates are applied together. Without batching, if there are two `setState` calls, the first update renders (partial UI), then the second update renders. The user could see the half-updated UI between renders. Batching keeps the UI always consistent.

Q: In React 17, if there are two setState calls inside a setTimeout, what happens?
A. Two separate re-renders happen since setTimeout is not batched in React 17
B. A single re-render happens since batching is available everywhere in React 17
C. Both setState calls are ignored because setTimeout is outside React
D. Only the first setState executes, the second throws an error
> A. In React 17, batching only happened inside event handlers (onClick, onChange). `setTimeout`, Promises, and async/await were not batched — each `setState` triggered its own separate re-render. That's why React 18 introduced "Automatic Batching."

Q: In the context of batching, what does "inconsistent intermediate state" mean?
A. The state type changes from number to string mid-render
B. Some updates have been applied but others haven't — the user sees a half-updated UI
C. The component's state conflicts with another component's state
D. The browser's memory state differs from the actual DOM state
> B. Without batching, each `setState` triggers a separate render. If you have two `setState` calls, the first update renders (state is partially updated), but the second update hasn't applied yet — the user sees an incomplete UI. Batching ensures all updates are applied together.

## TrueFalse

Q: In React 18, batching only happens inside event handlers — setTimeout and Promises are not batched.
- True
- False
> False. React 18 introduced "Automatic Batching" — batching now happens everywhere: event handlers, `setTimeout`, `setInterval`, Promises, async/await, and native event listeners. React 17 had this limitation, but React 18 removed it.

---

Q: Using flushSync improves performance since updates are processed immediately instead of waiting for batching.
- True
- False
> False. `flushSync` breaks batching — each `setState` triggers a separate render. This hurts performance since multiple renders are triggered. Use `flushSync` only in rare cases where you need to read DOM state after an update. In general, batching is the better approach.

---

Q: Batching is only a performance feature — it has no effect on UI consistency.
- True
- False
> False. Batching ensures two things — performance (fewer renders = less work) and consistency (multiple updates are applied at once; the user never sees a half-updated state). Without batching, if an event handler has two `setState` calls, the first update renders before the second is applied, showing an incomplete UI.

---

Q: If there are 5 setState calls inside an event handler, React triggers 5 separate re-renders, one per setState.
- True
- False
> False. React batches all 5 state updates — they're applied in a single re-render. Whether there are 5 or 50 `setState` calls, there's only one render at the end of the event handler. That's the core concept of batching — group first, process together.

## ShortAnswer

Q: What's the difference between React 17 and React 18 batching? Explain with an example.

<details>
<summary>Sample Answer</summary>

**React 17:** Batching only happened inside event handlers (onClick, onChange, onSubmit). Everywhere else — `setTimeout`, `setInterval`, Promises, async/await, native event listeners — each `setState` triggered its own separate re-render.

```jsx
// React 17
function handleClick() {
  setCount(c + 1);
  setText("Clicked");
  // ✅ Single render — batching happens inside event handlers
}

setTimeout(() => {
  setCount(c + 1);
  setText("Updated");
  // ❌ Two separate renders — setTimeout is not batched in React 17
}, 1000);
```

**React 18 (Automatic Batching):** Batching now happens everywhere — whether in event handlers, `setTimeout`, Promises, or native event listeners.

```jsx
// React 18
setTimeout(() => {
  setCount(c + 1);
  setText("Updated");
  // ✅ Single render — React 18 batches setTimeout too
}, 1000);
```

This change makes React 18 more consistent — developers no longer need to wonder "where does batching apply and where does it not?"

</details>

Q: When and why do you use `flushSync`? Explain with an example.

<details>
<summary>Sample Answer</summary>

**`flushSync`** is a React 18 function that breaks batching. Any `setState` calls inside `flushSync` are processed **immediately** — triggering a separate render right away.

**When to use it?**
When you need to read DOM state right after a state update:
- `scrollHeight`, `scrollTop`
- `getBoundingClientRect()`
- Input element's `selectionStart`, `selectionEnd`
- Any DOM measurement that might change after an update

```jsx
import { flushSync } from "react-dom";

function handleClick() {
  flushSync(() => {
    setCount(c => c + 1);
  });
  // React re-renders immediately now
  // The DOM is updated — safe to read
  console.log(element.scrollHeight);

  // Updates outside flushSync batch normally
  setText("Done"); // This goes into the next render
}
```

**Why avoid it?**
`flushSync` triggers extra renders — a performance cost. Only use it when genuinely necessary. In general, batching is the better approach.

</details>
