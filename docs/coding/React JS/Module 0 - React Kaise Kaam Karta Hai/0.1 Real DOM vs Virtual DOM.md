Imagine you're writing a 100-page book. You spotted a mistake in one word on one page. With the browser's Real DOM approach — you create a brand-new copy of all 100 pages just to fix that single word. A huge waste of time and memory, right?

This problem isn't just about books — it happens with the browser's **Real DOM** too. Whenever you change something in the DOM, the browser recalculates the entire page's layout. On a small website it doesn't matter, but when an app grows (hundreds of elements, frequent updates), it gets slow.

React found a solution to this problem. And its name is — the **Virtual DOM**.

---

## What is DOM?

DOM stands for **Document Object Model**. In simple words — when the browser loads an HTML page, it creates a **tree structure** of that page. Every HTML tag becomes a node.

```html
<div>
  <h1>Hello</h1>
  <p>World</p>
</div>
```

The browser represents this like:

<img src="/diagrams/react/dom-tree.svg" width="180" alt="DOM Tree" />

You can manipulate this tree with JavaScript:

```js
const heading = document.querySelector("h1");
heading.textContent = "Namaste";
```

The DOM is the browser's **internal representation**. When you change anything in the DOM, the browser re-renders the page.

## Why is Real DOM Slow?

Whenever you change something in the DOM, the browser does two things:

1. **Reflow** — recalculating the layout of the entire page (where everything should go)
2. **Repaint** — drawing the new layout onto the screen

Reflow is the most expensive operation. When an element's size or position changes, the browser has to recalculate the layout of the **entire page** from scratch.

Imagine you made 3 DOM changes:

```js
document.querySelector("#title").textContent = "New Title";
document.querySelector("#list").innerHTML = "<li>Item 1</li>";
document.querySelector("#footer").style.color = "red";
```

Three times — the browser triggers reflow + repaint. These are three separate operations. If 30-40 changes are happening, the browser can freeze.

> **Analogy — Copying a Book:** Think of you having a book. Every time you fix a word, you print an entire new copy of the book. That's Real DOM. With Virtual DOM, you keep one draft copy, make changes there first, and then print only the page that actually changed.

## React's Solution — Virtual DOM

Virtual DOM is a **lightweight JavaScript object** — a copy of the Real DOM. But it's not as heavy as Real DOM. Real DOM carries many browser-specific properties that take up memory. Virtual DOM only keeps basic properties — type, props, children.

![Real DOM Node vs Virtual DOM Node — side by side comparison](/diagrams/react/node-comparison.svg)

Here's how React works:

1. **Render** — A Virtual DOM tree is created for the app
2. **Compare** — The new Virtual DOM is compared against the old one (Reconciliation — detailed in 0.3)
3. **Update** — Only the real DOM nodes that actually changed get updated

## How Does it Work?

```jsx
// Don't worry about useState details right now — we'll cover it in Batch 1
// Just understand the concept: how React code looks and how it uses Virtual DOM
function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}
```

When `setCount(1)` is called:

1. React creates a **new Virtual DOM tree**
2. Compares the new tree against the old one
3. Figures out that only the `<h1>` text changed
4. The browser performs just a **single DOM operation**: `h1.textContent = "Count: 1"`
5. The button and div stay untouched — no changes needed

This is called **minimized DOM manipulation**. React makes sure the browser does as little work as possible.

> **Analogy — Post-it Notes:** Think of you reading a book and spotting mistakes. Real DOM approach: rewrite the entire chapter. Virtual DOM approach: first mark all mistakes on a rough copy, decide which ones actually matter, then apply only those changes to the real book.

### What Virtual DOM is NOT

- ❌ Virtual DOM is **not exclusive to React** — Vue, Preact also use it
- ❌ Virtual DOM isn't **always faster** — for small apps, direct DOM manipulation can be quicker (but less maintainable)
- ❌ Virtual DOM is **not a separate library** — it's part of React's internal implementation

1. When something changes in the Real DOM, what does the browser do?

<details>
<summary>Sample Answer</summary>

**Answer:** When something changes in the Real DOM, the browser does two things — **Reflow** (recalculating the entire page's layout) and **Repaint** (drawing the new layout onto the screen). Multiple changes trigger multiple reflows/repaints, which can get slow.

</details>

2. How does Virtual DOM work — in one line?

<details>
<summary>Sample Answer</summary>

**Answer:** The Virtual DOM is a lightweight JavaScript object that is a copy of the Real DOM. When state changes, React creates a new Virtual DOM, compares it with the old one, and updates only the real DOM elements that actually changed.

</details>

3. What does "Minimized DOM manipulation" mean?

<details>
<summary>Sample Answer</summary>

**Answer:** React makes sure that only the minimum necessary operations happen on the Real DOM. If you change things in 10 places but only 2 real DOM nodes are actually affected — only those 2 get updated. The other 8 remain untouched. This means less work for the browser and a faster app.

</details>

4. Give a real-life analogy for how Virtual DOM works.

<details>
<summary>Sample Answer</summary>

**Answer:** Like editing an essay. You make all your changes (cut, paste, rewrite) on a draft copy first. Then, when you create the final version, only the meaningful changes get reflected on the real document. React's Virtual DOM works the same way — changes are first made on a rough copy, then only the final changes get applied to the real DOM.

</details>
