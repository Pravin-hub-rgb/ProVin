When something changes in the Real DOM, the browser recalculates the entire page's layout (reflow) and redraws the screen (repaint). These operations are expensive. On a small website it doesn't matter, but when an app grows (hundreds of elements, frequent updates), direct DOM manipulation becomes slow.

React found a solution to this problem. And its name is — the **Virtual DOM**.

---

## What is DOM?

DOM stands for **Document Object Model**. Let's break down each word:

- **Document** — the HTML file you wrote. When the browser loads your HTML page, that's the "document." The DOM is the browser's representation of that document.
- **Object** — every HTML tag becomes a JavaScript object in memory. A `<div>` becomes a `HTMLDivElement` object, an `<h1>` becomes an `HTMLHeadingElement` object, a `<p>` becomes an `HTMLParagraphElement` object. These objects have properties (like `textContent`, `className`, `style`) and methods (like `addEventListener`, `querySelector`).
- **Model** — it's a model/representation of the document. Not the actual HTML text, but a structured model of it — a tree of objects that JavaScript can read and modify.

In simple words — when the browser loads an HTML page, it creates a **tree structure** of that page. Every HTML tag becomes a node (an object) in that tree.

```html
<div>
  <h1>Hello</h1>
  <p>World</p>
</div>
```

The browser represents this like:

<img src="/diagrams/react/dom-tree.svg" width="180" alt="DOM Tree" />

You can manipulate this tree with JavaScript:

```js
const heading = document.querySelector("h1");
heading.textContent = "Namaste";
```

The DOM is the browser's **internal representation** of the document. When you change anything in the DOM, the browser re-renders the page.

## Why is Real DOM Slow?

Whenever you change something in the DOM, the browser does two things:

1. **Reflow** — recalculating the layout of the entire page (where everything should go)
2. **Repaint** — drawing the new layout onto the screen

Reflow is the most expensive operation. When an element's size or position changes, the browser has to recalculate the layout of the **entire page** from scratch.

Three DOM changes:

```js
document.querySelector("#title").textContent = "New Title";
document.querySelector("#list").innerHTML = "<li>Item 1</li>";
document.querySelector("#footer").style.color = "red";
```

Three times — the browser triggers reflow + repaint. These are three separate operations. If 30-40 changes are happening, the browser can freeze.

## React's Solution — Virtual DOM

The DOM we just described — the one the browser creates by default when it loads an HTML page — **is the Real DOM**. It's the actual tree of objects in the browser's memory. Every time something changes, the browser does reflow + repaint on the entire tree. That's why it's slow for large apps.

React's solution is the **Virtual DOM** — a lightweight JavaScript object that is a copy of the Real DOM. But it's not as heavy as Real DOM. Real DOM carries many browser-specific properties that take up memory. Virtual DOM only keeps basic properties — type, props, children.

The Virtual DOM is NOT a replacement for the Real DOM. It's a working copy that React uses behind the scenes. The Real DOM is still what the user sees on screen. React just uses the Virtual DOM to figure out *what changed* before touching the Real DOM.

![Real DOM Node vs Virtual DOM Node — side by side comparison](/diagrams/react/node-comparison.svg)

Here's how React works — step by step:

1. **Initial Render** — React takes your JSX and creates a **Virtual DOM tree** (a lightweight JavaScript object tree). Then React creates the matching **Real DOM** tree in the browser. The user sees the page.
2. **State Changes** — When state changes (e.g., `setCount(1)`), React creates a **NEW Virtual DOM tree** (not a new Real DOM tree). This new tree represents what the UI should look like now.
3. **Compare (Diffing)** — React compares the **new Virtual DOM tree** against the **old Virtual DOM tree** (the one from the previous render). This is Virtual DOM vs Virtual DOM — not Real DOM vs Virtual DOM. React figures out exactly which nodes changed.
4. **Update (Commit)** — React applies **only the changed nodes** to the **Real DOM**. If only `<h1>` text changed, only that one element gets updated. The rest of the Real DOM stays untouched.

## How Does it Work?

```jsx
// Don't worry about useState details right now — we'll cover it in Batch 1
// Just understand the concept: how React code looks and how it uses Virtual DOM
function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}
```

When `setCount(1)` is called:

1. React creates a **new Virtual DOM tree** (the "after" version) — based on the new state
2. Compares the new Virtual DOM tree against the **old Virtual DOM tree** (the "before" version from the previous render) — this is Virtual DOM vs Virtual DOM, not Real DOM vs Virtual DOM
3. Figures out that only the `<h1>` text changed (from "Count: 0" to "Count: 1")
4. The browser performs just a **single DOM operation** on the Real DOM: `h1.textContent = "Count: 1"`
5. The button and div in the Real DOM stay untouched — no changes needed

**Key point:** The comparison happens between two Virtual DOM trees (old vs new). The Real DOM is only touched at the very end, and only for the nodes that actually changed. This is why it's called "minimized DOM manipulation" — React makes sure the browser does as little work as possible on the Real DOM.

### What Virtual DOM is NOT

- ❌ Virtual DOM is **not exclusive to React** — Vue, Preact also use it
- ❌ Virtual DOM isn't **always faster** — for small apps, direct DOM manipulation can be quicker (but less maintainable)
- ❌ Virtual DOM is **not a separate library** — it's part of React's internal implementation

3. What does "Minimized DOM manipulation" mean?

<details>
<summary>Sample Answer</summary>

**Answer:** React makes sure that only the minimum necessary operations happen on the Real DOM. If you change things in 10 places but only 2 real DOM nodes are actually affected — only those 2 get updated. The other 8 remain untouched. This means less work for the browser and a faster app.

</details>
