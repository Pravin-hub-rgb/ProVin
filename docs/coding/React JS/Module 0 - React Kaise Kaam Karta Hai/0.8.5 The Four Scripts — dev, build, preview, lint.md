The project is set up, `npm run dev` is running, and ESLint "works out of the box" — that's where 0.8 ended. But open your `package.json` and look at the `scripts` section: there were never just one command in there. There are four. This doc explains all four — because together they form the full lifecycle of every React project you'll ever ship: code while it's in dev mode, build it, check the build, then let the world see it.

## The Four Scripts — One Look

Open `package.json` in your Vite project. Depending on when the project was created and which linter you picked, the `scripts` block looks close to this:

```json
"scripts": {
  "dev": "vite",
  "build": "tsc -b && vite build",
  "lint": "eslint .",
  "preview": "vite preview"
}
```

Line by line:

- `"dev": "vite"` — starts the dev server. You know this one; it's what you've been running since 0.8
- `"build": "tsc -b && vite build"` — creates the production version. `tsc -b` runs the TypeScript compiler check first, and `&&` means "only if that passes, run `vite build`"
- `"lint": "eslint ."` — scans the whole project for code problems. (In newer templates this says `oxlint .` — more on that soon)
- `"preview": "vite preview"` — serves the production build locally, so you can test it before deploying

Every one of these runs the same way: `npm run dev`, `npm run build`, `npm run lint`, `npm run preview`. The names in `scripts` are yours to run — npm just forwards the command.

You've lived in `dev` so far. Let's walk the other three in the order you'll actually use them: lint, build, preview.

## `npm run lint` — The Code Checker

**Linting** means running a tool that scans your code for problems **without actually running it**. No browser, no server — the tool just reads your source files and checks them against a list of rules.

You've already seen the result of linting, even if you didn't know its name: those **squiggly underline lines** in VS Code. Your editor runs the linter in the background as you type, and every red or yellow squiggle is the linter saying "this breaks a rule." Running `npm run lint` in the terminal does the same check — just across the entire project at once instead of the file you have open.

What does it catch? Typical examples:

```ts
const userName = "Vin";        // declared but never used — lint flags it

function Bad() {
  useEffect(() => {});         // hook called in the wrong place — lint flags it
  return <p>hi</p>;
}

console.log(userNane);         // variable doesn't exist (typo) — lint flags it
```

- **Unused variables** — declared, never used. Dead weight that usually means leftover code
- **Undefined variables** — a typo like `userNane` would crash at runtime; lint catches it while you type
- **React's rules** — like calling hooks in the wrong place. React has strict rules about hooks (we'll explore them in 2.1), and the linter is what enforces them as you write
- **Inconsistent style** — on a team, the linter keeps everyone's code following the same patterns

One honest distinction, because it matters: **TypeScript and the linter overlap, but they're not the same job.** TypeScript checks *types* — "you passed a string where a number was expected." The linter checks *patterns and rules* — "you declared this and never used it," "you broke React's hook rules." TypeScript has opinions about types; the linter has opinions about everything else. Serious projects run both.

## ESLint vs Oxlint — Same Job, Different Engine

The classic linting tool for JavaScript is **ESLint** — it's been around for years, and most existing projects use it. That's why the script above says `eslint .`.

Recently a new option appeared: **Oxlint**, from the Oxc project. The pitch is simple: **it does the same job as ESLint, but it's written in Rust, so it's dramatically faster.** Same kind of rules, same squiggly lines, same `npm run lint` — just a faster engine underneath.

And here's something you may have noticed without knowing what it was: **the current Vite React templates now set up Oxlint by default.** When you run `npx create-vite` on a fresh project today, the template uses Oxlint out of the box — with an option to choose ESLint if you'd rather have the older tool. If your newest project's lint script says `oxlint .` instead of `eslint .` — that's why.

Is Oxlint *replacing* ESLint? That's too strong. ESLint is still everywhere — every existing project that already uses it keeps using it, and some setups still require it. The accurate interview answer is: **"new Vite templates now default to Oxlint because it's much faster, while ESLint is still the common standard in existing projects."** That sentence shows you know both tools *and* the current landscape.

The practical part: from your side, nothing changes. Squiggly lines in the editor, `npm run lint` in the terminal — whichever engine runs it, you interact with it the same way.

## `npm run build` — The Production Version

Here's a question worth sitting with: the code that runs on your machine in dev mode — is that what visitors should receive?

No. Dev mode is full of things visitors don't need: the code is served **unbundled** (many separate files, exactly as you wrote them), **unminified** (full variable names, spaces, comments), plus dev-only helpers like HMR machinery and strict-mode double-checks. Perfect for you. Wasteful for a visitor on a phone network.

`npm run build` produces the real thing. It does three jobs to your code:

1. **Bundling** — combines your many files and modules into a small number of optimized files
2. **Minification** — shrinks the code: short variable names, no spaces, no comments. Same behavior, far fewer bytes — which means smaller files and faster loading for visitors
3. **Tree-shaking** — removes code you never use, so visitors don't download it

Where does the output go? A new folder called **`dist`** — short for **distribution**. (Easy to mishear as "list" — it's D-I-S-T.) That folder is the finished product: the version of your app that actually gets served to the world. One note for later: this is Vite's convention — Next.js, which 1.0's comparison table mentioned, builds into a folder called `.next` instead. Different tool, same idea: a folder of optimized output.

And remember the script: `"build": "tsc -b && vite build"`. The TypeScript check runs **first** — so if your code has type errors or lint-level problems, **the build fails and stops**. Nothing is produced. That sounds annoying; it's actually a feature. A build error is the best possible time to find out about a bug — in your terminal, before deploying, not in front of users.

## `npm run preview` — Test the Build Before the World Does

So you've built. The `dist` folder exists. Deploy it straight away?

Not yet — first, test the actual built output on your own machine. That's `npm run preview` (`vite preview`): it starts a small local server that serves the **`dist` folder**, usually at `localhost:4173` — compare that to dev mode's `localhost:5173`. Different port, because it's a different thing: this is your production build, not your dev server.

Why bother, if dev mode already shows the app working? Because **dev mode and the production build can behave differently.** Dev is unbundled and unminified; production is bundled and optimized. The overwhelming majority of the time they behave identically — but "overwhelming majority" isn't "always," and rare build-only problems are exactly the ones you want to find on your machine, not after deploying. Preview exists to catch them.

Two rules about preview:

- **It builds nothing itself.** It only serves what `npm run build` already produced. Run preview with no build first, and there's no `dist` folder to serve
- **It's not a real production server.** It's a local check, nothing more. The real serving happens on the platform you deploy to

## The Vercel Connection — Where This All Pays Off

Now connect this to deployment — the moment you push a project to the world with Vercel (the platform this course uses; we'll do it hands-on in 7.5):

```
1. Your code is on GitHub
2. You import the repo in Vercel
3. Vercel CLONES it
4. Vercel runs npm install        ← installs your dependencies
5. Vercel runs npm run build      ← the same build script you just learned
6. Build fails?  → deployment FAILS. Nothing goes live.
   Build passes? → Vercel serves the dist folder it just built. Your app is live.
```

Read step 5 again. The build you ran locally with `npm run build` — bundling, minification, the TypeScript gate, the `dist` folder — is **exactly** what Vercel runs on its servers. There's no separate "deployment magic." Vercel is doing your build, remotely, and serving the result. And when the build has errors, the deployment doesn't happen — which is why errors stop you from going live.

Better still: this isn't a one-time event. **Every push to GitHub triggers this cycle again** — clone, install, build, deploy. That automatic rebuild-on-every-push is called **continuous deployment**, and it means fixing a bug and pushing the fix is literally the same action as deploying the fix.

## The Full Flow — One Picture

```
while coding            when ready to ship        before deploying         to go live
────────────            ──────────────────        ────────────────         ─────────
npm run dev       →     npm run build       →     npm run preview    →     push to GitHub
localhost:5173          creates dist/             localhost:4173           Vercel builds + serves it
unbundled,              bundled, minified,        test the REAL            (build fails = no deploy)
unminified              type-checked              built output
```

Dev while you work. Build when you're done. Preview to check the build. Push to go live — and the platform reruns the build for you. Four scripts, one lifecycle, every React project you'll ever ship.

## What It Is NOT

- **Lint is not TypeScript.** TypeScript checks types; the linter checks patterns and rules (unused variables, React's hook rules, style). Projects run both
- **Oxlint is not a new thing to learn.** Same job, same squiggles, same `npm run lint` — only the engine underneath is different (and faster)
- **`build` does not touch your source code.** It reads `src/` and writes an optimized copy into `dist/`. Your original files stay exactly as they were
- **`preview` is not a production server.** It's a local test of the build — the real serving happens on Vercel
- **Vercel is not doing something alien.** It runs the same install + build scripts from your `package.json` — just on its machines instead of yours

## Check Yourself

1. You see a squiggly yellow underline in VS Code, then run `npm run lint` in the terminal. Are these two different tools? What's the relationship?

   <details>
   <summary>Sample Answer</summary>

   Same tool, two ways of seeing it. The editor runs the linter in the background as you type and shows problems as squiggly underlines; `npm run lint` runs the same check across the whole project at once. One is continuous and per-file, the other is on-demand and project-wide — the rules and the engine are the same.
   </details>

2. Why can a project run perfectly in `npm run dev` and still fail its Vercel deployment? What exactly fails?

   <details>
   <summary>Sample Answer</summary>

   Dev mode serves code as-is, but deployment runs `npm run build` — and the build is stricter: it runs the TypeScript check (`tsc -b`) first, and type errors or rule violations stop the build. When the build fails on Vercel, the deployment fails and nothing goes live. The code "ran" in dev because dev skips the checks the build performs — which is why testing the build (locally or via Vercel) matters.
   </details>

3. Your friend says: "the dev server already shows my app working — why would I ever run preview?" Give the two-part answer.

   <details>
   <summary>Sample Answer</summary>

   Part one: dev and production behave differently — dev is unbundled and unminified, the build is bundled and optimized, and rare problems only show up in the built output. Preview serves the actual `dist` folder at localhost:4173 so you catch those on your machine. Part two: preview builds nothing itself — you must run `npm run build` first, or there's no `dist` folder to serve. And it's a local check, not a real production server.
   </details>

4. What is the `dist` folder, what three things did the build do to produce it, and what happens to it on Vercel?

   <details>
   <summary>Sample Answer</summary>

   `dist` (short for distribution) is the finished production output of a Vite build. To produce it, the build bundled the code (many files → few optimized ones), minified it (short names, no spaces, no comments — smaller files, faster loading), and tree-shook it (removed unused code). On Vercel, the platform clones the repo, runs `npm install` and `npm run build` itself, and serves the `dist` folder it built — and if that build has errors, the deployment fails.
   </details>

5. A friend says "ESLint is dead, Oxlint replaced it." Give the accurate one-sentence version for an interview.

   New Vite templates now default to Oxlint — a Rust-based linter that does the same job much faster — but ESLint isn't replaced: it's still the common standard in existing projects and some setups still require it. Both work the same way from the developer's side: squiggly lines in the editor, `npm run lint` in the terminal.
   </details>
