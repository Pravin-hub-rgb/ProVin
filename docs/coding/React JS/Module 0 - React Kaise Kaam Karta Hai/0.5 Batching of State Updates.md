0.4 mein humne dekha ki Fiber ne reconciliation ko interruptible banaya. Lekin React aur bhi smart hai — jab ek event handler mein multiple state updates ho rahi hain, toh React unhe ek saath group karta hai. Ise kehte hain **Batching**.

Agar batching na hoti, toh har `setState` call ke saath ek alag re-render trigger hota. Isse performance hit hoti aur beech ke inconsistent states user ko dikh sakti thi. React ne ye problem pehle se soch li.

---


## Problem — Multiple SetState = Multiple Renders?

Dekho ye code:

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  const [text, setText] = useState("");

  function handleClick() {
    setCount(count + 1);  // State update 1
    setText("Clicked!");  // State update 2
  }

  return (
    <div>
      <p>{count} — {text}</p>
      <button onClick={handleClick}>Click</button>
    </div>
  );
}
```

`handleClick` mein do `setState` calls hain. Kya React do baar re-render karega?

**Nahi.** React dono state updates ko **batch** karega — ek hi re-render mein dono changes apply ho jayenge. Component ek baar render hoga, dono naye values ke saath.

## React 17 and Before — Limited Batching

React 17 mein batching sirf **event handlers** ke andar hoti thi:

```jsx
// ✅ Batch hota hai (event handler ke andar)
function handleClick() {
  setCount(c => c + 1);
  setText("Clicked");
  // Ek hi re-render — both updates together
}

// ❌ Batch nahi hota (event handler ke bahar)
setTimeout(() => {
  setCount(c => c + 1);
  setText("Updated");
  // Do alag re-render!
}, 1000);

// ❌ Promise mein bhi batch nahi hota
fetch("/api/data").then(() => {
  setCount(c => c + 1);
  setText("Fetched");
  // Do alag re-render!
});
```

React 17 mein, `setTimeout`, Promises, aur native event listeners ke andar batching nahi hoti thi — har `setState` apna alag re-render trigger karta tha.

## React 18 — Automatic Batching

React 18 ne is limit ko hata diya. Ab **har jagah** batching hoti hai:

```jsx
// ✅ Event handler — batches (React 17 mein bhi hota tha)
function handleClick() {
  setCount(c => c + 1);
  setText("Clicked");
  // Ek re-render
}

// ✅ setTimeout — ab batch hota hai (React 18 naya feature)
setTimeout(() => {
  setCount(c => c + 1);
  setText("Updated");
  // Ek re-render — React 17 mein do alag the!
}, 1000);

// ✅ Promise — ab batch hota hai
fetch("/api/data").then(() => {
  setCount(c => c + 1);
  setText("Fetched");
  // Ek re-render — React 17 mein do alag the!
}, 1000);

// ✅ Native event — ab batch hota hai
button.addEventListener("click", () => {
  setCount(c => c + 1);
  setText("Clicked");
  // Ek re-render
});
```

> **Analogy — Grocery Shopping:** React 17 ki tarah — agar tum 5 cheezein lena chahte ho toh har cheez ke liye alag trip karte ho (5 trips). React 18 ki tarah — ek list banakar ek hi trip mein saaman le aate ho (1 trip). Dono mein same kaam hota hai, lekin ek efficient hai.

## Batch Kaise Kaam Karta Hai?

Jab tum `setCount(c + 1)` call karte ho, React immediately re-render nahi karta. React internally ek **queue** mein updates ko store karta hai:

```
Step 1: setCount(1)     → Queue: [count update]
Step 2: setText("Hi")   → Queue: [count update, text update]
Step 3: (event handler done) → React processes queue → Single re-render
```

React ka internal logic kuch aisa hota hai — "Event handler ke andar jo bhi state updates ho rahi hain, unhe collect karo, jab handler khatam ho tab ek saath process karo."

## Batch Ko Break Kaise Karein?

Kabhi-kabhi tum **nahi chahte** ki updates batch hon. Chahte ho ki har update immediately process ho. React 18 mein `flushSync` milta hai:

```jsx
import { flushSync } from "react-dom";

function handleClick() {
  flushSync(() => {
    setCount(c => c + 1);
  });
  // React abhi immediately re-render karega

  flushSync(() => {
    setText("Done");
  });
  // Phir doosra re-render — alag se
}

// Do alag re-render honge (batch nahi hoga)
```

`flushSync` rare cases mein use hota hai — jaise jab tumhe DOM state immediately read karni ho (`scrollHeight`, `getBoundingClientRect()`, etc.). General practice mein batching **achhi** cheez hai — avoid `flushSync` unless really needed.

## Batching Kyun Important Hai?

1. **Performance** — Kam re-render = kam kaam = fast app
2. **Consistency** — Dono state updates ek saath apply hoti hain, beech ka inconsistent state nahi dikhta
3. **Predictable** — Ek event handler ke baad ek hi render, predictable behavior


> ❌ Batching **state updates ko delay nahi karta** — wo event handler ke end mein process hoti hain (microtask level)
> ❌ Batching **saare updates ko ignore nahi karta** — sab updates apply hote hain, bas ek saath
> ❌ Batching **sirf performance feature nahi hai** — consistency bhi ensure karta hai (intermediate renders nahi)
> ❌ Batching **React 18 ke baad sab jagah hoti hai** — no more `setTimeout` gotchas

**In Your Own Words**

1. State batching kya hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** State batching React ka optimization hai jisme multiple `setState` calls ko group karke ek single re-render mein process kiya jaata hai. Jaise ek event handler mein 3 setState calls hain — React teen alag renders nahi karega, balki ek hi render mein sab apply karega.

</details>

2. React 17 aur React 18 ki batching mein kya fark hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** React 17 mein batching sirf event handlers (onClick, onChange, etc.) ke andar hoti thi. setTimeout, Promises, aur native events ke andar batching nahi hoti thi — har setState apna alag render trigger karta tha. React 18 ne "Automatic Batching" introduce kiya — ab har jagah batching hoti hai, chahe event handler ho, setTimeout ho, Promise ho, ya native event listener.

</details>

3. React batch kaise implement karta hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Jab setState call hota hai, React immediately re-render nahi karta. Woh update ko ek internal queue mein daal deta hai. Jab current execution context khatam hota hai (event handler, setTimeout callback), tab React queue ko process karta hai — saare updates ek saath — aur ek single re-render trigger karta hai.

</details>

4. `flushSync` kab use karte hain?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `flushSync` tab use karte hain jab hume force karna ho ki batching na ho aur update immediately process ho. Rare cases mein — jaise jab DOM ko immediately read karna ho update ke baad (scrollHeight, getBoundingClientRect). General practice mein avoid karna chahiye kyunki performance hit hoti hai.

</details>

5. Batching ka real-world analogy kya ho sakta hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Jaise WhatsApp mein ek saath multiple messages bhejna. Agar tum ek-ek karke bhejoge toh baar-baar network request hogi. Lekin agar saare messages type karke ek saath bhejoge, toh ek hi request mein sab chala jayega. React ka batching bhi aisa hi hai — multiple state updates ek saath batch karke ek hi render mein process karta hai.

</details>
