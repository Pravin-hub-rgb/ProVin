
## MCQ

Q: What does React's "Declarative approach" mean?
A. You declare the outcome, React decides how to do it
B. You write DOM manipulation step-by-step yourself
C. You write server-side code that generates HTML
D. You use a template language inside HTML
> A. "Declarative" means — you say "what it should look like", and React handles "how to do it". In the Imperative approach (B), you update the DOM yourself.

---

Q: When an app is small, vanilla JS DOM manipulation works fine. But why does it become a problem when the app grows?
A. Because vanilla JavaScript becomes slow
B. Because the code becomes messy and bug-prone
C. Because the browser stops supporting vanilla JS
D. Because DOM manipulation only works in mobile apps
> B. In vanilla JS, DOM manipulation is manual — `document.getElementById()`, `element.textContent`, etc. In an app with 50-100 components, this approach becomes hard to maintain. React introduced a declarative approach — you declare the UI, React handles the DOM.

---

Q: What is the most important feature of React components?
A. Components style HTML with CSS
B. Components only render on the server-side
C. Components are written once and can be reused
D. Components take data directly from a database
> C. The biggest advantage of components is reusability — write a `Button` component once and use it everywhere. Just like Lego blocks.

---

Q: React is a UI library. What is the difference between a library and a framework?
A. A library has limited scope, a framework provides everything
B. A library is only used in mobile apps, a framework in web
C. A library is old technology, a framework is modern
D. There is no difference between a library and a framework
> A. A library does specific work only (React handles just UI). A framework is a complete package (Angular, Next.js) where routing, data fetching, etc. are built-in.

---

Q: Which statement about React is FALSE?
A. React uses a component-based architecture
B. React is a full-stack framework that provides backend
C. React uses a declarative approach
D. React is maintained by Meta (Facebook)
> B. React is only a frontend UI library, not a full-stack framework. Backend features are provided by Next.js (a React-based framework).

---

Q: There is software that provides UI, routing, data fetching, authentication — everything built-in. What would you call it?
A. Library
B. Framework
C. Database
D. API
> B. A framework is a complete package — everything is built-in. A library is for specific work only. (React = library, Next.js/Angular = framework)

## TrueFalse

Q: In React, you have to write every DOM operation yourself, just like in vanilla JavaScript.
- True
- False
> False. In vanilla JS, you write DOM operations yourself. In React, you just declare the UI (declarative), and React handles all DOM operations itself.

---

Q: Using React for a small app can be overkill.
- True
- False
> True. For a simple 2-3 page website, plain HTML/CSS or vanilla JS is sufficient. React's complexity only pays off when the app grows, state gets complex, or components need to be reused.

## ShortAnswer

Q: Explain the "Declarative approach" in your own words. Why is it better than Imperative approach?

<details>
<summary>Sample Answer</summary>

**Declarative approach** — you declare the outcome, React handles the implementation.

Simple example:

**Imperative (vanilla JS):**
```js
const btn = document.getElementById("btn");
const msg = document.getElementById("message");
btn.addEventListener("click", () => {
  msg.textContent = "Clicked!";
  msg.style.color = "blue";
});
```
You're telling it — "find this element, change this, set this color."

**Declarative (React):**
```jsx
function App() {
  const [clicked, setClicked] = useState(false);
  return (
    <div>
      <button onClick={() => setClicked(true)}>Click</button>
      {clicked && <p style={{color: "blue"}}>Clicked!</p>}
    </div>
  );
}
```
You're just saying — "if clicked is true, show this." React decides how to update the DOM itself.

Why is Declarative better? Because the code is predictable, maintainable, and easy to debug. Change something in one place, React updates that exact spot in the DOM automatically — no need to write a single `getElementById` call.

**Analogy:** In a taxi, you tell the driver "take me to CP" (declarative). You don't say "turn left, go 200 meters, take a U-turn" (imperative).

</details>

Q: Why are React components useful? Give 2 reasons.

<details>
<summary>Sample Answer</summary>

**1. Reusability (DRY Principle):** Write a component once and use it anywhere. Once you create a `Button` component — use it in the login form, the signup form, the settings page. You don't have to duplicate code.

**2. Isolation:** Each component works within its own scope. A bug in one component doesn't affect another. If the `Navbar` has a problem, the `Footer` is unaffected. This makes debugging easier.

**Analogy:** Kitchen appliances — a toaster, a microwave, a fridge. If one breaks, the others keep working. But if everything was in one machine, one broken part would break the whole system.

</details>
