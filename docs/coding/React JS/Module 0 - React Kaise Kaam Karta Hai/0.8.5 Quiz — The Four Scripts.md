
## MCQ

Q: What does linting mean?
A. Running the test suite before committing code
B. Scanning code for problems without actually running it
C. Formatting code so it looks consistent
D. Compiling TypeScript into JavaScript
> B. Linting means a tool scans your source files and checks them against a list of rules — no browser, no server, the code is never executed. It catches unused variables, undefined variables, React rule violations, and style inconsistencies.

---

Q: Those red/yellow squiggly underlines in VS Code — what are they?
A. TypeScript's compiler running in the background
B. The browser reporting runtime errors back to the editor
C. The linter running in the background as you type
D. Git marking lines that differ from the last commit
> C. The editor runs the linter in the background while you type, and each squiggle is a rule violation. Running `npm run lint` in the terminal does the same check across the whole project at once.

---

Q: What is Oxlint?
A. A replacement for Vite's dev server
B. A linter that does the same job as ESLint but written in Rust, so it's much faster
C. A stricter TypeScript compiler mode
D. A formatting tool that replaces Prettier
> B. Oxlint (from the Oxc project) is a linter written in Rust that performs the same job as ESLint — similar rules, same squiggly lines, same `npm run lint` — just with a much faster engine. The current Vite React templates set it up by default.

---

Q: What is the correct interview phrasing about Oxlint and ESLint?
A. "Oxlint has completely replaced ESLint everywhere"
B. "ESLint is outdated and no longer used in new projects"
C. "New Vite templates default to Oxlint for speed, while ESLint is still common in existing projects"
D. "You must choose one — they cannot run on the same project"
> C. "Replacing" is too strong. New Vite templates now default to Oxlint (Rust, faster), but ESLint remains the standard in existing projects, and some setups still require it. Both work identically from the developer's side.

Q: What does `npm run build` produce, and where does the output go?
A. A faster dev server, served from `node_modules`
B. The production version — bundled, minified output in a `dist` folder
C. A ZIP archive of the source code ready to email
D. Updated `package.json` with locked dependency versions
> B. The build bundles your many files into a few optimized ones, minifies them (short names, no spaces, no comments — fewer bytes, faster loading), and tree-shakes unused code. The finished output lands in the `dist` folder (short for "distribution"). Your source code in `src/` is untouched.

Q: You import your GitHub repo into Vercel and the deployment fails. What most likely happened?
A. Vercel only deploys on weekends
B. The `npm run build` step ran into errors, so nothing went live
C. Vercel requires a paid plan for React projects
D. The `dist` folder was committed to GitHub
> B. Vercel clones the repo, runs `npm install`, then runs your build script (`npm run build`). If that build has errors, the deployment fails and nothing goes live. If it passes, Vercel serves the `dist` folder it built — the same build you run locally.

## TrueFalse

Q: `npm run preview` builds the project and then serves it.
- True
- False
> False. Preview builds nothing — it only serves the `dist` folder that `npm run build` already produced. Run preview without building first and there's no `dist` folder to serve. It's a local check of the build, usually at `localhost:4173`, not a real production server.

---

Q: Dev mode and the production build always behave exactly the same.
- True
- False
> False. Dev serves code unbundled and unminified with dev-only helpers; the production build is bundled, minified, and optimized. They behave identically most of the time — which is exactly why `preview` exists: to test the real built output locally and catch the rare build-only differences before deploying.

---

Q: The build process modifies your source files to make them smaller.
- True
- False
> False. The build reads `src/` and writes an optimized copy into `dist/` — your original source files stay exactly as they were. Minification happens on the copy, never on your code.

---

Q: A project can pass in dev mode but fail the build, because the build runs stricter checks (like the TypeScript compiler).
- True
- False
> True. The build script is `"tsc -b && vite build"` — the TypeScript check runs first, and errors stop the build before anything is produced. That strictness is a feature: it's better to find the bug in your terminal than in front of users after deploying.

## ShortAnswer

Q: List the four scripts in a Vite React project's `package.json` and explain what each one does. Then describe the full lifecycle in order.

<details>
<summary>Sample Answer</summary>

**The four scripts:**

- `"dev": "vite"` — starts the dev server (`localhost:5173`) with HMR, for coding
- `"build": "tsc -b && vite build"` — creates the production version: TypeScript check first, then bundling, minification, and tree-shaking into the `dist` folder
- `"lint": "eslint ."` (or `oxlint .` in newer templates) — scans the whole project for problems without running the code
- `"preview": "vite preview"` — serves the already-built `dist` folder locally (`localhost:4173`) to test the production build

**The lifecycle:** `npm run dev` while coding → `npm run build` when ready to ship → `npm run preview` to test the real built output → push to GitHub, where Vercel reruns the build and serves the result. Build fails = no deploy.
</details>

---

Q: Your project runs fine in `npm run dev`, but Vercel refuses to deploy it. Walk through what Vercel does, and why the error only shows up at deployment.

<details>
<summary>Sample Answer</summary>

**What Vercel does:** clones the GitHub repo → runs `npm install` → runs `npm run build`. If the build errors, the deployment fails and nothing goes live; if it passes, Vercel serves the `dist` folder it built. Every push to GitHub repeats this cycle — that's continuous deployment.

**Why the error only appears now:** dev mode serves code as-is — unbundled, unminified, with no compile gate. The build is stricter: `tsc -b` type-checks first, and `vite build` fails on errors that dev mode tolerated. The bug existed all along; dev mode just never ran the check that catches it. That's also why testing with `npm run preview` locally (after building) catches the same problems before pushing.
</details>

Q: Explain linting to a junior dev: what it is, what the squiggly lines are, what it catches, and how ESLint and Oxlint relate.

<details>
<summary>Sample Answer</summary>

**What it is:** a tool that scans code for problems without running it. TypeScript checks types; the linter checks patterns and rules beyond types — projects run both.

**The squiggly lines:** your editor runs the linter in the background as you type — every red/yellow underline is a rule violation. `npm run lint` runs the same check project-wide in the terminal.

**What it catches:** declared-but-unused variables, undefined variables (typos that would crash at runtime), React rule violations (like hooks called in the wrong place), and inconsistent style across a team.

**ESLint vs Oxlint:** same job, different engines. ESLint is the classic, used by most existing projects. Oxlint (from the Oxc project) is written in Rust and is much faster — new Vite React templates now default to it, with an ESLint option if you want. "Replaced" is too strong; from the developer's side nothing changes — same squiggles, same `npm run lint`.
</details>

Q: What is the `dist` folder? What does the build do to your code to produce it, and what happens to it on Vercel?

<details>
<summary>Sample Answer</summary>

**What it is:** the production output folder of a Vite build — "dist" is short for **distribution** (easy to mishear as "list"). It contains the finished, optimized version of the app that actually gets served to visitors. (Next.js builds into `.next` instead — different tool, same idea.)

**What the build did:** bundled the code (many files → few optimized ones), minified it (short names, no spaces, no comments → fewer bytes → faster loading), and tree-shook it (removed unused code). The source in `src/` is never modified — `dist/` is a separate output copy.

**On Vercel:** the platform runs the same `npm run build` on its own servers after cloning the repo — no "deployment magic," just your build script remotely — and serves the `dist` folder it produced.
</details>
