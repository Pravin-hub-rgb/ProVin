In 0.5, we saw how React batches state updates inside event handlers. But a question arises — **how do React's event handlers (`onClick`, `onChange`) actually work?**

```jsx
<button onClick={handleClick}>Click Me</button>
```

When the user clicks the button, the `handleClick` function runs. But how does React know the button was clicked? To answer that, we first need to understand the browser's event system.

---

## What are Browser Events?

The browser generates many events on its own — `click`, `change`, `input`, `submit`, `keydown`, `mousemove`, and so on.

```html
<button>Click</button>
```

In JavaScript, you listen for events like this:

```javascript
const btn = document.querySelector("button");
btn.addEventListener("click", () => {
  console.log("Clicked");
});
```

Here, the browser itself generates the `"click"` event. That's why it's called a **Native Event** — the browser's original event.

## What React Does

In React, we normally write:

```jsx
<button onClick={handleClick}>Click</button>
```

We didn't write `addEventListener()` ourselves, yet the click was still detected. **How?**

React listens to the browser's events internally. But React doesn't pass the browser's raw event directly to your handler. In between, React wraps it in its own **wrapper object** called the **SyntheticEvent**.

```
Browser Click
     │
     ▼
Native Event
     │
     ▼
React
     │
     ▼
SyntheticEvent
     │
     ▼
Your onClick Handler
```

In other words, your handler doesn't receive the browser's raw event. React wraps it first.

## What is SyntheticEvent?

When you receive an event in your `onClick`:

```jsx
function handleClick(event) {
  console.log(event);
}
```

This `event` is not the browser's event. It's a React-made object called **SyntheticEvent**.

If you need the original browser event:

```jsx
function handleClick(event) {
  console.log(event);             // SyntheticEvent
  console.log(event.nativeEvent); // The browser's original event
}
```

### Definition

> **SyntheticEvent is React's own wrapper event object built on top of the browser's native event. It provides consistent properties across all browsers.**

## Why Did React Create a Wrapper?

In old browsers, the same event behaved differently. For example, some browsers supported `event.target` while others used `event.srcElement`. The `pageX` behavior of mouse events also varied. Even `preventDefault()` wasn't the same everywhere.

React decided — "No matter which browser, the developer should get the same format." That's why SyntheticEvent was created. Now you use the same properties everywhere — `event.target`, `event.currentTarget`, `event.preventDefault()`, `event.stopPropagation()`. React ensures these work consistently.

```jsx
function handleClick(e) {
  e.preventDefault();    // Cross-browser — works in all browsers
  e.stopPropagation();   // Same
  e.target;              // Same
  e.currentTarget;       // Same
  e.clientX;             // Mouse events — cross-browser consistent
  e.key;                 // Keyboard events — same
}
```

## Event Delegation — One Listener for Everything

If a page has 100 buttons, does React create 100 separate event listeners? No.

Browser events **bubble** — they travel from child to parent:

```
Button click → Div → Body → Document
```

React takes advantage of this bubbling behavior. React attaches a **single event listener** — on its root element (the `<div id="root">`). When a button is clicked, the event bubbles up to the root, and React's single listener catches it. React then decides — "which button was clicked? Which `onClick` handler should fire?"

```
React: A single listener at the root
─────────────────────────────────
     root (React listener here ☝️)
       └── div
            ├── button#1  ← click
            ├── button#2
            └── button#3
```

### Definition

> **Event Delegation is a technique where React attaches a single event listener to the root element (`<div id="root">`) instead of each individual element, and uses event bubbling to determine which component's handler should fire.**

## Event Bubbling

Event Delegation is only possible because events travel upward through the DOM. This process is called **Event Bubbling**.

```html
<div>
  <button>Click</button>
</div>
```

When the button is clicked, the event's path is:

```
Button → Div → Body → Document
```

React takes advantage of this. Without bubbling, the root listener could never catch a button click.

---

> ### ⏳ Legacy Concept — Event Pooling (React 17 and earlier)
>
> Only read this section when you encounter `event.persist()` in older codebases. If you're learning React 18, this is optional.
>
> **What pooling means:** Imagine you have 100 plastic bottles. Instead of throwing one away after drinking, you wash it and reuse it. This is called Object Pooling — reusing an existing object instead of creating a new one.
>
> React 17 worked the same way. You clicked a button — React created a SyntheticEvent object. Your handler ran. Once the handler finished, React would **empty** that object (set all properties to null) and reuse it for future events. That's why it was called Pooled Events.
>
> **Where the problem occurred:** If you accessed the event inside a `setTimeout`:
>
> ```jsx
> function handleClick(event) {
>   setTimeout(() => {
>     console.log(event.type); // null — the object has already been cleared
>   }, 1000);
> }
> ```
>
> The sequence:
> 1. Button clicked → `event.type = "click"`
> 2. `setTimeout` started (callback fires after 1 second)
> 3. `handleClick` finishes → React clears the event object (`type` becomes null)
> 4. After 1 second, the callback runs → `console.log(event.type)` → **null**
>
> **The solution was `event.persist()`:**
>
> ```jsx
> function handleClick(event) {
>   event.persist(); // Tell React — "don't reuse this object"
>   setTimeout(() => {
>     console.log(event.type); // ✅ "click" — the object hasn't been cleared
>   }, 1000);
> }
> ```
>
> `event.persist()` in React 17 removed the SyntheticEvent from the pool. In React 18, pooling was removed entirely — SyntheticEvent now behaves like a normal JavaScript object. `persist()` is no longer needed.
>

## How to Write Events in React

```jsx
function App() {
  return (
    <>
      {/* ✅ React way — onClick, onChange, etc. */}
      <button onClick={() => alert("Clicked!")}>Click</button>
      <input onChange={(e) => console.log(e.target.value)} />
      <form onSubmit={(e) => { e.preventDefault(); /* submit */ }}>
        <button type="submit">Submit</button>
      </form>
    </>
  );
}
```

You don't need to use `addEventListener` directly with React. React's built-in SyntheticEvent system handles everything.

> ❌ SyntheticEvent **doesn't replace native events** — it's a wrapper built on top of them
> ❌ SyntheticEvent is **only available in React's event handlers** — you won't get SyntheticEvent from `addEventListener`
> ❌ SyntheticEvent **is NOT pooled in React 18** — use it freely, no need to remember `persist()`
> ❌ SyntheticEvent **uses event delegation internally for performance** — but this is React internals, you don't do anything special

---

### Quick Definitions (Revision)

> **Native Event:** The browser's original event (`click`, `change`, etc.) that you listen to with `addEventListener`.

> **SyntheticEvent:** React's wrapper object built on top of the native event. It provides consistent properties across all browsers.

> **Event Delegation:** React keeps a single listener at the root element and uses event bubbling to determine which component's handler should fire.

> **Event Bubbling:** The browser's mechanism where an event travels from the target element up through its ancestors to the root.

> **Event Pooling (React 17):** Reusing SyntheticEvent objects by clearing them after the handler finishes. Removed in React 18.

**In Your Own Words**

1. How does event delegation work in React?

<details>
<summary>Sample Answer</summary>

**Answer:** React doesn't attach a separate listener to every element. Instead, it attaches a single event listener at the root element (`<div id="root">`). When an event occurs, it bubbles up to the root. React's single listener catches all events and decides which component's handler to invoke. This is memory-efficient — whether there are 100 or 1000 buttons, there's just one listener.

</details>

2. What is SyntheticEvent and why does it exist?

<details>
<summary>Sample Answer</summary>

**Answer:** SyntheticEvent is React's own event wrapper object built on top of the browser's native event. It exists for cross-browser consistency — `event.target`, `event.preventDefault()`, and other properties work the same in every browser. React ensures that developers get the same properties regardless of the browser's internal differences.

</details>

3. What's the relationship between Event Delegation and Event Bubbling?

<details>
<summary>Sample Answer</summary>

**Answer:** Event Bubbling is what makes Event Delegation possible. An event travels from the child element up to the parent. Event Delegation takes advantage of this — React keeps one listener at the root, and events bubble up to it. Without bubbling, the root listener could never catch a button click.

</details>

4. What was Event Pooling and why was it removed in React 18?

<details>
<summary>Sample Answer</summary>

**Answer:** Event Pooling was React 17's memory optimization — after an event handler finished, React would clear the SyntheticEvent object's properties (set them to null) and reuse the object for future events. The problem was that accessing the event in asynchronous code (`setTimeout`, `Promise`) caused the properties to be null. React 18 removed pooling because modern JavaScript engines are fast enough that reuse isn't needed. SyntheticEvent now behaves like a normal JavaScript object.

</details>

5. Should you use `addEventListener` directly in React, or rely on React's event system?

<details>
<summary>Sample Answer</summary>

**Answer:** You should rely on React's built-in event system (`onClick`, `onChange`, `onSubmit`, etc.) — no need for direct `addEventListener`. Direct `addEventListener` bypasses React's SyntheticEvent system, so you lose cross-browser consistency, event delegation, and React's internal optimizations. React's event system handles everything, so prefer it.

</details>
