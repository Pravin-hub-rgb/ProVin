In 0.3, we saw that React compares Virtual DOM trees through reconciliation. But in the transition, a problem was hinted at — **when React does reconciliation, the browser freezes.** In React 15, reconciliation was synchronous — once it started, it ran until everything was done, and the whole time the browser tab was frozen.

React 16 brought a new internal engine that solved this problem — the **Fiber Architecture**.

---

## Problem — Synchronous Reconciliation

Up to React 15, reconciliation was synchronous. That means — once reconciliation started, it couldn't be paused, and the browser stayed frozen until all the work was done.

![Browser Main Thread — Synchronous Reconciliation causes freeze and lag](/diagrams/react/fiber-timeline.svg)

If 50ms of reconciliation is happening, the browser can't do anything else for those 50ms. That's the problem:
- Animations freeze (janky feel)
- Typing gets delayed (laggy input)
- Scrolling doesn't stay smooth

## What Was Needed?

A system that could:
1. Break work into **smaller pieces**
2. **Pause** in the middle if something urgent comes up
3. Decide on **priority** — "do this first, do that later"
4. Give the browser a **breather** (no dropped frames)

## What is Fiber?

Fiber is a **JavaScript object** — a unit of work. Each component gets its own Fiber node. Where React 15 used to recursively process the tree, Fiber uses a linked-list-based approach.

Think of each Fiber as a "work package" — a chunk of work small enough to complete within a single frame.

![React 15 vs React 16 Fiber — synchronous vs interruptible rendering](/diagrams/react/fiber-vs-sync.svg)

## How Fiber Works

### 1. Work as a Tree of Fibers

React creates a Fiber node for every element. These nodes are connected via a linked list:

```jsx
<App>
  <header>
    <h1>Title</h1>
  </header>
  <main>
    <p>Content</p>
  </main>
</App>
```

React builds a **Fiber Tree** where each node is connected to three links:
- **child** — the first child node
- **sibling** — the next sibling node
- **return** — the parent node (to go back up)

```
           App Fiber
          /          \
    header Fiber    main Fiber
       |               |
    h1 Fiber        p Fiber
```

This linked-list structure lets React **interrupt** — process one node, check if something urgent came up, then process the next node.

### 2. Two Phases — Render + Commit

In the Fiber architecture, work is split into two phases:

**Phase 1: Render (aka "Reconciliation Phase")**
- Traverse the Virtual DOM tree
- Calculate changes (diffing)
- **Interruptible** — you can pause midway
- Side-effect free (DOM doesn't change yet)

**Phase 2: Commit**
- Apply the calculated changes to the real DOM
- **Not interruptible** — once you start, you have to finish
- Lifecycle methods are called (`componentDidMount`, `useEffect`)

```
Render Phase (interruptible):      Commit Phase (not interruptible):
[Fiber1] [Fiber2] [Fiber3] [Fiber4]  →  [DOM Update 💥]
    ↺ can pause here                    ↺ cannot pause
```

### 3. Priority Levels

React Fiber assigns different priorities:

| Priority | Example |
|----------|---------|
| 🔴 **Immediate** | User input, click events |
| 🟡 **High** | Animations, transitions |
| 🟢 **Normal** | Normal state updates |
| 🔵 **Low** | Data fetching, lazy loading |
| ⚫ **Idle** | Pre-rendering, offscreen content |

Imagine — if the user is typing (Immediate priority) and an animation is running (High priority), React processes the user input first, then the animation, then the rest.

### 4. Cooperative Scheduling

React "cooperates" with the browser. Like this:

```
Frame 1:  [React work (5ms)] [Browser idle (11ms)] [Render next frame]
                                   ↺ React will wait here
Frame 2:  [React work (5ms)] [Browser work (8ms)]  [React again...]
```

React uses an approach similar to `requestIdleCallback` (but its own internal implementation). When the browser signals "nothing urgent right now," React picks up the remaining work and continues.

> **Analogy — Office Work:** Imagine you have a project with 10 tasks. Before Fiber — do all 10 tasks in one go, and if a call comes in, ignore it. With Fiber — do one task, check if an urgent email arrived, then do the next task. Urgent work (client call = user input) comes first, normal work (documentation = background rendering) comes later.

## What Do You Need to Do With Fiber?

**Nothing.** Fiber is an internal implementation detail. You write your React components exactly as before. Fiber lives inside the framework — you don't write Fiber code.

But understanding Fiber has benefits:
- Interviewers ask — "What changed in React 16?"
- When debugging performance issues, you understand "why is this render low priority?"
- Your mental model of React becomes stronger — "Ah, that's why it behaves asynchronously"

> ❌ Fiber is **not new syntax** — it's an internal change, the API is the same
> ❌ Fiber is **not asynchronous rendering** — it's cooperative scheduling (the foundation of concurrent mode)
> ❌ Fiber doesn't mean **you write anything differently** — same `useState`, same `useEffect`
> ❌ Fiber is **not a general-purpose library** — it's specific to React's internals

**In Your Own Words**

1. What problem did React 15's synchronous reconciliation cause?

<details>
<summary>Sample Answer</summary>

**Answer:** In React 15, reconciliation was synchronous — once it started, it couldn't be paused. Until the entire work was complete, the browser stayed frozen. This caused janky animations, laggy typing, and choppy scrolling.

</details>

2. How does Fiber architecture solve this problem?

<details>
<summary>Sample Answer</summary>

**Answer:** Fiber breaks work into smaller pieces (units of work). Each piece is small enough to complete within a single frame. After each piece, React checks — "did something urgent come up?" If yes, it does that first, then continues with the remaining Fiber work. This is called cooperative scheduling.

</details>

3. What's the difference between the Render phase and the Commit phase?

<details>
<summary>Sample Answer</summary>

**Answer:** In the Render phase (Reconciliation phase), React traverses the Virtual DOM, calculates changes — this phase is **interruptible** (you can pause it), and the DOM doesn't change. In the Commit phase, the calculated changes are applied to the real DOM — this phase is **not interruptible** (once you start, you finish). `useEffect` and lifecycle methods are called during the Commit phase.

</details>

4. How does React Fiber assign priorities?

<details>
<summary>Sample Answer</summary>

**Answer:** React assigns different priorities — Immediate (user input, clicks), High (animations, transitions), Normal (regular state updates), Low (data fetching, lazy loading), and Idle (pre-rendering, offscreen content). This lets React decide which work goes first. User input is highest priority, background pre-rendering is lowest.

</details>

5. What does "Cooperative scheduling" mean?

<details>
<summary>Sample Answer</summary>

**Answer:** It means React cooperates with the browser. React breaks its work into small pieces and after each piece, gives control back to the browser — "you handle your rendering and events for now, I'll pick up my next piece when you're done." This prevents the browser from freezing and keeps the user experience smooth.

</details>
