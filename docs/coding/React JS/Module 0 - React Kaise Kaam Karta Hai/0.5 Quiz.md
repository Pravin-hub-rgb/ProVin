
## MCQ

Q: State batching ka kya matlab hai?
A. Har setState call apne aap ek alag component render trigger karti hai
B. Multiple setState calls ko group karke ek single re-render mein process karna
C. State updates ko delay karna taaki browser ko processing time mile
D. State ko local storage mein save karna taaki page refresh pe bhi bana rahe
> B. Batching means React groups multiple state updates together and does a single re-render instead of one per setState call. Isse performance improve hoti hai aur inconsistent intermediate states avoid hote hain.

---

Q: React 17 mein batching kaun si jagah automatically hoti thi?
A. Sirf event handlers ke andar — onClick, onChange, onSubmit, etc.
B. setTimeout aur setInterval callbacks ke andar
C. Promise chains aur async/await functions ke andar
D. Native DOM event listeners (addEventListener) ke andar
> A. React 17 mein batching sirf event handlers ke andar hoti thi. setTimeout, Promises, aur native events ke andar React 17 mein batching nahi hoti thi — har setState apna alag render trigger karta tha.

---

Q: React 18 ka "Automatic Batching" feature React 17 se kaise alag hai?
A. React 18 mein batching sirf click events mein hoti hai, React 17 mein sab jagah hoti thi
B. React 18 ne batching hata di — har setState ab alag render trigger karta hai
C. React 18 mein batching ab har jagah hoti hai — event handlers, setTimeout, Promises, native events
D. React 17 aur React 18 ki batching mein koi fark nahi hai — dono same tarah kaam karte hain
> C. React 17 mein batching sirf event handlers tak limited thi. React 18 introduced "Automatic Batching" — ab setTimeout, Promises, async/await, aur native event listeners sab mein batching hoti hai. React 17 mein in cases mein har setState alag render trigger karta tha.

Q: Jab ek event handler ke andar do setState calls hote hain, React internally kya karta hai?
A. Pehla setState immediately process karta hai, phir doosra — do alag renders
B. Dono updates ko ek queue mein store karta hai aur event handler khatam hote hi ek saath process karta hai
C. Sirf pehla setState leta hai, doosra ignore karta hai
D. Ek naya thread spawn karta hai aur dono updates parallel mein process karta hai
> B. React updates ko immediately process nahi karta. Woh unhe internal queue mein store karta hai. Jab current execution context (event handler, setTimeout callback) complete hota hai, tab React queue ko process karta hai — saare updates ek saath, ek single re-render.

Q: flushSync function kya karta hai?
A. State updates ko delay karta hai taaki browser pehle render complete kar sake
B. Batching ko forcefully break karta hai — update immediately process hota hai
C. Saare pending state updates ko cancel kar deta hai
D. State updates ko ek file mein save kar deta hai debugging ke liye
> B. flushSync React 18 ka function hai jo batching ko bypass karta hai. Iske andar jo setState calls hain, woh immediately process hoti hain — bina batch kiye, alag render trigger karte hain. Rare cases mein use hota hai — jaise DOM state immediately read karni ho.

Q: Batching ka sabse important fayda kya hai?
A. Code likhna zyada aasan ho jata hai kyunki setState syntax simple hai
B. Component ka state automatically localStorage mein save ho jata hai
C. Multiple state updates ek saath apply hoti hain — beech ka inconsistent state user ko nahi dikhta
D. setState ab bina curly braces ke likha ja sakta hai — boilerplate kam ho jata hai
> C. Batching ensure karta hai ki multiple updates ek saath apply hon. Agar batching na hoti, toh pehla update apply, render, doosra update apply, render — beech mein user ko half-updated UI dikh sakta hai. Batching se UI always consistent rehta hai.

Q: React 17 mein agar setTimeout ke andar do setState calls hain, toh kya hoga?
A. Do alag re-render honge kyunki setTimeout ke andar batching nahi hoti thi
B. Ek hi re-render hoga kyunki batching React 17 mein har jagah hoti thi
C. Dono setState calls ignore ho jayengi kyunki setTimeout React ke bahar hai
D. Sirf pehla setState chalega, doosra error dega
> A. React 17 mein batching sirf event handlers (onClick, onChange) ke andar hoti thi. setTimeout, Promises, aur async/await ke andar React 17 mein batching nahi hoti thi — har setState apna alag re-render trigger karta tha. Isliye React 18 ne "Automatic Batching" laaya.

Q: Batching ke context mein "inconsistent intermediate state" ka kya matlab hai?
A. State ka type number se string mein change ho jata hai beech ke render mein
B. Kuch updates apply ho chuke hain lekin baaki nahi — user ko aadhi-adhuri UI dikh sakti hai
C. Component ka state kisi aur component ke state se mismatch ho jata hai
D. Browser ki memory aur actual DOM state mein fark aa jata hai
> B. Bina batching ke har setState ek alag render trigger karta hai. Agar do setState hain — pehla render hone ke baad lekin doosra render hone se pehle, user ko incomplete UI dikhegi (jaise count update ho gaya lekin text update nahi hua). Batching ensure karta hai ki saare updates ek saath apply hon.

## TrueFalse

Q: React 18 mein batching sirf event handlers ke andar hoti hai — setTimeout aur Promises ke andar nahi hoti.
- True
- False
> False. React 18 ne "Automatic Batching" introduce kiya — ab har jagah batching hoti hai: event handlers, setTimeout, setInterval, Promises, async/await, native event listeners. React 17 mein ye limitation thi, React 18 mein nahi.

---

Q: flushSync ka use karke agar tum batching break karoge, toh performance better hogi kyunki updates immediately process ho jaate hain.
- True
- False
> False. flushSync batching break karta hai — har setState alag render trigger karta hai. Isse performance hit hoti hai kyunki multiple renders trigger hote hain. flushSync rare cases mein use karo — jaise DOM state immediately read karni ho (scrollHeight, getBoundingClientRect). General practice mein batching achhi cheez hai.

---

Q: Batching sirf performance feature hai — iska UI consistency se koi lena dena nahi hai.
- True
- False
> False. Batching do cheezein ensure karta hai — performance (kam renders = kam kaam) aur consistency (multiple updates ek saath, beech ka inconsistent state user ko nahi dikhta). Batching ke bina, agar ek event handler mein do setState calls hain, toh pehle update ke baad component render hoga jisme doosra update applied nahi hoga.

---

Q: Ek event handler ke andar 5 setState calls hain — React 5 alag re-renders karega, ek per setState.
- True
- False
> False. React saare 5 state updates ko batch karega — ek single re-render mein sab apply ho jayenge. Chahe 5 setState calls ho ya 50, event handler ke end mein ek hi render hoga. Yahi batching ka core concept hai — group karo, ek saath process karo.

## ShortAnswer

Q: React 17 aur React 18 ki batching mein kya antar hai? Example ke saath explain karo.

<details>
<summary>Sample Answer</summary>

**React 17:** Batching sirf event handlers (onClick, onChange, onSubmit) ke andar hoti thi. Baaki jagah — setTimeout, setInterval, Promises, async/await, native event listeners — har setState apna alag re-render trigger karta tha.

```jsx
// React 17
function handleClick() {
  setCount(c + 1);
  setText("Clicked");
  // ✅ Ek hi render — event handler ke andar batching hoti hai
}

setTimeout(() => {
  setCount(c + 1);
  setText("Updated");
  // ❌ Do alag render — setTimeout ke andar batching nahi hoti
}, 1000);
```

**React 18 (Automatic Batching):** Batching ab har jagah hoti hai — chahe event handler ho, setTimeout ho, Promise ho, ya native event listener.

```jsx
// React 18
setTimeout(() => {
  setCount(c + 1);
  setText("Updated");
  // ✅ Ek hi render — React 18 mein setTimeout ke andar bhi batching hoti hai
}, 1000);
```

Is change ki wajah se React 18 mein zyada consistent behavior hai — developer ko ab ye sochne ki zaroorat nahi ki "kahaan batching ho rahi hai aur kahaan nahi."

</details>

Q: flushSync kab aur kyun use karte hain? Example ke saath explain karo.

<details>
<summary>Sample Answer</summary>

**flushSync** React 18 ka function hai jo batching ko forcefully break karta hai. Iske andar jo setState calls hain, woh **immediately** process hoti hain — ek alag re-render trigger hota hai.

**Kab use karein?**
Jab tumhe state update ke immediately baad DOM ki koi property read karni ho:
- `scrollHeight`, `scrollTop`
- `getBoundingClientRect()`
- Input element ki `selectionStart`, `selectionEnd`
- Koi bhi DOM measurement jo update ke baad change ho gayi ho

```jsx
import { flushSync } from "react-dom";

function handleClick() {
  flushSync(() => {
    setCount(c => c + 1);
  });
  // Ab React immediately re-render karega
  // Yahan DOM updated hai — safe hai read karna
  console.log(element.scrollHeight);
  
  // flushSync ke bahar wali updates normal batch hongi
  setText("Done"); // Ye next render mein jayega
}
```

**Kyun avoid karein?**
flushSync extra render trigger karta hai — performance hit hoti hai. Sirf tab use karo jab genuinely zaroorat ho. General practice mein batching achhi hai.

</details>
