
## MCQ

Q: What problem did React 15's synchronous reconciliation cause?
A. State updates were not batched — every setState triggered a separate render
B. JSX needed separate Babel configuration to compile
C. The browser froze — animations lagged, typing was delayed, scrolling wasn't smooth
D. Without the `key` prop, React destroyed and rebuilt the entire list
> C. Synchronous reconciliation means once it started, it couldn't pause — the browser stayed frozen until all work was done. This caused janky animations, laggy typing, and choppy scrolling.

---

Q: What is Fiber architecture's most important feature that React 15 didn't have?
A. Breaking work into smaller pieces and pausing in between to continue later
B. Compiling JSX into browser-friendly code without Babel
C. Correctly reordering lists even without the `key` prop
D. Grouping multiple setState calls into a single render
> A. In React 15, everything happened all at once (synchronous, non-interruptible). Fiber breaks work into smaller units (work packages), and after each unit, it can check if something urgent came up, then process the next unit.

---

Q: Which data structure does Fiber architecture use that enables interruptible rendering?
A. Binary tree — each node has two children
B. Linked-list — each node is connected via child, sibling, and return pointers
C. Stack — nodes are stacked one on top of each other, processed in LIFO order
D. HashMap — each node has a unique key with O(1) lookup time
> B. Fiber uses a linked-list-based approach. Each node has three connections — child (the first child), sibling (the next sibling), and return (to go back to the parent). This structure lets React process one node, check for urgent work, then move to the next.

---

Q: In Fiber architecture, what is the difference between the Render phase and the Commit phase?
A. Render phase is for mobile devices, Commit phase is for desktop
B. Render phase calculates DOM changes (interruptible), Commit phase applies them (not interruptible)
C. Render phase processes event handlers, Commit phase applies state updates
D. Render phase is asynchronous, Commit phase is synchronous — both are interruptible
> B. In the Render phase (Reconciliation phase), the Virtual DOM is traversed and changes are calculated — this is interruptible and doesn't modify the DOM. In the Commit phase, the calculated changes are applied to the real DOM — this is not interruptible.

---

Q: Which priority level is the highest in Fiber architecture?
A. Normal — regular state updates, data fetching, general rendering
B. High — animations, transitions, visual feedback
C. Immediate — user input, click events, typing
D. Low — pre-rendering, offscreen content, background tasks
> C. Immediate priority is the highest — user input, click events, typing. React ensures user interactions are processed first, then animations, then normal updates, and lastly background tasks.

Q: What does "Cooperative scheduling" mean?
A. React does all the work at once and gives the browser control only at the end
B. React doesn't give the browser control — it freezes the browser until all work is done
C. React breaks its work into small pieces and gives control back to the browser after each piece
D. React and the browser work in parallel on different CPU cores
> C. React cooperates with the browser — it breaks its work into small pieces, processes one piece, then gives control back to the browser (so the browser can do its rendering and event handling), then picks up the next piece. This prevents the browser from freezing.

---

Q: Which statement about Fiber architecture is correct?
A. Fiber is a new React syntax that makes developers write code in a different style
B. Fiber is an internal implementation change — the API stays the same, developers write nothing differently
C. Fiber works only with class components and ignores functional components
D. Fiber is a third-party library that needs to be installed alongside React
> B. Fiber is an internal change to React's engine — a complete rewrite of the reconciliation engine introduced in React 16. Developers write exactly the same code — same `useState`, same `useEffect`, same components. React just became faster and interruptible.

---

Q: Which problem did Fiber architecture NOT solve?
A. The synchronous reconciliation problem — the browser was freezing
B. Breaking work into smaller pieces for interruptible rendering
C. Priority-based rendering — user input first, background tasks later
D. JSX compilation — running JSX without Babel
> D. JSX compilation has nothing to do with Fiber. JSX is compiled by Babel; Fiber only changes the reconciliation and rendering engine. The other three problems were all solved by Fiber.

## TrueFalse

Q: Fiber architecture existed in React 15, and React 16 just improved it.
- True
- False
> False. React 15 had synchronous reconciliation (no Fiber). Fiber was introduced in React 16 as a completely new reconciliation engine. React 15 processed the tree recursively, while Fiber uses a linked-list-based approach.

---

Q: During the Render phase, DOM changes are calculated and the phase is interruptible — you can pause it midway.
- True
- False
> True. The Render phase (aka Reconciliation phase) only does calculations — the actual DOM doesn't change yet. Since it's interruptible, you can pause and resume later (to handle urgent work first). The Commit phase (where real DOM updates happen) is NOT interruptible.

---

Q: Fiber architecture makes React completely asynchronous — all work runs on a background thread.
- True
- False
> False. Fiber is NOT asynchronous rendering — it's cooperative scheduling (the foundation of concurrent mode). All work happens on the main thread, but it's broken into small pieces so the browser doesn't freeze.

---

Q: The Commit phase calls lifecycle methods (like useEffect) and this phase is not interruptible.
- True
- False
> True. The Commit phase starts when React is sure about which changes to apply. Once the commit begins, it can't be paused — all DOM updates and lifecycle methods (`componentDidMount`, `useEffect`) execute together.

## ShortAnswer

Q: What problem did synchronous reconciliation cause, and how did Fiber solve it?

<details>
<summary>Sample Answer</summary>

**Problem:** In React 15, reconciliation was synchronous — once it started, it couldn't be paused. Until the entire Virtual DOM tree was compared, the browser stayed frozen. Even 50ms of reconciliation meant the browser couldn't run animations, typing lagged, and scrolling wasn't smooth.

**Solution — Fiber Architecture:**

1. **Break work into smaller pieces:** Fiber divides work into units (work packages). Each unit is small enough to complete within a single browser frame (16ms).

2. **Interruptible:** After each unit, React can check — "did something urgent come up?" If yes (user click, typing), it handles that first, then continues with the remaining Fiber work.

3. **Priority levels:** React can decide — user input first, then animations, then normal updates, then background tasks.

4. **Linked-list structure:** The Fiber tree is connected via a linked list (child, sibling, return pointers). This lets React process one node, check for interruptions, then move to the next.

</details>

Q: What is the difference between the Render phase and the Commit phase? Explain the characteristics of each.

<details>
<summary>Sample Answer</summary>

**Render Phase (Reconciliation Phase):**
- The Virtual DOM tree is traversed
- Changes are calculated (diffing)
- **Interruptible** — you can pause it midway
- **Side-effect free** — the actual DOM doesn't change yet
- Can span multiple frames

**Commit Phase:**
- The calculated changes are applied to the real DOM
- **Not interruptible** — once you start, you have to finish
- Lifecycle methods are called (`componentDidMount`, `useEffect`)
- Completes within a single frame
- DOM mutations, refs, and effects are all handled here

**Analogy:** Think of writing an essay. The Render phase is like drafting — deciding on changes, editing, pausing to think. The Commit phase is like printing the final copy — once the printer starts, you can't stop halfway.

</details>
