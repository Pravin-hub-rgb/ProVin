Q: React Router mein navigation enable karne ke liye component tree ke top-level par kaunsa component wrap karna padta hai?

B. `<BrowserRouter>` — routing context provide karta hai poore app ko

> B. BrowserRouter (ya HashRouter) sabse upar wrap hota hai taaki routing context available ho. A galat — Routes is a container for Route components, router nahi. C galat — Route ek single mapping hai, wrapper nahi. D galat — Link ek navigation element hai, context provider nahi.

## TrueFalse

Q: `<BrowserRouter>` HTML5 history API ka istemal karta hai URLs manage karne ke liye.
- True
- False
> True. BrowserRouter window.location aur HTML5 history API (pushState, popState) use karta hai. Isliye clean URLs milte hain jaise /about, /contact.

---

Q: `<Link>` component page refresh trigger karta hai jab user click kare.
- True
- False
> False. Link `<a>` tag render karta hai but default behavior prevent karta hai (event.preventDefault). Sirf React Router ke history mechanism se URL change hota hai — koi page reload nahi hota.

---

Q: `navigate(-1)` user ko browser history mein ek step peeche le jaata hai.
- True
- False
> True. Negative value history stack mein back jaane ke liye use hoti hai. navigate(-1) browser ke back button ke barabar hai.

---

Q: `<Routes>` component har URL ke liye saare matching Route components render karta hai.
- True
- False
> False. Routes sirf pehla matching Route render karta hai. Ek time pe sirf ek Route ka element active hota hai.

Q: React Router v6 mein `<Route path="/about" component={About} />` syntax kaam karta hai.
- True
- False
> False. v6 mein `component` prop remove ho gaya. Ab `element={<About />}` syntax use hota hai.

## ShortAnswer

Q: `<BrowserRouter>` aur `<HashRouter>` mein kya fark hai? Kab kaunsa use karna chahiye?

<details>
<summary>Sample Answer</summary>

**BrowserRouter** HTML5 History API (pushState, popState) use karta hai. Iske URLs real paths hote hain — jaise `/about`, `/contact`. Production apps ke liye yeh better hai kyunki URLs clean lagte hain. Lekin server ko configure karna padta hai ki har route pe same `index.html` serve kare (nahi toh refresh karne par 404 aayega).

**HashRouter** URL hash (`#`) use karta hai — jaise `/#/about`, `/#/contact`. Hash ke baad ka part server tak nahi jaata, isliye kisi server configuration ki zaroorat nahi. Yeh un environments mein kaam aata hai jahan server control nahi hai — jaise GitHub Pages, Sandpack, ya static hosting.

Kab kaunsa:
- Production app with server control → BrowserRouter (clean URLs)
- Static hosting / iframe / no server control → HashRouter
- Development / prototyping — koi bhi chalega
</details>

Q: `useNavigate` aur `<Link>` dono navigation kar sakte hain. Kab kaunsa use karna chahiye? Examples ke saath explain karo.

<details>
<summary>Sample Answer</summary>

**Link** declarative hai — JSX mein directly likh dete ho ki "yeh element click karne par X path pe jaayega". Ye tab use karo jab navigation kisi clickable UI element se trigger ho rahi ho jo hamesha dikhega. Jaise:
- Navbar mein links
- 404 page mein "Go to Home" link
- Kisi bhi card ya button ka clickable link

**useNavigate** programmatic hai — code se call karte ho. Ye tab use karo jab navigation kisi event ya condition ke baad honi chahiye jo direct click nahi hai. Jaise:
- Form submit karne ke baad redirect
- API call successful hone ke baad navigate
- Timer/interval ke baad navigate
- navigate(-1) back button behavior

```tsx
// Link example — declarative, UI mein dikhta hai
<Link to="/dashboard">Dashboard</Link>

// useNavigate example — programmatic, code ke baad
function handleSubmit() {
  await saveData(formData);
  navigate("/success");
}
```

Rule of thumb: agar navigation ka trigger UI ka permanent part hai → Link. Agar code ki logic ke baad navigate karna hai → useNavigate.
</details>

Q: 404 page banane ke liye `path="*"` use karte hain. Isko hamesha Routes ke end mein kyun rakhna chahiye?

<details>
<summary>Sample Answer</summary>

Routes component sequentially (top se bottom) path match karta hai aur **pehla match milte hi render kar deta hai**. Agar `path="*"` ko pehle rakha gaya, toh woh har URL se match karega (kyunki * ka matlab "kuch bhi") — chahe URL `/about` ho ya `/contact`. Iski wajah se specific routes (jaise `/about`, `/contact`) kabhi render nahi honge, kyunki Routes un tak pahunchne se pehle hi * route match kar lega.

```tsx
{/* ✅ Sahi — specific routes pehle, * last mein */}
<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/about" element={<About />} />
  <Route path="*" element={<NotFound />} />
</Routes>

{/* ❌ Galat — * pehle hai, specific routes kabhi nahi chalenge */}
<Routes>
  <Route path="*" element={<NotFound />} />
  <Route path="/" element={<Home />} />
  <Route path="/about" element={<About />} />
</Routes>
```

Isliye rule hai: **specific paths first, catch-all (*) last**. Isko "route ordering" kehte hain.
</details>
