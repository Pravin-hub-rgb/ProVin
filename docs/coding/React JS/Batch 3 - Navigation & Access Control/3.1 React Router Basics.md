## Where We Left Off

In 2.7, we built To-Do App v2 — Context API for the theme toggle, useEffect for categories, useRef for auto-focus. It worked well, but it had one limit: everything lived on **one screen**. The user clicked from one part of the app to another, but nothing actually moved — everything rendered on the same page. There was no way to go "somewhere else".

Real apps are not like that. They have a home page, a list page, a details page, a login page. So the next question is: how do we move between them? That is what this module is about.

## What Is Navigation?

**Navigation** means moving from one place in an app to another. You click something, you land somewhere new, and the address in the browser tells you where you are.

Picture a library website:

- `/` is the home page.
- `/library` shows all the books.
- `/library/1` shows the details of book number 1.

Our goal in this module is to build exactly that in React: click a book, land on `/library/1`, and see that book.

Before we build it, we need to remember how websites have always done this. React does it differently, and that difference is the whole reason React Router exists.

## How Navigation Worked Before React: The `<a>` Tag

You already know this one from HTML:

```html
<a href="/library/1">Book 1</a>
```

When you click it, three things happen:

1. The browser sends a request to the server.
2. The server sends back a brand new HTML page.
3. The browser throws away the old page and shows the new one.

This is a **full page reload**. The screen flashes, and everything that was in memory is lost: typed text, open menus, React state.

For an old-style website, that is perfectly fine — because every page really is a separate HTML file waiting on the server.

But a React app is not built that way. So what is it built like?

## How a React App Is Built: One Page, Many Components

A React app has only one HTML file, `index.html`, with one empty box in it:

```html
<div id="root"></div>
```

React draws the entire app inside that box. So a React app is one page, loaded once. That is what **SPA (Single Page Application)** means.

Here is the picture to keep in your head. A normal website is like a book: each page is a separate sheet, and following a link means the server hands you a different sheet. A React app is like a picture frame: there is only one frame, and React swaps what is inside it.

So "going to a new page" in React does not mean getting a new HTML file. It means taking one component out of the frame and putting another one in.

In our library, the app might look like this:

```
<App>
  <Navbar />          {/* always visible at the top */}
  <BooksList />       {/* shown on /library */}
  <BookDetails />     {/* shown on /library/1 */}
</App>
```

When the user goes from `/library` to `/library/1`, we only want to swap `<BooksList />` for `<BookDetails />`. The `<Navbar />` should stay exactly as it is — and so should any state in the app. That is why React apps feel fast and smooth.

That sounds great. So what happens if we simply use the `<a>` tag we already know?

## What Goes Wrong When We Use `<a>` in React

Suppose the book links inside `<BooksList />` are plain `<a>` tags.

The user clicks "Book 1", and the browser does what `<a>` always does: it asks the server for a new page and reloads everything. The `<Navbar />` is destroyed and rebuilt, all state resets, and the screen flashes. Our single page app has just behaved like an old website.

So `<a>` cannot give us two things that we need:

1. A way to change the URL without reloading the page.
2. A way to show the right component for each URL.

React itself does not give us either one. It only draws components. So the real question becomes: who is going to handle the URL?

## Could We Handle the URL Ourselves?

Yes. React is a library, and it is only responsible for drawing the UI. It has no routing built in, so nothing stops you from writing your own. The idea is small: read the current address, change it with the browser's History API when a link is clicked, and show a component based on it.

```tsx
import { useState } from "react";

function App() {
  const [path, setPath] = useState(window.location.pathname);

  function go(to: string) {
    window.history.pushState({}, "", to); // change the URL, no reload
    setPath(to);                          // tell React to redraw
  }

  return (
    <>
      <button onClick={() => go("/")}>Home</button>
      <button onClick={() => go("/about")}>About</button>
      {path === "/" && <Home />}
      {path === "/about" && <About />}
    </>
  );
}
```

For two pages, this works. But a real app quickly needs much more:

- The back and forward buttons (you must listen for them yourself).
- Dynamic paths like `/library/1`, `/library/2`, `/library/3`.
- Nested layouts, where a navbar stays while only the inside changes.
- A 404 page and redirects.
- Active link styling for the current page.
- Links that still behave properly when opened in a new tab.

Building and testing all that for every project would be slow and error-prone. So developers do what they do with many other problems: they use a library that already solved it.

## So We Use a Library: React Router

Think of React as a puzzle piece that draws the UI. Other libraries are other pieces that snap in for other jobs, and routing is one of those jobs. The piece we will use is React Router.

**Why React Router?**

It is one of the most widely used routing libraries for React, so you will meet it in tutorials, jobs and existing projects. It is also beginner friendly, because routes are just components and hooks that you already know how to read. And the ideas you learn here — URL decides component, links change the URL without reloading — carry over to every other router.

Notice what it really is, though: it is the "write it ourselves" code from the last section, written by someone else, tested by thousands of projects for years, and grown to cover every item on that pain list. We are not learning magic. We are learning our own idea, maintained.

**Is it the only puzzle piece?**

No. There are other options, and it is useful to know their names:

- **TanStack Router**: a newer router that is very strict about types.
- **Wouter**: a very small and simple router.
- **Next.js**: a full framework where your folder structure becomes your URLs, so routing is built in.

They look different, but they all solve the same two problems from the `<a>` section. Learn one well and the others feel familiar.

**What does React Router actually do?**

It fakes the trip. When the user clicks a link, the address bar changes to `/library/1`, but nothing is fetched from the server. React Router reads the new address and swaps in the matching component. The user sees a new page, but nothing reloaded.

The URL is just a label. React Router's whole job is to read that label and decide which component belongs in the frame.

The browser's back and forward buttons keep working, refreshing keeps you on the same "page", and links never reload the app. It feels multi-page, but it is really one page.

It does this with four tools, and each solves one piece of the problem:

1. **BrowserRouter**: watches the URL and shares it with the app.
2. **Routes and Route**: the map from URL to component (`/library` shows `<BooksList />`).
3. **Link and NavLink**: clickable links that change the URL without reloading, replacing `<a>`.
4. **useNavigate**: moving to another URL from code, for example after a login.

Let us set it up and meet them one by one, in the order they depend on each other.

## Step 1 — Installation

First, add the library to the project:

```bash
npm install react-router-dom
```

(Use `bun add react-router-dom` or `pnpm add react-router-dom` if that is your package manager. Same package.)

This course uses **v6**. In `package.json` you should see `"react-router-dom": "^6.x"`. Everything is done with components and hooks.

**Note:** v7 exists too. It has the same ideas, and the imports come from `"react-router"` instead (`react-router-dom` still works). Everything you learn here carries over.

With the library installed, the first tool to meet is the one that everything else depends on.

## Step 2 — Tool 1: BrowserRouter (The Watcher)

In our library, before a link can turn `/library` into `/library/1` without a reload, something must be watching the URL. That watcher is `<BrowserRouter>`, and it must sit above everything that uses routing:

```tsx
// main.tsx
import { BrowserRouter } from "react-router-dom";

ReactDOM.createRoot(document.getElementById("root")!).render(
  <React.StrictMode>
    <BrowserRouter>
      <App />
    </BrowserRouter>
  </React.StrictMode>,
);
```

**Why is it in `main.tsx` here?**

Because `main.tsx` is the file that boots the app — `createRoot` and `<React.StrictMode>` live there. A provider that the *entire* app needs belongs next to them: wrap `<App />` there and everything below it is inside the routing context from the very first render. (StrictMode has nothing to do with routing — the two are just neighbors in the same file.)

But "must be in `main.tsx`" is **not** a rule. The only rule is "above everything that uses routing" — and `App.tsx` works too (the mini-project at the end of this file puts BrowserRouter inside App.tsx instead). We'll compare both placements properly in Step 3.

**What does it actually do?**

BrowserRouter is a provider, just like Context's provider. It does two jobs:

1. It watches the URL (using the browser's History API).
2. It shares the current URL with everything inside it, so Routes, Link and useNavigate can work.

This gives you clean URLs like `/about` and `/contact`.

**Why must it wrap the app?**

Because it is a provider, only components inside it can reach the routing information. If you put a component with a `<Link>` outside BrowserRouter (for example, a sibling of it in `main.tsx`), React Router throws an error like `Link may be used only in the context of a Router component`.

It is not about where the link sits in the file. It is about whether the component is rendered inside BrowserRouter.

**Other routers (you will rarely need them)**

- **HashRouter**: puts the route after a `#` (`/#/about`). The server never sees that part, so it is useful on static hosts where you cannot set up a server fallback.
- **MemoryRouter**: keeps the URL in memory instead of the address bar. Mostly used for tests.
- **createBrowserRouter + RouterProvider**: the newer "data router" style that supports loaders and actions. BrowserRouter is perfect for learning and simple apps.

**Does BrowserRouter talk to the server?**

This is the part that is easy to get wrong, so let us be precise:

- Clicking a `<Link>`: **no request** to the server. React Router changes the URL and swaps the component.
- Typing `/about` directly or refreshing on it: the browser **does ask the server** for `/about`. If the server only knows `index.html`, it returns a 404.

That is why in production you must configure the server to return `index.html` for every route, so React Router can take over. In development, Vite already does this for you.

Now the URL is being watched. But watching is not enough: something has to say which component goes with which URL.

## Step 3 — Tool 2: Routes and Route (The Map)

In our library, this is the map that says `/library` shows `<BooksList />` and `/library/1` shows `<BookDetails />`. `<Routes>` is the container, and each `<Route>` maps one path to one component:

```tsx
import { Routes, Route } from "react-router-dom";

function App() {
  return (
    <Routes>
      <Route path="/" element={<Home />} />
      <Route path="/about" element={<About />} />
      <Route path="/contact" element={<Contact />} />
    </Routes>
  );
}
```

**How it works:**

1. The URL becomes `/about`.
2. React Router compares it with each Route's path.
3. The matching Route's element renders. `<Home />` and `<Contact />` do not.

Only one route's element is shown at a time.

**Where does this code live — `main.tsx` or `App.tsx`?**

Fair question, because both files have already shown up. The rule is simple:

`<Routes>` is a component like any other, so it lives wherever your page content lives — and in a Vite app, that place is `App.tsx`. App is the layout root: navbar at the top, page area below it, and `<Routes>` is what fills that page area. That is why `App.tsx` is the standard home for Routes.

The one **hard** rule is about BrowserRouter, not Routes: anything that uses routing — `<Routes>`, `<Link>`, `useNavigate` — must be rendered **inside** `<BrowserRouter>`. Both of these setups satisfy that rule, so both work:

```tsx
// Setup 1 — provider in main.tsx, Routes in App.tsx
// main.tsx
<BrowserRouter>
  <App />
</BrowserRouter>
// App.tsx — App is INSIDE the provider, so Routes in App is fine
<Routes>
  <Route path="/" element={<Home />} />
</Routes>
```

```tsx
// Setup 2 — everything in App.tsx (the mini-project below does this)
// App.tsx renders the provider itself, Routes inside it
<BrowserRouter>
  <nav>...</nav>
  <Routes>
    <Route path="/" element={<Home />} />
  </Routes>
</BrowserRouter>
```

What breaks is rendering routing components as **siblings** of the provider instead of children:

```tsx
// ❌ Broken — App is OUTSIDE the provider
<BrowserRouter>
  <div>nothing routing-related in here</div>
</BrowserRouter>
<App />   {/* ❌ App's <Routes>/<Link> throw: no router context */}
```

It is the same "provider above everything" idea from Step 2 — the error to expect is `useRoutes() may be used only in the context of a <Router> component`.

So: pick a setup, stay consistent. Setup 2 keeps all router code in one file, which is nice while learning — that's what the mini-project below does. In bigger apps, developers sometimes move the `<Routes>` block into its own component (like `AppRoutes.tsx`) just to keep App small — same rule applies there too: it must render inside the provider.

**The 404 page: `path="*"`**

What if the user types a URL that matches nothing? `*` means "anything that did not match above", and it is used for a Not Found page:

```tsx
<Route path="*" element={<NotFound />} />
```

By habit, put it last. (In v6, React Router picks the **best** match rather than the first one, so the order is not strictly required — but last is the clearest and safest convention.)

So now the URL is watched and mapped to components. The last missing piece is the one the user actually touches: the link.

## Step 4 — Tool 3: Link (Replacing `<a>`)

These are the book links inside `<BooksList />`. They must change the URL without the full reload that `<a>` causes. For that, React Router gives us `<Link>`:

```tsx
import { Link } from "react-router-dom";

function Navbar() {
  return (
    <nav>
      <Link to="/">Home</Link>
      <Link to="/about">About</Link>
      <Link to="/contact">Contact</Link>
    </nav>
  );
}
```

Note that `<Link>` uses `to`, not `href`.

**What is the difference between `<a>` and `<Link>`?**

- `<a>` is built into HTML. Click it and the browser requests a new page from the server (full reload). It works anywhere and needs no router.
- `<Link>` is a React Router component. Under the hood it still renders an `<a>` tag, but on click it calls `event.preventDefault()` to stop the reload, changes the URL, and tells the router. React then swaps the component. CSS works on it just like on any `<a>`.

**The walkie-talkie picture**

`<Link>` is one radio, and `<BrowserRouter>` is the other. When you click a Link, it shouts "the URL is now `/library/1`!" — BrowserRouter hears it and tells Routes which component to show. With no BrowserRouter above it, the Link has nobody to talk to, so it throws an error. This is the connection between tools 1, 2 and 3.

**Use `<a>` for outside links**

For links to other websites (`https://google.com`), use a normal `<a>`. React Router only handles navigation inside your app.

Link does the job, but a navbar usually wants a little more: it should show which page you are on.

## Step 5 — Tool 3b: NavLink (A Link That Knows Where You Are)

`<NavLink>` is `<Link>` with an extra ability: it knows whether its `to` matches the current URL. That makes it perfect for highlighting the current tab in a navbar.

```tsx
import { NavLink } from "react-router-dom";

function Navbar() {
  return (
    <nav>
      <NavLink
        to="/"
        className={({ isActive }) => (isActive ? "nav-link active" : "nav-link")}
      >
        Home
      </NavLink>
      <NavLink
        to="/movies"
        className={({ isActive }) => (isActive ? "nav-link active" : "nav-link")}
      >
        Movies
      </NavLink>
    </nav>
  );
}
```

`isActive` is a boolean that NavLink passes in automatically. It is `true` when this link's route is the current one. Then style it in CSS:

```css
.nav-link { color: gray; text-decoration: none; }
.nav-link.active { color: blue; font-weight: bold; }
```

(NavLink also adds an `active` class by default, so a simple `.active` style works too.)

So far, every move between pages has started with a click on a visible link. But sometimes the app itself should decide to move.

## Step 6 — Tool 4: useNavigate (Navigating From Code)

Think of a login form. The user clicks "Login", the app checks the password, and only if it succeeds should it move to the dashboard. There is no link to click. `<Link>` cannot do this, but the `useNavigate` hook can: it gives you a function you call from code.

```tsx
import { useNavigate } from "react-router-dom";

function LoginPage() {
  const navigate = useNavigate();

  function handleLogin() {
    // ...login logic...
    navigate("/dashboard"); // go to the dashboard after login
  }

  return <button onClick={handleLogin}>Login</button>;
}
```

**Common patterns:**

```tsx
navigate("/about");                    // push a new history entry
navigate("/about", { replace: true }); // replace the current entry instead
navigate(-1);                          // go back one step
navigate(2);                           // go forward two steps
```

Use `replace: true` when the user should not be able to press Back and return to the current page. A classic example is login: after logging in, Back should not take them to the login form again.

**Related:** there is also a `<Navigate to="/login" />` component (with a capital N) that redirects automatically when it renders. You will see it in protected routes later.

We now have several ways to move around, so let us line them up.

## Which One Should I Use?

- `<a href>`: links to other websites, or when you really want a full reload.
- `<Link to>`: normal links between pages inside your app.
- `<NavLink to>`: navbar links that should look different when active.
- `useNavigate()`: navigate from code, after an action such as a submit, login or API call.
- `<Navigate to>`: redirect automatically while rendering.

## Mini-Project: Movie Browser (Part 1 — Home Page)

We'll build this mini-project in two parts. Part 1 (here) — home page with a movie list and links. Part 2 (3.2) — movie detail page with dynamic routes.

### Step 1 — Movie Data + Home Page Component

First, a simple movie list component:

```tsx
// components/MovieList.tsx
import { Link } from "react-router-dom";

const movies = [
  { id: "tt1375666", title: "Inception", year: 2010 },
  { id: "tt0816692", title: "Interstellar", year: 2014 },
  { id: "tt0133093", title: "The Matrix", year: 1999 },
  { id: "tt0167260", title: "The Lord of the Rings: The Return of the King", year: 2003 },
  { id: "tt0111161", title: "The Shawshank Redemption", year: 1994 },
];

export default function MovieList() {
  return (
    <div>
      <h1>🍿 Movie Browser</h1>
      <div className="movie-grid">
        {movies.map((movie) => (
          <div key={movie.id} className="movie-card">
            <h3>{movie.title}</h3>
            <p>{movie.year}</p>
            <Link to={`/movies/${movie.id}`}>View Details →</Link>

        ))}

```

Notice the dynamic path in `` <Link to={`/movies/${movie.id}`}> ``. Each movie gets its own detail page, and this path will be captured by `useParams` in 3.2.

### Step 2 — App.tsx with Router Setup

```tsx
// App.tsx
import { BrowserRouter, Routes, Route, Link } from "react-router-dom";
import MovieList from "./components/MovieList";

function HomePage() {
  return (
    <div>
      <h2>Welcome to Movie Browser</h2>
      <p>Browse our collection of classic movies.</p>
    </div>
  );
}

export default function App() {
  return (
    <BrowserRouter>
      <div className="app">
        <nav>
          <Link to="/">Home</Link>
          <Link to="/movies">Movies</Link>
        </nav>
        <Routes>
          <Route path="/" element={<HomePage />} />
          <Route path="/movies" element={<MovieList />} />
          <Route path="*" element={<h2>404 — Page not found</h2>} />
        </Routes>
      </div>
    </BrowserRouter>
  );
}
```

**Why `<BrowserRouter>` inside App?** Some developers wrap it in `main.tsx`, others in App.tsx. Both work — the difference is scope. If you wrap it in App, all router-related code stays together. It depends on your project structure.

## What It Is NOT

- **React Router is not server-side routing** — it's client-side. The URL changes but no server request is made (when clicking a Link — the refresh/direct-URL case is the one exception, covered in Step 2).
- **`<Link>` still renders an `<a>` tag** — it just overrides the default behavior. CSS styling works the same as a normal `<a>`.
- **React Router doesn't make the app multi-page** — it's still a single page (SPA) that *feels* multi-page. That's what "Single Page Application" means.
- **The router must be at the top of the component tree** — BrowserRouter needs to be above all Routes, Links, and useNavigate calls, or they won't work.
- **React Router is not the only router** — TanStack Router, Wouter, and Next.js's built-in routing all solve the same two problems. We pick React Router for popularity and beginner friendliness; the ideas transfer everywhere.

## In Your Own Words

<details>
<summary>Why use React Router instead of plain `<a>` tags?</summary>

A plain `<a>` tag triggers a full page reload — the browser fetches a new HTML page from the server, the React app's entire state resets, and there's a flash (blank screen) during load. React Router's `<Link>` component does a client-side component swap — state is preserved, no reload, and transitions are smooth.
</details>

<details>
<summary>What does `<BrowserRouter>` do, and why must it wrap the app?</summary>

BrowserRouter is a provider component that gives React Router information about browser URL changes. It listens to `window.location` and the HTML5 History API — when the URL changes, it triggers a re-render of the matching `Routes`. Without a router at the top, `Routes`, `Link`, and `useNavigate` can't work because the routing context wouldn't exist.
</details>

<details>
<summary>What does `path="*"` match, and where should it go?</summary>

`*` matches any URL that didn't match any other Route. It's used for 404 pages. In v6, matching is ranked by specificity — the `*` route has the lowest rank, so it only matches when nothing more specific does, no matter where you place it. Putting it last is simply the clearest and safest convention.
</details>

<details>
<summary>What's the difference between `useNavigate` and `<Link>`? When use which?</summary>

`<Link>` is a component — it handles click events on visible links. `useNavigate` is a hook — it returns a function you call from code (event handlers, async callbacks, timers). Use `<Link>` when the navigation is a visible link in your UI. Use `useNavigate()` when the navigation happens after an action — form submit, API response, timeout.
</details>

<details>
<summary>What does `<NavLink>` provide that `<Link>` doesn't? What is `isActive`?</summary>

`<NavLink>` is `<Link>`'s enhanced version — it automatically detects whether its `to` matches the current URL. `isActive` is a boolean that gets passed to the `className` or `style` function — `true` means this NavLink's route is the current route. You use it to apply an "active" style, like bold or a different color, so the navigation highlights the current page.
</details>

<details>
<summary>Could you build routing yourself, without React Router? What would you have to build?</summary>

Yes — React has no routing built in, so nothing stops you. The core is small: read `window.location.pathname`, call `history.pushState` on click, and render a component based on the path. But a real app also needs the back/forward buttons (you'd listen for them yourself), dynamic paths like `/library/1`, nested layouts, a 404 page, active link styling, and new-tab behavior. Building and testing all of that for every project is slow and error-prone — React Router is exactly that logic, maintained and hardened by years of use. Alternatives like TanStack Router, Wouter, or Next.js's built-in routing solve the same problems with the same ideas.
</details>

## Cheat Sheet (Quick Recall)

**The problem:** one HTML file = one screen; every `<a>` click is a full page reload that destroys state. React only draws components — nobody handles the URL.

**The fix — react-router-dom:** URLs select components instead of pages. History works, refresh keeps you where you are, no reloads ever. (DIY routing is possible — `location` + `pushState` — but React Router is that logic, maintained.)

**Setup (once):** `npm install react-router-dom` → wrap `<BrowserRouter>` around the app → declare `<Routes>` → each path is a `<Route>`.

```tsx
import { BrowserRouter, Routes, Route, Link } from "react-router-dom";

// BrowserRouter wraps the entire app
<BrowserRouter>
  <Routes>
    <Route path="/" element={<Home />} />
    <Route path="/about" element={<About />} />
  </Routes>
</BrowserRouter>

// Use Link instead of <a> - no page reload
<Link to="/about">About</Link>

// Programmatic navigation
const navigate = useNavigate();
navigate("/about");       // push
navigate("/about", { replace: true });  // replace history
navigate(-1);             // back (history stack)

// NavLink - styling for active route
<NavLink to="/" className={({ isActive }) => isActive ? "active" : ""}>
  Home
</NavLink>
```

**Which tool:** `<a>` for external sites · `<Link>` for internal pages · `<NavLink>` for active-styled navbar links · `useNavigate()` for navigation from code · `<Navigate>` for automatic redirects while rendering.
