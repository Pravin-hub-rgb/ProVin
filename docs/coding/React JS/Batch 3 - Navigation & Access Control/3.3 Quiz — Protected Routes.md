
## MCQ

Q: Why use a guard pattern (`if (!ctx) throw Error`) in a context consumer custom hook?
A. To trigger an error boundary
B. To throw an error when the hook is used outside its Provider
C. To avoid TypeScript warnings
D. To force a component re-render
> B. If the context is `undefined` (used outside its Provider), the guard throws a clear error message. A is wrong because error boundaries are a separate React feature. C is wrong because guards produce runtime errors, not compile-time warnings. D is wrong because guards don't trigger re-renders.

## TrueFalse

Q: `<Navigate>` immediately triggers a redirect when rendered, without user interaction.
- True
- False
> True: Navigate is declarative — as soon as it renders, the redirect fires. You use it with a condition in the render: "if user is null, render this."

---

Q: `useNavigate` can only be called inside event handlers.
- True
- False
> False: useNavigate can be called anywhere in the component — event handlers, `useEffect`, callbacks, timers. The only requirement is being inside a Router.

---

Q: Using `<Navigate>` without `replace` can create a back-button redirect loop.
- True
- False
> True: Without `replace`, a new history entry is pushed. Pressing back returns to the guarded page, which redirects again — creating a loop. `replace` prevents this by replacing the entry instead of pushing.

---

Q: Context providers must be inside BrowserRouter because guard components use `<Navigate>` which requires Router context.
- True
- False
> True: `<Navigate>` uses the Router context internally. If the auth provider is outside the Router, the guard's Navigate can't access routing context and throws an error.

## ShortAnswer

Q: What is the difference between `<Navigate>` and `useNavigate`? When would you use each? Give a code example.

<details>
<summary>Sample Answer</summary>

Both handle redirects, but in different ways:

**`<Navigate />` — Declarative (in JSX):**

```tsx
// Used when the redirect is a render condition
function ProtectedRoute({ children }) {
  const { user } = useAuth();
  if (!user) return <Navigate to="/login" replace />;
  return <>{children}</>;
}
```

**`useNavigate()` — Programmatic (in code):**

```tsx
// Used when redirect happens after an event or async action
function LoginPage() {
  const { login } = useAuth();
  const navigate = useNavigate();

  function handleLogin() {
    login("DemoUser");
    navigate("/", { replace: true });
  }

  return <button onClick={handleLogin}>Login</button>;
}
```

**When to use each:**
- `<Navigate />` — JSX conditional rendering (auth guards, feature flags)
- `useNavigate()` — event handlers, after form submit, after API response, timers

**Simple rule:** If the redirect is part of what gets rendered → `<Navigate />`. If the redirect happens from a code event → `useNavigate()`.

</details>

Q: Explain the wrapper/guard component pattern for protected routes. How does the `children` prop work here, and why is it better than inline checks in each page?

<details>
<summary>Sample Answer</summary>

The guard component pattern wraps protected content and checks authentication before rendering:

```tsx
interface ProtectedRouteProps {
  children: ReactNode;
}

export default function ProtectedRoute({ children }: ProtectedRouteProps) {
  const { user } = useAuth();

  // Not logged in → redirect to login
  if (!user) {
    return <Navigate to="/login" replace />;
  }

  // Logged in → render the protected content
  return <>{children}</>;
}
```

**How `children` works:**
- The protected page passes itself as `children`: `<ProtectedRoute><Dashboard /></ProtectedRoute>`
- The guard checks auth — if valid, it renders `{children}` (the Dashboard)
- If invalid, it renders `<Navigate>` instead (redirect)

**Why this is better than inline checks:**
1. **Reusable** — Write the guard once, wrap any component
2. **DRY** — Auth logic lives in one place, not duplicated in every page
3. **Consistent** — Every protected route uses the same redirect target and behavior
4. **Maintainable** — Change the login path or add logic in one place

Without the guard, each page would repeat the same `if (!user) navigate("/login")` logic. The wrapper abstracts that into a single component.

</details>

Q: Why does `AuthProvider` need to be inside `BrowserRouter`? What error occurs if you put it outside?

<details>
<summary>Sample Answer</summary>

`AuthProvider` needs to be inside `BrowserRouter` because the `ProtectedRoute` component uses `<Navigate />` for redirects, and `<Navigate>` internally requires the Router context (which `BrowserRouter` provides).

If `AuthProvider` is placed outside `BrowserRouter`, the `ProtectedRoute` component — which sits inside the Router tree — calls `<Navigate />`. But `Navigate` tries to access the nearest Router context, finds none, and throws:

```
useNavigate() may be used only in the context of a <Router> component.
```

The provider order must be:

```tsx
<BrowserRouter>          {/* 1. Router context at the top */}
  <AuthProvider>        {/* 2. Auth context inside Router */}
    <Routes>            {/* 3. Routes get both contexts */}
      <Route path="/dashboard" element={
        <ProtectedRoute><Dashboard /></ProtectedRoute>  {/* Uses both auth + Navigate */}
      } />
    </Routes>
  </AuthProvider>
</BrowserRouter>
```

The key insight: any component that uses `<Navigate />` or `useNavigate()` must be rendered inside the Router tree. Since `ProtectedRoute` does both, its entire context (including `AuthProvider`) must be inside `BrowserRouter`.
</details>
