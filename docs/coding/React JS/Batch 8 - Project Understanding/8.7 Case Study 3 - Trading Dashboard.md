## The Project

**What it is:** A crypto trading simulator with live prices. Users watch real-time prices, build a watchlist, place paper trades (buy/sell), track their portfolio with live P&L, and view candlestick charts with technical indicators — all in the browser, no real money, no backend.

**Core loop:** Live price tick → P&L recalculates → chart updates → user sees real-time changes.

**Tech stack:** React + TypeScript + Zustand + TradingView Lightweight Charts + Tailwind + Vitest + Vercel

---

## Step 1: Requirements → SRS

The user needs: watch live prices, place paper trades, track portfolio with live P&L, view charts with indicators.

**Key difference from other projects:** Real-time data. Prices update every second. State changes are frequent and performance-critical.

**Entities:** Ticker (live price), Candle (OHLC), Trade, Position, WatchlistItem, PriceAlert

**Features:** Live price feed, candlestick chart, watchlist, paper trading, portfolio with live P&L, trade history, technical indicators, price alerts, dark/light theme.

---

## Step 2: Data Model → Entities

| Entity | Key attributes | Relationships |
|--------|---------------|---------------|
| Ticker | symbol, price, change24h, volume24h | One per symbol (BTC, ETH, SOL, BNB) |
| Candle | time, open, high, low, close, volume | Many per symbol (one per time interval) |
| Trade | id, symbol, side, entryPrice, quantity, timestamp, status | Belongs to user (simulated) |
| Position | symbol, quantity, avgEntryPrice, currentPrice, pnl, pnlPercent | Derived from open trades |
| WatchlistItem | symbol, addedAt | Belongs to user |
| PriceAlert | id, symbol, targetPrice, direction, triggered | Belongs to user |

**Key decisions:**
- No backend — everything in Zustand + localStorage
- Position is derived from trades (not stored separately)
- P&L is calculated on every price tick (not stored)
- Candles update in place (same timestamp = replace, new timestamp = append)

---

## Step 3: State Design → Zustand Store

| Slice/State | Holds | Key actions |
|-------------|-------|-------------|
| tickers | Live prices per symbol | updateTicker |
| candles | Candle arrays per symbol | updateCandles, appendCandle |
| selectedSymbol | Currently viewed symbol | selectSymbol |
| trades | All trades (open + closed) | buy, sell, closePosition |
| positions | Derived from open trades | recalculatePositions |
| watchlist | Watched symbols | addToWatchlist, removeFromWatchlist |
| alerts | Price alerts | addAlert, removeAlert |
| theme | dark/light | toggleTheme |

**Why Zustand (not Redux Toolkit):**
- Real-time data updates every second — Zustand's minimal API is faster to build
- No Provider wrapper needed — direct store access
- Selective subscriptions — components only re-render on relevant state changes
- Simpler for a frontend-only project with no complex derived views (P&L is calculated in a hook, not selectors)

**When to use Redux Toolkit instead:** Large apps with many derived views, complex middleware, or team collaboration. For real-time data with frequent updates, Zustand's simplicity wins.

---

## Step 4: Architecture Decisions

| Decision | Why | Tradeoff |
|----------|-----|----------|
| Zustand (not Redux Toolkit) | Simpler, faster to build, no Provider, selective subscriptions | Less ecosystem, no built-in memoized selectors |
| Binance WebSocket (public) | Free, no API key, real market data | Rate limits, connection drops, no historical data via WS |
| TradingView Lightweight Charts | Industry-standard, native candlestick, `series.update()` for live | Imperative API (not declarative), separate DOM management |
| Client-side P&L calculation | Instant updates, no network round-trip | CPU usage on every tick (mitigated by useMemo) |
| No backend | Frontend-only project, simpler deploy | No user accounts, no persistent data across devices |
| localStorage for portfolio | Survives refresh, works offline | Size limits, no multi-device sync |

---

## What Makes This Project Unique

1. **Real-time WebSocket data** — not just REST fetch, but streaming data with auto-reconnect
2. **Live P&L** — recalculated on every price tick, no manual refresh
3. **TradingView charts** — industry-standard charting with live candle updates
4. **Technical indicators** — SMA, RSI, MACD calculated client-side
5. **Performance-conscious** — useMemo for P&L, selective subscriptions, incremental chart updates
6. **Paper trading simulation** — buy/sell at live prices, track positions, close for realized P&L

## In Your Own Words

1. Why is real-time data handling harder than fetching data once?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Real-time data arrives continuously (every second or faster), requiring state updates on every tick. This means: (1) more frequent re-renders, (2) P&L must recalculate on every update, (3) charts must update incrementally (not full re-render), (4) memory management (don't store infinite candles), and (5) handling connection drops and reconnections. A fetch-once app doesn't have any of these concerns.

</details>

2. What's the difference between a REST API call and a WebSocket connection?

<details>
<summary>Show Answer</summary>

**Sample Answer:** REST is request-response: client asks, server answers, connection closes. WebSocket is persistent: client connects once, server pushes data continuously. REST is good for "get me this data" (trade history, user profile). WebSocket is good for "keep me updated" (live prices, order book). In this project, REST would be used for trade CRUD (if backend existed), WebSocket for live prices.

</details>

3. Why separate the chart library's DOM from React's DOM?

<details>
<summary>Show Answer</summary>

**Sample Answer:** TradingView Lightweight Charts is an imperative library — it creates its own DOM elements inside a container. React manages the surrounding UI (buttons, panels, layout), but the chart library manages its own internals (canvas, SVG, event handlers). Mixing them would cause conflicts. The `useRef` + `useEffect` pattern bridges them: React provides the container, the chart library takes over its contents.

</details>
