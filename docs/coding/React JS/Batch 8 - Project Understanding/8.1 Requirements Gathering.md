# Batch 8 - Project Understanding

## 8.1 Requirements Gathering — SRS, BRD, PRD, User Stories

---

## Where We Left Off

In 8.0, we saw the gap between coding and engineering. The first engineering skill is **understanding what to build before writing code**. That starts with requirements.

---

## The Problem: "Just Build It"

Most beginners start coding immediately. They open VS Code, create a component, and start typing. Three days later, they realize they built the wrong thing.

Professional developers do it differently: **requirements first, then design, then code.**

---

## What is a Requirement?

A **requirement** is a statement of what the software must do or how well it must do it. Not how to build it — what to build.

| Type | Question it answers | Example |
|------|---------------------|---------|
| **Functional (FR)** | What must the system do? | "Admin can create a project" |
| **Non-functional (NFR)** | How well must it do it? | "Page loads in under 3 seconds" |

---

## The Documents

People use several acronyms for requirement documents. Here is how they differ:

| Acronym | Full name | Written for | Content |
| --- | --- | --- | --- |
| **BRD** | Business Requirements Document | Business people | Goals, money, why the project exists |
| **SRS** | Software Requirements Specification | Developers and clients | What the software must do (functions, rules, limits) |
| **PRD** | Product Requirements Document | Product teams | Features, users, priorities, success measures |
| **TDD** or design doc | Technical Design Document | Developers | How it is built: data, architecture, tools |
| **ER diagram** | Entity Relationship diagram | Developers | Picture of the entities and how they connect |
| **ADR** | Architecture Decision Record | Developers | One decision, its reason and its tradeoffs |

("SRD" is sometimes used loosely for the same idea as an SRS. Teams differ, so ask what a company means.)

## The Vocabulary

| Term | Meaning | Example |
| --- | --- | --- |
| **Stakeholder** | Anyone affected by or interested in the product | The manager, the team members |
| **Functional requirement (FR)** | What the system must do | "Admin can create a project" |
| **Non-functional requirement (NFR)** | How well it must do it | "Loads in under 3 seconds" |
| **User story** | A need in one sentence | "As an employee, I want to move my task, so that the manager sees my progress" |
| **Acceptance criteria** | Conditions that prove a requirement is met | "Given an employee, when they try to move a task to Done, then it is refused" |
| **Scope** | What is included | v1 features |
| **Out of scope** | What is deliberately excluded | Notifications, file attachments |
| **Scope creep** | Scope growing without control | Adding chat "because it is easy" |
| **Assumption** | Something believed true but unconfirmed | "One assignee per task" |
| **Constraint** | A fixed limit | "No backend in v1" |

## User Stories

A user story is a need in one sentence, written from the user's perspective:

**Format:** "As a [role], I want [action], so that [benefit]."

Examples from Team Task Dashboard:
- "As an admin, I want to create a project, so that I can organize work."
- "As an employee, I want to move my task to In Progress, so that the manager sees I started."
- "As an admin, I want to see overdue tasks, so that I can follow up."

**Acceptance criteria** prove the story is done:
- "Given an admin, when they create a project with a name, then it appears in the project list."
- "Given an employee, when they try to move a task they don't own, then it is refused."

## How to Read an SRS

When you get an SRS, look for these sections:

1. **Project overview** — what is it, who is it for, why does it exist
2. **Users and roles** — who can do what
3. **User flows** — step-by-step what happens
4. **Functional requirements** — numbered list of what the system must do (FR-1, FR-2, etc.)
5. **Non-functional requirements** — performance, accessibility, security, etc.
6. **Tech stack** — what tools to use
7. **Data model** — what information to store
8. **Routes** — what pages exist
9. **Build plan** — tickets with outcomes
10. **Scope** — what's in v1, what's later, what's out

---

## How to Find Entities from an SRS

The skill worth learning: **read the SRS and look for nouns the app must remember.**

**Step 1: Underline the nouns.** Users, admin, employee, project, task, status, priority, comment, history, dashboard, team, board, column.

**Step 2: Ask the test question for each noun:** "Will the app keep a list of these, with details about each?"

| Noun | Keep a list with details? | Verdict |
| --- | --- | --- |
| User (admin, employee) | Yes: name, email, password | **Entity** |
| Project | Yes: name, deadline | **Entity** |
| Task | Yes: title, due date, assignee | **Entity** |
| Comment | Yes: text, author, time | **Entity** |
| History line | Yes: who, what, when | **Entity** (ActivityEntry) |
| Status | No, it is just one of 4 values on a task | **Attribute** (enum) |
| Priority | No, just one of 3 values | **Attribute** (enum) |
| Role | No, just admin or employee | **Attribute** (enum) |
| Dashboard, Board | No, these are screens that *show* data | **Not an entity** |
| Overdue | No, worked out from due date and status | **Not stored** (derived) |
| Project progress | No, worked out from its tasks | **Not stored** (derived) |

**Step 3: Decide one entity or two for similar things.** Admin and Employee look like two entities, but they share the same attributes. So we keep **one User entity** with a `role` attribute.

**Step 4: List attributes by asking what each person needs to see.** Picture a task card, then the task detail window. Every piece of information you want on screen is an attribute somewhere.

**Step 5: Find the links.** Use the golden rule: "The many side stores the id of the one side."

## Non-Functional Requirements (NFRs)

NFRs describe **how well** the system must perform, not what it does:

| Area | Example NFR |
|------|-------------|
| **Performance** | First load under 3 seconds. Routes lazy loaded. |
| **Accessibility** | Semantic HTML, keyboard navigable, WCAG AA contrast |
| **Responsiveness** | Works from 360px mobile up to desktop |
| **Reliability** | Error boundary around routes. No white screens. |
| **Security** | No secrets in bundle. Only `VITE_` public values. |
| **Maintainability** | Strict TypeScript, no `any`. Consistent folder structure. |
| **Testing** | Unit tests for slices and selectors. Component tests for key flows. |

---

## Scope: v1, Later, Never

Every project needs a scope boundary. Without it, you'll never finish.

| In v1 | Later (v2) | Out of scope |
|-------|-----------|-------------|
| Two roles, seeded accounts | Real backend with auth | Billing |
| Projects, tasks, Kanban board | Notifications, reminders | Native mobile app |
| Admin dashboard with charts | File attachments | Full real-time collaboration |
| Comments, activity log | Export reports as PDF/CSV | Integrations |

**The rule:** Freeze v1 scope. New ideas go to the v2 list. Don't build it until needed (YAGNI).

## In Your Own Words

1. What is the difference between a functional and non-functional requirement?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A functional requirement (FR) says what the system must do — "Admin can create a project." A non-functional requirement (NFR) says how well it must do it — "Page loads in under 3 seconds" or "WCAG AA contrast." FRs are features; NFRs are quality attributes.

</details>

2. What is a user story, and what are acceptance criteria?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A user story is a need in one sentence from the user's perspective: "As an employee, I want to move my task, so that the manager sees my progress." Acceptance criteria are the conditions that prove the story is done: "Given an employee, when they move a task to In Progress, then the status updates and a history entry is logged."

</details>

3. How do you find entities from an SRS?

<details>
<summary>Show Answer</summary>

**Sample Answer:** (1) Underline all nouns in the SRS. (2) Ask "Will the app keep a list of these with details?" — if yes, it's an entity. (3) Decide one entity vs two for similar things (admin/employee → one User with role). (4) List attributes by picturing what each user needs to see. (5) Find relationships using "the many side stores the id of the one side."

</details>

4. What is scope creep, and how do you prevent it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Scope creep is when the scope grows without control — adding features "because they're easy" without planning. Prevent it by: freezing v1 scope, keeping a v2 ideas list, saying "not in v1" to new ideas, and using the Definition of Done checklist for every ticket.

</details>
