## The Project

**What it is:** A habit tracker + dashboard. Users track daily habits (wake up early, drink water, workout), maintain streaks, and view progress on a dashboard.

**Core loop:** User checks in daily → streak increases → progress visualized on dashboard.

**Tech stack:** React + TypeScript + Redux Toolkit + redux-persist + React Router + Tailwind + Framer Motion + Vitest + Vercel

---

## Step 1: Requirements → SRS

The user needs: track daily habits, maintain streaks, view progress. No backend — frontend-only with localStorage persistence.

**Entities:** User, Habit, CheckIn, Prefs

**Features:** CRUD habits, daily check-in, streak calculation, dashboard with charts, dark/light theme, error boundary, testing, deploy.

---

## Step 2: Data Model → Entities

| Entity | Key attributes | Relationships |
|--------|---------------|---------------|
| User | id, name, email, password, role | has many Habits |
| Habit | id, name, description, frequency, createdBy, createdAt | belongs to User, has many CheckIns |
| CheckIn | id, habitId, userId, date, completed | belongs to Habit and User |
| Prefs | theme, notifications | belongs to User |

**Key decisions:**
- Habits and tasks are different: a habit is recurring (daily/weekly), a task is one-time
- Streak = consecutive days with check-ins. Calculated, not stored.
- CheckIn has a date (not timestamp) — one check-in per habit per day
- redux-persist saves everything to localStorage — refresh-safe

---

## Step 3: State Design → Redux Slices

| Slice | Holds | Key actions |
|-------|-------|-------------|
| authSlice | Current user id, login state | login, logout |
| habitsSlice | Habits | addHabit, updateHabit, deleteHabit |
| checkInsSlice | Check-ins | checkIn, uncheck |
| prefsSlice | Theme, preferences | setTheme |

**Selectors:** habitsByUser, checkInsByHabit, currentStreak, longestStreak, completionRate, habitsDueToday

**Thunks:** checkInHabit (creates check-in + updates streak calculation)

---

## Step 4: Architecture Decisions

| Decision | Why | Tradeoff |
|----------|-----|----------|
| Redux Toolkit (not Zustand) | Relational data (habits → check-ins), many derived views (streaks, completion rates) | More boilerplate than Zustand |
| redux-persist for localStorage | Refresh-safe without backend | localStorage size limits (~5MB) |
| Streaks calculated, not stored | Always correct, no stale data | Recalculation on every render (solved by selectors) |
| useFetch for motivational quote | Demonstrates real API usage, no fake complexity | External dependency (API might be down) |
| Framer Motion for animations | Smooth check-in feedback, professional feel | Extra bundle size |

---

## What Makes This Project Unique

1. **Streak calculation** — consecutive day logic with edge cases (missed days, timezone handling)
2. **redux-persist** — data survives refresh, works offline
3. **useFetch generic hook** — typed API calls with loading/error states
4. **Error boundary** — crash-proof (if chart fails, rest of app works)
5. **Testing** — Vitest + RTL on hooks, store, and components
6. **Deploy** — Vercel with README, screenshots, demo credentials

## In Your Own Words

1. How is a habit different from a task in terms of data modeling?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A task is one-time (create → do → done). A habit is recurring (daily/weekly). A habit needs a CheckIn entity (one per day) to track completion. A task has a status (todo → done). A habit has a streak (calculated from check-ins). The data model reflects this: Task has status, Habit has CheckIns. You can't model a habit as a task because the recurring nature changes the entire data structure.

</details>

2. Why calculate streaks instead of storing them?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Streaks depend on check-in dates. If you store the streak, it goes stale when a check-in is added or removed. By calculating from check-ins (filter by date, find consecutive days), the streak is always correct. The calculation is memoized via selectors, so it's not expensive.

</details>

3. What's the hardest part of building TrackIt?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Streak calculation with edge cases — timezone handling, missed days, partial weeks. Also, redux-persist configuration (serializable check, versioning for migrations). And making the dashboard responsive with multiple panels (charts, stat cards, habit list) on mobile.

</details>
