# Developer Process and Interview Guide

*The full map: how a professional project moves from a client's idea to a live app, the vocabulary for each stage, how to describe your architecture and decisions, how to tell your story with STAR and its cousins, and how to keep your own memory (and your chat context) healthy.*

Written for a beginner who just learned React and wants to build the **Team Task Dashboard** while truly understanding it.

---

## 2. The product (the "what and why")

Practice saying this out loud until it is smooth.

**The 30-second pitch:**

> "The Team Task Dashboard is a Kanban-style web app for a small team. A manager creates projects, breaks them into tasks and assigns them. Employees see only their own tasks and move them across four stages. The manager gets a live dashboard showing progress, workload and overdue work. It has no backend: data lives in the browser with Redux and is saved locally. I built it end to end, starting from the requirements."

**Facts to know cold:**

| Question | Answer |
| --- | --- |
| Who is it for? | A manager (Admin) and a small team (Employees) |
| What problem does it solve? | Work is assigned over chat and spreadsheets, so nobody sees what is stuck until someone complains |
| The core loop? | Admin assigns, employee updates status, admin tracks progress |
| What is out of scope? | Real backend and auth, multi-user sync, notifications, attachments, export |

## 3. The lifecycle: where every document sits

The general name for the stages of building software is the **SDLC** (Software Development Life Cycle).

| Stage | Question | Output | Your project |
| --- | --- | --- | --- |
| 1. Requirements gathering (also called discovery or analysis) | What should we build? | SRS | Client meeting with Raj, then the SRS |
| 2. Design | How will we build it? | Design documents | Data Model, Tech Stack, State Design |
| 3. Planning | In what order? | Tickets | Tickets v2 |
| 4. Implementation | Build it | Working code | Coding in VS Code |
| 5. Testing | Does it work? | Test results | Vitest and manual checks |
| 6. Deployment | Make it live | Live link | Vercel |
| 7. Maintenance | Fix and improve | New versions | v2 ideas |

### 3.1 The documents and their names

People use several acronyms for requirement documents. Here is how they differ:

| Acronym | Full name | Written for | Content |
| --- | --- | --- | --- |
| **BRD** | Business Requirements Document | Business people | Goals, money, why the project exists |
| **SRS** | Software Requirements Specification | Developers and clients | What the software must do (functions, rules, limits) |
| **PRD** | Product Requirements Document | Product teams | Features, users, priorities, success measures |
| **TDD** or design doc | Technical Design Document | Developers | How it is built: data, architecture, tools |
| **ER diagram** | Entity Relationship diagram | Developers | Picture of the entities and how they connect |
| **ADR** | Architecture Decision Record | Developers | One decision, its reason and its tradeoffs |

("SRD" is sometimes used loosely for the same idea as an SRS. Teams differ, so ask what a company means.)

### 3.2 Requirements vocabulary

| Term | Meaning | Example |
| --- | --- | --- |
| **Stakeholder** | Anyone affected by or interested in the product | Raj, the employees |
| **Functional requirement (FR)** | What the system must do | "Admin can create a project" |
| **Non-functional requirement (NFR)** | How well it must do it | "Loads in under 3 seconds" |
| **User story** | A need in one sentence | "As an employee, I want to move my task, so that the manager sees my progress" |
| **Acceptance criteria** | Conditions that prove a requirement is met | "Given an employee, when they try to move a task to Done, then it is refused" |
| **Scope** | What is included | v1 features |
| **Out of scope** | What is deliberately excluded | Notifications |
| **Scope creep** | Scope growing without control | Adding chat "because it is easy" |
| **Assumption** | Something believed true but unconfirmed | "One assignee per task" |
| **Constraint** | A fixed limit | "No backend in v1" |

### 3.3 Data vocabulary

| Term | Meaning |
| --- | --- |
| **Entity** | A real-world thing the app stores data about, distinctly identifiable |
| **Attribute** | A property of an entity |
| **Primary key** | The unique id of a record |
| **Foreign key** | An attribute storing another record's id (a link) |
| **Relationship** | A connection between entities: one to one, one to many, many to many |
| **Cardinality** | How many on each side of a relationship |
| **Normalization** | Storing each fact once and linking by id |
| **Schema** | The full structure of the data |
| **Derived data** | Values worked out from other data (overdue, progress), never stored |

## 4. How you build: methods of work

### 4.1 Waterfall and Agile

|  | Waterfall | Agile |
| --- | --- | --- |
| Idea | Finish each stage completely, then move to the next | Build in small cycles, get feedback, adjust |
| Planning | Everything up front | Plan a little, build a little |
| Client sees it | At the end | Often |
| Risk | Discover problems late | Scope can drift if not managed |

Your project is a **mix**: you wrote requirements and design up front (waterfall-like), then build in vertical slices with demos (Agile-like). Most real teams do something like this.

### 4.2 Horizontal and vertical slicing

|  | Horizontal (layer by layer) | Vertical (feature by feature) |
| --- | --- | --- |
| Builds | All types, then the whole store, then all screens | One small feature through data, logic and screen |
| Visible result | Late | After every ticket |
| Testing | Hard without a screen | Easy: you see it |
| Risk | You work blind; mistakes appear late | Earlier code needs revisiting (refactoring) |
| Best when | You fully understand the whole data model and can test without a UI | You learn as you go and want visible progress |

**Your choice:** vertical, because you test visually and want to learn step by step. That is a defensible, professional answer.

### 4.3 Working vocabulary

| Term | Meaning |
| --- | --- |
| **Walking skeleton** | The thinnest version that runs end to end (login to a role page) |
| **MVP** | Minimum viable product: the smallest version that is truly usable |
| **Iteration** | One round of build, check and improve |
| **Sprint** | A short fixed work cycle (often 1 to 2 weeks) ending in a demo |
| **Demo** | Showing something working |
| **Feedback** | The client's reaction, used to adjust |
| **Backlog** | The list of work not yet done |
| **Ticket** | One small, finishable piece of work |
| **Definition of Done** | The checklist every ticket must meet |
| **Refactoring** | Improving code without changing what it does |
| **Technical debt** | Shortcuts that will cost time later |
| **YAGNI** | "You aren't gonna need it": do not build it until needed |
| **DRY** | "Don't repeat yourself": keep each rule in one place |
| **Separation of concerns** | Keep different jobs in different places |
| **Critical path** | The chain of tickets that decides the minimum time to finish |

### 4.4 Git workflow

| Term | Meaning |
| --- | --- |
| **Repository** | The project folder tracked by Git |
| **Commit** | A saved snapshot with a message |
| **Branch** | A separate line of work |
| **Merge** | Joining a branch back |
| **Pull request (PR)** | A request to merge, with review |

A good habit: one branch per ticket (`td-9-task-crud`) and commit messages that start with the ticket: `TD-9: add task create and edit`.

## 5. How it is built: the architecture

**Architecture** means how the pieces of a system are organized, and why. Even a frontend-only app has one.

### 5.1 The big picture

| Layer | What lives there | Tool |
| --- | --- | --- |
| **Presentation** | Screens and components: what the user sees | React, Tailwind |
| **State** | The app's data and how it changes | Redux Toolkit slices, thunks |
| **Derived data** | Calculated answers from the state | Selectors (createSelector) |
| **Rules** | Who may do what | Permission helper (`usePermissions`) |
| **Routing** | Which screen for which address, and the guards | React Router |
| **Persistence** | Saving to the browser | redux-persist (localStorage) |

**Type of app:** a **single page application (SPA)**: one page loads, then JavaScript swaps screens without reloading.

### 5.2 The patterns you used (with their proper names)

| Pattern | What it means in your project |
| --- | --- |
| **Unidirectional data flow** | Data goes one way: action, then store, then screen. Screens never change data directly |
| **Flux / Redux pattern** | A single store changed only by dispatching actions to reducers |
| **Normalized state** | Each entity stored once in an object keyed by id, linked by ids |
| **Selector pattern** | Calculated answers live in selectors, not in components or in the store |
| **Memoization** | Selectors remember their last answer and recalculate only when data changes |
| **Thunk (command-style action)** | One function that performs several steps, like creating a task and logging history |
| **RBAC (role-based access control)** | Permissions depend on the user's role (admin or employee) |
| **Route guards** | `ProtectedRoute` and `RoleRoute` check access before a page loads |
| **Feature-based structure** | Code grouped by feature (`tasks`, `projects`), not by file type |
| **Code splitting / lazy loading** | A page is downloaded only when visited |
| **Error boundary** | A component that catches crashes and shows a friendly screen |
| **Append-only log** | History entries are added, never edited or deleted |

### 5.3 Data flow, step by step

**Example: an employee moves a card to In Review.**

1. **dnd-kit** reports the drop in the new column.
2. The permission helper checks the move (own task, one step, allowed).
3. The screen dispatches the "move task" thunk.
4. The thunk updates the task's status **and** adds a history entry.
5. **redux-persist** saves the new state.
6. **Selectors** recalculate counts, progress and overdue.
7. **React** redraws the board and the admin dashboard.

### 5.4 The rule to repeat

> **Slices store. Selectors calculate. Components read and dispatch. Permission rules live in one place.**

### 5.5 How to answer "what architecture did you follow?"

> "It is a single page app with a feature-based folder structure and a centralized, normalized Redux store. I separated storing data from calculating it: slices hold entities by id, and memoized selectors derive things like overdue tasks and project progress. Permissions are enforced in one helper and in route guards, and multi-step actions are thunks so related changes, like a task change and its history entry, always happen together."

## 6. Why you chose it: decisions and tradeoffs

A **tradeoff** means you gain something and give something up. Interviewers love hearing that you knew both sides. Each row below is a small **ADR** (Architecture Decision Record).

| Decision | Why | What you gave up | When you would choose differently |
| --- | --- | --- | --- |
| Redux Toolkit, not Zustand | Relational data with many derived views; memoized selectors; mature persistence | More setup and concepts | A small app with simple state: Zustand |
| Normalized state (object keyed by id) | Fast lookup, no duplication, one place to update | Joins are done by hand in selectors | Tiny data sets where nesting is simpler |
| Derived data never stored | Always correct; no stale numbers | Recalculation (solved by memoization) | Very expensive calculations: cache them |
| One `User` entity with a `role` | Admin and employee share the same attributes | A role field must be checked everywhere | Roles with very different data: separate entities |
| Deactivate users, never delete | Old tasks and comments keep working | Inactive users stay in the data | Privacy rules requiring real deletion |
| History as its own entity | Many entries per task; append-only | Extra slice and thunk code | A tiny app needing no audit trail |
| Thunks for multi-slice actions | Related changes always happen together | An extra layer to understand | `extraReducers` if you prefer slices to react to each other |
| localStorage persistence | No backend in v1 | Not shared between users; insecure | Any real multi-user product: a backend |
| UI-only role enforcement | Fits a frontend-only project | Anyone can bypass it by editing storage | Real products: enforce on the server |
| Vertical slicing | Visible progress; fits a visual tester | Planned rework of earlier code | Fully known design, no UI needed: horizontal |
| dnd-kit with a "Move to" menu | Active library; keyboard and touch support | Extra UI for the menu | Never skip the alternative: accessibility |
| Feature-based folders | Everything about a feature in one place | Shared code needs care | Very small apps |

### 6.1 How to explain a tradeoff

Use this shape: **"I chose X because Y. The cost is Z. If the situation were W, I would choose V."**

Example: *"I stored users by id in an object instead of an array, because looking one up is a direct key access instead of a loop. The cost is that I have to turn the object into an array when I want a list. For a few hundred records that is fine."*

## 7. How you know it works: quality

### 7.1 Testing

| Kind | What it checks | In your project |
| --- | --- | --- |
| **Unit test** | One function in isolation | Selectors (overdue, progress, counts), `canMoveTask` |
| **Component / integration test** | A screen behaving as a user would use it | Login success and failure, moving a task |
| **End-to-end (E2E) test** | The whole app in a real browser | Not in v1 (a v2 idea: Playwright or Cypress) |
| **Manual test** | A person using the app | You, after every ticket |

**Test the rules, not the colors.** Permission rules and calculations are where bugs hurt most.

### 7.2 Other quality areas

| Area | What you did |
| --- | --- |
| **Type safety** | Strict TypeScript, no `any`, unions for statuses and roles |
| **Accessibility (a11y)** | Keyboard use, labels, visible focus, WCAG AA contrast, a non-drag way to move cards |
| **Responsiveness** | Works from 360px upward |
| **Performance** | Lazy-loaded pages, memoized selectors, load under 3 seconds |
| **Error handling** | Error boundary, friendly empty and error states |
| **Security (frontend scope)** | No secrets in the bundle, safe rendering of user text |

### 7.3 The honest security limits

Say this confidently. It shows maturity:

> "Roles are enforced in the UI only, because there is no backend. Anyone who edits browser storage can bypass them, and the demo passwords are plain text. In a real product, authentication and authorization would run on a server and passwords would be hashed."

## 8. Telling stories: STAR and its cousins

### 8.1 STAR

| Letter | Stands for | Answers | Length |
| --- | --- | --- | --- |
| **S** | Situation | What was the context? | 1 to 2 sentences |
| **T** | Task | What was your responsibility or goal? | 1 sentence |
| **A** | Action | What did **you** do? (the longest part) | 3 to 5 sentences |
| **R** | Result | What happened? Use numbers if you can | 1 to 2 sentences |

### 8.2 The cousins

| Method | Stands for | Use it when |
| --- | --- | --- |
| **STAR** | Situation, Task, Action, Result | The safe default for behavioral questions |
| **STARL** | STAR plus Learning | You want to show growth (best for beginners) |
| **SOAR** | Situation, Obstacle, Action, Result | The story is about overcoming a problem |
| **CAR** | Context, Action, Result | You need a short answer |
| **PAR** | Problem, Action, Result | The simplest form |
| **CARL** | Context, Action, Result, Learning | A short answer that still shows learning |

All share one skeleton: **set the scene, say what you did, say what happened.**

### 8.3 Where each one fits

| Question type | Example | Use |
| --- | --- | --- |
| Behavioral | "Tell me about a time you were stuck" | STAR or STARL |
| Problem-solving | "A bug that was hard to find" | SOAR |
| Quick follow-up | "What did you do about it?" | CAR |
| Technical decision | "Why Redux?" | Not STAR. Use the tradeoff shape from section 6.1 |

### 8.4 Example shapes (replace with YOUR real stories)

These are **templates showing the shape**, not stories to memorize. Only tell stories that really happened to you. You will collect real ones in your dev log.

**Template (STARL):**

> **Situation:** "While building \[feature\] in my Team Task Dashboard, \[what was happening\]." **Task:** "I needed \[goal\]." **Action:** "I \[first step\], then \[second step\], and \[third step\]." **Result:** "\[What worked, and how I verified it\]." **Learning:** "Next time I would \[what you would do differently\]."

**Shape of a possible real story** (it only counts if it happens to you): a rule you wrote in two places drifted apart, you moved it into one permission helper, and a test now protects it. Your own words, your own details.

### 8.5 How to explain your whole project (the 2-minute walkthrough)

1. **Problem** (15 seconds): who it is for and why.
2. **Process** (30 seconds): requirements, data model, tickets, vertical slices.
3. **Architecture** (45 seconds): the layers and the rule in section 5.4.
4. **A hard decision or bug** (20 seconds): one real story.
5. **Honest limits and next steps** (10 seconds): UI-only roles, what v2 adds.

## 9. Your dev log: where real stories come from

You cannot know your problems before you build. So **collect them as you go.**

### 9.1 Template (one file in the project, `DEVLOG.md`)

```md
## 2026-12-03 | TD-10 | Kanban board
**What I was doing:** moving cards between columns
**What broke:** employee could drop a task straight into Done
**What I tried:** hiding the Done column (did not stop typed actions)
**What fixed it:** one canMoveTask helper, checked in the thunk too
**What I learned:** UI hiding is not enforcement; check at the action
**Time lost:** about 2 hours
```

Write an entry whenever you are stuck for more than 20 minutes, fix a real bug, change an earlier decision, or do planned rework. Two minutes per entry is enough.

### 9.2 Decision log

Keep a second small table of choices and reasons (section 6 is your starting point). When you change your mind, add a line instead of erasing the old one.

### 9.3 Keeping your chat context healthy

A long chat will eventually run out of room. Your **documents are the memory**:

| Document | Holds |
| --- | --- |
| SRS | What to build |
| Data Model | Entities and relationships |
| Tech Stack | Tools and reasons |
| State Design | Slices, selectors, permissions |
| Tickets v2 | The build order |
| This guide | Process, interview preparation |
| `DEVLOG.md` | Your real problems and learnings |

**Start each new chat with a handoff note:**

```md
Project: Team Task Dashboard (React, TypeScript, Redux Toolkit)
Docs attached: SRS, Data Model, Tech Stack, State Design, Tickets v2
Current ticket: TD-__ (name)
Done so far: TD-1 to TD-__
What I am stuck on: ...
How I like to work: one idea at a time, ask me before explaining the next
```

One ticket per chat works well.

## 10. Using AI honestly (the question you will be asked)

You could have asked AI to generate the whole project in an hour. Many people do. Choosing to understand it is your advantage, **if you can show it**.

### 10.1 Rules that keep you honest and strong

1. **Decide first, then ask.** Make your guess before asking for the answer, as you did throughout this project.
2. **Write the core logic yourself.** Selectors, permission rules and thunks are the parts to type and understand line by line.
3. **Use AI as a tutor and reviewer**, not only as a generator: ask "why", ask for an alternative, ask it to find bugs.
4. **Never ship a line you cannot explain.** If you cannot explain it, you do not own it yet.
5. **Keep your own artifacts**: the ER diagram you drew, your dev log, your decisions.

### 10.2 A safe way to say it in an interview

> "I used AI as a mentor. I wrote the requirements and design documents with it by asking questions and making the decisions myself, and I drew the ER diagram on my own. During the build I wrote the core logic and used AI to explain concepts and review my work. I can walk through any part of the code and tell you why it is the way it is."

Only say this if it is true for you. Then make it true.

## 11. Interview question bank

**Short answer outlines.** Practice in your own words.

| Question | Outline of a good answer |
| --- | --- |
| Walk me through the project | Section 8.5 |
| Why Redux Toolkit? | Relational data, derived views, memoized selectors, persistence. Mention Zustand as the lighter alternative |

| Why vertical slicing? | Visible progress, easier testing, earlier feedback; the cost is planned refactoring |
