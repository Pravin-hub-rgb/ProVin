## Where We Left Off

In 8.2, we designed the data model (entities, attributes, relationships). Now we translate that data model into **Redux Toolkit state** — slices, selectors, and permission rules.

---

## From Data Model to Redux State

The data model says: "We have User, Project, Task, Comment, ActivityEntry entities." The state design says: "Each entity gets its own slice, stored as an object keyed by id."

| Data Model | Redux State |
|---|---|
| Entity | Slice |
| Attribute | Property on the entity object |
| Relationship (foreign key) | Id reference (e.g., `projectId` on Task) |
| Derived data | Selector (memoized calculation) |
| Business rules | Permission helper + thunks |

---

## Slice Design

| Slice | Holds | Key actions |
| --- | --- | --- |
| `authSlice` | Current user id and login state | `login`, `logout` |
| `usersSlice` | Team members | `addUser`, `setUserActive` |
| `projectsSlice` | Projects | `addProject`, `updateProject`, `deleteProject` |
| `tasksSlice` | Tasks | `addTask`, `updateTask`, `moveTask`, `assignTask`, `deleteTask` |
| `commentsSlice` | Comments | `addComment` |
| `activitySlice` | History log | `logActivity` |
| `prefsSlice` | Theme and UI preferences | `setTheme` |

**The pattern:** Each slice holds one entity type. Actions modify that slice. Multi-entity actions (like "create task + log activity") use thunks.

---

## Normalized State

Each slice stores entities as an **object keyed by id**, not an array:

```ts
// GOOD — normalized (object keyed by id)
tasks: {
  "t_001": { id: "t_001", title: "Design layout", status: "todo" },
  "t_002": { id: "t_002", title: "Build API", status: "in_progress" },
}

// BAD — nested array
tasks: [
  { id: "t_001", title: "Design layout", status: "todo" },
  { id: "t_002", title: "Build API", status: "in_progress" },
]
```

**Why normalized?**
- **Fast lookup:** `state.tasks[id]` is O(1). Array find is O(n).
- **No duplication:** Each entity stored once. No "user name copied in 5 places."
- **Easy updates:** Change one property on one object. No digging through nested arrays.

## Selectors (createSelector)

Selectors are **memoized calculations** that derive data from the store. They live in one file.

```ts
// selectors.ts
import { createSelector } from "@reduxjs/toolkit";
import { RootState } from "./store";

// Basic selectors (input selectors)
const selectTasks = (state: RootState) => state.tasks;
const selectProjects = (state: RootState) => state.projects;

// Derived selectors (memoized)
export const selectTasksByProject = createSelector(
  [selectTasks, (_state, projectId: string) => projectId],
  (tasks, projectId) => Object.values(tasks).filter(t => t.projectId === projectId)
);

export const selectOverdueTasks = createSelector(
  [selectTasks],
  (tasks) => Object.values(tasks).filter(t =>
    new Date(t.dueDate) < new Date() && t.status !== "done"
  )
);

export const selectProjectProgress = createSelector(
  [selectTasks, (_state, projectId: string) => projectId],
  (tasks, projectId) => {
    const projectTasks = Object.values(tasks).filter(t => t.projectId === projectId);
    if (projectTasks.length === 0) return 0;
    const done = projectTasks.filter(t => t.status === "done").length;
    return Math.round((done / projectTasks.length) * 100);
  }
);

export const selectWorkloadByEmployee = createSelector(
  [selectTasks, selectUsers],
  (tasks, users) => {
    const workload: Record<string, number> = {};
    for (const task of Object.values(tasks)) {
      if (task.assigneeId && task.status !== "done") {
        workload[task.assigneeId] = (workload[task.assigneeId] || 0) + 1;
      }
    }
    return workload;
  }
);
```

**Why selectors?**
- **Single source of truth:** Business logic lives in one place, not scattered in components.
- **Memoization:** `createSelector` remembers the last result. If inputs haven't changed, it returns the cached result — no recalculation.
- **Testable:** Selectors are pure functions. Easy to unit test.

## Permission Helper (usePermissions)

Business rules (who can do what) live in one helper hook, not in components:

```ts
// hooks/usePermissions.ts
export function usePermissions() {
  const user = useAppSelector(selectCurrentUser);
  const isAdmin = user?.role === "admin";

  return {
    canCreateProject: isAdmin,
    canDeleteProject: isAdmin,
    canCreateTask: isAdmin,
    canAssignTask: isAdmin,
    canMoveTask: (task: Task) => {
      if (isAdmin) return true;
      return task.assigneeId === user?.id && canMoveOneStep(task.status);
    },
    canComment: (task: Task) => {
      if (isAdmin) return true;
      return task.assigneeId === user?.id;
    },
    canReassign: isAdmin,
    canDeleteTask: isAdmin,
  };
}
```

**The rule:** Slices store. Selectors calculate. Components read and dispatch. Permission rules live in one place.

## Thunks (Multi-Slice Actions)

When an action needs to update multiple slices (e.g., create task + log activity), use a thunk:

```ts
// thunks/taskThunks.ts
export const createTask = createAsyncThunk(
  "tasks/createTask",
  async (taskData: CreateTaskPayload, { dispatch, getState }) => {
    const task = { id: generateId(), ...taskData, status: "todo", createdAt: new Date().toISOString(), updatedAt: new Date().toISOString() };
    dispatch(tasksSlice.actions.addTask(task));
    dispatch(activitySlice.actions.logActivity({
      taskId: task.id,
      actorId: getState().auth.currentUserId!,
      type: "created",
      detail: "Task created",
    }));
    return task;
  }
);
```

**Why thunks?** Related changes always happen together. If you create a task, the history entry is always logged. No "forgot to log activity" bugs.

## Persistence

Persist everything except transient UI state. Add a version number so you can migrate data later.

```ts
// store.ts
import { configureStore } from "@reduxjs/toolkit";
import { persistReducer, persistStore } from "redux-persist";
import storage from "redux-persist/lib/storage";
import { combineReducers } from "redux";

const persistConfig = {
  key: "team-task-dashboard",
  version: 1,
  storage,
  whitelist: ["auth", "users", "projects", "tasks", "comments", "activity", "prefs"],
};

const rootReducer = combineReducers({
  auth: authSlice.reducer,
  users: usersSlice.reducer,
  projects: projectsSlice.reducer,
  tasks: tasksSlice.reducer,
  comments: commentsSlice.reducer,
  activity: activitySlice.reducer,
  prefs: prefsSlice.reducer,
});

const persistedReducer = persistReducer(persistConfig, rootReducer);

export const store = configureStore({
  reducer: persistedReducer,
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware({
      serializableCheck: {
        ignoredActions: [FLUSH, REHYDRATE, PAUSE, PERSIST, PURGE, REGISTER],
      },
    }),
});

export const persistor = persistStore(store);
```

**Why serializableCheck ignore?** redux-persist dispatches non-serializable actions (functions, promises). The middleware warns about them. We ignore those specific actions.

## In Your Own Words

1. What is normalized state, and why use it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Normalized state stores each entity once in an object keyed by id, with relationships represented as id references. Instead of nesting tasks inside projects (which makes updates hard), you have flat lists: `users: { id: {...} }`, `projects: { id: {...} }`, `tasks: { id: { projectId: "p1", assigneeId: "u2" } }`. This gives O(1) lookups, no data duplication, and easy updates — change one object, everything that references it sees the new value.

</details>

2. Why use `createSelector` instead of calculating in components?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `createSelector` memoizes the result — it only recalculates when inputs change. If you calculate in components, every render recalculates (even if data hasn't changed). Selectors also centralize business logic — "overdue tasks" is defined once, not in every component that needs it. And they're pure functions, easy to unit test.

</details>

3. What is a thunk, and when do you use one?

<details>
<summary>Show Answer</summary>

**Sample Answer:** A thunk is a function that dispatches multiple actions. Use it when one user action needs to update multiple slices — e.g., creating a task also logs an activity entry. The thunk ensures both happen together. Without thunks, you'd dispatch two actions separately and risk one failing while the other succeeds.

</details>

4. Why persist to localStorage, and what's the serializableCheck issue?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Persist to localStorage so data survives page refreshes — without a backend, this is the only way to keep data. redux-persist saves the store state to localStorage and rehydrates it on startup. The serializableCheck middleware warns about non-serializable values (functions, promises) in actions/state. redux-persist dispatches non-serializable actions internally, so we ignore those specific actions (`FLUSH`, `REHYDRATE`, etc.) to avoid false warnings.

</details>
