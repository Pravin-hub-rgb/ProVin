## The Project

**What it is:** A Kanban board app where a manager (Admin) creates projects, breaks them into tasks, and assigns them to team members (Employees). Employees move their tasks across the board. The Admin sees live progress on a dashboard.

**Core loop:** Admin assigns → Employee updates status → Admin tracks progress.

**Tech stack:** React + TypeScript + Redux Toolkit + redux-persist + React Router + Tailwind + dnd-kit + Recharts + Framer Motion + Vitest

---

## Step 1: Requirements → SRS

The client said: "I assign work over chat and spreadsheets. Nobody knows what is stuck until someone complains. I want one place where I assign work, people update their own status, and I can see progress at a glance."

From this, we derived:
- **Users:** Admin (manager) and Employee (team member)
- **Entities:** User, Project, Task, Comment, ActivityEntry
- **Features:** CRUD projects/tasks, Kanban board, dashboard, comments, activity log, filters
- **Non-goals:** No backend, no real auth, no notifications, no file attachments

See: `Capstone 3 - Team Task Dashboard/Team_Task_Dashboard_SRS.md`

---

## Step 2: Data Model → Entities

We found 5 entities by underlining nouns in the SRS and asking "will the app keep a list of these?"

| Entity | Key attributes | Relationships |
|--------|---------------|---------------|
| User | id, name, email, password, role, active | creates Projects, assigned Tasks, writes Comments |
| Project | id, name, description, deadline, createdBy | has many Tasks |
| Task | id, title, description, projectId, assigneeId, priority, dueDate, status | belongs to Project, assigned to User, has Comments + Activity |
| Comment | id, taskId, createdBy, text, createdAt | belongs to Task, written by User |
| ActivityEntry | id, taskId, updatedBy, type, detail, createdAt | belongs to Task, caused by User |

**Key decisions:**
- One `User` entity with `role` (not separate Admin/Employee entities)
- `assigneeId` can be null (tasks created before assignment)
- History is its own entity (append-only log)
- Store only ids, never copied names

See: `Capstone 3 - Team Task Dashboard/Team Task Dashboard Data Model (Design Phase).md`

## Step 3: State Design → Redux Slices

7 slices, one per entity type:

| Slice | Holds | Key actions |
|-------|-------|-------------|
| authSlice | Current user id, login state | login, logout |
| usersSlice | Team members | addUser, setUserActive |
| projectsSlice | Projects | addProject, updateProject, deleteProject |
| tasksSlice | Tasks | addTask, updateTask, moveTask, assignTask, deleteTask |
| commentsSlice | Comments | addComment |
| activitySlice | History log | logActivity |
| prefsSlice | Theme, UI preferences | setTheme |

**Selectors** (memoized with createSelector): tasksByProject, tasksByAssignee, overdueTasks, countsByStatus, progressPerProject, workloadPerEmployee.

**Thunks:** createTask (creates task + logs activity), moveTask (updates status + logs activity).

See: `Capstone 3 - Team Task Dashboard/Team Task Dashboard State Design.md`

## Step 5: Architecture Decisions

| Decision | Why | Tradeoff |
|----------|-----|----------|
| Redux Toolkit (not Zustand) | Relational data with many derived views; memoized selectors | More setup and concepts |
| Normalized state | Fast lookup, no duplication | Joins done by hand in selectors |
| Derived data never stored | Always correct, no stale numbers | Recalculation (solved by memoization) |
| UI-only role enforcement | Fits frontend-only project | Anyone can bypass by editing storage |
| dnd-kit (not react-beautiful-dnd) | Actively maintained, accessible, keyboard support | Extra UI for "Move to" menu |
| Feature-based folders | Everything about a feature in one place | Shared code needs care |

---

## What Makes This Project Unique

1. **Normalized state** — entities stored by id, linked by id references. No nesting.
2. **Permission system** — `usePermissions` hook centralizes all business rules. Components read permissions, don't implement them.
3. **Activity log** — append-only history. Every action is logged with who, what, when.
4. **Kanban board** — accessible drag-and-drop with keyboard alternative (dnd-kit).
5. **Dashboard** — stat cards, charts (Recharts), progress per project, workload per person.

## In Your Own Words

1. Walk through the Team Task Dashboard data model in 30 seconds.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Five entities: User (admin/employee with role), Project (name, deadline, createdBy), Task (title, projectId, assigneeId, status, priority, dueDate), Comment (taskId, authorId, text), ActivityEntry (taskId, actorId, type, detail). All relationships are one-to-many — the "many" side stores the foreign key. Normalized state: each entity in its own flat list, linked by ids. Derived data (overdue, progress, counts) calculated via memoized selectors, never stored.

</details>

2. Why did you choose Redux Toolkit for this project?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The data is relational (projects → tasks → comments → activity) with many derived views (tasks by project, tasks by assignee, overdue, counts by status, progress per project, workload per employee). Redux Toolkit's createSelector memoizes these calculations. Zustand is simpler but lacks built-in memoized selectors. For a data-heavy app with many derived views, RTK is the better fit.

</details>

3. How do roles work without a backend?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Roles are enforced in the UI only. The auth slice stores the current user's id and role. ProtectedRoute and RoleRoute components check the role before rendering. The usePermissions hook centralizes all business rules (canCreateProject, canMoveTask, etc.). Components read permissions, they don't implement them. The README honestly states this is a UI-level simulation — real authorization belongs on a backend.

</details>
