## Cheat Sheet

```ts
Record<K, V>   // Object: har key K type ki, har value V type ki
Partial<T>     // Sab properties optional
Required<T>    // Sab properties required
Readonly<T>    // Sab properties read-only (modify nahi kar sakte)
Pick<T, K>     // Sirf kuch properties chuno
Omit<T, K>     // Kuch properties hata do
Exclude<T, U>  // Union T mein se U jaisi types nikaalo
Extract<T, U>  // Union T mein se sirf U jaisi types rakho
NonNullable<T> // null aur undefined hata do
```

## Abhi Tak Kya Hua

Pehle wale topics mein TypeScript ke core types seekhe — primitives, objects, arrays, functions, interfaces, union types. Ye sab apni khud ki types banane ke tools the. Ab ek nayi cheez seekhenge: **utility types** — yeh TypeScript ke built-in generic types hain jo existing types ko transform karte hain.

## Broader Goal

Kai baar hume ek existing type ka modified version chahiye — jaise "saari properties optional ho jayein" ya "kuch properties hata do". Utility types exact yahi karte hain. Inhe seekhne ke baad, baar baar naye interfaces banane ki zaroorat nahi padegi.

---

## 1.5.1 Record<K, V> — Dynamic Object Type

**SOCH:** Kabhi kabhi hume ek object chahiye jisme keys hume pehle se nahi pata, lekin har value ka structure pata hai. Jaise translation object — keys language names hain ("en", "hi"), har value ek specific shape ka object hai.

**CONCEPT — `Record<K, V>`:** Ye ek object type banata hai jisme har key type `K` ki hoti hai aur har value type `V` ki. Koi property miss nahi ho sakti — agar K union type hai toh union ki har value ke liye ek entry chahiye.

Samajhne ka simple tarika: `Record<string, number>` ka matlab hai "ek object jisme har key string hai aur har value number hai". TypeScript ko yeh batana ki object ka shape kya hoga. Yeh sirf development time pe exist karta hai — runtime pe kuch nahi hota, sirf type safety ke liye hai.

```ts
type Language = "en" | "hi";

const texts: Record<Language, string> = {
  en: "Hello",
  hi: "नमस्ते",
};
```

Yahan `Record<Language, string>` ka matlab: "ek object jisme har key `en` ya `hi` hai, aur har value string hai." Dono keys dena mandatory hai — ek bhi bhoologe toh TypeScript error dega.

**Kyun useful hai:** Jab bhi keys ek known set se aati hain aur har value same shape ki hoti hai, Record use karo. Jaise — API responses mapped by ID, translation tables, config objects.

> **What It Is NOT:** Record `{}` ya `Object` nahi hai. `{}` kisi bi key allow karta hai bina value type check kiye. Record strict hai — key type aur value type dono enforce karta hai.

```ts
const bad: Record<string, number> = { a: 1, b: "hello" }; // ❌ "hello" number nahi hai
```

## 1.5.2 Partial<T> — Sab Properties Optional

**SOCH:** Ek user profile form lo — user sirf naam change karega, baaki fields nahi. Lekin aapke paas pura `User` interface hai jisme saari fields required hain. Ek naya interface `PartialUser` banana padega? Nahi — `Partial<T>` se kaam ho jayega.

**CONCEPT — `Partial<T>`:** T ki saari properties ko optional bana deta hai. Har property ke aage `?` lag jata hai.

```ts
interface User {
  id: number;
  name: string;
  email: string;
}

// Manual way — naya interface banana padega
interface PartialUser {
  id?: number;
  name?: string;
  email?: string;
}

// Partial way — ek hi line
type PartialUser = Partial<User>; // { id?: number; name?: string; email?: string }
```

**Real use case:** Update API calls — aapko sirf wahi fields bhejni hain jo change hui hain. Partial se type mil jaata hai bina naya interface banaye.

```ts
function updateUser(id: number, updates: Partial<User>) {
  // Sirf jo fields bheje hain wahi change honge
}
```

> **What It Is NOT:** Partial sab properties ko optional banata hai, lekin yeh optional `undefined` assign karne ki permission nahi deta. Agar property optional hai toh uski value missing ho sakti hai, lekin explicitly `undefined` set karna allowed hai (TypeScript strict mode ke baare mein soche).

## 1.5.3 Required<T> — Sab Properties Zaroori

Partial ka opposite. Saari optional properties ko required bana deta hai.

```ts
interface Config {
  url?: string;
  timeout?: number;
  retries?: number;
}

// Saari properties ab required ho gayi
type StrictConfig = Required<Config>;
// { url: string; timeout: number; retries: number; }
```

**Kab use karein:** Jab koi internal function actually saari values expect karta ho, lekin public API ne unhe optional rakha ho.

## 1.5.4 Readonly<T> — Sirf Padho, Likho Nahi

**SOCH:** Ek config object hai — ek baar set hone ke baad koi use modify nahi karna chahiye. Lekin TypeScript by default allow karta hai `config.url = "new"`. Readonly isse rokta hai.

**CONCEPT:** Saari properties ko `readonly` bana deta hai. Koi bhi assignment attempt compile-time error dega.

```ts
interface Theme {
  primary: string;
  secondary: string;
}

const theme: Readonly<Theme> = { primary: "#000", secondary: "#fff" };
theme.primary = "#111"; // ❌ Error: Cannot assign to 'primary' because it is a read-only property
```

**Real use case:** Redux state, global configs, any data jo immutable hona chahiye.

> **What It Is NOT:** `Readonly<T>` sirf TypeScript level pe enforce karta hai — runtime pe koi rok nahi hai. Agar koi JavaScript code se modify karega, toh ho jayega. Yeh sirf development time safety hai.

## 1.5.5 Pick<T, K> — Kuch Properties Chuno

**SOCH:** Ek `User` interface hai jisme 10 properties hain. Ek component ko sirf `name` aur `email` chahiye. Kya naya interface banayenge? Pick se karo.

```ts
interface User {
  id: number;
  name: string;
  email: string;
  role: "admin" | "user";
  createdAt: Date;
}

type UserPublic = Pick<User, "name" | "email">;
// { name: string; email: string; }
```

**Line by line:** `Pick<User, "name" | "email">` matlab — `User` interface mein se sirf `"name"` aur `"email"` properties le lo, baaki hata do.

**Real use case:** API se sirf kuch fields bhejni hain (jaise public profile), internal properties nahi dikhani.

---

## 1.5.6 Omit<T, K> — Kuch Properties Hata Do

Pick ka opposite. Specify ki gayi properties hata deta hai, baaki rakhta hai.

```ts
interface User {
  id: number;
  name: string;
  email: string;
  password: string;
  ssn: string;
}

type UserPublic = Omit<User, "password" | "ssn">;
// { id: number; name: string; email: string; }
```

**Pick vs Omit — Kab kya use karein?**
- **Pick** tab jab tumhe **chahiye kya** clear hai — chuno specific properties
- **Omit** tab jab tumhe **nahi chahiye kya** clear hai — hatao sensitive/private fields

Rule of thumb: `Pick` chhoti list ke liye, `Omit` badi list ke liye.

## 1.5.7 Exclude<T, U> — Union Mein Se Types Nikaalo

**SOCH:** Ek union type hai `Status = "loading" | "success" | "error"`. Ek function sirf `"success" | "error"` accept karta hai. Manual duplicate type banane ki zaroorat nahi.

```ts
type Status = "loading" | "success" | "error";

type FinishedStatus = Exclude<Status, "loading">;
// "success" | "error"
```

**CONCEPT:** `Exclude<T, U>` union type `T` mein se un types ko hata deta hai jo `U` mein bhi hain. `T` aur `U` dono union types hote hain.

```ts
type T = "a" | "b" | "c" | "d";
type U = Exclude<T, "a" | "b">;
// "c" | "d"
```

---

## 1.5.8 Extract<T, U> — Union Mein Se Types Chuno

Exclude ka opposite. Sirf wahi types rakhta hai jo `U` se match karein.

```ts
type T = "a" | "b" | "c" | "d";
type U = Extract<T, "a" | "b">;
// "a" | "b"
```

**Real use case:** Jab event types filter karne ho — `Extract<EventType, "click" | "submit">` sirf wahi return karega.

---

## 1.5.9 NonNullable<T> — null/undefined Hata Do

Union type mein se `null` aur `undefined` ko hata deta hai.

```ts
type MaybeString = string | null | undefined;
type DefinitelyString = NonNullable<MaybeString>;
// string
```

**Real use case:** API responses jo nullable aati hain — non-nullable version chahiye internal processing ke liye.

## Kab Kya Use Karein — Quick Reference

| Problem | Solution |
|---------|----------|
| "Har value same shape, keys dynamic ya fixed set se" | `Record<K, V>` |
| "Kuch properties optional banao form update ke liye" | `Partial<T>` |
| "Saari properties required chahiye internal use mein" | `Required<T>` |
| "Config/state ko koi modify na kar paye" | `Readonly<T>` |
| "Sirf 2-3 properties chahiye interface mein se" | `Pick<T, K>` |
| "Sensitive fields hata do, baaki sab rakho" | `Omit<T, K>` |
| "Union type mein se kuch values hata do" | `Exclude<T, U>` |
| "Union type mein se kuch values chuno" | `Extract<T, U>` |
| "Nullable type se null/undefined hatao" | `NonNullable<T>` |

## Common Mistakes

1. **Record mein extra property dena bhoolna** — Agar key union type hai, toh union ki saari values ke liye entry chahiye.
2. **Partial ko runtime default samajhna** — Partial sirf type ko optional banata hai. Runtime mein value undefined ho sakti hai — handle karna padega.
3. **Pick/Omit mein property names galat likhna** — TypeScript error dega. IDE ka autocomplete use karo.
4. **Exclude/Extract ko object types pe lagana** — Ye sirf union types ke saath kaam karte hain (string literals, number literals). Object types ke saath Pick/Omit use karo.

---

## Summary

| Utility Type | Kaam |
|---|---|
| `Record<K, V>` | Object type with dynamic/constrained keys |
| `Partial<T>` | All properties optional |
| `Required<T>` | All properties required |
| `Readonly<T>` | All properties read-only |
| `Pick<T, K>` | Pick specific properties |
| `Omit<T, K>` | Omit specific properties |
| `Exclude<T, U>` | Remove types from a union |
| `Extract<T, U>` | Keep only matching union types |
| `NonNullable<T>` | Remove null and undefined |

Sab utility types sirf TypeScript time pe exist karte hain — runtime pe inka koi effect nahi. Yeh code likhne mein speed aur safety dete hain.

3. Pick aur Omit mein kya antar hai? Ek example do jahan Pick better hai aur ek jahan Omit better.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Pick specified properties ko rakhta hai, baaki hata deta hai. Omit specified properties ko hata deta hai, baaki rakhta hai. Pick better hai jab tumhe kuch specific properties chahiye (jaise public profile ke liye sirf name aur email). Omit better hai jab tumhe kuch specific properties nahi chahiye (jaise user object se password aur ssn hatao). Short list ho toh Pick use karo, long list ho toh Omit.

</details>

4. Readonly runtime pe kyun enforce nahi hota? Iska matlab kya hai practical usage mein?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Readonly sirf TypeScript ka compile-time feature hai. Jab code JavaScript mein compile hota hai, readonly hat jata hai — runtime pe koi restriction nahi. Practical usage mein iska matlab hai ki development time pe galti se value change nahi karoge, lekin agar koi external JavaScript code modify karega (jaise browser console), toh ho sakta hai. Redux state, config objects, theme objects — in sab mein Readonly use karo safety ke liye.

</details>

5. Exclude aur Extract dono union types ke saath kaam karte hain. Kaunsa kab use karna chahiye?

<details>

**Sample Answer:** Exclude union mein se unwanted types hata deta hai — jaise `Status` union mein se "loading" hata do. Extract union mein se sirf wanted types rakhta hai — jaise `Status` union mein se sirf "success" | "error" rakho. Exclude tab use karo jab pata ho ki kya nahi chahiye. Extract tab use karo jab pata ho ki kya chahiye.
