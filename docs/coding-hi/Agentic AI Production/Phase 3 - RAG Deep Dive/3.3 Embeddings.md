# 3.3 Embeddings

3.2 mein chunks ban gaye — ab ek aisa sawaal uthta hai: **FAISS kaise pata karega ki "student discount" wala chunk kaun hai, jab user puchhe *"discount policy kya hai?"*?** FAISS sirf number-lists (vectors) hi compare karta hai — text nahi. Toh pehle yeh text-wala chunk → **384-number vector** hona chahiye.

## Embedding kya hota hai — zip-code analogy

Socho har chunk ek city hai, embedding uss city ka **zip code** — 384-number ka address jo uss chunk ki *meaning location* batata hai. Jitne do shaharein pass hone lage, utne hi meaning pass hone lage:

```
"student discount 50% off"  → [0.21, -0.05, 0.84, ... 0.10]   (384 numbers)
"50% off student discount"  → [0.22, -0.04, 0.85, ... 0.11]   (bahut kareeb!)
"stock market crash"        → [-0.71, 0.60, 0.12, ... -0.33]  (poora alag)
```

User ke sawaal ka bhi embedding banega — FAISS uss zip code se sabse kareeb ke 3-5 chunks de dega.

## bge-small-en-v1.5 — kyun yehi?

- **Name:** `BAAI/bge-small-en-v1.5` (Beijing Academy of AI)
- **Dimension:** 384 — chhota, fast, acchi accuracy-to-size ratio
- **Local + free:** download hone ke baad koi API/rupaye nahi — CPU pe chalta hai
- **Retrieval-optimized:** ise *query vs passage* matching ke liye train kiya — same-meaning wale sentences kareeb aate hain

## Cosine similarity — "kaise kareeb hain" ka hisab

Vectors ke beech **angle** dekhte hain — dot product divided by norms. bge ke embeddings **L2-normalized** hote hain (magnitude hamesha 1) — isliye `dot(a,b)` hi cosine ban jaata hai — FAISS ko alag normalize nahi karna padta.

## Code: text → vector dekho

```python
# 3.3_embeddings.py
from langchain_huggingface import HuggingFaceEmbeddings
import numpy as np

emb = HuggingFaceEmbeddings(model_name="BAAI/bge-small-en-v1.5")

q   = "Student discount kitna hai?"
good = "Student discount 10th standard ko 50% off milta hai."
bad  = "Stock market today crashed by 12%."

vq = emb.embed_query(q)              # (1) query → vector
vg = emb.embed_query(good)          # (2) passage → vector
vb = emb.embed_query(bad)           # (3) unrelated → vector

print("len:", len(vq))                              # 384 hona chahiye
print("sim(q,good):", round(float(np.dot(vq, vg)), 3))  # ~0.8+
print("sim(q,bad): ", round(float(np.dot(vq, vb)), 3))  # ~0.2
```

Line-by-line: `embed_query(text)` — ek sentence → 384-number vector (query user ke liye). `embed_documents([list])` — multiple → vectors (index banate waqt) — yahan 3 queries ek-sath bhi likh sakte hain. `len(vq)` — dimension check — 384 hona chahiye — agar 768 aa raha — wrong model chal raha. `np.dot(vq, vg)` — normalized hone ki wajah se dot product = cosine — high value = kareeb.

## Nutshell

Embedding = text → 384-number vector; same-meaning vectors pass aate hain; cosine (dot) similarity unki kareebiyon ka hisab karta hai.

## Common Mistakes
- ❌ Query ke liye ek model, index ke liye doosra → dim mismatch crash → fix: ek hi `HuggingFaceEmbeddings` object reuse karo
- ❌ L2-normalize bhool gaye → cosine galat lagega → fix: bge built-in normalize karta — ya `from numpy.linalg import norm` se manually
- ❌ Embedding = perfect synonym detector maan liya → nuance miss hogi → fix: RAG pipeline ko end-to-end test karo, chunk quality dekho

## What It Is NOT
- ⚠️ Perfect semantic understanding nahi — "bank" (river vs finance) confuse kar sakta hai
- ⚠️ Human-readable numbers nahi — har number ka koi meaning nahi, sirf vector ka *direction* matter karta hai
- ⚠️ Keyword search nahi — "discount" → "bargain" match karega, "discount" → "discount" nahi hamesha zyada

## In Your Own Words

<details>
<summary>1. Embedding dimension 384 kyun hoti hai?</summary>
**Jawab:** Trade-off — zyada dimensions acchi accuracy de sakti hain lekin slow + badi memory. 384 — ek chhota size jo retrieval ke liye kaafi hota hai. Model ko yahi dimension mila train-time par.
</details>

<details>
<summary>2. embed_query aur embed_documents mein kya fark hai?</summary>
**Jawab:** Functional roop se ek hi model chalega — dono text → vector karte hain. Difference — convention: `embed_query` ek document ke liye, `embed_documents` list ke liye, kabhi-kabhi query pe alag normalization hoti hai.
</details>

<details>
<summary>3. Cosine similarity vs Euclidean distance — kaun behtar retrieval mein?</summary>
**Jawab:** Cosine — kyunki woh magnitude nahi, sirf direction dekhta hai. Ek lamba document aur ek chhota answer — dono same topic — cosine unhe kareeb lagayegi, Euclidean length se bias ho sakta hai.
</details>
