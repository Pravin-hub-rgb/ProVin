1.7 mein model ko memory de di. Ab soch ek real production wali baat — airport security. Woh kehti hai: har person ke paas se guzre, bag check hoga, boarding pass verify hoga. Har output ke pehle ek chhaana rehta hai.

Agent ke saath wahi — jab tak model call seedha hota hai, tumhe us call ke aas-paas koi control nahi. Logging kahan karni? Agar API fail ho toh kya? Cost kaise track karein? Wahi is 1.8 mein hai — **middleware**.

# 1.8 Middleware

**Middleware** matlab — extra logic jo model call ke andar aur baad mein wrap ho jaati hai. Model call ke pehle (before) aur baad (after) ki extra steps. LangChain khud yeh definition mention karta hai: "Middleware provides a way to more tightly control what happens inside the agent."

Aise socho — airport security. Model call = passenger. Sekurity se pehle hi extra checks lagte hain: `before_model` — andar jaate waqt boarding check, `after_model` — bahar nikalte waqt ek aur check. Ye checks hi middleware hain. Tum model call pe extra rules lagate ho bina model ke code ko change kiye.

## Built-in (Ready-Made) Middleware

LangChain ke paas ready-made middlewares hote hain jo common problems solve karte hain:

| Middleware | Kya karta hai |
|---|---|
| **Logging** | Har call ka record — kya bheja, kya aaya |
| **Retry** | Agar API call fail (network kharab), khud baar baar try karta hai |
| **Fallback** | Primary model down (kharab) toh backup model try karta hai |
| **Rate limit** | Ek time mein kitni calls allowed, usse control karta hai (bill bachat) |
| **Guardrails** | Input/output ko rules se check — unsafe cheez reject |
| **PII detection** | Email, credit card jaisi sensitive info detect/replace |

In sab ka faayda — ye normal model call mein inject ho jaati hain bina model ke logic ko change kiye. Sirf `model.with_middlewares([...])` jaisi line se.

## Custom Middleware — Your Own

Ready-made ke alawa tum apna khud ka middleware likh sakte ho. Example — ek simple middleware jo har request aur response log karta hai:

```python
from langchain.middleware.base import BaseMiddleware

class LoggingMiddleware(BaseMiddleware):
    async def before_model(self, request):
        print("REQUEST:", request.input)
        return request

    async def after_model(self, response):
        print("RESPONSE:", response.output)
        return response
```

Samjho:

* `class LoggingMiddleware(BaseMiddleware)` — nayi class jo `BaseMiddleware` se inherit karti hai. `BaseMiddleware` base hai jisse middleware banne ke liye.
* `async def before_model(self, request)` — ye method call hota hai **model se pehle**. `async` matlab yeh async function hai (Python mein concurrency handle karne ka pattern). `request` mein wo input hota hai jo model ko jaane wala hai.
* `print("REQUEST:", request.input)` — request print karo, taaki tum dekho kya bhej rahe ho.
* `return request` — request ko aage bhejo (wapis karo) — warna pipeline toot jayegi.
* `async def after_model(self, response)` — isko call hota hai **model ke baad**. `response` wo output jo model ne banaya.
* `print("RESPONSE:", response.output)` — output print.
* `return response` — response aage bhejo.

## Attach the Middleware to the Model

Ab is logging wale ko model se jodna hai:

```python
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model

load_dotenv()

model = init_chat_model("llama-3.3-70b-versatile")

wrapped = model.with_middlewares([LoggingMiddleware()])

response = wrapped.invoke("Hello! Kya haal hai?")
print(response.content)
```

* `LoggingMiddleware()` — middleware ka ek instance (object) banao.
* `model.with_middlewares([...])` — model ki ek nayi wrapped copy banata hai jisme wo middleware inject ho gaya hai. Ab jab bhi `wrapped.invoke()` karega, pehle `before_model` chalega (REQUEST print), model se baat hogi, phir `after_model` (RESPONSE print).
* Mind it — original `model` usi tarah ka raha. Middleware sirf wrapped copy pe lagta hai.

Chala ke dekho — har call pe REQUEST aur RESPONSE print hoga, bina model ke code ko touch kiye.

## Where All This Is Useful

Middleware se tum model ke saath production-ready behaviour bana sakte ho — bina model class ko tode. Rules alag se rakho:

* **Logging** — logs har request, debugging easy.
* **Retry** — network hiccup pe apne aap try kar.
* **Fallback** — ek model girne pe doosra automatic.
* **Guardrails** — unsafe inputs/outputs turant pakdo.
* **PII** — sensitive data (email, card) detect/replace.

Yeh sab "har model call pe laga do" style hai. Jab tumhar pas ek hi model call hoti hai toh lagega extra, par real app mein ye hi hai jo cost control, security, aur reliability dete hain. Phase 6 mein guardrails ko aur deep karenge.

## Bridge — What Phase 1 Taught

Phase 1 pehla kadam tha — tumne LangChain ke core building blocks seekhe. Toolkit: model call, messages, structured output, tools, streaming, memory, middleware. Ye saare blocks ab tumhare paas hai jo kisi bhi agent ki backbone hain.

Agla phase hai **LangGraph** — jahan tum in blocks ko ek graph mein jodoge (nodes/edges) — controlled, multi-step agents jahan har kadam ka apna direction hota hai. Socho — Phase 1 mein tum blocks dekh rahe the; ab unse koi cheez assemble karte hai.

## What It Is NOT

⚠️ **Middleware = model ka code nahi badalta.** Wo model ke logic se alag rehta hai. Tum model call ke pehle/baad extra logic daalte ho bina model class ko modify kiye.

⚠️ **`before_model`/`after_model` har jagah same flow nahi.** Do alag hooks hai — before (pehle) aur after (baad). Inhe mix-up mat karo; har ek apna kaam.

⚠️ **Middleware sirf LangChain ki cheez nahi hai.** Ye ek general concept hai — Express/Next.js ke routers, JavaScript mein bhi middleware hota hai. LangChain ne usi concept ko model calls pe lagaya.
