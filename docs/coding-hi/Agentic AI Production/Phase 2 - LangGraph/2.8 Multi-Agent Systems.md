# 2.8 Multi-Agent Systems

Ab takh ek hi agent ek kaam karta tha — sochta, tool call karta, jawab deta. Par duniya mein bahut kaam aise hote hain jo ek se ziyada experts chahiye. Jaisa ek article likhane mein ek writer chahiye, phir ek reviewer. 

LangGraph mein ek hi graph ke andar **multiple agents** (subgraphs) rakh sakte hain jo ek dusre ke saath kaam karte hain — writer likhe, reviewer check kare, phir phir se writer theek kare. Ye **multi-agent system**.

## Supervisor pattern — ek manager, do workers

Sabse common design: ek **supervisor** (manager) node decide karta hai ki agle step pe kon chalega — writer ya reviewer ya khatam. Workers apna kaam karte hain, phir wapas supervisor ko bhej deti hain.

```python
from typing import Annotated, Literal, TypedDict
from langchain_groq import ChatGroq
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage
from langgraph.graph import StateGraph, START, END, add_messages
from langgraph.types import Command   # routing ke liye

llm = ChatGroq(model_name="llama-3.3-70b-versatile")

# --- shared state: messages + "next" (kaun agla worker chalega) ---
class State(TypedDict):
    messages: Annotated[list, add_messages]   # reducer = merge, naa replace
    next: Literal["writer", "reviewer", "FINISH"]

# --- Worker 1: writer (likhega ek draft) ---
def writer(state: State):
    res = llm.invoke([SystemMessage(content="Tum ek talented copywriter hain. User ke sawal pe ek accha jawaab likho.")] + state["messages"])
    return {"messages": [res], "next": "reviewer"}

# --- Worker 2: reviewer (check + correct) ---
def reviewer(state: State):
    res = llm.invoke([SystemMessage(content="Tum ek senior editor hain. Pichle jawab ko check karo, galati dhundho, behtar banao.")] + state["messages"])
    return {"messages": [res], "next": "FINISH"}

# --- Supervisor (manager decides who runs next) ---
def supervisor(state: State):
    prompt = ("Aap team manager hain. Team mein writer aur reviewer hain. "
              "Agar likha hua jawaab nahi hai to writer ko bulao. "
              "Agar likha hua hai to reviewer ko bulao. "
              "Agar kaam poora ho gaya ho to FINISH likho.")
    res = llm.invoke([SystemMessage(content=prompt)] + state["messages"])
    pick = res.content.strip().lower()
    next_ = "reviewer" if "reviewer" in pick else ("FINISH" if "finish" in pick or "poora" in pick else "writer")
    return {"next": next_}

# --- Graph bana do ---
builder = StateGraph(State)
builder.add_node("writer", writer)
builder.add_node("reviewer", reviewer)
builder.add_node("supervisor", supervisor)

def route(state):
    nxt = state.get("next", "FINISH")
    if nxt == "writer":   return "writer"
    if nxt == "reviewer": return "reviewer"
    return END

builder.add_edge(START, "supervisor")
builder.add_edge("writer", "supervisor")
builder.add_edge("reviewer", "supervisor")
builder.add_conditional_edges("supervisor", route)
graph = builder.compile()

# run
    result = graph.invoke(
        {"messages": [HumanMessage(content="Electromagnetic field kya hota hai? Thoda lamba batao.")]},
        {"configurable": {"thread_id": "multi-1"}},
    )
for m in result["messages"]:
    if isinstance(m, AIMessage):
        print("----"); print(m.content)
```

## Kaise chalta hai — step by step

1. `Annotated[list, add_messages]` — `messages` field ek **reducer** se jod ke li gayi. Matlab jab koi node `{"messages": [...]}` return karta hai, LangGraph purane messages se **merge** (append) karti hai, replace nahi. Bina reducer ke last value jalmahal ho jalta hai.
2. `next` field — ek string jo decide karta hai "agla kaun chalega". Supervisor isse set karta hai, router padhta hai.
3. `add_conditional_edges("supervisor", route)` — supervisor ke baad `route()` chalta hai, return karta hai node-name ya `END`. Graph usi hote se aage badhta hai — na ke seedhi linear.
4. Flow: START → supervisor (writer) → writer → supervisor (reviewer) → reviewer → supervisor (FINISH) → END. Har worker kaam karta hai, phir manager ke paas wapas aata hai.

## State kahan jatai hai beech workers ke?

Har worker apni `messages` ko update karti hai (reducer ke mazduri se judti rehti hai). Reviewer writer ke saare messages dekh kar apni review add karti hai. Ek hi `messages` list = ek shared board — sabko ek hi jagah milta hai.

## What It Is NOT

⚠️ **Multi-agent = ek jama thread pool nahi.** Har agent ek alag node/function hai, ek hi graph ke andar — shared state + routing ke saath.

⚠️ **Supervisor hamesha model-driven hona zaroori nahi.** Kabhū aap seedhi Python `if/else` se bhi route kar sakte hain (jaise `route()` function). Model se poochna flexible hota hai, lekin zaroori nahi.

⚠️ **Har worker ek full LLM call nahi hota.** Kabhi kabhi worker ek tool call ya calculation bhi karti hai — agent ek "role" hoti hai, koi strict template nahi.

## In Your Own Words

<details>
<summary>1. add_messages reducer kyun zaroori hai?</summary>

**Jawab:** Bina iske jab worker apna message return karega, dusre worker ke paas purana message nahi aayega (state overwrite ho jati). Reducer ensure karta hai naye messages purane mein judi rahein — seedhi conversation banti rahe.

</details>

<details>
<summary>2. Supervisor vs Worker — dono ka kya farq?</summary>

**Jawab:** Supervisor sirf decide karta hai "kaun agla chalega". Worker kaam karta — sochna, likhna, tool call karna. Agar supervisor khud kaam karega toh logic confuse ho jayega. Role-separation rakho.

</details>

<details>
<summary>3. route() return kya karta hai?</summary>

**Jawab:** route() ek node-name ("writer"/"reviewer") ya `END` return karta hai. Conditional edges use karti hai — graph seedhi nahi, dynamically decide karta hai kaunse node aage chalega.

</details>
