2.3 me tumne chat rooms banaye: room_id -> connections list, plus per-room message history. Same machinery — connections track karo, subset ko broadcast — live stock price streaming power karti hai. TradeStack ke backend me `streaming.py` naam ka module hai jo exactly ye karta hai, par chat messages ke bajaye market data ke liye.

Ye file **padhne ke liye hai, likhne ke liye nahi**. Hum TradeStack change nahi karenge. Hum uska pattern padhenge aur jo tum already jaante ho usme map karenge.

# 2.4 TradeStack WebSocket — Production Streaming Same Pattern Kaise Use Karta Hai

## Soch (Sochne Wala Scene)

Do scenarios socho:

**Scenario A (chat):** 5 dost ek room me. Koi bhi bol sakta hai. Sab sunte hain. Messages text hain. Koi "subscribe" nahi kar raha — wo bas present hain.

**Scenario B (trading):** 5 clients RELIANCE dekh rahe hain. Server Upstox (exchange feed) se connect hota hai, price ticks receive karta hai, aur in 5 clients ko push karta hai. Clients nahi bolte. Wo sirf sunte hain. Aur TCS dekhne wala client RELIANCE ticks nahi receive karna chahiye.

Difference hai **data ki direction** aur **subscription model**. Chat many-to-many hai (koi bhi send, sab receive). Trading one-to-many hai single upstream source se (Upstox -> server -> subscribers), symbol se filter.

Same WebSocket plumbing. Upar alag application logic.

## Concept: Upstox WebSocket for Live Price Ticks

Upstox (aur zyada brokers) live market data ke liye WebSocket endpoint expose karte hain. Tumhe har second "abhi price kya hai?" poll karne ki jagah, ek baar connect karo, symbols subscribe karo, aur broker **push** karta hai ticks jab wo hote hain.

Ek tick roughly aisa dikhta hai:

```json
{
  "type": "tick",
  "symbol": "RELIANCE",
  "ltp": 2450.50,
  "volume": 12345,
  "timestamp": "2026-11-04T09:15:03+05:30"
}
```

Tumhara server do jobs karta hai:
1. **Upstream:** Upstox WebSocket se connect, ticks receive.
2. **Downstream:** relevant ticks apne connected clients (browsers, dashboards) ko forward.

Ye **proxy/fan-out** pattern hai: ek upstream connection bahut saare downstream connections ko feed karta hai.

## Concept: Production me ConnectionManager

TradeStack ka `streaming.py` ek ConnectionManager use karta hai jo familiar lagta hai. Pattern ka simplified, readable version (exact production code nahi):

```python
# streaming.py (padhne ke liye simplified)
import json
import asyncio
from fastapi import WebSocket
from collections import defaultdict

class MarketStreamManager:
    def __init__(self):
        # symbol -> set of client WebSockets subscribed
        self.subscribers: dict[str, set[WebSocket]] = defaultdict(set)
        # symbol -> latest tick (cache taaki new subscribers current price le)
        self.latest: dict[str, dict] = {}
        # upstream connection to Upstox (ek poore server ke liye)
        self.upstream_ws = None

    async def subscribe(self, websocket: WebSocket, symbol: str):
        await websocket.accept()
        self.subscribers[symbol].add(websocket)
        # Cached latest tick immediately bhejo taaki client blank na rahe
        if symbol in self.latest:
            await websocket.send_text(json.dumps(self.latest[symbol]))

    def unsubscribe(self, websocket: WebSocket, symbol: str):
        self.subscribers[symbol].discard(websocket)

    async def on_tick(self, tick: dict):
        # Upstox ne naya tick push kiya
        symbol = tick["symbol"]
        self.latest[symbol] = tick
        # Sirf IS symbol ke subscribers ko fan out
        dead = []
        for ws in list(self.subscribers[symbol]):
            try:
                await ws.send_text(json.dumps(tick))
            except Exception:
                dead.append(ws)
        for ws in dead:
            self.subscribers[symbol].discard(ws)

    async def broadcast_all(self, message: str):
        # System messages (market open/close, errors) -> sab clients
        for symbol, subs in self.subscribers.items():
            for ws in list(subs):
                try:
                    await ws.send_text(message)
                except Exception:
                    subs.discard(ws)
```

Jo tum jaante ho usme map:
- `subscribe()` ≈ 2.2/2.3 ka `connect()` — handshake accept, connection store.
- `subscribers: symbol -> set[WebSocket]` ≈ rooms, par keyed by **symbol** instead of room_id.
- `unsubscribe()` ≈ `disconnect()`.
- `on_tick()` ≈ `broadcast(room_id)` — par triggered by upstream data, client message se nahi.
- `latest` cache ≈ message history, par "current state" hai "last N messages" nahi.

Shape identical hai RoomManager se. Sirf trigger badalta hai: chat me client message broadcast trigger karta hai; trading me upstream tick broadcast trigger karta hai.

## Concept: Chat vs Trading — Real Differences

| Aspect | Chat (2.3) | Trading (streaming.py) |
|--------|-----------|------------------------|
| Kaun data bhejta hai | Koi bhi client | Upstream broker (Upstox) |
| Kaun receive karta hai | Room ke sab | Us symbol ke subscribers |
| Client -> server messages | Haan (chat text) | Rare (subscribe/unsubscribe commands) |
| Data direction | Many-to-many | One-to-many (fan-out) |
| History | Last N messages | Latest tick (current state) |
| Subscription key | room_id | symbol |
| Ordering | Message order matters | Latest wins (stale ticks dropped) |

Sabse bada conceptual shift: chat me server **relay** hai (clients ke beech messages pass). Trading me server **gateway/proxy** hai (ek upstream feed bahut saare clients ko fanned out). WebSocket plumbing same; server ka role badalta hai.

## Concept: Real Pattern Padhna (Kya Dhoondhna Hai)

Jab tum TradeStack ka `streaming.py` kholo, ye paanch cheezein dhoondho — samajh aa jayega:

1. **Symbol keyed dict** (ya channel) holding connection sets — ye "rooms" equivalent hai.
2. **Upstream task** — ek `asyncio` task jo Upstox se connect karta hai aur `receive()` pe loop. Ye data source hai.
3. **Fan-out loop** — har upstream tick pe subscribers iterate aur `send_text`. Ye `broadcast()` hai.
4. **Cleanup path** — sends ke around `try/except`, dead sockets remove. Same as 2.2/2.3.
5. **Latest state cache** — taaki late-joining client immediately current price le, next tick ka wait na kare.

Ye paanch mil gaye to file samajh aa gayi. Baaki (auth, reconnect logic, heartbeat) plumbing hai.

## Concept: Subscribe/Unsubscribe Commands

Trading me clients sirf connect karke sab nahi receive karte. Wo commands bhejte hain:

```json
{ "action": "subscribe", "symbol": "RELIANCE" }
{ "action": "unsubscribe", "symbol": "RELIANCE" }
```

Endpoint inhe parse karta hai aur `manager.subscribe()` / `manager.unsubscribe()` call karta hai. Ye chat ka "join room" / "leave room" equivalent hai — par yahan client ek connection pe multiple symbols subscribe kar sakta hai, aur server symbol ke basis pe ticks filter karta hai.

Minimal endpoint:

```python
@app.websocket("/ws/market")
async def market_endpoint(websocket: WebSocket):
    await websocket.accept()
    subscribed = set()
    try:
        while True:
            raw = await websocket.receive_text()
            cmd = json.loads(raw)
            if cmd["action"] == "subscribe":
                symbol = cmd["symbol"]
                manager.subscribers[symbol].add(websocket)
                subscribed.add(symbol)
                if symbol in manager.latest:
                    await websocket.send_text(json.dumps(manager.latest[symbol]))
            elif cmd["action"] == "unsubscribe":
                symbol = cmd["symbol"]
                manager.subscribers[symbol].discard(websocket)
                subscribed.discard(symbol)
    except WebSocketDisconnect:
        # Is client ke SAB subscriptions clean karo
        for symbol in subscribed:
            manager.subscribers[symbol].discard(websocket)
```

Notice: ek connection multiple symbols subscribe kar sakta hai. Disconnect pe cleanup har subscribed symbol ke set se remove karna padta hai — isliye `subscribed` set track karta hai ki client ne kya maanga.

## What It Is NOT

- ❌ **Broker nahi hai** — TradeStack prices generate nahi karta. Wo Upstox feed proxy karta hai. Exchange source of truth hai.
- ❌ **Chat nahi hai** — clients ek doosre ko market data nahi bhejte. Data direction upstream -> server -> clients only.
- ❌ **Persistent nahi hai** — ticks ephemeral hain. History chahiye to time-series DB me store karo (ya at least latest cache). WebSocket layer khud kuch remember nahi karta.
- ❌ **REST ka replacement nahi** — "yesterday ka OHLC do" ya "order place karo" ke liye REST endpoints chahiye. WebSocket sirf live stream ke liye.
- ❌ **Ek machine pe scaled nahi** — ek process sab subscriptions hold karta hai. Real scale ke liye Redis pub/sub use karo server instances ke beech taaki instance A pe receive hua tick instance B ke clients tak pahunche.

## Nutshell

**Trading WebSocket = chat jaisa plumbing, alag role. Server gateway hai: ek upstream feed (Upstox) symbol ke basis pe subscribers ko fanned out. subscribe/unsubscribe = join/leave room. latest-tick cache = message history. streaming.py padho paanch cheezein dhoondh kar: symbol dict, upstream task, fan-out loop, cleanup, latest cache.**

## Common Mistakes (padhte ya likhte waqt)

- ❌ **"Har client directly Upstox se connect karta hai"** — nahi. Server pe ek upstream connection sab clients ko feed karta hai. Nahi to N clients = N broker connections, jo brokers allow nahi karte aur bandwidth waste hota.
- ❌ **"Ticks chat messages ki tarah store hote hain"** — nahi. Sirf latest tick per symbol cache hota hai. Har tick memory me store karna server ko OOM kar dega.
- ❌ **"Client ek baar globally subscribe karta hai"** — nahi. Subscription per-symbol hai. Ek client 10 symbols dekh sakta hai.
- ❌ **"Disconnect pe cleanup bhoolna"** — socket har subscribed symbol ke set se remove nahi kiya to dead sockets accumulate honge aur `send_text` forever throw karega.
- ❌ **"Isse chat samajhna"** — clients ko ticks broadcast karne mat do ek doosre ko. Data direction upstream -> server -> clients only.
