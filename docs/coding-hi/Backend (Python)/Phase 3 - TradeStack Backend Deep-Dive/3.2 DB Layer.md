3.1 mein tumne dekha `server.py` kaise organized hai — routes, middleware, lifespan, background tasks. Par har route jo data touch karta hai woh `src/db.py` mein call karta hai. Yeh file database layer hai. Phase 1 ka SQLite single connection tha single thread mein. TradeStack ka multi-threaded hai, WAL-mode, 9 tables aur migrations ke saath. Difference dekho.

# 3.2 DB Layer — SQLite Production Mein

## Soch (Sochne Wala Scene)

Phase 1 ka SQLite ek person with one notebook jaisa tha. Kholo, likho, band karo. No concurrency, no drama.

TradeStack ka SQLite office ka shared whiteboard jaisa hai. Multiple people (threads) same time pe likhna chahte hain. Agar sab same marker grab karein, smudged text aur arguments milenge. Toh har person ko apna marker do (thread-local connection) par same whiteboard (ek `.db` file on disk). Aur WAL mode on karo taaki readers writers ko block na karein aur writers readers ko — jaise whiteboard with transparent overlay sheet.

## Concept — Thread-Local Connections

FastAPI sync routes thread pool mein run hote hain. Background tasks apne threads mein. Agar sab threads ONE `sqlite3.Connection` share karein, "SQLite objects created in a thread can only be used in that thread" error milega.

TradeStack ka fix: `threading.local()`:

```python
_local = threading.local()

def get_connection() -> sqlite3.Connection:
    if not hasattr(_local, "conn") or _local.conn is None:
        DB_PATH.parent.mkdir(parents=True, exist_ok=True)
        _local.conn = sqlite3.connect(str(DB_PATH), timeout=10)
        _local.conn.row_factory = sqlite3.Row
        _local.conn.execute("PRAGMA journal_mode=WAL")
        _local.conn.execute("PRAGMA synchronous=NORMAL")
        _local.conn.execute("PRAGMA busy_timeout=5000")
        logger.debug(f"SQLite connection opened for thread {threading.current_thread().name}")
    return _local.conn
```

Har thread ko apna connection milta hai, lazily first use pe create, `_local` mein cache. Sab connections same on-disk file point karte hain. No cross-thread sharing, no errors.

Pragmas:
- `journal_mode=WAL` — Write-Ahead Logging. Writers `-wal` file mein append karte hain; readers main DB read karte hain. Readers aur writers ek doosre ko block nahi karte.
- `synchronous=NORMAL` — kam fsync. Faster writes, power loss pe tiny risk (is app ke liye acceptable).
- `busy_timeout=5000` — agar write lock held hai, 5 seconds wait karo instead of immediately fail. Rare collision handle karta hai.

## Concept — Schema (9 Tables)

`SCHEMA_SQL` tables create karta hai agar nahi hain (`CREATE TABLE IF NOT EXISTS`). Key ones:

| Table | Purpose |
|---|---|
| `cache_index` | `.pkl` cache files ka metadata index (symbol, row_count, first/last date, file size) |
| `upstox_config` | Upstox token + api key/secret (key-value) |
| `settings` | All app settings type/category/label/validation metadata ke saath |
| `settings_meta` | Settings schema version tracking |
| `stock_list_items` | Trading lists (continuation/reversal picks) close, trend_context, period ke saath |
| `breadth_results` | Per date market breadth (up/down counts, above/below MA) |
| `trade_log` | Paper trade entries entry/exit, P&L ke saath |

Clever part: `cache_index` `.pkl` files ka **metadata index** hai, data nahi. Actual OHLCV data `data/cache/RELIANCE.pkl` mein hai. SQLite sirf store karta hai "RELIANCE has 180 rows, last date 2026-11-03, file size 42 KB". Isse "list all cached symbols" instant (ek SQL query) instead of 2000 files glob.

## Concept — db.py Pattern (Domain-wise CRUD)

`db.py` domain-wise organized hai, har section apne functions ke saath:

```python
# --- Cache Index CRUD ---
def upsert_cache_index(symbol, row_count, first_date, last_date, file_size_bytes): ...
def get_cache_stats() -> dict: ...
def list_symbols_from_index() -> list[str]: ...
def rebuild_cache_index(cache_dir): ...

# --- Upstox Config CRUD ---
def upstox_get(key) -> Optional[str]: ...
def upstox_set(key, value): ...

# --- Settings CRUD ---
def settings_get_all() -> list[dict]: ...
def settings_get(key) -> Optional[dict]: ...
def settings_upsert(...): ...
def settings_set_value(key, value): ...

# --- Stock List CRUD ---
def add_stock_to_list(list_type, symbol, ...): ...
def get_stock_list(list_type): ...

# --- Breadth Results CRUD ---
def upsert_breadth(...): ...
def get_all_breadth(): ...

# --- Trade Log CRUD ---
def add_trade_log(...): ...
def get_trade_logs(...): ...
def update_trade_log(trade_id, exit_date, exit_price): ...
```

Har function same shape follow karta hai: get connection → execute SQL with `?` placeholders → commit → return. No ORM, no query builder. Raw SQL with parameterized queries (SQL injection safe).

## Concept — Batch Operations (Commit Control)

Bulk inserts mein per row commit slow hota hai. Toh batch variant hai:

```python
def upsert_cache_index(symbol, ...):
    conn = get_connection()
    conn.execute("INSERT ... ON CONFLICT DO UPDATE ...", (...))
    conn.commit()          # immediately commits

def upsert_cache_index_batch(symbol, ...):
    conn = get_connection()
    conn.execute("INSERT ... ON CONFLICT DO UPDATE ...", (...))
    # NO commit — caller commits later

def commit_cache_index():
    get_connection().commit()
```

`cache_manager.save()` default `commit=True` use karta hai but bulk rebuilds mein `commit=False` pass karta hai, phir ek baar end mein commit. Yeh 2000 commits ko 1 mein turn karta hai.

## Concept — Migrations (Schema Evolution)

Old databases mein new columns nahi hote. Migration framework ke bajaye, TradeStack lazy column adds karta hai:

```python
def _run_migrations():
    conn = get_connection()
    for col, dtype in [("exit_date", "TEXT"), ("pnl_type", "TEXT"), ("pnl_amount", "REAL"),
                       ("trade_type", "TEXT"), ("exit_price", "REAL"), ("quantity", "INTEGER DEFAULT 100")]:
        try:
            conn.execute(f"ALTER TABLE trade_log ADD COLUMN {col} {dtype}")
        except Exception:
            pass  # column already exists
    conn.commit()
```

Column add try karo; agar exist karta hai, exception swallow. Import pe run (`init_db()` phir `_run_migrations()`). Simple, idempotent, single-file DB ke liye kaafi.

## Concept — Init on Import

```python
# --- Initialize on import ---
init_db()
_run_migrations()
```

`db.py` ke bottom pe. Jab bhi koi module `from src.db import ...` kare, DB create aur migrate ho jaata hai. `server.py` early `db` import karta hai, toh routes run hone se pehle tables exist karte hain. `DB_PATH` env var `TRADESTACK_DB_PATH` se override ho sakta hai (tests prod data se isolate karne ke liye).

## Concept — Phase 1 Se Compare

| Phase 1 (mini) | TradeStack (production) |
|---|---|
| Single connection, single thread | Thread-local connections, one per thread |
| No WAL (default journal mode) | WAL mode + busy_timeout + synchronous=NORMAL |
| Ek table (`stocks`) | 9 tables (cache_index, settings, stock_list, breadth, trade_log, ...) |
| `CREATE TABLE` once | `CREATE TABLE IF NOT EXISTS` + lazy migrations |
| Har write pe commit | Bulk ops ke liye batch commit |
| Route mein direct sqlite3 calls | `db.py` mein domain-grouped CRUD functions |
| No env override | `TRADESTACK_DB_PATH` test isolation ke liye |

Pattern same hai (raw SQL, parameterized queries, commit). Difference concurrency safety aur scale mein hai.

## What It Is NOT

- ❌ **ORM nahi** — no SQLAlchemy, no models. Raw SQL with `?` placeholders.
- ❌ **Server process nahi** — SQLite ek file hai; separate DB server run karne ki zaroorat nahi.
- ❌ **Multi-process safe by default nahi** — thread-local connections ek process ke threads handle karte hain. Multiple server processes ko separate DB files ya real DB chahiye.
- ❌ **OHLCV data ka cache nahi** — SQLite metadata (cache_index) aur config (settings, lists, trades) store karta hai. Price data `.pkl` files mein hai.

## Nutshell

**TradeStack DB = ek SQLite file, thread-local connections, WAL mode, 9 tables, domain-grouped CRUD, lazy migrations, batch commits, env-overridable path. Phase 1 ka same raw-SQL pattern, multi-threaded production ke liye hardened.**

## Common Mistakes

- ❌ **"Threads ke beech ek connection share karo"** — SQLite throw karega "created in a thread can only be used in that thread". `threading.local()` use karo.
- ❌ **"WAL mode bhool jaana"** — default journal mode mein readers writers ko block karte hain (ya vice versa); production mein lock errors.
- ❌ **"Bulk mein per row commit"** — 2000 commits = slow. Batch variants + single commit use karo.
- ❌ **"DB path hardcode karo"** — tests isolate nahi kar sakte. Env var override use karo.
- ❌ **"Migrations separate step ke roop mein run karo"** — TradeStack import pe run karta hai, toh bhool nahi sakte.

<details>

</details>
