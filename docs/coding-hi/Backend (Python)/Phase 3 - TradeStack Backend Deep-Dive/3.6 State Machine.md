# 3.6 State Machine — Live Trader Logic, Order State Transitions

## Soch (Sochne Wala Scene)

Traffic light boolean "go/stop" nahi hai. States hain: RED, YELLOW, GREEN. Transitions constrained hain: GREEN → YELLOW → RED → GREEN. GREEN → RED directly jump nahi kar sakte, aur "GREEN" ka matlab specific hai (ja sakte ho). State batata hai next mein kya allowed hai.

State machine exactly yehi hai: fixed states ka set, aur explicit rules kaunse transitions legal hain. Code current state check karta hai before kuch bhi karne se, aur state sirf defined transitions se change hota hai.

## Concept — State Machine Kya Hai

State machine = (states, transitions, current state). Teen rules:

1. **Finite states** — small, enumerated set (not free-form strings).
2. **Transitions explicit** — `enter_position()` INITIALIZED → ENTERED move karta hai; kuch aur nahi.
3. **Actions state-gated** — `exit_position()` sirf tab sense karta hai jab state ENTERED hai.

TradeStack ka live trader 12 states define karta hai (`StockStateEnum`):

```python
# Python equivalent of the TS enum
from enum import Enum

class StockStateEnum(Enum):
    INITIALIZED = "initialized"
    WAITING_FOR_OPEN = "waiting_for_open"
    GAP_VALIDATED = "gap_validated"
    QUALIFIED = "qualified"
    SELECTED = "selected"
    WAITING_FOR_ENTRY = "waiting_for_entry"
    ENTERED = "entered"
    NOT_SELECTED = "not_selected"
    REJECTED = "rejected"
    UNSUBSCRIBED = "unsubscribed"
    EXITED = "exited"
```

Aur `transitionTo(newState, reason)` method jo har change log karta hai:

```python
def transitionTo(self, new_state, reason=""):
    old = self.state
    self.state = new_state
    msg = f"[{self.symbol}] State: {old} -> {new_state}" + (f" ({reason})" if reason else "")
    print(msg)
```

Har transition logged. Jab 9:47 AM pe trade galat ho, log replay karo aur exactly dekho state kya tha aur kyun move hua.

## Concept — Order States (Simpler View)

Orders ke liye classic state machine 4 states:

```
PENDING → OPEN → FILLED
              ↘ CANCELLED
```

- **PENDING**: order created, broker ko nahi bheja.
- **OPEN**: broker ko bheja, fill ka wait.
- **FILLED**: broker ne execution confirm.
- **CANCELLED**: fill se pehle cancel (user ya system).

Transitions:
- `PENDING → OPEN` (submit)
- `OPEN → FILLED` (broker fill)
- `OPEN → CANCELLED` (cancel)
- `PENDING → CANCELLED` (submit se pehle cancel)

Illegal: `FILLED → OPEN`, `CANCELLED → FILLED`, `FILLED → CANCELLED`. State machine inhe enforce karta hai sirf legal transitions define karke.

## Concept — Runnable Python State Machine (Orders)

Complete, runnable example, paste karke run:

```python
from enum import Enum

class OrderState(Enum):
    PENDING = "pending"
    OPEN = "open"
    FILLED = "filled"
    CANCELLED = "cancelled"

class Order:
    def __init__(self, symbol, qty, price):
        self.symbol = symbol
        self.qty = qty
        self.price = price
        self.state = OrderState.PENDING
        self._history = [OrderState.PENDING]

    def _transition(self, new_state):
        legal = {
            OrderState.PENDING: {OrderState.OPEN, OrderState.CANCELLED},
            OrderState.OPEN: {OrderState.FILLED, OrderState.CANCELLED},
            OrderState.FILLED: set(),
            OrderState.CANCELLED: set(),
        }
        if new_state not in legal[self.state]:
            raise ValueError(f"Illegal transition: {self.state.value} -> {new_state.value}")
        self.state = new_state
        self._history.append(new_state)
        print(f"[{self.symbol}] {self._history[-2].value} -> {new_state.value}")

    def submit(self):
        self._transition(OrderState.OPEN)

    def fill(self, fill_price):
        self._transition(OrderState.FILLED)
        self.price = fill_price

    def cancel(self):
        self._transition(OrderState.CANCELLED)

# Demo
o = Order("RELIANCE", 10, 2450.0)
o.submit()          # pending -> open
o.fill(2451.5)      # open -> filled
try:
    o.cancel()      # raises: filled terminal
except ValueError as e:
    print("Blocked:", e)

o2 = Order("TCS", 5, 3800.0)
o2.submit()
o2.cancel()         # open -> cancelled
print("History:", [s.value for s in o2._history])
```

Run: `pending -> open -> filled`, phir `cancel()` raises. Yehi bug prevented: filled order cancel nahi kar sakte.

## Concept — TradeStack Ka Real State Machine (Stocks, Not Orders)

TradeStack ka state machine orders ke baare mein nahi — **stocks being evaluated for entry** ke baare mein during live session. Har stock object `StateMachineMixin` (from `orb-base.ts`) mix in karta hai aur `state: StockStateEnum` hold karta hai.

Flow (reversal example):

```
INITIALIZED
  → (open price arrives) WAITING_FOR_OPEN
  → validateGap() → GAP_VALIDATED   (or REJECTED if gap too flat / too high)
  → checkLowViolation() → QUALIFIED  (or REJECTED if low violated)
  → prepareEntry() → SELECTED → WAITING_FOR_ENTRY
  → (entry trigger fires) → ENTERED
  → (exit trigger fires) → EXITED
```

Key methods, each state-gated:

```typescript
transitionTo(newState, reason = "") { ... }   // state change ka only way
reject(reason) { isActive=false; isSubscribed=false; transitionTo(REJECTED) }
validateGap(): boolean { ... }                 // INITIALIZED-ish -> GAP_VALIDATED or REJECTED
checkLowViolation(): boolean { ... }           // -> QUALIFIED or REJECTED
prepareEntry(): void { if state==QUALIFIED: transitionTo(SELECTED); ... }
enterPosition(price, ts) { ... transitionTo(ENTERED) }
exitPosition(price, ts, reason) { ... transitionTo(EXITED) }
```

Notice `prepareEntry()` check karta hai `if (this.state === StockStateEnum.QUALIFIED)` before SELECTED pe transition. Aur `enterPosition`/`exitPosition` state explicitly check nahi karte par tick processor sirf tab call karta hai jab state right ho. State single source of truth hai "stock kis phase mein hai".

## Concept — State Machine Bugs Kyun Prevent Karta Hai

State machine ke bina:

```python
if not entered and price > entry_high:
    enter()
if entered and price < stop_loss:
    exit()
```

Yeh break hota hai jab:
- Tick out of order aata hai (exit before enter).
- Do ticks simultaneously (double enter).
- Reconnect old ticks replay (exit ke baad re-enter).

State machine ke saath, state hi guard hai:

```python
def on_tick(self, price):
    if self.state == StockStateEnum.WAITING_FOR_ENTRY and price >= self.entry_price:
        self.enterPosition(price, now())
    elif self.state == StockStateEnum.ENTERED and price <= self.entry_sl:
        self.exitPosition(price, now(), "stop loss")
    # any other state: do nothing — tick irrelevant
```

`self.state` pe `elif` chain means ENTERED stock never re-enters, aur non-entered stock never exits. State "kya hua hai" ka memory hai; separate boolean flags jaise `entered`, `exited` nahi chahiye (though TradeStack convenience ke liye rakhta hai — state authoritative hai).

## Concept — State vs Flags (Tempting Mistake)

TradeStack ka mixin dono rakhta hai: `state: StockStateEnum` AND booleans (`entered`, `entryReady`, `gapValidated`). Slightly redundant but pragmatic — booleans hot tick paths mein fast check ke liye, aur `state` audit trail. Rule: **agar disagree karein, `state` trust karo**. Booleans caches hain; state truth hai.

## Concept — Terminal States

Kuch states terminal hain — no transitions out:

- `REJECTED` (stock failed a check; never trade)
- `EXITED` (position closed; done)
- `NOT_SELECTED` / `UNSUBSCRIBED`

Terminal states "zombie" re-evaluation se protect karte hain. Once rejected, stock session ke liye rejected rehta hai; tick revive nahi kar sakta. Reconnects mein crucial: replayed ticks duplicate entries trigger nahi karte.

## Concept — Phase 1/2 Se Compare

| Phase 1-2 | TradeStack (production) |
|---|---|
| Booleans (`is_connected`, `entered`) | Enum state + booleans |
| Ad-hoc `if` checks | Gated transitions via `transitionTo` |
| No transition log | Every transition logged with reason |
| No terminal states | REJECTED/EXITED terminal |
| Single flag per concern | One state machine per stock object |

## What It Is NOT

- ❌ **Database state nahi** — in-memory per stock, per session. Restarts reset all states.
- ❌ **Workflow engine nahi** — no persistence, no retries, no sagas. Sirf ek enum + transition method.
- ❌ **Thread-safe by default nahi** — state machine single-threaded tick processing per stock assume. Same stock pe concurrent ticks race karenge; tick processor serialize karta hai.
- ❌ **Order state nahi** — TradeStack ka machine *stock evaluation phase* track karta hai, not broker order lifecycle. (Orders separately SQLite `trade_log` mein logged.)

## Nutshell

**State machine = finite enum of states + explicit legal transitions + state-gated actions + logged transitions + terminal states. Ad-hoc boolean flags replace karta hai aur illegal sequences prevent (exit-before-enter, double-enter, zombie revival). TradeStack `StockStateEnum` (12 states) per stock use karta hai; simpler order version PENDING/OPEN/FILLED/CANCELLED use.**

## Common Mistakes

- ❌ **"Booleans use karo enum ke bajaye"** — booleans compose badly (3 booleans = 8 states, most illegal). Enum illegal states unrepresentable banata hai.
- ❌ **"Any transition allow karo"** — purpose defeat. `legal` map define karo aur illegal pe raise.
- ❌ **"Terminal states bhool jaana"** — inke bina rejected stock stray tick se revive ho sakta hai.
- ❌ **"Transition logging skip karo"** — 9:47 AM pe live trade misbehave kare toh log hi only evidence.
- ❌ **"State ke bajaye booleans trust karo"** — booleans caches hain; `state` truth. Disagree pe state wins.
