# 3.1 Server.py Walkthrough — 930 Lines Kaise Organized Hain

## Soch (Sochne Wala Scene)

Restaurant kitchen socho. Ek giant chef nahi hota jo sab kuch kare. Prep station, grill station, plating station, aur ek expediter jo orders coordinate kare. Har station ke apne tools hain, par same kitchen space share karte hain.

## Concept — Order Kyun Matter Karta Hai

FastAPI import time pe top-to-bottom execute hota hai. Toh:

- **Imports first** — `from src.scanner import ...` module run karta hai; agar scanner.py mein syntax error hai, server start hi nahi hoga.
- **Logging next** — logging setup karo before anything else logs, taaki early errors lost na ho.
- **Middleware before routes** — middleware every request wrap karta hai; routes define hone se pehle register hona chahiye (registration order = execution order).
- **Lifespan before `app = FastAPI(...)`** — lifespan function constructor mein pass hota hai, toh pehle exist karna chahiye.
- **`app = FastAPI(...)`** — yahan app object born hota hai. Iske baad sab attach hota hai.
- **Routes** — `@app.get` decorators `app` pe endpoints attach karte hain. `app` exist hone ke baad anywhere define ho sakte hain.
- **Background tasks** — plain functions, later defined, routes mein naam se reference.
- **Entry point** — sirf jab `python server.py` directly run karo (`__name__ == "__main__"`).

## Concept — Middleware (Do Layers)

Do middlewares stacked hain:

1. **CORSMiddleware** — frontend (`localhost:3000`) ko backend (`localhost:8001`) call karne deta hai. Iske bina browser har request block karega CORS error se.

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000", "http://127.0.0.1:3000"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

2. **AccessLogMiddleware** (custom, `BaseHTTPMiddleware`) — har request log karta hai aur `X-Process-Time` header add karta hai:

```python
class AccessLogMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        start = time.perf_counter()
        try:
            response = await call_next(request)
        except Exception:
            logger.exception(f"Unhandled error on {request.method} {request.url.path}")
            raise
        duration_ms = (time.perf_counter() - start) * 1000
        response.headers["X-Process-Time"] = f"{duration_ms:.1f}ms"
        logger.info(
            "access %s %s -> %d (%.1f ms)",
            request.method, request.url.path, response.status_code, duration_ms,
        )
        return response
```

`call_next(request)` magic call hai — request ko chain mein pass karta hai (next middleware ya route handler) aur response return karta hai. Timing/logging se wrap karo.

Global exception handler bhi hai jo kisi bhi unhandled exception ko consistent JSON 500 mein convert karta hai:

```python
@app.exception_handler(Exception)
def unhandled_exception_handler(request: Request, exc: Exception):
    logger.exception(f"Unhandled exception on {request.method} {request.url.path}")
    detail = f"Internal server error: {exc.__class__.__name__}"
    return JSONResponse(status_code=500, content={"detail": detail})
```

Isliye frontend hamesha `detail` read karta hai error responses se.

## Concept — Lifespan (Startup / Shutdown)

FastAPI ka modern way startup/shutdown code run karne ka `@asynccontextmanager` hai:

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # --- STARTUP ---
    stats = get_cache_stats()
    if stats["stock_count"] == 0:
        logger.info("Cache index is empty — rebuilding from .pkl files...")
        count = cache_manager.rebuild_index()
        logger.info(f"Cache index rebuilt: {count} entries")
    else:
        logger.info(f"Cache index has {stats['stock_count']} entries — no rebuild needed")
    logger.info("Startup complete")
    yield
    # --- SHUTDOWN ---
    logger.info("Shutdown complete")
```

`yield` se pehle ka code = startup (server boot pe run). `yield` ke baad ka code = shutdown (server stop pe run). `yield` control deta hai FastAPI ko beech mein requests serve karne ke liye.

TradeStack startup mein SQLite `cache_index` rebuild karta hai agar empty hai (first boot ya recovery). Shutdown mein kuch heavy nahi — connections thread-local hain aur OS clean karta hai.

## Concept — In-Memory Operation Tracking

Long-running jobs (bhavcopy update, scan, historical download) minutes lete hain. HTTP ek connection itni der hold nahi kar sakta reliably, toh TradeStack **polling pattern** use karta hai:

```python
active_operations: dict = {}

@app.post("/api/scanner/continuation")
def trigger_continuation_scan(request=None):
    operation_id = f"scan_{datetime.now().strftime('%Y%m%d_%H%M%S')}_{uuid.uuid4().hex[:6]}"
    active_operations[operation_id] = {
        "operation_id": operation_id,
        "type": "continuation_scan",
        "status": "starting",
        "progress": 0,
        "message": "Scanning...",
        "logs": [...],
    }
    t = threading.Thread(target=_run_continuation_scan, args=(operation_id, params, scan_date), daemon=True)
    t.start()
    return {"status": "started", "operation_id": operation_id}

@app.get("/api/scanner/status/{operation_id}")
def get_scan_status(operation_id: str):
    op = active_operations.get(operation_id)
    if not op:
        raise HTTPException(status_code=404, detail="Operation not found")
    return op
```

Flow: client POST karta hai → `operation_id` milta hai → `GET /status/{id}` poll karta hai every second → `progress`, `message`, `logs` read karta hai → jab `status` `completed`/`error` ho tab stop.

Mix hai: kuch jobs `BackgroundTasks` use karte hain (FastAPI built-in, response ke baad same event loop thread pool mein run) aur kuch `threading.Thread` (manual, CPU-bound scans ke liye). Dono same `active_operations[op_id]` dict update karte hain in place — yahi progress polling client tak stream hota hai.

## Concept — Background Tasks (Do Styles)

Style A — `BackgroundTasks` (FastAPI native):

```python
@app.post("/api/data/update-bhavcopy")
def trigger_update(background_tasks: BackgroundTasks, request=None):
    ...
    background_tasks.add_task(_run_bhavcopy_update, operation_id, target)
    return {"status": "started", "operation_id": operation_id}
```

FastAPI response bhejne ke baad `_run_bhavcopy_update` run karta hai. I/O-bound work ke liye good.

Style B — `threading.Thread` (manual):

```python
t = threading.Thread(target=_run_continuation_scan, args=(operation_id, params, scan_date), daemon=True)
t.start()
```

Scanner ke liye use hota hai kyunki CPU-bound aur blocking hai; thread event loop free rakhta hai. `daemon=True` means thread process ke saath die ho jaata hai (shutdown pe zombie threads nahi).

## What It Is NOT

- ❌ **Ek giant function nahi** — sections (health, data, token, scanner, stock list, breadth, trades) comment banners se glued.
- ❌ **Router-per-file nahi** — `routers/` folder nahi; sab `server.py` mein. TradeStack ne simplicity chose ki modularity ke over.
- ❌ **Async everywhere nahi** — routes sync `def` hain (FastAPI thread pool mein run). Sirf lifespan aur middleware `async` hain.
- ❌ **Stateless nahi** — `active_operations` in-memory hai; server restart wipe karta hai in-flight job progress.

## Nutshell

**server.py = imports → logging → middleware → lifespan → app → active_operations → route groups → background tasks → entry point. Top-to-bottom padho. Routes comment banners se grouped (banner naam Ctrl+F). Long jobs operation_id + polling pattern use karte hain.**

## Common Mistakes

- ❌ **"930 lines sab padhne padenge pehle"** — no. Pehle skeleton padho (imports, app, middleware, lifespan), phir jo section chahiye jump karo.
- ❌ **"BackgroundTasks aur threading.Thread same hain"** — no. BackgroundTasks FastAPI thread pool mein response ke baad run; threading.Thread manual hai aur tum manage karte ho. TradeStack dono deliberately use karta hai.
- ❌ **"active_operations restart ke baad persist karta hai"** — no, plain dict in memory. Restart = gone.
- ❌ **"Routes async hone chahiye"** — no. Sync `def` routes fine hain aur common blocking work ke liye; FastAPI thread pool handle karta hai.
- ❌ **"14 modules 14 files hain"** — no, 14 logical sections ek file mein (plus `src/` modules jo import hote hain).

1. `server.py` ke 9 sections order mein kya hain, aur order kyun matter karta hai?

<summary>Sample Answer</summary>

**Answer:** Imports → logging → middleware → lifespan → app creation → active_operations → route groups → background tasks → entry point. Order matters kyunki FastAPI import time pe top-to-bottom execute hota hai: logging exist hona chahiye before anything logs, middleware routes se pehle register, lifespan defined before `FastAPI(...)` mein pass, aur `app` exist before routes attach.

</details>

2. `lifespan` function startup mein kya karta hai, aur yeh `asynccontextmanager` kyun hai?

<details>
<summary>Sample Answer</summary>

**Answer:** Startup mein `get_cache_stats()` check karta hai; agar cache index empty hai (0 stocks), `cache_manager.rebuild_index()` se `.pkl` files se index rebuild karta hai. `asynccontextmanager` isliye taaki `yield` se pehle ka code startup pe run ho aur `yield` ke baad ka shutdown pe, aur `yield` beech mein FastAPI ko requests serve karne de.

</details>

3. Frontend kaise track karta hai long-running scan ka progress?

<details>
<summary>Sample Answer</summary>

**Answer:** POST trigger karta hai scan, `operation_id` receive karta hai, phir `GET /api/scanner/status/{operation_id}` poll karta hai every second. Server `active_operations[op_id]` mein dict store karta hai `status`, `progress`, `message`, `logs` ke saath, background thread in place update karta hai. Polling stop hota hai jab `status` `completed` ya `error` ho.

</details>

4. Is codebase mein `BackgroundTasks` aur `threading.Thread` mein kya farak hai, aur kaunse jobs kaunsa use karte hain?

<details>
<summary>Sample Answer</summary>

**Answer:** `BackgroundTasks` FastAPI-native hai — response ke baad FastAPI thread pool mein run, I/O-bound jobs jaise bhavcopy update ke liye. `threading.Thread` manual hai — khud create/start karo, CPU-bound scans ke liye taaki event loop free rahe. 5. Global `@app.exception_handler(Exception)` kyun hai?

<details>
