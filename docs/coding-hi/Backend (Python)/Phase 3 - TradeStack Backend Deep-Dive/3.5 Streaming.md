# 3.5 Streaming — Upstox WebSocket, Live Price Ticks, SSE Frontend Ko

## Soch (Sochne Wala Scene)

Newspaper batched hota hai: ek baar din mein print, subah deliver. Yeh REST + historical cache hai (3.3, 3.4). Radio station continuously broadcast karta hai; tune in karo aur suno abhi kya ho raha hai. Yeh WebSocket streaming hai. Radio se "kya play ho raha hai?" har 10 seconds nahi puchte — woh bas play karta hai, tum sunte ho.

TradeStack ka streaming radio station hai: ek upstream connection Upstox se (broadcaster), bahut saare downstream listeners (browser tabs, dashboards), symbol se filter.

## Concept — Streaming Kyun Exist Karta Hai (Polling Problem)

Streaming ke bina, frontend `GET /api/price/RELIANCE` har second poll karega. Problems:

- 1000 clients × 1 req/sec = 1000 req/sec server pe hammer.
- Har request connection open/close (HTTP overhead).
- Hamesha 1 second peeche (polling interval).
- Broker APIs rate limits; 2000 symbols directly poll karna impossible.

WebSocket streaming flip karta hai: ek baar connect, subscribe, broker **push** karta hai ticks as they happen. Server clients ko fan out. Zero polling, near-real-time, ek upstream connection.

## Concept — Architecture (Do Layers)

TradeStack ke do streaming layers hain:

1. **Backend (Python) — proxy/fan-out** (Phase 2.4 mein describe): `streaming.py` Upstox WebSocket se connect, ticks receive, subscribed frontend clients ko symbol se fan out. (Note: actual repo mein backend REST expose karta hai aur frontend Upstox se directly JS SDK se connect; pattern identical hai either way.)

2. **Frontend (TypeScript) — `streamer.ts`**: Upstox JS SDK ka `MarketDataStreamerV3` use karta hai Upstox se directly connect, protobuf-encoded ticks receive, decode, aur `onTick` callbacks call jo live trader aur UI feed karte hain.

Concepts same hain dono mein: symbol se subscribe, ticks fan out, reconnects handle, dead connections clean.

## Concept — Tick Processing (Tick Kaisa Dikhta Hai)

Upstox tick (decoded) carry karta hai:

## Concept — Backend Fan-Out Pattern (Python)

TradeStack ka actual live streaming frontend mein run hota hai, par backend proxy pattern canonical hai aur wohi build karte agar broker token server-side rakhna ho. Python version (Phase 2.4 match):

```python
import json, asyncio
from fastapi import WebSocket
from collections import defaultdict

class MarketStreamManager:
    def __init__(self):
        self.subscribers: dict[str, set[WebSocket]] = defaultdict(set)  # symbol -> clients
        self.latest: dict[str, dict] = {}                               # symbol -> last tick
        self.upstream_ws = None

    async def subscribe(self, websocket: WebSocket, symbol: str):
        await websocket.accept()
        self.subscribers[symbol].add(websocket)
        if symbol in self.latest:
            await websocket.send_text(json.dumps(self.latest[symbol]))  # instant current price

    def unsubscribe(self, websocket, symbol):
        self.subscribers[symbol].discard(websocket)

    async def on_tick(self, tick: dict):
        symbol = tick["symbol"]
        self.latest[symbol] = tick
        dead = []
        for ws in list(self.subscribers[symbol]):
            try:
                await ws.send_text(json.dumps(tick))
            except Exception:
                dead.append(ws)
        for ws in dead:
            self.subscribers[symbol].discard(ws)

    async def broadcast_all(self, message: str):
        for symbol, subs in self.subscribers.items():
            for ws in list(subs):
                try:
                    await ws.send_text(message)
                except Exception:
                    subs.discard(ws)
```

Aur endpoint jo subscribe/unsubscribe commands parse karta hai:

```python
@app.websocket("/ws/market")
async def market_endpoint(websocket: WebSocket):
    await websocket.accept()
    subscribed = set()
    try:
        while True:
            raw = await websocket.receive_text()
            cmd = json.loads(raw)
            if cmd["action"] == "subscribe":
                symbol = cmd["symbol"]
                manager.subscribers[symbol].add(websocket)
                subscribed.add(symbol)
                if symbol in manager.latest:
                    await websocket.send_text(json.dumps(manager.latest[symbol]))
            elif cmd["action"] == "unsubscribe":
                symbol = cmd["symbol"]
                manager.subscribers[symbol].discard(websocket)
                subscribed.discard(symbol)
    except WebSocketDisconnect:
        for symbol in subscribed:
            manager.subscribers[symbol].discard(websocket)
```

## Concept — SSE Frontend Ko (Server-Sent Events)

Sab kuch WebSocket nahi chahiye. One-way server→client streams jahan client never sends back (live scan progress, breadth updates, log tails), **SSE** simpler hai:

```python
from fastapi.responses import StreamingResponse
import asyncio, json

async def event_stream(operation_id: str):
    while True:
        op = active_operations.get(operation_id)
        if not op:
            yield f"data: {json.dumps({'error': 'not found'})}\n\n"
            break
        yield f"data: {json.dumps(op)}\n\n"
        if op["status"] in ("completed", "error"):
            break
        await asyncio.sleep(1)

@app.get("/api/stream/{operation_id}")
def stream_progress(operation_id: str):
    return StreamingResponse(event_stream(operation_id), media_type="text/event-stream")
```

SSE HTTP reuse karta hai (no upgrade handshake), browser mein `EventSource` se auto-reconnect, one-way. TradeStack aaj polling use karta hai (`GET /status/{id}`), par SSE natural upgrade hai "live" dashboards ke liye. Rule of thumb: **WebSocket** bidirectional ke liye (chat, subscribe/unsubscribe, live trader commands); **SSE** one-way server pushes ke liye (progress, ticks, logs).

## Concept — Reconnects & Resilience

Live streams break: network blips, server restarts, token expiry. Frontend `streamer.ts` handle karta hai:

- `reconnectAttempts` counter max 5.
- Exponential backoff: `5 * 2^(attempt-1)` seconds.
- `close` event pe, agar intentional nahi, `reconnect()` call.
- Reconnect success pe, all active instruments re-subscribe.
- Lock file per bot type (`reversal_bot.lock` / `continuation_bot.lock`) prevents two instances same symbols stream (duplicate orders).

## Concept — SSE vs WebSocket vs Polling

| Approach | Direction | Reconnect | Use case |
|---|---|---|---|
| Polling (`GET /status`) | Client pulls | Manual | Job progress (simple) |
| SSE (`EventSource`) | Server pushes, one-way | Auto (browser) | Live progress, logs, ticks (read-only) |
| WebSocket | Bidirectional | Manual (you code it) | Chat, subscribe/unsubscribe, live trader |

## Concept — Phase 2 Se Compare

| Phase 2 (mini) | TradeStack (production) |
|---|---|
| Single chat room | Symbol-keyed subscriptions |
| Clients send messages | Clients send subscribe/unsubscribe commands |
| Relay (client→client) | Gateway (Upstox→server→clients) |
| No reconnect logic | Exponential backoff + lock files |
| In-memory only | Latest-tick cache + reconnect-resubscribe |

## What It Is NOT

- ❌ **Broker nahi** — TradeStack prices generate nahi karta. Upstox proxy karta hai. Exchange source of truth.
- ❌ **Persistent nahi** — ticks ephemeral hain. History chahiye to time-series DB ya `.pkl` cache. Stream layer sirf latest tick per symbol yaad rakhta hai.
- ❌ **REST ka replacement nahi** — "yesterday ka OHLC do" ya "order place karo" ke liye REST endpoints chahiye. WebSocket sirf live stream ke liye.
- ❌ **Ek machine pe scaled nahi** — ek process sab subscriptions hold. Real scale Redis pub/sub between instances.

## Nutshell

**Streaming = ek upstream Upstox WebSocket → server ticks fan out to subscribers keyed by symbol, latest-tick cache aur reconnect logic ke saath. Bidirectional subscribe/unsubscribe ke liye WebSocket, one-way server pushes ke liye SSE, simple progress ke liye polling. Plumbing chat jaisa (Phase 2); sirf data direction aur subscription key badalta hai.**

## Common Mistakes

- ❌ **"Har client directly Upstox se connect karta hai"** — no. Ek upstream connection sab clients ko feed (broker connection limits).
- ❌ **"Ticks chat messages ki tarah store hote hain"** — no. Sirf latest tick per symbol cached. Har tick memory mein store karna server OOM kar dega.
- ❌ **"Subscription global hai"** — no, per-symbol. Ek client 10 symbols dekh sakta hai.
- ❌ **"Disconnect pe cleanup bhoolna"** — dead sockets har subscribed symbol ke set se remove hone chahiye.
- ❌ **"Isse chat samajhna"** — clients ek doosre ko ticks broadcast nahi karte. Data upstream → server → clients only.

## In Your Own Words

1. Ek sentence mein, chat WebSocket aur trading WebSocket mein kya farak hai?

<details>
<summary>Sample Answer</summary>

**Answer:** Chat many-to-many relay hai (koi bhi client send, room ke sab receive); trading one-to-many gateway hai (ek upstream feed symbol ke subscribers ko fanned out). Same WebSocket plumbing, different data direction aur subscription model.

</details>

2. Server Upstox se ek hi upstream connection kyun rakhta hai, har client ke liye alag nahi?

<details>
<summary>Sample Answer</summary>

**Answer:** Broker connection limits aur efficiency. Ek upstream connection all ticks receive karta hai; server unhe apne bahut saare clients ko fan out. Nahi toh N clients = N broker connections, jo brokers allow nahi karte aur bandwidth waste.

</details>

3. `latest` tick cache kis liye hai, aur chat ki message history se kaise alag hai?

<details>
<summary>Sample Answer</summary>

**Answer:** `latest[symbol]` most recent tick hold karta hai taaki newly subscribed client immediately current price le, next tick ka wait na kare. Chat history last N messages rakhti hai (list); trading sirf single latest value per symbol rakhta hai (current state, log nahi).

</details>

4. Kab SSE choose karna chahiye WebSocket ke bajaye live feature ke liye?

<details>
<summary>Sample Answer</summary>

**Answer:** Jab flow one-way server→client ho (live progress, log tails, read-only ticks) aur client kabhi send back nahi karta. SSE HTTP reuse karta hai, browser mein `EventSource` se auto-reconnect, simpler. WebSocket use karo jab client commands bhejna ho (subscribe/unsubscribe, chat, live trader actions).

</details>

5. Streaming module padhte waqt five cheezein kaun si dhoondhni hain?

<details>
<summary>Sample Answer</summary>

**Answer:** (1) symbol keyed dict holding connection sets, (2) upstream task broker se connect, (3) fan-out loop ticks subscribers ko bhejne wala, (4) dead sockets ka cleanup, (5) per symbol latest tick cache.

</details>
