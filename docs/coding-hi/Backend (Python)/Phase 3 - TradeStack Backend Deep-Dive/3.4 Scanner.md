# 3.4 Scanner — ProcessPoolExecutor, 2000 Stocks, 13 Indicators

## Soch (Sochne Wala Scene)

Phase 1 ka scan ek cook 4 vegetables chop karta hai — fast enough. TradeStack ka scan ek cook 2000 vegetables 13 different cuts each. Ek cook forever lagega. Toh vegetables bowls mein split karo, har bowl ek different cook (process) ko do, parallel chop. Sab bowls done, results combine.

Yehi `ProcessPoolExecutor` hai: 2000 symbols N chunks mein split, har chunk separate process mein run, results collect. Python ka GIL threads ko truly parallelize nahi karne deta CPU work ke liye — processes kar sakte hain.

## Concept — Kyun Processes, Not Threads

Python ka Global Interpreter Lock (GIL): ek time pe ek hi thread Python bytecode execute karta hai. I/O (network wait) ke liye threads help. CPU (indicators compute) ke liye threads nahi — bas turn-by-turn.

`ProcessPoolExecutor` separate Python processes spawn karta hai, har ek apna GIL aur memory. Multi-core pe true parallelism. Trade-off: processes memory share nahi kar sakte, toh arguments/results **picklable** hone chahiye (process boundaries pe serialize).

Isliye `_run_chunk` module-level function hai (not method) aur andar re-imports:

```python
def _run_chunk(symbols: list, params: dict, scan_date, mode: str) -> list[dict]:
    """Process a chunk of symbols in a worker process (module-level for pickling)."""
    from src.cache_manager import cache_manager
    from src.indicators import compute_all_indicators
    ...
```

Module-level = picklable. Andar re-imports isliye kyunki worker process fresh start hota hai — `cache_manager` import nahi hai wahan.

## Concept — Scanner Structure

```python
class ContinuationScanner:
    def __init__(self, params: dict):
        self.params = params

    def run(self, progress_callback=None, num_workers=None, scan_date=None) -> list[dict]:
        if scan_date is None:
            scan_date = _detect_scan_date()
        symbols = cache_manager.list_symbols()
        total = len(symbols)
        if total == 0:
            return []

        if num_workers is None:
            num_workers = min(os.cpu_count() or 4, total)

        chunk_size = max(1, total // num_workers)
        chunks = [symbols[i:i + chunk_size] for i in range(0, total, chunk_size)]

        results = []
        processed = 0

        with ProcessPoolExecutor(max_workers=num_workers) as pool:
            future_map = {pool.submit(_run_chunk, ch, self.params, scan_date, "continuation"): len(ch) for ch in chunks}
            for future in as_completed(future_map):
                chunk_len = future_map[future]
                try:
                    chunk_results = future.result()
                    results.extend(chunk_results)
                except Exception as e:
                    logger.error(f"Continuation chunk failed: {e}")
                processed += chunk_len
                if progress_callback:
                    pct = int((processed / total) * 100)
                    progress_callback(pct, f"Scanned {processed}/{total} stocks, found {len(results)} candidates")

        results.sort(key=lambda r: r["symbol"])
        return results
```

Steps:
1. Detect scan date (cache ka latest trading date) agar nahi diya.
2. Cache index se all symbols.
3. Worker count = `min(cpu_count, total)` (stocks se zyada processes mat spawn).
4. Symbols chunks mein split (ek per worker).
5. Har chunk pool mein submit → `Future` milta hai.
6. Jab chunk finish ho (`as_completed`), results collect.
7. Progress callback update (polling frontend movement dekhe).
8. Final results symbol se sort.

`ReversalScanner` identical hai except mode="reversal" aur apna `_analyze_pattern`.

## Concept — `_run_chunk` Per Stock Kya Karta Hai

```python
def _run_chunk(symbols, params, scan_date, mode):
    is_continuation = mode == "continuation"
    min_rows = params.get("cont_min_data_rows" if is_continuation else "rev_min_data_rows", 50)

    scanner = ContinuationScanner(params) if is_continuation else ReversalScanner(params)

    ind_params = {
        "sma_period": params.get("sma_period", 20),
        "adr_period": params.get("adr_period", 14),
        "high_low_period": params.get("high_low_period", 20),
        "ma_angle_points": params.get("ma_angle_points", 5),
        "price_change_periods": params.get("price_change_periods", [1, 5, 20]),
    }

    results = []
    for symbol in symbols:
        try:
            data = cache_manager.load(symbol)
            if data is None or len(data) < min_rows:
                continue
            if scan_date is not None and not _stock_has_date(data, scan_date):
                continue
            if scan_date is not None:
                data = data[data.index <= pd.Timestamp(scan_date)]   # no lookahead
                if len(data) < min_rows: continue

            data = compute_all_indicators(data, indicator_params=ind_params)
            latest = data.iloc[-1]

            if scanner._passes_filters(latest, data):
                hit = scanner._analyze_pattern(data)  # or _analyze_pattern(data, scan_date)
                if hit is not None:
                    results.append({**hit, "symbol": symbol, "close": round(float(latest["close"]), 2)})
        except Exception:
            pass
    return results
```

Per stock: load `.pkl` → enough rows check → scan date present check → slice to scan date (lookahead bias prevent) → indicators compute → filter → pattern analysis → hit append. Exceptions swallowed (ek bad stock scan nahi todna chahiye).

## Concept — Indicators (13 Mein Se)

`compute_all_indicators` (in `src/indicators.py`) DataFrame mein columns add karta hai. Scanner use karta hai: SMA (20), ADR (14-day avg daily range), high/low 20 days, MA angle, price change 1/5/20 days. Phase 1 mein 2 (SMA, RSI). TradeStack mein 13 — par scanner subset use karta hai; baaki other features (breadth, volume profile) use.

## Concept — Filters vs Pattern Analysis

Per stock do stages:

1. **`_passes_filters(latest, data)`** — cheap rejection. Price range, ADR minimum, liquidity (volume + movement days). Most stocks yahan fail aur expensive pattern work se pehle skip.

2. **`_analyze_pattern(data)`** — real logic. Continuation ke liye: 3-phase pattern detect (Phase 1 high above MA → Phase 2 decline below MA → Phase 3 recovery near MA, rising MA ke saath). Reversal ke liye: best decline period find (N consecutive red days, ≥10% decline) aur trend context classify.

Yeh two-stage design scan fast rakhta hai: filters O(1) per stock, pattern analysis O(lookback window).

## Concept — No Lookahead Bias

```python
if scan_date is not None:
    data = data[data.index <= pd.Timestamp(scan_date)]
```

Historical dates scan karte waqt, scanner sirf us date tak ka data dekhta hai. Iske bina "last Tuesday" ka scan secretly Wednesday ke prices use karega — cheating. Phase 1 nahi bother; production must.

## Concept — Progress Callback + Polling

Scanner `progress_callback(pct, msg)` leta hai aur har chunk ke baad call karta hai. Route wrap karta hai:

```python
def progress(pct, msg):
    op["progress"] = pct
    op["message"] = msg

scanner = ContinuationScanner(params)
results = scanner.run(progress_callback=progress, scan_date=scan_date)
```

Frontend `/api/scanner/status/{op_id}` poll karta hai aur `progress`/`message` read. Chunks out of order finish hote hain (`as_completed`), toh progress steps mein jump karta hai, smoothly nahi — fine hai.

## Concept — Phase 1 Se Compare

| Phase 1 (mini) | TradeStack (production) |
|---|---|
| 4 stocks | ~2000 stocks |
| 2 indicators (SMA, RSI) | 13 indicators |
| Simple `for` loop | `ProcessPoolExecutor` (N processes) |
| No chunking | Symbols N chunks mein split |
| No progress reporting | `progress_callback` per chunk |
| No date slicing | Slice to `scan_date` (no lookahead) |
| Ek scanner | Do scanners (continuation + reversal) |
| Sync, blocking | `threading.Thread` mein run (event loop free) |

## What It Is NOT

- ❌ **Threads nahi** — `ProcessPoolExecutor`, not `ThreadPoolExecutor`. CPU-bound work processes chahiye.
- ❌ **Shared memory nahi** — har process apna cache copy disk se load karta hai. Yehi true parallelism ka cost.
- ❌ **Deterministic order nahi** — `as_completed` finish order mein chunks return karta hai, submission order mein nahi. Results end mein sort.
- ❌ **Per-stock fault-tolerant nahi** — exceptions swallowed (`pass`), toh corrupt `.pkl` sirf us stock ko skip. No per-stock error reporting.

## Nutshell

**Scanner = 2000 symbols N chunks mein split → har chunk separate process mein run (ProcessPoolExecutor) → per stock: load .pkl → slice to scan date → indicators compute → filter → pattern analysis → hits collect → sort. Progress callback per chunk. Two-stage (cheap filter, phir pattern) fast rakhta hai.**

## Common Mistakes

- ❌ **"CPU-bound scans ke liye threads use karo"** — GIL parallelism prevent. Processes use karo.
- ❌ **"Scanner logic class method mein rakh ke `self` pool ko pass karo"** — picklable nahi. Module-level function use karo.
- ❌ **"Worker ke andar re-import bhool jaana"** — worker processes fresh start; `cache_manager` import nahi. `_run_chunk` ke andar re-import.
- ❌ **"scan_date slice skip karo"** — lookahead bias. Hamesha `data.index <= scan_date` slice.
- ❌ **"Ek bad stock whole scan crash kare"** — per-stock work try/except mein wrap aur `pass`. Scan complete hona chahiye.

## In Your Own Words

1. TradeStack scanning ke liye `ProcessPoolExecutor` kyun use karta hai `ThreadPoolExecutor` ke bajaye?

<details>
<summary>Sample Answer</summary>

**Answer:** Scanning CPU-bound hai (2000 stocks pe indicators compute). Python ka GIL ek time pe ek thread ko Python bytecode run karne deta hai, toh threads CPU work parallelize nahi kar sakte. Processes apna GIL aur memory rakhte hain, true multi-core parallelism. Trade-off: arguments/results picklable hone chahiye.

</details>

2. `_run_chunk` module-level function kyun hai jo andar `cache_manager` re-import karta hai?

<details>
<summary>Sample Answer</summary>

**Answer:** Module-level functions picklable hain, toh `ProcessPoolExecutor` unhe worker processes ko send kar sakta hai. `self` bound methods nahi. Re-import isliye kyunki worker processes fresh Python interpreter se start hote hain — `cache_manager` wahan import nahi hai.

</details>

3. Per-stock processing ke do stages kya hain, aur split kyun?

<details>
<summary>Sample Answer</summary>

**Answer:** (1) `_passes_filters` — price range, ADR, liquidity se cheap rejection. (2) `_analyze_pattern` — expensive pattern detection (3-phase continuation ya best-decline reversal). Split isliye taaki scan fast rahe: most stocks cheap filter pe fail aur pattern analysis tak nahi pahunchte.

</details>

4. "Lookahead bias" kya hai aur scanner kaise prevent karta hai?

<details>
<summary>Sample Answer</summary>

**Answer:** Lookahead bias future data use karna hai past date analyze karte waqt (e.g., "last Tuesday" scan Wednesday ke prices se). Scanner `data = data[data.index <= pd.Timestamp(scan_date)]` slice se prevent karta hai taaki har stock sirf scan date tak ka data dekhe.

</details>

5. Scanner se frontend tak progress reporting kaise kaam karta hai?

<details>
<summary>Sample Answer</summary>

**Answer:** Scanner `progress_callback(pct, msg)` leta hai aur har chunk finish hone pe call karta hai (`as_completed` ke saath). Route `pct`/`msg` ko `active_operations[op_id]` mein store karta hai. Frontend `GET /status/{op_id}` poll karta hai aur `progress` aur `message` read. Progress steps mein jump karta hai kyunki chunks out of order finish.

</details>
