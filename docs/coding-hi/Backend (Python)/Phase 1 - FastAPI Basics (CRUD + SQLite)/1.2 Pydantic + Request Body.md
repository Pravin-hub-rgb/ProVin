1.1 me tumne seekha — URL se **single values** kaise aati hain (path + query). Ab ek step aage.

DukaanOS wapas pehle. Customer ne billing ki. Ab counter pe baith ke staff ne wo data **type** karna shuru kiya — product ka naam, quantity, price. Ye data URL me nahi aa sakta — wo **body** me aata hai. Aur agar staff galti se price `"abc"` likh de, to system accept nahi karna chahiye.

Yehi Pydantic + Request Body ka kaam hai.

---

## Sochо (Sochne Wala Scene)

Tum DukaanOS ka counter chalara ho. Ek action ho raha hai — **"naya item add karo."**

1. Staff type karta hai: item ka naam **"Parle-G"**, category **"Biscuit"**, price **"10"**, stock **"50"**.
2. Ye 4 cheezein staff ke haath me hain, browser me form ke through **bheji** ja rahi hain server ko.
3. Server ko ye 4 values ek saath milni chahiye, aur har ek ka type check hona chahiye — `price` number hona chahiye, `name` string hona chahiye.

Ab sawal ye hai — **ye data server tak kaise jaata hai?**

1.1 me humne seekha tha URL se single value aati hai (`?limit=10`). Par yahan **4 values** hain, aur ek item describe karna hai. URL me daalna absurd hoga — `POST /api/items?name=Parle-G&category=Biscuit&price=10&stock=50`. Messy, length limit hai, aur har naye field ke liye URL badalna padega.

Isliye data ke liye **alag jagah** hai — **Request Body**. Ye wahi JSON hai jo tumne Phase 0 me `0.3 API and JSON` me padha tha. Browser JSON bhejta hai body me, FastAPI usse padhta hai.

## Manual Tareeka (dard wala)

Agar FastAPI na hota, to body read karna padta manually. FastAPI ke pehle (Starlette) tarike se ya phir raw bytes se:

```python
# Manual (ye bhi kabhi mat karna)
from starlette.requests import Request
import json

@app.post("/api/items")
async def add_item(request: Request):
    raw = await request.body()          # raw bytes
    data = json.loads(raw)              # manually JSON parse

    # Ab khud validate karo... har field pe if
    if "name" not in data:
        raise ValueError("name required")
    if "price" not in data:
        raise ValueError("price required")
    try:
        price = float(data["price"])    # manually convert
    except (ValueError, TypeError):
        raise ValueError("price must be a number")
    if price < 0:
        raise ValueError("price negative nahi ho sakta")

    return {"name": data["name"], "price": price}
```

Dekho kya dard hai:

- **`raw = await request.body()`** — raw bytes mile, unhe `json.loads` se manually parse karna pada.
- **Har field ke liye alag `if`** — `name` chahiye, `price` chahiye, `stock` chahiye. 4 fields = 8+ lines. Aur har naya field = 2 aur lines.
- **Manual type conversion** — `float(data["price"])`, phir `try/except` se error pakadna.
- **Custom error messages** — har field ke liye alag message likhna. Aur galat error format — user ko proper "field required" wala message nahi milega, balki raw exception.
- **Ye sab har endpoint pe repeat** — 48 endpoints pe ye likhoge to 48 baar same code.

Pydantic ye **saara dard ek line** me khatam kar deta hai.

## Concept: Pydantic Model = Data Ka Naqsha (Shape)

Pydantic me tum ek **class** define karte ho jo batati hai — *"is endpoint ka data aisa dikhna chahiye."* Ye class tumhare data ka **contract** hai.

```python
from pydantic import BaseModel

class ItemCreate(BaseModel):
    name: str
    category: str
    price: float
    stock: int = 0        # default — optional
```

Ab is class ka use karo:

```python
@app.post("/api/items")
def add_item(item: ItemCreate):
    # item ab ek validated object hai
    return {
        "name": item.name,
        "category": item.category,
        "price": item.price,
        "stock": item.stock,
    }
```

**Kya hua yahan?** Jaise hi `def add_item(item: ItemCreate)` likha, FastAPI ne khud:

1. **Body se JSON padha** — `await request.body()` aur `json.loads` tumhe bachaye.
2. **Har field validate kiya** — `name` string hai? `price` number hai? `stock` int hai? Galat hua to **422 reject**.
3. **Type convert kiya** — agar `"price": "10"` bheja (string me number), to Pydantic use `10` (float) bana dega. Tumhe `float()` likhne ki zaroorat nahi.
4. **Response me accept kiya** — ab `item` ek proper object hai, `item.price` se direct float milega.

**Type hints (`name: str`, `price: float`) hi validation ka kaam karte hain.** Jaise 1.1 me path/query params ke liye type hints kaam karte the, waise hi body ke liye.

---

## Concept: Request Body vs Path/Query — Kab Kaunsa?

Yeh sabse important decision hai. Rule clear kar do:

| Data kahan se aata hai | Kaise bhejte hain | FastAPI me | Example |
|---|---|---|---|
| **Kaunsa resource** (identity) | URL ke path me | Path param `{symbol}` | `/api/stocks/RELIANCE` |
| **Kya chahiye** (options/filter) | URL ke `?` ke baad | Query param `?limit=10` | `/api/stocks?limit=10` |
| **Naya data** (create/update) | Request **body** me (JSON) | Pydantic model | `POST /api/items` with JSON |

DukaanOS se samajho:
- *"RELIANCE ka data dikha"* → **GET** `/api/stocks/RELIANCE` — koi data bhej nahi rahe, sirf puch rahe hain. Query param optional hai (jaise `?days=90`).
- *"Naya item add kar"* → **POST** `/api/items` + **body** `{name, category, price}` — naya data bhej rahe hain, wo body me jaata hai.

**POST/PUT me data hamesha body se aata hai. GET/DELETE me data hamesha URL se.** Ye rule interview me bhi poochha jaata hai — yaad rakhna.

---

## Concept: Optional Fields aur Defaults

1.1 me `limit: int = 20` seekha tha. Body me bhi same rule — koi field chahiye to simple, optional hai to default ya `| None`.

```python
class ItemCreate(BaseModel):
    name: str                  # required — string chahiye
    price: float               # required — number chahiye
    category: str | None = None    # optional — default None
    stock: int = 0             # optional — default 0
    discount: float = 0.0      # optional — default 0.0
```

**Do tarah se optional likh sakte ho:**
- `stock: int = 0` — default value di (number, but specific)
- `category: str | None = None` — ya to string, ya `None` (bata nahi ki kya hoga)

Agar user sirf `{name, price}` bhejega, to Pydantic **khud** `category=None, stock=0, discount=0.0` bana dega. Tumhe koi `if` likhne ki zaroorat nahi "missing field" check karne ke liye.

## Concept: Response Models (bonus, 2 min me)

Abhi humne **input** validate karna seekha. **Output** bhi validate ho sakta hai — aur bahut ka kaam aata hai.

```python
class Item(BaseModel):
    id: int
    name: str
    price: float
    stock: int

@app.get("/api/items/{item_id}", response_model=Item)
def get_item(item_id: int):
    return {"id": item_id, "name": "Parle-G", "price": 10.0, "stock": 50, "secret": "delete_me"}
```

`response_model=Item` ka matlab — **sirf in 4 fields ka response jayega**. `secret` field automatically **filter out** ho jayega, kyunki wo `Item` model me nahi hai.

Ye do kaam karta hai:
1. **Response ka shape guarantee** — agar tu bhool ke `password` bhej de, to wo leak nahi hoga.
2. **Docs me exact schema** — Swagger me response ka structure sahi dikhega.

Real TradeStack me bhi yahi hota hai — scanner ke response typed models se jaate hain.

## Code: Complete Example (Step by Step)

Ek chhota, realistic items API — DukaanOS wala feel:

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="Trading Backend Basic")


# --- Models (data ka shape) ---

class ItemCreate(BaseModel):
    name: str
    price: float
    category: str | None = None
    stock: int = 0

class Item(BaseModel):
    id: int
    name: str
    price: float
    category: str | None = None
    stock: int


# In-memory storage (abhi — 1.4 me SQLite se replace karenge)
items: dict[int, Item] = {}
next_id = 1


# --- Endpoints ---

@app.post("/api/items", response_model=Item)
def create_item(data: ItemCreate):
    """Naya item banao."""
    global next_id
    item = Item(
        id=next_id,
        name=data.name,
        price=data.price,
        category=data.category,
        stock=data.stock,
    )
    items[next_id] = item
    next_id += 1
    return item


@app.get("/api/items/{item_id}", response_model=Item)
def get_item(item_id: int):
    """Ek item lao by id (1.1 ka path param)."""
    if item_id not in items:
        return {"error": "not found"}   # abhi simple; 1.3 me proper 404
    return items[item_id]


@app.get("/api/items", response_model=list[Item])
def list_items(limit: int = 20, category: str | None = None):
    """List karo, filter + limit ke saath (1.1 ka query param)."""
    result = list(items.values())
    if category:
        result = [i for i in result if (i.category or "").lower() == category.lower()]
    return result[:limit]
```

**Dekho ab kya hua:**

- `create_item` me **koi validation `if` nahi**. `data` pehle se validated hai — `price` float hai, `name` string hai. `data.stock` default `0` hai agar nahi bheja.
- `get_item` me **koi `int()` convert nahi** — `item_id` pehle se int hai (1.1 se).
- `list_items` me **koi query parse nahi** — `limit`, `category` seedhe aaye hain.

**Sirf business logic bacha** — dict me rakhna, filter karna, ID badhana. Baaki sab framework. Yehi FastAPI ka vaada hai — 48 endpoints likhne wale ko ye bachat ka kaam hota hai.

## Test: Kaise Verify Karein (Browser Se)

Server chalao `uvicorn app.main:app --reload`, phir `http://localhost:8000/docs` kholo.

**Test sequence (1.2 ke liye):**

1. **`POST /api/items`** — "Try it out" pe click karo, body me likho:
   ```json
   { "name": "Parle-G", "price": 10, "category": "Biscuit" }
   ```
   `stock` nahi bheja — dekho response me `"stock": 0` **automatically aa gaya** (default). Execute dabao.

2. **Type conversion test:** body me `"price": "25"` bhejo (string me number). Response me `"price": 25.0` aayega — **number** ban gaya. Pydantic ne convert kiya, bina tumhare code me kuch kiye.

3. **Validation test (sabse important):** body me `"price": "abc"` bhejo ya `name` hata ke bhejo. Dekho FastAPI **422** dega with field-level error — *"field required"* ya *"not a valid number"*. **Yehi Pydantic ka proof hai** — tumne koi `if` nahi likha tha, phir bhi galat data reject hua.

4. **`GET /api/items/1`** — path param se item lao. `GET /api/items?category=Biscuit&limit=5` — query param se filter.

Har step pe "Execute" dabao, **response aur status code dono** dekho. 200 = theek, 422 = validation ne kaam kiya.

## Nutshell

- **Request body** = naya/complex data jo JSON me aata hai (POST/PUT me).
- **Pydantic model** = data ka contract. Type hints likhi, to validation, conversion, aur docs **automatic**.
- Body ke liye model, path ke liye `{param}`, query ke liye `?param=` — **teen alag jagah, teen alag kaam**.
- `field: type` = required, `field: type = default` ya `field: type | None = None` = optional.
- Galat data FastAPI **422** se reject — tumhare code me koi `if` nahi likhna.

---

## Common Mistakes

1. **Body ke fields ko path param banana.** `POST /api/items/{name}/{price}` galat hai. Body wale fields (name, price, category) **hamesha body me** jaate hain, path me nahi. Path sirf identity ke liye.

2. **Optional field ko required banana.** `category: str` likhoge to wo **required** ho jayega — user na bheje to 422. Agar optional chahiye to `str | None = None` likho.

3. **`dict` body accept karna foran.** `def create(data: dict)` — kuch validate nahi hoga, koi type safety nahi. Hamesha Pydantic model banao shape ke liye.

4. **Body vs query mix karna.** Filter (jaise `?sector=IT`) query param hai. Sirf naya data body me. Confuse mat ho.

5. **Response me sensitive field bhejna.** Bina `response_model` ke poora object ja sakta hai (password leak). `response_model` lagao ya manually sirf safe fields bhejo.

6. **`from pydantic import BaseModel` bhoolna.** Ye import sabse upar — bina iske `BaseModel` undefined hoga aur error aayega.

## In Your Own Words

<details>
<summary>1. Pydantic model kyun banate hain? Manual validation se kya behtar hai?</summary>

Pydantic model data ka **contract** hai — ek class jisme type hints se pata chalta hai ki har field ka type kya hoga. Manual validation me har field ke liye alag `if` likhna padta, manually type convert karna padta, har field ka custom error message likhna padta, aur ye sab har endpoint pe repeat hota tha. Pydantic me ek class likhi to FastAPI khud **parse, validate, convert, aur docs generate** kar deta hai — aur wahi code 48 endpoints pe reuse hota hai. Validation ek jagah define hoti hai, har jagah automatically lagti hai.

</details>

<details>
<summary>2. Request body aur query parameter me kya farak hai? Kab kaunsa use hoga?</summary>

Request body naya ya complex data bhejne ke liye hai — jo client **bhej** raha hai (jaise naya item: name, price, category), aur ye POST/PUT me JSON body me aata hai. Query parameter **filter/options** ke liye hai — jo client **maang** raha hai (jaise `?limit=10`, `?sector=IT`), aur ye GET me `?` ke baad aata hai. Rule: **naya data = body, filter/options = query, identity = path.**

</details>

<details>
<summary>3. `price: float` likha, user ne `"price": "10"` (string) bheja. Kya hoga?</summary>

Pydantic **automatically convert** kar dega. Wo `"10"` string ko dekhke, `float` type hint ke hisaab se, `10.0` float bana dega — aur app accept kar lega. Ye manual tareeke se mushkil tha jahan tumhe khud `float()` call karna padta. **Par** agar user `"price": "abc"` bheje (jo number nahi hai), to Pydantic convert nahi kar paayega aur **422 error** de dega — kyunki `"abc"` valid float nahi hai. Ye validation ka kaam hai.

</details>

<details>
<summary>4. Optional field kaise banate hain? `stock: int = 0` aur `stock: int | None = None` me kya farak hai?</summary>

Dono optional hain — matlab user bhej de ya na bheje, dono chalega. `stock: int = 0` ka matlab hai "default value 0 rakh do agar nahi bheja" — to field hamesha number rahega (0 ya koi aur number). `stock: int | None = None` ka matlab hai "default None rakh do, aur ye legitimately None bhi ho sakta hai" (jaise "stock ki info maloom nahi"). Simple soch: agar default me koi **specific value** chahiye to `= value`, agar **"hoga bhi ya nahi bhi"** wala semantics hai to `| None = None`.

</details>

<details>
<summary>5. `response_model=Item` kya karta hai? Ye validate ke liye bhi hai ya sirf output shape ke liye?</summary>

`response_model` mainly **output ka shape** control karta hai — FastAPI sirf us model me **defined fields** hi response me bhejega, baaki filter out kar dega. Ye **security** ke liye bhi important hai (jaise password field galti se leak na ho) aur **docs** ke liye bhi (Swagger me sahi schema dikhe). Ye input validation ki tarah kaam nahi karta — wo `ItemCreate` model (function parameter) karta hai. Response sirf tab validate hota hai ki sahi fields hain.

</details>

<details>
<summary>6. GET request me body kyun nahi hoti?</summary>

GET ka matlab hai "mujhe kuch **de** do" — read-only. Data body me bhejne ka koi logical reason nahi — URL me params rakhna cleaner hai, browser me bookmark kar sakta hai, aur caching kaam karti hai. GET me agar body bhejo to bhi technically ho sakta hai (sirf `def` likh do na `async def`), par ye **anti-pattern** hai — bahut se clients aur proxies GET bodies ignore kar dete hain. Isliye rule ban gaya: **GET/DELETE me data = URL (path/query), POST/PUT me data = body.**

</details>

## What It Is NOT

- ❌ **Ye data store nahi kar raha** — `items` dict me memory me hai, restart pe gayab. SQLite (1.4) se fix hoga.
- ❌ **Ye authentication nahi** — koi bhi koi bhi item bana sakta hai. Real me token check hoga (Phase 2/3).
- ❌ **Ye complex validation nahi** — jaise "price aur stock dono ek saath zero na hoon." Ye Pydantic ke advanced validators se hoga, baad me.
- ❌ **Ye nested objects nahi** — `metadata: dict` ya list of objects bhejna Pydantic me ho sakta hai, par abhi simple flat fields seekh rahe hain.

## Agle Step Mein Kya Hoga?

Ab tumhe pata hai data **aata** kaise hai aur validate kaise hota hai. Par abhi ek bada problem hai — data **khatam** ho jaata hai restart pe! `items` dict memory me hai, server band karo, sab gayab.

Iska solution hai **SQLite** — ek file-based database jo restart pe bhi data rakhta hai. Par usse pehle ek zaroori concept: **CRUD** — Create, Read, Update, Delete — poora data lifecycle. Kyunki abhi humne sirf Create (POST) aur Read (GET) banaye. Update aur Delete kaise hote hain, aur har ek me kya alag hota hai, wo 1.3 me.
