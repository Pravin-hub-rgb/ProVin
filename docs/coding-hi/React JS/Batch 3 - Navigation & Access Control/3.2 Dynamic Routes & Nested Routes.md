## What Happened So Far

In 3.1, we learned React Router setup — BrowserRouter, Routes, Route, Link, NavLink, useNavigate. Those were static routes — each path was fixed (`/`, `/movies`, `/about`). But real apps have dynamic URLs — like `/movies/tt123456` where `tt123456` changes per movie.

Now we'll learn: dynamic routes (capturing values from URLs) and nested routes (reusable layout patterns).

## Broader Goal

Without dynamic routes, you'd need a separate Route for every single item — `/movies/inception`, `/movies/interstellar`, `/movies/matrix`. With 1000 movies, that's 1000 routes. Not feasible. Dynamic routes solve this with a single pattern.

Nested routes solve a different problem: layouts. Imagine a Movie Browser where every page shares the same navbar, sidebar, footer. Without nested routes, you'd repeat the navbar in every page component. With nested routes, a parent Layout renders once, and child routes only provide the changing content.

## Step 1 — Dynamic Routes and `useParams`

### 1.1 Concept — Variables in the URL

Think back to 3.1 — static routes like `/`, `/movies`, `/about`. Now imagine a store with a product catalog. Each product has its own URL — `/products/p1`, `/products/p2`, `/products/p3`. That `p1` part changes per product — it's a variable in the URL.

React Router captures variables with `useParams`, and marks them in the path with a colon (`:`).

### 1.2 Syntax — Defining Variables with `:`

Put a colon wherever you need a variable segment:

```tsx
<Route path="/products/:id" element={<ProductDetail />} />
```

Visual mapping:

```
URL:           /products/p1
                      └── this segment is variable

Route Path:    /products/:id
                      └── :id captures "p1"
```

`:id` is just a label. You could use `:productId`, `:slug`, `:itemId` — whatever name you use, that's what `useParams` returns.

### 1.3 Minimal Example — Just Using `useParams`

A simple component that pulls ID from URL and displays it:

```tsx
// components/ProductDetail.tsx — minimal version
import { useParams } from "react-router-dom";

export default function ProductDetail() {
  const { id } = useParams();
  return <h2>Product ID: {id}</h2>;
}
```

That's it. `useParams()` returns an object: `{ id: "p1" }`. Destructure to get `id`. Now you can do anything with it — API call, data lookup, etc.

### 1.4 Flow — When User Visits `/products/p1`

Step by step:

1. Browser URL changes to `/products/p1`
2. React Router searches `Routes` for a matching path — `"/products/:id"` matches
3. `:id` captures the variable segment — `"p1"`
4. React Router stores this internally
5. `<ProductDetail />` renders
6. Inside the component, `useParams()` is called — React Router returns the stored value: `{ id: "p1" }`
7. Destructuring gives us `id = "p1"`

Every dynamic route follows this same pattern. URL segment is captured → `useParams` retrieves it → use it however you need.

### 1.5 Real Example — ProductDetail with Data Lookup

Now a real component that uses the ID to find and display product data:

```tsx
// components/ProductDetail.tsx — full version
import { useParams } from "react-router-dom";

// Step 1 — product data (array of objects, each with its own id)
const products = [
  { id: "p1", name: "Wireless Headphones", price: 2499, desc: "Noise-cancelling Bluetooth 5.0 headphones with 30hr battery life." },
  { id: "p2", name: "Smart Watch", price: 3999, desc: "Fitness tracker with heart rate monitor, GPS, and 7 days battery." },
  { id: "p3", name: "USB-C Hub", price: 1299, desc: "7-in-1 USB-C hub with HDMI 4K, USB 3.0, and SD card reader." },
];

export default function ProductDetail() {
  // Step 2 — extract ID from URL
  const { id } = useParams<{ id: string }>();

  // Step 3 — find the product (.find on the array)
  const product = products.find(p => p.id === id);

  // Step 4 — guard: did we find it?
  if (!product) {
    return <h2>Product not found</h2>;
  }

  // Step 5 — render
  return (
    <div className="product-detail">
      <h1>{product.name}</h1>
      <p><strong>Price:</strong> ₹{product.price}</p>
      <p>{product.desc}</p>
    </div>
  );
}
```

Each step does a clear job:
- **Step 1:** Product data — an array of objects, each with its own `id` property. Normally this comes from an API, but hardcoded for now.
- **Step 2:** `useParams` extracts the `:id` from the URL
- **Step 3:** `products.find(p => p.id === id)` — finds the first matching object. Returns the object, or `undefined` if not found.
- **Step 4:** Guard — if no product found (invalid ID), show "not found"
- **Step 5:** If found, render the details

> **Why an array?** Arrays support both `.map()` (for rendering lists) and `.find()` (for lookups). A plain object (Record) only supports bracket notation `[id]`, not `.map()`. Using arrays here because we'll need both operations.

### When the ID is Invalid

Always add a guard — `if (!product)`. A user can type anything in the browser — `/products/xyz` — and that product won't exist. The `ProductDetail` component must handle every state: found, not found, loading (if fetching from API).

> **What It Is NOT:** `useParams` doesn't parse the URL itself — React Router does. `useParams` just returns the values that were matched against the route's colon segments. And `useParams` takes a TypeScript generic — `<{ id: string }>` — for proper typing.

## Step 2 — Nested Routes with `Outlet`

### 2.1 Nested Routes Syntax

#### Two Ways to Express the Same Thing

In 3.1, we wrote routes flat — one line each:

```tsx
<Route path="/products/:id" element={<ProductDetail />} />
```

This is a **flat route** — path is full, component is inline. Works fine, simple enough.

But what if we need more routes under `/products`? Like featured products, reviews:

```tsx
<Route path="/products/:id" element={<ProductDetail />} />
<Route path="/products/featured" element={<FeaturedProducts />} />
<Route path="/products/reviews" element={<Reviews />} />
```

`/products/` repeats every time. With 10 routes, that's 10 repetitions. Want to change the parent path to `/catalog`? You'd edit every single route.

**Nested routes** solve this — one parent `Route` with the shared path, and children with only their unique part:

```tsx
<Route path="products">
  <Route path=":id" element={<ProductDetail />} />
  <Route path="featured" element={<FeaturedProducts />} />
  <Route path="reviews" element={<Reviews />} />
</Route>
```

The parent path `"products"` is automatically prepended to all children. React Router handles the concatenation.

#### Both Approaches — Same Result

| Flat Route (3.1 style) | Nested Route (3.2 style) |
|---|---|
| `<Route path="/products/:id" ... />` | `<Route path="products"><Route path=":id" ... /></Route>` |
| `<Route path="/products/featured" ... />` | `<Route path="products"><Route path="featured" ... /></Route>` |
| `<Route path="/products/reviews" ... />` | `<Route path="products"><Route path="reviews" ... /></Route>` |

The URLs are identical — `/products/ps5`, `/products/featured`, `/products/reviews`. The only difference is code organization.

#### Why Do Devs Use Nesting?

1. **No repetition** — `/products/` is written once in the parent, no more repetition
2. **Clear URL structure** — all `/products` routes are visibly grouped
3. **Change parent path in one place** — change `"products"` to `"catalog"`, all children update automatically
4. **Parent can have `element` + `<Outlet />`** — create a layout once, children render inside it (we'll see this next)

#### Multiple Children

```tsx
<Route path="products">
  <Route path=":id" element={<ProductDetail />} />
  <Route path="featured" element={<FeaturedProducts />} />
  <Route path="reviews" element={<Reviews />} />
</Route>
```

Each child is relative to its parent:

| Child Path | Full URL | Component |
|---|---|---|
| `:id` | `/products/ps5` | ProductDetail |
| `featured` | `/products/featured` | FeaturedProducts |
| `reviews` | `/products/reviews` | Reviews |

#### Parent Can Have `element` (Optional)

Notice — the parent `<Route>` has no `element` right now:

```tsx
<Route path="products">           {/* no element prop — just grouping */}
  <Route path=":id" element={<ProductDetail />} />
</Route>
```

This is just **grouping** — child routes are organized under a shared prefix. But you can also give the parent an `element` — a Layout component. That Layout renders once, and children go inside it via `<Outlet />`. We cover that in the next section.

#### Key Points

- **Flat route = everything on one line** — simple, fine for fewer routes
- **Nested route = parent groups children** — organized, maintainable, avoids repetition
- **Both produce the same URLs** — the difference is only code structure
- **Parent's `element` is optional** — without it, just grouping; with it, Layout + Outlet
- **One parent, multiple children** — each child has its own path and component

### 2.2 Problem — Layout Repetition

Back in 3.1, you saw that each page component had to repeat the navbar:

```tsx
// Old style — navbar repeated in every component
function HomePage() {
  return (
    <div>
      <nav>
        <Link to="/">Home</Link>
        <Link to="/products">Products</Link>
      </nav>
      <hr />
      <h2>Welcome</h2>
    </div>
  );
}

function ProductList() {
  return (
    <div>
      <nav>                     {/* same navbar again */}
        <Link to="/">Home</Link>
        <Link to="/products">Products</Link>
      </nav>
      <hr />
      <h2>Products</h2>
    </div>
  );
}
```

If you need to change the navbar, you'd edit every single component. Nested routes solve this — a parent Layout with `<Outlet />`, and child routes only provide the content that changes.

### 2.3 Visual — Route Tree

Think of nested routes as a tree:

```
Path: "/"
└── Layout
    ├── index       → HomePage       (URL: /)
    ├── products    → ProductList    (URL: /products)
    ├── products/:id → ProductDetail  (URL: /products/p1)
    └── *           → NotFound       (URL: /xyz)
```

The parent route (`/`) has `<Layout />` as its `element`. Layout contains `<Outlet />`, where child route content renders. When the URL is `/products`, Layout renders and Outlet shows ProductList. When URL is `/products/p1`, Outlet shows ProductDetail.

> **Note:** In 3.1, we saw a parent `<Route>` without `element` — just grouping. Here, the parent **has** an `element` — a Layout component. The Layout decides where child content goes.

### 2.4 Solution — Layout + `Outlet`

Now we see the problem (navbar repetition) and the nesting syntax (2.1). Let's see how parent `element` + `<Outlet />` solve it.

#### What is `Outlet`?

`<Outlet />` is a **placeholder component** that React Router provides. Put it in your parent Layout, and the matched child route's component renders there.

Think of it like a TV and an HDMI port:
- **Layout** = the TV (the frame stays the same — navbar, footer)
- **`<Outlet />`** = the HDMI port (where you plug in different devices)
- **Child route** = the device you plug in (PlayStation = Home, Fire Stick = Products)

The TV frame doesn't change. Just the content at the HDMI port changes.

#### Syntax

```tsx
import { Outlet } from "react-router-dom";

function Layout() {
  return (
    <div>
      <nav>Home | Products</nav>
      <hr />
      <Outlet />     {/* child route renders here */}
    </div>
  );
}
```

Give the parent route `element={<Layout />}`, and place `<Outlet />` inside it:

```tsx
<Route path="/" element={<Layout />}>
  <Route index element={<HomePage />} />
  <Route path="products" element={<ProductList />} />
</Route>
```

#### How It Works

```
URL: /             → Layout renders → Outlet renders HomePage
URL: /products     → Layout renders → Outlet renders ProductList
```

Layout renders every time — navbar stays visible. Only the Outlet content changes based on the child route.

#### Without `Outlet` — What Happens?

If the parent Layout doesn't have `<Outlet />`, child routes never render:

```tsx
function Layout() {
  return (
    <div>
      <nav>
        <Link to="/">Home</Link>
        <Link to="/products">Products</Link>
      </nav>
      {/* ❌ No <Outlet /> — child routes never render */}
    </div>
  );
}
```

Visit `/products` and you'll only see the navbar — `ProductList` never appears. `Outlet` is the slot React Router uses to say "render the child here."

#### Minimal Example — Outlet in Action

With just two child routes to see the pattern:

```tsx
// App.tsx
import { BrowserRouter, Routes, Route, Link, Outlet } from "react-router-dom";

function Layout() {
  return (
    <div>
      <nav>
        <Link to="/">Home</Link>
        <Link to="/products">Products</Link>
      </nav>
      <hr />
      <Outlet />   {/* child route renders here */}
    </div>
  );
}

export default function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Layout />}>
          <Route index element={<HomePage />} />
          <Route path="products" element={<ProductList />} />
        </Route>
      </Routes>
    </BrowserRouter>
  );
}
```

Notice the structure:
- **Parent:** `<Route path="/" element={<Layout />}>` — Layout renders at `/`. It contains `<Outlet />` where children render
- **Index child:** `<Route index element={<HomePage />} />` — when URL is exactly `/`, HomePage renders in Layout's Outlet
- **Relative path:** `<Route path="products" ... />` — `path` is relative to parent (3.1's concept). Full path becomes `/products`. ProductList renders in the Outlet.

**What renders visually:**

```
URL: /
     ↓
Layout → <nav>Home | Products</nav> <hr /> [Outlet → HomePage]

URL: /products
     ↓
Layout → <nav>Home | Products</nav> <hr /> [Outlet → ProductList]
```

`Outlet` acts like a switch — the child route's content appears there, while Layout stays the same.

### 2.5 Build Up — Adding Dynamic Route and 404

Now Layout + Outlet is set up. Adding new routes is simple — just add a child `<Route>`. Let's add two more:

```tsx
<Route path="/" element={<Layout />}>
  <Route index element={<HomePage />} />
  <Route path="movies" element={<MovieList />} />
  <Route path="movies/:id" element={<MovieDetail />} />   {/* dynamic */}
  <Route path="*" element={<NotFound />} />                {/* 404 */}
</Route>
```

Layout now has 4 child routes:

| Route | URL | Component | Source |
|---|---|---|---|
| `index` | `/` | HomePage | From 2.4 |
| `movies` | `/movies` | MovieList | From 2.4 |
| `movies/:id` | `/movies/p1` | MovieDetail | **Step 1**'s dynamic route, now under Layout |
| `*` | `/xyz` | NotFound | **3.1**'s catch-all, now under Layout |

Each new route just changes the content. Layout stays the same — now even the 404 page has a navbar! (3.1's `*` was standalone; here it's inside Layout.)

> **Important — `useParams` with Nested Routes:** Nesting doesn't affect `useParams`. Whether `ProductDetail` renders flat (Step 1 style) or nested under Layout, the URL is the same — `/movies/p1`. `useParams` extracts from the URL, not the route tree. So `useParams()` always returns `{ id: "p1" }`.

### 2.6 Index Route — What and Why

When you build nested routes, a question comes up: **"When the URL matches just the parent path, what should the child show?"**

Without an index route, there's no matching child:

```tsx
<Route path="/" element={<Layout />}>
  <Route path="products" element={<ProductList />} />
  <Route path="products/:id" element={<MovieDetail />} />
  <Route path="*" element={<NotFound />} />
</Route>

// URL is "/" → Layout renders, but Outlet is EMPTY
// No child matched — nothing shows in the content area
```

This is where **index routes** come in.

#### What Is an Index Route?

`<Route index>` means: **"when the parent's path matches exactly, this is the default child to render."**

It has no `path` of its own. It renders inside the parent Layout when the URL is exactly the parent's path.

```tsx
<Route path="/" element={<Layout />}>
  <Route index element={<HomePage />} />              {/* no path written */}
  <Route path="products" element={<ProductList />} />
  <Route path="products/:id" element={<ProductDetail />} />
  <Route path="*" element={<NotFound />} />
</Route>

// URL is "/" → Layout renders → Outlet shows HomePage
```

#### Without Index Route — What Happens?

Without an index route, you'd do this:

```tsx
<Routes>
  <Route path="/" element={<HomePage />} />    {/* separate — OUTSIDE Layout */}
  <Route path="/" element={<Layout />}>         {/* separate route */}
    <Route path="products" element={<ProductList />} />
  </Route>
</Routes>
```

**Problem:** When you visit `/`, `Layout` never renders! You just see `<HomePage />` — **no navbar**, because Layout is outside the route for `/`.

#### Visual Comparison

The easiest way to understand: look at these two visuals.

**Without index route (wrong approach):**
```
URL: /
     ↓
Layout never renders
Just <HomePage /> shows — the app looks broken
```

**With index route (correct approach):**
```
URL: /
     ↓
Layout → <nav>Home | Products</nav> → [Outlet → HomePage]
                                          ↑
                          index route decides
                          "default child → HomePage"
```

#### Real-Life Analogy

Think of yourself in a **shopping mall** (`Layout`). Each section is a child route:

| Section | URL | Content |
|---|---|---|
| Entrance (index) | `/` | Welcome desk, map |
| Electronics Store | `/products` | Product list |
| Specific Product | `/products/p1` | Product detail |

When you **just enter the mall** (URL = `/`), you're at the entrance area — the **index route** says "show the welcome desk here."

Without an index route, entering the mall shows you an **empty lobby** — no content, just the frame.

#### Rules of Index Routes

- **No `path` property** — write `<Route index>`, not `<Route index path="..." />`
- **Only inside nested children** — can't be a standalone route
- **One per parent** — each parent can have only one index route
- **Matches parent's exact path** — `/products` won't trigger it, only `/`

#### When to Use Index Routes

✅ **Use when:**
- You have a Layout component (parent route)
- You want content to show at the parent's exact path
- That content should appear inside the Layout

❌ **Don't use when:**
- No Layout component
- You want `/` to be a completely different page (outside any Layout)
- The parent path shouldn't show any default content

#### Summary

```
Index route = default child for parent's path
              ├── No path property
              ├── Renders inside parent Layout
              ├── Only when URL = parent's exact path
              └── One per parent
```

### 2.7 Relative vs Absolute Paths

In nested routes, you can write a child's path two ways — **relative** (no leading `/`) and **absolute** (starts with `/`).

#### Relative Path — Default Behavior

When a child's path has **no leading `/`**, it's relative to its parent:

```tsx
<Route path="dashboard" element={<Layout />}>
  <Route path="settings" element={<Settings />} />     {/* → /dashboard/settings */}
  <Route path=":id" element={<Profile />} />            {/* → /dashboard/123 */}
</Route>
```

React Router concatenates parent path + child path:

```
Parent path:  "dashboard"
Child path:   ":id"
Result:       "/dashboard/:id"    ← automatic
```

#### Absolute Path — Leading `/`

When a child's path starts with **`/`**, it's absolute — it ignores the parent and matches from the root:

```tsx
<Route path="dashboard" element={<Layout />}>
  <Route path="/help" element={<Help />} />             {/* → /help, NOT /dashboard/help */}
</Route>
```

The `/` prefix ignores the parent — Help only renders at `/help`, not `/dashboard/help`.

#### Visual Comparison

```
Parent: "products" (URL = /products)
│
├── Child relative:  "featured"        → /products/featured     ✅
├── Child relative:  ":id"             → /products/ps5          ✅
├── Child absolute:  "/about"          → /about                 ✅ (parent ignored)
├── Child absolute:  "/products/top"   → /products/top          ✅ (explicit full path)
└── Child relative:  "/featured"       → /featured              ❌ WAIT — this is absolute!
                                                  because it starts with /
```

#### Rule of Thumb

```
Path starts with:  no "/"  →  relative (joins parent)
Path starts with:  "/"     →  absolute (ignores parent, matches root)
```

#### Common Mistakes

**Mistake 1 — Making a relative path absolute by accident:**
```tsx
<Route path="products" element={<Layout />}>
  <Route path="/:id" element={<ProductDetail />} />   {/* /:id → root URL, not /products/123 */}
</Route>
// Expected: /products/ps5
// Actual:   /ps5
```
Fix: Don't use `/` — write `path=":id"`

**Mistake 2 — Making an absolute path relative by accident:**
```tsx
<Route path="products" element={<Layout />}>
  <Route path="about" element={<About />} />           {/* about → /products/about */}
</Route>
// Expected: /about
// Actual:   /products/about
```
Fix: Add `/` prefix — `path="/about"`

#### When to Use Which

| Scenario | Path Type | Example |
|---|---|---|
| Child logically belongs under parent | Relative | `path="reviews"` → `/products/reviews` |
| Dynamic segment | Relative | `path=":id"` → `/products/ps5` |
| Child has no relation to parent | Absolute | `path="/about"` → `/about` |
| Child reused across sections | Absolute | `path="/trending"` → `/trending` |

#### Real-Life Analogy

You're on **floor 2** (`/products`). You say:

- **"bathroom"** → that floor's bathroom → `/products/bathroom` (relative — same floor)
- **"/ground-floor bathroom"** → ground floor's bathroom → `/bathroom` (absolute — different floor)

Relative = "somewhere on this floor." Absolute = "go straight to ground floor."

#### Why This Matters

Confusing relative and absolute means:
- Your `/about` page never shows (because it became `/products/about`)
- Or your `:id` route matches at root (`/ps5`), instead of `/products/ps5`

Always ask: **"does this route logically belong under the parent?"** → relative. **"Is it a completely separate section?"** → absolute.

### 2.8 What It Is NOT — Outlet and Nested Routes

- **`<Outlet />` doesn't render an extra DOM element** — it's just a placeholder. In DevTools, you see the child component, not Outlet itself.
- **Nested routes ≠ JSX nesting** — `<Route>` nesting is about URL structure, not DOM structure. A child component only appears inside the parent when the parent renders `<Outlet />`.
- **`useParams` works based on URL, not route tree** — it doesn't matter if the component is a flat route or deeply nested. `useParams` extracts from the URL, not from the route nesting level.

#### 2. `components/MovieList.tsx` — Grid with Links

```tsx
import { Link } from "react-router-dom";

export default function MovieList() {
  return (
    <div>
      <h1>Movie List</h1>
      <div className="movie-grid">
        {movies.map((movie) => (
          <div key={movie.id} className="movie-card">
            <h3>{movie.title}</h3>
            <p>{movie.year} · {movie.director}</p>
            <Link to={`/movies/${movie.id}`}>View Details →</Link>
          </div>
        ))}
      </div>
    </div>
  );
}
```

What's happening:
- `movies.map(movie => ...)` — one card per movie
- `key={movie.id}` — React uses this to track which item changed (list rendering rule)
- `<Link to={\`/movies/${movie.id}\`}>` — each card gets a dynamic link. The URL is built from the movie's ID

#### 3. `components/MovieDetail.tsx` — Lookup + Render

```tsx
import { useParams, Link } from "react-router-dom";
import { movies } from "../data/movies";

export default function MovieDetail() {
  const { id } = useParams<{ id: string }>();
  const movie = movies.find((m) => m.id === id);

  if (!movie) {
    return (
      <div>
        <h2>404 — Movie not found</h2>
        <Link to="/movies">← Back to Movies</Link>
      </div>
    );
  }

  return (
    <div className="movie-detail">
      <h1>{movie.title}</h1>
      <p><strong>Year:</strong> {movie.year}</p>
      <p><strong>Director:</strong> {movie.director}</p>
      <p>{movie.plot}</p>
      <Link to="/movies">← Back to Movies</Link>
    </div>
  );
}
```

1.5's logic is the same — `useParams` → `.find()` → guard → render. The only difference is data comes from `data/movies.ts` via import.

#### 4. `App.tsx` — Nested Routes + Layout

```tsx
import { BrowserRouter, Routes, Route, Link, Outlet } from "react-router-dom";
import MovieList from "./components/MovieList";
import MovieDetail from "./components/MovieDetail";

function Layout() {
  return (
    <div className="app">
      <nav>
        <Link to="/">Home</Link>
        <Link to="/movies">Movies</Link>
      </nav>
      <hr />
      <Outlet />     {/* child route content goes here */}
    </div>
  );
}

export default function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Layout />}>
          <Route index element={<h2>Welcome to Movie Browser</h2>} />
          <Route path="movies" element={<MovieList />} />
          <Route path="movies/:id" element={<MovieDetail />} />
          <Route path="*" element={<h2>404 — Page not found</h2>} />
        </Route>
      </Routes>
    </BrowserRouter>
  );
}
```

#### Data Flow — From Source to Screen

```
data/movies.ts  ──imported by──▶  MovieList.tsx        MovieDetail.tsx
                    │                  movies.map()           useParams → id
                    │                  grid of cards          movies.find(m => m.id === id)
                    │                  <Link> with ID         guard → render
                    │                       │
                    └──────────────────────┘
                        same array, same structure
```

- **One data source:** `data/movies.ts` is imported by both components. No sync issues — change data in one place, both pages reflect it.
- **MovieList:** Maps the array into a grid of cards. Each card has a `Link` with a dynamic ID.
- **MovieDetail:** Uses the same array with `.find()` to look up a single movie by ID from the URL.
- **Routing:** Nested routes with `Layout` + `Outlet` — navbar renders once, content swaps per route.

### Feature Comparison

| Feature | Static Routes (3.1) | Nested Routes (3.2) |
|---|---|---|
| Layout | Repeated in every page component | Written once in parent Layout |
| Navbar | Copy-pasted in every component | One Layout component, shared |
| Path pattern | Fixed (`/movies`) | Dynamic (`/movies/:id`) |
| URL data capture | Not possible | `useParams` extracts it |
| Add new page | Add component + repeat layout + add route | Just add a child `<Route>` |

Nested routes shine when layouts get complex — sidebar, breadcrumbs, loading states — all handled by the parent. Child routes focus only on their specific content.

---

## What It Is NOT

- **`Outlet` is not a layout wrapper** — it doesn't add styling or structure. It's a placeholder that renders child route content. The Layout component itself defines the structure around it.
- **`useParams` doesn't care about nesting** — it extracts from the URL, not the route tree. Whether `MovieDetail` is flat or nested under Layout, `useParams()` returns the same `{ id: "..." }`.
- **`Outlet` doesn't render children from props** — it renders child **routes** that match the URL. Passing children as JSX props (`<Layout><HomePage /></Layout>`) is completely different — that's Composition, not routing.

## In Your Own Words

<details>
<summary>What is a dynamic route, and how does `useParams` capture values from the URL?</summary>

A dynamic route has a variable segment in the path, marked with a colon: `/movies/:id`. When the URL `/movies/tt1375666` is visited, `:id` captures `"tt1375666"`. `useParams()` is a React Router hook that returns an object of these captured values — `{ id: "tt1375666" }`. You destructure to get the ID, then use it however you need (API call, `.find()` lookup, etc.). The colon is just a marker — the variable name can be anything (`:id`, `:productId`, `:slug`).
</details>

<details>
<summary>What problem do nested routes solve? Why use `<Outlet />`?</summary>

Without nested routes, every page component repeats the same layout (navbar, sidebar, footer). Nested routes let you define a parent Layout once with `<Outlet />` as a placeholder, then child routes only provide the content that changes. `Outlet` is where the child route's component renders. It's like a TV with an empty slot — the frame stays, just the content changes.
</details>

<details>
<summary>What is an index route? When is it needed?</summary>

An index route is the default child that renders when the parent's path matches exactly. If you have `<Route path="/" element={<Layout />}>` with nested children, the index route determines what shows at `/`. Without it, visiting the parent path renders the Layout but the `Outlet` is empty — nothing shows in the content area.
</details>

<details>
<summary>Relative vs absolute paths in nested routes — what's the difference?</summary>

Relative paths (no leading `/`) concatenate with the parent: `"settings"` under `"dashboard"` becomes `/dashboard/settings`. Absolute paths (leading `/`) ignore the parent and match from root: `"/help"` is always `/help` regardless of parent. Use relative when the child belongs under the parent; use absolute when the route is independent.
</details>

<details>
<summary>What is the order of route matching in `<Routes>`?</summary>

Routes matches sequentially from top to bottom and renders the **first** match. This is why `path="*"` must be last — if it's first, it matches everything and specific routes never render. Same principle as the 3.1 catch-all route, just with ordered matching.
</details>
