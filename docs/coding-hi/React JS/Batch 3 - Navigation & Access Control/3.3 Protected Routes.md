## Cheat Sheet (Quick Recall)

```tsx
// Auth context — global auth state
const AuthContext = createContext<...>(undefined);
function useAuth() { return useContext(AuthContext); }

// ProtectedRoute — guard component
function ProtectedRoute({ children }: { children: ReactNode }) {
  const { user } = useAuth();
  if (!user) return <Navigate to="/login" replace />;
  return <>{children}</>;
}

// Usage — wrap protected routes
<Route path="/watchlist" element={
  <ProtectedRoute><Watchlist /></ProtectedRoute>
} />
```

## What Happened So Far

In 3.2, we learned nested routes + dynamic routes. The Movie Browser had a layout — `/`, `/movies`, `/movies/:id`. Any user could visit any page — no restrictions.

But in real apps, some pages should only be visible to **logged-in users** — "My Watchlist", "Settings", "Orders". If the user isn't logged in, redirect them to the login page or hide the content.

The pattern is a **guard component** that checks: "is the user authenticated?" If yes, show the content. If no, redirect.

## Broader Goal

In this doc, we add a `/watchlist` page to the Movie Browser that only logged-in users can access. For this we need:

1. Global auth state (Context API — remember 2.6's pattern?)
2. React Router's redirect tools — `<Navigate>` and `useNavigate`
3. A guard component that checks "is the user logged in?"
4. Connect the guard to the route

After this, protecting any route is as simple as wrapping it in `ProtectedRoute`.

## Step 2 — Auth State: Global State with Context API

**Think:** A page should only show for logged-in users. So we need to store somewhere "who is the logged-in user." And that state needs to be globally available — every component should be able to check it. React's Context API is perfect for this — same pattern as ThemeContext in 2.6.

**Concept — Auth Context** provides three things:
- `user` — the logged-in user's name (or `null` if logged out)
- `login(name)` — function to log a user in
- `logout()` — function to log a user out

Same trio of Context API: `createContext` → Provider component → custom hook with guard.

Let's build it. First, create a new folder `context/` — keeping auth logic in its own file is cleaner.

Think about why a new folder before creating the file:
- Components have their own folder (`components/`)
- Data has its own folder (`data/`)
- Context providers get their own folder — `context/` — this is a common React convention

**CODE:**

```tsx
// context/AuthContext.tsx
import { createContext, useContext, useState } from "react";
import type { ReactNode } from "react";
```

Imports — `createContext` and `useContext` from React, `useState` for state, `ReactNode` for the children type (remember it from 1.6).

```tsx
interface AuthContextValue {
  user: string | null;
  login: (username: string) => void;
  logout: () => void;
}
```

Interface defines the context shape: `user` is a string or null, `login` is a function taking a string (username), `logout` is a function taking nothing.

```tsx
const AuthContext = createContext<AuthContextValue | undefined>(undefined);
```

Context created with initial value `undefined` — because without a Provider, the context is undefined. TypeScript knows it can be `AuthContextValue` or `undefined` — so we'll add a guard later.

```tsx
export function useAuth(): AuthContextValue {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within AuthProvider");
  return ctx;
}
```

Custom hook — `useAuth()`. Guard pattern: if context is undefined (Provider missing), throw an error. This is the same pattern from 2.6's `ThemeContext`.

```tsx
export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<string | null>(null);

  const login = (username: string) => setUser(username);
  const logout = () => setUser(null);

  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}
```

Provider component. Starts with `useState<string | null>(null)` — null means no one is logged in. `login` calls `setUser(username)`, `logout` calls `setUser(null)`.

**Test:** Add `console.log("AuthContext ready")` to verify the file imports correctly. We're not using it yet — just confirming exports and imports are wired right.

> **Nutshell:** AuthContext is a global state container — `user`, `login`, `logout` are accessible anywhere in the app without passing props.

## Step 3 — Redirecting with React Router: `<Navigate>` and `useNavigate`

**Think:** Auth state is ready. Now we need a guard component — when the user isn't logged in, redirect to the login page. But how do you redirect in React Router? Two ways — one declarative (a component in JSX) and one programmatic (a function in code). Let's learn both.

**Concept — `<Navigate>` component:**

`<Navigate>` is a React Router component. When it renders, it immediately redirects. Use it when you have a condition in JSX that decides "redirect or not."

Syntax:

```tsx
<Navigate to="/login" replace />
```

- `to="/login"` — where to redirect
- `replace` — replaces the current history entry instead of pushing a new one. So pressing back doesn't return to the guarded page

**Concept — `useNavigate` hook:**

`useNavigate` returns a function you call to navigate. Use it when you need to redirect from within an event handler, async callback, or timer.

Syntax:

```tsx
const navigate = useNavigate();
navigate("/", { replace: true });
```

Both do the same thing — redirect. The difference is context:
- `<Navigate />` — declarative, in JSX (e.g., "if not logged in, render this")
- `useNavigate()` — programmatic, in code (e.g., "redirect after form submit")

**Minimal example — `<Navigate />`:**

```tsx
import { Navigate } from "react-router-dom";

function GuestGuard() {
  const isLoggedIn = false; // hardcoded for now

  if (!isLoggedIn) {
    return <Navigate to="/login" replace />;
  }

  return <h2>Welcome, user!</h2>;
}
```

Since `isLoggedIn` is `false`, `<Navigate to="/login" replace />` renders — the browser immediately goes to `/login`. No error in console — `<Navigate>` redirects silently.

**Test:** Drop this component into a route — the browser should automatically redirect to `/login`.

**Minimal example — `useNavigate`:**

```tsx
import { useNavigate } from "react-router-dom";

function LoginButton() {
  const navigate = useNavigate();

  function handleClick() {
    // login logic would go here
    navigate("/dashboard", { replace: true });
  }

  return <button onClick={handleClick}>Login</button>;
}
```

Inside `handleClick`, we call `navigate("/dashboard")`. Click the button and the browser URL changes, showing the dashboard (if the route exists).

**Test:** Click the button — the URL should change and the dashboard should appear (if the route is defined).

**Why `replace` matters:**

Without `replace`, navigating pushes a new history entry. Press back and you return to the page that just redirected — which redirects again — creating a loop. With `replace`, the current entry is replaced, so back skips over it.

I once forgot `replace` — user was on the login page, clicked login, went to dashboard, hit back — back to login page. Hit back again, hit forward... confusing loop. That's when I learned why `replace` is necessary.

**Now using it in the project — LoginPage:**

Both tools are learned. Now we use them in the Movie Browser. First use case: **LoginPage** where the user logs in and gets redirected home.

Let's create `components/LoginPage.tsx`:

```tsx
// components/LoginPage.tsx
import { useNavigate } from "react-router-dom";
import { useAuth } from "../context/AuthContext";
```

Two imports — `useNavigate` for redirecting after login (learned in this step), `useAuth` to access auth state (created in Step 2).

```tsx
export default function LoginPage() {
  const { login } = useAuth();
  const navigate = useNavigate();

  function handleLogin() {
    login("DemoUser");
    navigate("/", { replace: true });
  }

  return (
    <div>
      <h2>Login</h2>
      <button onClick={handleLogin}>Login as DemoUser</button>
    </div>
  );
}
```

`handleLogin` first calls `login("DemoUser")` to update auth state, then `navigate("/", { replace: true })` to send the user home. `replace: true` replaces the current history entry, so hitting back won't return to the login page.

Add the `/login` route in App.tsx:

```tsx
// App.tsx — new route
import LoginPage from "./components/LoginPage";

// Inside <Routes>
<Route path="login" element={<LoginPage />} />
```

**Test:** Visit `/login`, click the button — should redirect to the home page. Check the browser URL.

> **Nutshell:** `<Navigate />` is for declarative redirects (in JSX conditions). `useNavigate()` is for programmatic redirects (in event handlers and code). `replace` prevents back-button redirect loops. LoginPage demonstrates a real use of `useNavigate()` — redirect after login.

## Step 4 — ProtectedRoute Component: The Wrapper Pattern

**Think:** Auth state is ready, redirect tools learned. Now we need a guard component — check "is the user logged in?" If not, redirect to login. This guard wraps any protected page.

**Concept — ProtectedRoute** is a **wrapper component** — it receives `children` (the protected page). It:

1. Calls `useAuth()` to check the current user
2. If `user` is `null` → `return <Navigate to="/login" replace />`
3. If user exists → `return <>{children}</>`

That's it. Wrap pattern means you can protect any component just by wrapping it.

Let's build it:

```tsx
// components/ProtectedRoute.tsx
import { Navigate } from "react-router-dom";
import { useAuth } from "../context/AuthContext";
import type { ReactNode } from "react";
```

Three imports. `Navigate` from React Router (learned in Step 3), `useAuth` from our auth context (Step 2), `ReactNode` for the children type.

```tsx
interface ProtectedRouteProps {
  children: ReactNode;
}
```

Simple interface — just receives `children`.

```tsx
export default function ProtectedRoute({ children }: ProtectedRouteProps) {
  const { user } = useAuth();

  if (!user) {
    return <Navigate to="/login" replace />;
  }

  return <>{children}</>;
}
```

Here's the logic: `useAuth()` gives us `user`. If `!user` (null — not logged in), render `<Navigate>` which redirects to `/login`. The `replace` prop prevents back-button issues. If the user IS logged in, render `<>{children}</>` — the protected page.

**Test:** Wrap any dummy page in `ProtectedRoute`, add a `console.log(user)` — you'll see that `<Navigate />` renders when user is null.

> **Nutshell:** ProtectedRoute is a guard component that checks auth and redirects unauthorized users — wrap any page with `children` and it's protected.

## Step 5 — Integrate in App: AuthProvider + ProtectedRoute

**Think:** We have three pieces ready — AuthContext, ProtectedRoute, and Watchlist. Let's wire them into App. There's one tricky part: **AuthProvider must be inside BrowserRouter** because ProtectedRoute uses `<Navigate>` which needs the Router context. BrowserRouter provides that context.

**Concept — Hierarchy matters.** Context providers should be inside the Router if components need routing. If a context only provides data (like ThemeContext), it can go outside the Router. But auth + redirect needs both.

I made this mistake the first time — put AuthProvider outside the Router. `useAuth()` worked fine, but `<Navigate>` in ProtectedRoute failed with: "useNavigate may be used only in the context of a `<Router>` component." Then I understood.

Let's update App.tsx. Existing code stays (Layout, HomePage, MovieList, MovieDetail, NotFound) — just add the new pieces:

```tsx
// App.tsx — new imports
import { AuthProvider, useAuth } from "./context/AuthContext";
import ProtectedRoute from "./components/ProtectedRoute";
import Watchlist from "./components/Watchlist";
```

Add login/logout buttons in HomePage — so the user can actually log in:

```tsx
function HomePage() {
  const { user, login, logout } = useAuth();
  return (
    <div>
      <h2>Welcome to Movie Browser</h2>
      {user ? (
        <div>
          <p>Logged in as: <strong>{user}</strong></p>
          <button onClick={logout}>Logout</button>
        </div>
      ) : (
        <div>
          <p>You are not logged in.</p>
          <button onClick={() => login("DemoUser")}>Login as DemoUser</button>
        </div>
      )}
    </div>
  );
}
```

Using `useAuth()` — destructuring `user`, `login`, `logout`. If `user` exists, show "logged in as X" with a logout button. If not, show "not logged in" with a login button. `login("DemoUser")` is called directly in `onClick` — this is dummy auth, so no form needed.

Now update the `App()` component:

```tsx
export default function App() {
  return (
    <BrowserRouter>
      <AuthProvider>
        <Routes>
          <Route path="/" element={<Layout />}>
            <Route index element={<HomePage />} />
            <Route path="movies" element={<MovieList />} />
            <Route path="movies/:id" element={<MovieDetail />} />
            <Route path="login" element={<LoginPage />} />
            <Route path="watchlist" element={
              <ProtectedRoute>
                <Watchlist />
              </ProtectedRoute>
            } />
            <Route path="*" element={<NotFound />} />
          </Route>
        </Routes>
      </AuthProvider>
    </BrowserRouter>
  );
}
```

Notice: `AuthProvider` is **inside** `BrowserRouter`. The `watchlist` route doesn't have a plain component as its element — it's wrapped in `<ProtectedRoute>`. When someone visits `/watchlist`, ProtectedRoute checks if the user is logged in. If not, `<Navigate>` sends them to `/login`. If logged in, `<Watchlist />` renders.

**Test:** Visit `/watchlist` — should redirect to `/login` (since we're logged out). Then go to the home page, click "Login", then visit `/watchlist` again — Watchlist should now be visible.

## Dummy Auth vs Real Auth

This mini-project uses dummy auth — click login, user becomes "DemoUser". Real apps have:

1. A login form (username + password inputs)
2. An API call to the server
3. Server returns a token (JWT)
4. Token stored in localStorage or cookie
5. Auth context checks the token on page refresh

But the pattern is the same — ProtectedRoute, AuthContext, redirect logic. Only the `login` function changes to make an actual API call. Learn the pattern with dummy auth, migrate to real auth later.

---

## What It Is NOT

- **`ProtectedRoute` is not security** — it's a front-end guard. Anyone can read the code in DevTools. Real protection requires backend authorization on every API request.
- **`ProtectedRoute` is not the same as server-side auth** — the backend must also validate the user on every protected request. This route guard is just UX.
- **This isn't a complete auth system** — no password validation, no session persistence, no token refresh. It's the pattern, not the full implementation.
- **`useAuth` doesn't persist across refreshes** — `useState` resets on page reload. Real apps read from localStorage on initial load.

## Common Mistakes

1. **Putting `AuthProvider` outside `BrowserRouter`:**

```tsx
❌ <AuthProvider><BrowserRouter>...</BrowserRouter></AuthProvider>
✅ <BrowserRouter><AuthProvider>...</AuthProvider></BrowserRouter>
```

ProtectedRoute uses `<Navigate />` which needs Router context. If the provider is outside the Router, Navigate fails. The error: "useNavigate may be used only in the context of a `<Router>` component."

2. **Forgetting `replace` on `<Navigate>`:**

```tsx
❌ if (!user) return <Navigate to="/login" />;
✅ if (!user) return <Navigate to="/login" replace />;
```

Without `replace`, the back button takes you back to the guarded page, which redirects again — infinite loop.

3. **Using ProtectedRoute inside component logic instead of at route level:**

ProtectedRoute should wrap at the route level. If you need auth inside a component, call `useAuth()` directly. Wrapping every component in ProtectedRoute creates confusing nesting.

4. **Confusing `<Navigate>` and `useNavigate`:**

Both redirect. `<Navigate />` is in JSX (render-time, declarative). `useNavigate()` is in code (event-driven, programmatic). Don't try to call `<Navigate />` inside an `onClick` — it won't work.

## Summary

- **AuthContext** — global auth state (`user`, `login`, `logout`)
- **`<Navigate to="/path" replace />`** — declarative redirect component (in JSX)
- **`useNavigate()`** — programmatic redirect hook (in event handlers)
- **`replace`** — replaces history entry instead of pushing — avoids back-button loops
- **ProtectedRoute** — wrapper component that checks auth and redirects
- **Provider hierarchy** — AuthProvider inside BrowserRouter, because ProtectedRoute needs both auth and router context
