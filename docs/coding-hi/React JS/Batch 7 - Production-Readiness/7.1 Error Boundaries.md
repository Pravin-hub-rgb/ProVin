## Problem First — White Screen of Death

Imagine this. Your app is live. A user opens a profile page, and one user's `email` field is missing (empty in the database). The component tries `email.toUpperCase()` → `undefined.toUpperCase()` throws a **TypeError**. The error is thrown mid-render.

**What does React do by default?** Look:

```
Component throws error during render
        │
        ▼
React unmounts the entire component tree
        │
        ▼
User sees a BLIND WHITE SCREEN
```

The entire app. Just because of one missing field. If the user refreshes, they still get the same error, the same blank screen. This is called the **"White Screen of Death."**

**Coder mindset:** "The user shouldn't see a blank screen. Something should show — and the rest of the app (the parts that didn't crash) should keep running."

This is exactly the problem Error Boundaries solve. Let's build it step by step.

## What Is an Error Boundary

An **Error Boundary** is a component that **catches** render errors in its child subtree and shows a **fallback UI** in their place.

```
Error Boundary
    │
    ├── [component that crashed]   ← error happened here
    │
    ▼
Boundary catches → shows fallback UI → rest of app stays safe
```

**Important:** An error boundary is still a React component, but it must be a **class component**. Why? Because error boundaries need React's lifecycle methods, and those methods only exist in class components:

| Class method | What it does |
|-------------|------|
| `static getDerivedStateFromError()` | When an error happens, update state → fallback will render |
| `componentDidCatch()` | Log the error (side effects — console, API call) |

This is a rare case where a class component is the **only** option (the React team is working on a hook API for this). The rest of the app will be written in modern React (hooks).

## Step 4 — Building the ErrorBoundary, Piece by Piece

We'll build the boundary now. But this time, before the code — **let's understand what the code will do**. Because class component syntax is fresh, we don't just dump code and let you figure it out.

### Important Note — How Imports Work

When you create a new file, React needs to be **imported**. Why emphasize? Look:

```
ErrorBoundary.tsx  ← different file, React lives in a different folder
        │
        ▼
If you don't write "Component", React doesn't know what "Component" is
        │
        ▼
import { Component } from "react"  ← pull it from React
```

Every component file has three things, line by line:

1. **Import** what you need from React
2. **Types** for props and state
3. **Export** the component

Keep these rules in mind before looking at the code — every file follows this same pattern.

---

### Step 4a — First File: Structure Only

Create the first file — `src/components/ErrorBoundary.tsx` (the `components` folder may already exist, if not, create it).

**Think through the logic first:**

- **`Component` — what is it?** React's built-in class — components *derive* from it. Your class inherits its functionality (state, `render`, lifecycle). That's why you write `extends Component` — "this class uses all of Component's powers."
- **`ReactNode` — what is it?** The type for `children`. `children` = the elements you put inside a component (`<ErrorBoundary><UserCard/></ErrorBoundary>` — the `<UserCard/>`). `ReactNode` means — "children can be anything: text, element, or array." That's what makes it type-safe.
- **`Props` and `State` — why?** A class component has two types: data that comes from outside (props) and state you want to track. Error boundary needs just one prop (`children`) and one piece of state (`hasError`).

Now the code — `src/components/ErrorBoundary.tsx`:

```tsx
// src/components/ErrorBoundary.tsx
import { Component, type ReactNode } from "react";

interface ErrorBoundaryProps {
  children: ReactNode;
}

interface ErrorBoundaryState {
  hasError: boolean;
}

export class ErrorBoundary extends Component<
  ErrorBoundaryProps,
  ErrorBoundaryState
> {
  constructor(props: ErrorBoundaryProps) {
    super(props);
    this.state = { hasError: false };
  }

  render() {
    return this.props.children;
  }
}
```

**Line by line, what each line means:**

| Code | Meaning |
|------|--------|
| `import { Component, type ReactNode } from "react"` | Pull `Component` (for making classes) and `ReactNode` (children's type) from React |
| `interface ErrorBoundaryProps` | Shape of props — this boundary receives `children` |
| `interface ErrorBoundaryState` | Shape of state — one boolean `hasError` |
| `class ErrorBoundary extends Component<Props, State>` | A new class built on React's `Component`; inside `<>` two types — first Props, then State |
| `constructor(props)` | Whenever an instance of this component is created, set the initial state here |
| `super(props)` | Call `Component`'s own constructor (give React the props). **Without it, the class doesn't connect properly.** |
| `this.state = { hasError: false }` | Initial state — no error yet, so `false` |
| `render()` | Every class component has `render()` — it decides what UI shows. Right now it just returns `children` |
| `return this.props.children` | "Whatever you put inside me, I'll show it" |

Right now this boundary does nothing — it just passes children through (like a normal wrapper). The structure works. Now we add error handling — but first, one concept.

---

### Step 4b — getDerivedStateFromError + Fallback

**Concept first — what does `static` mean?**

Inside a class there are two kinds of methods:

| Type | For whom | Example |
|-------|---------|--------|
| **`static` method** | The class itself — no instance (object) needed | `Math.round()` — you don't make a `Math` instance, you call it directly |
| **Normal method** | A specific instance — only it has access to `this` | `obj.method()` |

Static means the method is **not tied to any specific component instance**. React calls it directly without creating a component instance. Because of this, it has no `this` — you can't write `this.state`, `this` doesn't point to any instance. That's where the confusion comes from.

**Concept — understand the name `getDerivedStateFromError`:**

```
getDerivedState  →  "Derive the state"  →  build state from the error
fromError        →  this comes FROM an error
```

React is telling you there's an error in the environment. It calls this method. You do your job: "set my state's `hasError` to `true`." Return the new state object — React applies it.

**Why check in `render`?** Until now, state was `hasError: false`. When an error happens, `getDerivedStateFromError` sets it to `true`. Now what `render()` shows depends on this check:

```
hasError?  →  TRUE  →  show fallback UI ("Something went wrong")
          →  FALSE →  show children (normal)
```

Now the code — same file `ErrorBoundary.tsx`, add this:

```tsx
// src/components/ErrorBoundary.tsx (update — add these two)
  static getDerivedStateFromError(): ErrorBoundaryState {
    return { hasError: true };
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="error-fallback">
          <h2>Something went wrong 😅</h2>
          <p>Try refreshing. If the error persists, please report it.</p>
        </div>
      );
    }

    return this.props.children;
  }
```

One at a time:

- `static getDerivedStateFromError()` — **static** (explained above) + return type `ErrorBoundaryState`.
- `return { hasError: true }` — state derived from the error. React applies it.
- `if (this.state.hasError)` — on the next render: check if an error has happened.
- `<h2>Something went wrong 😅</h2>` — fallback UI. Instead of a blank screen, the user knows there's a problem.
- `return this.props.children` — otherwise (no error), show normal children.

---

### Step 4c — componentDidCatch (Logging)

A fallback is only half the job — **what showed up** is half the job. The other half is **what happened**, for debugging. That's `componentDidCatch`.

**Concept — why the name?** "Did Catch" = "caught it." React caught the error and is telling you by calling this method. `componentDidCatch` is a lifecycle method — it automatically runs after an error is caught.

**Why a separate method?** Logic separation — `getDerivedStateFromError` handles render-phase state (UI), and `componentDidCatch` handles side effects (logging, reporting). Because side effects go in `componentDidCatch`, not in `getDerivedStateFromError`.

Now the code — add to the same file:

```tsx
// src/components/ErrorBoundary.tsx (update — add this method)
  componentDidCatch(error: Error, info: { componentStack: string }) {
    console.error("💥 Error caught:", error.message, info.componentStack);
  }
```

Understand the params:

- **`error: Error`** — the actual error object (`.message`, `.stack` are on it).
- **`info: { componentStack: string }`** — tells you where in the component tree the error happened. Golden for debugging.
- `console.error` — local logging for now. In a real app, you'd send to services like Sentry/LogRocket:

```ts
// concept — how real apps report errors
sendToErrorService({
  message: error.message,
  stack: error.stack,
  componentStack: info.componentStack,
  url: window.location.href,
});
```

Remember — `componentDidCatch` is added here, but keep this in mind: **the fallback comes from `getDerivedStateFromError` + `render`. `componentDidCatch` is only for logging.**

### Full ErrorBoundary — Complete Picture

Now the three pieces (4a + 4b + 4c) work together like this:

```
Child subtree throws error during render
        │
        ▼
React calls getDerivedStateFromError() (static, no instance needed)
        │
        ▼
state.hasError = true
        │
        ▼
render() → shows fallback UI ("Something went wrong")
        │
        ▼
componentDidCatch(error, info) → error is logged
        │
        ▼
Rest of tree (outside boundary) keeps rendering
```

Look — **that's what we built step by step**: Step 4a was structure (just a class, does nothing), Step 4b was fallback, Step 4c was logging. Each step is small, each one makes sense, and every new concept was explained before its code.

### Full Code — All Together

The three pieces (4a + 4b + 4c) in one file look like this. You can copy-paste and run:

```tsx
// src/components/ErrorBoundary.tsx
import { Component, type ReactNode } from "react";

interface ErrorBoundaryProps {
  children: ReactNode;
}

interface ErrorBoundaryState {
  hasError: boolean;
}

export class ErrorBoundary extends Component<
  ErrorBoundaryProps,
  ErrorBoundaryState
> {
  constructor(props: ErrorBoundaryProps) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(): ErrorBoundaryState {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: { componentStack: string }) {
    console.error("💥 Error caught:", error.message, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="error-fallback">
          <h2>Something went wrong 😅</h2>
          <p>Try refreshing. If the error persists, please report it.</p>
        </div>
      );
    }

    return this.props.children;
  }
}
```

Memory trick for order: **"Error came → update state (`getDerivedStateFromError`) → what to show (`render`) → what to log (`componentDidCatch`)"** — React calls these in this exact order.

## Step 5 — Using the Boundary

Now wrap the boundary around the App. Two ways to do it.

### Option A — Wrap the Entire Section

Wrap the user list inside the boundary in `src/App.tsx`:

```tsx
// src/App.tsx (update)
import { users } from "./data";
import { UserCard } from "./UserCard";
import { ErrorBoundary } from "./components/ErrorBoundary";

function App() {
  return (
    <main>
      <h1>Team</h1>
      <ErrorBoundary>
        {users.map((user) => (
          <UserCard key={user.name} user={user} />
        ))}
      </ErrorBoundary>
    </main>
  );
}

export default App;
```

Open in browser — **no white screen**. The "Team" heading shows, and instead of the user list, you see the fallback — "Something went wrong 😅". The error is logged in the console. The whole page is working.

### Option B — One Boundary Per Card (Granular)

Want tighter control? Give each card its own boundary:

```tsx
// src/App.tsx (update — each card gets its own boundary)
      {users.map((user) => (
        <ErrorBoundary key={user.name}>
          <UserCard user={user} />
        </ErrorBoundary>
      ))}
```

What happens now? **Rahul's card shows the fallback, but Amit and Priya's cards render fine.** All cards visible. Only the crashing one shows the fallback. That's the power of granularity.

Try it in the browser — the difference is clear. Amit card + Priya card + Rahul's fallback. The whole app stays safe.

## Granularity — Where to Wrap

This is the level that separates production apps — **not every error boundary is the same**. Decision: where to wrap?

| Where to wrap | Benefit | Drawback |
|-----------|-------|---------|
| Entire app | Safest — no crash becomes a blank screen | A small section's error brings the entire app into fallback |
| Specific section | Crash section gets isolated — rest of app stays alive | Every section needs its own boundary |

**Industry pattern:** Layered — top-level + feature-level:

```
ErrorBoundary (top-level — prevents blank screens)
    │
    └── App
          ├── Header (no boundary — simple, never crashes)
          ├── ErrorBoundary → UserList      ← feature-level boundary
          ├── ErrorBoundary → UserProfile   ← world's riskiest section
          └── Footer (no boundary)
```

A top-level boundary = **last line of defense**. Feature-level boundaries = **isolate crashes**, rest of app stays live.

**Rule of thumb:** Sections that take data from outside (APIs, user input) — wrap those. Static UI sections — wrapping is unnecessary.

## What Error Boundaries Are NOT

Error boundaries don't catch every error. Important to know:

| Scenario | Boundary catches it? |
|----------|--------------------------|
| Render error (inside a component function) | ✅ Yes |
| Lifecycle error (inside `useEffect`) | ✅ Yes (React 16+) |
| Event handler error (`onClick`) | ❌ No — React doesn't wrap event handlers in try/catch |
| Async error (`setTimeout`, Promise) | ❌ No — runs outside the event loop |
| Server-side rendering error | ❌ No |
| The boundary's own error | ❌ No — a boundary can't catch itself crashing |

**What about event handler errors?** They don't reach the boundary — React logs them to console. If you need to handle them, wrap your handler in try/catch:

```tsx
const handleClick = () => {
  try {
    // risky logic
  } catch (err) {
    console.error("Click handler error:", err);
  }
};
```

**Takeaway:** Error boundary = **render + lifecycle** errors' net. Async and event-handler errors need their own handling.

## So Here's the Takeaway

Error boundaries are React apps' **safety net**. They're class components — not built with hooks. They do two jobs: showing a fallback (`getDerivedStateFromError`) and logging the error (`componentDidCatch`). They prevent the white screen of death, and let the rest of the app keep running.

3. What are the different responsibilities of `getDerivedStateFromError` and `componentDidCatch`?

<details>
<summary>Show Answer</summary>

That's why it's static and shouldn't have side effects. `componentDidCatch` is called during the commit phase — its job is side effects: logging the error to console, or sending it to an error-tracking service. <details>
