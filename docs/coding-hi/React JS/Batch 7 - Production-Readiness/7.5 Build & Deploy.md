## Problem First — Dev Server Is Only for You

The `bun run dev` server is only for **local development.** It can't be deployed:

| `bun run dev` | Production |
|---|---|
| Serves source code directly | Serves an optimized bundle |
| Slow (files on-the-fly) | Fast (minified + compressed) |
| HMR, error overlay — dev tooling | No dev tooling — focused on performance |
| Only on your machine | On every device (mobile, desktop) |

**Production is a different thing.** The browser doesn't want raw source code — it wants optimized files that load fast. That's why the first step is: **build.**

---

## Step 1 — Production Build

Vite apps have a build command. Run it in the `custom-hooks-demo` project:

```bash
bun run build
```

**What happens:**

```
Source code (TSX, TS, CSS)
        │
        ▼
Vite: bundling → minification → optimization
        │
        ▼
dist/ folder — production-ready files
├── index.html
├── assets/
│   ├── index-abc123.js   ← minified JS bundle
│   ├── index-xyz456.css  ← minified CSS
│   └── ...
```

**What each step does:**

| Step | What it does |
|------|-----|
| **Bundling** | Combines all JS/TSX files into one (or a few) small files |
| **Minification** | Shorter variable names (`a`, `b`), removes spaces and comments — smaller file |
| **Tree-shaking** | Removes unused code (unused imports, dead code) from the bundle |
| **Code splitting** | Separates lazy parts (from 7.5.1) — only loaded when needed |
| **Hash filenames** | `index-abc123.js` — cache busting, new file on every update |

**Result:** The `dist/` folder holds optimized files that load quickly in the browser.

---

## Step 2 — Checking the Production Build

After building, test the production build locally with the `preview` command:

```bash
bun run preview
```

This serves the production build locally — like a real production experience. Check here: routing works? lazy loading works? The build is ready to deploy?

**Build check is important:** Remove source maps from production builds (don't expose your code), and pay attention to bundle size:

```bash
bun run build
```

Vite reports the bundle size in output:

```
dist/index.html                    0.52 kB │ gzip: 0.31 kB
dist/assets/index-DcP2b5sB.js  212.35 kB │ gzip: 68.21 kB
```

**Why bundle size matters:** 68KB gzipped JS — about 1 second load time on Indian 4G. 2MB gzipped — 15+ seconds, users leave. Performance = user retention.

## Step 3 — Env Vars in Production

In 7.2 we learned `.env` + `VITE_` prefix. Here's how it works in production builds:

**Build-time injection:** Vite injects env vars **at build time** into the bundle. Not at runtime.

```
At build time (bun run build):
  import.meta.env.VITE_QUOTE_API_URL → "https://api.quotable.io/random"
                                        ↑ written directly into the bundle

Then the bundle runs in the browser — with that URL hardcoded
```

**What this means:** Set production env vars *before* deploying. Two ways:

**Method 1 — `.env.production` file:**

```
# .env.production
VITE_QUOTE_API_URL=https://api.quotable.io/random
```

Vite automatically uses `.env.production` at build time (when you run `bun run build`).

**Method 2 — Platform env settings:** Set env vars in Vercel/Netlify dashboard (shown in the deploy step).

## Step 5 — Deploy (Vercel)

**Vercel** is the most popular deploy platform for React/Vite projects (free tier). Two ways: push to GitHub and connect Vercel (auto-deploy), or use the CLI.

### Method 1 — GitHub + Vercel (Recommended)

**First, create a GitHub repo and push:**

```bash
git init
git add .
git commit -m "init: custom hooks demo"
git remote add origin https://github.com/yourname/custom-hooks-demo.git
git push -u origin main
```

**Then on Vercel:**
1. Sign up at [vercel.com](https://vercel.com) (with GitHub)
2. Click "Add New Project" → select your repo
3. Framework: **Vite** (Vercel auto-detects)
4. Add env vars (`VITE_QUOTE_API_URL` if you have one)
5. Click Deploy — you'll get a URL like `https://custom-hooks-demo.vercel.app`

**Auto-deploy magic:** Every push to GitHub → Vercel auto-builds + auto-deploys. This is **Continuous Deployment** — you push code, the app updates.

### Method 2 — Vercel CLI

```bash
bunx vercel
```

After CLI prompts, it deploys directly.

## Step 6 — Deploy (GitHub Pages)

**GitHub Pages** is GitHub's free static hosting. Setup differs slightly from Vercel — Pages needs static files.

**First**, set `base` in `vite.config.ts` — for the repo subdirectory:

```ts
// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  // GitHub Pages serves the app in a repo subfolder
  base: "/custom-hooks-demo/",
});
```

**Then build + deploy:**

```bash
bun run build
```

Upload the `dist/` folder to GitHub Pages — manually, or via GitHub Actions (a workflow file).

## Vercel vs GitHub Pages — When to Use What

| | Vercel | GitHub Pages |
|---|---|---|
| **Setup** | Auto (framework detection) | Manual (base path config) |
| **Env vars** | Easy on the dashboard | Set at build time |
| **Continuous Deploy** | Auto on every GitHub push | Via GitHub Actions |
| **Best for** | Professional portfolio projects | Small static projects |

**Recommendation:** For portfolio/capstone projects, **Vercel** — cleanest setup + auto-deploy. GitHub Pages also works but needs extra config (base path, Actions).

## In Your Own Words

1. What happens in a production build (`bun run build`) that doesn't happen in `bun run dev`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** During production build, Vite converts source code into an optimized bundle — bundling (combines all files into a few small ones), minification (shorter variable names, removes spaces), tree-shaking (strips unused code), code splitting (splits lazy parts into separate chunks), and hash filenames (cache busting). The dev server just serves source files on-the-fly — slow, with dev tools. Production build produces a `dist/` folder that loads fast and is ready to deploy.

</details>

2. How do env vars work in a production build? What does "build-time injection" mean?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Values from `import.meta.env.VITE_*` are **injected directly into the bundle at build time** — not at runtime. When you run `bun run build`, Vite reads the `.env.production` file or platform env settings and writes the values into the bundle. The bundle then carries those values hardcoded. This means env vars must be set before deploying — they can't be changed after building without rebuilding. `.env.production` is automatically used during build.

</details>

3. Vercel vs GitHub Pages for deployment — main differences, and which is recommended for a portfolio project?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Vercel auto-detects the framework (recognizes Vite right away), env vars are set easily on the dashboard, and pushing to GitHub triggers auto-deployment (Continuous Deployment). GitHub Pages requires manual `base` path config in `vite.config.ts` (since the app is served in a repo subfolder) and env vars must be set at build time. For portfolio/capstone projects, Vercel is recommended — cleanest setup, auto-deploy, professional URL. GitHub Pages is better for smaller static projects.

</details>

4. What sections should a README have, and what do recruiters look at first?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Essential sections: project name + one-line description, Tech Stack, Setup instructions (install + run), Scripts table, Features list, and Deployed At URL. Recruiters look at Tech Stack and Features first — "what modern technologies are used" and "what was built" — then click the live demo URL. A clean README creates a professional impression before anyone even looks at the code.

</details>

5. What verification checks are essential after deployment and why?

<details>
<summary>Show Answer</summary>

**Sample Answer:** (1) Open the live URL on mobile — verify responsive UI (production must work on all devices). (2) Hard refresh — confirm the new bundle loads, not the cached old version, because hash filenames should force a fresh load. (3) Check DevTools console — no JavaScript errors. (4) Run Lighthouse — get performance + accessibility scores. (5) Verify production env vars — API URL is correct, not pointing to localhost. These checks ensure the app isn't just "deployed" but "working correctly in production" — which is what matters.

</details>
