## Step 1 — Testing useLocalStorage

Test `useLocalStorage`. Create new file — `src/hooks/__tests__/useLocalStorage.test.tsx`:

```tsx
// src/hooks/__tests__/useLocalStorage.test.tsx
import { renderHook, act } from "@testing-library/react";
import { beforeEach, describe, it, expect } from "vitest";
import { useLocalStorage } from "../useLocalStorage";

describe("useLocalStorage", () => {
  beforeEach(() => {
    localStorage.clear();
  });

  it("returns the initial value when localStorage is empty", () => {
    const { result } = renderHook(() =>
      useLocalStorage("todos", [])
    );

    expect(result.current[0]).toEqual([]);
  });

  it("saves to localStorage when state updates", () => {
    const { result } = renderHook(() =>
      useLocalStorage<string[]>("todos", [])
    );

    act(() => {
      result.current[1](["Buy milk", "Pay bills"]);
    });

    expect(result.current[0]).toEqual(["Buy milk", "Pay bills"]);

    // also saved in localStorage
    const saved = localStorage.getItem("todos");
    expect(saved).not.toBeNull();
    expect(JSON.parse(saved as string)).toEqual(["Buy milk", "Pay bills"]);
  });

  it("loads the saved value from localStorage if present", () => {
    localStorage.setItem("todos", JSON.stringify(["Old task"]));

    const { result } = renderHook(() =>
      useLocalStorage<string[]>("todos", [])
    );

    expect(result.current[0]).toEqual(["Old task"]);
  });
});
```

**What we're testing:**

| Test | Behaviour |
|------|-----------|
| `when localStorage is empty` | Default initial value |
| `when state updates` | State updates + localStorage syncs |
| `saved value loads` | Refresh scenario — existing data loads |

`beforeEach(() => localStorage.clear())` — clears localStorage before each test. Because jsdom's localStorage persists between tests — if you don't clear, one test affects another.

## Step 2 — Testing useFetch

Test `useFetch`. Create new file — `src/hooks/__tests__/useFetch.test.tsx`:

```tsx
// src/hooks/__tests__/useFetch.test.tsx
import { renderHook, act, waitFor } from "@testing-library/react";
import { describe, it, expect, vi, beforeEach } from "vitest";
import { useFetch } from "../useFetch";

describe("useFetch", () => {
  beforeEach(() => {
    vi.restoreAllMocks();
  });

  it("on success — data is set, isLoading is false", async () => {
    vi.spyOn(globalThis, "fetch").mockResolvedValue(
      new Response(JSON.stringify({ name: "Chicken" }), {
        headers: { "Content-Type": "application/json" },
      })
    );

    const { result } = renderHook(() =>
      useFetch<{ name: string }>("https://api.example.com/recipe")
    );

    // initially loading
    expect(result.current.isLoading).toBe(true);

    // wait for fetch to complete
    await waitFor(() => {
      expect(result.current.isLoading).toBe(false);
    });

    expect(result.current.data).toEqual({ name: "Chicken" });
    expect(result.current.error).toBeNull();
  });

  it("on error — error state is set", async () => {
    vi.spyOn(globalThis, "fetch").mockRejectedValue(new Error("Network fail"));

    const { result } = renderHook(() =>
      useFetch<{ name: string }>("https://api.example.com/recipe")
    );

    await waitFor(() => {
      expect(result.current.error).toBe("Network fail");
    });

    expect(result.current.data).toBeNull();
    expect(result.current.isLoading).toBe(false);
  });
});
```

**What's happening:**

| Thing | Why |
|-------|-----|
| `vi.spyOn(globalThis, "fetch")` | Replace the real network call with a **mock** fetch — don't hit the real API in tests (slow + unreliable) |
| `new Response(JSON.stringify(...))` | Fake API response — like the server sent JSON |
| `mockResolvedValue` | Fetch **resolves successfully** |
| `mockRejectedValue` | Fetch **throws an error** |
| `waitFor` | Wait for async rendering — transition from loading to data |
| `vi.restoreAllMocks()` | Reset mocks after each test — one test doesn't affect another |

**Note:** You have to mock `useFetch` because real network calls in tests are slow and flaky. This mock-fetch pattern is industry standard — `vi.spyOn(globalThis, "fetch")`.

## Step 3 — Testing the Zustand Store

Test the Zustand store — the counter store from 6.4. New file — `src/stores/__tests__/counterStore.test.ts`:

```ts
// src/stores/__tests__/counterStore.test.ts
import { describe, it, expect, beforeEach } from "vitest";
import { useCounterStore } from "../counterStore";

describe("counterStore", () => {
  beforeEach(() => {
    // reset state before each test — keep it clean
    useCounterStore.setState({ count: 0 });
  });

  it("increment increases the count", () => {
    useCounterStore.getState().increment();
    useCounterStore.getState().increment();

    expect(useCounterStore.getState().count).toBe(2);
  });

  it("decrement decreases the count", () => {
    useCounterStore.getState().increment();
    useCounterStore.getState().decrement();

    expect(useCounterStore.getState().count).toBe(0);
  });

  it("reset sets the count to 0", () => {
    useCounterStore.getState().increment();
    useCounterStore.getState().reset();

    expect(useCounterStore.getState().count).toBe(0);
  });
});
```

**Why store tests differ from component tests:**

| | Component test | Store test |
|---|---|---|
| Access | `render` + interact with UI | `getState()` + call action |
| Assert | Query the DOM | `getState().count` |
| State update | `userEvent` (through UI) | `getState().increment()` (direct) |

Testing a Zustand store doesn't require rendering any component — just call `useCounterStore.getState().increment()` directly, and verify with `getState().count`. Fast and isolated.

`beforeEach` with `setState({ count: 0 })` — resets state because the store is a module-level singleton shared between tests.

## Step 4 — Component Tests: TodoApp

In 7.3 we wrote the first test for `TodoApp`. Now we add more tests — delete and toggle behaviour. Update `src/components/__tests__/TodoApp.test.tsx`:

```tsx
// src/components/__tests__/TodoApp.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, it, expect, beforeEach } from "vitest";
import TodoApp from "../TodoApp";

describe("TodoApp", () => {
  beforeEach(() => {
    localStorage.clear();
  });

  it("adds a new task", async () => {
    const user = userEvent.setup();
    render(<TodoApp />);

    await user.type(screen.getByPlaceholderText("Add a task..."), "Buy milk");
    await user.click(screen.getByRole("button", { name: "Add" }));

    expect(screen.getByText("Buy milk")).toBeInTheDocument();
  });

  it("toggles task completion", async () => {
    const user = userEvent.setup();
    render(<TodoApp />);

    await user.type(screen.getByPlaceholderText("Add a task..."), "Pay bills");
    await user.click(screen.getByRole("button", { name: "Add" }));

    const checkbox = screen.getByRole("checkbox", { name: "Pay bills" });
    await user.click(checkbox);

    expect(checkbox).toBeChecked();
  });

  it("deletes a task", async () => {
    const user = userEvent.setup();
    render(<TodoApp />);

    await user.type(screen.getByPlaceholderText("Add a task..."), "Temp task");
    await user.click(screen.getByRole("button", { name: "Add" }));

    await user.click(screen.getByRole("button", { name: "Delete" }));

    expect(screen.queryByText("Temp task")).not.toBeInTheDocument();
  });
});
```

**Things to notice:**

| Pattern | What |
|---------|------|
| `getByRole("checkbox", { name: "Pay bills" })` | Checkbox found by accessible name — its label |
| `expect(checkbox).toBeChecked()` | jest-dom matcher — checked state |
| `queryByText(...).not.toBeInTheDocument()` | **queryBy** (returns null) + negative assertion — "doesn't exist" check |
| `localStorage.clear()` in each test | Tests stay isolated |

**The difference between getBy and queryBy shows up here:** `getByText` throws an error if the element is not found. `queryByText` returns null if not found — so to verify "task was removed," you use `queryByText`.

4. **Store tests** — Zustand store tests directly via `getState()` without rendering components

6. **getBy vs queryBy** — "element exists" vs "element is gone" — different use cases

## In Your Own Words

1. Why use `vi.spyOn(globalThis, "fetch")` instead of real API calls in tests?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Real network calls make tests slow and flaky — network delay, server down, rate limits, random failures. Tests must be deterministic — same result every time. Mock fetch (`vi.spyOn`) replaces the real API with controlled responses that you manage — success or error exactly when you want. This makes tests fast, reliable, and isolated. Depending on a real server in tests is never best practice.

</details>

2. What do `renderHook` and `act` do? Why don't they need both in store tests?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `renderHook` renders a hook without a component, and you access its return value via `result.current`. When a hook's state updates (like `result.current[1](newValue)`), `act` tells React to re-render — so the assertion reads the updated value. Store tests don't need either because a Zustand store lives outside React's render cycle — `useCounterStore.getState().increment()` calls the action directly, and `getState().count` reads the value directly. No render, no `act` needed.

</details>

3. What's the difference between `getByText` and `queryByText`, and why `queryByText` in the delete test?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `getByText` throws an **error** if the element isn't found — it checks "exists." `queryByText` returns **null** if not found — it checks "doesn't exist." In the delete test, you're verifying the task was removed — `queryByText("Temp task")` returns null if deleted, and `expect(...).not.toBeInTheDocument()` passes on null. If you used `getByText`, it would throw "not found" after deletion — instead of confirming deletion, you'd get an error about the element not existing, which messes up the test's intent.

</details>

4. Why is `localStorage.clear()` and `setState({ count: 0 })` before each test essential?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Because jsdom's `localStorage` and the Zustand store are **module-level singletons** — they persist across tests. If one test saves a value and you don't clean up, the next test sees that same value and its assertions may fail. `beforeEach` cleanup guarantees every test starts isolated — with fresh state, not depending on any other test's data. Isolated tests are deterministic.

</details>

5. Why are store tests faster and simpler than component tests? When is store testing better than component testing?

<details>
<summary>Show Answer</summary>

**Sample Answer:** In store tests, no component is rendered, no DOM, no user interaction simulation — just `getState().action()` and verify with `getState().value`. That's why they're fast and simple. Component tests are useful when you need to verify UI behavior — what happens when the user clicks something and what appears on screen. Best practice: **test the store's logic with store tests, test the UI's logic with component tests.** The store holds business logic (increment, decrement, reset) in plain JavaScript — wrapping that in a component is unnecessary overhead. In components, test the rendering behavior (task appears, checkbox gets checked).

</details>
