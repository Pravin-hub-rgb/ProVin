## Problem First — Fear of Regression

Imagine an app. Yesterday you added a "filter" feature. Today you're adding "dark theme". Do you know that the filter still works? You manually tested 2 minutes ago — because filter was on your mind at that moment.

But 3 weeks later — maybe a new developer, or even you — you change the filter logic. The filter breaks somehow. **And nobody knows** because there were no tests.

```
Code change (theme, new feature)
        │
        ▼
Old feature (filter) broke — REGRESSION
        │
        ▼
Nobody knows — because there were no tests
```

**Automated tests solve this exact problem:** Write the test once — "filter works." Every time code changes, run the tests. If the filter breaks, the test turns **red**, and you know immediately. The fear of regression is gone.

---

## What Is Vitest — And How It Differs from Jest

**Vitest** is a JavaScript testing framework — **built on top of Vite.** Since your project is Vite-based, Vitest integrates smoothly.

| | Jest (old standard) | Vitest (new, Vite-native) |
|---|---|---|
| **Setup** | Separate config, Babel/ts-jest | Reuses Vite config — near-zero config |
| **Speed** | Slow (rebuilds everything) | Fast (Vite's native ESM + on-demand) |
| **TypeScript** | Needs ts-jest / Babel | Native — Vite handles it already |
| **Hot reload** | No | Even for tests |

Jest is the old industry standard — you'll hear about it in interviews. But for new Vite projects, **Vitest** is best practice — it's made by the Vite team. That's what we'll use.

## Step 2 — A Tiny App to Test

Testing doesn't need a big app. Create a **Counter** — a number, a button. Simple things = simple tests = focus on testing, not the app.

### Counter Structure — Three Files

The counter needs three things: a component, the hook with its logic, and App that renders the counter.

New file — `src/hooks/useCounter.ts` (counter logic — count + increment):

```ts
// src/hooks/useCounter.ts
import { useState } from "react";

export function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);

  const increment = () => setCount((c) => c + 1);

  return { count, increment };
}
```

**What this does:** A custom hook — returns `count` (state) and `increment` (function that adds 1). `initial` defaults to 0. Custom hook concept from 6.1 — state logic that any component can use.

New file — `src/components/Counter.tsx` (component that uses the hook):

```tsx
// src/components/Counter.tsx
import { useCounter } from "../hooks/useCounter";

export function Counter() {
  const { count, increment } = useCounter(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={increment}>Increment</button>
    </div>
  );
}
```

**What this does:** Renders the counter — a heading with the current count, and an "Increment" button. Click it → `increment()` → count goes up.

Now render `Counter` in `src/App.tsx`:

```tsx
// src/App.tsx
import { Counter } from "./components/Counter";

function App() {
  return <Counter />;
}

export default App;
```

Test in browser — count shows 0, click the button, 1, 2, 3... works fine. **This is the app we'll test** — one component and one hook. That's all you need.

## Step 3 — Install Testing Packages

Testing a React project needs 5 packages. Install:

```bash
bun add -d vitest jsdom @testing-library/react @testing-library/user-event @testing-library/jest-dom
```

**What each package does:**

| Package | Job |
|---------|------|
| `vitest` | Testing framework — runs the tests |
| `jsdom` | Simulates a browser in Node — provides fake DOM APIs |
| `@testing-library/react` | Renders React components + queries |
| `@testing-library/user-event` | Realistic user interactions (typing, clicking) |
| `@testing-library/jest-dom` | Extra matchers (`toBeInTheDocument`, `toHaveTextContent`) |

**In short:** vitest runs tests, jsdom gives you a fake browser (renders React components in a DOM), testing-library helps you render and query, and jest-dom gives you readable assertions.

## Step 4 — Config: Telling Vitest What to Do

Three small things needed — tell Vitest the test environment, register jest-dom, and create a test script.

First — create `vitest.config.ts` (in project root, next to `package.json`):

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "jsdom",
    setupFiles: "./src/test/setup.ts",
  },
});
```

**What this says:** `environment: "jsdom"` — tests run simulating a browser (React components need a DOM). `setupFiles` — this file runs before every test (where jest-dom gets registered).

Second — create new file `src/test/setup.ts`:

```ts
// src/test/setup.ts
import "@testing-library/jest-dom/vitest";
```

Just one line — jest-dom's extra matchers (`toBeInTheDocument`) are available in every test.

Third — add the test script to `package.json`:

```json
// package.json (add to scripts section)
{
  "scripts": {
    "test": "vitest"
  }
}
```

Now run: `bun run test` — no tests yet, so "No test files found" appears. Fine — now we write tests.

## The First Test — What to Write?

There's a fundamental pattern in testing: **AAA — Arrange, Act, Assert**

```
ARRANGE — setup: what are you testing (render a component, pass data)
ACT      — action: what does the user do (click, type)
ASSERT   — verify: what do you expect (result is present?)
```

New file — `src/components/__tests__/Counter.test.tsx` (folder `__tests__` is new):

```tsx
// src/components/__tests__/Counter.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, it, expect } from "vitest";
import { Counter } from "../Counter";

describe("Counter", () => {
  it("starts by showing count 0", () => {
    // ARRANGE — render the component
    render(<Counter />);

    // ASSERT — the heading should have 0
    expect(screen.getByRole("heading", { name: "Count: 0" })).toBeInTheDocument();
  });

  it("clicking Increment increases the count", async () => {
    // ARRANGE — render + user simulation setup
    const user = userEvent.setup();
    render(<Counter />);

    // ACT — click the button
    await user.click(screen.getByRole("button", { name: "Increment" }));

    // ASSERT — count became 1
    expect(screen.getByRole("heading", { name: "Count: 1" })).toBeInTheDocument();
  });
});
```

**What each part does:**

| Thing | What it is |
|-------|---------|
| `describe("Counter", ...)` | Test group — all Counter tests go here |
| `it("...", ...)` | One test case — i.e., one behaviour |
| `userEvent.setup()` | Sets up realistic user simulation |
| `render(<Counter />)` | Renders the component into fake DOM (jsdom) |
| `screen.getByRole("heading", { name: "Count: 0" })` | Find heading — by role + accessible name |
| `screen.getByRole("button", { name: "Increment" })` | Find button — by role (accessible) |
| `await user.click(...)` | The user clicks |
| `expect(...).toBeInTheDocument()` | Assertion — the element should be in the document |

**Why use `getByRole`?** Because it's an **accessibility-first** query — finding a button by its accessible name. A screen reader identifies it the same way. Testing Library's philosophy: **test the way the user uses it** — not DOM structure, but user experience.

## Jest-DOM Matchers — The Language of Assertions

`@testing-library/jest-dom` provides handy matchers that are more readable than plain assertions:

| Matcher | Checks | In the Counter |
|---------|------------------|--------------|
| `toBeInTheDocument()` | Element is in the DOM | Heading is visible |
| `toHaveTextContent("...")` | Element contains text | `expect(screen.getByRole("heading", { name: "Count: 1" }))` |
| `toBeDisabled()` / `toBeEnabled()` | Button disabled/enabled | Form buttons |
| `toHaveValue("...")` | Input's value | Form inputs |
| `toHaveClass("...")` | Class attribute | Styling |

**Why matchers help:** assertions read like written English — "this element should be in the document." How clear the test is depends on how much it reads like that.

## Testing Hooks — renderHook

Components are tested with `render`. Hooks (like our `useCounter`) have their own helper — **`renderHook`**. New file — `src/hooks/__tests__/useCounter.test.ts`:

```tsx
// src/hooks/__tests__/useCounter.test.ts
import { renderHook, act } from "@testing-library/react";
import { describe, it, expect } from "vitest";
import { useCounter } from "../useCounter";

describe("useCounter", () => {
  it("returns the initial value when no default is given", () => {
    const { result } = renderHook(() => useCounter());

    expect(result.current.count).toBe(0);
  });

  it("increases count when increment is called", () => {
    const { result } = renderHook(() => useCounter(5));

    act(() => {
      result.current.increment();
    });

    expect(result.current.count).toBe(6);
  });
});
```

**Difference — components vs hooks tests:**

| | Component test | Hook test |
|---|---|---|
| Helper | `render(<Component />)` | `renderHook(() => useHook(...))` |
| Get result | Query from DOM | `result.current` |
| State update | `userEvent` | `act(() => result.current.increment())` |
| Assert | `screen.getBy...` | `result.current.count` |

`act()` — tells React that "state is updating, re-render now." When testing hooks and state updates, wrap them in `act`.

## Common Testing Patterns

### Pattern 1 — getByRole vs getByText

```tsx
// Accessible — role + name (recommended)
screen.getByRole("button", { name: "Increment" })

// By text (when you need a specific element)
screen.getByText("Increment")
```

### Pattern 2 — Query Errors

Testing Library queries **throw an error** if they don't find an element:

- `getBy...` — throws an **error** if not found (most common)
- `queryBy...` — returns **null** if not found (use to check "does not exist")
- `findBy...` — **waits** for it asynchronously (after loading)

```tsx
it("shows data after loading", async () => {
  render(<RecipeList />);
  expect(screen.queryByText("Loading...")).not.toBeInTheDocument();
  expect(await screen.findByText("Chicken Soup")).toBeInTheDocument();
});
```

`findByText` **waits** for async rendering — perfect for components that fetch data. (If you have a component that gets data from an API — like the one built in 2.2.)

### Pattern 3 — One Behaviour, One `it`

```tsx
describe("Counter", () => {
  it("starts at count 0", () => { ... });
  it("increases count on increment", () => { ... });
});
```

Each `it` = one behaviour. Don't put "Counter is totally fine" in one test — separate tests for separate verifications.

## What Testing Is NOT

- ❌ Testing doesn't mean **writing tests for every line of code** — cover the core behaviours
- ❌ Tests aren't just **assertions** — they're documentation of behaviour ("if user does X, Y shows up")
- ❌ `getByRole` isn't just for **class/id** — use accessible queries (the screen reader difference matters)
- ❌ Tests **must be deterministic** — no timing guesses, no randomness — same result every time
- ❌ Test passing doesn't mean the app is **production-ready** — tests are one layer, manual QA + E2E needed too

3. What is the AAA pattern? Where was each A in the Counter's increment test?

<details>
<summary>Show Answer</summary>

**Sample Answer:** AAA = Arrange, Act, Assert. Arrange — setup: `userEvent.setup()` and `render(<Counter />)`. Act — action: `await user.click(screen.getByRole("button", { name: "Increment" }))`. Assert — verify: `expect(screen.getByRole("heading", { name: "Count: 1" })).toBeInTheDocument()` — the count became 1. Every test follows this pattern — setup first, then action, then verification. </details>

4. `getByRole` vs `getByText` — when to use each, and why is `getByRole` recommended?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `getByRole` finds an element by its ARIA role + accessible name — like `getByRole("button", { name: "Increment" })`. It's recommended because it's accessibility-first — a screen reader identifies the element the same way. This means tests check user experience, not DOM structure — change the structure and the test won't break. Use `getByText` when finding by role feels unnatural (like targeting a specific paragraph's text). Rule of thumb: try role queries first, then text.

</details>

5. What's the difference between `render` and `renderHook`, and why is `act()` needed in hook tests?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `render` puts a component into the fake DOM — you check the result using queries on `screen`. `renderHook` renders a hook without a component — you access the return value via `result.current`. When a hook's state updates (like `result.current.increment()`), `act()` tells React to re-render — so your assertion reads the updated value. Without `act()`, React warns and the assertion might read the stale value.

</details>
