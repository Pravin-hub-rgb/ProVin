## Where We Left Off

In 1.2, we created our first component — `ProfileCard` — a function that starts with a capital letter and returns JSX. We used it inside `App()` with `<ProfileCard />`. Everything was in one file — `App.tsx`. But in real projects, code gets split across different files. For that, we need the **import/export** system.

## Broader Goal

So far you've written code in one file. But when the project grows to 10, 50, or 100 files, how does one file use things from another? The browser gives each file its own scope — variables from one file aren't automatically accessible in another. That's why JavaScript has a **module system** — `export` sends things out, `import` brings them in. We'll start with simple values and functions, then build up to React components.

## Step 1 — Feel the Problem

Think: "I created a variable in `data.ts` — `const name = "Vin"`. How do I use `name` inside `App.tsx`?"

Every file in the browser has its own **scope** — variables from `data.ts` aren't directly accessible in `App.tsx`. If you write `console.log(name)` in `App.tsx`, you'll get an error: "name is not defined."

That's why JavaScript has a module system — two simple words:

- **`export`** — "this thing will leave the file" (you're sending it out)
- **`import`** — "this thing comes from another file" (you're receiving it)

## Step 2 — Simplest Case: Exporting/Importing a Variable

Think: "I want to send a string variable to another file. How?"

`data.ts`:

```ts
export const name = "Vin";
```

`App.tsx`:

```tsx
import { name } from "./data";

console.log(name); // "Vin"
```

**Export:** The `export` keyword goes in front of the variable.

**Import:** `import { name } from "./data"` — the curly braces `{ }` hold the same name that was exported. `"./data"` is a relative path — "the `data.ts` file in the current folder."

File extensions like `.ts` aren't needed in the import path — TypeScript figures it out automatically.

> **"Restaurant menu" analogy:** `export` is adding an item to the menu. `import` is telling the waiter your order — you name the item exactly as it appears on the menu. (`export const name = "Vin"` → "name" is on the menu. Tell the waiter: `{ name }`.)

## Step 3 — Exporting Multiple Values

Think: "I want to export more than just `name` — `age` and `isStudent` too. Can I export them separately?"

**Concept — Named Export:** One file can export multiple things. Each export has its own name.

`data.ts`:

```ts
export const name = "Vin";
export const age = 25;
export const isStudent = true;
```

`App.tsx`:

```tsx
import { name, age, isStudent } from "./data";

console.log(name);      // "Vin"
console.log(age);       // 25
console.log(isStudent); // true
```

Or only import what you need:

```tsx
import { name } from "./data";          // just name
import { age, isStudent } from "./data"; // or separate lines
```

**Key Rules:**
- The imported name must **exactly match** the exported name — export `name`, import `{ name }`. Not `{ userName }`.
- Selective imports — take only what you need.
- `{ name }` with curly braces means "named import" — you're searching for that specific name in the file.

## Step 4 — Exporting Functions

Think: "Variables worked. Can I export functions too?"

Absolutely. Functions follow the same pattern — put `export` in front of the function.

`utils.ts`:

```ts
export function greet(name: string) {
  return `Hello, ${name}!`;
}

export function add(a: number, b: number) {
  return a + b;
}
```

`App.tsx`:

```tsx
import { greet, add } from "./utils";

console.log(greet("Vin"));  // "Hello, Vin!"
console.log(add(2, 3));     // 5
```

### Inline Export vs. Exporting at the Bottom

You can export inline while defining, or define first and export at the bottom:

```ts
// Style 1 — inline (most common)
export function greet(name: string) {
  return `Hello, ${name}!`;
}

// Style 2 — export at bottom
function greet(name: string) {
  return `Hello, ${name}!`;
}
export { greet }; // or export { greet as hello }
```

Both do the same thing. Inline style is more common — define and export in one place.

## Step 5 — Default Export

Think: "One file should have one main export — like `App.tsx` has the `App` component. Do I have to use curly braces every time?"

**Concept — Default Export:** When a file has one **most important thing**. Default exports are imported without curly braces.

`config.ts`:

```ts
const appName = "ProVin";
export default appName;
```

`App.tsx`:

```tsx
import appName from "./config";

console.log(appName); // "ProVin"
```

Notice — no `{ appName }`. Just `appName`. And in the file, the variable can have any name before default export:

```ts
const xyz = "ProVin";
export default xyz;  // variable name can be anything
```

```tsx
import appName from "./config";    // ✅ you choose the import name
import anything from "./config";   // ✅ allowed — default import names are your choice
console.log(appName); // "ProVin"
console.log(anything); // "ProVin"
```

**Default vs Named — the core difference:**

| | Named Export | Default Export |
|---|---|---|
| Syntax | `export const name = "Vin"` | `const name = "Vin"; export default name` |
| Import | `{ name }` — names must match | `anything` — you choose the name |
| Per file | Multiple | Only one |
| Use case | Utility functions, constants, types | The main component, the main class |

### Common Mistake — Direct Default Export with `const`

This is **wrong**:

```ts
export default const appTitle = "ProVin"; // ❌ Syntax error
```

Why? `export default` is followed by an **expression**, not a declaration. `const/let/var` are declarations, not expressions.

```ts
// ✅ Correct — expressions
export default "ProVin";
export default 42;
export default { name: "Vin" };

// ✅ Correct — declare first, then export
const appTitle = "ProVin";
export default appTitle;

// ✅ Correct — anonymous function (this IS an expression)
export default function() { return "hello"; }
```

**Exception:** Only `export default function greet() {}` works (named function declaration). This is a JavaScript historical exception — function declarations were allowed with `export default`. But not `const`/`let`/`var`.

**Rule of thumb:** Declare the variable first, then on a separate line write `export default variableName`. Or just put the value/expression directly.

## Step 6 — Apply to React Components

Think: "Variables and functions exported fine. A component is also a function — the one with a capital letter. So it exports the same way?"

Exactly the same. A component is just a function returning JSX:

`ProfileCard.tsx`:

```tsx
function ProfileCard() {
  return <div>Hello from ProfileCard</div>;
}

export default ProfileCard;  // component's default export
```

`App.tsx`:

```tsx
import ProfileCard from "./ProfileCard";

function App() {
  return <ProfileCard />;
}

export default App;
```

**Standard pattern for component files:**
- A file exports one component → **`export default`** is the perfect fit
- Match the component name to the file name — `ProfileCard.tsx` exports `ProfileCard`
- `App.tsx` also uses `export default App` — entry point of every app

### Default Import Name Flexibility

With default imports, you choose the name yourself:

```tsx
import Card from "./ProfileCard";        // ✅ allowed
import MyComponent from "./ProfileCard";  // ✅ allowed
```

But convention is to keep the same name as the component/file — makes code easier to read. This course follows that convention.

## Step 7 — Default + Named Exports Together

Think: "I default-exported the component. But I also have helper functions to export — like a type interface or constants. Can I add them with named export?"

Yes — a file can have **one `default` + multiple `named`** exports.

`ProfileCard.tsx`:

```tsx
export default function ProfileCard() {
  return <div>Profile</div>;
}

export function ProfileImage() {
  return <img src="..." alt="profile" />;
}

export const MAX_CARDS = 10;
```

Import:

```tsx
import ProfileCard, { ProfileImage, MAX_CARDS } from "./ProfileCard";
```

Default import without curly braces, named imports with curly braces. Both can be on one line.

## Step 8 — Import Renaming (`as` keyword)

Think: "Two different files both export a function called `greet` — `utils.ts` and `helpers.ts`. How do I resolve the naming conflict?"

Use the `as` keyword to rename imports:

```tsx
import { greet as greetFromUtils } from "./utils";
import { greet as greetFromHelpers } from "./helpers";

greetFromUtils("Vin");   // Hello, Vin!
greetFromHelpers("Vin"); // Hey, Vin!
```

## Step 9 — `import type`

Think: "I need to export an interface. But interfaces don't exist at runtime — they're TypeScript-only, for compile time. Does that matter for bundling?"

`types.ts`:

```ts
export interface User {
  name: string;
  age: number;
}
```

`App.tsx`:

```tsx
import type { User } from "./types";

const user: User = { name: "Vin", age: 25 };
```

`import type` tells the bundler (Vite) that this is type-only — don't include it in the runtime bundle. This reduces bundle size.

When the interface is defined in the same component file:

`ProfileCard.tsx`:

```tsx
export interface ProfileCardProps {
  name: string;
  role: string;
}

export default function ProfileCard({ name, role }: ProfileCardProps) {
  return <div>{name} — {role}</div>;
}
```

Import:

```tsx
import ProfileCard, { type ProfileCardProps } from "./ProfileCard";
```

Here the `type` keyword goes inline with the named import — signaling that `ProfileCardProps` is a type, not a runtime value.

## Summary

- **Variable export:** `export const name = "Vin"` → import: `{ name }`
- **Function export:** `export function greet() {}` → import: `{ greet }`
- **Default export:** `export default App` → import: `App` (no curly braces)
- **Default + named:** `import X, { Y, Z } from "./file"`
- **Named imports** must match exactly, **default imports** let you choose the name
- **Multiple named exports** per file, only **one** default
- **`as` keyword** to rename imports: `import { X as Y }`
- **`import type`** — for types only, runtime bundle is optimized
- File extensions aren't needed in import paths — TypeScript handles it
- `./` means "current folder" — paths are relative
