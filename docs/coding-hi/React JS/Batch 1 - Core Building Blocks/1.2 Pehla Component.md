## Step 1 — What is a Component?

Think: "In `App.tsx`, there's a function returning JSX. Can I create more functions like this?"

In every real app, code needs to be broken into small, reusable pieces. In React, each of those pieces is called a **component**.

**Concept:** A React component is just a JavaScript function with two rules:

1. **The function name must start with a capital letter** — `ProfileCard`, `Button`, `Header`
2. **The function must return JSX** — what React should render

```
// ❌ Not a component — starts with lowercase
function profileCard() { return <div>...</div>; }

// ✅ A component — starts with capital letter
function ProfileCard() { return <div>...</div>; }
```

Why capital letters? React needs to know whether something is a component or a regular HTML tag. `div` — React thinks "that's an HTML div tag." `ProfileCard` — React thinks "that's my custom component, render it."

## Step 2 — Create the ProfileCard Component

Think: "I get what a component function is. How do I actually use one?"

In `App.tsx`, add this new function above the `App` function:

```tsx
function ProfileCard() {
  const name = "Vin";
  const role = "React Developer";

  return (
    <div>
      <h2>{name}</h2>
      <p>{role}</p>
    </div>
  );
}

function App() {
  return (
    <div>
      <h1>My App</h1>
      <ProfileCard />
    </div>
  );
}
```

Notice — inside `App`, we've written `<ProfileCard />`. That's how you use a component — just like an HTML tag.

Browser check:

```
My App
Vin
React Developer
```

If you see a warning like `'ProfileCard' is defined but never used` — ignore it, that's a TypeScript warning. It'll be fixed once we import components in later files.

## Step 3 — TypeScript Component Typing

Think: "A component is a function returning JSX. How do you write its return type in TypeScript?"

From the TypeScript warm-up in 0.7, we learned you can explicitly write a function's return type. For React components, the return type is `JSX.Element`.

```tsx
function ProfileCard(): JSX.Element {
  const name = "Vin";
  const role = "React Developer";

  return (
    <div>
      <h2>{name}</h2>
      <p>{role}</p>
    </div>
  );
}
```

`JSX.Element` tells TypeScript that this function returns JSX. If you accidentally return something else, TypeScript catches it:

```tsx
function ProfileCard(): JSX.Element {
  return "Hello"; // ❌ Error — string is not JSX.Element
}
```

> **Note:** With React 19, `JSX.Element` is now a built-in global type (no React import needed). In React 18, you'd use `React.ReactNode` or `React.FC` instead. In React 19, `JSX.Element` is the standard.

### Important — don't put a line break between `return` and JSX

The most common beginner mistake:

```tsx
function ProfileCard(): JSX.Element {
  return                // ❌ Line break — ASI trap
  <div>
    <h2>Vin</h2>
  </div>
}
```

This won't work. Why? JavaScript's **Automatic Semicolon Insertion (ASI)** — when a line break immediately follows `return`, JavaScript thinks "that's the end of return, return undefined" and the `<div>` becomes unreachable code.

```tsx
// The JS engine parses it like:
return;
<div>...</div>  // Never executes
```

ProfileCard now returns nothing — `void`. But React components need JSX, not `void`.

**Two ways to fix it:**

1. **Keep return and JSX on the same line** (when JSX is short):

   ```tsx
   return <div>...</div>
   ```

2. **Wrap in parentheses** — the standard React pattern for multi-line JSX:

   ```tsx
   return (
     <div>...</div>
   )
   ```

   Parentheses don't trigger ASI because after `return (`, the line break happens but the expression isn't complete yet (waiting for the closing `)`). So JavaScript knows "wait, this expression isn't done yet, ignore the line break."

**Rule of thumb:** Wrap multi-line JSX in parentheses. Keep single-line JSX on the same line.

```tsx
// ✅ Single line — same line
return <h2>Vin</h2>;

// ✅ Multi-line — parentheses
return (
  <div>
    <h2>Vin</h2>
    <p>React Developer</p>
  </div>
);

// ❌ Never — line break then multi-line
return
<div>...</div>;
```

## Step 4 — Using Multiple Components

Think: "I've built one ProfileCard. Can I use it multiple times?"

In `App.tsx`:

```tsx
function App() {
  return (
    <div>
      <h1>My Team</h1>
      <ProfileCard />
      <ProfileCard />
      <ProfileCard />
    </div>
  );
}
```

Three cards show up in the browser — all with the same "Vin" and "React Developer." Nothing dynamic yet, but this demonstrates **component reusability** — write once, use multiple times.

### Component vs Regular Function

What's the difference between a component and a regular function?

| Feature | Regular Function | React Component |
|---------|-----------------|-----------------|
| Usage | Normal call: `greet("Vin")` | JSX tag: `<Greet name="Vin" />` |
| Return | Anything — string, number, object | JSX (what React renders) |
| Name | `greet` (lowercase) | `Greet` (capitalized) |
| Re-render | N/A | React handles automatically when state/props change |

A component is technically just a function — React gives it special treatment.

## Step 5 — TypeScript Type Inference

Think: "If I don't write the return type explicitly, will TypeScript complain?"

Try it — remove the `: JSX.Element`. TypeScript won't error.

**Concept — Type Inference:** TypeScript automatically infers that the component returns `JSX.Element`. Explicit return type is optional. React developers usually skip it because TypeScript infers it for them.

But when learning a new concept, writing the explicit type is a good habit — you know exactly what the function is returning.
