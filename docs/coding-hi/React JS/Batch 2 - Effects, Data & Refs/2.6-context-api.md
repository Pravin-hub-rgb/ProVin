```ts
// FILE: contexts/ThemeContext.tsx — don't forget to export

import { createContext } from "react";
export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("Must be inside ThemeProvider");
  return ctx;
}

export function ThemeProvider({ children }) { ... }

// FILE: App.tsx — import ThemeProvider from contexts file
// FILE: components/Navbar.tsx — import useTheme from contexts file
```

- **createContext** (export it) → creates a context container object

- **useContext(guard)** — consume value + error check

## Step 1 — Feel the Problem: Prop Drilling Without Escape

We need a dark/light mode toggle. Every component needs to know the current theme — background color, text color, everything changes. What happens if we lift state up?

I used to ignore prop drilling too — "2-3 levels, that's fine." But when I had to pass props 8 levels deep in a project, I realized something better was needed. Context API lets you provide a value in one place and access it from any nested component without passing props through middle components.

```text
App (theme state lives here)
  ├── Navbar
  │   ├── Logo (needs theme)
  │   └── ThemeToggle (needs theme + setter)
  ├── MainContent
  │   ├── Sidebar
  │   │   └── MenuItem[] (needs theme)
  │   └── Article (needs theme)
  └── Footer (needs theme)
```

Every component needs a `theme` prop — 10+ components, including middle ones that only pass props through. Prop drilling gone too far.

**Context API is the solution** — data reaches any component directly without middle components passing props. We do this in three steps: create → provide → consume.

**Why is it called "API"?** Think of a REST API — any client can make a direct request and get data without asking permission from intermediate servers. Context API is the same — any child component can call `useContext()` directly and get data without going through parent components for props. `createContext` creates an "endpoint" — the Provider serves data at that endpoint, and any component can fetch directly from it. That's why it's called "Context API" — React's built-in data-fetching endpoint for the component tree.

## Step 2 — Create Context (in a separate file)

**Think:** First we need a container where theme data can be stored. This container travels through the component tree — we create it with `createContext`.

**Concept — `createContext`:** This is a React built-in function. It creates a "container" object that can hold any value.

**Concept — Default value:** `createContext` always needs a default value. This is used when a component consumes context but has no Provider. We pass `undefined` so we can use the guard pattern later.

**File structure — Context in its own file is best practice.** Two benefits:
1. Any component can import context without circular dependencies
2. **No Fast Refresh warning** — In Vite/React dev mode, if a file exports both a component and a non-component (like `ThemeContext`), you get a warning: *"Fast refresh only works when a file only exports components."* Keeping context in its own file avoids this.

Create this file: `src/contexts/ThemeContext.tsx`

```ts
import { createContext } from "react";

export type Theme = "light" | "dark";

export interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);
```

**Line by line:**
- `import { createContext } from "react"` — importing from React
- `export type Theme = "light" | "dark"` — union type. `export` it so App.tsx and Navbar.tsx can use this type too
- `export interface ThemeContextValue` — the blueprint for the context container. `export` is essential — other files need to know what shape the context data has
  - `theme: Theme` — current theme value
  - `toggleTheme: () => void` — function to switch theme
- `export const ThemeContext = createContext<...>(undefined)` — the container is created. `export` is mandatory — without it, other files can't import it
  - Generic type `ThemeContextValue | undefined` — TypeScript knows either a properly typed object or undefined
  - `undefined` default — if used outside a Provider, you get undefined

> **Important:** If you don't `export`, then `ThemeContext`, `Theme`, and `ThemeContextValue` are only accessible within this file. Other files (App.tsx, Navbar.tsx) cannot import the context.

**Test:** Nothing prints in the console yet — we just created a container, haven't used it. ✅

## Step 3 — Provide Value (in App.tsx)

**Think:** Container is created, now we need to put the actual value in it. Theme state lives in App — we need to get it to every child component. Wrap children with `<ThemeContext>`, pass the value via the `value` prop.

**Concept — Provider component:** When we write `<ThemeContext value={...}>`, React creates a provider. This provider passes the value directly to all children inside the tree.

**Concept — React 19 syntax:** Previously you had to write `<ThemeContext.Provider value={...}>`. In React 19, the context object itself acts as a provider — no `.Provider` suffix needed.

**File:** This code goes in `src/App.tsx`. We need to import ThemeContext from `contexts/ThemeContext`.

```tsx
import { useState } from "react";
import { ThemeContext, type Theme } from "./contexts/ThemeContext";

function App() {
  const [theme, setTheme] = useState<Theme>("light");

  const toggleTheme = () => {
    setTheme((prev) => (prev === "light" ? "dark" : "light"));
  };

  return (
    <ThemeContext value={{ theme, toggleTheme }}>
      <Navbar />
      <MainContent />
      <Footer />
    </ThemeContext>
  );
}
```

**Line by line:**
- `import { ThemeContext, type Theme } from "./contexts/ThemeContext"` — importing the context container and type from Step 2. ThemeContext is used to provide/consume, Theme type keeps state type-safe
- `const [theme, setTheme] = useState<Theme>("light")` — theme state created
- `toggleTheme` function — sets the theme to its opposite
- `<ThemeContext value={{ theme, toggleTheme }}>` — provider wraps children, passing value
  - `{ theme, toggleTheme }` shorthand — both packed together

**Test:** Still nothing in console, but structure is ready. ✅

## Step 4 — Consume Value (in components/Navbar.tsx)

**Think:** Now child components need the theme. We can pull the value out with the `useContext` hook. But if a component uses context outside its Provider, it gets `undefined` — we must handle that.

**Concept — `useContext` hook:** This hook takes a context container as an argument and returns whatever value is inside it.

**Concept — Guard pattern:** If a component calls `useContext` outside its Provider, the default value (`undefined`) is returned. To prevent this, we check — if it's `undefined`, throw an error.

**File:** This code goes in `src/components/Navbar.tsx`. Since Navbar is a separate component, it needs `export default` so App.tsx can import it. ThemeContext must be imported from `../contexts/ThemeContext` (go up one level, then into contexts folder).

```tsx
import { useContext } from "react";
import { ThemeContext } from "../contexts/ThemeContext";

export default function Navbar() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("Navbar must be used within a ThemeProvider");

  return (
    <nav style={{ background: ctx.theme === "dark" ? "#333" : "#eee" }}>
      <ThemeToggle />
    </nav>
  );
}
```

**Line by line:**
- `import { useContext } from "react"` — importing the React hook
- `import { ThemeContext } from "../contexts/ThemeContext"` — importing the context container from Step 2. The `../` path is needed because the components folder is a sibling of the contexts folder
- `export default function Navbar()` — `export default` is needed so App.tsx can do `import Navbar from "./components/Navbar"`
- `const ctx = useContext(ThemeContext)` — pulling the value out of context
- `if (!ctx) throw new Error("Navbar must be used within a ThemeProvider")` — guard pattern. Include the component name in the error so debugging is easier
- `ctx.theme === "dark" ? "#333" : "#eee"` — background color based on theme

> **What It Is NOT:** Context API is **not** a global state management tool — it's a dependency injection mechanism. Redux/Zustand don't have their own store/cache the way Context does. Context just passes values through the React component tree without props. If you need complex state management, use Context + useReducer or Zustand.

**Test:** Open the browser — Navbar visible. In light mode, background is "#eee". Click the theme toggle — theme changes, Navbar background becomes "#333". ✅

## Step 5 — Custom Hook: `useTheme()` (Safe Pattern)

Writing `useContext(ThemeContext)` + `if (!ctx) throw` in every component is repetitive. Wrap it in a custom hook so it's reusable everywhere.

**Think:** Writing the same `useContext` + guard code in every component is repetitive. Wrap it in a custom hook so it's reusable everywhere.

**Concept — Custom hook:** Any function that starts with `use` is considered a hook in React. A custom hook is a wrapper function that uses existing hooks inside it.

**File:** This code goes in `contexts/ThemeContext.tsx` — that's where `ThemeContext`, `Theme`, and `ThemeContextValue` are already defined. No need to import `ThemeContext` — it's already in this same file. Just import `useContext` from React.

```tsx
import { createContext, useContext } from "react";

export type Theme = "light" | "dark";

export interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext);
  if (!ctx) {
    throw new Error("useTheme must be used within a ThemeProvider");
  }
  return ctx;
}
```

**Line by line:**
- `import { createContext, useContext } from "react"` — now we also import `useContext`
- `export function useTheme(): ThemeContextValue` — the custom hook. Return type is specified as ThemeContextValue
  - `useTheme` naming — React convention: custom hooks start with `use`
- `const ctx = useContext(ThemeContext)` — pulling value from context. ThemeContext is defined in this same file, no import needed
- `if (!ctx) throw new Error(...)` — guard pattern
- `return ctx` — returning the safe value. TypeScript now knows this is `ThemeContextValue`, not `undefined`

**Now use it in Navbar (don't forget to import):**
```tsx
// src/components/Navbar.tsx
import { useTheme } from "../contexts/ThemeContext";

export default function Navbar() {
  const { theme, toggleTheme } = useTheme();

  return (
    <nav style={{ background: theme === "dark" ? "#333" : "#eee", padding: "1rem" }}>
      <h1>My App</h1>
      <button onClick={toggleTheme}>
        Switch to {theme === "light" ? "Dark" : "Light"} Mode
      </button>
    </nav>
  );
}
```

Look at how clean that is — no need to write `useContext` and guard separately. It's all inside `useTheme()`. The component just calls `useTheme()` and gets what it needs. The `toggleTheme` function also comes from context — no more need to pass it as a prop.

**Test:** Any component that calls `useTheme()` automatically gets the guard check. ✅

## Step 6 — `ThemeProvider` Component (in contexts/ThemeContext.tsx)

In Step 5, we built the `useTheme()` custom hook. But we can also extract the provider logic into its own component.

**Think:** Right now all the provider logic is in the App component — state, toggle function, context wrapping. It's better to extract a `ThemeProvider` component that only handles providing context.

**Concept — Separation of concerns:** Each component should have one job. ThemeProvider's job is to hold theme state and provide it via context. App's job is to build the layout.

**File:** `ThemeProvider` also goes in `contexts/ThemeContext.tsx` — because it needs `ThemeContext`, `Theme`, and `useTheme` (added just now), and they're all already in this same file. Keeping all context-related logic in one file is a clean pattern.

```tsx
import { createContext, useContext, useState, type ReactNode } from "react";

export type Theme = "light" | "dark";

export interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
}

export const ThemeContext = createContext<ThemeContextValue | undefined>(undefined);

export function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext);
  if (!ctx) {
    throw new Error("useTheme must be used within a ThemeProvider");
  }
  return ctx;
}

interface ThemeProviderProps {
  children: ReactNode;
}

export function ThemeProvider({ children }: ThemeProviderProps) {
  const [theme, setTheme] = useState<Theme>("light");

  const toggleTheme = () => {
    setTheme((prev) => (prev === "light" ? "dark" : "light"));
  };

  return (
    <ThemeContext value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext>
  );
}
```

**Line by line:**
- `import { createContext, useContext, useState, type ReactNode } from "react"` — now we also import `useState` and `ReactNode`
- `interface ThemeProviderProps` — blueprint for props
  - `children: ReactNode` — accepts any React content
- `export function ThemeProvider` — exporting the provider component
- `const [theme, setTheme] = useState<Theme>("light")` — state lives here now
- `toggleTheme` function — same toggle logic
- `<ThemeContext value={{ theme, toggleTheme }}>` — children wrapped in context
- `{children}` — all inner components render here

**Now using App.tsx changes (don't forget imports):**
```tsx
import { ThemeProvider } from "./contexts/ThemeContext";
import Navbar from "./components/Navbar";

function App() {
  return (
    <ThemeProvider>
      <Navbar />
    </ThemeProvider>
  );
}
```

**Test:** All components can now access theme via `useTheme()`. App is clean. ✅

### Phase 3 — Dynamic Styles Based on Theme

**Think:** Styles are hardcoded now — `background: "#fff"` is always white. Background should change with theme. Create a styles object with values for both light and dark.

**Concept — Conditional styles:** `Record<string, React.CSSProperties>` is a type where keys are strings and values are CSS property objects. Put both light and dark styles under their keys, then use `styles[theme]` to apply styles for the current theme.

**Concept — Spread operator in styles:** `{...styles[theme]}` means — spread all CSS properties of the current theme style into the div's `style` object. Background, color, border — all applied at once.

**File:** `src/components/ThemedBox.tsx` — same import, only JSX and styles change.

```tsx
import { useTheme } from "../contexts/ThemeContext";

export default function ThemedBox() {
  const { theme, toggleTheme } = useTheme();

  const styles: Record<string, React.CSSProperties> = {
    light: { background: "#fff", color: "#000", border: "1px solid #ddd" },
    dark: { background: "#1a1a2e", color: "#fff", border: "1px solid #333" },
  };

  return (
    <div style={{ padding: "40px", ...styles[theme] }}>
      <h2>Current Theme: {theme}</h2>
      <button onClick={toggleTheme}>
        Switch to {theme === "light" ? "Dark" : "Light"} Mode
      </button>
      <p style={{ marginTop: "20px" }}>
        This box uses Context for theming — no props drilling!
      </p>
    </div>
  );
}
```

**Line by line:**
- `const styles: Record<string, React.CSSProperties>` — created styles object
  - `Record<string, ...>` means keys are strings ("light", "dark")
  - `React.CSSProperties` is the built-in TypeScript type for inline CSS
- `light: { background: "#fff", color: "#000", border: "1px solid #ddd" }` — light mode styles
- `dark: { background: "#1a1a2e", color: "#fff", border: "1px solid #333" }` — dark mode styles
- `{ padding: "40px", ...styles[theme] }` — padding stays fixed, rest spreads from current theme
- `theme === "light" ? "Dark" : "Light"` — button text also changes dynamically

## Step 8 — Context API: When to Use, When to Avoid

Look, Context API is powerful but dumping everything into it is an emotional decision — I've made this mistake too. Follow this rule:

### Use Context For:
- Theme (dark/light)
- Auth user
- Locale/language
- Any data almost every component needs

### Avoid Context For:
- High-frequency updates (animations, real-time data) — the entire subtree re-renders
- Data only 2-3 components need — lifting state up is enough
- Complex state logic — Context + useReducer works, but Zustand is better (Batch 6)

## Step 9 — Performance Note: useMemo to Keep Context Value Stable

This is the thing I've forgotten so many times.

**Think:** When context value changes → all consuming components re-render. Imagine: ThemeProvider renders → a new `{ theme, toggleTheme }` object is created (new reference) → all children re-render, even if the theme didn't change. That's unnecessary.

**Concept — Object references in React:** Every time you create a new object `{ theme, toggleTheme }`, React sees it as new because the memory location is different. Compared to the previous object, the reference is different → re-render triggered.

**Concept — useMemo hook:** This hook memoizes — as long as dependencies haven't changed, it returns the same stored value/reference instead of creating a new one.

```tsx
import { useMemo, useCallback } from "react";

function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>("light");
  const toggleTheme = useCallback(() => {
    setTheme((prev) => (prev === "light" ? "dark" : "light"));
  }, []);

  const value = useMemo(() => ({ theme, toggleTheme }), [theme]);

  return (
    <ThemeContext value={value}>{children}</ThemeContext>
  );
}
```

**Line by line:**
- `const toggleTheme = useCallback(..., [])` — keep function reference stable
  - `useCallback` memorizes the function
  - Empty dependency array `[]` means it never creates a new function reference
- `const value = useMemo(() => ({ theme, toggleTheme }), [theme])` — object memoized
  - `useMemo` takes a callback that returns the object
  - `[theme]` — dependencies: only when `theme` changes, create a new object
- `value={value}` — now a stable reference is passed

**Test:** Open React DevTools, Components tab — expand ThemeProvider. When you toggle theme, only ThemeProvider re-renders, not the children. ✅

## Trade-off: Context vs Alternatives

| Pattern | Use Case | Problem |
|---|---|---|
| **Lifting State Up** | 2-3 siblings share state | Prop drilling in deep trees |
| **Composition** | Deep tree, middle components don't need the data | Can't solve every case |
| **Context API** | Global data (theme, auth, locale) | High-frequency updates → full subtree re-render |
| **Zustand/Redux** (Batch 6) | Complex state, high performance | Extra boilerplate, learning curve |

**Rule of thumb:** Lift first. Compose second. Context third. Zustand when Context's re-render becomes a problem.

---

## Common Mistakes

1. **Forgetting the Provider** — Context value stays `undefined`. The custom hook guard gives a clear error.
2. **Putting everything in Context** — Only put data that almost every component needs (theme, auth). For 2-3 components, lifting state up is enough.
3. **High-frequency updates in Context** — Each update re-renders the entire consuming subtree. Real-time stock prices? Don't use Context — use Zustand or an external store.
4. **Forgetting useMemo** — Context value is an object/function, so every render creates a new reference. Wrap it with `useMemo` to avoid unnecessary re-renders.
