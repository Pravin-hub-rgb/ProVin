
## Cheat Sheet (Quick Recall)

```
Pattern: Data down, Actions up
State → prop (parent → child)
Child → callback → parent (via onXxx props)

Lifting State Up = pull state from child into a common parent
Siblings share data → keep state in parent, pass via props

Prop Drilling = middle components in a deep tree receiving props they don't need
Solution: Composition (children) or Context API
```

## What Happened So Far

We've learned three hooks — `useState` (client state), `useRef` (DOM refs + mutable values), and `useQuery` (server data). But one thing we haven't seen yet — **when two sibling components need the same data, how do we handle it?** The state lives in one child, and the other sibling also needs that data. React's data flow is top → bottom — siblings can't directly share data.

## Broader Goal

We'll build a simple counter with two sibling components:

- `CountDisplay` — shows the count
- `CountButton` — increments the count

First, we'll do the wrong approach (state in child) and feel the problem. Then we'll fix it with **Lifting State Up** — keep state in the common parent, pass data via props, pass actions via callbacks. Step by step, line by line.

---

## Step 1 — Static UI: Just HTML skeleton, no logic

**Think:** We're building a counter. One number displays, there's a button. First, all hardcoded — no state, no separate components, just HTML.

```tsx
function App() {
  return (
    <div>
      <p>Count: 0</p>
      <button>+1</button>
    </div>
  );
}
```

**Test:** Browser shows "Count: 0" and "+1" button. ✅ Just HTML — no state, no click logic.

---

## Step 2 — Two sibling components (still hardcoded)

**Think:** Split this HTML into two separate components — `CountDisplay` and `CountButton`. These are siblings — both are direct children of `App`. Still hardcoded, no state yet.

**Concept — Sibling components:** Two components rendered side by side under the same parent in the React tree.

```tsx
function CountDisplay() {
  return <p>Count: 0</p>;
}

function CountButton() {
  return <button>+1</button>;
}

function App() {
  return (
    <div>
      <CountDisplay />
      <CountButton />
    </div>
  );
}
```

**Test:** Same UI in the browser — "Count: 0" and "+1" button. ✅

**Where's the state?** Nowhere. Just hardcoded HTML split into two components.

---

## Step 3 — Put state in CountButton (wrong approach)

**Think:** Clicking the button should increment the count. Let me put `useState` inside `CountButton` — it manages its own count.

```tsx
function CountButton() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

Clicking the button increments — and it also shows "Count: {count}" inside the button itself.

Now I want `CountDisplay` to show the same count. Since both components are in the same file (`App.tsx`), can I just use the `count` variable directly in `CountDisplay`?

```tsx
function CountDisplay() {
  return <p>Count: {count}</p>;  // ❌ count doesn't exist here!
}
```

**This won't work.** `count` was declared inside the `CountButton` function — its **scope** is limited to only `CountButton`. `CountDisplay` is a separate function — it can't access variables declared inside `CountButton`, even if they're in the same file.

```
CountButton() {
  const count = ...  ← count lives here
  // Accessible only within CountButton
}

CountDisplay() {
  // count ❌ — outside CountButton's scope
}
```

React components are functions too — the same scope rules apply. That's why `CountDisplay` can't access `CountButton`'s `count`.

So for now, we hardcode it in `CountDisplay`:

```tsx
function CountDisplay() {
  return <p>Count: 0</p>;  // Hardcoded — no state yet
}
```

**Full code:**

```tsx
import { useState } from "react";

function CountDisplay() {
  return <p>Count: 0</p>;
}

function CountButton() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}

export default function App() {
  return (
    <div>
      <CountDisplay />
      <CountButton />
    </div>
  );
}
```

**Test:** Click the button — count increments inside the button, but `CountDisplay` still shows "Count: 0". ✅ (partially working)

The problem is clear now — `count` is locked inside `CountButton`'s scope, and `CountDisplay` can't reach it. It's a scope issue, not a file issue. How do we solve this? We need something "global"-like that both components can access?

---

## Step 4 — Feel the problem: CountDisplay doesn't know

**Think:** The scope problem was that `count` was locked inside `CountButton`. But what if we make a "global" variable that both components can access? Like, declare a variable outside of `App`? Let's try:

```tsx
let globalCount = 0;  // Global variable — both components can access

function CountDisplay() {
  return <p>Count: {globalCount}</p>;
}

function CountButton() {
  return <button onClick={() => { globalCount++; console.log(globalCount); }}>+1</button>;
}
```

**Test:** Click the button — `globalCount` changes in the console, but `CountDisplay` doesn't update! ❌

Why? Because **React doesn't know that `globalCount` changed.** React only re-renders when a `useState` setter is called. Changing a plain variable does nothing for React.

**Concept — React's data flow:**

React data flows **top → bottom** — from parent to child through props. There's no direct sharing mechanism between siblings.

```
React data flows only parent → child through props.
Siblings cannot directly communicate.

When two siblings need the same data:
  ❌ One child's state — the other can't access it
  ❌ Global variable — React doesn't track it
  ✅ Common parent holds state — both get it via props
```

See the problem — `CountButton`'s state can't reach `CountDisplay`. `globalCount` didn't work either because React doesn't track it.

**Current code — the problem is visible:**

```tsx
function CountDisplay() {
  return <p>Count: 0</p>;  // ❌ Hardcoded — not showing the real count
}

function CountButton() {
  const [count, setCount] = useState(0);  // Count lives here
  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}

function App() {
  return (
    <div>
      <CountDisplay />
      <CountButton />
    </div>
  );
}
```

**Test:** Click the button — `CountDisplay` still shows "Count: 0". ❌ This is broken state. The problem is clear: state is in one child, the other can't access it.

---

## Step 5 — Lift state to App (Step 1 of the pattern)

**Think:** The problem is clear — state is in `CountButton`, and `CountDisplay` can't access it. Solution: put the state in their **common parent** (`App`). Then both children can receive it via props.

**Concept — Lifting State Up:** Pulling state out of a child component and into a common parent is called "Lifting State Up." This is how siblings share data — through the parent.

**First step — pull state out of `CountButton` and into `App`:**

```tsx
import { useState } from "react";

function App() {
  const [count, setCount] = useState(0);  // State now lives in App

  return (
    <div>
      <CountDisplay />
      <CountButton />
    </div>
  );
}
```

`CountButton` is now stateless — it has no `count` or `setCount`. Its button text is just "+1" (no longer dynamic).

```tsx
function CountButton() {
  return <button>+1</button>;  // Stateless — just a button
}
```

**Test:** Clicking the button does nothing now — because `setCount` is in `App`, not `CountButton`. This is an intentionally incomplete state. ✅

---

## Step 6 — Data down: Pass `count` as a prop to CountDisplay

**Think:** State is now in `App`. `CountDisplay` needs to show the count — pass it as a prop. In React, data flows from parent to child through props.

**Concept — Props:** Props are React's mechanism for passing data from parent to child. Child components receive props like function arguments. When parent state changes, React re-renders the child with new props.

```tsx
function CountDisplay({ count }: { count: number }) {
  return <p>Count: {count}</p>;
}
```

`{ count }: { count: number }` — TypeScript type annotation. The first `{ count }` is destructuring (pulling `count` out of the props object). The second `{ count: number }` is the type — declaring that this prop is a `number`.

Now pass it from `App`:

```tsx
<CountDisplay count={count} />
```

**Test:** Browser shows "Count: 0". But this 0 is no longer hardcoded — it comes from App's state. `CountDisplay` is receiving the actual count now. ✅

---

## Step 7 — Actions up: Pass a callback prop to CountButton

**Think:** `CountDisplay` got its data (the `count` prop). Now `CountButton` needs a way to trigger state updates. `setCount` lives in `App` — so pass a function prop that calls `App`'s `setCount`. In React, child-to-parent actions work through callbacks.

I'll name it `onIncrement` first to distinguish it from HTML's `onClick` — we'll cover conventions later.

```tsx
function CountButton({ onIncrement }: { onIncrement: () => void }) {
  return <button onClick={onIncrement}>+1</button>;
}
```

Notice — `onIncrement` is a prop that `CountButton` receives. Then `<button onClick={onIncrement}>` assigns this prop as the button's `onClick` handler. The prop name and the event handler name are different — no confusion.

Using it in `App`:

```tsx
<CountButton onIncrement={() => setCount(count + 1)} />
```

`() => setCount(count + 1)` — an arrow function. When `CountButton` calls `onIncrement()`, App's `setCount` runs → state updates → re-render → `CountDisplay` gets the new count.

**Full working code:**

```tsx
import { useState } from "react";

function CountDisplay({ count }: { count: number }) {
  return <p>Count: {count}</p>;
}

function CountButton({ onIncrement }: { onIncrement: () => void }) {
  return <button onClick={onIncrement}>+1</button>;
}

function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <CountDisplay count={count} />
      <CountButton onIncrement={() => setCount(count + 1)} />
    </div>
  );
}
```

**Data flow visually:**

```
App (state: count, setCount)
  │
  ├── CountDisplay
  │     └── receives "count" as prop (data down)
  │
  └── CountButton
        └── receives "onIncrement" as prop (actions up)
            → click → App's setCount is called
            → App re-renders
            → CountDisplay receives new count
```

**Test:** Click the button — does `CountDisplay`'s count update? ✅ ✅ ✅

**Convention note:** In codebases, callback props are often named with the `onXxx` convention — like `onClick`, `onToggle`, `onDelete`. I kept it as `onIncrement` so it's clearly a custom prop. Following the convention, you could name it `onClick` too — the logic is the same, just a different name.

> **Nutshell:** Lifting State Up = pull state from a child into the common parent. Data flows down (via props), actions flow up (via callbacks) — siblings share data through the parent.

## Step 8 — Prop Drilling: When you need to lift in a deep tree

**Think:** So far it's only 2 levels deep (App → children). What if the tree is 4-5 levels deep? Say App has a Layout, Layout has a Sidebar, Sidebar has an Avatar — and Avatar needs the state.

**Concept — Prop Drilling:** When state needs to reach a child 3+ levels deep, every middle component has to receive and pass through that prop — even though they don't use it. This is called prop drilling.

```
App (count state lives here)
  └── Layout ← receives count prop (just pass-through)
      └── Sidebar ← receives count prop (just pass-through)
          └── Avatar ← finally uses count
```

```tsx
function Layout({ count }: { count: number }) {
  return <Sidebar count={count} />;  // Pass-through — count not used here
}

function Sidebar({ count }: { count: number }) {
  return <Avatar count={count} />;  // Pass-through — count not used here
}

function Avatar({ count }: { count: number }) {
  return <p>Count: {count}</p>;  // Finally used here
}
```

`Layout` and `Sidebar` don't need `count` — they're just passing it along. This makes the code verbose, and refactoring is hard — adding or removing a component in the middle means updating all the props.

**Solutions:**
- **Composition (`children`)** — send `Avatar` directly from parent, no prop needed for middle components
- **Context API** — we'll learn this in the next doc (2.6)

> **Nutshell:** Prop drilling = passing props through middle components in a deep tree when they don't need the data. Solutions: Composition (children) or Context API.

---

## What It Is NOT

- **Not global state** — the state lives in the parent, children access it via props. This is exactly the correct React pattern.
- **Not a replacement for `useRef`** — `useRef` doesn't trigger re-renders. In this pattern, we need `useState` because the UI must update.
- **Not everything in one file** — the same pattern works across files: state in parent, props passed to children.

---

## Common Mistakes

1. **Keeping state in one child when both need it** — always keep state in the common parent, never in just one child
2. **Defining callbacks inline in the child** — define `() => setCount(c+1)` in the parent, pass only the function reference to the child
3. **Ignoring prop drilling** — if you're going 4+ levels deep, consider Composition or Context API
4. **Using `useRef` for state sharing** — `useRef` doesn't trigger re-renders, the display component won't update

## In Your Own Words

1. What does "Lifting State Up" mean? When is it needed?

   <details>
   <summary>Sample Answer</summary>

   Pulling state out of a child component into a common parent. It's needed when two siblings need to share the same data — because in React, data flows top → down, and siblings can't talk directly.
   </details>

2. What are the three steps of Lifting State Up?

   <details>
   <summary>Sample Answer</summary>

   (1) Pull state out of the child into the parent. (2) Pass state down to children as props. (3) Pass a callback up to children so they can trigger state updates.
   </details>

3. What is prop drilling? When does it become a problem?

   <details>
   <summary>Sample Answer</summary>

   When state needs to reach a child 4+ levels deep, every middle component has to receive and pass through that prop — even though they don't use it. **Prop drilling** is this problem. Solutions: Composition (the `children` prop) or Context API.
   </details>

4. Why doesn't `useRef` work for Lifting State Up?

   <details>
   <summary>Sample Answer</summary>

   `useRef` doesn't trigger re-renders when its value changes. The display component won't know the count changed. For UI updates, you need `useState` — which triggers a re-render and displays the new count.
   </details>

5. What other name is this pattern known by?

   <details>
   <summary>Sample Answer</summary>

   "Data down, Actions up." State flows from parent to children via props (down). Children send actions back via callbacks (up).
   </details>

## Summary

| Concept | Explanation |
|---|---|
| Lifting State Up | Pull state from child → common parent |
| Data down | Parent → child via props |
| Actions up | Child → parent via callbacks |
| Prop drilling | Middle components in a deep tree receiving props they don't need |
| Solution | Composition (children) or Context API |
