## Cheat Sheet (Quick Recall)

```ts
useEffect(() => { /* side effect */ }, [deps]);  // runs after render
useEffect(() => { return () => { /* cleanup */ }; }, []);  // mount + unmount
```
- **Side effect** = code outside React's render cycle (timer, API, storage)
- **Dependency array** = controls when the effect should re-run
- **Cleanup** = runs before unmount/re-run — prevents memory leaks

## Where We Left Off

In Batch 1, we built the To-Do App — components, props, useState, everything was synchronous. React's job is: state changes → component re-renders → new JSX returned → DOM updates. This cycle is called the **render cycle**. As long as everything stays within this cycle, React handles it automatically.

But in real apps, we need to run timers, fetch data from APIs, save to localStorage — these all happen **outside** the render cycle. React calls these **side effects**. I was confused about where to put them too. This doc explains exactly that.

## Step 1 — Doing Work After Render

The component renders and the UI appears. But sometimes we need to do work **after** the render completes — change the browser tab title, fetch data from an API, start a timer. These are all **side effects**.

A developer's thinking:
> "Let me render first, show the UI — then do this work."

This concept is not new. Recall from vanilla JS — when we needed to access a DOM element, we'd wait for the `DOMContentLoaded` event? Because accessing an element before the DOM is ready throws an error. The same idea applies in React:

```
Vanilla JS:  DOMContentLoaded → DOM ready → then access elements
React:       Render complete → DOM ready → then useEffect runs
```

`useEffect` is React's equivalent of `DOMContentLoaded` — it runs after the component renders and the DOM is safe to access. Let's see it in action:

```tsx
'use client'
import { useEffect } from "react";

function PageTitle() {
  useEffect(() => {
    document.title = "Page Loaded! 🎉";
  }, []);

  return <p>Check your browser tab — title changed?</p>;
}
```

Look in the browser — the component rendered, UI appeared, then `useEffect` changed the title. First render, then effect. Keep this order in mind — it'll come up often.

**Nutshell:** `useEffect` is a hook that **runs after the component renders** — just like the `DOMContentLoaded` event in vanilla JS fires after the DOM is ready. It's the place for all post-render work (title changes, API calls, timers).

## Step 2 — But This Is a Side Effect (Feel the Problem)

Now let's understand **why** these operations shouldn't be written inside React's render cycle. To understand side effects, let's try running a timer that ticks every second. I'll put `setInterval` directly in the component body:

```tsx
function Timer() {
  let count = 0;
  setInterval(() => {
    count++;
    console.log(count);
  }, 1000);
  return <p>Check console</p>;
}
```

<detail>
<summary>⚡ What is setInterval / clearInterval? — Browser's built-in API</summary>

`setInterval` is not a React feature — it's a **browser API**. It's a direct part of the browser's JavaScript engine. The job: run a function every X milliseconds.

```js
setInterval(() => { console.log("Tick"); }, 1000);
// Prints "Tick" every 1 second — infinite, until stopped
```

**`setInterval` returns a unique numeric ID** — think of it as an "identity card" for that interval. When you want to stop it, you use that ID:

```js
const id = setInterval(() => { console.log("Tick"); }, 1000);
// id = some number, like 5

clearInterval(id);  // Stop it! No more "Tick" prints
```

**Think of it like a TV remote.** `setInterval` = pressing the button "show 'Tick' on screen every second." That ID is your remote code. `clearInterval(id)` = entering the same remote code to turn it OFF. If you never turn it OFF, the TV runs forever.

This concept will come up again in Step 5 — the cleanup function uses `clearInterval` to stop the timer on unmount.
</detail>

Look at the console — ticks are appearing. But there's a problem: **React has no idea anything is changing.** Nothing updates on screen.

Let me explain why React doesn't know. This is React's core design:

React's job is: whenever **state** changes, the component re-renders. But here I wrote `let count = 0` — that's a local variable, not React state. Yes, `count++` is incrementing, but React has no mechanism to "notice" that a local variable changed. How does it know? Because React has no way to detect that you're mutating local variables.

**Think of it this way:** React is the manager of a restaurant. The waiter (state setter) tells the manager "order arrived" and then the manager takes action. A local variable is like a customer who walks straight into the kitchen and starts cooking — the manager has no idea what's happening in the kitchen. The manager only takes action when the waiter tells him to.

React's render cycle is triggered **only** by state changes. You call the `useState` setter → React finds out → component re-renders. But `let count` has no setter, no "hey React, I changed" signal. So React stays unaware.

**Why this design?** React intentionally separates "what triggers a render" (state) from "what's used inside render" (local variables). If React re-rendered on every local JS variable change, performance would degrade. So React says: "If you want to signal a change, call the setter. Otherwise, I won't notice."

And there's another problem — what if the component is conditionally displayed or the page changes? The component disappears from the UI (this is called **unmount**). But `setInterval` keeps running in the background — because nobody told it to stop. Every second, it increments a new `count` and holds a reference to variables. React's garbage collector can't free that memory because the interval is still active. This is a **memory leak** — memory that should have been freed but stays occupied because the interval reference was never released. I made this mistake the first time too — the component left but the timer kept ticking, console kept printing, and I'm thinking "what's going on?"

Timers, API calls, localStorage — these are all outside the render cycle. React calls these **side effects**. The render cycle should be pure — same props + same state = same JSX. Timers and API calls break this purity because they interact with external systems.

You saw this in DukaanOS auto-save and TradeStack stock price polling — those were side effects too.

**Nutshell:** Side effects are operations that happen **outside** React's render cycle — timers, API calls, browser APIs. They need to be handled separately, after the render.

## Step 3 — useEffect Syntax + Render-First Verification

The problem is clear — side effects need to be handled after the render. React provides a hook for this: `useEffect`.

`useEffect` takes two arguments:

```ts
useEffect(() => {
  // side effect logic
}, [dependencies]);
```

- First argument: **setup function** — the side effect code
- Second argument: **dependency array** — controls when the effect should re-run

The setup function runs **after** every render — always. Like tea: the cup is prepared first (render), then the tea bag is added (useEffect). If the cup isn't ready, there's no point adding the tea bag.

Let's visually verify that it runs after render:

```tsx
import { useState, useEffect } from "react";

function TimerApp() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    console.log("🔧 useEffect ran — count is:", count);
  });

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </div>
  );
}
```

Look in the browser — every time you click the button, `useEffect` runs in the console. **Notice the order:** first the screen changes (render), then the console log (effect).

```
Initial render   → DOM update   → 🔧 useEffect ran — count is: 0
Button click     → DOM update   → 🔧 useEffect ran — count is: 1
Button click     → DOM update   → 🔧 useEffect ran — count is: 2
```

**Why every time?** No dependency array was provided — when there's no array, `useEffect` runs **after every render**.

**Nutshell:** `useEffect(fn, [deps])` is a React hook that calls `fn` **after the component renders**. The second argument (dependency array) controls when `fn` is called again.

## Step 4 — Dependency Array: Three Cases

Now let's understand the three cases of the dependency array. It confused me for a while too, but once you see it in the console, it becomes clear.

---

**Case 1 — Empty Array `[]`: Runs Only on Mount**

Sometimes you only want it to run once — when the component first appears on screen (this is called **mount**). Like fetching data from an API: the component appears, fetch once, not every time.

```tsx
useEffect(() => {
  console.log("🟢 Component mounted — once only");
}, []);  // empty dependency array
```

Click the button 10 times — only one log appears. Just on mount.

```
Initial render   → 🟢 Component mounted — once only
Button click     → (nothing)
Button click     → (nothing)
```

The empty array is unique because no value can change. React decides: "this effect will only run on mount, never again."

---

**Case 2 — With Value `[count]`: Only When Count Changes**

```tsx
useEffect(() => {
  console.log("🔄 Count changed:", count);
}, [count]);  // only re-runs when count changes
```

```
Initial render   → 🔄 Count changed: 0
Button click     → 🔄 Count changed: 1
Button click     → 🔄 Count changed: 2
```

The effect only runs when count changes — not on any other state change. Say you have an input that sets `text` — changing text doesn't trigger the effect. Only clicking the count button triggers it. The dependency array narrowed the effect to count.

---

**Case 3 — No Array: On Every Render (Rare, Avoid)**

```tsx
useEffect(() => {
  console.log("Runs on every render");
});  // no array = every time
```

This was the case in Step 3 — no dependency array was provided. Usually avoid this because of the risk of infinite loops (we'll see why later).

---

**Nutshell:** The dependency array `[dep1, dep2]` tells `useEffect`: "re-run this effect only when these values change." Empty array `[]` = only on mount. No array = every render (avoid).

---

## Step 5 — Cleanup Function: Cleaning Up the Mess

And one thing I forgot the first time — cleanup. Think about it: in Step 2, I started a `setInterval`. Now the component leaves the UI (unmount) — maybe you changed the page or hit a Hide button. But `setInterval` is still running in the background. Why? Because nobody told it to stop. React doesn't automatically stop timers — it only manages JSX.

Every second, the interval function runs, holds references to variables, consumes resources. And since the interval never ends, React's garbage collector can't free that memory. This is called a **memory leak** — memory that should have been freed but stays occupied because the interval reference was never released. A few of these running and the browser slows down, hangs in seconds.

The setup function in `useEffect` can return a cleanup function. React calls this cleanup:
- On unmount
- Before re-running the effect (cleans up the old effect before starting the new one)

```tsx
useEffect(() => {
  console.log("⏱️ Timer setup");
  const id = setInterval(() => {
    console.log("⏰ Tick");
  }, 1000);

  return () => {
    console.log("🧹 Cleanup — removing timer");
    clearInterval(id);
  };
}, []);
```

<detail>
<summary>⚡ What does clearInterval(id) do?</summary>

In Step 2, we saw that `setInterval` returns a unique numeric ID. That ID is the interval's "remote code."

```js
const id = setInterval(() => { ... }, 1000);
// id = some number, like 7

clearInterval(id);  // Press OFF — stop it
```

Passing that ID to `clearInterval` means "stop the interval with this ID." Without `clearInterval`, the interval runs forever — whether the component is on screen or not. This is called a **memory leak**.

React's garbage collector cannot automatically stop `setInterval` — the browser's JS engine doesn't know you no longer need that interval. You have to call `clearInterval` yourself. That's exactly what the cleanup function is for.
</detail>

First, an empty array `[]` — the `setInterval` only runs on mount. The cleanup runs on unmount.

Try it in the browser:
1. Component mounts → "⏱️ Timer setup" + "⏰ Tick" every second
2. Component unmounts (toggle it off via conditional rendering) → "🧹 Cleanup — removing timer"
3. The timer is no longer running in the background

**Visibility Toggle — visually verify that cleanup runs**

Now that cleanup makes sense. But how do we visually see that cleanup runs on unmount? Use conditional rendering to hide/show the component — when the component leaves the UI, cleanup should fire.

**Step 6 — Add seconds state to Timer component:**

Now Timer should show real seconds counting up, not just static "0s". For this, we need state — `useState` to track `seconds`. Why? Because the value changes every second and React needs to re-render.

```tsx

```

Right now `seconds` stays at 0 — nothing increments it yet. Screen shows "Timer: 0s". ✅

**Step 7 — Try without useEffect — feel the problem:**

Now we need `seconds` to increment every second. Let's first try putting `setInterval` directly in the component body, without `useEffect`:

```tsx
function Timer() {
  const [seconds, setSeconds] = useState(0);
  setInterval(() => {
    setSeconds(seconds + 1);
  }, 1000);
  return <p>Timer: {seconds}s</p>;
}
```

Look in the browser — seconds are incrementing? Yes, 1, 2, 3... seems to work. ✅ But wait — this is a trap.

**What's the problem?** Every time the component renders, a **new** `setInterval` is created. The old interval is never cleared. So:

```
Render 1 → interval #1 created  (seconds = 0)
Render 2 → interval #2 created  (seconds = 0, but #1 still running)
Render 3 → interval #3 created  (seconds = 0, #1, #2, #3 all running)
...
Render 30 → 30 intervals running simultaneously
```

Throw in a `console.log("interval created")` and see — it prints every render. Seconds also jump fast because multiple intervals are all calling `setSeconds(0 + 1)` — they all see 0, so it stays at 1, but CPU is being wasted.

And hit "Hide Timer" — the component unmounted. But all 30 intervals are still running in the background — memory leak. The browser will slow down.

**This is the same problem from Step 2** — side effects shouldn't be written inside the render cycle. They need to be handled separately, after the render.

**Step 8 — Add useEffect — separate side effect from render cycle:**

First, let me clear up a common confusion — **mount** vs **render**:

- **Render** = the component function runs. Every time state or props change, the component function re-runs. When this happens, we call it a re-render.
- **Mount** = the component **first appears** on screen. Mount involves a render (the first one), but not every render is a mount.

```
Mount → Render happens (first time)
State change → Render happens (re-render) → NOT a mount
```

**Recall Step 7's code** — `setInterval` was written directly inside the component body. So every render would execute that line. It ran on mount, then state changed → re-render → it ran again, then state changed again → re-render → ran again... Each render created a new interval.

`useEffect` solves this. `useEffect(fn, [])` means: run `fn` **only on mount** (after first render), and don't re-run when state changes. `[]` tells React "nothing to track, just run once."

```tsx
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds((prev) => prev + 1);
    }, 1000);
  }, []);
  // [] → React: "just run once, no conditions"

  return <p>Timer: {seconds}s</p>;
}
```

**Compare in the console:**

| Scenario | Without useEffect (Step 7) | useEffect + `[]` (Step 8) |
|---|---|---|
| On mount | "interval created" ✅ | "interval created" ✅ |
| State change → re-render | "interval created" again ❌ — another interval | No output ✅ — only one interval |
| After 10 re-renders | 11 intervals running | Just 1 interval ✅ |
| On unmount | All 11 still in background | Cleanup stops them ✅ |

Throw in a `console.log("interval created")` and see — Step 7 it printed every time, Step 8 only once.

But look at the timer in the browser — **did it get stuck on 1?** It went 1, 2, 3... no, it's only incrementing by 1 each second. Actually wait — it might go 0, 2, 4, 6. That's not a bug — that's **React StrictMode**.

**What is StrictMode?** When you created your project with Vite (Batch 1, *1.0 React Project Structure.md*), `main.tsx` has a `<StrictMode>` wrapper. In development, StrictMode mounts the component **twice**: **mount → unmount → remount**. This is to catch side-effect bugs early.

Let's see what's happening:

```
First mount → setInterval created (id = 1)
StrictMode unmounts → ❌ but clearInterval was never called (no cleanup written)
StrictMode remounts → second setInterval created (id = 2)
Now BOTH intervals are running → both call setSeconds(prev => prev + 1)
Result → counter increments 2x → 0, 2, 4, 6...
```

`useEffect(() => {...}, [])` only runs on mount — but without cleanup, the first interval stays alive. When StrictMode unmounts and remounts the component, the old interval keeps ticking in the background. A new interval is created on remount — now two intervals run in parallel. That's why the counter increments at double speed.

**The good news:** StrictMode revealed the bug — cleanup wasn't written. That's its job — surface bugs. In production, StrictMode does nothing extra.

The solution is the **cleanup function** — which `useEffect` can always return. React calls cleanup on unmount, and before re-running the effect. So if we put `clearInterval(id)` in the cleanup, the first interval gets stopped before remount, and only one interval runs.

Let's implement in Step 9.

**So useEffect's real job:** separate side effects from the render cycle. Run only on mount (via dependency array). And cleanup provides a way to clean up — which we'll see in full detail in Step 9.

**Step 9 — Add Cleanup — Stop Timer on Unmount:**

Back to the problem from Step 8 — StrictMode caused 0, 2, 4, 6 because cleanup wasn't written. And another issue: "Hide Timer" — the component unmounts. But `setInterval` is still running in the background. Memory leak. **Both problems have one solution: the cleanup function.** Let's return a cleanup function from `useEffect`:

```tsx
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds((prev) => prev + 1);
    }, 1000);

    return () => clearInterval(id);
  }, []);
}
```

`return () => clearInterval(id)` — when the component unmounts, this runs and stops the interval.

**Observe in the browser:**
1. Click "Show Timer" → Timer mounts → setInterval starts → seconds increment
2. Click "Hide Timer" → Timer unmounts → `clearInterval(id)` runs → interval stops → no more incrementing
3. Click "Show Timer" again → new mount → new setInterval starts → timer starts at 0
4. **Even with StrictMode active**, only one interval runs — because the cleanup stopped the old one before remount. The counter now increments correctly: 1, 2, 3... ✅

Notice: when the component unmounted, `clearInterval(id)` ran — timer stopped. When it mounted again, a new interval started. No more memory leak.

> **What It Is NOT:** Cleanup function doesn't only run on unmount — it also runs before re-run. When dependencies change, the old effect's cleanup runs first, then the new one starts. Think of it as `useEffect`'s "reset" mechanism.

**Nutshell:** The cleanup function is a regular function returned by the setup function in `useEffect`. React calls it when the component unmounts and before the effect re-runs — to clean up resources (timers, subscriptions, listeners).

## Step 6 — Mini-Project: Countdown Timer (With All Concepts)

Let's put all concepts together — dependency array, timers, cleanup. Let's build a countdown timer.

**What we need:**
- User sets initial time (in seconds)
- Click Start → countdown begins
- Pause/Resume works
- When time runs out → show alert
- Cleanup handled

### UI + State Setup

```tsx
function CountdownApp() {
  const [timeLeft, setTimeLeft] = useState(0);
  const [isRunning, setIsRunning] = useState(false);
  const [initial, setInitial] = useState(10);

  return (
    <div style={{ padding: "20px" }}>
      <h1>⏱️ Countdown: {timeLeft}s</h1>
      <div>
        <input
          type="number"
          value={initial}
          onChange={(e) => setInitial(Number(e.target.value))}
        />
        <button onClick={() => { setTimeLeft(initial); setIsRunning(false); }}>
          Set
        </button>
      </div>
      <div style={{ marginTop: "10px" }}>
        <button onClick={() => setIsRunning(true)} disabled={isRunning || timeLeft <= 0}>
          Start
        </button>
        <button onClick={() => setIsRunning(false)} disabled={!isRunning}>
          Pause
        </button>
        <button onClick={() => { setTimeLeft(0); setIsRunning(false); }}>
          Reset
        </button>
      </div>
    </div>
  );
}
```

### useEffect with Timer + Cleanup

We need a timer that decrements `timeLeft` every second — but only when `isRunning` is true.

```tsx
useEffect(() => {
  if (!isRunning) return;

  const id = setInterval(() => {
    setTimeLeft((prev) => {
      if (prev <= 1) {
        setIsRunning(false);
        return 0;
      }
      return prev - 1;
    });
  }, 1000);

  return () => clearInterval(id);
}, [isRunning]);
```

`isRunning` is in the dependencies because it's used inside — if the effect doesn't re-run, it'll use the stale value. But `timeLeft` isn't in dependencies because we're using functional update `setTimeLeft(prev => ...)` — the stale closure problem is prevented.

### Handle Time Up

```tsx
useEffect(() => {
  if (timeLeft === 0 && isRunning) {
    setIsRunning(false);
    alert("Time's up! 🛎️");
  }
}, [timeLeft, isRunning]);
```

    <div style={{ padding: "20px" }}>
      <h1>⏱️ Countdown: {timeLeft}s</h1>
      <div>
        <input
          type="number"
          value={initial}

        />

          Set
        </button>
      </div>
      <div style={{ marginTop: "10px" }}>

## Step 7 — useEffect Recap: When to Use Which Pattern

| Dependency Array | When It Runs | Use Case |
|---|---|---|
| `[]` (empty) | Only on mount | Initial API fetch, third-party setup |
| `[dep1, dep2]` | Mount + when dep changes | Sync with state/props |
| No array | Every render (rare) | Debug/logging (avoid in production) |

### What It Is NOT

- `useEffect` is **not the solution for data fetching** — it's just a tool. TanStack Query/SWR are better (we'll see in the next doc).
- `useEffect` is **not synchronous** — it runs after render. That means the JSX goes to the DOM first (user sees it), then the effect runs. So the user won't see any "flash" (like a loading spinner then content) — because by the time the effect runs, the DOM is already ready.
- Don't think of the dependency array as an "optimization" — it's **behavior definition**. If you use a reactive value inside, it should be in the array, whether it affects performance or not.

---

## Common Mistakes

1. **Forgetting the dependency array** — `useEffect(() => { ... })` without an array runs after every render, causing infinite loops.
2. **Forgetting cleanup** — if you start `setInterval` / `addEventListener` without cleaning up, you get memory leaks. Always `return () => clearInterval(id)`.
3. **Making useEffect async** — `useEffect(async () => { ... })` is wrong. Why? `useEffect`'s first argument is a function that expects to return either nothing (void) or a cleanup function. An `async` function always returns a Promise — not a cleanup function. React will treat the Promise as cleanup and it won't work. Solution: define an async function inside and call it:
   ```tsx
   useEffect(() => {
     async function fetchData() {
       const data = await api.get(...);
     }
     fetchData();
   }, []);
   ```
4. **Stale closure** — if `count` is used inside but you pass `[]`, the effect only runs on mount. The value of `count` at mount time (0) gets captured in the closure. Even after `count` changes, the effect won't re-run (because `[]`), so the inner `count` always stays 0. Rule: **any reactive value used inside should be in the dependency array.**

## Try It Yourself

1. Without scrolling, answer: `useEffect(() => {}, [count])` — when does it run? How many times on initial render?
   
   <details>
   <summary>Sample Answer</summary>
   Runs on mount, then every time `count` changes. Runs once on initial render.
   </details>

2. Write code — a component that prints "Tick" to the console every 2 seconds, with cleanup (timer stopped on unmount).
   
   <details>
   <summary>Sample Answer</summary>
   
   ```tsx
   useEffect(() => {
     const id = setInterval(() => console.log("Tick"), 2000);
     return () => clearInterval(id);
   }, []);
   ```
   </details>

3. Predict — `useEffect(() => { setCount(count + 1) }, [])` — will this cause an infinite loop? Why?
   
   <details>
   <summary>Sample Answer</summary>
   No. It only runs on mount because of `[]`. `setCount` will run on mount, count becomes 1, but the effect won't re-run because deps haven't changed.
   </details>

## Summary

| Concept | Understanding |
|---|---|
| Side Effect | Code outside the render cycle — timer, API, browser API |
| `useEffect(fn, [deps])` | Calls `fn` after render; re-runs when deps change |
| Cleanup Function | Return from `fn` — runs on unmount and before re-run |
| Empty `[]` | Effect runs only on mount |
| `[dep]` | Mount + when dep changes |
| No array | Every render (rare) |
