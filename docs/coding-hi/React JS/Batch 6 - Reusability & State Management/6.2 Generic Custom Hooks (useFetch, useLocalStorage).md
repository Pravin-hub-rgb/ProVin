## Generics — Understand This First

TypeScript generics do not click in a day, but the basic concept is simple.

**Problem:** A function that takes any type of array and returns its first element:

```ts
function first(arr: number[]): number {
  return arr[0];
}

const num = first([1, 2, 3]); // number — correct
// const str = first(["a", "b"]); // ❌ Type error — string[] is not number[]
```

A second function must be written for strings:

```ts
function firstString(arr: string[]): string {
  return arr[0];
}
```

And a new function for every new type. That is duplication.

**Solution — Generics:**

```ts
function first<T>(arr: T[]): T {
  return arr[0];
}

const num = first<number>([1, 2, 3]); // number
const str = first<string>(["a", "b"]); // string
const bool = first<boolean>([true, false]); // boolean
```

`<T>` is a **type parameter**. Just as a function parameter takes a value, a generic type parameter **takes a type**. The caller decides which type `T` is — number, string, boolean, or any custom interface.

TypeScript can also infer it:

```ts
const str = first(["a", "b"]); // TypeScript will automatically infer T = string
```

Visual mapping:

```
first<T>(arr: T[]): T
   │       │       │
   │       │       └── Return type same as T
   │       │
   │       └── Array of T
   │
   └── Type parameter — caller decides

Call: first<number>([1, 2, 3])
              │
              ▼
     first<number>(arr: number[]): number
```

Now we will apply this concept to custom hooks — hooks that work with any data type, with TypeScript types automatically inferred.

## useFetch<T> — Generic Data Fetching Hook

Remember in Batch 2 the Recipe Finder — `useEffect` + `useState` triplets (data, loading, error) + try/catch/finally? That pattern repeats in every API call. Let's create a generic hook that fetches **any type** of data — and automatically handles loading/error states.

### Step 1 — Define the State Type

First, think about how many states a fetch operation has:

1. **Idle** — fetch has not started yet
2. **Loading** — fetch is in progress
3. **Success** — data has arrived
4. **Error** — something went wrong

Create a type — create a new file in `src/hooks/` called `useFetch.ts`:

```ts
// src/hooks/useFetch.ts
type FetchState<T> = {
  data: T | null;
  isLoading: boolean;
  error: string | null;
};
```

`FetchState<T>` is generic. `T` can be any type — `Meal[]`, `string[]`, `Task[]`, anything.

### Step 2 — Hook Skeleton

Add the hook in the same file (`src/hooks/useFetch.ts`):

```ts
// src/hooks/useFetch.ts
import { useState, useEffect } from "react";

function useFetch<T>(url: string): FetchState<T> {
  const [data, setData] = useState<T | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    // fetch logic here
  }, [url]);

  return { data, isLoading, error };
}
```

**What is happening:**

| Line | What It Is |
|------|---------|
| `useFetch<T>` | Generic hook — the caller decides which type T is |
| `url: string` | The URL to fetch from |
| `FetchState<T>` | Return type — uses the same T type |
| `useState<T \| null>` | Data type will automatically be T |
| `useState<string \| null>` | Error is always a string type |

### Step 3 — Fetch Logic + Cleanup

Continue in the same file (`src/hooks/useFetch.ts`) — add the fetch logic to the Step 2 skeleton:

```ts
// src/hooks/useFetch.ts
import { useState, useEffect } from "react";

function useFetch<T>(url: string): FetchState<T> {
  const [data, setData] = useState<T | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    let ignore = false;

    async function fetchData() {
      setIsLoading(true);
      setError(null);

      try {
        const res = await fetch(url);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const json = await res.json();
        if (!ignore) {
          setData(json as T);
        }
      } catch (err) {
        if (!ignore) {
          setError(err instanceof Error ? err.message : "Something went wrong");
        }
      } finally {
        if (!ignore) {
          setIsLoading(false);
        }
      }
    }

    fetchData();

    return () => {
      ignore = true;
    };
  }, [url]);

  return { data, isLoading, error };
}
```

**Important parts:**

| Thing | Why |
|-------|------|
| `let ignore = false` | Prevents race conditions — rejects the response of old URLs |
| `res.ok` check | Handles HTTP errors (404, 500) |
| `json as T` | TypeScript assertion — we know the JSON is type T |
| `return () => { ignore = true }` | Cleanup — when component unmounts or URL changes |

**Flow — When useFetch Is Called:**

```
Component renders with url="https://api.example.com/meals"
    │
    ▼
useEffect triggers
    │
    ├── ignore = false
    ├── setIsLoading(true)      → isLoading = true
    ├── setError(null)           → error = null
    │
    ├── fetch(url) starts
    │       │
    │       ├── Success → json as T → setData(json) → data = json
    │       └── Error → setError("message")         → error = "message"
    │
    └── finally → setIsLoading(false)               → isLoading = false
    │
    ▼
Component re-renders with { data, isLoading, error }
```

### Step 4 — Using useFetch

Now use this hook in a component. Create a new component — `src/components/RecipeList.tsx` — and import `useFetch` from `../hooks/useFetch`:

```tsx
// src/components/RecipeList.tsx
import { useState } from "react";
import { useFetch } from "../hooks/useFetch";

interface Meal {
  idMeal: string;
  strMeal: string;
  strMealThumb: string;
  strCategory: string;
}

function RecipeList() {
  const [query, setQuery] = useState("chicken");
  const { data: meals, isLoading, error } = useFetch<Meal[]>(
    `https://www.themealdb.com/api/json/v1/1/search.php?s=${query}`
  );

  if (isLoading) return <Spinner />;
  if (error) return <p className="text-red-500">{error}</p>;

  return (
    <div>
      {meals?.length === 0 ? (
        <p>No recipes found</p>
      ) : (
        meals?.map(meal => <RecipeCard key={meal.idMeal} meal={meal} />)
      )}
    </div>
  );
}
```

Notice? No `useEffect`, no `try/catch`, no `useState` triplets. Just one line — `useFetch<Meal[]>(url)` — and the entire fetch logic is handled. Clean, readable, reusable.

**TypeScript magic:** `meals` is automatically typed as `Meal[] | null`. `isLoading` is `boolean`. Everything is type-safe. No manual type annotations needed.

## useLocalStorage<T> — Generic LocalStorage Hook

The same pattern for localStorage. In the Batch 2 To-Do app, we saw — `useState` + `JSON.parse` + `useEffect` + `JSON.stringify`. Repeated in every component.

### Step 1 — Basic Version

Create a new file — `src/hooks/useLocalStorage.ts`:

```ts
// src/hooks/useLocalStorage.ts
import { useState, useEffect } from "react";

function useLocalStorage<T>(key: string, initialValue: T) {
  const [storedValue, setStoredValue] = useState<T>(() => {
    try {
      const item = localStorage.getItem(key);
      return item ? (JSON.parse(item) as T) : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      localStorage.setItem(key, JSON.stringify(storedValue));
    } catch (err) {
      console.error("Could not set localStorage:", err);
    }
  }, [key, storedValue]);

  return [storedValue, setStoredValue] as const;
}
```

**What is happening:**

| Line | What It Is |
|------|---------|
| `useLocalStorage<T>(key, initialValue)` | Generic — T can be any type |
| `useState<T>(() => { ... })` | Lazy initializer — only runs once |
| `localStorage.getItem(key)` | Read saved value |
| `JSON.parse(item) as T` | Parse string and cast to type T |
| `try/catch` | If localStorage is corrupt, return initialValue |
| `useEffect(() => { localStorage.setItem(key, JSON.stringify(storedValue)) }, [key, storedValue])` | Whenever storedValue changes, update localStorage |
| `return [storedValue, setStoredValue] as const` | Same interface as `useState` — familiar pattern |

**Without custom hooks:**

```tsx
const [tasks, setTasks] = useState<Task[]>(() => {
  const saved = localStorage.getItem("tasks");
  return saved ? JSON.parse(saved) : [];
});

useEffect(() => {
  localStorage.setItem("tasks", JSON.stringify(tasks));
}, [tasks]);
```

This code repeats for every localStorage feature. `useLocalStorage<T>` reduces it to one line.

### Step 2 — Use in To-Do App

Create a new component — `src/components/TodoApp.tsx` — and import `useLocalStorage` from `../hooks/useLocalStorage`:

```tsx
// src/components/TodoApp.tsx
import { useLocalStorage } from "../hooks/useLocalStorage";

function TodoApp() {
  const [tasks, setTasks] = useLocalStorage<Task[]>("tasks", []);

  function addTask(text: string) {
    const newTask: Task = {
      id: Date.now(),
      text,
      completed: false,
    };
    setTasks([...tasks, newTask]);
    // localStorage automatically updates — no useEffect needed!
  }

  return (
    <div>
      <TaskInput onAdd={addTask} />
      <TaskList tasks={tasks} onToggle={...} onDelete={...} />
    </div>
  );
}
```

Notice? No `localStorage.getItem`, no `JSON.parse`, no `useEffect` sync. The hook handles everything. The component just works with its state, just like a normal `useState`.

### Flow — useLocalStorage Lifecycle:

```
Component renders
    │
    ├── First render: localStorage.getItem("tasks") → null
    │   └── useState lazy init → returns initialValue []
    │
    ├── Second render (state change): storedValue updates
    │   └── useEffect → localStorage.setItem("tasks", JSON.stringify(newValue))
    │
    ├── Page refresh: localStorage.getItem("tasks") → "[...]"
    │   └── useState lazy init → JSON.parse → returns parsed value
    │
    └── LocalStorage is corrupt:
        └── try/catch → returns initialValue
```

### useLocalStorage vs useState

| Feature | `useState` | `useLocalStorage` |
|---------|-----------|-------------------|
| Persistence | Until re-render | Survives browser tab close |
| Syntax | `const [v, setV] = useState(initial)` | `const [v, setV] = useLocalStorage(key, initial)` |
| Type-safe | Yes | Yes (generic) |
| JSON parse/sync | Manual | Automatic |
| Error handling | N/A | try/catch built-in |

## Combining Generics — useFetch + useLocalStorage Together

Now both hooks can be used in any component. TypeScript will automatically infer types. Example — a component that fetches data and caches it in localStorage. Create a new component — `src/components/Dashboard.tsx` — importing both hooks:

```tsx
// src/components/Dashboard.tsx
import { useFetch } from "../hooks/useFetch";
import { useLocalStorage } from "../hooks/useLocalStorage";

function Dashboard() {
  const { data, isLoading } = useFetch<DashboardData>("/api/dashboard");
  const [preferences, setPreferences] = useLocalStorage<Preferences>("dashboard-prefs", {
    theme: "dark",
    widgets: ["stats", "chart"],
  });

  if (isLoading) return <Spinner />;

  return (
    <div className={preferences.theme}>
      <WidgetSelector
        selected={preferences.widgets}
        onChange={setPreferences}
      />
      {/* Dashboard content */}
    </div>
  );
}
```

Both hooks used together — one fetches data from a URL (generic type `DashboardData`), the other stores user preferences in localStorage (generic type `Preferences`). No manual type annotations — TypeScript infers everything automatically.

## Common Patterns in Generic Hooks

### 1. Return Type Always Includes Loading/Error States

A fetch hook's return type always includes the three states:

```ts
type FetchState<T> = {
  data: T | null;
  isLoading: boolean;
  error: string | null;
};
```

This is called the "tri-state" pattern. Every fetch operation has these three states. The hook handles them consistently.

### 2. useReducer Version for Complex State

For more control, you can use `useReducer` inside:

```ts
type Action<T> =
  | { type: "loading" }
  | { type: "success"; payload: T }
  | { type: "error"; payload: string };

function fetchReducer<T>(state: FetchState<T>, action: Action<T>): FetchState<T> {
  switch (action.type) {
    case "loading": return { ...state, isLoading: true, error: null };
    case "success": return { data: action.payload, isLoading: false, error: null };
    case "error": return { ...state, isLoading: false, error: action.payload };
  }
}
```

This pattern was covered in 5.5 (useReducer) — discriminated union actions + reducer. Useful for more complex hooks.

### 3. AbortController for Advanced Cleanup

The `ignore` flag is sufficient for simple cases. For advanced cleanup, use `AbortController`:

```ts
useEffect(() => {
  const controller = new AbortController();

  async function fetchData() {
    try {
      const res = await fetch(url, { signal: controller.signal });
      // ...
    } catch (err) {
      if (err instanceof DOMException && err.name === "AbortError") return;
      // handle error
    }
  }

  fetchData();
  return () => controller.abort();
}, [url]);
```

`AbortController` actually cancels the fetch request at the network level, while the `ignore` flag only ignores the response. For performance, `AbortController` is better.

## What useFetch Is NOT

- **Not a caching solution:** It will fetch on every component mount / URL change. For caching, use TanStack Query (covered in Batch 2.3).
- **Not a retry solution:** It does not retry on error. TanStack Query has built-in retries.
- **Not a mutation solution:** It is not for POST/PUT/DELETE. Mutations need a different approach.

`useFetch` is simple — fetch data, handle loading/error. For complex features, use dedicated libraries.

## In Your Own Words

1. What is the benefit of TypeScript generics in custom hooks? How is the hook limited without generics?

<details>
<summary>Show Answer</summary>

**Sample Answer:** Without generics, a custom hook only works with one specific type. Like `useFetch` would only work for `Meal[]`, and you need a separate hook for `string[]`. Generics let the caller decide which type to use — `useFetch<Meal[]>` or `useFetch<Task[]>` or `useFetch<string>`. TypeScript's automatic type inference means the caller doesn't even need to specify types — just call the hook and types set themselves.

</details>

2. Why is the `ignore` flag used in `useFetch`? What problem could arise without it?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The `ignore` flag prevents race conditions. Imagine a user typing fast in a search bar. Each keystroke generates a new URL and starts a new fetch. If an older fetch's response arrives after a newer one, it would set the wrong data (the result of the older query would render later). The `ignore` flag ensures that when a new URL comes in (effect re-runs), the old effect's response is ignored. Without `ignore`, fast typing could show flickering and stale data.

</details>

3. Why is the `useState` lazy initializer used in `useLocalStorage`? Why not just write `useState(localStorage.getItem(key))`?

<details>
<summary>Show Answer</summary>

**Sample Answer:** The lazy initializer (`() => { ... }`) only runs once — on the first render. This makes `localStorage.getItem()` efficient because the local storage is read only once. If you wrote `useState(localStorage.getItem(key))` directly, `localStorage.getItem()` would be called on every render (even though React might ignore the value), which is wasteful. The lazy initializer ensures that the expensive operation (reading local storage) only happens when needed — on first render.

</details>

4. Why should `useFetch` not be used for mutations (POST/PUT/DELETE)?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `useFetch` fetches inside an effect, which triggers on component mount or URL change. Mutations (POST/PUT/DELETE) happen in response to user interactions — button clicks, form submissions. A mutation hook needs to return a `mutate` function that the caller invokes manually. `useFetch` is designed for simple GET requests that trigger automatically. For mutations, use something like TanStack Query's `useMutation` which provides a `mutate` function.

</details>

5. What is the difference between `useLocalStorage<T>` and `useState<T>`? When should each be used?

<details>
<summary>Show Answer</summary>

**Sample Answer:** `useState` keeps state only during the component's lifecycle — it resets on page refresh. `useLocalStorage` persists state to localStorage — it survives browser tab close/refresh. Use `useLocalStorage` when data needs to persist — user preferences, saved items, draft data. Use `useState` when data is only for the current session — form inputs, temporary UI state, toggle states. The syntax is nearly identical (easy to swap), but localStorage has IO cost, so for very frequent updates use `useState` and only sync to `useLocalStorage` when meaningful data is ready.

</details>
