## Step 1 — Problem: An Inaccessible Form

Here's a typical form without ARIA — what happens when a screen reader encounters it?

```tsx
<form>
  <input placeholder="Name" />
  <input placeholder="Email" />
  <button>Send Message</button>
</form>
```

A screen reader user hears:
- "Edit text" (for Name) — but is it required? What if it's invalid?
- "Edit text" (for Email) — same issue.
- No labels — the placeholder disappears once you start typing.

**Every one of these problems has an ARIA solution.** Let's fix them one at a time.

## Step 3 — Validation: Check on Submit

Now add validation. On submit, check the fields — if something's wrong, set the errors state.

### 3.1 Concept — "Where does the data go?"

An HTML form's default behavior: on submit, the page refreshes and data goes to a URL or server. In a React app, we don't want a page refresh. We want to capture the form data in React state, process it, and update the UI — all without reloading.

So the first thing: attach an **onSubmit handler** to the form that intercepts the event.

### 3.2 Syntax — "Add onSubmit to the Form"

```tsx
<form onSubmit={handleSubmit}>
```

`handleSubmit` doesn't exist yet — we're creating it next.

### 3.3 Create the Handler — Capture the Event

Start simple — just log the values. No type yet — get the flow first:

```tsx
function handleSubmit(event) {
  console.log("submitting — name:", name, "email:", email)
}
```

Don't forget to wire it up:

```tsx
<form onSubmit={handleSubmit}>
```

### 3.4 Test — Observe the Problem

**TEST:** Fill the fields and submit.

Console shows "submitting — name: Pravin email: pravin@test.com" ✅.

But notice the **page refreshed** — there's a flash. And the console output disappears after the refresh. That's because the browser's default form behavior is to reload the page.

That's the problem — **a form submission triggers a page refresh by default.** In a React app, we don't want that.

### 3.5 Fix — `preventDefault()`

Fix it with `preventDefault()`:

```tsx
function handleSubmit(event) {
  event.preventDefault()
  console.log("submitting — name:", name, "email:", email)
}
```

**Cause and effect:**
- `event.preventDefault()` → browser skips the page refresh
- React app stays intact — console output stays visible
- You can process data — run validation, call an API, update state

### 3.6 TypeScript Type — `SyntheticEvent`

Now that we're in TypeScript land, the event needs a type. React doesn't pass the browser's native event — it wraps it in **SyntheticEvent**:

```
Browser fires:    Native submit event
                    ↓
React intercepts:   Wraps in SyntheticEvent
                    ↓
Your handler gets:  SyntheticEvent
```

`SyntheticEvent` is the base class — React's specific event subtypes branch from it:

```
React.SyntheticEvent          ← Base — wrapper around the native event
  ├── React.FormEvent         ← Form events (submit) [deprecated in latest types]
  ├── React.ChangeEvent       ← Input changes (onChange) [deprecated]
  ├── React.KeyboardEvent     ← Key presses (onKeyDown) [deprecated]
  └── React.MouseEvent        ← Clicks (onClick) [deprecated]
```

In the latest `@types/react`, those specific subtypes are deprecated. You just use `SyntheticEvent` with a generic parameter:

```tsx
const handleSubmit = (e: React.SyntheticEvent<HTMLFormElement>) => {
  e.preventDefault()
  console.log("submitting — name:", name, "email:", email)
}
```

`<HTMLFormElement>` tells React what element fired the event. With that, `e.currentTarget` is automatically typed correctly.

Test again — no page refresh, console output stays visible ✅

### 3.7 — Validation: Error State + `validate()` + `handleSubmit`

Now let's add validation. The pattern:

- Before: no errors (all fields valid)
- User submits: errors appear (some fields invalid)
- User fixes: errors disappear (all valid again)

**React rule:** Any UI that can change is **state**. Errors can appear and disappear — so they need state.

Store errors as an object where each field is optional — if the property doesn't exist, there's no error; if it has a string value, that's the error message:

```tsx
const [errors, setErrors] = useState<{ name?: string; email?: string }>({})
```

Now — **where do you put the validation logic?** You could inline it in `handleSubmit`:

```tsx
// ❌ Don't mix concerns all in one place
const handleSubmit = (e) => {
  e.preventDefault()
  if (!name.trim()) setErrors({ name: "Name is required" })
  else setErrors({})
  // and the submit logic too...
}
```

But that mixes two concerns:
1. **Checking** — what's wrong?
2. **Acting** — should we submit or not?

When mixed together:
- Add a new field or rule → you have to dig through `handleSubmit` (it's already 200 lines)
- Reuse in an edit form → copy-paste the whole thing
- Testing is hard — the function does three things at once

**Better approach — extract a `validate()` function.** Single responsibility: "tell me what's wrong." It's a **pure function** — same input always gives same output, no side effects. It shouldn't call `setErrors` — just return the errors object. This gives you:

- Easy to test — pass inputs, check outputs
- Easy to extend — one line per rule
- Reusable — use in edit forms too
- Clean separation — `validate()` checks, `handleSubmit()` decides

```tsx
const validate = (name: string, email: string) => {
  const newErrors: { name?: string; email?: string } = {}
  if (!name.trim()) newErrors.name = "Name is required"
  if (!email.trim()) newErrors.email = "Email is required"
  else if (!email.includes("@")) newErrors.email = "Enter a valid email"
  return newErrors
}
```

Note — `validate` takes parameters, doesn't read state directly. If it read `name` and `email` from closure, it wouldn't be a pure function — the output would depend on external state. Parameters guarantee: same input = same output.

Verify with console.log first:

```tsx
console.log("validation result:", validate("", ""))
```

**TEST — Case 1:** `validate("", "")` → `{name: 'Name is required', email: 'Email is required'}` ✅
**TEST — Case 2:** `validate("Pravin", "abc")` → `{email: 'Enter a valid email'}` ✅
**TEST — Case 3:** `validate("Pravin", "pra@test.com")` → `{}` ✅

Confident it works. Now call `validate()` inside `handleSubmit`, set errors, and bail early if there are any:

```tsx
const handleSubmit = (e: React.SyntheticEvent<HTMLFormElement>) => {
  e.preventDefault()

  const newErrors = validate(name, email)
  console.log("errors after validation:", newErrors)
  setErrors(newErrors)

  if (Object.keys(newErrors).length > 0) {
    console.log("form invalid — showing errors")
    return  // validation failed — stop here
  }

  // reaching here means all valid
  console.log("form valid, submitting")
  alert("Form submitted!")
  setName("")
  setEmail("")
}
```

**Cause and effect:**
- `validate(name, email)` → returns errors object (just checks)
- `setErrors(newErrors)` → React state update → triggers re-render (action)
- `Object.keys(newErrors).length > 0` → are there errors? → `return` — stop, don't submit
- No errors → submit, reset form

**Clean separation:**
- **validate()** — only checks, sets nothing
- **handleSubmit()** — decides what action to take

**TEST — Case 1:** Both fields empty. Console: "errors after validation: {name: 'Name is required', email: 'Email is required'}" ✅ + "form invalid — showing errors" ✅
**TEST — Case 2:** Name filled, email = "abc". Console: "errors after validation: {email: 'Enter a valid email'}" ✅
**TEST — Case 3:** Both correct. Console: "form valid, submitting" ✅. Alert pops up? ✅.

Now the errors state is being set. Next step — show them in the UI with ARIA attributes.

## Step 4 — Error Display: `aria-invalid` + `aria-describedby`

The errors object is updating. Now render them in the UI — red borders, error messages under each field, and ARIA attributes so screen readers announce the errors.

**Verify with console.log — is the errors state rendering?**

```tsx
// Inside the form, under the Name input:
{console.log("rendering errors:", errors)}
{errors.name && (
  <p style={{ color: "red" }}>{errors.name}</p>
)}
```

**TEST:** Submit with empty fields. Console: "rendering errors: {name: 'Name is required', email: 'Email is required'}" ✅. Red text shows on screen ✅.

Now do it properly — wire up `htmlFor` + `id`, `aria-invalid` + `aria-describedby`, and `role="alert"` on the error span:

```tsx
<div className="mb-4">
  <label htmlFor="contact-name" className="block font-medium mb-1">Name</label>
  <input
    id="contact-name"
    type="text"
    value={name}
    onChange={(e) => setName(e.target.value)}
    aria-required="true"
    aria-invalid={!!errors.name}
    aria-describedby={errors.name ? "name-error" : undefined}
    className={`w-full border rounded-lg px-3 py-2 focus:ring-2 focus:ring-blue-500 focus:outline-none ${
      errors.name ? "border-red-500" : "border-gray-300"
    }`}
  />
  {errors.name && (
    <span id="name-error" role="alert" className="text-red-600 text-sm mt-1 block">
      {errors.name}
    </span>
  )}
</div>
```

Each attribute's role:

| Attribute | What it does |
|-----------|-------------|
| `htmlFor="contact-name"` | Links the label to the input — click the label, focus the input. Screen reader says "Name" when the input is focused. |
| `id="contact-name"` | The input's unique ID. `htmlFor` matches this. |
| `aria-required="true"` | Screen reader announces "Name, required" — the user knows this field can't be empty |
| `aria-invalid={!!errors.name}` | When there's an error → `aria-invalid="true"`. Screen reader says "Name, invalid entry" |
| `aria-describedby="name-error"` | Links the error message to the input — screen reader reads the error when the input is announced |
| `role="alert"` | The moment the error span appears, the screen reader announces it immediately — no need to navigate to it |

**`aria-describedby` is dynamic** — `errors.name ? "name-error" : undefined`. When there's no error, the attribute doesn't exist. The screen reader only reads the error description when an error actually exists. No false positives.

## Step 5 — Email Field + Complete Form

Same pattern for email:

```tsx
<div className="mb-4">
  <label htmlFor="contact-email" className="block font-medium mb-1">Email</label>
  <input
    id="contact-email"
    type="email"
    value={email}
    onChange={(e) => setEmail(e.target.value)}
    aria-required="true"
    aria-invalid={!!errors.email}
    aria-describedby={errors.email ? "email-error" : undefined}
    className={`w-full border rounded-lg px-3 py-2 focus:ring-2 focus:ring-blue-500 focus:outline-none ${
      errors.email ? "border-red-500" : "border-gray-300"
    }`}
  />
  {errors.email && (
    <span id="email-error" role="alert" className="text-red-600 text-sm mt-1 block">
      {errors.email}
    </span>
  )}
</div>
```

Add `noValidate` to the form — we're validating with JavaScript. Without `noValidate`, the browser runs its own HTML5 validation (the `required` attribute, type checking, etc.) on top of ours, and the two can conflict:

```tsx
<form onSubmit={handleSubmit} noValidate>
```

`noValidate` disables the browser's built-in validation. Since we're handling everything ourselves, we don't need the browser to interfere.

Complete final component:

```tsx
import { useState } from "react"

export default function ContactSection() {
  const [name, setName] = useState("")
  const [email, setEmail] = useState("")
  const [errors, setErrors] = useState<{ name?: string; email?: string }>({})

  const validate = (name: string, email: string) => {
    const newErrors: { name?: string; email?: string } = {}
    if (!name.trim()) newErrors.name = "Name is required"
    if (!email.trim()) newErrors.email = "Email is required"
    else if (!email.includes("@")) newErrors.email = "Enter a valid email"
    return newErrors
  }

  const handleSubmit = (e: React.SyntheticEvent<HTMLFormElement>) => {
    e.preventDefault()
    const newErrors = validate(name, email)
    if (Object.keys(newErrors).length > 0) {
      setErrors(newErrors)
      return
    }
    setErrors({})
    alert("Form submitted!")
    setName("")
    setEmail("")
  }

  return (
    <section className="py-16 bg-gray-50" aria-labelledby="contact-heading">
      <div className="max-w-xl mx-auto px-4">
        <h2 id="contact-heading" className="text-3xl font-bold text-center mb-8">
          Contact Us
        </h2>

        <form onSubmit={handleSubmit} noValidate>
          <div className="mb-4">
            <label htmlFor="contact-name" className="block font-medium mb-1">Name</label>
            <input
              id="contact-name" type="text" value={name}
              onChange={(e) => setName(e.target.value)}
              aria-required="true"
              aria-invalid={!!errors.name}
              aria-describedby={errors.name ? "name-error" : undefined}
              className={`w-full border rounded-lg px-3 py-2 focus:ring-2 focus:ring-blue-500 focus:outline-none ${
                errors.name ? "border-red-500" : "border-gray-300"
              }`}
            />
            {errors.name && (
              <span id="name-error" role="alert" className="text-red-600 text-sm mt-1 block">
                {errors.name}
              </span>
            )}
          </div>

          <div className="mb-4">
            <label htmlFor="contact-email" className="block font-medium mb-1">Email</label>
            <input
              id="contact-email" type="email" value={email}
              onChange={(e) => setEmail(e.target.value)}
              aria-required="true"
              aria-invalid={!!errors.email}
              aria-describedby={errors.email ? "email-error" : undefined}
              className={`w-full border rounded-lg px-3 py-2 focus:ring-2 focus:ring-blue-500 focus:outline-none ${
                errors.email ? "border-red-500" : "border-gray-300"
              }`}
            />
            {errors.email && (
              <span id="email-error" role="alert" className="text-red-600 text-sm mt-1 block">
                {errors.email}
              </span>
            )}
          </div>

          <button type="submit"
            className="w-full bg-blue-600 hover:bg-blue-700 text-white py-3 rounded-lg font-semibold transition-colors focus:ring-2 focus:ring-blue-500 focus:ring-offset-2">
            Send Message
          </button>
        </form>
      </div>
    </section>
  )
}
```

## Common Mistakes

- **Using `placeholder` as a label:** The placeholder vanishes once the user starts typing. The screen reader reads it, but visually the user forgets what the field is for. Always use a real `<label>`.
- **Forgetting `aria-invalid`:** You show the red border and error text, but the screen reader has no idea the field is invalid. The user doesn't know where the error is.
- **Missing `role="alert"`:** The error message appears on screen but the screen reader doesn't announce it. The user only discovers it if they navigate to it manually.
- **`htmlFor` / `id` mismatch:** The label's `htmlFor` must match the input's `id`. A typo breaks the association.
- **Forgetting `noValidate`:** The browser runs its own validation alongside yours — confusing and redundant.

## Try It Yourself

1. Remove `aria-required`. Test with a screen reader — does the user still know the field is required?
2. Remove `role="alert"`. Submit with empty fields — the error shows on screen, but does the screen reader announce it?
3. Misspell the `htmlFor` ID (e.g., `"contact-nme"` instead of `"contact-name"`). Click the label — does the input get focus?
