Before writing any code, some tools need to be understood — they're the backbone of running a project. We'll go through them in the right order: first the runtime needed to run things (Node.js, and the modern alternative Bun), then the tools that come with them (npm/npx), then the build tool (Vite), then actual project creation, folder structure, the first component, dev server + HMR, and finally code-quality tools (ESLint/Prettier). Each section builds on the previous one — no topic is isolated.

---

## 1. Node.js — Running JavaScript Outside the Browser

Normally, JavaScript only runs inside browsers — Chrome, Firefox execute it with their own engines. But setting up a React project, installing packages, and running a dev server all happen in the terminal, outside the browser. For that, you need a separate runtime that can execute JavaScript in the terminal/server.

**Node.js** is that runtime — a JavaScript engine that runs JavaScript outside the browser, in the terminal and on the server.

```
Browser  → Executes JavaScript inside the browser
Node.js  → Executes JavaScript in the terminal/server
```

Node.js is required for a React project because:
- It comes bundled with **npm** (the package manager) — for installing packages
- The dev server runs on this runtime
- The build process (compiling code for production) also runs here

**Clarification:** Node.js is not part of React — it's an independent, separate tool. React doesn't depend on Node.js, but React's tooling (npm, dev server, build) runs on Node.js.

**Check if it's already installed:**
```
node --version
npm --version
```

If you see version numbers, it's installed. If you get an error, install it from nodejs.org.

Now that you understand Node.js, it's important to also look at a modern alternative, because both are actively used in the development community, and when you see commands later, you should know both syntaxes.

---

## 2. Bun — Node.js's Modern Alternative

**Bun** is also a JavaScript runtime, just like Node.js — it runs JavaScript in the terminal too. The difference is that Bun is newer and designed to be fast.

```
Node.js → Came out in 2009, most widely used, "legacy standard"
Bun     → Came out in 2023, faster, has more built-in tooling
```

Bun's specific advantages:
- **Speed** — package installation is significantly faster than Node.js (up to ~4x)
- **Built-in TypeScript support** — no need to configure TypeScript separately
- **Built-in bundler, test runner, and package manager** — all three tools built into one runtime, no separate installation needed

**Check if installed:**
```
bun --version
```

If not installed, get it from bun.sh.

Both Node.js and Bun are runtimes — both run JavaScript in the terminal, but Bun is newer and faster. Both have their own command-line tools (`npm`/`npx` for Node.js, and Bun equivalents) — let's look at those next.

## 3. npm, npx, and Bun

### What is a "Package"?

In the JavaScript world, any reusable library or tool is called a **package**. React is a package, Vite is a package, Axios is a package — code written by another developer, published on the internet, and you can use it in your project.

The question is — how do these packages get onto your computer?

### npm — Installing Packages Permanently

npm (Node Package Manager) comes bundled with Node.js. Its job is to download packages from the internet and add them to your project permanently.

```bash
npm install react
```

This command means: "Install the React package into my project." React is used every day — building components, managing state — so it's installed permanently.

> **npm's job:** Permanently install and manage packages.

But do you need to install every package permanently?

### Vite — What is it? (Brief)

We'll cover Vite in detail in the next section, but for now, just know this: Vite is a tool that automatically sets up a new React project — creates the folder structure, adds configuration, and installs React.

Vite's installer is called **create-vite**. When you run `create-vite`, it creates the project. Once the project is created, you never need that installer again.

That's why permanently installing `create-vite` would be wasteful. This is where `npx` comes in.

### npx — Run Once Without Installing

npx also comes with npm. Its job is to run a package **once, without permanently installing it.**

```bash
npx create-vite
```

This command means:
1. npx downloads the `create-vite` package from the internet
2. Runs it once — it creates the project
3. After the work is done, npx does NOT permanently install that installer

> **npx's job:** Run a package temporarily, without permanently installing it.

### npm vs npx — Which to Use When

| Scenario | Command | Why? |
|---|---|---|
| React needed in the project permanently | `npm install react` | You'll import it in every component |
| Just need to create a project once | `npx create-vite` | The installer is not needed after |

**Simple rule:** If you use the package every day → `npm install`. If you only need to run it once → `npx`.

### Bun's Equivalents

Bun has the same concept, just different command names:

| Use Case | Node.js | Bun |
|---|---|---|
| Install all dependencies | `npm install` | `bun install` |
| Add a new package | `npm install react` | `bun add react` |
| Run a package without installing | `npx create-vite` | `bunx create-vite` |
| Start the dev server | `npm run dev` | `bun run dev` |

The concepts are identical — just different syntax. Now let's use these tools to actually create a project. But first, it's important to understand which tool actually creates the project and runs during development — that's Vite.

## 4. Vite — The Build Tool

**Vite** is a build tool that does three things:
1. Generates the starting structure of a React project
2. Runs a local development server
3. Builds the final optimized code for production

**Before Vite:** Create React App (CRA) was the standard tool. CRA was webpack-based — every small code change triggered a full project re-bundle, which was slow. React's official documentation no longer recommends CRA; Vite is the standard.

**Clarification:** Vite isn't just a "better CRA" — it's a complete rewrite at the architecture level.

**Why Vite is fast:** During development, Vite uses native ES modules — when a module changes, only that module is reloaded, not the whole project. (You'll see the practical effect with HMR — Hot Module Replacement — in a moment, when you can actually see it in action.)

Now that we understand Node.js/Bun, npm/npx, and Vite, let's combine them to create an actual project.

## 5. Creating the Project (Step-by-Step)

For every step, commands for both Node.js and Bun are provided — follow whichever runtime you chose consistently.

**Step 1 — Create and enter a folder:**
```
cd Desktop
mkdir react-course
cd react-course
```

**Step 2 — Generate the project:**

Node.js:
```
npx create-vite@latest . -- --template react-ts
```
Bun:
```
bunx create-vite@latest . -- --template react-ts
```

This command:
- Generates the project in the current folder (`.`)
- Uses the `react-ts` template — React + TypeScript pre-configured
- Sets up Vite as the build tool

**Step 3 — Install dependencies:**

Node.js:
```
npm install
```
Bun:
```
bun install
```

This downloads all the libraries listed in `package.json` and stores them in the `node_modules` folder. With Node.js, a `package-lock.json` is created; with Bun, a `bun.lock` is created — both track the exact installed versions.

**Step 4 — Start the dev server:**

Node.js:
```
npm run dev
```
Bun:
```
bun run dev
```

The output should look something like:
```
VITE v6.x.x  ready in 200ms
➜  Local:   http://localhost:5173/
```

Open `http://localhost:5173` in the browser — the project should be running.

The dev server is running — in this state, you'll see an important behavior when you make code changes. That's HMR, which we'll see practically now.

## 6. HMR — Hot Module Replacement

From now on, whenever you make a code change while the dev server is running, the browser updates automatically — without a full page reload. This is called HMR.

**Flow:**
```
Code change made
       ↓
Vite replaces only the module that changed
       ↓
Browser updates — current state is preserved
       ↓
No full page reload
```

**Clarification:** HMR is not a browser-native feature — it's a Vite feature. Vite detects the changes and selectively updates the browser.

This difference is very noticeable compared to CRA — CRA showed a visible delay on reload after even small changes, while Vite is near-instant.

Now that the project is running and HMR is understood — it's important to look inside the project to see which files were actually created and what each one does.

## 7. Project Folder Structure

```
react-course/
├── index.html
├── package.json
├── tsconfig.json
├── tsconfig.app.json
├── tsconfig.node.json
├── vite.config.ts
├── public/
└── src/
    ├── main.tsx
    ├── App.tsx
    ├── App.css
    ├── index.css
    └── vite-env.d.ts
```

**What each file does:**

- **`index.html`** — The browser loads this file first. It contains `<div id="root">` where the React app mounts, and a `<script type="module" src="/src/main.tsx">` that loads the React app.
- **`package.json`** — The project's metadata (name, version), the list of dependencies, and the runnable scripts (`dev`, `build`, etc.). `npm install` / `bun install` read this file to download packages.
- **`tsconfig.json`** — TypeScript's configuration — strictness level, allowed features, etc. (`tsconfig.app.json` is for app code, `tsconfig.node.json` is for Vite-style Node tooling — two separate configs because app code and build tooling code have different requirements.)
- **`vite.config.ts`** — Vite's own configuration file (plugins, build options).
- **`src/main.tsx`** — Entry point. This is where `ReactDOM.createRoot()` is called, rendering the React app into `<div id="root">`.
- **`src/App.tsx`** — The root component. This is where you start writing your actual React code.

You now understand the folder structure — now let's look inside that `App.tsx` file and write our first actual component.

## 8. The First Component

Replace `src/App.tsx` with this code:

```tsx
interface GreetingProps {
  name: string;
  age?: number;
}

function Greeting({ name, age }: GreetingProps) {
  return (
    <div>
      <h1>Hello, {name}!</h1>
      {age && <p>Age: {age}</p>}
    </div>
  );
}

function App() {
  return (
    <div>
      <Greeting name="Vin" age={25} />
    </div>
  );
}

export default App;
```

**Breakdown:**
- `GreetingProps` — an `interface` that defines that `Greeting` needs `name` (string, required) and `age` (number, optional — marked with `?`).
- `Greeting` — a functional component that displays `name` and (if present) `age`.
- `App` — the root component, which renders `Greeting`.

Notice — this code has no `useState`, `useRef`, or generics. Just basic TypeScript types + `interface`. This is intentional — no new concept is introduced until there's an actual need for it.

Save the file, check the browser (if the dev server is already running, HMR reflects the change instantly) — you should see "Hello, Vin!" and "Age: 25" displayed.

The component is built and the project is running — there's one final setup step that every professional project has: code quality tools.

## 9. ESLint + Prettier Setup

**ESLint** — a code quality checker that flags potential bugs and inconsistent patterns. Vite's `react-ts` template already has this configured — it works out of the box, no extra setup needed.

**Prettier** — a code formatter that prevents formatting-style conflicts. You install it separately:

Node.js:
```
npm install -D prettier eslint-config-prettier
```
Bun:
```
bun add -d prettier eslint-config-prettier
```

Create a `.prettierrc` file in the project root:

```json
{
  "semi": true,
  "singleQuote": false,
  "tabWidth": 2,
  "trailingComma": "all",
  "printWidth": 100
}
```

**Clarification:** In team-based or professional projects, ESLint/Prettier are not optional — they're standard practice to set up on day one.
