In 0.4, we saw how Fiber made reconciliation interruptible. But React is even smarter — when an event handler makes multiple state updates, React groups them together into a single render. This is called **Batching**.

Without batching, every `setState` call would trigger a separate re-render. That hurts performance and could show inconsistent states to the user mid-update. React thought this through ahead of time.

---

## Problem — Multiple SetState = Multiple Renders?

Look at this code:

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  const [text, setText] = useState("");

  function handleClick() {
    setCount(count + 1);  // State update 1
    setText("Clicked!");  // State update 2
  }

  return (
    <div>
      <p>{count} — {text}</p>
      <button onClick={handleClick}>Click</button>
    </div>
  );
}
```

There are two `setState` calls in `handleClick`. Does React re-render twice?

**No.** React **batches** both updates into a single re-render. Both new values are applied in one render.

## React 17 and Before — Limited Batching

In React 17, batching only happened **inside event handlers**:

```jsx
// ✅ Batched (inside event handler)
function handleClick() {
  setCount(c => c + 1);
  setText("Clicked");
  // Single re-render — both updates together
}

// ❌ Not batched (outside event handler)
setTimeout(() => {
  setCount(c => c + 1);
  setText("Updated");
  // Two separate re-renders!
}, 1000);

// ❌ Not batched in Promises either
fetch("/api/data").then(() => {
  setCount(c => c + 1);
  setText("Fetched");
  // Two separate re-renders!
});
```

In React 17, `setTimeout`, Promises, and native event listeners were **not** batched — each `setState` triggered its own re-render.

## React 18 — Automatic Batching

React 18 removed this limitation. Now **everything** is batched:

```jsx
// ✅ Event handler — batched (React 17 did this too)
function handleClick() {
  setCount(c => c + 1);
  setText("Clicked");
  // Single re-render
}

// ✅ setTimeout — now batched (new in React 18)
setTimeout(() => {
  setCount(c => c + 1);
  setText("Updated");
  // Single re-render — React 17 did two separate renders here!
}, 1000);

// ✅ Promise — now batched
fetch("/api/data").then(() => {
  setCount(c => c + 1);
  setText("Fetched");
  // Single re-render — React 17 did two separate renders here!
}, 1000);

// ✅ Native event — now batched
button.addEventListener("click", () => {
  setCount(c => c + 1);
  setText("Clicked");
  // Single re-render
});
```

> **Analogy — Grocery Shopping:** React 17 is like going to the store for each item — need 5 things? Make 5 separate trips. React 18 is like making one shopping list and doing one trip. Same items, but much more efficient.

## How Batching Works Internally

When you call `setCount(c + 1)`, React doesn't re-render immediately. Instead, React stores the update in an internal **queue**:

```
Step 1: setCount(1)     → Queue: [count update]
Step 2: setText("Hi")   → Queue: [count update, text update]
Step 3: (event handler ends) → React processes queue → Single re-render
```

React's internal logic is essentially — "collect all state updates within the current execution context. When the context ends, process them all at once."

## How to Break Batching

Sometimes you **don't** want updates to batch. You want each update to process immediately. In React 18, `flushSync` lets you do this:

```jsx
import { flushSync } from "react-dom";

function handleClick() {
  flushSync(() => {
    setCount(c => c + 1);
  });
  // React re-renders immediately now

  flushSync(() => {
    setText("Done");
  });
  // Then another re-render — separate
}

// Two separate re-renders (not batched)
```

`flushSync` is for rare cases — like when you need to read DOM state immediately after an update (`scrollHeight`, `getBoundingClientRect()`, etc.). In general, batching is a **good thing** — avoid `flushSync` unless truly needed.

## Why Batching Matters

1. **Performance** — Fewer re-renders = less work = faster app
2. **Consistency** — Both state updates are applied at once; the user never sees a half-updated UI
3. **Predictable** — One event handler = one render, predictable behavior

> ❌ Batching doesn't **delay** state updates — they're processed at the end of the event handler (microtask level)
> ❌ Batching doesn't **ignore** any updates — all updates are applied, just together
> ❌ Batching isn't **just a performance feature** — it also ensures consistency (no intermediate renders)
> ❌ Batching is **available everywhere in React 18** — no more `setTimeout` gotchas

**In Your Own Words**

1. What is state batching?

<details>
<summary>Sample Answer</summary>

**Answer:** State batching is a React optimization where multiple `setState` calls are grouped together and processed in a single re-render. If there are 3 `setState` calls in an event handler, React doesn't re-render 3 times — it applies all updates at once in a single render.

</details>

2. What's the difference between React 17 and React 18 batching?

<details>
<summary>Sample Answer</summary>

**Answer:** In React 17, batching only happened inside event handlers (onClick, onChange, etc.). `setTimeout`, Promises, and native event listeners were not batched — each `setState` triggered its own re-render. React 18 introduced "Automatic Batching" — now batching happens everywhere, whether in an event handler, `setTimeout`, Promises, or native event listeners.

</details>

3. How does React implement batching internally?

<details>
<summary>Sample Answer</summary>

**Answer:** When `setState` is called, React doesn't re-render immediately. It stores the update in an internal queue. When the current execution context is complete (the event handler, the `setTimeout` callback), React processes the queue — applies all updates at once, and triggers a single re-render.

</details>

4. When do you use `flushSync`?

<details>
<summary>Sample Answer</summary>

**Answer:** You use `flushSync` when you want to force an update to process immediately, bypassing batching. This is for rare cases — like when you need to read DOM state right after an update (`scrollHeight`, `getBoundingClientRect()`). In general, avoid it since it causes performance hits.

</details>

5. What's a real-world analogy for batching?

<details>
<summary>Sample Answer</summary>

**Answer:** Like sending multiple messages on WhatsApp. If you send one by one, each triggers a separate network request. But if you type all messages and send them together, only one request carries everything. React's batching is the same — multiple state updates are grouped into a single render instead of triggering separate renders.

</details>
