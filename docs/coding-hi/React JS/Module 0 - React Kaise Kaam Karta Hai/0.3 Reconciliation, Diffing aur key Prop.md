In 0.2, we saw that JSX compiles into `React.createElement()` calls, which create Virtual DOM nodes. When state changes, React creates a new Virtual DOM tree. Now React has two trees — the old one (from the previous render) and the new one (current). React needs to decide: **what's different between these two trees?** Which nodes actually changed?

This process is called — **Reconciliation**.

---

## What is Reconciliation?

Reconciliation means — **comparing two trees to figure out exactly what changed.**

React's reconciliation process ensures two things:

1. **Speed** — Don't update the Real DOM over and over
2. **Accuracy** — Only update the elements that actually changed

## Naive Approach — The O(n³) Problem

If React compared two trees brute-force (comparing every node against every node), the time complexity would be **O(n³)** — where n is the total number of nodes. 1000 nodes would need 1 billion comparisons. That's way too slow.

React solved this problem with two assumptions:

1. **Different type → different tree** — If the parent element's type changed (div → span), rebuild the entire subtree
2. **`key` prop → stable identity** — For same-type elements, the `key` tells React which element is which

Thanks to these two assumptions, React went from O(n³) to **O(n)** — linear time. 1000 nodes need only 1000 comparisons.

## Diffing Algorithm — How it Works

### 1. Compare Root Elements

React first compares the root elements. If the type is different, the entire old tree is destroyed and a new one is built:

```jsx
// Before
<div>
  <Counter />
</div>

// After
<span>
  <Counter />
</span>
```

⚠️ Here, `<Counter />` gets destroyed and its state resets — because the parent changed from `<div>` to `<span>`. The whole subtree unmounts and remounts.

### 2. Same Type — Update Props

If the type is the same, React only compares the props:

```jsx
// Before
<div className="old" style={{ color: 'red' }} />

// After
<div className="new" style={{ color: 'blue' }} />
```

What React will do:
- `className` — update to `"new"`
- `style.color` — update to `"blue"`
- Doesn't destroy the DOM element, just updates the properties

### 3. Same Type — Recursively Compare Children

Then React applies the same process recursively to children.

```jsx
// Before
<div>
  <h1>Title</h1>
  <p>Description</p>
</div>

// After
<div>
  <h1>New Title</h1>
  <p>New Description</p>
  <footer>Footer</footer>
</div>
```

What React will do:
- Update the text content of `<h1>`
- Update the text content of `<p>`
- `<footer>` is a new element — add it

## `key` Prop — Why is it Critical?

Now the question — **how does this work with lists?**

```jsx
// Before
<ul>
  <li>Apple</li>
  <li>Mango</li>
  <li>Banana</li>
</ul>

// After (Banana moved to the front)
<ul>
  <li>Banana</li>
  <li>Apple</li>
  <li>Mango</li>
</ul>
```

Without a `key`, what does React do? It compares by position:
- Position 1: `Apple` → `Banana` (text changed — update)
- Position 2: `Mango` → `Apple` (text changed — update)
- Position 3: `Banana` → `Mango` (text changed — update)

**3 updates!** Even though only the order changed, not the content.

Now with `key`:

```jsx
// Before
<ul>
  <li key="a">Apple</li>
  <li key="m">Mango</li>
  <li key="b">Banana</li>
</ul>

// After
<ul>
  <li key="b">Banana</li>     // key="b" — was at position 3, now position 1
  <li key="a">Apple</li>      // key="a" — was at position 1, now position 2
  <li key="m">Mango</li>      // key="m" — was at position 2, now position 3
</ul>
```

React sees the `key` and knows — **the elements are the same, only the order changed.** So React doesn't destroy DOM elements, it just **reorders** them. The text doesn't even change — same elements.

**0 updates in the DOM!** Just a position swap.

> **Analogy — Student Roll Numbers:** Imagine a classroom with students. Their names can change (content change), but their roll numbers are fixed (key). If the teacher calls by name, reordering the list becomes a mess. But calling by roll number — "Roll 3, move forward" — easy. The `key` gives React that roll number.

## How to Choose a `key`

```jsx
// ✅ Good — unique ID
<li key={item.id}>{item.name}</li>

// ❌ Bad — index (bugs when the list changes)
<li key={index}>{item.name}</li>

// ❌ Bad — Math.random() (new key every render = destroy + remount)
<li key={Math.random()}>{item.name}</li>
```

**Why is index a bad choice?**

Imagine a list where you add, remove, or delete items:

```jsx
// Don't worry about useState details — we'll cover it in Batch 1
// Just the idea: items is an array with 'A', 'B', 'C'
const [items, setItems] = useState(['A', 'B', 'C']);

// Now you deleted 'A' — items is now ['B', 'C']
// Previously at index 0 was 'A', now it's 'B' — but React sees the same index (same key)
// If there was typed text in 'A', that state would transfer to 'B'!
```

The **stability** of `key` tells React which element is **actually the same** across re-renders. Index is unstable — when the list changes, indices shift.

## Reconciliation Summary

```
State Change → New Virtual DOM → Compare with Old
                                         |
                               ┌─────────┴──────────┐
                               │  Type Different?    │
                               │  → Destroy + Rebuild│
                               └─────────┬──────────┘
                                         │
                               ┌─────────┴──────────┐
                               │  Same Type?         │
                               │  → Update Props     │
                               └─────────┬──────────┘
                                         │
                               ┌─────────┴──────────┐
                               │  Lists?             │
                               │  → Compare by key   │
                               └─────────────────────┘
```

> ❌ Reconciliation is **not the Virtual DOM** — Virtual DOM is a data structure, Reconciliation is a process
> ❌ The `key` prop is **not just for performance** — it's also for correctness (state preservation)
> ❌ Reconciliation is **not always perfect** — it's React's "best-effort." Manual optimization is sometimes needed (`React.memo`, `useMemo`)
> ❌ **Never** use index as `key` — unless the list is absolutely static (never reordered)

**In Your Own Words**

1. What is Reconciliation?

<details>
<summary>Sample Answer</summary>

**Answer:** Reconciliation is React's process that compares the new Virtual DOM tree against the old one and decides which changes to apply to the Real DOM. Thanks to this process, React only updates the elements that actually changed.

</details>

2. How does React's diffing algorithm work in O(n)?

<details>
<summary>Sample Answer</summary>

**Answer:** React makes two assumptions — (1) Different type = completely different tree (destroy + rebuild), (2) The `key` prop gives stable identity across re-renders. Thanks to these assumptions, React doesn't do brute-force comparison (O(n³)), but instead does linear comparison (O(n)). Each node is compared only once.

</details>

3. Why is the `key` prop important in lists? What problem occurs without it?

<details>
<summary>Sample Answer</summary>

**Answer:** The `key` prop tells React which element is actually the same across re-renders. Without it, React compares by position — if a list reorders (item deleted/inserted), React updates the wrong elements. This causes bugs — like an input field's state transferring to the wrong element. With `key`, React reorders elements instead of recreating them.

</details>

4. What happens when the parent element's type changes (div → span)?

<details>
<summary>Sample Answer</summary>

**Answer:** React destroys the entire subtree and rebuilds a new one. If there was a component inside (like `<Counter />`), it gets unmounted and its state resets. That's why you need to be careful when wrapping components in different elements.

</details>

5. Why is index a bad choice for the `key` prop? Give an example.

<details>
<summary>Sample Answer</summary>

**Answer:** Index is the array position — when the list changes (delete/insert), the index also changes. Example — list is ['A','B','C'], index 0='A', 1='B', 2='C'. If you delete 'A', the list becomes ['B','C'] — now index 0='B', 1='C'. But React thinks the element at index 0 is still the same one, so the state that belonged to 'A' transfers to 'B'. That's why you need a unique, stable key — like `item.id`.

</details>
