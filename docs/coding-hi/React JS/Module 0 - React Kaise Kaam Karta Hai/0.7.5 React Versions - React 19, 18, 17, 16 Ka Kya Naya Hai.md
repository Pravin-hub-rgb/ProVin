React is the same — each major version adds significant new capabilities, some things get deprecated, and you always need to check compatibility. React's major version timeline looks like this:

```
React 15 → React 16 → React 17 → React 18 → React 19
  (2016)   (2017)   (2020)   (2022)   (2024)
  Legacy   Fiber    Bridge   Auto-   Actions
           +Hooks   Version  Batch   +use()
```

> **One-line takeaway:** The version number isn't just a number — each major version brings new capabilities or deprecates old ones. In this file, we'll understand each version in one line.

## What are React Versions? — `major.minor.patch`

React version format is **major.minor.patch** — like `19.0.0`, `18.3.1`, `17.0.2`.

| Part | Meaning | Example |
|------|---------|---------|
| **Major** (19) | Breaking changes or major new features | Upgrading may require a migration guide |
| **Minor** (0) | New features, backward compatible | React 19.1 — new small features |
| **Patch** (0) | Bug fixes only | React 19.0.1 — just a bug fix |

We're mainly interested in **major versions** since those are where significant changes happen. React 18.3.1 vs React 18.0.0 — same major, your code runs on both (maybe slightly faster). But upgrading from React 18 to React 19 — new features, some old things deprecated, possible migration needed.

**Important:** React `19.0.0` is the latest stable version (released December 2024). This course uses React 19 — all examples, features, and syntax are React 19 compatible.

## React 19 (December 2024) — The Current Latest Stable

React 19 is the latest stable version, and it's what we'll be using. It introduces several major improvements that make React even more powerful:

### 1. Actions — Server-Side Form Handling

Up until React 18, form submission logic was client-side. You'd call `event.preventDefault()`, then fire `fetch()` to your API, then update state. React 19 introduced **Actions** — sending form submissions directly to the server without any client-side orchestration.

```jsx
// React 19 — Actions
import { useFormState } from "react";

export default function TodoForm() {
  const [state, formAction, isPending] = useFormState(createTodo, null);

  return (
    <form action={formAction}>
      <input name="todo" type="text" />
      <button type="submit" disabled={isPending}>
        Add
      </button>
    </form>
  );
}

async function createTodo(prev, formData) {
  "use server"; // This function runs directly on the server
  const todo = formData.get("todo");
  // Save to database
  return { success: true };
}
```

**How it works:**
- `<form action={formAction}>` — the form automatically POSTs to the `formAction` function on the server
- `"use server"` directive — tells React this function runs server-side
- `useFormState` — manages form state (previous state, current state, loading status)
- `isPending` — shows the form submission loading state

> **Remember this:** Actions didn't exist before React 18. In React 18, you handled everything manually with `fetch()` and `useState`. In React 19, the form automatically goes to the server. This aligns with Next.js's Server Actions.

### 2. `use()` Hook — Promise and Context in One

React 19 introduced a new hook — `use()`. You can use promises directly in render (no need for `useEffect` + `useState`):

```jsx
import { use } from "react";

function User({ userId }) {
  // use() resolves the promise directly
  const user = use(fetchUser(userId));

  return <h1>{user.name}</h1>;
}
```

> **Remember this:** `use()` is a new React 19 feature. In React 18, you used the `useEffect` + `useState` combo for data fetching. `use()` is simpler — it resolves the promise directly in render.

### 3. `useOptimistic` — Instant-Feeling UI

Send an action and want the UI to show it's done before the server actually finishes? Like sending a message on WhatsApp — it shows "sent" immediately while the server saves it in the background. React 19's `useOptimistic` gives you exactly this:

```jsx
import { useOptimistic } from "react";

function Chat() {
  const [messages, setMessages] = useState([]);
  const [optimisticMessages, addOptimistic] = useOptimistic(
    messages,
    (state, newMessage) => [...state, newMessage]
  );

  async function sendMessage(text) {
    addOptimistic({ text, sending: true }); // Show UI immediately
    await actualSendMessage(text);         // Send to server
    setMessages([...messages, { text, sent: true }]); // Real state update
  }
}
```

**How it works:**
- `addOptimistic(newMessage)` — updates the UI immediately (as if the message was sent)
- When `actualSendMessage` completes, `setMessages` updates the real state
- If the server fails, the optimistic update is rolled back

### 4. Refs as Props — No More `forwardRef` Needed

In React 18, if you needed to pass a `ref` to a component, `forwardRef` was required:

```jsx
// React 18 — forwardRef was required
const Input = React.forwardRef((props, ref) => (
  <input ref={ref} />
));
```

In React 19, `ref` became a regular prop — no `forwardRef` needed:

```jsx
// React 19 — ref is just a prop
const Input = ({ ref, ...props }) => (
  <input ref={ref} />
);
```

> **Remember:** `forwardRef` still works in React 19 (backward compatible), but using `ref` as a direct prop is cleaner.

### 5. Server Components — Now Stable

React 18 had Server Components as experimental. React 19 makes them stable — production-ready, no warnings. The benefit of Server Components: the component renders on the server, the browser never receives its JavaScript, and the bundle size shrinks.

### 6. Hydration Improvements — Partial Hydration

In React 18, you needed `hydrateRoot` on the client. React 19 makes hydration automatic — React figures out where hydration should start. Partial hydration means if a component was already server-rendered, React can skip it and only render the remaining pieces.

## React 18 (March 2022) — Start of the Concurrent Era

React 18 was a major release that laid the foundation for concurrent rendering — a system that lets React prioritize multiple tasks.

### 1. Automatic Batching — Batched Everywhere

We saw the React 17 vs React 18 batching difference in 0.5. React 17 only batched inside event handlers. React 18 introduced **Automatic Batching** — now batching happens everywhere:

```jsx
// React 18 — all of this will be a single render
setTimeout(() => {
  setCount(c => c + 1);
  setText("Updated");
}, 1000);

fetch("/api/data").then(() => {
  setCount(c => c + 1);
  setText("Fetched");
});
```

> **Remember:** In React 17, these triggered separate renders. In React 18, one render — that's why React 18 introduced "Automatic Batching."

### 2. `useId` — SSR-Safe Unique IDs

A common problem with server-side rendering: if you generate an ID with `Math.random()` or `Date.now()`, the server and client generate different IDs, and hydration fails. React 18 introduced `useId`:

```jsx
function Dropdown() {
  const id = useId(); // Same ID on every render, server and client
  return (
    <>
      <label htmlFor={id}>Choose:</label>
      <select id={id}>
        <option>A</option>
      </select>
    </>
  );
}
```

### 3. `startTransition` — Urgent vs Non-Urgent Updates

React 18 gave us `startTransition` — keep user input urgent (clicks, typing), while deferring non-urgent work (data fetching, list filtering):

```jsx
import { startTransition } from "react";

function Search() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState([]);

  function handleChange(e) {
    // Keep the input responsive (urgent)
    setQuery(e.target.value);

    // Defer the filtering (non-urgent)
    startTransition(() => {
      const filtered = filterResults(e.target.value);
      setResults(filtered);
    });
  }
}
```

> **Remember:** `startTransition` is a React 18 feature that's still used in React 19. It keeps the UI responsive during heavy updates.

### 4. Concurrent Root — `createRoot`

React 18 replaced `ReactDOM.render()` with `createRoot()` — this enables the concurrent root:

```jsx
// React 18+ — use createRoot
const root = ReactDOM.createRoot(document.getElementById("root"));
root.render(<App />);

// Old way (React 17 and earlier) — now deprecated
// ReactDOM.render(<App />, document.getElementById("root"));
```

> ⚠️ **Note:** The Project Setup file (0.8) uses Vite's `react-ts` template, which automatically uses `createRoot` — that's been the standard since React 18.

### 5. `useDeferredValue` + `useSyncExternalStore`

- **`useDeferredValue`** — defer a value (like showing search results a moment later)
- **`useSyncExternalStore`** — the standard way to subscribe to external stores (Redux, Zustand). It existed in React 17, but was stabilized in React 18.

## React 17 (October 2020) — The "Bridge" Version

React 17 is an unusual release — **no new features**. Its sole purpose was to simplify the upgrade path:

- **Event delegation change** — React events moved from the old `document` to the root element. This reduced DOM conflicts (like with jQuery).
- **New JSX transform** — `"react/jsx-runtime"` — you no longer need `import React from "react"` for JSX (but we import it in this course for clarity).
- **No breaking changes** — Upgrading from React 16 to 17 was smooth.

> **Remember:** React 17 was a "bridge" — no new features, just smoothing the path from React 16 to React 18. It was React 17 that facilitated the journey from Hooks (16.8) to Concurrent mode (18).

---

## React 16 (September 2017) — The Birth of Fiber and Hooks

React 16 was a major release — a complete rewrite of React's engine:

### Fiber Architecture (covered in detail in 0.4)

React 16 replaced the React engine with **Fiber** — a new reconciliation algorithm that doesn't block the browser. As detailed in 0.4, this introduced priority levels, interruptible rendering, and cooperative scheduling.

### Error Boundaries (React 16.0)

When an error occurs in the component tree, instead of crashing the whole app, show a fallback UI:

```jsx
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  render() {
    if (this.state.hasError) return <h1>Something went wrong.</h1>;
    return this.props.children;
  }
}
```

### Hooks (React 16.8 — The Biggest Moment)

React 16.8 brought Hooks — this changed React forever:

> **"Hooks at 16.8 — function components gained full power."**

```jsx
// Hooks existed only in class components before — now in function components too
function Counter() {
  const [count, setCount] = useState(0); // useEffect introduced in React 16.8
  useEffect(() => { /* ... */ }, []);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
```

**What changed with Hooks?**
- No more class components — `this` binding is a thing of the past
- `useState`, `useEffect`, `useContext`, `useRef`, `useMemo`, `useCallback` — all added in 16.8
- Stateful logic became reusable — custom hooks emerged

## React 15 and Earlier (Brief) — Legacy Era

React 15 and earlier versions had:

- **`ReactDOM.render()`** — single root rendering (used until React 18, now deprecated).
- **Legacy Context API** — `childContextTypes` / `contextTypes` (prop-based, complex). React 16.3 introduced the new Context API.
- **String refs** — `ref="myRef"` (now deprecated, use `createRef` or `useRef`).
- **No Fiber** — synchronous rendering (the browser freeze problem).

> **Remember:** React 15 and earlier are not used anymore — React 16+ (Fiber + Hooks) is the standard. React 18+ (`createRoot`) is the production standard.

## Which Version Should You Use?

**Rule of thumb: Use the latest stable version — React 19.**

Why?
- Latest features — Actions, `use()`, `useOptimistic`
- Best performance optimizations
- Security fixes
- Active community support
- Best compatibility with Next.js (Next.js 15 = React 19)

> ❌ **React 18 is still common in production** — yes, React 18 is widely used in production (for stability). But for new projects, use React 19. This course uses React 19 — all concepts, examples, and code are React 19 compatible.

### TypeScript Compatibility

| React Version | TypeScript Version | Notes |
|---------------|-------------------|-------|
| **React 19** | TS 5.0+ | With `@types/react` 19 |
| **React 18** | TS 4.7+ | With `@types/react` 18 |
| **React 16** | TS 3.0+ | Old, not recommended |

If you're using React 19, you need TypeScript 5.0+ and `@types/react` 19 (or newer).

---

## What It Is NOT

- ❌ **React versions mean breaking changes in every upgrade** — no. Minor and patch releases are backward compatible. Only major versions (18→19) bring breaking changes.
- ❌ **All features exist in all versions** — no. `useOptimistic` didn't exist before React 19. `startTransition` didn't exist before React 18. `useState` didn't exist before React 16.8.
- ❌ **React 17 was a "feature release"** — no. React 17 was an intentional no-feature release, just to smooth the upgrade path.
- ❌ **To upgrade React, just run `npm install react@latest`** — for major version upgrades (18→19), you need to read the migration guide. Some APIs may be deprecated.
- ❌ **Old React versions are still worth using** — no. Latest stable (React 19) is best for new projects. Old versions are only for legacy maintenance.

## In Your Own Words

1. What is React 19's biggest new feature, and how did you handle this in React 18?

<details>
<summary>Sample Answer</summary>

**Answer:** React 19's biggest new feature is **Actions** — sending form submissions directly to the server (`action` prop + `useFormState` + `"use server"`). In React 18, you handled this manually with `event.preventDefault()`, `fetch()`, and `useState`. In React 19, the whole process becomes automatic — the form submits to the server directly.

</details>

2. Why is React 17 called a "bridge version"? Did it have any new features?

<details>
<summary>Sample Answer</summary>

**Answer:** React 17 is called a "bridge version" because it had **no new features**. Its only purpose was to smooth the upgrade path — making the jump from React 16 (legacy) to React 18 (concurrent) easier. Changes included: event delegation moved from `document` to the root element (reducing conflicts), and the new JSX transform (`react/jsx-runtime`) that doesn't require importing React.

</details>

3. When did Hooks arrive, and how did this change React?

<details>
<summary>Sample Answer</summary>

**Answer:** Hooks arrived in React **16.8**. This fundamentally changed React — function components now had full power (state, effects, context via hooks). No more class components, no `this` binding headaches. Stateful logic became reusable through custom hooks. React 16.8 was the moment that truly transformed the framework.

</details>

4. What's the difference between React 18 and React 19 regarding batching?

<details>
<summary>Sample Answer</summary>

**Answer:** Both versions have batching — React 18 introduced "Automatic Batching" (batching happens everywhere, not just event handlers). React 19 doesn't change batching — it works the same. The difference is that React 19 adds new features like Actions, `use()`, and `useOptimistic` that didn't exist in React 18.

</details>

5. If a project uses React 16.8, which of these are available: `useState`, `useId`, `startTransition`, `useOptimistic`?

<details>
<summary>Sample Answer</summary>

**Answer:** With React 16.8, `useState` is available (Hooks were introduced in 16.8). `useId` is not — that's a React 18 feature. `startTransition` is not — also React 18. `useOptimistic` is not — that's React 19. So only the core Hooks are available, not the React 18/19 features.

</details>
