
## MCQ

Q: What does "Reconciliation" mean?
A. React's internal engine that pauses and resumes rendering
B. React's process that compares old and new trees and decides what changed
C. React's feature that groups multiple state updates together
D. React's syntax extension that compiles HTML-like code into JavaScript
> B. Reconciliation means comparing old and new Virtual DOM trees to figure out what changed. It's the process that decides which real DOM nodes to update — it's not the engine (that's Fiber), not batching (that's... batching), and not compilation (that's Babel).

---

Q: If React compared two trees with brute-force, what would the time complexity be?
A. O(n) — number of comparisons equals the node count
B. O(log n) — logarithmic to the node count
C. O(n²) — square of the node count
D. O(n³) — cube of the node count
> D. Brute-force tree comparison is O(n³) — comparing every node against every other node. For 1000 nodes, that's 1 billion comparisons. That's why React made assumptions to bring it down to O(n).

---

Q: What two assumptions does React's diffing algorithm make to work in O(n)?
A. First — ignore identical parent types, second — prioritize text changes
B. First — different type = rebuild whole tree, second — key prop gives stable identity
C. First — only check root element nesting, second — match children types
D. First — compare every node against every node in the other tree, second — depth limit of 3
> B. React makes two assumptions: (1) Different type = completely different tree (destroy + rebuild), (2) `key` prop gives stable identity across re-renders. These bring O(n³) down to O(n).

Q: When the parent element's type changes from div to span, what does React do?
A. Only changes the parent's tag name, children remain untouched
B. Destroys the entire subtree and builds a new one
C. Nothing changes since both div and span are block elements
D. React throws an error since type changes aren't allowed
> B. When the parent type changes, React destroys the entire old subtree and builds a new one. Any components inside (like `<Counter />`) also get unmounted and their state resets.

---

Q: When the same type of element exists, what does React compare?
A. Only compares children, ignores props
B. Only compares and updates text content
C. Only compares props and applies the ones that changed
D. Nothing — same type elements are always completely ignored
> C. For same-type elements, React only compares the props and updates the ones that changed in the real DOM. The DOM element is not destroyed — just its properties are updated.

---

Q: When rendering list items without a `key`, how does React compare them?
A. Compares each item's actual text content
B. Compares each item by its array position or index
C. Compares each item's HTML structure and nesting pattern
D. Compares randomly — there's no fixed rule
> B. Without a `key`, React compares by position (index). Position 1's element — is it the same? Position 2's? etc. When items reorder, React may update the wrong elements.

---

Q: What information does the `key` prop give React?
A. How to CSS-style the element
B. Where to position the element in the DOM tree
C. Whether the element is the same or different across different renders
D. When to render the element and when to skip it
> C. The `key` prop gives React a stable identity — "this element is actually the same one from last render, just the position changed." Without `key`, React compares by position, which can cause bugs.

---

Q: Why is index a bad choice for the `key` prop?
A. Because index starts at 0, and React treats index 0 as the root
B. Because index is the array position — when the list changes, the index shifts too
C. Because index is a number, but key should be a string
D. Because React only shows a performance warning, but the code runs correctly
> B. Index is unstable. If you delete 'A' from a list, the item at index 1 ('B') is now at index 0. React thinks the element at index 0 is still the same one — so 'B' inherits the state that 'A' had. Index is only safe for static lists that never change.

## TrueFalse

Q: React's reconciliation process is always perfect — manual optimization is never needed.
- True
- False
> False. Reconciliation is React's "best-effort" approach. In complex cases, manual optimization may be needed — like using `React.memo` or `useMemo`. Reconciliation is efficient, but not perfect.

---

Q: If a list is absolutely static (never changes, never reorders), using index as the `key` is safe.
- True
- False
> True. In a static list, items are never added, removed, or reordered — the index stays stable, and no shifting occurs. But if the list becomes dynamic (even one delete or insert), the index becomes unsafe.

---

Q: If only the className of a same-type element changes (from "old" to "new"), React destroys the entire DOM element and creates a new one.
- True
- False
> False. When the type is the same, React does NOT destroy the DOM element. Only the props that changed (className in this case) are updated. The element stays the same — only its properties change.

---

Q: Fragments (`<>...</>`) also compile into `React.createElement(React.Fragment)`, so they go through reconciliation too.
- True
- False
> True. A Fragment is also a React element — it just doesn't create an extra DOM node. During reconciliation, React checks the Fragment's type too. If Fragment changes to div, the subtree gets rebuilt.

## ShortAnswer

Q: How does React's diffing algorithm reduce from O(n³) to O(n)? Explain the two assumptions React makes.

<details>
<summary>Sample Answer</summary>

React makes two assumptions that turn brute-force comparison (O(n³)) into linear time (O(n)):

**Assumption 1 — Different Type = Completely Different Tree**
If the parent element's type changes (div → span, or ComponentA → ComponentB), React discards the entire old subtree and builds a new one. Because of this assumption, React doesn't need to compare every node against every other — it just checks the type and immediately decides.

**Assumption 2 — `key` Prop = Stable Identity**
For same-type elements, the `key` prop tells React which element is actually the same across re-renders. When React sees the same type with the same key, it knows "this is the same element" — even if its position changed. Because of this, React doesn't need to compare the content of each list item.

With these two assumptions, React does O(n) — for 1000 nodes, only 1000 comparisons.

</details>

Q: What problem occurs when you don't add a `key` prop to list items? Explain with an example.

<details>
<summary>Sample Answer</summary>

Without a `key`, React compares by position (index). This causes bugs when the list changes.

**Example — List Reorder:**

Before:
```
<ul>
  <li>Apple</li>    // position 1
  <li>Mango</li>    // position 2
  <li>Banana</li>   // position 3
</ul>
```

After (Banana moved to front):
```
<ul>
  <li>Banana</li>   // position 1 — was Apple
  <li>Apple</li>    // position 2 — was Mango
  <li>Mango</li>    // position 3 — was Banana
</ul>
```

Without `key`: React compares by position → 3 updates (text changed at every position).
With `key`: React recognizes the same elements just reordered → 0 updates, just a reorder.

**Example — Input field state bug:**

If the list contains input fields:
```
<li key={index}><input /></li>   // ['A', 'B', 'C']
```
Delete 'A' → list becomes ['B', 'C']. The input state that belonged to 'A' now transfers to 'B', because index 0 is now 'B'.

That's why you need a stable, unique `key` — like `item.id`.

</details>
