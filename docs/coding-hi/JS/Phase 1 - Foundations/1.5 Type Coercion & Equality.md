In the last topic, you learned about hoisting — how JavaScript reads all declarations before running any code. But there's another JavaScript behavior that confuses almost everyone: type coercion.

You've probably seen memes about JavaScript. `0 == "0"` returns `true`. `0 == []` returns `true`. `"0" == []` returns `false`. What is going on?

It's actually very simple once you understand one thing: JavaScript sometimes automatically converts values from one type to another before comparing them. That's type coercion.

---

## The Currency Converter Analogy

Imagine you're traveling to a different country. You have $100 USD. You want to buy something that costs €85 EUR. Can you compare them directly? No — they're different currencies. You need to convert one to the other first.

But there are two ways to do this:

1. **Loose comparison:** Convert everything to the same currency first, then compare. "Is $100 worth more than €85?" You check the exchange rate, convert, and compare.
2. **Strict comparison:** Don't convert at all. "Is $100 the same as €85?" No — they're different currencies. The answer is always no.

`==` is the loose comparison. It converts types first. `===` is the strict comparison. It doesn't convert at all.

---

## ✅ What is type coercion?

> **Type coercion is JavaScript's automatic conversion of a value from one data type to another.**

Let's unpack that.

**"Automatic conversion"** — JavaScript does this without being asked. You don't call a function to convert. It just happens when you use certain operators like `==`, `+`, or `if()`.

**"From one data type to another"** — a string becomes a number. A number becomes a boolean. A boolean becomes a string. JavaScript decides what type it needs and converts your value to match.

---

## ✅ The two equality operators

| Operator | What it does |
|---|---|
| `==` | Loose Equality. Converts both sides to the same type first, then compares. |
| `===` | Strict Equality. No conversion. Compares both value and type. |

### Example 1: String and Number

```js
"5" == 5   // ✅ true
"5" === 5  // ❌ false
```

`==` converts the string `"5"` to the number `5`. Then they're equal. `===` does no conversion. A string is never equal to a number.

### Example 2: 0 and false

```js
0 == false   // ✅ true
0 === false  // ❌ false
```

`==` converts both to numbers. `false` becomes `0`. So `0 == 0` is `true`. `===` sees a number and a boolean — different types, so `false`.

### Example 3: The special case

```js
null == undefined  // ✅ true
null === undefined // ❌ false
```

This is the only special rule in the entire language. `null` and `undefined` are considered equal with `==`, but they're different types with `===`.

Here's why it's special: in the previous examples, `==` works by coercing one side to match the other's type. But `null` and `undefined` break that pattern. They don't coerce to anything:

```js
null == 0       // ❌ false  (null does NOT become 0)
null == ""      // ❌ false
null == false   // ❌ false
null == null    // ✅ true
undefined == 0  // ❌ false
```

The spec has a hardcoded rule: `null` and `undefined` are only equal to each other and to themselves. Nothing else.

---

## ✅ Other places coercion happens

Coercion doesn't just happen with `==`. It happens in other places too:

### if statements

```js
if ("hello") {
  // This runs. "hello" is coerced to true.
}

if (0) {
  // This does NOT run. 0 is coerced to false.
}
```

Values that coerce to `false`: `0`, `""` (empty string), `null`, `undefined`, `NaN`, `false`. Everything else coerces to `true`.

### A practical problem: Default values

Now that you know about falsy values, here's a real problem. Suppose you have a variable `count` that could be `null` or a number. You want a default value of `10` if `count` is `null`:

```js
const displayCount = count || 10;
```

This works — if `count` is `null`, `||` returns `10`. But what if `count` is `0`?

```js
const count = 0;
const displayCount = count || 10;
console.log(displayCount); // 10 😱
```

Wait, `0` is a valid count! But `||` treats `0` as falsy, so it returns `10`. This is wrong. `||` falls back for **all falsy values** — but sometimes you only want to fall back for `null`/`undefined`.

### Enter: Nullish Coalescing Operator (`??`)

```js
const count = 0;
const displayCount = count ?? 10;
console.log(displayCount); // 0 ✅
```

`??` only falls back for `null` and `undefined` — not for `0`, `""`, or `false`. It's the safer default value operator.

| Expression | `\|\|` Result | `??` Result |
|---|---|---|
| `null ?? 10` | `10` | `10` |
| `0 ?? 10` | `10` ❌ (0 is valid!) | `0` ✅ |
| `"" ?? "default"` | `"default"` ❌ | `""` ✅ |
| `false ?? true` | `true` ❌ | `false` ✅ |

You'll see `??` everywhere in React code — especially when API responses might return `null`. Remember: `||` checks falsy, `??` checks nullish (only `null`/`undefined`).

### The + operator

```js
1 + "1"   // "11"  — number is coerced to string, then concatenated
"1" + 1   // "11"  — same thing
1 + 1     // 2     — both numbers, so addition
```

When `+` sees a string, it converts everything to strings and concatenates. When it sees only numbers, it adds.

### The - operator

```js
"5" - 1   // 4     — string is coerced to number, then subtraction
"5" - "3" // 2     — both strings coerced to numbers
```

Unlike `+`, the `-` operator only works with numbers. So it always coerces to numbers.

---

## 🚨 The Golden Rule

> **Always use `===`.** Always. No exceptions.

Never use `==` in real code. Ever.

You will only ever need to know about `==` for interviews. In real projects, `===` prevents an entire category of bugs. Linters (tools that check your code for errors) will flag `==` as a warning.

---

## ✅ What It Is NOT

- **Type coercion is NOT the same as type conversion.** Coercion is automatic — JavaScript does it without being asked. Conversion is explicit — you call `Number()`, `String()`, or `Boolean()` to convert a value yourself. Explicit conversion is fine. Coercion is where bugs hide.

- **`==` is NOT the same as `===`.** They look similar but behave completely differently. `==` coerces types. `===` does not. Always use `===`.

- **Coercion is NOT random.** It follows specific rules. Once you learn the rules, the behavior is predictable. It's not magic — it's just a set of conversion rules that JavaScript applies automatically.

- **`NaN` is NOT equal to itself.** `NaN === NaN` returns `false`. This is not coercion — it's a rule of IEEE 754 floating point math. `NaN` represents "not a number," and by definition, something that's not a number can't be equal to itself. Use `Number.isNaN()` to check for `NaN`.

## 🧠 Interview Questions

> ❓ What is the difference between == and ===?
> == is loose equality — it performs type coercion before comparing. === is strict equality — it compares both value and type without any conversion.

> ❓ What is type coercion?
> Type coercion is JavaScript's automatic conversion of a value from one type to another. It happens with operators like ==, +, and in conditional statements like if().

> ❓ What values coerce to false in JavaScript?
> Six values: false, 0, "" (empty string), null, undefined, and NaN. Everything else coerces to true.

> ❓ Why does null == undefined return true but null === undefined return false?
> The == operator has a special rule that null and undefined are equal to each other (and only to each other). But they are different types, so === returns false.

> ❓ Why does NaN === NaN return false?
> NaN is the only value in JavaScript that is not equal to itself. This is a rule from the IEEE 754 floating point standard. Use Number.isNaN() to check for NaN.

<details>

**Sample Answer:** `==` can produce unexpected results because of type coercion. For example, `0 == ""` returns `true` and `0 == "0"` returns `true`, but `"" == "0"` returns `false`. These inconsistencies can hide bugs. `===` never coerces, so the result is always predictable — if the types don't match, it's `false`. Using `===` prevents an entire category of bugs.

<details>
<summary>Show Answer</summary>

**Sample Answer:** Six values coerce to `false`: `false`, `0`, `""` (empty string), `null`, `undefined`, and `NaN`. Everything else coerces to `true`.
