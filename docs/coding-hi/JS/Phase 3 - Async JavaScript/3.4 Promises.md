Remember that pyramid of doom from the last topic? The one with `getUser`, `getPosts`, `getComments`, `getLikes` all nested inside each other, pushing code further right until you can't even see it without scrolling?

Imagine trying to debug that at 2 AM. A bug is hiding somewhere inside those 7 levels of nesting. Where do you even start?

What if there was a way to write async code that reads top-to-bottom, left-to-right — like normal code — without getting pushed further right with every step?

That's exactly what Promises are for.

---

## The Restaurant Analogy

You walk into a restaurant, sit down, and order a meal. The waiter doesn't bring your food immediately — the kitchen needs time to cook. But the waiter doesn't just stand there waiting either. They give you a **receipt** for your order.

That receipt is not the food. But it's a guarantee: "Your food is coming. When it's ready, we'll bring it to you."

While the kitchen works, you can do other things. Check your phone, talk to your friend, read the menu again. You don't have to sit and stare at the kitchen door waiting for the food. You go about your business, and when the food is ready, the waiter brings it to you.

If something goes wrong — they're out of ingredients, the chef burnt your dish — the waiter comes back and tells you what happened. Maybe they give you a chance to order something else.

That receipt is a Promise.

---

## ✅ What is a Promise?

> **A Promise is an object that represents the eventual result of an asynchronous operation.**

Let's unpack that because it's a lot of words packed into one sentence.

**"Eventual result"** — you don't have the value yet, but you will. Like that restaurant receipt: it's not the food, but it's a guarantee the food is coming.

**"Asynchronous operation"** — something that takes time. A network request, a timer, a file read. The kind of thing that would freeze your browser if you had to wait for it synchronously.

**"Object"** — it's a real JavaScript object with methods like `.then()` and `.catch()`. You can store it in a variable, pass it to a function, return it from a function. It's not magic — it's just an object with special behavior.

So putting it all together: a Promise is a JavaScript object that acts as a placeholder for a value you don't have yet. You create it, it starts working, and when the work is done, it gives you the result — or tells you why it couldn't.

A Promise can only be in one of three states at any time:

| State | What it means | Restaurant version |
|---|---|---|
| `pending` | Still running. No result yet. | Kitchen is cooking. You have the receipt. |
| `fulfilled` | Success. We have a value. | Food arrives at your table. |
| `rejected` | Failure. We have an error. | Waiter comes back to say the kitchen messed up. |

Once a Promise is fulfilled or rejected, it's **settled**. No going back to pending. A Promise can only change state once — from pending to fulfilled, or from pending to rejected. That's it.

## ✅ Creating a Promise

Before we look at a real example with timers and conditions, let's start with the absolute simplest Promise possible. Just to see the connection clearly.

### The simplest Promise ever:

```js
const simplePromise = new Promise((resolve, reject) => {
  resolve("Hello from resolve!");
});

simplePromise.then((message) => {
  console.log(message); // "Hello from resolve!"
});
```

Let's trace exactly what happens here:

1. `new Promise(...)` creates a Promise. The function inside runs immediately.
2. Inside that function, we call `resolve("Hello from resolve!")`. This tells the Promise: "you are now fulfilled, and the value is this string."
3. The Promise transitions from **pending → fulfilled**. The value `"Hello from resolve!"` is stored inside the Promise.
4. JavaScript checks: "does anyone have a `.then()` attached?" Yes.
5. It runs the `.then()` callback and passes the stored value as the `message` parameter.
6. `console.log(message)` prints `"Hello from resolve!"`.

The connection is direct: **whatever you pass to `resolve()` becomes the argument in `.then()`.** There is no hidden wiring. It is a direct handoff.

```
resolve("Hello from resolve!")  ──→  .then((message) => ...)
                                          message = "Hello from resolve!"
```

### What about when it fails?

```js
const failPromise = new Promise((resolve, reject) => {
  reject("Something went wrong!");
});

failPromise.catch((error) => {
  console.log(error); // "Something went wrong!"
});
```

Same thing, just different path. The Promise transitions from **pending → rejected**. JavaScript checks: "does anyone have a `.catch()` attached?" Yes. The value you passed to `reject()` arrives as the `error` parameter in `.catch()`.

```
reject("Something went wrong!")  ──→  .catch((error) => ...)
                                            error = "Something went wrong!"
```

### Both together — resolve vs reject:

```js
const myPromise = new Promise((resolve, reject) => {
  const success = true;

  if (success) {
    resolve("✅ It worked!");
  } else {
    reject("❌ It failed.");
  }
});

myPromise
  .then((result) => {
    console.log(result); // "✅ It worked!"  (runs when resolve was called)
  })
  .catch((error) => {
    console.log(error); // "❌ It failed."   (runs when reject was called)
  });
```

Only one of them runs. The Promise cannot be both fulfilled and rejected. It picks a path.

```
                 ┌── resolve("✅ It worked!")  ──→  .then() runs
myPromise ──→   ┤
                 └── reject("❌ It failed.")   ──→  .catch() runs
```

### Now with a delay (realistic):

Now that you understand the direct connection, let's add a timer. The only difference is that `resolve()` doesn't run immediately — it waits 3 seconds.

```js
const orderFood = new Promise((resolve, reject) => {
  // This is the kitchen. The async work happens here.
  setTimeout(() => {
    const kitchenHasIngredients = true;

    if (kitchenHasIngredients) {
      resolve("🍝 Pasta Carbonara is ready!");
    } else {
      reject("Sorry, we're out of pasta.");
    }
  }, 3000);
});

orderFood
  .then((food) => {
    console.log(food); // (after 3s) "🍝 Pasta Carbonara is ready!"
  })
  .catch((error) => {
    console.log(error); // "Sorry, we're out of pasta."
  })
  .finally(() => {
    console.log("Waiter cleared the table."); // Always runs
  });
```

Same logic as the simple example. Same direct connection. The only difference is that `resolve("🍝 Pasta Carbonara is ready!")` runs after 3 seconds instead of immediately. But when it finally runs, the `.then()` still receives that exact value.

**The `.finally()` always runs** — whether the Promise was fulfilled or rejected. Think of it like the last line after an `if/else`: it runs regardless of which branch was taken.

| Method | When does it run? | Restaurant version |
|---|---|---|
| `.then()` | When the Promise fulfills. Receives the resolved value. | "The food is here. Now eat it." |
| `.catch()` | When the Promise rejects. Receives the error/reason. | "Something went wrong. Handle it." |
| `.finally()` | Always runs, whether fulfilled or rejected. | "Waiter clears the table either way." |

`.finally()` is useful for cleanup — hiding a loading spinner, closing a database connection, disabling a button. It runs no matter what.

## ✅ Promise Chaining — Fixing Callback Hell

Remember this from the Callbacks topic?

```js
getUser(userId, function(user) {
  getPosts(user.id, function(posts) {
    getComments(posts[0].id, function(comments) {
      getLikes(comments[0].id, function(likes) {
        // You cannot escape this nesting
      });
    });
  });
});
```

Here's the same logic rewritten with Promises:

```js
getUser(userId)
  .then((user) => getPosts(user.id))
  .then((posts) => getComments(posts[0].id))
  .then((comments) => getLikes(comments[0].id))
  .then((likes) => {
    console.log(likes);
  })
  .catch((error) => {
    console.log("Something broke:", error);
  });
```

Notice: the `.then()` calls are **chained** one after another, not nested. Each `.then()` returns a new Promise, and the next `.then()` waits for that Promise to resolve. The code reads top-to-bottom, like normal synchronous code.

And error handling? One single `.catch()` at the end catches any error from any step in the chain. No need to handle errors at every level of nesting. If `getUser` fails, it skips straight to the `.catch()` — `getPosts`, `getComments`, and `getLikes` never even run.

That's the whole point. Promises flatten async code from a pyramid back into readable lines.

---

## ✅ Return Values in Chaining

Here's an important detail: whatever you return from a `.then()` callback becomes the resolved value of the next `.then()`.

```js
getUser(userId)
  .then((user) => {
    return user.id; // This becomes the input to the next .then()
  })
  .then((id) => {
    console.log(id); // The user.id from previous step
  });
```

If you return a plain value, the next `.then()` receives it immediately. If you return a Promise, the next `.then()` waits for it to resolve. That's how the chain works — each step waits for the previous one, no nesting needed.

## ✅ Promise Combinators

Sometimes you need to coordinate multiple Promises at once. JavaScript provides four combinator methods for this.

### Promise.all() — Wait for All

```js
Promise.all([ fetchUser(), fetchPosts(), fetchComments() ])
  .then(([ user, posts, comments ]) => {
    // All 3 completed. You have all the data.
  })
  .catch((error) => {
    // Any one of them failed. This runs immediately.
  });
```

Think of ordering from multiple restaurants. You want all the food to arrive before you start eating. If any restaurant can't deliver, the whole meal is ruined.

- Waits for **all** to fulfill
- If **any** rejects, it fails immediately with that error

### Promise.allSettled() — Wait for All, No Matter What

```js
Promise.allSettled([ fetchUser(), fetchPosts(), fetchComments() ])
  .then((results) => {
    results.forEach((result) => {
      if (result.status === "fulfilled") {
        console.log("Got data:", result.value);
      } else {
        console.log("Failed:", result.reason);
      }
    });
  });
```

Same multiple restaurants, but this time you don't care if some orders fail. You'll still eat what arrived. Maybe the pasta failed, but the dessert came through fine.

- Waits for **all** to finish (fulfilled or rejected)
- Returns an array of objects with `status`, `value`, or `reason`

### Promise.race() — First One Wins

```js
Promise.race([ fetchFromServerA(), fetchFromServerB() ])
  .then((firstResult) => {
    console.log("Fastest server responded:", firstResult);
  });
```

Multiple couriers racing to your door. You take the food from whoever arrives first, even if the other courier crashes on the way.

- Returns the **first** Promise that settles, whether fulfilled or rejected

### Promise.any() — First Success Wins

```js
Promise.any([ fetchFromServerA(), fetchFromServerB() ])
  .then((firstSuccess) => {
    console.log("First successful response:", firstSuccess);
  })
  .catch((error) => {
    console.log("All failed:", error);
  });
```

Same racing couriers, but this time you only accept the food if it arrives intact. If a courier crashes, you ignore it and wait for the next. Only if all of them crash do you fail.

- Returns the **first fulfilled** Promise
- Ignores rejections unless **all** reject

## ✅ What It Is NOT

- **A Promise is NOT a callback.** Callbacks are functions you pass to be called later. A Promise is an object you create that manages its own state and notifies you when done. Different patterns entirely.

- **A Promise is NOT synchronous.** The executor function runs synchronously (JavaScript runs it immediately), but the `.then()` and `.catch()` callbacks run asynchronously — they go through the event loop (we covered that in 3.2). Creating a Promise doesn't block your code.

- **A Promise is NOT cancellable.** Once you create a Promise and start an async operation, you can't cancel it from the outside. There's no built-in `.cancel()` method. If you need cancellation, you'd use a library like AbortController (which we'll cover later) or build it yourself with extra logic.

- **A Promise is NOT the same as async/await.** Async/await is syntactic sugar built on top of Promises. They're not alternatives — async/await uses Promises under the hood. We'll cover that in the next topic.

## 🧠 Interview Questions

> ❓ What are the 3 states of a Promise?
> Pending, Fulfilled, Rejected. A Promise starts as pending, then transitions to either fulfilled (success) or rejected (failure). Once settled, it cannot change state again.

> ❓ What is the difference between Promise.all() and Promise.allSettled()?
> Promise.all fails immediately if any promise rejects — it's all-or-nothing. Promise.allSettled waits for every promise to finish regardless of success or failure, returning an array of result objects.

> ❓ What is the difference between Promise.race() and Promise.any()?
> Promise.race returns the first settled promise — could be success or failure. Promise.any returns only the first fulfilled promise, ignoring rejections until all fail.

> ❓ How do Promises solve callback hell?
> Promises allow chaining with .then() instead of nesting callbacks inside each other. This makes asynchronous code read top-to-bottom, left-to-right, and centralises error handling in one .catch() at the end of the chain.

> ❓ Can a Promise change from fulfilled to rejected?
> No. A Promise can only transition once: from pending to fulfilled, or pending to rejected. Once settled, it's frozen in that state forever.
