Till now, we have been working with plain objects.

```js
const user1 = { name: "Arjun", age: 22, isAdmin: false };
const user2 = { name: "Priya", age: 25, isAdmin: true };
```

This works fine for one or two objects. But there is a problem — **there is no structure**. What if I accidentally wrote:

```js
const user3 = { nam: "Rahul", aage: 30, admin: false };
```

No error. JavaScript does not care. Now I have a user with a typo in every field, and this will cause bugs that are hard to find.

What if I want to make 100 users? I would have to manually copy-paste the object 100 times. And if I need to add a new field (like `email`) to every user, I would have to go find and update all 100 objects manually.

**That is the problem classes solve.** A class is a **blueprint** that guarantees every object created from it has exactly the same structure. No typos. No missing fields. No inconsistency.

---

## ✅ What is a class?

A class is a blueprint for creating objects. It defines what properties and methods all objects created from it will have.

Think of a class like a **mould for making id cards**. The mould has empty slots for "Name", "Photo", "ID Number". You do not fill those in the mould itself — the mould just defines the blank structure. When you actually go to the counter and get your card made, that is when you fill in your specific details.

Let's start simple. Here is a class **without a constructor**:

```js
class Dog {
  bark() {
    console.log("Woof!");
  }
}
```

That's it. This class says: "Every dog created from me will be able to bark." Let's use it:

```js
const dog1 = new Dog();
const dog2 = new Dog();

dog1.bark(); // Woof!
dog2.bark(); // Woof!
```

Both dogs bark. The class guarantees that any dog we make will have the `bark` method.

But here is the problem. Our dogs are identical. They both bark, but they have no identity. Neither has a name. Neither has a color. You could do this after creating them:

```js
dog1.name = "Max";
dog2.name = "Bella";
```

But now we are back to the same problem as plain objects — nothing forces you to set a name, and if you forget, your dog just has no name. Inconsistent. Error-prone.

---

## ✅ The constructor

This is where the **constructor** comes in.

**The constructor is a special method that runs automatically the moment you create a new object from the class.** It is the setup function. It lets you pass in custom values so each instance gets its own identity.

Every dog has 4 legs — that is a default, every dog gets it automatically. But every dog needs its own name — that should be passed in when the dog is created. The constructor handles both:

```js
class Dog {
  constructor(name) {
    this.name = name;
    this.legs = 4;    // ← every dog has 4 legs. Set automatically. No need to ask.
  }

  bark() {
    console.log(`${this.name} says Woof!`);
  }
}
```

But wait — why are we writing `this.name = name`? Why `this`?

Because `name` (without `this`) is just the **parameter** — it is a local variable that only exists inside the constructor. Once the constructor finishes, that variable disappears.

`this` refers to the **brand new object that is being created**. When we write `this.name = name`, we are saying:

> "Take the value that was passed in as `name` and **store it on this new object** as a property called `name`."

So the `this.` prefix is how you attach values to the new object. Without it:

```js
constructor(name) {
  name = name;  // ❌ This just assigns the parameter to itself. Useless.
  // No property gets created on the object. Nothing gets stored.
}
```

The `name` value would just vanish when the constructor finishes. And other methods like `bark()` would have no way to access it because `this.name` would be undefined.

That is also why `bark()` uses `this.name` — it is saying "look at `this` object (the dog that was created) and get its `name` property."

Now let's create dogs:

```js
const dog1 = new Dog("Max");
const dog2 = new Dog("Bella");

console.log(dog1.name);  // Max
console.log(dog1.legs);  // 4  — automatically set
dog1.bark();             // Max says Woof!

console.log(dog2.name);  // Bella
console.log(dog2.legs);  // 4  — automatically set
dog2.bark();             // Bella says Woof!
```

Every dog has 4 legs (we did not have to set that manually — the constructor did it). Every dog has its own name (we passed it in when creating the dog). If you try to create a dog without a name:

```js
const dog3 = new Dog();
console.log(dog3.name);  // undefined — constructor still runs, name just wasn't passed
```

The constructor *always* runs. It runs the moment you write `new Dog(...)`. You cannot skip it.

In the id card analogy: the class is the mould, and the **constructor** is the person at the counter who takes your details and fills them into a fresh card. The mould defines the slots (name, photo, ID), the constructor fills them in for each specific card.

## ✅ Creating objects from a class

Let's use a more practical example — a `Car` class:

```js
class Car {
  constructor(color) {
    this.color = color;
    this.speed = 0;
  }

  accelerate() {
    this.speed += 10;
  }
}
```

Here is what each part means:

- `class Car` — "I am defining a blueprint for cars"
- `constructor(color)` — "When a new car is being made, accept a `color` value"
- `this.color = color` — "Take that color and store it on this specific car"
- `this.speed = 0` — "Every car starts with speed set to 0. Automatically."
- `accelerate()` — "All cars will have this action available"

Now create cars from the blueprint:

```js
const myCar = new Car("red");

console.log(myCar.color); // red
console.log(myCar.speed); // 0

myCar.accelerate();
console.log(myCar.speed); // 10
```

When you write `new Car("red")`, here is exactly what happens behind the scenes:

1. JavaScript creates a brand new empty object `{}`
2. It runs the `constructor` function, passing `"red"` as the `color` argument
3. Inside the constructor, `this` refers to that brand new object
4. All the `this.color = ...` and `this.speed = ...` lines fill that new object
5. The finished object is returned and stored in `myCar`

You can make as many cars as you want. Every one is completely separate. Each time you call `new Car(...)`, you get a fresh object with its own `color` and `speed`:

```js
const car1 = new Car("red");
const car2 = new Car("blue");
const car3 = new Car("green");

console.log(car1.color); // red
console.log(car2.color); // blue
console.log(car3.color); // green

car1.accelerate();
console.log(car1.speed);  // 10
console.log(car2.speed);  // 0  — unaffected
```

## ✅ Inheritance

Now we have a `Car` class. What if I want a more specific type of car? Like an `ElectricCar` that has everything a normal car has, plus a `batteryLevel` and a `charge()` method?

I could copy the entire `Car` class and add my new stuff. But that is the same problem we had with objects — duplication. If I later change `Car` (add a new method, fix a bug), I would have to remember to update my copy too.

**Inheritance** solves this. One class can **extend** another class. The child class gets everything from the parent class, and then adds its own stuff on top.

```js
class Car {
  constructor(color) {
    this.color = color;
    this.speed = 0;
  }

  accelerate() {
    this.speed += 10;
  }

  brake() {
    this.speed = 0;
  }
}
```

Now let's create an `ElectricCar` that extends `Car`:

```js
class ElectricCar extends Car {
  charge() {
    console.log("Charging... battery full!");
  }
}
```

That is it. Three words: `extends Car`. Now `ElectricCar` has everything `Car` has — `color`, `speed`, `accelerate()`, `brake()` — plus its own `charge()` method.

```js
const myEV = new ElectricCar("white");

console.log(myEV.color);     // white       ← from Car
myEV.accelerate();            //             ← from Car
console.log(myEV.speed);     // 10          ← from Car
myEV.charge();                // Charging!  ← from ElectricCar
myEV.brake();                 //             ← from Car
console.log(myEV.speed);     // 0           ← from Car
```

The electric car can do everything a normal car can do, plus its own thing. It inherited all the car behavior.

## ✅ But what if the child needs its own constructor?

Here is where it gets interesting. An `ElectricCar` might need extra properties — like `batteryCapacity`. So it needs its own constructor.

But there is a problem. The parent `Car` constructor is the one that sets up `this.color` and `this.speed`. If the child writes its own constructor, the parent's constructor never runs. Now `color` and `speed` never get set.

What we need is a way to say: "Run the parent's constructor first (so color and speed are set up), then run my additional setup."

That is exactly what `super()` does.

```js
class ElectricCar extends Car {
  constructor(color, batteryCapacity) {
    super(color);       // ← calls Car's constructor with "color"
    this.batteryCapacity = batteryCapacity;  // ← my own setup
  }

  charge() {
    console.log("Charging... battery full!");
  }
}
```

**`super()` calls the constructor of the parent class.** You pass it the arguments that the parent constructor expects. In this case, `Car`'s constructor expects `color`, so we pass `color` to `super(color)`.

And this rule is enforced by JavaScript: **you must call `super()` before you can use `this` in the child constructor.**

```js
class ElectricCar extends Car {
  constructor(color, batteryCapacity) {
    // ❌ This will throw an error:
    this.batteryCapacity = batteryCapacity;  // Must call super() first!

    super(color);
  }
}
```

Why? Because `this` does not exist yet until the parent constructor has done its setup. The parent creates `this`, fills in the shared properties, and only then can the child add its own. So `super()` must be the first line in your child constructor. Always.

## ✅ Overriding methods

Sometimes the child wants to do something **different** from the parent, not just add new stuff.

Let's say `Car` has a `start()` method:

```js
class Car {
  start() {
    console.log("Engine started. Vroom!");
  }
}
```

A `Tesla` is a car, but it does not have an engine. It should start differently. You can just write the same method name in the child class, and it **replaces** the parent's version:

```js
class Tesla extends Car {
  start() {
    console.log("Electric motor ready. Silent startup.");
  }
}
```

```js
const normalCar = new Car("red");
normalCar.start();  // Engine started. Vroom!

const myTesla = new Tesla("black");
myTesla.start();    // Electric motor ready. Silent startup.
```

This is called **overriding**. The child version wins over the parent version.

But what if you want to keep the parent's behavior and add to it, not replace it entirely? You can call `super` on methods too, just like with constructors:

```js
class Tesla extends Car {
  start() {
    super.start();                     // ← first do what a normal car does
    console.log("No emissions!");      // ← then add Tesla-specific stuff
  }
}
```

```js
myTesla.start();
// Engine started. Vroom!
// No emissions!
```

`super.start()` calls the parent's `start` method. This is useful when you want to extend the behavior, not replace it.

## ✅ Complete picture — All together

```js
class User {
  constructor(email, password) {
    this.email = email;
    this.password = password;
  }

  login() {
    console.log(`${this.email} logged in`);
  }
}

class Admin extends User {
  constructor(email, password, role) {
    super(email, password);   // ← run User's constructor first
    this.role = role;         // ← then add admin-specific field
  }

  login() {
    console.log(`${this.email} logged in as admin`);  // ← override
  }

  deleteUser(userId) {
    console.log(`Admin deleted user ${userId}`);
  }
}
```

```js
const user = new User("arjun@email.com", "1234");
user.login();        // arjun@email.com logged in

const admin = new Admin("priya@email.com", "5678", "superadmin");
admin.login();       // priya@email.com logged in as admin
admin.deleteUser(42); // Admin deleted user 42
```

## 🧠 Interview Questions

> ❓ Why do we need classes instead of plain objects?
> Classes provide a consistent blueprint. Without a class, every object is manually created and there is no guarantee of structure. With a class, every object has exactly the same properties and methods.

> ❓ What is the purpose of super()?
> It calls the constructor of the parent class. Must be called before using this in child constructor.

> ❓ What is the difference between class and object?
> Class is the blueprint. Object is the actual instance created from the class.

> ❓ Can a class extend multiple classes?
> No. JavaScript does not support multiple inheritance.

## 🎯 Interview Ready Answer

> "Classes in JavaScript are blueprints for creating objects. They solve the problem of inconsistent object structure by defining a template. The constructor method runs automatically when a new instance is created, handling initial setup. Classes support inheritance through the extends keyword, where super() must be called in the child constructor before accessing this. Methods can be overridden in child classes, and super.methodName() can be used to call the parent's version. Classes are syntactic sugar over JavaScript's prototype system."

That is the full correct answer.
