
When you drive a car, you do not plan to crash. But cars still have airbags, seatbelts, and crumple zones. Not because you *want* to crash, but because things go wrong and you want to walk away when they do.

Error handling is the airbag for your code.

No matter how carefully you write your JavaScript, things will go wrong. The network will fail. The user will send invalid data. A file will not exist. A third-party API will go down. If you do not handle these gracefully, your entire application crashes and the user sees a blank white screen. The user does not know or care whose fault it is — they just know your site is broken.

`try/catch` is your airbag. It lets you say "try running this code, and if something breaks, catch the error and handle it instead of crashing."

---

## ✅ Basic try / catch

✅ When code throws an error it will crash your entire program unless you catch it.

```js
try {
  // code that might fail
  const data = JSON.parse("this is not json");
} catch (error) {
  // only runs if there was an error
  console.log("Something went wrong");
}
```

✅ If there is an error inside try, execution jumps immediately to catch.
✅ If there is no error catch is completely skipped.

---

## ✅ Error object

✅ Every error has 3 standard properties:

```js
try {
  JSON.parse("bad json");
} catch (err) {
  console.log(err.name);      // SyntaxError
  console.log(err.message);   // Unexpected token 'b'
  console.log(err.stack);     // full stack trace
}
```

✅ Always log these. Never just log `err` by itself.

---

## ✅ finally

✅ `finally` always runs. No matter what.

```js
try {
  // try something
} catch (err) {
  // only on error
} finally {
  // always runs. Always.
  // put cleanup code here: close connections, remove loaders
}
```

✅ Even if you return from inside try or catch, finally will still run.

## ✅ Throwing errors

So far we have only been *catching* errors from other code (`JSON.parse` fails, network request fails). But what if YOUR code detects something wrong?

For example, a `registerUser` function receives an age of 15. Your app requires users to be 18+. What should happen? The function needs to signal that something invalid happened, so the caller can handle it — show a message to the user, log the attempt, etc.

✅ You can throw your own errors:

```js
function registerUser(age) {
  if (age < 18) {
    throw new Error("You must be 18 or older");
  }
  // proceed with registration
}
```

Now anyone calling `registerUser` can wrap it in a `try/catch` and handle the failure gracefully instead of the whole app crashing.

✅ Always throw actual Error objects. Never throw strings. Error objects have proper stack traces that tell you exactly where the error happened.

---

## ✅ Custom errors

What if your app needs to distinguish between different types of errors? A network error should show a "try again" button. A validation error should show a red highlight on the input field. A permission error should redirect to the login page.

A plain `Error` with just a message string cannot tell them apart. You would have to parse the message text, which is fragile and terrible practice.

✅ Extend the Error class to create custom error types with their own names and extra data:

```js
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}
```

✅ Usage:
```js
throw new ValidationError("Email is invalid", "email");
```

✅ Now in your catch block you can check the error type and handle each one differently:

```js
try {
  registerUser(data);
} catch (err) {
  if (err instanceof ValidationError) {
    // highlight the specific field
    showFieldError(err.field, err.message);
  } else {
    // generic error page
    showErrorPage(err.message);
  }
}
```

✅ This is how professional codebases handle errors.

## ✅ Async / Await error handling

✅ Exactly the same pattern:

```js
async function fetchUser() {
  try {
    const res = await fetch('/api/user');

    if (!res.ok) {
      throw new Error(`HTTP Error: ${res.status}`);
    }

    return await res.json();
  } catch (err) {
    console.error("Failed to fetch user:", err);
  }
}
```

## 🧠 Interview Questions

> ❓ When does finally run?
> Always. No matter if there was an error or not. Even if you return.

> ❓ Should you throw strings or Error objects?
> Always throw Error objects. They have proper stack traces.

> ❓ Can you have try without catch?
> Yes. But you must have finally.

## 🎯 Interview Ready Answer

> "Error handling in JavaScript uses the try/catch/finally pattern. Code inside try is executed, any thrown errors will be caught and handled in the catch block. Finally always runs regardless of outcome for cleanup operations. Custom errors can be created by extending the built in Error class."

That is the full correct answer.
