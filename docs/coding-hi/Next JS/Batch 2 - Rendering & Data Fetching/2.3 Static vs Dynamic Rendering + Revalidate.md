## Broader Goal

Now a critical question: **how often should this fetch happen?** 

- Fetch once at build time and serve the cached HTML forever? (Fast, but stale.)
- Fetch on every request? (Always fresh, but slow.)
- Fetch once, then refresh periodically? (The middle ground.)

This file covers:

**A — Server-Side Caching.** How Next.js caches `fetch` responses on the server (not the browser).

**B — Three Rendering Strategies.** Static (SSG), Dynamic (no-store), and ISR (revalidate).

**C — When to Use Each.** Decision framework for choosing the right strategy.

## Manual Approach — Every Request Is Fresh (React)

### The React Model

React had no concept of build-time caching. Every time a component mounted, it fetched fresh:

```tsx
// React — always fresh data
useEffect(() => {
  fetch('/api/products').then(...)
}, []);
```

Every visit. Every refresh. The API was hit **every time**. This guarantees fresh data but:
- Every user waits for the API
- The API gets hammered under load
- First paint is delayed

### The Performance Problem

```
User 1 → fetch → API
User 2 → fetch → API
User 3 → fetch → API
...
User 1000 → fetch → API  ← API is overwhelmed
```

All 1000 users hit the API. If each fetch takes 500ms, each user waits 500ms. The API server is stressed.

## Better Approach — Server-Side Caching

### Cache Lives On The Server, Not The Browser

Next.js's `fetch` has a **server-side cache**. This is **not** browser cache (Chrome/Firefox storage) — it is Next.js's server memory storing responses.

Think of it like this: your Next.js server is a building. The cache is a shelf right at the entrance. The real API is a deep basement. Before hitting the basement, Next.js checks the shelf:

```
┌─────────────────────────────────────────┐
│          Next.js SERVER                  │
│  ┌──────────────────────────────┐       │
│  │  LAYER 1: Cache (Shelf)      │       │
│  │  (First to check)            │       │
│  │  Hit? → serve cached         │       │
│  │  Miss? → go deeper           │       │
│  └──────────────────────────────┘       │
│          ↓                              │
│  ┌──────────────────────────────┐       │
│  │  LAYER 2: API CALL (Basement)│       │
│  │  (Real fetch)                │       │
│  │  Store response in cache     │       │
│  └──────────────────────────────┘       │
└─────────────────────────────────────────┘
                      ↑
             External API
        (dummyjson.com/products)
```

### The 100 Users Scenario

**With caching (default):**

```
User 1 → Cache MISS → API call → Cache response → Serve User 1
User 2 → Cache HIT  → Serve cached → No API call
User 3 → Cache HIT  → Serve cached → No API call
...
User 100 → Cache HIT → Serve cached → No API call

Result: 1 API call total. Fast for everyone.
```

**Without caching (`cache: "no-store"`):**

```
User 1 → Cache skip → API call → Serve User 1
User 2 → Cache skip → API call → Serve User 2
...
User 100 → Cache skip → API call → Serve User 100

Result: 100 API calls. Slow for everyone.
```

## A — Three Rendering Strategies

### 1. Static (SSG) — Build Time Only

By default (no options), `fetch` caches the response and the page becomes static HTML generated at build time:

```tsx
// app/products/page.tsx
export default async function ProductsPage() {
  const res = await fetch('https://dummyjson.com/products');  // caches forever
  const data = await res.json();
  return <ul>...</ul>;
}
```

- The fetch runs **once** during `next build`.
- The resulting HTML is stored and served from a CDN.
- It never re-fetches — until you build again.

**Test it:** Visit the page, note the time. Refresh — same time. The HTML is frozen from build time.

**Limitation:** If the API data changes, users see stale data until you rebuild.

### 2. Dynamic (`cache: "no-store"`) — Every Request

When data changes frequently, disable caching:

```tsx
// app/cart/page.tsx — user-specific, always fresh
export default async function CartPage() {
  const res = await fetch('https://api.example.com/cart', {
    cache: 'no-store',  // never cache — always re-fetch
  });
  const data = await res.json();
  return <ul>...</ul>;
}
```

- Every request hits the API fresh.
- No stale data — but slower and more API load.

**Use when:** data is user-specific (cart, dashboard) or real-time (stock prices, live scores).

### 3. ISR (`revalidate`) — Static + Background Refresh

The sweet spot: serve static HTML for speed, but refresh periodically:

```tsx
// app/products/page.tsx — revalidate every 60 seconds
export default async function ProductsPage() {
  const res = await fetch('https://dummyjson.com/products', {
    next: { revalidate: 60 },  // refresh every 60 seconds
  });
  const data = await res.json();
  return <ul>...</ul>;
}
```

- First request: cache MISS → API call → serve + cache the HTML.
- Next 59 seconds: cache HIT → serve instantly.
- At 60 seconds: Next.js **re-validates** in the background — fires off a new fetch, but still serves the **old** HTML to the current user.
- Once the new fetch completes, the cache is updated.

**What the user sees:**

```
Time 0:00  → API call (slow) → cached
Time 0:30  → cached (instant)
Time 1:00  → cached (instant) → background refetch starts
Time 1:01  → cached (instant) → new data now cached
```

The user **never** waits for the refetch — it happens in the background while serving stale data.

### Visual Comparison

| Strategy | First Request | Subsequent Requests | Stale? |
|---|---|---|---|
| Static (default) | Build time | Cached (forever) | Yes (until rebuild) |
| Dynamic (`no-store`) | Fresh each time | Fresh each time | Never |
| ISR (`revalidate`) | Fresh | Cached | Stale briefly (until revalidate) |

## B — When to Use Each

### Decision Matrix

| Data Characteristic | Strategy | Why |
|---|---|---|
| Never changes (About page, docs) | Static | Nothing to update, maximum speed |
| Changes often (stock prices, live data) | Dynamic (`no-store`) | Must always be fresh |
| Changes occasionally (product catalog) | ISR (`revalidate`) | Fresh enough, fast always |
| User-specific (cart, dashboard) | Dynamic (`no-store`) | Each user has different data |

### Practical Guidelines

**Static (default) — Use for:**
- Blog posts (updated on new published post)
- Product listings (updated on price change)
- About, Contact pages

**ISR (`revalidate`) — Use for:**
- Product listings with periodic price updates
- Blog post lists (new posts are rare)
- Any content that changes "eventually" but not "constantly"

**Dynamic (`no-store`) — Use for:**
- Shopping carts
- User dashboards
- Search results
- Live feeds

---

## Common Mistakes

- **Using `no-store` everywhere** — every page becomes a fresh API call. Your server gets overwhelmed and pages are slow.
- **Using the default (static) for user-specific data** — all users see the same cached data. Security and correctness issue.
- **Setting `revalidate: 1`** — revalidating every second is almost free to cache. Use a reasonable interval (60+ seconds for most data).
- **Testing ISR in `npm run dev`** — the dev server does not cache `fetch` the same way production does. To test ISR, use `npm run build && npm start`.
- **Expecting ISR to be real-time** — `revalidate: 60` means data is at most 60 seconds stale. For sub-second freshness, use dynamic.

## In Your Own Words

1. Where does Next.js cache `fetch` responses — in the browser or the server?

<details>
<summary>Sample Answer</summary>

**Answer:** Next.js caches on the **server** — it is server-side caching, not browser caching. The cached response lives in Next.js's server memory. When a new request comes in, Next.js checks its own cache first before making an external API call. This is completely invisible to the browser.

</details>

2. Explain the difference between `cache: "no-store"` and `next: { revalidate: 60 }`. When would you use each?

<details>
<summary>Sample Answer</summary>

**Answer:** `cache: "no-store"` means "never cache — always fetch fresh data." Every request hits the API. Use this for user-specific data (carts, dashboards) or anything that must always be current. `next: { revalidate: 60 }` means "serve cached data, but re-fetch in the background every 60 seconds." Use this for content that changes occasionally (product listings, blog lists) — you get static speed with periodic freshness.

</details>

3. Why might the default (static caching) be a problem in production?

<details>
<summary>Sample Answer</summary>

**Answer:** The default caches data forever — it only updates when you run `next build` again. If your API data changes frequently (prices, inventory), users see stale data until you rebuild and redeploy. In development it is not noticeable, but in production with real data changes, users get outdated information. That is why ISR (`revalidate`) is recommended for content that changes — it keeps the cache fresh without sacrificing performance.

</details>

4. How does ISR avoid making the user wait during revalidation?

<details>
<summary>Sample Answer</summary>

**Answer:** ISR serves the stale (cached) HTML to the current request immediately. Meanwhile, in the background, Next.js starts a new fetch to update the cache. The next request after the revalidate interval will get the fresh data. The user never waits for the background refetch — they get instant responses from cache, and the data is updated behind the scenes.

</details>
