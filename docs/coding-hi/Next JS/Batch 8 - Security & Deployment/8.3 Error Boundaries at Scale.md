In 1.4, we learned what `error.tsx` is — basic error handling: the `error` object + the `reset` function. Those were the concepts — now let's look at them **at scale** in a production app. The Photo Gallery has many routes — `/`, `/photo/[id]`, modal. If something crashes on `/photo/[id]`, will the entire app shut down? No — error boundaries work at different levels. But **which boundary catches which error?** That hierarchy needs to be understood — only then errors are handled gracefully in a production app.

---

## Manual Problem — One Error Boundary Is Not Enough

In 1.4, we created one `error.tsx` at the route level. But in a production app, errors can come from different places:

- **Route-level error** — data fetch fails on `/photo/[id]`
- **Layout error** — shared layout (like a navbar) crashes
- **Root layout crash** — the entire app's root layout fails
- **Client Component error** — runtime error in a `'use client'` component

If there's only one `error.tsx` — will it also catch layout errors? No — the layout sits above that boundary. **Multiple error boundaries are needed** — one at each level. That's what "at scale" means.

---

## CONCEPT — Error Hierarchy (Which Boundary Catches What)

In Next.js, error boundaries are **nested** — like Russian dolls (small doll inside, big doll outside). Each folder has its own `error.tsx` that catches errors for **that folder and its children.**

**Error Hierarchy Diagram:**

```
app/
├── global-error.tsx        ← Root layout crash (last resort — outermost)
├── not-found.tsx           ← Global 404
├── layout.tsx              ← Root layout (error here = global-error catches)
├── page.tsx                ← / (home)
├── photo/
│   ├── error.tsx           ← All /photo/* route errors
│   ├── loading.tsx         ← /photo/* loading
│   └── [id]/
│       ├── error.tsx       ← /photo/[id] specific errors
│       └── page.tsx        ← /photo/:id
├── error.tsx               ← App-level errors (after root)
└── not-found.tsx
```

**Understand the flow:**

1. Data fetch fails on `/photo/5` → an error occurs
2. Next.js first looks for the **smallest (nearest) boundary** — `photo/[id]/error.tsx`
3. If not found → go up — `photo/error.tsx`
4. If that's not found either → `app/error.tsx`
5. If the root layout crashes — `app/global-error.tsx` (last resort)

**This is the hierarchy — start from the smallest boundary, work up to the largest.**

---

## CODE — `global-error.tsx` (Last Resort)

`global-error.tsx` catches errors when the **root layout** itself crashes. It's special because:

- It's not inside the root layout — it's in the root `app/` folder
- It renders in place of the root layout — so you must provide `<html>` and `<body>` yourself
- `'use client'` is required (same reason as `error.tsx`)

**File:** `app/global-error.tsx` — new file (in root `app/` folder)

```tsx
'use client'

export default function GlobalError({
  error,
  reset,
}: {
  error: Error & { digest?: string }
  reset: () => void
}) {
  return (
    <html lang="en">
      <body>
        <div style={{ padding: "2rem", textAlign: "center" }}>
          <h2>Something very bad happened</h2>
          <p>{error.message}</p>
          <button onClick={() => reset()}>Try Again</button>
        </div>
      </body>
    </html>
  )
}
```

**A few important things:**

1. **`'use client'`** — required because error handling is client-side
2. **`<html>` and `<body>`** — you must write these — because this renders in place of the root layout. The layout isn't available, so you provide it yourself
3. **`error.digest`** — in production, Next.js hashes errors (a string identifier). It's an optional property, you can display the digest for debugging

## CODE — Route-Level `error.tsx` (Basic)

This is the concept from 1.4 — now at scale for one route:

**File:** `app/photo/[id]/error.tsx` — new file

```tsx
'useuse client'

export default function PhotoError({
  error,
  reset,
}: {
  error: Error & { digest?: string }
  reset: () => void
}) {
  return (
    <div style={{ padding: "2rem", textAlign: "center" }}>
      <h2>Photo could not be loaded</h2>
      <p>{error.message}</p>
      <button onClick={() => reset()}>Try Again</button>
    </div>
  )
}
```

You can also create `app/photo/error.tsx` — it would cover all `/photo/*` routes. If both exist, `photo/[id]/error.tsx` catches first (smallest boundary).

---

## CONCEPT — Error Recovery UX (Production vs Development)

Errors look different in development and production:

**Development:**
- Next.js shows a **red error overlay** (detailed error, stack trace)
- `error.tsx` also renders — but the overlay appears on top
- Useful for debugging

**Production:**
- No overlay — only the `error.tsx` UI is shown
- Show the user a friendly message — "Something went wrong" + retry button
- You can show `error.digest` (hash identifier — useful for support team)

**So keep `error.tsx` clean in production:**
- Friendly message (don't show technical details to the user)
- Retry button (`reset()`)
- Error logging (server-side `console.error(error)` — don't show to user)

## Nutshell

In the error hierarchy, **start from the smallest boundary, work up to the largest.** Each folder's `error.tsx` catches errors for that folder + its children. `global-error.tsx` lives in the root `app/` folder — it's the last resort when the root layout crashes. In development, Next.js shows the overlay; in production, only the `error.tsx` UI shows. Every error boundary should have a friendly message + retry button (`reset()`) — don't show technical details to the user.

---

## What It Is NOT

- **`global-error.tsx` = "catches every error" is NOT true.** It only catches **root layout crashes.** Route-level errors are caught by that route's `error.tsx`.
- **`error.tsx` = "fixes the error" is NOT true.** It **gracefully handles** the error — shows the user a friendly message. The actual fix must be in the code.
- **`reset()` = "the error is fixed" is NOT true.** It just **re-renders** the page. If the error was transient (network), it might resolve. A permanent error will come right back.
- **Error boundaries = "try-catch" is NOT true.** Error boundaries are class components that catch render errors. Next.js' `error.tsx` is a wrapper for them — you don't need to write a class yourself.
