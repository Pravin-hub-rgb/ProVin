# Add Comment — POST with Server Action (3.3.1)

## Where We Left Off

In the previous topic (3.3), you learned about Server Actions — the concept that a form can directly call a server function without needing an API route. You saw the basic shape: `"use server"` directive, a function that takes `FormData`, and a form with `action`.

But that was just theory. The example didn't actually save a comment — it just returned a message. Now we'll apply Server Actions to our real comments project, connecting them to the existing data layer in `lib/comments.ts`.

This topic focuses on converting **POST (add comment)** to a Server Action and adding user feedback with `useActionState` and toast notifications.

## Current Code — How POST Worked Before

Let's see how POST was implemented in 3.1. Two pieces of code:

1. **Route Handler** — on the server side, `app/api/comments/route.ts`
2. **Client fetch** — in `app/components/CommentForm.tsx`

```tsx
// app/api/comments/route.ts — POST from 3.1
export async function POST(request: Request) {
  const body = await request.json();

  if (!body.text || !body.text.trim()) {
    return NextResponse.json(
      { error: "Comment cannot be empty" },
      { status: 400 }
    );
  }

  const newComment = addComment(body.text);
  return NextResponse.json(newComment, { status: 201 });
}
```

```tsx
// app/components/CommentForm.tsx — handleSubmit from 3.1
const handleSubmit = async (e: React.FormEvent) => {
  e.preventDefault();

  const res = await fetch("/api/comments", {
    method: "POST",
    body: JSON.stringify({ text }),
    headers: { "Content-Type": "application/json" },
  });

  if (!res.ok) {
    const error = await res.json();
    console.error("Error:", error.error);
    return;
  }

  const newComment = await res.json();
  console.log("Added:", newComment);
  setText("");
};
```

Notice the gap between these two pieces: the client sends a JSON string that the server parses back into an object. That's the **extra layer** that Server Actions eliminate.

## Step 1: Create the Server Actions File — `app/actions.ts`

In 3.3, we learned Server Actions go in a separate file with the `"use server"` directive. Let's create it now, but with **real logic** — we'll call the existing `addComment()` from `lib/comments.ts`.

**File:** `app/actions.ts`

```tsx
// app/actions.ts — NEW FILE
"use server";

import { addComment } from "@/lib/comments";

export async function addCommentAction(formData: FormData) {
  const text = formData.get("comment") as string;

  // Validation — don't allow empty comments
  if (!text || !text.trim()) {
    return; // empty comment — do nothing
  }

  // This is the same function from lib/comments.ts (3.1)
  addComment(text);
}
```

**Key differences** from the old route handler:

| Route Handler (3.1) | Server Action (now) |
|---|---|
| Data comes from `request.json()` | Data comes from `formData.get("comment")` |
| Response via `NextResponse.json()` | Returns nothing — just calls the function |
| Must set status codes | No status codes needed |

**Notice: the action returns nothing.** This is intentional — when you use `action={...}` directly on a form (without `useActionState`), TypeScript expects the action to return `void`. If you try to return an object, you get a TypeScript error.

**Server vs Client — what changed?** The form is now connected to the server (via Server Action). But the list (`ShowComments.tsx`) is still a client component — it fetches data in `useEffect([])` and never re-fetches after mount.

This means: after submitting, the new comment gets saved to `comments.json` but **won't appear in the list**. This is expected — not a bug. To fix the list, we need two things:

1. **The list data should come from a Server Component** — so every page render gets fresh data
2. **After mutation, tell Next.js to re-render** — with `revalidatePath`

Both of these will be covered in 3.3.2.

For now, focus on the mutation — verify the comment gets saved to the JSON file. The list update is a deliverable for 3.3.2.

**`addComment` — where did it come from?** The same function created in 3.1's `lib/comments.ts` — reads from `comments.json`, adds the comment, writes back. **The data layer didn't change at all** — only the way it's called changed.

## Step 2: Connect the Form — Remove fetch, Add action

Now let's update `CommentForm.tsx` — remove the `handleSubmit` and `fetch` call, replace with `action={addCommentAction}`:

**File:** `app/components/CommentForm.tsx`

```tsx
// app/components/CommentForm.tsx — UPDATED (fetch removed)
```

**What changed:**
1. **`handleSubmit` and `fetch` removed** — the form now calls the Server Action directly via `action={addCommentAction}`. No API route, no JSON.stringify, no headers.
2. **`name="comment"`** — matches `formData.get("comment")` in the action
3. **`value`/`onChange` removed** — the form is now uncontrolled; the browser manages the input value
4. **`useState` removed** — no longer needed since we're not tracking text in React state

**User feedback? There is none.** The action returns `void` — there's no loading state, no success message. The comment gets saved, but the user has no idea. We'll fix this now — we can't leave it like this for another chapter.

Let me be direct: this is a deliberate **regression**. In 3.1/3.2, we had `useState` for a "Comment added!" message and loading state. We just removed that. We're fixing it immediately in Step 4 with `useActionState` and toast. Don't wait — this needs to be resolved in this same file.

## Step 4: Add User Feedback — useActionState + Toast

Now for the missing piece: user feedback. When you submit a form, the user should know:
1. Something is happening (pending/loading state)
2. It worked (success message)
3. It failed (error message)

In 3.1/3.2, we managed this manually with `useState`. Server Actions give us `useActionState` — a React hook built specifically for this purpose, plus we'll add **toast notifications** for modern UX feedback.

### useActionState — Connect Actions to State

Think of `useActionState` as `useState` but for form actions. Where `useState(0)` gives you a state value, `useActionState` gives you the action's return value:

```tsx
const [state, formAction, isPending] = useActionState(action, initialState);
```

Three parts:

1. **`action`** — the Server Action to call. `useActionState` will call this when the form submits.
2. **`initialState`** — the starting value before any submission. Like passing `0` to `useState(0)`.
3. **Three return values:**
   - `state` — the action's return value. Starts as `initialState`, updates after each submission.
   - `formAction` — a wrapped version of your action. This goes on the form's `action` attribute.
   - `isPending` — `true` while the action is running, `false` when done. Use this for loading states.

### Update the Action to Return State

For `useActionState` to work, the action must return a value. Let's update `addCommentAction`:

```tsx
// app/actions.ts — UPDATED
"use server";

import { addComment } from "@/lib/comments";

export type FormState = {
  success: boolean;    // true or false
  message: string;     // text message
};

export async function addCommentAction(
  prevState: FormState,
  formData: FormData
): Promise<FormState> {
  const text = formData.get("comment") as string;

  if (!text || !text.trim()) {
    return { success: false, message: "Comment cannot be empty!" };
  }

  addComment(text);

  return { success: true, message: "Comment added!" };
}
```

**What's new:**
- **`FormState` type** — defines what the return value looks like: `success` (boolean) and `message` (string)
- **`prevState: FormState`** — first argument. `useActionState` calls actions with `(prevState, formData)`. We don't use `prevState` here (we don't need previous state to add a comment), but it must be in the signature.
- **Returns `FormState`** — the action now returns `{ success: true, message: "..." }` instead of `void`

### formAction — The Adapter That Makes It Work

Why `action={formAction}` instead of `action={addCommentAction}`? Here's the key detail:

A regular `<form action={fn}>` calls `fn(formData)` — **one argument only**. But `useActionState` actions expect **two arguments**: `(prevState, formData)`.

`formAction` is a special adapter that bridges this gap: when the form submits, it automatically provides the `prevState` (or `initialState`) and calls `addCommentAction(prevState, formData)`.

> **Memory trick:** `action={addCommentAction}` = fire and forget, no feedback. `action={formAction}` = action fires, result comes back to `state`.

### Toast — Modern Notification System

For displaying messages, we'll use **toast notifications** — small popups that appear briefly in a corner of the screen. We'll use the `sonner` library — it's lightweight and works perfectly with React 19.

Install and set it up:

```bash
npm install sonner
```

Then add the `<Toaster />` component to your layout:

```tsx
// app/layout.tsx
import { Toaster } from "sonner";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        {children}
        <Toaster position="bottom-right" />
      </body>
    </html>
  );
}
```

`<Toaster />` is a provider — whenever you call `toast.success()` or `toast.error()` anywhere in your app, the notification appears there. One setup, works everywhere.

### Build the Component — All Three Pieces Together

Here's the complete `CommentForm.tsx` with `useActionState`, toast, and loading states:

```tsx
// app/components/CommentForm.tsx — COMPLETE
"use client";

import { useEffect, useActionState } from "react";
import { toast } from "sonner";
import { addCommentAction, FormState } from "../actions";

const initialState: FormState = {
  success: false,     // nothing has happened yet
  message: "",        // no message yet
};

export default function CommentForm() {
  const [state, formAction, isPending] = useActionState(
    addCommentAction,
    initialState
  );

  // Watch for state changes and trigger toast
  useEffect(() => {
    if (state.message) {
      if (state.success) toast.success(state.message);
      else toast.error(state.message);
    }
  }, [state]);

  return (
    <form action={formAction} className="mb-4">
      <input
        name="comment"
        placeholder="Write a comment..."
        className="border p-2 rounded mr-2"
        disabled={isPending}
      />
      <button
        type="submit"
        disabled={isPending}
        className="bg-blue-500 text-white px-4 py-2 rounded disabled:bg-gray-400"
      >
        {isPending ? "Adding..." : "Submit"}
      </button>
    </form>
  );
}
```

**How it all works together:**
1. User types a comment and clicks "Submit"
2. `isPending` becomes `true` → button shows "Adding..." and input disables
3. Server Action executes with `(prevState, formData)`
4. Action returns `{ success: true, message: "Comment added!" }`
5. `state` updates → `useEffect` fires → `toast.success("Comment added!")` shows
6. `isPending` becomes `false` → button returns to normal

> **Note on `useFormState`:** In older React versions, you might see `useFormState` imported from `react-dom`. In React 19 (used by Next.js 15), this was renamed to **`useActionState`** from React, and it adds `isPending` as a bonus. Make sure to use `useActionState` from `react`, not `useFormState` from `react-dom`.

### Toast vs Inline Message — When to Use Which?

| Type | How it looks | When to use |
|------|-------------|-------------|
| Toast (`sonner`) | Small popup in corner | Global notifications, auto-dismisses, modern UX |
| Inline message (`<p>`) | Text inside the form | Simple, single location, no library needed |

We're using toast because the same pattern will be reused for delete and edit operations later.

## Step 5: Why List Doesn't Update — Server vs Client Reality Check

Let me address the confusion head-on: **the form submits successfully (data is saved), but the list doesn't update.** This is not a bug — it's a consequence of how the pieces are connected.

**Current setup:**
- **Form (`CommentForm`)** — connected to the server via Server Action (data gets saved to file)
- **List (`ShowComments`)** — still a client component that fetched data in `useEffect([])` on mount (never re-fetches)

The form changes data on the server. But the list has no idea data changed — it has the old state from when it first mounted.

**This gets fixed in two parts, both coming in 3.3.2:**
1. List data comes from a **Server Component** — `page.tsx` calls `getAllComments()` directly and passes data as props
2. After mutation, `revalidatePath("/")` tells Next.js to re-render

We'll explore this in detail in the next topic.

## Summary of Changes

| Aspect | Before (3.1/3.2) | Now (3.3.1) |
|---|---|---|
| **Server code** | `app/api/comments/route.ts` POST handler | `app/actions.ts` `addCommentAction` |
| **Client code** | `fetch("/api/comments", { method: "POST", ... })` | `<form action={formAction}>` + `useActionState` |
| **Feedback** | `useState` for messages | `useActionState` (`isPending`) + `sonner` toast |
| **Data format** | JSON string travels over network | Direct function parameters via FormData |
| **Refresh** | Manual reload (3.1) | Not working yet — fix in 3.3.2 |

**Boilerplate eliminated:** the POST route handler function on the server, `fetch()` + method + headers + JSON.stringify on the client, `request.json()` on the server, and manual `useState` for feedback messages. Replaced with `action={formAction}` + two hooks.

## In Your Own Words

<details>
<summary>Question 1: Why can't you use `useState` inside a Server Action?</summary>
<p><strong>Answer:</strong> Server Actions run on the server during form submission — they don't participate in React's render cycle on the client. `useState` is a React hook that only works inside Client Components during rendering. Server Actions execute outside of component rendering.</p>
</details>

<details>
<summary>Question 2: What does `useActionState` return and how do you use each part?</summary>
<p><strong>Answer:</strong> It returns `[state, formAction, isPending]`: `state` holds the action's return value (starts as `initialState`), `formAction` is what goes on the form's `action` attribute (not the raw action function), and `isPending` is a boolean for loading states.</p>
</details>

<details>
<summary>Question 3: Why do you need `formAction` instead of passing `addCommentAction` directly to the form?</summary>
<p><strong>Answer:</strong> `<form action={fn}>` only calls `fn(formData)` — one argument. But `useActionState` actions expect `(prevState, formData)` — two arguments. `formAction` is the adapter that bridges this gap by automatically providing `prevState`.</p>
</details>

<details>
<summary>Question 4: Why must `action` return the same type as `initialState`?</summary>
<p><strong>Answer:</strong> `useActionState` uses `initialState` as the type for both the starting value and the action's return value. If they don't match, TypeScript can't guarantee type safety — you'd get errors when accessing properties on `state`.</p>
</details>

## Common Mistakes

- **`"use server"` directive omitted** — without it, the function runs on the client
- **Using browser APIs in Server Actions** — `localStorage`, `window`, and `document` don't exist on the server
- **Not exporting the function** — you need `export async function`
- **Putting `"use server"` in the wrong place** — it goes at the top of the file or above a function declaration
- **Returning an object from a direct `action={fn}` form** — without `useActionState`, forms expect `void` return type; use `useActionState` if you need to return state
