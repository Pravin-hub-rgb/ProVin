## Side-by-Side Comparison

### File Structure

| Route Handler Version | Server Actions Version |
|---|---|
| `app/api/reviews/route.ts` — GET + POST | `app/actions.ts` — all Server Actions |
| `app/api/reviews/[id]/route.ts` — GET + PUT + DELETE | *(deleted — no route files needed)* |
| 2 route files | 1 actions file |

### Create (Add Review)

| Route Handler | Server Actions |
|---|---|
| **Client:** `useState` for text, rating, pending, message | `useActionState` provides state automatically |
| **Client:** `<form onSubmit={handleSubmit}>` with manual `e.preventDefault()` | `<form action={formAction}>` — automatic |
| **Client:** `axios.post("/api/reviews", data)` with `try/catch` | Direct — no axios, no try/catch |
| **Client:** `window.location.reload()` | `revalidatePath("/reviews")` in action |
| **Server:** API route with `request.json()`, validation, `NextResponse.json()` | Server Action with `formData.get()`, validation, return object |

### Read (List Reviews)

| Route Handler | Server Actions |
|---|---|
| Client: `axios.get("/api/reviews?productId=1")` in `useEffect` | Server Component: `getReviewsByProduct(1)` direct call |
| `useState` for reviews array | No state needed |
| `loading` state while fetching | No loading — data ready at render |
| `"use client"` required | Server Component (no `"use client"`) |

### Update (Edit Review)

| Route Handler | Server Actions |
|---|---|
| Client: `useState` × 4 (review, editing, editText, editRating) | Client: `useState` × 1 (editing only) |
| `useEffect` + `axios.get()` to load review | Server Component reads directly |
| `axios.put("/api/reviews/{id}", data)` | `action={formAction}` |
| Controlled inputs (`value` + `onChange`) | Uncontrolled (`defaultValue`) |
| `window.location.reload()` | `revalidatePath` (both detail + list pages) |

### Delete Review

| Route Handler | Server Actions |
|---|---|
| `onClick={handleDelete}` + `axios.delete()` | `<form action={formAction}>` + hidden input |
| `useState` for pending | `isPending` from `useActionState` |
| `window.location.reload()` | `revalidatePath("/reviews")` |
| `window.confirm()` in handler | `onSubmit` with `e.preventDefault()` |

## Code Volume Comparison

### Route Handler — Create Form

```tsx
// ~35 lines for the component
"use client";
import { useState } from "react";
import axios from "axios";

export function ReviewForm({ productId }) {
  const [text, setText] = useState("");
  const [rating, setRating] = useState(5);
  const [pending, setPending] = useState(false);
  const [message, setMessage] = useState("");

  const handleSubmit = async (e) => {
    e.preventDefault();
    setPending(true);
    setMessage("");
    try {
      await axios.post("/api/reviews", { productId, text, rating });
      setMessage("Review added!");
      setText("");
      setRating(5);
      window.location.reload();
    } catch (err) {
      setMessage("Failed to add review");
    } finally {
      setPending(false);
    }
  };
  // ... JSX for form with controlled inputs
}
```

**States to manage: 4** (`text`, `rating`, `pending`, `message`)

### Server Action — Create Form

```tsx
// ~20 lines for the component
"use client";
import { useActionState } from "react";
import { addReviewAction } from "../actions";

const [state, formAction, isPending] = useActionState(addReviewAction, initialState);

<form action={formAction}>
  <input type="hidden" name="productId" value={productId} />
  <textarea name="text" />
  <select name="rating">...</select>
  <button disabled={isPending}>{isPending ? "Adding..." : "Submit"}</button>
  {state.message && <p>{state.message}</p>}
</form>
```

**States to manage: 0** — all handled by `useActionState`

## When to Use Which

### Use Route Handlers When

| Scenario | Why |
|---|---|
| **External clients** (mobile app, third-party website) | REST APIs are universally accessible |
| **API as a product** (exposing data to other teams/projects) | Industry standard, documented with OpenAPI |
| **Complex operations** (file upload, payment processing) | Need full HTTP control, streaming, custom headers |
| **Caching strategies** (CDN caching, edge functions) | Fine-grained control over cache headers |
| **Debugging** (need to see network requests) | All requests show in browser's Network tab |
| **Existing REST ecosystem** (React Query, SWR, mobile clients) | Already built for REST APIs |

### Use Server Actions When

| Scenario | Why |
|---|---|
| **Next.js-only app** (no external API consumers) | No need for REST overhead |
| **Simple forms** (comments, feedback, settings) | Zero boilerplate |
| **Rapid prototyping** (need it built fast) | Less code = faster iteration |
| **Type safety between server/client** | TypeScript flows through automatically |
| **Automatic revalidation** | `revalidatePath` replaces manual refreshes |
| **Built-in pending states** | `useActionState` provides `isPending` |

### Decision Tree

```
Do external clients need access to this data?
├── Yes → Route Handler (REST API)
└── No → Is this a simple form submission?
    ├── Yes → Server Action
    └── No → Is it complex (uploads, payments)?
        ├── Yes → Route Handler
        └── No → Server Action is fine
```

### What Stayed the Same

- **`lib/reviews.ts`** — The data layer never changed across versions
- **`lib/reviews.json`** — The seed data stayed the same
- **Business logic** — Validation rules, ID generation, file I/O — all identical

### What Changed

- **How data is accessed** — Server Component direct call vs Client Component via API
- **How mutations work** — Server Action direct call vs axios to an API route
- **State management** — `useActionState` vs multiple `useState` calls
- **Refresh mechanism** — `revalidatePath` vs `window.location.reload()`

## Key Takeaways

1. **Server Components read data** — they call data layer functions directly. No API route needed.
2. **Server Actions write data** — forms with `action={serverAction}` call server functions directly. No axios needed.
3. **`useActionState` eliminates manual state** — pending state, return values, and error handling come built-in.
4. **`revalidatePath` replaces manual refresh** — mutations automatically trigger fresh renders.
5. **Uncontrolled inputs simplify forms** — `name` + `defaultValue` replace `value` + `onChange` + `useState`.
6. **Hidden inputs carry hidden data** — pass IDs, product IDs, or any server-only values to actions.
7. **The data layer stays untouched** — whether you use Route Handlers or Server Actions, `lib/reviews.ts` is the same.

## Common Mistakes Checklist

- [ ] Did you forget `"use server"` on the actions file?
- [ ] Did you use `action={addReviewAction}` instead of `action={formAction}`?
- [ ] Did you use `name` on form inputs (not just `value`)?
- [ ] Did you call `revalidatePath` after mutations?
- [ ] Did you await `params` in dynamic routes?
- [ ] Did you use `Number()` to convert string params to numbers?
- [ ] Did you use `useActionState` from `react` (not `useFormState` from `react-dom`)?
- [ ] Did you delete unused route handlers when refactoring?

## In Your Own Words

<details>
<summary>Question 1: If you need both a mobile app and a Next.js web app, which approach do you use?</summary>
<p><strong>Answer:</strong> Route Handlers for the API endpoints (mobile app needs REST), Server Actions for web-only forms (comments, settings). Both can coexist — Route Handlers serve external clients, Server Actions serve the Next.js app's own forms.</p>
</details>

<details>
<summary>Question 2: What's the most important pattern to remember for Server Actions?</summary>
<p><strong>Answer:</strong> Every Server Action follows the same shape: `export async function action(prevState, formData)`, extract with `formData.get("name")`, call the data layer, `revalidatePath("/")`, return `{ success, message }`. On the client: `useActionState(action, initial)` returns `[state, formAction, isPending]`, use `action={formAction}`.</p>
</details>

<details>
<summary>Question 3: Why didn't `lib/reviews.ts` need to change?</summary>
<p><strong>Answer:</strong> The data layer is just functions that read/write a JSON file. Whether a Route Handler or a Server Action calls them doesn't matter — the function signatures and implementations stay the same. This is the power of abstraction: change the interface, not the implementation.</p>
</details>

<details>
<summary>Question 4: What's the relationship between Server Components, Server Actions, and Route Handlers?</summary>
<p><strong>Answer:</strong> Server Components handle reads (call data layer directly). Server Actions handle writes (called by forms). Route Handlers handle external access (REST endpoints). They work together: a Server Component can call `getAllReviews()`, a Server Action can call `addReview()`, and a Route Handler can expose both via HTTP for external clients.</p>
</details>
