# GitHub OAuth Wiring

## Where We Left Off

In 5.5.2 the layout was confirmed: pages render, but the login button is fake, nothing is protected, and the navbar is static. Now the **real auth wiring** — assembling all the 5.4.x pieces into a working project. The GitHub OAuth app was already created in 5.4.1 (Client ID + Secret stored in `.env.local`), and the callback URL `http://localhost:3000/api/auth/callback/github` is already registered — those same credentials work here. ## Step 1 — Environment Variables

In `.env.local` at the project root (same as 5.4.1):

```env
AUTH_SECRET=<output of `npx auth secret`>
AUTH_GITHUB_ID=<your GitHub OAuth client ID>
AUTH_GITHUB_SECRET=<your GitHub OAuth client secret>
```

Generate `AUTH_SECRET` with:

```bash
npx auth secret
```

That writes a random secret into `.env.local`. The two GitHub values come from the OAuth app created back in 5.4.1. If that app no longer exists, return to 5.4.1 Steps 1–2 — it's a 5-minute setup.

## Step 3 — Layout: Wrap with `SessionProvider`

The 5.4.2 pattern: client components receive session via Context. The layout was built statically in 5.5.2; now it's wrapped (new parts marked `// NEW`):

**File:** `app/layout.tsx` (update)

```tsx
import type { Metadata } from "next";
import "./globals.css";
import Navbar from "./components/Navbar";
import { SessionProvider } from "next-auth/react";      // NEW: import

export const metadata: Metadata = {
  title: "Member Dashboard",
  description: "My Account App",
};

export default function RootLayout({
  children,
}: Readonly<{
  children: React.ReactNode;
}>) {
  return (
    <html lang="en">
      <body>
        <SessionProvider>                                {/* NEW: wrap */}
          <Navbar />
          {children}
        </SessionProvider>                                {/* NEW: wrap */}
      </body>
    </html>
  );
}
```

`SessionProvider` is the bridge that lets Client Components call `useSession()` — the split from 5.4.2 between server `auth()` and client access. It lives at the root so any component can reach it.

## Step 4 — Navbar: Static → Session-Aware

Replace the static navbar from 5.5.2 with the session-aware version from 5.4.2. Full current state (new parts marked `// NEW`):

**File:** `app/components/Navbar.tsx` (update)

```tsx
"use client";                                            // NEW

import { useSession, signIn, signOut } from "next-auth/react";   // NEW: imports

export default function Navbar() {
  const { data: session, status } = useSession();        // NEW

  return (
    <nav style={{ display: "flex", justifyContent: "space-between", padding: 12 }}>
      <span style={{ fontWeight: "bold" }}>MemberHub</span>
      <div style={{ display: "flex", gap: 12, alignItems: "center" }}>
        <a href="/">Home</a>
        <a href="/dashboard">Dashboard</a>
        <a href="/profile">Profile</a>
        {status === "loading" && <span>Loading...</span>}             {/* NEW */}
        {status === "unauthenticated" && <a href="/login">Login</a>}  {/* NEW */}
        {status === "authenticated" && (                              {/* NEW */}
          <button onClick={() => signOut()}>Logout ({session?.user?.name})</button>
        )}
      </div>
    </nav>
  );
}
```

What changed:

- `"use client"` — required so the component can use `useSession` and `signOut` in the browser.
- Static "Login" link → **three states**: `loading`, unauthenticated (Login link), authenticated (Logout button + the GitHub name).
- Logout calls `signOut()` — no logout existed in 5.5.2.
- `session?.user?.name` — the GitHub-provided name, shown only when authenticated.

## Step 5 — Login Page: Real Sign In

The 5.5.2 fake button becomes a real `signIn("github")` action — from 5.4.1. One addition beyond the demo: a signed-in user who lands on `/login` is sent to `/dashboard`. Full current state (new parts marked `// NEW`):

**File:** `app/login/page.tsx` (update)

```tsx
import { signIn, auth } from "@/auth";                    // NEW: imports
import { redirect } from "next/navigation";               // NEW: import

export default async function LoginPage() {
  const session = await auth();                           // NEW
  if (session) {                                          // NEW
    redirect("/dashboard");                               // NEW
  }

  return (
    <main>
      <h1>Sign In</h1>
      <form
        action={async () => {                             // NEW: form + action
          "use server";
          await signIn("github");
        }}
      >
        <button type="submit">Sign in with GitHub</button>
      </form>
    </main>
  );
}
```

`signIn("github")` triggers the full OAuth handshake: GitHub redirect → approval → callback → token → profile → session. The `auth()` pre-check keeps a signed-in user off the login page (and is also reinforced by `proxy.ts` in Step 7).

## Step 6 — `(protected)` Route Group: Lock Down Dashboard + Profile

From the 5.5.1 plan: dashboard and profile share one protected layout. Time to move them into a route group:

```bash
mkdir app/(protected)
# move app/dashboard/* -> app/(protected)/dashboard/
# move app/profile/*  -> app/(protected)/profile/
```

**What does the folder move mean?** A route group (Batch 1) — the parentheses mean the folder is **organization only**, invisible in the URL. `/dashboard` still resolves to `/dashboard`; it's just that the file now lives at `app/(protected)/dashboard/page.tsx`, and there's a parent layout to share.

**File:** `app/(protected)/layout.tsx` (new — the 5.4.3 check, now at group level)

```tsx
// app/(protected)/layout.tsx
import { redirect } from "next/navigation";
import { auth } from "@/auth";

export default async function ProtectedLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const session = await auth();
  if (!session) {
    redirect("/login");
  }
  return <>{children}</>;
}
```

Same guard as 5.4.3, now applying to **both** dashboard and profile at once. Any new protected page dropped into the group inherits protection automatically — that's the group's payoff.

## Step 7 — `proxy.ts`: Routing

The routing-level proxy from 5.4.3 — redirect a signed-in user away from `/login`. Copying the final version (5.4.3 Stage 3) — the `auth()` wrapper, the `req.auth` routing rule, and the `matcher`:

**File:** `proxy.ts` (project root — new)

- `auth()` wrapper injects the session into `req.auth`.
- Rule: `if (isLoggedIn && isLoginPage)` → redirect to `/dashboard`.
- `config.matcher` keeps it off static assets.

Not enforcing auth here — that's the layout from Step 6 (the CVE-2025-29927 rule from 5.4.3). `proxy.ts` is routing-only.

Build output shows `ƒ Proxy (Middleware)` and dashboard/profile as `ƒ (Dynamic)` — the server-component signature from 5.4.3.

## What It Is NOT

- **Dynamic data yet.** Dashboard and profile still show hardcoded "Pravin" data — the wiring makes pages *secure* and *session-aware*, not *data-populated*. Real identity arrives in 5.5.4.
- **Login implying correct profile data.** Sign-in works, but the displayed name/bio is still hardcoded — 5.5.4 swaps in `auth()` and the data layer.
- **Route group as a hidden/secure route.** `(protected)` is organization only; the URL doesn't change. Security is the `auth()` check in the group's layout, not the group's existence.

## Common Mistakes

- **Forgetting to fix relative imports after moving pages** into `(protected)/`. Using the `@/` alias avoids this.
- **Creating a page *inside* the group** (e.g. `app/(protected)/page.tsx`). A group doesn't define its own route — pages belong under `app/(protected)/dashboard` etc., and `/dashboard` resolves naturally.
- **Putting auth enforcement in `proxy.ts`.** Keep the proxy routing-only ("logged-in + `/login` → dashboard"). Don't make it block `/dashboard` — that's the layout's job, and it's what CVE-2025-29927 teaches.
- **Not restarting the dev server after `.env.local` changes.** Next reads env at startup — edit the file, then restart `npm run dev`.

## Nutshell

Auth wiring sequence: env vars (`AUTH_SECRET` + GitHub credentials) → root `auth.ts` + `app/api/auth/[...nextauth]/route.ts` → wrap the root layout with `SessionProvider` → make `Navbar` session-aware (loading / sign-in / sign-out) → make `/login` a real `signIn("github")` form with a signed-in redirect → move dashboard and profile into the `(protected)` route group and add the shared layout's `auth()` + redirect → add the routing-only `proxy.ts`. Pages are now secure and session-aware.

## In Your Own Words

<details>
<summary>1. What does moving dashboard and profile into a `(protected)` group gain you, and what would you do instead without it?</summary>

**Sample Answer:** Without a group, every protected folder needs its own `layout.tsx` — one for dashboard, one for profile, another for each new protected page. The `(protected)` group gives them one shared parent layout: a single `auth()` check covers dashboard **and** profile, and any future protected page dropped in is protected automatically. The route is organization-only — `/dashboard` still resolves normally; nothing about the URL changes.

</details>

<details>
<summary>2. Why does the navbar render three states instead of just a static "Login" link?</summary>

**Sample Answer:** A static link shows the same thing to everyone — a signed-in user seeing "Login" is wrong. The session-aware navbar reflects reality: `loading` (session still resolving), `unauthenticated` (Login link), and `authenticated` (the GitHub name + Logout button). `useSession()` exposes `status` exactly so the UI can render the right action for the current user.

</details>

<details>
<summary>3. Is the `if (session) redirect("/dashboard")` on the login page a duplicate of the proxy's "logged-in → away from `/login`" rule?</summary>

**Sample Answer:** No — different layers. The login-page check runs when the login page renders (server-component level). The proxy runs on every request, before render, for all routes (routing level). Both produce the same redirect, but the proxy acts faster and applies globally. This is defense in depth (the 5.4.3 pattern): the page-level check and the proxy reinforce each other. Note this is UX routing only — auth **enforcement** (blocking `/dashboard` when signed out) lives solely in the layout, never the proxy.

</details>

<details>
<summary>4. Why doesn't the profile page need its own `auth()` check?</summary>

**Sample Answer:** Because the `(protected)` layout wraps it — and every other protected page. The layout's `auth()` runs first; if there's no session it redirects before the profile page is ever rendered. The profile page can't be reached unauthenticated because the layout, a parent of the page, already blocked it. One check at the group level protects all children.

</details>

<details>
<summary>5. Why is dashboard data still hardcoded at the end of a phase where auth wiring is supposedly "done"?</summary>

**Sample Answer:** Because auth wiring (login, protection, session-aware navbar) is one concern and data population is another. This phase makes the app secure and session-aware; it does not yet read the session into the dashboard. That separation is deliberate: if wiring and data were done together and a bug appeared, you couldn't tell which layer was wrong. Next is 5.5.4: replace static identity with `auth()` and static bio with the data layer.

</details>
