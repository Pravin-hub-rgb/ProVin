## Where We Left Off

In the last file (1.3), we built the dynamic `[slug]/page.tsx` — one page catches every blog post via `params.slug`, with `await params` (Next.js 15 Promise) and `notFound()` for unmatched slugs.

## Broader Goal

So far we have routes that render instantly — static pages and dynamic slugs that read from a hardcoded array. But real apps talk to APIs. When the network call is slow, the user sees nothing. When the API fails, the page crashes. When a slug does not match, it breaks silently.

Next.js handles these real-world cases with **three special files**:

**A — `loading.tsx` — Loading State.** Show a spinner/fallback while data loads.

**B — `error.tsx` — Error Boundary.** Catch crashes and offer a "retry" button.

**C — `not-found.tsx` — Custom 404.** Replace the default 404 with your own page.

Plus the navigation toolbox (`next/navigation`) that provides `notFound()`, `redirect()`, and more.

## Manual → Better

In React, you manually wrapped pages in `<Suspense>`, built `ErrorBoundary` class components, and coded catch-all 404 routes. Next.js makes all of this automatic via conventions.

## A — `loading.tsx` — Loading State

### Manual Approach — React Suspense

In React, showing a loading state required manually wrapping the component:

```tsx
// React — manual Suspense wrapper
import { Suspense } from 'react';

<Suspense fallback={<div>Loading...</div>}>
  <BlogPost />
</Suspense>
```

You had to know exactly where to place `<Suspense>`, remember to wrap every async component, and manage fallbacks in multiple places.

### Better — Next.js `loading.tsx`

Drop a single file named `loading.tsx` next to your `page.tsx` — Next.js automatically wraps the page in Suspense with it as the fallback:

```
app/blog/
└── [slug]/
    ├── loading.tsx        →  shows while data loads
    ├── error.tsx          →  shows when something crashes
    └── page.tsx           →  /blog/:slug
```

```tsx
// app/blog/[slug]/loading.tsx
export default function LoadingPost() {
  return (
    <article>
      <h2>Loading post...</h2>
      <p>Just a moment.</p>
    </article>
  );
}
```

### How It Works

When a user navigates to `/blog/my-first-post`:

1. Next.js sees `loading.tsx` exists for this route.
2. It **renders `LoadingPost()` immediately** — no waiting.
3. In the background, Next.js renders `page.tsx` (which may fetch data).
4. Once `page.tsx` finishes, the loading component is **swapped out** for the real content.

You do not need to add `<Suspense>` anywhere. Next.js sees the `loading.tsx` file and wires up the Suspense boundary automatically.

### Loading Shows Only When There Is Async Work

```tsx
// app/blog/[slug]/page.tsx
export default async function BlogPost({ params }) {
  const { slug } = await params;
  const post = await fetch(`https://api.example.com/posts/${slug}`).then((res) => res.json());
  return <h1>{post.title}</h1>;
}
```

- `page.tsx` is `async` and does a `fetch` — it **suspends**. `loading.tsx` shows.
- If `page.tsx` were synchronous (no async work) — `loading.tsx` would **not** show. It only appears when the page actually needs time to prepare content.

### Convention — Same As `page.tsx`

Just like every other special file:
1. Must be named `loading.tsx` (`.js` works too).
2. Must have `export default function Loading()` — a **default export**. Named exports are ignored.

## B — `error.tsx` — Error Boundary

### Manual Approach — React ErrorBoundary

In React, handling errors required a **class component** called an Error Boundary:

```tsx
// React — manual ErrorBoundary (class component)
class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    console.error("Error caught:", error, errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return <h1>Something went wrong.</h1>;
    }
    return this.props.children;
  }
}

// Then wrap every page:
<ErrorBoundary>
  <BlogPost />
</ErrorBoundary>
```

A class component, manual `getDerivedStateFromError`, manual `componentDidCatch` — lots of boilerplate just to catch an error.

### Better — Next.js `error.tsx`

Create `error.tsx` — Next.js wraps your page in an error boundary automatically. When `page.tsx` throws, your error component renders.

```tsx
// app/blog/[slug]/error.tsx
"useuse client";  // IMPORTANT: error.tsx MUST be a Client Component

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div>
      <h2>Something went wrong!</h2>
      <p>{error.message}</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  );
}
```

### The `"use client"` Requirement

**Error boundaries must be Client Components** — add `"use use client"` at the top of `error.tsx`. This is because error boundaries need hooks (like `useState`, `useTransition`) to manage the retry behavior, and hooks only work in Client Components.

```tsx
"use use client";  // required at the top
export default function Error({ error, reset }) { ... }
```

Without `"use client"`, Next.js throws an error during build.

### `error` and `reset` — Props From Next.js

Just like `params` in `page.tsx` and `children` in `layout.tsx`:

- `error` — the error object that was thrown. `error.message` is the readable description (e.g. "Failed to fetch").
- `reset` — a **function** Next.js provides. Calling `reset()` tells Next.js to retry rendering the page.

```tsx
<button onClick={() => reset()}>Try again</button>
```

When the user clicks "Try again," Next.js re-runs the page's rendering — the loading state shows again, then either the content or the error appears again.

### `error` Is an Object — `error.message`

`error` is the JavaScript `Error` object. It has a `.message` property (the error text) and `.digest` (a Next.js internal ID). Show `error.message` to the user, or log it.

```tsx
<p>Error: {error.message}</p>         // "Failed to fetch"
<p>Digest: {error.digest}</p>          // internal ID, optional
```

### `reset` Is a Function — You Call It

`reset` is a function reference — you do **not** access properties on it, you **call** it: `reset()`. It is not `reset()` (a value to display) — it is a handler to invoke on click.

## C — `not-found.tsx` — Custom 404 Page

### Manual Approach — React Router Catch-All

In React Router, a 404 required a catch-all route:

```tsx
// React Router — wildcard 404 route
<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/about" element={<About />} />
  <Route path="*" element={<NotFound />} />  // catch-all
</Routes>
```

You needed to remember to register the `*` route at the end.

### Better — Next.js `not-found.tsx`

In Next.js, create `app/not-found.tsx`. Any unmatched URL renders this page automatically:

```
app/
├── not-found.tsx      →  global 404 (applies to all unmatched routes)
├── layout.tsx
├── page.tsx
└── blog/
    └── [slug]/
        └── page.tsx
```

```tsx
// app/not-found.tsx
export default function NotFound() {
  return (
    <div>
      <h2>404 — Page Not Found</h2>
      <p>The page you are looking for does not exist.</p>
    </div>
  );
}
```

### `not-found.tsx` vs `notFound()`

There are **two ways** to trigger a 404:

1. **`not-found.tsx`** — automatic. When no route matches a URL, Next.js renders this page.
2. **`notFound()` from `next/navigation`** — manual. Inside a page, if data is missing but the URL is valid, call `notFound()` to switch to the 404 page.

```tsx
// app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation';

export default async function BlogPost({ params }) {
  const { slug } = await params;
  const post = posts.find((p) => p.slug === slug);

  if (!post) {
    notFound();  // URL was valid (/blog/xyz) but data not found → show 404
  }

  return <h1>{post.title}</h1>;
}
```

The URL `/blog/xyz` matched the `[slug]` route — but `xyz` is not in our posts array. `notFound()` switches the response to the 404 page (`not-found.tsx`).

## `next/navigation` — The Navigation Toolbox

### What It Is

`next/navigation` is a **module shipped with Next.js**. It is not a third-party package — you install nothing extra. It provides navigation helpers:

- `notFound()` — trigger a 404
- `redirect()` — redirect to another URL
- `useRouter()` — imperative navigation (programmatic)
- `useParams()` — read URL params in a Client Component
- `usePathname()` — get the current URL path
- `useSearchParams()` — read query parameters

```tsx
import { notFound, redirect } from 'next/navigation';
```

### `redirect()` — Send User Elsewhere

When a user should not see the current page, redirect them:

```tsx
// Redirect unauthenticated users
if (!user) {
  redirect('/login');
}
```

`redirect()` does **not return** — calling it immediately sends the user to `/login`. Any code after `redirect()` is unreachable (just like `notFound()`).

### `useRouter()` — Programmatic Navigation

For navigating based on events (form submit, button click):

```tsx
"use client";
import { useRouter } from 'next/navigation';

function SearchButton() {
  const router = useRouter();

  return (
    <button onClick={() => router.push('/search')}>
      Search
    </button>
  );
}
```

`router.push('/path')` navigates — same as clicking a `<Link>`, but triggered by code.

> Note: React Router used `useNavigate()`. Next.js uses `useRouter()`. Same idea, different name.

## Cheat Sheet — Loading, Error, 404

| File | Purpose | Special Rules |
|---|---|---|
| `loading.tsx` | Shows while data loads | `export default`, no `"use client"` needed (Server Component) |
| `error.tsx` | Shows when page crashes | `export default` + `"use client"` at top, receives `{ error, reset }` props |
| `not-found.tsx` | Shows when URL is not found | `export default`, no props |
| `notFound()` | Manually trigger 404 | Import from `next/navigation`, call like a function |
| `redirect(path)` | Manually redirect | Import from `next/navigation`, call like a function |

## In Your Own Words

1. Where does `loading.tsx` go, and when does it show up?

<details>
<summary>Sample Answer</summary>

**Answer:** `loading.tsx` goes **next to `page.tsx`** in the route folder (e.g., `app/blog/[slug]/loading.tsx`). It shows up automatically while the page is loading data — Next.js sees the file and wraps the page in Suspense. It does NOT show for static pages with no async work — only when the page actually suspends while fetching.

</details>

2. Why does `error.tsx` need `"use client"` at the top? What are the `error` and `reset` props?

<details>
<summary>Sample Answer</summary>

**Answer:** `error.tsx` needs `"use client"` because error boundaries require React hooks (for retry logic like `useTransition`), and hooks only work in Client Components. The `error` prop is the error object that was thrown (`error.message` gives the description). The `reset` prop is a function Next.js provides — calling `reset()` asks Next.js to re-render the page from scratch.

</details>

3. What is the difference between `not-found.tsx` and calling `notFound()`? When would you use each?

<details>
<summary>Sample Answer</summary>

**Answer:** `not-found.tsx` is a file that shows up automatically when no route matches a URL (e.g., visiting `/products` when you never created that page). `notFound()` is a function you call **inside a page** when the URL is valid but the data is not found — e.g., `/blog/xyz` matched the `[slug]` route but `xyz` is not a real post. `not-found.tsx` = automatic 404 for unknown URLs; `notFound()` = manual 404 for known URLs with missing data.

</details>

4. In `next/navigation`, what is the difference between `notFound()` and `redirect()`? How do they behave differently?

<details>
<summary>Sample Answer</summary>

**Answer:** `notFound()` triggers a 404 page — it calls `not-found.tsx`. `redirect('/path')` sends the user to a different URL — it navigates programmatically. Both do **not return** — calling either one immediately interrupts rendering. The difference is the outcome: 404 page vs. navigation to another route. Both are imported from `next/navigation` and called like functions.

</details>
