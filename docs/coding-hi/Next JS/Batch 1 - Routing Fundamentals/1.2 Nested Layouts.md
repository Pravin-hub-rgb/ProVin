## Broader Goal

A real web application has a **shared structure**: a header at the top, a navigation sidebar, a footer at the bottom — and then content in the middle that changes per page. In React you duplicated this structure manually. **Layouts** in Next.js solve this: the header, footer, and sidebar persist across page navigation — only the content swaps.

This file covers:

**A — Nested Layouts in Practice.** Create a persistent header and footer that apply to every page automatically — without repeating them.

**B — `children` — The Content Slot.** Understand how `{children}` in a layout gets replaced by the actual page content.

**C — Layout Nesting Depth.** How many levels of layout nesting you can have, and when to use nested layouts vs the root layout.

## Manual → Better

Again: React Router required a manual `Layout` wrapper component. Next.js makes layouts happen automatically through `layout.tsx`.

## A — Nested Layouts in Practice

### The Problem — Duplicated Header/Footer

Imagine every page needs the same header and footer:

```tsx
// WITHOUT layouts — repeated in every page
export default function About() {
  return (
    <div>
      <header>My Site — Header</header>
      <main><h1>About</h1></main>
      <footer>© 2026 My Site</footer>
    </div>
  );
}

export default function Projects() {
  return (
    <div>
      <header>My Site — Header</header>
      <main><h1>Projects</h1></main>
      <footer>© 2026 My Site</footer>
    </div>
  );
}
```

Ten pages → ten copies of `<header>` and `<footer>`. Violates DRY (Don't Repeat Yourself). If you need to change the footer, you edit ten files.

### Manual Approach — React Router Layout

In React Router, you created a separate `Layout` component and wrapped `<Routes>`:

```tsx
// React Router — manual layout wrapping
import { Routes, Route, Link } from 'react-router-dom';

function Layout({ children }) {
  return (
    <>
      <header>My Site — Header</header>
      {children}
      <footer>© 2026 My Site</footer>
    </>
  );
}

export default function App() {
  return (
    <Layout>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/about" element={<About />} />
      </Routes>
    </Layout>
  );
}
```

You wrote the Layout, imported it, wrapped your routes. Manual boilerplate — and you still needed that `<header>` and `<footer>` somewhere. If the layout itself needed data (current user, unread messages), it got awkward fast.

### Better — Next.js `layout.tsx`

In Next.js, create `app/layout.tsx` (or `app/layout.ts` in some setups — `.tsx` if it uses JSX). **Every page in `app/` automatically renders inside this layout.** No wrapping needed — Next.js does it for you.

The layout wraps the page **like a parent**:

```
app/
├── layout.tsx        →  ROOT layout (applies to every page)
├── page.tsx          →  Home content
├── about/
│   └── page.tsx
└── blog/
    └── [slug]/
        └── page.tsx
```

```tsx
// app/layout.tsx — ROOT layout
import Link from 'next/link';
import type { ReactNode } from 'react';

export default function RootLayout({ children }: { readonly children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <header>
          <nav>
            <Link href="/">Home</Link>
            <Link href="/about">About</Link>
            <Link href="/blog">Blog</Link>
          </nav>
        </header>

        {/* The page fills this slot */}
        {children}

        <footer>© 2026 My Site</footer>
      </body>
    </html>
  );
}
```

Now visit `/`, `/about`, `/blog` — the `<header>` and `<footer>` always render. Only `{children}` (the page content) changes.

## B — `children` — The Content Slot

### What `children` Is

The `children` prop is **the part that changes**. It is a slot — like a placeholder that gets filled by whatever page is currently active:

```tsx
// The layout wraps around the page's output
<html>
  <body>
    <header>My Site</header>
    {children}  {/* ← this becomes the page content */}
    <footer>© 2026</footer>
  </body>
</html>
```

When you visit `/about`:
- `children` = whatever `app/about/page.tsx` renders
- The layout stays the same — header and footer are untouched

When you visit `/blog`:
- `children` = whatever `app/blog/page.tsx` renders
- The layout stays the same — header and footer are untouched

**The layout does not re-render on navigation.** It mounts once, and `{children}` swaps out.

### Why `{children}` Works

`children` is just a React prop convention. When Next.js renders a page, it does something like:

```tsx
// Conceptually — Next.js internally does this
<RootLayout>
  <AboutPage />  {/* this becomes children */}
</RootLayout>
```

Your layout receives the page component as the `children` prop. You decide where it goes — usually in the middle, between the header and footer.

### The `ReactNode` Type

```tsx
{ children }: { readonly children: ReactNode }
```

`ReactNode` is TypeScript's type for "anything that can be rendered": a string, a number, an element, an array, `null`, `undefined` — it covers all of them. When you destructure `children` and render it as `{children}`, React knows how to place it in the tree.

**Why `readonly`?** `readonly children: ReactNode` means the children should not be reassigned within the function. It is a best practice — it prevents accidental mutation and helps catch bugs. Omit `readonly` and you will get a lint warning in Next.js.

## C — Layout Nesting Depth

### Root Layout — The Single Shell

There is **exactly one** place where `<html>` and `<body>` live: the **Root Layout** (`app/layout.tsx`). Next.js enforces this — only the root layout gets the full document shell. Nested layouts are just components; they do not contain `<html>` or `<body>`.

```tsx
// ✅ app/layout.tsx — root layout (has html + body)
<html lang="en">
  <body>...</body>
</html>

// ✅ app/blog/layout.tsx — nested layout (NO html/body)
export default function BlogLayout({ children }: { children: ReactNode }) {
  return <section>{children}</section>;
}

// ❌ app/blog/layout.tsx — ERROR: nested layout with html/body
<html lang="en"><body>...</body></html>  // This breaks Next.js
```

### Nested Layouts — Section-Specific Wrappers

You can place a `layout.tsx` **inside any route folder** to create a layout that applies only to that section:

```
app/
├── layout.tsx              →  root layout
├── page.tsx                →  /
├── about/
│   └── page.tsx            →  /about
└── blog/
    ├── layout.tsx          →  applies to /blog, /blog/:slug
    ├── page.tsx            →  /blog
    └── [slug]/
        └── page.tsx        →  /blog/:slug
```

```tsx
// app/blog/layout.tsx — applies only to blog routes
export default function BlogLayout({ children }: { readonly children: ReactNode }) {
  return (
    <section className="blog-section">
      <aside>Sidebar — Recent Posts</aside>
      {children}
    </section>
  );
}
```

Every page under `/blog/` (the blog list, individual posts, etc.) now renders with this sidebar wrapping it.

### How Nesting Stacks

When a nested layout exists, the tree stacks up:

1. **Root Layout** renders (`<html>`, `<body>`, global header, global footer)
2. **Blog Layout** renders inside root (blog-specific sidebar)
3. **Page** renders inside blog layout (the actual post content)

The `children` of each layout becomes the input to the next:

```tsx
// Root renders → BlogLayout renders → BlogPost renders
<RootLayout>          // html, body, header, footer
  <BlogLayout>        // blog sidebar
    <BlogPost />      // the actual page
  </BlogLayout>
</RootLayout>
```

### How Deep Can Nesting Go?

You can nest layouts as deep as you need:

```
app/products/
├── layout.tsx          →  /products/*
├── page.tsx
└── [id]/
    ├── layout.tsx      →  /products/:id/*
    ├── page.tsx
    └── reviews/
        └── page.tsx    →  /products/:id/reviews
```

Each `layout.tsx` adds one more wrapper around the page. There is no hard limit — but in practice, 2-3 levels is common. Beyond that, the tree becomes hard to reason about.

## In Practice — Adding a Persistent Layout

### Applying the Root Layout

For the Blog project, the navigation bar with `<Link>`s goes in the root layout so it appears on every page:

```tsx
// app/layout.tsx
import Link from 'next/link';
import type { ReactNode } from 'react';
import './globals.css';

export default function RootLayout({ children }: { readonly children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <nav>
          <Link href="/">Home</Link> |{" "}
          <Link href="/about">About</Link> |{" "}
          <Link href="/projects">Projects</Link> |{" "}
          <Link href="/contact">Contact</Link> |{" "}
          <Link href="/blog">Blog</Link>
        </nav>
        <main>{children}</main>
      </body>
    </html>
  );
}
```

Now every page automatically has the navigation bar. Click any link → the page swaps, the nav persists.

### Adding a Blog-Specific Layout

```tsx
// app/blog/layout.tsx
import type { ReactNode } from 'react';

export default function BlogLayout({ children }: { readonly children: ReactNode }) {
  return (
    <section>
      <header>
        <h1>My Blog</h1>
      </header>
      {children}
    </section>
  );
}
```

Every blog page now renders with "My Blog" as a sub-header, in addition to the global navigation.

### Testing the Persistence

Navigate between `/about` and `/contact` — the `<nav>` bar at the top does not re-mount. Only the `<main>` content swaps. This is the key behavior that makes client-side navigation feel instant.

## In Your Own Words

1. How does `layout.tsx` solve the DRY problem that React Router's manual Layout had?

<details>
<summary>Sample Answer</summary>

**Answer:** React Router required me to manually create a Layout component, import it, and wrap `<Routes>` in `<Layout>`. Next.js makes this automatic — just create `layout.tsx` and every page in `app/` renders inside it. No import needed, no wrapping. The header/footer in the layout applies to every page without any manual wiring. It is zero-config DRY.

</details>

2. What is `{children}` in a layout, and why is it typed as `ReactNode`?

<details>
<summary>Sample Answer</summary>

**Answer:** `{children}` is the slot where the current page's output gets injected — it is how the page renders *inside* the layout. It is typed as `ReactNode` because children can be anything renderable: a string, element, array, or null. The layout decides where to place `<main>{children}</main>`, and Next.js fills it with whichever page is active.

</details>

3. Where do `<html>` and `<body>` live, and what happens if a nested layout tries to include them?

<details>
<summary>Sample Answer</summary>

**Answer:** `<html>` and `<body>` live **only in the root layout** (`app/layout.tsx`). If a nested layout (like `app/blog/layout.tsx`) tries to include `<html>` or `<body>`, Next.js throws an error — only the root layout is allowed the document shell. Nested layouts are plain wrapper components.

</details>

4. When does a layout re-mount vs. persist? Give one example of each from the blog project.

<details>
<summary>Sample Answer</summary>

**Answer:** A layout **persists** (does not re-mount) when you navigate between pages **within the same layout's scope**. For example, going from `/blog` to `/blog/my-first-post` — the BlogLayout stays mounted. A layout **re-mounts** when navigating to a page **outside its scope**. Going from `/blog/my-first-post` to `/about` — the root layout persists (it is the outermost), but the BlogLayout unmounts since `/about` is not under the blog section.

</details>

Layouts give the site a persistent shell — header, footer, and navigation that survive page-to-page navigation. The next file (1.3) adds **dynamic routes** so individual blog posts work with a single `[slug]` page.
