# Proxy Setup & `NextResponse.next()`

## Where We Left Off

In 4.1 we described the proxy as a request-interception layer — a guard at the building entrance that runs before any page renders. Now we write the **actual file** and verify that it really does run on every request. We will cover: where `proxy.ts` lives, what `NextRequest` and `NextResponse` carry, why `NextResponse.next()` is mandatory, and the first cut of the matcher.

## Where the File Goes

The proxy file goes in the **project root** — next to `next.config.ts`, **outside** `app/`:

```
my-app/
  app/
    page.tsx
    layout.tsx
  proxy.ts        ← here
  public/
  package.json
  next.config.ts
```

Next.js looks for it in exactly this location. Put it inside `app/` and it is silently ignored — no error, it just never runs. This is a framework convention, not something you can configure.

## Step 1 — The Minimal Proxy

Start with a single line:

```ts
console.log("proxy ran!")
```

Run the dev server and open any URL. You will get an error — Next.js is saying it cannot find the proxy function.

Why? The file has no exported function. You must export the handler:

```ts
export function proxy() {
  console.log("proxy ran!")
}
```

Now try again. It works — "proxy ran!" appears in the terminal. (The `GET / 200` lines Next.js prints are its own internal logs, not from the proxy.)

## Step 2 — Reading the Request

Now print the path. Next.js gives the proxy a `request` object typed as `NextRequest`, which carries `nextUrl` — a parsed URL with a `pathname` property:

```ts
import { NextRequest, NextResponse } from "next/server"

export function proxy(request: NextRequest) {
  console.log("proxy ran!", request.nextUrl.pathname)
  return NextResponse.next()
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.svg).*)"],
}
```

Reading line by line:

- `import { NextRequest, NextResponse } from "next/server"` — both come from `next/server`. `NextRequest` is the request's type (URL, headers, cookies — all inside). `NextResponse` builds the output (next / redirect / rewrite).
- `export function proxy(request: NextRequest)` — Next.js calls this on every matched request, passing the full request data. A named export works; `export default` is more common.
- `request.nextUrl.pathname` — the path portion of the URL: `/`, `/about`, `/dashboard`.
- `return NextResponse.next()` — this line is required. So far the proxy only logs. But **it must tell Next.js to continue** — `NextResponse.next()` means "I have checked, forward to the destination." Without it, the request hangs and the page never loads.
- `config.matcher` — tells Next.js which routes the proxy runs on. The regex here is the standard "exclude static assets" snippet copied into most tutorials. 4.3 breaks it down; for now, treat it as "run on everything except Next.js's JS/CSS, optimized images, the favicon, and SVGs."

## Step 3 — Verifying It Runs on Every Route

Start the dev server (`npm run dev`) and open `http://localhost:3000`:

```
proxy ran! /
```

Create a couple more pages:

```tsx
// app/about/page.tsx
export default function About() {
  return <h1>About</h1>
}

// app/dashboard/page.tsx
export default function Dashboard() {
  return <h1>Dashboard</h1>
}
```

Then visit:

```
http://localhost:3000/about
http://localhost:3000/dashboard
```

```
proxy ran! /about
proxy ran! /dashboard
```

Both run. The same file covered every route — that is the proxy's value: one place, every route.

## The Security-Guard Analogy (Reinforcement)

- Guard sees you arrive (proxy ran — the request is somewhere).
- Guard checks you (our current check: just logging).
- Guard says "proceed" (`NextResponse.next()`).
- You enter the building (the page renders).

`NextResponse.next()` is the guard's hand signal saying "go on through."

## What It Is NOT

- **`NextResponse.next()` is not optional** — without a return, the request hangs and the page never loads. Always return something (`next`, `redirect`, or `rewrite`).
- **The proxy does not run on excluded paths** — the matcher decides that. That is why only page requests appear, not static-asset requests.
- **The `request` type annotation is not mandatory** — it compiles without it, but you lose type safety. In a TypeScript project, `NextRequest` is the right type.

## Common Mistakes

- **Putting `proxy.ts` inside `app/`** — Next.js ignores it there. Put it at the project root, next to `next.config.ts`.
- **Forgetting `return NextResponse.next()`** — the request hangs. Every code path must return a response.
- **Confusing the matcher's excluded paths with real traffic** — the standard matcher hides static-asset noise, so the terminal only shows real page requests. That is expected.
- **Forgetting to restart the dev server after `config` changes** — the function body hot-reloads, but `config` (including the matcher) is read at startup. Change the matcher → restart.

## Nutshell

`proxy.ts` lives at the project root. `export function proxy(request: NextRequest)` runs on every matched request; `request.nextUrl.pathname` gives the path; `return NextResponse.next()` is mandatory — "proceed to the destination." The matcher in `config` decides which routes are included; always exclude static assets. One file, every route.

## In Your Own Words

<details>
<summary>1. Where does `proxy.ts` go, and what happens if you put it in the wrong place?</summary>

**Sample Answer:** At the project root, alongside `next.config.ts`, outside `app/`. Next.js only looks there for it. Put it in `app/` and it is silently ignored — no error, it just never runs. This is a convention, not configurable.

</details>

<details>
<summary>2. Why is `return NextResponse.next()` required?</summary>

**Sample Answer:** It is the "continue" signal. The proxy has intercepted the request; Next.js waits for a response. `NextResponse.next()` means "check complete, forward to the destination." Without a return, Next.js never gets a decision — the request hangs and the page never loads.

</details>

<details>
<summary>3. What does `request.nextUrl.pathname` give you?</summary>

**Sample Answer:** The path portion of the URL, excluding the query string and host. For `http://localhost:3000/dashboard?tab=settings`, `pathname` is `/dashboard`. It tells you which route the user is heading to.

</details>

<details>
<summary>4. What does the matcher regex exclude, and why?</summary>

**Sample Answer:** `_next/static`, `_next/image`, `favicon.ico`, and `*.svg` — Next.js's own JS, optimized images, the favicon, and SVG assets. These are framework/browser internals, not user routes, so running proxy logic on them is wasteful and noisy. The matcher keeps the proxy to real page requests.

</details>

<details>
<summary>5. One place, every route — what does that actually buy you?</summary>

**Sample Answer:** Any logic you put in the proxy runs on every request automatically. Want to log every visit? Add one `console.log`. No need to touch each page. That is the centralization guarantee: write once, apply everywhere.

</details>
