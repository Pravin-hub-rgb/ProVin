## Where We Left Off

In 0.3 we learned that Server Components render on the server and produce HTML, while Client Components run in the browser and handle interactivity. But there is a gap: the server sends HTML (no behavior), and the browser needs JavaScript (to handle clicks, state, events). How do those two connect?

## Broader Goal

This file explains **hydration** — the step that turns server-rendered HTML into an interactive page. You will understand:

- Why server HTML is not enough (it is just markup — no behavior)
- How hydration attaches JavaScript to existing HTML
- What a hydration error is and how to avoid it

## Two Things Travel to the Browser

Consider a simple "Like" button:

```tsx
"use use client";
export default function LikeButton() {
  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>Like ({likes})</button>;
}
```

Two separate things are created from this one component, and they travel to the browser by different routes:

**Thing 1 — HTML (for immediate display):**
The server renders this component into HTML — just the markup string: `<button>Like (0)</button>`. This arrives in the browser immediately. The user sees the button right away. But this HTML has no `onClick`, no `useState` — it is just text on a page.

**Thing 2 — JavaScript bundle (for behavior):**
The full JavaScript code (`onClick`, `useState`, everything inside the component) is bundled and sent separately. The browser downloads this a little later.

The browser handles them separately: the HTML is painted immediately (the button is visible), and the JavaScript bundle downloads in the background. When the bundle arrives, React **attaches the event listeners** onto the existing HTML — that is hydration. Until then, the button is visible but **dead**: clicking does nothing, because the handler has not been attached yet.

## HTML Displays, JavaScript Provides Behavior

Before anything else, remember this distinction — it is the key to understanding hydration:

> **HTML only describes what the user sees. JavaScript contains what happens when the user interacts.**

What the server sent for the Like button:

```html
<button>Like (0)</button>
```

This is just markup — a button element with text inside. It cannot "listen" for clicks. HTML is a document, not a program — it does not respond to the user.

JavaScript is what makes things respond. The actual logic lives in the client bundle:

```tsx
"useclient";
export default function LikeButton() {
  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>Like ({likes})</button>;
}
```

The difference:
- What the server sent = `<button>Like (0)</button>` (just the visible markup)
- What is in the client bundle = `useState` + `onClick` handler (the behavior)

So when the page first loads, the button is visible (HTML arrived) but its **behavior is still on the way** (the bundle is downloading).

## Hydration — Attaching Behavior to Existing HTML

**Hydration** is the step where React, running in the browser, takes the HTML the server already produced and **attaches event listeners + component state** to it — so the static markup becomes interactive.

It is important to understand what hydration is **not**: React does **not** throw away the server HTML and start over. The DOM nodes the server created are **adopted** — React reuses them and layers the JavaScript behavior on top. The content does not disappear and reappear.

This is why hydration is not "re-render" — the content is already correct; hydration just adds the interactivity.

## Timeline — What Actually Happens

```
t=0       User opens the page
t=50ms    Server HTML arrives → button "Like (0)" is VISIBLE
           (content is visible immediately — this is the SSR advantage)
t=...     Browser downloads the JS bundle (background)
t=...     React hydrates → onClick + useState attached to the existing button
           → now clicking increases the count
```

### The Gap — Button Is Visible but Unresponsive

Between t=50ms (HTML arrives) and the moment hydration finishes (bundle downloaded and executed), the button is **visible but dead** — clicking does nothing because the `onClick` handler has not been attached yet. This gap exists because the JavaScript that defines the behavior travels in a separate bundle. It is the same tension described in 0.1: SSR gets content to the user faster, but interactivity still requires JavaScript to download and execute.

And one frame showing the old state before the update is normal — React updates the UI after hydration completes, and the animation is expected behavior, not a bug.

## Why Not Throw Away the HTML and Re-render?

You might wonder: *"Why not just discard the server HTML and let React render everything fresh on the client?"* Because the server already built the correct DOM. Throwing it away means:

- The content would flash or change (old HTML disappears, new HTML appears)
- The benefit of SSR — content visible immediately — is completely lost

React **adopts the existing server DOM nodes** and attaches behavior to them. Hydration is a one-time setup step — after that, state updates (`setLikes`) are normal React re-renders, not hydration.

## Hydration Errors — When Server and Client HTML Don't Match

So far we have assumed the HTML the server sends and the tree the client builds are the same. But what happens when they are **not**? React compares them — if they don't match, it throws a **hydration error.**

This is not a bug in React — it is React protecting you. React says: *"You told me the server and client would render the same thing. They are different. I do not know which one is correct, so I am throwing an error."*

### When It Happens

The simplest example: using `Math.random()` or `Date.now()` in the render. The server produces one value, the client produces another:

```tsx
"useclient";
export default function Bad() {
  return <p>{new Date().toString()}</p>;   // server and client produce different values
}
```

But the real-world pattern that causes this most often is reading from `localStorage` or checking `typeof window` to set an initial state:

```tsx
"useclient";
export default function Tabs() {
  // ❌ This is wrong — causes a hydration mismatch
  const savedTab = typeof window !== 'undefined' ? localStorage.getItem('activeTab') : null;
  const [activeTab, setActiveTab] = useState(savedTab ?? "Dashboard");

  return <nav>...</nav>;
}
```

Why is this wrong? Because the server and client disagree on the initial value:

- On the **server**, `window` does not exist → `savedTab` is `null` → `activeTab = "Dashboard"`
- On the **client**, `window` exists → `savedTab = "Coding"` (from localStorage) → `activeTab = "Coding"`

The server rendered "Dashboard", the client renders "Coding" — mismatch.

### Step by Step — What Goes Wrong

| Step | Where | What happens | Result |
|---|---|---|---|
| 1 | Server | `typeof window` → **false** | `savedTab = null` → `activeTab = "Dashboard"` |
| 2 | Server | HTML is rendered | Navbar shows "Dashboard" as active (blue) |
| 3 | Browser | Receives the HTML | You briefly see "Dashboard" active (1ms) |
| 4 | Browser | `typeof window` → **true** | `savedTab = "Coding"` → `activeTab = "Coding"` |
| 5 | Browser | React hydrates | Navbar switches to "Coding" (blue) |
| 6 | React | Compares server HTML vs client tree | **MISMATCH** — error! |

React's reaction: *"The server said 'Dashboard' is active, but the client says 'Coding' is active. These are different. I cannot tell which is correct. Hydration error."*

### This Is Not Your Fault

Everyone learns this pattern first — check `typeof window`, read from localStorage, set initial state. It *feels* correct. But it always causes a hydration mismatch. It is a common trap.

### The Correct Fix — Same Initial State, Update in `useEffect`

The root cause is that **the server and client start from different initial states.** The fix: both start from the **same default value**, and any client-only values are read **after hydration** in `useEffect`:

```tsx
"useclient";
export default function Tabs() {
  // ✅ Same initial value on both server and client
  const [activeTab, setActiveTab] = useState("Dashboard");

  // ✅ Client-only read — runs AFTER hydration
  useEffect(() => {
    const saved = localStorage.getItem('activeTab');
    if (saved) setActiveTab(saved);
  }, []);

  // ✅ Save to localStorage in useEffect too
  useEffect(() => {
    if (typeof window !== "undefined") {
      localStorage.setItem("activeTab", activeTab);
    }
  }, [activeTab]);

  return <nav>...</nav>;
}
```

Now the flow is clean:

| Step | Where | What happens |
|---|---|---|
| 1 | Server | `activeTab = "Dashboard"` |
| 2 | Server | HTML renders → "Dashboard" is blue |
| 3 | Browser | HTML arrives → "Dashboard" is blue |
| 4 | Browser | React hydrates → **EXACT MATCH** ✅ |
| 5 | Browser | `useEffect` runs → reads "Coding" from localStorage |
| 6 | Browser | State updates → Navbar switches to "Coding" (blue) |

**Zero hydration errors.** For one frame the user sees "Dashboard", then it switches to "Coding" — this is completely normal and correct.

### Rules to Remember

- **Server and client must produce the same initial render.** This is the most important rule.
- **Client-only values** (`localStorage`, `window`, `Date`, `Math.random`) must **not** be used to set initial state during render.
- Move client-only reads into `useEffect` — it runs only on the client, and only after hydration.
- React only complains about the **first render**. Updates after that (state changes, props changes) are always fine.

## What It Is NOT

⚠️ **Hydration does not re-render the HTML.** The server already sent correct HTML — hydration attaches behavior to it. The content does not disappear and reappear.

⚠️ **Hydration is not an SEO fix.** The SEO benefit comes from the HTML being in the response in the first place. Hydration just makes the page interactive.

⚠️ **Server Components have no hydration overhead.** Since their JavaScript never reaches the client, there is nothing to attach — they are pure static content, fully optimized.

## Summary

- HTML is just markup (what the user sees) — JavaScript contains behavior (what happens on interaction)
- **Hydration** = React, in the browser, attaches event listeners and state onto the server-generated HTML
- Timeline: HTML visible immediately → bundle downloads → hydration → interactive (gap exists in between)
- React **adopts** existing DOM nodes — it does not throw them away and re-render
- **Hydration error** happens when server HTML and client tree don't match
- **Fix:** same initial state on both sides; move `localStorage` / `window` reads into `useEffect`

## In Your Own Words

1. Why doesn't the server HTML already have `onClick` handlers?

<details>
<summary>Sample Answer</summary>

**Answer:** HTML is a markup language — it describes document structure and content, not behavior. Event handlers like `onClick` are JavaScript, and JavaScript lives in the client bundle (a separate file). The server sends HTML for immediate display; the JavaScript bundle travels separately and is attached later via hydration.

</details>

2. What is hydration, in one sentence?

<details>
<summary>Sample Answer</summary>

**Answer:** Hydration is the step where React, running in the browser, takes the HTML the server already rendered and attaches event listeners and component state to it — turning static markup into an interactive page.

</details>

3. Why are buttons unresponsive for a brief moment after the page first loads?

<details>
<summary>Sample Answer</summary>

**Answer:** The HTML (which shows the button) arrives immediately, but the JavaScript (which contains the `onClick` handler) is in a separate bundle that must download and execute. Until the bundle arrives and hydration runs, the button is visible but has no attached behavior — clicking does nothing.

</details>

4. What is a hydration mismatch, and what is the #1 real-world cause?

<details>
<summary>Sample Answer</summary>

**Answer:** A hydration mismatch occurs when the HTML the server generates and the tree the client builds do not match — React refuses to proceed because it cannot determine which is correct. The #1 cause is using client-only values (like `localStorage` or `typeof window`) to set initial state during render. The server can't access these, so it renders a default, while the client renders the actual value.

</details>

5. How do you fix a hydration mismatch caused by `localStorage`?

<details>
<summary>Sample Answer</summary>

**Answer:** Use the same default value on both server and client (e.g., `useState("Dashboard")`), then move the `localStorage` read into `useEffect` — which runs only on the client, after hydration. This way, the first render matches, and any client-only values are applied afterward as an update.

</details>

6. Why is the hydration overhead zero for Server Components?

<details>
<summary>Sample Answer</summary>

**Answer:** Server Components do not send JavaScript to the client — only HTML. Since there is no client bundle for that component, there is nothing to download, nothing to attach, and no hydration step. The content is already there and does not need to become interactive.

</details>
