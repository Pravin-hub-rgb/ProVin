So far in Module 0 we covered the *why* behind Next.js — SSR, SSG, ISR, Server Components, hydration, caching — but not the *how*. How does a URL like `/about` map to an actual file in your project? How do layouts work? That is the **App Router** — Next.js's file-based routing system.

## Broader Goal

This file establishes the routing mental model:

- How the file system becomes the router (folders = URLs, `page.tsx` = content)
- How dynamic routes work (`[slug]` folders + `params`)
- How layouts wrap pages (`layout.tsx`)
- How Server and Client Components interact within routing

## File-Based Routing — Folder = URL

Next.js routing is direct: **the folder name becomes the URL path, and a `page.tsx` file inside becomes the content for that route.**

**In Next.js:** create a folder (`app/about/`) and add a `page.tsx` file inside it — the `/about` URL is created automatically. No route config, no setup. The folder structure *is* the routes.

```
app/
├── page.tsx          →  /          (home)
├── about/
│   └── page.tsx      →  /about
├── blog/
│   ├── page.tsx      →  /blog
│   └── [slug]/
│       └── page.tsx  →  /blog/:slug  (dynamic)
├── layout.tsx        →  shared layout (wraps pages)
└── not-found.tsx     →  404 page
```

### The Rules

| Concept | File | URL |
|---|---|---|
| Home page | `app/page.tsx` | `/` |
| Static route | `app/about/page.tsx` | `/about` |
| Dynamic route | `app/blog/[slug]/page.tsx` | `/blog/:slug` → `params.slug` |
| Shared layout | `app/layout.tsx` | (wraps every page) |
| 404 page | `app/not-found.tsx` | (handles unmatched routes) |

### Dynamic Route — `params`

```tsx
// app/blog/[slug]/page.tsx
export default async function BlogPost({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;   // the variable from the URL
  return <h1>Blog: {slug}</h1>;
}
```

Compare with React Router: you used `useParams()` to extract `{ slug }`. **The concept is the same** — a dynamic segment produces a variable — but the implementation is different. In Next.js, you create a folder named `[slug]` and the value arrives as the `params` prop. No hook needed.

## Layouts — Shared Wrapper

`app/layout.tsx` is the **root layout** — it wraps every page and renders shared content like headers, footers, and navigation. It works just like the `Outlet` / wrapper pattern from React Router:

```tsx
// app/layout.tsx
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <body>
        <Header />          {/* shown on every page */}
        {children}           {/* the current page content */}
      </body>
    </html>
  );
}
```

You can also create **nested layouts** — `app/blog/layout.tsx` wraps only the blog section, not every page in the app.

## Server Layout + Client Navbar — How They Coexist

A common point of confusion: `layout.tsx` is a **Server Component** by default, but you want to put a `<Navbar />` in it that uses `useState`, click handlers, and interactivity — so it needs `"use client"`. Does that mean the Server Component imports a Client Component? Do they mix?

They coexist, but the boundary is always clear:

```tsx
// components/Navbar.tsx — Client Component
"useuse client";
import { useState } from "react";

export default function Navbar() {
  const [menuOpen, setMenuOpen] = useState(false);
  return (
    <nav onClick={() => setMenuOpen(!menuOpen)}>
      {/* menu logic */}
    </nav>
  );
}
```

```tsx
// app/layout.tsx — Server Component (default, no "use client")
import Navbar from '@/components/Navbar';

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <Navbar />   {/* Client Component — gets a placeholder on the server */}
        {children}
      </body>
    </html>
  );
}
```

Here is what happens, step by step:

| Step | Where | What happens |
|---|---|---|
| 1 | Server | `layout.tsx` renders → HTML is built |
| 2 | Server | `<Navbar />` produces only a **placeholder** in the HTML (a reserved spot) |
| 3 | Server | everything else (`<html>`, `<body>`, `{children}`) renders as full HTML |
| 4 | Browser | HTML arrives — Navbar's spot shows a placeholder |
| 5 | Browser | Navbar's JavaScript bundle downloads |
| 6 | Browser | React hydrates — the placeholder is replaced with the real interactive Navbar |

The server never renders the actual Navbar — only a placeholder. The real Navbar code ships in the client bundle and hydrates in the browser. The boundary is clear: **above `"use client"` is server, below is client.**

### Boundary Direction — One Rule

The `"use client"` directive always applies to the **entire file** it appears in. If `Navbar.tsx` has `"use client"`, then everything in that file — including any components it imports or renders like `<Logo />` or `<Menu />` — is also a Client Component. The boundary is per-file, not per-component.

```tsx
// This entire file is a Client Component
"useclient";
export default function Navbar() {
  return (
    <nav>
      <Logo />      {/* Client — it is below "use client" */}
      <Menu />      {/* Client — same reason */}
    </nav>
  );
}
```

But you can still mix at the page level:

```tsx
// layout.tsx — Server Component (default)
import Navbar from './Navbar';       // Client — has "use client"
import ServerComp from './ServerComp'; // Server — no "use client"

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <Navbar />       {/* Client */}
        <ServerComp />   {/* Server — its HTML is rendered directly */}
        {children}
      </body>
    </html>
  );
}
```

`ServerComp` is a Server Component because `layout.tsx` does not have `"use client"`. Its HTML is generated on the server and sent as real content — no placeholder.

### Passing Server Components as Children (The Safe Pattern)

You cannot import a Server Component directly inside a Client Component (it would pull server code into the bundle). But you **can** pass it as a child prop:

```tsx
// layout.tsx (Server)
import Navbar from './Navbar';
import ServerFooter from './ServerFooter';  // Server Component

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <Navbar>
          <ServerFooter />   {/* passed as children — not imported directly */}
        </Navbar>
        {children}
      </body>
    </html>
  );
}
```

```tsx
// Navbar.tsx (Client)
"useclient";
export default function Navbar({ children }) {
  return (
    <nav>
      <Logo />        {/* Client */}
      {children}      {/* Server — passed as prop, React handles it */}
    </nav>
  );
}
```

This works because `ServerFooter` is not directly imported inside the Client Component — it is passed through `children`. React renders it on the server and sends the result as props.

## Client vs Server in Routing

With the example above, the pattern should be clear: `layout.tsx` and `page.tsx` are **Server Components by default**. They can import and render Client Components (anything with `"use client"`). For navigation between pages, use `<Link>`:

```tsx
import Link from "next/link";

<Link href="/blog">Blog</Link>   {/* smooth client-side navigation, no full reload */}
```

## What It Is NOT

⚠️ **Not every folder becomes a URL.** Special folders like `[slug]` (dynamic segments) and `(group)` (route groups) do **not** appear in the URL. Only normal folders produce routes.

⚠️ **App Router is not React Router with different syntax.** You do not write `<Routes>` / `<Route>` configs. But the concepts carry over — `Link` for navigation, `params` (instead of `useParams()`), nested structure. File-based routing is Next.js's model.

⚠️ **`page.tsx` must be named exactly `page.tsx`.** `about/index.tsx` or `about/Home.tsx` will not work — Next.js only looks for `page.tsx` inside route folders.

## Summary

- **File-based routing** — a folder + `page.tsx` = a URL route (no config needed)
- **Dynamic routes** — `[slug]` folder + `params` prop
- **Layouts** — `layout.tsx` wraps every page (shared header, footer, navigation)
- Server and Client Components mix through `"use client"` boundaries
- `<Link>` provides smooth, client-side navigation between pages

## In Your Own Words

1. How do you create a route for `/about` in the App Router?

<details>
<summary>Sample Answer</summary>

**Answer:** Create a folder `app/about/` and add a `page.tsx` file inside it. The route `/about` is created automatically. No route configuration or router library needed — the folder structure is the router.

</details>

2. How does a dynamic route work in Next.js, and how does it differ from React Router?

<details>
<summary>Sample Answer</summary>

**Answer:** In Next.js, you create a folder with square brackets like `[slug]`, and the URL segment is automatically extracted into the `params` prop (no hook needed). In React Router, you wrote `path="/blog/:slug"` and called `useParams()` to get the value. The concept is the same, but Next.js uses the file system instead of route config.

</details>

3. What does `layout.tsx` do?

<details>
<summary>Sample Answer</summary>

**Answer:** It wraps every page as a shared layout — header, footer, navigation are defined once and appear on all routes. It is like the `Outlet` wrapper pattern from React Router, but automatic. Nested layouts can also be created for specific sections.

</details>

4. How does `<Link>` differ from a plain `<a>` tag?

<details>
<summary>Sample Answer</summary>

**Answer:** `<Link>` performs client-side navigation — it changes the URL and swaps page content without a full page reload. This gives a fast, SPA-like experience. A plain `<a>` tag triggers a full page reload, which is slower and resets scroll position.

</details>
