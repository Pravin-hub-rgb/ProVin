In 0.4 we learned about hydration — how React attaches JavaScript behavior to server-generated HTML. The server sends HTML, the browser downloads JS, and hydration bridges the gap. But we left one question unanswered: **where does the data come from that the server uses to render that HTML?** The server fetches it on every request — or does it cache? That is 0.5.

## Broader Goal

This file explains **Next.js's fetch caching model** — how `fetch()` behaves differently in Next.js compared to React. You will understand:

- What caching means and why it matters
- How `fetch()` is cached by default in Next.js (unlike React)
- When to override the default with `no-store` or `revalidate`
- The trade-off between performance and data freshness

## Caching — The Core Idea

**Cache** = temporary storage that holds a copy of data so it does not need to be recomputed.

**Fetch caching** means: when a Server Component fetches data from an API or database, the result is stored. The next time the same data is requested, Next.js serves the stored copy instead of fetching again.

> **Why it matters:** caching trades freshness for performance. Cached data is faster (no round-trip to the database/API) and reduces server load. But it can go stale — the stored copy may be outdated. You invalidate (refresh) the cache when you know the underlying data has changed.

## Next.js Default Fetch Behavior (App Router)

In React, calling `fetch()` in a component means: fetch fresh data every time the component renders. In Next.js, **`fetch()` inside a Server Component is cached by default.** The first request fetches the data and stores it; subsequent requests get the cached copy.

```tsx
// app/page.tsx — DEFAULT
export default async function Page() {
  const res = await fetch("https://api.example.com/posts");
  const posts = await res.json();
  return <PostList posts={posts} />;
}
```

By default (App Router, Next.js 15+), this `fetch` is **cached** — the first request fetches and stores the data; every request after that gets the cached copy. This enables **static rendering** (SSG, from 0.2) — the HTML is generated at build time and served from cache.

### When You Don't Want to Cache — `no-store`

If the data must be fresh on every request — live stock prices, real-time dashboards, user-specific data — use `cache: "no-store"`:

```tsx
const res = await fetch("https://api.example.com/prices", {
  cache: "no-store",   // always fetch fresh — never cache
});
```

### When You Want Conditional Freshness — `revalidate`

If the data can be cached for a while, then refreshed — product catalogs, blog posts that update occasionally — use `next: { revalidate: 60 }`:

```tsx
const res = await fetch("https://api.example.com/posts", {
  next: { revalidate: 60 },  // cache for 60 seconds, then fetch fresh
});
```

(This is covered in full detail in 0.6 — ISR. Here, we are just introducing the format.)

## Quick Reference — Fetch Options

| Option | What it does | When to use |
|---|---|---|
| Default `fetch()` | Cached (static), generated at build time | Rarely-changing public data (blogs, catalog) |
| `cache: "no-store"` | Always fetch fresh | Live data (prices, real-time updates, user-specific) |
| `next: { revalidate: 60 }` | Cached for 60s, then refresh | Data that updates occasionally (ISR — 0.6) |

## How to Decide — Cache or Not?

A simple rule: **if the data rarely changes and is the same for everyone, cache it.** Think product info, help docs, blog posts — these are perfect for static caching. **If the data is different for each user or must be live (user dashboard, shopping cart, real-time feed), do not cache** — use `no-store` to keep it fresh.

> **The trade-off to always remember:** caching improves speed and reduces backend load, but the data can go stale. `no-store` keeps data fresh but adds load on every request.

## What It Is NOT

⚠️ **Caching is not "static HTML everywhere."** Caching is a pattern — store a response and serve the copy. It applies to both static and dynamic pages. The difference is where and how long the cache lives.

⚠️ **This cache is not the browser's HTTP cache.** The browser cache lives on the client (the user's machine). Next.js's fetch cache lives on the **server** — its purpose is to reduce server/backend load, not to tell the browser what to cache.

⚠️ **`no-store` is not "bad."** It means "always fetch fresh from the source" — which is correct for live or user-specific endpoints. It is not a downgrade; it is the right tool for the right job.

## Summary

- **Caching** = store a copy and serve it again without re-fetching (faster, less backend load, but can go stale)
- In the App Router, `fetch()` is **cached by default** (static at build time)
- `cache: "no-store"` → always fetch fresh (live / per-user data)
- `next: { revalidate: 60 }` → cache for 60 seconds, then refresh (ISR)
- Decision rule: rarely-changing + public → cache; live + per-user → no-store

1. What is caching, and why is it useful for data fetching?

<details>
<summary>Sample Answer</summary>

**Answer:** Caching means storing a copy of fetched data so it does not need to be fetched again on every request. The benefit is performance — the server does not have to call the API or database every time, so responses are faster and backend load is lower. The trade-off is that cached data can become stale.

</details>

2. How does `fetch()` behave inside a Server Component in Next.js — and how was it different in React?

<details>
<summary>Sample Answer</summary>

**Answer:** In Next.js, `fetch()` inside a Server Component is **cached by default** — the first request fetches and stores the data, and subsequent requests serve the cached copy (which enables static generation). In React, `fetch()` always fetched fresh data with no caching — you handled caching manually with libraries like React Query or TanStack Query.

</details>

3. When would you use `cache: "no-store"` vs leaving the default behavior?

<details>
<summary>Sample Answer</summary>

**Answer:** Use `no-store` when the data must be fresh on every request — live stock prices, real-time feeds, user-specific dashboards. Leave the default when the data rarely changes and is public — blog posts, product catalogs, help docs. The default enables static generation; `no-store` forces a fresh fetch each time.

</details>

4. Give one example of stale data and one of live data — which strategy for each?

<details>
<summary>Sample Answer</summary>

**Answer:** A product catalog (rarely changes, same for everyone) → cache it (default fetch, static generation). A user's shopping cart (different per user, changes in real-time) → `no-store` so it is always fresh per request.

</details>
