> **Prefer practicing in the browser?** Use the **[Git Lab](/lab/gitgithub?scenario=capstone-parallel)** simulator. It gives you a split-screen terminal where **Junior Dev** (purple terminal) creates a feature branch, pushes, and opens a PR, while **Senior Dev** (blue terminal) reviews and merges — then they swap roles so both devs practice the full workflow.

Now the real teamwork simulation begins. Both devs work at the same time on different features. This creates a realistic scenario where branches overlap and syncing matters.

**Dev-A's first task: Build the hero section (#1)**

```bash
# On dev-A's machine
git switch main
git pull origin main
git switch -c feature/hero-section
```

Build the hero in `index.html`. Add profile placeholder, name, tagline.

```html
<!-- inside index.html, replace the <div id="app"> content -->
<div id="app">
  <header class="hero">
    <img src="https://via.placeholder.com/100" alt="Profile" class="avatar" />
    <h1>Hi, I'm Dev A</h1>
    <p class="tagline">Builder & learner. Making things on the internet.</p>
  </header>
</div>
```

Add styles to `style.css`:

```css
.hero { text-align: center; margin: 3rem 0; }
.avatar { border-radius: 50%; margin-bottom: 1rem; }
.tagline { color: #666; margin-top: 0.5rem; }
```

Commit, push, PR:

```bash
git add index.html style.css
git commit -m "Add hero section with avatar and tagline"
git push -u origin feature/hero-section
```

Open a PR on GitHub with description: `Builds the hero section with profile avatar, name, and tagline. Closes #1`. Wait for review before merging.

**Dev-B's first task: Build the links section (#2)**

At the same time, dev-B starts their work. They branch off the same main (which still only has the skeleton — hero hasn't merged yet).

```bash
# On dev-B's machine
git switch main
git pull origin main
git switch -c feature/links-section
```

Build the links section:

```html
<!-- inside index.html, after the hero -->
<main class="links">
  <a href="https://twitter.com/yourhandle" class="link-card">Twitter</a>
  <a href="https://github.com/yourhandle" class="link-card">GitHub</a>
  <a href="https://yourportfolio.com" class="link-card">Portfolio</a>
</main>
```

```css
.links { display: flex; flex-direction: column; gap: 1rem; }
.link-card { padding: 1rem; background: #f5f5f5; border-radius: 8px; text-decoration: none; color: #333; text-align: center; }
.link-card:hover { background: #e5e5e5; }
```

Commit, push, PR:

```bash
git add index.html style.css
git commit -m "Add links section with social cards"
git push -u origin feature/links-section
```

Open a PR with: `Builds clickable link cards for social profiles. Closes #2`.

**The state of things now:**

- dev-A's PR #1 (hero) is open, awaiting review
- dev-B's PR #2 (links) is open, awaiting review
- Both branched off the same main at the same time
- Both edited `index.html` and `style.css` — different sections, but conflict potential exists

**Review and merge the hero first:**

As dev-B, review PR #1. Check the "Files changed" tab. It looks good? Approve and merge.

Back on dev-A's machine:

```bash
git switch main
git pull origin main
git branch -d feature/hero-section
```

Now main has the hero section. But dev-B's links branch was created before hero was merged. The links branch is behind main.

---

**In Your Own Words:**

<details>
<summary>1. Why do both devs branch off main at the same time at the start?</summary>

To simulate real parallel work. Both devs start from the same base and work independently.
</details>

<details>
<summary>2. What's the state of dev-B's branch after the hero PR merges but before links is merged?</summary>

It's behind main — it doesn't have the hero section commits. Main is ahead of dev-B's branch.
</details>

<details>
<summary>3. Why link the PR description to the Issue with Closes #1?</summary>

So the Issue auto-closes when the PR merges, creating a clean audit trail.
</details>
