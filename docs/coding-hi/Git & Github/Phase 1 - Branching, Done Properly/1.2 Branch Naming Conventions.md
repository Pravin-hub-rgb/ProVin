You know you should branch for everything. Next question: what do you name the branch?

When you're working alone, you can name a branch `my-branch` or `test` and it doesn't matter. But on a team with 20-30 active branches, good names are the difference between "I know exactly what this is" and "what the heck is `asdfgh`?"

Most teams use a pattern like this:

```
<type>/<short-description>
```

![Good branch names on the left vs bad names on the right, with type legend at bottom](/diagrams/gitgithub/branch-naming.svg)

The diagram above shows good names on the left and bad names on the right. Good names like `feature/user-authentication` tell you instantly what the branch is about. Bad names like `my-branch` or `fix` tell you nothing. The bottom section shows the common type prefixes and what they mean.

Here are the common types:

| Type | When to use | Example |
|------|-------------|---------|
| `feature/` | Adding something new | `feature/search-bar` |
| `fix/` | Fixing a bug | `fix/login-button` |
| `chore/` | Maintenance tasks | `chore/update-deps` |
| `refactor/` | Rewriting code without changing behavior | `refactor/auth-service` |
| `docs/` | Documentation changes | `docs/api-guide` |
| `test/` | Adding or fixing tests | `test/user-model` |

The description should be short but helpful. Use hyphens between words.

Good examples:
- `feature/payment-integration`
- `fix/wrong-currency-format`
- `chore/remove-dead-code`

Bad examples:
- `my-branch` (what does it do?)
- `vin-test-42` (who's Vin? what's test 42?)
- `fix` (fix what? too vague)
- `asdfgh` (meaningless)

Some teams also include the issue number from their task tracker:

```
feature/142-user-authentication
```

Now anyone seeing the branch knows what issue it relates to.

**Common mistakes:**

- Spaces in branch names: `feature/add new stuff` will cause problems. Use hyphens.
- Being too vague: `fix/update` doesn't help. `fix/update-user-avatar` does.
- Inconsistent types: one person uses `feature/`, another uses `feat/`, another uses `ft/`. Pick one and stick with it.

**Why this matters:**

When you're looking at 30 branches and need to find the login bug fix, you can spot `fix/login-button` immediately without opening anything. That's the whole point.

---

**In Your Own Words:**

<details>
<summary>1. What's the standard branch naming pattern?</summary>

`<type>/<short-description>` — for example, `feature/navbar` or `fix/login-button`.
</details>

<details>
<summary>2. Name four common type prefixes and when to use them.</summary>

`feature/` (new features), `fix/` (bug fixes), `chore/` (maintenance), `docs/` (documentation).
</details>

<details>
<summary>3. Why is `my-branch` a bad name on a team project?</summary>

It gives no information about what the branch does. A good name like `fix/login-button` tells you immediately.
</details>

<details>
<summary>4. What characters should you avoid in branch names?</summary>

Spaces and special characters. Use hyphens between words, all lowercase.
</details>
