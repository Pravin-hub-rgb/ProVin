So we know commits form a chain. A single line of history. Now imagine five people all trying to add to that same chain at the same time. Each person has different changes. Some are half-done. Some might break things. It would be chaos, right? Nothing would be stable.

That's exactly why branches exist.

**A branch is just a separate line of work.**

Think of it like a tree. The trunk (`main`) is the stable, working version of your project. Branches grow out from the trunk. Each branch is its own separate line of development. You can work on your branch without affecting anyone else. Your teammate can work on theirs. The trunk stays healthy.

When you're done with your branch — your feature is built, tested, reviewed — you bring it back to the trunk. That's called "merging."

**But what is a branch technically?**

Just a label pointing to a commit. Nothing more. When you create a new branch, Git creates a tiny file with a commit hash in it. No files are copied. No folders are duplicated. It costs almost nothing.

This is why Git encourages you to create branches for everything. Even tiny changes. Even one-line fixes. Branches are cheap and safe.

**Why this matters on a team:**

Imagine a team of four developers all working on the same app at the same time:

- Alice is adding a login page
- Bob is fixing a CSS bug
- Charlie is updating the database
- Diana is writing documentation

Without branches, they all work on the same `main` branch. Alice's half-finished login page breaks things for everyone. Bob can't test his CSS fix because Alice's broken code is in the way. Charlie's database change might mess up Diana's docs. Nobody can ship anything because `main` is always broken.

With branches:
- Alice works on `feature/login-page`
- Bob works on `fix/css-button`
- Charlie works on `refactor/database`
- Diana works on `docs/readme`

Everyone works in isolation. Nobody affects anyone else. When Alice finishes, she merges just her completed feature into main. The codebase stays stable.

The diagram above shows the difference clearly. On the left: without branches, five developers all throw their half-finished work directly at main. Main is always broken. Nobody can deploy. On the right: each developer works on their own branch (`feature/login`, `fix/css-button`, etc.). Main stays clean. Each branch only merges back when the work is complete and reviewed.

**The one rule that matters:**

Never commit directly to main on a team project. Ever. Not even for "just one small thing." Every single change gets its own branch, goes through review, and only then gets merged.

On real teams, even a one-character typo fix in a readme file gets its own branch. It might seem like overkill, but it's insurance. That "small fix" might accidentally break something. The branch + review process catches it before it reaches main.

**What people often get wrong:**

Thinking branches are "extra work" or only for big features. They're not. Branches save work by preventing problems before they happen. A branch costs nothing to create. A broken main costs hours to fix.
