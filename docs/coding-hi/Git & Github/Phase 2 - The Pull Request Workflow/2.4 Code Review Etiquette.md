You know the PR workflow. You can open one, review one, merge one. But there's a layer above the buttons — how you actually talk to another human about their code. This is what separates someone who just clicks buttons from someone who's good to work with.

**Code review is not about proving you're smarter.**

The goal of a review is: catch problems before they reach main, and help each other get better. That's it. Not to show off, not to nitpick, not to flex your knowledge.

**How to write good review comments:**

Good comments are specific, constructive, and kind.

Bad: "This is wrong."
Good: "This loop runs every render. Since the data doesn't change, we could memoize it with `useMemo` to skip unnecessary work."

Bad: "Fix your naming."
Good: "What do you think about renaming this to `fetchUserData`? The current name `getStuff` doesn't tell me what it does."

Bad: "You forgot to handle the edge case."
Good: "Looks like if the API returns an empty array, this line will crash. We should add a check for `data.length === 0` before accessing `data[0]`."

See the difference? The good versions explain WHY, not just WHAT. They offer alternatives, not demands. They assume good intent.

**The three review types and when to use them:**

- **Comment** — use for suggestions, questions, or minor things that don't block merging. "Could we extract this into a helper function?" or "What happens if this value is null?"
- **Approve** — use when everything looks good, or when the remaining comments are minor/style-only. "This looks solid. Left one nitpick about naming, but not blocking."
- **Request changes** — use when there's something genuinely broken, a security issue, or a design flaw that needs fixing before merge. Not for "I would have written this differently."

A good rule: if something is a preference, leave a Comment. If something is a bug, leave a Request Changes. Don't block merges over tabs vs spaces.

**How to receive code review:**

This is harder than giving it. Someone is looking at your code and pointing out things you missed. It can sting. Here's how to handle it:

- Assume good intent. They're trying to help, not attack.
- If you disagree, say why. "I considered that but went with this approach because..." is a fine response.
- If you're not sure, ask. "Can you explain more? I don't quite follow."
- Say thank you. Even if the comment is nitpicky. Someone took time to look at your code.

**Real example of a good review thread:**

```
Reviewer: "This API call doesn't have error handling. If the network fails,
the user will see a blank screen. Could we wrap it in a try/catch and show
an error message?"

Author: "Good catch, I'll add that. Do you want a generic error message or
specific ones per error type?"

Reviewer: "Generic is fine for now — we can refine it later."
```

Productive. Fast. No ego. Both people walk away feeling good.

**What NOT to do:**

- Rubber-stamp approving without reading. "LGTM" on a 500-line PR that you didn't look at helps no one.
- Leaving drive-by comments with no explanation. "This is bad" helps no one.
- Making personal comments about the author, not the code. "You should know better" helps no one.
- Requesting changes over trivial preferences. "I would have used single quotes" is not a reason to block a merge.

**On a real team:**

You'll develop a shared review style. Some teams are thorough and leave many comments. Some are fast and trust each other. Both work if the team agrees on it. When you join a new team, watch how reviews go for the first few days before forming habits.
