Let's address the thing that scares people most about Git: merge conflicts. If you've seen one before, you know the feeling. That `CONFLICT` message. The `<<<<<<<` markers. The panic of "did I break everything?"

Here's the truth: merge conflicts are boring. They're not a sign you did something wrong. They're just Git being honest with you.

**A merge conflict happens in exactly one situation.**

Two branches changed the same lines (or very close lines) of the same file differently. That's it. Nothing else causes a conflict. If you and your teammate edited different files, Git merges them automatically. If you edited the same file but different sections — say you changed the header and they changed the footer — Git merges automatically. The only time Git gives up and asks for help is when the same lines were changed in two different ways and it doesn't know which one to keep.

**Let's be concrete.**

You and a teammate both clone the same repo. The `index.html` has this on line 10:

```html
<h1>Welcome to our site</h1>
```

You change it to:

```html
<h1>Welcome to the best site ever</h1>
```

Your teammate changes it to:

```html
<h1>Welcome, friends!</h1>
```

Both of you commit. When one of you tries to merge (or pull) the other's changes, Git looks at line 10 and says: "I have two different versions of this line. I don't know which is right. Human, you decide."

That's a merge conflict.

**What does NOT cause a conflict:**

- Different files being edited — no conflict, auto-merges fine
- Same file but different areas — Git can handle this. If you edit the header on line 10 and they edit the footer on line 100, both changes coexist.
- One person adds a file, another adds a different file — fine, no conflict.
- Same file, same general area but not the exact same lines — Git is surprisingly good at handling adjacent changes.

The only trigger: same lines, changed differently.

**Then why do people say conflicts are scary?**

Two reasons. First, they've never been taught what actually causes one — so it feels like random chaos striking their repo. Second, by the time most people see their first conflict, they've been working in isolation for a week and built up 15 conflicts at once. That's not the conflict being scary. That's the conflict being neglected.

If you sync your branch daily (remember 1.5?), conflicts are small, predictable, and take 30 seconds to fix.

**The good news:**

- Most merges have zero conflicts. Like, well over 90%.
- A conflict is not an error. It's a pause. Git is asking a question.
- You cannot permanently break anything with a conflict. Worst case, you abort the merge (`git merge --abort`) and your branch goes back to exactly how it was.

**In Your Own Words:**

<details>
<summary>1. What's the one condition that causes a merge conflict?</summary>

Two branches changed the same lines (or very close lines) of the same file in different ways.
</details>

<details>
<summary>2. Does editing a different file than your teammate cause a conflict?</summary>

No. Git auto-merges changes to different files without any issues.
</details>

<details>
<summary>3. If you edit line 10 and your teammate edits line 100 of the same file, does that conflict?</summary>

No. Git handles non-overlapping changes to the same file just fine.
</details>

<details>
<summary>4. Is a merge conflict an error?</summary>

No. It's a pause where Git asks you to decide which version to keep.
</details>

<details>
<summary>5. How do you safely abort a merge if you're not ready to resolve conflicts?</summary>

`git merge --abort` puts everything back to how it was before the merge.
</details>
