## The Story: You Broke the Navbar

You just pushed a navbar update to `main`:

```bash
$ git push origin main
```

Your teammate pulled it. Then you checked the live site. **The navbar is broken.** Links don't work. The logo is misaligned. It's a mess.

Your teammate already has your broken commit. If you use `git reset` to delete it, their repo will be out of sync with yours. You need a different tool.

## Enter `git revert`

Instead of erasing the commit from history, `git revert` creates a **brand new commit** that undoes all the changes from the broken one. History stays intact. Everyone's repos stay in sync.

```bash
$ git log --oneline
9a8b7c6 (HEAD -> main) Fix navbar alignment
e5f6g7h Add responsive navbar
a1b2c3d Initial commit
```

The broken commit is `e5f6g7h` ("Add responsive navbar"). You want it gone, but can't delete it because your teammate already pulled. So you revert:

```bash
$ git revert e5f6g7h
```

Git opens your editor with a pre-filled message. Save and close:

```
Revert "Add responsive navbar"

This reverts commit e5f6g7h.
```

**The revert commit is created automatically.** No `git add`. No `git commit`. Git figures out what the broken commit changed, creates the opposite changes, and commits them in one step.

Check the log:

```bash
$ git log --oneline
000000d (HEAD -> main) Revert "Add responsive navbar"
9a8b7c6 Fix navbar alignment
e5f6g7h Add responsive navbar
a1b2c3d Initial commit
```

Notice: `e5f6g7h` is still there. Nothing was erased. A new commit `000000d` simply undid the navbar changes. Your code is now back to how it was **before** you added the broken navbar.

## What Now? Push It.

The revert commit is only on your machine. **Revert does not push.** You still need to share it:

```bash
$ git push origin main
```

Your teammate pulls and gets the revert. The navbar works again on their end too. No conflicts. No drama.

The full flow is:

```
you broke it → git revert <hash>  → git push origin main
                ↑                      ↑
                auto-commits locally    sends it to everyone else
```

## Later: Fix It Properly

Revert didn't **fix** the navbar — it **undid** it. The feature is gone. That's fine. Later, when you have time:

1. Create a new branch: `git switch -c fix-navbar`
2. Write the navbar correctly this time
3. Test it locally
4. Push and open a PR

The revert commit stays in history as proof that "someone tried this, it broke, we undid it, then fixed it later." That's honest history.

## Revert vs Reset — The Golden Rule

```
git reset   = for your own unpushed work    (safe, local only)
git revert  = for anything already shared   (safe for teams)
```

Memorize this. It's the single most important rule of undoing in Git.

## Reverting a Merge Commit

This is trickier. If you merged a feature branch and then need to undo that merge, a regular revert isn't enough. You need to tell Git which parent branch to follow:

```bash
git revert -m 1 <merge-commit-hash>
```

The `-m 1` means "follow the first parent" — which is usually main. This reverts all the changes that came in from the merge, as if the merge never happened. We'll cover this more in 4.5.

## Revert on GitHub

On a merged PR, GitHub has a "Revert" button in the PR page. Clicking it creates a new PR that reverts the changes. Same concept as the terminal command, just through the UI.

## What People Get Wrong About Revert

- **"I need to fix the code and stage it after revert."** — No. Revert creates the undo commit for you automatically. It undoes the broken changes — you don't fix the broken code, you undo it and fix it later on a new branch.
- **"Revert also pushes to GitHub."** — No. The revert commit is only on your machine. You still need `git push` to share it. Revert only saves you from typing `git add` and `git commit`. Push is still your job.
- **"Revert erases the old commit."** — It doesn't. It adds a new one. The history is preserved.
- **"History with both 'Add X' and 'Revert X' looks messy."** — That's fine. Real projects have real history. It's honest.
- **"Revert is the same as reset."** — No. Reset removes, revert counteracts. Reset rewrites history, revert adds to it.
