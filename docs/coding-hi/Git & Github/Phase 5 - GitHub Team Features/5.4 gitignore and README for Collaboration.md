**`.gitignore` — what not to commit.**

Git tracks everything in your project folder by default. But there are files you never want in version control:

- `node_modules/` — can be gigabytes, regenerated from `package.json` with `npm install`
- `.env` files — contain secrets, API keys, passwords
- Build output — `dist/`, `build/`, `.next/` — generated from source, no need to track
- OS files — `.DS_Store` (Mac), `Thumbs.db` (Windows)
- IDE config — `.vscode/`, `.idea/` (unless the team agrees to share settings)

A `.gitignore` file at the root of your repo tells Git: "ignore these files and folders. Don't track them. Don't show them in `git status`."

Example `.gitignore` for a Node.js project:

```
node_modules/
.env
dist/
.next/
.DS_Store
*.log
```

**The critical rule about `.gitignore`:**

Add files to `.gitignore` BEFORE you commit them. If you accidentally commit a file and then add it to `.gitignore` later, Git still tracks it (it's already in history). You'd need extra steps to remove it.

If you ever accidentally commit a `.env` file with a real API key or password: change the key/password immediately. It's in Git history forever unless you do advanced history rewriting (beyond this course). Prevention via `.gitignore` is the real fix.

**`README.md` — the front door of your repo.**

A README is a markdown file that GitHub displays on your repo's main page. Every repo should have one. It answers the first questions someone has when they land on your project:

- What does this project do?
- How do I set it up?
- How do I run it?
- How do I contribute?

A minimal README:

```markdown
# Team Practice

A simple practice repo for learning Git and GitHub team workflows.

## Setup

1. Clone: `git clone https://github.com/yourname/team-practice.git`
2. Open `index.html` in your browser (it's a static site)

## Contributing

1. Branch off main: `git switch -c feature/your-feature`
2. Make changes, commit, push
3. Open a PR and request review

## License

MIT
```

**Why these files matter on a team:**

- `.gitignore` prevents the #1 beginner mistake: committing node_modules or secrets
- A good README means new teammates (or your future self) can get the project running without asking anyone anything
- Both files show you care about the repo's health — it's basic professionalism

**In Your Own Words:**

<details>
<summary>1. What kinds of files should go in `.gitignore`?</summary>

`node_modules/`, `.env` files, build output folders (dist, .next), OS files (.DS_Store), IDE config, log files.
</details>

<details>
<summary>2. When should you create your `.gitignore`?</summary>

Before committing any files to the repo. Adding it after committing won't stop already-tracked files from being tracked.
</details>

<details>
<summary>3. What should a good README contain?</summary>

What the project does, how to set it up, how to run it, and how to contribute.
</details>

<details>
<summary>4. Why does a `.gitignore` matter for team collaboration?</summary>

It prevents accidental commits of unnecessary files (node_modules) and dangerous files (secrets in .env) that cause real problems for everyone.
</details>
