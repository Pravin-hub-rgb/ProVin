You built something cool. You put it on GitHub. Now someone asks: "What license is this under?" If you don't know, the answer is actually scary — **nobody can legally use your code.**

This chapter covers the 5 licenses you'll actually encounter, what each one means, and how to pick one for your project in under 2 minutes.

---

## Why Licenses Matter

Code without a license is **not open source**. It's just code sitting on the internet. In most countries, copyright is automatic — the moment you write code, you own the copyright. Without a license, nobody has permission to:

- Copy your code
- Modify it
- Use it in their own project (even a free one)
- Distribute it

Technically, someone who clones your repo without a license is breaking copyright law. Most people don't realize this, which is why "no license" is the most common license on GitHub — by accident, not by choice.

**A license** is a legal document that says: "You can use my code, under these conditions." That's it.

## The Big 5 Licenses (What You'll Actually See)

Most projects use one of these five. They range from "do literally whatever you want" to "you must also open source your changes."

### 1. MIT — The "Do Whatever" License

**Used by:** React, Vue, jQuery, Node.js, Express, Laravel

```
MIT License

Permission is hereby granted, free of charge, to any person obtaining a copy
of this software... to deal in the Software without restriction...
```

**What it allows:**
- Use the code in any project (open source or commercial)
- Modify it
- Sell it
- Keep your changes private (you don't have to open source your version)

**The only requirement:** Include the original copyright notice (the license text).

**Who should use it:** You. If you're putting a side project on GitHub and want maximum adoption with minimum headache, MIT is the default choice. It's short, well-understood, and lawyers everywhere are comfortable with it.

### 2. Apache 2.0 — MIT + Patent Protection

**Used by:** Android, Kubernetes, Swift, TensorFlow

Almost identical to MIT, but adds an explicit grant of patent rights. If someone contributes to your project and then tries to sue you for patent infringement using something from that contribution, they lose their license automatically.

**The practical difference:** Big companies prefer Apache 2.0 over MIT because it explicitly handles patents. If you work at a company and they open-source something, Apache 2.0 is often their default.

**Added requirement:** You must include a notice file (`NOTICE`) listing any third-party attributions.

### 3. BSD (2-Clause) — MIT's Cousin

**Used by:** Go, Redis, Nginx

BSD 2-Clause is nearly identical to MIT — do whatever, just keep the notice. BSD 3-Clause adds a "no endorsement" clause (you can't use the author's name to promote derivative works). BSD 4-Clause is obsolete and should not be used.

**BSD vs MIT:** They're functionally identical for most purposes. The difference is mostly historical and cultural. Pick MIT unless your project already uses BSD.

### 4. GPL v3 — The "Share Alike" License

**Used by:** Linux, Git itself, WordPress, GIMP

```
This program is free software: you can redistribute it and/or modify
it under the terms of the GNU General Public License...

...if you distribute the software, you must also distribute the source code
for any modifications you make.
```

**What it requires:**
- If you use GPL code in YOUR project and distribute that project, you must also release YOUR entire project's source code under GPL
- This is called **copyleft** — it's like copyright but flipped: instead of "all rights reserved," it says "all rights granted, and you must grant the same rights to others"

**What it allows:**
- Use the code in internal/private projects without sharing your changes
- As soon as you **distribute** the software to others (sell it, give it away as a compiled app, put it on a device), you must share the source

**The "copyleft" trap:** If you use GPL code in a commercial product that you distribute, your entire product must become GPL. This is why companies avoid GPL for their core products. If your project depends on a GPL library, you need to understand whether you're "distributing" or just running it on a server.

**AGPL — The "Even If It's On A Server" version:** This extends GPL so that if you use AGPL code in a web service, you must also share your source. MongoDB, Elasticsearch (before switching), and Nextcloud use this.

### 5. Creative Commons (CC) — For Non-Code

Used for documentation, designs, images, fonts — anything that isn't software.

Common variants:
- **CC0** — "No rights reserved." Public domain equivalent. Use this for docs/art you want everyone to freely use.
- **CC BY 4.0** — You can use/edit/share it, but you must credit the author.
- **CC BY-NC 4.0** — Same as BY but not for commercial use. Be careful with this one — it can prevent people from using your work in ways you might actually want (like a company using your tutorial internally as training material).

## Quick Comparison Table

| License | Can use commercially | Must share source | Must credit author | Patent protection |
|---------|---------------------|-------------------|--------------------|--------------------|
| MIT | Yes | No | Yes | No |
| Apache 2.0 | Yes | No | Yes | Yes |
| BSD 2-Clause | Yes | No | Yes | No |
| GPL v3 | Yes | **Yes** | Yes | Yes |
| AGPL v3 | Yes | **Yes (even on servers)** | Yes | Yes |
| CC0 | Yes | No | No | N/A |
| No license | No | No | No | No |

## How to Choose in 10 Seconds

1. **Is it code?** → Go to step 2. **Not code (docs, art)?** → CC0 or CC BY.
2. **Do you care if companies use it in closed-source products?** → MIT or Apache 2.0.
3. **Do you want to force everyone who uses your code to also open source their changes?** → GPL v3.
4. **Does your company have a legal team that prefers Apache 2.0?** → Apache 2.0.
5. **Don't care, just want people to use it?** → MIT.

For most of your projects: **MIT.** It's the default for a reason.

## How to Add a License to a Repo

**Option A — GitHub's built-in tool:**
When creating a new repo, GitHub has a "Add a license" dropdown. Pick one. Done.

**Option B — Add a file:**
Create a file called `LICENSE` or `LICENSE.md` in the root of your repo. Paste the full license text (you can copy it from choosealicense.com).

**Option C — For existing projects:**
1. Go to your repo on GitHub.com
2. Click "Add file" → "Create new file"
3. Name it `LICENSE`
4. Click "Choose a license template" on the right
5. Pick one, GitHub fills in your name and year automatically

Then: `git pull` locally, and you're set.

## What Happens If You Use Someone Else's GPL Code

If you use a GPL library in your project and distribute that project, you MUST release your project's source under GPL too. This is the single biggest licensing mistake beginners make — they use a GPL library without realizing their whole project becomes GPL by extension.

**How to avoid this:** Before adding a dependency to your project, check its license. If it's GPL, make sure you're okay with your project also being GPL.

## Common Scenarios

**"I found code on GitHub with no license. Can I use it?"**
No. Without a license, copyright law applies by default. You can't legally use, modify, or distribute it. If you need to use it, contact the author and ask them to add a license.

**"I forked a MIT project. What license can my fork be?"**
MIT or any more permissive license. You can even make it proprietary (closed source). But you MUST include the original MIT copyright notice.

**"I forked a GPL project. What license can my fork be?"**
Only GPL (or a compatible copyleft license). You cannot re-license GPL code as MIT.

**"Can I change my project's license later?"**
Yes, if you're the only contributor. If others have contributed, you need their permission to re-license their contributions. This is why many projects have a Contributor License Agreement (CLA) — it lets the project owner change the license later without tracking down every contributor.

## What People Get Wrong About Licenses

- **"No license means it's public domain."** — Wrong. No license means ALL RIGHTS RESERVED by default. Nobody can touch your code.
- **"I put 'MIT' in a comment, that's enough."** — Not really. Courts look for the full license text in a dedicated file. Use the standard `LICENSE` file.
- **"I don't need a license for a small project."** — Even small projects get copied. If you'd be annoyed someone used your code without credit, add a license. If you wouldn't care, also add a license — MIT takes 2 seconds.
- **"GPL means I can't charge money."** — You can sell GPL software. The catch is whoever you sell it to can also redistribute it for free. The license doesn't prevent commerce — it prevents closed-source redistribution.
- **"I'll just write my own license."** — Don't. Custom licenses are risky because:
  - Courts haven't tested them
  - Nobody knows what they mean
  - They may contradict each other in unexpected ways
  - Pick a standard one. There's one for every need.
