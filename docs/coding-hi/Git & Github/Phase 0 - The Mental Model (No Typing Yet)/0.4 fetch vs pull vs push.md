You might have used `git pull` before and had something weird happen. Maybe your files changed unexpectedly. Maybe you saw a scary screen full of `<<<<<<<` symbols. That confusion comes from not understanding the difference between `fetch` and `pull`. Let's clear that up.

There are three main ways your computer and GitHub talk to each other. Here's what each one does.

---

**`git fetch` — "Let me see what's new without changing anything."**

This downloads new information from GitHub but does NOT touch your files. Nothing changes in your editor. Your current work stays exactly as it is.

Think of it like checking your mailbox. You walk outside, open the box, and see there are letters inside. You know what arrived. You can see who sent what. But you don't open any of them yet. You just know what's there.

Here's what `git fetch` looks like in your terminal:

```
$ git fetch origin
remote: Enumerating objects: 8, done.
remote: Counting objects: 100% (8/8), done.
remote: Compressing objects: 100% (4/4), done.
remote: Total 4 (delta 3), reused 0 (delta 0), pack-reused 0
Unpacking objects: 100% (4/4), 1.21 KiB | 124.00 KiB/s, done.
From https://github.com/yourname/project
   a1b2c3d..e5f6g7h  main       -> origin/main
```

The last line is the key part — it tells you "main on your computer went from commit a1b2c3d to e5f6g7h on GitHub." Your local main hasn't changed yet. You just know what's new.

After a fetch, you can run commands like `git log origin/main` to see what new commits your teammates have made.

![What origin/main means — your local main branch vs the remote main branch on GitHub, connected by push/pull](/diagrams/gitgithub/origin-main-notation.svg)

The diagram above explains the `origin/main` notation. Think of it as a phrase: "the `main` branch as it exists on the remote called `origin`." Your local `main` is your version on your computer. `origin/main` is your local memory of what GitHub had last time you checked. They're separate — which is why you need `git push` to update GitHub's `main`, and `git fetch` to update your local `origin/main`.

You're just looking. Nothing is merged into your work yet.

**`git pull` — "Get the latest stuff AND add it to my work."**

`git pull` does two things in one go: it fetches (downloads the latest) AND merges (tries to combine it with your current work). This is where surprises come from. When you run `git pull`, you're not just "updating" your code. You're performing a merge. And merges can create conflicts.

Here's a smooth `git pull` when nothing conflicts:

```
$ git pull origin main
From https://github.com/yourname/project
 * branch            main       -> FETCH_HEAD
Updating a1b2c3d..e5f6g7h
Fast-forward
 index.html | 3 +++
 1 file changed, 3 insertions(+)
```

"Fast-forward" means Git just moved your branch forward — no merge needed. Nobody else changed the same files.

Here's what it looks like when there IS a conflict:

```
$ git pull origin main
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
```

If you open `index.html` now, you'll see something like:

```
<<<<<<< HEAD
<h1>My Project</h1>
=======
<h1>Our Project</h1>
>>>>>>> main
```

The part above `=======` is your version (HEAD). Below it is the incoming version from main. You delete the markers and decide what stays. It's not broken — Git is just asking you to choose. But it can feel jarring when all you wanted was to "get the latest."

![git fetch, git pull, and git push shown as arrows between your computer and GitHub, with explanations](/diagrams/gitgithub/fetch-pull-push.svg)

The diagram above shows all three operations visually. Fetch (purple) is a one-way download of information — nothing changes on your computer. Pull (amber) is fetch plus merge combined — it downloads AND merges. Push (green) uploads your commits. The table at the bottom summarizes each one.

**`git push` — "Send my work to GitHub so others can see it."**

This uploads your commits to GitHub. Here's what a successful push looks like:

```
$ git push origin main
Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
Delta compression using up to 8 threads
Compressing objects: 100% (3/3), done.
Writing objects: 100% (3/3), 512 bytes | 512.00 KiB/s, done.
Total 3 (delta 2), reused 0 (delta 0), pack-reused 0
To https://github.com/yourname/project.git
   a1b2c3d..e5f6g7h  main -> main
```

The last line confirms your commits were uploaded.

If someone else has pushed changes since your last pull, Git will reject your push:

```
$ git push origin main
To https://github.com/yourname/project.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/yourname/project.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. You may want to first integrate the remote changes
hint: (e.g., 'git pull ...') before pushing again.
```

This is Git protecting you from accidentally erasing someone else's work. If that happens, pull first (get their changes), merge, then push again.

The first time you push a new branch (a separate line of work in your project), you need to add `-u`:

```
git push -u origin feature/navbar
```

The `-u` just sets up a connection so future pushes can be shorter: `git push`.

---

**Which one should you use?**

- **Use `git fetch`** when you want to check what's new without changing your files. It's the safe option.
- **Use `git pull`** when you're ready to bring the latest changes into your work and deal with any conflicts right now.
- **Use `git push`** when you've committed your work and want to share it with the team.

A lot of experienced developers do `fetch` first, check what changed, then manually merge. It gives them control. They're not caught off guard by surprise conflicts.

```
git fetch origin
git log origin/main --oneline   # --oneline shows each commit as one line, easier to read
git merge origin/main            # now bring it in (only if you're ready)
```

**Usual mistakes:**

- Pulling when you have uncommitted changes. Git may refuse or make a mess. Commit or save your work aside first.
- Thinking `git pull` just "updates" your files. It doesn't. It fetches AND merges. That merge can create conflicts.

**In Your Own Words:**

<details>
<summary>1. What does `git fetch` do? Does it change your files?</summary>

It downloads new information from GitHub about new commits and branches. No, it does NOT change your files. Your work stays untouched.
</details>

<details>
<summary>2. What's the difference between `git fetch` and `git pull`?</summary>

`git pull` = `git fetch` + `git merge`. Fetch just looks. Pull downloads AND tries to combine the new changes with your work.
</details>

<details>
<summary>3. What does `git push` do?</summary>

It uploads your local commits to GitHub so your team can see them.
</details>

<details>
<summary>4. Why might someone use `git fetch` and then `git merge` instead of just `git pull`?</summary>

To stay in control. They want to see what's new before deciding to merge it. This avoids surprise conflicts.
</details>
