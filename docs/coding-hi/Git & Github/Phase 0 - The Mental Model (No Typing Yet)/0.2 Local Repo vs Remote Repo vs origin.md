So we just learned Git saves versions on your computer, and GitHub holds a copy online. Now let's talk about how those two copies are connected. Because this is where people get confused — they think their computer and GitHub are the same thing somehow. They're not.

**Your "local repo" is the Git history sitting on your computer.**

Remember that hidden `.git` folder we talked about? That's your local repo. Every snapshot (commit) you make gets stored in there. Every branch (a separate line of work — like a different version you can switch between) you create lives in there. It's your personal, full copy of the project history.

When you open a project folder in your editor, the files you see are just the latest snapshot that Git checked out for you from that `.git` folder. The real history is inside `.git`.

**A "remote repo" is the same Git history, but hosted somewhere else — usually on GitHub's servers.**

It's not special. It's not the "real" copy. It's literally just another `.git` folder that happens to be on the internet instead of your computer. When you connect to a remote, you can upload your changes to it or download changes from it.

Think of it like this: you have a folder of photos on your laptop (your local repo). You upload those photos to Google Drive (the remote repo). Your friend also has them on their laptop (their local repo). Nobody's laptop is the "real" one. Google Drive is just where everyone syncs through.

![Multiple developers with local repos connecting to a shared remote repo on GitHub, with push and pull arrows](/diagrams/gitgithub/local-remote-origin.svg)

The diagram above shows three developers, each with their own local repo on their computer. The shared remote in the center (on GitHub's servers) is where everyone syncs through. Dev A pushes changes up, Dev B pulls changes down, Dev C does both. Notice how each local repo is separate — nobody works directly on the remote. The remote is just the meeting point.

**Now, `origin` is just a nickname.**

When you first download (clone) a project from GitHub, Git remembers where it came from. It gives that remote a nickname. By default, it calls it `origin`. That's all it is — a shortcut so you don't have to type the full URL every time.

Instead of writing:
```
git push https://github.com/yourname/project.git main
```

You can write:
```
git push origin main
```

(`main` here is the name of your main branch — the primary version of your project. `push` means "upload my commits to the remote." We'll cover both properly in later sections.)

Much easier, right? That's all `origin` does. It holds the URL for you.

You could rename it to anything:
```
git remote rename origin my-backup
```

Now you'd type `git push my-backup main` instead. Works exactly the same.

You can even have multiple nicknames pointing to different places. Here's a common example:

Say you want to contribute to someone else's project on GitHub. You'd first make your own copy of their project (this is called "forking" — we'll cover it properly later). Your copy is on GitHub under YOUR username. The original is under THEIR username. Now you'd set up two remotes:

- `origin` — your copy of the project (where you push/upload your changes)
- `upstream` — the original project (where you fetch/download their latest updates)

You use `origin` to push your changes. You use `upstream` to pull in updates the original author made. Two nicknames, two different URLs, two different jobs.

**How to see what remotes you have:**

```
git remote -v
```

This shows you all the nicknames and the URLs they point to. You'll see something like:

```
origin    https://github.com/yourname/project.git (fetch)
origin    https://github.com/yourname/project.git (push)
```

The same nickname appears twice — once for downloading (fetch) and once for uploading (push). Usually they point to the same URL. We'll explain what fetch and push actually do in the next section.

**What this all means when working with a team:**

Your team has ONE shared remote on GitHub. Everyone clones it. Everyone gets their own local copy. Everyone works on their own computer. When someone finishes their work, they push their changes to the shared remote. Everyone else pulls those changes down.

The remote is just the meeting point. It's where everyone's work comes together. Your computer has your version. GitHub has the shared version. They're separate, and that's okay.
