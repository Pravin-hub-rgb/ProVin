You've probably seen people type `git add` and then `git commit`. Two separate commands, one after the other. If you've ever wondered "why not just one command?" — you're asking the right question. The answer is Git's three areas.

Most people just memorize these commands without understanding why they exist. Let's fix that.

**Area 1: Your Working Directory**

This is just your files as they sit on your computer right now. The `index.html` file you can see in your editor. The `style.css` you're editing. When you write code and hit save, those changes are in your working directory.

Git sees these changes. If you run `git status`, it'll show you "hey, these files are different from the last saved version." But Git isn't doing anything with them yet. They're just sitting there.

**Area 2: The Staging Area (also called "the index")**

This is a middle step. Think of it like a prep table in a kitchen. Your working directory is your counter with ingredients spread everywhere. The staging area is where you put the specific ingredients you're about to cook.

When you run `git add <filename>`, you're telling Git: "take this file from my working directory and put it on the prep table. I'm thinking about committing this."

Why would you need a middle step? Imagine you're working on a new feature and you notice a typo in your readme file. You fix the typo. Now you have two changes in your working directory — the half-finished feature and the typo fix. If you commit everything at once, both go into one commit. That's messy. Your commit message can't describe both.

With staging, you can do this:

```
git add readme.md                # stage just the typo fix
git commit -m "Fix typo in readme"  # commit just that

git add src/feature.js            # now stage the feature stuff
git commit -m "Add search bar WIP"  # commit that separately
```

Two clean commits instead of one confusing mess. Later when you look at your history, you can see exactly what happened and when.

There's even a way to stage parts of a file. `git add -p` shows you each chunk of changes in a file and asks "stage this part?" You can say yes to some chunks and no to others. Super useful when a single file has multiple unrelated changes.

**Area 3: The Repository (your local history)**

This is the permanent record. When you run `git commit`, Git takes everything from the staging area, packages it up with your message, and stores it forever in the `.git` folder. That commit is now part of your project's history.

The diagram above shows how the three areas connect. Start on the left: you edit files in your Working Directory. When you're happy with a change, you run `git add` to move it to the Staging Area (the middle box). Once everything you want is staged, you run `git commit` to lock it into the Repository (the permanent history on the right). Each arrow is a command you type.

Think of it like this:
- Working directory = a workspace where you make changes
- Staging area = a checklist of "I want these changes in my next commit"
- Repository = the photo album where all your commits live permanently

**What you see when you run these commands:**

After editing `index.html` and saving it, then running `git status`:

```
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   index.html

no changes added to commit (use "git add" and/or "git commit -a")
```

After staging it with `git add index.html` and running status again:

```
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   index.html
```

Notice how the file moved from "not staged" to "to be committed." That's the staging area in action.

If you want to see exactly what lines changed before staging:

```
$ git diff
diff --git a/index.html b/index.html
index e69de29..3b2a5b4 100644
--- a/index.html
+++ b/index.html
@@ -0,0 +1,3 @@
+<h1>Hello World</h1>
+<p>This is my first Git project.</p>
```

The lines starting with `+` are new. After you stage and run `git diff --staged`, you see the same diff but only for what's waiting in staging.

**The full flow in one place:**

```
git status              # shows what's changed, what's staged, what's not
git add <file>          # move a file from working dir to staging
git add -p              # move parts of a file to staging (ask for each part)
git commit -m "message" # take everything in staging and save it forever
git diff                # show what's changed but NOT staged yet
git diff --staged       # show what's staged and ready to commit
```

**What people often get wrong:**

Always using `git add .` — which adds everything at once. It's quick and easy, but it bundles all your changes into one commit whether they're related or not. On a team, clean commits matter. One commit = one logical change. That's the habit to build.

**In Your Own Words:**

<details>
<summary>1. What are Git's three areas? Explain each in one sentence.</summary>

Working Directory — your actual files on disk. Staging Area — where you put changes you want to commit. Repository — the permanent history of all commits.
</details>

<details>
<summary>2. Why does the staging area exist? Why not just commit directly?</summary>

So you can decide which changes go into which commit. If you have a bug fix and a half-finished feature in the same file, staging lets you commit the fix first.
</details>

<details>
<summary>3. What does `git add -p` do differently from `git add .`?</summary>

`git add -p` shows you each chunk of changes and asks if you want to stage it. `git add .` stages everything without asking.
</details>

<details>
<summary>4. What's the difference between `git diff` and `git diff --staged`?</summary>

`git diff` shows unstaged changes (what you haven't added yet). `git diff --staged` shows what's in staging and about to be committed.
</details>
