So you know a commit is a saved version of your project. But what's actually inside a commit? And how does Git know which commit came before which?

Let's open one up and look inside.

**Every commit is a package with these things:**

- **A unique ID (called a hash)** — a long string like `a1b2c3d4e5f6...`. This is the commit's fingerprint. No two commits anywhere in the world will ever have the same one.
- **Who made it** — name and email
- **When** — date and time
- **A message** — whatever you wrote after `-m`. It should explain WHY you made this change.
- **A link to its parent** — the commit that came before it

That last part is the key to everything.

Every commit points back to the commit that came before it. Like a chain:

```
Commit C → Commit B → Commit A (first commit, no parent)
```

This chain is your entire project history. It goes backwards from your most recent commit all the way to the very first one. That's it. That's Git's entire data model — a chain of snapshots.

**What is a branch in this model?**

A branch is just a label that points to one of these commits. That's all. When you're on a branch and make a new commit, Git:
1. Creates the new commit with the parent = where the branch currently points
2. Moves the branch label to the new commit

So the branch label keeps moving forward as you commit. Think of it like a bookmark that follows your latest page.

Creating a new branch is instant because Git isn't copying files. It's just creating a new label (a tiny file with a commit hash in it).

The diagram above shows exactly how this works. The top half shows three commits in a chain — each one pointing to its parent. Notice how the latest commit (with the green border) has a label called "main" — that's a branch, just a label on a commit. The bottom half shows a merge: two branches (main in blue, feature in green) join together into a merge commit with TWO parents.

**What about a merge?**

A merge creates a commit with TWO parents — one pointing to each branch that was merged. That's how Git remembers "these two lines of history came together here."

```
Merge Commit
├── Parent 1: what was on main
└── Parent 2: what was on the feature branch
```

**Why this matters:**

When you understand this chain, branches and merges stop being mysterious. You can LOOK at your history instead of guessing. And there's a command that shows the whole thing as a picture.

Set up this shortcut once:

```
git config --global alias.tree "log --oneline --graph --all --decorate"
```

Now instead of typing that whole thing, you just type `git tree`. Here's what it looks like in a real project:

```
$ git tree

*   a1b2c3d (HEAD -> main) Merge pull request #42 from feature/payment
|\  
| * f5e6d7c (feature/payment) Add Stripe webhook handler
| * 8a9b0c1 Add payment confirmation email template
* | 4d3e2f1 Fix cart total calculation bug
* | 9f8e7d6 Update checkout page styling
|/  
* 1a2b3c4 Add product search by category
* 2b3c4d5 Set up database connection pool
* 3c4d5e6 Initial commit — project scaffolding
```

Read this from bottom to top. Started with scaffolding. Then database setup, search feature. Then two people worked in parallel — one on `feature/payment` (indented lines) and one on `main` directly (the `* |` lines). At the top, the feature branch was merged into main via a Pull Request.

Let's break down the flags in `git tree`'s command:
- `--oneline` — show each commit as a single line (abbreviated hash + title)
- `--graph` — draw the ASCII lines so you can SEE the branches
- `--all` — show ALL branches, not just the one you're on
- `--decorate` — show branch names like `(main)`, `(feature/payment)` next to commits

Another command you'll use constantly is `git show`. It opens up a single commit and shows you everything inside it — who made it, when, why, and exactly what lines changed:

```
$ git show a1b2c3d

commit a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b
Author: Alice <alice@team.com>
Date:   Mon Jun 29 14:30:00 2026 +0530

    Fix cart total calculation bug
    
    The cart wasn't accounting for quantity when calculating
    the subtotal for items with variant pricing. Fixed by
    multiplying unit price by quantity before adding to total.

diff --git a/src/cart/calculator.js b/src/cart/calculator.js
index a1b2c3d..e4f5g6h 100644
--- a/src/cart/calculator.js
+++ b/src/cart/calculator.js
@@ -15,7 +15,7 @@ function calculateSubtotal(items) {
   return items.reduce((total, item) => {
     const price = item.variantPrice || item.basePrice
-    return total + price
+    return total + price * item.quantity
   }, 0)
 }
```

Notice the structure:
- The commit hash (long version — full 40 characters)
- Author name + email
- Date and time
- Commit message with body explaining WHY (not just what)
- The diff — green line with `+` is what was added, red line with `-` is what was removed

The `git show` output is how you review exactly what someone changed. On a team, you'll do this every day when reviewing Pull Requests — looking at each commit's diff to understand what happened.

**A note about commit messages:**

The message is your chance to tell future-you (and your team) WHY a change was made. Not what changed (Git can show that itself), but why.

A good one looks like:
```
Fix login button not working on mobile

The button had a z-index that was too low, 
so the navigation bar was covering it on small screens.
```

A bad one is just: `fix` or `updates` or (worst of all) no message at all.

Future-you will thank present-you for good messages. Especially at 2 AM when something breaks.

**In Your Own Words:**

<details>
<summary>1. What five things does every commit store?</summary>

A unique ID (hash), the author's name and email, a timestamp, a message, and a link to the parent commit.
</details>

<details>
<summary>2. How does Git know which commit came before which?</summary>

Each commit stores a link (pointer) to its parent commit. They form a chain going backwards from the newest to the very first commit.
</details>

<details>
<summary>3. What is a branch in simple terms?</summary>

A branch is just a label that points to a specific commit. It moves forward as you make new commits.
</details>

<details>
<summary>4. What command shows all your branches and commits as a visual graph?</summary>

`git log --oneline --graph --all --decorate` or the shortcut `git tree` (if you set up the alias).
</details>

<details>
<summary>5. What makes a good commit message vs a bad one?</summary>

Good: explains WHY the change was made. Bad: just says "fix" or "updates" or is left empty.
</details>
