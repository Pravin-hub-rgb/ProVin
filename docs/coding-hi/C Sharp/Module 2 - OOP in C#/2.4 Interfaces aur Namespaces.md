Pichhle file mein ek problem reh gayi — C# mein **single inheritance** hai: ek class sirf ek hi class se inherit kar sakti hai (`class Student : Person`). Par kabhi kabhi rule aisa hota hai jo kai alag-alag families pe lagu ho — "jo cheez save hoti hai wo `Save()` method rakhegi", chahe `Student` ho ya `Product` ya `Order`. Iska solution hai **interface**.

# Interfaces aur Namespaces

## Interface — sirf rule, implementation nahi

Interface ek **contract** hai: "jo bhi isse implement kare, usko ye methods hone hi chahiye". Andar ka code tum doge — sirf signature:

```csharp
interface ISaveable               // I se shuru = naming convention
{
    void Save();                  // body nahi — sirf rule
    string GetId();
}

class Student : ISaveable         // implement = contract sign kiya
{
    public string Name;

    public void Save()
    {
        Console.WriteLine(Name + " DB mein save hua");
    }

    public string GetId()
    {
        return "STU-" + Name.Length;
    }
}

class Product : ISaveable         // ek aur family — wahi contract
{
    public void Save() => Console.WriteLine("Product save hua");
    public string GetId() => "PRD-001";
}
```

Fark inheritance se:

| | Class inherit | Interface |
|---|---|---|
| Kya milta hai | code (fields + methods) | sirf signature (rule) |
| Kitni | **ek hi** parent | **jitni chaaho** (`: ISaveable, IComparable`) |
| Body | hoti hai | nahi — sab khud likhna |
| Kaam kiska | reusability | capability/"can-do" |

`ISaveable` ka matlab "save ho sakta hai" — `Student` pehle se `Person` se inherit hai, phir bhi `ISaveable` le sakta hai. **Yahi iska faayda** — doosri families ke rules ek saath.

## Real .NET interfaces — jo roz milenge

Tum yeh interface khud nahi banate, .NET ke ready-made bahut use hote hain:

```csharp
// IEnumerable — "isme se loop chala sakte ho" (foreach wala rule)
foreach (var item in myObject) { }   // agar IEnumerable implement hai → chalega

// IEquatable<Student> — "do students compare ho sakte hain"
// IComparable — "sort ho sakte hain"
```

Aur module 5 mein ASP.NET Core ke interfaces (`IActionResult`, `IService`) aayenge — tab ye word familiar lagega. Abhi bas yaad rakho: **interface = plug ka shape.** Apka device chahe Samsung ho ya Sony, plug ka shape same hai toh bijli wala (system) sabme laga deta hai.

## Interface vs Abstract class — kab kaunsa

- **Abstract class** tab jab **ek hi family** ka shared code ho (jaise sab employees ka common `RaiseRequest()`), aur state bhi ho.
- **Interface** tab jab **alag-alag families** ko ek rule dena ho (`ISaveable`, `ILoginable`), ya multiple capabilities chahiye hon.
- C#: ek abstract parent + jitni interfaces — dono ek saath chal sakte hain.

```csharp
class Manager : Person, ISaveable, IPromotable   // ek class, do contracts
{
}
```

## Default interface methods (C# 8+) — halka sa extra

```csharp
interface ILogger
{
    void Log(string msg);

    void LogError(string msg) => Log("[ERROR] " + msg;   // yahan bhi body ho sakti hai
}
```

Implement karne wale ko `Log` likhna hi padega, `LogError` chahiye toh override karo warna default chalega. Advanced hai — bas jaan lo aisa hota hai.

## Namespaces — folder system jaisa naam bachana

C# mein jab bhi `Console`, `Math` type hote hain — koi na koi **namespace** mein rehte hain. File ke top pe jo likha tha wohi hai:

```csharp
using System;                 // System namespace ke items seedhe chahenge
using System.Collections.Generic;   // List<>

Console.WriteLine("hi");      // actually System.Console.WriteLine — using se chhota
List<int> l = new List<int>(); // actually System.Collections.Generic.List<int>
```

**`using` = JS ka `import`** (direction ulta — JS mein `"react"` import karte hain, C# mein namespace "use" karte hain). `using` na likho toh poora naam likhna padega: `System.Console.WriteLine(...)`.

Apne namespaces khud banao — bade project mein naam takkar (collision) se bachne ke liye:

```csharp
namespace SchoolApp.Domain          // dot se hierarchy, folder jaisa
{
    class Student { }
}

// use:
// using SchoolApp.Domain;
// SchoolApp.Domain.Student s = new SchoolApp.Domain.Student();
```

`namespace` ke andar classes — JS module jaisa ki "SchoolApp.Domain wale `Student`" aur "School wale `Student`" alag hain. Bade solutions (jaise .NET ke andar) isi se organized hote hain.

> Modern C# mein file-scope namespace bhi chalta hai (`namespace SchoolApp.Domain;` file ke top pe ek line) — dono milega codebase mein.

## Yeh kya NAHI hai

- **Interface ke andar data/fields nahi hote** — sirf methods/properties ke signature (C# 8 ke default methods body dete hain, par field nahi). State ke liye class chahiye.
- **Interface = abstract class nahi** — ek rule deta hai, doosra partial code bhi. Multiple inheritance sirf interface se milti hai, class se nahi.
- **`using` import nahi hai JS wala** — koi file download nahi hoti; bas naam-space short kar diya. Packages (`NuGet`) alag cheez hain — module 3 mein.
- **Naam `I` se zaroori nahi hota** par .NET convention yahi hai (`IList`, `IDisposable`) — `I` dekhte hi samajh lo interface hai.

## Ek complete program — contract wala design

```csharp
// Program.cs
using System;
using System.Collections.Generic;

interface IExportable
{
    string Export();          // har exportable cheez CSV string degi
}

class Report : IExportable
{
    public string Title;
    public Report(string t) { Title = t; }

    public string Export() => $"Report: {Title}, date: {DateTime.Now:yyyy-MM-dd}";
}

class Invoice : IExportable
{
    public double Amount;
    public Invoice(double a) { Amount = a; }

    public string Export() => $"Invoice, amount: {Amount}";
}

// --- ek hi code, alag-alag types ---
List<IExportable> items = new List<IExportable>
{
    new Report("Monthly Sales"),
    new Invoice(2500)
};

foreach (IExportable it in items)
{
    Console.WriteLine(it.Export());   // apna-apna Export chala
}
```

`List<IExportable>` — ab isme `Report` bhi aayega, `Invoice` bhi, aur aane wale kisi bhi nayi type bhi — bas `IExportable` implement karni chahiye. **Yahi extension ka pattern hai jo .NET codebase har jagah dikhta hai.**

## In Your Own Words

1. Interface aur class inheritance — teen fark batao.

<summary>Sample Jawab</summary>

**Jawab:** Class inheritance code (fields+methods) deti hai, interface sirf signature/rule. Class sirf ek parent le sakti hai, interfaces jitni chaaho. Interface body nahi (mostly) — implement karne wala khud likhta hai; parent class ka code chal jaata hai.

</details>

2. `ISaveable` jaisa interface kab banate hain — "IS-A" kyun kaam nahi karta?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Jab rule alag-alag families pe lagu ho — Student bhi save ho, Product bhi. Student "is a" Saveable nahi hai (family relation nahi), par "save ho sakta hai" (capability) hai. Multiple classes ek sath ye capability le sakti hain jo single inheritance se possible nahi tha.

</details>

3. `using System;` kya karta hai — bina iske kya hota?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `System` namespace ke type (`Console`, `Math`) seedhe use karne deta hai. Bina `using` ke poora naam likhna padega — `System.Console.WriteLine(...)`. Import (file load) nahi, sirf naam chhota karne wali facility.

</details>

4. Interface vs abstract class — project mein kaise decide karoge?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Ek hi family ka shared code/state ho toh abstract class (jaise sab employees ka common code). Alag-alag families ko ek rule/capability deni ho ya multiple capabilities chahiye hon toh interface. .NET mein dono milte hain — zaroorat ke hisaab se.

</details>
