Data store karne ke liye ek structure chahiye (tables), aur us structure mein actual data bharana padta hai (rows). Ye structure define karna aur data manage karna — ye kaam karta hai **DBMS**.

# DBMS vs RDBMS + Keys

## DBMS Kya Hai

**DBMS** = Database Management System. Koi bhi software jo data store, retrieve, aur manage karta hai.

Simple shabdon mein — data hai, usko organize karna hai, search karna hai, update karna hai. Ye sab kaam ek system karega — wo DBMS hai.

Real examples: MySQL, PostgreSQL, MongoDB, SQLite,甚至 Excel bhi technically ek DBMS hai (structured data store hai).

## RDBMS Kya Hai

**RDBMS** = Relational Database Management System. Data ko **tables** mein store karta hai (rows + columns), aur tables ke beech **relationships** define karta hai (foreign keys ke through).

```sql
-- Products table
CREATE TABLE products (
  product_id SERIAL PRIMARY KEY,
  name VARCHAR(100),
  price DECIMAL(10, 2)
);

-- Orders table — products se related
CREATE TABLE orders (
  order_id SERIAL PRIMARY KEY,
  product_id INTEGER REFERENCES products(product_id),
  quantity INTEGER
);
```

Ye "relationship" hai — `orders.product_id` actually `products.product_id` ko refer kar raha hai. RDBMS ye relationship enforce karta hai — tum galat `product_id` daal nahi sakte.

## DBMS vs RDBMS — Kya Fark Hai

| | DBMS | RDBMS |
|---|---|---|
| Data storage | Files, hierarchical, ya koi bhi format | Tables (rows + columns) |
| Relationships | Manually manage karna padta hai | Foreign keys se automatic |
| ACID support | Zaroori nahi | Hota hai (consistency guarantee) |
| Data integrity | Tum khud ensure karo | Database khud ensure karta hai |
| Example | MongoDB, File system | PostgreSQL, MySQL, SQLite |

**Simple:** DBMS = koi bhi data management system. RDBMS = ek specific type hai DBMS ka jisme data tables mein hota hai aur relationships foreign keys se define hote hain.

Interview mein jab poochhein "DBMS aur RDBMS mein difference," toh seedha bolo: "RDBMS ek specific type hai DBMS ka jisme data tables mein hota hai aur relationships foreign keys se define hote hain. Plain DBMS mein ye guarantee nahi hoti."

## Keys — Database Ke Identifiers

Har table mein rows ko uniquely identify karna hota hai. Iske liye **keys** use hoti hain.

### Primary Key

Har table mein ek column jo **har row ko uniquely identify** kare — ye Primary Key hai. Null nahi ho sakta, duplicate nahi ho sakta.

```sql
CREATE TABLE products (
  product_id SERIAL PRIMARY KEY,  -- ye Primary Key hai
  name VARCHAR(100),
  price DECIMAL(10, 2)
);
```

`SERIAL` ka matlab hai database khud ek number generate karta hai — 1, 2, 3... Har row ka ek unique `product_id`.

### Foreign Key

Ek table ka column jo **dusre table ke Primary Key ko reference** kare — ye Foreign Key hai. Ye relationship banata hai.

```sql
CREATE TABLE orders (
  order_id SERIAL PRIMARY KEY,
  product_id INTEGER REFERENCES products(product_id),  -- Foreign Key
  quantity INTEGER
);
```

`REFERENCES products(product_id)` — ye line database ko bolti hai ki `product_id` column mein sirf wahi values aayin jo `products` table mein exist karti hain. Agar tum galat `product_id` daaloge toh database error dega.

### Composite Key

Kabhi kabhi ek column akela unique nahi hota — do ya zyada columns milkar unique banate hain.

```sql
CREATE TABLE order_items (
  order_id INTEGER,
  product_id INTEGER,
  quantity INTEGER,
  PRIMARY KEY (order_id, product_id)  -- Composite Key
);
```

Ye kaam aata hai jab junction table banana ho — jaise "kis order mein kaunsa product hai." `order_id` akela unique nahi hai (ek order mein bahut saare items ho sakte hain), `product_id` akela unique nahi hai (ek product bahut saare orders mein ho sakta hai). But dono milkar unique hain.

### Candidate Key

Wo columns jo Primary Key ban sakte the (unique + not null) but nahi bane. Jaise `email` bhi unique ho sakta hai `users` table mein, but tumne `user_id` ko Primary Key banaya.

## DukaanOS Context — Real Schema

Apna Prisma schema socho:

```prisma
model Product {
  id        String   @id @default(uuid())
  name      String
  price     Float
  barcode   String   @unique
  orders    OrderItem[]
}

model Order {
  id        String   @id @default(uuid())
  date      DateTime
  items     OrderItem[]
}

model OrderItem {
  id        String   @id @default(uuid())
  orderId   String
  productId String
  quantity  Int
  order     Order    @relation(fields: [orderId], references: [id])
  product   Product  @relation(fields: [productId], references: [id])
}
```

Yahan:
- `Product.id`, `Order.id`, `OrderItem.id` — **Primary Keys** hain
- `OrderItem.orderId` — **Foreign Key** hai jo `Order.id` ko refer karta hai
- `OrderItem.productId` — **Foreign Key** hai jo `Product.id` ko refer karta hai
- `barcode String @unique` — ye Candidate Key hai (unique hai but Primary Key nahi bana)

Prisma automatically ye relationships samajhta hai — `@relation` directive se. But interview mein tumhe pata hona chahiye ki andar kya ho raha hai.

---

## What It Is NOT

⚠️ **Primary Key = sirf `id` column nahi.** Koi bhi column jo unique aur not null ho, Primary Key ban sakta hai. `barcode` bhi Primary Key ban sakta hai agar tum chaho.

⚠️ **Foreign Key mein duplicate values ho sakti hain.** Bahut saare orders mein ek hi `product_id` ho sakta hai. Sirf NULL nahi ho sakta agar required hai.

⚠️ **RDBMS = SQL nahi.** RDBMS ek system hai, SQL ek language hai. PostgreSQL RDBMS hai, SQL uski language hai. MongoDB DBMS hai, SQL nahi use karta.

## In Your Own Words

1. DBMS aur RDBMS mein kya fark hai? RDBMS kyun use karte hain?

<details>
<summary>Sample Jawab</summary>

**Jawab:** DBMS koi bhi data management system hai — file system bhi ho sakta hai. RDBMS ek specific type hai DBMS ka jisme data tables mein hota hai aur relationships foreign keys se define hote hain. RDBMS use karte hain kyunki ye data integrity ensure karta hai — tum galat data nahi daal sakte, relationships automatically maintain hoti hain, aur ACID transactions milte hain.

</details>

2. Agar tumhare `orders` table mein `product_id` column hai jo `products` table ke `product_id` ko refer karta hai, toh ye kya kehlata hai aur ye kyun zaroori hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Ye Foreign Key hai. Zaroori hai kyunki ye ensure karta hai ki `orders` mein sirf wahi `product_id` aaye jo `products` table mein exist karta hai. Agar tum galat product ID daaloge toh database error dega. Ye relationship maintain karta hai — data consistent rahega.

</details>

3. Composite Key kab use karni chahiye? Kya har table mein zaroori hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Composite Key tab use karte hain jab ek column akela unique nahi ho pa raha. Jaise `order_items` table mein — `order_id` aur `product_id` dono akle unique nahi, but milkar unique hain (ek order mein ek product sirf ek baar). Har table mein zaroori nahi — jab tak single column unique ho, kaam chal jaata hai.

</details>

4. Primary Key aur Candidate Key mein kya fark hai?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Candidate Key wo columns hain jo unique aur not null hain — ye Primary Key ban sakte the. Primary Key wohi hai jo actually select kiya gaya hai unique identifier ke roop mein. Jaise `users` table mein `user_id` aur `email` dono unique ho sakte hain (candidate keys), but `user_id` ko Primary Key banaya gaya.

</details>

5. Agar tum `products` table mein `barcode` column pe `@unique` lagao, toh ye kya karega?

<details>
<summary>Sample Jawab</summary>

**Jawab:** `@unique` ensure karega ki `products` table mein koi do products ke same barcode nahi ho sakte. Duplicate barcode daalne pe error aayega. Ye Candidate Key hai — unique hai but Primary Key nahi bana (Primary Key `id` hai). Practical use: voice billing mein barcode se product dhundhna hai, isliye unique hona zaroori hai.

</details>
