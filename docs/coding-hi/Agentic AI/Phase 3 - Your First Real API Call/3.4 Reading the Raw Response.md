Now you know how to structure your input — the messages array with user and assistant roles, system prompts setting the tone. But what comes back? When the model responds, it sends a JSON object packed with useful information. Not just the text reply, but token counts, stop reasons, model metadata. The kind of stuff that demystifies how Cline, opencode, and other tools work.

Let's open the hood and look at the full response.

# 3.4 Reading the Raw Response

We already glimpsed the response object in 3.2. Now let's take it apart properly. Understanding the raw response is what separates people who think AI is magic from people who know it's just a JSON API.

## Log the Whole Thing

Run this:

```javascript
import Groq from "groq-sdk";
import dotenv from "dotenv";
dotenv.config();

const client = new Groq({ apiKey: process.env.GROQ_API_KEY });

const completion = await client.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: [
    { role: "user", content: "List three colors." }
  ],
});

// Dump everything
console.log(JSON.stringify(completion, null, 2));
```

The `JSON.stringify(completion, null, 2)` formats the object with 2-space indentation so it's readable. You'll see something like:

```json
{
  "id": "chatcmpl-abc123def456",
  "object": "chat.completion",
  "model": "llama-3.3-70b-versatile",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Here are three colors:\n\n1. Red\n2. Blue\n3. Green"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 10,
    "completion_tokens": 24,
    "total_tokens": 34
  }
}
```

## Walking Through Every Field

### `id`
A unique identifier for this completion. Groq's API generates it server-side. It's useful for logging, debugging, and support tickets — if something goes wrong, you can reference this ID.

### `object`
Always `"chat.completion"` for this endpoint. This tells you what kind of response you got — useful if you're working with multiple API endpoints (streaming, etc.).

### `model`
Confirms which model produced the response. If you're trying different models, check this field to verify you're hitting the right one.

### `choices`
This is the payload you actually care about. It's an array of **response choices** (usually one, unless you set `n > 1`). Each choice has:

- **`index`**: The position of this choice (0 for the first/only one).
- **`message`**: The response message object:
  - **`role`**: Always `"assistant"`. This matters when you append the response to your conversation array — you'll push `{ role: completion.choices[0].message.role, content: completion.choices[0].message.content }` back so the model sees its own previous response next turn.
  - **`content`**: The model's text output. This is what you'll display to the user 90% of the time.
  - **`tool_calls`**: An array of tool call requests (coming in Phase 4).
- **`finish_reason`**: Why the model stopped generating.

You access the text like this:

```javascript
completion.choices[0].message.content
```

When tool calling enters the picture in Phase 4, you'd iterate over `tool_calls`:

```javascript
for (const choice of completion.choices) {
  if (choice.finish_reason === "tool_calls") {
    for (const tool of choice.message.tool_calls) {
      console.log("Model wants to call:", tool.function.name);
    }
  }
}
```

### `finish_reason`
Why the model stopped generating. This is useful for debugging:

| Value | Meaning |
|-------|---------|
| `"stop"` | The model finished its response naturally |
| `"length"` | The response was cut off because it hit the token limit |
| `"tool_calls"` | The model is requesting to use a tool (more in Phase 4) |

If you see `"length"`, your response was truncated. Increase `max_tokens` or make your prompt more specific.

### `usage`
Your bill. `prompt_tokens` is what you sent (your prompt + conversation history), `completion_tokens` is what the model generated. `total_tokens` is the sum. Multiply by the per-token rate for your model to get the cost.

## What Cline, opencode, and Kodu See

Every time Cline or Kodu or opencode calls a model, it gets back a response object just like this. It extracts `choices[0].message.content`, checks `finish_reason` to see if the model finished or hit a limit, reads `usage` to track costs, and uses `choices[0].message.role` to format the next request.

There's no secret sauce. It's the same JSON you're looking at right now. The difference is that coding tools wrap this in loops — they send a message, get a tool call, execute the tool, send the result back, get another response, and repeat until the task is done.

You now understand the bottom layer. Everything else is just orchestration.

Of course, orchestration doesn't matter if your code crashes. Let's look at what can go wrong.

---

## What It Is NOT

The response object is NOT just the text the model generated. It's a structured envelope with metadata that's critical in production. The `finish_reason` tells you if the response was truncated (`"length"`), the `usage` object is your billing receipt, and `model` confirms which engine processed your request. Ignoring these fields is like driving a car while only looking at the speedometer — you'll miss the fuel gauge and check engine light.

`JSON.stringify()` is also NOT something you'd use in a production app. It's a debugging tool to inspect what the API returns. In real code you'd access specific fields like `completion.choices[0].message.content` or iterate over choices, not dump the entire object.

### In Your Own Words

<details>
<summary>1. How would you check if the model requested a tool call vs returning text?</summary>

**Sample Answer:** Check `completion.choices[0].finish_reason`. If it's `"tool_calls"`, the model wants to call a tool and `completion.choices[0].message.tool_calls` will be populated. If it's `"stop"`, the model returned text normally. You'd branch your code based on `finish_reason` before deciding how to handle the response.

</details>

<details>
<summary>2. If you see `"finish_reason": "length"`, what are two different ways to fix it?</summary>

**Sample Answer:** You can increase `max_tokens` in your request to give the model more room to finish, or make your prompt more specific so the model gives a shorter answer. If the model keeps hitting the limit, it might be trying to generate a longer response than you anticipated — think of it like a suitcase that's too small for everything you're trying to pack.

</details>

<details>
<summary>3. The `usage` object shows `prompt_tokens` and `completion_tokens`. How would you calculate the total cost of a conversation with 5 turns?</summary>

**Sample Answer:** Sum the `prompt_tokens` and `completion_tokens` across all 5 responses, then multiply by the per-token rate for your model. Each turn's `prompt_tokens` includes the entire conversation history so far, so costs grow with each turn. It's like a taxi meter — the fare increases not just for distance traveled, but for every mile driven total.

</details>

<details>
<summary>4. Why does the response include a `model` field? When might it differ from what you requested?</summary>

**Sample Answer:** The `model` field confirms which model actually processed your request. If you're using a generic alias or a provider performs automatic failover, the actual model might differ from what you requested. The field is also useful for logging and auditing, especially if you're switching between models for A/B testing.

</details>

<details>
<summary>5. In the OpenAI/Groq format, how would you extract the assistant's message to append it back to your conversation array?</summary>

**Sample Answer:** You'd access `completion.choices[0].message` directly, since it already has both `role` and `content` fields. Push it straight into your array: `conversation.push(completion.choices[0].message)`. If the model made tool calls, those are in `message.tool_calls` and should be pushed as a separate assistant turn with the tool call data.</details>
