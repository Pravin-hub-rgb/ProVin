Tools give an agent power. But power without direction is just chaos. An agent needs to figure out *what to do first, what to do second, and what to do third*. That's planning.

There are two approaches agents take, and you've seen both:

![Two Approaches to Planning — Reactive Step-by-Step vs Planned Divide and Conquer](/diagrams/agenticai/planning-comparison.svg)

**1. Reactive (step-by-step):** The agent doesn't plan ahead. It just looks at the current situation and asks "what should I do next?" This is the basic ReAct loop you learned in 2.2. It works fine for simple tasks where each step is obvious from the previous result. Need to fix a bug? Read the error → find the file → edit the line → test again. Each step tells you what comes next.

**2. Planned (divide and conquer):** The agent first creates a full plan — a list of steps — and then executes them one by one. This is better for complex tasks where you'd get lost without a map.

Here's how "Build me a landing page" plays out with the second approach:

1. Agent thinks: *"I need a landing page. That means: create a project folder, write the HTML, write the CSS, add content, and test it in a browser."*
2. Agent creates the folder: `mkdir landing-page`
3. Agent writes `index.html` with a headline, subtext, and a CTA button
4. Agent writes `styles.css` with a clean modern design
5. Agent opens `index.html` in the browser to verify it works
6. Agent reports back: "Your landing page is ready at landing-page/index.html"

The key difference? The agent spent a few seconds *thinking about the whole task* before touching anything. That upfront thinking means it doesn't get halfway through and realize it forgot something important.

You've seen Cline or opencode do this. When you give it a big task like "build a full-stack todo app," the agent often pauses, thinks, then says something like "Here's my plan: first I'll set up the backend with Express, then create the React frontend, then connect them." That's the planned approach. Then it executes step by step, and if something goes wrong, it adapts.

The best agents do both. They start with a plan, then react to what happens during execution. If step 3 fails, they don't just blindly retry — they update the plan.

This is where the real magic happens. An agent that can plan, execute, and replan in real time feels less like a tool and more like a teammate.

## What It Is NOT

Planning is **not** a sign that the agent is "conscious" or "thinking like a human." The plan is just a structured text output — a list of steps the model generates based on the task. It's no different from asking a model to summarize an article. The model is still doing pattern matching on its training data, just aimed at the question "what steps would solve this problem?" It looks like human planning, but it's the same prediction engine you learned about in Phase 1, pointed at a different kind of output.

### In Your Own Words

<details>
<summary>1. Think of a task you'd break into a plan before starting. Now think of a task you'd just "figure out as you go." What's different about them?</summary>

**Sample Answer:** I'd plan before building a house (blueprints first, then build) but figure out as I go when cooking a stir-fry (taste and adjust). The difference is risk and reversibility. If a step in house-building is wrong, it's expensive to undo. If I overseason a stir-fry, I can dilute it. Agents should plan when mistakes are costly and react when adaptation is cheap.

</details>

<details>
<summary>2. Why is the planned approach risky? What happens if the agent's initial plan is wrong?</summary>

**Sample Answer:** A bad plan means the agent wastes time and resources executing steps that don't help. Worse, it might commit to a wrong approach early and ignore evidence that the plan needs to change. It's like following GPS into a lake — the GPS said "turn here," so you turn here. Plans need to be flexible, and agents need to notice when reality doesn't match the plan.

</details>

<details>
<summary>3. Have you seen Cline (or another agent) make a plan before acting? What did it look like? Did it follow the plan or change course?</summary>

**Sample Answer:** I've seen Cline or opencode say "Here's my plan: first set up the backend, then the frontend, then connect them." It usually follows the plan, but adapts when errors pop up — like if npm install fails, it tries a different approach. That combination — plan first, react during — is the sweet spot. It's like a road trip with a route but a willingness to take detours.

</details>

<details>
<summary>4. What's a task that would be too complex for reactive (step-by-step) planning? What makes it too complex?</summary>

**Sample Answer:** Building a multi-service microservice architecture from scratch. Reactive planning would work one file at a time and might create services that don't match on ports, APIs, or data formats. The complexity comes from the number of interconnected parts — you need an overarching design before you start, otherwise you'll paint yourself into a corner.

</details>

<details>
<summary>5. If an agent creates a bad plan, who's responsible — the agent or the person who gave it the goal? Why?</summary>

**Sample Answer:** The person. The agent is a tool, and like any tool, the user is responsible for the outcome. If your calculator gives you a wrong answer, you don't blame the calculator — you check the inputs. Similarly, you should review the agent's plan before it executes, especially for high-stakes tasks. As agents get better, this might shift, but today the human is still the one accountable.

</details>
