You now know the loop. But the loop needs something to act *on*. That's where **tools** come in.

A tool is just a capability the agent can invoke. Think of it as a function the model can call. The model doesn't magically *become* a file system — it makes a request to a tool that knows how to read and write files. The model doesn't *become* a web browser — it calls a tool that goes and fetches a page.

Here's a list of common tools you'll see agents using today:

| Tool | What it does | Why an agent needs it |
|------|-------------|----------------------|
| Read/write files | Create, edit, delete files on your machine | This is how Cline or opencode writes your code |
| Run commands | Execute shell commands, scripts, install packages | This is how Cline or opencode runs `npm install` or `git commit` |
| Search the web | Look up current information | For research, finding docs, checking APIs |
| Call APIs | Make HTTP requests to external services | Send emails, update databases, post to Slack |
| Browse web pages | Click links, fill forms, read rendered pages | For testing your app or scraping data |
| Query databases | Run SQL queries against a database | Pull customer data, update records, generate reports |
| Call other AI models | Ask another model for help | Use a specialized model for images, audio, or translation |

![Tools Available to Agents — Read/Write Files, Run Commands, Search Web, Call APIs, Browse Pages, Query Databases](/diagrams/agenticai/agent-tools.svg)

Every tool has three parts:
- A **name** (like `read_file`)
- Some **parameters** (like `filepath: "src/index.js"`)
- A **return value** (like the contents of the file)

The agent's job is to pick the right tool with the right parameters at the right time.

You've seen most of these in Cline or opencode already. These agents can read your files, write new ones, run terminal commands, search for patterns in your code, and even use the web. Every one of those is a tool. When Cline or opencode asks for permission before running a command, it's showing you which tool it wants to call and what parameters it plans to use.

This is also why agents need good context windows (remember Phase 1?). Every tool result gets fed back into the model's context as the "Observe" step. A tool that returns a huge file or a long web page eats up tokens. Managing that is part of what makes agent design hard.

---

Having tools is one thing. Knowing what to do with them is another. That's where planning comes in.

## What It Is NOT

Giving an agent tools does **not** mean the agent magically understands how to use them perfectly. The model still has to figure out which tool to call, with what parameters, and in what order. It can guess wrong — calling a write_file tool when it should have called a search tool, or running a command with the wrong flags. Tools are like giving a carpenter a new power tool. The tool is powerful, but the carpenter still needs to know when to use it and how to handle it safely.

### In Your Own Words

<details>
<summary>1. Pick three tools from the list. For each one, describe a task you'd want an agent to do that uses that tool.</summary>

**Sample Answer:** (1) Run commands — automatically install npm dependencies and start a dev server when I open a project. (2) Search the web — look up the latest React docs to find the correct hook syntax. (3) Call APIs — post a daily standup summary to our Slack channel without me copying and pasting. Each tool lets the agent do something I'd otherwise do myself.

</details>

<details>
<summary>2. What happens if an agent doesn't have a tool it needs? Let's say it needs to send an email but has no email API tool. What should it do?</summary>

**Sample Answer:** The agent should tell you it can't complete the task and explain what's missing. A good agent would say: "I can't send emails directly, but here's the draft content — you can paste it into your email client." It shouldn't silently fail or pretend it succeeded. Honesty about capability is part of being trustworthy.

</details>

<details>
<summary>3. You've seen Cline request permission before running commands. Why do you think agents ask for confirmation instead of just acting? Is that a feature or a limitation?</summary>

**Sample Answer:** It's a feature disguised as a limitation. Asking for permission is a safety guardrail — agents can make mistakes, and you'd rather say "no" before a destructive command runs than recover from disaster. Over time, as trust builds, you might reduce confirmation frequency. It's like letting a junior developer push to production: you want a code review at first, even if it slows things down.

</details>

<details>
<summary>4. If you could give an agent one new tool that isn't in the list, what would it be? Be creative.</summary>

**Sample Answer:** A "send push notification" tool that pings my phone. The agent could tell me "build finished with errors" or "deployment succeeded" without me staring at a terminal. It turns the agent from something I watch into something that watches for me — it pushes information instead of waiting for me to pull it.

</details>

<details>
<summary>5. How does the "tool result uses up tokens" problem affect what kinds of tasks an agent can handle? What's a task that would be hard because of this?</summary>

**Sample Answer:** Tasks that involve large files or many steps become expensive. For example, asking an agent to refactor a 10,000-line file means every time it reads or writes, it consumes thousands of tokens just for the file content. Eventually the context window fills up and the agent loses track of earlier steps. It's like trying to assemble IKEA furniture on a table that can only hold three instruction pages at a time — you keep having to swap pages in and out.

</details>
