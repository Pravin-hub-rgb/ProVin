You've built an agent that can call tools. Feels good, right? You wire up a prompt, the model decides to call `search_files`, you get the result back, and it answers. But there's a catch — after each API call, the model forgets everything. Every call starts from a blank slate. If you want it to "remember" what happened in a previous turn, you must send the entire history yourself, every single time.

That's because LLMs are **stateless**. The model has no built-in memory. It doesn't know you asked it to "find all TODO comments" two turns ago unless you cram that info back into the next request. The API doesn't keep state between calls — you are the one responsible for carrying the backpack of past conversation.

Let me show you exactly what this looks like with the dark/light theme example. Imagine you're in a session and this happens:

```
You: Create a dark theme and a light theme for this website.
Cline: Let me read the current styles.css first. [Reads file]
Cline: I'll add CSS variables for theming. [Writes code]
Cline: Done! The dark theme uses --primary-dark: #0f0f23.
You: Change the dark theme background to something slightly lighter.
Cline: [Writes new code with the updated color]
...20 more exchanges about other parts of the project...
You: Remember we set --primary-dark to #0f0f23 earlier? Change it to #1a1a3e.
Cline: I don't see that variable in the current styles.css. Where should I add it?
```

The agent didn't forget — the conversation where you first specified `--primary-dark` got pushed out of the context window to make room for the 20 newer exchanges. Each API call is stateless. The model literally has no access to that earlier conversation anymore because you stopped sending it.

![Stateless vs Stateful — Each API Call Starts Fresh, No Memory Between Calls](/diagrams/agenticai/stateless-vs-stateful.svg)

Without memory, an agent can't track progress. It can't learn from earlier steps. It can't say "oh wait, I already tried that approach and it failed." Every turn is a fresh attempt with zero context of what just happened. Imagine debugging code where you can't remember the last line you wrote. That's your agent without memory.

You've probably felt this already. Ever been in a long session with Cline or opencode where the agent starts repeating itself or forgets something you told it twenty messages ago? That's the context window overflowing. The model didn't "forget" in the human sense — the old stuff got pushed out because you hit the token limit. Or maybe you expected it to remember a preference you stated early on, but it acted like you never said it. Frustrating, right?

That's why context management is a real skill. Knowing how to manage what the model sees, what it remembers, and when to trim or summarize is the difference between a toy agent and one that can actually do multi-step work. This entire phase is about that skill.

We're going to look at the different kinds of memory, how to handle conversation history, how system prompts shape behavior, and finally how RAG lets agents work with knowledge that doesn't fit in the context window at all. Let's start with the types of memory an agent can use.

---

## What It Is NOT

Statelessness is **not** the model being forgetful like a person with bad memory. Your friend might forget what they ate for breakfast — that's a memory failure. An LLM was never "told" the previous message in the first place. It's a deliberate architectural decision: each API call is independent so the system scales horizontally, any server can handle any request, and you don't need sticky sessions. Statelessness isn't a flaw — it's what lets services like Cline and opencode run reliably across millions of concurrent requests without shared state.

### In Your Own Words

<details>
<summary>1. Why can't an LLM remember what was said in a previous API call?</summary>

**Sample Answer:** Because each API call is completely independent — the model gets a fresh start every time. It's like handing a calculator a math problem: it solves it, clears the screen, and waits for the next input. You have to type the whole history again because the calculator never stored the previous problem.

</details>

<details>
<summary>2. Have you experienced an AI assistant forgetting something mid-session? What happened?</summary>

**Sample Answer:** Most people have. The assistant didn't "forget" like a human — older parts of the conversation got pushed out of the context window when it filled up. It's like taking notes on a small whiteboard: when you run out of space, you have to erase something to write something new.

</details>

<details>
<summary>3. Why is statelessness actually a design choice, not a bug?</summary>

**Sample Answer:** Statelessness makes the API simple, scalable, and reliable. Each request can go to any server — no sticky sessions, no state synchronization, no consistency headaches. If the model had built-in memory, you'd need to track which server handled which request and sync state across machines. Statelessness avoids all that complexity by design.

</details>

<details>
<summary>4. What goes wrong when an agent can't track its own progress across multiple steps?</summary>

**Sample Answer:** It repeats work, makes the same mistakes, and can't build on earlier findings. It's like a painter who forgets which walls they've already painted and keeps going over the same spot, while missing others entirely.

</details>

<details>
<summary>5. If you had to explain "context window" to another developer, how would you describe it?</summary>

**Sample Answer:** The context window is the model's desk space. Everything currently on the desk is visible and usable — recent conversation, files, instructions. But the desk only holds so much. When it fills up, you have to file old papers away (or throw them out) to make room for new ones. The model can only work with what's currently on the desk.

</details>
