The simplest and most essential memory technique: keeping track of the conversation so the agent knows what's been said.

Here's the core idea. Every API call to an LLM takes a list of messages. You start with a system message (we'll talk about that in 5.4), then the user says something, the assistant responds, the user says something else, and so on. Each turn, you append both the user's message and the assistant's response to the array. Then you send the whole thing with the next request. That's it. That's conversation history.

```
Turn 1: [system] + [user: "find all TODOs"] → [assistant: "found 3"]
Turn 2: [system] + [user: "find all TODOs"] + [assistant: "found 3"] + [user: "show me the first one"] → [assistant: shows it]
```

But there's a problem: every token costs money, and context windows are finite. As the conversation grows, you'll eventually hit the limit. Now you need a strategy.

![Three Strategies for Conversation History — Sliding Window, Summarization, Relevance Filtering](/diagrams/agenticai/history-management.svg)

The simplest approach is a **sliding window**. Decide on a maximum number of messages — say 20. When the conversation exceeds that, drop the oldest messages (but keep the system prompt). This is what most chat UIs do. It's crude but effective. The agent loses the oldest context, but it can still follow the recent thread.

A better approach is **summarization**. When the conversation gets too long, ask the model to summarize everything up to a certain point. Then replace the old messages with that summary. The agent loses detail but keeps the gist. This is more expensive (one extra API call to summarize), but it preserves more useful context.

An even more targeted approach is **relevance filtering**. Instead of keeping everything or summarizing blindly, you keep only the turns that are relevant to the current task. If the agent spent five turns debugging a CSS issue and now you're asking about the database schema, drop the CSS turns. This requires some logic on your end to decide what's relevant, but it's the most efficient use of the context window.

You'll likely start with the sliding window — it's dead simple and works fine for short sessions. As your agent gets more complex, you'll want to graduate to summarization or relevance filtering.

One important detail: always keep the system prompt. It's your anchor. We're going to talk about exactly that next.

---

## What It Is NOT

Conversation history management is **not** giving the model actual memory. The model remains stateless — it still forgets everything between API calls. You're just curating what it sees on each turn, like a movie editor choosing which scenes to include in the final cut. The model never "remembers" anything on its own; you're the one reconstructing the past and handing it to the model fresh each time.

### In Your Own Words

<details>
<summary>1. What happens to the oldest messages when you use a sliding window?</summary>

**Sample Answer:** They get dropped entirely — gone from the context. It's like a conveyor belt: new items go on, old items fall off the edge. The agent can no longer reference anything that was in those old messages.

</details>

<details>
<summary>2. When would summarization be better than just dropping old messages?</summary>

**Sample Answer:** When the dropped messages contain important context that you can't afford to lose entirely. Summarization is like writing an executive summary of a long meeting — you lose detail but keep the key decisions and outcomes. This is better than just shredding the meeting notes.

</details>

<details>
<summary>3. How would you decide which turns are "relevant enough" to keep?</summary>

**Sample Answer:** Look for topic shifts. If the conversation moved from debugging CSS to designing a database schema, the CSS turns are no longer relevant. You can use keywords, detect tool calls, or simply track when the user changes the subject. The goal is to keep only what helps answer the current question.

</details>

<details>
<summary>4. What's the cost trade-off of using summarization vs. dropping messages?</summary>

**Sample Answer:** Summarization costs one extra API call per summary but preserves useful context in a condensed form. Dropping messages is free but can lose critical information. It's like the choice between compressing a file (costs CPU time but saves the data) or just deleting it (saves resources but the data is gone forever).

</details>

<details>
<summary>5. If you had a conversation with 100 turns, what strategy would you use?</summary>

**Sample Answer:** I'd combine approaches: keep a sliding window of the most recent 20-30 turns for immediate context, and summarize the earlier turns into a condensed overview. If I can detect topic shifts, I'd add relevance filtering to drop unrelated turns. This gives the agent both the recent thread and the big picture from earlier context.

</details>
