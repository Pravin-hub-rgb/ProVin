Not all memory is the same. When people say "the agent remembers," they could mean four very different things. Let's break them down so you know which one you're dealing with and when to use each.

![Four Types of Memory in Agents — In-Context, External, In-Weights, In-Cache](/diagrams/agenticai/four-memory-types.svg)

**In-context memory.** This is everything inside the current context window — the messages array you send with each API call. It's the most common form of memory you'll work with. You literally put the past conversation into the next request. It's temporary, limited by token count, and costs you tokens every time. When the window fills up, stuff gets dropped. This is the "memory" you're managing when you trim old messages or summarize them. As a builder, this is your daily bread.

**External memory (vector stores).** Sometimes in-context isn't enough. You want the agent to remember facts across sessions, or you want it to search through a large codebase. That's where external memory comes in. You store information in a database — usually a vector database — and retrieve the relevant pieces when needed. The agent doesn't see everything; it sees only what you fetch. This is how RAG works, how Cline or opencode searches your project files, and how agents can "know" about documentation they were never trained on. We'll dig into this in 5.5.

**In-weights memory.** This is what the model learned during training. All the facts, patterns, language rules, and reasoning abilities are stored in the neural network weights. You can't change this at runtime. You can't add your company's internal docs to it. It's permanent (until the next training run). Think of it as the model's education — everything it learned before you ever started talking to it.

**In-cache memory.** This is more advanced and we won't go deep, but you should know it exists. Some systems cache intermediate computation states to speed up repeated requests. If the same prompt comes in, the system can reuse previously computed activations rather than running the full model again. It's a performance optimization, not really a memory you control as a developer.

For you, the two that matter are **in-context memory** and **external memory**. In-context is what you use when the agent is having a conversation. External memory is what you use when the agent needs to know more than fits in one window. Everything else is infrastructure.

The most basic form of memory management — and the one you'll implement first — is handling conversation history. Let's look at how that works.

## What It Is NOT

These four memory types are **not** mutually exclusive — real agents use all of them simultaneously. In-context memory doesn't replace external memory, and external memory doesn't replace in-weights memory. They're like tools in a toolbox: you grab the right one for the job, and often you use several at once. A customer support bot, for example, uses in-context memory for the current conversation, external memory for product documentation, and in-weights memory for general language understanding.

### In Your Own Words

<details>
<summary>1. Which type of memory changes when you switch from GPT-4 to Claude?</summary>

**Sample Answer:** In-weights memory changes. That's the knowledge and reasoning patterns embedded in the model's parameters during training. Each model has different training data, architecture, and learned behavior — switching models is like hiring a different employee with different education and experience.

</details>

<details>
<summary>2. Why can't you just throw everything into in-context memory forever?</summary>

**Sample Answer:** Finite context window and cost. Every token costs money and the window has a hard limit. Think of it as trying to keep every sticky note you've ever written pinned to your desk — eventually there's no room on the desk and you can't find the one you need anyway.

</details>

<details>
<summary>3. When would you choose external memory over in-context memory?</summary>

**Sample Answer:** When the information is too large to fit in context, needs to persist across user sessions, or needs to be searchable. For example, a support agent referencing a product manual with thousands of pages — you can't put that in a prompt, but you can store it in a vector database and retrieve relevant sections as needed.

</details>

<details>
<summary>4. What's an example of in-weights memory affecting how an agent behaves?</summary>

**Sample Answer:** The model knowing programming syntax, world facts, language rules — all from training. If you ask about Python list comprehensions, the model isn't reading documentation — it's using what's stored in its weights. That's why a model trained before 2023 won't know about events from 2024; its in-weights memory is frozen at training time.

</details>

<details>
<summary>5. If you were building a customer support bot, which memory types would it need?</summary>

**Sample Answer:** All three main types. In-context memory for tracking the conversation flow. External memory for product documentation, past tickets, and knowledge base articles. In-weights memory for general language understanding and reasoning. In-cache memory might help with performance at scale, but it's optional.

</details>
