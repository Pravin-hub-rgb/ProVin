In 1.1, you learned that a language model predicts text one word at a time. But here's something I glossed over: when I said the model predicts "one word at a time," I was lying a little. It doesn't actually predict words. It predicts something smaller — and understanding what that something is changes how you think about everything the model does.

Let me back up. Think about how you read. You look at a word like "unbelievable" and you see one unit — one chunk of meaning. The model doesn't work that way. It sees that word as pieces: maybe "un" and "believable." Maybe even smaller. It breaks everything down before it can understand anything.

Those pieces are called **tokens**.

A token is the smallest piece of text a model can process. It's the atomic unit of its universe. When you send a message — whether it's "create a dark theme" or a 500-line CSS file — the model isn't looking at letters or whole sentences or even whole words. It breaks everything down into tokens first, then processes those tokens one by one.

Now here's where it gets interesting: tokens are not words. They're sub-word chunks.

# 1.2 Tokens: The Atomic Units of AI Language

Take the word "unbelievable." A model might split it into two tokens: "un" and "believable." The word "running" might be one token. A common word like "the" is usually one token. A rare word like "antidisestablishment" might be three or four.

Why does the model do this? Because it needs to handle any word it might encounter, including ones it's never seen before. If it only knew whole words, it'd be helpless against typos, compound words, or new terminology. By learning sub-word pieces, it can assemble meaning from familiar building blocks — like a child who's never seen "unbelievable" but knows what "un" and "believable" mean separately.

You can actually see this in action. Most AI providers have a tokenizer tool where you paste text and it shows you exactly how it gets chopped up. The results are sometimes surprising. "Hello!" might be one token, but "Hello?" might be two because the question mark is less common. Spaces, punctuation, even capitalization all affect how things get split.

Here's a rough rule of thumb: **1 token ≈ 0.75 words in English.** So a 500-word email is around 650 tokens. But this varies a lot — code tends to be more token-dense than prose because of indentation, special characters, and long variable names.

Let's make this concrete with a real example. Remember the dark/light theme example from 1.1? Here's what that prompt looks like when it gets tokenized:

> "Create a dark theme and a light theme for this website"

Notice "a" gets its own token, "dark" is one token, "theme" is one token. Now imagine the full context — your system prompt, the conversation history, the `styles.css` file you attached. A 200-line CSS file could be 800-1200 tokens. A conversation with 10 back-and-forth messages could be another 2000 tokens. All of that gets tokenized before the model even starts predicting.

This is why large files eat up your token budget so fast. Every line of CSS, every comment, every extra space — it all gets counted.

Why should you, as a vibe coder, care about any of this? Two big reasons:

First, **everything costs tokens.** Every message you send, every file you ask the model to read, every response it generates — that's all metered in tokens. It's like a taxi meter running the whole conversation — every word you type and every word the model writes clicks the meter forward. When you're using Cline or opencode and you upload a large file, you're burning through your available token budget. Models have a maximum they can handle, called the context window.

Second, **token awareness helps you prompt better.** If you know the model sees "un" and "believable" as separate tokens, you understand why it might occasionally lose the relationship between them in a very long conversation. You start to think in terms of the model's granularity, not your own.

## What It Is NOT

Tokens are NOT characters or bytes. A tokenizer isn't just splitting on spaces and punctuation — it uses a statistical algorithm (Byte Pair Encoding) trained on millions of documents to find the most efficient chunks. That's why a common word like "the" might be one token, but a rare one like "xylophone" might break into several. Think of it like a chef who pre-minces garlic because they use it constantly but leaves a whole truffle to be shaved fresh — common things get treated as one unit, rare things get broken down.

So that's tokens: not words, not letters — somewhere in between. They're the currency of every interaction you have with an AI. And they live inside something called a **context window**, which is exactly what's up next.

### In Your Own Words

<details>
<summary>1. Why do models use sub-word tokens instead of whole words? What problem does that solve?</summary>

**Sample Answer:** If models only knew whole words, they'd be helpless against typos, compound words, or new terms like "cryptocurrency" when it first appeared. Sub-word tokens let the model assemble meaning from smaller building blocks — like a kid who's never seen "unbelievable" but can figure out "un" + "believable." It's the difference between having a fixed dictionary of 50,000 words versus being able to construct any word from a set of 10,000 pieces.

</details>

<details>
<summary>2. Open your AI tool and think about the last file you asked it to read. Roughly how many tokens do you think that file was? How did that affect the conversation?</summary>

**Sample Answer:** A 1000-line JavaScript file is roughly 8,000–12,000 tokens. If your model has a 128K context window, that one file takes up about 10% of your budget — meaning you have less room for conversation and additional context. It's like packing a suitcase: that file is your winter coat, and every other file you add means something else might not fit, or the conversation history (your socks and shirts) gets pushed out.

</details>

<details>
<summary>3. A character like a semicolon in code takes up one token. A whole function definition might take dozens. How might tokenization affect the way a model "sees" your code differently than you do?</summary>

**Sample Answer:** You see a function as a single logical unit — "this block handles authentication." The model sees it as a flat sequence of dozens of individual tokens, each with equal weight. A misplaced semicolon takes up one token, just like a well-named variable. The model has no sense that some tokens are more important than others — it's like reading a book where every character, every space, and every punctuation mark has the same significance. A typo and a plot twist both occupy the same footprint.

</details>

<details>
<summary>4. Can you think of a situation where splitting a word into multiple tokens could cause the model to lose some meaning or nuance?</summary>

**Sample Answer:** Take a word like "breakdown" — if the model tokenizes it as "break" + "down", it might lean toward the literal meaning (something falling apart) when you meant it as a psychological or mechanical term. Each token carries its own associations from training, and reassembling them can subtly shift the meaning. It's like a game of telephone happening inside the model itself — the more pieces a word gets split into, the more chances there are for meaning to drift.

</details>
