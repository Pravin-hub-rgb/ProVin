So the model can ask to use tools. But how does it even know what tools exist? You have to tell it. You define tools by saying: "Here's what you have, what each one does, and what parameters they take."

The model doesn't magically know about `read_file` or `execute_command`. You describe each tool in a format the model understands — JSON.

### The Anatomy of a Tool Definition

![Anatomy of a Tool Definition — Name, Description, and Input Schema](/diagrams/agenticai/tool-definition.svg)

Every tool needs three things:

- **name**: A short identifier the model uses to call it
- **description**: What the tool does, in plain language. This is how the model *decides* when to use it
- **parameters**: The parameters the tool expects, described using JSON Schema

Here's what a tool definition looks like in the Groq SDK format (OpenAI-compatible):

```javascript
const tools = [
  {
    type: "function",
    function: {
      name: "calculator",
      description: "Evaluate a mathematical expression. Use this when the user asks you to do math.",
      parameters: {
        type: "object",
        properties: {
          expression: {
            type: "string",
            description: "The math expression to evaluate, e.g. '2 + 2' or 'sqrt(16)'"
          }
        },
        required: ["expression"]
      }
    }
  }
];
```

Let's break it down:

- `type: "function"` — This tells the API this is a tool definition (the standard OpenAI format)
- `function.name: "calculator"` — The model will say "I want to call `calculator`"
- `function.description` — This is the model's only hint about when to use this tool. Make it clear and specific. If the description is bad, the model will misuse the tool
- `function.parameters.properties` — Each parameter gets a `type` (string, number, array, etc.) and a `description`
- `function.parameters.required` — Which parameters the model must provide

### JSON Schema Is Your Language

The `parameters` field uses JSON Schema format. You don't need to be an expert, but you need to know the basics:

```javascript
parameters: {
  type: "object",
  properties: {
    filename: {
      type: "string",
      description: "Path to the file to read"
    },
    line_count: {
      type: "number",
      description: "How many lines to read"
    },
    show_line_numbers: {
      type: "boolean",
      description: "Whether to prefix each line with its number"
    }
  },
  required: ["filename"]
}
```

This describes a tool that takes three parameters: a required filename string, an optional line count, and an optional boolean. The model looks at this schema and knows exactly what JSON to generate.

### How the Model Sees Tools

When you call the API, you pass the tools array alongside your messages. Here's a minimal example with the Groq SDK:

```javascript
import Groq from "groq-sdk";

const client = new Groq();

const response = await client.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: [
    { role: "system", content: "You are a helpful assistant with tools." },
    { role: "user", content: "What is 14 * 37?" }
  ],
  tools: tools  // <-- the array we defined above
});
```

When the model decides it needs the calculator, it won't return plain text. It'll populate `response.choices[0].message.tool_calls` in the response. We'll see exactly what that looks like in the next section.

### The Model Decides, Not You

You don't tell the model *when* to use a tool. You just describe what's available and let the model decide. The model's training has taught it patterns like: "If the user asks a math question, I should use the calculator tool." Your descriptions reinforce that.

A bad description leads to bad behavior:

```javascript
// Bad — too vague
{ description: "A calculator tool" }

// Good — tells the model when to reach for it
{ description: "Evaluate mathematical expressions. Use this for any arithmetic, algebra, or numeric computation rather than doing math yourself." }
```

The description is your only leverage. Make it count.

### What We Just Built

That `tools` array is the interface between the model and the real world. The model says "I want this" using the names and schemas you defined. Your code listens for those names and executes the matching function.

## What It Is NOT

Defining tools is **not** the same as writing the functions that implement them. A tool definition is metadata — a description and a schema — that tells the model what tools exist. You still need separate JavaScript functions that actually do the work. The definition is the menu; the function is the kitchen that cooks the food.

**Sample Answer:** The description is the model's only guidance for deciding when to use a tool. If it's vague, the model will misuse it — like using a calculator tool for question-answering because you wrote "use this for everything." A good description is like a clear label on a button; a bad one is like an unlabeled button that the model will press just to see what happens.

</details>

<details>
<summary>3. What is JSON Schema used for in tool definitions?</summary>

**Sample Answer:** JSON Schema describes the parameters a tool expects — their names, types (string, number, boolean, etc.), and which ones are required. The model reads this schema and knows exactly what JSON to generate when it calls the tool. It's like a fill-in-the-blank form where the blanks have labels saying "enter a number here" or "enter text here."

</details>

<summary>4. When you send a tools array to the API, who decides *which* tool to use — you or the model?</summary>

**Sample Answer:** The model decides. You just describe what's available and let the model choose based on the descriptions and the user's question. You're not a puppeteer — you're a shopkeeper laying out your wares and letting the customer pick what they need.

</details>

<summary>5. If you defined a tool called `delete_all_files` with no description, do you think the model would ever call it? Why or why not?</summary>
