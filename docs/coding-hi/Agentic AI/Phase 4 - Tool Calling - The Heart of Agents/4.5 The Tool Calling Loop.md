The examples so far handle one round of tool calls. But real agents keep going. The model calls a tool, gets the result, decides if it needs another tool, calls again, and only stops when it has enough information to answer in plain text.

That's the **agent loop** — the same loop from Phase 2, now in actual code. It's just a `while` loop.

### The Full Agent Loop

Here's the pattern that powers every AI agent:

```javascript
import Groq from "groq-sdk";

const client = new Groq();

// --- Tool Definitions ---
const tools = [
  {
    type: "function",
    function: {
      name: "calculator",
      description: "Evaluate a mathematical expression.",
      parameters: {
        type: "object",
        properties: {
          expression: { type: "string", description: "The math expression" }
        },
        required: ["expression"]
      }
    }
  },
  {
    type: "function",
    function: {
      name: "get_current_date",
      description: "Get today's date.",
      parameters: {
        type: "object",
        properties: {}
      }
    }
  }
];

// --- Tool Implementations ---
function calculator(expression) {
  try {
    return String(eval(expression));
  } catch (err) {
    return `Error: ${err.message}`;
  }
}

function getCurrentDate() {
  return new Date().toISOString().split("T")[0];
}

async function executeToolCall(name, input) {
  switch (name) {
    case "calculator": return calculator(input.expression);
    case "get_current_date": return getCurrentDate();
    default: return `Unknown tool: ${name}`;
  }
}

// --- The Agent Loop ---
const messages = [
  { role: "system", content: "You are a helpful assistant with tools." },
  { role: "user", content: "How many days until Christmas from today? First get today's date, then calculate." }
];

// Loop until the model decides to stop calling tools
while (true) {
  const response = await client.chat.completions.create({
    model: "llama-3.3-70b-versatile",
    messages: messages,
    tools: tools
  });

  const message = response.choices[0].message;

  // Check if the model produced any tool calls
  if (!message.tool_calls || message.tool_calls.length === 0) {
    // No tool calls — the model is giving us the final answer
    console.log("Assistant:", message.content);
    break;
  }

  // Add the assistant's response (with tool_calls) to history
  messages.push({
    role: "assistant",
    content: message.content || "",
    tool_calls: message.tool_calls
  });

  // Execute each tool and collect results
  for (const toolCall of message.tool_calls) {
    const args = JSON.parse(toolCall.function.arguments);
    const result = await executeToolCall(toolCall.function.name, args);
    console.log(`  → ${toolCall.function.name}: ${JSON.stringify(args)} => ${result}`);

    // Send each tool result back
    messages.push({
      role: "tool",
      content: result,
      tool_call_id: toolCall.id
    });
  }

  // Loop continues — model gets tool results and decides what to do next
}
```

### What's Different Here

This is the real deal. Let's trace through what happens:

1. **First API call**: The model gets "How many days until Christmas?"
2. Model outputs: `tool_calls[0] = { function: { name: "get_current_date", arguments: "{}" } }`
3. Your code executes `getCurrentDate()` → returns `"2026-06-14"`
4. Result is sent back. Loop continues.
5. **Second API call**: Model sees today's date, now needs to calculate the difference
6. Model outputs: `tool_calls[0] = { function: { name: "calculator", arguments: "{...}" } }`
7. Your code runs the calculator. Result sent back. Loop continues.
8. **Third API call**: Model has the number of days
9. Model outputs: `message.content: "There are 194 days until Christmas."`
10. No `tool_calls` → `if (!message.tool_calls)` → `break`. Loop ends.

The loop handles any number of rounds automatically. The model leads, and your code follows until the model says "I'm done."

### Breaking Down the Key Parts

**The while(true) loop** — This keeps running until we explicitly break. Each iteration is one round of "model thinks → executes tools → gets results."

**Checking for tool_calls** — `message.tool_calls` gives us all the tools the model wants to call in this response. If `message.tool_calls` is undefined or empty, we're done.

**Pushing assistant message before results** — We push the entire message (which includes `tool_calls`) as the `assistant` role. This tells the API: "The assistant already called these tools, here are the results." Without this, the model gets confused.

**Each tool result gets its own message** — Even if the model called multiple tools at once, each result goes into the conversation history separately with `role: "tool"`. The `tool_call_id` tells the API which tool call each result belongs to.

### Running It Yourself

Save this as `agent-loop.mjs` and run it with:

```bash
node agent-loop.mjs
```

You'll see output like:

```

Assistant: There are 193 days until Christmas.
```

Notice the model called `calculator` twice! It first got a decimal, realized it should round down, and called again. The loop handled both automatically because it doesn't stop until there are no more `tool_calls`.

### What We've Built

This loop is the engine of every agent. Cline runs this same pattern. opencode runs this same pattern. Every AI coding tool is a while loop checking for tool calls:

```
while model is not done:
  call model with tools
  if message.content and no tool_calls → done, print it
  if tool_calls exist → execute, send results back, repeat
```

That's it. That's the secret sauce. Not magic. Not AGI. A while loop and a switch statement.

## What It Is NOT

The `while(true)` loop is **not** truly infinite. The model will eventually stop calling tools and return plain text — it's trained to do so. A real safety concern is a buggy tool that keeps returning confusing results, making the model call it again in a loop. That's why production agents add a max iteration limit. Also, the loop is **not** the model driving — it's your code driving. The model is just a passenger giving directions; your code decides when to stop.

## A Better Analogy: The Waiter and the Kitchen

Think of the agent loop as a waiter (your code) and a chef (the model). The waiter asks the chef what they need. The chef says "I need onions." The waiter fetches onions. The chef says "Now I need a pan." The waiter fetches a pan. The chef says "Now I need fire." The waiter lights the fire. The chef says "The soup is ready" — the waiter serves it. The waiter keeps going back and forth until the chef is satisfied. That's the loop.

<details>
<summary>1. Why do we use a `while (true)` loop instead of just handling one round of tool calls?</summary>

**Sample Answer:** Because we don't know in advance how many tools the model needs to call. It might need one, two, or five rounds. The `while(true)` loop keeps going until the model signals it's done by returning plain text. One round would fail if the model's first tool call's result triggers the need for a second tool call — like checking the date, then calculating, then formatting.

</details>

<details>
<summary>2. What is the stop condition that ends the loop? How does the model signal it's done?</summary>

**Sample Answer:** The loop stops when `message.tool_calls` is undefined or empty — meaning the model only returned plain text. The model signals "I'm done" by just answering in words instead of asking for a tool. It's like the chef saying "the food is ready" instead of asking for more ingredients.

</details>

<details>
<summary>3. Trace through what happens if the model calls three tools in sequence. How many API calls happen?</summary>

**Sample Answer:** Four API calls total. Call 1: model returns first tool call. Your code executes it, sends result back. Call 2: model sees result, returns second tool call. Your code executes it, sends result back. Call 3: model sees result, returns third tool call. Your code executes it, sends result back. Call 4: model has all the info, returns plain text. Loop ends with `break`.

</details>

<details>
<summary>4. Why do we push the assistant's response to messages *before* executing the tools? What would break if we reversed the order?</summary>

**Sample Answer:** The message history needs to show the model's tool call *before* the tool result, because the result is a response to the model's request. If you reversed the order, the conversation would show a tool result with no preceding tool call — like serving food before anyone ordered. The API would either reject it or the model would be confused about what the result is for.

</details>

<details>
<summary>5. This loop gives the model infinite opportunities to call tools. How would you add a safety limit so it doesn't run forever?</summary>

**Sample Answer:** Add a counter that increments each loop iteration and a maximum (say 25). When the counter hits the limit, stop the loop and print "Agent exceeded maximum iterations." You could also check for repeated identical tool calls — if the model calls the same tool with the same input three times in a row, something is wrong and you should bail out.

</details>
