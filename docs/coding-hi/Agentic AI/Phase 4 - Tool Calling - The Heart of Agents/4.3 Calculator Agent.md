Enough theory. Let's build a working calculator agent from scratch. We'll define a tool, wire it up, call the model, execute the tool, and send the result back. You'll see the entire tool calling loop in action.

Create a new file called `calculator-agent.mjs` and follow along. Every line is explained.

### Step 1: Imports and Setup

```javascript
import Groq from "groq-sdk";

const client = new Groq();
```

We import the Groq SDK and create a client. You'll need your `GROQ_API_KEY` set in your environment or you can pass it directly: `new Groq({ apiKey: "gsk_..." })`.

### Step 2: Define the Tool

```javascript
const tools = [
  {
    type: "function",
    function: {
      name: "calculator",
      description: "Evaluate a mathematical expression. Returns the numeric result.",
      parameters: {
        type: "object",
        properties: {
          expression: {
            type: "string",
            description: "The mathematical expression to evaluate, like '2 + 2' or 'Math.sqrt(16)'"
          }
        },
        required: ["expression"]
      }
    }
  }
];
```

We define one tool called `calculator`. It takes one required parameter: `expression`, a string. The model will fill in `expression` when it calls this tool.

### Step 3: The Actual Tool Function

```javascript
function calculator(expression) {
  try {
    const result = eval(expression);
    return String(result);
  } catch (err) {
    return `Error: ${err.message}`;
  }
}
```

This is the JavaScript function that actually does the work. When the model asks for the calculator, *our code* will call this function, not the model.

- `eval(expression)` evaluates the expression string as JavaScript code
- We wrap it in try/catch because bad input would crash our program
- We return a string because we're going to send the result back to the model

**Warning:** `eval` is dangerous in production. We use it here for simplicity. A real app would use a safe expression parser like `mathjs`.

### Step 4: Call the Model with the Tool

```javascript
const messages = [
  { role: "system", content: "You are a helpful assistant with a calculator tool. Use it when the user asks you math questions." },
  { role: "user", content: "What is 144 * 37 + 12?" }
];

const response = await client.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: messages,
  tools: tools
});
```

We send a message asking for a calculation. We include our tools array so the model knows the calculator exists.

### Step 5: Check the Model's Response

After the API call, `response.choices[0].message` contains either text or tool calls. Check `response.choices[0].finish_reason` — if it's `"tool_calls"`, the model wants to use a tool. The `tool_calls` array has all the details.

```javascript
const message = response.choices[0].message;

if (message.content) {
  console.log("Assistant:", message.content);
}

if (message.tool_calls) {
  for (const toolCall of message.tool_calls) {
    console.log("Tool call:", toolCall.function.name, "with input", toolCall.function.arguments);
  }
}
```

When the model decides to use the calculator, it sets `finish_reason` to `"tool_calls"` and populates `message.tool_calls`. Each tool call has `function.name` (which tool) and `function.arguments` (a JSON string you need to parse).

### Step 6: Execute the Tool and Send the Result Back

```javascript
const message = response.choices[0].message;

if (message.tool_calls) {
  for (const toolCall of message.tool_calls) {
    // Step 6a: Parse arguments and execute the tool function
    const args = JSON.parse(toolCall.function.arguments);
    const result = calculator(args.expression);

    // Step 6b: Add the assistant's tool_calls to conversation history
    messages.push({
      role: "assistant",
      content: message.content || "",
      tool_calls: message.tool_calls
    });

    // Step 6c: Add the tool result
    messages.push({
      role: "tool",
      content: result,
      tool_call_id: toolCall.id
    });

    // Step 6d: Call the model again with the result
    const finalResponse = await client.chat.completions.create({
      model: "llama-3.3-70b-versatile",
      messages: messages,
      tools: tools
    });

    console.log("Final answer:", finalResponse.choices[0].message.content);
  }
}
```

This is the critical part. Let's trace through it:

1. The model said "I want to call calculator with expression = '144 * 37 + 12'"
2. **Our code** runs `calculator("144 * 37 + 12")` which returns `"5340"`
3. We push the model's full message (with `tool_calls`) into the message history — this tells the API that the model *did* call a tool
4. We push a `role: "tool"` message containing the result `"5340"` and the matching `tool_call_id` — this is how the model "sees" the tool output
5. We call the API again, and now the model reads the result and gives us the final answer

### The Full Script

Here's everything together in one file:

```javascript
import Groq from "groq-sdk";

const client = new Groq();

const tools = [
  {
    type: "function",
    function: {
      name: "calculator",
      description: "Evaluate a mathematical expression. Returns the numeric result.",
      parameters: {
        type: "object",
        properties: {
          expression: {
            type: "string",
            description: "The mathematical expression to evaluate"
          }
        },
        required: ["expression"]
      }
    }
  }
];

function calculator(expression) {
  try {
    const result = eval(expression);
    return String(result);
  } catch (err) {
    return `Error: ${err.message}`;
  }
}

const messages = [
  { role: "system", content: "You are a helpful assistant with a calculator tool." },
  { role: "user", content: "What is 144 * 37 + 12?" }
];

const response = await client.chat.completions.create({
  model: "llama-3.3-70b-versatile",
  messages: messages,
  tools: tools
});

const message = response.choices[0].message;

if (message.tool_calls) {
  for (const toolCall of message.tool_calls) {
    const args = JSON.parse(toolCall.function.arguments);
    const result = calculator(args.expression);

    messages.push({ role: "assistant", content: message.content || "", tool_calls: message.tool_calls });
    messages.push({
      role: "tool",
      content: result,
      tool_call_id: toolCall.id
    });

    const finalResponse = await client.chat.completions.create({
      model: "llama-3.3-70b-versatile",
      messages: messages,
      tools: tools
    });

    console.log("Assistant:", finalResponse.choices[0].message.content);
  }
}
```

### What Actually Happens

When you run this, here is what the model outputs on the first call (you'd see this if you logged the response):

```
finish_reason: "tool_calls"
message.tool_calls: [
  {
    id: "call_abc123",
    type: "function",
    function: {
      name: "calculator",
      arguments: "{\"expression\": \"144 * 37 + 12\"}"
    }
  }
]
```

No text. Just a tool_calls array. The model skipped the chit-chat and went straight to "I need the calculator."

After your code parses the arguments, runs the calculator, and sends back `"5340"`, the model responds with:

```
finish_reason: "stop"
message.content: "144 * 37 + 12 equals 5,340."
```

That's the full loop. The model asked, you executed, the model answered.

### Key Takeaway

The model never does math. It told you the expression. You evaluated it. It read the result and formatted the answer. The model is the brain; your code is the body.

One tool is good. But agents usually have multiple options, and the model needs to choose. That's next.

---

## What It Is NOT

The calculator agent is **not** "the model doing math." The model never actually evaluates `144 * 37 + 12`. It only produces the string expression and passes it to your code. Your `eval()` call does the actual computation. The model is like a person who hands you a calculator and tells you what buttons to press — you're the one pressing them.

### In Your Own Words

<details>
<summary>1. Walk through the tool calling loop step by step without looking at the code.</summary>

**Sample Answer:** First, I send the user's question plus tool definitions to the model. The model responds with a `tool_calls` array saying "call calculator with this expression." My code parses the arguments, runs the actual calculator function with that expression, and pushes the assistant's message (with `tool_calls`) and the tool result back into the conversation. Then I call the model again. Finally, the model reads the result and gives me the answer in plain text.

</details>

<details>
<summary>2. Why do we push the assistant's original response into the message history before adding the tool result?</summary>

**Sample Answer:** The API needs to know that the assistant *did* call a tool — otherwise it looks like the result came out of nowhere. Pushing the assistant response tells the API: "Yes, the model said it wanted to call calculator, and here's what it got back." Without this, the model gets confused because the conversation history is missing its own action.

</details>

<details>
<summary>3. What is the `tool_call_id` used for? Why does the model need to know which call we're responding to?</summary>

**Sample Answer:** The `tool_call_id` links the result back to the specific tool call. If the model called three tools at once, each result needs to match the right call. It's like labeling each takeout order with a number so the kitchen knows which burger goes with which fries.

</details>

<details>
<summary>4. What would happen if we skipped the second API call and just printed the calculator result directly?</summary>

**Sample Answer:** You'd get the raw number — `5340` — without any context or natural language. The model wouldn't have a chance to format the answer, explain what it means, or do anything else with it. It's like getting the answer to a trivia question without the question — technically correct but completely useless on its own.

</details>

<details>
<summary>5. Why does the calculator function return a string instead of a number?</summary>

**Sample Answer:** The tool result gets inserted into a text conversation. The model reads everything as text, so returning a string ensures it fits naturally into the message flow. Returning a number would require the model to convert it to text anyway, so we save it the trouble. Think of it like writing a note to hand to someone — you'd write the number as text on paper, not hand them a numeric keypad.

</details>
