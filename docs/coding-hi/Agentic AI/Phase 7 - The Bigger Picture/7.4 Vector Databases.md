When you have multiple agents handling lots of information, you need better memory systems. The context window of a single LLM call is limited — even the big ones top out at a couple hundred thousand tokens. For real-world applications, that's not enough.

This is where vector databases come in.

A vector database stores text as mathematical representations called **embeddings**. An embedding takes a piece of text — a sentence, a paragraph, a whole document — and converts it into a list of numbers (a vector). The trick is that similar texts produce similar vectors.

Think about it like this: the vector for "dogs playing in the park" will be close to the vector for "puppies running outside," but far from the vector for "quantum physics equations." The database can search by **meaning**, not just keywords.

![Vector Databases — Text Converted to Embeddings, Search by Meaning](/diagrams/agenticai/vector-database.svg)

The main vector databases you'll hear about:

- **Pinecone** — fully managed, easy to start with, paid
- **Chroma** — open source, runs locally, great for prototyping
- **Weaviate** — open source, supports hybrid search (vector + keyword)
- **Qdrant** — open source, fast, written in Rust

Here's how an agent uses a vector database in practice:

1. You feed the agent's past conversations, documents, or project files into the database. Each piece gets converted to an embedding and stored.
2. When the agent needs to answer a question, it converts the question into an embedding.
3. It searches the vector database for the closest vectors — the pieces of text most *meaningfully* related to the question.
4. It pulls those relevant pieces into the context window.
5. Now the LLM has the relevant information right in its context, without needing to fit the entire history.

This is how AI coding tools "remember" your past projects across sessions. When Cline, opencode, or Cursor suggests something based on your older code, it's likely pulling from a vector database. This is called **RAG** (Retrieval Augmented Generation) — retrieve relevant information first, then generate the answer.

Vector databases are the bridge between the limited context window of an LLM and the unlimited information you want it to work with.

## What It Is NOT

A vector database doesn't "understand" your text. It doesn't know what "dogs playing in the park" means. It just converts text to numbers and finds which numbers are closest together — that's pure math. Think of it like a photo album sorted by color instead of date: similar shades end up next to each other, but the photos have no idea what they show. Vector similarity is a useful approximation of meaning, but it can also give you weird results — like matching "apple the company" with "apple the fruit" because their vectors happen to be close.

### In Your Own Words

<details>
<summary>1. How is searching by meaning (vectors) different from searching by keywords?</summary>

**Sample Answer:** Keyword search is like looking for someone at a conference by checking their name tag — if the name is wrong or misspelled, you won't find them. Vector search is like describing what they look like to a friend who knows everyone — "tall, glasses, blue shirt" — and the friend points you to the right person even if you don't know their name. Vector search captures intent and topic, not just exact word matches.

</details>

<details>
<summary>2. What happens if the vector database returns irrelevant information? How could that affect the agent's response?</summary>

**Sample Answer:** If the vector DB brings back irrelevant context, the agent will incorporate that bad information into its response — like someone trying to answer a cooking question but reading a plumbing manual by mistake. The answer might be confidently wrong because the LLM doesn't know it was fed garbage. That's why RAG systems need a relevance check: either a minimum similarity threshold or a secondary filter to verify each retrieved chunk actually answers the question.

</details>

<details>
<summary>3. Can you think of a situation where a vector database would be overkill and a simple file search would work better?</summary>

**Sample Answer:** If you're searching for an exact line of code you wrote yesterday — like "where did I define the getUser function" — a simple grep or file search is faster, cheaper, and more accurate. Vector search is overkill when you know the exact keywords. It shines when you don't know the exact terms — "find the part where I handled rate limiting" — which is where a vector DB can match the concept even if none of those words appear literally.

</details>
