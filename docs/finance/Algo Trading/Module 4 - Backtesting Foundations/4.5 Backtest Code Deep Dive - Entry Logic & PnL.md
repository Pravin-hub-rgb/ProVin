# 4.5 Backtest Code Deep Dive: Entry Logic & PnL

## Problem #1 — Repeated Entries! 😱

Think: strong trend running.

9 EMA stays ABOVE 21 for many candles.

If rule simply: *"fast > slow → BUY"*

...then NEW BUY on EVERY CANDLE!!

```text
Candle 1: fast > slow → BUY ❗
Candle 2: fast > slow → BUY ❗
Candle 3: fast > slow → BUY ❗
...100 positions created!! 💀
```

We want: **only ONE position at a time.**

## Solution — The Entry Flag 🚦

Keep one switch:

```python
entry = False    # start: NO position
```

| Switch | Meaning |
|---|---|
| `entry = False` | Flat — new entry ALLOWED |
| `entry = True` | Position already — NOT again! |

In loop:

```python
if fast_now > slow_now and not entry:
    entry = True          # now position taken!
    buy_price = df["close"][i]
```

```text
not entry   → "when switch is OFF" = when flat
and         → BOTH conditions TOGETHER true then entry
```

Now checked every candle:

*"bullish AND we have no position?"* → then BUY!

## ⚠️⚠️ BIGGEST CORRECTION — PnL Formula!

**Read carefully — original material had BIG bug here!**

Original notes said:

```text
❌ WRONG (original material):
PnL = buy_price − sell_price

"Buy at 100, Sell at 110 → PnL = 100−110 = −10 (LOSS)" ❌
"Buy at 100, Sell at 90  → PnL = 100−90  = +10 (PROFIT)" ❌
```

**BOTH ARE REVERSED!** 😱

Think like your shop:

```text
You BOUGHT goods at 100
Sold at 110 → pocket has 10 MORE = PROFIT!
Sold at 90  → pocket has 10 LESS  = LOSS!
```

Correct formula:

```text
✅ CORRECT:
PnL = sell_price − buy_price

Buy 100, Sell 110 → 110−100 = +10 PROFIT ✅
Buy 100, Sell 90  → 90−100  = −10 LOSS   ✅
```

### Why This Is So Dangerous?

This is **silent bug:**

```text
Code ran        ✅
No error came   ✅
But every WINNER shown as loss, every LOSER as profit!
Net result REVERSED!
```

You'll think "strategy is bad" when actually CODE was bad.

That's why always SANITY CHECK:

> *"Bought at 100, sold at 110 — I should get +10.
> What does code say?"*

If weird → verify formulas FIRST!

## Complete Working Code — Full Engine!

Now combine everything into runnable script:

```python
qty = 10              # how many shares per trade
entry = False         # switch: position or not
buy_price = 0.0       # at what bought (to remember)
net_pnl = 0.0         # total profit/loss
trades = []           # each trade's PnL in list

for i in range(len(df)):
    fast_now = df["ema_9"][i]
    slow_now = df["ema_21"][i]

    # ENTRY: bullish + currently flat
    if fast_now > slow_now and not entry:
        entry = True
        buy_price = df["close"][i]

    # EXIT: bearish + position open
    elif fast_now < slow_now and entry:
        sell_price = df["close"][i]
        pnl = (sell_price - buy_price) * qty    # ✅ CORRECT FORMULA!
        net_pnl += pnl                           # add to total
        trades.append(pnl)                       # keep in log
        entry = False                            # switch OFF — new entry possible

print(f"Total trades:   {len(trades)}")
print(f"Winning trades: {sum(1 for t in trades if t > 0)}")
print(f"Net PnL:        {net_pnl:.2f}")
```

**In Your Own Words**

1. Role of entry flag? What without it?

<details>
<summary>Sample Answer</summary>

**Answer:** Flag tracks whether position is OPEN (switch ON/OFF). Entry-condition stays true on EVERY candle in strong trend — without flag, new BUY every candle (100+ overlapping positions!). `and not entry` ensures entry only in flat-state. Switch reset to False on exit — fresh entry possible on next crossover. This 3-line pattern is heart of all algo-trading.

</details>

2. PnL bug what was? How to sanity check?

<details>
<summary>Sample Answer</summary>

**Answer:** Original material had PnL = buy_price − sell_price — REVERSED! Buy@100/Sell@110 shown as −10 (loss) when profit. Correct: sell − buy (for long). Sanity check: shop-thinking — "bought 100, sold 110 = pocket 10 more." If backtest shows every winner as loss or results weird → verify formulas FIRST. Silent bugs don't give errors — give reversed answers.

</details>

3. Why elif, not two ifs?

<details>
<summary>Sample Answer</summary>

**Answer:** Because both conditions can't be SIMULTANEOUSLY true on one candle — fast EMA can't be above AND below slow at same time! They're mutually exclusive. elif expresses intent: "only ONE of these will run." Two ifs technically work but elif is cleaner and prevents accidental double-processing. Readability + safety both.

</details>

4. Why trades list when net_pnl total already given?

<details>
<summary>Sample Answer</summary>

**Answer:** Net PnL is just ONE number — final score. But analysis needs DISTRIBUTION: how many trades? how many won? avg win vs avg loss? worst trade? All comes from per-trade data that trades list holds. Next file (Metrics) calculates win-rate/expectancy/drawdown on this list. Can't understand strategy from total alone — need trade-level data.

</details>

5. Why multiply by qty in `(sell_price - buy_price) * qty`?

<details>
<summary>Sample Answer</summary>

**Answer:** Because price-difference is PER SHARE; real PnL is in rupees = shares × difference. Example: ₹10 move × 10 shares = ₹100 actual profit (without qty only "10" comes — wrong units!). Qty central for position-sizing — becomes even more important in Module 5 (risk-per-trade calculation).

</details>
