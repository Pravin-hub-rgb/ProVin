# 1.4 Overview of Exchanges, APIs and Data Providers

In the previous file you saw that an automated system places orders on its own. But wait a minute — who does your code send the order to? Straight to the exchange? To someone else? If you understand this flow, 90% of algo trading confusion disappears, because most beginners' problems come from not understanding this flow. So in this file we'll look at three things in detail — **Exchange, API, and Data Provider** — and also how these three are connected to each other.

## A Bit of History — The 2000s Scene

To understand today's system, we need to go back. In the 2000s:

Trading back then could only be done by institutions — not retail traders. Exchanges did exist (like NSE and BSE today), but brokers as we know them today didn't exist. Today's discount brokers — Angel One, Upstox, Dhan — didn't exist back then.

A retail trader had a normal broker person (a human). They'd tell that person their order, and he'd get the order to the exchange. Even if the order needed changing, he'd do it.

And APIs? Exchanges technically provided APIs, but with strict rules — "you must have enough money, then you get access." So this facility was only with big institutions. Retail traders got neither API nor data. Meaning retail algo trading wasn't possible at all.

Then a turnaround came in the early 2000s:

1. The exchange launched co-location servers
2. From there, brokers were born from exchanges
3. Brokers launched their own APIs
4. Only then could retail traders do algo trading through brokers

## Today's Order Flow

Now let's look at today's system. The normal retail flow is like this:

```
You (Retail Trader) → Broker → Exchange → Broker → You
```

Understand with an example — Angel One is your broker:

1. You say: *"I want to buy Reliance"*
2. You tell the broker
3. The broker buys on the exchange on your behalf
4. The exchange returns the output to the broker
5. The broker returns it to you

The API flow is exactly the same — only the way of speaking changes:

1. You tell the broker via API (through code)
2. The broker tells the exchange the same thing
3. The exchange returns the output
4. The API returns the output to you

That's all there is to it.

And the institutions' flow? Earlier, exchanges ↔ institutions talked directly — they still do. Institutions don't link through brokers — they place their orders directly, through coding. Big players like Vijay Kedia have their own prop desk that talks directly to the exchange — they don't pay brokerage to any broker.

## Why Understanding This Flow Matters

Because whoever understands this flow — how data + orders move — moves from a manual trader's mindset to a quant's mindset.

**Quant = someone who understands things mathematically, who understands flows and executions.**

Once the flow is clear, building algorithms becomes much easier, because you know who your code will talk to and where the order will go.

## Market System Hierarchy

Now let's look at the three layers one by one.

### Level 1 — Exchange

Examples: NSE, BSE — crypto: Binance.

Exchange = the marketplace where all buyers and sellers meet. Where all buyers-sellers gather. And the exchange itself decides the market structure — what the tick size will be, what the margin rules will be, etc.

Remember one rule here: algo trading is possible directly with the exchange only if you have a direct connection — that's for institutions. A retail trader's algo does NOT connect directly to the exchange. If you use Zerodha, you can't sell directly on NSE. You must connect to the broker first, then to the exchange. The broker is what connects you and your algo to the exchange — because you use their APIs.

### Level 2 — Broker

Examples: Zerodha, Angel One, Upstox.

Broker = the middle layer between the exchange and you. All your orders reach the exchange only through the broker.

One exception: Binance is BOTH an exchange AND a broker — it plays both roles at once.

### Level 3 — API

**API = digital bridge between your CODE and your BROKER (not exchange).** Your algo sends orders through it, receives data through it, and executes rules through it.

## What is an API — The Home-Key Analogy

Let's nail down the API with an example.

Imagine a house, and its door. The house belongs to your friend Rahul. You want to go inside. What do you need to go inside? A key! Only with the key can you open the door and go inside. And if he doesn't give you his key at all, how would I get into his house?

Now the mapping:

- **House** = Broker
- **You (the one going inside)** = Your Code
- **The door's key** = API Key

Your code needs an API key to talk to the broker — that's the key. (Full form: API = Application Programming Interface.)

And why do you get the key at all? Because your friend wants only you to come to his house, no third person. Exactly the same way, your broker wants only you to use your account, no one else to use your API. So he gives the key specifically to YOU — an API key.

Log in to the broker app (like Angel One) → Trading APIs section → Generate API key. You get two things: **API Key** and **API Secret**. Copy these and use them in your code.

⚠️ **Security warning:** If this API key/secret gets shared with someone else by mistake, they can access your account through code — they can even place orders in your name. So never share it with anyone.

### What You Can Do With an API

Everything needed in trading, programmatically:

- Fetch real-time price
- Fetch historical data
- Place order
- Modify stop loss
- Exit orders
- Check position
- Check PnL
- Manage portfolio

That's why it's said — **API is the backbone of automation.** You can generate signals, but without an API/broker connection you can't place trades.

## Types of APIs

Every broker has its own API documentation (like Angel One's). There are mainly 3 types:

**1. Historical API:** Fetches only historical data — past data of any stock/index.

**2. Market Data API:** Current live LTP (Latest Trading Price) — the price currently moving in the market. From this you get OHLCV data (Open, High, Low, Close, Volume), live ticks (values as price changes in NIFTY), and historical data too.

**3. Trading API:** Executes orders — buy/sell, place orders, check order status (whether the order is running or not).

How do brokers provide them? Some brokers let you do all three through one API. Some give separate APIs for each task. Most brokers give both (data + trading), but some give only one — either just a trading API or just a data API. You'll have to use whatever you get.

## Data Providers — The Real Engine of Backtesting

Now the last piece of the chain. Orders go through the API, but what do you need before building a strategy? **Data.**

A data provider is someone who provides you historical data of any stock/index — so you can test your strategy.

Why data is needed — three reasons:

1. **Backtest** — test the strategy on past data
2. **Strategy validation** — verify that the strategy works
3. **ML training** — data needed to train machine learning models

And here's one line to never forget:

> **Good data = Good backtesting. Bad data = Fake profit.**

Bad data means the data values are wrong. The result? Profit looks correct in the backtest, but that strategy won't work in the actual live market. All your hard work's result is fake.

## Historical Data vs Live Data

Data comes in two types, and their behavior is different:

**Historical data:** Clean, already processed. Closed candles (finalized). No gaps. No filtering needed. Used for backtesting.

**Live data:** Raw — comes tick by tick. Changes with every price movement. Lag can occur, spikes can occur. Filtering is necessary. Used for live trading.

An algo trader must know how to handle both — because backtesting happens on historical data, and money is made on live data.

## Full Algo Trading Flow — End to End

Now let's join everything and see the full picture:

```
1. Create Strategy Logic with Python
        ↓
2. Fetch Historical Data from Data Provider
        ↓
3. BACKTEST (verify the strategy)
        ↓
4. Run LIVE on Broker (live algo trading engine)
        ↓
5. Connect Code to Broker API
        ↓
6. Broker connects to Exchange
        ↓
7. LOGS / Dashboard / Monitoring
```

The last step is important — when your algo starts working, it gives logs (telling you how it's working) and provides a dashboard where you can see how the strategy is performing. Complete results come, which you can monitor.

Real example: Zerodha's API is called **Kite API**. See the flow — your bot fetches live price from Kite API → logic decides buy/sell → bot sends order on API → order goes to exchange (NSE) → exchange returns to Kite → Kite returns to you. The same flow happens in crypto too.

## Nutshell

The order's journey is: **your code → API → broker → exchange** — and the response comes back through the same path. Exchange is the marketplace, broker is the middle layer, API is the digital bridge between your code and the broker. Data providers are the engine of backtesting — good data = good backtesting, bad data = fake profit.

## What It Is NOT

- ❌ **Your code does not talk directly to the exchange.** A retail trader's algo always goes through the broker. Direct exchange connection is only with institutions.
- ❌ **API is not the exchange's door.** API is the bridge between your code and the BROKER. The broker talks to the exchange.
- ❌ **Backtest profit is not real profit.** If the data was bad, the backtest profit is fake. That same strategy can fail in the live market.
