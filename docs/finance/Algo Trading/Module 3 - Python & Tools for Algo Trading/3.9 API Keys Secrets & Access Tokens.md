# 3.9 API Keys, Secrets & Access Tokens

## The Home Key Story

Imagine your home has two doors:

```text
MAIN DOOR    → entry into home (access to everything)
GODOWN LOCK  → only godown opens
```

Brokers use same system — digital keys:

| Key | What It Opens |
|---|---|
| **API Key** | Tells your identity — "who is this person" |
| **API Secret** | Like password — "is this REALLY them" proof |
| **Access Token** | Temporary pass — "entry allowed for today" |

Three things, three roles. Now one by one in detail.

## API Key + Secret — Permanent Identity

After creating account on broker dashboard, you get:

```text
API_KEY    = "abc123xyz..."     ← can be shown (like ID card)
API_SECRET = "xyz789secret..."  ← NEVER give to anyone! (password)
```

```text
API Key    → like username — "I am Rahul"
API Secret → like password — proof that really Rahul
```

⚠️ Most important rule:

> **Secret = PASSWORD.** Writing it openly in code, showing in screenshot, WhatsApp to friend — ALL WRONG.

Secret leaked? Anyone can trade from YOUR account.

## Access Token — Today's Pass

Now problem: sending secret with every request is risky.

Like you don't show your original passport at office every day —

once shown, you get a **visitor badge** for the day.

That's **access token:**

```text
STEP 1: Login with Key + Secret        (showed passport)
STEP 2: Broker gave ACCESS TOKEN       (got badge)
STEP 3: Now only TOKEN goes with every request   (show badge, work done)
```

Benefit: real secret travels on network again and again NOT.

Only token goes — and token expires (new one every day).

## Wait — Three Things in One Line

```text
API Key     → ID card (who am I)
API Secret  → password (proof)
Access Token→ today's visitor badge
```

Flow: **make token with key+secret → do work with token.**

Now real question: where to write these keys in CODE?

## ❌ Biggest Beginner Mistake

```python
# WRONG WAY:
api_key = "abc123xyz..."
secret = "xyz789secret..."

# ...rest code...
```

This will run. Will work too.

**But one day you put this code on GitHub... or shared screenshot...**

Keys became public. Some stranger started trading from your account.

That's why this way is BANNED.

## ✅ Correct Ways — Two Options

### Option 1: Keep in Separate File

```python
# tokens.py   ← only keys here
API_KEY = "abc123xyz..."
SECRET = "xyz789secret..."
```

```python
# main.py    ← real code
from tokens import API_KEY, SECRET     # import from there
```

If sharing code, skip `tokens.py`, share rest.

### Option 2: Environment Variables

```python
import os

api_key = os.getenv("MY_API_KEY")
```

```text
os.getenv("NAME")  → "is there value named NAME in computer's memory?
                      Give that."
```

Values are kept in computer's settings — nowhere visible in code.

When deploying to cloud (Module 8), this same system will be used — for now grab the concept.

### And One Habit — .gitignore

Whenever code goes to GitHub, a `.gitignore` file is made that says: *"don't upload these files."*

`tokens.py` and `.env` must always be in it:

```text
# .gitignore
tokens.py
.env
```

Git will ignore them — never uploaded. (Detail in Module 7.)

## Wait — Security Checklist

```text
✅ Secret = password, never give to anyone
✅ Keys in separate file (.py) or env-vars — NOT in main code
✅ .gitignore setup — before upload
✅ Token = temporary badge; secret = permanent identity
```

These 4 lines will be used practically in every broker file. Stay alive, remember them!

## Nutshell

Three security layers: **API Key** (ID — who), **API Secret** (password — proof), **Access Token** (today's badge — made from key+secret, requests go with it, expires). Never share secret openly. Store keys: separate file (`tokens.py`) or environment variables (`os.getenv`) — never in main code. `.gitignore` mandatory before GitHub. Leak = account takeover.

## What It Is NOT

- ❌ **Key and token are not same thing.** Key+secret = PERMANENT credentials (login material). Token = TEMPORARY pass made from them, expires. Token leaked? Dies tomorrow. Secret leaked? Entire account compromised.
- ❌ **"My account is small, who'll hack" — wrong thinking.** Hackers run bots that scan EVERY leaked key on internet, in seconds. They don't look at size. Automation is on their side too!
- ❌ **os.getenv() doesn't create values itself.** It only READS — value must be placed first by you/computer/cloud settings. If not set, you'll get None (and confusing error later).

2. Why is writing keys directly in code wrong? Two correct ways?

<details>
<summary>Sample Answer</summary>

**Answer:** Because code is SHARED — GitHub, screenshots, sent to friend... wherever it goes, keys go. Bots scan leaked keys in seconds. Fixes: (1) separate file — keys in tokens.py, main code uses from tokens import; skip that file while sharing. (2) Environment variables — os.getenv("KEY") takes value from computer/cloud settings, value nowhere visible in code. Plus .gitignore so files don't accidentally push.

</details>

3. What's the benefit of access token expiring (looks like drawback, right)?

<details>
<summary>Sample Answer</summary>

**Answer:** Benefit is SECURITY. If token leaks, damage is limited time window — dies tomorrow. If it were permanent credential, hacker would be inside forever. Trade-off: you must re-login frequently (a bit annoying), but hacker also needs fresh access which they don't have. Short-life = small blast radius. This is a design feature, not a bug.

</details>

4. `os.getenv("MY_KEY")` returned None — what happened?

<details>
<summary>Sample Answer</summary>

**Answer:** Meaning no environment variable named "MY_KEY" is SET in computer/memory — getenv returns None when nothing found. Fix: value must be set first (env var on local machine / .env file; cloud dashboard setting). Common beginner confusion: thinking getenv creates value itself — no, it's only a READER. First place, then fetch.

</details>
