# 3.11 Zerodha Kite Connect API

## Setup — Platform First

Zerodha's API system is different — platform called **Kite Connect**:

```text
developers.kite.trade → go → login with Zerodha account
→ Create new app
```

App creation gives:

```text
API_KEY     → ID card (remember 3.9?)
API_SECRET  → password
```

Save both in `tokens.py` (habit now!):

```python
# tokens.py
api_key = "xyz123..."
api_secret = "secret789..."
```

Install library:

```bash
pip install kiteconnect
```

## Three-Token Dance — First Understand Story

Other brokers: *"give password, get token."* Done.

Zerodha: *"Wait... first login in BROWSER, then get a code, then make another token..."*

Three steps:

```text
TOKEN 1: REQUEST TOKEN   ← comes after browser login (once)
TOKEN 2: CHECKSUM        ← made from api_secret + request_token
TOKEN 3: ACCESS TOKEN    ← real badge! Data comes with this
```

Analogy:

```text
Going to club:
1. Show ID at gate          → entry slip received (request token)
2. Slip + secret handshake  → VIP band made (checksum)
3. Show band                → inside! Access for whole day (access token)
```

Confusing? Let's DO it in code — will make sense.

## Login — Step-by-Step Code

Best practice: keep login code in **separate file** — `login.py`.

Because this dance repeats daily, pack in one place (3.3's concept!).

```python
# login.py

from kiteconnect import KiteConnect
from tokens import api_key, api_secret

# STEP 1: Make Kite object
kite = KiteConnect(api_key=api_key)

# STEP 2: Generate login URL
print(kite.login_url())
```

Line by line:

```python
from kiteconnect import KiteConnect   ← took main class from library
kite = KiteConnect(api_key=...)       ← waiter ready — requests will go
kite.login_url()                      → a URL prints
```

Run it. A URL will come in terminal.

**Open that URL in browser** → login to Zerodha (normally, like in app).

After login, browser redirects... and look in address bar:

```text
https://127.0.0.1/....?request_token=ABC123XYZ&status=success
                               ↑↑↑↑↑↑↑↑↑
                           LOOK HERE! TOKEN 1 received!
```

The string after `request_token=` — copy it.

This is **Token 1: Request Token.** Slip received! 🎫

## Token 2 + 3 — Now Real Magic

Copy request token, continue in `login.py`:

```python
# login.py (rest part)

request_token = "ABC123XYZ"     ← what you just copied from browser

data = kite.generate_session(request_token, api_secret=api_secret)

access_token = data["access_token"]
kite.set_access_token(access_token)

print("LOGIN DONE! ✅")
print(f"Token: {access_token}")
```

Line by line:

```python
kite.generate_session(request_token, api_secret=...)
```

This is the **checksum step** — request token + api secret sent to Zerodha together.

Zerodha verifies: *"yes, this login was really yours"* — and gives:

```python
data["access_token"]    ← TOKEN 3! Real badge 🎫
```

```python
kite.set_access_token(access_token)
```

Badge stuck on Kite object — now goes automatically with every request.

**DONE!** Login complete. Three-token dance over.

## ⚠️ Access Token Expiry — Daily Truth

One important thing that surprises everyone:

> **Zerodha's access token lasts only ~24 hours.**

Tomorrow's token won't work today.

Meaning daily (or whenever expired) this dance must repeat:

```text
Browser login → copy request_token → generate_session → new token
```

That's why `login.py` was kept in separate file!

Daily: just run `login.py` → new token → rest code runs normally.

(Quick tip: request_token is also single-use — once used, won't work again.)

## Wait — Dance Summary

```text
1. Print login_url()        → open URL in browser
2. Browser login            → request_token received (copy)
3. generate_session(rt, secret) → access_token received
4. set_access_token(at)     → badge stuck — WORK STARTS!
```

Four steps. Repeat daily. That's it.

## Nutshell

Zerodha = popular but dramatic login. **Three tokens:** request_token from browser login → generate_session with request_token + api_secret → access_token → set_access_token(). Token expires in ~24 hours — that's why login.py separate file, run daily. Fetch: `historical_data(instrument_token, from_date, to_date, interval)` — token NUMBER needed (`kite.instruments("NSE")` for list). Convert → DataFrame. Dance is annoying but pattern same golden one.

## What It Is NOT

- ❌ **Kite app ≠ Kite Connect API.** Kite app = normal trading app (on phone). Kite Connect = SEPARATE developer platform with separate account/app setup. API access needs app creation on developers.kite.trade.
- ❌ **request_token is not reusable.** Once used in `generate_session`, dead. Need fresh → login again in browser. That's why complete flow in one run.
- ❌ **Access token expiring ≠ something broke.** This is DESIGN — for security (3.9 explained: short-life = small blast radius). Running login.py daily becomes routine — 2 minute job.
