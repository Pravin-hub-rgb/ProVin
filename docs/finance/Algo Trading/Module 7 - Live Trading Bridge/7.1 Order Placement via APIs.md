# 7.1 Order Placement via APIs

## Data API ≠ Trading API

Module 3's all APIs were READ-ONLY — just reading candles.

Trading API is next level:

| | Data API | Trading API |
|---|---|---|
| Work | Read candles | SEND orders |
| On mistake | Nothing | **Real money loss** |
| Setup | Basic keys | IP whitelist + permissions + margins |

That's why brokers give trading-keys extra carefully.

And you'll use them extra carefully too!

## First Understand Order Anatomy

Every broker's order roughly asks SAME fields:

```text
ORDER =
    instrument   → which stock?
    side         → BUY or SELL?
    order_type   → MARKET / LIMIT / STOPLOSS?
    quantity     → how many shares?
    product      → INTRADAY or DELIVERY?
```

One by one:

### order_type — Three Flavours

| Type | Meaning | Analogy |
|---|---|---|
| `MARKET` | BUY now at current price instantly | "Take whatever available!" |
| `LIMIT` | "ONLY at this price or better" | "Only cheaper than ₹100, else no!" |
| `STOPLOSS` | Activate when trigger crosses | "Save me if it falls!" |

```text
MARKET   → execution GUARANTEED, price not
LIMIT    → price CONTROLLED, execution not guaranteed
```

### quantity — Lot Rules Carefully!

Stocks = number of shares (10, 50...)

F&O = LOTS! (Reliance futures 1 lot = like 250 shares)

Wrong lot-multiple = order REJECTED!

### product — Two Types

```text
INTRADAY (MIS)  → auto-close by evening (position doesn't stay overnight)
DELIVERY (CNC)  → shares stay WITH YOU

Algo traders mostly use INTRADAY!
```

## Wait — What Happened So Far?

```text
✅ Order = instrument + side + type + qty + product
✅ MARKET = instant | LIMIT = your price | SL = trigger
✅ F&O counts LOTS, not shares!
✅ MIS = intraday (auto-close), CNC = delivery
```

## Order Lifecycle — MOST Important Concept!

Concept beginners MISS:

```text
You SENT order          → "placed"     (broker received)
Exchange queued it      → "open"       (waiting to match)
Matched                 → "filled" ✅  (deal done!)
(or)                    → "rejected" ❌ (couldn't)
```

**MOST IMPORTANT LINE:**

> **"Order placed successfully" ≠ "position created!"**

Placement is only RECEIPT!

Limit order can stay OPEN whole day — without fill.

That's why serious systems check **fill confirmation:**

*"ask order book — did my order execute or not?"*

### Common Rejection Reasons

```text
❌ Insufficient margin
❌ Wrong quantity (lot rules!)
❌ Market closed
❌ Token/session expired
```

## Auth's Three Styles (3.9's Practical!)

In Module 3 saw three styles —

trading uses SAME patterns:

### Style 1 — Direct Token (Dhan-style)

Simplest: token in header:

```python
import requests

headers = {
    "access-token": MY_TOKEN,          # showed badge
    "Content-Type": "application/json"
}

payload = {                             # order details
    "securityId": "2885",              # Reliance's number
    "transactionType": "BUY",
    "orderType": "MARKET",
    "quantity": 10,
    "productType": "INTRADAY"
}

resp = requests.post("https://api.dhan.co/v2/orders",
                     json=payload, headers=headers)
print(resp.json())                      # orderId comes back!
```

Line by line:

```text
headers   → on envelope "this is authorized"
payload   → all order details in one dict
requests.post(...) → gave order to waiter!
resp.json() → broker's response (orderId + status)
```

### Style 2 — Session Login (Kite/Angel/Groww-style)

Login flow generates token (done in M3),

then same token with every trading call:

```python
# Zerodha example:
kite.place_order(
    tradingsymbol="RELIANCE",
    transaction_type="BUY",
    quantity=10,
    product="MIS",
    order_type="MARKET"
)
```

Pattern: **import session from login.py → functions in orders.py!**

### Style 3 — HMAC Signature (Delta/crypto-style)

Crypto exchanges want EXTRA layer: **signature**.

Every request must be signed with your SECRET —

server verifies request REALLY came from your system!

```python
import hmac, hashlib

signature = hmac.new(secret.encode(),
                     message.encode(),
                     hashlib.sha256).hexdigest()
```

Concept simple:

```text
Secret NEVER travels on network.
Only SIGNATURE made from it travels.
Server verifies with same secret.
```

(Practically libraries like `delta-rest-client` do this INTERNALLY —

but now you know what's happening inside! 🔓)

### Style 4 (Bonus) — MT5 Desktop

In MetaTrader5 orders go through desktop-terminal:

```python
result = mt5.order_send(request_dict)

if result.retcode != mt5.TRADE_RETCODE_DONE:
    print(f"FAILED! retcode = {result.retcode}")   # error code says why
```

`retcode` = MT5 version of fill-confirmation.

**"Check order_send's retcode"** — remember this rule!

## 🛡️ Safety Protocol — Before First Order!

This checklist is NON-NEGOTIABLE:

```text
1. DEMO ACCOUNT FIRST!
   Delta demo / MT5 demo / broker paper-trading.
   Direct entry on real money = madness.

2. START WITH MINIMUM QUANTITY
   1 share/lot. Let system prove itself!

3. IDEMPOTENCY GUARD
   Same signal came twice? NO double order!
   (check: position already open?)

4. POSITION STATE TRACK
   System should know: position open or not?
   (4.5's flag — now on REAL money!)

5. KILL SWITCH ready
   Emergency script that closes ALL positions instantly!

6. LOGS EVERYWHERE
   Save every order-request + response in file.
   GOLD for debugging.
```

## Nutshell

Trading API = data API + real-money risk + stricter auth. Order anatomy: instrument/side/type(MARKET-LIMIT-SL)/qty(lots!)/product(MIS-CNC). **Lifecycle: placed → open → filled/rejected; PLACEMENT ≠ FILL — confirmation mandatory!** Auth styles: direct-token, session-login, HMAC-signature (+MT5 retcode). Safety: demo-first, min-qty, idempotency, state-tracking, kill-switch, logs. Structure: tokens/login/orders/server split.

## What It Is NOT

- ❌ **"Order placed" ≠ "money invested."** Placement is only RECEIPT — LIMIT order can stay open all day, MARKET fills with slippage, insufficient margin can REJECT. Status-check part of every serious system.
- ❌ **MARKET order doesn't guarantee price.** Guarantees EXECUTION, not price! In illiquid moments slippage can be bad (2.1 microstructure). Want price → LIMIT — but then fill risk is yours.
- ❌ **Signature system ≠ secret safe.** HMAC is only TRANSIT protection (no tampering mid-way). If secret leaked from FILE (GitHub push!), everything wasted — storage discipline (next file!) equally necessary.

**In Your Own Words**

1. Risk-difference between Data API and Trading API?

<details>
<summary>Sample Answer</summary>

**Answer:** Data API is read-only — worst mistake gives WRONG DATA, money safe. Trading API MODIFIES account — wrong side, wrong qty, duplicate order = DIRECT monetary loss! Hence trading APIs have extra auth layers (IP-whitelist, scopes, signatures) and different testing protocol: demo-first, min-qty, kill-switch. Risk-asymmetry itself is treatment difference.

</details>

2. MARKET vs LIMIT vs STOPLOSS — when which?

<details>
<summary>Sample Answer</summary>

**Answer:** MARKET = execution-certainty needed, price secondary (SL-exits, urgent square-off). LIMIT = price-control critical, can wait (entries at level, no-slippage). STOPLOSS = automatic exit on trigger-cross (risk-management). Algo strategies commonly combo: LIMIT entries + STOPLOSS exits. Trade-off always: certainty-of-fill vs certainty-of-price.

</details>

3. "Placement ≠ fill" — explain lifecycle.

<details>
<summary>Sample Answer</summary>

**Answer:** Stages: PLACED (API accepted) → OPEN (in exchange queue, unfilled) → FILLED (matched!) OR REJECTED (margin/qty/rules issue). "Placed ≠ fill" means API-success is only RECEIPT — LIMIT order can stay open all day; market-order fills with slippage; some reject due to insufficient margin. Hence production systems keep ORDER-STATUS polling/alerts and update position-state from them.

</details>

4. What does HMAC signature solve, what NOT?

<details>
<summary>Sample Answer</summary>

**Answer:** SOLVES: request-authenticity + integrity — server can verify request came from your secret-holding system AND wasn't modified mid-way (secret doesn't travel on network, only hash made from it). DOES NOT SOLVE: secret-STORAGE security — if secret leaked from file (GitHub push!), anyone can make valid signatures. Transit-crypto ≠ storage-security; hence .gitignore/env-vars discipline separately needed.

</details>

5. Six safety steps before first live order?

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Test full flow on DEMO/paper-account, (2) minimum quantity — 1 lot/share, (3) idempotency-guard — block double-order on duplicate-signal (open-position check), (4) position-state tracking + recovery-plan (server-restart scenario!), (5) kill-switch ready — emergency flatten-script, (6) full logging — every request/response recorded. Without these, live = blindfolded driving on highway!

</details>
