# 7.1 Order Placement via APIs

## Data API ≠ Trading API

Module 3 mein jo APIs use ki thi woh sab **read-only** thi — historical candles ka data. Trading API ek alag permission level hai:

| | Data API | Trading API |
|---|---|---|
| Kaam | Candles padhna | Orders bhejna |
| Galat hone pe | Kuch nahi | **Real paisa loss** |
| Auth level | Basic keys | Full account access |
| Extra setup | NahI | IP whitelist, permissions, margins |

Isliye brokers trading keys ko extra carefully treat karte hain — scopes, IP whitelisting, signatures. Aur tu bhi karega.

## Pehle Order Anatomy Samjho

Har broker API ka order roughly same fields maangta hai:

```text
ORDER =
    instrument   → kis stock/contract pe (symbol ya token)
    side         → BUY ya SELL
    order_type   → MARKET / LIMIT / STOPLOSS
    quantity     → kitne shares/lots (lot-size rules!)
    product      → INTRADAY (MIS) ya DELIVERY (CNC)
    price        → LIMIT orders ke liye
```

Field-by-field:

- **order_type:** `MARKET` = abhi current price pe turant (execution guaranteed, price nahi). `LIMIT` = "is price ya better pe" (price controlled, execution NOT guaranteed). `STOPLOSS` = trigger price cross hote hi activate.
- **quantity:** stocks mein shares; F&O mein **lots** — Reliance futures 1 lot = 250 shares jaise. Galat lot multiple = order reject.
- **product:** intraday position (MIS) shaam ko auto-square-off hoti hai; delivery (CNC) tere paas rehti hai. Algo traders mostly MIS use karte hain.

## Order Lifecycle — Placement ≠ Fill!

Sabse important concept jo beginners miss karte hain:

```text
Tumne order BHEJA          → "placed"
Exchange ne queue kiya      → "open"
Match ho gaya               → "filled" ✅
(ya)                        → "rejected" ❌
```

**"Order placed successfully" ka matlab "position ban gayi" NAHI hai.** Limit order lag sakta hai poore din filled na ho. Isliye har serious system **fill confirmation check** karta hai — order book/status API se poochta hai: "mera order hua ya nahi?"

Common rejection reasons: insufficient margin, galat quantity (lot rules), market band hai, token/session expire, duplicate order ID.

## Auth Families — Teen Styles Jo Hum Dekh Chuke

Course mein teeno style ke examples mil chuke hain (data ke liye); trading pe bhi same patterns apply hote hain:

### Style 1 — Direct Access Token (Dhan-style)

Simplest: login se mila access token, header mein bhejo.

```python
import requests

headers = {
    "access-token": DHAN_ACCESS_TOKEN,
    "Content-Type": "application/json",
}
payload = {
    "securityId": "2885",          # instrument token
    "transactionType": "BUY",
    "orderType": "MARKET",
    "quantity": 10,
    "productType": "INTRADAY",
}
resp = requests.post("https://api.dhan.co/v2/orders",
                     json=payload, headers=headers)
print(resp.json())                  # orderId milti hai response mein
```

### Style 2 — Session Login (Kite/SmartAPI/Groww-style)

Login flow se access token generate hota hai (3.11/3.12/3.13 mein kiya), phir wahi token har trading call ke saath jaata hai. Zerodha example: `kite.place_order(tradingsymbol="RELIANCE", transaction_type="BUY", quantity=10, product="MIS", order_type="MARKET")`. Pattern same: **login.py se session import karo**, orders.py mein order functions likho.

### Style 3 — HMAC Signature (Delta/crypto-style)

Crypto exchanges (Delta, Binance family) ek aur layer add karte hain: **signature**. Har request ko tere API secret se cryptographically sign karna padta hai — server verify karta hai ki request sach mein tere system se aayi hai.

Concept:

```python
import hmac, hashlib, time

def make_signature(api_secret, payload_str):
    return hmac.new(api_secret.encode(),
                    payload_str.encode(),
                    hashlib.sha256).hexdigest()

timestamp = str(int(time.time() * 1000))
signature = make_signature(API_SECRET, timestamp + payload_str)
# request headers mein: api-key, timestamp, signature bhejo
```

Matlab: secret kabhi network pe nahi jaata — sirf usse banaya hua signature jaata hai. (Practical mein `delta-rest-client` jaisi libraries yeh internally handle karti hain — par ab tu jaanta hai andar kya ho raha hai.)

### MT5 Style — Desktop IPC

MetaTrader5 alag hai: orders desktop terminal ke through jaate hain (`mt5.order_send()`), aur response mein **retcode** milta hai jo batata hai order accept hua ya kyun reject hua. Module 8 ke project mein use karenge — abhi bas itna: MT5 mein bhi "order_send ka retcode check karo" = "fill confirmation check karo".

## Safety Protocol — Pehli Baar Orders Ke Liye

Yeh checklist non-negotiable hai:

1. **Demo/paper account pehle** — Delta demo account, MT5 demo, broker paper trading. Real paise pe direct entry nahi.
2. **Minimum quantity se shuru** — 1 share/lot. System proof hone de.
3. **Idempotency guard** — same signal do baar aaye toh double order na lage (duplicate detection: trade ID ya open-position check).
4. **Position state track karo** — system ko pata hona chahiye abhi position open hai ya nahi (4.5 wala flag, ab real money pe!). Server restart ho gaya toh position state recover kaise hogi — sochna.
5. **Kill switch** — emergency stop button/script jo saare open positions flatten kar de.
6. **Logs har jagah** — har order request + response file mein. Debugging ke liye gold.

## Nutshell

Trading API = data API + real-money risk + stricter auth. Order anatomy: instrument, side, type (MARKET/LIMIT/SL), quantity (lots!), product (MIS/CNC). Lifecycle: placed → open → filled/rejected; **placement ≠ fill** — confirmation check mandatory. Teen auth styles: direct token, session token, HMAC signature (+MT5 retcode variant). Safety protocol: demo first, min qty, idempotency, position tracking, kill switch, logging. Project structure: tokens/login/orders/server split. Agli file mein iska `server.py` hissa samjhenge — webhooks!

## What It Is NOT

- ❌ **"Order placed" ≠ "paisa lag gaya."** Placement acknowledgement sirf kehta hai exchange ne receive kiya. Fill/reject status alag se check hota hai. Is miss ne bahut algo accounts uda diye hain.
- ❌ **Market order = price guarantee nahi.** Guaranteed EXECUTION hai, price nahi — illiquid moments mein slippage badhiya aa sakti hai (2.1 microstructure). Price control chahiye toh LIMIT, par fill ka risk tumhara.
- ❌ **Signature security = secret safe nahi hota.** HMAC sirf transit protection deta hai (koi beech mein tamper na kare). Secret leak ho gayi toh signature system bhi compromised hai — storage discipline (agli file) utni hi zaroori hai.

**In Your Own Words**

1. Data API vs Trading API — risk profile mein kya farq?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Data API read-only hai — galti se max galat data aata hai, paisa safe. Trading API account modify karti hai — galat side, galat qty, duplicate order = direct monetary loss. Isliye trading APIs pe extra auth layers (IP whitelist, scopes, signatures), aur testing protocol alag hai (demo-first, min-qty, kill switch). Risk asymmetry hi dono ke treatment ka difference hai.

</details>

2. MARKET vs LIMIT vs STOPLOSS order types — kab kaunsa?

<details>
<summary>Sample Jawab</summary>

**Jawab:** MARKET — execution certainty chahiye, price secondary (stop-loss exit, urgent square-off). LIMIT — price control critical, execution wait kar sakta hai (entries at level, avoid slippage). STOPLOSS — trigger-cross hone pe automatic exit (risk management). Algo strategy mein combo common: LIMIT entries + STOPLOSS exits. Trade-off hamesha: certainty-of-fill vs certainty-of-price.

</details>

3. Order lifecycle ke steps aur "placement ≠ fill" ka matlab?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Placed (API accepted) → Open (exchange queue mein, unfilled) → Filled (matched) YA Rejected (margin/qty/rules issue). "Placement ≠ fill" matlab API ka success response sirf receipt hai — LIMIT order din bhar open pada reh sakta hai, market order slippage pe fill hota hai, koi order margin kam padne se reject ho sakta hai. Isliye production systems order-status polling/alerts rakhte hain aur position state unse update karte hain.

</details>

4. HMAC signature kya solve karta hai, kya NAHI?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Solve karta hai: request authenticity + integrity — server verify kar pata hai ki request tere secret-key-wale system se aayi aur beech mein modify nahi hui (secret network pe travel nahi karta, sirf hash). Solve NahI karta: secret STORAGE security — agar secret file se leak ho gayi (GitHub push!), koi bhi valid signatures bana lega. Transit crypto ≠ storage security; isliye .gitignore/env-vars discipline alag se chahiye.

</details>

5. Pehli live order se pehle ke 6 safety steps?

<details>
<summary>Sample Jawab</summary>

**Jawab:** (1) Demo/paper account pe poora flow test, (2) minimum quantity (1 lot/share), (3) idempotency guard — duplicate signals pe double order block, (4) position state tracking + recovery plan (server restart scenario), (5) kill switch ready — sab positions flatten karne wala script, (6) full logging — har request/response record. In ke bina live jaana = blindfolded driving.

</details>
