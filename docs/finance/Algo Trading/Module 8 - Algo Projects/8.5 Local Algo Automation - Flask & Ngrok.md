## Login Ek Baar, Token Reuse

Broker pe login karke **access token** milta hai — isi token se saari orders jaati hain. Design decision jo original session ne explicitly AI se banwaya:

> *"Make my login file separate so that we need to login first time only."*

| Ek hi file mein sab | login.py alag |
|---|---|
| Har order se pehle login | Login sirf ek baar |
| 100 orders = 100 logins ❌ | 1 token → sab jagah reuse ✅ |
| Slow + rate-limit risk | Fast — jaise app mein ek baar login |

```python
# login.py
import dhanhq                    # 3.10 wali library!
from api_data import API_KEY, SECRET

dhan = dhanhq(API_KEY, SECRET)   # client ready — token internally manage
```

⚠️ Production note: tokens expire hote hain (din badle toh re-login). Bot jo hafton chalega, usme token-expiry handling add karna padega — catch error → fresh login → retry.

## Order Test — Pehle Manual

### Square-Off Rule

> **Same quantity ka opposite order = square off.** BUY 1 kiya → SELL 1 lagao → position zero. (BUY 1, SELL 2 mat lagana — doosri position ban jayegi!)

Ek detail: har order mein alag **order reference ID** — conflict avoid karne ke liye. (Baad mein pata chala ki yeh optional hai — phir bhi dena achhi practice hai.)

## What It Is NOT

- ❌ **Local automation = production system nahi.** Laptop sleep/band/ngrok-restart = bot dead ya unreachable. Session-testing rig hai; 24x7 ke liye cloud chahiye (agli file!).
- ❌ **Position +1 dikhna = strategy working nahi.** Sirf PIPELINE verify hua hai (signal→order). Profitability alag sawaal hai — uska jawab backtest + forward-test metrics denge.
- ❌ **api_data.py = complete security nahi.** Keys main-code se alag zaroor hain, par yeh file khud git mein ja sakti hai (7.3!). Complete setup: .env + .gitignore + env-vars. Layered security hoti hai, single-file trick nahi.

1. login.py alag kyun — "100 orders = 100 logins" problem samjhao?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Har broker call authentication maangti hai. Naive design: har order function ke andar full login flow (credentials → token) — matlab har trade pe re-authentication: slow, rate-limit trigger karne wala, aur credentials baar-baar handle ho rahi. Better: login.py ek baar client/session bana ke export karta hai; orders.py usko import karta hai. Token reuse hota hai jab tak expire na ho. App-analogy: app kholte waqt ek baar login, phir har action pe nahi.

</details>

2. Square-off verification rule ("pehle check position exists") kyun important?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Kyunki duplicate/garbled alerts real hain (15-sec candle incident!). Agar long-exit alert aaya jab koi long THA HI NAHI (already closed, ya entry miss hua), blind square-off SELL lagayega — aur woh NAYI SHORT position ban jayegi! Ab tu unintended direction mein exposed hai. Verification (position check before exit-order) system ko state-aware banata hai: exit-without-position = no-op, not accident.

</details>

3. 15-second candle problem ka root cause aur 2-level fix?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Root cause: ultra-short TF pe ek hi candle window mein multiple conditions true hoti hain — entry AUR exit dono alerts same candle se fire. System sequential processing ke liye bana hai, burst handling nahi. Fixes: (1) Strategy level: realistic TF use karo (5-min) — signals sparse rahenge; HFT infra chahiye hi nahi. (2) Code level: idempotency guard — per-symbol last-signal timestamp/candle-id track karo; same-candle repeat signal ignore. Dono levels milake robust banta hai.

</details>
