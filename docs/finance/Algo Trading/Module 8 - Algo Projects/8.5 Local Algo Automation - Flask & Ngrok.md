**In Your Own Words**

1. Why separate login.py — "100-orders = 100-logins" problem?

<details>
<summary>Sample Answer</summary>

**Answer:** Every-broker-call needs AUTHENTICATION. Naive-design: full-login-flow (credentials→token) INSIDE every order-function — meaning re-AUTHENTICATION on every trade: slow, rate-limit-triggering, credentials handled repeatedly! Better: login.py creates client/session ONCE and EXPORTS; orders.py IMPORTS it. Token-REUSED until-expire. App-analogy: login ONCE when opening app; not before every action!

</details>

2. Square-off VERIFICATION-rule ("check-position-exists-first")?

<details>
<summary>Sample Answer</summary>

**Answer:** Because duplicate/garbled-alerts are REAL (15-sec-candle-incident!). If long-exit-alert comes when NO-long-existed (already-closed, or entry-missed!), blind-square-off SELL placed — creating NAYI-SHORT-position!! Now UNINTENDED-direction exposure! Verification (position-check-before-exit-order) makes system STATE-AWARE: exit-without-position = NO-OP, not ACCIDENT!

</details>

3. 15-second-candle problem root-cause + 2-level fix?

<details>
<summary>Sample Answer</summary>

**Answer:** Root-cause: on ultra-short-TF, MULTIPLE-conditions become true in SAME-candle-window — entry AND exit both alert from SAME-candle! System built for sequential-processing, not BURST-handling! Fixes: (1) STRATEGY-level: use realistic-TF (5-min) — signals stay SPARSE; no HFT-infra needed. (2) CODE-level: idempotency-guard — track per-symbol last-signal-TIMESTAMP/candle-ID; ignore same-candle-repeat. Both-levels together = ROBUST!

</details>

4. Why Dhan specifically chosen (unnamed in original)?

<details>
<summary>Sample Answer</summary>

**Answer:** REPRODUCIBILITY! Unnamed-broker + "docs-confusing-jugaad" = student can't REPLICATE anything!! Dhan already-covered in course (3.10): library (dhanhq), auth-style, API-patterns all match PAST-knowledge — ZERO-new-learning-overhead! General-principle: build projects on KNOWN-tools; introduce new-tool SEPARATELY. And if docs-confusing — find community/examples — jugaad should be SYSTEMATIC!

</details>

5. "Automation-skills ≠ profitable-strategy" separation WHY?

<details>
<summary>Sample Answer</summary>

**Answer:** Because VALIDATIONS are DIFFERENT! Automation-test: PIPELINE-integrity — signal-came? order-went? fill-happened? logs-clean? (technical-QA). Strategy-test: expectancy, drawdown, multi-regime-survival (statistical-QA, M4-5!). MIXING causes CONFUSION: seeing automated-bot running, thinking "system-running = money-making" — WRONG! Perfectly-automated LOSING-strategy possible!! Prove BOTH separately, THEN combine!

</details>
