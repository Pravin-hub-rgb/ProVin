## Step 1 — Pehle Direct Order Test (Bina TradingView Ke)

Sabse smart approach: pipeline ke tukdon ko ALAG test karo. Pehle seedha Python se order:

```python
import os
from dotenv import load_dotenv
from delta_rest_client import DeltaRestClient

load_dotenv()

client = DeltaRestClient(
    base_url="https://api.india.delta.exchange",   # demo/testnet ke liye alag URL hota hai!
    api_key=os.getenv("DELTA_KEY"),
    api_secret=os.getenv("DELTA_SECRET"),
)

# Product ID dhundo — symbol se ID map karna zaroori hota hai
products = client.get_products()
btc = [p for p in products if p["symbol"] == "BTCUSD"]
product_id = btc[0]["id"]
print(f"BTCUSD product_id: {product_id}")
```

⚠️ Ek subtlety jo beginners miss karte hain: `size` parameter **contract size** mein hota hai, coins mein nahi — BTCUSD perp ka 1 contract = 0.001 BTC type. Docs check karke qty calculate karo.

Ab test orders:

```python
# BUY
client.place_order(product_id=product_id,
                   side="buy",
                   order_type="market_order",
                   size=1)

# ...check demo wallet... ab close:
client.place_order(product_id=product_id,
                   side="sell",
                   order_type="market_order",
                   size=1)
```

BUY place hua? Demo wallet mein position dikhi? Client working hai ✅ — ab signals jodte hain.

## Step 3 — Python Backend

Flask server chahiye jo alerts receive kare aur orders fire kare. AI prompt:

```text
Build me a Python Flask server that receives alert messages from
TradingView. When a BUY alert comes, place a BUY market order on
Delta Exchange. When a SELL alert comes, FIRST close any existing
BUY position, then place the SELL order.
```

AI ne do files diye — Module 7 ka architecture exactly:

| File | Kaam |
|---|---|
| `server.py` | Flask webhook route — alert receive + parse |
| `main.py` | Order logic — BUY/SELL/close-position calls |

**Run flow (4 terminals/processes):**

```text
1. python server.py        → localhost:5000 pe live
2. ngrok http 5000         → public URL mila (e.g., https://abc.ngrok.app)
3. TradingView alert create → Webhook URL field mein ngrok URL paste
   ⚠️ Message box EMPTY rakho! (code ka alert() khud bhejta hai)
4. Signal aaya? Alert → tunnel → Flask → orders.py → Delta 🚀
```

## Troubleshooting — Teen Real Errors

**Error 1: "Alert received but Delta pe kuch nahi hua"**
Server ne message receive kiya par order nahi laga. Root cause: alert **message box mein kuch likha tha** — usne code ke dynamic message ko OVERRIDE kar diya! Fix: **message box empty rakho** — `alert()` function khud signal info bhejta hai.

**Error 2: Pine v4 "can't do that"**
Dynamic alert message v4 mein allowed nahi. Fix: AI se v5 upgrade prompt (upar).

**Error 3: "Server rejected request"**
Checklist: IP whitelist mein current IP hai? product_id sahi hai? order_type valid? Terminal logs padho — server.py ka console error batata hai.

## Safety Gaps Jo Original Build Mein Rahi — Tu Better Banna

Original session mein yeh cheezein gloss ho gayi thin — production ke liye address karni zaroori hain:

1. **Position state memory:** server restart hua toh usko nahi pata rahega ki position open thi — orphaned exposure! Fix: startup pe broker se positions fetch karo (`get_positions()`), state file/db maintain karo.
2. **Duplicate alerts:** fast candles pe TradingView multiple alerts fire karta hai — double orders! Fix: idempotency guard (7.1) — same-candle second signal ignore.
3. **Demo vs real URL:** `api.india.delta.exchange` (demo) vs real endpoint alag hota hai — switch karte waqt env var hi badlo, code nahi.
4. **ngrok URL rotation:** restart pe URL badla = TradingView settings update. Cloud deployment iska permanent fix hai (agli files).

## Nutshell

Full pipeline live: Pine indicator (single combined alert via `alert()`, v5) → TradingView webhook → ngrok tunnel → Flask `server.py` → order logic `main.py` → Delta demo orders (delta-rest-client, market_order, product_id mapping). Testing philosophy: har layer alag test karo (pehle direct Python order!). Top troubleshooting: empty-message-box rule, v4→v5 upgrade, IP whitelist checks. Flip logic (sell = close-buy-first) standard pattern hai. Production gaps: position state recovery, dedup guard, env-based URLs.

## What It Is NOT

- ❌ **Demo account = kamzor testing nahi.** Delta demo same matching engine/API structure use karta hai — sirf wallet virtual hai. Pipeline ki har mechanical cheez yahin verify ho sakti hai. Real money ka step sirf capital risk ka hai.
- ❌ **Indicator working = strategy profitable nahi.** Yeh project prove karta hai ki SIGNALS orders tak pahunchte hain (execution works). Ki signals PAISA banate hain woh backtest/forward-test ka sawaal hai (Module 4-5) — dono alag validations hain.
- ❌ **Local setup = production nahi.** Laptop band = bot dead; ngrok URL unstable; IP whitelist fragile. Yeh learning rig hai — 24x7 ke liye cloud deployment chahiye (aage aa raha hai).

2. "Alert message box EMPTY rakho" — kyun?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Kyunki script ke andar `alert()` function dynamically message generate karta hai (buy/sell info ke saath). TradingView alert UI ka message box usko override kar deta hai — jab tumne box mein static text likha, wohi static text gaya, dynamic buy/sell info NAHI gayi. Server parse nahi kar paya → no order. Rule: dynamic-alert scripts ke saath box empty; static alerts mein box hi message source hota hai.

</details>

3. Server restart hone pe kya problem ho sakti hai? Fix?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Problem: in-memory position state lost — server ko nahi pata open BUY position thi. Agar ab SELL alert aaya jiska handler "close existing BUY first" hai, woh position dhundh hi nahi payega ya assumptions galat — orphaned exposure risk. Fixes: (1) startup pe `get_positions()` call karke state rebuild, (2) state ko file/database mein persist karo har trade ke baad, (3) broker ko source-of-truth maano — apni copy sirf cache hai.

</details>

4. Demo pe test karne ke baad real account pe shift kaise hogi (safe tareeke)?

<details>
<summary>Sample Jawab</summary>

**Jawab:** (1) Env vars mein base_url + keys change karo — code untouched (isliye config-driven design!). (2) Real keys ke liye fresh API key generate karo, IP whitelist update. (3) Pehle MINIMUM size pe manual trigger test (requests se khud POST). (4) Kill-switch ready + logs watch. (5) Chhote capital se forward-test period. Demo→real jump mechanical hona chahiye (config flip), behavioral nahi (naya untested code nahi!).

</details>

5. Flip logic (SELL = close-BUY-then-SELL) kyun zaroori hai simple SELL se?

<details>
<summary>Sample Jawab</summary>

**Jawab:** Kyunki crypto perps mein SELL order do matlab ho sakte hain: (a) existing long CLOSE karo, (b) NAYI short position open karo. Naive SELL bhejoge jab long open hai toh broker netting ke hisaab se behave karega — tumhare intended "flip" ki jagah sirf partial close ya unexpected netting ho sakta hai. Explicit sequence (close-long THEN open-short) deterministic hai — har state transition tumhare control mein, audit-friendly bhi.

</details>
