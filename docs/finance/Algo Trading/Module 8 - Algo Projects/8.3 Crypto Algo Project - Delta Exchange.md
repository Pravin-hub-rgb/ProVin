## Troubleshooting — Three REAL Errors!

### Error 1: "Alert received but nothing happened on Delta!"

Server received message but order NOT placed!

**Root-cause:** something written in alert-message-box —

it OVERRIDED code's dynamic-message!!

**Fix:** ⚠️ **KEEP MESSAGE-BOX EMPTY!**

`alert()` function itself sends signal-info!

(This error so-common every crypto-bot-builder faces it!)

### Error 2: Pine-v4 "can't do that"

Dynamic-alert-message not allowed in v4.

Fix: AI v5-upgrade-prompt (above!).

**In Your Own Words**

1. Trace complete pipeline — signal to order!

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Pine-indicator detects condition on chart → `alert()` fires dynamic-message ('buy'/'sell'). (2) TradingView-alert POSTs to configured-webhook-URL. (3) URL is ngrok's public-HTTPS → tunnel → laptop-port-5000. (4) Flask server.py route receives+parses. (5) main.py takes action: BUY→market-order; SELL→first-close-open-BUY-then-SELL. (6) delta-rest-client signed-API-call → Delta → order-placed, wallet-update!

</details>

2. Why "keep alert-message-box EMPTY"?!

<details>
<summary>Sample Answer</summary>

**Answer:** Because script's `alert()` function itself generates dynamic-message (with buy/sell-info)! TradingView-alert-UI's message-box OVERRIDES it — when you write static-text in box, THAT-static-text goes, not dynamic buy/sell-info! Server can't parse → no-order! Rule: with dynamic-alert-scripts keep box-EMPTY; with static-alerts box itself is message-source!

</details>

3. Server-restart problem? Fix?

<details>
<summary>Sample Answer</summary>

**Answer:** Problem: in-memory position-state LOST — server doesn't know open-BUY-position existed! If SELL-alert comes whose handler is "close-existing-BUY-first", it can't find position OR wrong assumptions → orphaned-exposure-risk! Fixes: (1) on startup call get_positions() to REBUILD state, (2) PERSIST state in file/database after every trade, (3) treat BROKER as source-of-truth — your copy is only CACHE!

</details>

4. Demo→real shift safely how?

<details>
<summary>Sample Answer</summary>

**Answer:** (1) Change base_url + keys in env-vars — code UNTOUCHED (config-driven-design!). (2) Generate FRESH-API-key for real + update IP-whitelist. (3) First MANUAL-trigger test at MINIMUM-size (POST yourself via requests). (4) Kill-switch ready + logs-watch. (5) FORWARD-test-period with small-capital. Demo→real jump should be MECHANICAL (config-flip!), not BEHAVIORAL (no new untested-code!).

</details>

5. Why flip-logic (SELL = close-buy-then-sell) necessary vs simple-SELL?

<details>
<summary>Sample Answer</summary>

**Answer:** In crypto-perps SELL-order has TWO meanings: (a) close existing-long, (b) OPEN new-short-position! Naive-SELL when long-open → broker behaves per NETTING rules — intended "flip" becomes partial-close or unexpected-netting! Explicit-SEQUENCE (close-long THEN open-short) is DETERMINISTIC — every state-transition under your-control, audit-friendly too!

</details>
